## 탄생 배경: Inbox Search로 드러난 RDB의 한계

2007~2008년은 페이스북 사용자 수가 수천만에서 수억으로 급격히 늘어나던 시기였다. 이때 사내에서 다루기 까다로운 기능이 하나 있었다. 바로 **Inbox Search**로, 사용자가 자신이 주고받은 모든 쪽지(메시지)에서 단어나 상대방 이름으로 검색하는 기능이었다.

이 워크로드의 특성을 RDB 엔지니어의 관점에서 살펴보자.

- **쓰기가 매우 많다.** 메시지가 하나 오갈 때마다 역색인(reverse index) 엔트리가 여러 개 쌓인다. 단어 → (사용자, 메시지) 매핑이 수십억 건으로 늘어난다.
- **데이터가 거대하다.** 수억 명의 사용자가 수년 동안 주고받은 메시지를 저장해야 한다. 단일 MySQL 인스턴스의 디스크와 메모리로는 감당할 수 없다.
- **항상 켜져 있어야 한다.** 페이스북은 글로벌 서비스이므로 "점검 시간"에 검색이 멈추면 안 된다.
- **지리적으로 분산되어 있다.** 처음에는 미국 서부와 동부, 나중에는 여러 대륙에 걸쳐 있었다. 데이터센터(datacenter) 하나가 통째로 죽어도 서비스는 계속 동작해야 한다.

당시의 일반적인 해법은 **MySQL 샤딩(sharding)** 이었다. user_id를 해시해서 수백 대의 MySQL에 나누어 저장하는 방식이다. 하지만 이 방식은 운영 부담이 매우 크다.

> [!note] RDB였다면
> 샤드를 추가할 때마다 데이터를 재분배(resharding)해야 하고, 그동안 애플리케이션은 "어느 샤드에 무엇이 있는지"를 알려 주는 매핑 테이블을 관리해야 한다. 마스터(master)가 죽으면 수동으로 페일오버(failover)해야 한다. 누군가 새벽에 일어나 슬레이브를 마스터로 승격시켜야 하고, 그 사이 쓰기는 멈춘다.
>
> 데이터센터 간 복제는 비동기 슬레이브로 흉내 낼 수 있지만, 마스터가 한 곳에만 있으므로 다른 대륙의 쓰기도 결국 한 곳으로 모인다. 즉 **단일 장애점(SPOF, Single Point of Failure)이 구조 자체에 들어 있다.**

페이스북은 이 문제를 풀기 위해 **Avinash Lakshman**과 **Prashant Malik**에게 새 저장소 개발을 맡겼다. 여기서 눈여겨볼 점이 하나 있다. Avinash Lakshman은 바로 전에 **Amazon에서 Dynamo 논문의 공저자**였다.

Dynamo는 아마존 장바구니(shopping cart)를 위해 만든 분산 키-값 저장소로, "쓰기를 절대 거부하지 않는" 것을 목표로 했다. 그는 Dynamo의 분산 운영 방식이 뛰어나다는 것을 알고 있었지만, Dynamo는 단순한 키-값 모델이어서 Inbox Search처럼 다양한 질의가 필요한 기능에는 부족했다.

그래서 그는 두 방식을 합치기로 했다. **Dynamo의 분산 인프라에 BigTable의 데이터 모델을 결합한 것**이 Cassandra의 기본 구조다. 이름에도 의미가 있다. 카산드라(Cassandra)는 그리스 신화에서 "아무도 믿지 않는 예언자"이다. 이 이름에 오라클(Oracle, RDB의 대표 제품)에 대한 가벼운 농담이 섞여 있다는 해석도 있다.

**타임라인**:

```text
2007  Amazon, Dynamo 논문 발표 (Lakshman 공저)
2008  Facebook, Cassandra 사내 개발 → 7월 오픈소스로 공개
2009  Apache Incubator 입성
2010  Apache Top-Level Project로 졸업 (정식 Apache 프로젝트)
2010~ DataStax 설립, 상용 지원·CQL 등장
2015  Cassandra 3.x — Storage Engine 재작성, Materialized View
2021  Cassandra 4.0 — 안정성·성능, 내부 정리
2024  Cassandra 5.0 — SAI, UCS, Vector Search, JDK 17 (9월 GA, 이 노트의 기준)
```

흥미롭게도 정작 페이스북은 나중에 Inbox Search/Messages를 **HBase로 옮겼다.** 그런데도 Cassandra는 오픈소스 커뮤니티와 Netflix, Apple, Instagram, Uber 등의 지원을 받으며 독립적으로 성장했다.

공개된 발표에 따르면 Apple은 10만 개가 넘는 노드로 Cassandra를 운영한다(2014년 Summit에서 75,000노드/10PB, 2015년에 10만+ 노드로 언급). Cassandra가 실제로 검증된 곳은 페이스북이 아니라, 그 뒤에 Cassandra를 도입한 대규모 운영 현장이었다.

## 두 계보의 결합: Dynamo의 인프라와 BigTable의 데이터 모델

Cassandra를 한 문장으로 정의하면 **"Dynamo의 인프라 위에 BigTable의 데이터 모델을 얹은 것"** 이다. 이 문장을 제대로 이해하면 Cassandra의 설계 결정 대부분을 여기서 이끌어 낼 수 있다. 두 계보를 나누어 살펴보자.

### Dynamo에서 물려받은 것: 어떻게 분산하고, 장애를 어떻게 견디는가

Dynamo는 데이터를 어디에 두고, 어떻게 복제하고, 노드가 죽었을 때 어떻게 견디는지를 정한 설계도이다. Cassandra는 이 설계를 거의 전부 가져왔다.

| Dynamo 기술 | 무엇을 하나 | Cassandra에서의 모습 |
|---|---|---|
| **Consistent Hashing** | 키를 토큰 링(token ring) 위에 배치, 노드 추가/제거 시 일부만 이동 | 파티션 키 해시 → 토큰 → 담당 노드 결정 ([[02 - 분산 아키텍처]]) |
| **Replication** | 데이터를 N개 노드에 복제 | 복제 계수(replication factor, RF), 링 위 다음 노드들에 사본 ([[03 - 복제 전략과 데이터센터]]) |
| **Gossip Protocol** | 노드들이 서로의 상태를 잡담하듯 전파 | 매초 gossip, 마스터 없이 클러스터 멤버십·상태 동기화 |
| **Hinted Handoff** | 죽은 노드 몫의 쓰기를 살아있는 노드가 잠시 보관 | 노드 복귀 시 힌트(hint) 전달, "항상 쓰기 가능" 보장 |
| **Eventual Consistency** | 지금 당장은 아니어도 결국 같아진다 | Tunable consistency로 일관성 수준을 쿼리마다 선택 ([[04 - Tunable Consistency]]) |
| **Read Repair / Anti-Entropy** | 읽을 때·주기적으로 사본 간 불일치 보정 | read repair + Merkle tree 기반 repair |
| **Masterless (P2P)** | 모든 노드가 동등, 리더 없음 | 어느 노드든 코디네이터(coordinator)가 될 수 있음 |

이 가운데 가장 중요한 것은 마지막 줄의 **마스터리스**다. Dynamo와 Cassandra에는 마스터, 프라이머리, 리더가 없고, 모든 노드가 완전히 동등하다(peer-to-peer). 클라이언트의 요청을 받은 노드가 어느 것이든 그 요청의 "코디네이터" 역할을 임시로 맡는다. 코디네이터는 데이터가 실제로 저장된 노드들에게 작업을 나누어 주고 결과를 모은다.

마스터가 없으므로 "마스터가 죽으면 어떻게 되는가?"라는 질문 자체가 성립하지 않는다. Cassandra에 **단일 장애점이 없다(no SPOF)** 고 말하는 근거가 바로 이것이다.

### BigTable에서 물려받은 것: 데이터를 어떻게 모델링하고 디스크에 어떻게 기록하는가

Dynamo는 단순한 키-값 저장소였다. 키 하나에 내용을 알 수 없는(opaque) 값 하나가 대응하는 구조여서, 검색처럼 다양한 질의를 처리하기에는 모델이 너무 단순했다. 그래서 Cassandra는 데이터 모델과 저장 엔진을 **Google BigTable**에서 가져왔다.

| BigTable 기술 | 무엇을 하나 | Cassandra에서의 모습 |
|---|---|---|
| **Column-Family 데이터 모델** | 행(row) 안에 동적인 컬럼들, 희소(sparse) 저장 | 파티션(partition) + 클러스터링된 행, wide row ([[05 - 데이터 모델링 1 - Query First]]) |
| **Commit Log** | 쓰기를 먼저 순차 로그에 적어 내구성 보장 | commitlog, 크래시 복구의 기반 ([[10 - Write Path와 Read Path]]) |
| **Memtable** | 메모리 안의 정렬된 쓰기 버퍼 | memtable, 5.0은 trie 기반 메모리 인덱스 |
| **SSTable** | 불변(immutable) 정렬 파일로 디스크에 플러시 | SSTable, 한 번 쓰면 절대 수정 안 함 ([[08 - Storage Engine 내부]]) |
| **LSM-Tree** | 쓰기를 순차 append로 변환, 나중에 병합 | LSM(Log-Structured Merge) + compaction ([[09 - Compaction 전략]]) |

BigTable 계보의 핵심은 **LSM-Tree(Log-Structured Merge Tree)** 라는 저장 방식이다. RDB의 B-Tree는 데이터를 "제자리(in place)"에서 수정한다. 디스크에서 특정 페이지를 찾아가 그 자리를 덮어쓰므로 랜덤 I/O(random write)가 발생한다.

반면 LSM-Tree는 **모든 쓰기를 메모리(memtable)에 모았다가 한꺼번에 순차적으로(sequential write) 디스크의 새 파일에 기록한다.** 기존 파일은 절대 수정하지 않으며, 수정과 삭제도 "새로운 사실을 추가하는 것"으로 표현한다.

```text
[RDB / B-Tree]                  [Cassandra / LSM-Tree]
쓰기 = 디스크 특정 위치 수정      쓰기 = 메모리에 추가 → 나중에 순차 flush
랜덤 I/O (느림)                  순차 I/O (빠름)
제자리 갱신 (in-place update)    불변 파일 (immutable, append-only)
읽기 빠름, 쓰기 비쌈             쓰기 빠름, 읽기는 여러 파일 병합 필요
```

이 선택 하나 때문에 Cassandra는 **쓰기 최적화(write-optimized)** 데이터베이스가 된다. Inbox Search처럼 쓰기가 폭발적으로 많은 워크로드에 LSM-Tree가 적합했던 이유도 여기에 있다.

대신 치러야 할 비용도 있다. 논리적인 행 하나가 여러 SSTable에 흩어져 있을 수 있으므로, 읽을 때는 여러 파일을 찾아서 병합해야 한다. 그래서 Cassandra의 읽기 경로에는 bloom filter, partition index, key cache 같은 장치가 많이 붙어 있다. 이 메커니즘은 8장(Storage Engine 내부)과 10장(Write Path와 Read Path)에서 자세히 다룬다.

> [!note] 직관 하나
> Cassandra에서 `DELETE`는 데이터를 지우지 않는다. **"이 데이터는 삭제됨"이라는 표식(tombstone, 툼스톤)을 새로 추가**할 뿐이다. 불변 파일에서는 무언가를 지울 수 없으므로, 삭제도 추가로 표현하는 것이다. 이 특성 때문에 나중에 "삭제를 많이 하면 오히려 읽기가 느려지는" 직관에 어긋나는 함정이 생긴다([[06 - 데이터 모델링 2 - 고급 타입과 안티패턴]]).

## CAP 정리를 정확하게: Cassandra는 정말 "AP"인가?

분산 데이터베이스를 이야기할 때 거의 빠짐없이 인용되는 것이 **CAP 정리(CAP theorem)** 다. Eric Brewer가 2000년에 제시했고, Gilbert와 Lynch가 2002년에 증명했다. 그런데 이 정리는 거의 항상 **부정확하게** 인용된다. "셋 중 둘만 고를 수 있다"는 표현은 절반쯤 틀렸다. 정확하게 정리해 보자.

### C, A, P의 정확한 정의

- **C (Consistency, 일관성)**: 여기서 말하는 일관성은 RDB ACID의 'C'가 아니라 **선형성(linearizability)** 에 가깝다. 모든 읽기는 가장 최근에 완료된 쓰기를 보거나, 에러를 받는다. 클라이언트 입장에서는 마치 단일 노드가 요청을 순서대로 처리하는 것처럼 보인다.
- **A (Availability, 가용성)**: 장애가 없는 모든 노드는 모든 요청에 (유한한 시간 안에) **에러가 아닌 정상 응답**을 반환한다. "느리더라도 응답한다"가 아니라 "반드시 응답한다"는 뜻이다.
- **P (Partition tolerance, 분단 내성)**: 네트워크가 노드 그룹 사이의 메시지를 임의로 잃어버리거나 지연시켜도(즉 네트워크 분단이 일어나도) 시스템이 계속 동작한다.

여기서 놓치지 말아야 할 점이 있다. **P는 선택할 수 있는 항목이 아니다.** 여러 대의 머신을 네트워크로 묶는 순간, 네트워크 분단은 "일어날 수도 있는 일"이 아니라 "반드시 일어나는 일"이 된다. 스위치가 죽고, 케이블이 끊기고, GC 때문에 노드가 잠깐 멈추기도 한다.

따라서 실제 분산 시스템이 고를 수 있는 것은 "P를 포기할 것인가"가 아니다. **"분단이 일어났을 때(P를 유지해야 할 때) C와 A 중 무엇을 희생할 것인가"** 이다.

```text
        네트워크 분단(partition) 발생!
        노드 X와 노드 Y가 서로 대화 불가
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
   [CP를 택함]              [AP를 택함]
   일관성 유지를 위해        가용성 유지를 위해
   소수파(또는 양쪽)         양쪽 다 응답은 하되,
   요청을 거부(에러)         잠시 서로 다른 값을 볼 수 있음
        │                       │
   "틀린 답 줄 바엔          "오래된 답이라도
    응답 안 함"               응답은 함"
```

### Cassandra가 "AP"로 분류되는 이유와, 그 분류가 절반만 맞는 이유

Dynamo 계보를 그대로 물려받은 Cassandra의 **기본 성향**은 **AP**다. 네트워크 분단이 일어나도 양쪽 파티션이 모두 읽기와 쓰기를 받아들인다. 노드 하나가 죽거나 데이터센터 하나가 통째로 단절되어도, 남은 노드들은 계속 요청에 응답한다. "항상 쓰기 가능(always writable)"이라는 슬로건이 바로 이 AP 성향을 나타낸다.

하지만 여기서 멈추면 Cassandra를 절반만 이해한 것이다. **Cassandra의 일관성은 쿼리마다 조정할 수 있다(tunable consistency).** 클라이언트는 읽기와 쓰기마다 **일관성 수준(consistency level, CL)** 을 지정한다. 정족수(quorum) 규칙을 이용하면 쿼리 하나를 사실상 CP처럼 동작시킬 수도 있다.

이를 결정하는 부등식은 다음과 같다.

```text
W + R > RF  ⇒  강한 일관성(읽기가 항상 최신 쓰기를 봄)

W  = 쓰기가 성공으로 간주되기 위해 응답해야 하는 사본 수 (write CL)
R  = 읽기가 모아야 하는 사본 수 (read CL)
RF = 복제 계수(replication factor)
```

예를 들어 RF=3에서 쓰기와 읽기를 모두 `QUORUM`(과반수 = 2)으로 수행하면 다음과 같다.

```text
W=2, R=2, RF=3  →  2 + 2 = 4 > 3  ✓
```

이때 읽기가 모은 사본 2개 가운데 적어도 하나는 마지막 쓰기를 반영한 노드와 반드시 겹친다(비둘기집 원리). 따라서 이 쿼리는 **강한 일관성**을 보장하며, 이 쿼리에 한해서는 Cassandra가 **CP처럼** 동작한다. 분단 때문에 정족수를 모으지 못하면 쿼리는 실패한다. 가용성을 희생하는 것이므로, 정확히 CP의 동작이다.

여기서 한 가지를 분명히 해 두자. `W+R>RF`가 보장하는 "강한 일관성"은 **"마지막으로 성공한 쓰기를 읽는다"(read-your-writes·monotonic read)** 수준이며, 완전한 **선형성(linearizability)** 은 아니다. Cassandra의 쓰기는 사본들 사이에서 **격리(isolation)되지 않기 때문**이다.

QUORUM 쓰기가 진행되는 도중에 들어온 QUORUM 읽기는, 아직 정족수에 도달하지 못해 기록이 끝나지 않은 값을 부분적으로 볼 수 있다(쓰기가 결국 성공할지 실패할지 모르는 상태에서도 노출될 수 있다). 또 동시에 들어온 쓰기는 합의(consensus)가 아니라 **셀 타임스탬프 기반 last-write-wins**로 정리된다.

그래서 "읽고 → 조건 비교 → 갱신"(compare-and-set)처럼 **진짜 선형성**이 필요한 연산에는 QUORUM만으로는 부족하다. 이런 연산에는 별도의 합의 프로토콜인 LWT(`SERIAL`/`LOCAL_SERIAL`, Paxos)를 써야 한다([[11 - LWT Batch Counter 내부]]). QUORUM은 "최신값 읽기"를 보장하지만, "원자적 read-modify-write"는 보장하지 않는다.

반대로 CL을 `ONE`으로 낮추면 다음과 같다.

```text
W=1, R=1, RF=3  →  1 + 1 = 2 > 3 ?  ✗

→ 강한 일관성 보장 없음. 가장 빠르고, 거의 항상 쓰기/읽기 성공.
  하지만 방금 쓴 값을 다른 노드에서 읽으면 아직 못 볼 수 있음(AP).
```

> [!warning] 흔한 오해
> "Cassandra는 AP이므로 강한 일관성을 제공하지 못한다." → **틀렸다.** Cassandra는 **시스템 전체로 보면 AP 성향**이지만, **쿼리 단위로 일관성 수준을 선택**할 수 있으므로 특정 쿼리를 CP처럼 만들 수 있다. CAP은 "시스템 전체에 영구히 붙는 라벨"이 아니라 "분단 상황에서의 동작"을 말하며, Cassandra는 그 동작을 **쿼리마다** 바꾼다.
>
> 이 미묘한 차이가 Cassandra를 배울 때 가장 까다로운 부분이다. W/R/CL/RF의 모든 조합은 4장(Tunable Consistency)에서 자세히 살펴본다.

한 가지 더 분명히 해 두자. CL이 같더라도 이 보장은 **단일 파티션의 단일 행**에 대해서만 성립한다. Cassandra는 여러 파티션이나 여러 행에 걸친 원자성(atomicity)과 격리(isolation)를 일반적으로 제공하지 않는다. 이런 보장이 필요하면 경량 트랜잭션(LWT, Lightweight Transaction)이라는 별도의 무거운 메커니즘을 써야 한다(11장 LWT Batch Counter 내부).

### PACELC: CAP이 말하지 않는 나머지 절반

CAP의 가장 큰 한계는 **"분단이 일어났을 때"만** 다룬다는 점이다. 그런데 분단은 드물고, 시스템은 **대부분의 시간을 분단 없이** 보낸다. CAP은 이 평상시의 트레이드오프에 대해서는 아무것도 알려 주지 않는다.

이 문제에 답하는 것이 **PACELC**(Daniel Abadi, 2012)다. 읽는 방법은 다음과 같다.

```text
PAC ELC
 │  │
 │  └─ Else (분단이 없을 때): Latency(지연) vs Consistency(일관성)
 │
 └──── if Partition (분단이 있을 때): Availability vs Consistency  ← 이게 곧 CAP
```

풀어 쓰면 **"분단(P)이 일어나면(if) 가용성(A)과 일관성(C) 중 하나를 택하고, 그렇지 않으면(Else) 지연(L)과 일관성(C) 중 하나를 택한다"** 는 뜻이다.

Cassandra는 PACELC로 분류하면 **PA/EL** 이다.

- **PA**: 분단 시 가용성을 택한다(앞에서 본 AP 성향).
- **EL**: **분단이 없는 평상시에도, 더 강한 일관성을 얻으려고 더 많은 사본의 응답을 기다리면 그만큼 지연이 늘어난다.** `CL=ONE`은 빠르지만 일관성이 약하고, `CL=ALL`은 느리지만 일관성이 강하다. 분단이 없어도 이 트레이드오프는 모든 쿼리에 적용된다.

실무에서 더 자주 마주치는 트레이드오프는 이 EL 쪽이다. 멀티 데이터센터 환경에서 `LOCAL_QUORUM`을 쓸지 `EACH_QUORUM`을 쓸지 고르는 일이 바로 "평상시 지연과 일관성" 사이의 균형을 정하는 일이다. 결제 시스템이라면 이 균형을 어디에 두느냐에 따라 사용자 경험과 데이터 정합성의 균형이 정해진다.

비교하자면 전통적인 RDB(단일 마스터)는 **PC/EC**다. 분단 시에도, 평상시에도 일관성을 택하고, 그 대신 가용성과 지연을 희생한다. DynamoDB는 Cassandra처럼 PA/EL 성향이지만, 강한 일관성 읽기 옵션을 제공한다.

## 설계 철학: 네 가지 원칙

지금까지의 내용을 설계 철학의 관점에서 정리하면 네 가지 원칙이 보인다. 이 원칙들은 서로를 뒷받침한다.

### 원칙 1: Masterless (단일 장애점 제거)

모든 노드가 동등하며, 리더 선출도 마스터 페일오버도 없다. 어느 노드든 클라이언트 요청의 코디네이터가 될 수 있고, 데이터는 토큰 링 위에 나뉘어 RF만큼 복제된다.

```text
        Node A ───── Node B
          │  ╲      ╱  │
          │   ╲    ╱   │       ← 완전 P2P 메시 (gossip)
          │    ╲  ╱    │          마스터 없음. 누가 죽어도
        Node E   ╳   Node C       남은 노드가 계속 응답.
          │    ╱  ╲    │
          │   ╱    ╲   │
          └ Node D ────┘
```

> [!note] RDB였다면 vs Cassandra
> MySQL 마스터-슬레이브 구성에서 마스터가 죽으면, 페일오버 도구(Orchestrator 등)가 슬레이브를 승격시키는 동안 **쓰기가 멈춘다**(수초~수분). Cassandra에는 노드 하나가 죽어도 "승격"이라는 개념 자체가 없다. 그 노드가 맡던 데이터는 이미 다른 노드에도 복제되어 있으므로, 코디네이터는 살아 있는 사본에 요청을 보낸다.
>
> 죽은 노드가 받아야 할 쓰기는 hinted handoff로 잠시 보관했다가 노드가 복귀하면 전달한다. Cassandra는 **다운타임 0을 구조적으로 추구한다.**

### 원칙 2: Linear Scalability (선형 확장)

노드를 2배로 늘리면 처리량도 (이상적으로는) 2배가 된다. 마스터가 없으므로 쓰기가 몰리는 단일 병목 지점이 없고, consistent hashing 덕분에 노드를 추가해도 데이터가 일부만 재분배된다. Netflix의 유명한 벤치마크는 노드 수를 늘릴수록 초당 쓰기 처리량이 거의 직선으로 증가한다는 것을 보여 주었다(수백 노드, 백만 단위 writes/sec).

```text
처리량
  │              ╱  Cassandra (선형)
  │            ╱
  │          ╱
  │        ╱
  │      ╱
  │    ╱        ┄┄┄┄┄ 샤딩 RDB (마스터 병목·재샤딩 비용으로 점차 평탄)
  │  ╱    ┄┄┄┄┄
  │╱┄┄┄┄
  └──────────────────────── 노드 수
```

이것은 "스케일 업(scale-up, 더 큰 서버)"이 아니라 **"스케일 아웃(scale-out, 더 많은 서버)"** 방식이다. 비싼 대형 머신 한 대 대신 평범한 머신을 여러 대 늘린다(commodity hardware).

### 원칙 3: Write-Optimized & Always Writable

LSM-Tree 덕분에 쓰기는 메모리 append와 commitlog 순차 기록만으로 끝나며, 디스크 랜덤 I/O가 없다. 또 마스터리스 구조와 hinted handoff 덕분에 **노드 일부가 죽어도 쓰기를 받아들인다.** "쓰기를 절대 거부하지 않는다"는 Dynamo 장바구니의 설계 원칙이 그대로 이어진 것이다.

> [!note] 정밀하게
> "항상 쓰기 가능"은 무조건 성립하는 것이 아니다. **선택한 일관성 수준(CL)이 요구하는 수만큼 사본이 살아 있을 때** 성립한다. CL이 낮을수록 더 많은 장애를 견딘다. 가장 낮은 `CL=ANY`에서는 담당 사본이 전부 죽어도 코디네이터가 **hinted handoff로 힌트만 남기고** 쓰기를 성공으로 처리한다(가장 공격적인 "always writable"). 반대로 `QUORUM`이나 `ALL`에서는 정족수만큼 사본이 살아 있어야 쓰기가 성공하고, 모자라면 쓰기는 실패한다.
>
> `ANY`를 제외하면 **hinted handoff가 보관한 힌트는 일관성 수준을 충족했는지 판단할 때 세지 않는다**(힌트는 어디까지나 사후 복구용이다). "쓰기를 거부하지 않는다"는 것은 Dynamo의 *기본 성향*일 뿐이고, 일관성 수준을 어떻게 설정하느냐에 따라 그 정도가 달라진다.

```text
쓰기 한 번의 내부:
  1. commitlog에 순차 append (내구성 확보)   ─┐
  2. memtable(메모리)에 정렬 삽입            ─┴ 둘 다 빠른 연산
  3. 클라이언트에 ACK
  ───────────────────────────────────────
  (나중에 비동기로) memtable → SSTable flush
  (더 나중에) compaction으로 SSTable 병합
```

디스크를 많이 쓰는 작업(flush, compaction)은 모두 **쓰기 경로 밖에서 비동기로** 처리한다. 그래서 사용자가 체감하는 쓰기 지연이 일관되게 낮다. 자세한 메커니즘은 10장(Write Path와 Read Path)에서 다룬다.

### 원칙 4: Operational Simplicity (운영 단순성)

모든 노드가 같은 역할을 한다는 점은 운영을 크게 단순하게 만든다. "마스터 노드용 설정"과 "슬레이브용 설정"을 따로 둘 필요가 없다. 노드를 추가할 때는 새 머신에 같은 설정으로 Cassandra를 띄우고 클러스터에 합류시키기만 하면 된다(bootstrap). 노드를 뺄 때도 같은 방식으로 반대 작업을 하면 되고, 데이터센터를 추가할 때도 같은 패턴을 반복한다.

즉 **동질성(homogeneity)이 운영을 단순하게 만든다.** 물론 compaction 튜닝, repair 스케줄, tombstone 관리처럼 Cassandra에만 있는 운영 과제는 따로 있다([[12 - 운영과 트러블슈팅]]).

## RDB와 비교해 무엇을 포기했고, 그 대가로 무엇을 얻었나

엔지니어링에 공짜는 없다. Cassandra의 장점은 모두 RDB가 당연하게 제공하던 기능을 **의도적으로 포기**한 대가로 얻은 것이다. 중요한 것은 "무엇을 버렸는가"가 아니라 **"그 대가로 무엇을 얻었는가"** 이다. 이 거래(trade)의 양쪽을 함께 봐야 한다.

| 포기한 것 (RDB가 주던 것) | 왜 포기했나 | 그 대가로 얻은 것 |
|---|---|---|
| **JOIN** | JOIN은 여러 테이블의 데이터를 런타임에 모은다. 분산 환경에서는 그 데이터가 여러 노드에 흩어져 있어 네트워크 셔플(shuffle)이 필요 → 확장 불가능 | 데이터를 노드 로컬에서 한 번에 읽음. 비정규화(denormalization)로 JOIN을 쓰기 시점에 미리 해둠. **예측 가능한 읽기 성능** |
| **임의 WHERE / ad-hoc 쿼리** | 인덱스 없는 컬럼으로 필터링하려면 전체 노드를 스캔(full scan)해야 함 → 분산 환경에서는 치명적 | 쿼리는 파티션 키 기반으로만. **모든 읽기가 특정 노드로 라우팅**되어 O(1)에 가까운 노드 도달. Query-First 모델링(5장 데이터 모델링 1 - Query First) |
| **멀티키 ACID 트랜잭션** | 여러 노드에 걸친 2PC(2-phase commit)는 가용성과 지연을 크게 떨어뜨린다(분단 시 블로킹) | 단일 파티션 원자성 + 필요 시 LWT(Paxos). **항상 쓰기 가능 + 선형 확장**(11장 LWT Batch Counter 내부) |
| **강한 일관성 default** | 모든 쓰기를 모든 사본에 동기 복제하면 가용성과 지연이 크게 나빠짐 | Tunable consistency. **쿼리마다 일관성 vs 가용성/지연을 선택**(4장 Tunable Consistency) |
| **정규화(normalization)** | 정규화는 JOIN을 전제로 한다. 분산 환경에서는 JOIN이 불가능 | 의도적 비정규화·데이터 중복. 디스크는 싸고 읽기는 빠름. **쓰기 증폭을 감수하고 읽기를 단순화** |
| **단일 노드 격리(isolation) 수준** | 분산 MVCC·락은 코디네이션 비용이 큼 | last-write-wins(타임스탬프 기준 충돌 해소). **락 없는 동시 쓰기** |

이 표를 한 문장으로 줄이면 다음과 같다. **"Cassandra는 '읽기 시점의 유연함'을 버리고, 결정을 '쓰기 시점'으로 옮겼다."** RDB는 데이터를 정규화해서 저장해 두고, 읽을 때 JOIN과 WHERE로 자유롭게 조합한다. 반면 Cassandra는 **"어떻게 읽을지"를 먼저 정하고, 그 읽기에 맞춰 데이터를 미리 가공해서 저장**한다. 이것이 잘 알려진 **Query-First 데이터 모델링**이며, RDB에 익숙한 엔지니어가 사고방식을 가장 크게 바꿔야 하는 부분이다.

> [!note] 결제 엔지니어를 위한 번역
> RDB에서 `SELECT * FROM payments WHERE user_id = ? AND status = ? AND created_at > ?` 같은 쿼리를 필요할 때마다 즉석에서 실행하던 습관은 버려야 한다. Cassandra에서는 "사용자별 최근 결제 목록"이라는 **쿼리를 먼저 정하고**, 그 쿼리가 단일 파티션 안에서 클러스터링 컬럼만으로 처리되도록 테이블을 설계한다.
>
> 새로운 쿼리 패턴이 생기면 **새 테이블(또는 비정규화된 사본)을 만든다.** "테이블 = 쿼리"라는 등식이 Cassandra 모델링의 출발점이다.

## 적합한 워크로드와 부적합한 워크로드: 언제 쓰고, 언제 쓰지 말아야 하는가

Cassandra는 만능이 아니다. 잘못된 곳에 쓰면 오히려 RDB보다 훨씬 힘들어진다. 지금까지 Cassandra의 특성을 살펴보았으니, 이제 어떤 문제에 적용할지 판단해 보자.

### Cassandra가 강점을 보이는 워크로드

- **쓰기가 매우 많은(write-heavy) 시계열·이벤트 데이터.** IoT 센서, 로그, 메트릭, 클릭스트림, 그리고 **이벤트 소싱(event sourcing)** 이 여기에 해당한다. append-only LSM 모델과 완벽하게 맞는다([[13 - 실전 Event Sourcing on Cassandra]]).
- **접근 패턴이 미리 정해져 있는** 대규모 데이터. "사용자별 타임라인", "기기별 최근 측정값"처럼 파티션 키가 자연스럽게 정해지는 경우이다.
- **항상 켜져 있어야 하고(고가용성)**, 일부 노드나 DC의 장애를 견뎌야 하는 서비스.
- **지리적으로 분산**되어 멀티 DC 액티브-액티브 구성이 필요한 경우. Cassandra는 멀티 DC 복제를 핵심 기능으로 지원한다(3장 복제 전략과 데이터센터).
- **거대한 데이터셋**(TB~PB)을 commodity hardware로 선형 확장하며 다뤄야 할 때.

### Cassandra를 피해야 할 워크로드 (안티패턴)

- **강한 트랜잭션 정합성이 핵심인 도메인.** 계좌 잔액 이체처럼 "A에서 빼고 B에 더하는" 멀티키 원자성이 핵심이라면 Cassandra는 적합한 도구가 아니다. LWT로 흉내 낼 수는 있지만 비용이 크고(Paxos 라운드트립) 제약도 많다.
- **즉석에서 만드는 분석 쿼리(ad-hoc, OLAP).** "지난달 카테고리별 매출 집계를 갑자기 보고 싶다" 같은 임의 집계와 JOIN은 Cassandra의 약점이다. 이런 작업은 분석 전용 시스템으로 처리해야 한다(Spark 같은 분석 엔진을 Cassandra 위에 얹거나, 데이터를 별도 데이터 웨어하우스로 옮긴다).
- **데이터는 작은데(수 GB) 복잡한 관계가 많은** 경우. 이때는 PostgreSQL 한 대가 훨씬 단순하고 강력하다. **"나중에 스케일이 필요할지도 모른다"는 막연한 이유로 Cassandra를 도입하는 것이 가장 흔한 실수다.**
- **읽을 때마다 조건이 바뀌는** 검색·필터 위주의 워크로드. (5.0의 SAI가 이 영역을 일부 넓혀 주었지만, RDB의 자유로운 WHERE를 대체하지는 못한다.)
- **높은 카디널리티에서 일관된 카운팅**이 핵심인 경우. Cassandra에도 카운터가 있지만 다루기 까다롭고 멱등(idempotent)하지 않다(11장 LWT Batch Counter 내부).

> [!note] 한 줄 판단 기준
> "접근 패턴을 **미리** 알 수 있고, 그 패턴을 **파티션 키로 라우팅**할 수 있으며, 무엇보다 **쓰기 처리량·가용성·확장성**이 꼭 필요한가?" 세 질문에 모두 yes라면 Cassandra를 쓴다. 하나라도 확신이 서지 않으면 RDB부터 검토하라.

## Cassandra 5.0 개요: 무엇이 새로워졌나

이 시리즈의 기준 버전인 **Cassandra 5.0**(2024년 정식 릴리스)은 단순한 버그 수정 릴리스가 아니다. Cassandra를 현대적인 워크로드(특히 AI와 검색)에 맞게 끌어올린 메이저 릴리스다. 여기서는 중요한 변화만 짚고, 각 항목의 내부 구조는 해당 장에서 자세히 다룬다.

- **SAI (Storage-Attached Indexing)**: 새로운 2차 인덱스(secondary index) 엔진이다. 기존 2i(secondary index)는 노드별 로컬 인덱스여서 카디널리티에 따라 성능 편차가 컸고, 실무에서는 사용을 피하는 기능이었다. SAI는 SSTable에 결합되어(storage-attached) 컬럼당 인덱스 비용이 낮고, 여러 인덱스를 조합한 쿼리와 범위·prefix 검색을 훨씬 효율적으로 처리한다. "Cassandra에서 인덱스는 쓰지 마라"는 오래된 격언을 부분적으로 뒤집은 변화다. (그래도 만능은 아니다. 6장 데이터 모델링 2 - 고급 타입과 안티패턴 참고)
- **UCS (Unified Compaction Strategy)**: compaction 전략을 하나로 통합했다. 이전에는 STCS(Size-Tiered), LCS(Leveled), TWCS(Time-Window) 가운데 워크로드에 맞는 전략을 골라야 했고, 잘못 고르면 쓰기 증폭(write amplification)이나 공간 증폭(space amplification) 문제가 생겼다. UCS는 파라미터로 조정하는 전략 하나로 이 전략들을 대신해 튜닝을 단순하게 만든다(9장 Compaction 전략).
- **Vector Search / ANN**: `VECTOR<FLOAT, N>` 타입과 근사 최근접 이웃(ANN, Approximate Nearest Neighbor) 검색을 지원한다. 내부적으로는 JVector 라이브러리를 기반으로 한다. 임베딩(embedding)을 저장하고 코사인 유사도로 검색할 수 있어, Cassandra를 **벡터 데이터베이스나 RAG 백엔드**로도 쓸 수 있게 되었다. AI 워크로드를 겨냥한 기능으로, 5.0에서 가장 주목받은 기능이다.
- **JDK 17 지원**: 4.x는 JDK 8과 11을 지원했다. 5.0은 JDK 11과 함께 **JDK 17**을 지원하므로 최신 GC(ZGC 등)와 언어·런타임 개선의 이점을 누릴 수 있다. GC 일시정지(pause)는 Cassandra의 꼬리 지연(tail latency)에 직접 영향을 주므로 의미가 크다.
- **Trie 기반 메모리/디스크 인덱스**: memtable과 SSTable 인덱스에 trie(BTI, Big Trie-Indexed SSTable format) 자료구조를 도입했다. 기존의 정렬 배열이나 스킵리스트보다 메모리 효율과 조회 성능이 좋아졌다. 같은 힙 크기로 memtable에 더 많은 데이터를 담을 수 있으므로 flush 빈도와 compaction 부하가 줄어든다(8장 Storage Engine 내부).

> [!warning] 버전 주의
> SAI, UCS, Vector Search는 모두 5.0에서 정식 기능이 되었다. 4.x 클러스터에서는 이 기능들을 기대하면 안 된다. 또한 5.0의 일부 기능(예: trie 인덱스 SSTable 포맷)을 쓰려면 업그레이드할 때 SSTable 포맷과 호환성을 함께 점검해야 한다.

## 경쟁 제품 비교: 분산 데이터 저장소 가운데 Cassandra의 위치

Cassandra를 제대로 이해하는 좋은 방법은, 비슷해 보이지만 다른 선택을 한 제품들과 나란히 비교해 보는 것이다. 각 제품이 어떤 트레이드오프를 골랐는지 보면 Cassandra의 특징이 분명해진다.

| | **Cassandra 5.0** | **DynamoDB** | **ScyllaDB** | **HBase** | **MongoDB** |
|---|---|---|---|---|---|
| **계보** | Dynamo + BigTable | Dynamo (의 상용 후예) | Cassandra 호환 재구현 | BigTable (의 OSS 구현) | 독자 문서 모델 |
| **아키텍처** | 마스터리스 P2P | 마스터리스(완전 관리형) | 마스터리스 P2P | 마스터/리전서버 + HDFS | 레플리카셋(프라이머리 1) + 샤딩 |
| **SPOF** | 없음 | 없음(관리형) | 없음 | HMaster/ZK 의존(완화됨) | 프라이머리 페일오버 필요 |
| **데이터 모델** | wide-column (CQL) | 키-값/문서 | wide-column (CQL 호환) | wide-column | 문서(BSON/JSON) |
| **구현 언어** | Java (JVM) | (비공개, 관리형) | **C++** (no GC) | Java (JVM) | C++ |
| **일관성** | tunable (PA/EL) | eventual / strong 선택 | tunable (Cassandra 호환) | 강한 일관성(행 단위) | tunable(write/read concern) |
| **운영 모델** | 셀프 호스팅/Astra | **완전 관리형(AWS 종속)** | 셀프/Cloud | 셀프(Hadoop 생태계) | 셀프/Atlas |
| **강점** | 멀티 DC, 쓰기 처리량, 성숙도 | 무운영, AWS 통합, 서버리스 | 같은 모델에 더 낮은 지연·높은 처리량 | Hadoop·강한 일관성 | 풍부한 쿼리·인덱스·집계 |
| **약점** | 운영 과제, ad-hoc 쿼리 | AWS 락인, 비용 예측·핫키 | 생태계가 Cassandra만큼 넓진 않음 | 운영 복잡, 멀티 DC 약함 | 대규모 쓰기 확장은 Cassandra만 못함 |

각 비교를 짧게 정리하면 다음과 같다.

- **vs DynamoDB**: 둘 다 Dynamo의 설계 원칙을 따르지만, DynamoDB는 **완전 관리형(AWS 종속)** 서비스다. 운영을 전혀 하지 않으려면 DynamoDB를, 멀티 클라우드나 온프렘에서 직접 통제하며 멀티 DC를 자유롭게 구성하려면 Cassandra를 고른다. DynamoDB는 운영 부담이 거의 없지만, 비용 모델(RCU/WCU)과 핫 파티션 제약, AWS 락인이 따라온다.
- **vs ScyllaDB**: ScyllaDB는 **Cassandra를 C++로 다시 구현한 것**이다. CQL과 프로토콜이 호환되며, JVM의 GC를 없애고 shard-per-core 아키텍처를 써서 같은 워크로드에서 더 낮은 꼬리 지연과 더 높은 처리량을 낸다고 주장한다. Cassandra의 모델은 맞지만 JVM과 GC 튜닝에 지쳤다면 검토해 볼 만하다. 다만 커뮤니티와 생태계, 검증 사례의 폭은 여전히 Cassandra가 넓다.
- **vs HBase**: HBase는 BigTable을 그대로 따른 OSS 구현으로, **강한 일관성**(행 단위)을 기본으로 제공한다. 하지만 HDFS, ZooKeeper, HMaster에 의존하므로 운영이 무겁고 멀티 DC 지원이 약하다. 페이스북이 Cassandra에서 HBase로 옮긴 이유도 강한 일관성과 Hadoop 생태계 통합이었다. 이미 Hadoop 생태계를 쓰고 있고 강한 일관성이 필요하다면 HBase를, 멀티 DC 고가용성과 운영 단순성이 중요하다면 Cassandra를 고른다.
- **vs MongoDB**: MongoDB는 처음부터 성격이 다른 데이터베이스다. **문서(document) 모델** 위에 다양한 ad-hoc 쿼리, 2차 인덱스, 집계 파이프라인을 제공하므로 개발하기 편하다. 하지만 기본 구조가 **프라이머리 1 + 세컨더리**로 이루어진 레플리카셋이어서 쓰기 확장은 샤딩에 의존하고, 그 운영도 Cassandra의 대칭적인 확장만큼 매끄럽지 않다. 유연한 스키마와 다양한 쿼리가 우선이면 MongoDB를, 대규모 쓰기 처리량과 마스터리스 가용성이 우선이면 Cassandra를 고른다.

이 제품들의 위치를 그림으로 나타내면 두 축이 보인다.

```text
        강한 일관성 / 풍부한 쿼리
                  ▲
         RDB ·    │   · HBase
        MongoDB   │
                  │
 ←────────────────┼────────────────→
 단일/관리 단순    │      대규모 쓰기·멀티DC·가용성
                  │
              DynamoDB · ScyllaDB
                  │   · Cassandra
                  ▼
        약한(조정형) 일관성 / 고정 접근 패턴
```

Cassandra는 이 그림의 오른쪽 아래 영역(**대규모 쓰기 처리량, 마스터리스 고가용성, 멀티 DC, 조정 가능한 일관성**)에서 가장 성숙하고 검증된 제품이다.
