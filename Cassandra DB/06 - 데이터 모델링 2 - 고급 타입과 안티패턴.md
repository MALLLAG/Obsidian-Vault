[[05 - 데이터 모델링 1 - Query First]]에서는 "쿼리가 테이블을 정의한다"는 원칙과, 파티션 키(partition key)와 클러스터링 키(clustering key)가 데이터의 물리적 배치를 결정한다는 사실을 배웠다. 그 장에서는 `text`, `int`, `uuid`, `timestamp` 같은 스칼라(scalar) 타입만으로 모델링했다.

하지만 CQL은 이보다 훨씬 다양한 도구를 제공한다. 컬렉션(list/set/map), 사용자 정의 타입(UDT), 튜플(tuple), 카운터(counter), 정적 컬럼(static column)이 있고, 인덱싱 계열로는 보조 인덱스(secondary index), SAI, Materialized View가 있다.

문제는 이 도구들이 모두 장점과 위험을 함께 가지고 있다는 점이다. RDB에서 넘어온 엔지니어는 이들을 "익숙한 기능의 Cassandra 버전"으로 오해하기 쉽다. 그래서 컬렉션을 JSON 컬럼처럼 쓰고, Materialized View를 트리거처럼 쓰고, 카운터를 `SELECT COUNT`처럼 쓴다. 그러다 운영 6개월 차에 5초씩 걸리는 읽기, 사라지지 않는 톰스톤(tombstone), 한 노드에만 부하가 몰리는 핫스팟(hotspot)을 만나게 된다.

## 컬렉션 타입: list / set / map은 "셀의 묶음"이다

CQL에는 세 가지 컬렉션이 있다.

```cql
CREATE TABLE user (
    user_id     uuid PRIMARY KEY,
    emails      set<text>,            -- 중복 없음, 정렬됨
    login_log   list<timestamp>,      -- 순서 있음, 중복 허용
    attributes  map<text, text>       -- 키-값
);
```

겉보기에는 "한 컬럼에 여러 값을 담는 편의 기능"이지만, 제대로 이해하려면 **이 컬렉션들이 디스크에서 어떻게 표현되는지**부터 알아야 한다.

결론부터 말하면 **non-frozen 컬렉션은 원소 하나하나가 각각 셀(cell) 하나로 저장된다.** 셀은 Cassandra 스토리지 엔진의 최소 단위로, `(이름, 값, 타임스탬프, [TTL])`을 묶은 것이다(자세한 내용은 [[08 - Storage Engine 내부]]에서 다룬다). 스칼라 컬럼 `name text`는 행(row)마다 셀이 하나지만, `emails set<text>`는 원소 개수만큼 셀이 생긴다.

### 내부 표현: 컬렉션은 행 안의 "미니 클러스터링"이다

원리는 단순하다. **컬렉션의 원소를 셀 이름(cell name) 안에 인코딩한다.** 행 안에 정렬된 키-값 구조를 하나 더 만드는 셈이며, 이는 사실상 클러스터링 컬럼과 같은 메커니즘이다.

```text
세 가지 컬렉션의 셀 표현 (논리적 모식)

set<text> emails = {'a@x.com', 'b@x.com'}
  ┌──────────────────────────────────────────────┐
  │ cell name = (emails, 'a@x.com')   value = ∅   │  ← 원소가 "이름"에, 값은 빈 바이트
  │ cell name = (emails, 'b@x.com')   value = ∅   │
  └──────────────────────────────────────────────┘

map<text,text> attributes = {'tier':'gold', 'city':'seoul'}
  ┌──────────────────────────────────────────────┐
  │ cell name = (attributes, 'city')  value='seoul'│  ← 맵 키가 "이름"에, 맵 값이 "값"에
  │ cell name = (attributes, 'tier')  value='gold' │
  └──────────────────────────────────────────────┘

list<text> login_log = ['x', 'y']
  ┌──────────────────────────────────────────────┐
  │ cell name = (login_log, <timeuuid_1>) value='x'│ ← 순서 보존용 timeuuid가 "이름"에
  │ cell name = (login_log, <timeuuid_2>) value='y'│
  └──────────────────────────────────────────────┘
```

이 표현에서 세 컬렉션의 설계 의도가 그대로 드러난다.

- **set**: 원소 자체를 셀 이름에 넣으므로 **중복이 자동으로 제거**되고(같은 이름의 셀은 하나뿐이다), 셀 이름의 바이트 정렬 순서에 따라 **정렬**된다. 원소가 이미 이름에 모두 들어 있으므로 값은 비어 있다.
- **map**: 맵의 키를 셀 이름에, 맵의 값을 셀 값에 넣는다. 그래서 같은 키에 쓰면 덮어쓰게 되고, 원소는 키 정렬 순서로 저장된다.
- **list**: 순서에 의미가 있으므로 셀 이름에 **timeuuid**(시간 기반 UUID)를 붙인다. 그래서 같은 값('x')을 두 번 넣어도 셀 이름이 서로 달라 **중복이 허용**되고, 삽입 순서도 보존된다. 뒤에서 다룰 list의 동시성 함정은 바로 이 timeuuid 메커니즘에서 비롯된다.

> [!note] RDB였다면 vs Cassandra
> RDB의 배열/JSON 컬럼은 하나의 값으로 통째로 저장되므로, 원소 하나를 바꾸려 해도 컬럼 전체를 다시 써야 한다. Cassandra의 **non-frozen** 컬렉션은 정반대다. 원소마다 독립된 셀이므로 `attributes['city'] = 'busan'` 한 줄로 그 셀 하나만 갱신하고, 다른 원소는 건드리지 않는다. non-frozen 컬렉션은 이 때문에 존재한다.

> [!warning] 숨은 비용: 컬렉션을 통째로 재대입하면 톰스톤이 생긴다
> 부분 갱신(`+`/`-`)과 달리, non-frozen 컬렉션을 통째로 다시 대입하면(`SET tags = {'a','b'}`, 또는 `INSERT`에서 컬렉션 컬럼을 지정) Cassandra는 새 셀을 쓰기 전에 먼저 **그 컬렉션 범위 전체를 덮는 톰스톤(range tombstone)** 을 기록한다. "기존 원소를 확실히 비운다"는 의미를 지키려면 피할 수 없는 동작이지만, 컬렉션을 자주 통째로 덮어쓰면 톰스톤이 대량으로 생겨 읽기와 컴팩션이 무거워진다.
>
> 일부만 바꾸는 것이 목적이라면 재대입하지 말고 반드시 `+`/`-` 연산을 써야 한다. (톰스톤이 왜 비싼지는 이 장 뒤쪽의 큐 패턴과 8장(Storage Engine 내부), [[09 - Compaction 전략]]에서 다룬다.)

### 한계 1: 읽을 때는 "전부" 읽는다

원소가 여러 셀로 나뉘어 있으면 갱신에는 유리하지만 읽기에는 불리하다. **컬렉션 안에서는 페이징을 할 수 없다.** `SELECT emails FROM user WHERE user_id = ?`를 실행하면 그 행의 emails에 속한 **모든 셀**이 한꺼번에 메모리로 올라오고, 직렬화되어 클라이언트로 전달된다. "emails의 처음 10개만" 같은 서버 측 슬라이싱은 불가능하다(클러스터링 컬럼이라면 `LIMIT`이나 범위 슬라이스를 쓸 수 있지만, 컬렉션 원소는 그 대상이 아니다).

예외가 하나 있다. non-frozen **map**은 키가 셀 이름으로 정렬되어 있으므로 `SELECT attributes['city']`처럼 키 하나를 지정해 읽을 수 있다. frozen 컬렉션은 통째로 셀 하나이므로 역직렬화 한 번으로 끝난다. 그래도 "임의의 N개를 페이징"하는 것은 어느 경우든 불가능하다.

그래서 컬렉션의 원소가 수천~수만 개로 늘어나면, 그 행을 읽을 때마다 큰 덩어리 전체가 직렬화된다. 그 결과 읽기 지연이 갑자기 커지고, 코디네이터(coordinator)의 힙(heap)에 부담이 가며, 네트워크 페이로드가 커진다.

### 한계 2: 권장 원소 상한과 가드레일(guardrail)

native protocol v2 시절에는 컬렉션 원소가 **65,535개**를 넘을 수 없다는 하드 리밋이 있었다(원소 개수를 16비트로 인코딩했기 때문이다). 이후 프로토콜에서는 이 제한이 없어졌지만, **그렇다고 해서 원소를 많이 담아도 된다는 뜻은 아니다.** 실무 가이드는 보수적이다.

- 원소 수: 수백 개 이내가 안전하며, 많아도 **1,000개 미만**을 권장한다.
- 직렬화 크기: 컬렉션 하나가 수십 KB를 넘기 시작하면 위험 신호다.

Cassandra **4.1**부터 도입된 통합 **가드레일(guardrails) 프레임워크**를 쓰면 운영 환경에서 이 기준을 강제할 수 있다(5.0에도 그대로 있다). 설정은 `cassandra.yaml`에서 하며, 키는 보통 최상위에 평탄하게 놓인다.

```text
items_per_collection_warn_threshold   # 컬렉션 원소 수 경고 임계
items_per_collection_fail_threshold   # 컬렉션 원소 수 거부 임계
collection_size_warn_threshold        # 직렬화된 컬렉션 바이트 크기 경고
```

> [!warning] 함정
> 이 가드레일들은 배포판에 따라 **기본값이 비활성(미설정)** 인 경우가 많다. 클러스터가 알아서 막아 주리라 기대하지 말고 임계를 직접 설정해 두어야 운영 안전장치가 된다. (설정을 확인하지 않은 클러스터라면 `nodetool`이나 `cassandra.yaml`에서 실제 설정을 점검해야 한다.)

### 대안: 정말 큰 컬렉션은 "클러스터링 행"으로 풀어라

원소가 많아질 가능성이 있다면 컬렉션 대신 클러스터링 컬럼으로 모델링한다. 컬렉션은 "행 안의 미니 클러스터링"일 뿐이고, 실제 클러스터링은 페이징과 범위 쿼리, `LIMIT`을 지원하므로 확장하기에 유리하다.

```cql
-- 안티패턴: 로그인 기록을 컬렉션에 무한히 담기
CREATE TABLE user_bad (
    user_id uuid PRIMARY KEY,
    logins  list<timestamp>   -- 계속 append → 무한 성장, 읽으면 전체 직렬화
);

-- 대안: 클러스터링 행으로 풀기 (페이징·LIMIT·범위 슬라이스 가능)
CREATE TABLE user_logins (
    user_id   uuid,
    login_at  timestamp,
    ip        inet,
    PRIMARY KEY ((user_id), login_at)
) WITH CLUSTERING ORDER BY (login_at DESC);
-- SELECT * FROM user_logins WHERE user_id=? LIMIT 20;  ← 최근 20개만
```

컬렉션은 한 사용자의 전화번호 두세 개나 상품의 태그 몇 개처럼 "값에 딸린 작은 부속물"일 때만 쓴다. 끝없이 늘어날 수 있는 데이터는 절대 컬렉션에 담지 않는다.

## frozen vs non-frozen: 한 덩어리인가, 셀의 모음인가

`frozen` 키워드를 붙이면 컬렉션과 UDT의 저장 방식이 근본적으로 달라진다.

```cql
CREATE TABLE t (
    id     uuid PRIMARY KEY,
    tags   set<text>,           -- non-frozen: 원소마다 셀
    coords frozen<set<int>>     -- frozen:     전체가 단일 블롭(blob) 1개 셀
);
```

- **non-frozen** (기본): 앞 절에서 본 것처럼 원소마다 독립된 셀에 저장한다. 부분 갱신(`tags = tags + {'new'}`)을 할 수 있다.
- **frozen**: 컬렉션 전체를 하나의 바이너리 블롭으로 직렬화해 **셀 한 개**에 넣는다. 부분 갱신은 할 수 없고, 값을 바꾸려면 전체를 통째로 덮어써야 한다.

```text
non-frozen set<text> {'a','b','c'}        frozen<set<text>> {'a','b','c'}
  ┌─────────────────────┐                  ┌─────────────────────────────┐
  │ cell (tags,'a') = ∅ │                  │ cell (coords) = [a|b|c] blob │  ← 셀 1개
  │ cell (tags,'b') = ∅ │                  └─────────────────────────────┘
  │ cell (tags,'c') = ∅ │                   원소 하나 바꾸려면 blob 전체 재기록
  └─────────────────────┘
   원소 하나만 add/remove 가능
```

### frozen을 쓰는 곳

frozen의 가장 큰 쓸모는 **컬렉션과 UDT를 기본 키(primary key)의 일부로 쓸 수 있다**는 점이다. non-frozen 컬렉션은 "여러 셀의 집합"이어서 하나의 값으로 비교할 수 없으므로 키가 될 수 없다. 반면 frozen은 하나의 블롭, 즉 하나의 값으로 비교할 수 있으므로 파티션 키나 클러스터링 키에 넣을 수 있다.

```cql
CREATE TABLE route (
    -- 출발-도착 좌표쌍 전체를 하나의 키로
    endpoints frozen<tuple<text,text>>,
    departed_at timestamp,
    PRIMARY KEY (endpoints, departed_at)
);
```

frozen은 "이 컬렉션은 항상 통째로 다루고 부분 갱신은 하지 않는다"는 의도를 타입으로 명시한다. 어차피 통째로 다룰 데이터라면 frozen이 셀 개수를 줄여 주므로 저장 공간과 읽기 측면에서 더 효율적이다.

| 구분 | non-frozen | frozen |
|------|-----------|--------|
| 저장 | 원소마다 셀 | 전체가 단일 블롭 1셀 |
| 부분 갱신 | O (원소 add/remove/set) | X (전체 덮어쓰기만) |
| PK 사용 | 불가 | 가능 |
| 셀 타임스탬프 | 원소마다 별도 | 컬렉션 1개 |
| 읽기 | 원소 셀 모두 머지 | 블롭 1개 역직렬화 |
| 적합한 경우 | 자주 부분 변경되는 작은 집합 | 불변/통째 교체, 키로 사용 |

> **튜플(tuple)은 언제나 frozen이다.** `tuple<...>`은 따로 명시하지 않아도 항상 frozen으로 취급된다. 그래서 부분 갱신을 할 수 없고 통째로만 교체할 수 있다.

## list의 함정: read-before-write와 동시성

list는 세 컬렉션 중 가장 위험하다. 순서를 보존하려고 timeuuid를 쓰는 구조 때문에 두 가지 문제가 생긴다.

### 함정 1: 인덱스 기반 연산은 read-before-write를 강제한다

list의 일부 연산은 **먼저 읽지 않으면 쓸 수 없다.** 셀 이름이 사용자가 지정한 인덱스(0,1,2…)가 아니라 내부 timeuuid이기 때문이다. "두 번째 원소"가 어떤 timeuuid를 가진 셀인지 알려면, 코디네이터가 먼저 list 전체를 읽어 위치를 계산한 다음 그 셀을 갱신하거나 삭제해야 한다.

```cql
-- read-before-write가 필요한 연산 (느리고 race에 취약)
UPDATE t SET login_log[2] = ?      WHERE id = ?;   -- 인덱스로 set
DELETE login_log[2]                FROM t WHERE id = ?; -- 인덱스로 delete
UPDATE t SET login_log = login_log - [?] WHERE id = ?; -- 값으로 remove

-- read-before-write가 불필요한 연산 (빠름, 권장)
UPDATE t SET login_log = login_log + [?] WHERE id = ?; -- append
UPDATE t SET login_log = [?] + login_log WHERE id = ?; -- prepend
```

read-before-write는 느릴 뿐 아니라 **원자성도 보장하지 못한다.** 읽은 시점과 쓰는 시점 사이에 다른 클라이언트가 list를 바꾸면, 인덱스 2가 가리키던 원소가 이미 달라져 엉뚱한 원소를 덮어쓰게 된다. Cassandra는 LWT를 쓰지 않는 한 이 구간에 락을 걸지 않는다. 따라서 **인덱스 기반 list 연산은 동시성 환경에서 신뢰할 수 없다.**

### 함정 2: append조차 멱등하지 않다

append는 read-before-write가 없어서 빠르지만, **재시도하면 중복**이 생긴다. append는 실행할 때마다 새 timeuuid 셀을 만든다. 클라이언트가 append를 보냈는데 코디네이터 응답이 타임아웃됐다고 하자. 서버에는 이미 셀이 기록되었지만 클라이언트는 이를 알지 못한다. 그래서 재시도하면 다른 timeuuid로 셀이 하나 더 생기고, 결국 **같은 값이 두 개**가 된다.

```text
append 재시도가 중복을 만드는 시퀀스

client: append('x') ──┐
                       └─> server: 셀(timeuuid_1, 'x') 기록 완료
client: (timeout!  응답 못 받음, 재시도)
client: append('x') ──┐
                       └─> server: 셀(timeuuid_2, 'x') 또 기록
결과: login_log = ['x', 'x']   ← 비멱등
```

set이라면 같은 값은 같은 셀 이름이 되므로 중복이 흡수되어 멱등하다. 하지만 list는 timeuuid 때문에 멱등하지 않다.

> [!note] 실무 규칙
> 순서가 꼭 필요하고 중복을 허용해야 하는 경우가 아니라면 **list 대신 set이나 클러스터링 행을 써야 한다.** 순서가 필요할 때도 list보다 `clustering order by`가 안전하다. list는 "작고, 거의 바뀌지 않고, append만 하며, 중복에 의미가 있는" 좁은 경우에만 쓴다.

## 사용자 정의 타입(UDT)과 튜플: 구조체를 한 컬럼에

UDT는 여러 필드를 묶은 구조체를 하나의 타입으로 정의한다. 정규화했다면 별도 테이블이 되었을 데이터를, 조인이 없는 Cassandra에서 한 행 안에 넣기 위한 도구다.

```cql
CREATE TYPE address (
    street text,
    city   text,
    zip    text
);

CREATE TABLE customer (
    id       uuid PRIMARY KEY,
    name     text,
    home     frozen<address>,          -- 통째로 다룰 주소
    shipping list<frozen<address>>     -- 주소 여러 개
);
```

### frozen UDT vs non-frozen UDT

UDT도 컬렉션처럼 frozen과 non-frozen으로 나뉜다.

- **frozen UDT**: 구조체 전체를 하나의 블롭으로 직렬화한다. 필드 하나를 바꾸려 해도 전체를 교체해야 한다. 키로 쓸 수 있다. **컬렉션 안에 UDT를 넣으려면 frozen이어야 한다**(`list<frozen<address>>`).
- **non-frozen UDT** (Cassandra 3.6+): 필드마다 독립된 셀에 저장하므로 `UPDATE ... SET home.city = ?`처럼 **필드 단위로 갱신**할 수 있다. 다만 컬렉션의 원소로도, 키로도 쓸 수 없다는 제약이 있다.

```text
frozen<address>                    non-frozen address
  ┌───────────────────────┐         ┌──────────────────────┐
  │ cell(home)=[s|c|z] blob│         │ cell(home,street)=...│
  └───────────────────────┘         │ cell(home,city)  =...│
   home.city만 못 바꿈              │ cell(home,zip)   =...│
                                     └──────────────────────┘
                                      home.city 단독 갱신 가능
```

내부 메커니즘은 컬렉션과 같다. frozen은 셀 1개이고, non-frozen은 필드마다 셀이 하나씩이다. 그래서 트레이드오프도 같다. 부분 갱신이 잦으면 non-frozen을, 통째로 다루거나 키로 쓰려면 frozen을 선택한다.

### 튜플: 이름 없는 가벼운 구조체

튜플은 필드 이름이 없는 고정 길이 묶음이다. 항상 frozen이며, 스키마를 바꾸지 않고 값 몇 개를 간단히 묶고 싶을 때 쓴다.

```cql
coords tuple<double, double>   -- (위도, 경도)
```

UDT는 필드에 이름이 있어 읽기 쉽고 스키마를 발전시키기에도 유리하다(`ALTER TYPE ... ADD`로 필드 추가). 튜플은 가볍지만 각 값의 의미가 위치로만 정해지므로 쉽게 깨진다. 그래서 보통 **오래 유지할 스키마에는 UDT를, 일회성 묶음에는 튜플**을 선택한다.

> [!warning] 주의
> UDT는 스키마를 발전시킬 수 있지만(필드 추가만 허용되고 삭제나 타입 변경은 불가), frozen UDT를 키에 쓰면 직렬화 형식이 키 정렬에 묶이므로 사실상 바꾸기 어렵다. [[13 - 실전 Event Sourcing on Cassandra]]에서 다루는 이벤트 스키마 호환성과 같은 이유로 주의해야 한다. 한 번 정해진 직렬화 형식은 계속 유지해야 한다.

## Static column: 파티션이 공유하는 컬럼

정적 컬럼(static column)은 **한 파티션의 모든 행이 함께 쓰는 단 하나의 값**이다. 정적 컬럼을 쓰면 파티션 단위 메타데이터를 행마다 중복해서 저장하지 않아도 된다.

```cql
CREATE TABLE order_items (
    order_id     uuid,
    item_seq     int,
    -- 아래 두 개는 주문(파티션) 전체에 하나씩만 존재
    customer_name text    STATIC,
    order_status  text    STATIC,
    -- 아래는 아이템(행)마다
    product_id   uuid,
    qty          int,
    PRIMARY KEY ((order_id), item_seq)
);
```

이 테이블에서 `customer_name`과 `order_status`는 `order_id` 파티션 전체에 **값이 하나**뿐이다. 아이템이 100개여도 `order_status`는 한 번만 저장되고, 어느 아이템 행에서 읽어도 같은 값이 보인다. 갱신도 파티션 단위로 한다. `UPDATE order_items SET order_status='shipped' WHERE order_id=?`처럼 클러스터링 키 없이 파티션 전체의 정적 값을 바꾼다.

```text
파티션(order_id=A) 내부

  static:  customer_name='Kim'   order_status='shipped'   ← 파티션당 1벌
  ─────────────────────────────────────────────────────
  row item_seq=1:  product=P1  qty=2
  row item_seq=2:  product=P2  qty=1
  row item_seq=3:  product=P3  qty=5
  → 어느 행을 읽어도 동일한 static 값이 함께 보인다
```

### 용도와 제약

- **용도**: 주문 상태, 소유자, 집계 캐시처럼 파티션의 머리글 역할을 하는 정보를 담는다. LWT로 파티션 단위 조건부 갱신을 할 때 기준점(anchor)으로도 쓴다. `IF order_status='pending'` 같은 조건을 정적 컬럼에 걸면 파티션 전체의 상태 머신을 만들 수 있다([[11 - LWT Batch Counter 내부]]).
- **제약**: 정적 컬럼은 **클러스터링 컬럼이 있는 테이블에서만** 의미가 있다(파티션에 행이 여러 개 있어야 "공유"가 성립한다). 클러스터링 키가 없는 테이블에는 정적 컬럼을 둘 수 없다. 또한 정적 컬럼은 파티션 키만으로 읽고 쓸 수 있으므로, 클러스터링 행 없이 정적 값만 있는 "행 없는 파티션"이 생길 수도 있다.

> [!note] 결제 시스템 관점
> 결제(payment) 파티션 하나 아래에 시도(attempt) 행 여러 개를 클러스터링하는 모델을 생각해 보자. 결제 전체 상태(`paid`/`failed`/`cancelled`)를 정적 컬럼으로 두면, 시도 행마다 상태를 복제하지 않고도 파티션 상태를 한 곳에서 관리할 수 있다. 다만 정적 컬럼을 갱신하면 파티션 전체에 영향이 가므로, 동시에 갱신될 수 있다면 LWT가 필요하다.

## Counter: 분산 카운터는 본질적으로 멱등하지 않다

카운터는 "분산 환경에서 숫자를 늘리거나 줄이는" 특수 타입이다. 좋아요 수나 조회 수처럼 여러 곳에서 동시에 +1을 하는 값에 쓴다. 그런데 카운터는 Cassandra에서 **제약이 가장 많고 가장 위험한** 타입이다.

### 제약 1: 카운터는 전용 테이블에만 둘 수 있다

카운터 컬럼이 있는 테이블은 **기본 키를 제외한 모든 컬럼이 카운터여야 한다.** 일반 컬럼과 섞어 쓸 수 없다.

```cql
-- OK: PK 외 전부 counter
CREATE TABLE page_views (
    page_id text PRIMARY KEY,
    views   counter,
    likes   counter
);

-- 불가: counter와 일반 컬럼 혼재
CREATE TABLE bad (
    id    text PRIMARY KEY,
    views counter,
    title text          -- ERROR: 카운터 테이블에 일반 컬럼 금지
);
```

그래서 "조회수"와 "게시글 본문"을 한 테이블에 둘 수 없다. 카운터는 별도 테이블로 분리하고 키로 연결해야 한다. 카운터에는 `INSERT`가 없으며, `UPDATE ... SET c = c + n`만 쓸 수 있다. 절댓값을 직접 설정할 수도 없고 TTL도 쓸 수 없다.

```cql
UPDATE page_views SET views = views + 1 WHERE page_id = ?;   -- 유일한 쓰기 방식
```

### 제약 2: 비멱등성 때문에 타임아웃 뒤 재시도하면 오차가 생긴다

카운터에서 가장 위험한 부분이다. **카운터 증감은 멱등하지 않다.** 일반 쓰기 `SET x = 5`는 몇 번을 재시도해도 결과가 5다(멱등). 하지만 `SET views = views + 1`은 적용된 횟수에 따라 결과가 달라진다.

문제는 **타임아웃**이다. 코디네이터가 클라이언트에 `WriteTimeout`을 돌려줬다고 해서 쓰기가 실패했다는 뜻은 아니다. "지정한 일관성 수준만큼 ack를 제때 모으지 못했다"는 뜻일 뿐이며, **실제로는 적용되었을 수도 있다.**

```text
카운터 타임아웃 재시도의 딜레마

client: views += 1  ──> coordinator ──> replica 적용 성공
                         (ack 지연으로 WriteTimeout 반환)
client: (적용됐나? 안 됐나? 알 수 없음)
  ├─ 재시도 안 함 → 실제로 안 됐다면 -1 누락 (under-count)
  └─ 재시도 함   → 실제로 됐다면   +1 중복 (over-count)
어느 쪽도 안전하지 않다. 멱등 키로 보호할 수도 없다.
```

일반 쓰기라면 같은 데이터를 다시 보내 멱등하게 재시도하면 된다. 카운터는 그렇게 할 수 없다. 그래서 **카운터로는 "정확히 한 번"을 보장할 수 없다.** 좋아요 수처럼 가끔 1~2 정도 틀려도 되는 곳에는 쓰지만, **돈이나 재고처럼 정확해야 하는 값에는 절대 쓰지 않는다.**

### 제약 3: 내부 구조가 read-before-write다

2.1에서 새로 작성된 카운터 구현은 증분을 적용할 때 리더 레플리카(leader replica)에서 **현재 값을 읽고, 새 값을 계산한 뒤, 기록**한다. 즉 카운터 쓰기는 사실상 읽기-수정-쓰기(read-modify-write)이므로 일반 쓰기보다 무겁고 지연도 크다.

내부적으로 카운터 값은 정수 하나가 아니라 **레플리카별 증분 샤드의 합(counter context)** 으로 표현된다. 증분에는 클라이언트가 붙인 식별자가 없으므로, 서버는 "재시도"와 "실제 두 번째 증가"를 구분할 방법이 없다. 일부만 적용된 증분을 나중에 분해하거나 상쇄해 되돌릴 방법도 없다. 삭제한 카운터를 다시 증가시키는 동작은 정의되어 있지 않으므로 사실상 금지된다(한 번 delete한 카운터 키는 재사용하지 않는다).

> [!note] 결제 시스템 관점
> "오늘 거래 건수"나 "정산 합계" 같은 값을 카운터로 만들고 싶어지기 쉽다. 하지만 타임아웃이 한 번만 나도 합계가 틀어지고, 틀어진 값을 나중에 검증하거나 교정할 방법이 없다. 정확한 집계가 필요하면 카운터 대신 **원본 이벤트를 적재해 두고 배치나 스트림으로 다시 계산**하거나, LWT 기반 멱등 처리로 해결한다. 카운터의 정확성 한계와 내부 동작은 11장(LWT Batch Counter 내부)에서 자세히 다룬다.

## 보조 인덱스(Secondary Index): 숨은 테이블과 scatter-gather

RDB에서 몸에 밴 "조회 조건이 늘면 인덱스를 추가한다"는 습관은 Cassandra에서 가장 자주 사고를 일으킨다. Cassandra의 전통적인 보조 인덱스는 RDB의 B-tree 인덱스와 **이름만 같을 뿐 동작 방식이 전혀 다르다.**

### 내부: 보조 인덱스는 "숨은 로컬 테이블"이다

`CREATE INDEX`를 실행하면 Cassandra는 내부적으로 **숨은 테이블(hidden table)** 을 만든다. 인덱싱된 컬럼 값을 파티션 키로, 원본 행의 기본 키를 클러스터링으로 갖는 역색인이다. 중요한 점은 이 인덱스가 **로컬(local)** 이라는 것이다. 각 노드는 **자기 노드에 있는 데이터만** 색인하며, 전역 인덱스는 없다.

```text
원본 테이블 (user) — 파티션 키 user_id 로 링에 분산
  node A: user_id=1 (city=seoul), user_id=4 (city=busan)
  node B: user_id=2 (city=seoul), user_id=5 (city=seoul)
  node C: user_id=3 (city=busan), ...

CREATE INDEX ON user(city) → 각 노드에 "숨은 로컬 인덱스"
  node A index:  seoul→{1}      busan→{4}
  node B index:  seoul→{2,5}
  node C index:  busan→{3}
  ↑ 어느 노드도 "seoul 전체"를 알지 못한다. 자기 몫만 안다.
```

### 멀티 노드에서 안티패턴인 이유: scatter-gather

`SELECT * FROM user WHERE city='seoul'`을 파티션 키 없이 인덱스만으로 실행하면, 인덱스가 로컬이므로 코디네이터는 seoul 데이터가 어느 노드에 있는지 알지 못한다. 그래서 **링의 모든 노드(정확히는 토큰 범위를 모두 커버하는 레플리카 세트)에 질의를 흩뿌리고(scatter), 각 노드가 로컬 인덱스를 뒤져 돌려준 결과를 모은다(gather).** 이를 scatter-gather 또는 fan-out이라고 한다.

```text
파티션 키 없는 인덱스 쿼리 = 전 노드 fan-out

         ┌─────────► node A (로컬 인덱스 조회) ─┐
client → coordinator ─► node B (로컬 인덱스 조회) ─┼─► 결과 머지
         └─────────► node C (로컬 인덱스 조회) ─┘
  노드가 100대면 100대를 다 깨운다. 한 노드라도 느리면 전체가 느리다.
  클러스터가 클수록 더 나빠진다 (안티-스케일).
```

노드 수가 늘수록 질의가 닿는 노드도 늘어나므로, **클러스터가 커질수록 오히려 느려지는** 반(反)확장적 패턴이다. Cassandra에서 좋은 쿼리는 모두 "파티션 키로 노드를 특정"하는데, 인덱스만으로 거는 쿼리는 그 반대로 동작한다.

### 카디널리티(cardinality)가 너무 높아도, 너무 낮아도 나쁘다

- **고카디널리티**(값이 거의 모두 다름, 예: email): 인덱스 파티션 수가 폭증하고, 인덱스 파티션마다 행이 한두 개뿐이다. fan-out으로 모든 노드를 깨워도 대부분의 노드는 결과가 없다. 매우 비효율적이다.
- **저카디널리티**(값이 몇 개뿐, 예: `is_active boolean`, `status`): 인덱스 파티션 수는 적지만 파티션 하나하나가 **거대**해진다. `is_active=true` 인덱스 파티션 하나에 수백만 행이 몰려, 거대 파티션(large partition) 문제가 그대로 다시 나타난다.

> [!note] 그럼 언제 써도 되나
> 보조 인덱스는 **파티션 키와 함께** 쓸 때만 안전하다. `WHERE user_id=? AND city='seoul'`처럼 파티션 키로 노드를 특정한 뒤, 그 파티션 안에서 인덱스로 거르는 경우다. 이때는 fan-out이 없고, 한 노드 안에서 좁은 범위를 검색하게 된다. 안티패턴은 "파티션 키 없이 인덱스만 쓰는 쿼리"이지, 인덱스 자체가 금지된 것은 아니다.

전통적인 보조 인덱스의 이런 한계 때문에 SAI가 등장했다.

---

## SASI에서 SAI로: 5.0의 Storage Attached Index

전통적인 보조 인덱스(2i)의 한계를 넘으려는 시도는 두 가지였다. SASI(SSTable Attached Secondary Index)와 SAI(Storage Attached Index)다.

### SASI: 좋은 아이디어였지만 끝내 완성되지 못했다

SASI는 3.4에서 실험적으로 도입되었다. 인덱스를 SSTable에 붙여(attached) 컴팩션과 함께 관리하고, `LIKE` 접두/접미 검색과 범위 질의를 가능하게 했다. 분명 발전이었지만 메모리 사용량, 디스크 오버헤드, 동작 안정성 문제 때문에 **프로덕션 권장 단계에 이르지 못했고, 5.0에서는 사실상 폐기(deprecated)되는 중**이다. SASI는 가능성을 보여 주었을 뿐이고, 그 방향을 완성한 것은 SAI다.

### SAI: 5.0의 권장 인덱스

SAI(Storage Attached Index)는 Cassandra 5.0의 대표 기능 중 하나다(CEP-7). 주요 개선점은 다음과 같다.

```text
            전통적 2i            SASI(deprecated)        SAI (5.0 권장)
저장        숨은 테이블          SSTable attached        SSTable attached
범위 쿼리   사실상 불가          부분 지원               숫자 range 1급 지원
텍스트      = 만                 LIKE prefix/suffix      = · analyzer 토큰 매칭
멀티 컬럼   인덱스마다 독립      독립                    여러 인덱스 AND 결합·공유
디스크      행마다 큼            큼                      매우 낮은 오버헤드
컴팩션      별도 관리            함께                    함께(수명주기 일치)
```

- **숫자 범위(numeric range)**: `WHERE amount > 10000 AND amount < 50000` 같은 범위 질의를 정식 기능으로 지원한다. 전통적인 2i에서는 사실상 불가능했던 질의다.
- **텍스트 매칭**: 동등 비교(`=`)에 더해, 컬럼에 **analyzer**(예: standard, 비토크나이징, n-gram 등 Lucene 계열)를 지정하면 토큰 단위 매칭(대소문자·악센트 정규화 등)을 할 수 있다. 다만 SASI의 대표 기능이던 `LIKE 'foo%'`나 `'%foo%'` 같은 **임의 접두·접미 와일드카드 검색은 SASI처럼 정식 기능으로 제공하지 않는다**(필요하면 n-gram analyzer로 우회한다). SAI는 정확 매칭과 범위, 토큰 매칭에 초점을 둔다.
- **여러 컬럼 인덱스의 결합**: 한 테이블의 여러 컬럼에 SAI를 걸고, `WHERE a=? AND b>?`처럼 **여러 SAI 인덱스를 AND로 교집합**할 수 있다. 내부적으로 인덱스들이 공유 인프라 위에서 동작하므로, 컬럼이 늘어도 디스크 비용이 선형으로 급증하지 않는다.
- **SSTable에 붙어 있음(storage-attached)**: 인덱스가 SSTable과 한 덩어리이므로 컴팩션, 플러시(flush)와 수명주기가 같다. 따로 동기화할 필요가 없고, 디스크와 쓰기 오버헤드가 전통적인 2i보다 훨씬 낮다.

```cql
CREATE INDEX ON payments(amount) USING 'sai';
CREATE INDEX ON payments(status) USING 'sai';
-- 숫자 범위 + 동등을 결합 (단, 아래의 한계 주의)
SELECT * FROM payments WHERE user_id=? AND status='paid' AND amount > 10000;
```

> 위의 `USING 'sai'`는 축약 별칭이고, 긴 형식은 `CREATE CUSTOM INDEX ... USING 'StorageAttachedIndex'`이다. 두 형식은 같은 인덱스를 만든다.

### SAI로도 해결되지 않는 한계

SAI는 2i보다 훨씬 낫지만 **만능은 아니다.** 여전히 **로컬 인덱스**이기 때문이다. 따라서 다음 한계가 남는다.

- **파티션 키 없는 쿼리는 여전히 scatter-gather다.** SAI는 fan-out을 더 효율적으로 만들 뿐 fan-out 자체를 없애지는 못한다. 모든 노드를 깨우는 구조는 그대로이므로, 클러스터가 크면 여전히 비용이 크다.
- **저카디널리티와 거대 파티션 문제를 해결하지 않는다.** 인덱스가 가리키는 원본이 거대 파티션이면 읽기는 여전히 무겁다.
- 조인, 집계, OR 같은 관계형 연산을 제공하지 않는다. SAI는 "필터"이지 쿼리 엔진이 아니다.
- 일관성은 베이스 데이터와 같은 최종 일관성(eventual)을 따른다.

> [!note] 결론
> SAI는 "쿼리 테이블을 따로 만들 정도는 아닌, **파티션 키로 좁힌 범위 안에서 쓰는 보조 필터**"에 가장 알맞다. "파티션 키 없이 전체 데이터를 인덱스로 뒤지는" 용도라면 SAI를 써도 안티패턴이다. 그런 쿼리는 5장(데이터 모델링 1 - Query First)의 원칙대로 **전용 쿼리 테이블로 비정규화**하는 것이 정답이다.

## Materialized View: 자동 비정규화의 편리함과 함정

수동 비정규화는 번거롭다. 같은 데이터를 쿼리별 테이블에 여러 벌 직접 써야 하고, 정합성도 애플리케이션이 책임져야 한다. Materialized View(MV)는 이 작업을 자동화해 주겠다는 기능이다. 베이스 테이블(base table)에 쓰면 Cassandra가 알아서 뷰(view) 테이블에 비정규화된 사본을 만든다.

```cql
CREATE TABLE payments (
    user_id   text,
    payment_id text,
    status    text,
    paid_at   timestamp,
    PRIMARY KEY ((user_id), payment_id)
);

-- status로 조회하는 뷰를 자동 유지
CREATE MATERIALIZED VIEW payments_by_status AS
    SELECT * FROM payments
    WHERE user_id IS NOT NULL AND status IS NOT NULL AND payment_id IS NOT NULL
    PRIMARY KEY ((user_id), status, payment_id);
```

이제 `payments`에 INSERT나 UPDATE를 하면 `payments_by_status`가 자동으로 갱신된다. 매력적인 기능이다. 하지만 **5.0에서도 MV는 experimental이며 기본값은 비활성**이다.

### experimental인 이유: 내부 동작과 일관성 문제

베이스에 쓰기가 들어오면 MV는 그 쓰기 때문에 뷰의 어느 행을 바꿔야 하는지 계산하려고 **베이스를 먼저 읽는다(read-before-write).** 예를 들어 `status`가 `pending`에서 `paid`로 바뀌면, 뷰에서 `pending` 행을 지우고 `paid` 행을 새로 넣어야 한다. 그러려면 이전 status가 무엇이었는지 알아야 하므로 베이스를 로컬에서 읽어야 한다.

```text
MV 쓰기 경로 (개략)

UPDATE payments SET status='paid' WHERE user_id=U AND payment_id=P
        │
        ▼ (베이스 레플리카에서)
   1) 기존 행 읽기: status_old = 'pending'    ← read-before-write
   2) 뷰 업데이트 생성:
        - DELETE payments_by_status (U,'pending',P)
        - INSERT payments_by_status (U,'paid',P)
   3) 베이스 쓰기 + 뷰 쓰기를 비동기 전파
```

이 구조에서 두 가지 비용과 위험이 생긴다.

- **성능**: 모든 베이스 쓰기에 로컬 읽기가 따라붙으므로 쓰기 처리량이 떨어진다.
- **일관성**: 베이스와 뷰의 갱신은 원자적이지 않다. 노드 장애나 전파 실패가 생기면 **뷰가 베이스와 어긋날 수 있다.** 더 큰 문제는 어긋난 뷰를 쉽게 검증하거나 교정할 도구가 부족하다는 점이다(불일치가 생기면 사실상 뷰를 재구축하는 것밖에 복구 수단이 없고, 대형 테이블에서는 비용이 매우 크다). repair가 베이스와 뷰의 정합을 항상 보장한다고 단정하기도 어렵다.

MV에는 모델링 제약도 있다. **뷰의 기본 키는 베이스의 기본 키 컬럼을 모두 포함해야** 하고, 여기에 추가할 수 있는 베이스의 비키 컬럼은 **최대 하나**다. 그래서 표현할 수 있는 뷰가 제한적이다.

MV를 쓰려면 `cassandra.yaml`에서 명시적으로 켜야 한다.

```text
materialized_views_enabled: true   # 5.0, 기본 false (experimental)
```

### MV vs 수동 비정규화 트레이드오프

| 관점 | Materialized View | 수동 비정규화 테이블 |
|------|-------------------|----------------------|
| 작성 편의 | 자동, 코드 적음 | 앱이 직접 다중 테이블 기록 |
| 일관성 제어 | 엔진에 위임(불일치 시 교정 난해) | 앱이 통제(LOGGED BATCH로 묶기 등) |
| 쓰기 비용 | 베이스 read-before-write | 추가 테이블 쓰기(보통 읽기 불필요) |
| 모델 유연성 | 키 제약(비키 +1만) | 자유롭게 설계 |
| 운영 성숙도 | experimental, 기본 off | 검증된 표준 패턴 |
| 불일치 복구 | 뷰 재구축(고비용) | 앱 레벨 재기록/검증 가능 |

> [!warning] 흔한 오해
> "MV는 Cassandra가 공식으로 제공하니 안전할 것이다"라고 생각하기 쉽지만 그렇지 않다. 공식 기능이긴 해도 experimental이고 기본값은 비활성이다. 결제나 정산처럼 정합성이 중요한 핵심 경로에서는 **MV 대신 수동 비정규화**를 쓰는 것이 사실상 업계 표준이다.
>
> 같은 데이터를 두 테이블에 쓰되, 둘이 같은 파티션 키 그룹이면 `LOGGED BATCH`로 원자성에 가까운 효과를 내고(11장 LWT Batch Counter 내부), 불일치는 멱등 재기록과 검증 잡으로 잡아낸다. MV는 "정확성보다 편의가 우선이고 불일치를 감수할 수 있는" 비핵심 경로에서만 신중하게 쓴다.

## 안티패턴 카탈로그: 증상 · 원인 · 대안

지금까지 살펴본 기능의 오용을 포함해, 실전에서 반복되는 안티패턴을 표 하나로 정리한다. 모든 안티패턴의 근본 원인은 하나다. 바로 **"파티션의 물리적 현실을 무시한 모델링"** 이다.

| 안티패턴 | 증상 | 근본 원인 | 대안 |
|----------|------|-----------|------|
| **무한 파티션 성장**(unbounded partition) | 시간이 갈수록 특정 파티션 읽기 지연·GC 압박 증가 | 시간 경계 없는 파티션 키(예: `user_id` 하나로 모든 이벤트) | 시간 버킷팅(`(user_id, yyyymm)`), 복합 파티션 키로 상한 부여 |
| **핫스팟**(hotspot) | 한 노드만 CPU/IO 폭주, 나머지 한가 | 단조·저카디널리티 파티션 키(예: 오늘 날짜로 전부 몰림) | 버킷/해시 접두로 분산, 키 카디널리티 상향 |
| **큐 패턴**(tombstone hell) | 읽기 지연이 시간에 비례해 악화, `TombstoneOverwhelmingException` | insert 후 처리 완료 행 delete → 좁은 범위에 톰스톤 누적, 읽을 때 톰스톤을 스캔 | Cassandra를 큐로 쓰지 않기; 불가피하면 시간 버킷+TTL로 톰스톤 스캔 회피 |
| **거대 파티션**(large partition) | 특정 파티션 읽기 느림, repair·컴팩션 시 힙 압박, 복구 지연 | 한 파티션에 너무 많은 행/바이트(~100MB·수십만 행 초과) | 파티션 분할(버킷팅), 행 폭 줄이기, 컬렉션→클러스터링 |
| **저카디널리티 인덱스** | 인덱스 쿼리 느림, 인덱스 파티션 비대 | `boolean`/`status` 등에 보조 인덱스 → 한 인덱스 파티션에 수백만 행 | 전용 쿼리 테이블, 또는 파티션 키와 함께 SAI 사용 |
| **read-before-write** | 레이스로 값 유실/중복, 지연 증가 | list index 연산, "읽고 검사 후 쓰기"를 무락(無lock)으로 수행 | LWT로 보호하거나(비용 인지), 그런 연산이 없도록 재모델링 |
| **컬렉션 남용** | 행 읽기마다 거대 컬렉션 직렬화, 쓰기 비대 | 무한 성장하는 데이터를 list/set/map에 적재 | 클러스터링 행으로 풀기, 컬렉션은 작은 부속물로 한정 |

### 안티패턴 자세히 보기

**무한 파티션 성장과 거대 파티션은 사실상 같은 문제다.** 둘 다 "파티션 키에 상한이 없다"는 같은 원인에서 나온 서로 다른 증상이다. 해결책은 **버킷팅(bucketing)** 이다. 파티션 키에 시간이나 해시 차원을 더해 파티션 하나의 크기를 물리적으로 제한한다. 5장(데이터 모델링 1 - Query First)의 시계열 모델링에서 본 `(sensor_id, day)` 패턴이 바로 이 방법이다.

```cql
-- 무한 성장 (나쁨): 한 device의 모든 이벤트가 한 파티션에 영원히 쌓임
PRIMARY KEY ((device_id), event_at)

-- 버킷팅 (좋음): 일 단위로 파티션을 잘라 크기 상한 부여
PRIMARY KEY ((device_id, event_day), event_at)
```

**큐 패턴(tombstone hell)** 은 Cassandra 입문자가 가장 흔히 빠지는 함정이다. "할 일을 INSERT하고, 처리가 끝나면 DELETE한다"는 방식은 RDB에서는 자연스럽지만 Cassandra에서는 심각한 문제를 일으킨다. DELETE는 데이터를 즉시 지우지 않고 **톰스톤**이라는 "삭제 표식"을 남기며, 이 톰스톤은 `gc_grace_seconds`(기본 864,000초=10일) 동안 SSTable에 남아 있다.

큐의 머리(가장 오래된 미처리 항목)를 읽으려 하면, 코디네이터는 이미 삭제된 수많은 항목의 **톰스톤을 모두 스캔해서 버린 뒤**에야 살아 있는 행에 도달한다. 처리량이 늘수록 톰스톤이 쌓여 읽기가 점점 느려지고, 결국 `tombstone_failure_threshold`(기본 100,000)에 걸려 쿼리 전체가 실패한다.

```text
큐 패턴이 죽는 과정 (한 파티션 안의 SSTable 스캔)

읽기: "가장 오래된 미처리 항목" → 파티션 앞에서부터 스캔
  [tomb][tomb][tomb][tomb]...[tomb][LIVE]
   └────────── 다 읽고 버림 ──────┘  ↑ 겨우 여기
  tombstone_warn_threshold=1000 초과 → 경고 로그
  tombstone_failure_threshold=100000 초과 → 쿼리 실패(예외)
```

해결책은 명확하다. **Cassandra를 작업 큐로 쓰지 말고** Kafka나 SQS 같은 전용 큐를 써야 한다. 꼭 Cassandra를 써야 한다면, 시간 버킷을 두어 처리가 끝난 영역을 통째로 버리거나(파티션 단위 TTL/드롭), 읽기 범위가 쌓인 톰스톤을 가로지르지 않도록 모델링한다. 톰스톤과 `gc_grace_seconds`의 내부 메커니즘은 8장(Storage Engine 내부)과 9장(Compaction 전략)에서 다룬다.

**핫스팟**은 일관성 모델이 아니라 **부하 분산**의 문제다. Cassandra는 파티션 키를 해시(murmur3)해서 토큰 링([[02 - 분산 아키텍처]])에 배치한다. 키가 잘 분산되면 부하도 고르게 퍼지지만, 모든 쓰기가 "오늘 날짜" 파티션 하나로 몰리면 그 파티션을 담당하는 노드 세트에만 부하가 집중된다. 해결책은 파티션 키에 분산 차원을 더하는 것이다. 예를 들어 `(date)` 대신 `(date, bucket)`을 키로 두고 `bucket = hash(id) % N`처럼 나누면, 같은 날의 쓰기가 N개 파티션으로 흩어진다.

> [!note] 모든 안티패턴에 공통되는 원칙
> Cassandra에서 좋은 모델은 읽기와 쓰기가 **소수의, 크기가 제한된, 고르게 분산된 파티션**에 떨어지도록 만든다. 무한 성장, 핫스팟, 거대 파티션, 큐 패턴은 모두 이 원칙을 어긴 결과다.
