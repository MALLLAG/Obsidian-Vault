앞선 장들에서는 Cassandra가 토큰 링(token ring) 위에 데이터를 분산 배치하고([[02 - 분산 아키텍처]]), 그 데이터를 여러 노드에 복제하며([[03 - 복제 전략과 데이터센터]]), 정족수(quorum)로 일관성 수준을 조정한다는 것([[04 - Tunable Consistency]])을 살펴보았다.

이 메커니즘은 모두 하나의 질문으로 이어진다. **"방금 보낸 이 쿼리는 정확히 몇 개의 노드에 접근하는가?"** 이 장에서는 이 질문의 답을 데이터 모델을 설계하는 단계에서 *미리* 정해 두는 방법론을 다룬다.

이 장에서는 Cassandra에서 테이블보다 쿼리를 먼저 설계하는 이유, `PRIMARY KEY (a, b, c)`의 각 요소가 디스크에서 하는 역할, `WHERE` 절 제약과 `ALLOW FILTERING`을 위험하게 취급하는 이유, 그리고 파티션 크기의 한계를 다룬다. 이 과정에서 "데이터 모델링"이라는 말이 RDB와 Cassandra에서 거의 정반대의 작업을 가리킨다는 점을 확인하게 된다.

## 1. Query-First: 정규화와 반대 방향에서 시작하기

### RDB의 관점: 데이터를 먼저, 쿼리는 나중에

관계형 데이터베이스로 시스템을 설계해 본 사람에게는 익숙한 순서가 있다.

1. 도메인의 엔티티를 식별한다(사용자, 주문, 상품, 결제 등).
2. 엔티티 사이의 관계를 정의한다(1:N, N:M).
3. 정규화(normalization)를 적용한다. 같은 데이터가 두 곳에 저장되지 않도록, 즉 모든 사실(fact)이 한 곳에만 존재하도록 테이블을 나눈다.
4. 이렇게 만든 깔끔한 스키마 위에서, 필요할 때마다 `JOIN`으로 데이터를 다시 조합해 쿼리를 작성한다.

이 접근은 "**쿼리는 나중에 얼마든지 만들 수 있다**"고 가정한다. 정규화된 스키마는 일종의 *진실의 단일 원천*(single source of truth)이고, 옵티마이저(optimizer)가 인덱스를 골라 가며 `JOIN`을 효율적으로 처리해 준다. 그래서 RDB에서 "좋은 스키마"란 중복이 없고 갱신 이상(update anomaly)이 생기지 않는 스키마를 말한다.

이 관점이 성립하는 이유는 하나뿐이다. **`JOIN`의 비용이 낮기 때문**이다. 단일 노드 RDB에서는 두 테이블이 같은 디스크, 같은 메모리, 같은 버퍼 풀 위에 있다. 인덱스로 한쪽 테이블의 행을 찾은 뒤 그 키로 다른 테이블을 다시 찾는 비용은 밀리초 단위다.

### Cassandra의 관점: `JOIN`이 없으므로 쿼리가 먼저다

Cassandra에는 `JOIN`이 없다. 이는 빠뜨린 기능이 아니라 **설계상 의도적으로 제외한 기능**이다. 분산 환경에서 `JOIN`을 구현하려면, 서로 다른 노드(심지어 다른 데이터센터나 다른 대륙)에 흩어져 있는 임의의 두 행을 네트워크를 거쳐 모아야 한다. 100개 노드로 구성된 클러스터에서 무심코 실행한 `JOIN` 하나가 100개 노드를 모두 동원하고, 노드 간 네트워크를 데이터로 가득 채울 수 있다.

Cassandra는 이처럼 드러나지 않게 비용이 커지는 연산을 처음부터 금지해서, 모든 쿼리의 비용을 *예측할 수 있게* 만든다.

`JOIN`이 없고, 서버 측 집계도 사실상 없으며, 임의 컬럼으로 필터링하는 것도 막혀 있다면 "쿼리는 나중에 만들면 된다"는 가정은 성립하지 않는다. 앞으로 실행할 쿼리를 *지금* 알지 못하면, 그 쿼리를 뒷받침할 테이블 구조를 만들 수 없다. 그래서 Cassandra 데이터 모델링은 **읽기 패턴(read pattern)에서 시작해서 테이블로 끝난다.**

> [!warning] 흔한 오해
> "Cassandra는 스키마가 유연하니까 일단 데이터를 넣고 쿼리는 나중에 고민하면 된다." 사실은 정반대다. Cassandra는 컬럼을 추가하는 데는 관대하지만, 쿼리 패턴을 나중에 바꾸는 데는 가장 까다로운 DB다. 파티션 키를 잘못 정하면 테이블을 통째로 다시 만들고 데이터를 마이그레이션해야만 고칠 수 있다.

### 네 단계 방법론: conceptual → workflow → logical → physical

DataStax가 정리하고 업계가 받아들인 Cassandra 데이터 모델링의 표준 흐름은 네 단계로 이루어진다. RDB의 흐름과 나란히 놓고 비교해 보자.

```text
  RDB (Data-First)                  Cassandra (Query-First)
  ─────────────────                 ────────────────────────
  ① 개념 모델 (엔티티/관계)   →     ① 개념 모델 (엔티티/관계)   ← 여기까지는 같다
  ② 정규화 → 논리 스키마             ② 애플리케이션 워크플로
  ③ 물리 스키마 (인덱스)              ──> "어떤 화면이 어떤 데이터를
  ④ 쿼리를 SQL로 작성                     어떤 순서로 읽는가?"
                                          = 필요한 쿼리(Q1..Qn) 도출
                                    ③ 논리 모델: 쿼리 1개 = 테이블 1개
                                    ④ 물리 모델: CQL DDL, 파티션 크기 검증
```

각 단계를 자세히 살펴보자.

**① 개념 모델 (conceptual model)**: 이 단계는 RDB와 같다. 도메인을 ER 다이어그램으로 그리고, "결제(Payment)는 여러 개의 환불(Refund)을 가진다", "사용자(User)는 여러 활동(Activity)을 발생시킨다" 같은 엔티티와 관계를 식별한다. 이 단계는 비즈니스 개념을 이해하는 단계이지 저장 구조를 정하는 단계가 아니다.

**② 애플리케이션 워크플로 (application workflow)**: 여기서부터 RDB와 달라진다. 이 단계에서는 "이 시스템의 화면과 API가 데이터에 *어떻게 접근하는가*"를 그린다. 결제 콘솔의 상세 화면은 무엇을 보여 주는가? 사용자가 "내 최근 결제 내역"을 누르면 무엇을 어떤 순서로 읽는가? 워크플로 다이어그램의 각 화살표가 하나의 **접근 패턴(access pattern)**, 즉 하나의 쿼리가 된다. 이 단계의 결과물은 다음과 같은 쿼리 목록이다.

```text
Q1: userId로 특정 사용자의 최근 결제 목록을 최신순으로 조회
Q2: paymentId로 단일 결제의 상세 조회
Q3: userId로 특정 사용자의 활동 타임라인을 시간 역순으로 조회
Q4: sensorId + 날짜로 그 날의 센서 측정값을 시간순으로 조회
...
```

**③ 논리 모델 (logical model)**: Query-First에서 가장 중요한 단계다. **쿼리 하나마다 테이블을 하나씩 만든다.** Q1을 위한 테이블, Q2를 위한 테이블, Q3을 위한 테이블을 각각 만들고, 같은 데이터가 여러 테이블에 중복으로 들어가더라도 신경 쓰지 않는다. 각 테이블의 파티션 키와 클러스터링 컬럼은 해당 쿼리의 `WHERE`/`ORDER BY`를 그대로 처리할 수 있도록 거꾸로 계산해서 정한다.

**④ 물리 모델 (physical model)**: 논리 모델을 실제 CQL 데이터 타입과 DDL로 구체화하고, 각 테이블의 파티션이 지나치게 커지지 않는지, 핫스팟(hotspot)이 생기지 않는지를 수치로 검증한다. 파티션이 너무 커진다면 버킷팅(bucketing)으로 나누는 등의 조정도 이 단계에서 한다.

### "정규화 원칙을 어기는 것 아닌가?"라는 거부감 다루기

RDB에 익숙한 엔지니어는 ③단계에서 거의 항상 거부감을 느낀다. "같은 결제 정보를 테이블 세 개에 복사한다고? 한쪽만 수정되면 데이터가 어긋나잖아!" RDB에서라면 이 직관이 옳다. 하지만 Cassandra에서는 트레이드오프가 반대 방향으로 기울어 있다.

| 축 | RDB (정규화) | Cassandra (비정규화) |
|---|---|---|
| 최적화 대상 | 저장 공간, 쓰기 일관성 | 읽기 지연시간, 수평 확장성 |
| 디스크 | 비싸다고 가정 | 싸다고 가정 (그냥 더 사면 됨) |
| 중복 | 피해야 할 것 (anomaly의 원천) | 장점 (각 쿼리가 자기 데이터를 따로 가짐) |
| 일관성 유지 | DB가 `JOIN`/트랜잭션으로 보장 | **애플리케이션이 쓰기 시점에 책임** |
| 쓰기 비용 | 한 곳에만 쓰면 됨 | 여러 테이블에 동시에 써야 함 |

이유는 하나다. **Cassandra에서는 쓰기 비용이 매우 낮다.** [[08 - Storage Engine 내부]]에서 자세히 다루겠지만, Cassandra의 쓰기는 메모리(memtable)에 추가하고 커밋 로그에 append 하는 것이 전부다. 디스크에 있는 기존 데이터를 읽어서 갱신하는(read-modify-write) 과정이 없다.

그래서 같은 데이터를 5개 테이블에 쓰더라도 1개 테이블에 쓸 때보다 5배 느려지는 것이 아니라, 여전히 충분히 빠르다. 반면 읽기에서 `JOIN`이나 필터링을 하면 비용이 통제할 수 없을 만큼 커진다. **Cassandra는 쓰기 작업을 더 늘리는 대신 읽기 비용을 거의 없애는 방식을 택한다.**

> [!note] 결제 시스템 비유
> 결제 도메인에 적용해 보면, "결제 이벤트"는 한 번 발생하면 바뀌지 않는다(append-only). 그런데 그 이벤트를 보여 주는 화면은 여러 개다. 사용자별 목록, 결제 ID로 하는 단건 조회, 정산 대사용 일자별 집계가 있다. 이벤트가 불변이라면, 같은 이벤트를 여러 형태로 여러 테이블에 미리 펼쳐 두는 것은 위험하기는커녕 자연스러운 방식이다. 이것이 [[13 - 실전 Event Sourcing on Cassandra]]에서 다루는 이벤트 소싱이 Cassandra와 잘 맞는 근본적인 이유다.

## 2. Primary Key 구조: 파티션 키와 클러스터링 컬럼

Query-First가 설계 원칙이라면, 그 원칙을 디스크 수준에서 적용하는 물리적 메커니즘이 PRIMARY KEY다. CQL의 PRIMARY KEY는 RDB의 PRIMARY KEY와 이름만 같을 뿐, 완전히 다른 두 가지 역할을 함께 맡고 있다.

```cql
PRIMARY KEY ( (partition_key) , clustering_col_1, clustering_col_2, ... )
              └──────┬───────┘  └──────────────────┬─────────────────┘
            데이터가 "어느 노드"에 가는가     파티션 "내부에서 어떻게 정렬"되는가
```

이 한 줄을 정확히 읽는 법을 익히면 Cassandra 데이터 모델링의 대부분을 이해한 것이다.

### 파티션 키(partition key): 어느 노드에 저장할지 정하는 좌표

파티션 키는 PRIMARY KEY 정의에서 **맨 앞에 오는 컬럼(들)** 이다. 괄호로 감싸면 여러 컬럼을 묶어 하나의 파티션 키로 만들 수 있고(복합 파티션 키, 뒤에서 다룬다), 괄호가 없으면 첫 번째 컬럼 하나가 파티션 키가 된다.

파티션 키는 2장(분산 아키텍처)에서 본 토큰 링과 직접 연결된다. Cassandra는 파티션 키 값을 **Murmur3 해시 함수**(`Murmur3Partitioner`가 기본값)에 넣어 -2⁶³ ~ 2⁶³-1 범위의 토큰(token) 하나를 만든다. 이 토큰이 토큰 링의 어느 구간에 속하는지에 따라 이 데이터의 "주인 노드"가 정해진다.

다만 Cassandra는 마스터가 없는(masterless) 구조이므로, 여기서 말하는 "주인"은 그 토큰 구간을 담당하는 첫 번째 복제 노드(natural endpoint)일 뿐이고 읽기와 쓰기를 독점하는 마스터가 아니다. 복제본 노드는 모두 대등하며, 어느 복제본이든 코디네이터를 거쳐 요청을 처리할 수 있다(3장 복제 전략과 데이터센터).

```text
       partition_key = "user_abc"
              │
              ▼
        Murmur3 해시
              │
              ▼
        token = 3812...  (64비트 정수)
              │
              ▼
   ┌─────────── 토큰 링 ───────────┐
   │   NodeA        NodeB          │
   │  [min..t1]   [t1..t2]         │
   │                  ▲            │
   │     token이 여기 떨어짐 → NodeB가 주인
   │   NodeD        NodeC          │
   │  [t3..max]   [t2..t3]         │
   └───────────────────────────────┘
```

여기서 가장 중요한 두 가지 성질이 나온다.

1. **같은 파티션 키 값은 항상 같은 토큰이 되므로, 항상 같은 노드 집합으로 간다.** 해시는 결정적(deterministic)이므로 `user_abc`의 모든 데이터는 항상 같은 노드(들)에 모여 있다. 이 성질 덕분에 단일 노드에서 빠르게 읽을 수 있다는 것이 보장된다.
2. **해시는 값의 순서를 보존하지 않는다.** `user_abc`와 `user_abd`는 알파벳 순서로는 이웃이지만, 해시한 뒤의 토큰은 링의 정반대편에 놓일 수 있다. 그래서 **파티션 키로는 범위 조회(`WHERE pk > x`)가 의미를 갖지 못한다.** `>`로 비교하더라도 그것은 토큰의 순서일 뿐 값의 순서가 아니기 때문이다. 뒤에서 설명할 "파티션 키는 등치(`=`) 조건만 가능하다"는 규칙도 이런 물리적 이유에서 나온다.

> [!note] 직관
> 파티션 키를 정하는 것은 데이터의 우편번호를 정하는 일과 같다. 우편번호가 같으면 같은 배송 트럭(노드)에 실린다. 그런데 우체국이 우편번호를 *해시*해서 트럭을 배정하므로, 1번지와 2번지가 전혀 다른 트럭에 실릴 수도 있다.

### 클러스터링 컬럼(clustering column): 파티션 내부의 정렬 기준

PRIMARY KEY에서 파티션 키 *뒤에* 오는 컬럼이 클러스터링 컬럼이다. 클러스터링 컬럼은 노드를 고르는 데는 전혀 관여하지 않는다. 대신 **하나의 파티션 안에서 행(row)들이 디스크에 어떤 순서로 정렬되어 저장될지**를 결정한다.

핵심은 "물리적으로 정렬되어 저장된다"는 점이다. RDB의 인덱스는 데이터와 별도로 존재하는 보조 자료구조다. 반면 Cassandra의 클러스터링 컬럼은 데이터 자체의 저장 순서이며, RDB로 치면 클러스터드 인덱스(clustered index)에 가깝다. 8장(Storage Engine 내부)에서 보겠지만, 하나의 파티션은 SSTable 안에서 클러스터링 컬럼 순서로 정렬된 연속된 행들의 블록으로 저장된다.

```text
  파티션 키 = user_42 인 단 하나의 파티션 (한 노드 위, 디스크에 연속 저장)
  ┌──────────────────────────────────────────────────────────────┐
  │ user_42                                                        │
  │   ├─ [2026-06-26 10:00] activity=login    ← 클러스터링 컬럼   │
  │   ├─ [2026-06-26 09:30] activity=pay       (created_at DESC) │
  │   ├─ [2026-06-25 22:10] activity=logout     로 미리 정렬됨    │
  │   └─ [2026-06-25 18:00] activity=view                         │
  └──────────────────────────────────────────────────────────────┘
       ▲ 같은 파티션 내부는 디스크에서 이미 이 순서로 누워 있다
```

이 구조 덕분에 "최근 활동 10개"를 읽는 작업은 정렬도 필터링도 아닌, **이미 정렬된 블록의 앞에서부터 10줄을 순차적으로 읽는(sequential scan) 연산**이 된다. 디스크 헤드가 한 번 자리를 잡고 이어서 읽기만 하면 된다. 이것이 시계열·타임라인 데이터에서 Cassandra가 강점을 보이는 이유다.

테이블 정의에 `WITH CLUSTERING ORDER BY (created_at DESC)`를 넣으면, 그 정렬 방향이 *디스크에 저장할 때부터* 적용된다. 따라서 최신순 조회가 대부분이라면, 처음부터 내림차순으로 저장해서 읽을 때 순서를 뒤집는 비용까지 없앨 수 있다.

### 파티션 키 + 클러스터링 컬럼 = 한 행을 가리키는 좌표

전체 PRIMARY KEY는 한 행을 유일하게 식별한다. 단, 이 식별은 두 단계로 나뉜다.

- **파티션 키**: "어느 파티션(어느 노드)인가"를 정한다. 클러스터 전체에서 데이터를 *찾아가는* 역할이다.
- **클러스터링 컬럼**: "그 파티션 안에서 정확히 어느 행인가"를 정한다. 파티션 내부에서 *정렬 순서와 정렬 범위*를 만드는 역할이다.

```cql
-- 예: 결제 이벤트 타임라인
CREATE TABLE payment_events_by_payment (
    payment_id   text,        -- 파티션 키: 어느 결제의 이벤트인가
    event_seq    bigint,      -- 클러스터링: 그 결제 안에서 몇 번째 이벤트인가
    event_type   text,
    payload      text,
    occurred_at  timestamp,
    PRIMARY KEY ( payment_id, event_seq )
) WITH CLUSTERING ORDER BY ( event_seq ASC );
```

이 테이블에서 `payment_id`는 "이 결제의 모든 이벤트를 한 노드에 모아라"라는 뜻이고, `event_seq`는 "그 안에서 발생 순서대로 정렬해 두어라"라는 뜻이다. 그 결과 특정 결제의 전체 이벤트 히스토리를 순서대로 읽는 작업은 단일 파티션을 한 번 순차적으로 읽는 것으로 끝난다. 이벤트 소싱 히스토리를 조회할 때 가장 이상적인 형태다.

## 3. 복합 파티션 키와 복합 클러스터링: 여러 차원의 좌표

### 복합 파티션 키 `((a, b))`: 여러 값을 묶은 하나의 우편번호

단일 컬럼으로 파티션을 나누면 파티션이 너무 커지거나 데이터가 한쪽으로 몰리는 경우가 있다. 이때는 **여러 컬럼을 괄호로 묶어 하나의 파티션 키**로 만든다.

```cql
PRIMARY KEY ( (sensor_id, day) , reading_time )
              └────────┬──────┘
              이 둘을 합쳐서 해시 → 토큰 1개
```

여기서 매우 중요한 점이 있다. `(sensor_id, day)`는 **두 값을 합쳐서 하나의 해시 입력**으로 사용한다. 따라서 파티션을 특정하려면 `sensor_id`와 `day`를 **둘 다** 등치 조건으로 지정해야 한다. 하나만 알아서는 토큰을 계산할 수 없고, 토큰을 모르면 어느 노드로 가야 할지 알 수 없다.

```cql
-- ✅ 가능: 두 컬럼 모두 등치 → 토큰 계산 가능 → 단일 파티션 타격
SELECT * FROM readings WHERE sensor_id = 's1' AND day = '2026-06-26';

-- ❌ 불가: day가 빠지면 토큰을 못 만든다 → 어느 노드로 갈지 모름
SELECT * FROM readings WHERE sensor_id = 's1';
```

복합 파티션 키는 단일 키로는 지나치게 커지는 파티션을 잘게 나누는 핵심 도구다(다음 절에서 다룰 버킷팅이 바로 이 기법이다).

### 복합 클러스터링: 다단계 정렬과 prefix 규칙

클러스터링 컬럼은 여러 개를 둘 수 있으며, 이 컬럼들은 **선언된 순서대로 다단계 정렬(sort)** 을 만든다. SQL의 `ORDER BY col1, col2, col3`를 디스크 저장 순서로 고정해 둔 것이라고 생각하면 정확하다.

```cql
CREATE TABLE sales_by_region (
    region      text,
    category    text,
    sold_at     timestamp,
    item_id     uuid,
    amount      bigint,
    PRIMARY KEY ( region, category, sold_at, item_id )
) WITH CLUSTERING ORDER BY ( category ASC, sold_at DESC, item_id ASC );
```

이 테이블에서 파티션(`region` 하나) 내부의 디스크 정렬 순서는 다음과 같다.

```text
region = "KR" 파티션 내부:
  category="book"   ├─ sold_at=10:00 ├─ item_id=a...
                    │                 └─ item_id=b...
                    └─ sold_at=09:00 └─ item_id=c...
  category="food"   ├─ sold_at=11:00 └─ item_id=d...
                    └─ sold_at=08:00 └─ item_id=e...
   ▲ 1차 정렬       ▲ 2차 정렬        ▲ 3차 정렬
   (category)       (sold_at)         (item_id)
```

이 다단계 정렬이 다음 절에서 다룰 prefix 규칙의 물리적 근거다. 전화번호부가 "성 → 이름" 순으로 정렬되어 있어서 성을 모르면 이름만으로는 찾을 수 없는 것과 같은 원리다.

## 4. WHERE 절의 규칙: 임의의 조건을 걸 수 없는 이유

이제 이 장에서 가장 많은 사람이 어려워하는 주제인 `WHERE` 절의 제약을 다룬다. 이 제약을 "Cassandra가 못 하는 것"의 목록으로 외울 것이 아니라, **저장 구조에서 필연적으로 따라 나오는 결과**로 이해하는 것이 핵심이다. 그렇게 이해하면 따로 외울 필요가 없다.

### 규칙 1: 파티션 키는 반드시 전부 등치(`=`)로 지정한다

쿼리는 거의 항상 파티션 키 *전체*를 `=`로 지정해야 한다. 이유는 2절에서 본 그대로다. 파티션 키를 모르면 토큰을 계산할 수 없고, 토큰이 없으면 코디네이터(coordinator) 노드는 이 요청을 어느 노드에 보내야 하는지 알 수 없다. 파티션 키는 데이터의 주소이고, 주소가 없으면 배달할 수 없다.

범위 조회(`>`, `<`)가 안 되는 이유도 같다. 해시는 값의 순서를 보존하지 않으므로(2절), `WHERE pk > 'm'`은 토큰 공간에서 아무 의미 없는 구간이 된다.

> [!note] 단 하나의 예외: `token()` 함수
> 파티션 키 *값*에 대한 범위 조건은 불가능하지만, 그 값의 *토큰*에 대한 범위 조건은 허용된다. `WHERE token(payment_id) > ? AND token(payment_id) <= ?`는 토큰 링을 구간 단위로 훑는 정상적인 쿼리이며, 전체 테이블 스캔이나 Spark 같은 분석 커넥터가 모든 파티션을 노드별로 나눠 순회할 때 바로 이 방식을 쓴다.
>
> 하지만 이 쿼리는 "특정 값의 범위"가 아니라 "링의 한 구간"을 읽는 것이므로, `WHERE pk > 'm'` 같은 값 기준 범위 조회를 결코 대신할 수 없다.

```cql
-- ✅ 파티션 키 전체를 등치로
SELECT * FROM payment_events_by_payment WHERE payment_id = 'pay_123';

-- ❌ 파티션 키에 범위 조건
SELECT * FROM payment_events_by_payment WHERE payment_id > 'pay_100';
-- Error: Only EQ relations are supported on partition key
```

### 규칙 2: 클러스터링 컬럼은 앞 컬럼부터 순서대로(prefix) 지정하고, 범위 조건은 마지막에 하나만 둔다

클러스터링 컬럼에 거는 조건은 다음 두 규칙을 모두 만족해야 한다.

1. **prefix 규칙**: 선언된 순서대로 앞에서부터 빠짐없이 조건을 채워야 한다. `(c1, c2, c3)`가 있을 때 `c2`에 조건을 걸려면 `c1`에도 조건이 있어야 하고, `c3`에 조건을 걸려면 `c1`과 `c2` 모두에 조건이 있어야 한다.
2. **마지막 범위 규칙**: 등치(`=`)로 연속해서 채운 뒤, *그 바로 다음 컬럼 하나*에만 범위 조건(`>`, `<`, `>=`, `<=`)을 걸 수 있다. 범위 조건을 건 컬럼 뒤의 컬럼에는 더 이상 조건을 걸 수 없다.

`IN`은 범위라기보다 "여러 등치 조건의 묶음"에 가깝다. 그래서 `c1 IN (...) AND c2 = ...`처럼 IN 뒤의 컬럼에도 조건을 이어서 걸 수 있다는 점이 실제 범위 연산과 다르다. 다만 IN은 지정한 값마다 별도의 슬라이스를 읽으므로 값의 개수가 늘어나면 비용도 그만큼 배로 늘어난다. 따라서 IN 목록을 크게 만드는 것은 피하는 것이 좋다.

왜 이런 규칙이 있을까? 3절의 다단계 정렬 그림을 다시 보자. 파티션 내부는 `category → sold_at → item_id` 순으로 정렬되어 있다. 이는 정확히 "정렬된 1차원 줄(sorted run)"이다. 디스크에서 효율적으로 할 수 있는 일은 **이 줄에서 연속된 구간(contiguous slice)을 잘라내는 것** 하나뿐이다.

```text
정렬된 줄에서 "연속 구간"을 자를 수 있는 조건:
  category="book" AND sold_at >= 09:00      → ✅ 한 덩어리로 연속
  ├──┬──┬──┐
  │  │  │  │  ← 여기부터 여기까지, 한 칼로 잘림

"category는 무시하고 sold_at >= 09:00"      → ❌ 줄 전체에 흩어짐
  book/10:00  food/11:00  book/09:00  food/08:00
   ✓           ✓           ✓           ✗
  ← 자르고 싶은 행들이 줄 곳곳에 흩어져 있어 "한 칼"로 못 자른다
```

`category`를 건너뛰고 `sold_at`에만 조건을 걸 수 없는 이유가 여기에 있다. `sold_at`은 *각 `category` 블록 안에서만* 정렬되어 있을 뿐, 파티션 전체에서 정렬되어 있지는 않다. 전화번호부에서 성을 무시하고 이름이 '철수'인 사람을 찾으려면 책 전체를 넘겨 봐야 하는 것과 같다. 이것은 슬라이스가 아니라 풀스캔이다.

범위 조건을 한 컬럼에만, 그것도 마지막 등치 컬럼 *바로 다음*에만 걸 수 있는 이유도 같다. 한 컬럼에 범위 조건을 걸어 구간을 열면, 그 구간 안에서는 다음 컬럼의 정렬이 더 이상 연속 구간을 보장하지 못한다. 범위 조건을 두 곳에 걸면 한 번에 잘라낼 수 있는 모양이 아니게 된다.

```cql
-- ✅ prefix를 채우고 마지막에 범위 1개
SELECT * FROM sales_by_region
 WHERE region = 'KR' AND category = 'book' AND sold_at >= '2026-06-01';

-- ❌ category(선행 컬럼)를 건너뜀
SELECT * FROM sales_by_region
 WHERE region = 'KR' AND sold_at >= '2026-06-01';
-- Error: PRIMARY KEY column "sold_at" cannot be restricted
--        as preceding column "category" is not restricted

-- ❌ 범위를 두 컬럼에
SELECT * FROM sales_by_region
 WHERE region = 'KR' AND category > 'a' AND sold_at >= '2026-06-01';
-- Error: Clustering column "sold_at" cannot be restricted (range on "category")
```

### 표로 정리한 WHERE 규칙

| 키 종류 | 허용되는 조건 | 이유(물리적 근거) |
|---|---|---|
| 파티션 키 | `=` (또는 `IN`), **전체 컬럼** 필수 | 해시→토큰으로 노드를 찾아야 함. 순서 정보 없음 |
| 클러스터링 컬럼 (선행) | `=` (prefix로 빈틈없이) | 정렬된 줄에서 연속 구간을 열어두기 위함 |
| 클러스터링 컬럼 (마지막 1개) | 범위(`>`,`<`,`>=`,`<=`) 허용 | 정렬된 줄의 연속 슬라이스를 자르는 연산 |
| 범위 뒤의 클러스터링 컬럼 | 조건 불가 | 범위가 열린 뒤엔 하위 정렬이 무의미 |
| 일반(non-key) 컬럼 | 기본 불가 (`ALLOW FILTERING` 필요) | 정렬·인덱스 없음 → 전수 검사 필요 |

> [!warning] 흔한 오해
> "`WHERE`에 `=`만 잘 쓰면 어떤 컬럼에든 조건을 걸 수 있을 것이다." 그렇지 않다. `=`든 `>`든, 그 컬럼이 *PRIMARY KEY의 적절한 위치*에 있지 않으면 거부된다. 조건 연산자의 문제가 아니라 **저장 정렬 구조에서의 위치** 문제다.

### `ORDER BY`에도 같은 규칙이 적용된다

CQL의 `ORDER BY`는 RDB처럼 임의로 정렬하지 못한다. 클러스터링 컬럼의 정렬 순서를 그대로 따르거나, 그 순서를 정확히 뒤집는 것(전체 컬럼을 한꺼번에 reverse)만 가능하다. 이제 이유는 분명하다. 데이터가 이미 그 순서로 디스크에 저장되어 있고, Cassandra가 할 수 있는 일은 그대로 읽거나 거꾸로 읽는 것뿐이기 때문이다. 새로운 순서로 정렬하려면 전체 데이터를 메모리에 올려 다시 정렬해야 하는데, 이는 Cassandra가 거부하는, 드러나지 않게 비용이 커지는 연산이다.

## 5. ALLOW FILTERING: 위험 신호인 이유

4절 표의 마지막 줄에서 보았듯이, 일반 컬럼이나 prefix 규칙을 어긴 조건으로 쿼리하면 Cassandra는 에러를 낸다. 그런데 그 에러 메시지 끝에는 종종 쓰고 싶어지는 한 줄이 붙어 있다.

```text
... If you want to execute this query despite the performance
unpredictability, use ALLOW FILTERING
```

`ALLOW FILTERING`을 붙이면 그 쿼리는 실행된다. 그래서 처음 Cassandra를 쓰는 사람은 이 키워드만 붙이면 된다고 생각하고 코드 곳곳에 넣는다. 이는 production에서 언제든 문제를 일으킬 수 있는 시한폭탄이다.

### `ALLOW FILTERING`이 실제로 하는 일

`ALLOW FILTERING`은 "효율적으로 잘라낼 수 없는 조건이지만, 그래도 **데이터를 다 읽어 와서 메모리에서 하나씩 검사해라**"라는 명령이다. 문제는 "다 읽어 오는" 범위를 통제할 수 없다는 데 있다.

파티션 키를 지정하지 않은 채 `ALLOW FILTERING`을 쓰면, 코디네이터는 **클러스터의 모든 노드에 "네 파티션을 전부 스캔해서 조건에 맞는 것을 보내라"** 고 요청한다. 노드가 100개라면 100개 노드 모두가 디스크 전체를 읽는다.

```text
SELECT * FROM payments WHERE status = 'FAILED' ALLOW FILTERING;

  Coordinator
      │ "status='FAILED'인 행 다 찾아와"
      ├──────────────► Node1: [전체 파티션 스캔] ─┐
      ├──────────────► Node2: [전체 파티션 스캔] ─┤
      ├──────────────► Node3: [전체 파티션 스캔] ─┼─► 다 모아서
      ├──────────────► ...                        │   메모리에서 필터링
      └──────────────► NodeN: [전체 파티션 스캔] ─┘
   읽는 데이터: 수억 행   →   결과: 12행
   (12행을 위해 수억 행을 디스크에서 읽고 네트워크로 옮긴다)
```

### 진짜 함정은 성능을 예측할 수 없다는 점이다

`ALLOW FILTERING`의 가장 위험한 점은 느리다는 것 자체가 아니라, **언제 느려질지 예측할 수 없다**는 것이다.

- 개발 환경: 테이블에 1만 행이 있다. `ALLOW FILTERING` 쿼리가 5ms 만에 결과를 돌려준다. 빠르다고 판단하고 배포한다.
- 6개월 후 production: 테이블에 5억 행이 있다. 같은 쿼리가 30초 걸리고, 그동안 코디네이터의 힙을 가득 채워 GC를 일으키며, 다른 정상 쿼리까지 타임아웃에 빠뜨린다.

쿼리는 한 글자도 바뀌지 않았는데, 데이터가 늘어나면서 성능이 **급격하게** 떨어진다. 더 나쁜 점은 이 문제가 부하가 가장 높은 시간대(데이터도 많고 트래픽도 많을 때)에 터진다는 것이다. RDB의 풀스캔은 옵티마이저가 경고를 주거나 인덱스를 추가해서 해결할 여지라도 있지만, Cassandra에서 `ALLOW FILTERING`은 *설계가 잘못되었다는 신호*다.

> [!note] 현장 규칙
> production 코드에 `ALLOW FILTERING`을 쓰고 싶어진다면, 그것은 이 쿼리를 위한 테이블이 아직 없다는 뜻이다. 해결책은 `ALLOW FILTERING`이 아니라 **새 테이블(또는 보조 인덱스 전략)을 추가하는 것**이다.
>
> 예외는 *이미 단일 파티션으로 범위를 좁힌 뒤* 그 파티션 안의 소량 데이터를 추가로 필터링하는 경우 정도다. 이때는 `WHERE pk = ... AND some_col = ... ALLOW FILTERING`처럼 파티션이 고정되어 있어 비용이 파티션 하나의 크기로 제한되므로 상대적으로 안전하다.

[[06 - 데이터 모델링 2 - 고급 타입과 안티패턴]]에서 보겠지만, 그래도 가끔은 키가 아닌 컬럼으로 조회하고 싶다는 요구는 보조 인덱스(secondary index), SASI, Storage-Attached Index(SAI, Cassandra 5.0의 핵심 신기능) 같은 도구로 해결해야 하며, `ALLOW FILTERING`으로 해결할 문제가 아니다.

## 6. 파티션 크기 설계: 너무 큰 파티션이라는 시한폭탄

Query-First로 테이블을 잘 설계했더라도 검증을 하나 더 통과해야 한다. **"이 파티션은 얼마나 커질 수 있는가?"** 이는 ④ 물리 모델 단계의 핵심 작업이며, production 사고가 가장 많이 나는 부분이기도 하다.

### 파티션은 나뉘지 않고 한 노드에 통째로 저장된다

먼저 물리적 사실부터 분명히 하자. **하나의 파티션은 결코 여러 노드에 나뉘어 저장되지 않는다.** 파티션 키 `user_42`에 속한 행은 1개든 1억 개든 모두 같은 노드(들)에 저장된다. 복제본도 마찬가지로 각 복제 노드에 통째로 복사된다. 단일 파티션 읽기가 빠르다는 보장에는 이런 대가가 따른다. 읽기가 빠른 대신 **한 파티션의 크기가 한 노드의 처리 능력에 묶인다.**

따라서 어떤 파티션이 한없이 커지면, 그 파티션을 가진 노드에서는 다음과 같은 문제가 생긴다.

- 읽기 지연 증가: 거대한 파티션의 일부만 읽더라도 인덱스 탐색과 디스크 I/O가 늘어난다.
- 복구·스트리밍 지연: 노드를 교체하거나 추가할 때 거대한 파티션을 통째로 스트리밍해야 한다.
- 컴팩션 부담: [[09 - Compaction 전략]]에서 다룰 컴팩션이 거대한 파티션을 처리할 때 메모리와 CPU를 과도하게 사용한다.
- JVM 힙 압박과 GC: 일부 연산은 파티션의 상당 부분을 힙에 올린다. 거대한 파티션은 GC 폭주와 노드 다운으로 이어질 수 있다.

### 권장 상한: "100MB / 10만 셀(cells)"이라는 경험칙

업계와 DataStax가 오랫동안 공유해 온 경험칙(rule of thumb)은 다음과 같다. *절대적인 규칙이 아니라 설계 가드레일로* 받아들이자.

- **파티션 크기: 대략 100MB 이하** (안전하게는 10MB 안팎을 목표로 하고, 100MB를 경고선으로 둔다)
- **파티션당 셀(cell) 수: 대략 10만(100,000) 이하**
- **파티션당 행(row) 수: 대략 10만 이하**: 위의 셀 기준과는 *별개인* 독립 가드레일이다. 셀 수는 대략 (행 수 × 일반 컬럼 수)이므로, 컬럼이 여러 개인 테이블이라면 행 수가 10만에 이르기 한참 전에 셀 한계에 먼저 걸린다. 세 기준 중 하나라도 넘으면 경고로 받아들이는 것이 안전하다.

여기서 "셀(cell)"이라는 단위가 중요하다. Cassandra의 저장 단위는 행이 아니라 셀이다.

```text
파티션의 셀 수 ≈ (행 수) × (행당 일반 컬럼 수)

예) 한 행에 일반 컬럼이 10개인 테이블에서
    행이 10,000개라면  → 셀 ≈ 10,000 × 10 = 100,000 셀 (경고선 도달)
```

컬럼이 많은 와이드(wide) 테이블은 행 수가 적어 보여도 셀 기준으로는 일찍 한계에 이른다. 파티션 크기를 추정할 때는 행 수만 보지 말고, **행 수 × 컬럼 수 × 평균 셀 크기**로 바이트 수와 셀 수를 함께 계산해야 한다.

한 가지는 분명히 해 두자. 위의 10만이라는 숫자는 어디까지나 *설계 가드레일*이지 시스템이 강제하는 한계가 아니다. 저장 포맷의 구조적인 하드 리밋은 파티션당 약 20억(2³¹) 셀이지만, 실무에서 그 근처의 값은 의미가 없다. 그보다 한참 전에 읽기 지연, GC 압박, 컴팩션 비용이 급격히 늘어나 노드가 먼저 버티지 못하기 때문이다. 그래서 실제로 신경 써야 하는 기준은 언제나 하드 리밋이 아니라 가드레일이다.

운영 중에는 `nodetool tablehistograms <keyspace> <table>` 로 실제 파티션 크기 분포(특히 99퍼센타일과 max)를 점검할 수 있다([[12 - 운영과 트러블슈팅]]).

```bash
nodetool tablehistograms myks payment_events_by_payment
# Partition Size (bytes)와 Cell Count의 분포에서
# Max / 99% 값이 가드레일을 넘는지 확인
```

### Unbounded partition: 가장 흔한 설계 실수

이런 위험은 모두 하나의 안티패턴으로 이어진다. 바로 **시간이 지날수록 한없이 커지는(unbounded) 파티션**이다. 전형적인 예를 보자.

```cql
-- ⚠️ 위험: sensor_id 하나가 영원히 자란다
CREATE TABLE readings_bad (
    sensor_id    text,
    reading_time timestamp,
    value        double,
    PRIMARY KEY ( sensor_id, reading_time )
) WITH CLUSTERING ORDER BY ( reading_time DESC );
```

이 테이블에서 센서 `s1`이 1초에 한 번씩 측정값을 쌓는다고 하자. 하루에 86,400행, 한 달에 약 260만 행, 1년에 약 3,150만 행이 쌓인다. `sensor_id='s1'` 파티션 하나가 끝없이 커져서 몇 달 안에 가드레일을 한참 넘기고, 결국 그 센서가 배정된 노드를 마비시킨다. 설계할 당시에는 아무 문제가 없어 보였다는 점이 이 함정의 본질이다.

### 해법: 시간 버킷팅(time bucketing)으로 파티션 나누기

해법은 파티션 키에 **시간 버킷(bucket)을 추가**해서, 한없이 커지는 파티션 하나를 크기가 제한된 여러 파티션으로 나누는 것이다. 3절에서 본 복합 파티션 키가 바로 이 역할을 한다.

```cql
-- ✅ 일(day) 단위로 버킷팅
CREATE TABLE readings_by_day (
    sensor_id    text,
    day          date,           -- 시간 버킷: 파티션 키의 일부
    reading_time timestamp,
    value        double,
    PRIMARY KEY ( (sensor_id, day), reading_time )
) WITH CLUSTERING ORDER BY ( reading_time DESC );
```

이제 `(sensor_id='s1', day='2026-06-26')`가 하나의 파티션이 되고, 그 안에는 하루치 데이터(86,400행)만 들어간다. 파티션이 매일 새로 생기므로 파티션 하나가 끝없이 커지지 않는다. 버킷 크기(일/시간/주/월)는 **데이터 유입 속도**에 맞춰 고른다.

```text
버킷 단위 선택의 기준:
  유입이 빠름(초당 다건)  → 시간(hour) 버킷, 심하면 분 버킷
  유입이 보통(분당 다건)  → 일(day) 버킷
  유입이 느림(시간당 다건) → 월(month) 버킷

목표: 한 버킷 파티션이 ~10만 셀 / ~100MB 안에 들도록 역산
```

버킷팅의 대가는 여러 날에 걸친 조회를 한 번의 쿼리로 처리할 수 없다는 점이다. 6월 한 달을 조회하려면 30개의 `day` 버킷을 각각(또는 `IN`이나 애플리케이션의 병렬 fan-out으로) 읽어야 한다. 이것은 추가 비용이라기보다 비용을 있는 그대로 드러내는 것이다. 30일치를 읽는 일은 곧 30개 파티션을 읽는 일이고, Cassandra는 그 비용을 숨기지 않을 뿐이다.

```cql
-- 6월 한 달 조회: 버킷을 명시적으로 fan-out
SELECT * FROM readings_by_day
 WHERE sensor_id = 's1' AND day IN ('2026-06-01','2026-06-02', ... ,'2026-06-30')
   AND reading_time >= '2026-06-01' AND reading_time < '2026-07-01';
-- (실무에서는 IN의 파티션 수를 적게 유지하고, 보통은 앱에서 날짜별로
--  병렬 쿼리를 던져 코디네이터 한 곳에 부하가 몰리는 것을 피한다)
```

## 7. Hotspot: 데이터가 한곳으로 몰릴 때

파티션 *크기* 문제가 "한 파티션이 너무 크다"는 것이었다면, hotspot 문제는 "트래픽이 소수의 파티션과 소수의 노드로 몰린다"는 것이다. 둘은 서로 다른 문제이지만, 둘 다 파티션 키를 어떻게 고르는지에서 비롯된다.

### 카디널리티가 낮은 파티션 키: 우편번호가 너무 적을 때

파티션 키의 카디널리티(cardinality, 서로 다른 값의 개수)가 낮으면 토큰 링 위에 파티션이 몇 개밖에 생기지 않고, 데이터와 트래픽이 그 소수의 노드로 집중된다.

```cql
-- ⚠️ 안티패턴: country를 파티션 키로
PRIMARY KEY ( country, user_id )
```

전 세계 사용자 대부분이 `country='KR'`이라면, `KR` 파티션 하나가 거대해지고(크기 문제) 동시에 그 파티션을 가진 노드로 읽기와 쓰기가 몰린다(hotspot 문제). 노드가 100개 있어도 실제로는 한두 노드만 일하게 된다. 수평 확장의 이점이 완전히 사라지는 것이다.

> [!note] 가이드
> 파티션 키는 **높은 카디널리티와 고른 분포**를 가져야 한다. 이상적으로는 클러스터의 노드 수보다 훨씬 많은 서로 다른 파티션이 생겨서, 데이터와 트래픽이 토큰 링 전체에 고르게 퍼져야 한다.

### 단조 증가하는 파티션 키: 항상 링의 같은 지점에만 쓰기가 몰린다

파티션 키가 **단조 증가(monotonically increasing)** 할 때는 더 알아차리기 어려운 hotspot이 생긴다. 타임스탬프나 순차 ID를 파티션 키로 쓰는 경우다.

```cql
-- ⚠️ 안티패턴: 시간 버킷을 "단독" 파티션 키로
PRIMARY KEY ( bucket_minute, event_id )   -- bucket_minute = 분 단위 시각
```

해시는 값을 고르게 흩어 놓지만, 문제는 *지금 이 순간의 쓰기가 모두 같은 파티션 키 값*으로 향한다는 데 있다. 현재 시각이 10:00이라면 새로운 쓰기는 모두 `bucket_minute='10:00'` 파티션으로 간다. 그 파티션은 노드 하나(와 복제본)에만 있으므로, 그 순간 클러스터 전체의 쓰기 부하가 한 노드로 몰린다. 1분 뒤에는 다음 노드로 옮겨 가면서 hotspot이 링을 따라 이동한다. 시계열 데이터를 시간만으로 파티셔닝하면 항상 이 함정에 빠진다.

### 해결책: 합성 키(salting)와 복합 분산

해결책은 파티션 키에 **값을 분산시키는 차원을 섞는 것**이다.

1. **자연 키와 결합**: 시간만 쓰지 말고 `(sensor_id, day)`처럼 카디널리티가 높은 자연 차원을 함께 묶는다. 같은 시간대의 쓰기라도 `sensor_id`가 제각각이므로 서로 다른 토큰으로 흩어진다. 6절의 버킷팅이 크기 문제와 hotspot 문제를 *동시에* 해결하는 이유가 여기에 있다.

2. **샤딩/솔팅(sharding/salting)**: 자연 키마저 한쪽으로 몰린다면, 인위적인 분산 컬럼(예: `bucket = hash(id) % N`)을 파티션 키에 추가한다.

```cql
-- 핫한 단일 키를 N개 샤드로 인위 분산
CREATE TABLE hot_counter_sharded (
    entity_id  text,
    shard      int,            -- 0..N-1, 쓰기 시 무작위/해시로 분배
    event_time timestamp,
    payload    text,
    PRIMARY KEY ( (entity_id, shard), event_time )
);
-- 읽을 때는 N개 샤드를 fan-out해서 합친다 (쓰기 분산의 대가)
```

샤딩은 쓰기를 N개 파티션으로 흩어서 hotspot을 N분의 1로 줄이지만, 읽을 때는 N개 파티션을 모아야 하는 비용이 생긴다. *쓰기 hotspot을 줄이는 대신 읽기 fan-out을 감수하는* 전형적인 트레이드오프다. 카운터나 리더보드처럼 단일 키에 쓰기가 몰리는 경우에만 신중하게 사용한다.

| 파티션 키 안티패턴 | 증상 | 처방 |
|---|---|---|
| 저카디널리티 (`country`) | 소수 거대 파티션 + 노드 쏠림 | 고카디널리티 자연 키로 교체/결합 |
| 단조 증가 (`timestamp` 단독) | hotspot이 링을 따라 이동 | 자연 차원과 결합, 또는 솔팅 |
| 무한 성장 (버킷 없는 자연 키) | unbounded partition | 시간 버킷팅 |
| 단일 핫 키 (인기 셀럽 ID) | 한 파티션에 쓰기 폭주 | 샤딩(salting) + 읽기 fan-out |

## 8. 실전 1: 사용자별 활동 타임라인

이제 방법론을 처음부터 끝까지 한 번 적용해 보자. 요구사항은 흔히 볼 수 있는 것이다. **"사용자가 자기 페이지에서 최근 활동을 시간 역순으로, 무한 스크롤로 본다."**

### ① 개념 / ② 워크플로 → 쿼리 도출

화면 흐름을 따라가며 접근 패턴을 적는다.

```text
Q1: 특정 user의 활동을 최신순으로 페이지네이션 조회
Q2: 특정 활동 1건의 상세 조회 (알림 클릭 → 딥링크)
Q3: 특정 user의 특정 종류(예: 'PAYMENT') 활동만 최신순 조회
```

### ③ 논리 / ④ 물리 → 쿼리마다 테이블 하나

Q1의 핵심은 사용자별 시간 역순이다. `user_id`를 파티션 키로 두고, 시간을 클러스터링 컬럼으로 삼아 내림차순으로 저장한다. 단, 활동이 많은 사용자의 파티션이 unbounded가 되지 않도록 월(month) 버킷을 추가한다.

```cql
-- Q1: 사용자 활동 타임라인 (최신순, 월 버킷)
CREATE TABLE activity_by_user (
    user_id      uuid,
    bucket_month text,          -- 'YYYY-MM' 시간 버킷
    activity_id  timeuuid,      -- 시간 순서 + 유일성을 한 컬럼에
    activity_type text,
    target_id    text,
    payload      text,
    PRIMARY KEY ( (user_id, bucket_month), activity_id )
) WITH CLUSTERING ORDER BY ( activity_id DESC );
```

여기서는 `timeuuid`(시간 기반 UUID)를 클러스터링 컬럼으로 쓴 것이 핵심이다. 이 컬럼 하나로 **시간 정렬과 행 유일성을 동시에** 해결한다. 같은 밀리초에 두 활동이 발생해도 timeuuid는 서로 다르므로 충돌하지 않고, 시간 순서도 보존된다. (`now()`/`maxTimeuuid()`/`minTimeuuid()`로 범위 조회도 할 수 있다.)

```cql
-- Q1 실행: 최신 페이지 (파티션 1개 순차 읽기)
SELECT * FROM activity_by_user
 WHERE user_id = 8b... AND bucket_month = '2026-06'
 LIMIT 20;

-- 다음 페이지: 마지막으로 본 activity_id 이후로 이어서
SELECT * FROM activity_by_user
 WHERE user_id = 8b... AND bucket_month = '2026-06'
   AND activity_id < 7f...      -- 커서 기반 페이지네이션
 LIMIT 20;
```

이 페이지네이션이 효율적인 이유를 살펴보자. 파티션이 `activity_id DESC` 순서로 디스크에 저장되어 있으므로, `activity_id < cursor`는 4절에서 설명한 "정렬된 줄의 연속 슬라이스"를 정확히 한 번에 잘라내는 연산이다. RDB의 `OFFSET` 기반 페이지네이션처럼 앞부분을 세어 가며 건너뛰는 낭비가 없다. 뒤쪽 페이지로 가더라도 비용이 일정하다.

Q2(활동 단건 상세)는 사용자를 거치지 않고 activity_id로 바로 찾아야 한다. 그래서 **별도 테이블**을 만든다. 같은 데이터를 다른 파티션 키로 중복 저장하는, 1절에서 설명한 비정규화다.

```cql
-- Q2: 활동 단건 조회 (activity_id가 파티션 키)
CREATE TABLE activity_by_id (
    activity_id   timeuuid,
    user_id       uuid,
    activity_type text,
    target_id     text,
    payload       text,
    PRIMARY KEY ( activity_id )
);
```

Q3(종류별 필터)는 `ALLOW FILTERING`을 쓰고 싶어지는 지점이다. 이 유혹을 단호히 거부하고 *테이블을 하나 더* 만든다. `activity_type`을 파티션 키에 포함해서 종류별로 미리 나누어 둔다.

```cql
-- Q3: 사용자의 특정 종류 활동 (type을 파티션 키에 포함)
CREATE TABLE activity_by_user_and_type (
    user_id       uuid,
    activity_type text,
    bucket_month  text,
    activity_id   timeuuid,
    target_id     text,
    payload       text,
    PRIMARY KEY ( (user_id, activity_type, bucket_month), activity_id )
) WITH CLUSTERING ORDER BY ( activity_id DESC );
```

세 테이블이 같은 활동을 세 번 저장한다. RDB의 관점에서는 끔찍해 보이지만 Cassandra의 관점에서는 올바른 설계다. 핵심은 **쓰기 시점에 세 테이블을 함께 갱신**할 책임이 애플리케이션(또는 `BATCH`)에 있다는 점이다. 활동은 불변(append-only)이므로 갱신 이상이 생길 위험이 거의 없고, 이 점이 설계를 안전하게 만든다.

같은 파티션을 공유한다면 원자적 `BATCH`로 묶을 수도 있다([[11 - LWT Batch Counter 내부]]에서 logged batch의 의미와 비용을 다룬다).

## 9. 실전 2: 시계열 센서 데이터

두 번째 예제는 IoT와 모니터링에서 전형적으로 쓰이는 **시계열(time-series)** 데이터다. 결제 시스템에서도 "초당 거래량 메트릭"이나 "서비스별 응답시간 시계열" 같은 형태로 똑같이 나타난다.

요구사항은 다음과 같다.

```text
Q1: 특정 센서의 특정 기간(하루/몇 시간) 측정값을 시간순 조회
Q2: 특정 센서의 가장 최근 측정값 N개 조회 (대시보드 실시간 패널)
```

6절과 7절에서 다룬 원칙을 모두 테이블 하나에 반영한다.

```cql
CREATE TABLE sensor_readings (
    sensor_id    text,
    bucket_hour  text,          -- 'YYYY-MM-DD-HH', 시간 버킷
    reading_time timestamp,
    value        double,
    unit         text,
    PRIMARY KEY ( (sensor_id, bucket_hour), reading_time )
) WITH CLUSTERING ORDER BY ( reading_time DESC )
  AND default_time_to_live = 7776000;   -- 90일 후 자동 만료 (TTL)
```

설계 선택의 근거를 하나씩 살펴보자.

- **`(sensor_id, bucket_hour)` 복합 파티션 키**: `sensor_id`는 카디널리티를 확보해 hotspot을 막고(7절), `bucket_hour`는 파티션을 1시간 단위로 나눠 unbounded 파티션을 막는다(6절). 초당 1건이 들어온다면 파티션 하나에 3,600행 안팎이 쌓이므로, 가드레일에 한참 못 미치는 적정한 크기다.
- **`reading_time DESC` 클러스터링**: Q2의 "최근 N개"를 `LIMIT N` 한 번으로 처리할 수 있도록 최신순으로 디스크에 저장한다.
- **`default_time_to_live`(TTL)**: 시계열 데이터는 오래될수록 가치가 급격히 떨어진다. TTL을 걸면 90일이 지난 데이터가 자동으로 만료되므로 파티션과 디스크 사용량이 한없이 늘어나지 않는다. TTL 만료는 tombstone을 만들고, 이는 9장(Compaction 전략), 특히 TWCS(Time Window Compaction Strategy)와 직접 연결된다. 시계열 데이터에 TTL을 쓸 때는 TWCS와 함께 쓰는 것이 정석이다.

```cql
-- Q1: 특정 시간 버킷 내 기간 조회 (단일 파티션 슬라이스)
SELECT reading_time, value FROM sensor_readings
 WHERE sensor_id = 'temp-01' AND bucket_hour = '2026-06-26-10'
   AND reading_time >= '2026-06-26 10:15:00'
   AND reading_time <  '2026-06-26 10:45:00';

-- Q2: 최근 5개 (DESC 정렬 덕에 그냥 앞 5줄)
SELECT reading_time, value FROM sensor_readings
 WHERE sensor_id = 'temp-01' AND bucket_hour = '2026-06-26-10'
 LIMIT 5;
```

Q1에서 `reading_time`에 범위 조건을 걸 수 있는 이유를 다시 확인하자. 파티션 키(`sensor_id`, `bucket_hour`)가 모두 `=`로 고정되었고(규칙 1), 그다음 클러스터링 컬럼 `reading_time` 하나에만 범위 조건이 걸렸다(규칙 2). 교과서적인 단일 파티션 슬라이스다.

여러 시간대에 걸친 조회에는 8절의 타임라인과 같은 트레이드오프가 따른다. "오전 10시부터 12시대까지"를 보려면 `bucket_hour`를 `10`, `11`, `12` 세 개로 fan-out 해야 한다.

버킷 단위(시간/일)는 이 fan-out 빈도와 파티션 크기 사이의 균형을 보고 정한다. 대시보드가 주로 "한 시간 창"을 본다면 시간 버킷이, "하루 추이"를 본다면 일 버킷이 fan-out을 가장 적게 만든다. **버킷 단위는 데이터 유입 속도와 주로 쓰이는 조회 창(query window)을 모두 고려해서 정한다.** 시계열 모델링에서 가장 실전적인 판단이 바로 이것이다.
