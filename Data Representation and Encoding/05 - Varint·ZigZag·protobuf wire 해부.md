이 시리즈의 바로 앞 장인 [[04 - 돈을 표현하는 법 - fixed-point와 decimal]]에서는 정수 하나에 금액과 스케일 같은 의미를 담는 방법을 다뤘다. 이제 그 정수를 **바이트로 직렬화**할 차례다.

가장 단순한 방법은 [[01 - 비트·바이트·엔디안]]에서 본 고정폭(fixed-width) 정수로, `int32`면 항상 4바이트, `int64`면 8바이트를 쓴다. 하지만 실제 데이터는 대부분 작은 수다. 사용자 ID 7번, 길이 0, 카운트 3을 8바이트로 보내면 7바이트를 0으로 채워 낭비하게 된다. 이 장에서는 이 낭비를 없애는 **가변길이 정수(variable-length integer)** 라는 아이디어 전체를 살펴본다.

흔히 varint를 protobuf에만 있는 것으로 좁게 생각하지만, protobuf는 varint를 쓰는 여러 사례 중 하나일 뿐이다. DWARF 디버그 정보, WebAssembly 바이트코드, MIDI 파일, SQLite의 레코드 포맷, Git 팩파일, Lucene 인덱스, ASN.1의 OID, CBOR과 Avro가 모두 저마다의 가변길이 정수를 쓴다.

protobuf wire 포맷의 **상세 구조**(필드 태그, 메시지 중첩, packed repeated 등)는 gRPC 시리즈의 [[03 - Protocol Buffers 2 - 인코딩과 와이어 포맷]]에서 다룬다. 이 장은 varint라는 발상 자체, 즉 7비트 그룹, continuation 비트, 부호 처리, 엔디안, 속도를 높인 변종, 그리고 보안 문제에 집중한다.

## 1. 왜 가변길이 정수인가: 작은 수가 대부분이라는 사실

### 1.1 고정폭의 낭비

고정폭 정수는 단순하고 빠르다. `uint32` 하나는 항상 4바이트이므로 메모리에 그대로 올리면 되고, 1장(비트·바이트·엔디안)에서 본 엔디안만 합의하면 된다. 랜덤 액세스도 쉽다. `i`번째 정수는 `base + 4*i`에 있다. CPU 입장에서도 유리하다. 정렬된 4/8바이트 로드는 한 사이클에 끝난다.

문제는 **실제 데이터의 분포**다. 직렬화되는 정수를 모아 히스토그램을 그려 보면 대다수가 작은 값이다.

```text
어떤 로그 레코드의 정수 필드 분포 (개념적)

값의 크기      빈도
0..127        ████████████████████████████  73%   (1바이트면 충분)
128..16383    ████████                      19%   (2바이트면 충분)
16384..2^21   ██                             6%
그 이상        ▏                              2%
```

값의 73%가 0~127 범위에 있는데 이를 `uint64`로 보내면 값 하나마다 7바이트가 0으로 채워진다. 레코드가 100만 개라면 7MB가 순수한 패딩이다. 이 패딩은 네트워크, 디스크, 캐시 모두에서 비용이 된다.

> varint는 "작은 수가 흔하다"는 경험적 사실을 전제로 한 인코딩이다. 흔한 경우(작은 수)는 짧게, 드문 경우(큰 수)는 길게 표현한다. 이는 정보이론에서 **빈도가 높은 심볼에 짧은 코드**를 주는 가변길이 코드(Huffman 부호화의 원리)와 같은 발상이다. SQLite 문서가 자신들의 varint를 아예 "static Huffman encoding of 64-bit integers"라고 부르는 것도 이 때문이다.

### 1.2 단위 비용: 7비트당 1비트의 오버헤드

varint의 기본 아이디어는 정수를 **7비트 단위**로 나누고, 각 바이트의 최상위 비트(MSB) 1개를 "**뒤에 더 있음(continuation)**" 플래그로 쓰는 것이다. 즉 한 바이트는 데이터 7비트와 제어 1비트로 이루어진다.

```text
varint 한 바이트의 구조

   bit7  bit6 ........ bit0
  ┌────┬───────────────────┐
  │ C  │   payload (7bit)   │
  └────┴───────────────────┘
    │            │
    │            └── 값의 7비트 조각
    └── continuation: 1 = 다음 바이트가 더 있다
                      0 = 이 바이트가 마지막
```

이 설계의 비용은 7비트마다 1비트, 즉 **약 12.5%의 오버헤드**다. 그래서 큰 수에서는 손해를 본다. 64비트를 꽉 채운 값을 7비트씩 자르면 ⌈64/7⌉ = 10조각, 즉 **10바이트** 가 되어 고정폭 8바이트보다 2바이트 크다. varint는 작은 수에서 아낀 공간으로 큰 수에서 생기는 손해를 메우는 방식이고, 실제 데이터 분포에서는 거의 항상 이득이 남는다.

| 값 범위 | varint 바이트 수 | fixed32 | fixed64 |
|---|---|---|---|
| 0 .. 127 | 1 | 4 | 8 |
| 128 .. 16,383 | 2 | 4 | 8 |
| 16,384 .. 2,097,151 | 3 | 4 | 8 |
| 2^21 .. 2^28−1 | 4 | 4 | 8 |
| 2^28 .. 2^32−1 | 5 | 4 | 8 |
| 2^32 .. 2^35−1 | 5 | - | 8 |
| … | … | - | … |
| 2^63 .. 2^64−1 | 10 | - | 8 |

표에서 손익분기점을 확인할 수 있다. 32비트 값은 약 2^28(2억 7천만) 이상부터 varint가 fixed32보다 커지고, 64비트 값은 2^56 부근부터 fixed64보다 커진다. 그보다 작은 값에서는 varint가 더 작다.

## 2. LEB128: 가변길이 정수의 표준형

가변길이 정수에서 가장 널리 쓰이는 형태는 **LEB128 (Little-Endian Base 128)** 이다. 이름에 정의가 그대로 담겨 있다. 밑(base)이 128(=2^7)인 자릿수를 **작은 자리부터(little-endian)** 나열한다. DWARF 디버그 포맷과 WebAssembly가 표준으로 채택했고, protobuf의 varint도 본질적으로 unsigned LEB128이다.

### 2.1 unsigned LEB128 인코딩: 손으로 따라가기

규칙은 세 가지다.

1. 값을 이진수로 쓰고, **하위 7비트부터** 7비트씩 그룹으로 자른다.
2. 그룹들을 **하위 그룹이 먼저** 오도록 바이트열로 나열한다.
3. 마지막 바이트를 제외한 모든 바이트의 MSB에 continuation 비트 1을 세운다. 마지막 바이트의 MSB는 0이다.

**예제 A: 300을 인코딩**

```text
300 = 0b1_0010_1100              (9비트)

하위 7비트부터 7비트씩 자르기:
   그룹0(하위): 010 1100  = 0x2C = 44
   그룹1(상위):      10  = 000 0010 = 0x02 = 2

little-endian으로 그룹0 먼저, 그룹1 나중:
   바이트0 = 그룹0 + continuation(1) = 1 0101100 = 0xAC
   바이트1 = 그룹1 + last(0)         = 0 0000010 = 0x02

결과:  AC 02
```

검산해 보면 디코더는 `44 + (2 << 7) = 44 + 256 = 300`을 얻는다. 이 `AC 02`는 protobuf 문서에 자주 나오는 예다.

**예제 B: 624485 (Wikipedia의 대표 예제)**

```text
624485 = 0b1001_1000_0111_0110_0101    (20비트)

하위 7비트씩 (몫/나머지로 계산):
   624485 mod 128 = 101         → 0x65   (그룹0)
   624485 // 128  = 4878
   4878   mod 128 = 14          → 0x0E   (그룹1)
   4878   // 128  = 38
   38     mod 128 = 38          → 0x26   (그룹2, 마지막)

continuation 붙이기:
   바이트0 = 0x65 | 0x80 = 0xE5
   바이트1 = 0x0E | 0x80 = 0x8E
   바이트2 = 0x26        = 0x26   (마지막, MSB 0)

결과:  E5 8E 26
```

검산하면 `0x65 + (0x0E << 7) + (0x26 << 14) = 101 + 1792 + 622592 = 624485`로 정확히 맞는다.

### 2.2 unsigned LEB128 디코딩: 손으로 따라가기

디코더는 continuation 비트가 0인 바이트를 만날 때까지 7비트씩 모은다. **shift는 7씩 증가**하고, 각 바이트의 payload를 해당 shift 위치에 OR한다.

```text
입력:  E5 8E 26  을 디코딩

byte0 = 0xE5 = 1110_0101 → C=1, payload = 110_0101 = 0x65 = 101
   result = 101 << 0           = 101
byte1 = 0x8E = 1000_1110 → C=1, payload = 000_1110 = 0x0E = 14
   result |= 14 << 7   (14*128=1792)   → 101 + 1792 = 1893
byte2 = 0x26 = 0010_0110 → C=0, payload = 010_0110 = 0x26 = 38   (마지막)
   result |= 38 << 14  (38*16384=622592) → 1893 + 622592 = 624485

디코딩 완료: 624485
```

### 2.3 의사코드

```python
def uleb128_encode(n: int) -> bytes:           # n >= 0
    out = bytearray()
    while True:
        byte = n & 0x7F          # 하위 7비트
        n >>= 7
        if n != 0:
            out.append(byte | 0x80)   # 더 있음 → continuation 켜기
        else:
            out.append(byte)          # 마지막
            break
    return bytes(out)

def uleb128_decode(buf: bytes) -> (int, int):  # (value, bytes_consumed)
    result = 0
    shift = 0
    for i, byte in enumerate(buf):
        result |= (byte & 0x7F) << shift
        if (byte & 0x80) == 0:        # continuation 0 → 끝
            return result, i + 1
        shift += 7
    raise ValueError("truncated varint")        # continuation이 안 끝남
```

> "LEB128은 protobuf가 만든 것"이라는 생각은 흔한 오해다. LEB128은 원래 **DWARF 디버깅 정보 표준**(컴파일러가 만드는 .debug_* 섹션)에서 정의되었고, 이름의 LEB도 여기서 왔다. WebAssembly 바이너리 포맷도 모든 정수 즉시값(immediate)을 LEB128로 기록한다. protobuf의 varint는 이 unsigned LEB128과 **같은 코덱**이다. protobuf는 varint를 발명한 것이 아니라 채택한 것이다.

## 3. signed LEB128: 부호확장으로 음수 담기

지금까지는 음이 아닌 정수만 다뤘다. 음수는 어떻게 표현할까? 서로 전혀 다른 두 가지 접근이 있고, 이 장에서 가장 중요한 비교가 여기서 시작된다. 첫째는 DWARF와 WASM이 쓰는 **signed LEB128 (SLEB128)** 이다.

### 3.1 발상: 2의 보수를 부호확장하며 자른다

signed LEB128은 값을 **2의 보수**로 보고 7비트씩 자르되, 위쪽으로 **부호 비트가 무한히 이어진다**고 가정한다. 양수면 위쪽이 전부 0, 음수면 위쪽이 전부 1로 채워진 무한 비트열로 보고, 더 잘라도 정보가 달라지지 않는 순간에 멈춘다.

unsigned와 다른 핵심은 멈춤 조건 하나뿐이다.

- 다음 경우에 멈춘다(이 바이트가 마지막이다).
  - 남은 값이 `0`이고 현재 바이트의 **부호 비트(payload의 최상위, 즉 bit6 = 0x40)가 0** 인 경우
  - 남은 값이 `-1`이고 현재 바이트의 **부호 비트(bit6)가 1** 인 경우
- 그 밖의 경우에는 continuation을 켜고 계속한다.

부호 비트(bit6)를 확인하는 이유는 마지막 7비트 조각의 최상위 비트가 부호를 **올바르게 표현**해야 하기 때문이다. 양수인데 마지막 조각의 bit6이 1이면 디코더가 음수로 잘못 해석하므로, 0x00 바이트를 하나 더 붙여야 한다.

### 3.2 손으로 따라가기: −123456

```text
value = -123456,  산술 우측 시프트(>>)는 부호 채움(음수는 -∞쪽으로 내림)

--- 반복 1 ---
byte  = -123456 & 0x7F
   -123456 mod 128 = 64        → byte = 0x40 = 0100_0000
value = -123456 >> 7 = floor(-123456/128) = -965
멈춤? value=-965 (0도 -1도 아님) → 계속, continuation
   emit 0x40 | 0x80 = 0xC0

--- 반복 2 ---
byte  = -965 & 0x7F
   -965 mod 128 = 59           → byte = 0x3B = 0011_1011
value = -965 >> 7 = floor(-965/128) = -8
멈춤? value=-8 → 계속, continuation
   emit 0x3B | 0x80 = 0xBB

--- 반복 3 ---
byte  = -8 & 0x7F = 0x78 = 0111_1000   (bit6 = 1)
value = -8 >> 7 = floor(-8/128) = -1
멈춤? value=-1 이고 bit6=1 → 멈춤!
   emit 0x78

결과:  C0 BB 78
```

디코딩으로 검산해 보자. `0x40 + (0x3B<<7) + (0x78<<14)` 를 모으면 `64 + 7552 + 1966080 = 1973696`이다. 마지막 바이트 `0x78`의 bit6이 1이므로 **부호확장**을 해서 21비트 위를 전부 1로 채운다. `1973696 − 2^21 = 1973696 − 2097152 = −123456`이 되어 원래 값이 정확히 복원된다.

### 3.3 작은 음수는 1바이트

signed LEB128의 장점은 **−1, −2 같은 작은 음수가 1바이트**라는 점이다.

```text
value = -1
byte  = -1 & 0x7F = 0x7F = 0111_1111   (bit6 = 1)
value = -1 >> 7 = -1
멈춤? value=-1 이고 bit6=1 → 멈춤
결과:  7F       (단 1바이트!)
```

`0x7F`를 디코딩하면 payload는 `1111111`이고, 마지막 바이트의 bit6이 1이므로 부호확장을 한다. 7비트 `1111111`을 위쪽으로 무한히 1로 확장하면 `−1`이 된다. 범위로 보면 signed LEB128에서는 **−64 ~ 63** 이 1바이트(7비트 부호 정수 범위)이고, −65나 64부터는 2바이트다.

### 3.4 의사코드

```python
def sleb128_encode(n: int) -> bytes:
    out = bytearray()
    while True:
        byte = n & 0x7F
        n >>= 7                          # 산술 시프트 (부호 채움)
        sign_bit_set = (byte & 0x40) != 0
        if (n == 0 and not sign_bit_set) or (n == -1 and sign_bit_set):
            out.append(byte)             # 마지막
            return bytes(out)
        out.append(byte | 0x80)

def sleb128_decode(buf: bytes, width=64) -> int:
    result, shift = 0, 0
    for byte in buf:
        result |= (byte & 0x7F) << shift
        shift += 7
        if (byte & 0x80) == 0:
            if shift < width and (byte & 0x40):   # 부호 비트 켜져 있으면
                result |= (~0 << shift)           # 위쪽을 1로 부호확장
            return result
    raise ValueError("truncated")
```

DWARF는 abbreviation 코드나 라인 번호 프로그램의 주소 증분 등에서 양수에는 ULEB128을, 부호 있는 증분에는 SLEB128을 섞어 쓴다. WebAssembly도 `i32.const`, `i64.const` 같은 즉시값은 SLEB128로, 음이 아닌 길이와 인덱스는 ULEB128로 기록한다. **부호 유무에 따라 코덱을 바꾸는** 이 설계는 뒤에서 볼 protobuf의 선택과 정반대다.

## 4. protobuf varint와 LEB128, 그리고 음수 int32가 10바이트인 이유

### 4.1 protobuf는 코덱을 하나만 쓴다

protobuf wire 포맷의 정수 필드는 모두 **unsigned LEB128이라는 하나의 코덱**으로 직렬화된다. `int32`, `int64`, `uint32`, `uint64`, `bool`, `enum`은 모두 wire type 0(varint)이고, 값을 **부호 없는 64비트 정수로 본 뒤** ULEB128로 기록한다. 핵심은 부호 처리를 위해 signed LEB128을 도입하지 않는다는 점이다.

필드 태그와 wire type의 자세한 내용은 gRPC 시리즈 3장(Protocol Buffers 2 인코딩과 와이어 포맷)에서 다루고, 여기서는 표 하나로만 요약한다.

| wire type | 약칭 | 코덱 | 담는 타입 |
|---|---|---|---|
| 0 | VARINT | ULEB128 | int32/64, uint32/64, sint32/64, bool, enum |
| 1 | I64 | 고정 8바이트 LE | fixed64, sfixed64, double |
| 2 | LEN | 길이(varint)+바이트 | string, bytes, 중첩 메시지, packed repeated |
| 5 | I32 | 고정 4바이트 LE | fixed32, sfixed32, float |

(wire type 3과 4는 deprecated된 group이다.) 태그 자체도 varint이며, `tag = (field_number << 3) | wire_type`으로 계산한다. 필드 1, wire type 0이면 태그는 `(1<<3)|0 = 0x08`이다.

**미니 예제: 필드 1(int32) = 150**

```text
태그   = (1<<3)|0 = 0x08
값 150 = 0b1001_0110
   하위 7비트 = 001_0110 = 0x16,  남은 비트 = 1
   바이트0 = 0x16 | 0x80 = 0x96
   바이트1 = 0x01
와이어:  08 96 01      (태그 + varint)
```

### 4.2 음수 int32가 10바이트가 되는 과정 재현

protobuf에서 가장 잘 알려진 함정이다. `int32` 필드에 **음수**를 넣으면 항상 **10바이트**가 된다. 이유는 4.1의 규칙에 그대로 들어 있다. 음수를 부호 없는 64비트 정수로 보기 때문에, 음수는 64비트로 **부호확장된 매우 큰 수**가 되고, 이를 ULEB128로 자르면 10조각이 된다.

`int32 = -123456`을 직접 바이트로 인코딩해 보자.

```text
-123456 을 64비트 2의 보수로 부호확장:
   123456    = 0x000000000001E240
   -123456   = 0xFFFFFFFFFFFE1DC0   (64비트)

이 64비트 값을 ULEB128(하위 7비트씩)로 자르면:

  group0 (bit0-6)   : 100_0000 = 0x40
  group1 (bit7-13)  : 011_1011 = 0x3B
  group2 (bit14-20) : 111_1000 = 0x78
  group3..8 (bit21-62): 전부 1 = 0x7F  (여섯 그룹)
  group9 (bit63)    : 1       = 0x01

continuation 붙이기 (마지막만 0):
  C0 BB F8 FF FF FF FF FF FF 01      ← 10바이트!
```

여기서 **결정적인 차이**가 드러난다. signed LEB128로 −123456을 인코딩하면 `C0 BB 78`(3바이트)였다. 두 인코딩의 **앞 두 바이트 `C0 BB`는 똑같다**. 차이는 세 번째 바이트에서 생긴다.

- signed LEB128: 세 번째 그룹이 `0x78`이고 bit6이 1이므로, 여기서부터 위쪽은 전부 부호(1)라고 판단해 **멈춘다**.
- protobuf(64비트 값의 ULEB128): 같은 그룹이지만 64비트를 끝까지 채워야 하므로 `0x78 | 0x80 = 0xF8`로 **continuation을 켜고**, 1로 가득 찬 바이트를 끝까지 내보낸다.

같은 정보(작은 음수)를 두고, 코덱이 부호를 아는 방식(SLEB128)과 부호를 모르는 단일 코덱으로 64비트를 통째로 기록하는 방식(protobuf)의 결과가 3바이트와 10바이트로 갈린다. 가장 극단적인 예는 `int32 = -1`이다.

```text
-1 (64비트) = 0xFFFFFFFFFFFFFFFF
ULEB128:  FF FF FF FF FF FF FF FF FF 01   (10바이트)
```

> protobuf에서 음수가 될 수 있는 정수 필드에는 `int32/int64`(부호확장 → 음수 10바이트)가 아니라 **`sint32/sint64`(ZigZag)** 를 써야 한다. 양수만 나온다면 `int32`도 괜찮지만, 음수가 흔하다면 `sint`가 최대 약 8배(10바이트 → 1~2바이트) 유리하다. `uint32/uint64`는 애초에 음수가 없으므로 부호확장 문제도 없다.

그렇다면 protobuf는 왜 처음부터 signed LEB128을 쓰지 않고 ZigZag라는 별도 장치를 두었을까? 이것이 다음 절의 주제다.

## 5. ZigZag: 음수를 작은 양수로 접는 수학

### 5.1 문제 재정의

목표는 분명하다. **절댓값이 작은 수는 부호와 관계없이 짧게** 표현하는 것이다. −1도 1바이트, +1도 1바이트, −2도 1바이트여야 한다. 즉 0 근처의 작은 정수를 모두 작은 unsigned 값으로 매핑한 뒤, protobuf가 이미 가진 유일한 코덱인 ULEB128로 기록하면 된다. 코덱을 새로 만들지 않고 **전처리 변환**만 추가하는 것, 이것이 ZigZag의 설계 의도다.

### 5.2 매핑: 부호를 LSB로 접기

ZigZag는 정수 직선을 **지그재그로 접어** 음수와 양수를 번갈아 자연수에 대응시킨다.

```text
원래값 n :  0   -1    1   -2    2   -3    3   -4 ...
zigzag u :  0    1    2    3    4    5    6    7 ...
              \  /  \  /  \  /  \  /
               접는 선
```

여기서 규칙을 읽을 수 있다. **0과 양수는 짝수, 음수는 홀수**가 되고, 절댓값이 커질수록 u도 커진다. u의 최하위 비트(LSB)가 부호를 나타낸다. 0이면 양수, 1이면 음수다.

### 5.3 수학 유도

32비트 정수에서 ZigZag 인코딩은 다음 한 줄로 표현된다.

```text
encode(n) = (n << 1) XOR (n >> 31)      (>>는 산술 시프트)
encode(n) = (n << 1) XOR (n >> 63)      (64비트면 63)
```

이 식이 왜 5.2의 매핑을 만드는지 나눠서 살펴보자. `n >> 31`은 부호 비트를 31칸 복제하는 산술 시프트이므로, **n이 음수면 0xFFFFFFFF(= 전부 1 = −1), 양수면 0x00000000(= 0)** 이다. 즉 부호 마스크 역할을 한다.

- **양수 n**: `(n<<1) XOR 0 = n<<1` = 2n이므로 짝수가 된다. (n=3 → 6)
- **음수 n**: `(n<<1) XOR 0xFFFFFFFF` = `NOT(n<<1)` = `~(2n)` = `−(2n) − 1` = `2|n| − 1`이므로 홀수가 된다. (n=−3 → 2·3−1 = 5)

디코딩은 이 변환의 역변환이다.

```text
decode(u) = (u >> 1) XOR -(u & 1)        ((u>>1)은 논리 시프트)
```

`u & 1`이 부호 비트다. 이 값이 0이면 `−(0)=0`이므로 `(u>>1) XOR 0 = u/2`가 된다. 1이면 `−(1) = 0xFFFFFFFF`이므로 `(u>>1) XOR 0xFFFFFFFF = ~(u>>1) = −(u>>1)−1`이 된다. 검산해 보자.

```text
u=4 → (4>>1)=2, -(4&1)=0,  2 XOR 0 = 2          ✓ (원래 +2)
u=3 → (3>>1)=1, -(3&1)=-1, 1 XOR (-1) = ~1 = -2  ✓ (원래 -2)
u=1 → (1>>1)=0, -(1&1)=-1, 0 XOR (-1) = -1       ✓ (원래 -1)
```

### 5.4 매핑표와 바이트 결과

| n (signed) | zigzag u | u의 varint |
|---|---|---|
| 0 | 0 | `00` |
| −1 | 1 | `01` |
| 1 | 2 | `02` |
| −2 | 3 | `03` |
| 2 | 4 | `04` |
| 63 | 126 | `7E` |
| −64 | 127 | `7F` |
| 64 | 128 | `80 01` |
| −65 | 129 | `81 01` |
| 2147483647 | 4294967294 | `FE FF FF FF 0F` |
| −2147483648 | 4294967295 | `FF FF FF FF 0F` |

1바이트로 표현되는 범위는 **−64 ~ 63** (u가 0~127)이다. 흥미롭게도 이는 signed LEB128의 1바이트 범위와 **정확히 같다**. 둘 다 7비트의 표현력을 부호 1비트와 크기 6비트로 나눠 쓰기 때문이다.

### 5.5 손으로 따라가기: sint32 = −123456

```text
n = -123456
encode = (n << 1) XOR (n >> 31)
   n << 1  = -246912
   n >> 31 = -1            (음수라 부호 마스크 = 전부 1)
   -246912 XOR -1 = ~(-246912) = 246912 - 1 = 246911

zigzag = 246911 을 ULEB128로:
   246911 mod 128 = 127 → 0x7F,  246911//128 = 1928
   1928   mod 128 = 8   → 0x08,  1928//128   = 15
   15     mod 128 = 15  → 0x0F   (마지막)
   continuation:  FF 88 0F

결과:  sint32(-123456) = FF 88 0F      (3바이트)
```

### 5.6 같은 수, 세 가지 인코딩의 최종 비교

`−123456`이라는 같은 값이 코덱에 따라 다음과 같이 달라진다.

```text
signed LEB128         :  C0 BB 78                        (3바이트)  ← DWARF/WASM
protobuf int32(ULEB128):  C0 BB F8 FF FF FF FF FF FF 01  (10바이트) ← 부호확장
protobuf sint32(ZigZag):  FF 88 0F                        (3바이트) ← 전처리 변환
```

### 5.7 signed LEB128과 ZigZag: 이 장의 핵심 비교

두 방식은 작은 음수를 짧게 표현한다는 같은 목표를 달성하고, 1바이트 범위(−64~63)도 같다. 하지만 **설계 철학이 다르다**.

| 측면 | signed LEB128 | ZigZag + ULEB128 |
|---|---|---|
| 부호를 누가 아는가 | **코덱이 안다** (SLEB128/ULEB128 별개 코덱) | **코덱은 모른다**. 부호는 사전 변환이 처리 |
| 부호 처리 메커니즘 | 마지막 바이트 bit6의 부호확장 | LSB로 부호를 접는 비트 트릭 |
| 필요한 코덱 수 | 2개 (부호 유무로 분기) | 1개 (ULEB128) + 변환 함수 |
| 작은 음수(−1) | `7F` 1바이트 | `01` 1바이트 |
| 디코딩 분기 | 마지막 바이트에서 부호확장 분기 | 변환은 분기 없는 비트연산 |
| 채택처 | DWARF, WebAssembly | protobuf `sint`, Avro, 다수의 컬럼 스토어 |
| 직교성 | 부호가 코덱과 얽혀 있음 | 변환과 코덱이 **분리(orthogonal)** |

protobuf의 선택을 한 문장으로 정리하면 **"코덱은 하나(ULEB128)만 두고, 부호 문제는 직교적인 변환(ZigZag)으로 분리한다"** 이다. 그 덕분에 wire 포맷의 정수는 모두 같은 디코드 루프를 거치고, 부호 있는 타입은 그 위에 ZigZag 변환 하나만 더하면 된다.

반면 DWARF와 WASM은 부호 유무에 따라 SLEB128과 ULEB128을 명시적으로 바꿔 쓰는, **코덱이 부호를 아는** 모델을 택했다. 둘 다 올바른 설계다. 분기를 코덱 선택에 둘지, 변환 함수에 둘지의 차이일 뿐이다.

> "ZigZag는 압축 알고리즘이다." 그렇지 않다. ZigZag는 압축이 아니라 **재매핑(bijection)** 이다. 비트 수를 줄이지 않고, 음수를 작은 unsigned 값으로 옮겨 *뒤따르는* varint가 짧아지게 할 뿐이다. 실제로 ZigZag만 적용하고 varint를 쓰지 않으면 바이트 수는 변하지 않는다. ZigZag는 항상 varint(또는 다른 가변길이 코덱)와 **짝**을 이뤄 쓰인다.

> "sint는 int보다 항상 작다." 그렇지 않다. **음수에서만** 유리하다. 큰 양수에서는 ZigZag가 왼쪽으로 한 칸 시프트(×2)하므로 경계에서 오히려 1바이트 커질 수 있다. 예를 들어 양수 `2^28−1`은 int32로 4바이트지만, sint32(zigzag로 ×2 → 약 2^29)로는 5바이트다. 값의 부호 분포를 보고 골라야 한다.

## 6. 엔디안의 함정: LEB128(LE)과 VLQ(BE)

### 6.1 같은 7비트인데 순서가 반대

LEB128의 LE는 "Little-Endian"으로, **하위 7비트 그룹을 먼저** 보낸다는 뜻이다. 그런데 7비트 continuation 인코딩을 쓰면서도 **반대로 상위 그룹을 먼저** 보내는 표준도 많다. 대표적인 예가 **VLQ (Variable-Length Quantity)** 로, MIDI 파일의 델타 타임이나 표준 MIDI 메타 이벤트 길이 등에 쓰인다. VLQ는 **big-endian**, 즉 가장 상위 그룹을 먼저(most significant group first) 보낸다.

같은 7비트 그룹과 같은 continuation 비트를 쓰는데도 그룹을 나열하는 순서가 정반대이므로, **같은 숫자가 다른 바이트열**이 된다. 디코더를 바꿔 쓸 때 생기는 흔한 버그가 여기서 나온다.

### 6.2 손으로 보는 비교: 128

```text
값 128 = 0b1_0000000   (8비트)
그룹0(하위 7비트) = 0000000 = 0
그룹1(상위)       =       1 = 1

LEB128 (little-endian, 하위 먼저):
   바이트0 = 그룹0 + cont = 1000_0000 = 0x80
   바이트1 = 그룹1 + last = 0000_0001 = 0x01
   →  80 01

VLQ (big-endian, 상위 먼저):
   바이트0 = 그룹1 + cont = 1000_0001 = 0x81
   바이트1 = 그룹0 + last = 0000_0000 = 0x00
   →  81 00
```

결과는 `80 01`과 `81 00`이다. **continuation 비트의 위치도 자연스럽게 반대**가 된다. LE에서는 마지막(상위) 바이트의 MSB가 0이고, BE에서는 첫(상위) 바이트의 MSB가 1이고 마지막(하위) 바이트의 MSB가 0이다.

### 6.3 VLQ(MIDI) 대표 표

MIDI 표준 스펙에 실린 VLQ 예시(big-endian)다. 이 표는 외워 둘 만하다.

| 정수값(hex) | VLQ 바이트열 |
|---|---|
| 0x0000_0000 | `00` |
| 0x0000_0040 | `40` |
| 0x0000_007F | `7F` |
| 0x0000_0080 | `81 00` |
| 0x0000_2000 | `C0 00` |
| 0x0000_3FFF | `FF 7F` |
| 0x0010_0000 | `C0 80 00` |
| 0x001F_FFFF | `FF FF 7F` |
| 0x0FFF_FFFF | `FF FF FF 7F` |

> "7비트 그룹 + continuation 비트"는 하나의 *아이디어*일 뿐이고, 그룹을 나열하는 **방향은 표준마다 다르다**. 1장(비트·바이트·엔디안)에서 본 바이트 단위 엔디안 문제가 여기서는 7비트 그룹 단위 엔디안이라는 한 단계 위의 형태로 다시 나타난다. 디코더를 작성할 때는 이 varint가 LE인지 BE인지를 가장 먼저 확정해야 한다. 둘은 호환되지 않는다.

엔디안이 갈리는 데에는 실용적인 이유도 있다. **BE varint는 사전식(lexicographic) 바이트 비교가 수치 순서와 일치**할 여지가 있어 정렬 키로 쓰기 좋다(상위 자리가 앞에 오기 때문이다). 반대로 **LE varint는 인코딩이 단순하고**(하위부터 차례로 잘라 내면 된다), 디코드 루프에서 shift만 누적하면 된다. SQLite가 정렬 가능한 키 표현을 염두에 두고 big-endian varint를 택한 것도 이 때문이다.

## 7. 여러 varint 변종: SQLite·Git·Lucene·base128

같은 발상이 시스템마다 조금씩 다른 규칙으로 구현되어 있다. 이 변종들의 독특한 규칙을 비교하면 설계 트레이드오프를 여러 각도에서 이해할 수 있다.

### 7.1 SQLite varint: 1~9바이트, 9번째는 8비트 전부 데이터

SQLite의 레코드 포맷이 쓰는 varint는 LEB128과 두 가지가 다르다.

1. VLQ처럼 **big-endian** (상위 그룹 먼저)이다.
2. **최대 9바이트**이고, **9번째 바이트는 continuation 규칙을 따르지 않고 8비트를 전부 데이터로** 쓴다.

규칙은 다음과 같다. 처음 8바이트는 각각 MSB가 continuation이고 하위 7비트가 데이터다. 8번째 바이트까지 MSB가 켜져 있으면 9번째 바이트가 이어지고, 그 **9번째 바이트는 8비트 모두 데이터**다. 그래서 8×7 + 8 = **64비트**를 정확히 9바이트에 담는다.

```text
값 300 (SQLite varint, big-endian):
   300 = 0b1_0010_1100
   그룹1(상위)=2=000_0010, 그룹0(하위)=44=010_1100
   바이트0 = 2 | 0x80 = 0x82
   바이트1 = 44       = 0x2C
   →  82 2C

비교:  LEB128(300) = AC 02     (LE, 순서·continuation 위치 모두 반대)
```

9번째 바이트 규칙의 장점은 **상한**에서 드러난다. 64비트가 전부 1인 `0xFFFFFFFFFFFFFFFF`를 기록해 보자.

```text
SQLite : FF FF FF FF FF FF FF FF FF      (9바이트, 9번째가 8비트 통째)
LEB128 : FF FF FF FF FF FF FF FF FF 01   (10바이트)
```

SQLite는 64비트 최댓값을 **9바이트**에 담는다. LEB128이 10번째 바이트(`01`)를 써서 담는 마지막 1비트를 SQLite는 9번째 바이트의 남는 비트로 흡수한다. 작은 차이처럼 보이지만, 최악의 경우에도 10바이트가 아니라 9바이트라는 보장은 레코드 헤더 크기를 계산할 때 실질적인 의미가 있다.

### 7.2 Git의 가변길이 정수: 두 종류와 bijective 트릭

Git 팩파일은 varint를 **두 가지** 쓴다.

**(a) 오브젝트 헤더 크기**는 LEB128 계열(little-endian)이다. 다만 첫 바이트는 특수하다. 상위 3비트가 오브젝트 타입, 그다음 비트가 continuation, 하위 4비트가 크기의 최하위 4비트다. 두 번째 바이트부터는 일반적인 7비트 단위다.

```text
첫 바이트:  C TTT SSSS
            │ │   └ 크기 하위 4비트
            │ └── 타입(3비트)
            └──── continuation
이후 바이트: C SSSSSSS  (7비트씩, little-endian)
```

**(b) ofs-delta 오프셋**이 더 흥미롭다. 델타 베이스까지의 거리를 기록하는 이 인코딩은 big-endian이면서 **"+1 트릭"** 으로 **중복 없는(bijective) 인코딩**을 만든다. 디코드는 다음과 같다.

```python
def git_ofs_decode(read):
    c = read()
    offset = c & 0x7F
    while c & 0x80:
        c = read()
        offset = ((offset + 1) << 7) | (c & 0x7F)   # 매 단계 +1
    return offset
```

핵심은 이 `+1` 한 줄이다. 일반적인 7비트 varint에는 **overlong** 문제가 있다. 예를 들어 값 0을 `00`으로도, `80 00`으로도 기록할 수 있다(앞 바이트는 의미 없는 0 그룹이다). Git의 ofs 인코딩은 바이트가 늘어날 때마다 1을 더해 두 표현이 절대 겹치지 않게 한다.

그 결과 n바이트로 표현할 수 있는 값의 범위가 (n−1)바이트 범위 바로 뒤에 **정확히 이어져서** 빈틈도 중복도 없다. 모든 값에 **유일한 최단 인코딩**이 존재한다. 9.4절의 보안 논의에서 다시 다룰, 중복(redundancy)을 설계 단계에서 없앤 좋은 사례다.

### 7.3 Lucene VInt

Apache Lucene의 인덱스 포맷은 양의 정수를 **VInt**로 기록하는데, 이는 본질적으로 little-endian LEB128(ULEB128)이다. 32비트 양수는 최대 5바이트가 된다. Lucene 포스팅 리스트(문서 ID 간격, 텀 빈도)는 전통적으로 작은 값 위주라 VInt가 잘 맞았다.

음수는 부호확장 때문에 항상 5바이트가 되므로, 음수가 필요한 곳에서는 ZigZag를 적용한 **zig-zag VInt**를 따로 쓴다. protobuf의 int와 sint 구분과 똑같은 구도가 검색 엔진에서도 나타나는 것이다.

### 7.4 base-128: ASN.1 OID의 인코딩

X.509 인증서 안의 **OID(Object Identifier)** 도 7비트 continuation 인코딩, 즉 **base-128 big-endian**(= VLQ)을 쓴다. 각 OID 서브식별자(arc)를 base-128로, MSB를 continuation으로 삼아 큰 자리부터 기록한다. 자세한 내용은 [[11 - ASN.1·DER·PEM - 인증서를 바이트로]]에서 다루지만, 핵심 인코딩이 이 장의 VLQ와 같다는 점을 손으로 확인해 두자.

```text
OID 1.2.840.113549  (RSA 계열 OID들의 그 공통 prefix)

첫 두 arc 1.2 → 한 바이트로 합침: 1*40 + 2 = 42 = 0x2A

840 = base128 (big-endian):
   840 = 6*128 + 72 → 그룹[6, 72]
   바이트: 6|0x80=0x86, 72=0x48  →  86 48

113549 = base128:
   113549 //128=887 r13,  887//128=6 r119,  6//128=0 r6
   그룹[6, 119, 13] → 6|0x80=0x86, 119|0x80=0xF7, 13=0x0D
   →  86 F7 0D

전체:  2A 86 48 86 F7 0D
```

`2A 86 48 86 F7 0D`는 인증서를 분석해 본 사람이라면 익숙한 바이트열로, RSA 관련 OID들의 공통 앞부분이다. 7비트 varint는 1980년대 ITU-T X.680/X.690 표준에 이미 들어 있었다. protobuf는 한참 뒤에 등장한 후손이다.

| 변종 | 엔디안 | 바이트당 데이터 | 최대 길이(64bit) | 특이점 |
|---|---|---|---|---|

## 8. 속도 지향 변종: continuation 분기를 없애라

### 8.1 varint가 느린 진짜 이유

varint 디코드 루프의 문제는 **바이트마다 "더 있는가?"를 확인하는 분기**가 있다는 점이다.

```text
loop:
   byte = load()
   result |= (byte & 0x7F) << shift
   if (byte & 0x80) == 0: break    ← 이 분기가 문제
   shift += 7
```

이 `if`는 데이터에 따라 결과가 달라지므로 CPU의 **분기 예측기(branch predictor)** 가 맞히기 어렵다. 값의 길이가 1바이트인지 5바이트인지가 데이터마다 제각각이면 예측 실패(misprediction)가 잦아지고, 그때마다 파이프라인이 비워지면서 수십 사이클을 잃는다. Operating Systems 시리즈의 [[15 - 메모리 계층과 캐시]]에서 본 파이프라인과 예측 비용이 여기에 그대로 적용된다.

게다가 각 바이트는 직렬로 의존한다(앞 바이트를 봐야 다음 바이트가 있는지 안다). 그래서 ILP(명령 수준 병렬성)도 거의 활용하지 못한다. 작은 정수를 초당 수십억 개 디코드하는 검색·분석 엔진에서는 이 분기가 병목이 된다.

해법들의 공통 아이디어는 **"길이 정보를 데이터 바이트 밖으로 빼낸다"** 는 것이다. 길이를 먼저 한꺼번에 알면 데이터 바이트는 분기 없이 한 번에 읽어 올 수 있다.

### 8.2 Group Varint (Jeff Dean): 4개의 길이를 1바이트에

Jeff Dean이 대규모 검색 인덱스용으로 제시한 **Group Varint**(Varint-GB)는 정수를 **4개씩 묶어** 처리한다. 묶음 맨 앞에 **제어 바이트 1개**를 두고, 여기에 네 정수 각각의 바이트 길이를 **2비트씩(=길이−1)** 담는다. 그 뒤로 데이터 바이트가 길이만큼 이어진다.

```text
제어 바이트:  [len0:2][len1:2][len2:2][len3:2]   (각 2비트 = 바이트수-1)
   00 = 1바이트, 01 = 2바이트, 10 = 3바이트, 11 = 4바이트
그 뒤:  int0 바이트들 | int1 바이트들 | int2 | int3   (각 little-endian)

4개 정수 묶음 크기: 최소 1+4=5바이트, 최대 1+16=17바이트
```

**손으로 인코딩: [1, 300, 70000, 5]** (이 글의 레이아웃에서는 제어 바이트의 상위 2비트부터 int0이다)

```text
int0 = 1     → 1바이트  → len 00 → 데이터 01
int1 = 300   = 0x012C → 2바이트(LE) → len 01 → 데이터 2C 01
int2 = 70000 = 0x011170 → 3바이트(LE) → len 10 → 데이터 70 11 01
int3 = 5     → 1바이트  → len 00 → 데이터 05

제어 바이트 = 00 01 10 00 = 0b0001_1000 = 0x18

전체:  18  01  2C 01  70 11 01  05
       └제어┘└int0┘└─int1─┘└──int2──┘└int3┘
4개 정수에 8바이트 (제어1 + 데이터7)
```

디코드의 핵심은 **분기가 없다**는 점이다. 제어 바이트 `0x18`을 **256엔트리 룩업 테이블**의 인덱스로 써서 네 정수의 길이와 오프셋을 한 번에 가져온다. 그다음에는 메모리에서 정해진 만큼 읽어 시프트와 OR로 조립하면 되므로, 데이터에 의존하는 분기가 사라진다. Jeff Dean의 발표(WSDM 2009)에 따르면 이 방식은 일반 varint에 비해 디코드 속도를 대략 두 배로 높였다.

### 8.3 PrefixVarint: 길이를 첫 바이트의 prefix로

또 다른 접근은 **PrefixVarint**(Google·WebKit 계열)다. continuation 비트를 바이트마다 흩어 두는 대신 **첫 바이트의 하위 비트에 unary prefix**로 전체 길이를 기록한다. 예를 들어 첫 바이트의 최하위부터 연속된 1의 개수가 추가 바이트 수를 뜻하게 한다.

그러면 첫 바이트 하나만 보고 **count-trailing-ones(또는 zeros) 명령 한 번**으로 길이를 알아내고, **정렬되지 않은 1회 로드와 시프트**로 값을 통째로 꺼낼 수 있다. 바이트마다 있던 분기가 사라진다.

사실 이 구조는 이미 익숙한 것이다. **UTF-8의 선두 바이트가 길이를 인코딩하는 방식과 똑같다**(10절). PrefixVarint는 UTF-8의 길이 prefix 기법을 정수 varint에 그대로 가져온 것이라고 봐도 된다.

### 8.4 Stream VByte: SIMD로 4개를 한 번에

Daniel Lemire 등이 제시한 **Stream VByte**는 Group Varint를 SIMD에 맞게 변형한 것이다. 핵심은 **제어 바이트와 데이터 바이트를 완전히 분리된 두 스트림**으로 저장하는 것이다. 제어 스트림에는 정수 4개당 1바이트(2비트×4)씩 빈틈없이 담고, 데이터 스트림에는 가변 길이 바이트만 빈틈없이 담는다.

디코드할 때는 제어 바이트 하나를 읽어 **셔플 마스크(x86 SSSE3의 PSHUFB 인덱스)** 를 룩업하고, 데이터 스트림에서 16바이트를 한 번에 로드한 뒤 **단일 SIMD 셔플 명령**으로 32비트 정수 4개를 동시에 정렬·확장한다. 분기는 물론 바이트 단위의 직렬 의존까지 없앤다. 논문 제목 그대로 "초당 수십억 정수" 디코드가 목표다.

```text
일반 varint :  [c d][c d d][c d][c d d d] ...   제어·데이터가 섞여 직렬 분기
Stream VByte:
   제어 스트림:  [4개분 길이][4개분 길이]...     ← 미리 다 안다
   데이터 스트림:[연속된 값 바이트들]...         ← SIMD로 16B씩 셔플
```

### 8.5 varint와 fixed: 트레이드오프 정리

| 측면 | varint (LEB128류) | 고정폭 (fixed32/64) |
|---|---|---|
| 작은 값 크기 | **작다** (1~2바이트) | 크다 (항상 4/8) |
| 큰/랜덤 값 크기 | 크다 (오버헤드 +12.5%) | **일정** |
| 디코드 분기 | 바이트마다 분기(예측 실패) | **없음** |
| 랜덤 액세스 | **불가** (i번째 위치 모름) | 가능 (`base+4i`) |
| SIMD 친화성 | 낮음(기본형), 변종으로 개선 | **높음** |
| 정렬 키로 사용 | LE는 부적합, BE varint는 가능 | 엔디안 맞추면 가능 |
| 엔디안 합의 | 코덱이 정의(LE/BE 고정) | 양측이 합의 필요 |

> 데이터가 **작고 한쪽으로 치우쳐** 있고 **순차 스캔**한다면 varint(또는 그 속도 변종)를 쓴다. 데이터가 **고르게 크거나 랜덤 액세스·SIMD·고정 오프셋**이 필요하다면 fixed를 쓴다.
>
> "varint가 작으니 무조건 좋다"고 생각하면 큰 값이 많은 데이터셋에서 크기와 속도 모두 손해를 본다. protobuf가 `fixed32/fixed64` 타입을 따로 두는 이유도 여기에 있다(gRPC 시리즈 3장 Protocol Buffers 2 인코딩과 와이어 포맷). 해시값이나 랜덤 ID처럼 큰 값에는 varint가 불리하기 때문이다.

## 9. 보안과 견고성: overlong varint와 신뢰할 수 없는 입력

### 9.1 overlong: 같은 값을 두 바이트열로

varint에서 가장 알아차리기 어려운 함정은 **하나의 값에 여러 인코딩**이 존재한다는 점이다. 값 0을 예로 들어 보자.

```text
0 의 정상(canonical) 인코딩 :  00
0 의 overlong 인코딩들       :  80 00,  80 80 00,  80 80 80 00, ...
                              (앞 바이트들은 payload가 전부 0인 빈 그룹)
```

`80 00`은 "그룹0 = 0(더 있음), 그룹1 = 0(끝)"이므로 `0 + (0<<7) = 0`이다. 정상 인코딩 `00`과 같은 값이지만 한 바이트 더 길다. 대부분의 디코더는 이런 **overlong(불필요하게 긴) varint**를 받아들이는데, 받아들인다는 사실 자체가 **문제**다.

### 9.2 왜 보안 취약점이 되는가

같은 값을 여러 바이트열로 기록할 수 있으면 다음과 같은 문제가 생긴다.

- **서명·해시 우회**: 메시지에 서명하거나 해시를 계산하는 시스템에서 공격자가 의미는 같지만 바이트가 다른(overlong) 인코딩을 만들면, 검증을 통과하는 변형 메시지를 만들 수 있다(서명 malleability). 또 정규화한 뒤 서명한다고 가정한 캐시나 중복 제거가 무력화된다.
- **파서 불일치(parser differential)**: 방화벽이나 검사기와 백엔드가 같은 바이트열을 서로 다르게 해석하면(한쪽은 overlong을 거부하고 다른 쪽은 허용하면) 우회 공격이 가능해진다. Operating Systems 시리즈의 [[25 - 보안 익스플로잇과 사이드채널]]에서 보는 파서 불일치 공격의 전형적인 예다.
- **자원 고갈**: 길이 제한이 없는 varint 루프라면 공격자가 `80 80 80 ...`을 끝없이 보내 디코더를 계속 돌게 만들 수 있다.

### 9.3 방어: 길이 상한과 canonical 검증

견고한 디코더는 다음 규칙을 따른다.

1. **최대 바이트 수를 강제한다.** 64비트 varint는 **최대 10바이트**, 32비트는 5바이트다. 이를 넘으면 즉시 거부한다. 이 한 줄이 무한 루프와 자원 고갈을 막는다.
2. **10번째 바이트의 잉여 비트를 검증한다.** 64비트 값에서 10번째 바이트는 **bit63 하나만** 의미가 있다(payload의 최하위 1비트). 따라서 유효한 10번째 바이트는 `0x00` 또는 `0x01`뿐이고, 그 밖의 값(payload bit1~6이 켜진 값)은 64비트를 넘으므로 malformed다. 관대한 구현은 잉여 비트를 그냥 **버리고**(마스킹) 받아들이는데, 바로 이것이 overlong과 모호성(ambiguity)의 원인이다.
3. **canonical(최단) 인코딩만 받을지를 정책으로 정한다.** WebAssembly 스펙은 LEB128이 **"필요 이상으로 길면 안 되고, 마지막 바이트의 미사용 비트는 0(부호확장 값과 일치)이어야 한다"** 고 규정해 overlong을 명시적으로 금지한다. 신뢰할 수 없는 입력을 파싱한다면 이렇게 canonical 인코딩을 강제하는 편이 안전하다.

```python
def uleb128_decode_strict(buf, max_bytes=10):
    result, shift = 0, 0
    for i in range(max_bytes):
        byte = buf[i]
        if i == max_bytes - 1 and (byte & 0x7F) > 0x01:
            raise ValueError("varint overflows 64 bits")   # 잉여 비트 거부
        result |= (byte & 0x7F) << shift
        if (byte & 0x80) == 0:
            if i > 0 and byte == 0x00:
                raise ValueError("overlong (non-canonical) varint")  # 정책에 따라
            return result, i + 1
        shift += 7
    raise ValueError("varint too long")     # 10바이트 넘으면 거부
```

### 9.4 중복(redundancy)을 설계로 없앤 사례들

흥미롭게도 좋은 설계는 검증에 기대지 않고 **인코딩 자체를 bijective**로 만들어 overlong이 생길 여지를 처음부터 없앤다.

- **Git ofs-delta(7.2절)**: 바이트마다 `+1` 트릭을 적용해 모든 값에 유일한 인코딩만 존재한다. overlong이 *수학적으로 불가능*하다.
- **UTF-8(10절)**: 각 코드포인트에는 **최단 형식만 적법**하고, overlong 인코딩(예: ASCII `/`를 `C0 AF`로 쓰는 것)은 **표준이 명시적으로 불법**으로 규정한다(RFC 3629). 1990년대 후반에는 overlong UTF-8을 이용한 디렉터리 traversal 공격(`..%C0%AF..`)이 실제로 있었고, 그 뒤로 모든 UTF-8 디코더는 overlong을 거부한다.

> 가변길이 인코딩에서 "여러 표현이 같은 값을 뜻한다"는 중복은 *편의*가 아니라 *취약점*이다. 가능하면 인코딩을 bijective하게 설계하고(Git), 그럴 수 없다면 canonical 인코딩만 허용해야 한다(UTF-8/WASM). 신뢰할 수 없는 입력에는 **항상 길이 상한과 잉여 비트 검증**을 적용해야 한다.

## 10. UTF-8: 또 하나의 self-delimiting 가변길이 인코딩

가변길이는 정수에만 해당하는 이야기가 아니다. 우리가 매일 쓰는 텍스트 인코딩인 **UTF-8**도 따지고 보면 같은 계열이다. UTF-8은 유니코드 코드포인트(U+0000 ~ U+10FFFF)를 **1~4바이트**로 기록하고, **선두 바이트가 전체 길이를 인코딩**한다.

```text
범위                    바이트 패턴
U+0000  .. U+007F  (1B):  0xxxxxxx
U+0080  .. U+07FF  (2B):  110xxxxx 10xxxxxx
U+0800  .. U+FFFF  (3B):  1110xxxx 10xxxxxx 10xxxxxx
U+10000 .. U+10FFFF(4B):  11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
```

여기서 varint와 닮은 점이 분명히 드러난다.

- **길이를 선두 바이트의 prefix로** 인코딩한다. 선두 바이트에서 **연속된 1의 개수**가 곧 전체 바이트 수다(`0`=1B, `110`=2B, `1110`=3B, `11110`=4B). 이는 8.3절 **PrefixVarint와 같은 기법**이다. count-leading-ones 명령 한 번으로 길이를 알 수 있다.
- **continuation 바이트는 `10xxxxxx`** 로 고정되어 있다. LEB128의 continuation 비트와 역할이 같다(이어지는 조각임을 표시한다). 다만 UTF-8은 **모든** 후속 바이트가 `10`으로 시작하므로 **self-synchronizing**(어느 바이트에서 시작해도 문자 경계를 찾을 수 있음)이라는 추가 장점을 얻는다.
- **overlong 금지**가 보안 규칙이라는 점(9.4절)도 varint와 똑같다.

UTF-8은 코드포인트라는 정수를 담는 **self-delimiting 가변길이 정수 인코딩의 특수한 형태**다. 차이가 있다면 varint는 7비트 단위의 균일한 그룹을 쓰는 반면, UTF-8은 정렬, 동기화, ASCII 호환을 위해 비트를 비대칭으로 배분했다는 점 정도다.

정규화나 grapheme cluster처럼 텍스트로서의 특성은 [[08 - 유니코드 정규화와 grapheme cluster]]와 [[09 - 유니코드 보안 - confusables와 homograph]]에서 본격적으로 다룬다. 여기서 말하려는 요점은 가변길이, continuation, overlong 금지라는 *바이트 수준의 발상*이 정수와 텍스트에서 똑같이 반복된다는 것이다.

## 11. 다른 직렬화 포맷 속의 varint

이 장에서 다룬 발상이 이후 장들에서 어떻게 다시 등장하는지 미리 정리해 두자.

- **CBOR (RFC 8949)**: 정수를 7비트 varint로 기록하지 *않는다*. 대신 major type 3비트와 추가 정보 5비트로 시작해서, 값이 작으면 그 5비트에 바로 담고, 크면 **고정 1/2/4/8바이트(big-endian)** 로 뒤에 붙인다. 가변길이지만 길이가 1·2·4·8 중 하나로 양자화된 방식이라 7비트 varint보다 디코드가 단순하고 SIMD와 정렬에 유리하다. CBOR의 설계 의도와 zero-copy 친화성은 [[12 - CBOR·Avro·zero-copy 직렬화]]에서 다룬다.
- **Avro**: 정수를 **ZigZag + ULEB128**로 기록한다. 즉 protobuf의 `sint`와 *완전히 같은 코덱*이다. Avro의 `int`/`long`은 항상 zigzag varint다. 이 장의 5절을 이해했다면 Avro 정수 디코더를 직접 작성할 수 있다.
- **ASN.1 BER/DER**: OID arc는 base-128(VLQ)을 쓰고, 길이 필드는 또 다른 가변길이 방식("definite long form": 첫 바이트가 뒤따르는 길이 바이트 수를 알려 주는 prefix 방식)을 쓴다. 11장(ASN.1·DER·PEM)에서 인증서 한 장을 바이트 단위로 분석할 때 다시 나온다.
- **protobuf**: 이 장의 ULEB128과 ZigZag가 wire 포맷의 토대다. 필드 태그, packed repeated, 메시지 중첩 같은 *상위 구조*는 gRPC 시리즈 3장(Protocol Buffers 2 인코딩과 와이어 포맷)에서, 타입 시스템과 proto 문법은 [[02 - Protocol Buffers 1 - 문법과 타입 시스템]]에서 다룬다.
- **저장 엔진**: LSM/SSTable의 키·값 길이와 블록 오프셋도 흔히 varint로 기록한다. 압축, 체크섬과 얽히는 부분은 Cassandra DB 시리즈의 [[08 - Storage Engine 내부]]에서 다룬다.

## 12. 정리: 하나의 발상, 여러 변형

가변길이 정수는 **작은 수가 흔하니 작은 수를 짧게 표현한다**는 단순한 발상에서 출발한다. 이 발상을 바이트로 구현하면서 모든 시스템이 같은 질문에 부딪혔고, 저마다 다른 답을 골랐다.

- **그룹 크기**: 거의 모두 7비트에 continuation 1비트를 쓴다. (CBOR만 1/2/4/8바이트로 양자화한다.)
- **그룹 순서(엔디안)**: LEB128, Lucene, Git 헤더는 little-endian이고, VLQ, SQLite, OID, Git 오프셋은 big-endian이다. *같은 7비트인데 방향이 반대*라는 점이 디코더 호환에서 만나는 첫 번째 함정이다.
- **부호 처리**: signed LEB128은 부호확장을 쓰며 *코덱이 부호를 안다*. ZigZag는 작은 음수를 작은 양수로 접은 뒤 *단일 코덱에 맡긴다*. protobuf의 `int`(부호확장 → 음수 10바이트)와 `sint`(zigzag) 사이의 큰 차이가 이 결정을 보여 주는 실제 사례다.
- **상한과 canonical 인코딩**: 64비트 값은 최대 10바이트(LEB128) 또는 9바이트(SQLite)다. overlong은 보안 위협이므로 길이 상한과 잉여 비트 검증이 필수이고, Git(+1 bijective)과 UTF-8(overlong 금지)은 인코딩 설계로 중복을 처음부터 없앴다.
- **속도**: continuation 분기가 병목이므로 Group Varint, PrefixVarint, Stream VByte는 길이를 데이터 밖으로 빼내 분기와 직렬 의존을 없애고, SIMD로 4개씩 디코드한다.

이 발상은 정수에만 머물지 않는다. **UTF-8** 은 코드포인트를 담는 self-delimiting 가변길이 인코딩이고, prefix로 길이를 알리는 기법과 overlong 금지 규칙을 varint와 공유한다. 다음 장 [[06 - CRC의 수학과 체크섬]]에서는 이렇게 인코딩한 바이트열이 전송이나 저장 중에 **변형되지 않았음**을 보장하는 체크섬의 수학을 다룬다. 즉 바이트를 어떻게 기록하는가에서, 그 바이트가 손상되지 않았는지 어떻게 확인하는가로 넘어간다.
