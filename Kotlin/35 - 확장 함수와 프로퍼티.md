[[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]까지는 타입을 파라미터화하는 방법과 그 파라미터가 런타임에 소거되는 과정을 살펴보았다. 제네릭이 *타입에 대한 추상화*였다면, 이 장에서 다루는 확장(extension)은 *소유권의 방향을 뒤집는 기능*이다. 지금까지는 클래스에 기능을 넣으려면 그 클래스의 소스 파일을 열어 멤버를 추가해야 했다.

하지만 우리가 소스를 관리하지 않는 클래스(`String`, `List`, 서드파티 라이브러리의 타입, 자바 표준 클래스 등)에도 원래 메서드가 있는 것처럼 `s.lastChar()`를 호출하고 싶을 때가 있다. 확장 함수와 확장 프로퍼티는 이런 요구를 해결한다. 클래스를 수정하지 않고, 클래스 바깥에서 점(`.`) 문법으로 호출할 수 있는 기능을 덧붙인다.

다만 이 편리함에는 한 가지 대가가 따른다. 확장은 클래스에 **실제 멤버를 추가하지 않는다**. 확장은 수신 타입을 첫 인자로 받는 *일반 함수*에 특별한 호출 문법을 씌운 것이다. 그리고 어느 확장이 호출될지는 실행 시점의 실제 객체가 아니라 **컴파일 시점에 알려진 정적 타입(static type)** 으로 결정된다.

이 사실 하나로 흔한 오해 세 가지를 모두 바로잡을 수 있다. 확장이 클래스에 메서드를 추가한다는 오해, 확장이 수신 객체의 `private`에 접근할 수 있다는 오해, 확장이 같은 이름의 멤버보다 우선한다는 오해다. 확장은 "바깥에서 붙인 메서드"처럼 *보이지만*, 실제로는 "정적으로 결정되는 함수 호출"이다. 이 장은 겉모습과 실제 동작 사이의 이 차이를 중심으로 전개된다.

이 장에서는 확장의 정체(정적 함수)와 컴파일 결과, 디스패치 규칙, 멤버와의 우선순위, 캡슐화 경계, 상태가 없는 확장 프로퍼티, nullable·제네릭 수신자, 스코프와 임포트, 멤버 확장의 이중 수신자, 컴패니언 확장을 차례로 다룬다.

확장으로 연산자를 정의하는 규칙(`operator fun Vector.plus`)은 [[19 - 연산자 오버로딩과 관례]]에서, 수신 객체 지정 람다 `T.() -> R`을 스코프 함수에서 쓰는 방식은 [[16 - 스코프 함수와 수신 객체 관용구]]에서, 이 람다를 타입 안전 빌더로 발전시키는 내용은 [[37 - 타입 안전 빌더와 DSL]]에서 설명한다.

백킹 필드 `field`가 언제 생기는지는 [[22 - 프로퍼티와 백킹 필드]]에서 다루므로, 이 장에서는 확장 프로퍼티에 그 필드가 애초에 없는 이유만 설명한다. 자바에서 확장을 호출하는 방법은 [[45 - Java 상호운용]]에서 다룬다.

## 1. 확장이라는 발상: 소스를 관리하지 않는 클래스에 기능 추가하기

### 1.1 문제: 우리가 수정할 수 없는 클래스

객체지향 언어에서는 "이 타입에 이런 동작이 있으면 좋겠다"는 요구가 자주 생긴다. 문자열의 마지막 글자를 얻고 싶을 수도 있고, 리스트를 두 번째 원소부터 보고 싶을 수도 있다. 그런데 `String`이나 `List`는 표준 라이브러리의 소스라서 우리가 편집할 수 없다. 전통적인 해법은 두 가지였는데, 둘 다 아쉬운 점이 있었다.

첫째는 **유틸리티 클래스(static helper)** 이다. 자바에서는 `StringUtils.lastChar(s)`처럼 정적 메서드를 모아 둔 클래스를 만든다. 동작은 하지만 호출이 어색하다. 주체인 `s`가 인자 자리로 밀려나서 `s.lastChar()`가 아니라 `lastChar(s)`가 된다. 여러 유틸리티를 엮으면 `reverse(capitalize(trim(s)))`처럼 안쪽에서 바깥쪽으로 읽어야 하는 뒤집힌 코드가 된다.

둘째는 **상속(subclassing)** 이다. `class MyString : String`으로 확장하려 해도 `String`은 `final`이라서 상속할 수 없다(코틀린 클래스도 기본적으로 `final`이다. [[24 - 상속과 오버라이딩과 초기화 순서]] 참고). 게다가 상속으로는 이미 존재하는 수많은 `String` 인스턴스에 기능을 소급해서 적용할 수도 없다.

코틀린의 확장 함수는 세 번째 방법이다. 멤버처럼 `s.lastChar()`로 자연스럽게 호출할 수 있으면서도, 클래스를 상속하거나 편집하지 않는다.

```kotlin
fun String.lastChar(): Char = this[this.length - 1]

fun main() {
    println("Kotlin".lastChar())   // => n
}
```

`fun String.lastChar()`에서 `String`을 **수신 타입(receiver type)** 이라고 부르고, 함수 본문 안의 `this`를 **수신 객체(receiver object)** 라고 부른다. 여기서 수신 객체는 `.lastChar()`를 호출한 바로 그 문자열이다.

`this`는 대개 생략할 수 있으므로 `this[this.length - 1]`은 `this[length - 1]`로 쓰거나, 인덱싱 문맥에서 명확하게 써 주면 된다. 겉으로 보면 `String`에 메서드를 하나 새로 추가한 것 같다. 이 장 전체에 걸쳐 바로잡을 대상이 바로 이 착시다.

### 1.2 확장은 "바깥에서 정의하고 안에서 호출하는" 함수

핵심 직관부터 정리해 두자. 확장 함수는 두 영역에 걸쳐 있다.

- **정의하는 쪽**: 확장은 클래스 *바깥*의 최상위(top-level)나 다른 클래스/객체 안에 정의한다. 클래스의 본문(body) 안에는 들어가지 않는다.
- **호출하는 쪽**: 확장은 클래스 *안*에 있는 멤버처럼 `수신객체.함수()` 문법으로 호출한다.

이런 이중성 때문에 확장은 "멤버처럼 쓸 수 있는 문법적 편의"와 "함수라는 정적인 본질"을 함께 가진다. 실무에서 이 편의는 매우 크다. 코틀린 표준 라이브러리는 전체가 이 편의를 바탕으로 만들어졌고(10절), 스코프 함수(16장)와 컬렉션 파이프라인([[39 - 컬렉션 연산과 함수형 파이프라인]]), DSL(37장)도 모두 이 발상에서 나왔다.

> [!info] 역사 메모
> 클래스를 수정하지 않고 메서드처럼 호출하는 기능은 코틀린이 처음 만든 것이 아니다. C#은 2007년에 LINQ를 위해 확장 메서드(extension method)를 도입했고, 스칼라는 `implicit class`로, 스위프트는 `extension` 키워드로 비슷한 기능을 제공한다. 이 언어들은 공통적으로 *정적 디스패치*를 택했다.
>
> 확장이 동적으로 디스패치된다면(즉 실제 멤버라면) 클래스의 가상 메서드 테이블(vtable)을 바깥에서 수정해야 한다. 그러면 분리 컴파일(separate compilation)과 이진 호환성이 깨진다. 확장을 정적으로 정한 것은, 편의를 얻으려고 안전성과 예측 가능성을 포기하지는 않겠다는 여러 언어의 공통된 절충이다.

### 1.3 최소 예제로 감 잡기

몇 가지 도메인 예제로 확장을 직접 써 보자. 좌표점에는 거리 계산을, 은행 계좌 금액에는 포맷 기능을 추가한다.

```kotlin
data class Point(val x: Double, val y: Double)

// Point에 확장 함수 — Point.kt를 편집하지 않고
fun Point.distanceTo(other: Point): Double {
    val dx = x - other.x      // this.x 를 this 생략
    val dy = y - other.y
    return kotlin.math.sqrt(dx * dx + dy * dy)
}

fun Int.wonFormat(): String = "%,d원".format(this)   // 수신자 = this (Int)

fun main() {
    val a = Point(0.0, 0.0)
    val b = Point(3.0, 4.0)
    println(a.distanceTo(b))       // => 5.0
    println(1234567.wonFormat())   // => 1,234,567원
}
```

`Point.distanceTo`는 `Point`의 소스를 전혀 몰라도 정의할 수 있고, `Int.wonFormat`은 원시 정수 타입에도 메서드처럼 붙는다. 이런 자유로움이 확장의 장점이다. 하지만 이 자유에는 규칙이 있으며, 그 규칙은 모두 "확장은 사실 함수다"라는 한 문장에서 도출된다. 다음 절에서 그 함수가 실제로 어떤 모습인지 살펴본다.

## 2. 확장 함수의 컴파일: 정적 메서드와 수신자 인자

### 2.1 겉모습 뒤에서 일어나는 시그니처 변환

확장 함수가 실제로 무엇인지 확실히 이해하려면, 컴파일러가 확장 함수를 무엇으로 바꾸는지 보면 된다. JVM 백엔드에서 최상위 확장 함수는 **평범한 정적 메서드(static method)** 로 컴파일되고, 수신 객체는 **첫 번째 파라미터**로 들어간다. 개념적인 변환은 다음과 같다.

```text
소스 (확장 문법):
    fun String.lastChar(): Char = this[length - 1]

JVM 백엔드가 만드는 것 (개념적 의사 표현):
    public static final char lastChar(String $receiver) {
        return $receiver.charAt($receiver.length() - 1);
    }
    // 파일 Foo.kt 안이면 → 클래스 FooKt 의 정적 메서드로 배치
```

호출하는 쪽도 함께 변환된다.

```text
소스 호출:
    "Kotlin".lastChar()

JVM 백엔드가 만드는 호출:
    FooKt.lastChar("Kotlin")   // 정적 메서드 호출, 수신자를 인자로
```

즉 `수신객체.확장함수(인자들)`은 `확장을담은클래스.확장함수(수신객체, 인자들)`을 보기 좋게 쓴 문법 설탕이다. 본문 안의 `this`는 첫 번째 파라미터(`$receiver`)를 가리키는 이름일 뿐이다. 이 장의 결론은 거의 모두 이 사실에서 나온다.

> [!note] 명세 기준
> "정적 메서드로 컴파일된다"는 설명은 **JVM 백엔드**에 해당한다. 코틀린은 JVM/Native/JS/Wasm을 대상으로 하는 멀티타깃 언어이고([[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]), 백엔드마다 확장을 표현하는 물리적인 형태가 다르다. 하지만 확장이 수신자를 암시적인 첫 인자로 받는 함수이고 정적으로 결정된다는 *의미*는 모든 타깃에서 똑같이 명세로 보장된다.
>
> 이 장에서 "정적 메서드"라고 하면 JVM에서의 구체적인 형태를, "정적 디스패치/정적 해소"라고 하면 백엔드와 관계없는 언어 규칙을 가리킨다.

이 변환에서 바로 따라 나오는 결과가 **자바에서 확장을 호출하는 방법**이다. 자바에는 확장 문법이 없으므로, 코틀린 확장을 자바에서 호출하려면 컴파일된 형태 그대로 정적 메서드에 수신자를 첫 인자로 넘겨야 한다. 확장이 실제로 정적 함수라는 결정적인 증거다.

```java
// 코틀린: fun String.lastChar(): Char (파일 StringExtKt.kt)
// 자바에서 호출:
char c = StringExtKt.lastChar("Kotlin");   // 정적 메서드 + 수신자를 첫 인자로
// System.out.println(c);  // => n
```

`"Kotlin".lastChar()`라는 깔끔한 문법은 전적으로 코틀린 컴파일러가 제공하는 것이고, 그 밑에는 `StringExtKt.lastChar("Kotlin")`이라는 평범한 정적 호출이 있다. 자바 상호운용의 세부 사항은 45장(Java 상호운용)에서 다루지만, 이 예제 하나만 보아도 "확장 = 정적 메서드 + 수신자 인자"라는 등식이 비유가 아니라 말 그대로의 사실임을 알 수 있다.

### 2.2 클래스에는 아무 변화도 없다

앞의 변환을 다시 보자. `lastChar`는 `FooKt`라는 *별도의 클래스*에 속한 정적 메서드가 되었다. `String` 클래스의 바이트코드는 전혀 바뀌지 않았다. `String.class`를 리플렉션으로 살펴봐도 `lastChar`라는 메서드는 없다. 이 사실은 **"확장 함수는 클래스에 메서드를 추가한다"** 는 오해를 정확히 반박한다.

```kotlin
fun String.shout(): String = uppercase() + "!"

fun main() {
    // 확장은 String 클래스의 멤버가 아니다 — 리플렉션으로 확인
    val hasShoutMember = String::class.members.any { it.name == "shout" }
    println(hasShoutMember)   // => false  (String 클래스에 shout 멤버는 없음)
    println("hi".shout())     // => HI!    (그래도 호출은 된다: 정적 함수라서)
}
```

`String` 클래스에는 `shout`가 없는데도 `"hi".shout()`은 문제없이 동작한다. 모순처럼 보이지만 모순이 아니다. `"hi".shout()`은 `String` 인스턴스에 메시지를 보내는 것이 아니라, 컴파일 시점에 이미 `shout(String)`이라는 정적 함수 호출로 확정되어 있기 때문이다. 확장 함수는 클래스에 무언가를 *추가*하지 않는다. 그 클래스의 인스턴스를 첫 인자로 받는 함수를 멤버처럼 보이는 문법으로 호출할 수 있게 해 줄 뿐이다.

> [!warning] 흔한 오해
> "확장을 정의하면 그 타입의 모든 인스턴스가 새 메서드를 갖게 된다"고 생각하기 쉽지만 그렇지 않다. 인스턴스도 클래스도 바뀌지 않는다. 바뀌는 것은 *컴파일러가 그 타입에 대해 `.함수()` 문법을 받아들이는지*뿐이며, 그것도 확장이 스코프에 임포트되어 있을 때만 그렇다(8절). "메서드가 붙는다"가 아니라 "호출 문법이 허용된다"고 말해야 정확하다.

### 2.3 왜 정적 메서드인가: 설계상의 필연

확장을 정적으로 만든 것은 임의로 고른 선택이 아니라 거의 불가피한 결론이다. 확장이 실제 멤버(가상 메서드)라면 확장을 정의하는 순간 `String`의 vtable에 슬롯을 추가해야 한다. 그런데 `String`은 이미 컴파일되어 JDK 안에 들어 있고, 이를 참조하는 다른 라이브러리도 이미 수천 개가 있다. 바깥에서 vtable을 늘리면 이진 호환성이 크게 무너진다. 게다가 서로 다른 두 모듈이 같은 타입에 같은 이름의 확장을 정의하면 vtable 슬롯이 충돌한다.

정적 메서드를 쓰면 이런 문제가 모두 사라진다. 정적 함수는 클래스와 독립된 별도의 심볼이고, 이름 충돌은 임포트로 국소적으로 해결되며(8절), 어떤 확장이 호출될지는 호출 지점의 스코프와 정적 타입만으로 결정된다. 대신 다형성을 잃게 되는데(3절), 이는 확장을 설계할 때 명시적으로 받아들인 트레이드오프다.

```text
멤버 함수 vs 확장 함수 — 디스패치 축의 대비

  멤버 함수 호출  s.member()
    → 런타임에 s의 실제 클래스의 vtable을 조회 (동적 디스패치)
    → 오버라이드 가능, 다형적

  확장 함수 호출  s.ext()
    → 컴파일 타임에 s의 정적 타입 + 스코프로 함수 확정 (정적 해소)
    → 오버라이드 불가, 비다형적
```

## 3. 정적 디스패치: 실제 타입이 아니라 정적 타입으로 결정된다

### 3.1 핵심 실험: 부모 타입 변수에 담은 자식 객체

확장이 정적으로 결정된다는 말이 실제로 무슨 뜻인지는 다음 예제에서 가장 잘 드러난다. 도형 계층을 만들고, 부모와 자식에 각각 같은 이름의 확장을 정의한 뒤, *부모 타입 변수*에 담아서 호출한다.

```kotlin
open class Shape
class Circle : Shape()
class Rectangle : Shape()

fun Shape.describe(): String = "어떤 도형"
fun Circle.describe(): String = "원"
fun Rectangle.describe(): String = "직사각형"

fun main() {
    val shapes: List<Shape> = listOf(Circle(), Rectangle())
    for (s in shapes) {
        // s의 정적 타입은 Shape (List<Shape>의 원소니까)
        println(s.describe())   // => 어떤 도형
                                // => 어떤 도형   (Circle.describe/Rectangle.describe 아님!)
    }
}
```

`shapes`의 원소 `s`는 런타임에 실제로 `Circle`이거나 `Rectangle`이지만, 컴파일러가 아는 `s`의 정적 타입은 `Shape`이다. 확장을 결정할 때는 이 정적 타입만 본다. 그래서 실제 객체가 원이든 사각형이든 항상 `Shape.describe`가 호출된다. `describe`가 멤버 함수였다면 동적 디스패치가 일어나서 결과는 "원", "직사각형"이 되었을 것이다. 이 차이가 정적 디스패치의 핵심이다.

### 3.2 멤버와 확장을 나란히 두면 차이가 드러난다

같은 계층에서 하나는 멤버로, 하나는 확장으로 만들어 나란히 호출하면 두 디스패치 방식의 차이가 분명해진다.

```kotlin
open class Animal {
    open fun sound(): String = "..."          // 멤버 (open → 오버라이드 가능)
}
class Dog : Animal() {
    override fun sound(): String = "멍멍"       // 오버라이드
}

fun Animal.label(): String = "동물"            // 확장
fun Dog.label(): String = "개"                 // 확장

fun main() {
    val a: Animal = Dog()
    println(a.sound())   // => 멍멍   (멤버: 동적 디스패치 → 실제 타입 Dog)
    println(a.label())   // => 동물   (확장: 정적 해소   → 정적 타입 Animal)
}
```

정적 타입이 `Animal`이고 실제 타입이 `Dog`인 같은 변수 `a`에 대해 `sound()`는 "멍멍"을, `label()`은 "동물"을 반환한다. 멤버는 실제 타입을 따르고, 확장은 선언된 타입을 따른다. 즉 24장(상속과 오버라이딩과 초기화 순서)에서 배운 다형성은 확장에 적용되지 않는다. 확장 함수에 `override`나 `open`을 붙일 수 없는 것도 같은 이유다. 오버라이드할 vtable 슬롯이 애초에 없기 때문이다.

```kotlin
// 확장은 open/override 불가
open fun String.foo() {}   // 컴파일 에러: modifier 'open' is not applicable to top level function
```

### 3.3 스마트 캐스트와 확장 결정

정적 타입이 확장을 결정한다는 규칙은 스마트 캐스트([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]])와 함께 쓰일 때 은근히 유용하다. 스마트 캐스트는 컴파일러가 아는 정적 타입을 *좁히므로*, 좁혀진 타입에 맞는 더 구체적인 확장이 선택된다.

```kotlin
fun Any.brief(): String = "무언가"
fun String.brief(): String = "문자열: $this"

fun handle(x: Any) {
    println(x.brief())          // => 무언가        (정적 타입 Any)
    if (x is String) {
        // 여기서 x의 정적 타입은 스마트캐스트로 String 으로 좁혀짐
        println(x.brief())      // => 문자열: ...   (더 구체적인 String.brief 선택)
    }
}

fun main() {
    handle("hello")
    // => 무언가
    // => 문자열: hello
}
```

`if (x is String)` 블록 안에서 `x`의 정적 타입이 `String`으로 좁혀지면, 확장 결정 과정은 `Any.brief` 대신 `String.brief`를 고른다. 이것은 "실제 타입을 본" 것이 아니라 여전히 "정적 타입을 본" 것이다. 다만 스마트 캐스트가 정적 타입을 바꾸어 주었을 뿐이다. 따라서 확장은 항상 컴파일 시점에 아는 정보만으로 확정된다는 원칙과 어긋나지 않는다.

> [!caution] 성능 주의
> 정적 디스패치는 성능 면에서는 오히려 이점이 있다. 가상 호출(vtable 조회, 다형성 방어)이 필요 없고, 인라인 함수([[15 - 인라인 함수와 reified]])와 함께 쓰면 호출 자체가 사라진다. 표준 라이브러리의 많은 확장이 `inline`인 이유가 여기에 있다. 확장이 다형적이지 않다는 점은 단점이면서 동시에 장점이다.

## 4. 항상 멤버가 우선한다

### 4.1 규칙: 시그니처가 같으면 멤버가 우선한다

수신 타입에 이미 멤버 함수가 있고 같은 이름·같은 시그니처의 확장 함수도 스코프에 있다면, **호출은 항상 멤버로 간다**. 확장은 멤버에 가려져서 절대 호출되지 않는다. 따라서 **"확장이 같은 이름의 멤버보다 우선한다"** 는 생각은 오해이며, 실제로는 정반대로 멤버가 우선한다.

```kotlin
class Greeter {
    fun hello(): String = "멤버 인사"
}

fun Greeter.hello(): String = "확장 인사"   // 같은 시그니처의 확장

fun main() {
    val g = Greeter()
    println(g.hello())   // => 멤버 인사   (확장은 그림자에 가림)
}
```

`g.hello()`는 멤버 `hello`를 호출한다. 확장 `Greeter.hello`는 정의되어 있지만 이 호출에서는 절대 선택되지 않는다. 이런 경우 컴파일러는 대개 "확장이 멤버에 의해 가려졌다(shadowed)"는 경고를 표시한다.

### 4.2 왜 멤버가 우선해야 하는가: 클래스 작성자의 권한

이 우선순위는 안전을 위해 반드시 필요하다. 확장이 멤버보다 우선한다면 어떤 라이브러리든 확장 하나만 정의해서 남의 클래스의 핵심 동작을 바깥에서 몰래 바꿔치기할 수 있다. 클래스 작성자가 `equals`를 정의했는데 어떤 임포트 때문에 다른 `equals`가 호출된다면 캡슐화와 불변식(invariant)이 무너진다. 그래서 언어는 "클래스 작성자가 정의한 멤버가 기준"이라는 원칙을 세우고, 확장은 항상 그다음 순위의 보조 수단으로 정했다.

이 규칙에는 실무에서 빠지기 쉬운 함정이 하나 있다. **어떤 클래스의 확장을 정의해서 잘 쓰고 있는데, 나중에 그 클래스의 작성자가 같은 시그니처의 멤버를 추가하면, 내 코드는 아무 말 없이 멤버를 호출하기 시작한다.** 컴파일은 통과하고 경고만 뜨지만 동작이 바뀔 수 있다. 라이브러리가 발전하는 과정에서 "멤버 추가"는 까다로운 소스 호환성 문제가 된다.

```kotlin
// 라이브러리 v1 — Box에 size 멤버 없음
class Box(val items: List<Int>)
fun Box.size(): Int = items.size          // 내 확장

// (내 코드) box.size()  →  확장이 불림, 결과 items.size

// 라이브러리 v2 — 소유자가 size() 멤버를 추가하면
//   class Box(val items: List<Int>) { fun size(): Int = 0 }
// 이제 box.size()  →  멤버가 불림 (내 확장은 그림자에 가림, 동작 바뀜)
```

### 4.3 시그니처가 다르면 오버로딩처럼 공존한다

"멤버가 우선한다"는 규칙은 *시그니처가 같을* 때만 적용된다. 이름이 같아도 파라미터가 다르면 멤버와 확장은 오버로딩 관계로 함께 존재하고, 인자에 따라 알맞은 쪽이 선택된다.

```kotlin
class Printer {
    fun show(x: Int) = println("멤버: 정수 $x")
}

fun Printer.show(x: String) = println("확장: 문자열 $x")   // 다른 시그니처

fun main() {
    val p = Printer()
    p.show(42)        // => 멤버: 정수 42     (Int 인자 → 멤버)
    p.show("hi")      // => 확장: 문자열 hi   (String 인자 → 확장, 멤버엔 없는 오버로드)
}
```

여기서는 멤버와 확장이 충돌하지 않는다. `show(Int)`는 멤버에만 있고 `show(String)`은 확장에만 있으므로, 호출마다 후보가 하나뿐이다. "멤버 우선"은 두 후보가 *똑같이 적용 가능할 때* 순위를 정하는 타이브레이커이지, 확장을 무조건 무력화하는 규칙이 아니다.

> [!note] 명세 기준
> 코틀린의 오버로드 해소(overload resolution)는 세 단계를 거친다. (1) 스코프에서 후보를 모으고, (2) 적용 가능성(applicability)으로 거르고, (3) 가장 구체적인(most specific) 후보를 고른다. 멤버와 확장이 *둘 다 똑같이 적용 가능하고 똑같이 구체적*이면 타이브레이커로 멤버가 우선한다.
>
> 4.1의 예처럼 시그니처가 완전히 같으면 이 타이브레이커가 작동해서 멤버가 선택된다. 4.3처럼 적용 가능한 후보가 처음부터 하나뿐이면 타이브레이커는 개입하지 않는다.

### 4.4 확장끼리 경쟁하면 수신 타입이 더 구체적인 쪽이 선택된다

멤버가 없고 확장끼리 경쟁할 때는 어떻게 될까? 이때는 오버로드 해소의 "가장 구체적인 후보" 규칙이 그대로 적용되어, **수신 타입이 더 구체적인(하위 타입인) 확장이 선택된다.** 3.3절에서 스마트 캐스트 뒤에 `String.brief`가 선택된 것도 이 규칙 때문이었다.

```text
확장 해소의 우선순위 (같은 이름·같은 인자, 멤버 없음)

  수신 객체의 정적 타입: String  (String <: CharSequence <: Any)
  스코프에 보이는 확장 후보들:
      fun Any.tag()          ← 가장 덜 구체적
      fun CharSequence.tag()
      fun String.tag()       ← 가장 구체적  ★ 선택됨

  선택 규칙: 정적 타입에 적용 가능한 후보 중 가장 구체적인 수신 타입
```

```kotlin
fun Any.kind(): String = "Any"
fun CharSequence.kind(): String = "CharSequence"
fun String.kind(): String = "String"

fun main() {
    val s = "hi"                     // 정적 타입 String
    println(s.kind())                // => String       (가장 구체적)
    val cs: CharSequence = "hi"      // 정적 타입 CharSequence
    println(cs.kind())               // => CharSequence (String.kind는 후보 아님 — 정적 타입이 CharSequence)
    val a: Any = "hi"                // 정적 타입 Any
    println(a.kind())                // => Any
}
```

실제 객체가 같은 `"hi"`라도 그 객체를 담은 변수의 *정적 타입*에 따라 후보 집합이 달라지고, 그중 가장 구체적인 확장이 선택된다. `cs`는 실제로 `String` 인스턴스이지만 정적 타입이 `CharSequence`이므로 `String.kind`는 후보에도 들지 못한다. 3절의 정적 디스패치 원칙이 여기서도 다시 확인된다. 확장 결정은 전부 컴파일 시점의 정적 타입을 기준으로 이루어진다.

## 5. 캡슐화 경계: 확장은 private에 접근할 수 없다

### 5.1 확장은 바깥에 있는 함수이므로 바깥에서 보이는 것만 볼 수 있다

확장 함수가 정적 함수이고 클래스 바깥에 있다는 사실은 캡슐화에 직접 영향을 준다. **확장 함수는 자신이 확장하는 클래스의 `private`·`protected` 멤버에 접근할 수 없다.** 확장은 그 클래스의 멤버가 아니라 외부 함수이므로, 외부에서 보이는 것(`public`, `internal` 등)만 볼 수 있다. 따라서 **"확장 함수는 수신 객체의 private에 접근한다"** 는 생각은 오해다.

```kotlin
class BankAccount(initial: Long) {
    private var balance: Long = initial          // private 필드
    fun currentBalance(): Long = balance         // public 접근자
}

fun BankAccount.deposit(amount: Long) {
    balance += amount    // 컴파일 에러: Cannot access 'balance': it is private in 'BankAccount'
}

fun BankAccount.snapshot(): Long {
    return currentBalance()   // OK — public 멤버는 접근 가능
}
```

`deposit`은 `private` 필드인 `balance`에 접근하려다 컴파일 에러가 난다. 확장은 `BankAccount`의 내부에 속하지 않기 때문이다. 반면 `snapshot`은 `public`인 `currentBalance()`만 사용하므로 문제없다. 확장은 클래스의 *공개 표면(public surface)* 에서만 동작한다.

### 5.2 이것이 좋은 설계인 이유

이 제약은 불편함이 아니라 안전장치다. 확장이 `private`에 접근할 수 있었다면 누구든 확장 하나로 남의 클래스가 지키는 불변식을 바깥에서 깨뜨릴 수 있었을 것이다. 은행 계좌의 `balance`를 검증 없이 음수로 만들거나 내부 캐시를 오염시킬 수도 있다. 확장을 공개 표면으로 제한하면 "클래스가 스스로 보장하는 규약은 확장으로도 깨뜨릴 수 없다"는 성질이 성립한다. 확장은 클래스를 *편리하게 쓰기 위한* 도구이지, *내부를 침범하는* 도구가 아니다.

### 5.3 예외처럼 보이는 경우: 같은 스코프의 private

이 규칙에는 "같은 스코프는 예외"라는 정확한 단서가 붙는다. 확장이 대상 클래스의 `private` 멤버에 접근할 수 있는 경우는 그 확장이 **그 클래스와 같은 가시성 스코프 안에** 선언되었을 때뿐이다. 대표적인 예는 (a) 클래스 안에 선언한 멤버 확장과 (b) 최상위 `private` 심볼과 같은 파일에 있는 최상위 확장이다.

```kotlin
class Counter {
    private var count = 0

    // (a) 클래스 안의 멤버 확장 — Counter의 멤버이므로 private에 접근 가능
    fun Counter.bumpInternal() {
        count += 1        // OK: 이 확장은 Counter의 멤버라서 private 접근 허용
    }
}

// (b) 최상위 private 과 같은 파일
private fun secretHelper() = 42
fun Int.usesSecret(): Int = this + secretHelper()   // OK: 같은 파일의 file-private 접근
```

(a)의 `bumpInternal`은 `Counter` 클래스 본문 안에 있으므로 `Counter`의 `private count`를 볼 수 있다. 이것은 확장이어서가 아니라 *멤버여서* 접근할 수 있는 것이다(9절의 멤버 확장). (b)도 확장이 특별해서가 아니라, 코틀린의 `private`이 최상위에서는 *파일 스코프*를 뜻한다는 규칙([[26 - 가시성 한정자]]) 때문이다.

두 경우 모두 "확장이 캡슐화를 뚫는다"가 아니라 "가시성 규칙을 정상적으로 따른다"로 설명된다. 확장은 자신에게 보이는 것만 볼 수 있다는 원칙은 그대로 유지된다.

> [!warning] 흔한 오해
> "확장 함수는 클래스에 붙는 것이니 그 클래스의 내부도 볼 수 있을 것"이라고 생각하기 쉽지만 정반대다. 확장은 클래스에 *붙지 않고* 바깥에 있기 때문에 내부를 볼 수 없다. 확장이 `private`에 접근하는 것처럼 보인다면, 그 확장은 사실 그 클래스(또는 같은 파일)의 스코프 안에 선언된 것이다. 접근 권한을 결정하는 것은 확장이라는 형태가 아니라 *선언된 위치*다.

## 6. 확장 프로퍼티: 상태를 저장할 곳이 없다

### 6.1 프로퍼티도 확장할 수 있지만 조건이 하나 있다

함수만 확장할 수 있는 것은 아니다. 프로퍼티도 확장할 수 있다. `val 수신타입.이름` 문법으로 선언하고, `수신객체.이름`처럼 접근한다.

```kotlin
val String.lastIndex: Int
    get() = length - 1

data class Point(val x: Double, val y: Double)
val Point.magnitude: Double
    get() = kotlin.math.sqrt(x * x + y * y)

fun main() {
    println("Kotlin".lastIndex)          // => 5
    println(Point(3.0, 4.0).magnitude)   // => 5.0
}
```

`String.lastIndex`와 `Point.magnitude`는 그 타입에 프로퍼티가 새로 생긴 것처럼 읽힌다. 하지만 확장 함수와 똑같은 사실이 여기에도 적용된다. 이것은 정적으로 결정되는 *접근자 함수*(게터)이며, 클래스에 새 필드가 생긴 것이 아니다.

### 6.2 백킹 필드가 없으므로 초기화식도 없다

확장 프로퍼티의 결정적인 제약이 여기에 있다. 22장(프로퍼티와 백킹 필드)에서 배웠듯이, 일반 프로퍼티가 값을 저장할 때는 컴파일러가 백킹 필드 `field`를 자동으로 만들어 준다. 그런데 확장 프로퍼티는 클래스 바깥에 있는 정적 함수이므로, 그 클래스의 인스턴스 안에 저장 공간을 마련할 방법이 애초에 없다. **확장 프로퍼티에는 백킹 필드가 없다.** 따라서 다음 제약이 생긴다.

- 초기화식(`val String.foo: Int = 0`)을 붙일 수 없다. 저장할 곳이 없기 때문이다.
- 게터 본문에서 `field`를 쓸 수 없다. 그런 필드가 존재하지 않기 때문이다.
- 반드시 **커스텀 게터**(`var`라면 세터도)를 명시해야 한다.

```kotlin
// 확장 프로퍼티에 초기화식 → 불가
val String.tag: Int = 0          // 컴파일 에러: Extension property cannot be initialized
                                 //             because it has no backing field

// field 사용 → 불가
val String.tag2: Int
    get() = field                // 컴파일 에러: 'field' unresolved (백킹 필드 없음)

// 올바른 형태: 계산 게터만
val String.wordCount: Int
    get() = trim().split(Regex("\\s+")).size
```

확장 프로퍼티는 본질적으로 *계산 프로퍼티(computed property)* 일 수밖에 없다. 접근할 때마다 게터가 실행되어 값을 새로 만든다. 상태를 "저장"하는 것이 아니라 매번 "계산해서 얻는" 것이다.

### 6.3 var 확장 프로퍼티: 게터와 세터가 기존 상태를 읽고 쓴다

`var` 확장 프로퍼티도 만들 수 있다. 다만 저장할 필드가 없으므로, 게터와 세터는 각각 어딘가에 *이미 존재하는* 공개 상태를 읽고 쓰는 방식이어야 한다.

```kotlin
class MutablePoint(var x: Int, var y: Int)

// 이미 있는 x, y 위에 얹은 파생 프로퍼티
var MutablePoint.manhattan: Int
    get() = kotlin.math.abs(x) + kotlin.math.abs(y)
    set(value) {
        // 저장할 필드가 없으니, 기존 공개 상태로 환원해서 써야 함
        x = value
        y = 0
    }

fun main() {
    val p = MutablePoint(3, 4)
    println(p.manhattan)   // => 7   (게터: |3|+|4|)
    p.manhattan = 10       // 세터: x=10, y=0
    println("${p.x}, ${p.y}")   // => 10, 0
}
```

세터는 `field = value` 같은 방식으로 저장할 수 없고, 반드시 다른 공개 상태(`x`, `y`)로 값을 옮겨 저장해야 한다. 이 제약 때문에 `var` 확장 프로퍼티는 실무에서 드물고, 주로 파생 뷰(derived view)를 표현할 때만 쓴다.

> [!caution] 성능 주의
> 확장 프로퍼티에 필드가 없다는 사실은 성능에도 영향을 준다. `list.lastIndex` 같은 확장 프로퍼티는 접근할 때마다 게터가 실행된다(여기서는 `size - 1`을 계산한다). 무거운 계산을 확장 프로퍼티 게터에 넣고 반복해서 접근하면 매번 다시 계산하므로 손해를 본다.
>
> "프로퍼티처럼 보이니 저장되어 있겠지"라는 직관은 확장 프로퍼티에서 위험하다. 필드가 없으므로 캐시되지 않는다. 실제로 값을 저장해야 한다면 확장이 아니라 멤버 프로퍼티나 위임 프로퍼티([[23 - 위임 프로퍼티]])를 써야 한다.

## 7. 수신 타입의 표현력: nullable과 제네릭

### 7.1 nullable 수신 타입: null에도 호출할 수 있는 확장

수신 타입을 `T?`(nullable)로 선언하면 수신 객체가 `null`이어도 호출할 수 있는 확장이 된다. 멤버 함수로는 불가능한 일이다. `null`에는 멤버를 호출할 수 없기 때문이다. 하지만 확장은 정적 함수이고 수신자는 인자일 뿐이므로, `null`을 인자로 넘기는 데 아무 문제가 없다.

```kotlin
fun String?.orEmpty(): String {
    // this가 null일 수 있으므로 안에서 검사
    return this ?: ""
}

fun Any?.describe(): String = when (this) {
    null -> "널"
    is String -> "문자열($this)"
    else -> "기타(${this::class.simpleName})"
}

fun main() {
    val s: String? = null
    println(s.orEmpty())         // => (빈 문자열)  — null.orEmpty() 가 크래시하지 않음
    println(s.describe())        // => 널
    println("hi".describe())     // => 문자열(hi)
    println(42.describe())       // => 기타(Int)
}
```

`s.orEmpty()`에서 `s`가 `null`인데도 `NullPointerException`이 발생하지 않는다. `orEmpty`는 `orEmpty(s)`라는 정적 호출로 변환되고, 그 안에서 `this`(= `null`)를 검사하기 때문이다.

표준 라이브러리에서 `null`에 대해서도 "null"을 반환하는 `toString`(`Any?.toString()`)이나 `isNullOrEmpty()`, `isNullOrBlank()` 같은 함수는 모두 이런 nullable 수신 확장으로 만들어졌다.

```kotlin
val name: String? = null
println(name.toString())        // => null   (크래시 아님 — Any?.toString 확장)
println(name.isNullOrEmpty())   // => true
```

이런 표현력 덕분에 널 안전성(6장)을 다루는 실무 코드가 훨씬 간결해진다. `?.`로 안전 호출을 이어 붙이는 대신, nullable 값 자체를 다루는 확장을 만들어 널 처리 로직을 캡슐화할 수 있다.

### 7.2 non-null 확장은 null 수신자를 거부한다

반대로 수신 타입을 non-null `T`로 선언하면, `null`일 수 있는 값에는 안전 호출 없이 호출할 수 없다. 컴파일러가 정적 타입을 보고 막는다.

```kotlin
fun String.shout() = uppercase() + "!"   // non-null 수신자

fun main() {
    val s: String? = "hi"
    // s.shout()          // 컴파일 에러: safe(?.) or non-null asserted(!!) call required
    println(s?.shout())   // => HI!   (안전 호출로 널이면 건너뜀)
    val t: String? = null
    println(t?.shout())   // => null
}
```

즉 확장의 수신 타입에 `?`를 붙이는지 여부로 "이 확장이 널을 처리할 책임을 지는가"를 타입 수준에서 선언한다. 확장을 설계할 때 중요하게 결정해야 하는 부분이다.

### 7.3 제네릭 수신 타입: 타입 파라미터에 대한 확장

수신 타입을 제네릭으로 만들면 임의의 타입에 대해 동작하는 확장을 작성할 수 있다. 표준 라이브러리의 스코프 함수와 컬렉션 연산은 모두 이런 형태다.

```kotlin
// 임의 타입 T 위의 확장 — 스코프 함수 let의 축약판
fun <T, R> T.transform(block: (T) -> R): R = block(this)

// 제네릭 컬렉션 확장
fun <T> List<T>.secondOrNull(): T? = if (size >= 2) this[1] else null

fun main() {
    val len = "Kotlin".transform { it.length }   // => 6
    println(len)
    println(listOf(10, 20, 30).secondOrNull())   // => 20
    println(listOf(10).secondOrNull())           // => null
}
```

제네릭 확장에는 상한(bound)을 지정할 수도 있고(34장 제네릭 2), 변성이 있는 타입([[33 - 제네릭 1 - 타입 파라미터와 변성]])에 대해서도 정의할 수 있다. 특히 `inline` 확장에 `reified` 타입 파라미터를 함께 쓰면(15장 인라인 함수와 reified) 런타임에 타입을 검사하는 확장도 만들 수 있다.

```kotlin
inline fun <reified T> List<*>.filterByType(): List<T> =
    this.filterIsInstance<T>()   // reified 덕에 런타임에 T를 안다

fun main() {
    val mixed: List<Any> = listOf(1, "a", 2, "b", 3)
    println(mixed.filterByType<Int>())      // => [1, 2, 3]
    println(mixed.filterByType<String>())   // => [a, b]
}
```

### 7.4 확장과 변성의 미묘한 관계

제네릭 확장에서는 수신 타입의 타입 인자를 어떻게 쓰느냐에 따라 변성이 적용된다. 예를 들어 `List<out E>`는 공변이므로 `List<Any>`를 받는 확장에 `List<String>`을 넘길 수 있다. 그래도 확장이 정적으로 결정된다는 원칙은 바뀌지 않는다. 어떤 확장이 호출될지는 여전히 컴파일 시점의 정적 타입으로 결정되고, 제네릭은 그 정적 타입을 더 정밀하게 만들어 줄 뿐이다.

```kotlin
fun List<Number>.sumDoubles(): Double = sumOf { it.toDouble() }

fun main() {
    val ints: List<Int> = listOf(1, 2, 3)
    // List<out E> 공변 → List<Int>는 List<Number>로 취급 가능
    println(ints.sumDoubles())   // => 6.0
}
```

## 8. 스코프와 임포트: 확장이 보이는 범위

### 8.1 확장은 임포트해야 보인다

확장이 정적 함수라는 사실은 확장의 *가시성 규칙*도 결정한다. 확장 함수는 선언된 스코프 안에서 쓰거나, 다른 파일에서 **임포트했을 때**에야 `.함수()` 문법으로 쓸 수 있다. 같은 패키지의 최상위 확장은 자동으로 보이지만, 다른 패키지의 확장은 명시적으로 `import`해야 한다.

```kotlin
// 파일 geometry/Vectors.kt
package geometry

fun Double.squared(): Double = this * this
```

```kotlin
// 파일 main/App.kt
package app

import geometry.squared   // 확장을 함수처럼 임포트해야 함

fun main() {
    println(3.0.squared())   // => 9.0
}
```

`import geometry.squared`가 없으면 `3.0.squared()`는 "unresolved reference" 오류로 컴파일되지 않는다. 확장은 저절로 전역에 퍼지는 것이 아니라, 임포트해서 스코프로 가져와야 하는 *심볼*이다. 이 점 덕분에 확장의 편의를 통제할 수 있다. 어떤 확장이 활성화되어 있는지가 파일 상단의 임포트 목록에 명시적으로 드러나기 때문이다.

### 8.2 이름 충돌은 임포트로 국소적으로 해결한다

서로 다른 패키지가 같은 타입에 같은 이름의 확장을 정의할 수 있다. 이때 어느 것을 쓸지는 임포트로 정하고, 둘 다 필요하면 임포트 별칭(`as`)으로 구분한다.

```kotlin
// stringsA.kt (package a)
package a
fun String.decorate(): String = "[$this]"

// stringsB.kt (package b)
package b
fun String.decorate(): String = "<$this>"
```

```kotlin
package app

import a.decorate
import b.decorate as decorateAngle   // 별칭으로 충돌 회피

fun main() {
    println("x".decorate())        // => [x]   (a.decorate)
    println("x".decorateAngle())   // => <x>   (b.decorate, 별칭으로 호출)
}
```

이런 국소성은 확장이 정적 함수이기 때문에 얻는 큰 이점이다. 확장이 클래스에 실제로 합쳐진다면 이런 충돌은 전역에 영향을 주는 심각한 문제가 될 것이다. 하지만 정적 함수와 임포트를 쓰는 모델에서는 파일마다 원하는 확장만 골라서 가져오면 된다.

### 8.3 지역 스코프의 확장

확장은 최상위뿐 아니라 함수 안(지역), 클래스 안(멤버 확장, 9절), 객체 안에도 선언할 수 있다. 지역 확장은 해당 지역 스코프 안에서만 보인다.

```kotlin
fun process(names: List<String>): List<String> {
    // 이 함수 안에서만 보이는 지역 확장
    fun String.normalize(): String = trim().lowercase()

    return names.map { it.normalize() }
}

fun main() {
    println(process(listOf("  Alice ", "BOB")))   // => [alice, bob]
}
```

`normalize`는 `process` 함수 밖에서는 존재하지 않는다. 지역 확장은 특정 알고리즘 안에서만 의미가 있는 보조 동작을 캡슐화할 때 깔끔하게 쓸 수 있다.

> [!note] 명세 기준
> 확장 함수를 결정할 때는 두 가지를 함께 본다. (1) 수신 객체의 *정적 타입*(어떤 타입의 확장인가)과 (2) 호출 지점의 *스코프*(어떤 확장이 임포트되거나 선언되어 보이는가)이다. 멤버 함수는 (1)만으로 결정되지만(실제로는 동적 디스패치로), 확장은 (2)의 스코프 규칙도 통과해야 한다.
>
> 그래서 "이 코드에서 어떤 확장이 호출되는가"는 파일의 임포트에 따라 달라진다. 같은 표현식이라도 다른 파일에서는 다른 확장을 가리키거나, 가리키는 확장이 없을 수도 있다.

## 9. 멤버 확장: 수신자가 둘인 경우

### 9.1 클래스 안에 선언한 확장

확장을 클래스 본문 안에 선언하면 **멤버 확장(member extension)** 이 된다. 이때 확장 함수는 수신 객체를 두 개 가진다.

- **디스패치 수신자(dispatch receiver)**: 확장이 선언된 클래스의 인스턴스.
- **확장 수신자(extension receiver)**: 확장이 확장하는 타입의 인스턴스.

```kotlin
class HtmlBuilder {
    private val sb = StringBuilder()

    // String을 확장하되, HtmlBuilder의 멤버로 선언 → 멤버 확장
    fun String.wrapWith(tag: String) {
        // 여기서 두 수신자가 모두 보인다:
        //   this@HtmlBuilder : 디스패치 수신자 (HtmlBuilder 인스턴스, sb 접근 가능)
        //   this             : 확장 수신자     (String)
        sb.append("<$tag>").append(this).append("</$tag>")
    }

    fun build(block: HtmlBuilder.() -> Unit): String {
        block()
        return sb.toString()
    }
}

fun main() {
    val html = HtmlBuilder().build {
        "제목".wrapWith("h1")     // String.wrapWith 는 HtmlBuilder 안에서만 보인다
        "본문".wrapWith("p")
    }
    println(html)   // => <h1>제목</h1><p>본문</p>
}
```

`String.wrapWith`는 `HtmlBuilder` 안에 있으므로 `HtmlBuilder`의 스코프 안(위의 `build`에 넘긴 람다 내부)에서만 `"제목".wrapWith(...)`로 호출할 수 있다. 그 안에서 함수 본문은 `this`(String, 확장 수신자)와 `this@HtmlBuilder`(HtmlBuilder, 디스패치 수신자)를 동시에 볼 수 있다.

5.3절에서 본 "확장이 private에 접근하는 것처럼 보이는" 경우가 바로 이것이다. `sb`는 `private`이지만 `wrapWith`는 `HtmlBuilder`의 멤버이므로 접근할 수 있다. 접근 권한은 확장이어서가 아니라 *멤버여서* 생긴다.

### 9.2 두 수신자의 이름이 겹치면 확장 수신자가 더 가깝다

디스패치 수신자와 확장 수신자에 같은 이름의 멤버가 있으면, 암시적 `this`는 더 가까운 스코프인 **확장 수신자**를 가리킨다. 디스패치 수신자의 멤버를 쓰려면 `this@클래스명`으로 명시해야 한다.

```kotlin
class Formatter {
    fun size(): Int = -1                 // 디스패치 수신자의 size()

    fun List<Int>.report(): String {
        val a = size()                   // 확장 수신자(List)의 size() — 더 가까움
        val b = this@Formatter.size()    // 디스패치 수신자(Formatter)의 size()
        return "list=$a formatter=$b"
    }

    fun run(): String = listOf(1, 2, 3).report()
}

fun main() {
    println(Formatter().run())   // => list=3 formatter=-1
}
```

`size()`는 확장 수신자인 `List`의 `size`(값 3)를 호출하고, `this@Formatter.size()`는 명시적으로 디스패치 수신자를 지정해 `-1`을 반환한다. "가까운 수신자가 우선한다"는 이 규칙은 스코프 함수를 중첩할 때(16장 스코프 함수와 수신 객체 관용구)와 DSL(37장 타입 안전 빌더와 DSL)에서 매우 중요하다. 바로 이런 모호함을 통제하려고 `@DslMarker` 애노테이션이 존재하며, 자세한 내용은 37장에서 다룬다.

### 9.3 멤버 확장의 디스패치는 절반만 정적이다

멤버 확장은 디스패치 방식에서 흥미로운 혼합형이다. **디스패치 수신자**(선언된 클래스)에 대해서는 그 클래스가 다형적이면 가상 디스패치가 일어날 수 있지만, **확장 수신자**에 대해서는 여전히 정적으로 결정된다. 즉 "어떤 클래스의 멤버 확장을 호출하는가"는 디스패치 수신자의 실제 타입을 따를 수 있지만, "확장 수신자에 대해 어느 오버로드를 고르는가"는 정적 타입으로 결정된다.

```kotlin
open class Renderer {
    open fun Int.render(): String = "기본:$this"
}
class FancyRenderer : Renderer() {
    override fun Int.render(): String = "화려:$this"   // 디스패치 수신자 축에서 오버라이드
}

fun useRenderer(r: Renderer): String {
    with(r) {
        return 7.render()   // 확장 수신자(Int)는 정적, 디스패치 수신자(r)는 동적
    }
}

fun main() {
    println(useRenderer(Renderer()))        // => 기본:7
    println(useRenderer(FancyRenderer()))   // => 화려:7   (디스패치 수신자 다형성)
}
```

같은 `7.render()` 호출이 디스패치 수신자 `r`의 실제 타입에 따라 다른 결과를 낸다. 멤버 확장은 그 클래스의 실제 멤버(가상 메서드일 수도 있다)이기 때문이다. 확장 수신자 쪽은 정적이고 디스패치 수신자 쪽은 동적일 수 있다는 이 미묘한 공존 때문에, 멤버 확장은 확장 가운데 가장 복잡한 경우가 된다.

> [!warning] 흔한 오해
> "멤버 확장은 그냥 클래스 안에 확장을 넣은 것"이라고 가볍게 넘기기 쉽다. 하지만 멤버 확장은 확장 중에서 유일하게 다음 세 가지 성질을 가진다.
>
> - 수신자를 두 개 가진다.
> - 디스패치 수신자 쪽에서 `open`/`override`가 가능하다.
> - 그 클래스의 `private`에 접근할 수 있다.
>
> 3절에서 정리한 "확장은 정적이고 오버라이드할 수 없다"는 규칙은 확장 *수신자* 쪽에 대한 것이며, 멤버 확장이 속한 클래스(디스패치 수신자) 쪽에는 적용되지 않는다.

## 10. 컴패니언 확장과 표준 라이브러리

### 10.1 컴패니언 객체에 정의하는 확장: 정적 팩토리처럼 쓰기

동반 객체([[28 - object와 companion - 싱글턴과 동반 객체]])에도 확장을 정의할 수 있다. `타입.Companion`을 수신 타입으로 지정하면, 바깥에서 정적 팩토리 메서드를 추가한 것처럼 `타입.함수()` 형태로 호출할 수 있다. 단, 그 클래스에 컴패니언 객체가 *선언되어 있어야* 한다(비어 있어도 된다).

```kotlin
class Temperature private constructor(val celsius: Double) {
    companion object      // 비어 있어도 반드시 선언되어 있어야 확장 가능
}

// 컴패니언에 확장 → Temperature.fromFahrenheit(...) 로 호출
fun Temperature.Companion.fromFahrenheit(f: Double): Temperature =
    fromCelsius((f - 32) * 5 / 9)

fun Temperature.Companion.fromCelsius(c: Double): Temperature {
    // 실제 생성은 별도 경로 필요 (여기선 예시로 리플렉션 대신 개념만)
    return factory(c)
}

private fun factory(c: Double): Temperature =
    // 같은 파일이라 private 생성자 대신 file-private 우회 (개념 시연)
    TemperatureFactory.make(c)

private object TemperatureFactory {
    fun make(c: Double) = Temp(c)
}
private class Temp(c: Double)   // (설명용 스텁)

fun main() {
    val t = Temperature.fromFahrenheit(212.0)
    println(t.celsius)   // => 100.0
}
```

위 예제는 `private` 생성자에 접근하는 세부 사항을 단순화한 개념 시연이다. 핵심은 `Temperature.fromFahrenheit(...)`처럼 *타입 이름에 직접* 확장을 붙일 수 있다는 점이다. 컴패니언 확장은 팩토리, 파싱, 상수 생성 같은 "타입 수준" 유틸리티를 클래스를 수정하지 않고 추가하는 관용구다. 컴패니언 객체가 없는 클래스에는 이 방식을 쓸 수 없다는 점이 중요한 제약이다.

### 10.2 표준 라이브러리는 확장으로 만들어져 있다

확장이 언어의 부수적인 기능이 아니라 핵심 기능이라는 가장 강력한 증거는 표준 라이브러리 자체다. 코틀린 stdlib의 상당 부분이 확장으로 구현되어 있다.

| 영역 | 대표 확장 | 수신 타입 |
|------|-----------|-----------|
| 컬렉션 파이프라인 | `map`, `filter`, `reduce`, `fold`, `groupBy`, `first`, `associate` | `Iterable<T>`, `Sequence<T>` |
| 스코프 함수 | `let`, `run`, `apply`, `also`, `takeIf` | `T`(제네릭) |
| 문자열 | `trim`, `split`, `substringBefore`, `toIntOrNull` | `String`, `CharSequence` |
| 널 처리 | `orEmpty`, `isNullOrBlank`, `isNullOrEmpty` | `String?`, `Collection?` |
| 수/범위 | `coerceIn`, `until`, `downTo`, `sumOf` | `Int`, `Comparable<T>` |

이 사실이 뜻하는 바는 크다. 코틀린 언어의 코어([[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]])는 놀라울 만큼 작다. 우리가 "언어 기능"이라고 느끼는 많은 것(`filter`, `let`, `first`)은 사실 확장으로 만든 *라이브러리 함수*다. 확장이 있었기 때문에 stdlib는 `Iterable`, `String`, `Int` 같은 기존 타입(상당수는 자바에서 온 타입이다)을 편집하지 않고도 풍부한 API를 제공할 수 있었다.

확장은 "라이브러리로 언어를 확장하는" 메커니즘이다. 이 장에서 바로잡은 세 가지 오해는 모두 이 거대한 시스템이 어떻게 안전하게 동작하는지에 대한 오해다.

### 10.3 확장을 쓸 때와 멤버로 둘 때

마지막으로 실무 지침을 정리한다. 확장이 항상 옳은 선택은 아니다.

- **확장이 적절할 때**: 소스를 관리하지 않는 타입(표준·서드파티)에 편의 API를 추가할 때. 클래스의 핵심 책임이 아닌 부수적·파생적 동작일 때. 널 처리처럼 nullable 수신자가 필요할 때. 특정 스코프에서만 의미 있는 지역 동작일 때.
- **멤버가 적절할 때**: 클래스의 불변식을 유지하기 위해 `private` 상태에 접근해야 할 때. 다형적으로 오버라이드되어야 할 때(확장은 오버라이드할 수 없다). 그 동작이 타입의 본질적인 계약(contract)의 일부일 때.

판단의 핵심 기준은 3~5절의 세 가지 규칙이다. *다형성이 필요하면* 확장을 쓸 수 없다(정적 디스패치, 3절). *멤버와 이름이 겹치면* 확장은 가려진다(멤버 우선, 4절). *내부 상태에 접근해야 하면* 확장으로는 할 수 없다(캡슐화, 5절). 이 세 가지 제약을 받아들일 수 있을 때에만 확장이 알맞은 도구다.
