앞의 두 장 [[07 - 수 1 - Int와 Long과 부동소수점]]과 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]에서는 Kotlin의 수 타입이 "소스 코드에서는 객체이지만 JVM 백엔드에서는 원시형으로 컴파일된다"는 이중성을 살펴보았다. `Char`에도 똑같은 이중성이 있다. 소스에서 `Char`는 `Any`의 하위 타입인 온전한 클래스이지만, JVM 백엔드에서는 16비트 원시형 `char`로 컴파일된다.

그래서 이 장은 앞의 두 장에 자연스럽게 이어진다. `Char`는 "문자"라는 이름을 달고 있지만, 실제로는 **부호 없는 16비트 정수에 매우 가까운 값**, 정확히 말하면 UTF-16 코드 유닛 하나이기 때문이다.

이 장에서는 `Char`가 UTF-16 코드 유닛이라는 점에서 출발해 `String`의 불변성과 내부 표현, 유니코드 때문에 생기는 함정(코드 포인트와 코드 유닛의 차이, 서로게이트, 이모지의 길이), 문자열 템플릿이 컴파일되는 방식, raw string과 이스케이프, 문자열의 동등성·비교·연결을 차례로 다룬다.

이어서 표준 라이브러리의 문자열 함수와 멀티플랫폼에서의 `Char`/`String`까지 살펴본다. `==`(구조적 동등)와 `===`(참조 동일성)의 일반 이론은 [[10 - 불리언과 동등성과 동일성]]에서 설명한다.

## 1. Char: 정수가 아니라 UTF-16 코드 유닛이다

### 1.1 Char의 정체: 16비트이지만 "문자"는 아니다

Kotlin에서 `Char`는 흔히 문자 하나를 나타내는 타입으로 소개된다. 하지만 이 설명은 절반만 맞다. 정확히 말하면 `Char`는 **UTF-16 인코딩의 코드 유닛 하나**, 즉 16비트 값이다. 이 장에서 다루는 문제는 대부분 "문자"와 "코드 유닛"의 차이에서 생긴다. 사람이 "문자 하나"라고 부르는 것(예: 이모지 😀, 한글 조합 '각')이 언제나 코드 유닛 하나로 표현되지는 않기 때문이다.

`Char`의 범위는 `'\u0000'`부터 `'\uFFFF'`까지이다. 이는 부호 없는 16비트 정수의 범위 $[0, 2^{16}-1] = [0, 65535]$와 정확히 같다.

```kotlin
val a: Char = 'A'
println(a.code)                 // => 65
println('가'.code)              // => 44032
println('\uFFFF'.code)          // => 65535
println(Char.MIN_VALUE.code)    // => 0
println(Char.MAX_VALUE.code)    // => 65535
```

여기서 `code`는 코드 유닛의 정수 값을 돌려주는 프로퍼티이다. 이 값을 "이 문자의 유니코드 값"이라고 부르고 싶어지지만, 정확히는 **UTF-16 코드 유닛의 값**이다. U+FFFF보다 큰 유니코드 코드 포인트(예: 😀 = U+1F600)는 `Char` 하나에 담기지 않는다. 이 문제는 3절에서 자세히 다룬다.

> [!note] 명세 기준
> JVM 백엔드에서 `Char`는 원시형 `char`(16비트)로 컴파일된다. 7장(수 1)에서 `Int`가 `int`로 컴파일되는 것과 같은 원리이다. 다른 타깃(Native, JS, Wasm)에서도 `Char`가 16비트 코드 유닛이라는 **언어 수준의 계약**은 같지만, 물리적인 표현은 백엔드마다 다르다. "16비트 코드 유닛"은 언어의 계약이고, "원시형 char로 컴파일"은 JVM 백엔드의 구현이다.

### 1.2 Char와 Int 사이에는 암시적 변환이 없다

Java 프로그래머가 Kotlin에서 가장 먼저 부딪히는 차이가 이것이다. Java에서는 `char c = 'A'; int i = c + 1;`이 문제없이 컴파일되고, `char`가 `int`로 자동 승격된다. Kotlin은 이런 암시적 확대 변환을 **전혀 허용하지 않는다**. 7장에서 본 "암시적 확대 변환 없음" 원칙이 `Char`에도 그대로 적용된다.

```kotlin
val c: Char = 'A'
// val i: Int = c            // 컴파일 에러: type mismatch, Char는 Int가 아니다
val i: Int = c.code          // => 65, 명시적 변환 필요
val back: Char = 65.toChar() // => 'A', Int에서 Char로도 명시적
val back2: Char = Char(65)   // => 'A', Char(code: Int) 생성자도 가능
```

`Char`를 `Int`로 바꾸려면 `code`를 쓰고, `Int`를 `Char`로 바꾸려면 `toChar()`나 `Char(Int)` 생성자를 쓴다. 이렇게 명시해야 하는 것은 번거로워 보이지만 버그를 미리 막아 준다. 문자를 숫자로 쓰고 있다는 사실이 코드에 항상 드러나기 때문이다.

> [!info] 역사 메모
> Kotlin 1.5 이전에는 `Char.toInt()`가 `code`의 역할을 했다. 그런데 `Char.toInt()`라는 이름은 오해를 불렀다. `Int.toLong()`처럼 타입 변환으로 보였지만, `Char`에는 처음부터 "값으로서의 자연수 표현"이라는 의미가 분명하지 않았다.
>
> 그래서 1.5에서 `Char.code`(코드 유닛 값)와 `Char.digitToInt()`(숫자 문자를 해당 숫자로 변환) 등으로 의도를 나누었고, `Char.toInt()`는 사용 중단(deprecated)되었다. Kotlin 2.x 코드에서는 `code`를 쓰는 것이 표준이다. 8장(수 2)에서 부호 없는 정수를 도입한 것과 비슷하게, 이름으로 의도를 드러내려는 설계이다.

`'7'.code`와 `'7'.digitToInt()`는 반드시 구분해야 한다.

```kotlin
println('7'.code)          // => 55  (문자 '7'의 UTF-16 코드 유닛 값)
println('7'.digitToInt())  // => 7   (문자 '7'이 나타내는 숫자)
println('A'.digitToInt(16))// => 10  (16진법에서 'A'는 10)
// println('A'.digitToInt()) // 예외: IllegalArgumentException, 'A'는 10진 숫자가 아님
```

`'7'.code`가 55인 이유는 ASCII와 유니코드에서 `'0'`이 48이고, `'7'`은 그보다 7만큼 큰 55이기 때문이다. 이 관계 덕분에 `c - '0'`으로 숫자를 얻는 오래된 관용구가 성립한다(다음 절에서 설명한다).

### 1.3 Char 산술: 어떤 결과가 Char이고 어떤 결과가 Int인가

초심자가 자주 헷갈리는 비대칭이 여기서 나온다. `Char`에 정의된 산술 연산자([[19 - 연산자 오버로딩과 관례]]에서 설명하는 관례 함수)는 다음 세 가지뿐이다.

| 식 | 관례 함수 | 결과 타입 | 의미 |
|----|-----------|-----------|------|
| `Char + Int` | `Char.plus(Int)` | `Char` | 코드 유닛을 n만큼 이동한 문자 |
| `Char - Int` | `Char.minus(Int)` | `Char` | 코드 유닛을 n만큼 뒤로 이동한 문자 |
| `Char - Char` | `Char.minus(Char)` | `Int` | 두 문자의 코드 유닛 거리 |

그리고 **`Char + Char`는 없다.** 처음에는 이상해 보이지만, 의미를 따져 보면 옳은 설계이다.

```kotlin
val next: Char = 'A' + 1      // => 'B'   (Char + Int → Char)
val prev: Char = 'C' - 1      // => 'B'   (Char - Int → Char)
val dist: Int  = 'C' - 'A'    // => 2     (Char - Char → Int)
// val bad = 'A' + 'B'        // 컴파일 에러: 'A' + 'B'는 정의되지 않음
```

`Char + Char`가 없는 이유는 "문자 + 문자"에 자연스러운 의미가 없기 때문이다. `'A' + 'B'`는 무엇을 뜻해야 할까? 두 코드 값을 더한 문자(`'A'.code + 'B'.code = 65 + 66 = 131` → `''`)라고 해석할 수는 있지만, 그런 연산에는 쓸모가 없다. 반면 `Char - Char`는 두 문자가 코드 유닛 기준으로 얼마나 떨어져 있는지라는 분명한 의미(거리, `Int`)를 가진다.

이 설계는 물리학의 차원 분석과 같다. 위치(문자)에서 위치(문자)를 빼면 변위(정수)가 되지만, 위치와 위치를 더하는 것은 의미가 없다. Kotlin은 의미가 있는 연산만 타입으로 허용한다.

이 규칙에서 잘 알려진 관용구가 나온다.

```kotlin
// 숫자 문자를 실제 숫자로 (digitToInt와 동치, 단 검증 없음)
val n: Int = '7' - '0'        // => 7  (Char - Char → Int)

// 알파벳 인덱스
val idx: Int = 'e' - 'a'      // => 4

// 시저 암호(Caesar cipher): 3글자 밀기
fun shift(c: Char): Char = 'a' + (c - 'a' + 3) % 26
println(shift('x'))           // => 'a'  ('x'는 0부터 세어 23번째, +3=26, %26=0 → 'a')
// 'x' - 'a' = 23, +3 = 26, %26 = 0 → 'a' + 0 = 'a'
```

주석의 계산을 따라가 보면 `'x' - 'a' = 23`(a를 0으로 세는 0-indexed 기준으로 x는 23번째), `23 + 3 = 26`, `26 % 26 = 0`, `'a' + 0 = 'a'`이다. 즉 `x`를 3칸 밀면 알파벳을 한 바퀴 돌아 `a`가 된다. `Char - Char`는 `Int`를, `Char + Int`는 `Char`를 돌려주므로 이 한 줄은 타입 검사를 통과하고 올바르게 동작한다.

> [!warning] 흔한 오해
> "`Char`는 정수이므로 `'A' + 'B'`도 될 것"이라고 생각하기 쉽지만, 그렇지 않다. Kotlin은 `Char`를 "정수처럼 쓸 수 있는 값"이 아니라 "코드 유닛 위의 좌표"로 모델링한다. 좌표 + 좌표는 금지되고, 좌표 ± 변위는 좌표가 되며, 좌표 − 좌표는 변위가 된다. 규칙은 이 세 가지가 전부이다.

### 1.4 문자 분류와 대소문자

`Char`에는 유니코드 속성을 기준으로 문자를 분류하는 함수가 확장 함수([[35 - 확장 함수와 프로퍼티]])로 많이 정의되어 있다. 이 함수들은 ASCII만 보는 것이 아니라 유니코드 카테고리를 참조한다(구현이나 백엔드에 따라 유니코드 데이터베이스 버전이 다를 수 있다).

```kotlin
println('가'.isLetter())    // => true  (한글도 문자)
println('5'.isDigit())      // => true
println(' '.isWhitespace()) // => true
println('가'.isLetterOrDigit()) // => true
println('A'.isUpperCase())  // => true
println('a'.uppercaseChar())// => 'A'
println('İ'.uppercase())    // => "İ" (String을 반환할 수 있음, 아래 주의)
```

여기에는 미묘한 함정이 있다. `Char.uppercaseChar()`는 `Char`를 돌려주지만, `Char.uppercase()`는 `String`을 돌려준다. 어떤 문자는 대문자로 바꾸면 코드 유닛 하나로 표현할 수 없기 때문이다. 예를 들어 독일어 'ß'(에스체트)의 대문자는 두 글자인 "SS"이다.

```kotlin
println('ß'.uppercase())     // => "SS"  (String, 두 글자!)
println('ß'.uppercaseChar()) // => 'ß'   (Char로는 표현 못 해서 그대로)
```

`uppercaseChar()`는 1:1로 대응하지 않으면 원래 문자를 그대로 두는, 정보가 손실될 수 있는 연산이다. 반면 `uppercase()`는 유니코드 규칙에 맞게 정확히 대문자로 바꾸므로 `String`을 돌려준다. 로케일에 따라 달라지는 대소문자 변환(터키어 'i'/'İ' 문제)은 6.3절에서 다시 살펴본다.

## 2. String: 불변 UTF-16 시퀀스

### 2.1 불변성의 의미와 보장

`String`은 **불변(immutable)** 이다. 한 번 만든 문자열의 내용은 절대 바뀌지 않는다. 문자열을 "수정"하는 연산은 모두 실제로는 **새 문자열을 만들어 돌려준다**.

```kotlin
val s = "hello"
val t = s.uppercase()   // 새 String "HELLO"를 만든다
println(s)              // => hello  (원본 그대로)
println(t)              // => HELLO
val r = s.replace('l', 'L') // 또 새 String
println(s)              // => hello  (여전히 그대로)
```

이 불변성은 `val`/`var`와는 다른 차원의 이야기이다. `val s`는 `s`라는 이름에 다시 대입할 수 없다는 뜻일 뿐이다([[11 - 변수와 초기화 - val과 const와 lateinit]]에서 설명한다). 반면 `String`의 불변성은 문자열 객체 자체의 내용이 바뀌지 않는다는 뜻이다. 두 성질은 서로 독립적이다.

```kotlin
var s = "a"     // var: 재대입 가능
s = s + "b"     // OK: s에 새 String을 재대입, "b"를 원본에 덧붙인 게 아님
println(s)      // => ab
// 여기서 원래의 "a" 객체는 여전히 불변이었고, s가 새 "ab"를 가리키게 됐을 뿐
```

불변성에서 얻는 이점은 크다. 문자열을 자유롭게 공유해도 누구도 몰래 내용을 바꿀 수 없으므로 스레드 안전하고, 해시 값을 캐싱할 수 있으며(10장 불리언과 동등성의 `hashCode`), 방어적 복사도 필요 없다.

Kotlin은 문자열을 바꾸고 싶다는 요구를 `StringBuilder`(7절)라는 별도의 가변 타입으로 분리했다. 불변 `String`과 가변 `StringBuilder`를 나눈 것은 [[38 - 컬렉션 - 읽기 전용과 가변]]에서 `List`와 `MutableList`를 나눈 것과 같은 설계 방침이다.

### 2.2 String은 Char의 시퀀스: CharSequence 계층

`String`은 `Char`를 순서대로 담은 시퀀스이다. 인덱스로 접근할 수 있고, 순회할 수 있으며, 길이를 가진다.

```kotlin
val s = "abc"
println(s[0])          // => 'a'   (get 관례, Char 반환)
println(s.length)      // => 3
for (c in s) print("$c ") // => a b c
println(s.first())     // => 'a'
println(s.last())      // => 'c'
```

`s[0]`은 19장(연산자 오버로딩과 관례)의 `get` 관례에 따라 `s.get(0)`을 호출하고, 결과는 `Char`이다. `for (c in s)`는 `String`을 `Iterable<Char>`처럼 순회할 수 있으므로 `Char`를 하나씩 준다(엄밀히는 `iterator()` 관례이며, [[18 - 범위와 진행과 반복]]에서 다룬다).

`String`은 `CharSequence` 인터페이스를 구현한다. `CharSequence`는 "읽을 수 있는 문자 시퀀스"를 추상화한 인터페이스로, `length`, `get(index)`, `subSequence(start, end)` 세 멤버만 요구한다.

```text
        CharSequence  (인터페이스: length, get, subSequence)
        /          \
    String       StringBuilder   (그리고 java.lang.StringBuffer 등)
   (불변)         (가변)
```

이 추상화 덕분에 표준 라이브러리 함수 중 상당수가 `String`이 아니라 `CharSequence`를 받도록 선언되어 있다. 따라서 `String`과 `StringBuilder`를 똑같이 넘길 수 있다.

```kotlin
fun countVowels(cs: CharSequence): Int =
    cs.count { it in "aeiou" }

println(countVowels("hello"))              // => 2   (String)
println(countVowels(StringBuilder("wxy"))) // => 0   (StringBuilder)
```

> [!note] 명세 기준
> `String.length`는 프로퍼티이고, `CharSequence.length`도 프로퍼티이다(둘 다 접근자이며, [[22 - 프로퍼티와 백킹 필드]]에서 다룬다). Java의 `String.length()`는 메서드이지만, Kotlin에서는 Java의 `length()`가 프로퍼티 `length`로 매핑되어 노출된다([[45 - Java 상호운용]]의 getter↔프로퍼티 규칙). 그래서 Kotlin 코드에서는 괄호 없이 `s.length`로 쓴다.

### 2.3 length는 글자 수가 아니라 코드 유닛의 개수이다

`String.length`가 세는 것은 **UTF-16 코드 유닛의 개수**이다. 사람이 보는 글자 수도 아니고, 유니코드 코드 포인트의 개수도 아니다. BMP(기본 다국어 평면) 안의 문자만 쓸 때는 세 값이 우연히 같으므로 이 차이가 드러나지 않는다.

```kotlin
println("abc".length)   // => 3   (코드 유닛 3, 코드 포인트 3, 글자 3 — 모두 같음)
println("한글".length)   // => 2   (한글도 각각 BMP 안, 코드 유닛 = 코드 포인트 = 글자)
```

하지만 BMP를 벗어나는 문자가 나오면 세 값이 달라진다. 이 부분은 3절에서 본격적으로 다룬다. 여기서는 사실만 확인해 두자. `length`는 코드 유닛을 센다. 인덱스 `s[i]`도 코드 유닛 단위로 접근하므로 서로게이트 쌍의 절반을 가리킬 수 있고, 그러면 반쪽짜리 `Char`가 나온다.

### 2.4 JVM에서의 String 표현과 인턴

JVM 백엔드에서 Kotlin의 `String`은 `java.lang.String`과 **같은 타입**이다(45장 Java 상호운용). 별도로 감싸지 않는다. 그래서 Java의 문자열 상수 풀(string constant pool)과 인턴(interning) 메커니즘이 그대로 적용된다.

소스 코드에 나오는 문자열 리터럴은 JVM에서 상수 풀에 인턴되므로, 같은 리터럴은 같은 객체를 가리킨다.

```kotlin
val a = "hello"
val b = "hello"
println(a == b)    // => true   (구조적 동등: 내용이 같다)
println(a === b)   // => true   (참조 동일: JVM에서 리터럴이 인턴되어 같은 객체)

val c = StringBuilder("hel").append("lo").toString()
println(a == c)    // => true   (내용 같음)
println(a === c)   // => false  (런타임에 만든 새 객체, 다른 참조)
```

여기서 얻을 중요한 교훈은 **Kotlin에서 문자열을 비교할 때는 언제나 `==`(구조적 동등, `equals`)를 써야 한다**는 것이다. `===`(참조 동일성)로 문자열을 비교하는 것은 거의 언제나 버그이다. `a === c`가 `false`인 것에서 보듯, 내용은 같지만 서로 다른 객체인 문자열은 얼마든지 생긴다.

이 함정은 Java의 유명한 버그와 같다. Java의 `==`는 참조를 비교하므로, 리터럴끼리는 우연히 `true`를 주지만 런타임에 만든 문자열에는 `false`를 준다.

Kotlin은 이 함정을 언어 차원에서 대부분 없앴다. Kotlin의 `==`는 `equals`를 호출하므로(10장 불리언과 동등성) 언제나 내용을 비교한다. Java에서 넘어온 사람은 "Kotlin의 `==`는 Java의 `==`가 아니라 Java의 `.equals()`에 해당한다"는 점을 확실히 익혀 두어야 한다. 이 주제는 6절에서 더 자세히 다룬다.

> [!caution] 성능 주의
> JDK 9 이상의 "compact strings" 최적화에서 `java.lang.String`은 문자열이 전부 Latin-1(코드 유닛 0~255) 범위이면 내부적으로 `byte[]`(문자당 1바이트)에 저장하고, 그렇지 않으면 `byte[]`+UTF-16 coder로 저장한다(구현 세부 사항이며 JDK 버전에 따라 다르다).
>
> 하지만 이는 내부 저장 방식의 최적화일 뿐이며, `length`·`get`·순회가 **UTF-16 코드 유닛 단위로 동작한다는 의미는 전혀 바뀌지 않는다**. Kotlin 소스에서는 항상 "코드 유닛의 시퀀스"라는 논리 모델만 생각하면 된다. 물리적 저장 방식은 [[46 - 멀티플랫폼과 진화와 어두운 구석]]에서 다룬다.

## 3. 유니코드: 코드 포인트와 코드 유닛, 그리고 이모지 함정

이 절이 이 장의 핵심이다. 앞에서 계속 "코드 유닛"과 "글자"를 구분했는데, 이제 그 구분이 왜 반드시 필요한지, 사람들이 어디서 실수하는지를 JVM 수준에서 자세히 살펴본다.

### 3.1 유니코드의 세 층위: 코드 포인트, 인코딩, 그래핌

문자열을 정확히 이해하려면 세 층위를 구분해야 한다.

```text
[ 사람이 보는 글자 ]   그래핌 클러스터(grapheme cluster)   예: 각, 👨‍👩‍👧, é
        ↑ (렌더링/결합 규칙)
[ 유니코드의 추상 문자 ]  코드 포인트(code point)           예: U+AC01, U+1F600, U+0065 U+0301
        ↑ (인코딩)
[ 저장되는 실제 바이트 ]  코드 유닛(code unit)              UTF-16: 16비트 단위, UTF-8: 8비트 단위
```

- **코드 포인트(code point)**: 유니코드가 추상 문자마다 부여한 번호이다. U+0000부터 U+10FFFF까지 모두 $17 \times 2^{16} = 1{,}114{,}112$개의 자리가 있다. `U+` 뒤의 16진수가 코드 포인트이다.
- **코드 유닛(code unit)**: 특정 인코딩에서 저장하는 단위 하나이다. UTF-16은 16비트, UTF-8은 8비트, UTF-32는 32비트가 코드 유닛이다.
- **그래핌 클러스터**: 사람이 "한 글자"로 인식하는 단위이다. 여러 코드 포인트가 결합해 하나로 보일 수 있다(결합 문자, 이모지 ZWJ 시퀀스 등).

Kotlin의 `Char`는 **UTF-16 코드 유닛**이고, `String.length`는 **코드 유닛의 개수**이다. 코드 포인트도 아니고 그래핌도 아니다. 3절의 나머지 내용은 모두 이 사실에서 나온다.

### 3.2 UTF-16과 서로게이트 쌍

유니코드 코드 포인트는 U+10FFFF까지 있지만, 16비트 코드 유닛 하나로는 U+FFFF까지만 표현할 수 있다($2^{16}=65536$). 그렇다면 U+10000 이상(보충 평면, supplementary planes)의 문자는 UTF-16에서 어떻게 표현할까? **서로게이트 쌍(surrogate pair)**, 즉 16비트 코드 유닛 두 개로 표현한다.

유니코드는 이를 위해 BMP 안에 특별한 영역을 비워 두었다. U+D800~U+DBFF(하이 서로게이트 1024개)와 U+DC00~U+DFFF(로우 서로게이트 1024개)는 **그 자체로는 문자가 아니며**, 쌍을 이루어 보충 평면의 코드 포인트를 인코딩하는 데만 쓰인다. 조합의 수는 $1024 \times 1024 = 2^{20} = 1{,}048{,}576$개이고, 이는 U+10000~U+10FFFF 범위의 크기와 정확히 같다.

코드 포인트 $C$ ($C \geq \text{0x10000}$)를 서로게이트 쌍 (high, low)로 인코딩하는 공식은 다음과 같다.

$$
C' = C - \text{0x10000}, \quad \text{high} = \text{0xD800} + \lfloor C'/\text{0x400}\rfloor, \quad \text{low} = \text{0xDC00} + (C' \bmod \text{0x400})
$$

역변환(디코딩)은 다음과 같다.

$$
C = \text{0x10000} + (\text{high} - \text{0xD800}) \times \text{0x400} + (\text{low} - \text{0xDC00})
$$

예를 들어 😀 = U+1F600을 살펴보자.

```kotlin
val emoji = "😀"
println(emoji.length)             // => 2   (코드 유닛 2개!)
println(emoji[0].code.toString(16)) // => d83d  (하이 서로게이트 U+D83D)
println(emoji[1].code.toString(16)) // => de00  (로우 서로게이트 U+DE00)

// 서로게이트 쌍에서 코드 포인트 복원
val high = emoji[0].code   // 0xD83D = 55357
val low  = emoji[1].code   // 0xDE00 = 56832
val cp = 0x10000 + (high - 0xD800) * 0x400 + (low - 0xDC00)
println(cp.toString(16))          // => 1f600  (U+1F600, 복원 성공!)
```

계산을 확인해 보자. `high - 0xD800 = 0xD83D - 0xD800 = 0x3D = 61`이고, `low - 0xDC00 = 0xDE00 - 0xDC00 = 0x200 = 512`이다. 따라서 `0x10000 + 61 * 0x400 + 512 = 65536 + 61*1024 + 512 = 65536 + 62464 + 512 = 128512 = 0x1F600`이 되며, 이는 정확히 😀의 코드 포인트이다.

표준 라이브러리에는 (공통 소스셋에도) `Char`가 서로게이트인지 판별하는 함수가 있다.

```kotlin
val emoji = "😀"
println(emoji[0].isHighSurrogate()) // => true
println(emoji[1].isLowSurrogate())  // => true
println(emoji[0].isSurrogate())     // => true
println('A'.isSurrogate())          // => false
```

### 3.3 이모지 길이 함정: length가 예상과 다른 이유

이제 잘 알려진 함정을 직접 살펴보자. 이모지 하나로 된 문자열의 length는 왜 2일까?

```kotlin
println("😀".length)         // => 2   (서로게이트 쌍이라 코드 유닛 2개)
println("a😀b".length)       // => 4   (a=1, 😀=2, b=1)
println("😀"[0])             // => '?'  (반쪽 서로게이트, 온전한 문자가 아님)
```

`"😀".length`가 2인 이유는 이제 알 수 있다. `length`는 코드 유닛을 세고, 😀는 서로게이트 쌍이므로 코드 유닛이 2개이다. 더 큰 문제는 `"😀"[0]`이 하이 서로게이트 하나만 돌려준다는 점이다. 이 값은 그 자체로는 유효한 문자가 아니라 반쪽짜리 코드 유닛이며, 출력하면 대개 `?`나 깨진 글자로 보인다.

이 함정은 실무에서 문자열을 자를 때 심각한 문제를 일으킨다.

```kotlin
val s = "a😀b"
println(s.substring(0, 2))   // => "a?"  서로게이트 쌍을 반으로 갈랐다!
// s.substring(0, 2)는 코드 유닛 0,1을 취함: 'a' + 하이 서로게이트 반쪽
```

`substring`, 인덱스 슬라이싱, `take`/`drop`, 반복문 안의 `s[i]` 등 **코드 유닛을 기준으로 하는 연산은 모두 서로게이트 쌍을 쪼갤 위험**이 있다. "앞의 n글자만 잘라 미리보기로 보여 주기" 같은 단순한 코드가 이모지를 만나면 깨진 문자를 만든다.

> [!warning] 흔한 오해
> "이모지는 특수한 경우라서 우리 앱에는 나오지 않는다"고 방심하면 사고가 난다. 이모지뿐 아니라 CJK 확장 한자(𩸽 같은 희귀 한자), 고대 문자, 수학 기호($\mathbb{Z}$의 볼드 유니코드 등)도 모두 보충 평면에 있으므로 서로게이트 쌍으로 표현된다. 사용자 이름, 닉네임, 메모처럼 자유롭게 입력받는 곳이라면 반드시 나온다.

### 3.4 코드 포인트 단위로 다루기

그렇다면 실제 유니코드 문자(코드 포인트) 단위로 세거나 순회하려면 어떻게 해야 할까? JVM 백엔드에서는 `java.lang.String`/`Character`의 코드 포인트 API를 쓸 수 있다.

```kotlin
// JVM 백엔드 한정: java.lang.Character / String의 코드 포인트 API
val s = "a😀b"
println(s.length)                          // => 4   (코드 유닛)
println(s.codePointCount(0, s.length))     // => 3   (코드 포인트: a, 😀, b)
s.codePoints().forEach {
    println("U+${it.toString(16).uppercase()}")
}
// => U+61   (a)
// => U+1F600 (😀)
// => U+62   (b)
```

`codePointCount`, `codePoints()`, `codePointAt(index)`는 `java.lang.String`의 메서드이며, JVM에서 그대로 호출된다. 이 메서드들은 서로게이트 쌍을 코드 포인트 하나로 묶어서 센다. 코드 포인트로 문자열을 만들 때는 `Character.toChars(codePoint)`나 문자열 빌더를 쓴다.

```kotlin
// JVM 백엔드: 코드 포인트에서 String 만들기
val emoji = String(Character.toChars(0x1F600))
println(emoji)      // => 😀
println(emoji.length) // => 2  (여전히 UTF-16 코드 유닛으로는 2)
```

공통(common) 소스셋에는 `codePoints()` 같은 함수가 없을 수 있다. 따라서 멀티플랫폼 코드에서는 서로게이트를 직접 판별해 3.2절의 공식으로 코드 포인트를 조립하거나, 코드 포인트를 순회하는 유틸리티를 직접 구현해야 한다. 코드 포인트 API가 어디까지 공통으로 제공되는지는 백엔드와 표준 라이브러리 버전에 따라 다르므로, 멀티플랫폼 라이브러리를 만든다면 실제 표준 라이브러리 문서에서 확인해야 한다.

### 3.5 그래핌 클러스터: 코드 포인트도 "글자"는 아니다

코드 포인트 단위로 세면 이제 글자 수가 맞을까? 여전히 그렇지 않다. 사람이 보는 "한 글자"는 여러 코드 포인트가 결합한 **그래핌 클러스터**일 수 있다.

```kotlin
// 결합 문자: 'e' + 결합 악센트(U+0301)
val precomposed = "é"        // é (완성형 코드 포인트 U+00E9)
val decomposed  = "é"       // e + ́ (결합 악센트)
println(precomposed.length)       // => 1   (코드 유닛 1)
println(decomposed.length)        // => 2   (코드 유닛 2: e + 결합문자)
println(precomposed == decomposed)// => false  (코드 유닛이 다르므로!)
// 화면에는 둘 다 "é"로 똑같이 보이지만 다른 문자열이다
```

이 문제는 6절의 동등성 함정과도 이어진다. 화면에서는 똑같아 보이는 두 "é"가 `==`로 비교하면 다르다. 비교 결과를 안정적으로 얻으려면 유니코드 정규화(NFC/NFD)를 거쳐야 하는데, 이는 표준 라이브러리 공통 API가 다루지 않는 영역(JVM에서는 `java.text.Normalizer`)이므로 이 장에서는 개념만 짚는다.

더 극단적인 예는 이모지 ZWJ(Zero Width Joiner) 시퀀스이다. "가족" 이모지 👨‍👩‍👧는 사람에게는 한 글자이지만, 코드 포인트로는 여러 개(남자 + ZWJ + 여자 + ZWJ + 소녀)이고 코드 유닛으로는 그보다 더 많다.

```kotlin
val family = "👨‍👩‍👧"
println(family.length)        // => 8  (구현/이모지 버전에 따라, 코드 유닛 여러 개)
// 사람에겐 1글자, 코드 포인트론 5개(3인물 + ZWJ 2개), 코드 유닛으론 8개
```

정리하면, 글자 수를 정확히 세는 단위는 그래핌 클러스터이다. 그러나 그래핌 클러스터를 나누려면 유니코드 텍스트 분할(UAX #29) 규칙을 따르는 복잡한 알고리즘이 필요하며, 이 알고리즘은 Kotlin 표준 라이브러리 공통 API에 없다. `String.length`가 세 층위 중 가장 아래인 코드 유닛을 센다는 사실만 확실히 기억하면, 이모지가 2로 세어지는 이유와 substring이 문자를 깨뜨리는 이유를 모두 설명할 수 있다.

```text
"👨‍👩‍👧" 를 세는 단위별 개수
┌──────────────────┬──────┬────────────────────────────────┐
│ 단위             │ 개수 │ Kotlin API                     │
├──────────────────┼──────┼────────────────────────────────┤
│ 그래핌(사람 글자)│  1   │ (표준 라이브러리 공통엔 없음)  │
│ 코드 포인트      │  5   │ codePointCount (JVM)           │
│ 코드 유닛(Char)  │  8   │ length                         │
└──────────────────┴──────┴────────────────────────────────┘
```

## 4. 문자열 템플릿: `$x`와 `${expr}`, 그리고 컴파일 결과

### 4.1 문법: `$identifier`와 `${expression}`

Kotlin의 문자열 템플릿은 문자열 안에 값을 삽입하는 언어 기능이다. 두 가지 형태가 있다.

```kotlin
val name = "Toby"
val age = 7
println("$name is $age years old")       // => Toby is 7 years old
println("${name.uppercase()} scored ${age * 10}") // => TOBY scored 70
println("next year: ${age + 1}")         // => next year: 8
```

- `$identifier`: 단순한 식별자(변수 이름) 하나를 삽입한다. 예: `$name`.
- `${expression}`: 임의의 표현식을 중괄호로 감싸 삽입한다. 예: `${age + 1}`, `${list.size}`.

여기에는 자주 빠지는 함정이 있다. `$` 뒤에서는 **식별자 하나만** 읽는다. 프로퍼티에 접근하거나 함수를 호출하려면 반드시 `${}`를 써야 한다.

```kotlin
data class Point(val x: Int, val y: Int)
val p = Point(3, 4)

println("$p.x")     // => Point(x=3, y=4).x   ← 함정! $p만 해석되고 .x는 리터럴
println("${p.x}")   // => 3                    ← 올바름
```

`"$p.x"`에서 `$p`는 `p` 객체 전체를 문자열로 바꾸고, 그 뒤의 `.x`는 그냥 리터럴 텍스트이다. 프로퍼티 값인 `p.x`를 원한다면 `"${p.x}"`라고 써야 한다. 초심자라면 거의 반드시 한 번은 겪는 실수이다.

### 4.2 템플릿의 컴파일 결과

문자열 템플릿에 특별한 마법은 없다. 컴파일러는 템플릿을 **문자열 연결(concatenation)** 로 desugar한다. JVM 백엔드에서는 전통적으로 `StringBuilder`를 사용하는 코드로 변환된다(개념적인 의사코드).

```kotlin
val s = "$name is $age years old"
```

위 코드는 대략 다음 코드와 같은 형태로 컴파일된다(JVM 백엔드, 개념적 표현).

```java
// 개념적 desugar (JVM 백엔드, 전통적 형태)
String s = new StringBuilder()
    .append("")
    .append(name)
    .append(" is ")
    .append(age)
    .append(" years old")
    .toString();
```

각 `append`는 리터럴 조각과 삽입된 값을 번갈아 붙인다. 삽입된 값이 `String`이 아니면 `toString()`을 거쳐 문자열로 바뀐다(다음 절에서 설명한다). 템플릿이 없는 순수한 리터럴 문자열은 상수 풀에 그대로 들어가므로 이런 변환을 거치지 않는다.

> [!caution] 성능 주의
> JVM 9 이상에서는 `-Xstring-concat=indy`나 `indy-with-constants` 컴파일러 옵션을 쓰면 템플릿을 `StringBuilder` 대신 `invokedynamic`(`java.lang.invoke.StringConcatFactory`) 기반 문자열 연결로 컴파일할 수 있다. 이 방식은 런타임이 가장 적합한 연결 전략을 고르게 하므로 더 빠를 수 있다.
>
> 어떤 전략을 쓰는지는 컴파일러 버전과 옵션, 타깃 JVM에 따라 다르다(구현 세부 사항). 따라서 "템플릿은 문자열 연결로 바뀐다"는 개념만 확실히 해 두고, 물리적인 형태는 백엔드가 결정하도록 둔다. 핵심은 **템플릿이 런타임에 문자열을 파싱하는 것이 아니라 컴파일 타임에 정해진 연결 코드**라는 점이다.

주변에 리터럴 없이 값 하나만 삽입하는 템플릿 `"$x"`는 개념적으로 `x`를 문자열로 바꾸는 코드 하나로 컴파일된다. 즉 `String.valueOf(x)`에 해당하는 널 안전 변환이 일어난다.

### 4.3 null과 toString

템플릿에 삽입한 값은 `toString()`을 거쳐 문자열이 된다. 그렇다면 값이 `null`이면 어떻게 될까? `null.toString()`을 호출하면 NPE가 날 것 같지만, 템플릿은 null을 안전하게 처리해 `"null"`이라는 문자열을 넣는다.

```kotlin
val x: String? = null
println("value: $x")       // => value: null   (NPE 아님!)
println("value: ${x}")     // => value: null
```

컴파일러가 `String.valueOf`에 해당하는 널 안전 변환을 쓰기 때문이다(null이면 리터럴 `"null"`). 그래서 로그 문자열에 nullable 값을 안심하고 넣을 수 있다. [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 본 널 안전성 원칙이 여기에도 적용되어 있다.

`toString()`을 직접 정의하면 템플릿에는 그 결과가 들어간다([[27 - 데이터 클래스]]가 자동으로 만드는 `toString`도 마찬가지이다).

```kotlin
class Money(val cents: Int) {
    override fun toString() = "$%.2f".format(cents / 100.0)
}
println("price: ${Money(1250)}")  // => price: $12.50
```

### 4.4 템플릿 안의 `$`와 이스케이프

문자 그대로의 `$`를 문자열에 넣으려면 이스케이프해야 한다. 일반 문자열에서는 `\$`를 쓰고, raw string에서는 `${'$'}` 관용구를 쓴다(raw string은 백슬래시 이스케이프를 해석하지 않기 때문이다. 5절에서 설명한다).

```kotlin
val price = 5
println("cost: \$$price")           // => cost: $5   (\$는 리터럴 $, $price는 삽입)
println("""cost: ${'$'}$price""")   // => cost: $5   (raw string에서 리터럴 $)
```

`${'$'}`는 문자 `'$'`를 표현식으로 삽입하는 방식으로, raw string에 리터럴 `$`를 넣는 표준 관용구이다. `$` 뒤에 식별자나 `{`가 오지 않으면 그냥 리터럴 `$`로 취급되기도 하지만(예: `"5$ each"`처럼 `$` 뒤가 공백인 경우), 의도를 분명히 하려면 이스케이프를 쓰는 편이 안전하다.

## 5. 이스케이프와 raw string

### 5.1 이스케이프 시퀀스

일반 문자열 리터럴(`"..."`)과 문자 리터럴(`'...'`)은 백슬래시 이스케이프를 해석한다. Kotlin이 지원하는 이스케이프 시퀀스는 많지 않고 명확하다.

| 이스케이프 | 의미 | 코드 유닛 |
|-----------|------|-----------|
| `\t` | 탭 | U+0009 |
| `\n` | 줄바꿈(LF) | U+000A |
| `\r` | 캐리지 리턴(CR) | U+000D |
| `\b` | 백스페이스 | U+0008 |
| `\'` | 작은따옴표 | U+0027 |
| `\"` | 큰따옴표 | U+0022 |
| `\\` | 백슬래시 | U+005C |
| `\$` | 달러 기호 | U+0024 |
| `\uXXXX` | UTF-16 코드 유닛 | (16진 4자리) |

```kotlin
val tab = "col1\tcol2"
val quote = "She said \"hi\""
val path = "C:\\Users\\toby"
val nl = "line1\nline2"
println('A')     // => A
```

Kotlin에는 Java나 C에 있는 **8진 이스케이프(`\0`, `\012`)가 없다.** 널 문자는 `'\u0000'`으로 써야 한다. 또 위 표에 없는 이스케이프(예: `\d`, `\x41`)를 쓰면 컴파일 에러가 난다. 지원하는 것만 명시적으로 지원하는 Kotlin의 엄격한 설계이다.

```kotlin
// val bad = "\x41"   // 컴파일 에러: illegal escape
val nul = "\u0000"    // 널 문자는 유니코드 이스케이프로
```

### 5.2 \uXXXX는 코드 포인트가 아니라 코드 유닛이다

이 절에서 바로잡을 핵심 오해는 다음과 같다. `\uXXXX`는 정확히 **UTF-16 코드 유닛 하나**(16비트, 16진 4자리)를 나타내며, "유니코드 문자"를 나타내지 않는다. 그래서 BMP 밖의 문자(😀 = U+1F600)는 `\u` 하나로 쓸 수 없고, 서로게이트 쌍 두 개를 써야 한다.

```kotlin
val a = "\u0041"       // => "A"   (U+0041, BMP)
val ga = "\uAC01"          // => "각"  (U+AC01, BMP)
// val emoji = "\u1F600"   // 이건 "ὠ" + "0" 으로 파싱됨! (4자리만 읽음)
val emoji = "\uD83D\uDE00" // => "😀"  서로게이트 쌍으로 U+1F600 표현
println(emoji)             // => 😀
println(emoji.length)      // => 2
```

`"\u1F600"`이 위험한 이유는 `\u`가 **정확히 16진 숫자 4개**만 읽기 때문이다. 그래서 `"\u1F600"`은 `"ὠ"`(U+1F60 = 그리스 문자 'ὠ') 뒤에 리터럴 `'0'`이 붙은 문자열로 해석되며, 의도한 😀와 전혀 다르다. 보충 평면 문자를 리터럴로 쓰려면 서로게이트 쌍 `"\uD83D\uDE00"`(코드 유닛 2개)을 쓰거나, 소스 파일에 이모지 문자를 직접 붙여 넣는 편이 안전하다(소스 파일은 대개 UTF-8이다).

> [!note] 명세 기준
> `\u`가 코드 유닛(16진 4자리)을 나타낸다는 것은 Java와 같은 계약이다. 이는 Kotlin의 `Char`가 UTF-16 코드 유닛이라는 1절의 정의와 정확히 맞아떨어진다. `Char` 하나가 코드 유닛 하나이고 `\uXXXX`가 코드 유닛 하나를 나타내므로, 문자 리터럴 `'\uXXXX'`에는 정확히 하나만 들어간다. `'😀'`는 코드 유닛이 2개이므로 문자 리터럴로 쓸 수 없으며, 쓰면 컴파일 에러가 난다.

```kotlin
// val c: Char = '😀'   // 컴파일 에러: too many characters in a character literal
val c: Char = 'A'        // OK, 코드 유닛 하나
```

### 5.3 raw string: """..."""

raw string(원시 문자열, 삼중 따옴표 `"""..."""`)은 **백슬래시 이스케이프를 해석하지 않으며**, 줄바꿈을 포함한 여러 줄을 그대로 담는다. 정규식, 파일 경로, JSON/SQL 조각, 여러 줄 텍스트에 알맞다.

```kotlin
val regex = """\d+\.\d+"""      // 백슬래시가 그대로 (이스케이프 안 함)
println(regex)                  // => \d+\.\d+

val path = """C:\Users\toby"""  // 백슬래시 이스케이프 지옥 탈출
println(path)                   // => C:\Users\toby

val json = """
    {
        "name": "Toby",
        "age": 7
    }
"""
```

raw string에서 `\n`은 "백슬래시와 n" 두 글자 그대로이다. 실제 줄바꿈을 넣으려면 소스에서 줄을 바꾸면 된다. 큰따옴표도 이스케이프 없이 넣을 수 있다(단, 세 개 이상 연속되면 주의해야 한다). 유일한 예외는 앞에서 본 `$`이다. raw string에서도 템플릿은 동작하므로 리터럴 `$`는 `${'$'}`로 넣는다.

### 5.4 trimIndent와 trimMargin이 잘라 내는 것

raw string을 코드 안에서 들여쓰기와 함께 쓰면 그 들여쓰기 공백도 문자열에 포함된다. 이를 정리하는 함수가 `trimIndent()`와 `trimMargin()`이다. 두 함수의 동작 차이를 정확히 알아 두어야 한다.

**`trimIndent()`**: 모든 줄에서 **공통 최소 들여쓰기**를 찾아 각 줄에서 그만큼 제거한다. 또 첫 줄과 마지막 줄이 공백뿐이면 제거한다(즉 앞뒤의 빈 줄을 정리한다).

```kotlin
val text = """
    Hello
      World
    End
""".trimIndent()
println(text)
// => Hello
//   World
// End
```

여기서 세 줄 `Hello`, `World`, `End`의 공통 최소 들여쓰기는 4칸(`Hello`, `End`)이다(`World`는 6칸이지만 최소값은 4이다). 그래서 각 줄에서 4칸을 제거하므로 `Hello`는 0칸, `World`는 2칸(6-4), `End`는 0칸이 남는다. 첫 줄(`"""` 다음의 빈 줄)과 마지막 줄(닫는 `"""` 앞의 빈 줄)은 제거된다.

**`trimMargin(marginPrefix = "|")`**: 각 줄에서 앞쪽 공백과 **마진 접두사(기본값 `|`)까지**를 제거한다. 명시적인 마진 마커로 내용의 시작 위치를 표시하는 방식이라 결과를 예측하기 쉽다.

```kotlin
val text = """
    |Hello
    |  World
    |End
""".trimMargin()
println(text)
// => Hello
//   World
// End
```

각 줄에서 `|` 앞의 공백과 `|` 자체를 제거한다. 그래서 `|Hello`는 `Hello`, `|  World`는 `  World`(마진 뒤의 공백은 보존), `|End`는 `End`가 된다. 마진 접두사는 `trimMargin(">")`처럼 바꿀 수 있다.

두 함수의 핵심 차이는 다음과 같다.

| | `trimIndent()` | `trimMargin("\|")` |
|---|---|---|
| 기준 | 공통 최소 들여쓰기(자동 계산) | 명시적 마진 마커 `\|` |
| 마커 필요 | 없음 | 각 줄에 `\|` 필요 |
| 빈 줄이 섞이면 | 빈 줄은 공통 계산에서 제외 | 마커 없는 줄은 그대로 |
| 예측성 | 들여쓰기가 섞이면 헷갈림 | 마커로 명확 |

> [!caution] 성능 주의
> `trimIndent()`와 `trimMargin()`은 **런타임에** 문자열을 처리하는 일반 함수이며, 컴파일 타임 상수가 아니다. 즉 raw string 리터럴 자체는 들여쓰기까지 포함한 원본이고, `trimIndent()`가 실행 시점에 새 문자열을 만든다. 자주 실행되는 반복문(hot loop)에서 매번 `"""...""".trimIndent()`를 호출하면 매번 문자열을 새로 만들게 되므로, 내용이 고정되어 있다면 최상위 `val`로 한 번만 계산하는 것이 좋다.

## 6. 동등성과 비교: `==`는 안전하지만 유니코드는 단순하지 않다

### 6.1 `==`는 구조적 동등이다 (Java의 함정이 없다)

Kotlin에서 두 문자열을 비교할 때는 `==`를 쓴다. Kotlin의 `==`는 `equals`를 호출하는 **구조적 동등**이므로(10장 불리언과 동등성), 내용이 같으면 `true`이다. 참조를 비교하는 Java의 `==`와는 다르다.

```kotlin
val a = "hello"
val b = buildString { append("hel"); append("lo") }
println(a == b)    // => true   (내용 같음, equals)
println(a === b)   // => false  (참조 다름, b는 런타임 생성)
println(a.equals(b)) // => true
```

Java에서 `"hello" == someRuntimeString`이 `false`를 내는 유명한 버그는 Kotlin의 `==`에서는 생기지 않는다. Kotlin이 언어 차원에서 개선한 부분이다. `null` 비교도 안전하다. `==`는 양쪽이 null인 경우를 알아서 처리한다.

```kotlin
val x: String? = null
println(x == "a")     // => false  (NPE 아님)
println(x == null)    // => true
println(null == null) // => true
```

`==`는 개념적으로 `a?.equals(b) ?: (b === null)`처럼 동작한다. 즉 좌변이 null이면 우변도 null일 때만 `true`이다. 그래서 문자열 비교에 null이 섞여도 안심할 수 있다.

### 6.2 compareTo: UTF-16 코드 유닛 기준의 사전식 순서

문자열의 크기 비교(`<`, `>`, 정렬)는 `Comparable<String>`의 `compareTo`를 거친다(19장 연산자 오버로딩과 관례). `String.compareTo`는 **UTF-16 코드 유닛 값을 앞에서부터 비교하는 사전식(lexicographic) 순서**를 따른다.

```kotlin
println("apple" < "banana")  // => true   ('a'(97) < 'b'(98))
println("Apple" < "apple")   // => true   ('A'(65) < 'a'(97), 대문자가 앞!)
println("abc" < "abd")       // => true   앞 두 글자 같고 'c' < 'd'
println("ab" < "abc")        // => true   접두사가 더 짧으면 앞
println(listOf("banana","apple","cherry").sorted())
// => [apple, banana, cherry]
```

`compareTo`는 처음으로 달라지는 위치에서 코드 유닛 값의 차이를 본다. `"Apple" < "apple"`이 `true`인 것은 대문자 `'A'`(65)의 코드 유닛 값이 소문자 `'a'`(97)보다 작기 때문이다. 이 순서는 일반적인 사전 순서와 미묘하게 다르다. 사람이 쓰는 사전은 대소문자를 무시하지만, 코드 유닛 순서에서는 모든 대문자(65~90)가 모든 소문자(97~122)보다 앞에 온다.

> [!note] 명세 기준
> 사전식 비교가 코드 유닛을 기준으로 하므로, 보충 평면 문자가 섞이면 **코드 포인트 순서와 어긋날 수 있다.** 서로게이트(U+D800~U+DFFF)는 코드 유닛 값이 U+E000~U+FFFF의 BMP 문자보다 작다. 그래서 U+1F600(서로게이트로 시작) 같은 이모지는 코드 유닛 비교에서 U+E000대 BMP 문자보다 "작게" 정렬될 수 있으며, 이는 코드 포인트 순서(U+1F600 > U+E000)와 반대이다.
>
> 대부분의 앱에서는 문제가 되지 않지만, 유니코드 전체를 정확히 정렬해야 한다면 코드 포인트 기반 비교(또는 로케일을 인식하는 `Collator`)가 필요하다.

### 6.3 대소문자를 무시한 비교와 로케일 함정

대소문자를 무시하고 비교하려면 `equals`의 `ignoreCase` 파라미터나 `compareTo`의 옵션을 쓴다.

```kotlin
println("Hello".equals("HELLO", ignoreCase = true)) // => true
println("Hello".compareTo("HELLO", ignoreCase = true)) // => 0
```

여기에는 로케일 함정이 있다. 대소문자 변환 규칙은 언어마다 다르다. 가장 유명한 예가 터키어의 점 없는 i이다. 터키어 로케일에서 `'i'`의 대문자는 `'İ'`(점 있는 대문자 I)이고, `'I'`의 소문자는 `'ı'`(점 없는 소문자)이다. 그래서 로케일을 인식하는 변환은 예상하지 못한 결과를 낸다.

```kotlin
// JVM 백엔드: 로케일에 의존하는 변환은 함정
val turkish = java.util.Locale("tr", "TR")
println("title".uppercase(turkish))  // => "TİTLE"  (i가 점 있는 İ로!)
println("TITLE".lowercase(turkish))  // => "tıtle"  (I가 점 없는 ı로!)
```

그래서 Kotlin 표준 라이브러리의 `uppercase()`/`lowercase()`(파라미터 없는 버전)는 **로케일과 무관하게**(root/invariant locale) 동작하도록 설계되었다. 식별자, 프로토콜 토큰, 키 비교처럼 언어와 관계없이 일관되어야 하는 대소문자 처리에는 이 로케일 독립 버전을 써야 한다.

로케일을 고려하는 것은 사람에게 보여 줄 텍스트의 대소문자를 바꿀 때뿐이다. 이 구분을 놓치면 "터키에서만 로그인이 안 되는" 식의 버그가 생긴다.

> [!info] 역사 메모
> Kotlin 1.5에서 `toUpperCase()`/`toLowerCase()`의 이름이 `uppercase()`/`lowercase()`로 바뀌었다. 예전 이름의 함수는 플랫폼 기본 로케일을 사용했기 때문에 위의 터키어 버그를 일으켰다. 새 이름의 함수는 기본적으로 로케일과 무관하게 동작하므로 훨씬 안전하다. Kotlin 2.x에서는 `uppercase()`/`lowercase()`가 표준이다.

### 6.4 부동소수점·NaN과 비교해 본 문자열 동등의 안정성

10장에서 다루는 부동소수점 동등의 함정(`NaN != NaN`, `-0.0 == 0.0`)과 비교하면, 문자열 동등은 훨씬 안정적이다. `String.equals`는 동등성 계약(반사성·대칭성·추이성·일관성)을 모두 만족한다. `hashCode`도 내용에 따라 정해지며 `equals`와 일관된다. 그래서 문자열은 `HashMap`/`HashSet`의 키로 쓰기에 알맞다.

```kotlin
val map = hashMapOf("a" to 1)
println(map["a"])                          // => 1
println(map[buildString { append("a") }])  // => 1   (다른 객체지만 equals/hashCode 같음)
```

`buildString { append("a") }`가 리터럴 `"a"`와 다른 객체라도, `equals`와 `hashCode`가 내용을 기준으로 하므로 맵에서 정확히 조회된다. 이 점은 3.5절에서 본 정규화 함정과 대비된다. `"é"`와 `"é"`는 화면에서는 같아 보여도 코드 유닛이 다르므로 `equals`는 `false`이고 해시도 다르게 나온다. 문자열 동등은 "바이트(코드 유닛) 수준의 동등"이지 "시각적 동등"이 아니다.

## 7. 연결과 StringBuilder: +의 실제 비용

### 7.1 +는 plus 관례이다

`String + Any?`는 19장(연산자 오버로딩과 관례)의 `plus` 관례로 해석된다. `String.plus(other: Any?): String`이 정의되어 있으므로, 오른쪽 피연산자가 무엇이든 그 `toString()` 결과를 붙인 새 문자열을 만든다.

```kotlin
val s = "count: " + 42          // => "count: 42"  (Int의 toString)
val t = "point: " + Point(1,2)  // => "point: Point(x=1, y=2)"  (커스텀 toString)
val u = "x" + null              // => "xnull"  (null도 안전)
```

`String + null`이 `"xnull"`이 되는 것은 `plus`가 널 안전 문자열 변환을 쓰기 때문이다(4.3절의 템플릿과 같은 원리이다). 단, `plus`의 수신 객체(왼쪽)는 `String`이어야 한다. `42 + "x"`는 `Int.plus(String)`을 찾는데, 그런 함수가 없으므로 컴파일 에러가 난다.

```kotlin
// val bad = 42 + "x"   // 컴파일 에러: Int에는 plus(String)이 없음
val ok = "" + 42 + "x"  // => "42x"  왼쪽이 String이면 OK
```

이 점은 어느 쪽이든 문자열이면 연결해 주는 Java의 관대한 `+`와 다르다. Kotlin은 왼쪽이 문자열일 때만 연결한다는 관례 규칙을 엄격하게 따른다.

### 7.2 반복 연결의 함정과 StringBuilder

`String`은 불변이므로 `+`로 연결할 때마다 **새 문자열이 만들어진다.** 짧은 연결에는 문제가 없지만, 반복문 안에서 문자열을 누적하면 반복할 때마다 새 문자열을 할당하고 복사하므로 비용이 $O(n^2)$로 커진다.

```kotlin
// 나쁜 예: O(n^2) — 매 반복마다 전체 문자열 재생성
var result = ""
for (i in 1..1000) {
    result += i        // 매번 새 String 할당 + 복사
}
```

$k$번째 반복에서 길이 $k$인 문자열을 복사하므로 총비용은 $\sum_{k=1}^{n} k = \frac{n(n+1)}{2} = O(n^2)$이다. $n=1000$이면 문자를 약 50만 번 복사한다.

해결책은 `StringBuilder`이다. `StringBuilder`는 **가변** 문자 버퍼이며, `append`는 버퍼를 제자리에서 늘린다(분할 상환 $O(1)$). 그리고 마지막에 `toString()`으로 불변 `String`을 한 번만 만든다.

```kotlin
// 좋은 예: O(n) — 가변 버퍼에 append 후 한 번 toString
val sb = StringBuilder()
for (i in 1..1000) {
    sb.append(i)
}
val result = sb.toString()   // 여기서 한 번만 불변 String 생성
```

`StringBuilder`는 `CharSequence`를 구현하며(2.2절), `append`, `insert`, `deleteAt`, `setCharAt`, `reverse` 같은 가변 연산을 제공한다. 불변 `String`과 가변 `StringBuilder`를 짝지은 것은 38장(컬렉션 읽기 전용과 가변)의 읽기 전용/가변 짝과 같은 설계 방침이다.

### 7.3 buildString: 관용적인 스코프

Kotlin은 `StringBuilder`를 더 관용적으로 쓸 수 있도록 `buildString`이라는 인라인 함수를 제공한다. 이 함수는 수신 객체 지정 람다([[16 - 스코프 함수와 수신 객체 관용구]])로 `StringBuilder`를 구성하고, 자동으로 `toString()` 결과를 돌려준다.

```kotlin
val result = buildString {
    // this: StringBuilder
    append("Point(")
    append(3)
    append(", ")
    append(4)
    append(")")
}
println(result)   // => Point(3, 4)
```

`buildString { ... }`은 `StringBuilder().apply { ... }.toString()`과 사실상 같지만(16장 스코프 함수의 `apply`), 의도를 더 분명하게 드러낸다. 인라인 함수이므로 람다 할당 비용도 없다([[15 - 인라인 함수와 reified]]). 여러 조각을 조립해 문자열을 만들 때 쓰는 표준 관용구이다.

## 8. 표준 라이브러리의 문자열 함수 개관

이 절에서는 앞 절들보다 가볍게, 전체 구성을 파악하는 데 초점을 맞춰 표준 라이브러리의 문자열 함수들을 훑어본다. 핵심은 **이 함수들 대부분이 `String`/`CharSequence`의 확장 함수**(35장 확장 함수와 프로퍼티)라는 점이다. `String` 클래스 자체에 메서드 수백 개가 들어 있는 것이 아니라, 표준 라이브러리가 확장 함수로 만들어 둔 것이다.

### 8.1 부분 문자열과 인덱스

```kotlin
val s = "hello world"
println(s.substring(0, 5))    // => "hello"   (start, endExclusive)
println(s.substring(6))       // => "world"
println(s.take(3))            // => "hel"
println(s.drop(6))            // => "world"
println(s.indexOf("o"))       // => 4
println(s.lastIndexOf("o"))   // => 7
println(s.startsWith("hello"))// => true
println(s.endsWith("world"))  // => true
println("o" in s)             // => true   (contains, in 관례)
```

`substring`은 코드 유닛 인덱스를 기준으로 하므로, 3.3절에서 본 서로게이트 절단 위험이 그대로 남아 있다는 점을 잊지 말자. `in` 연산자는 `contains` 관례(19장 연산자 오버로딩과 관례)를 통해 부분 문자열이나 문자가 포함되어 있는지 검사한다.

### 8.2 분리·결합·치환

```kotlin
val csv = "a,b,c"
println(csv.split(","))              // => [a, b, c]  (List<String>)
println(listOf("a","b","c").joinToString("-")) // => "a-b-c"
println("  trim me  ".trim())        // => "trim me"
println("hello".replace("l", "L"))   // => "heLLo"
println("hello".uppercase())         // => "HELLO"
println("Hello World".split(" ").map { it.first() }.joinToString(""))
// => "HW"
```

`split`은 `List<String>`을 돌려주고, `joinToString`은 컬렉션의 원소를 구분자로 이어 붙인다([[39 - 컬렉션 연산과 함수형 파이프라인]]). 두 함수는 문자열과 컬렉션을 서로 연결해 준다.

### 8.3 문자열을 시퀀스로 다루기

`String`은 `Char`의 시퀀스이므로 39장(컬렉션 연산과 함수형 파이프라인)의 함수형 연산을 그대로 쓸 수 있다.

```kotlin
val s = "hello world"
println(s.count { it == 'o' })       // => 2
println(s.filter { it != ' ' })      // => "helloworld"
println(s.map { it.uppercaseChar() }.joinToString("")) // => "HELLO WORLD"
println(s.groupingBy { it }.eachCount()) // => {h=1, e=1, l=3, o=2, ' '=1, w=1, r=1, d=1}
println(s.reversed())                // => "dlrow olleh"
```

`filter`, `map`, `count`, `groupingBy`는 모두 `CharSequence`/`Iterable<Char>`에 대한 확장 함수이다. `filter`가 다시 `String`을 돌려주는 것은 문자열 전용 오버로드(`CharSequence.filter`)가 있기 때문이다.

주의할 점이 있다. `reversed()`도 **코드 유닛 단위로 뒤집기** 때문에, 서로게이트 쌍이 있으면 쌍의 순서가 뒤바뀌어 문자가 깨진다.

```kotlin
println("a😀b".reversed())   // => "b<깨진>a"  서로게이트 쌍이 뒤집혀 깨짐
// 원래 [a, 하이, 로우, b] → 뒤집으면 [b, 로우, 하이, a] → 로우-하이 순서라 무효
```

이 예도 3절에서 본 "코드 유닛과 코드 포인트"의 함정이 표준 라이브러리 곳곳에 있다는 것을 보여 준다. 코드 유닛 단위로 문자열을 다루는 연산은 모두 보충 평면 문자를 만나면 조심해야 한다.

### 8.4 문자열과 수 사이의 변환

```kotlin
println("42".toInt())          // => 42
println("3.14".toDouble())     // => 3.14
println("42".toIntOrNull())    // => 42
println("abc".toIntOrNull())   // => null   (예외 대신 null)
// println("abc".toInt())      // 예외: NumberFormatException
println(255.toString(16))      // => "ff"   (16진 문자열)
println("ff".toInt(16))        // => 255
```

`toIntOrNull()` 계열은 파싱에 실패하면 예외를 던지는 대신 `null`을 돌려주므로(6장 널 안전성), 실패를 널 안전하게 처리할 수 있다. 이는 [[41 - 예외와 Nothing]]에서 다루는 "예외와 결과 타입" 논의와 이어진다.

## 9. 멀티플랫폼에서의 Char와 String

마지막으로 JVM에 치우친 관점에서 벗어나 멀티플랫폼 관점에서 정리한다. Kotlin은 JVM만을 위한 언어가 아니다([[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]]).

### 9.1 Char와 String의 언어 계약은 타깃과 무관하다

`Char`가 16비트 UTF-16 코드 유닛이고 `String`이 그 코드 유닛의 불변 시퀀스라는 **언어 수준의 계약**은 모든 타깃(JVM, Native, JS, Wasm)에서 같다. `length`가 코드 유닛을 세고, 서로게이트 쌍이 존재하며, 이모지가 2로 세어지는 것도 타깃과 관계없다. Kotlin이 UTF-16을 문자열 모델로 선택한 것은 JVM(과 JS)과의 상호운용을 고려한 실용적인 결정이다.

```text
언어 계약(모든 타깃 동일):
  Char        = UTF-16 코드 유닛 (16비트)
  String      = Char의 불변 시퀀스
  length      = 코드 유닛 개수
  s[i]        = i번째 코드 유닛
  == / equals = 코드 유닛 단위 구조적 동등

물리적 표현(백엔드마다 다름):
  JVM     : java.lang.String (compact strings, byte[])
  JS      : JS String (자바스크립트도 UTF-16이라 자연스러운 매핑)
  Native  : Kotlin/Native 런타임의 String 표현
  Wasm    : Wasm 타깃의 표현
```

### 9.2 JS 타깃과 잘 맞는 이유

흥미롭게도 JavaScript의 문자열도 UTF-16 코드 유닛을 기반으로 한다. JS의 `string.length`도 코드 유닛을 세므로, JS에서도 `"😀".length === 2`이다(자매 시리즈인 JavaScript 시리즈 참조). 그래서 Kotlin의 UTF-16 모델은 JS 타깃과 자연스럽게 맞아떨어지며, 두 언어는 같은 "코드 유닛 함정"을 공유한다.

반면 Rust(`String`이 UTF-8)와 Swift(`Character`가 그래핌 클러스터)는 다른 모델을 선택했다. 언어마다 `length`의 의미가 다르므로, 여러 언어를 오갈 때는 반드시 "이 언어에서 문자열의 단위는 무엇인가"를 확인해야 한다.

### 9.3 코드 포인트 API의 이식성

3.4절에서 본 `codePoints()`, `codePointAt()` 등은 `java.lang.String`/`Character`의 메서드이므로 **JVM 백엔드에서만** 쓸 수 있다. 멀티플랫폼 공통 코드에서 코드 포인트 단위 처리가 필요하다면, 서로게이트를 직접 판별해(공통 소스셋에 있는 `Char.isHighSurrogate()` 등) 3.2절의 공식으로 조립하거나, 표준 라이브러리 공통 API가 이를 지원하는지 문서에서 확인해야 한다.

어떤 함수가 공통이고 어떤 함수가 플랫폼 전용인지는 표준 라이브러리 버전에 따라 바뀔 수 있다(구현과 버전에 따라 다르다). 따라서 멀티플랫폼 라이브러리를 작성할 때는 반드시 확인해야 한다.
