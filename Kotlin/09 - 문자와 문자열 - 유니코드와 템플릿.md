- `\uXXXX` 이스케이프는 "유니코드 문자"를 표현하는가, 아니면 "UTF-16 코드 유닛"을 표현하는가? 이 둘의 차이가 어디서 사고를 내는가?

앞의 두 장 [[07 - 수 1 - Int와 Long과 부동소수점]]과 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]에서 우리는 Kotlin의 수 타입이 "소스 코드에서는 객체지만 JVM 백엔드에서는 원시형으로 내려간다"는 이중성을 파고들었다. `Char`도 정확히 같은 이중성을 산다. 소스에서 `Char`는 `Any`의 하위 타입인 어엿한 클래스이지만, JVM 백엔드에서는 16비트 원시형 `char`로 컴파일된다. 그래서 이 장은 두 장의 자연스러운 연장선이다. `Char`는 "문자"라는 이름을 달고 있지만 그 정체는 **부호 없는 16비트 정수와 아주 가까운 무엇**, 정확히는 UTF-16 코드 유닛 하나이기 때문이다.

이 장이 다루는 것과 다루지 않는 것을 먼저 못박자. 이 장은 `Char`의 정체(UTF-16 코드 유닛), `String`의 불변성과 내부 표현, 유니코드가 만들어내는 함정(코드 포인트 대 코드 유닛, 서로게이트, 이모지 길이), 문자열 템플릿의 컴파일, raw string과 이스케이프, 그리고 문자열의 동등성·비교·연결을 다룬다. 반면 `==`(구조적 동등)와 `===`(참조 동일성)의 일반 이론, 박싱 캐시가 만드는 `===`의 예측 불가(M6, M48)는 [[10 - 불리언과 동등성과 동일성]]이 정본으로 소유한다. `+`가 왜 `plus`라는 관례 함수로 해소되는지, `compareTo`와 `<`의 관계는 [[19 - 연산자 오버로딩과 관례]]가, `CharRange`와 `'a'..'z'` 같은 문자 범위는 [[18 - 범위와 진행과 반복]]가 소유한다. `Array<Char>`·`CharArray`·`List<Char>`가 왜 서로 다른 계약인지(M43)는 [[38 - 컬렉션 - 읽기 전용과 가변]]가 맡는다. 이 장은 그 경계선까지만 걸어가서 필요한 만큼만 링크한다.

이 장의 논증 궤적은 이렇다. 먼저 `Char`가 정수가 아니라 "UTF-16 코드 유닛"이라는 좁고 구체적인 무언가임을 확정하고(1절), `String`이 그 코드 유닛들의 불변 시퀀스임을 보인다(2절). 그다음 유니코드의 실제 구조(코드 포인트, 평면, 서로게이트 쌍)를 파고들어, `length`가 "글자 수"라는 순진한 직관이 왜 이모지 앞에서 무너지는지를 기계 수준에서 해부한다(3절). 이어서 언어가 문자열을 다루기 편하게 만들어주는 장치들 — 템플릿(4절), 이스케이프와 raw string(5절) — 이 컴파일 타임에 무엇으로 변환되는지 보이고, 마지막으로 동등성·비교(6절), 연결과 `StringBuilder`(7절), 표준 라이브러리 지형(8절), 멀티플랫폼에서의 `Char`/`String`(9절)로 확장한다.

## 1. Char — UTF-16 코드 유닛이지 정수가 아니다

### 1.1 Char의 정체: 16비트, 그러나 "문자"가 아니다

Kotlin에서 `Char`는 하나의 문자를 나타내는 타입이라고 흔히 소개된다. 하지만 이 소개는 절반만 맞다. 정확히 말하면 `Char`는 **UTF-16 인코딩의 코드 유닛 하나**, 즉 16비트짜리 값이다. 여기서 "문자"와 "코드 유닛"의 간극이 이 장 전체의 긴장을 만든다. 사람이 "문자 하나"라고 부르는 것(예: 이모지 😀, 한글 조합 '각')이 항상 코드 유닛 하나로 표현되는 것은 아니기 때문이다.

`Char`의 범위는 `'\u0000'`부터 `'\uFFFF'`까지, 즉 부호 없는 16비트 정수의 범위 $[0, 2^{16}-1] = [0, 65535]$와 정확히 일치한다.

```kotlin
val a: Char = 'A'
println(a.code)                 // => 65
println('가'.code)              // => 44032
println('\uFFFF'.code)          // => 65535
println(Char.MIN_VALUE.code)    // => 0
println(Char.MAX_VALUE.code)    // => 65535
```

여기서 `code`는 "이 코드 유닛의 정수 값"을 돌려주는 프로퍼티다. 이것이 곧 "이 문자의 유니코드 값"이라고 말하고 싶은 유혹이 있지만, 정확히는 **UTF-16 코드 유닛의 값**이다. U+FFFF를 넘어가는 유니코드 코드 포인트(예: 😀 = U+1F600)는 단일 `Char`에 담기지 않는다. 이 지점을 3절에서 정면으로 판다.

> **명세 정밀**: JVM 백엔드에서 `Char`는 원시형 `char`(16비트)로 컴파일된다(M4의 사례). 이는 [[07 - 수 1 - Int와 Long과 부동소수점]]에서 `Int`가 `int`로 내려가는 것과 같은 원리다. 다른 타깃(Native, JS, Wasm)에서도 `Char`는 16비트 코드 유닛이라는 **언어 수준의 계약**은 동일하지만, 물리적 표현은 백엔드에 따라 다르다. "16비트 코드 유닛"은 언어 계약이고, "원시형 char로 컴파일"은 JVM 백엔드의 구현이다.

### 1.2 Char와 Int 사이에 암시적 변환은 없다

Java 프로그래머가 Kotlin에서 가장 먼저 부딪히는 벽이 이것이다. Java에서는 `char c = 'A'; int i = c + 1;`이 아무 불평 없이 컴파일되고, `char`가 `int`로 조용히 승격된다. Kotlin은 이 암시적 확대 변환을 **전면 금지**한다. [[07 - 수 1 - Int와 Long과 부동소수점]]에서 본 "암시적 확대 변환 없음" 원칙이 `Char`에도 그대로 적용된다.

```kotlin
val c: Char = 'A'
// val i: Int = c            // 컴파일 에러: type mismatch, Char는 Int가 아니다
val i: Int = c.code          // => 65, 명시적 변환 필요
val back: Char = 65.toChar() // => 'A', Int에서 Char로도 명시적
val back2: Char = Char(65)   // => 'A', Char(code: Int) 생성자도 가능
```

`Char`를 `Int`로 만들려면 `code`를 쓰고, `Int`를 `Char`로 만들려면 `toChar()` 또는 `Char(Int)` 생성자를 쓴다. 이 명시성은 성가셔 보이지만 버그를 원천 차단한다. "문자를 숫자로 쓰고 있다"는 사실이 코드에 항상 드러나기 때문이다.

> **역사 메모**: Kotlin 1.5 이전에는 `Char.toInt()`가 `code`의 역할을 했다. 그러나 `Char.toInt()`는 이름이 오해를 낳았다 — `Int.toLong()`처럼 "타입 변환"으로 보였지만, `Char`에는 애초에 "값으로서의 자연수 표현"이라는 의미가 흐릿했다. 그래서 1.5에서 `Char.code`(코드 유닛 값)와 `Char.digitToInt()`(숫자 문자를 그 숫자로) 등으로 의도를 분리하고, `Char.toInt()`는 사용 중단(deprecated)되었다. Kotlin 2.x 코드에서는 `code`를 쓰는 것이 표준이다. 이는 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]의 부호 없는 정수 도입과 비슷한 "이름으로 의도를 드러내기" 정신이다.

`'7'.code`와 `'7'.digitToInt()`의 차이를 반드시 구분해야 한다.

```kotlin
println('7'.code)          // => 55  (문자 '7'의 UTF-16 코드 유닛 값)
println('7'.digitToInt())  // => 7   (문자 '7'이 나타내는 숫자)
println('A'.digitToInt(16))// => 10  (16진법에서 'A'는 10)
// println('A'.digitToInt()) // 예외: IllegalArgumentException, 'A'는 10진 숫자가 아님
```

`'7'.code == 55`인 이유는 ASCII/유니코드에서 `'0'`이 48이고 `'7'`이 그보다 7 큰 55이기 때문이다. 이 관계 덕분에 `c - '0'`으로 숫자를 뽑는 고전 관용구가 성립한다(다음 절).

### 1.3 Char 산술: 무엇이 Char이고 무엇이 Int인가

여기서 초심자가 자주 혼란스러워하는 대칭이 등장한다. `Char`에 정의된 산술 연산자([[19 - 연산자 오버로딩과 관례]]의 관례 함수)는 다음 세 가지뿐이다.

| 식 | 관례 함수 | 결과 타입 | 의미 |
|----|-----------|-----------|------|
| `Char + Int` | `Char.plus(Int)` | `Char` | 코드 유닛을 n만큼 이동한 문자 |
| `Char - Int` | `Char.minus(Int)` | `Char` | 코드 유닛을 n만큼 뒤로 이동한 문자 |
| `Char - Char` | `Char.minus(Char)` | `Int` | 두 문자의 코드 유닛 거리 |

그리고 **`Char + Char`는 존재하지 않는다.** 이것이 처음엔 이상해 보이지만 의미론적으로 완벽하게 옳다.

```kotlin
val next: Char = 'A' + 1      // => 'B'   (Char + Int → Char)
val prev: Char = 'C' - 1      // => 'B'   (Char - Int → Char)
val dist: Int  = 'C' - 'A'    // => 2     (Char - Char → Int)
// val bad = 'A' + 'B'        // 컴파일 에러: 'A' + 'B'는 정의되지 않음
```

왜 `Char + Char`가 없는가? "문자 + 문자"에는 자연스러운 의미가 없기 때문이다. `'A' + 'B'`가 도대체 무엇을 뜻해야 하는가? 두 코드 값을 더한 문자(`'A'.code + 'B'.code = 65 + 66 = 131` → `''`)? 그건 무의미한 연산이다. 반면 `Char - Char`는 "두 문자가 코드 유닛 상에서 얼마나 떨어져 있는가"라는 명확한 의미(거리, `Int`)를 갖는다. 이 설계는 물리학의 차원 분석과 같다 — 위치(문자) − 위치(문자) = 변위(정수)는 말이 되지만, 위치 + 위치는 말이 안 된다. Kotlin은 "말이 되는 연산만" 타입으로 허용한다.

이 규칙에서 유명한 관용구가 나온다.

```kotlin
// 숫자 문자를 실제 숫자로 (digitToInt와 동치, 단 검증 없음)
val n: Int = '7' - '0'        // => 7  (Char - Char → Int)

// 알파벳 인덱스
val idx: Int = 'e' - 'a'      // => 4

// 시저 암호(Caesar cipher): 3글자 밀기
fun shift(c: Char): Char = 'a' + (c - 'a' + 3) % 26
println(shift('x'))           // => 'a'  ('x'는 24번째, +3=27, %26=1 → 'b'? 확인)
// 'x' - 'a' = 23, +3 = 26, %26 = 0 → 'a' + 0 = 'a'
```

주석의 계산을 따라가 보면 `'x' - 'a' = 23`(a가 0이므로 x는 23번째, 0-indexed), `23 + 3 = 26`, `26 % 26 = 0`, `'a' + 0 = 'a'`. 즉 `x`를 3칸 밀면 알파벳을 한 바퀴 돌아 `a`가 된다. `Char - Char`가 `Int`를, `Char + Int`가 `Char`를 돌려주기에 이 한 줄이 타입 검사를 통과하며 정확히 동작한다.

> **흔한 오해**: "`Char`는 정수니까 `'A' + 'B'`도 되겠지"라고 생각하기 쉽다. 아니다. Kotlin은 `Char`를 "정수처럼 쓸 수 있는 것"이 아니라 "코드 유닛 위의 좌표"로 모델링한다. 좌표 + 좌표는 금지, 좌표 ± 변위는 좌표, 좌표 − 좌표는 변위. 이 세 규칙이 전부다.

### 1.4 문자 분류와 대소문자

`Char`에는 유니코드 속성에 근거한 분류 함수들이 확장 함수([[35 - 확장 함수와 프로퍼티]])로 잔뜩 붙어 있다. 이들은 단순히 ASCII를 보는 게 아니라 유니코드 카테고리를 참조한다(구현/백엔드에 따라 유니코드 데이터베이스 버전이 다를 수 있다).

```kotlin
println('가'.isLetter())    // => true  (한글도 문자)
println('5'.isDigit())      // => true
println(' '.isWhitespace()) // => true
println('가'.isLetterOrDigit()) // => true
println('A'.isUpperCase())  // => true
println('a'.uppercaseChar())// => 'A'
println('İ'.uppercase())    // => "İ" (String을 반환할 수 있음, 아래 주의)
```

여기 미묘한 함정이 있다. `Char.uppercaseChar()`는 `Char`를 돌려주지만, `Char.uppercase()`는 `String`을 돌려준다. 왜? 어떤 문자는 대문자로 바꿀 때 코드 유닛 하나로 표현할 수 없기 때문이다. 예컨대 독일어 'ß'(에스체트)의 대문자는 "SS"(두 글자)다.

```kotlin
println('ß'.uppercase())     // => "SS"  (String, 두 글자!)
println('ß'.uppercaseChar()) // => 'ß'   (Char로는 표현 못 해서 그대로)
```

`uppercaseChar()`는 "1:1 매핑이 안 되면 원본을 유지"하는 손실 있는 연산이고, `uppercase()`는 "정확한 유니코드 대문자화"라서 `String`을 돌려준다. 로케일에 의존하는 대소문자 변환(터키어 'i'/'İ' 문제)은 6.3에서 다시 본다.

## 2. String — 불변 UTF-16 시퀀스

### 2.1 불변성이 뜻하는 것과 보장하는 것

`String`은 **불변(immutable)** 이다. 한 번 만들어진 문자열의 내용은 절대 바뀌지 않는다. 문자열을 "수정"하는 모든 연산은 사실 **새 문자열을 만들어 돌려준다**.

```kotlin
val s = "hello"
val t = s.uppercase()   // 새 String "HELLO"를 만든다
println(s)              // => hello  (원본 그대로)
println(t)              // => HELLO
val r = s.replace('l', 'L') // 또 새 String
println(s)              // => hello  (여전히 그대로)
```

이 불변성은 `val`/`var`와는 다른 층위의 이야기임을 분명히 하자. `val s`는 "`s`라는 이름에 재대입할 수 없다"는 뜻일 뿐이고(M3, [[11 - 변수와 초기화 - val과 const와 lateinit]]가 소유), `String`의 불변성은 "그 문자열 객체 자체의 내용이 불변"이라는 뜻이다. 이 둘은 직교한다.

```kotlin
var s = "a"     // var: 재대입 가능
s = s + "b"     // OK: s에 새 String을 재대입, "b"를 원본에 덧붙인 게 아님
println(s)      // => ab
// 여기서 원래의 "a" 객체는 여전히 불변이었고, s가 새 "ab"를 가리키게 됐을 뿐
```

불변성이 사주는 이득은 크다. 문자열을 마음 놓고 공유해도 아무도 몰래 바꾸지 못하고(스레드 안전), 해시 값을 캐싱할 수 있으며([[10 - 불리언과 동등성과 동일성]]의 `hashCode`), 방어적 복사가 필요 없다. Kotlin은 "문자열을 바꾸고 싶다"는 요구를 `StringBuilder`(7절)라는 별도의 가변 타입으로 분리했다. 불변 `String`과 가변 `StringBuilder`의 이 분리는 [[38 - 컬렉션 - 읽기 전용과 가변]]의 `List`/`MutableList` 분리와 정확히 같은 설계 철학이다.

### 2.2 String은 Char의 시퀀스: CharSequence 계층

`String`은 `Char`들을 순서대로 담은 시퀀스다. 인덱스로 접근할 수 있고, 순회할 수 있으며, 길이를 갖는다.

```kotlin
val s = "abc"
println(s[0])          // => 'a'   (get 관례, Char 반환)
println(s.length)      // => 3
for (c in s) print("$c ") // => a b c
println(s.first())     // => 'a'
println(s.last())      // => 'c'
```

`s[0]`은 [[19 - 연산자 오버로딩과 관례]]의 `get` 관례로 `s.get(0)`을 부르고, 결과는 `Char`다. `for (c in s)`는 `String`이 `Iterable<Char>`처럼 순회 가능하기에 각 `Char`를 준다(엄밀히는 `iterator()` 관례, [[18 - 범위와 진행과 반복]]).

`String`은 `CharSequence` 인터페이스를 구현한다. `CharSequence`는 "문자들의 읽기 가능한 시퀀스"를 추상화한 인터페이스로, `length`, `get(index)`, `subSequence(start, end)` 세 멤버만 요구한다.

```text
        CharSequence  (인터페이스: length, get, subSequence)
        /          \
    String       StringBuilder   (그리고 java.lang.StringBuffer 등)
   (불변)         (가변)
```

이 추상화 덕분에 많은 표준 라이브러리 함수가 `String`이 아니라 `CharSequence`를 받도록 선언된다. 그러면 `String`이든 `StringBuilder`든 똑같이 쓸 수 있다.

```kotlin
fun countVowels(cs: CharSequence): Int =
    cs.count { it in "aeiou" }

println(countVowels("hello"))              // => 2   (String)
println(countVowels(StringBuilder("wxy"))) // => 0   (StringBuilder)
```

> **명세 정밀**: `String.length`는 프로퍼티지만 `CharSequence.length`도 프로퍼티다(둘 다 접근자, [[22 - 프로퍼티와 백킹 필드]]). Java의 `String.length()`는 메서드지만, Kotlin에서 Java의 `length()`는 프로퍼티 `length`로 매핑되어 노출된다([[45 - Java 상호운용]]의 getter↔프로퍼티 규칙). 그래서 Kotlin 코드에서는 `s.length`(괄호 없음)로 쓴다.

### 2.3 length는 코드 유닛의 개수다 (글자 수가 아니다)

`String.length`가 세는 것은 **UTF-16 코드 유닛의 개수**다. "사람이 보는 글자 수"도 아니고 "유니코드 코드 포인트의 개수"도 아니다. BMP(기본 다국어 평면) 안의 문자들만 쓸 때는 셋이 우연히 일치하기 때문에 이 구분이 안 보인다.

```kotlin
println("abc".length)   // => 3   (코드 유닛 3, 코드 포인트 3, 글자 3 — 모두 같음)
println("한글".length)   // => 2   (한글도 각각 BMP 안, 코드 유닛 = 코드 포인트 = 글자)
```

하지만 BMP를 벗어나는 순간 셋이 갈라진다. 그 파열의 지점이 3절의 본론이다. 지금은 사실만 확정하자: `length`는 코드 유닛을 센다. 인덱스 `s[i]`도 코드 유닛 단위로 접근한다. 서로게이트 쌍의 절반을 가리킬 수 있고, 그러면 반쪽짜리 `Char`가 나온다.

### 2.4 JVM에서의 String 표현과 인턴

JVM 백엔드에서 Kotlin의 `String`은 `java.lang.String`과 **동일한 타입**이다([[45 - Java 상호운용]]). 별도의 래핑이 없다. 그래서 Java의 문자열 상수 풀(string constant pool)과 인턴(interning) 메커니즘이 그대로 적용된다.

소스 코드에 등장한 문자열 리터럴은 JVM에서 상수 풀에 인턴되어, 같은 리터럴은 같은 객체를 가리킨다.

```kotlin
val a = "hello"
val b = "hello"
println(a == b)    // => true   (구조적 동등: 내용이 같다)
println(a === b)   // => true   (참조 동일: JVM에서 리터럴이 인턴되어 같은 객체)

val c = StringBuilder("hel").append("lo").toString()
println(a == c)    // => true   (내용 같음)
println(a === c)   // => false  (런타임에 만든 새 객체, 다른 참조)
```

여기서 결정적 교훈: **Kotlin에서 문자열 비교는 언제나 `==`(구조적, `equals`)를 쓴다.** `===`(참조 동일성)로 문자열을 비교하는 것은 거의 항상 버그다. `a === c`가 `false`인 데서 보듯, "내용이 같지만 다른 객체"인 문자열은 얼마든지 만들어진다. 이 함정은 Java에서 `==`(Java의 `==`는 참조 비교)가 리터럴에 대해서는 우연히 `true`를 주지만 런타임 문자열에는 `false`를 주는 그 악명 높은 버그와 같다.

Kotlin은 이 함정을 언어 차원에서 대부분 해소한다. Kotlin의 `==`는 `equals`를 부르므로(M6, [[10 - 불리언과 동등성과 동일성]]가 소유) 항상 내용을 비교한다. Java에서 넘어온 사람은 "Kotlin `==`는 Java `==`가 아니라 Java `.equals()`"라는 것을 몸에 새겨야 한다. 이 주제는 6절에서 더 판다.

> **성능 주의**: JDK 9+의 "compact strings" 최적화로, `java.lang.String`은 내부적으로 문자열이 전부 Latin-1(코드 유닛 0~255) 범위면 `byte[]`(1바이트/문자)로, 아니면 `byte[]`+UTF-16 coder로 저장한다(구현 세부, JDK 버전에 따라 다름). 그러나 이는 순전히 내부 저장 최적화이며, `length`·`get`·순회의 **UTF-16 코드 유닛 의미론은 전혀 바뀌지 않는다**. Kotlin 소스에서는 항상 "코드 유닛의 시퀀스"라는 논리적 모델만 보면 된다. 물리적 저장은 [[46 - 멀티플랫폼과 진화와 어두운 구석]]의 관심사다.

## 3. 유니코드 — 코드 포인트 대 코드 유닛, 그리고 이모지 함정

이 절이 이 장의 심장이다. 앞에서 계속 "코드 유닛"과 "글자"를 구분해 왔는데, 이제 그 구분이 왜 반드시 필요한지, 어디서 사람들이 넘어지는지를 기계 수준에서 해부한다.

### 3.1 유니코드의 세 층위: 코드 포인트, 인코딩, 그래핌

문자열을 정확히 이해하려면 세 개의 층을 분리해야 한다.

```text
[ 사람이 보는 글자 ]   그래핌 클러스터(grapheme cluster)   예: 각, 👨‍👩‍👧, é
        ↑ (렌더링/결합 규칙)
[ 유니코드의 추상 문자 ]  코드 포인트(code point)           예: U+AC01, U+1F600, U+0065 U+0301
        ↑ (인코딩)
[ 저장되는 실제 바이트 ]  코드 유닛(code unit)              UTF-16: 16비트 단위, UTF-8: 8비트 단위
```

- **코드 포인트(code point)**: 유니코드가 각 추상 문자에 부여한 번호. U+0000부터 U+10FFFF까지, 총 $17 \times 2^{16} = 1{,}114{,}112$개의 자리. `U+` 뒤의 16진수가 코드 포인트다.
- **코드 유닛(code unit)**: 특정 인코딩에서 하나의 저장 단위. UTF-16은 16비트, UTF-8은 8비트, UTF-32는 32비트가 코드 유닛이다.
- **그래핌 클러스터**: 사람이 "한 글자"로 인식하는 단위. 여러 코드 포인트가 결합해 하나로 보일 수 있다(결합 문자, 이모지 ZWJ 시퀀스 등).

Kotlin의 `Char`는 **UTF-16 코드 유닛**이고, `String.length`는 **코드 유닛의 개수**다. 코드 포인트도 그래핌도 아니다. 이 사실이 3절의 나머지를 지배한다.

### 3.2 UTF-16과 서로게이트 쌍

유니코드 코드 포인트는 U+10FFFF까지 가는데, 16비트 코드 유닛 하나는 U+FFFF까지밖에 표현하지 못한다($2^{16}=65536$). 그렇다면 U+10000 이상(보충 평면, supplementary planes)의 문자는 UTF-16에서 어떻게 표현하는가? **서로게이트 쌍(surrogate pair)**, 즉 두 개의 16비트 코드 유닛으로 표현한다.

유니코드는 이를 위해 BMP 안에 특별한 구멍을 뚫어 두었다. U+D800~U+DBFF(하이 서로게이트 1024개)와 U+DC00~U+DFFF(로우 서로게이트 1024개)는 **그 자체로는 문자가 아니고**, 오직 쌍을 이루어 보충 평면의 코드 포인트를 인코딩하는 데만 쓰인다. $1024 \times 1024 = 2^{20} = 1{,}048{,}576$개, 이것이 U+10000~U+10FFFF 범위와 정확히 일치한다.

코드 포인트 $C$ ($C \geq \text{0x10000}$)를 서로게이트 쌍 (high, low)로 인코딩하는 공식:

$$C' = C - \text{0x10000}, \quad \text{high} = \text{0xD800} + \lfloor C'/\text{0x400}\rfloor, \quad \text{low} = \text{0xDC00} + (C' \bmod \text{0x400})$$

역변환(디코딩):

$$C = \text{0x10000} + (\text{high} - \text{0xD800}) \times \text{0x400} + (\text{low} - \text{0xDC00})$$

예를 들어 😀 = U+1F600을 보자.

```kotlin
val emoji = "😀"
println(emoji.length)             // => 2   (코드 유닛 2개!)
println(emoji[0].code.toString(16)) // => d83d  (하이 서로게이트 U+D83D)
println(emoji[1].code.toString(16)) // => de00  (로우 서로게이트 U+DE00)

// 서로게이트 쌍에서 코드 포인트 복원
val high = emoji[0].code   // 0xD83D = 55357
val low  = emoji[1].code   // 0xDE00 = 56832
val cp = 0x10000 + (high - 0xD800) * 0x400 + (low - 0xDC00)
println(cp.toString(16))          // => 1f600  (U+1F600, 복원 성공!)
```

계산을 검증하자. `high - 0xD800 = 0xD83D - 0xD800 = 0x3D = 61`. `low - 0xDC00 = 0xDE00 - 0xDC00 = 0x200 = 512`. `0x10000 + 61 * 0x400 + 512 = 65536 + 61*1024 + 512 = 65536 + 62464 + 512 = 128512 = 0x1F600`. 정확히 😀의 코드 포인트다.

`Char`에는 서로게이트를 판별하는 함수들이 표준 라이브러리에 (공통 소스셋에도) 있다.

```kotlin
val emoji = "😀"
println(emoji[0].isHighSurrogate()) // => true
println(emoji[1].isLowSurrogate())  // => true
println(emoji[0].isSurrogate())     // => true
println('A'.isSurrogate())          // => false
```

### 3.3 이모지 길이 함정: length는 왜 배신하는가

이제 저 유명한 함정을 정면으로 본다. "이모지 하나짜리 문자열의 length가 왜 2인가?"

```kotlin
println("😀".length)         // => 2   (서로게이트 쌍이라 코드 유닛 2개)
println("a😀b".length)       // => 4   (a=1, 😀=2, b=1)
println("😀"[0])             // => '?'  (반쪽 서로게이트, 온전한 문자가 아님)
```

`"😀".length == 2`인 이유를 이제 우리는 안다. `length`는 코드 유닛을 세고, 😀는 서로게이트 쌍이라 코드 유닛이 2개다. 더 나쁜 것은 `"😀"[0]`이 하이 서로게이트 단독을 돌려준다는 점이다. 이건 그 자체로는 유효한 문자가 아니라 반쪽짜리 코드 유닛이다. 출력하면 대개 `?`나 깨진 글자로 보인다.

이 함정은 실무에서 문자열을 자를 때 참사를 낸다.

```kotlin
val s = "a😀b"
println(s.substring(0, 2))   // => "a?"  서로게이트 쌍을 반으로 갈랐다!
// s.substring(0, 2)는 코드 유닛 0,1을 취함: 'a' + 하이 서로게이트 반쪽
```

`substring`, 인덱스 슬라이싱, `take`/`drop`, 반복문에서 `s[i]` 등 **모든 코드 유닛 기반 연산은 서로게이트 쌍을 쪼갤 위험**을 안고 있다. "n글자만 미리보기로 자르기" 같은 순진한 코드가 이모지 앞에서 깨진 문자를 만든다.

> **흔한 오해**: "이모지는 특수한 예외라 내 앱엔 안 나온다"는 방심이 사고를 부른다. 이모지뿐 아니라 CJK 확장 한자(𩸽 같은 희귀 한자), 고대 문자, 수학 기호($\mathbb{Z}$의 볼드 유니코드 등) 모두 보충 평면에 있고 서로게이트 쌍이다. 사용자 이름·닉네임·메모 등 자유 입력을 받는 곳이면 반드시 나온다.

### 3.4 코드 포인트 단위로 다루기

그러면 "진짜 유니코드 문자(코드 포인트)" 단위로 세거나 순회하려면 어떻게 하는가? JVM 백엔드에서는 `java.lang.String`/`Character`의 코드 포인트 API를 쓸 수 있다.

```kotlin
// JVM 백엔드 한정: java.lang.Character / String의 코드 포인트 API
val s = "a😀b"
println(s.length)                          // => 4   (코드 유닛)
println(s.codePointCount(0, s.length))     // => 3   (코드 포인트: a, 😀, b)
s.codePoints().forEach {
    println("U+${it.toString(16).uppercase()}")
}
// => U+61   (a)
// => U+1F600 (😀)
// => U+62   (b)
```

`codePointCount`, `codePoints()`, `codePointAt(index)`는 `java.lang.String`의 메서드로, JVM에서 그대로 호출된다. 이들은 서로게이트 쌍을 하나의 코드 포인트로 묶어 센다. 코드 포인트로부터 문자열을 만들 때는 `Character.toChars(codePoint)` 또는 문자열 빌더를 쓴다.

```kotlin
// JVM 백엔드: 코드 포인트에서 String 만들기
val emoji = String(Character.toChars(0x1F600))
println(emoji)      // => 😀
println(emoji.length) // => 2  (여전히 UTF-16 코드 유닛으로는 2)
```

공통(common) 소스셋에서는 `codePoints()` 같은 함수가 없을 수 있으므로, 멀티플랫폼 코드라면 서로게이트를 직접 판별해 3.2의 공식으로 코드 포인트를 조립하거나(수동), 코드 포인트 순회 유틸리티를 직접 구현해야 한다. "코드 포인트 API는 어디까지 공통인가"는 백엔드/표준 라이브러리 버전에 따라 다르므로, 멀티플랫폼 라이브러리를 만든다면 실제 표준 라이브러리 문서에서 확인해야 한다.

### 3.5 그래핌 클러스터: 코드 포인트조차 "글자"가 아니다

코드 포인트 단위로 세면 이제 "글자 수"가 맞을까? 여전히 아니다. 사람이 보는 "한 글자"는 여러 코드 포인트가 결합한 **그래핌 클러스터**일 수 있다.

```kotlin
// 결합 문자: 'e' + 결합 악센트(U+0301)
val precomposed = "é"        // é (완성형 코드 포인트 U+00E9)
val decomposed  = "é"       // e + ́ (결합 악센트)
println(precomposed.length)       // => 1   (코드 유닛 1)
println(decomposed.length)        // => 2   (코드 유닛 2: e + 결합문자)
println(precomposed == decomposed)// => false  (코드 유닛이 다르므로!)
// 화면에는 둘 다 "é"로 똑같이 보이지만 다른 문자열이다
```

이건 6절의 동등성 함정과도 이어진다. 화면상 똑같이 보이는 두 "é"가 `==`로는 다르다. 유니코드 정규화(NFC/NFD)를 거쳐야 비교가 안정적인데, 이는 표준 라이브러리 공통 API 밖(JVM에서는 `java.text.Normalizer`)의 영역이라 이 장에서는 개념만 짚는다.

더 극단적인 예는 이모지 ZWJ(Zero Width Joiner) 시퀀스다. "가족" 이모지 👨‍👩‍👧는 사람에게는 한 글자지만, 코드 포인트로는 여러 개(남자 + ZWJ + 여자 + ZWJ + 소녀), 코드 유닛으로는 그보다 더 많다.

```kotlin
val family = "👨‍👩‍👧"
println(family.length)        // => 8  (구현/이모지 버전에 따라, 코드 유닛 여러 개)
// 사람에겐 1글자, 코드 포인트론 5개(3인물 + ZWJ 2개), 코드 유닛으론 8개
```

정리하면 "한 글자를 세는" 정확한 단위는 그래핌 클러스터인데, 이건 유니코드 텍스트 세분화(UAX #29) 규칙을 따르는 복잡한 알고리즘이 필요하고 Kotlin 표준 라이브러리 공통 API에는 없다. `String.length`가 셋 중 가장 낮은 층위인 코드 유닛을 센다는 사실만 뼈에 새기면, "왜 이모지가 2로 세지는지", "왜 substring이 깨지는지"가 전부 설명된다.

```text
"👨‍👩‍👧" 를 세는 단위별 개수
┌──────────────────┬──────┬────────────────────────────────┐
│ 단위             │ 개수 │ Kotlin API                     │
├──────────────────┼──────┼────────────────────────────────┤
│ 그래핌(사람 글자)│  1   │ (표준 라이브러리 공통엔 없음)  │
│ 코드 포인트      │  5   │ codePointCount (JVM)           │
│ 코드 유닛(Char)  │  8   │ length                         │
└──────────────────┴──────┴────────────────────────────────┘
```

## 4. 문자열 템플릿 — $x와 ${expr}, 그리고 그 컴파일

### 4.1 문법: $identifier와 ${expression}

Kotlin의 문자열 템플릿은 문자열 안에 값을 끼워 넣는 언어 기능이다. 두 형태가 있다.

```kotlin
val name = "Toby"
val age = 7
println("$name is $age years old")       // => Toby is 7 years old
println("${name.uppercase()} scored ${age * 10}") // => TOBY scored 70
println("next year: ${age + 1}")         // => next year: 8
```

- `$identifier`: 단순 식별자(변수 이름) 하나를 끼워 넣는다. `$name`.
- `${expression}`: 임의의 표현식을 중괄호로 감싸 끼워 넣는다. `${age + 1}`, `${list.size}`.

여기 자주 걸리는 함정이 있다. `$` 뒤에는 **식별자 하나만** 읽힌다. 프로퍼티 접근이나 함수 호출을 하려면 반드시 `${}`를 써야 한다.

```kotlin
data class Point(val x: Int, val y: Int)
val p = Point(3, 4)

println("$p.x")     // => Point(x=3, y=4).x   ← 함정! $p만 해석되고 .x는 리터럴
println("${p.x}")   // => 3                    ← 올바름
```

`"$p.x"`에서 `$p`는 `p`(전체 객체)를 문자열로 바꾸고, 그 뒤의 `.x`는 그냥 리터럴 텍스트다. `p.x`(프로퍼티 값)를 원하면 `"${p.x}"`라고 써야 한다. 이건 초심자가 거의 반드시 한 번은 밟는 지뢰다.

### 4.2 템플릿은 무엇으로 컴파일되는가

문자열 템플릿은 마법이 아니다. 컴파일러가 이를 **문자열 연결(concatenation)** 로 desugar한다. JVM 백엔드에서 전통적으로는 `StringBuilder`를 사용한 코드로 변환된다(개념적 의사코드).

```kotlin
val s = "$name is $age years old"
```

는 대략 다음과 동등한 코드로 컴파일된다(JVM 백엔드, 개념적):

```java
// 개념적 desugar (JVM 백엔드, 전통적 형태)
String s = new StringBuilder()
    .append("")
    .append(name)
    .append(" is ")
    .append(age)
    .append(" years old")
    .toString();
```

각 `append`는 리터럴 조각과 삽입된 값을 번갈아 붙인다. 삽입된 값이 `String`이 아니면 `toString()`을 통해 문자열로 변환된다(다음 절). 순수한 리터럴 문자열(템플릿 없음)은 상수 풀에 그대로 들어가므로 이런 변환이 없다.

> **성능 주의**: JVM 9+에서는 `-Xstring-concat=indy` 또는 `indy-with-constants` 컴파일러 옵션으로, 템플릿을 `StringBuilder` 대신 `invokedynamic`(`java.lang.invoke.StringConcatFactory`) 기반 문자열 연결로 컴파일할 수 있다. 이는 런타임이 최적의 연결 전략을 고르게 해 더 빠를 수 있다. 어느 전략이 쓰이는지는 컴파일러 버전·옵션·타깃 JVM에 따라 다르므로(구현 세부), "템플릿은 문자열 연결로 바뀐다"는 개념만 확정하고 물리적 형태는 백엔드에 맡긴다. 핵심은 **템플릿이 런타임 문자열 파싱이 아니라 컴파일 타임에 결정된 연결 코드**라는 것이다.

단일 삽입만 있는 템플릿 `"$x"`(주변 리터럴 없음)는 개념적으로 `x`의 문자열 변환 하나로 컴파일된다. 즉 `String.valueOf(x)`에 해당하는 널 안전 변환이 일어난다.

### 4.3 null과 toString

템플릿에 삽입되는 값은 `toString()`으로 문자열이 된다. 그런데 값이 `null`이면? `null.toString()`을 부르면 NPE가 날 것 같지만, 템플릿은 널 안전하게 처리해 `"null"` 문자열을 넣는다.

```kotlin
val x: String? = null
println("value: $x")       // => value: null   (NPE 아님!)
println("value: ${x}")     // => value: null
```

이는 컴파일러가 `String.valueOf`에 해당하는 널 안전 변환을 쓰기 때문이다(널이면 리터럴 `"null"`). 그래서 로그 문자열에서 nullable 값을 안심하고 끼워 넣을 수 있다. [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 본 널 안전 철학이 여기에도 배어 있다.

커스텀 `toString()`을 정의하면 템플릿에 그 결과가 나온다([[27 - 데이터 클래스]]의 자동 `toString`도 마찬가지).

```kotlin
class Money(val cents: Int) {
    override fun toString() = "$%.2f".format(cents / 100.0)
}
println("price: ${Money(1250)}")  // => price: $12.50
```

### 4.4 템플릿 안의 $와 이스케이프

문자 그대로의 `$`를 문자열에 넣으려면 이스케이프해야 한다. 일반 문자열에서는 `\$`, raw string에서는 `${'$'}` 관용구를 쓴다(raw string은 백슬래시 이스케이프를 해석하지 않으므로, 5절).

```kotlin
val price = 5
println("cost: \$$price")           // => cost: $5   (\$는 리터럴 $, $price는 삽입)
println("""cost: ${'$'}$price""")   // => cost: $5   (raw string에서 리터럴 $)
```

`${'$'}`는 "문자 `'$'`를 표현식으로 삽입"하는 것으로, raw string에서 리터럴 `$`를 넣는 표준 관용구다. `$` 뒤에 식별자나 `{`가 오지 않으면 그냥 리터럴 `$`로 취급되기도 하지만(예: `"5$ each"`에서 `$` 뒤가 공백), 명확성을 위해 이스케이프를 쓰는 게 안전하다.

## 5. 이스케이프와 raw string

### 5.1 이스케이프 시퀀스

일반 문자열 리터럴(`"..."`)과 문자 리터럴(`'...'`)은 백슬래시 이스케이프를 해석한다. Kotlin이 지원하는 이스케이프 시퀀스는 제한적이고 명확하다.

| 이스케이프 | 의미 | 코드 유닛 |
|-----------|------|-----------|
| `\t` | 탭 | U+0009 |
| `\n` | 줄바꿈(LF) | U+000A |
| `\r` | 캐리지 리턴(CR) | U+000D |
| `\b` | 백스페이스 | U+0008 |
| `\'` | 작은따옴표 | U+0027 |
| `\"` | 큰따옴표 | U+0022 |
| `\\` | 백슬래시 | U+005C |
| `\$` | 달러 기호 | U+0024 |
| `\uXXXX` | UTF-16 코드 유닛 | (16진 4자리) |

```kotlin
val tab = "col1\tcol2"
val quote = "She said \"hi\""
val path = "C:\\Users\\toby"
val nl = "line1\nline2"
println('A')     // => A
```

Kotlin에는 Java나 C에 있는 **8진 이스케이프(`\0`, `\012`)가 없다.** 널 문자는 `'\u0000'`으로 써야 한다. 또 위 표에 없는 이스케이프(예: `\d`, `\x41`)는 컴파일 에러다. "지원하는 것만 명시적으로 지원"하는 Kotlin의 엄격함이다.

```kotlin
// val bad = "\x41"   // 컴파일 에러: illegal escape
val nul = "\u0000"    // 널 문자는 유니코드 이스케이프로
```

### 5.2 \uXXXX는 코드 유닛이지 코드 포인트가 아니다

이 절의 핵심 오해 교정. `\uXXXX`는 정확히 **하나의 UTF-16 코드 유닛**(16비트, 16진 4자리)을 나타낸다. "유니코드 문자"가 아니다. 그래서 BMP 밖의 문자(😀 = U+1F600)를 단일 `\u`로는 쓸 수 없다. 서로게이트 쌍 두 개를 써야 한다.

```kotlin
val a = "\u0041"       // => "A"   (U+0041, BMP)
val ga = "\uAC01"          // => "각"  (U+AC01, BMP)
// val emoji = "\u1F600"   // 이건 "ὠ" + "0" 으로 파싱됨! (4자리만 읽음)
val emoji = "\uD83D\uDE00" // => "😀"  서로게이트 쌍으로 U+1F600 표현
println(emoji)             // => 😀
println(emoji.length)      // => 2
```

`"\u1F600"`이 왜 위험한가? `\u`는 **정확히 4개의 16진 숫자**만 읽는다. 그래서 `"\u1F600"`은 `"ὠ"`(U+1F60 = 'ὠ' 그리스 문자) 뒤에 리터럴 `'0'`이 붙은 것으로 해석된다. 의도한 😀와 전혀 다르다. 보충 평면 문자를 리터럴로 쓰려면 서로게이트 쌍 `"\uD83D\uDE00"`을 쓰거나(코드 유닛 2개), 그냥 소스 파일에 직접 이모지 문자를 붙여넣는 편이 안전하다(소스는 대개 UTF-8).

> **명세 정밀**: `\u`가 코드 유닛(4 hex)이라는 것은 Java와 동일한 계약이다. Kotlin `Char` = UTF-16 코드 유닛이라는 1절의 정의와 정확히 맞물린다. `Char` 하나가 코드 유닛 하나고, `\uXXXX`가 코드 유닛 하나를 표현하니 `'\uXXXX'`(문자 리터럴)에는 딱 하나만 들어간다. `'😀'`는 코드 유닛 2개라 문자 리터럴로 쓸 수 없다 — 컴파일 에러다.

```kotlin
// val c: Char = '😀'   // 컴파일 에러: too many characters in a character literal
val c: Char = 'A'        // OK, 코드 유닛 하나
```

### 5.3 raw string: """..."""

raw string(원시 문자열, 삼중 따옴표 `"""..."""`)은 **백슬래시 이스케이프를 해석하지 않고**, 줄바꿈을 포함한 여러 줄을 그대로 담는다. 정규식, 파일 경로, JSON/SQL 스니펫, 여러 줄 텍스트에 이상적이다.

```kotlin
val regex = """\d+\.\d+"""      // 백슬래시가 그대로 (이스케이프 안 함)
println(regex)                  // => \d+\.\d+

val path = """C:\Users\toby"""  // 백슬래시 이스케이프 지옥 탈출
println(path)                   // => C:\Users\toby

val json = """
    {
        "name": "Toby",
        "age": 7
    }
"""
```

raw string에서는 `\n`이 "백슬래시 n" 두 글자 그대로다. 실제 줄바꿈을 넣으려면 소스에서 그냥 줄을 바꾸면 된다. 큰따옴표도 이스케이프 없이 넣을 수 있다(단, 연속 세 개 이상은 주의). 유일한 예외는 앞서 본 `$` — raw string에서도 템플릿은 살아 있으므로 리터럴 `$`는 `${'$'}`로 넣는다.

### 5.4 trimIndent와 trimMargin: 무엇을 자르는가

raw string을 코드 안에 들여쓰기와 함께 쓰면, 그 들여쓰기 공백이 문자열에 포함된다. 이걸 정리하는 두 함수가 `trimIndent()`와 `trimMargin()`이다. 둘의 동작 차이를 정확히 알아야 한다.

**`trimIndent()`**: 모든 줄에서 **공통된 최소 들여쓰기**를 찾아 그만큼을 각 줄에서 제거한다. 또 첫 줄과 마지막 줄이 공백뿐이면 제거한다(즉 앞뒤 빈 줄 정리).

```kotlin
val text = """
    Hello
      World
    End
""".trimIndent()
println(text)
// => Hello
//   World
// End
```

여기서 세 줄 `Hello`, `World`, `End`의 공통 최소 들여쓰기는 4칸(`Hello`, `End`)이다(`World`는 6칸이지만 최소는 4). 그래서 각 줄에서 4칸을 제거한다. `Hello`는 0칸, `World`는 2칸(6-4), `End`는 0칸이 남는다. 첫 줄(`"""` 다음의 빈 줄)과 마지막 줄(닫는 `"""` 앞의 빈 줄)은 제거된다.

**`trimMargin(marginPrefix = "|")`**: 각 줄에서 앞쪽 공백과 **마진 접두사(기본 `|`)까지**를 제거한다. 명시적 마진 마커로 "여기부터가 내용"을 표시하는 방식이라 더 예측 가능하다.

```kotlin
val text = """
    |Hello
    |  World
    |End
""".trimMargin()
println(text)
// => Hello
//   World
// End
```

각 줄에서 `|` 앞의 공백과 `|` 자체를 제거한다. `|Hello` → `Hello`, `|  World` → `  World`(마진 뒤의 공백은 보존), `|End` → `End`. 마진 접두사는 바꿀 수 있다: `trimMargin(">")`.

두 함수의 핵심 차이:

| | `trimIndent()` | `trimMargin("\|")` |
|---|---|---|
| 기준 | 공통 최소 들여쓰기(자동 계산) | 명시적 마진 마커 `\|` |
| 마커 필요 | 없음 | 각 줄에 `\|` 필요 |
| 빈 줄이 섞이면 | 빈 줄은 공통 계산에서 제외 | 마커 없는 줄은 그대로 |
| 예측성 | 들여쓰기가 섞이면 헷갈림 | 마커로 명확 |

> **성능 주의**: `trimIndent()`와 `trimMargin()`은 **런타임에** 문자열을 처리하는 일반 함수다. 컴파일 타임 상수가 아니다. 즉 raw string 리터럴 자체는 들여쓰기까지 포함한 원본이고, `trimIndent()`가 실행 시점에 새 문자열을 만든다. 뜨거운 반복문에서 매번 `"""...""".trimIndent()`를 호출하면 매번 문자열을 다시 만드는 것이니, 상수라면 최상위 `val`로 한 번만 계산하는 게 좋다.

## 6. 동등성과 비교 — `==`는 안전하지만 유니코드는 순진하지 않다

### 6.1 `==`는 구조적 동등이다 (Java의 함정 없음)

Kotlin에서 두 문자열을 비교할 때는 `==`를 쓴다. Kotlin의 `==`는 `equals`를 호출하는 **구조적 동등**이므로(M6, [[10 - 불리언과 동등성과 동일성]]가 소유), 내용이 같으면 `true`다. Java의 `==`(참조 비교)가 아니다.

```kotlin
val a = "hello"
val b = buildString { append("hel"); append("lo") }
println(a == b)    // => true   (내용 같음, equals)
println(a === b)   // => false  (참조 다름, b는 런타임 생성)
println(a.equals(b)) // => true
```

Java에서 `"hello" == someRuntimeString`이 `false`를 내는 유명한 버그가 Kotlin `==`에서는 발생하지 않는다. 이는 Kotlin이 언어 차원에서 정리한 개선이다. `null` 비교도 안전하다 — `==`는 양쪽 널을 알아서 처리한다.

```kotlin
val x: String? = null
println(x == "a")     // => false  (NPE 아님)
println(x == null)    // => true
println(null == null) // => true
```

`==`는 개념적으로 `a?.equals(b) ?: (b === null)`처럼 동작한다. 즉 좌변이 널이면 우변도 널일 때만 `true`. 그래서 문자열 비교에 널이 섞여도 안심이다.

### 6.2 compareTo: UTF-16 코드 유닛 기준 어휘식 순서

문자열의 크기 비교(`<`, `>`, 정렬)는 `Comparable<String>`의 `compareTo`를 통한다([[19 - 연산자 오버로딩과 관례]]). `String.compareTo`는 **UTF-16 코드 유닛 값을 기준으로 앞에서부터 비교하는 어휘식(lexicographic) 순서**다.

```kotlin
println("apple" < "banana")  // => true   ('a'(97) < 'b'(98))
println("Apple" < "apple")   // => true   ('A'(65) < 'a'(97), 대문자가 앞!)
println("abc" < "abd")       // => true   앞 두 글자 같고 'c' < 'd'
println("ab" < "abc")        // => true   접두사가 더 짧으면 앞
println(listOf("banana","apple","cherry").sorted())
// => [apple, banana, cherry]
```

`compareTo`는 첫 번째로 다른 위치의 코드 유닛 값 차이를 본다. `"Apple" < "apple"`이 `true`인 것은 대문자 `'A'`(65)가 소문자 `'a'`(97)보다 코드 유닛 값이 작기 때문이다. 이건 "사전순"과 미묘하게 다르다 — 사람의 사전은 대소문자를 무시하지만 코드 유닛 순서는 모든 대문자(65~90)를 모든 소문자(97~122)보다 앞에 둔다.

> **명세 정밀**: 어휘식 비교가 "코드 유닛" 기준이라, 보충 평면 문자가 섞이면 **코드 포인트 순서와 어긋날 수 있다.** 서로게이트(U+D800~U+DFFF)는 코드 유닛 값으로 U+E000~U+FFFF의 BMP 문자보다 작다. 그래서 U+1F600(서로게이트로 시작) 같은 이모지가 코드 유닛 비교에서는 U+E000대 BMP 문자보다 "작게" 정렬될 수 있는데, 이는 코드 포인트 순서(U+1F600 > U+E000)와 반대다. 대부분의 앱에선 문제가 안 되지만, 유니코드 전체를 정확히 정렬해야 한다면 코드 포인트 기반 비교(또는 로케일 인식 `Collator`)가 필요하다.

### 6.3 대소문자 무시 비교와 로케일 함정

대소문자를 무시하고 비교하려면 `equals`의 `ignoreCase` 파라미터나 `compareTo`의 옵션을 쓴다.

```kotlin
println("Hello".equals("HELLO", ignoreCase = true)) // => true
println("Hello".compareTo("HELLO", ignoreCase = true)) // => 0
```

여기서 로케일 함정이 도사린다. 대소문자 변환은 언어에 따라 다르다. 가장 악명 높은 예가 터키어의 점 없는 i다. 터키어 로케일에서 `'i'`의 대문자는 `'İ'`(점 있는 대문자 I)이고, `'I'`의 소문자는 `'ı'`(점 없는 소문자)다. 로케일 인식 변환은 예상 밖 결과를 낸다.

```kotlin
// JVM 백엔드: 로케일에 의존하는 변환은 함정
val turkish = java.util.Locale("tr", "TR")
println("title".uppercase(turkish))  // => "TİTLE"  (i가 점 있는 İ로!)
println("TITLE".lowercase(turkish))  // => "tıtle"  (I가 점 없는 ı로!)
```

그래서 Kotlin 표준 라이브러리의 `uppercase()`/`lowercase()`(파라미터 없는 버전)는 **로케일 독립적**(root/invariant locale)으로 동작하도록 설계되었다. 식별자·프로토콜 토큰·키 비교처럼 "언어와 무관하게 일관돼야 하는" 대소문자 처리에는 이 로케일 독립 버전을 써야 한다. 사람에게 보여줄 텍스트의 대소문자화만 로케일을 고려한다. 이 구분을 놓치면 "터키에서만 로그인이 안 되는" 종류의 버그가 난다.

> **역사 메모**: Kotlin 1.5에서 `toUpperCase()`/`toLowerCase()`가 `uppercase()`/`lowercase()`로 이름이 바뀌었다. 옛 이름은 플랫폼 기본 로케일을 써서 위의 터키어 버그를 유발했고, 새 이름은 기본이 로케일 독립이라 훨씬 안전하다. Kotlin 2.x에서는 `uppercase()`/`lowercase()`가 표준이다.

### 6.4 부동소수·NaN과의 대조로 본 문자열 동등의 안정성

[[10 - 불리언과 동등성과 동일성]]에서 볼 부동소수점 동등의 함정(`NaN != NaN`, `-0.0 == 0.0`)과 대조하면, 문자열 동등은 훨씬 안정적이다. `String.equals`는 동등성 계약(반사성·대칭성·추이성·일관성)을 완전히 만족한다. `hashCode`도 내용에 따라 결정되며 `equals`와 일치한다. 그래서 문자열은 `HashMap`/`HashSet`의 키로 이상적이다.

```kotlin
val map = hashMapOf("a" to 1)
println(map["a"])                          // => 1
println(map[buildString { append("a") }])  // => 1   (다른 객체지만 equals/hashCode 같음)
```

`buildString { append("a") }`가 리터럴 `"a"`와 다른 객체여도, `equals`와 `hashCode`가 내용 기반이라 맵에서 정확히 조회된다. 이것이 3.5에서 본 정규화 함정과 대비된다 — `"é"`와 `"é"`은 화면상 같아 보여도 코드 유닛이 다르므로 `equals`가 `false`, 다른 해시가 나온다. 문자열 동등은 "바이트(코드 유닛) 수준의 동등"이지 "시각적 동등"이 아니다.

## 7. 연결과 StringBuilder — +의 진짜 비용

### 7.1 +는 plus 관례다

`String + Any?`는 [[19 - 연산자 오버로딩과 관례]]의 `plus` 관례로 해소된다. `String.plus(other: Any?): String`이 정의돼 있어, 오른쪽 피연산자가 무엇이든 그 `toString()`을 붙인 새 문자열을 만든다.

```kotlin
val s = "count: " + 42          // => "count: 42"  (Int의 toString)
val t = "point: " + Point(1,2)  // => "point: Point(x=1, y=2)"  (커스텀 toString)
val u = "x" + null              // => "xnull"  (null도 안전)
```

`String + null`이 `"xnull"`인 것은 `plus`가 널 안전 문자열 변환을 쓰기 때문이다(4.3의 템플릿과 같은 원리). 단, `plus`의 수신자(왼쪽)는 `String`이어야 한다. `42 + "x"`는 `Int.plus(String)`을 찾는데 그런 게 없으니 컴파일 에러다.

```kotlin
// val bad = 42 + "x"   // 컴파일 에러: Int에는 plus(String)이 없음
val ok = "" + 42 + "x"  // => "42x"  왼쪽이 String이면 OK
```

이건 Java의 관대한 `+`(어느 쪽이든 문자열이면 연결)와 다르다. Kotlin은 "왼쪽이 문자열일 때만 연결"이라는 관례 규칙을 엄격히 따른다.

### 7.2 반복 연결의 함정과 StringBuilder

`String`이 불변이라, `+`로 연결할 때마다 **새 문자열이 만들어진다.** 짧은 연결에는 문제없지만, 반복문 안에서 문자열을 누적하면 매 반복마다 새 문자열을 할당·복사하는 $O(n^2)$ 재앙이 된다.

```kotlin
// 나쁜 예: O(n^2) — 매 반복마다 전체 문자열 재생성
var result = ""
for (i in 1..1000) {
    result += i        // 매번 새 String 할당 + 복사
}
```

$k$번째 반복에서 길이 $k$짜리 문자열을 복사하므로 총 비용은 $\sum_{k=1}^{n} k = \frac{n(n+1)}{2} = O(n^2)$이다. $n=1000$이면 약 50만 번의 문자 복사다.

해법은 `StringBuilder`다. `StringBuilder`는 **가변** 문자 버퍼로, `append`가 제자리에서 버퍼를 늘린다(분할 상환 $O(1)$). 마지막에 `toString()`으로 한 번만 불변 `String`을 만든다.

```kotlin
// 좋은 예: O(n) — 가변 버퍼에 append 후 한 번 toString
val sb = StringBuilder()
for (i in 1..1000) {
    sb.append(i)
}
val result = sb.toString()   // 여기서 한 번만 불변 String 생성
```

`StringBuilder`는 `CharSequence`를 구현하므로(2.2) `append`, `insert`, `deleteAt`, `setCharAt`, `reverse` 등 가변 연산을 제공한다. `String`(불변)과 `StringBuilder`(가변)의 이 짝은 [[38 - 컬렉션 - 읽기 전용과 가변]]의 읽기 전용/가변 짝과 같은 철학이다.

### 7.3 buildString: 관용적 스코프

Kotlin은 `StringBuilder`를 더 관용적으로 쓰도록 `buildString`이라는 인라인 함수를 제공한다. 수신 객체 지정 람다([[16 - 스코프 함수와 수신 객체 관용구]])로 `StringBuilder`를 구성하고 자동으로 `toString()`을 돌려준다.

```kotlin
val result = buildString {
    // this: StringBuilder
    append("Point(")
    append(3)
    append(", ")
    append(4)
    append(")")
}
println(result)   // => Point(3, 4)
```

`buildString { ... }`은 `StringBuilder().apply { ... }.toString()`과 사실상 같지만([[16 - 스코프 함수와 수신 객체 관용구]]의 `apply`), 더 명확한 의도를 드러낸다. 인라인 함수라 람다 할당 비용도 없다([[15 - 인라인 함수와 reified]]). 여러 조각을 조립해 문자열을 만들 때의 표준 관용구다.

## 8. 표준 라이브러리 문자열 지형

이 절은 앞 절들보다 얕게, 그러나 지도를 그리기 위해 표준 라이브러리의 문자열 함수군을 개관한다. 핵심은 **이들 대부분이 `String`/`CharSequence`의 확장 함수**([[35 - 확장 함수와 프로퍼티]])라는 점이다. `String` 클래스 자체에 수백 개의 메서드가 박혀 있는 게 아니라, 표준 라이브러리가 확장으로 지어 올린 것이다.

### 8.1 부분 문자열과 인덱스

```kotlin
val s = "hello world"
println(s.substring(0, 5))    // => "hello"   (start, endExclusive)
println(s.substring(6))       // => "world"
println(s.take(3))            // => "hel"
println(s.drop(6))            // => "world"
println(s.indexOf("o"))       // => 4
println(s.lastIndexOf("o"))   // => 7
println(s.startsWith("hello"))// => true
println(s.endsWith("world"))  // => true
println("o" in s)             // => true   (contains, in 관례)
```

`substring`은 코드 유닛 인덱스 기반이라 3.3의 서로게이트 절단 위험을 그대로 안는다는 것을 잊지 말자. `in` 연산자는 `contains` 관례([[19 - 연산자 오버로딩과 관례]])로 부분 문자열/문자 포함을 검사한다.

### 8.2 분리·결합·치환

```kotlin
val csv = "a,b,c"
println(csv.split(","))              // => [a, b, c]  (List<String>)
println(listOf("a","b","c").joinToString("-")) // => "a-b-c"
println("  trim me  ".trim())        // => "trim me"
println("hello".replace("l", "L"))   // => "heLLo"
println("hello".uppercase())         // => "HELLO"
println("Hello World".split(" ").map { it.first() }.joinToString(""))
// => "HW"
```

`split`은 `List<String>`을 돌려주고, `joinToString`은 컬렉션을 구분자로 이어 붙인다([[39 - 컬렉션 연산과 함수형 파이프라인]]). 이들은 문자열과 컬렉션 세계를 잇는 다리다.

### 8.3 문자열을 시퀀스로 다루기

`String`은 `Char`의 시퀀스이므로 [[39 - 컬렉션 연산과 함수형 파이프라인]]의 함수형 연산을 그대로 받는다.

```kotlin
val s = "hello world"
println(s.count { it == 'o' })       // => 2
println(s.filter { it != ' ' })      // => "helloworld"
println(s.map { it.uppercaseChar() }.joinToString("")) // => "HELLO WORLD"
println(s.groupingBy { it }.eachCount()) // => {h=1, e=1, l=3, o=2, ' '=1, w=1, r=1, d=1}
println(s.reversed())                // => "dlrow olleh"
```

`filter`, `map`, `count`, `groupingBy` 모두 `CharSequence`/`Iterable<Char>`에 대한 확장이다. `filter`가 다시 `String`을 돌려주는 것(`CharSequence.filter`)은 문자열 특화 오버로드 덕분이다.

주의: `reversed()`도 **코드 유닛 단위 뒤집기**라, 서로게이트 쌍이 있으면 쌍의 순서가 뒤바뀌어 깨진다.

```kotlin
println("a😀b".reversed())   // => "b<깨진>a"  서로게이트 쌍이 뒤집혀 깨짐
// 원래 [a, 하이, 로우, b] → 뒤집으면 [b, 로우, 하이, a] → 로우-하이 순서라 무효
```

이것 역시 3절의 "코드 유닛 대 코드 포인트" 함정이 표준 라이브러리 곳곳에 스며 있음을 보여준다. 코드 유닛 단위로 문자열을 만지는 모든 연산은 보충 평면 문자 앞에서 조심해야 한다.

### 8.4 문자열 ↔ 수 변환

```kotlin
println("42".toInt())          // => 42
println("3.14".toDouble())     // => 3.14
println("42".toIntOrNull())    // => 42
println("abc".toIntOrNull())   // => null   (예외 대신 null)
// println("abc".toInt())      // 예외: NumberFormatException
println(255.toString(16))      // => "ff"   (16진 문자열)
println("ff".toInt(16))        // => 255
```

`toIntOrNull()` 계열은 파싱 실패 시 예외 대신 `null`을 돌려주어([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]) 널 안전하게 처리할 수 있게 한다. 이는 [[41 - 예외와 Nothing]]의 "예외 대 결과 타입" 논의와 이어진다.

## 9. 멀티플랫폼에서의 Char와 String

마지막으로 JVM 편향을 걷어내고 멀티플랫폼 관점에서 정리한다. Kotlin은 JVM만의 언어가 아니다(M2, [[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]]).

### 9.1 Char와 String의 언어 계약은 타깃 독립

`Char`가 16비트 UTF-16 코드 유닛이고 `String`이 그 코드 유닛의 불변 시퀀스라는 **언어 수준의 계약**은 모든 타깃(JVM, Native, JS, Wasm)에서 동일하다. `length`가 코드 유닛을 세고, 서로게이트 쌍이 존재하며, 이모지가 2로 세지는 것도 타깃 무관이다. Kotlin이 UTF-16을 문자열 모델로 택한 것은 JVM(과 JS)와의 상호운용을 위한 실용적 결정이다.

```text
언어 계약(모든 타깃 동일):
  Char        = UTF-16 코드 유닛 (16비트)
  String      = Char의 불변 시퀀스
  length      = 코드 유닛 개수
  s[i]        = i번째 코드 유닛
  == / equals = 코드 유닛 단위 구조적 동등

물리적 표현(백엔드마다 다름):
  JVM     : java.lang.String (compact strings, byte[])
  JS      : JS String (자바스크립트도 UTF-16이라 자연스러운 매핑)
  Native  : Kotlin/Native 런타임의 String 표현
  Wasm    : Wasm 타깃의 표현
```

### 9.2 JS 타깃과의 자연스러운 궁합

흥미롭게도 JavaScript의 문자열도 UTF-16 코드 유닛 기반이다(자매 시리즈 JavaScript 참조 — JS의 `string.length`도 코드 유닛을 세고, JS에서도 `"😀".length === 2`다). 그래서 Kotlin의 UTF-16 모델은 JS 타깃과 자연스럽게 맞물린다. 두 언어 다 같은 "코드 유닛 함정"을 공유한다. 반대로 Rust(`String`이 UTF-8)나 Swift(`Character`가 그래핌 클러스터)는 다른 모델을 택했다 — 각 언어의 `length` 의미가 다르니, 언어를 넘나들 때 반드시 "이 언어의 문자열 단위는 무엇인가"를 물어야 한다.

### 9.3 코드 포인트 API의 이식성

3.4에서 본 `codePoints()`, `codePointAt()` 등은 `java.lang.String`/`Character`의 것이라 **JVM 백엔드 한정**이다. 멀티플랫폼 공통 코드에서 코드 포인트 단위 처리가 필요하면, 서로게이트를 직접 판별해(공통 소스셋에 있는 `Char.isHighSurrogate()` 등) 3.2의 공식으로 조립하거나, 표준 라이브러리 공통 API에서 지원 여부를 문서로 확인해야 한다. "어느 함수가 공통이고 어느 것이 플랫폼 한정인가"는 표준 라이브러리 버전에 따라 변할 수 있으므로(구현/버전에 따라), 멀티플랫폼 라이브러리를 짤 때는 반드시 확인이 필요하다.

이 절이 이 장 전체의 겸손을 요약한다. `Char`/`String`은 겉보기엔 단순하지만, 그 밑에는 유니코드라는 거대한 표준과 UTF-16이라는 인코딩의 역사적 타협이 깔려 있다. Kotlin은 그 위에 "코드 유닛의 불변 시퀀스"라는 명료한 언어 모델을 세우고, 템플릿·raw string·확장 함수로 편의를 얹었다. 우리가 도입부에서 던진 질문들 — `Char`는 정수인가(아니다, 코드 유닛이다), `length`는 글자 수인가(아니다, 코드 유닛 수다), 이모지는 왜 2인가(서로게이트 쌍이다), 템플릿은 무엇이 되는가(컴파일 타임 연결 코드다), 문자열은 정말 불변인가(그렇다, 그래서 `StringBuilder`가 따로 있다), `\u`는 문자인가(아니다, 코드 유닛이다) — 이 모두가 "`Char` = UTF-16 코드 유닛"이라는 하나의 사실에서 뻗어 나온다. 이 한 문장을 정확히 붙들면 문자열의 거의 모든 함정이 예측 가능해진다.

## 핵심 요약

- **`Char`는 정수가 아니라 UTF-16 코드 유닛(16비트) 하나다.** `Int`와의 암시적 변환이 없어 `code`/`toChar()`/`Char(Int)`로 명시 변환해야 하며, JVM 백엔드에서는 원시형 `char`로 컴파일된다(M4 참조). "문자"라기보다 "코드 유닛 위의 좌표"로 이해해야 한다.
- **`Char` 산술은 좌표 대수다.** `Char + Int → Char`(이동), `Char - Int → Char`(역이동), `Char - Char → Int`(거리)만 존재하고 `Char + Char`는 없다 — "위치 + 위치"는 의미가 없기 때문이다. `'7' - '0' == 7` 관용구가 여기서 나온다.
- **`String`은 `Char`(코드 유닛)의 불변 시퀀스이며, `String.length`는 코드 유닛의 개수다.** "글자 수"도 "코드 포인트 수"도 아니다. BMP 안에서만 셋이 우연히 일치한다.
- **보충 평면 문자(이모지, 희귀 한자 등)는 서로게이트 쌍(코드 유닛 2개)으로 표현되어 `"😀".length == 2`가 되고, `substring`·인덱싱·`reversed`가 쌍을 쪼개 문자를 깨뜨린다.** 코드 유닛·코드 포인트·그래핌 클러스터 세 층위를 분리해야 한다.
- **문자열 템플릿 `$x`/`${expr}`은 런타임 파싱이 아니라 컴파일 타임에 문자열 연결 코드(JVM 백엔드에서 `StringBuilder` 또는 `invokedynamic`)로 desugar된다.** `$id`는 식별자 하나만 읽으므로 프로퍼티/호출엔 `${...}`가 필요하다(`"$p.x"` 함정). null은 널 안전하게 `"null"`로 변환된다.
- **`\uXXXX`는 "유니코드 문자"가 아니라 UTF-16 코드 유닛 하나(16진 4자리)다.** 그래서 `"\u1F600"`은 😀가 아니라 `"ὠ"+"0"`으로 파싱되고, 보충 평면 문자는 서로게이트 쌍 `"\uD83D\uDE00"`으로 써야 하며, `'😀'`는 문자 리터럴이 될 수 없다(컴파일 에러).
- **raw string `"""..."""`은 백슬래시 이스케이프를 해석하지 않고 여러 줄을 담으며, `trimIndent()`는 공통 최소 들여쓰기를 자동 제거하고 `trimMargin("|")`은 명시적 마진 마커까지를 제거한다.** 둘 다 컴파일 상수가 아니라 런타임 함수다.
- **Kotlin `==`는 구조적 동등(`equals`)이라 문자열 내용을 비교하며, Java `==`(참조)의 함정이 없다(M6 참조).** `===`(참조 동일성)로 문자열을 비교하는 것은 거의 항상 버그다 — JVM 리터럴 인턴 때문에 우연히 맞을 뿐, 런타임 문자열엔 `false`가 난다(M48 참조).
- **`String.compareTo`는 UTF-16 코드 유닛 값 기준 어휘식 순서라, 대문자가 소문자보다 앞서고 보충 평면 문자에선 코드 포인트 순서와 어긋날 수 있다.** 파라미터 없는 `uppercase()`/`lowercase()`는 로케일 독립이라 터키어 i 함정을 피한다(식별자 비교엔 이 버전을 써야 함).
- **`String`이 불변이라 `+`는 매번 새 문자열을 만들어, 반복 연결은 $O(n^2)$가 된다.** 누적엔 가변 `StringBuilder`(또는 `buildString {}` 관용구)를 써서 $O(n)$으로 만든다 — 불변 `String`/가변 `StringBuilder`의 분리는 읽기 전용/가변 컬렉션(M26, M27)과 같은 설계 철학이다.
- **`Char`/`String`의 언어 계약(UTF-16 코드 유닛, 불변 시퀀스)은 JVM/Native/JS/Wasm 모든 타깃에서 동일하다.** 물리적 표현과 코드 포인트 API의 이식성만 백엔드/표준 라이브러리 버전에 따라 다르다(M2 참조).

## 연결 노트

- [[07 - 수 1 - Int와 Long과 부동소수점]] — `Char`↔`Int`의 암시적 확대 변환 없음, JVM 원시형 컴파일(M4)의 원리를 공유한다. `Char`는 수 타입 계열의 논리를 그대로 잇는다.
- [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]] — `Char.code`의 비트 표현, 코드 유닛의 정수적 성질, `IntArray`처럼 `CharArray`도 원시 배열이라는 점이 이어진다.
- [[10 - 불리언과 동등성과 동일성]] — `==`(구조적)와 `===`(참조)의 정본(M6, M48). 문자열 인턴이 `===`를 예측 불가로 만드는 이유, `equals`/`hashCode` 계약을 여기서 깊이 판다.
- [[19 - 연산자 오버로딩과 관례]] — `s[i]`(`get`), `+`(`plus`), `<`(`compareTo`), `in`(`contains`)이 모두 관례 함수로 해소되는 메커니즘의 정본.
- [[18 - 범위와 진행과 반복]] — `'a'..'z'` 같은 `CharRange`와 문자 진행, `for (c in s)`의 이터레이터 기반 순회를 소유한다.
- [[38 - 컬렉션 - 읽기 전용과 가변]] — `String`(불변)/`StringBuilder`(가변)의 분리가 `List`/`MutableList` 분리와 같은 철학임을, `CharArray`가 별개 타입(M43)임을 잇는다.
- [[03 - 렉시컬 구조와 세미콜론 추론]] — 문자·문자열 리터럴, 이스케이프, `\uXXXX`, raw string이 렉서 수준에서 어떻게 토큰화되는지를 소유한다.
- [[35 - 확장 함수와 프로퍼티]] — `filter`·`split`·`trimIndent` 등 문자열 API 대부분이 확장 함수로 지어졌다는 사실의 정본(정적 디스패치 M14).
- [[45 - Java 상호운용]] — Kotlin `String` = `java.lang.String`, `length()`↔`length` 프로퍼티 매핑, `CharSequence` 상호운용, 로케일 API 접근을 다룬다.
- [[46 - 멀티플랫폼과 진화와 어두운 구석]] — `Char`/`String`의 타깃별 물리 표현, 코드 포인트 API 이식성, UTF-16 선택의 역사적 배경을 종합한다(M2 회수).
