**이 장이 답하는 질문:**

- 함수가 "일급(first-class)"이라는 말은 정확히 무슨 뜻이며, 코틀린에서 함수를 값으로 다룬다는 것은 컴파일된 뒤에 무엇이 되는가?
- `(Int) -> String` 같은 함수 타입은 새로운 종류의 타입인가, 아니면 우리가 이미 아는 인터페이스의 다른 표기일 뿐인가?
- 람다와 익명 함수는 둘 다 "이름 없는 함수"인데 왜 두 문법이 따로 있으며, `return`이 두 경우에 다르게 동작하는 이유는 무엇인가?
- `it`은 정말 "어디서나 쓸 수 있는 마법 이름"인가? (M42)
- `::foo`, `String::length`, `obj::method`, `::Circle`는 각각 어떤 타입의 값을 만들며, 바운드 참조와 언바운드 참조는 무엇이 다른가?
- `f(x)`라고 함수 값을 호출할 때 JVM 바이트코드 수준에서는 실제로 어떤 메서드가 불리는가?
- 자바 인터페이스에 람다를 넘길 수 있는데 왜 코틀린 인터페이스에는 안 되고, `fun interface`는 그 규칙을 어떻게 바꾸는가?
- `A.() -> B`처럼 점(`.`)이 붙은 함수 타입은 무엇이고, 왜 스코프 함수와 DSL의 토대가 되는가?

[[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]에서 우리는 함수를 *선언하고 호출하는* 문법을 해부했다. 파라미터가 어떻게 바인딩되고, 기본 인자가 어떻게 오버로드를 대체하며, `tailrec`가 어떤 조건에서 재귀를 반복문으로 접는지까지. 그러나 그 장에서 함수는 시종일관 *부르는 대상*이었다. 이름을 적고 괄호를 붙여 호출하는 정적인 실체. 이 장은 그 함수를 무대 아래에서 끌어올려, 변수에 담고 인자로 넘기고 반환값으로 돌려받는 *값*으로 만든다. 함수가 데이터와 같은 시민권을 얻는 순간, 코틀린이라는 언어의 표현력 절반이 여기서 풀려나온다.

이 장이 다루는 것은 세 겹이다. 첫째, **함수 타입**(`(A) -> B`) — 함수를 담을 수 있는 타입이 어떤 구조를 가지며 컴파일러 눈에 무엇으로 보이는가. 둘째, **람다와 익명 함수** — 그 타입의 값을 즉석에서 만드는 두 가지 리터럴 문법과 그 미묘한 차이. 셋째, **함수 참조**(`::foo`) — 이미 이름을 가진 함수를 값으로 승격시키는 문법. 이 셋은 결국 하나의 질문으로 수렴한다: "함수를 값처럼 쓴다"는 추상을 코틀린은 어떤 콘크리트로 떠받치는가.

경계를 못박아 두자. 람다 안에서 바깥 변수를 붙잡는 **클로저와 캡처**의 메커니즘, 그리고 캡처된 `var`가 어떻게 살아남는가는 [[14 - 클로저와 캡처]]가 소유한다. 람다를 넘길 때 객체 할당을 없애는 `inline`과 비지역 반환의 정밀한 규칙, 그리고 `reified`는 [[15 - 인라인 함수와 reified]]가 다룬다. `A.() -> B` 수신 함수 타입을 관용구로 부리는 스코프 함수(`apply`/`with`/`run`)와 그것으로 짓는 DSL은 [[16 - 스코프 함수와 수신 객체 관용구]]와 [[37 - 타입 안전 빌더와 DSL]]의 몫이다. 이 장은 그 모든 것의 *타입 기반*을 놓는다 — 함수가 값이 되는 바로 그 지점의 문법과 표현.

이 장의 논증 궤적은 이렇다. 먼저 "일급 함수"의 의미를 정하고(§1), 그 값을 담는 함수 타입의 문법과 내부 표현을 연다(§2). 그다음 그 타입의 값을 만드는 람다(§3)와, 람다의 축약인 `it`을 정면으로 해부하며 M42를 교정한다(§4). 후행 람다 관례(§5)로 문법의 결을 다듬고, 람다와 다른 리터럴인 익명 함수(§6)로 `return`의 의미가 갈라지는 지점을 짚는다. 이름 있는 함수를 값으로 올리는 함수 참조(§7)를 네 갈래로 나눠 보고, 이 모든 값이 JVM에서 무엇이 되는지(§8) — `FunctionN` 인터페이스와 `invoke`, SAM 변환 — 를 파헤친다. 마지막으로 nullable 함수 타입(§9)과 수신 함수 타입(§10)으로 마무리하며 다음 장들로 다리를 놓는다.

## 1. 일급 함수 — 값이 된 함수

### 1.1 "일급"이라는 자격 요건

어떤 언어에서 값이 **일급(first-class)** 시민이라는 것은, 그 값에 대해 다음을 모두 할 수 있다는 뜻이다: 변수에 담기, 함수의 인자로 넘기기, 함수의 반환값으로 돌려받기, 자료구조(리스트·맵)에 넣기, 런타임에 만들기. 정수 `3`이나 문자열 `"cat"`은 당연히 일급이다. 코틀린에서는 *함수도* 이 자격을 모두 갖는다.

```kotlin
// 변수에 담기
val square: (Int) -> Int = { n -> n * n }

// 인자로 넘기기
fun apply2(x: Int, f: (Int) -> Int): Int = f(f(x))
apply2(3, square)        // => 81  (3→9→81)

// 반환값으로 돌려받기
fun adder(base: Int): (Int) -> Int = { n -> n + base }
val add10 = adder(10)
add10(5)                 // => 15

// 자료구조에 넣기
val ops: List<(Int) -> Int> = listOf(square, add10, { it - 1 })
ops.map { op -> op(4) }  // => [16, 14, 3]
```

이 코드에서 `square`는 이름이 있지만 그 이름은 *변수 이름*이지 함수 선언의 이름이 아니다. `square`가 가리키는 것은 `(Int) -> Int` 타입의 **값**이다. 이 구분이 이 장 전체의 씨앗이다: 코틀린에는 이제 "함수 선언"(§[[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]])과 "함수 값" 두 세계가 공존하며, 함수 참조(§7)가 그 둘을 잇는 다리다.

### 1.2 왜 언어가 이것을 지원해야 하는가

일급 함수가 없는 세계를 상상해 보라. "컬렉션의 각 원소에 어떤 연산을 적용한다"는 발상을 표현하려면, 연산마다 별도 함수를 만들거나 거대한 `when`으로 분기해야 한다. 일급 함수가 있으면 *연산 자체*를 인자로 받는 하나의 `map`으로 끝난다. [[39 - 컬렉션 연산과 함수형 파이프라인]] 전체가 이 능력 위에 서 있고, [[40 - 시퀀스와 지연 평가]], [[23 - 위임 프로퍼티]]의 `by lazy { ... }`, [[42 - suspend와 코루틴 - 언어 수준의 중단]]의 코루틴 빌더까지 — 코틀린 표준 라이브러리의 관용적 표면 대부분이 "함수를 인자로 받는 함수", 즉 **고차 함수(higher-order function)** 로 지어져 있다.

> **역사 메모**: 함수를 값으로 다루는 발상은 코틀린이 발명한 것이 아니다. 그 뿌리는 1930년대 알론조 처치의 **람다 계산법(lambda calculus)** 으로, 거기서는 애초에 *모든 것*이 함수다. Lisp(1958)가 이를 실용 언어로 들여왔고, ML·Haskell을 거쳐 주류로 퍼졌다. 코틀린의 `{ ... }` 람다는 이 계보의 최신 후손이다. 이론적 배경이 궁금하면 Type Theory 시리즈의 무타입 람다 계산 장을 참고하라. 다만 코틀린 람다는 순수 람다 계산과 달리 *타입이 붙어 있고*, 부수 효과(변수 변경, I/O)를 자유롭게 일으킨다.

### 1.3 고차 함수라는 용어

**고차 함수**는 다음 둘 중 하나 이상을 만족하는 함수다: (1) 함수를 인자로 받는다, (2) 함수를 반환한다. 위의 `apply2`는 (1), `adder`는 (2), 표준 라이브러리 `fold`는 둘 다이다. 이 장의 나머지는 "고차 함수에 넘길 값을 어떻게 만들고, 그 값이 무엇인가"를 파고든다. 고차 함수를 넘길 때 발생하는 성능 비용(객체 할당)과 그것을 없애는 `inline`은 [[15 - 인라인 함수와 reified]]로 미룬다 — 여기서는 "함수 값은 대개 객체 하나를 만든다"는 사실만 심어 두자(§8에서 정밀화).

## 2. 함수 타입의 문법과 구조

### 2.1 기본 문법

함수 타입은 **파라미터 타입 목록**을 괄호로 감싸고, 화살표 `->`, 그리고 **반환 타입**을 적어 만든다.

```kotlin
val f0: () -> Unit                 // 인자 없음, Unit 반환
val f1: (Int) -> String            // Int 하나 받고 String 반환
val f2: (Int, Int) -> Int          // Int 둘 받고 Int 반환
val f3: (String, Int, Boolean) -> Double
```

몇 가지 규칙을 못박자:

- **파라미터가 없어도 괄호는 필수**: `() -> Unit`. 파라미터 하나여도 괄호 필수: `(Int) -> String` (자바스크립트의 `x => ...`처럼 괄호를 생략하는 문법은 없다).
- **반환 타입은 생략 불가**: 값을 안 돌려주면 `Unit`을 명시해야 한다. `(Int) ->` 같은 표기는 없다. `Unit`이 실제 타입이라는 사실은 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서 다뤘고(M10), 함수 타입에서 그 위상이 드러난다.
- **화살표는 오른쪽 결합**: `(Int) -> (Int) -> Int`는 "Int를 받아, (Int를 받아 Int를 반환하는 함수)를 반환하는 함수"다. 커링(currying)을 표현할 때 이 결합성이 중요하다.

```kotlin
// 오른쪽 결합: (Int) -> ((Int) -> Int)
val curriedAdd: (Int) -> (Int) -> Int = { a -> { b -> a + b } }
curriedAdd(3)(4)     // => 7
```

### 2.2 파라미터 이름은 문서일 뿐

함수 타입 안의 파라미터에 이름을 붙일 수 있지만, 그 이름은 **가독성용 주석**이며 타입 동일성에 영향을 주지 않는다.

```kotlin
val withNames: (radius: Double, height: Double) -> Double = { r, h -> Math.PI * r * r * h }
val without:   (Double, Double) -> Double = withNames   // OK: 같은 타입
```

이름은 IDE 힌트와 문서에만 쓰인다. 호출 시 그 이름으로 인자를 지정할 수는 *없다* — 이름 붙은 인자([[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]])는 함수 *선언*에서만 동작하고, 함수 *타입을 통한 호출*에서는 위치 기반뿐이다.

```kotlin
val volume: (radius: Double, height: Double) -> Double = { r, h -> Math.PI * r * r * h }
volume(radius = 2.0, height = 5.0)   // 컴파일 에러: 함수 타입 호출엔 이름 붙은 인자 불가
volume(2.0, 5.0)                     // => 62.83...
```

> **명세 정밀**: 함수 타입의 파라미터 이름이 타입에 무의미하다는 것은, 두 함수 타입의 하위타입 관계와 동일성이 오직 (파라미터 타입들, 반환 타입, 수신 타입, 그리고 `suspend` 여부)로 결정된다는 뜻이다. 이는 §10의 수신 함수 타입과 §8의 JVM 표현을 이해하는 열쇠다.

### 2.3 함수 타입은 사실 인터페이스다

여기가 이 장의 첫 번째 큰 반전이다. `(Int) -> String`은 **새로운 종류의 타입이 아니다**. 이것은 표준 라이브러리에 선언된 제네릭 인터페이스 `Function1<in P1, out R>`의 다른 표기법이다. 즉 `(Int) -> String`은 `Function1<Int, String>`과 같은 타입이다. 코틀린 표준 라이브러리는 아리티(arity, 파라미터 개수)별로 인터페이스를 미리 선언해 둔다:

```text
Function0<R>                       ≡  () -> R
Function1<P1, R>                    ≡  (P1) -> R
Function2<P1, P2, R>               ≡  (P1, P2) -> R
...
Function22<P1, ..., P22, R>        ≡  (P1, ..., P22) -> R
```

이 인터페이스들(JVM 백엔드에서는 `kotlin.jvm.functions` 패키지)은 각각 딱 하나의 추상 메서드 `invoke`를 가진다:

```kotlin
public interface Function1<in P1, out R> : Function<R> {
    public operator fun invoke(p1: P1): R
}
```

`operator` 키워드(§8, [[19 - 연산자 오버로딩과 관례]])가 붙은 `invoke` 덕분에 `f(x)`라는 호출 문법이 `f.invoke(x)`로 풀린다. 이것이 §8에서 정밀화할 핵심 사실이다. 그리고 이 구조가 **변성**(variance, [[33 - 제네릭 1 - 타입 파라미터와 변성]])의 교과서 예시라는 점을 지금 심어 두자: 파라미터 타입은 `in`(반공변), 반환 타입은 `out`(공변)이다.

$$\text{Function1}\langle \text{in } P_1,\ \text{out } R\rangle$$

이 변성이 함수 타입의 하위타입 규칙을 낳는다: **"인자는 넓게 받고, 결과는 좁게 준다"** — 즉 `(Animal) -> Dog`는 `(Cat) -> Animal`의 하위타입이다(Cat ⊂ Animal ⊂ 상관없음, Dog ⊂ Animal). 아래에서 이를 직접 확인한다.

```kotlin
open class Animal
class Cat : Animal()
class Dog : Animal()

val specific: (Animal) -> Dog = { Dog() }     // 아무 Animal 받고 Dog 반환
val general: (Cat) -> Animal = specific        // OK! 반공변 인자 + 공변 반환
// specific은 Animal을 받으니 Cat(Animal의 하위)도 당연히 받을 수 있고,
// Dog를 주니 Animal 자리에 넣어도 안전하다.
```

> **흔한 오해**: "함수 타입은 코틀린 컴파일러가 특수 취급하는 마법 타입"이라는 오해. 사실 함수 타입은 *문법적 설탕*일 뿐이며 그 아래에는 평범한 제네릭 인터페이스가 있다. 그래서 우리는 함수 타입을 **손으로 구현**할 수도 있다(§2.4). 다만 파라미터 22개를 넘어가면 특수 인터페이스가 등장한다(§8.4).

### 2.4 함수 타입을 손으로 구현하기

함수 타입이 인터페이스이므로, 클래스로 직접 구현할 수 있다. 이는 "람다는 결국 이 인터페이스의 인스턴스"라는 §8의 논증을 미리 손에 쥐게 해 준다.

```kotlin
class Multiplier(val factor: Int) : (Int) -> Int {
    override fun invoke(p1: Int): Int = p1 * factor
}

val triple: (Int) -> Int = Multiplier(3)
triple(5)          // => 15  (triple.invoke(5))
listOf(1, 2, 3).map(triple)   // => [3, 6, 9]
```

`Multiplier`는 이름 있는 클래스이고 상태(`factor`)를 가지며 함수 타입을 구현한다. 함수 값과 객체 사이의 경계가 얼마나 얇은지가 여기서 드러난다 — 람다는 이 클래스를 컴파일러가 자동으로 만들어 준 것에 지나지 않는다.

### 2.5 typealias로 함수 타입에 이름 붙이기

긴 함수 타입은 반복되면 읽기 어렵다. [[36 - 타입 별칭과 인라인 value class]]에서 자세히 다룰 `typealias`로 별명을 줄 수 있다.

```kotlin
typealias IntPredicate = (Int) -> Boolean
typealias Reducer<T> = (acc: T, item: T) -> T

val isEven: IntPredicate = { it % 2 == 0 }
val sum: Reducer<Int> = { a, b -> a + b }
```

`IntPredicate`는 **새 타입이 아니라 별명**이다(M38). `(Int) -> Boolean`을 기대하는 자리에 `IntPredicate` 값을 자유롭게 넘길 수 있고 그 역도 성립한다 — 둘은 컴파일러에게 *같은 타입*이다. 이 사실은 §7의 함수 참조와 조합할 때 편리하다.

## 3. 람다 표현식 — 함수 값을 만드는 리터럴

### 3.1 문법의 해부

람다는 함수 타입 값을 즉석에서 만드는 **리터럴**이다. 정수 리터럴 `42`가 `Int` 값을 만들 듯, 람다 리터럴 `{ ... }`가 함수 값을 만든다. 완전한 문법은 이렇다:

```kotlin
val f = { x: Int, y: Int -> x + y }
//      └┬┘ └──────┬──────┘ └──┬──┘
//     중괄호   파라미터 목록   본문(마지막 식이 반환값)
```

구성 요소를 하나씩 뜯자:

- **중괄호 `{ }`는 필수**. 람다는 항상 중괄호로 둘러싸인다.
- **파라미터 목록**은 괄호 *없이* 나열하고 `->`로 본문과 구분한다. (함수 타입 표기와 달리 람다 파라미터엔 괄호가 없다는 데 유의.)
- **본문**은 여러 문장(statement)을 가질 수 있고, **마지막 표현식이 반환값**이 된다. 별도의 `return` 키워드가 없다(§6에서 `return`의 의미를 정밀화).

```kotlin
val describe = { n: Int ->
    val parity = if (n % 2 == 0) "짝수" else "홀수"
    val sign = if (n >= 0) "양수/영" else "음수"
    "$n 은 $parity 이고 $sign"        // 마지막 표현식 = 반환값
}
describe(-4)     // => "-4 은 짝수 이고 음수"
```

### 3.2 타입 추론의 두 방향

람다의 파라미터 타입은 **문맥(expected type)** 에서 추론될 수도, 람다 안에서 **명시**될 수도 있다. 이 두 방향을 구분하는 것이 초심자가 자주 헷갈리는 지점이다.

```kotlin
// 방향 A: 기대 타입이 있으면 파라미터 타입 생략 가능
val g: (Int) -> Int = { x -> x * 2 }      // x는 Int로 추론됨

// 방향 B: 기대 타입이 없으면 파라미터 타입 명시 필수
val h = { x: Int -> x * 2 }               // 타입 명시 → h: (Int) -> Int
val bad = { x -> x * 2 }                  // 컴파일 에러: x의 타입을 알 수 없음
```

`map`, `filter` 같은 고차 함수에 넘길 때는 함수 시그니처가 기대 타입을 제공하므로 파라미터 타입을 거의 항상 생략한다. 이것이 코틀린 람다가 그토록 간결해 보이는 이유다.

```kotlin
listOf(1, 2, 3, 4).filter { x -> x % 2 == 0 }   // filter의 시그니처가 x: Int를 알려줌
// => [2, 4]
```

**반환 타입**도 마찬가지로 마지막 표현식에서 추론된다. 람다는 반환 타입을 명시하는 문법이 없다 — 이것이 익명 함수와 갈라지는 첫 번째 지점이다(§6).

### 3.3 파라미터가 없는 람다와 여러 개인 람다

```kotlin
val noArg: () -> String = { "결과" }              // 파라미터 없음: -> 도 없음
val twoArg: (Int, Int) -> Int = { a, b -> a + b } // 둘 이상: 콤마로 나열
```

파라미터가 하나도 없으면 `->`조차 생략한다(`{ "결과" }`). 파라미터가 하나면 `it`으로 축약할 수 있는데(§4), 이것이 M42의 무대다.

### 3.4 구조 분해와 밑줄

람다 파라미터는 [[20 - 구조 분해]]로 분해할 수 있다. `Pair`, `Map.Entry`, 데이터 클래스 등 `componentN`을 가진 값이 파라미터일 때 유용하다.

```kotlin
val points = listOf(1 to "one", 2 to "two", 3 to "three")
points.map { (num, name) -> "$num=$name" }
// => [1=one, 2=two, 3=three]

// 안 쓰는 성분은 밑줄로 무시
points.forEach { (num, _) -> print(num) }   // 123
```

구조 분해 파라미터는 괄호로 감싼다는 데 유의하라 — `{ (num, name) -> ... }`. 괄호 없이 `{ num, name -> ... }`이라고 쓰면 이것은 "파라미터 두 개"를 뜻하지 "Pair 하나를 분해"하는 것이 아니다. 이 문법적 함정은 §5의 후행 람다와 만나면 특히 헷갈린다.

> **명세 정밀**: 람다에서 `(a, b)` 구조 분해는 *위치 기반*이다. `componentN()`이 반환하는 순서대로 매칭되며, 이름은 아무 의미가 없다. 데이터 클래스의 프로퍼티 이름과 분해 변수명이 일치할 필요가 없고, 순서만 맞으면 된다. 이 함정의 상세는 [[20 - 구조 분해]]가 소유한다.

## 4. `it` — 단일 파라미터 람다의 암시적 이름 (M42 교정)

### 4.1 오개념: "`it`은 어디서나 쓸 수 있다"

많은 입문자가 `it`을 "코틀린 어디서나 현재 값을 가리키는 마법 키워드"로 오해한다(M42). 이것은 틀렸다. **`it`은 파라미터가 정확히 하나인 람다에서, 그 유일한 파라미터를 명시적으로 이름 짓지 않았을 때 컴파일러가 부여하는 암시적 이름일 뿐이다.** 키워드도 아니고, 전역적으로 유효한 무언가도 아니다.

```kotlin
listOf(1, 2, 3).map { it * 2 }      // it = 유일한 파라미터. { n -> n * 2 } 와 동일
// => [2, 4, 6]
```

`{ it * 2 }`는 `{ it: Int -> it * 2 }`도 아니고, 그저 `{ n -> n * 2 }`에서 `n`이라는 이름을 안 짓고 관례적 이름 `it`을 쓴 것이다. 이 사실에서 `it`의 모든 한계가 따라 나온다.

### 4.2 `it`이 통하지 않는 경우들

**(1) 파라미터가 둘 이상이면 `it`은 없다.** 파라미터가 여럿이면 반드시 이름을 지어야 한다.

```kotlin
val add: (Int, Int) -> Int = { a, b -> a + b }
val bad: (Int, Int) -> Int = { it + it }    // 컴파일 에러: it은 다중 파라미터에 없음
```

**(2) 파라미터가 아예 없으면 `it`은 없다.**

```kotlin
val supplier: () -> Int = { it }            // 컴파일 에러: 파라미터가 없어 it도 없음
```

**(3) 익명 함수에는 `it`이 없다.** `it`은 오직 람다 문법의 산물이다(§6).

```kotlin
val square = fun(x: Int): Int = it * it     // 컴파일 에러: 익명 함수엔 it 없음
```

**(4) 스코프 함수의 `it`도 결국 람다 파라미터다.** `let`이나 `also`의 `it`이 특별해 보이지만, 그것은 `let`이 `(T) -> R` 타입의 람다를 받고 그 유일한 파라미터가 `it`으로 노출될 뿐이다([[16 - 스코프 함수와 수신 객체 관용구]]). 마법이 아니라 §4.1의 규칙이 그대로 적용된 것이다.

```kotlin
val name: String? = "Fido"
name?.let { println("이름: $it") }    // it = let에 넘긴 람다의 유일 파라미터(String)
```

### 4.3 중첩 람다에서의 `it` 그림자

`it`이 "유일 파라미터의 이름"이라는 정의는 **중첩**된 람다에서 명확한 결과를 낳는다: 안쪽 람다의 `it`이 바깥 람다의 `it`을 **가린다(shadow)**. 즉 안쪽에서 `it`이라고 쓰면 항상 *가장 가까운* 람다의 파라미터다.

```kotlin
val matrix = listOf(listOf(1, 2), listOf(3, 4))
matrix.map { row ->
    row.map { it * 10 }          // 여기 it = 안쪽 원소(Int). 바깥 row가 아님
}
// => [[10, 20], [30, 40]]

// 만약 두 층 다 it을 쓰면 바깥 it에 접근 불가
matrix.map {
    it.map { it * 10 }           // 바깥 it(List)과 안쪽 it(Int)이 겹침 — 바깥 it은 여기서 못 씀
}
```

두 번째 예는 컴파일은 되지만 바깥 리스트를 안쪽에서 참조할 방법이 사라진다. 그래서 **중첩되면 이름을 지으라**는 관례가 생긴다. `it`은 편의이지 규율이 아니다.

> **성능 주의**: `it`을 쓰든 이름을 짓든 컴파일 결과는 완전히 동일하다. `it`은 순수한 문법 축약이며 런타임 비용이 전혀 없다. 성능 때문에 `it`을 피할 이유는 없다 — 오직 *가독성*만이 판단 기준이다. 파라미터 하나에 의미가 자명하면 `it`, 문맥이 복잡하거나 중첩되면 이름.

### 4.4 `it`의 타입은 어디서 오는가

`it`의 타입 역시 §3.2의 추론에서 온다. 기대 타입이 있어야 `it`을 쓸 수 있다.

```kotlin
val f: (String) -> Int = { it.length }   // it: String (기대 타입에서)
val g = { it * 2 }                        // 컴파일 에러: 기대 타입 없음 → it 타입 미상
```

즉 `it`은 "기대 타입이 함수 타입이고, 그 아리티가 1일 때만" 등장할 수 있다. 이 조건은 M42의 정확한 반례다: `it`은 특정 문법적·타입적 조건에서만 존재하는 편의이지, 편재하는 마법이 아니다.

## 5. 후행 람다 — 문법의 결

### 5.1 규칙: 마지막 인자가 함수면 괄호 밖으로

고차 함수의 **마지막 파라미터가 함수 타입**이면, 그 람다를 인자 괄호 *바깥*에 쓸 수 있다. 이를 **후행 람다(trailing lambda)** 라 한다.

```kotlin
fun repeatAction(times: Int, action: (Int) -> Unit) {
    for (i in 0 until times) action(i)
}

// 정석: 람다가 괄호 안
repeatAction(3, { i -> println(i) })

// 후행 람다: 마지막 함수 인자를 괄호 밖으로
repeatAction(3) { i -> println(i) }        // 동일한 호출

// 함수가 유일한 인자면 괄호 자체를 생략
listOf(1, 2, 3).forEach { println(it) }    // forEach(f)에서 () 생략
```

이 관례가 코틀린 코드를 마치 언어에 내장된 제어 구문처럼 보이게 한다. `repeatAction(3) { ... }`은 마치 `for`문 같지만, 실은 그냥 함수 호출이다. [[37 - 타입 안전 빌더와 DSL]]의 모든 마법이 이 하나의 관례에서 자란다.

### 5.2 후행 람다와 다른 인자의 조합

마지막 인자만 후행으로 뺄 수 있다. 다른 인자들은 괄호 안에 남는다.

```kotlin
fun <T, R> transform(input: T, times: Int, mapper: (T) -> R): List<R> {
    return List(times) { mapper(input) }
}

transform("x", 3) { it.uppercase() }       // input="x", times=3, mapper는 후행
// => [X, X, X]
```

만약 함수 타입 파라미터가 마지막이 아니라면 후행 람다를 쓸 수 없고 괄호 안에 넣어야 한다. 이 때문에 API 설계자들은 **함수 파라미터를 관례적으로 마지막에 둔다**(표준 라이브러리의 `map`, `filter`, `fold`가 모두 그렇다). `fold`처럼 초기값과 함수를 받을 때 함수를 뒤에 두는 이유가 바로 후행 람다를 살리기 위함이다.

```kotlin
listOf(1, 2, 3, 4).fold(0) { acc, x -> acc + x }   // 초기값 0, 함수는 후행
// => 10
```

### 5.3 후행 람다의 함정: 마지막 인자가 함수여야만

후행 람다는 *마지막 파라미터가 함수 타입일 때만* 가능하다. 이를 잊으면 혼란스러운 에러를 본다.

```kotlin
fun log(action: (String) -> String, tag: String) { /* ... */ }

log({ it.uppercase() }, "TAG")             // OK: 람다가 괄호 안 (함수가 첫 인자라)
log("TAG") { it.uppercase() }              // 컴파일 에러: 후행 람다는 마지막 인자에만
```

또 하나 미묘한 점: 함수를 받는 파라미터가 nullable이거나 기본값이 있어도 후행 람다는 여전히 동작한다 — 마지막 위치이기만 하면 된다.

### 5.4 빈 후행 람다와 두 개의 람다

파라미터가 없으면 `{ }`만으로 후행 람다를 쓰고, 만약 함수 타입 파라미터가 둘이면 하나만 후행으로 뺄 수 있다(마지막 것).

```kotlin
fun onResult(onSuccess: () -> Unit, onFailure: () -> Unit) { /* ... */ }

onResult({ println("성공") }) { println("실패") }
// onSuccess는 괄호 안, onFailure(마지막)만 후행
```

두 람다를 모두 후행처럼 쓰는 문법은 없다. 가독성을 위해 이런 경우 둘 다 괄호 안에 이름 붙여 넣거나, `fun interface`(§8.5)로 콜백을 묶는 설계를 택한다.

## 6. 익명 함수 — 람다의 사촌

### 6.1 왜 두 번째 리터럴이 필요한가

코틀린에는 함수 값을 만드는 리터럴이 *둘* 있다: 람다(§3)와 **익명 함수(anonymous function)**. 익명 함수는 `fun` 키워드를 쓰되 이름을 생략한 형태다.

```kotlin
val square = fun(x: Int): Int { return x * x }
val squareExpr = fun(x: Int) = x * x        // 단일 표현식 형태

square(5)        // => 25
```

겉보기엔 람다의 장황한 버전 같지만, 익명 함수에는 람다가 못 하는 두 가지가 있다: **반환 타입 명시**와 **일반적인 `return` 의미**. 이 둘이 익명 함수가 별도로 존재하는 이유다.

### 6.2 차이 1: 반환 타입 명시

람다는 반환 타입을 마지막 표현식에서만 추론한다. 익명 함수는 반환 타입을 *명시*할 수 있어, 복잡한 본문에서 타입을 못박고 싶을 때 유용하다.

```kotlin
// 람다: 반환 타입 추론만 가능
val parse1 = { s: String -> s.toIntOrNull() ?: 0 }   // (String) -> Int로 추론

// 익명 함수: 반환 타입 명시
val parse2 = fun(s: String): Number {
    return s.toDoubleOrNull() ?: s.toIntOrNull() ?: 0
}
```

### 6.3 차이 2: `return`의 의미 — 이 장의 핵심 갈림길

이것이 가장 중요한 차이다. **람다 안의 `return`과 익명 함수 안의 `return`은 다른 곳으로 돌아간다.**

- **익명 함수에서 `return`**: 그 익명 함수 자신에서 반환한다. 직관적이다.
- **람다에서 벌거벗은 `return`**: 람다를 감싼 *바깥 함수*에서 반환하려는 시도다. 이를 **비지역 반환(non-local return)** 이라 하고, 오직 `inline` 함수에 넘긴 람다에서만 허용된다(M41). 인라인이 아니면 컴파일 에러이며, 람다만 벗어나려면 라벨 `return@label`을 써야 한다.

```kotlin
fun findFirstEven(nums: List<Int>): Int? {
    // 익명 함수의 return은 익명 함수만 벗어남 → forEach를 못 멈춤
    nums.forEach(fun(n) {
        if (n % 2 == 0) return       // 이 익명 함수에서만 반환, 루프 계속
    })
    return null
}
```

반면 람다에서:

```kotlin
fun findFirstEven(nums: List<Int>): Int? {
    nums.forEach { n ->
        if (n % 2 == 0) return n     // 비지역 반환: findFirstEven에서 반환!
    }                                // forEach가 inline이라 허용됨
    return null
}
findFirstEven(listOf(1, 3, 4, 5))    // => 4
```

`forEach`가 `inline`(§[[15 - 인라인 함수와 reified]])이기 때문에 람다의 `return n`이 바깥 `findFirstEven`을 즉시 벗어난다. 만약 `forEach`가 인라인이 아니었다면 `return n`은 컴파일 에러가 났을 것이다. 이 비지역 반환의 정밀한 규칙 — 왜 인라인에서만 되는가, `crossinline`은 왜 그것을 막는가 — 는 [[14 - 클로저와 캡처]]와 [[15 - 인라인 함수와 reified]]가 소유하며(M41), 여기서는 "리터럴 종류에 따라 `return`의 목적지가 다르다"는 사실만 확립한다.

### 6.4 라벨 반환: 람다에서 람다만 벗어나기

인라인이든 아니든, 람다에서 *람다만* 벗어나고 싶으면 라벨을 쓴다. 함수 이름이 자동 라벨이 되므로 `return@forEach`처럼 쓸 수 있다.

```kotlin
fun sumPositives(nums: List<Int>): Int {
    var sum = 0
    nums.forEach { n ->
        if (n < 0) return@forEach    // 이 반복만 건너뜀 (continue 같은 효과)
        sum += n
    }
    return sum
}
sumPositives(listOf(1, -2, 3, -4, 5))   // => 9
```

`return@forEach`는 람다의 그 실행만 끝내고 `forEach`의 다음 원소로 넘어간다. 명시적 라벨을 붙일 수도 있다: `nums.forEach loop@ { ... return@loop }`. 이 라벨 문법의 전모는 [[14 - 클로저와 캡처]]에서 다룬다.

### 6.5 람다 vs 익명 함수 요약표

| 항목 | 람다 `{ ... }` | 익명 함수 `fun(...) { ... }` |
|------|----------------|------------------------------|
| 반환 타입 | 마지막 표현식에서 추론만 | 명시 가능 |
| `it` | 단일 파라미터 시 사용 가능 | 없음(파라미터 이름 필수) |
| 벌거벗은 `return` | 비지역 반환(인라인에서만) | 익명 함수 자신에서 반환 |
| 문법 간결성 | 매우 간결 | 다소 장황 |
| 후행 람다 | 가능 | 불가(괄호 안에 위치) |
| 파라미터 기본값 | 불가 | 불가 |

실무에서는 람다가 압도적으로 흔하다. 익명 함수는 "반환 타입을 명시해야 하거나, `return`이 로컬이길 원하거나, 여러 반환 지점이 있는 복잡한 콜백"에서 선택한다.

## 7. 함수 참조 — 이름 있는 함수를 값으로

### 7.1 왜 참조가 필요한가

이미 선언된 함수를 고차 함수에 넘기고 싶을 때, 람다로 감싸면 장황하다.

```kotlin
fun isOdd(n: Int): Boolean = n % 2 == 1

listOf(1, 2, 3, 4).filter { isOdd(it) }   // 람다로 감쌈: 파라미터를 그대로 전달
listOf(1, 2, 3, 4).filter(::isOdd)         // 함수 참조: 더 간결
// 둘 다 => [1, 3]
```

`::isOdd`는 **함수 참조(function reference)** 다. 이것은 `isOdd`라는 *선언*을 `(Int) -> Boolean` 타입의 *값*으로 승격시킨다. `{ isOdd(it) }`와 `::isOdd`는 같은 타입의 값을 만들지만, 참조는 인자를 그대로 전달하는 얇은 껍데기라 의도가 명확하다. 함수 참조는 네 갈래가 있다.

### 7.2 갈래 1: 최상위·지역 함수 참조 `::foo`

가장 단순한 형태. 최상위 함수나 지역 함수를 `::이름`으로 참조한다.

```kotlin
fun double(x: Int): Int = x * 2
fun greet(name: String): String = "안녕, $name"

val d: (Int) -> Int = ::double
val g: (String) -> String = ::greet
d(21)              // => 42
g("도형")          // => 안녕, 도형
```

오버로드가 있으면 어떤 것을 참조하는지 모호할 수 있는데, 이때는 기대 타입으로 해소한다.

```kotlin
fun area(r: Double): Double = Math.PI * r * r
fun area(w: Double, h: Double): Double = w * h

val circle: (Double) -> Double = ::area           // 첫 오버로드
val rect: (Double, Double) -> Double = ::area     // 둘째 오버로드
// 기대 타입이 어떤 area인지 결정한다
```

### 7.3 갈래 2: 언바운드 멤버 참조 `Class::method`

멤버 함수를 *수신 객체 없이* 참조하면, **수신 객체가 첫 번째 파라미터로 승격된 함수 타입**이 된다.

```kotlin
val lengths: (String) -> Int = String::length     // 수신자 String이 파라미터로
lengths("cat")     // => 3

listOf("a", "bb", "ccc").map(String::length)       // => [1, 2, 3]

// 메서드에 파라미터가 있으면 수신자 + 원래 파라미터
val prefixed: (String, String) -> Boolean = String::startsWith
prefixed("hello", "he")   // => true  ("hello".startsWith("he"))
```

`String::length`의 타입이 `(String) -> Int`라는 데 주목하라. 프로퍼티도 사실 게터 함수이므로 이렇게 참조된다([[22 - 프로퍼티와 백킹 필드]]). 언바운드 참조는 "이 클래스의 어떤 인스턴스에든 적용할 연산"을 표현할 때 완벽하다.

### 7.4 갈래 3: 바운드 멤버 참조 `obj::method`

특정 *인스턴스*에 묶인 참조. 수신 객체가 이미 정해져 있으므로, 함수 타입에 수신자 파라미터가 나타나지 않는다.

```kotlin
val greeting = "안녕하세요"
val getLength: () -> Int = greeting::length       // greeting에 바운드
getLength()        // => 5 (한글 5자)

class Counter(var count: Int = 0) {
    fun increment(): Int = ++count
}
val c = Counter()
val inc: () -> Int = c::increment                  // c 인스턴스에 바운드
inc(); inc()       // c.count가 2가 됨
```

언바운드(`String::length`, 타입 `(String) -> Int`)와 바운드(`greeting::length`, 타입 `() -> Int`)의 차이가 핵심이다: 바운드 참조는 수신 객체를 *포획*하고 있어 파라미터 목록에서 그것이 사라진다. 이것은 §8에서 볼 "람다가 캡처하는 것"과 같은 원리다 — 바운드 참조는 사실상 그 객체를 캡처한 클로저다([[14 - 클로저와 캡처]]).

`this::method`로 현재 인스턴스의 메서드를 바운드 참조할 수도 있다. 콜백 등록에 흔하다.

```kotlin
class Widget {
    fun onClick() { println("클릭됨") }
    fun register(handler: () -> Unit) { /* ... */ }
    fun setup() { register(this::onClick) }        // 자기 메서드를 바운드 참조
}
```

### 7.5 갈래 4: 생성자 참조 `::ClassName`

생성자를 함수 값으로 참조한다. 타입은 "생성자 파라미터 → 인스턴스"인 함수 타입이다.

```kotlin
class Point(val x: Int, val y: Int) {
    override fun toString() = "($x, $y)"
}

val makePoint: (Int, Int) -> Point = ::Point
makePoint(3, 4)    // => (3, 4)

// 팩토리처럼 매핑에 사용
val xs = listOf(1, 2, 3)
val points = xs.map { Point(it, 0) }               // 람다
val origins = xs.map(::Point.partial(0))           // (개념적; 실제로는 아래처럼)
listOf(1 to 2, 3 to 4).map { (x, y) -> Point(x, y) }   // => [(1, 2), (3, 4)]
```

생성자 참조는 데이터 변환 파이프라인에서 "생성자를 매핑 함수로" 쓸 때 특히 간결하다. `typealias`로 별명을 준 클래스나 [[27 - 데이터 클래스]]의 생성자에도 그대로 적용된다.

```kotlin
data class User(val name: String, val age: Int)
val names = listOf("A", "B")
val ages = listOf(20, 30)
names.zip(ages, ::User)         // => [User(name=A, age=20), User(name=B, age=30)]
// zip의 셋째 인자가 (String, Int) -> User 이고 ::User가 정확히 그 타입
```

### 7.6 프로퍼티 참조와 리플렉션의 문턱

`::` 문법은 함수뿐 아니라 프로퍼티도 참조한다. `String::length`는 사실 `KProperty1<String, Int>`이자 동시에 `(String) -> Int` 함수로 쓸 수 있는 값이다. 프로퍼티 참조는 값을 읽는 것 이상 — 이름, 가변이면 세터까지 — 을 제공한다.

```kotlin
class Box(var content: String)
val prop = Box::content                            // KMutableProperty1<Box, String>
val box = Box("초기값")
prop.get(box)                  // => "초기값"
prop.set(box, "변경됨")
box.content                    // => "변경됨"
prop.name                      // => "content"
```

여기서 `.get`, `.set`, `.name`은 **리플렉션 API**의 표면이다. 함수 참조가 단순 함수 값을 넘어 `KFunction`/`KProperty`라는 리플렉션 객체이기도 하다는 사실, 그리고 그 대가(리플렉션 메타데이터, `kotlin-reflect` 의존성)는 [[44 - 애노테이션과 리플렉션]]이 소유한다. 이 장에서는 "함수 참조는 함수 타입 값인 *동시에* 리플렉션 핸들"이라는 이중성만 짚어 둔다.

> **명세 정밀**: `::foo`의 정적 타입은 함수 타입(`(A) -> B`)과 `KFunction` 계열 인터페이스의 *교집합*이다. 함수 타입 문맥에서는 함수처럼, 리플렉션 문맥에서는 `KFunction`처럼 동작한다. 단순 호출·전달만 하면 리플렉션 라이브러리가 필요 없지만, `.name`·`.parameters` 같은 메타데이터에 접근하면 `kotlin-reflect`가 필요할 수 있다.

### 7.7 네 갈래 요약표

| 문법 | 이름 | 예 | 결과 타입 |
|------|------|-----|-----------|
| `::foo` | 최상위/지역 함수 | `::isOdd` | `(Int) -> Boolean` |
| `Class::m` | 언바운드 멤버 | `String::length` | `(String) -> Int` |
| `obj::m` | 바운드 멤버 | `"cat"::length` | `() -> Int` |
| `::Class` | 생성자 | `::Point` | `(Int, Int) -> Point` |
| `Class::prop` | 프로퍼티(언바운드) | `Box::content` | `(Box) -> String` + KProperty |

## 8. 함수 값의 JVM 표현 — invoke와 SAM

이 절은 "함수를 값으로 다룬다"는 추상이 **JVM 백엔드에서** 어떤 콘크리트가 되는지 파고든다. (Native/JS/Wasm 백엔드는 세부가 다르며, 아래는 JVM 한정이다.)

### 8.1 람다는 인터페이스의 인스턴스가 된다

§2.3에서 함수 타입이 `Function1` 같은 인터페이스임을 봤다. 논리적 귀결은: **람다는 그 인터페이스를 구현한 객체 하나**로 컴파일된다. `{ x: Int -> x * 2 }`는 개념적으로 다음과 같은 익명 클래스의 인스턴스다.

```java
// JVM 백엔드가 생성하는 것의 개념적 모습 (Java 유사 의사코드)
final class Lambda$1 implements Function1<Integer, Integer> {
    public Integer invoke(Integer x) {
        return x * 2;
    }
}
// { x -> x * 2 } 자리에 new Lambda$1() 가 놓인다
```

즉 `val f = { x: Int -> x * 2 }`는 대략 `Function1` 구현 객체 하나를 힙에 만든다. 이것이 §1.3에서 예고한 "함수 값은 대개 객체 하나를 만든다"의 정체다. 고차 함수에 람다를 많이 넘기면 이 객체 할당이 쌓이는데, `inline`([[15 - 인라인 함수와 reified]])이 바로 이 할당을 컴파일 타임에 제거하는 장치다.

> **구현 정밀**: 컴파일러 버전과 옵션에 따라 람다는 (a) 이름 붙은 익명 클래스, 또는 (b) `invokedynamic` + `LambdaMetafactory` 기반의 지연 생성으로 컴파일된다. 코틀린 2.x의 JVM 백엔드는 기본적으로 `invokedynamic` 방식을 쓰며(`-Xlambdas=indy`), 이는 클래스 파일 수를 줄이고 시작 시간을 개선한다. 어느 방식이든 *런타임에는* `Function1` 등을 구현한 객체가 만들어진다는 관찰 가능한 의미론은 동일하다. 정확한 형태는 디컴파일로 확인하는 법을 [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]가 안내한다.

### 8.2 캡처 없는 람다는 싱글턴이 될 수 있다

바깥 변수를 하나도 붙잡지 않는 람다(캡처 없음, [[14 - 클로저와 캡처]])는 매번 새 객체를 만들 필요가 없다. 상태가 없으니 인스턴스 하나를 재사용해도 안전하다. JVM 백엔드는 이런 람다를 **싱글턴 인스턴스**로 최적화할 수 있다.

```kotlin
fun makeDoubler(): (Int) -> Int = { it * 2 }       // 캡처 없음
val a = makeDoubler()
val b = makeDoubler()
// a와 b는 (구현에 따라) 같은 싱글턴 인스턴스일 수 있다
```

반면 바깥 변수를 캡처하는 람다는 그 캡처값을 담아야 하므로 매 생성마다 새 객체다. 이 차이가 [[14 - 클로저와 캡처]]의 성능 논의로 이어진다.

> **성능 주의**: "람다 = 객체 할당"이라는 사실 때문에 뜨거운 루프 안에서 매번 새 캡처 람다를 만드는 것은 GC 압박이 될 수 있다. 두 해법이 있다: (1) 고차 함수를 `inline`으로 만들어 할당 자체를 없앤다, (2) 캡처 없는 람다는 상수처럼 밖으로 빼서 재사용한다. 표준 라이브러리의 `map`/`filter`/`forEach`가 인라인인 이유가 (1)이다.

### 8.3 `invoke` — 호출의 진짜 정체

함수 값 `f`를 `f(x)`로 호출하는 것은 문법적 설탕이다. 실제로는 `Function1`의 `invoke` 연산자 메서드가 불린다([[19 - 연산자 오버로딩과 관례]], M40). 다음 세 줄은 완전히 동등하다.

```kotlin
val f: (Int) -> Int = { it + 1 }
f(41)              // => 42
f.invoke(41)       // => 42  (위와 완전히 동일)
```

`invoke`가 그냥 메서드이므로, 우리는 *아무 객체에나* `operator fun invoke`를 정의해 그 객체를 "함수처럼 호출 가능"하게 만들 수 있다. 함수 타입을 구현하지 않아도 된다.

```kotlin
class Accumulator {
    var total = 0
    operator fun invoke(x: Int): Int { total += x; return total }
}
val acc = Accumulator()
acc(10)            // => 10   (acc.invoke(10))
acc(5)             // => 15
```

`acc`는 `(Int) -> Int` 타입이 *아니지만* 호출 문법을 지원한다. 이것이 "호출 가능성"과 "함수 타입임"이 별개임을 보여 준다 — 전자는 `invoke` 연산자만 있으면 되고, 후자는 `FunctionN` 인터페이스 구현을 뜻한다. [[28 - object와 companion - 싱글턴과 동반 객체]]의 팩토리나 DSL에서 `invoke`를 정의해 생성 문법을 매끄럽게 만드는 관용구가 여기서 나온다.

### 8.4 파라미터 22개의 벽

`Function0`부터 `Function22`까지가 표준 라이브러리에 선언돼 있다. 그렇다면 파라미터가 23개 이상인 함수 타입은? 이때는 **`FunctionN`** 이라는 특수 인터페이스가 등장한다(가변 인자 배열로 호출을 받는 형태). 실무에서 파라미터 23개짜리 함수는 거의 병리적이므로 이 경계를 마주칠 일은 드물지만, "함수 타입 = 아리티별 인터페이스"라는 모델에 상한이 있다는 사실은 알아 둘 가치가 있다.

```text
아리티     인터페이스
0          Function0<R>
1          Function1<P1, R>
...        ...
22         Function22<P1, ..., P22, R>
23+        FunctionN<R>   (특수 처리)
```

### 8.5 SAM 변환 — 자바 인터페이스와 fun interface

**SAM(Single Abstract Method)** 은 추상 메서드가 딱 하나인 인터페이스다. 자바의 `Runnable`, `Comparator`, `Callback` 같은 것들. 코틀린은 자바 SAM 인터페이스를 기대하는 자리에 **람다를 자동 변환**해 넣어 준다 — 이를 **SAM 변환**이라 한다.

```kotlin
// 자바 인터페이스 java.lang.Runnable { void run(); } 에 람다 전달
val thread = Thread { println("실행 중") }          // Runnable로 SAM 변환
thread.start()

// java.util.Comparator에도
val byLength = Comparator<String> { a, b -> a.length - b.length }
```

여기서 중요한 규칙 하나: **SAM 변환은 기본적으로 자바 인터페이스에만 자동으로 일어난다.** 코틀린에서 정의한 일반 인터페이스에 람다를 넘기려 하면 컴파일 에러다. 왜냐하면 코틀린에는 이미 함수 타입(`(A) -> B`)이라는 더 나은 표현이 있어서, 콜백을 인터페이스가 아니라 함수 타입 파라미터로 받도록 권장하기 때문이다.

```kotlin
interface OnClick {                                // 일반 코틀린 인터페이스
    fun handle(x: Int)
}
fun register(cb: OnClick) { /* ... */ }
register { println(it) }                            // 컴파일 에러: 일반 인터페이스엔 SAM 변환 없음
```

이 벽을 허무는 것이 **`fun interface`**(functional interface, [[25 - 인터페이스]])다. 인터페이스 앞에 `fun`을 붙이면 SAM 변환이 활성화된다.

```kotlin
fun interface OnClick {                             // functional interface
    fun handle(x: Int)
}
fun register(cb: OnClick) { cb.handle(42) }
register { println("클릭: $it") }                    // OK! SAM 변환 → "클릭: 42"
```

`fun interface`는 "람다로 만들 수 있는 인터페이스"를 명시적으로 선언하는 방법이다. 함수 타입과 `fun interface`는 언제 무엇을 쓸까? 함수 타입은 이름 없는 순수 함수 계약에, `fun interface`는 이름을 붙이고 싶거나(가독성) 자바와 상호운용해야 할 때 유리하다.

| 콜백 표현 방법 | 람다 전달 | 언제 쓰나 |
|----------------|-----------|-----------|
| 함수 타입 `(Int) -> Unit` | 항상 됨 | 코틀린 내부, 이름 불필요 |
| `fun interface Foo` | SAM 변환으로 됨 | 이름·의미 부여, 자바 노출 |
| 일반 `interface Foo` | 안 됨(객체 명시 필요) | 메서드 여럿, 상태 계약 |

> **역사 메모**: 자바 8이 람다와 함수형 인터페이스를 들여오면서 SAM 변환이 자바 생태계의 표준이 됐다. 코틀린은 자바와의 매끄러운 상호운용을 위해 자바 SAM 변환을 자동 지원하되, 자국 인터페이스에는 함수 타입을 밀고 `fun interface`를 옵트인으로 열어 두는 절충을 택했다. 이 설계는 [[45 - Java 상호운용]]의 큰 주제 중 하나다.

### 8.6 함수 값과 `is` 검사

함수 값도 객체이므로 타입 검사가 된다. 다만 제네릭 소거([[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]) 때문에 타입 인자까지는 못 본다.

```kotlin
val f: (Int) -> Int = { it + 1 }
f is Function1<*, *>       // => true
f is (Int) -> Int          // 경고/제약: 타입 인자는 소거되어 완전 검사 불가
```

즉 "함수인지"는 알 수 있어도 "무슨 타입의 함수인지"는 JVM 런타임에서 완전히 알 수 없다. 이는 함수 타입이 결국 제네릭 인터페이스이기 때문이며, 소거의 일반 규칙(M19)이 그대로 적용된 것이다.

## 9. nullable 함수 타입과 안전 호출

### 9.1 괄호가 만드는 차이

함수 타입을 nullable로 만들려면 **전체를 괄호로 감싸고** `?`를 붙인다. 괄호 위치가 의미를 완전히 바꾸므로 정밀해야 한다.

```kotlin
val a: ((Int) -> Int)?      // 전체가 nullable: 함수가 없을 수도 있음
val b: (Int) -> Int?        // 반환 타입이 nullable: 함수는 있고, Int? 반환
val c: (Int?) -> Int        // 파라미터가 nullable
```

- `((Int) -> Int)?` : `a` 자체가 `null`일 수 있다.
- `(Int) -> Int?` : `b`는 항상 함수이며, 그 함수가 `Int?`(즉 null 가능한 정수)를 반환한다.
- `(Int?) -> Int` : `c`는 함수이며 null 가능한 정수를 받는다.

이 세 가지를 혼동하면 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]의 널 규칙이 예상 밖으로 작동한다.

### 9.2 nullable 함수의 호출: `?.invoke`

nullable 함수를 그냥 `a(x)`로 부르면 컴파일 에러다(널일 수 있으니). §8.3에서 `f(x)`가 `f.invoke(x)`임을 봤으니, 안전 호출을 `invoke`에 적용하면 된다: `a?.invoke(x)`.

```kotlin
var onProgress: ((Int) -> Unit)? = null

fun report(pct: Int) {
    onProgress?.invoke(pct)      // onProgress가 null이면 아무 일 없음
}

report(50)                       // (핸들러 없음) 아무 출력 없음
onProgress = { println("진행: $it%") }
report(75)                       // => 진행: 75%
```

`onProgress?.invoke(pct)`는 "핸들러가 등록돼 있으면 부르고, 없으면 조용히 넘어간다"는 옵셔널 콜백 관용구다. 엘비스와 결합하면 기본 동작도 줄 수 있다.

```kotlin
val result = (transformer?.invoke(input)) ?: input   // 변환기 없으면 원본 그대로
```

`f(x)`라는 직접 호출 문법에는 안전 호출 버전(`f?(x)` 같은 것)이 없다 — nullable 함수는 반드시 `?.invoke`로 불러야 한다. 이것이 `invoke`가 그냥 메서드라는 사실(§8.3)의 실용적 귀결이다.

### 9.3 nullable 함수 타입과 SAM

nullable 함수 타입 파라미터에도 람다를 넘길 수 있고, `null`도 넘길 수 있다. 기본값과 결합해 "선택적 콜백"을 만드는 것이 흔한 API 패턴이다.

```kotlin
fun download(
    url: String,
    onProgress: ((Int) -> Unit)? = null,      // 선택적 콜백, 기본 null
    onDone: () -> Unit                          // 필수 콜백
) {
    onProgress?.invoke(0)
    // ... 다운로드 ...
    onProgress?.invoke(100)
    onDone()
}

download("http://x") { println("완료") }         // onProgress 생략, onDone은 후행 람다
download("http://y", { println("$it%") }) { println("끝") }
```

주의: `onDone`이 마지막이라 후행 람다는 `onDone`에 붙는다. `onProgress`를 후행으로 쓸 수는 없다(마지막이 아니므로, §5.3).

## 10. 수신 객체 지정 함수 타입 `A.() -> B`

### 10.1 점 하나가 바꾸는 것

함수 타입 앞에 `수신타입.`을 붙이면 **수신 객체 지정 함수 타입(function type with receiver)** 이 된다. `A.() -> B`는 "A를 수신 객체로 삼아 실행되고 B를 반환하는 함수"다. 결정적 차이: 함수 본문 안에서 그 A 인스턴스가 **`this`가 되어**, 멤버를 수신자 없이 부를 수 있다.

```kotlin
// 일반 함수 타입: 수신자를 파라미터로 받음
val f1: (StringBuilder) -> Unit = { sb -> sb.append("x") }

// 수신 함수 타입: 수신자가 this가 됨
val f2: StringBuilder.() -> Unit = { append("x") }   // this.append("x"), this 생략

val sb = StringBuilder()
f1(sb)                 // 파라미터로 전달
sb.f2()                // 확장 함수처럼 호출! (또는 f2(sb)도 가능)
sb.toString()          // => "xx"
```

`f2` 안에서 `append`는 `this.append`이며, 여기서 `this`는 `f2`가 실행되는 수신 객체다. 즉 `StringBuilder.() -> Unit`은 "StringBuilder에 대한 임시 확장 함수"처럼 행동한다([[35 - 확장 함수와 프로퍼티]]와 같은 원리).

### 10.2 왜 이것이 DSL의 토대인가

수신 함수 타입 덕분에, 람다 블록 *안에서 마치 그 객체의 내부인 것처럼* 코드를 쓸 수 있다. 이것이 빌더 패턴과 DSL을 자연스럽게 만든다.

```kotlin
class HtmlTag(val name: String) {
    val children = mutableListOf<HtmlTag>()
    fun tag(name: String, init: HtmlTag.() -> Unit) {
        val child = HtmlTag(name)
        child.init()                 // 자식을 수신자로 삼아 init 실행
        children.add(child)
    }
    override fun toString(): String =
        "<$name>${children.joinToString("")}</$name>"
}

fun html(init: HtmlTag.() -> Unit): HtmlTag {
    val root = HtmlTag("html")
    root.init()                      // root를 this로 삼아 실행
    return root
}

val page = html {                    // 이 블록 안에서 this = root HtmlTag
    tag("body") {                    // this.tag(...), this = root
        tag("p") { }                 // 이 블록 안에서 this = body 태그
    }
}
page.toString()   // => <html><body><p></p></body></html>
```

`html { ... }` 블록 안의 `tag("body") { ... }`는 사실 `this.tag(...)` 호출이고, 그 `this`는 루트 태그다. 수신 함수 타입이 없다면 이 코드는 `html { root -> root.tag(...) }`처럼 수신자를 명시적으로 넘겨야 해 훨씬 지저분하다. 이 관용구의 전모 — `@DslMarker`로 중첩 수신자 스코프를 통제하는 법까지 — 는 [[37 - 타입 안전 빌더와 DSL]]가 소유하고, 스코프 함수(`apply`/`with`/`run`)가 어떻게 이 타입으로 지어졌는지는 [[16 - 스코프 함수와 수신 객체 관용구]]가 다룬다.

### 10.3 수신 함수 타입의 정체: 사실은 일반 함수 타입

JVM 표현 수준(§8)에서 `A.() -> B`는 **`(A) -> B`, 즉 `Function1<A, B>`와 같은 구조**로 컴파일된다. 수신자가 그저 첫 파라미터로 자리를 옮긴 것뿐이다. 그래서 코틀린은 이 둘을 문맥에 따라 서로 바꿔 쓸 수 있게 해 준다.

```kotlin
val withReceiver: StringBuilder.() -> Unit = { append("!") }
val asParam: (StringBuilder) -> Unit = withReceiver          // 변환 가능

val sb = StringBuilder("hi")
asParam(sb)            // 파라미터 스타일 호출
sb.toString()          // => "hi!"
```

"수신자냐 파라미터냐"는 *호출 문법과 본문 안 this 접근*의 차이일 뿐, 런타임 구조는 같다. 이 사실은 §2.2의 "함수 타입 동일성은 파라미터·반환·수신·suspend로 결정된다"는 명제와 맞물린다 — 수신자는 타입 시스템 상에서는 구별되지만 백엔드에서는 첫 파라미터로 접힌다.

> **명세 정밀**: `A.() -> B`와 `(A) -> B`는 타입 시스템 수준에서는 *구별되는* 타입이다(호출 관례가 다르므로). 하지만 컴파일러는 둘 사이의 암시적 변환을 허용하며, JVM 백엔드에서는 동일한 `Function1<A, B>`로 표현된다. 따라서 "수신 함수 타입은 새 종류의 런타임 실체를 만들지 않는다"가 정확한 서술이다.

### 10.4 suspend 함수 타입 — 예고편

함수 타입 앞에 `suspend`를 붙이면 `suspend () -> Unit`처럼 **중단 가능한 함수 타입**이 된다. 이것은 코루틴 빌더가 받는 람다의 타입이며, `suspend`가 타입 시스템에 나타나는 방식이다(M33/M34). 이 타입의 값은 컴파일러가 `Continuation` 파라미터를 몰래 추가한 CPS 형태로 변환하지만 — 그 상세는 [[42 - suspend와 코루틴 - 언어 수준의 중단]]와 코루틴 자매 시리즈의 CPS·상태 기계 장이 소유한다. 여기서는 "함수 타입에 `suspend`라는 변조자가 하나 더 있다"는 사실, 그리고 그것이 §2.2에서 함수 타입 동일성의 결정 요소로 언급된 이유만 확인한다.

```kotlin
val block: suspend () -> Int = { /* 중단 가능한 본문 */ 42 }
// 이 block은 일반 () -> Int 자리에 넣을 수 없다: suspend가 타입의 일부
```

---

일급 함수라는 한 줄의 약속에서 시작해, 우리는 함수 타입이 사실은 `FunctionN` 인터페이스의 표기이고(§2), 람다와 익명 함수가 그 인터페이스의 인스턴스를 만드는 두 리터럴이며(§3·§6), `it`이 마법이 아니라 단일 파라미터의 관례적 이름일 뿐임(§4, M42)을 확인했다. 후행 람다는 함수 호출을 제어 구문처럼 보이게 하는 문법의 결이었고(§5), 함수 참조는 이름 있는 함수를 네 갈래로 값으로 승격시키는 다리였다(§7). 그 모든 값이 JVM에서는 `invoke`를 가진 객체가 되며(§8), SAM 변환과 `fun interface`가 자바와의 경계를 잇고, nullable 함수 타입(§9)과 수신 함수 타입(§10)이 이 체계의 마지막 두 조각이었다. 이 장은 함수가 값이 되는 *지점*을 놓았다 — 그 값이 바깥 변수를 어떻게 붙잡는가([[14 - 클로저와 캡처]]), 그 값을 넘길 때 할당을 어떻게 없애는가([[15 - 인라인 함수와 reified]]), 그리고 수신 함수 타입으로 무엇을 짓는가([[16 - 스코프 함수와 수신 객체 관용구]], [[37 - 타입 안전 빌더와 DSL]])는 이제 열린 문 너머의 다음 장들이다.

## 핵심 요약

- **함수는 코틀린에서 일급 값이다.** 변수에 담고, 인자로 넘기고, 반환하고, 컬렉션에 넣을 수 있다. 함수를 인자로 받거나 반환하는 함수를 고차 함수라 부르며, 표준 라이브러리의 관용적 표면 대부분이 이 위에 서 있다.
- **함수 타입 `(A) -> B`는 새 종류의 타입이 아니라 `Function1<A, B>` 인터페이스의 표기다.** 아리티별로 `Function0`~`Function22`가 선언돼 있고(23개 이상은 특수 `FunctionN`), 각각 딱 하나의 `invoke` 연산자 메서드를 가진다. 그래서 함수 타입을 클래스로 손수 구현할 수도 있다.
- **함수 타입은 파라미터에 반공변(`in`), 반환에 공변(`out`)이다.** `(Animal) -> Dog`는 `(Cat) -> Animal`의 하위타입 — "인자는 넓게, 결과는 좁게"라는 안전 규칙의 교과서 사례다(변성은 [[33 - 제네릭 1 - 타입 파라미터와 변성]]).
- **람다 `{ ... }`와 익명 함수 `fun(...) { ... }`는 함수 값을 만드는 두 리터럴이며, `return`의 목적지가 다르다.** 람다의 벌거벗은 `return`은 바깥 함수를 벗어나려는 비지역 반환으로 인라인에서만 허용되고(M41, [[15 - 인라인 함수와 reified]]), 익명 함수의 `return`은 자기 자신만 벗어난다. 람다만 벗어나려면 `return@label`.
- **`it`은 파라미터가 정확히 하나인 람다에서 그 유일 파라미터를 이름 짓지 않았을 때의 암시적 이름일 뿐이다(M42).** 키워드도, 편재하는 마법도 아니다. 파라미터가 없거나 둘 이상이거나 익명 함수이거나 기대 타입이 없으면 `it`은 존재하지 않으며, 중첩 람다에서는 안쪽 `it`이 바깥 `it`을 가린다.
- **후행 람다 관례는 마지막 인자가 함수 타입일 때만 성립한다.** 그래서 API는 함수 파라미터를 관례적으로 마지막에 둔다. 이 관례가 함수 호출을 언어 내장 제어 구문처럼 보이게 하며 DSL의 문법적 토대가 된다.
- **함수 참조 `::`는 네 갈래다.** `::foo`(최상위/지역), `Class::m`(언바운드, 수신자가 첫 파라미터로 승격), `obj::m`(바운드, 수신자를 캡처해 파라미터에서 제거), `::Class`(생성자). 참조는 함수 타입 값인 동시에 `KFunction`/`KProperty` 리플렉션 핸들이기도 하다([[44 - 애노테이션과 리플렉션]]).
- **`f(x)`는 `f.invoke(x)`의 설탕이다(M40, [[19 - 연산자 오버로딩과 관례]]).** `operator fun invoke`를 아무 객체에 정의하면 함수 타입이 아니어도 호출 가능해지고, nullable 함수는 반드시 `f?.invoke(x)`로 안전 호출해야 한다(`f?(x)` 문법은 없다).
- **JVM 백엔드에서 람다는 `FunctionN`을 구현한 객체가 되며, 캡처 없는 람다는 싱글턴으로 최적화될 수 있다.** 캡처 람다는 매번 새 객체다. 이 할당 비용이 고차 함수를 `inline`으로 만드는 동기이며(JS/Native는 표현이 다름), 정확한 컴파일 형태는 버전·옵션(예: `-Xlambdas=indy`)에 따른다.
- **SAM 변환은 기본적으로 자바 SAM 인터페이스에만 자동 적용되고, 코틀린 일반 인터페이스에는 적용되지 않는다.** 코틀린 인터페이스에 람다를 넘기려면 `fun interface`로 선언해 SAM 변환을 옵트인해야 한다([[25 - 인터페이스]], [[45 - Java 상호운용]]).
- **`A.() -> B` 수신 함수 타입은 본문 안에서 A를 `this`로 만든다.** 임시 확장 함수처럼 동작해 빌더·DSL·스코프 함수의 토대가 되지만, JVM에서는 `(A) -> B`와 같은 `Function1` 구조로 접히며 둘은 문맥상 서로 변환된다.

## 연결 노트

- [[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]] — 함수를 *선언·호출*하는 문법의 장. 이 장은 그 함수를 *값*으로 승격시키므로 직접적인 앞 장이다.
- [[14 - 클로저와 캡처]] — 람다가 바깥 변수를 붙잡는 메커니즘, 비지역 반환의 라벨 규칙, 바운드 참조가 캡처하는 것. 이 장의 함수 값이 "무엇을 기억하는가"를 소유한다.
- [[15 - 인라인 함수와 reified]] — 함수 값의 객체 할당을 제거하는 `inline`과 비지역 반환(M41)의 정밀한 규칙. §6·§8의 성능·`return` 논의가 이어진다.
- [[16 - 스코프 함수와 수신 객체 관용구]] — `let`/`apply`/`with`가 §10의 수신 함수 타입으로 지어진 관용구. `let`의 `it`이 §4 규칙의 실례다.
- [[37 - 타입 안전 빌더와 DSL]] — §10의 `A.() -> B`와 §5의 후행 람다가 만나 DSL이 되는 종착지. `@DslMarker`로 중첩 수신자를 통제한다.
- [[19 - 연산자 오버로딩과 관례]] — `f(x)`를 `f.invoke(x)`로 푸는 `invoke` 관례(M40)의 소유 장. §8.3의 근거.
- [[25 - 인터페이스]] — `fun interface`(functional interface)와 SAM 변환(§8.5)의 소유 장.
- [[33 - 제네릭 1 - 타입 파라미터와 변성]] — 함수 타입의 반공변 파라미터·공변 반환(§2.3)이 변성 규칙의 대표 사례다.
- [[45 - Java 상호운용]] — 자바 SAM 인터페이스로의 자동 변환(§8.5)과 함수 타입의 자바 노출을 다룬다.
- [[42 - suspend와 코루틴 - 언어 수준의 중단]] — §10.4의 `suspend` 함수 타입이 CPS 변환으로 무엇이 되는지(M33/M34)를 소유한다.
