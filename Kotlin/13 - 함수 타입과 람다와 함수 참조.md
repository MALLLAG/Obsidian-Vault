[[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]에서는 함수를 *선언하고 호출하는* 문법을 살펴보았다. 파라미터가 어떻게 바인딩되는지, 기본 인자가 어떻게 오버로드를 대신하는지, `tailrec`가 어떤 조건에서 재귀를 반복문으로 바꾸는지까지 다루었다. 하지만 그 장에서 함수는 처음부터 끝까지 *호출하는 대상*이었다. 이름을 적고 괄호를 붙여 호출하는 정적인 대상이었던 것이다.

이 장에서는 함수를 변수에 담고, 인자로 넘기고, 반환값으로 돌려받는 *값*으로 다룬다. 함수가 데이터와 같은 지위를 얻으면 코틀린 표현력의 상당 부분이 여기서 나온다. 구체적으로는 함수를 담는 **함수 타입**(`(A) -> B`), 그 타입의 값을 즉석에서 만드는 **람다와 익명 함수**, 이미 이름이 있는 함수를 값으로 만드는 **함수 참조**(`::foo`)를 다루고, 이 값들이 JVM에서 어떻게 표현되는지도 살펴본다.

람다가 바깥 변수를 캡처하는 방식은 [[14 - 클로저와 캡처]]에서, `inline`과 비지역 반환의 세부 규칙, `reified`는 [[15 - 인라인 함수와 reified]]에서 다룬다. 수신 함수 타입 `A.() -> B`를 활용하는 스코프 함수(`apply`/`with`/`run`)와 DSL은 [[16 - 스코프 함수와 수신 객체 관용구]]와 [[37 - 타입 안전 빌더와 DSL]]에서 설명한다.

## 1. 일급 함수: 값이 된 함수

### 1.1 "일급"이 되기 위한 조건

어떤 언어에서 값이 **일급(first-class)** 시민이라는 말은 그 값으로 다음 일을 모두 할 수 있다는 뜻이다. 변수에 담을 수 있고, 함수의 인자로 넘길 수 있고, 함수의 반환값으로 돌려받을 수 있고, 리스트나 맵 같은 자료구조에 넣을 수 있고, 런타임에 만들 수 있다. 정수 `3`이나 문자열 `"cat"`은 당연히 일급이다. 코틀린에서는 *함수도* 이 조건을 모두 갖춘다.

```kotlin
// 변수에 담기
val square: (Int) -> Int = { n -> n * n }

// 인자로 넘기기
fun apply2(x: Int, f: (Int) -> Int): Int = f(f(x))
apply2(3, square)        // => 81  (3→9→81)

// 반환값으로 돌려받기
fun adder(base: Int): (Int) -> Int = { n -> n + base }
val add10 = adder(10)
add10(5)                 // => 15

// 자료구조에 넣기
val ops: List<(Int) -> Int> = listOf(square, add10, { it - 1 })
ops.map { op -> op(4) }  // => [16, 14, 3]
```

이 코드에서 `square`에는 이름이 있지만, 그 이름은 *변수 이름*이지 함수 선언의 이름이 아니다. `square`가 가리키는 것은 `(Int) -> Int` 타입의 **값**이다. 이 구분이 이 장 전체의 출발점이다. 코틀린에는 "함수 선언"(12장)과 "함수 값"이라는 두 세계가 함께 있고, 함수 참조(7절)가 둘을 연결한다.

### 1.2 언어가 일급 함수를 지원해야 하는 이유

일급 함수가 없다고 생각해 보자. "컬렉션의 각 원소에 어떤 연산을 적용한다"는 생각을 표현하려면 연산마다 함수를 따로 만들거나 커다란 `when`으로 분기해야 한다. 일급 함수가 있으면 *연산 자체*를 인자로 받는 `map` 하나로 충분하다.

[[39 - 컬렉션 연산과 함수형 파이프라인]]의 내용 전체가 이 능력을 바탕으로 한다. [[40 - 시퀀스와 지연 평가]], [[23 - 위임 프로퍼티]]의 `by lazy { ... }`, [[42 - suspend와 코루틴 - 언어 수준의 중단]]의 코루틴 빌더도 마찬가지다. 코틀린 표준 라이브러리에서 관용적으로 쓰는 API 대부분은 "함수를 인자로 받는 함수", 즉 **고차 함수**(higher-order function)로 만들어져 있다.

> [!info] 역사 메모
> 함수를 값으로 다루는 발상은 코틀린이 처음 만든 것이 아니다. 그 뿌리는 1930년대 알론조 처치의 **람다 계산법**(lambda calculus)이며, 람다 계산법에서는 애초에 *모든 것*이 함수다. Lisp(1958)가 이 발상을 실용 언어에 들여왔고, ML과 Haskell을 거쳐 주류 언어로 퍼졌다. 코틀린의 `{ ... }` 람다는 이 계보의 최신 후손이다.
>
> 이론적 배경이 궁금하다면 Type Theory 시리즈의 무타입 람다 계산 장을 참고하라. 다만 코틀린 람다는 순수 람다 계산과 달리 *타입이 붙어 있고*, 변수 변경이나 I/O 같은 부수 효과를 자유롭게 일으킬 수 있다.

### 1.3 고차 함수라는 용어

**고차 함수**는 다음 두 조건 중 하나 이상을 만족하는 함수다. 하나는 함수를 인자로 받는 것이고, 다른 하나는 함수를 반환하는 것이다. 위의 `apply2`는 앞의 조건을, `adder`는 뒤의 조건을 만족하고, 표준 라이브러리의 `fold`는 둘 다 만족한다.

이 장의 나머지 부분에서는 "고차 함수에 넘길 값을 어떻게 만들고, 그 값의 정체는 무엇인가"를 살펴본다. 함수를 넘길 때 생기는 성능 비용(객체 할당)과 그 비용을 없애는 `inline`은 15장에서 다룬다. 여기서는 "함수 값은 대개 객체 하나를 만든다"는 사실만 기억해 두자(8절에서 자세히 설명한다).

## 2. 함수 타입의 문법과 구조

### 2.1 기본 문법

함수 타입은 **파라미터 타입 목록**을 괄호로 감싼 뒤 화살표 `->`와 **반환 타입**을 적어서 만든다.

```kotlin
val f0: () -> Unit                 // 인자 없음, Unit 반환
val f1: (Int) -> String            // Int 하나 받고 String 반환
val f2: (Int, Int) -> Int          // Int 둘 받고 Int 반환
val f3: (String, Int, Boolean) -> Double
```

몇 가지 규칙을 정리해 두자.

- **파라미터가 없어도 괄호는 필수다**: `() -> Unit`. 파라미터가 하나일 때도 괄호가 필요하다: `(Int) -> String`. 자바스크립트의 `x => ...`처럼 괄호를 생략하는 문법은 없다.
- **반환 타입은 생략할 수 없다**: 값을 돌려주지 않으면 `Unit`을 명시해야 한다. `(Int) ->` 같은 표기는 없다. `Unit`이 실제 타입이라는 사실은 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서 다루었는데, 함수 타입에서 그 의미가 분명하게 드러난다.
- **화살표는 오른쪽으로 결합한다**: `(Int) -> (Int) -> Int`는 "Int를 받아서, (Int를 받아 Int를 반환하는 함수)를 반환하는 함수"다. 커링(currying)을 표현할 때 이 결합 방향이 중요하다.

```kotlin
// 오른쪽 결합: (Int) -> ((Int) -> Int)
val curriedAdd: (Int) -> (Int) -> Int = { a -> { b -> a + b } }
curriedAdd(3)(4)     // => 7
```

### 2.2 파라미터 이름은 문서 역할만 한다

함수 타입 안의 파라미터에 이름을 붙일 수 있지만, 그 이름은 **가독성을 위한 주석**일 뿐 타입이 같은지를 판단하는 데는 영향을 주지 않는다.

```kotlin
val withNames: (radius: Double, height: Double) -> Double = { r, h -> Math.PI * r * r * h }
val without:   (Double, Double) -> Double = withNames   // OK: 같은 타입
```

이 이름은 IDE 힌트와 문서에만 쓰인다. 호출할 때 그 이름으로 인자를 지정할 수는 *없다*. 이름 붙은 인자(12장)는 함수 *선언*을 호출할 때만 동작하고, 함수 *타입을 통해 호출*할 때는 위치 기반 인자만 쓸 수 있다.

```kotlin
val volume: (radius: Double, height: Double) -> Double = { r, h -> Math.PI * r * r * h }
volume(radius = 2.0, height = 5.0)   // 컴파일 에러: 함수 타입 호출엔 이름 붙은 인자 불가
volume(2.0, 5.0)                     // => 62.83...
```

> [!note] 명세 기준
> 함수 타입의 파라미터 이름이 타입에 아무 의미가 없다는 것은, 두 함수 타입의 하위 타입 관계와 동일성이 오직 파라미터 타입들, 반환 타입, 수신 타입, 그리고 `suspend` 여부로만 결정된다는 뜻이다. 이 점은 10절의 수신 함수 타입과 8절의 JVM 표현을 이해하는 데 중요하다.

### 2.3 함수 타입은 사실 인터페이스다

이 장에서 처음 만나는 중요한 사실이 여기에 있다. `(Int) -> String`은 **새로운 종류의 타입이 아니다**. 이것은 표준 라이브러리에 선언된 제네릭 인터페이스 `Function1<in P1, out R>`을 다르게 표기한 것이다. 즉 `(Int) -> String`은 `Function1<Int, String>`과 같은 타입이다. 코틀린 표준 라이브러리는 아리티(arity, 파라미터 개수)별로 인터페이스를 미리 선언해 둔다.

```text
Function0<R>                       ≡  () -> R
Function1<P1, R>                    ≡  (P1) -> R
Function2<P1, P2, R>               ≡  (P1, P2) -> R
...
Function22<P1, ..., P22, R>        ≡  (P1, ..., P22) -> R
```

이 인터페이스들(JVM 백엔드에서는 `kotlin.jvm.functions` 패키지에 있다)은 각각 추상 메서드 `invoke`를 딱 하나씩 가진다.

```kotlin
public interface Function1<in P1, out R> : Function<R> {
    public operator fun invoke(p1: P1): R
}
```

`invoke`에 `operator` 키워드(8절, [[19 - 연산자 오버로딩과 관례]])가 붙어 있기 때문에 `f(x)`라는 호출 문법이 `f.invoke(x)`로 풀린다. 이것이 8절에서 자세히 설명할 핵심 사실이다. 그리고 이 구조가 **변성**(variance, [[33 - 제네릭 1 - 타입 파라미터와 변성]])의 대표적인 예라는 점도 지금 기억해 두자. 파라미터 타입은 `in`(반공변)이고, 반환 타입은 `out`(공변)이다.

$$\text{Function1}\langle \text{in } P_1,\ \text{out } R\rangle$$

이 변성에서 함수 타입의 하위 타입 규칙이 나온다. **"인자는 넓게 받고, 결과는 좁게 준다"** 는 규칙이다. 즉 `(Animal) -> Dog`는 `(Cat) -> Animal`의 하위 타입이다(Cat ⊂ Animal, Dog ⊂ Animal). 아래 코드에서 직접 확인해 보자.

```kotlin
open class Animal
class Cat : Animal()
class Dog : Animal()

val specific: (Animal) -> Dog = { Dog() }     // 아무 Animal 받고 Dog 반환
val general: (Cat) -> Animal = specific        // OK! 반공변 인자 + 공변 반환
// specific은 Animal을 받으니 Cat(Animal의 하위)도 당연히 받을 수 있고,
// Dog를 주니 Animal 자리에 넣어도 안전하다.
```

> [!warning] 흔한 오해
> "함수 타입은 코틀린 컴파일러가 특별하게 취급하는 마법 같은 타입"이라고 오해하기 쉽다. 사실 함수 타입은 *문법적 설탕*일 뿐이고, 그 아래에는 평범한 제네릭 인터페이스가 있다. 그래서 함수 타입을 **직접 구현**할 수도 있다(2.4절). 다만 파라미터가 22개를 넘으면 특수한 인터페이스가 쓰인다(8.4절).

### 2.4 함수 타입을 직접 구현하기

함수 타입은 인터페이스이므로 클래스로 직접 구현할 수 있다. 이 예를 보면 "람다는 결국 이 인터페이스의 인스턴스"라는 8절의 설명을 미리 이해할 수 있다.

```kotlin
class Multiplier(val factor: Int) : (Int) -> Int {
    override fun invoke(p1: Int): Int = p1 * factor
}

val triple: (Int) -> Int = Multiplier(3)
triple(5)          // => 15  (triple.invoke(5))
listOf(1, 2, 3).map(triple)   // => [3, 6, 9]
```

`Multiplier`는 이름이 있는 클래스이고, 상태(`factor`)를 가지며, 함수 타입을 구현한다. 이 예에서 함수 값과 객체의 경계가 매우 얇다는 것을 알 수 있다. 람다는 이런 클래스를 컴파일러가 자동으로 만들어 준 것에 지나지 않는다.

### 2.5 typealias로 함수 타입에 이름 붙이기

긴 함수 타입이 반복되면 읽기 어렵다. 이럴 때는 [[36 - 타입 별칭과 인라인 value class]]에서 자세히 다룰 `typealias`로 별칭을 붙일 수 있다.

```kotlin
typealias IntPredicate = (Int) -> Boolean
typealias Reducer<T> = (acc: T, item: T) -> T

val isEven: IntPredicate = { it % 2 == 0 }
val sum: Reducer<Int> = { a, b -> a + b }
```

`IntPredicate`는 **새 타입이 아니라 별칭**이다. `(Int) -> Boolean`을 기대하는 자리에 `IntPredicate` 값을 자유롭게 넘길 수 있고, 그 반대도 가능하다. 컴파일러에게 둘은 *같은 타입*이기 때문이다. 이 성질은 7절의 함수 참조와 함께 쓸 때 편리하다.

## 3. 람다 표현식: 함수 값을 만드는 리터럴

### 3.1 문법의 구성

람다는 함수 타입의 값을 즉석에서 만드는 **리터럴**이다. 정수 리터럴 `42`가 `Int` 값을 만드는 것처럼, 람다 리터럴 `{ ... }`는 함수 값을 만든다. 전체 문법은 다음과 같다.

```kotlin
val f = { x: Int, y: Int -> x + y }
//      └┬┘ └──────┬──────┘ └──┬──┘
//     중괄호   파라미터 목록   본문(마지막 식이 반환값)
```

구성 요소를 하나씩 살펴보자.

- **중괄호 `{ }`는 필수다**. 람다는 항상 중괄호로 둘러싸인다.
- **파라미터 목록**은 괄호 *없이* 나열하고, `->`로 본문과 구분한다. 함수 타입 표기와 달리 람다 파라미터에는 괄호가 없다는 점에 유의하자.
- **본문**에는 여러 문장(statement)이 올 수 있고, **마지막 표현식이 반환값**이 된다. 따로 `return` 키워드를 쓰지 않는다(`return`의 의미는 6절에서 자세히 설명한다).

```kotlin
val describe = { n: Int ->
    val parity = if (n % 2 == 0) "짝수" else "홀수"
    val sign = if (n >= 0) "양수/영" else "음수"
    "$n 은 $parity 이고 $sign"        // 마지막 표현식 = 반환값
}
describe(-4)     // => "-4 은 짝수 이고 음수"
```

### 3.2 타입 추론의 두 방향

람다의 파라미터 타입은 **문맥의 기대 타입**(expected type)에서 추론할 수도 있고, 람다 안에서 **명시**할 수도 있다. 이 두 방향을 구분하지 못해 처음 배우는 사람이 자주 헷갈린다.

```kotlin
// 방향 A: 기대 타입이 있으면 파라미터 타입 생략 가능
val g: (Int) -> Int = { x -> x * 2 }      // x는 Int로 추론됨

// 방향 B: 기대 타입이 없으면 파라미터 타입 명시 필수
val h = { x: Int -> x * 2 }               // 타입 명시 → h: (Int) -> Int
val bad = { x -> x * 2 }                  // 컴파일 에러: x의 타입을 알 수 없음
```

`map`이나 `filter` 같은 고차 함수에 람다를 넘길 때는 함수 시그니처가 기대 타입을 알려 주므로, 파라미터 타입을 거의 항상 생략한다. 코틀린 람다가 그렇게 간결해 보이는 이유가 여기에 있다.

```kotlin
listOf(1, 2, 3, 4).filter { x -> x % 2 == 0 }   // filter의 시그니처가 x: Int를 알려줌
// => [2, 4]
```

**반환 타입**도 마찬가지로 마지막 표현식에서 추론한다. 람다에는 반환 타입을 명시하는 문법이 없다. 이것이 람다가 익명 함수와 달라지는 첫 번째 지점이다(6절).

### 3.3 파라미터가 없는 람다와 여러 개인 람다

```kotlin
val noArg: () -> String = { "결과" }              // 파라미터 없음: -> 도 없음
val twoArg: (Int, Int) -> Int = { a, b -> a + b } // 둘 이상: 콤마로 나열
```

파라미터가 하나도 없으면 `->`까지 생략한다(`{ "결과" }`). 파라미터가 하나이면 `it`으로 줄여 쓸 수 있는데(4절), 여기서 흔한 오해가 생긴다.

### 3.4 구조 분해와 밑줄

람다 파라미터는 [[20 - 구조 분해]]로 분해할 수 있다. `Pair`, `Map.Entry`, 데이터 클래스처럼 `componentN`을 가진 값이 파라미터로 들어올 때 유용하다.

```kotlin
val points = listOf(1 to "one", 2 to "two", 3 to "three")
points.map { (num, name) -> "$num=$name" }
// => [1=one, 2=two, 3=three]

// 안 쓰는 성분은 밑줄로 무시
points.forEach { (num, _) -> print(num) }   // 123
```

구조 분해 파라미터는 괄호로 감싼다는 점에 유의하라: `{ (num, name) -> ... }`. 괄호 없이 `{ num, name -> ... }`라고 쓰면 "파라미터 두 개"라는 뜻이 되고, "Pair 하나를 분해한다"는 뜻이 되지 않는다. 이 문법적 함정은 5절의 후행 람다와 함께 쓸 때 특히 헷갈린다.

> [!note] 명세 기준
> 람다에서 `(a, b)` 구조 분해는 *위치 기반*이다. `componentN()`이 반환하는 순서대로 대응되며, 이름에는 아무 의미가 없다. 데이터 클래스의 프로퍼티 이름과 분해 변수 이름이 같을 필요가 없고, 순서만 맞으면 된다. 이 함정은 20장에서 자세히 다룬다.

## 4. `it`: 파라미터가 하나인 람다의 암시적 이름

### 4.1 오해: "`it`은 어디서나 쓸 수 있다"

처음 배우는 사람은 `it`을 "코틀린 어디에서나 현재 값을 가리키는 마법 키워드"로 오해하기 쉽다. 이것은 틀린 생각이다. **`it`은 파라미터가 정확히 하나인 람다에서 그 파라미터에 이름을 붙이지 않았을 때, 컴파일러가 붙여 주는 암시적 이름일 뿐이다.** 키워드도 아니고, 어디서나 유효한 무언가도 아니다.

```kotlin
listOf(1, 2, 3).map { it * 2 }      // it = 유일한 파라미터. { n -> n * 2 } 와 동일
// => [2, 4, 6]
```

`{ it * 2 }`는 `{ it: Int -> it * 2 }`와 같은 특별한 형태가 아니다. `{ n -> n * 2 }`에서 `n`이라는 이름을 짓지 않고 관례적인 이름 `it`을 쓴 것뿐이다. `it`의 한계는 모두 이 사실에서 나온다.

### 4.2 `it`을 쓸 수 없는 경우

**(1) 파라미터가 둘 이상이면 `it`이 없다.** 파라미터가 여러 개이면 반드시 이름을 지어야 한다.

```kotlin
val add: (Int, Int) -> Int = { a, b -> a + b }
val bad: (Int, Int) -> Int = { it + it }    // 컴파일 에러: it은 다중 파라미터에 없음
```

**(2) 파라미터가 아예 없으면 `it`도 없다.**

```kotlin
val supplier: () -> Int = { it }            // 컴파일 에러: 파라미터가 없어 it도 없음
```

**(3) 익명 함수에는 `it`이 없다.** `it`은 람다 문법에만 있다(6절).

```kotlin
val square = fun(x: Int): Int = it * it     // 컴파일 에러: 익명 함수엔 it 없음
```

**(4) 스코프 함수의 `it`도 결국 람다 파라미터다.** `let`이나 `also`의 `it`은 특별해 보이지만, `let`이 `(T) -> R` 타입의 람다를 받고 그 유일한 파라미터가 `it`이라는 이름으로 드러날 뿐이다(16장). 마법이 아니라 4.1절의 규칙이 그대로 적용된 것이다.

```kotlin
val name: String? = "Fido"
name?.let { println("이름: $it") }    // it = let에 넘긴 람다의 유일 파라미터(String)
```

### 4.3 중첩 람다에서 `it`이 가려지는 문제

`it`이 "유일한 파라미터의 이름"이라는 정의에 따르면, 람다가 **중첩**될 때 결과가 분명해진다. 안쪽 람다의 `it`이 바깥 람다의 `it`을 **가린다**(shadow). 즉 안쪽에서 `it`이라고 쓰면 항상 *가장 가까운* 람다의 파라미터를 가리킨다.

```kotlin
val matrix = listOf(listOf(1, 2), listOf(3, 4))
matrix.map { row ->
    row.map { it * 10 }          // 여기 it = 안쪽 원소(Int). 바깥 row가 아님
}
// => [[10, 20], [30, 40]]

// 만약 두 층 다 it을 쓰면 바깥 it에 접근 불가
matrix.map {
    it.map { it * 10 }           // 바깥 it(List)과 안쪽 it(Int)이 겹침 — 바깥 it은 여기서 못 씀
}
```

두 번째 예는 컴파일은 되지만, 안쪽에서 바깥 리스트를 참조할 방법이 없어진다. 그래서 **람다가 중첩되면 이름을 지으라**는 관례가 생겼다. `it`은 편의를 위한 것이지 반드시 따라야 하는 규칙이 아니다.

> [!caution] 성능 주의
> `it`을 쓰든 이름을 짓든 컴파일 결과는 완전히 같다. `it`은 순수한 문법 축약이라 런타임 비용이 전혀 없다. 따라서 성능 때문에 `it`을 피할 이유는 없고, 오직 *가독성*만 판단 기준이 된다. 파라미터가 하나이고 의미가 분명하면 `it`을 쓰고, 문맥이 복잡하거나 람다가 중첩되면 이름을 짓는다.

### 4.4 `it`의 타입은 어디서 오는가

`it`의 타입도 3.2절의 추론 규칙으로 정해진다. 따라서 기대 타입이 있어야 `it`을 쓸 수 있다.

```kotlin
val f: (String) -> Int = { it.length }   // it: String (기대 타입에서)
val g = { it * 2 }                        // 컴파일 에러: 기대 타입 없음 → it 타입 미상
```

즉 `it`은 "기대 타입이 함수 타입이고 그 아리티가 1일 때"에만 쓸 수 있다. 이 조건이 앞의 오해를 정확히 반박한다. `it`은 특정한 문법 조건과 타입 조건에서만 존재하는 편의 기능이고, 어디에나 있는 마법이 아니다.

## 5. 후행 람다: 문법을 다듬는 관례

### 5.1 규칙: 마지막 인자가 함수이면 괄호 밖으로 뺄 수 있다

고차 함수의 **마지막 파라미터가 함수 타입**이면, 그 자리에 넘길 람다를 인자 괄호 *바깥*에 쓸 수 있다. 이것을 **후행 람다(trailing lambda)** 라고 한다.

```kotlin
fun repeatAction(times: Int, action: (Int) -> Unit) {
    for (i in 0 until times) action(i)
}

// 정석: 람다가 괄호 안
repeatAction(3, { i -> println(i) })

// 후행 람다: 마지막 함수 인자를 괄호 밖으로
repeatAction(3) { i -> println(i) }        // 동일한 호출

// 함수가 유일한 인자면 괄호 자체를 생략
listOf(1, 2, 3).forEach { println(it) }    // forEach(f)에서 () 생략
```

이 관례 덕분에 코틀린 코드는 언어에 내장된 제어 구문처럼 보인다. `repeatAction(3) { ... }`은 `for` 문처럼 보이지만 실제로는 평범한 함수 호출이다. 37장(타입 안전 빌더와 DSL)에서 다루는 기법도 모두 이 관례에서 출발한다.

### 5.2 후행 람다와 다른 인자를 함께 쓰기

후행으로 뺄 수 있는 것은 마지막 인자뿐이다. 나머지 인자는 괄호 안에 남는다.

```kotlin
fun <T, R> transform(input: T, times: Int, mapper: (T) -> R): List<R> {
    return List(times) { mapper(input) }
}

transform("x", 3) { it.uppercase() }       // input="x", times=3, mapper는 후행
// => [X, X, X]
```

함수 타입 파라미터가 마지막이 아니면 후행 람다를 쓸 수 없고, 람다를 괄호 안에 넣어야 한다. 그래서 API를 설계할 때는 **관례적으로 함수 파라미터를 마지막에 둔다**. 표준 라이브러리의 `map`, `filter`, `fold`가 모두 그렇다. `fold`처럼 초기값과 함수를 함께 받을 때 함수를 뒤에 두는 것도 후행 람다를 쓸 수 있게 하기 위해서다.

```kotlin
listOf(1, 2, 3, 4).fold(0) { acc, x -> acc + x }   // 초기값 0, 함수는 후행
// => 10
```

### 5.3 후행 람다의 함정: 마지막 인자가 함수여야 한다

후행 람다는 *마지막 파라미터가 함수 타입일 때만* 쓸 수 있다. 이 점을 잊으면 이해하기 어려운 에러를 보게 된다.

```kotlin
fun log(action: (String) -> String, tag: String) { /* ... */ }

log({ it.uppercase() }, "TAG")             // OK: 람다가 괄호 안 (함수가 첫 인자라)
log("TAG") { it.uppercase() }              // 컴파일 에러: 후행 람다는 마지막 인자에만
```

한 가지 더 알아 둘 점이 있다. 함수를 받는 파라미터가 nullable이거나 기본값이 있어도 후행 람다는 그대로 동작한다. 마지막 위치이기만 하면 된다.

### 5.4 빈 후행 람다와 람다 두 개

파라미터가 없는 함수 타입이면 `{ }`만으로 후행 람다를 쓸 수 있다. 함수 타입 파라미터가 두 개이면 그중 마지막 것 하나만 후행으로 뺄 수 있다.

```kotlin
fun onResult(onSuccess: () -> Unit, onFailure: () -> Unit) { /* ... */ }

onResult({ println("성공") }) { println("실패") }
// onSuccess는 괄호 안, onFailure(마지막)만 후행
```

두 람다를 모두 후행 람다로 쓰는 문법은 없다. 이런 경우에는 가독성을 위해 두 람다를 모두 괄호 안에 이름 붙은 인자로 넣거나, `fun interface`(8.5절)로 콜백을 묶는 설계를 택한다.

## 6. 익명 함수: 람다와 비슷한 또 하나의 리터럴

### 6.1 두 번째 리터럴이 필요한 이유

코틀린에는 함수 값을 만드는 리터럴이 *두 가지* 있다. 하나는 람다(3절)이고, 다른 하나는 **익명 함수(anonymous function)** 다. 익명 함수는 `fun` 키워드를 쓰되 이름을 생략한 형태다.

```kotlin
val square = fun(x: Int): Int { return x * x }
val squareExpr = fun(x: Int) = x * x        // 단일 표현식 형태

square(5)        // => 25
```

겉보기에는 람다를 길게 쓴 것 같지만, 익명 함수에는 람다가 하지 못하는 일이 두 가지 있다. **반환 타입을 명시**할 수 있고, **`return`이 일반 함수처럼 동작**한다. 이 두 가지 때문에 익명 함수가 따로 존재한다.

### 6.2 차이 1: 반환 타입 명시

람다는 반환 타입을 마지막 표현식에서 추론할 수밖에 없다. 반면 익명 함수는 반환 타입을 *명시*할 수 있으므로, 본문이 복잡해서 타입을 확실히 정해 두고 싶을 때 유용하다.

```kotlin
// 람다: 반환 타입 추론만 가능
val parse1 = { s: String -> s.toIntOrNull() ?: 0 }   // (String) -> Int로 추론

// 익명 함수: 반환 타입 명시
val parse2 = fun(s: String): Number {
    return s.toDoubleOrNull() ?: s.toIntOrNull() ?: 0
}
```

### 6.3 차이 2: `return`의 의미

이것이 가장 중요한 차이다. **람다 안의 `return`과 익명 함수 안의 `return`은 서로 다른 곳으로 돌아간다.**

- **익명 함수의 `return`**: 그 익명 함수 자신에서 반환한다. 직관적으로 이해할 수 있다.
- **람다의 라벨 없는 `return`**: 람다를 감싼 *바깥 함수*에서 반환하려는 시도다. 이것을 **비지역 반환(non-local return)** 이라고 하며, `inline` 함수에 넘긴 람다에서만 허용된다. 인라인이 아니면 컴파일 에러가 나고, 람다만 벗어나려면 라벨을 붙인 `return@label`을 써야 한다.

```kotlin
fun findFirstEven(nums: List<Int>): Int? {
    // 익명 함수의 return은 익명 함수만 벗어남 → forEach를 못 멈춤
    nums.forEach(fun(n) {
        if (n % 2 == 0) return       // 이 익명 함수에서만 반환, 루프 계속
    })
    return null
}
```

반면 람다에서는 다음과 같이 동작한다.

```kotlin
fun findFirstEven(nums: List<Int>): Int? {
    nums.forEach { n ->
        if (n % 2 == 0) return n     // 비지역 반환: findFirstEven에서 반환!
    }                                // forEach가 inline이라 허용됨
    return null
}
findFirstEven(listOf(1, 3, 4, 5))    // => 4
```

`forEach`가 `inline`(15장)이기 때문에 람다의 `return n`은 바깥 함수 `findFirstEven`을 곧바로 벗어난다. `forEach`가 인라인이 아니었다면 `return n`은 컴파일 에러가 났을 것이다. 비지역 반환의 자세한 규칙, 즉 왜 인라인에서만 허용되는지와 `crossinline`이 왜 그것을 막는지는 14장과 15장에서 다룬다. 여기서는 "리터럴 종류에 따라 `return`이 돌아가는 곳이 다르다"는 사실만 확인해 둔다.

### 6.4 라벨 반환: 람다에서 람다만 벗어나기

인라인이든 아니든 람다에서 *람다만* 벗어나고 싶으면 라벨을 쓴다. 람다를 넘긴 함수의 이름이 자동으로 라벨이 되므로 `return@forEach`처럼 쓸 수 있다.

```kotlin
fun sumPositives(nums: List<Int>): Int {
    var sum = 0
    nums.forEach { n ->
        if (n < 0) return@forEach    // 이 반복만 건너뜀 (continue 같은 효과)
        sum += n
    }
    return sum
}
sumPositives(listOf(1, -2, 3, -4, 5))   // => 9
```

`return@forEach`는 람다의 현재 실행만 끝내고 `forEach`의 다음 원소로 넘어간다. 라벨을 직접 붙일 수도 있다: `nums.forEach loop@ { ... return@loop }`. 라벨 문법 전체는 14장(클로저와 캡처)에서 다룬다.

### 6.5 람다와 익명 함수 비교표

| 항목 | 람다 `{ ... }` | 익명 함수 `fun(...) { ... }` |
|------|----------------|------------------------------|
| 반환 타입 | 마지막 표현식에서 추론만 | 명시 가능 |
| `it` | 단일 파라미터 시 사용 가능 | 없음(파라미터 이름 필수) |
| 라벨 없는 `return` | 비지역 반환(인라인에서만) | 익명 함수 자신에서 반환 |
| 문법 간결성 | 매우 간결 | 다소 장황 |
| 후행 람다 | 가능 | 불가(괄호 안에 위치) |
| 파라미터 기본값 | 불가 | 불가 |

실무에서는 람다를 훨씬 많이 쓴다. 익명 함수는 반환 타입을 명시해야 할 때, `return`이 그 함수 안에서만 동작하기를 원할 때, 반환 지점이 여러 곳인 복잡한 콜백을 작성할 때 선택한다.

## 7. 함수 참조: 이름 있는 함수를 값으로 쓰기

### 7.1 참조가 필요한 이유

이미 선언된 함수를 고차 함수에 넘기려고 할 때 람다로 감싸면 코드가 길어진다.

```kotlin
fun isOdd(n: Int): Boolean = n % 2 == 1

listOf(1, 2, 3, 4).filter { isOdd(it) }   // 람다로 감쌈: 파라미터를 그대로 전달
listOf(1, 2, 3, 4).filter(::isOdd)         // 함수 참조: 더 간결
// 둘 다 => [1, 3]
```

`::isOdd`를 **함수 참조(function reference)** 라고 한다. 함수 참조는 `isOdd`라는 *선언*을 `(Int) -> Boolean` 타입의 *값*으로 바꾼다. `{ isOdd(it) }`와 `::isOdd`는 같은 타입의 값을 만들지만, 참조는 인자를 그대로 전달하기만 하는 얇은 껍데기이므로 의도가 더 분명하다. 함수 참조에는 네 가지 형태가 있다.

### 7.2 형태 1: 최상위 함수와 지역 함수 참조 `::foo`

가장 단순한 형태로, 최상위 함수나 지역 함수를 `::이름`으로 참조한다.

```kotlin
fun double(x: Int): Int = x * 2
fun greet(name: String): String = "안녕, $name"

val d: (Int) -> Int = ::double
val g: (String) -> String = ::greet
d(21)              // => 42
g("도형")          // => 안녕, 도형
```

오버로드가 있으면 어느 함수를 참조하는지 모호할 수 있다. 이때는 기대 타입으로 모호함을 해소한다.

```kotlin
fun area(r: Double): Double = Math.PI * r * r
fun area(w: Double, h: Double): Double = w * h

val circle: (Double) -> Double = ::area           // 첫 오버로드
val rect: (Double, Double) -> Double = ::area     // 둘째 오버로드
// 기대 타입이 어떤 area인지 결정한다
```

### 7.3 형태 2: 언바운드 멤버 참조 `Class::method`

멤버 함수를 *수신 객체 없이* 참조하면, **수신 객체가 첫 번째 파라미터가 된 함수 타입**이 만들어진다.

```kotlin
val lengths: (String) -> Int = String::length     // 수신자 String이 파라미터로
lengths("cat")     // => 3

listOf("a", "bb", "ccc").map(String::length)       // => [1, 2, 3]

// 메서드에 파라미터가 있으면 수신자 + 원래 파라미터
val prefixed: (String, String) -> Boolean = String::startsWith
prefixed("hello", "he")   // => true  ("hello".startsWith("he"))
```

`String::length`의 타입이 `(String) -> Int`라는 점에 주목하라. 프로퍼티도 사실은 게터 함수이므로 이렇게 참조할 수 있다([[22 - 프로퍼티와 백킹 필드]]). 언바운드 참조는 "이 클래스의 어느 인스턴스에나 적용할 연산"을 표현하기에 알맞다.

### 7.4 형태 3: 바운드 멤버 참조 `obj::method`

특정 *인스턴스*에 묶인 참조다. 수신 객체가 이미 정해져 있으므로 함수 타입에 수신자 파라미터가 나타나지 않는다.

```kotlin
val greeting = "안녕하세요"
val getLength: () -> Int = greeting::length       // greeting에 바운드
getLength()        // => 5 (한글 5자)

class Counter(var count: Int = 0) {
    fun increment(): Int = ++count
}
val c = Counter()
val inc: () -> Int = c::increment                  // c 인스턴스에 바운드
inc(); inc()       // c.count가 2가 됨
```

핵심은 언바운드 참조(`String::length`, 타입 `(String) -> Int`)와 바운드 참조(`greeting::length`, 타입 `() -> Int`)의 차이다. 바운드 참조는 수신 객체를 *캡처*하고 있으므로 파라미터 목록에서 수신 객체가 사라진다. 이것은 8절에서 살펴볼 "람다가 캡처하는 것"과 같은 원리다. 바운드 참조는 사실상 그 객체를 캡처한 클로저다(14장).

`this::method`로 현재 인스턴스의 메서드를 바운드 참조할 수도 있다. 콜백을 등록할 때 자주 쓰인다.

```kotlin
class Widget {
    fun onClick() { println("클릭됨") }
    fun register(handler: () -> Unit) { /* ... */ }
    fun setup() { register(this::onClick) }        // 자기 메서드를 바운드 참조
}
```

### 7.5 형태 4: 생성자 참조 `::ClassName`

생성자를 함수 값으로 참조한다. 이때 타입은 "생성자 파라미터를 받아 인스턴스를 반환하는" 함수 타입이다.

```kotlin
class Point(val x: Int, val y: Int) {
    override fun toString() = "($x, $y)"
}

val makePoint: (Int, Int) -> Point = ::Point
makePoint(3, 4)    // => (3, 4)

// 팩토리처럼 매핑에 사용
val xs = listOf(1, 2, 3)
val points = xs.map { Point(it, 0) }               // 람다
val origins = xs.map(::Point.partial(0))           // (개념적; 실제로는 아래처럼)
listOf(1 to 2, 3 to 4).map { (x, y) -> Point(x, y) }   // => [(1, 2), (3, 4)]
```

생성자 참조는 데이터 변환 파이프라인에서 "생성자를 매핑 함수로" 쓸 때 특히 간결하다. `typealias`로 별칭을 붙인 클래스나 [[27 - 데이터 클래스]]의 생성자에도 똑같이 적용된다.

```kotlin
data class User(val name: String, val age: Int)
val names = listOf("A", "B")
val ages = listOf(20, 30)
names.zip(ages, ::User)         // => [User(name=A, age=20), User(name=B, age=30)]
// zip의 셋째 인자가 (String, Int) -> User 이고 ::User가 정확히 그 타입
```

### 7.6 프로퍼티 참조와 리플렉션

`::` 문법으로는 함수뿐 아니라 프로퍼티도 참조할 수 있다. `String::length`는 사실 `KProperty1<String, Int>`이면서 동시에 `(String) -> Int` 함수로 쓸 수 있는 값이다. 프로퍼티 참조는 값을 읽는 것 이상의 기능을 제공한다. 프로퍼티의 이름을 알 수 있고, 가변 프로퍼티라면 세터도 쓸 수 있다.

```kotlin
class Box(var content: String)
val prop = Box::content                            // KMutableProperty1<Box, String>
val box = Box("초기값")
prop.get(box)                  // => "초기값"
prop.set(box, "변경됨")
box.content                    // => "변경됨"
prop.name                      // => "content"
```

여기서 쓴 `.get`, `.set`, `.name`은 **리플렉션 API**의 일부다. 함수 참조는 단순한 함수 값일 뿐 아니라 `KFunction`/`KProperty`라는 리플렉션 객체이기도 하다. 이 사실과 그에 따르는 비용(리플렉션 메타데이터, `kotlin-reflect` 의존성)은 [[44 - 애노테이션과 리플렉션]]에서 다룬다. 이 장에서는 "함수 참조는 함수 타입의 값이면서 *동시에* 리플렉션 핸들"이라는 이중성만 짚어 둔다.

> [!note] 명세 기준
> `::foo`의 정적 타입은 함수 타입(`(A) -> B`)과 `KFunction` 계열 인터페이스의 *교집합*이다. 그래서 함수 타입 문맥에서는 함수처럼, 리플렉션 문맥에서는 `KFunction`처럼 동작한다. 단순히 호출하거나 전달하기만 하면 리플렉션 라이브러리가 필요 없지만, `.name`이나 `.parameters` 같은 메타데이터에 접근하면 `kotlin-reflect`가 필요할 수 있다.

### 7.7 함수 참조 형태 비교표

| 문법 | 이름 | 예 | 결과 타입 |
|------|------|-----|-----------|
| `::foo` | 최상위/지역 함수 | `::isOdd` | `(Int) -> Boolean` |
| `Class::m` | 언바운드 멤버 | `String::length` | `(String) -> Int` |
| `obj::m` | 바운드 멤버 | `"cat"::length` | `() -> Int` |
| `::Class` | 생성자 | `::Point` | `(Int, Int) -> Point` |
| `Class::prop` | 프로퍼티(언바운드) | `Box::content` | `(Box) -> String` + KProperty |

## 8. 함수 값의 JVM 표현: invoke와 SAM

이 절에서는 "함수를 값으로 다룬다"는 추상적인 개념이 **JVM 백엔드에서** 실제로 무엇이 되는지 살펴본다. Native, JS, Wasm 백엔드는 세부 사항이 다르며, 아래 설명은 JVM에만 해당한다.

### 8.1 람다는 인터페이스의 인스턴스가 된다

2.3절에서 함수 타입이 `Function1` 같은 인터페이스라는 것을 보았다. 그렇다면 자연스럽게 **람다는 그 인터페이스를 구현한 객체 하나**로 컴파일된다는 결론이 나온다. `{ x: Int -> x * 2 }`는 개념적으로 다음과 같은 익명 클래스의 인스턴스다.

```java
// JVM 백엔드가 생성하는 것의 개념적 모습 (Java 유사 의사코드)
final class Lambda$1 implements Function1<Integer, Integer> {
    public Integer invoke(Integer x) {
        return x * 2;
    }
}
// { x -> x * 2 } 자리에 new Lambda$1() 가 놓인다
```

즉 `val f = { x: Int -> x * 2 }`는 대략 `Function1`을 구현한 객체 하나를 힙에 만든다. 1.3절에서 말한 "함수 값은 대개 객체 하나를 만든다"는 말이 바로 이것이다. 고차 함수에 람다를 많이 넘기면 이런 객체 할당이 쌓이는데, `inline`(15장)은 이 할당을 컴파일 타임에 없애는 장치다.

> [!note] 구현 기준
> 컴파일러 버전과 옵션에 따라 람다는 (a) 이름이 붙은 익명 클래스로 컴파일되거나, (b) `invokedynamic` + `LambdaMetafactory` 기반으로 지연 생성되도록 컴파일된다. 코틀린 2.x의 JVM 백엔드는 기본적으로 `invokedynamic` 방식을 쓰며(`-Xlambdas=indy`), 이 방식은 클래스 파일 수를 줄이고 시작 시간을 개선한다.
>
> 어느 방식이든 *런타임에는* `Function1` 등을 구현한 객체가 만들어지므로, 관찰할 수 있는 동작은 같다. 정확한 형태를 디컴파일로 확인하는 방법은 [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]에서 설명한다.

### 8.2 캡처가 없는 람다는 싱글턴이 될 수 있다

바깥 변수를 하나도 캡처하지 않는 람다(14장)는 매번 새 객체를 만들 필요가 없다. 상태가 없으므로 인스턴스 하나를 재사용해도 안전하기 때문이다. JVM 백엔드는 이런 람다를 **싱글턴 인스턴스**로 최적화할 수 있다.

```kotlin
fun makeDoubler(): (Int) -> Int = { it * 2 }       // 캡처 없음
val a = makeDoubler()
val b = makeDoubler()
// a와 b는 (구현에 따라) 같은 싱글턴 인스턴스일 수 있다
```

반면 바깥 변수를 캡처하는 람다는 캡처한 값을 담아야 하므로 만들 때마다 새 객체가 생긴다. 이 차이는 14장에서 다루는 성능 논의로 이어진다.

> [!caution] 성능 주의
> "람다는 객체 할당"이기 때문에, 자주 실행되는 루프(hot loop) 안에서 캡처하는 람다를 매번 새로 만들면 GC에 부담이 될 수 있다. 해결 방법은 두 가지다. (1) 고차 함수를 `inline`으로 만들어 할당 자체를 없애거나, (2) 캡처가 없는 람다를 상수처럼 밖으로 빼서 재사용한다. 표준 라이브러리의 `map`/`filter`/`forEach`가 인라인인 이유가 (1)이다.

### 8.3 `invoke`: 호출의 실제 모습

함수 값 `f`를 `f(x)`로 호출하는 것은 문법적 설탕이다. 실제로는 `Function1`의 `invoke` 연산자 메서드가 호출된다(19장 연산자 오버로딩과 관례). 아래 코드의 두 호출은 완전히 같다.

```kotlin
val f: (Int) -> Int = { it + 1 }
f(41)              // => 42
f.invoke(41)       // => 42  (위와 완전히 동일)
```

`invoke`는 평범한 메서드이므로, *어떤 객체에든* `operator fun invoke`를 정의해서 그 객체를 "함수처럼 호출할 수 있게" 만들 수 있다. 함수 타입을 구현하지 않아도 된다.

```kotlin
class Accumulator {
    var total = 0
    operator fun invoke(x: Int): Int { total += x; return total }
}
val acc = Accumulator()
acc(10)            // => 10   (acc.invoke(10))
acc(5)             // => 15
```

`acc`는 `(Int) -> Int` 타입이 *아니지만* 호출 문법을 지원한다. 이 예는 "호출할 수 있다"는 것과 "함수 타입이다"라는 것이 별개임을 보여 준다. 앞의 것은 `invoke` 연산자만 있으면 되고, 뒤의 것은 `FunctionN` 인터페이스를 구현한다는 뜻이다. [[28 - object와 companion - 싱글턴과 동반 객체]]의 팩토리나 DSL에서 `invoke`를 정의해 생성 문법을 자연스럽게 만드는 관용구가 여기서 나온다.

### 8.4 파라미터 22개 제한

표준 라이브러리에는 `Function0`부터 `Function22`까지 선언되어 있다. 그렇다면 파라미터가 23개 이상인 함수 타입은 어떻게 될까? 이때는 **`FunctionN`** 이라는 특수 인터페이스가 쓰인다(가변 인자 배열로 호출을 받는 형태다). 실무에서 파라미터가 23개인 함수는 거의 비정상적인 경우라 이 경계를 만날 일은 드물다. 하지만 "함수 타입은 아리티별 인터페이스"라는 모델에 상한이 있다는 사실은 알아 둘 만하다.

```text
아리티     인터페이스
0          Function0<R>
1          Function1<P1, R>
...        ...
22         Function22<P1, ..., P22, R>
23+        FunctionN<R>   (특수 처리)
```

### 8.5 SAM 변환: 자바 인터페이스와 fun interface

**SAM(Single Abstract Method)** 인터페이스는 추상 메서드가 딱 하나인 인터페이스다. 자바의 `Runnable`, `Comparator`, `Callback` 같은 것들이 여기에 속한다. 코틀린은 자바 SAM 인터페이스가 필요한 자리에 **람다를 자동으로 변환**해 넣어 준다. 이것을 **SAM 변환**이라고 한다.

```kotlin
// 자바 인터페이스 java.lang.Runnable { void run(); } 에 람다 전달
val thread = Thread { println("실행 중") }          // Runnable로 SAM 변환
thread.start()

// java.util.Comparator에도
val byLength = Comparator<String> { a, b -> a.length - b.length }
```

여기서 중요한 규칙이 하나 있다. **SAM 변환은 기본적으로 자바 인터페이스에만 자동으로 적용된다.** 코틀린에서 정의한 일반 인터페이스에 람다를 넘기면 컴파일 에러가 난다. 코틀린에는 이미 함수 타입(`(A) -> B`)이라는 더 나은 표현이 있으므로, 콜백을 인터페이스가 아니라 함수 타입 파라미터로 받도록 권장하기 때문이다.

```kotlin
interface OnClick {                                // 일반 코틀린 인터페이스
    fun handle(x: Int)
}
fun register(cb: OnClick) { /* ... */ }
register { println(it) }                            // 컴파일 에러: 일반 인터페이스엔 SAM 변환 없음
```

이 제약을 없애는 것이 **`fun interface`**(functional interface, [[25 - 인터페이스]])다. 인터페이스 앞에 `fun`을 붙이면 SAM 변환을 쓸 수 있다.

```kotlin
fun interface OnClick {                             // functional interface
    fun handle(x: Int)
}
fun register(cb: OnClick) { cb.handle(42) }
register { println("클릭: $it") }                    // OK! SAM 변환 → "클릭: 42"
```

`fun interface`는 "람다로 만들 수 있는 인터페이스"를 명시적으로 선언하는 방법이다. 그렇다면 함수 타입과 `fun interface` 중 무엇을 언제 써야 할까? 이름이 필요 없는 순수한 함수 계약에는 함수 타입이 알맞고, 가독성을 위해 이름을 붙이고 싶거나 자바와 상호 운용해야 할 때는 `fun interface`가 유리하다.

| 콜백 표현 방법 | 람다 전달 | 언제 쓰나 |
|----------------|-----------|-----------|
| 함수 타입 `(Int) -> Unit` | 항상 됨 | 코틀린 내부, 이름 불필요 |
| `fun interface Foo` | SAM 변환으로 됨 | 이름·의미 부여, 자바 노출 |
| 일반 `interface Foo` | 안 됨(객체 명시 필요) | 메서드 여럿, 상태 계약 |

> [!info] 역사 메모
> 자바 8이 람다와 함수형 인터페이스를 도입하면서 SAM 변환은 자바 생태계의 표준이 되었다. 코틀린은 자바와 매끄럽게 상호 운용하기 위해 자바 SAM 변환은 자동으로 지원하되, 코틀린 자체 인터페이스에는 함수 타입을 권장하고 `fun interface`를 선택적으로(옵트인) 쓸 수 있게 하는 절충안을 택했다. 이 설계는 [[45 - Java 상호운용]]의 주요 주제 중 하나다.

### 8.6 함수 값과 `is` 검사

함수 값도 객체이므로 타입 검사를 할 수 있다. 다만 제네릭 소거([[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]) 때문에 타입 인자까지는 확인할 수 없다.

```kotlin
val f: (Int) -> Int = { it + 1 }
f is Function1<*, *>       // => true
f is (Int) -> Int          // 경고/제약: 타입 인자는 소거되어 완전 검사 불가
```

즉 JVM 런타임에서 "함수인지"는 알 수 있어도 "어떤 타입의 함수인지"는 완전히 알 수 없다. 함수 타입이 결국 제네릭 인터페이스이기 때문이며, 타입 소거의 일반 규칙이 그대로 적용된 결과다.

## 9. nullable 함수 타입과 안전 호출

### 9.1 괄호 위치에 따른 차이

함수 타입을 nullable로 만들려면 **함수 타입 전체를 괄호로 감싼 뒤** `?`를 붙인다. 괄호 위치에 따라 의미가 완전히 달라지므로 정확하게 써야 한다.

```kotlin
val a: ((Int) -> Int)?      // 전체가 nullable: 함수가 없을 수도 있음
val b: (Int) -> Int?        // 반환 타입이 nullable: 함수는 있고, Int? 반환
val c: (Int?) -> Int        // 파라미터가 nullable
```

- `((Int) -> Int)?` : `a` 자체가 `null`일 수 있다.
- `(Int) -> Int?` : `b`는 항상 함수이고, 그 함수가 `Int?`(null일 수 있는 정수)를 반환한다.
- `(Int?) -> Int` : `c`는 함수이고, null일 수 있는 정수를 인자로 받는다.

이 세 가지를 혼동하면 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]의 널 규칙이 예상과 다르게 동작한다.

### 9.2 nullable 함수 호출하기: `?.invoke`

nullable 함수를 그냥 `a(x)`로 호출하면 null일 수 있으므로 컴파일 에러가 난다. 8.3절에서 `f(x)`가 `f.invoke(x)`라는 것을 보았으니, 안전 호출을 `invoke`에 적용하면 된다: `a?.invoke(x)`.

```kotlin
var onProgress: ((Int) -> Unit)? = null

fun report(pct: Int) {
    onProgress?.invoke(pct)      // onProgress가 null이면 아무 일 없음
}

report(50)                       // (핸들러 없음) 아무 출력 없음
onProgress = { println("진행: $it%") }
report(75)                       // => 진행: 75%
```

`onProgress?.invoke(pct)`는 "핸들러가 등록되어 있으면 호출하고, 없으면 조용히 넘어간다"는 뜻의 선택적 콜백 관용구다. 엘비스 연산자와 함께 쓰면 기본 동작도 지정할 수 있다.

```kotlin
val result = (transformer?.invoke(input)) ?: input   // 변환기 없으면 원본 그대로
```

`f(x)`처럼 직접 호출하는 문법에는 안전 호출 버전(`f?(x)` 같은 것)이 없다. 따라서 nullable 함수는 반드시 `?.invoke`로 호출해야 한다. 이것은 `invoke`가 평범한 메서드라는 사실(8.3절)에서 나오는 실용적인 결과다.

### 9.3 nullable 함수 타입과 선택적 콜백

nullable 함수 타입 파라미터에는 람다를 넘길 수도 있고 `null`을 넘길 수도 있다. 기본값과 함께 써서 "선택적 콜백"을 만드는 것은 흔한 API 패턴이다.

```kotlin
fun download(
    url: String,
    onProgress: ((Int) -> Unit)? = null,      // 선택적 콜백, 기본 null
    onDone: () -> Unit                          // 필수 콜백
) {
    onProgress?.invoke(0)
    // ... 다운로드 ...
    onProgress?.invoke(100)
    onDone()
}

download("http://x") { println("완료") }         // onProgress 생략, onDone은 후행 람다
download("http://y", { println("$it%") }) { println("끝") }
```

주의할 점이 있다. `onDone`이 마지막 파라미터이므로 후행 람다는 `onDone`에 전달된다. `onProgress`는 마지막 파라미터가 아니므로 후행 람다로 쓸 수 없다(5.3절).

## 10. 수신 객체 지정 함수 타입 `A.() -> B`

### 10.1 점 하나로 달라지는 것

함수 타입 앞에 `수신타입.`을 붙이면 **수신 객체 지정 함수 타입(function type with receiver)** 이 된다. `A.() -> B`는 "A를 수신 객체로 삼아 실행되고 B를 반환하는 함수"다. 일반 함수 타입과의 결정적인 차이는 함수 본문 안에서 그 A 인스턴스가 **`this`가 된다**는 점이다. 그래서 본문에서 수신자를 적지 않고 멤버를 호출할 수 있다.

```kotlin
// 일반 함수 타입: 수신자를 파라미터로 받음
val f1: (StringBuilder) -> Unit = { sb -> sb.append("x") }

// 수신 함수 타입: 수신자가 this가 됨
val f2: StringBuilder.() -> Unit = { append("x") }   // this.append("x"), this 생략

val sb = StringBuilder()
f1(sb)                 // 파라미터로 전달
sb.f2()                // 확장 함수처럼 호출! (또는 f2(sb)도 가능)
sb.toString()          // => "xx"
```

`f2` 안의 `append`는 `this.append`이고, 여기서 `this`는 `f2`가 실행되는 수신 객체다. 즉 `StringBuilder.() -> Unit`은 "StringBuilder에 대한 임시 확장 함수"처럼 동작한다([[35 - 확장 함수와 프로퍼티]]와 같은 원리다).

### 10.2 수신 함수 타입이 DSL의 토대가 되는 이유

수신 함수 타입을 쓰면 람다 블록 안에서 *마치 그 객체의 내부에 있는 것처럼* 코드를 쓸 수 있다. 이 성질 덕분에 빌더 패턴과 DSL을 자연스럽게 작성할 수 있다.

```kotlin
class HtmlTag(val name: String) {
    val children = mutableListOf<HtmlTag>()
    fun tag(name: String, init: HtmlTag.() -> Unit) {
        val child = HtmlTag(name)
        child.init()                 // 자식을 수신자로 삼아 init 실행
        children.add(child)
    }
    override fun toString(): String =
        "<$name>${children.joinToString("")}</$name>"
}

fun html(init: HtmlTag.() -> Unit): HtmlTag {
    val root = HtmlTag("html")
    root.init()                      // root를 this로 삼아 실행
    return root
}

val page = html {                    // 이 블록 안에서 this = root HtmlTag
    tag("body") {                    // this.tag(...), this = root
        tag("p") { }                 // 이 블록 안에서 this = body 태그
    }
}
page.toString()   // => <html><body><p></p></body></html>
```

`html { ... }` 블록 안의 `tag("body") { ... }`는 사실 `this.tag(...)` 호출이고, 여기서 `this`는 루트 태그다. 수신 함수 타입이 없다면 `html { root -> root.tag(...) }`처럼 수신자를 명시적으로 넘겨야 하므로 코드가 훨씬 복잡해진다.

`@DslMarker`로 중첩된 수신자 스코프를 제어하는 방법을 포함한 이 관용구 전체는 37장(타입 안전 빌더와 DSL)에서 다룬다. 스코프 함수(`apply`/`with`/`run`)가 이 타입으로 어떻게 만들어졌는지는 16장(스코프 함수와 수신 객체 관용구)에서 다룬다.

### 10.3 수신 함수 타입의 실체: 사실은 일반 함수 타입

JVM 표현 수준(8절)에서 `A.() -> B`는 **`(A) -> B`, 즉 `Function1<A, B>`와 같은 구조**로 컴파일된다. 수신자가 첫 번째 파라미터로 자리를 옮긴 것뿐이다. 그래서 코틀린에서는 문맥에 따라 둘을 서로 바꿔 쓸 수 있다.

```kotlin
val withReceiver: StringBuilder.() -> Unit = { append("!") }
val asParam: (StringBuilder) -> Unit = withReceiver          // 변환 가능

val sb = StringBuilder("hi")
asParam(sb)            // 파라미터 스타일 호출
sb.toString()          // => "hi!"
```

수신자로 받느냐 파라미터로 받느냐는 *호출 문법과 본문 안에서 this로 접근하는지*의 차이일 뿐이고, 런타임 구조는 같다. 이 사실은 2.2절에서 "함수 타입의 동일성은 파라미터, 반환, 수신, suspend 여부로 결정된다"고 한 설명과 이어진다. 수신자는 타입 시스템에서는 구별되지만, 백엔드에서는 첫 번째 파라미터로 합쳐진다.

> [!note] 명세 기준
> `A.() -> B`와 `(A) -> B`는 호출 관례가 다르므로 타입 시스템 수준에서는 *서로 다른* 타입이다. 하지만 컴파일러는 둘 사이의 암시적 변환을 허용하고, JVM 백엔드에서는 둘 다 같은 `Function1<A, B>`로 표현된다. 따라서 "수신 함수 타입은 새로운 종류의 런타임 실체를 만들지 않는다"고 말하는 것이 정확하다.

### 10.4 suspend 함수 타입 미리 보기

함수 타입 앞에 `suspend`를 붙이면 `suspend () -> Unit`처럼 **중단 가능한 함수 타입**이 된다. 코루틴 빌더가 받는 람다의 타입이 바로 이것이며, `suspend`는 이런 방식으로 타입 시스템에 나타난다. 컴파일러는 이 타입의 값을 `Continuation` 파라미터를 몰래 추가한 CPS 형태로 변환한다.

그 자세한 내용은 42장(suspend와 코루틴)과 코루틴 자매 시리즈의 CPS·상태 기계 장에서 다룬다. 여기서는 함수 타입에 `suspend`라는 수식어가 하나 더 있다는 사실, 그리고 그 때문에 2.2절에서 `suspend` 여부를 함수 타입 동일성의 결정 요소로 언급했다는 점만 확인한다.

```kotlin
val block: suspend () -> Int = { /* 중단 가능한 본문 */ 42 }
// 이 block은 일반 () -> Int 자리에 넣을 수 없다: suspend가 타입의 일부
```
