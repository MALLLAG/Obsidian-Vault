[[32 - 클래스 위임]]까지는 구체적인 타입 하나를 어떻게 만들고, 합성하고, 재사용하는지를 다뤘다. 클래스, 인터페이스, 위임은 모두 `Point`나 `BankAccount`처럼 *이미 이름이 붙은 타입*을 대상으로 한다.

그러나 실무에서는 "무엇을 담을지는 나중에 정해지는 그릇"을 만드는 일이 절반을 차지한다. 리스트는 정수도, 문자열도, 좌표도 담을 수 있어야 한다. 이렇게 나중에 정해지는 타입을 타입 수준에서 안전하게 표현하는 장치가 제네릭(generics), 즉 타입 파라미터(type parameter)다.

이 장에서는 제네릭의 앞부분을 명세 수준에서 다룬다. 타입 파라미터를 선언하는 방법과 기본 상한 `Any?`의 의미, 그리고 제네릭 타입 사이의 하위 타입 방향을 정하는 변성(variance)을 살펴본다. 변성에는 선언 지점 변성(`out`/`in`), 사용 지점 변성(타입 프로젝션), 스타 프로젝션이 있다.

런타임에 `List<String>`의 `String`이 사라지는 이유(타입 소거, type erasure), `reified`로 소거를 우회하는 방법, `where`와 재귀 제네릭 같은 상한(bound) 문법은 [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]에서 설명하고, 여기서는 변성을 이해하는 데 필요한 만큼만 소거를 언급한다.

`Nothing`과 `Any?`의 위치는 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서, nullable 타입의 널 안전 규칙은 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 다루므로, 이 장에서는 이들이 변성과 만나는 지점만 본다.

## 1. 제네릭이 없는 세계: 왜 타입 파라미터가 필요한가

### 1.1 `Any`로 담을 때의 대가

제네릭을 이해하려면 제네릭이 *없을 때* 무엇을 잃는지 보는 것이 가장 빠르다. 5장(타입 시스템의 지형)에서 본 것처럼 Kotlin의 모든 참조 타입은 `Any?`를 최상위로 하는 하나의 계층에 속한다. 따라서 이론상 "무엇이든 담는 그릇"은 `Any`(또는 `Any?`)를 담으면 된다. 제네릭 없이 정수 하나를 담는 상자를 만들어 보자.

```kotlin
class AnyBox(val value: Any?)

fun main() {
    val box = AnyBox(42)
    val n: Int = box.value as Int      // 캐스팅이 강제된다
    println(n + 1)                      // => 43

    val box2 = AnyBox("hello")
    val m: Int = box2.value as Int     // 컴파일은 통과한다!
    println(m + 1)                      // 런타임: ClassCastException
}
```

이 코드에서는 세 가지를 잃는다.

- **첫째, 컴파일러가 타입 정보를 잃는다.** `box.value`의 정적 타입은 `Any?`이므로, 컴파일러는 그 안에 무엇이 들어 있는지 알지 못한다. 42를 넣었다는 사실은 `AnyBox` 생성자를 거치는 순간 사라진다.
- **둘째, 안전을 개발자의 기억에 맡기게 된다.** `box2.value as Int`는 "이 값은 정수일 것"이라는 개발자의 *주장*이고, 컴파일러는 이 주장을 검증하지 못한 채 통과시킨다. 잘못된 주장은 컴파일 타임이 아니라 런타임에 `ClassCastException`으로 드러난다.
- **셋째, 문제가 퍼져 나간다.** `Any?`를 반환하는 API를 쓰면 그 값을 받는 모든 곳에서 캐스팅이 필요하고, 캐스팅 하나하나가 새로운 런타임 실패 지점이 된다.

> [!warning] 흔한 오해
> "동적 타입 언어처럼 `Any`로 모두 담고 필요할 때 캐스팅하면 유연하다"고 생각하기 쉽다. 그러나 이것은 유연한 것이 아니라 *검증을 미루는 것*이다. 미룬 검증은 사라지지 않고, 타입 시스템(컴파일 타임)에서 예외 처리(런타임)로 자리를 옮길 뿐이다. Kotlin의 널 안전이 런타임 NPE를 컴파일 타임 검사로 앞당겼듯이, 제네릭은 런타임 `ClassCastException`을 컴파일 타임 타입 검사로 앞당긴다.

### 1.2 타입 파라미터: 컴파일러가 약속을 지키게 하는 변수

제네릭은 타입 자체를 변수로 다뤄서 이 문제를 해결한다. 상자에 담을 원소의 타입을 미리 고정하지 않고, `T`라는 *타입 파라미터*로 남겨 둔다.

```kotlin
class Box<T>(val value: T)

fun main() {
    val intBox = Box(42)          // T = Int (추론)
    val n: Int = intBox.value      // 캐스팅 불필요! value의 타입이 이미 Int
    println(n + 1)                 // => 43

    val strBox = Box("hello")     // T = String
    val m: Int = strBox.value      // 컴파일 에러: Type mismatch (String → Int)
}
```

`class Box<T>`의 `<T>`는 "이 클래스를 사용할 때 실제 타입 하나를 채워 넣어야 한다"는 선언이다. `T`는 클래스 본문 전체에서 나중에 채워질 그 타입을 가리키는 이름으로 쓰인다. `Box(42)`라고 쓰면 컴파일러는 인자 `42`의 타입(`Int`)에서 `T = Int`를 *추론*하고, 그때부터 이 `Box`의 `value`를 `Int`로 취급한다. 따라서 `strBox.value`를 `Int`에 대입하려는 코드는 런타임까지 가지 않고 컴파일 타임에 잡힌다.

핵심은 다음과 같다. **타입 파라미터는 "이 그릇에 넣은 값과 꺼낸 값의 타입이 같다"는 약속을 컴파일러가 강제하도록 만드는 장치다.** `T`는 값이 아니라 타입 수준의 변수이며, 인스턴스마다 하나의 구체 타입으로 *실체화(instantiation)* 된다. `Box<Int>`, `Box<String>`, `Box<Box<Int>>`는 서로 다른 타입이다.

### 1.3 제네릭 함수: 함수에 타입 파라미터 붙이기

타입 파라미터는 클래스뿐 아니라 함수에도 붙일 수 있다. 함수의 타입 파라미터는 함수 이름 *앞의* 꺾쇠괄호에 쓴다.

```kotlin
fun <T> firstOf(list: List<T>): T = list[0]

fun <A, B> pair(a: A, b: B): Pair<A, B> = Pair(a, b)

fun main() {
    val x: Int = firstOf(listOf(1, 2, 3))          // T = Int
    val s: String = firstOf(listOf("a", "b"))       // T = String
    val p: Pair<String, Int> = pair("age", 30)      // A = String, B = Int
    println("$x $s $p")                             // => 1 a (age, 30)
}
```

`fun <T> firstOf`에서 `<T>`가 함수 이름 *앞에* 온다는 점은 문법적으로 중요하다. "이 함수를 호출할 때마다 `T`가 새로 정해진다"는 뜻이기 때문이다. `firstOf(listOf(1, 2, 3))`에서는 인자 타입 `List<Int>`에서 `T = Int`가 추론되고, 반환 타입도 그에 따라 `Int`가 된다. 타입 추론이 실패하거나 모호하면 호출하는 쪽에서 `firstOf<Int>(...)`처럼 타입을 명시할 수도 있다.

지금까지 타입 파라미터가 하는 일, 즉 넣은 값과 꺼낸 값의 타입이 같음을 컴파일러가 보장한다는 점을 확인했다. 이제 타입 파라미터 자체를 더 자세히 살펴보자. 특히 타입 파라미터가 *어떤 타입을* 받을 수 있는지, 그리고 null과 어떤 관계인지가 첫 번째 오해가 생기는 지점이다.

## 2. 타입 파라미터의 구조: 상한과 기본값 `Any?`

### 2.1 기본 상한은 `Any?`다

아무 제약 없이 선언한 타입 파라미터 `T`는 어떤 타입까지 받을 수 있을까? 흔한 오해가 여기서 시작된다.

> [!warning] 흔한 오해
> "타입 파라미터 `T`에는 null을 넣을 수 없고, null을 담으려면 `T?`라고 써야 한다"고 생각하기 쉽다. **이것은 틀렸다.** 제약 없는 `T`의 *기본 상한(upper bound)* 은 `Any`가 아니라 **`Any?`** 이다. 즉 `T`는 처음부터 nullable 타입까지 포함하는 가장 넓은 범위를 받는다.

코드로 확인해 보자.

```kotlin
class Box<T>(val value: T)

fun main() {
    val nullableBox: Box<String?> = Box(null)   // OK! T = String?
    println(nullableBox.value)                   // => null

    val box2 = Box<Int?>(null)                   // OK! T = Int?
    println(box2.value)                          // => null
}
```

`Box<String?>`와 `Box<Int?>`는 아무 문제 없이 성립한다. `T`의 상한이 `Any?`이기 때문이다. 따라서 다음 두 선언은 완전히 같다.

```kotlin
class Box<T>          // T의 상한: Any? (암시적)
class Box<T : Any?>   // T의 상한: Any? (명시적) — 위와 완전히 같다
```

타입 계층에서 `Any?`는 최상위이므로, `T : Any?`는 가장 느슨한 상한, 즉 사실상 제약이 없다는 뜻이다. 반면 널을 허용하지 않는 `Any`는 `Any?`보다 좁다. 이 오해는 전적으로 이 작은 차이에서 비롯된다.

```text
        Any?          ← 기본 상한 (nullable 타입 전부 포함)
       /    \
     Any    (String?, Int?, ... 같은 nullable 타입들)
    /   \
 String  Int  ...
    \   /
   Nothing    ← 바닥 타입 (모든 타입의 하위)
```

### 2.2 `T`와 `T?`: 이미 null을 포함할 수 있는 `T`에 `?`를 더하면

그렇다면 `T`와 `T?`는 무엇이 다를까? `T`가 이미 nullable 타입이 될 수 있는데 `T?`는 왜 필요할까?

`T?`는 "`T`가 무엇이든 거기에 null 가능성을 *더한* 타입"이다. 핵심은 이 타입이 **평탄화(flatten)** 된다는 점이다. nullable 타입에 다시 nullable을 더해도 이중 null이 되지 않는다.

```kotlin
fun <T> nullableOf(value: T): T? = value

fun main() {
    val a: String? = nullableOf("hi")     // T = String, T? = String?
    val b: String? = nullableOf<String?>(null)
    //  T = String?, T? = String?? = String?  (평탄화)
    println("$a $b")                       // => hi null
}
```

여기서는 두 가지를 구분해야 한다. 먼저 **`T` 자체가 nullable일 수 있다**(상한이 `Any?`이기 때문이다). 그리고 함수가 "무엇을 받든 null일 수 있는 결과"를 반환하려면 `T?`라고 명시한다. `T = String`이면 `T?`는 `String?`이고, `T = String?`이어도 `T?`는 여전히 `String?`이다(`String??`라는 타입은 없다). 정리하면 다음과 같다.

| 표기 | 의미 | `T = String`일 때 | `T = String?`일 때 |
|------|------|------------------|-------------------|
| `T` | 타입 파라미터 그 자체 | `String` | `String?` |
| `T?` | `T`에 null 가능성을 더함(평탄화) | `String?` | `String?` |

이 구분은 표준 라이브러리의 시그니처를 읽을 때 매우 중요하다. 예를 들어 `List<T>.firstOrNull(): T?`는 "원소 타입 `T`가 무엇이든 리스트가 비어 있으면 null을 반환할 수 있다"는 뜻을 나타내려고 `T`가 아니라 `T?`를 반환한다.

### 2.3 null을 허용하지 않으려면 `T : Any`

`T`의 기본 상한이 `Any?`라는 것은, null을 *거부*하려면 상한을 `Any`로 명시해서 좁혀야 한다는 뜻이다.

```kotlin
fun <T : Any> requireValue(value: T): T = value   // T는 널 불가

fun main() {
    requireValue("hi")                 // OK
    requireValue(null)                 // 컴파일 에러:
    // Null can not be a value of a non-null type T
}
```

`<T : Any>`는 "`T`는 null을 허용하지 않는 타입이어야 한다"는 계약이다. 표준 라이브러리에는 이 패턴이 많다. 대표적으로 `requireNotNull`, `checkNotNull`, 컬렉션의 `filterNotNull(): List<T>` 같은 함수가 결과에 null이 없음을 타입으로 보장하려고 `T : Any`를 사용한다.

```kotlin
// 개념적 시그니처
fun <T : Any> Iterable<T?>.filterNotNull(): List<T>
//              ^^^^^^^^^^^ 널 포함 입력          ^^^^^^^ 널 제거된 출력 (T : Any)
```

여기서 입력은 null을 포함하는 `Iterable<T?>`이고, 출력은 `List<T>`이다. `T`가 `Any`의 하위 타입이므로 출력에는 null이 없다. 상한을 `Any`로 정했기 때문에 "null을 걸러 낸다"는 의미가 타입에 정확히 드러난다.

> [!note] 명세 기준
> `T : Any`는 상한으로 null을 막지만, 이것은 "null이 아닌 값을 강제하는 실행 시점 검사"와는 다르다. 상한은 *컴파일 타임* 제약이다. Java 상호운용에서 넘어온 플랫폼 타입(6장 널 안전성)은 이 컴파일 타임 검사를 우회할 수 있으므로, 경계에서는 여전히 방어 코드가 필요하다. 이 상호운용 함정은 [[45 - Java 상호운용]]에서 다룬다.

### 2.4 여러 타입 파라미터와 이름 관례

타입 파라미터는 여러 개일 수 있고, 각각 자신의 상한을 가진다. 상한을 여러 개(교집합) 걸려면 `where` 절을 쓰는데, 이 문법은 34장(제네릭 2)에서 자세히 다루므로 여기서는 이름만 언급한다.

```kotlin
class Cache<K, V>                          // 두 파라미터
fun <T : Comparable<T>> max(a: T, b: T): T = if (a >= b) a else b  // 재귀 상한(34장)
```

관례적으로 `T`(Type), `E`(Element), `K`/`V`(Key/Value), `R`(Result), `A`/`B`(임의)를 쓴다. 이것은 규칙이 아니라 관습이므로 `Animal`처럼 의미 있는 긴 이름을 써도 된다. 다만 한 글자 관례가 널리 통용되기 때문에 표준 라이브러리도 이를 따른다.

이제 타입 파라미터를 *선언*하는 방법은 정리했다. 그러나 정말 어려운 문제는 여기서부터다. `Cat`이 `Animal`의 하위 타입일 때 `Box<Cat>`은 `Box<Animal>`의 하위 타입일까? 이 장의 나머지는 모두 이 질문에 답하는 내용이다.

## 3. 무공변: 왜 `List<Cat>`은 기본적으로 `List<Animal>`이 아닌가

### 3.1 하위 타입 관계는 제네릭에 자동으로 전파되지 않는다

먼저 예제에 쓸 타입을 정하자. 상속 계층은 [[24 - 상속과 오버라이딩과 초기화 순서]]에서 다뤘다.

```kotlin
open class Animal(val name: String)
class Cat(name: String) : Animal(name)
class Dog(name: String) : Animal(name)
```

`Cat`은 `Animal`의 하위 타입($\text{Cat} <: \text{Animal}$)이다. 그렇다면 `Box<Cat>`은 `Box<Animal>`의 하위 타입일까? 직관적으로는 "고양이 상자도 동물 상자일 것"이라고 생각하기 쉽지만, Kotlin의 기본 답은 **아니다**.

```kotlin
class Box<T>(var value: T)

fun main() {
    val catBox: Box<Cat> = Box(Cat("나비"))
    val animalBox: Box<Animal> = catBox   // 컴파일 에러:
    // Type mismatch: inferred type is Box<Cat> but Box<Animal> was expected
}
```

`Box<T>`에는 변성 표기가 없으므로 **무공변(invariant)** 이다. 무공변은 "$\text{Cat} <: \text{Animal}$이더라도 $\text{Box<Cat>}$과 $\text{Box<Animal>}$ 사이에는 아무런 하위 타입 관계가 없다"는 뜻이다. `Box<Cat>`은 `Box<Animal>`의 하위 타입도 상위 타입도 아니다. `Box<Cat> <: Box<Cat>`처럼 자기 자신과의 관계만 성립한다.

처음에는 지나치게 엄격해 보일 수 있다. 하지만 무공변을 *기본값*으로 삼은 데에는 분명한 안전상의 이유가 있다.

### 3.2 무공변이 안전한 기본값인 이유: 쓰기의 위험

`Box<Cat>`을 `Box<Animal>`로 취급할 수 있다고 가정하고, 그러면 어떤 문제가 생기는지 따라가 보자.

```kotlin
class Box<T>(var value: T)   // 읽기(get)도 쓰기(set)도 가능

fun main() {
    val catBox: Box<Cat> = Box(Cat("나비"))

    // (가정) 만약 이 대입이 허용된다면...
    val animalBox: Box<Animal> = catBox   // 실제로는 컴파일 에러지만, 허용됐다 치자

    animalBox.value = Dog("바둑이")        // Animal 상자니까 Dog를 넣는 건 합법
    // 그런데 animalBox와 catBox는 같은 객체다!

    val cat: Cat = catBox.value            // catBox는 여전히 Box<Cat>
    // → 실제로는 Dog가 들어 있다! 힙 오염(heap pollution)
}
```

문제의 핵심은 `Box`가 값을 *꺼내기만* 하지 않고 *넣기도* 한다는 점이다. `Animal` 상자의 관점에서 `animalBox.value = Dog(...)`는 완전히 합법이다(개도 동물이기 때문이다). 그러나 이 상자는 실제로 `catBox`와 같은 객체이고, `catBox`는 "고양이만 담는다"고 약속했다. 고양이 상자에 개가 들어가는 이 모순을 컴파일러가 미리 막으려면, 처음부터 `Box<Cat>`을 `Box<Animal>`로 취급하지 못하게 해야 한다. 이것이 바로 무공변이다.

일반화하면 다음과 같다. **타입 파라미터가 "쓰기 위치(입력 위치, in-position)"에 나타나면, 그 방향으로 하위 타입 관계를 전파하는 것은 안전하지 않다.** `Box<Cat>`을 `Box<Animal>`로 넓히면, `Animal`을 받는 세터를 통해 `Cat`이 아닌 값을 넣을 수 있게 되기 때문이다. 무공변은 이 위험을 처음부터 막는 가장 보수적인 선택이다.

> [!note] 명세 기준
> 하위 타입 관계의 이 성질을 형식적으로 쓰면, 타입 생성자 $F$가 무공변이라는 것은 $\text{A} <: \text{B}$로부터 $F\langle A\rangle <: F\langle B\rangle$도 $F\langle B\rangle <: F\langle A\rangle$도 유도되지 *않는다*는 뜻이다.
>
> 공변은 방향을 보존하고($A <: B \Rightarrow F\langle A\rangle <: F\langle B\rangle$), 반공변은 방향을 뒤집는다($A <: B \Rightarrow F\langle B\rangle <: F\langle A\rangle$). 뒤에서 이 세 규칙이 왜 성립하는지 하나씩 설명한다.

### 3.3 Java 배열의 공변 함정: 이 안전을 깬 반례

무공변이 올바른 기본값인 이유를 잘 보여 주는 반례가 Java의 배열이다. Java는 배열을 **공변(covariant)** 으로 설계했다. 즉 `Cat[]`이 `Animal[]`의 하위 타입이다. 이 결정이 어떤 결과를 낳는지 보자.

```java
// Java
Cat[] cats = new Cat[]{ new Cat("나비") };
Object[] objects = cats;          // 합법! Java 배열은 공변
objects[0] = new Dog("바둑이");   // 컴파일 통과!
// 런타임: java.lang.ArrayStoreException
```

Java 컴파일러는 `objects[0] = new Dog(...)`를 통과시킨다. `objects`의 정적 타입은 `Object[]`이고 `Dog`는 `Object`이기 때문이다. 그러나 이 배열은 실제로 `Cat[]`이다.

그래서 JVM은 배열에 값을 저장할 때마다 *런타임에* 실제 원소 타입을 검사하고, 맞지 않으면 `ArrayStoreException`을 던진다. 결국 Java는 배열 공변의 대가로 **모든 배열 쓰기에 런타임 타입 검사를 넣어야** 했고, 그런데도 오류는 컴파일 타임이 아니라 런타임에야 드러난다.

Kotlin은 이 역사적 실수를 반복하지 않았다. **Kotlin의 `Array<T>`는 무공변이다.**

```kotlin
fun main() {
    val cats: Array<Cat> = arrayOf(Cat("나비"))
    val animals: Array<Animal> = cats   // 컴파일 에러:
    // Type mismatch: Array<Cat> is not a subtype of Array<Animal>
}
```

Kotlin에서는 `Array<Cat>`을 `Array<Animal>`에 대입하려는 코드가 *컴파일 타임에* 막힌다. 배열은 `arr[i]`로 읽고 `arr[i] = x`로 쓰는 가변 그릇이므로, 3.2절의 논리에 따라 무공변이어야 안전하다. Kotlin은 배열을 이 원칙에 맞게 설계해서 `ArrayStoreException`이라는 런타임 함정을 언어 수준에서 없앴다.

> [!info] 역사 메모
> Java 배열의 공변은 제네릭이 없던 1995년에 "`Object[]`를 받는 정렬 유틸리티 하나로 모든 배열을 정렬"할 수 있도록 실용성을 위해 도입되었다. 이후 제네릭(2004, Java 5)이 뒤늦게 추가되면서 이 결정은 언어의 약점으로 남았다.
>
> Kotlin은 이 교훈을 바탕으로 배열을 무공변으로 만들고, 변성은 개발자가 *의도적으로* 표시하도록 했다. (`IntArray` 같은 원시 배열이 `Array<Int>`와 또 다른 별개의 타입이라는 내용은 [[38 - 컬렉션 - 읽기 전용과 가변]]과 34장(제네릭 2)에서 다룬다.)

이제 무공변이 안전한 기본값이라는 점은 분명하다. 그러나 무공변만으로는 불편하다. 고양이 리스트를 동물 리스트로 넘겨서 이름만 읽는 것처럼 완전히 안전한 코드까지 막히기 때문이다. 그래서 Kotlin은 개발자가 "이 그릇은 쓰지 않고 읽기만 한다" 또는 "읽지 않고 쓰기만 한다"는 점을 *증명*하면, 그에 맞는 하위 타입 관계를 허용한다. 이것이 변성이다.

## 4. 변성의 원리: 생산과 소비

### 4.1 "`out`=반환, `in`=인자"는 절반만 맞다

변성을 처음 배우면 대개 "`out`은 타입 파라미터를 반환 타입에만 쓸 때, `in`은 인자 타입에만 쓸 때"라는 암기법을 접한다. 이 규칙은 *결과적으로는* 맞지만, 왜 그런지를 설명하지 않기 때문에 위험하다.

> [!warning] 흔한 오해
> "`out`은 반환에만, `in`은 인자에만 쓴다고 외우면 변성은 끝이다"라고 생각하기 쉽다. 그러나 이 암기법은 규칙의 *증상*일 뿐 *원인*이 아니다. 변성은 근본적으로 **안전성 규칙**이다. 타입 파라미터가 값을 *생산(produce/out)* 하기만 하는지, *소비(consume/in)* 하기만 하는지에 따라 어느 방향으로 하위 타입 관계를 전파해야 안전한지가 정해진다.
>
> "반환/인자"는 이 생산과 소비가 시그니처에 드러나는 *겉모습*일 뿐이다. 원리를 알면 프로퍼티, 함수 타입, 프로젝션까지 스스로 판단할 수 있지만, 암기만 하면 세터(`var`)나 함수 타입의 반공변 위치 같은 곳에서 판단이 틀어진다.

원리부터 정리하자. 제네릭 타입 `Container<T>`에서 `T`는 API의 두 가지 위치 중 하나(또는 둘 다)에 나타난다.

- **out 위치(생산 위치)**: `T`가 *밖으로 나오는* 자리다. 함수의 반환 타입과 `val` 프로퍼티의 타입이 여기에 해당한다. 이때 `Container`는 `T`를 *만들어 내보내는* 생산자다.
- **in 위치(소비 위치)**: `T`가 *안으로 들어가는* 자리다. 함수의 파라미터 타입과 `var` 프로퍼티의 세터가 받는 값이 여기에 해당한다. 이때 `Container`는 `T`를 *받아들이는* 소비자다.

안전성의 핵심 명제는 다음과 같다.

$$
\text{T가 out 위치에만 있으면} \Rightarrow \text{공변이 안전} \qquad \text{T가 in 위치에만 있으면} \Rightarrow \text{반공변이 안전}
$$

### 4.2 공변(`out`): 생산자만 안전하게 넓힐 수 있다

`T`를 *생산하기만* 하는 그릇을 생각해 보자. 원소를 꺼내 주기만 하고 넣을 수는 없는 읽기 전용 생산자다.

```kotlin
class Producer<out T>(private val value: T) {
    fun get(): T = value    // T는 out 위치(반환)에만 등장
}

fun main() {
    val catProducer: Producer<Cat> = Producer(Cat("나비"))
    val animalProducer: Producer<Animal> = catProducer   // OK! 공변
    val a: Animal = animalProducer.get()                 // Cat을 Animal로 받음 — 안전
    println(a.name)                                        // => 나비
}
```

왜 안전할까? `animalProducer.get()`이 반환하는 값은 실제로 `Cat`이지만, 고양이는 동물이므로 `Animal`로 받아도 아무 문제가 없다. 이 그릇에는 *값을 넣는 통로가 없으므로*, 3.2절에서 본 것처럼 개를 밀어 넣는 문제가 처음부터 생길 수 없다. 생산만 하는 그릇은 `Producer<Cat>`에서 `Producer<Animal>`로 넓혀도 안전하다. 이것이 공변이다.

`out` 수식어는 컴파일러에게 두 가지를 함께 지시한다. **(1)** 하위 타입 관계를 같은 방향으로 전파하도록 허용한다($\text{Cat} <: \text{Animal} \Rightarrow \text{Producer<Cat>} <: \text{Producer<Animal>}$). **(2)** 그 대신 `T`가 in 위치(소비 위치)에 나타나지 않는지 *강제로 검사*한다.

`Producer<out T>`에 `fun set(v: T)`를 추가하면 컴파일러가 거부한다(5.2절에서 자세히 설명한다). 즉 `out`은 "넓혀도 되지만, 그 대신 값을 넣지 않겠다고 약속한다"는 계약이다.

### 4.3 반공변(`in`): 소비자만 안전하게 좁힐 수 있다

이번에는 반대 경우를 보자. `T`를 *소비하기만* 하는 그릇, 즉 값을 받아 처리하기만 하고 내보내지는 않는 소비자다.

```kotlin
class Consumer<in T> {
    fun consume(item: T) {   // T는 in 위치(파라미터)에만 등장
        println("소비: $item")
    }
}

fun main() {
    val animalConsumer: Consumer<Animal> = Consumer()
    val catConsumer: Consumer<Cat> = animalConsumer   // OK! 반공변 — 방향 역전
    catConsumer.consume(Cat("나비"))                    // => 소비: Cat...
}
```

여기서는 방향이 *뒤집힌다*. $\text{Cat} <: \text{Animal}$인데 `Consumer<Animal>`이 `Consumer<Cat>`의 하위 타입이 된다($\text{Consumer<Animal>} <: \text{Consumer<Cat>}$). 왜 안전할까? "고양이를 소비하는 자리"에 "동물을 소비할 수 있는 객체"를 두는 것은 안전하다. 동물 소비자는 어떤 동물이든 처리할 수 있으므로, 동물의 한 종류인 고양이를 넘겨도 당연히 처리한다.

반대로 "동물을 소비하는 자리"에 "고양이만 소비하는 객체"를 두면 위험하다. 개를 넘기면 고양이만 처리하는 소비자는 이를 처리하지 못한다.

`in` 수식어의 계약도 이와 대칭이다. **(1)** 하위 타입 관계를 반대 방향으로 전파하도록 허용하고, **(2)** `T`가 out 위치(생산 위치)에 나타나지 못하게 강제한다. `Consumer<in T>`에 `fun produce(): T`를 넣으면 컴파일 에러가 난다.

### 4.4 변성의 수학: 방향의 보존, 역전, 차단

세 가지 변성을 형식적으로 한 표에 모으면 원리가 더 분명해진다. $\sqsubseteq$를 하위 타입 관계, $F$를 타입 생성자라고 하자.

| 변성 | 표기 | 규칙 | 직관 | `T`가 나타날 수 있는 위치 |
|------|------|------|------|--------------------------|
| 공변 (covariant) | `out T` | $A \sqsubseteq B \Rightarrow F\langle A\rangle \sqsubseteq F\langle B\rangle$ | 방향 **보존** | out(생산)만 |
| 반공변 (contravariant) | `in T` | $A \sqsubseteq B \Rightarrow F\langle B\rangle \sqsubseteq F\langle A\rangle$ | 방향 **역전** | in(소비)만 |
| 무공변 (invariant) | `T` | 아무 관계 없음 | 방향 **차단** | out·in 모두 |

무공변이 out 위치와 in 위치를 *모두* 허용한다는 점에 주목하자. 무공변은 "안전을 위해 하위 타입 관계의 전파를 포기하는 대신, `T`를 자유롭게 생산하고 소비할 수 있다"는 거래다. 반대로 공변과 반공변은 "하위 타입 관계의 전파를 얻는 대신, `T`를 한쪽 용도로만 쓰도록 제한"한다. 이것이 변성의 근본적인 맞교환 관계다. 하위 타입 관계의 유연함과 사용의 자유를 동시에 모두 가질 수는 없다.

```text
        하위타입 전파 유연함  vs  T 사용의 자유
  out T:      얻음 (공변)          잃음 (생산만)
  in  T:      얻음 (반공변)        잃음 (소비만)
  (무공변):    잃음                얻음 (생산·소비 다)
```

가장 좋은 예는 함수 타입이다. Kotlin의 함수 타입 `(P) -> R`은 내부적으로 `Function1<in P, out R>`이다. 즉 **파라미터 타입은 반공변(`in`)이고, 반환 타입은 공변(`out`)이다**. 이것은 우연이 아니라 4.2절과 4.3절의 원리를 함수에 그대로 적용한 결과다. 함수는 파라미터를 *소비*하고 결과를 *생산*하기 때문이다.

```kotlin
fun main() {
    // (Cat) -> Any 자리에 (Animal) -> Cat 을 넣을 수 있는가?
    val stricter: (Animal) -> Cat = { _ -> Cat("복제묘") }
    val looser: (Cat) -> Any = stricter   // OK!
    // 파라미터: Cat <: Animal 인데 (Animal)->_ <: (Cat)->_  (반공변, 역전)
    // 반환:     Cat <: Any   이고  _->Cat  <: _->Any        (공변, 보존)
    val r: Any = looser(Cat("나비"))
    println(r)
}
```

`(Animal) -> Cat`이 `(Cat) -> Any`의 하위 타입이라는 규칙은 함수형 프로그래밍의 근본 원리 가운데 하나다. 함수 타입은 [[13 - 함수 타입과 람다와 함수 참조]]에서 자세히 다루고, 여기서는 이것이 변성의 두 방향을 한 타입에 담은 전형적인 사례라는 점만 확인한다.

원리를 정리했으니, 이제 변성을 코드의 *어디에 표시하는지* 살펴보자. 클래스 선언에 표시하는 방식(선언 지점)과 사용하는 곳에서 표시하는 방식(사용 지점)이 있다.

## 5. 선언 지점 변성: 클래스에 한 번 표시한다

### 5.1 `out T`/`in T`를 클래스 선언에 붙이기

Kotlin이 Java와 크게 다른 부분이 여기다. Java에서는 변성을 *사용할 때마다* 와일드카드(`? extends`, `? super`)로 붙여야 한다. Kotlin에서는 클래스를 *선언할 때 한 번* 변성을 표시할 수 있다. 이것을 **선언 지점 변성(declaration-site variance)** 이라고 한다.

```kotlin
interface Source<out T> {       // 이 인터페이스는 T의 생산자다 — 선언에 못박음
    fun next(): T
}

interface Sink<in T> {          // 이 인터페이스는 T의 소비자다
    fun put(item: T)
}
```

한 번 이렇게 선언해 두면 `Source<Cat>`을 `Source<Animal>`로 쓰는 모든 코드가 별도 표기 없이 그대로 동작한다. 표준 라이브러리의 `List<out E>`가 대표적인 예다. `List<Animal>`이 필요한 자리에 `List<Cat>`을 넘길 때 와일드카드를 전혀 쓰지 않아도 되는 이유는 `List`의 선언에 이미 `out`이 붙어 있기 때문이다.

```kotlin
fun printNames(animals: List<Animal>) {
    for (a in animals) println(a.name)
}

fun main() {
    val cats: List<Cat> = listOf(Cat("나비"), Cat("치즈"))
    printNames(cats)   // OK! List<out E> 라서 List<Cat> <: List<Animal>
}
```

### 5.2 컴파일러의 위치 검사: 변성은 강제되는 계약이다

`out`/`in`은 "이렇게 취급해 달라"는 요청이 아니라 컴파일러가 *검증하는 계약*이다. `out T`를 붙이면 컴파일러는 `T`가 소비(in) 위치에 나타나지 않는지 전부 검사한다.

```kotlin
interface Source<out T> {
    fun next(): T           // OK: T는 반환(out) 위치
    fun put(item: T)        // 컴파일 에러:
    // Type parameter T is declared as 'out' but occurs in 'in' position in type T
}
```

가장 자주 걸리는 곳은 `var` 프로퍼티다. `val` 프로퍼티는 게터만 있으므로 out 위치이지만, `var` 프로퍼티는 세터가 있으므로 in 위치이기도 하다.

```kotlin
class Box<out T>(val value: T)    // OK: val은 게터만 → out 위치
class Box2<out T>(var value: T)   // 컴파일 에러:
// Type parameter T is declared as 'out' but occurs in 'invariant' position
// (var의 세터 파라미터가 in 위치이기 때문)
```

4.1절에서 말한 원리와 암기의 차이가 실제로 드러나는 곳이 바로 이 검사다. "`out`=반환"만 외운 사람은 `var value: T`가 왜 막히는지 설명하지 못한다. 반면 "`out`은 `T`를 소비 위치에 쓰지 못하게 하고, `var`의 세터는 소비 위치다"라는 원리를 아는 사람은 바로 이해한다.

> [!note] 명세 기준
> 이 위치 검사에는 예외가 있다. **`private` 멤버는 클래스의 외부 계약이 아니므로 변성 위치 검사에서 제외된다.** 예를 들어 `class Box<out T>(private var value: T)`는 컴파일된다. 세터가 in 위치이긴 하지만 `private`이라서 외부에서 `T`를 넣을 통로가 없으므로 안전이 깨지지 않기 때문이다.
>
> 이 예외는 변성이 본질적으로 *공개 API 표면*에 대한 안전성 규칙이라는 점을 보여 준다. 소비가 외부에 노출되지 않으면 공변이어도 안전하다. (컴파일러의 판단을 더 강하게 무시하는 `@UnsafeVariance` 애노테이션은 34장(제네릭 2)에서 다룬다.)

### 5.3 표준 라이브러리의 변성 지도

Kotlin 표준 라이브러리를 읽어 보면 변성이 설계의 뼈대라는 점을 알 수 있다. 핵심적인 몇 가지를 표로 정리하자.

| 타입                                   | 변성  | 이유                                |
| ------------------------------------ | --- | --------------------------------- |
| `List<out E>`                        | 공변  | 읽기 전용 인터페이스라서 원소를 생산만 함           |
| `Iterable<out T>`, `Iterator<out T>` | 공변  | 순회하며 원소를 내보내기만 함                  |
| `MutableList<E>`                     | 무공변 | `add`(소비)와 `get`(생산)을 둘 다 함       |
| `Comparable<in T>`                   | 반공변 | `compareTo(other: T)`로 `T`를 소비만 함 |
| `Function1<in P, out R>`             | 혼합  | 파라미터 소비(in) + 결과 생산(out)          |
| `Array<T>`                           | 무공변 | 읽기·쓰기 둘 다(3.3)                    |

특히 `Comparable<in T>`의 반공변은 자세히 살펴볼 만하다. 동물끼리 비교할 수 있는 `Comparable<Animal>`은 `Comparable<Cat>`이 필요한 자리에 쓸 수 있다. 동물을 비교할 수 있으면 고양이도 당연히 비교할 수 있기 때문이다. 4.3절에서 본 반공변의 직관과 같다.

```kotlin
open class Animal(val name: String) : Comparable<Animal> {
    override fun compareTo(other: Animal): Int = name.compareTo(other.name)
}
class Cat(name: String) : Animal(name)

fun <T : Comparable<T>> sortInPlace(list: MutableList<T>) { /* ... */ }

fun main() {
    // Cat은 Comparable<Cat>을 직접 구현하진 않지만
    // Comparable<Animal>을 상속하고, Comparable<in T>의 반공변 덕에
    // Cat <: Comparable<Cat> 이 성립한다.
    val cats = mutableListOf(Cat("치즈"), Cat("나비"))
    cats.sort()   // OK: Comparable의 반공변이 이 정렬을 가능하게 함
    println(cats.map { it.name })   // => [나비, 치즈]
}
```

### 5.4 `List`와 `MutableList`: 변성으로 갈리는 두 타입

38장(컬렉션)에서 다룰 읽기 전용과 가변의 구분은 타입 이론으로 보면 여기에서 출발한다. `List<out E>`는 공변이고 `MutableList<E>`는 무공변이다. 이 차이는 우연이 아니라 4장에서 설명한 원리에서 바로 나온 결과다.

```kotlin
fun main() {
    val cats: List<Cat> = listOf(Cat("나비"))
    val animals: List<Animal> = cats          // OK: List는 공변

    val mCats: MutableList<Cat> = mutableListOf(Cat("나비"))
    val mAnimals: MutableList<Animal> = mCats  // 컴파일 에러: MutableList는 무공변
    // (만약 허용됐다면 mAnimals.add(Dog(...))로 고양이 리스트를 오염시킬 수 있다 — 3.2)
}
```

읽기 전용 `List`는 원소를 생산만 하므로 공변이어도 안전하다. 그러나 `MutableList`는 `add`로 원소를 소비하기도 하므로, 공변을 허용하면 3.2절의 힙 오염이 그대로 생긴다. 그래서 무공변이다. **변성은 "읽기 전용이면 넓혀도 되고, 가변이면 넓힐 수 없다"는 규칙을 타입 시스템으로 형식화한 것이다.** 컬렉션 계층 전체는 38장에서 설명한다.

선언 지점 변성은 강력하지만 한계가 있다. `MutableList` 같은 무공변 타입은 본질적으로 생산과 소비를 모두 하므로 선언에 `out`이나 `in`을 붙일 수 없다. 그런데 특정 사용처에서는 "이 함수 안에서는 이 리스트를 읽기만 한다"는 지역적인 사실이 있을 수 있다. 이 지역적인 사실을 타입으로 표현하는 것이 사용 지점 변성이다.

## 6. 사용 지점 변성: 타입 프로젝션으로 필요할 때마다 좁히기

### 6.1 무공변 타입을 호출하는 쪽에서 공변으로 다루기

`Array<T>`는 무공변이다(3.3절). 그런데 배열의 원소를 읽어 다른 배열에 복사하는 함수를 작성한다면, 원본 배열은 읽기만 하므로 공변이어도 안전하다. 이런 지역적인 안전성을 표현하는 것이 **사용 지점 변성(use-site variance)**, 즉 타입 프로젝션(type projection)이다.

```kotlin
fun copy(from: Array<out Any>, to: Array<Any>) {
    //          ^^^^^^^^^^^^^ out 프로젝션: from은 읽기 전용으로 취급
    for (i in from.indices) {
        to[i] = from[i]   // 읽기만 함 — 안전
    }
}

fun main() {
    val ints: Array<Int> = arrayOf(1, 2, 3)
    val anys: Array<Any> = arrayOf<Any>(0, 0, 0)   // 목적지 배열
    copy(ints, anys)   // OK! Array<Int>를 Array<out Any> 자리에 넘길 수 있다
    println(anys.toList())   // => [1, 2, 3]
}
```

`Array<out Any>`는 "원소 타입이 `Any`이거나 그 하위 타입인 어떤 배열"을 뜻한다. `from`을 이렇게 프로젝션하면, 이 함수 안에서 `from`은 *읽기 전용으로 투영(project)* 된다. 즉 `from[i]`로 읽을 수는 있지만 `from[i] = ...`로 쓸 수는 없다. 그 대신 `Array<Int>`, `Array<Cat>`처럼 원소가 `Any`의 하위 타입인 무공변 배열을 이 자리에 넘길 수 있다. 무공변 타입에 지역적으로 공변성을 부여한 것이다.

### 6.2 `out` 프로젝션: 쓰기 통로가 닫힌다

프로젝션의 핵심은 무언가를 얻는 대신 무언가를 잃는 맞교환이다. `out` 프로젝션은 공변성(하위 타입으로 넓히기)을 얻는 대신, `T`를 소비하는 멤버(쓰기)를 잃는다.

```kotlin
fun readOnly(list: MutableList<out Animal>) {
    val a: Animal = list[0]      // OK: get(): E 는 out 위치 → Animal로 나옴
    list.add(Cat("나비"))         // 컴파일 에러:
    // Type mismatch: inferred type is Cat but Nothing was expected
    // (add(element: E)의 E가 out 프로젝션되어 파라미터 타입이 Nothing이 됨)
    list.removeAt(0)             // OK: 인덱스만 받는 연산은 E를 소비하지 않음
}
```

여기서 어떤 일이 일어날까? `MutableList<out Animal>`로 프로젝션하면, 컴파일러는 `T`를 in 위치에 쓰는 멤버(`add(element: E)`, `set(index, element: E)`)의 파라미터 타입을 **`Nothing`으로 바꾼다**. `Nothing`은 값이 없는 바닥 타입(5장 타입 시스템의 지형, [[41 - 예외와 Nothing]])이므로 `add`에 넘길 수 있는 값이 존재하지 않고, 사실상 호출할 수 없다.

"쓰기 통로가 닫힌다"는 말은 실제로 이런 뜻이다. 반면 `get(): E`처럼 `T`를 out 위치에만 쓰는 멤버는 그대로 `Animal`을 반환하며 정상적으로 동작한다.

> [!note] 명세 기준
> `out` 프로젝션이 in 위치 파라미터를 `Nothing`으로 바꾸는 것은 8절에서 볼 "`Nothing`은 변성의 극한"이라는 주제와 정확히 맞물린다. `add`가 받을 수 있는 타입이 `Nothing`이라는 것은 "아무것도 받을 수 없다"를 타입 이론으로 표현한 것이다. Kotlin의 `out`/`in` 프로젝션은 Java의 `? extends T`/`? super T` 와일드카드에 정확히 대응하지만, `Nothing`이라는 진짜 바닥 타입이 있어서 그 의미가 더 깔끔하게 드러난다.

### 6.3 `in` 프로젝션: 읽으면 `Any?`만 나온다

반대로 `in` 프로젝션은 반공변성을 얻는 대신, `T`를 생산하는 멤버(읽기)에서 타입 정보를 잃는다.

```kotlin
fun fillWithCats(list: MutableList<in Cat>) {
    list.add(Cat("나비"))        // OK: Cat이나 그 하위를 넣을 수 있다
    list.add(Cat("치즈"))        // OK
    val x = list[0]              // x의 타입은 Any? (Cat이 아니다!)
    // in 프로젝션에서 get(): E 의 E는 Any?로 투영된다
    println(x)
}

fun main() {
    val animals: MutableList<Animal> = mutableListOf()
    fillWithCats(animals)   // OK! MutableList<Animal>을 MutableList<in Cat> 자리에
    val catBox: MutableList<Any> = mutableListOf()
    fillWithCats(catBox)    // OK! MutableList<Any>도 가능 (Cat의 상위 타입 리스트면 됨)
    println(animals.map { (it as Animal).name })  // => [나비, 치즈]
}
```

`MutableList<in Cat>`은 "원소 타입이 `Cat`이거나 그 상위 타입인 어떤 리스트"다. 어떤 상위 타입의 리스트든 고양이는 받아 주므로, `Cat`을 안전하게 *넣을* 수 있다. 그 대신 *읽을* 때는 컴파일러가 원소를 `Cat`이라고 보장할 수 없다. 실제로는 `Animal` 리스트일 수도 있고 `Any` 리스트일 수도 있기 때문이다. 그래서 `list[0]`은 모든 타입의 최상위, 즉 "가장 적게 아는" 타입인 `Any?`로 투영된다.

이 비대칭을 한눈에 정리하면 다음과 같다.

| 프로젝션 | 얻는 것(하위타입) | 읽기(out 멤버) | 쓰기(in 멤버) |
|----------|------------------|---------------|--------------|
| `MutableList<out Animal>` | `<Cat>`, `<Dog>` 등을 받음 | `Animal`로 읽힘 ✅ | `Nothing`이라 사실상 불가 ❌ |
| `MutableList<in Cat>` | `<Animal>`, `<Any>` 등을 받음 | `Any?`로만 읽힘 ⚠️ | `Cat` 이하를 넣음 ✅ |
| `MutableList<Animal>` (무공변) | `<Animal>`만 | `Animal`로 읽힘 ✅ | `Animal` 이하를 넣음 ✅ |

### 6.4 PECS와 Java 와일드카드 대응

이 규칙은 Java 커뮤니티에서 **Producer-Extends, Consumer-Super**, 줄여서 "PECS"라는 기억법으로 널리 알려져 있다. 생산자에는 `? extends`(Kotlin의 `out`)를, 소비자에는 `? super`(Kotlin의 `in`)를 쓴다는 뜻이다. Kotlin의 프로젝션은 이 와일드카드와 일대일로 대응한다.

```text
  Kotlin (사용지점)          Java (와일드카드)
  Array<out Any>       ↔    Array<? extends Object>   (읽기 전용 = 생산)
  MutableList<in Cat>  ↔    List<? super Cat>          (쓰기 전용 = 소비)
  MutableList<*>       ↔    List<?>                    (스타 프로젝션)
```

Java와의 핵심 차이는 Kotlin이 선언 지점 변성을 *추가로* 제공한다는 점이다. Java에는 선언 지점 변성이 없어서 `List`가 근본적으로 무공변이고, 그래서 사용하는 곳마다 와일드카드를 반복해야 한다. Kotlin에서는 `List<out E>`처럼 한 번 선언하면 대부분의 사용처에서 프로젝션이 필요 없다.

사용 지점의 프로젝션은 `MutableList`나 `Array`처럼 *처음부터 무공변인* 타입을 특정 문맥에서만 좁게 다루고 싶을 때 쓰는 도구다. Java 상호운용의 세부 사항은 45장(Java 상호운용)에서 다룬다.

프로젝션까지 보면 변성의 표현력은 거의 갖춰진다. 그러나 극단적인 경우가 하나 남아 있다. 타입 인자가 무엇인지 전혀 모르거나 알 필요가 없는 경우로, 이때 쓰는 것이 스타 프로젝션이다.

## 7. 스타 프로젝션 `*`: 알 수 없는 어떤 타입

### 7.1 `*`의 의미: "어떤 특정 타입이지만 무엇인지 모름"

제네릭 타입을 다루면서도 타입 인자에는 관심이 없을 때가 있다. 리스트의 크기를 출력하는 함수는 원소가 무엇이든 상관없다. 이럴 때 스타 프로젝션 `*`를 쓴다.

```kotlin
fun sizeOf(list: List<*>): Int = list.size

fun main() {
    println(sizeOf(listOf(1, 2, 3)))        // => 3
    println(sizeOf(listOf("a", "b")))       // => 2
    println(sizeOf(listOf<Cat>()))          // => 0
}
```

`List<*>`의 정확한 의미는 "**구체적인 타입 인자가 있긴 하지만, 그것이 무엇인지 모른다**"이다. 여기에는 중요한 차이가 숨어 있다. `*`는 "아무 타입이나(any type)"가 아니라 "알 수 없지만 하나로 정해진 특정 타입(some unknown but fixed type)"이다. 즉 `List<*>` 안의 원소는 모두 같은 타입이며, 다만 우리가 그 타입을 모를 뿐이다.

### 7.2 `*`와 `Any?`의 결정적 차이

여기서 가장 흔한 혼동을 정리하자.

> [!warning] 흔한 오해
> "`List<*>`는 무엇이든 담을 수 있는 리스트인 `List<Any?>`와 같다"고 생각하기 쉽다. **그러나 둘은 다르다.** `List<Any?>`는 "원소가 실제로 `Any?` 타입인, 즉 무엇이든 섞어 담기로 *약속한* 리스트"다. 반면 `List<*>`는 "원소 타입이 하나로 정해져 있지만 우리가 그것을 모르는 리스트"다. 앞의 것은 특정 타입 인자(`Any?`)이고, 뒤의 것은 타입 인자를 *모른다*는 사실을 표현한 것이다.

이 차이는 쓰기에서 크게 드러난다.

```kotlin
fun main() {
    val anyList: MutableList<Any?> = mutableListOf(1, "two")
    anyList.add(3.0)           // OK: Any? 리스트니까 무엇이든 추가 가능
    anyList.add(Cat("나비"))    // OK

    val starList: MutableList<*> = mutableListOf(1, 2, 3)
    starList.add(4)            // 컴파일 에러!
    // Required: Nothing, Found: Int
    // (원소의 진짜 타입을 모르므로, 무엇을 넣어도 그 타입을 위반할 수 있다)
}
```

`MutableList<*>`에는 *아무것도 추가할 수 없다.* 실제 리스트가 `MutableList<Int>`일 수도 있고 `MutableList<Cat>`일 수도 있는데, 컴파일러는 어느 쪽인지 모른다. `Cat`을 추가하도록 허용했는데 실제로는 `Int` 리스트였다면 힙 오염이 생긴다. 그래서 `*` 프로젝션에서는 6.2절의 `out` 프로젝션과 같은 논리로 in 위치가 `Nothing`이 되어 쓰기가 막힌다. 반면 읽기는 상한 타입으로 안전하게 할 수 있다.

```kotlin
fun main() {
    val starList: List<*> = listOf(1, 2, 3)
    val first: Any? = starList[0]    // 읽기는 OK, 단 타입은 Any? (상한)
    println(first)                    // => 1
}
```

### 7.3 `*`의 정확한 전개 규칙

명세의 핵심은 스타 프로젝션이 무공변, 공변, 반공변 타입 파라미터 각각에 대해 무엇으로 전개되는지다. 타입 파라미터의 상한을 $B$라고 하자.

| 원래 선언 | `Foo<*>`의 의미 | 읽기 | 쓰기 |
|-----------|----------------|------|------|
| `Foo<out T : B>` (공변) | `Foo<out B>` | `B`로 읽힘 | (원래 쓰기 없음) |
| `Foo<in T>` (반공변) | `Foo<in Nothing>` | (원래 읽기 없음) | `Nothing`이라 불가 |
| `Foo<T : B>` (무공변) | 읽기는 `out B`, 쓰기는 `in Nothing`처럼 | `B`로 읽힘 | `Nothing`이라 불가 |

즉 공변 파라미터의 `*`는 상한 `B`로의 `out` 프로젝션이고, 반공변 파라미터의 `*`는 `Nothing`으로의 `in` 프로젝션이다. 무공변 파라미터는 두 제약을 함께 받아 "읽으면 `B`, 쓰기는 불가"가 된다.

```kotlin
class Box<T : Number>(val v: T)

fun main() {
    val box: Box<*> = Box(42)
    val n: Number = box.v    // Box<*>는 Box<out Number> → v는 상한 Number로 읽힘
    println(n)                // => 42
}
```

`Box<T : Number>`에서 `Box<*>`는 `Box<out Number>`와 같으므로 `box.v`는 `Number`로 읽힌다. 상한이 정보를 제공하는 것이다. `*`라고 해서 무조건 `Any?`가 되는 것은 아니고, 선언된 상한만큼은 알 수 있다. 반대로 쓰기 쪽은 `in Nothing`으로 막혀 어떤 값도 넣을 수 없다.

스타 프로젝션은 타입 인자를 모르는 상태에서 그릇을 안전하게 다뤄야 할 때 쓰는 마지막 도구다. 리플렉션([[44 - 애노테이션과 리플렉션]]의 `KClass<*>`), 로깅, 크기 측정처럼 원소 타입과 관계없는 연산에서 쓰인다. 그런데 지금까지의 논의에는 `Nothing`이 계속 등장했다. `out` 프로젝션의 쓰기와 `*`의 쓰기는 모두 `Nothing`으로 귀결되었다. 이제 `Nothing`이 변성의 구조에서 어떤 자리를 차지하는지 살펴보자.

## 8. `Nothing`과 `Any?`: 변성의 두 극한

### 8.1 `List<Nothing>`: 모든 리스트의 하위 타입

`Nothing`은 값이 없는 바닥 타입이며 *모든 타입의 하위 타입*이다(5장 타입 시스템의 지형). 이 성질이 공변과 만나면 흥미로운 결과가 나온다. `List<out E>`가 공변이므로, $\text{Nothing} <: T$인 모든 $T$에 대해 다음이 성립한다.

$$
\text{Nothing} <: T \;\Rightarrow\; \text{List<Nothing>} <: \text{List<T>}
$$

즉 **`List<Nothing>`은 모든 `List<T>`의 하위 타입**이다. `emptyList()`가 어떤 타입의 리스트로도 쓰일 수 있는 이유가 바로 이것이다.

```kotlin
fun main() {
    val ints: List<Int> = emptyList()        // OK
    val cats: List<Cat> = emptyList()        // OK
    val strs: List<String> = emptyList()     // OK
    // 하나의 emptyList()가 모든 타입의 빈 리스트로 쓰인다
}
```

표준 라이브러리의 `emptyList()`는 내부적으로 `EmptyList`라는 싱글턴 객체 하나를 반환하는데, 그 타입은 개념적으로 `List<Nothing>`이다. 원소가 없으므로 원소 타입을 "아무것도 아님", 즉 `Nothing`으로 보는 것이 자연스럽다. 그리고 `List`가 공변이므로 이 빈 리스트 하나가 `List<Int>`, `List<Cat>` 등 어떤 타입으로도 쓰인다.

원소가 하나도 없으므로 "고양이를 꺼내려는데 정수가 나오는" 위험은 처음부터 없다. 꺼낼 것이 없기 때문이다. `Nothing`과 공변이 함께 이 안전성을 타입으로 증명한다.

```text
                List<Any?>
                    ▲
              List<Animal>
               ▲        ▲
         List<Cat>   List<Dog>
               ▲        ▲
                List<Nothing>   ← emptyList()가 여기 산다. 모든 List의 하위.
```

### 8.2 `Nothing`은 `out` 프로젝션과 `*`의 쓰기 자리다

6.2절과 7.2절에서 되풀이해 본 현상, 즉 `out` 프로젝션과 `*`의 in 위치가 `Nothing`이 되는 것도 같은 원리에서 나온다. "무엇을 넣어야 하는가?"에 대한 답이 `Nothing`이라는 것은 `Nothing`에 인스턴스가 없으므로 "넣을 수 있는 값이 존재하지 않는다"는 뜻이다. 즉 `Nothing`은 소비 위치의 극한인 "아무것도 소비할 수 없음"을, `Any?`는 생산 위치의 극한인 "무엇이 나올지 전혀 모름"을 표현한다.

```kotlin
fun main() {
    val list: MutableList<out Animal> = mutableListOf<Cat>()
    // add(element: E)에서 E가 out 프로젝션 → 파라미터 타입이 Nothing
    // list.add(???) — Nothing 타입의 값은 만들 수 없으므로 호출 불가
    // 유일하게 "될" 법한 것: 예외를 던지는 표현식(그 타입이 Nothing)
    // list.add(throw RuntimeException()) — 문법상 되지만 실행되면 예외 (무의미)
    println(list.size)   // 읽기·크기 등 E를 소비 안 하는 연산만 유효
}
```

소비의 극한인 `Nothing`과 생산의 극한인 `Any?`, 이 대칭이 변성의 전체 구조를 받친다. 어떤 제네릭 위치든 안전을 위해 필요한 "가장 제한적인 타입"으로 좁혀지고, 그 극한이 바닥 타입과 최상위 타입이다.

### 8.3 `MutableList<Nothing>`은 무엇인가

반대 방향의 질문도 해 보자. 무공변인 `MutableList<Nothing>`은 존재할 수는 있지만 거의 쓸모가 없다. 원소 타입이 `Nothing`이면 `Nothing` 인스턴스가 없으므로 `add`에 넘길 값이 없고, `get`은 `Nothing`을 반환하지만 그 값도 존재할 수 없다. 즉 "원소를 절대 가질 수 없는 가변 리스트"다. 실무에서는 "비어 있을 수밖에 없는 컬렉션"을 타입으로 표현할 때에만 가끔 등장한다.

반대쪽 극한인 `MutableList<Any?>`는 "무엇이든 담을 수 있는 리스트"로 흔히 쓰이지만, 7.2절에서 강조했듯 `MutableList<*>`와는 근본적으로 다르다. `Any?`는 *약속한* 최대의 유연성이고, `*`는 *모른다*는 표현이다.

이처럼 `Nothing`과 `Any?`가 변성의 두 극한에 있다는 점을 보면, 변성이 단순한 편의 규칙이 아니라 타입 계층 전체의 구조와 맞물린 근본 원리임을 알 수 있다. 부분 타입, 함수 공간에서의 공변과 반공변처럼 언어와 무관한 변성 이론의 기초는 타입 이론에서 더 깊이 다루며, 볼트의 타입 이론 시리즈에서 그 수학적 토대를 참조할 수 있다.

## 9. 실전에서 변성 때문에 막히는 곳: 흔한 함정과 판단 기준

### 9.1 무공변 타입을 반환하거나 저장할 때 생기는 문제

변성 규칙을 알아도 실전에서는 미묘한 곳에서 막힌다. 가장 흔한 실수는 무공변 타입을 공변 타입으로 착각하고 대입하는 것이다.

```kotlin
fun makeCatList(): MutableList<Cat> = mutableListOf(Cat("나비"))

fun main() {
    val animals: MutableList<Animal> = makeCatList()   // 컴파일 에러: 무공변
    // 해법 1: 읽기만 할 거면 읽기 전용 타입으로 받는다
    val readOnly: List<Animal> = makeCatList()          // OK: List는 공변
    // 해법 2: 진짜 가변 동물 리스트가 필요하면 새로 복사한다
    val fresh: MutableList<Animal> = makeCatList().toMutableList()  // OK
    println(readOnly.map { it.name })                   // => [나비]
}
```

여기서 얻을 교훈은 **가변성이 필요 없으면 읽기 전용 타입으로 받으라**는 것이다. `List<Animal>`로 받으면 공변이므로 `MutableList<Cat>`을 그대로 받을 수 있다. 38장(컬렉션)에서 강조하는 "읽기 전용 인터페이스로 노출한다"는 원칙이 변성과 만나는 지점이 여기다.

### 9.2 함수 파라미터에서 변성을 활용하는 판단 기준

함수 시그니처를 설계할 때 파라미터를 얼마나 넓게 받을지는 변성으로 조절한다. 원소를 읽기만 하는 함수는 `List<out T>`라고 쓸 필요 없이 이미 공변인 `List<T>`를 받으면 된다. 무공변 타입을 파라미터로 받으면서 함수 안에서 읽기만 한다면 `out` 프로젝션으로 넓게 받는다.

```kotlin
// 나쁨: 무공변 MutableList<Animal>만 받아 유연성이 없다
fun countNamed(list: MutableList<Animal>, name: String): Int =
    list.count { it.name == name }

// 좋음: 읽기만 하므로 List<out Animal>(=List<Animal>)로 넓게 받는다
fun countNamedBetter(list: List<Animal>, name: String): Int =
    list.count { it.name == name }

fun main() {
    val cats: List<Cat> = listOf(Cat("나비"), Cat("나비"))
    // countNamed(cats, "나비")        // 에러: List<Cat> ↛ MutableList<Animal>
    println(countNamedBetter(cats, "나비"))   // => 2  (공변 덕에 통과)
}
```

판단 기준을 한 문장으로 정리하면 다음과 같다. **함수 안에서 그 파라미터로부터 값을 꺼내기만 하면 out(또는 공변 타입), 값을 넣기만 하면 in, 둘 다 하면 무공변을 쓴다.** 4장에서 설명한 원리를 실무에 그대로 적용한 것이다.

### 9.3 변성과 타입 소거 (34장 미리 보기)

마지막으로 변성을 다룰 때 반드시 기억해야 할 경계가 하나 있다. 변성은 *컴파일 타임* 개념이다. JVM 백엔드에서는 런타임에 타입 인자가 소거되므로, `List<Cat>`과 `List<Dog>`는 런타임에 똑같은 `List`다.

```kotlin
fun main() {
    val cats: List<Cat> = listOf(Cat("나비"))
    val dogs: List<Dog> = listOf(Dog("바둑이"))
    println(cats::class == dogs::class)   // => true (둘 다 런타임엔 그냥 List)
    // cats is List<Cat> — 이런 검사는 컴파일 에러 (소거로 확인 불가)
}
```

즉 이 장에서 다룬 `out`, `in`, 프로젝션, `*` 같은 변성 검사는 모두 *소스 코드와 컴파일러 단계*에서 안전을 보장한다. 런타임에 타입 인자가 남지 않는다는 사실과, `reified inline`으로 소거를 제한적으로 우회하는 방법은 34장(제네릭 2)에서 다룬다. 변성이 컴파일 타임에 이렇게 엄격한 이유 중 절반은 런타임에 도움이 될 타입 정보가 없기 때문이기도 하다. 컴파일러가 지금 안전을 지켜 두지 않으면 나중에는 아무도 지켜 주지 않는다.
