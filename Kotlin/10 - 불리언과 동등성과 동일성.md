[[07 - 수 1 - Int와 Long과 부동소수점]]과 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]에서는 수가 기계에서 어떻게 표현되는지, 즉 JVM 백엔드에서 언제 원시형이 되고 언제 박스로 감싸지는지를 살펴보았다. [[09 - 문자와 문자열 - 유니코드와 템플릿]]에서는 `String`이 불변이고 `==`로 내용을 비교한다는 사실을 짧게 언급하고 넘어갔다. 이 장에서는 그 문장을 자세히 살펴본다.

두 값이 "같은지" 판정하는 일은 프로그래밍에서 가장 흔하면서도 가장 미묘한 연산이다. Kotlin은 이 연산을 **구조적 동등**(structural equality) `==`와 **참조 동일**(referential identity) `===` 두 가지로 나누었다. 이 구분을 이해하지 못한 채 Java 습관을 그대로 가져오면, 자신도 모르는 사이에 버그를 만들게 된다.

이 장에서는 세 가지를 다룬다. 첫째는 값이 둘뿐인 가장 작은 타입인 **불리언**(Boolean)과 그 위의 논리 연산(단축 평가 `&&`/`||`와 즉시 평가 `and`/`or`)이다. 둘째는 **동등성**으로, `==`가 `equals` 호출로 바뀌는 과정, `equals`가 지켜야 하는 계약, 그 계약과 짝을 이루는 `hashCode`를 살펴본다.

셋째는 **동일성**으로, `===`가 무엇을 비교하는지, 그리고 JVM 백엔드의 박싱 캐시 때문에 이 연산의 결과를 예측하기 어려워지는 이유를 설명한다. 마지막으로 부동소수점 동등의 함정(NaN, `-0.0`)과, `Comparable`/`compareTo`가 정하는 순서라는 또 다른 동등까지 다룬다.

연산자 오버로딩의 관례 함수 전체(`equals`, `compareTo`가 어떤 관례로 `==`/`<`에 연결되는지)는 [[19 - 연산자 오버로딩과 관례]]에서 다루고, 여기서는 동등과 순서에 필요한 만큼만 먼저 가져다 쓴다.

`data class`가 `equals`/`hashCode`를 자동 생성하는 방식과 그 함정은 [[27 - 데이터 클래스]], `null` 처리(안전 호출 `?.`, 엘비스 `?:`, 스마트 캐스트)는 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]], 읽기 전용 컬렉션과 가변 컬렉션, 배열의 특수성은 [[38 - 컬렉션 - 읽기 전용과 가변]]에서 설명한다.

## 1. 불리언: 값이 둘뿐인 타입

### 1.1 Boolean은 독립된 타입이다

Kotlin의 `Boolean`은 `true`와 `false`, 정확히 두 값만 가지는 타입이다. C처럼 `0`을 거짓으로, `0이 아니면` 참으로 보는 정수 기반 표현이 아니며, 조건문에 정수나 널을 넣을 수도 없다. 따라서 `if (1)`은 컴파일되지 않는다.

```kotlin
val isRaining: Boolean = true
val hasUmbrella = false        // 타입 추론 → Boolean

if (isRaining) println("우산 챙기기")
// if (1) { ... }              // 컴파일 에러: Int는 Boolean이 아니다
// val x: Boolean = null       // 컴파일 에러: null은 Boolean에 대입 불가
```

`Boolean`은 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서 본 타입 계층에 정식으로 속하는 타입이다. `Any`의 하위 타입이고 `Comparable<Boolean>`을 구현한다. 따라서 `false < true`가 성립한다(8절에서 `compareTo`를 다룰 때 다시 살펴본다).

```kotlin
println(false < true)          // => true
println(true.compareTo(false)) // => 1  (양수 = 좌변이 크다)
```

> [!note] 명세 기준
> JVM 백엔드에서 `Boolean`은 가능한 곳에서는 원시 `boolean`으로 컴파일되고, 널 가능 위치나 제네릭 위치에서는 박스형 `java.lang.Boolean`으로 컴파일된다. 8장(박싱과 오버플로)에서 본 원시형과 박스형의 이중성과 같은 원리이다. 이는 JVM 백엔드에만 해당하는 표현이며, Native/JS/Wasm 백엔드는 각자 다른 표현을 사용한다.

### 1.2 논리 연산: 단축 평가와 즉시 평가

Kotlin은 불리언 논리 연산을 **두 가지**로 제공한다. 이 차이를 모르면 부수 효과(side effect)가 있는 코드에서 알아채기 어려운 버그가 생긴다.

| 연산 | 이름 | 단축 평가 | 형태 |
|------|------|-----------|------|
| `&&` | 논리 곱(AND) | O (좌변이 `false`면 우변 미평가) | 연산자 |
| `\|\|` | 논리 합(OR) | O (좌변이 `true`면 우변 미평가) | 연산자 |
| `!` | 부정(NOT) | - | 연산자 |
| `and` | 논리 곱 | **X** (항상 양변 평가) | 중위 함수 |
| `or` | 논리 합 | **X** (항상 양변 평가) | 중위 함수 |
| `xor` | 배타적 합 | X | 중위 함수 |
| `not()` | 부정 | - | 함수 |

`&&`와 `||`는 **단축 평가**(short-circuit evaluation)를 한다. 왼쪽만으로 결과가 정해지면 오른쪽은 아예 계산하지 않는다. 반면 `and`와 `or`는 kotlin.Boolean에 정의된 평범한 **중위 함수**이다. 함수 호출이므로 인자인 우변을 항상 먼저 평가한다.

```kotlin
fun sideEffect(): Boolean {
    println("우변 평가됨!")
    return true
}

val a = false && sideEffect()  // "우변 평가됨!" 출력 안 됨 (단축)
// => a = false, 아무것도 출력 안 함

val b = false and sideEffect() // "우변 평가됨!" 출력됨 (즉시)
// => 콘솔: 우변 평가됨!
// => b = false
```

이 차이는 **널 검사**나 **비용이 큰 계산**을 오른쪽에 둘 때 결과를 좌우한다.

```kotlin
val name: String? = null
// 단축 평가 덕분에 안전: 좌변이 false면 name!!.length는 절대 실행 안 됨
if (name != null && name.length > 3) { /* ... */ }

// 'and'였다면 name.length가 평가되어 스마트 캐스트도, 널 검사도 무의미
// if (name != null and name.length > 3)  // 스마트캐스트 안 되고 위험
```

`name != null && name.length > 3`의 우변에서 `name`이 널이 아닌 타입으로 **스마트 캐스트**(6장 널 안전성)되는 것도 `&&`의 단축 평가 규칙 덕분이다. 컴파일러는 우변이 좌변이 참일 때만 평가된다는 사실을 알고 있으므로, 우변 안에서 `name`의 타입을 널이 아닌 타입으로 좁힐 수 있다. `and`는 이런 흐름을 보장하지 않으므로, 같은 자리에 쓰면 의미가 달라진다.

> [!caution] 성능 주의
> `and`/`or`는 양변을 모두 평가해야 할 때를 위해 존재한다. 예를 들어 양쪽 모두 부수 효과가 필요하거나, 분기 예측 실패 비용이 단축 분기보다 클 때이다. 일상적인 조건 논리에서는 거의 항상 `&&`/`||`가 맞다.
>
> `and`/`or`는 정수의 비트 연산 `and`/`or`(8장 박싱과 오버플로)와 이름이 같지만, 수신 타입이 `Boolean`이면 논리 연산이고 `Int`면 비트 연산인 서로 다른 함수이다.

### 1.3 불리언과 동등성: 가장 단순한 경우

Kotlin에는 C나 JavaScript에 있는 **진리값 강제 변환**(truthiness)이 없다. `if`, `while`, `&&`, `||`, `!`의 피연산자는 반드시 `Boolean`이어야 한다. `0`이나 빈 문자열, `null`이 조건에서 "거짓처럼" 취급되는 일은 없다. 이 엄격함은 [[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]]에서 말한 "안전"이라는 설계 목표와 이어진다. 의도하지 않은 암묵적 변환을 언어 차원에서 막는 것이다.

```kotlin
val list = listOf(1, 2, 3)
// if (list) { ... }               // 컴파일 에러: List는 Boolean이 아니다
if (list.isNotEmpty()) { /* ... */ }  // 의도를 명시적으로

val text: String? = null
// if (text) { ... }               // 컴파일 에러
if (text != null) { /* ... */ }    // 명시적 널 검사
```

자매 시리즈에서 다루는 JavaScript의 `if (x)`가 `x`의 truthiness를 보는 것과 크게 다르다. Kotlin에서는 무엇이 참인지를 개발자가 매번 `Boolean` 식으로 명시해야 한다. 그래서 "빈 문자열이 왜 false지?" 같은 언어별 진리값 규칙을 외울 필요가 없다.

불리언은 동등성을 살펴보기에 가장 단순한 대상이다. 값이 둘뿐이므로 `==`, `===`, 논리적 동치를 뜻하는 `==`가 모두 같은 것처럼 보인다.

```kotlin
val p = true
val q = true
println(p == q)   // => true  (구조적: 두 값이 같은 진리값)
println(p === q)  // => true  (참조: 아래 설명)
```

JVM 백엔드에서 `Boolean?`을 박싱하면 `java.lang.Boolean.TRUE`/`FALSE`라는 고정된 캐시 인스턴스를 재사용한다. 따라서 박스형 `true`끼리는 항상 같은 객체이고, `===`도 `true`가 된다.

하지만 이것은 4절에서 "박싱 캐시가 만드는 착시"라고 부를 바로 그 현상이다. 불리언에서는 캐시가 모든 값을 포함하므로 우연히 안전해 보일 뿐이고, `===`의 결과에 의미를 두어서는 안 된다. 불리언에는 항상 `==`(또는 그냥 `if (b)`)를 쓰고 `===`는 쓰지 않는다. 본격적인 문제는 다음 절부터 시작된다.

## 2. Java와 반대인 규칙: Java의 `==` 습관을 버려라

### 2.1 흔한 오해 바로잡기

**흔한 오해: "`==`는 참조를 비교한다."** Java에서 온 개발자가 가장 자주, 그리고 눈에 띄지 않게 만드는 버그가 여기서 나온다. Java에서 `a == b`는 두 변수가 같은 객체를 가리키는지, 즉 **참조 동일성**을 비교한다. 내용을 비교하려면 `a.equals(b)`를 따로 호출해야 한다. 그래서 Java 개발자는 `"foo" == someString`의 결과를 예측할 수 없다는 점을 경험으로 잘 알고 있다.

Kotlin은 이 관계를 **뒤집었다**. Kotlin에서는 다음과 같다.

- `==`(그리고 `!=`)는 **구조적 동등**을 비교한다. 내부적으로 `equals`를 호출한다.
- `===`(그리고 `!==`)는 **참조 동일**을 비교한다. 두 참조가 같은 객체인지 확인한다.

```kotlin
val s1 = StringBuilder("cat").toString()   // "cat"
val s2 = StringBuilder("cat").toString()   // 다른 "cat" 인스턴스

println(s1 == s2)   // => true   (내용 같음, equals 호출)
println(s1 === s2)  // => false  (서로 다른 객체)
```

```java
// Java — 정반대 습관
String s1 = new StringBuilder("cat").toString();
String s2 = new StringBuilder("cat").toString();
System.out.println(s1 == s2);        // => false  (참조 비교)
System.out.println(s1.equals(s2));   // => true   (내용 비교)
```

같은 두 줄이 `==`에 대해 정반대의 답을 낸다. Kotlin의 `s1 == s2`는 Java의 `s1.equals(s2)`에 해당하고, Kotlin의 `s1 === s2`는 Java의 `s1 == s2`에 해당한다.

Java 습관대로 "내용을 비교하려면 `.equals()`를 써야 한다"고 생각해 Kotlin에서 굳이 `.equals()`를 호출하는 것은 틀리지는 않지만 관용적이지 않다. 반대로 "참조가 아니라 값을 보려면 `==`를 피해야 한다"고 생각하는 순간 버그가 생긴다.

### 2.2 대조표: 두 언어의 연산자 대응

| 의도 | Kotlin | Java |
|------|--------|------|
| 내용(구조)이 같은가 | `a == b` | `a.equals(b)` (혹은 `Objects.equals`) |
| 같은 객체인가(동일성) | `a === b` | `a == b` |
| 내용이 다른가 | `a != b` | `!a.equals(b)` |
| 다른 객체인가 | `a !== b` | `a != b` |

이 장에서 외워야 할 표는 이것 하나뿐이다. **Kotlin `==` = Java `.equals`**, **Kotlin `===` = Java `==`** 이다. 나머지 내용은 이 대응을 자세히 살펴보는 것이다.

### 2.3 왜 이렇게 설계했나

Kotlin이 `==`를 `equals`로 정의한 이유는 1장(코틀린이란 무엇인가)에서 설명한 설계 철학인 **실용주의** 때문이다. 실제 코드에서 개발자가 원하는 것은 대부분 "내용이 같은가"이고, "같은 메모리 주소인가"가 아니다.

Java에서 문자열을 `==`로 비교했다가 생기는 버그는 수많은 신입 개발자를 괴롭혔다. Kotlin은 자주 쓰는 의도에 짧은 문법을 배정한다는 원칙에 따라 `==`를 구조적 동등에 할당했다. 그리고 참조 동일성이 필요한 드문 경우(캐시 식별, 싱글턴 확인, 순환 참조 감지)를 위해 `===`를 따로 남겨 두었다.

> [!info] 역사 메모
> `===`(등호 세 개)는 Kotlin이 새로 만든 기호가 아니다. JavaScript의 `===`("엄격 동등")에서 모양을 따왔지만 의미는 다르다. JS의 `===`는 *타입 강제 변환 없는 동등* 비교이고, Kotlin의 `===`는 *참조 동일* 비교이다. 두 언어를 함께 쓰는 개발자는 이 차이에 특히 주의해야 한다. (자매 시리즈 JavaScript의 `==`/`===` 비교를 참고한다.)

## 3. `==`의 정확한 탈설탕과 null 안전

### 3.1 `a == b`는 무엇으로 번역되는가

"`==`는 equals를 호출한다"는 설명은 절반만 맞다. 정확한 탈설탕(desugaring) 결과에는 널 안전 처리가 포함되어 있다. Kotlin 명세에 따르면 `a == b`는 다음과 같이 번역된다.

```kotlin
a?.equals(b) ?: (b === null)
```

이 한 줄을 나누어 보면 `==`의 성질이 모두 드러난다.

- `a`가 널이 아니면 `a.equals(b)`를 호출한다. 구조적 비교의 본체가 이 부분이다.
- `a`가 널이면 안전 호출 `?.`가 `null`을 반환하므로 엘비스 `?:`의 우변 `(b === null)`이 평가된다. 즉 **양쪽이 모두 널이면 `true`** 이고, `a`만 널이면 `false`이다.

핵심은 두 가지이다. 하나는 이 식이 **좌변(`a`)의 `equals`를 호출한다**는 점이고, 다른 하나는 **좌변이 널이어도 NPE를 던지지 않는다**는 점이다. Java에서는 `a`가 널이면 `a.equals(b)`가 NPE를 던지지만, Kotlin의 `==`는 안전 호출로 감싸져 있으므로 어느 피연산자가 널이어도 예외가 발생하지 않는다.

```kotlin
val a: String? = null
val b: String? = null
val c: String? = "x"

println(a == b)   // => true   (둘 다 null → b === null → true)
println(a == c)   // => false  (a는 null, c는 not null)
println(c == a)   // => false  (c.equals(null) → false)
println(a == null)// => true
```

### 3.2 좌변을 기준으로 하는 비대칭

`a == b`가 `a.equals(b)`로 번역된다는 사실에는 미묘한 결과가 따른다. **어느 쪽의 `equals`를 호출할지는 좌변이 결정한다.** 잘 설계된 `equals`는 대칭적이므로(5절) 보통은 차이가 드러나지 않는다. 하지만 `equals`를 잘못 구현하면 `a == b`와 `b == a`가 서로 다른 답을 낼 수 있다.

```kotlin
class CaseInsensitive(val s: String) {
    override fun equals(other: Any?): Boolean =
        other is CaseInsensitive && s.equals(other.s, ignoreCase = true)
    override fun hashCode() = s.lowercase().hashCode()
}

val x = CaseInsensitive("Cat")
val y = CaseInsensitive("cat")
println(x == y)   // => true  (x.equals(y))
println(y == x)   // => true  (y.equals(x)) — 여기선 대칭이 지켜짐
```

이 예에서는 대칭이 지켜지지만, 상속이 끼어들면 대칭이 깨진다(5.3절에서 자세히 다룬다). 지금은 **`==`에 방향이 있다**는 점, 즉 좌변의 타입이 호출될 `equals`를 정한다는 점만 기억하면 된다.

### 3.3 정적 타입이 원시형이면 다르다

`==`가 항상 `equals` 메서드 호출로 바뀌는 것은 아니다. **JVM 백엔드에서** 피연산자의 정적 타입이 원시형으로 표현되는 경우(`Int`, `Long`, `Double`, `Boolean` 등 널 불가 타입), 컴파일러는 `equals`를 호출하는 대신 원시형 비교 명령(바이트코드 `if_icmpeq` 등)을 생성한다. 값을 비교한다는 의미는 대부분 같지만, 부동소수점에서는 이 차이가 결과를 바꾼다(7절).

```kotlin
val i = 42
val j = 42
println(i == j)  // JVM 백엔드에서: 박싱/equals 없이 원시 int 비교
```

즉 `==`의 의미는 "구조적 동등"으로 통일되어 있지만, 그 구조적 동등을 *구현하는 코드*는 정적 타입에 따라 (a) 원시형 직접 비교가 되거나 (b) `equals` 호출이 된다. 이렇게 구현이 두 가지이기 때문에 부동소수점에서는 결과가 두 가지로 갈린다.

> [!note] 명세 기준
> 위의 탈설탕 `a?.equals(b) ?: (b === null)`은 피연산자가 널 가능 타입이거나 참조형일 때의 개념적인 형태이다. 정적 타입이 널이 아닌 원시형이면 컴파일러는 이 형태를 거치지 않고 원시 비교로 최적화한다. 두 경로가 부동소수점에서 어떻게 달라지는지는 7절에서 다룬다. 이 원시 비교 최적화는 JVM 백엔드의 특성이다.

### 3.4 `!=`와 `!==`, 그리고 부정의 탈설탕

`!=`는 `==`의 부정이고, `!==`는 `===`의 부정이다. 정확히 번역하면 다음과 같다.

| 표현 | 번역 |
|------|------|
| `a != b`  | `!(a == b)` → `!(a?.equals(b) ?: (b === null))` |
| `a !== b` | `!(a === b)` |

`!=`도 `==`와 마찬가지로 널 안전하다. 어느 피연산자가 널이어도 NPE가 발생하지 않는다. 그래서 `if (x != null)`을 안전하게 쓸 수 있고, 이 식이 스마트 캐스트가 시작되는 지점이 된다(6장 널 안전성).

`x != null`을 풀어 쓰면 `!(x?.equals(null) ?: (null === null))`이다. 좌변 `x`가 `null`이면 `null === null`이 `true`이므로 `==`는 `true`, `!=`는 `false`가 된다. 따라서 `x != null`은 "널이 아닐 때만 `true`"로 정확히 동작한다.

```kotlin
val x: String? = null
println(x != null)   // => false  (x는 null이므로 "널 아님"은 거짓)
val y: String? = "a"
println(y != null)   // => true

// != 도 좌변 equals의 부정 — 커스텀 equals를 그대로 반영
data class Tag(val v: String)
println(Tag("a") != Tag("b"))  // => true
```

부정 연산자 `!`는 `Boolean`에만 적용되며, `not()` 함수의 연산자 형태이다. `!` 뒤에 오는 식이 `Boolean`이 아니면 컴파일 에러가 난다. 이 엄격함은 truthiness가 없다는 점(1.3절)과 같은 맥락이다.

## 4. `===` 참조 동일성과 박싱 캐시의 함정

### 4.1 `===`는 무엇을 비교하나

`a === b`는 **두 참조가 힙에 있는 같은 객체를 가리키는지**를 확인한다. `equals`를 호출하지 않으며, 재정의할 수도 없다. 연산자 오버로딩 대상이 아니기 때문이다(19장 연산자 오버로딩). 순수하게 물리적인 동일성만 비교한다.

```kotlin
class Point(val x: Int, val y: Int)

val p = Point(1, 2)
val q = p
val r = Point(1, 2)

println(p === q)  // => true   (같은 객체, q는 p의 별칭)
println(p === r)  // => false  (내용은 같지만 다른 객체)
println(p == r)   // => false  (Point는 equals 미재정의 → Any.equals → 참조 비교)
```

마지막 줄을 눈여겨볼 만하다. `Point`는 `equals`를 재정의하지 않았으므로 `Any`의 기본 `equals`를 사용하는데, `Any.equals`는 **참조 동일성**으로 구현되어 있다. 따라서 `equals`를 재정의하지 않은 클래스에서는 `==`와 `===`가 같은 답을 낸다. `data class`(27장 데이터 클래스)로 만들거나 `equals`를 직접 재정의해야 `==`가 구조적 비교로 동작한다.

### 4.2 흔한 오해 바로잡기: `===`가 모든 값에서 의미 있는 것은 아니다

**흔한 오해: "`===`는 어떤 값에든 명확한 의미가 있다."** 참조 동일성은 *객체*에서만 의미가 있다. 그런데 JVM 백엔드에서는 정적 타입이 원시형으로 컴파일되는 값이면 `===`가 `==`와 사실상 같아진다. 반면 박스형으로 컴파일되는 값이면 **박싱 캐시** 때문에 결과를 예측할 수 없게 된다.

먼저 명세가 보장하는 부분부터 보자. 정적 타입이 런타임에 원시형으로 표현되는 값(예: 널이 아닌 `Int`)에서는 `===` 검사가 `==` 검사와 **동등**하다. 원시형에는 "참조"가 없으므로, 물리적 동일성이 값의 동일성과 같은 의미가 된다.

문제는 **박싱이 끼어들 때** 생긴다. `Int?`나 `Any`로 상향 변환된 `Int`, 제네릭 타입 인자로 들어간 `Int` 등은 JVM 백엔드에서 `java.lang.Integer` 박스가 된다. 그리고 `java.lang.Integer.valueOf`는 `-128..127` 범위의 값에 대해 **캐시된 박스 인스턴스**를 재사용한다(JLS가 요구하는 캐시이다). 그 결과는 다음과 같다.

```kotlin
val a: Int? = 127
val b: Int? = 127
println(a === b)  // => true   (127은 캐시 → 같은 Integer 객체)

val c: Int? = 128
val d: Int? = 128
println(c === d)  // => false  (128은 캐시 밖 → 서로 다른 Integer 객체)

println(a == b)   // => true   (구조적 동등, 언제나 값으로)
println(c == d)   // => true   (구조적 동등, 언제나 값으로)
```

`127 === 127`은 `true`인데 `128 === 128`은 `false`이다. 두 경우 모두 같은 값끼리 비교하는데도, 캐시 경계 하나 때문에 답이 뒤집힌다. 핵심은 다음과 같다. **박스로 표현되는 값에 `===`를 쓰면 결과가 백엔드의 박싱 캐시 전략에 따라 달라지며, 언어는 그 결과를 보장하지 않는다.**

```text
Int? 박싱 캐시 (JVM 백엔드, Integer.valueOf)

 값:  ...  -129  -128 ─────────── 127  128  129  ...
                  └── 캐시된 공유 박스 ──┘
             (===가 값이 같으면 true)   (매번 새 박스, ===는 false)

핵심: === 의 답이 "값"이 아니라 "어느 박스 인스턴스냐"에 달림
```

### 4.3 왜 이런 일이 생기고, 어떻게 피하나

이 함정은 8장(박싱과 오버플로)에서 본 박싱에서 비롯된다. `Int`는 원시형이지만 널 가능 위치나 제네릭 위치에서는 박스가 된다. 박스는 힙 객체이므로 참조 동일성이라는 개념이 다시 생긴다. 그런데 JVM은 작은 정수 박스를 캐시로 공유하므로, 값에 따라 참조 동일성이 성립하기도 하고 성립하지 않기도 한다.

**교훈은 단순하다. 수, 불리언, 문자 같은 값 타입에는 절대 `===`를 쓰지 않는다.** 값이 같은지는 항상 `==`로 확인한다. `===`는 "이것이 바로 저 특정 객체인가"를 물을 때, 즉 실제로 참조를 식별해야 하는 캐시, 싱글턴, 순환 감지에서만 의미가 있다. 그런 대상은 원시형으로 컴파일되지 않는 실제 객체이다.

> [!caution] 성능 주의
> JVM에서는 `-XX:AutoBoxCacheMax`로 캐시 범위(`-128..127`)의 상한을 조정할 수 있으므로, 환경에 따라 범위가 더 넓어질 수도 있다. 이 사실은 박싱 캐시에 기대는 `===`의 결과가 환경에 따라 달라진다는 점을 다시 확인해 준다. 이식성 있는 코드는 절대 이 캐시에 의존해서는 안 된다.

> [!warning] 흔한 오해
> "`===`가 `true`면 확실히 같은 값이다"는 참이다(같은 객체이면 같은 값이다). 하지만 그 역인 "값이 같으면 `===`가 `true`이다"는 박스형에서 거짓이다. `===`는 값 동등의 충분조건도 필요조건도 아니며, 물리적 동일성이라는 전혀 다른 질문이다.

### 4.4 `===`를 정당하게 쓰는 경우

`===`를 무조건 피할 필요는 없다. 정당하게 쓰는 경우가 있다.

```kotlin
// (1) equals 구현 안에서의 빠른 경로: 같은 객체면 즉시 true
class Vector(val dx: Double, val dy: Double) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true        // 동일 객체면 빠르게 종료
        if (other !is Vector) return false
        return dx == other.dx && dy == other.dy
    }
    override fun hashCode() = 31 * dx.hashCode() + dy.hashCode()
}

// (2) 싱글턴/센티넬 확인
object Empty
val token: Any = Empty
println(token === Empty)   // => true, 이 센티넬 그 자체인지 확인

// (3) 널 리터럴 비교 — null === null은 관용적
```

이 세 경우에 `===`는 "바로 그 객체인가"를 정확하게 묻는다. 특히 (1)은 `equals` 구현의 표준 관용구이다. 값 타입이 아니라 **참조의 정체성이 중요한 대상**에만 `===`를 쓴다는 원칙을 지키면 박싱 캐시의 함정을 완전히 피할 수 있다.

## 5. `equals` 계약: 다섯 가지 조항

### 5.1 `Any.equals`와 다섯 가지 계약

`==`가 결국 `equals`를 호출한다면, `equals`가 올바르게 동작해야 `==`도 믿을 수 있다. `equals`는 `Any`에 선언된 메서드이다.

```kotlin
open operator fun equals(other: Any?): Boolean
```

`operator`가 붙어 있으므로 `==`가 이 함수로 탈설탕된다(19장 연산자 오버로딩). 파라미터 타입이 `Any?`라는 점이 중요하다. 어떤 타입이든, 널이든 받을 수 있어야 한다는 뜻이다. `equals`를 재정의할 때는 다음 **다섯 가지 계약**을 반드시 지켜야 한다. 수학적으로는 동치 관계의 성질에 널 처리를 더한 것이다.

1. **반사성**(reflexive): 널이 아닌 `x`에 대해 `x.equals(x)`는 항상 `true`이다.
2. **대칭성**(symmetric): `x.equals(y)`가 `true`이면 `y.equals(x)`도 `true`이다.
3. **추이성**(transitive): `x.equals(y)`이고 `y.equals(z)`이면 `x.equals(z)`이다.
4. **일관성**(consistent): 비교에 쓰는 정보가 바뀌지 않는 한, 여러 번 호출해도 결과가 같다.
5. **널 처리**: 널이 아닌 `x`에 대해 `x.equals(null)`은 항상 `false`이다.

이 계약은 강제되지 않는다. 컴파일러가 검사하지 못하기 때문이다. 계약을 어겨도 컴파일은 되지만, 해시 기반 컬렉션이나 정렬, 캐시 등이 아무 경고 없이 잘못 동작한다. 이 계약이 곧 "믿을 수 있는 동등"의 정의이다.

### 5.2 올바른 수동 구현의 기본 형태

```kotlin
class Money(val amount: Long, val currency: String) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true          // 반사성 빠른 경로 + 성능
        if (other !is Money) return false        // 타입 다르면 false (널 처리 포함:
                                                 //   null is Money → false)
        return amount == other.amount && currency == other.currency
    }

    override fun hashCode(): Int =               // 6절에서 필수임을 설명
        31 * amount.hashCode() + currency.hashCode()
}

val m1 = Money(1000, "KRW")
val m2 = Money(1000, "KRW")
val m3 = Money(1000, "USD")
println(m1 == m2)   // => true
println(m1 == m3)   // => false
println(m1 == null) // => false  (null is Money가 false → 계약5 만족)
```

`other is Money` 검사 하나가 두 가지 계약을 함께 처리한다. `null is Money`는 `false`이므로 널 처리(계약 5)가 자동으로 만족되고, 타입이 다르면 `false`를 반환하므로 서로 다른 타입끼리의 비교도 막는다. `this === other` 빠른 경로는 반사성을 보장하면서(자기 자신과는 무조건 `true`), 같은 객체일 때 필드 비교를 건너뛰는 최적화이기도 하다.

### 5.3 상속이 대칭성을 깨는 방식

`equals`에서 가장 악명 높은 버그는 **상속과 대칭성** 문제이다. 하위 클래스가 필드를 추가하면서 대칭을 지키려 하지만 실패하는 경우이다.

```kotlin
open class Shape(val name: String) {
    override fun equals(other: Any?): Boolean =
        other is Shape && name == other.name
    override fun hashCode() = name.hashCode()
}

class ColoredShape(name: String, val color: String) : Shape(name) {
    override fun equals(other: Any?): Boolean =
        other is ColoredShape && name == other.name && color == other.color
    override fun hashCode() = 31 * name.hashCode() + color.hashCode()
}

val s = Shape("circle")
val cs = ColoredShape("circle", "red")

println(s == cs)   // => true   (s.equals(cs): cs is Shape이고 name 같음)
println(cs == s)   // => false  (cs.equals(s): s is ColoredShape가 false)
// 대칭성 위반! s==cs 와 cs==s 가 다르다
```

`s == cs`는 `Shape.equals`를 호출하고 "이름만 같으면 같다"고 판정한다. `cs == s`는 `ColoredShape.equals`를 호출하고 "색도 있어야 한다"며 거부한다. 방향에 따라 답이 달라지므로 대칭성이 깨진 것이다. 이 상태로 `HashSet`에 두 객체를 넣으면, 실행 순서와 버킷 배치에 따라 중복 판정 결과가 달라진다.

근본 원인은 **`equals`와 상속이 잘 맞지 않는다**는 데 있다. 흔히 쓰는 해법은 세 가지이다.

- **`equals`를 재정의하는 클래스를 `final`로 만든다**: 하위 클래스가 필드를 추가해 동등의 의미를 바꾸는 것을 처음부터 막는다. Kotlin은 클래스가 기본적으로 `final`이므로([[24 - 상속과 오버라이딩과 초기화 순서]]) 자연스럽게 적용된다.
- **클래스가 정확히 일치하는지 검사한다**: `is` 대신 `this.javaClass == other?.javaClass`(JVM 백엔드)나 `if (other == null || this::class != other::class) return false`를 쓴다. 그러면 `Shape`와 `ColoredShape`는 아예 비교 대상이 되지 않으므로 대칭 위반이 사라진다. 다만 상속 계층 사이의 비교가 항상 `false`가 된다는 부작용을 감수해야 한다.
- **상속 대신 합성(composition)을 쓴다**: 색을 가진 도형을 별도의 값 객체로 감싸 상속을 피한다.

Kotlin이 클래스를 기본적으로 `final`로 만들고 `data class`(27장 데이터 클래스)를 `open`으로 선언할 수 없게 한 것은, 바로 이 함정을 언어 차원에서 줄이기 위한 설계이다. `data class`가 자동 생성하는 `equals`는 `other is 클래스이름` 검사를 쓴다. 그런데 `data class`는 `final`이어서 하위 타입이 존재할 수 없으므로, `is` 검사가 곧 정확한 타입 일치 검사가 되고 대칭성이 저절로 지켜진다.

> [!note] 명세 기준
> `equals`의 파라미터가 `Any?`라는 것과 `data class`가 정확한 타입 일치를 검사한다는 것은 별개의 문제이다. 표준 라이브러리 `data class`에서 생성된 `equals`는 대략 `if (this === other) return true; if (other !is 클래스이름) return false`를 거친 뒤 각 프로퍼티를 비교하는 형태이다.
>
> `is`(JVM 백엔드에서는 `instanceof`) 검사를 쓰지만, `data class`는 `final`이라 하위 타입이 없다. 따라서 이 검사는 정확한 타입 일치 검사와 같아지고, 다른 타입을 대칭적으로 거부한다. 자세한 생성 규칙은 27장에서 다룬다.

### 5.4 가변 필드와 일관성

계약 4(일관성)는 **동등 판정에 쓰는 필드가 바뀌지 않아야** 한다는 뜻으로 이어진다. 가변(`var`) 필드를 `equals`/`hashCode`에 넣으면, 컬렉션에 넣은 뒤 그 필드를 바꾸는 순간 컬렉션이 그 객체를 찾지 못하게 된다.

```kotlin
class MutableKey(var id: Int) {
    override fun equals(other: Any?) = other is MutableKey && id == other.id
    override fun hashCode() = id
}

val set = hashSetOf(MutableKey(1))
val k = set.first()
k.id = 99                       // equals/hashCode에 쓰이는 필드를 변경!
println(k in set)               // => false  (해시 버킷이 바뀌어 못 찾음)
println(set.first().id)         // => 99      (그런데 셋 안엔 여전히 있음)
```

객체는 여전히 셋 안에 있지만 `in`으로는 찾지 못한다. `hashCode`가 바뀌어 다른 버킷을 찾기 때문이다. 이 예는 **불변 데이터로만 `equals`/`hashCode`를 구성하라**는 원칙이 실제로 왜 필요한지 보여 준다. 이 원칙은 [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 말한 `val` 선호와도 통한다.

## 6. `hashCode` 계약: `equals`와 짝을 이루는 계약

### 6.1 왜 `equals`만으로는 부족한가

`equals`를 재정의했다면 `hashCode`도 반드시 재정의해야 한다. 이것은 권장 사항이 아니라 **계약**이다. `Any`의 계약은 다음과 같다.

- **일관성**: 같은 객체에 대해 `hashCode()`는 (동등 판정에 쓰는 정보가 바뀌지 않는 한) 항상 같은 정수를 반환한다.
- **equals-hashCode 연대**: `a.equals(b)`가 `true`이면 `a.hashCode() == b.hashCode()`여야 한다.
- (역은 요구하지 않는다): 해시가 같다고 해서 동등할 필요는 없다(해시 충돌을 허용한다).

핵심은 두 번째 조항이다. **동등한 객체는 반드시 같은 해시코드**를 가져야 한다. 해시 기반 자료구조(`HashMap`, `HashSet`, `LinkedHashMap` 등)는 먼저 `hashCode`로 버킷을 고르고, 그 버킷 안에서만 `equals`로 정밀하게 비교한다. 동등한데 해시가 다르면 두 객체는 서로 다른 버킷에 들어가므로 절대 비교되지 않는다.

### 6.2 `equals`만 재정의했을 때 생기는 문제

```kotlin
class BadMoney(val amount: Long, val currency: String) {
    override fun equals(other: Any?): Boolean =
        other is BadMoney && amount == other.amount && currency == other.currency
    // hashCode 재정의 안 함 → Any.hashCode (객체 식별 기반, 인스턴스마다 다름)
}

val set = hashSetOf(BadMoney(1000, "KRW"))
println(BadMoney(1000, "KRW") in set)   // => false (!!)
// 논리적으로 같은 돈인데 셋에 없다고 나옴
```

```text
HashSet 조회 실패의 해부

넣은 객체:   BadMoney(1000,"KRW")  hashCode=0x1A2B  → 버킷 5
찾는 객체:   BadMoney(1000,"KRW")  hashCode=0x9F0C  → 버킷 12
                                    (Any.hashCode = 서로 다른 인스턴스 = 다른 해시)

버킷 12를 뒤짐 → 아무것도 없음 → "없다"  ← equals는 호출조차 안 됨
```

`equals`는 `true`를 반환할 수 있지만, `hashCode`가 처음부터 다른 버킷을 가리키므로 `equals`는 **호출되지도 않는다**. 이것이 `equals`만 재정의했을 때 생기는 전형적인 문제이다. 컴파일도 되고 `==` 비교도 잘 되므로 테스트에서 놓치기 쉽지만, 해시 컬렉션에 넣는 순간 아무 경고 없이 잘못 동작한다.

### 6.3 올바른 `hashCode`와 자동 생성

`hashCode`는 `equals`에 쓴 필드들로부터 결정론적으로 계산해야 한다. 표준 관용구는 소수(관례상 31)를 곱해 누적하는 방식이다.

```kotlin
override fun hashCode(): Int {
    var result = amount.hashCode()
    result = 31 * result + currency.hashCode()
    return result
}
// 또는 표준 라이브러리 헬퍼:
override fun hashCode(): Int = Objects.hash(amount, currency)  // JVM, 약간 느림
```

31을 쓰는 이유는 홀수 소수여서 해시 분포가 좋고, `31 * x`가 `(x shl 5) - x`로 최적화되기 때문이다(8장 박싱과 오버플로의 시프트 연산). 중요한 점은 **`equals`가 보는 필드 집합과 `hashCode`가 보는 필드 집합이 정확히 일치**해야 연대 계약이 지켜진다는 것이다.

실무에서는 이 짝을 직접 작성하지 않고 27장(데이터 클래스)에서 설명하는 `data class`를 사용한다. `data class`는 주 생성자 프로퍼티로부터 `equals`/`hashCode`/`toString`/`componentN`/`copy`를 **자동 생성**하며, 생성된 `equals`와 `hashCode`는 항상 서로 일치한다.

```kotlin
data class Money(val amount: Long, val currency: String)

val set = hashSetOf(Money(1000, "KRW"))
println(Money(1000, "KRW") in set)   // => true  (equals/hashCode 자동 정합)
```

다만 `data class`의 자동 생성에는 **주 생성자 프로퍼티만** 참여한다는 함정과, `copy`가 얕은 복사라는 함정이 있다. 이 내용은 27장에서 자세히 다룬다. 여기서는 "동등과 해시를 일치시키려면 `data class`를 쓰는 것이 가장 안전하다"는 점만 기억한다.

> [!caution] 성능 주의
> `hashCode`는 맵을 조회할 때마다 호출될 만큼 자주 쓰이므로 비용이 커서는 안 된다. 필드가 많고 불변이면 처음 필요할 때 계산해 캐시해 두는 기법(`by lazy`, [[23 - 위임 프로퍼티]])도 있지만, 대부분은 필요하지 않다. 반대로 모든 객체가 같은 `hashCode`(예: 항상 0)를 반환하면 계약은 지켜지지만, 해시 컬렉션이 링크드 리스트처럼 동작하게 되어 $O(1)$이 $O(n)$이 된다.

### 6.4 세 함수의 관계 정리

| 상황 | `==` (equals) | `===` | 해시 컬렉션 동작 |
|------|---------------|-------|------------------|
| 둘 다 재정의, 정합 | 값 비교 | 객체 비교 | 정상 |
| equals만 재정의 | 값 비교 | 객체 비교 | **잘못 동작** (조회 실패) |
| hashCode만 재정의 | 참조 비교(Any) | 객체 비교 | 값이 같아도 모두 다르게 취급 |
| 둘 다 미재정의 | 참조 비교(Any) | 객체 비교 | 인스턴스 식별로만 동작 |

가운데 두 줄이 버그가 생기는 경우이다. **`equals`와 `hashCode`는 항상 짝으로 재정의**하거나, 참조 기준의 동등으로 충분하다면 둘 다 재정의하지 않아야 한다.

## 7. 부동소수점 동등: IEEE 754와 전순서

### 7.1 두 가지 규칙을 따르는 동등

부동소수점은 동등성에서 가장 미묘한 부분이다. `Double`과 `Float`는 `==`의 결과가 **정적 타입에 따라** 달라진다. 이것은 버그가 아니라 Kotlin이 의도적으로 설계한 **두 가지 규칙**이다.

- **정적 타입이 `Float`/`Double`(또는 그 널 가능 타입)일 때**: 연산은 **IEEE 754** 표준을 따른다. 즉 `NaN != NaN`이고, `-0.0 == 0.0`이다.
- **정적 타입이 `Any`, `Comparable<...>`, 제네릭 타입 파라미터 등이어서 부동소수로 정적으로 알려지지 않았을 때**: `Float`/`Double`의 `equals`/`compareTo` 구현을 사용하며, 이 구현은 **전순서**(total order)를 제공한다. 즉 `NaN.equals(NaN) == true`이고, `(-0.0).equals(0.0) == false`이다.

```kotlin
val nan = Double.NaN

// (1) 정적 타입 Double → IEEE 754
println(nan == nan)            // => false  (NaN은 자기 자신과도 같지 않다)
println(0.0 == -0.0)           // => true   (IEEE: +0과 -0은 같다)

// (2) 정적 타입 Any → 전순서(equals)
val a: Any = nan
val b: Any = nan
println(a == b)                // => true   (Double.equals: NaN == NaN)

println(nan.equals(nan))       // => true   (equals 직접 호출도 전순서)
println((-0.0).equals(0.0))    // => false  (equals: -0.0 != 0.0)
```

같은 `nan`을 비교해도 정적 타입이 `Double`이면 `false`, `Any`이면 `true`이다. 같은 `0.0`과 `-0.0`도 `Double` 비교에서는 같고 `equals` 비교에서는 다르다. 이 차이를 모르면 "왜 컬렉션에서만 결과가 다르지?"라는 의문을 풀지 못한다.

### 7.2 왜 규칙이 두 가지인가

IEEE 754는 수치 계산의 정확성을 위해 `NaN != NaN`(계산이 의미를 잃었다는 신호)과 `-0.0 == 0.0`(부호 있는 0은 수치적으로 같다)을 규정한다. 순수한 산술에서는 이 규칙이 옳다.

하지만 **컬렉션과 정렬**에는 다른 성질이 필요하다. `HashSet<Double>`에 `NaN`을 넣었다면 나중에 그 `NaN`을 다시 찾을 수 있어야 하고(반사성), 정렬이 안정적이려면 모든 원소 사이에 순서가 정해져 있어야 한다(전순서). `NaN != NaN`이면 셋에 넣은 `NaN`을 영원히 찾지 못하고, 정렬도 `NaN` 근처에서 무너진다.

그래서 Kotlin은 **박스형과 제네릭 문맥에서는 IEEE 규칙 대신 전순서를 사용한다**. `NaN`을 자기 자신과 같게 만들어 반사성을 되살리고, `NaN`을 모든 값보다 크게, `-0.0`을 `0.0`보다 작게 정의한다.

```text
전순서(total order)에서의 Double 배치 (equals/compareTo 기준)

  -∞ < ... < -0.0 < +0.0 < ... < +∞ < NaN
              └ 서로 다름 ┘         └ 자기 자신과 같고, 최대 ┘

IEEE 754에서는:  -0.0 == +0.0  이고  NaN 은 어떤 것과도 비교 불가(순서 없음)
```

`NaN`을 "최대"로 둔 것은 임의로 고른 것이지만, 컬렉션 안에서 일관된 위치를 갖게 하려는 실용적인 결정이다.

### 7.3 컬렉션에서 드러나는 결과

```kotlin
val nan = Double.NaN

// contains는 원소를 Any로 다루므로 전순서(equals) 사용
println(listOf(nan).contains(nan))   // => true   (NaN을 찾을 수 있다!)
println(listOf(nan).indexOf(nan))    // => 0

// -0.0과 0.0은 equals가 다르므로 둘 다 셋에 들어간다
val s = hashSetOf(0.0, -0.0)
println(s.size)                      // => 2      (전순서: -0.0 != 0.0)

// 정렬도 전순서 → NaN이 맨 뒤로
println(listOf(3.0, nan, 1.0, -0.0, 0.0).sorted())
// => [-0.0, 0.0, 1.0, 3.0, NaN]
```

`nan == nan`이 `false`이므로 `listOf(nan).contains(nan)`도 `false`일 것 같지만, 컬렉션은 원소를 `Any`로 다루므로 `equals`(전순서)를 사용해 `true`가 된다. **부동소수점에서 "수식의 `==`"와 "컬렉션 안의 동등"이 달라지는 이유는 바로 이 정적 타입의 차이이다.**

### 7.4 실전 지침

```kotlin
// 나쁨: 부동소수 동등을 정확한 값으로 비교
val computed = 0.1 + 0.2
println(computed == 0.3)             // => false  (0.30000000000000004)

// 좋음: 허용 오차(epsilon) 비교
fun approxEquals(a: Double, b: Double, eps: Double = 1e-9) =
    kotlin.math.abs(a - b) < eps
println(approxEquals(computed, 0.3)) // => true
```

부동소수점은 값을 정확하게 표현하지 못하는 한계가 있으므로(8장 박싱과 오버플로, IEEE 754 자체는 데이터 표현 시리즈 참조), 계산 결과를 `==`로 정확히 비교하는 것은 거의 항상 버그이다. 허용 오차 비교를 쓰되, `NaN`이 섞일 수 있다면 `NaN` 검사(`x.isNaN()`)를 명시적으로 한다.

그리고 `Double`을 해시 키나 정렬 키로 쓸 때는 전순서 규칙(NaN의 반사성, -0.0≠0.0)이 적용된다는 점을 기억해야 한다. 이 규칙이 의도와 다르면 정규화가 필요하다. 예를 들어 `if (x == 0.0) 0.0 else x`로 -0.0을 없애거나, `NaN`을 미리 걸러 낸다.

> [!note] 명세 기준
> "정적 타입이 `Double`/`Float` 또는 그 널 가능 타입이면 IEEE 754를 따른다"는 규칙에서, **널 가능 타입(`Double?`)도 IEEE를 따른다**는 점은 직관과 다르다. `Double?`은 박스처럼 보이지만, 컴파일러가 정적 타입을 알고 있으므로 (널 처리를 포함한) IEEE 비교 코드를 생성한다.
>
> 반면 `Any`로 상향 변환되면 정적 타입 정보가 사라지므로 전순서 `equals`를 사용한다. 즉 두 규칙을 가르는 기준은 "런타임에 박스인가"가 아니라 "컴파일 시점에 정적 타입이 부동소수로 알려져 있는가"이다.

```kotlin
val x: Double? = Double.NaN
val y: Double? = Double.NaN
println(x == y)   // => false  (Double? 도 IEEE → NaN != NaN)

val p: Any = Double.NaN
println(p == Double.NaN)  // => true   (Any → 전순서)
```

## 8. `Comparable`과 `compareTo`: 순서라는 또 다른 동등

### 8.1 세 번째 비교 기준

지금까지 구조적 동등(`==`/`equals`)과 참조 동일(`===`)이라는 두 종류의 "같음"을 살펴보았다. 비교 기준은 하나 더 있는데, 바로 **순서**(ordering)이다. `<`, `<=`, `>`, `>=`는 `Comparable` 인터페이스의 `compareTo`로 탈설탕된다.

```kotlin
public interface Comparable<in T> {
    public operator fun compareTo(other: T): Int
}
```

`operator`가 붙어 있으므로 비교 연산자와 연결된다(19장 연산자 오버로딩). 탈설탕 규칙은 다음과 같다.

| 표현 | 번역 |
|------|------|
| `a < b`  | `a.compareTo(b) < 0` |
| `a > b`  | `a.compareTo(b) > 0` |
| `a <= b` | `a.compareTo(b) <= 0` |
| `a >= b` | `a.compareTo(b) >= 0` |

`compareTo`는 음수(좌변이 작다), `0`(순서상 같다), 양수(좌변이 크다) 가운데 하나를 반환한다. 주의할 점이 있다. **비교 연산자는 `compareTo`로만 번역되고, 절대 `==`로 번역되지 않는다.** `a == b`는 항상 `equals`이고, `a < b`는 항상 `compareTo`이다. 두 연산은 서로 다른 함수를 호출한다.

```kotlin
println(3 < 5)               // 3.compareTo(5) < 0 → true
println("apple" < "banana")  // 사전순 compareTo → true
println('a' < 'z')           // Char의 compareTo (코드유닛 비교, 9장)
```

### 8.2 `compareTo == 0`과 `equals`는 별개이다

흔한 오해 가운데 하나는 "`a.compareTo(b) == 0`이면 `a == b`이다"라는 생각이다. **그렇지 않다.** 순서상 "같은 위치"에 있는 것과 구조적으로 동등한 것은 계약상 별개이다. `Comparable`의 문서에는 "`compareTo`가 `equals`와 **일관되도록 강력히 권장**하지만 강제하지는 않는다"고 적혀 있다.

이 불일치를 보여 주는 대표적인 예는 (JVM 백엔드에서 쓰는) `BigDecimal`이다.

```kotlin
import java.math.BigDecimal
val a = BigDecimal("2.0")
val b = BigDecimal("2.00")

println(a.compareTo(b))   // => 0     (수치적으로 같은 위치)
println(a == b)           // => false (equals는 스케일까지 봄: 2.0 ≠ 2.00)
println(a.equals(b))      // => false
```

`2.0`과 `2.00`은 같은 수이므로 순서상 같은 자리에 있지만, `equals`는 스케일(소수 자릿수)까지 구별하므로 둘을 다르다고 판정한다. 그 결과 `TreeSet`(순서 기반)과 `HashSet`(equals 기반)은 이 두 값을 다르게 취급한다.

```kotlin
println(java.util.TreeSet<BigDecimal>().apply { add(a); add(b) }.size)  // => 1 (compareTo)
println(hashSetOf(a, b).size)                                           // => 2 (equals)
```

**같은 두 값을 순서 기반 컬렉션은 하나로, 해시 기반 컬렉션은 둘로 센다.** 이 함정을 피하려면 순서 기반 자료구조에 넣을 타입은 `compareTo`와 `equals`가 일관되도록 설계해야 한다.

### 8.3 `compareValuesBy`와 다중 키 정렬

여러 필드로 순서를 정할 때는 `compareTo`를 직접 작성하는 대신 표준 라이브러리 헬퍼를 쓴다.

```kotlin
class Person(val lastName: String, val firstName: String, val age: Int) : Comparable<Person> {
    override fun compareTo(other: Person): Int =
        compareValuesBy(this, other,
            { it.lastName }, { it.firstName }, { it.age })
}

val list = listOf(
    Person("Kim", "Bora", 30),
    Person("Kim", "Ana", 25),
    Person("Lee", "Ana", 40),
)
println(list.sorted().map { "${it.lastName} ${it.firstName}" })
// => [Kim Ana, Kim Bora, Lee Ana]
```

`compareValuesBy`는 셀렉터를 순서대로 적용하다가 처음으로 차이가 나는 지점에서 순서를 결정한다(사전식 비교). 정렬할 때는 `sortedBy`, `sortedWith(compareBy(...).thenBy(...))` 같은 확장 함수([[39 - 컬렉션 연산과 함수형 파이프라인]])도 쓸 수 있다. 이 함수들은 모두 `compareTo`가 정의하는 전순서를 사용한다.

### 8.4 순서의 전순서 계약

`Comparable`이 정의하는 순서는 **전순서**(total order)여야 한다. 조건은 다음과 같다.

- 반사적이다: `x.compareTo(x)==0`
- 반대칭적이다: `x<y`이면 `y>x`
- 추이적이다: `x<y`이고 `y<z`이면 `x<z`
- 모든 원소 쌍을 비교할 수 있다: 7.2절에서 부동소수의 `NaN`을 전순서에 포함시킨 이유가 이것이다.

이 계약을 어긴 `compareTo`(예: 상황에 따라 다른 부호를 반환하는 구현)를 정렬에 쓰면 결과가 뒤섞이거나 예외가 발생할 수 있다.

```text
세 개의 비교 축 — 서로 독립적인 판정

  a === b   (참조 동일)   ── "같은 객체인가"        재정의 불가
  a == b    (구조 동등)   ── equals 호출            재정의: equals
  a < b     (순서)        ── compareTo 호출         재정의: compareTo(Comparable)

계약의 다리:
  a === b  ⇒  a == b            (같은 객체면 구조도 같다, equals가 정상이면)
  a == b   ⇏  a.compareTo(b)==0 (권장되나 강제 아님: BigDecimal 반례)
  a.compareTo(b)==0 ⇏ a == b    (같은 자리 ≠ 구조 동등)
```

이 다이어그램은 이 장의 내용을 한눈에 보여 준다. 세 가지 비교는 각각 독립적으로 재정의되며, 잘 설계된 값 타입에서는 서로 일관된다. 하지만 계약이 강제하는 관계는 하나뿐이다. 동등하면 해시가 같아야 한다는 `equals`와 `hashCode`의 연대 계약이다. 나머지 일관성은 개발자가 책임져야 한다.

## 9. 실전 종합: 값 타입을 올바르게 만들기

### 9.1 배열의 함정

동등성의 마지막 함정은 배열이다. `Array<T>`(38장 컬렉션)는 `equals`를 재정의하지 않으므로 `==`가 **참조 비교**가 된다.

```kotlin
val a = arrayOf(1, 2, 3)
val b = arrayOf(1, 2, 3)
println(a == b)              // => false  (참조 비교! 내용 아님)
println(a === b)             // => false
println(a.contentEquals(b))  // => true   (내용 비교는 이걸로)

// 중첩 배열은 contentDeepEquals
val m1 = arrayOf(intArrayOf(1), intArrayOf(2))
val m2 = arrayOf(intArrayOf(1), intArrayOf(2))
println(m1.contentEquals(m2))     // => false (한 겹만 비교, 원소는 참조)
println(m1.contentDeepEquals(m2)) // => true
```

`List`는 구조적 `equals`를 제공하지만(`listOf(1,2,3) == listOf(1,2,3)`은 `true`), 배열은 그렇지 않다. 배열이 이렇게 예외적으로 동작하는 것은 JVM 배열의 동작을 Kotlin이 그대로 드러냈기 때문이다. 배열을 비교할 때는 `contentEquals`/`contentDeepEquals`를 써야 한다는 점을 반드시 기억해야 한다.

### 9.2 값 타입 설계 체크리스트

지금까지 살펴본 계약을 하나의 체크리스트로 정리한다. "이 클래스의 두 인스턴스를 내용이 같으면 같은 것으로 취급해야 하는가?"라는 질문에 답이 `yes`라면 다음을 확인한다.

```text
값 타입(value-semantics) 설계 체크리스트

□ data class로 만들 수 있으면 그렇게 하라 (equals/hashCode 자동 정합)
□ 손수 만든다면:
   □ equals와 hashCode를 항상 짝으로 재정의
   □ 같은 필드 집합을 equals와 hashCode에 사용
   □ equals: this===other 빠른 경로 → is 타입검사 → 필드 비교
   □ equals에 쓰는 필드는 불변(val)으로 — 일관성 계약
   □ 상속이 관여하면 final로 만들거나 정확한 클래스 검사
□ Comparable을 구현한다면 compareTo가 equals와 일관되게 (특히 정렬 컬렉션 사용 시)
□ 부동소수 필드가 있으면 NaN/-0.0의 전순서 동작을 인지
□ 배열 필드가 있으면 equals/hashCode에서 contentEquals/contentHashCode 사용
□ 값이 같은지 판정엔 언제나 == , === 는 참조 정체성이 본질일 때만
```

### 9.3 종합 예제

```kotlin
data class Color(val r: Int, val g: Int, val b: Int) : Comparable<Color> {
    // 밝기(luminance)로 순서 정의 — equals와 일관되지 않을 수 있음에 주의
    private val luminance get() = 0.299 * r + 0.587 * g + 0.114 * b
    override fun compareTo(other: Color): Int =
        luminance.compareTo(other.luminance)
}

val red = Color(255, 0, 0)
val green = Color(0, 255, 0)
val red2 = Color(255, 0, 0)

println(red == red2)           // => true   (data class equals: 필드 동일)
println(red === red2)          // => false  (다른 객체)
println(red < green)           // => true   (red가 더 어둡다, compareTo)
println(hashSetOf(red, red2).size)  // => 1  (equals/hashCode 정합)
```

이 `Color`는 세 가지 비교를 모두 보여 준다. `==`는 RGB 필드로 동등을 판정하고(data class가 자동 생성), `===`는 물리적 객체를 식별하며, `<`는 밝기 순서(compareTo)를 비교한다.

주의할 점이 있다. `compareTo`를 밝기로 정의했으므로, 서로 다른 색이 같은 밝기를 가지면 `compareTo == 0`이지만 `equals`는 `false`가 될 수 있다(8.2절의 불일치). 이 `Color`를 `TreeSet`에 넣으면 밝기가 같은 서로 다른 색이 하나로 합쳐질 수 있다. 그런 용도로 쓴다면 `compareTo`를 RGB 사전식 비교로 바꿔 `equals`와 일관되게 만들어야 한다.
