- `==`는 참조를 비교하는가, 값을 비교하는가? Java에서 넘어온 습관은 왜 Kotlin에서 조용히 버그가 되는가?
- `a == b`는 컴파일러가 정확히 어떤 코드로 번역하는가? 좌변이 `null`이면, 우변이 `null`이면 무슨 일이 일어나는가?
- `===`는 언제 의미가 있고, 언제 예측 불가능한가? `val a: Int? = 127; a === 127`은 왜 `true`인데 `128`은 `false`인가?
- `equals`가 지켜야 하는 다섯 계약(반사·대칭·추이·일관·null)은 무엇이고, 상속이 왜 대칭성을 깨는가?
- `equals`를 재정의하면서 `hashCode`를 빼먹으면 `HashSet` 안에서 정확히 무엇이 부서지는가?
- `Double.NaN == Double.NaN`은 왜 `false`인데 `listOf(Double.NaN).contains(Double.NaN)`은 왜 `true`인가?
- `-0.0`과 `0.0`은 같은가? 정적 타입이 `Double`일 때와 `Any`일 때 답이 왜 달라지는가?
- `a < b`는 어떤 함수 호출로 바뀌며, `compareTo`가 `0`을 돌려주는 것과 `equals`가 `true`인 것은 왜 별개의 사건인가?

앞의 [[07 - 수 1 - Int와 Long과 부동소수점]]과 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]에서 우리는 수가 기계 위에서 어떻게 표현되는지 — JVM 백엔드에서 언제 원시형이 되고 언제 박스로 감싸지는지 — 를 파헤쳤다. [[09 - 문자와 문자열 - 유니코드와 템플릿]]에서는 `String`이 불변이며 `==`로 내용을 비교한다는 사실을 스쳐 지나갔다. 이 장은 그 "스쳐 지나간" 문장을 정면으로 해부한다. 두 값이 "같다"는 판정은 프로그래밍에서 가장 흔하면서도 가장 미묘한 연산이고, Kotlin은 이 연산을 두 겹으로 — **구조적 동등(structural equality)** `==`와 **참조 동일(referential identity)** `===` 로 — 갈라 놓았다. 이 분리를 이해하지 못하면, Java 습관을 그대로 들고 온 개발자는 자기도 모르는 사이에 버그를 심는다.

이 장이 다루는 것은 세 개의 축이다. 첫째는 **불리언(Boolean)** — 값이 둘뿐인 가장 작은 타입, 그리고 그 위의 논리 연산(단축 평가 `&&`/`||`와 즉시 평가 `and`/`or`)이다. 둘째는 **동등성** — `==`가 사실은 `equals` 호출로 탈설탕되는 과정, 그 `equals`가 지켜야 하는 계약, 그리고 그 계약의 그림자인 `hashCode`다. 셋째는 **동일성** — `===`가 무엇을 비교하며, JVM 백엔드의 박싱 캐시가 어떻게 이 연산의 결과를 예측 불가능하게 만드는가(M48)다. 마지막으로 우리는 부동소수점 동등의 함정(NaN, `-0.0`)과 `Comparable`/`compareTo`가 만드는 "순서라는 또 다른 동등"까지 밀고 나간다.

다루지 않는 것도 못박아 둔다. 연산자 오버로딩의 관례 함수 전체 표 — `equals`, `compareTo`가 어떤 관례로 `==`/`<`에 연결되는지의 *체계* — 는 [[19 - 연산자 오버로딩과 관례]]가 소유한다. 여기서는 동등/순서에 필요한 만큼만 미리 당겨 쓴다. `data class`가 `equals`/`hashCode`를 어떻게 **자동 생성**하며 그 함정이 무엇인지는 [[27 - 데이터 클래스]]가 정본이다. `null` 자체의 취급 — 안전 호출 `?.`, 엘비스 `?:`, 스마트 캐스트 — 는 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에 있다. 컬렉션에서 읽기 전용과 가변, 배열의 특수성은 [[38 - 컬렉션 - 읽기 전용과 가변]]으로 넘긴다. 이 장은 오로지 "같음"과 "동일함"의 의미론에 집중한다.

논증의 궤적은 이렇다. 불리언에서 시작해(동등성의 가장 단순한 무대), Java의 `==`가 왜 Kotlin의 `==`와 다른지를 못박고(M6), `==`의 정확한 탈설탕을 해부한 뒤, `===`로 넘어가 박싱 캐시의 함정을 드러낸다(M48). 그다음 `equals`의 다섯 계약과 `hashCode`의 연대 계약을 세우고, 부동소수점이 이 계약을 어떻게 두 얼굴로 만족시키는지를 본다. 끝으로 `compareTo`라는 세 번째 비교 축을 세워, "같음의 세 가지 판정"이 어떻게 서로 독립적이면서도 서로에게 계약을 지우는지로 마무리한다.

## 1. 불리언 — 값이 둘뿐인 타입

### 1.1 Boolean은 진짜 타입이다

Kotlin의 `Boolean`은 값이 정확히 둘 — `true`와 `false` — 인 타입이다. C에서처럼 `0`이 거짓이고 `0이 아니면` 참인 정수 위장이 아니고, 조건문에 정수나 널을 넣을 수도 없다. `if (1)`은 컴파일되지 않는다.

```kotlin
val isRaining: Boolean = true
val hasUmbrella = false        // 타입 추론 → Boolean

if (isRaining) println("우산 챙기기")
// if (1) { ... }              // 컴파일 에러: Int는 Boolean이 아니다
// val x: Boolean = null       // 컴파일 에러: null은 Boolean에 대입 불가
```

`Boolean`은 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서 본 타입 계층의 정식 시민이다. `Any`의 하위 타입이며, `Comparable<Boolean>`을 구현한다. 즉 `false < true`가 성립한다(뒤의 8절에서 `compareTo`로 다시 본다).

```kotlin
println(false < true)          // => true
println(true.compareTo(false)) // => 1  (양수 = 좌변이 크다)
```

> **명세 정밀**: JVM 백엔드에서 `Boolean`은 가능한 곳에서 원시 `boolean`으로, 널 가능하거나 제네릭 위치에서는 박스형 `java.lang.Boolean`으로 컴파일된다([[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]의 원시/박스 이중성과 같은 원리). 이는 JVM 백엔드에 한정된 표현이며, Native/JS/Wasm 백엔드는 각자의 표현을 쓴다.

### 1.2 논리 연산 — 단축 평가와 즉시 평가

Kotlin은 불리언 논리에 대해 **두 벌**의 연산을 제공한다. 이 이중성을 모르면 부수 효과(side effect)가 있는 코드에서 미묘한 버그가 난다.

| 연산 | 이름 | 단축 평가 | 형태 |
|------|------|-----------|------|
| `&&` | 논리 곱(AND) | O (좌변이 `false`면 우변 미평가) | 연산자 |
| `\|\|` | 논리 합(OR) | O (좌변이 `true`면 우변 미평가) | 연산자 |
| `!` | 부정(NOT) | — | 연산자 |
| `and` | 논리 곱 | **X** (항상 양변 평가) | 중위 함수 |
| `or` | 논리 합 | **X** (항상 양변 평가) | 중위 함수 |
| `xor` | 배타적 합 | X | 중위 함수 |
| `not()` | 부정 | — | 함수 |

`&&`와 `||`는 **단축 평가(short-circuit evaluation)** 를 한다. 왼쪽만으로 결과가 정해지면 오른쪽을 아예 계산하지 않는다. 반면 `and`, `or`는 kotlin.Boolean에 정의된 평범한 **중위 함수**이고, 함수 호출이므로 인자(우변)를 무조건 먼저 평가한다.

```kotlin
fun sideEffect(): Boolean {
    println("우변 평가됨!")
    return true
}

val a = false && sideEffect()  // "우변 평가됨!" 출력 안 됨 (단축)
// => a = false, 아무것도 출력 안 함

val b = false and sideEffect() // "우변 평가됨!" 출력됨 (즉시)
// => 콘솔: 우변 평가됨!
// => b = false
```

이 차이는 **널 방어**나 **비싼 계산**을 오른쪽에 둘 때 결정적이다.

```kotlin
val name: String? = null
// 단축 평가 덕분에 안전: 좌변이 false면 name!!.length는 절대 실행 안 됨
if (name != null && name.length > 3) { /* ... */ }

// 'and'였다면 name.length가 평가되어 스마트 캐스트도, 널 검사도 무의미
// if (name != null and name.length > 3)  // 스마트캐스트 안 되고 위험
```

여기서 `name != null && name.length > 3`의 우변에서 `name`이 널이 아님으로 **스마트 캐스트**([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]])되는 것도 `&&`의 단축 의미론과 결합되어 성립한다. 컴파일러는 "우변은 좌변이 참일 때만 평가된다"는 사실을 알기에, 우변 안에서 `name`을 비-널로 좁힐 수 있다. `and`는 그런 흐름 보장이 없으므로 이 자리에서 쓰면 의미가 달라진다.

> **성능 주의**: `and`/`or`가 존재하는 이유는 "양변을 모두 평가하고 싶을 때"(예: 양쪽 모두 부수 효과가 필요하거나, 분기 예측 실패 비용이 단축 분기보다 클 때)를 위해서다. 일상 조건 논리에서는 거의 항상 `&&`/`||`가 옳다. `and`/`or`는 정수의 비트 연산 `and`/`or`([[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]])와 이름이 겹치지만, 수신 타입이 `Boolean`이면 논리 연산, `Int`면 비트 연산으로 서로 다른 함수다.

### 1.3 불리언과 동등성 — 가장 단순한 무대

Kotlin에는 C나 JavaScript 같은 **진리값 강제(truthiness)** 가 없다. `if`, `while`, `&&`, `||`, `!`의 피연산자는 정확히 `Boolean`이어야 한다. `0`, 빈 문자열, `null`이 조건에서 "거짓처럼" 취급되는 일이 없다. 이 엄격함은 [[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]]의 "안전" 축과 통한다 — 의도치 않은 암묵적 변환을 언어가 원천 차단한다.

```kotlin
val list = listOf(1, 2, 3)
// if (list) { ... }               // 컴파일 에러: List는 Boolean이 아니다
if (list.isNotEmpty()) { /* ... */ }  // 의도를 명시적으로

val text: String? = null
// if (text) { ... }               // 컴파일 에러
if (text != null) { /* ... */ }    // 명시적 널 검사
```

자매 시리즈 JavaScript에서 `if (x)`가 `x`의 truthiness를 보는 것과 극명히 대비된다. Kotlin은 "무엇이 참인가"를 개발자가 매번 `Boolean` 식으로 못박게 만든다. 이 덕분에 "빈 문자열이 왜 false지?" 같은 언어별 진리값 규칙을 외울 필요가 없다.

불리언은 동등성의 가장 단순한 실험대다. 값이 둘뿐이므로 `==`, `===`, 심지어 논리적 동치 `==`가 모두 겹쳐 보인다.

```kotlin
val p = true
val q = true
println(p == q)   // => true  (구조적: 두 값이 같은 진리값)
println(p === q)  // => true  (참조: 아래 설명)
```

`Boolean?`을 박싱하면 JVM 백엔드에서는 `java.lang.Boolean.TRUE`/`FALSE`라는 고정된 캐시 인스턴스를 재사용하므로, 박스형 `true`끼리는 항상 같은 객체다. 그래서 `===`도 `true`가 나온다. 하지만 이건 우리가 4절에서 "박싱 캐시가 만드는 착시"로 부를 바로 그 현상이다 — 불리언에서는 캐시가 값 전체를 덮으니 우연히 안전해 보일 뿐, `===`에 의미를 부여하면 안 된다. 불리언에서는 언제나 `==`(또는 그냥 `if (b)`)를 쓰고 `===`는 잊어라. 진짜 문제는 다음 절부터 시작된다.

## 2. 두 세계의 충돌 — Java의 `==`를 버려라 (M6)

### 2.1 오개념 정면 교정

**오개념(M6): "`==`는 참조를 비교한다."** — Java에서 온 개발자가 가장 자주, 가장 조용히 심는 버그의 근원이다. Java에서 `a == b`는 **참조 동일성**(두 변수가 같은 객체를 가리키는가)을 비교하고, 내용 비교는 `a.equals(b)`로 따로 해야 한다. 그래서 Java 개발자는 `"foo" == someString`이 예측 불가능하다는 걸 뼈저리게 안다.

Kotlin은 이 관계를 **뒤집었다**. Kotlin에서:

- `==` (그리고 `!=`)는 **구조적 동등** — 내부적으로 `equals`를 호출한다.
- `===` (그리고 `!==`)는 **참조 동일** — 두 참조가 같은 객체인지 본다.

```kotlin
val s1 = StringBuilder("cat").toString()   // "cat"
val s2 = StringBuilder("cat").toString()   // 다른 "cat" 인스턴스

println(s1 == s2)   // => true   (내용 같음, equals 호출)
println(s1 === s2)  // => false  (서로 다른 객체)
```

```java
// Java — 정반대 습관
String s1 = new StringBuilder("cat").toString();
String s2 = new StringBuilder("cat").toString();
System.out.println(s1 == s2);        // => false  (참조 비교)
System.out.println(s1.equals(s2));   // => true   (내용 비교)
```

같은 두 줄이 `==`에 대해 정반대 답을 낸다. Kotlin의 `s1 == s2`는 Java의 `s1.equals(s2)`에 해당하고, Kotlin의 `s1 === s2`가 Java의 `s1 == s2`에 해당한다. Java 습관대로 "내용을 비교하려면 `.equals()`를 써야지"라고 생각해 Kotlin에서 굳이 `.equals()`를 부르는 건 틀리진 않지만 관용적이지 않고, 반대로 "참조가 아니라 값을 보려고 `==`를 피해야지"라고 생각하는 순간 버그다.

### 2.2 대조표 — 두 언어의 연산자 대응

| 의도 | Kotlin | Java |
|------|--------|------|
| 내용(구조)이 같은가 | `a == b` | `a.equals(b)` (혹은 `Objects.equals`) |
| 같은 객체인가(동일성) | `a === b` | `a == b` |
| 내용이 다른가 | `a != b` | `!a.equals(b)` |
| 다른 객체인가 | `a !== b` | `a != b` |

이 표는 이 장 전체에서 외워야 할 유일한 표다. **Kotlin `==` = Java `.equals`**, **Kotlin `===` = Java `==`**. 나머지는 이 대응의 세부를 파는 것이다.

### 2.3 왜 이렇게 설계했나

Kotlin이 `==`를 `equals`로 정의한 이유는 **실용주의**([[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]]의 설계 철학)다. 실제 코드에서 개발자가 압도적으로 자주 원하는 건 "내용이 같은가"이지 "같은 메모리 주소인가"가 아니다. Java에서 문자열을 `==`로 비교했다가 겪는 버그가 신입 개발자를 무수히 괴롭혔고, Kotlin은 흔한 의도를 짧은 문법에 배정한다는 원칙에 따라 `==`를 구조적 동등에 줬다. 참조 동일성이 필요한 드문 경우(캐시 식별, 싱글턴 확인, 순환 참조 감지)를 위해 별도의 `===`를 남겨 뒀다.

> **역사 메모**: `===`(세 글자 등호)는 Kotlin이 발명한 기호가 아니다. JavaScript의 `===`("엄격 동등")에서 시각적 착안을 얻었지만 의미는 다르다. JS의 `===`는 *타입 강제 변환 없는 동등* 비교이고, Kotlin의 `===`는 *참조 동일*이다. 두 언어를 오가는 개발자는 이 겹침에 특히 주의해야 한다. (자매 시리즈 JavaScript의 `==`/`===` 대조 참고.)

## 3. `==`의 정확한 탈설탕과 null 안전

### 3.1 `a == b`는 무엇으로 번역되는가

`==`가 "equals를 호출한다"는 건 반쪽 진실이다. 정확한 탈설탕(desugaring)은 널 안전을 포함한다. Kotlin 명세에 따라 `a == b`는 다음으로 번역된다:

```kotlin
a?.equals(b) ?: (b === null)
```

이 한 줄을 뜯어보면 `==`의 모든 성질이 드러난다.

- `a`가 널이 아니면 → `a.equals(b)`를 호출한다. (구조적 비교의 본체)
- `a`가 널이면 → 안전 호출 `?.`가 `null`을 반환하므로, 엘비스 `?:`의 우변 `(b === null)`이 평가된다. 즉 **양쪽이 모두 널이면 `true`**, `a`만 널이면 `false`.

핵심은 이것이 **좌변(`a`)의 `equals`를 호출한다**는 것, 그리고 **좌변이 널일 때조차 NPE를 던지지 않는다**는 것이다. Java에서 `a.equals(b)`는 `a`가 널이면 NPE지만, Kotlin의 `==`는 안전 호출로 감싸 있어 어떤 피연산자가 널이어도 절대 터지지 않는다.

```kotlin
val a: String? = null
val b: String? = null
val c: String? = "x"

println(a == b)   // => true   (둘 다 null → b === null → true)
println(a == c)   // => false  (a는 null, c는 not null)
println(c == a)   // => false  (c.equals(null) → false)
println(a == null)// => true
```

### 3.2 좌변 기준이라는 비대칭

`a == b`가 `a.equals(b)`로 번역된다는 사실은 미묘한 결과를 낳는다: **어느 쪽 `equals`가 불리는지는 좌변이 결정한다.** 잘 설계된 `equals`는 대칭적(5절)이므로 보통 티가 안 나지만, `equals`를 잘못 구현하면 `a == b`와 `b == a`가 다른 답을 낼 수 있다.

```kotlin
class CaseInsensitive(val s: String) {
    override fun equals(other: Any?): Boolean =
        other is CaseInsensitive && s.equals(other.s, ignoreCase = true)
    override fun hashCode() = s.lowercase().hashCode()
}

val x = CaseInsensitive("Cat")
val y = CaseInsensitive("cat")
println(x == y)   // => true  (x.equals(y))
println(y == x)   // => true  (y.equals(x)) — 여기선 대칭이 지켜짐
```

이 예는 대칭이 지켜지지만, 상속이 끼면 깨진다(5.3절에서 자세히). 지금 기억할 점은 **`==`의 방향성** — 좌변의 타입이 호출될 `equals`를 정한다 — 이다.

### 3.3 정적 타입이 원시형이면 다르다

`==`가 항상 `equals` 메서드 호출로 바뀌는 건 아니다. **JVM 백엔드에서** 피연산자의 정적 타입이 원시형으로 표현되는 경우(`Int`, `Long`, `Double`, `Boolean` 등 널 불가), 컴파일러는 `equals` 호출 대신 원시형 비교 명령(바이트코드 `if_icmpeq` 등)을 낸다. 결과 의미론은 대부분 같지만(값 비교), 부동소수점에서는 이 차이가 결정적 결과를 낳는다(7절).

```kotlin
val i = 42
val j = 42
println(i == j)  // JVM 백엔드에서: 박싱/equals 없이 원시 int 비교
```

즉 `==`의 의미는 "구조적 동등"으로 통일돼 있지만, 그 구조적 동등을 *구현하는 코드*는 정적 타입에 따라 (a) 원시형 직접 비교이거나 (b) `equals` 호출이다. 이 이중 구현이 부동소수점에서 두 얼굴을 만든다.

> **명세 정밀**: 위 탈설탕 `a?.equals(b) ?: (b === null)`은 피연산자가 널 가능하거나 참조형일 때의 개념적 형태다. 정적 타입이 원시형(비-널)일 때 컴파일러는 이 형태를 거치지 않고 원시 비교로 최적화한다. 두 경로가 어떻게 부동소수점에서 갈라지는지는 7절에서 다룬다. 이 원시 최적화는 JVM 백엔드 특성이다.

### 3.4 `!=`와 `!==`, 그리고 부정의 탈설탕

`!=`는 `==`의 부정이고 `!==`는 `===`의 부정이다. 정확히는:

| 표현 | 번역 |
|------|------|
| `a != b`  | `!(a == b)` → `!(a?.equals(b) ?: (b === null))` |
| `a !== b` | `!(a === b)` |

`!=`도 `==`와 똑같이 널 안전하다 — 어떤 피연산자가 널이어도 NPE가 없다. 그래서 `if (x != null)`이 안전하게 성립하고([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]의 스마트 캐스트 진입점), `x != null`은 `!(x?.equals(null) ?: (null === null))`이 아니라 — 좌변이 `null`이면 `null === null`이 `true`이므로 `==`가 `true`, `!=`가 `false` — 즉 "널이 아닐 때만 `true`"로 정확히 동작한다.

```kotlin
val x: String? = null
println(x != null)   // => false  (x는 null이므로 "널 아님"은 거짓)
val y: String? = "a"
println(y != null)   // => true

// != 도 좌변 equals의 부정 — 커스텀 equals를 그대로 반영
data class Tag(val v: String)
println(Tag("a") != Tag("b"))  // => true
```

부정 연산자 `!`는 `Boolean`에만 적용되며, `not()` 함수의 연산자 형태다. `!` 뒤에 붙는 식이 `Boolean`이 아니면 컴파일 에러다. 이 엄격함이 truthiness 부재(1.3절)와 짝을 이룬다.

## 4. `===` 참조 동일성과 박싱 캐시의 함정 (M48)

### 4.1 `===`는 무엇을 비교하나

`a === b`는 **두 참조가 힙 위의 같은 객체를 가리키는지**를 묻는다. `equals`를 부르지 않고, 재정의도 불가능하다(연산자 오버로딩 대상이 아니다 — [[19 - 연산자 오버로딩과 관례]]). 순수하게 물리적 동일성이다.

```kotlin
class Point(val x: Int, val y: Int)

val p = Point(1, 2)
val q = p
val r = Point(1, 2)

println(p === q)  // => true   (같은 객체, q는 p의 별칭)
println(p === r)  // => false  (내용은 같지만 다른 객체)
println(p == r)   // => false  (Point는 equals 미재정의 → Any.equals → 참조 비교)
```

마지막 줄이 흥미롭다. `Point`는 `equals`를 재정의하지 않았으므로 `Any`의 기본 `equals`를 쓰는데, `Any.equals`는 **참조 동일성**으로 구현되어 있다. 그래서 `equals`를 재정의하지 않은 클래스에서는 `==`와 `===`가 같은 답을 낸다. `data class`([[27 - 데이터 클래스]])로 만들거나 `equals`를 손수 재정의해야 비로소 `==`가 구조적 비교로 갈라진다.

### 4.2 오개념 정면 교정 — `===`는 모든 값에서 의미가 있지 않다 (M48)

**오개념(M48): "`===`는 어떤 값에든 명확한 의미가 있다."** — 참조 동일성은 *객체*에서만 의미가 있다. 그런데 JVM 백엔드에서는 정적 타입이 원시형으로 컴파일되는 값에 대해 `===`가 `==`와 사실상 같아지고, 박스형으로 컴파일되는 값에 대해서는 **박싱 캐시** 때문에 결과가 예측 불가능해진다. 이것이 이 장이 소유한 M48이다.

먼저 명세가 보장하는 부분: 정적 타입이 런타임에 원시형으로 표현되는 값(예: 비-널 `Int`)에 대해 `===` 검사는 `==` 검사와 **동등**하다. 원시형에는 "참조"가 없으니 물리적 동일성 개념이 값 동일성으로 붕괴한다.

문제는 **박싱이 개입할 때**다. `Int?`, `Any`로 상향 변환된 `Int`, 제네릭 타입 인자로 들어간 `Int` 등은 JVM 백엔드에서 `java.lang.Integer` 박스가 된다. 그리고 `java.lang.Integer.valueOf`는 `-128..127` 범위의 값에 대해 **캐시된 박스 인스턴스**를 재사용한다(JLS가 요구하는 캐시). 그 결과:

```kotlin
val a: Int? = 127
val b: Int? = 127
println(a === b)  // => true   (127은 캐시 → 같은 Integer 객체)

val c: Int? = 128
val d: Int? = 128
println(c === d)  // => false  (128은 캐시 밖 → 서로 다른 Integer 객체)

println(a == b)   // => true   (구조적 동등, 언제나 값으로)
println(c == d)   // => true   (구조적 동등, 언제나 값으로)
```

`127 === 127`은 `true`인데 `128 === 128`은 `false`다. 값은 똑같이 "자기 자신과 비교"하는데 캐시 경계 하나로 답이 뒤집힌다. 이것이 M48의 핵심 — **박스로 표현되는 값에 `===`를 쓰면 결과는 백엔드의 박싱 캐시 전략에 좌우되며 언어가 보장하지 않는다.**

```text
Int? 박싱 캐시 (JVM 백엔드, Integer.valueOf)

 값:  ...  -129  -128 ─────────── 127  128  129  ...
                  └── 캐시된 공유 박스 ──┘
             (===가 값이 같으면 true)   (매번 새 박스, ===는 false)

핵심: === 의 답이 "값"이 아니라 "어느 박스 인스턴스냐"에 달림
```

### 4.3 왜 이런 일이 — 그리고 어떻게 피하나

이 함정의 뿌리는 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]에서 본 박싱이다. `Int`는 원시형이지만 널 가능성이나 제네릭 위치에서 박스가 되고, 박스는 힙 객체이므로 참조 동일성 개념이 살아난다. 그런데 JVM은 작은 정수 박스를 캐시로 공유하니, 참조 동일성이 값에 따라 켜졌다 꺼졌다 한다.

**교훈은 단순하다: 수·불리언·문자 같은 값 타입에는 절대 `===`를 쓰지 마라.** 값이 같은지는 언제나 `==`다. `===`는 "이것이 저 특정 객체 그 자체인가"를 물을 때 — 즉 진짜 참조 식별이 필요한 캐시·싱글턴·순환 감지에서만 — 의미가 있고, 그런 대상은 원시형으로 컴파일되지 않는 진짜 객체다.

> **성능 주의**: 캐시 범위(`-128..127`)는 JVM에서 `-XX:AutoBoxCacheMax`로 상한을 조정할 수 있어 환경에 따라 넓어질 수도 있다. 이는 "박싱 캐시에 기대는 `===` 결과는 환경 의존적"이라는 M48을 더욱 못박는다. 이식성 있는 코드는 절대 이 캐시에 의존해선 안 된다.

> **흔한 오해**: "`===`가 `true`면 확실히 같은 값이다"는 참이다(같은 객체면 같은 값). 하지만 그 역 — "값이 같으면 `===`가 `true`" — 은 박스형에서 거짓이다. `===`는 값 동등의 충분조건도 필요조건도 아닌, 물리적 동일성이라는 완전히 다른 질문이다.

### 4.4 `===`가 정당하게 쓰이는 자리

`===`를 완전히 금기시할 필요는 없다. 정당한 용례가 있다.

```kotlin
// (1) equals 구현 안에서의 빠른 경로: 같은 객체면 즉시 true
class Vector(val dx: Double, val dy: Double) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true        // 동일 객체면 빠르게 종료
        if (other !is Vector) return false
        return dx == other.dx && dy == other.dy
    }
    override fun hashCode() = 31 * dx.hashCode() + dy.hashCode()
}

// (2) 싱글턴/센티넬 확인
object Empty
val token: Any = Empty
println(token === Empty)   // => true, 이 센티넬 그 자체인지 확인

// (3) 널 리터럴 비교 — null === null은 관용적
```

이 세 자리에서 `===`는 "그 객체 자체인가"를 정확히 묻는다. 특히 (1)은 `equals` 구현의 표준 관용구다. 값 타입이 아니라 **참조 정체성이 본질인 대상**에만 `===`를 쓴다는 원칙을 지키면 M48의 함정을 완전히 피한다.

## 5. `equals` 계약 — 다섯 조항

### 5.1 `Any.equals`와 다섯 계약

`==`가 결국 `equals`를 부른다면, `equals`가 잘 행동해야 `==`가 믿을 만해진다. `equals`는 `Any`에 선언된 메서드다:

```kotlin
open operator fun equals(other: Any?): Boolean
```

`operator`가 붙어 있어 `==`가 이 함수로 탈설탕된다([[19 - 연산자 오버로딩과 관례]]). 파라미터 타입이 `Any?`인 점이 중요하다 — 어떤 타입이든, 널이든 받을 수 있어야 한다. `equals`를 재정의하는 사람은 다음 **다섯 계약**을 반드시 지켜야 한다(수학적으로는 동치 관계의 성질에 널 처리를 더한 것):

1. **반사성(reflexive)**: 널 아닌 `x`에 대해 `x.equals(x)`는 항상 `true`.
2. **대칭성(symmetric)**: `x.equals(y)`가 `true`면 `y.equals(x)`도 `true`.
3. **추이성(transitive)**: `x.equals(y)`이고 `y.equals(z)`이면 `x.equals(z)`.
4. **일관성(consistent)**: 비교에 쓰이는 정보가 바뀌지 않는 한, 여러 번 호출해도 같은 결과.
5. **널 처리**: 널 아닌 `x`에 대해 `x.equals(null)`은 항상 `false`.

이 계약은 강제되지 않는다 — 컴파일러가 검사하지 못한다. 위반해도 컴파일은 되지만, 해시 기반 컬렉션, 정렬, 캐시 등이 조용히 오작동한다. 계약은 "믿을 수 있는 동등"의 정의 그 자체다.

### 5.2 올바른 수동 구현의 뼈대

```kotlin
class Money(val amount: Long, val currency: String) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true          // 반사성 빠른 경로 + 성능
        if (other !is Money) return false        // 타입 다르면 false (널 처리 포함:
                                                 //   null is Money → false)
        return amount == other.amount && currency == other.currency
    }

    override fun hashCode(): Int =               // 6절에서 필수임을 설명
        31 * amount.hashCode() + currency.hashCode()
}

val m1 = Money(1000, "KRW")
val m2 = Money(1000, "KRW")
val m3 = Money(1000, "USD")
println(m1 == m2)   // => true
println(m1 == m3)   // => false
println(m1 == null) // => false  (null is Money가 false → 계약5 만족)
```

`other is Money` 검사가 두 계약을 동시에 처리한다. `null is Money`는 `false`이므로 널 처리(계약5)가 자동 만족되고, 타입이 다르면 `false`를 반환해 이종 비교를 막는다. `this === other` 빠른 경로는 반사성을 보장하면서(자기 자신과는 무조건 `true`) 동일 객체일 때 필드 비교를 건너뛰는 최적화다.

### 5.3 상속이 대칭성을 깨는 방식

`equals`에서 가장 악명 높은 버그는 **상속과 대칭성**이다. 하위 클래스가 필드를 추가하면서 대칭을 지키려다 실패한다.

```kotlin
open class Shape(val name: String) {
    override fun equals(other: Any?): Boolean =
        other is Shape && name == other.name
    override fun hashCode() = name.hashCode()
}

class ColoredShape(name: String, val color: String) : Shape(name) {
    override fun equals(other: Any?): Boolean =
        other is ColoredShape && name == other.name && color == other.color
    override fun hashCode() = 31 * name.hashCode() + color.hashCode()
}

val s = Shape("circle")
val cs = ColoredShape("circle", "red")

println(s == cs)   // => true   (s.equals(cs): cs is Shape이고 name 같음)
println(cs == s)   // => false  (cs.equals(s): s is ColoredShape가 false)
// 대칭성 위반! s==cs 와 cs==s 가 다르다
```

`s == cs`는 `Shape.equals`를 부르고 "이름만 같으면 같다"고 판정한다. `cs == s`는 `ColoredShape.equals`를 부르고 "색도 있어야 한다"며 거부한다. 방향에 따라 답이 달라진다 — 대칭성 붕괴다. 이 상태로 `HashSet`에 두 객체를 넣으면 중복 판정이 실행 순서와 버킷 배치에 따라 요동친다.

근본 원인은 **`equals`와 상속의 상성이 나쁘다**는 것이다. 흔한 해법 세 가지:

- **`equals`가 관여하는 클래스는 `final`로**: 하위 클래스가 필드를 더해 동등 의미를 바꾸는 걸 원천 차단. Kotlin은 기본이 `final`이라([[24 - 상속과 오버라이딩과 초기화 순서]]) 자연스럽다.
- **정확한 클래스 일치 검사**: `is` 대신 `this.javaClass == other?.javaClass`(JVM 백엔드) 또는 `if (other == null || this::class != other::class) return false`. 그러면 `Shape`와 `ColoredShape`는 아예 비교 대상조차 아니게 되어 대칭 위반이 사라진다. 단, 상속 계층 간 비교가 영원히 `false`가 되는 부작용을 감수해야 한다.
- **상속 대신 합성(composition)**: 색을 가진 도형을 별도 값 객체로 감싸 상속을 피한다.

Kotlin이 클래스를 기본 `final`로 만들고 `data class`([[27 - 데이터 클래스]])를 `open` 불가로 못박은 것은 바로 이 함정을 언어 차원에서 줄이려는 설계다. `data class`가 자동 생성하는 `equals`는 `other is 클래스이름` 검사를 쓰는데, `data class`가 `final`이라 하위 타입이 존재할 수 없으니 `is` 검사가 곧 정확한 타입 일치가 되어 대칭성이 저절로 지켜진다.

> **명세 정밀**: `equals`의 파라미터가 `Any?`인 것과 `data class`가 정확한 타입 일치를 검사하는 것은 별개다. 표준 라이브러리 `data class`의 생성된 `equals`는 대략 `if (this === other) return true; if (other !is 클래스이름) return false` 후 각 프로퍼티를 비교하는 형태다. `is`(JVM 백엔드에선 `instanceof`) 검사를 쓰지만 `data class`가 `final`이라 하위 타입이 없어, 이 검사가 정확한 타입 일치와 같아져 이종 타입을 대칭적으로 거부한다. 자세한 생성 규칙은 27장이 소유한다.

### 5.4 가변 필드와 일관성

계약 4(일관성)는 **동등 판정에 쓰는 필드가 변하지 않아야** 한다는 뜻으로 이어진다. 가변(`var`) 필드를 `equals`/`hashCode`에 넣으면, 컬렉션에 넣은 뒤 그 필드를 바꾸는 순간 객체가 "길을 잃는다".

```kotlin
class MutableKey(var id: Int) {
    override fun equals(other: Any?) = other is MutableKey && id == other.id
    override fun hashCode() = id
}

val set = hashSetOf(MutableKey(1))
val k = set.first()
k.id = 99                       // equals/hashCode에 쓰이는 필드를 변경!
println(k in set)               // => false  (해시 버킷이 바뀌어 못 찾음)
println(set.first().id)         // => 99      (그런데 셋 안엔 여전히 있음)
```

객체는 여전히 셋 안에 있는데 `in`으로는 못 찾는다. `hashCode`가 바뀌어 다른 버킷을 뒤지기 때문이다. **불변 데이터로만 `equals`/`hashCode`를 구성하라**는 원칙([[11 - 변수와 초기화 - val과 const와 lateinit]]의 `val` 선호와 통한다)이 여기서 실전적으로 정당화된다.

## 6. `hashCode` 계약 — `equals`의 그림자

### 6.1 왜 `equals`만으론 부족한가

`equals`를 재정의했으면 `hashCode`도 반드시 재정의해야 한다. 이건 예의가 아니라 **계약**이다. `Any`의 계약은:

- **일관성**: 같은 객체에 대해 `hashCode()`는 (동등 관련 정보가 안 바뀌는 한) 항상 같은 정수를 반환.
- **equals-hashCode 연대**: `a.equals(b)`가 `true`이면 `a.hashCode() == b.hashCode()`여야 한다.
- (역은 요구 안 함): 해시가 같다고 동등할 필요는 없다(해시 충돌 허용).

핵심은 두 번째다. **동등한 객체는 반드시 같은 해시코드**를 가져야 한다. 해시 기반 자료구조(`HashMap`, `HashSet`, `LinkedHashMap` 등)는 값을 먼저 `hashCode`로 버킷을 고르고, 그 버킷 안에서만 `equals`로 정밀 비교한다. 동등한데 해시가 다르면 서로 다른 버킷에 떨어져 영원히 만나지 못한다.

### 6.2 `equals`만 재정의한 재앙

```kotlin
class BadMoney(val amount: Long, val currency: String) {
    override fun equals(other: Any?): Boolean =
        other is BadMoney && amount == other.amount && currency == other.currency
    // hashCode 재정의 안 함 → Any.hashCode (객체 식별 기반, 인스턴스마다 다름)
}

val set = hashSetOf(BadMoney(1000, "KRW"))
println(BadMoney(1000, "KRW") in set)   // => false (!!)
// 논리적으로 같은 돈인데 셋에 없다고 나옴
```

```text
HashSet 조회 실패의 해부

넣은 객체:   BadMoney(1000,"KRW")  hashCode=0x1A2B  → 버킷 5
찾는 객체:   BadMoney(1000,"KRW")  hashCode=0x9F0C  → 버킷 12
                                    (Any.hashCode = 서로 다른 인스턴스 = 다른 해시)

버킷 12를 뒤짐 → 아무것도 없음 → "없다"  ← equals는 호출조차 안 됨
```

`equals`는 `true`를 낼 준비가 돼 있지만, 애초에 `hashCode`가 다른 버킷을 가리켜 `equals`가 **불리지도 않는다**. 이게 "`equals`만 재정의"의 전형적 재앙이다. 컴파일은 되고, `==` 비교는 잘 되니 테스트에서 놓치기 쉽고, 해시 컬렉션에 들어간 순간 조용히 부서진다.

### 6.3 올바른 `hashCode`와 자동 생성

`hashCode`는 `equals`에 쓴 필드들로부터 결정론적으로 계산해야 한다. 표준 관용구는 소수(관례상 31)를 누적하는 것이다:

```kotlin
override fun hashCode(): Int {
    var result = amount.hashCode()
    result = 31 * result + currency.hashCode()
    return result
}
// 또는 표준 라이브러리 헬퍼:
override fun hashCode(): Int = Objects.hash(amount, currency)  // JVM, 약간 느림
```

31을 쓰는 건 홀수 소수라 해시 분포가 좋고, `31 * x`가 `(x shl 5) - x`로 최적화되기 때문이다([[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]의 시프트). 중요한 건 **`equals`가 보는 필드 집합과 `hashCode`가 보는 필드 집합이 정확히 일치**해야 연대 계약이 지켜진다는 것.

실무에서는 이 짝을 손으로 쓰지 않고 [[27 - 데이터 클래스]]에 맡긴다. `data class`는 주 생성자 프로퍼티로부터 `equals`/`hashCode`/`toString`/`componentN`/`copy`를 **자동 생성**하며, 이 짝은 언제나 정합하다.

```kotlin
data class Money(val amount: Long, val currency: String)

val set = hashSetOf(Money(1000, "KRW"))
println(Money(1000, "KRW") in set)   // => true  (equals/hashCode 자동 정합)
```

단, `data class`의 자동 생성은 **주 생성자 프로퍼티만** 참여한다는 함정(M21)과 `copy`가 얕은 복사(M22)라는 함정이 있는데, 이는 27장이 정본으로 다룬다. 여기서는 "동등/해시의 정합은 `data class`로 얻는 게 가장 안전하다"만 취한다.

> **성능 주의**: `hashCode`는 자주(맵 조회마다) 불리므로 비싸면 안 된다. 필드가 많고 불변이면 지연 계산 후 캐시(`by lazy`, [[23 - 위임 프로퍼티]])하는 기법도 있으나, 대부분은 필요 없다. 반대로 모든 객체가 같은 `hashCode`(예: 항상 0)를 반환하면 계약은 지켜지지만 해시 컬렉션이 링크드 리스트로 퇴화해 $O(1)$이 $O(n)$이 된다.

### 6.4 세 함수의 연대표

| 상황 | `==` (equals) | `===` | 해시 컬렉션 동작 |
|------|---------------|-------|------------------|
| 둘 다 재정의, 정합 | 값 비교 | 객체 비교 | 정상 |
| equals만 재정의 | 값 비교 | 객체 비교 | **부서짐** (조회 실패) |
| hashCode만 재정의 | 참조 비교(Any) | 객체 비교 | 값 다뤄도 다 다르게 취급 |
| 둘 다 미재정의 | 참조 비교(Any) | 객체 비교 | 인스턴스 식별로만 동작 |

가운데 두 줄이 버그 지대다. **`equals`와 `hashCode`는 항상 짝으로 재정의**하거나, 둘 다 손대지 말거나(참조 의미론으로 충분한 경우) 해야 한다.

## 7. 부동소수점 동등 — IEEE 754 vs 전순서

### 7.1 두 얼굴을 가진 동등

부동소수점은 동등성의 가장 미묘한 무대다. `Double`과 `Float`는 `==`의 결과가 **정적 타입에 따라** 달라진다. 이건 버그가 아니라 Kotlin이 의도적으로 설계한 **두 얼굴**이다.

- **정적 타입이 `Float`/`Double`(또는 그 널 가능 짝)일 때**: 연산은 **IEEE 754** 표준을 따른다. 즉 `NaN != NaN`, `-0.0 == 0.0`.
- **정적 타입이 `Any`, `Comparable<...>`, 제네릭 타입 파라미터 등 부동소수로 정적으로 알려지지 않았을 때**: `Float`/`Double`의 `equals`/`compareTo` 구현을 쓰며, 이는 **전순서(total order)** 를 제공한다. 즉 `NaN.equals(NaN) == true`, `(-0.0).equals(0.0) == false`.

```kotlin
val nan = Double.NaN

// (1) 정적 타입 Double → IEEE 754
println(nan == nan)            // => false  (NaN은 자기 자신과도 같지 않다)
println(0.0 == -0.0)           // => true   (IEEE: +0과 -0은 같다)

// (2) 정적 타입 Any → 전순서(equals)
val a: Any = nan
val b: Any = nan
println(a == b)                // => true   (Double.equals: NaN == NaN)

println(nan.equals(nan))       // => true   (equals 직접 호출도 전순서)
println((-0.0).equals(0.0))    // => false  (equals: -0.0 != 0.0)
```

같은 `nan`을 비교하는데 정적 타입이 `Double`이면 `false`, `Any`면 `true`다. 같은 `0.0`과 `-0.0`이 `Double` 비교에선 같고 `equals` 비교에선 다르다. 이 이중성을 모르면 "왜 컬렉션에서만 결과가 다르지?"라는 미궁에 빠진다.

### 7.2 왜 두 얼굴인가

IEEE 754는 수치 계산의 정확성을 위해 `NaN != NaN`(계산이 무의미해졌다는 신호)과 `-0.0 == 0.0`(부호 있는 0은 수치적으로 같다)을 규정한다. 순수 산술에서는 이게 옳다.

하지만 **컬렉션과 정렬**은 다른 걸 요구한다. `HashSet<Double>`에 `NaN`을 넣었으면 나중에 그 `NaN`을 다시 찾을 수 있어야 하고(반사성!), 정렬 시 모든 원소가 서로 순서 지어져야(전순서) 안정적이다. `NaN != NaN`이면 `NaN`을 셋에서 영원히 못 찾고, 정렬이 `NaN` 근처에서 무너진다. 그래서 Kotlin은 **박스형·제네릭 문맥에서는 IEEE를 버리고 전순서를 쓴다**: `NaN`을 자기 자신과 같게 만들고(반사성 회복), `NaN`을 모든 값보다 크게, `-0.0`을 `0.0`보다 작게 정의한다.

```text
전순서(total order)에서의 Double 배치 (equals/compareTo 기준)

  -∞ < ... < -0.0 < +0.0 < ... < +∞ < NaN
              └ 서로 다름 ┘         └ 자기 자신과 같고, 최대 ┘

IEEE 754에서는:  -0.0 == +0.0  이고  NaN 은 어떤 것과도 비교 불가(순서 없음)
```

`NaN`을 "최대"로 둔 건 임의 선택이지만, 컬렉션 안에서 일관되게 자리 잡게 하려는 실용적 결정이다.

### 7.3 컬렉션에서 드러나는 결과

```kotlin
val nan = Double.NaN

// contains는 원소를 Any로 다루므로 전순서(equals) 사용
println(listOf(nan).contains(nan))   // => true   (NaN을 찾을 수 있다!)
println(listOf(nan).indexOf(nan))    // => 0

// -0.0과 0.0은 equals가 다르므로 둘 다 셋에 들어간다
val s = hashSetOf(0.0, -0.0)
println(s.size)                      // => 2      (전순서: -0.0 != 0.0)

// 정렬도 전순서 → NaN이 맨 뒤로
println(listOf(3.0, nan, 1.0, -0.0, 0.0).sorted())
// => [-0.0, 0.0, 1.0, 3.0, NaN]
```

정적 `Double` 비교였다면 `listOf(nan).contains(nan)`이 `false`가 나야 할 것 같지만(왜냐면 `nan == nan`은 `false`니까), 컬렉션은 원소를 `Any`로 다루므로 `equals`(전순서)를 써서 `true`가 된다. **"수식에서의 `==`"와 "컬렉션 안에서의 동등"이 부동소수점에서 갈라지는 이유가 바로 이 정적 타입의 차이다.**

### 7.4 실전 지침

```kotlin
// 나쁨: 부동소수 동등을 정확한 값으로 비교
val computed = 0.1 + 0.2
println(computed == 0.3)             // => false  (0.30000000000000004)

// 좋음: 허용 오차(epsilon) 비교
fun approxEquals(a: Double, b: Double, eps: Double = 1e-9) =
    kotlin.math.abs(a - b) < eps
println(approxEquals(computed, 0.3)) // => true
```

부동소수점의 정확한 표현 한계([[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]], 그리고 IEEE 754 자체는 데이터 표현 시리즈 참조)로 인해, 계산 결과를 `==`로 정확히 비교하는 건 거의 항상 버그다. 허용 오차 비교를 쓰되, `NaN`이 낄 수 있으면 `NaN` 검사(`x.isNaN()`)를 명시적으로 하라. 그리고 `Double`을 해시 키나 정렬 키로 쓸 때는 전순서 의미론(NaN 반사성, -0.0≠0.0)이 작동한다는 걸 기억하라 — 그것이 의도와 다르면 정규화(예: `if (x == 0.0) 0.0 else x`로 -0.0 제거, `NaN` 사전 배제)가 필요하다.

> **명세 정밀**: "정적 타입이 `Double`/`Float` 또는 그 널 가능 짝이면 IEEE 754"라는 규칙에서 **널 가능 짝(`Double?`)도 IEEE**라는 점이 반직관적이다. `Double?`은 박스처럼 보이지만, 컴파일러가 정적 타입을 알기에 IEEE 비교 코드(널 처리 포함)를 낸다. 반면 `Any`로 상향 변환되면 정적 타입 정보가 사라져 전순서 `equals`로 간다. 즉 갈림길은 "런타임에 박스냐"가 아니라 "컴파일 타임에 정적 타입이 부동소수로 알려졌느냐"다.

```kotlin
val x: Double? = Double.NaN
val y: Double? = Double.NaN
println(x == y)   // => false  (Double? 도 IEEE → NaN != NaN)

val p: Any = Double.NaN
println(p == Double.NaN)  // => true   (Any → 전순서)
```

## 8. `Comparable`과 `compareTo` — 순서라는 또 다른 동등

### 8.1 세 번째 비교 축

지금까지 우리는 두 종류의 "같음"을 봤다: 구조적 동등(`==`/`equals`)과 참조 동일(`===`). 세 번째 비교 축이 있다 — **순서(ordering)**. `<`, `<=`, `>`, `>=`는 `Comparable` 인터페이스의 `compareTo`로 탈설탕된다.

```kotlin
public interface Comparable<in T> {
    public operator fun compareTo(other: T): Int
}
```

`operator`가 붙어 있어 비교 연산자로 연결된다([[19 - 연산자 오버로딩과 관례]]). 탈설탕 규칙:

| 표현 | 번역 |
|------|------|
| `a < b`  | `a.compareTo(b) < 0` |
| `a > b`  | `a.compareTo(b) > 0` |
| `a <= b` | `a.compareTo(b) <= 0` |
| `a >= b` | `a.compareTo(b) >= 0` |

`compareTo`는 음수(좌변이 작다)/`0`(순서상 같다)/양수(좌변이 크다)를 반환한다. 주의: **비교 연산자는 `compareTo`로만 가고, `==`로는 절대 가지 않는다.** `a == b`는 언제나 `equals`, `a < b`는 언제나 `compareTo`다. 이 둘은 서로 다른 함수다.

```kotlin
println(3 < 5)               // 3.compareTo(5) < 0 → true
println("apple" < "banana")  // 사전순 compareTo → true
println('a' < 'z')           // Char의 compareTo (코드유닛 비교, 9장)
```

### 8.2 `compareTo == 0`과 `equals`는 별개의 사건

가장 흔한 오해: "`a.compareTo(b) == 0`이면 `a == b`다." — **아니다.** 순서상 "같은 위치"인 것과 구조적으로 동등한 것은 계약상 별개다. `Comparable`의 문서는 "`compareTo`가 `equals`와 **일관되기를 강력히 권장**하지만 강제하지 않는다"고 명시한다.

이 불일치의 교과서적 예는 (JVM 백엔드에서 쓰는) `BigDecimal`이다:

```kotlin
import java.math.BigDecimal
val a = BigDecimal("2.0")
val b = BigDecimal("2.00")

println(a.compareTo(b))   // => 0     (수치적으로 같은 위치)
println(a == b)           // => false (equals는 스케일까지 봄: 2.0 ≠ 2.00)
println(a.equals(b))      // => false
```

`2.0`과 `2.00`은 순서상 같은 자리지만(같은 수), `equals`는 스케일(소수 자릿수)까지 구별해 다르다고 본다. 그 결과 `TreeSet`(순서 기반)과 `HashSet`(equals 기반)에서 이 둘의 취급이 갈린다.

```kotlin
println(java.util.TreeSet<BigDecimal>().apply { add(a); add(b) }.size)  // => 1 (compareTo)
println(hashSetOf(a, b).size)                                           // => 2 (equals)
```

**같은 두 값이 순서 기반 컬렉션에선 하나, 해시 기반 컬렉션에선 둘로 센다.** 이 함정을 피하려면 순서 기반 자료구조에 넣는 타입은 `compareTo`와 `equals`가 일관되도록 설계해야 한다.

### 8.3 `compareValuesBy`와 다중 키 정렬

여러 필드로 순서를 정할 때 `compareTo`를 손으로 짜는 대신 표준 라이브러리 헬퍼를 쓴다.

```kotlin
class Person(val lastName: String, val firstName: String, val age: Int) : Comparable<Person> {
    override fun compareTo(other: Person): Int =
        compareValuesBy(this, other,
            { it.lastName }, { it.firstName }, { it.age })
}

val list = listOf(
    Person("Kim", "Bora", 30),
    Person("Kim", "Ana", 25),
    Person("Lee", "Ana", 40),
)
println(list.sorted().map { "${it.lastName} ${it.firstName}" })
// => [Kim Ana, Kim Bora, Lee Ana]
```

`compareValuesBy`는 셀렉터를 순서대로 적용해 첫 번째 차이가 나는 지점에서 결정한다(사전식 비교). 정렬 시엔 `sortedBy`, `sortedWith(compareBy(...).thenBy(...))` 같은 확장([[39 - 컬렉션 연산과 함수형 파이프라인]])도 있다. 이들은 모두 `compareTo`가 만드는 전순서를 소비한다.

### 8.4 순서의 전순서 계약

`Comparable`이 정의하는 순서는 **전순서(total order)** 여야 한다: 반사적(`x.compareTo(x)==0`), 반대칭적(`x<y`면 `y>x`), 추이적(`x<y`이고 `y<z`면 `x<z`), 그리고 모든 원소 쌍이 비교 가능(부동소수의 `NaN`이 7.2절에서 전순서로 편입된 이유가 이것). 이 계약을 어긴 `compareTo`(예: 상황에 따라 다른 부호를 반환)를 정렬에 쓰면 결과가 뒤죽박죽이 되거나 예외가 날 수 있다.

```text
세 개의 비교 축 — 서로 독립적인 판정

  a === b   (참조 동일)   ── "같은 객체인가"        재정의 불가
  a == b    (구조 동등)   ── equals 호출            재정의: equals
  a < b     (순서)        ── compareTo 호출         재정의: compareTo(Comparable)

계약의 다리:
  a === b  ⇒  a == b            (같은 객체면 구조도 같다, equals가 정상이면)
  a == b   ⇏  a.compareTo(b)==0 (권장되나 강제 아님: BigDecimal 반례)
  a.compareTo(b)==0 ⇏ a == b    (같은 자리 ≠ 구조 동등)
```

이 다이어그램이 이 장의 전체 지도다. 세 축은 독립적으로 재정의되며, 이상적으로는 서로 일관되지만(잘 설계된 값 타입), 계약이 강제하는 다리는 하나뿐이다 — 동등이면 해시가 같아야 한다는 `equals`↔`hashCode` 연대. 나머지 일관성은 개발자의 책임이다.

## 9. 실전 종합 — 값을 올바르게 짓기

### 9.1 배열의 함정

동등성의 마지막 함정은 배열이다. `Array<T>`([[38 - 컬렉션 - 읽기 전용과 가변]], M43)는 `equals`를 재정의하지 않으므로 `==`가 **참조 비교**로 떨어진다.

```kotlin
val a = arrayOf(1, 2, 3)
val b = arrayOf(1, 2, 3)
println(a == b)              // => false  (참조 비교! 내용 아님)
println(a === b)             // => false
println(a.contentEquals(b))  // => true   (내용 비교는 이걸로)

// 중첩 배열은 contentDeepEquals
val m1 = arrayOf(intArrayOf(1), intArrayOf(2))
val m2 = arrayOf(intArrayOf(1), intArrayOf(2))
println(m1.contentEquals(m2))     // => false (한 겹만 비교, 원소는 참조)
println(m1.contentDeepEquals(m2)) // => true
```

`List`는 구조적 `equals`를 제공하지만(`listOf(1,2,3) == listOf(1,2,3)`은 `true`), 배열은 아니다. 배열의 이 예외성은 JVM 배열이 그렇게 동작하는 것을 Kotlin이 그대로 노출한 결과다. 배열을 다룰 땐 `contentEquals`/`contentDeepEquals`를 반드시 기억하라.

### 9.2 값 타입을 짓는 체크리스트

지금까지의 계약을 하나의 체크리스트로 압축한다. "이 클래스의 두 인스턴스가 내용으로 같다고 취급되어야 하는가?"가 `yes`라면:

```text
값 타입(value-semantics) 설계 체크리스트

□ data class로 만들 수 있으면 그렇게 하라 (equals/hashCode 자동 정합)
□ 손수 만든다면:
   □ equals와 hashCode를 항상 짝으로 재정의
   □ 같은 필드 집합을 equals와 hashCode에 사용
   □ equals: this===other 빠른 경로 → is 타입검사 → 필드 비교
   □ equals에 쓰는 필드는 불변(val)으로 — 일관성 계약
   □ 상속이 관여하면 final로 만들거나 정확한 클래스 검사
□ Comparable을 구현한다면 compareTo가 equals와 일관되게 (특히 정렬 컬렉션 사용 시)
□ 부동소수 필드가 있으면 NaN/-0.0의 전순서 동작을 인지
□ 배열 필드가 있으면 equals/hashCode에서 contentEquals/contentHashCode 사용
□ 값이 같은지 판정엔 언제나 == , === 는 참조 정체성이 본질일 때만
```

### 9.3 마지막 종합 예제

```kotlin
data class Color(val r: Int, val g: Int, val b: Int) : Comparable<Color> {
    // 밝기(luminance)로 순서 정의 — equals와 일관되지 않을 수 있음에 주의
    private val luminance get() = 0.299 * r + 0.587 * g + 0.114 * b
    override fun compareTo(other: Color): Int =
        luminance.compareTo(other.luminance)
}

val red = Color(255, 0, 0)
val green = Color(0, 255, 0)
val red2 = Color(255, 0, 0)

println(red == red2)           // => true   (data class equals: 필드 동일)
println(red === red2)          // => false  (다른 객체)
println(red < green)           // => true   (red가 더 어둡다, compareTo)
println(hashSetOf(red, red2).size)  // => 1  (equals/hashCode 정합)
```

여기서 `Color`는 세 축 모두를 보여준다: `==`는 RGB 필드로 동등(data class 자동), `===`는 물리적 객체 식별, `<`는 밝기 순서(compareTo). 주의할 점 — `compareTo`를 밝기로 정의했으므로 서로 다른 색이 같은 밝기를 가지면 `compareTo == 0`이지만 `equals`는 `false`가 될 수 있다(8.2절의 불일치). 이 `Color`를 `TreeSet`에 넣으면 밝기가 같은 다른 색이 하나로 뭉개질 수 있으니, 그런 용도라면 `compareTo`를 RGB 사전식으로 바꿔 `equals`와 일관되게 해야 한다.

---

우리는 "같다"라는 단순한 단어가 Kotlin에서 세 갈래 — 구조적 동등(`==`), 참조 동일(`===`), 순서상 같음(`compareTo==0`) — 로 갈라진다는 것을 보았다. Java에서 온 습관대로 `==`를 참조 비교로 여기면(M6) 조용한 버그가 심기고, 반대로 `===`를 값 비교로 신뢰하면 박싱 캐시가 `127`과 `128` 사이에서 답을 뒤집는다(M48). `==`는 `a?.equals(b) ?: (b === null)`로 탈설탕되어 널 안전하게 좌변의 `equals`를 부르고, 그 `equals`는 반사·대칭·추이·일관·null의 다섯 계약을 져야 하며, 그림자처럼 따라붙는 `hashCode`가 없으면 해시 컬렉션 안에서 부서진다. 부동소수점은 정적 타입에 따라 IEEE 754의 얼굴(`NaN != NaN`)과 전순서의 얼굴(`NaN.equals(NaN)`)을 번갈아 쓰고, `compareTo`는 순서라는 세 번째 판정을 세우되 `equals`와 강제 일관되지는 않는다. 불리언에서 시작한 이 여정은 결국 하나의 원칙으로 수렴한다 — **값이 같은지는 언제나 `==`, 그리고 값 타입을 만들면 `equals`와 `hashCode`는 짝으로 짓고 필요하면 `compareTo`까지 일관되게 한다.** 다음 [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 우리는 이 값들이 담기는 그릇 — `val`과 `var`, 그리고 불변성의 진짜 의미(M3) — 로 넘어간다.

## 핵심 요약

- **Kotlin의 `==`는 구조적 동등(`equals` 호출)이고 `===`가 참조 동일이다. Java의 습관 — `==`는 참조 비교 — 을 그대로 들고 오면 조용한 버그가 된다 (M6).**
- **`a == b`는 `a?.equals(b) ?: (b === null)`로 탈설탕된다. 좌변의 `equals`를 부르되 어떤 피연산자가 널이어도 NPE를 던지지 않으며, 양쪽이 모두 널이면 `true`다.**
- **`===`는 물리적 객체 동일성이며 재정의 불가다. 값이 같은지 판정에 `===`를 쓰면 안 된다 — 참조 정체성이 본질인 캐시·싱글턴·`equals` 빠른 경로에서만 쓴다.**
- **박스로 표현되는 값에 `===`를 쓰면 결과가 예측 불가능하다: JVM 백엔드의 박싱 캐시(`-128..127`) 때문에 `Int? 127 === 127`은 `true`, `128 === 128`은 `false`다. `===`는 모든 값에서 의미 있지 않다 (M48).**
- **`equals`는 반사·대칭·추이·일관·널처리의 다섯 계약을 진다. 상속이 대칭성을 깨는 대표 함정이며, Kotlin이 클래스를 기본 `final`로 두고 `data class`를 `open` 불가로 한 것은 이 함정을 줄이는 설계다.**
- **`equals`를 재정의하면 `hashCode`도 반드시 짝으로 재정의해야 한다. 동등한 객체는 같은 해시를 가져야 하며(연대 계약), 어기면 `HashSet`/`HashMap`이 조용히 조회에 실패한다. `data class`는 이 짝을 자동 정합시킨다 (M21 참조).**
- **`equals`/`hashCode`에 쓰는 필드는 불변(`val`)이어야 한다. 컬렉션에 넣은 뒤 가변 필드를 바꾸면 객체가 해시 버킷을 잃어 `in`으로 찾을 수 없게 된다.**
- **부동소수점 동등은 정적 타입에 따라 두 얼굴이다: `Double`/`Float`(널 가능 짝 포함)이면 IEEE 754(`NaN != NaN`, `-0.0 == 0.0`), `Any`/제네릭이면 전순서 `equals`(`NaN.equals(NaN)==true`, `(-0.0).equals(0.0)==false`).**
- **그래서 `listOf(NaN).contains(NaN)`은 `true`이고 `hashSetOf(0.0, -0.0).size`는 `2`다 — 컬렉션은 원소를 `Any`로 다뤄 전순서를 쓴다. 부동소수 값 비교는 허용 오차(epsilon)로 하라.**
- **`<`/`>`/`<=`/`>=`는 `Comparable.compareTo`로 탈설탕되며 `==`와 완전히 별개다. `compareTo == 0`이 `equals == true`를 함의하지 않는다(`BigDecimal` 반례). 순서 기반 컬렉션과 해시 기반 컬렉션이 같은 값을 다르게 셀 수 있다.**
- **세 비교 축(`===`, `==`, `compareTo`)은 독립적으로 재정의되며, 계약이 강제하는 유일한 다리는 `equals`↔`hashCode` 연대다. 나머지 일관성은 값 타입을 짓는 개발자의 책임이다.**
- **배열(`Array<T>`)은 `equals`가 참조 비교로 떨어진다. 내용 비교는 `contentEquals`/`contentDeepEquals`를 써야 한다 (M43 참조).**
