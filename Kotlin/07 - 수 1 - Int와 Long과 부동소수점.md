**이 장이 답하는 질문:**

- 코틀린엔 정말 원시 타입(primitive)이 없는가? 그렇다면 `Int`는 왜 `Integer`처럼 무겁지 않은가?
- `val l: Long = 1`은 되는데 `val l: Long = i`(i가 `Int`)는 왜 컴파일 에러인가?
- `3.14`의 타입은 `Float`인가 `Double`인가? `val f: Float = 3.14`는 왜 안 되는가?
- `val b1: Byte = 1; val b2: Byte = 2` 일 때 `b1 + b2`의 타입은 왜 `Byte`가 아니라 `Int`인가?
- `val ms: Long = 25 * 24 * 60 * 60 * 1000`은 왜 음수가 되는가?
- 정수 `1 / 0`은 예외를 던지는데 `1.0 / 0.0`은 왜 조용히 `Infinity`를 내놓는가?
- `0.1 + 0.2`는 왜 `0.3`이 아닌가? 이건 코틀린의 버그인가?
- `1 == 1L`은 왜 컴파일 에러인데 `1 < 1L`은 되는가?
- `Double.MIN_VALUE`는 왜 음수가 아니라 아주 작은 양수인가?

앞의 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서 우리는 "코틀린에서는 모든 것이 객체이고, 최상단에 `Any`가, 최하단에 `Nothing`이 있다"는 지형을 그렸다. 그때 미뤄 둔 약속이 하나 있었다. "원시 타입은 없다, 자세한 것은 07·08장에서"라는 약속이다. 이 장은 그 약속을 지키는 첫 절반이다. 우리는 `Int`, `Long`, `Double` 같은 수 타입이 소스 코드에서는 완전한 클래스처럼 행동하면서, 기계 위에서는 어떻게 CPU가 직접 아는 비트 뭉치로 변신하는지를 파고든다.

이 장은 **수의 표면 문법과 타입 규칙**을 소유한다. 정수 여섯 종류의 타입, 리터럴 문법, 타입 추론의 기본형, 리터럴 상수의 특례, "암시적 확대 변환 없음"이라는 자바와의 결정적 차이, 정수 나눗셈, 그리고 JVM 백엔드가 원시형으로 컴파일한다는 사실(M4)까지가 여기 있다. 반대로 이 장이 **다루지 않는** 것도 분명히 못박아 둔다. 박싱과 언박싱의 기계적 상세, 오버플로가 만드는 비트 래핑, 비트 연산(`shl`/`and`/`inv`), 부호 없는 정수(`UInt`), 그리고 캐시된 박스와 `===`의 함정은 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]가 소유한다. `Char`가 왜 수가 아닌지는 [[09 - 문자와 문자열 - 유니코드와 템플릿]]이, `==`와 `===`의 완전한 계약과 부동소수점 동등성의 전면적 함정은 [[10 - 불리언과 동등성과 동일성]]이 가져간다. 이 장은 그 두께의 절반, "값과 문법과 산술" 층만 판다.

논증의 궤적은 이렇다. 먼저 여섯 개의 수 타입과 그 위에 앉은 `Number` 슈퍼타입을 지도로 펼친다(1절). 그다음 리터럴이 어떤 문법으로 쓰이고 어떤 타입을 얻는지(2절), 그 타입이 어떻게 추론되는지(3절)를 본다. 여기서 핵심 반전이 온다. 코틀린은 자바가 당연하게 여기는 **암시적 확대 변환을 거부**하는데(5절), 이 거부가 왜 안전을 사는 대신 초심자를 당황시키는지, 그리고 그 예외인 **리터럴 상수의 특례**(4절)가 왜 필요한지를 설명한다. 이어서 정수 나눗셈과 산술의 함정(6절)을 지나, 마침내 "원시 타입은 없다"는 명제를 기계 수준에서 정면으로 교정하고(7절), 부동소수점(IEEE 754)의 근본(8절)과 변환·비교의 총정리(9절)로 마무리한다.

## 1. 수의 지형 — 여섯 개의 타입과 하나의 슈퍼타입

### 1.1 여섯 개의 내장 수 타입

코틀린의 표준 라이브러리(`kotlin` 패키지)에는 정확히 여섯 개의 실수·정수 타입이 내장되어 있다. 정수 계열 넷과 부동소수점 계열 둘이다.

| 타입 | 비트 폭 | 계열 | 범위(닫힌 구간) | 리터럴 접미사 |
|------|--------|------|----------------|--------------|
| `Byte` | 8 | 정수 | $[-2^{7},\ 2^{7}-1]$ = $[-128,\ 127]$ | 없음 |
| `Short` | 16 | 정수 | $[-2^{15},\ 2^{15}-1]$ = $[-32768,\ 32767]$ | 없음 |
| `Int` | 32 | 정수 | $[-2^{31},\ 2^{31}-1]$ | 없음(기본) |
| `Long` | 64 | 정수 | $[-2^{63},\ 2^{63}-1]$ | `L` |
| `Float` | 32 | 부동소수 | IEEE 754 단정밀도 | `f` / `F` |
| `Double` | 64 | 부동소수 | IEEE 754 배정밀도 | 없음(기본) |

각 타입은 자신의 극값을 `MIN_VALUE`/`MAX_VALUE` 상수로 노출한다. 정수와 부동소수점에서 이 상수의 **의미가 다르다**는 점을 여기서 못박아 두자. 뒤(8절)에서 다시 다루지만, 이것이 첫 번째 함정이다.

```kotlin
println(Int.MIN_VALUE)   // => -2147483648  (가장 작은 '음수')
println(Int.MAX_VALUE)   // => 2147483647   (가장 큰 '양수')
println(Long.MAX_VALUE)  // => 9223372036854775807

println(Double.MIN_VALUE) // => 4.9E-324  (가장 작은 '양수'! 음수가 아님)
println(Double.MAX_VALUE) // => 1.7976931348623157E308
```

정수의 `MIN_VALUE`는 표현 가능한 **가장 작은 값**(가장 큰 음수)이다. 그러나 부동소수점의 `MIN_VALUE`는 표현 가능한 **가장 작은 양수**(0에 가장 가까운 양수)다. 정수의 직관을 부동소수점에 옮기면 "가장 작은 double"을 찾으려고 `Double.MIN_VALUE`를 쓰는 실수를 하게 된다. 부동소수점에서 "가장 작은(가장 음수인) 값"은 `-Double.MAX_VALUE`다.

> **흔한 오해**: `Double.MIN_VALUE`가 음의 무한대에 가까운 값이라고 생각하는 것. 실제로는 $4.9 \times 10^{-324}$, 즉 0보다 아주 조금 큰 양의 서브노멀 값이다. 이 불일치는 코틀린의 발명이 아니라 자바의 `Double.MIN_VALUE`, 나아가 IEEE 754의 관습을 그대로 물려받은 것이다. 정수와 부동소수점을 한 문장에서 같은 이름의 상수로 다룰 때 늘 조심할 것.

### 1.2 `Number` 슈퍼타입

여섯 타입은 모두 추상 클래스 `Number`의 하위 타입이다. `Number`는 값을 다른 수 타입으로 변환하는 추상 메서드들을 계약으로 요구한다.

```text
                     Any
                      │
                   Number  (추상 클래스)
      ┌────┬────┬────┼────┬─────┬──────┐
    Byte Short  Int  Long Float Double
```

```kotlin
abstract class Number {
    abstract fun toDouble(): Double
    abstract fun toFloat(): Float
    abstract fun toLong(): Long
    abstract fun toInt(): Int
    abstract fun toShort(): Short
    abstract fun toByte(): Byte
    // toChar()는 과거에 있었으나 Kotlin 1.5부터 Number에서 deprecated
}
```

`Number`는 **산술 연산자를 정의하지 않는다**. `plus`, `times` 같은 관례 함수([[19 - 연산자 오버로딩과 관례]])는 구체 타입(`Int`, `Double` 등)에만 있다. 그래서 `Number` 타입 변수로는 더하기를 할 수 없다.

```kotlin
val a: Number = 3
val b: Number = 4
// val c = a + b   // 컴파일 에러: Number에는 plus 연산자가 없음
val c = a.toInt() + b.toInt()  // 구체 타입으로 내려와야 산술 가능
println(c) // => 7
```

이 설계에는 의도가 있다. `Number`는 "어떤 수든 담는 공통 상자"라는 다형적 그릇일 뿐, 그 상자 안에서 무슨 산술을 해야 할지는 정의되지 않는다(`Byte`끼리의 `+`와 `Double`끼리의 `+`는 기계 수준에서 완전히 다른 명령이다). 그리고 뒤(7절)에서 보겠지만, `Number` 타입으로 값을 담는 순간 JVM 백엔드에서는 **박싱**이 강제된다. `Number`는 원시형이 될 수 없기 때문이다.

한 가지 명세 정밀을 덧붙이자. `Char`는 `Number`의 하위 타입이 **아니다**. 문자는 코드 유닛(정수처럼 생긴 값)을 감싸지만, 코틀린은 `Char`를 수가 아니라 별도 타입으로 취급한다. `Char`에는 `+`가 `Int`를 받아 다시 `Char`를 내는 특수한 관례만 있을 뿐, `Number` 계약에 참여하지 않는다. 이 결정의 이유는 [[09 - 문자와 문자열 - 유니코드와 템플릿]]에서 다룬다.

### 1.3 `Boolean`은 이 장의 손님이 아니다

혼동을 막기 위해 경계를 하나 더 긋는다. `Boolean`은 수가 아니다. C나 자바스크립트처럼 `true`를 1로, `false`를 0으로 암묵 변환하는 일은 코틀린에 없다. `if (1)` 같은 코드는 컴파일되지 않는다. 불리언과 동등성·동일성은 [[10 - 불리언과 동등성과 동일성]]의 영역이다. 이 장은 오직 정수와 부동소수점, 그리고 그것들 사이의 변환만 다룬다.

## 2. 리터럴의 문법과 타입

### 2.1 정수 리터럴의 네 가지 진법

정수 리터럴은 십진, 십육진, 이진의 세 표기가 있다. **팔진(octal)은 지원하지 않는다.**

```kotlin
val dec = 42          // 십진
val hex = 0x2A        // 십육진 (0x 또는 0X 접두)
val bin = 0b101010    // 이진 (0b 또는 0B 접두)
// val oct = 0o52     // 컴파일 에러: 팔진 표기 없음
```

팔진을 없앤 것은 의도적이다. C·자바에서는 `010`이 "십진 8"(팔진 리터럴)을 뜻해, 전화번호나 우편번호를 무심코 `010...`으로 쓰면 값이 바뀌는 고전적 버그가 있었다. 코틀린은 이 함정을 아예 제거하기 위해 **선행 0을 금지**한다.

```kotlin
val zip = 0        // OK: 단일 0
// val zip = 007   // 컴파일 에러: 선행 0을 가진 정수 리터럴 불가
```

> **역사 메모**: 팔진 리터럴은 1970년대 PDP-11 시절 워드 단위 조작에 유용했지만, 십진에 익숙한 현대 개발자에게는 순수한 함정이 되었다. 스칼라·코틀린 같은 후발 JVM 언어들이 공통적으로 팔진을 버린 이유다. 필요하면 `Integer.parseInt("52", 8)`처럼 명시적 진법 파싱을 쓰라는 것이 코틀린의 입장이다.

### 2.2 자릿수 구분자 `_`

가독성을 위해 리터럴 안에 밑줄을 넣을 수 있다. 밑줄은 순전히 시각적 장식이며 값에 영향을 주지 않는다.

```kotlin
val million    = 1_000_000
val creditCard = 1234_5678_9012_3456L
val bytes      = 0xFF_EC_DE_5E
val bits       = 0b1101_0010_0110_1001
```

밑줄은 숫자 사이에만 올 수 있다. 접두사(`0x`) 직후, 접미사(`L`) 직전, 리터럴의 처음·끝에는 오지 못한다.

```kotlin
// val bad1 = _1000      // 에러: 식별자로 해석됨
// val bad2 = 1000_      // 에러: 끝에 밑줄
// val bad3 = 0x_FF      // 에러: 접두사 직후 밑줄
// val bad4 = 100_L      // 에러: 접미사 직전 밑줄
```

### 2.3 `Long` 접미사는 대문자 `L`만

`Long` 리터럴은 접미사 `L`을 붙인다. 소문자 `l`은 **허용되지 않는다**.

```kotlin
val big = 10L       // Long
// val bad = 10l    // 에러: 소문자 l 금지
```

이유는 단순하지만 실용적이다. 소문자 `l`은 숫자 `1`과 시각적으로 거의 구별되지 않아 `10l`이 `101`처럼 보인다. 코틀린은 이 혼동을 원천 봉쇄하기 위해 대문자만 허용한다. 자바는 소문자 `l`도 받아들이지만 대부분의 코드 스타일 가이드가 이를 금지하는데, 코틀린은 그 관습을 언어 규칙으로 승격시켰다.

### 2.4 부동소수점 리터럴과 `Float` 접미사

소수점이나 지수 표기가 들어가면 부동소수점 리터럴이다. **접미사가 없으면 `Double`** 이다. `Float`을 원하면 `f` 또는 `F`를 붙인다.

```kotlin
val pi     = 3.14         // Double
val piF    = 3.14f        // Float
val sci    = 1.5e3        // Double, 1500.0
val sciNeg = 2.5E-4       // Double, 0.00025
val expOnly = 1e10        // Double, 소수점 없어도 지수가 있으면 부동소수
```

`Double`에는 자바의 `d` 접미사 같은 것이 필요 없다(붙일 수도 없다). 소수점이나 지수가 있는 리터럴은 그 자체로 `Double`이다. 반대로 정수처럼 보이는 리터럴은 소수점을 붙이지 않으면 절대 부동소수점이 되지 않는다. `1`은 `Int`, `1.0`은 `Double`이다. 이 구분이 뒤(4·5절)에서 "`val d: Double = 1`이 왜 에러인가"의 열쇠가 된다.

### 2.5 리터럴 요약표

| 리터럴 | 추론 타입 | 비고 |
|--------|----------|------|
| `42` | `Int` | Int 범위에 들면 Int |
| `4_000_000_000` | `Long` | Int 범위 초과 → 자동으로 Long |
| `42L` | `Long` | 명시 접미사 |
| `0x1F` | `Int` | 십육진, 값이 Int 범위 |
| `0b1010` | `Int` | 이진 |
| `3.14` | `Double` | 접미사 없는 소수 |
| `3.14f` | `Float` | f/F 접미사 |
| `1e10` | `Double` | 지수 표기 |
| `'A'` | `Char` | 수 아님(9장) |
| `true` | `Boolean` | 수 아님(10장) |

`4_000_000_000`이 자동으로 `Long`이 되는 규칙은 다음 절에서 자세히 본다. 이것은 "리터럴이 `Int`에 안 들어가면 컴파일러가 알아서 `Long`을 고른다"는 편의 규칙이다.

## 3. 타입 추론의 기본형 — `Int`와 `Double`

### 3.1 기본형이 `Int`와 `Double`인 이유

문맥이 타입을 강제하지 않을 때, 정수 리터럴은 `Int`로, 부동소수점 리터럴은 `Double`로 추론된다. 이것이 "기본형(default type)"이다.

```kotlin
val a = 100        // Int  (Byte도 Short도 아님)
val b = 3.14       // Double  (Float 아님)
val c = 100L       // Long  (명시했으므로)
val d = 100.0f     // Float (명시했으므로)
```

왜 하필 `Int`와 `Double`인가? `Int`(32비트)는 현대 CPU가 가장 효율적으로 다루는 정수 폭이고 대부분의 카운터·인덱스·산술에 충분하다. `Byte`·`Short`를 기본으로 삼으면 조금만 큰 값에서 곧바로 오버플로가 나고, `Long`을 기본으로 삼으면 메모리와 산술이 낭비된다. 부동소수점에서 `Double`을 기본으로 고른 것은 정밀도 때문이다. `Float`(약 7자리 유효숫자)은 웬만한 계산에서 오차가 눈에 띄게 커, 실수 계산의 안전한 출발점은 `Double`(약 15~17자리)이다.

### 3.2 리터럴이 `Int` 범위를 넘으면 `Long`

정수 리터럴이 `Int`가 표현할 수 있는 범위를 넘으면, 접미사 `L`이 없어도 컴파일러가 자동으로 `Long`으로 추론한다.

```kotlin
val small = 2_147_483_647       // Int (Int.MAX_VALUE)
val big   = 2_147_483_648       // Long (Int.MAX_VALUE + 1, 자동 승격)

val x = 9_000_000_000           // Long
// 만약 이 규칙이 없다면 컴파일 에러였을 것
```

이것은 "리터럴은 문맥이 없으면 `Int`이되, `Int`에 담을 수 없으면 `Long`으로 넓힌다"는 특별 규칙이다. 변수(`Int` 값)에는 이런 자동 승격이 절대 없다는 점과 대비된다(5절). 리터럴은 컴파일 타임 상수여서 컴파일러가 그 값을 알고 있고, 그래서 안전하게 타입을 고를 수 있다.

### 3.3 문맥(기대 타입)이 추론을 이끈다

기본형은 문맥이 없을 때의 이야기다. 기대 타입(expected type)이 주어지면 리터럴은 그 타입에 맞춰진다. 이것이 4절의 "리터럴 상수 특례"와 연결된다.

```kotlin
val a = 1              // 문맥 없음 → Int
val b: Long = 1        // 기대 타입 Long → 리터럴이 Long이 됨
val c: Byte = 1        // 기대 타입 Byte → 리터럴이 Byte가 됨

fun feed(amount: Long) { /* ... */ }
feed(1)                // 인자 기대 타입 Long → 리터럴 1이 Long

val list = listOf(1L, 2L, 3L)   // 원소 기대 타입 Long
```

여기서 결정적으로 중요한 것은 **정수 리터럴만** 이 특례를 받는다는 사실이다. 부동소수점은 이 관용을 받지 못한다.

```kotlin
val ok: Long = 1        // OK: 정수 리터럴 특례
// val no: Float = 1.0  // 컴파일 에러: Double 리터럴은 Float로 좁혀지지 않음
val yes: Float = 1.0f   // OK: 애초에 Float 리터럴
// val no2: Double = 1  // 컴파일 에러: 정수 리터럴은 Double로 넓혀지지 않음
val yes2: Double = 1.0  // OK: 부동소수점 리터럴
```

`val no2: Double = 1`이 에러라는 것이 특히 자바 사용자를 놀라게 한다. 자바는 `double d = 1;`을 조용히 받아준다(정수→부동소수 확대). 코틀린은 정수 리터럴을 `Byte`/`Short`/`Long`으로 좁히거나 넓히는 것은 허용하지만, **정수에서 부동소수점으로 건너뛰는 것은 허용하지 않는다**. `1`을 `Double`로 쓰려면 `1.0`으로 써야 한다. 다음 절에서 이 특례의 정확한 경계를 본다.

## 4. 리터럴 상수 특례 — 왜 `val b: Byte = 1`이 되는가

### 4.1 상수 표현식의 컴파일 타임 좁힘

3.3절에서 본 `val b: Byte = 1`은 조금 신기한 일이다. `Byte`는 `Int`의 하위 타입이 아니고, 코틀린은 암시적 변환을 싫어하는데(5절), 어떻게 `Int`처럼 생긴 `1`이 `Byte`가 될까?

답은 "`1`은 `Int` 값이 아니라 **정수 리터럴 상수**"라는 데 있다. 컴파일러는 컴파일 타임에 이 리터럴의 실제 값을 알고 있다. 기대 타입이 `Byte`이고, 그 값 `1`이 `Byte` 범위 $[-128, 127]$에 들어가면, 컴파일러는 그냥 그것을 `Byte` 리터럴로 만든다. 런타임 변환이 아니라 컴파일 타임 결정이다.

```kotlin
val b1: Byte = 1        // OK: 1이 Byte 범위에 있음
val b2: Byte = 127      // OK: 경계값
val b3: Byte = -128     // OK: 경계값
// val b4: Byte = 128   // 컴파일 에러: 128은 Byte 범위 초과
// val b5: Byte = 200   // 컴파일 에러: 범위 초과

val s: Short = 30000    // OK
// val s2: Short = 40000 // 컴파일 에러: Short.MAX(32767) 초과
```

`val b4: Byte = 128`이 **컴파일 에러**라는 점이 이 규칙의 아름다움이다. 만약 이것이 런타임 변환이었다면 `128`은 `Byte`로 좁혀지며 조용히 `-128`로 오버플로했을 것이다. 하지만 컴파일러가 상수를 알기 때문에, 범위를 벗어나는 순간 컴파일이 막힌다. 안전이 컴파일 타임으로 당겨진다.

### 4.2 특례는 "상수 표현식"에만 적용된다

이 관용은 리터럴 하나에만 국한되지 않는다. 컴파일 타임에 값이 확정되는 **상수 표현식(constant expression)** 전체에 적용된다. 리터럴들의 산술, `const val` 참조 등이 여기 포함된다.

```kotlin
val b: Byte = 1 + 1          // OK: 1+1은 상수 표현식, 값 2가 Byte 범위
val c: Byte = 100 + 27       // OK: 값 127
// val d: Byte = 100 + 28    // 컴파일 에러: 값 128, 범위 초과

const val BASE = 10
val e: Byte = BASE + 5       // OK: const val은 컴파일 상수, 값 15
```

여기서 `1 + 1`이 `Byte`가 될 수 있는 이유는, 이 덧셈이 런타임에 일어나는 것이 아니라 컴파일 타임에 `2`로 접힌(constant folding) 다음, 그 상수 `2`가 기대 타입 `Byte`로 맞춰지기 때문이다.

> **명세 정밀**: 상수 표현식이 아닌 것은 이 특례를 못 받는다. 변수를 거치는 순간 값은 이미 `Int`로 굳어져 있고, 컴파일러는 그 안의 값을 모른다. 그래서 아래는 실패한다. 이것이 5절의 주제로 이어진다.

```kotlin
val i = 1                 // i는 Int
// val b: Byte = i        // 컴파일 에러: i는 Int 값, 상수 아님
val b: Byte = i.toByte()  // 명시 변환 필요
```

`i`가 명백히 `1`을 담고 있어도, `i`는 상수가 아니라 `Int` 타입 변수다. 컴파일러는 "`i`의 타입은 `Int`, 기대 타입은 `Byte`, 둘 사이에 암시적 변환은 없다"고만 판단한다. 이 엄격함이 코틀린 수 시스템의 척추다.

## 5. 암시적 확대 변환의 부재 — 자바와의 결정적 차이

### 5.1 코틀린은 넓히지도 좁히지도 않는다

자바에서는 정수 타입 사이에 **암시적 확대 변환(widening)** 이 자동으로 일어난다. `int`를 `long` 자리에 넣으면 조용히 넓혀지고, `int`를 `double`에도 넣을 수 있다. 코틀린은 이것을 **전면 금지**한다. 좁히는 변환(narrowing)이 위험하다는 것은 누구나 알지만, 코틀린은 안전해 보이는 넓히는 변환까지 막는다.

```java
// Java
int i = 10;
long l = i;      // OK: 암시적 확대
double d = i;    // OK: 암시적 확대
```

```kotlin
// Kotlin
val i: Int = 10
// val l: Long = i     // 컴파일 에러: Int는 Long의 하위 타입이 아님
// val d: Double = i   // 컴파일 에러
val l: Long = i.toLong()      // 명시 변환
val d: Double = i.toDouble()  // 명시 변환
```

이 결정이 처음에는 짜증나게 느껴질 수 있다. "값을 잃지도 않는데 왜 손으로 `toLong()`을 써야 하나?" 그러나 여기엔 세 가지 깊은 이유가 있다.

### 5.2 이유 1 — 타입 계층의 정합성

`Int`가 `Long`으로 자동 변환되려면 `Int`가 `Long`의 하위 타입이어야 한다(리스코프 치환). 그러나 실제로는 그렇지 않다. `Long`이 할 수 있는 일 중 `Int`가 못 하는 것이 있고(예: `Long.MAX_VALUE`를 담기), `Int`가 할 수 있는 일 중 `Long`이 다르게 하는 것이 있다. 두 타입은 상속 관계가 아니라 형제(둘 다 `Number`의 자식)다. 암시적 변환은 상속 관계를 흉내 내지만 실제 타입 관계와 어긋나고, 이 어긋남이 제네릭·변성([[33 - 제네릭 1 - 타입 파라미터와 변성]])과 만나면 무너진다. 코틀린은 "하위 타입이면 변환, 아니면 명시"라는 단순하고 견고한 규칙을 택했다.

### 5.3 이유 2 — 오버로드 해소의 명료함

암시적 확대는 함수 오버로드 해소를 악몽으로 만든다. 자바에서 `f(1)`을 호출할 때 `f(int)`, `f(long)`, `f(double)`, `f(Integer)`, `f(Object)`가 모두 후보가 되고, 어느 것이 뽑히는지는 복잡한 우선순위 규칙에 달려 있다. 코틀린은 리터럴 특례(4절)를 제외하면 변수의 타입이 정확히 일치하는 오버로드만 후보로 삼아, "어느 `f`가 불릴까?"라는 질문의 답을 명료하게 만든다.

```kotlin
fun describe(x: Int)  = "정수 $x"
fun describe(x: Long) = "긴정수 $x"

val i: Int = 5
println(describe(i))        // => 정수 5   (Int 오버로드, 모호함 없음)
println(describe(i.toLong())) // => 긴정수 5
```

### 5.4 이유 3 — 조용한 정밀도 손실 방지

자바가 허용하는 `int → float`, `long → double` 확대는 사실 값이 손상될 수 있다. `float`은 유효숫자가 약 7자리뿐이라 큰 `int`를 담으면 정밀도를 잃고, `long`을 `double`에 넣어도 큰 값에서 정밀도가 깨진다. 코틀린은 이런 "안전해 보이지만 실은 손실이 있는" 변환도 손으로 쓰게 강제해, 개발자가 그 변환을 **의식하도록** 만든다.

```kotlin
val big: Long = 9_007_199_254_740_993L    // 2^53 + 1
val asDouble: Double = big.toDouble()     // 명시적으로 써야 함
println(asDouble.toLong())                // => 9007199254740992  (1 손실!)
```

`2^53 + 1`은 `Double`이 정확히 표현하지 못하는 첫 정수다(가수부 52비트의 한계). 자바라면 `double d = big;`이 조용히 이 손실을 냈겠지만, 코틀린은 `.toDouble()`을 손으로 쓰게 해서 "여기서 정밀도가 바뀔 수 있다"는 신호를 남긴다.

### 5.5 변환 함수 총람

모든 수 타입은 다른 수 타입으로 가는 `toXxx()` 변환 함수를 제공한다.

| 함수 | 하는 일 | 손실 |
|------|---------|------|
| `toByte()` | 하위 8비트만 취함 | 좁힘 시 상위 비트 버림 |
| `toShort()` | 하위 16비트만 취함 | 좁힘 시 손실 |
| `toInt()` | 하위 32비트 / 부동소수는 0으로 향해 절삭 | 좁힘·절삭 |
| `toLong()` | 부동소수는 0으로 향해 절삭 | 부동소수→정수 시 절삭 |
| `toFloat()` | 배정밀도→단정밀도 반올림 | 정밀도 손실 |
| `toDouble()` | 단정밀도→배정밀도(무손실) | 정수→double은 큰 값에서 손실 |

```kotlin
println(300.toByte())     // => 44    (300 = 256 + 44, 상위 비트 버림)
println(3.99.toInt())     // => 3     (0으로 향해 절삭, 반올림 아님)
println((-3.99).toInt())  // => -3    (0으로 향해 절삭)
println(1_000_000.toShort()) // => 16960  (하위 16비트)
```

`toInt()`가 반올림이 아니라 **0을 향한 절삭(truncation toward zero)** 이라는 점을 기억하자. `3.99.toInt()`는 `4`가 아니라 `3`이고, `(-3.99).toInt()`는 `-4`가 아니라 `-3`이다. 반올림을 원하면 `Math.round`나 `roundToInt()` 확장 함수를 써야 한다.

```kotlin
println(3.99.roundToInt())    // => 4  (반올림)
println((-3.5).roundToInt())  // => -3 (half-up: -3.5는 -3으로)
```

이 좁히는 변환들이 데이터를 어떻게 비트 수준에서 자르는지(그리고 부동소수 특수값이 정수로 어떻게 변환되는지)의 상세는 9절과 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]에서 더 판다.

## 6. 정수 나눗셈과 산술의 함정

### 6.1 정수 나눗셈은 소수를 버린다

`/` 연산자는 피연산자 타입에 따라 완전히 다르게 행동한다. 둘 다 정수면 **정수 나눗셈**(몫만 남고 나머지는 버림)이고, 하나라도 부동소수점이면 실수 나눗셈이다.

```kotlin
println(7 / 2)       // => 3    (정수 나눗셈, 0.5 버려짐)
println(7 / 2.0)     // => 3.5  (한쪽이 Double → 실수 나눗셈)
println(7.0 / 2)     // => 3.5
println(7 / 2.toDouble()) // => 3.5
```

이것이 초심자를 가장 자주 무는 함정이다. `val average = sum / count`에서 `sum`과 `count`가 둘 다 `Int`면 평균이 정수로 잘려 나온다. `1 / 2`는 `0.5`가 아니라 `0`이다.

```kotlin
val total = 5
val n = 2
val avg = total / n           // Int 나눗셈 → 2 (2.5가 아님!)
val avgReal = total.toDouble() / n  // => 2.5
```

### 6.2 절삭의 방향과 나머지의 부호

정수 나눗셈의 절삭은 **0을 향한다**(truncated division). 음수가 끼면 이 방향이 중요해진다.

```kotlin
println(7 / 2)     // => 3
println(-7 / 2)    // => -3   (내림 -4가 아니라 0 방향 절삭)
println(7 / -2)    // => -3
println(-7 / -2)   // => 3
```

나머지 연산자 `%`(관례 함수 `rem`)는 이 절삭과 짝을 이룬다. 결과의 부호는 **피제수(왼쪽 피연산자)의 부호**를 따른다.

```kotlin
println(7 % 3)     // => 1
println(-7 % 3)    // => -1   (피제수 -7의 부호)
println(7 % -3)    // => 1    (제수의 부호는 무관)
println(-7 % -3)   // => -1
```

수학적으로 항상 성립하는 항등식은 다음과 같다. 몫을 $q = a \mathbin{/} b$, 나머지를 $r = a \mathbin{\%} b$라 하면

$$a = b \times q + r, \qquad q = \operatorname{trunc}\!\left(\frac{a}{b}\right)$$

즉 나머지는 항상 몫의 절삭 방식에 의해 결정된다.

### 6.3 `rem`과 `mod`는 다르다

음수에서 "수학적 나머지"(항상 0 이상)를 원한다면 `%`가 아니라 `mod` 함수를 써야 한다. `mod`는 **내림 나눗셈(floored division)** 에 기반해, 결과의 부호가 **제수(divisor)** 를 따른다.

```kotlin
println(-7 % 3)      // => -1   (rem: 피제수 부호)
println((-7).mod(3)) // => 2    (mod: 제수 부호, 항상 0..제수-1)

println(-1 % 12)      // => -1
println((-1).mod(12)) // => 11  (시계·원형 인덱스에 유용)
```

`mod`가 특히 유용한 곳은 원형 인덱싱이다. 시계에서 "1시간 전"을 `(hour - 1) % 12`로 계산하면 0시에서 `-1`이 나오지만, `.mod(12)`를 쓰면 `11`이 정확히 나온다.

> **명세 정밀**: `mod`는 Kotlin 1.5에서 정식 추가되었다. `%`(=`rem`)와 `mod`는 제수가 나눠떨어질 때는 같지만, 나머지가 있고 부호가 엇갈릴 때 달라진다. 항등식으로는 `a.mod(b)`는 항상 `b`와 같은 부호(또는 0)이고 `0 <= a.mod(b).absoluteValue < b.absoluteValue`를 만족한다.

### 6.4 오버플로는 조용히 감싼다

정수 산술이 타입의 범위를 넘으면, 코틀린은 예외를 던지지 않고 **2의 보수 방식으로 감싼다(wrap around)**. 이것은 밑에 깔린 하드웨어 산술을 그대로 노출한 것이다.

```kotlin
println(Int.MAX_VALUE + 1)   // => -2147483648  (Int.MIN_VALUE로 감김)
println(Int.MIN_VALUE - 1)   // => 2147483647
```

이 감김 동작 자체의 비트 수준 해부와, 예외를 던지는 `Math.addExact` 같은 대안은 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]에서 소유한다. 여기서는 산술의 함정으로서 실무에서 어떻게 나타나는지만 본다.

```kotlin
// "하루는 몇 밀리초?" — 흔한 오버플로 버그
val oneDayMs   = 24 * 60 * 60 * 1000            // 86_400_000, Int로 OK
val days25Ms   = 25 * 24 * 60 * 60 * 1000       // 오버플로! 2_160_000_000 > Int.MAX
println(days25Ms)                                // => -2134967296 (음수!)

val fixed: Long = 25L * 24 * 60 * 60 * 1000     // => 2160000000, Long 산술
println(fixed)
```

### 6.5 "산술은 승격되지만 변수는 승격되지 않는다"

여기서 5절과 이어지는 미묘한 구분이 있다. 5절에서 "암시적 확대는 없다"고 했는데, 그렇다면 `1 + 1L`은 왜 되는가? `1`은 `Int`, `1L`은 `Long`인데?

답은 이것이 **암시적 변환이 아니라 연산자 오버로드**라는 데 있다. `Int`는 `Long`을 받는 `plus` 오버로드를 정의한다. `Int.plus(Long): Long`. 그래서 `1 + 1L`은 `1.plus(1L)`로 해석되고, 이 오버로드가 결과를 `Long`으로 준다. `Int` 값이 `Long`으로 변환된 것이 아니라, "Int와 Long을 더하면 Long"이라는 연산이 정의되어 있을 뿐이다.

```kotlin
val x = 1 + 1L         // Long (Int.plus(Long) 오버로드)
val y = 1 + 1.0        // Double (Int.plus(Double) 오버로드)
val z = 1L + 1.0f      // Float (Long.plus(Float) 오버로드)
```

각 수 타입은 여섯 개의 다른 수 타입 모두에 대한 `plus`/`minus`/`times`/`div`/`rem` 오버로드를 갖고 있다. 이것이 "혼합 산술은 넓은 쪽으로 승격된다"처럼 보이는 이유다. 그러나 이는 변수 대입의 암시적 변환과는 완전히 다른 메커니즘이다.

### 6.6 `Byte + Byte = Int`의 충격

이 오버로드 규칙의 가장 반직관적인 귀결이 있다. `Byte`끼리, 혹은 `Short`끼리 더하면 결과가 **`Int`** 다.

```kotlin
val b1: Byte = 10
val b2: Byte = 20
val sum = b1 + b2        // sum의 타입은 Int! (Byte 아님)
println(sum)             // => 30

// val bad: Byte = b1 + b2   // 컴파일 에러: Int를 Byte에 대입 불가
val ok: Byte = (b1 + b2).toByte()  // 명시 변환 필요
```

이유는 `Byte`가 `Byte`를 받는 `plus`를 `Byte`가 아니라 `Int`로 정의하기 때문이다. `Byte.plus(Byte): Int`. `Short`도 마찬가지다. 애초에 `Byte`·`Short`에는 자기끼리의 산술 오버로드가 `Int` 반환으로만 존재한다. 하드웨어가 8비트·16비트 산술을 32비트로 올려서 계산하는 관습(자바의 정수 승격)과 일치한다.

> **흔한 오해**: `Byte + Byte`가 `Byte`일 것이라는 기대. 실제로는 `Int`다. `Byte`·`Short`는 저장(메모리 절약)에는 쓰이지만, 산술에 들어가는 순간 곧바로 `Int`로 올라간다. 그래서 코틀린 코드에서 `Byte`·`Short`로 산술을 반복하는 것은 이득이 거의 없고, 매번 `.toByte()`를 부르느라 오히려 번거롭다. 카운터·인덱스·산술에는 그냥 `Int`를 쓰는 것이 관례다.

### 6.7 0으로 나누기 — 정수와 부동소수의 갈림길

정수를 0으로 나누면 `ArithmeticException`이 던져진다. 부동소수점을 0으로 나누면 예외 없이 `Infinity` 또는 `NaN`이 나온다.

```kotlin
// println(1 / 0)      // 런타임 예외: java.lang.ArithmeticException: / by zero (JVM 백엔드)
println(1.0 / 0.0)    // => Infinity
println(-1.0 / 0.0)   // => -Infinity
println(0.0 / 0.0)    // => NaN
// println(1 % 0)     // 이것도 ArithmeticException: / by zero
```

이 비대칭은 IEEE 754가 부동소수점에 `Infinity`와 `NaN`이라는 특수값을 정의해 두었기 때문이다. 정수에는 그런 특수값이 없어서, 0으로 나누기가 표현 불가능한 상황이 되고 예외로 처리된다. 이 특수값들의 정체는 다음 절에서 본다.

> **명세 정밀**: "정수 0으로 나누기가 `ArithmeticException`"이라는 서술은 JVM 백엔드에 정확히 맞는다. 다른 백엔드(Native/JS/Wasm)에서 이 동작이 완전히 동일하다고 명세가 모든 세부까지 보장하지는 않으므로, 플랫폼 독립적으로 안전하려면 나누기 전에 제수를 검사하는 것이 원칙이다.

## 7. 원시 타입으로의 컴파일 — M4의 정면 교정

### 7.1 오개념: "코틀린엔 원시 타입이 없다"

이제 이 장이 소유한 오개념 **M4**를 정면으로 다룬다. 자주 이렇게 말한다. "코틀린엔 원시 타입(primitive)이 없다. 모든 것이 객체다." 이 문장은 **절반만 참이고 절반은 오해를 부른다.** 정확히 나누어 보자.

- **참**: 코틀린 **소스 언어**에는 `int`/`Integer` 같은 원시/래퍼 이분법이 없다. `Int`는 하나의 타입이고, 메서드를 갖고, `Any`의 하위 타입이며, 타입 시스템에서 완전한 클래스처럼 행동한다. 소스에는 원시 타입이라는 별개 범주가 없다.
- **오해를 부르는 부분**: "그러니 코틀린 `Int`는 자바 `Integer`처럼 힙에 박싱된 객체다"라는 추론. **이것은 틀렸다.** JVM 백엔드는 가능한 모든 곳에서 `Int`를 원시 `int`로 컴파일한다.

즉 M4의 진실은 이렇다. **원시 타입은 소스 언어의 개념 층위에서만 사라졌고, 기계 층위에서는 그대로 살아 있다.** 코틀린은 "모든 것이 객체"라는 *일관된 소스 모델*과 "가능하면 원시형"이라는 *효율적 기계 모델*을 컴파일러가 다리 놓아 둘 다 얻는다.

### 7.2 JVM 백엔드에서 실제로 무슨 일이 일어나는가

같은 코틀린 소스가 문맥에 따라 원시형 `int`로도, 박싱된 `Integer`로도 컴파일된다.

```kotlin
val a: Int = 42          // JVM: 원시 int
val b: Int? = 42         // JVM: 박싱된 java.lang.Integer (null 표현 필요)
val list = listOf(1, 2)  // JVM: List<Integer> — 제네릭은 참조 타입만 가능 → 박싱
fun sq(x: Int) = x * x   // JVM: (I)I — 원시 int 파라미터·반환
```

이것을 `text` 의사 바이트코드로 그려 보면 차이가 선명하다.

```text
소스:  fun sq(x: Int): Int = x * x
JVM:   public static final int sq(int x) {   // int, 박싱 없음
           return x * x;                       // imul 명령 하나
       }

소스:  fun sqBox(x: Int?): Int? = ...
JVM:   public static final Integer sqBox(Integer x) {  // Integer, 박싱
           ...                                          // Integer.valueOf 등
       }
```

원시형으로 남는 경우와 박싱되는 경우를 규칙으로 정리하면 다음과 같다(JVM 백엔드 기준).

| 상황 | JVM 표현 | 이유 |
|------|---------|------|
| `val x: Int` (널 불가) | 원시 `int` | null을 표현할 필요 없음 |
| `val x: Int?` (널 가능) | 박싱 `Integer` | null은 원시형으로 표현 불가 |
| 제네릭 타입 인자 `List<Int>` | 박싱 `Integer` | JVM 제네릭은 참조 타입만 받음(소거) |
| `Number`/`Any`로 상향 | 박싱 | 슈퍼타입은 참조 타입 |
| 함수 파라미터·반환(널 불가) | 원시 `int` | 박싱 불필요 |
| 컬렉션 원소 | 박싱 | 위 제네릭 사유 |

박싱과 언박싱, 그리고 그것이 `===` 및 캐시된 박스와 만나 만드는 함정(M5, M48)은 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]와 [[10 - 불리언과 동등성과 동일성]]이 깊게 판다. 이 장에서는 "널 불가 `Int`는 원시형, 널 가능·제네릭·슈퍼타입은 박싱"이라는 큰 규칙만 못박는다.

### 7.3 다른 백엔드에서는 "원시"의 의미가 다르다

M4를 논할 때 JVM만 보면 안 된다. 코틀린은 멀티타깃 언어([[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]])이고, "원시형으로 컴파일된다"는 서술은 **JVM 백엔드에 한정**된 이야기다.

- **Kotlin/Native**(LLVM): `Int`는 네이티브 기계 정수(LLVM `i32`)로 컴파일된다. 힙 할당 없는 값으로 다뤄진다.
- **Kotlin/JS**: JavaScript에는 정수 타입이 없다(모든 수가 배정밀도 부동소수 `number`). `Int`·`Double`은 JS `number`로 표현되고, `Int` 산술은 32비트로 절삭하는 코드가 삽입된다. `Long`은 JS의 `number`로 담을 수 없어(53비트 정수 한계), **별도의 에뮬레이션 클래스**로 컴파일된다(구현 세부는 버전·백엔드에 따라 다르다).
- **Kotlin/Wasm**: WebAssembly는 `i32`/`i64`/`f32`/`f64`를 네이티브로 갖고 있어, `Int`→`i32`, `Long`→`i64`, `Double`→`f64`로 자연스럽게 매핑된다.

```text
             Int                Long              Double
 JVM     int / Integer      long / Long       double / Double
 Native  LLVM i32           LLVM i64          LLVM double
 JS      number(32비트절삭)  에뮬레이션 클래스  number
 Wasm    i32                i64               f64
```

이 표가 말하는 바는 이렇다. "코틀린 `Int`가 무엇으로 컴파일되는가"에는 백엔드 독립적인 단일 답이 없다. 소스 수준에서는 언제나 같은 `Int`지만, 그 아래의 표현은 타깃마다 다르다. 그러므로 M4의 정확한 진술은 이렇게 되어야 한다.

> **명세 정밀 (M4)**: 코틀린 소스 언어에는 원시 타입 범주가 없다(모든 수 타입은 클래스처럼 행동한다). 그러나 이것이 곧 "런타임에도 항상 박싱된다"는 뜻은 **아니다**. 컴파일러는 각 백엔드가 가진 가장 효율적인 기계 표현으로 내려보낸다. JVM 백엔드에서는 널이 불가능한 곳에서 `int`·`long`·`double` 같은 원시형으로 컴파일하고, 널 가능·제네릭·슈퍼타입 위치에서만 래퍼로 박싱한다.

### 7.4 왜 이렇게 설계했나 — 통일성과 효율의 동시 획득

자바는 `int`(원시)와 `Integer`(객체)를 두 개의 다른 타입으로 노출해, 개발자가 늘 "여기선 어느 쪽?"을 신경 쓰게 만든다. `List<int>`는 불가능하고 `List<Integer>`만 되며, 오토박싱이 언제 일어나는지 추적해야 한다. 코틀린은 소스에서 이 이분법을 지워 개발자에게 **하나의 통일된 타입 모델**을 준다. `Int` 하나만 알면 된다.

동시에 컴파일러가 뒤에서 원시형 최적화를 해 주기 때문에, 이 통일성이 성능을 희생시키지 않는다. 널 불가 `Int`로 짠 루프는 자바의 `int` 루프와 동일한 바이트코드로 컴파일된다. 개발자는 "모든 것이 객체"라는 깔끔한 정신 모델로 코드를 짜고, 기계는 원시형으로 빠르게 돈다. 이 분리가 M4의 핵심이자 코틀린 수 설계의 우아함이다.

> **성능 주의**: 이 우아함에는 새는 구멍이 있다. 코드가 `Int?`, `List<Int>`, `Number`, 제네릭 `T`를 지나가는 순간 박싱이 개입한다. 뜨거운 루프에서 무심코 `Int?`나 박싱 컬렉션을 돌리면 원시형 최적화가 사라지고 힙 할당이 폭발한다. "코틀린 수는 공짜로 빠르다"가 아니라 "널 불가·비제네릭 경로에서만 빠르다"가 정확한 이해다. 상세는 08장.

## 8. 부동소수점의 기초 — IEEE 754

### 8.1 `Float`과 `Double`의 비트 레이아웃

`Float`과 `Double`은 정수처럼 값을 곧이곧대로 비트에 담지 않는다. 부호(sign)·지수(exponent)·가수(mantissa/significand)의 세 부분으로 쪼개어, 과학적 표기법의 이진 버전으로 실수를 근사한다. 이것이 IEEE 754 표준이다.

```text
Float (32비트):
  ┌─┬────────┬───────────────────────┐
  │S│  E(8)  │        M(23)           │
  └─┴────────┴───────────────────────┘
   부호  지수         가수

Double (64비트):
  ┌─┬───────────┬──────────────────────────────────────────┐
  │S│   E(11)   │                 M(52)                     │
  └─┴───────────┴──────────────────────────────────────────┘
```

값은 대략 다음 공식으로 복원된다(정규 수 기준). $s$는 부호 비트, $e$는 지수, $m$은 가수 비트열, $\text{bias}$는 지수 편향(Double은 1023, Float은 127)이다.

$$\text{value} = (-1)^{s} \times 1.m_{2} \times 2^{\,e - \text{bias}}$$

가수 앞의 `1.`(암시적 선행 1비트)과 `2`의 거듭제곱이라는 점이 핵심이다. 실수를 **2의 거듭제곱의 합**으로 표현하기 때문에, 10진 소수 중 상당수가 정확히 표현되지 않는다.

### 8.2 `0.1 + 0.2`가 `0.3`이 아닌 이유

이것은 코틀린의 버그가 아니라 이진 부동소수점의 근본 성질이다. 언어와 무관하게 자바·C·파이썬·자바스크립트 모두 같은 결과를 낸다.

```kotlin
println(0.1 + 0.2)          // => 0.30000000000000004
println(0.1 + 0.2 == 0.3)   // => false
```

`0.1`은 이진으로 유한하게 표현되지 않는다. 십진 `1/10`을 이진으로 쓰면 `0.0001100110011...`처럼 무한 순환한다. `1/3`을 십진 소수로 정확히 못 쓰는 것과 똑같은 현상이다. `Double`은 이 무한 순환을 52비트에서 잘라 저장하므로, `0.1`은 정확히 `0.1`이 아니라 그에 아주 가까운 값이다. `0.1`과 `0.2`의 이런 미세 오차가 더해지면서 `0.3`과는 다른 값이 된다.

$$0.1_{10} = 0.0\overline{0011}_2 \quad(\text{이진 무한 순환})$$

그래서 부동소수점 값을 `==`로 비교하는 것은 거의 항상 잘못이다. 오차 허용 범위(epsilon) 안에 드는지를 봐야 한다.

```kotlin
val eps = 1e-9
println(kotlin.math.abs((0.1 + 0.2) - 0.3) < eps)  // => true
```

돈 계산에 `Double`을 쓰면 안 되는 이유가 여기 있다. `0.1`(10센트)조차 정확히 표현 못 하는 타입으로 회계를 하면 반올림 오차가 쌓인다. 금액은 정수 단위(예: 최소 화폐 단위)나 `BigDecimal`로 다뤄야 한다.

> **역사 메모**: IEEE 754는 1985년에 표준화되어 오늘날 거의 모든 CPU의 부동소수점 유닛이 이를 구현한다. "0.1 + 0.2 문제"는 특정 언어의 결함이 아니라 유한 비트로 실수를 근사하려는 시도의 필연적 대가다. 정확한 이진 표현·반올림 규칙·서브노멀 수의 상세는 컴퓨터 구조·데이터 표현 계열 자료의 IEEE 754 장을 참고하라(이 시리즈의 범위 밖).

### 8.3 특수값 — `Infinity`, `-Infinity`, `NaN`

IEEE 754는 정상 수로 표현할 수 없는 결과를 위해 세 특수값을 예약한다. 이들은 지수 비트가 전부 1인 패턴으로 인코딩된다.

```kotlin
println(Double.POSITIVE_INFINITY)  // => Infinity
println(Double.NEGATIVE_INFINITY)  // => -Infinity
println(Double.NaN)                // => NaN

println(1.0 / 0.0)          // => Infinity
println(-1.0 / 0.0)         // => -Infinity
println(0.0 / 0.0)          // => NaN
println(Double.MAX_VALUE * 2) // => Infinity (오버플로는 예외 아님)
println(kotlin.math.sqrt(-1.0)) // => NaN
```

`NaN`(Not a Number)은 "정의되지 않은 실수 연산"의 결과다. `0.0/0.0`, 음수의 제곱근, `Infinity - Infinity` 등에서 나온다. `NaN`의 가장 악명 높은 성질은 **자기 자신과도 같지 않다**는 것이다.

```kotlin
val nan = Double.NaN
println(nan == nan)          // => false  (IEEE 754 규칙, 정적 타입 Double)
println(nan != nan)          // => true
println(nan.isNaN())         // => true   (NaN 검사의 올바른 방법)
```

`NaN == NaN`이 `false`인 것은 IEEE 754가 그렇게 정했기 때문이다. 그래서 값이 `NaN`인지 확인하려면 `==`가 아니라 `isNaN()`을 써야 한다. `x != x`가 참이면 `x`는 `NaN`이라는 관용구도 이 성질에서 나온다.

### 8.4 `-0.0`과 정적 타입의 함정 — 10장 예고

부동소수점에는 `0.0`과 `-0.0`이 따로 있다. 두 값은 IEEE 비교(`==`)에서는 같지만, 비트로는 다르다.

```kotlin
println(0.0 == -0.0)                  // => true  (IEEE 비교)
println(0.0.toRawBits())              // => 0
println((-0.0).toRawBits())           // => -9223372036854775808 (부호 비트만 1)
```

그런데 여기서 코틀린의 미묘하고 중요한 규칙이 등장한다. **피연산자의 정적 타입이 `Double`/`Float`일 때는 IEEE 754 비교**를 쓰지만, 그 값이 **박싱되거나 `Comparable`·컬렉션·`equals`를 통해 다뤄질 때는 "전순서(total order)"** 를 써서 `NaN == NaN`을 참으로, `-0.0 < 0.0`을 참으로 취급한다.

```kotlin
println(Double.NaN == Double.NaN)                 // => false (정적 Double, IEEE)
println(Double.NaN.equals(Double.NaN))            // => true  (전순서)
println(listOf(Double.NaN).contains(Double.NaN))  // => true  (컬렉션은 equals → 전순서)

println(0.0 == -0.0)                    // => true  (IEEE)
println(0.0.compareTo(-0.0))            // => 1     (전순서: 0.0 > -0.0)
println(0.0.equals(-0.0))               // => false (전순서: 다른 값)
```

이 이중성(`==` 연산자 vs `equals`/`compareTo`)이 왜 존재하는지, 그리고 그것이 `HashSet`·정렬에서 어떤 놀라움을 만드는지의 완전한 해부는 [[10 - 불리언과 동등성과 동일성]]과 그 안의 M48이 소유한다. 이 장에서는 "부동소수점 비교는 문맥에 따라 규칙이 갈린다"는 사실만 심어 둔다. 부동소수점을 다룰 때는 `==`의 결과와 컬렉션·정렬의 결과가 다를 수 있음을 늘 의심하라.

### 8.5 `Float`의 정밀도 한계

`Float`(32비트)은 가수부가 23비트뿐이라 유효숫자가 약 7자리에 그친다. `Double`은 52비트로 약 15~17자리다. 그래서 `Float`은 저장 공간이나 GPU 인터페이스가 중요한 특수 상황이 아니면 잘 쓰지 않는다.

```kotlin
val f: Float = 0.1f + 0.2f
println(f)                    // => 0.3  (Float 정밀도에서는 오차가 반올림에 묻힘)
println((0.1f + 0.2f) == 0.3f) // => true (우연히 맞지만 신뢰하지 말 것)

println(16_777_217.toFloat())  // => 1.6777216E7 (2^24 + 1, Float가 표현 못 함 → 1 손실)
```

`16_777_217`(=$2^{24}+1$)은 `Float`이 정확히 표현하지 못하는 첫 정수다. 가수부 23비트의 한계에서 정밀도가 끊긴다. `Double`은 $2^{53}$까지 정수를 정확히 표현한다(5.4절에서 본 `2^53 + 1` 손실과 같은 원리, 폭만 다름). 부동소수점은 큰 수일수록 표현 가능한 값들 사이 간격이 벌어지는 "가변 정밀도"임을 잊지 말자.

## 9. 비교와 변환의 총정리

### 9.1 비교 연산자는 `compareTo`로 간다

`<`, `>`, `<=`, `>=`는 관례 함수 `compareTo`([[19 - 연산자 오버로딩과 관례]])로 변환된다. 각 수 타입은 다른 모든 수 타입에 대한 `compareTo` 오버로드를 갖고 있어, 서로 다른 타입의 값도 값 기준으로 비교할 수 있다.

```kotlin
println(1 < 2L)        // => true  (Int.compareTo(Long))
println(3.14 > 3)      // => true  (Double.compareTo(Int))
println(1L <= 1.0)     // => true
```

### 9.2 그런데 `1 == 1L`은 왜 에러인가

비교 연산자는 혼합 타입을 받는데, 동등 연산자 `==`는 그렇지 않다. `1 == 1L`은 **컴파일 에러**다.

```kotlin
println(1 < 1L)        // => true   (compareTo 오버로드 존재)
// println(1 == 1L)    // 컴파일 에러: Int와 Long의 == 불가
println(1 == 1)        // => true
println(1L == 1L)      // => true
println(1.toLong() == 1L) // => true (같은 타입으로 맞춰서)
```

이 비대칭은 두 연산의 성질이 다르기 때문이다. `<`는 `Comparable` 계약(순서)이라 "이 값이 저 값보다 큰가"라는 질문이 타입을 가로질러도 의미가 있다. 그러나 `==`는 **동등성(equality)** 계약이라, 코틀린은 서로 다른 정적 타입 사이의 `==`를 원칙적으로 막는다. `Int` `1`과 `Long` `1`은 "같은 값"처럼 보이지만 다른 타입이고, 코틀린은 타입이 어긋난 동등 비교를 컴파일 타임에 거부해 실수를 막는다. 값 비교를 원하면 한쪽을 명시적으로 변환해 타입을 맞춰야 한다. `==`의 이 계약 전체는 [[10 - 불리언과 동등성과 동일성]]의 소유다.

### 9.3 변환은 언제나 명시적, 그리고 방향이 있다

5절에서 본 `toXxx()` 변환들을 방향별로 정리하자. 무손실 방향(넓히기)과 손실 가능 방향(좁히기)이 있다.

```text
무손실(대체로):  Byte → Short → Int → Long
                          Int → Double,  Long → Double(단, 2^53 넘으면 손실)
                        Float → Double
손실 가능(좁히기): 반대 방향 전부
                  Double → Int/Long: 0으로 절삭
                  Double → Float: 반올림, Infinity/큰값 손실
                  Int → Byte: 하위 8비트만
```

부동소수점을 정수로 변환할 때의 특수값 처리는 반드시 알아 둬야 할 함정이다.

```kotlin
println(Double.NaN.toInt())               // => 0
println(Double.POSITIVE_INFINITY.toInt()) // => 2147483647 (Int.MAX_VALUE)
println(Double.NEGATIVE_INFINITY.toInt()) // => -2147483648 (Int.MIN_VALUE)
println(1e20.toInt())                     // => 2147483647 (Int 범위 넘으면 saturate)
println(1e20.toLong())                    // => 9223372036854775807 (Long.MAX)
```

`NaN.toInt()`가 예외가 아니라 `0`을, `Infinity.toInt()`가 `Int.MAX_VALUE`를 내는 것은 JVM의 `d2i` 명령 의미론(포화 변환)을 그대로 따른 것이다. 이것을 모르면 `NaN`이 섞인 데이터를 정수로 변환할 때 조용히 `0`이 끼어드는 버그를 만난다.

> **명세 정밀**: 부동소수→정수 변환이 "0으로 절삭, NaN은 0, 무한대·범위초과는 포화(saturate)"라는 서술은 JVM 백엔드의 동작이다. 이 세부가 모든 백엔드에서 비트 단위로 동일하다고 명세가 보장한다고 단정하지 말고, 플랫폼 독립 코드에서는 변환 전에 `isNaN()`·`isInfinite()`·범위를 검사하는 편이 안전하다.

### 9.4 유용한 표준 라이브러리 도구

수 타입에는 산술 외에도 여러 확장·프로퍼티가 있다. 몇 가지 자주 쓰는 것을 정리한다.

```kotlin
println(5.coerceIn(0, 10))       // => 5   (범위로 클램프)
println(15.coerceIn(0, 10))      // => 10
println((-5).coerceAtLeast(0))   // => 0

println((-7).absoluteValue)      // => 7   (kotlin.math)
println(3.7.roundToInt())        // => 4
println(maxOf(3, 7, 2))          // => 7
println(10.0.pow(3))             // => 1000.0 (kotlin.math)

println(255.toString(16))        // => "ff"  (16진 문자열)
println("ff".toInt(16))          // => 255   (16진 파싱)
println("2147483648".toIntOrNull()) // => null (Int 범위 초과, 예외 대신 null)
```

`toIntOrNull()`이 예외 대신 `null`을 준다는 점이 특히 유용하다. 사용자 입력을 파싱할 때 `toInt()`는 형식이 틀리거나 범위를 넘으면 `NumberFormatException`을 던지지만, `toIntOrNull()`은 널을 돌려줘 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]의 안전 호출·엘비스와 자연스럽게 결합된다.

```kotlin
fun parseAge(input: String): Int =
    input.toIntOrNull()?.coerceIn(0, 150) ?: 0   // 파싱 실패 시 0
```

지금까지 우리는 코틀린의 수를 표면 문법에서 기계 표현까지 훑어 내려왔다. 여섯 개의 타입과 그것들을 잇는 `Number`에서 출발해, 리터럴이 어떻게 쓰이고 어떤 타입으로 추론되는지, 그 추론이 상수 표현식의 특례로 어떻게 유연해지는지를 보았다. 그다음 코틀린이 자바의 암시적 확대 변환을 거부하며 안전을 사들이는 대목에서, "변수는 승격되지 않지만 연산자 오버로드는 혼합 산술을 허용한다"는 미묘한 이중성을 만났고, 그것이 `Byte + Byte = Int`라는 반직관을 낳는 것을 확인했다. 그리고 이 장의 심장인 M4에서, "원시 타입이 없다"는 말이 소스 언어의 통일성에 관한 진술일 뿐 기계 층위에서는 JVM이 여전히 `int`로 컴파일한다는 사실을 정면으로 교정했다. 마지막으로 부동소수점의 IEEE 754 근본을 파고들어, `0.1 + 0.2`가 왜 `0.3`이 아닌지, `NaN`이 왜 자기 자신과 다른지, 정적 타입과 전순서가 왜 다른 비교 규칙을 쓰는지를 들췄다. 도입부의 질문들—`val l: Long = 1`은 되고 `= i`는 안 되는 이유, `1 == 1L`은 에러인데 `1 < 1L`은 되는 이유—은 모두 하나의 원리로 수렴한다. **코틀린의 수는 소스에서 통일되어 있고, 규칙에서 엄격하며, 기계 위에서 효율적이다.** 이 세 성질의 긴장이 이 장 전체를 관통한다. 남은 절반—박싱의 기계학, 오버플로의 비트, 비트 연산, 부호 없는 정수—은 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]가 이어받는다.

## 핵심 요약

- **코틀린엔 원시 타입 범주가 소스 언어에 없을 뿐, 기계 층위에서는 살아 있다.** JVM 백엔드는 널 불가 `Int`를 원시 `int`로, 널 가능·제네릭·슈퍼타입 위치에서만 박싱된 `Integer`로 컴파일한다. "모든 것이 객체"는 정신 모델의 통일성이고, 그것이 성능을 희생하지 않는다. (M4)
- **수 타입은 여섯 개(`Byte`/`Short`/`Int`/`Long`/`Float`/`Double`)이며 모두 추상 클래스 `Number`의 하위 타입이다.** `Number`는 변환 메서드만 계약하고 산술 연산자는 정의하지 않아, `Number` 타입으로는 더하기를 할 수 없고 박싱을 강제한다. `Char`와 `Boolean`은 수가 아니다.
- **문맥이 없으면 정수 리터럴은 `Int`, 부동소수점 리터럴은 `Double`로 추론된다.** 정수 리터럴이 `Int` 범위를 넘으면 접미사 없이도 자동으로 `Long`이 된다. `Long`은 대문자 `L`만, `Float`은 `f`/`F`를, `Double`은 접미사가 없다.
- **정수 리터럴(과 상수 표현식)만 기대 타입으로 좁혀지는 특례를 받는다.** `val b: Byte = 1`은 컴파일 타임에 상수 `1`을 `Byte`로 확정하기 때문이며, `val b: Byte = 128`은 범위 초과로 컴파일이 막힌다. 부동소수점 리터럴은 이 관용을 못 받아 `val f: Float = 1.0`은 에러다.
- **코틀린은 암시적 확대 변환을 전면 거부한다(자바와의 결정적 차이).** `val l: Long = i`(i가 `Int`)는 에러이고 `i.toLong()`을 손으로 써야 한다. 타입 계층 정합성, 오버로드 해소의 명료함, 조용한 정밀도 손실 방지가 그 이유다.
- **변수는 승격되지 않지만, 산술은 연산자 오버로드로 혼합 타입을 허용한다.** `1 + 1L`이 `Long`인 것은 `Int.plus(Long): Long` 오버로드 때문이지 암시적 변환이 아니다. 그 귀결로 `Byte + Byte`는 `Byte`가 아니라 `Int`가 된다.
- **정수 나눗셈은 0을 향해 절삭하고 소수를 버린다.** `7 / 2 == 3`, `-7 / 2 == -3`. 나머지 `%`(=`rem`)는 피제수의 부호를, `mod`는 제수의 부호를 따른다. 평균 계산에서 `sum / count`가 둘 다 정수면 결과가 잘린다.
- **정수 오버플로는 예외 없이 2의 보수로 감기고, 정수 0 나누기는 예외를, 부동소수 0 나누기는 `Infinity`/`NaN`을 낸다.** `25 * 24 * 60 * 60 * 1000` 같은 식은 `Int`에서 오버플로해 음수가 되므로 `25L`로 시작해야 한다.
- **부동소수점은 IEEE 754로 실수를 이진 근사한다.** `0.1`은 이진에서 무한 순환하므로 `0.1 + 0.2 != 0.3`이며, 이는 언어 버그가 아니라 표준의 성질이다. 금액에 `Double`을 쓰면 안 된다. 비교는 `==` 대신 epsilon으로.
- **`NaN`은 자기 자신과도 같지 않다(`NaN == NaN`은 `false`).** 검사는 `isNaN()`으로 한다. `Double.MIN_VALUE`는 가장 큰 음수가 아니라 가장 작은 양수다.
- **부동소수점 비교는 문맥에 따라 규칙이 갈린다.** 정적 타입 `Double`의 `==`는 IEEE 규칙(`NaN != NaN`, `-0.0 == 0.0`)을, `equals`·`compareTo`·컬렉션은 전순서(`NaN == NaN`, `-0.0 < 0.0`)를 쓴다. 완전한 해부는 10장. (M48 참조)
- **`1 < 1L`은 되지만 `1 == 1L`은 컴파일 에러다.** `compareTo`는 혼합 타입 오버로드가 있지만, 동등 연산 `==`는 서로 다른 정적 타입 사이를 거부한다. 값 비교를 원하면 타입을 명시적으로 맞춰야 한다.
