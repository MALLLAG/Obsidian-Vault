앞의 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서는 "코틀린에서는 모든 것이 객체이고, 가장 위에 `Any`가, 가장 아래에 `Nothing`이 있다"는 타입 계층을 살펴보았다. 그때 "원시 타입은 없다, 자세한 내용은 07장과 08장에서 다룬다"고 미뤄 둔 설명이 있었는데, 이 장에서 그 앞 절반을 다룬다.

`Int`, `Long`, `Double` 같은 수 타입이 소스 코드에서는 완전한 클래스처럼 동작하면서도, 기계 수준에서는 어떻게 CPU가 직접 다루는 비트 묶음으로 바뀌는지를 살펴본다.

이 장에서는 수 타입 여섯 가지와 `Number` 슈퍼타입, 리터럴 문법과 타입 추론, 리터럴 상수의 특례, 자바와 결정적으로 다른 "암시적 확대 변환 없음" 규칙, 정수 나눗셈, JVM 백엔드가 수 타입을 원시형으로 컴파일한다는 사실, 그리고 부동소수점(IEEE 754)의 기본과 변환·비교 규칙을 다룬다.

박싱과 언박싱의 세부 동작, 오버플로, 비트 연산(`shl`/`and`/`inv`), 부호 없는 정수(`UInt`), 캐시된 박스와 `===`의 함정은 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]에서 설명한다. `Char`가 수가 아닌 이유는 [[09 - 문자와 문자열 - 유니코드와 템플릿]]에서, `==`와 `===`의 전체 계약과 부동소수점 동등성의 함정은 [[10 - 불리언과 동등성과 동일성]]에서 다룬다.

## 1. 수 타입 전체 구조: 여섯 개의 타입과 하나의 슈퍼타입

### 1.1 여섯 개의 내장 수 타입

코틀린 표준 라이브러리(`kotlin` 패키지)에는 수 타입이 정확히 여섯 개 내장되어 있다. 정수 계열이 네 개, 부동소수점 계열이 두 개이다.

| 타입 | 비트 폭 | 계열 | 범위(닫힌 구간) | 리터럴 접미사 |
|------|--------|------|----------------|--------------|
| `Byte` | 8 | 정수 | $[-2^{7},\ 2^{7}-1]$ = $[-128,\ 127]$ | 없음 |
| `Short` | 16 | 정수 | $[-2^{15},\ 2^{15}-1]$ = $[-32768,\ 32767]$ | 없음 |
| `Int` | 32 | 정수 | $[-2^{31},\ 2^{31}-1]$ | 없음(기본) |
| `Long` | 64 | 정수 | $[-2^{63},\ 2^{63}-1]$ | `L` |
| `Float` | 32 | 부동소수 | IEEE 754 단정밀도 | `f` / `F` |
| `Double` | 64 | 부동소수 | IEEE 754 배정밀도 | 없음(기본) |

각 타입은 자신의 최솟값과 최댓값을 `MIN_VALUE`/`MAX_VALUE` 상수로 제공한다. 그런데 정수와 부동소수점에서 이 상수의 **의미가 다르다**. 8절에서 다시 다루겠지만, 이것이 첫 번째 함정이다.

```kotlin
println(Int.MIN_VALUE)   // => -2147483648  (가장 작은 '음수')
println(Int.MAX_VALUE)   // => 2147483647   (가장 큰 '양수')
println(Long.MAX_VALUE)  // => 9223372036854775807

println(Double.MIN_VALUE) // => 4.9E-324  (가장 작은 '양수'! 음수가 아님)
println(Double.MAX_VALUE) // => 1.7976931348623157E308
```

정수의 `MIN_VALUE`는 표현할 수 있는 **가장 작은 값**(절댓값이 가장 큰 음수)이다. 반면 부동소수점의 `MIN_VALUE`는 표현할 수 있는 **가장 작은 양수**(0에 가장 가까운 양수)이다. 정수에서 익힌 직관을 부동소수점에 그대로 적용하면, "가장 작은 double"을 구하려고 `Double.MIN_VALUE`를 쓰는 실수를 하게 된다. 부동소수점에서 가장 작은 값(가장 작은 음수)은 `-Double.MAX_VALUE`이다.

> [!warning] 흔한 오해
> `Double.MIN_VALUE`를 음의 무한대에 가까운 값으로 생각하기 쉽다. 실제로는 $4.9 \times 10^{-324}$, 즉 0보다 아주 조금 큰 양의 서브노멀 값이다. 이 불일치는 코틀린이 만든 것이 아니라, 자바의 `Double.MIN_VALUE`와 그 바탕인 IEEE 754의 관습을 그대로 물려받은 것이다. 정수와 부동소수점의 같은 이름 상수를 함께 다룰 때는 항상 주의해야 한다.

### 1.2 `Number` 슈퍼타입

여섯 타입은 모두 추상 클래스 `Number`의 하위 타입이다. `Number`는 값을 다른 수 타입으로 변환하는 추상 메서드들을 구현하도록 요구한다.

```text
                     Any
                      │
                   Number  (추상 클래스)
      ┌────┬────┬────┼────┬─────┬──────┐
    Byte Short  Int  Long Float Double
```

```kotlin
abstract class Number {
    abstract fun toDouble(): Double
    abstract fun toFloat(): Float
    abstract fun toLong(): Long
    abstract fun toInt(): Int
    abstract fun toShort(): Short
    abstract fun toByte(): Byte
    // toChar()는 과거에 있었으나 Kotlin 1.5부터 Number에서 deprecated
}
```

`Number`는 **산술 연산자를 정의하지 않는다**. `plus`, `times` 같은 관례 함수([[19 - 연산자 오버로딩과 관례]])는 `Int`, `Double` 같은 구체 타입에만 있다. 따라서 `Number` 타입 변수끼리는 더할 수 없다.

```kotlin
val a: Number = 3
val b: Number = 4
// val c = a + b   // 컴파일 에러: Number에는 plus 연산자가 없음
val c = a.toInt() + b.toInt()  // 구체 타입으로 내려와야 산술 가능
println(c) // => 7
```

이렇게 설계한 데에는 이유가 있다. `Number`는 어떤 수든 담을 수 있는 공통 타입일 뿐이고, 그 안에 담긴 값으로 어떤 산술을 해야 하는지는 정의되어 있지 않다(`Byte`끼리의 `+`와 `Double`끼리의 `+`는 기계 수준에서 완전히 다른 명령이다). 또한 7절에서 보겠지만, 값을 `Number` 타입으로 담으면 JVM 백엔드에서는 반드시 **박싱**이 일어난다. `Number`는 원시형이 될 수 없기 때문이다.

명세 기준으로 한 가지를 덧붙인다. `Char`는 `Number`의 하위 타입이 **아니다**. 문자는 코드 유닛(정수처럼 보이는 값)을 감싸고 있지만, 코틀린은 `Char`를 수가 아닌 별도 타입으로 취급한다. `Char`에는 `Int`를 받아 다시 `Char`를 돌려주는 특수한 `+` 관례만 있을 뿐, `Number` 계약에는 참여하지 않는다. 이렇게 결정한 이유는 09장(문자와 문자열)에서 다룬다.

### 1.3 `Boolean`은 이 장에서 다루지 않는다

혼동을 막기 위해 범위를 하나 더 정해 둔다. `Boolean`은 수가 아니다. C나 자바스크립트처럼 `true`를 1로, `false`를 0으로 암묵적으로 변환하는 일은 코틀린에 없으므로, `if (1)` 같은 코드는 컴파일되지 않는다. 불리언과 동등성·동일성은 10장(불리언과 동등성과 동일성)에서 다룬다. 이 장에서는 정수와 부동소수점, 그리고 둘 사이의 변환만 다룬다.

## 2. 리터럴의 문법과 타입

### 2.1 정수 리터럴의 세 가지 진법

정수 리터럴은 십진, 십육진, 이진의 세 가지 표기를 지원한다. **팔진(octal)은 지원하지 않는다.**

```kotlin
val dec = 42          // 십진
val hex = 0x2A        // 십육진 (0x 또는 0X 접두)
val bin = 0b101010    // 이진 (0b 또는 0B 접두)
// val oct = 0o52     // 컴파일 에러: 팔진 표기 없음
```

팔진 표기를 없앤 것은 의도적인 결정이다. C와 자바에서는 `010`이 십진수 8(팔진 리터럴)을 뜻하기 때문에, 전화번호나 우편번호를 무심코 `010...`으로 쓰면 값이 바뀌는 고전적인 버그가 있었다. 코틀린은 이 함정을 없애려고 **선행 0을 금지**한다.

```kotlin
val zip = 0        // OK: 단일 0
// val zip = 007   // 컴파일 에러: 선행 0을 가진 정수 리터럴 불가
```

> [!info] 역사 메모
> 팔진 리터럴은 1970년대 PDP-11 시절에 워드 단위로 값을 조작할 때 유용했지만, 십진수에 익숙한 현대 개발자에게는 함정일 뿐이다. 스칼라와 코틀린 같은 후발 JVM 언어들이 공통적으로 팔진 표기를 없앤 이유가 여기에 있다. 팔진수가 필요하면 `Integer.parseInt("52", 8)`처럼 진법을 명시해 파싱하라는 것이 코틀린의 입장이다.

### 2.2 자릿수 구분자 `_`

가독성을 위해 리터럴 안에 밑줄을 넣을 수 있다. 밑줄은 보기 좋게 하려는 표시일 뿐이며 값에는 영향을 주지 않는다.

```kotlin
val million    = 1_000_000
val creditCard = 1234_5678_9012_3456L
val bytes      = 0xFF_EC_DE_5E
val bits       = 0b1101_0010_0110_1001
```

밑줄은 숫자와 숫자 사이에만 올 수 있다. 접두사(`0x`) 바로 뒤, 접미사(`L`) 바로 앞, 리터럴의 맨 앞과 맨 끝에는 쓸 수 없다.

```kotlin
// val bad1 = _1000      // 에러: 식별자로 해석됨
// val bad2 = 1000_      // 에러: 끝에 밑줄
// val bad3 = 0x_FF      // 에러: 접두사 직후 밑줄
// val bad4 = 100_L      // 에러: 접미사 직전 밑줄
```

### 2.3 `Long` 접미사는 대문자 `L`만 허용한다

`Long` 리터럴에는 접미사 `L`을 붙인다. 소문자 `l`은 **허용되지 않는다**.

```kotlin
val big = 10L       // Long
// val bad = 10l    // 에러: 소문자 l 금지
```

이유는 단순하지만 실용적이다. 소문자 `l`은 숫자 `1`과 눈으로 거의 구별되지 않아서, `10l`이 `101`처럼 보인다. 코틀린은 이런 혼동을 막으려고 대문자만 허용한다. 자바는 소문자 `l`도 받아들이지만 대부분의 코드 스타일 가이드가 이를 금지하고 있으며, 코틀린은 이 관습을 언어 규칙으로 만들었다.

### 2.4 부동소수점 리터럴과 `Float` 접미사

소수점이나 지수 표기가 들어간 리터럴은 부동소수점 리터럴이다. **접미사가 없으면 `Double`** 이 된다. `Float`이 필요하면 `f` 또는 `F`를 붙인다.

```kotlin
val pi     = 3.14         // Double
val piF    = 3.14f        // Float
val sci    = 1.5e3        // Double, 1500.0
val sciNeg = 2.5E-4       // Double, 0.00025
val expOnly = 1e10        // Double, 소수점 없어도 지수가 있으면 부동소수
```

`Double`에는 자바의 `d` 같은 접미사가 필요 없다(붙일 수도 없다). 소수점이나 지수가 있는 리터럴은 그 자체로 `Double`이다. 반대로 정수처럼 보이는 리터럴은 소수점을 붙이지 않는 한 부동소수점이 되지 않는다. `1`은 `Int`이고, `1.0`은 `Double`이다. 이 구분이 4절과 5절에서 "`val d: Double = 1`이 왜 에러인가"를 이해하는 열쇠가 된다.

### 2.5 리터럴 요약표

| 리터럴 | 추론 타입 | 비고 |
|--------|----------|------|
| `42` | `Int` | Int 범위에 들면 Int |
| `4_000_000_000` | `Long` | Int 범위 초과 → 자동으로 Long |
| `42L` | `Long` | 명시 접미사 |
| `0x1F` | `Int` | 십육진, 값이 Int 범위 |
| `0b1010` | `Int` | 이진 |
| `3.14` | `Double` | 접미사 없는 소수 |
| `3.14f` | `Float` | f/F 접미사 |
| `1e10` | `Double` | 지수 표기 |
| `'A'` | `Char` | 수 아님(9장) |
| `true` | `Boolean` | 수 아님(10장) |

`4_000_000_000`이 자동으로 `Long`이 되는 규칙은 다음 절에서 자세히 살펴본다. 이 규칙은 리터럴이 `Int` 범위에 들어가지 않으면 컴파일러가 알아서 `Long`을 고르는 편의 규칙이다.

## 3. 타입 추론의 기본형: `Int`와 `Double`

### 3.1 기본형이 `Int`와 `Double`인 이유

문맥이 타입을 정해 주지 않으면 정수 리터럴은 `Int`로, 부동소수점 리터럴은 `Double`로 추론된다. 이것을 기본형(default type)이라고 한다.

```kotlin
val a = 100        // Int  (Byte도 Short도 아님)
val b = 3.14       // Double  (Float 아님)
val c = 100L       // Long  (명시했으므로)
val d = 100.0f     // Float (명시했으므로)
```

왜 `Int`와 `Double`일까? `Int`(32비트)는 현대 CPU가 가장 효율적으로 다루는 정수 폭이고, 카운터나 인덱스, 일반적인 산술에는 대부분 충분하다. `Byte`나 `Short`를 기본형으로 삼으면 값이 조금만 커져도 바로 오버플로가 나고, `Long`을 기본형으로 삼으면 메모리와 연산이 낭비된다.

부동소수점에서 `Double`을 기본형으로 고른 이유는 정밀도이다. `Float`(유효숫자 약 7자리)은 웬만한 계산에서도 오차가 눈에 띄게 커지므로, 실수 계산은 `Double`(약 15~17자리)에서 시작하는 것이 안전하다.

### 3.2 리터럴이 `Int` 범위를 넘으면 `Long`이 된다

정수 리터럴이 `Int`로 표현할 수 있는 범위를 넘으면, 접미사 `L`이 없어도 컴파일러가 자동으로 `Long`으로 추론한다.

```kotlin
val small = 2_147_483_647       // Int (Int.MAX_VALUE)
val big   = 2_147_483_648       // Long (Int.MAX_VALUE + 1, 자동 승격)

val x = 9_000_000_000           // Long
// 만약 이 규칙이 없다면 컴파일 에러였을 것
```

이것은 "리터럴은 문맥이 없으면 `Int`로 추론하되, `Int`에 담을 수 없으면 `Long`으로 넓힌다"는 특별 규칙이다. `Int` 값을 가진 변수에는 이런 자동 승격이 전혀 일어나지 않는다는 점(5절)과 대조된다. 리터럴은 컴파일 타임 상수이므로 컴파일러가 그 값을 알고 있고, 그래서 안전하게 타입을 고를 수 있다.

### 3.3 문맥(기대 타입)이 추론 결과를 정한다

기본형은 문맥이 없을 때 적용된다. 기대 타입(expected type)이 주어지면 리터럴은 그 타입에 맞춰진다. 이 내용은 4절의 "리터럴 상수 특례"로 이어진다.

```kotlin
val a = 1              // 문맥 없음 → Int
val b: Long = 1        // 기대 타입 Long → 리터럴이 Long이 됨
val c: Byte = 1        // 기대 타입 Byte → 리터럴이 Byte가 됨

fun feed(amount: Long) { /* ... */ }
feed(1)                // 인자 기대 타입 Long → 리터럴 1이 Long

val list = listOf(1L, 2L, 3L)   // 원소 기대 타입 Long
```

여기서 가장 중요한 점은 이 특례가 **정수 리터럴에만** 적용된다는 것이다. 부동소수점 리터럴에는 적용되지 않는다.

```kotlin
val ok: Long = 1        // OK: 정수 리터럴 특례
// val no: Float = 1.0  // 컴파일 에러: Double 리터럴은 Float로 좁혀지지 않음
val yes: Float = 1.0f   // OK: 애초에 Float 리터럴
// val no2: Double = 1  // 컴파일 에러: 정수 리터럴은 Double로 넓혀지지 않음
val yes2: Double = 1.0  // OK: 부동소수점 리터럴
```

자바 사용자는 특히 `val no2: Double = 1`이 에러라는 점에 놀란다. 자바는 `double d = 1;`을 경고 없이 받아들이기 때문이다(정수에서 부동소수로의 확대 변환). 코틀린은 정수 리터럴을 `Byte`/`Short`/`Long`으로 좁히거나 넓히는 것은 허용하지만, **정수에서 부동소수점으로 넘어가는 것은 허용하지 않는다**. `1`을 `Double`로 쓰려면 `1.0`이라고 써야 한다. 다음 절에서 이 특례가 정확히 어디까지 적용되는지 살펴본다.

## 4. 리터럴 상수 특례: `val b: Byte = 1`이 허용되는 이유

### 4.1 상수 표현식을 컴파일 타임에 좁히기

3.3절에서 본 `val b: Byte = 1`은 조금 이상해 보인다. `Byte`는 `Int`의 하위 타입이 아니고 코틀린은 암시적 변환을 허용하지 않는데(5절), `Int`처럼 보이는 `1`이 어떻게 `Byte`가 될 수 있을까?

답은 `1`이 `Int` 값이 아니라 **정수 리터럴 상수**라는 데 있다. 컴파일러는 컴파일 타임에 이 리터럴의 실제 값을 알고 있다. 기대 타입이 `Byte`이고 값 `1`이 `Byte` 범위 $[-128, 127]$에 들어가면, 컴파일러는 이 리터럴을 그대로 `Byte` 리터럴로 만든다. 런타임에 변환하는 것이 아니라 컴파일 타임에 결정하는 것이다.

```kotlin
val b1: Byte = 1        // OK: 1이 Byte 범위에 있음
val b2: Byte = 127      // OK: 경계값
val b3: Byte = -128     // OK: 경계값
// val b4: Byte = 128   // 컴파일 에러: 128은 Byte 범위 초과
// val b5: Byte = 200   // 컴파일 에러: 범위 초과

val s: Short = 30000    // OK
// val s2: Short = 40000 // 컴파일 에러: Short.MAX(32767) 초과
```

이 규칙의 장점은 `val b4: Byte = 128`이 **컴파일 에러**가 된다는 점이다. 만약 런타임 변환이었다면 `128`은 `Byte`로 좁혀지면서 아무 경고 없이 `-128`로 오버플로했을 것이다. 하지만 컴파일러가 상수 값을 알고 있으므로, 범위를 벗어나면 바로 컴파일이 실패한다. 오류를 컴파일 타임에 잡을 수 있는 것이다.

### 4.2 특례는 상수 표현식에만 적용된다

이 특례는 리터럴 하나에만 적용되는 것이 아니다. 컴파일 타임에 값이 확정되는 **상수 표현식**(constant expression) 전체에 적용된다. 리터럴끼리의 산술이나 `const val` 참조도 여기에 포함된다.

```kotlin
val b: Byte = 1 + 1          // OK: 1+1은 상수 표현식, 값 2가 Byte 범위
val c: Byte = 100 + 27       // OK: 값 127
// val d: Byte = 100 + 28    // 컴파일 에러: 값 128, 범위 초과

const val BASE = 10
val e: Byte = BASE + 5       // OK: const val은 컴파일 상수, 값 15
```

`1 + 1`이 `Byte`가 될 수 있는 이유는 이 덧셈이 런타임에 일어나지 않기 때문이다. 컴파일러가 컴파일 타임에 이 식을 `2`로 계산해 두고(constant folding), 그 상수 `2`를 기대 타입 `Byte`에 맞춘다.

> [!note] 명세 기준
> 상수 표현식이 아니면 이 특례를 적용받지 못한다. 변수를 거치면 값은 이미 `Int` 타입으로 정해져 있고, 컴파일러는 그 안에 든 값을 알지 못한다. 그래서 아래 코드는 실패한다. 이 내용이 5절의 주제로 이어진다.

```kotlin
val i = 1                 // i는 Int
// val b: Byte = i        // 컴파일 에러: i는 Int 값, 상수 아님
val b: Byte = i.toByte()  // 명시 변환 필요
```

`i`에 `1`이 들어 있는 것이 분명해도, `i`는 상수가 아니라 `Int` 타입 변수이다. 컴파일러는 "`i`의 타입은 `Int`이고 기대 타입은 `Byte`이며, 둘 사이에는 암시적 변환이 없다"고만 판단한다. 이런 엄격함이 코틀린 수 체계의 근간이다.

## 5. 암시적 확대 변환이 없다: 자바와의 결정적 차이

### 5.1 코틀린은 넓히지도 좁히지도 않는다

자바에서는 수 타입 사이에 **암시적 확대 변환**(widening)이 자동으로 일어난다. `int`를 `long` 자리에 넣으면 경고 없이 넓혀지고, `int`를 `double` 자리에 넣을 수도 있다. 코틀린은 이런 변환을 **전면 금지**한다. 좁히는 변환(narrowing)이 위험하다는 것은 누구나 알지만, 코틀린은 안전해 보이는 넓히는 변환까지 막는다.

```java
// Java
int i = 10;
long l = i;      // OK: 암시적 확대
double d = i;    // OK: 암시적 확대
```

```kotlin
// Kotlin
val i: Int = 10
// val l: Long = i     // 컴파일 에러: Int는 Long의 하위 타입이 아님
// val d: Double = i   // 컴파일 에러
val l: Long = i.toLong()      // 명시 변환
val d: Double = i.toDouble()  // 명시 변환
```

처음에는 이 결정이 번거롭게 느껴질 수 있다. 값을 잃지도 않는데 왜 `toLong()`을 직접 써야 할까? 하지만 여기에는 세 가지 중요한 이유가 있다.

### 5.2 이유 1: 타입 계층의 정합성

`Int`가 `Long`으로 자동 변환되려면 `Int`가 `Long`의 하위 타입이어야 한다(리스코프 치환 원칙). 그러나 실제로는 그렇지 않다. `Long`은 할 수 있지만 `Int`는 할 수 없는 일이 있고(예: `Long.MAX_VALUE` 담기), `Int`와 `Long`이 서로 다르게 동작하는 일도 있다. 두 타입은 상속 관계가 아니라 둘 다 `Number`의 자식인 형제 관계이다.

암시적 변환은 상속 관계가 있는 것처럼 동작하지만 실제 타입 관계와는 맞지 않는다. 이 불일치는 제네릭과 변성([[33 - 제네릭 1 - 타입 파라미터와 변성]])을 만나면 문제를 일으킨다. 그래서 코틀린은 "하위 타입이면 변환하고, 아니면 명시적으로 변환한다"는 단순하고 견고한 규칙을 택했다.

### 5.3 이유 2: 오버로드 해소를 명확하게

암시적 확대 변환은 함수 오버로드 해소를 매우 복잡하게 만든다. 자바에서 `f(1)`을 호출하면 `f(int)`, `f(long)`, `f(double)`, `f(Integer)`, `f(Object)`가 모두 후보가 되고, 어느 것이 선택될지는 복잡한 우선순위 규칙에 따라 정해진다. 코틀린은 리터럴 특례(4절)를 제외하면 변수의 타입과 정확히 일치하는 오버로드만 후보로 삼는다. 그래서 어느 `f`가 호출될지가 분명하다.

```kotlin
fun describe(x: Int)  = "정수 $x"
fun describe(x: Long) = "긴정수 $x"

val i: Int = 5
println(describe(i))        // => 정수 5   (Int 오버로드, 모호함 없음)
println(describe(i.toLong())) // => 긴정수 5
```

### 5.4 이유 3: 알아차리기 어려운 정밀도 손실 방지

자바가 허용하는 `int → float`, `long → double` 확대 변환은 실제로 값을 손상시킬 수 있다. `float`은 유효숫자가 약 7자리뿐이라 큰 `int`를 담으면 정밀도를 잃고, `long`을 `double`에 넣어도 값이 크면 정밀도가 깨진다. 코틀린은 안전해 보이지만 실제로는 손실이 있는 이런 변환도 직접 쓰게 해서, 개발자가 변환을 **의식하도록** 만든다.

```kotlin
val big: Long = 9_007_199_254_740_993L    // 2^53 + 1
val asDouble: Double = big.toDouble()     // 명시적으로 써야 함
println(asDouble.toLong())                // => 9007199254740992  (1 손실!)
```

`2^53 + 1`은 `Double`이 정확히 표현하지 못하는 첫 번째 정수이다(가수부 52비트의 한계). 자바라면 `double d = big;`에서 아무 표시 없이 이 손실이 일어났겠지만, 코틀린은 `.toDouble()`을 직접 쓰게 해서 "여기서 정밀도가 바뀔 수 있다"는 신호를 코드에 남긴다.

### 5.5 변환 함수 정리

모든 수 타입은 다른 수 타입으로 변환하는 `toXxx()` 함수를 제공한다.

| 함수 | 하는 일 | 손실 |
|------|---------|------|
| `toByte()` | 하위 8비트만 취함 | 좁힘 시 상위 비트 버림 |
| `toShort()` | 하위 16비트만 취함 | 좁힘 시 손실 |
| `toInt()` | 하위 32비트 / 부동소수는 0으로 향해 절삭 | 좁힘·절삭 |
| `toLong()` | 부동소수는 0으로 향해 절삭 | 부동소수→정수 시 절삭 |
| `toFloat()` | 배정밀도→단정밀도 반올림 | 정밀도 손실 |
| `toDouble()` | 단정밀도→배정밀도(무손실) | 정수→double은 큰 값에서 손실 |

```kotlin
println(300.toByte())     // => 44    (300 = 256 + 44, 상위 비트 버림)
println(3.99.toInt())     // => 3     (0으로 향해 절삭, 반올림 아님)
println((-3.99).toInt())  // => -3    (0으로 향해 절삭)
println(1_000_000.toShort()) // => 16960  (하위 16비트)
```

`toInt()`는 반올림이 아니라 **0을 향한 절삭**(truncation toward zero)이라는 점을 기억해야 한다. `3.99.toInt()`는 `4`가 아니라 `3`이고, `(-3.99).toInt()`는 `-4`가 아니라 `-3`이다. 반올림하려면 `Math.round`나 `roundToInt()` 확장 함수를 써야 한다.

```kotlin
println(3.99.roundToInt())    // => 4  (반올림)
println((-3.5).roundToInt())  // => -3 (half-up: -3.5는 -3으로)
```

이런 좁히는 변환이 비트 수준에서 데이터를 어떻게 자르는지, 그리고 부동소수 특수값이 정수로 어떻게 변환되는지는 9절과 08장(수 2)에서 더 자세히 다룬다.

## 6. 정수 나눗셈과 산술의 함정

### 6.1 정수 나눗셈은 소수 부분을 버린다

`/` 연산자는 피연산자 타입에 따라 완전히 다르게 동작한다. 둘 다 정수이면 **정수 나눗셈**(몫만 남기고 나머지는 버림)이고, 하나라도 부동소수점이면 실수 나눗셈이다.

```kotlin
println(7 / 2)       // => 3    (정수 나눗셈, 0.5 버려짐)
println(7 / 2.0)     // => 3.5  (한쪽이 Double → 실수 나눗셈)
println(7.0 / 2)     // => 3.5
println(7 / 2.toDouble()) // => 3.5
```

초심자가 가장 자주 빠지는 함정이 이것이다. `val average = sum / count`에서 `sum`과 `count`가 둘 다 `Int`이면 평균이 정수로 잘려서 나온다. `1 / 2`는 `0.5`가 아니라 `0`이다.

```kotlin
val total = 5
val n = 2
val avg = total / n           // Int 나눗셈 → 2 (2.5가 아님!)
val avgReal = total.toDouble() / n  // => 2.5
```

### 6.2 절삭 방향과 나머지의 부호

정수 나눗셈은 **0을 향해 절삭한다**(truncated division). 음수가 섞이면 이 방향이 중요해진다.

```kotlin
println(7 / 2)     // => 3
println(-7 / 2)    // => -3   (내림 -4가 아니라 0 방향 절삭)
println(7 / -2)    // => -3
println(-7 / -2)   // => 3
```

나머지 연산자 `%`(관례 함수 `rem`)는 이 절삭 방식과 짝을 이룬다. 결과의 부호는 **피제수(왼쪽 피연산자)의 부호**를 따른다.

```kotlin
println(7 % 3)     // => 1
println(-7 % 3)    // => -1   (피제수 -7의 부호)
println(7 % -3)    // => 1    (제수의 부호는 무관)
println(-7 % -3)   // => -1
```

몫을 $q = a \mathbin{/} b$, 나머지를 $r = a \mathbin{\%} b$라고 하면, 다음 항등식이 항상 성립한다.

$$
a = b \times q + r, \qquad q = \operatorname{trunc}\!\left(\frac{a}{b}\right)
$$

즉 나머지는 항상 몫을 절삭하는 방식에 따라 결정된다.

### 6.3 `rem`과 `mod`는 다르다

음수에서도 수학적인 나머지(항상 0 이상)를 얻으려면 `%`가 아니라 `mod` 함수를 써야 한다. `mod`는 **내림 나눗셈**(floored division)을 기반으로 하므로, 결과의 부호가 **제수**(divisor)를 따른다.

```kotlin
println(-7 % 3)      // => -1   (rem: 피제수 부호)
println((-7).mod(3)) // => 2    (mod: 제수 부호, 항상 0..제수-1)

println(-1 % 12)      // => -1
println((-1).mod(12)) // => 11  (시계·원형 인덱스에 유용)
```

`mod`는 특히 원형 인덱싱에서 유용하다. 시계에서 "1시간 전"을 `(hour - 1) % 12`로 계산하면 0시일 때 `-1`이 나오지만, `.mod(12)`를 쓰면 정확히 `11`이 나온다.

> [!note] 명세 기준
> `mod`는 Kotlin 1.5에서 정식으로 추가되었다. `%`(=`rem`)와 `mod`는 나누어떨어질 때는 결과가 같지만, 나머지가 있고 두 피연산자의 부호가 다를 때는 달라진다. 항등식으로 표현하면, `a.mod(b)`는 항상 `b`와 부호가 같거나 0이고, `0 <= a.mod(b).absoluteValue < b.absoluteValue`를 만족한다.

### 6.4 오버플로는 예외 없이 값을 감싼다

정수 산술 결과가 타입의 범위를 넘으면, 코틀린은 예외를 던지지 않고 **2의 보수 방식으로 값을 감싼다**(wrap around). 하드웨어 산술 동작을 그대로 드러내는 것이다.

```kotlin
println(Int.MAX_VALUE + 1)   // => -2147483648  (Int.MIN_VALUE로 감김)
println(Int.MIN_VALUE - 1)   // => 2147483647
```

값이 감기는 동작을 비트 수준에서 분석하는 내용과 예외를 던지는 `Math.addExact` 같은 대안은 08장(수 2)에서 다룬다. 여기서는 이 동작이 실무에서 산술의 함정으로 어떻게 나타나는지만 살펴본다.

```kotlin
// "하루는 몇 밀리초?" — 흔한 오버플로 버그
val oneDayMs   = 24 * 60 * 60 * 1000            // 86_400_000, Int로 OK
val days25Ms   = 25 * 24 * 60 * 60 * 1000       // 오버플로! 2_160_000_000 > Int.MAX
println(days25Ms)                                // => -2134967296 (음수!)

val fixed: Long = 25L * 24 * 60 * 60 * 1000     // => 2160000000, Long 산술
println(fixed)
```

### 6.5 산술 결과는 승격되지만 변수는 승격되지 않는다

여기에는 5절과 이어지는 미묘한 구분이 있다. 5절에서 암시적 확대 변환은 없다고 했는데, 그렇다면 `1 + 1L`은 왜 컴파일될까? `1`은 `Int`이고 `1L`은 `Long`인데 말이다.

답은 이것이 **암시적 변환이 아니라 연산자 오버로드**라는 데 있다. `Int`에는 `Long`을 받는 `plus` 오버로드 `Int.plus(Long): Long`이 정의되어 있다. 그래서 `1 + 1L`은 `1.plus(1L)`로 해석되고, 이 오버로드가 `Long` 결과를 돌려준다. `Int` 값이 `Long`으로 변환된 것이 아니라, "Int와 Long을 더하면 Long"이라는 연산이 정의되어 있을 뿐이다.

```kotlin
val x = 1 + 1L         // Long (Int.plus(Long) 오버로드)
val y = 1 + 1.0        // Double (Int.plus(Double) 오버로드)
val z = 1L + 1.0f      // Float (Long.plus(Float) 오버로드)
```

각 수 타입은 여섯 가지 수 타입 모두에 대해 `plus`/`minus`/`times`/`div`/`rem` 오버로드를 가지고 있다. 그래서 혼합 산술은 넓은 쪽 타입으로 승격되는 것처럼 보인다. 하지만 이것은 변수 대입에서의 암시적 변환과는 완전히 다른 메커니즘이다.

### 6.6 `Byte + Byte`는 `Int`이다

이 오버로드 규칙에서 가장 직관에 어긋나는 결과가 있다. `Byte`끼리, 또는 `Short`끼리 더하면 결과가 **`Int`** 가 된다.

```kotlin
val b1: Byte = 10
val b2: Byte = 20
val sum = b1 + b2        // sum의 타입은 Int! (Byte 아님)
println(sum)             // => 30

// val bad: Byte = b1 + b2   // 컴파일 에러: Int를 Byte에 대입 불가
val ok: Byte = (b1 + b2).toByte()  // 명시 변환 필요
```

`Byte`가 `Byte`를 받는 `plus`의 반환 타입을 `Byte`가 아니라 `Int`로 정의하기 때문이다(`Byte.plus(Byte): Int`). `Short`도 마찬가지이다. `Byte`와 `Short`의 같은 타입끼리 산술 오버로드는 처음부터 `Int`를 반환하는 형태로만 존재한다. 이는 하드웨어가 8비트·16비트 산술을 32비트로 올려서 계산하는 관습(자바의 정수 승격)과 일치한다.

> [!warning] 흔한 오해
> `Byte + Byte`의 결과가 `Byte`일 것이라고 기대하기 쉽지만, 실제로는 `Int`이다. `Byte`와 `Short`는 메모리를 아끼는 저장 용도로는 쓰이지만, 산술에 들어가면 바로 `Int`로 올라간다. 그래서 코틀린 코드에서 `Byte`나 `Short`로 산술을 반복해도 얻는 것이 거의 없고, 매번 `.toByte()`를 호출해야 해서 오히려 번거롭다. 카운터, 인덱스, 산술에는 그냥 `Int`를 쓰는 것이 관례이다.

### 6.7 0으로 나누기: 정수와 부동소수의 차이

정수를 0으로 나누면 `ArithmeticException`이 발생한다. 부동소수점을 0으로 나누면 예외 없이 `Infinity` 또는 `NaN`이 나온다.

```kotlin
// println(1 / 0)      // 런타임 예외: java.lang.ArithmeticException: / by zero (JVM 백엔드)
println(1.0 / 0.0)    // => Infinity
println(-1.0 / 0.0)   // => -Infinity
println(0.0 / 0.0)    // => NaN
// println(1 % 0)     // 이것도 ArithmeticException: / by zero
```

이런 비대칭이 생기는 이유는 IEEE 754가 부동소수점에 `Infinity`와 `NaN`이라는 특수값을 정의해 두었기 때문이다. 정수에는 이런 특수값이 없으므로, 0으로 나눈 결과를 표현할 수 없어서 예외로 처리한다. 이 특수값들이 무엇인지는 8절에서 살펴본다.

> [!note] 명세 기준
> "정수를 0으로 나누면 `ArithmeticException`이 발생한다"는 설명은 JVM 백엔드에 정확히 들어맞는다. 다른 백엔드(Native/JS/Wasm)에서도 이 동작이 완전히 같다고 명세가 모든 세부까지 보장하지는 않는다. 따라서 플랫폼과 관계없이 안전하려면 나누기 전에 제수를 검사하는 것이 원칙이다.

## 7. 원시 타입으로 컴파일된다: 흔한 오해 바로잡기

### 7.1 오해: "코틀린에는 원시 타입이 없다"

이제 이 장의 핵심 오해를 직접 다룬다. 흔히 "코틀린에는 원시 타입(primitive)이 없고, 모든 것이 객체다"라고 말한다. 이 문장은 **절반만 맞고, 나머지 절반은 오해를 부른다.** 정확히 나누어 보자.

- **맞는 부분**: 코틀린 **소스 언어**에는 `int`/`Integer` 같은 원시 타입과 래퍼 타입의 구분이 없다. `Int`는 하나의 타입이고, 메서드를 가지며, `Any`의 하위 타입이고, 타입 시스템에서 완전한 클래스처럼 동작한다. 소스 코드에는 원시 타입이라는 별도 범주가 없다.
- **오해를 부르는 부분**: "그러니 코틀린 `Int`는 자바 `Integer`처럼 힙에 박싱된 객체다"라고 추론하는 것이다. **이 추론은 틀렸다.** JVM 백엔드는 가능한 모든 곳에서 `Int`를 원시 `int`로 컴파일한다.

정리하면, **원시 타입은 소스 언어의 개념 수준에서만 사라졌고, 기계 수준에서는 그대로 남아 있다.** 코틀린은 "모든 것이 객체"라는 *일관된 소스 모델*과 "가능하면 원시형"이라는 *효율적인 기계 모델*을 컴파일러가 연결해 주므로, 둘 다 얻을 수 있다.

### 7.2 JVM 백엔드에서 실제로 일어나는 일

같은 코틀린 소스도 문맥에 따라 원시형 `int`로 컴파일되기도 하고, 박싱된 `Integer`로 컴파일되기도 한다.

```kotlin
val a: Int = 42          // JVM: 원시 int
val b: Int? = 42         // JVM: 박싱된 java.lang.Integer (null 표현 필요)
val list = listOf(1, 2)  // JVM: List<Integer> — 제네릭은 참조 타입만 가능 → 박싱
fun sq(x: Int) = x * x   // JVM: (I)I — 원시 int 파라미터·반환
```

이것을 의사 바이트코드로 나타내 보면 차이가 분명하게 드러난다.

```text
소스:  fun sq(x: Int): Int = x * x
JVM:   public static final int sq(int x) {   // int, 박싱 없음
           return x * x;                       // imul 명령 하나
       }

소스:  fun sqBox(x: Int?): Int? = ...
JVM:   public static final Integer sqBox(Integer x) {  // Integer, 박싱
           ...                                          // Integer.valueOf 등
       }
```

원시형으로 남는 경우와 박싱되는 경우를 규칙으로 정리하면 다음과 같다(JVM 백엔드 기준).

| 상황 | JVM 표현 | 이유 |
|------|---------|------|
| `val x: Int` (널 불가) | 원시 `int` | null을 표현할 필요 없음 |
| `val x: Int?` (널 가능) | 박싱 `Integer` | null은 원시형으로 표현 불가 |
| 제네릭 타입 인자 `List<Int>` | 박싱 `Integer` | JVM 제네릭은 참조 타입만 받음(소거) |
| `Number`/`Any`로 상향 | 박싱 | 슈퍼타입은 참조 타입 |
| 함수 파라미터·반환(널 불가) | 원시 `int` | 박싱 불필요 |
| 컬렉션 원소 | 박싱 | 위 제네릭 사유 |

박싱과 언박싱, 그리고 박싱이 `===`나 캐시된 박스와 만나 생기는 함정은 08장(수 2)과 10장(불리언과 동등성과 동일성)에서 자세히 다룬다. 이 장에서는 "널 불가 `Int`는 원시형이고, 널 가능·제네릭·슈퍼타입 위치에서는 박싱된다"는 큰 규칙만 정리해 둔다.

### 7.3 다른 백엔드에서는 "원시"의 의미가 다르다

이 문제를 다룰 때 JVM만 보아서는 안 된다. 코틀린은 여러 플랫폼을 대상으로 하는 언어([[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]])이고, "원시형으로 컴파일된다"는 설명은 **JVM 백엔드에만 해당**한다.

- **Kotlin/Native**(LLVM): `Int`는 네이티브 기계 정수(LLVM `i32`)로 컴파일되고, 힙 할당이 없는 값으로 다뤄진다.
- **Kotlin/JS**: JavaScript에는 정수 타입이 없다(모든 수가 배정밀도 부동소수 `number`이다). `Int`와 `Double`은 JS `number`로 표현되고, `Int` 산술에는 결과를 32비트로 절삭하는 코드가 삽입된다. `Long`은 JS `number`에 담을 수 없으므로(53비트 정수 한계), **별도의 에뮬레이션 클래스**로 컴파일된다(구현 세부는 버전과 백엔드에 따라 다르다).
- **Kotlin/Wasm**: WebAssembly는 `i32`/`i64`/`f32`/`f64`를 기본으로 지원하므로, `Int`는 `i32`, `Long`은 `i64`, `Double`은 `f64`로 자연스럽게 대응된다.

```text
             Int                Long              Double
 JVM     int / Integer      long / Long       double / Double
 Native  LLVM i32           LLVM i64          LLVM double
 JS      number(32비트절삭)  에뮬레이션 클래스  number
 Wasm    i32                i64               f64
```

이 표에서 알 수 있듯이, "코틀린 `Int`는 무엇으로 컴파일되는가"라는 질문에는 백엔드와 무관한 하나의 답이 없다. 소스 수준에서는 언제나 같은 `Int`이지만, 그 아래의 표현은 타깃마다 다르다. 따라서 정확하게 말하면 다음과 같다.

> [!note] 명세 기준
> 코틀린 소스 언어에는 원시 타입이라는 범주가 없다(모든 수 타입은 클래스처럼 동작한다). 그러나 이것이 "런타임에도 항상 박싱된다"는 뜻은 **아니다**. 컴파일러는 각 백엔드에서 가장 효율적인 기계 표현으로 변환한다. JVM 백엔드에서는 널이 불가능한 곳에서 `int`·`long`·`double` 같은 원시형으로 컴파일하고, 널 가능·제네릭·슈퍼타입 위치에서만 래퍼 타입으로 박싱한다.

### 7.4 설계 이유: 통일성과 효율을 함께 얻기

자바는 `int`(원시)와 `Integer`(객체)를 서로 다른 두 타입으로 노출하므로, 개발자는 항상 "여기서는 어느 쪽을 써야 하는가"를 신경 써야 한다. `List<int>`는 쓸 수 없고 `List<Integer>`만 쓸 수 있으며, 오토박싱이 언제 일어나는지도 추적해야 한다. 코틀린은 소스에서 이 구분을 없애 개발자에게 **하나의 통일된 타입 모델**을 제공한다. `Int` 하나만 알면 된다.

동시에 컴파일러가 내부에서 원시형 최적화를 해 주므로, 이 통일성 때문에 성능을 희생하지 않는다. 널 불가 `Int`로 작성한 루프는 자바의 `int` 루프와 같은 바이트코드로 컴파일된다. 개발자는 "모든 것이 객체"라는 깔끔한 모델로 코드를 작성하고, 기계에서는 원시형으로 빠르게 실행된다. 이렇게 두 수준을 분리한 것이 이 오해를 푸는 핵심이자, 코틀린 수 설계의 장점이다.

> [!caution] 성능 주의
> 이 설계에도 빈틈이 있다. 코드가 `Int?`, `List<Int>`, `Number`, 제네릭 `T`를 거치면 박싱이 일어난다. 자주 실행되는 루프(hot loop)에서 무심코 `Int?`나 박싱된 컬렉션을 순회하면 원시형 최적화가 사라지고 힙 할당이 크게 늘어난다. "코틀린 수는 항상 빠르다"가 아니라 "널 불가·비제네릭 경로에서만 빠르다"고 이해해야 정확하다. 자세한 내용은 08장에서 다룬다.

## 8. 부동소수점의 기초: IEEE 754

### 8.1 `Float`과 `Double`의 비트 배치

`Float`과 `Double`은 정수처럼 값을 있는 그대로 비트에 담지 않는다. 부호(sign), 지수(exponent), 가수(mantissa/significand)의 세 부분으로 나누어, 과학적 표기법을 이진수로 옮긴 방식으로 실수를 근사한다. 이것이 IEEE 754 표준이다.

```text
Float (32비트):
  ┌─┬────────┬───────────────────────┐
  │S│  E(8)  │        M(23)           │
  └─┴────────┴───────────────────────┘
   부호  지수         가수

Double (64비트):
  ┌─┬───────────┬──────────────────────────────────────────┐
  │S│   E(11)   │                 M(52)                     │
  └─┴───────────┴──────────────────────────────────────────┘
```

값은 대략 다음 공식으로 복원된다(정규 수 기준). $s$는 부호 비트, $e$는 지수, $m$은 가수 비트열, $\text{bias}$는 지수 편향(Double은 1023, Float은 127)이다.

$$
\text{value} = (-1)^{s} \times 1.m_{2} \times 2^{\,e - \text{bias}}
$$

여기서 핵심은 가수 앞의 `1.`(암시적 선행 1비트)과, 값이 `2`의 거듭제곱으로 표현된다는 점이다. 실수를 **2의 거듭제곱의 합**으로 나타내기 때문에, 십진 소수 가운데 상당수는 정확히 표현되지 않는다.

### 8.2 `0.1 + 0.2`가 `0.3`이 아닌 이유

이것은 코틀린의 버그가 아니라 이진 부동소수점의 근본적인 성질이다. 자바, C, 파이썬, 자바스크립트 모두 언어와 관계없이 같은 결과를 낸다.

```kotlin
println(0.1 + 0.2)          // => 0.30000000000000004
println(0.1 + 0.2 == 0.3)   // => false
```

`0.1`은 이진수로 유한하게 표현되지 않는다. 십진수 `1/10`을 이진수로 쓰면 `0.0001100110011...`처럼 끝없이 순환한다. `1/3`을 십진 소수로 정확히 쓸 수 없는 것과 같은 현상이다. `Double`은 이 무한 순환을 52비트에서 잘라 저장하므로, `0.1`은 정확히 `0.1`이 아니라 그에 아주 가까운 값이 된다. `0.1`과 `0.2`에 있던 이런 미세한 오차가 더해지면서, 결과가 `0.3`과 다른 값이 된다.

$$
0.1_{10} = 0.0\overline{0011}_2 \quad(\text{이진 무한 순환})
$$

그래서 부동소수점 값을 `==`로 비교하는 것은 거의 언제나 잘못이다. 두 값의 차이가 오차 허용 범위(epsilon) 안에 드는지를 확인해야 한다.

```kotlin
val eps = 1e-9
println(kotlin.math.abs((0.1 + 0.2) - 0.3) < eps)  // => true
```

돈 계산에 `Double`을 쓰면 안 되는 이유도 여기에 있다. `0.1`(10센트)조차 정확히 표현하지 못하는 타입으로 회계 처리를 하면 반올림 오차가 쌓인다. 금액은 정수 단위(예: 최소 화폐 단위)나 `BigDecimal`로 다뤄야 한다.

> [!info] 역사 메모
> IEEE 754는 1985년에 표준화되었고, 오늘날 거의 모든 CPU의 부동소수점 장치가 이 표준을 구현한다. "0.1 + 0.2 문제"는 특정 언어의 결함이 아니라, 유한한 비트로 실수를 근사할 때 피할 수 없는 대가이다. 정확한 이진 표현, 반올림 규칙, 서브노멀 수의 세부 내용은 컴퓨터 구조나 데이터 표현을 다루는 자료의 IEEE 754 장을 참고하면 된다(이 시리즈의 범위 밖이다).

### 8.3 특수값: `Infinity`, `-Infinity`, `NaN`

IEEE 754는 정상적인 수로 표현할 수 없는 결과를 위해 세 가지 특수값을 예약해 두었다. 이 값들은 지수 비트가 모두 1인 패턴으로 인코딩된다.

```kotlin
println(Double.POSITIVE_INFINITY)  // => Infinity
println(Double.NEGATIVE_INFINITY)  // => -Infinity
println(Double.NaN)                // => NaN

println(1.0 / 0.0)          // => Infinity
println(-1.0 / 0.0)         // => -Infinity
println(0.0 / 0.0)          // => NaN
println(Double.MAX_VALUE * 2) // => Infinity (오버플로는 예외 아님)
println(kotlin.math.sqrt(-1.0)) // => NaN
```

`NaN`(Not a Number)은 정의되지 않은 실수 연산의 결과이다. `0.0/0.0`, 음수의 제곱근, `Infinity - Infinity` 같은 연산에서 나온다. `NaN`의 가장 악명 높은 성질은 **자기 자신과도 같지 않다**는 것이다.

```kotlin
val nan = Double.NaN
println(nan == nan)          // => false  (IEEE 754 규칙, 정적 타입 Double)
println(nan != nan)          // => true
println(nan.isNaN())         // => true   (NaN 검사의 올바른 방법)
```

`NaN == NaN`이 `false`인 것은 IEEE 754가 그렇게 정했기 때문이다. 따라서 값이 `NaN`인지 확인하려면 `==`가 아니라 `isNaN()`을 써야 한다. "`x != x`가 참이면 `x`는 `NaN`이다"라는 관용구도 이 성질에서 나왔다.

### 8.4 `-0.0`과 정적 타입의 함정: 10장 미리 보기

부동소수점에는 `0.0`과 `-0.0`이 따로 있다. 두 값은 IEEE 비교(`==`)에서는 같지만, 비트로는 다르다.

```kotlin
println(0.0 == -0.0)                  // => true  (IEEE 비교)
println(0.0.toRawBits())              // => 0
println((-0.0).toRawBits())           // => -9223372036854775808 (부호 비트만 1)
```

여기서 코틀린의 미묘하지만 중요한 규칙이 등장한다. **피연산자의 정적 타입이 `Double`/`Float`이면 IEEE 754 비교**를 사용한다. 하지만 값이 **박싱되거나 `Comparable`·컬렉션·`equals`를 통해 다뤄지면 전순서(total order)** 를 사용해서, `NaN == NaN`을 참으로, `-0.0 < 0.0`을 참으로 취급한다.

```kotlin
println(Double.NaN == Double.NaN)                 // => false (정적 Double, IEEE)
println(Double.NaN.equals(Double.NaN))            // => true  (전순서)
println(listOf(Double.NaN).contains(Double.NaN))  // => true  (컬렉션은 equals → 전순서)

println(0.0 == -0.0)                    // => true  (IEEE)
println(0.0.compareTo(-0.0))            // => 1     (전순서: 0.0 > -0.0)
println(0.0.equals(-0.0))               // => false (전순서: 다른 값)
```

`==` 연산자와 `equals`/`compareTo`의 규칙이 왜 둘로 나뉘는지, 그리고 이 차이가 `HashSet`이나 정렬에서 어떤 예상 밖의 결과를 만드는지는 10장(불리언과 동등성과 동일성)에서 자세히 분석한다. 이 장에서는 부동소수점 비교 규칙이 문맥에 따라 달라진다는 사실만 기억해 두자. 부동소수점을 다룰 때는 `==`의 결과와 컬렉션·정렬의 결과가 다를 수 있다는 점을 항상 염두에 두어야 한다.

### 8.5 `Float`의 정밀도 한계

`Float`(32비트)은 가수부가 23비트뿐이라 유효숫자가 약 7자리에 그친다. `Double`은 가수부가 52비트로 약 15~17자리이다. 그래서 `Float`은 저장 공간이나 GPU 인터페이스가 중요한 특수한 상황이 아니면 잘 쓰지 않는다.

```kotlin
val f: Float = 0.1f + 0.2f
println(f)                    // => 0.3  (Float 정밀도에서는 오차가 반올림에 묻힘)
println((0.1f + 0.2f) == 0.3f) // => true (우연히 맞지만 신뢰하지 말 것)

println(16_777_217.toFloat())  // => 1.6777216E7 (2^24 + 1, Float가 표현 못 함 → 1 손실)
```

`16_777_217`(=$2^{24}+1$)은 `Float`이 정확히 표현하지 못하는 첫 번째 정수이다. 가수부 23비트의 한계 때문에 여기서 정밀도가 끊긴다. `Double`은 $2^{53}$까지의 정수를 정확히 표현한다(5.4절에서 본 `2^53 + 1`의 손실과 같은 원리이고, 비트 폭만 다르다). 부동소수점은 수가 클수록 표현할 수 있는 값 사이의 간격이 넓어지는 "가변 정밀도" 방식이라는 점을 잊지 말아야 한다.

## 9. 비교와 변환 정리

### 9.1 비교 연산자는 `compareTo`로 변환된다

`<`, `>`, `<=`, `>=`는 관례 함수 `compareTo`(19장 연산자 오버로딩과 관례)로 변환된다. 각 수 타입은 다른 모든 수 타입에 대한 `compareTo` 오버로드를 가지고 있으므로, 타입이 서로 다른 값도 값을 기준으로 비교할 수 있다.

```kotlin
println(1 < 2L)        // => true  (Int.compareTo(Long))
println(3.14 > 3)      // => true  (Double.compareTo(Int))
println(1L <= 1.0)     // => true
```

### 9.2 그런데 `1 == 1L`은 왜 에러인가

비교 연산자는 타입이 섞인 피연산자를 받지만, 동등 연산자 `==`는 그렇지 않다. `1 == 1L`은 **컴파일 에러**이다.

```kotlin
println(1 < 1L)        // => true   (compareTo 오버로드 존재)
// println(1 == 1L)    // 컴파일 에러: Int와 Long의 == 불가
println(1 == 1)        // => true
println(1L == 1L)      // => true
println(1.toLong() == 1L) // => true (같은 타입으로 맞춰서)
```

이런 비대칭은 두 연산의 성질이 다르기 때문에 생긴다. `<`는 순서를 다루는 `Comparable` 계약이므로, "이 값이 저 값보다 큰가"라는 질문은 타입이 달라도 의미가 있다. 반면 `==`는 **동등성**(equality) 계약이므로, 코틀린은 정적 타입이 서로 다른 값 사이의 `==`를 원칙적으로 막는다.

`Int` `1`과 `Long` `1`은 같은 값처럼 보이지만 타입이 다르고, 코틀린은 타입이 맞지 않는 동등 비교를 컴파일 타임에 거부해 실수를 막는다. 값을 비교하려면 한쪽을 명시적으로 변환해 타입을 맞춰야 한다. `==`의 전체 계약은 10장(불리언과 동등성과 동일성)에서 다룬다.

### 9.3 변환은 항상 명시적이고, 방향이 있다

5절에서 본 `toXxx()` 변환들을 방향별로 정리해 보자. 손실이 없는 방향(넓히기)과 손실이 생길 수 있는 방향(좁히기)이 있다.

```text
무손실(대체로):  Byte → Short → Int → Long
                          Int → Double,  Long → Double(단, 2^53 넘으면 손실)
                        Float → Double
손실 가능(좁히기): 반대 방향 전부
                  Double → Int/Long: 0으로 절삭
                  Double → Float: 반올림, Infinity/큰값 손실
                  Int → Byte: 하위 8비트만
```

부동소수점을 정수로 변환할 때 특수값이 어떻게 처리되는지는 반드시 알아 두어야 할 함정이다.

```kotlin
println(Double.NaN.toInt())               // => 0
println(Double.POSITIVE_INFINITY.toInt()) // => 2147483647 (Int.MAX_VALUE)
println(Double.NEGATIVE_INFINITY.toInt()) // => -2147483648 (Int.MIN_VALUE)
println(1e20.toInt())                     // => 2147483647 (Int 범위 넘으면 saturate)
println(1e20.toLong())                    // => 9223372036854775807 (Long.MAX)
```

`NaN.toInt()`가 예외를 던지지 않고 `0`을 돌려주고, `Infinity.toInt()`가 `Int.MAX_VALUE`를 돌려주는 것은 JVM `d2i` 명령의 동작 방식(포화 변환)을 그대로 따르기 때문이다. 이 점을 모르면 `NaN`이 섞인 데이터를 정수로 변환할 때 아무 경고 없이 `0`이 끼어드는 버그를 만나게 된다.

> [!note] 명세 기준
> 부동소수를 정수로 변환할 때 "0을 향해 절삭하고, NaN은 0이 되며, 무한대와 범위를 넘는 값은 포화(saturate)된다"는 설명은 JVM 백엔드의 동작이다. 이 세부 동작이 모든 백엔드에서 비트 단위까지 같다고 명세가 보장한다고 단정해서는 안 된다. 플랫폼 독립적인 코드에서는 변환하기 전에 `isNaN()`, `isInfinite()`, 범위를 검사하는 편이 안전하다.

### 9.4 유용한 표준 라이브러리 도구

수 타입에는 산술 연산 외에도 여러 확장 함수와 프로퍼티가 있다. 자주 쓰는 것 몇 가지를 정리한다.

```kotlin
println(5.coerceIn(0, 10))       // => 5   (범위로 클램프)
println(15.coerceIn(0, 10))      // => 10
println((-5).coerceAtLeast(0))   // => 0

println((-7).absoluteValue)      // => 7   (kotlin.math)
println(3.7.roundToInt())        // => 4
println(maxOf(3, 7, 2))          // => 7
println(10.0.pow(3))             // => 1000.0 (kotlin.math)

println(255.toString(16))        // => "ff"  (16진 문자열)
println("ff".toInt(16))          // => 255   (16진 파싱)
println("2147483648".toIntOrNull()) // => null (Int 범위 초과, 예외 대신 null)
```

특히 `toIntOrNull()`이 예외 대신 `null`을 돌려준다는 점이 유용하다. 사용자 입력을 파싱할 때 `toInt()`는 형식이 틀리거나 범위를 넘으면 `NumberFormatException`을 던지지만, `toIntOrNull()`은 `null`을 돌려준다. 그래서 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 다룬 안전 호출이나 엘비스 연산자와 자연스럽게 함께 쓸 수 있다.

```kotlin
fun parseAge(input: String): Int =
    input.toIntOrNull()?.coerceIn(0, 150) ?: 0   // 파싱 실패 시 0
```
