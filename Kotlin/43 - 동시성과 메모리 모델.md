앞의 [[42 - suspend와 코루틴 - 언어 수준의 중단]]에서는 `suspend`가 *새 스레드를 만들지 않으며*, 스레드를 몇 개 어떻게 쓸지는 디스패처가 결정한다는 점을 확인했다. 코루틴은 "언제 멈추고 언제 재개하는가"를 언어 수준에서 다루는 도구이지, "두 실행 흐름이 같은 메모리를 동시에 건드리면 무슨 일이 일어나는가"를 다루는 도구는 아니다.

이 장에서는 그 뒤에 남은 문제인 **공유 가변 상태(shared mutable state)** 와 **메모리 모델(memory model)** 을 다룬다. 코루틴을 쓰든 생(raw) 스레드를 쓰든, 두 흐름이 하나의 변수를 동시에 건드리는 순간부터 이 장의 규칙이 적용된다.

구체적으로는 경쟁 상태(race condition), 가시성(visibility), 재배열(reordering)이라는 세 가지 위험과, Kotlin이 이 문제를 JVM 백엔드에서는 자바 메모리 모델(JMM)에, Kotlin/Native에서는 자체 메모리 관리자에 맡기는 방식, 그리고 언어와 표준 라이브러리가 제공하는 최소한의 도구(`@Volatile`, `@Synchronized`, `kotlin.concurrent.atomics`, 불변성)를 살펴본다.

`CoroutineScope`, 구조적 동시성, `Mutex`, `Flow`를 이용한 상태 격리 같은 실전 설계는 Kotlin Coroutines 시리즈의 [[06 - CoroutineScope와 구조적 동시성]]과 [[18 - 공유 상태와 동기화 - Mutex Semaphore 격리]]에서 다루고, 여기서는 그런 도구가 *왜 필요한지*를 설명하는 하부 원리까지만 다룬다.

`val`이 재대입만 막을 뿐 불변을 보장하지 않는다는 사실([[11 - 변수와 초기화 - val과 const와 lateinit]])이 스레드 안전성에서 왜 중요한 함정인지도 함께 살펴본다.

## 1. 동시성은 언어 기능이 아니라 플랫폼 계약이다

### 1.1 Kotlin 언어 명세에는 "스레드"가 없다

먼저 의외일 수 있는 사실부터 짚자. **Kotlin 언어 명세에는 스레드, 락, 메모리 배리어 같은 개념이 사실상 등장하지 않는다.** `for`, `when`, `suspend`는 언어의 문법과 의미론에 포함되어 있지만 `Thread`나 `synchronized`는 그렇지 않다. `synchronized`도 키워드가 아니라 *표준 라이브러리 함수*이고, 그마저 JVM 백엔드에서만 쓸 수 있다.

이는 실수가 아니라 의도된 설계이다. [[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]]에서 보았듯 Kotlin은 JVM, Native, JS, Wasm처럼 *동시성 모델이 서로 크게 다른* 타깃에서 실행된다. JVM은 선점형 스레드와 공유 메모리를, JS는 단일 스레드 이벤트 루프를, Wasm은 (초기에는) 스레드가 없는 환경을 전제한다.

언어가 "스레드는 이렇게 동작한다"고 정해 버리면 어느 타깃에서는 반드시 틀린 설명이 된다. 그래서 Kotlin은 동시성의 *의미론*을 **각 백엔드가 기반으로 하는 플랫폼의 메모리 모델에 맡긴다**.

```text
Kotlin 소스
    │  (동시성 의미론을 언어가 정의하지 않음)
    ▼
┌──────────────┬───────────────┬────────────┬────────────┐
│ JVM 백엔드    │ Kotlin/Native │ Kotlin/JS  │ Kotlin/Wasm│
│ → 자바 메모리 │ → 자체 메모리  │ → 단일     │ → (초기)   │
│    모델(JMM)  │    관리자      │    스레드   │   스레드 없음│
└──────────────┴───────────────┴────────────┴────────────┘
```

이렇게 플랫폼에 맡긴 결과는 실무에서 분명하게 드러난다. **"이 코드는 스레드 안전한가?"라는 질문에는 타깃을 밝히지 않으면 답할 수 없다.** JVM에서는 JMM의 happens-before로 판정하고, JS에서는 애초에 진짜 병렬 실행이 없으므로(단일 스레드) 데이터 경쟁도 존재하지 않는다. 이 장은 대부분 **JVM 백엔드**를 전제로 설명하고, Native는 9절에서 따로 다룬다. 설명이 JVM에만 해당할 때는 따로 밝힌다.

> [!note] 명세 기준
> Kotlin 공용 표준 라이브러리(`kotlin-stdlib`의 common 부분)에는 `kotlin.concurrent.Volatile`, `kotlin.concurrent.atomics` 같은 *멀티플랫폼 동시성 기본 요소*가 일부 있다(도입 당시에는 실험적이었고, 버전에 따라 안정화 상태가 다르다). 그러나 이들도 "각 플랫폼에서 무엇으로 매핑되는가"로 정의될 뿐, 언어 명세가 배타적 실행을 보장하지는 않는다.
>
> JVM에서 `@Volatile`은 JVM의 `volatile`로, Native에서는 Native 메모리 관리자의 원자적 접근으로 구현된다.

### 1.2 "동시성"과 "병렬성"과 "비동기"는 서로 다른 축이다

용어부터 구분해 두자. 세 단어는 자주 섞여 쓰이지만 서로 다른 축을 가리킨다.

| 개념 | 정의 | Kotlin에서 해당하는 것 |
|------|------|-------------------|
| 동시성(concurrency) | 여러 작업이 *논리적으로 겹쳐* 진행된다 (한 CPU에서 번갈아 실행해도 된다) | 코루틴, 스레드 모두 |
| 병렬성(parallelism) | 여러 작업이 *물리적으로 동시에* 실행된다 (여러 코어) | 멀티스레드, 멀티코어 디스패처 |
| 비동기(asynchrony) | 호출과 결과가 시간상 분리된다 (블로킹하지 않는다) | `suspend`, 콜백, `Future` |

핵심은 **이 장에서 다루는 메모리 모델 문제가 "병렬성"에서 생긴다**는 점이다. 두 스레드가 서로 다른 코어에서 *실제로 동시에* 같은 변수를 건드릴 때 가시성과 재배열 문제가 생긴다. 단일 스레드 코루틴은 동시성은 있어도 병렬성이 없으므로 데이터 경쟁이 없다. 그래서 42장(suspend와 코루틴)에서 보았듯 단일 스레드 디스패처는 잠금 없이도 안전할 수 있다.

suspend가 "비동기가 아니라 중단할 수 있을 뿐"이라는 사실도 이 표에서 다시 확인할 수 있다. suspend는 비동기 축의 도구이고, 병렬성을 만들어 내지는 않는다.

## 2. 스레드: 가장 낮은 실행 단위 (JVM 백엔드)

### 2.1 Thread와 Runnable

JVM 백엔드에서 가장 기본이 되는 실행 흐름은 스레드이다. Kotlin은 자바의 `java.lang.Thread`를 그대로 사용하고, 표준 라이브러리가 그 위에 얇은 확장을 제공한다.

```kotlin
import kotlin.concurrent.thread

fun main() {
    // 방법 1: 자바 API 직접 사용 (람다가 SAM 변환으로 Runnable이 됨)
    val t1 = Thread {
        println("t1: ${Thread.currentThread().name}")
    }
    t1.start()   // 새 스레드 시작. run()을 직접 부르면 현재 스레드에서 실행됨(함정)
    t1.join()    // t1이 끝날 때까지 현재 스레드가 기다림

    // 방법 2: kotlin.concurrent.thread 확장 (더 관용적)
    val t2 = thread(start = true, isDaemon = false, name = "worker") {
        println("t2 실행 중")
    }
    t2.join()
}
```

`thread { }`는 `kotlin.concurrent.thread` 함수이다. 이 함수는 `Thread`를 만들고, 옵션에 따라 곧바로 `start()`까지 호출해 준다(JVM 전용). 여기에 넘긴 람다는 [[13 - 함수 타입과 람다와 함수 참조]]에서 본 SAM 변환을 거쳐 `Runnable`이 된다. `Runnable`은 추상 메서드가 하나뿐인 함수형 인터페이스이므로 람다를 바로 대입할 수 있다.

> [!warning] 흔한 오해
> `Thread.start()`와 `Thread.run()`을 혼동하면 심각한 문제가 생긴다. `start()`는 *새 스레드*를 만들고 그 스레드에서 `run()`을 호출한다. 반면 `run()`을 직접 호출하면 **현재 스레드에서 일반 메서드처럼 실행**되므로 병렬성이 전혀 없다. "왜 병렬로 실행되지 않지?"라는 문제의 흔한 원인이다.

### 2.2 데몬 스레드와 생명주기

`isDaemon = true`로 만든 데몬 스레드는 JVM이 종료할 때 *기다려 주지 않는다*. 데몬이 아닌 사용자 스레드가 모두 끝나면 JVM은 데몬 스레드가 남아 있어도 종료한다. 데몬 스레드는 캐시 정리 같은 백그라운드 관리 작업에 쓴다. 반대로 사용자 스레드가 하나라도 살아 있으면 `main`이 반환되어도 프로세스는 종료되지 않는다.

```kotlin
import kotlin.concurrent.thread

fun main() {
    thread(isDaemon = true) {
        while (true) { /* 무한 루프지만 데몬이므로 JVM 종료를 막지 않음 */ }
    }
    println("main 끝")
    // main 반환 → 사용자 스레드 없음 → 데몬 무시하고 JVM 종료
}
```

### 2.3 스레드 풀: 스레드를 재사용하기

스레드는 무겁다. 전통적인 모델에서 JVM 스레드 하나는 OS 스레드 하나에 대응하고, 기본 스택 크기가 수백 KB에서 1MB에 이른다. 스레드를 수만 개 만들면 메모리와 컨텍스트 스위칭 비용이 급격히 늘어난다.

그래서 작업마다 스레드를 새로 만드는 대신, 스레드를 몇 개만 만들어 두고 작업을 큐에 넣어 재사용하는 **스레드 풀(thread pool)** 을 쓴다. JVM 백엔드에서는 자바의 `java.util.concurrent.Executors`를 그대로 사용한다.

```kotlin
import java.util.concurrent.Executors

fun main() {
    val pool = Executors.newFixedThreadPool(4)   // 스레드 4개 재활용
    repeat(100) { i ->
        pool.submit { println("작업 $i @ ${Thread.currentThread().name}") }
    }
    pool.shutdown()   // 새 작업 거부, 진행 중 작업은 마침 (누락하면 JVM이 안 끝날 수 있음)
}
```

여기에는 중요한 함정이 하나 있다. **스레드 풀은 스레드를 *재사용*하므로, 스레드에 묶인 상태(`ThreadLocal` 등)에 이전 작업의 값이 남아 있을 수 있다.** 풀에서 가져온 스레드가 깨끗하다고 가정해서는 안 된다. 또한 풀 안의 여러 작업이 같은 가변 상태를 건드리면 이 장에서 다루는 경쟁 상태가 그대로 생긴다. 풀은 스레드 생성 비용을 줄여 줄 뿐, 동시성 문제를 없애지는 않는다.

코루틴의 디스패처는 개념적으로 이 스레드 풀 위에 올린 상위 추상화이다. `Dispatchers.Default`는 CPU 코어 수만큼의 스레드 풀을, `Dispatchers.IO`는 그보다 큰 풀을 관리하고, 코루틴들은 그 스레드를 잘게 나누어 사용한다.

### 2.4 스레드는 비싸고, 코루틴은 그 위에서 실행된다

이는 코루틴이 존재하는 실용적인 이유 중 하나이다. 코루틴은 *스레드보다 훨씬 가벼운* 중단 가능한 작업 단위라서, 적은 수의 스레드 위에서 수십만 개를 실행할 수 있다. 스레드가 스택과 커널 스케줄링 같은 OS 자원이라면, 코루틴은 힙에 놓인 상태 기계 객체(42장에서 본 CPS 변환)일 뿐이어서 훨씬 싸다.

하지만 그 수십만 개의 코루틴이 하나의 가변 상태를 공유하면 *이 장의 문제*가 그대로 다시 나타난다. 코루틴은 스레드를 아껴 줄 뿐, 메모리 모델 문제를 없애 주지는 않는다.

## 3. 경쟁 상태 분석: `counter++`가 원자적이지 않은 이유

### 3.1 증가 연산 하나, 기계 연산 세 개

동시성 버그의 가장 기본적인 형태는 "잃어버린 갱신(lost update)"이다. 가장 단순한 예를 보자.

```kotlin
import kotlin.concurrent.thread

var counter = 0   // 공유 가변 상태

fun main() {
    val threads = List(100) {
        thread {
            repeat(1000) { counter++ }   // 각 스레드가 1000번 증가
        }
    }
    threads.forEach { it.join() }
    println(counter)   // 기대: 100000, 실제: 그보다 작은 비결정적 값 (예: 87342)
}
```

스레드 100개가 각각 1000번씩 증가시키므로 답은 100000이어야 한다. 그러나 실행할 때마다 그보다 작은 *비결정적인* 값이 나온다. `counter++`가 원자적 연산이 아니기 때문이다. JVM 백엔드에서 이 한 줄은 대략 세 개의 바이트코드 단계로 나뉜다.

```text
counter++  ≡  (JVM 백엔드에서 대략)
    1. temp   = counter      // 필드에서 읽기 (getstatic)
    2. temp   = temp + 1     // 레지스터에서 더하기 (iadd)
    3. counter = temp        // 필드에 쓰기 (putstatic)
```

두 스레드 A와 B가 이 세 단계를 번갈아 실행(interleaving)하면 갱신이 사라진다.

```text
counter = 41 인 상태에서:

  스레드 A               스레드 B
  ─────────              ─────────
  read 41
                         read 41       ← 아직 A가 안 썼음
  add → 42
                         add → 42
  write 42
                         write 42      ← A의 증가가 덮여 사라짐

결과: counter = 42  (기대: 43)  → 갱신 1건 소실
```

이것이 "읽기-수정-쓰기(read-modify-write)" 연산에 내재된 위험이다. `counter++`, `list.add(x)`, `map[k] = map[k]!! + 1` 같은 복합 연산은 원자적이지 않다. 따라서 여러 스레드가 동시에 실행하면 중간 상태가 서로를 덮어쓴다.

> [!note] 명세 기준
> JMM은 `int`처럼 32비트 이하인 값의 개별 읽기와 쓰기가 원자적이라고 보장한다. 문제는 `++`가 *세 개의* 연산이라는 점이다. 반대로 `long`과 `double`(64비트)은 **`volatile`이 아니면 개별 읽기와 쓰기조차 원자성이 보장되지 않는다**. 한 번의 쓰기가 상위 32비트와 하위 32비트로 나뉘어 "찢긴 읽기/쓰기(torn read/write)"가 이론적으로 가능하다.
>
> 이는 JLS의 *long/double 비원자적 처리*에 해당하며, JLS가 별도로 정의하고 금지하는 "워드 찢김(word tearing)", 즉 인접한 필드나 배열 원소 사이의 간섭과는 다른 개념이다. 64비트 JVM에서는 실무상 원자적으로 구현되지만 *명세가 보장하지는 않으므로*, 공유되는 `long`/`double`에는 `@Volatile`을 붙여야 이식성 있게 안전하다.

### 3.2 확인 후 행동(check-then-act) 경쟁

또 하나의 대표적인 예는 "확인한 뒤에 행동하기"이다. 지연 초기화를 단순하게 구현한 코드를 보자.

```kotlin
class LazyResource {
    private var instance: Heavy? = null

    fun get(): Heavy {
        if (instance == null) {        // (1) 확인
            instance = Heavy()         // (2) 행동
        }
        return instance!!
    }
}
```

두 스레드가 (1)을 동시에 통과하면 `Heavy()`가 *두 번* 생성된다. 게다가 뒤에서 보겠지만, 다른 스레드가 `instance`의 일부만 초기화된 상태를 볼 수도 있다(가시성과 재배열 문제). [[23 - 위임 프로퍼티]]의 `by lazy`가 기본으로 `SYNCHRONIZED` 모드를 쓰는 이유가 바로 이 패턴이다. 표준 라이브러리가 이 함정을 대신 막아 준다.

경쟁 상태의 세 가지 유형을 정리하면 다음과 같다.

- **원자성 위반(atomicity)**: `counter++`처럼 복합 연산이 여러 단계로 나뉘어 다른 스레드와 번갈아 실행된다.
- **가시성 위반(visibility)**: 한 스레드가 쓴 값이 다른 스레드에 *보이지 않는다*(다음 절).
- **순서 위반(ordering/reordering)**: 컴파일러나 CPU가 연산 순서를 바꾸어, 관측되는 순서가 뒤바뀐다(다음 절).

이 세 가지를 하나의 이론으로 묶는 것이 JMM의 happens-before이다.

## 4. 자바 메모리 모델(JMM): 가시성, 재배열, happens-before (JVM 백엔드)

### 4.1 왜 "쓰기만 하면 보이지 않는가"

직관적으로는 한 스레드가 `x = 42`라고 쓰면 다른 스레드가 곧바로 `x`에서 42를 읽을 것 같다. **그렇지 않다.** 현대 하드웨어와 컴파일러는 성능을 위해 다음과 같은 일을 자유롭게 한다.

```text
[각 코어의 메모리 계층]

  코어 A                     코어 B
  ┌─────────┐               ┌─────────┐
  │ 레지스터 │               │ 레지스터 │
  │  L1 캐시 │               │  L1 캐시 │  ← A의 쓰기가 여기까지 안 내려오면
  └────┬────┘               └────┬────┘     B는 옛 값을 봄
       │                         │
       └──────── 공유 메모리 ─────┘
```

- **캐싱**: 코어 A가 `x`를 자기 L1 캐시나 레지스터에 담아 두고, 공유 메모리(또는 다른 코어)로 곧바로 내보내지 않을 수 있다. 그러면 코어 B는 여전히 옛 값을 본다.
- **재배열(reordering)**: 컴파일러(JIT 포함)와 CPU는 데이터 의존성이 없다고 판단한 명령의 순서를 바꾸어 실행할 수 있다. 단일 스레드에서는 결과가 같지만, 다른 스레드가 관측하면 순서가 뒤바뀌어 보인다.

이 두 가지 자유가 없으면 최적화를 할 수 없다. 그래서 JMM은 "모든 쓰기가 즉시 보인다"고 보장하지 *않는다*. 그 대신 **"어떤 조건에서 가시성과 순서가 보장되는가"를 happens-before라는 반순서(partial order)로 정의한다.**

### 4.2 재배열이 실제로 관측되는 예

대표적인 "깃발과 데이터" 예제이다.

```kotlin
var data = 0          // 비-volatile
var ready = false     // 비-volatile

// 스레드 A (생산자)
fun producer() {
    data = 42          // (A1)
    ready = true       // (A2)
}

// 스레드 B (소비자)
fun consumer() {
    while (!ready) { /* 스핀 */ }   // (B1)
    println(data)                   // (B2)  기대: 42
}
```

단순하게 생각하면 `ready == true`를 보았으니 `data == 42`도 보아야 한다. 하지만 happens-before 관계가 없으므로 다음 중 어떤 일이든 일어날 수 있다.

- (B2)가 `42`가 아니라 `0`을 출력한다. A가 쓴 `data = 42`가 아직 B에게 보이지 않기 때문이다(가시성).
- (A1)과 (A2)가 재배열되어, B는 `ready == true`를 보았는데 `data`는 아직 0이다(순서).
- `while (!ready)`가 *영원히* 끝나지 않는다. 컴파일러가 `ready`를 레지스터로 끌어올려(hoisting) 다시 읽지 않을 수 있기 때문이다(가시성 문제의 극단적인 경우).

세 가지 모두 **`volatile`이 아닌 필드에서 일어난 데이터 경쟁(data race)** 의 정당한 결과이다. 버그가 "가끔"만 재현되는 이유도 여기에 있다. 특정 CPU, JIT, 부하 조건에서만 드러나기 때문이다.

### 4.3 happens-before 규칙

JMM의 핵심 계약은 다음과 같다. **연산 X가 연산 Y보다 happens-before이면, X의 모든 메모리 효과가 Y에게 보이고 X가 Y보다 먼저 일어난 것으로 관측된다.** happens-before 관계를 만드는 주요 규칙은 다음과 같다.

| 규칙 | 내용 |
|------|------|
| 프로그램 순서(program order) | *같은 스레드 안*에서는 소스 순서대로 happens-before이다 (단일 스레드에서 생기는 착각의 근거) |
| 모니터 락(monitor lock) | 어떤 락의 `unlock`은 그 뒤에 오는 같은 락의 `lock`보다 happens-before이다 |
| `volatile` 필드 | `volatile` 쓰기는 그 뒤에 오는 같은 필드의 `volatile` 읽기보다 happens-before이다 |
| 스레드 시작(thread start) | `t.start()`는 스레드 `t`의 첫 동작보다 happens-before이다 |
| 스레드 종료(thread join) | 스레드 `t`의 마지막 동작은 `t.join()`이 반환된 이후보다 happens-before이다 |
| 전이성(transitivity) | X ⇒ Y 이고 Y ⇒ Z 이면 X ⇒ Z |

마지막 두 규칙 덕분에 3절의 `join()` 예제가 안전해진다. `thread { counter++ }` 자체는 경쟁하지만, `join()`으로 합류한 뒤 `counter`를 읽는 `main`은 각 스레드의 마지막 쓰기를 *본다*. 다만 번갈아 실행되면서 값이 사라지는 문제는 별개이다. join은 가시성만 보장할 뿐 원자성을 주지는 않는다.

$$
\text{X} \xrightarrow{hb} \text{Y} \;\Longrightarrow\; \text{X의 메모리 효과가 Y에게 보이고, 순서가 관측됨}
$$

happens-before 관계가 *없는* 두 연산은 "순서가 없는(unordered)" 연산이며, 서로의 효과를 볼 수도 있고 보지 못할 수도 있다. 데이터 경쟁이란 정확히 **happens-before로 순서가 정해지지 않았고, 적어도 하나가 쓰기인 두 접근**이다.

이 정의를 자바와 나란히 놓으면, Kotlin이 새 규칙을 만든 것이 아니라 JVM의 계약을 *그대로 물려받았다*는 점이 분명해진다.

```java
// Java — 동일한 JMM 위에서 같은 happens-before 규칙
class Flag {
    volatile boolean ready = false;   // Kotlin의 @Volatile과 같은 바이트코드
    int data = 0;
}
```

Kotlin의 `@Volatile var ready`와 자바의 `volatile boolean ready`는 JVM 백엔드에서 *동일한 필드 플래그(ACC_VOLATILE)* 로 컴파일된다. 즉 이 장에서 다루는 happens-before 직관은 자바 개발자의 직관과 완전히 같으며, 이것이 두 언어가 같은 `.class`를 주고받으며 함께 동작할 수 있는 근거이다([[45 - Java 상호운용]]).

차이는 문법과 기본값(자바 필드는 기본적으로 가변이고, Kotlin은 `val`로 불변을 권장한다)뿐이고, 메모리 모델 자체는 하나이다.

> [!note] 명세 기준
> 자바/JVM의 메모리 모델은 데이터 경쟁이 있더라도 "아무 근거 없이 나타난 값(out-of-thin-air)"이 나오는 것은 금지한다. C/C++에서는 데이터 경쟁이 *미정의 동작(undefined behavior)* 이어서 크래시를 포함해 어떤 결과든 허용된다. 반면 JVM에서는 값이 어떤 스레드가 실제로 쓴 값들 중 하나로 제한된다.
>
> 그래도 "옛 값을 본다", "순서가 뒤바뀐다", "영원히 옛 값을 본다"는 모두 정당한 결과이다. 안전하지 않다는 사실은 변하지 않는다.

### 4.4 final 필드의 특별한 보장과 `val`

JMM은 눈에 잘 띄지 않는 보장을 하나 더 제공한다. **`final` 필드는 생성자가 정상적으로 끝나면(그리고 생성 도중 `this`가 밖으로 새어 나가지 않았다면), 별도의 동기화 없이도 다른 스레드에서 올바른 값이 보인다.** 이것이 불변 객체를 안전하게 공유할 수 있는 근거이다.

백킹 필드가 있는 Kotlin의 `val` 프로퍼티는 JVM 백엔드에서 `final` 필드로 컴파일된다([[22 - 프로퍼티와 백킹 필드]], 11장 변수와 초기화). 따라서 다음 코드는 안전하다.

```kotlin
class Point(val x: Int, val y: Int)   // x, y는 JVM에서 final 필드

// 스레드 A가 만든 Point를 스레드 B가 받으면,
// x, y는 동기화 없이도 42, 7로 보인다 (final 필드 보증)
```

여기서 [[24 - 상속과 오버라이딩과 초기화 순서]]에서 경고한 "`this` 탈출(escape)"이 다시 등장한다. 생성자가 끝나기 전에 `this`를 다른 스레드가 접근할 수 있는 곳(예: 정적 컬렉션, 리스너 등록)에 넣으면 final 필드 보장이 깨지고, 일부만 초기화된 객체가 보일 수 있다. 이는 생성자에서 open 멤버를 호출하는 문제와 원인이 같다.

> [!warning] 흔한 오해
> "`val`이니까 스레드 안전하다"는 말은 절반만 맞다(11장 변수와 초기화). `val x: Int = 42`처럼 *원시 값이나 불변 값*을 담으면 final 보장 덕분에 안전하다. 그러나 `val list = mutableListOf<Int>()`는 **참조를 재대입할 수 없을 뿐, 참조가 가리키는 리스트는 가변**이다.
>
> 두 스레드가 그 리스트에 동시에 `add`하면 경쟁 상태가 된다. `val`은 *참조*가 불변이라는 뜻이지 *객체*가 불변이라는 뜻이 아니다. 참조가 가리키는 대상이 정말로 불변일 때에만 별도 비용 없이 스레드 안전성을 얻는다.

## 5. `@Volatile`: 가시성과 원자성의 정확한 경계

### 5.1 `@Volatile`이 보장하는 것

`@Volatile`(JVM 백엔드에서는 `kotlin.jvm.Volatile`, 멀티플랫폼 공통에서는 `kotlin.concurrent.Volatile`)은 프로퍼티의 백킹 필드를 JVM `volatile`로 만든다. 이 애너테이션이 제공하는 계약은 두 가지이다.

1. **가시성**: `volatile` 필드에 쓴 값은 *곧바로* 다른 스레드에 보인다(캐시에 머물지 않는다). 읽기는 항상 메인 메모리의 최신 값을 가져온다.
2. **순서(happens-before)**: `volatile` 쓰기는 그 뒤에 오는 `volatile` 읽기보다 happens-before이다. 게다가 `volatile` 쓰기 *이전*의 모든 쓰기(`volatile`이 아닌 쓰기 포함)도 그 읽기 이후에 보인다.

4.2절의 깃발 예제에서 `ready`에 `@Volatile`을 붙여 고쳐 보자.

```kotlin
var data = 0
@Volatile var ready = false   // 이제 volatile

fun producer() {
    data = 42          // (A1)
    ready = true       // (A2) volatile 쓰기 — A1이 이보다 먼저 일어남을 발행(publish)
}

fun consumer() {
    while (!ready) { }         // (B1) volatile 읽기 — 매번 최신값 확인, 무한루프 안 됨
    println(data)              // (B2) => 42  보장됨
}
```

핵심은 **`volatile`인 `ready` 하나가 `volatile`이 아닌 `data`까지 안전하게 전달한다**는 점이다. `ready = true`(volatile 쓰기)가 그 앞의 일반 쓰기인 `data = 42`를 "함께 발행"하고, `consumer`가 `ready == true`(volatile 읽기)를 보는 순간 그 앞의 모든 쓰기, 즉 `data = 42`도 보이게 된다. 이것이 volatile의 "발행/구독" 효과이다.

### 5.2 `@Volatile`이 보장하지 *않는* 것: 원자성

가장 많이 틀리는 부분이 여기이다. **`@Volatile`은 가시성만 보장하고, 원자성은 보장하지 않는다.**

```kotlin
@Volatile var counter = 0

fun main() {
    val threads = List(100) {
        thread { repeat(1000) { counter++ } }
    }
    threads.forEach { it.join() }
    println(counter)   // 여전히 100000이 아님!
}
```

`@Volatile`을 붙여도 `counter++`는 여전히 "읽기, 더하기, 쓰기"의 세 단계이다. volatile은 단계마다 최신 값을 보게 해 주지만, *세 단계를 하나로 묶어 주지는 않는다*. 두 스레드가 같은 값을 읽고 각자 더해 덮어쓰면 갱신은 여전히 사라진다. **복합(read-modify-write) 연산에는 volatile만으로 부족하며**, 원자적 연산(7절)이나 락(6절)이 필요하다.

| 시나리오 | `@Volatile`로 충분한가? |
|----------|------------------------|
| 한 스레드가 쓰고 여러 스레드가 읽는 *깃발/상태 플래그* | 충분 (`ready`, 종료 신호 등) |
| 한 번만 대입되는 참조의 안전한 발행 | 충분 (더블 체크 잠금의 필드) |
| `counter++`, 누적, 복합 갱신 | **불충분** (원자성 필요) |
| `long`/`double`의 원자적 읽기/쓰기 | 충분 (찢긴 읽기/쓰기 방지) |

> [!caution] 성능 주의
> `volatile`에도 비용이 있다. 읽을 때마다 메모리 배리어가 생겨 캐시 최적화를 포기하게 된다. 자주 읽는 필드에 무분별하게 붙이면 성능이 떨어진다. 실제로 스레드 사이에 공유되고 가시성이 필요한 필드에만 붙여야 한다.

### 5.3 더블 체크 잠금(double-checked locking)의 올바른 형태

3.2절의 지연 초기화를 제대로 고쳐 보면 volatile이 왜 필요한지 분명해진다.

```kotlin
class LazyResource {
    @Volatile private var instance: Heavy? = null
    private val lock = Any()

    fun get(): Heavy {
        val local = instance
        if (local != null) return local          // 빠른 경로: 락 없이 읽기
        return synchronized(lock) {
            instance ?: Heavy().also { instance = it }   // 느린 경로: 락 안에서 재확인
        }
    }
}
```

`instance`가 `@Volatile`이 아니면, 다른 스레드가 `Heavy` 생성자가 *끝나기 전의, 일부만 초기화된 참조*를 볼 수 있다. 재배열 때문에 "참조 대입"이 "필드 초기화"보다 먼저 보일 수 있기 때문이다. `@Volatile`은 이 재배열을 막아 안전한 발행을 보장한다. 물론 실무에서는 이렇게 직접 구현하기보다 23장(위임 프로퍼티)의 `by lazy`를 쓰는 것이 맞다. 표준 라이브러리가 바로 이 패턴을 검증된 형태로 캡슐화해 두었다.

## 6. `@Synchronized`와 락: 상호 배제 (JVM 백엔드)

### 6.1 `synchronized` 함수와 `@Synchronized` 애노테이션

원자성과 가시성을 *한꺼번에* 얻는 가장 직접적인 도구는 상호 배제(mutual exclusion), 즉 락이다. JVM 백엔드에서 Kotlin은 두 가지 형태를 제공한다.

```kotlin
val lock = Any()   // 락으로 쓸 임의의 객체 (모니터)

var counter = 0

fun increment() {
    synchronized(lock) {   // 이 블록은 한 번에 한 스레드만 진입
        counter++          // 이제 원자적 + 가시적
    }
}
```

`synchronized(lock) { ... }`는 `kotlin.synchronized` 인라인 함수(JVM 전용)이다. 블록에 들어갈 때 `lock` 객체의 모니터를 획득하고, 블록을 나갈 때(예외로 나가더라도) 해제한다. 4.3절의 happens-before 표에 따르면 **한 스레드의 `unlock`은 다음 스레드의 `lock`보다 happens-before**이다. 따라서 락 안에서 한 모든 쓰기는 다음에 같은 락을 잡은 스레드에게 보인다. 가시성은 추가 비용 없이 함께 얻는다.

메서드 전체를 동기화하려면 `@Synchronized`(`kotlin.jvm.Synchronized`, JVM 전용)를 쓴다.

```kotlin
class Counter {
    private var value = 0

    @Synchronized fun increment() { value++ }   // 메서드 전체가 임계 구역
    @Synchronized fun get(): Int = value
}
```

`@Synchronized` 메서드는 인스턴스 메서드이면 `this`를, 정적 메서드나 최상위 함수이면 클래스 객체를 모니터로 쓴다. 여기서 `get()`에도 `@Synchronized`를 붙인 이유가 중요하다. **쓰기만 동기화하고 읽기를 동기화하지 않으면 가시성이 깨진다.** 락은 "같은 락을 공유하는 접근들 사이에서만" happens-before 관계를 만든다. 읽는 쪽도 같은 락을 잡아야 최신 값을 볼 수 있다.

> [!note] 명세 기준
> `synchronized`와 `@Synchronized`는 **JVM 백엔드 전용**이다. Kotlin/Native와 JS에는 이 함수가 없으므로 멀티플랫폼 공통 코드에서는 쓸 수 없다. 멀티플랫폼에서 상호 배제가 필요하면 `kotlinx.coroutines`의 `Mutex`나 라이브러리(예: atomicfu의 락)를 쓴다. 이는 1절에서 말한 "동시성은 플랫폼 계약"이라는 명제에서 곧바로 따라 나오는 결과이다.

### 6.2 락의 함정: 교착, 과도한 범위, 잘못된 락 객체

락은 강력하지만 새로운 버그를 만들기도 한다.

- **교착 상태(deadlock)**: 스레드 A가 락1을 잡고 락2를 기다리는 동안 스레드 B가 락2를 잡고 락1을 기다리면, 두 스레드는 영원히 멈춘다. 여러 락은 항상 *같은 순서*로 획득해야 한다.
- **과도한 락 범위**: 임계 구역이 크면 병렬성이 사라진다. 락은 *공유 상태를 건드리는 최소 구간*에만 걸어야 한다.
- **잘못된 락 객체**: `String` 리터럴이나 박싱된 `Integer`를 락으로 쓰면, JVM이 그 객체를 다른 코드와 공유(인터닝/캐시)하므로 예기치 않은 경합이나 교착이 생긴다. `Any()`로 만든 전용 락 객체를 쓰는 것이 안전하다.
- **서로 다른 락으로 보호한 같은 데이터**: 같은 변수를 어떤 곳에서는 락 A로, 다른 곳에서는 락 B로 보호하면 상호 배제가 전혀 성립하지 않는다. *하나의 상태는 하나의 락으로* 보호해야 한다.

```text
[교착 상태]
  스레드 A: lock(L1) ─ 대기 ─▶ lock(L2)   (B가 쥐고 있음)
  스레드 B: lock(L2) ─ 대기 ─▶ lock(L1)   (A가 쥐고 있음)
              ▲                    │
              └────────────────────┘
              서로를 영원히 기다림
```

### 6.3 재진입(reentrancy)과 JVM 모니터

JVM의 내장 모니터(`synchronized`)는 **재진입할 수 있다**. 즉 이미 락을 쥔 스레드가 같은 락을 다시 잡아도 교착되지 않고, 카운터만 증가한다.

```kotlin
class Node {
    @Synchronized fun outer() { inner() }   // this의 모니터 획득
    @Synchronized fun inner() { /* ... */ } // 같은 스레드가 this 모니터를 재획득 — OK
}
```

재진입이 가능하므로 동기화된 메서드끼리 서로 호출해도 안전하다. 반면 뒤에서 볼 kotlinx의 `Mutex`는 기본적으로 재진입할 수 *없다*. 같은 코루틴이 이미 잠근 `Mutex`를 다시 잠그려 하면 교착된다. 도구마다 계약이 다르다는 점을 늘 확인해야 한다(자세한 내용은 Kotlin Coroutines 시리즈 18장(공유 상태와 동기화)에서 다룬다).

## 7. 원자적 연산과 CAS: 락 없이 정확성 얻기

### 7.1 `kotlin.concurrent.atomics`

락은 무겁고(경합이 생기면 스레드가 잠들었다가 깨어나야 한다) 교착 위험도 있다. 단일 변수에 대한 read-modify-write라면 더 가벼운 도구인 **원자적 타입**을 쓸 수 있다. Kotlin 2.x는 멀티플랫폼 공통 표준 라이브러리에 `kotlin.concurrent.atomics` 패키지를 도입했다. 도입 당시에는 실험적이었고 이후 버전에서 안정화되었으므로, 사용할 때 버전별로 opt-in이 필요한지 확인해야 한다.

```kotlin
import kotlin.concurrent.atomics.AtomicInt

val counter = AtomicInt(0)

fun main() {
    val threads = List(100) {
        thread { repeat(1000) { counter.fetchAndAdd(1) } }   // 원자적 증가
    }
    threads.forEach { it.join() }
    println(counter.load())   // => 100000  정확히 맞음
}
```

주요 타입은 `AtomicInt`, `AtomicLong`, `AtomicBoolean`, `AtomicReference<T>`(그리고 `AtomicIntArray` 같은 배열 변형)이다. API는 명시적인 로드와 스토어를 강조한다.

| 연산 | 의미 |
|------|------|
| `load()` | 원자적 읽기 (volatile 읽기 의미) |
| `store(v)` | 원자적 쓰기 (volatile 쓰기 의미) |
| `exchange(v)` | 새 값으로 바꾸고 이전 값을 반환 |
| `compareAndSet(expected, new)` | 현재 값이 `expected`이면 `new`로 교체하고, 성공 여부를 `Boolean`으로 반환 |
| `compareAndExchange(expected, new)` | 위와 같지만 이전 값을 반환 |
| `fetchAndAdd(delta)` / `addAndFetch(delta)` | 원자적 덧셈 (이전/이후 값 반환) |
| `fetchAndIncrement()` / `incrementAndFetch()` | 원자적 +1 |
| `update { }` / `updateAndFetch { }` | 임의의 갱신 함수를 CAS 루프로 원자적으로 적용 (확장) |

> [!note] 명세 기준
> JVM 백엔드에서 `kotlin.concurrent.atomics`의 타입은 `java.util.concurrent.atomic`의 `AtomicInteger`, `AtomicLong`, `AtomicReference` 등으로 매핑된다. 따라서 성능 특성도 이들과 같다. 자바 상호운용(45장)에서 기존 `AtomicInteger`를 직접 써도 되지만, 멀티플랫폼 공통 코드에서는 `kotlin.concurrent.atomics`를 써야 다른 플랫폼에서도 동작한다.

### 7.2 CAS(compare-and-set)의 원리

원자적 타입의 핵심은 **CAS(compare-and-swap/set)** 라는 하드웨어 명령이다. CAS는 "현재 값이 기대한 값과 같으면 새 값으로 바꾸고, 다르면 실패한다"를 *하나의 원자적 단계*로 수행한다(x86의 `LOCK CMPXCHG` 등). 이 명령을 이용해 락 없이 read-modify-write를 구현하는 표준 패턴이 CAS 루프이다.

```kotlin
import kotlin.concurrent.atomics.AtomicInt

val value = AtomicInt(0)

// value = value * 2 를 원자적으로 (곱셈은 내장 원자 연산이 없으므로 직접 루프)
fun doubleIt() {
    while (true) {
        val current = value.load()          // 1. 현재 값 읽기
        val next = current * 2              // 2. 새 값 계산
        if (value.compareAndSet(current, next)) return   // 3. 그 사이 안 바뀌었으면 커밋
        // 누가 중간에 바꿨으면 CAS 실패 → 처음부터 재시도
    }
}
// 위 루프는 표준 라이브러리의 update { it * 2 } 로 축약 가능
```

CAS 루프의 장점은 **락이 없다**는 점이다. 스레드를 재우지 않고 교착도 생기지 않는다. 경합이 적으면 락보다 훨씬 빠르다. 대신 경합이 매우 심하면 CAS 실패와 재시도가 반복되어 "라이브락(livelock)"처럼 CPU를 소모할 수 있다.

이런 방식을 "락-프리(lock-free)"라고 부른다. 시스템 전체로는 항상 진행하지만, 개별 스레드는 오랫동안 진행하지 못할(기아) 수도 있다.

$$
\text{CAS}(addr, expected, new) = \begin{cases} \text{true, } *addr \leftarrow new & \text{if } *addr = expected \\ \text{false} & \text{otherwise}\end{cases} \quad\text{(원자적)}
$$

### 7.3 원자적 타입도 만능은 아니다: 조합의 위험

원자적 타입은 *단일 변수*에 대한 연산만 원자적으로 만든다. 원자 변수 여러 개를 조합하면 다시 경쟁이 생긴다.

```kotlin
val a = AtomicInt(0)
val b = AtomicInt(0)

// "a와 b의 합이 항상 짝수"라는 불변식을 지키고 싶다면?
fun bump() {
    a.fetchAndIncrement()   // 원자적
    b.fetchAndIncrement()   // 원자적
    // 그러나 이 두 줄 "사이"에서 다른 스레드가 a+b를 읽으면 홀수를 본다!
}
```

각 연산은 원자적이지만 *두 연산의 조합*은 원자적이지 않다. 여러 변수에 걸친 불변식은 락이나 단일 원자 참조로 지켜야 한다. 후자는 두 값을 묶은 불변 객체를 `AtomicReference`로 한 번에 교체하는 방식이다. **"원자적 타입이면 스레드 안전"이 아니라 "원자적 연산 하나가 스레드 안전"** 이라는 점을 놓치면 안 된다.

### 7.4 ABA 문제: CAS에 숨은 함정

CAS는 "값이 기대한 값과 *같은가*"만 확인한다. 그래서 값이 A → B → A로 바뀌었다가 돌아오면 CAS는 "바뀌지 않았다"고 잘못 판단한다. 이것이 **ABA 문제**이다.

```text
스레드 X: current = A 읽음
                              스레드 Y: A → B 로 바꿈
                              스레드 Y: B → A 로 되돌림
스레드 X: compareAndSet(A, ...) 성공!  ← 그 사이 두 번 바뀐 걸 놓침
```

정수 카운터처럼 값 자체만 중요하다면 ABA는 해가 없을 때가 많다. 하지만 *참조*를 CAS로 다루는 락-프리 자료구조(스택, 큐)에서는 치명적일 수 있다. 노드가 해제되었다가 같은 주소로 다시 할당되면 링크가 깨진다. 전통적인 해결책은 값에 버전 번호(스탬프)를 붙여 A(v1)와 A(v3)를 구별하는 것이다(자바의 `AtomicStampedReference`가 이 역할을 한다).

보통은 이런 락-프리 자료구조를 직접 작성하기보다 검증된 라이브러리를 쓰는 것이 맞다. 그래도 "CAS가 성공했으니 아무도 건드리지 않았다"는 추론이 항상 참은 아니라는 점은 기억해야 한다.

> [!note] 명세 기준
> JVM에서 참조를 CAS로 다룰 때 ABA가 실제 메모리 손상으로 이어지지 않는 이유 중 하나는 GC이다. X가 A를 참조하고 있는 동안에는 그 객체가 회수되지 않으므로, 같은 주소를 다른 객체가 재사용하는 C/C++식 시나리오가 생기지 않는다. 그래도 "논리적 상태가 A→B→A로 돌아왔다"는 의미상의 ABA는 여전히 발생하며, 이것이 알고리즘의 불변식을 깰 수 있다.

## 8. 불변성과 안전한 공개: 가장 강력한 도구

### 8.1 공유하지 않거나, 바꾸지 않거나

지금까지 본 도구(volatile, 락, 원자적 타입)는 모두 "공유 가변 상태를 *조심스럽게* 다루는" 방법이었다. 그런데 동시성 버그는 "공유"와 "가변"이 *겹치는* 곳에서 생긴다. 둘 중 하나만 없애도 문제가 사라진다.

```text
        공유됨          공유 안 됨
      ┌──────────┬──────────────┐
가변  │ 위험!!!   │ 안전 (지역 변수, │
      │ (경쟁 상태)│  스레드 전용)   │
      ├──────────┼──────────────┤
불변  │ 안전     │ 안전          │
      │ (불변 공유)│              │
      └──────────┴──────────────┘
```

- **공유 없애기**: 각 스레드나 코루틴이 자기만의 상태를 갖게 한다(스레드 한정, thread confinement). 코루틴에서 단일 스레드 디스패처 안에 상태를 가두는 것이 이 전략이다.
- **가변성 없애기**: 데이터를 실제로 불변으로 만든다. 불변 객체는 여러 스레드가 얼마든지 읽어도 안전하다(4.4절의 final 필드 보장).

Kotlin에서는 두 번째 방법이 특히 효과적이다. `val` 프로퍼티(11장 변수와 초기화)와, 값을 바꾸는 대신 새 객체를 만드는 [[27 - 데이터 클래스]]의 `copy` 관례 덕분에 불변 데이터 모델링이 자연스럽다.

```kotlin
data class Point(val x: Int, val y: Int)   // 완전 불변 (x, y가 원시 val)

val origin = Point(0, 0)
// 여러 스레드가 origin을 읽어도 안전. "이동"은 새 객체 생성:
val moved = origin.copy(x = origin.x + 1)
```

### 8.2 얕은 불변성의 함정

그러나 여기에는 27장(데이터 클래스)에서 배운 함정이 숨어 있다. **`copy`는 얕은 복사(shallow copy)** 이고, `val`은 참조만 고정한다(11장 변수와 초기화).

```kotlin
data class Team(val name: String, val members: MutableList<String>)
//                                 ↑ 가변 리스트를 품은 "불변" data class

val t = Team("A", mutableListOf("kim"))
// t는 val이고 data class지만...
t.members.add("lee")   // 컴파일 OK! 내부 가변 상태가 노출됨

// 두 스레드가 t.members에 동시에 add → 경쟁 상태 (Team이 "불변"처럼 보여도)
```

"불변 객체는 안전하다"는 명제는 **실제로(깊은 수준까지) 불변일 때만** 성립한다. `val`이 가변 컬렉션이나 가변 객체를 가리키면, 겉으로만 불변일 뿐 실제로는 공유 가변 상태이다. 진정한 불변성을 원한다면 다음 방법을 쓴다.

- 가변 컬렉션 대신 읽기 전용 인터페이스로 노출하되([[38 - 컬렉션 - 읽기 전용과 가변]]), *기반 컬렉션이 정말 불변인지* 확인해야 한다. `listOf(...)`가 반환하는 것은 읽기 전용 *뷰*일 뿐이어서, 기반이 가변이면 뒤에서 바뀔 수 있다.
- 생성할 때 방어적 복사(`members.toList()`)를 해서 외부 참조와의 연결을 끊는다.
- 실제 불변 컬렉션이 필요하면 kotlinx.collections.immutable 같은 영속(persistent) 컬렉션을 쓴다.

> [!warning] 흔한 오해
> "`listOf`로 만들면 불변이므로 스레드 안전하다"는 생각은 틀렸다(38장 컬렉션). `List`는 *읽기 전용 인터페이스*이지 불변 자료구조가 아니다. `val ro: List<Int> = mutableListOf(1,2,3)`처럼 가변 인스턴스를 읽기 전용 타입으로 참조할 수 있다.
>
> 이때 원래의 가변 참조를 가진 코드가 뒤에서 수정하면, 그 변화가 `ro`를 통해서도 보인다. 읽기 전용 참조는 *불변성을 보장하는 것이 아니라 할 수 있는 일을 제한할* 뿐이다.

### 8.3 `by lazy`와 스레드 안전한 초기화

지연 초기화에서는 동시성과 불변성이 함께 문제가 된다. 23장(위임 프로퍼티)의 `by lazy`는 세 가지 스레드 모드를 제공한다.

```kotlin
// 1) 기본: 스레드 안전. 여러 스레드가 동시에 접근해도 초기화는 정확히 한 번.
val a: Heavy by lazy { Heavy() }                          // LazyThreadSafetyMode.SYNCHRONIZED

// 2) 여러 스레드가 동시에 초기화를 시도할 수 있지만, 첫 성공값만 채택.
val b: Heavy by lazy(LazyThreadSafetyMode.PUBLICATION) { Heavy() }

// 3) 동기화 없음. 단일 스레드 전용. 다중 스레드에서 쓰면 미정의.
val c: Heavy by lazy(LazyThreadSafetyMode.NONE) { Heavy() }
```

- `SYNCHRONIZED`(기본): 내부적으로 락을 써서 초기화를 정확히 한 번만 하고, 결과를 안전하게 발행한다. 5.3절의 더블 체크 잠금을 표준 라이브러리가 대신 구현한 것이다.
- `PUBLICATION`: 여러 스레드가 동시에 `Heavy()`를 만들 수 있지만, CAS로 처음 성공한 값을 확정하고 나머지는 버린다. 초기화에 부작용이 없고 값만 필요할 때 쓴다.
- `NONE`: 동기화 비용은 0이지만 다중 스레드 안전성이 없다. 단일 스레드에서만 쓴다는 것이 확실할 때 사용한다.

이와 관련해 [[28 - object와 companion - 싱글턴과 동반 객체]]의 `object` 선언은 JVM 백엔드에서 **클래스 초기화(class initialization)의 스레드 안전성**에 의존한다. JVM은 클래스를 처음 사용할 때 클래스 로더 락으로 정적 초기화를 정확히 한 번만 수행한다고 보장한다.

그래서 `object Singleton`은 별도 동기화 없이도 지연 초기화되며, 스레드 안전하게 초기화된다. `object`가 "정적 클래스일 뿐"이 아니라 *스레드 안전하게 발행되는 실제 인스턴스*라는 점이 여기서 동시성 측면의 보장으로 이어진다.

## 9. Kotlin/Native의 메모리 모델: 동결에서 자유로운 공유로

### 9.1 Native는 왜 달랐는가

지금까지의 규칙은 JVM 백엔드의 이야기였다. LLVM 기반으로 네이티브 컴파일하는 Kotlin/Native(1장 코틀린이란 무엇인가)에는 JVM이 없으므로 JMM도 없다. 대신 자체 메모리 관리자가 규칙을 정한다. 그리고 그 규칙은 역사적으로 *두 번* 크게 바뀌었다.

초기 Kotlin/Native(대략 2017~2021)는 **동결(freezing) 기반의 엄격한 모델**을 썼다. 기본 원칙은 "스레드 사이에 공유되는 객체는 반드시 불변(frozen)이어야 한다"는 급진적인 것이었다. 구체적으로는 다음과 같았다.

- 객체를 다른 스레드로 넘기려면 `freeze()`로 동결해야 했고, 동결된 객체를 수정하려고 하면 `InvalidMutabilityException`이 발생했다.
- 각 스레드는 자기만의 가변 객체 그래프를 가졌고, 공유는 불변 그래프나 원자 참조(`AtomicReference` 등)로만 할 수 있었다.
- 최상위 `val`은 기본적으로 동결되었다. 스레드별 가변 전역 상태가 필요하면 `@ThreadLocal`을, 불변 공유 전역 상태에는 `@SharedImmutable`을 붙였다.

```kotlin
// [구 동결 모델 — 현재는 폐기된 개념, 역사적 설명]
// val config = Config(...)     // 다른 스레드로 넘기려면 config.freeze() 필요
// config.freeze()              // 이후 config를 수정하면 InvalidMutabilityException
```

이 모델은 데이터 경쟁을 *컴파일 시점과 런타임에 강하게* 배제했지만, 그 대신 개발자에게 큰 인지 부담을 주었다. 공유 상태를 다루기가 매우 까다로웠고, JVM 코드를 Native로 옮기면 곳곳에서 동결 예외가 발생했다. 특히 여러 스레드에 걸쳐 코루틴을 쓰기가 무척 어려웠다.

### 9.2 새 메모리 관리자 (현행)

이런 부담 때문에 JetBrains는 **새 메모리 관리자(new memory manager)** 를 도입해 기본값으로 삼았다(대략 Kotlin 1.7.20부터 기본값이 되었고, 이후 안정화되었다). 새 모델의 핵심 변화는 다음과 같다.

- **동결이 필요 없다.** JVM처럼 가변 객체를 스레드 사이에 자유롭게 공유할 수 있다. `freeze()`와 `@SharedImmutable`은 폐기(deprecated) 대상이 되었다.
- 추적 기반 가비지 컬렉터(tracing GC)를 도입해 순환 참조를 처리하고, 스레드 사이의 객체 이동 제약을 없앴다.
- 대신 **JVM처럼 데이터 경쟁에 대한 책임이 다시 개발자에게 돌아왔다.** 이제 Native에서도 공유 가변 상태를 `@Volatile`, 원자적 타입, 적절한 동기화로 보호해야 한다. "동결이 대신 막아 주던" 안전장치가 사라진 대가이다.

즉 **Kotlin/Native의 동시성 모델은 이제 개념적으로 JVM과 비슷해졌다.** 이 장에서 다룬 원자성, 가시성, happens-before에 대한 직관은 세부 구현은 다르더라도 Native에도 대체로 적용된다.

`kotlin.concurrent.atomics`가 멀티플랫폼 공통으로 제공되는 이유도 여기에 있다. 같은 API가 JVM에서는 `java.util.concurrent.atomic`으로, Native에서는 네이티브 원자 연산으로 구현되므로, 공통 코드는 하나의 모델로 생각하고 작성할 수 있다.

> [!info] 역사 메모
> 초기 동결 모델은 "공유하려면 불변이어야 한다"는 깔끔한 원칙을 언어 차원에서 강제한 과감한 실험이었다. 이론적으로는 데이터 경쟁을 원천적으로 막았지만, 실용성 면에서 치른 대가가 너무 컸다. 새 모델로의 전환은 Kotlin의 실용주의 철학(1장 코틀린이란 무엇인가)이 이상보다 개발자 경험을 택한 대표적인 사례이다. 다만 `@ThreadLocal`처럼 스레드별 상태를 명시하는 도구는 새 모델에서도 유효하다.

### 9.3 `@ThreadLocal`과 전역 상태

Native에서 최상위 프로퍼티를 초기화하고 공유하는 방식은 JVM과 미묘하게 다르다. `@ThreadLocal`을 붙이면 그 전역 상태는 스레드마다 독립된 복사본을 갖는다. "공유하지 않기"(8.1절) 전략을 전역 수준에서 구현하는 도구이다.

세부적인 초기화 시점과 규칙은 Kotlin/Native 버전에 따라 달라질 수 있다. 따라서 멀티플랫폼 라이브러리를 작성할 때는 전역 가변 상태 자체를 피하고, 필요한 상태를 명시적으로 주입하는 편이 안전하다. 이 주제의 자세한 내용은 [[46 - 멀티플랫폼과 진화와 어두운 구석]]에서 다룬다.

## 10. 코루틴과 메모리 모델: 상위 추상화는 하부 원리를 대부분 감춘다

### 10.1 코루틴은 스레드 관리를 추상화하지만, 공유 상태 문제는 그대로 남는다

이 장의 내용을 42장(suspend와 코루틴)과 연결해 보자. 코루틴은 "스레드를 몇 개, 어떻게 쓰는가"를 디스패처 뒤로 감춘다. 그래서 실무에서는 대부분의 동시성 코드를 생 `Thread` 대신 코루틴으로 작성한다. 하지만 suspend는 중단할 수 있다는 뜻일 뿐이므로, **코루틴이 메모리 모델 문제를 없애 주지는 않는다**.

```kotlin
// 개념 예시 (kotlinx.coroutines)
var counter = 0   // 공유 가변 상태

// 여러 코루틴이 멀티스레드 디스패처(Dispatchers.Default)에서 병렬 실행되면
// 아래 counter++ 는 3절과 똑같은 경쟁 상태다. suspend가 지켜 주지 않는다.
// launch { repeat(1000) { counter++ } }  ← 여전히 잃어버린 갱신 발생
```

`Dispatchers.Default`처럼 여러 스레드를 쓰는 디스패처에서는 코루틴들이 *실제로 병렬*로 실행된다. 그 위에서 공유 `var`를 건드리면 이 장의 모든 규칙(원자성, 가시성)이 그대로 적용된다. 코루틴은 스레드를 아껴 줄 뿐, 병렬 실행이 만드는 하드웨어 수준의 문제를 없애지는 못한다.

### 10.2 코루틴이 제공하는 세 가지 해법

그렇다면 코루틴을 쓸 때는 이 장의 문제를 어떻게 다루는가? 방법은 세 가지이며, 모두 8.1절의 "공유하지 않거나 바꾸지 않거나"를 응용한 것이다.

1. **스레드 한정(confinement)**: 단일 스레드 디스패처 안에 상태를 가둔다. `newSingleThreadContext`나 `Dispatchers.Main` 같은 단일 스레드에서만 상태를 건드리면 병렬성이 없으므로 경쟁이 원천적으로 차단된다.
2. **불변 데이터 전달**: 코루틴 사이에 가변 상태를 공유하는 대신, 불변 메시지를 `Channel`이나 `Flow`로 흘려보낸다(8.2절의 불변성 전략).
3. **명시적 상호 배제**: 공유 가변 상태가 꼭 필요하면 `Mutex`나 원자적 타입을 쓴다. `Mutex`는 코루틴에 맞춘 락으로, 잠금을 기다리는 동안 스레드를 블로킹하지 않고 코루틴만 중단한다.

`CoroutineScope`로 생명주기를 묶는 구조적 동시성이나 `Mutex`/`Semaphore`의 정확한 사용법 같은 실전 설계는 이 장에서 다루지 않는다. 이런 내용은 Kotlin Coroutines 시리즈 6장(CoroutineScope와 구조적 동시성)과 18장(공유 상태와 동기화)에서 다룬다. 이 장에서 설명한 것은 *그런 도구가 왜 필요한가*, 즉 병렬 실행이 원자성, 가시성, 순서를 어떻게 위협하는가라는 하부 원리였다.

### 10.3 `Mutex`와 `synchronized`의 차이

마지막으로 실무에서 중요한 차이를 하나 짚어 두자. 6절의 `synchronized`/`@Synchronized`는 **스레드를 블로킹**한다. 락을 잡지 못하면 그 스레드가 잠들어 다른 코루틴을 실행하지 못한다. 코루틴 위에서 `synchronized`를 쓰면 비용이 큰 스레드 하나가 통째로 묶이므로 코루틴의 이점이 줄어든다. 반면 `Mutex.withLock`은 락을 기다리는 동안 코루틴만 *중단*하고, 스레드는 다른 코루틴을 계속 실행한다.

```text
[synchronized]  락 대기 → 스레드 블로킹 → 그 스레드의 다른 코루틴도 정지
[Mutex]         락 대기 → 코루틴 중단(suspend) → 스레드는 다른 코루틴 실행
```

즉 어떤 도구를 고를지는 "스레드 기반 코드인가, 코루틴 기반 코드인가"에 달려 있다. 순수 스레드 코드에는 `synchronized`가, 코루틴 코드에는 `Mutex`가 맞다. 둘 다 이 장에서 본 같은 원리(happens-before 확립)로 같은 목적(상호 배제)을 달성하지만, 기다리는 방식이 다르다.
