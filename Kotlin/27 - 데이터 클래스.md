[[21 - 클래스와 생성자]]에서는 주 생성자, `init` 블록, 프로퍼티 초기화 순서를 따라가며 클래스가 만들어지는 과정을 기계 수준에서 살펴봤다. [[22 - 프로퍼티와 백킹 필드]]에서는 프로퍼티가 실제로는 필드가 아니라 접근자(get/set)를 추상화한 것이고, 백킹 필드는 필요할 때만 생긴다는 점을 확인했다. [[10 - 불리언과 동등성과 동일성]]에서는 `==`가 `equals`를 호출하는 구조적 동등이고 `===`가 참조 동일이라는 Kotlin의 두 가지 비교 체계를 정리했다.

이 장은 이 세 주제를 하나로 묶는다. 데이터 클래스는 값을 담는 클래스에 반복해서 필요한 `equals`/`hashCode`/`toString` 같은 보일러플레이트를, 주 생성자의 프로퍼티를 기준으로 컴파일러가 대신 만들어 주는 장치이기 때문이다.

이 장에서는 데이터 클래스를 손으로 쓴 동등한 클래스로 풀어 쓴(desugar) 뒤, 자동 생성되는 멤버의 정확한 규칙을 명세 수준에서 하나씩 살펴본다. 그 과정에서 초심자가 자주 틀리는 두 가지, 즉 **주 생성자 프로퍼티만 생성 멤버에 참여한다**는 점과 **copy는 얕은 복사**라는 점을 바로잡는다. 이어서 데이터 클래스가 `final`인 이유와 배열, 부동소수점, 상속에서 생기는 함정을 다루고, `data object`와 데이터 클래스를 쓰지 말아야 할 경우로 마무리한다.

구조 분해 선언의 문법과 위치 기반 함정은 [[20 - 구조 분해]]에서, 싱글턴으로서의 `object`는 [[28 - object와 companion - 싱글턴과 동반 객체]]에서, 대수적 데이터 타입에서 데이터 클래스가 곱타입(product type) 역할을 하는 큰 그림은 [[30 - sealed 클래스와 대수적 데이터 타입]]에서 다룬다.

## 1. 데이터 클래스란 무엇인가: 컴파일러가 대신 작성하는 코드

### 1.1 문제: 값을 담는 클래스의 반복 작업

프로그램의 상당 부분은 데이터를 담기만 하는 클래스로 이루어진다. 2차원 좌표, 사람의 이름과 나이, 은행 계좌의 번호와 잔액 같은 것들은 행위(behavior)보다 상태(state)가 핵심이다. 이런 클래스를 제대로 만들려면 Java든 다른 언어든 매번 같은 작업을 반복해야 한다.

- 두 좌표가 같은지 판단하려면 필드별로 비교하도록 `equals`를 재정의해야 한다.
- 해시 기반 컬렉션(`HashSet`, `HashMap`)에 넣으려면 `equals`와 일관된 `hashCode`를 재정의해야 한다.
- 디버깅할 때 사람이 읽을 수 있도록 `toString`이 필요하다.
- 불변 객체의 일부만 바꿔 새로 만들려면 "복사한 뒤 일부를 변경하는" 메서드가 필요하다.

이런 보일러플레이트를 손으로 쓰는 일은 지루할 뿐 아니라 *위험하다*. 필드를 하나 추가하고 `equals`에 반영하지 않으면 서로 다른 두 객체가 같다고 판정되고, `hashCode`에 반영하지 않으면 `HashMap`에서 값을 찾지 못하게 된다. 이런 오류는 컴파일러가 잡아 주지 않는다.

```kotlin
// data 없이 손으로 쓴 값 클래스 — 지루하고, 실수하기 쉽다
class Point(val x: Int, val y: Int) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true
        if (other !is Point) return false
        return x == other.x && y == other.y
    }
    override fun hashCode(): Int = 31 * x + y
    override fun toString(): String = "Point(x=$x, y=$y)"
    fun copy(x: Int = this.x, y: Int = this.y): Point = Point(x, y)
}
```

### 1.2 해법: `data` 수식어 하나

Kotlin은 이 반복 작업을 언어 기능으로 처리한다. 클래스 선언 앞에 `data` 수식어(modifier)를 붙이면 컴파일러가 위 코드를 *자동으로* 생성한다.

```kotlin
data class Point(val x: Int, val y: Int)

fun main() {
    val a = Point(1, 2)
    val b = Point(1, 2)
    println(a)          // => Point(x=1, y=2)   (toString)
    println(a == b)     // => true              (equals: 구조적 동등)
    println(a === b)    // => false             (참조는 다름)
    println(a.hashCode() == b.hashCode())  // => true  (hashCode 일관성)
    val c = a.copy(y = 99)
    println(c)          // => Point(x=1, y=99)  (copy + 일부 변경)
    val (x, y) = a      // 구조 분해 (component1/component2)
    println("$x, $y")   // => 1, 2
}
```

`data`는 마법이 아니다. **컴파일러가 주 생성자의 프로퍼티를 기준으로 여섯 개의 멤버를 생성(codegen)하도록 지시하는 수식어**이다. 생성되는 멤버를 정리하면 다음과 같다.

| 멤버 | 역할 | 생성 근거 |
|------|------|-----------|
| `equals(other): Boolean` | 구조적 동등 | 주 생성자 프로퍼티 순서대로 `==` 비교 |
| `hashCode(): Int` | 해시 코드 | 주 생성자 프로퍼티들의 해시 조합 |
| `toString(): String` | 문자열 표현 | `클래스명(prop1=값, prop2=값, ...)` |
| `componentN(): Tn` | 구조 분해용 | 주 생성자 각 프로퍼티마다 하나씩 |
| `copy(...): T` | 부분 변경 복사 | 각 프로퍼티를 기본 인자로 갖는 팩토리 |

> [!note] 명세 기준
> 이 멤버들 가운데 `equals`/`hashCode`/`toString`은 컴파일러가 생성하지만, **개발자가 직접 선언하면 생성을 건너뛴다**. 즉 자동 생성은 멤버가 없을 때만 채워 넣는 방식이다. 반면 `componentN`과 `copy`는 개발자가 직접 정의하는 것이 **금지되거나(component) 충돌 시 경고/에러(copy)** 로 처리되므로 사실상 컴파일러만 만들 수 있다. 이 비대칭은 뒤에서 다시 살펴본다.

### 1.3 풀어 쓰기: 컴파일러가 보는 데이터 클래스

`data class Point(val x: Int, val y: Int)`를 JVM 백엔드로 컴파일하면, 1.1절에서 손으로 쓴 클래스와 거의 같은 바이트코드가 나온다. 여기에 `component1()`과 `component2()`가 추가된다. IntelliJ의 "Kotlin bytecode → Decompile" 기능으로 직접 확인할 수 있으며, 개념적으로는 다음과 같다.

```text
data class Point(val x, val y)
        │
        │  K2 프론트엔드(FIR): data 수식어 인지
        │  → 없는 멤버 목록 계산: equals, hashCode, toString,
        │    component1, component2, copy
        │
        ▼  IR 단계에서 각 멤버의 본문을 합성(synthesize)
   ┌─────────────────────────────────────────┐
   │ equals    : this===other || (Point이고   │
   │             x,y가 각각 ==)               │
   │ hashCode  : x.hashCode()*31 + y.hashCode()│
   │ toString  : "Point(x=" + x + ", y=" + y +")"│
   │ component1: x                            │
   │ component2: y                            │
   │ copy      : (x=this.x, y=this.y)->Point  │
   └─────────────────────────────────────────┘
        │
        ▼  JVM 백엔드 → Point.class (일반 final 클래스)
```

핵심은 데이터 클래스가 런타임에 특별한 종류의 객체가 *아니라는* 점이다. `Point`는 평범한 `final` 클래스이고, 생성된 멤버도 평범한 메서드이다. `data`는 순수하게 **컴파일 타임의 코드 생성 지시자**일 뿐이다.

런타임에 데이터 클래스임을 나타내는 플래그나 특별한 인터페이스는 없다. 리플렉션에서 `KClass.isData`로 데이터 클래스인지 조회할 수는 있지만, 이것은 메타데이터일 뿐 동작을 바꾸지 않는다. 이 사실은 뒤에서 "리플렉션 없이는 임의의 두 데이터 클래스를 일반화해 다룰 수 없는 이유"를 이해하는 열쇠가 된다.

## 2. `equals`와 `hashCode`: 자동 생성의 세부 규칙

### 2.1 생성되는 `equals`의 정확한 형태

컴파일러가 만드는 `equals`는 10장(불리언과 동등성과 동일성)에서 정리한 `equals` 계약(반사성, 대칭성, 추이성, 일관성, null 처리)을 지키도록 설계되어 있다. 그 골격은 항상 다음 순서를 따른다.

```kotlin
override fun equals(other: Any?): Boolean {
    if (this === other) return true      // 1) 참조가 같으면 즉시 true (최적화 + 반사성)
    if (other !is Point) return false    // 2) 타입이 다르면 false (null도 여기서 false)
    // 3) 주 생성자 프로퍼티를 순서대로 == 비교
    if (x != other.x) return false
    if (y != other.y) return false
    return true
}
```

세 단계에는 각각 의미가 있다.

- 1단계 `this === other`는 성능 최적화이면서 반사성(`a == a`는 항상 참)을 보장한다.
- 2단계 `other !is Point`는 타입 검사이다. Kotlin의 `is`는 null에 대해 false를 돌려주므로, `other`가 `null`이면 자동으로 `false`가 되어 null 처리 계약도 만족한다.
- 3단계는 각 프로퍼티를 `==`, 즉 그 프로퍼티 타입의 `equals`로 비교한다.

3단계의 `!=`는 `==`의 부정이고 `==`는 다시 `equals`를 호출하므로, **중첩된 값의 동등성은 재귀적으로 그 값의 `equals`가 판단한다**. `Point`가 다른 데이터 클래스를 프로퍼티로 가지고 있다면, 그 프로퍼티의 자동 생성 `equals`가 다시 호출된다.

> [!warning] 흔한 오해
> "데이터 클래스의 `equals`는 모든 필드를 비교한다"는 요약은 **틀렸다**. 정확히는 **주 생성자에 선언된 프로퍼티만** 비교하고, 클래스 본문에 선언한 프로퍼티는 제외한다. 이 내용은 3절에서 자세히 살펴본다.

### 2.2 생성되는 `hashCode`의 형태와 31을 쓰는 이유

`hashCode`는 주 생성자 프로퍼티들의 해시 코드를 조합해 만든다. 관례적으로 첫 프로퍼티부터 시작해 `result = result * 31 + next.hashCode()` 형태로 누적한다.

```kotlin
override fun hashCode(): Int {
    var result = x.hashCode()   // (Int의 hashCode는 자기 자신 값)
    result = 31 * result + y.hashCode()
    return result
}
```

곱셈 상수로 31을 쓰는 데에는 수학적인 이유가 있다. 31은 홀수이면서 소수(prime)이고, $31 = 2^5 - 1$이므로 곱셈을 시프트와 뺄셈($31 \cdot n = (n \ll 5) - n$)으로 최적화할 수 있다. 홀수 소수를 곱하면 필드 배치가 다를 때 해시가 서로 다르게 흩어질 가능성이 높아서 해시 충돌이 줄어든다.

다만 이 상수와 알고리즘의 세부는 **컴파일러 구현에 맡겨진 부분**이며 명세가 정한 것이 아니다. 보장되는 것은 "**`equals`로 같은 두 객체는 반드시 같은 `hashCode`를 낸다**"는 계약뿐이다.

이 계약이 왜 중요한지는 해시 컬렉션의 동작을 보면 알 수 있다.

```kotlin
data class Point(val x: Int, val y: Int)

fun main() {
    val set = HashSet<Point>()
    set.add(Point(1, 2))
    println(Point(1, 2) in set)   // => true
    // 이것이 동작하는 이유:
    //  1) Point(1,2).hashCode()가 두 번 다 같음 → 같은 버킷을 찾아감
    //  2) 버킷 안에서 equals가 true → 같은 원소로 인정
}
```

데이터 클래스가 아니고 손으로 `equals`만 재정의하고 `hashCode`는 재정의하지 않았다면, 두 `Point(1,2)`는 `Object`의 기본 identity 해시가 서로 달라 다른 버킷으로 들어간다. 그러면 `in` 검사가 `false`가 되어 값을 "잃어버린다". 데이터 클래스는 `equals`와 `hashCode`를 항상 *짝으로* 생성하므로 이런 함정이 처음부터 생기지 않는다. 그래서 데이터 클래스는 `HashMap`의 키나 `Set`의 원소로 안심하고 쓸 수 있다.

> [!note] 명세 기준
> JVM 백엔드에서 `Int.hashCode()`는 그 정수 값 자체이다. `Long.hashCode()`는 `(value xor (value ushr 32))`의 하위 32비트이고, `String.hashCode()`는 `s[0]*31^(n-1) + s[1]*31^(n-2) + ...`이다. 데이터 클래스는 각 프로퍼티의 이런 `hashCode`를 호출할 뿐, 새로운 해시 알고리즘을 만들지 않는다. 따라서 프로퍼티 타입의 `hashCode`가 나쁘면 데이터 클래스의 `hashCode`도 나쁘다.

### 2.3 부분 재정의: 일부만 직접 작성하기

데이터 클래스에서 개발자가 `equals`/`hashCode`/`toString` 중 일부를 직접 선언하면, 컴파일러는 **그 멤버만** 생성하지 않고 나머지는 그대로 생성한다. 이 규칙은 편리하지만 함정이 되기도 한다.

```kotlin
data class CaseInsensitiveName(val value: String) {
    // equals만 대소문자 무시로 재정의
    override fun equals(other: Any?): Boolean =
        other is CaseInsensitiveName &&
        value.equals(other.value, ignoreCase = true)
    // hashCode는 자동 생성 그대로 → value의 대소문자를 구분!
}

fun main() {
    val a = CaseInsensitiveName("Hello")
    val b = CaseInsensitiveName("hello")
    println(a == b)                        // => true  (내 equals)
    println(a.hashCode() == b.hashCode())  // => false (자동 hashCode: "Hello" vs "hello")
    val set = hashSetOf(a)
    println(b in set)                      // => false! equals는 같다는데 못 찾음
}
```

`equals`만 바꾸고 `hashCode`는 자동 생성에 맡기면 계약이 깨진다. `a == b`인데 `a.hashCode() != b.hashCode()`이므로, 해시 컬렉션에서 두 객체가 서로 다른 버킷으로 가고 `b in set`이 실패한다. **`equals`를 직접 바꾸면 `hashCode`도 반드시 함께 바꿔야 한다.** 데이터 클래스도 이 규칙에서 예외가 아니다. 부분 재정의는 컴파일러가 빈칸을 채워 주는 편의 기능일 뿐, 계약 위반까지 막아 주지는 않는다.

## 3. 주 생성자 프로퍼티만 참여한다

### 3.1 흔한 오해 바로잡기

**"데이터 클래스는 완전한 값 타입이므로, 클래스가 가진 모든 상태가 동등성에 참여한다."** 데이터 클래스에 관한 오해 가운데 가장 흔하고 대가도 가장 큰 오해이다. 사실은 분명하다. **`equals`·`hashCode`·`toString`·`componentN`·`copy`는 주 생성자(primary constructor)에 선언된 프로퍼티만 사용한다.** 클래스 본문(중괄호 안)에 선언한 프로퍼티는 이 다섯 멤버 어디에도 참여하지 않는다.

```kotlin
data class User(val id: Int, val name: String) {
    var lastLoginEpoch: Long = 0L    // body 프로퍼티 — 자동 멤버에서 제외됨!
}

fun main() {
    val a = User(1, "Ann").apply { lastLoginEpoch = 1000 }
    val b = User(1, "Ann").apply { lastLoginEpoch = 9999 }

    println(a == b)         // => true!  lastLoginEpoch가 달라도 같다고 판정
    println(a.hashCode() == b.hashCode())  // => true
    println(a)              // => User(id=1, name=Ann)   lastLoginEpoch 안 나옴
    val c = a.copy()
    println(c.lastLoginEpoch)  // => 0   copy는 lastLoginEpoch를 복사 안 함! 기본값 0
}
```

이 코드에서 세 가지를 한꺼번에 확인할 수 있다.

1. `a == b`가 참이다. `lastLoginEpoch`가 1000과 9999로 달라도 두 객체는 동등하다.
2. `toString` 결과에 `lastLoginEpoch`가 없다.
3. 가장 위험한 점으로, `copy()`는 `lastLoginEpoch`를 복사하지 *않고* 프로퍼티 초기화식의 기본값 `0L`로 되돌린다. `copy`의 시그니처는 주 생성자 프로퍼티만 파라미터로 받아 `User(x, y)`를 호출하고, 본문 프로퍼티는 그 과정에서 초기화식으로 다시 설정되기 때문이다.

### 3.2 왜 이렇게 설계했는가

이 규칙은 실수가 아니라 의도된 원칙이다. 데이터 클래스의 자동 멤버는 **주 생성자의 시그니처를 이 객체의 정체성(identity)으로 본다**. 주 생성자는 이 객체를 만드는 데 필요한 값들의 목록이고, 그 값들이 같으면 같은 객체로 본다는 것이 값 의미론(value semantics)의 정의이다.

본문 프로퍼티는 파생 상태(derived state)나 캐시, 가변 부가 정보인 경우가 많아서 동등성의 근거로 삼기에 적절하지 않다. 컴파일러가 이런 프로퍼티까지 자동으로 포함했다면, 캐시 하나 때문에 논리적으로 같은 두 객체가 다르다고 판정되는 더 나쁜 함정이 생겼을 것이다.

> [!note] 명세 기준
> Kotlin 명세는 데이터 클래스의 자동 멤버가 "주 생성자에 선언된 프로퍼티들(properties declared in the primary constructor)"만을 기반으로 한다고 규정한다. 이때 그 프로퍼티는 반드시 `val` 또는 `var`로 선언해야 한다.
>
> 주 생성자에 `val`/`var` 없이 파라미터만 쓰면(`data class C(x: Int)`) 이는 프로퍼티가 아니라 단순한 생성자 파라미터가 된다. 게다가 **데이터 클래스의 주 생성자 파라미터는 전부 `val`/`var`여야 한다**는 제약(6절)이 있으므로 컴파일 에러가 난다.

### 3.3 파생 프로퍼티를 동등성에 넣고 싶다면

본문 프로퍼티를 정말로 동등성에 포함하고 싶다면, 그 값이 원래 값의 본질이라는 뜻이므로 **주 생성자로 옮겨야 한다**. 반대로 파생값을 동등성에서 빼고 싶다면, 그 값을 커스텀 게터를 가진 계산 프로퍼티로 본문에 두면 자연스럽게 제외된다.

```kotlin
// 파생값을 body의 계산 프로퍼티로 → 동등성에서 자동 제외 (백킹 필드 없음)
data class Circle(val radius: Double) {
    val area: Double get() = Math.PI * radius * radius   // 매번 계산, 상태 아님
}

fun main() {
    val a = Circle(2.0)
    val b = Circle(2.0)
    println(a == b)     // => true  (radius만 비교, area는 파생)
    println(a.area)     // => 12.566...
}
```

`area`를 `val area: Double get() = ...`로 두면, 22장(프로퍼티와 백킹 필드)에서 설명한 대로 백킹 필드가 없는 순수 접근자가 된다. 저장된 상태가 아니므로 동등성 판단에서 아예 빠진다. 데이터 클래스에서 파생값을 다루는 관용적인 방법이다.

### 3.4 컴파일러 경고: 애매한 경우

컴파일러는 사용자가 이 규칙을 모르고 실수하는 일을 줄이려고 경고를 보여 준다. 본문에 `equals`/`hashCode`에 참여하지 않는 프로퍼티가 있으면, 이를 알려 주는 경고가 뜰 수 있다(버전과 설정에 따라 다르다). 하지만 경고일 뿐 에러는 아니므로, **규칙 자체를 이해하는 것이 유일한 방어책**이다.

## 4. `copy`와 얕은 복사

### 4.1 `copy`가 만들어지는 형태

`copy`는 데이터 클래스에서 가장 유용한 멤버이며, 불변(immutable) 데이터를 다루는 함수형 스타일의 핵심 도구이다. 컴파일러는 주 생성자 프로퍼티마다 **현재 값을 기본 인자로 삼는** 파라미터를 두어 `copy` 함수를 만든다.

```kotlin
data class Point(val x: Int, val y: Int)

// 컴파일러가 생성하는 copy (개념적):
// fun copy(x: Int = this.x, y: Int = this.y): Point = Point(x, y)

fun main() {
    val p = Point(1, 2)
    val q = p.copy(y = 10)   // x는 기본값(1) 유지, y만 10
    println(q)               // => Point(x=1, y=10)
    val r = p.copy()         // 전부 기본값 → 같은 값의 새 인스턴스
    println(r == p)          // => true
    println(r === p)         // => false  (새 객체)
}
```

덕분에 "불변 객체에서 필드 하나만 바꾼 새 버전"을 이름 붙은 인자로 간결하게 표현할 수 있다. `val`로 선언한 불변 프로퍼티를 재대입 없이 갱신하는 방법 가운데 가장 깔끔한 것이 `copy`이다.

### 4.2 오해 바로잡기: copy는 얕은 복사(shallow copy)이다

**"데이터 클래스의 copy는 깊은 복사(deep copy)이다."** 이것은 위험한 오해이다. 사실 **`copy`는 얕은 복사이다.** `copy`는 주 생성자 프로퍼티들의 *참조(또는 원시값)를 그대로 새 객체에 넘겨* 생성자를 호출할 뿐이다. 프로퍼티가 가변 객체를 가리킨다면 원본과 복사본은 **같은 가변 객체를 공유**한다.

```kotlin
data class Team(val name: String, val members: MutableList<String>)

fun main() {
    val a = Team("Blue", mutableListOf("Ann", "Bob"))
    val b = a.copy()

    println(a == b)                 // => true  (지금은 같은 내용)
    println(a.members === b.members)// => true! 같은 리스트 객체를 공유

    b.members.add("Cara")           // b를 통해 리스트 변경
    println(a.members)              // => [Ann, Bob, Cara]  a도 바뀐다!
    println(a == b)                 // => true  (여전히 같은 리스트를 보므로)
}
```

`b.members.add("Cara")`를 호출하면 `a.members`까지 바뀐다. `copy`가 `members`가 가리키는 `MutableList`를 새로 만들지 않고 같은 참조를 넘겼기 때문이다. `a.members === b.members`가 `true`라는 것이 결정적인 증거이다.

이 함정은 [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 바로잡은 "val은 불변 객체를 만든다"는 오해와 같은 뿌리를 가진다. `val members`는 재대입만 막을 뿐, 리스트 내부는 얼마든지 바뀔 수 있다. 데이터 클래스의 값 의미론은 **필드가 전부 불변이고, 그 필드가 가리키는 것도 불변일 때만** 온전히 성립한다.

```text
copy의 메모리 그림 (얕은 복사)

  a ─────► Team{ name:"Blue", members ─┐
  b ─────► Team{ name:"Blue", members ─┼──► MutableList["Ann","Bob"]
                                       ┘    (하나의 리스트, 둘이 공유!)

  ↑ Team 객체는 둘 (a, b 다름)
    그러나 members가 가리키는 리스트는 하나 → 한쪽 mutate가 양쪽에 보임
```

### 4.3 왜 깊은 복사가 아닌가: 깊은 복사는 정의할 수 없다

컴파일러가 깊은 복사를 하려면 각 프로퍼티 타입을 어떻게 깊이 복사해야 하는지 알아야 한다. 그러나 임의의 타입에 대해 깊은 복사는 일반적으로 정의할 수 없다.

- 순환 참조가 있으면 복제가 끝없이 이어진다.
- `Socket`이나 파일 핸들 같은 자원은 복사한다는 것 자체가 의미가 없다.
- 리스트 안의 원소가 또 가변 객체라면, 그것까지 복사해야 하는지 언어가 결정할 수 없다.

그래서 언어는 유일하게 안전하고 예측 가능한 선택인 **얕은 복사(참조 전달)** 를 택한다. 깊은 복사가 필요하면 개발자가 명시적으로 구성해야 한다.

```kotlin
// 깊은 복사가 필요하면 손으로: 중첩 컬렉션을 새로 만든다
val deep = a.copy(members = a.members.toMutableList())
println(a.members === deep.members)  // => false  독립적
deep.members.add("Zoe")
println(a.members)                   // => [Ann, Bob]  a는 안 바뀜
```

이 문제를 근본적으로 없애는 방법은 **데이터 클래스에 가변 프로퍼티를 넣지 않는 것**이다. `MutableList` 대신 읽기 전용 `List`를 쓰고 원소도 불변 값으로 두면, 얕은 복사와 깊은 복사를 구분할 필요가 없어진다. 공유하더라도 아무도 바꿀 수 없기 때문이다. 이것이 데이터 클래스를 진짜 값처럼 쓰는 정석이다.

> [!caution] 성능 주의
> 얕은 복사이기 때문에 `copy`는 비용이 적다. 새 객체 하나를 할당하고 참조 몇 개를 대입하면 끝난다. 큰 리스트를 담은 데이터 클래스를 `copy`해도 리스트를 복제하지 않으므로 O(1)에 가깝다. 이 점은 함수형 불변 갱신을 값싸게 만드는 장점이지만, 4.2절의 공유 함정과 표리 관계에 있다. 비용이 적은 대신 상태를 공유하게 되는 것이다.

### 4.4 `copy`와 생성자의 미묘한 차이

`copy`는 주 생성자를 호출하므로 **`init` 블록과 프로퍼티 초기화식이 모두 다시 실행된다**(21장 클래스와 생성자에서 본 초기화 순서 그대로이다). 그래서 3.1절에서 봤듯이 본문 프로퍼티는 초기화식의 기본값으로 초기화되고, `init`에 부수 효과(로그, 카운터)가 있으면 copy할 때마다 다시 발생한다. `copy`는 메모리를 그대로 memcpy하는 것이 아니라, 같은 주 생성자 인자로 새 객체를 만드는 것임을 기억해야 한다.

```kotlin
data class Ticket(val id: Int) {
    init { println("Ticket $id created") }
}

fun main() {
    val t = Ticket(1)    // => Ticket 1 created
    val u = t.copy()     // => Ticket 1 created   (init 재실행!)
    val v = t.copy(id = 2) // => Ticket 2 created
}
```

## 5. `toString`과 `componentN`: 나머지 자동 멤버

### 5.1 `toString`의 형식과 쓰임새

자동 생성된 `toString`은 `클래스이름(프로퍼티1=값1, 프로퍼티2=값2, ...)` 형식이며, 주 생성자 프로퍼티만 순서대로 나열한다. 각 값은 그 값의 `toString`으로 문자열이 된다.

```kotlin
data class Account(val number: String, val balance: Long)
data class Portfolio(val owner: String, val accounts: List<Account>)

fun main() {
    val p = Portfolio("Ann", listOf(Account("A-1", 100), Account("A-2", 250)))
    println(p)
    // => Portfolio(owner=Ann, accounts=[Account(number=A-1, balance=100), Account(number=A-2, balance=250)])
}
```

중첩된 데이터 클래스도 재귀적으로 잘 출력되는 것을 볼 수 있다. 이렇게 거저 얻는 `toString`은 디버깅과 로깅에서 매우 유용하다. 손으로 클래스를 만들면 대개 `toString`을 빠뜨려서 `Account@1b6d3586` 같은 쓸모없는 출력이 나온다.

다만 보안 함정이 있다. **민감 정보(비밀번호, 토큰)를 담은 데이터 클래스는 자동 `toString`이 그 값을 로그에 그대로 출력한다.** 그런 필드가 있다면 `toString`을 직접 재정의해 값을 가려야 한다.

```kotlin
data class Credential(val user: String, val secret: String) {
    override fun toString(): String = "Credential(user=$user, secret=***)"
}
```

### 5.2 `componentN`과 구조 분해

주 생성자 프로퍼티마다 `component1()`, `component2()`, ... 함수가 순서대로 생성되며, 이 함수들 덕분에 20장(구조 분해)의 구조 분해 선언을 쓸 수 있다.

```kotlin
data class Point(val x: Int, val y: Int)

fun main() {
    val p = Point(3, 4)
    // 컴파일러: val x = p.component1(); val y = p.component2()
    val (x, y) = p
    println("$x, $y")   // => 3, 4

    // 컬렉션 순회에서도
    val points = listOf(Point(1, 1), Point(2, 4))
    for ((px, py) in points) println(px + py)  // => 2, 6
}
```

여기서 20장에서 다룬 핵심 함정을 다시 떠올려 보자. 구조 분해는 **위치 기반이지 이름 기반이 아니다**. `val (y, x) = p`라고 써도 컴파일러는 `component1`을 첫 번째 변수에, `component2`를 두 번째 변수에 넣는다. 따라서 실제로는 `y`에 x좌표(3)가, `x`에 y좌표(4)가 들어가며, 변수 이름은 무시된다.

리팩터링하면서 데이터 클래스의 프로퍼티 순서를 바꾸면, 구조 분해를 쓰는 모든 곳이 아무 경고 없이 깨진다. 이런 위험이 있으므로 프로퍼티가 3개를 넘으면 구조 분해보다 이름으로 접근하는 편이 안전하다.

> [!info] 역사 메모
> 사용자가 `componentN`을 직접 재정의하지 못하게 컴파일러가 막는 이유는 구조 분해의 위치 계약을 안정적으로 유지하기 위해서이다. 한편 `Pair`, `Triple`, `Map.Entry` 같은 표준 라이브러리 타입도 `componentN`을 제공하는데, 이들은 데이터 클래스이거나 그에 준하게 만들어진 타입이다. `Map`의 엔트리를 구조 분해하는 `for ((k, v) in map)`도 바로 이 관례를 따른다.

### 5.3 `copy`와 `componentN`을 직접 만들 수 없는 이유

`equals`/`hashCode`/`toString`은 직접 재정의할 수 있다. 하지만 `componentN`은 사용자가 직접 선언할 수 없고(같은 시그니처를 만들려고 하면 충돌이나 에러가 난다), `copy`도 데이터 클래스에서 직접 정의하려고 하면 충돌한다.

이런 비대칭이 생기는 이유는 다음과 같다. 앞의 세 멤버는 `Any`에 이미 있는 오버라이드 대상이므로 "재정의"라는 자연스러운 의미가 있다. 반면 `copy`/`componentN`은 데이터 클래스가 새로 도입한 합성 멤버이므로, 사용자 정의와 충돌하면 의미가 모호해진다. 실무적으로 보면, 데이터 클래스의 copy/component 동작이 언제나 컴파일러가 보장하는 표준 형태라는 예측 가능성을 지키는 장치이다.

## 6. 데이터 클래스의 제약 조건: 언어가 강제하는 규칙

데이터 클래스는 아무렇게나 선언할 수 있는 클래스가 아니다. 값 의미론을 지키기 위한 여러 제약이 문법 수준에서 강제된다. 이 제약들을 모아 보면 언어가 데이터 클래스를 무엇으로 보는지가 드러난다.

### 6.1 주 생성자가 필수이고, 파라미터는 전부 `val`/`var`

데이터 클래스는 **반드시 주 생성자를 가져야 하고, 주 생성자에 파라미터가 하나 이상 있어야 하며, 그 파라미터는 전부 `val` 또는 `var`로 표시**해야 한다.

```kotlin
data class Empty()                 // 컴파일 에러: data class는 최소 하나의 주 생성자 파라미터 필요
data class Bad(x: Int)             // 컴파일 에러: 파라미터가 val/var가 아님
data class Good(val x: Int)        // OK
data class AlsoOk(var x: Int, val y: String)  // OK (var도 허용)
```

이 규칙은 자연스럽다. 자동 멤버는 주 생성자 프로퍼티를 기준으로 만들어지는데, 파라미터가 프로퍼티가 아닌 단순 파라미터라면 `equals`가 참조할 상태가 없다. 그래서 언어는 파라미터가 전부 프로퍼티여야 한다고 규정한다.

### 6.2 `final`이다: open/abstract/sealed/inner 불가

데이터 클래스는 **암묵적으로 `final`이며, `open`·`abstract`·`sealed`·`inner`로 만들 수 없다**. 다른 클래스가 데이터 클래스를 상속할 수 없다는 뜻이다.

```kotlin
open data class Base(val x: Int)   // 컴파일 에러: data class는 open일 수 없음
abstract data class A(val x: Int)  // 컴파일 에러
```

이 제약이 왜 반드시 필요한지는 7절에서 `equals`의 대칭성을 통해 자세히 설명한다. 간단히 말하면, 상속을 허용하면 "부모 타입으로 본 자식"과 "자식으로 본 부모"를 비교할 때 대칭성이 깨질 수밖에 없기 때문이다.

반면 데이터 클래스가 **다른 클래스나 인터페이스를 상속(구현)하는 것은 가능**하다. 자신이 final이라 자식을 가질 수 없을 뿐, 부모는 가질 수 있다.

```kotlin
interface Named { val name: String }
data class Dog(override val name: String, val breed: String) : Named   // OK
```

### 6.3 부생성자와 `init`은 허용되지만, 자동 멤버는 여전히 주 생성자 기준

데이터 클래스에도 `init` 블록과 부생성자(secondary constructor)를 둘 수 있다. 다만 부생성자는 21장(클래스와 생성자)의 규칙대로 결국 주 생성자에 위임(`this(...)`)해야 한다. 또한 자동 멤버가 주 생성자 프로퍼티만 본다는 사실은 달라지지 않는다.

```kotlin
data class Temperature(val celsius: Double) {
    constructor(fahrenheit: Int) : this((fahrenheit - 32) / 1.8)  // 주 생성자로 위임
    init { require(celsius >= -273.15) { "절대영도 미만 불가" } }
}

fun main() {
    val t = Temperature(fahrenheit = 212)
    println(t)   // => Temperature(celsius=100.0)
}
```

### 6.4 제약 요약

| 항목 | 규칙 | 이유 |
|------|------|------|
| 주 생성자 | 필수, 파라미터 ≥ 1 | 자동 멤버의 근거 필요 |
| 주 생성자 파라미터 | 전부 `val`/`var` | 전부 프로퍼티여야 함 |
| 상속 가능성 | `final` 고정 (open/abstract/sealed 불가) | equals 대칭성 보전 |
| inner | 불가 | 값 타입 성격과 충돌 |
| 부모 갖기 | 클래스/인터페이스 상속 가능 | 자기만 final이면 됨 |
| body 프로퍼티 | 허용, 그러나 자동 멤버 제외 | 주 생성자 프로퍼티만 참여(3절) |
| `init`/부생성자 | 허용 | 주 생성자로 위임 |

## 7. 데이터 클래스와 상속: 왜 `final`이어야 하는가

### 7.1 상속과 `equals` 대칭성의 근본적인 충돌

6.2절에서 데이터 클래스는 `final`이라고 했다. 이는 임의로 정한 제약이 아니다. `equals` 계약(10장 불리언과 동등성과 동일성)의 **대칭성(symmetry)**, 즉 `a == b`이면 `b == a`라는 성질을 지키려면 논리적으로 이렇게 될 수밖에 없다. 상속을 허용하면 자동 `equals`가 왜 대칭성을 깰 수밖에 없는지, 손으로 쓴 코드로 사고 실험을 해 보자.

`data class`가 아니라, 상속 가능한 값 클래스를 손으로 만들었다고 가정한다.

```kotlin
open class Point2D(open val x: Int, open val y: Int) {
    override fun equals(other: Any?): Boolean {
        if (other !is Point2D) return false
        return x == other.x && y == other.y   // x, y만 비교
    }
    override fun hashCode() = 31 * x + y
}

class Point3D(x: Int, y: Int, val z: Int) : Point2D(x, y) {
    override fun equals(other: Any?): Boolean {
        if (other !is Point3D) return false
        return x == other.x && y == other.y && z == other.z   // z까지 비교
    }
    override fun hashCode() = 31 * (31 * x + y) + z
}

fun main() {
    val a = Point2D(1, 2)
    val b = Point3D(1, 2, 3)
    println(a == b)   // => true!  Point2D.equals: b는 Point2D이고 x,y 같음
    println(b == a)   // => false! Point3D.equals: a는 Point3D가 아님
    // 대칭성 붕괴: a==b 는 true 인데 b==a 는 false
}
```

`a == b`는 `Point2D.equals`를 호출한다. `b`는 `Point2D`의 하위 타입이고 x와 y가 같으므로 결과는 `true`이다. 그러나 `b == a`는 `Point3D.equals`를 호출하고, `a`는 `Point3D`가 아니므로 결과는 `false`이다. **대칭성이 깨졌다.**

이런 객체를 `HashSet`에 넣으면 넣는 순서에 따라 동작이 달라지는 골치 아픈 상황이 벌어진다. Effective Java에서 "equals와 상속은 함께 갈 수 없다"고 지적한 유명한 문제가 바로 이것이다.

Kotlin은 이 함정이 **처음부터 생기지 않도록** 막았다. 데이터 클래스를 `final`로 고정해 아무도 상속하지 못하게 하면 `Point3D` 같은 확장을 만들 수 없다. 따라서 자동 생성 `equals`는 언제나 정확히 자기 타입(`other is Point`)만 같다고 판정하고, 대칭성이 수학적으로 보장된다. 값 타입의 안전성을 위해 상속이라는 표현력을 포기한, 의식적인 설계 결정이다.

### 7.2 `equals`의 타입 검사: `is`와 `javaClass`

7.1절에서 말한 자동 `equals`가 `other is Point`(instanceof 계열)를 쓰는지, `other?.javaClass == javaClass`(정확한 클래스 일치)를 쓰는지는 미묘하지만 중요한 문제이다. 데이터 클래스는 `final`이라 하위 타입이 없으므로, `other is Point`를 통과하는 것은 정확히 `Point`뿐이다. 즉 두 방식은 실질적으로 같다.

`final`이 두 방식의 차이를 없애 주기 때문에 `equals`가 단순하고 안전하게 유지된다. 상속이 가능했다면 어느 방식을 택하든 7.1절의 대칭성 문제나 리스코프 치환 문제가 생겼을 것이다.

### 7.3 상속이 필요하다면: 봉인 계층과 데이터 클래스

값이면서 다형적인 계층이 필요할 때가 있다. 예를 들어 도형을 `Circle`과 `Rectangle`로 나누되 각각이 값이기를 원하는 경우이다. 이때 정답은 데이터 클래스를 상속하는 것이 아니라, **30장(sealed 클래스와 대수적 데이터 타입)의 봉인 계층 아래에 각 케이스를 데이터 클래스로 두는 것**이다.

```kotlin
sealed interface Shape
data class Circle(val radius: Double) : Shape
data class Rectangle(val width: Double, val height: Double) : Shape

fun area(s: Shape): Double = when (s) {   // when 완전성: else 불필요
    is Circle -> Math.PI * s.radius * s.radius
    is Rectangle -> s.width * s.height
}
```

여기서 `Shape`는 봉인 인터페이스(합타입, sum type)이고, 각 데이터 클래스는 곱타입(product type)이다. 이 조합이 대수적 데이터 타입(ADT)이며, 데이터 클래스가 상속을 포기한 대가로 얻은 안전한 다형성의 형태이다. `Circle`끼리, `Rectangle`끼리의 `equals`는 각 클래스가 final이므로 대칭이고, 서로 다른 타입 사이의 동등성은 항상 `false`이므로 문제가 없다.

## 8. 주의할 구석: 배열, 부동소수점, 그 밖의 함정

### 8.1 배열 프로퍼티: `equals`가 참조 비교로 바뀐다

데이터 클래스가 `Array<T>`나 원시 배열(`IntArray` 등)을 프로퍼티로 가지면, 자동 `equals`는 **배열의 내용이 아니라 참조를 비교**한다. [[38 - 컬렉션 - 읽기 전용과 가변]]에서 다루듯이, Kotlin에서 `Array`의 `==`(즉 `equals`)는 참조 동일성이기 때문이다.

```kotlin
data class Packet(val header: Int, val payload: IntArray)

fun main() {
    val a = Packet(1, intArrayOf(1, 2, 3))
    val b = Packet(1, intArrayOf(1, 2, 3))
    println(a == b)   // => false!  payload가 내용은 같지만 다른 배열 객체
    println(a.payload.contentEquals(b.payload))  // => true (내용 비교는 이렇게)
}
```

`a == b`가 `false`인 이유는 다음과 같다. 자동 `equals`는 `header == other.header && payload == other.payload`를 실행하는데, `payload == other.payload`는 `IntArray.equals`, 즉 참조 비교이므로 서로 다른 두 배열 객체는 항상 다르다. `hashCode`도 마찬가지로 배열의 identity 해시를 쓰기 때문에 내용이 같아도 값이 다르다. 데이터 클래스에서 가장 악명 높은 함정이다.

해결책은 배열 프로퍼티를 가진 데이터 클래스에서 `equals`/`hashCode`를 **직접 재정의**해 `contentEquals`/`contentHashCode`를 쓰는 것이다.

```kotlin
data class Packet(val header: Int, val payload: IntArray) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true
        if (other !is Packet) return false
        return header == other.header && payload.contentEquals(other.payload)
    }
    override fun hashCode(): Int = 31 * header + payload.contentHashCode()
}
```

더 근본적인 정석은 **데이터 클래스에 배열을 넣지 말고 `List`를 쓰는 것**이다. `List`의 `equals`는 원소별 구조 비교이므로 데이터 클래스와 잘 맞는다.

```kotlin
data class Packet(val header: Int, val payload: List<Int>)  // List면 내용 비교 정상 작동
// Packet(1, listOf(1,2,3)) == Packet(1, listOf(1,2,3))  → true
```

> [!warning] 흔한 오해
> "데이터 클래스니까 배열을 넣어도 값처럼 비교되겠지"라는 생각은 틀렸다. `Array`는 `List`가 아니고, `Array.equals`는 참조 비교이다. IntelliJ 같은 IDE는 데이터 클래스에 배열 프로퍼티가 있으면 "array property in data class"라는 경고를 띄워 이 함정을 알려 준다.

### 8.2 부동소수점 프로퍼티: NaN과 -0.0의 역설

데이터 클래스가 `Double`/`Float` 프로퍼티를 가지면, `equals`는 IEEE 754 산술의 `==`가 아니라 **`Double.equals`(전순서, total order)** 를 쓴다. 이 차이 때문에 뜻밖의 결과가 나온다.

```kotlin
data class Measure(val value: Double)

fun main() {
    // (1) NaN: IEEE 754에서 NaN != NaN 이지만, data class에서는 같다
    val a = Measure(Double.NaN)
    val b = Measure(Double.NaN)
    println(Double.NaN == Double.NaN)  // => false (원시 비교, IEEE 754)
    println(a == b)                    // => true!  (Double.equals 사용, total order)

    // (2) -0.0 vs 0.0: IEEE 754에서 같지만, data class에서는 다르다
    println(0.0 == -0.0)               // => true  (원시 비교)
    println(Measure(0.0) == Measure(-0.0))  // => false!  (total order로 구분)
}
```

이 역설의 근본 원리는 10장(불리언과 동등성과 동일성)에서 설명했다. `Double`을 원시값으로 직접 비교하는 `==`와, `Double`을 `Any`로 박싱한 뒤 `equals`로 비교하는 것은 **서로 다른 함수**이다.

데이터 클래스의 자동 `equals`는 프로퍼티를 `equals`(전순서)로 비교하므로, `NaN`끼리는 같고 `+0.0`과 `-0.0`은 다르다. 해시 컬렉션에서 NaN 키를 다시 찾을 수 있게 하려는 실용적인 선택이다. 반면 원시 `Double`의 `==`는 IEEE 754를 따르므로 결과가 정반대이다. 데이터 클래스에 부동소수점 값을 담을 때는 이 이중성을 반드시 알고 있어야 한다.

### 8.3 가변 프로퍼티(`var`)와 해시 컬렉션의 함정

데이터 클래스의 주 생성자 프로퍼티를 `var`로 선언하면 그 값을 나중에 바꿀 수 있다. 그런데 그 객체가 이미 `HashMap`/`HashSet`에 들어가 있다면 심각한 문제가 생긴다. `hashCode`가 프로퍼티에 의존하므로, 프로퍼티가 바뀌면 해시도 바뀌어 객체가 잘못된 버킷에 남게 된다.

```kotlin
data class Key(var id: Int)

fun main() {
    val k = Key(1)
    val set = hashSetOf(k)
    println(k in set)    // => true

    k.id = 999           // 이미 set에 든 객체의 해시 기여 필드를 변경!
    println(k in set)    // => false!  해시가 바뀌어 원래 버킷에서 못 찾음
    println(set.first()) // => Key(id=999)  객체는 여전히 안에 있으나 조회 불가
}
```

`k`는 여전히 `set` 안에 있지만(`set.first()`가 그 객체를 반환한다), `k in set`은 `false`이다. `id=999`의 해시로 버킷을 찾는데, 정작 그 객체는 `id=1`일 때의 버킷에 물리적으로 남아 있기 때문이다.

**해시 기반 컬렉션의 키나 원소로 쓰는 데이터 클래스는 불변(`val`이면서 깊이 불변)이어야 한다.** 데이터 클래스를 되도록 `val`로만 구성하라는 강력한 실무 규칙은 여기에서 나온다.

### 8.4 제네릭 데이터 클래스와 타입 소거

데이터 클래스도 제네릭일 수 있다. [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]에서 다룰 타입 소거 때문에 자동 `equals`는 타입 파라미터의 실제 타입을 알 수 없다. 하지만 실제로는 문제가 되지 않는다. `equals`는 각 프로퍼티 값에 대해 그 값의 런타임 `equals`를 호출하므로, 타입 파라미터를 몰라도 올바르게 동작한다.

```kotlin
data class Box<T>(val content: T)

fun main() {
    println(Box(42) == Box(42))       // => true
    println(Box("hi") == Box("hi"))   // => true
    println(Box(42) == Box("42"))     // => false  (Int 42 vs String "42": equals false)
}
```

`Box<Int>`와 `Box<String>`은 런타임에 둘 다 `Box`로 소거되지만, `content`의 실제 값(`42`와 `"42"`)에 대한 `equals`가 `false`를 내므로 결과는 올바르다. 데이터 클래스의 값 의미론은 타입 소거와 관계없이 성립한다.

## 9. `data object`: 2.x가 채운 빈칸

### 9.1 문제: 봉인 계층의 상태 없는 케이스

28장(object와 companion)에서 다루는 `object`는 싱글턴 인스턴스이다. 봉인 계층에서 상태가 없는 단일 케이스를 표현할 때는 `object`가 자연스럽다. 예를 들어 로딩 상태 기계에서 `Loading`은 데이터가 없는 단일 상태이다.

```kotlin
sealed interface UiState
data class Success(val data: String) : UiState
data class Error(val message: String) : UiState
object Loading : UiState                          // 상태 없는 단일 케이스
```

그런데 여기서 미묘한 비대칭이 생긴다. `Success`와 `Error`는 데이터 클래스이므로 `toString`이 `Success(data=...)`처럼 보기 좋게 나오지만, `Loading`은 일반 `object`이므로 `toString`이 `Loading@1b6d3586` 같은 identity 형식으로 나온다. 로그를 보거나 디버깅할 때 이 불일치가 거슬린다.

```kotlin
println(Loading)   // (data 없는 object) => Loading@6d06d69c  ← 못생김
```

### 9.2 해법: `data object`

Kotlin 1.9에서 안정화된 `data object`가 이 빈칸을 채운다. `data object`는 일반 `object`처럼 싱글턴이지만, **`toString`이 클래스 이름을 반환**하도록 자동 생성한다.

```kotlin
sealed interface UiState
data class Success(val data: String) : UiState
data class Error(val message: String) : UiState
data object Loading : UiState

fun main() {
    println(Loading)   // => Loading   (예쁜 toString)
}
```

이제 봉인 계층의 모든 케이스가 일관된 `toString`을 가진다. 이것이 `data object`가 존재하는 일차적인 이유이다.

### 9.3 `data object`가 생성하는 것과 생성하지 않는 것

`data object`가 자동 생성하는 멤버는 제한적이다. `object`는 정의상 인스턴스가 하나뿐이므로, 데이터 클래스의 여러 멤버가 의미가 없거나 필요하지 않다.

| 멤버 | data class | data object |
|------|-----------|-------------|
| `toString` | 생성 (프로퍼티 나열) | **생성** (클래스 이름만) |
| `equals` | 생성 (프로퍼티 비교) | 생성 (항상 동일 인스턴스, 아래 참조) |
| `hashCode` | 생성 | 생성 (상수) |
| `copy` | 생성 | **생성 안 함** (싱글턴은 복사 무의미) |
| `componentN` | 생성 | **생성 안 함** (프로퍼티 목록 개념 없음) |

`data object`의 `equals`는 특별하다. object는 인스턴스가 하나뿐이므로, 논리적으로 같은 타입의 object는 항상 자기 자신이다. `data object`는 이를 보장하는 `equals`/`hashCode`를 가진다.

이것이 필요한 이유는 역직렬화(deserialization)나 리플렉션으로 object의 "복제본"이 만들어지는 비정상적인 상황에서도 구조적 동등을 유지하기 위해서이다. 일반 `object`는 identity `equals`를 쓰므로 그런 복제본이 원본과 다르다고 판정될 수 있다. 반면 `data object`는 같은 data object 타입이면 같다고 명시적으로 보장한다.

```kotlin
data object Singleton
fun main() {
    println(Singleton == Singleton)   // => true
    println(Singleton.toString())     // => Singleton
}
```

> [!info] 역사 메모
> `data object`가 1.9에 와서야 언어에 들어오기 전까지, 개발자들은 `object Loading { override fun toString() = "Loading" }`처럼 `toString`을 직접 재정의해 문제를 피했다. 봉인 계층과 상태 기계 패턴이 Kotlin에서 널리 쓰이면서 이 보일러플레이트가 충분히 흔해졌고, 언어가 이를 기능으로 받아들였다.
>
> `enum`과의 관계도 흥미롭다. [[29 - enum 클래스]]의 enum 상수도 각각 상태 없는 단일 케이스이지만, `data object`는 봉인 계층 안에서 데이터 클래스 케이스들과 *섞어* 쓸 수 있다는 점이 다르다.

## 10. 언제 데이터 클래스를 쓰는가: 값 객체와 엔티티의 경계

### 10.1 데이터 클래스가 잘 맞는 곳: 값 객체

데이터 클래스의 이상적인 용도는 **값 객체(value object)** 이다. 값 객체는 정체성(identity)이 아니라 값 자체로 정의된다. 좌표 `(3, 4)`는 어떤 `(3, 4)`든 같은 좌표이고, 돈 `100원`은 어떤 `100원`이든 같으며, 색상 `#FF0000`은 언제나 같은 빨강이다. 이런 대상에는 "두 값이 같으면 같은 것"이라는 값 의미론이 자연스럽고, 데이터 클래스의 자동 `equals`/`hashCode`/`copy`가 정확히 이 의미론을 구현한다.

값 객체는 대개 **불변**이어야 한다. 8.3절에서 봤듯이 가변이면 해시 컬렉션에서 문제가 생긴다. 따라서 데이터 클래스의 모든 프로퍼티를 `val`로 선언하고, 그 프로퍼티가 가리키는 것도 불변(원시값, `String`, 읽기 전용 `List`, 다른 불변 데이터 클래스)으로 구성하는 것이 정석이다. 그러면 `copy`의 얕은 복사도 안전하다. 공유되는 것이 아무도 바꿀 수 없는 불변 값이기 때문이다.

```kotlin
// 좋은 값 객체: 전부 val + 불변 구성요소
data class Money(val amount: Long, val currency: String)
data class Rgb(val r: Int, val g: Int, val b: Int)
data class LineItem(val name: String, val unitPrice: Money, val quantity: Int) {
    val total: Money get() = unitPrice.copy(amount = unitPrice.amount * quantity)  // 파생값
}
```

### 10.2 데이터 클래스를 쓰지 말아야 할 곳: 엔티티

반대로 **엔티티(entity)** 에는 데이터 클래스가 적절하지 않다. 엔티티는 값이 바뀌어도 동일성이 유지되는, 정체성으로 정의되는 대상이다. 사람은 이름이 바뀌어도 같은 사람이고, 은행 계좌는 잔액이 바뀌어도 같은 계좌이다. 이런 대상은 id로 식별되고 나머지 속성은 바뀔 수 있다는 정체성 의미론을 가지므로, 모든 필드를 비교하는 데이터 클래스의 `equals`는 오히려 틀린 답을 낸다.

```kotlin
// 나쁜 사용: 엔티티를 data class로
data class Account(val id: String, var balance: Long)  // ← 함정투성이

// balance가 바뀌면 equals가 달라진다 → "같은 계좌"인데 다르다고 판정
val a = Account("A-1", 100)
val b = Account("A-1", 100)
println(a == b)   // true, 그러나 balance가 다르면?
b.balance = 200
println(a == b)   // false! 같은 계좌(A-1)인데 다르다? 정체성 의미론 위반
// 게다가 var 필드가 hashCode에 기여 → 8.3의 해시 컬렉션 배신
```

엔티티는 일반 클래스로 만들고 `equals`/`hashCode`를 **id만으로** 재정의하는 것이 옳다.

```kotlin
class Account(val id: String, var balance: Long) {
    override fun equals(other: Any?) = other is Account && id == other.id
    override fun hashCode() = id.hashCode()   // 불변 id만 → 해시 안정
}
```

이렇게 하면 `balance`가 바뀌어도 같은 계좌로 판정되고, `id`는 불변이므로 해시 컬렉션에서도 안전하다. 데이터 클래스에서는 모든 주 생성자 프로퍼티가 동등성에 참여하므로 이 패턴을 표현할 수 없다. 그래서 엔티티에는 직접 작성한 클래스가 맞다.

### 10.3 판단 기준 정리

| 질문 | 값 객체 (data class ✓) | 엔티티 (일반 class) |
|------|----------------------|-------------------|
| 무엇으로 같음을 판단? | 모든 속성이 같으면 같음 | id가 같으면 같음 |
| 속성이 변하는가? | 불변(전부 val) | 일부 가변(잔액 등) |
| 예시 | 좌표, 돈, 색, 날짜 | 사람, 계좌, 주문 |
| copy 의미 | 자연스러움(새 값) | 어색함(정체성 복제?) |
| 해시 키 적합성 | 적합(불변) | id만 쓰면 적합 |

> [!caution] 성능 주의
> 데이터 클래스의 자동 멤버에도 비용이 있다. 각 멤버가 실제 메서드로 생성되므로 클래스 크기가 커지고, 프로퍼티가 많은 데이터 클래스의 `copy`는 파라미터 목록이 길어진다(다만 얕은 복사이므로 실행 비용은 낮다). 대부분의 경우 이 비용은 무시할 만하다.
>
> 오히려 문제는 무조건 `data`를 붙이는 습관이다. 이런 습관은 엔티티에까지 값 의미론을 강제해 논리 버그를 부른다. `data`는 값 객체라는 *의도*를 선언하는 수식어이지, 모든 클래스의 기본값이 아니다.

### 10.4 프로퍼티가 많을 때: 빌더 대신 이름 붙은 인자와 copy

프로퍼티가 많을 때도 데이터 클래스는 [[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]에서 본 이름 붙은 인자, 기본 인자와 함께 쓰여 빌더 패턴을 대신한다. `copy`가 부분 변경을 이름으로 표현하므로, Java의 빌더 클래스가 하던 일을 언어 차원에서 처리하는 셈이다.

```kotlin
data class ServerConfig(
    val host: String = "localhost",
    val port: Int = 8080,
    val useTls: Boolean = false,
    val timeoutMs: Long = 30_000,
)

fun main() {
    val base = ServerConfig()
    val secure = base.copy(useTls = true, port = 443)   // 빌더 없이 부분 설정
    println(secure)   // => ServerConfig(host=localhost, port=443, useTls=true, timeoutMs=30000)
}
```

기본 인자는 빌더의 선택적 필드를, `copy`는 빌더의 부분 변경을, 이름 붙은 인자는 빌더의 가독성을 대신한다. 데이터 클래스가 단순히 보일러플레이트를 없애는 데서 그치지 않고 API 설계 도구가 되는 지점이다.
