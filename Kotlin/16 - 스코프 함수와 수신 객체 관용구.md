**이 장이 답하는 질문:**

- `let`, `run`, `with`, `apply`, `also` — 이름은 다섯 개인데 이들을 실제로 가르는 축은 몇 개인가?
- 왜 어떤 스코프 함수 안에서는 `this`로, 어떤 함수 안에서는 `it`으로 대상을 부르는가? 그 차이는 문법적 우연인가, 타입 수준의 결정인가?
- `apply`는 왜 람다의 결과가 아니라 수신 객체를 돌려주며, 그것이 어떻게 "빌더 없는 빌더"를 가능하게 하는가?
- 스코프 함수에 넘긴 람다는 힙에 객체로 할당되는가? 뜨거운 루프 안에서 `let`을 100만 번 써도 되는가?
- `apply { ... }` 블록 안에서 `return`을 쓰면 무엇이 종료되는가? (M41)
- 왜 `run { val x = ...; ... }` 안에서 선언한 `val`을 컴파일러는 "정확히 한 번 초기화된다"고 확신할 수 있는가?
- `x?.let { }`가 널일 때 블록을 건너뛰는 것과, `takeIf`가 조건이 거짓일 때 `null`을 내는 것은 어떻게 결합되는가?
- 스코프 함수는 코드를 짧게 만든다 — 그런데 왜 남용하면 오히려 읽기 어려워지는가? 선택의 기준은 무엇인가?

---

[[13 - 함수 타입과 람다와 함수 참조]]는 함수를 값으로 만드는 문법을 놓았고, 그 장 말미에서 점이 붙은 함수 타입 `A.() -> B` — 이른바 **수신 객체 지정 람다**(lambda with receiver) — 를 소개하며 "이것이 스코프 함수와 DSL의 토대"라고 예고했다. [[14 - 클로저와 캡처]]는 그 람다가 자유 변수를 어떻게 붙잡는지를, [[15 - 인라인 함수와 reified]]는 `inline`이 람다의 몸통을 호출 지점에 복사해 할당과 가상 호출을 없애고 **비지역 반환**(non-local return, M41)을 가능하게 함을 밝혔다. 이 장은 그 세 장이 쌓아 올린 기반 위에 서 있다. 스코프 함수는 새로운 언어 기능이 아니다. 표준 라이브러리에 정의된 다섯 개의 평범한 `inline` 확장 함수일 뿐이다. 놀라운 것은 그토록 얇은 도구가 코틀린 코드의 결을 얼마나 바꾸는가다.

이 장이 다루는 것은 두 겹이다. 첫째, `let`/`run`/`with`/`apply`/`also` 다섯 함수와 그 사촌인 `takeIf`/`takeUnless`의 **정확한 계약** — 무엇을 수신자로 넘기고, `this`로 부르는가 `it`으로 부르는가, 무엇을 돌려주는가. 이 다섯은 겉보기에 제각각이지만, 실은 딱 두 개의 축(수신자 참조 방식 · 반환값)이 만드는 $2 \times 2$ 격자에 거의 정확히 들어맞는다. 이 격자를 손에 쥐는 것이 이 장의 절반이다. 둘째, 그 관용구를 떠받치는 **기계** — 왜 스코프 함수가 람다를 할당하지 않는지(inline), 왜 그 안에서 선언한 `val`이 정확히 한 번 초기화된다고 컴파일러가 아는지(contracts), 왜 `apply` 안의 `return`이 바깥 함수를 종료시키는지(비지역 반환).

경계를 못박자. 수신 객체 지정 람다 `A.() -> B`라는 *타입 자체*의 문법과 JVM 표현은 [[13 - 함수 타입과 람다와 함수 참조]]가 소유한다 — 이 장은 그것을 *부리는 관용구*를 다룬다. 그 관용구를 극한까지 밀어 **타입 안전 빌더**를 짓는 이야기, `@DslMarker`로 수신자 스코프를 통제하는 이야기는 [[37 - 타입 안전 빌더와 DSL]]의 몫이다. 확장 함수의 정적 디스패치 원리(M14~M16)는 [[35 - 확장 함수와 프로퍼티]]가, 널 안전 연산자 `?.`/`?:`의 정본은 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]가 소유한다. 이 장은 그 연산자들을 스코프 함수와 *조합하는* 관용구에 집중한다.

논증의 궤적은 이렇다. 먼저 다섯 함수를 가르는 두 축을 세워 좌표계를 그리고(§1), 그 좌표계의 세로축인 "수신 객체 지정 람다"의 문법적 토대를 다시 판다(§2). 그다음 다섯 함수를 하나씩 — `let`(§3), `run`(§4), `with`(§5), `apply`(§6), `also`(§7) — 각자의 관용구와 함께 해부한다. 조건을 값의 흐름에 끼워 넣는 `takeIf`/`takeUnless`(§8)를 보고, 그 모든 것을 떠받치는 내부 기계 — inline·contracts·비지역 반환 — 를 연다(§9). 마지막으로 선택의 규칙과 남용의 안티패턴(§10)으로 닫는다.

## 1. 두 개의 축 — 스코프 함수를 가르는 좌표계

### 1.1 다섯 개의 이름, 두 개의 질문

초보자가 스코프 함수 앞에서 길을 잃는 이유는 이름이 다섯 개이기 때문이다. `let`, `run`, `with`, `apply`, `also` — 무엇이 무엇인지 외우려 들면 반드시 헷갈린다. 그러나 이 다섯은 본질적으로 딱 두 개의 질문에 대한 답의 조합일 뿐이다.

**질문 1: 블록 안에서 대상을 어떻게 부르는가?**
- **`this`**(수신자로) — 대상이 암시적 수신자가 되어 이름 없이 그 멤버를 부를 수 있다. 람다 타입이 `T.() -> R`(수신 객체 지정).
- **`it`**(인자로) — 대상이 람다의 유일한 파라미터로 넘어와 `it`이라는 이름으로 참조된다. 람다 타입이 `(T) -> R`(보통 람다).

**질문 2: 블록이 끝나면 무엇을 돌려주는가?**
- **람다의 결과**(block result) — 블록의 마지막 표현식 값. 대상을 *변환*하는 데 쓴다.
- **수신 객체 자신**(the object) — 대상을 그대로 다시 돌려준다. 대상을 *구성/관찰*하고 흐름을 이어가는 데 쓴다.

이 두 질문이 $2 \times 2$ 격자를 만든다. 그리고 다섯 함수는 다음처럼 배치된다.

| | **`this`로 (수신자)** | **`it`으로 (인자)** |
|---|---|---|
| **람다 결과 반환** | `run`, `with` | `let` |
| **수신 객체 반환** | `apply` | `also` |

`run`과 `with`가 같은 칸에 있는 이유는 단 하나 — `with`만 확장 함수가 아니라 일반 함수라 대상을 인자로 받는다는 점이다(§5). 나머지 넷은 전부 확장 함수라 `대상.함수 { }` 꼴로 붙는다. 그래서 사실상 **네 개의 실질적 선택지**(`this`+결과 / `this`+수신자 / `it`+결과 / `it`+수신자)만 기억하면 된다. 이름을 외우지 말고 두 축을 외워라.

### 1.2 표준 라이브러리의 실제 시그니처

추상적 격자가 아니라 코틀린 표준 라이브러리(`kotlin-stdlib`)에 실제로 적힌 시그니처를 보자. 다섯 함수 전부 `public inline`이다.

```kotlin
// kotlin.let
public inline fun <T, R> T.let(block: (T) -> R): R

// kotlin.run (확장 형태)
public inline fun <T, R> T.run(block: T.() -> R): R

// kotlin.run (수신자 없는 형태)
public inline fun <R> run(block: () -> R): R

// kotlin.with
public inline fun <T, R> with(receiver: T, block: T.() -> R): R

// kotlin.apply
public inline fun <T> T.apply(block: T.() -> Unit): T

// kotlin.also
public inline fun <T> T.also(block: (T) -> Unit): T
```

시그니처가 두 축을 그대로 증언한다.

- **수신자 참조**: 람다 파라미터 타입이 `T.() -> R`(수신 람다)면 블록 안에서 `this`, `(T) -> R`(보통 람다)면 `it`이다. `run`/`with`/`apply`는 `T.()`, `let`/`also`는 `(T)`.
- **반환값**: 반환 타입이 `R`(제네릭 결과)이면 람다 결과를, `T`(수신자 타입)이면 수신 객체를 돌려준다. `let`/`run`/`with`는 `R`, `apply`/`also`는 `T`.
- `apply`/`also`의 블록 반환 타입이 `-> Unit`인 것도 의미심장하다. 이 둘은 블록의 결과를 아예 버리도록(수신자를 돌려주므로) 설계됐다. 그래서 블록 안에서 무엇을 마지막에 쓰든 반환값에 영향이 없다.

> **명세 정밀**: 이 함수들은 언어 키워드가 아니라 **라이브러리 함수**다. 컴파일러에 `let`이라는 특별 규칙은 없다. 다만 `inline`이라서 [[15 - 인라인 함수와 reified]]가 밝힌 인라이닝·비지역 반환의 언어 규칙이 적용되고, 뒤에서 볼 **계약**(contract) 애노테이션 덕에 스마트 캐스트·초기화 분석이 블록을 관통한다. 즉 "특별함"은 전부 이미 존재하는 언어 기능의 조합에서 나온다.

> **역사 메모**: `with`는 코틀린 초기부터 있던 함수로, 자바에는 없는 "수신자 블록"을 라이브러리로 흉내 낸 첫 사례다(파스칼·비주얼베이직의 `with` 문에서 이름을 빌렸으나, 코틀린의 것은 문법이 아니라 고차 함수다). `let`/`apply`/`also`/`run`은 그 뒤 표준 라이브러리 관용구로 다듬어졌고, 이름이 겹치던 혼란기를 거쳐 지금의 "두 축" 체계로 정착했다. `also`는 상대적으로 늦게(1.1) 추가돼 "`apply`의 `it` 버전"이라는 빈칸을 채웠다. 이 진화의 결과가 격자가 거의 완벽히 차 있는 지금의 다섯 함수다 — 유일하게 빈 칸은 "`with`의 확장·널안전 버전"인데, 그것을 `run`이 겸한다.

### 1.3 왜 하필 이 조합인가 — 관용구와의 대응

두 축의 각 조합이 자연스럽게 하나의 *관용구*에 대응한다. 이것이 다섯 함수가 우연히 다섯인 게 아닌 이유다.

```text
              반환: 람다 결과 R          반환: 수신 객체 T
            ┌────────────────────┬────────────────────┐
  this로    │  run / with        │  apply             │
 (수신자)   │  "이 객체 위에서    │  "이 객체를 구성해  │
            │   계산해 결과를"    │   그대로 돌려줘"    │
            ├────────────────────┼────────────────────┤
  it으로    │  let               │  also              │
 (인자)     │  "이 값을 이름 붙여 │  "이 값에 부수효과  │
            │   변환해"          │   흘리고 계속 흘려" │
            └────────────────────┴────────────────────┘
```

- `let`: 값 하나를 `it`(또는 이름)으로 받아 **변환**한다. 널 처리(`?.let`)의 주역.
- `run`: 수신자 위에서 여러 문장을 실행해 **결과**를 낸다. `with`의 확장·널안전 버전.
- `with`: 수신자를 인자로 명시하고 그 위에서 **결과**를 낸다. 널 아닌 대상의 그룹 호출.
- `apply`: 수신자를 `this`로 **구성**하고 그 수신자를 돌려준다. 객체 초기화의 주역.
- `also`: 값에 `it`으로 **부수효과**(로깅·검증)를 흘리고 원본을 이어 흘린다.

이 대응을 손에 쥐면, 코드를 쓸 때 "무엇을 하려는가"에서 함수가 자동으로 결정된다. 변환이면 `let`, 구성이면 `apply`, 관찰이면 `also`. 다음 절부터 이 대응을 하나씩 실증한다. 그 전에 세로축 — `this`로 부르게 만드는 "수신 객체 지정 람다" — 를 한 번 더 파야 한다. 이것이 스코프 함수의 진짜 심장이자, 이 장이 DSL(37장)로 이어지는 다리이기 때문이다.

## 2. 수신 객체 지정 람다 — 관용구의 문법적 토대

### 2.1 `T.() -> R`는 무엇을 바꾸는가

[[13 - 함수 타입과 람다와 함수 참조]]에서 함수 타입 `(A) -> B`를 봤다. **수신 객체 지정 람다**의 타입 `A.() -> B`는 여기에 점 하나(`A.`)를 더한 것이다. 이 점이 하는 일은 단순하면서도 근본적이다: 첫 번째 인자를 *암시적 수신자*로 승격시킨다.

```kotlin
// 보통 함수 타입: 대상이 파라미터로
val describe1: (String) -> Int = { s -> s.length }
describe1("hello")            // => 5, 안에서 s로 참조

// 수신 함수 타입: 대상이 this로
val describe2: String.() -> Int = { this.length }
"hello".describe2()          // => 5, 안에서 this(또는 생략)로 참조
"hello".describe2()          // 확장 함수처럼 점 표기로 호출
```

`describe2`의 몸통 `{ this.length }`에서 `this`는 호출 대상 문자열이다. 그리고 `this`는 대개 **생략 가능**하다 — `{ length }`라고만 써도 `this.length`로 해소된다. 바로 이 생략이 `apply`/`with`/`run` 안에서 대상의 멤버를 이름 없이 줄줄이 부를 수 있게 하는 마법의 정체다.

```kotlin
class Rectangle {
    var width: Double = 0.0
    var height: Double = 0.0
    fun area() = width * height
}

val r = Rectangle().apply {
    width = 3.0        // this.width = 3.0
    height = 4.0       // this.height = 4.0
}                      // apply는 r을 돌려줌 (수신자 반환)
println(r.area())      // => 12.0
```

`apply`의 블록 타입은 `Rectangle.() -> Unit`이다. 그래서 블록 안에서 `width`, `height`가 곧바로 수신자의 프로퍼티로 해소된다. 만약 `apply`가 보통 람다 `(Rectangle) -> Unit`를 받았다면 우리는 `it.width = 3.0`처럼 써야 했을 것이다 — 그게 바로 `also`다.

### 2.2 암시적 수신자의 해소 규칙과 그림자

`this` 생략이 편하지만, 여기엔 함정이 산다. 블록 안에서 이름 하나를 썼을 때, 컴파일러는 그것을 **가장 가까운 암시적 수신자**부터 바깥으로 훑으며 해소한다. 수신 람다는 새 암시적 수신자를 하나 쌓기 때문에, 바깥 스코프의 동명 멤버와 충돌할 수 있다.

```kotlin
class Config {
    var timeout: Int = 30
    fun log(msg: String) = println("config: $msg")
}

class Service {
    var timeout: Int = 100          // 바깥에도 timeout
    fun setup() {
        Config().apply {
            timeout = 5             // ⚠️ 어느 timeout? → Config.timeout (가까운 수신자 우선)
            log("configured")       // Config.log (Service엔 log 없음)
        }
        println(timeout)            // => 100 (Service.timeout은 안 바뀜)
    }
}
```

`apply` 블록 안의 `timeout = 5`는 가장 가까운 암시적 수신자인 `Config`의 것으로 해소된다. 의도가 그것이었다면 좋지만, `Service.timeout`을 바꾸려 했다면 조용한 버그다. 바깥 수신자를 명시하려면 **레이블 붙은 `this`** 를 쓴다([[31 - 중첩 클래스와 이너 클래스와 익명 객체]]가 `this@Outer` 관용구를 소유).

```kotlin
Config().apply {
    this.timeout = 5                // Config.timeout (명시)
    this@Service.timeout = 200      // Service.timeout (바깥 수신자)
}
```

> **흔한 오해**: "`apply` 안에서는 항상 새 객체의 멤버가 우선한다"는 생각은 위험하다. 우선하는 것은 맞지만, 새 객체에 *없는* 이름은 바깥 수신자로 흘러 해소된다. 그래서 오타나 리팩터링으로 프로퍼티 이름이 바뀌면, 컴파일 에러가 나는 대신 조용히 바깥 것을 건드릴 수 있다. `it`을 쓰는 `also`/`let`은 이런 그림자가 없어 이 점에서 더 안전하다(§7, §10).

### 2.3 확장 함수와 같은 뿌리

수신 객체 지정 람다는 사실 [[35 - 확장 함수와 프로퍼티]]의 확장 함수와 같은 메커니즘 위에 있다. 확장 함수 `fun String.foo()`가 컴파일되면 `String`을 첫 인자(수신자)로 받는 정적 메서드가 되듯, `String.() -> R` 람다도 내부적으로는 수신자를 첫 인자로 받는 `Function1`류로 표현된다(정확한 표현은 [[13 - 함수 타입과 람다와 함수 참조]]). 차이는 오직 *호출 문법*이다. 이 공통 뿌리 때문에, 수신 람다를 파라미터로 받는 함수(`apply`, `with`, `buildString`, DSL 빌더 등)는 전부 "블록 안에서 특정 타입이 암시적 수신자가 되는" 같은 경험을 준다.

이 사실이 [[37 - 타입 안전 빌더와 DSL]]로 가는 다리다. `apply`가 "임의의 `T`에 대해 그 `T`를 수신자로 만드는" 범용 도구라면, DSL 빌더는 "특정 도메인 타입(HTML 노드, 설정 트리)을 수신자로 만드는" 특화 도구일 뿐이다. 스코프 함수를 이해하면 DSL은 그 일반화에 지나지 않는다. 이제 다섯 함수를 하나씩, 각자의 관용구와 함께 해부하자.

## 3. let — 값을 이름에 담아 변환한다

### 3.1 계약: `it`으로 받아 결과를 낸다

`let`의 시그니처는 `T.let(block: (T) -> R): R`이다. 수신자 `T`가 블록에 **인자로**(`it`) 넘어가고, 블록의 **결과 `R`** 이 반환된다. 즉 `let`은 "이 값을 `it`이라는 지역 이름에 담고, 그 위에서 무언가 계산해, 계산 결과를 내라"는 관용구다.

```kotlin
val name = "  Alice  "
val len: Int = name.let { it.trim().length }   // it = name
println(len)                                    // => 6
```

여기서 `let`이 없어도 `name.trim().length`로 충분하다. `let`이 진짜 값을 발하는 곳은 두 지점이다: **널 처리**(§3.2)와 **긴 표현식에 임시 이름 붙이기**(§3.3).

`it`은 마법 이름이 아니다(M42). `it`은 [[13 - 함수 타입과 람다와 함수 참조]]가 밝혔듯 *단일 파라미터 람다의 암시적 파라미터 이름*일 뿐이며, 원하면 이름을 지어 가독성을 높일 수 있다.

```kotlin
val len = name.let { raw -> raw.trim().length }   // it 대신 raw로 명명
```

### 3.2 널 처리의 주역 — `?.let`

`let`이 코틀린 코드에서 가장 자주 보이는 이유는 안전 호출 `?.`([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]])와의 조합이다. `nullable?.let { }`는 "널이 아니면 블록 실행, 널이면 통째로 건너뛰고 `null`"이라는 관용구를 만든다.

```kotlin
fun greet(name: String?) {
    name?.let {
        // 이 안에서 it은 String (널 아님) — 스마트 캐스트
        println("Hello, ${it.uppercase()}")
    }
    // name이 null이면 블록 전체를 건너뛴다
}

greet("bob")   // => Hello, BOB
greet(null)    // (아무것도 출력 안 함)
```

핵심은 블록 안에서 `it`의 타입이 `String?`가 아니라 **`String`**(널 아님)이라는 것이다. `?.`가 널을 걸러 냈으므로 `let`의 인자 `T`는 널 아닌 타입으로 확정된다. 이것은 `if (name != null) { ... }`의 표현식 버전이며, 특히 대상이 `var`거나 커스텀 게터라 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]의 스마트 캐스트가 안 되는 경우(M13)에 유용하다. `?.let`은 값을 지역 `it`에 *복사*하므로, 다른 스레드나 게터가 그 사이 값을 바꿔도 `it`은 안전하다.

```kotlin
class Box(var content: String?)     // var 프로퍼티 — 스마트 캐스트 불가

fun show(box: Box) {
    // box.content가 var라 if (box.content != null) 안에서도 스마트캐스트 안 됨
    box.content?.let { c ->
        println(c.length)           // c는 안전하게 캡처된 널 아닌 값
    }
}
```

여기에 엘비스 `?:`([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]], M32)를 붙이면 "널이면 기본값" 관용구가 완성된다.

```kotlin
fun lengthOrZero(s: String?): Int =
    s?.let { it.length } ?: 0        // 널이면 let 건너뛰고 → null → ?: 로 0
```

`s`가 널이면 `s?.let { }` 전체가 `null`이 되고, `?:`가 그 `null`을 잡아 `0`을 낸다. `?:`의 우변에는 [[41 - 예외와 Nothing]]이 소유하는 `throw`나 `return`도 올 수 있어, "널이면 던지거나 조기 반환"으로도 확장된다.

### 3.3 표현식에 임시 이름 붙이기

`let`의 두 번째 쓸모는 이름 없는 중간 표현식에 지역 이름을 부여해 가독성을 높이는 것이다. 특히 체인 중간의 결과를 한 번만 쓰되 그 정체를 이름으로 드러내고 싶을 때다.

```kotlin
val result = readNumbers()
    .filter { it > 0 }
    .let { positives -> positives.sum() to positives.size }
    // positives라는 이름으로 두 번 참조하며 (합, 개수) 쌍을 만든다
```

`let` 없이 하려면 `positives`를 별도 `val`로 선언해야 하는데, `let`은 그 지역 변수를 블록 스코프 안에 가둬 바깥을 오염시키지 않는다. 다만 이 관용구는 남용하면 오히려 흐름이 끊긴다(§10).

> **성능 주의**: `let`은 `inline` 함수다(§9). 그래서 `name.let { ... }`는 람다 객체를 **할당하지 않는다** — 블록 몸통이 호출 지점에 그대로 펼쳐진다. 뜨거운 루프 안에서 `?.let`을 수백만 번 써도 힙 할당이 반복되지 않는다. 이것이 스코프 함수를 부담 없이 쓸 수 있는 근본 이유다. (단, `let`을 함수 참조 `::let`으로 넘기는 등 인라인이 안 되는 방식으로 쓰면 이 이점은 사라진다.)

## 4. run — 수신자 위에서 블록을 실행해 결과를 낸다

### 4.1 계약: `this`로 받아 결과를 낸다

`run`의 확장 형태 시그니처는 `T.run(block: T.() -> R): R`이다. `let`과 반환값(`R`, 람다 결과)은 같지만, 대상을 **`this`로**(수신자로) 받는다는 점이 다르다. 즉 `run`은 "이 객체를 수신자로 삼아 여러 문장을 실행하고, 마지막 표현식을 결과로 내라"는 관용구다.

```kotlin
class Circle(val radius: Double) {
    fun circumference() = 2 * Math.PI * radius
    fun area() = Math.PI * radius * radius
}

val summary: String = Circle(2.0).run {
    // this = Circle(2.0), 멤버를 이름 없이 호출
    "둘레=%.2f, 넓이=%.2f".format(circumference(), area())
}
println(summary)   // => 둘레=12.57, 넓이=12.57
```

`let`으로 같은 걸 쓰면 `it.circumference()`, `it.area()`처럼 매번 `it.`을 붙여야 한다. 대상의 멤버를 여러 번 호출할 때는 `this`로 받는 `run`이 잡음이 적다. 반대로 대상을 다른 함수의 인자로 넘기거나 `it`이라는 이름으로 명시하고 싶으면 `let`이 낫다. 이 선택 — `it` vs `this` — 이 §10 결정 트리의 한 축이다.

### 4.2 `?.run` — 널 안전 그룹 호출

`run`도 확장 함수라 `?.`와 결합한다. `nullable?.run { }`은 "널이 아니면 그 객체를 수신자로 블록 실행, 결과 반환"이다.

```kotlin
class Account(val balance: Long, val owner: String)

fun report(acc: Account?): String =
    acc?.run {
        "$owner: $balance"      // this.owner, this.balance
    } ?: "계좌 없음"
```

이것은 `with`(§5)로는 깔끔히 못 쓰는 패턴이다. `with`는 확장이 아니라 대상을 인자로 받으므로 `acc?.with`처럼 널 안전 호출을 붙일 수 없다. 널 가능 대상을 수신자로 두고 그룹 호출하려면 `?.run`이 정답이다.

### 4.3 수신자 없는 `run` — 문장을 표현식으로 접기

`run`에는 확장이 아닌 두 번째 오버로드가 있다: `run(block: () -> R): R`. 수신자가 없고 그냥 블록을 실행해 결과를 낸다. 얼핏 무의미해 보이지만, 이것은 **여러 문장을 하나의 표현식으로 접는** 도구다. 코틀린에서 `if`/`when`은 표현식이지만([[17 - 표현식으로서의 제어 흐름 - if와 when]]), 여러 문장이 필요한 초기화에는 블록이 필요하다. 수신자 없는 `run`이 그 블록을 값으로 만든다.

```kotlin
val connectionString: String = run {
    val host = System.getenv("DB_HOST") ?: "localhost"
    val port = System.getenv("DB_PORT") ?: "5432"
    "jdbc:postgresql://$host:$port/app"     // 마지막 표현식이 결과
}
```

`run { }`이 없다면 `host`, `port`가 바깥 스코프로 새어 나가거나, 별도 함수를 만들어야 한다. `run`은 그 계산을 지역 스코프에 가두고 결과 하나만 밖으로 낸다. 프로퍼티 초기화나 `when` 분기 안에서 특히 유용하다.

또한 이 형태는 **비지역 반환**(§9.3)과 결합해 조기 종료 관용구를 만들기도 한다.

```kotlin
fun process(input: String?) {
    val data = run {
        if (input.isNullOrBlank()) return   // 바깥 process()를 종료 (비지역 반환, M41)
        input.trim()
    }
    println(data.length)
}
```

`run`이 `inline`이라 그 안의 `return`은 `run`이 아니라 바깥 `process`를 종료한다(§9.3에서 정밀히). 이 관용구는 강력하지만, 흐름을 읽기 어렵게 만들 수 있어 주의가 필요하다(§10).

## 5. with — 수신자를 인자로 받는 비확장 형제

### 5.1 계약: 확장이 아닌 `run`

`with`의 시그니처는 `with(receiver: T, block: T.() -> R): R`이다. `run`과 완전히 같은 일 — `this`로 받아 결과 반환 — 을 하지만, **확장 함수가 아니다**. 대상을 첫 인자로 명시적으로 넘긴다. 그래서 호출 문법이 다르다.

```kotlin
val c = Circle(3.0)

// run: 확장 — 점 표기
val a1 = c.run { area() }

// with: 비확장 — 대상을 인자로
val a2 = with(c) { area() }
```

두 호출은 결과가 같다. 차이는 순전히 문법과 널 안전성이다.

| | `x.run { }` | `with(x) { }` |
|---|---|---|
| 형태 | 확장 함수 | 일반 함수 (인자) |
| 널 안전 | `x?.run { }` 가능 | `x?.with` 불가 |
| 대상이 이미 널 아님이 확실할 때 | 둘 다 가능 | 자연스러움 |
| 체인 중간 | 자연스러움 (`x.foo().run {}`) | 어색함 (`with(x.foo()) {}`) |

### 5.2 언제 with, 언제 run

경험칙은 이렇다. **대상이 널 아님이 확실하고, 체인의 일부가 아니라 독립된 "이 객체로 작업하는 블록"을 열고 싶을 때** `with`가 문장으로서 잘 읽힌다.

```kotlin
val html: String = with(StringBuilder()) {
    append("<div>")
    append("내용")
    append("</div>")
    toString()          // 마지막 표현식 = 결과
}
```

`with(receiver) { ... }`는 영어로 "receiver를 가지고(with) 다음을 하라"로 읽혀, 그룹 호출의 의도를 문장 첫머리에 드러낸다. 반면 널 가능 대상이거나 체인 중간이면 `?.run`이 낫다. 기능은 동일하니 **가독성**이 유일한 선택 기준이다.

> **흔한 오해**: "`with`는 `apply`처럼 객체를 설정하는 함수"라는 오해가 흔하다. 아니다. `with`는 **결과를 반환**(`R`)하지 대상을 반환하지 않는다. 위 예에서 마지막에 `toString()`을 안 쓰면 `with` 블록의 결과는 마지막 `append(...)`의 반환값(`StringBuilder`)이 되어 우연히 대상처럼 보일 뿐, 이는 `append`가 자기 자신을 돌려주기 때문이지 `with`의 계약이 아니다. 대상을 확실히 돌려받고 싶으면 `apply`를 써야 한다(§6).

### 5.3 여러 수신자를 여는 함정

`with`(그리고 `run`/`apply`)를 중첩하면 암시적 수신자가 여러 겹 쌓인다. 그러면 §2.2에서 본 그림자 문제가 증폭된다.

```kotlin
class Outer { fun name() = "outer" }
class Inner { fun name() = "inner" }

with(Outer()) {
    with(Inner()) {
        name()              // => "inner" (가장 가까운 수신자)
        this@with           // Inner  — 레이블은 함수명 기준
    }
}
```

중첩 `with`에서 `name()`은 가장 안쪽 `Inner`로 해소된다. 바깥 `Outer`의 것을 부르려면 레이블이 필요한데, 두 블록이 같은 `with`라 레이블이 모호해진다. 이런 다중 수신자 스코프를 안전하게 통제하는 것이 [[37 - 타입 안전 빌더와 DSL]]의 `@DslMarker` — 바깥 암시적 수신자를 가려 실수로 못 부르게 막는 장치 — 다. 스코프 함수의 중첩은 편하지만, 세 겹을 넘어가면 거의 항상 가독성이 무너진다(§10).

## 6. apply — 객체를 구성하고 그 객체를 돌려준다

### 6.1 계약: `this`로 받아 수신자를 돌려준다

`apply`의 시그니처는 `T.apply(block: T.() -> Unit): T`이다. 대상을 **`this`로** 받고, 블록의 결과는 버린 채(`-> Unit`) **대상 자신(`T`)** 을 돌려준다. 이 조합이 딱 하나의 관용구 — **객체 구성**(configuration) — 을 위해 존재한다.

```kotlin
val point = Point().apply {
    x = 10          // this.x = 10
    y = 20          // this.y = 20
}                   // apply는 구성된 Point를 돌려줌
// point는 x=10, y=20으로 구성된 Point
```

`apply`가 없다면 이렇게 써야 한다:

```kotlin
val point = Point()
point.x = 10
point.y = 20
// point 변수를 세 번 반복
```

`apply`는 대상 이름을 반복하지 않고, 대상을 `this`로 삼아 프로퍼티를 줄줄이 설정한 뒤 그 대상을 그대로 표현식 값으로 돌려준다. 그래서 `val`로 한 번에 받으며 구성까지 끝낼 수 있다. Java의 빌더 패턴이 하던 일을, 별도 빌더 클래스 없이, 일반 클래스의 세터만으로 해낸다.

### 6.2 빌더 없는 빌더

`apply`의 진짜 힘은 반환값이 대상이라는 점에서 나온다. 반환값이 대상이므로 **표현식으로서 곧바로 넘기거나 이어 붙일 수 있다.**

```kotlin
class HttpRequest {
    var url: String = ""
    var method: String = "GET"
    val headers: MutableMap<String, String> = mutableMapOf()
}

fun send(req: HttpRequest) { /* ... */ }

// 임시 변수 없이 구성 → 즉시 전달
send(HttpRequest().apply {
    url = "https://example.com/api"
    method = "POST"
    headers["Content-Type"] = "application/json"
})
```

`HttpRequest()`를 만들고, `apply` 안에서 구성하고, 그 구성된 객체가 곧장 `send`의 인자가 된다. 중간 변수가 하나도 없다. 이 관용구는 특히 **가변 컬렉션·빌더 객체의 초기 채우기**에 자주 등장한다.

```kotlin
val list = mutableListOf<Int>().apply {
    add(1)
    add(2)
    addAll(listOf(3, 4))
}   // 채워진 리스트를 돌려받음
```

> **흔한 오해**: `apply`가 람다의 결과를 돌려준다고 착각하면 큰 버그가 난다. `apply` 블록의 마지막 표현식이 무엇이든 반환값은 **항상 대상**이다.
> ```kotlin
> val n = StringBuilder().apply {
>     append("hi")
>     length              // 마지막 표현식 = 2, 하지만 무시됨
> }
> // n의 타입은 Int가 아니라 StringBuilder! (apply는 수신자를 돌려줌)
> ```
> 만약 `length`(=2)를 값으로 받고 싶었다면 `run`을 썼어야 한다. `apply`(수신자 반환) ↔ `run`(결과 반환)의 이 대칭이 두 함수를 가르는 전부다.

### 6.3 apply와 val — 불변 참조에 가변 구성

`apply`는 [[11 - 변수와 초기화 - val과 const와 lateinit]]의 `val`과 함께 자주 쓰인다. `val`은 재대입 불가일 뿐 대상 객체는 가변일 수 있다는 사실(M3)을 `apply`가 잘 활용한다.

```kotlin
val cache = HashMap<String, Int>().apply {
    put("a", 1)
    put("b", 2)
}
// cache는 val (재대입 불가) 이지만, apply로 초기 내용을 채웠고
// 이후에도 cache.put(...)으로 내용은 계속 바꿀 수 있다 (M3: val ≠ immutable)
```

`val cache`는 참조가 고정될 뿐, 그 `HashMap`은 가변이다. `apply`는 그 가변 객체를 *선언 시점에 한 번에* 구성하는 관용구를 제공한다. 이 조합이 코틀린에서 "선언과 초기 구성을 붙여 쓰는" 흔한 스타일의 뼈대다.

### 6.4 apply와 자바 빌더의 대비

`apply`가 무엇을 대체하는지는 자바와 나란히 두면 선명하다. 자바에서 "객체를 만들며 여러 세터를 부르고 그 객체를 넘기는" 일은 빌더 클래스를 따로 만들거나, 임시 변수를 두고 세터를 반복하거나 둘 중 하나였다.

```java
// Java — 임시 변수 + 반복되는 참조
Rectangle r = new Rectangle();
r.setWidth(3.0);
r.setHeight(4.0);
r.setColor("red");
draw(r);
```

```kotlin
// Kotlin — apply로 변수 없이 구성 후 전달
draw(Rectangle().apply {
    width = 3.0        // 참조 반복 없음, this 생략
    height = 4.0
    color = "red"
})
```

자바 코드는 `r`을 네 번 적는다. 코틀린은 `apply`가 `this`를 암시적 수신자로 세워 대상 이름을 0번 적게 하고, 반환값이 대상이라 `draw(...)`에 곧장 흘려보낸다. 자바가 이 우아함을 얻으려면 대상 클래스에 빌더(수십 줄의 보일러플레이트)를 심어야 하지만, 코틀린은 *임의의* 클래스에 `apply`를 붙일 수 있다 — `apply`가 특정 타입에 매인 메서드가 아니라 `<T> T.apply`라는 범용 확장이기 때문이다. 이것이 "빌더 없는 빌더"의 진짜 의미다: 빌더를 클래스마다 짓는 대신, 언어가 모든 타입에 하나의 구성 관용구를 공짜로 준다.

## 7. also — 부수효과를 흘려보내고 원본을 이어간다

### 7.1 계약: `it`으로 받아 수신자를 돌려준다

`also`의 시그니처는 `T.also(block: (T) -> Unit): T`이다. 대상을 **`it`으로**(인자로) 받고, 블록 결과는 버린 채 **대상 자신(`T`)** 을 돌려준다. `apply`와 반환값(수신자)은 같지만 대상을 `this`가 아니라 `it`으로 받는다. 이 미묘한 차이가 `also`를 **부수효과와 관찰**의 도구로 만든다.

```kotlin
val numbers = mutableListOf(1, 2, 3)
    .also { println("초기: $it") }      // it = 리스트, 관찰만
    .also { it.add(4) }                 // 부수효과, 원본을 이어 흘림
// numbers = [1, 2, 3, 4], 로그도 출력됨
```

`also`는 값의 흐름을 끊지 않고 그 흐름 옆에서 무언가를 하고 싶을 때 쓴다 — 로깅, 검증, 디버깅 출력, 부가 등록 같은 것. 함수형 파이프라인의 `peek`에 해당한다([[39 - 컬렉션 연산과 함수형 파이프라인]]과 개념적으로 통한다). 대상을 그대로 돌려주니 체인 중간에 자연스럽게 끼어든다.

### 7.2 apply vs also — this vs it의 실전 판단

`apply`와 `also`는 둘 다 수신자를 돌려주므로 서로 바꿔 쓸 수 있는 것처럼 보인다. 차이는 대상을 부르는 방식(`this` vs `it`)이고, 이 차이가 실전에서 중요하다.

```kotlin
class User {
    var name: String = ""
    var age: Int = 0
}

// apply: 대상의 멤버를 이름 없이 설정 (구성)
val u1 = User().apply {
    name = "Alice"     // this.name
    age = 30
}

// also: 대상을 it으로 받아 다른 함수에 넘기거나 관찰 (부수효과)
val u2 = User().apply { name = "Bob" }.also { user ->
    registerUser(user)          // 대상을 인자로 넘김 — it이 자연스러움
    println("등록: ${user.name}")
}
```

판단 기준은 이렇다.
- 대상의 **멤버를 설정/호출**하는 게 주 목적이면 `apply`(`this`로 멤버를 직접 만짐).
- 대상을 **다른 함수의 인자로 넘기거나** `it.name`처럼 명시적으로 참조하는 게 주 목적이면 `also`(`it`으로 이름 붙여 받음).

특히 §2.2에서 본 **그림자 문제**를 피하려면 `also`가 더 안전하다. `also`의 `it`은 새 암시적 수신자를 쌓지 않으므로 바깥 스코프의 이름과 충돌하지 않는다.

```kotlin
class Service {
    var timeout = 100
    fun setup() {
        Config().also {
            it.timeout = 5      // 명확히 Config의 timeout (모호함 없음)
        }
        // this@Service 없이도 timeout은 여전히 Service의 것으로만 해소
    }
}
```

`also` 안에서 `it.timeout`은 명백히 `Config`의 것이고, 그냥 `timeout`은 여전히 `Service.timeout`이다. `apply`였다면 `timeout`이 `Config`로 흘러가 그림자가 졌다. 그래서 "이름 충돌이 걱정되는 초기화"에는 `also { it. }`이 방어적으로 안전하다.

### 7.3 also로 검증·확인 흘리기

`also`의 또 다른 관용구는 값을 만들면서 동시에 그 값에 대한 검증이나 확인을 흘리는 것이다.

```kotlin
fun parsePositive(s: String): Int =
    s.toInt()
        .also { require(it > 0) { "양수여야 함: $it" } }   // 검증, 통과 시 원본 흘림
// 검증에 실패하면 require가 예외를 던지고, 통과하면 파싱값을 그대로 반환
```

`also`는 값을 변형하지 않고(변형은 `let`) 곁다리 작업만 하므로, 반환 타입이 원본과 같다는 보장을 준다. 이 "타입을 바꾸지 않는다"는 성질이 파이프라인 안전성의 작은 초석이다.

## 8. takeIf / takeUnless — 조건을 값의 흐름에 끼워 넣기

### 8.1 계약: 조건이 맞으면 값, 아니면 null

스코프 함수 오형제와 함께 다니는 사촌이 `takeIf`/`takeUnless`다. 시그니처는 이렇다.

```kotlin
public inline fun <T> T.takeIf(predicate: (T) -> Boolean): T?
public inline fun <T> T.takeUnless(predicate: (T) -> Boolean): T?
```

`takeIf`는 술어(predicate)가 **참이면 값 자신(`T`), 거짓이면 `null`** 을 낸다. `takeUnless`는 그 반대다. 반환 타입이 `T?`(널 가능)라는 점이 핵심이다 — 조건을 통과 못 하면 널 흐름으로 빠진다. 이것은 컬렉션의 `filter`를 단일 값에 적용한 것과 같다: "이 값이 조건에 맞으면 통과, 아니면 걸러 냄".

```kotlin
val even: Int? = 7.takeIf { it % 2 == 0 }      // 7은 짝수 아님 → null
val positive: Int? = 5.takeIf { it > 0 }       // 5 > 0 → 5
val nonBlank: String? = "".takeUnless { it.isBlank() }  // 빈 문자열 → null
```

### 8.2 `?:`, `?.let`과의 삼각 결합

`takeIf`의 진가는 반환이 `T?`라는 점에서 나온다. 그래서 엘비스 `?:`나 `?.let`과 곧바로 이어진다.

```kotlin
// "조건 맞으면 그 값, 아니면 기본값"
fun clampScore(raw: Int): Int =
    raw.takeIf { it in 0..100 } ?: 0    // 범위 밖이면 0

// "조건 맞을 때만 후속 처리"
fun processFile(path: String) {
    path.takeIf { it.endsWith(".txt") }
        ?.let { readText(it) }           // .txt일 때만 읽음
        ?.let { println(it.length) }
}
```

`takeIf`가 조건을 `null` 여부로 번역해 주면, `?.`와 `?:`라는 널 처리 도구가 그다음을 이어받는다. 이렇게 **조건 → 널 → 널 처리**로 흐름을 잇는 것이 코틀린식 관용구다. `if`로 쓰면 중첩이 생기지만, `takeIf` 체인은 평평하게 흐른다.

```kotlin
// takeIf 없이 if로:
fun clampScore2(raw: Int): Int =
    if (raw in 0..100) raw else 0        // 이 경우엔 if도 충분히 명료

// takeIf가 이기는 경우: 대상이 긴 표현식이라 이름을 두 번 쓰기 싫을 때
fun normalize(input: String): String =
    input.trim().lowercase()
        .takeIf { it.isNotEmpty() } ?: "default"
    // trim().lowercase() 결과를 변수 없이 조건 검사 + 기본값
```

핵심 판단: **대상을 조건에서 다시 언급하기 번거로운 긴 표현식**이면 `takeIf`가 이기고, 짧은 변수 하나면 그냥 `if`가 더 읽기 쉽다.

> **성능 주의**: `takeIf`/`takeUnless`도 `inline`이라 술어 람다를 할당하지 않는다. 다만 반환 타입이 `T?`라, 원시 타입 대상(`Int` 등)에 쓰면 널을 표현하기 위해 **박싱**이 일어날 수 있다([[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]], M5). `7.takeIf { ... }`의 결과 `Int?`는 JVM 백엔드에서 대개 `Integer`로 박싱된다. 극한의 수치 루프에서는 이 점을 의식하되, 일반 코드에서는 무시해도 좋은 수준이다.

## 9. 내부 기계 — inline, contracts, 비지역 반환

지금까지 다섯 함수를 "무엇을 하는가"로 봤다. 이제 "어떻게 그것이 공짜이고 안전한가"를 연다. 답은 세 가지 언어 기능의 조합이다: **inline**(할당 제거), **contracts**(분석 관통), **비지역 반환**(제어 흐름).

### 9.1 전부 inline이라 할당이 없다

다섯 함수와 `takeIf`/`takeUnless`는 전부 `public inline fun`이다([[15 - 인라인 함수와 reified]]). 이것이 스코프 함수를 "부담 없이 어디서나 쓸 수 있게" 만드는 첫째 이유다. `x.let { ... }`를 컴파일하면 `let`의 몸통도, 넘긴 람다의 몸통도 호출 지점에 그대로 펼쳐진다. 즉 다음 두 코드는 컴파일 결과가 사실상 같다.

```kotlin
// 우리가 쓴 것
val len = name?.let { it.trim().length } ?: 0

// 인라인 후 개념적으로 (람다 객체 할당 없음)
val len = if (name != null) name.trim().length else 0
```

`Function1` 구현 객체도, 캡처 래퍼도 만들어지지 않는다. 만약 스코프 함수가 `inline`이 아니었다면 `list.forEach { it.let { ... } }` 같은 흔한 코드가 원소마다 람다 객체를 할당해 파이프라인을 무겁게 했을 것이다. inline이 그 비용을 0으로 만든다. (다만 스코프 함수의 람다 자체가 *또 다른* 비인라인 람다를 캡처하거나, 스코프 함수를 함수 참조로 넘기면 인라인이 깨질 수 있다 — 그 경계는 [[15 - 인라인 함수와 reified]]가 소유한다.)

### 9.2 contracts — 왜 블록 안의 val을 "정확히 한 번"이라 아는가

스코프 함수가 얇은 라이브러리 함수인데도 컴파일러의 흐름 분석이 블록을 *관통*하는 이유는 **계약**(contract)이다. 표준 라이브러리의 스코프 함수 구현은 대략 이렇게 생겼다.

```kotlin
// kotlin-stdlib의 실제 구현 (개념)
public inline fun <T, R> T.let(block: (T) -> R): R {
    contract { callsInPlace(block, InvocationKind.EXACTLY_ONCE) }
    return block(this)
}

public inline fun <T> T.apply(block: T.() -> Unit): T {
    contract { callsInPlace(block, InvocationKind.EXACTLY_ONCE) }
    block()
    return this
}
```

`callsInPlace(block, EXACTLY_ONCE)`는 컴파일러에게 "이 블록은 이 함수가 반환하기 전에 정확히 한 번 호출된다"고 약속한다. 이 계약 덕에 **초기화 분석**이 블록을 넘어 이어진다.

```kotlin
val greeting: String
run {
    greeting = "hello"       // 계약이 EXACTLY_ONCE라 → 컴파일러: "정확히 한 번 대입됨"
}
println(greeting)            // OK — val이 확실히 초기화됐음을 안다
```

계약이 없다면 컴파일러는 "`run`의 블록이 정말 실행되는지" 알 수 없어, `greeting`이 초기화 안 됐을 가능성을 이유로 `println(greeting)`을 거부했을 것이다. `callsInPlace`가 그 불확실성을 없앤다. 같은 원리로 **스마트 캐스트**도 블록을 관통한다.

```kotlin
fun describe(x: Any) {
    val label = when (x) {
        is String -> x.let { "문자열 길이 ${it.length}" }   // it: String (스마트캐스트)
        else -> "기타"
    }
    println(label)
}
```

> **명세 정밀**: `kotlin.contracts`는 코틀린 1.3부터 있던 기능이지만, 사용자 코드에서 `contract { }`를 선언하려면 여전히 `@OptIn(ExperimentalContracts::class)`가 필요하다(2.x 기준 표준 라이브러리 계약은 안정적으로 *소비*되지만, *선언* API는 실험적). 우리가 `let`/`run`을 쓸 때 계약의 이점(초기화·스마트캐스트 관통)은 안정적으로 누린다 — 계약을 직접 *쓰는* 것만 opt-in이다. 계약과 애노테이션 일반론은 [[44 - 애노테이션과 리플렉션]]이 더 다룬다.

### 9.3 비지역 반환 — apply 안의 return은 무엇을 끝내는가

스코프 함수가 `inline`이라는 사실의 세 번째 결과가 **비지역 반환**(non-local return, M41)이다. 인라인 람다 안의 `return`은 람다가 아니라 그 람다를 *둘러싼 함수*를 종료한다([[15 - 인라인 함수와 reified]], [[14 - 클로저와 캡처]]).

```kotlin
fun findFirstEven(nums: List<Int>): Int? {
    nums.forEach { n ->
        n.takeIf { it % 2 == 0 }?.let {
            return it            // findFirstEven을 종료! (takeIf/let/forEach 모두 inline)
        }
    }
    return null
}

findFirstEven(listOf(1, 3, 4, 5))   // => 4
```

`return it`은 `let`이나 `forEach`를 벗어나는 게 아니라 바깥 `findFirstEven` 전체를 종료한다. 세 함수(`forEach`, `takeIf`, `let`)가 전부 인라인이라 가능한 일이다. 만약 `let`이 인라인이 아니었다면 이 `return`은 컴파일 에러거나 `return@let`으로만 가능했을 것이다.

이 성질은 강력하지만 함정도 된다. `apply` 블록 안에 무심코 쓴 `return`이 예상치 못하게 바깥 함수를 끝낼 수 있다.

```kotlin
fun build(flag: Boolean): Config {
    return Config().apply {
        timeout = 10
        if (flag) return@apply      // apply 블록만 벗어남 (라벨 명시)
        // if (flag) return         // ← 이렇게 쓰면 build 전체가 종료 (Config 반환 안 됨!)
        retries = 3
    }
}
```

블록만 벗어나려면 **라벨 반환** `return@apply`([[14 - 클로저와 캡처]])를 명시해야 한다. 그냥 `return`은 바깥 함수를 끝낸다. 이 구분은 스코프 함수 남용의 대표적 사고 지점이다(§10).

### 9.4 컴파일 결과를 눈으로 확인하는 법

스코프 함수가 정말 할당을 안 하는지 의심스러우면(외부 라이브러리 불신의 태도), [[15 - 인라인 함수와 reified]]가 안내한 방식으로 확인할 수 있다. JVM 백엔드에서 `.kt`를 컴파일한 뒤 IntelliJ IDEA의 *Tools → Kotlin → Show Kotlin Bytecode → Decompile*로 역컴파일하면, `x.let { ... }`가 람다 객체 생성 없이 인라인된 것을 눈으로 볼 수 있다. "라이브러리가 그렇다더라"가 아니라 바이트코드로 검증하는 것이 이 시리즈의 태도다. (Native/JS 백엔드는 표현이 다르지만 인라인·계약의 *의미론*은 동일하다 — 여기 서술한 할당 제거·비지역 반환은 언어 수준 보장이다.)

## 10. 선택 규칙과 안티패턴 — 남용의 해부

### 10.1 결정 트리

두 축(수신자 참조 · 반환값)을 질문으로 바꾸면 선택은 기계적이다.

```text
목적이 무엇인가?
│
├─ 대상을 다른 타입으로 "변환"한다 (결과가 필요)
│   ├─ 대상을 it/이름으로 받고 싶다 ............ let
│   └─ 대상의 멤버를 this로 여럿 부른다 ........ run  (널 가능? → ?.run)
│                                              (대상이 인자로 넘겨짐 · 널 아님) → with
│
├─ 대상을 "구성"하고 그 대상을 돌려받는다
│   ├─ 멤버를 this로 직접 설정한다 ............. apply
│   └─ 대상을 it으로 넘기거나 관찰만 한다 ...... also
│
└─ 대상을 "조건"으로 거른다 (맞으면 값, 아니면 null)
    ├─ 조건 참일 때 통과 ....................... takeIf
    └─ 조건 거짓일 때 통과 ..................... takeUnless
```

세 갈래 — 변환 / 구성 / 조건 — 를 먼저 정하고, 그 안에서 `this` vs `it`을 정하면 함수가 하나로 좁혀진다. 이 트리를 손에 쥐면 다섯 함수를 외울 필요가 없다.

### 10.2 안티패턴 1 — 아무것도 안 하는 스코프 함수

가장 흔한 남용은 스코프 함수가 아무 값도 더하지 않는데 습관적으로 쓰는 것이다.

```kotlin
// 나쁨: let이 하는 일이 없다
val len = name.let { it.length }        // == name.length
val x = value.also { }                  // == value (빈 블록)
val y = obj.run { toString() }          // == obj.toString()

// 좋음: 직접 쓴다
val len = name.length
```

`let`은 널 처리나 이름 붙이기 같은 *이유*가 있을 때만 값을 더한다. 단일 멤버 접근에 `let`을 두르면 잡음만 는다. "이 스코프 함수를 지우면 코드가 더 짧고 명료해지는가?"를 물어라. 그렇다면 지워라.

### 10.3 안티패턴 2 — this/it 혼동과 그림자

`apply`/`run`(this)와 `let`/`also`(it)를 섞어 중첩하면 어느 대상을 부르는지 순식간에 흐려진다.

```kotlin
// 나쁨: this와 it이 뒤섞여 대상이 헷갈린다
user.apply {
    name = "A"
    address.let {
        it.city = "Seoul"
        street = "..."          // ⚠️ this.street? 어느 객체의 street인가? (user? address?)
    }
}
```

`street`가 `user`의 것인지 `address`의 것인지 즉시 안 보인다(§2.2 그림자). 중첩할 때는 안쪽에서 `it`을 쓰거나(명시적), 아예 스코프 함수를 풀어 임시 변수로 쪼개는 편이 낫다.

```kotlin
// 좋음: 명시적 it 또는 평범한 변수
val addr = user.address
addr.city = "Seoul"
addr.street = "..."
user.name = "A"
```

### 10.4 안티패턴 3 — 숨은 비지역 반환

§9.3에서 봤듯 스코프 함수 블록 안의 `return`은 바깥 함수를 끝낸다. 긴 `apply`/`run` 블록 중간에 `return`을 숨겨 두면, 그 함수가 어디서 끝나는지 읽는 사람이 놓친다.

```kotlin
// 나쁨: apply 안의 return이 build를 조용히 끝낸다
fun build(): Result = Result().apply {
    step1()
    if (invalid) return       // build 전체를 종료 — Result가 반환 안 됨!
    step2()
}
```

이런 조기 반환은 스코프 함수 밖으로 꺼내 명시적 흐름으로 두는 게 안전하다. 스코프 함수는 "값을 다듬는 짧은 블록"에 어울리지, 복잡한 제어 흐름을 담는 그릇이 아니다.

### 10.5 안티패턴 4 — 세 겹 이상의 중첩

스코프 함수 중첩이 세 겹을 넘으면 암시적 수신자·`it`·반환값이 얽혀 거의 항상 가독성이 무너진다.

```kotlin
// 나쁨: 무엇이 무엇인지 추적 불가
data.let { d ->
    d.items.also { items ->
        items.forEach { item ->
            item.tags.apply { /* this? it? d? */ }
        }
    }
}
```

이 지경이면 스코프 함수의 이득(간결함)이 손실(불명료)에 완전히 잡아먹힌다. 이럴 땐 이름 있는 지역 변수와 평범한 `for`로 풀어야 한다. 스코프 함수는 조미료다 — 한 스푼이 요리를 살리지만, 통째로 부으면 못 먹는다.

### 10.6 요약 표 — 한눈에

| 함수 | 수신자 참조 | 반환값 | 확장? | 주 관용구 | 대표 조합 |
|------|-----------|--------|-------|----------|----------|
| `let` | `it` | 람다 결과 | ✓ | 변환 · 널 처리 | `?.let`, `?.let{}?:` |
| `run` | `this` | 람다 결과 | ✓ | 그룹 호출 → 결과 | `?.run`, 수신자 없는 `run{}` |
| `with` | `this` | 람다 결과 | ✗ | 널 아닌 대상 그룹 호출 | `with(x){}` |
| `apply` | `this` | 수신 객체 | ✓ | 객체 구성 | `X().apply{}` |
| `also` | `it` | 수신 객체 | ✓ | 부수효과 · 관찰 | `.also{ log(it) }` |
| `takeIf` | `it` | `T?` | ✓ | 조건 필터 | `.takeIf{}?:` |
| `takeUnless` | `it` | `T?` | ✓ | 역조건 필터 | `.takeUnless{}?:` |

이 표 한 장이 이 장 전체의 압축이다. 두 축(참조·반환)과 세 관용구(변환·구성·조건)만 기억하면, 다섯 함수는 격자 위의 좌표로 정확히 되살아난다.

---

우리는 다섯 개의 이름에서 출발해 두 개의 축에 도달했다. `this`냐 `it`이냐 — 대상을 암시적 수신자로 삼는가, 이름 붙은 인자로 받는가. 람다 결과냐 수신 객체냐 — 대상을 변환하는가, 구성하고 돌려받는가. 이 $2 \times 2$ 격자가 `let`·`run`·`with`·`apply`·`also`를 정확히 배치했고, 여기에 조건을 널 흐름으로 번역하는 `takeIf`/`takeUnless`가 사촌으로 붙었다. 그 밑에서 이 관용구를 공짜이자 안전하게 만든 것은 새 언어 기능이 아니라 이미 배운 세 가지의 조합이었다 — `inline`이 람다 할당을 지웠고(15장), 계약이 초기화·스마트 캐스트 분석을 블록 너머로 이었으며(6장), 비지역 반환이 `apply` 속 `return`에 바깥 함수를 끝내는 힘을 줬다(14·15장). 그래서 스코프 함수는 마법이 아니라 조합이고, 그 조합을 이해하면 남용의 함정 — 빈 블록, `this`/`it` 그림자, 숨은 `return`, 세 겹 중첩 — 도 함께 보인다. 그리고 이 장의 심장인 수신 객체 지정 람다 `T.() -> R`는 이 장에서 멈추지 않는다. 그것을 도메인 타입으로 특화하고 `@DslMarker`로 스코프를 통제하면, 코틀린으로 새로운 언어를 짓는 [[37 - 타입 안전 빌더와 DSL]]의 문이 열린다.

## 핵심 요약

- **다섯 스코프 함수는 딱 두 축의 조합이다: 대상을 `this`(수신자)로 받는가 `it`(인자)로 받는가, 그리고 람다 결과를 돌려주는가 수신 객체를 돌려주는가.** 이 $2 \times 2$ 격자에 `let`(it·결과), `run`/`with`(this·결과), `apply`(this·수신자), `also`(it·수신자)가 정확히 배치된다.
- **`let`은 값을 `it`으로 받아 변환해 결과를 낸다.** 널 안전 호출과 결합한 `x?.let { }`는 "널 아니면 실행"의 표현식 버전이며, 블록 안에서 `it`은 널 아닌 타입으로 확정된다(M13 회피, M32 결합).
- **`run`은 대상을 `this`로 받아 그룹 호출 후 결과를 낸다.** `with`는 확장이 아니라 대상을 인자로 받는 형제라 널 안전 호출을 못 붙인다 — 널 가능 대상엔 `?.run`이 정답이다.
- **`apply`는 대상을 `this`로 구성하고 그 대상을 돌려준다.** 블록의 마지막 표현식이 무엇이든 반환값은 항상 수신 객체다 — 이 대칭이 `apply`(수신자)와 `run`(결과)을 가르는 전부이며, 착각하면 타입 버그가 난다.
- **`also`는 대상을 `it`으로 받아 부수효과를 흘리고 원본을 돌려준다.** `it`은 새 암시적 수신자를 쌓지 않아 그림자 문제가 없어, 이름 충돌이 걱정되는 초기화에 `apply`보다 방어적으로 안전하다.
- **`takeIf`/`takeUnless`는 조건을 `T?`(널 여부)로 번역한다.** 그래서 `?.`·`?:`와 삼각으로 이어져 "조건 → 널 → 널 처리"의 평평한 흐름을 만든다. 단, 원시 대상엔 널 표현을 위한 박싱이 낄 수 있다(M5).
- **다섯 함수는 전부 `public inline`이라 람다를 힙에 할당하지 않는다(M17 관련).** 뜨거운 루프 안에서 수백만 번 써도 객체 생성이 반복되지 않는다 — 스코프 함수를 부담 없이 쓸 수 있는 근본 이유다.
- **`callsInPlace(block, EXACTLY_ONCE)` 계약이 초기화·스마트 캐스트 분석을 블록 너머로 잇는다.** 그래서 `run { greeting = ... }` 뒤에서 컴파일러가 `val greeting`을 "정확히 한 번 초기화됨"으로 안다. 계약 *소비*는 안정적이고, 계약 *선언*만 실험적 opt-in이다.
- **스코프 함수 블록 안의 `return`은 인라인 덕에 바깥 함수를 종료한다(비지역 반환, M41).** `apply` 속 무심한 `return`이 객체를 반환하지 않고 함수를 끝낼 수 있으니, 블록만 벗어나려면 `return@apply` 라벨을 명시해야 한다.
- **수신 객체 지정 람다 `T.() -> R`가 `this` 계열(run/with/apply)의 심장이다.** 암시적 수신자의 멤버를 이름 없이 부르게 하지만, 바깥 스코프와 동명 멤버가 충돌하면 조용한 그림자가 지므로 `this@Label`로 못박아야 한다.
- **선택은 기계적이다: 변환이면 `let`/`run`, 구성이면 `apply`, 관찰이면 `also`, 조건이면 `takeIf`.** 그 뒤 `this`냐 `it`이냐만 정하면 함수가 하나로 좁혀진다 — 이름을 외우지 말고 두 축과 세 관용구를 외워라.
- **스코프 함수는 조미료다: 빈 블록·this/it 혼동·숨은 return·세 겹 중첩은 이득(간결)을 손실(불명료)로 뒤집는다.** "이 스코프 함수를 지우면 더 명료한가?"가 남용을 가르는 리트머스다.

## 연결 노트

- [[13 - 함수 타입과 람다와 함수 참조]] — 이 장의 토대. 수신 객체 지정 람다 `T.() -> R`의 타입 문법과 `it`(M42)의 정본. 스코프 함수는 그 타입을 부리는 관용구다.
- [[14 - 클로저와 캡처]] — 스코프 함수 블록도 클로저다. 라벨 반환 `return@apply`와 캡처의 수명이 여기서 온다.
- [[15 - 인라인 함수와 reified]] — 다섯 함수가 전부 `inline`이라 할당이 없고 비지역 반환(M41)이 가능한 이유의 정본.
- [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]] — `?.let`·`?:`·`takeIf ?:` 조합이 조립하는 널 처리 관용구의 부품(M13, M32)을 소유.
- [[35 - 확장 함수와 프로퍼티]] — `let`/`run`/`apply`/`also`가 확장 함수라는 사실의 뿌리. 정적 디스패치와 수신자 개념(M14~M16).
- [[37 - 타입 안전 빌더와 DSL]] — 수신 객체 지정 람다를 도메인 타입으로 특화하고 `@DslMarker`로 다중 수신자 스코프를 통제하는 이 장의 연장선.
- [[11 - 변수와 초기화 - val과 const와 lateinit]] — `apply`가 `val`(재대입 불가지만 가변 대상, M3)과 결합해 "선언 + 초기 구성"을 붙이는 관용구.
- [[17 - 표현식으로서의 제어 흐름 - if와 when]] — 수신자 없는 `run { }`이 여러 문장을 하나의 표현식으로 접는 것은 `if`/`when` 표현식과 같은 사고의 연장.
- [[41 - 예외와 Nothing]] — `?:` 우변의 `throw`, `also { require(...) }`처럼 스코프 함수와 예외/`Nothing`이 만나는 지점.
- [[31 - 중첩 클래스와 이너 클래스와 익명 객체]] — `this@Outer` 레이블 수신자 관용구의 소유 장. 중첩 스코프 함수의 그림자를 푸는 열쇠.
