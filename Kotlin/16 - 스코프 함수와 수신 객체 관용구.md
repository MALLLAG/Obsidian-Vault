[[13 - 함수 타입과 람다와 함수 참조]]에서는 함수를 값으로 다루는 문법을 배웠고, 그 장 끝에서 점이 붙은 함수 타입 `A.() -> B`, 즉 **수신 객체 지정 람다**(lambda with receiver)를 소개하면서 "이것이 스코프 함수와 DSL의 토대"라고 예고했다.

[[14 - 클로저와 캡처]]에서는 그 람다가 자유 변수를 어떻게 캡처하는지를 살펴보았다. [[15 - 인라인 함수와 reified]]에서는 `inline`이 람다 본문을 호출 지점에 복사해 할당과 가상 호출을 없애고 **비지역 반환**(non-local return)을 가능하게 한다는 점을 설명했다.

이 장은 세 장에서 다룬 내용을 바탕으로 한다. 스코프 함수는 새로운 언어 기능이 아니라, 표준 라이브러리에 정의된 평범한 `inline` 확장 함수 다섯 개일 뿐이다. 그런데도 이렇게 얇은 도구가 코틀린 코드의 모양을 크게 바꾼다는 점이 흥미롭다.

이 장에서는 `let`/`run`/`with`/`apply`/`also` 다섯 함수와 비슷한 함수인 `takeIf`/`takeUnless`의 **정확한 계약**을 다룬다. 계약이란 무엇을 수신자로 넘기는지, 블록 안에서 수신자를 `this`로 부르는지 `it`으로 부르는지, 무엇을 반환하는지를 말한다.

다섯 함수는 겉보기에는 제각각이지만, 수신자 참조 방식과 반환값이라는 두 축이 만드는 $2 \times 2$ 격자에 거의 정확히 들어맞는다.

이어서 이 관용구를 떠받치는 내부 동작도 살펴본다. 스코프 함수가 람다를 할당하지 않는 이유(inline), 블록 안에서 선언한 `val`이 정확히 한 번 초기화된다는 사실을 컴파일러가 아는 이유(contracts), `apply` 안의 `return`이 바깥 함수를 종료하는 이유(비지역 반환)가 그것이다.

`A.() -> B`라는 타입 자체의 문법과 JVM 표현은 13장(함수 타입과 람다)에서 다루었고, 이 장은 그 타입을 활용하는 관용구에 집중한다.

이 관용구로 **타입 안전 빌더**를 만들고 `@DslMarker`로 수신자 스코프를 제어하는 방법은 [[37 - 타입 안전 빌더와 DSL]]에서, 확장 함수의 정적 디스패치는 [[35 - 확장 함수와 프로퍼티]]에서, 널 안전 연산자 `?.`/`?:`는 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 자세히 설명한다. 이 장에서는 그 연산자들을 스코프 함수와 조합하는 관용구를 다룬다.

## 1. 두 개의 축: 스코프 함수를 나누는 좌표계

### 1.1 다섯 개의 이름, 두 개의 질문

처음 스코프 함수를 배울 때 헷갈리는 이유는 이름이 다섯 개이기 때문이다. `let`, `run`, `with`, `apply`, `also`가 각각 무엇인지 외우려고 하면 거의 반드시 헷갈린다. 하지만 이 다섯 함수는 본질적으로 두 가지 질문에 대한 답을 조합한 것일 뿐이다.

**질문 1: 블록 안에서 대상을 어떻게 부르는가?**

- **`this`**(수신자로): 대상이 암시적 수신자가 되므로 이름 없이 대상의 멤버를 호출할 수 있다. 람다 타입은 `T.() -> R`(수신 객체 지정)이다.
- **`it`**(인자로): 대상이 람다의 유일한 파라미터로 전달되고, `it`이라는 이름으로 참조된다. 람다 타입은 `(T) -> R`(일반 람다)이다.

**질문 2: 블록이 끝나면 무엇을 반환하는가?**

- **람다의 결과**(block result): 블록의 마지막 표현식 값이다. 대상을 *변환*할 때 쓴다.
- **수신 객체 자신**(the object): 대상을 그대로 다시 반환한다. 대상을 *구성*하거나 *관찰*한 뒤 흐름을 이어 갈 때 쓴다.

이 두 질문이 $2 \times 2$ 격자를 만들고, 다섯 함수는 다음과 같이 배치된다.

| | **`this`로 (수신자)** | **`it`으로 (인자)** |
|---|---|---|
| **람다 결과 반환** | `run`, `with` | `let` |
| **수신 객체 반환** | `apply` | `also` |

`run`과 `with`가 같은 칸에 있는 이유는, 둘의 차이가 하나뿐이기 때문이다. `with`만 확장 함수가 아닌 일반 함수여서 대상을 인자로 받는다(5절). 나머지 넷은 모두 확장 함수이므로 `대상.함수 { }` 형태로 호출한다. 따라서 실제로는 **네 가지 선택지**(`this`+결과, `this`+수신자, `it`+결과, `it`+수신자)만 기억하면 된다. 이름을 외우기보다 두 축을 기억하는 편이 낫다.

### 1.2 표준 라이브러리의 실제 시그니처

추상적인 격자 대신 코틀린 표준 라이브러리(`kotlin-stdlib`)에 실제로 선언된 시그니처를 보자. 다섯 함수는 모두 `public inline`이다.

```kotlin
// kotlin.let
public inline fun <T, R> T.let(block: (T) -> R): R

// kotlin.run (확장 형태)
public inline fun <T, R> T.run(block: T.() -> R): R

// kotlin.run (수신자 없는 형태)
public inline fun <R> run(block: () -> R): R

// kotlin.with
public inline fun <T, R> with(receiver: T, block: T.() -> R): R

// kotlin.apply
public inline fun <T> T.apply(block: T.() -> Unit): T

// kotlin.also
public inline fun <T> T.also(block: (T) -> Unit): T
```

시그니처에 두 축이 그대로 드러난다.

- **수신자 참조**: 람다 파라미터 타입이 `T.() -> R`(수신 객체 지정 람다)이면 블록 안에서 `this`를 쓰고, `(T) -> R`(일반 람다)이면 `it`을 쓴다. `run`/`with`/`apply`는 `T.()`이고, `let`/`also`는 `(T)`이다.
- **반환값**: 반환 타입이 `R`(제네릭 결과)이면 람다 결과를 반환하고, `T`(수신자 타입)이면 수신 객체를 반환한다. `let`/`run`/`with`는 `R`이고, `apply`/`also`는 `T`이다.
- `apply`/`also`의 블록 반환 타입이 `-> Unit`이라는 점도 눈여겨볼 만하다. 두 함수는 수신자를 반환하므로 블록의 결과를 처음부터 버리도록 설계되었다. 그래서 블록 안에서 마지막에 무엇을 쓰든 반환값에는 영향이 없다.

> [!note] 명세 기준
> 이 함수들은 언어 키워드가 아니라 **라이브러리 함수**이다. 컴파일러에 `let`을 위한 특별한 규칙은 없다. 다만 `inline`이므로 15장(인라인 함수와 reified)에서 설명한 인라이닝과 비지역 반환 규칙이 적용되고, 뒤에서 볼 **계약**(contract) 애노테이션 덕분에 스마트 캐스트와 초기화 분석이 블록 안까지 이어진다. 즉 스코프 함수의 "특별한" 동작은 모두 이미 있는 언어 기능을 조합한 결과이다.

> [!info] 역사 메모
> `with`는 코틀린 초기부터 있던 함수로, 자바에는 없는 "수신자 블록"을 라이브러리로 흉내 낸 첫 사례이다. 이름은 파스칼과 비주얼베이직의 `with` 문에서 빌렸지만, 코틀린의 `with`는 문법이 아니라 고차 함수이다. `let`/`apply`/`also`/`run`은 그 뒤에 표준 라이브러리 관용구로 다듬어졌고, 이름이 겹치던 혼란기를 거쳐 지금의 "두 축" 체계로 자리 잡았다.
>
> `also`는 비교적 늦게(1.1) 추가되어 "`apply`의 `it` 버전"이라는 빈칸을 채웠다. 이렇게 발전한 결과, 지금의 다섯 함수는 격자를 거의 빈틈없이 채운다. 유일하게 빈 칸은 "`with`의 확장·널 안전 버전"인데, 이 역할은 `run`이 함께 맡는다.

### 1.3 왜 이런 조합인가: 관용구와의 대응

두 축의 각 조합은 자연스럽게 하나의 *관용구*에 대응한다. 스코프 함수가 우연히 다섯 개가 된 것이 아닌 이유가 여기에 있다.

```text
              반환: 람다 결과 R          반환: 수신 객체 T
            ┌────────────────────┬────────────────────┐
  this로    │  run / with        │  apply             │
 (수신자)   │  "이 객체 위에서    │  "이 객체를 구성해  │
            │   계산해 결과를"    │   그대로 돌려줘"    │
            ├────────────────────┼────────────────────┤
  it으로    │  let               │  also              │
 (인자)     │  "이 값을 이름 붙여 │  "이 값에 부수효과  │
            │   변환해"          │   흘리고 계속 흘려" │
            └────────────────────┴────────────────────┘
```

- `let`: 값 하나를 `it`(또는 지정한 이름)으로 받아 **변환**한다. 널 처리(`?.let`)에 가장 많이 쓰인다.
- `run`: 수신자 위에서 여러 문장을 실행해 **결과**를 만든다. `with`의 확장·널 안전 버전이다.
- `with`: 수신자를 인자로 명시하고, 그 수신자 위에서 **결과**를 만든다. 널이 아닌 대상에 대해 여러 호출을 묶을 때 쓴다.
- `apply`: 수신자를 `this`로 받아 **구성**하고, 그 수신자를 반환한다. 객체 초기화에 가장 많이 쓰인다.
- `also`: 값을 `it`으로 받아 로깅이나 검증 같은 **부수 효과**를 실행하고, 원본을 그대로 넘긴다.

이 대응을 알고 있으면 코드를 쓸 때 "무엇을 하려는가"만 정하면 함수가 정해진다. 변환이면 `let`, 구성이면 `apply`, 관찰이면 `also`를 쓴다. 다음 절부터 이 대응을 하나씩 확인한다. 그 전에 세로축, 즉 대상을 `this`로 부르게 만드는 "수신 객체 지정 람다"를 한 번 더 살펴보아야 한다. 이것이 스코프 함수의 핵심이고, 이 장의 내용이 DSL(37장)로 이어지는 연결 고리이기 때문이다.

## 2. 수신 객체 지정 람다: 관용구의 문법적 토대

### 2.1 `T.() -> R`는 무엇을 바꾸는가

13장(함수 타입과 람다)에서 함수 타입 `(A) -> B`를 살펴보았다. **수신 객체 지정 람다**의 타입 `A.() -> B`는 여기에 점 하나(`A.`)를 더한 것이다. 이 점이 하는 일은 단순하지만 근본적이다. 첫 번째 인자를 *암시적 수신자*로 바꾼다.

```kotlin
// 보통 함수 타입: 대상이 파라미터로
val describe1: (String) -> Int = { s -> s.length }
describe1("hello")            // => 5, 안에서 s로 참조

// 수신 함수 타입: 대상이 this로
val describe2: String.() -> Int = { this.length }
"hello".describe2()          // => 5, 안에서 this(또는 생략)로 참조
"hello".describe2()          // 확장 함수처럼 점 표기로 호출
```

`describe2`의 본문 `{ this.length }`에서 `this`는 호출 대상 문자열이다. 그리고 `this`는 대개 **생략할 수 있다**. `{ length }`라고만 써도 `this.length`로 해석된다. 이 생략 덕분에 `apply`/`with`/`run` 안에서 대상의 멤버를 이름 없이 연달아 호출할 수 있다.

```kotlin
class Rectangle {
    var width: Double = 0.0
    var height: Double = 0.0
    fun area() = width * height
}

val r = Rectangle().apply {
    width = 3.0        // this.width = 3.0
    height = 4.0       // this.height = 4.0
}                      // apply는 r을 돌려줌 (수신자 반환)
println(r.area())      // => 12.0
```

`apply`의 블록 타입은 `Rectangle.() -> Unit`이다. 그래서 블록 안의 `width`와 `height`는 바로 수신자의 프로퍼티로 해석된다. 만약 `apply`가 일반 람다 `(Rectangle) -> Unit`를 받았다면 `it.width = 3.0`처럼 써야 했을 것이고, 그렇게 동작하는 함수가 바로 `also`이다.

### 2.2 암시적 수신자의 해석 규칙과 가려짐

`this`를 생략할 수 있어 편하지만, 여기에는 함정이 있다. 블록 안에서 이름 하나를 쓰면 컴파일러는 **가장 가까운 암시적 수신자**부터 바깥쪽으로 차례로 찾아 그 이름을 해석한다. 수신 객체 지정 람다는 암시적 수신자를 하나 더 쌓기 때문에, 바깥 스코프에 같은 이름의 멤버가 있으면 충돌할 수 있다.

```kotlin
class Config {
    var timeout: Int = 30
    fun log(msg: String) = println("config: $msg")
}

class Service {
    var timeout: Int = 100          // 바깥에도 timeout
    fun setup() {
        Config().apply {
            timeout = 5             // ⚠️ 어느 timeout? → Config.timeout (가까운 수신자 우선)
            log("configured")       // Config.log (Service엔 log 없음)
        }
        println(timeout)            // => 100 (Service.timeout은 안 바뀜)
    }
}
```

`apply` 블록 안의 `timeout = 5`는 가장 가까운 암시적 수신자인 `Config`의 프로퍼티로 해석된다. 그것이 의도였다면 문제없지만, `Service.timeout`을 바꾸려 했다면 아무 경고 없이 버그가 생긴다. 바깥 수신자를 명시하려면 **레이블을 붙인 `this`** 를 쓴다(`this@Outer` 관용구는 [[31 - 중첩 클래스와 이너 클래스와 익명 객체]]에서 다룬다).

```kotlin
Config().apply {
    this.timeout = 5                // Config.timeout (명시)
    this@Service.timeout = 200      // Service.timeout (바깥 수신자)
}
```

> [!warning] 흔한 오해
> "`apply` 안에서는 항상 새 객체의 멤버가 우선한다"고만 생각하면 위험하다. 새 객체의 멤버가 우선하는 것은 맞지만, 새 객체에 *없는* 이름은 바깥 수신자에서 찾아 해석된다. 그래서 오타가 나거나 리팩터링으로 프로퍼티 이름이 바뀌면, 컴파일 에러가 나는 대신 바깥 수신자의 멤버를 아무 경고 없이 건드릴 수 있다. `it`을 쓰는 `also`/`let`에는 이런 가려짐 문제가 없으므로 이 점에서는 더 안전하다(7절, 10절).

### 2.3 확장 함수와 같은 원리

수신 객체 지정 람다는 사실 35장(확장 함수와 프로퍼티)의 확장 함수와 같은 메커니즘을 바탕으로 한다. 확장 함수 `fun String.foo()`를 컴파일하면 `String`을 첫 번째 인자(수신자)로 받는 정적 메서드가 되는 것처럼, `String.() -> R` 람다도 내부적으로는 수신자를 첫 번째 인자로 받는 `Function1` 계열로 표현된다(정확한 표현은 13장에서 설명했다). 둘의 차이는 *호출 문법*뿐이다.

원리가 같기 때문에, 수신 객체 지정 람다를 파라미터로 받는 함수(`apply`, `with`, `buildString`, DSL 빌더 등)는 모두 "블록 안에서 특정 타입이 암시적 수신자가 된다"는 같은 사용 경험을 준다.

이 점이 37장(타입 안전 빌더와 DSL)으로 이어진다. `apply`가 "임의의 `T`를 수신자로 만드는" 범용 도구라면, DSL 빌더는 "HTML 노드나 설정 트리 같은 특정 도메인 타입을 수신자로 만드는" 특화 도구이다. 스코프 함수를 이해하면 DSL은 그것을 일반화한 것에 지나지 않는다. 이제 다섯 함수를 하나씩, 각 함수의 관용구와 함께 살펴보자.

## 3. let: 값에 이름을 붙여 변환한다

### 3.1 계약: `it`으로 받아 결과를 반환한다

`let`의 시그니처는 `T.let(block: (T) -> R): R`이다. 수신자 `T`는 블록에 **인자로**(`it`) 전달되고, 블록의 **결과 `R`** 이 반환된다. 즉 `let`은 "이 값을 `it`이라는 지역 이름에 담고, 그 값으로 무언가를 계산해 결과를 반환하라"는 관용구이다.

```kotlin
val name = "  Alice  "
val len: Int = name.let { it.trim().length }   // it = name
println(len)                                    // => 6
```

이 예에서는 `let`이 없어도 `name.trim().length`로 충분하다. `let`이 실제로 쓸모 있는 곳은 두 군데로, **널 처리**(3.2절)와 **긴 표현식에 임시 이름 붙이기**(3.3절)이다.

`it`은 특별한 이름이 아니다. 13장에서 설명했듯이 `it`은 *파라미터가 하나인 람다의 암시적 파라미터 이름*일 뿐이므로, 원하면 직접 이름을 붙여 가독성을 높일 수 있다.

```kotlin
val len = name.let { raw -> raw.trim().length }   // it 대신 raw로 명명
```

### 3.2 널 처리의 대표 관용구: `?.let`

코틀린 코드에서 `let`이 가장 자주 보이는 이유는 안전 호출 `?.`(6장 널 안전성)와 함께 쓰이기 때문이다. `nullable?.let { }`는 "널이 아니면 블록을 실행하고, 널이면 블록 전체를 건너뛰고 `null`을 반환한다"는 관용구를 만든다.

```kotlin
fun greet(name: String?) {
    name?.let {
        // 이 안에서 it은 String (널 아님) — 스마트 캐스트
        println("Hello, ${it.uppercase()}")
    }
    // name이 null이면 블록 전체를 건너뛴다
}

greet("bob")   // => Hello, BOB
greet(null)    // (아무것도 출력 안 함)
```

핵심은 블록 안에서 `it`의 타입이 `String?`가 아니라 **`String`**(널 아님)이라는 점이다. `?.`가 널을 걸러 냈으므로 `let`의 인자 `T`는 널이 아닌 타입으로 확정된다. 이 관용구는 `if (name != null) { ... }`를 표현식으로 쓴 것과 같다.

특히 대상이 `var`이거나 커스텀 게터여서 6장에서 설명한 스마트 캐스트가 적용되지 않을 때 유용하다. `?.let`은 값을 지역 이름 `it`에 *복사*하므로, 그사이에 다른 스레드나 게터가 값을 바꿔도 `it`은 안전하다.

```kotlin
class Box(var content: String?)     // var 프로퍼티 — 스마트 캐스트 불가

fun show(box: Box) {
    // box.content가 var라 if (box.content != null) 안에서도 스마트캐스트 안 됨
    box.content?.let { c ->
        println(c.length)           // c는 안전하게 캡처된 널 아닌 값
    }
}
```

여기에 엘비스 연산자 `?:`(6장 널 안전성)를 붙이면 "널이면 기본값을 쓴다"는 관용구가 된다.

```kotlin
fun lengthOrZero(s: String?): Int =
    s?.let { it.length } ?: 0        // 널이면 let 건너뛰고 → null → ?: 로 0
```

`s`가 널이면 `s?.let { }` 전체가 `null`이 되고, `?:`가 그 `null`을 받아 `0`을 반환한다. `?:`의 우변에는 `throw`나 `return`도 올 수 있으므로([[41 - 예외와 Nothing]]), "널이면 예외를 던지거나 일찍 반환한다"는 형태로도 확장할 수 있다.

### 3.3 표현식에 임시 이름 붙이기

`let`의 두 번째 쓰임새는 이름 없는 중간 표현식에 지역 이름을 붙여 가독성을 높이는 것이다. 특히 체인 중간의 결과를 그 자리에서만 쓰면서도, 그 결과가 무엇인지 이름으로 드러내고 싶을 때 유용하다.

```kotlin
val result = readNumbers()
    .filter { it > 0 }
    .let { positives -> positives.sum() to positives.size }
    // positives라는 이름으로 두 번 참조하며 (합, 개수) 쌍을 만든다
```

`let` 없이 같은 일을 하려면 `positives`를 별도의 `val`로 선언해야 한다. `let`을 쓰면 그 지역 변수가 블록 스코프 안에만 있으므로 바깥 스코프를 어지럽히지 않는다. 다만 이 관용구를 남용하면 오히려 코드의 흐름이 끊긴다(10절).

> [!caution] 성능 주의
> `let`은 `inline` 함수이다(9절). 그래서 `name.let { ... }`는 람다 객체를 **할당하지 않고**, 블록 본문이 호출 지점에 그대로 펼쳐진다. 자주 실행되는 루프(hot loop) 안에서 `?.let`을 수백만 번 써도 힙 할당이 반복되지 않는다. 스코프 함수를 부담 없이 쓸 수 있는 근본적인 이유가 이것이다. 단, `let`을 함수 참조 `::let`으로 넘기는 것처럼 인라인되지 않는 방식으로 쓰면 이 이점은 사라진다.

## 4. run: 수신자 위에서 블록을 실행해 결과를 반환한다

### 4.1 계약: `this`로 받아 결과를 반환한다

`run`의 확장 형태 시그니처는 `T.run(block: T.() -> R): R`이다. 반환값(`R`, 람다 결과)은 `let`과 같지만, 대상을 **`this`로**(수신자로) 받는다는 점이 다르다. 즉 `run`은 "이 객체를 수신자로 삼아 여러 문장을 실행하고, 마지막 표현식을 결과로 반환하라"는 관용구이다.

```kotlin
class Circle(val radius: Double) {
    fun circumference() = 2 * Math.PI * radius
    fun area() = Math.PI * radius * radius
}

val summary: String = Circle(2.0).run {
    // this = Circle(2.0), 멤버를 이름 없이 호출
    "둘레=%.2f, 넓이=%.2f".format(circumference(), area())
}
println(summary)   // => 둘레=12.57, 넓이=12.57
```

같은 코드를 `let`으로 쓰면 `it.circumference()`, `it.area()`처럼 매번 `it.`을 붙여야 한다. 대상의 멤버를 여러 번 호출할 때는 `this`로 받는 `run`이 더 간결하다. 반대로 대상을 다른 함수의 인자로 넘기거나 `it`이라는 이름으로 명시하고 싶다면 `let`이 낫다. 이 `it`과 `this` 사이의 선택이 10절 결정 트리의 한 축이다.

### 4.2 `?.run`: 널 안전하게 여러 호출 묶기

`run`도 확장 함수이므로 `?.`와 함께 쓸 수 있다. `nullable?.run { }`은 "널이 아니면 그 객체를 수신자로 삼아 블록을 실행하고 결과를 반환한다"는 뜻이다.

```kotlin
class Account(val balance: Long, val owner: String)

fun report(acc: Account?): String =
    acc?.run {
        "$owner: $balance"      // this.owner, this.balance
    } ?: "계좌 없음"
```

이 패턴은 `with`(5절)로는 깔끔하게 쓸 수 없다. `with`는 확장 함수가 아니라 대상을 인자로 받는 함수여서 `acc?.with`처럼 안전 호출을 붙일 수 없기 때문이다. 널이 될 수 있는 대상을 수신자로 두고 여러 호출을 묶으려면 `?.run`을 쓰면 된다.

### 4.3 수신자 없는 `run`: 여러 문장을 표현식 하나로 묶기

`run`에는 확장 함수가 아닌 두 번째 오버로드 `run(block: () -> R): R`이 있다. 수신자 없이 블록을 실행해 결과를 반환한다. 얼핏 쓸모없어 보이지만, 이 형태는 **여러 문장을 표현식 하나로 묶는** 도구이다. 코틀린에서 `if`/`when`은 표현식이지만([[17 - 표현식으로서의 제어 흐름 - if와 when]]), 여러 문장이 필요한 초기화에는 블록이 필요하다. 수신자 없는 `run`은 그 블록을 값으로 만든다.

```kotlin
val connectionString: String = run {
    val host = System.getenv("DB_HOST") ?: "localhost"
    val port = System.getenv("DB_PORT") ?: "5432"
    "jdbc:postgresql://$host:$port/app"     // 마지막 표현식이 결과
}
```

`run { }`이 없다면 `host`와 `port`가 바깥 스코프로 새어 나가거나, 별도의 함수를 만들어야 한다. `run`은 계산을 지역 스코프 안에 가두고 결과 하나만 밖으로 내보낸다. 프로퍼티를 초기화하거나 `when` 분기 안에서 쓸 때 특히 유용하다.

이 형태는 **비지역 반환**(9.3절)과 결합해 일찍 종료하는 관용구를 만들기도 한다.

```kotlin
fun process(input: String?) {
    val data = run {
        if (input.isNullOrBlank()) return   // 바깥 process()를 종료 (비지역 반환, M41)
        input.trim()
    }
    println(data.length)
}
```

`run`이 `inline`이므로 그 안의 `return`은 `run`이 아니라 바깥 함수 `process`를 종료한다(자세한 내용은 9.3절). 이 관용구는 강력하지만 흐름을 읽기 어렵게 만들 수 있으므로 주의해야 한다(10절).

## 5. with: 수신자를 인자로 받는 비확장 함수

### 5.1 계약: 확장 함수가 아닌 `run`

`with`의 시그니처는 `with(receiver: T, block: T.() -> R): R`이다. 대상을 `this`로 받아 결과를 반환한다는 점에서 `run`과 완전히 같은 일을 하지만, **확장 함수가 아니다**. 대상을 첫 번째 인자로 명시해서 넘기므로 호출 문법이 다르다.

```kotlin
val c = Circle(3.0)

// run: 확장 — 점 표기
val a1 = c.run { area() }

// with: 비확장 — 대상을 인자로
val a2 = with(c) { area() }
```

두 호출의 결과는 같다. 차이는 문법과 널 안전성뿐이다.

| | `x.run { }` | `with(x) { }` |
|---|---|---|
| 형태 | 확장 함수 | 일반 함수 (인자) |
| 널 안전 | `x?.run { }` 가능 | `x?.with` 불가 |
| 대상이 널이 아님이 확실할 때 | 둘 다 가능 | 자연스러움 |
| 체인 중간 | 자연스러움 (`x.foo().run {}`) | 어색함 (`with(x.foo()) {}`) |

### 5.2 with와 run 중 무엇을 쓸까

경험칙은 다음과 같다. **대상이 널이 아님이 확실하고, 체인의 일부가 아니라 "이 객체로 작업하는 블록"을 따로 열고 싶을 때**는 `with`가 문장처럼 잘 읽힌다.

```kotlin
val html: String = with(StringBuilder()) {
    append("<div>")
    append("내용")
    append("</div>")
    toString()          // 마지막 표현식 = 결과
}
```

`with(receiver) { ... }`는 영어로 "receiver를 가지고(with) 다음을 하라"로 읽히므로, 여러 호출을 묶는다는 의도가 문장 첫머리에 드러난다. 반면 대상이 널이 될 수 있거나 체인 중간에 있다면 `?.run`이 낫다. 기능은 같으므로 **가독성**만이 선택 기준이다.

> [!warning] 흔한 오해
> "`with`는 `apply`처럼 객체를 설정하는 함수"라고 오해하는 경우가 많지만 그렇지 않다. `with`는 대상이 아니라 **결과**(`R`)를 반환한다. 위 예에서 마지막에 `toString()`을 쓰지 않으면 `with` 블록의 결과는 마지막 `append(...)`의 반환값(`StringBuilder`)이 된다.
>
> 결과가 우연히 대상처럼 보이는 것은 `append`가 자기 자신을 반환하기 때문이고, `with`의 계약 때문이 아니다. 대상을 확실히 돌려받으려면 `apply`를 써야 한다(6절).

### 5.3 수신자를 여러 겹 열 때의 함정

`with`(그리고 `run`/`apply`)를 중첩하면 암시적 수신자가 여러 겹 쌓인다. 그러면 2.2절에서 본 가려짐 문제가 더 커진다.

```kotlin
class Outer { fun name() = "outer" }
class Inner { fun name() = "inner" }

with(Outer()) {
    with(Inner()) {
        name()              // => "inner" (가장 가까운 수신자)
        this@with           // Inner  — 레이블은 함수명 기준
    }
}
```

중첩된 `with`에서 `name()`은 가장 안쪽의 `Inner`로 해석된다. 바깥 `Outer`의 `name()`을 호출하려면 레이블이 필요한데, 두 블록이 모두 `with`여서 레이블이 모호해진다. 이런 다중 수신자 스코프를 안전하게 제어하는 장치가 37장(타입 안전 빌더와 DSL)의 `@DslMarker`이다. `@DslMarker`는 바깥 암시적 수신자를 가려서 실수로 호출하지 못하게 막는다. 스코프 함수를 중첩하면 편하지만, 세 겹을 넘으면 거의 항상 가독성이 크게 떨어진다(10절).

## 6. apply: 객체를 구성하고 그 객체를 반환한다

### 6.1 계약: `this`로 받아 수신자를 반환한다

`apply`의 시그니처는 `T.apply(block: T.() -> Unit): T`이다. 대상을 **`this`로** 받고, 블록의 결과는 버린 채(`-> Unit`) **대상 자신(`T`)** 을 반환한다. 이 조합은 **객체 구성**(configuration)이라는 관용구 하나를 위해 존재한다.

```kotlin
val point = Point().apply {
    x = 10          // this.x = 10
    y = 20          // this.y = 20
}                   // apply는 구성된 Point를 돌려줌
// point는 x=10, y=20으로 구성된 Point
```

`apply`가 없다면 다음과 같이 써야 한다.

```kotlin
val point = Point()
point.x = 10
point.y = 20
// point 변수를 세 번 반복
```

`apply`를 쓰면 대상 이름을 반복하지 않고 대상을 `this`로 삼아 프로퍼티를 차례로 설정한 뒤, 그 대상을 그대로 표현식의 값으로 반환한다. 그래서 `val`로 한 번에 받으면서 구성까지 끝낼 수 있다. Java에서 빌더 패턴으로 하던 일을 별도의 빌더 클래스 없이 일반 클래스의 세터만으로 해낼 수 있다.

### 6.2 빌더 없는 빌더

`apply`의 진짜 장점은 대상을 반환한다는 데서 나온다. 반환값이 대상이므로 **표현식으로 바로 넘기거나 이어 붙일 수 있다.**

```kotlin
class HttpRequest {
    var url: String = ""
    var method: String = "GET"
    val headers: MutableMap<String, String> = mutableMapOf()
}

fun send(req: HttpRequest) { /* ... */ }

// 임시 변수 없이 구성 → 즉시 전달
send(HttpRequest().apply {
    url = "https://example.com/api"
    method = "POST"
    headers["Content-Type"] = "application/json"
})
```

`HttpRequest()`를 만들고 `apply` 안에서 구성하면, 구성된 객체가 곧바로 `send`의 인자가 된다. 중간 변수가 하나도 없다. 이 관용구는 특히 **가변 컬렉션이나 빌더 객체에 초기 내용을 채울 때** 자주 쓰인다.

```kotlin
val list = mutableListOf<Int>().apply {
    add(1)
    add(2)
    addAll(listOf(3, 4))
}   // 채워진 리스트를 돌려받음
```

> [!warning] 흔한 오해
> `apply`가 람다의 결과를 반환한다고 착각하면 큰 버그가 생긴다. `apply` 블록의 마지막 표현식이 무엇이든 반환값은 **항상 대상**이다.
> ```kotlin
> val n = StringBuilder().apply {
>     append("hi")
>     length              // 마지막 표현식 = 2, 하지만 무시됨
> }
> // n의 타입은 Int가 아니라 StringBuilder! (apply는 수신자를 돌려줌)
> ```
> `length`(=2)를 값으로 받고 싶었다면 `run`을 썼어야 한다. `apply`는 수신자를 반환하고 `run`은 결과를 반환한다는 이 대칭이 두 함수의 유일한 차이이다.

### 6.3 apply와 val: 불변 참조와 가변 객체 구성

`apply`는 [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 다룬 `val`과 함께 자주 쓰인다. `val`은 재대입만 막을 뿐 참조하는 객체는 가변일 수 있는데, `apply`는 이 성질을 잘 활용한다.

```kotlin
val cache = HashMap<String, Int>().apply {
    put("a", 1)
    put("b", 2)
}
// cache는 val (재대입 불가) 이지만, apply로 초기 내용을 채웠고
// 이후에도 cache.put(...)으로 내용은 계속 바꿀 수 있다 (M3: val ≠ immutable)
```

`val cache`는 참조만 고정할 뿐, 그 `HashMap`은 가변이다. `apply`를 쓰면 이 가변 객체를 *선언하는 시점에 한 번에* 구성할 수 있다. 이 조합은 코틀린에서 "선언과 초기 구성을 붙여 쓰는" 흔한 스타일의 기본 형태이다.

### 6.4 apply와 자바 빌더 비교

`apply`가 무엇을 대체하는지는 자바 코드와 나란히 놓으면 분명해진다. 자바에서 "객체를 만들면서 여러 세터를 호출하고 그 객체를 넘기려면" 빌더 클래스를 따로 만들거나, 임시 변수를 두고 세터를 반복해서 호출해야 했다.

```java
// Java — 임시 변수 + 반복되는 참조
Rectangle r = new Rectangle();
r.setWidth(3.0);
r.setHeight(4.0);
r.setColor("red");
draw(r);
```

```kotlin
// Kotlin — apply로 변수 없이 구성 후 전달
draw(Rectangle().apply {
    width = 3.0        // 참조 반복 없음, this 생략
    height = 4.0
    color = "red"
})
```

자바 코드는 `r`을 네 번 적는다. 코틀린에서는 `apply`가 `this`를 암시적 수신자로 정하므로 대상 이름을 한 번도 적지 않아도 되고, 반환값이 대상이므로 곧바로 `draw(...)`에 넘길 수 있다. 자바에서 이렇게 간결하게 쓰려면 대상 클래스에 수십 줄짜리 빌더 보일러플레이트를 만들어야 한다.

반면 코틀린에서는 *어떤* 클래스에든 `apply`를 붙일 수 있다. `apply`가 특정 타입에 묶인 메서드가 아니라 `<T> T.apply`라는 범용 확장 함수이기 때문이다. "빌더 없는 빌더"의 진짜 의미가 이것이다. 클래스마다 빌더를 만드는 대신, 언어가 모든 타입에 하나의 구성 관용구를 추가 비용 없이 제공한다.

## 7. also: 부수 효과를 실행하고 원본을 그대로 넘긴다

### 7.1 계약: `it`으로 받아 수신자를 반환한다

`also`의 시그니처는 `T.also(block: (T) -> Unit): T`이다. 대상을 **`it`으로**(인자로) 받고, 블록 결과는 버린 채 **대상 자신(`T`)** 을 반환한다. 수신자를 반환한다는 점은 `apply`와 같지만, 대상을 `this`가 아니라 `it`으로 받는다. 이 작은 차이 때문에 `also`는 **부수 효과와 관찰**을 위한 도구가 된다.

```kotlin
val numbers = mutableListOf(1, 2, 3)
    .also { println("초기: $it") }      // it = 리스트, 관찰만
    .also { it.add(4) }                 // 부수효과, 원본을 이어 흘림
// numbers = [1, 2, 3, 4], 로그도 출력됨
```

`also`는 값의 흐름을 끊지 않고, 그 흐름과 별개로 로깅이나 검증, 디버깅 출력, 부가 등록 같은 작업을 하고 싶을 때 쓴다. 함수형 파이프라인의 `peek`에 해당하며, 개념적으로는 [[39 - 컬렉션 연산과 함수형 파이프라인]]과 통한다. 대상을 그대로 반환하므로 체인 중간에 자연스럽게 끼워 넣을 수 있다.

### 7.2 apply와 also: 실전에서 this와 it 중 무엇을 고를까

`apply`와 `also`는 둘 다 수신자를 반환하므로 서로 바꿔 써도 될 것처럼 보인다. 둘의 차이는 대상을 부르는 방식(`this`와 `it`)이고, 이 차이가 실전에서는 중요하다.

```kotlin
class User {
    var name: String = ""
    var age: Int = 0
}

// apply: 대상의 멤버를 이름 없이 설정 (구성)
val u1 = User().apply {
    name = "Alice"     // this.name
    age = 30
}

// also: 대상을 it으로 받아 다른 함수에 넘기거나 관찰 (부수효과)
val u2 = User().apply { name = "Bob" }.also { user ->
    registerUser(user)          // 대상을 인자로 넘김 — it이 자연스러움
    println("등록: ${user.name}")
}
```

판단 기준은 다음과 같다.

- 대상의 **멤버를 설정하거나 호출**하는 것이 주목적이면 `apply`를 쓴다. `this`로 멤버를 직접 다룰 수 있다.
- 대상을 **다른 함수의 인자로 넘기거나** `it.name`처럼 명시적으로 참조하는 것이 주목적이면 `also`를 쓴다. 대상을 `it`이라는 이름으로 받는다.

특히 2.2절에서 본 **가려짐 문제**를 피하려면 `also`가 더 안전하다. `also`의 `it`은 암시적 수신자를 새로 쌓지 않으므로 바깥 스코프의 이름과 충돌하지 않는다.

```kotlin
class Service {
    var timeout = 100
    fun setup() {
        Config().also {
            it.timeout = 5      // 명확히 Config의 timeout (모호함 없음)
        }
        // this@Service 없이도 timeout은 여전히 Service의 것으로만 해소
    }
}
```

`also` 안에서 `it.timeout`은 분명히 `Config`의 프로퍼티이고, 그냥 `timeout`이라고 쓰면 여전히 `Service.timeout`이다. `apply`였다면 `timeout`이 `Config`의 프로퍼티로 해석되어 바깥 이름이 가려졌을 것이다. 그래서 이름 충돌이 걱정되는 초기화에는 방어적으로 `also { it. }`을 쓰는 편이 안전하다.

### 7.3 also로 검증과 확인 끼워 넣기

`also`의 또 다른 관용구는 값을 만들면서 그 값에 대한 검증이나 확인을 함께 실행하는 것이다.

```kotlin
fun parsePositive(s: String): Int =
    s.toInt()
        .also { require(it > 0) { "양수여야 함: $it" } }   // 검증, 통과 시 원본 흘림
// 검증에 실패하면 require가 예외를 던지고, 통과하면 파싱값을 그대로 반환
```

`also`는 값을 변형하지 않고(변형은 `let`이 맡는다) 부가 작업만 하므로, 반환 타입이 원본과 같다는 것이 보장된다. 이렇게 타입을 바꾸지 않는다는 성질은 파이프라인을 안전하게 만드는 작은 기반이 된다.

## 8. takeIf / takeUnless: 조건을 값의 흐름에 끼워 넣기

### 8.1 계약: 조건이 맞으면 값을, 아니면 null을 반환한다

다섯 스코프 함수와 함께 자주 쓰이는 함수로 `takeIf`/`takeUnless`가 있다. 시그니처는 다음과 같다.

```kotlin
public inline fun <T> T.takeIf(predicate: (T) -> Boolean): T?
public inline fun <T> T.takeUnless(predicate: (T) -> Boolean): T?
```

`takeIf`는 술어(predicate)가 **참이면 값 자신(`T`)을, 거짓이면 `null`** 을 반환한다. `takeUnless`는 그 반대이다. 핵심은 반환 타입이 `T?`(널 가능)라는 점이다. 조건을 통과하지 못하면 널 흐름으로 넘어간다. 이것은 컬렉션의 `filter`를 값 하나에 적용한 것과 같다. 즉 "이 값이 조건에 맞으면 통과시키고, 아니면 걸러 낸다".

```kotlin
val even: Int? = 7.takeIf { it % 2 == 0 }      // 7은 짝수 아님 → null
val positive: Int? = 5.takeIf { it > 0 }       // 5 > 0 → 5
val nonBlank: String? = "".takeUnless { it.isBlank() }  // 빈 문자열 → null
```

### 8.2 `?:`, `?.let`과 함께 쓰기

`takeIf`의 진가는 `T?`를 반환한다는 데서 나온다. 그래서 엘비스 연산자 `?:`나 `?.let`으로 곧바로 이어 쓸 수 있다.

```kotlin
// "조건 맞으면 그 값, 아니면 기본값"
fun clampScore(raw: Int): Int =
    raw.takeIf { it in 0..100 } ?: 0    // 범위 밖이면 0

// "조건 맞을 때만 후속 처리"
fun processFile(path: String) {
    path.takeIf { it.endsWith(".txt") }
        ?.let { readText(it) }           // .txt일 때만 읽음
        ?.let { println(it.length) }
}
```

`takeIf`가 조건을 `null` 여부로 바꿔 주면, 그다음은 `?.`와 `?:` 같은 널 처리 도구가 이어받는다. 이렇게 **조건 → 널 → 널 처리** 순서로 흐름을 잇는 것이 코틀린다운 관용구이다. `if`로 쓰면 중첩이 생기지만, `takeIf` 체인은 평평하게 이어진다.

```kotlin
// takeIf 없이 if로:
fun clampScore2(raw: Int): Int =
    if (raw in 0..100) raw else 0        // 이 경우엔 if도 충분히 명료

// takeIf가 이기는 경우: 대상이 긴 표현식이라 이름을 두 번 쓰기 싫을 때
fun normalize(input: String): String =
    input.trim().lowercase()
        .takeIf { it.isNotEmpty() } ?: "default"
    // trim().lowercase() 결과를 변수 없이 조건 검사 + 기본값
```

판단 기준은 다음과 같다. 대상이 **조건에서 다시 쓰기 번거로운 긴 표현식**이면 `takeIf`가 낫고, 짧은 변수 하나라면 그냥 `if`가 더 읽기 쉽다.

> [!caution] 성능 주의
> `takeIf`/`takeUnless`도 `inline`이므로 술어 람다를 할당하지 않는다. 다만 반환 타입이 `T?`이므로, 원시 타입 대상(`Int` 등)에 쓰면 널을 표현하기 위해 **박싱**이 일어날 수 있다([[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]). `7.takeIf { ... }`의 결과인 `Int?`는 JVM 백엔드에서 대개 `Integer`로 박싱된다. 수치 연산이 극도로 많은 루프에서는 이 점을 의식해야 하지만, 일반 코드에서는 무시해도 좋은 수준이다.

## 9. 내부 동작: inline, contracts, 비지역 반환

지금까지는 다섯 함수가 "무엇을 하는가"를 살펴보았다. 이제 스코프 함수가 "어떻게 비용 없이 안전하게 동작하는가"를 살펴본다. 답은 세 가지 언어 기능의 조합이다. **inline**은 할당을 없애고, **contracts**는 흐름 분석이 블록 안까지 이어지게 하며, **비지역 반환**은 제어 흐름을 결정한다.

### 9.1 모두 inline이므로 할당이 없다

다섯 함수와 `takeIf`/`takeUnless`는 모두 `public inline fun`이다(15장 인라인 함수와 reified). 스코프 함수를 "부담 없이 어디서나 쓸 수 있는" 첫 번째 이유가 이것이다. `x.let { ... }`를 컴파일하면 `let`의 본문과 넘긴 람다의 본문이 모두 호출 지점에 그대로 펼쳐진다. 따라서 다음 두 코드의 컴파일 결과는 사실상 같다.

```kotlin
// 우리가 쓴 것
val len = name?.let { it.trim().length } ?: 0

// 인라인 후 개념적으로 (람다 객체 할당 없음)
val len = if (name != null) name.trim().length else 0
```

`Function1` 구현 객체도, 캡처 래퍼도 만들어지지 않는다. 스코프 함수가 `inline`이 아니었다면 `list.forEach { it.let { ... } }` 같은 흔한 코드가 원소마다 람다 객체를 할당해 파이프라인이 무거워졌을 것이다. inline이 그 비용을 0으로 만든다. 다만 스코프 함수의 람다가 *또 다른* 비인라인 람다를 캡처하거나, 스코프 함수를 함수 참조로 넘기면 인라인되지 않을 수 있다. 그 경계는 15장에서 자세히 다룬다.

### 9.2 contracts: 블록 안의 val이 "정확히 한 번" 초기화된다는 것을 아는 이유

스코프 함수는 얇은 라이브러리 함수인데도 컴파일러의 흐름 분석이 블록 안까지 *이어진다*. 그 이유는 **계약**(contract)이다. 표준 라이브러리의 스코프 함수 구현은 대략 다음과 같다.

```kotlin
// kotlin-stdlib의 실제 구현 (개념)
public inline fun <T, R> T.let(block: (T) -> R): R {
    contract { callsInPlace(block, InvocationKind.EXACTLY_ONCE) }
    return block(this)
}

public inline fun <T> T.apply(block: T.() -> Unit): T {
    contract { callsInPlace(block, InvocationKind.EXACTLY_ONCE) }
    block()
    return this
}
```

`callsInPlace(block, EXACTLY_ONCE)`는 컴파일러에게 "이 블록은 이 함수가 반환되기 전에 정확히 한 번 호출된다"고 약속한다. 이 계약 덕분에 **초기화 분석**이 블록 경계를 넘어 이어진다.

```kotlin
val greeting: String
run {
    greeting = "hello"       // 계약이 EXACTLY_ONCE라 → 컴파일러: "정확히 한 번 대입됨"
}
println(greeting)            // OK — val이 확실히 초기화됐음을 안다
```

계약이 없다면 컴파일러는 `run`의 블록이 실제로 실행되는지 알 수 없다. 그러면 `greeting`이 초기화되지 않았을 가능성을 이유로 `println(greeting)`을 거부했을 것이다. `callsInPlace`가 이 불확실성을 없앤다. 같은 원리로 **스마트 캐스트**도 블록 안까지 이어진다.

```kotlin
fun describe(x: Any) {
    val label = when (x) {
        is String -> x.let { "문자열 길이 ${it.length}" }   // it: String (스마트캐스트)
        else -> "기타"
    }
    println(label)
}
```

> [!note] 명세 기준
> `kotlin.contracts`는 코틀린 1.3부터 있던 기능이지만, 사용자 코드에서 `contract { }`를 선언하려면 여전히 `@OptIn(ExperimentalContracts::class)`가 필요하다. 2.x 기준으로 표준 라이브러리의 계약은 안정적으로 *소비*할 수 있지만, 계약을 *선언*하는 API는 아직 실험적이다.
>
> 따라서 `let`/`run`을 쓸 때 초기화 분석과 스마트 캐스트가 블록 안까지 이어지는 이점은 안정적으로 누릴 수 있고, 계약을 직접 *작성*할 때만 opt-in이 필요하다. 계약과 애노테이션 전반은 [[44 - 애노테이션과 리플렉션]]에서 더 다룬다.

### 9.3 비지역 반환: apply 안의 return은 무엇을 종료하는가

스코프 함수가 `inline`이어서 생기는 세 번째 결과가 **비지역 반환**(non-local return)이다. 인라인 람다 안의 `return`은 람다가 아니라 그 람다를 *감싸는 함수*를 종료한다(15장 인라인 함수와 reified, 14장 클로저와 캡처).

```kotlin
fun findFirstEven(nums: List<Int>): Int? {
    nums.forEach { n ->
        n.takeIf { it % 2 == 0 }?.let {
            return it            // findFirstEven을 종료! (takeIf/let/forEach 모두 inline)
        }
    }
    return null
}

findFirstEven(listOf(1, 3, 4, 5))   // => 4
```

`return it`은 `let`이나 `forEach`를 벗어나는 것이 아니라 바깥 함수 `findFirstEven` 전체를 종료한다. 세 함수(`forEach`, `takeIf`, `let`)가 모두 인라인이기 때문에 가능한 일이다. `let`이 인라인이 아니었다면 이 `return`은 컴파일 에러가 되거나, `return@let`으로만 쓸 수 있었을 것이다.

이 성질은 강력하지만 함정이 되기도 한다. `apply` 블록 안에 무심코 쓴 `return`이 예상과 달리 바깥 함수를 종료할 수 있다.

```kotlin
fun build(flag: Boolean): Config {
    return Config().apply {
        timeout = 10
        if (flag) return@apply      // apply 블록만 벗어남 (라벨 명시)
        // if (flag) return         // ← 이렇게 쓰면 build 전체가 종료 (Config 반환 안 됨!)
        retries = 3
    }
}
```

블록만 벗어나려면 **라벨 반환** `return@apply`(14장 클로저와 캡처)를 명시해야 한다. 그냥 `return`이라고 쓰면 바깥 함수가 종료된다. 스코프 함수를 남용할 때 사고가 나는 대표적인 지점이 이 구분이다(10절).

### 9.4 컴파일 결과를 직접 확인하는 방법

스코프 함수가 정말 할당을 하지 않는지 의심스럽다면(외부 라이브러리를 그대로 믿지 않는 태도), 15장에서 안내한 방식으로 확인할 수 있다. JVM 백엔드에서 `.kt` 파일을 컴파일한 뒤 IntelliJ IDEA의 *Tools → Kotlin → Show Kotlin Bytecode → Decompile*로 역컴파일하면, `x.let { ... }`가 람다 객체 생성 없이 인라인된 것을 직접 볼 수 있다.

"라이브러리가 그렇다고 하더라"에 기대지 않고 바이트코드로 검증하는 것이 이 시리즈의 태도이다. Native/JS 백엔드에서는 표현이 다르지만 인라인과 계약의 *의미*는 같다. 여기서 설명한 할당 제거와 비지역 반환은 언어 수준에서 보장된다.

## 10. 선택 규칙과 안티패턴: 남용 사례 분석

### 10.1 결정 트리

두 축(수신자 참조, 반환값)을 질문으로 바꾸면 어떤 함수를 쓸지 기계적으로 정할 수 있다.

```text
목적이 무엇인가?
│
├─ 대상을 다른 타입으로 "변환"한다 (결과가 필요)
│   ├─ 대상을 it/이름으로 받고 싶다 ............ let
│   └─ 대상의 멤버를 this로 여럿 부른다 ........ run  (널 가능? → ?.run)
│                                              (대상이 인자로 넘겨짐 · 널 아님) → with
│
├─ 대상을 "구성"하고 그 대상을 돌려받는다
│   ├─ 멤버를 this로 직접 설정한다 ............. apply
│   └─ 대상을 it으로 넘기거나 관찰만 한다 ...... also
│
└─ 대상을 "조건"으로 거른다 (맞으면 값, 아니면 null)
    ├─ 조건 참일 때 통과 ....................... takeIf
    └─ 조건 거짓일 때 통과 ..................... takeUnless
```

먼저 변환, 구성, 조건 세 갈래 중 하나를 정하고, 그 안에서 `this`와 `it` 중 하나를 고르면 함수가 하나로 좁혀진다. 이 트리를 알고 있으면 다섯 함수를 따로 외울 필요가 없다.

### 10.2 안티패턴 1: 아무 역할도 하지 않는 스코프 함수

가장 흔한 남용은 스코프 함수가 아무 역할도 하지 않는데 습관적으로 쓰는 것이다.

```kotlin
// 나쁨: let이 하는 일이 없다
val len = name.let { it.length }        // == name.length
val x = value.also { }                  // == value (빈 블록)
val y = obj.run { toString() }          // == obj.toString()

// 좋음: 직접 쓴다
val len = name.length
```

`let`은 널 처리나 이름 붙이기 같은 *이유*가 있을 때만 쓸모가 있다. 멤버 하나에 접근하는 코드를 `let`으로 감싸면 코드만 복잡해진다. "이 스코프 함수를 지우면 코드가 더 짧고 명료해지는가?"를 스스로 물어보고, 그렇다면 지우는 것이 좋다.

### 10.3 안티패턴 2: this와 it의 혼동과 가려짐

`apply`/`run`(this)과 `let`/`also`(it)를 섞어서 중첩하면 어느 대상을 가리키는지 금방 흐려진다.

```kotlin
// 나쁨: this와 it이 뒤섞여 대상이 헷갈린다
user.apply {
    name = "A"
    address.let {
        it.city = "Seoul"
        street = "..."          // ⚠️ this.street? 어느 객체의 street인가? (user? address?)
    }
}
```

`street`가 `user`의 프로퍼티인지 `address`의 프로퍼티인지 바로 보이지 않는다(2.2절의 가려짐). 중첩해야 한다면 안쪽에서 `it`을 명시적으로 쓰거나, 아예 스코프 함수를 풀고 임시 변수로 나누는 편이 낫다.

```kotlin
// 좋음: 명시적 it 또는 평범한 변수
val addr = user.address
addr.city = "Seoul"
addr.street = "..."
user.name = "A"
```

### 10.4 안티패턴 3: 숨은 비지역 반환

9.3절에서 보았듯이 스코프 함수 블록 안의 `return`은 바깥 함수를 종료한다. 긴 `apply`/`run` 블록 중간에 `return`이 숨어 있으면, 읽는 사람은 그 함수가 어디서 끝나는지 놓치기 쉽다.

```kotlin
// 나쁨: apply 안의 return이 build를 조용히 끝낸다
fun build(): Result = Result().apply {
    step1()
    if (invalid) return       // build 전체를 종료 — Result가 반환 안 됨!
    step2()
}
```

이런 조기 반환은 스코프 함수 밖으로 꺼내 흐름이 명시적으로 드러나게 두는 편이 안전하다. 스코프 함수는 "값을 다듬는 짧은 블록"에 어울리며, 복잡한 제어 흐름을 담는 용도로는 적합하지 않다.

### 10.5 안티패턴 4: 세 겹 이상의 중첩

스코프 함수를 세 겹 넘게 중첩하면 암시적 수신자와 `it`, 반환값이 얽혀서 거의 항상 가독성이 크게 떨어진다.

```kotlin
// 나쁨: 무엇이 무엇인지 추적 불가
data.let { d ->
    d.items.also { items ->
        items.forEach { item ->
            item.tags.apply { /* this? it? d? */ }
        }
    }
}
```

이 정도가 되면 스코프 함수로 얻는 간결함보다 코드가 불명확해지는 손실이 훨씬 크다. 이럴 때는 이름 있는 지역 변수와 평범한 `for` 문으로 풀어 써야 한다. 스코프 함수는 조미료와 같아서, 조금 넣으면 요리를 살리지만 통째로 부으면 먹을 수 없게 된다.

### 10.6 요약 표

| 함수 | 수신자 참조 | 반환값 | 확장? | 주 관용구 | 대표 조합 |
|------|-----------|--------|-------|----------|----------|
| `let` | `it` | 람다 결과 | ✓ | 변환 · 널 처리 | `?.let`, `?.let{}?:` |
| `run` | `this` | 람다 결과 | ✓ | 여러 호출 묶기 → 결과 | `?.run`, 수신자 없는 `run{}` |
| `with` | `this` | 람다 결과 | ✗ | 널이 아닌 대상의 여러 호출 묶기 | `with(x){}` |
| `apply` | `this` | 수신 객체 | ✓ | 객체 구성 | `X().apply{}` |
| `also` | `it` | 수신 객체 | ✓ | 부수 효과 · 관찰 | `.also{ log(it) }` |
| `takeIf` | `it` | `T?` | ✓ | 조건 필터 | `.takeIf{}?:` |
| `takeUnless` | `it` | `T?` | ✓ | 역조건 필터 | `.takeUnless{}?:` |

이 표에 이 장의 내용이 담겨 있다. 두 축(참조 방식, 반환값)과 세 관용구(변환, 구성, 조건)만 기억하면, 다섯 함수의 위치를 격자 위에서 정확히 다시 찾을 수 있다.
