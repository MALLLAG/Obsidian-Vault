[[31 - 중첩 클래스와 이너 클래스와 익명 객체]]에서는 한 클래스가 다른 클래스의 *인스턴스*를 품는 여러 방식을 살펴보았다. `inner` 클래스는 바깥 인스턴스 참조를 캡처했고, 익명 객체는 인터페이스를 그 자리에서 구현했다. 이 장치들은 모두 "객체가 다른 객체를 어떻게 참조하고 있는가"를 조금씩 다르게 푼 것이었다.

이 장은 여기서 한 걸음 더 나아간다. 한 객체가 다른 객체를 *품는 데서 그치지 않고, 자신이 약속한 인터페이스의 일을 전부 그 객체에게 넘긴다.* 이것이 클래스 위임(class delegation)이다.

클래스 위임은 "상속보다 컴포지션(composition over inheritance)"이라는 오래된 설계 격언을 코틀린이 *문법 한 줄*로 쉽게 쓸 수 있게 만든 장치다. 다른 언어에서 데코레이터(decorator)를 직접 작성하려면 인터페이스의 모든 메서드마다 `override fun m() = inner.m()` 같은 전달(forwarding) 코드를 반복해서 써야 한다. 코틀린에서는 `by` 키워드 하나만 쓰면 컴파일러가 이 전달 메서드를 모두 대신 생성한다.

그래서 이 장의 절반은 "이 편의 기능이 정확히 무엇을 생성하는가"를 다루고, 나머지 절반은 "이 편의 기능이 상속과 어떻게 다르게 동작해서 함정이 되는가"를 다룬다.

이 장에서 다루는 것은 클래스 헤더의 상위 타입 자리에 쓰는 `: Base by b`, 즉 **인터페이스 위임**이다. 컴파일러가 생성하는 전달 메서드와 필드, 위임 객체가 생성 시점에 한 번만 캡처된다는 성질, `override`로 가로챌 수 있는 범위와 가로챌 수 없는 **self 문제**, 다중 위임과 충돌 해소, 실전 데코레이터와 안티패턴을 차례로 살펴본다.

이름이 비슷한 **위임 프로퍼티**(`val x: Int by lazy { ... }`)는 같은 `by` 키워드를 쓰지만 *전혀 다른 메커니즘*이며 [[23 - 위임 프로퍼티]]에서 설명한다. 두 기능의 차이는 3절과 8절에서 따로 짚는다.

## 1. 상속의 문제: 왜 위임이라는 장치가 필요한가

### 1.1 취약한 기반 클래스 문제

상속은 코드를 재사용하는 가장 오래된 도구지만, 재사용하는 대신 *구현 결합(implementation coupling)* 이라는 비용을 치른다. 하위 클래스는 상위 클래스의 공개 계약뿐 아니라, 상위 클래스가 내부에서 자기 메서드를 어떤 순서로, 어떤 자기 호출(self-call)로 엮는지에도 은연중에 의존하게 된다.

그래서 상위 클래스가 이 내부 구조를 바꾸면, 계약은 그대로인데도 하위 클래스가 조용히 깨진다. 이것이 잘 알려진 **취약한 기반 클래스 문제(fragile base class problem)** 다.

교과서에 자주 나오는 예를 보자. 추가된 원소 개수를 세는 컬렉션을 만들려고 `ArrayList`를 상속했다고 하자.

```kotlin
// 상속으로 "추가된 원소 개수"를 세려는 시도 — 위험하다
class CountingList<E> : ArrayList<E>() {
    var added = 0
        private set

    override fun add(element: E): Boolean {
        added++
        return super.add(element)
    }

    override fun addAll(elements: Collection<E>): Boolean {
        added += elements.size
        return super.addAll(elements)  // 내부에서 add를 부를까? 모른다.
    }
}
```

상위 클래스의 `addAll`이 내부에서 원소마다 `add`를 호출하도록 구현되어 있다면, `added`는 원소 하나당 *두 번* 증가한다(`addAll`에서 한 번, 거기서 호출된 `add`에서 또 한 번). 반대로 `addAll`이 `add`를 호출하지 않고 배열을 직접 복사한다면 개수는 정확하다. 어느 쪽인지는 상위 클래스의 *비공개 구현 세부*에 달려 있고, 라이브러리 버전이 올라가면서 바뀔 수도 있다. 하위 클래스 코드는 한 글자도 건드리지 않았는데 계산이 틀리기 시작하는 것이다.

이 취약성의 근본 원인은 상속이 상위 클래스와 하위 클래스의 자기 호출을 *하나의 `this`로 합친다*는 데 있다. 초기화 순서에서 이렇게 합쳐진 `this`가 함정이 되는 경우는 [[24 - 상속과 오버라이딩과 초기화 순서]]에서 다룬다.

### 1.2 데코레이터를 직접 쓰는 반복 작업

취약성을 피하는 정석은 상속을 쓰지 않고 **컴포지션**을 쓰는 것이다. `ArrayList`를 *상속*하는 대신 *필드로 품고*, 겉으로는 `MutableList` 인터페이스를 구현하되 실제 일은 품은 리스트에게 넘긴다. 이것이 데코레이터 패턴이다.

```kotlin
// 컴포지션 + 수동 전달 — 안전하지만 지루하다
class CountingList<E>(private val inner: MutableList<E>) : MutableList<E> {
    var added = 0
        private set

    override fun add(element: E): Boolean {
        added++
        return inner.add(element)
    }
    override fun addAll(elements: Collection<E>): Boolean {
        added += elements.size
        return inner.addAll(elements)
    }

    // ...그리고 나머지 수십 개를 전부 손으로 전달해야 한다
    override val size: Int get() = inner.size
    override fun get(index: Int): E = inner[index]
    override fun isEmpty(): Boolean = inner.isEmpty()
    override fun contains(element: E): Boolean = inner.contains(element)
    override fun iterator(): MutableIterator<E> = inner.iterator()
    override fun remove(element: E): Boolean = inner.remove(element)
    override fun clear() = inner.clear()
    override fun indexOf(element: E): Int = inner.indexOf(element)
    // ... set, removeAt, listIterator, subList, containsAll, lastIndexOf,
    //     removeAll, retainAll, add(index, element), addAll(index, ...) ...
    // MutableList는 20개가 넘는 멤버를 요구한다.
}
```

이 코드는 취약하지 않다. `inner`의 내부 자기 호출은 `inner` 안에서 끝나므로 `CountingList`의 오버라이드로 이어지지 않기 때문이다(그 이유는 6절에서 형식적으로 설명한다). 하지만 비용은 분명하다. **인터페이스가 요구하는 모든 멤버를 한 줄씩 전달하는 보일러플레이트**가 생긴다.

`MutableList`처럼 큰 인터페이스라면 기계적인 전달 코드가 20~30줄 나오고, 그중 실제로 동작을 바꾸는 것은 두 개(`add`, `addAll`)뿐이다. 나머지는 읽을 때 방해만 되는 코드이고, 인터페이스에 멤버가 하나 추가되면 컴파일 에러가 나서 다시 손을 대야 한다.

### 1.3 "상속보다 컴포지션"을 문법으로 지원하기

여기서 코틀린의 설계 결정이 등장한다. *컴포지션은 안전하지만 손이 많이 간다. 그렇다면 그 작업을 컴파일러에게 맡기자.* 그것이 `by`다.

```kotlin
// 컴파일러가 전달 메서드를 대신 찍어낸다
class CountingList<E>(private val inner: MutableList<E>) : MutableList<E> by inner {
    var added = 0
        private set

    override fun add(element: E): Boolean {
        added++
        return inner.add(element)
    }
    override fun addAll(elements: Collection<E>): Boolean {
        added += elements.size
        return inner.addAll(elements)
    }
    // 나머지 size, get, iterator, remove ... 는 전부 자동 전달. 한 줄도 안 쓴다.
}
```

`: MutableList<E> by inner`는 "이 클래스는 `MutableList`를 구현하는데, *내가 직접 오버라이드하지 않은* 멤버는 모두 `inner`에게 그대로 전달한다"는 뜻이다. `add`와 `addAll`은 직접 오버라이드했으므로 이 클래스의 구현이 쓰이고, 나머지는 컴파일러가 `inner.size`, `inner.get(...)` 같은 전달 메서드를 자동으로 생성한다. 1.2절의 30줄이 1.3절에서는 헤더의 한 부분으로 줄었다.

> [!info] 역사 메모
> "상속보다 컴포지션을 선호하라(favor composition over inheritance)"는 GoF의 『Design Patterns』(1994)와 Joshua Bloch의 『Effective Java』("Item: Favor composition over inheritance", 취약한 기반 클래스를 직접 다룸)를 통해 널리 알려진 격언이다. 코틀린은 이 격언을 *권고*로만 두지 않고 언어 문법(`by` 위임)으로 지원하는, 주류 언어 중에서는 드문 사례다.
>
> 이는 코틀린의 실용주의 철학([[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]])과 이어진다. 클래스가 기본적으로 `final`이어서 상속을 허용하려면 `open`을 명시해야 하는 정책(24장 상속과 오버라이딩)도 같은 철학에서 나왔다. 언어가 상속은 *예외적인 선택*으로, 위임은 *비용이 적은 기본값*으로 권하는 것이다.

정리하면, 위임은 두 가지를 동시에 얻으려고 존재한다. 하나는 **컴포지션의 안전성**(취약한 기반 클래스 회피)이고, 다른 하나는 **상속의 간결함**(멤버를 일일이 전달하지 않아도 됨)이다. 이제 문법과 의미를 정확히 정의해 보자.

## 2. `by`의 문법과 의미

### 2.1 최소 예제로 본 형태

위임은 클래스 헤더의 상위 타입 목록에서 특정 인터페이스 뒤에 `by <표현식>`을 붙여서 쓴다.

```kotlin
interface Printer {
    fun print(msg: String)
    fun printLine(msg: String)
}

class ConsolePrinter : Printer {
    override fun print(msg: String) = kotlin.io.print(msg)
    override fun printLine(msg: String) = println(msg)
}

// ConsolePrinter의 인스턴스에게 Printer의 일을 통째로 위임
class TaggedPrinter(private val delegate: Printer) : Printer by delegate

fun main() {
    val p = TaggedPrinter(ConsolePrinter())
    p.printLine("hello")   // => hello   (delegate.printLine으로 전달됨)
    p.print("world\n")     // => world   (delegate.print으로 전달됨)
}
```

`TaggedPrinter`는 본문이 비어 있지만 `Printer`를 완전히 구현한 정상적인 클래스다. `print`와 `printLine`을 하나도 직접 작성하지 않았는데도, 컴파일러가 `delegate`로 호출을 넘기는 전달 메서드를 만들어 주기 때문이다. 여기서 `by` 뒤의 `delegate`는 *생성자 파라미터*를 참조한다.

`A by b`는 "타입 `A`를 `b`에게 위임한다"고 읽는다. `A`는 반드시 상위 타입 목록에 있는 **인터페이스**여야 하고, `b`는 그 인터페이스 타입(또는 하위 타입)의 인스턴스를 돌려주는 **표현식**이다.

### 2.2 위임 대상은 인터페이스여야 한다

가장 먼저 기억해야 할 제약은 **클래스 위임은 인터페이스에만 쓸 수 있다**는 것이다. 위임하려는 상위 타입이 클래스라면 컴파일되지 않는다.

```kotlin
open class Animal {
    open fun sound(): String = "..."
}

// 컴파일 에러: only interfaces can be delegated to
class Dog(a: Animal) : Animal by a   // ✗  Animal은 클래스다
```

```text
error: only interfaces can be delegated to
    class Dog(a: Animal) : Animal by a
                                  ^
```

이유는 개념적으로 분명하다. 위임은 "인터페이스가 요구하는 멤버를 다른 객체에게 전달"하는 장치다. 그런데 클래스는 인터페이스처럼 순수한 계약이 아니라 상태와 생성자, `final`/`open` 정책을 가진다. 클래스를 위임하려면 그 클래스의 생성자를 호출해 자기 자신의 상위 부분을 초기화해야 하는데, 이는 전달이 아니라 상속이다. 두 메커니즘은 섞일 수 없으므로 코틀린은 이를 아예 금지했다.

클래스를 재사용해야 한다면, 그 클래스가 구현하는 인터페이스를 추출해 그 인터페이스를 위임하거나, 실제로 상속해야 한다.

```kotlin
interface Speaker { fun sound(): String }   // 인터페이스로 계약 추출
open class Animal : Speaker { override fun sound() = "..." }

class Dog(s: Speaker) : Speaker by s          // ✓  이제 가능
```

> [!note] 명세 기준
> 위임은 상위 *인터페이스*마다 따로 지정한다. 클래스 헤더에는 `: SuperClass(...), InterfaceA by a, InterfaceB by b`처럼 실제 상위 클래스 하나와 여러 위임 인터페이스를 함께 쓸 수 있다. 위임 지정은 인터페이스 뒤에서만 유효하고, 상위 클래스 자리에는 `by`를 쓸 수 없다.

### 2.3 위임 표현식은 무엇이든 될 수 있다

`by` 뒤에는 *식별자*만 와야 한다고 오해하기 쉽지만, 실제로는 **인터페이스 타입을 돌려주는 어떤 표현식이든** 올 수 있다. 생성자 파라미터가 가장 흔하지만 그 밖에도 다양한 형태가 가능하다.

```kotlin
interface Base { fun who(): String }
class Impl(val name: String) : Base { override fun who() = name }

// (1) 생성자 파라미터 참조
class D1(b: Base) : Base by b

// (2) 즉석에서 새 객체를 만드는 표현식
class D2 : Base by Impl("inline")

// (3) 익명 객체를 위임
class D3 : Base by object : Base {
    override fun who() = "anonymous"
}

// (4) 함수 호출 결과
fun makeBase(): Base = Impl("factory")
class D4 : Base by makeBase()

// (5) 파라미터를 변형해서 위임
class D5(b: Base) : Base by wrap(b)
fun wrap(b: Base): Base = object : Base { override fun who() = "[" + b.who() + "]" }
```

이 유연함이 4절에서 다룰 함정의 원인이 된다. `by` 뒤의 표현식은 *생성자가 실행될 때 정확히 한 번 평가되고*, 그 결과 참조가 고정된다. 표현식이 파라미터든, 새로 만든 객체든, 함수 호출이든 "한 번 평가한 뒤 고정된다"는 성질은 같다.

스코프 제약도 하나 있다. `by` 표현식은 생성자 파라미터와 바깥 스코프는 참조할 수 있지만, **클래스 본문에 선언한 프로퍼티는 참조할 수 없다.** 본문 프로퍼티는 아직 초기화되기 전이기 때문이다.

```kotlin
class Bad(b: Base) : Base by helper {   // ✗ 'helper'가 스코프에 없음(본문 프로퍼티)
    val helper: Base = b
}
// error: unresolved reference: helper
```

### 2.4 같은 `by`, 다른 관례: 위임 프로퍼티와 구분하기

키워드가 같아서 헷갈리지만, 클래스 위임과 위임 프로퍼티는 서로 다른 메커니즘이다. 표로 정리하면 다음과 같다.

| 축 | 클래스 위임 (이 장) | 위임 프로퍼티 (23장) |
|----|------|--------------------|
| 문법 위치 | 클래스 헤더의 상위 타입 자리 | 프로퍼티 선언 `val/var x ... by ...` |
| 대상 타입 | 인터페이스 인스턴스 | `getValue`/`setValue` 연산자를 가진 객체 |
| 관례 함수 | 없음(직접 전달 메서드 생성) | `getValue`, `setValue`, (선택) `provideDelegate` |
| 컴파일 결과 | 인터페이스 멤버별 전달 메서드 + 합성 필드 | 프로퍼티 접근자가 `delegate.getValue(...)` 호출 + `KProperty` 메타데이터 |
| 예 | `class C(b: List<Int>) : List<Int> by b` | `val x by lazy { 42 }` |

```kotlin
// 클래스 위임: 인터페이스의 일을 통째로 넘김
class Wrapper(b: Runnable) : Runnable by b

// 위임 프로퍼티: 프로퍼티 하나의 get/set을 넘김. getValue 관례 필요.
class Config {
    val cached: String by lazy { expensiveCompute() }   // lazy는 getValue를 가진 객체
}
fun expensiveCompute(): String = "..."
```

핵심 차이는 클래스 위임이 어떤 *관례 함수*도 요구하지 않는다는 점이다. `Printer by delegate`가 성립하는 조건은 `delegate`가 `Printer`라는 것 하나뿐이다. 반면 위임 프로퍼티는 `delegate`가 `getValue(thisRef, property)` 시그니처의 `operator` 함수를 가지고 있어야 성립한다([[19 - 연산자 오버로딩과 관례]]). 이 장에서 앞으로 말하는 "위임"은 언제나 *클래스(인터페이스) 위임*을 뜻한다.

## 3. 컴파일: 전달 메서드가 생성되는 방식

### 3.1 합성 필드 `$$delegate_0`

위임이 실제로 어떻게 동작하는지는 컴파일러가 생성하는 코드를 보면 알 수 있다. `by` 표현식의 값은 생성자에서 평가되어 **합성 필드**에 저장되고, 인터페이스의 각 멤버는 그 필드로 호출을 넘기는 전달 메서드가 된다. JVM 백엔드에서 이 합성 필드의 이름은 관례적으로 `$$delegate_0`(두 번째 위임이면 `$$delegate_1`, ...)이다.

```kotlin
interface Base {
    val message: String
    fun printMessage()
    fun printMessageLine()
}

class BaseImpl(val x: Int) : Base {
    override val message = "BaseImpl: x = $x"
    override fun printMessage() { print(message) }
    override fun printMessageLine() { println(message) }
}

class Derived(b: Base) : Base by b
```

`Derived`를 JVM 바이트코드로 컴파일한 뒤 Java로 역컴파일하면 개념적으로 다음과 같은 형태가 나온다.

```java
// Derived를 디컴파일한 개념적 형태 (JVM 백엔드)
public final class Derived implements Base {
   private final Base $$delegate_0;      // by 표현식이 저장되는 합성 필드

   public Derived(Base b) {
      this.$$delegate_0 = b;             // 생성자에서 한 번 캡처
   }

   // 인터페이스의 각 멤버가 전달 메서드로 생성됨
   public String getMessage() {
      return this.$$delegate_0.getMessage();
   }
   public void printMessage() {
      this.$$delegate_0.printMessage();
   }
   public void printMessageLine() {
      this.$$delegate_0.printMessageLine();
   }
}
```

여기서 눈여겨볼 점은 세 가지다.

1. `Derived`는 `Base`를 **직접 구현(`implements Base`)** 한다. 위임했다고 해서 인터페이스 구현이 면제되는 것이 아니라, 인터페이스를 구현하되 메서드 본문을 컴파일러가 채워 넣은 것이다.
2. `by` 값은 `$$delegate_0`라는 **비공개 합성 필드**에 한 번 저장된다.
3. 각 전달 메서드는 `$$delegate_0.멤버(...)`를 그대로 호출한다. 이것이 나중에 self 문제의 원인이 된다(6절).

> [!caution] 성능 주의
> 전달에도 비용이 있다. `derived.printMessage()`는 전달 메서드 → 필드 로드 → 대상 메서드라는 한 단계의 간접 호출(indirection)을 거친다. 대부분은 JIT가 이 얇은 전달 메서드를 인라이닝해 비용이 사라지지만, 위임을 여러 겹 중첩하면(데코레이터 위에 데코레이터) 이론상 호출 체인이 길어진다. 실제로 걱정할 수준은 아니지만, "위임은 필드 하나와 전달 메서드들"이라는 메모리·호출 비용은 알아 두는 편이 좋다.

### 3.2 생성되는 전달 메서드의 정확한 범위

컴파일러가 전달 메서드를 만드는 대상은 **위임된 인터페이스가 선언한 멤버 중에서 파생 클래스가 직접 오버라이드하지 않은 멤버 전부**다. 이 범위를 정확히 알아야 함정을 피할 수 있다.

- 위임 인터페이스가 선언한 **추상 멤버**: 전달 메서드를 생성한다.
- 위임 인터페이스가 선언한 **기본 구현이 있는 멤버**: 이 경우에도 전달 메서드를 생성한다(3.3절에서 자세히 설명).
- 파생 클래스가 **`override`한 멤버** : 전달 메서드를 생성하지 않는다(5절). 파생 클래스의 오버라이드가 쓰인다.
- **`Any`의 멤버(`equals`, `hashCode`, `toString`)** : 전달 메서드를 생성하지 **않는다**. 인터페이스가 아니라 `Any`에서 온 멤버이기 때문이다. 이 점이 8.1절의 컬렉션 래핑 함정을 만든다.

마지막 항목이 특히 중요하다. `equals`/`hashCode`/`toString`은 어떤 인터페이스의 멤버가 아니라 모든 클래스의 조상인 `Any`([[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]])에서 상속된다. 위임은 *인터페이스* 멤버만 전달하므로, 이 세 멤버는 절대 위임 대상으로 넘어가지 않는다. 위임 래퍼는 `Any`의 기본 구현(참조 동일성 기반 `equals`, 아이덴티티 `hashCode`)을 그대로 쓴다.

```kotlin
interface Named { val name: String }
class Person(override val name: String) : Named

class Badge(p: Named) : Named by p

fun main() {
    val a = Badge(Person("Ada"))
    val b = Badge(Person("Ada"))
    println(a.name == b.name)   // => true   (name은 위임되어 둘 다 "Ada")
    println(a == b)             // => false  (equals는 위임 안 됨 → Any의 참조 비교)
    println(a == Person("Ada")) // => false  (역시 위임 안 됨)
}
```

`name`은 `Named` 인터페이스의 멤버이므로 전달되지만, `==`(즉 `equals`, [[10 - 불리언과 동등성과 동일성]])는 위임되지 않아 참조 비교가 된다. 구조적 동등성이 필요하다면 파생 클래스에서 `equals`/`hashCode`를 직접 오버라이드해야 한다.

### 3.3 기본 구현이 있는 멤버도 전달된다

미묘한 부분이 하나 있다. 위임 인터페이스가 어떤 멤버에 **기본 구현**을 제공하면([[25 - 인터페이스]]) 파생 클래스가 그 기본 구현을 그대로 쓸 것 같지만, 컴파일러는 이 멤버에 대해서도 *위임 대상으로 넘기는 전달 메서드*를 만든다.

```kotlin
interface Greeter {
    fun name(): String
    fun greet(): String = "Hello, ${name()}!"   // 기본 구현
}

class RealGreeter(private val who: String) : Greeter {
    override fun name() = who
}

class Proxy(g: Greeter) : Greeter by g

fun main() {
    val p = Proxy(RealGreeter("Kotlin"))
    println(p.greet())   // => Hello, Kotlin!
}
```

`greet()`는 기본 구현이 있으므로 `RealGreeter`가 오버라이드하지 않았다. `Proxy`에서 `greet()`를 호출하면 컴파일러가 만든 전달 메서드가 `$$delegate_0.greet()`를 호출하고, 그러면 위임 대상(`RealGreeter` 인스턴스)에서 기본 구현이 실행된다.

이 기본 구현 안의 `name()` 호출은 `Proxy`가 아니라 위임 대상 자신의 `name()`을 호출한다. "기본 구현 안의 self 호출이 위임 대상에 묶인다"는 이 성질은 6절에서 다룰 self 문제를 미리 보여 준다.

역컴파일하면 `Proxy`에 `greet()` 전달 메서드가 실제로 있음을 확인할 수 있다.

```java
// Proxy 디컴파일 (개념)
public final class Proxy implements Greeter {
   private final Greeter $$delegate_0;
   public Proxy(Greeter g) { this.$$delegate_0 = g; }
   public String name()  { return this.$$delegate_0.name(); }
   public String greet() { return this.$$delegate_0.greet(); }  // 기본 구현도 전달
}
```

> [!note] 명세 기준
> "기본 구현 멤버도 전달 메서드로 생성된다"는 규칙은 코틀린이 인터페이스 위임을 *완전한 데코레이터*로 만들기 위해 내린 결정이다. 만약 기본 구현 멤버를 전달하지 않고 파생 클래스가 인터페이스의 기본 구현을 직접 상속한다면, 그 기본 구현은 위임 대상의 상태가 아니라 파생 클래스의 (존재하지 않는) 상태에 접근하려다 어긋날 것이다. 모든 멤버를 위임 대상으로 넘기기 때문에 "위임 대상이 곧 구현체"라는 일관성이 유지된다.

### 3.4 직접 확인하는 방법

이 장의 주장은 모두 직접 검증할 수 있다. 코틀린 코드를 바이트코드나 역컴파일 결과로 확인하는 방법은 두 가지다.

- **IntelliJ IDEA**: `Tools → Kotlin → Show Kotlin Bytecode`를 열면 바이트코드가 나타나고, 그 창의 `Decompile` 버튼을 누르면 Java에 가까운 코드를 얻을 수 있다. `$$delegate_0` 필드와 전달 메서드가 그대로 보인다.
- **명령줄**: `kotlinc Derived.kt -d out.jar`로 컴파일한 뒤 `javap -p -c -cp out.jar Derived`로 필드와 메서드 시그니처를 확인한다. 더 읽기 쉬운 결과가 필요하면 CFR/Fernflower 같은 역컴파일러로 Java 코드를 복원한다.

디컴파일은 이 장뿐 아니라 위임 프로퍼티(23장), 인라인 함수([[15 - 인라인 함수와 reified]]), 데이터 클래스([[27 - 데이터 클래스]])의 생성 코드를 확인할 때도 두루 쓰이는 도구다. "컴파일러가 무엇을 생성하는지 모르겠으면 디컴파일하라"는 [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]의 습관을 여기서도 적용한다.

## 4. 위임 대상 저장의 함정: 스냅샷 시맨틱

### 4.1 생성 시점에 딱 한 번 캡처된다

3절에서 보았듯이 `by` 표현식의 값은 생성자에서 `$$delegate_0`에 저장된다. 이 문장이 무엇을 뜻하는지 정확히 짚어야 한다. **위임 대상은 객체가 만들어지는 순간의 참조로 고정된다.** 전달 메서드를 호출할 때마다 `by` 표현식을 다시 평가하지 않고, 생성 시점의 스냅샷만 사용한다.

```kotlin
interface Clock { fun now(): Long }

var globalClock: Clock = object : Clock { override fun now() = 100L }

class Watch : Clock by globalClock   // 생성 시점의 globalClock을 캡처

fun main() {
    val w = Watch()
    println(w.now())     // => 100

    // 전역 시계를 통째로 갈아치운다
    globalClock = object : Clock { override fun now() = 999L }

    println(w.now())     // => 100  (여전히 옛 시계! Watch는 생성 시 캡처했다)
    println(globalClock.now())  // => 999
}
```

`Watch`가 캡처한 것은 `globalClock`이라는 *변수*가 아니라, 생성될 때 그 변수가 가리키던 *객체*다. 나중에 `globalClock`이 다른 객체를 가리켜도 `Watch`의 위임 대상은 바뀌지 않는다. 흔히 "**위임 대상 저장 여부의 함정: 생성자 프로퍼티가 아니면 재계산되지 않는다**"라고 요약하는 문제가 바로 이것이다. 사실 생성자 프로퍼티든 아니든 다시 계산하는 일은 없다. `by` 뒤가 함수 호출이어도 한 번만 호출된다.

```kotlin
var callCount = 0
fun freshBase(): Base {
    callCount++
    return object : Base { override val message = "call #$callCount"
        override fun printMessage() {}; override fun printMessageLine() {} }
}

class Once : Base by freshBase()

fun main() {
    val o = Once()
    println(o.message)   // => call #1
    println(o.message)   // => call #1  (freshBase()는 다시 호출되지 않는다)
    println(callCount)   // => 1
}
```

### 4.2 `val`/`var` 프로퍼티와 위임 필드는 별개다

가장 널리 퍼진 오해는 이것이다. "`class D(val b: Base) : Base by b`라고 쓰면 프로퍼티 `b`와 위임이 같은 것을 가리키므로, `b`를 바꾸면 위임도 따라 바뀐다." 이는 틀린 생각이다. **프로퍼티 `b`(있다면)와 합성 위임 필드 `$$delegate_0`는 서로 다른 저장 슬롯**이다. 생성 시점에는 둘 다 같은 객체를 가리키지만, 그 뒤에 `b`를 (`var`라면) 다시 대입해도 `$$delegate_0`는 바뀌지 않는다.

```kotlin
interface Base2 { fun who(): String }
class Impl2(val tag: String) : Base2 { override fun who() = tag }

class Swappable(var current: Base2) : Base2 by current
//                  ^^^ 프로퍼티(var)          ^^^ 위임 대상은 생성 시 current의 값

fun main() {
    val s = Swappable(Impl2("A"))
    println(s.who())        // => A
    println(s.current.who())// => A

    s.current = Impl2("B")  // 프로퍼티만 바꾼다
    println(s.current.who())// => B   (프로퍼티는 바뀌었다)
    println(s.who())        // => A   (위임은 여전히 "A"! $$delegate_0는 생성 시 값)
}
```

역컴파일해 보면 이유가 분명해진다. `Swappable`에는 `current`용 필드와 `$$delegate_0` 필드가 *둘 다* 있고, 생성자에서 같은 인자로 초기화된 뒤에는 서로 독립적으로 존재한다.

```java
// Swappable 디컴파일 (개념)
public final class Swappable implements Base2 {
   private Base2 current;            // var 프로퍼티 백킹 필드
   private final Base2 $$delegate_0; // 위임 필드 (final! 재대입 불가)
   public Swappable(Base2 current) {
      this.current = current;
      this.$$delegate_0 = current;   // 같은 값으로 시작하지만 별개 슬롯
   }
   public Base2 getCurrent() { return this.current; }
   public void setCurrent(Base2 v) { this.current = v; }   // $$delegate_0는 안 건드림
   public String who() { return this.$$delegate_0.who(); } // 언제나 원래 대상
}
```

`$$delegate_0`가 `final`이라는 점에 주목하자. 위임 대상은 처음부터 다시 대입할 수 없는 슬롯이다. 클래스 위임에는 "위임 대상을 런타임에 바꾸는" 기능이 없다. 그런 기능이 필요하다면 위임을 쓰지 말고, 전달 메서드를 직접 작성해 `var` 필드를 참조하게 해야 한다.

> [!warning] 흔한 오해
> "위임 대상을 `val`로 노출하면 위임이 그 프로퍼티를 따라간다"는 착각은 문법상 두 이름이 가까이 붙어 있어서 생긴다. `Base by b`의 `b`와 프로퍼티 `b`는 이름이 같아 하나처럼 보이지만, 컴파일러 입장에서 `by b`는 *생성자 시점에 평가한 표현식 `b`의 값*일 뿐이고, 프로퍼티 `b`와는 초기값만 공유한다.
>
> `class Swappable(var current: Base2) : Base2 by current`에서 `current`에 새 값을 대입해도 위임 대상은 생성 시점의 값 그대로다. 생성자 파라미터와 프로퍼티의 이름을 나눠 보면(`class Swappable(initial: Base2) : Base2 by initial { var current = initial }`) 둘이 별개라는 점이 분명해진다.

### 4.3 위임 대상에 접근하려면 명시적으로 저장하라

`class D(b: Base) : Base by b`처럼 `b`에 `val`을 붙이지 않으면, 그 참조는 `$$delegate_0`라는 *접근할 수 없는* 합성 필드에만 남는다. 합성 이름이라 소스 코드에서 `this.$$delegate_0`를 이름으로 참조할 방법이 없다. 따라서 **나중에 코드에서 위임 대상을 다루고 싶다면 `by` 표현식과 별도로 프로퍼티에도 저장**해야 한다.

```kotlin
// 위임 대상을 접근하고 싶으면 val 프로퍼티로도 붙들기
class Accessible(val delegate: Base) : Base by delegate {
    fun rawMessage(): String = delegate.message   // delegate 프로퍼티로 접근 가능
}

// 접근 불가 버전 — b는 $$delegate_0에만 있고 코드에선 못 부른다
class Inaccessible(b: Base) : Base by b {
    // 여기서 위임 대상을 직접 참조할 길이 없다
}
```

이 관용구는 8.3절에서 데코레이터가 "감싼 원본"을 노출할 때 다시 나온다. 요점은 `val`을 붙여 프로퍼티로 만드는 비용이 필드 하나(그리고 게터)를 더 쓰는 것뿐이라는 점이다. 이미 `$$delegate_0`가 있으므로 참조가 두 슬롯에 중복 저장되지만, 접근성을 얻는 대가로 흔히 감수한다.

## 5. `override`로 가로채기: 어디까지 가능한가

### 5.1 오버라이드한 멤버는 전달 메서드가 생성되지 않는다

위임의 진짜 장점은 "전부 넘기되 *일부만* 가로챌 수 있다"는 데 있다. 파생 클래스가 위임 인터페이스의 특정 멤버를 `override`하면, 컴파일러는 그 멤버에 대해 전달 메서드를 만들지 않고 파생 클래스의 구현을 쓴다. 데코레이터는 이 방식으로 기존 동작에 새 동작을 덧붙인다.

```kotlin
interface Base3 {
    fun a(): String
    fun b(): String
    fun c(): String
}

class Original : Base3 {
    override fun a() = "orig-a"
    override fun b() = "orig-b"
    override fun c() = "orig-c"
}

class Decorator(base: Base3) : Base3 by base {
    override fun b() = "DECORATED-b"   // b만 가로챈다
}

fun main() {
    val d = Decorator(Original())
    println(d.a())   // => orig-a       (전달됨)
    println(d.b())   // => DECORATED-b  (가로채짐 — 파생의 오버라이드)
    println(d.c())   // => orig-c       (전달됨)
}
```

`Decorator`를 디컴파일하면 `a()`와 `c()`는 `$$delegate_0.a()`, `$$delegate_0.c()`를 호출하는 전달 메서드다. 반면 `b()`는 전달 메서드가 아니라 `"DECORATED-b"`를 직접 반환하는 파생 클래스 자신의 메서드다.

```java
public final class Decorator implements Base3 {
   private final Base3 $$delegate_0;
   public Decorator(Base3 base) { this.$$delegate_0 = base; }
   public String a() { return this.$$delegate_0.a(); }   // 전달
   public String b() { return "DECORATED-b"; }           // 오버라이드 — 전달 아님!
   public String c() { return this.$$delegate_0.c(); }   // 전달
}
```

이 우선순위 규칙은 [[35 - 확장 함수와 프로퍼티]]에서 다루는 "멤버가 확장보다 우선한다"는 규칙과 비슷하다. **파생 클래스에 실제로 있는 멤버가 언제나 우선한다.** 위임 전달 메서드는 파생 클래스가 아무것도 작성하지 않았을 때만 그 빈자리를 채운다.

### 5.2 오버라이드 안에서 위임 대상을 호출할 수 있는가

가로챈 뒤 원래 동작에 무언가를 덧붙이고 싶다면 위임 대상을 명시적으로 호출해야 한다. 그런데 4.3절에서 보았듯이 `by` 파라미터에 `val`을 붙이지 않으면 위임 대상에 접근할 수 없다. 그래서 "가로채면서 원본도 호출하는" 데코레이터는 위임 대상을 프로퍼티로도 저장한다.

```kotlin
interface Base4 { fun compute(): Int }
class Core : Base4 { override fun compute() = 10 }

class PlusOne(private val inner: Base4) : Base4 by inner {
    override fun compute(): Int = inner.compute() + 1
    //                            ^^^^^ 위임 대상을 명시적으로 참조
}

fun main() {
    println(PlusOne(Core()).compute())   // => 11
}
```

여기서 `super.compute()`는 쓸 수 없다는 점에 주의하자. `PlusOne`은 `Base4`를 *상속*한 것이 아니라 *위임*했으므로 `super`가 가리킬 구현 클래스가 없다. `super`는 인터페이스의 기본 구현이나 상위 클래스의 구현을 호출하는 키워드이지, 위임 대상을 호출하는 키워드가 아니다.

위임 대상을 호출하려면 그 참조(`inner`)를 직접 써야 한다. 상속에서는 `super`를 쓰고 위임에서는 명시적 참조를 쓴다는 이 비대칭이, 겉으로 드러난 6절 self 문제의 한 모습이다.

### 5.3 프로퍼티도 가로챌 수 있다

멤버 함수뿐 아니라 인터페이스 프로퍼티도 오버라이드로 가로챌 수 있다. 프로퍼티 위임(백킹 필드 없는 게터로 전달)과 오버라이드는 자연스럽게 함께 쓰인다.

```kotlin
interface HasSize { val size: Int }
class Box(private val items: List<Int>) : HasSize { override val size get() = items.size }

class PaddedBox(private val inner: HasSize) : HasSize by inner {
    override val size: Int get() = inner.size + 2   // 크기를 부풀려서 보고
}

fun main() {
    val b = PaddedBox(Box(listOf(1, 2, 3)))
    println(b.size)   // => 5   (inner.size 3 + 2)
}
```

인터페이스 프로퍼티는 백킹 필드가 없는 접근자 계약(25장 인터페이스)이다. 그래서 위임하면 `getSize()` 전달 메서드가 생기고, 오버라이드하면 파생 클래스의 게터가 그 자리를 대신한다. 함수와 완전히 같은 방식이다.

## 6. self 문제: 위임의 핵심이자 함정

### 6.1 열린 재귀와 닫힌 전달

이제 이 장에서 가장 깊이 있고, 가장 자주 실수하는 지점을 살펴볼 차례다. 5절에서는 오버라이드로 *외부에서 호출되는* 멤버를 가로챌 수 있음을 보았다. 그런데 위임 대상이 *자기 내부에서* 어떤 멤버를 호출하면, 그 호출은 파생 클래스의 오버라이드로 오지 않고 **위임 대상 자신의 구현으로 간다.** 상속이라면 정반대로 동작한다. 이 차이를 직접 확인해 보자.

```kotlin
interface Logger {
    fun log(msg: String)
    fun logAll(msgs: List<String>) {   // 기본 구현: 각 메시지마다 log를 부름
        for (m in msgs) log(m)
    }
}

class BaseLogger : Logger {
    override fun log(msg: String) = println("BASE: $msg")
}

// (A) 위임으로 log를 가로채기
class UpperDelegated(b: Logger) : Logger by b {
    override fun log(msg: String) = println("UPPER: ${msg.uppercase()}")
}

// (B) 상속으로 log를 가로채기 (비교용). BaseLogger를 open으로 만든다고 가정.
open class OpenBaseLogger : Logger {
    override fun log(msg: String) = println("BASE: $msg")
}
class UpperInherited : OpenBaseLogger() {
    override fun log(msg: String) = println("UPPER: ${msg.uppercase()}")
}

fun main() {
    println("--- 위임 ---")
    UpperDelegated(BaseLogger()).logAll(listOf("a", "b"))
    // => BASE: a
    // => BASE: b        (!! UPPER가 아니다)

    println("--- 상속 ---")
    UpperInherited().logAll(listOf("a", "b"))
    // => UPPER: A
    // => UPPER: B        (기대대로 오버라이드가 먹힌다)
}
```

결과가 서로 다르다. 위임에서는 `logAll`이 호출하는 내부 `log`가 오버라이드를 *무시*하고, 상속에서는 오버라이드된 `log`가 *호출된다*. 왜 이런 차이가 생길까?

### 6.2 단계별로 본 동작

**위임 (A)** 의 경우, `UpperDelegated`가 `logAll`을 오버라이드하지 않았으므로 컴파일러는 전달 메서드 `logAll(msgs) = $$delegate_0.logAll(msgs)`를 만든다. `$$delegate_0`는 `BaseLogger` 인스턴스다. 이 인스턴스의 `logAll`은 인터페이스의 기본 구현이고, 그 안의 `log(m)`은 `this.log(m)`이다. **여기서 `this`는 `UpperDelegated`가 아니라 `BaseLogger` 인스턴스**다. 그래서 `BaseLogger.log`("BASE: ...")가 호출된다. 오버라이드는 `UpperDelegated`에 있고, 위임 대상은 그 존재를 모른다.

```text
위임의 디스패치:
  UpperDelegated.logAll(msgs)          [전달 메서드]
      └─> $$delegate_0.logAll(msgs)    [$$delegate_0 = BaseLogger]
              └─> this.log(m)          [this = BaseLogger]  ← 여기가 갈림길
                      └─> BaseLogger.log  → "BASE: ..."      (오버라이드 못 봄)
```

**상속 (B)** 의 경우, `UpperInherited`는 `OpenBaseLogger`를 상속했고 `logAll`도 상속받았다. `UpperInherited().logAll(...)`을 호출하면 상속된 `logAll`이 실행되고, 그 안의 `log(m)`은 `this.log(m)`이다. **여기서 `this`는 `UpperInherited` 인스턴스**다. 따라서 가상 디스패치(virtual dispatch)에 의해 `UpperInherited.log`("UPPER: ...")가 호출된다.

```text
상속의 디스패치:
  UpperInherited.logAll(msgs)          [상속된 메서드]
      └─> this.log(m)                  [this = UpperInherited]  ← 가상 디스패치
              └─> UpperInherited.log  → "UPPER: ..."            (오버라이드 탐)
```

차이의 핵심은 단 하나, **`this`가 누구인가**다. 상속은 상위 클래스와 하위 클래스를 하나의 객체로 합치므로 `this`가 항상 최종 파생 인스턴스를 가리킨다(늦은 바인딩, late binding). 위임은 두 개의 독립된 객체(래퍼와 위임 대상)를 두고, 위임 대상의 `this`는 위임 대상 자신을 가리킨다(전달, forwarding). 위임 대상은 자신을 감싼 래퍼가 있는지조차 모른다.

### 6.3 형식화: 고정점과 self

이 현상은 객체지향 이론에서 **열린 재귀(open recursion)** 와 **닫힌 전달**의 문제로 오래전부터 알려져 있다. 형식적으로 보면 명확하다.

객체를 "self를 인자로 받는 생성자(generator)"로 보자. 어떤 객체의 메서드 묶음을 self에 의존하는 함수 $F$로 쓰면 다음과 같다.

$$
F(\text{self}) = \{\, \texttt{log} \mapsto \dots,\quad \texttt{logAll} \mapsto (\lambda \text{msgs}.\ \forall m.\ \text{self}.\texttt{log}(m)) \,\}
$$

실제 객체는 이 생성자의 **고정점(fixed point)** 이다.

$$
\text{obj} = \operatorname{fix}(F) \qquad \text{where}\quad \operatorname{fix}(F) = F(\operatorname{fix}(F))
$$

즉 `self`가 완성된 객체 자신에 묶인다. **상속**은 고정점을 *취하기 전에* $F$의 일부 메서드를 오버라이드로 교체한다.

$$
\text{obj}' = \operatorname{fix}(F') \quad\text{where}\quad F'(\text{self}) = F(\text{self})\ \text{with}\ \texttt{log}\ \text{replaced}
$$

교체가 고정점 *안쪽*에서 일어나므로, `logAll`이 참조하는 `self.log`는 교체된 `log`를 본다. 이것이 열린 재귀다. self가 최종 결과에 늦게 묶이는 것이다.

**위임**은 정반대다. 위임 대상은 이미 *닫힌* 고정점 $d = \operatorname{fix}(F_{\text{base}})$이다. 래퍼 $W$는 완성된 $d$를 참조하면서 자기 메서드 중 일부를 재정의하지만, $d$ 내부의 `self`에는 관여할 수 없다.

$$
W = \{\, \texttt{log} \mapsto \text{new impl},\quad \texttt{logAll} \mapsto (\lambda \text{msgs}.\ d.\texttt{logAll}(\text{msgs})) \,\}
$$

$d$의 `self`는 이미 $d$로 고정되었으므로($d$의 고정점은 래퍼가 생기기 훨씬 전에 계산되었다), $d.\texttt{logAll}$ 안의 `self.log`는 항상 $d.\texttt{log}$다. $W$의 새 `log`는 $d$의 범위 밖에 있으므로 호출되지 않는다.

$$
\text{상속: self} = \operatorname{fix}(F') \quad(\text{늦은 바인딩})
\qquad
\text{위임: self}_d = d \quad(\text{이른 고정})
$$

이 한 줄의 수식 차이가 6.1절의 출력 차이를 모두 설명한다.

> [!info] 역사 메모
> self 문제(the "self problem")는 1980년대 위임 기반 언어 연구에서 정식화되었다. Henry Lieberman의 프로토타입/위임 논문("Using Prototypical Objects to Implement Shared Behavior in Object-Oriented Systems", OOPSLA 1986)과 Lynn Andrea Stein의 "Delegation Is Inheritance"(OOPSLA 1987) 논쟁이 그 출발점이다.
>
> 핵심 질문은 "위임 대상이 원래 요청을 받은 객체(self)를 알아야 하는가"였다.
>
> 진정한 위임(true delegation)은 self를 넘겨 열린 재귀를 흉내 내지만, 코틀린의 클래스 위임은 self를 넘기지 *않는* 단순 전달(forwarding/consultation)이다. 그래서 코틀린 위임은 이론적으로 "위임"보다 "전달"에 가깝고, 상속의 열린 재귀를 재현하지 않는다. 이 선택은 의도적이다. 열린 재귀가 바로 취약한 기반 클래스 문제(1.1절)의 근본 원인이므로, 위임은 그 결합을 끊어 안전성을 얻는다.

### 6.4 언제 버그가 되고, 언제 장점이 되는가

self 문제에는 양면이 있다.

**장점이 되는 경우**: 1.1절의 `CountingList`가 위임으로 안전해진 이유가 바로 이것이다. 위임 대상(`ArrayList`)의 `addAll`이 내부에서 `add`를 호출하든 말든, 그 `add`는 위임 대상 자신의 `add`이지 `CountingList`가 가로챈 `add`가 아니다. 그래서 `added`가 두 번 세어지지 않는다. 상속이었다면 취약했을 부분을 위임의 닫힌 전달이 구조적으로 막아 준다. "위임 대상 내부의 자기 호출이 바깥으로 새지 않는다"는 성질 덕분에 취약한 기반 클래스 문제가 생기지 않는다.

**버그가 되는 경우**: 6.1절의 `UpperDelegated`가 그렇다. 의도는 "모든 로그를 대문자로 출력한다"였지만, `logAll`처럼 위임 대상 내부에서 `log`를 거치는 경로는 오버라이드를 피해 간다. 개발자는 "log를 가로챘으니 모든 로그가 대문자"라고 믿지만, 위임 대상의 내부 호출 경로를 거치는 메서드들은 조용히 원래 동작을 낸다. 이는 위임의 결함이 아니라 *상속에서 얻은 직관을 위임에 잘못 적용*해서 생기는 오해다.

실무 규칙은 이렇다. **위임으로 어떤 멤버를 가로챌 때는, 위임 인터페이스의 다른 멤버가 그 멤버를 내부에서 호출하는지 반드시 확인하라.** 그렇다면 그 상위 메서드(`logAll`)도 함께 오버라이드해 동작을 일관되게 맞춰야 한다. 인터페이스가 "self-use 계약"(어떤 메서드가 어떤 메서드를 self로 호출하는지)을 문서화하지 않으면 위임 데코레이터를 안전하게 쓸 수 없다. Bloch가 상속에 대해 말한 "self-use를 문서화하라"는 조언이 위임에도 그대로 적용되는 것이다.

```kotlin
// 버그 수정: log를 가로챌 거면 log를 경유하는 logAll도 함께 가로챈다
class UpperFixed(private val b: Logger) : Logger by b {
    override fun log(msg: String) = println("UPPER: ${msg.uppercase()}")
    override fun logAll(msgs: List<String>) {   // self-use 경로도 오버라이드
        for (m in msgs) log(m)   // 이제 this.log = UpperFixed.log
    }
}
// UpperFixed(BaseLogger()).logAll(listOf("a","b")) => UPPER: A / UPPER: B
```

## 7. 다중 위임과 충돌 해소

### 7.1 여러 인터페이스를 동시에 위임하기

한 클래스는 여러 인터페이스를 각각 다른 대상에게 위임할 수 있다. 이 덕분에 위임을 "믹스인(mixin) 조합" 도구로 쓸 수 있다. 위임마다 별도의 합성 필드(`$$delegate_0`, `$$delegate_1`, ...)가 생긴다.

```kotlin
interface Reader { fun read(): String }
interface Writer { fun write(s: String) }

class FileReader : Reader { override fun read() = "data-from-file" }
class FileWriter : Writer { override fun write(s: String) = println("wrote: $s") }

// 읽기는 r에게, 쓰기는 w에게 — 두 능력을 한 객체로 합성
class ReadWriter(r: Reader, w: Writer) : Reader by r, Writer by w

fun main() {
    val rw = ReadWriter(FileReader(), FileWriter())
    println(rw.read())    // => data-from-file  ($$delegate_0으로 전달)
    rw.write("hello")     // => wrote: hello     ($$delegate_1으로 전달)
}
```

`ReadWriter`는 상속으로는 표현하기 어려운 조합이다. 단일 상속 언어에서는 두 클래스를 동시에 상속할 수 없기 때문이다. 위임은 인터페이스마다 독립적인 대상을 두므로 기능을 자유롭게 조합할 수 있다. "위임은 다중 상속의 안전한 대안"이라는 관점이 여기서 나온다.

### 7.2 같은 시그니처가 겹치면 오버라이드를 강제한다

두 위임 인터페이스가 *같은 시그니처의 멤버*를 가지고 있으면, 컴파일러는 어느 쪽으로 전달할지 스스로 정하지 않는다. 다이아몬드 충돌(25장 인터페이스)과 똑같이 **파생 클래스가 명시적으로 오버라이드**하도록 강제한다.

```kotlin
interface A { fun greet(): String }
interface B { fun greet(): String }

class AImpl : A { override fun greet() = "from A" }
class BImpl : B { override fun greet() = "from B" }

// 컴파일 에러: greet가 A와 B 양쪽에서 오므로 모호하다
class Ambiguous(a: A, b: B) : A by a, B by b   // ✗
// error: class 'Ambiguous' must override public open fun greet(): String
//        because it inherits many implementations of it
```

해결 방법은 오버라이드로 어느 대상을 호출할지 명시하는 것이다. 이때 위임 대상을 참조하려면 `val` 프로퍼티로 저장해 두어야 한다(4.3절).

```kotlin
class Resolved(private val a: A, private val b: B) : A by a, B by b {
    override fun greet(): String = a.greet()   // A 쪽을 선택 (또는 b.greet(), 또는 조합)
}

fun main() {
    println(Resolved(AImpl(), BImpl()).greet())   // => from A
}
```

여기서도 `super<A>.greet()` 문법은 쓸 수 없다는 점에 주의하자. `super<A>`는 A를 *상속*했을 때 A의 구현을 호출하는 문법인데, 지금은 위임이므로 상속한 A의 구현이 없다. 위임 대상 참조(`a`, `b`)를 직접 써야 한다. 5.2절과 이 절에서 반복해서 나온 "위임에는 `super`가 없다"는 규칙을 기억해 두자.

### 7.3 위임 대상이 상태를 가질 때: 공유의 함정

위임 대상은 상태를 가진 실제 객체다. 여러 래퍼가 *같은* 위임 대상을 공유하면, 한쪽을 통한 변경이 다른 쪽에도 보인다. 위임은 참조를 복사할 뿐 상태를 복사하지 않는다.

```kotlin
interface MutableCounter {
    var count: Int
    fun increment()
}
class CounterImpl : MutableCounter {
    override var count = 0
    override fun increment() { count++ }
}

fun main() {
    val shared = CounterImpl()
    val w1 = object : MutableCounter by shared {}   // 같은 shared에 위임
    val w2 = object : MutableCounter by shared {}   // 역시 같은 shared

    w1.increment()
    w1.increment()
    println(w2.count)   // => 2   (w1으로 올린 값이 w2에도 보인다 — 같은 대상 공유)
    println(shared.count) // => 2
}
```

`w1`과 `w2`는 서로 다른 래퍼지만 위임 대상은 하나(`shared`)다. 그래서 `w1.increment()`가 `shared.count`를 올리면, 역시 `shared.count`로 전달되는 `w2.count`도 함께 오른다. 4.1절에서 "위임 대상을 스냅샷한다"고 한 것은 *참조*를 스냅샷한다는 뜻이지 *깊은 복사*를 한다는 뜻이 아니다.

데코레이터마다 독립적인 상태가 필요하다면 각각에게 별도의 위임 대상 인스턴스를 넘겨야 한다. 이런 얕은 공유는 27장(데이터 클래스)의 `copy`가 얕은 복사라는 점과 같은 종류의 함정이다. 둘 다 참조 의미론을 값 의미론으로 착각해서 생긴다.

## 8. 실전 패턴과 안티패턴

### 8.1 데코레이터: 읽기 전용 컬렉션 래핑과 `equals` 함정

실전에서 가장 흔한 용례는 컬렉션이나 서비스 인터페이스에 얇은 동작을 덧붙이는 데코레이터다. 그런데 3.2절에서 경고한 `equals` 미전달 문제가 여기서 드러난다.

```kotlin
// 접근을 로깅하는 List 데코레이터
class LoggingList<E>(private val inner: List<E>) : List<E> by inner {
    override fun get(index: Int): E {
        println("get($index)")
        return inner[index]
    }
}

fun main() {
    val list = LoggingList(listOf(10, 20, 30))
    println(list[1])          // => get(1) / 20
    println(list.size)        // => 3    (size는 전달됨)

    // 함정: equals는 위임되지 않는다
    println(list == listOf(10, 20, 30))   // => false  (Any.equals — 참조 비교)
    println(listOf(10, 20, 30) == list)   // => false  (역방향도 마찬가지)
}
```

`List`의 구조적 동등성 계약은 `Any`에서 온 `equals`/`hashCode`로 구현되는데, 위임은 인터페이스 멤버만 넘기므로 이 둘이 빠진다. 그래서 `LoggingList`는 리스트처럼 보이지만 같은 원소를 가진 리스트와 같다고 판정되지 않는다. 동등성 비교가 필요하다면 명시적으로 오버라이드하거나, `equals`/`hashCode`가 필요 없는 곳에서만 위임 래퍼를 쓴다.

```kotlin
class EquatableList<E>(private val inner: List<E>) : List<E> by inner {
    override fun equals(other: Any?): Boolean = inner == other
    override fun hashCode(): Int = inner.hashCode()
    override fun toString(): String = inner.toString()
}
```

> [!caution] 성능 주의
> 위임으로 만든 컬렉션 데코레이터는 원본을 감싼 얇은 층이므로 메모리·복사 비용이 없다(원본을 복사하지 않고 참조만 가진다). 이 점은 방어적 복사([[38 - 컬렉션 - 읽기 전용과 가변]])와 대비된다. 방어적 복사는 O(n) 메모리를 쓰지만 원본과 완전히 분리되고, 위임 래퍼는 O(1)이지만 원본과 상태를 공유한다(7.3절). 상황에 맞게 선택하자.

### 8.2 믹스인: 기능의 수평 조합

7.1절의 다중 위임을 하나의 패턴으로 발전시키면 믹스인이 된다. 작은 기능(인터페이스)을 각각 구현한 재사용 부품을 위임으로 조립해 큰 객체를 만드는 방식이다.

```kotlin
interface Serializable2 { fun serialize(): String }
interface Validatable { fun validate(): Boolean }
interface Cacheable { fun cacheKey(): String }

// 재사용 가능한 능력 구현들
class JsonSerializer(private val name: String) : Serializable2 {
    override fun serialize() = """{"name":"$name"}"""
}
class NonEmptyValidator(private val name: String) : Validatable {
    override fun validate() = name.isNotEmpty()
}
class NameCacheKey(private val name: String) : Cacheable {
    override fun cacheKey() = "name:$name"
}

// 세 능력을 위임으로 조립
class Entity(name: String) :
    Serializable2 by JsonSerializer(name),
    Validatable by NonEmptyValidator(name),
    Cacheable by NameCacheKey(name)

fun main() {
    val e = Entity("Kotlin")
    println(e.serialize())   // => {"name":"Kotlin"}
    println(e.validate())    // => true
    println(e.cacheKey())    // => name:Kotlin
}
```

위임 대상마다 `name`을 따로 받는 것이 눈에 걸릴 수 있다. 이는 위임 대상이 서로 독립된 객체라 상태를 공유하지 않기 때문이다. 상태를 실제로 공유해야 한다면 하나의 구현 객체가 여러 인터페이스를 구현하게 하고, 그 객체 하나에 위임하면 된다(`ReadWriter`처럼).

### 8.3 위임 대상 노출과 언랩

데코레이터는 "감싼 원본"을 밖으로 내주어야 할 때가 많다. 이때는 4.3절의 관용구대로 `val`로 저장해 노출한다.

```kotlin
interface Repository<T> { fun findAll(): List<T> }

class CachingRepository<T>(val underlying: Repository<T>) : Repository<T> by underlying {
    private var cache: List<T>? = null
    override fun findAll(): List<T> = cache ?: underlying.findAll().also { cache = it }
    fun invalidate() { cache = null }
    fun unwrap(): Repository<T> = underlying   // 원본 노출
}
```

`underlying`이 `val` 프로퍼티이므로 `findAll` 오버라이드(캐시 미스일 때 원본 호출)와 `unwrap`(원본 반환)을 모두 구현할 수 있다. `by underlying`은 `findAll` 이외의 멤버(있다면)를 원본으로 전달하고, `findAll`만 캐싱으로 가로챈다. 위임과 프로퍼티를 함께 쓰는 전형적인 형태다.

### 8.4 안티패턴: 위임을 쓰지 말아야 할 때

위임은 강력하지만 남용하면 새로운 함정이 생긴다.

1. **self-use가 많은 인터페이스를 무심코 위임하기**: 6절에서 보았듯이 위임 대상 내부의 자기 호출은 오버라이드를 우회한다. `template method` 패턴처럼 "상위 메서드가 하위 훅을 호출하는" 설계의 인터페이스를 위임으로 데코레이트하면, 훅을 오버라이드해도 적용되지 않는다. 이런 인터페이스라면 위임보다 상속이 의도에 맞거나, self-use 경로를 모두 오버라이드해야 한다.
2. **`equals`/`hashCode`가 중요한 값 객체를 위임으로 래핑하기**: 8.1절의 함정이다. `Set`/`Map`의 키로 쓰이거나 구조적 비교가 필요한 타입을 위임 래퍼로 만들면 동등성이 조용히 깨진다.
3. **위임 대상을 바꿀 수 있다는 착각**: 4.2절에서 보았듯이 위임 필드는 `final`이고 생성 시점에 고정된다. "런타임에 위임 대상을 교체"해야 한다면 위임 대신 수동 전달과 `var` 필드를 써야 한다.
4. **깊은 위임 중첩으로 디버깅이 어려워지는 경우**: 데코레이터 위에 데코레이터를 여러 겹 쌓으면, 어떤 호출이 어느 층에서 처리되고 어디서 전달되는지 추적하기 어려워진다. 스택 트레이스에도 `$$delegate_0` 전달 프레임이 끼어든다. 두세 겹까지는 명료하지만, 그 이상이라면 명시적인 구성을 고려하자.
5. **위임을 상속의 완전한 대체로 오해하기**: 위임은 인터페이스에만 쓸 수 있고, `super` 호출이 없으며, 위임 대상의 protected 멤버에 접근할 수 없고, 위임 대상 내부의 self-use를 바꿀 수 없다. 상속이 주는 열린 재귀와 구현 재사용이 *꼭 필요한* 드문 경우에는 상속이 맞다. 위임은 "대부분의 경우 더 안전한 기본값"이지 "만능 대체재"가 아니다.

이 다섯 가지를 뒤집으면 위임을 쓰기 가장 좋은 조건이 나온다. **작고 self-use가 적은 인터페이스를, 상태와 동등성을 공유해도 문제없는 데코레이터나 믹스인으로, 생성 후 대상이 바뀌지 않는 방식으로** 쓸 때, 위임은 상속의 취약함 없이 컴포지션의 안전성을 적은 비용으로 제공한다.
