**이 장이 답하는 질문:**

- 코틀린의 프로퍼티는 자바의 필드와 무엇이 다른가? "프로퍼티는 필드다"라는 직관은 왜 틀렸는가?
- `field`라는 예약어는 어디서 튀어나오고, 백킹 필드는 정확히 *언제* 생성되며 *언제* 생성되지 않는가?
- 커스텀 게터를 하나 붙이는 순간 그 프로퍼티의 저장 공간에는 무슨 일이 일어나는가?
- `val` 프로퍼티는 왜 매 접근마다 다른 값을 돌려줄 수 있는가? 그게 `val`의 불변성과 모순되지 않는가?
- 계산 프로퍼티(computed property)와 저장 프로퍼티(stored property)의 경계는 컴파일러에게 어떻게 보이는가?
- 백킹 프로퍼티(backing property) 패턴은 왜 필요하고, `private val _items`/`public val items` 관용구는 무슨 문제를 푸는가?
- JVM 백엔드에서 프로퍼티는 무엇으로 컴파일되는가 — `getX()`/`setX()`, `isX()`, 그리고 `@JvmField`가 바꾸는 것은?
- 접근자에 프로퍼티와 다른 가시성을 줄 수 있는가? 왜 게터는 되고 세터만 조일 수 있는가?
- 인터페이스 프로퍼티는 왜 상태를 저장하지 못하는가?

---

[[21 - 클래스와 생성자]]에서 우리는 `class Circle(val radius: Double)`처럼 주 생성자 괄호 안에 `val`/`var`를 적으면 "프로퍼티가 선언된다"고 배웠다. 그런데 그때 우리가 실제로 만든 것이 무엇인지는 얼버무리고 넘어갔다. 자바를 아는 사람은 무심코 "필드(field)가 하나 생겼구나"라고 읽는다. 이 장은 바로 그 무심한 독해를 정면으로 부순다. 코틀린에서 우리가 `val radius`라고 쓸 때 언어가 만드는 일차적 대상은 저장 공간(필드)이 아니라 **접근자(accessor) — 즉 게터와 세터라는 한 쌍의 함수**다. 저장 공간은 그 접근자를 뒷받침하기 위해 *필요할 때만* 조용히 딸려 나온다. 이 순서를 뒤집어 이해하는 것이 이 장 전체의 핵심이며, 전역 오개념 원장의 **M35("코틀린 프로퍼티는 필드다")** 를 이 장이 소유해 정면으로 교정하는 이유다.

이 장이 다루는 것과 다루지 않는 것의 경계를 먼저 못박자. 우리는 *일반 프로퍼티*의 해부 — 접근자, 백킹 필드 `field`, 커스텀 게터/세터, 계산 프로퍼티, 백킹 프로퍼티 패턴, JVM 컴파일 형태 — 를 끝까지 판다. 그러나 프로퍼티의 저장·계산 로직을 아예 다른 객체에게 위임하는 `by` 문법, 즉 **위임 프로퍼티**는 [[23 - 위임 프로퍼티]]가 소유한다(이 장은 예고만 한다). 인터페이스가 프로퍼티를 선언하되 상태를 못 가지는 이유는 여기서 원리를 짚되 심화는 [[25 - 인터페이스]]가 가져간다(M37). 프로퍼티가 상속·오버라이드되며 초기화 순서와 얽히는 함정은 [[24 - 상속과 오버라이딩과 초기화 순서]]가(M47), 클래스 밖에서 프로퍼티를 얹는 확장 프로퍼티는 [[35 - 확장 함수와 프로퍼티]]가 소유한다. `val` vs `var` vs `const` vs `lateinit`의 변수 축은 [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 이미 세웠으니(M3/M9/M36), 이 장은 그중 *멤버 프로퍼티*에 초점을 맞춘다.

논증의 궤적은 이렇다. 먼저 프로퍼티를 "접근자 추상"으로 다시 정의하고(1절), 그 추상을 물리적으로 뒷받침하는 `field`가 언제 태어나는지의 규칙을 세운다(2절). 그다음 커스텀 게터·세터를 붙이며 백킹 필드가 사라지거나 남는 경계를 실험하고(3절), `val`/`var`가 사실은 "세터의 유무"에 불과함을 보인다(4절). 접근자의 가시성(5절)과 백킹 프로퍼티 패턴(6절)으로 실전 관용구를 익힌 뒤, JVM 백엔드가 이 모든 것을 무엇으로 번역하는지(7절)와 인터페이스·추상 프로퍼티의 무상태성(8절)으로 마무리한다. 끝에 이르면 "프로퍼티는 필드다"라는 문장이 왜 편의상은 통하지만 원리상은 거짓인지가 몸에 붙어 있을 것이다.

## 1. 프로퍼티라는 추상 — 필드가 아니라 접근자

### 1.1 자바의 필드와 코틀린의 프로퍼티는 다른 층위다

자바에서 클래스의 상태는 **필드(field)** 로 저장하고, 캡슐화를 위해 손으로 `getX()`/`setX()` 메서드를 짜서 감싼다. 필드는 "저장 슬롯"이고 게터/세터는 "그 슬롯을 감싼 함수"이며, 이 둘은 문법적으로 완전히 별개다.

```java
// Java
public class Circle {
    private double radius;              // 필드: 저장 슬롯
    public double getRadius() {         // 손으로 짠 게터
        return radius;
    }
    public void setRadius(double r) {   // 손으로 짠 세터
        this.radius = r;
    }
}
```

코틀린은 이 구도를 뒤집는다. 코틀린에서 클래스 멤버로 선언하는 일차 시민은 **프로퍼티(property)** 이고, 프로퍼티의 정체는 "이름으로 접근하는 값" 뒤에 붙은 **게터(그리고 var면 세터)라는 접근자 함수**다. 저장 슬롯은 프로퍼티의 본질이 아니라, 접근자가 값을 어딘가에 담아야 할 때 컴파일러가 몰래 제공하는 뒷받침에 불과하다.

```kotlin
class Circle {
    var radius: Double = 0.0    // 프로퍼티 하나 — 게터+세터가 자동 합성됨
}

fun main() {
    val c = Circle()
    c.radius = 5.0              // 문법은 필드 대입처럼 보이지만 → 세터 호출
    println(c.radius)           // => 5.0   문법은 필드 읽기처럼 보이지만 → 게터 호출
}
```

`c.radius = 5.0`은 필드에 직접 값을 쓰는 것처럼 보이지만, 코틀린의 관점에서 이것은 `c.setRadius(5.0)` 접근자 호출의 문법 설탕이다. `c.radius` 읽기는 `c.getRadius()` 호출이다. 이 겉모습과 속살의 분리 — 필드처럼 보이는 표기 뒤에 함수 호출이 있다는 것 — 이 프로퍼티의 전부다. 이것이 **M35**의 정확한 교정이다: 코틀린 프로퍼티는 필드가 아니라 *접근자 추상*이며, 필드는 그 추상을 물리적으로 실현하기 위한 선택적 부산물이다.

> **흔한 오해 (M35)**: "코틀린 프로퍼티는 결국 자바 필드 + 자동 게터/세터일 뿐이다." 절반만 맞다. 프로퍼티는 필드를 *가질 수도 있고 안 가질 수도 있다*. 백킹 필드가 없는 프로퍼티(계산 프로퍼티)는 저장 슬롯이 아예 존재하지 않으며, 접근할 때마다 게터 본문이 실행되어 값을 새로 만들어 낸다. 프로퍼티를 필드와 동일시하면 이 부류 전체가 시야에서 사라진다.

### 1.2 프로퍼티 선언의 완전한 문법 형태

코틀린 명세가 정의하는 프로퍼티 선언의 전체 형태는 다음과 같다. 실무에서는 대부분 생략되지만, 무엇이 생략되고 있는지를 알면 프로퍼티의 구조가 또렷해진다.

```text
[modifiers] val|var <이름>[: <타입>] [= <초기화식> | by <위임>]
    [get() [ = <식> | { <본문> } ]]
    [set(<파라미터>) [ = <식> | { <본문> } ]]
```

- `val`이면 게터만, `var`이면 게터와 세터를 가질 수 있다.
- 초기화식(`= ...`)이 있으면 그 값을 담을 **백킹 필드**가 생긴다.
- `get()`/`set()`을 명시하지 않으면 컴파일러가 **기본 접근자**를 합성한다. 기본 게터는 `field`를 반환하고, 기본 세터는 `field = value`를 대입한다.

```kotlin
class Account {
    var balance: Long = 0          // 기본 게터/세터 (아래와 동치)
}

// 위 선언은 개념적으로 이것과 같다:
class AccountExplicit {
    var balance: Long = 0
        get() = field              // 기본 게터: 백킹 필드 반환
        set(value) { field = value }   // 기본 세터: 백킹 필드에 대입
}
```

두 선언은 바이트코드 수준에서 동일하다. 코틀린이 우리에게 준 편의는 "이 자명한 접근자 한 쌍을 안 적어도 된다"는 것이지, "필드를 만들어 준다"가 아니다. 만들어지는 접근자가 우연히 필드를 필요로 할 뿐이다.

### 1.3 균일 접근 원칙 — 이 설계가 사는 이유

왜 코틀린은 필드가 아니라 프로퍼티를 일차 시민으로 삼았을까? 답은 버트런드 마이어가 정식화한 **균일 접근 원칙(Uniform Access Principle)** 이다: *"클라이언트 코드는 어떤 값이 저장된 것인지 계산된 것인지 구별하지 않고 동일한 표기로 접근할 수 있어야 한다."*

자바에서는 처음에 `public double radius;` 필드로 노출했다가, 나중에 "반지름을 읽을 때 로그를 남기자"거나 "지름으로부터 계산하자"는 요구가 생기면 필드를 메서드로 바꿔야 하고, 그러면 `obj.radius`를 쓰던 모든 호출부가 `obj.getRadius()`로 깨진다. 이 때문에 자바 개발자는 처음부터 방어적으로 모든 필드를 private로 숨기고 게터/세터를 짠다. 코틀린에서는 이 갈등이 아예 없다. `radius`를 저장 프로퍼티로 시작했다가 나중에 계산 프로퍼티로 바꿔도 **호출부 `obj.radius`는 한 글자도 바뀌지 않는다**. 접근 표기가 이미 접근자 호출이기 때문이다.

```kotlin
// v1: 저장 프로퍼티
class Circle1(var radius: Double) {
    var diameter: Double = radius * 2      // 저장 — 독립적으로 값을 가짐
}

// v2: 요구가 바뀌어 diameter를 radius에서 파생하도록 변경
class Circle2(var radius: Double) {
    var diameter: Double                   // 이제 계산 프로퍼티 — 백킹 필드 없음
        get() = radius * 2
        set(value) { radius = value / 2 }
}

// 두 버전 모두 호출부는 동일:
fun use(c: Circle2) {
    println(c.diameter)     // 표기 불변
    c.diameter = 20.0       // 표기 불변
}
```

이 원칙이 코틀린 프로퍼티 설계의 심장이다. 프로퍼티는 "저장이냐 계산이냐"를 **구현 세부로 숨기는 인터페이스**이고, 백킹 필드는 그 인터페이스가 저장을 택했을 때만 등장하는 사적 구현이다. 이 관점을 손에 쥐면 이후의 모든 규칙이 자연스럽게 따라 나온다.

## 2. 백킹 필드 `field` — 언제 태어나고 언제 태어나지 않는가

### 2.1 백킹 필드 생성 규칙: "field를 참조하면 생긴다"

백킹 필드(backing field)는 프로퍼티의 값을 담는 실제 저장 슬롯이다. 코틀린 컴파일러는 백킹 필드를 무조건 만들지 않는다. **정확한 규칙**은 다음과 같다:

> **명세 정밀**: 프로퍼티에 대해 백킹 필드는 다음 중 하나라도 참일 때 생성된다.
> 1. 프로퍼티가 **기본 게터 또는 기본 세터를 최소한 하나** 사용한다(즉 그 접근자를 커스텀으로 짜지 않았다). 기본 접근자는 암묵적으로 `field`를 참조하기 때문이다.
> 2. 커스텀 접근자의 본문이 **명시적으로 `field` 식별자를 참조**한다.
>
> 둘 다 아니면 — 즉 모든 접근자를 커스텀으로 짰고 그중 누구도 `field`를 쓰지 않으면 — 백킹 필드는 생성되지 않는다. 그런 프로퍼티는 "저장 슬롯이 없는" 순수 계산 프로퍼티다.

이 규칙을 표로 정리하면 다음과 같다.

| 선언 형태 | `field` 참조 여부 | 백킹 필드 |
|---|---|---|
| `var x = 0` (기본 접근자) | 기본 접근자가 암묵 참조 | **생성** |
| `val x = f()` (기본 게터) | 기본 게터가 암묵 참조 | **생성** |
| `val x get() = a + b` | 참조 안 함 | **생성 안 됨** |
| `var x get() = a; set(v){ a = v }` | 참조 안 함 | **생성 안 됨** |
| `var x get() = field; set(v){ field = v * 2 }` | 참조함 | **생성** |
| `val x: Int` (추상/인터페이스) | 접근자 본문 없음 | **생성 안 됨** |

핵심 직관: **`field`는 백킹 필드를 존재하게 만드는 스위치**다. 접근자 안에서 `field`를 한 번이라도 쓰면 컴파일러는 "이 프로퍼티는 저장할 곳이 필요하구나"라고 판단해 필드를 마련한다. 반대로 `field`를 전혀 안 쓰면 저장할 곳도 없다.

### 2.2 계산 프로퍼티에는 백킹 필드가 없다

`field`를 참조하지 않는 프로퍼티를 **계산 프로퍼티(computed property)** 또는 파생 프로퍼티라 부른다. 이런 프로퍼티는 값을 어디에도 저장하지 않고, 접근될 때마다 게터 본문을 실행해 값을 즉석에서 만든다.

```kotlin
class Rectangle(val width: Double, val height: Double) {
    val area: Double                      // 백킹 필드 없음
        get() = width * height            // 매 접근마다 계산

    val isSquare: Boolean
        get() = width == height           // 매 접근마다 계산
}

fun main() {
    val r = Rectangle(3.0, 4.0)
    println(r.area)      // => 12.0   (width*height를 지금 계산)
    println(r.area)      // => 12.0   (또 계산 — 저장된 값이 아니다)
    println(r.isSquare)  // => false
}
```

`area`는 객체의 메모리 레이아웃에 자리를 차지하지 않는다. `Rectangle` 인스턴스는 `width`와 `height` 두 필드만 갖고, `area`는 `getArea()` 함수로만 존재한다. 이것이 "프로퍼티 ≠ 필드"의 가장 선명한 증거다. `area`는 완전한 프로퍼티지만 저장 슬롯이 0바이트다.

```text
Rectangle 인스턴스의 메모리 레이아웃 (JVM 백엔드, 개념)
┌─────────────────────────────┐
│ 객체 헤더                    │
├─────────────────────────────┤
│ double width   ← 백킹 필드   │
│ double height  ← 백킹 필드   │
└─────────────────────────────┘
   area, isSquare는 여기 없음 — getArea(), getIsSquare() 함수로만 존재
```

> **성능 주의**: 계산 프로퍼티는 접근할 때마다 본문을 실행한다. `area`를 루프에서 수백만 번 읽으면 곱셈이 수백만 번 일어난다. 저렴한 계산이면 문제없지만, 무거운 계산(예: 리스트 정렬, 정규식 매칭)을 계산 프로퍼티에 숨기면 호출부는 "그냥 값 읽기"로 오해하고 성능 함정에 빠진다. 무거운데 값이 안 변하면 저장 프로퍼티로 캐싱하거나 [[23 - 위임 프로퍼티]]의 `by lazy`로 한 번만 계산하게 하라. 관용상 "필드처럼 싸게 읽힌다"는 기대를 배신하는 게터는 나쁜 API다.

### 2.3 `field`는 접근자 안에서만 보이는 소프트 키워드

`field`는 특별한 식별자다. 그것은 오직 **프로퍼티 접근자의 본문 안에서만** 의미를 가지며, 그 프로퍼티 자신의 백킹 필드를 가리킨다. 접근자 밖에서 `field`는 평범한 이름일 뿐이다. 즉 `field`는 [[03 - 렉시컬 구조와 세미콜론 추론]]에서 다룬 **소프트 키워드**로, 맥락에 따라 예약어가 되기도 하고 보통 식별자가 되기도 한다.

```kotlin
class Temperature {
    var celsius: Double = 0.0
        set(value) {
            field = value.coerceAtLeast(-273.15)   // field = 이 프로퍼티의 백킹 필드
        }

    fun field() = "이건 그냥 메서드 이름"   // 접근자 밖 — field는 평범한 이름
}
```

중요한 제약: **`field`로는 오직 자기 자신의 백킹 필드만 접근할 수 있다.** 다른 프로퍼티의 백킹 필드를 `field`로 건드릴 방법은 없다. 다른 프로퍼티는 이름으로(즉 접근자를 통해) 접근해야 한다. 이 격리 덕분에 백킹 필드는 프로퍼티의 완전한 사적 구현으로 남는다.

`field`를 쓸 때 반드시 붙는 짝이 세터의 파라미터다. 커스텀 세터의 파라미터는 관례적으로 `value`라 이름 짓지만 아무 이름이나 가능하며, 그것이 대입되려는 새 값이다. `field = value`가 "백킹 필드에 새 값을 저장한다"는 뜻이고, 기본 세터가 하는 일이 바로 이것이다.

## 3. 커스텀 게터와 세터 — 접근자에 로직을 심다

### 3.1 커스텀 게터

커스텀 게터는 프로퍼티를 읽을 때 실행할 코드를 우리가 정하는 것이다. `get()` 뒤에 단일 식(`= expr`)이나 블록(`{ ... }`)을 둔다.

```kotlin
class Person(val firstName: String, val lastName: String) {
    val fullName: String
        get() = "$firstName $lastName"        // 단일 식 게터, 백킹 필드 없음

    val initials: String
        get() {                                // 블록 게터
            val f = firstName.firstOrNull() ?: ' '
            val l = lastName.firstOrNull() ?: ' '
            return "$f.$l."
        }
}
```

게터의 반환 타입은 프로퍼티 타입과 같아야 한다. 프로퍼티 타입을 명시했다면 게터는 그 타입을 반환해야 하고, 생략했다면 게터 식으로부터 추론된다(단, 계산 프로퍼티에서 타입 추론이 되려면 게터가 프로퍼티 선언 직후에 와야 한다).

저장 프로퍼티에도 커스텀 게터를 얹어 "저장은 하되 읽을 때 가공"할 수 있다. 이때 `field`를 써야 백킹 필드가 유지된다.

```kotlin
class Counter {
    var count: Int = 0
        get() {
            println("count 읽힘")     // 부수효과(로깅) 삽입
            return field              // field 참조 → 백킹 필드 유지됨
        }
}
```

### 3.2 커스텀 세터와 `value` 파라미터 — 검증·정규화·불변식

커스텀 세터는 프로퍼티에 값을 대입할 때 실행된다. 세터의 세계에서 가장 흔한 쓰임은 **검증(validation)과 정규화(normalization)**, 즉 저장 전에 불변식을 강제하는 것이다.

```kotlin
class BankAccount {
    var balance: Long = 0
        set(value) {
            require(value >= 0) { "잔액은 음수가 될 수 없다: $value" }
            field = value             // 검증 통과 시에만 저장
        }

    var ownerName: String = ""
        set(value) {
            field = value.trim()      // 저장 전 정규화(공백 제거)
        }
}

fun main() {
    val acc = BankAccount()
    acc.balance = 1000
    println(acc.balance)              // => 1000
    acc.ownerName = "  Alice  "
    println("[${acc.ownerName}]")     // => [Alice]  (trim됨)
    acc.balance = -5                  // => IllegalArgumentException: 잔액은 음수가 될 수 없다: -5
}
```

세터 파라미터의 타입은 프로퍼티 타입으로 고정된다. 타입을 명시할 수는 있으나 반드시 프로퍼티 타입과 같아야 하며(`var balance: Long`에 `set(value: String)`처럼 다른 타입을 적으면 컴파일 에러), 어차피 프로퍼티 타입으로 정해져 있으니 보통은 생략하고 `set(value)`로만 쓴다. 파라미터 이름은 자유지만 관례는 `value`다.

세터에서 흥미로운 점은 **게터가 돌려주는 값과 세터가 받는 값이 반드시 대칭일 필요가 없다**는 것이다. 세터가 값을 변형해 저장하면 게터로 읽을 때 원래 넣은 값과 다른 값이 나올 수 있다.

```kotlin
class CaseInsensitiveTag {
    var value: String = ""
        set(v) { field = v.lowercase() }   // 소문자로 저장

    // getter는 기본 → field 그대로 반환
}

fun main() {
    val t = CaseInsensitiveTag()
    t.value = "HELLO"
    println(t.value)     // => hello   (넣은 값과 다름)
}
```

이 비대칭은 강력하지만 위험하다. API 사용자는 대개 "넣은 대로 나온다"를 기대하므로, 세터가 값을 조용히 바꾸면 놀란다. 정규화가 도메인적으로 자명할 때(공백 제거, 대소문자 통일)만 쓰고, 그렇지 않으면 별도 메서드로 명시하는 편이 낫다.

### 3.3 접근자 안에서 프로퍼티 이름을 쓰면 — 무한 재귀

프로퍼티 접근자를 처음 짜는 사람이 거의 반드시 한 번은 밟는 지뢰가 있다. **접근자 안에서 `field` 대신 프로퍼티 이름을 쓰는 것**이다.

```kotlin
class Broken {
    var x: Int = 0
        get() = x            // 함정! x를 읽으면 getX() 호출 → 다시 get() → 무한 재귀
        set(value) { x = value }   // 함정! x에 대입 → setX() 호출 → 다시 set() → 무한 재귀
}

fun main() {
    val b = Broken()
    println(b.x)             // => StackOverflowError (게터가 자기 자신을 무한 호출)
}
```

`get() = x`에서 `x`는 백킹 필드가 아니라 **프로퍼티 `x`에 대한 접근**이고, 프로퍼티 접근은 곧 게터 호출이므로 게터가 게터를 부르는 무한 재귀가 된다. 세터도 마찬가지다. 올바른 코드는 `field`를 써야 한다.

```kotlin
class Fixed {
    var x: Int = 0
        get() = field                 // 백킹 필드 직접 접근 — 재귀 없음
        set(value) { field = value }
}
```

> **흔한 오해**: "게터 안의 `x`는 '지금 정의 중인 이 프로퍼티'니까 필드를 뜻하겠지." 아니다. 코틀린에는 "프로퍼티 이름 = 필드" 같은 지름길이 없다. 프로퍼티 이름은 *언제나* 접근자 호출로 해소되고, 백킹 필드에 닿는 유일한 통로는 `field` 예약어다. 이 규칙에 예외는 없으며, 바로 이 일관성이 균일 접근 원칙(1.3)을 떠받친다.

이 함정은 코틀린이 프로퍼티를 접근자로 본다는 사실을 가장 아프게 가르쳐 준다. `x`가 필드라면 `get() = x`는 필드를 읽는 정상 코드일 것이다. 하지만 `x`는 필드가 아니라 접근자 쌍의 이름이므로, 자기 안에서 자기를 부르는 재귀가 된다.

## 4. `val` vs `var` 프로퍼티 — 사실은 "세터의 유무"

### 4.1 `val`은 게터만, `var`은 게터+세터

[[11 - 변수와 초기화 - val과 const와 lateinit]]에서 `val`은 "재대입 불가", `var`은 "재대입 가능"으로 배웠다. 멤버 프로퍼티 층위에서 이 구분은 접근자로 번역된다: **`val` 프로퍼티는 게터만 가지고, `var` 프로퍼티는 게터와 세터를 가진다.** 그래서 `val` 프로퍼티에는 `set()`을 정의할 수 없다.

```kotlin
class C {
    val readOnly: Int = 10
        // set(v) { ... }   // 컴파일 에러: A 'val'-property cannot have a setter

    var readWrite: Int = 10
        get() = field
        set(v) { field = v }
}
```

"재대입 불가"라는 성질이 세터의 부재로 실현된다는 것은 중요하다. `val`이 막는 것은 "이 프로퍼티에 대입하는 문법(`obj.readOnly = ...`)"이지, "이 프로퍼티가 가리키는 값의 내부 변경"이 아니다. 이것이 [[11 - 변수와 초기화 - val과 const와 lateinit]]가 소유한 **M3**(val은 재대입 불가일 뿐 불변 객체를 만들지 않는다)의 프로퍼티 판본이다.

```kotlin
class Basket {
    val items: MutableList<String> = mutableListOf()   // val — 재대입 불가
}

fun main() {
    val b = Basket()
    b.items.add("apple")      // OK — 가리키는 리스트를 변경(세터 호출 아님)
    b.items.add("banana")
    println(b.items)          // => [apple, banana]
    // b.items = mutableListOf()   // 컴파일 에러: val cannot be reassigned (세터 없음)
}
```

`b.items.add(...)`는 세터를 호출하지 않는다. 게터가 돌려준 리스트 객체의 메서드를 부를 뿐이다. `val`은 게터가 돌려주는 참조를 다른 참조로 갈아끼우는 것(세터)만 막는다.

### 4.2 `val` 프로퍼티도 매번 다른 값을 낼 수 있다

`val`이 "불변"을 뜻한다고 오해하면 다음 코드가 당혹스럽다.

```kotlin
import kotlin.random.Random

class Dice {
    val roll: Int                 // val인데…
        get() = Random.nextInt(1, 7)   // 매 접근마다 새 난수
}

fun main() {
    val d = Dice()
    println(d.roll)   // => 4  (예)
    println(d.roll)   // => 1  (또 다름!)
    println(d.roll)   // => 6
}
```

`roll`은 `val`이지만 읽을 때마다 다른 값을 낸다. 모순이 아니다. `val`은 세터가 없다는 뜻이지 "게터가 항상 같은 값을 반환한다"는 뜻이 아니기 때문이다. `val` 프로퍼티는 백킹 필드에 저장된 불변값을 낼 수도 있고(저장 프로퍼티), 매번 계산한 값을 낼 수도 있다(계산 프로퍼티). `val`은 접근자 구조에 대한 제약(세터 없음)이지 게터 결과의 안정성에 대한 보증이 아니다.

> **명세 정밀**: 이 성질 때문에 **커스텀 게터를 가진 `val` 프로퍼티는 스마트 캐스트가 되지 않는다**([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]의 M13 참조). 컴파일러가 `if (obj.p != null) { obj.p.foo() }`를 스마트 캐스트하려면 두 번의 `obj.p` 접근이 같은 값을 낸다고 보장할 수 있어야 하는데, 커스텀 게터는 매번 다른 값을 낼 수 있으므로 그 보장이 깨진다. 반면 백킹 필드를 가진 `val`(같은 모듈)은 값이 고정이라 스마트 캐스트가 허용된다.

```kotlin
class Node(val next: Node?, val value: Int) {
    val computedNext: Node?
        get() = next            // 커스텀 게터
}

fun traverse(n: Node) {
    if (n.next != null) {
        println(n.next.value)          // OK — next는 백킹 필드 val → 스마트 캐스트됨
    }
    if (n.computedNext != null) {
        // println(n.computedNext.value)  // 컴파일 에러: smart cast impossible
        //   (커스텀 게터라 매 접근마다 다를 수 있음 — 값을 지역 변수로 받아야 함)
    }
}
```

### 4.3 초기화식과 프로퍼티 — 백킹 필드는 생성자에서 채워진다

저장 프로퍼티의 초기화식(`= ...`)은 백킹 필드의 초기값을 정하며, 이 초기화는 [[21 - 클래스와 생성자]]에서 본 대로 **생성자 실행 시점에 선언 순서대로** 이뤄진다. 초기화식은 백킹 필드에 직접 값을 넣으며, 이때는 세터를 거치지 않는다.

```kotlin
class Config {
    var level: Int = 3            // 초기화: 백킹 필드에 3을 직접 저장(세터 안 거침)
        set(value) {
            println("세터 호출: $value")
            field = value
        }
}

fun main() {
    val c = Config()             // 생성 시 "세터 호출" 출력 안 됨 — 초기화는 세터 우회
    c.level = 5                  // => 세터 호출: 5   (여기서부터 세터 경유)
}
```

이 점은 미묘하지만 중요하다. 초기화식은 세터의 검증 로직을 통과하지 않는다. 그러므로 세터에 `require(value >= 0)` 같은 불변식을 걸었더라도 초기값이 그 불변식을 만족하는지는 컴파일러가 자동으로 챙겨 주지 않는다. 초기값도 유효해야 한다면 초기값 자체를 유효하게 적어야 한다.

계산 프로퍼티(백킹 필드 없음)에는 초기화식을 붙일 수 없다. 저장할 곳이 없는데 무엇을 초기화하겠는가.

```kotlin
class Bad {
    val area: Double = 0.0        // 초기화식 있음 → 백킹 필드 생김
        get() = 3.14              // …그런데 게터가 field를 안 쓰니 초기값 0.0은 죽은 값
    // 컴파일은 되지만 초기값이 무의미 — 게터가 항상 3.14 반환
}
```

위 코드는 컴파일되지만 `= 0.0`은 아무 의미가 없다(게터가 `field`를 안 읽으니 저장된 0.0은 영원히 안 쓰인다). 계산 프로퍼티라면 초기화식을 아예 빼는 게 옳다.

## 5. 접근자의 가시성과 한정자

### 5.1 세터만 좁히기 — `private set`의 관용구

프로퍼티의 게터와 세터는 서로 다른 가시성을 가질 수 있다. 실무에서 압도적으로 흔한 형태는 **"밖에서는 읽되 못 쓰게" — 게터는 public, 세터만 private**로 두는 것이다.

```kotlin
class Counter {
    var count: Int = 0
        private set              // 게터는 public, 세터는 private

    fun increment() {
        count++                  // 클래스 내부라 세터 접근 가능
    }
}

fun main() {
    val c = Counter()
    c.increment()
    println(c.count)             // => 1   읽기는 OK (게터 public)
    // c.count = 100             // 컴파일 에러: setter is private (밖에서 쓰기 금지)
}
```

이것은 [[26 - 가시성 한정자]]와 결합해 캡슐화를 표현하는 정석 패턴이다. `var count: Int = 0; private set`은 "값은 공개하지만 변경 경로는 클래스가 독점한다"는 계약을 한 줄로 못박는다. 자바에서 같은 걸 하려면 private 필드 + public 게터만 + 세터 없음으로 손수 짜야 하는데, 코틀린은 `private set` 한 마디로 끝낸다.

세터에 본문 없이 가시성만 줄 수도 있고(`private set`), 본문과 함께 줄 수도 있다.

```kotlin
class Registry {
    var lastUpdated: Long = 0L
        private set(value) {          // 가시성 + 본문
            field = maxOf(value, field)   // 시간은 되감기지 않음
        }
}
```

### 5.2 가시성 규칙 — 게터는 왜 못 좁히는가

접근자 가시성에는 명확한 비대칭 규칙이 있다.

> **명세 정밀**: 게터의 가시성은 **반드시 프로퍼티 자신의 가시성과 같아야 한다**. 게터에는 별도 가시성 한정자를 붙일 수 없다. 오직 세터만 프로퍼티보다 **같거나 더 좁은** 가시성을 가질 수 있다.

```kotlin
class Example {
    var a: Int = 0
        // private get() = field    // 컴파일 에러: getter visibility must match property

    var b: Int = 0
        private set                  // OK: 세터를 더 좁게

    public var c: Int = 0
        // internal set             // OK: public 프로퍼티에 internal 세터도 가능
}
```

왜 이런 비대칭인가? 프로퍼티의 "가시성"은 곧 "어디서 이 프로퍼티를 읽을 수 있는가"를 뜻하고, 읽기는 게터로 이뤄진다. 따라서 프로퍼티 가시성과 게터 가시성은 같은 개념이며 둘을 어긋나게 두면 모순이다("프로퍼티는 public인데 못 읽는다"?). 반면 세터는 "쓸 수 있는 범위"라는 독립적 축이므로 더 좁힐 수 있다. 읽기 범위 안에 쓰기 범위가 포함되는 구조 — 읽을 수 있는 사람 중 일부만 쓸 수 있다 — 만 논리적으로 성립한다.

### 5.3 인라인 접근자와 애노테이션 타깃

접근자는 개별적으로 `inline`이 될 수 있다. 백킹 필드가 없는 프로퍼티(계산 프로퍼티)는 프로퍼티 전체를 `inline`으로 표시할 수도 있다. 인라인의 의미론은 [[15 - 인라인 함수와 reified]]가 소유하지만, 요지는 접근자 호출 비용(특히 람다를 받는 접근자)을 없앨 수 있다는 것이다.

```kotlin
class Wrapper(val list: List<Int>) {
    val firstOrZero: Int
        inline get() = list.firstOrNull() ?: 0    // 접근자 인라인화
}
```

또 프로퍼티에 애노테이션을 붙일 때, 그 애노테이션이 게터·세터·백킹 필드·파라미터 중 어디에 붙어야 하는지를 **사용지점 타깃(use-site target)** 으로 지정할 수 있다. 이는 [[44 - 애노테이션과 리플렉션]]이 소유하지만, 프로퍼티가 여러 요소(프로퍼티 자체, 게터, 세터, 필드)로 컴파일되기 때문에 이런 타깃이 필요하다는 사실 자체가 "프로퍼티는 단일 필드가 아니다"를 다시 증언한다.

```kotlin
class Bean {
    @get:JvmName("fetchName")     // 게터에만 붙는 애노테이션
    @field:Volatile               // 백킹 필드에만 붙는 애노테이션
    var name: String = ""
}
```

`@get:`, `@set:`, `@field:`, `@param:` 같은 타깃이 존재한다는 것은, 하나의 프로퍼티 선언이 게터·세터·필드라는 서로 다른 대상들로 흩어져 컴파일된다는 물리적 사실을 반영한다.

## 6. 백킹 프로퍼티 패턴 — 노출과 저장을 분리하다

### 6.1 문제: 밖에는 읽기 전용, 안에서는 가변으로 다루고 싶다

가장 흔한 실무 요구를 보자. 클래스가 리스트를 관리하는데, **밖에서는 읽기만 하게 하되 안에서는 자유롭게 추가·삭제**하고 싶다. `private set`은 참조 재대입만 막지 리스트 내용 변경은 못 막는다. 노출 타입 자체를 좁혀야 한다.

순진한 시도는 실패한다.

```kotlin
class TaskListNaive {
    val tasks: List<String> = mutableListOf()   // 읽기전용 타입으로 노출
    // 문제: 이 클래스 자신도 tasks에 add를 못 함 (List엔 add가 없음)
}
```

`List`로 노출하면 밖에서는 안전하지만, 정작 클래스 자신도 `add`를 쓸 수 없다(게터 반환 타입이 `List`라 가변 메서드가 안 보인다). 여기서 **백킹 프로퍼티 패턴**이 등장한다. 실제 가변 저장은 private 프로퍼티에 두고, public 프로퍼티는 그 private 프로퍼티를 읽기전용 타입으로 노출하는 계산 프로퍼티(또는 게터)로 만든다.

```kotlin
class TaskList {
    private val _tasks: MutableList<String> = mutableListOf()   // 실제 저장(가변)

    val tasks: List<String>            // 노출(읽기전용) — 백킹 필드 없음
        get() = _tasks

    fun add(task: String) {
        _tasks.add(task)               // 내부에서는 가변으로 자유롭게
    }
}

fun main() {
    val list = TaskList()
    list.add("write chapter")
    println(list.tasks)                // => [write chapter]   읽기 OK
    // list.tasks.add("hack")          // 컴파일 에러: List엔 add 없음 (밖에선 못 바꿈)
}
```

`_tasks`(밑줄 접두사가 관례)는 진짜 저장소이고 `MutableList` 타입이라 내부에서 마음대로 조작한다. `tasks`는 `_tasks`를 `List`로 좁혀 내보내는 게터일 뿐 백킹 필드가 없다(`field`를 안 쓰고 `_tasks`만 읽는다). 밖에서 `list.tasks`로 얻는 참조는 정적 타입이 `List`라 가변 메서드가 보이지 않는다.

> **명세 정밀 (M26/M27 연결)**: 이 패턴이 제공하는 안전은 **정적 타입 수준의 캡슐화**다. `list.tasks`가 반환하는 실제 객체는 여전히 `_tasks`와 동일한 가변 `ArrayList`다. 밖에서 그것을 `(list.tasks as MutableList).add(...)`로 캐스팅해 변경하면 뚫린다. 즉 이것은 "읽기 전용 참조"이지 "불변 컬렉션"이 아니다([[38 - 컬렉션 - 읽기 전용과 가변]]의 M26/M27). 진짜 방어가 필요하면 게터에서 `_tasks.toList()`로 방어적 복사를 반환해야 한다(대신 매 접근마다 복사 비용).

### 6.2 백킹 프로퍼티로 캐싱·지연 초기화 흉내 내기

백킹 프로퍼티는 "계산 결과를 캐싱하되 노출은 계산 프로퍼티처럼" 하고 싶을 때도 쓴다. private 저장 프로퍼티에 nullable로 캐시를 두고, public 게터가 없으면 계산하고 있으면 재사용한다.

```kotlin
class Report(val rawData: List<Int>) {
    private var _summary: String? = null      // 캐시 저장소

    val summary: String
        get() {
            if (_summary == null) {
                _summary = expensiveCompute()  // 최초 1회만 계산
            }
            return _summary!!
        }

    private fun expensiveCompute(): String =
        "합계=${rawData.sum()}, 개수=${rawData.size}"
}
```

이 수동 캐싱은 스레드 안전하지 않고 장황하다. 코틀린은 정확히 이 패턴을 위해 `by lazy` 위임을 제공하므로, 실전에서는 손으로 백킹 프로퍼티를 짜기보다 [[23 - 위임 프로퍼티]]의 `val summary by lazy { expensiveCompute() }`를 쓰는 게 낫다. 위임 프로퍼티는 이 절의 수동 패턴을 언어 차원에서 일반화한 것이며, 위임 객체가 백킹 필드를 대체한다.

### 6.3 명명 관례와 왜 하필 밑줄인가

백킹 프로퍼티의 밑줄 접두사(`_tasks`, `_summary`)는 코틀린 코딩 컨벤션이 권장하는 관례다. 이유는 두 가지다. 첫째, public 프로퍼티(`tasks`)와 이름이 충돌하면 안 되므로 다른 이름이 필요하다. 둘째, 밑줄 접두사는 "이건 내부 저장소이니 직접 만지지 말라"는 신호이며, private 저장소를 게터에서 참조할 때 `this.` 없이 바로 쓸 수 있어 간결하다.

| 요소 | 이름 | 타입 | 가시성 | 역할 |
|---|---|---|---|---|
| 저장 프로퍼티 | `_tasks` | `MutableList<T>` | `private` | 실제 가변 저장 |
| 노출 프로퍼티 | `tasks` | `List<T>` | `public` | 읽기전용 뷰 |

이 분리는 자바에서 "private 가변 필드 + public 게터가 `Collections.unmodifiableList(field)` 반환"으로 손수 짜던 것을 코틀린이 타입 시스템(읽기전용 인터페이스)으로 우아하게 표현한 결과다.

## 7. JVM 백엔드에서의 컴파일 형태

> 이 절의 구체적 산출물(메서드 이름, `@JvmField` 효과 등)은 **JVM 백엔드에서**의 이야기다. Kotlin/Native, JS, Wasm 백엔드는 프로퍼티를 각 타깃 방식으로 실현하며 세부는 다르다. 개념(접근자 추상)은 모든 타깃에 공통이지만, 아래 `getX`/`setX` 같은 매핑은 JVM 한정이다.

### 7.1 프로퍼티는 `getX()`/`setX()` + private 필드로 번역된다

JVM 백엔드에서 프로퍼티 하나는 대체로 다음으로 컴파일된다: 백킹 필드가 있으면 **private 필드 하나**, 그리고 **public `getX()` 메서드**(var면 `setX()`도). 이 덕분에 자바 코드는 코틀린 프로퍼티를 익숙한 게터/세터로 호출한다.

```kotlin
// Kotlin
class Circle {
    var radius: Double = 1.0
    val area: Double get() = Math.PI * radius * radius
}
```

위는 JVM에서 개념적으로 다음 자바에 대응한다.

```java
// JVM 바이트코드에 대응하는 개념적 Java
public final class Circle {
    private double radius = 1.0;         // 백킹 필드(있음)

    public final double getRadius() { return this.radius; }
    public final void setRadius(double v) { this.radius = v; }

    // area는 백킹 필드 없음 — 게터 메서드만 존재
    public final double getArea() { return Math.PI * radius * radius; }
}
```

`radius`는 백킹 필드가 있으니 private 필드 + 게터 + 세터로, `area`는 백킹 필드가 없으니 게터 메서드만으로 번역된다. 자바에서 이 클래스를 쓰면:

```java
Circle c = new Circle();
c.setRadius(5.0);
double a = c.getArea();     // Kotlin의 c.area는 Java에선 c.getArea()
```

**이름 규칙의 예외 — `is`로 시작하는 프로퍼티**: 프로퍼티 이름이 `is`로 시작하고 타입이 `Boolean`이면, 게터 이름에 `get` 접두사를 붙이지 않고 이름을 그대로 쓰며(`isEmpty()`), 세터는 `is`를 `set`으로 바꾼다(`setEmpty()`).

```kotlin
class Box {
    var isEmpty: Boolean = true    // JVM: isEmpty() 게터, setEmpty(boolean) 세터
}
```

이 규칙은 자바 빈 관례와 맞추기 위한 것이며, 역방향으로도 작동한다: 자바 클래스의 `isFoo()`/`getFoo()` 게터는 코틀린에서 프로퍼티 `foo`/`isFoo`로 보인다([[45 - Java 상호운용]]).

### 7.2 `@JvmField` — 접근자를 없애고 필드를 직접 노출

가끔 우리는 게터/세터의 오버헤드나 상용구를 원치 않고, 자바 쪽에 순수한 **public 필드**를 노출하고 싶다(예: 자바 라이브러리가 리플렉션으로 필드를 읽는 경우, 또는 성능이 극도로 민감한 경우). 이때 `@JvmField`를 붙이면 컴파일러가 게터/세터를 생성하지 않고 백킹 필드를 프로퍼티와 같은 가시성의 필드로 직접 노출한다.

```kotlin
class Point {
    @JvmField var x: Int = 0    // JVM: public int x; (게터/세터 없음)
    @JvmField var y: Int = 0
}
```

```java
// Java에서
Point p = new Point();
p.x = 3;         // 필드 직접 접근 (getX/setX 아님)
p.y = 4;
```

`@JvmField`에는 제약이 있다. 대략 다음의 프로퍼티에는 붙일 수 없다: 커스텀 게터/세터가 있는 프로퍼티, `open`/`override`/`const` 프로퍼티, 위임 프로퍼티, 인터페이스 안의 프로퍼티. 요컨대 "접근자로서의 개성이 있거나 상태를 못 갖는" 프로퍼티에는 필드 직접 노출이 논리적으로 안 맞기 때문이다.

> **성능 주의**: 코틀린 안에서 코틀린 프로퍼티끼리의 접근은 대개 게터/세터를 거치지만, JIT 컴파일러가 단순 접근자를 인라인해 실질적으로 필드 접근과 같은 비용으로 만든다. 따라서 성능만을 이유로 `@JvmField`를 남발할 필요는 거의 없다. `@JvmField`의 진짜 용도는 자바 상호운용(필드 직접 노출을 기대하는 API) 쪽이다.

### 7.3 `const`, 컴패니언, `lateinit`의 컴파일 형태

세 가지 특수 프로퍼티의 JVM 표현을 정리하자. 이들의 개념적 소유는 다른 장이지만(11장·28장·11장), 컴파일 형태를 여기서 함께 보면 프로퍼티↔필드 매핑의 전체 그림이 완성된다.

- **`const val`** ([[11 - 변수와 초기화 - val과 const와 lateinit]], M36): 컴파일 타임 상수. JVM에서 `public static final` 필드로 나오지만, **사용처는 값이 인라인**된다(호출부 바이트코드에 상수값이 직접 박힌다). 그래서 게터도 없다. `const`는 원시 타입/`String`, 최상위/`object`/`companion` 안, 리터럴 초기화만 허용된다.

- **`lateinit var`** ([[11 - 변수와 초기화 - val과 const와 lateinit]], M9): 비-널 프로퍼티의 초기화 지연. JVM에서 백킹 필드는 `null`로 시작하고(초기화 전), 게터가 접근 시 null이면 `UninitializedPropertyAccessException`을 던진다. `lateinit`은 백킹 필드가 반드시 있어야 하므로 커스텀 접근자를 못 가진다. `::prop.isInitialized`로 초기화 여부를 검사한다.

```kotlin
class Service {
    lateinit var connection: String       // 백킹 필드는 null로 시작

    fun connect() { connection = "opened" }
    fun status(): String =
        if (::connection.isInitialized) connection else "미연결"
}

fun main() {
    val s = Service()
    println(s.status())        // => 미연결   (아직 미초기화 — 예외 안 남)
    // println(s.connection)   // => UninitializedPropertyAccessException
    s.connect()
    println(s.connection)      // => opened
}
```

- **`companion object`의 프로퍼티** ([[28 - object와 companion - 싱글턴과 동반 객체]], M25): 동반 객체의 프로퍼티는 그 동반 객체 인스턴스의 필드로 저장되고, 바깥에서 `Outer.prop`으로 접근하면 실제로는 동반 객체 인스턴스의 게터를 호출한다. 진짜 자바 `static` 필드가 되려면 `@JvmStatic`이나 `@JvmField`가 필요하다(M25).

### 7.4 코틀린에서 자바 필드에 접근하기

역방향도 있다. 자바 클래스는 순수 public 필드를 노출하기도 하는데, 코틀린에서 그 필드는 프로퍼티처럼 보인다. 자바 필드에 대응하는 게터/세터가 자바 쪽에 없으면, 코틀린은 그 필드를 이름으로 직접 읽고 쓸 수 있는 프로퍼티(이른바 synthetic property)처럼 취급한다. 자바의 `getFoo()`/`setFoo()` 게터 쌍 역시 코틀린에서는 프로퍼티 `foo`로 나타난다. 이 매핑의 세부와 함정(플랫폼 타입, 이름 충돌)은 [[45 - Java 상호운용]]이 소유한다.

```text
Kotlin 프로퍼티 → JVM 산출물 요약
┌──────────────────────────┬────────────────────────────────────┐
│ 프로퍼티 형태            │ JVM 백엔드 산출물                    │
├──────────────────────────┼────────────────────────────────────┤
│ var x (백킹 필드 있음)    │ private field + getX() + setX()      │
│ val x (백킹 필드 있음)    │ private field + getX()               │
│ val x (계산, 필드 없음)   │ getX()만                             │
│ var isX: Boolean          │ private field + isX() + setX()       │
│ @JvmField var x           │ public field x (접근자 없음)         │
│ const val X               │ public static final + 사용처 인라인  │
│ lateinit var x            │ 비-private field(null 시작) + 접근자 │
└──────────────────────────┴────────────────────────────────────┘
```

## 8. 인터페이스·추상 프로퍼티 — 상태 없는 접근자 선언 (M37 참조)

### 8.1 인터페이스 프로퍼티에는 백킹 필드가 없다

프로퍼티를 접근자로 보는 관점이 가장 극적으로 갚아지는 곳이 인터페이스다. 인터페이스는 **상태(저장)를 가질 수 없다** — 인스턴스 필드를 못 가진다. 그렇다면 인터페이스가 프로퍼티를 선언할 수 있다는 사실은 오직 "프로퍼티 = 접근자"일 때만 말이 된다. 인터페이스의 프로퍼티는 **게터/세터라는 계약(추상 메서드)의 선언**일 뿐, 그 뒤에 저장 슬롯은 없다.

```kotlin
interface Named {
    val name: String          // 추상 프로퍼티 — 게터 계약만, 백킹 필드 불가
    // val id: Int = 0        // 컴파일 에러: 인터페이스 프로퍼티엔 백킹 필드가 없어 초기화 불가
}
```

`val id: Int = 0`이 금지되는 이유가 정확히 M37이다. 초기화식 `= 0`은 백킹 필드를 요구하는데, 인터페이스는 백킹 필드를 못 가진다. 그래서 인터페이스 프로퍼티는 초기화식도, `field`를 참조하는 접근자도 가질 수 없다. 오직 추상 선언이거나, `field`를 안 쓰는 계산 게터만 가능하다.

```kotlin
interface Shape {
    val area: Double                     // 추상 게터 계약
    val name: String
        get() = "shape"                  // 기본 구현 OK — field 안 씀(계산)
    // val cached: Int = 0               // 에러 — 저장 불가
}

class Square(val side: Double) : Shape {
    override val area: Double
        get() = side * side              // 구현 클래스가 게터를 채움
    override val name: String = "square" // 구현 클래스는 백킹 필드로 상태 저장 가능
}
```

인터페이스는 `name`에 대한 기본 게터를 줄 수 있지만 그것은 `field`를 안 쓰는 계산이어야 한다. 상태(`= 0`으로 저장)는 오직 구현 클래스에서만 가질 수 있다. 이것이 **M37**("코틀린 인터페이스는 상태를 가질 수 있다"는 오해)에 대한 이 장에서의 참조 교정이며, 정본 해부는 [[25 - 인터페이스]]가 소유한다.

### 8.2 추상 프로퍼티와 오버라이드

`abstract` 프로퍼티(추상 클래스 안)도 인터페이스 프로퍼티와 같은 원리다. 본문 없는 접근자 선언이며 백킹 필드가 없다. 하위 클래스가 오버라이드하며 구현(계산 게터 또는 저장 프로퍼티)을 채운다.

```kotlin
abstract class Animal {
    abstract val legs: Int               // 추상 — 백킹 필드 없음

    val description: String
        get() = "다리 $legs 개의 동물"     // legs는 게터로 접근
}

class Dog : Animal() {
    override val legs: Int = 4            // 저장 프로퍼티로 구현(백킹 필드 있음)
}

class Snake : Animal() {
    override val legs: Int
        get() = 0                        // 계산 프로퍼티로 구현(백킹 필드 없음)
}
```

같은 추상 프로퍼티 `legs`를 `Dog`는 저장으로, `Snake`는 계산으로 오버라이드한다. 상위 타입 관점에서는 둘 다 그냥 "게터 계약을 만족한 것"이라 구별되지 않는다 — 균일 접근 원칙이 상속 축에서도 관철된다.

프로퍼티 오버라이드에는 방향 규칙이 있다. **`val`을 `var`로 오버라이드할 수 있지만(게터에 세터를 더하는 것) 그 반대는 안 된다.** `var`은 게터+세터 계약인데 `val`로 오버라이드하면 세터가 사라져 상위 계약을 어기기 때문이다.

```kotlin
open class Base {
    open val x: Int = 0        // 게터만
    open var y: Int = 0        // 게터+세터
}
class Derived : Base() {
    override var x: Int = 10   // OK: val을 var로 (세터 추가는 계약 강화)
    // override val y: Int     // 에러: var를 val로 (세터 제거는 계약 위반)
}
```

이 오버라이드 규칙과 초기화 순서의 얽힘(상위 생성자에서 오버라이드된 프로퍼티/게터를 부르는 함정)은 [[24 - 상속과 오버라이딩과 초기화 순서]]가 소유한다(M47). 요지만 미리 말하면: 상위 클래스 생성자가 실행되는 시점에 하위 클래스의 프로퍼티 초기화식은 *아직 실행되지 않았으므로*, 상위 생성자에서 오버라이드된 프로퍼티를 읽으면 하위의 백킹 필드가 기본값(예: 0, null)인 상태를 보게 된다.

### 8.3 위임 프로퍼티로 가는 다리

지금까지 우리는 프로퍼티의 값을 백킹 필드에 저장하거나(저장 프로퍼티), 매번 계산하거나(계산 프로퍼티), 다른 private 프로퍼티에 저장했다(백킹 프로퍼티 패턴). 이 셋의 공통점은 "저장·계산 로직을 접근자 안에 직접 적었다"는 것이다.

코틀린은 여기서 한 걸음 더 나아가, 접근자의 구현 자체를 **다른 객체(위임 객체)에게 통째로 넘기는** 문법을 제공한다. `val x: T by delegate`라고 쓰면, `x`를 읽을 때 `delegate.getValue(...)`가, 쓸 때 `delegate.setValue(...)`가 호출된다. 이때 백킹 필드는 값이 아니라 **위임 객체 인스턴스**를 담는다. `by lazy`(최초 접근 시 계산해 캐싱), `Delegates.observable`(변경 관찰), map 기반 위임 등이 표준으로 제공된다.

```kotlin
class LazyExample {
    val heavy: String by lazy {          // 백킹 필드엔 Lazy 객체가 저장됨
        println("계산 중…")
        "무거운 결과"
    }
}

fun main() {
    val e = LazyExample()
    println("생성됨")        // => 생성됨   (아직 계산 안 함)
    println(e.heavy)         // => 계산 중…  => 무거운 결과   (최초 접근 시 계산)
    println(e.heavy)         // => 무거운 결과   (캐시됨, 재계산 안 함)
}
```

이 위임 메커니즘 — `getValue`/`setValue` 관례([[19 - 연산자 오버로딩과 관례]]), `provideDelegate`, `KProperty`, 컴파일 형태 — 는 [[23 - 위임 프로퍼티]]가 온전히 소유한다. 이 장에서 기억할 것은 하나다: 위임 프로퍼티는 "프로퍼티는 접근자 추상"이라는 이 장의 명제를 극한까지 밀어붙인 것이다. 접근자가 하는 일을 외부 객체로 뽑아낼 수 있다는 것 자체가, 프로퍼티가 필드가 아니라 *동작(behavior)의 이름*임을 최종적으로 증명한다.

---

이제 도입부의 질문들을 한 줄기로 회수하자. 코틀린 프로퍼티가 필드와 다른 이유는 그것이 저장 슬롯이 아니라 게터/세터라는 접근자 함수의 이름이기 때문이고(1절), `field`라는 예약어는 그 접근자가 값을 저장할 곳을 필요로 할 때만 백킹 필드를 존재하게 만드는 스위치다(2절). 커스텀 게터를 붙이면 그 게터가 `field`를 참조하는지 여부에 따라 저장 슬롯이 남거나 사라진다(3절). `val` 프로퍼티가 매번 다른 값을 낼 수 있는 것은 `val`이 세터의 부재일 뿐 게터 결과의 안정성 보증이 아니기 때문이며, 바로 그래서 커스텀 게터 `val`은 스마트 캐스트가 안 된다(4절). 계산 프로퍼티와 저장 프로퍼티의 경계는 컴파일러에게 "`field` 참조 여부"라는 단 하나의 기준으로 보이고, 그 경계 위에서 백킹 프로퍼티 패턴(6절)과 위임(8.3절)이 자라난다. JVM 백엔드는 이 모든 것을 `getX`/`setX`/private 필드로 번역하되, `@JvmField`로 필드를 직접 노출하거나 `is` 프로퍼티로 이름을 바꾸는 예외를 둔다(7절). 그리고 인터페이스가 상태 없이 프로퍼티를 선언할 수 있다는 사실 자체가(8절), "프로퍼티는 필드다"라는 문장이 왜 편의상은 통하지만 원리상은 거짓인지를 마지막으로 못박는다. 프로퍼티는 필드가 아니라, 필드를 가질 수도 있는 접근자 추상이다.

## 핵심 요약

- **코틀린 프로퍼티는 필드가 아니라 게터/세터라는 접근자 추상이다.** `obj.x` 읽기는 게터 호출, `obj.x = v` 쓰기는 세터 호출이며, 저장 슬롯(백킹 필드)은 접근자가 필요로 할 때만 딸려 나오는 선택적 구현이다. "프로퍼티 = 필드"는 편의상 통하지만 원리상 거짓이다 (M35).
- **백킹 필드는 `field`를 참조할 때만 생성된다.** 기본 접근자를 하나라도 쓰거나 커스텀 접근자가 `field`를 명시적으로 참조하면 필드가 생기고, 모든 접근자를 커스텀으로 짜고 아무도 `field`를 안 쓰면 저장 슬롯은 존재하지 않는다(순수 계산 프로퍼티).
- **`field`는 접근자 본문 안에서만 의미를 갖는 소프트 키워드이며 오직 자기 자신의 백킹 필드만 가리킨다.** 접근자 안에서 `field` 대신 프로퍼티 이름을 쓰면 접근자가 자기를 무한 호출해 `StackOverflowError`가 난다.
- **계산 프로퍼티는 저장 없이 접근할 때마다 게터 본문을 실행한다.** 메모리에 자리를 차지하지 않지만 매 접근이 재계산이므로, 무거운 계산을 게터에 숨기면 "싸게 읽힌다"는 기대를 배신한다.
- **`val`은 "세터 없음", `var`은 "게터+세터"일 뿐이다.** `val`은 재대입(세터)을 막을 뿐 게터가 항상 같은 값을 반환한다는 보증이 아니며, 그래서 커스텀 게터를 가진 `val`은 매번 다른 값을 낼 수 있고 스마트 캐스트되지 않는다 (M3, M13 참조).
- **초기화식은 세터를 우회해 백킹 필드에 직접 값을 넣는다.** 세터에 건 검증 로직은 초기값에 적용되지 않으므로 초기값 자체의 유효성은 따로 챙겨야 한다.
- **게터 가시성은 프로퍼티와 반드시 같고, 세터만 더 좁힐 수 있다.** `var count: Int = 0; private set`은 "읽기는 공개, 쓰기는 클래스 독점"이라는 캡슐화를 한 줄로 표현한다.
- **백킹 프로퍼티 패턴(`private val _items: MutableList` + `val items: List get() = _items`)은 내부 가변·외부 읽기전용을 정적 타입으로 분리한다.** 단 이는 읽기전용 뷰이지 불변 컬렉션이 아니며 캐스팅으로 뚫릴 수 있다 (M26/M27 참조).
- **JVM 백엔드에서 프로퍼티는 private 필드 + `getX()`/`setX()`로 컴파일된다.** `is`로 시작하는 `Boolean` 프로퍼티는 `isX()`/`setX()`로, `@JvmField`는 접근자 없이 public 필드를 직접 노출한다(JVM 한정).
- **인터페이스·추상 프로퍼티는 백킹 필드를 못 가지므로 초기화식도 `field` 참조도 불가하다.** 상태 없는 게터/세터 계약일 뿐이며 상태는 구현 클래스만 가질 수 있다 — "프로퍼티 = 접근자"라야만 성립하는 사실이다 (M37 참조).
- **`val`을 `var`로 오버라이드할 수 있으나 그 반대는 안 된다.** 세터 추가는 계약 강화지만 세터 제거는 상위 계약 위반이기 때문이다.
- **위임 프로퍼티(`by`)는 접근자 구현을 외부 객체로 통째로 뽑아낸 것이며, 프로퍼티가 필드가 아니라 동작의 이름임을 최종 증명한다.** 이때 백킹 필드는 값이 아니라 위임 객체 인스턴스를 담는다.
