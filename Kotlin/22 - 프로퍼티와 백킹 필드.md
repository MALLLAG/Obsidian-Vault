[[21 - 클래스와 생성자]]에서는 `class Circle(val radius: Double)`처럼 주 생성자 괄호 안에 `val`/`var`를 적으면 "프로퍼티가 선언된다"고 배웠다. 하지만 그때 실제로 무엇이 만들어지는지는 자세히 설명하지 않았다. 자바에 익숙한 사람은 이 코드를 보고 별생각 없이 "필드(field)가 하나 생겼다"고 읽는다.

이 장에서는 그런 이해가 왜 틀렸는지 설명한다. 코틀린에서 `val radius`라고 쓰면 언어가 우선 만드는 것은 저장 공간(필드)이 아니라 **접근자**(accessor), 즉 게터와 세터라는 한 쌍의 함수이다. 저장 공간은 그 접근자를 뒷받침하기 위해 *필요할 때만* 함께 만들어진다. 이 순서를 제대로 이해하는 것이 이 장의 핵심이며, "코틀린 프로퍼티는 필드다"라는 흔한 오해를 바로잡는 출발점이다.

이 장에서는 일반 프로퍼티의 접근자, 백킹 필드 `field`, 커스텀 게터와 세터, 계산 프로퍼티, 백킹 프로퍼티 패턴, JVM 컴파일 형태를 다룬다.

저장과 계산 로직을 다른 객체에 맡기는 `by` 문법인 위임 프로퍼티는 [[23 - 위임 프로퍼티]]에서, 인터페이스 프로퍼티는 [[25 - 인터페이스]]에서, 상속과 초기화 순서가 얽히는 함정은 [[24 - 상속과 오버라이딩과 초기화 순서]]에서, 확장 프로퍼티는 [[35 - 확장 함수와 프로퍼티]]에서 자세히 설명한다.

`val`, `var`, `const`, `lateinit`의 차이는 [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 이미 다루었으므로, 이 장은 그중 *멤버 프로퍼티*에 초점을 맞춘다.

## 1. 프로퍼티라는 추상: 필드가 아니라 접근자

### 1.1 자바의 필드와 코틀린의 프로퍼티는 다른 층위다

자바에서는 클래스의 상태를 **필드(field)** 로 저장하고, 캡슐화를 위해 `getX()`/`setX()` 메서드를 직접 작성해 감싼다. 필드는 "저장 슬롯"이고 게터와 세터는 "그 슬롯을 감싼 함수"이며, 두 가지는 문법적으로 완전히 별개이다.

```java
// Java
public class Circle {
    private double radius;              // 필드: 저장 슬롯
    public double getRadius() {         // 손으로 짠 게터
        return radius;
    }
    public void setRadius(double r) {   // 손으로 짠 세터
        this.radius = r;
    }
}
```

코틀린은 이 구조를 반대로 놓는다. 코틀린에서 클래스 멤버로 선언하는 기본 단위는 **프로퍼티(property)** 이고, 프로퍼티의 실체는 "이름으로 접근하는 값" 뒤에 있는 **게터(`var`라면 세터도)라는 접근자 함수**이다. 저장 슬롯은 프로퍼티의 본질이 아니다. 접근자가 값을 어딘가에 담아야 할 때 컴파일러가 뒤에서 제공하는 보조 장치일 뿐이다.

```kotlin
class Circle {
    var radius: Double = 0.0    // 프로퍼티 하나 — 게터+세터가 자동 합성됨
}

fun main() {
    val c = Circle()
    c.radius = 5.0              // 문법은 필드 대입처럼 보이지만 → 세터 호출
    println(c.radius)           // => 5.0   문법은 필드 읽기처럼 보이지만 → 게터 호출
}
```

`c.radius = 5.0`은 필드에 직접 값을 쓰는 것처럼 보이지만, 코틀린에서 이 코드는 `c.setRadius(5.0)`이라는 접근자 호출을 간단히 쓴 문법 설탕이다. `c.radius`를 읽는 것도 `c.getRadius()` 호출이다. 필드처럼 보이는 표기 뒤에 함수 호출이 있다는 것, 즉 겉모습과 실제 동작이 분리되어 있다는 것이 프로퍼티의 핵심이다. 정리하면 코틀린 프로퍼티는 필드가 아니라 *접근자 추상*이며, 필드는 그 추상을 물리적으로 구현하기 위해 선택적으로 생기는 부산물이다.

> [!warning] 흔한 오해
> "코틀린 프로퍼티는 결국 자바 필드에 게터와 세터를 자동으로 붙인 것일 뿐이다"라는 말은 절반만 맞다. 프로퍼티는 필드를 *가질 수도 있고 가지지 않을 수도 있다*. 백킹 필드가 없는 프로퍼티(계산 프로퍼티)에는 저장 슬롯이 아예 없으며, 접근할 때마다 게터 본문이 실행되어 값을 새로 만든다. 프로퍼티를 필드와 같은 것으로 보면 이런 프로퍼티를 전부 놓치게 된다.

### 1.2 프로퍼티 선언의 완전한 문법 형태

코틀린 명세가 정의하는 프로퍼티 선언의 전체 형태는 다음과 같다. 실무에서는 대부분을 생략하지만, 무엇이 생략되는지 알면 프로퍼티의 구조가 분명해진다.

```text
[modifiers] val|var <이름>[: <타입>] [= <초기화식> | by <위임>]
    [get() [ = <식> | { <본문> } ]]
    [set(<파라미터>) [ = <식> | { <본문> } ]]
```

- `val`이면 게터만, `var`이면 게터와 세터를 가질 수 있다.
- 초기화식(`= ...`)이 있으면 그 값을 담을 **백킹 필드**가 생긴다.
- `get()`/`set()`을 명시하지 않으면 컴파일러가 **기본 접근자**를 합성한다. 기본 게터는 `field`를 반환하고, 기본 세터는 `field = value`로 대입한다.

```kotlin
class Account {
    var balance: Long = 0          // 기본 게터/세터 (아래와 동치)
}

// 위 선언은 개념적으로 이것과 같다:
class AccountExplicit {
    var balance: Long = 0
        get() = field              // 기본 게터: 백킹 필드 반환
        set(value) { field = value }   // 기본 세터: 백킹 필드에 대입
}
```

두 선언은 바이트코드 수준에서 동일하다. 코틀린이 제공하는 편의는 "뻔한 접근자 한 쌍을 적지 않아도 된다"는 것이지, "필드를 만들어 준다"는 것이 아니다. 만들어지는 접근자가 마침 필드를 필요로 할 뿐이다.

### 1.3 균일 접근 원칙: 이 설계가 필요한 이유

코틀린은 왜 필드가 아니라 프로퍼티를 기본 단위로 삼았을까? 답은 버트런드 마이어가 정리한 **균일 접근 원칙(Uniform Access Principle)** 에 있다. 이 원칙은 *"클라이언트 코드는 어떤 값이 저장된 것인지 계산된 것인지 구별하지 않고 같은 표기로 접근할 수 있어야 한다"* 는 것이다.

자바에서 처음에 `public double radius;` 필드로 노출했다고 하자. 나중에 "반지름을 읽을 때 로그를 남기자"거나 "지름에서 계산하자"는 요구가 생기면 필드를 메서드로 바꿔야 하고, 그러면 `obj.radius`를 쓰던 호출부가 모두 `obj.getRadius()`로 바뀌어야 한다. 그래서 자바 개발자는 처음부터 방어적으로 모든 필드를 private으로 숨기고 게터와 세터를 작성한다.

코틀린에는 이런 문제가 없다. `radius`를 저장 프로퍼티로 시작했다가 나중에 계산 프로퍼티로 바꿔도 **호출부의 `obj.radius`는 한 글자도 바뀌지 않는다**. 접근 표기가 처음부터 접근자 호출이기 때문이다.

```kotlin
// v1: 저장 프로퍼티
class Circle1(var radius: Double) {
    var diameter: Double = radius * 2      // 저장 — 독립적으로 값을 가짐
}

// v2: 요구가 바뀌어 diameter를 radius에서 파생하도록 변경
class Circle2(var radius: Double) {
    var diameter: Double                   // 이제 계산 프로퍼티 — 백킹 필드 없음
        get() = radius * 2
        set(value) { radius = value / 2 }
}

// 두 버전 모두 호출부는 동일:
fun use(c: Circle2) {
    println(c.diameter)     // 표기 불변
    c.diameter = 20.0       // 표기 불변
}
```

이 원칙이 코틀린 프로퍼티 설계의 중심이다. 프로퍼티는 "저장하는지 계산하는지"를 **구현 세부 사항으로 숨기는 인터페이스**이고, 백킹 필드는 그 인터페이스가 저장 방식을 택했을 때만 나타나는 내부 구현이다. 이 관점을 이해하면 이후의 규칙들이 자연스럽게 따라 나온다.

## 2. 백킹 필드 `field`: 언제 생기고 언제 생기지 않는가

### 2.1 백킹 필드 생성 규칙: "field를 참조하면 생긴다"

백킹 필드(backing field)는 프로퍼티의 값을 담는 실제 저장 슬롯이다. 코틀린 컴파일러가 백킹 필드를 항상 만드는 것은 아니다. **정확한 규칙**은 다음과 같다.

> [!note] 명세 기준
> 다음 중 하나라도 참이면 프로퍼티의 백킹 필드가 생성된다.
> 1. 프로퍼티가 **기본 게터나 기본 세터를 하나 이상** 사용한다(즉 그 접근자를 직접 작성하지 않았다). 기본 접근자는 암묵적으로 `field`를 참조하기 때문이다.
> 2. 커스텀 접근자의 본문이 **`field` 식별자를 명시적으로 참조**한다.
>
> 둘 다 아니라면, 즉 모든 접근자를 직접 작성했고 그중 어느 것도 `field`를 쓰지 않는다면 백킹 필드는 생성되지 않는다. 그런 프로퍼티는 저장 슬롯이 없는 순수 계산 프로퍼티이다.

이 규칙을 표로 정리하면 다음과 같다.

| 선언 형태 | `field` 참조 여부 | 백킹 필드 |
|---|---|---|
| `var x = 0` (기본 접근자) | 기본 접근자가 암묵적으로 참조 | **생성** |
| `val x = f()` (기본 게터) | 기본 게터가 암묵적으로 참조 | **생성** |
| `val x get() = a + b` | 참조하지 않음 | **생성 안 됨** |
| `var x get() = a; set(v){ a = v }` | 참조하지 않음 | **생성 안 됨** |
| `var x get() = field; set(v){ field = v * 2 }` | 참조함 | **생성** |
| `val x: Int` (추상/인터페이스) | 접근자 본문 없음 | **생성 안 됨** |

핵심은 **`field`가 백킹 필드를 존재하게 만드는 스위치**라는 점이다. 접근자 안에서 `field`를 한 번이라도 쓰면 컴파일러는 이 프로퍼티에 저장할 곳이 필요하다고 판단해 필드를 만든다. 반대로 `field`를 전혀 쓰지 않으면 저장할 곳도 없다.

### 2.2 계산 프로퍼티에는 백킹 필드가 없다

`field`를 참조하지 않는 프로퍼티를 **계산 프로퍼티(computed property)** 또는 파생 프로퍼티라고 부른다. 이런 프로퍼티는 값을 어디에도 저장하지 않고, 접근할 때마다 게터 본문을 실행해 값을 그 자리에서 만든다.

```kotlin
class Rectangle(val width: Double, val height: Double) {
    val area: Double                      // 백킹 필드 없음
        get() = width * height            // 매 접근마다 계산

    val isSquare: Boolean
        get() = width == height           // 매 접근마다 계산
}

fun main() {
    val r = Rectangle(3.0, 4.0)
    println(r.area)      // => 12.0   (width*height를 지금 계산)
    println(r.area)      // => 12.0   (또 계산 — 저장된 값이 아니다)
    println(r.isSquare)  // => false
}
```

`area`는 객체의 메모리 레이아웃에서 자리를 차지하지 않는다. `Rectangle` 인스턴스에는 `width`와 `height` 두 필드만 있고, `area`는 `getArea()` 함수로만 존재한다. 이것이 "프로퍼티 ≠ 필드"를 가장 분명하게 보여 주는 예이다. `area`는 온전한 프로퍼티이지만 저장 슬롯은 0바이트이다.

```text
Rectangle 인스턴스의 메모리 레이아웃 (JVM 백엔드, 개념)
┌─────────────────────────────┐
│ 객체 헤더                    │
├─────────────────────────────┤
│ double width   ← 백킹 필드   │
│ double height  ← 백킹 필드   │
└─────────────────────────────┘
   area, isSquare는 여기 없음 — getArea(), getIsSquare() 함수로만 존재
```

> [!caution] 성능 주의
> 계산 프로퍼티는 접근할 때마다 본문을 실행한다. `area`를 루프에서 수백만 번 읽으면 곱셈도 수백만 번 일어난다. 가벼운 계산이면 문제가 없지만, 무거운 계산(예: 리스트 정렬, 정규식 매칭)을 계산 프로퍼티 안에 두면 호출부는 이것을 단순한 값 읽기로 오해하고 성능 문제를 겪게 된다.
>
> 계산이 무겁고 값이 바뀌지 않는다면 저장 프로퍼티로 캐싱하거나, 23장(위임 프로퍼티)의 `by lazy`를 사용해 한 번만 계산하게 하자. 관례상 사람들은 게터가 필드처럼 가볍게 읽힌다고 기대하므로, 이 기대를 깨는 게터는 나쁜 API이다.

### 2.3 `field`는 접근자 안에서만 보이는 소프트 키워드

`field`는 특별한 식별자이다. **프로퍼티 접근자 본문 안에서만** 의미를 가지며, 그 프로퍼티 자신의 백킹 필드를 가리킨다. 접근자 밖에서 `field`는 평범한 이름일 뿐이다. 즉 `field`는 [[03 - 렉시컬 구조와 세미콜론 추론]]에서 다룬 **소프트 키워드**로, 문맥에 따라 예약어가 되기도 하고 보통 식별자가 되기도 한다.

```kotlin
class Temperature {
    var celsius: Double = 0.0
        set(value) {
            field = value.coerceAtLeast(-273.15)   // field = 이 프로퍼티의 백킹 필드
        }

    fun field() = "이건 그냥 메서드 이름"   // 접근자 밖 — field는 평범한 이름
}
```

중요한 제약이 있다. **`field`로는 자기 자신의 백킹 필드에만 접근할 수 있다.** 다른 프로퍼티의 백킹 필드를 `field`로 다룰 방법은 없으며, 다른 프로퍼티에는 이름으로(즉 접근자를 통해) 접근해야 한다. 이렇게 분리되어 있기 때문에 백킹 필드는 프로퍼티만의 내부 구현으로 남는다.

`field`를 쓸 때 항상 함께 등장하는 것이 세터의 파라미터이다. 커스텀 세터의 파라미터는 관례적으로 `value`라고 이름 짓지만 어떤 이름이든 쓸 수 있으며, 새로 대입하려는 값을 담는다. `field = value`는 "백킹 필드에 새 값을 저장한다"는 뜻이고, 기본 세터가 하는 일이 바로 이것이다.

## 3. 커스텀 게터와 세터: 접근자에 로직 넣기

### 3.1 커스텀 게터

커스텀 게터를 쓰면 프로퍼티를 읽을 때 실행할 코드를 직접 정할 수 있다. `get()` 뒤에 단일 식(`= expr`)이나 블록(`{ ... }`)을 둔다.

```kotlin
class Person(val firstName: String, val lastName: String) {
    val fullName: String
        get() = "$firstName $lastName"        // 단일 식 게터, 백킹 필드 없음

    val initials: String
        get() {                                // 블록 게터
            val f = firstName.firstOrNull() ?: ' '
            val l = lastName.firstOrNull() ?: ' '
            return "$f.$l."
        }
}
```

게터의 반환 타입은 프로퍼티 타입과 같아야 한다. 프로퍼티 타입을 명시했다면 게터는 그 타입을 반환해야 하고, 생략했다면 게터 식에서 타입을 추론한다(단, 계산 프로퍼티에서 타입을 추론하려면 게터가 프로퍼티 선언 바로 뒤에 와야 한다).

저장 프로퍼티에도 커스텀 게터를 붙여서 "저장은 하되 읽을 때 가공"하게 만들 수 있다. 이때 `field`를 써야 백킹 필드가 유지된다.

```kotlin
class Counter {
    var count: Int = 0
        get() {
            println("count 읽힘")     // 부수효과(로깅) 삽입
            return field              // field 참조 → 백킹 필드 유지됨
        }
}
```

### 3.2 커스텀 세터와 `value` 파라미터: 검증, 정규화, 불변식

커스텀 세터는 프로퍼티에 값을 대입할 때 실행된다. 세터를 가장 흔하게 쓰는 곳은 **검증(validation)과 정규화(normalization)**, 즉 저장하기 전에 불변식을 강제하는 일이다.

```kotlin
class BankAccount {
    var balance: Long = 0
        set(value) {
            require(value >= 0) { "잔액은 음수가 될 수 없다: $value" }
            field = value             // 검증 통과 시에만 저장
        }

    var ownerName: String = ""
        set(value) {
            field = value.trim()      // 저장 전 정규화(공백 제거)
        }
}

fun main() {
    val acc = BankAccount()
    acc.balance = 1000
    println(acc.balance)              // => 1000
    acc.ownerName = "  Alice  "
    println("[${acc.ownerName}]")     // => [Alice]  (trim됨)
    acc.balance = -5                  // => IllegalArgumentException: 잔액은 음수가 될 수 없다: -5
}
```

세터 파라미터의 타입은 프로퍼티 타입으로 고정된다. 타입을 명시할 수는 있지만 반드시 프로퍼티 타입과 같아야 한다(`var balance: Long`에 `set(value: String)`처럼 다른 타입을 적으면 컴파일 에러가 난다). 어차피 프로퍼티 타입으로 정해져 있으므로 보통은 생략하고 `set(value)`로만 쓴다. 파라미터 이름은 자유롭게 정할 수 있지만 관례는 `value`이다.

세터에서 흥미로운 점은 **게터가 돌려주는 값과 세터가 받는 값이 반드시 대칭일 필요는 없다**는 것이다. 세터가 값을 변형해 저장하면, 게터로 읽을 때 처음 넣은 값과 다른 값이 나올 수 있다.

```kotlin
class CaseInsensitiveTag {
    var value: String = ""
        set(v) { field = v.lowercase() }   // 소문자로 저장

    // getter는 기본 → field 그대로 반환
}

fun main() {
    val t = CaseInsensitiveTag()
    t.value = "HELLO"
    println(t.value)     // => hello   (넣은 값과 다름)
}
```

이런 비대칭은 유용하지만 위험하기도 하다. API 사용자는 대개 넣은 값이 그대로 나오리라고 기대하므로, 세터가 값을 몰래 바꾸면 당황하게 된다. 공백 제거나 대소문자 통일처럼 도메인에서 당연한 정규화일 때만 쓰고, 그렇지 않다면 별도 메서드로 명시하는 편이 낫다.

### 3.3 접근자 안에서 프로퍼티 이름을 쓰면 무한 재귀가 된다

프로퍼티 접근자를 처음 작성하는 사람이 거의 한 번은 겪는 실수가 있다. **접근자 안에서 `field` 대신 프로퍼티 이름을 쓰는 것**이다.

```kotlin
class Broken {
    var x: Int = 0
        get() = x            // 함정! x를 읽으면 getX() 호출 → 다시 get() → 무한 재귀
        set(value) { x = value }   // 함정! x에 대입 → setX() 호출 → 다시 set() → 무한 재귀
}

fun main() {
    val b = Broken()
    println(b.x)             // => StackOverflowError (게터가 자기 자신을 무한 호출)
}
```

`get() = x`에서 `x`는 백킹 필드가 아니라 **프로퍼티 `x`에 대한 접근**이다. 프로퍼티 접근은 곧 게터 호출이므로, 게터가 게터를 부르는 무한 재귀가 된다. 세터도 마찬가지이다. 올바르게 작성하려면 `field`를 써야 한다.

```kotlin
class Fixed {
    var x: Int = 0
        get() = field                 // 백킹 필드 직접 접근 — 재귀 없음
        set(value) { field = value }
}
```

> [!warning] 흔한 오해
> "게터 안의 `x`는 지금 정의하고 있는 이 프로퍼티이니 필드를 뜻할 것이다"라고 생각하기 쉽지만 그렇지 않다. 코틀린에는 "프로퍼티 이름 = 필드" 같은 예외 경로가 없다. 프로퍼티 이름은 *언제나* 접근자 호출로 해석되고, 백킹 필드에 접근하는 유일한 방법은 `field` 예약어이다. 이 규칙에는 예외가 없으며, 이런 일관성이 있기에 균일 접근 원칙(1.3)이 성립한다.

이 함정은 코틀린이 프로퍼티를 접근자로 본다는 사실을 가장 분명하게 보여 준다. `x`가 필드라면 `get() = x`는 필드를 읽는 정상적인 코드였을 것이다. 하지만 `x`는 필드가 아니라 접근자 쌍의 이름이므로, 자기 안에서 자기를 호출하는 재귀가 된다.

## 4. `val`과 `var` 프로퍼티: 사실은 "세터가 있는가"의 차이

### 4.1 `val`은 게터만, `var`는 게터와 세터를 가진다

11장(변수와 초기화)에서는 `val`은 "재대입 불가", `var`는 "재대입 가능"이라고 배웠다. 멤버 프로퍼티에서는 이 구분이 접근자의 차이로 바뀐다. **`val` 프로퍼티는 게터만 가지고, `var` 프로퍼티는 게터와 세터를 가진다.** 그래서 `val` 프로퍼티에는 `set()`을 정의할 수 없다.

```kotlin
class C {
    val readOnly: Int = 10
        // set(v) { ... }   // 컴파일 에러: A 'val'-property cannot have a setter

    var readWrite: Int = 10
        get() = field
        set(v) { field = v }
}
```

"재대입 불가"라는 성질이 세터가 없다는 사실로 구현된다는 점이 중요하다. `val`이 막는 것은 "이 프로퍼티에 대입하는 문법(`obj.readOnly = ...`)"이지, "이 프로퍼티가 가리키는 값의 내부 변경"이 아니다. 11장에서 다룬 "`val`은 재대입을 막을 뿐 불변 객체를 만들지 않는다"는 원칙이 프로퍼티에서도 그대로 적용되는 것이다.

```kotlin
class Basket {
    val items: MutableList<String> = mutableListOf()   // val — 재대입 불가
}

fun main() {
    val b = Basket()
    b.items.add("apple")      // OK — 가리키는 리스트를 변경(세터 호출 아님)
    b.items.add("banana")
    println(b.items)          // => [apple, banana]
    // b.items = mutableListOf()   // 컴파일 에러: val cannot be reassigned (세터 없음)
}
```

`b.items.add(...)`는 세터를 호출하지 않는다. 게터가 돌려준 리스트 객체의 메서드를 부를 뿐이다. `val`이 막는 것은 게터가 돌려주는 참조를 다른 참조로 바꾸는 일(세터)뿐이다.

### 4.2 `val` 프로퍼티도 매번 다른 값을 낼 수 있다

`val`이 "불변"을 뜻한다고 오해하면 다음 코드가 당황스럽게 느껴진다.

```kotlin
import kotlin.random.Random

class Dice {
    val roll: Int                 // val인데…
        get() = Random.nextInt(1, 7)   // 매 접근마다 새 난수
}

fun main() {
    val d = Dice()
    println(d.roll)   // => 4  (예)
    println(d.roll)   // => 1  (또 다름!)
    println(d.roll)   // => 6
}
```

`roll`은 `val`이지만 읽을 때마다 다른 값을 낸다. 이것은 모순이 아니다. `val`은 세터가 없다는 뜻이지, 게터가 항상 같은 값을 반환한다는 뜻이 아니기 때문이다. `val` 프로퍼티는 백킹 필드에 저장된 변하지 않는 값을 낼 수도 있고(저장 프로퍼티), 매번 계산한 값을 낼 수도 있다(계산 프로퍼티). 즉 `val`은 접근자 구조에 대한 제약(세터 없음)이지, 게터 결과가 안정적이라는 보증이 아니다.

> [!note] 명세 기준
> 이런 성질 때문에 **커스텀 게터를 가진 `val` 프로퍼티는 스마트 캐스트되지 않는다**([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]] 참조). 컴파일러가 `if (obj.p != null) { obj.p.foo() }`를 스마트 캐스트하려면 `obj.p`에 두 번 접근했을 때 같은 값이 나온다고 보장할 수 있어야 한다.
>
> 그런데 커스텀 게터는 매번 다른 값을 낼 수 있으므로 이 보장이 성립하지 않는다. 반면 백킹 필드를 가진 `val`(같은 모듈)은 값이 고정되어 있으므로 스마트 캐스트가 허용된다.

```kotlin
class Node(val next: Node?, val value: Int) {
    val computedNext: Node?
        get() = next            // 커스텀 게터
}

fun traverse(n: Node) {
    if (n.next != null) {
        println(n.next.value)          // OK — next는 백킹 필드 val → 스마트 캐스트됨
    }
    if (n.computedNext != null) {
        // println(n.computedNext.value)  // 컴파일 에러: smart cast impossible
        //   (커스텀 게터라 매 접근마다 다를 수 있음 — 값을 지역 변수로 받아야 함)
    }
}
```

### 4.3 초기화식과 프로퍼티: 백킹 필드는 생성자에서 채워진다

저장 프로퍼티의 초기화식(`= ...`)은 백킹 필드의 초기값을 정한다. 21장(클래스와 생성자)에서 본 것처럼 이 초기화는 **생성자가 실행될 때 선언 순서대로** 이루어진다. 초기화식은 백킹 필드에 값을 직접 넣으며, 이때 세터를 거치지 않는다.

```kotlin
class Config {
    var level: Int = 3            // 초기화: 백킹 필드에 3을 직접 저장(세터 안 거침)
        set(value) {
            println("세터 호출: $value")
            field = value
        }
}

fun main() {
    val c = Config()             // 생성 시 "세터 호출" 출력 안 됨 — 초기화는 세터 우회
    c.level = 5                  // => 세터 호출: 5   (여기서부터 세터 경유)
}
```

이 점은 알아차리기 어렵지만 중요하다. 초기화식은 세터의 검증 로직을 거치지 않는다. 따라서 세터에 `require(value >= 0)` 같은 불변식을 걸어 두었더라도, 초기값이 그 불변식을 만족하는지는 컴파일러가 자동으로 확인해 주지 않는다. 초기값도 유효해야 한다면 처음부터 유효한 값을 적어야 한다.

계산 프로퍼티(백킹 필드 없음)에는 초기화식을 붙일 수 없다. 저장할 곳이 없으니 초기화할 대상도 없다.

```kotlin
class Bad {
    val area: Double = 0.0        // 초기화식 있음 → 백킹 필드 생김
        get() = 3.14              // …그런데 게터가 field를 안 쓰니 초기값 0.0은 죽은 값
    // 컴파일은 되지만 초기값이 무의미 — 게터가 항상 3.14 반환
}
```

위 코드는 컴파일되지만 `= 0.0`에는 아무 의미가 없다(게터가 `field`를 읽지 않으므로 저장된 0.0은 끝내 쓰이지 않는다). 계산 프로퍼티라면 초기화식을 아예 빼는 것이 맞다.

## 5. 접근자의 가시성과 한정자

### 5.1 세터만 좁히기: `private set` 관용구

프로퍼티의 게터와 세터는 서로 다른 가시성을 가질 수 있다. 실무에서 가장 흔한 형태는 **밖에서는 읽을 수만 있도록 게터는 public, 세터만 private**으로 두는 것이다.

```kotlin
class Counter {
    var count: Int = 0
        private set              // 게터는 public, 세터는 private

    fun increment() {
        count++                  // 클래스 내부라 세터 접근 가능
    }
}

fun main() {
    val c = Counter()
    c.increment()
    println(c.count)             // => 1   읽기는 OK (게터 public)
    // c.count = 100             // 컴파일 에러: setter is private (밖에서 쓰기 금지)
}
```

이것은 [[26 - 가시성 한정자]]와 함께 캡슐화를 표현하는 대표적인 패턴이다. `var count: Int = 0; private set`은 "값은 공개하지만 값을 바꾸는 경로는 클래스만 가진다"는 계약을 한 줄로 표현한다. 자바에서 같은 일을 하려면 private 필드와 public 게터를 만들고 세터는 만들지 않는 식으로 직접 작성해야 하지만, 코틀린에서는 `private set` 한 마디로 끝난다.

세터에는 본문 없이 가시성만 지정할 수도 있고(`private set`), 본문과 함께 지정할 수도 있다.

```kotlin
class Registry {
    var lastUpdated: Long = 0L
        private set(value) {          // 가시성 + 본문
            field = maxOf(value, field)   // 시간은 되감기지 않음
        }
}
```

### 5.2 가시성 규칙: 게터는 왜 좁힐 수 없는가

접근자 가시성에는 분명한 비대칭 규칙이 있다.

> [!note] 명세 기준
> 게터의 가시성은 **반드시 프로퍼티 자신의 가시성과 같아야 한다**. 게터에는 별도의 가시성 한정자를 붙일 수 없다. 세터만 프로퍼티와 **같거나 더 좁은** 가시성을 가질 수 있다.

```kotlin
class Example {
    var a: Int = 0
        // private get() = field    // 컴파일 에러: getter visibility must match property

    var b: Int = 0
        private set                  // OK: 세터를 더 좁게

    public var c: Int = 0
        // internal set             // OK: public 프로퍼티에 internal 세터도 가능
}
```

왜 이런 비대칭이 있을까? 프로퍼티의 가시성은 "어디서 이 프로퍼티를 읽을 수 있는가"를 뜻하고, 읽기는 게터로 이루어진다. 따라서 프로퍼티 가시성과 게터 가시성은 같은 개념이며, 둘이 다르면 "프로퍼티는 public인데 읽을 수 없다" 같은 모순이 생긴다.

반면 세터는 "쓸 수 있는 범위"라는 별개의 기준이므로 더 좁힐 수 있다. 읽을 수 있는 범위 안에 쓸 수 있는 범위가 포함되는 구조, 즉 읽을 수 있는 사람 중 일부만 쓸 수 있는 구조만 논리적으로 성립한다.

### 5.3 인라인 접근자와 애노테이션 타깃

접근자마다 따로 `inline`을 붙일 수 있다. 백킹 필드가 없는 프로퍼티(계산 프로퍼티)는 프로퍼티 전체를 `inline`으로 표시할 수도 있다. 인라인의 동작 방식은 [[15 - 인라인 함수와 reified]]에서 자세히 다루며, 요점은 접근자 호출 비용(특히 람다를 받는 접근자)을 없앨 수 있다는 것이다.

```kotlin
class Wrapper(val list: List<Int>) {
    val firstOrZero: Int
        inline get() = list.firstOrNull() ?: 0    // 접근자 인라인화
}
```

또 프로퍼티에 애노테이션을 붙일 때는, 그 애노테이션이 게터, 세터, 백킹 필드, 파라미터 중 어디에 붙어야 하는지를 **사용지점 타깃(use-site target)** 으로 지정할 수 있다. 자세한 내용은 [[44 - 애노테이션과 리플렉션]]에서 다룬다. 다만 프로퍼티가 여러 요소(프로퍼티 자체, 게터, 세터, 필드)로 컴파일되기 때문에 이런 타깃이 필요하다는 사실 자체가 "프로퍼티는 단일 필드가 아니다"라는 점을 다시 보여 준다.

```kotlin
class Bean {
    @get:JvmName("fetchName")     // 게터에만 붙는 애노테이션
    @field:Volatile               // 백킹 필드에만 붙는 애노테이션
    var name: String = ""
}
```

`@get:`, `@set:`, `@field:`, `@param:` 같은 타깃이 있다는 것은, 프로퍼티 선언 하나가 게터, 세터, 필드라는 서로 다른 대상으로 나뉘어 컴파일된다는 물리적 사실을 반영한다.

## 6. 백킹 프로퍼티 패턴: 노출과 저장을 분리한다

### 6.1 문제: 밖에서는 읽기 전용, 안에서는 가변으로 다루고 싶다

실무에서 가장 흔한 요구를 보자. 클래스가 리스트를 관리하는데, **밖에서는 읽기만 하게 하고 안에서는 자유롭게 추가·삭제**하고 싶다. `private set`은 참조 재대입만 막을 뿐 리스트 내용 변경은 막지 못한다. 노출하는 타입 자체를 좁혀야 한다.

단순하게 시도하면 실패한다.

```kotlin
class TaskListNaive {
    val tasks: List<String> = mutableListOf()   // 읽기전용 타입으로 노출
    // 문제: 이 클래스 자신도 tasks에 add를 못 함 (List엔 add가 없음)
}
```

`List`로 노출하면 밖에서는 안전하지만, 정작 클래스 자신도 `add`를 쓸 수 없다(게터의 반환 타입이 `List`이므로 가변 메서드가 보이지 않는다). 여기서 **백킹 프로퍼티 패턴**이 필요하다. 실제 가변 저장은 private 프로퍼티에 두고, public 프로퍼티는 그 private 프로퍼티를 읽기 전용 타입으로 노출하는 계산 프로퍼티(또는 게터)로 만든다.

```kotlin
class TaskList {
    private val _tasks: MutableList<String> = mutableListOf()   // 실제 저장(가변)

    val tasks: List<String>            // 노출(읽기전용) — 백킹 필드 없음
        get() = _tasks

    fun add(task: String) {
        _tasks.add(task)               // 내부에서는 가변으로 자유롭게
    }
}

fun main() {
    val list = TaskList()
    list.add("write chapter")
    println(list.tasks)                // => [write chapter]   읽기 OK
    // list.tasks.add("hack")          // 컴파일 에러: List엔 add 없음 (밖에선 못 바꿈)
}
```

`_tasks`(밑줄 접두사가 관례)는 실제 저장소이고, `MutableList` 타입이므로 내부에서 자유롭게 조작할 수 있다. `tasks`는 `_tasks`를 `List`로 좁혀 내보내는 게터일 뿐이고 백킹 필드가 없다(`field`를 쓰지 않고 `_tasks`만 읽는다). 밖에서 `list.tasks`로 얻는 참조는 정적 타입이 `List`이므로 가변 메서드가 보이지 않는다.

> [!note] 명세 기준
> 이 패턴이 제공하는 안전성은 **정적 타입 수준의 캡슐화**이다. `list.tasks`가 반환하는 실제 객체는 여전히 `_tasks`와 같은 가변 `ArrayList`이다. 밖에서 `(list.tasks as MutableList).add(...)`처럼 캐스팅해 변경하면 막을 수 없다.
>
> 즉 이것은 "읽기 전용 참조"이지 "불변 컬렉션"이 아니다([[38 - 컬렉션 - 읽기 전용과 가변]] 참조). 확실하게 막아야 한다면 게터에서 `_tasks.toList()`로 방어적 복사본을 반환해야 한다(대신 접근할 때마다 복사 비용이 든다).

### 6.2 백킹 프로퍼티로 캐싱과 지연 초기화 흉내 내기

백킹 프로퍼티는 "계산 결과를 캐싱하되 계산 프로퍼티처럼 노출"하고 싶을 때도 쓴다. private 저장 프로퍼티에 nullable 캐시를 두고, public 게터는 캐시가 없으면 계산하고 있으면 재사용한다.

```kotlin
class Report(val rawData: List<Int>) {
    private var _summary: String? = null      // 캐시 저장소

    val summary: String
        get() {
            if (_summary == null) {
                _summary = expensiveCompute()  // 최초 1회만 계산
            }
            return _summary!!
        }

    private fun expensiveCompute(): String =
        "합계=${rawData.sum()}, 개수=${rawData.size}"
}
```

이렇게 직접 캐싱하는 방식은 스레드 안전하지 않고 코드도 길다. 코틀린은 바로 이 패턴을 위해 `by lazy` 위임을 제공하므로, 실무에서는 백킹 프로퍼티를 직접 작성하기보다 23장(위임 프로퍼티)의 `val summary by lazy { expensiveCompute() }`를 쓰는 편이 낫다. 위임 프로퍼티는 이 절의 수동 패턴을 언어 차원에서 일반화한 것이며, 위임 객체가 백킹 필드를 대신한다.

### 6.3 명명 관례: 왜 밑줄을 쓰는가

백킹 프로퍼티의 밑줄 접두사(`_tasks`, `_summary`)는 코틀린 코딩 컨벤션이 권장하는 관례이다. 이유는 두 가지이다. 첫째, public 프로퍼티(`tasks`)와 이름이 겹치면 안 되므로 다른 이름이 필요하다. 둘째, 밑줄 접두사는 "내부 저장소이니 직접 건드리지 말라"는 신호이며, private 저장소를 게터에서 참조할 때 `this.` 없이 바로 쓸 수 있어 간결하다.

| 요소 | 이름 | 타입 | 가시성 | 역할 |
|---|---|---|---|---|
| 저장 프로퍼티 | `_tasks` | `MutableList<T>` | `private` | 실제 가변 저장 |
| 노출 프로퍼티 | `tasks` | `List<T>` | `public` | 읽기 전용 뷰 |

자바에서는 이런 분리를 "private 가변 필드와, `Collections.unmodifiableList(field)`를 반환하는 public 게터"로 직접 작성했다. 코틀린은 같은 구조를 타입 시스템(읽기 전용 인터페이스)으로 간결하게 표현한다.

## 7. JVM 백엔드에서의 컴파일 형태

> 이 절에서 설명하는 구체적 결과물(메서드 이름, `@JvmField`의 효과 등)은 **JVM 백엔드**에 해당한다. Kotlin/Native, JS, Wasm 백엔드는 각 타깃에 맞는 방식으로 프로퍼티를 구현하므로 세부가 다르다. 접근자 추상이라는 개념은 모든 타깃에 공통이지만, 아래의 `getX`/`setX` 같은 매핑은 JVM에만 해당한다.

### 7.1 프로퍼티는 `getX()`/`setX()`와 private 필드로 번역된다

JVM 백엔드에서 프로퍼티 하나는 대체로 다음과 같이 컴파일된다. 백킹 필드가 있으면 **private 필드 하나**가 생기고, **public `getX()` 메서드**(`var`라면 `setX()`도)가 생긴다. 덕분에 자바 코드는 코틀린 프로퍼티를 익숙한 게터와 세터로 호출할 수 있다.

```kotlin
// Kotlin
class Circle {
    var radius: Double = 1.0
    val area: Double get() = Math.PI * radius * radius
}
```

위 코드는 JVM에서 개념적으로 다음 자바 코드에 대응한다.

```java
// JVM 바이트코드에 대응하는 개념적 Java
public final class Circle {
    private double radius = 1.0;         // 백킹 필드(있음)

    public final double getRadius() { return this.radius; }
    public final void setRadius(double v) { this.radius = v; }

    // area는 백킹 필드 없음 — 게터 메서드만 존재
    public final double getArea() { return Math.PI * radius * radius; }
}
```

`radius`는 백킹 필드가 있으므로 private 필드와 게터, 세터로 번역되고, `area`는 백킹 필드가 없으므로 게터 메서드로만 번역된다. 자바에서 이 클래스를 쓰면 다음과 같다.

```java
Circle c = new Circle();
c.setRadius(5.0);
double a = c.getArea();     // Kotlin의 c.area는 Java에선 c.getArea()
```

**이름 규칙의 예외(`is`로 시작하는 프로퍼티)**: 프로퍼티 이름이 `is`로 시작하고 타입이 `Boolean`이면, 게터 이름에 `get` 접두사를 붙이지 않고 이름을 그대로 쓰며(`isEmpty()`), 세터는 `is`를 `set`으로 바꾼다(`setEmpty()`).

```kotlin
class Box {
    var isEmpty: Boolean = true    // JVM: isEmpty() 게터, setEmpty(boolean) 세터
}
```

이 규칙은 자바 빈 관례에 맞추기 위한 것이며, 반대 방향으로도 적용된다. 자바 클래스의 `isFoo()`/`getFoo()` 게터는 코틀린에서 프로퍼티 `foo`/`isFoo`로 보인다([[45 - Java 상호운용]]).

### 7.2 `@JvmField`: 접근자를 없애고 필드를 직접 노출한다

게터와 세터의 오버헤드나 상용구 코드 없이 자바 쪽에 순수한 **public 필드**를 노출하고 싶을 때가 있다(예: 자바 라이브러리가 리플렉션으로 필드를 읽는 경우, 성능에 극도로 민감한 경우). 이때 `@JvmField`를 붙이면 컴파일러는 게터와 세터를 생성하지 않고, 백킹 필드를 프로퍼티와 같은 가시성의 필드로 직접 노출한다.

```kotlin
class Point {
    @JvmField var x: Int = 0    // JVM: public int x; (게터/세터 없음)
    @JvmField var y: Int = 0
}
```

```java
// Java에서
Point p = new Point();
p.x = 3;         // 필드 직접 접근 (getX/setX 아님)
p.y = 4;
```

`@JvmField`에는 제약이 있다. 커스텀 게터나 세터가 있는 프로퍼티, `open`/`override`/`const` 프로퍼티, 위임 프로퍼티, 인터페이스 안의 프로퍼티에는 대체로 붙일 수 없다. 접근자 고유의 동작이 있거나 상태를 가질 수 없는 프로퍼티라면, 필드를 직접 노출하는 것이 논리적으로 맞지 않기 때문이다.

> [!caution] 성능 주의
> 코틀린 코드 안에서 코틀린 프로퍼티에 접근하면 대개 게터와 세터를 거치지만, JIT 컴파일러가 단순한 접근자를 인라인하므로 실제 비용은 필드 접근과 같아진다. 따라서 성능만을 이유로 `@JvmField`를 남발할 필요는 거의 없다. `@JvmField`는 주로 자바 상호운용(필드 직접 노출을 기대하는 API)을 위해 쓴다.

### 7.3 `const`, 컴패니언, `lateinit`의 컴파일 형태

세 가지 특수 프로퍼티가 JVM에서 어떻게 표현되는지 정리하자. 개념은 다른 장(11장, 28장)에서 다루지만, 컴파일 형태를 여기서 함께 보면 프로퍼티와 필드가 어떻게 대응하는지 전체 그림을 볼 수 있다.

- **`const val`** (11장 변수와 초기화): 컴파일 타임 상수이다. JVM에서는 `public static final` 필드로 만들어지지만, **사용하는 곳에서는 값이 인라인**된다(호출부 바이트코드에 상수값이 직접 들어간다). 그래서 게터도 없다. `const`는 원시 타입이나 `String`에만, 최상위나 `object`/`companion` 안에서만, 리터럴로 초기화할 때만 쓸 수 있다.

- **`lateinit var`** (11장 변수와 초기화): 널이 아닌 프로퍼티의 초기화를 뒤로 미룬다. JVM에서 백킹 필드는 초기화 전에 `null`로 시작하고, 게터는 접근할 때 값이 null이면 `UninitializedPropertyAccessException`을 던진다. `lateinit`에는 반드시 백킹 필드가 있어야 하므로 커스텀 접근자를 가질 수 없다. 초기화 여부는 `::prop.isInitialized`로 검사한다.

```kotlin
class Service {
    lateinit var connection: String       // 백킹 필드는 null로 시작

    fun connect() { connection = "opened" }
    fun status(): String =
        if (::connection.isInitialized) connection else "미연결"
}

fun main() {
    val s = Service()
    println(s.status())        // => 미연결   (아직 미초기화 — 예외 안 남)
    // println(s.connection)   // => UninitializedPropertyAccessException
    s.connect()
    println(s.connection)      // => opened
}
```

- **`companion object`의 프로퍼티** ([[28 - object와 companion - 싱글턴과 동반 객체]]): 동반 객체의 프로퍼티는 그 동반 객체 인스턴스의 필드로 저장된다. 바깥에서 `Outer.prop`으로 접근하면 실제로는 동반 객체 인스턴스의 게터를 호출한다. 진짜 자바 `static` 필드로 만들려면 `@JvmStatic`이나 `@JvmField`가 필요하다.

### 7.4 코틀린에서 자바 필드에 접근하기

반대 방향도 있다. 자바 클래스는 순수한 public 필드를 노출하기도 하는데, 코틀린에서는 그 필드가 프로퍼티처럼 보인다. 자바 쪽에 그 필드에 대응하는 게터와 세터가 없으면, 코틀린은 그 필드를 이름으로 직접 읽고 쓸 수 있는 프로퍼티(이른바 synthetic property)처럼 다룬다. 자바의 `getFoo()`/`setFoo()` 게터 쌍도 코틀린에서는 프로퍼티 `foo`로 나타난다. 이 매핑의 세부 사항과 함정(플랫폼 타입, 이름 충돌)은 45장(Java 상호운용)에서 다룬다.

```text
Kotlin 프로퍼티 → JVM 산출물 요약
┌──────────────────────────┬────────────────────────────────────┐
│ 프로퍼티 형태            │ JVM 백엔드 산출물                    │
├──────────────────────────┼────────────────────────────────────┤
│ var x (백킹 필드 있음)    │ private field + getX() + setX()      │
│ val x (백킹 필드 있음)    │ private field + getX()               │
│ val x (계산, 필드 없음)   │ getX()만                             │
│ var isX: Boolean          │ private field + isX() + setX()       │
│ @JvmField var x           │ public field x (접근자 없음)         │
│ const val X               │ public static final + 사용처 인라인  │
│ lateinit var x            │ 비-private field(null 시작) + 접근자 │
└──────────────────────────┴────────────────────────────────────┘
```

## 8. 인터페이스·추상 프로퍼티: 상태 없는 접근자 선언

### 8.1 인터페이스 프로퍼티에는 백킹 필드가 없다

프로퍼티를 접근자로 보는 관점이 가장 잘 들어맞는 곳이 인터페이스이다. 인터페이스는 **상태(저장)를 가질 수 없다**. 즉 인스턴스 필드를 가질 수 없다. 그런데도 인터페이스가 프로퍼티를 선언할 수 있다는 사실은 "프로퍼티 = 접근자"일 때만 설명된다. 인터페이스의 프로퍼티는 **게터/세터라는 계약(추상 메서드)을 선언한 것**일 뿐이고, 그 뒤에 저장 슬롯은 없다.

```kotlin
interface Named {
    val name: String          // 추상 프로퍼티 — 게터 계약만, 백킹 필드 불가
    // val id: Int = 0        // 컴파일 에러: 인터페이스 프로퍼티엔 백킹 필드가 없어 초기화 불가
}
```

`val id: Int = 0`이 금지되는 이유가 바로 여기에 있다. 초기화식 `= 0`에는 백킹 필드가 필요한데, 인터페이스는 백킹 필드를 가질 수 없다. 그래서 인터페이스 프로퍼티는 초기화식도, `field`를 참조하는 접근자도 가질 수 없다. 추상 선언이거나 `field`를 쓰지 않는 계산 게터만 가능하다.

```kotlin
interface Shape {
    val area: Double                     // 추상 게터 계약
    val name: String
        get() = "shape"                  // 기본 구현 OK — field 안 씀(계산)
    // val cached: Int = 0               // 에러 — 저장 불가
}

class Square(val side: Double) : Shape {
    override val area: Double
        get() = side * side              // 구현 클래스가 게터를 채움
    override val name: String = "square" // 구현 클래스는 백킹 필드로 상태 저장 가능
}
```

인터페이스는 `name`에 기본 게터를 제공할 수 있지만, 그 게터는 `field`를 쓰지 않는 계산이어야 한다. 상태(`= 0`처럼 저장하는 것)는 구현 클래스에서만 가질 수 있다. "코틀린 인터페이스는 상태를 가질 수 있다"는 오해는 이 점으로 바로잡을 수 있으며, 자세한 내용은 25장(인터페이스)에서 다룬다.

### 8.2 추상 프로퍼티와 오버라이드

추상 클래스 안의 `abstract` 프로퍼티도 인터페이스 프로퍼티와 원리가 같다. 본문 없는 접근자 선언이며 백킹 필드가 없다. 하위 클래스가 오버라이드하면서 구현(계산 게터 또는 저장 프로퍼티)을 채운다.

```kotlin
abstract class Animal {
    abstract val legs: Int               // 추상 — 백킹 필드 없음

    val description: String
        get() = "다리 $legs 개의 동물"     // legs는 게터로 접근
}

class Dog : Animal() {
    override val legs: Int = 4            // 저장 프로퍼티로 구현(백킹 필드 있음)
}

class Snake : Animal() {
    override val legs: Int
        get() = 0                        // 계산 프로퍼티로 구현(백킹 필드 없음)
}
```

같은 추상 프로퍼티 `legs`를 `Dog`는 저장 방식으로, `Snake`는 계산 방식으로 오버라이드한다. 상위 타입에서 보면 둘 다 "게터 계약을 만족한 것"이므로 구별되지 않는다. 균일 접근 원칙이 상속에서도 그대로 적용되는 것이다.

프로퍼티 오버라이드에는 방향 규칙이 있다. **`val`을 `var`로 오버라이드할 수는 있지만(게터에 세터를 더하는 것) 그 반대는 안 된다.** `var`는 게터와 세터를 함께 약속하는데, 이를 `val`로 오버라이드하면 세터가 사라져 상위 타입의 계약을 어기기 때문이다.

```kotlin
open class Base {
    open val x: Int = 0        // 게터만
    open var y: Int = 0        // 게터+세터
}
class Derived : Base() {
    override var x: Int = 10   // OK: val을 var로 (세터 추가는 계약 강화)
    // override val y: Int     // 에러: var를 val로 (세터 제거는 계약 위반)
}
```

이 오버라이드 규칙이 초기화 순서와 얽히는 문제(상위 생성자에서 오버라이드된 프로퍼티나 게터를 호출하는 함정)는 24장(상속과 오버라이딩과 초기화 순서)에서 다룬다. 요점만 미리 말하면, 상위 클래스 생성자가 실행되는 시점에는 하위 클래스의 프로퍼티 초기화식이 *아직 실행되지 않았다*. 따라서 상위 생성자에서 오버라이드된 프로퍼티를 읽으면 하위 클래스의 백킹 필드가 기본값(예: 0, null)인 상태를 보게 된다.

### 8.3 위임 프로퍼티로 이어지는 연결

지금까지는 프로퍼티의 값을 백킹 필드에 저장하거나(저장 프로퍼티), 매번 계산하거나(계산 프로퍼티), 다른 private 프로퍼티에 저장했다(백킹 프로퍼티 패턴). 세 방식의 공통점은 저장이나 계산 로직을 접근자 안에 직접 적었다는 것이다.

코틀린은 여기서 한 걸음 더 나아가, 접근자 구현 자체를 **다른 객체(위임 객체)에 통째로 맡기는** 문법을 제공한다. `val x: T by delegate`라고 쓰면 `x`를 읽을 때는 `delegate.getValue(...)`가, 쓸 때는 `delegate.setValue(...)`가 호출된다. 이때 백킹 필드에는 값이 아니라 **위임 객체 인스턴스**가 담긴다.

표준 라이브러리는 `by lazy`(처음 접근할 때 계산해 캐싱), `Delegates.observable`(변경 관찰), map 기반 위임 등을 제공한다.

```kotlin
class LazyExample {
    val heavy: String by lazy {          // 백킹 필드엔 Lazy 객체가 저장됨
        println("계산 중…")
        "무거운 결과"
    }
}

fun main() {
    val e = LazyExample()
    println("생성됨")        // => 생성됨   (아직 계산 안 함)
    println(e.heavy)         // => 계산 중…  => 무거운 결과   (최초 접근 시 계산)
    println(e.heavy)         // => 무거운 결과   (캐시됨, 재계산 안 함)
}
```

이 위임 메커니즘, 즉 `getValue`/`setValue` 관례([[19 - 연산자 오버로딩과 관례]]), `provideDelegate`, `KProperty`, 컴파일 형태는 23장(위임 프로퍼티)에서 자세히 다룬다. 이 장에서 기억할 것은 하나이다. 위임 프로퍼티는 "프로퍼티는 접근자 추상"이라는 생각을 끝까지 밀고 나간 결과이다. 접근자가 하는 일을 외부 객체로 떼어 낼 수 있다는 사실 자체가, 프로퍼티는 필드가 아니라 *동작(behavior)의 이름*이라는 점을 보여 준다.
