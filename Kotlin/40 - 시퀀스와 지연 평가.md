앞의 [[39 - 컬렉션 연산과 함수형 파이프라인]]에서는 `map`, `filter`, `fold` 같은 연산이 **즉시(eager) 평가**된다는 점을 확인했다. `list.map { it * 2 }.filter { it > 10 }`에서는 먼저 `map`이 리스트 전체를 순회해 새 리스트를 만들고, 완성된 중간 리스트를 `filter`가 다시 전부 순회한다. 단계마다 원소 개수만큼의 임시 컬렉션이 힙에 생겼다가 사라진다.

이것이 컬렉션 연산의 기본 동작이다. 흔히 "`map`/`filter`는 지연 평가된다"고 생각하지만, 컬렉션에서는 그렇지 않다. 지연 평가는 이 장에서 다루는 `Sequence`에서만 일어난다.

`Sequence`는 컬렉션과 같은 표준 라이브러리에 있고 연산 이름과 시그니처도 거의 같지만, **평가 시점과 데이터가 흐르는 방향이 근본적으로 다르다**. 컬렉션 파이프라인에서는 연산 하나가 데이터 전체를 처리한 뒤 다음 연산으로 넘긴다(가로 처리). 시퀀스 파이프라인에서는 데이터 하나가 연산 전체를 통과한 뒤 다음 데이터로 넘어간다(세로 처리).

이 차이 덕분에 무한 시퀀스를 다룰 수 있고, 조기 종료(short-circuit)가 자동으로 일어나며, 중간 리스트 할당이 사라진다. 반면 작은 데이터에서는 오히려 손해가 될 수 있다.

이 장에서는 `Sequence` 프로토콜의 정의와 시퀀스를 만드는 다섯 가지 방법, 중간 연산과 종단 연산의 구분, 데코레이터 체인으로 이루어진 내부 구현, 상태 없는 연산과 상태 있는 연산, 무한 시퀀스와 조기 종료, 성능 손익을 차례로 다룬다.

컬렉션 계층과 읽기 전용/가변 구분은 [[38 - 컬렉션 - 읽기 전용과 가변]]에서, `sequence{}` 빌더가 기반으로 삼는 코루틴과 중단 메커니즘은 [[42 - suspend와 코루틴 - 언어 수준의 중단]]에서 자세히 설명한다. 마지막에는 동기적인 지연 스트림인 시퀀스를 비동기 지연 스트림인 코루틴 `Flow`와 비교하고, "시퀀스는 항상 빠르다"는 오해를 손익 분석으로 바로잡는다.

## 1. Sequence란 무엇인가: Iterator 위에 세운 얇은 프로토콜

### 1.1 추상 메서드는 하나뿐이다

`kotlin.sequences.Sequence`의 정의는 놀라울 만큼 작다. JVM 백엔드에서 디컴파일하든 소스를 보든, 핵심은 다음 한 줄이다.

```kotlin
public interface Sequence<out T> {
    public operator fun iterator(): Iterator<T>
}
```

정의는 이것이 전부다. `Sequence`는 "요청을 받으면 `Iterator`를 하나 내주겠다"는 약속일 뿐이다. `Iterable`과 시그니처가 사실상 같다는 점에 주목하자. `Iterable<T>`도 `iterator(): Iterator<T>` 하나만 요구한다. 두 인터페이스는 **구조적으로 쌍둥이**이며, 차이는 인터페이스 자체가 아니라 **그 위에 정의된 확장 함수들의 구현 방식**에 있다.

```kotlin
// Iterable에 걸린 map (kotlin.collections) — 즉시 평가
public inline fun <T, R> Iterable<T>.map(transform: (T) -> R): List<R> {
    // 새 ArrayList를 만들어 전부 채워 반환한다
    return mapTo(ArrayList<R>(collectionSizeOrDefault(10)), transform)
}

// Sequence에 걸린 map (kotlin.sequences) — 지연 평가
public fun <T, R> Sequence<T>.map(transform: (T) -> R): Sequence<R> {
    return TransformingSequence(this, transform)
}
```

이름은 같은 `map`이지만 반환 타입이 다르다. `Iterable.map`은 완성된 값인 `List<R>`를 돌려주고, `Sequence.map`은 또 다른 지연 프로토콜인 `Sequence<R>`를 돌려준다. 지연성은 **전적으로 이 반환 타입의 차이에서 나온다**. 리스트를 돌려주는 순간에는 계산이 끝나 있어야 하지만, 시퀀스를 돌려줄 때는 "나중에 요청하면 계산하겠다"는 약속을 한 겹 더 감쌀 뿐이다.

> [!note] 명세 기준
> `Sequence.map`은 `inline`이 아니다. 컬렉션의 `Iterable.map`은 `inline`이므로 람다가 호출 지점에 펼쳐진다(할당과 간접 호출이 사라진다, [[15 - 인라인 함수와 reified]] 참조). 반면 시퀀스의 `map`은 람다를 `TransformingSequence` 객체의 필드에 저장해야 하므로 인라인될 수 없다. 이 비대칭은 뒤에서 다룰 성능 손익(7절)의 한 축이 된다.

### 1.2 즉시 평가와 지연 평가: 실행 순서를 추적한다

설명보다 실행 순서를 직접 보는 편이 빠르다. 두 파이프라인에 부수 효과(`println`)를 넣고, 각 원소가 어떤 순서로 각 단계를 통과하는지 관찰해 보자.

```kotlin
fun main() {
    println("=== 컬렉션 (즉시) ===")
    listOf(1, 2, 3)
        .map { println("map $it"); it * 2 }
        .filter { println("filter $it"); it > 2 }

    println("=== 시퀀스 (지연) ===")
    listOf(1, 2, 3).asSequence()
        .map { println("map $it"); it * 2 }
        .filter { println("filter $it"); it > 2 }
        .toList() // ← 종단 연산이 있어야 흐른다
}
```

출력:

```text
=== 컬렉션 (즉시) ===
map 1
map 2
map 3
filter 2
filter 4
filter 6
=== 시퀀스 (지연) ===
map 1
filter 2
map 2
filter 4
map 3
filter 6
```

컬렉션은 먼저 `map`을 세 원소 모두에 적용해 가로 한 줄을 완성하고, 그 결과 리스트를 `filter`가 다시 세 번 순회한다. 단계마다 처리가 완결된다. 시퀀스에서는 원소 `1`이 `map`과 `filter`를 통과한 **뒤에야** 원소 `2`가 흐르기 시작한다. 원소 하나가 파이프라인 전체를 세로로 통과하고 나서 다음 원소로 넘어간다.

```text
컬렉션 (가로 처리, breadth-first)        시퀀스 (세로 처리, depth-first)
                                          
[1,2,3]                                   1 → map → filter ─┐
  │ map (전체)                            2 → map → filter ─┤→ [ ... ]
  ▼                                       3 → map → filter ─┘
[2,4,6]  ← 중간 리스트 할당               (중간 리스트 없음, 원소 단위 스트리밍)
  │ filter (전체)
  ▼
[4,6]    ← 결과 리스트 할당
```

세로 처리에서는 세 가지 결과가 곧바로 따라온다.

- **중간 컬렉션이 없다.** `map`의 결과인 `[2,4,6]`이 실체화되지 않는다. 원소 `2`는 만들어지자마자 `filter`로 넘어가 버려지거나 살아남는다.
- **조기 종료가 추가 비용 없이 된다.** `first { it > 2 }`를 붙이면 원소 `1`이 통과해 조건을 만족하는 순간, 나머지 `2`와 `3`에는 `map`조차 실행되지 않는다.
- **무한 소스를 다룰 수 있다.** 원소가 필요할 때 하나씩만 가져오므로, 소스가 무한해도 앞부분만 소비하면 끝난다.

이 세 가지 이점이 다음 절들의 중심 내용이다.

### 1.3 "원소 단위 스트리밍"의 정확한 의미

세로 처리를 흔히 "스트리밍"이라고 부르지만, 이 표현은 오해를 부르기 쉽다. 시퀀스에서 스트리밍은 **한 시점에 원소 하나만 파이프라인 안에 있다**는 뜻이지, 데이터가 병렬로 흐른다는 뜻이 아니다. 처리는 여전히 단일 스레드에서 순차적으로 일어나며, `next()`를 한 번 호출할 때마다 원소 하나가 위(소스)에서 아래(종단)로 당겨진다.

처리를 움직이는 것은 **종단 연산이 당기는 힘(pull)** 이다. 강물이 위에서 흘러 내려오는 것이 아니라, 종단 연산이 위쪽 원소를 빨아들이는 펌프에 가깝다.

이 pull 모델은 반대 방향인 push 모델의 `Flow`(42장 suspend와 코루틴)와 대조된다. `Sequence`는 소비자가 `next()`로 직접 원소를 당기는 동기 pull 방식이고, `Flow`는 생산자가 `emit`으로 원소를 밀어 넣는 비동기 push 방식이다. 둘 다 지연 평가라는 성질을 공유하지만, 제어 방향과 동시성 유무가 다르다. 이 장은 pull 방식의 동기 처리만 다룬다.

## 2. 시퀀스를 만드는 다섯 가지 방법

`Sequence`는 인터페이스일 뿐이므로, 이를 구현한 무언가가 있어야 파이프라인이 시작된다. 표준 라이브러리는 소스 유형에 따라 다섯 가지 생성 방법을 제공한다.

### 2.1 asSequence: 기존 컬렉션을 지연 뷰로 감싼다

가장 흔히 쓰는 진입점이다. 이미 가지고 있는 `Iterable`(리스트, 셋 등)을 시퀀스로 감싼다.

```kotlin
val numbers = listOf(1, 2, 3, 4, 5)
val seq: Sequence<Int> = numbers.asSequence()
```

구현은 매우 얇다.

```kotlin
public fun <T> Iterable<T>.asSequence(): Sequence<T> {
    return Sequence { this.iterator() }
}
```

`Sequence { ... }`는 SAM 변환([[13 - 함수 타입과 람다와 함수 참조]])이다. `Sequence`는 `iterator()` 메서드 하나만 가진 인터페이스이므로 람다가 곧 구현체가 된다. 여기서 `this.iterator()`는 원본 컬렉션의 이터레이터를 그대로 돌려준다.

즉 `asSequence`는 **원본을 복사하지 않는** 뷰(view)일 뿐이다. 따라서 가변 리스트의 원본이 나중에 바뀌면, 시퀀스를 소비할 때 그 변경이 반영된다.

주의할 함정도 있다. 컬렉션에서 시퀀스로 갔다가 다시 컬렉션으로 돌아오면 오히려 손해다.

```kotlin
// 안티패턴: 단일 연산에 시퀀스를 끼워 넣기
val bad = list.asSequence().map { it * 2 }.toList()
// asSequence로 감싸는 비용 + 매 원소 iterator 간접호출 + 다시 toList로 리스트 재생성
// 그냥 list.map { it * 2 } 가 더 빠르다 (7절 M29)
```

### 2.2 sequenceOf: 리터럴 원소로 시퀀스 만들기

`listOf`의 시퀀스 버전이다. 고정된 원소들로 시퀀스를 만든다.

```kotlin
val seq = sequenceOf("dog", "cat", "owl")
// 내부적으로 배열을 만들고 그 iterator를 감싼다: array.asSequence()
```

실무에서 직접 쓸 일은 드물다. 원소가 이미 모두 있다면 지연 평가의 이점(무한 소스, 조기 종료, 중간 할당 회피)을 거의 얻을 수 없기 때문이다. 주로 테스트나 시퀀스 합성(`+` 연산)의 재료로 쓴다. 빈 시퀀스는 `emptySequence<T>()`로 만든다.

### 2.3 generateSequence: 무한 시퀀스를 안전하게 생성하기

여기서부터 시퀀스는 컬렉션으로는 할 수 없는 일을 한다. 시드(seed)와 "다음 원소를 계산하는 함수"만으로 잠재적으로 무한한 시퀀스를 만든다.

```kotlin
// 형태 1: 무한 시퀀스 (nextFunction이 절대 null을 안 냄)
val naturals = generateSequence(1) { it + 1 }
// 1, 2, 3, 4, ... 무한

val powers = generateSequence(1) { it * 2 }
println(powers.take(5).toList()) // => [1, 2, 4, 8, 16]

// 형태 2: null로 종료되는 유한 시퀀스
val downTo = generateSequence(10) { if (it > 1) it - 1 else null }
println(downTo.toList()) // => [10, 9, 8, ..., 1]
```

시그니처를 보면 종료 조건이 타입에 드러나 있다.

```kotlin
public fun <T : Any> generateSequence(
    seed: T?,
    nextFunction: (T) -> T?
): Sequence<T>
```

`nextFunction`의 반환 타입은 `T?`이다. **`null`을 반환하면 그 지점에서 시퀀스가 끝난다.** 타입 상한이 `T : Any`인 이유도 여기에 있다. `null`을 "끝"을 알리는 신호로 예약해야 하므로, 원소 타입 자체는 non-null이어야 한다. `null`을 유효한 원소로 담고 싶다면 이 오버로드를 쓸 수 없다.

시드가 `T?`인 별도 오버로드도 있어서, 시드 자체를 지연 계산하는 형태(`generateSequence(seedFunction) { ... }`)도 쓸 수 있다. 이 형태는 순회할 때마다 시드부터 다시 계산하므로, 파일 읽기처럼 순회할 때마다 새로 시작해야 하는 소스에 쓴다.

```kotlin
// 실전 관용구: BufferedReader에서 한 줄씩 지연 읽기
fun readLinesLazily(reader: java.io.BufferedReader): Sequence<String> =
    generateSequence { reader.readLine() } // null(EOF) 만나면 종료
// 파일 전체를 메모리에 안 올리고 한 줄씩 흘려보낸다
```

무한 시퀀스가 무한 루프에 빠지지 않는 이유는 1.3절에서 본 pull 모델 때문이다. `generateSequence`는 "다음 원소를 계산하라"는 요청이 올 때만 `nextFunction`을 한 번 실행한다. 종단 연산이 `take(5)`처럼 유한한 개수만 요구하거나 `first`처럼 조건을 만족하는 순간 멈추면, 무한 소스에서는 필요한 만큼만 원소를 가져온다.

반대로 `naturals.toList()`나 `naturals.count()`처럼 **전체를 요구하는 종단 연산을 무한 시퀀스에 걸면 실제로 무한 루프**에 빠진다(6절).

### 2.4 sequence { }: yield 기반 빌더

표현력이 가장 강한 생성 방법이다. 임의의 제어 흐름 안에서 원소를 하나씩 내보낸다.

```kotlin
val fib = sequence {
    var a = 0
    var b = 1
    while (true) {
        yield(a)          // 원소 하나를 내놓고 여기서 "멈춘다"
        val next = a + b
        a = b
        b = next
    }
}
println(fib.take(8).toList()) // => [0, 1, 1, 2, 3, 5, 8, 13]
```

무한 `while(true)` 안에 있는데도 실행이 멈춘다. 그 이유는 `yield`가 **중단 함수(suspend)** 라는 데 있다. `sequence { }` 블록은 사실 **제약된 코루틴(restricted suspension coroutine)** 이다.

`yield(a)`를 만나면 코루틴은 그 지점에서 중단되어 원소 `a`를 소비자에게 넘기고, 현재 상태를 그대로 보존한다. 소비자가 다음 원소를 요청(`next()`)하면 코루틴은 멈췄던 지점 바로 다음부터 다시 실행된다. 지역 변수 `a`와 `b`의 값은 코루틴의 상태 기계 안에 보존된다.

```kotlin
// 시그니처 (핵심만)
public fun <T> sequence(
    block: suspend SequenceScope<T>.() -> Unit
): Sequence<T>

// SequenceScope가 제공하는 것
public abstract class SequenceScope<in T> {
    public abstract suspend fun yield(value: T)          // 원소 하나
    public abstract suspend fun yieldAll(iterator: Iterator<T>)  // 여럿
}
```

`yieldAll`은 다른 이터러블이나 시퀀스의 원소를 한꺼번에 내보낸다. 트리 순회처럼 재귀적인 구조를 시퀀스로 펼칠 때 유용하다.

```kotlin
// 이진 트리를 중위 순회로 지연 스트리밍
class Node(val value: Int, val left: Node? = null, val right: Node? = null)

fun Node.inorder(): Sequence<Int> = sequence {
    left?.let { yieldAll(it.inorder()) }  // 왼쪽 서브트리 전체
    yield(value)                           // 자기 자신
    right?.let { yieldAll(it.inorder()) } // 오른쪽 서브트리 전체
}
```

> [!note] 명세 기준
> `sequence { }`의 코루틴은 `@RestrictsSuspension`으로 제약된 스코프에서 실행된다. 이 블록 안에서는 `SequenceScope`의 `yield`/`yieldAll` 외의 임의의 `suspend` 함수(예: `delay`, 네트워크 호출)를 호출할 수 없다. 즉 **동기 코루틴**이다. 비동기 중단이 필요하면 시퀀스가 아니라 `Flow`(42장 suspend와 코루틴)를 써야 한다.
>
> 이 제약 때문에 시퀀스는 "지연되지만 동기적인" 도구로 자리가 정해진다. 코루틴 상태 기계 자체는 자매 시리즈의 [[02 - suspend와 Continuation - CPS와 상태 기계]]에서 자세히 다룬다.

`sequence { }`로 만든 시퀀스는 **여러 번 순회할 수 있다**. `iterator()`를 호출할 때마다 새 코루틴이 시작되어 블록을 처음부터 다시 실행하기 때문이다. 부수 효과가 있다면 순회할 때마다 다시 실행된다는 뜻이기도 하다(8절).

### 2.5 Iterator 직접 구현 또는 Sequence 람다

가장 낮은 수준에서는 `Sequence { }` SAM 람다로 이터레이터를 직접 반환하거나, `Iterator<T>`를 직접 구현할 수 있다. 하드웨어 스트림이나 특수 프로토콜 같은 커스텀 소스를 감쌀 때 쓴다.

```kotlin
// 난수를 무한히 내놓는 시퀀스
val randoms = Sequence {
    object : Iterator<Int> {
        override fun hasNext() = true
        override fun next() = kotlin.random.Random.nextInt(0, 100)
    }
}
println(randoms.take(3).toList()) // => 예: [42, 7, 88]
```

`Iterator.asSequence()`라는 방법도 있는데, 여기에는 중요한 함정이 있다.

```kotlin
public fun <T> Iterator<T>.asSequence(): Sequence<T> =
    Sequence { this }.constrainOnce()
```

이터레이터는 본질적으로 **일회성**이다. 한 번 소진하면 끝이다. 그래서 이터레이터를 감싼 시퀀스도 `constrainOnce()`로 "한 번만 순회할 수 있게" 제약된다. 두 번 순회하려고 하면 `IllegalStateException`을 던진다. 재사용할 수 있는지 여부의 구분은 8절에서 다룰 핵심 함정이다.

**다섯 가지 방법 요약:**

| 방법 | 유한/무한 | 재순회 | 전형적 용도 |
|------|-----------|--------|-------------|
| `asSequence()` (Iterable) | 소스에 따라 다름 | 소스에 따라 다름(대개 가능) | 기존 컬렉션에 지연 파이프라인 적용 |
| `sequenceOf(...)` | 유한 | 가능 | 리터럴 원소, 합성 재료 |
| `generateSequence(seed) { }` | 둘 다 | 가능(재시드) | 수열, 파일 라인, 무한 생성 |
| `sequence { yield }` | 둘 다 | 가능(재실행) | 복잡한 제어 흐름, 트리 순회 |
| `Iterator.asSequence()` | 소스에 따라 다름 | **불가(constrainOnce)** | 일회성 스트림 감싸기 |

## 3. 중간 연산과 종단 연산: 두 부류의 구분이 지연을 만든다

### 3.1 중간 연산은 또 다른 시퀀스를 반환한다

시퀀스 연산은 정확히 두 부류로 나뉘며, 반환 타입만 봐도 구분할 수 있다.

- **중간(intermediate) 연산**: `Sequence<R>`를 반환하며 지연된다. 실제 계산은 하지 않고, 계산 방법을 기억하는 새 시퀀스 객체를 만들 뿐이다. `map`, `filter`, `filterNot`, `take`, `drop`, `takeWhile`, `dropWhile`, `distinct`, `sorted`, `mapIndexed`, `flatMap`, `zip`, `plus`, `windowed`, `chunked` 등이 있다.
- **종단(terminal) 연산**: 리스트, 수, 원소, 불리언 같은 구체적인 값을 반환한다. 이 연산을 호출하는 순간 파이프라인이 실제로 실행된다. `toList`, `toSet`, `sum`, `count`, `first`, `firstOrNull`, `find`, `last`, `single`, `reduce`, `fold`, `forEach`, `any`, `all`, `none`, `joinToString`, `maxOrNull`, `associate` 등이 있다.

```kotlin
val pipeline = sequenceOf(1, 2, 3, 4, 5)
    .map { println("map $it"); it * it }   // 중간: 아무것도 출력 안 됨
    .filter { println("filter $it"); it % 2 == 1 } // 중간: 아무것도 출력 안 됨

// 여기까지 실행해도 콘솔은 조용하다. pipeline은 "레시피"일 뿐.
println("아직 아무 일도 안 일어났다")

val result = pipeline.toList() // ← 여기서 비로소 map/filter 로그가 쏟아진다
```

이 지연 동작 때문에 실수하는 경우가 많다. `list.asSequence().map { sideEffect() }`만 쓰고 종단 연산을 빠뜨리면, 컴파일도 되고 경고도 거의 없지만 부수 효과는 전혀 실행되지 않는다.

### 3.2 종단 연산이 파이프라인을 "당긴다"

종단 연산은 최종 시퀀스의 `iterator()`를 얻은 뒤 `hasNext()`/`next()`를 반복해서 호출한다. 이 호출은 데코레이터 체인을 따라 위로 전파되어, 소스에서 원소를 하나씩 가져온다(자세한 내용은 4절에서 다룬다). 핵심은 위쪽 단계가 **종단 연산이 요구하는 만큼만** 계산된다는 점이다.

```kotlin
val n = generateSequence(1) { it + 1 } // 무한
    .map { it * it }                    // 무한
    .first { it > 50 }                  // 종단: 조건 만족 즉시 멈춤
println(n) // => 64 (8² = 64 > 50), 1²..8²만 계산됨. 9² 이후는 손도 안 댐
```

`first { }`는 조건을 만족하는 원소를 찾는 순간 반복을 중단한다(내부적으로 예외 없이 `return`한다). 그 뒤에 무한 소스가 남아 있어도 원소를 더 가져오지 않는다. **조기 종료가 파이프라인 전체에 자동으로 전파된다**는 점이 지연 평가의 가장 실용적인 이점이다.

### 3.3 종단 연산이 없으면 정말로 아무 일도 일어나지 않는다

이 성질은 분명히 기억해 두자. 중간 연산만 이어 붙인 시퀀스는 **부수 효과가 있는 람다조차 실행하지 않는다.**

```kotlin
fun main() {
    val counter = intArrayOf(0)
    val seq = (1..1_000_000).asSequence()
        .onEach { counter[0]++ } // onEach도 중간 연산이다!
        .map { it * 2 }
    println("counter = ${counter[0]}") // => counter = 0
    // seq를 소비(종단)하지 않았으므로 onEach가 한 번도 안 돌았다
}
```

`onEach`는 부수 효과를 위한 연산처럼 보이지만, **중간 연산**이므로 지연된다. 부수 효과를 곧바로 실행하려면 종단 연산인 `forEach`를 쓰거나 `.toList()` 등으로 시퀀스를 소비해야 한다. 컬렉션의 `onEach`(즉시)와 시퀀스의 `onEach`(지연)는 이름이 같지만 실행 시점이 다르다. "컬렉션 연산도 지연 평가된다"는 오해와 같은 계열의 혼동이 흔히 여기서 생긴다.

> [!warning] 흔한 오해
> "시퀀스로 바꾸면 성능이 좋아진다"고 믿고 `asSequence()`만 붙였는데 결과가 나오지 않는다면, 종단 연산을 붙이지 않았기 때문이다. 반대로 "왜 이렇게 느리지?" 싶다면, 같은 시퀀스에 종단 연산을 여러 번 걸어 파이프라인이 매번 다시 실행되고 있지 않은지 확인하자(8.1절).

## 4. 파이프라인 내부: 데코레이터 체인과 hasNext 전파

### 4.1 각 중간 연산은 시퀀스를 감싸는 데코레이터다

지연 평가는 사실 평범한 객체지향 패턴인 **데코레이터(Decorator)** 로 구현된다. 각 중간 연산은 원본 시퀀스를 필드로 가지고 있다가, `iterator()`가 호출되면 원본의 이터레이터를 감싼 새 이터레이터를 돌려준다. 표준 라이브러리의 실제 구현을 단순화하면 다음과 같다.

```kotlin
// map의 구현체 (kotlin.sequences.TransformingSequence 단순화)
internal class TransformingSequence<T, R>(
    private val sequence: Sequence<T>,
    private val transformer: (T) -> R
) : Sequence<R> {
    override fun iterator(): Iterator<R> = object : Iterator<R> {
        val iterator = sequence.iterator() // 위쪽 이터레이터를 품는다
        override fun next(): R = transformer(iterator.next()) // 당길 때 변환
        override fun hasNext(): Boolean = iterator.hasNext()
    }
}

// filter의 구현체 (FilteringSequence 단순화)
internal class FilteringSequence<T>(
    private val sequence: Sequence<T>,
    private val predicate: (T) -> Boolean
) : Sequence<T> {
    override fun iterator(): Iterator<T> = object : Iterator<T> {
        val iterator = sequence.iterator()
        var nextState = -1 // -1 미정, 0 없음, 1 있음
        var nextItem: T? = null

        private fun calcNext() {
            // 조건을 만족하는 다음 원소를 만날 때까지 위쪽을 당긴다
            while (iterator.hasNext()) {
                val item = iterator.next()
                if (predicate(item)) {
                    nextItem = item; nextState = 1; return
                }
            }
            nextState = 0
        }
        override fun next(): T { /* calcNext 후 nextItem 반환 */ ... }
        override fun hasNext(): Boolean { if (nextState == -1) calcNext(); return nextState == 1 }
    }
}
```

`seq.map { }.filter { }`는 실행 시점에 다음과 같은 객체 그래프를 만든다.

```text
FilteringSequence(predicate)
   └ sequence = TransformingSequence(transformer)
                   └ sequence = (원본, 예: 리스트의 asSequence)

종단 연산 toList()가 FilteringSequence.iterator()를 얻으면:

  Filter.Iterator ──next()/hasNext()──> Transform.Iterator ──> 원본.Iterator
        │  (조건 통과할 때까지 반복 당김)      │ (당긴 값에 map 적용)
        ▼                                       ▼
   원소를 걸러 내보냄                      원소를 변환해 내보냄
```

### 4.2 hasNext/next가 위로 전파되는 흐름

종단 연산 `toList()`의 내부 루프는 결국 다음과 같은 모양이다.

```kotlin
val iterator = finalSequence.iterator()
val list = ArrayList<T>()
while (iterator.hasNext()) {   // ← 이 hasNext가 체인 꼭대기까지 전파
    list.add(iterator.next())  // ← 이 next도 마찬가지
}
```

`Filter.hasNext()`는 조건을 통과하는 원소를 찾기 위해 `Transform.hasNext()`/`Transform.next()`를 호출하고, 이 호출은 다시 `원본.hasNext()`/`원본.next()`를 호출한다. 원소 하나가 이 체인을 세로로 통과해 위에서 아래로 흐른다. 1.2절에서 본 "세로 처리"는 실제로 이렇게 동작한다.

여기서 성능의 장단점이 드러난다. **장점**은 중간 리스트가 하나도 없다는 것이다. `Transform.Iterator`와 `Filter.Iterator`라는 작은 이터레이터 객체만 하나씩 있고, 원소는 스택을 따라 흐르다가 사라진다.

**단점**은 원소마다 `hasNext`/`next`의 **가상 호출(virtual call)이 체인 깊이만큼 늘어난다**는 것이다. 3단 파이프라인이라면 원소 하나당 최소 3~6번의 간접 호출이 일어난다. 컬렉션의 `inline` `map`에서는 이런 간접 호출이 호출 지점에 펼쳐져 사라지지만, 시퀀스에서는 그럴 수 없다(1.1절 명세 기준). 작은 데이터에서 시퀀스가 더 느린 근본 이유가 여기에 있다(7절).

> [!caution] 성능 주의
> 시퀀스 파이프라인의 각 단계는 힙에 이터레이터 객체를 하나씩 만든다. 종단 연산을 한 번 실행할 때마다 `연산 개수 + 1`개 정도의 이터레이터가 할당된다. 데이터가 크면 이 상수 비용은 무시할 만하지만(원소당 추가 비용은 O(1) 상수다), 데이터가 작으면 이 상수가 전체 비용의 대부분을 차지한다.

### 4.3 flatMap과 take: 전파 규칙의 변형

모든 중간 연산이 원소를 1:1로 흘려보내는 것은 아니다.

- **`flatMap`**: 원소 하나를 시퀀스나 이터러블로 펼친다. `Flattening Sequence`는 위쪽에서 원소 하나를 가져와 내부 이터레이터로 만들고, 그 내부 이터레이터를 소진한 뒤에야 다음 원소를 가져온다. 이 과정도 여전히 지연된다. 내부 이터레이터의 원소도 필요할 때만 가져온다.
- **`take(n)`**: `n`개를 센 뒤 위쪽에 `hasNext=false`를 돌려주어 파이프라인을 끊는다. 조기 종료를 명시적으로 표현하는 형태이며, 무한 시퀀스를 유한하게 만드는 핵심 도구다.
- **`takeWhile { }`**: 조건이 처음 깨지는 순간 끊는다. `filter`와 달리 조건을 만족하지 않는 원소가 나온 뒤로는 아예 보지 않는다.

```kotlin
val s = generateSequence(1) { it + 1 }
println(s.takeWhile { it < 5 }.toList()) // => [1, 2, 3, 4]  (5에서 즉시 종료)
println(s.filter { it < 5 }.take(4).toList()) // => [1, 2, 3, 4] 지만 위험!
// filter는 조건이 깨져도 계속 위를 당긴다. take(4)가 없었다면 무한 루프.
// takeWhile은 스스로 멈추지만, filter는 스스로 멈추지 않는다 — 무한 소스에 filter만 쓰면 안 됨
```

무한 시퀀스에서는 `takeWhile`과 `filter`의 이 차이가 프로그램이 끝나는지 여부를 결정한다(6.2절).

## 5. 상태 없는 연산과 상태 있는 연산

### 5.1 대부분의 연산은 상태가 없다(원소 하나만 보면 된다)

`map`, `filter`, `take`, `drop`, `flatMap` 등은 **상태 없는(stateless)** 연산이다. 다음 원소를 만들 때 지금 흐르는 원소와, 많아야 카운터 하나만 있으면 된다. 이전 원소들을 기억할 필요가 없으므로 세로 처리가 자연스럽게 성립하고, 무한 시퀀스와도 잘 맞는다. 표준 라이브러리 KDoc은 이런 연산에 "The operation is _stateless_."라고 명시한다.

### 5.2 일부 연산은 원소 전체나 일부를 모아야 한다

반면 어떤 연산은 원소 하나만 보고는 결과를 낼 수 없다. 이런 연산을 **상태 있는(stateful)** 연산이라고 한다. 대표적인 예는 다음과 같다.

- **`sorted` / `sortedBy` / `sortedWith`**: 정렬은 전체를 봐야 첫 원소가 무엇인지 알 수 있다. 소스 전체를 리스트로 모아 정렬한 뒤에야 첫 원소를 내보낸다.
- **`distinct` / `distinctBy`**: 중복을 제거하려면 지금까지 본 원소를 `HashSet`에 기억해야 한다. 원소를 흘려보내면서 셋을 키워 간다.
- **`chunked(n)` / `windowed(...)`**: `n`개를 버퍼에 모아야 청크 하나가 완성된다.
- **`minByOrNull` 등 일부 종단 연산**: 종단 연산이므로 여기서 논할 대상은 아니지만, 전체 소비를 요구한다.

`sorted`의 내부를 보면 지연성이 어떻게 깨지는지 분명하게 드러난다.

```kotlin
public fun <T : Comparable<T>> Sequence<T>.sorted(): Sequence<T> {
    return object : Sequence<T> {
        override fun iterator(): Iterator<T> {
            val sortedList = this@sorted.toMutableList() // ← 전체를 여기서 실체화!
            sortedList.sort()
            return sortedList.iterator()
        }
    }
}
```

`sorted`는 여전히 `Sequence`를 반환하므로 **겉으로는 중간 연산**이다. 하지만 `iterator()`가 처음 호출되는 순간 **위쪽 원소 전체를 `toMutableList()`로 모은다.** 지연 평가의 겉모습은 유지하면서, 그 지점에서 파이프라인을 둘로 나누는 배리어(barrier)를 만드는 것이다.

```text
map → filter → sorted → map → toList
 └───지연─────┘   ▲    └──지연──┘
              여기서 위쪽 전체를 모아 정렬(배리어).
              sorted 아래로는 다시 지연 스트리밍.
```

### 5.3 배리어는 그 지점에서 지연 평가의 이점을 없앤다

상태 있는 연산이 파이프라인 중간에 있으면, **그 위쪽에서는 지연 평가의 세 가지 이점이 사라진다.**

```kotlin
// 위험: 무한 시퀀스 + sorted = 무한 루프
val bad = generateSequence(1) { it + 1 }
    .sorted()          // 무한을 전부 모으려다 영원히 멈춤
    .take(5).toList()  // take는 너무 늦게 온다
// sorted가 무한 소스를 toMutableList()로 모으다 OutOfMemory 또는 무한 루프
```

`take(5)`가 있어도 소용없다. 조기 종료는 `sorted`의 배리어를 넘어 위로 전파되지 못한다. `sorted`가 정렬 결과의 첫 원소를 내보내려면 위쪽 원소를 전부 봐야 하는데, 위쪽이 무한하면 거기서 끝나지 않는다. 중간 할당을 피하는 이점도 배리어에서 사라진다. `sorted`는 분명히 리스트를 하나 만들기 때문이다.

실천 규칙은 다음과 같다. **상태 있는 연산(특히 `sorted`)은 파이프라인에서 가능한 한 뒤쪽에 두고, `take`/`filter`로 데이터를 충분히 줄인 다음에 배치**하자. 무한 시퀀스에서는 상태 있는 연산을 상류에 두지 않는다.

> [!note] 명세 기준
> `distinct`는 상태 있는 연산이지만, 뒤에 조기 종료가 따라오면 무한 시퀀스에서도 안전할 수 있다. `sorted`와 달리 `distinct`는 원소를 흘려보내면서 셋에 기록하므로, `generateSequence(...).distinct().take(5)`는 앞쪽에서 서로 다른 원소 5개를 찾으면 멈춘다. 다만 셋이 한없이 커질 수 있으므로 메모리에 주의해야 한다.
>
> 즉 상태 있는 연산이라고 해서 모두 무한 시퀀스에서 위험한 것은 아니다. 실제 기준은 **전체를 봐야 첫 결과가 나오는가**(`sorted`, `chunked`의 마지막 청크 등)이다.

## 6. 무한 시퀀스와 조기 종료

### 6.1 무한 시퀀스가 성립하는 조건

무한 시퀀스를 실제로 쓰려면 두 가지 조건이 맞아야 한다. 첫째, 소스가 pull 방식으로 원소를 하나씩 지연 생성해야 한다(`generateSequence`, `sequence{}`). 둘째, 파이프라인 어딘가에서 **유한하게 끊는 연산**이 소비를 제한해야 한다. 끊는 연산은 두 종류다.

- **개수 제한**: `take(n)` (중간 연산, n개 뒤에 끊음)
- **조건 또는 단일 소비 종단 연산**: `first`, `firstOrNull`, `find`, `indexOfFirst`, `any { }`(참을 만나면 멈춤), `none`, `takeWhile`(중간 연산, 조건이 깨지면 끊음)

```kotlin
val primes = generateSequence(2) { it + 1 }
    .filter { n -> (2 until n).none { n % it == 0 } } // 소수만 (비효율적 예시)

println(primes.take(5).toList())        // => [2, 3, 5, 7, 11]
println(primes.first { it > 20 })       // => 23
println(primes.takeWhile { it < 15 }.toList()) // => [2, 3, 5, 7, 11, 13]
```

### 6.2 무한 시퀀스를 끝나지 않게 만드는 종단 연산들

반면 **전체 소비를 요구하는 종단 연산**을 무한 시퀀스에 걸면 곧바로 무한 루프(또는 OOM)에 빠진다. 컴파일러는 이를 막아 주지 않는다. 타입만 보면 `Sequence<Int>`일 뿐이고, 유한한지 무한한지는 타입에 드러나지 않기 때문이다.

```kotlin
val naturals = generateSequence(1) { it + 1 }

naturals.toList()   // 무한 루프 (모든 원소를 리스트에)
naturals.count()    // 무한 루프 (끝까지 세려 함)
naturals.sum()      // 무한 루프 + Int 오버플로([[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]])
naturals.max()      // 무한 루프
naturals.last()     // 무한 루프 (마지막이 없음)
naturals.forEach {} // 무한 루프
```

이를 막으려면 소비하기 전에 반드시 `take`나 조건 종단 연산으로 시퀀스를 유한하게 만들어야 한다. `filter`로는 유한하게 만들 수 없다(4.3절 예시에서 보았듯 `filter`만으로는 멈추지 않는다). `takeWhile`은 조건이 언젠가 반드시 깨진다는 보장이 있을 때만 시퀀스를 유한하게 만든다.

```text
무한 시퀀스에 안전한 것          무한 시퀀스를 죽이는 것
──────────────────────          ──────────────────────
take(n)                          toList / toSet
first / firstOrNull / find       count / sum / average
takeWhile { 언젠가 false }       max / min / last
any { 언젠가 true }              forEach / joinToString
elementAt(유한 index)            reduce / fold
                                 sorted / distinct(전체) 상류에서
```

### 6.3 무한 시퀀스와 상태 배리어의 충돌

5.3절과 6.2절의 내용을 합치면 가장 알아차리기 어려운 함정이 나온다. 무한 시퀀스에서 상태 있는 연산을 상류에 두면, 그 아래에 `take`가 있어도 끝나지 않는다.

```kotlin
generateSequence(1) { it + 1 }.sorted().take(3)   // 죽음 (sorted가 전체 요구)
generateSequence(1) { it + 1 }.take(3).sorted()   // 안전 (3개만 뽑아 정렬)
```

순서만 바꿨을 뿐인데 하나는 무한 루프에 빠지고, 다른 하나는 `[1,2,3]`을 돌려준다. 여기서는 **유한하게 끊는 연산을 상태 배리어보다 위(상류)에 두라**는 규칙이 결정적이다.

## 7. 성능: "시퀀스는 항상 빠르다"는 사실이 아니다

### 7.1 오해 살펴보기

시퀀스를 처음 배우면 "중간 리스트를 만들지 않으니 무조건 빠르다"는 인상을 받기 쉽다. 하지만 **"Sequence는 항상 빠르다"** 는 생각은 사실이 아니다. 실제로는 조건에 따라 다르다. 시퀀스는 **큰 데이터, 여러 중간 연산, 그리고 (특히) 조기 종료**가 함께 있을 때 이득이고, **작은 데이터와 단순한 연산**에서는 오히려 손해다.

손익을 결정하는 두 요인은 서로 반대 방향으로 작용한다.

- **시퀀스가 아끼는 것**: 중간 컬렉션 할당이다. 컬렉션 파이프라인은 단계 개수 $k$만큼 크기 $n$의 리스트를 만든다. 따라서 대략 $O(k \cdot n)$개의 임시 원소를 저장하고, $k$번의 배열 할당과 GC가 일어난다. 시퀀스는 이 비용을 0으로 만든다.
- **시퀀스가 더 쓰는 것**: 원소당 간접 호출이다. 원소 하나가 $k$단 체인을 통과할 때마다 `hasNext`/`next`의 가상 호출이 쌓인다. 또한 시퀀스의 `map`은 `inline`이 아니어서 람다가 객체로 남고, 호출할 때마다 간접 호출이 된다. 컬렉션의 `inline map`은 이 간접 호출을 아예 없앤다.

$$
\text{컬렉션 비용} \approx \underbrace{k \cdot n \cdot c_{\text{원소처리}}}_{\text{처리}} + \underbrace{k \cdot A_{\text{리스트할당}}}_{\text{할당}}
$$

$$
\text{시퀀스 비용} \approx \underbrace{k \cdot n \cdot (c_{\text{원소처리}} + c_{\text{간접호출}})}_{\text{처리, 원소당 오버헤드 증가}} + \underbrace{k \cdot A_{\text{이터레이터할당}}}_{\text{작은 상수}}
$$

원소 수 $n$이 작으면 할당 항 $k \cdot A$가 작아서 시퀀스의 이점은 미미하고, 원소당 $c_{\text{간접호출}}$만큼의 손해는 그대로 남는다. $n$이 크면 컬렉션의 할당 항이 커지고 GC 부담까지 더해져 시퀀스가 앞선다.

**교차점**은 흔히 수십~수백 원소 부근이라고 관찰된다(연산 복잡도와 JIT 상태에 따라 크게 달라진다). 하지만 **정확한 값은 워크로드, 플랫폼, JIT 상태에 따라 다르다.** 이 수치를 절대적인 기준으로 외우지 말고, 성능이 중요하다면 JMH 같은 도구로 실제 벤치마크를 측정하자.

### 7.2 조기 종료가 결과를 뒤집는다

시퀀스의 가장 큰 이점은 할당 절약이 아니라 **조기 종료**다. 100만 개 중 조건에 맞는 첫 원소만 필요한 경우를 보자.

```kotlin
val data = (1..1_000_000).toList()

// 컬렉션: map을 100만 번 다 돌고, filter도 다 돌고, 그 다음 first
val a = data.map { it * 2 }.filter { it > 10 }.first()
// map 100만 회 + 중간 리스트 100만 원소 + filter 100만 회 (first 전에 이미 다 계산됨)

// 시퀀스: 조건 맞는 첫 원소를 찾는 순간 멈춤
val b = data.asSequence().map { it * 2 }.filter { it > 10 }.first()
// map 6회 + filter 6회 정도 (6 * 2 = 12 > 10). 나머지 99만 9994개는 손도 안 댐
```

이 경우 연산 횟수는 100만 대 6으로 **십만 배 넘게** 차이 난다. 이는 상수 배 개선이 아니라 **계산량 자체가 줄어드는** 개선이므로, 데이터가 클수록 격차가 벌어진다. `first`, `find`, `any`, `take(소수)`처럼 앞부분만 필요한 종단 연산이 있을 때는 거의 항상 시퀀스가 옳은 선택이다.

### 7.3 작은 컬렉션에서 시퀀스가 느린 이유

반대 사례도 보자. 원소 3개짜리 리스트를 두 번 변환하는 경우다.

```kotlin
val small = listOf(1, 2, 3)

val a = small.map { it * 2 }.filter { it > 2 }          // 컬렉션
val b = small.asSequence().map { it * 2 }.filter { it > 2 }.toList() // 시퀀스
```

이 경우에는 시퀀스가 더 느리다. 이유는 다음과 같다.

1. `asSequence()`로 감싸는 래퍼 객체를 1개 할당한다.
2. `map`/`filter`가 각각 `TransformingSequence`/`FilteringSequence` 객체를 할당해 2개가 생긴다.
3. 종단 연산 `toList()`를 호출하는 시점에 각 단계의 이터레이터 객체를 2~3개 할당한다.
4. `map`/`filter` 람다가 인라인되지 않으므로 함수 객체로 남아, 원소마다 간접 호출이 일어난다.
5. 결과를 다시 `ArrayList`로 모으면서 1개를 할당한다.

반면 컬렉션 버전은 `inline map`/`inline filter` 덕분에 람다가 펼쳐지고, `ArrayList`를 2개만 만든다. 원소가 3개뿐이라 중간 리스트도 기껏해야 원소 3개짜리이므로, 시퀀스로 아낄 것이 거의 없다. 정리하면 다음과 같다.

| 상황 | 유리한 쪽 | 이유 |
|------|------|------|
| 작은 컬렉션(수십 개 이하) + 1~2개 연산 | **컬렉션** | 시퀀스 래퍼와 이터레이터 할당 오버헤드가 대부분을 차지 |
| 큰 컬렉션 + 여러 중간 연산 | **시퀀스** | 중간 리스트 할당과 GC 절약 |
| 조기 종료(`first`/`find`/`take` 소수) | **시퀀스** | 계산량 자체가 크게 줄어듦 |
| 무한 소스 | **시퀀스(유일)** | 컬렉션으로는 애초에 불가능 |
| 단일 연산(`map`만) | **컬렉션** | 아낄 중간 리스트가 없음 |
| `sorted` 등 상태 있는 연산이 대부분 | 대개 **컬렉션** | 어차피 전체를 실체화하므로 시퀀스 이점이 사라짐 |

### 7.4 박싱은 양쪽 모두 있다: 시퀀스가 해결하지 않는다

흔한 착각이 하나 더 있다. "시퀀스를 쓰면 박싱이 없어진다"는 생각이다. 그렇지 않다. JVM 백엔드에서 `Sequence<Int>`의 이터레이터는 `next(): Int`가 아니라 제네릭 `next(): Any?`를 거치므로 원소가 박싱된다([[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]). 컬렉션 `List<Int>`도 마찬가지로 박싱된다.

**둘 다 박싱하며, 시퀀스가 박싱을 없애 주지는 않는다.** 원시 타입 성능이 꼭 필요하다면 시퀀스가 아니라, 박싱이 없는 원시 배열 `IntArray`를 직접 순회해야 한다. 이 사실도 "시퀀스를 쓰면 성능이 좋아진다"는 오해가 틀렸음을 보여 준다.

> [!caution] 성능 주의
> 마이크로 벤치마크로 시퀀스와 컬렉션을 비교할 때는 JIT 워밍업, 이스케이프 분석, 죽은 코드 제거가 결과를 크게 왜곡한다. `println` 없는 순수 계산은 JIT가 통째로 지워 버릴 수도 있다. 신뢰할 만한 수치는 JMH 같은 도구로만 얻을 수 있다. "시퀀스가 빠르겠지" 하고 감으로 바꾸는 것은 "시퀀스는 항상 빠르다"는 오해를 되풀이하는 일이다.

## 8. 재사용과 부수 효과, 일회성의 함정

### 8.1 시퀀스는 (대개) 여러 번 순회할 수 있지만, 매번 다시 실행된다

컬렉션에 종단 연산을 두 번 걸면 이미 계산된 결과를 두 번 읽을 뿐이다. 하지만 시퀀스에 종단 연산을 두 번 걸면 **파이프라인 전체가 두 번 실행된다.** 시퀀스는 결과를 캐시하지 않는다. 시퀀스는 "완성된 요리"가 아니라 "레시피"이기 때문이다.

```kotlin
val seq = listOf(1, 2, 3).asSequence().map {
    println("계산 $it"); it * 2
}

println("첫 번째:"); seq.toList()  // 계산 1, 계산 2, 계산 3
println("두 번째:"); seq.sum()      // 계산 1, 계산 2, 계산 3 (또!)
```

출력:

```text
첫 번째:
계산 1
계산 2
계산 3
두 번째:
계산 1
계산 2
계산 3
```

`map` 람다가 두 번 실행되었다. 로깅, 카운터 증가, DB 조회 같은 부수 효과가 있다면 종단 연산 횟수만큼 반복된다. 값을 계산하는 비용이 크다면 시퀀스에 종단 연산을 여러 번 거는 대신, **한 번 `toList()`로 실체화한 뒤 그 리스트를 재사용**해야 한다.

### 8.2 일회성 시퀀스: constrainOnce

2.5절에서 보았듯 `Iterator.asSequence()`로 만든 시퀀스는 `constrainOnce()`로 제약되어 **한 번만** 순회할 수 있다. 두 번째로 순회하면 예외가 발생한다.

```kotlin
val once = listOf(1, 2, 3).iterator().asSequence() // Iterator → 일회성
println(once.toList()) // => [1, 2, 3]
println(once.toList()) // 예외: IllegalStateException:
                       //   This sequence can be consumed only once.
```

일회성을 명시적으로 강제하고 싶다면 `constrainOnce()`를 직접 붙인다. 여러 번 순회할 수 있는 시퀀스에 부수 효과가 있어서 다시 실행되는 것을 막고 싶을 때 방어적으로 쓴다.

```kotlin
val guarded = generateSequence(1) { it + 1 }.take(3).constrainOnce()
guarded.toList()  // OK
guarded.toList()  // 예외
```

반대로 **다시 순회할 수 있음을 보장**하고 싶다면 소스가 재순회를 지원해야 한다. `Iterable.asSequence()`(원본 컬렉션을 다시 순회할 수 있음), `generateSequence`(시드부터 다시 계산), `sequence{}`(블록을 다시 실행)는 모두 여러 번 순회할 수 있다. 소스마다 재순회 가능 여부가 다르다는 점이 8.1절의 "매번 다시 실행된다"는 성질과 얽혀 찾기 어려운 버그를 만든다.

### 8.3 부수 효과와 지연 평가가 잘 맞지 않는 이유

지연 평가와 부수 효과는 근본적으로 잘 맞지 않는다. 람다가 "언제 실행될지"가 종단 연산이 있는지, 어떤 종류인지, 몇 번 호출되는지에 따라 달라지기 때문이다. 함수형 파이프라인(39장 컬렉션 연산)이 지향하는 것은 **순수 변환**이다. 각 람다가 입력만으로 출력을 정하고 바깥 상태를 건드리지 않아야 한다. 시퀀스에서는 이 원칙이 선택이 아니라 사실상 필수다.

```kotlin
// 위험한 관용구: 지연 파이프라인 안에서 외부 상태 변경
val log = mutableListOf<Int>()
val seq = (1..10).asSequence().map { log.add(it); it * 2 }

val firstThree = seq.take(3).toList()
println(log) // => [1, 2, 3]  ← 3개만 실행됐다! log가 [1..10]일 거라 기대하면 버그
```

`map`의 부수 효과(`log.add`)는 종단 연산이 요구한 3개에만 적용되었다. 컬렉션이었다면 10개 모두에 실행되었을 것이다. 지연 파이프라인에서 부수 효과가 실행되는 범위는 **하류의 종단 연산이 원소를 얼마나 가져가느냐**에 달려 있고, 이는 상류만 봐서는 알 수 없다. 부수 효과는 `forEach`(전체를 소비한다는 점이 분명한 종단 연산) 같은 곳에 모아 두고, 중간 연산은 순수하게 유지하자.

> [!warning] 흔한 오해
> "`onEach`로 로그를 남기면 파이프라인 전체가 찍히겠지"라고 생각하기 쉽다. 하지만 시퀀스의 `onEach`는 중간 연산이므로 하류가 가져가는 원소에만 실행된다. `take(3)` 아래에 `onEach`가 있으면 3번만 찍힌다. 전체에 실행되는 컬렉션의 `onEach`와는 실행 시점이 다르다.

## 9. Java Stream과 비교, Flow 미리 보기

### 9.1 Sequence와 Java Stream

JVM 백엔드에서 시퀀스는 겉으로 보면 Java 8의 `Stream`과 비슷하다. 둘 다 중간 연산은 지연하고 종단 연산은 즉시 실행하는 모델이다. 하지만 설계 목표가 다르기 때문에 세부 사항이 갈린다.

| 특성 | Kotlin `Sequence` | Java `Stream` |
|------|-------------------|---------------|
| 지연 평가 | 예 | 예 |
| 병렬 처리 | **없음**(순차 전용) | `parallelStream()` 지원 |
| 재사용 | 소스에 따라 다름(대개 가능) | **불가**(재사용 시 IllegalStateException) |
| 원시 타입 특화 | 없음(제네릭, 박싱) | `IntStream`/`LongStream`/`DoubleStream` |
| 자원 관리 | 없음 | `AutoCloseable`(파일 스트림 등) |
| 생성 문법 | `sequence { yield }` 코루틴 | `Stream.iterate`/`generate`/`Builder` |
| 무한 지원 | 예 | 예 |
| 소속 | Kotlin 표준 라이브러리(멀티플랫폼) | JDK(JVM 전용) |

핵심 차이는 세 가지다.

- **시퀀스에는 병렬 처리가 없다.** 데이터 병렬 처리가 필요하면 시퀀스가 아니라 Java Stream의 `parallelStream()`이나 코루틴 기반 분할을 써야 한다. 이는 의도된 설계다. 시퀀스는 "지연"만 담당하고, "병렬"은 별도의 관심사로 분리했다.
- **재사용 가능성이 다르다.** Stream은 무조건 일회성인 반면, 시퀀스는 소스에 따라 여러 번 순회할 수 있다(8.2절).
- **멀티플랫폼을 지원한다.** Stream은 JVM 전용이지만, `Sequence`는 Kotlin/Native, JS, Wasm에서도 동작하는 공통 표준 라이브러리의 일부다. 이식성이 중요하다면 시퀀스가 유일한 선택이다.

```java
// Java Stream — 병렬 가능, 일회성, 원시 특화
IntStream.rangeClosed(1, 1000)   // 원시 int, 박싱 없음
    .map(x -> x * 2)
    .filter(x -> x > 10)
    .findFirst();
```

```kotlin
// Kotlin Sequence — 순차, 재사용 가능(소스 따라), 박싱(JVM)
(1..1000).asSequence()
    .map { it * 2 }
    .filter { it > 10 }
    .first()
```

> [!info] 역사 메모
> Kotlin은 초기에 `Stream`이라는 이름을 쓰다가, Java 8의 `java.util.stream.Stream`과 혼동되는 문제와 JVM에 종속된 듯한 인상을 피하려고 `Sequence`로 이름을 바꿨다(Kotlin 1.0 전후). 이름을 바꾼 것은 단순히 충돌을 피하려는 것이 아니라, 멀티플랫폼, 순차 처리, 재사용 가능이라는 다른 성격을 분명히 하려는 선택이었다.

### 9.2 Flow: 비동기 지연 스트림

`Sequence`로 해결할 수 없는 문제가 하나 있다. "원소를 만드는 데 네트워크 요청처럼 시간이 걸리면 어떻게 할까?" 시퀀스의 `sequence { }` 블록은 **제약된 코루틴**이므로 `delay`나 실제 `suspend` I/O를 호출할 수 없다(2.4절 명세 기준). 즉 시퀀스는 **동기적인 지연 평가**만 한다.

이 빈자리를 kotlinx.coroutines의 `Flow`가 채운다. `Flow`는 **비동기 지연 스트림**이다. 지연 평가라는 성질은 같지만, 원소를 만드는 동안 스레드를 블록하지 않고 중단(suspend)할 수 있다.

```kotlin
// Sequence: 동기. 각 원소를 만드는 동안 스레드 블록
val syncSeq = sequence {
    yield(fetchBlocking()) // suspend 불가, 블로킹만
}

// Flow: 비동기. 원소를 만드는 동안 중단(다른 코루틴에 스레드 양보)
val asyncFlow = flow {
    emit(fetchSuspending()) // suspend 가능
}
```

| 축 | `Sequence` | `Flow` |
|----|-----------|--------|
| 지연 | 예(pull) | 예(push, 콜드 플로우) |
| 제어 방향 | 소비자가 당김(pull) | 생산자가 밀어냄(emit) |
| 중단(suspend) | 불가(동기) | 가능(비동기) |
| 동시성 | 없음 | 코루틴 기반 |
| 소속 | 표준 라이브러리 | kotlinx.coroutines(별도 의존성) |

`Flow`와 코루틴의 동작 원리는 이 시리즈의 42장(suspend와 코루틴)과 Kotlin Coroutines 시리즈에서 자세히 다룬다. 여기서 기억할 점은 하나다. **지연 평가는 하나의 개념이고, `Sequence`는 이를 동기·순차 방식으로, `Flow`는 비동기·동시성 방식으로 구현한 것이다.** 어느 쪽을 쓸지는 "원소를 만드는 동안 I/O 같은 기다림이 있는가"로 정해진다.

### 9.3 선택 규칙: 언제 시퀀스를 쓰는가

지금까지 살펴본 손익을 실천 규칙으로 정리하면 다음과 같다.

```text
시퀀스를 써라:
  ✓ 데이터가 크고(수백~수천+) 중간 연산이 여럿일 때
  ✓ 조기 종료(first/find/take 소수)가 있을 때 — 거의 항상 이득
  ✓ 무한/미지 크기 소스(파일 라인, 수열, 스트림)일 때
  ✓ 원소 생성이 비싸서 필요한 것만 만들고 싶을 때

컬렉션(즉시)을 써라:
  ✓ 데이터가 작을 때(수십 이하) — 시퀀스 오버헤드가 손해 (M29)
  ✓ 연산이 1~2개뿐일 때 — 아낄 중간 리스트가 없음
  ✓ 결과를 여러 번 재사용할 때 — 시퀀스는 매번 재실행(8.1)

둘 다 아니다 (다른 도구):
  ✗ 병렬 처리 필요 → Java Stream parallelStream / 코루틴
  ✗ 비동기 I/O 스트림 → Flow (42장)
  ✗ 원시 성능 극한 → IntArray 직접 순회 (박싱 회피)
```
