이 장은 [[17 - 표현식으로서의 제어 흐름 - if와 when]]과 [[18 - 범위와 진행과 반복]]에서 다룬 내용을 바탕으로 한다. 17장에서는 `if`와 `when`이 문(statement)이 아니라 표현식이라는 점을 보았다. 18장에서는 `1..10` 같은 범위 리터럴과 `for (x in c)` 같은 반복 구문이 실제로는 **평범한 함수 호출로 번역되는 문법 설탕**이라는 점을 보았다.

18장에서 간단히 넘어간 이 번역 규칙, 즉 `..`는 `rangeTo`를, `in`은 `contains`를, `for`는 `iterator`를 호출한다는 규칙을 이 장에서 자세히 살펴본다.

Kotlin에는 별도의 "연산자 오버로딩 문법"이 없다. 그 대신 언어가 미리 정해 둔 **관례 이름(convention name)** 으로 함수를 정해진 시그니처에 맞춰 정의하고 `operator` 키워드를 붙이면, 그 함수를 대응하는 기호(`+`, `*`, `[]`, `()`, `..`, `in` 등)로 호출할 수 있다. 이것이 이 장의 중심 주제다.

흔히 "연산자 오버로딩이니 원하는 기호를 마음대로 정의할 수 있을 것"이라고 생각하지만, 사실은 정반대다. Kotlin의 연산자 오버로딩은 **매우 폐쇄적**이다. 오버로딩할 수 있는 기호의 집합, 각 기호에 대응하는 함수 이름, 연산자 사이의 우선순위와 결합성이 모두 언어 문법에 **고정되어 있어** 바꿀 수 없다. 개발자가 정할 수 있는 것은 정해진 이름의 함수가 어떤 일을 하는지뿐이다.

이 장에서는 관례가 이름 기반이고 폐쇄적인 이유와 `operator` 키워드의 역할에서 출발해 산술, 복합 대입, 단항·증감, 동등성, 비교, 인덱싱과 호출, 범위와 멤버십 연산자가 동작하는 방식을 차례로 다루고, 우선순위 고정과 연산자 남용이라는 함정으로 마무리한다.

`for` 루프의 `iterator`/`hasNext`/`next` 관례는 18장에서, 구조 분해의 `componentN` 관례는 [[20 - 구조 분해]]에서, 위임 프로퍼티의 `getValue`/`setValue`/`provideDelegate` 관례는 [[23 - 위임 프로퍼티]]에서 자세히 다루므로, 이 장에서는 그 관례들이 존재한다는 사실과 원리만 개괄한다.

동등성(`==` vs `===`)의 계약과 부동소수점의 함정은 [[10 - 불리언과 동등성과 동일성]]에서 다루므로, 이 장에서는 `==`가 `equals` 관례로 **번역되는 방식**만 설명한다.

## 1. 관례라는 설계: 왜 이름 기반이고 왜 폐쇄적인가

### 1.1 연산자는 기호가 아니라 이름이다

C++를 아는 사람은 연산자 오버로딩을 "기호 `+`에 대한 정의를 작성하는 일"로 이해한다. `operator+(const Vec& a, const Vec& b)`처럼 기호 자체가 함수 이름의 일부이기 때문이다. Kotlin의 접근은 다르다. Kotlin에서 `+` 기호는 언제나 **`plus`라는 이름의 함수 호출로 번역**된다. 기호는 함수 이름과 관계없이 고정된 문법적 표기일 뿐이다.

```kotlin
data class Vec(val x: Int, val y: Int) {
    operator fun plus(other: Vec): Vec = Vec(x + other.x, y + other.y)
}

fun main() {
    val a = Vec(1, 2)
    val b = Vec(3, 4)
    println(a + b)        // => Vec(x=4, y=6)
    println(a.plus(b))    // => Vec(x=4, y=6)  — 완전히 같은 호출
}
```

`a + b`와 `a.plus(b)`는 **같은 바이트코드로 컴파일**된다. `+`는 `plus`를 호출하라는 지시일 뿐이다. 이 사실이 Kotlin 연산자 시스템의 성격을 결정한다. 기호는 정해진 이름의 함수로 이어지는 통로이고, 통로의 개수와 목적지 이름은 언어가 고정한다.

이 설계의 이점은 두 가지다. 첫째는 **가독성**이다. `a + b`가 `a.plus(b)`라는 것을 알면, 낯선 타입에 `+`가 쓰인 것을 보더라도 `plus`라는 멤버나 확장 함수가 있을 것이라고 짐작하고 정의를 찾아갈 수 있다. 둘째는 **일관성**이다. 언어가 이름을 강제하므로, 라이브러리마다 `+`를 서로 다른 이름의 함수로 정의하는 혼란이 생기지 않는다. `+`는 언제나 `plus`다.

### 1.2 operator 키워드: 우연히 같은 이름과 의도한 관례를 구분한다

`plus`라는 이름의 함수를 정의했다고 해서 자동으로 `+`로 호출되지는 않는다. 반드시 **`operator` 변경자(modifier)** 를 붙여야 한다.

```kotlin
class Money(val cents: Int) {
    fun plus(other: Money): Money = Money(cents + other.cents)   // operator 없음
}

fun main() {
    val a = Money(100)
    val b = Money(50)
    // val c = a + b     // 컴파일 에러:
    // 'operator' modifier is required on 'plus' in 'Money'
    val c = a.plus(b)    // OK — 그냥 이름이 plus인 평범한 메서드일 뿐
    println(c.cents)     // => 150
}
```

이런 강제가 필요한 이유는 `plus`, `get`, `contains`, `invoke` 같은 이름이 관례와 상관없이 그 자체로도 좋은 메서드 이름이기 때문이다. 어떤 개발자가 순수하게 도메인 의미로 `contains` 멤버를 만들었는데, 그 함수가 자신도 모르게 `in` 연산자로 호출될 수 있다면 위험하다. `operator` 키워드는 **"이 함수를 연산자 기호로 호출하도록 의도했다"** 는 명시적 선언이다. 우연히 이름이 겹친 경우와 의도한 관례를 구분하는 안전장치인 셈이다.

`operator`를 붙이면 **컴파일러의 시그니처 검사**도 함께 켜진다. 관례 함수는 정해진 시그니처 규칙을 따라야 한다. `compareTo`는 `Int`를 반환해야 하고, `inc`는 수신 타입과 호환되는 타입을 반환해야 하며, `get`/`set`은 정해진 파라미터 규칙을 따라야 한다. `operator`를 붙이면 컴파일러가 이 규칙을 어긴 코드를 잡아낸다. 붙이지 않으면 평범한 함수이므로 어떤 시그니처든 허용된다.

> [!note] 명세 기준
> `operator`는 함수 선언에 붙는 변경자다. 멤버 함수와 확장 함수에 모두 붙일 수 있다(9.2절). 단, **`equals`만은 예외**다. `equals(other: Any?): Boolean`은 `Any`에 이미 정의된 멤버이며, 이를 오버라이드할 때는 `operator`를 붙이지 않는다(붙이면 에러가 난다). `==`를 `equals`로 번역하는 관례는 언어에 하드코딩되어 있어서 `operator` 표시가 필요 없다(5절).

### 1.3 오버로딩할 수 있는 기호의 닫힌 목록

이제 흔한 오해를 바로잡자. **오해**는 "연산자 오버로딩이니 임의의 기호를 내 연산자로 만들 수 있다"는 것이다. **사실**은 Kotlin이 오버로딩을 허용하는 기호와 그에 대응하는 함수 이름이 **완전히 고정된 유한 목록**이며, 새 기호를 만들어 낼 수 없다는 것이다.

아래가 그 전체 목록이다. 이 표에 없는 기호는 오버로딩할 수 없다.

| 범주 | 기호 | 번역되는 관례 함수 | 반환 타입 제약 |
|------|------|-------------------|----------------|
| 이항 산술 | `a + b` | `a.plus(b)` | 자유 |
| | `a - b` | `a.minus(b)` | 자유 |
| | `a * b` | `a.times(b)` | 자유 |
| | `a / b` | `a.div(b)` | 자유 |
| | `a % b` | `a.rem(b)` | 자유 |
| 범위 | `a..b` | `a.rangeTo(b)` | 자유 |
| | `a..<b` | `a.rangeUntil(b)` | 자유 |
| 복합 대입 | `a += b` | `a.plusAssign(b)` 또는 `a = a.plus(b)` | `Assign`은 `Unit` |
| | `a -= b` | `a.minusAssign(b)` 또는 `a = a.minus(b)` | |
| | `a *= b` | `a.timesAssign(b)` 또는 `a = a.times(b)` | |
| | `a /= b` | `a.divAssign(b)` 또는 `a = a.div(b)` | |
| | `a %= b` | `a.remAssign(b)` 또는 `a = a.rem(b)` | |
| 단항 접두 | `+a` | `a.unaryPlus()` | 자유 |
| | `-a` | `a.unaryMinus()` | 자유 |
| | `!a` | `a.not()` | 자유(보통 Boolean) |
| 증감 | `a++`, `++a` | `a.inc()` | 수신 타입과 호환 |
| | `a--`, `--a` | `a.dec()` | 수신 타입과 호환 |
| 인덱싱 | `a[i]` | `a.get(i)` | 자유 |
| | `a[i] = v` | `a.set(i, v)` | 자유 |
| 호출 | `a()` | `a.invoke()` | 자유 |
| | `a(i)` | `a.invoke(i)` | 자유 |
| 멤버십 | `a in b` | `b.contains(a)` | `Boolean` |
| | `a !in b` | `!b.contains(a)` | `Boolean` |
| 비교 | `a < b` | `a.compareTo(b) < 0` | `Int` |
| | `a > b` | `a.compareTo(b) > 0` | `Int` |
| | `a <= b` | `a.compareTo(b) <= 0` | `Int` |
| | `a >= b` | `a.compareTo(b) >= 0` | `Int` |
| 동등성 | `a == b` | `a?.equals(b) ?: (b === null)` | `Boolean` |
| | `a != b` | `!(a?.equals(b) ?: (b === null))` | `Boolean` |
| 반복 | `for (x in a)` | `a.iterator()`, `.hasNext()`, `.next()` | (18장) |
| 구조 분해 | `val (x, y) = a` | `a.component1()`, `a.component2()` | (20장) |
| 위임 | `val x by a` | `a.getValue(...)` / `a.setValue(...)` | (23장) |

이 목록에 **없는** 것들을 살펴보자. 거듭제곱 `**`은 없다. 그래서 Kotlin에서는 `x.pow(y)`라는 평범한 함수를 쓴다.

비트 연산 `&`, `|`, `^`, `<<`, `>>`도 연산자가 아니다. Kotlin은 이 연산들을 `and`, `or`, `xor`, `shl`, `shr`라는 **중위(infix) 함수**로 제공한다([[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]). 논리 연산 `&&`, `||`는 단축 평가라는 특수한 의미를 보존해야 하므로 오버로딩할 수 없다(5.5절 참조). 대입 `=`, 삼항 연산자(애초에 없다), 엘비스 `?:`도 오버로딩할 수 없다.

> [!warning] 흔한 오해
> "그렇다면 `Matrix ** Matrix`로 행렬 거듭제곱을 정의하면 보기 좋겠다"고 생각할 수 있지만, 불가능하다. `**`는 Kotlin 문법에 존재하지 않는 토큰이라 파싱조차 되지 않는다. 도메인에서 거듭제곱이 필요하다면 `infix fun Matrix.pow(n: Int)`처럼 중위 함수를 만들어 `matrix pow 3`으로 쓰거나, 그냥 `matrix.pow(3)`으로 쓴다. Kotlin에는 기호를 새로 만들 자유가 없다. 이것은 결함이 아니라 의도된 제약이다(9.4절).

### 1.4 왜 이렇게 폐쇄적인가: 설계 철학

Scala처럼 임의의 기호 연산자를 허용하는 언어도 있다. 그런 언어에서는 `<*>`, `>>=`, `|@|` 같은 기호가 라이브러리마다 등장해 "기호 지옥"을 만든다. 처음 보는 사람은 그 기호가 어떤 함수인지, 우선순위가 어떤지 알 방법이 없다. Kotlin은 이 자유를 의도적으로 포기했다. 오버로딩할 수 있는 연산자를 산술, 비교, 인덱싱처럼 **누구나 직관적으로 의미를 아는 기호**로 한정하고, 그 밖의 연산은 이름 있는 함수(중위 함수든 아니든)로 표현하게 했다.

이 철학은 Kotlin 전반에 걸친 "명시성과 실용의 균형"([[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]])과 일치한다. `+`가 벡터 덧셈이라는 것은 누구나 알지만, `>>=`가 무엇인지는 알기 어렵다. 그래서 Kotlin은 전자만 허용한다.

우선순위와 결합성까지 고정하는 이유도 여기에 있다. 사용자가 우선순위를 정의할 수 있다면 `a + b * c`가 라이브러리마다 다르게 파싱될 수 있다. Kotlin에서 `a + b * c`는 타입과 관계없이 언제나 `a + (b * c)`다(9.4절).

## 2. 이항 산술 연산자: plus, minus, times, div, rem

### 2.1 다섯 개의 이항 연산자와 그 이름

이항 산술 연산자는 다섯 개이며, 각각 정해진 관례 이름이 있다.

```text
기호   관례 이름   예시
────   ─────────   ──────────────────
 +     plus        a + b  →  a.plus(b)
 -     minus       a - b  →  a.minus(b)
 *     times       a * b  →  a.times(b)
 /     div         a / b  →  a.div(b)
 %     rem         a % b  →  a.rem(b)
```

도메인 타입 하나에 이 연산자들을 정의해 보자. 2차원 좌표를 예로 든다.

```kotlin
data class Point(val x: Double, val y: Double) {
    operator fun plus(o: Point) = Point(x + o.x, y + o.y)
    operator fun minus(o: Point) = Point(x - o.x, y - o.y)
    operator fun times(scale: Double) = Point(x * scale, y * scale)   // 스칼라 곱
    operator fun div(scale: Double) = Point(x / scale, y / scale)
}

fun main() {
    val p = Point(1.0, 2.0)
    val q = Point(3.0, 4.0)
    println(p + q)        // => Point(x=4.0, y=6.0)
    println(q - p)        // => Point(x=2.0, y=2.0)
    println(p * 2.0)      // => Point(x=2.0, y=4.0)
    println(q / 2.0)      // => Point(x=1.5, y=2.0)
}
```

여기서 두 가지를 확인할 수 있다. 첫째, **왼쪽과 오른쪽 피연산자의 타입이 달라도 된다.** `times`의 인자는 `Double`이고 수신자는 `Point`다. 연산자 함수의 수신자가 왼쪽 피연산자, 인자가 오른쪽 피연산자가 된다. 둘째, **반환 타입에 제약이 없다.** `plus`가 반드시 `Point`를 반환해야 하는 것은 아니다. 두 벡터의 내적을 `Double`로 반환하는 `times`를 정의할 수도 있다(권장하지는 않지만 문법적으로는 가능하다).

### 2.2 피연산자 순서와 비대칭 연산자

`a * b`는 `a.times(b)`이지 `b.times(a)`가 아니다. 따라서 곱셈이 교환법칙을 만족하지 않는 상황을 자연스럽게 표현할 수 있지만, 이 점이 함정이 되기도 한다.

```kotlin
data class Point(val x: Double, val y: Double) {
    operator fun times(scale: Double) = Point(x * scale, y * scale)
}

fun main() {
    val p = Point(1.0, 2.0)
    println(p * 2.0)      // => Point(x=2.0, y=4.0)  — Point.times(Double)
    // println(2.0 * p)   // 컴파일 에러: Double에는 times(Point)가 없음
}
```

`p * 2.0`은 되지만 `2.0 * p`는 되지 않는다. `2.0 * p`는 `2.0.times(p)`를 찾는데, `Double`에는 `Point`를 받는 `times`가 없기 때문이다. 수학에서는 스칼라 곱이 교환 가능하지만, Kotlin의 연산자 번역은 왼쪽 피연산자의 타입에서 함수를 찾는다. 대칭을 원한다면 **확장 함수**로 반대 방향도 정의해야 한다.

```kotlin
operator fun Double.times(p: Point) = p * this   // 2.0 * p 를 가능하게

fun main() {
    val p = Point(1.0, 2.0)
    println(2.0 * p)      // => Point(x=2.0, y=4.0)  — 이제 OK
}
```

기본 타입인 `Double`에도 확장 함수로 연산자를 추가할 수 있다는 점이 강력하다(9.2절). `Double.times(Point)` 확장이 스코프에 임포트되어 있으면 `2.0 * p`가 컴파일된다.

### 2.3 rem, 그리고 사라진 mod: 역사의 흔적

나눗셈의 나머지 연산 `%`는 `rem`으로 번역된다. 이 이름에는 사연이 있다.

> [!info] 역사 메모
> Kotlin 1.0~1.1 초기에는 `%`가 `mod`라는 이름으로 번역되었다. 그런데 `mod`라는 이름은 수학의 모듈로 연산(항상 음이 아닌 결과를 내는 floored modulo)을 연상시키는 반면, 실제 `%`의 의미는 나머지(remainder, 피제수의 부호를 따르는 truncated remainder)였다. 이름과 의미가 맞지 않는 문제를 바로잡기 위해 Kotlin 1.1에서 관례 이름을 `rem`으로 바꾸었고, `mod`는 연산자 관례에서 폐기(deprecated)되었다.
>
> 오늘날 `%`는 `rem`이다. 별도로 존재하는 `Int.mod(Int)` 같은 표준 라이브러리 함수는 floored modulo를 계산하는 **연산자가 아닌 일반 함수**이며, 부호 처리가 `rem`과 다르다.

```kotlin
fun main() {
    println((-7) % 3)        // => -1   (rem: 피제수 -7의 부호를 따름)
    println((-7).rem(3))     // => -1   (동일)
    println((-7).mod(3))     // => 2    (floored modulo: 항상 0..2 범위, 연산자 아님)
}
```

`%`와 `mod()`가 음수에서 다른 값을 낸다는 점은 실무에서 흔한 버그의 원인이다. "인덱스를 순환시키려고 `i % n`을 썼는데 `i`가 음수일 때 음수 인덱스가 나온다"는 문제는 `%` 대신 `mod()`를 써야 해결된다. 하지만 `mod()`는 연산자가 아니므로 `i mod n` 같은 기호 문법으로는 쓸 수 없고, `i.mod(n)`으로만 호출한다.

### 2.4 반환 타입이 자유롭다는 점의 활용: String의 plus

반환 타입에 제약이 없다는 점은 표준 라이브러리 곳곳에서 활용된다. 대표적인 예가 `String`의 `plus`다.

```kotlin
// 표준 라이브러리 개념
// operator fun String.plus(other: Any?): String

fun main() {
    val s: String = "count: " + 42          // String.plus(Any?) → "count: 42"
    val t: String = "point: " + Point(1.0, 2.0)  // 무엇이든 toString되어 붙음
    println(s)    // => count: 42
    println(t)    // => point: Point(x=1.0, y=2.0)
}
```

`String.plus`의 인자 타입은 `Any?`이고 반환 타입은 `String`이다. 어떤 값이든 오른쪽에 붙여 문자열을 만든다(내부적으로 `toString()`을 호출한다, [[09 - 문자와 문자열 - 유니코드와 템플릿]]). 이처럼 왼쪽과 오른쪽의 타입, 반환 타입이 모두 달라도 된다는 유연함이 연산자 관례의 표현력이다. 다만 이 유연함은 남용될 위험도 함께 안고 있다(9.5절).

## 3. 복합 대입 연산자: plusAssign과 두 갈래 번역

### 3.1 두 가지 해석이 충돌하는 지점

`a += b` 같은 복합 대입은 Kotlin에서 유일하게 **두 가지 번역이 경쟁**하는 까다로운 연산자다. 두 해석은 다음과 같다.

1. **재대입 해석**: `a = a.plus(b)`. `plus`로 새 값을 만들어 `a`에 다시 대입한다.
2. **제자리 변경 해석**: `a.plusAssign(b)`. `plusAssign`이 `a`가 가리키는 객체 자체를 변경하고 아무것도 반환하지 않는다.

컴파일러는 다음 규칙에 따라 둘 중 하나를 고르거나 에러를 낸다.

```text
a += b 의 번역 결정 규칙
────────────────────────
1. a.plusAssign(b)가 적용 가능하고, a.plus(b)로 재대입도 적용 가능하다
      → 모호성 에러 (컴파일 실패)
2. a.plusAssign(b)만 적용 가능하다
      → a.plusAssign(b)  (제자리 변경)
3. a.plus(b)로 재대입만 적용 가능하다 (a가 var여야 함)
      → a = a.plus(b)    (재대입)
4. 둘 다 불가능
      → 컴파일 에러
```

가장 주의할 함정은 규칙 1이다. `plus`와 `plusAssign`을 **둘 다** 정의하면, `a += b`가 어느 쪽을 의도한 것인지 컴파일러가 결정할 수 없어 에러가 난다.

```kotlin
class Counter(var value: Int) {
    operator fun plus(n: Int) = Counter(value + n)     // 새 객체 반환
    operator fun plusAssign(n: Int) { value += n }     // 제자리 변경, Unit 반환
}

fun main() {
    var c = Counter(0)
    // c += 5    // 컴파일 에러:
    // Assignment operators ambiguity:
    //   public final operator fun plus(n: Int): Counter
    //   public final operator fun plusAssign(n: Int): Unit
}
```

따라서 **한 타입에 `plus`와 `plusAssign`을 동시에 정의하지 말아야 한다.** 둘 중 하나만 골라야 하며, 어느 쪽을 고를지는 그 타입이 가변인지 불변인지에 따라 정한다.

### 3.2 불변 타입에는 plus, 가변 타입에는 plusAssign

관례는 명확하다. **불변(immutable) 값 타입**에는 `plus`만 정의한다. 이때 `+=`는 새 객체를 만들어 재대입한다. **가변(mutable) 컬렉션 타입**에는 `plusAssign`을 정의한다. 이때 `+=`는 컨테이너 자체를 변경한다.

```kotlin
// 불변 값 타입: plus만
data class Vec(val x: Int, val y: Int) {
    operator fun plus(o: Vec) = Vec(x + o.x, y + o.y)
}

fun main() {
    var v = Vec(1, 1)
    v += Vec(2, 3)      // v = v.plus(Vec(2,3)) — v는 새 Vec를 가리킴
    println(v)          // => Vec(x=3, y=4)
}
```

`v`가 `var`여야 `v += ...`가 재대입으로 동작한다. `val v`라면 재대입할 수 없으므로, `plus`만 있는 타입에서는 `+=`가 컴파일 에러가 된다.

표준 라이브러리가 이 원칙을 잘 보여 준다. 읽기 전용 `List`에는 `plus`만 있다(새 리스트를 반환한다). 가변 `MutableList`에는 `plusAssign`이 있다(제자리에 추가한다).

```kotlin
fun main() {
    // 읽기 전용 List: plus → 새 리스트
    var readOnly: List<Int> = listOf(1, 2)
    readOnly += 3               // readOnly = readOnly.plus(3) — 새 리스트 [1,2,3]
    println(readOnly)           // => [1, 2, 3]

    // 가변 MutableList: plusAssign → 제자리
    val mutable: MutableList<Int> = mutableListOf(1, 2)
    mutable += 3                // mutable.plusAssign(3) — 원본 변경, val이어도 OK
    println(mutable)            // => [1, 2, 3]
}
```

차이에 주목하자. `readOnly`는 `plus`로 재대입해야 하므로 `var`여야 한다. 반면 `mutable`은 `val`이어도 된다. `plusAssign`은 참조를 바꾸지 않고 내용만 바꾸기 때문이다. 여기서 [[11 - 변수와 초기화 - val과 const와 lateinit]]의 "`val`은 참조를 재대입할 수 없을 뿐, 객체 내용은 가변일 수 있다"는 원칙과 [[38 - 컬렉션 - 읽기 전용과 가변]]의 읽기 전용/가변 구분이 연산자 수준에서 드러난다.

> [!note] 명세 기준
> `plusAssign`(및 다른 `*Assign`)은 관례상 `Unit`을 반환해야 한다. 무언가를 반환하면 "제자리 변경이 아니라 재대입 대상인가?"라는 혼란이 생기고, 컴파일러도 `Unit`이 아닌 반환에 경고를 낸다. `*Assign` 계열은 부수 효과만 있고 값은 없다. `void`처럼 취급하지만, Kotlin에서는 값이 하나뿐인 타입 `Unit`이다([[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]).

### 3.3 인덱싱과 복합 대입의 조합: map[k] += 1의 함정

복합 대입이 인덱싱과 결합하면 매우 흔한 버그가 생긴다.

```kotlin
fun main() {
    val freq = mutableMapOf<String, Int>()
    val word = "apple"
    // freq[word] += 1     // 컴파일 에러 또는 런타임 NPE (아래 설명)
}
```

`freq[word] += 1`은 어떻게 번역될까? `Map`/`MutableMap`에는 `Int`에 대한 `plusAssign`이 없으므로 재대입 해석이 쓰인다.

```kotlin
// freq[word] += 1  의 번역
freq.set(word, freq.get(word).plus(1))
//              ~~~~~~~~~~~~~~
//              여기서 freq.get(word)는 Int? (없는 키면 null)
```

`MutableMap.get(key)`는 키가 없으면 `null`을 반환하므로 타입이 `Int?`다. `Int?`에는 `.plus(1)`을 바로 호출할 수 없으므로 컴파일 에러가 나거나(정확한 진단은 상황에 따라 다르다), 억지로 널 아님 단언을 끼워 넣으면 런타임에 `NullPointerException`이 난다. 초기값이 보장되지 않는 맵 카운터에서 `+=`를 그냥 쓰면 안 된다는 뜻이다.

올바른 관용구는 기본값을 명시하거나 전용 함수를 쓰는 것이다.

```kotlin
fun main() {
    val freq = mutableMapOf<String, Int>()
    for (w in listOf("a", "b", "a", "a")) {
        freq[w] = (freq[w] ?: 0) + 1          // 엘비스로 기본값 0
        // 또는:  freq.merge(w, 1, Int::plus)  // JVM 백엔드의 Map.merge
        // 또는:  freq.getOrPut(w) { 0 }.let { freq[w] = it + 1 }
    }
    println(freq)     // => {a=3, b=1}
}
```

`freq[w] = (freq[w] ?: 0) + 1`은 `get`이 반환한 `Int?`를 엘비스 연산자 `?:`([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]])로 `0`으로 보정한 뒤 `plus`를 호출한다. 인덱싱, 산술, 대입처럼 연산자 관례가 **여러 개 조합**될 때 각 단계의 타입을 정확히 추적하지 않으면 이런 널 함정에 빠진다. `set`/`get` 관례(7절)와 복합 대입 규칙이 만나는 지점의 대표적인 사례다.

## 4. 단항 연산자와 증감: unaryMinus, not, inc, dec

### 4.1 세 개의 단항 접두 연산자

피연산자 하나에 붙는 접두 연산자는 세 개다.

```text
기호   관례 이름       예시
────   ─────────       ─────────────
 +a    unaryPlus       +a  →  a.unaryPlus()
 -a    unaryMinus      -a  →  a.unaryMinus()
 !a    not             !a  →  a.not()
```

`unaryPlus`는 대개 값을 그대로 돌려주는 항등 연산이라 잘 쓰지 않지만, DSL에서 특별한 의미를 부여할 때 쓰인다. `unaryMinus`는 부호 반전에 자연스럽게 어울린다. `not`은 논리 부정인데, 반드시 `Boolean`을 반환할 필요는 없다(관례상 부정의 의미를 가진 값이면 된다).

```kotlin
data class Vec(val x: Int, val y: Int) {
    operator fun unaryMinus() = Vec(-x, -y)      // 반대 방향 벡터
    operator fun unaryPlus() = this              // 항등
}

class Toggle(val on: Boolean) {
    operator fun not() = Toggle(!on)             // 상태 반전
}

fun main() {
    val v = Vec(3, -4)
    println(-v)          // => Vec(x=-3, y=4)
    println(+v)          // => Vec(x=3, y=-4)  (this 그대로)

    val t = Toggle(true)
    println((!t).on)     // => false
}
```

단항 연산자에는 **인자가 없다.** 수신자 하나로 모든 정보가 결정된다. 반환 타입은 자유롭다(`not`은 관용적으로 같은 타입이나 `Boolean`을 반환한다).

### 4.2 증감 연산자 inc/dec: 새 값을 만들어 다시 대입한다

`++`와 `--`는 각각 `inc`와 `dec`로 번역된다. 그런데 이 연산자들은 단순히 함수를 호출하는 데서 끝나지 않고, **변수에 재대입**하는 부수 효과를 함께 일으킨다.

```kotlin
data class Counter(val n: Int) {
    operator fun inc() = Counter(n + 1)     // 새 Counter 반환 (불변)
    operator fun dec() = Counter(n - 1)
}

fun main() {
    var c = Counter(0)
    c++                    // c = c.inc()  →  c는 Counter(1)
    println(c)             // => Counter(n=1)
    ++c                    // c = c.inc()  →  c는 Counter(2)
    println(c)             // => Counter(n=2)
}
```

요점은 `inc()`가 **자신을 변경하지 않고 새 값을 반환**하며, 컴파일러가 그 반환값을 변수에 **다시 대입**한다는 것이다. 그래서 `c++`는 `c = c.inc()`다. `inc`의 반환 타입은 수신 타입에 대입할 수 있어야 한다(여기서는 `Counter` 그대로다).

이 때문에 `++`/`--`는 반드시 **`var`에만** 적용된다. `val c`라면 다시 대입할 수 없으므로 `c++`가 컴파일 에러가 된다. 이 점에서 `inc`/`dec`는 다른 산술 연산자와 다르다. `plus`는 값만 만들지만, `inc`는 값 생성과 재대입이 하나로 묶여 있다.

### 4.3 접두 ++x와 접미 x++: 표현식 값의 차이

`x++`(접미)와 `++x`(접두)는 **재대입은 같지만, 표현식으로서 내놓는 값이 다르다.**

```text
접미 x++ 의 의미론:              접두 ++x 의 의미론:
─────────────────               ─────────────────
tmp = x                         x = x.inc()
x = x.inc()                     결과값 = x         (증가 후 값)
결과값 = tmp   (증가 전 값)
```

```kotlin
fun main() {
    var a = 5
    val postfix = a++      // postfix는 증가 전 값 5, 이후 a는 6
    println("$postfix, $a") // => 5, 6

    var b = 5
    val prefix = ++b       // prefix는 증가 후 값 6, b도 6
    println("$prefix, $b")  // => 6, 6
}
```

접미 `a++`는 증가 **전** 값을 표현식의 값으로 내놓고, 접두 `++a`는 증가 **후** 값을 내놓는다. 커스텀 `inc()`를 정의한 타입에도 이 규칙이 그대로 적용된다.

```kotlin
data class Counter(val n: Int) {
    operator fun inc() = Counter(n + 1)
}

fun main() {
    var c = Counter(10)
    println(c++)     // => Counter(n=10)  (증가 전)
    println(c)       // => Counter(n=11)
    println(++c)     // => Counter(n=12)  (증가 후)
}
```

> [!note] 명세 기준
> `inc`/`dec`는 수신 객체를 **변경하지 않아야** 관례에 맞는다. 컴파일러는 `inc()`의 반환값을 변수에 대입할 뿐, 수신 객체의 상태 변경에 의존하지 않는다. 만약 `inc()` 안에서 `this`를 변경하고 `this`를 반환하도록 구현하면, 접미/접두 연산의 "이전 값" 의미가 깨진다. 같은 객체를 두 번 가리키게 되어 이전 값과 이후 값을 구별할 수 없기 때문이다.
>
> 그래서 `inc`/`dec`는 **불변 스타일로 새 값을 반환**하도록 구현해야 한다. 표준 라이브러리의 `Int.inc()`도 새 `Int`를 반환한다(원시 값이라 애초에 불변이다).

### 4.4 증감과 인덱싱의 조합

`inc`/`dec`도 인덱싱과 함께 쓸 수 있다. `a[i]++`는 `a.get(i)`로 값을 얻고, `inc`로 증가시킨 뒤, `a.set(i, ...)`로 다시 쓴다.

```kotlin
fun main() {
    val arr = intArrayOf(10, 20, 30)
    arr[1]++                       // arr.set(1, arr.get(1).inc()) 유사
    println(arr.toList())          // => [10, 21, 30]
}
```

이 조합에서도 `get`이 반환하는 값이 nullable이면 3.3절과 같은 널 함정이 생긴다. `IntArray`는 원시 배열이라 `get`이 `Int`(non-null)를 반환하므로 안전하다(38장 컬렉션 읽기 전용과 가변).

## 5. 동등성 관례: equals와 `==`의 특수한 번역

### 5.1 `==`는 equals로 번역되지만, 특별한 방식으로 번역된다

Kotlin의 `==`는 Java의 습관과 정반대다. Java에서 `==`는 참조 비교이지만, Kotlin에서는 **`==`가 `equals`(구조적 동등성)이고 `===`가 참조 동일성**이다(자세한 내용은 10장 불리언과 동등성과 동일성). 이 장에서는 `==`가 관례로서 어떻게 번역되는지, 그 **방식**만 살펴본다.

`a == b`는 단순히 `a.equals(b)`가 아니다. null 안전을 위해 다음과 같이 번역된다.

```kotlin
// a == b 의 정확한 번역
a?.equals(b) ?: (b === null)
```

풀어서 읽으면, `a`가 `null`이 아니면 `a.equals(b)`를 호출하고, `a`가 `null`이면 `b`도 `null`인지(`b === null`)를 결과로 삼는다. 그래서 `null == null`은 `true`, `null == something`은 `false`가 된다. 왼쪽이 `null`이어도 `NullPointerException`이 나지 않는다. `==`가 관례 함수를 그냥 호출하지 않고 **널 처리로 감싸서** 번역되는 이유가 이것이다.

```kotlin
fun main() {
    val a: String? = null
    val b: String? = null
    val c: String? = "x"
    println(a == b)      // => true   (null == null)
    println(a == c)      // => false  (null == "x")
    println(c == a)      // => false  ("x".equals(null))
}
```

`a != b`는 이를 부정한 `!(a == b)`로 번역된다. 그래서 `!=`를 위한 관례 함수를 따로 정의할 필요가 없다. `equals` 하나가 `==`와 `!=`를 모두 담당한다.

### 5.2 왜 equals에는 operator를 붙이지 않는가

1.2절에서 언급한 예외를 이제 자세히 살펴보자. `equals`는 관례 함수이면서도 `operator` 키워드를 붙이지 **않는다**(붙이면 에러가 난다).

```kotlin
class Money(val cents: Int) {
    // operator override fun equals(...)   // 에러: equals에 operator 불가
    override fun equals(other: Any?): Boolean =
        other is Money && other.cents == cents

    override fun hashCode(): Int = cents
}
```

`equals`가 **이미 `Any`의 멤버**이기 때문이다(5장 타입 시스템의 지형). 모든 타입은 `Any`로부터 `equals(other: Any?): Boolean`을 물려받는다. `==`를 위한 관례는 "`Any`에 정의된 `equals`를 호출한다"는 형태로 언어에 하드코딩되어 있어서, 새로 `operator`를 선언할 여지가 없다. 개발자가 할 일은 상속받은 멤버를 **오버라이드**하는 것뿐이다.

이 사실에서 몇 가지 중요한 결과가 나온다.

- **`==`에 쓸 목적으로 `equals`를 확장 함수로 정의할 수는 없다.** 확장 함수는 멤버를 오버라이드하지 못하고, 멤버가 항상 우선한다([[35 - 확장 함수와 프로퍼티]]). 설령 `operator fun Money.equals(...)` 확장을 억지로 작성하더라도, `==`는 언제나 멤버 `equals`(오버라이드한 것이든 `Any`의 기본 구현이든)를 호출한다. 확장 함수로는 `==`의 동작을 바꿀 수 없다.
- **`equals`의 인자 타입은 반드시 `Any?`여야 한다.** `equals(other: Money)`처럼 시그니처를 좁히면 오버라이드가 아니라 **오버로드**가 되고, `==`는 여전히 `Any?`를 받는 원래 `equals`를 호출한다. 10장과 [[27 - 데이터 클래스]]에서도 반복해서 나오는 함정이다.

### 5.3 다른 비교 연산자와 달리 equals는 정적 타입과 무관하다

`compareTo`(6절)나 `plus`는 왼쪽 피연산자의 **정적 타입**에서 함수를 찾는다. 하지만 `equals`는 `Any`의 멤버라서 항상 존재하며, 실제 호출은 **동적 디스패치**(가상 호출)로 이루어져 런타임 타입의 오버라이드를 호출한다. 그래서 `==`는 어떤 두 값 사이에서도 컴파일되고(둘 다 `Any?`로 비교할 수 있다), 실제 비교 로직은 왼쪽 값의 런타임 타입이 결정한다.

```kotlin
fun main() {
    val a: Any = "hello"
    val b: Any = "hello"
    println(a == b)      // => true  — String.equals가 동적으로 호출됨
}
```

이런 유연함 덕분에 `==`는 타입이 완전히 다른 두 값 사이에서도 컴파일 에러 없이 쓸 수 있다(결과가 대개 `false`일 뿐이다). Kotlin은 컴파일 시점에 두 값이 절대 같을 수 없다고 판단되는 경우(서로 관계없는 최종 타입)에만 경고를 낸다.

### 5.4 부동소수점 동등성의 함정: `==`가 항상 equals인 것은 아니다

여기에 미묘한 예외가 있다. **정적 타입이 `Float`나 `Double`일 때** `==`는 `equals`가 아니라 **IEEE 754 비교**로 번역된다. 이 차이는 `NaN`과 `-0.0`에서 드러난다.

```kotlin
fun main() {
    val nan = Double.NaN
    println(nan == nan)              // => false  (IEEE 754: NaN은 자기 자신과 같지 않음)
    println(nan.equals(nan))        // => true   (equals는 total order 사용)

    println(0.0 == -0.0)            // => true   (IEEE 754: +0.0과 -0.0은 같음)
    println((0.0).equals(-0.0))    // => false  (equals는 비트로 구별)
}
```

정적 타입이 원시 `Double`이면 `==`는 하드웨어 부동소수점 비교(`NaN != NaN`, `0.0 == -0.0`)를 쓴다.

반면 `Double`이 `Any`나 제네릭 타입으로 박싱되어 있으면(8장 박싱과 오버플로와 비트와 부호 없는 정수) `==`는 `equals`를 호출하고, `equals`는 컬렉션 정렬을 위한 **total order**(NaN을 자기 자신과 같게, -0.0을 0.0과 다르게 취급)를 쓴다. 이 이중성은 10장에서 다루는 주제이므로, 여기서는 "`==`의 번역이 정적 타입에 따라 관례를 벗어날 수 있다"는 점만 짚어 둔다.

### 5.5 오버로딩할 수 없는 논리 연산자

동등성과 함께 알아 둘 점은 **`&&`와 `||`를 오버로딩할 수 없다**는 것이다. 이 연산자에는 관례 이름이 없다. 핵심 의미가 **단축 평가(short-circuit)** 이기 때문이다. `a && b`에서 `a`가 `false`면 `b`는 아예 평가되지 않는다. 이를 일반 함수 호출로 번역하면 두 인자를 모두 평가해야 하므로 단축 평가가 깨진다. 그래서 언어는 `&&`/`||`를 오버로딩할 수 없도록 고정하고, `Boolean` 전용 특수 문법으로 남겨 두었다.

```kotlin
fun main() {
    fun sideEffect(): Boolean { println("평가됨"); return true }
    val x = false
    val r = x && sideEffect()    // "평가됨"이 출력되지 않음 — 단축 평가
    println(r)                    // => false
}
```

단축 평가 없이 양쪽을 항상 평가하는 비트 논리 `and`/`or`는 중위 함수로 따로 있다(8장 박싱과 오버플로와 비트와 부호 없는 정수). 즉 `&&`와 `and`는 서로 다르다. 전자는 단축 평가를 하고 오버로딩할 수 없으며, 후자는 단축 평가를 하지 않는 평범한 함수다.

## 6. 비교 관례: compareTo 하나로 네 개의 부등호를 만든다

### 6.1 하나의 Int가 네 개의 연산자를 만든다

`<`, `>`, `<=`, `>=` 네 개의 비교 연산자는 모두 **단 하나의 관례 함수 `compareTo`** 로 번역된다. `compareTo`는 `Int`를 반환하며, 그 부호가 대소를 결정한다.

```text
compareTo의 계약
────────────────
a.compareTo(b) < 0   →  a가 b보다 작다
a.compareTo(b) == 0  →  a와 b가 같은 순위
a.compareTo(b) > 0   →  a가 b보다 크다

기호 번역:
a < b   →  a.compareTo(b) <  0
a > b   →  a.compareTo(b) >  0
a <= b  →  a.compareTo(b) <= 0
a >= b  →  a.compareTo(b) >= 0
```

네 연산자가 하나의 함수에서 나오므로, `compareTo` 하나만 올바르게 정의하면 네 부등호가 일관되게 동작한다. 반환 타입이 `Boolean`이 아니라 `Int`인 이유도 여기에 있다. `Boolean`은 참과 거짓 두 가지만 표현하지만, 대소 비교의 결과는 "작다, 같다, 크다" 세 가지다. 이 세 가지를 하나의 값에 담으려면 부호 있는 정수가 필요하다. 하나의 3-way 비교로 네 개의 2-way 부등호를 이끌어 내는 설계다.

```kotlin
class Version(val major: Int, val minor: Int) : Comparable<Version> {
    override fun compareTo(other: Version): Int {
        val byMajor = major.compareTo(other.major)
        return if (byMajor != 0) byMajor else minor.compareTo(other.minor)
    }
}

fun main() {
    val v1 = Version(1, 4)
    val v2 = Version(1, 9)
    println(v1 < v2)        // => true   (v1.compareTo(v2) < 0)
    println(v1 >= v2)       // => false
    println(v1 == v2)       // => false  (equals — compareTo와 별개!)
}
```

### 6.2 Comparable 인터페이스와 operator의 관계

`compareTo`는 보통 `Comparable<T>` 인터페이스를 구현하면서 정의한다. `Comparable`의 `compareTo`는 **이미 `operator`로 선언되어 있으므로**, 이를 오버라이드할 때 `operator`를 다시 붙이지 않아도 자동으로 연산자가 된다(오버라이드한 함수는 `operator` 상태를 물려받는다).

```kotlin
// 표준 라이브러리 개념
public interface Comparable<in T> {
    public operator fun compareTo(other: T): Int
}
```

`Comparable`을 구현해서 얻는 이점은 비교 연산자만이 아니다. `sorted()`, `max()`, `min()`, `coerceIn()`, 범위 `in` 검사(18장 범위와 진행과 반복) 등 표준 라이브러리의 수많은 기능이 `Comparable`을 요구한다. 즉 `compareTo` 하나로 부등호 네 개와 함께 표준 라이브러리의 정렬·범위 기능 전체를 쓸 수 있게 된다.

한편 `compareTo`를 `Comparable` 없이 **확장 연산자**로 정의할 수도 있다. 하지만 그러면 부등호는 쓸 수 있어도, 정렬처럼 `Comparable`을 요구하는 기능은 쓸 수 없다. 대개는 `Comparable`을 구현하는 편이 낫다.

### 6.3 compareTo와 equals의 일관성: 계약의 함정

`compareTo`가 `0`을 반환하는 것과 `equals`가 `true`를 반환하는 것은 **논리적으로 별개**다. 컴파일러는 둘의 일관성을 강제하지 않는다. 하지만 둘이 어긋나면 정렬된 컬렉션(`TreeSet`, `TreeMap` 등)에서 미묘한 버그가 생긴다.

```kotlin
// 위험: compareTo와 equals가 불일치
class CaseInsensitive(val s: String) : Comparable<CaseInsensitive> {
    override fun compareTo(other: CaseInsensitive): Int =
        s.compareTo(other.s, ignoreCase = true)   // 대소문자 무시
    // equals는 오버라이드 안 함 → 기본 참조 동등
}

fun main() {
    val a = CaseInsensitive("Hello")
    val b = CaseInsensitive("hello")
    println(a.compareTo(b))    // => 0    (같은 순위)
    println(a == b)            // => false (참조 다름 — equals 미구현)
    // TreeSet은 compareTo로 중복을 판단하지만 HashSet은 equals/hashCode로 판단 → 불일치
}
```

`compareTo == 0`이면 순위가 같다는 뜻인데 `equals == false`라면, `TreeSet`은 두 값을 중복으로 보고 `HashSet`은 서로 다른 원소로 본다. `Comparable`을 구현할 때는 `compareTo`가 `0`을 반환하는 값들에 대해 `equals`도 `true`를 반환하도록 함께 오버라이드하는 것이 안전한 계약이다. 이 계약은 10장에서 자세히 다룬다.

> [!note] 명세 기준
> `compareTo`의 반환 타입은 반드시 `Int`여야 한다. `Boolean`이나 다른 타입을 반환하면 `operator` 검사에서 컴파일 에러가 난다. 관례상 반환값은 부호만 의미가 있고 구체적인 크기는 의미가 없다. `-1`/`0`/`1`을 쓰든 `-42`/`0`/`17`을 쓰든 부호가 같으면 동작도 같다.
>
> 흔히 `a - b` 같은 뺄셈으로 `compareTo`를 구현하고 싶어지는데, 이 방식은 **정수 오버플로**(8장 박싱과 오버플로와 비트와 부호 없는 정수)로 부호가 뒤집힐 수 있어 위험하다. `Int.compareTo`나 `compareValuesBy`를 쓰는 편이 안전하다.

## 7. 인덱싱과 호출: get, set, invoke

### 7.1 인덱스 접근: get과 set

대괄호 `[]`는 인덱스 접근 관례다. 읽기는 `get`으로, 쓰기는 `set`으로 번역된다.

```text
a[i]        →  a.get(i)
a[i, j]     →  a.get(i, j)          (임의 개수의 인덱스)
a[i] = v    →  a.set(i, v)
a[i, j] = v →  a.set(i, j, v)       (마지막 인자가 대입값)
```

인덱스 개수에 제약이 없다는 점이 강력하다. 덕분에 2차원 행렬을 `m[i, j]`처럼 자연스럽게 접근할 수 있다.

```kotlin
class Matrix(val rows: Int, val cols: Int) {
    private val data = DoubleArray(rows * cols)
    operator fun get(r: Int, c: Int): Double = data[r * cols + c]
    operator fun set(r: Int, c: Int, value: Double) { data[r * cols + c] = value }
}

fun main() {
    val m = Matrix(2, 2)
    m[0, 0] = 1.0
    m[0, 1] = 2.0
    m[1, 0] = 3.0
    println(m[0, 1])       // => 2.0
    println(m[1, 0])       // => 3.0
}
```

`set`의 번역에서 주의할 점은 **대입값이 마지막 인자**가 된다는 것이다. `a[i, j] = v`는 `a.set(i, j, v)`이지 `a.set(v, i, j)`가 아니다. 인덱스가 앞에 오고 우변의 값이 맨 뒤에 온다. `get`은 인덱스만 받고, `set`은 인덱스와 값을 받는다.

인덱스 인자의 타입도 자유롭다. `Map`의 인덱스 접근이 이를 보여 준다. 키가 `Int`가 아니어도 된다.

```kotlin
fun main() {
    val ages = mutableMapOf("Alice" to 30, "Bob" to 25)
    println(ages["Alice"])       // => 30   (Map.get("Alice"))
    ages["Carol"] = 28           // Map.set("Carol", 28)
    println(ages["Carol"])       // => 28
    println(ages["Unknown"])     // => null (없는 키는 null — §3.3의 함정 원천)
}
```

`Map.get`이 nullable을 반환한다는 점(`ages["Unknown"]`이 `null`)이 3.3절에서 본 `map[k] += 1` 함정의 근본 원인이다. `get`의 반환 타입은 도메인에 따라 정한다.

### 7.2 호출 연산자 invoke: 객체를 함수처럼 호출한다

소괄호 `()`는 호출 관례다. `a(args)`는 `a.invoke(args)`로 번역된다. 이 관례가 있기 때문에 **함수 타입의 값을 호출할 수** 있다.

```kotlin
fun main() {
    val square: (Int) -> Int = { it * it }
    println(square(5))        // => 25
    println(square.invoke(5)) // => 25  — 완전히 같은 호출
}
```

`(Int) -> Int` 타입의 값 `square`는 JVM 백엔드에서 `Function1` 인터페이스의 인스턴스이고, 그 인터페이스에는 `invoke` 메서드가 있다([[13 - 함수 타입과 람다와 함수 참조]]). `square(5)`가 `square.invoke(5)`로 번역된다는 사실이 "함수는 일급 값"이라는 성질이 실제로 구현되는 방식이다. 함수 값을 호출하는 문법 `f(x)`는 사실 `invoke`라는 연산자 관례일 뿐이다.

임의의 객체에 `invoke`를 정의하면 그 객체를 함수처럼 호출할 수 있다.

```kotlin
class Adder(val base: Int) {
    operator fun invoke(x: Int): Int = base + x
}

fun main() {
    val add10 = Adder(10)
    println(add10(5))        // => 15   (add10.invoke(5))
    println(add10(100))      // => 110
}
```

`Adder`는 함수가 아니라 클래스인데도 `add10(5)`처럼 호출된다. 상태(`base`)를 가진, 함수처럼 동작하는 객체다. 함수형 프로그래밍의 "부분 적용된 함수"나 "펑터(functor)" 개념을 클래스로 표현한 것이다.

### 7.3 companion object의 invoke: 팩토리 패턴

`invoke`의 가장 깔끔한 응용은 **동반 객체(companion object)에 정의하는 것**이다. 이렇게 하면 `ClassName(...)`이 생성자처럼 보이지만, 실제로는 팩토리 함수를 호출한다.

```kotlin
class Color private constructor(val rgb: Int) {
    companion object {
        operator fun invoke(r: Int, g: Int, b: Int): Color =
            Color((r shl 16) or (g shl 8) or b)   // shl/or는 중위 비트 함수
    }
}

fun main() {
    val red = Color(255, 0, 0)     // Color.Companion.invoke(255, 0, 0) — 생성자처럼 보임
    println(red.rgb)               // => 16711680
}
```

`Color(255, 0, 0)`은 문법적으로 생성자 호출처럼 보이지만, 실제로는 `Color.Companion.invoke(...)`를 호출한다([[28 - object와 companion - 싱글턴과 동반 객체]]). 이 패턴은 진짜 생성자를 `private`으로 감추고 팩토리 로직(캐싱, 검증, 다형적 반환 등)을 `invoke`에 넣을 때 쓴다. 호출하는 쪽은 생성자와 팩토리를 구분하지 않고 자연스럽게 `Color(...)`를 쓰면 된다.

> [!warning] 흔한 오해
> "`operator fun invoke`를 정의하면 생성자를 오버라이드하는 것"이라고 생각하기 쉽지만, 그렇지 않다. `invoke`는 생성자와 완전히 별개다. 진짜 생성자는 `constructor`로 선언하고([[21 - 클래스와 생성자]]), `invoke`는 `()` 문법으로 호출되는 메서드일 뿐이다. `ClassName(...)`이라는 표기가 우연히 겹칠 뿐이며, 컴파일러는 먼저 생성자를 찾고, 생성자가 없거나 맞지 않으면 companion의 `invoke`를 찾는다.

### 7.4 인덱싱과 호출의 결합: 도메인 문법의 표현력

`get`/`set`/`invoke`를 결합하면 도메인 특화 문법을 만들 수 있다. 예를 들어 다차원 격자에 함수형 접근을 더하는 식이다.

```kotlin
class Grid(val w: Int, val h: Int, init: (Int, Int) -> Int) {
    private val cells = IntArray(w * h) { i -> init(i % w, i / w) }
    operator fun get(x: Int, y: Int) = cells[y * w + x]
    operator fun set(x: Int, y: Int, v: Int) { cells[y * w + x] = v }
}

fun main() {
    val g = Grid(3, 3) { x, y -> x + y }   // 초기화 람다 (invoke가 아니라 생성자 인자)
    println(g[2, 2])        // => 4
    g[0, 0] = 99
    println(g[0, 0])        // => 99
}
```

이처럼 자연스러운 인덱스·호출 문법은 [[37 - 타입 안전 빌더와 DSL]]에서 DSL의 재료가 된다. 연산자 관례는 라이브러리 작성자가 Kotlin 문법 안에서 도메인 언어를 만들어 내는 핵심 도구다.

## 8. 범위와 멤버십: rangeTo, rangeUntil, contains

### 8.1 범위 연산자 rangeTo와 rangeUntil

`..`는 범위 관례 `rangeTo`로, `..<`는 `rangeUntil`로 번역된다.

```text
a..b   →  a.rangeTo(b)      (닫힌 범위, b 포함)
a..<b  →  a.rangeUntil(b)   (반열림 범위, b 제외)
```

`Int`, `Char` 등에는 이미 `rangeTo`가 정의되어 있어서 `1..10`, `'a'..'z'`가 동작한다(18장 범위와 진행과 반복). 커스텀 타입에도 `rangeTo`를 정의하면 `..`로 범위를 만들 수 있다.

```kotlin
data class Date(val epochDay: Long) : Comparable<Date> {
    override fun compareTo(other: Date) = epochDay.compareTo(other.epochDay)
    operator fun rangeTo(end: Date) = DateRange(this, end)
}

class DateRange(val start: Date, val end: Date) {
    operator fun contains(d: Date): Boolean = d >= start && d <= end   // §8.2
}

fun main() {
    val range = Date(100)..Date(200)     // Date.rangeTo(Date) → DateRange
    println(Date(150) in range)          // => true
    println(Date(250) in range)          // => false
}
```

> [!info] 역사 메모
> `..<`(그리고 관례 `rangeUntil`)는 비교적 최근에 생긴 기능이다. Kotlin 1.7.20에서 실험적(experimental) 기능으로 도입되었고, 1.8에서 안정화되었다. 그 전에는 반열림 범위를 `until` 중위 함수(`1 until 10`)로만 표현했다. `until`은 지금도 유효하지만, `..<` 기호가 더 명료해서 선호된다. `..<`가 관례 함수 `rangeUntil`로 번역된다는 점, 그리고 이 관례가 언어에 나중에 추가되었다는 점을 기억해 두면 된다.

### 8.2 멤버십 in의 번역: 피연산자 순서가 뒤집힌다

`in` 연산자는 `contains`로 번역되는데, **피연산자의 위치가 뒤집힌다**는 점이 독특하다.

```text
a in b    →  b.contains(a)      ← 수신자가 b(오른쪽), 인자가 a(왼쪽)!
a !in b   →  !b.contains(a)
```

`a in b`는 "`a`가 `b` 안에 있는가"라는 의미이므로, 자연스럽게 "`b`가 `a`를 포함하는가", 즉 `b.contains(a)`가 된다. 컨테이너 `b`가 수신자이고 원소 `a`가 인자다. 왼쪽 피연산자가 수신자가 되는 2절의 이항 산술 연산자(`a + b` → `a.plus(b)`)와 **정반대**인 관례라서 헷갈리기 쉽다.

```kotlin
class IntSet(private val elements: Set<Int>) {
    operator fun contains(value: Int): Boolean = value in elements
}

fun main() {
    val s = IntSet(setOf(1, 3, 5))
    println(3 in s)          // => true   (s.contains(3))
    println(4 in s)          // => false
    println(4 !in s)         // => true   (!s.contains(4))
}
```

`3 in s`가 `s.contains(3)`이라는 점, 즉 왼쪽 값이 인자가 되고 오른쪽 컨테이너가 수신자가 된다는 점을 기억해야 한다. `contains`의 반환 타입은 반드시 `Boolean`이어야 한다(관례로 강제된다).

### 8.3 in의 두 가지 쓰임: 멤버십과 반복

`in` 키워드는 문맥에 따라 **완전히 다른 두 관례**를 호출한다. 둘을 혼동하지 말아야 한다.

```text
문맥                      번역                   관례
──────────────────────    ──────────────────    ──────────
x in collection           collection.contains(x) contains  (멤버십 검사, Boolean)
for (x in collection)      collection.iterator()  iterator  (반복, 18장)
```

```kotlin
fun main() {
    val list = listOf(10, 20, 30)

    // 첫째 얼굴: 멤버십 — contains
    println(20 in list)           // => true  (list.contains(20))

    // 둘째 얼굴: 반복 — iterator
    for (x in list) print("$x ")  // list.iterator() 사용
    println()                     // => 10 20 30
}
```

같은 `in`이지만 `x in list`(불리언 표현식)는 `contains`를 호출하고, `for (x in list)`는 `iterator`를 호출한다. 후자의 반복 관례(`iterator`/`hasNext`/`next`)는 18장에서 다루므로, 여기서는 "`in`이 문맥에 따라 두 관례 중 하나를 호출한다"는 사실만 짚어 둔다.

### 8.4 범위와 contains의 결합: 읽기 좋은 구간 검사

`rangeTo`와 `contains`를 함께 쓰면 `x in a..b`라는 매우 읽기 좋은 구간 검사가 된다.

```kotlin
fun main() {
    val score = 85
    println(score in 0..100)         // => true   (0..100).contains(85)
    println(score in 90..100)        // => false  ("A 등급 아님")

    val c = 'k'
    println(c in 'a'..'z')           // => true   소문자 판별
}
```

`score in 0..100`은 먼저 `0.rangeTo(100)`으로 `IntRange`를 만들고, 그 범위의 `contains(85)`를 호출한다. 조건문에서 이 관용구는 `if (score >= 0 && score <= 100)`보다 훨씬 읽기 좋다. 표준 라이브러리는 `IntRange` 등의 `contains`를 원시 비교로 최적화하므로(18장), 가독성과 성능을 모두 얻을 수 있다.

## 9. 나머지 관례와 고정된 규칙: 확장 연산자, 우선순위, 남용

### 9.1 다른 장에서 자세히 다루는 관례 개괄

이 장의 중심 주제는 아니지만 반드시 언급해야 할 관례가 세 가지 있다. 빠짐없이 살펴보기 위해 여기서 개괄하고, 자세한 내용은 각 장으로 넘긴다.

**componentN: 구조 분해** (20장 구조 분해): `val (a, b) = pair`는 `pair.component1()`, `pair.component2()`를 호출한다. `operator fun component1()`, `component2()`, … 를 정의하면 그 타입을 구조 분해할 수 있다. 데이터 클래스(27장 데이터 클래스)는 이 함수들을 자동으로 생성한다. 이름이 아니라 위치를 기준으로 한다는 함정은 20장에서 다룬다.

```kotlin
data class Pair2(val first: Int, val second: String)
fun main() {
    val (n, s) = Pair2(42, "hi")     // component1(), component2()
    println("$n $s")                  // => 42 hi
}
```

**iterator: 반복** (18장 범위와 진행과 반복): `for (x in c)`는 `c.iterator()`가 반환한 이터레이터의 `hasNext()`/`next()`를 반복해서 호출한다. `operator fun iterator()`를 정의하면 커스텀 타입을 `for`로 순회할 수 있다. C 스타일 `for`가 없는 Kotlin에서 모든 반복의 기반이 되는 관례다.

**getValue/setValue: 위임 프로퍼티** (23장 위임 프로퍼티): `val x by delegate`는 `delegate.getValue(thisRef, property)`를 호출하고, `var x by delegate`에 대입하면 `delegate.setValue(thisRef, property, value)`를 호출한다. `by lazy`, `Delegates.observable` 등이 이 관례로 만들어졌다.

```kotlin
import kotlin.reflect.KProperty
class UpperCase {
    private var backing = ""
    operator fun getValue(ref: Any?, prop: KProperty<*>) = backing
    operator fun setValue(ref: Any?, prop: KProperty<*>, value: String) {
        backing = value.uppercase()
    }
}
class Demo { var name: String by UpperCase() }
fun main() {
    val d = Demo()
    d.name = "hello"
    println(d.name)      // => HELLO
}
```

### 9.2 확장 함수로서의 연산자: 다른 타입에 연산자 추가하기

연산자 관례 함수는 **확장 함수로도 정의할 수 있다**(35장 확장 함수와 프로퍼티). 이미 존재하는 타입, 즉 직접 수정할 수 없는 표준 라이브러리 타입이나 Java 타입에 연산자를 추가하는 방법은 이것뿐이다.

```kotlin
import java.math.BigInteger

// BigInteger에 이미 plus/times가 있지만, 예시로 새 연산자 추가:
operator fun BigInteger.times(n: Int): BigInteger = this * n.toBigInteger()

// 표준 라이브러리 타입 List에 연산자 확장
operator fun <T> List<T>.get(range: IntRange): List<T> = this.subList(range.first, range.last + 1)

fun main() {
    println(BigInteger.TEN * 3)       // => 30   (확장 times)
    val nums = listOf(10, 20, 30, 40, 50)
    println(nums[1..3])                // => [20, 30, 40]  (확장 get(IntRange))
}
```

확장 연산자는 2.2절의 `Double.times(Point)`처럼 **기본 타입에도** 추가할 수 있다. 대칭 연산자(양방향 곱셈 등)를 완성하거나, 다른 사람이 만든 컬렉션에 도메인에 맞는 인덱싱을 추가할 때 유용하다. 단, 확장 함수는 정적으로 디스패치되고 멤버가 우선한다는 규칙(35장)이 그대로 적용된다. 이미 멤버로 있는 연산자를 확장 함수로 "덮어쓸" 수는 없다.

### 9.3 infix 함수: 연산자는 아니지만 기호처럼 호출한다

`operator`와 자주 혼동되는 것이 **`infix`(중위) 함수**다. `infix`는 연산자 오버로딩이 아니다. 정해진 관례 이름도, 특별한 번역도 없다. 단지 **점과 괄호 없이 중위 표기로 호출할 수 있게** 해 주는 문법 편의다.

```kotlin
infix fun Int.repeatString(s: String): String = s.repeat(this)

fun main() {
    println(3 repeatString "ab")     // => ababab   (3.repeatString("ab")와 동일)
}
```

`infix` 함수가 되려면 멤버 함수나 확장 함수여야 하고, **파라미터가 정확히 하나**여야 하며, `vararg`나 기본값이 없어야 한다. 표준 라이브러리의 `to`(Pair 생성), `and`/`or`/`shl`(비트 연산), `until`/`downTo`/`step`(범위) 등이 모두 `infix` 함수다.

`operator`와 `infix`의 결정적인 차이는 다음과 같다. `operator` 함수는 **기호**(`+`, `[]`, `in` 등)로 호출되고, 번역 방식은 언어가 정의한다. `infix` 함수는 **함수 이름 그대로** 중위 표기로 호출되며 특별한 번역이 없다.

`a + b`는 관례에 따라 `plus`를 호출하지만, `a shl b`는 그냥 `shl`이라는 이름의 함수를 중위 표기로 호출한 것일 뿐이다. 1.3절에서 "비트 연산은 연산자가 아니라 중위 함수"라고 한 말의 의미가 여기서 분명해진다.

| 구분 | `operator` | `infix` |
|------|-----------|---------|
| 호출 표기 | 정해진 기호(`+`, `[]`, `..`, `in`) | 함수 이름을 중위로 (`a name b`) |
| 이름 | 언어가 고정(`plus`, `get`, …) | 자유 |
| 번역 | 언어 정의(`a+b`→`a.plus(b)`) | 없음(`a f b`→`a.f(b)`) |
| 파라미터 수 | 관례별 고정 | 정확히 1개 |
| 예 | 산술·비교·인덱싱 | `to`, `shl`, `until`, `downTo` |

### 9.4 우선순위와 결합성은 고정되어 있다

폐쇄성은 우선순위에도 적용된다. **연산자의 우선순위(precedence)와 결합성(associativity)은 언어 문법에 고정되어 있어 바꿀 수 없다.** `plus`를 어떻게 구현하든 `a + b * c`는 언제나 `a + (b * c)`다. 곱셈이 덧셈보다 먼저 묶인다는 것은 문법이 정하며, 함수 구현과는 관계가 없다.

```text
Kotlin 연산자 우선순위 (높음 → 낮음)
───────────────────────────────────
후위(postfix)      ++  --  .  ?.  ()  []
전위(prefix)       +a  -a  ++a  --a  !
곱셈류             *  /  %              (times, div, rem)
덧셈류             +  -                 (plus, minus)
범위              ..  ..<              (rangeTo, rangeUntil)
중위 함수          a infixFun b
엘비스            ?:
이름 검사          in  !in  is  !is     (contains …)
비교              <  >  <=  >=         (compareTo)
동등              ==  !=               (equals)
논리곱            &&
논리합            ||
스프레드          *args
대입              =  +=  -=  *=  /=  %=
```

이 표에서 실전에서 마주치는 함정 몇 가지가 나온다.

```kotlin
fun main() {
    // 범위(..)가 덧셈보다 낮다 → 1..n+1 은 1..(n+1)
    val n = 5
    println((1..n + 1).toList())     // => [1, 2, 3, 4, 5, 6]  (1..6)

    // 중위 함수가 덧셈보다 낮다 → 1 to 2 + 3 은 1 to (2+3)
    val pair = 1 to 2 + 3
    println(pair)                     // => (1, 5)

    // 모든 중위 함수는 같은 우선순위, 왼쪽 결합 → a to b to c 는 (a to b) to c
    val nested = 1 to 2 to 3
    println(nested)                   // => ((1, 2), 3)
}
```

`1..n+1`이 `1..(n+1)`이 되는 것은 범위 연산자의 우선순위가 덧셈보다 낮기 때문이다. `(1..n)+1`을 의도했다면 괄호가 필요하다. `1 to 2 + 3`이 `1 to 5`가 되는 것도 중위 함수의 우선순위가 덧셈보다 낮아서다.

이런 파싱은 **모든 타입에서 같다.** `to`를 어떻게 정의하든 우선순위는 바뀌지 않는다. Kotlin이 임의의 기호 연산자를 허용하지 않는 실질적인 근거가 여기에 있다(1.4절). 우선순위가 고정되어 있어야 코드를 읽는 사람이 파싱 결과를 예측할 수 있다.

> [!note] 명세 기준
> 사용자가 정의한 `infix` 함수는 모두 **하나의 우선순위 수준**(덧셈·범위보다 낮고 엘비스보다 높다)을 공유하며 **왼쪽 결합**이다. 중위 함수마다 우선순위를 다르게 지정할 방법은 없다. 그래서 `a shl b or c`는 왼쪽부터 묶여 `(a shl b) or c`가 된다(비트 연산 우선순위가 C와 다르다!). 비트 연산을 섞어 쓸 때는 괄호를 명시하는 것이 안전하다.

### 9.5 연산자 남용: "할 수 있다"와 "해야 한다"는 다르다

연산자 오버로딩에서 마지막으로 얻을 교훈은 기술이 아니라 절제다. **문법적으로 가능한 것과 의미상 옳은 것은 다르다.** `plus`를 정의하면 `+`를 쓸 수 있지만, 그 `+`가 직관에 어긋나면 코드는 읽기 어려워진다.

```kotlin
// 나쁜 예: + 가 "덧셈"과 무관한 일을 함
class User(val name: String, val friends: List<User> = emptyList()) {
    operator fun plus(other: User): User =    // "친구 추가"를 +로?
        User(name, friends + other)
}

fun main() {
    val alice = User("Alice")
    val withBob = alice + User("Bob")   // alice에 Bob을 "더한다"? 의미가 모호
    println(withBob.friends.size)        // => 1
}
```

`alice + User("Bob")`이 "친구 추가"를 뜻한다는 것은 `+`의 관례적 의미(수치나 컬렉션의 결합)에서 벗어난다. 읽는 사람은 `+`를 보면 덧셈이나 병합을 기대하지, "친구 목록에 추가"를 떠올리지 않는다. 이럴 때는 `alice.addFriend(User("Bob"))`처럼 **이름 있는 함수**가 훨씬 명료하다.

연산자를 정의해도 좋은지 판단하는 기준은 다음과 같다.

- **수학적 구조가 명확할 때**: 벡터, 행렬, 복소수, 큰 정수, 물리 단위처럼 `+`/`*`가 표준적인 수학 의미를 갖는 도메인.
- **컬렉션과 비슷한 결합이나 포함일 때**: 커스텀 컨테이너의 `in`(멤버십), `+`(원소 추가로 널리 이해되는 경우), `[]`(인덱싱).
- **함수 호출과 비슷할 때**: 상태를 가진 함수 객체의 `invoke`, 팩토리 역할을 하는 companion의 `invoke`.

그 밖의 연산, 특히 `+`가 부수 효과를 내거나(불변 관례 위반), 순서에 강하게 의존하거나, 도메인 용어로 이름을 붙이는 편이 더 자연스러운 연산은 연산자로 만들지 말아야 한다. Kotlin이 오버로딩할 수 있는 기호를 소수로 제한한 것(1.4절)과 같은 생각이다. 표현력은 절제될 때 가독성이 된다.

> [!caution] 성능 주의
> 연산자 관례 함수도 평범한 함수 호출이므로 가상 호출과 객체 할당 비용이 그대로 든다. 특히 불변 값 타입의 `plus`는 호출할 때마다 새 객체를 할당하므로, 자주 실행되는 루프(hot loop)에서 `acc = acc + delta`를 반복하면 할당이 쌓인다.
>
> 표준 라이브러리는 `Int` 같은 원시 타입의 연산자를 JVM 백엔드에서 원시 명령(`iadd` 등)으로 컴파일해 이 비용을 없앤다([[07 - 수 1 - Int와 Long과 부동소수점]]). 커스텀 타입에서 성능이 중요하다면 가변 누산기와 `plusAssign`을 고려하거나, 값 클래스([[36 - 타입 별칭과 인라인 value class]])로 박싱을 줄인다.
