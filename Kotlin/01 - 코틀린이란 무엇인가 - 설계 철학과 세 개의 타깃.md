이 노트는 "학습노트/Kotlin" 시리즈의 첫 장이다. 앞선 장이 없으므로 이어받을 내용은 없고, 대신 뒤따르는 45개 장 전체의 바탕이 되는 내용을 다룬다.

세미콜론 추론([[03 - 렉시컬 구조와 세미콜론 추론]]), 널 안전성([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]), 코루틴([[42 - suspend와 코루틴 - 언어 수준의 중단]]) 같은 세부 주제는 모두 "코틀린은 어떤 언어가 되도록 설계되었는가"라는 하나의 질문에서 출발한다. 이 장에서는 그 출발점을 정확히 정리한다.

이 장에서 바로잡으려는 통념은 두 가지이다. 첫째는 **"코틀린은 Java의 문법 설탕일 뿐"** 이라는 오해이다. 이 통념은 코틀린을 Java 위에 얹은 편의 기능 정도로 낮춰 보게 만든다. 그 결과 코틀린이 가진 별도의 타입 시스템이 전혀 보이지 않게 된다. 코틀린에서는 널 가능성이 타입에 표시되고, 변성을 선언 지점에서 표현하며, `Nothing`이라는 바닥 타입이 있고, 스마트 캐스트가 제어 흐름을 분석한다.

둘째는 **"코틀린 = JVM 언어"** 라는 오해이다. 코틀린이 JVM 생태계에서 태어난 것은 맞지만, JVM은 코틀린의 네 가지 정식 타깃 중 하나일 뿐이다. 언어 명세도 특정 런타임에 묶이지 않도록 설계되었다.

이 장에서는 두 오해를 바로잡는 것을 중심으로 언어의 역사와 철학, 세 가지 설계 축, 네 가지 컴파일 타깃과 멀티플랫폼, 언어 명세와 표준 라이브러리의 위상, Java와의 관계를 큰 그림으로 살펴본다.

컴파일러가 K2 프론트엔드와 IR 백엔드를 거치는 과정은 [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]에서, 타입 계층의 정확한 형태는 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서, 원시 타입이 컴파일되는 방식은 [[07 - 수 1 - Int와 Long과 부동소수점]]과 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]에서 다룬다. 여기서는 그 세부가 "왜 그렇게 설계되었는가"를 설명하는 공통의 맥락을 먼저 잡는다.

## 1. 코틀린은 어디서 왔는가: JetBrains와 실용주의의 기원

### 1.1 도구 회사가 언어를 만들었다

코틀린을 이해하려면 "누가, 왜 만들었는가"를 보는 것이 가장 빠르다. 코틀린은 대학 연구실이나 표준화 위원회가 아니라 **IntelliJ IDEA를 만드는 IDE 회사 JetBrains**가 만들었다. 이런 배경이 언어의 성격을 근본적으로 결정했다. JetBrains는 언어를 "논문으로 증명할 아름다운 계산 모델"로 보지 않았다. 그보다는 "매일 수백만 줄의 코드를 다루는 도구 회사가 실제로 쓸 도구"로 보았다.

> [!info] 역사 메모
> 코틀린은 2011년 7월 JetBrains가 공개했고, 2012년 Apache 2.0 라이선스로 오픈소스가 되었으며, 첫 안정 버전 1.0은 2016년 2월에 나왔다. 이름은 상트페테르부르크 근처의 **코틀린 섬**(Kotlin Island)에서 따왔다. Java가 인도네시아 자바 섬에서 이름을 딴 것을 의식한 이름이다. JetBrains의 주요 개발 거점 중 하나가 상트페테르부르크였다.

JetBrains가 코틀린을 만든 동기는 자신들의 필요였다. 주력 제품인 IntelliJ IDEA는 방대한 Java 코드베이스였다. Java는 안정적이었지만 장황했고, 당시(Java 6~7 시절)에는 언어 발전도 느렸다. 그렇다고 Scala로 옮길 수도 없었다. Scala는 표현력이 높았지만 **컴파일이 느렸고**, 이는 IDE를 만드는 회사에 치명적이었다. IDE에서 가장 중요한 것은 빠른 증분 컴파일과 정확한 코드 분석인데, 언어 자체가 이를 방해해서는 안 되었다.

그래서 요구사항은 아주 구체적이었다.

1. **Java와 100% 상호운용될 것**: 기존 IntelliJ 코드와 섞어 써야 했기 때문이다.
2. **Java만큼 빠르게 컴파일될 것**
3. **Java보다 훨씬 안전하고 간결할 것**

당시 시장에는 이 세 조건을 모두 만족하는 언어가 없었다. Scala는 (1)과 (3)은 만족했지만 (2)를 만족하지 못했고, Groovy는 동적 타입 언어라서 (3)의 정적 안전성이 약했다. 코틀린은 이 빈자리를 채우려고 만든, 필요에서 나온 언어이다.

### 1.2 실용주의라는 설계 원칙

이런 배경에서 나온 코틀린의 첫 번째이자 가장 중요한 철학이 **실용주의**(pragmatism)이다. 코틀린은 "이론적으로 완벽한 언어"를 목표로 하지 않는다. 대신 "현업 개발자가 오늘 바로 쓰기에 가장 불편이 적은 언어"를 목표로 한다. 이런 태도는 언어 곳곳에 드러난다.

예를 들어 코틀린은 순수 함수형 언어가 아니다. Haskell처럼 부수 효과를 타입으로 격리하지도 않고, 불변성을 강제하지도 않는다. `var`가 있고, 예외를 던질 수 있으며, `null`도 통제된 형태로 존재한다. 현실의 코드는 상태를 가지고, 실패하며, 값이 없는 경우도 있기 때문이다.

코틀린은 이런 현실을 부정하지 않고, 대신 **더 안전하게 다룰 수 있는 도구**를 제공한다. 불변성을 강제하는 대신 `val`을 권장하고, 검사 예외는 없앴지만 예외 자체는 남겼으며, `null`을 금지하는 대신 타입에 표시해 컴파일러가 검사하게 한다.

```kotlin
// 순수주의라면 금지했을 것들을, 코틀린은 "통제된 형태로" 허용한다
var counter = 0                    // 가변 변수 — 필요하면 쓴다
counter += 1

val list = mutableListOf(1, 2, 3)  // 가변 컬렉션 — 실용적으로 흔하다
list.add(4)

fun risky(): Int = throw RuntimeException("실패")  // 예외 — 없애지 않았다

val name: String? = null           // null — 금지가 아니라 타입에 새김
```

이 실용주의는 언어가 발전하는 방식에도 나타난다. 코틀린은 매년 새 버전을 내지만 **기존 코드를 깨뜨리지 않는 것**을 가장 중요하게 여긴다. 새 기능은 대개 실험적(experimental) 기능으로 먼저 나오고, 옵트인(opt-in)으로 검증을 거친 뒤에야 안정화된다. 이런 신중한 발전 방식은 [[46 - 멀티플랫폼과 진화와 어두운 구석]]에서 자세히 다룬다.

### 1.3 Android 덕분에 널리 퍼졌지만, Android 언어는 아니다

코틀린이 대중화된 가장 큰 계기는 **2017년 Google I/O에서 발표한 Android 공식 지원**이다. 2019년에는 Google이 "Android는 이제 Kotlin-first"라고 선언하면서 코틀린을 신규 Android 개발의 기본 언어로 삼았다. 많은 개발자가 이때 처음 코틀린을 접했고, 그래서 "코틀린 = Android 언어"라는 인상도 널리 퍼졌다.

하지만 Android는 **코틀린이 성장한 계기이지, 코틀린의 정체성을 정의하지는 않는다**. 코틀린은 Android 공식 지원보다 6년 먼저 나왔고, Android는 코틀린이 쓰이는 여러 분야 중 큰 분야 하나일 뿐이다. 코틀린 언어에는 Android를 위한 특수 문법도, 특수 타입도 없다. Android SDK는 Java로 작성된 거대한 라이브러리이고, 코틀린은 상호운용을 통해 그 라이브러리를 호출할 뿐이다.

코틀린은 서버 백엔드, 데스크톱, 데이터 과학, 빌드 스크립트(Gradle Kotlin DSL), 그리고 뒤에서 볼 멀티플랫폼까지 훨씬 넓은 분야에서 쓰인다.

이 구분은 뒤에서 "코틀린 = JVM 언어"라는 오해를 바로잡을 때 다시 중요해진다. Android가 JVM(정확히는 ART) 위에서 동작한다는 사실이 이 오해를 강화하기 때문이다. 언어의 정체성과 인기 있는 사용처를 혼동하지 말아야 한다.

## 2. 설계 철학의 네 기둥: 간결, 안전, 상호운용, 도구

JetBrains가 코틀린을 소개할 때 반복해서 쓰는 네 단어가 있다. **간결**(concise), **안전**(safe), **상호운용**(interoperable), **도구 친화**(tooling-friendly)이다. 이 네 가지는 슬로건이 아니라 설계를 결정할 때마다 실제로 쓰이는 판단 기준이다. 각 기둥을 하나씩 살펴보고, 기둥들이 서로 어떻게 충돌하고 균형을 이루는지도 보자.

### 2.1 간결: 보일러플레이트는 없애지만 마법은 아니다

간결함은 코틀린을 처음 접한 사람이 가장 먼저 느끼는 장점이다. 코틀린은 같은 일을 Java보다 훨씬 적은 코드로 표현한다.

```java
// Java — 값 객체 하나에 이만큼
public final class Point {
    private final int x;
    private final int y;
    public Point(int x, int y) { this.x = x; this.y = y; }
    public int getX() { return x; }
    public int getY() { return y; }
    @Override public boolean equals(Object o) { /* ... 장황 ... */ }
    @Override public int hashCode() { /* ... */ }
    @Override public String toString() { return "Point(x=" + x + ", y=" + y + ")"; }
}
```

```kotlin
// Kotlin — 한 줄
data class Point(val x: Int, val y: Int)
// => equals/hashCode/toString/copy/component1/component2 자동 생성
```

하지만 간결함에 대한 코틀린의 태도는 단순하지 않다. 코틀린은 코드를 **덜 쓰게 하되, 덜 명확하게 만들지는 않으려** 한다. 이 점은 코틀린이 의도적으로 채택하지 않은 기능을 보면 알 수 있다.

코틀린에서는 Scala처럼 기호 연산자를 자유롭게 정의할 수 없다. [[19 - 연산자 오버로딩과 관례]]에서 보듯 정해진 관례 이름만 오버로드할 수 있다. 암시적 변환(implicit conversion)도 없다. `Long`이 필요한 자리에 `Int`를 그대로 넣을 수 없고, `.toLong()`을 명시해야 한다(7장 Int와 Long과 부동소수점).

이렇게 하는 이유는 암시적 변환이 코드를 짧게 만들지만, **코드를 읽는 사람이 무슨 일이 일어나는지 알 수 없게** 만들기 때문이다. 코틀린의 간결함은 타이핑을 줄이는 것이지, 실제로 일어나는 일을 숨기는 것이 아니다.

> [!warning] 흔한 오해
> "간결한 언어 = 마법 같은 언어"라는 등식은 코틀린에 맞지 않는다. `data class`가 자동으로 생성하는 `equals`는 주 생성자 프로퍼티를 비교한다는, 완전히 예측 가능한 규칙을 따른다([[27 - 데이터 클래스]]). 생성된 결과를 디컴파일하면 그대로 Java 코드로 보인다. 간결함은 컴파일러가 뻔한 코드를 대신 작성해 주는 데서 나오며, 런타임 마법에서 나오지 않는다.

### 2.2 안전: 실패를 컴파일 타임으로 앞당긴다

두 번째 기둥인 안전은 코틀린의 가장 근본적인 특성이다. 핵심 아이디어는 **런타임에 발생할 오류를 가능한 한 컴파일 타임에 잡는 것**이다. 대표적인 예가 널 안전성이다. Java에서 `NullPointerException`은 런타임에, 대개 프로덕션에서 발생한다. 코틀린은 `null`이 될 수 있는 값과 없는 값을 **타입 수준에서 구분**한다. 그래서 널이 될 수 있는 값을 널 검사 없이 역참조하려 하면 **컴파일러가 거부**한다.

```kotlin
fun length(s: String): Int = s.length      // s는 절대 null 아님 — 보장됨
fun lengthN(s: String?): Int = s.length    // 컴파일 에러: s가 null일 수 있음
//                              ^ Only safe (?.) or non-null asserted (!!) calls allowed
```

이 방식이 "안전"한 이유는 이 검사에 **런타임 비용이 들지 않기** 때문이다. 널 안전성은 대부분 컴파일 타임 분석으로 이루어지며(6장 널 안전성), 컴파일된 바이트코드에는 별도의 검사 코드가 거의 들어가지 않는다. 실패할 가능성을 **타입에 표현**하고 컴파일러가 그 타입을 추적하게 하는 것이 코틀린이 안전을 확보하는 핵심 기법이다.

같은 아이디어가 언어 곳곳에서 반복된다. 봉인 클래스로 가능한 상태를 제한하고([[30 - sealed 클래스와 대수적 데이터 타입]]), `when`의 완전성 검사로 빠진 경우를 잡으며([[17 - 표현식으로서의 제어 흐름 - if와 when]]), 불변인 `val`을 기본으로 권장한다.

안전에는 **의도적인 불편함**이라는 측면도 있다. 코틀린 클래스는 기본적으로 `final`이므로 상속하려면 `open`을 명시해야 하고([[24 - 상속과 오버라이딩과 초기화 순서]]), 오버라이드할 때도 `override` 키워드가 필수이다. 이렇게 명시를 강제하면 타이핑은 늘어나지만, 실수로 상속되거나 실수로 오버라이드되는 종류의 버그를 원천적으로 막을 수 있다. 여기서 안전과 간결이 충돌하는데, 코틀린은 안전을 선택한다.

### 2.3 상호운용: 절대 타협하지 않은 제약

세 번째 기둥인 상호운용은 앞에서 보았듯 코틀린이 만들어진 전제 조건이었다. 코틀린은 **기존 Java 코드를 한 줄도 고치지 않고 그대로 호출**할 수 있어야 했고, 반대로 Java에서 코틀린 코드를 호출할 수도 있어야 했다. 이 요구는 매우 강한 제약이었다. 상호운용 때문에 코틀린은 많은 설계에서 "이상적인 선택"을 포기하고 "Java와 맞물리는 선택"을 해야 했다.

```kotlin
// Java 표준 라이브러리를 그냥 쓴다 — 래퍼도, 변환도 없다
import java.util.ArrayList
import java.time.LocalDate

val list = ArrayList<String>()   // Java 클래스를 직접 인스턴스화
list.add("hello")
val today = LocalDate.now()      // Java 8 API 그대로
```

상호운용성의 흔적은 언어 곳곳에 남아 있다. 코틀린 함수는 JVM 백엔드에서 컴파일될 때 Java가 호출할 수 있는 메서드가 된다. 코틀린 프로퍼티는 `getX()/setX()` 형태로 노출되고([[22 - 프로퍼티와 백킹 필드]]), 코틀린의 `Unit`은 Java에서 사실상 `void`처럼 보이도록 매핑된다.

코틀린이 새로 도입한 개념(널 가능성 등)도 Java와 만나는 지점에서는 **플랫폼 타입**으로 자연스럽게 다뤄지도록 설계되었다([[45 - Java 상호운용]]). 이런 세부 사항 전체는 45장에서 정리한다.

> [!note] 명세 기준
> 상호운용은 **JVM 타깃에서 가장 깊다**. Kotlin/JS는 JavaScript 생태계와, Kotlin/Native는 C/Objective-C/Swift와 상호운용한다. 즉 상호운용이라는 기둥은 Java라는 하나의 대상이 아니라 **각 타깃의 호스트 생태계와 맞물리는 것**을 뜻한다. Java 상호운용은 그중 가장 성숙한 사례일 뿐이다.

### 2.4 도구: 언어가 IDE를 배려한다

네 번째 기둥인 도구는 자주 간과되지만, JetBrains가 만든 언어답게 코틀린의 기본 구조에 반영되어 있다. 코틀린은 **컴파일러가 빠르고, 오류 메시지가 정확하며, IDE가 코드를 잘 이해할 수 있도록** 설계되었다. 문법조차 도구를 배려한다. 예를 들어 타입이 항상 이름 뒤에 오는 `val x: Int` 형식(Pascal 계열의 순서)은 파서가 왼쪽에서 오른쪽으로 읽으면서 "이것은 선언이다"를 빨리 확정할 수 있게 해 준다.

이 기둥이 가장 뚜렷하게 드러난 사례가 **K2 컴파일러**이다. 코틀린 2.0에서 기본이 된 K2는 프론트엔드를 완전히 새로 작성한 것으로, 컴파일 속도와 타입 추론의 정확도를 크게 높였다. 이는 "언어가 완성되었으니 이제 손을 뗀다"가 아니라 "도구로서의 언어를 계속 다듬는다"는 태도에서 나온 결과이다. K2의 내부 구조는 2장(K2와 IR 백엔드)에서 다룬다.

네 기둥이 항상 조화를 이루는 것은 아니다. 간결함은 때로 명시성(안전)과 부딪치고, 안전은 때로 상호운용(Java의 느슨함을 받아들여야 함)과 부딪친다. 코틀린 설계의 핵심은 이 긴장 관계 사이에서 균형을 잡은 방식에 있으며, 이후의 장들은 사실상 그 균형점을 하나씩 자세히 살펴보는 과정이다.

## 3. "Java의 문법 설탕"이라는 착각: 별도의 타입 시스템

이제 이 장에서 바로잡으려는 첫 번째 오해를 살펴보자.

### 3.1 오해의 내용

**"코틀린은 Java의 문법 설탕(syntactic sugar)일 뿐이다."** 이 오해는 그럴듯한 관찰에서 출발한다. 코틀린은 JVM 바이트코드로 컴파일되고, Java 라이브러리를 사용하며, `data class`를 디컴파일하면 평범한 Java 클래스가 나온다. 그래서 "결국 Java로 번역되는 편의 문법이 아니냐"고 생각하기 쉽다.

이 생각이 틀린 이유는 **"무엇으로 컴파일되는가"와 "어떤 언어인가"가 서로 다른 질문**이기 때문이다. C도 어셈블리로 컴파일되지만, C를 "어셈블리의 문법 설탕"이라고 부르지 않는다. TypeScript는 JavaScript로 컴파일되지만, 별개의 타입 시스템을 가진 별개의 언어이다. 컴파일 타깃이 같다는 것은 **런타임을 공유한다**는 뜻이지, **언어의 의미론(semantics)이 같다**는 뜻이 아니다.

엄밀히 말해 문법 설탕은 "같은 언어 안에서 더 짧게 쓰는 표기"이다. 예를 들어 Java의 향상된 for문은 이터레이터 루프의 문법 설탕이다. 코틀린이 문법 설탕이라면 코틀린의 모든 구성 요소가 "Java에 이미 있는 개념의 짧은 표기"여야 한다. 그런데 코틀린에는 **Java에 대응하는 개념 자체가 없는 것들**이 많다. 이것이 코틀린이 별개의 언어라는 증거이다.

### 3.2 Java에 대응하는 개념이 없는 것들: 타입 시스템

코틀린이 별개의 타입 시스템을 가졌다는 것을 Java에 없는 개념들로 확인해 보자.

**(1) 널 가능성이 타입의 일부이다.** Java에서 `String`은 언제나 `null`일 수 있고, 그 사실은 타입에 드러나지 않는다. 코틀린에서 `String`과 `String?`은 **서로 다른 타입**이다. 이것은 편의 표기가 아니라 타입 시스템을 근본적으로 확장한 것이다.

```kotlin
val a: String = "x"    // null 불가 타입
val b: String? = null  // null 가능 타입 — a와 b는 다른 타입
// b를 String이 요구되는 곳에 넣으면 컴파일 에러 (b는 String의 하위타입 아님... 정확히는 String이 String?의 하위타입)
```

Java에는 이런 구분이 없다. 대응하는 개념 자체가 없으므로, 이것은 "Java 개념의 짧은 표기"가 될 수 없다.

**(2) `Nothing` 바닥 타입.** 코틀린에는 값이 하나도 없는 타입 `Nothing`이 있고, 이 타입은 **모든 타입의 하위 타입**이다(5장 타입 시스템의 지형). `throw`의 타입이 `Nothing`이므로 아래 코드는 타입 검사를 통과한다.

```kotlin
val name: String = person.name ?: throw IllegalStateException("이름 없음")
// throw의 타입이 Nothing이고 Nothing은 String의 하위타입이므로
// 엘비스 ?:의 양변 타입이 String으로 합쳐진다
```

Java에는 바닥 타입이 없다. `throw`는 문(statement)이고, 값을 가지는 표현식이 아니다. 이것은 표기의 차이가 아니라 타입 이론 수준의 차이이다.

**(3) 선언 지점 변성(declaration-site variance).** 코틀린에서는 `class Box<out T>`처럼 클래스를 선언하는 곳에서 변성을 지정한다([[33 - 제네릭 1 - 타입 파라미터와 변성]]). Java에서는 사용하는 곳에서 `List<? extends T>` 같은 와일드카드로만 변성을 표현한다. 즉 두 언어는 제네릭 타입 시스템의 구조 자체가 다르다.

**(4) 스마트 캐스트.** 코틀린 컴파일러는 제어 흐름을 분석해서 타입을 자동으로 좁힌다(6장 널 안전성).

```kotlin
fun describe(x: Any): String {
    if (x is String) {
        return x.length.toString()  // x가 여기선 String으로 자동 인식 — 캐스트 안 씀
    }
    return "other"
}
```

Java(구버전)에서는 `if (x instanceof String)` 뒤에서도 `((String) x).length()`처럼 명시적으로 캐스트해야 했다. 스마트 캐스트는 **컴파일러의 데이터 흐름 분석**이라는 별도의 메커니즘이다.

### 3.3 Java에 대응하는 개념이 없는 것들: 언어 구조

타입 시스템만 다른 것이 아니다. 언어 구조에서도 Java에 없는 것이 많다.

| 코틀린 개념 | Java 대응 | 설명 |
|-------------|-----------|------|
| 확장 함수 | 없음 | 클래스를 고치지 않고 함수를 "붙여" 쓴다(정적 디스패치). [[35 - 확장 함수와 프로퍼티]] |
| 프로퍼티 | 필드+게터/세터의 관례일 뿐 | 코틀린 프로퍼티는 접근자를 추상화한 것이고, 백킹 필드는 필요할 때만 생긴다. 22장(프로퍼티와 백킹 필드) |
| `when` 표현식 | switch 문 | 완전성 검사, 임의 조건, 값 반환. 17장(if와 when) |
| 봉인 클래스 | 없음(Java 17에 뒤늦게 도입) | 제한된 계층 + 완전성. 30장(sealed 클래스) |
| 최상위 함수 | 없음(모든 것이 클래스 안) | 파일에 함수를 바로 선언한다. [[04 - 파일과 패키지와 선언 - 프로그램의 골격]] |
| `object` 선언 | 없음 | 언어 차원의 싱글턴. [[28 - object와 companion - 싱글턴과 동반 객체]] |
| 연산자 관례 | 없음 | `plus`, `get`, `invoke` 등 관례 이름을 오버로드한다. 19장(연산자 오버로딩과 관례) |
| 인라인 함수 | 없음 | 람다를 호출부에 펼쳐 넣는다, `reified`. [[15 - 인라인 함수와 reified]] |
| `suspend` | 없음 | 언어 수준의 중단. 42장(suspend와 코루틴) |

이 표의 어느 항목도 "Java 개념의 짧은 표기"가 아니다. 모두 코틀린이 새로 정의한 의미론이다. `if`가 표현식이라는 점부터 이미 Java와 다르다. 코틀린에는 삼항 연산자 `? :`가 없는데, 필요가 없기 때문이다. `val max = if (a > b) a else b`처럼 `if` 자체가 값을 만든다.

```kotlin
// if가 표현식 — Java의 삼항 연산자를 대체하는 게 아니라, 개념이 다르다
val max = if (a > b) a else b
val category = when {
    score >= 90 -> "A"
    score >= 80 -> "B"
    else -> "C"
}  // when도 값을 내는 표현식
```

### 3.4 그러면 왜 Java로 번역되는 것처럼 보이는가

이 오해가 쉽게 사라지지 않는 이유는 관찰이 부분적으로 맞기 때문이다. JVM 백엔드에서 코틀린은 결국 JVM 바이트코드가 되고, 그 바이트코드는 Java 컴파일러가 만드는 것과 형식이 같다. 즉 **런타임 표현은 공유**한다. 확장 함수는 정적 메서드로, 프로퍼티는 게터/세터로, `object`는 정적 필드를 가진 클래스로 컴파일된다.

중요한 점은 이것이 **컴파일 결과일 뿐, 언어의 정체성은 아니라는 것**이다. 코틀린 컴파일러는 코틀린의 풍부한 의미론을 JVM이라는 비교적 단순한 실행 모델로 **낮춰 번역(lowering)** 한다. 이 과정에서 널 가능성 정보 같은 것은 일부가 애노테이션으로 남지만 상당 부분 소거된다. 정보가 소거된다는 것은 그 정보가 **컴파일 타임에만 존재했다**는 뜻이다. 즉 Java에 없는 별도의 정적 검사 계층이 있었다는 결정적인 증거이다.

게다가 **JVM 백엔드는 코틀린의 여러 백엔드 중 하나일 뿐이다**. Kotlin/Native로 컴파일하면 처음부터 JVM 바이트코드가 나오지 않고, LLVM을 거쳐 네이티브 기계어가 나온다. "Java로 번역된다"는 관찰은 JVM 타깃에서만 부분적으로 성립하며, 이 점은 다음 절에서 다룰 두 번째 오해로 이어진다.

> [!note] 명세 기준
> 코틀린에는 **공식 언어 명세**(Kotlin language specification)가 있으며, 이 명세는 특정 백엔드(JVM)에 묶이지 않고 언어의 의미론을 정의한다. 코틀린은 Java와 별개의 문법(grammar), 별개의 타입 시스템, 별개의 이름 해석(name resolution) 규칙을 가진다. 별도의 명세가 있다는 사실 자체가 코틀린이 문법 설탕이 아니라 하나의 언어라는 증거이다. 명세의 위상은 이 장 7절에서 다룬다.

## 4. 세 개의 축: 정적 타입, 널 안전, 함수형 지향

코틀린이 별개의 언어라면, 그 언어를 떠받치는 축은 무엇인가? 세 개의 축으로 요약할 수 있다. 이 셋은 서로 독립적이지 않고, 각 축이 다른 두 축을 강화한다.

### 4.1 첫째 축: 정적 타입과 강타입

코틀린은 **정적 타입(statically typed)** 언어이다. 모든 표현식의 타입이 컴파일 타임에 결정되고 검사된다. 그러나 코틀린의 정적 타입은 **타입 추론(type inference)** 과 결합되어 있어서 동적 언어처럼 가볍게 보인다.

```kotlin
val count = 42          // 타입 명시 없지만 Int로 추론됨 — 여전히 정적 타입
val name = "Alice"      // String으로 추론
val pi = 3.14           // Double로 추론

// 하지만 타입은 확정돼 있다
count = "hello"         // 컴파일 에러: Int에 String 대입 불가
```

여기서 **타입 추론과 동적 타입은 다르다**는 점을 구분해야 한다. `var x = 5` 다음에 `x = "hello"`를 쓸 수 없는 것은 `x`의 타입이 첫 대입 순간에 `Int`로 **영구히 확정**되었기 때문이다. 이것이 JavaScript 같은 동적 언어와의 결정적인 차이이다(자매 시리즈인 JavaScript의 동적 타입과 비교하면 분명해진다). 코틀린은 "타이핑은 덜 하되 안전은 모두 챙긴다"는 실용주의를 타입 추론이라는 도구로 실현한다.

코틀린은 또한 **강타입(strongly typed)** 언어이다. 앞에서 보았듯 암시적 변환이 없다. `Int`와 `Long` 사이에도 자동 변환이 없어서 `.toLong()`을 써야 한다. 이런 엄격함 덕분에 "42 + '2' = ?"처럼 언어마다 결과가 제각각인 함정을 원천적으로 피할 수 있다.

정적 타입과 강타입은 나머지 두 축의 **전제**이다. 널 안전성이 컴파일 타임에 동작하려면 타입이 정적이어야 하고, 함수형 도구(고차 함수, 제네릭)가 안전하려면 타입이 강해야 한다.

### 4.2 둘째 축: 널 안전

두 번째 축인 널 안전은 앞의 안전 기둥에서 소개했지만, 여기서는 언어를 떠받치는 축으로서의 위상을 강조한다. 널 안전은 코틀린 타입 시스템의 **일부이며, 부가 기능이 아니다**. 모든 타입은 널이 될 수 있는 버전(`T?`)과 널이 될 수 없는 버전(`T`)이 짝을 이루고, 이 구분이 타입 계층 전체에 적용된다.

```text
타입 계층에서 nullable의 위상 (개념도)

        Any?                    ← 모든 nullable 타입의 최상위
       /    \
     Any    (null 만 담는 영역)
    /   \
 String  Int ...
    |
 String?  ← String ∪ {null}, String의 상위타입
```

이 축은 언어에 폭넓은 영향을 준다. 안전 호출 `?.`, 엘비스 `?:`, 널 단언 `!!`, 안전 캐스트 `as?` 같은 연산자는 모두 이 축에서 나온다. 스마트 캐스트도 상당 부분 널 검사와 관련되어 있다.

`lateinit`, `by lazy` 같은 초기화 도구도 "널이 될 수 없지만 나중에 값을 채운다"는 문제를 해결하려고 존재한다([[11 - 변수와 초기화 - val과 const와 lateinit]]). 널 안전이라는 축 하나가 언어 표면의 상당 부분을 결정한다. 전체 내용은 6장(널 안전성)에서 다룬다.

### 4.3 셋째 축: 함수형 지향

세 번째 축은 **함수형 지향(functional-oriented)** 이다. 여기서 주의할 단어는 "지향"이다. 코틀린은 순수 함수형 언어가 아니라(1.2절 실용주의 참조), **객체지향과 함수형을 결합한 다중 패러다임 언어**이다. 함수형을 "지향"한다는 것은 함수를 일급 시민으로 다루고 함수형 스타일을 편하게 쓸 수 있게 만들었다는 뜻이다.

```kotlin
// 함수가 일급 시민 — 변수에 담고, 인자로 넘기고, 반환한다
val square: (Int) -> Int = { x -> x * x }
val nums = listOf(1, 2, 3, 4, 5)

val result = nums
    .filter { it % 2 == 1 }   // 고차 함수에 람다 전달
    .map { it * it }          // 함수형 파이프라인
    .sum()
// => 1 + 9 + 25 = 35
```

이 축에서 나오는 기능은 다음과 같다. 함수 타입([[13 - 함수 타입과 람다와 함수 참조]]), 람다와 클로저([[14 - 클로저와 캡처]]), 고차 함수와 인라인(15장 인라인 함수와 reified), 스코프 함수([[16 - 스코프 함수와 수신 객체 관용구]]), 컬렉션의 함수형 연산([[39 - 컬렉션 연산과 함수형 파이프라인]]), 시퀀스의 지연 평가([[40 - 시퀀스와 지연 평가]])이다.

`Nothing`을 활용한 표현식 중심 설계, 즉 `if`, `when`, `try`가 모두 값을 만드는 표현식이라는 점도 함수형 지향에서 나온 결과이다. 문(statement)보다 표현식(expression)을 선호하는 것은 함수형 언어의 특징이다.

세 축을 겹쳐 보면 코틀린의 성격이 분명해진다. **정적 타입과 강타입이라는 견고한 바탕 위에 널 안전이라는 방어 장치를 두고, 함수형 지향이라는 표현력을 더한 것이다.** 그리고 실용주의가 이 모든 것을 조율하기 때문에 어느 축도 극단으로 밀어붙이지 않는다. 정적 타입이지만 추론으로 부담을 줄이고, 널 안전을 지키지만 `!!`라는 탈출구를 남기며, 함수형을 지향하지만 `var`와 부수 효과를 허용한다.

## 5. 하나의 언어, 네 개의 타깃: JVM, Native, JS, Wasm

이제 이 장에서 바로잡으려는 두 번째 오해를 살펴보자.

### 5.1 오해의 내용

**"코틀린은 JVM 언어다."** 이 오해는 첫 번째 오해보다도 널리 퍼져 있고, 여러 이유로 강화된다. 코틀린은 JVM 생태계에서 태어났고, 가장 성숙한 타깃이 JVM이며, 가장 유명한 사용처인 Android도 ART라는 JVM 계열 런타임 위에서 동작한다. 많은 튜토리얼이 JVM을 전제로 작성되고, 예제에는 `System.out.println` 같은 Java API가 자주 등장한다. 그래서 "코틀린 = JVM 위에서 동작하는 Java의 대안"이라는 이미지가 굳어졌다.

이 생각이 틀린 이유는 **JVM이 코틀린의 네 가지 정식 컴파일 타깃 중 하나일 뿐**이기 때문이다. 코틀린 컴파일러는 프론트엔드(언어 분석)와 백엔드(코드 생성)로 나뉜다. 프론트엔드는 타깃과 관계없이 공통이고, 백엔드가 여러 개이다. 같은 코틀린 소스를 JVM 바이트코드로도, 네이티브 기계어로도, JavaScript로도, WebAssembly로도 컴파일할 수 있다. 언어 명세도 특정 런타임을 전제하지 않도록 설계되었다.

> [!note] 명세 기준
> 코틀린 타입 계층의 최상위는 `java.lang.Object`가 **아니라** `kotlin.Any`이다. 이 사실 하나만으로도 두 번째 오해가 틀렸음을 알 수 있다. 코틀린이 JVM 언어라면 최상위 타입이 `Object`여야 하지만, 코틀린은 자체 타입인 `Any`를 정의하고 JVM 백엔드에서만 이를 `Object`로 매핑한다. Kotlin/Native나 Kotlin/JS에서 `Any`는 `Object`와 아무 관계가 없다. 즉 언어의 타입 시스템이 특정 런타임과 독립적으로 정의되어 있다.

### 5.2 네 타깃의 전체 구조

네 타깃을 하나씩 살펴보자. 모든 타깃은 "같은 언어, 다른 런타임"이라는 구조를 따른다.

```text
                    Kotlin 소스 (.kt)
                          |
                 프론트엔드 (K2/FIR)   ← 파싱·타입추론·진단, 타깃 무관
                          |
                    공통 IR (중간표현)
              /        |        |        \
         JVM 백엔드  Native   JS 백엔드  Wasm 백엔드
             |      백엔드       |          |
        .class      LLVM      .js        .wasm
        바이트코드   → 기계어   JavaScript  WebAssembly
             |         |         |          |
          JVM/ART   OS 직접   브라우저/    Wasm 런타임
                    실행      Node.js    (브라우저 등)
```

- **Kotlin/JVM**: 가장 성숙한 타깃이다. 코틀린 소스를 JVM 바이트코드(`.class`)로 컴파일해 JVM(또는 Android의 ART)에서 실행한다. Java 생태계 전체와 상호운용하며, 서버 백엔드, Android, 데스크톱에서 주로 쓰인다.
- **Kotlin/Native**: 코틀린을 **LLVM을 거쳐 네이티브 기계어**로 컴파일한다. JVM 없이 OS에서 직접 실행되는 실행 파일이 만들어진다. iOS, macOS, Linux, Windows, 임베디드 등을 대상으로 하며, C/Objective-C/Swift와 상호운용한다. 가비지 컬렉션은 자체 런타임이 담당한다. iOS 앱에서 코틀린 로직을 공유하는 KMP의 핵심 타깃이다.
- **Kotlin/JS**: 코틀린을 **JavaScript로 컴파일**한다. 브라우저나 Node.js에서 실행되며, npm 생태계와 DOM API와 상호운용한다. 웹 프런트엔드나 풀스택 코틀린에 쓰인다.
- **Kotlin/Wasm**: 코틀린을 **WebAssembly**로 컴파일한다. 비교적 최근에 나온 타깃으로, 브라우저 등 Wasm 런타임에서 실행된다.

> [!info] 역사 메모
> 타깃마다 성숙도가 다르다. Kotlin/JVM과 Kotlin/JS는 오래전에 안정화되었고, Kotlin/Native도 안정 타깃이다. **Kotlin/Wasm은 비교적 나중에 나온 타깃으로, 2.x 기준으로 아직 발전 중이다(Alpha 수준인 부분이 있다).** 따라서 "네 가지 정식 타깃"이라고 할 때 Wasm의 성숙도가 나머지 셋과 같지 않다는 점을 정확히 알아 두어야 한다. 제목의 "세 개의 타깃"은 성숙한 JVM/Native/JS를 강조한 표현이고, Wasm까지 세면 네 개이다.

### 5.3 "같은 언어"에서 정확히 무엇이 같은가

여기서는 정확하게 구분할 필요가 있다. "하나의 소스가 네 타깃으로 컴파일된다"는 말이 "어떤 코틀린 코드든 네 타깃에서 모두 동작한다"는 뜻은 **아니다**. 무엇이 공통이고 무엇이 타깃마다 다른지 분명히 하자.

**공통인 것(언어 코어):**

- 문법과 의미론: `val`/`var`, 클래스, 함수, 널 안전, 제네릭, 람다, `when`, 확장 함수 등 언어 자체의 규칙.
- 타입 시스템: `Any`/`Unit`/`Nothing`, 널 가능성, 변성.
- **표준 라이브러리(kotlin-stdlib)의 공통 부분**: `List`, `Map`, `String` 연산, 컬렉션 함수형 API, 코루틴 기초 등 타깃과 관계없이 정의된 부분.

**타깃마다 다른 것:**

- **호스트 플랫폼 API**: `java.util.ArrayList`는 JVM에만, DOM API는 JS에만, POSIX는 Native에만 존재한다. Java 표준 라이브러리를 사용한 코드는 JVM에서만 동작한다.
- **일부 저수준 동작**: 원시 타입 표현, 박싱 규칙, 메모리 모델([[43 - 동시성과 메모리 모델]])은 백엔드마다 다르다. 예를 들어 JVM 백엔드는 `Int`를 원시 `int`로 컴파일하지만, 다른 백엔드는 다르게 표현할 수 있다.
- **상호운용 대상**: JVM은 Java, JS는 JavaScript, Native는 C/Swift와 상호운용한다.

```kotlin
// 이 코드는 네 타깃 모두에서 돈다 — 순수 코틀린 + 공통 stdlib만 사용
fun average(nums: List<Int>): Double {
    if (nums.isEmpty()) return 0.0
    return nums.sum().toDouble() / nums.size
}

// 이 코드는 JVM 타깃에서만 돈다 — Java API 사용
import java.time.LocalDate
fun daysUntilNewYear(): Long { /* java.time 의존 */ ... }
```

이 구분은 다음 절에서 다룰 멀티플랫폼(KMP)의 전제이다. 공통 부분에 로직을 작성하고, 타깃마다 다른 부분만 따로 채우는 것이 KMP의 기본 아이디어이다.

### 5.4 이 오해가 위험한 이유

이 오해는 단지 부정확한 표현에 그치지 않고 **실제로 문제를 일으키기도** 한다. "코틀린 = JVM"이라고 믿으면 코틀린 코드를 작성할 때 무심코 JVM 전용 API를 섞어 쓰게 되고, 그러면 그 코드를 멀티플랫폼으로 옮길 수 없다. 또 "널이 될 수 있는 `Int?`는 항상 박싱된다" 같은 JVM 전용 사실을 언어 전반에 해당하는 사실로 착각하게 된다. 실제로 박싱은 JVM 백엔드의 구현 세부 사항이며, 언어 명세가 강제하는 것이 아니다(8장 박싱과 오버플로).

그래서 이 시리즈 전체는 하나의 원칙을 따른다. **JVM에서만 참인 사실은 반드시 "JVM 백엔드에서"라고 한정해서 쓴다.** "코틀린은 `Int`를 원시 타입으로 컴파일한다"가 아니라 "JVM 백엔드에서 코틀린은 `Int`를 원시 `int`로 컴파일한다"고 쓴다. 이렇게 한정하는 습관을 들이면 실무에서 이 오해를 예방할 수 있다.

## 6. 코틀린 멀티플랫폼(KMP)의 구조

타깃이 네 개라는 사실이 실제로 힘을 발휘하는 곳이 **코틀린 멀티플랫폼**(Kotlin Multiplatform, KMP)이다. KMP를 쓰면 하나의 코드베이스에서 로직을 공유하고, 플랫폼별 부분만 따로 구현할 수 있다.

### 6.1 공통 소스셋과 플랫폼 소스셋

KMP 프로젝트는 소스를 **소스셋(source set)** 으로 나눈다. `commonMain`은 모든 타깃이 공유하는 공통 코드이고, `jvmMain`/`iosMain`/`jsMain` 등은 각 타깃 전용 코드이다. 공통 코드는 공통 표준 라이브러리와 다른 공통 코드에만 의존할 수 있다.

```text
프로젝트 소스셋 구조 (개념)

  commonMain/     ← 모든 타깃 공유, 순수 코틀린 + 공통 stdlib만
     └ 비즈니스 로직, 도메인 모델, 검증 규칙 ...
        │
        │ (아래는 타깃별로 갈라짐)
        │
  jvmMain/    androidMain/    iosMain/    jsMain/
     └ Java     └ Android       └ Cocoa    └ 브라우저
       API        API             API        API
```

### 6.2 expect / actual: 공통 선언과 플랫폼 구현

공통 코드에서 플랫폼별 기능이 필요할 때 쓰는 장치가 `expect`/`actual`이다. 공통 소스셋에서 `expect`로 "이런 선언이 있다"고 약속하고, 각 플랫폼 소스셋에서 `actual`로 실제 구현을 제공한다.

```kotlin
// commonMain — "이런 게 있을 것이다"라는 기대 선언
expect fun currentPlatformName(): String

// jvmMain — JVM용 실제 구현
actual fun currentPlatformName(): String = "JVM"

// iosMain — iOS(Native)용 실제 구현
actual fun currentPlatformName(): String = "iOS"
```

이 구조 덕분에 공통 코드는 `currentPlatformName()`을 자유롭게 호출할 수 있고, 실제로 무엇이 실행될지는 컴파일 대상 타깃에 따라 정해진다. 그래서 4.3절에서 본 함수형 파이프라인 같은 로직을 한 번만 작성해 여러 플랫폼에서 재사용할 수 있다. KMP의 정확한 문법, 소스셋 계층, 계층적 공통화 등은 46장(멀티플랫폼과 진화와 어두운 구석)에서 다룬다.

### 6.3 KMP는 "모든 것을 공유"하지 않는다

여기서 흔한 과장을 경계하자. KMP는 "한 번 작성하면 어디서나 실행된다(write once, run anywhere)"는 마케팅 문구를 다시 내세운 것이 아니다. KMP의 실용주의적 입장은 **"로직은 공유하고, UI 같은 플랫폼 고유 부분은 각자 구현한다"** 는 것이다.

실제로 널리 쓰이는 패턴은 도메인 로직, 네트워크, 검증처럼 공유할 수 있는 부분을 `commonMain`에 두고, UI는 각 플랫폼의 네이티브 방식(iOS는 SwiftUI, Android는 Compose 등)으로 작성하는 것이다. 물론 Compose Multiplatform처럼 UI까지 공유하는 방식도 있지만, 이는 선택 사항이며 강제되지 않는다.

이렇게 목표를 절제한 것이 바로 코틀린 실용주의의 표현이다. "이론적으로 모든 것을 공유할 수 있다"가 아니라 "현실적으로 공유해서 이득이 되는 것만 공유한다"는 것이다.

## 7. 언어 명세의 위상: 스펙과 표준 라이브러리

"코틀린은 어떤 언어인가"라는 질문을 끝까지 따라가면 "무엇이 코틀린을 정의하는가"라는 질문에 이른다. 여기에는 언어 명세, 컴파일러, 표준 라이브러리라는 세 층위가 있다.

### 7.1 언어 명세: 무엇이 코틀린을 코틀린으로 만드는가

코틀린에는 **공식 언어 명세**(Kotlin language specification)가 있다. 이 문서는 언어의 문법, 타입 시스템, 이름 해석, 제어 흐름, 오버로드 해석 등의 규칙을 형식적으로 기술한다. 명세가 있다는 사실은 두 가지를 의미한다.

첫째, 3.4절에서 보았듯 **코틀린이 별개의 언어**라는 증거이다. 명세는 Java나 JVM을 전제하지 않고 코틀린 자체의 의미론을 정의한다.

둘째, **명세와 구현(컴파일러)이 원리상 분리**된다. 명세는 "무엇이 올바른 코틀린 프로그램이고 그 프로그램이 무슨 의미인가"를 정하고, 컴파일러는 "그 명세를 어떻게 실현하는가"를 담당한다. 실제로는 JetBrains의 참조 컴파일러가 사실상의 표준 역할을 하지만, 개념적으로 둘은 다른 층이다.

이 구분은 "언어가 보장하는 것"과 "구현이 재량으로 정하는 것"을 나누는 이 시리즈의 서술 원칙과 직접 연결된다. 명세가 보장하는 것은 단정적으로 쓰고, 컴파일러 구현에 달린 것은 "구현/백엔드에 따라"라고 한정해서 쓴다.

> [!note] 명세 기준
> 코틀린 명세는 여전히 발전 중인 문서이며, 언어의 최신 기능이 모두 즉시 반영되지는 않는다. 실무에서 코틀린의 실제 동작을 확인하는 가장 확실한 방법은 컴파일러의 실제 동작과 공식 문서이다. 그럼에도 명세가 별도로 존재한다는 사실은 코틀린이 "구현이 곧 정의"인 임시방편 언어가 아니라 **정의된 언어**임을 보여 준다.

### 7.2 컴파일러: 명세를 실현하는 도구

두 번째 층은 컴파일러이다. 앞에서 여러 번 언급한 K2 컴파일러가 현재의 참조 구현이다. 컴파일러가 프론트엔드(언어 이해)와 백엔드(코드 생성)로 나뉘고, 백엔드가 네 타깃으로 갈라진다는 것은 5절에서 보았다.

이 장에서 중요한 것은 위상에 관한 한 가지 사실이다. **컴파일러는 언어가 아니다.** 코틀린이라는 언어는 명세로 정의되고, 컴파일러는 그 언어를 특정 런타임 위에 구현한다. 그래서 "JVM 백엔드가 `Int`를 원시형으로 만든다"는 컴파일러(그것도 특정 백엔드)에 관한 사실이지, 언어에 관한 사실이 아니다. 컴파일러의 실제 구조는 2장(K2와 IR 백엔드)에서 다룬다.

### 7.3 표준 라이브러리(kotlin-stdlib): 언어인가 라이브러리인가

세 번째 층은 조금 미묘하다. **표준 라이브러리 `kotlin-stdlib`** 는 `List`, `Map`, `String`의 확장 함수, `let`/`run` 같은 스코프 함수, 컬렉션 연산, 범위(range), `Pair`/`Triple`, `Result` 등 우리가 "코틀린 코드"라고 여기는 것의 대부분을 제공한다. 그렇다면 표준 라이브러리는 언어의 일부인가, 아니면 함께 제공되는 라이브러리일 뿐인가?

답은 **"둘 사이"** 이다. 정확히 말하면 **언어 문법 자체는 stdlib를 필요로 하지 않지만, 몇몇 언어 기능은 stdlib의 특정 타입과 맞물려 있다.** 예를 들면 다음과 같다.

- `for (x in collection)`의 반복은 언어의 `for` 문법이지만, `collection`이 `Iterator`를 제공해야 하고 그 `Iterator`/`Iterable`은 stdlib에 정의되어 있다.
- 문자열 템플릿 `"$name"`은 언어 문법이지만, 결과 타입 `String`은 stdlib(정확히는 코어 타입)에 속한다.
- 위임 프로퍼티 `by lazy`에서 `lazy`는 stdlib 함수이다([[23 - 위임 프로퍼티]]).

그래서 코틀린을 배운다는 것은 사실 **언어 코어와 stdlib**를 함께 배우는 것이다. 이 시리즈도 그렇게 다룬다. 예를 들어 컬렉션([[38 - 컬렉션 - 읽기 전용과 가변]])이나 스코프 함수(16장 스코프 함수와 수신 객체 관용구)는 엄밀히 말하면 라이브러리이지만, 언어를 사용하는 데 꼭 필요한 부분이므로 언어처럼 다룬다.

> [!warning] 흔한 오해
> "`listOf`, `let`, `map`은 언어 키워드다"라고 생각하기 쉽지만, 이들은 모두 **stdlib의 함수**이다. `let`은 `public inline fun <T, R> T.let(block: (T) -> R): R`라는 확장 함수이고(35장 확장 함수와 프로퍼티), `map`도 컬렉션 확장 함수이다.
>
> 언어 키워드(`val`, `fun`, `when`, `is`, `in`)와 라이브러리 함수를 구분하는 것이 언어를 정확히 이해하는 첫걸음이다. 이 경계는 3장(렉시컬 구조와 세미콜론 추론)에서 키워드를 분류하며 자세히 정리한다.

한편 stdlib에도 타깃마다 다른 부분이 있다(5.3절). 공통 부분은 모든 타깃에서 쓸 수 있고, `kotlin.io`의 파일 API처럼 특정 타깃에서만 의미가 있는 부분은 그 타깃의 stdlib에만 있다.

## 8. Java와의 관계: 대체가 아니라 공존

코틀린을 이해하는 마지막 큰 축은 Java와의 관계이다. 이 관계는 코틀린이 어떤 언어가 될지를 결정한 가장 큰 요인이었다.

### 8.1 코틀린은 Java를 몰아내려 하지 않았다

흔히 "코틀린이 Java를 대체한다"고 이야기하지만, 이는 코틀린의 실제 설계 철학을 오해한 것이다. 코틀린의 목표는 **Java를 몰아내는 것이 아니라 Java와 공존하는 것**이었다. 이는 이상이 아니라 필연이었다. 앞에서 보았듯 JetBrains는 자신들의 거대한 Java 코드베이스와 섞어 쓰려고 코틀린을 만들었다. Java 코드를 모두 버리고 코틀린으로 다시 작성하는 것은 처음부터 선택지가 아니었다.

공존이라는 전제가 코틀린 설계에 얼마나 큰 영향을 주었는지 보자. 코틀린이 Java를 완전히 대체할 생각이었다면 훨씬 급진적으로 설계할 수 있었다. Java와 다른 컬렉션 프레임워크, Java와 다른 예외 모델, Java 타입과 매핑되지 않는 자체 타입 시스템을 만들 수도 있었다.

하지만 코틀린은 그렇게 하지 않았다. 코틀린의 `List`는 Java의 `List`와 상호운용되고, 코틀린의 예외는 Java의 `Throwable` 계층을 그대로 사용하며([[41 - 예외와 Nothing]]), 코틀린의 `Int`는 JVM에서 Java의 `int`/`Integer`와 자연스럽게 오간다. 상호운용이라는 제약 때문에 자유롭게 설계할 수는 없었지만, 바로 그 제약이 코틀린을 "당장 쓸 수 있는 언어"로 만들었다.

### 8.2 공존이 남긴 흔적: 플랫폼 타입

공존에는 대가가 있었다. 가장 큰 대가가 **플랫폼 타입(platform type)** 이다. Java 코드에는 (널 애노테이션이 없는 한) 널 가능성 정보가 없다. Java 메서드가 `String`을 반환할 때, 코틀린은 그 값이 `null`일 수 있는지 알 수 없다. 코틀린이 이 문제를 처리하는 방법으로는 세 가지 선택지가 있었다.

1. **모두 널이 될 수 없는 타입으로 취급**: Java가 실제로 `null`을 반환하면 예상하지 못한 NPE가 발생한다. 게다가 안전하다는 착각을 준다.
2. **모두 널이 될 수 있는 타입으로 취급**: 모든 Java 호출에 `?.`나 `!!`를 붙여야 한다. 상호운용이 매우 번거로워진다.
3. **"알 수 없는 타입"으로 취급하고 개발자에게 맡김**: 이것이 플랫폼 타입 `T!`이다.

코틀린은 3번을 선택했다. 플랫폼 타입 `T!`는 널 가능성 검사를 미루는 타입이다. 널이 될 수 없는 타입처럼 쓸 수도 있고 널이 될 수 있는 타입처럼 쓸 수도 있지만, 실제 값이 `null`이면 사용하는 지점에서 NPE가 발생한다(45장 Java 상호운용). 이것은 코틀린의 널 안전성에 난 구멍이지만, **의도된 실용적 타협**이다. 완벽한 안전을 고집했다면(2번) Java 상호운용이 불가능했을 것이고, 그랬다면 코틀린은 만들어지지도 못했을 것이다.

```kotlin
// Java의 System.getProperty(String)은 String을 반환하지만 null일 수 있다
// 코틀린은 이를 String! (플랫폼 타입)으로 본다
val v = System.getProperty("user.name")  // 타입: String! (널 가능성 미정)
val len = v.length   // 컴파일러가 막지 않음 — 하지만 v가 null이면 여기서 NPE
```

플랫폼 타입은 "널 안전성은 런타임 검사다"라는 오해와 "플랫폼 타입은 안전하다"라는 오해가 함께 걸리는 지점이다. 코틀린 코드 안에서 널 안전은 컴파일 타임에 보장되지만, Java 경계를 넘는 순간 그 보장이 미뤄지고 런타임 NPE가 발생할 수 있게 된다. 자세한 내용은 6장(널 안전성)과 45장(Java 상호운용)에서 나누어 다룬다.

### 8.3 공존이 남긴 다른 흔적

플랫폼 타입 말고도 공존의 흔적은 많다. 코틀린에 **검사 예외(checked exception)가 없다**는 점(41장 예외와 Nothing)도 공존과 관련이 있다. 코틀린은 검사 예외를 강제하지 않지만, Java와 상호운용할 수 있도록 `@Throws` 애노테이션으로 Java 쪽에 예외 시그니처를 노출하는 수단을 남겼다.

코틀린 프로퍼티가 JVM에서 `getX()/setX()`로 컴파일되는 것(22장 프로퍼티와 백킹 필드)도 Java에서 코틀린 프로퍼티를 자연스럽게 쓸 수 있게 하려는 배려이다. `@JvmStatic`, `@JvmField`, `@JvmName`, `@JvmOverloads` 같은 애노테이션은 모두 "코틀린을 Java에서 편하게 쓸 수 있게 하는" 상호운용 도구이다(45장 Java 상호운용).

이 모든 사례에서 알 수 있는 점은 **코틀린의 많은 설계가 "이상적인 선택"과 "Java와의 공존" 사이에서 절충한 결과**라는 것이다. 코틀린을 깊이 이해한다는 것은 어떤 설계가 순수한 언어 철학에서 나왔고, 어떤 설계가 Java와의 타협에서 나왔는지를 구분할 수 있다는 뜻이다. 이 구분은 앞으로 여러 장에서 반복해서 등장한다.

## 9. 코틀린은 왜 이런 모습인가: 트레이드오프와 경계

마지막으로 지금까지 살펴본 내용을 하나로 묶고, 이 장에서 **다루지 않은** 주제의 경계를 분명히 하자.

### 9.1 세 가지 힘이 합쳐진 결과로서의 코틀린

코틀린의 모든 설계는 세 가지 힘이 합쳐진 결과이다.

- **실용주의**: "현업 개발자가 오늘 쓸 언어"라는 목표가 이론적 순수함보다 앞선다. 그래서 `var`, 예외, `null`, `!!`가 모두 남았다. 코틀린이 순수 함수형 언어가 아니라 다중 패러다임 언어인 이유이다.
- **안전에 대한 집착**: "런타임 오류를 컴파일 타임에 잡는다"는 원칙이 언어의 기본 구조를 이룬다. 널 안전, 봉인 클래스, `when` 완전성 검사, 기본 `final`, 명시적 `override`는 모두 이 원칙을 표현한 것이다. 실용주의와 안전은 자주 부딪치는데, 코틀린은 대개 안전 쪽으로 조금 기운다. 그러나 `!!`라는 탈출구를 남긴 것처럼 극단으로 가지는 않는다.
- **상호운용과 이식성**: Java와 공존해야 한다는 제약이 초기 설계를 결정했고, 나중에는 네 타깃으로의 이식성이 언어를 특정 런타임에 묶이지 않게 만들었다. `Any`가 `Object`가 아니라는 점, stdlib에 공통 부분이 있다는 점, JVM 전용 사실을 언어 전반의 사실과 구분해야 한다는 점이 모두 이 힘에서 나왔다.

```text
코틀린 설계를 빚은 세 힘 (요약)

  실용주의 ──────┐
  "당장 쓸 언어"  │
                ├──→  다중 패러다임, 통제된 가변성/예외/null,
  안전에의 집착 ──┤       타입에 새긴 안전, 명시 강제,
  "오류를 컴파일   │       Java 공존 + 4개 타깃 이식성
   타임으로"      │
                │
  상호운용/이식성 ┘
  "Java 공존, 멀티타깃"
```

### 9.2 이 장에서 다루지 않은 것

이 장은 코틀린의 전체 모습을 큰 그림으로 그렸을 뿐, 각 주제의 세부는 깊이 다루지 않았다. 세부 주제는 다음 장들에서 다룬다.

- **컴파일러가 실제로 동작하는 방식**: K2 프론트엔드, FIR, IR, 백엔드별 코드 생성, 증분 컴파일, 컴파일러 플러그인은 2장(K2와 IR 백엔드)에서 다룬다.
- **문법의 최소 단위**: 토큰, 키워드 분류, 세미콜론 추론, 리터럴은 3장(렉시컬 구조와 세미콜론 추론)에서 다룬다.
- **타입 계층의 정확한 형태**: `Any`/`Unit`/`Nothing`의 위상과 nullable이 타입 이론에서 차지하는 자리는 5장(타입 시스템의 지형)에서 다룬다.
- **널 안전의 세부 동작**: `?.`/`?:`/`!!`/`as?`, 스마트 캐스트 알고리즘, 플랫폼 타입은 6장(널 안전성)에서 다룬다.
- **원시 타입과 박싱의 실제**: "코틀린에는 원시 타입이 없다"는 말의 정확한 의미는 7장(Int와 Long과 부동소수점)과 8장(박싱과 오버플로)에서 다룬다.
- **Java 상호운용 전반**: 플랫폼 타입, 애노테이션, 이름 맹글링은 45장(Java 상호운용)에서 다룬다.
- **멀티플랫폼의 구체적 문법과 언어의 발전**: `expect`/`actual`, 소스셋 계층, 옵트인, 안정성 등급은 46장(멀티플랫폼과 진화와 어두운 구석)에서 다룬다.
