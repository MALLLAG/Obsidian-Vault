**이 장이 답하는 질문:**

- 코틀린은 왜 클래스와 멤버를 기본으로 `final`로 봉인하고, `open`을 명시하라고 강요하는가? 이것은 자바에 대한 어떤 반성인가?
- `override`가 선택이 아니라 *의무*인 이유는 무엇이며, 그 강제가 막아 주는 버그는 어떤 종류인가?
- `val`을 `var`로 오버라이드할 수 있는데 그 역은 왜 불가능한가? 프로퍼티를 오버라이드한다는 것은 필드를 오버라이드하는 것인가, 접근자를 오버라이드하는 것인가?
- 상위 클래스 생성자와 하위 클래스 생성자, `init` 블록, 프로퍼티 초기화자는 정확히 어떤 순서로 실행되는가?
- 생성자 안에서 `open` 멤버를 호출하면 왜 위험한가? "가상 함수를 부르면 결국 내 오버라이드가 실행되니 안전하다"는 직관은 어디서 무너지는가? (M47)
- `super.f()`는 정확히 무엇을 호출하며, 그 호출은 정적으로 묶이는가 동적으로 묶이는가?
- 멤버 함수의 동적 디스패치는 기계 수준에서 어떻게 일어나고, 왜 확장 함수는 그렇게 되지 않는가?
- 모든 클래스의 뿌리인 `Any`는 정확히 무엇을 선언하며, `equals`/`hashCode`/`toString`을 오버라이드할 때 무엇을 계약으로 짊어지는가?

[[21 - 클래스와 생성자]]에서 우리는 *하나의* 클래스가 자기 자신을 초기화하는 메커니즘을 끝까지 파고들었다. 주 생성자와 부 생성자, `init` 블록과 프로퍼티 초기화자가 한 클래스 안에서 어떤 순서로 인터리빙되는지, 그리고 "부 생성자가 있으면 주 생성자 초기화가 안 돈다"는 오해(M46)가 왜 틀렸는지를 확정했다. 그러나 그 논의에는 천장이 있었다. 계층이 없었다. 모든 예제는 상위 타입 없이 홀로 서 있는 클래스였다.

이 장은 그 천장을 뚫는다. 클래스가 다른 클래스를 *물려받을* 때 벌어지는 일—`open`으로 봉인을 여는 문법, `override`로 상위의 행동을 갈아 끼우는 규칙, `super`로 덮인 구현을 되불러오는 통로, 그리고 무엇보다 **초기화가 상위에서 하위로 흐르는 순서**—를 기계 수준에서 해부한다. 이 장의 심장은 두 개다. 하나는 초기화 순서를 확정하는 실행 다이어그램이고, 다른 하나는 그 순서가 낳는 이 장의 소유 오개념 M47—"오버라이드한 멤버를 상위 생성자에서 불러도 안전하다"—을 정면으로 반박하는 일이다.

경계를 못박아 두자. 여기서는 **클래스 대 클래스**의 단일 상속과 그 위에서의 오버라이딩·초기화를 다룬다. 인터페이스의 다중 상속, 백킹 필드 없는 인터페이스 프로퍼티(M37), 다이아몬드 충돌의 완전한 해소는 [[25 - 인터페이스]]가 소유한다—이 장에서는 `super<A>.f()` 문법을 맛보기로만 건드린다. 프로퍼티가 어떻게 백킹 필드로 컴파일되는지(M35)는 [[22 - 프로퍼티와 백킹 필드]]의 영역이고, `val`이 재대입 불가일 뿐 불변이 아니라는 사실(M3)은 [[11 - 변수와 초기화 - val과 const와 lateinit]]이 정본이다. 상속을 아예 쓰지 않고 위임으로 대체하는 `by`는 [[32 - 클래스 위임]]으로 위임한다(말장난이 아니라 실제로 그렇다). 이 장은 상속이라는 도구의 *날카로운 날*—그 강력함과 그 위험—에 집중한다.

논증의 궤적은 이렇다. 먼저 코틀린이 왜 상속을 기본 봉인했는지, 그 결정 뒤에 있는 "취약한 기반 클래스(fragile base class)" 문제를 짚는다. 그다음 `open`/`abstract`/`override`의 삼각형을 문법·의미론 양면에서 해부하고, 프로퍼티 오버라이딩이 접근자 오버라이딩임을 확인한다. `super`의 정적 성격을 밝힌 뒤, 이 장의 절정인 초기화 순서로 들어가 상위→하위 흐름을 다이어그램으로 확정하고, 그 흐름 위에서 M47 함정이 어떻게 발생하는지를 실행 로그로 재현한다. 마지막으로 동적 디스패치의 기계(vtable, `invokevirtual`), `Any`의 세 멤버, 그리고 "상속보다 조합"이라는 오래된 지혜로 마무리한다.

## 1. `final`이 기본값인 이유 — 취약한 기반 클래스 문제

### 1.1 봉인된 채로 태어나는 클래스

코틀린에서 아무 수식 없이 선언한 클래스는 상속할 수 없다.

```kotlin
class Animal
class Dog : Animal()   // 컴파일 에러: This type is final, so it cannot be inherited from
```

멤버도 마찬가지다. 클래스를 어찌어찌 `open`으로 열어도, 그 안의 함수와 프로퍼티는 여전히 봉인된 채다.

```kotlin
open class Animal {
    fun sound(): String = "..."         // 암시적 final
}
class Dog : Animal() {
    override fun sound(): String = "멍"  // 컴파일 에러: 'sound' in 'Animal' is final, cannot be overridden
}
```

상속 계층을 만들려면 두 곳에서 명시적으로 봉인을 풀어야 한다. 클래스 앞에 `open`, 그리고 오버라이드를 허용할 각 멤버 앞에 `open`.

```kotlin
open class Animal {
    open fun sound(): String = "..."
}
class Dog : Animal() {
    override fun sound(): String = "멍"  // => OK
}
```

이것은 자바와 정반대의 기본값이다. 자바에서 클래스와 메서드는 기본으로 오버라이드 *가능*하고, 막으려면 `final`을 붙여야 한다. 코틀린은 그 정책을 뒤집었다. 왜?

### 1.2 "상속을 위해 설계하고 문서화하라, 아니면 금지하라"

이 뒤집기의 사상적 뿌리는 조슈아 블로크(Joshua Bloch)의 『이펙티브 자바』 항목 19—"상속을 위해 설계하고 문서화하라, 그럴 수 없다면 상속을 금지하라"—다. 핵심은 **상속이 캡슐화를 깨는 위험한 결합**이라는 통찰이다.

문제의 이름은 취약한 기반 클래스(fragile base class). 어떤 클래스 `Base`를 누군가 상속해 `Derived`를 만들었다고 하자. `Base`의 저자가 훗날 내부 구현을 "겉보기엔 무해하게" 바꾼다. 예컨대 어떤 공개 메서드가 내부적으로 다른 공개 메서드를 호출하도록 리팩터링한다. 그 순간, 그 두 메서드를 모두 오버라이드한 `Derived`는 자기가 예상하지 못한 방식으로 자기 오버라이드가 재진입(re-entrant)당하면서 깨진다. `Base`의 저자는 API 시그니처를 하나도 바꾸지 않았는데도.

고전적 예를 코틀린으로 옮겨 보자. 원소 추가를 세는 컬렉션이다.

```kotlin
open class CountingSet<T> {
    var addCount = 0
        private set
    private val backing = mutableSetOf<T>()

    open fun add(element: T): Boolean {
        addCount++
        return backing.add(element)
    }
    open fun addAll(elements: Collection<T>): Boolean {
        addCount += elements.size          // 여기서 세고
        return backing.addAll(elements)    // 내부적으로 add를 부를 수도, 안 부를 수도
    }
}
```

만약 어떤 하위 클래스가 `add`만 오버라이드해 로그를 남기고, `addAll`의 내부 구현이 `add`를 반복 호출하도록 되어 있다면, 원소가 실제로 두 번 세어질 수 있다. 반대로 `addAll`이 `add`를 부르지 않게 구현을 바꾸면 하위 클래스의 로그가 갑자기 안 남는다. **하위 클래스의 정확성이 상위 클래스의 문서화되지 않은 내부 호출 패턴(self-use)에 의존**하게 된 것이다. 이 의존은 컴파일러가 잡아 주지 않는다. 시그니처는 완벽히 호환되니까.

블로크의 처방은 두 갈래였다. (1) 상속을 정말 의도한다면, 어떤 메서드가 어떤 메서드를 내부적으로 호출하는지를 문서로 남기고(그 self-use 패턴 자체가 API의 일부가 된다), (2) 그럴 의도가 없다면 클래스를 `final`로 잠가 상속을 아예 막아라. 자바는 (2)를 *옵트인*으로 두었다. 즉 개발자가 명시적으로 `final`을 쳐야만 잠긴다. 현실에서 그 손가락은 게을렀고, 잠기지 않은 클래스가 온 세상에 상속되어 취약해졌다.

코틀린은 (2)를 *기본값*으로 만들었다. "상속을 허용한다"는 것은 이제 명시적 의사 표시—`open`—를 요구하는 신중한 결정이 되었다. 봉인이 기본이므로, `open`이라는 단어가 붙은 클래스를 보면 "이 저자는 상속을 *의도했고*, 아마도 self-use 패턴을 고려했겠구나"라고 신뢰할 근거가 생긴다.

> **역사 메모**: 이 결정은 논쟁적이었다. 스프링(Spring)처럼 런타임에 클래스를 프록시로 감싸(subclass 기반 AOP) 확장하는 자바 프레임워크들은 코틀린 클래스가 `final`이라 프록시를 만들 수 없어 곤란을 겪었다. 그래서 코틀린은 `all-open` 컴파일러 플러그인(과 스프링 전용 `kotlin-spring`)을 제공한다—특정 애노테이션이 붙은 클래스를 컴파일 시점에 자동으로 `open`으로 바꿔 주는 플러그인이다. 언어의 기본은 안전(봉인)으로 두되, 프레임워크의 요구는 플러그인으로 예외 처리한 절충이다.

### 1.3 봉인의 이득과 비용

봉인이 주는 것은 **불변식(invariant)의 보호**다. `final` 클래스의 저자는 자기 메서드가 절대 오버라이드되지 않음을 안다. 따라서 한 메서드가 다른 메서드를 호출할 때 그 호출이 항상 *자기가 작성한* 구현으로 간다고 확신할 수 있다. 이 확신이 있어야 클래스 내부의 논리를 자유롭게 리팩터링할 수 있다. 봉인은 미래의 자기 자신에게 주는 리팩터링 자유의 보증서다.

비용은 **유연성의 선불 지불**이다. 라이브러리를 쓰는 사람이 "이 클래스의 이 메서드 하나만 살짝 바꿔서 쓰고 싶은데"라고 할 때, 저자가 `open`을 안 열어 두었으면 상속으로는 손댈 수 없다. 이 비용을 코틀린은 다른 도구들로 상쇄한다. 확장 함수([[35 - 확장 함수와 프로퍼티]])로 기존 타입에 기능을 덧붙이고, 클래스 위임([[32 - 클래스 위임]])으로 상속 없이 행동을 조합하며, 인터페이스([[25 - 인터페이스]])로 계약만 공유한다. 상속은 이 도구 상자에서 *가장 강하지만 가장 결합도 높은* 도구이고, 코틀린은 그것을 기본 손에 쥐여 주는 대신 서랍에 넣어 두었다.

## 2. `open`·`abstract`·`override` — 상속 문법의 삼각형

### 2.1 `open` 멤버와 `override`의 의무

세 키워드가 상속의 문법 골격을 이룬다. `open`(오버라이드를 *허용*), `abstract`(구현 없이 오버라이드를 *강제*), `override`(상위 멤버를 갈아 끼운다는 *선언*). 먼저 `open`과 `override`의 짝을 보자.

```kotlin
open class Shape {
    open fun area(): Double = 0.0
    open val name: String = "도형"
}

class Circle(val radius: Double) : Shape() {
    override fun area(): Double = Math.PI * radius * radius
    override val name: String = "원"
}
```

코틀린에서 `override`는 **선택이 아니라 의무**다. 상위의 `open` 멤버와 시그니처가 일치하는 멤버를 하위에서 선언하면서 `override`를 빠뜨리면 컴파일되지 않는다.

```kotlin
class Square(val side: Double) : Shape() {
    fun area(): Double = side * side  // 컴파일 에러: 'area' hides member of supertype 'Shape' and needs 'override' modifier
}
```

이 강제가 막아 주는 버그는 두 방향이다.

**첫째, 의도치 않은 오버라이드.** 자바에서는 상위에 있는 줄도 모르는 메서드와 이름·시그니처가 우연히 겹치면 조용히 오버라이드가 일어난다. 상위 클래스가 나중에 그 이름의 메서드를 추가해도 마찬가지다. 코틀린은 `override` 없이는 그런 일이 불가능하다. 우연한 겹침은 "override 키워드가 필요하다"는 에러로 즉시 드러난다.

**둘째, 오버라이드했다고 착각한 오타.** 반대로, 오버라이드할 *의도*로 `override`를 붙였는데 상위에 그런 멤버가 없으면(오타로 `area`를 `aera`로 썼다든지) 역시 컴파일 에러다.

```kotlin
class Triangle : Shape() {
    override fun aera(): Double = 0.0  // 컴파일 에러: 'aera' overrides nothing
}
```

자바에서는 `@Override` 애노테이션이 이 역할을 하지만, 그것은 *권장* 사항이라 붙이는 걸 잊으면 방어가 사라진다. 코틀린은 애노테이션이 아니라 *키워드*로 승격시켜 강제했다. 두 방향 모두에서 "이름은 같은데 의도가 어긋난" 상황이 컴파일 타임에 걸린다. 이것이 널 안전성(M7)과 같은 결의 설계 철학—런타임에 터질 오류를 타입 시스템으로 앞당겨 잡는—이다.

### 2.2 `abstract` — 구현 없는 계약

`abstract`는 "이 멤버는 여기서 구현하지 않는다, 하위가 반드시 구현하라"는 선언이다. 추상 멤버를 하나라도 가지면 클래스도 `abstract`여야 하고, 추상 클래스는 인스턴스화할 수 없다.

```kotlin
abstract class Shape {
    abstract fun area(): Double        // 본문 없음
    abstract val name: String          // 초기화자 없음

    fun describe(): String = "$name: 넓이 ${area()}"  // 구체 메서드가 추상 멤버를 사용
}

val s = Shape()  // 컴파일 에러: Cannot create an instance of an abstract class
```

두 가지가 중요하다.

첫째, **`abstract` 멤버는 암시적으로 `open`이다.** 추상 멤버는 정의상 오버라이드되어야 하므로 `open`을 또 붙일 필요가 없다(붙이면 잉여). 봉인이 기본인 세계에서 `abstract`는 봉인을 여는 또 하나의 방식이되, `open`보다 강한—"열었다"가 아니라 "반드시 채워라"—버전이다.

둘째, **추상 클래스도 상태와 구체 구현을 가질 수 있다.** 위 `describe()`처럼 추상 멤버 위에 구체 로직을 얹을 수 있고, 생성자와 프로퍼티(백킹 필드 포함)를 가질 수 있다. 이 점이 인터페이스와의 결정적 차이다—인터페이스의 프로퍼티는 백킹 필드를 가질 수 없어 상태를 저장하지 못한다(M37, [[25 - 인터페이스]]). 추상 클래스는 "부분적으로 구현된 클래스"이고, 인터페이스는 "상태 없는 계약"이다. 이 대비는 9절에서 선택 기준으로 다시 다룬다.

```text
open class     : 완전히 구현됨, 상속·오버라이드 허용
abstract class : 일부만 구현됨(추상 멤버 존재), 인스턴스화 불가, 상태 가능
interface      : 계약 + 기본 구현, 상태(백킹 필드) 불가, 다중 상속 가능
```

### 2.3 `override`는 그 자체로 `open`이다 — 그리고 `final override`

미묘하지만 자주 놓치는 규칙. **오버라이드한 멤버는 별도 표시가 없으면 다시 `open`이다.** 즉 오버라이드는 봉인을 도로 잠그지 않는다.

```kotlin
open class A {
    open fun f() = println("A.f")
}
open class B : A() {
    override fun f() = println("B.f")   // override지만 여전히 open — C가 또 오버라이드 가능
}
class C : B() {
    override fun f() = println("C.f")   // => OK
}
```

`B.f`는 `override`일 뿐 `open`이라고 쓰지 않았는데도 `C`가 오버라이드할 수 있다. 이는 "한 번 열린 멤버는 계층 아래로 계속 열려 있다"는 규칙이다. 이 사슬을 여기서 끊고 싶으면 `final override`를 명시한다.

```kotlin
open class B : A() {
    final override fun f() = println("B.f")  // 여기서 봉인
}
class C : B() {
    override fun f() = println("C.f")  // 컴파일 에러: 'f' in 'B' is final, cannot be overridden
}
```

`final override`는 "상위의 계약은 지키되(오버라이드) 나 이하로는 더 못 바꾸게 잠근다(final)"는 흔한 관용구다. 계층의 중간 클래스가 자기 오버라이드의 불변식을 하위로부터 지키고 싶을 때 쓴다.

### 2.4 시그니처 규칙 — 공변 반환, 불변 파라미터

오버라이드가 성립하려면 시그니처가 맞아야 하는데, "맞는다"의 정의가 반환 타입과 파라미터 타입에서 다르다.

**반환 타입은 공변(covariant)이다.** 오버라이드하는 함수는 상위가 선언한 반환 타입의 *하위 타입*을 반환할 수 있다.

```kotlin
open class Animal
class Cat : Animal()

open class AnimalShelter {
    open fun adopt(): Animal = Animal()
}
class CatShelter : AnimalShelter() {
    override fun adopt(): Cat = Cat()   // => OK: Cat은 Animal의 하위 타입 (공변 반환)
}
```

이것은 리스코프 치환 원칙(LSP)과 정확히 맞아떨어진다. `AnimalShelter`를 기대하는 코드는 `adopt()`가 `Animal`을 준다고 믿는데, `CatShelter`가 더 구체적인 `Cat`을 줘도 그 믿음은 깨지지 않는다(`Cat`은 `Animal`이니까). 반환 위치는 *생산(out)* 위치이므로 하위 타입이 안전하다—이 직관은 변성([[33 - 제네릭 1 - 타입 파라미터와 변성]])의 씨앗이다.

**파라미터 타입은 불변(invariant)이다.** 파라미터 타입을 넓히거나(반공변) 좁히면(공변) 오버라이드가 아니라 오버로드가 되거나 컴파일 에러가 난다.

```kotlin
open class Printer {
    open fun print(x: Animal) {}
}
class BadPrinter : Printer() {
    override fun print(x: Cat) {}  // 컴파일 에러: 'print' overrides nothing
                                   // (Cat을 받는 print는 Animal을 받는 print를 오버라이드하지 못함)
}
```

파라미터를 좁히면(Cat만 받게 하면) `Printer`로서 `Animal`을 넘기는 코드가 깨지므로 LSP 위반이라 애초에 오버라이드로 인정되지 않는다. 파라미터는 *소비(in)* 위치라 상위 타입이라야 안전한데, 코틀린은 그 방향의 변화를 오버라이드로 허용하지 않고 그냥 별개 메서드(오버로드)로 취급한다.

> **명세 정밀**: 가시성(visibility)에도 규칙이 있다. 오버라이드하는 멤버는 상위 멤버보다 가시성을 *넓힐* 수는 있어도 좁힐 수는 없다. `protected open fun`을 `public override fun`으로 넓히는 것은 되지만, `public`을 `protected`로 좁히면 LSP를 깨므로 금지된다([[26 - 가시성 한정자]]).

## 3. 프로퍼티 오버라이딩 — 필드가 아니라 접근자를 갈아 끼운다

### 3.1 `val`을 `var`로, 그러나 `var`를 `val`로는 안 된다

프로퍼티도 함수처럼 오버라이드된다. 여기서 프로퍼티가 *접근자의 추상*(M35, [[22 - 프로퍼티와 백킹 필드]])이라는 사실이 결정적으로 작동한다. 프로퍼티를 오버라이드한다는 것은 **필드를 갈아 끼우는 게 아니라 게터/세터를 갈아 끼우는 것**이다.

`val`을 `var`로 오버라이드할 수 있다.

```kotlin
open class Base {
    open val x: Int = 1     // 게터만
}
class Derived : Base() {
    override var x: Int = 2 // 게터 + 세터
        get() = field
        set(value) { field = value }
}
```

되는 이유를 접근자로 풀면 명확하다. `val x`는 "게터가 있다"는 계약이다. `var x`는 "게터가 있고 *추가로* 세터도 있다"는 계약이다. `var`는 `val`이 요구하는 게터를 이미 포함하므로, `var`로 오버라이드해도 상위의 `val` 계약("읽을 수 있다")은 완전히 만족된다. 세터는 그저 덤이다.

역방향은 불가능하다.

```kotlin
open class Base {
    open var y: Int = 1
}
class Derived : Base() {
    override val y: Int = 2  // 컴파일 에러: 'var'-property cannot be overridden by 'val'-property
}
```

`var y`를 기대하는 코드는 `y = 3`처럼 *쓸* 수 있다고 믿는다. 이걸 `val`(게터만)로 오버라이드하면 세터가 사라져 그 믿음이 깨진다. LSP 위반이다. **계약을 넓히는 방향(val→var)은 되고, 좁히는 방향(var→val)은 안 된다**—2.4절의 반환 타입 공변, 가시성 확대와 같은 결의 규칙이다.

| 상위 | 하위 오버라이드 | 가능? | 이유 |
|------|----------------|-------|------|
| `open val x` | `override val x` | O | 게터 계약 유지 |
| `open val x` | `override var x` | O | 게터 계약 + 세터 추가 (넓힘) |
| `open var y` | `override var y` | O | 게터·세터 계약 유지 |
| `open var y` | `override val y` | X | 세터 계약 상실 (좁힘, LSP 위반) |

### 3.2 게터 오버라이드와 백킹 필드

프로퍼티 오버라이드가 접근자 교체임을 가장 선명하게 보여 주는 것은, 하위에서 초기화자 대신 *커스텀 게터*로 오버라이드하는 경우다.

```kotlin
open class Rectangle(val width: Int, val height: Int) {
    open val area: Int = width * height   // 백킹 필드 있음, 생성 시 한 번 계산
}

class MutableRectangle(var w: Int, var h: Int) : Rectangle(w, h) {
    override val area: Int
        get() = w * h                      // 백킹 필드 없음, 접근할 때마다 계산
}
```

상위 `Rectangle.area`는 백킹 필드를 갖는다—생성 시점에 `width * height`를 한 번 계산해 필드에 저장한다. 하위 `MutableRectangle.area`는 **커스텀 게터로 오버라이드했고 백킹 필드가 없다**—접근할 때마다 `w * h`를 다시 계산한다. `w`, `h`가 `var`라 변할 수 있으니 이 재계산이 필요하다.

핵심은, 오버라이드된 프로퍼티에 접근할 때 *어느 접근자가 실행되는가*가 런타임 타입에 따라 결정된다는 것이다. `MutableRectangle` 인스턴스를 `Rectangle` 타입 변수에 담아 `area`를 읽어도, 실행되는 것은 하위의 커스텀 게터다. 프로퍼티 접근도 함수 호출과 똑같이 **동적 디스패치**된다(7절). 프로퍼티는 필드처럼 *보이지만* 오버라이드 관점에서는 철저히 메서드처럼 행동한다.

이 사실에서 초기화 함정(6절, M47)의 씨앗이 나온다. 상위 생성자에서 `area`를 읽으면, 그것이 필드 읽기가 아니라 *하위의 게터 호출*로 디스패치되고, 그 게터가 아직 초기화 안 된 하위 필드(`w`, `h`)를 건드릴 수 있다.

> **성능 주의**: `open val area = width * height`(필드에 저장)와 `open val area get() = width * height`(매번 계산)는 의미가 다르다. 전자는 값을 한 번 계산해 캐시하지만 오버라이드 함정에 노출되고, 후자는 매 접근마다 비용을 치르지만 항상 최신값을 준다. `open` 프로퍼티에서 이 선택은 성능뿐 아니라 초기화 안전성의 문제이기도 하다.

### 3.3 생성자 파라미터로서의 오버라이드 프로퍼티

주 생성자 파라미터에 `override`를 직접 붙일 수도 있다. 이때 상위의 추상/열린 프로퍼티가 생성자를 통해 채워진다.

```kotlin
abstract class Vehicle {
    abstract val wheels: Int
}

class Car(override val wheels: Int = 4) : Vehicle()
class Motorcycle : Vehicle() {
    override val wheels: Int = 2
}

val v: Vehicle = Car()
println(v.wheels)  // => 4
```

`Car`는 추상 프로퍼티 `wheels`를 생성자 파라미터로 구현했다. 문법적으로는 [[21 - 클래스와 생성자]]에서 본 "주 생성자 프로퍼티" 선언(`val`을 붙여 파라미터를 프로퍼티로 승격)에 `override`가 더해진 것이다. 이 프로퍼티는 백킹 필드를 갖고, 생성자가 그 필드를 채운다.

주의할 점—이 프로퍼티의 필드가 채워지는 시점은 여전히 하위 클래스 초기화 단계다. 즉 상위 `Vehicle`의 `init` 블록에서 `wheels`를 읽으면 아직 0이다(6절에서 재현). 생성자 파라미터로 오버라이드했다고 해서 초기화 순서 규칙에서 면제되지는 않는다.

## 4. `super` — 덮인 구현으로 가는 통로

### 4.1 `super.method()`의 의미와 정적 성격

오버라이드는 상위 구현을 *가린다*. 가려진 상위 구현을 하위에서 다시 부르려면 `super`를 쓴다. 흔한 패턴은 "상위 행동을 하고 나서 추가 작업"이다.

```kotlin
open class Logger {
    open fun log(msg: String) {
        println("[LOG] $msg")
    }
}
class TimestampLogger : Logger() {
    override fun log(msg: String) {
        super.log("${System.currentTimeMillis()} $msg")  // 상위 구현 재사용
    }
}
```

`super.log(...)`는 `TimestampLogger`가 오버라이드로 가린 `Logger.log`를 콕 집어 호출한다. 여기서 결정적인 성질—**`super` 호출은 정적으로 묶인다(statically bound)**. `super.log`는 "이 클래스의 *직속 상위*의 `log`"를 컴파일 타임에 확정한다. 아무리 하위 클래스가 더 있어도, `super`는 절대 아래로 디스패치되지 않는다. 이것이 일반 메서드 호출(동적 디스패치)과 `super` 호출(정적 디스패치)의 근본 차이다.

기계 수준에서, JVM 백엔드는 일반 가상 호출을 `invokevirtual`로, `super` 호출을 `invokespecial`로 컴파일한다. `invokespecial`은 vtable을 타지 않고 지정된 클래스의 메서드를 직접 호출하는 명령이다—생성자 호출(`<init>`)과 private 메서드 호출에도 쓰이는, "여기 이 구현으로 가라"는 명령이다.

```text
일반 호출  obj.log(m)      → invokevirtual  (런타임 타입의 vtable에서 찾음, 동적)
super 호출  super.log(m)    → invokespecial  (지정 클래스 구현 직접, 정적)
```

이 정적 성격 때문에 `super`는 무한 재귀를 만들지 않는다. `super.log`가 다시 아래로 디스패치되어 자기 자신(`TimestampLogger.log`)으로 돌아온다면 무한 루프가 될 텐데, 정적 바인딩이 그것을 막는다.

### 4.2 다중 상속 충돌과 `super<A>.f()`

클래스 단일 상속에서는 `super`의 대상이 유일하다(상위 클래스 하나뿐). 그러나 클래스 하나 + 인터페이스 여럿을 상속하면 같은 시그니처의 기본 구현이 여럿 상속될 수 있고, 그때 `super`만으로는 어느 것인지 모호해진다. 이 완전한 해소는 [[25 - 인터페이스]]가 소유하지만, 문법의 모양만 미리 본다.

```kotlin
open class Machine {
    open fun start() = println("기계 시동")
}
interface Rechargeable {
    fun start() { println("충전 확인 후 시동") }  // 인터페이스 기본 구현
}

class ElectricCar : Machine(), Rechargeable {
    override fun start() {
        super<Machine>.start()        // 클래스 쪽 구현
        super<Rechargeable>.start()   // 인터페이스 쪽 구현
    }
}
// ElectricCar().start()
// => 기계 시동
// => 충전 확인 후 시동
```

`ElectricCar`는 `Machine`(클래스)의 `start`와 `Rechargeable`(인터페이스)의 기본 `start`를 둘 다 물려받는다. 코틀린은 이 충돌을 **컴파일 에러로 강제**한다—하위 클래스가 반드시 오버라이드해서 모호성을 해결해야 한다. 해결 안에서 `super<Machine>.start()`, `super<Rechargeable>.start()`처럼 꺾쇠로 어느 상위인지 명시한다. 이 명시적 충돌 해소가 "다이아몬드 문제"에 대한 코틀린의 답이다. 자세한 규칙(어떤 조합이 충돌로 판정되는지, 인터페이스끼리의 충돌은 어떻게 되는지)은 25장으로 넘긴다.

> **명세 정밀**: 이너 클래스([[31 - 중첩 클래스와 이너 클래스와 익명 객체]])에서 바깥 클래스의 `super`를 부르려면 `super@Outer.f()`처럼 라벨을 붙인다. `super`의 대상은 "지금 이 클래스의 상위"이므로, 중첩 상황에서 어느 `this`의 상위인지를 라벨로 명시하는 것이다.

## 5. 초기화 순서 — 상위에서 하위로 흐른다

이 장의 심장 첫 번째. 상속 계층에서 인스턴스가 만들어질 때, 각 층의 생성자·`init` 블록·프로퍼티 초기화자가 정확히 어떤 순서로 실행되는가.

### 5.1 생성자 위임 사슬 — 상위 생성자는 반드시 먼저

[[21 - 클래스와 생성자]]에서 한 클래스 안의 순서(프로퍼티 초기화자와 `init` 블록이 소스 등장 순서대로 인터리빙)를 확정했다. 계층이 생기면 그 위에 **"상위가 하위보다 먼저"**라는 규칙이 얹힌다.

주 생성자가 있는 하위 클래스는 상위 타입 지정자에서 상위 생성자를 호출한다.

```kotlin
open class Base(val a: Int)
class Derived(val b: Int) : Base(b * 10)  // Base(...) 호출이 상위 초기화
```

`Derived(3)`을 만들면, `Base(30)`가 *먼저* 완전히 초기화되고, 그다음 `Derived`의 몫이 초기화된다. 이 순서는 협상 불가다. JVM 백엔드에서 이것은 언어 규칙일 뿐 아니라 바이트코드 검증기(verifier)의 요구이기도 하다—하위 생성자 `<init>`는 반드시 자기 몸통의 어떤 코드보다 먼저 상위 `<init>`를 `invokespecial`로 호출해야 한다. "상위를 초기화하기 전에는 하위 필드에 손대지 못한다"가 기계 수준의 계약이다.

주 생성자가 없는 클래스는 각 부 생성자가 `super(...)`로 상위를 초기화하거나 `this(...)`로 다른 부 생성자에 위임한다.

```kotlin
open class Base(val a: Int)
class Derived : Base {
    val b: Int
    constructor(b: Int) : super(b * 10) {  // super로 상위 초기화
        this.b = b
    }
}
```

어느 경로든 결론은 같다. **상위 생성자가 완전히 끝난 뒤에야 하위의 초기화가 시작된다.**

### 5.2 한 층 안의 순서를 계층으로 확장

한 클래스 안의 초기화 순서를 다시 상기하자(21장): 주 생성자 파라미터 평가 → 소스에 등장하는 순서대로 프로퍼티 초기화자와 `init` 블록 실행. 이제 이것을 계층에 겹치면, 각 층에서 이 "한 층 순서"가 돌되, 층 자체는 위에서 아래로 진행한다.

세 층짜리 계층으로 전체를 재현해 보자.

```kotlin
open class A {
    val a1 = log("A.a1 초기화자")
    init { log("A.init 블록") }
    val a2 = log("A.a2 초기화자")
    constructor() { log("A 생성자 본문") }
}

open class B : A {
    val b1 = log("B.b1 초기화자")
    init { log("B.init 블록") }
    constructor() : super() { log("B 생성자 본문") }
}

class C : B() {
    val c1 = log("C.c1 초기화자")
    init { log("C.init 블록") }
}

fun log(s: String): Unit = println(s)
```

`C()`를 실행하면 출력은 이렇다.

```text
A.a1 초기화자      ← A층: 초기화자·init 블록 (소스 순서)
A.init 블록
A.a2 초기화자
A 생성자 본문       ← A층: 생성자 본문은 초기화자·init 블록 뒤
B.b1 초기화자      ← B층
B.init 블록
B 생성자 본문
C.c1 초기화자      ← C층
C.init 블록
```

읽어 낼 규칙이 두 개다.

**규칙 1 (층간): 위층이 완전히 끝난 뒤 아래층이 시작된다.** A의 모든 초기화(초기화자·init·생성자 본문)가 끝나야 B가 시작되고, B가 끝나야 C가 시작된다.

**규칙 2 (층내): 한 층에서는 프로퍼티 초기화자와 `init` 블록이 소스 등장 순서대로 실행되고, 생성자 본문은 그 뒤에 실행된다.** A층에서 `a1`→`init`→`a2`가 소스 순서대로 돌고, 그다음 생성자 본문이 돈다. 부 생성자의 본문(`{ ... }`)은 그 층의 초기화자·init 블록 *뒤*에 실행된다는 점이 핵심이다—`super()` 위임이 먼저 상위를 초기화하고, 돌아와서 이 층의 초기화자·init을 돌린 뒤, 마지막에 생성자 본문 코드를 실행한다.

### 5.3 전체 실행 순서 다이어그램

이 흐름을 시간축으로 펼치면 다음과 같다. `Derived : Base(...)` 한 층 위임을 기준으로.

```text
new Derived(args) 요청
   │
   ├─ (1) Derived 주 생성자 파라미터의 기본값 표현식 평가 (필요 시)
   │        그리고 상위 지정자 Base(expr)의 expr 평가
   │
   ├─ (2) Base 생성자로 위임  ─────────────────┐
   │                                            │  ← 여기서부터 Base 초기화
   │        (2a) Base 프로퍼티 초기화자 + init  │     (this는 이미 Derived 인스턴스지만
   │             (소스 순서)                     │      Derived의 필드는 아직 전부 기본값!)
   │        (2b) Base 생성자 본문                │
   │                                            │
   │     ◄────────────────────────────────────┘  Base 초기화 완료, Derived로 복귀
   │
   ├─ (3) Derived 프로퍼티 초기화자 + init 블록 (소스 순서)
   │
   └─ (4) Derived 생성자 본문 (부 생성자면 그 본문)
           인스턴스 준비 완료
```

주석에 박아 둔 (2a)의 진실이 6절의 함정 전부를 낳는다. **(2) 단계에서 `this`는 이미 `Derived` 타입의 객체다**(가상 디스패치는 `Derived`의 오버라이드로 간다). 그런데 그 시점에 `Derived`가 선언한 필드들은 아직 (3)에서 채워지지 않아 *기본값*(참조 타입은 `null`, 수치 타입은 `0`/`0.0`, 불리언은 `false`)이다. 즉 **"타입은 하위, 필드는 미초기화"**라는 위험한 중간 상태가 상위 생성자 실행 동안 존재한다.

> **명세 정밀**: 이 순서는 코틀린만의 특이점이 아니라 대부분의 클래스 기반 OOP 언어(자바, C#, C++)가 공유하는 근본 제약이다. "부분 객체(상위 부분)를 먼저 완성해야 전체 객체(하위 부분)를 쌓을 수 있다"는 것은 상속의 물리적 필연이다. 다만 언어마다 이 중간 상태에서 가상 디스패치가 어디로 가는지가 다르다. 코틀린·자바·C#은 생성 중에도 가상 호출이 하위 오버라이드로 간다(그래서 함정이 있다). C++은 생성자 실행 중에는 `this`의 동적 타입이 "현재 생성 중인 그 층"으로 취급되어 가상 호출이 하위로 가지 *않는다*(그래서 C++엔 이 특정 함정이 없는 대신 다른 규칙이 있다). 이 차이는 6.2절에서 다시 짚는다.

## 6. M47 정면 교정 — 생성자에서 `open` 멤버를 부르는 함정

이 장의 소유 오개념. **"오버라이드한 프로퍼티/함수를 `open` 생성자에서 부르면 안전하다"는 착각(M47).** 직관은 이렇다—"가상 함수를 부르면 어차피 내 오버라이드가 실행될 테니, 상위 생성자든 어디든 불러도 올바르게 동작하겠지." 이 직관은 틀렸고, 5절에서 확정한 초기화 순서가 그 이유다.

### 6.1 미초기화 필드를 관찰하는 순간

가장 짧은 재현. 상위 생성자가 오버라이드된 프로퍼티를 읽는다.

```kotlin
open class Base {
    open val size: Int = 0

    init {
        println("Base.init: size = $size")  // open 프로퍼티를 상위 초기화에서 읽음
    }
}

class Derived : Base() {
    override val size: Int = 42
}

fun main() {
    Derived()
}
// 출력:
// Base.init: size = 0     ← 42가 아니라 0!
```

기대와 다르다. `Derived.size`는 42로 오버라이드했는데, `Base.init`은 42가 아니라 **0**을 봤다. 5.3절 다이어그램으로 추적하면 명확하다.

1. `Derived()` → `Base()` 위임 (단계 2)
2. `Base`의 초기화 시작. `Base.init`의 `$size`는 `size` 게터를 호출한다.
3. `size`는 `open`이고 `this`는 `Derived`이므로, 게터는 **`Derived.size`로 디스패치**된다.
4. `Derived.size`의 백킹 필드는? `Derived`의 프로퍼티 초기화자(`= 42`)는 단계 3에서야 실행되는데 지금은 아직 단계 2다. 그래서 필드는 초기화 전 기본값 **0**.
5. 게터가 그 필드(0)를 반환. `Base.init`은 0을 출력.

함수로 바꾸면 더 위험해진다. 미초기화 참조 필드를 건드리면 `NullPointerException`이 난다.

```kotlin
open class View(open val title: String) {
    init {
        // 상위 생성자가 오버라이드된 메서드를 호출
        render()
    }
    open fun render() {
        println("렌더링: $title")
    }
}

class Button(override val title: String, private val label: String) : View(title) {
    override fun render() {
        // label을 대문자로 — 그런데 이 시점에 label은?
        println("버튼[${label.uppercase()}]: $title")
    }
}

fun main() {
    Button("확인", "OK")
}
// 컴파일은 되지만 런타임에:
// Exception: NullPointerException
//   (label이 아직 null인 채 label.uppercase() 호출)
```

`View`의 `init`이 `render()`를 호출한다. `render`는 `open`이고 `this`가 `Button`이니 `Button.render`로 디스패치된다. 그런데 `Button.render`는 `label`을 쓰는데, `label`은 `Button`의 생성자 파라미터 프로퍼티라 그 필드는 `View` 초기화가 끝난 *뒤*에야 채워진다. `View.init` 시점의 `label`은 `null`이다(비-널 `String`으로 선언했는데도!). `label.uppercase()`가 NPE를 던진다.

이것이 M47의 핵심—**널 안전성(M7)이 보장된다고 믿는 코틀린에서조차, 초기화 순서의 틈에서는 비-널 프로퍼티가 `null`이 되는 순간이 존재한다.** 컴파일러는 이 특정 함정을 대부분 잡지 못한다(가상 디스패치 너머의 흐름을 추적하기 어렵다). 다만 IDE와 컴파일러는 "open 멤버를 생성자에서 호출한다"에 대해 경고(`Calling non-final function in constructor` / `Accessing non-final property in constructor`)를 낸다—이 경고는 무시하면 안 되는 진짜 신호다.

### 6.2 왜 하필 이런 순서인가 — 가상 디스패치와 초기화의 충돌

두 규칙이 서로 충돌한다.

- **규칙 A (동적 디스패치):** `open` 멤버 호출은 항상 런타임 타입의 오버라이드로 간다. `this`가 `Button`이면 `Button.render`로.
- **규칙 B (초기화 순서):** 상위 초기화가 하위 초기화보다 먼저 끝난다. 하위 필드는 상위 초기화 동안 미초기화다.

상위 생성자에서 `open` 멤버를 부르면 이 둘이 정면충돌한다. 규칙 A가 "하위 오버라이드로 가라"고 하고, 규칙 B가 "그런데 하위 필드는 아직 없다"고 한다. 결과는 "존재하지만 아직 비어 있는 하위 객체의 메서드"가 실행되는, 반쯤 태어난 객체(half-constructed object) 위에서의 호출이다.

앞서 5.3절 명세 정밀에서 언급했듯, C++은 이 충돌을 *다른 방식*으로 해결한다—생성자 실행 중에는 `this`의 가상 타입을 "지금 생성 중인 그 층"으로 고정해, 상위 생성자에서 가상 함수를 부르면 하위가 아니라 *상위* 구현으로 간다. 그래서 C++엔 이 NPE 함정이 없다(대신 "상위 생성자에서 부른 가상 함수는 하위 오버라이드로 안 간다"는, 초보자를 놀래는 다른 규칙이 생긴다). 코틀린·자바·C#은 반대 선택을 했다—생성 중에도 `this`는 최종 런타임 타입이고 가상 호출은 하위로 간다. 이 선택의 대가가 M47 함정이다. 어느 쪽도 공짜가 아니며, 두 진영 다 "상위 생성자에서 가상 멤버를 부르지 마라"는 결론에 도달한다.

정리하면, M47은 언어 설계의 근본 트레이드오프에서 나온 *구조적* 함정이지 코틀린의 버그가 아니다. 그래서 해법은 "고친다"가 아니라 "피한다"이다.

### 6.3 방어책 — `final`, `private`, 팩토리, 지연

**방어 1: 생성자에서 부르는 멤버는 `final`이거나 `private`이게 하라.** 오버라이드 불가능한 멤버는 가상 디스패치가 없으므로 함정이 없다. `private` 멤버는 애초에 오버라이드 대상이 아니다.

```kotlin
open class View2(val title: String) {
    init {
        renderInternal()  // private → 항상 이 구현, 안전
    }
    private fun renderInternal() {
        println("렌더링: $title")  // title은 상위 프로퍼티, 이미 초기화됨
    }
}
```

`title`을 `View2`의 (하위가 오버라이드하지 않는) 일반 프로퍼티로 두고, `renderInternal`을 `private`으로 두면 초기화 시점에 안전하다.

**방어 2: 초기화 로직을 생성자 밖으로.** 객체를 다 만든 *뒤에* 초기화 메서드를 부르는 팩토리 패턴을 쓴다.

```kotlin
open class Widget protected constructor() {
    open fun onCreate() {}   // 하위가 오버라이드해도 안전 — 생성 후 호출되므로
    companion object {
        fun <T : Widget> create(w: T): T {
            // w는 이미 완전히 생성됨. 이제 가상 호출해도 필드가 다 차 있다.
            w.onCreate()
            return w
        }
    }
}
```

**방어 3: `by lazy`로 지연.** 상위에서 즉시 계산하는 대신, 처음 접근할 때 계산하도록 미룬다([[23 - 위임 프로퍼티]]).

```kotlin
open class Report {
    open val header: String get() = "일반 보고서"
    // 지연: 최초 접근 시점엔 하위 필드가 다 차 있다
    val cachedHeader: String by lazy { header }
}
```

`cachedHeader`는 생성 시점이 아니라 최초 *접근* 시점에 `header`를 읽는다. 인스턴스가 완성된 뒤 접근하면 하위 오버라이드가 올바른 값을 준다.

**방어 4: 그냥 부르지 마라.** 가장 확실한 방어다. 코틀린 컴파일러/IDE의 "생성자에서 non-final 멤버 호출" 경고가 뜨면, 그 호출을 팩토리나 지연 초기화나 명시적 `init()` 호출로 옮긴다. 이 경고는 스타일이 아니라 정확성의 문제다.

> **흔한 오해**: "그럼 상위 생성자에서는 어떤 멤버도 부르면 안 되나?" 아니다. `final`·`private` 멤버, 그리고 상위 자신의 완전히 초기화된 프로퍼티는 얼마든지 부를 수 있다. 위험한 것은 **오버라이드 가능한(`open`/`abstract`) 멤버**를 부르는 것뿐이다. `abstract` 멤버를 상위 생성자에서 부르는 것은 특히 위험하다—상위엔 구현조차 없으니 반드시 하위 오버라이드로 가고, 그 오버라이드는 십중팔구 하위 필드를 쓴다.

## 7. 동적 디스패치의 기계 — vtable과 `invokevirtual`

6절의 함정을 제대로 이해하려면, "가상 호출이 하위로 간다"가 기계 수준에서 무엇을 뜻하는지 봐야 한다.

### 7.1 정적 타입 vs 런타임 타입

변수는 두 개의 타입을 갖는다. **정적 타입**(컴파일 타임에 컴파일러가 아는 선언 타입)과 **런타임 타입**(실제로 그 변수가 가리키는 객체의 클래스). 오버라이드된 멤버 호출은 정적 타입이 아니라 **런타임 타입**을 따른다.

```kotlin
open class Animal {
    open fun speak(): String = "..."
}
class Dog : Animal() {
    override fun speak(): String = "멍"
}
class Cat : Animal() {
    override fun speak(): String = "야옹"
}

fun main() {
    val animals: List<Animal> = listOf(Dog(), Cat())  // 정적 타입은 전부 Animal
    for (a in animals) {
        println(a.speak())  // 런타임 타입에 따라 다르게 디스패치
    }
}
// => 멍
// => 야옹
```

`a`의 정적 타입은 모두 `Animal`이다. 컴파일러는 `a`가 `Dog`인지 `Cat`인지 모른다. 그런데도 `a.speak()`는 각각 `Dog.speak`, `Cat.speak`를 실행한다. 이 "정적 타입은 하나인데 실행은 런타임 타입별로 갈라지는" 능력이 다형성(polymorphism)의 본질이고, 그것을 구현하는 기계가 가상 메서드 테이블(virtual method table, vtable)이다.

### 7.2 JVM 백엔드에서의 `invokevirtual`

JVM 백엔드에서 각 클래스는 vtable을 갖는다—오버라이드 가능한 각 메서드에 대해 "이 클래스에서 실제로 실행할 구현의 포인터"를 담은 배열이다. 하위 클래스는 상위의 vtable을 복사한 뒤, 자기가 오버라이드한 슬롯만 자기 구현으로 덮어쓴다.

```text
                 vtable (개념도)
Animal:   [ speak → Animal.speak ]
Dog:      [ speak → Dog.speak    ]   ← 슬롯 덮어씀
Cat:      [ speak → Cat.speak    ]   ← 슬롯 덮어씀

a.speak() 실행:
   1. a가 가리키는 객체의 헤더에서 클래스 포인터를 읽음 (런타임 타입 확인)
   2. 그 클래스의 vtable에서 speak 슬롯을 찾음
   3. 슬롯이 가리키는 구현으로 점프
```

바이트코드로는 `a.speak()`가 `invokevirtual Animal.speak()`로 컴파일된다. `invokevirtual`은 "선언 타입은 `Animal.speak`이지만, 실제 대상은 스택 맨 위 객체의 런타임 타입 vtable에서 찾아라"는 명령이다. 이 조회가 6절의 "상위 생성자에서 `open` 멤버를 부르면 하위로 간다"의 정체다—`this`의 런타임 타입이 이미 `Derived`이므로, `invokevirtual`은 `Derived`의 vtable 슬롯(하위 오버라이드)으로 점프한다. 생성이 아직 안 끝났든 말든 vtable은 처음부터 최종 타입의 것이다.

대조적으로 4.1절의 `super` 호출은 `invokespecial`이다. `invokespecial`은 vtable을 *거치지 않고* 명령에 박힌 클래스의 구현을 직접 부른다. 그래서 `super`는 항상 정적으로 지정된 상위 구현으로 가고, 하위로 재디스패치되지 않는다.

```text
invokevirtual  : vtable 조회 → 런타임 타입의 구현 (동적)
invokespecial  : 명령에 박힌 클래스의 구현 직접 (정적) — super, 생성자, private
invokestatic   : 인스턴스 없는 정적 메서드 (@JvmStatic, 확장 함수 등)
```

> **명세 정밀**: vtable은 JVM 백엔드의 구현 전략이다. Kotlin/Native나 JS/Wasm 백엔드는 다형성을 다른 자료구조(예: 타입 정보 테이블, 함수 포인터 맵)로 구현할 수 있다. 그러나 *의미론*—"오버라이드된 멤버는 런타임 타입에 따라 디스패치된다"—은 모든 백엔드에서 동일하다. "vtable"이라는 단어는 편의상 쓰는 JVM 관점의 그림이고, 언어가 보장하는 것은 그 위의 다형적 행동이다.

### 7.3 확장 함수와의 대조 — 정적 디스패치(M14 참조)

이 장은 멤버 함수의 *동적* 디스패치를 다루지만, 대비를 위해 확장 함수의 *정적* 디스패치를 짚어 둘 가치가 있다(정본은 M14, [[35 - 확장 함수와 프로퍼티]]).

```kotlin
open class Animal
class Dog : Animal()

fun Animal.describe() = "동물"
fun Dog.describe() = "개"

fun main() {
    val a: Animal = Dog()  // 런타임 타입은 Dog, 정적 타입은 Animal
    println(a.describe())  // => 동물  (개가 아니라!)
}
```

멤버 함수라면 `Dog`로 디스패치되어 "개"가 나왔을 것이다. 하지만 `describe`는 확장 함수다. **확장 함수는 vtable에 슬롯이 없다.** 컴파일러는 수신자의 *정적 타입*(`Animal`)만 보고 `Animal.describe`를 컴파일 타임에 확정한다—`invokestatic`으로 컴파일되는, 첫 인자가 수신자인 평범한 정적 함수 호출이다. 그래서 런타임 타입이 `Dog`여도 "동물"이 나온다.

이 대조가 상속의 핵심을 역설적으로 밝힌다. **오버라이딩(멤버, 동적)과 확장(정적)은 겉모습이 같지만(`a.f()`) 기계가 정반대다.** 상속 계층의 다형적 행동을 원하면 멤버 함수를 `open`으로 열어 오버라이드하고, 기존 타입에 부수적 기능만 얹으려면 확장을 쓴다. 확장으로 다형성을 흉내 내려다 이 정적 디스패치에 발이 걸리는 것이 흔한 초보 함정이다.

## 8. `Any` — 모든 클래스의 뿌리

### 8.1 `Any`가 선언하는 세 멤버

명시적 상위 타입이 없는 코틀린 클래스는 자동으로 `Any`를 상속한다. `Any`는 타입 계층의 최상단(비-널 쪽)이다([[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]). `Any`가 선언하는 멤버는 **딱 세 개**다.

```kotlin
// kotlin.Any의 개념적 선언
open class Any {
    open operator fun equals(other: Any?): Boolean
    open fun hashCode(): Int
    open fun toString(): String
}
```

이 셋은 모든 코틀린 객체가 갖는다. 그리고 모두 `open`이므로 어떤 클래스든 오버라이드할 수 있다.

여기서 자바 배경의 흔한 오해를 교정할 필요가 있다. JVM 백엔드에서 `Any`는 `java.lang.Object`로 매핑되지만, **코틀린의 `Any`는 `Object`의 모든 메서드를 노출하지 않는다.** `wait()`, `notify()`, `getClass()` 같은 `Object`의 다른 메서드는 코틀린 `Any`의 멤버가 아니다(스레드 대기 원시 연산은 코틀린이 의도적으로 감췄다—동시성은 더 고수준 도구로 다루라는 뜻, [[43 - 동시성과 메모리 모델]]로 위임). 코틀린에서 객체의 클래스를 얻으려면 `Object.getClass()`가 아니라 `::class`(리플렉션, [[44 - 애노테이션과 리플렉션]])나 `javaClass`(JVM 확장)를 쓴다. 즉 `Any`는 "JVM `Object`의 코틀린식 정제판"이지 그 별칭이 아니다. Kotlin/Native나 JS 백엔드에는 `Object`가 아예 없고, `Any`가 그 자체로 뿌리다.

### 8.2 `equals`/`hashCode`/`toString` 오버라이딩 — 상속되는 계약

이 셋을 오버라이드하는 것은 단순히 함수를 바꾸는 게 아니라 **계약을 짊어지는** 일이다(정본은 [[10 - 불리언과 동등성과 동일성]]).

```kotlin
class Point(val x: Int, val y: Int) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true
        if (other !is Point) return false
        return x == other.x && y == other.y
    }
    override fun hashCode(): Int = 31 * x + y
    override fun toString(): String = "Point($x, $y)"
}
```

`equals`를 오버라이드할 때의 계약: 반사성(자기 자신과 같다), 대칭성(`a == b`면 `b == a`), 추이성(`a == b`, `b == c`면 `a == c`), 일관성(같은 입력엔 같은 결과). 그리고 **`equals`를 오버라이드하면 반드시 `hashCode`도 같이** 오버라이드해야 한다—"같은 두 객체는 같은 해시코드를 가져야 한다"는 계약을 어기면 `HashMap`/`HashSet`이 조용히 오작동한다. 이 두 함수를 자동으로 올바르게 생성해 주는 것이 데이터 클래스([[27 - 데이터 클래스]])다. 데이터 클래스는 `equals`/`hashCode`/`toString`/`componentN`/`copy`를 주 생성자 프로퍼티 기준으로 생성해, 이 계약을 손으로 지키는 수고를 없앤다(단 주 생성자 프로퍼티만 참여한다는 함정이 있다—M21).

상속 계층에서 `equals`는 특히 까다롭다. 상위 타입과 하위 타입의 인스턴스를 비교할 때 대칭성을 지키기 어렵기 때문이다. 이 때문에 데이터 클래스는 다른 클래스를 상속할 수는 있어도(2.x) `open`이 될 수 없고, 상속을 염두에 둔 `equals` 설계는 매우 조심스러워야 한다. 이 깊은 논의는 10장과 27장이 소유한다.

> **성능 주의**: `toString`은 디버깅·로깅에서 끝없이 호출된다. 무거운 계산(전체 컬렉션 순회, 문자열 대량 연결)을 `toString`에 넣으면 로그를 켜는 순간 성능이 급락할 수 있다. `toString`은 값싸고 부작용 없어야 한다는 것이 암묵적 계약이다.

## 9. 추상 클래스 vs 인터페이스, 그리고 상속보다 조합

### 9.1 언제 추상 클래스, 언제 인터페이스

상속 계층을 설계할 때 첫 갈림길은 "추상 클래스인가 인터페이스인가"다. 둘 다 오버라이드할 멤버를 남길 수 있지만 성질이 다르다.

| 축 | 추상 클래스 | 인터페이스 |
|----|------------|-----------|
| 상태(백킹 필드) | 가질 수 있음 | 불가 (M37) |
| 생성자 | 있음 | 없음 |
| 다중 상속 | 불가 (하나만) | 가능 (여럿) |
| 기본 구현 | 가능 | 가능 |
| "is-a" 관계 | 강한 정체성 | 능력/역할 |

선택의 실용적 기준.

- **상태를 공유해야 하면 추상 클래스.** 하위 클래스들이 공통으로 저장할 필드가 있다면(예: 모든 `Shape`가 갖는 위치 좌표), 인터페이스로는 그 상태를 담을 수 없다.
- **여러 독립적 능력을 조합해야 하면 인터페이스.** 한 클래스가 `Comparable`이면서 `Serializable`이면서 `Drawable`일 수 있다. 클래스 상속은 하나뿐이라 이 조합을 표현하지 못한다.
- **애매하면 인터페이스를 먼저.** 인터페이스는 결합도가 낮고 나중에 여럿 조합할 여지를 남긴다. 추상 클래스는 "이미 클래스 상속 슬롯을 하나 써 버리는" 강한 결정이다.

코틀린에서는 인터페이스도 기본 구현을 가질 수 있으므로("자바 8+의 default 메서드와 유사"), 예전 자바에서 "구현을 공유하려면 추상 클래스" 하던 이유가 상당 부분 사라졌다. 남은 결정적 차이는 **상태**와 **생성자**다. 인터페이스가 상태를 못 갖는 이유(백킹 필드 없음)와 그 우회(백킹 프로퍼티, 구현 클래스에 상태 위임)는 [[25 - 인터페이스]]의 몫이다.

### 9.2 취약한 기반 클래스와 위임 — "상속보다 조합"

1절에서 본 취약한 기반 클래스 문제를 근본적으로 피하는 길은, 애초에 상속하지 않는 것이다. 블로크의 또 다른 격언—"상속보다 조합(favor composition over inheritance)"—이 여기 온다. 상속으로 `is-a`를 표현하는 대신, 필드로 다른 객체를 *가지고*(`has-a`) 그 객체에 일을 위임한다.

1.2절의 `CountingSet`을 조합으로 다시 써 보자. 상속 대신 코틀린의 클래스 위임(`by`, [[32 - 클래스 위임]])을 쓴다.

```kotlin
class CountingSet<T>(
    private val inner: MutableSet<T> = mutableSetOf()
) : MutableSet<T> by inner {          // 위임: MutableSet의 모든 메서드를 inner로 전달
    var addCount = 0
        private set

    override fun add(element: T): Boolean {
        addCount++
        return inner.add(element)      // 명시적으로 inner를 호출 — self-use 문제 없음
    }
    override fun addAll(elements: Collection<T>): Boolean {
        addCount += elements.size
        return inner.addAll(elements)  // inner.addAll의 내부가 add를 부르든 말든
                                       // 우리 add와 무관 (inner는 남의 인스턴스)
    }
}
```

핵심은, `inner`가 *별개의 객체*라 그것의 `addAll` 내부 구현이 우리 `add`를 재진입시키지 않는다는 것이다. 1.2절의 취약성—"상위의 self-use 패턴에 하위 정확성이 의존"—이 사라졌다. `by inner`는 우리가 오버라이드하지 않은 `MutableSet`의 나머지 메서드(전부 수십 개)를 자동으로 `inner`에 전달하는 코드를 컴파일러가 생성해 주므로, 위임의 장황함도 없다. 이 위임 메커니즘의 컴파일 형태와 함정(위임 대상을 프로퍼티로 저장하지 않으면 재계산되는 문제 등)은 32장이 소유한다.

이것이 이 장 전체의 실천적 결론이다. 상속은 강력하지만 결합도가 높고, 초기화 순서의 함정(M47)과 취약한 기반 클래스의 위험을 품는다. 그래서 코틀린은 상속을 *기본 봉인*했고, 확장·인터페이스·위임이라는 덜 위험한 대안을 풍부히 제공한다. 상속을 쓸 때는 `open`이라는 명시적 의사 표시와 함께, 6절의 방어책(생성자에서 `open` 멤버를 부르지 않기)과 1절의 self-use 문서화를 함께 짊어져야 한다.

---

지금까지 우리는 봉인된 채 태어나는 코틀린 클래스에서 출발해, `open`이 어떻게 상속의 문을 열고 `override`가 어떻게 그 계약을 의무로 만드는지를 보았다. 프로퍼티 오버라이딩이 필드가 아니라 접근자의 교체임을 확인하고, `val`→`var`는 되고 그 역은 안 되는 규칙이 계약을 넓히는가 좁히는가의 문제임을 밝혔다. `super`가 정적으로 상위 구현을 콕 집는 `invokespecial`인 반면, 일반 멤버 호출은 vtable을 타는 동적 `invokevirtual`임을 기계 수준에서 확인했다. 그리고 이 장의 심장—초기화가 상위에서 하위로 흐르며, 그 흐름 속에서 "타입은 하위, 필드는 미초기화"라는 위험한 중간 상태가 존재한다는 사실—이 M47 함정의 정체임을 실행 로그로 재현했다. 첫머리의 질문들로 돌아가면, "가상 함수를 부르면 내 오버라이드가 실행되니 안전하다"는 직관은 바로 그 중간 상태에서 무너진다. 하위 오버라이드는 *실행되지만*, 그것이 딛고 서야 할 하위 필드가 아직 없다. 널 안전한 코틀린에서조차 비-널 프로퍼티가 `null`이 되는 순간이 여기 있다. 상속은 언어가 준 가장 날카로운 칼이고, 이 장은 그 칼의 손잡이와 날을 구분하는 법이었다. 다음 장 [[25 - 인터페이스]]는 이 계약을 상태 없이, 다중으로 공유하는 또 다른 축을 연다.

---

## 핵심 요약

- **코틀린 클래스와 멤버는 기본으로 `final`이며, 상속·오버라이드를 허용하려면 `open`(또는 `abstract`)을 명시해야 한다.** 이는 "취약한 기반 클래스" 문제와 블로크의 "상속을 위해 설계하지 않을 거면 금지하라"에 대한 언어 차원의 응답이다. 자바의 기본값을 정확히 뒤집은 것이다.
- **`override`는 애노테이션이 아니라 키워드로 강제된다.** 의도치 않은 우연한 오버라이드와, 오타로 인한 오버라이드 실패를 둘 다 컴파일 타임에 잡는다. 오버라이드한 멤버는 표시가 없으면 다시 `open`이며, 사슬을 끊으려면 `final override`.
- **프로퍼티 오버라이딩은 필드가 아니라 접근자(게터/세터)의 교체다.** `val`을 `var`로 오버라이드할 수 있으나(게터 계약에 세터를 더함) 그 역은 불가능하다(세터 계약 상실, LSP 위반). 반환 타입은 공변, 파라미터는 불변, 가시성은 확대만 허용된다.
- **초기화는 상위에서 하위로 흐른다.** 상위 생성자(그 프로퍼티 초기화자·init 블록·본문)가 완전히 끝난 뒤에야 하위 초기화가 시작된다. JVM 백엔드에서는 바이트코드 검증기가 "상위 `<init>`를 먼저"를 강제한다.
- **상위 생성자 실행 중 `this`는 이미 최종(하위) 런타임 타입이지만, 하위가 선언한 필드는 아직 기본값이다.** "타입은 하위, 필드는 미초기화"라는 이 중간 상태가 M47 함정의 근원이다.
- **생성자에서 `open`/`abstract` 멤버를 호출하면 하위 오버라이드로 동적 디스패치되고, 그 오버라이드는 아직 채워지지 않은 하위 필드를 관찰한다(M47).** 비-널 프로퍼티가 `null`로 읽혀 `NullPointerException`이 나거나, 값이 기본값(0/false)으로 관찰된다. 널 안전한 코틀린에서도 초기화 순서의 틈에서는 이 일이 벌어진다.
- **M47의 방어책은 "고치기"가 아니라 "피하기"다.** 생성자에서 부르는 멤버를 `final`/`private`로 두거나, 초기화를 팩토리·명시적 `init()`·`by lazy`로 객체 완성 이후로 미룬다. 컴파일러/IDE의 "생성자에서 non-final 멤버 호출" 경고는 정확성 신호다.
- **`super.f()`는 정적으로 묶여(`invokespecial`) 지정된 상위 구현을 직접 부른다.** 절대 아래로 재디스패치되지 않아 무한 재귀를 막는다. 반면 일반 멤버 호출은 vtable을 타는 동적 `invokevirtual`로 런타임 타입의 오버라이드로 간다.
- **멤버 함수는 동적 디스패치(런타임 타입), 확장 함수는 정적 디스패치(정적 타입)다(M14 참조).** 겉모습 `a.f()`가 같아도 기계가 정반대이며, 확장으로 다형성을 흉내 내려다 정적 바인딩에 걸리는 것이 흔한 함정이다.
- **모든 클래스는 `Any`를 상속하며 `Any`는 `equals`/`hashCode`/`toString` 셋만 선언한다.** JVM의 `java.lang.Object`로 매핑되지만 `wait`/`notify`/`getClass` 등은 노출하지 않는 정제판이다. `equals`를 오버라이드하면 반드시 `hashCode`도 함께(계약), 이 수고를 없애는 것이 데이터 클래스.
- **추상 클래스와 인터페이스의 결정적 차이는 상태(백킹 필드)와 생성자, 다중 상속 가능성이다.** 상태 공유가 필요하면 추상 클래스, 능력 조합이 필요하면 인터페이스. 애매하면 결합도 낮은 인터페이스를 먼저.
- **상속의 위험(취약한 기반 클래스, M47)을 근본적으로 피하는 길은 "상속보다 조합"이다.** 별개 객체를 필드로 갖고 위임(`by`)하면 self-use 재진입과 초기화 함정이 사라진다. 코틀린은 상속을 봉인하는 대신 확장·인터페이스·위임이라는 덜 위험한 대안을 제공한다.

- [[33 - 제네릭 1 - 타입 파라미터와 변성]] — 오버라이드의 공변 반환·불변 파라미터가 변성 규칙(out/in)의 씨앗. 그 이론적 완성.
