[[21 - 클래스와 생성자]]에서는 *하나의* 클래스가 자기 자신을 초기화하는 과정을 자세히 살펴보았다. 주 생성자와 부 생성자, `init` 블록과 프로퍼티 초기화자가 한 클래스 안에서 어떤 순서로 번갈아 실행되는지 확인했고, "부 생성자가 있으면 주 생성자 초기화가 실행되지 않는다"는 오해가 왜 틀렸는지도 보였다. 하지만 그 논의에는 한계가 있었다. 클래스 계층이 없었기 때문이다. 모든 예제는 상위 타입이 없는 독립된 클래스였다.

이 장에서는 클래스가 다른 클래스를 *상속할* 때 일어나는 일을 JVM 수준까지 내려가 살펴본다. `open`으로 상속을 허용하는 문법, `override`로 상위 클래스의 동작을 바꾸는 규칙, `super`로 가려진 구현을 다시 호출하는 방법, 그리고 무엇보다 **초기화가 상위 클래스에서 하위 클래스 순서로 진행된다는 점**을 다룬다.

핵심은 두 가지다. 하나는 초기화 순서를 실행 다이어그램으로 확정하는 것이고, 다른 하나는 이 순서 때문에 "오버라이드한 멤버를 상위 생성자에서 호출해도 안전하다"는 생각이 틀리다는 것을 보이는 것이다.

이 장은 클래스와 클래스 사이의 단일 상속, 그리고 그 위에서의 오버라이딩과 초기화만 다룬다. 인터페이스의 다중 상속, 백킹 필드가 없는 인터페이스 프로퍼티, 다이아몬드 충돌의 해소는 [[25 - 인터페이스]]에서 다루고, 여기서는 `super<A>.f()` 문법만 간단히 소개한다.

프로퍼티가 백킹 필드로 컴파일되는 방식은 [[22 - 프로퍼티와 백킹 필드]]에서, `val`이 재대입만 막을 뿐 불변을 보장하지 않는다는 점은 [[11 - 변수와 초기화 - val과 const와 lateinit]]에서, 상속 대신 `by`로 위임하는 방법은 [[32 - 클래스 위임]]에서 설명한다.

## 1. `final`이 기본값인 이유: 취약한 기반 클래스 문제

### 1.1 기본적으로 상속할 수 없는 클래스

코틀린에서 아무 수식어 없이 선언한 클래스는 상속할 수 없다.

```kotlin
class Animal
class Dog : Animal()   // 컴파일 에러: This type is final, so it cannot be inherited from
```

멤버도 마찬가지다. 클래스를 `open`으로 열더라도, 그 안의 함수와 프로퍼티는 여전히 오버라이드할 수 없다.

```kotlin
open class Animal {
    fun sound(): String = "..."         // 암시적 final
}
class Dog : Animal() {
    override fun sound(): String = "멍"  // 컴파일 에러: 'sound' in 'Animal' is final, cannot be overridden
}
```

상속 계층을 만들려면 두 곳에 명시적으로 `open`을 붙여야 한다. 하나는 클래스 앞이고, 다른 하나는 오버라이드를 허용할 각 멤버 앞이다.

```kotlin
open class Animal {
    open fun sound(): String = "..."
}
class Dog : Animal() {
    override fun sound(): String = "멍"  // => OK
}
```

이 기본값은 자바와 정반대다. 자바에서는 클래스와 메서드를 기본으로 오버라이드*할 수 있고*, 이를 막으려면 `final`을 붙여야 한다. 코틀린은 이 정책을 뒤집었다. 그 이유는 무엇일까?

### 1.2 "상속을 위해 설계하고 문서화하라, 그러지 않을 거라면 금지하라"

이 결정의 사상적 배경은 조슈아 블로크(Joshua Bloch)의 『이펙티브 자바』 항목 19, "상속을 위해 설계하고 문서화하라, 그럴 수 없다면 상속을 금지하라"이다. 핵심은 **상속이 캡슐화를 깨뜨리는 위험한 결합**이라는 점이다.

이 문제를 취약한 기반 클래스(fragile base class) 문제라고 부른다. 누군가 클래스 `Base`를 상속해 `Derived`를 만들었다고 하자. 나중에 `Base`의 작성자가 내부 구현을 "겉보기에는 무해하게" 바꾼다. 예를 들어 어떤 공개 메서드가 내부에서 다른 공개 메서드를 호출하도록 리팩터링한다.

그러면 두 메서드를 모두 오버라이드한 `Derived`에서는 자신이 예상하지 못한 방식으로 자기 오버라이드가 다시 호출(re-entrant)되면서 동작이 깨진다. `Base`의 작성자는 API 시그니처를 하나도 바꾸지 않았는데도 그렇다.

잘 알려진 예를 코틀린으로 옮겨 보자. 원소를 추가한 횟수를 세는 컬렉션이다.

```kotlin
open class CountingSet<T> {
    var addCount = 0
        private set
    private val backing = mutableSetOf<T>()

    open fun add(element: T): Boolean {
        addCount++
        return backing.add(element)
    }
    open fun addAll(elements: Collection<T>): Boolean {
        addCount += elements.size          // 여기서 세고
        return backing.addAll(elements)    // 내부적으로 add를 부를 수도, 안 부를 수도
    }
}
```

어떤 하위 클래스가 `add`만 오버라이드해 로그를 남기는데 `addAll`의 내부 구현이 `add`를 반복 호출한다면, 원소가 실제로 두 번 세어질 수 있다. 반대로 `addAll`이 `add`를 호출하지 않도록 구현을 바꾸면 하위 클래스의 로그가 갑자기 남지 않는다. **하위 클래스가 올바르게 동작하는지가 상위 클래스의 문서화되지 않은 내부 호출 패턴(self-use)에 의존**하게 된 것이다. 시그니처는 완벽히 호환되므로, 컴파일러는 이 의존을 잡아내지 못한다.

블로크의 처방은 두 가지였다.

- 상속을 정말 의도한다면, 어떤 메서드가 내부에서 어떤 메서드를 호출하는지 문서로 남긴다. 이때 self-use 패턴 자체가 API의 일부가 된다.
- 그럴 의도가 없다면 클래스를 `final`로 잠가 상속을 아예 막는다.

자바는 두 번째 처방을 *옵트인*으로 두었다. 즉 개발자가 명시적으로 `final`을 붙여야만 클래스가 잠긴다. 현실에서는 개발자들이 `final`을 잘 붙이지 않았고, 잠기지 않은 클래스들이 곳곳에서 상속되면서 취약해졌다.

코틀린은 두 번째 처방을 *기본값*으로 만들었다. 이제 상속을 허용하려면 `open`이라는 명시적인 의사 표시가 필요하므로, 상속 허용은 신중한 결정이 된다. 상속 금지가 기본이기 때문에, `open`이 붙은 클래스를 보면 "작성자가 상속을 *의도했고*, self-use 패턴도 고려했을 것"이라고 믿을 근거가 생긴다.

> [!info] 역사 메모
> 이 결정은 논쟁을 불러왔다. 스프링(Spring)처럼 런타임에 클래스를 프록시로 감싸 확장하는(subclass 기반 AOP) 자바 프레임워크들은 코틀린 클래스가 `final`이라서 프록시를 만들 수 없었다.
>
> 그래서 코틀린은 `all-open` 컴파일러 플러그인(과 스프링 전용 `kotlin-spring`)을 제공한다. 특정 애노테이션이 붙은 클래스를 컴파일 시점에 자동으로 `open`으로 바꿔 주는 플러그인이다. 언어의 기본값은 안전한 쪽(상속 금지)으로 두고, 프레임워크의 요구는 플러그인으로 예외 처리한 절충안이다.

### 1.3 상속 금지의 이점과 비용

상속을 막으면 **불변식(invariant)을 보호할 수 있다**. `final` 클래스의 작성자는 자신의 메서드가 절대 오버라이드되지 않는다는 것을 안다. 따라서 한 메서드가 다른 메서드를 호출할 때, 그 호출이 항상 *자신이 작성한* 구현으로 간다고 확신할 수 있다. 이런 확신이 있어야 클래스 내부 로직을 자유롭게 리팩터링할 수 있다. 상속 금지는 나중에 자유롭게 리팩터링할 수 있도록 보장해 주는 장치다.

비용은 **유연성을 미리 포기해야 한다는 점**이다. 라이브러리 사용자가 "이 클래스의 이 메서드 하나만 조금 바꿔서 쓰고 싶다"고 해도, 작성자가 `open`을 붙여 두지 않았다면 상속으로는 바꿀 수 없다.

코틀린은 이 비용을 다른 도구로 보완한다. 확장 함수([[35 - 확장 함수와 프로퍼티]])로 기존 타입에 기능을 덧붙이고, 클래스 위임(32장)으로 상속 없이 동작을 조합하며, 인터페이스(25장)로 계약만 공유한다. 이 도구들 가운데 상속은 *가장 강력하지만 결합도도 가장 높은* 도구다. 그래서 코틀린은 상속을 기본으로 허용하지 않고, 필요할 때만 꺼내 쓰도록 했다.

## 2. `open`, `abstract`, `override`: 상속 문법의 세 가지 키워드

### 2.1 `open` 멤버와 `override`의 의무

상속 문법의 뼈대는 세 키워드로 이루어진다.

- `open`: 오버라이드를 *허용*한다.
- `abstract`: 구현 없이 두고 오버라이드를 *강제*한다.
- `override`: 상위 멤버를 대체한다고 *선언*한다.

먼저 `open`과 `override`가 짝을 이루는 모습을 보자.

```kotlin
open class Shape {
    open fun area(): Double = 0.0
    open val name: String = "도형"
}

class Circle(val radius: Double) : Shape() {
    override fun area(): Double = Math.PI * radius * radius
    override val name: String = "원"
}
```

코틀린에서 `override`는 **선택이 아니라 의무**다. 상위 클래스의 `open` 멤버와 시그니처가 같은 멤버를 하위 클래스에 선언하면서 `override`를 빠뜨리면 컴파일되지 않는다.

```kotlin
class Square(val side: Double) : Shape() {
    fun area(): Double = side * side  // 컴파일 에러: 'area' hides member of supertype 'Shape' and needs 'override' modifier
}
```

이 강제는 두 방향의 버그를 막아 준다.

**첫째, 의도하지 않은 오버라이드를 막는다.** 자바에서는 상위 클래스에 있는지도 몰랐던 메서드와 이름과 시그니처가 우연히 겹치면 아무 경고 없이 오버라이드가 일어난다. 상위 클래스가 나중에 같은 이름의 메서드를 추가해도 마찬가지다. 코틀린에서는 `override` 없이 이런 일이 일어날 수 없다. 우연히 겹치면 "override 키워드가 필요하다"는 에러로 바로 드러난다.

**둘째, 오버라이드했다고 착각한 오타를 잡는다.** 반대로 오버라이드할 *의도*로 `override`를 붙였는데 상위 클래스에 그런 멤버가 없다면(예를 들어 `area`를 `aera`로 잘못 썼다면), 이것도 컴파일 에러가 된다.

```kotlin
class Triangle : Shape() {
    override fun aera(): Double = 0.0  // 컴파일 에러: 'aera' overrides nothing
}
```

자바에서는 `@Override` 애노테이션이 이 역할을 하지만, *권장* 사항이라서 붙이는 것을 잊으면 보호받지 못한다. 코틀린은 이를 애노테이션이 아니라 *키워드*로 만들어 강제했다. 그래서 두 방향 모두에서 "이름은 같은데 의도가 어긋난" 상황이 컴파일 타임에 잡힌다. 런타임에 발생할 오류를 타입 시스템으로 미리 잡는다는 점에서, 널 안전성과 같은 설계 철학이다.

### 2.2 `abstract`: 구현 없는 계약

`abstract`는 "이 멤버는 여기서 구현하지 않으니, 하위 클래스가 반드시 구현하라"는 선언이다. 추상 멤버가 하나라도 있으면 클래스도 `abstract`여야 하고, 추상 클래스는 인스턴스로 만들 수 없다.

```kotlin
abstract class Shape {
    abstract fun area(): Double        // 본문 없음
    abstract val name: String          // 초기화자 없음

    fun describe(): String = "$name: 넓이 ${area()}"  // 구체 메서드가 추상 멤버를 사용
}

val s = Shape()  // 컴파일 에러: Cannot create an instance of an abstract class
```

여기서 중요한 점이 두 가지 있다.

첫째, **`abstract` 멤버는 암시적으로 `open`이다.** 추상 멤버는 정의상 오버라이드되어야 하므로 `open`을 따로 붙일 필요가 없다(붙이면 불필요한 중복이다). 상속 금지가 기본인 코틀린에서 `abstract`는 상속을 허용하는 또 하나의 방법이다. 다만 `open`보다 강해서, "열어 두었다"가 아니라 "반드시 구현하라"는 뜻이다.

둘째, **추상 클래스도 상태와 구체적인 구현을 가질 수 있다.** 위의 `describe()`처럼 추상 멤버를 사용하는 구체 로직을 둘 수 있고, 생성자와 프로퍼티(백킹 필드 포함)도 가질 수 있다. 이 점이 인터페이스와 결정적으로 다르다. 인터페이스의 프로퍼티는 백킹 필드를 가질 수 없어서 상태를 저장하지 못한다(25장 인터페이스). 추상 클래스는 "일부만 구현된 클래스"이고, 인터페이스는 "상태 없는 계약"이다. 이 차이는 9절에서 선택 기준으로 다시 다룬다.

```text
open class     : 완전히 구현됨, 상속·오버라이드 허용
abstract class : 일부만 구현됨(추상 멤버 존재), 인스턴스화 불가, 상태 가능
interface      : 계약 + 기본 구현, 상태(백킹 필드) 불가, 다중 상속 가능
```

### 2.3 `override`한 멤버는 그 자체로 `open`이다: `final override`

미묘해서 자주 놓치는 규칙이 있다. **오버라이드한 멤버는 따로 표시하지 않으면 계속 `open`이다.** 즉 오버라이드했다고 해서 다시 잠기지 않는다.

```kotlin
open class A {
    open fun f() = println("A.f")
}
open class B : A() {
    override fun f() = println("B.f")   // override지만 여전히 open — C가 또 오버라이드 가능
}
class C : B() {
    override fun f() = println("C.f")   // => OK
}
```

`B.f`에는 `override`만 붙였고 `open`은 쓰지 않았지만, `C`는 이 메서드를 오버라이드할 수 있다. "한 번 열린 멤버는 계층 아래로 계속 열려 있다"는 규칙 때문이다. 이 연결을 중간에서 끊으려면 `final override`를 명시한다.

```kotlin
open class B : A() {
    final override fun f() = println("B.f")  // 여기서 봉인
}
class C : B() {
    override fun f() = println("C.f")  // 컴파일 에러: 'f' in 'B' is final, cannot be overridden
}
```

`final override`는 "상위 클래스의 계약은 지키되(오버라이드), 내 아래로는 더 바꾸지 못하게 잠근다(final)"는 뜻으로 흔히 쓰는 관용구다. 계층 중간에 있는 클래스가 자기 오버라이드의 불변식을 하위 클래스로부터 지키고 싶을 때 쓴다.

### 2.4 시그니처 규칙: 공변 반환, 불변 파라미터

오버라이드가 성립하려면 시그니처가 맞아야 한다. 그런데 "맞는다"의 정의는 반환 타입과 파라미터 타입에서 서로 다르다.

**반환 타입은 공변(covariant)이다.** 오버라이드하는 함수는 상위 클래스가 선언한 반환 타입의 *하위 타입*을 반환할 수 있다.

```kotlin
open class Animal
class Cat : Animal()

open class AnimalShelter {
    open fun adopt(): Animal = Animal()
}
class CatShelter : AnimalShelter() {
    override fun adopt(): Cat = Cat()   // => OK: Cat은 Animal의 하위 타입 (공변 반환)
}
```

이 규칙은 리스코프 치환 원칙(LSP)과 정확히 들어맞는다. `AnimalShelter`를 기대하는 코드는 `adopt()`가 `Animal`을 반환한다고 가정한다. `CatShelter`가 더 구체적인 `Cat`을 반환해도 이 가정은 깨지지 않는다(`Cat`도 `Animal`이기 때문이다). 반환 위치는 값을 *생산*(out)하는 위치이므로 하위 타입을 써도 안전하다. 이 직관이 변성([[33 - 제네릭 1 - 타입 파라미터와 변성]])의 출발점이 된다.

**파라미터 타입은 불변(invariant)이다.** 파라미터 타입을 넓히거나(반공변) 좁히면(공변) 오버라이드가 아니라 오버로드가 되거나 컴파일 에러가 난다.

```kotlin
open class Printer {
    open fun print(x: Animal) {}
}
class BadPrinter : Printer() {
    override fun print(x: Cat) {}  // 컴파일 에러: 'print' overrides nothing
                                   // (Cat을 받는 print는 Animal을 받는 print를 오버라이드하지 못함)
}
```

파라미터를 좁히면(`Cat`만 받게 하면) `Printer`로 보고 `Animal`을 넘기는 코드가 깨진다. 이는 LSP 위반이므로 처음부터 오버라이드로 인정되지 않는다. 파라미터는 값을 *소비*(in)하는 위치라서 상위 타입이어야 안전한데, 코틀린은 그 방향의 변경도 오버라이드로 허용하지 않고 별개의 메서드(오버로드)로 취급한다.

> [!note] 명세 기준
> 가시성(visibility)에도 규칙이 있다. 오버라이드하는 멤버는 상위 멤버보다 가시성을 *넓힐* 수는 있지만 좁힐 수는 없다. `protected open fun`을 `public override fun`으로 넓히는 것은 허용되지만, `public`을 `protected`로 좁히면 LSP를 깨므로 금지된다([[26 - 가시성 한정자]]).

## 3. 프로퍼티 오버라이딩: 필드가 아니라 접근자를 바꾼다

### 3.1 `val`을 `var`로 바꿀 수는 있지만, `var`를 `val`로는 바꿀 수 없다

프로퍼티도 함수처럼 오버라이드할 수 있다. 여기서 프로퍼티가 *접근자를 추상화한 것*이라는 사실(22장 프로퍼티와 백킹 필드)이 결정적인 역할을 한다. 프로퍼티를 오버라이드한다는 것은 **필드를 바꾸는 것이 아니라 게터와 세터를 바꾸는 것**이다.

`val`은 `var`로 오버라이드할 수 있다.

```kotlin
open class Base {
    open val x: Int = 1     // 게터만
}
class Derived : Base() {
    override var x: Int = 2 // 게터 + 세터
        get() = field
        set(value) { field = value }
}
```

접근자 관점에서 보면 이것이 가능한 이유가 분명해진다. `val x`는 "게터가 있다"는 계약이고, `var x`는 "게터가 있고 *추가로* 세터도 있다"는 계약이다. `var`는 `val`이 요구하는 게터를 이미 포함하므로, `var`로 오버라이드해도 상위 클래스의 `val` 계약("읽을 수 있다")을 완전히 만족한다. 세터는 추가로 생긴 기능일 뿐이다.

반대 방향은 불가능하다.

```kotlin
open class Base {
    open var y: Int = 1
}
class Derived : Base() {
    override val y: Int = 2  // 컴파일 에러: 'var'-property cannot be overridden by 'val'-property
}
```

`var y`를 기대하는 코드는 `y = 3`처럼 값을 *쓸* 수 있다고 가정한다. 이 프로퍼티를 `val`(게터만 있음)로 오버라이드하면 세터가 사라져 그 가정이 깨지므로, LSP 위반이다. 즉 **계약을 넓히는 방향(val→var)은 허용되고, 좁히는 방향(var→val)은 허용되지 않는다.** 2.4절에서 본 반환 타입 공변이나 가시성 확대와 같은 원리의 규칙이다.

| 상위 | 하위 오버라이드 | 가능? | 이유 |
|------|----------------|-------|------|
| `open val x` | `override val x` | O | 게터 계약 유지 |
| `open val x` | `override var x` | O | 게터 계약 + 세터 추가 (넓힘) |
| `open var y` | `override var y` | O | 게터·세터 계약 유지 |
| `open var y` | `override val y` | X | 세터 계약 상실 (좁힘, LSP 위반) |

### 3.2 게터 오버라이드와 백킹 필드

프로퍼티 오버라이드가 접근자를 바꾸는 것이라는 점은, 하위 클래스에서 초기화자 대신 *커스텀 게터*로 오버라이드하는 경우에 가장 잘 드러난다.

```kotlin
open class Rectangle(val width: Int, val height: Int) {
    open val area: Int = width * height   // 백킹 필드 있음, 생성 시 한 번 계산
}

class MutableRectangle(var w: Int, var h: Int) : Rectangle(w, h) {
    override val area: Int
        get() = w * h                      // 백킹 필드 없음, 접근할 때마다 계산
}
```

상위 클래스의 `Rectangle.area`에는 백킹 필드가 있다. 생성 시점에 `width * height`를 한 번 계산해 필드에 저장한다. 하위 클래스의 `MutableRectangle.area`는 **커스텀 게터로 오버라이드했으므로 백킹 필드가 없고**, 접근할 때마다 `w * h`를 다시 계산한다. `w`와 `h`가 `var`라서 값이 바뀔 수 있으므로 이렇게 다시 계산해야 한다.

핵심은 오버라이드된 프로퍼티에 접근할 때 *어느 접근자가 실행되는지*가 런타임 타입에 따라 결정된다는 점이다. `MutableRectangle` 인스턴스를 `Rectangle` 타입 변수에 담아 `area`를 읽어도, 실행되는 것은 하위 클래스의 커스텀 게터다. 프로퍼티 접근도 함수 호출과 똑같이 **동적 디스패치**된다(7절). 프로퍼티는 필드처럼 *보이지만*, 오버라이드 관점에서는 완전히 메서드처럼 동작한다.

6절에서 다룰 초기화 함정은 이 사실에서 비롯된다. 상위 생성자에서 `area`를 읽으면, 이 접근은 필드 읽기가 아니라 *하위 클래스의 게터 호출*로 디스패치된다. 그리고 그 게터는 아직 초기화되지 않은 하위 클래스의 필드(`w`, `h`)를 읽을 수 있다.

> [!caution] 성능 주의
> `open val area = width * height`(필드에 저장)와 `open val area get() = width * height`(매번 계산)는 의미가 다르다. 전자는 값을 한 번 계산해 캐시하지만 오버라이드 함정에 노출되고, 후자는 접근할 때마다 비용이 들지만 항상 최신 값을 돌려준다. `open` 프로퍼티에서 이 선택은 성능 문제일 뿐 아니라 초기화 안전성 문제이기도 하다.

### 3.3 생성자 파라미터로 선언한 오버라이드 프로퍼티

주 생성자 파라미터에 `override`를 직접 붙일 수도 있다. 이 경우 상위 클래스의 추상 프로퍼티나 열린 프로퍼티가 생성자를 통해 채워진다.

```kotlin
abstract class Vehicle {
    abstract val wheels: Int
}

class Car(override val wheels: Int = 4) : Vehicle()
class Motorcycle : Vehicle() {
    override val wheels: Int = 2
}

val v: Vehicle = Car()
println(v.wheels)  // => 4
```

`Car`는 추상 프로퍼티 `wheels`를 생성자 파라미터로 구현했다. 문법으로 보면 21장(클래스와 생성자)에서 본 "주 생성자 프로퍼티" 선언(파라미터에 `val`을 붙여 프로퍼티로 만드는 것)에 `override`를 더한 것이다. 이 프로퍼티에는 백킹 필드가 있고, 생성자가 그 필드를 채운다.

주의할 점이 있다. 이 프로퍼티의 필드가 채워지는 시점은 여전히 하위 클래스의 초기화 단계다. 따라서 상위 클래스 `Vehicle`의 `init` 블록에서 `wheels`를 읽으면 아직 0이다(6절에서 재현한다). 생성자 파라미터로 오버라이드했다고 해서 초기화 순서 규칙에서 벗어나는 것은 아니다.

## 4. `super`: 가려진 상위 구현을 호출하는 방법

### 4.1 `super.method()`의 의미와 정적 바인딩

오버라이드하면 상위 클래스의 구현이 *가려진다*. 가려진 상위 구현을 하위 클래스에서 다시 호출하려면 `super`를 쓴다. 흔한 패턴은 "상위 클래스의 동작을 실행한 뒤 추가 작업을 하는 것"이다.

```kotlin
open class Logger {
    open fun log(msg: String) {
        println("[LOG] $msg")
    }
}
class TimestampLogger : Logger() {
    override fun log(msg: String) {
        super.log("${System.currentTimeMillis()} $msg")  // 상위 구현 재사용
    }
}
```

`super.log(...)`는 `TimestampLogger`가 오버라이드해서 가린 `Logger.log`를 지정해 호출한다. 여기서 중요한 성질이 있다. **`super` 호출은 정적으로 바인딩된다(statically bound).**

`super.log`는 "이 클래스의 *바로 위* 상위 클래스의 `log`"로 컴파일 타임에 확정된다. 하위 클래스가 더 있더라도 `super`는 절대 아래쪽으로 디스패치되지 않는다. 이것이 일반 메서드 호출(동적 디스패치)과 `super` 호출(정적 디스패치)의 근본적인 차이다.

JVM 백엔드는 일반 가상 호출을 `invokevirtual`로, `super` 호출을 `invokespecial`로 컴파일한다. `invokespecial`은 vtable을 거치지 않고 지정한 클래스의 메서드를 직접 호출하는 명령이다. 생성자 호출(`<init>`)과 private 메서드 호출에도 쓰이며, "바로 이 구현을 실행하라"는 뜻이다.

```text
일반 호출  obj.log(m)      → invokevirtual  (런타임 타입의 vtable에서 찾음, 동적)
super 호출  super.log(m)    → invokespecial  (지정 클래스 구현 직접, 정적)
```

이렇게 정적으로 바인딩되므로 `super`는 무한 재귀를 만들지 않는다. `super.log`가 다시 아래로 디스패치되어 자기 자신(`TimestampLogger.log`)을 호출한다면 무한 루프가 되겠지만, 정적 바인딩이 이를 막는다.

### 4.2 다중 상속 충돌과 `super<A>.f()`

클래스 단일 상속에서는 `super`가 가리키는 대상이 하나뿐이다(상위 클래스가 하나이기 때문이다). 하지만 클래스 하나와 인터페이스 여러 개를 상속하면 시그니처가 같은 기본 구현을 여러 개 상속받을 수 있고, 이때는 `super`만으로 어느 구현인지 알 수 없다. 이 문제의 해결 방법은 25장(인터페이스)에서 자세히 다루고, 여기서는 문법의 모양만 미리 살펴본다.

```kotlin
open class Machine {
    open fun start() = println("기계 시동")
}
interface Rechargeable {
    fun start() { println("충전 확인 후 시동") }  // 인터페이스 기본 구현
}

class ElectricCar : Machine(), Rechargeable {
    override fun start() {
        super<Machine>.start()        // 클래스 쪽 구현
        super<Rechargeable>.start()   // 인터페이스 쪽 구현
    }
}
// ElectricCar().start()
// => 기계 시동
// => 충전 확인 후 시동
```

`ElectricCar`는 `Machine`(클래스)의 `start`와 `Rechargeable`(인터페이스)의 기본 `start`를 모두 상속받는다. 코틀린은 이 충돌을 **컴파일 에러로 알려서** 하위 클래스가 반드시 오버라이드해 모호성을 해결하도록 한다. 오버라이드한 메서드 안에서는 `super<Machine>.start()`, `super<Rechargeable>.start()`처럼 꺾쇠괄호로 어느 상위 타입인지 명시한다.

이렇게 충돌을 명시적으로 해결하게 하는 것이 "다이아몬드 문제"에 대한 코틀린의 답이다. 어떤 조합이 충돌로 판정되는지, 인터페이스끼리 충돌하면 어떻게 되는지 같은 자세한 규칙은 25장에서 설명한다.

> [!note] 명세 기준
> 이너 클래스([[31 - 중첩 클래스와 이너 클래스와 익명 객체]])에서 바깥 클래스의 `super`를 호출하려면 `super@Outer.f()`처럼 라벨을 붙인다. `super`는 "현재 클래스의 상위"를 가리키므로, 클래스가 중첩된 상황에서는 어느 `this`의 상위인지를 라벨로 명시해야 한다.

## 5. 초기화 순서: 상위에서 하위로 진행된다

이 장의 첫 번째 핵심 주제다. 상속 계층에서 인스턴스를 만들 때 각 계층의 생성자, `init` 블록, 프로퍼티 초기화자는 정확히 어떤 순서로 실행될까?

### 5.1 생성자 위임 연쇄: 상위 생성자가 반드시 먼저 실행된다

21장(클래스와 생성자)에서는 한 클래스 안의 실행 순서를 확인했다. 프로퍼티 초기화자와 `init` 블록이 소스에 나온 순서대로 번갈아 실행된다. 클래스 계층이 생기면 여기에 **"상위가 하위보다 먼저"** 라는 규칙이 더해진다.

주 생성자가 있는 하위 클래스는 상위 타입 지정자에서 상위 생성자를 호출한다.

```kotlin
open class Base(val a: Int)
class Derived(val b: Int) : Base(b * 10)  // Base(...) 호출이 상위 초기화
```

`Derived(3)`을 만들면 `Base(30)`가 *먼저* 완전히 초기화되고, 그다음에 `Derived` 부분이 초기화된다. 이 순서는 바꿀 수 없다. JVM 백엔드에서 이 순서는 언어 규칙일 뿐 아니라 바이트코드 검증기(verifier)의 요구 사항이기도 하다. 하위 생성자 `<init>`는 자기 본문의 어떤 코드보다도 먼저 상위 `<init>`를 `invokespecial`로 호출해야 한다. "상위를 초기화하기 전에는 하위 필드를 건드릴 수 없다"는 것이 JVM 수준의 계약이다.

주 생성자가 없는 클래스에서는 각 부 생성자가 `super(...)`로 상위 클래스를 초기화하거나, `this(...)`로 다른 부 생성자에 위임한다.

```kotlin
open class Base(val a: Int)
class Derived : Base {
    val b: Int
    constructor(b: Int) : super(b * 10) {  // super로 상위 초기화
        this.b = b
    }
}
```

어느 경로로 가든 결론은 같다. **상위 생성자가 완전히 끝난 뒤에야 하위 클래스의 초기화가 시작된다.**

### 5.2 한 클래스 안의 순서를 계층으로 확장하기

한 클래스 안의 초기화 순서를 다시 떠올려 보자(21장). 먼저 주 생성자 파라미터를 평가하고, 그다음 소스에 나온 순서대로 프로퍼티 초기화자와 `init` 블록을 실행한다. 이를 계층에 적용하면, 각 계층 안에서는 이 순서대로 실행되고 계층 자체는 위에서 아래로 진행된다.

세 단계 계층으로 전체 순서를 재현해 보자.

```kotlin
open class A {
    val a1 = log("A.a1 초기화자")
    init { log("A.init 블록") }
    val a2 = log("A.a2 초기화자")
    constructor() { log("A 생성자 본문") }
}

open class B : A {
    val b1 = log("B.b1 초기화자")
    init { log("B.init 블록") }
    constructor() : super() { log("B 생성자 본문") }
}

class C : B() {
    val c1 = log("C.c1 초기화자")
    init { log("C.init 블록") }
}

fun log(s: String): Unit = println(s)
```

`C()`를 실행하면 다음과 같이 출력된다.

```text
A.a1 초기화자      ← A층: 초기화자·init 블록 (소스 순서)
A.init 블록
A.a2 초기화자
A 생성자 본문       ← A층: 생성자 본문은 초기화자·init 블록 뒤
B.b1 초기화자      ← B층
B.init 블록
B 생성자 본문
C.c1 초기화자      ← C층
C.init 블록
```

이 결과에서 두 가지 규칙을 읽을 수 있다.

**규칙 1 (계층 사이): 위 계층이 완전히 끝난 뒤 아래 계층이 시작된다.** A의 모든 초기화(초기화자, init 블록, 생성자 본문)가 끝나야 B가 시작되고, B가 끝나야 C가 시작된다.

**규칙 2 (계층 안): 한 계층 안에서는 프로퍼티 초기화자와 `init` 블록이 소스에 나온 순서대로 실행되고, 생성자 본문은 그 뒤에 실행된다.** A 계층에서는 `a1`→`init`→`a2`가 소스 순서대로 실행된 다음 생성자 본문이 실행된다. 핵심은 부 생성자의 본문(`{ ... }`)이 그 계층의 초기화자와 init 블록 *뒤에* 실행된다는 점이다. `super()` 위임으로 상위 클래스를 먼저 초기화하고, 돌아와서 이 계층의 초기화자와 init 블록을 실행한 뒤, 마지막으로 생성자 본문을 실행한다.

### 5.3 전체 실행 순서 다이어그램

이 흐름을 시간 순서로 펼치면 다음과 같다. `Derived : Base(...)`처럼 한 단계 위임하는 경우를 기준으로 그렸다.

```text
new Derived(args) 요청
   │
   ├─ (1) Derived 주 생성자 파라미터의 기본값 표현식 평가 (필요 시)
   │        그리고 상위 지정자 Base(expr)의 expr 평가
   │
   ├─ (2) Base 생성자로 위임  ─────────────────┐
   │                                            │  ← 여기서부터 Base 초기화
   │        (2a) Base 프로퍼티 초기화자 + init  │     (this는 이미 Derived 인스턴스지만
   │             (소스 순서)                     │      Derived의 필드는 아직 전부 기본값!)
   │        (2b) Base 생성자 본문                │
   │                                            │
   │     ◄────────────────────────────────────┘  Base 초기화 완료, Derived로 복귀
   │
   ├─ (3) Derived 프로퍼티 초기화자 + init 블록 (소스 순서)
   │
   └─ (4) Derived 생성자 본문 (부 생성자면 그 본문)
           인스턴스 준비 완료
```

(2a)의 주석에 적어 둔 사실이 6절에서 다룰 함정의 원인이다. **(2) 단계에서 `this`는 이미 `Derived` 타입의 객체다**(따라서 가상 디스패치는 `Derived`의 오버라이드로 간다).

그런데 그 시점에 `Derived`가 선언한 필드들은 (3) 단계가 아직 실행되지 않아 *기본값*(참조 타입은 `null`, 수치 타입은 `0`/`0.0`, 불리언은 `false`)이다. 즉 상위 생성자가 실행되는 동안에는 **"타입은 하위 클래스인데 필드는 초기화되지 않은"** 위험한 중간 상태가 존재한다.

> [!note] 명세 기준
> 이 순서는 코틀린만의 특징이 아니라, 대부분의 클래스 기반 OOP 언어(자바, C#, C++)에 공통된 근본적인 제약이다. 부분 객체(상위 부분)를 먼저 완성해야 전체 객체(하위 부분)를 만들 수 있다는 것은 상속 구조상 피할 수 없다. 다만 이 중간 상태에서 가상 디스패치가 어디로 가는지는 언어마다 다르다.
>
> 코틀린, 자바, C#에서는 생성 중에도 가상 호출이 하위 클래스의 오버라이드로 간다(그래서 함정이 생긴다). C++에서는 생성자가 실행되는 동안 `this`의 동적 타입을 "현재 생성 중인 계층"으로 취급하므로, 가상 호출이 하위 클래스로 가지 *않는다*(그래서 C++에는 이 함정이 없는 대신 다른 규칙이 있다). 이 차이는 6.2절에서 다시 살펴본다.

## 6. 생성자에서 `open` 멤버를 호출하는 함정

이 절에서 바로잡을 오해는 **"오버라이드한 프로퍼티나 함수를 `open` 클래스의 생성자에서 호출해도 안전하다"는 생각**이다. 이런 직관이다. "가상 함수를 호출하면 어차피 내 오버라이드가 실행될 테니, 상위 생성자든 어디서든 호출해도 올바르게 동작할 것이다." 이 직관은 틀렸고, 그 이유는 5절에서 확인한 초기화 순서에 있다.

### 6.1 초기화되지 않은 필드가 보이는 순간

가장 짧은 예제로 재현해 보자. 상위 생성자가 오버라이드된 프로퍼티를 읽는다.

```kotlin
open class Base {
    open val size: Int = 0

    init {
        println("Base.init: size = $size")  // open 프로퍼티를 상위 초기화에서 읽음
    }
}

class Derived : Base() {
    override val size: Int = 42
}

fun main() {
    Derived()
}
// 출력:
// Base.init: size = 0     ← 42가 아니라 0!
```

결과는 기대와 다르다. `Derived.size`를 42로 오버라이드했지만, `Base.init`이 읽은 값은 42가 아니라 **0**이다. 5.3절의 다이어그램을 따라가 보면 이유가 분명해진다.

1. `Derived()`가 `Base()`에 위임한다(단계 2).
2. `Base`의 초기화가 시작된다. `Base.init`의 `$size`는 `size` 게터를 호출한다.
3. `size`는 `open`이고 `this`는 `Derived`이므로, 게터 호출은 **`Derived.size`로 디스패치**된다.
4. 이때 `Derived.size`의 백킹 필드에는 무엇이 들어 있을까? `Derived`의 프로퍼티 초기화자(`= 42`)는 단계 3에서야 실행되는데, 지금은 아직 단계 2다. 그래서 필드에는 초기화 전 기본값인 **0**이 들어 있다.
5. 게터는 그 필드 값(0)을 반환하고, `Base.init`은 0을 출력한다.

함수를 호출하면 더 위험하다. 초기화되지 않은 참조 필드를 사용하면 `NullPointerException`이 발생한다.

```kotlin
open class View(open val title: String) {
    init {
        // 상위 생성자가 오버라이드된 메서드를 호출
        render()
    }
    open fun render() {
        println("렌더링: $title")
    }
}

class Button(override val title: String, private val label: String) : View(title) {
    override fun render() {
        // label을 대문자로 — 그런데 이 시점에 label은?
        println("버튼[${label.uppercase()}]: $title")
    }
}

fun main() {
    Button("확인", "OK")
}
// 컴파일은 되지만 런타임에:
// Exception: NullPointerException
//   (label이 아직 null인 채 label.uppercase() 호출)
```

`View`의 `init`이 `render()`를 호출한다. `render`는 `open`이고 `this`는 `Button`이므로 `Button.render`로 디스패치된다. 그런데 `Button.render`는 `label`을 사용한다.

`label`은 `Button`의 생성자 파라미터 프로퍼티이므로, 그 필드는 `View`의 초기화가 끝난 *뒤에야* 채워진다. 따라서 `View.init` 시점의 `label`은 `null`이다(널이 될 수 없는 `String`으로 선언했는데도 그렇다). 결국 `label.uppercase()`에서 NPE가 발생한다.

이 함정의 핵심은 **널 안전성을 보장한다고 믿는 코틀린에서도, 초기화 순서의 틈에서는 널이 될 수 없는 프로퍼티가 `null`인 순간이 있다**는 점이다. 컴파일러는 이 함정을 대부분 잡아내지 못한다(가상 디스패치를 거친 흐름까지 추적하기 어렵기 때문이다).

다만 IDE와 컴파일러는 생성자에서 open 멤버를 호출하는 코드에 경고(`Calling non-final function in constructor` / `Accessing non-final property in constructor`)를 표시한다. 이 경고는 무시하면 안 되는 실제 문제의 신호다.

### 6.2 왜 이런 순서가 되는가: 가상 디스패치와 초기화의 충돌

여기서는 두 규칙이 서로 충돌한다.

- **규칙 A (동적 디스패치):** `open` 멤버를 호출하면 항상 런타임 타입의 오버라이드가 실행된다. `this`가 `Button`이면 `Button.render`가 실행된다.
- **규칙 B (초기화 순서):** 상위 클래스의 초기화가 하위 클래스의 초기화보다 먼저 끝난다. 상위 클래스를 초기화하는 동안 하위 클래스의 필드는 아직 초기화되지 않은 상태다.

상위 생성자에서 `open` 멤버를 호출하면 두 규칙이 정면으로 충돌한다. 규칙 A는 "하위 클래스의 오버라이드를 실행하라"고 하고, 규칙 B는 "그런데 하위 클래스의 필드는 아직 준비되지 않았다"고 한다. 결과적으로 "존재하지만 아직 비어 있는 하위 객체의 메서드"를 실행하게 된다. 즉 절반만 생성된 객체(half-constructed object)에서 메서드를 호출하는 것이다.

5.3절의 명세 기준에서 언급했듯이, C++은 이 충돌을 *다른 방식*으로 해결한다. 생성자가 실행되는 동안 `this`의 가상 타입을 "지금 생성 중인 계층"으로 고정하므로, 상위 생성자에서 가상 함수를 호출하면 하위 클래스가 아니라 *상위 클래스의* 구현이 실행된다. 그래서 C++에는 이 NPE 함정이 없다. 대신 "상위 생성자에서 호출한 가상 함수는 하위 클래스의 오버라이드로 가지 않는다"는, 초보자를 당황하게 하는 다른 규칙이 생긴다.

코틀린, 자바, C#은 반대로 선택했다. 생성 중에도 `this`는 최종 런타임 타입이고, 가상 호출은 하위 클래스로 간다. 이 선택의 대가가 바로 이 함정이다. 어느 쪽에도 비용이 있으며, 두 방식 모두 "상위 생성자에서 가상 멤버를 호출하지 마라"는 결론에 도달한다.

정리하면, 이 함정은 언어 설계의 근본적인 트레이드오프에서 생긴 *구조적인* 문제이지 코틀린의 버그가 아니다. 그래서 해법은 "고치는 것"이 아니라 "피하는 것"이다.

### 6.3 방어책: `final`, `private`, 팩토리, 지연 초기화

**방어 1: 생성자에서 호출하는 멤버는 `final`이나 `private`으로 둔다.** 오버라이드할 수 없는 멤버는 가상 디스패치가 일어나지 않으므로 함정도 없다. `private` 멤버는 처음부터 오버라이드 대상이 아니다.

```kotlin
open class View2(val title: String) {
    init {
        renderInternal()  // private → 항상 이 구현, 안전
    }
    private fun renderInternal() {
        println("렌더링: $title")  // title은 상위 프로퍼티, 이미 초기화됨
    }
}
```

`title`을 `View2`의 일반 프로퍼티(하위 클래스가 오버라이드하지 않는 프로퍼티)로 두고 `renderInternal`을 `private`으로 선언하면, 초기화 시점에도 안전하다.

**방어 2: 초기화 로직을 생성자 밖으로 옮긴다.** 객체를 다 만든 *뒤에* 초기화 메서드를 호출하는 팩토리 패턴을 쓴다.

```kotlin
open class Widget protected constructor() {
    open fun onCreate() {}   // 하위가 오버라이드해도 안전 — 생성 후 호출되므로
    companion object {
        fun <T : Widget> create(w: T): T {
            // w는 이미 완전히 생성됨. 이제 가상 호출해도 필드가 다 차 있다.
            w.onCreate()
            return w
        }
    }
}
```

**방어 3: `by lazy`로 계산을 미룬다.** 상위 클래스에서 즉시 계산하지 않고, 처음 접근할 때 계산하도록 미룬다([[23 - 위임 프로퍼티]]).

```kotlin
open class Report {
    open val header: String get() = "일반 보고서"
    // 지연: 최초 접근 시점엔 하위 필드가 다 차 있다
    val cachedHeader: String by lazy { header }
}
```

`cachedHeader`는 생성 시점이 아니라 처음 *접근하는* 시점에 `header`를 읽는다. 인스턴스가 완성된 뒤에 접근하면 하위 클래스의 오버라이드가 올바른 값을 돌려준다.

**방어 4: 아예 호출하지 않는다.** 가장 확실한 방어다. 코틀린 컴파일러나 IDE가 "생성자에서 non-final 멤버 호출" 경고를 표시하면, 그 호출을 팩토리나 지연 초기화, 명시적인 `init()` 호출로 옮긴다. 이 경고는 스타일 문제가 아니라 정확성 문제다.

> [!warning] 흔한 오해
> "그렇다면 상위 생성자에서는 어떤 멤버도 호출하면 안 되는가?" 그렇지 않다. `final` 멤버와 `private` 멤버, 그리고 상위 클래스 자신의 완전히 초기화된 프로퍼티는 얼마든지 호출할 수 있다. 위험한 것은 **오버라이드할 수 있는(`open`/`abstract`) 멤버**를 호출하는 경우뿐이다.
>
> 특히 `abstract` 멤버를 상위 생성자에서 호출하는 것은 매우 위험하다. 상위 클래스에는 구현조차 없으므로 반드시 하위 클래스의 오버라이드가 실행되고, 그 오버라이드는 거의 틀림없이 하위 클래스의 필드를 사용하기 때문이다.

## 7. 동적 디스패치의 동작 원리: vtable과 `invokevirtual`

6절의 함정을 제대로 이해하려면, "가상 호출이 하위 클래스로 간다"는 말이 JVM 수준에서 무엇을 뜻하는지 알아야 한다.

### 7.1 정적 타입과 런타임 타입

변수에는 두 가지 타입이 있다. 하나는 **정적 타입**(컴파일러가 컴파일 타임에 아는 선언 타입)이고, 다른 하나는 **런타임 타입**(그 변수가 실제로 가리키는 객체의 클래스)이다. 오버라이드된 멤버를 호출할 때는 정적 타입이 아니라 **런타임 타입**을 따른다.

```kotlin
open class Animal {
    open fun speak(): String = "..."
}
class Dog : Animal() {
    override fun speak(): String = "멍"
}
class Cat : Animal() {
    override fun speak(): String = "야옹"
}

fun main() {
    val animals: List<Animal> = listOf(Dog(), Cat())  // 정적 타입은 전부 Animal
    for (a in animals) {
        println(a.speak())  // 런타임 타입에 따라 다르게 디스패치
    }
}
// => 멍
// => 야옹
```

`a`의 정적 타입은 모두 `Animal`이다. 컴파일러는 `a`가 `Dog`인지 `Cat`인지 모른다. 그런데도 `a.speak()`는 각각 `Dog.speak`와 `Cat.speak`를 실행한다. 이처럼 정적 타입은 하나인데 런타임 타입에 따라 실행되는 구현이 달라지는 능력이 다형성(polymorphism)의 본질이다. 그리고 이를 구현하는 장치가 가상 메서드 테이블(virtual method table, vtable)이다.

### 7.2 JVM 백엔드의 `invokevirtual`

JVM 백엔드에서는 클래스마다 vtable이 있다. vtable은 오버라이드할 수 있는 각 메서드에 대해 "이 클래스에서 실제로 실행할 구현의 포인터"를 담은 배열이다. 하위 클래스는 상위 클래스의 vtable을 복사한 뒤, 자신이 오버라이드한 슬롯만 자기 구현으로 덮어쓴다.

```text
                 vtable (개념도)
Animal:   [ speak → Animal.speak ]
Dog:      [ speak → Dog.speak    ]   ← 슬롯 덮어씀
Cat:      [ speak → Cat.speak    ]   ← 슬롯 덮어씀

a.speak() 실행:
   1. a가 가리키는 객체의 헤더에서 클래스 포인터를 읽음 (런타임 타입 확인)
   2. 그 클래스의 vtable에서 speak 슬롯을 찾음
   3. 슬롯이 가리키는 구현으로 점프
```

바이트코드에서 `a.speak()`는 `invokevirtual Animal.speak()`로 컴파일된다. `invokevirtual`은 "선언 타입은 `Animal.speak`이지만, 실제로 실행할 구현은 스택 맨 위 객체의 런타임 타입 vtable에서 찾으라"는 명령이다.

6절에서 본 "상위 생성자에서 `open` 멤버를 호출하면 하위 클래스로 간다"는 현상의 실체가 바로 이 조회다. `this`의 런타임 타입이 이미 `Derived`이므로, `invokevirtual`은 `Derived`의 vtable 슬롯(하위 클래스의 오버라이드)으로 점프한다. 생성이 끝났는지와 관계없이, 객체의 vtable은 처음부터 최종 타입의 것이다.

반면 4.1절의 `super` 호출은 `invokespecial`이다. `invokespecial`은 vtable을 *거치지 않고*, 명령에 지정된 클래스의 구현을 직접 호출한다. 그래서 `super`는 항상 정적으로 지정된 상위 구현을 실행하고, 하위 클래스로 다시 디스패치되지 않는다.

```text
invokevirtual  : vtable 조회 → 런타임 타입의 구현 (동적)
invokespecial  : 명령에 박힌 클래스의 구현 직접 (정적) — super, 생성자, private
invokestatic   : 인스턴스 없는 정적 메서드 (@JvmStatic, 확장 함수 등)
```

> [!note] 명세 기준
> vtable은 JVM 백엔드의 구현 방식이다. Kotlin/Native나 JS/Wasm 백엔드는 다형성을 다른 자료구조(예: 타입 정보 테이블, 함수 포인터 맵)로 구현할 수 있다. 하지만 "오버라이드된 멤버는 런타임 타입에 따라 디스패치된다"는 *의미*는 모든 백엔드에서 같다. "vtable"은 설명의 편의를 위해 JVM 관점에서 쓰는 용어이고, 언어가 보장하는 것은 그 위의 다형적 동작이다.

### 7.3 확장 함수와 비교: 정적 디스패치

이 장은 멤버 함수의 *동적* 디스패치를 다루지만, 비교를 위해 확장 함수의 *정적* 디스패치도 짚어 둘 만하다(자세한 내용은 35장 확장 함수와 프로퍼티).

```kotlin
open class Animal
class Dog : Animal()

fun Animal.describe() = "동물"
fun Dog.describe() = "개"

fun main() {
    val a: Animal = Dog()  // 런타임 타입은 Dog, 정적 타입은 Animal
    println(a.describe())  // => 동물  (개가 아니라!)
}
```

멤버 함수였다면 `Dog`로 디스패치되어 "개"가 출력되었을 것이다. 하지만 `describe`는 확장 함수다. **확장 함수는 vtable에 슬롯이 없다.** 컴파일러는 수신 객체의 *정적 타입*(`Animal`)만 보고 컴파일 타임에 `Animal.describe`로 확정한다. 이 호출은 `invokestatic`으로 컴파일되며, 첫 번째 인자가 수신 객체인 평범한 정적 함수 호출이다. 그래서 런타임 타입이 `Dog`여도 "동물"이 출력된다.

이 비교를 통해 상속의 핵심이 오히려 분명해진다. **오버라이딩(멤버, 동적)과 확장(정적)은 호출 모양(`a.f()`)은 같지만 동작 방식은 정반대다.** 상속 계층에서 다형적인 동작을 원한다면 멤버 함수를 `open`으로 열어 오버라이드하고, 기존 타입에 부수적인 기능만 덧붙이려면 확장 함수를 쓴다. 확장 함수로 다형성을 흉내 내려다 이 정적 디스패치 때문에 예상과 다른 결과를 얻는 것은 초보자가 흔히 빠지는 함정이다.

## 8. `Any`: 모든 클래스의 최상위 타입

### 8.1 `Any`가 선언하는 세 멤버

상위 타입을 명시하지 않은 코틀린 클래스는 자동으로 `Any`를 상속한다. `Any`는 타입 계층의 최상단(널이 될 수 없는 타입 쪽)이다([[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]). `Any`가 선언하는 멤버는 **딱 세 개**다.

```kotlin
// kotlin.Any의 개념적 선언
open class Any {
    open operator fun equals(other: Any?): Boolean
    open fun hashCode(): Int
    open fun toString(): String
}
```

모든 코틀린 객체는 이 세 멤버를 가진다. 그리고 셋 다 `open`이므로 어떤 클래스든 오버라이드할 수 있다.

여기서 자바에 익숙한 개발자가 흔히 하는 오해를 바로잡아야 한다. JVM 백엔드에서 `Any`는 `java.lang.Object`로 매핑되지만, **코틀린의 `Any`는 `Object`의 모든 메서드를 노출하지 않는다.**

`wait()`, `notify()`, `getClass()` 같은 `Object`의 다른 메서드는 코틀린 `Any`의 멤버가 아니다. 스레드 대기용 저수준 연산은 코틀린이 의도적으로 숨겼는데, 동시성은 더 높은 수준의 도구로 다루라는 뜻이다([[43 - 동시성과 메모리 모델]]).

코틀린에서 객체의 클래스를 얻으려면 `Object.getClass()` 대신 `::class`(리플렉션, [[44 - 애노테이션과 리플렉션]])나 `javaClass`(JVM 확장)를 쓴다. 즉 `Any`는 JVM `Object`의 별칭이 아니라, `Object`를 코틀린 방식으로 다듬은 타입이다. Kotlin/Native나 JS 백엔드에는 `Object`가 아예 없고, `Any` 자체가 최상위 타입이다.

### 8.2 `equals`, `hashCode`, `toString` 오버라이딩: 상속되는 계약

이 세 멤버를 오버라이드하는 것은 단순히 함수를 바꾸는 일이 아니라 **계약을 지켜야 하는** 일이다(자세한 내용은 [[10 - 불리언과 동등성과 동일성]]).

```kotlin
class Point(val x: Int, val y: Int) {
    override fun equals(other: Any?): Boolean {
        if (this === other) return true
        if (other !is Point) return false
        return x == other.x && y == other.y
    }
    override fun hashCode(): Int = 31 * x + y
    override fun toString(): String = "Point($x, $y)"
}
```

`equals`를 오버라이드할 때 지켜야 할 계약은 다음과 같다.

- 반사성: 자기 자신과 같다.
- 대칭성: `a == b`이면 `b == a`이다.
- 추이성: `a == b`이고 `b == c`이면 `a == c`이다.
- 일관성: 같은 입력에는 같은 결과를 낸다.

그리고 **`equals`를 오버라이드하면 반드시 `hashCode`도 함께** 오버라이드해야 한다. "같은 두 객체는 해시코드도 같아야 한다"는 계약을 어기면 `HashMap`과 `HashSet`이 아무 오류 없이 잘못 동작한다.

이 두 함수를 자동으로 올바르게 만들어 주는 것이 데이터 클래스([[27 - 데이터 클래스]])다. 데이터 클래스는 주 생성자 프로퍼티를 기준으로 `equals`/`hashCode`/`toString`/`componentN`/`copy`를 생성하므로, 이 계약을 직접 지키는 수고를 덜어 준다(단, 주 생성자 프로퍼티만 참여한다는 함정이 있다).

상속 계층에서는 `equals`가 특히 까다롭다. 상위 타입과 하위 타입의 인스턴스를 비교할 때 대칭성을 지키기 어렵기 때문이다. 그래서 데이터 클래스는 다른 클래스를 상속할 수는 있지만(2.x) `open`이 될 수는 없고, 상속을 고려한 `equals` 설계는 매우 신중해야 한다. 자세한 논의는 10장과 27장에서 다룬다.

> [!caution] 성능 주의
> `toString`은 디버깅과 로깅에서 수없이 호출된다. 무거운 계산(전체 컬렉션 순회, 대량의 문자열 연결)을 `toString`에 넣으면 로그를 켜는 순간 성능이 급격히 떨어질 수 있다. `toString`은 비용이 적고 부작용이 없어야 한다는 것이 암묵적인 계약이다.

## 9. 추상 클래스와 인터페이스, 그리고 상속보다 조합

### 9.1 추상 클래스와 인터페이스 중 무엇을 쓸까

상속 계층을 설계할 때 처음 만나는 선택은 "추상 클래스를 쓸 것인가, 인터페이스를 쓸 것인가"이다. 둘 다 오버라이드할 멤버를 남겨 둘 수 있지만 성질이 다르다.

| 축 | 추상 클래스 | 인터페이스 |
|----|------------|-----------|
| 상태(백킹 필드) | 가질 수 있음 | 불가 |
| 생성자 | 있음 | 없음 |
| 다중 상속 | 불가 (하나만) | 가능 (여럿) |
| 기본 구현 | 가능 | 가능 |
| "is-a" 관계 | 강한 정체성 | 능력/역할 |

실용적인 선택 기준은 다음과 같다.

- **상태를 공유해야 한다면 추상 클래스를 쓴다.** 하위 클래스들이 공통으로 저장할 필드가 있다면(예: 모든 `Shape`가 가지는 위치 좌표), 인터페이스로는 그 상태를 담을 수 없다.
- **독립적인 능력 여러 개를 조합해야 한다면 인터페이스를 쓴다.** 한 클래스가 `Comparable`이면서 `Serializable`이면서 `Drawable`일 수 있다. 클래스 상속은 하나만 가능하므로 이런 조합을 표현하지 못한다.
- **판단하기 어렵다면 인터페이스를 먼저 고려한다.** 인터페이스는 결합도가 낮고, 나중에 여러 개를 조합할 여지를 남긴다. 추상 클래스는 "하나뿐인 클래스 상속 자리를 이미 써 버리는" 무거운 결정이다.

코틀린에서는 인터페이스도 기본 구현을 가질 수 있으므로("자바 8+의 default 메서드와 유사"), 예전 자바에서 "구현을 공유하려면 추상 클래스를 쓴다"고 하던 이유는 상당 부분 사라졌다. 남은 결정적인 차이는 **상태**와 **생성자**다. 인터페이스가 상태를 가질 수 없는 이유(백킹 필드가 없음)와 이를 우회하는 방법(백킹 프로퍼티, 구현 클래스에 상태 위임)은 25장(인터페이스)에서 다룬다.

### 9.2 취약한 기반 클래스와 위임: "상속보다 조합"

1절에서 본 취약한 기반 클래스 문제를 근본적으로 피하는 방법은 처음부터 상속하지 않는 것이다. 블로크의 또 다른 격언인 "상속보다 조합(favor composition over inheritance)"이 여기에 해당한다. 상속으로 `is-a` 관계를 표현하는 대신, 다른 객체를 필드로 *가지고*(`has-a`) 그 객체에 작업을 위임한다.

1.2절의 `CountingSet`을 조합 방식으로 다시 작성해 보자. 상속 대신 코틀린의 클래스 위임(`by`, 32장)을 사용한다.

```kotlin
class CountingSet<T>(
    private val inner: MutableSet<T> = mutableSetOf()
) : MutableSet<T> by inner {          // 위임: MutableSet의 모든 메서드를 inner로 전달
    var addCount = 0
        private set

    override fun add(element: T): Boolean {
        addCount++
        return inner.add(element)      // 명시적으로 inner를 호출 — self-use 문제 없음
    }
    override fun addAll(elements: Collection<T>): Boolean {
        addCount += elements.size
        return inner.addAll(elements)  // inner.addAll의 내부가 add를 부르든 말든
                                       // 우리 add와 무관 (inner는 남의 인스턴스)
    }
}
```

핵심은 `inner`가 *별개의 객체*이므로, `inner`의 `addAll` 내부 구현이 우리가 작성한 `add`를 다시 호출하지 않는다는 점이다. 1.2절에서 본 취약성, 즉 "하위 클래스가 올바르게 동작하는지가 상위 클래스의 self-use 패턴에 의존하는 문제"가 사라졌다.

또한 `by inner`를 쓰면 우리가 오버라이드하지 않은 `MutableSet`의 나머지 메서드(모두 수십 개)를 `inner`로 전달하는 코드를 컴파일러가 자동으로 생성하므로, 위임 코드를 장황하게 쓸 필요도 없다. 이 위임 방식이 어떻게 컴파일되는지, 어떤 함정이 있는지(위임 대상을 프로퍼티로 저장하지 않으면 다시 계산되는 문제 등)는 32장에서 다룬다.

이것이 이 장의 실천적인 결론이다. 상속은 강력하지만 결합도가 높고, 초기화 순서의 함정과 취약한 기반 클래스의 위험을 안고 있다. 그래서 코틀린은 상속을 *기본적으로 금지*했고, 확장 함수와 인터페이스, 위임이라는 덜 위험한 대안을 충분히 제공한다. 상속을 쓸 때는 `open`으로 의도를 명시하는 것과 함께, 6절의 방어책(생성자에서 `open` 멤버를 호출하지 않기)과 1절의 self-use 문서화도 지켜야 한다.

다음 장인 25장(인터페이스)에서는 계약을 상태 없이, 여러 타입에 걸쳐 공유하는 방법을 다룬다.
