[[24 - 상속과 오버라이딩과 초기화 순서]]에서는 클래스가 다른 클래스를 확장할 때 생기는 문제, 즉 초기화 순서, 생성자에서 `open` 멤버를 호출하는 함정, `override`를 명시해야 하는 이유를 다뤘다. 그 논의는 처음부터 끝까지 "단일 상속"을 전제로 했다. 코틀린 클래스는 상위 클래스를 *하나만* 가질 수 있기 때문이다.

그런데 실제 타입은 여러 능력을 동시에 갖는 경우가 많다. 오리는 헤엄칠 수 있고, 날 수 있고, 이름도 있다. 이렇게 여러 능력을 한 타입에 조합하는 수단이 인터페이스다. 이 장에서는 클래스 상속으로는 해결하지 못한 다중 상속과 능력 조합을 인터페이스가 어떻게 해결하는지 살펴본다.

이 장에서는 인터페이스의 메서드와 프로퍼티 선언, 기본 구현, 다이아몬드 문제 해소, JVM에서의 컴파일 형태, 추상 클래스와의 선택 기준, `fun interface`와 SAM 변환, 마커 인터페이스, 제네릭·변성과 인터페이스를 다룬다.

특히 "코틀린 인터페이스는 상태를 가질 수 있다"는 흔한 오해를 바로잡는다. 인터페이스에 `val x: String`을 선언할 수 있고 `val x get() = ...`처럼 기본 게터까지 줄 수 있으니 필드를 담는다고 착각하기 쉽지만, 인터페이스 프로퍼티는 **백킹 필드가 없는 접근자 추상**이다. 이 점이 인터페이스와 추상 클래스를 가르는 근본적인 차이이며, 다중 상속이 안전한 이유이기도 하다.

`class C(b: Base) : Base by b` 같은 구현 위임은 [[32 - 클래스 위임]]에서, `sealed interface`는 [[30 - sealed 클래스와 대수적 데이터 타입]]에서, 백킹 필드와 접근자의 일반 원리는 [[22 - 프로퍼티와 백킹 필드]]에서, 함수 타입과 람다 문법은 [[13 - 함수 타입과 람다와 함수 참조]]에서 설명한다.

## 1. 인터페이스란 무엇인가: 계약이자 능력

### 1.1 두 가지 역할: 명세(what)와 조합(mix-in)

인터페이스에는 서로 다른 두 가지 목적이 겹쳐 있다. 하나는 **계약(contract)** 으로, "이 타입을 쓰려면 이런 연산이 있어야 한다"는 명세다. 다른 하나는 **능력의 조합(mix-in)** 으로, "이 타입은 이런 능력을 함께 갖춘다"는 구성이다. 코틀린 인터페이스는 이 두 가지를 하나의 장치로 처리한다.

```kotlin
interface Drawable {
    fun draw(): String            // 계약: 그릴 줄 알아야 한다
}

interface Named {
    val name: String              // 계약: 이름을 가져야 한다
}

// 능력의 조립: 도형은 그릴 수 있고 + 이름을 가진다
class Circle(override val name: String, val radius: Double) : Drawable, Named {
    override fun draw(): String = "○ $name (r=$radius)"
}

val c: Drawable = Circle("작은원", 1.0)
println(c.draw())          // => ○ 작은원 (r=1.0)
```

`Circle`은 두 인터페이스를 동시에 구현한다. 이 점이 클래스 상속과 결정적으로 다르다. 클래스는 하나만 확장할 수 있지만, 인터페이스는 쉼표로 구분해 얼마든지 나열할 수 있다. 능력은 여러 개를 겹쳐 쌓을 수 있는 것이지, 하나의 계보를 따라 물려받는 것이 아니기 때문이다.

### 1.2 클래스는 하나만, 인터페이스는 여러 개를 상속할 수 있는 이유

이 비대칭은 임의로 정한 것이 아니다. **상태(state)** 를 담는지 여부의 차이에서 나온다. 클래스는 필드, 즉 실제 메모리 슬롯을 가진다. 여러 클래스를 동시에 상속하면 각 클래스의 필드가 합쳐지면서 "이름이 같은 필드가 두 개"인 상황이나 "어느 상위 클래스의 생성자가 먼저 실행되는가" 같은 난제(고전적인 다이아몬드 상속 문제)가 생긴다. C++는 가상 상속(virtual inheritance)이라는 복잡한 장치로 이 문제를 다루지만, 그 비용이 크기로 유명하다.

코틀린은 자바가 택한 방식을 따른다. **상태를 담는 클래스는 단일 상속으로 제한하고, 상태가 없는 계약인 인터페이스만 다중 상속을 허용한다.** 인터페이스에는 저장할 필드가 없으므로 필드 충돌이 원천적으로 일어날 수 없다. 남는 것은 "시그니처가 같은 *메서드*가 여러 개"인 경우인데, 이는 뒤에서 볼 `super<T>.f()`로 명시적으로 해결한다.

즉 이 설계의 핵심은 해결하기 어려운 필드 충돌을 없애고, 명시적으로 해소할 수 있는 메서드 충돌만 남긴 것이다.

```text
        클래스 (상태 있음)              인터페이스 (상태 없음)
        ─────────────────              ────────────────────
  상속    단 하나 (single)             여럿 (multiple)
  이유    필드 충돌·초기화 순서         필드 없음 → 충돌 불가
          → 다이아몬드 지옥            메서드 충돌만 → super<T>로 해소

   class Dog : Animal, Pet   // 컴파일 에러: 클래스는 하나만
   class Dog : Animal, Runnable, Barkable  // OK: Animal만 클래스, 나머지 인터페이스
```

### 1.3 인터페이스는 인터페이스만 확장한다

인터페이스는 다른 인터페이스를 확장할 수 있지만, 클래스를 확장할 수는 없다. 계약이 다른 계약을 좁히거나 합치는 것은 자연스럽지만, 계약이 구현(상태)을 물려받으면 앞 절의 원칙이 깨지기 때문이다.

```kotlin
interface Shape {
    val area: Double
}

// 인터페이스가 인터페이스를 확장 — OK
interface ColoredShape : Shape {
    val color: String
}

class RedSquare(val side: Double) : ColoredShape {
    override val area: Double get() = side * side   // Shape의 계약
    override val color: String get() = "red"        // ColoredShape의 계약
}
```

`ColoredShape`를 구현하는 클래스는 `Shape`와 `ColoredShape`의 계약을 *모두* 이행해야 한다. 이처럼 인터페이스 계층에서는 계약이 누적된다.

> [!warning] 흔한 오해
> "인터페이스는 자바 8 이전처럼 비어 있는 메서드 선언의 모음일 뿐"이라는 인식이 아직도 흔하다. 하지만 코틀린 인터페이스는 처음부터(자바 8의 default 메서드 도입과 관계없이) 메서드 기본 구현, 프로퍼티 선언, 게터 구현, 중첩 타입, 컴패니언 객체를 담을 수 있었다. 인터페이스는 "기능이 부족한 추상 클래스"가 아니라 "상태만 없는 완전한 타입"이다.

## 2. 인터페이스 프로퍼티: 상태가 없다는 것의 의미

### 2.1 백킹 필드가 없다는 것

이 절에서는 이 장의 가장 중요한 주제인 "인터페이스는 상태를 가질 수 있다"는 오해를 다룬다. 인터페이스 본문에 프로퍼티를 선언할 수 있기 때문에, 많은 사람이 "그렇다면 인터페이스도 값을 저장하는 것 아닌가?"라고 생각한다. **그렇지 않다.** 인터페이스 프로퍼티는 값을 저장할 슬롯, 즉 백킹 필드(backing field)를 가질 수 없다.

프로퍼티가 곧 필드라는 착각은 22장(프로퍼티와 백킹 필드)에서 이미 바로잡았다. 프로퍼티는 근본적으로 *접근자(get/set)의 추상*이며, 백킹 필드는 "실제로 저장이 필요할 때만" 컴파일러가 만들어 주는 부산물이다. 인터페이스에서는 이 부산물이 원천적으로 만들어지지 않는다.

```kotlin
interface Named {
    val name: String            // 추상 프로퍼티: 게터만 있는 계약. 필드 없음.
}
```

`val name: String`은 "이 타입은 `name`을 *읽을 수 있어야 한다*"는 계약일 뿐이다. 값을 *어디에* 저장할지는 인터페이스가 아니라 구현 클래스가 정한다.

초기화자를 붙이면 컴파일러가 막는다.

```kotlin
interface Named {
    val name: String = "이름없음"
    // 컴파일 에러: Property initializers are not allowed in interfaces
}
```

에러 메시지가 이유를 정확히 알려 준다. 초기화자 `= "이름없음"`은 값을 어딘가에 저장하라는 요청이다. 저장하려면 필드가 필요한데, 인터페이스에는 필드가 없다. `field` 식별자를 직접 쓰려고 해도 마찬가지다.

```kotlin
interface Counter {
    var count: Int
        get() = field          // 컴파일 에러: 'field' cannot be used here
        set(value) { field = value }
}
```

인터페이스 프로퍼티의 게터와 세터 본문에는 `field`가 존재하지 않는다. 접근자 안에서 참조할 저장 슬롯이 아예 없기 때문이다.

### 2.2 그렇다면 무엇을 담을 수 있는가: 계산 프로퍼티

인터페이스가 담을 수 있는 것은 **다른 추상 멤버로부터 값을 계산하는 게터**다. 이는 저장이 아니라 파생(derivation)이다.

```kotlin
interface Person {
    val firstName: String        // 추상 — 구현이 채운다
    val lastName: String         // 추상 — 구현이 채운다

    val fullName: String         // 기본 게터로 파생 — 저장 아님
        get() = "$firstName $lastName"
}

class Employee(
    override val firstName: String,
    override val lastName: String,
) : Person

val e = Employee("가", "나다")
println(e.fullName)              // => 가 나다
```

`fullName`은 인터페이스가 "구현"을 제공하는 것처럼 보이지만, 실제로는 호출할 때마다 `firstName`과 `lastName`을 읽어 문자열을 새로 만든다. `fullName`이라는 값은 어디에도 *보관되지* 않고, 접근할 때마다 다시 계산된다.

이것이 "상태 없음(stateless)"의 정확한 의미다. 인터페이스가 제공하는 것은 **행동(계산 규칙)** 이지 **저장된 데이터**가 아니다.

```text
[인터페이스가 담을 수 있는 것]          [담을 수 없는 것]
  추상 프로퍼티 (게터 계약)      ✓       val x = 초기값 (초기화자)   ✗
  추상 프로퍼티 (세터 계약)      ✓       get() = field / set{field=} ✗
  계산 게터  val y get() = f()  ✓       lateinit var                ✗ (필드 필요)
  추상 메서드                    ✓       by lazy / by Delegates     ✗ (저장 필요)
  기본 구현 메서드               ✓       init 블록                   ✗ (인스턴스 상태)
  중첩 클래스 / companion        ✓       주/부 생성자                ✗ (필드 초기화)
```

`lateinit`을 쓸 수 없는 것도 같은 이유다. `lateinit var`는 나중에 채울 *필드*를 미리 확보해 두는 장치인데([[11 - 변수와 초기화 - val과 const와 lateinit]]), 인터페이스에는 확보할 필드가 없다. `by lazy`나 `Delegates.observable` 같은 위임 프로퍼티([[23 - 위임 프로퍼티]])도 위임 객체를 *저장*해야 하므로 인터페이스에서는 쓸 수 없다.

### 2.3 상태를 담고 싶다면: 백킹 프로퍼티 패턴

그래도 인터페이스가 어떤 상태를 강제하고 싶다면 방법은 하나다. **상태를 구현 클래스로 옮기는 것이다.** 인터페이스는 추상 프로퍼티로 *계약만* 정하고, 실제 저장은 이를 구현하는 클래스의 필드가 맡는다.

```kotlin
interface Stack<T> {
    val size: Int                 // 계약: 크기를 알 수 있어야 한다
    fun push(item: T)
    fun pop(): T
    val isEmpty: Boolean           // 파생 — size로부터 계산
        get() = size == 0
}

class ArrayStack<T> : Stack<T> {
    private val items = mutableListOf<T>()   // ← 상태는 여기, 구현 클래스에!
    override val size: Int get() = items.size

    override fun push(item: T) { items.add(item) }
    override fun pop(): T = items.removeAt(items.lastIndex)
}
```

`Stack` 인터페이스는 "크기를 알 수 있다"는 계약과 "비었는지 판단하는 규칙"(파생)만 제공한다. 실제 원소를 담는 `items` 필드는 `ArrayStack`이라는 *클래스*에 있다. 인터페이스에 상태가 없다는 원칙을 실제 코드로 적용하면 이렇게 된다. 인터페이스는 능력의 명세이고, 그 능력을 뒷받침하는 상태는 언제나 클래스에 있다.

인터페이스가 "값을 하나 가진 것처럼" 보이게 하고 싶을 때도 마찬가지다.

```kotlin
interface HasId {
    val id: Long
}

// 구현마다 저장 방식이 다르다 — 인터페이스는 관여하지 않는다
class DbUser(override val id: Long, val email: String) : HasId          // 생성자 필드
class SeqUser(val seq: Int) : HasId {
    override val id: Long get() = seq.toLong() + 1000                    // 파생 (필드 없음)
}
```

같은 `HasId` 계약을 `DbUser`는 실제 필드로, `SeqUser`는 계산으로 만족한다. 인터페이스 입장에서는 둘 다 "`id`를 읽을 수 있는 타입"으로 같다. 저장할지 말지는 전적으로 구현이 결정한다.

> [!note] 명세 기준
> 코틀린 인터페이스 프로퍼티는 `val`과 `var`를 모두 선언할 수 있고, 게터(`var`라면 세터도)의 기본 구현을 줄 수도 있다. 다만 그 구현은 **다른 접근 가능한 멤버만** 참조할 수 있고, `field`는 참조할 수 없다.
>
> `var` 세터의 기본 구현이 유용한 경우는 드물다. 저장할 곳이 없으므로 보통 다른 추상 세터에 위임하거나 부수 효과를 내는 정도다. 그래도 문법적으로 금지되지는 않는다.

### 2.4 프로퍼티 오버라이드의 유연성

구현 클래스는 인터페이스의 추상 프로퍼티를 여러 방식으로 구현할 수 있고, `val`을 `var`로 넓힐 수도 있다.

```kotlin
interface ReadableName {
    val name: String             // 읽기 계약만
}

// 구현이 var로 넓힘 — 읽기 계약을 만족하면서 쓰기까지 추가
class MutableName(override var name: String) : ReadableName

val m = MutableName("처음")
println(m.name)                  // => 처음
m.name = "나중"
println(m.name)                  // => 나중
```

`val`은 "읽을 수 있다"는 최소한의 계약이므로, 이를 "읽고 쓸 수 있다"(`var`)로 강화해도 계약을 어기지 않는다. 리스코프 치환 원칙에도 맞는다. `ReadableName`으로 볼 때는 여전히 읽기만 노출되기 때문이다.

반대로 인터페이스가 `var name`을 요구하는데 구현이 `val`로 좁히는 것은 불가능하다. 쓰기 능력을 없애면 계약을 위반하기 때문이다. 프로퍼티 오버라이드의 일반 규칙은 24장(상속과 오버라이딩과 초기화 순서)에서 다룬다.

## 3. 기본 구현: 추상 멤버와 구체 멤버를 한 타입에

### 3.1 메서드에 본문 두기

코틀린 인터페이스의 메서드는 두 종류다. 본문이 없으면 구현을 강제하는 **추상 메서드**이고, 본문이 있으면 **기본 구현(default implementation)** 이다.

```kotlin
interface Greeter {
    val name: String                 // 추상 프로퍼티
    fun greet(): String              // 추상 메서드 — 구현 필수
    fun greetLoudly(): String =      // 기본 구현 — 오버라이드 선택
        greet().uppercase() + "!!!"
}

class Formal(override val name: String) : Greeter {
    override fun greet() = "안녕하십니까, ${name}입니다"
    // greetLoudly는 오버라이드하지 않아도 됨 — 기본 구현을 물려받음
}

val f = Formal("정중이")
println(f.greet())               // => 안녕하십니까, 정중이입니다
println(f.greetLoudly())         // => 안녕하십니까, 정중이입니다!!!
```

`greetLoudly`는 추상 멤버인 `greet`를 호출해 동작을 구성한다. 이것이 인터페이스 기본 구현의 전형적인 쓰임이다. **골격 알고리즘(template method)** 을 인터페이스에 두고, 비어 있는 부분(추상 멤버)만 구현 클래스가 채우게 한다. 상태 없이 행동만 조합하므로 여러 인터페이스에 걸쳐 능력을 겹겹이 쌓을 수 있다.

### 3.2 기본 구현도 상태에는 접근하지 못한다

기본 구현이 강력해 보여도 한계는 분명하다. **기본 구현 안에서도 인터페이스는 상태에 접근할 수 없다.** 참조할 수 있는 것은 추상 멤버든 기본 구현 멤버든 다른 멤버뿐이다.

```kotlin
interface Sequence2 {
    var current: Int              // 추상 — 저장은 구현 클래스가
    fun next(): Int {             // 기본 구현
        current += 1              // OK: 추상 프로퍼티 current의 세터/게터 호출
        return current
        // 여기서 로컬 캐시 필드를 두는 것은 불가능 — 저장할 곳이 없다
    }
}
```

`next()`의 `current += 1`은 추상 프로퍼티 `current`를 게터로 읽고 세터로 쓴다. 그 값이 실제로 어디에 저장되는지는 이 인터페이스가 알지 못하며, 실제 저장 위치는 구현 클래스의 필드다. 인터페이스는 상태를 *조작하는 규칙*은 담지만 상태 *자체*는 담지 않는다는 원칙이 기본 구현에서도 그대로 유지된다.

### 3.3 인터페이스의 private 헬퍼

기본 구현이 복잡해지면 인터페이스 안에 private 헬퍼 함수를 두고 싶어진다. 코틀린은 이를 허용한다. 단, private 멤버는 반드시 본문(구현)을 가져야 한다. 추상 private 멤버는 구현할 방법이 없으므로 모순이기 때문이다.

```kotlin
interface Validator {
    val rawInput: String

    fun isValid(): Boolean = normalized().isNotEmpty()    // public 기본 구현

    private fun normalized(): String =                     // private 헬퍼
        rawInput.trim().lowercase()
}
```

`normalized()`는 인터페이스 밖에서 보이지 않고, `isValid()` 같은 다른 기본 구현을 돕는 데만 쓰인다.

한편 인터페이스 멤버의 가시성에는 클래스와 다른 제약이 있다. **인터페이스 멤버는 `public`(기본값)이거나 `private`일 수만 있고, `protected`나 `internal`은 허용되지 않는다.** 가시성 한정자의 일반 원리는 [[26 - 가시성 한정자]]에서 다룬다. 여기서는 인터페이스가 "구현을 강제하는 공개 계약"이라는 성격 때문에 `protected`(하위 타입만 접근)나 `internal`(모듈 내부로 한정)이 의미를 갖기 어렵다는 점만 기억하면 된다.

```kotlin
interface Api {
    protected fun secret()       // 컴파일 에러: Modifier 'protected' is not applicable to 'member function of interface'
    internal fun scoped()        // 컴파일 에러: Modifier 'internal' is not applicable ...
}
```

### 3.4 인터페이스의 상수는 companion에 둔다

인터페이스 본문에는 `const val`이나 초기화된 프로퍼티를 직접 둘 수 없다. 2.1절에서 본 것처럼 저장 슬롯이 없기 때문이다. 상수를 두려면 인터페이스의 **컴패니언 객체**에 담는다.

```kotlin
interface HttpStatus {
    val code: Int

    companion object {
        const val OK = 200                 // 컴패니언은 진짜 객체 → 저장 가능
        const val NOT_FOUND = 404
    }
}

println(HttpStatus.OK)           // => 200
```

컴패니언 객체는 인터페이스에 딸린 *실제 싱글턴 인스턴스*이므로 상태를 저장할 수 있다([[28 - object와 companion - 싱글턴과 동반 객체]]). 인터페이스 본문에는 상태가 없고 컴패니언에는 상태가 있다는 경계를 혼동하지 않아야 한다.

## 4. 다중 상속과 다이아몬드: `super<T>`로 충돌 해결하기

### 4.1 충돌이 생기는 경우

두 인터페이스가 시그니처가 같은 기본 구현을 각각 제공하고 한 클래스가 두 인터페이스를 모두 구현하면, 어느 구현을 써야 하는지 모호해진다. 코틀린은 이 모호함을 **컴파일 에러로 막고, 개발자에게 명시적인 오버라이드를 요구**한다.

```kotlin
interface A {
    fun foo() { print("A") }     // 기본 구현
    fun bar()                    // 추상
}

interface B {
    fun foo() { print("B") }     // 기본 구현 — A와 충돌!
    fun bar() { print("bar") }   // 기본 구현
}

class D : A, B {
    // foo()를 오버라이드하지 않으면:
    // 컴파일 에러: Class 'D' must override public open fun foo(): Unit
    //             because it inherits many implementations of it
    override fun foo() {
        super<A>.foo()           // A의 기본 구현 명시 호출
        super<B>.foo()           // B의 기본 구현 명시 호출
    }
    override fun bar() {
        super<B>.bar()           // A.bar는 추상, B.bar는 구체 — 그래도 명시 오버라이드 요구
    }
}

D().foo()                        // => AB
```

`super<A>.foo()`와 `super<B>.foo()`가 다이아몬드 문제를 해결하는 핵심 문법이다. 꺾쇠 안에 어느 상위 타입의 구현을 호출할지 명시하면 모호함이 사라진다. 필요하면 둘 다 호출할 수도 있고, 하나만 골라 호출하거나 완전히 새로 작성할 수도 있다.

### 4.2 추상 하나와 기본 구현 하나여도 오버라이드가 필요한 이유

`bar()`를 보자. `A.bar()`는 추상이고 `B.bar()`에는 기본 구현이 있다. "구현이 하나뿐이니 B의 것을 쓰면 되지 않나?"라고 생각할 수 있지만, 코틀린은 이 경우에도 **명시적인 오버라이드를 요구**한다.

`D`가 두 상위 타입으로부터 `bar`에 대한 서로 다른 선언, 즉 추상 선언 하나와 구체 선언 하나를 상속받았기 때문이다. 컴파일러는 개발자가 어느 쪽을 의도적으로 선택했는지 코드로 확인하려 한다. 암묵적으로 B를 선택했다가 나중에 A의 계약이 바뀌면 아무 경고 없이 잘못 동작할 수 있는데, 명시적인 오버라이드는 그 선택을 코드에 분명히 남긴다.

```text
[다이아몬드]

        A            B
     foo(){A}     foo(){B}      ← 같은 이름의 기본 구현 두 개
     bar()        bar(){bar}    ← 추상 하나 + 기본 하나
        \          /
         \        /
            class D            ← foo, bar 모두 override 강제
                               ← super<A>/<B>로 어느 것을 부를지 명시
```

### 4.3 충돌이 없으면 그대로 물려받는다

당연하게도 충돌이 없으면 오버라이드할 필요가 없다. 한 인터페이스만 기본 구현을 제공하고 다른 인터페이스에는 그 멤버가 없다면, 그 기본 구현이 그대로 상속된다.

```kotlin
interface Walk { fun move() = "걷는다" }
interface Name { val label: String }

class Cat(override val label: String) : Walk, Name
// move()는 Walk의 기본 구현을 그대로 물려받음 — 충돌 없음

println(Cat("나비").move())      // => 걷는다
```

### 4.4 상위 클래스와 인터페이스가 겹칠 때

클래스 하나를 확장하면서 인터페이스도 구현하면, 클래스 쪽 구현과 인터페이스의 기본 구현이 같은 시그니처로 겹칠 수 있다. 자바에서는 이런 충돌이 생기면 "클래스가 인터페이스보다 우선한다"는 규칙에 따라 상위 클래스의 구현이 별다른 표시 없이 채택된다.

**코틀린은 더 엄격해서, 구체 구현 두 개(클래스의 구현과 인터페이스의 기본 구현)를 함께 상속하면 명시적인 오버라이드를 요구**한다. 다만 인터페이스 쪽 멤버가 기본 구현이 없는 *추상* 멤버라면, 상속받은 클래스의 구체 구현이 그 계약을 그대로 만족하므로 따로 오버라이드할 필요가 없다.

```kotlin
open class Vehicle {
    open fun describe() = "탈것"
}
interface Loud {
    fun describe() = "시끄러운 것"   // 인터페이스 기본
}

class Truck : Vehicle(), Loud {
    // Vehicle.describe(구체)와 Loud.describe(기본)가 충돌 → 명시 오버라이드 요구
    override fun describe() = super<Vehicle>.describe() + " / " + super<Loud>.describe()
}

println(Truck().describe())      // => 탈것 / 시끄러운 것
```

`super<Vehicle>`처럼 상위 클래스도 꺾쇠 문법으로 지정할 수 있다. 즉 `super<T>`는 인터페이스 전용 문법이 아니라 "여러 상위 타입 중 하나를 지정"하는 일반적인 장치다.

## 5. JVM 백엔드에서의 컴파일 형태

### 5.1 코틀린 인터페이스는 자바 인터페이스로 컴파일된다

JVM 백엔드에서 코틀린 인터페이스는 자바 인터페이스로 컴파일된다. 추상 메서드는 자바 인터페이스의 추상 메서드가 되고, 프로퍼티는 게터와 세터 메서드(`getName()`/`setName()`)의 추상 선언이 된다. 여기까지는 직관적이다. 흥미로운 부분은 **기본 구현이 어떤 형태로 컴파일되는가**다.

### 5.2 기본 구현: DefaultImpls와 JVM default 메서드

코틀린이 인터페이스의 기본 구현을 컴파일하는 방식은 **컴파일러의 jvm-default 모드에 따라** 달라진다. 역사적으로 두 가지 전략이 있었다.

- **DefaultImpls 전략(예전 기본값)**: 인터페이스에는 메서드를 추상으로만 두고, 기본 구현의 본문은 `인터페이스이름$DefaultImpls`라는 정적 중첩 클래스의 static 메서드로 분리한다. 인터페이스를 구현하는 클래스는 그 static 메서드를 호출하는 브리지 메서드를 갖는다. 이 방식은 자바 6/7 바이트코드와도 호환되었고, 인터페이스가 변경될 때 바이너리 호환성을 지키기에도 유리했다.
- **JVM default 메서드 전략**: 자바 8의 `default` 메서드를 그대로 사용해서, 기본 구현 본문을 인터페이스 안에 default 메서드로 직접 넣는다. 자바 쪽에서 코틀린 인터페이스를 상속할 때 더 자연스럽고, `DefaultImpls`라는 우회용 클래스가 없어진다.

```text
[DefaultImpls 전략 (개념)]
  interface Greeter { abstract greetLoudly()V ... }
  class Greeter$DefaultImpls {
      static greetLoudly(Greeter $this) { ... $this.greet() ... }
  }
  class Formal implements Greeter {
      greetLoudly() { return Greeter$DefaultImpls.greetLoudly(this); }   // 브리지
  }

[JVM default 전략 (개념)]
  interface Greeter { default greetLoudly()V { ... this.greet() ... } }
  class Formal implements Greeter { /* 인터페이스 default 그대로 상속 */ }
```

어느 전략을 쓸지는 컴파일러 플래그(`-jvm-default` / 과거의 `-Xjvm-default`)와 빌드 설정에 따라 정해진다. 코틀린 버전에 따라 기본값과 모드 이름이 바뀌어 왔으므로, 코드가 특정 바이트코드 형태를 가정해서는 안 된다.

확실한 것은 하나다. **어느 전략이든 인터페이스는 상태(필드)를 담지 않는다.** default 메서드든 DefaultImpls든 참조하는 것은 다른 멤버(추상 게터와 세터 포함)뿐이다. 컴파일 형태가 바뀌어도 인터페이스에 상태가 없다는 원칙은 변하지 않는다. 컴파일 파이프라인 전반은 [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]에서 다룬다.

> [!caution] 성능 주의
> DefaultImpls 전략에서는 기본 구현을 호출할 때 한 단계(브리지 → static 메서드)를 더 거치지만, JIT가 대개 인라인하므로 실제 비용은 무시할 만하다. 정말 주의할 점은 성능이 아니라 **바이너리 호환성**이다.
>
> 프로젝트 도중에 jvm-default 모드를 바꾸면, 이미 배포된 서브클래스와 새로 컴파일한 결과 사이에서 브리지 메서드의 유무가 어긋나 `AbstractMethodError`가 발생할 수 있다. 라이브러리를 배포한다면 이 모드를 신중하게 정해 고정해야 한다.

### 5.3 디컴파일로 확인하기

이 내용은 추측할 필요 없이 직접 확인할 수 있다. IntelliJ의 "Tools → Kotlin → Show Kotlin Bytecode → Decompile"을 쓰거나 CLI로 `.class` 파일을 역컴파일하면, `DefaultImpls` 클래스가 있는지와 게터 메서드 이름(`getName()`)을 직접 볼 수 있다. "인터페이스가 상태를 담는가?"라는 의문이 들 때는 컴파일된 인터페이스 클래스에 인스턴스 필드가 하나도 없다는 사실을 직접 확인하는 것이 가장 확실하다.

## 6. 인터페이스와 추상 클래스: 언제 무엇을 쓸까

### 6.1 결정적인 차이 세 가지

인터페이스와 추상 클래스는 "미완성 타입"이라는 점에서 비슷하지만, 세 가지 지점(표의 위 세 줄)에서 크게 갈린다. 나머지 세 줄은 이 차이에서 따라 나오는 결과다.

| 축 | 인터페이스 | 추상 클래스 |
|----|-----------|------------|
| 상태(필드) | 불가: 백킹 필드 없음 | 가능: 필드·`init`·생성자 보유 |
| 상속 개수 | 여럿 구현 가능 | 하나만 확장 가능 |
| 생성자 | 없음 | 있음 (파라미터·초기화 가능) |
| 가시성 한정자 | public/private만 | 클래스와 동일(protected/internal 포함) |
| 기본 구현 | 가능 (상태 없이) | 가능 (상태와 함께) |
| 존재 이유 | 능력/계약의 조합 | 부분 구현 + 공유 상태의 골격 |

### 6.2 판단 기준: 상태와 정체성

실무에서 선택하는 기준은 단순하다. **공유할 상태(필드)나 생성자 초기화 로직이 필요하면 추상 클래스를, 순수한 능력의 계약이면 인터페이스를 쓴다.** 그리고 여러 축의 능력을 함께 갖춰야 한다면 인터페이스를 쓸 수밖에 없다. 클래스는 하나만 상속할 수 있기 때문이다.

```kotlin
// 상태를 공유하고 초기화 로직이 있다 → 추상 클래스
abstract class Account(initial: Long) {
    var balance: Long = initial          // 공유 상태 (필드)
        protected set
    init { require(initial >= 0) }        // 생성자 검증 — 인터페이스엔 불가
    abstract fun interestRate(): Double   // 구멍
    fun applyInterest() { balance += (balance * interestRate()).toLong() }
}

// 순수 능력의 계약 → 인터페이스
interface Auditable {
    fun auditLog(): String                // 상태 없이 계약만
}

// 조합: 하나의 클래스 상속 + 여러 인터페이스
class SavingsAccount(initial: Long) : Account(initial), Auditable {
    override fun interestRate() = 0.02
    override fun auditLog() = "잔액 $balance"
}
```

`Account`는 `balance`라는 상태와 `init` 검증을 가지므로 추상 클래스여야 한다. `Auditable`은 상태가 없는 능력이므로 인터페이스가 알맞다. `SavingsAccount`는 `Account`를 유일한 상위 클래스로 확장하면서 `Auditable`도 함께 구현한다.

### 6.3 "인터페이스를 우선하라"는 관용

"가능하면 인터페이스를 우선하라"는 설계 격언이 있다. 인터페이스는 여러 개를 구현할 수 있으므로 앞으로의 조합 가능성을 열어 두고, 상태를 강요하지 않으므로 결합도가 낮다. 추상 클래스는 "이 계층이 반드시 공유해야 하는 상태나 불변식이 있을 때" 쓰는 무거운 도구다.

다만 코틀린에서는 이 격언의 비중이 자바보다 작다. 코틀린 인터페이스는 이미 기본 구현을 담을 수 있으므로, 자바에서 "추상 클래스로 공통 코드를 공유"하던 경우의 상당수를 인터페이스만으로 해결할 수 있기 때문이다.

> [!info] 역사 메모
> 자바 8 이전에는 인터페이스에 구현을 담을 수 없었으므로, 공통 코드를 공유하려면 추상 클래스를 쓸 수밖에 없었다. 그래서 `AbstractList`, `AbstractMap` 같은 골격 구현체가 표준 라이브러리에 많았다. 코틀린은 처음부터 인터페이스 기본 구현을 지원해서 이런 양자택일을 크게 완화했다.
>
> 그래도 코틀린에서도 상태가 필요하면 여전히 추상 클래스(또는 구현 클래스)를 써야 한다. 기본 구현이 있다고 해서 인터페이스에 상태가 없다는 제약이 사라지지는 않기 때문이다.

## 7. fun interface와 SAM 변환: 람다가 인터페이스가 될 때

### 7.1 아무 인터페이스에나 람다를 넘길 수 없는 이유

메서드가 하나뿐인 인터페이스, 즉 단일 추상 메서드(Single Abstract Method, SAM) 인터페이스는 개념적으로 함수 하나와 같다. 그렇다면 그 자리에 람다를 바로 넣을 수 있어야 자연스러울 것이다. 그러나 코틀린에서는 **일반 인터페이스 자리에 람다를 직접 넣을 수 없다.**

```kotlin
interface Predicate2<T> {
    fun test(t: T): Boolean
}

fun <T> filterOne(item: T, p: Predicate2<T>): Boolean = p.test(item)

// filterOne(5, { it > 0 })
// 컴파일 에러: Type mismatch — 람다는 Predicate2가 아니다
```

코틀린에는 이미 일급 함수 타입 `(T) -> Boolean`이 있다(13장 함수 타입과 람다와 함수 참조). 만약 모든 SAM 인터페이스로 람다가 자동 변환된다면 오버로드 해석이 모호해지고, "이 람다가 함수 타입인지, 어떤 인터페이스인지" 예측하기 어려워진다. 그래서 코틀린은 **명시적으로 표시한 인터페이스에만** SAM 변환을 허용한다.

### 7.2 fun interface: 함수형 인터페이스 선언

인터페이스 앞에 `fun`을 붙이면 **함수형 인터페이스(functional interface)** 가 되고, 람다를 그 타입으로 변환할 수 있다.

```kotlin
fun interface Predicate<T> {
    fun test(t: T): Boolean       // 정확히 하나의 추상 메서드
}

fun <T> filterOne(item: T, p: Predicate<T>): Boolean = p.test(item)

// 이제 람다가 곧바로 Predicate로 변환된다 (SAM 변환)
println(filterOne(5) { it > 0 })         // => true
println(filterOne(-3) { it > 0 })        // => false

val positive = Predicate<Int> { it > 0 } // 변수에 담을 때도 SAM 변환
println(positive.test(10))               // => true
```

`fun interface`에는 추상 메서드가 **정확히 하나** 있어야 한다. 추상 메서드가 없거나 둘 이상이면 컴파일 에러가 난다. 단, 기본 구현 메서드나 계산 프로퍼티처럼 추상이 아닌 멤버는 얼마든지 추가할 수 있다. 추상 멤버가 하나이기만 하면 되기 때문이다.

반면 **추상 프로퍼티는 허용되지 않는다.** 추상 프로퍼티는 그 자체로 추상 게터라는 또 하나의 추상 멤버가 되기 때문이다.

```kotlin
fun interface Transformer<T, R> {
    fun transform(input: T): R              // 유일한 추상 메서드
    fun describe(): String = "변환기"        // 기본 구현 — 허용
}
// fun interface Bad { fun a(); fun b() }   // 컴파일 에러: 추상 메서드가 둘
// fun interface Bad2 { val x: Int }        // 컴파일 에러: 추상 프로퍼티(추상 게터)
```

### 7.3 fun interface와 함수 타입 typealias 비교

"함수 하나"를 나타내는 방법은 `fun interface`와 함수 타입(또는 함수 타입의 `typealias`, [[36 - 타입 별칭과 인라인 value class]]) 두 가지다. 언제 무엇을 써야 할까?

```kotlin
// 방법 1: 함수 타입 (또는 typealias)
typealias IntPredicate = (Int) -> Boolean

// 방법 2: fun interface
fun interface IntPredicateFI {
    fun accept(n: Int): Boolean
}
```

| 축 | 함수 타입 `(Int)->Boolean` | `fun interface` |
|----|---------------------------|-----------------|
| 이름 있는 도메인 개념 | 약함 (구조적 타입) | 강함 (명목 타입) |
| 추가 멤버(기본 구현) | 불가 | 가능 |
| 여러 함수 타입과 오버로드 구분 | 어려움 | 쉬움(별개 명목 타입) |
| 다른 인터페이스 상속/구현 | 불가 | 가능 |
| 간결함 | 최고 | 선언 필요 |

일반적으로 **단순히 "함수 하나를 넘긴다"면 함수 타입**이 간결하고 충분하다. 반면 **그 함수에 이름 있는 정체성을 부여하거나, 기본 구현이나 부가 멤버를 함께 담거나, "함수 하나짜리" 개념 여러 개를 오버로드로 구별**하고 싶다면 `fun interface`가 낫다.

예를 들어 `(Int) -> Boolean` 하나로는 "짝수 판별"과 "양수 판별"을 타입으로 구분할 수 없지만, `EvenCheck`와 `PositiveCheck`라는 두 `fun interface`는 명목 타입으로 구별된다.

### 7.4 Java 인터페이스의 SAM 변환

코틀린이 SAM 변환을 `fun interface`로 제한하는 규칙에는 예외가 있다. **자바에서 정의한 단일 추상 메서드 인터페이스**는 `fun` 표시가 없어도 SAM 변환이 된다. 자바에는 `fun interface` 문법이 없고, 자바 라이브러리의 `Runnable`, `Comparator`, `Callable` 같은 인터페이스에 람다를 넘기는 상호운용이 꼭 필요하기 때문이다.

```kotlin
// java.lang.Runnable — 자바 SAM 인터페이스
val r = Runnable { println("실행") }       // SAM 변환 OK (fun 없이도)
r.run()                                     // => 실행

// java.util.Comparator — 자바 SAM 인터페이스
val byLength = Comparator<String> { a, b -> a.length - b.length }
println(listOf("bb", "a", "ccc").sortedWith(byLength))   // => [a, bb, ccc]
```

정리하면 SAM 변환이 되는 경우는 두 가지다. **(1) 코틀린 `fun interface`, (2) 자바에서 정의한 SAM 인터페이스.** 코틀린에서 `fun` 없이 선언한 일반 인터페이스는 SAM 변환 대상이 아니다. Java 상호운용 전반은 [[45 - Java 상호운용]]에서 다룬다.

### 7.5 SAM 변환의 컴파일

`Predicate<Int> { it > 0 }`를 컴파일하면, JVM 백엔드에서는 `Predicate`를 구현하는 익명 클래스 인스턴스(또는 `invokedynamic` 기반 람다 팩토리)가 생성된다. 개념적으로는 다음 코드와 같다.

```kotlin
// SAM 변환 전:  Predicate<Int> { it > 0 }
// 개념적으로:
object : Predicate<Int> {
    override fun test(t: Int): Boolean = t > 0
}
```

즉 SAM 변환은 "람다를 익명 객체로 감싸는" 문법 설탕이다. 익명 객체 자체는 [[31 - 중첩 클래스와 이너 클래스와 익명 객체]]에서 다룬다. 성능 면에서 보면, 인라인 고차 함수에 넘기는 람다는 객체 할당이 제거된다([[15 - 인라인 함수와 reified]]). 하지만 `fun interface` 값을 변수에 담거나 인라인이 아닌 함수에 넘기면 인스턴스가 실제로 만들어진다.

## 8. 마커 인터페이스와 인터페이스의 그 밖의 쓰임

### 8.1 멤버 없는 인터페이스: 태그로서의 타입

멤버가 하나도 없는 인터페이스를 **마커 인터페이스(marker interface)** 라 한다. 아무 계약도 강제하지 않지만, "이 타입에 속한다"는 사실 자체가 정보가 된다.

```kotlin
interface Cacheable        // 멤버 없음 — 순수 태그

class Report : Cacheable
class TempFile             // Cacheable 아님

fun store(x: Any) {
    if (x is Cacheable) {
        println("캐시에 저장")       // 타입으로 능력을 판별
    } else {
        println("캐시 생략")
    }
}

store(Report())            // => 캐시에 저장
store(TempFile())          // => 캐시 생략
```

`is Cacheable` 검사로 런타임에 "이 객체에 캐시 대상 태그가 붙어 있는지"를 확인한다. JVM의 `java.io.Serializable`이 대표적인 마커 인터페이스다. 메서드는 없지만 "직렬화할 수 있다"는 것을 타입 수준에서 표시한다.

### 8.2 마커 인터페이스와 애노테이션 비교

같은 "태그" 목적으로 애노테이션([[44 - 애노테이션과 리플렉션]])을 쓸 수도 있다. 둘의 차이는 결정적이다.

| 축 | 마커 인터페이스 | 마커 애노테이션 |
|----|----------------|-----------------|
| 타입 시스템 참여 | 예: `is`/타입 파라미터 상한에 사용 | 아니오: 리플렉션으로만 조회 |
| 컴파일 타임 검사 | 가능 (`fun f(x: Cacheable)`) | 불가 (런타임 조회) |
| 상속 | 하위 타입에 전파 | 기본적으로 전파 안 됨 |
| 파라미터(부가 정보) | 불가 | 가능 (`@Cache(ttl=60)`) |

**컴파일 타임에 타입으로 강제**하고 싶다면 마커 인터페이스가 낫다. `fun cache(x: Cacheable)`처럼 "캐시할 수 있는 것만 받는다"는 조건을 시그니처로 표현할 수 있다. 반면 **부가 데이터를 함께 담아야 하거나 순수한 메타데이터**라면 애노테이션이 맞다. 요약하면 마커 인터페이스는 타입 시스템 안에 있는 태그이고, 마커 애노테이션은 타입 시스템 밖에 있는 메타데이터다.

### 8.3 인터페이스와 익명 객체: 인스턴스 만들기

인터페이스는 구현이 완성되지 않았으므로 직접 인스턴스화할 수 없다. 하지만 **object 표현식**으로 그 자리에서 구현을 채워 인스턴스를 만들 수 있다.

```kotlin
interface ClickListener {
    fun onClick(x: Int, y: Int)
}

fun register(listener: ClickListener) { listener.onClick(10, 20) }

register(object : ClickListener {          // 익명 객체로 인터페이스 구현
    override fun onClick(x: Int, y: Int) {
        println("클릭: ($x, $y)")
    }
})
// => 클릭: (10, 20)
```

`ClickListener`가 `fun interface`였다면 이 자리에 람다를 쓸 수 있었을 것이다(7절). 추상 메서드가 여러 개이거나 `fun interface`가 아니라면 익명 객체를 쓰면 된다.

### 8.4 sealed interface 미리 보기

인터페이스 계층은 기본적으로 열려 있어서 누구나 구현할 수 있다. 이 계층을 봉인해 "이 인터페이스의 구현체는 이것이 전부"라고 컴파일러에 알려 주면, `when`이 `else` 없이도 모든 경우를 다루게 된다. 이것이 `sealed interface`이며, 대수적 데이터 타입(합타입)을 표현하는 강력한 도구다.

```kotlin
sealed interface Shape2
data class Circle2(val r: Double) : Shape2
data class Rect2(val w: Double, val h: Double) : Shape2

fun area(s: Shape2): Double = when (s) {   // else 불필요 — 완전성 보장
    is Circle2 -> Math.PI * s.r * s.r
    is Rect2 -> s.w * s.h
}
```

봉인 범위, ADT, enum과의 비교 같은 자세한 논의는 30장(sealed 클래스와 대수적 데이터 타입)에서 다룬다. 여기서는 "인터페이스도 봉인할 수 있고, 봉인하면 완전성 검사의 기반이 된다"는 점만 기억하면 된다.

## 9. 제네릭·변성과 인터페이스

### 9.1 변성은 주로 인터페이스에 선언된다

변성(variance), 즉 `out`(공변)과 `in`(반공변)은 대개 인터페이스에 선언된다. 표준 라이브러리의 핵심 인터페이스들을 보면 이를 알 수 있다.

```kotlin
interface Producer<out T> {       // out: T는 생산(반환) 위치에만
    fun produce(): T
}
interface Consumer<in T> {        // in: T는 소비(인자) 위치에만
    fun consume(item: T)
}
```

`Producer<out T>`가 공변이라는 것은 `Producer<Cat>`을 `Producer<Animal>`로 안전하게 다룰 수 있다는 뜻이다(고양이를 생산하는 것은 동물을 생산하는 것으로 볼 수 있다). 반대로 `Consumer<in T>`는 반공변이므로 `Consumer<Animal>`을 `Consumer<Cat>`으로 다룰 수 있다(동물을 소비할 수 있으면 고양이도 소비할 수 있다).

이 규칙이 안전하다는 증명과 사용 지점 변성 등은 [[33 - 제네릭 1 - 타입 파라미터와 변성]]과 [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]에서 다룬다.

여기서는 인터페이스가 변성을 선언하기에 자연스러운 자리인 이유만 짚는다. 인터페이스는 상태가 없어서 "생산만 하는 타입"이나 "소비만 하는 타입"을 순수하게 표현하기 좋다. 표준 라이브러리의 `Iterator<out T>`, `Comparable<in T>`, `Comparator<in T>`는 모두 인터페이스이면서 변성을 가진다.

### 9.2 인터페이스가 변성 표현에 적합한 이유

$Producer\langle Cat \rangle <: Producer\langle Animal \rangle$ 가 성립하려면($<:$는 하위 타입 관계), `T`가 출력 위치에만 나타나야 안전하다. 인터페이스는 필드(입력이자 출력인 상태)를 갖지 않으므로, `out T`를 선언하면 컴파일러가 "T가 정말 출력에만 쓰였는가"를 검사하기 쉽다.

클래스에도 변성을 선언할 수 있지만, 상태를 담는 클래스에서는 상태 필드가 입력 위치와 출력 위치를 모두 만족해야 하므로 변성 제약을 지키기 까다로운 경우가 많다. 변성과 인터페이스가 잘 어울리는 이유가 여기에 있다.

### 9.3 제네릭 인터페이스의 다중 구현 제약

한 클래스가 같은 제네릭 인터페이스를 서로 다른 타입 인자로 두 번 구현할 수는 없다.

```kotlin
interface Handler<T> { fun handle(x: T) }

// class Multi : Handler<Int>, Handler<String>
// 컴파일 에러: 'Handler' cannot be a superinterface twice with different type arguments
```

JVM 백엔드에서는 타입 소거(34장 타입 소거와 reified와 바운드) 때문에 `Handler<Int>`와 `Handler<String>`이 런타임에 같은 `Handler`가 되어 `handle` 메서드가 충돌한다. 코틀린은 이 모호함을 컴파일 타임에 막는다.

## 10. 인터페이스의 함정: 실전에서 자주 겪는 문제

### 10.1 인터페이스 프로퍼티는 초기화되지 않는다

가장 흔한 함정이다. 인터페이스에서 파생 게터로 정의한 프로퍼티에 "다른 추상 프로퍼티가 초기화되기 전에" 접근하면 예상하지 못한 값이 나온다. 특히 구현 클래스의 `init` 블록이나 생성자에서 인터페이스의 파생 프로퍼티를 호출하면 위험하다. 이는 24장(상속과 오버라이딩과 초기화 순서)에서 다룬 초기화 순서 함정과 원인이 같다.

```kotlin
interface HasFullName {
    val first: String
    val last: String
    val full: String get() = "$first $last"    // 파생
}

class P(override val first: String) : HasFullName {
    override val last: String = computeLast()    // 나중에 초기화
    private fun computeLast(): String { println("full 지금=$full"); return "김" }
}
// P("영희") 생성 시:
// => full 지금=영희 null    ← last가 아직 초기화 전! (파생 게터가 미초기화 last를 읽음)
```

`computeLast()`가 `full`을 읽는 시점에는 `last`가 아직 초기화되지 않았으므로 `null`(플랫폼의 기본값)이 섞여 나온다. 인터페이스의 파생 프로퍼티는 "접근하는 시점에 계산"되므로, 그 시점에 상태가 초기화되었는지에 전적으로 의존한다. 파생 게터는 초기화가 끝난 뒤에만 호출하는 것이 안전하다.

### 10.2 인터페이스 프로퍼티에서는 스마트 캐스트가 막힌다

인터페이스의 `val` 프로퍼티는 커스텀 게터를 가질 수 있으므로, 컴파일러는 "두 번 읽어도 같은 값"임을 보장하지 못한다. 따라서 인터페이스 프로퍼티에 대한 스마트 캐스트는 대체로 막힌다.

```kotlin
interface Box {
    val value: String?           // 커스텀 게터일 수 있음 → 안정성 미보장
}

fun show(b: Box) {
    if (b.value != null) {
        // println(b.value.length)
        // 컴파일 에러(또는 경고): Smart cast to 'String' is impossible,
        //   because 'b.value' is a property that has open or custom getter
    }
}
```

`b.value`는 호출할 때마다 다른 값을 돌려주는 게터일 수 있다. 첫 검사에서는 non-null이었어도 다음 접근에서는 null일 수 있으므로, 컴파일러는 스마트 캐스트를 거부한다. 지역 변수에 담아 값을 고정하면 이 문제를 피할 수 있다: `val v = b.value; if (v != null) v.length`. 스마트 캐스트의 원리와 불가능한 조건은 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 다룬다.

### 10.3 기본 구현을 바꾸면 경고 없이 동작이 달라질 수 있다

인터페이스 기본 구현은 편리하지만, 인터페이스를 변경할 때 문제를 일으킬 수 있다. 라이브러리가 인터페이스에 새 추상 메서드를 추가하면 기존 구현체가 모두 컴파일 에러를 내지만, 기본 구현이 있는 메서드를 추가하면 컴파일은 통과한다.

문제는 **의미가 바뀐 기본 구현이 그 메서드를 오버라이드하지 않은 모든 구현체에 아무 표시 없이 전파**된다는 점이다. 구현체가 "예전 기본 동작"에 의존하고 있었다면, 컴파일 에러 없이 런타임 동작만 달라진다. 인터페이스 기본 구현은 API를 안전하게 확장하는 수단이지만, 기본 동작의 계약은 신중하게 문서화해야 한다.

### 10.4 프로퍼티에 상태를 담고 싶은 유혹

인터페이스에 상태가 없다는 것을 이론으로 알고 나서도, 실전에서는 "인터페이스에 카운터를 하나 두고 싶다" 같은 생각이 든다. 컴파일러가 막으니 우회하려고 한다.

```kotlin
interface Counter {
    fun increment(): Int
    // "count를 인터페이스에 저장하고 싶다" — 방법이 없다
}
```

답은 언제나 같다. **상태는 구현 클래스에 둔다.** 인터페이스가 꼭 상태를 "요구"하고 싶다면, 추상 프로퍼티로 계약만 정하고 저장은 구현에 맡긴다(2.3절의 백킹 프로퍼티 패턴).

"인터페이스에 mutable 상태를 넣는 트릭"(예: 인스턴스를 키로 쓰는 전역 맵)은 스레드 안전성 문제, 메모리 누수, 캡슐화 파괴를 일으키는 안티패턴이므로 피해야 한다. 인터페이스가 상태를 담지 못하는 것은 한계가 아니라 다중 상속을 안전하게 만드는 설계 결정이라는 점을 기억하자(1.2절).

### 10.5 인터페이스 멤버는 final이 될 수 없다

클래스 멤버는 기본적으로 `final`이어서 `open`으로 열어 주어야 하지만(24장 상속과 오버라이딩과 초기화 순서), 인터페이스 멤버는 정반대다. 인터페이스 멤버는 본질적으로 `open`(오버라이드 가능)이며, `final`로 고정할 수 없다.

```kotlin
interface Foo {
    fun bar() = 1
    // final fun baz() = 2      // 컴파일 에러: Modifier 'final' is not applicable to 'member function of interface'
}
```

인터페이스는 "구현이 이래야 한다"는 계약이다. 구현 클래스가 기본 구현을 오버라이드할 자유를 원천적으로 막는 것은 인터페이스의 존재 이유와 맞지 않는다. 오버라이드를 막고 싶은 공통 로직이 있다면, 그 로직은 인터페이스가 아니라 구현 클래스의 `final` 멤버나 확장 함수 같은 다른 곳에 두어야 한다.
