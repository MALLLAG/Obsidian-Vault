**이 장이 답하는 질문:**

- 코틀린 인터페이스는 왜 프로퍼티를 선언할 수 있으면서도 "상태를 가질 수 없다"고 말하는가? (M37)
- `val name: String`을 인터페이스 본문에 쓰면 필드가 생기는가, 게터가 생기는가?
- 인터페이스에 메서드 본문(기본 구현)을 넣을 수 있다면, 그것은 추상 클래스와 무엇이 다른가?
- 두 인터페이스가 같은 시그니처의 기본 구현을 각각 제공할 때, 컴파일러는 왜 오버라이드를 강제하며 `super<A>.f()`는 어떻게 충돌을 푸는가?
- 코틀린 람다는 왜 아무 단일 메서드 인터페이스에나 꽂히지 않고, `fun interface`라고 표시해야만 SAM 변환이 되는가?
- 인터페이스는 여럿 상속되는데 클래스는 하나만 상속되는 이 비대칭은 어떤 문제(다이아몬드)를 피하려는 설계인가?
- 멤버가 하나도 없는 마커 인터페이스는 무엇을 위한 것이며, 애노테이션과 어떻게 다른가?
- 인터페이스 프로퍼티에 상태를 담고 싶을 때, "백킹 프로퍼티" 패턴은 왜 상태를 구현 클래스로 밀어내는가?

---

[[24 - 상속과 오버라이딩과 초기화 순서]]에서 우리는 클래스가 다른 클래스를 확장할 때 생기는 문제—초기화 순서, `open` 멤버를 생성자에서 부르는 함정(M47), `override`의 명시성—를 다뤘다. 그 논의는 내내 "단일 상속"을 전제했다. 코틀린 클래스는 상위 클래스를 *하나만* 가질 수 있다. 그런데 현실의 타입은 여러 능력을 동시에 지닌다. 오리는 헤엄칠 수 있고, 날 수 있고, 이름을 가진다. 이 "여러 능력을 한 타입에 조립"하는 축이 바로 인터페이스다. 이 장은 클래스 상속이 남긴 빈자리—다중 상속과 능력의 조합—를 인터페이스가 어떻게 채우는지를 정면으로 다룬다.

경계를 못박아 두자. 이 장은 **인터페이스라는 언어 장치 자체**—메서드와 프로퍼티 선언, 기본 구현, 다이아몬드 해소, `fun interface`, 마커 인터페이스—를 소유한다. 인터페이스를 이용해 "구현을 통째로 위임"하는 `class C(b: Base) : Base by b` 문법은 [[32 - 클래스 위임]]이 소유한다. 인터페이스 계층을 봉인해 `when`을 완전하게 만드는 `sealed interface`는 [[30 - sealed 클래스와 대수적 데이터 타입]]의 영역이다. 프로퍼티가 백킹 필드를 언제 갖고 게터/세터가 어떻게 컴파일되는지의 일반론은 [[22 - 프로퍼티와 백킹 필드]]가, 함수 타입과 람다 문법 자체는 [[13 - 함수 타입과 람다와 함수 참조]]가 소유한다. 이 장은 그 장치들이 *인터페이스 위에서* 어떻게 특수하게 작동하는지에 집중한다.

이 장의 소유 오개념은 M37이다. "코틀린 인터페이스는 상태를 가질 수 있다"는 흔한 오해를, 인터페이스 프로퍼티가 **백킹 필드 없는 접근자 추상**이라는 사실로 정면 교정한다. 인터페이스에 `val x: String`을 쓸 수 있고, 심지어 `val x get() = ...`처럼 기본 게터까지 줄 수 있으니 "필드를 담는다"고 착각하기 쉽다. 그러나 그 프로퍼티에는 값을 저장할 슬롯이 없다. 이 사실 하나가 인터페이스와 추상 클래스를 가르는 근본 경계선이며, 다중 상속이 안전한 이유이기도 하다.

논증의 궤적은 이렇다. 먼저 인터페이스가 "계약이자 능력"이라는 이중 정체성을 세우고, 왜 코틀린이 클래스는 단일·인터페이스는 다중으로 상속을 갈랐는지 본다. 그다음 인터페이스 프로퍼티를 해부해 M37을 교정하고, 상태를 담는 유일한 방법—구현 클래스로 밀어내기—을 확인한다. 이어 기본 구현이 만드는 다이아몬드 문제와 `super<T>` 해소, JVM 백엔드에서의 컴파일 형태, 추상 클래스와의 선택 기준을 다룬다. 후반부는 `fun interface`와 SAM 변환, 마커 인터페이스, 제네릭·변성과 인터페이스, 그리고 인터페이스를 다룰 때 사람들이 실제로 밟는 지뢰들을 훑는다.

## 1. 인터페이스란 무엇인가 - 계약이자 능력

### 1.1 두 얼굴: 명세(what)와 조립(mix-in)

인터페이스에는 서로 다른 두 목적이 겹쳐 있다. 하나는 **계약(contract)**—"이 타입을 쓰려면 이런 연산이 있어야 한다"는 명세다. 다른 하나는 **능력의 조립(mix-in)**—"이 타입은 이런 능력들을 겸비한다"는 조합이다. 코틀린 인터페이스는 이 둘을 한 장치로 처리한다.

```kotlin
interface Drawable {
    fun draw(): String            // 계약: 그릴 줄 알아야 한다
}

interface Named {
    val name: String              // 계약: 이름을 가져야 한다
}

// 능력의 조립: 도형은 그릴 수 있고 + 이름을 가진다
class Circle(override val name: String, val radius: Double) : Drawable, Named {
    override fun draw(): String = "○ $name (r=$radius)"
}

val c: Drawable = Circle("작은원", 1.0)
println(c.draw())          // => ○ 작은원 (r=1.0)
```

`Circle`은 두 인터페이스를 동시에 만족한다. 이것이 클래스 상속과 결정적으로 다른 점이다. 클래스는 하나만 확장할 수 있지만, 인터페이스는 콤마로 얼마든지 나열할 수 있다. 능력은 겹쳐 쌓이는 물건이지 단일 혈통이 아니기 때문이다.

### 1.2 왜 클래스는 하나, 인터페이스는 여럿인가

이 비대칭은 자의적이지 않다. **상태(state)를 담는 것과 담지 않는 것의 차이**에서 나온다. 클래스는 필드—실제 메모리 슬롯—를 가진다. 여러 클래스를 동시에 상속하면 각자의 필드가 합쳐지면서 "같은 이름의 필드가 둘"인 상황이나 "어느 상위의 생성자가 먼저 도는가" 같은 난제(고전적 다이아몬드 상속 문제)가 발생한다. C++가 가상 상속(virtual inheritance)이라는 복잡한 기계로 이 문제를 다루지만, 그 대가는 악명 높다.

코틀린은 자바가 택한 노선을 따른다. **상태를 담는 축(클래스)은 단일 상속으로 못박고, 상태 없는 계약의 축(인터페이스)만 다중으로 허용한다.** 인터페이스에는 저장할 필드가 없으니 필드 충돌이 원천적으로 불가능하다. 남는 것은 "같은 시그니처의 *메서드*가 여럿"인 경우인데, 이건 뒤에서 볼 `super<T>.f()`로 명시적으로 푼다. 필드 충돌(해결 난망)을 없애고 메서드 충돌(명시적 해소 가능)만 남긴 것이 이 설계의 핵심이다.

```text
        클래스 (상태 있음)              인터페이스 (상태 없음)
        ─────────────────              ────────────────────
  상속    단 하나 (single)             여럿 (multiple)
  이유    필드 충돌·초기화 순서         필드 없음 → 충돌 불가
          → 다이아몬드 지옥            메서드 충돌만 → super<T>로 해소

   class Dog : Animal, Pet   // 컴파일 에러: 클래스는 하나만
   class Dog : Animal, Runnable, Barkable  // OK: Animal만 클래스, 나머지 인터페이스
```

### 1.3 인터페이스는 인터페이스만 확장한다

인터페이스는 다른 인터페이스를 확장할 수 있지만, 클래스를 확장할 수는 없다. 계약이 다른 계약을 좁히거나 합치는 것은 자연스럽지만, 계약이 구현(상태)을 물려받는 것은 앞 절의 원칙을 깨기 때문이다.

```kotlin
interface Shape {
    val area: Double
}

// 인터페이스가 인터페이스를 확장 — OK
interface ColoredShape : Shape {
    val color: String
}

class RedSquare(val side: Double) : ColoredShape {
    override val area: Double get() = side * side   // Shape의 계약
    override val color: String get() = "red"        // ColoredShape의 계약
}
```

`ColoredShape`를 구현하는 클래스는 `Shape`와 `ColoredShape` *둘 다*의 계약을 이행해야 한다. 인터페이스 계층은 이렇게 계약을 누적한다.

> **흔한 오해**: "인터페이스는 자바 8 이전처럼 텅 빈 메서드 선언 모음일 뿐"이라는 인상이 아직도 흔하다. 코틀린 인터페이스는 처음부터(자바 8의 default 메서드 도입과 무관하게) 메서드 기본 구현, 프로퍼티 선언, 게터 구현, 중첩 타입, 컴패니언 객체를 담을 수 있다. 인터페이스는 "가난한 추상 클래스"가 아니라 "상태만 없는 완전한 타입"이다.

## 2. 인터페이스 프로퍼티 - 상태 없음의 진실 (M37)

### 2.1 백킹 필드가 없다는 것

이 장의 심장이자 소유 오개념 M37을 정면으로 다룬다. 인터페이스 본문에 프로퍼티를 선언할 수 있다는 사실 때문에 많은 사람이 "그럼 인터페이스도 값을 저장하네?"라고 생각한다. **아니다.** 인터페이스 프로퍼티는 값을 저장할 슬롯—백킹 필드(backing field)—을 가질 수 없다.

프로퍼티가 곧 필드라는 착각은 [[22 - 프로퍼티와 백킹 필드]]가 소유한 M35에서 이미 교정된다. 프로퍼티는 근본적으로 *접근자(get/set)의 추상*이며, 백킹 필드는 "저장이 실제로 필요할 때만" 컴파일러가 만들어 주는 부산물이다. 인터페이스에서는 그 부산물이 원천 봉쇄된다.

```kotlin
interface Named {
    val name: String            // 추상 프로퍼티: 게터만 있는 계약. 필드 없음.
}
```

`val name: String`은 "이 타입은 `name`을 *읽을 수 있어야 한다*"는 계약일 뿐이다. 값이 *어디에* 저장되는지는 인터페이스가 정하지 않는다. 구현 클래스가 정한다.

초기화자를 붙이려는 순간 컴파일러가 막는다.

```kotlin
interface Named {
    val name: String = "이름없음"
    // 컴파일 에러: Property initializers are not allowed in interfaces
}
```

에러 메시지가 정확히 이유를 말한다. 초기화자 `= "이름없음"`은 값을 어딘가에 저장하라는 요청이고, 저장하려면 필드가 필요하며, 인터페이스에는 필드가 없다. `field` 식별자를 직접 쓰려 해도 마찬가지다.

```kotlin
interface Counter {
    var count: Int
        get() = field          // 컴파일 에러: 'field' cannot be used here
        set(value) { field = value }
}
```

인터페이스 프로퍼티의 게터/세터 본문에서는 `field`가 존재하지 않는다. 접근자 안에서 참조할 저장 슬롯이 아예 없기 때문이다.

### 2.2 그렇다면 무엇을 담을 수 있나: 계산 프로퍼티

인터페이스가 담을 수 있는 것은 **다른 추상 멤버로부터 값을 계산하는 게터**다. 저장이 아니라 파생(derivation)이다.

```kotlin
interface Person {
    val firstName: String        // 추상 — 구현이 채운다
    val lastName: String         // 추상 — 구현이 채운다

    val fullName: String         // 기본 게터로 파생 — 저장 아님
        get() = "$firstName $lastName"
}

class Employee(
    override val firstName: String,
    override val lastName: String,
) : Person

val e = Employee("가", "나다")
println(e.fullName)              // => 가 나다
```

`fullName`은 인터페이스가 "구현"을 제공하는 것처럼 보이지만, 실제로는 매번 `firstName`과 `lastName`을 읽어 즉석에서 문자열을 만든다. 그 어디에도 `fullName`이라는 값이 *보관되지* 않는다. 접근할 때마다 다시 계산된다. 이것이 "상태 없음(stateless)"의 정확한 의미다—인터페이스가 제공하는 것은 **행동(계산 규칙)** 이지 **저장된 데이터**가 아니다.

```text
[인터페이스가 담을 수 있는 것]          [담을 수 없는 것]
  추상 프로퍼티 (게터 계약)      ✓       val x = 초기값 (초기화자)   ✗
  추상 프로퍼티 (세터 계약)      ✓       get() = field / set{field=} ✗
  계산 게터  val y get() = f()  ✓       lateinit var                ✗ (필드 필요)
  추상 메서드                    ✓       by lazy / by Delegates     ✗ (저장 필요)
  기본 구현 메서드               ✓       init 블록                   ✗ (인스턴스 상태)
  중첩 클래스 / companion        ✓       주/부 생성자                ✗ (필드 초기화)
```

`lateinit`이 안 되는 것도 같은 이유다. `lateinit var`는 나중에 채울 *필드*를 예약하는 장치인데([[11 - 변수와 초기화 - val과 const와 lateinit]], M9), 인터페이스엔 예약할 필드가 없다. `by lazy`나 `Delegates.observable` 같은 위임 프로퍼티([[23 - 위임 프로퍼티]])도 위임 객체를 *저장*해야 하므로 인터페이스에서는 쓸 수 없다.

### 2.3 상태를 담고 싶다면: 백킹 프로퍼티 패턴

"그래도 인터페이스가 어떤 상태를 강제하고 싶다"면, 방법은 하나다—**상태를 구현 클래스로 밀어낸다.** 인터페이스는 추상 프로퍼티로 *계약만* 걸고, 실제 저장은 이를 구현하는 클래스의 필드가 담당한다.

```kotlin
interface Stack<T> {
    val size: Int                 // 계약: 크기를 알 수 있어야 한다
    fun push(item: T)
    fun pop(): T
    val isEmpty: Boolean           // 파생 — size로부터 계산
        get() = size == 0
}

class ArrayStack<T> : Stack<T> {
    private val items = mutableListOf<T>()   // ← 상태는 여기, 구현 클래스에!
    override val size: Int get() = items.size

    override fun push(item: T) { items.add(item) }
    override fun pop(): T = items.removeAt(items.lastIndex)
}
```

`Stack` 인터페이스는 "크기를 안다"는 계약과 "비었는지 판단하는 규칙"(파생)만 제공한다. 실제 원소를 담는 `items` 필드는 `ArrayStack`이라는 *클래스*에 있다. 이것이 M37이 말하는 바의 실천이다. 인터페이스는 능력의 명세이고, 그 능력을 뒷받침하는 상태는 언제나 클래스로 내려간다.

한 걸음 더. 인터페이스가 "값을 하나 가진 것처럼" 보이게 하고 싶을 때도 마찬가지다.

```kotlin
interface HasId {
    val id: Long
}

// 구현마다 저장 방식이 다르다 — 인터페이스는 관여하지 않는다
class DbUser(override val id: Long, val email: String) : HasId          // 생성자 필드
class SeqUser(val seq: Int) : HasId {
    override val id: Long get() = seq.toLong() + 1000                    // 파생 (필드 없음)
}
```

같은 `HasId` 계약을 `DbUser`는 실제 필드로, `SeqUser`는 계산으로 만족한다. 인터페이스 관점에서는 둘 다 "`id`를 읽을 수 있는 타입"으로 동일하다. 저장 여부는 온전히 구현의 재량이다.

> **명세 정밀**: 코틀린 인터페이스 프로퍼티는 `val`/`var` 모두 선언할 수 있고, 게터(그리고 `var`면 세터)의 기본 구현도 줄 수 있다. 다만 그 구현은 **다른 접근 가능한 멤버만** 참조할 수 있고 `field`를 참조할 수 없다. `var`의 세터 기본 구현이 유용한 경우는 드물지만(저장할 곳이 없으니 보통 다른 추상 세터로 위임하거나 부수효과를 낼 뿐), 문법적으로 금지되진 않는다.

### 2.4 프로퍼티 오버라이드의 유연성

구현 클래스는 인터페이스의 추상 프로퍼티를 여러 방식으로 채울 수 있고, `val`을 `var`로 넓히는 것도 가능하다.

```kotlin
interface ReadableName {
    val name: String             // 읽기 계약만
}

// 구현이 var로 넓힘 — 읽기 계약을 만족하면서 쓰기까지 추가
class MutableName(override var name: String) : ReadableName

val m = MutableName("처음")
println(m.name)                  // => 처음
m.name = "나중"
println(m.name)                  // => 나중
```

`val`은 "읽을 수 있다"는 최소 계약이므로, 이를 "읽고 쓸 수 있다"(`var`)로 강화하는 것은 계약을 어기지 않는다(리스코프 치환 원칙에 부합—`ReadableName`으로 볼 땐 여전히 읽기만 노출된다). 반대로 인터페이스가 `var name`을 요구하는데 구현이 `val`로 좁히는 것은 불가능하다. 쓰기 능력을 없애면 계약 위반이기 때문이다. 프로퍼티 오버라이드 규칙 일반론은 [[24 - 상속과 오버라이딩과 초기화 순서]]가 소유한다.

## 3. 기본 구현 - 추상과 구체가 한 타입에

### 3.1 메서드에 본문을 담다

코틀린 인터페이스의 메서드는 두 가지다. 본문이 없으면 **추상 메서드**(구현 강제), 본문이 있으면 **기본 구현(default implementation)** 이다.

```kotlin
interface Greeter {
    val name: String                 // 추상 프로퍼티
    fun greet(): String              // 추상 메서드 — 구현 필수
    fun greetLoudly(): String =      // 기본 구현 — 오버라이드 선택
        greet().uppercase() + "!!!"
}

class Formal(override val name: String) : Greeter {
    override fun greet() = "안녕하십니까, ${name}입니다"
    // greetLoudly는 오버라이드하지 않아도 됨 — 기본 구현을 물려받음
}

val f = Formal("정중이")
println(f.greet())               // => 안녕하십니까, 정중이입니다
println(f.greetLoudly())         // => 안녕하십니까, 정중이입니다!!!
```

`greetLoudly`는 추상 멤버인 `greet`를 호출해 동작을 조립한다. 이것이 인터페이스 기본 구현의 전형적 쓰임이다—**골격 알고리즘(template method)** 을 인터페이스에 두고, 구멍(추상 멤버)만 구현 클래스가 메우게 한다. 상태 없이 행동만 조립하므로 여러 인터페이스에 걸쳐 능력을 겹겹이 쌓을 수 있다.

### 3.2 기본 구현도 상태에는 손대지 못한다

기본 구현이 강력해 보여도 그 한계는 명확하다. **기본 구현 안에서도 인터페이스는 상태에 접근할 수 없다.** 참조할 수 있는 것은 (추상이든 기본이든) 다른 멤버뿐이다.

```kotlin
interface Sequence2 {
    var current: Int              // 추상 — 저장은 구현 클래스가
    fun next(): Int {             // 기본 구현
        current += 1              // OK: 추상 프로퍼티 current의 세터/게터 호출
        return current
        // 여기서 로컬 캐시 필드를 두는 것은 불가능 — 저장할 곳이 없다
    }
}
```

`next()`의 `current += 1`은 `current`라는 추상 프로퍼티의 게터로 읽고 세터로 쓴다. 그 값이 실제로 어디 저장되는지는 이 인터페이스가 모른다—구현 클래스의 필드다. 인터페이스는 상태를 *조작하는 규칙*은 담지만 상태 *자체*는 담지 않는다는 원칙이 기본 구현에서도 그대로 유지된다.

### 3.3 인터페이스에도 private 헬퍼가 있다

기본 구현이 복잡해지면 인터페이스 내부에 private 헬퍼 함수를 두고 싶어진다. 코틀린은 이를 허용한다. 단, private 멤버는 반드시 본문(구현)을 가져야 한다—추상 private은 모순(구현할 방법이 없음)이기 때문이다.

```kotlin
interface Validator {
    val rawInput: String

    fun isValid(): Boolean = normalized().isNotEmpty()    // public 기본 구현

    private fun normalized(): String =                     // private 헬퍼
        rawInput.trim().lowercase()
}
```

`normalized()`는 인터페이스 밖에서 보이지 않고, `isValid()` 같은 다른 기본 구현을 돕는 데만 쓰인다. 한편 인터페이스 멤버의 가시성에는 클래스와 다른 제약이 있다. **인터페이스 멤버는 `public`(기본)이거나 `private`일 수 있을 뿐, `protected`나 `internal`은 허용되지 않는다.** 가시성 한정자의 일반론은 [[26 - 가시성 한정자]]가 소유하지만, 인터페이스가 "구현을 강제하는 공개 계약"이라는 성격상 `protected`(하위만 접근)나 `internal`(모듈 한정)이 의미를 갖기 어렵다는 점만 기억하면 된다.

```kotlin
interface Api {
    protected fun secret()       // 컴파일 에러: Modifier 'protected' is not applicable to 'member function of interface'
    internal fun scoped()        // 컴파일 에러: Modifier 'internal' is not applicable ...
}
```

### 3.4 인터페이스의 상수는 companion으로

인터페이스 본문에 직접 `const val`이나 초기화된 프로퍼티를 둘 수 없다(2.1에서 본 대로 저장 슬롯이 없다). 상수를 두려면 인터페이스의 **컴패니언 객체**에 담는다.

```kotlin
interface HttpStatus {
    val code: Int

    companion object {
        const val OK = 200                 // 컴패니언은 진짜 객체 → 저장 가능
        const val NOT_FOUND = 404
    }
}

println(HttpStatus.OK)           // => 200
```

컴패니언 객체는 인터페이스에 딸린 *진짜 싱글턴 인스턴스*이므로 상태를 저장할 수 있다([[28 - object와 companion - 싱글턴과 동반 객체]]). 인터페이스 본문은 상태 없음, 컴패니언은 상태 있음—이 경계가 헷갈리지 않아야 한다.

## 4. 다중 상속과 다이아몬드 - `super<T>`로 충돌 풀기

### 4.1 충돌이 생기는 순간

두 인터페이스가 같은 시그니처의 기본 구현을 각각 제공하고, 한 클래스가 둘 다 구현하면 어떤 구현을 써야 하는지 모호해진다. 코틀린은 이 모호함을 **컴파일 에러로 막고, 개발자에게 명시적 오버라이드를 강제**한다.

```kotlin
interface A {
    fun foo() { print("A") }     // 기본 구현
    fun bar()                    // 추상
}

interface B {
    fun foo() { print("B") }     // 기본 구현 — A와 충돌!
    fun bar() { print("bar") }   // 기본 구현
}

class D : A, B {
    // foo()를 오버라이드하지 않으면:
    // 컴파일 에러: Class 'D' must override public open fun foo(): Unit
    //             because it inherits many implementations of it
    override fun foo() {
        super<A>.foo()           // A의 기본 구현 명시 호출
        super<B>.foo()           // B의 기본 구현 명시 호출
    }
    override fun bar() {
        super<B>.bar()           // A.bar는 추상, B.bar는 구체 — 그래도 명시 오버라이드 요구
    }
}

D().foo()                        // => AB
```

`super<A>.foo()`와 `super<B>.foo()`가 다이아몬드 해소의 핵심 문법이다. 꺾쇠 안에 어느 상위 타입의 구현을 부를지 명시함으로써 모호함이 사라진다. 필요하면 둘 다 호출할 수도, 하나만 골라 부를 수도, 완전히 새로 쓸 수도 있다.

### 4.2 추상 하나 + 기본 하나여도 오버라이드가 필요한 이유

`bar()`에 주목하자. `A.bar()`는 추상이고 `B.bar()`는 기본 구현이 있다. "구현이 하나뿐이니 그냥 B 것을 쓰면 되지 않나?" 싶지만, 코틀린은 이 경우에도 **명시적 오버라이드를 요구**한다. 이유는 `D`가 두 상위로부터 `bar`에 대한 서로 다른 선언—하나는 추상, 하나는 구체—을 상속받았고, 컴파일러가 "개발자가 의도적으로 어느 쪽을 택했는지"를 코드로 확인받고자 하기 때문이다. 암묵적으로 B를 골랐다가 나중에 A의 계약이 바뀌면 조용히 잘못될 수 있는데, 명시적 오버라이드는 그 결정을 코드에 박제한다.

```text
[다이아몬드]

        A            B
     foo(){A}     foo(){B}      ← 같은 이름의 기본 구현 두 개
     bar()        bar(){bar}    ← 추상 하나 + 기본 하나
        \          /
         \        /
            class D            ← foo, bar 모두 override 강제
                               ← super<A>/<B>로 어느 것을 부를지 명시
```

### 4.3 충돌이 없으면 조용히 물려받는다

당연하지만, 충돌이 없으면 오버라이드는 필요 없다. 한 인터페이스만 기본 구현을 제공하고 다른 곳엔 그 멤버가 없다면, 그 기본 구현이 그대로 상속된다.

```kotlin
interface Walk { fun move() = "걷는다" }
interface Name { val label: String }

class Cat(override val label: String) : Walk, Name
// move()는 Walk의 기본 구현을 그대로 물려받음 — 충돌 없음

println(Cat("나비").move())      // => 걷는다
```

### 4.4 클래스 상위와 인터페이스가 겹칠 때

클래스를 하나 확장하면서 인터페이스도 구현할 때, 클래스 쪽 구현과 인터페이스 기본 구현이 같은 시그니처로 겹칠 수 있다. 자바라면 이런 충돌에서 "클래스가 인터페이스를 이긴다"는 규칙으로 상위 클래스 구현이 조용히 채택되지만, **코틀린은 더 엄격해서 구체 구현이 둘(클래스+인터페이스 기본) 함께 상속되면 명시적 오버라이드를 요구**한다. 다만 인터페이스 쪽 멤버가 *추상*(기본 구현 없음)이라면, 상속받은 클래스의 구체 구현이 그 계약을 그대로 만족시키므로 별도 오버라이드가 필요 없다.

```kotlin
open class Vehicle {
    open fun describe() = "탈것"
}
interface Loud {
    fun describe() = "시끄러운 것"   // 인터페이스 기본
}

class Truck : Vehicle(), Loud {
    // Vehicle.describe(구체)와 Loud.describe(기본)가 충돌 → 명시 오버라이드 요구
    override fun describe() = super<Vehicle>.describe() + " / " + super<Loud>.describe()
}

println(Truck().describe())      // => 탈것 / 시끄러운 것
```

`super<Vehicle>`처럼 클래스 상위도 꺾쇠 문법으로 지목할 수 있다. `super<T>` 문법은 인터페이스 전용이 아니라 "여러 상위 중 하나를 지목"하는 일반 장치다.

## 5. JVM 백엔드에서의 컴파일 형태

### 5.1 인터페이스는 Java 인터페이스로

JVM 백엔드에서 코틀린 인터페이스는 자바 인터페이스로 컴파일된다. 추상 메서드는 자바 인터페이스의 추상 메서드가 되고, 프로퍼티는 게터/세터 메서드(`getName()`/`setName()`)의 추상 선언이 된다. 여기까지는 직관적이다. 흥미로운 부분은 **기본 구현이 어떻게 내려앉는가**다.

### 5.2 기본 구현: DefaultImpls 대 JVM default 메서드

코틀린이 인터페이스 기본 구현을 컴파일하는 방식은 **컴파일러의 jvm-default 모드에 따라** 달라진다. 역사적으로 두 전략이 있다.

- **DefaultImpls 전략(옛 기본)**: 인터페이스에는 메서드를 추상으로만 두고, 기본 구현의 본문을 `인터페이스이름$DefaultImpls`라는 정적 중첩 클래스의 static 메서드로 뽑아낸다. 이를 구현하는 클래스는 그 static 메서드를 호출하는 브리지 메서드를 갖는다. 이 방식은 자바 6/7 바이트코드와도 호환됐고, 인터페이스 진화 시 바이너리 호환성을 지키기 유리했다.
- **JVM default 메서드 전략**: 자바 8의 `default` 메서드를 그대로 사용해, 기본 구현 본문을 인터페이스 안에 직접 default 메서드로 넣는다. 자바 쪽에서 코틀린 인터페이스를 상속할 때 더 자연스럽고, `DefaultImpls`라는 우회 클래스가 사라진다.

```text
[DefaultImpls 전략 (개념)]
  interface Greeter { abstract greetLoudly()V ... }
  class Greeter$DefaultImpls {
      static greetLoudly(Greeter $this) { ... $this.greet() ... }
  }
  class Formal implements Greeter {
      greetLoudly() { return Greeter$DefaultImpls.greetLoudly(this); }   // 브리지
  }

[JVM default 전략 (개념)]
  interface Greeter { default greetLoudly()V { ... this.greet() ... } }
  class Formal implements Greeter { /* 인터페이스 default 그대로 상속 */ }
```

어느 전략이 쓰이는지는 컴파일러 플래그(`-jvm-default` / 과거의 `-Xjvm-default`)와 빌드 설정에 좌우된다. 이 값은 코틀린 버전에 따라 기본값과 모드 이름이 바뀌어 왔으므로, 특정 바이트코드 형태를 코드가 가정해서는 안 된다. 확실한 것은 하나다—**어느 전략이든 인터페이스는 상태(필드)를 담지 않는다.** default 메서드든 DefaultImpls든 참조하는 것은 오직 다른 멤버(추상 게터/세터 포함)뿐이다. 컴파일 형태가 바뀌어도 M37은 흔들리지 않는다. 컴파일 파이프라인 전반은 [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]가 소유한다.

> **성능 주의**: DefaultImpls 전략에서는 기본 구현 호출이 한 단계(브리지 → static 메서드)를 더 거치지만, JIT가 대개 인라인해 실측 비용은 무시할 만하다. 진짜 주의점은 성능이 아니라 **바이너리 호환성**이다. jvm-default 모드를 프로젝트 중간에 바꾸면, 이미 배포된 서브클래스와 새 컴파일 결과 사이에 브리지 유무가 어긋나 `AbstractMethodError`가 날 수 있다. 라이브러리를 배포한다면 이 모드를 신중히 고정해야 한다.

### 5.3 디컴파일로 확인하기

이 모든 것은 추측할 필요 없이 직접 볼 수 있다. IntelliJ의 "Tools → Kotlin → Show Kotlin Bytecode → Decompile" 또는 CLI로 `.class`를 역컴파일하면, `DefaultImpls` 클래스의 유무와 게터 메서드 이름(`getName()`)을 눈으로 확인할 수 있다. "인터페이스가 상태를 담는가?"라는 의심이 들 때, 컴파일된 인터페이스 클래스에 인스턴스 필드가 하나도 없다는 사실을 직접 보는 것이 가장 확실한 교정이다.

## 6. 인터페이스 대 추상 클래스 - 언제 무엇을

### 6.1 결정적 차이 세 가지

인터페이스와 추상 클래스는 "미완성 타입"이라는 점에서 닮았지만 세 지점에서 갈린다.

| 축 | 인터페이스 | 추상 클래스 |
|----|-----------|------------|
| 상태(필드) | 불가 — 백킹 필드 없음 (M37) | 가능 — 필드·`init`·생성자 보유 |
| 상속 개수 | 여럿 구현 가능 | 하나만 확장 가능 |
| 생성자 | 없음 | 있음 (파라미터·초기화 가능) |
| 가시성 한정자 | public/private만 | 클래스와 동일(protected/internal 포함) |
| 기본 구현 | 가능 (상태 없이) | 가능 (상태와 함께) |
| 존재 이유 | 능력/계약의 조립 | 부분 구현 + 공유 상태의 골격 |

### 6.2 판단 기준: 상태와 정체성

실무의 선택 기준은 단순하다. **공유할 상태(필드)나 생성자 초기화 로직이 필요하면 추상 클래스, 순수한 능력의 계약이면 인터페이스**다. 그리고 "여러 축의 능력을 겸비"해야 하면 인터페이스가 강제된다(클래스는 하나만 상속되므로).

```kotlin
// 상태를 공유하고 초기화 로직이 있다 → 추상 클래스
abstract class Account(initial: Long) {
    var balance: Long = initial          // 공유 상태 (필드)
        protected set
    init { require(initial >= 0) }        // 생성자 검증 — 인터페이스엔 불가
    abstract fun interestRate(): Double   // 구멍
    fun applyInterest() { balance += (balance * interestRate()).toLong() }
}

// 순수 능력의 계약 → 인터페이스
interface Auditable {
    fun auditLog(): String                // 상태 없이 계약만
}

// 조합: 하나의 클래스 상속 + 여러 인터페이스
class SavingsAccount(initial: Long) : Account(initial), Auditable {
    override fun interestRate() = 0.02
    override fun auditLog() = "잔액 $balance"
}
```

`Account`는 `balance`라는 상태와 `init` 검증을 가지므로 추상 클래스여야 한다. `Auditable`은 상태 없는 능력이므로 인터페이스가 알맞다. `SavingsAccount`는 `Account`를 유일한 상위 클래스로 확장하면서 `Auditable`을 겸비한다.

### 6.3 "인터페이스 우선" 관용

설계 격언으로 "가능하면 인터페이스를 우선하라"는 말이 있다. 인터페이스는 여럿 구현 가능하므로 미래의 조합 가능성을 열어 두고, 상태를 강요하지 않아 결합도가 낮다. 추상 클래스는 "이 계층이 반드시 공유해야 하는 상태나 불변식이 있을 때"의 무거운 도구다. 다만 코틀린에서는 이 격언의 무게가 자바보다 덜하다—코틀린 인터페이스가 이미 기본 구현을 담을 수 있어, 자바에서 "추상 클래스로 공통 코드를 공유"하던 상당수를 인터페이스만으로 해결할 수 있기 때문이다.

> **역사 메모**: 자바 8 이전에는 인터페이스에 구현을 담을 수 없어, 공통 코드를 나누려면 추상 클래스가 불가피했다(그래서 `AbstractList`, `AbstractMap` 같은 골격 구현체가 표준 라이브러리에 즐비했다). 코틀린은 처음부터 인터페이스 기본 구현을 지원해 이 이분법을 크게 완화했다. 다만 코틀린도 상태가 필요한 순간에는 여전히 추상 클래스(또는 구현 클래스)로 내려가야 한다—기본 구현이 상태의 부재라는 벽을 넘게 해 주진 않기 때문이다.

## 7. fun interface와 SAM 변환 - 람다가 인터페이스가 될 때

### 7.1 왜 아무 인터페이스에나 람다가 꽂히지 않는가

메서드가 딱 하나인 인터페이스—단일 추상 메서드(Single Abstract Method, SAM)—는 개념적으로 함수 하나와 같다. 그렇다면 람다를 그 자리에 바로 넣을 수 있어야 자연스럽다. 그러나 코틀린에서 **일반 인터페이스에는 람다를 직접 넣을 수 없다.**

```kotlin
interface Predicate2<T> {
    fun test(t: T): Boolean
}

fun <T> filterOne(item: T, p: Predicate2<T>): Boolean = p.test(item)

// filterOne(5, { it > 0 })
// 컴파일 에러: Type mismatch — 람다는 Predicate2가 아니다
```

코틀린에 이미 일급 함수 타입 `(T) -> Boolean`이 있는데([[13 - 함수 타입과 람다와 함수 참조]]), 만약 아무 SAM 인터페이스에나 람다가 자동 변환된다면 오버로드 해소가 모호해지고 "이 람다가 함수 타입인지 어떤 인터페이스인지" 예측하기 어려워진다. 그래서 코틀린은 SAM 변환을 **명시적으로 표시된 인터페이스에만** 허용한다.

### 7.2 fun interface: 함수형 인터페이스 선언

인터페이스 앞에 `fun`을 붙이면 **함수형 인터페이스(functional interface)** 가 되고, 람다를 그 타입으로 변환할 수 있다.

```kotlin
fun interface Predicate<T> {
    fun test(t: T): Boolean       // 정확히 하나의 추상 메서드
}

fun <T> filterOne(item: T, p: Predicate<T>): Boolean = p.test(item)

// 이제 람다가 곧바로 Predicate로 변환된다 (SAM 변환)
println(filterOne(5) { it > 0 })         // => true
println(filterOne(-3) { it > 0 })        // => false

val positive = Predicate<Int> { it > 0 } // 변수에 담을 때도 SAM 변환
println(positive.test(10))               // => true
```

`fun interface`는 추상 메서드가 **정확히 하나**여야 한다. 추상 메서드가 없거나 둘 이상이면 컴파일 에러다. 단, 기본 구현 메서드나 계산 프로퍼티(추상이 아닌 것)는 얼마든지 추가할 수 있다—"추상"이 하나면 되기 때문이다. 반면 **추상 프로퍼티는 허용되지 않는다**(그 자체가 추상 게터라는 또 하나의 추상 멤버가 되기 때문).

```kotlin
fun interface Transformer<T, R> {
    fun transform(input: T): R              // 유일한 추상 메서드
    fun describe(): String = "변환기"        // 기본 구현 — 허용
}
// fun interface Bad { fun a(); fun b() }   // 컴파일 에러: 추상 메서드가 둘
// fun interface Bad2 { val x: Int }        // 컴파일 에러: 추상 프로퍼티(추상 게터)
```

### 7.3 fun interface 대 함수 타입 typealias

"함수 하나"를 나타내는 방법은 두 가지다—`fun interface`와 함수 타입(또는 그 `typealias`, [[36 - 타입 별칭과 인라인 value class]]). 언제 무엇을 쓰나?

```kotlin
// 방법 1: 함수 타입 (또는 typealias)
typealias IntPredicate = (Int) -> Boolean

// 방법 2: fun interface
fun interface IntPredicateFI {
    fun accept(n: Int): Boolean
}
```

| 축 | 함수 타입 `(Int)->Boolean` | `fun interface` |
|----|---------------------------|-----------------|
| 이름 있는 도메인 개념 | 약함 (구조적 타입) | 강함 (명목 타입) |
| 추가 멤버(기본 구현) | 불가 | 가능 |
| 여러 함수 타입과 오버로드 구분 | 어려움 | 쉬움(별개 명목 타입) |
| 다른 인터페이스 상속/구현 | 불가 | 가능 |
| 간결함 | 최고 | 선언 필요 |

일반적으로 **단순히 "함수 하나를 넘긴다"면 함수 타입**이 간결하고 충분하다. 반면 **그 함수에 이름 있는 정체성을 부여하거나, 기본 구현·부가 멤버를 함께 담거나, 여러 "함수 하나짜리" 개념을 오버로드로 구별**하고 싶으면 `fun interface`가 낫다. 예컨대 `(Int) -> Boolean` 하나로는 "짝수 판별"과 "양수 판별"을 타입으로 구분할 수 없지만, `EvenCheck`와 `PositiveCheck`라는 두 `fun interface`는 명목적으로 구별된다.

### 7.4 Java 인터페이스와의 SAM 변환

코틀린이 SAM 변환을 `fun interface`로 제한하는 규칙에는 예외가 있다—**자바에서 정의된 단일 추상 메서드 인터페이스**는 `fun` 표시가 없어도 SAM 변환이 된다. 자바에는 `fun interface` 문법이 없고, 자바 라이브러리의 `Runnable`, `Comparator`, `Callable` 같은 인터페이스에 람다를 넘기는 상호운용이 필수적이기 때문이다.

```kotlin
// java.lang.Runnable — 자바 SAM 인터페이스
val r = Runnable { println("실행") }       // SAM 변환 OK (fun 없이도)
r.run()                                     // => 실행

// java.util.Comparator — 자바 SAM 인터페이스
val byLength = Comparator<String> { a, b -> a.length - b.length }
println(listOf("bb", "a", "ccc").sortedWith(byLength))   // => [a, bb, ccc]
```

정리하면 SAM 변환이 되는 경우는 두 가지다. **(1) 코틀린 `fun interface`, (2) 자바에서 정의된 SAM 인터페이스.** 코틀린에서 `fun` 없이 선언한 일반 인터페이스는 SAM 변환 대상이 아니다. Java 상호운용 전반은 [[45 - Java 상호운용]]이 소유한다.

### 7.5 SAM 변환의 컴파일

`Predicate<Int> { it > 0 }`가 컴파일되면, JVM 백엔드에서는 `Predicate`를 구현하는 익명 클래스 인스턴스(또는 `invokedynamic` 기반 람다 팩토리)가 생성된다. 개념적으로는 다음과 동등하다.

```kotlin
// SAM 변환 전:  Predicate<Int> { it > 0 }
// 개념적으로:
object : Predicate<Int> {
    override fun test(t: Int): Boolean = t > 0
}
```

즉 SAM 변환은 "람다를 익명 객체로 감싸는" 문법 설탕이다. 익명 객체 자체는 [[31 - 중첩 클래스와 이너 클래스와 익명 객체]]가 소유한다. 성능 관점에서, 인라인 고차 함수에 넘기는 람다는 객체 할당이 제거되지만([[15 - 인라인 함수와 reified]]), `fun interface` 값을 변수에 담거나 인라인이 아닌 곳에 넘기면 인스턴스가 실제로 만들어진다.

## 8. 마커 인터페이스와 인터페이스의 그 밖의 쓰임

### 8.1 멤버 없는 인터페이스: 태그로서의 타입

멤버가 하나도 없는 인터페이스를 **마커 인터페이스(marker interface)** 라 한다. 아무 계약도 강제하지 않지만, "이 타입에 속한다"는 사실 자체가 정보다.

```kotlin
interface Cacheable        // 멤버 없음 — 순수 태그

class Report : Cacheable
class TempFile             // Cacheable 아님

fun store(x: Any) {
    if (x is Cacheable) {
        println("캐시에 저장")       // 타입으로 능력을 판별
    } else {
        println("캐시 생략")
    }
}

store(Report())            // => 캐시에 저장
store(TempFile())          // => 캐시 생략
```

`is Cacheable` 검사로 런타임에 "이 객체가 캐시 대상 태그를 달았는지"를 확인한다. JVM의 `java.io.Serializable`이 대표적 마커 인터페이스다—메서드는 없지만 "직렬화 가능"이라는 타입 수준 표식이다.

### 8.2 마커 인터페이스 대 애노테이션

같은 "태그" 목적으로 애노테이션([[44 - 애노테이션과 리플렉션]])을 쓸 수도 있다. 둘의 차이는 결정적이다.

| 축 | 마커 인터페이스 | 마커 애노테이션 |
|----|----------------|-----------------|
| 타입 시스템 참여 | 예 — `is`/타입 파라미터 상한에 사용 | 아니오 — 리플렉션으로만 조회 |
| 컴파일 타임 검사 | 가능 (`fun f(x: Cacheable)`) | 불가 (런타임 조회) |
| 상속 | 하위 타입에 전파 | 기본적으로 전파 안 됨 |
| 파라미터(부가 정보) | 불가 | 가능 (`@Cache(ttl=60)`) |

**컴파일 타임에 타입으로 강제**하고 싶으면 마커 인터페이스가 낫다. `fun cache(x: Cacheable)`처럼 시그니처로 "캐시 가능한 것만 받는다"를 표현할 수 있다. 반면 **부가 데이터를 실어야 하거나 순수 메타데이터**라면 애노테이션이 맞다. 요컨대 마커 인터페이스는 타입 시스템에 사는 태그, 마커 애노테이션은 그 밖에 사는 메타데이터다.

### 8.3 인터페이스와 익명 객체 - 인스턴스화

인터페이스는 직접 인스턴스화할 수 없다(구현이 미완성). 그러나 **object 표현식**으로 즉석에서 구현을 채워 인스턴스를 만들 수 있다.

```kotlin
interface ClickListener {
    fun onClick(x: Int, y: Int)
}

fun register(listener: ClickListener) { listener.onClick(10, 20) }

register(object : ClickListener {          // 익명 객체로 인터페이스 구현
    override fun onClick(x: Int, y: Int) {
        println("클릭: ($x, $y)")
    }
})
// => 클릭: (10, 20)
```

`ClickListener`가 `fun interface`였다면 이 자리에 람다를 쓸 수 있었을 것이다(7절). 추상 메서드가 여럿이거나 `fun`이 아니라면 익명 객체가 정답이다.

### 8.4 sealed interface 예고

인터페이스 계층은 기본적으로 열려 있어 누구나 구현할 수 있다. 이를 봉인해 "이 인터페이스의 구현체는 이것들이 전부"라고 컴파일러에 알리면, `when`이 `else` 없이 완전해진다. 이것이 `sealed interface`인데, 대수적 데이터 타입(합타입)을 표현하는 강력한 도구다.

```kotlin
sealed interface Shape2
data class Circle2(val r: Double) : Shape2
data class Rect2(val w: Double, val h: Double) : Shape2

fun area(s: Shape2): Double = when (s) {   // else 불필요 — 완전성 보장
    is Circle2 -> Math.PI * s.r * s.r
    is Rect2 -> s.w * s.h
}
```

깊이 있는 논의(봉인 범위, ADT, enum과의 대조)는 [[30 - sealed 클래스와 대수적 데이터 타입]]이 소유한다. 여기서는 "인터페이스는 봉인될 수 있고, 봉인되면 완전성 검사의 토대가 된다"는 연결만 기억하면 된다.

## 9. 제네릭·변성과 인터페이스

### 9.1 인터페이스는 변성의 주무대

변성(variance)—`out`(공변)/`in`(반공변)—은 대개 인터페이스에 선언된다. 표준 라이브러리의 핵심 인터페이스들이 이를 보여 준다.

```kotlin
interface Producer<out T> {       // out: T는 생산(반환) 위치에만
    fun produce(): T
}
interface Consumer<in T> {        // in: T는 소비(인자) 위치에만
    fun consume(item: T)
}
```

`Producer<out T>`가 공변이라는 것은, `Producer<Cat>`을 `Producer<Animal>`로 안전하게 볼 수 있다는 뜻이다(고양이를 생산하는 것은 동물을 생산하는 것으로 취급 가능). 반대로 `Consumer<in T>`는 반공변이라 `Consumer<Animal>`을 `Consumer<Cat>`으로 볼 수 있다(동물을 소비할 수 있으면 고양이도 소비할 수 있다). 이 규칙의 안전성 증명과 사용지점 변성 등은 [[33 - 제네릭 1 - 타입 파라미터와 변성]]과 [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]가 소유한다. 여기서는 "인터페이스가 왜 변성 선언의 자연스러운 자리인지"만 짚는다—인터페이스는 상태가 없어 "생산만 하는 타입", "소비만 하는 타입"을 순수하게 표현하기 좋기 때문이다. 표준 라이브러리의 `Iterator<out T>`, `Comparable<in T>`, `Comparator<in T>`가 모두 인터페이스이자 변성을 띤다.

### 9.2 인터페이스가 곧 변성 표현의 이유

$Producer\langle Cat \rangle <: Producer\langle Animal \rangle$ 가 성립하려면($<:$는 하위타입 관계), `T`가 오직 출력 위치에만 나타나야 안전하다. 인터페이스는 필드(입력이자 출력인 상태)를 갖지 않으므로, `out T`를 선언하면 컴파일러가 "T가 정말 출력에만 쓰였는가"를 검사하기 수월하다. 클래스에도 변성을 선언할 수 있지만, 상태를 담는 클래스는 그 상태 필드가 입력·출력 위치를 모두 만족시켜야 해서 변성 제약을 지키기 까다로울 때가 많다. 변성과 인터페이스가 잘 어울리는 이유가 여기 있다.

### 9.3 제네릭 인터페이스의 다중 구현 제약

한 클래스가 같은 제네릭 인터페이스를 서로 다른 타입 인자로 두 번 구현하는 것은 불가능하다.

```kotlin
interface Handler<T> { fun handle(x: T) }

// class Multi : Handler<Int>, Handler<String>
// 컴파일 에러: 'Handler' cannot be a superinterface twice with different type arguments
```

JVM 백엔드에서 타입 소거(M19, [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]) 때문에 `Handler<Int>`와 `Handler<String>`은 런타임에 같은 `Handler`가 되어 `handle` 메서드가 충돌한다. 코틀린은 이 모호함을 컴파일 타임에 막는다.

## 10. 인터페이스의 함정 - 실전에서 밟는 지뢰

### 10.1 인터페이스 프로퍼티는 초기화되지 않는다

가장 흔한 함정. 인터페이스에서 파생 게터로 정의한 프로퍼티가 "다른 추상 프로퍼티가 초기화되기 전에" 접근되면 예기치 않은 값이 나온다. 특히 구현 클래스의 `init` 블록이나 생성자에서 인터페이스 파생 프로퍼티를 부르면 위험하다—이는 [[24 - 상속과 오버라이딩과 초기화 순서]]의 M47(초기화 순서 함정)과 같은 뿌리다.

```kotlin
interface HasFullName {
    val first: String
    val last: String
    val full: String get() = "$first $last"    // 파생
}

class P(override val first: String) : HasFullName {
    override val last: String = computeLast()    // 나중에 초기화
    private fun computeLast(): String { println("full 지금=$full"); return "김" }
}
// P("영희") 생성 시:
// => full 지금=영희 null    ← last가 아직 초기화 전! (파생 게터가 미초기화 last를 읽음)
```

`computeLast()`가 `full`을 읽는 시점에 `last`는 아직 초기화되지 않아 `null`(플랫폼상 기본값)이 섞여 나온다. 인터페이스 파생 프로퍼티는 "접근 시점에 계산"되므로, 그 시점의 상태 초기화 여부에 전적으로 의존한다. 파생 게터는 초기화 완료 후에만 부르는 것이 안전하다.

### 10.2 스마트 캐스트가 인터페이스 프로퍼티에서 막힌다

인터페이스의 `val` 프로퍼티는 커스텀 게터를 가질 수 있으므로, 컴파일러가 "두 번 읽으면 같은 값"을 보장하지 못한다. 따라서 인터페이스 프로퍼티에 대한 스마트 캐스트(M13)는 대체로 막힌다.

```kotlin
interface Box {
    val value: String?           // 커스텀 게터일 수 있음 → 안정성 미보장
}

fun show(b: Box) {
    if (b.value != null) {
        // println(b.value.length)
        // 컴파일 에러(또는 경고): Smart cast to 'String' is impossible,
        //   because 'b.value' is a property that has open or custom getter
    }
}
```

`b.value`는 두 번 호출하면 다른 값을 낼 수도 있는 게터일 수 있으므로(첫 검사에선 non-null, 다음 접근에선 null일 가능성), 컴파일러는 스마트 캐스트를 거부한다. 지역 변수에 담아 고정하면 우회된다: `val v = b.value; if (v != null) v.length`. 스마트 캐스트의 원리와 불가 조건은 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]이 소유한다.

### 10.3 기본 구현을 바꾸면 조용히 깨질 수 있다

인터페이스 기본 구현은 편리하지만 진화의 지뢰다. 라이브러리가 인터페이스에 새 추상 메서드를 추가하면 모든 기존 구현체가 깨지지만(컴파일 에러), 기본 구현이 있는 메서드를 추가하면 컴파일은 통과한다. 문제는 **의미가 바뀐 기본 구현이 오버라이드하지 않은 모든 구현체에 조용히 전파**된다는 점이다. 구현체가 "예전 기본 동작"에 의존하고 있었다면, 컴파일 에러 없이 런타임 동작만 달라진다. 인터페이스 기본 구현은 "안전한 API 확장 수단"이지만, 그 기본 동작의 계약을 신중히 문서화해야 한다.

### 10.4 프로퍼티에 상태를 담으려는 유혹

M37을 이론으로 안 뒤에도, 실전에서는 "인터페이스에 카운터를 하나 두고 싶다" 같은 유혹이 온다. 컴파일러가 막으니 우회하려 든다.

```kotlin
interface Counter {
    fun increment(): Int
    // "count를 인터페이스에 저장하고 싶다" — 방법이 없다
}
```

정답은 언제나 같다. **상태는 구현 클래스로.** 굳이 인터페이스가 상태를 "요구"하고 싶다면, 추상 프로퍼티로 계약만 걸고 저장은 구현에 맡긴다(2.3의 백킹 프로퍼티 패턴). "인터페이스에 mutable 상태를 넣는 트릭"(예: 인스턴스를 키로 한 전역 맵)은 스레드 안전성, 메모리 누수, 캡슐화 파괴를 부르는 안티패턴이므로 피한다. 인터페이스가 상태를 못 담는 것은 한계가 아니라 다중 상속을 안전하게 만드는 설계 결정임을 기억하자(1.2).

### 10.5 인터페이스 멤버는 final이 될 수 없다

클래스 멤버는 기본이 `final`이고 `open`으로 열어야 하지만([[24 - 상속과 오버라이딩과 초기화 순서]]), 인터페이스 멤버는 정반대다. 인터페이스 멤버는 본질적으로 `open`(오버라이드 가능)이며, `final`로 못 박을 수 없다.

```kotlin
interface Foo {
    fun bar() = 1
    // final fun baz() = 2      // 컴파일 에러: Modifier 'final' is not applicable to 'member function of interface'
}
```

인터페이스는 "구현이 이래야 한다"는 계약이므로, 구현 클래스가 기본 구현을 오버라이드할 자유를 원천적으로 막는 것은 인터페이스의 존재 이유와 어긋난다. "오버라이드를 막고 싶은 공통 로직"이 있다면 그것은 인터페이스가 아니라 (구현 클래스의 `final` 멤버나 확장 함수로) 다른 자리에 있어야 한다.

---

인터페이스라는 장치의 전모를 한 줄기로 회수해 보자. 이 장을 여는 질문은 "인터페이스가 프로퍼티를 선언하면서도 왜 상태를 못 담는가"였다. 답은 백킹 필드의 부재였다—인터페이스 프로퍼티는 저장 슬롯 없는 접근자 추상이고(M37), 값은 언제나 구현 클래스의 필드로 내려간다. 이 하나의 사실이 나머지를 설명한다. 상태가 없으니 필드 충돌이 없고, 필드 충돌이 없으니 다중 상속이 안전하며, 남는 메서드 충돌만 `super<T>`로 명시적으로 푼다. 기본 구현은 상태 없이 행동만 조립하는 골격이고, 추상 클래스와 갈리는 지점은 정확히 "상태와 생성자를 갖느냐"다. `fun interface`는 코틀린이 SAM 변환을 아무 데나 허용하지 않고 명목적으로 표시된 곳에만 여는 신중함의 산물이며, 마커 인터페이스는 멤버 없이도 타입 시스템에 사는 태그다. 인터페이스가 상태를 못 담는다는 제약은 결핍이 아니라, "능력을 겹겹이 조립하되 그 조립이 언제나 안전하도록" 언어가 그은 경계선이다. 상태는 클래스에, 계약과 능력은 인터페이스에—이 분업이 코틀린 타입 시스템의 골격을 지탱한다.

## 핵심 요약

- **인터페이스 프로퍼티는 백킹 필드가 없는 접근자 추상이다.** `val x = 초기값`(초기화자), `get() = field`, `lateinit`, 위임 프로퍼티는 모두 저장 슬롯을 요구하므로 인터페이스에서 컴파일 에러다. 담을 수 있는 것은 추상 프로퍼티(계약)와 다른 멤버로부터 파생하는 계산 게터뿐이다. (M37)
- **인터페이스가 상태를 강제하고 싶으면 추상 프로퍼티로 계약만 걸고, 실제 저장은 구현 클래스의 필드가 담당한다(백킹 프로퍼티 패턴).** 같은 계약을 어떤 구현은 실제 필드로, 어떤 구현은 계산으로 만족할 수 있고, 인터페이스는 그 차이에 관여하지 않는다. (M37)
- **클래스는 하나만, 인터페이스는 여럿 상속되는 비대칭은 상태의 유무에서 나온다.** 상태 있는 클래스의 다중 상속은 필드 충돌·초기화 난제를 낳지만, 상태 없는 인터페이스는 필드 충돌이 불가능하고 메서드 충돌만 `super<T>`로 명시 해소하면 된다.
- **두 인터페이스가 같은 시그니처의 기본 구현을 제공하면 컴파일러가 명시적 오버라이드를 강제한다.** 심지어 한쪽이 추상, 다른 쪽이 기본 구현이어도 마찬가지다. `super<A>.foo()`/`super<B>.foo()`로 어느 상위 구현을 부를지 지목한다.
- **인터페이스 기본 구현은 JVM 백엔드에서 DefaultImpls 정적 클래스 또는 JVM default 메서드로 컴파일되며, 그 전략은 컴파일러의 jvm-default 모드에 달렸다.** 어느 전략이든 인터페이스에 인스턴스 필드는 생기지 않는다—컴파일 형태가 바뀌어도 상태 없음은 불변이다.
- **인터페이스 대 추상 클래스의 선택 기준은 상태와 생성자다.** 공유 상태·초기화 로직이 필요하면 추상 클래스, 순수한 능력의 계약이거나 여러 축을 겸비해야 하면 인터페이스다. 코틀린 인터페이스가 기본 구현을 담을 수 있어 자바보다 인터페이스만으로 해결되는 범위가 넓다.
- **코틀린 람다는 아무 SAM 인터페이스에나 꽂히지 않고, `fun interface`(또는 자바에서 정의된 SAM 인터페이스)에만 변환된다.** 함수 타입이 이미 일급이므로 무분별한 SAM 변환이 오버로드 모호성을 부르는 것을 막는 의도적 제한이다.
- **`fun interface`는 추상 메서드가 정확히 하나여야 하며, 추상 프로퍼티는 두 번째 추상 멤버가 되어 금지된다.** 기본 구현 메서드·계산 프로퍼티는 함께 담을 수 있다. "함수 하나"에 명목적 정체성·부가 멤버가 필요하면 함수 타입 대신 `fun interface`를 쓴다.
- **인터페이스 멤버는 기본이 `open`이며 `final`로 못 박을 수 없고, 가시성은 public 또는 private만 허용된다(protected·internal 불가).** private 멤버는 반드시 본문을 가진 헬퍼여야 한다.
- **인터페이스 프로퍼티는 커스텀 게터일 수 있어 스마트 캐스트가 대체로 막히고(M13 참조), 파생 게터는 초기화 순서에 취약하다(M47 참조).** 지역 변수에 값을 고정하면 스마트 캐스트가 풀리고, 파생 프로퍼티는 초기화 완료 후에만 접근해야 안전하다.
- **마커 인터페이스는 멤버 없이 타입 시스템에 사는 태그로, 컴파일 타임 검사가 가능한 반면, 마커 애노테이션은 런타임 메타데이터다.** 시그니처로 능력을 강제하려면 인터페이스, 부가 데이터를 실으려면 애노테이션을 쓴다.
- **인터페이스는 변성 선언의 자연스러운 자리다.** 상태가 없어 "생산만 하는 타입(`out T`)", "소비만 하는 타입(`in T`)"을 순수하게 표현할 수 있고, 표준 라이브러리의 `Iterator<out T>`·`Comparable<in T>`가 그 증거다. 같은 제네릭 인터페이스를 다른 타입 인자로 두 번 구현하는 것은 타입 소거 때문에 금지된다(M19 참조).

## 연결 노트

- [[24 - 상속과 오버라이딩과 초기화 순서]] — 클래스 단일 상속과 초기화 순서(M47)를 다룬 앞 장. 인터페이스 파생 프로퍼티의 초기화 함정(10.1)과 `super<T>` 문법이 여기서 이어진다.
- [[22 - 프로퍼티와 백킹 필드]] — 프로퍼티가 곧 접근자 추상(M35)이라는 일반론의 소유 장. 인터페이스 프로퍼티에 백킹 필드가 없다는 이 장의 핵심(M37)이 그 원리의 극단적 사례다.
- [[26 - 가시성 한정자]] — 인터페이스 멤버가 public/private만 허용되는(protected·internal 불가) 이유의 배경. internal의 모듈 단위 가시성(M44)을 소유한다.
- [[13 - 함수 타입과 람다와 함수 참조]] — `fun interface`의 SAM 변환이 대체하는 일급 함수 타입의 소유 장. 람다 문법과 `it`(M42)이 여기서 정의된다.
- [[30 - sealed 클래스와 대수적 데이터 타입]] — `sealed interface`로 인터페이스 계층을 봉인해 `when`을 완전하게 만드는 장(8.4의 심화). 합타입/ADT 표현을 소유한다.
- [[28 - object와 companion - 싱글턴과 동반 객체]] — 인터페이스의 상수를 담는 컴패니언 객체(3.4)와 익명 객체로 인터페이스를 구현하는 object 표현식의 토대. object가 인터페이스를 구현할 수 있다는 사실(M24)을 소유한다.
- [[32 - 클래스 위임]] — 인터페이스 구현을 통째로 다른 객체에 위임하는 `class C(b: Base) : Base by b` 문법의 소유 장. 상속 대신 조합으로 인터페이스를 만족하는 길이다.
- [[33 - 제네릭 1 - 타입 파라미터와 변성]] — 인터페이스가 주무대인 변성(`out`/`in`, M20)과 타입 파라미터 상한(M45)의 소유 장. 9절의 `Producer<out T>`/`Consumer<in T>`가 여기서 완결된다.
- [[35 - 확장 함수와 프로퍼티]] — 인터페이스에 "멤버처럼 보이는" 기능을 정적 디스패치로 덧붙이는 확장(M14~M16). 인터페이스 멤버(동적 디스패치)와의 대조가 중요하다.
- [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]] — 인터페이스가 만드는 타입 계층이 놓이는 전체 지형. 마커 인터페이스가 태그로 사는 타입 시스템의 골격을 소유한다.
