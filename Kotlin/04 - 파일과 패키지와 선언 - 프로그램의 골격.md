**이 장이 답하는 질문:**

- `.kt` 파일 하나는 도대체 무엇으로 컴파일되는가? 클래스 안에 넣지 않은 최상위 함수는 어디에 담기는가?
- 패키지 이름은 디렉터리 구조와 **반드시** 일치해야 하는가? 일치시키지 않으면 무슨 일이 벌어지는가?
- `import`는 정확히 무엇을 "가져오는가"? import가 없으면 그 심볼을 정말 못 쓰는가, 아니면 이름이 길어질 뿐인가?
- 아무 import도 없이 `println`, `listOf`, `TODO()`가 곧바로 되는 이유는 무엇인가?
- `main`은 반드시 `args: Array<String>`를 받아야 하는가? 파일 여러 개에 `main`이 있으면 어느 것이 진입점인가?
- 최상위에 `println("hi")` 같은 실행문을 그냥 흩뿌릴 수 있는가? 왜 되거나 안 되는가?
- 파일 위쪽 함수가 아직 정의를 만나지 않은 아래쪽 함수를 부를 수 있는가? 그렇다면 최상위 프로퍼티 초기화도 순서와 무관한가?
- 최상위 선언에 `private`을 붙이면 그 범위는 파일인가 패키지인가 모듈인가?

[[03 - 렉시컬 구조와 세미콜론 추론]]에서 우리는 문자열이 어떻게 토큰으로 쪼개지고, 줄바꿈이 어떤 조건에서 문장을 끝내는지—즉 컴파일러가 소스를 "읽어 들이는" 가장 낮은 층을 보았다. 토큰이 모이면 선언(declaration)이 되고, 선언이 모이면 파일이 되며, 파일이 모이면 프로그램이 된다. 이 장은 바로 그 다음 층, **하나의 `.kt` 파일이 어떤 골격으로 조직되고 그 골격이 컴파일 후 어떤 실체로 바뀌는가**를 다룬다. 렉서가 넘겨준 토큰 스트림을 받아 파서가 세우는 최상위 구조—파일 애노테이션, 패키지 헤더, import 목록, 그리고 최상위 선언들—이 이 장의 무대다.

이 장은 "무엇을 선언할 수 있는가"의 문법을 세세히 파헤치지 않는다. 함수의 인자·vararg·기본값은 [[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]가, 클래스와 생성자는 [[21 - 클래스와 생성자]]가, 프로퍼티의 백킹 필드는 [[22 - 프로퍼티와 백킹 필드]]가, 가시성 한정자의 전체 규칙은 [[26 - 가시성 한정자]]가 소유한다. 여기서는 그런 선언들이 **파일과 패키지라는 그릇 안에 어떻게 담기고, 어떻게 서로를 찾고, 어떻게 실체(JVM 백엔드에서는 `.class` 파일)로 번역되는가**만을 본다. Kotlin은 JVM/Native/JS/Wasm 네 개의 타깃을 가진 언어이므로(M2), "파일이 클래스가 된다" 같은 서술은 대부분 JVM 백엔드에 한정된 이야기임을 처음부터 못 박아 둔다. 다른 타깃에서는 같은 소스가 전혀 다른 실체로 번역된다.

논증의 궤적은 이렇다. 먼저 파일이라는 단위를 해부하고(그것이 왜 클래스보다 큰 그릇인지), 패키지가 이름공간을 어떻게 나누는지, import가 실제로 무슨 일을 하고 무슨 일을 하지 않는지, 최상위 선언이 왜 실행문이 아니라 선언만 허용하는지를 본다. 그다음 JVM 백엔드에서 파일이 어떻게 `*Kt` 클래스로 접히는지, `main`이 어떻게 진입점이 되는지, 그리고 마지막으로 "선언 순서는 무관하다"는 명제가 이름 해소에서는 참이지만 **초기화 순서에서는 거짓**이라는, 이 장에서 가장 미묘한 함정으로 마무리한다.

## 1. 파일이라는 단위 — 클래스보다 큰 그릇

### 1.1 하나의 `.kt` 파일의 형식적 골격

Kotlin 파일의 최상위 문법은 놀랄 만큼 단순하다. 문법 규칙(EBNF의 요지)으로 적으면 다음 순서다.

```text
kotlinFile
  : shebangLine?        // #!/usr/bin/env kotlin  (스크립트 실행용, 선택)
    fileAnnotation*      // @file:JvmName("...") 등, 파일 전체에 붙는 애노테이션
    packageHeader?       // package com.example.zoo
    importList           // import ... (0개 이상)
    topLevelObject*      // 함수/프로퍼티/클래스/객체/인터페이스/타입별칭 (0개 이상)
```

이 순서는 **강제**다. 파일 애노테이션은 패키지 선언보다 앞에, 패키지 선언은 import보다 앞에, import는 모든 최상위 선언보다 앞에 와야 한다. 이 배치를 어기면 파서가 즉시 진단(오류)을 낸다.

```kotlin
// Zoo.kt
@file:JvmName("ZooUtils")   // (1) 파일 애노테이션 — 반드시 맨 위

package com.example.zoo      // (2) 패키지 헤더 — 애노테이션 다음

import kotlin.math.sqrt      // (3) import 목록
import kotlin.math.PI

const val LEGS_PER_SPIDER = 8 // (4) 최상위 선언들 (순서 무관)

fun circleArea(r: Double): Double = PI * r * r

class Animal(val name: String)
```

Kotlin 파일이 담을 수 있는 것은 실행문이 아니라 **선언**이다(1.5절에서 이 제약을 정면으로 다룬다). 담을 수 있는 최상위 선언은 다음과 같다.

- 최상위 함수 (`fun`)
- 최상위 프로퍼티 (`val`/`var`, [[11 - 변수와 초기화 - val과 const와 lateinit]])
- 클래스·인터페이스·객체 (`class`/`interface`/`object`/`enum`/`sealed`/`annotation`)
- 타입 별칭 (`typealias`, 전통적으로 **최상위 선언**으로 쓰이며 클래스·인터페이스 안 중첩은 Kotlin 2.2+에서 가능 — 4.4절, [[36 - 타입 별칭과 인라인 value class]])

### 1.2 Java와의 결정적 차이 — 파일 이름과 클래스 이름의 분리

Java를 거쳐 온 개발자가 가장 먼저 놀라는 지점이다. Java에서 파일과 클래스는 사실상 한 몸이다.

```java
// Java: 파일 이름 = public 클래스 이름 (강제)
// 파일 Animal.java 는 반드시 public class Animal 을 담아야 한다.
// public 최상위 클래스는 파일당 정확히 하나.
public class Animal {
    public static final int LEGS = 4;
    public static void describe() { /* ... */ }
}
```

Kotlin은 이 결합을 완전히 끊는다.

```kotlin
// 파일 이름은 zoo_helpers.kt 인데
// 그 안에 public 클래스가 몇 개든 들어갈 수 있고, 파일 이름과 무관하다.
class Cat(val name: String)      // public 클래스 1
class Dog(val name: String)      // public 클래스 2
class Fish(val name: String)     // public 클래스 3
fun greetAll() { /* ... */ }     // 어떤 클래스에도 속하지 않는 함수
val zooName = "Central Zoo"      // 어떤 클래스에도 속하지 않는 프로퍼티
```

여기서 파일은 **클래스보다 큰 그릇**이다. 클래스는 파일 안에 담기는 여러 종류의 최상위 선언 중 하나일 뿐이고, 함수와 프로퍼티는 클래스에 속하지 **않고도** 파일에 직접 매달릴 수 있다. 이 "최상위 함수/프로퍼티"라는 개념이 Kotlin 파일 조직의 핵심이며, 뒤에서 볼 파일-클래스 컴파일(2절, 5절)의 존재 이유이기도 하다.

> **역사 메모**: Java가 "파일=public 클래스"를 강제한 것은 컴파일러가 어떤 소스가 어떤 클래스를 정의하는지 파일 경로만으로 알 수 있게 하려는 초기 설계였다. Kotlin은 IR 기반 다단계 컴파일([[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]])로 전체 모듈을 함께 리졸브하기 때문에 이 제약이 필요 없다. 대신 "최상위 함수를 어디에 넣을 것인가"라는 새 문제가 생겼고, 그 답이 `*Kt` 파일-클래스다.

### 1.3 `.kt`와 `.kts` — 선언 파일과 스크립트 파일

Kotlin에는 두 종류의 소스 확장자가 있다.

| 확장자 | 이름 | 최상위에 허용되는 것 | 진입 방식 |
|--------|------|-----------------------|-----------|
| `.kt` | 컴파일 단위 | **선언만** (함수·프로퍼티·클래스…) | `main` 함수 |
| `.kts` | 스크립트 | **선언 + 실행문** (문장을 그대로) | 파일 자체가 위→아래로 실행 |

```kotlin
// hello.kts (스크립트) — 최상위에 실행문을 그대로 쓸 수 있다
val name = "world"
println("Hello, $name")   // 이 줄이 최상위에서 곧바로 실행됨
```

```kotlin
// hello.kt (일반) — 최상위 실행문 금지
val name = "world"
println("Hello, $name")   // 컴파일 에러: expecting a top-level declaration
```

이 장의 나머지 전부는 `.kt`(일반 컴파일 단위)를 다룬다. `.kts`는 빌드 스크립트(Gradle Kotlin DSL — [[37 - 타입 안전 빌더와 DSL]])와 즉석 실행에 쓰이는 특수 형태로, 컴파일러가 파일 전체를 암묵적인 스크립트 클래스의 본문으로 감싸 위에서 아래로 실행한다. 즉 스크립트에서 "최상위 실행문"이 되는 것은 사실 감싸인 클래스의 초기화 블록에 들어가기 때문이다. 일반 `.kt`에는 그런 암묵 래핑이 없으므로 실행문을 둘 곳이 없다.

## 2. 패키지 — 이름공간이라는 좌표계

### 2.1 패키지는 이름을 나누는 논리적 좌표다

`package` 선언은 그 파일의 모든 최상위 선언에 **정규화된 이름(fully qualified name, FQN)** 의 접두사를 붙인다.

```kotlin
// 파일: geometry/Circle.kt
package com.example.geometry

class Circle(val radius: Double)   // FQN: com.example.geometry.Circle
fun area(c: Circle) = 3.14159 * c.radius * c.radius  // FQN: com.example.geometry.area
```

이제 `Circle`의 정규 이름은 `com.example.geometry.Circle`이다. 서로 다른 패키지에 같은 단순 이름(simple name)의 선언이 있어도 FQN이 다르므로 충돌하지 않는다. 이것이 패키지의 존재 이유 전부다: **이름 충돌을 막는 좌표계.**

정규 이름은 언제나 직접 쓸 수 있다. import가 없어도 아래는 유효하다.

```kotlin
package com.example.zoo

fun buildCage(): com.example.geometry.Circle {   // FQN 직접 사용 — import 불필요
    return com.example.geometry.Circle(5.0)
}
```

여기서 이미 중요한 사실이 드러난다: **import는 "그 심볼을 쓸 수 있게 해주는" 열쇠가 아니다.** FQN을 쓰면 import 없이도 언제나 쓸 수 있다. import는 단지 "매번 긴 FQN을 쓰지 않아도 단순 이름으로 부르게 해주는 편의"일 뿐이다(3절에서 정면으로 다룬다).

### 2.2 패키지 이름은 디렉터리 구조와 일치하지 않아도 된다

Java에서 패키지 `com.example.geometry`는 파일이 반드시 `com/example/geometry/` 디렉터리에 있어야 하고, 컴파일러가 이를 강제한다. **Kotlin은 강제하지 않는다.**

```kotlin
// 파일 위치: src/whatever/random/place/Shapes.kt  (디렉터리와 무관)
package com.example.geometry   // 컴파일러는 아무 불평도 하지 않는다

class Triangle
```

컴파일러 관점에서 소스 파일의 **물리적 경로**와 선언된 **논리적 패키지**는 독립이다. 컴파일러는 `package` 선언만 보고 FQN을 정하고, JVM 백엔드에서는 그 FQN에 따라 `.class` 파일을 출력 디렉터리의 `com/example/geometry/`에 쓴다—소스가 어디 있었든 상관없이.

그렇다면 왜 다들 디렉터리와 패키지를 맞추는가? 순전히 **관례와 도구 편의** 때문이다. IDE는 디렉터리와 패키지가 어긋나면 경고를 띄우고 "이동/리팩터링"을 제안한다. 사람이 파일을 찾기 쉽고, 대규모 프로젝트에서 구조가 예측 가능해진다. 하지만 이것은 **언어의 규칙이 아니라 사회적 규칙**이다.

> **명세 정밀**: "패키지와 디렉터리가 일치하지 않아도 된다"는 것은 언어 명세 수준의 사실이지만, 여기엔 조건이 붙는다. (1) 빌드 도구가 특정 소스 루트 규약을 강제할 수 있다(예: Gradle 소스셋 경계). (2) `main`을 찾을 때 빌드 설정이 FQN 기반 `mainClass`를 지정하므로, 패키지를 바꾸면 진입점 FQN도 바뀐다(6절). 언어는 자유롭지만 생태계는 관례를 기대한다.

### 2.3 루트(기본) 패키지 — 이름 없는 좌표

`package` 선언을 아예 생략하면 그 파일의 선언들은 **루트 패키지(root package)**, 즉 빈 이름의 패키지에 들어간다.

```kotlin
// 파일에 package 선언이 없음 → 루트 패키지
class Sandbox   // FQN: 그냥 Sandbox (접두사 없음)
fun quickTest() = 42
```

루트 패키지는 즉석 실습이나 아주 작은 프로그램엔 편하지만, 실무에서는 피하는 것이 정석이다. 특히 JVM 백엔드에서는 오래된 Java의 "무명 패키지(unnamed package)" 제약이 그대로 걸린다: **이름 있는 패키지에서 루트 패키지의 선언을 `import`로 끌어올 수 없다.** 즉 루트 패키지에 둔 클래스는 다른 패키지의 코드가 접근하기 곤란해진다. 그래서 라이브러리나 다중 모듈 프로젝트는 항상 이름 있는 패키지를 쓴다.

### 2.4 하나의 패키지는 여러 파일에 흩어질 수 있다

패키지는 파일 경계를 넘는다. 같은 `package` 선언을 가진 파일이 몇 개든, 그것들은 논리적으로 하나의 이름공간을 이룬다.

```kotlin
// 파일 A: Cats.kt
package com.example.zoo
class Cat

// 파일 B: Dogs.kt
package com.example.zoo
class Dog
fun cat(): Cat = Cat()   // 같은 패키지의 Cat을 import 없이 사용
```

같은 패키지 안에서는 서로의 최상위 선언을 **import 없이** 단순 이름으로 부른다. 파일 B의 `cat()`이 파일 A의 `Cat`을 그냥 쓸 수 있는 이유가 이것이다. 이 성질은 뒤에서 볼 `private`의 파일 스코프(7절)와 대비하면 더 선명해진다: **패키지는 파일을 가로질러 이름을 공유하지만, `private`은 파일에 갇힌다.**

같은 패키지·여러 파일에 **같은 단순 이름의 클래스나 최상위 프로퍼티**가 둘 있으면 재선언(redeclaration) 오류다. 다만 최상위 **함수**는 시그니처가 다르면 오버로딩으로 공존할 수 있다.

```kotlin
// Sound1.kt
package com.example.zoo
fun makeSound(cat: Cat) = "meow"

// Sound2.kt
package com.example.zoo
fun makeSound(dog: Dog) = "woof"   // OK: 오버로드 (파라미터 타입이 다름)
// fun makeSound(cat: Cat) = "..." // 두 번째 것이 있었다면 컴파일 에러: conflicting overloads
```

## 3. import — 무엇을 가져오고, 무엇을 가져오지 않는가

### 3.1 import의 본질은 "이름 축약"이지 "심볼 반입"이 아니다

앞서 못 박았듯 import는 없는 것을 만들어 주지 않는다. import는 **현재 파일 안에서 FQN을 단순 이름으로 쓰게 해주는 렉시컬 축약**이다.

```kotlin
package com.example.zoo

import com.example.geometry.Circle   // "이 파일에서 Circle 이라 쓰면 com.example.geometry.Circle 이다"

fun cage() = Circle(5.0)   // 이제 단순 이름으로
```

import가 하는 일을 정확히 개념화하면 이렇다. 컴파일러가 이름 `Circle`을 해소할 때 후보 집합을 만드는데, import는 그 후보 집합에 특정 FQN을 하나 얹는 지시다. 형식적으로 파일 $F$의 이름 해소 스코프를 후보들의 합집합으로 보면 대략

$$\text{Scope}(F) = \text{현재 패키지} \cup \text{기본 import} \cup \bigcup_{i} \text{명시 import}_i$$

이고, 사용처에서 단순 이름 하나에 후보가 유일하면 그 선언으로 확정, 둘 이상이면 모호성(ambiguity) 오류다. 즉 import는 스코프를 넓히는 연산이지 코드를 실행하거나 무언가를 로드하는 것이 아니다.

> **흔한 오해**: "import 문이 실행되어 클래스를 메모리에 올린다"는 상상은 Python의 `import`(모듈 실행)를 Kotlin에 투영한 것이다. Kotlin/Java의 import는 **컴파일 타임에만 존재하고 바이트코드에 흔적을 남기지 않는다.** 클래스 로딩은 실제로 그 타입을 처음 쓸 때 JVM이 지연 수행하며, import 여부와 무관하다. `import`를 지우고 FQN을 전부 손으로 적어도 실행 시맨틱은 한 치도 다르지 않다.

### 3.2 무엇을 import할 수 있는가 — 클래스만이 아니다

Java에서는 `import`가 타입을 가져오고 정적 멤버는 `import static`이 따로 필요하다. Kotlin에는 그런 구분이 없다. `import`는 이름을 가진 거의 모든 것을 가져온다.

```kotlin
import com.example.geometry.Circle        // 클래스
import com.example.geometry.area          // 최상위 함수
import com.example.geometry.PI_APPROX     // 최상위 프로퍼티
import com.example.zoo.Color.RED          // enum 상수 ([[29 - enum 클래스]])
import com.example.zoo.Registry.register  // object의 멤버 함수 ([[28 - object와 companion - 싱글턴과 동반 객체]])
import com.example.zoo.Animal.Companion.create // companion 멤버
```

특히 **확장 함수·확장 프로퍼티**는 import가 실질적으로 필요하다. 확장은 클래스에 실제 멤버를 넣지 않고 정적으로 해소되기 때문에([[35 - 확장 함수와 프로퍼티]], M14), 그 확장 선언이 **현재 파일의 스코프에 들어와 있어야만** 호출할 수 있다.

```kotlin
// 파일 StringExt.kt
package com.example.util
fun String.shout(): String = uppercase() + "!"

// 파일 Main.kt
package com.example.app
import com.example.util.shout   // 이 import가 없으면 shout()을 호출조차 못 한다

fun demo() = "hello".shout()    // => "HELLO!"
```

이것이 확장을 클래스 멤버와 구분 짓는 실용적 특징이다. 멤버 함수는 타입만 보이면 어디서든 부를 수 있지만, 확장은 "그 이름이 스코프에 들어와 있는지"가 호출 가능성을 결정한다.

### 3.3 별칭 `as` — 이름 충돌의 해법

같은 단순 이름을 가진 두 선언을 한 파일에서 모두 쓰고 싶으면 `as`로 하나에 새 이름을 준다.

```kotlin
import com.example.graphics.Color         // 그래픽스의 Color
import com.example.paint.Color as PaintColor  // 페인트의 Color를 PaintColor로 별칭

fun mix(a: Color, b: PaintColor) { /* 둘을 한 파일에서 명확히 구분 */ }
```

`as`는 그 파일 안에서만 유효한 지역적 새 이름이다. 원래 선언의 FQN이나 다른 파일에서의 이름을 바꾸지 않는다. 별칭은 이름 충돌 해소 외에도, 긴 이름을 짧게 하거나 문맥에 맞는 어휘를 부여할 때 쓴다. 다만 남용하면 코드를 읽는 사람이 실제 타입을 추적하기 어려워지므로 절제가 필요하다.

> **명세 정밀**: `import ... as X`로 부여한 별칭 `X`는 타입 별칭(`typealias`, [[36 - 타입 별칭과 인라인 value class]])과 다르다. import 별칭은 **한 파일 안의 지역 이름**일 뿐 새 타입도 아니고 다른 파일에서 보이지도 않는다. `typealias`는 최상위 선언이라 패키지 전체·import를 통해 다른 파일에서도 쓰인다. 둘 다 "새 타입은 아니다"라는 점(M38)은 같지만 가시 범위가 정반대다.

### 3.4 스타 임포트 `*` — 편의와 위험

`import 패키지.*`는 그 패키지(또는 객체·enum 등)의 **보이는 최상위 멤버 전부**를 단순 이름으로 끌어온다.

```kotlin
import com.example.geometry.*   // geometry 패키지의 모든 것
import kotlin.math.*            // sqrt, sin, PI, abs, ... 전부
```

스타 임포트에는 세 가지 규칙이 있다.

1. **별칭 불가**: `import foo.* as bar`는 불가능하다. `*`는 여러 이름을 한꺼번에 가져오므로 하나의 새 이름을 줄 수 없다.
2. **명시 import가 스타보다 강하다**: 이름이 겹치면 명시적으로 적은 import가 스타 임포트를 이긴다.
3. **모호성은 "사용할 때" 판정된다**: 서로 다른 두 스타 임포트가 같은 단순 이름을 제공해도, 그 이름을 실제로 쓰기 전에는 오류가 아니다. 쓰는 순간에만 모호성 오류가 난다.

```kotlin
import com.example.graphics.*   // 여기에 Color 가 있고
import com.example.paint.*      // 여기에도 Color 가 있다

// 아무 데서도 Color 를 안 쓰면 아무 오류 없음.
fun useColor() {
    val c: Color = TODO()   // 컴파일 에러: overload resolution ambiguity (여기서 비로소 충돌)
}
```

우선순위 규칙(명시 > 스타) 덕분에, 위 상황도 한쪽을 명시 import하면 즉시 해소된다.

```kotlin
import com.example.graphics.*
import com.example.paint.*
import com.example.graphics.Color   // 명시 import가 스타를 이긴다 → Color = graphics.Color 로 확정
```

> **성능 주의**: 스타 임포트는 런타임 성능에 아무 영향이 없다(import는 컴파일 타임 전용이므로). "스타 임포트가 무거운 클래스를 다 로드해서 느리다"는 것은 오해다. 스타 임포트의 진짜 비용은 **가독성**이다: 어떤 심볼이 어느 패키지에서 왔는지 파일만 봐선 알기 어렵고, 새 버전의 라이브러리가 같은 이름을 추가하면 조용히 모호성 오류가 생길 수 있다. 그래서 많은 팀이 스타 임포트를 스타일 규칙으로 제한한다.

### 3.5 기본 import — 왜 `println`과 `listOf`는 그냥 되는가

새 파일을 열어 import를 한 줄도 쓰지 않아도 `println`, `listOf`, `mapOf`, `require`, `TODO()`, `Int`, `String`이 곧바로 된다. 이는 컴파일러가 **모든 Kotlin 파일에 암묵적으로 삽입하는 기본 import** 덕분이다. 어느 타깃에서든 공통으로 들어오는 패키지는 다음과 같다.

```text
kotlin.*             // Int, String, Any, Unit, Nothing, TODO, require, run, let ...
kotlin.annotation.*  // @Target, @Retention 등 메타 애노테이션
kotlin.collections.* // List, Set, Map, listOf, mutableListOf, mapOf ...
kotlin.comparisons.* // compareBy, maxOf, minOf, naturalOrder ...
kotlin.io.*          // println, print, readLine ...
kotlin.ranges.*      // .. 연산으로 만들어지는 IntRange 등, until, downTo, step
kotlin.sequences.*   // Sequence, generateSequence, sequenceOf ...
kotlin.text.*        // String 확장들, StringBuilder, Regex, trimIndent ...
```

그리고 **타깃마다 추가되는** 기본 import가 있다(M2를 상기하라 — Kotlin은 멀티타깃 언어다).

| 타깃(백엔드) | 추가 기본 import |
|--------------|-------------------|
| JVM | `java.lang.*`, `kotlin.jvm.*` |
| JS | `kotlin.js.*` |

이 표가 왜 중요한가. JVM 백엔드에서 `Thread`, `Runnable`, `System`을 import 없이 쓸 수 있는 것은 `java.lang.*`가 기본 import이기 때문인데, **이것은 JVM 전용 편의**다. 같은 코드를 Kotlin/JS나 Kotlin/Native로 컴파일하면 `java.lang.*`는 존재하지 않으므로 `Thread` 같은 이름은 해소되지 않는다. 멀티플랫폼 공통 코드([[46 - 멀티플랫폼과 진화와 어두운 구석]])에서 `java.*`에 의존하면 안 되는 근본 이유가 여기 있다. "Kotlin에서 되니까 어디서나 되겠지"라는 감각은 JVM 편향에서 온 착각이다.

## 4. 최상위 선언 — 클래스 없이 사는 함수와 값

### 4.1 최상위 함수와 프로퍼티라는 발상

객체지향의 관습에서는 모든 함수가 어떤 클래스의 메서드여야 한다. Java에서 유틸리티 함수는 `Math.sqrt`, `Collections.sort`처럼 억지로 클래스에 담기고(그래서 `Math`는 인스턴스가 무의미한 정적 메서드 창고가 된다), 그 클래스는 오직 "함수를 담기 위한" 껍데기다.

Kotlin은 함수와 프로퍼티를 **일급 최상위 선언**으로 승격시켜 이 껍데기를 없앤다.

```kotlin
package com.example.mathx

const val GOLDEN_RATIO = 1.618033988749895   // 최상위 상수
val defaultPrecision = 6                       // 최상위 프로퍼티

fun clamp(x: Double, lo: Double, hi: Double): Double =   // 최상위 함수
    maxOf(lo, minOf(hi, x))
```

`clamp`는 어떤 클래스에도 속하지 않는다. 호출부는 `com.example.mathx.clamp(...)` 혹은 import 후 `clamp(...)`로 쓴다. 인위적인 `MathUtils` 클래스가 필요 없다. 이것이 Kotlin 코드가 Java보다 "가벼워" 보이는 큰 이유 중 하나다.

그러나 최상위 함수/프로퍼티는 개념적으로만 클래스 밖에 있을 뿐, **JVM 백엔드에서는 반드시 어떤 클래스에 담겨야 한다**(JVM에는 클래스 밖 메서드가 존재할 수 없으므로). 그 담는 클래스가 바로 파일-클래스(`*Kt`)이며, 5절에서 해부한다. 이 지점이 "소스의 개념 모델"과 "JVM 백엔드의 실체"가 갈라지는 대표적 장소다.

### 4.2 최상위 프로퍼티의 종류와 컴파일 형태(개념)

최상위에는 세 종류의 프로퍼티가 온다.

```kotlin
const val MAX_LEGS = 8      // 컴파일 상수 (M36)
val zooName = "Central"     // 읽기 전용 프로퍼티 (재대입 불가, M3)
var visitorCount = 0        // 가변 프로퍼티
```

이들의 차이는 [[11 - 변수와 초기화 - val과 const와 lateinit]]가 소유하지만, "파일에 담긴다"는 관점에서 지금 짚을 것은 이렇다.

- `const val`은 **컴파일 상수**다(M36). 값이 컴파일 타임에 확정되고, JVM 백엔드에서는 사용처에 값이 그대로 인라인된다. 원시 타입 또는 `String`만, 리터럴 또는 다른 `const`의 조합으로만 가능하다.
- `val`은 재대입 불가일 뿐 불변 객체를 뜻하지 않는다(M3). JVM 백엔드에서 최상위 `val`은 파일-클래스의 `private static` 필드와 `public static` 게터로 컴파일되는 것이 일반적이다.
- `var`은 게터와 세터를 모두 가진다.

여기서 M3(val은 불변 객체를 만든다는 오해)와 M36(const와 val이 같다는 오해)이 스치듯 등장한다. 이 장은 그것들을 정면 교정하지 않고 [[11 - 변수와 초기화 - val과 const와 lateinit]]에 위임하되, "최상위 `const`는 사용처에 인라인되므로 라이브러리 API에서 값을 바꾸면 재컴파일 없이는 반영 안 되는 함정이 있다"는 파일-관점의 한 조각만 남긴다.

### 4.3 최상위 선언끼리의 접근과 오버로딩

같은 패키지의 최상위 선언들은 서로를 자유롭게 부른다(2.4절). 최상위 함수는 파라미터가 다르면 오버로딩되고, 컴파일러의 오버로드 해소 규칙([[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]])에 따라 가장 구체적인 것이 선택된다.

```kotlin
package com.example.zoo

fun feed(a: Cat) = "fish"
fun feed(a: Dog) = "bone"
fun feed(a: Any) = "generic food"

fun test() {
    feed(Cat("x"))     // => "fish"  (가장 구체적인 Cat 오버로드)
    feed(42)           // => "generic food"  (Any 오버로드로 폴백)
}
```

### 4.4 타입 별칭의 위치 — 최상위와 (2.2+) 클래스 안

작은 세부지만 파일 조직 관점에서 기억할 것: `typealias`는 전통적으로 **최상위 선언**으로 쓰였다. Kotlin 2.2에서 클래스·인터페이스 안에 두는 **중첩 타입 별칭(nested type alias)** 이 도입되어(2.2 베타 → 2.3 안정화) 그 제약이 일부 풀렸지만, **함수 본문 안의 지역(local) 타입 별칭은 여전히 허용되지 않는다.**

```kotlin
typealias StringMap = Map<String, String>   // OK (최상위)

class Registry {
    typealias Handler = (String) -> Unit     // OK (클래스 안 중첩, Kotlin 2.2+)
}

fun demo() {
    // typealias LocalMap = Map<Int, Int>    // 컴파일 에러: local type aliases are not supported
}
```

지역(함수 안) 타입 별칭이 여전히 막힌 것은 타입 별칭이 순수한 이름 축약(M38, 새 타입 아님)이며, 함수 스코프의 일시적 이름으로 새 타입 이름을 도입하는 것을 언어가 지원하지 않기 때문이다(중첩 타입 별칭은 바깥 클래스의 타입 파라미터를 포획하지 못한다는 제약도 있다). 자세한 의미론은 [[36 - 타입 별칭과 인라인 value class]].

## 5. 파일-클래스 — JVM 백엔드에서 파일이 접히는 방식

### 5.1 `Utils.kt`는 `UtilsKt` 클래스가 된다

이제 이 장의 기술적 심장부다. JVM에는 "클래스 밖 함수"라는 개념이 없다. 그런데 Kotlin은 최상위 함수/프로퍼티를 허용한다(4절). 이 모순을 컴파일러는 **파일-클래스(file class, 흔히 파일 파사드facade라 부름)** 로 해결한다: 하나의 `.kt` 파일 안의 모든 최상위 함수와 프로퍼티를 하나의 합성 클래스에 정적 멤버로 모아 넣는다.

```kotlin
// 파일: Utils.kt
package com.example.util

fun greet(name: String) = "Hello, $name"
val version = "1.0"
```

JVM 백엔드에서 이것은 대략 다음 Java에 대응한다.

```java
// 개념적으로 생성되는 파일-클래스 (디컴파일 결과의 요지)
package com.example.util;

public final class UtilsKt {          // 파일 이름 Utils → UtilsKt
    private static final String version = "1.0";

    public static String greet(String name) {
        return "Hello, " + name;
    }
    public static String getVersion() {   // val 은 게터로
        return version;
    }
}
```

클래스 이름 규칙은 "파일 이름에서 확장자를 떼고, 첫 글자를 대문자로 만든 뒤 `Kt`를 붙인다"이다. `Utils.kt` → `UtilsKt`, `main.kt` → `MainKt`. (파일 이름에 식별자로 쓸 수 없는 문자가 있으면 컴파일러가 정규화하지만, 그 세부는 백엔드 구현 재량이므로 여기서 규칙을 단정하지 않는다.)

호출부에서 Kotlin으로는 `greet("world")`처럼 클래스를 의식하지 않지만, **Java에서 이 함수를 부를 때는** 파일-클래스 이름을 알아야 한다: `UtilsKt.greet("world")`. 이 상호운용 세부는 [[45 - Java 상호운용]]가 소유하지만, "왜 Java에서 Kotlin 최상위 함수가 `XxxKt.foo`로 보이는가"의 답이 바로 파일-클래스다.

> **명세 정밀**: 파일-클래스는 **JVM 백엔드에 한정된 산물**이다. Kotlin/Native, Kotlin/JS, Kotlin/Wasm은 각자의 방식으로 최상위 선언을 표현하며 `*Kt` 클래스라는 개념 자체가 없다. "`.kt`는 `*Kt.class`가 된다"는 문장은 언제나 "JVM 백엔드에서"라는 한정을 달고 읽어야 한다(M2).

### 5.2 `@file:JvmName` — 파일-클래스 이름 바꾸기

`UtilsKt`라는 자동 이름이 마음에 안 들거나, Java 사용자에게 더 자연스러운 이름을 주고 싶으면 파일 애노테이션으로 바꾼다.

```kotlin
@file:JvmName("StringUtils")   // 반드시 package 선언보다 위

package com.example.util

fun capitalizeFirst(s: String): String = s.replaceFirstChar { it.uppercase() }
```

이제 Java에서는 `StringUtils.capitalizeFirst(...)`로 부른다. `@file:` 접두사는 "이 애노테이션은 파일 전체(즉 파일-클래스)를 대상으로 한다"는 사용지점 타깃 표기이며([[44 - 애노테이션과 리플렉션]]에서 사용지점 타깃 전반을 다룬다), `JvmName`은 이름 그대로 JVM에서의 이름을 바꾼다. 이 애노테이션은 반드시 파일 최상단(패키지 선언보다 앞)에 놓여야 하는데, 1.1절에서 본 파일 골격 순서 규칙 때문이다.

### 5.3 `@file:JvmMultifileClass` — 여러 파일을 한 클래스로 합치기

표준 라이브러리를 디컴파일하면 `kotlin.collections.CollectionsKt` 하나에 엄청나게 많은 함수가 들어 있는 것을 볼 수 있다. 그런데 stdlib 소스는 그 함수들을 여러 파일에 나눠 둔다. 어떻게 여러 파일이 하나의 파사드 클래스에 모였을까? `@JvmName` + `@JvmMultifileClass` 조합이다.

```kotlin
// 파일: Collections1.kt
@file:JvmName("CollectionsKt")
@file:JvmMultifileClass
package com.example.col
fun <T> List<T>.second(): T = this[1]

// 파일: Collections2.kt
@file:JvmName("CollectionsKt")
@file:JvmMultifileClass
package com.example.col
fun <T> List<T>.third(): T = this[2]
```

두 파일이 **같은 `@JvmName("CollectionsKt")`** 를 선언하고 **둘 다 `@JvmMultifileClass`** 를 붙이면, JVM 백엔드는 이들을 하나의 파사드 클래스 `CollectionsKt`로 병합한다(내부적으로는 파일별 부분 클래스를 만들고 파사드가 그것들로 위임하는 형태). 이렇게 하면 소스는 논리적으로 잘게 쪼개면서도 사용자에게는 하나의 API 표면(`CollectionsKt.second`, `CollectionsKt.third`)을 제공한다.

`@JvmMultifileClass` 없이 두 파일이 같은 `@JvmName`만 가지면, 두 파일이 같은 클래스 이름을 놓고 충돌하여 오류가 난다. 병합 의도를 명시하는 애노테이션이 바로 `@JvmMultifileClass`인 것이다.

```text
소스 관점                       JVM 백엔드 산물
──────────────                  ─────────────────
Collections1.kt ─┐
                 ├─ @JvmMultifileClass ─▶  CollectionsKt (파사드)
Collections2.kt ─┘                          ├─ 위임 → Collections1__CollectionsKt (부분)
                                            └─ 위임 → Collections2__CollectionsKt (부분)
```

이 역시 순수 JVM 백엔드 이야기다. 다른 타깃에는 파사드 병합이라는 개념이 없다.

### 5.4 최상위 `val`을 필드로 노출하기 — `@JvmField`

기본적으로 최상위 `val`은 파일-클래스의 게터(`getX()`)로 노출된다. Java 쪽에서 필드처럼 직접 접근하고 싶으면 `@JvmField`를 붙여 게터 없이 `public static` 필드로 만들 수 있다(단 `const`가 아닌 경우에 의미가 있고, 몇 가지 제약이 있다). 이 최적화·상호운용 세부는 [[22 - 프로퍼티와 백킹 필드]]와 [[45 - Java 상호운용]]가 소유하므로 여기서는 "파일-클래스가 프로퍼티를 어떻게 정적 멤버로 노출하는지는 애노테이션으로 조율된다"는 것만 기억한다.

## 6. 진입점 `main` — 프로그램은 어디서 시작하는가

### 6.1 `main`의 여러 시그니처

Kotlin 프로그램의 진입점은 `main` 함수다. 허용되는 시그니처는 네 가지다.

```kotlin
fun main() { }                              // (1) 인자 없음 (Kotlin 1.3+)
fun main(args: Array<String>) { }           // (2) 명령행 인자
suspend fun main() { }                       // (3) 코루틴 진입점 (1.3+)
suspend fun main(args: Array<String>) { }    // (4) 코루틴 + 인자
```

역사적으로 원래는 `fun main(args: Array<String>)` 하나만 있었다. 인자를 쓰지 않는 프로그램조차 `args`를 억지로 선언해야 했는데, Kotlin 1.3에서 **인자 없는 `main`** 이 추가되어 상용구가 줄었다. 같은 버전에서 `suspend fun main`도 도입되어, 별도의 `runBlocking` 래핑 없이 최상위에서 코루틴을 시작할 수 있게 됐다([[42 - suspend와 코루틴 - 언어 수준의 중단]]).

```kotlin
fun main() {
    println("Hello, Kotlin")   // args 없이 간결하게
}
```

### 6.2 `main`은 최상위 함수다 — JVM 진입 규약과의 다리

`main`도 결국 최상위 함수이므로, JVM 백엔드에서는 그 파일의 파일-클래스에 정적 메서드로 담긴다. `Main.kt`에 `fun main()`을 두면 `MainKt` 클래스가 생기고 그 안에 진입 메서드가 들어간다.

JVM 런처는 `public static void main(String[] args)` 시그니처를 요구한다. Kotlin이 `fun main()`(인자 없음)을 썼을 때 컴파일러는 **인자를 무시하는 브리지 `main(String[])`** 를 파일-클래스에 생성해 JVM 규약을 만족시킨다. `suspend fun main`의 경우 컴파일러가 코루틴을 구동하는 래퍼를 갖춘 `main(String[])`을 생성한다. 즉 어떤 시그니처를 쓰든 최종적으로 JVM이 인식하는 표준 진입점이 만들어진다.

```text
소스: Main.kt 에 fun main()
   │  (JVM 백엔드)
   ▼
클래스 MainKt
   ├─ static void main(String[] args)   ← JVM 런처가 부르는 진입 메서드
   │     └─ 내부에서 인자 무시하고 실제 main() 호출
   └─ ...
```

실행 시 `mainClass`로 지정하는 것은 이 파일-클래스의 FQN(`com.example.MainKt`)이다. 그래서 패키지를 바꾸면 진입점 FQN도 바뀐다(2.2절의 경고가 여기서 회수된다).

### 6.3 `main`이 여러 개면 — 진입점은 언어가 아니라 빌드가 정한다

한 프로젝트에 `main` 함수가 여러 파일에 있을 수 있다. 언어는 이를 금지하지 않는다. 각 파일-클래스가 각자의 진입 메서드를 가질 뿐이다. **어느 것을 실제 진입점으로 삼을지는 언어가 아니라 빌드/실행 설정이 정한다**(예: Gradle `application` 플러그인의 `mainClass`, 또는 실행할 때 지정하는 클래스 FQN).

```kotlin
// AppA.kt (com.example)
fun main() = println("A")   // 파일-클래스 com.example.AppAKt

// AppB.kt (com.example)
fun main() = println("B")   // 파일-클래스 com.example.AppBKt
```

두 진입점이 공존한다. 실행 시 `com.example.AppAKt`를 지정하면 A가, `com.example.AppBKt`를 지정하면 B가 시작된다. 이것은 "프로그램에 진입점은 하나뿐"이라는 감각을 가진 사람에게 반직관적일 수 있는데, Kotlin에서 `main`은 특별한 언어 키워드가 아니라 **관례적 이름과 시그니처를 가진 평범한 최상위 함수**이고, 그중 무엇을 시작점으로 삼을지는 외부 도구의 몫이라는 것이 정확한 그림이다.

> **흔한 오해**: "`main`은 예약어이고 프로그램당 하나만 있을 수 있다"는 것은 오해다. `main`은 키워드가 아니며([[03 - 렉시컬 구조와 세미콜론 추론]]의 키워드 3분류 어디에도 없다), 이름·시그니처가 규약에 맞는 최상위 함수를 컴파일러/런처가 진입점 후보로 인식할 뿐이다. `fun main()`이라는 이름의 함수를 클래스 안 메서드로 두면 그것은 진입점이 아니라 그냥 메서드다.

### 6.4 최상위 실행문이 없다는 것의 의미

여기서 1.5절의 "최상위 실행문 금지"가 왜 자연스러운지 완성된다. 스크립트 언어(Python, 그리고 Kotlin의 `.kts`)는 파일 자체가 실행 흐름이라 최상위에 문장을 늘어놓는다. 그러나 `.kt`는 **선언들의 모음**일 뿐 실행 흐름이 아니다. 실행은 명시적으로 지정된 `main`에서 시작한다. 그래서 `.kt` 최상위에 `println(...)`을 두면 "실행할 곳이 없는 문장"이 되어 컴파일러가 거부한다. "어디서 시작하는가"를 `main`으로 못 박은 대가로, 선언의 배치 순서로부터 실행 순서를 분리할 수 있게 됐다(7~8절의 주제).

## 7. 최상위 가시성 — public 기본과 파일 스코프 private

### 7.1 최상위 선언의 기본 가시성은 public

명시하지 않으면 최상위 선언은 `public`이다. Kotlin은 Java의 "package-private 기본"을 버리고 **public 기본**을 택했다(그 철학적 배경은 [[26 - 가시성 한정자]]가 다룬다).

```kotlin
package com.example.zoo

fun openToAll() { }          // public (기본)
public fun alsoPublic() { }  // 명시해도 같음 (보통 생략)
```

최상위에 올 수 있는 가시성 한정자는 세 가지다: `public`, `internal`, `private`. **`protected`는 최상위에서 허용되지 않는다** — `protected`는 "하위 클래스에서 보임"을 뜻하는데 최상위 선언에는 상속 관계라는 개념이 없기 때문이다.

```kotlin
// protected fun cannotBeTopLevel() { }   // 컴파일 에러: modifier 'protected' is not applicable to 'top level declaration'
```

### 7.2 `private` 최상위 선언 = 파일 스코프

이 장에서 가장 중요한 가시성 사실이다. 최상위 선언에 `private`을 붙이면 그 범위는 **선언된 파일 전체**다. 클래스도 함수도 프로퍼티도 아닌, **파일**이 경계가 된다.

```kotlin
// 파일: Internal.kt
package com.example.zoo

private fun secretHelper() = 42          // 이 파일 안에서만 보임
private val secretKey = "abc"            // 이 파일 안에서만 보임

fun publicApi() = secretHelper() + secretKey.length  // 같은 파일 → OK
```

```kotlin
// 파일: Other.kt (같은 패키지 com.example.zoo)
package com.example.zoo

fun tryToUse() {
    // secretHelper()   // 컴파일 에러: cannot access 'secretHelper': it is private in file
}
```

여기서 2.4절과의 대비가 선명해진다. **같은 패키지의 다른 파일은 서로의 public 최상위 선언을 import 없이 쓸 수 있지만, `private` 최상위 선언은 파일을 넘지 못한다.** 즉 패키지는 파일을 가로지르는 이름공간이지만, `private`은 파일에 갇힌 지역성이다. 이 "파일 스코프 private"은 Java에는 대응물이 없다(Java의 최소 가시성은 package-private이라 파일보다 패키지에 묶인다).

### 7.3 `internal` — 모듈 스코프 (파일도 패키지도 아니다)

`internal`은 **모듈(module)** 단위 가시성이다(M44). 모듈은 함께 컴파일되는 단위—Gradle 모듈, Maven 프로젝트, IntelliJ 모듈, 하나의 컴파일러 호출 등—를 뜻한다.

```kotlin
package com.example.zoo

internal fun forThisModuleOnly() { }   // 같은 모듈 어디서나, 다른 모듈에선 안 보임
```

`internal`을 Java의 package-private과 혼동하기 쉽지만(M44), 둘은 경계가 다르다. Java의 package-private은 **패키지** 단위이고, Kotlin의 `internal`은 **모듈** 단위다. 모듈은 여러 패키지를 포함할 수 있으므로 `internal`이 훨씬 넓다. 이 M44는 [[26 - 가시성 한정자]]가 정면 교정하고, JVM 백엔드에서 `internal`이 이름 맹글링(name mangling)으로 표현되는 상호운용 세부는 [[45 - Java 상호운용]]가 소유한다. 이 장에서는 "최상위 선언의 가시성 경계는 각각 파일(private)·모듈(internal)·전역(public)으로 서로 다른 크기다"라는 지형만 확정한다.

| 한정자 | 최상위 선언의 가시 범위 | 크기 감각 |
|--------|--------------------------|-----------|
| `private` | 선언된 **파일** 안 | 가장 좁음 |
| `internal` | 같은 **모듈** 안 (M44) | 중간 |
| `public`(기본) | 어디서나 | 가장 넓음 |
| `protected` | (최상위에는 불가) | — |

## 8. 선언 순서 — 이름은 순서 무관, 초기화는 순서 의존

### 8.1 이름 해소는 순서를 따지지 않는다 (전방 참조)

Kotlin은 C처럼 "위에서 아래로 읽으며 정의를 만나야 부를 수 있다"는 언어가 아니다. 파일 위쪽의 선언이 아래쪽의 선언을 **자유롭게 앞서 참조(forward reference)** 할 수 있다.

```kotlin
fun start() = helper()    // 아래에 정의된 helper 를 위에서 호출 — OK

fun helper() = "done"     // 정의가 뒤에 있어도 문제없음
```

컴파일러는 파일(사실은 모듈 전체)의 모든 선언을 먼저 수집해 이름 심볼 테이블을 만든 뒤, 본문을 해소한다. 그래서 최상위 함수·클래스·프로퍼티는 **텍스트 순서와 무관하게 서로를 본다.** 클래스도 마찬가지다.

```kotlin
class Zoo(val star: Animal)   // Animal 이 아래에 정의됨 — OK

class Animal(val name: String)
```

이 성질은 "선언 순서는 아무 상관 없다"는 인상을 준다. 함수 호출·타입 참조에 관한 한 그 인상은 옳다. 그러나 여기엔 결정적 예외가 하나 있고, 그것이 이 장의 마지막이자 가장 미묘한 함정이다.

### 8.2 초기화는 텍스트 순서를 따른다 (예외)

**최상위 프로퍼티의 초기화 코드는 파일에 적힌 순서대로 실행된다.** 이름 해소는 순서 무관이지만, "초기화 표현식이 실제로 평가되는 시점"은 순서 의존이다. JVM 백엔드에서는 최상위 프로퍼티 초기화가 파일-클래스의 정적 초기화 블록(`<clinit>`)에 텍스트 순서대로 놓이기 때문이다.

여기서 함정이 나온다. 위쪽 프로퍼티의 초기화 식이 아직 초기화되지 않은 아래쪽 프로퍼티를 읽으면, 그 값은 **아직 초기화 전의 기본값**(참조는 `null`, 수치는 0)이다.

```kotlin
// 파일: Config.kt
val derived = base.uppercase()   // (1) 먼저 실행 — 이 시점에 base 는 아직 초기화 안 됨!
val base = "hello"               // (2) 나중에 실행

fun main() {
    println(base)      // => hello
    println(derived)   // 위쪽 초기화 때 base 가 아직 null 이었으므로
                       // 런타임 예외 (NPE) 또는 예기치 않은 값
}
```

여기서 `derived`의 초기화가 먼저 도는데, 그 순간 `base`는 아직 "hello"가 대입되기 전이라 참조 타입의 기본값 `null` 상태다. 그 `null`에 `uppercase()`를 부르면 런타임 예외가 난다. 이름 해소는 성공했지만(컴파일 통과), **초기화 순서**가 논리를 깬 것이다.

이 함정을 지역/멤버 초기화와 연결하면 [[24 - 상속과 오버라이딩과 초기화 순서]]의 M47(생성자에서 오버라이드 멤버 호출)과 같은 뿌리를 가진다는 걸 알 수 있다: **"선언되었다"와 "초기화되었다"는 다른 사건이고, 코드는 종종 전자를 후자로 착각한다.** 순서를 바꾸거나(`base`를 위로), 지연 초기화(`by lazy`, [[23 - 위임 프로퍼티]])를 쓰거나, 함수/게터로 계산을 미루면 해결된다.

```kotlin
// 해법 A: 순서 바로잡기
val base = "hello"
val derived = base.uppercase()   // 이제 base 가 먼저 초기화됨 → 안전

// 해법 B: 지연 계산
val base2 = "hello"
val derived2 by lazy { base2.uppercase() }   // 첫 접근 시 계산 → 순서 무관하게 안전
```

### 8.3 파일이 여러 개일 때 — 초기화 순서는 "클래스 로딩" 순서

한 파일 안의 최상위 프로퍼티 초기화 순서는 텍스트 순서로 명확하다. 그러나 **서로 다른 파일**의 최상위 프로퍼티 사이의 초기화 순서는 언어가 전역적으로 정해 주지 않는다. JVM 백엔드에서 각 파일-클래스는 별개의 클래스이고, 클래스의 정적 초기화는 **그 클래스가 처음 사용되는 시점에 지연(lazy) 수행**되기 때문이다. 즉 파일 A의 프로퍼티와 파일 B의 프로퍼티 중 무엇이 먼저 초기화되는지는 실행 중 어느 클래스가 먼저 로드되느냐에 달렸다.

```kotlin
// FileA.kt
val a = "A-init".also { println("init A") }

// FileB.kt
val b = "B-init".also { println("init B") }

// Main.kt
fun main() {
    println(b)   // B 를 먼저 건드리면 "init B" 가 먼저
    println(a)   // 그다음 "init A"
}
```

`main`이 `a`를 먼저 참조하면 파일-클래스 A가 먼저 로드되어 A가 먼저 초기화되고, `b`를 먼저 참조하면 B가 먼저 초기화된다. 따라서 **여러 파일의 최상위 프로퍼티가 서로의 초기화에 의존하도록 설계하면 안 된다.** 초기화 순서에 의존하는 전역 상태는 파일 경계를 넘는 순간 예측 불가에 가까워진다. 실무의 정석은 그런 순서 의존을 아예 없애는 것—필요하면 명시적 초기화 함수를 만들거나, 지연 초기화로 "쓸 때 준비되도록" 뒤집는 것이다.

> **성능 주의**: 최상위 프로퍼티는 편리하지만, JVM 백엔드에서 각 파일-클래스의 `<clinit>`은 그 클래스가 처음 쓰일 때 한 번 돈다. 무거운 초기화(파일 읽기·네트워크·큰 컬렉션 구성)를 최상위 `val` 초기화 식에 두면 그 클래스가 처음 로드될 때 그 비용이 갑자기 발생하고, 여러 최상위 값이 얽히면 초기화 순서 함정까지 겹친다. "지연이 필요한 무거운 값은 `by lazy`로"가 실용적 원칙이다.

### 8.4 순서 무관 vs 순서 의존을 한 표로

| 대상 | 텍스트 순서에 의존? | 이유 |
|------|----------------------|------|
| 함수 호출 (전방 참조) | 아니오 | 심볼 테이블을 먼저 구축 후 해소 |
| 타입 참조 (클래스가 아래에) | 아니오 | 위와 동일 |
| **같은 파일의 프로퍼티 초기화** | **예** | `<clinit>`에 텍스트 순서대로 배치(JVM) |
| 서로 다른 파일의 프로퍼티 초기화 | (정의 안 됨) | 클래스 로딩(지연) 순서에 좌우 |

이 표가 8절의 결론이다. "선언 순서는 무관하다"는 명제는 **이름 차원에서 참, 초기화 차원에서 거짓**이다. 이 구분을 놓치면 "컴파일은 되는데 값이 이상한" 유령 버그를 만난다.

## 9. 멀티타깃에서의 파일과 패키지 — 골격은 같고 실체는 다르다

### 9.1 소스 골격은 타깃 불변, 컴파일 산물은 타깃 가변

지금까지 본 파일 골격(파일 애노테이션 → 패키지 → import → 최상위 선언), 패키지 이름공간, import 규칙, 최상위 선언의 가시성, 선언 순서 규칙—이것들은 **어느 타깃에서든 동일한 소스 수준 규칙**이다. Kotlin/JVM이든 Kotlin/Native든 Kotlin/JS든, `.kt` 파일 하나를 쓰는 방식은 같다.

달라지는 것은 **컴파일 산물의 실체**다. 이 장에서 여러 번 한정했듯이:

- 파일-클래스(`*Kt`), `@JvmName`, `@JvmMultifileClass`, `@JvmField`, `main`의 `static void main(String[])` 브리지 — 모두 **JVM 백엔드 한정** 개념이다.
- `java.lang.*` 기본 import — **JVM 백엔드 한정**.
- 최상위 프로퍼티가 `<clinit>`에서 초기화된다는 것 — **JVM 백엔드의 실행 모델**. 다른 백엔드는 최상위 값의 초기화를 다른 메커니즘으로 처리한다.

이 분리를 계속 의식하는 것이 M2(Kotlin=JVM 언어라는 오해)에 빠지지 않는 방법이다. 파일과 패키지는 **논리적 골격**이고, `*Kt` 클래스니 정적 초기화니 하는 것은 그 골격을 특정 기계(JVM)에 앉힐 때 생기는 **번역의 흔적**이다.

### 9.2 `expect`/`actual`과 패키지 — 같은 좌표, 다른 구현

멀티플랫폼([[46 - 멀티플랫폼과 진화와 어두운 구석]])에서 공통 소스셋은 `expect` 선언을, 각 플랫폼 소스셋은 `actual` 구현을 둔다. 이때 결정적 규칙 하나가 이 장의 주제와 직접 맞닿는다: **`expect`와 그에 대응하는 `actual`은 같은 패키지·같은 이름을 가져야 한다.**

```kotlin
// 공통 소스셋: platform.kt
package com.example.platform
expect fun currentTimeMillis(): Long

// JVM 소스셋: platform.jvm.kt
package com.example.platform      // 같은 패키지
actual fun currentTimeMillis(): Long = System.currentTimeMillis()

// JS 소스셋: platform.js.kt
package com.example.platform      // 같은 패키지
actual fun currentTimeMillis(): Long = kotlin.js.Date.now().toLong()
```

패키지가 곧 이 매칭의 좌표계 역할을 한다. 공통 코드가 `com.example.platform.currentTimeMillis()`를 부르면, 컴파일러는 대상 플랫폼의 같은 좌표(같은 패키지·이름)에 있는 `actual`을 찾아 연결한다. 여기서 2절에서 세운 "패키지는 이름을 나누는 좌표"라는 개념이 멀티플랫폼의 뼈대로 확장된다. 파일은 소스셋에 따라 여러 벌 존재하지만, 패키지 좌표가 그것들을 하나의 논리적 선언으로 묶는다.

### 9.3 파일 조직이 API 설계다

마지막으로, 파일과 패키지를 나누는 방식은 단순한 "정리 정돈"이 아니라 **API 설계 그 자체**임을 짚는다. 최상위 함수를 어느 파일에 두느냐가 JVM에서 어느 파일-클래스에 담기는지를 정하고(Java 사용자에게 보이는 이름), 어느 패키지에 두느냐가 import 경로와 FQN을 정하며, `private`/`internal`/`public`을 어디에 붙이느냐가 노출 표면을 정한다. `@JvmMultifileClass`로 여러 파일을 한 API 표면으로 묶는 stdlib의 기법(5.3절)은 "소스는 잘게, API는 하나로"라는 설계 의도의 구현이다. 즉 이 장의 지식은 문법 세부가 아니라, **읽는 사람과 부르는 사람이 만나는 경계면을 어떻게 그릴 것인가**에 관한 것이다.

---

우리는 하나의 `.kt` 파일이 실행문의 나열이 아니라 선언들의 그릇임을 보았고, 그 그릇이 클래스보다 커서 함수와 프로퍼티를 클래스 없이도 품을 수 있음을 보았다. 패키지는 그 선언들에 좌표를 부여해 이름 충돌을 막고, 디렉터리와 반드시 일치하지 않으며(관례일 뿐), 파일을 가로질러 이름을 공유한다. import는 없는 것을 만들어 주는 열쇠가 아니라 FQN을 짧게 부르게 해주는 축약이며, `println`이 그냥 되는 것은 컴파일러가 삽입하는 기본 import 덕분—그중 `java.lang.*`는 JVM 백엔드 한정이라는 사실이 Kotlin이 멀티타깃 언어(M2)임을 조용히 상기시킨다. JVM 백엔드에서 파일은 `*Kt` 클래스로 접히고, `main`은 그 클래스의 정적 진입 메서드가 되며, 어느 `main`을 시작점으로 삼을지는 언어가 아니라 빌드가 정한다. 최상위 가시성은 파일(private)·모듈(internal)·전역(public)이라는 서로 다른 크기의 경계를 만들고, 선언 순서는 이름 해소에서는 무의미하지만 초기화에서는 결정적이다—"선언되었다"와 "초기화되었다"를 혼동하는 순간 컴파일은 통과하되 값이 어긋나는 유령을 만난다. 이 골격 위에서, 다음 장부터 우리는 그 안에 담기는 것들—타입 시스템의 지형([[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]])—을 하나씩 채워 나간다.

## 핵심 요약

- **`.kt` 파일은 실행문이 아니라 선언(함수·프로퍼티·클래스·타입별칭)의 그릇이며, 클래스보다 큰 단위다.** 파일 이름과 클래스 이름이 강제로 묶인 Java와 달리, 한 파일에 public 클래스를 여러 개 두거나 어떤 클래스에도 속하지 않는 최상위 함수/프로퍼티를 둘 수 있다.
- **파일 골격의 순서는 강제다: 파일 애노테이션(`@file:`) → 패키지 헤더 → import 목록 → 최상위 선언.** `@file:JvmName`이 패키지 선언 위에 와야 하는 이유가 이 순서 규칙이다.
- **패키지는 이름을 나누는 좌표계이고, 디렉터리 구조와 일치하지 않아도 언어는 허용한다.** 일치는 관례·도구 편의일 뿐 언어 규칙이 아니다. 같은 패키지는 파일을 가로질러 이름을 import 없이 공유한다.
- **import는 심볼을 "반입"하지 않는다. FQN을 단순 이름으로 쓰게 해주는 컴파일 타임 축약일 뿐이며, 바이트코드에 흔적을 남기지 않는다.** FQN을 직접 쓰면 import 없이도 언제나 접근 가능하다. 명시 import는 스타 임포트를 이기고, 스타 임포트의 모호성은 실제 사용 지점에서만 판정된다.
- **`println`·`listOf`가 import 없이 되는 것은 기본 import(`kotlin.*` 등) 덕분이며, `java.lang.*` 기본 import는 JVM 백엔드에 한정된다(M2 관련).** 공통 코드에서 `java.*`에 의존하면 다른 타깃에서 깨진다.
- **JVM 백엔드에서 하나의 `.kt` 파일의 최상위 함수·프로퍼티는 `<파일이름>Kt` 파일-클래스에 정적 멤버로 접힌다.** `@JvmName`으로 이름을 바꾸고 `@JvmMultifileClass`로 여러 파일을 한 파사드로 병합할 수 있다. 이 개념 전부가 JVM 백엔드 한정이다.
- **`main`은 예약어가 아니라 규약적 이름·시그니처를 가진 평범한 최상위 함수다.** `fun main()`/`fun main(args)`/`suspend fun main(...)` 네 형태가 있고, 진입점 지정은 언어가 아니라 빌드/실행 설정(`mainClass` FQN)이 한다. `main`이 여러 개여도 무방하다.
- **`.kt` 최상위에 실행문을 둘 수 없는 것은 실행 흐름이 `main`으로 명시되기 때문이다.** 스크립트(`.kts`)만이 파일 전체를 암묵적으로 실행 본문으로 감싼다.
- **최상위 선언의 기본 가시성은 public이고, `protected`는 최상위에 쓸 수 없다.** `private` 최상위 선언은 **파일 스코프**(파일이 경계), `internal`은 **모듈 스코프**(패키지 아님, M44)로, 셋은 서로 다른 크기의 경계를 만든다.
- **선언 순서는 이름 해소에서는 무의미하지만(전방 참조 가능) 초기화에서는 결정적이다.** 같은 파일의 최상위 프로퍼티는 텍스트 순서대로 초기화되므로, 위쪽 초기화 식이 아래쪽 프로퍼티를 읽으면 아직 초기화 전의 기본값(`null`/0)을 만난다—컴파일은 통과하되 런타임이 어긋난다.
- **서로 다른 파일의 최상위 프로퍼티 초기화 순서는 정의되지 않는다.** JVM 백엔드에서 각 파일-클래스의 정적 초기화가 지연 클래스 로딩 시점에 돌기 때문. 파일을 넘는 초기화 의존은 설계에서 배제하고 `by lazy`나 명시적 초기화로 뒤집어야 한다.
- **파일·패키지·가시성을 나누는 방식은 정리 정돈이 아니라 API 설계다.** 어느 파일·패키지·가시성에 두느냐가 FQN, Java에서 보이는 이름, 노출 표면을 결정한다. 멀티플랫폼의 `expect`/`actual`도 같은 패키지 좌표로 매칭된다.
