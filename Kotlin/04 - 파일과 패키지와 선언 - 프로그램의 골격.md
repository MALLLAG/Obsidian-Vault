[[03 - 렉시컬 구조와 세미콜론 추론]]에서는 컴파일러가 소스를 읽어 들이는 가장 낮은 층을 살펴보았다. 문자열이 토큰으로 나뉘는 과정과, 줄바꿈이 어떤 조건에서 문장을 끝내는지가 그 내용이었다. 토큰이 모이면 선언(declaration)이 되고, 선언이 모이면 파일이 되며, 파일이 모이면 프로그램이 된다.

이 장에서는 그다음 층을 다룬다. 즉 **하나의 `.kt` 파일이 어떤 구조로 짜이고, 그 구조가 컴파일된 뒤 어떤 결과물로 바뀌는가**를 살펴본다. 렉서가 넘겨준 토큰 스트림으로 파서가 만드는 최상위 구조, 곧 파일 애노테이션과 패키지 헤더, import 목록, 최상위 선언이 이 장의 대상이다.

개별 선언의 문법(함수의 인자나 클래스와 생성자, 백킹 필드, 가시성 규칙)은 각 장에서 따로 다루고, 이 장에서는 선언이 파일과 패키지 안에 담기고 서로를 찾고 결과물(JVM 백엔드에서는 `.class` 파일)로 번역되는 과정만 본다. Kotlin의 타깃은 JVM, Native, JS, Wasm 네 가지이므로, "파일이 클래스가 된다" 같은 설명은 대부분 JVM 백엔드에만 해당한다.

## 1. 파일이라는 단위: 클래스보다 큰 단위

### 1.1 `.kt` 파일 하나의 형식적 구조

Kotlin 파일의 최상위 문법은 매우 단순하다. 문법 규칙(EBNF의 요지)으로 적으면 다음과 같은 순서가 된다.

```text
kotlinFile
  : shebangLine?        // #!/usr/bin/env kotlin  (스크립트 실행용, 선택)
    fileAnnotation*      // @file:JvmName("...") 등, 파일 전체에 붙는 애노테이션
    packageHeader?       // package com.example.zoo
    importList           // import ... (0개 이상)
    topLevelObject*      // 함수/프로퍼티/클래스/객체/인터페이스/타입별칭 (0개 이상)
```

이 순서는 **반드시 지켜야 한다**. 파일 애노테이션은 패키지 선언보다 앞에, 패키지 선언은 import보다 앞에, import는 모든 최상위 선언보다 앞에 와야 한다. 이 배치를 어기면 파서가 곧바로 진단(오류)을 낸다.

```kotlin
// Zoo.kt
@file:JvmName("ZooUtils")   // (1) 파일 애노테이션 — 반드시 맨 위

package com.example.zoo      // (2) 패키지 헤더 — 애노테이션 다음

import kotlin.math.sqrt      // (3) import 목록
import kotlin.math.PI

const val LEGS_PER_SPIDER = 8 // (4) 최상위 선언들 (순서 무관)

fun circleArea(r: Double): Double = PI * r * r

class Animal(val name: String)
```

Kotlin 파일에 담을 수 있는 것은 실행문이 아니라 **선언**이다(이 제약은 1.3절과 6.4절에서 자세히 다룬다). 최상위에 둘 수 있는 선언은 다음과 같다.

- 최상위 함수 (`fun`)
- 최상위 프로퍼티 (`val`/`var`, [[11 - 변수와 초기화 - val과 const와 lateinit]])
- 클래스, 인터페이스, 객체 (`class`/`interface`/`object`/`enum`/`sealed`/`annotation`)
- 타입 별칭 (`typealias`). 전통적으로 **최상위 선언**으로 쓰였고, Kotlin 2.2부터는 클래스나 인터페이스 안에 중첩해 선언할 수도 있다(4.4절, [[36 - 타입 별칭과 인라인 value class]]).

### 1.2 Java와의 결정적 차이: 파일 이름과 클래스 이름의 분리

Java를 쓰다 온 개발자가 가장 먼저 놀라는 부분이다. Java에서는 파일과 클래스가 사실상 하나로 묶여 있다.

```java
// Java: 파일 이름 = public 클래스 이름 (강제)
// 파일 Animal.java 는 반드시 public class Animal 을 담아야 한다.
// public 최상위 클래스는 파일당 정확히 하나.
public class Animal {
    public static final int LEGS = 4;
    public static void describe() { /* ... */ }
}
```

Kotlin은 이 결합을 완전히 없앴다.

```kotlin
// 파일 이름은 zoo_helpers.kt 인데
// 그 안에 public 클래스가 몇 개든 들어갈 수 있고, 파일 이름과 무관하다.
class Cat(val name: String)      // public 클래스 1
class Dog(val name: String)      // public 클래스 2
class Fish(val name: String)     // public 클래스 3
fun greetAll() { /* ... */ }     // 어떤 클래스에도 속하지 않는 함수
val zooName = "Central Zoo"      // 어떤 클래스에도 속하지 않는 프로퍼티
```

Kotlin에서 파일은 **클래스보다 큰 단위**이다. 클래스는 파일에 담기는 여러 최상위 선언 중 하나일 뿐이고, 함수와 프로퍼티는 클래스에 속하지 **않고도** 파일에 직접 선언할 수 있다. 이 "최상위 함수와 최상위 프로퍼티"가 Kotlin 파일 구성의 핵심이며, 뒤에서 볼 파일 클래스 컴파일(4절, 5절)이 필요한 이유이기도 하다.

> [!info] 역사 메모
> Java가 "파일=public 클래스"를 강제한 것은, 컴파일러가 파일 경로만 보고도 어떤 소스가 어떤 클래스를 정의하는지 알 수 있게 하려던 초기 설계 때문이었다. Kotlin은 IR 기반 다단계 컴파일([[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]])로 모듈 전체를 함께 리졸브하므로 이 제약이 필요 없다. 대신 "최상위 함수를 어디에 넣을 것인가"라는 새 문제가 생겼고, 그 답이 `*Kt` 파일 클래스이다.

### 1.3 `.kt`와 `.kts`: 선언 파일과 스크립트 파일

Kotlin 소스 파일의 확장자는 두 가지이다.

| 확장자 | 이름 | 최상위에 허용되는 것 | 진입 방식 |
|--------|------|-----------------------|-----------|
| `.kt` | 컴파일 단위 | **선언만** (함수·프로퍼티·클래스…) | `main` 함수 |
| `.kts` | 스크립트 | **선언 + 실행문** (문장을 그대로) | 파일 자체가 위→아래로 실행 |

```kotlin
// hello.kts (스크립트) — 최상위에 실행문을 그대로 쓸 수 있다
val name = "world"
println("Hello, $name")   // 이 줄이 최상위에서 곧바로 실행됨
```

```kotlin
// hello.kt (일반) — 최상위 실행문 금지
val name = "world"
println("Hello, $name")   // 컴파일 에러: expecting a top-level declaration
```

이 장의 나머지는 모두 일반 컴파일 단위인 `.kt`를 다룬다. `.kts`는 빌드 스크립트(Gradle Kotlin DSL, [[37 - 타입 안전 빌더와 DSL]])나 즉석 실행에 쓰는 특수한 형태이다. 컴파일러는 파일 전체를 암묵적인 스크립트 클래스의 본문으로 감싸고, 위에서 아래로 실행한다.

즉 스크립트에서 최상위 실행문이 동작하는 것은, 그 문장이 실제로는 감싼 클래스의 초기화 블록에 들어가기 때문이다. 일반 `.kt` 파일에는 이런 암묵적인 감싸기가 없으므로 실행문을 둘 곳이 없다.

## 2. 패키지: 이름을 구분하는 이름공간

### 2.1 패키지는 이름을 나누는 논리적 단위이다

`package` 선언은 파일 안의 모든 최상위 선언에 **정규화된 이름**(fully qualified name, FQN)의 접두사를 붙인다.

```kotlin
// 파일: geometry/Circle.kt
package com.example.geometry

class Circle(val radius: Double)   // FQN: com.example.geometry.Circle
fun area(c: Circle) = 3.14159 * c.radius * c.radius  // FQN: com.example.geometry.area
```

이제 `Circle`의 정규화된 이름은 `com.example.geometry.Circle`이다. 서로 다른 패키지에 단순 이름(simple name)이 같은 선언이 있어도 FQN이 다르므로 충돌하지 않는다. 패키지가 있는 이유는 결국 이것 하나, 즉 **이름 충돌을 막는 것**이다.

정규화된 이름은 언제든 직접 쓸 수 있다. import가 없어도 아래 코드는 유효하다.

```kotlin
package com.example.zoo

fun buildCage(): com.example.geometry.Circle {   // FQN 직접 사용 — import 불필요
    return com.example.geometry.Circle(5.0)
}
```

여기서 이미 중요한 사실을 알 수 있다. **import는 심볼을 쓸 수 있게 해 주는 권한이 아니다.** FQN을 쓰면 import 없이도 언제나 사용할 수 있다. import는 매번 긴 FQN을 쓰지 않고 단순 이름으로 부를 수 있게 해 주는 편의 기능일 뿐이다(3절에서 자세히 다룬다).

### 2.2 패키지 이름이 디렉터리 구조와 일치하지 않아도 된다

Java에서 패키지가 `com.example.geometry`라면 파일은 반드시 `com/example/geometry/` 디렉터리에 있어야 하고, 컴파일러가 이를 강제한다. **Kotlin은 이를 강제하지 않는다.**

```kotlin
// 파일 위치: src/whatever/random/place/Shapes.kt  (디렉터리와 무관)
package com.example.geometry   // 컴파일러는 아무 불평도 하지 않는다

class Triangle
```

컴파일러 입장에서 소스 파일의 **물리적 경로**와 선언된 **논리적 패키지**는 서로 독립적이다. 컴파일러는 `package` 선언만 보고 FQN을 정한다. JVM 백엔드는 소스가 어디에 있었는지와 관계없이, 그 FQN에 따라 출력 디렉터리의 `com/example/geometry/`에 `.class` 파일을 쓴다.

그렇다면 왜 대부분 디렉터리와 패키지를 맞출까? 순전히 **관례와 도구의 편의** 때문이다. IDE는 디렉터리와 패키지가 어긋나면 경고를 띄우고 이동이나 리팩터링을 제안한다. 둘을 맞추면 사람이 파일을 찾기 쉽고, 큰 프로젝트에서도 구조를 예측할 수 있다. 하지만 이것은 **언어의 규칙이 아니라 개발자들 사이의 관례**이다.

> [!note] 명세 기준
> 패키지와 디렉터리가 일치하지 않아도 된다는 것은 언어 명세 수준의 사실이지만, 조건이 붙는다. (1) 빌드 도구가 특정한 소스 루트 규약을 강제할 수 있다(예: Gradle 소스셋 경계). (2) 빌드 설정은 `main`을 찾을 때 FQN 기반의 `mainClass`를 지정하므로, 패키지를 바꾸면 진입점의 FQN도 바뀐다(6절). 언어는 자유를 허용하지만, 생태계는 관례를 따르기를 기대한다.

### 2.3 루트(기본) 패키지: 이름이 없는 패키지

`package` 선언을 생략하면 그 파일의 선언은 **루트 패키지**(root package), 즉 이름이 빈 패키지에 들어간다.

```kotlin
// 파일에 package 선언이 없음 → 루트 패키지
class Sandbox   // FQN: 그냥 Sandbox (접두사 없음)
fun quickTest() = 42
```

루트 패키지는 즉석 실습이나 아주 작은 프로그램에는 편하지만, 실무에서는 피하는 것이 일반적이다. 특히 JVM 백엔드에서는 Java의 오래된 "무명 패키지(unnamed package)" 제약이 그대로 적용된다. 즉 **이름 있는 패키지에서는 루트 패키지의 선언을 `import`로 가져올 수 없다.**

따라서 루트 패키지에 둔 클래스는 다른 패키지의 코드에서 접근하기 어렵다. 그래서 라이브러리나 다중 모듈 프로젝트는 항상 이름 있는 패키지를 쓴다.

### 2.4 하나의 패키지가 여러 파일에 나뉠 수 있다

패키지는 파일 경계를 넘는다. `package` 선언이 같은 파일은 개수와 관계없이 논리적으로 하나의 이름공간을 이룬다.

```kotlin
// 파일 A: Cats.kt
package com.example.zoo
class Cat

// 파일 B: Dogs.kt
package com.example.zoo
class Dog
fun cat(): Cat = Cat()   // 같은 패키지의 Cat을 import 없이 사용
```

같은 패키지 안에서는 서로의 최상위 선언을 **import 없이** 단순 이름으로 부를 수 있다. 파일 B의 `cat()`이 파일 A의 `Cat`을 그대로 쓸 수 있는 것도 이 때문이다. 이 성질은 뒤에서 볼 `private`의 파일 스코프(7절)와 비교하면 더 분명해진다. **패키지는 여러 파일에 걸쳐 이름을 공유하지만, `private` 선언은 파일 안에서만 보인다.**

같은 패키지의 여러 파일에 **단순 이름이 같은 클래스나 최상위 프로퍼티**가 두 개 있으면 재선언(redeclaration) 오류가 난다. 다만 최상위 **함수**는 시그니처가 다르면 오버로딩으로 함께 존재할 수 있다.

```kotlin
// Sound1.kt
package com.example.zoo
fun makeSound(cat: Cat) = "meow"

// Sound2.kt
package com.example.zoo
fun makeSound(dog: Dog) = "woof"   // OK: 오버로드 (파라미터 타입이 다름)
// fun makeSound(cat: Cat) = "..." // 두 번째 것이 있었다면 컴파일 에러: conflicting overloads
```

## 3. import: 무엇을 가져오고, 무엇을 가져오지 않는가

### 3.1 import는 심볼을 가져오는 것이 아니라 이름을 줄여 쓰게 해 준다

앞에서 확인했듯이 import는 없는 것을 만들어 주지 않는다. import는 **현재 파일 안에서 FQN 대신 단순 이름을 쓸 수 있게 해 주는 렉시컬 축약**이다.

```kotlin
package com.example.zoo

import com.example.geometry.Circle   // "이 파일에서 Circle 이라 쓰면 com.example.geometry.Circle 이다"

fun cage() = Circle(5.0)   // 이제 단순 이름으로
```

import가 하는 일을 정확히 정리하면 다음과 같다. 컴파일러는 `Circle`이라는 이름을 해석할 때 후보 집합을 만드는데, import는 이 후보 집합에 특정 FQN 하나를 추가하라는 지시이다. 파일 $F$에서 이름을 해석하는 스코프를 후보들의 합집합으로 형식화하면 대략 다음과 같다.

$$\text{Scope}(F) = \text{현재 패키지} \cup \text{기본 import} \cup \bigcup_{i} \text{명시 import}_i$$

사용하는 자리에서 단순 이름 하나에 대한 후보가 하나뿐이면 그 선언으로 확정되고, 둘 이상이면 모호성(ambiguity) 오류가 난다. 즉 import는 스코프를 넓히는 연산이며, 코드를 실행하거나 무언가를 로드하지 않는다.

> [!warning] 흔한 오해
> "import 문이 실행되면서 클래스를 메모리에 올린다"는 생각은 모듈을 실행하는 Python의 `import`를 Kotlin에 그대로 적용한 것이다. Kotlin과 Java의 import는 **컴파일 타임에만 존재하며, 바이트코드에 흔적을 남기지 않는다.**
>
> 클래스 로딩은 그 타입을 처음 사용할 때 JVM이 지연해서 수행하며, import 여부와는 관계가 없다. `import`를 지우고 모든 FQN을 직접 적어도 실행 시맨틱은 조금도 달라지지 않는다.

### 3.2 import할 수 있는 것: 클래스만이 아니다

Java에서는 `import`로 타입을 가져오고, 정적 멤버를 가져오려면 `import static`을 따로 써야 한다. Kotlin에는 이런 구분이 없다. `import`로 이름이 있는 거의 모든 것을 가져올 수 있다.

```kotlin
import com.example.geometry.Circle        // 클래스
import com.example.geometry.area          // 최상위 함수
import com.example.geometry.PI_APPROX     // 최상위 프로퍼티
import com.example.zoo.Color.RED          // enum 상수 ([[29 - enum 클래스]])
import com.example.zoo.Registry.register  // object의 멤버 함수 ([[28 - object와 companion - 싱글턴과 동반 객체]])
import com.example.zoo.Animal.Companion.create // companion 멤버
```

특히 **확장 함수와 확장 프로퍼티**는 import가 실제로 필요하다. 확장은 클래스에 실제 멤버를 추가하지 않고 정적으로 해석되기 때문에([[35 - 확장 함수와 프로퍼티]]), 확장 선언이 **현재 파일의 스코프에 들어와 있어야만** 호출할 수 있다.

```kotlin
// 파일 StringExt.kt
package com.example.util
fun String.shout(): String = uppercase() + "!"

// 파일 Main.kt
package com.example.app
import com.example.util.shout   // 이 import가 없으면 shout()을 호출조차 못 한다

fun demo() = "hello".shout()    // => "HELLO!"
```

이 점이 확장과 클래스 멤버를 구분하는 실용적인 특징이다. 멤버 함수는 타입만 보이면 어디서든 부를 수 있지만, 확장은 그 이름이 스코프에 들어와 있는지에 따라 호출할 수 있는지가 정해진다.

### 3.3 별칭 `as`: 이름 충돌을 해결하는 방법

단순 이름이 같은 두 선언을 한 파일에서 모두 쓰려면 `as`로 한쪽에 새 이름을 붙인다.

```kotlin
import com.example.graphics.Color         // 그래픽스의 Color
import com.example.paint.Color as PaintColor  // 페인트의 Color를 PaintColor로 별칭

fun mix(a: Color, b: PaintColor) { /* 둘을 한 파일에서 명확히 구분 */ }
```

`as`로 붙인 이름은 그 파일 안에서만 유효한 지역적인 새 이름이다. 원래 선언의 FQN이나 다른 파일에서 쓰는 이름은 바뀌지 않는다. 별칭은 이름 충돌을 해결할 때 외에도, 긴 이름을 짧게 줄이거나 문맥에 맞는 어휘를 붙일 때 쓴다. 다만 너무 많이 쓰면 코드를 읽는 사람이 실제 타입을 추적하기 어려워지므로 적당히 써야 한다.

> [!note] 명세 기준
> `import ... as X`로 붙인 별칭 `X`는 타입 별칭(`typealias`, 36장 타입 별칭과 인라인 value class)과 다르다. import 별칭은 **한 파일 안에서만 쓰는 지역 이름**일 뿐이며, 새 타입도 아니고 다른 파일에서 보이지도 않는다. 반면 `typealias`는 최상위 선언이므로 패키지 전체에서, 그리고 import를 통해 다른 파일에서도 쓸 수 있다. 둘 다 새 타입이 아니라는 점은 같지만, 보이는 범위는 정반대이다.

### 3.4 스타 임포트 `*`: 편리하지만 위험하다

`import 패키지.*`는 그 패키지(또는 객체, enum 등)에서 **보이는 최상위 멤버 전부**를 단순 이름으로 가져온다.

```kotlin
import com.example.geometry.*   // geometry 패키지의 모든 것
import kotlin.math.*            // sqrt, sin, PI, abs, ... 전부
```

스타 임포트에는 세 가지 규칙이 있다.

1. **별칭을 붙일 수 없다**: `import foo.* as bar`는 불가능하다. `*`는 여러 이름을 한꺼번에 가져오므로 새 이름 하나를 붙일 수 없다.
2. **명시적 import가 스타 임포트보다 우선한다**: 이름이 겹치면 명시적으로 적은 import가 스타 임포트보다 우선한다.
3. **모호성은 사용할 때 판정한다**: 서로 다른 두 스타 임포트가 같은 단순 이름을 제공하더라도, 그 이름을 실제로 쓰기 전에는 오류가 아니다. 이름을 쓰는 순간에만 모호성 오류가 난다.

```kotlin
import com.example.graphics.*   // 여기에 Color 가 있고
import com.example.paint.*      // 여기에도 Color 가 있다

// 아무 데서도 Color 를 안 쓰면 아무 오류 없음.
fun useColor() {
    val c: Color = TODO()   // 컴파일 에러: overload resolution ambiguity (여기서 비로소 충돌)
}
```

명시적 import가 스타 임포트보다 우선한다는 규칙 덕분에, 위와 같은 상황도 한쪽을 명시적으로 import하면 바로 해결된다.

```kotlin
import com.example.graphics.*
import com.example.paint.*
import com.example.graphics.Color   // 명시 import가 스타를 이긴다 → Color = graphics.Color 로 확정
```

> [!caution] 성능 주의
> import는 컴파일 타임에만 쓰이므로 스타 임포트는 런타임 성능에 아무 영향도 주지 않는다. "스타 임포트를 쓰면 무거운 클래스를 모두 로드해서 느려진다"는 것은 오해이다.
>
> 스타 임포트의 실제 비용은 **가독성**이다. 어떤 심볼이 어느 패키지에서 왔는지 파일만 보고는 알기 어렵고, 라이브러리의 새 버전이 같은 이름을 추가하면 예고 없이 모호성 오류가 생길 수 있다. 그래서 많은 팀이 스타일 규칙으로 스타 임포트를 제한한다.

### 3.5 기본 import: `println`과 `listOf`를 바로 쓸 수 있는 이유

새 파일을 열고 import를 한 줄도 쓰지 않아도 `println`, `listOf`, `mapOf`, `require`, `TODO()`, `Int`, `String`을 곧바로 쓸 수 있다. 컴파일러가 **모든 Kotlin 파일에 암묵적으로 넣는 기본 import**가 있기 때문이다. 모든 타깃에 공통으로 들어오는 패키지는 다음과 같다.

```text
kotlin.*             // Int, String, Any, Unit, Nothing, TODO, require, run, let ...
kotlin.annotation.*  // @Target, @Retention 등 메타 애노테이션
kotlin.collections.* // List, Set, Map, listOf, mutableListOf, mapOf ...
kotlin.comparisons.* // compareBy, maxOf, minOf, naturalOrder ...
kotlin.io.*          // println, print, readLine ...
kotlin.ranges.*      // .. 연산으로 만들어지는 IntRange 등, until, downTo, step
kotlin.sequences.*   // Sequence, generateSequence, sequenceOf ...
kotlin.text.*        // String 확장들, StringBuilder, Regex, trimIndent ...
```

Kotlin은 여러 타깃을 지원하는 언어이므로, **타깃마다 추가되는** 기본 import도 있다.

| 타깃(백엔드) | 추가 기본 import |
|--------------|-------------------|
| JVM | `java.lang.*`, `kotlin.jvm.*` |
| JS | `kotlin.js.*` |

이 표가 중요한 이유가 있다. JVM 백엔드에서 `Thread`, `Runnable`, `System`을 import 없이 쓸 수 있는 것은 `java.lang.*`가 기본 import이기 때문인데, **이것은 JVM에서만 제공되는 편의**이다. 같은 코드를 Kotlin/JS나 Kotlin/Native로 컴파일하면 `java.lang.*`가 없으므로 `Thread` 같은 이름을 해석하지 못한다.

멀티플랫폼 공통 코드([[46 - 멀티플랫폼과 진화와 어두운 구석]])에서 `java.*`에 의존하면 안 되는 근본적인 이유가 여기에 있다. "Kotlin에서 되니까 어디서나 되겠지"라는 생각은 JVM에 익숙해서 생기는 착각이다.

## 4. 최상위 선언: 클래스 없이 존재하는 함수와 값

### 4.1 최상위 함수와 프로퍼티라는 발상

객체지향의 관습에서는 모든 함수가 어떤 클래스의 메서드여야 한다. Java에서 유틸리티 함수는 `Math.sqrt`, `Collections.sort`처럼 억지로 클래스에 담긴다. 그래서 `Math`는 인스턴스를 만드는 의미가 없는, 정적 메서드를 모아 두는 곳이 되고, 그 클래스는 오직 함수를 담기 위한 껍데기 역할만 한다.

Kotlin은 함수와 프로퍼티를 **일급 최상위 선언**으로 만들어 이 껍데기를 없앤다.

```kotlin
package com.example.mathx

const val GOLDEN_RATIO = 1.618033988749895   // 최상위 상수
val defaultPrecision = 6                       // 최상위 프로퍼티

fun clamp(x: Double, lo: Double, hi: Double): Double =   // 최상위 함수
    maxOf(lo, minOf(hi, x))
```

`clamp`는 어떤 클래스에도 속하지 않는다. 호출하는 쪽에서는 `com.example.mathx.clamp(...)`라고 쓰거나, import한 뒤 `clamp(...)`라고 쓴다. 인위적인 `MathUtils` 클래스가 필요 없다. Kotlin 코드가 Java보다 가벼워 보이는 큰 이유 중 하나가 이것이다.

그러나 최상위 함수와 프로퍼티는 개념적으로만 클래스 밖에 있을 뿐이다. JVM에는 클래스 밖에 메서드가 존재할 수 없으므로, **JVM 백엔드에서는 반드시 어떤 클래스에 담겨야 한다**. 이때 담는 클래스가 파일 클래스(`*Kt`)이며, 5절에서 자세히 살펴본다. 소스의 개념 모델과 JVM 백엔드의 실제 결과물이 달라지는 대표적인 지점이다.

### 4.2 최상위 프로퍼티의 종류와 컴파일 형태(개념)

최상위에는 세 종류의 프로퍼티를 둘 수 있다.

```kotlin
const val MAX_LEGS = 8      // 컴파일 상수 (M36)
val zooName = "Central"     // 읽기 전용 프로퍼티 (재대입 불가, M3)
var visitorCount = 0        // 가변 프로퍼티
```

세 프로퍼티의 차이는 11장(변수와 초기화)에서 자세히 다룬다. 여기서는 파일에 담긴다는 관점에서 다음 내용만 짚어 둔다.

- `const val`은 **컴파일 상수**이다. 값이 컴파일 타임에 확정되고, JVM 백엔드에서는 사용하는 곳에 값이 그대로 인라인된다. 원시 타입이나 `String`만 가능하며, 리터럴이나 다른 `const`를 조합한 값만 쓸 수 있다.
- `val`은 다시 대입할 수 없다는 뜻일 뿐, 불변 객체를 뜻하지 않는다. JVM 백엔드에서 최상위 `val`은 보통 파일 클래스의 `private static` 필드와 `public static` 게터로 컴파일된다.
- `var`은 게터와 세터를 모두 가진다.

"`val`이 불변 객체를 만든다"거나 "`const`와 `val`은 같다"는 오해는 11장에서 바로잡는다. 이 장에서는 파일 관점에서 한 가지만 기억해 두자. 최상위 `const`는 사용하는 곳에 인라인되므로, 라이브러리 API에서 그 값을 바꿔도 사용하는 쪽을 다시 컴파일하지 않으면 반영되지 않는다.

### 4.3 최상위 선언 사이의 접근과 오버로딩

같은 패키지의 최상위 선언은 서로를 자유롭게 호출할 수 있다(2.4절). 최상위 함수는 파라미터가 다르면 오버로딩되고, 컴파일러의 오버로드 해석 규칙([[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]])에 따라 가장 구체적인 함수가 선택된다.

```kotlin
package com.example.zoo

fun feed(a: Cat) = "fish"
fun feed(a: Dog) = "bone"
fun feed(a: Any) = "generic food"

fun test() {
    feed(Cat("x"))     // => "fish"  (가장 구체적인 Cat 오버로드)
    feed(42)           // => "generic food"  (Any 오버로드로 폴백)
}
```

### 4.4 타입 별칭의 위치: 최상위와 (2.2부터) 클래스 안

작은 부분이지만 파일 구성의 관점에서 기억해 둘 것이 있다. `typealias`는 전통적으로 **최상위 선언**으로 쓰였다. Kotlin 2.2에서 클래스나 인터페이스 안에 두는 **중첩 타입 별칭**(nested type alias)이 도입되면서(2.2 베타, 2.3 안정화) 이 제약이 일부 풀렸다. 하지만 **함수 본문 안의 지역(local) 타입 별칭은 여전히 허용되지 않는다.**

```kotlin
typealias StringMap = Map<String, String>   // OK (최상위)

class Registry {
    typealias Handler = (String) -> Unit     // OK (클래스 안 중첩, Kotlin 2.2+)
}

fun demo() {
    // typealias LocalMap = Map<Int, Int>    // 컴파일 에러: local type aliases are not supported
}
```

지역 타입 별칭이 여전히 막혀 있는 이유는, 타입 별칭이 새 타입이 아니라 순수한 이름 축약이고, 함수 스코프 안에서만 잠시 쓰이는 이름으로 새 타입 이름을 도입하는 기능을 언어가 지원하지 않기 때문이다. 중첩 타입 별칭에도 바깥 클래스의 타입 파라미터를 캡처할 수 없다는 제약이 있다. 자세한 의미는 36장(타입 별칭과 인라인 value class)에서 다룬다.

## 5. 파일 클래스: JVM 백엔드에서 파일이 클래스로 합쳐지는 방식

### 5.1 `Utils.kt`는 `UtilsKt` 클래스가 된다

이제 이 장에서 기술적으로 가장 중요한 부분이다. JVM에는 클래스 밖 함수라는 개념이 없는데, Kotlin은 최상위 함수와 프로퍼티를 허용한다(4절). 컴파일러는 이 모순을 **파일 클래스**(file class, 흔히 파일 파사드facade라고 부름)로 해결한다. 즉 `.kt` 파일 하나에 있는 모든 최상위 함수와 프로퍼티를 합성 클래스 하나에 정적 멤버로 모아 넣는다.

```kotlin
// 파일: Utils.kt
package com.example.util

fun greet(name: String) = "Hello, $name"
val version = "1.0"
```

JVM 백엔드에서 이 코드는 대략 다음 Java 코드에 해당한다.

```java
// 개념적으로 생성되는 파일-클래스 (디컴파일 결과의 요지)
package com.example.util;

public final class UtilsKt {          // 파일 이름 Utils → UtilsKt
    private static final String version = "1.0";

    public static String greet(String name) {
        return "Hello, " + name;
    }
    public static String getVersion() {   // val 은 게터로
        return version;
    }
}
```

클래스 이름은 파일 이름에서 확장자를 떼고, 첫 글자를 대문자로 바꾼 뒤 `Kt`를 붙여서 만든다. `Utils.kt`는 `UtilsKt`, `main.kt`는 `MainKt`가 된다. 파일 이름에 식별자로 쓸 수 없는 문자가 있으면 컴파일러가 이름을 정규화하지만, 그 세부 방식은 백엔드 구현에 따라 다르므로 여기서 규칙을 단정하지 않는다.

Kotlin에서 호출할 때는 `greet("world")`처럼 클래스를 의식하지 않아도 된다. 하지만 **Java에서 이 함수를 호출할 때는** `UtilsKt.greet("world")`처럼 파일 클래스 이름을 알아야 한다. 이 상호운용의 세부 내용은 [[45 - Java 상호운용]]에서 다룬다. "Java에서 Kotlin 최상위 함수가 왜 `XxxKt.foo`로 보이는가"라는 질문의 답이 바로 파일 클래스이다.

> [!note] 명세 기준
> 파일 클래스는 **JVM 백엔드에서만 만들어지는 결과물**이다. Kotlin/Native, Kotlin/JS, Kotlin/Wasm은 각자의 방식으로 최상위 선언을 표현하며, `*Kt` 클래스라는 개념 자체가 없다. 따라서 "`.kt`는 `*Kt.class`가 된다"는 문장은 항상 "JVM 백엔드에서"라는 조건을 붙여서 읽어야 한다.

### 5.2 `@file:JvmName`: 파일 클래스 이름 바꾸기

자동으로 붙는 `UtilsKt`라는 이름이 마음에 들지 않거나, Java 사용자에게 더 자연스러운 이름을 제공하고 싶다면 파일 애노테이션으로 이름을 바꾼다.

```kotlin
@file:JvmName("StringUtils")   // 반드시 package 선언보다 위

package com.example.util

fun capitalizeFirst(s: String): String = s.replaceFirstChar { it.uppercase() }
```

이제 Java에서는 `StringUtils.capitalizeFirst(...)`로 호출한다. `@file:` 접두사는 이 애노테이션이 파일 전체, 즉 파일 클래스를 대상으로 한다는 사용 지점 타깃 표기이다(사용 지점 타깃 전반은 [[44 - 애노테이션과 리플렉션]]에서 다룬다). `JvmName`은 이름 그대로 JVM에서 쓰이는 이름을 바꾼다. 1.1절에서 본 파일 구조의 순서 규칙 때문에, 이 애노테이션은 반드시 파일 맨 위(패키지 선언 앞)에 두어야 한다.

### 5.3 `@file:JvmMultifileClass`: 여러 파일을 한 클래스로 합치기

표준 라이브러리를 디컴파일하면 `kotlin.collections.CollectionsKt` 하나에 매우 많은 함수가 들어 있다. 그런데 stdlib 소스에서는 그 함수들이 여러 파일에 나뉘어 있다. 여러 파일이 어떻게 파사드 클래스 하나로 모였을까? `@JvmName`과 `@JvmMultifileClass`를 함께 쓰면 된다.

```kotlin
// 파일: Collections1.kt
@file:JvmName("CollectionsKt")
@file:JvmMultifileClass
package com.example.col
fun <T> List<T>.second(): T = this[1]

// 파일: Collections2.kt
@file:JvmName("CollectionsKt")
@file:JvmMultifileClass
package com.example.col
fun <T> List<T>.third(): T = this[2]
```

두 파일이 **같은 `@JvmName("CollectionsKt")`** 를 선언하고 **둘 다 `@JvmMultifileClass`** 를 붙이면, JVM 백엔드는 두 파일을 파사드 클래스 `CollectionsKt` 하나로 병합한다. 내부적으로는 파일마다 부분 클래스를 만들고, 파사드가 그 부분 클래스에 호출을 넘기는 형태이다.

이렇게 하면 소스는 논리적으로 잘게 나누면서도, 사용자에게는 하나의 API(`CollectionsKt.second`, `CollectionsKt.third`)를 제공할 수 있다.

`@JvmMultifileClass` 없이 두 파일에 같은 `@JvmName`만 붙이면, 두 파일이 같은 클래스 이름을 두고 충돌해서 오류가 난다. 병합하겠다는 의도를 명시하는 애노테이션이 바로 `@JvmMultifileClass`이다.

```text
소스 관점                       JVM 백엔드 산물
──────────────                  ─────────────────
Collections1.kt ─┐
                 ├─ @JvmMultifileClass ─▶  CollectionsKt (파사드)
Collections2.kt ─┘                          ├─ 위임 → Collections1__CollectionsKt (부분)
                                            └─ 위임 → Collections2__CollectionsKt (부분)
```

이것도 JVM 백엔드에만 해당하는 이야기이다. 다른 타깃에는 파사드 병합이라는 개념이 없다.

### 5.4 최상위 `val`을 필드로 노출하기: `@JvmField`

최상위 `val`은 기본적으로 파일 클래스의 게터(`getX()`)로 노출된다. Java에서 필드처럼 직접 접근하고 싶다면 `@JvmField`를 붙여 게터 없이 `public static` 필드로 만들 수 있다(`const`가 아닐 때만 의미가 있고, 몇 가지 제약이 있다).

이 최적화와 상호운용의 세부 내용은 [[22 - 프로퍼티와 백킹 필드]]와 45장(Java 상호운용)에서 다룬다. 여기서는 파일 클래스가 프로퍼티를 정적 멤버로 노출하는 방식을 애노테이션으로 조정할 수 있다는 점만 기억하자.

## 6. 진입점 `main`: 프로그램은 어디서 시작하는가

### 6.1 `main`의 여러 시그니처

Kotlin 프로그램의 진입점은 `main` 함수이다. 허용되는 시그니처는 네 가지이다.

```kotlin
fun main() { }                              // (1) 인자 없음 (Kotlin 1.3+)
fun main(args: Array<String>) { }           // (2) 명령행 인자
suspend fun main() { }                       // (3) 코루틴 진입점 (1.3+)
suspend fun main(args: Array<String>) { }    // (4) 코루틴 + 인자
```

원래는 `fun main(args: Array<String>)` 하나만 있었다. 그래서 인자를 쓰지 않는 프로그램도 `args`를 억지로 선언해야 했는데, Kotlin 1.3에서 **인자 없는 `main`** 이 추가되어 상용구가 줄었다. 같은 버전에서 `suspend fun main`도 도입되어, `runBlocking`으로 따로 감싸지 않고도 최상위에서 코루틴을 시작할 수 있게 되었다([[42 - suspend와 코루틴 - 언어 수준의 중단]]).

```kotlin
fun main() {
    println("Hello, Kotlin")   // args 없이 간결하게
}
```

### 6.2 `main`은 최상위 함수이다: JVM 진입 규약과 연결하기

`main`도 결국 최상위 함수이므로, JVM 백엔드에서는 그 파일의 파일 클래스에 정적 메서드로 담긴다. `Main.kt`에 `fun main()`을 두면 `MainKt` 클래스가 생기고, 그 안에 진입 메서드가 들어간다.

JVM 런처는 `public static void main(String[] args)` 시그니처를 요구한다. Kotlin에서 인자 없는 `fun main()`을 쓰면, 컴파일러는 JVM 규약을 맞추기 위해 **인자를 무시하는 브리지 메서드 `main(String[])`** 를 파일 클래스에 생성한다.

`suspend fun main`이면 컴파일러는 코루틴을 구동하는 래퍼를 갖춘 `main(String[])`을 생성한다. 즉 어떤 시그니처를 쓰든 최종적으로는 JVM이 인식하는 표준 진입점이 만들어진다.

```text
소스: Main.kt 에 fun main()
   │  (JVM 백엔드)
   ▼
클래스 MainKt
   ├─ static void main(String[] args)   ← JVM 런처가 부르는 진입 메서드
   │     └─ 내부에서 인자 무시하고 실제 main() 호출
   └─ ...
```

실행할 때 `mainClass`로 지정하는 것은 이 파일 클래스의 FQN(`com.example.MainKt`)이다. 그래서 패키지를 바꾸면 진입점의 FQN도 바뀐다. 2.2절에서 언급한 주의점이 바로 이것이다.

### 6.3 `main`이 여러 개일 때: 진입점은 언어가 아니라 빌드가 정한다

한 프로젝트에서 여러 파일에 `main` 함수가 있을 수 있다. 언어는 이를 금지하지 않으며, 각 파일 클래스가 각자의 진입 메서드를 가질 뿐이다. **어느 것을 실제 진입점으로 쓸지는 언어가 아니라 빌드와 실행 설정이 정한다**(예: Gradle `application` 플러그인의 `mainClass`, 또는 실행할 때 지정하는 클래스 FQN).

```kotlin
// AppA.kt (com.example)
fun main() = println("A")   // 파일-클래스 com.example.AppAKt

// AppB.kt (com.example)
fun main() = println("B")   // 파일-클래스 com.example.AppBKt
```

두 진입점은 함께 존재한다. 실행할 때 `com.example.AppAKt`를 지정하면 A가, `com.example.AppBKt`를 지정하면 B가 시작된다. "프로그램의 진입점은 하나뿐"이라고 생각해 온 사람에게는 직관에 어긋날 수 있다.

하지만 Kotlin에서 `main`은 특별한 언어 키워드가 아니라 **관례적인 이름과 시그니처를 가진 평범한 최상위 함수**이다. 그중 무엇을 시작점으로 삼을지는 외부 도구가 결정한다. 이렇게 이해하는 것이 정확하다.

> [!warning] 흔한 오해
> "`main`은 예약어이고 프로그램마다 하나만 있을 수 있다"는 것은 오해이다. `main`은 키워드가 아니며(3장 렉시컬 구조에서 본 키워드의 세 분류 어디에도 없다), 컴파일러와 런처는 이름과 시그니처가 규약에 맞는 최상위 함수를 진입점 후보로 인식할 뿐이다. `fun main()`을 클래스 안의 메서드로 선언하면 그것은 진입점이 아니라 평범한 메서드이다.

### 6.4 최상위 실행문이 없다는 것의 의미

이제 1.3절에서 본 "최상위 실행문 금지"가 왜 자연스러운지 설명할 수 있다. 스크립트 언어(Python, 그리고 Kotlin의 `.kts`)에서는 파일 자체가 실행 흐름이므로 최상위에 문장을 나열한다. 그러나 `.kt` 파일은 **선언의 모음**일 뿐 실행 흐름이 아니다. 실행은 명시적으로 지정한 `main`에서 시작한다.

그래서 `.kt` 파일의 최상위에 `println(...)`을 두면 실행될 곳이 없는 문장이 되므로 컴파일러가 거부한다. 실행을 시작하는 지점을 `main`으로 고정한 덕분에, 선언을 배치한 순서와 실행 순서를 분리할 수 있게 되었다(7~8절의 주제).

## 7. 최상위 가시성: 기본값 public과 파일 스코프 private

### 7.1 최상위 선언의 기본 가시성은 public

가시성을 명시하지 않은 최상위 선언은 `public`이다. Kotlin은 Java의 "기본값 package-private"을 버리고 **기본값 public**을 선택했다(그 설계 배경은 [[26 - 가시성 한정자]]에서 다룬다).

```kotlin
package com.example.zoo

fun openToAll() { }          // public (기본)
public fun alsoPublic() { }  // 명시해도 같음 (보통 생략)
```

최상위에 쓸 수 있는 가시성 한정자는 `public`, `internal`, `private` 세 가지이다. **`protected`는 최상위에서 허용되지 않는다.** `protected`는 "하위 클래스에서 보인다"는 뜻인데, 최상위 선언에는 상속 관계라는 개념이 없기 때문이다.

```kotlin
// protected fun cannotBeTopLevel() { }   // 컴파일 에러: modifier 'protected' is not applicable to 'top level declaration'
```

### 7.2 `private` 최상위 선언은 파일 스코프이다

이 장에서 가장 중요한 가시성 규칙이다. 최상위 선언에 `private`을 붙이면 그 범위는 **선언된 파일 전체**가 된다. 클래스나 함수, 프로퍼티가 아니라 **파일**이 경계가 된다.

```kotlin
// 파일: Internal.kt
package com.example.zoo

private fun secretHelper() = 42          // 이 파일 안에서만 보임
private val secretKey = "abc"            // 이 파일 안에서만 보임

fun publicApi() = secretHelper() + secretKey.length  // 같은 파일 → OK
```

```kotlin
// 파일: Other.kt (같은 패키지 com.example.zoo)
package com.example.zoo

fun tryToUse() {
    // secretHelper()   // 컴파일 에러: cannot access 'secretHelper': it is private in file
}
```

2.4절과 비교하면 차이가 분명해진다. **같은 패키지의 다른 파일은 서로의 public 최상위 선언을 import 없이 쓸 수 있지만, `private` 최상위 선언은 다른 파일에서 보이지 않는다.** 즉 패키지는 여러 파일에 걸친 이름공간이고, `private`은 파일 안으로 범위를 제한한다.

이런 파일 스코프 private에 해당하는 기능은 Java에 없다. Java에서 가장 좁은 최상위 가시성은 package-private인데, 이 범위는 파일이 아니라 패키지를 기준으로 한다.

### 7.3 `internal`: 모듈 스코프 (파일도 패키지도 아니다)

`internal`은 **모듈**(module) 단위의 가시성이다. 모듈은 함께 컴파일되는 단위를 뜻하며, Gradle 모듈, Maven 프로젝트, IntelliJ 모듈, 컴파일러를 한 번 호출할 때 컴파일되는 범위 등이 여기에 해당한다.

```kotlin
package com.example.zoo

internal fun forThisModuleOnly() { }   // 같은 모듈 어디서나, 다른 모듈에선 안 보임
```

`internal`을 Java의 package-private과 혼동하기 쉽지만, 두 한정자는 경계가 다르다. Java의 package-private은 **패키지** 단위이고, Kotlin의 `internal`은 **모듈** 단위이다. 모듈은 여러 패키지를 포함할 수 있으므로 `internal`의 범위가 훨씬 넓다.

이 혼동은 26장(가시성 한정자)에서 자세히 바로잡는다. JVM 백엔드에서 `internal`을 이름 맹글링(name mangling)으로 표현하는 상호운용의 세부 내용은 45장(Java 상호운용)에서 다룬다. 이 장에서는 최상위 선언의 가시성 경계가 파일(private), 모듈(internal), 전역(public)으로 각각 크기가 다르다는 점만 정리해 둔다.

| 한정자 | 최상위 선언의 가시 범위 | 크기 감각 |
|--------|--------------------------|-----------|
| `private` | 선언된 **파일** 안 | 가장 좁음 |
| `internal` | 같은 **모듈** 안 | 중간 |
| `public`(기본) | 어디서나 | 가장 넓음 |
| `protected` | (최상위에는 불가) | - |

## 8. 선언 순서: 이름은 순서와 무관하고, 초기화는 순서에 의존한다

### 8.1 이름 해석은 순서를 따지지 않는다 (전방 참조)

Kotlin은 C처럼 위에서 아래로 읽어 가며 정의를 먼저 만나야 호출할 수 있는 언어가 아니다. 파일 위쪽의 선언이 아래쪽의 선언을 **자유롭게 먼저 참조(forward reference)** 할 수 있다.

```kotlin
fun start() = helper()    // 아래에 정의된 helper 를 위에서 호출 — OK

fun helper() = "done"     // 정의가 뒤에 있어도 문제없음
```

컴파일러는 파일(실제로는 모듈 전체)의 모든 선언을 먼저 수집해 심볼 테이블을 만든 뒤, 본문의 이름을 해석한다. 그래서 최상위 함수와 클래스, 프로퍼티는 **텍스트 순서와 관계없이 서로를 볼 수 있다.** 클래스도 마찬가지이다.

```kotlin
class Zoo(val star: Animal)   // Animal 이 아래에 정의됨 — OK

class Animal(val name: String)
```

이 성질 때문에 선언 순서는 전혀 상관없다는 인상을 받기 쉽다. 함수 호출과 타입 참조에 관해서는 그 인상이 맞다. 그러나 결정적인 예외가 하나 있으며, 이것이 이 장에서 가장 미묘한 함정이다.

### 8.2 초기화는 텍스트 순서를 따른다 (예외)

**최상위 프로퍼티의 초기화 코드는 파일에 적힌 순서대로 실행된다.** 이름 해석은 순서와 무관하지만, 초기화 표현식이 실제로 평가되는 시점은 순서에 의존한다. JVM 백엔드에서는 최상위 프로퍼티의 초기화 코드가 파일 클래스의 정적 초기화 블록(`<clinit>`)에 텍스트 순서대로 놓이기 때문이다.

여기서 함정이 생긴다. 위쪽 프로퍼티의 초기화 식이 아직 초기화되지 않은 아래쪽 프로퍼티를 읽으면, 그 값은 **초기화 전의 기본값**(참조는 `null`, 수치는 0)이다.

```kotlin
// 파일: Config.kt
val derived = base.uppercase()   // (1) 먼저 실행 — 이 시점에 base 는 아직 초기화 안 됨!
val base = "hello"               // (2) 나중에 실행

fun main() {
    println(base)      // => hello
    println(derived)   // 위쪽 초기화 때 base 가 아직 null 이었으므로
                       // 런타임 예외 (NPE) 또는 예기치 않은 값
}
```

이 코드에서는 `derived`의 초기화가 먼저 실행된다. 그 순간 `base`에는 아직 "hello"가 대입되지 않았으므로, 참조 타입의 기본값인 `null` 상태이다. 그 `null`에 `uppercase()`를 호출하면 런타임 예외가 난다. 이름 해석은 성공해서 컴파일은 통과했지만, **초기화 순서** 때문에 논리가 깨진 것이다.

이 함정은 지역 초기화나 멤버 초기화의 문제, 예를 들어 [[24 - 상속과 오버라이딩과 초기화 순서]]에서 다루는 "생성자에서 오버라이드된 멤버를 호출하는 문제"와 원인이 같다. **선언되는 것과 초기화되는 것은 서로 다른 사건인데, 코드는 종종 선언된 것을 초기화된 것으로 착각한다.**

해결 방법은 세 가지이다. 순서를 바꾸거나(`base`를 위로), 지연 초기화(`by lazy`, [[23 - 위임 프로퍼티]])를 쓰거나, 함수나 게터로 계산을 미루면 된다.

```kotlin
// 해법 A: 순서 바로잡기
val base = "hello"
val derived = base.uppercase()   // 이제 base 가 먼저 초기화됨 → 안전

// 해법 B: 지연 계산
val base2 = "hello"
val derived2 by lazy { base2.uppercase() }   // 첫 접근 시 계산 → 순서 무관하게 안전
```

### 8.3 파일이 여러 개일 때: 초기화 순서는 클래스 로딩 순서를 따른다

한 파일 안에서 최상위 프로퍼티의 초기화 순서는 텍스트 순서로 분명하게 정해진다. 그러나 **서로 다른 파일**에 있는 최상위 프로퍼티 사이의 초기화 순서는 언어가 전역적으로 정해 주지 않는다.

JVM 백엔드에서 파일 클래스는 각각 별개의 클래스이고, 클래스의 정적 초기화는 **그 클래스를 처음 사용하는 시점까지 지연(lazy)되기** 때문이다. 즉 파일 A의 프로퍼티와 파일 B의 프로퍼티 중 무엇이 먼저 초기화되는지는 실행 중에 어느 클래스가 먼저 로드되는지에 달려 있다.

```kotlin
// FileA.kt
val a = "A-init".also { println("init A") }

// FileB.kt
val b = "B-init".also { println("init B") }

// Main.kt
fun main() {
    println(b)   // B 를 먼저 건드리면 "init B" 가 먼저
    println(a)   // 그다음 "init A"
}
```

`main`이 `a`를 먼저 참조하면 파일 클래스 A가 먼저 로드되어 A가 먼저 초기화되고, `b`를 먼저 참조하면 B가 먼저 초기화된다. 따라서 **여러 파일의 최상위 프로퍼티가 서로의 초기화에 의존하도록 설계해서는 안 된다.** 초기화 순서에 의존하는 전역 상태는 파일 경계를 넘는 순간 거의 예측할 수 없게 된다.

실무에서는 이런 순서 의존을 아예 없애는 것이 일반적이다. 필요하다면 명시적인 초기화 함수를 만들거나, 지연 초기화를 써서 값을 사용할 때 준비되도록 바꾼다.

> [!caution] 성능 주의
> 최상위 프로퍼티는 편리하지만, JVM 백엔드에서 각 파일 클래스의 `<clinit>`은 그 클래스를 처음 사용할 때 한 번 실행된다. 파일 읽기나 네트워크 호출, 큰 컬렉션 구성처럼 무거운 초기화를 최상위 `val`의 초기화 식에 두면, 그 클래스가 처음 로드될 때 그 비용이 한꺼번에 발생한다.
>
> 여러 최상위 값이 서로 얽혀 있으면 초기화 순서의 함정까지 겹친다. 그래서 늦게 계산해도 되는 무거운 값은 `by lazy`로 선언하는 것이 실용적인 원칙이다.

### 8.4 순서 무관과 순서 의존을 한 표로 정리

| 대상 | 텍스트 순서에 의존? | 이유 |
|------|----------------------|------|
| 함수 호출 (전방 참조) | 아니오 | 심볼 테이블을 먼저 구축 후 해소 |
| 타입 참조 (클래스가 아래에) | 아니오 | 위와 동일 |
| **같은 파일의 프로퍼티 초기화** | **예** | `<clinit>`에 텍스트 순서대로 배치(JVM) |
| 서로 다른 파일의 프로퍼티 초기화 | (정의 안 됨) | 클래스 로딩(지연) 순서에 좌우 |

이 표가 8절의 결론이다. "선언 순서는 무관하다"는 명제는 **이름의 관점에서는 참이고, 초기화의 관점에서는 거짓**이다. 이 구분을 놓치면 컴파일은 되는데 값이 이상하게 나오는, 원인을 찾기 어려운 버그를 만나게 된다.

## 9. 멀티타깃에서의 파일과 패키지: 소스 구조는 같고 결과물은 다르다

### 9.1 소스 구조는 타깃과 무관하고, 컴파일 결과물은 타깃마다 다르다

지금까지 본 파일 구조(파일 애노테이션, 패키지, import, 최상위 선언의 순서), 패키지 이름공간, import 규칙, 최상위 선언의 가시성, 선언 순서 규칙은 모두 **어느 타깃에서나 똑같이 적용되는 소스 수준의 규칙**이다. Kotlin/JVM이든 Kotlin/Native든 Kotlin/JS든, `.kt` 파일을 작성하는 방식은 같다.

달라지는 것은 **컴파일 결과물의 실제 형태**이다. 이 장에서 여러 번 조건을 달았듯이 다음 항목은 모두 JVM 백엔드에 해당한다.

- 파일 클래스(`*Kt`), `@JvmName`, `@JvmMultifileClass`, `@JvmField`, `main`의 `static void main(String[])` 브리지는 모두 **JVM 백엔드에만 있는** 개념이다.
- `java.lang.*` 기본 import도 **JVM 백엔드에만 있다**.
- 최상위 프로퍼티가 `<clinit>`에서 초기화된다는 것은 **JVM 백엔드의 실행 모델**이다. 다른 백엔드는 최상위 값의 초기화를 다른 메커니즘으로 처리한다.

이 구분을 계속 의식하면 Kotlin을 JVM 전용 언어로 오해하지 않을 수 있다. 파일과 패키지는 **논리적 구조**이고, `*Kt` 클래스나 정적 초기화 같은 것은 그 구조를 특정 플랫폼(JVM)에 맞게 옮길 때 생기는 **번역의 결과**이다.

### 9.2 `expect`/`actual`과 패키지: 같은 이름, 다른 구현

멀티플랫폼(46장 멀티플랫폼과 진화)에서는 공통 소스셋에 `expect` 선언을, 플랫폼별 소스셋에 `actual` 구현을 둔다. 이때 이 장의 주제와 직접 관련된 결정적인 규칙이 하나 있다. **`expect`와 그에 대응하는 `actual`은 패키지와 이름이 같아야 한다.**

```kotlin
// 공통 소스셋: platform.kt
package com.example.platform
expect fun currentTimeMillis(): Long

// JVM 소스셋: platform.jvm.kt
package com.example.platform      // 같은 패키지
actual fun currentTimeMillis(): Long = System.currentTimeMillis()

// JS 소스셋: platform.js.kt
package com.example.platform      // 같은 패키지
actual fun currentTimeMillis(): Long = kotlin.js.Date.now().toLong()
```

여기서는 패키지가 `expect`와 `actual`을 짝짓는 기준이 된다. 공통 코드가 `com.example.platform.currentTimeMillis()`를 호출하면, 컴파일러는 대상 플랫폼에서 패키지와 이름이 같은 `actual`을 찾아 연결한다.

2절에서 설명한 "패키지는 이름을 나누는 단위"라는 개념이 멀티플랫폼 구조의 기반으로 확장되는 것이다. 파일은 소스셋마다 여러 벌 존재하지만, 패키지와 이름이 그 파일들을 하나의 논리적 선언으로 묶는다.

### 9.3 파일 구성이 곧 API 설계이다

파일과 패키지를 나누는 방식은 단순한 정리 정돈이 아니라 **API 설계 그 자체**이다. 최상위 함수를 어느 파일에 두는지에 따라 JVM에서 어느 파일 클래스에 담길지(Java 사용자에게 보이는 이름)가 정해진다. 어느 패키지에 두는지에 따라 import 경로와 FQN이 정해지고, `private`/`internal`/`public`을 어디에 붙이는지에 따라 외부에 노출되는 범위가 정해진다.

`@JvmMultifileClass`로 여러 파일을 하나의 API로 묶는 stdlib의 기법(5.3절)은 "소스는 잘게 나누고, API는 하나로 제공한다"는 설계 의도를 구현한 것이다. 즉 이 장의 내용은 문법의 세부 사항이 아니라, **코드를 읽는 사람과 호출하는 사람이 만나는 경계를 어떻게 설계할 것인가**에 관한 것이다.
