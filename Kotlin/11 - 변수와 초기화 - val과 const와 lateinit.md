[[10 - 불리언과 동등성과 동일성]]에서는 "값이 같다"는 것과 "같은 객체이다"라는 것을 구분했다. `==`는 `equals`로 구조를 비교하고 `===`는 참조가 같은지를 비교한다. 이 구분은 이 장의 주제와 바로 이어진다. **변수는 값을 담는 상자가 아니라 객체를 가리키는 이름표**이기 때문이다. 변수를 "고정한다"고 할 때 고정하는 것이 *이름표가 가리키는 대상*인지 *이름표 자체*인지를 혼동하면, 코틀린의 `val`을 근본부터 잘못 이해하게 된다.

이 장에서는 `val`과 `var`, 그 위에 붙는 한정자 `const`와 `lateinit`, 그리고 위임 `by lazy`를 JVM 수준까지 살펴본다. 변수 하나가 선언되고 초기화되어 사용되기까지 컴파일러와 런타임이 무엇을 보장하고 무엇을 뒤로 미루는지가 주제이다.

먼저 `val`과 `var`의 차이가 불변성이 아니라 재대입 가능성이라는 점을 확인하고, 코틀린이 확정 대입 분석(definite assignment)으로 초기화를 강제하는 방식을 본다. 이어서 클래스 프로퍼티에서 이 강제를 피하는 `lateinit`과 `by lazy`를 다루고, 마지막으로 초기화를 컴파일 시점으로 앞당기는 `const val`을 살펴본다.

프로퍼티의 백킹 필드(backing field) 규칙과 커스텀 접근자는 [[22 - 프로퍼티와 백킹 필드]]에서, 위임 프로퍼티의 일반 메커니즘은 [[23 - 위임 프로퍼티]]에서, 생성자와 `init` 블록의 초기화 순서는 [[21 - 클래스와 생성자]]와 [[24 - 상속과 오버라이딩과 초기화 순서]]에서 다룬다. [[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]에서 함수 파라미터가 모두 `val`처럼 재대입할 수 없는 이유도 이 장의 내용을 알아야 이해할 수 있다.

## 1. 두 개의 이름: `val`과 `var`, 그리고 재대입이라는 기준

### 1.1 문법이 아니라 "능력"을 선언한다

코틀린에서 이름을 선언하는 키워드는 `val`과 `var` 두 가지뿐이다. 자바는 `int x = 5;`처럼 타입을 앞에 쓰지만, 코틀린은 이름이 무엇을 할 수 있는지를 앞에 쓴다.

```kotlin
val radius = 5          // 타입 추론: Int
var counter = 0         // 타입 추론: Int

radius = 6              // 컴파일 에러: Val cannot be reassigned
counter = 1             // OK
```

`val`(value의 약자)은 **재대입할 수 없는(read-only, single-assignment)** 이름이다. 한 번 대입하면 그 이름에 다시 `=`로 다른 값을 연결할 수 없다. `var`(variable)는 몇 번이든 다시 대입할 수 있다. 자바 개발자라면 처음에는 `val`을 지역 변수 앞에 붙인 `final`로, `var`를 일반 변수로 생각해도 된다. 다만 이 대응이 어디까지 맞고 어디서부터 달라지는지가 이 장 내용의 절반을 차지한다.

핵심은 `val`과 `var`가 **변수가 가리키는 대상의 성질이 아니라, 그 이름을 다른 대상에 다시 연결할 수 있는지**를 나타낸다는 점이다. 이름과 대상을 나누어 보는 습관이 없으면 다음 절에서 다룰 오해를 피하기 어렵다.

### 1.2 코틀린이 `val`을 권장하는 이유

코틀린 스타일 가이드와 관례는 "가능하면 `val`을 쓰라"고 권한다. 이것은 단순한 취향 문제가 아니다. 재대입할 수 없는 이름은 **코드를 읽는 사람과 컴파일러 모두에게 불변식(invariant)을 제공한다.** 이 지점 이후로 이름이 가리키는 값이 바뀌지 않는다는 보장이 있으면, 코드를 읽을 때 값을 추적하는 부담이 줄어든다.

컴파일러는 이 보장을 근거로 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 다룰 스마트 캐스트(smart cast)를 안전하게 적용할 수 있다.

```kotlin
fun describe(shape: Any) {
    val s = shape
    if (s is String) {
        // s는 여기서 String으로 스마트 캐스트됨.
        // s가 val이라 중간에 바뀔 수 없으므로 컴파일러가 안심하고 좁힌다.
        println(s.length)   // => 정상
    }
}
```

만약 `s`가 `var`여서 어딘가에서 다시 대입될 수 있다면, 컴파일러는 `is String` 검사 뒤에도 값이 그대로라고 보장할 수 없으므로 스마트 캐스트를 거부했을 것이다. 즉 `val`은 실수를 막는 데 그치지 않고 **타입 시스템이 더 많이 추론할 수 있게 해 준다**. 스마트 캐스트가 언제나 적용되는 것은 아니라는 점은 6장(널 안전성)에서 자세히 다룬다.

> [!info] 역사 메모
> 자바는 2004년 `for-each`를 도입하면서 지역 변수에 `final`을 붙이는 것도 함께 권장했지만, 문법이 길고 기본값도 아니어서 실무에서는 잘 쓰이지 않았다. 코틀린은 두 키워드를 대등하게 두고 `val`을 먼저 가르쳐서 "불변을 기본으로 한다"는 문화를 언어 차원에서 밀어붙였다.
>
> 자바 10의 `var`(2018)는 방향이 반대이다. 자바의 `var`는 타입 추론을 위한 키워드이고 가변성과는 관계가 없다. **이름은 같아서 헷갈리지만, 코틀린 `var`와 자바 `var`는 서로 다른 기준을 나타낸다.**

### 1.3 함수 파라미터는 언제나 `val`이다

여기서 바로 따라 나오는 사실이 하나 있다. 코틀린 함수의 파라미터는 언제나 재대입할 수 없다. 파라미터에는 `val`이나 `var` 키워드를 붙일 수도 없다(붙이면 컴파일 에러가 난다).

```kotlin
fun grow(size: Int): Int {
    size = size + 1     // 컴파일 에러: Val cannot be reassigned
    return size
}
```

파라미터에 다시 대입할 수 있는 자바와는 확연히 다르다. 이 규칙 때문에 파라미터를 지역 임시 변수처럼 바꿔 가며 쓰는 습관이 처음부터 막힌다. 새 값이 필요하면 지역 `val`을 새로 만들라는 것이 코틀린의 방침이다. 이 규칙과 [[14 - 클로저와 캡처]]의 캡처 규칙을 함께 보면, 코틀린에서 람다가 파라미터를 캡처해도 안전한 이유를 설명할 수 있다. 자세한 내용은 12장(함수)에서 다룬다.

## 2. `val`은 불변이 아니다: 이름표와 객체의 분리

### 2.1 재대입할 수 없다는 것은 불변과 다르다

가장 널리 퍼진 오해부터 바로잡자. **`val`은 불변(immutable) 객체를 만들지 않는다. `val`은 이름을 다른 대상에 다시 연결하지 못하게 할 뿐이다.** 이름이 가리키는 객체의 내부는 얼마든지 바뀔 수 있다.

```kotlin
val numbers = mutableListOf(1, 2, 3)
numbers.add(4)              // => [1, 2, 3, 4]  — 컴파일 통과, 정상 동작
numbers[0] = 99            // => [99, 2, 3, 4]  — 원소 교체도 OK
println(numbers)            // => [99, 2, 3, 4]

numbers = mutableListOf()  // 컴파일 에러: Val cannot be reassigned
```

`numbers.add(4)`가 컴파일되는 것은 전혀 모순이 아니다. `add`는 `numbers`라는 이름을 건드리지 않고, `numbers`가 가리키는 *리스트 객체의 내부 상태*만 바꾼다. `val`이 금지하는 것은 마지막 줄뿐이다. 즉 `numbers`라는 이름에 *다른 리스트*를 다시 연결하는 동작만 막는다.

메모리 그림으로 보면 분명해진다.

```text
val numbers ─────► [ MutableList 객체 ]
   (이름표 고정)        내부: 1,2,3,4  ← 이 안은 자유롭게 변함

금지되는 것:  numbers ──✗──► [ 다른 리스트 ]   (이름표 재부착 금지)
허용되는 것:  numbers ──────► [ 같은 리스트, 내용만 바뀜 ]  (객체 내부 변형 OK)
```

### 2.2 배열, 객체, 프로퍼티에서도 마찬가지이다

같은 원리가 배열과 사용자 정의 클래스에도 적용된다.

```kotlin
val coords = intArrayOf(0, 0)
coords[0] = 10             // => [10, 0]  — 배열 원소 대입 OK

class Account(var balance: Long)
val acc = Account(1000)
acc.balance = 2000         // OK — 객체의 var 프로퍼티는 여전히 가변
// acc = Account(0)        // 컴파일 에러 — 이름표 acc는 못 바꿈
```

`acc`는 `val`이지만 `acc.balance`는 `var` 프로퍼티이므로 값이 바뀐다. `val acc`가 고정한 것은 "`acc`가 이 계좌 객체를 가리킨다"는 사실이지, "이 계좌의 잔고가 영원히 그대로이다"라는 사실이 아니다. 진짜 불변 객체가 필요하다면 객체 *안의 프로퍼티를 모두 `val`로 만들고 가변 컬렉션을 외부에 노출하지 않아야* 한다. 언어가 이름 하나만으로 이것을 해 주지는 않는다.

> [!warning] 흔한 오해
> "`val`이면 스레드 안전하다"는 생각도 같은 데서 나온 오해이다. `val`은 재대입만 막으므로, `val`이 가리키는 가변 객체를 여러 스레드가 동시에 변경하면 여전히 데이터 경합이 생긴다. 스레드 안전성은 불변 객체를 쓰거나 동기화를 해야 확보할 수 있다. 이 내용은 [[43 - 동시성과 메모리 모델]]에서 다룬다.

### 2.3 진짜 불변이 필요하다면: 방어적 복사

`val`이 불변을 보장하지 않으므로, 진짜 불변이 필요하면 개발자가 직접 만들어야 한다. 대표적인 기법이 **방어적 복사(defensive copy)** 이다. 생성자로 받은 가변 컬렉션을 그대로 저장하면, 바깥에 남아 있는 참조를 통해 내용이 바뀔 수 있다.

```kotlin
class Polygon(points: List<Point>) {
    // 위험: 밖의 리스트를 그대로 참조
    val vertices: List<Point> = points
    // 안전: 받은 시점의 내용을 복사해 소유
    val safeVertices: List<Point> = points.toList()
}

val input = mutableListOf(Point(0, 0), Point(1, 1))
val poly = Polygon(input)
input.add(Point(9, 9))          // 밖에서 리스트를 변형
println(poly.vertices.size)     // => 3  (위험한 쪽은 영향받음!)
println(poly.safeVertices.size) // => 2  (복사한 쪽은 무사)
```

`vertices`가 `val`인데도 크기가 2에서 3으로 바뀐 것처럼 *보이는* 이유는 `vertices`가 바깥의 `input`과 **같은 객체를 공유**하기 때문이다. `val`은 `vertices`라는 이름을 고정했을 뿐, 그 객체의 내용을 지켜 주지 않는다. `toList()`로 복사본을 만들어 따로 가지고 있어야 바깥의 변경으로부터 격리된다.

방어적 복사와 읽기 전용 뷰의 미묘한 차이는 [[38 - 컬렉션 - 읽기 전용과 가변]]에서 자세히 다룬다. 이 장에서 얻을 교훈은 "`val`은 불변을 만드는 출발점일 뿐, 그것만으로 불변이 완성되지는 않는다"는 것이다.

### 2.4 읽기 전용 컬렉션 타입과의 관계

그렇다면 정말 바꿀 수 없는 컬렉션은 어떻게 얻을까? 코틀린은 타입 수준에서 `List`(읽기 전용 인터페이스)와 `MutableList`(가변)를 구분한다.

```kotlin
val readOnly: List<Int> = listOf(1, 2, 3)
// readOnly.add(4)   // 컴파일 에러: add는 List에 없음 (MutableList에만)
```

여기서 값을 바꿀 수 없는 이유는 `val` 때문이 아니라, **타입이 `List`여서** 변경 메서드가 아예 없기 때문이다. `val`과 `List`는 서로 독립된 두 기준이다. 게다가 이것도 "불변"을 완전히 보장하지는 않는다. 같은 객체를 가리키는 `MutableList` 참조가 어딘가에 있으면 내용이 바뀔 수 있기 때문이다.

이 미묘한 부분은 38장(컬렉션 읽기 전용과 가변)에서 자세히 다룬다. 이 장에서 기억할 것은 하나이다. **가변성은 이름(`val`/`var`)과 타입(`List`/`MutableList`)이라는 두 기준의 조합으로 결정되며, `val` 하나만으로는 불변이 만들어지지 않는다.**

## 3. 초기화 강제: 코틀린에는 "빈 변수"가 없다

### 3.1 변수는 사용하기 전에 값이 있어야 한다

자바에서는 `int x;`처럼 값 없이 선언해 두고 나중에 채우는 코드를 흔히 쓴다. 코틀린의 기본 방침은 정반대이다. **변수는 사용하기 전에 반드시 값을 가지고 있어야 한다.** 아래 코드는 겉보기에는 자바와 비슷하지만 코틀린에서는 대개 컴파일되지 않는다.

```kotlin
fun demo() {
    val x: Int
    println(x)          // 컴파일 에러: Variable 'x' must be initialized
}
```

여기서 흔한 오해 하나를 먼저 정리하자. 자바 필드에는 "타입별 기본값"(int는 0, 참조는 null)이 있지만, 코틀린의 지역 변수와 멤버 초기화 규칙에는 이런 개념이 없다. 개발자가 초기값을 명시하지 않으면 컴파일러가 통과시키지 않는다(단, 클래스 프로퍼티는 초기화 없이 선언하는 것 자체가 불가능하다. 이 내용은 3.3절에서 본다). 이 강제 덕분에 자바에서 악명 높은 "초기화하지 않은 변수를 실수로 읽는" 종류의 버그가 언어 차원에서 사라진다.

### 3.2 확정 대입 분석: 초기화를 미룰 수 있는 경우

그렇다고 3.1절의 규칙이 "선언과 대입을 반드시 한 줄에 써야 한다"는 뜻은 *아니다*. 코틀린 컴파일러는 **확정 대입 분석(definite assignment analysis)** 을 수행한다. 즉 이 변수를 읽는 모든 실행 경로에서 읽기 전에 값이 대입되었는지를 제어 흐름을 따라 추적한다. 모든 경로가 이 조건을 만족하면 선언과 대입이 떨어져 있어도 컴파일된다.

```kotlin
fun classify(score: Int): String {
    val grade: String           // 선언만 — 아직 값 없음
    if (score >= 90) {
        grade = "A"             // 경로 1에서 대입
    } else {
        grade = "B"             // 경로 2에서 대입
    }
    return grade                // 두 경로 모두 대입됐으므로 읽기 OK
}
```

`grade`는 `val`이지만 선언할 때 대입하지 않았다. 그래도 컴파일되는 이유는 `if`/`else`의 **모든 분기가 정확히 한 번씩** `grade`에 대입하고, `return`에서 읽기 전에 대입이 반드시 끝나기 때문이다. 이것을 "지연 초기화(deferred initialization)"라고 한다. 각 경로에서 딱 한 번씩만 대입하므로 `val`의 "single-assignment(단 한 번 대입)" 규칙과도 충돌하지 않는다.

어떤 경로에서 대입을 빠뜨리면 바로 에러가 난다.

```kotlin
fun broken(flag: Boolean): Int {
    val n: Int
    if (flag) {
        n = 1
    }
    return n     // 컴파일 에러: Variable 'n' must be initialized
                 // (flag가 false인 경로에서 n이 대입되지 않음)
}
```

반대로 `val`에 한 번 대입한 뒤 다른 경로에서 또 대입하면 "두 번 대입"이 되므로 이것도 막힌다.

```kotlin
fun twice(flag: Boolean) {
    val n: Int
    n = 1
    if (flag) {
        n = 2    // 컴파일 에러: Val cannot be reassigned
    }
}
```

> [!note] 명세 기준
> 확정 대입 분석은 코틀린 언어가 수행하는 제어 흐름 분석(control-flow analysis)의 일부이다. `if`/`when`/`try`뿐 아니라 `throw`나 반환이 있는 경로도 함께 고려한다. 예를 들어 어떤 분기가 예외를 던지면, 그 분기는 정상적으로 이후 코드에 도달하지 않으므로 대입 의무에서 면제된다.
>
> 이 규칙은 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서 다루는 바닥 타입 `Nothing`과 직접 연결된다. `throw`나 `return`의 타입이 `Nothing`이므로, 컴파일러는 그 지점 이후에 도달할 수 없다는 사실을 타입으로 알 수 있다.

```kotlin
fun withThrow(x: Int): String {
    val label: String
    when {
        x > 0 -> label = "positive"
        x < 0 -> label = "negative"
        else  -> throw IllegalArgumentException("zero")
        // else 분기는 Nothing으로 끝나므로 label 대입 의무 면제
    }
    return label    // OK — 도달하는 모든 경로에서 label이 대입됨
}
```

### 3.3 지역 변수와 클래스 프로퍼티: 규칙이 달라지는 지점

여기에 중요한 경계가 있다. 지금까지 본 "선언만 하고 나중에 대입하는" 방식은 **지역 변수**에서 특히 유연하다. 반면 **클래스 프로퍼티**(멤버 `val`/`var`)의 규칙은 더 엄격하다. 프로퍼티는 원칙적으로 선언한 자리에서 초기화하거나, `init` 블록이나 주 생성자 안에서 대입해야 한다.

```kotlin
class Circle(radius: Double) {
    val area: Double            // 프로퍼티 선언
    init {
        area = Math.PI * radius * radius   // init 블록에서 대입 — OK
    }
}
```

프로퍼티를 어디에서도 초기화하지 않고 생성자가 끝나면 컴파일 에러가 난다. 초기화 순서(주 생성자 → 프로퍼티 초기화자 → `init` 블록)의 자세한 규칙은 21장(클래스와 생성자)에서, 상속이 얽힐 때 생기는 함정은 24장(상속과 오버라이딩과 초기화 순서)에서 다룬다.

"프로퍼티는 객체를 생성할 때 초기화가 끝나야 한다"는 이 엄격함은 실무에서 마찰을 일으킨다. 의존성 주입, 프레임워크 콜백, 테스트의 `@BeforeEach` 같은 상황에서는 값이 객체를 만든 *직후*가 아니라 *조금 뒤*에 도착한다.

타입을 nullable로 두면 `null`로 시작했다가 나중에 채울 수 있다. 하지만 그러면 널이 아니어야 할 프로퍼티가 억지로 `T?`가 되어, 사용하는 곳마다 `?.`나 `!!`를 붙여야 한다. **이 딜레마를 해결하려고 도입된 것이 다음 절의 `lateinit`이다.**

### 3.4 확정 대입과 예외: try/catch의 미묘한 점

확정 대입 분석은 `try`/`catch`에서 특히 조심스럽게 동작한다. 대입 직전에 예외가 날 수 있으므로, `try` 블록 안의 대입이 성공적으로 끝났다고 장담할 수 없기 때문이다.

```kotlin
fun parse(text: String): Int {
    val n: Int
    try {
        n = text.toInt()       // 여기서 예외 가능
    } catch (e: NumberFormatException) {
        n = -1                  // catch에서 대입
    }
    return n                    // OK — try 성공 또는 catch, 두 경로 모두 대입
}
```

이 코드가 컴파일되는 이유는 `try`가 정상적으로 끝나면 `n`이 대입되고, 예외가 나면 `catch`에서 `n`에 대입하기 때문이다. 두 경로 모두 `n`을 채운다. 그러나 `catch`에서 대입을 빠뜨리면 컴파일러는 예외 경로에서 `n`이 대입되지 않았다고 지적한다. 코틀린의 `try`가 표현식이라는 점([[41 - 예외와 Nothing]])을 이용하면 더 깔끔하게 쓸 수 있다.

```kotlin
fun parseCleaner(text: String): Int {
    val n = try { text.toInt() } catch (e: NumberFormatException) { -1 }
    return n     // try 표현식의 값이 곧 n — 한 번 대입, 지연 없음
}
```

`try`를 표현식으로 쓰면 두 분기가 모두 값을 내므로, `val n`을 선언하면서 바로 대입할 수 있다. 확정 대입을 신경 쓸 필요가 처음부터 없어진다. 예외와 제어 흐름은 41장(예외와 Nothing)에서 자세히 다룬다.

## 4. `lateinit`: 널이 아닌 프로퍼티의 초기화를 미루기

### 4.1 lateinit은 nullable이 아니다

흔한 오해를 바로잡자. **`lateinit`은 "나중에 초기화하니까 결국 nullable"이라는 뜻이 아니다. `lateinit`은 *널이 아닌(non-null)* 타입 프로퍼티의 초기화 시점을 뒤로 미루겠다는 약속이다. 그 대가로 널 안전성 검사의 일부가 컴파일 타임에서 런타임으로 옮겨 간다.**

```kotlin
class Server {
    lateinit var config: Config      // 타입은 Config — nullable(Config?) 아님!

    fun boot() {
        config = loadConfig()        // 나중에 채움
    }

    fun handle() {
        // config는 Config로 취급 — ?. 나 !! 없이 그냥 사용
        println(config.port)
    }
}
```

`config`의 타입은 `Config`이고 `Config?`가 아니다. 그래서 사용하는 곳에서 `config.port`를 널 검사 없이 쓸 수 있으며, 이것이 `lateinit`을 쓰는 이유이다. nullable로 선언했다면 매번 `config?.port`나 `config!!.port`를 써야 했을 것이다. `lateinit`은 "이 값은 논리적으로 절대 null이 아니다. 다만 생성자가 실행되는 시점에는 아직 없을 뿐이다"라는 개발자의 선언이다.

### 4.2 초기화하기 전에 접근하면: NPE가 아니다

`lateinit`의 대가는 분명하다. 값을 채우기 *전에* 읽으면 실패한다. 다만 이때 나는 예외는 `NullPointerException`이 아니라 전용 예외이다.

```kotlin
class Server {
    lateinit var config: Config
    fun handle() = println(config.port)
}

Server().handle()
// => 런타임 예외: kotlin.UninitializedPropertyAccessException:
//    lateinit property config has not been initialized
```

왜 `UninitializedPropertyAccessException`이라는 별도의 예외를 쓸까? 이 점이 `lateinit`을 이해하는 핵심이다. `config`가 실제로 `Config?`였다면 초기화하기 전의 값은 `null`이고, `config.port`에 접근하면 `NullPointerException`이 났을 것이다. 하지만 `lateinit` 프로퍼티의 타입은 널이 아닌 `Config`이다.

개념적으로 "아직 값이 없다"와 "값이 null이다"는 서로 다른 상태이다. 코틀린은 두 상태를 구별해서 **"초기화되지 않음"이라는 별도의 오류 범주**로 알린다. 예외 이름 자체가 "이것은 널 문제가 아니라 초기화 순서 문제이다"라고 알려 주는 셈이다.

> [!note] 명세 기준: JVM 백엔드
> JVM 백엔드에서 `lateinit var`는 내부적으로 nullable 필드로 컴파일되고, 초기화 여부는 필드가 `null`인지로 판별한다. 즉 접근자(게터)가 필드를 읽어 `null`이면 `UninitializedPropertyAccessException`을 던지도록 컴파일된다.
>
> 다음 절에서 볼 원시 타입 제약도 여기서 생긴다. `null`을 센티넬(sentinel)로 쓰려면 필드가 참조 타입이어야 하기 때문이다. 이것은 JVM 구현의 세부 사항이며, 다른 백엔드에서는 표현 방식이 다를 수 있다.

### 4.3 lateinit의 제약: 쓸 수 없는 곳

`lateinit`은 아무 곳에나 붙일 수 없다. 제약을 이해하면 `lateinit`이 무엇인지 더 분명해진다.

| 제약 | 이유 |
|------|------|
| `var`에만 (❌ `val`) | 나중에 대입해야 하므로 재대입이 가능해야 함 |
| 널이 아닌 타입에만 (❌ `Int?`, `String?`) | nullable이면 처음부터 `null`로 시작하면 되므로 lateinit이 필요 없음 |
| 원시 타입 불가 (❌ `Int`, `Long`, `Double`, `Boolean`) | JVM 백엔드에서 null 센티넬을 쓸 수 없음 |
| 커스텀 게터/세터가 있으면 불가 | lateinit은 컴파일러가 접근자를 생성해 초기화 검사를 넣음 |

```kotlin
class Bad {
    lateinit val x: String    // 컴파일 에러: 'lateinit' modifier is not allowed on 'val'
    lateinit var n: Int       // 컴파일 에러: 'lateinit' modifier is not allowed on primitives
    lateinit var s: String?   // 컴파일 에러: 'lateinit' modifier is not allowed on nullable
}
```

원시 타입을 꼭 지연 초기화해야 한다면 `Int?`로 선언하거나 `Delegates.notNull()`(다음 절과 23장 위임 프로퍼티 참고) 같은 대안을 쓴다. `lateinit`은 참조 타입 프로퍼티를 위한 도구이다. 참고로 `lateinit`은 클래스 멤버뿐 아니라 **최상위 프로퍼티와 지역 변수에도** 쓸 수 있다(코틀린 1.2부터). 다만 실무에서는 압도적으로 클래스 멤버에 많이 쓴다.

### 4.4 초기화 여부 확인: `::x.isInitialized`

값이 채워졌는지를 접근하기 전에 알고 싶을 때가 가끔 있다. 코틀린은 이를 위한 특수 문법을 제공한다.

```kotlin
class Cache {
    lateinit var data: Map<String, Int>

    fun getOrEmpty(): Map<String, Int> =
        if (::data.isInitialized) data else emptyMap()
    //     ^^^^^^^^^^^^^^^^^^^^^ lateinit 프로퍼티에만 쓸 수 있는 검사
}
```

`::data.isInitialized`는 프로퍼티 참조에 붙는 특수 프로퍼티로, `lateinit` 프로퍼티가 채워졌는지를 `true`/`false`로 알려 준다. 이 검사는 접근할 수 있는 스코프 안(같은 클래스 내부, 또는 `this::data`나 바깥 클래스에서 접근할 수 있는 경우)에서만 쓸 수 있다. 아무 곳에서나 다른 객체의 `lateinit` 상태를 들여다볼 수는 없다.

> [!caution] 성능 주의
> 접근할 때마다 방어적으로 `::x.isInitialized`로 감싸는 코드는 좋지 않은 신호이다. `lateinit`은 "초기화가 반드시 먼저 일어난다"는 계약을 스스로 정한 도구이다. 매번 초기화 여부를 검사해야 한다면 애초에 값이 있을 수도 없을 수도 있다는 뜻이다. 그럴 때는 솔직하게 `T?`(nullable)로 모델링해야 타입이 실제 상황을 드러낸다.
>
> `isInitialized`는 프레임워크 통합 같은 경계에서 예외적으로 쓰는 안전망이지, 습관적으로 쓸 도구가 아니다.

### 4.5 lateinit을 쓸 곳과 피할 곳

`lateinit`이 잘 맞는 전형적인 경우는 다음과 같다.

- 의존성 주입 프레임워크가 객체를 생성한 뒤 필드를 채우는 경우
- 테스트에서 `@BeforeEach`가 픽스처를 준비하는 경우
- 안드로이드나 UI 프레임워크가 `onCreate` 콜백에서 뷰를 바인딩하는 경우

공통점은 **"생성자에서는 값을 줄 수 없지만, 처음 사용하기 전에는 반드시 채워진다"는 외부 계약이 확실하다**는 것이다.

반대로 피해야 할 경우도 있다. 값이 조건에 따라서만 존재하는 경우(→ nullable), 원시 수치(→ `Int?` 또는 `notNull`), 그리고 특히 **"비용이 커서 나중에 계산하고 싶은 경우"** 이다. 마지막 경우에는 `lateinit`이 아니라 다음 절의 `by lazy`를 써야 한다. `lateinit`은 바깥에서 값을 밀어 넣는(push) 모델이고, `by lazy`는 처음 읽힐 때 스스로 계산하는(pull) 모델이다.

## 5. `by lazy`: 처음 읽힐 때 계산하기

### 5.1 또 다른 방식의 지연 계산

`lateinit`이 "누군가 값을 대입해 줄 때까지 미루는" 방식이라면, `by lazy`는 "처음 접근하는 순간 람다를 실행해 값을 만들고, 그 뒤로는 그 값을 재사용하는" 위임 프로퍼티이다. 여기서는 초기화라는 관점에서 두 방식을 비교만 하고, 위임 메커니즘 자체는 23장(위임 프로퍼티)에서 다룬다.

```kotlin
class Report {
    val summary: String by lazy {
        println("계산 중...")     // 이 블록은 최초 접근 때 단 한 번만 실행
        expensiveComputation()
    }
}

val r = Report()
// 아직 "계산 중..." 안 찍힘 — summary를 읽지 않았으므로
println(r.summary)  // => 계산 중...  (여기서 처음 실행) 그리고 결과 출력
println(r.summary)  // => (계산 없이) 캐시된 결과만 출력
```

핵심 차이는 두 가지이다. 첫째, `by lazy`는 **`val`에 쓴다**(값이 한 번 만들어지면 고정된다). `lateinit`은 `var`에 쓴다. 둘째, `by lazy`는 **초기화 로직을 프로퍼티가 직접 가지고 있다**. 값을 바깥에서 받지 않고 스스로 계산한다. 그래서 `by lazy`는 원시 타입에도(`val n: Int by lazy { compute() }`), nullable 타입에도 쓸 수 있다. `lateinit`의 제약이 여기에는 없다.

### 5.2 스레드 안전성 모드

`lazy`에서는 여러 스레드가 동시에 처음 접근할 때의 동작을 모드로 고를 수 있다.

```kotlin
val a: Int by lazy { compute() }                              // 기본: SYNCHRONIZED
val b: Int by lazy(LazyThreadSafetyMode.PUBLICATION) { compute() }
val c: Int by lazy(LazyThreadSafetyMode.NONE) { compute() }
```

- `SYNCHRONIZED`(기본): 락으로 보호한다. 여러 스레드가 동시에 접근해도 초기화 람다는 정확히 한 번만 실행된다. 가장 안전하지만 락 비용이 든다.
- `PUBLICATION`: 여러 스레드가 동시에 람다를 실행할 수는 *있지만*, 가장 먼저 값을 정해 게시(publish)한 결과가 채택되고 나머지는 버려진다. 초기화에 부작용이 없고 결과 값이 같다면 유용하다.
- `NONE`: 동기화를 전혀 하지 않는다. 단일 스레드에서만 접근한다는 것이 보장될 때 가장 빠르다. 멀티스레드에서 쓰면 동작이 정의되지 않는다.

> [!caution] 성능 주의
> 단일 스레드 환경(예: UI 스레드에서만 쓰는 객체)에서 `by lazy`를 남발하면 기본 모드인 `SYNCHRONIZED`의 락 비용이 불필요하게 붙는다. 단일 스레드가 확실하다면 `LazyThreadSafetyMode.NONE`을 명시하는 편이 의도가 분명하고 빠르다.
>
> 다만 "확실히 단일 스레드"라는 판단이 틀리면 경합 버그가 생기므로, 애매하다면 기본값을 유지하라. 메모리 모델과 게시(publication)의 정확한 의미는 43장(동시성과 메모리 모델)에서 다룬다.

### 5.3 초기화가 실패하면: 예외는 어떻게 처리되는가

`by lazy`의 초기화 람다가 예외를 던지면 어떻게 될까? 모드에 따라 미묘하게 다르지만, 실무에서는 기본 `SYNCHRONIZED`와 `PUBLICATION`의 표준 동작을 이해하는 것이 중요하다.

```kotlin
class Flaky {
    var attempts = 0
    val value: String by lazy {
        attempts++
        if (attempts < 2) throw IllegalStateException("first attempt fails")
        "success"
    }
}

val f = Flaky()
runCatching { f.value }        // 1번째 접근: 예외 발생, 값 미확정
println(f.value)               // 2번째 접근: 다시 람다 실행 → => success
println(f.attempts)            // => 2  (람다가 두 번 실행됨)
```

기본 모드에서 초기화 람다가 예외를 던지면 값이 확정되지 않고, **다음에 접근할 때 람다가 다시 실행된다.** 즉 성공할 때까지 재시도한다. "한 번 성공하면 그 값을 계속 캐시하되, 실패는 확정하지 않는다"는 합리적인 설계이다. 다만 람다가 다시 실행될 수 있으므로, 초기화 람다는 **여러 번 실행되어도 안전하도록(부작용을 최소화해서)** 작성하는 것이 좋다.

> [!note] 명세 기준
> 위의 재시도 동작은 `SynchronizedLazyImpl`, `SafePublicationLazyImpl` 등 표준 `Lazy` 구현에서 관찰되는 계약이다. 정확한 세부 사항(예외를 캐시하는지 여부)은 구현이나 버전에 따라 달라질 수 있다. 따라서 "초기화가 반드시 딱 한 번 일어난다"는 강한 가정에 의존하는 코드는 피하고, 멱등(idempotent)하게 작성하는 편이 안전하다. 위임 구현의 내부는 23장(위임 프로퍼티)에서 다룬다.

### 5.4 lateinit과 by lazy 중 무엇을 쓸까

| 기준 | `lateinit var` | `val ... by lazy { }` |
|----|----------------|------------------------|
| 이름 종류 | `var` (재대입 가능) | `val` (한 번 고정) |
| 값의 출처 | 바깥에서 대입(push) | 스스로 계산(pull) |
| 초기화 시점 | 개발자가 대입하는 순간 | 처음 읽는 순간(자동) |
| nullable 가능? | ❌ 널이 아닌 타입만 | ✅ 가능 |
| 원시 타입 가능? | ❌ (JVM 백엔드) | ✅ 가능 |
| 초기화 전 접근 | `UninitializedPropertyAccessException` | (개념상 발생하지 않음, 접근하면 곧 초기화됨) |
| 값 교체 | 가능(재대입) | 불가 |
| 스레드 안전 | 없음(직접 관리) | 모드로 선택 가능 |
| 전형적인 용도 | DI, 콜백, 테스트 픽스처 | 비용이 큰 계산의 지연과 캐시 |

두 도구의 차이를 한 문장으로 정리하면 이렇다. **바깥에서 값이 채워지기를 기다린다면 `lateinit`, 처음 필요할 때 스스로 만든다면 `by lazy`이다.** 이 기준만 있으면 실무에서 마주치는 선택은 대부분 쉽게 정해진다.

## 6. `const val`: 초기화를 컴파일 시점으로 앞당기기

### 6.1 const val은 그냥 val이 아니다

이제 지금까지와 정반대 방향으로 동작하는 장치를 살펴본다. 4절과 5절의 도구가 초기화를 *뒤로* 미뤘다면, `const`는 초기화를 실행 이전인 컴파일 시점으로 *앞당긴다*. 흔한 오해를 바로잡자. **`const val`과 `val`은 같지 않다. `const val`은 *컴파일 타임 상수(compile-time constant)* 이며, 그 값은 컴파일 시점에 완전히 정해지고 사용하는 곳마다 값 자체가 인라인된다.**

```kotlin
const val MAX_RETRIES = 3
const val PI_APPROX = 3.14159
const val GREETING = "hello"

val runtimeValue = computeSomething()   // 일반 val — 실행 시점에 결정
```

`const val`은 "이 이름은 컴파일러가 지금 바로 값을 알 수 있는 진짜 리터럴 상수이다"라는 선언이다. 반면 일반 `val`은 재대입만 할 수 없을 뿐, 그 값은 `computeSomething()`의 결과처럼 실행 중에 정해질 수 있다. 둘의 차이는 "값이 언제 정해지는가"라는 시간 기준에 있다.

### 6.2 const val의 엄격한 조건

`const`는 아무 `val`에나 붙일 수 없다. 컴파일 타임에 값이 완전히 정해져야 하므로 조건이 엄격하다.

```kotlin
// ✅ 허용
const val A = 42                    // 최상위, 리터럴
const val B = "circle"              // String 리터럴
const val C = A + 1                 // 다른 const로 이뤄진 컴파일 타임 상수식

object Config {
    const val TIMEOUT = 30          // object 멤버 OK
}

class Limits {
    companion object {
        const val MAX = 100         // companion object 멤버 OK
    }
}

// ❌ 불가
const val D = readLine()            // 컴파일 에러: 런타임에 결정되는 값
const val E: Double = Math.sqrt(2.0)// 컴파일 에러: 함수 호출 결과는 상수 아님
val obj = object {}
// const val F = 1                  // (일반 클래스 본문의 인스턴스 멤버엔 불가)
```

조건을 정리하면 다음과 같다.

1. **타입은 원시 타입이나 `String`** 이어야 한다(`Int`, `Long`, `Double`, `Float`, `Boolean`, `Char`, `Byte`, `Short`, `String`). 임의의 객체나 컬렉션은 쓸 수 없다.
2. **위치는 최상위(top-level)이거나 `object`/`companion object`의 멤버**여야 한다. 일반 클래스의 인스턴스 프로퍼티에는 붙일 수 없다. 인스턴스마다 값이 달라질 여지가 없어야 하므로 클래스 인스턴스에 묶이면 안 되기 때문이다.
3. **초기값은 컴파일 타임 상수식**이어야 한다. 즉 리터럴이거나, 다른 `const val`로 이루어진 상수 산술식이나 문자열 결합이어야 한다.
4. **커스텀 게터와 위임을 쓸 수 없다**. `const`는 접근자 없이 값 그 자체이다.

> [!note] 명세 기준
> 왜 `object`/`companion` 멤버에는 쓸 수 있고 일반 클래스의 인스턴스 멤버에는 쓸 수 없을까? `const`는 인스턴스에 묶이지 않는 정적 상수여야 의미가 있다. `object`와 `companion object`는 인스턴스가 하나뿐인 싱글턴이므로, 그 멤버 상수를 "정적 상수"로 취급할 수 있다.
>
> 반면 일반 클래스는 인스턴스가 여러 개일 수 있어서 "컴파일 타임에 고정된 하나의 값"이라는 개념과 충돌한다. `object`와 `companion`이 무엇인지는 [[28 - object와 companion - 싱글턴과 동반 객체]]에서 다룬다.

### 6.3 const는 어디에 저장되고 무엇이 인라인되는가

`const`가 실제로 어떻게 동작하는지는 바이트코드를 보면 드러난다. JVM 백엔드에서 `const val`은 두 가지 효과를 낸다.

```kotlin
const val MAX_RETRIES = 3

fun retry() {
    for (i in 0 until MAX_RETRIES) { /* ... */ }
}
```

```text
JVM 백엔드에서 대략:
- MAX_RETRIES는 클래스 파일에 'public static final int MAX_RETRIES = 3'
  필드로 남되, ConstantValue 속성으로 값 3이 상수 풀에 박힌다.
- 그리고 retry()를 컴파일할 때, MAX_RETRIES 참조 자리에
  필드 읽기(getstatic)가 아니라 "리터럴 3"이 직접 인라인된다.

즉 retry()의 바이트코드에는 MAX_RETRIES라는 심볼이 사라지고 상수 3만 남는다.
```

이 인라인이 `const val`의 핵심이면서, 실무에서 함정이 생기는 원인이기도 하다. 일반 `val`은 사용하는 곳에서 필드를 읽어 오지만(`getstatic` + 게터 호출), `const val`은 **값이 사용하는 곳에 복사되어 들어간다.**

> [!caution] 성능 주의: 라이브러리 함정
> `const`의 인라인은 성능에는 좋지만 **바이너리 호환성**에서는 함정이 된다. 라이브러리 A가 `const val VERSION = 1`을 공개하고 앱 B가 이를 참조해 컴파일하면, 값 `1`이 B의 바이트코드에 *복사되어 들어간다*. 그 뒤 A만 `VERSION = 2`로 고쳐 다시 배포해도, B를 다시 컴파일하지 않으면 B는 여전히 예전 값 `1`을 쓴다.
>
> 일반 `val`이었다면 B가 실행할 때 A의 필드를 읽으므로 새 값을 보았을 것이다. 그래서 값이 바뀔 수 있는 API 상수에는 `const`가 오히려 위험하고, 절대 바뀌지 않는 진짜 상수에만 `const`가 알맞다.

### 6.4 const만 할 수 있는 것: 애노테이션 인자

`const`가 단순한 최적화 이상의 역할을 하는 결정적인 자리는 **애노테이션 인자**이다. 애노테이션의 인자는 컴파일 타임에 알려져야 하므로, 일반 `val`은 쓸 수 없고 `const val`만 쓸 수 있다.

```kotlin
const val API_PATH = "/v1/resource"

@Deprecated("Use $API_PATH instead")   // const라서 애노테이션 인자로 사용 가능
fun oldApi() { /* ... */ }

// 만약 API_PATH가 const가 아닌 일반 val이었다면:
// 컴파일 에러: An annotation argument must be a compile-time constant
```

`when`의 상수 분기, 애노테이션 인자, 그 밖에 컴파일 타임에 값이 필요한 모든 자리에서는 `const`를 다른 것으로 대체할 수 없다. 애노테이션은 [[44 - 애노테이션과 리플렉션]]에서 자세히 다룬다.

### 6.5 val과 const val 비교

| 기준 | `val x = ...` | `const val x = ...` |
|----|---------------|----------------------|
| 값 결정 시점 | 런타임(실행 중) | 컴파일 타임 |
| 허용 타입 | 임의 타입 | 원시 타입 + `String`만 |
| 위치 | 어디든(지역·멤버·최상위) | 최상위·`object`·`companion`만 |
| 초기값 | 임의 표현식·함수 호출 | 컴파일 타임 상수식만 |
| 커스텀 게터 | 가능 | 불가 |
| 사용처 표현(JVM) | 필드 읽기 | 값이 인라인(복사)됨 |
| 애노테이션 인자 | 불가 | 가능 |
| 값 변경 시 재컴파일 | 참조하는 쪽은 불필요 | 참조하는 쪽도 재컴파일 필요(안 하면 예전 값) |

한 문장으로 정리하면 이렇다. **`const val`은 재대입할 수 없을 뿐 아니라, 컴파일 타임에 값이 확정되어 사용하는 곳에 인라인되는 상수이다. 일반 `val`은 재대입할 수 없는 런타임 값일 뿐이다.**

### 6.6 자바의 final, static final과 비교

자바 개발자라면 이 세 도구를 자바 문법과 짝지어 두면 오해가 줄어든다. 다만 완전히 일대일로 대응하지는 않는다.

```java
// Java
final int x = compute();            // 지역 final ≈ 코틀린 지역 val
static final int MAX = 3;           // static final ≈ 코틀린 const val (상수 인라인 유사)
static final List<Integer> L = ...; // static final 참조 — 그러나 리스트 내용은 가변!
```

| 자바 | 코틀린 대응 | 주의 |
|------|-------------|------|
| 지역 `final T x` | `val x` | 거의 같다. 재대입할 수 없다. |
| 인스턴스 `final` 필드 | 멤버 `val` (JVM에서 final 필드) | 거의 같다. |
| `static final` 원시/String | `const val` | 자바에서도 원시 타입과 String의 `static final`은 상수로 인라인된다(JLS 13장 바이너리 호환성). 함정도 같다. |
| `static final` 객체 참조 | 최상위/companion `val` | `const`를 쓸 수 없다(원시 타입이나 String이 아님). 인라인되지 않는다. |

자바의 `static final int/String`이 사용하는 곳에 인라인되는 것과 코틀린 `const val`의 인라인은 사실상 같은 현상이다. "값을 바꿔도 참조하는 쪽을 다시 컴파일하지 않으면 예전 값이 남는다"는 함정(6.3절)도 자바에서 물려받은 것이다.

**중요한 공통점은 자바의 `final`이 가리키는 객체의 불변을 전혀 보장하지 않는 것처럼, 코틀린 `val`도 이를 보장하지 않는다는 점이다.** 두 언어 모두에서 "이름 고정"과 "객체 불변"을 혼동하면 안 된다. 자바 상호운용 전반은 [[45 - Java 상호운용]]에서 다룬다.

### 6.7 const가 아닌 val: 커스텀 게터로 매번 계산하기

비교할 것이 하나 더 있다. `const val`은 값이 고정되고 인라인되지만, **커스텀 게터가 있는 `val`은 접근할 때마다 다시 계산된다**. 똑같이 `val`이지만 성격은 정반대이다.

```kotlin
class Clock {
    val now: Long                      // val이지만...
        get() = System.currentTimeMillis()   // ...접근마다 새 값!
}

val c = Clock()
println(c.now)   // => 예: 1000
Thread.sleep(10)
println(c.now)   // => 예: 1010  (val인데 값이 "바뀐 것처럼" 보임)
```

`now`는 `val`이어서 재대입할 수 없지만, 커스텀 게터가 있으므로 백킹 필드가 없고(22장 프로퍼티와 백킹 필드) 접근할 때마다 게터를 호출한다. 그래서 읽을 때마다 다른 값이 나올 수 있다. 여기서 `val`은 "저장된 불변 값"이 아니라 "재대입할 수 없는 읽기 전용 접근자"를 뜻한다.

`const val`(고정되고 인라인됨), 커스텀 게터가 있는 `val`(매번 계산함), `by lazy`(처음 접근할 때 한 번 계산한 뒤 캐시함)는 모두 `val`이지만, 초기화와 계산 시점은 이처럼 크게 다르다. 이 차이가 이 장에서 가장 중요한 내용이다.

## 7. 스코프와 섀도잉: 이름의 수명과 가려짐

### 7.1 변수의 유효 범위

변수는 선언된 블록(중괄호 `{}`) 안에서만 유효하다. 블록을 벗어나면 그 이름은 더 이상 보이지 않는다. 이 스코프(scope) 규칙은 대부분의 정적 타입 언어와 같지만, 코틀린에는 몇 가지 관례가 더해진다.

```kotlin
fun scopeDemo() {
    val outer = 1
    run {
        val inner = 2
        println(outer + inner)   // => 3  (outer 보임, inner 보임)
    }
    // println(inner)            // 컴파일 에러: Unresolved reference 'inner'
}
```

또한 코틀린은 6장(널 안전성)에서 볼 스마트 캐스트를 위해, 스코프 안에서 변수의 "좁혀진 타입"을 추적한다. 즉 스코프는 이름이 보이는지뿐 아니라, 그 지점에서 그 이름이 어떤 타입으로 알려져 있는지까지 결정한다.

### 7.2 섀도잉: 안쪽 이름이 바깥 이름을 가린다

안쪽 스코프에서 바깥과 같은 이름의 변수를 선언하면, 안쪽에서는 바깥 변수가 **가려진다(shadowed)**. 바깥 변수가 사라지는 것이 아니라, 안쪽 스코프에서 그 이름이 안쪽 변수를 가리킬 뿐이다.

```kotlin
fun shadowDemo() {
    val x = 1
    run {
        val x = 2            // 경고: Name shadowed: x
        println(x)           // => 2  (안쪽 x)
    }
    println(x)               // => 1  (바깥 x는 그대로 살아 있음)
}
```

코틀린은 섀도잉을 **에러가 아니라 경고**로 처리한다. 섀도잉은 대부분 바깥 변수를 바꾸려다가 새 변수를 만들어 버린 실수이므로, 경고로 주의를 준다. 특히 함정이 되기 쉬운 경우는 루프 변수나 람다 파라미터가 바깥 이름을 가릴 때이다.

```kotlin
fun trap(items: List<Int>) {
    val total = 0
    items.forEach { total ->        // 경고: 파라미터 total이 바깥 total을 가림
        // 여기의 total은 각 원소. 바깥 val total(=0)이 아님.
        println(total)
    }
    println(total)                  // => 0  (바깥 total은 절대 안 바뀜)
}
```

`total`을 누적하려는 의도였다면 이 코드는 아무 오류 없이 틀린 결과를 낸다. 바깥 `total`은 `val`이어서 처음부터 누적할 수 없고, 안쪽 `total`은 매번 새 원소일 뿐이다. 컴파일러의 섀도잉 경고를 무시하면 안 되는 이유이다.

### 7.3 for 루프 변수는 반복마다 새 변수이다

코틀린이 잘 내린 결정이 하나 있다. `for` 루프의 변수는 **반복할 때마다 새로 만들어지는 `val`** 이다(재대입할 수 없고, 반복마다 독립적이다).

```kotlin
val actions = mutableListOf<() -> Int>()
for (i in 1..3) {
    actions.add { i }        // 각 람다가 캡처하는 i는 그 반복의 i
}
println(actions.map { it() })   // => [1, 2, 3]
```

자바에서는 옛 `for (int i = ...)`의 `i`를 람다가 아예 캡처할 수 없다(effectively final이 아니어서 컴파일 에러가 난다). 반복마다 같은 변수를 공유해 마지막 값만 보게 되는 고전적인 함정은 JavaScript의 `var` 루프에서 유명하다. 코틀린의 `for`는 반복마다 변수를 독립적으로 캡처하므로 `[1, 2, 3]`이 정확히 나온다.

"루프 변수는 `val`이며 반복마다 새로 생긴다"는 성질은 14장(클로저와 캡처)의 캡처 규칙과 직접 연결되며, 그 장에서 자세히 다룬다. 지금 기억할 것은 **코틀린 `for` 변수가 `var`가 아니라 반복마다 새로 생기는 `val`이라는 점**이다. 그래서 루프 안에서 `i = i + 1` 같은 재대입은 할 수 없다.

## 8. 타입 추론과 명시, 그리고 컴파일된 형태

### 8.1 추론의 기본 규칙

`val`과 `var`는 오른쪽 초기값에서 타입을 추론한다. 정수 리터럴은 `Int`, 실수 리터럴은 `Double`이 기본이다([[07 - 수 1 - Int와 Long과 부동소수점]] 참고).

```kotlin
val a = 5          // Int
val b = 5L         // Long
val c = 5.0        // Double
val d = 'x'        // Char
val e = "text"     // String
val f = listOf(1)  // List<Int>
```

타입을 명시해야 하는 경우는 세 가지이다.

- 추론 결과보다 넓거나 좁은 타입이 필요할 때(`val x: Long = 5`처럼 리터럴 `5`를 `Long`으로 쓰려는 경우)
- 초기화를 미루는 선언(3.2절의 `val grade: String`)
- 공개 API를 안정적으로 유지하려고 반환 타입이나 프로퍼티 타입을 명시적으로 고정할 때

지역 변수에서는 추론에 맡기는 것이 관례이다.

```kotlin
val x: Long = 5           // 명시로 Long 지정 (안 그러면 Int)
val n: Number = 5         // 상위 타입으로 넓혀 명시
```

> [!warning] 흔한 오해
> "타입을 추론하니 동적 타이핑이 아닌가?"라는 생각은 오해이다. 코틀린은 정적 타입이면서 강타입인 언어이다. 추론은 컴파일러가 타입 표기를 *생략하도록 허용*할 뿐이고, 타입은 컴파일 타임에 확정된다. `val a = 5` 뒤에 `a = "text"`를 쓰면 재대입 금지보다 먼저 **타입 불일치**로도 막힌다. 이런 정적 타입의 기반은 5장(타입 시스템의 지형)과 [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]에서 다룬다.

### 8.2 지역 변수의 컴파일 형태 (JVM 백엔드)

JVM 백엔드에서 지역 `val`/`var`는 어떻게 컴파일될까? 흥미롭게도 지역 변수 수준에서는 둘의 바이트코드가 거의 다르지 않다.

```text
JVM 백엔드에서:
- 지역 val, var 모두 메서드의 지역 변수 슬롯(local variable slot)에 놓인다.
- 바이트코드의 지역 변수에는 'final' 개념이 없다.
  즉 val의 "재대입 불가"는 *컴파일러가 강제*하는 것이지,
  바이트코드에 final 표식이 남는 것이 아니다.
- 따라서 지역 val/var의 런타임 표현은 사실상 동일. 차이는 컴파일 타임 검사뿐.
```

이 사실에서 알 수 있는 것은 **`val`의 안전성이 "런타임에 값을 잠그는" 방식이 아니라 "컴파일러가 재대입 코드를 거부하는" 방식으로 확보된다**는 점이다. 6장에서 다루는 널 안전성이 대부분 컴파일 타임 보장인 것과 같은 방식이다. 코틀린의 여러 안전장치는 런타임 비용 없이 컴파일러가 그 비용을 부담한다.

### 8.3 멤버와 최상위 변수의 컴파일 형태 (JVM 백엔드)

반면 클래스 멤버와 최상위 변수는 프로퍼티로 취급되므로 접근자와 필드가 생긴다. 이 부분은 22장(프로퍼티와 백킹 필드)에서 자세히 다루며, 여기서는 비교를 위해 개략만 본다.

```text
JVM 백엔드에서, 커스텀 접근자 없는 프로퍼티 기준:
- 멤버 val x → private final 백킹 필드 + public 게터 getX()
- 멤버 var x → private 백킹 필드 + getX() + setX()
- 최상위 val/var → 파일명Kt 클래스의 static 필드 + static 게터/세터
- const val    → public static final 필드 (ConstantValue) + 사용처 인라인 (6.3)
- lateinit var → non-final 백킹 필드 + 초기화 검사 게터 (4.2)
```

즉 지역 변수와 달리 멤버와 최상위 변수에서는 `val`이 실제로 `final` 필드로 컴파일되어 런타임 표현에도 흔적이 남는다. 자바 코드에서 코틀린 프로퍼티가 `getX()`/`setX()`로 보이는 이유도 여기에 있다. 이 상호운용의 세부 사항은 45장(Java 상호운용)에서 다룬다.

### 8.4 세 가지 형태를 알아야 하는 이유

지역, 멤버, 최상위 변수의 컴파일 형태가 다르다는 사실은 실무에서 세 가지로 드러난다.

- `const`를 최상위, `object`, `companion`에만 붙일 수 있는 이유(6.2절)가 이 형태 차이에서 나온다. 인스턴스에 묶인 필드는 정적 상수가 될 수 없기 때문이다.
- `lateinit`이 멤버(와 최상위 변수)에서는 자연스럽지만 지역 변수에서는 드문 이유도 여기에 있다.
- 23장(위임 프로퍼티)에서 다루는 `by lazy`가 멤버에서 어떻게 저장되는지도 이 필드 모델을 바탕으로 이해할 수 있다.

결국 이름을 어디에 선언했는지가 그 이름이 무엇으로 컴파일되는지를 결정하고, 그것이 다시 어떤 한정자를 붙일 수 있는지를 결정한다.

## 9. 전체 종합: 초기화 전략 결정 지도

### 9.1 다섯 도구의 자리

이 장에서 다룬 도구를 하나의 지도에 배치해 보자. 기준은 두 가지이다. 하나는 "값을 언제 결정하는가"(컴파일 타임 ↔ 런타임 지연)이고, 다른 하나는 "재대입할 수 있는가"이다.

```text
                 값 결정: 컴파일 타임 ─────────────► 런타임 즉시 ─────────► 런타임 지연

  재대입 불가:   const val            val (즉시 초기화)       val ... by lazy
  (read-only)    (인라인 상수)         (일반 읽기전용)          (첫 접근 시 계산)

  재대입 가능:   (해당 없음)           var (즉시 초기화)       lateinit var
  (mutable)                            (일반 가변)              (밖에서 나중 대입)
```

- **`const val`**: 절대 바뀌지 않는 리터럴 상수(원시 타입이나 String)에 쓴다. 컴파일 타임에 확정되고 인라인된다.
- **`val`**: 기본으로 선택한다. 재대입할 수 없다. 값은 실행 중에 정해질 수 있지만, 한 번 정해지면 이름은 고정된다.
- **`val ... by lazy`**: 비용이 큰 계산을 처음 사용할 때까지 미루고 결과를 캐시한다. 값을 스스로 계산한다.
- **`var`**: 값이 정말로 바뀌어야 할 때만 쓴다.
- **`lateinit var`**: 널이 아닌 프로퍼티인데 생성자에서는 채울 수 없고, 외부에서 나중에 값을 넣어 줄 때 쓴다.

### 9.2 결정 순서 (의사 결정 흐름)

```text
값이 필요할 때 자문하라:

1. 컴파일 타임에 값이 고정된 원시/String 리터럴인가?
     예 → const val
     아니오 ↓
2. 한 번 정해지면 안 바뀌는가?
     아니오(계속 바뀜) → var  (정말 필요한지 재고)
     예 ↓
3. 생성 시점에 바로 값을 줄 수 있는가?
     예 → val x = ...           (기본 선택, 가장 흔함)
     아니오 ↓
4. 처음 읽힐 때 스스로 계산해서 캐시하면 되는가?
     예 → val x by lazy { ... }
     아니오(밖에서 나중에 채워짐) ↓
5. 비-널 타입이고 첫 사용 전 반드시 채워지는 계약이 있는가?
     예 → lateinit var
     아니오(있을 수도 없을 수도) → val/var x: T?  (정직하게 nullable)
```

### 9.3 다음 장으로

지금까지 변수라는 이름이 선언되고, 초기화되고, 재대입되고, 스코프 안에서 쓰이는 과정을 살펴보았다. 이제 이 이름들이 함수 안에서 어떻게 다뤄지는지가 남았다. 함수 파라미터를 모두 재대입할 수 없는 이유(1.3절), 그리고 기본 인자와 이름 붙은 인자가 초기화를 어떻게 관례화하는지는 12장(함수)에서 이어서 다룬다. 이 장에서 미리 언급만 한 프로퍼티의 백킹 필드와 커스텀 접근자, `by lazy`의 위임 메커니즘은 각각 22장(프로퍼티와 백킹 필드)과 23장(위임 프로퍼티)에서 자세히 다룬다.
