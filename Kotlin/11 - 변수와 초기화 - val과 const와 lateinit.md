**이 장이 답하는 질문:**

- `val`은 정말로 "불변(immutable)"을 만드는가, 아니면 다른 무언가인가?
- `val list = mutableListOf(1, 2)` 뒤에 `list.add(3)`가 컴파일되는 것은 모순인가?
- 코틀린엔 왜 "선언만 하고 나중에 대입" 하는 자바식 `int x;`가 없는가? 그런데 왜 어떤 경우엔 되는가?
- `const val`과 그냥 `val`은 무엇이 다르며, 왜 `const`는 함수 안이나 일반 클래스 안에 못 쓰는가?
- `const val`로 선언한 값은 어디에 저장되고, 호출하는 쪽 바이트코드에는 무엇이 남는가?
- `lateinit`은 "늦게 초기화하니까 결국 nullable" 아닌가? 왜 접근하면 NPE가 아니라 다른 예외가 나는가?
- `lateinit var`와 `val ... by lazy`는 둘 다 "나중에 채운다"인데 무엇이 다르고 언제 무엇을 고르는가?
- 안쪽 스코프에서 같은 이름의 변수를 다시 선언하면(섀도잉) 바깥 변수는 어떻게 되는가?

[[10 - 불리언과 동등성과 동일성]]에서 우리는 "값이 같다는 것"과 "같은 객체라는 것"을 갈랐다. `==`는 `equals`로 구조를 비교하고 `===`는 참조 동일성을 본다는 그 구분은, 사실 이 장의 주제로 곧장 이어진다. 왜냐하면 **변수는 값을 담는 상자가 아니라 객체를 가리키는 이름표**이기 때문이다. 변수를 "고정한다"고 할 때, 우리가 고정하는 것이 *이름표가 가리키는 대상*인지 *이름표 그 자체*인지를 혼동하는 순간, 코틀린의 `val`을 근본적으로 오해하게 된다.

이 장은 코틀린에서 이름을 짓는 세 가지 방식 — `val`, `var`, 그리고 그 위에 얹히는 한정자 `const`·`lateinit`, 위임 `by lazy` — 을 기계 수준에서 해부한다. 다루는 것은 "변수 하나가 선언되어 초기화되고 사용되기까지 컴파일러와 런타임이 무엇을 보장하고 무엇을 미루는가"이다. 반대로 이 장이 다루지 *않는* 것도 분명히 해 두자. 클래스 멤버로서의 프로퍼티가 백킹 필드(backing field)를 갖는 정확한 규칙과 커스텀 접근자의 세계는 [[22 - 프로퍼티와 백킹 필드]]가 소유한다. `by lazy` 같은 위임 프로퍼티의 일반 메커니즘은 [[23 - 위임 프로퍼티]]가, 생성자와 `init` 블록의 초기화 순서는 [[21 - 클래스와 생성자]]와 [[24 - 상속과 오버라이딩과 초기화 순서]]가 정본으로 판다. 이 장은 그 문들 앞에 서서, "변수와 초기화"라는 공통 토대만을 깊게 파고 나머지는 정확한 위키링크로 넘긴다.

논증의 궤적은 이렇다. 먼저 `val`과 `var`의 진짜 의미가 "재대입 가능성"이지 "불변성"이 아님을 못박는다(M3). 그다음 코틀린이 초기화를 어떻게 *강제*하는지 — 확정 대입 분석(definite assignment) — 를 본다. 이 강제가 있기에 코틀린엔 "초기화 안 된 지역 변수"라는 자바의 함정이 없다. 그러나 클래스 프로퍼티에서는 이 강제가 불편할 때가 있고, 거기서 `lateinit`(M9)과 `by lazy`라는 탈출구가 등장한다. 마지막으로 `const val`(M36)은 "초기화를 미루는" 이 흐름과 정반대로, 초기화를 *컴파일 시점으로 당겨* 값 자체를 사라지게 만드는 장치임을 본다. [[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]에서 함수 파라미터가 왜 전부 `val`처럼 재대입 불가인지도 이 장의 관점이 있어야 이해된다.

## 1. 두 개의 이름 — `val`과 `var`, 그리고 재대입이라는 축

### 1.1 문법이 아니라 "능력"의 선언

코틀린에서 이름을 짓는 키워드는 정확히 둘, `val`과 `var`다. 자바가 타입을 앞세워 `int x = 5;`라고 쓰는 반면 코틀린은 능력을 앞세운다.

```kotlin
val radius = 5          // 타입 추론: Int
var counter = 0         // 타입 추론: Int

radius = 6              // 컴파일 에러: Val cannot be reassigned
counter = 1             // OK
```

`val`(value의 약자)은 **재대입 불가(read-only, single-assignment)** 이름이다. 한 번 대입되면 그 이름에 다시 `=`로 다른 것을 붙일 수 없다. `var`(variable)은 얼마든지 다시 대입할 수 있다. 자바 개발자에게 `val`은 지역 변수 앞의 `final`에, `var`는 그냥 변수에 대응한다고 첫인상을 잡아도 된다. 하지만 그 첫인상이 정확히 어디까지 맞고 어디서 갈라지는지가 이 장의 절반이다.

핵심은 `val`/`var`가 **변수가 가리키는 대상의 성질이 아니라, 그 이름을 다시 묶을 수 있는가**를 말한다는 점이다. 이름과 대상을 분리해서 보는 습관이 없으면 다음 절의 오해를 피할 수 없다.

### 1.2 왜 코틀린은 `val`을 권장하는가

코틀린 스타일 가이드와 관용은 "가능하면 `val`을 써라"이다. 이유는 단순한 취향이 아니다. 재대입 불가한 이름은 **읽는 사람과 컴파일러 양쪽에게 불변식(invariant)을 준다.** 이 이름은 이 지점 이후로 값이 바뀌지 않는다는 보장은, 코드를 읽을 때 추적 부담을 줄이고, 컴파일러에게는 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 볼 스마트 캐스트(smart cast)를 안전하게 적용할 근거를 준다.

```kotlin
fun describe(shape: Any) {
    val s = shape
    if (s is String) {
        // s는 여기서 String으로 스마트 캐스트됨.
        // s가 val이라 중간에 바뀔 수 없으므로 컴파일러가 안심하고 좁힌다.
        println(s.length)   // => 정상
    }
}
```

만약 `s`가 `var`였고 어딘가에서 재대입될 수 있었다면, 컴파일러는 `is String` 검사 이후에도 값이 그대로라고 장담할 수 없어 스마트 캐스트를 거절했을 것이다. 즉 `val`은 단지 "실수 방지"가 아니라 **타입 시스템의 추론 능력을 여는 열쇠**다. 이 연결고리는 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 M13(스마트 캐스트는 항상 되지 않는다)로 정밀하게 다뤄진다.

> **역사 메모**: 자바는 2004년 `for-each`와 함께 지역 변수 `final`을 장려했지만, 문법이 길고 기본값이 아니어서 실무에서 잘 쓰이지 않았다. 코틀린은 아예 두 키워드를 대등하게 두고 `val`을 먼저 가르침으로써 "불변을 기본으로"라는 문화를 언어 차원에서 밀었다. 자바 10의 `var`(2018)는 방향이 반대다 — 자바 `var`는 타입 추론용이지 가변성과 무관하다. **이름이 같아 헷갈리지만 코틀린 `var`와 자바 `var`는 다른 축을 말한다.**

### 1.3 함수 파라미터는 언제나 `val`이다

한 가지 즉시 파생되는 사실. 코틀린 함수의 파라미터는 항상 재대입 불가다. `val`/`var` 키워드를 붙일 수조차 없다(붙이면 컴파일 에러).

```kotlin
fun grow(size: Int): Int {
    size = size + 1     // 컴파일 에러: Val cannot be reassigned
    return size
}
```

이는 자바(파라미터 재대입 가능)와 확연히 다르며, 파라미터를 "지역의 임시 변수처럼 굴려 쓰는" 습관을 원천 차단한다. 새 값이 필요하면 새 지역 `val`을 만들라는 것이 코틀린의 태도다. 이 규칙과 [[14 - 클로저와 캡처]]의 캡처 규칙이 만나면, 코틀린에서 람다가 파라미터를 캡처할 때 왜 안전한지가 설명된다. 자세한 것은 [[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]로 넘긴다.

## 2. `val`은 불변이 아니다 — 이름표와 객체의 분리 (M3)

### 2.1 정면 교정: 재대입 불가 ≠ 불변

가장 널리 퍼진 오해를 정면으로 부순다. **`val`은 불변(immutable) 객체를 만들지 않는다. `val`은 이름을 다시 묶지 못하게 할 뿐이다(M3).** 이름이 가리키는 객체 내부는 얼마든지 변할 수 있다.

```kotlin
val numbers = mutableListOf(1, 2, 3)
numbers.add(4)              // => [1, 2, 3, 4]  — 컴파일 통과, 정상 동작
numbers[0] = 99            // => [99, 2, 3, 4]  — 원소 교체도 OK
println(numbers)            // => [99, 2, 3, 4]

numbers = mutableListOf()  // 컴파일 에러: Val cannot be reassigned
```

`numbers.add(4)`가 컴파일되는 것은 전혀 모순이 아니다. `add`는 `numbers`라는 이름을 건드리지 않는다. `numbers`가 가리키는 *리스트 객체의 내부 상태*를 바꿀 뿐이다. `val`이 금지하는 것은 마지막 줄 — `numbers`라는 이름에 *다른 리스트*를 다시 붙이는 행위 — 뿐이다.

메모리 그림으로 보면 명확하다.

```text
val numbers ─────► [ MutableList 객체 ]
   (이름표 고정)        내부: 1,2,3,4  ← 이 안은 자유롭게 변함

금지되는 것:  numbers ──✗──► [ 다른 리스트 ]   (이름표 재부착 금지)
허용되는 것:  numbers ──────► [ 같은 리스트, 내용만 바뀜 ]  (객체 내부 변형 OK)
```

### 2.2 배열, 객체, 프로퍼티에서도 동일

같은 원리가 배열과 사용자 정의 클래스에도 적용된다.

```kotlin
val coords = intArrayOf(0, 0)
coords[0] = 10             // => [10, 0]  — 배열 원소 대입 OK

class Account(var balance: Long)
val acc = Account(1000)
acc.balance = 2000         // OK — 객체의 var 프로퍼티는 여전히 가변
// acc = Account(0)        // 컴파일 에러 — 이름표 acc는 못 바꿈
```

`acc`는 `val`이지만 `acc.balance`는 `var` 프로퍼티라 바뀐다. `val acc`가 고정한 것은 "acc가 이 계좌 객체를 가리킨다"는 사실이지, "이 계좌의 잔고가 영원하다"가 아니다. 진짜 불변 객체를 원한다면 객체 *안의 프로퍼티들을 전부 `val`로 만들고 가변 컬렉션을 노출하지 않아야* 한다. 언어가 이름 하나로 그것을 해 주지 않는다.

> **흔한 오해**: "`val`이면 스레드 안전하다"도 같은 뿌리의 오해다. `val`은 재대입만 막으므로, `val`이 가리키는 가변 객체를 여러 스레드가 동시에 변형하면 여전히 데이터 경합이 난다. 진짜 스레드 안전은 불변 객체이거나 동기화가 있어야 성립한다 — [[43 - 동시성과 메모리 모델]]에서 다룬다.

### 2.3 진짜 불변을 원한다면 — 방어적 복사

`val`이 불변을 주지 않으니, 진짜 불변을 원하면 개발자가 손수 만들어야 한다. 대표 기법이 **방어적 복사(defensive copy)** 다. 생성자로 받은 가변 컬렉션을 그대로 저장하면, 밖에 남은 참조로 내용이 바뀔 수 있다.

```kotlin
class Polygon(points: List<Point>) {
    // 위험: 밖의 리스트를 그대로 참조
    val vertices: List<Point> = points
    // 안전: 받은 시점의 내용을 복사해 소유
    val safeVertices: List<Point> = points.toList()
}

val input = mutableListOf(Point(0, 0), Point(1, 1))
val poly = Polygon(input)
input.add(Point(9, 9))          // 밖에서 리스트를 변형
println(poly.vertices.size)     // => 3  (위험한 쪽은 영향받음!)
println(poly.safeVertices.size) // => 2  (복사한 쪽은 무사)
```

`val vertices`가 `val`인데도 크기가 2에서 3으로 바뀐 것처럼 *보이는* 이유는, `vertices`가 밖의 `input`과 **같은 객체를 공유**하기 때문이다. `val`은 `vertices`라는 이름을 고정했을 뿐, 그 객체의 내용을 지키지 않는다. `toList()`로 복사본을 만들어 소유하면 비로소 밖의 변형으로부터 격리된다. 이 방어적 복사·읽기 전용 뷰의 미묘함은 [[38 - 컬렉션 - 읽기 전용과 가변]]가 정본으로 판다. 이 장의 교훈은 "`val`은 시작일 뿐, 불변의 끝이 아니다"이다.

### 2.4 읽기 전용 컬렉션 타입과의 관계

그렇다면 "진짜 못 바꾸는" 컬렉션은 어떻게 얻는가? 코틀린은 타입 레벨에서 `List`(읽기 전용 인터페이스)와 `MutableList`(가변)를 나눈다.

```kotlin
val readOnly: List<Int> = listOf(1, 2, 3)
// readOnly.add(4)   // 컴파일 에러: add는 List에 없음 (MutableList에만)
```

여기서 못 바꾸는 이유는 `val`이 아니라 **타입이 `List`라서** 변형 메서드 자체가 없기 때문이다. `val`과 `List`는 직교하는 두 개의 축이다. 그리고 이조차 "불변"의 완전한 보장은 아니다 — 같은 객체를 가리키는 `MutableList` 참조가 어딘가에 있으면 내용은 바뀔 수 있다. 이 미묘함(M26·M27)은 [[38 - 컬렉션 - 읽기 전용과 가변]]이 정본으로 해부한다. 이 장에서 기억할 것은 하나다: **가변성은 이름(`val`/`var`)과 타입(`List`/`MutableList`)이라는 두 축의 곱으로 결정되며, `val` 하나로는 불변이 만들어지지 않는다.**

## 3. 초기화 강제 — 코틀린엔 "빈 변수"가 없다

### 3.1 선언과 동시에 값이 있어야 한다는 원칙

자바에서는 `int x;`처럼 값 없이 선언하고 나중에 채우는 것이 흔하다. 코틀린의 기본 태도는 정반대다. **변수는 사용되기 전에 반드시 값을 가져야 한다.** 아래는 겉보기엔 자바스럽지만 코틀린에선 대개 실패한다.

```kotlin
fun demo() {
    val x: Int
    println(x)          // 컴파일 에러: Variable 'x' must be initialized
}
```

여기서 핵심 오해 하나를 미리 정리하자. 코틀린엔 자바 필드가 갖는 "타입별 기본값"(int는 0, 참조는 null) 개념이 지역/멤버 초기화 규칙에는 없다. 개발자가 명시적으로 초기값을 주지 않으면 컴파일러가 통과시키지 않는다(단, 클래스의 프로퍼티는 초기화 없이 선언 자체가 불가하다 — 뒤의 3.3에서 본다). 이 강제는 자바에서 악명 높은 "초기화 안 된 변수를 실수로 읽는" 부류의 버그를 언어 차원에서 없앤다.

### 3.2 확정 대입 분석 — 미룬 초기화가 되는 경우

그런데 3.1의 규칙은 "선언과 대입이 반드시 한 줄이어야 한다"는 뜻이 *아니다*. 코틀린 컴파일러는 **확정 대입 분석(definite assignment analysis)** 을 수행한다. 즉 "이 변수를 읽는 모든 실행 경로에서, 읽기 전에 정확히 값이 대입되었는가"를 제어 흐름으로 추적한다. 모든 경로가 만족하면, 선언과 대입이 떨어져 있어도 통과한다.

```kotlin
fun classify(score: Int): String {
    val grade: String           // 선언만 — 아직 값 없음
    if (score >= 90) {
        grade = "A"             // 경로 1에서 대입
    } else {
        grade = "B"             // 경로 2에서 대입
    }
    return grade                // 두 경로 모두 대입됐으므로 읽기 OK
}
```

`grade`는 `val`이지만 선언 시점에 대입하지 않았다. 그럼에도 컴파일되는 이유는, `if`/`else`의 **모든 분기가 정확히 한 번씩** `grade`를 대입하고, `return`으로 읽기 전에 반드시 대입이 끝나기 때문이다. 이것이 "지연 초기화(deferred initialization)"이며, `val`의 "single-assignment(단 한 번 대입)" 규칙과 완벽히 양립한다 — 각 경로에서 딱 한 번씩만 대입되므로.

만약 어떤 경로가 대입을 빠뜨리면 즉시 에러가 난다.

```kotlin
fun broken(flag: Boolean): Int {
    val n: Int
    if (flag) {
        n = 1
    }
    return n     // 컴파일 에러: Variable 'n' must be initialized
                 // (flag가 false인 경로에서 n이 대입되지 않음)
}
```

`val`을 한 경로에서 대입하고 다른 경로에서 또 대입하면 "두 번 대입"이 되어 이 또한 막힌다.

```kotlin
fun twice(flag: Boolean) {
    val n: Int
    n = 1
    if (flag) {
        n = 2    // 컴파일 에러: Val cannot be reassigned
    }
}
```

> **명세 정밀**: 확정 대입 분석은 코틀린 언어의 제어 흐름 분석(control-flow analysis)의 일부다. `if`/`when`/`try`뿐 아니라 `throw`나 반환이 있는 경로도 함께 고려된다. 예컨대 어떤 분기가 예외를 던지면 그 분기는 "정상적으로 이후 코드에 도달하지 않으므로" 대입 의무에서 면제된다. 이는 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서 다루는 바닥 타입 `Nothing`과 직접 연결된다 — `throw`나 `return`의 타입이 `Nothing`이기에, 컴파일러는 그 지점 이후가 "도달 불가"임을 타입으로 안다.

```kotlin
fun withThrow(x: Int): String {
    val label: String
    when {
        x > 0 -> label = "positive"
        x < 0 -> label = "negative"
        else  -> throw IllegalArgumentException("zero")
        // else 분기는 Nothing으로 끝나므로 label 대입 의무 면제
    }
    return label    // OK — 도달하는 모든 경로에서 label이 대입됨
}
```

### 3.3 지역 변수 vs 클래스 프로퍼티 — 규칙이 갈라지는 지점

여기서 중요한 경계가 있다. 지금까지의 "선언만 하고 나중에 대입"은 **지역 변수**에서 특히 유연하다. 그러나 **클래스 프로퍼티**(멤버 `val`/`var`)는 더 엄격하다. 프로퍼티는 원칙적으로 선언 지점에서 초기화하거나, `init` 블록/주 생성자 안에서 대입해야 한다.

```kotlin
class Circle(radius: Double) {
    val area: Double            // 프로퍼티 선언
    init {
        area = Math.PI * radius * radius   // init 블록에서 대입 — OK
    }
}
```

프로퍼티를 아무 데서도 초기화하지 않은 채 생성자를 마치면 컴파일 에러다. 이 초기화 순서(주 생성자 → 프로퍼티 초기화자 → `init` 블록)의 정밀한 규칙은 [[21 - 클래스와 생성자]]가, 상속이 얽힐 때의 함정(M47)은 [[24 - 상속과 오버라이딩과 초기화 순서]]가 소유한다.

바로 이 "프로퍼티는 생성 시점에 초기화가 끝나야 한다"는 엄격함이 실무에서 마찰을 낳는다. 의존성 주입, 프레임워크 콜백, 테스트 `@BeforeEach` 등에서는 객체를 만든 *직후*가 아니라 *조금 나중*에 값이 도착한다. 값의 타입이 nullable이면 `null`로 시작해 나중에 채우면 되지만, 그러면 비-널이어야 마땅한 프로퍼티가 억지로 `T?`가 되어 사용처마다 `?.`나 `!!`를 달아야 한다. **이 딜레마를 풀려고 등장한 것이 다음 절의 `lateinit`이다.**

### 3.4 확정 대입과 예외 — try/catch의 미묘함

확정 대입 분석은 `try`/`catch`에서 특히 조심스럽다. `try` 블록 안의 대입은 "성공적으로 끝났다"고 장담할 수 없다 — 대입 직전에 예외가 날 수 있기 때문이다.

```kotlin
fun parse(text: String): Int {
    val n: Int
    try {
        n = text.toInt()       // 여기서 예외 가능
    } catch (e: NumberFormatException) {
        n = -1                  // catch에서 대입
    }
    return n                    // OK — try 성공 또는 catch, 두 경로 모두 대입
}
```

이 코드가 통과하는 이유는 `try`가 정상 완료되면 `n`이 대입되고, 예외가 나면 `catch`가 `n`을 대입하기 때문이다. 두 종착지 모두 `n`을 채운다. 그러나 `catch`에서 대입을 빠뜨리면 컴파일러는 "예외 경로에서 `n`이 미대입"임을 지적한다. 코틀린의 `try`가 표현식이라는 점([[41 - 예외와 Nothing]], M31)을 이용하면 더 깔끔하다.

```kotlin
fun parseCleaner(text: String): Int {
    val n = try { text.toInt() } catch (e: NumberFormatException) { -1 }
    return n     // try 표현식의 값이 곧 n — 한 번 대입, 지연 없음
}
```

`try`를 표현식으로 쓰면 두 분기가 모두 값을 내므로 `val n`을 선언과 동시에 대입할 수 있다. 확정 대입의 부담이 애초에 사라진다. 예외와 제어 흐름의 정본은 [[41 - 예외와 Nothing]]이다.

## 4. `lateinit` — 비-널 프로퍼티의 초기화를 미루기 (M9)

### 4.1 정면 교정: lateinit은 nullable이 아니다

오해 M9를 정면으로 부순다. **`lateinit`은 "늦게 초기화하니까 결국 nullable"이 아니다. `lateinit`은 *비-널(non-null)* 타입 프로퍼티의 초기화 시점을 뒤로 미루는 약속이며, 그 대가로 널 안전성 검사의 한 조각을 컴파일 타임에서 런타임으로 옮긴다(M9).**

```kotlin
class Server {
    lateinit var config: Config      // 타입은 Config — nullable(Config?) 아님!

    fun boot() {
        config = loadConfig()        // 나중에 채움
    }

    fun handle() {
        // config는 Config로 취급 — ?. 나 !! 없이 그냥 사용
        println(config.port)
    }
}
```

`config`의 타입은 `Config`이지 `Config?`가 아니다. 그래서 사용처에서 `config.port`를 널 검사 없이 쓸 수 있다 — 이것이 `lateinit`의 존재 이유다. nullable로 만들었다면 `config?.port`나 `config!!.port`를 매번 써야 했을 것이다. `lateinit`은 "이 값은 논리적으로 절대 null이 아니다. 단지 생성자 시점엔 아직 없을 뿐이다"라는 개발자의 선언이다.

### 4.2 초기화 전에 접근하면 — NPE가 아니다

`lateinit`의 대가는 명확하다. 값을 채우기 *전에* 읽으면 실패한다. 그런데 그 실패는 `NullPointerException`이 아니라 전용 예외다.

```kotlin
class Server {
    lateinit var config: Config
    fun handle() = println(config.port)
}

Server().handle()
// => 런타임 예외: kotlin.UninitializedPropertyAccessException:
//    lateinit property config has not been initialized
```

왜 `UninitializedPropertyAccessException`이라는 별도 예외인가? 이것이 M9를 이해하는 핵심이다. 만약 `config`가 사실 `Config?`였다면 초기화 전 값은 `null`이고, `config.port` 접근은 `NullPointerException`을 냈을 것이다. 하지만 `lateinit`의 타입은 비-널 `Config`다. 개념적으로 "아직 값이 없음"과 "값이 null임"은 다른 상태이며, 코틀린은 이 둘을 구별해 **"미초기화"라는 별도의 오류 범주**로 신호한다. 이 예외 이름 자체가 "이건 널 문제가 아니라 초기화 순서 문제다"라고 알려주는 것이다.

> **명세 정밀 / JVM 백엔드에서**: JVM 백엔드에서 `lateinit var`는 내부적으로 nullable 필드로 컴파일되고, 초기화 여부를 `null` 여부로 판별한다. 즉 접근자(게터)가 필드를 읽어 `null`이면 `UninitializedPropertyAccessException`을 던지도록 컴파일된다. 그래서 다음 절에서 볼 원시 타입 제약이 생긴다 — `null`을 센티넬(sentinel)로 쓰려면 필드가 참조 타입이어야 하기 때문이다. 이것은 JVM 구현의 세부이며, 다른 백엔드의 표현은 다를 수 있다.

### 4.3 lateinit의 제약 — 어디에 못 쓰는가

`lateinit`은 아무 데나 붙일 수 없다. 제약들을 이해하면 그 정체가 더 또렷해진다.

| 제약 | 이유 |
|------|------|
| `var`에만 (❌ `val`) | 나중에 대입해야 하므로 재대입 가능해야 함 |
| 비-널 타입에만 (❌ `Int?`, `String?`) | nullable이면 애초에 `null`로 시작하면 되니 lateinit이 불필요 |
| 원시 타입 불가 (❌ `Int`, `Long`, `Double`, `Boolean`) | JVM 백엔드에서 null 센티넬을 못 씀 |
| 커스텀 게터/세터 있으면 불가 | lateinit은 컴파일러가 접근자를 생성해 초기화 검사를 넣음 |

```kotlin
class Bad {
    lateinit val x: String    // 컴파일 에러: 'lateinit' modifier is not allowed on 'val'
    lateinit var n: Int       // 컴파일 에러: 'lateinit' modifier is not allowed on primitives
    lateinit var s: String?   // 컴파일 에러: 'lateinit' modifier is not allowed on nullable
}
```

원시 타입에 굳이 지연 초기화가 필요하면 `Int?`로 두거나 `Delegates.notNull()`(다음 절 참고, [[23 - 위임 프로퍼티]]) 같은 대안을 쓴다. `lateinit`은 참조 타입 프로퍼티를 위한 도구다. 참고로 `lateinit`은 클래스 멤버뿐 아니라 **최상위 프로퍼티와 지역 변수에도** 쓸 수 있다(코틀린 1.2 이후). 다만 실무의 압도적 다수는 클래스 멤버다.

### 4.4 초기화 여부 확인 — `::x.isInitialized`

가끔 "채워졌는지"를 접근 전에 알고 싶을 때가 있다. 코틀린은 이를 위한 특수 문법을 제공한다.

```kotlin
class Cache {
    lateinit var data: Map<String, Int>

    fun getOrEmpty(): Map<String, Int> =
        if (::data.isInitialized) data else emptyMap()
    //     ^^^^^^^^^^^^^^^^^^^^^ lateinit 프로퍼티에만 쓸 수 있는 검사
}
```

`::data.isInitialized`는 프로퍼티 참조에 대한 특수 프로퍼티로, `lateinit`이 채워졌는지를 `true`/`false`로 준다. 이 검사는 접근 가능한 스코프 안(같은 클래스 내부, 또는 `this::data` / 바깥 클래스에서 접근 가능한 경우)에서만 쓸 수 있다. 아무 곳에서나 남의 `lateinit` 상태를 엿볼 수는 없다.

> **성능 주의**: `::x.isInitialized`를 매 접근마다 방어적으로 두르는 코드는 냄새다. `lateinit`은 "초기화가 반드시 선행된다는 계약을 스스로에게 건" 도구다. 매번 초기화 여부를 검사해야 하는 상황이라면, 그것은 애초에 값이 "있을 수도 없을 수도" 있다는 뜻이고 — 그럴 땐 정직하게 `T?`(nullable)로 모델링하는 편이 타입이 진실을 말한다. `isInitialized`는 프레임워크 통합 같은 경계에서 예외적으로 쓰는 안전망이지 상시 습관이 아니다.

### 4.5 lateinit을 쓸 자리와 피할 자리

`lateinit`이 적합한 전형: 의존성 주입 프레임워크가 객체 생성 후 필드를 채우는 경우, 테스트에서 `@BeforeEach`가 픽스처를 준비하는 경우, 안드로이드/UI 프레임워크가 `onCreate` 콜백에서 뷰를 바인딩하는 경우. 공통점은 **"생성자에선 값을 못 주지만, 첫 사용 전엔 반드시 채워진다"는 외부 계약이 확실**하다는 것이다.

반대로 피해야 할 자리: 값이 조건부로만 존재하는 경우(→ nullable), 원시 수치(→ `Int?` 또는 `notNull`), 그리고 특히 **"비싸서 나중에 계산하고 싶은 경우"**. 마지막 것은 `lateinit`이 아니라 다음 절의 `by lazy`가 정답이다. `lateinit`은 "밖에서 값을 밀어 넣는(push)" 모델이고, `by lazy`는 "처음 읽힐 때 스스로 계산하는(pull)" 모델이다.

## 5. `by lazy` — 처음 읽힐 때 계산하기

### 5.1 지연 계산의 다른 축

`lateinit`이 "누군가 값을 대입해 줄 때까지 미룸"이라면, `by lazy`는 "처음 접근하는 순간 람다를 실행해 값을 만들고, 이후로는 그 값을 재사용"하는 위임 프로퍼티다. 여기서는 이 장의 초기화 관점에서 대조만 하고, 위임 메커니즘 자체는 [[23 - 위임 프로퍼티]]에 넘긴다.

```kotlin
class Report {
    val summary: String by lazy {
        println("계산 중...")     // 이 블록은 최초 접근 때 단 한 번만 실행
        expensiveComputation()
    }
}

val r = Report()
// 아직 "계산 중..." 안 찍힘 — summary를 읽지 않았으므로
println(r.summary)  // => 계산 중...  (여기서 처음 실행) 그리고 결과 출력
println(r.summary)  // => (계산 없이) 캐시된 결과만 출력
```

핵심 차이 두 가지. 첫째, `by lazy`는 **`val`에 쓴다**(값이 한 번 만들어지면 고정). `lateinit`은 `var`다. 둘째, `by lazy`는 **초기화 로직을 프로퍼티 자신이 품는다** — 값을 밖에서 받지 않고 스스로 계산한다. 그래서 `by lazy`는 원시 타입에도 쓸 수 있고(`val n: Int by lazy { compute() }`), nullable에도 쓸 수 있다. `lateinit`의 제약이 여기엔 없다.

### 5.2 스레드 안전성 모드

`lazy`는 여러 스레드가 동시에 최초 접근을 시도할 때의 동작을 모드로 고를 수 있다.

```kotlin
val a: Int by lazy { compute() }                              // 기본: SYNCHRONIZED
val b: Int by lazy(LazyThreadSafetyMode.PUBLICATION) { compute() }
val c: Int by lazy(LazyThreadSafetyMode.NONE) { compute() }
```

- `SYNCHRONIZED`(기본): 락으로 보호. 여러 스레드가 동시에 접근해도 초기화 람다는 정확히 한 번만 실행된다. 가장 안전하지만 락 비용이 있다.
- `PUBLICATION`: 여러 스레드가 동시에 람다를 실행할 수 *있으나*, 가장 먼저 값을 정해 게시(publish)한 결과가 채택되고 나머지는 버려진다. 초기화가 부작용 없고 값이 같다면 유용.
- `NONE`: 아무 동기화도 없음. 단일 스레드에서만 접근이 보장될 때 가장 빠르다. 멀티스레드에서 쓰면 미정의 동작.

> **성능 주의**: 단일 스레드 문맥(예: UI 스레드 전용 객체)에서 `by lazy`를 남발하면 기본 `SYNCHRONIZED`의 락 비용이 불필요하게 붙는다. 확실히 단일 스레드라면 `LazyThreadSafetyMode.NONE`을 명시하는 것이 정직하고 빠르다. 다만 "확실히 단일 스레드"라는 판단이 틀리면 경합 버그가 나므로, 애매하면 기본값을 유지하라. 메모리 모델과 게시(publication)의 정확한 의미는 [[43 - 동시성과 메모리 모델]]에서 다룬다.

### 5.3 초기화가 실패하면 — 예외의 운명

`by lazy`의 초기화 람다가 예외를 던지면 어떻게 될까? 이는 모드에 따라 미묘하게 다르지만, 기본 `SYNCHRONIZED`와 `PUBLICATION`의 표준 동작을 이해하는 것이 실무에 중요하다.

```kotlin
class Flaky {
    var attempts = 0
    val value: String by lazy {
        attempts++
        if (attempts < 2) throw IllegalStateException("first attempt fails")
        "success"
    }
}

val f = Flaky()
runCatching { f.value }        // 1번째 접근: 예외 발생, 값 미확정
println(f.value)               // 2번째 접근: 다시 람다 실행 → => success
println(f.attempts)            // => 2  (람다가 두 번 실행됨)
```

기본 모드에서 초기화 람다가 예외를 던지면 값이 확정되지 않고, **다음 접근에서 람다가 다시 실행된다.** 즉 성공할 때까지 재시도된다. 이는 "한 번 성공하면 그 값을 영원히 캐시하되, 실패는 확정하지 않는다"는 합리적 설계다. 다만 이 재실행 가능성 때문에 초기화 람다는 **여러 번 실행돼도 안전(부작용 최소)** 하도록 짜는 것이 좋다.

> **명세 정밀**: 위 재시도 동작은 `SynchronizedLazyImpl`·`SafePublicationLazyImpl` 등 표준 `Lazy` 구현의 관찰된 계약이다. 정확한 세부(예외 캐시 여부)는 구현/버전에 따라 달라질 수 있으므로, "초기화가 반드시 딱 한 번"이라는 강한 가정에 의존하는 코드는 피하고 멱등(idempotent)하게 작성하는 편이 안전하다. 위임 구현의 내부는 [[23 - 위임 프로퍼티]]가 다룬다.

### 5.4 lateinit vs by lazy — 결정표

| 축 | `lateinit var` | `val ... by lazy { }` |
|----|----------------|------------------------|
| 이름 종류 | `var` (재대입 가능) | `val` (한 번 고정) |
| 값의 출처 | 밖에서 대입(push) | 스스로 계산(pull) |
| 초기화 시점 | 개발자가 대입하는 순간 | 최초 읽기 순간(자동) |
| nullable 가능? | ❌ 비-널만 | ✅ 가능 |
| 원시 타입 가능? | ❌ (JVM 백엔드) | ✅ 가능 |
| 미초기화 접근 | `UninitializedPropertyAccessException` | (개념상 발생 안 함 — 접근이 곧 초기화) |
| 값 교체 | 가능(재대입) | 불가 |
| 스레드 안전 | 없음(직접 관리) | 모드로 선택 가능 |
| 전형적 쓰임 | DI, 콜백, 테스트 픽스처 | 비싼 계산의 지연·캐시 |

두 도구를 가르는 한 문장: **"밖에서 채워지길 기다린다"면 `lateinit`, "처음 필요할 때 스스로 만든다"면 `by lazy`.** 이 구분이 서면 실무의 선택 대부분이 자동으로 풀린다.

## 6. `const val` — 초기화를 컴파일 시점으로 당기기 (M36)

### 6.1 정면 교정: const val은 그냥 val이 아니다

이제 지금까지와 정반대 방향의 장치를 본다. 4·5절이 초기화를 *뒤로* 미뤘다면, `const`는 초기화를 *앞으로* — 실행 이전, 컴파일 시점으로 — 당긴다. 오해 M36을 부순다. **`const val`과 `val`은 같지 않다. `const val`은 *컴파일 타임 상수(compile-time constant)* 이며, 그 값은 컴파일 시점에 완전히 알려지고 사용처마다 값 자체가 인라인된다(M36).**

```kotlin
const val MAX_RETRIES = 3
const val PI_APPROX = 3.14159
const val GREETING = "hello"

val runtimeValue = computeSomething()   // 일반 val — 실행 시점에 결정
```

`const val`은 "이 이름은 컴파일러가 지금 당장 그 값을 아는 진짜 리터럴 상수다"라는 선언이다. 반면 일반 `val`은 재대입만 안 될 뿐, 그 값은 실행 중에 결정될 수 있다(`computeSomething()`의 결과처럼). 둘의 차이는 "언제 값이 정해지는가"라는 시간 축에 있다.

### 6.2 const val의 엄격한 조건

`const`는 아무 `val`에나 붙지 않는다. 컴파일 타임에 값이 완전히 결정되어야 하므로 조건이 엄격하다.

```kotlin
// ✅ 허용
const val A = 42                    // 최상위, 리터럴
const val B = "circle"              // String 리터럴
const val C = A + 1                 // 다른 const로 이뤄진 컴파일 타임 상수식

object Config {
    const val TIMEOUT = 30          // object 멤버 OK
}

class Limits {
    companion object {
        const val MAX = 100         // companion object 멤버 OK
    }
}

// ❌ 불가
const val D = readLine()            // 컴파일 에러: 런타임에 결정되는 값
const val E: Double = Math.sqrt(2.0)// 컴파일 에러: 함수 호출 결과는 상수 아님
val obj = object {}
// const val F = 1                  // (일반 클래스 본문의 인스턴스 멤버엔 불가)
```

조건을 정리하면:

1. **타입은 원시 타입 또는 `String`** 이어야 한다(`Int`, `Long`, `Double`, `Float`, `Boolean`, `Char`, `Byte`, `Short`, `String`). 임의 객체·컬렉션은 불가.
2. **위치는 최상위(top-level)이거나 `object`/`companion object`의 멤버**여야 한다. 일반 클래스의 인스턴스 프로퍼티엔 붙일 수 없다(인스턴스마다 다를 여지가 없어야 하므로 클래스 인스턴스에 매이면 안 됨).
3. **초기값은 컴파일 타임 상수식** — 리터럴이거나, 다른 `const val`들로 이뤄진 상수 산술/문자열 결합.
4. **커스텀 게터 불가**, 위임 불가. `const`는 접근자 없이 값 그 자체다.

> **명세 정밀**: 왜 `object`/`companion` 멤버는 되고 일반 클래스 인스턴스 멤버는 안 되는가? `const`는 인스턴스에 매이지 않는 정적 상수라야 의미가 있다. `object`와 `companion object`는 단일 인스턴스(싱글턴)이므로 그 멤버 상수는 "정적 상수"로 취급될 수 있다. 반면 일반 클래스는 인스턴스가 여럿일 수 있어 "컴파일 타임에 고정된 하나의 값"이라는 개념과 충돌한다. `object`/`companion`의 정체는 [[28 - object와 companion - 싱글턴과 동반 객체]]가 소유한다.

### 6.3 const는 어디에 저장되고 무엇이 인라인되는가

`const`의 진짜 정체는 바이트코드에서 드러난다. JVM 백엔드에서 `const val`은 두 가지 효과를 갖는다.

```kotlin
const val MAX_RETRIES = 3

fun retry() {
    for (i in 0 until MAX_RETRIES) { /* ... */ }
}
```

```text
JVM 백엔드에서 대략:
- MAX_RETRIES는 클래스 파일에 'public static final int MAX_RETRIES = 3'
  필드로 남되, ConstantValue 속성으로 값 3이 상수 풀에 박힌다.
- 그리고 retry()를 컴파일할 때, MAX_RETRIES 참조 자리에
  필드 읽기(getstatic)가 아니라 "리터럴 3"이 직접 인라인된다.

즉 retry()의 바이트코드에는 MAX_RETRIES라는 심볼이 사라지고 상수 3만 남는다.
```

이 "인라인"이 M36의 핵심이자 실무적 함정의 씨앗이다. 일반 `val`은 사용처가 필드를 읽어 오지만(`getstatic` + 게터 호출), `const val`은 **값이 사용처에 복사되어 박힌다.**

> **성능 주의 / 라이브러리 함정**: `const`의 인라인은 성능엔 좋지만 **바이너리 호환성**엔 함정이다. 라이브러리 A가 `const val VERSION = 1`을 노출하고, 앱 B가 이를 참조해 컴파일하면, 값 `1`이 B의 바이트코드에 *복사되어 박힌다*. 이후 A만 `VERSION = 2`로 고쳐 재배포해도, B를 재컴파일하지 않으면 B는 여전히 낡은 `1`을 쓴다. 일반 `val`이었다면 B가 실행 시 A의 필드를 읽으므로 새 값을 봤을 것이다. 그래서 "값이 바뀔 수 있는" API 상수는 `const`가 오히려 위험하고, "절대 안 바뀌는" 진짜 상수에만 `const`가 맞다.

### 6.4 const만 할 수 있는 것 — 애노테이션 인자

`const`가 단순 최적화 이상인 결정적 자리는 **애노테이션 인자**다. 애노테이션의 인자는 컴파일 타임에 알려져야 하므로, 일반 `val`은 못 쓰고 `const val`만 쓸 수 있다.

```kotlin
const val API_PATH = "/v1/resource"

@Deprecated("Use $API_PATH instead")   // const라서 애노테이션 인자로 사용 가능
fun oldApi() { /* ... */ }

// 만약 API_PATH가 const가 아닌 일반 val이었다면:
// 컴파일 에러: An annotation argument must be a compile-time constant
```

`when`의 상수 분기, 애노테이션 인자, 그리고 컴파일 타임에 값이 필요한 모든 자리 — 이곳들이 `const`가 대체 불가한 영역이다. 애노테이션의 세계는 [[44 - 애노테이션과 리플렉션]]이 소유한다.

### 6.5 val · const val 비교 정리

| 축 | `val x = ...` | `const val x = ...` |
|----|---------------|----------------------|
| 값 결정 시점 | 런타임(실행 중) | 컴파일 타임 |
| 허용 타입 | 임의 타입 | 원시 타입 + `String`만 |
| 위치 | 어디든(지역·멤버·최상위) | 최상위·`object`·`companion`만 |
| 초기값 | 임의 표현식·함수 호출 | 컴파일 타임 상수식만 |
| 커스텀 게터 | 가능 | 불가 |
| 사용처 표현(JVM) | 필드 읽기 | 값이 인라인(복사)됨 |
| 애노테이션 인자 | 불가 | 가능 |
| 값 변경 시 재컴파일 | 참조 측 불필요 | 참조 측 재컴파일 필요(안 하면 낡은 값) |

한 문장 요약: **`const val`은 "재대입 불가"에 더해 "컴파일 타임에 값이 확정되어 사용처에 인라인되는" 상수다. 일반 `val`은 그저 재대입 불가한 런타임 값이다.**

### 6.6 자바의 final·static final과의 대조

자바 개발자에게 이 세 도구를 매핑해 두면 오해가 준다. 다만 완전한 일대일 대응은 없다.

```java
// Java
final int x = compute();            // 지역 final ≈ 코틀린 지역 val
static final int MAX = 3;           // static final ≈ 코틀린 const val (상수 인라인 유사)
static final List<Integer> L = ...; // static final 참조 — 그러나 리스트 내용은 가변!
```

| 자바 | 코틀린 대응 | 주의 |
|------|-------------|------|
| 지역 `final T x` | `val x` | 거의 동일. 재대입 불가. |
| 인스턴스 `final` 필드 | 멤버 `val` (JVM에서 final 필드) | 거의 동일. |
| `static final` 원시/String | `const val` | 자바도 원시/String의 `static final`은 상수 인라인(§13 바이너리 호환) — 함정도 같다. |
| `static final` 객체 참조 | 최상위/companion `val` | `const` 불가(원시/String 아님). 인라인 안 됨. |

자바의 `static final int/String`이 사용처에 인라인되는 것과 코틀린 `const val`의 인라인은 사실상 같은 현상이며, "값을 바꿔도 참조 측을 재컴파일 안 하면 낡은 값이 남는" 함정(6.3)도 자바에서 물려받은 것이다. **결정적 차이는 자바의 `final`이 "가리키는 객체의 불변"을 전혀 보장하지 않듯, 코틀린 `val`도 그렇다는 점**(M3) — 두 언어 모두 "이름 고정"과 "객체 불변"을 혼동하면 안 된다. 자바 상호운용의 전모는 [[45 - Java 상호운용]]가 소유한다.

### 6.7 const가 아닌 val — 커스텀 게터로 매번 계산

한 가지 대조를 더 놓자. `const val`은 값이 고정·인라인되지만, **커스텀 게터를 가진 `val`은 접근할 때마다 다시 계산**된다. 이름은 같은 `val`이지만 정반대 성격이다.

```kotlin
class Clock {
    val now: Long                      // val이지만...
        get() = System.currentTimeMillis()   // ...접근마다 새 값!
}

val c = Clock()
println(c.now)   // => 예: 1000
Thread.sleep(10)
println(c.now)   // => 예: 1010  (val인데 값이 "바뀐 것처럼" 보임)
```

`now`는 `val`이라 재대입은 못 하지만, 커스텀 게터가 있어 백킹 필드가 없고([[22 - 프로퍼티와 백킹 필드]]) 매 접근이 게터 호출이다. 그래서 읽을 때마다 다른 값이 나올 수 있다. 여기서 `val`은 "저장된 불변 값"이 아니라 "재대입 불가한 읽기 전용 접근자"를 뜻한다. `const val`(고정·인라인), 커스텀 게터 `val`(매번 계산), `by lazy`(첫 접근 때 한 번 계산 후 캐시) — 세 `val`이 초기화·계산 시점에서 얼마나 다른지가 이 장의 큰 그림이다.

## 7. 스코프와 섀도잉 — 이름의 수명과 가림

### 7.1 변수의 유효 범위

변수는 선언된 블록(중괄호 `{}`) 안에서만 살아 있다. 블록을 벗어나면 그 이름은 더 이상 보이지 않는다. 이 규모(scope) 규칙은 대부분의 정적 타입 언어와 같지만, 코틀린은 몇 가지 관용이 얹힌다.

```kotlin
fun scopeDemo() {
    val outer = 1
    run {
        val inner = 2
        println(outer + inner)   // => 3  (outer 보임, inner 보임)
    }
    // println(inner)            // 컴파일 에러: Unresolved reference 'inner'
}
```

또한 코틀린은 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 볼 스마트 캐스트를 위해, 스코프 안에서 변수의 "정제된 타입"을 추적한다. 즉 스코프는 이름의 가시성뿐 아니라 그 이름이 그 지점에서 무슨 타입으로 알려져 있는지까지 관장한다.

### 7.2 섀도잉 — 안쪽이 바깥을 가린다

안쪽 스코프에서 바깥과 같은 이름의 변수를 선언하면, 안쪽에서는 바깥 변수가 **가려진다(shadowed)**. 바깥 변수가 사라지는 것이 아니라, 안쪽 스코프에서 그 이름이 안쪽 것을 가리킬 뿐이다.

```kotlin
fun shadowDemo() {
    val x = 1
    run {
        val x = 2            // 경고: Name shadowed: x
        println(x)           // => 2  (안쪽 x)
    }
    println(x)               // => 1  (바깥 x는 그대로 살아 있음)
}
```

코틀린은 섀도잉을 **에러가 아니라 경고**로 처리한다. 대부분의 섀도잉은 실수(바깥 변수를 바꾸려 했는데 새 변수를 만들어 버림)이기에 경고로 주의를 준다. 특히 함정이 되는 패턴은 루프 변수나 람다 파라미터가 바깥 이름을 가리는 경우다.

```kotlin
fun trap(items: List<Int>) {
    val total = 0
    items.forEach { total ->        // 경고: 파라미터 total이 바깥 total을 가림
        // 여기의 total은 각 원소. 바깥 val total(=0)이 아님.
        println(total)
    }
    println(total)                  // => 0  (바깥 total은 절대 안 바뀜)
}
```

`total`을 누적하려던 의도였다면 이 코드는 조용히 틀린다 — 바깥 `total`은 `val`이라 애초에 누적도 안 되고, 안쪽 `total`은 매번 새 원소일 뿐이다. 컴파일러의 섀도잉 경고를 무시하지 말아야 하는 이유다.

### 7.3 for 루프 변수는 매 반복 새 변수

한 가지 코틀린의 좋은 결정. `for` 루프의 변수는 **매 반복마다 새로운 `val`** 이다(재대입 불가이며, 반복마다 독립).

```kotlin
val actions = mutableListOf<() -> Int>()
for (i in 1..3) {
    actions.add { i }        // 각 람다가 캡처하는 i는 그 반복의 i
}
println(actions.map { it() })   // => [1, 2, 3]
```

자바의 옛 `for (int i = ...)`에서는 `i`가 하나뿐이라 람다가 캡처하면 마지막 값을 공유하는 고전적 함정이 있었다. 코틀린 `for`는 각 반복의 변수를 독립적으로 캡처하므로 `[1, 2, 3]`이 정확히 나온다. 이 "루프 변수가 `val`이며 반복마다 새로 생긴다"는 성질은 [[14 - 클로저와 캡처]]의 캡처 의미론과 직결되며, 거기서 정본으로 다룬다. 지금 기억할 것: **코틀린 `for` 변수는 `var`가 아니라 반복마다 새 `val`이다** — 그래서 루프 안에서 `i = i + 1` 같은 재대입은 불가하다.

## 8. 타입 추론과 명시, 그리고 컴파일된 형태

### 8.1 추론의 기본 규칙

`val`/`var`는 오른쪽 초기값에서 타입을 추론한다. 정수 리터럴은 `Int`, 실수 리터럴은 `Double`이 기본이다([[07 - 수 1 - Int와 Long과 부동소수점]] 참고).

```kotlin
val a = 5          // Int
val b = 5L         // Long
val c = 5.0        // Double
val d = 'x'        // Char
val e = "text"     // String
val f = listOf(1)  // List<Int>
```

명시적 타입이 필요한 경우는 세 가지다. 첫째, 추론 결과보다 넓은/좁은 타입을 원할 때(`val x: Long = 5` — 리터럴 `5`를 `Long`으로). 둘째, 초기화를 지연하는 선언에서(3.2의 `val grade: String`). 셋째, 공개 API의 안정성을 위해 반환·프로퍼티 타입을 명시로 못박을 때. 지역 변수에서는 추론에 맡기는 것이 관용이다.

```kotlin
val x: Long = 5           // 명시로 Long 지정 (안 그러면 Int)
val n: Number = 5         // 상위 타입으로 넓혀 명시
```

> **흔한 오해**: "타입 추론이니 동적 타이핑 아닌가?"는 오해다. 코틀린은 정적·강타입 언어다. 추론은 컴파일러가 타입을 *생략하게 허용*할 뿐, 타입은 컴파일 타임에 확정된다. `val a = 5` 뒤에 `a = "text"`는 재대입 금지 이전에 **타입 불일치**로도 막힌다. 이 정적성의 뿌리는 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]와 [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]가 다룬다.

### 8.2 지역 변수의 컴파일 형태 (JVM 백엔드)

JVM 백엔드에서 지역 `val`/`var`는 어떻게 컴파일될까? 흥미롭게도 지역 변수 수준에서는 둘의 바이트코드 차이가 거의 없다.

```text
JVM 백엔드에서:
- 지역 val, var 모두 메서드의 지역 변수 슬롯(local variable slot)에 놓인다.
- 바이트코드의 지역 변수에는 'final' 개념이 없다.
  즉 val의 "재대입 불가"는 *컴파일러가 강제*하는 것이지,
  바이트코드에 final 표식이 남는 것이 아니다.
- 따라서 지역 val/var의 런타임 표현은 사실상 동일. 차이는 컴파일 타임 검사뿐.
```

이 사실이 말해 주는 것: **`val`의 안전성은 "런타임에 값을 잠그는" 것이 아니라 "컴파일러가 재대입 코드를 거부하는" 것이다.** [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]의 널 안전성이 대부분 컴파일 타임 보장(M7)인 것과 같은 결이다. 코틀린의 여러 안전장치는 런타임 비용 없이 컴파일러가 지불한다.

### 8.3 멤버·최상위 변수의 컴파일 형태 (JVM 백엔드)

반면 클래스 멤버와 최상위 변수는 프로퍼티로 취급되어 접근자와 필드가 생긴다. 이 부분의 정본은 [[22 - 프로퍼티와 백킹 필드]]이지만, 이 장의 대조를 위해 개략만 본다.

```text
JVM 백엔드에서, 커스텀 접근자 없는 프로퍼티 기준:
- 멤버 val x → private final 백킹 필드 + public 게터 getX()
- 멤버 var x → private 백킹 필드 + getX() + setX()
- 최상위 val/var → 파일명Kt 클래스의 static 필드 + static 게터/세터
- const val    → public static final 필드 (ConstantValue) + 사용처 인라인 (6.3)
- lateinit var → non-final 백킹 필드 + 초기화 검사 게터 (4.2)
```

즉 지역 변수와 달리 멤버/최상위에서는 `val`이 실제로 `final` 필드로 컴파일되어 런타임 표현에도 흔적이 남는다. 자바 코드에서 코틀린 프로퍼티를 볼 때 `getX()`/`setX()`로 보이는 이유가 여기 있고, 이 상호운용의 세부는 [[45 - Java 상호운용]]가 소유한다.

### 8.4 왜 이 세 가지 형태를 알아야 하는가

지역/멤버/최상위의 컴파일 형태가 다르다는 사실은 실무에서 세 갈래로 체감된다. 첫째, `const`가 "최상위·object·companion에만" 붙는 이유(6.2)가 이 형태 차이에서 나온다 — 인스턴스에 매인 필드는 정적 상수가 못 되기 때문이다. 둘째, `lateinit`이 멤버(및 최상위)에는 자연스럽지만 지역 변수에선 드문 이유도 여기 있다. 셋째, [[23 - 위임 프로퍼티]]의 `by lazy`가 멤버에서 어떻게 저장되는지도 이 필드 모델 위에서 이해된다. 결국 "이 이름이 어디에 선언되었는가"가 "그것이 무엇으로 컴파일되는가"를 결정하고, 그것이 다시 "무슨 한정자를 붙일 수 있는가"를 결정한다.

## 9. 전체 종합 — 초기화 전략 결정 지도

### 9.1 다섯 도구의 자리

이 장의 도구들을 한 지도에 놓자. 축은 두 개다 — "값을 언제 결정하는가"(컴파일 타임 ↔ 런타임 지연)와 "재대입이 가능한가".

```text
                 값 결정: 컴파일 타임 ─────────────► 런타임 즉시 ─────────► 런타임 지연

  재대입 불가:   const val            val (즉시 초기화)       val ... by lazy
  (read-only)    (인라인 상수)         (일반 읽기전용)          (첫 접근 시 계산)

  재대입 가능:   (해당 없음)           var (즉시 초기화)       lateinit var
  (mutable)                            (일반 가변)              (밖에서 나중 대입)
```

- **`const val`**: 절대 안 바뀌는 리터럴 상수(원시/String). 컴파일 타임에 확정, 인라인.
- **`val`**: 기본 선택. 재대입 불가. 값은 실행 중 결정될 수 있으나 한 번 정해지면 이름은 고정.
- **`val ... by lazy`**: 비싼 계산을 첫 사용까지 미루고 캐시. 스스로 계산.
- **`var`**: 정말로 값이 바뀌어야 할 때만.
- **`lateinit var`**: 비-널 프로퍼티인데 생성자에선 못 채우고 외부가 나중에 밀어 넣을 때.

### 9.2 결정 순서 (의사 결정 흐름)

```text
값이 필요할 때 자문하라:

1. 컴파일 타임에 값이 고정된 원시/String 리터럴인가?
     예 → const val
     아니오 ↓
2. 한 번 정해지면 안 바뀌는가?
     아니오(계속 바뀜) → var  (정말 필요한지 재고)
     예 ↓
3. 생성 시점에 바로 값을 줄 수 있는가?
     예 → val x = ...           (기본 선택, 가장 흔함)
     아니오 ↓
4. 처음 읽힐 때 스스로 계산해서 캐시하면 되는가?
     예 → val x by lazy { ... }
     아니오(밖에서 나중에 채워짐) ↓
5. 비-널 타입이고 첫 사용 전 반드시 채워지는 계약이 있는가?
     예 → lateinit var
     아니오(있을 수도 없을 수도) → val/var x: T?  (정직하게 nullable)
```

이 흐름을 따르면, 이 장 서두의 질문들이 하나로 회수된다. "`val`이 불변인가?"는 아니오 — 재대입 불가일 뿐이며 가리키는 객체는 변할 수 있다(M3). "왜 빈 변수가 없는가?"는 확정 대입 분석이 초기화를 강제하기 때문이며, 그럼에도 모든 경로가 대입하면 지연 선언이 허용된다. "`const val`과 `val`이 같은가?"는 아니오 — `const`는 컴파일 타임 상수로 값이 사용처에 인라인된다(M36). "`lateinit`이 결국 nullable인가?"도 아니오 — 그것은 비-널 타입의 초기화를 미룰 뿐이며, 그래서 미초기화 접근은 NPE가 아니라 `UninitializedPropertyAccessException`이다(M9). 이름과 대상을 분리해 보고, 초기화가 결정되는 시간 축을 의식하는 순간, 다섯 도구의 자리가 저절로 정해진다.

### 9.3 다음 장으로

변수라는 이름의 삶 — 선언·초기화·재대입·스코프 — 을 훑었다. 다음으로 이 이름들이 함수의 문맥에서 어떻게 다뤄지는지가 남았다. 함수 파라미터가 왜 전부 재대입 불가인지(1.3), 기본 인자와 이름 붙은 인자가 초기화를 어떻게 관용화하는지는 [[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]가 잇는다. 그리고 이 장에서 예고만 한 프로퍼티의 백킹 필드와 커스텀 접근자, `by lazy`의 위임 메커니즘은 각각 [[22 - 프로퍼티와 백킹 필드]]와 [[23 - 위임 프로퍼티]]가 정본으로 판다.

## 핵심 요약

- **`val`은 불변(immutable)이 아니라 재대입 불가(read-only)다. 이름표를 다시 못 묶을 뿐, 그 이름이 가리키는 객체의 내부는 얼마든지 변할 수 있다** — `val list = mutableListOf(); list.add(x)`가 정상 동작하는 이유. (M3)
- **가변성은 이름(`val`/`var`)과 타입(`List`/`MutableList`)이라는 두 직교 축의 곱으로 결정된다.** `val` 하나로는 불변도 스레드 안전도 만들어지지 않는다.
- **코틀린엔 값 없는 변수가 없다.** 확정 대입 분석(definite assignment)이 "읽기 전 모든 경로에서 대입됨"을 강제한다. 그래서 지연 선언(`val x: T` 후 분기마다 대입)은 허용되되, 어느 경로가 빠지면 컴파일 에러다. `throw`/`return`(`Nothing` 타입)으로 끝나는 경로는 대입 의무에서 면제된다.
- **`lateinit`은 nullable이 아니다. 비-널 타입 프로퍼티의 초기화 시점을 미루는 약속이다.** 그래서 미초기화 접근은 `NullPointerException`이 아니라 `UninitializedPropertyAccessException`을 던진다 — "값이 null"과 "값이 아직 없음"은 다른 상태다. (M9)
- **`lateinit`의 제약이 그 정체를 말한다**: `var`에만, 비-널에만, 원시 타입 불가(JVM 백엔드의 null 센티넬 때문), 커스텀 접근자 불가. `::x.isInitialized`로 초기화 여부를 검사할 수 있으나 상시 방어 습관은 냄새다.
- **`lateinit`은 밖에서 값을 밀어 넣는(push) 모델, `by lazy`는 첫 접근 때 스스로 계산하는(pull) 모델이다.** `lateinit var`는 재대입 가능·비-널 전용, `val by lazy`는 고정·nullable/원시 허용·스레드 안전 모드 선택 가능.
- **`const val`은 그냥 `val`이 아니라 컴파일 타임 상수다.** 값이 컴파일 시점에 확정되고, JVM 백엔드에서 사용처마다 리터럴로 인라인(복사)된다. 원시 타입·`String`만, 최상위·`object`·`companion`에만, 컴파일 타임 상수식으로만. (M36)
- **`const`의 인라인은 바이너리 호환성의 함정이다.** 라이브러리의 `const` 값을 바꿔도 참조 측을 재컴파일하지 않으면 낡은 값이 박힌 채 남는다. 반대로 애노테이션 인자·`when` 상수 분기처럼 컴파일 타임 값이 *필요한* 자리에서는 `const`만 쓸 수 있다.
- **함수 파라미터와 `for` 루프 변수는 언제나 재대입 불가다.** `for`의 변수는 `var`가 아니라 반복마다 새로 생기는 `val`이라, 람다가 캡처해도 각 반복의 값을 정확히 붙든다.
- **섀도잉은 에러가 아니라 경고다.** 안쪽 스코프가 같은 이름으로 바깥을 가릴 뿐 바깥 변수는 살아 있다. 누적하려다 새 변수를 만드는 실수를 컴파일러가 경고로 잡아 준다.
- **`val`의 안전성은 런타임이 아니라 컴파일러가 지불한다.** JVM 백엔드에서 지역 `val`은 바이트코드에 `final` 표식조차 남기지 않는다 — 재대입 거부는 컴파일 타임 검사일 뿐이다. 반면 멤버/최상위 `val`은 `final` 필드로 컴파일되어 흔적을 남긴다.
- **선언 위치(지역/멤버/최상위)가 컴파일 형태를 결정하고, 그것이 다시 붙일 수 있는 한정자를 결정한다.** `const`가 최상위·`object`·`companion`에만 붙는 것도, `lateinit`이 멤버에 자연스러운 것도 이 형태 차이에서 나온다.

## 연결 노트

- [[10 - 불리언과 동등성과 동일성]] — 앞 장. "값이 같음"과 "같은 객체"의 구분(`==`/`===`)이 이 장의 "이름표와 객체의 분리"로 이어진다. `val`이 고정하는 것이 참조라는 통찰의 전제.
- [[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]] — 다음 장. 함수 파라미터가 왜 전부 재대입 불가인지, 기본 인자·이름 붙은 인자가 초기화를 어떻게 관용화하는지 잇는다.
- [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]] — `val`이 스마트 캐스트를 여는 열쇠인 이유(M13), `lateinit`을 nullable과 대조하는 근거, 안전성이 컴파일 타임 보장(M7)이라는 결.
- [[22 - 프로퍼티와 백킹 필드]] — 멤버 `val`/`var`가 백킹 필드와 접근자로 컴파일되는 정본. 이 장의 8.3을 정밀하게 판다.
- [[23 - 위임 프로퍼티]] — `by lazy`를 포함한 위임 프로퍼티의 일반 메커니즘(`getValue`/`setValue`, `KProperty`)의 정본.
- [[21 - 클래스와 생성자]] — 프로퍼티 초기화 순서(주 생성자 → 초기화자 → `init`)와 부 생성자 위임(M46)의 정본. 이 장 3.3의 "프로퍼티는 생성 시 초기화 완료" 규칙을 확장한다.
- [[24 - 상속과 오버라이딩과 초기화 순서]] — 상속이 얽힐 때 초기화 순서의 함정(M47). open 멤버를 생성자에서 부르는 위험.
- [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]] — 확정 대입 분석에서 `throw`/`return` 경로가 면제되는 근거인 바닥 타입 `Nothing`.
- [[14 - 클로저와 캡처]] — `for` 루프 변수가 반복마다 새 `val`이라 캡처가 안전한 이유의 정본. `var` 캡처와의 대비.
- [[28 - object와 companion - 싱글턴과 동반 객체]] — `const val`이 `object`/`companion` 멤버에만 붙는 이유. 싱글턴 멤버가 정적 상수로 취급되는 근거.
