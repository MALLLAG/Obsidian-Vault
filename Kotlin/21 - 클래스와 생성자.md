**이 장이 답하는 질문:**

- `class C(val x: Int)` 한 줄에는 대체 몇 개의 서로 다른 개념이 압축되어 있는가?
- 주 생성자(primary constructor)에는 왜 코드를 쓸 수 없고, 그 자리를 `init` 블록이 어떻게 메우는가?
- 프로퍼티 초기화자와 `init` 블록은 뒤섞여 있을 때 어떤 순서로 실행되는가? 그 순서를 결정하는 규칙은 무엇인가?
- 부 생성자(secondary constructor)가 있으면 주 생성자의 초기화(프로퍼티 초기화 + `init`)는 건너뛰는가? (M46)
- 주 생성자가 아예 없는 클래스에서 `init` 블록은 언제, 어느 생성자에서 실행되는가?
- 부 생성자는 대체 언제 필요한가? "기본 인자로 부 생성자를 대체하라"는 조언의 한계는 어디인가?
- 생성자를 `private`으로 만들거나 애노테이션을 붙이려면 왜 갑자기 `constructor` 키워드가 필요해지는가?
- 코틀린에 `new`가 없다는 사실은 단순한 문법 차이인가, 아니면 그 이상의 설계 선택인가?

---

[[20 - 구조 분해]]에서 우리는 이미 만들어진 객체를 여러 이름으로 *풀어내는* 문법을 다뤘다. `componentN` 관례에 기대어 `val (x, y) = point`가 어떻게 위치 기반으로 분해되는지 보았다. 그러나 그 모든 논의는 "객체가 이미 존재한다"는 전제 위에 서 있었다. 이 장은 그 전제 이전, 즉 객체가 *어떻게 태어나는가*를 정면으로 다룬다. 클래스 선언의 문법, 주 생성자와 부 생성자, 그리고 인스턴스가 만들어질 때 코틀린 런타임이 정확히 어떤 순서로 필드를 채우는가.

이 장의 경계를 못박아 두자. 여기서는 **하나의 클래스가 자기 자신을 초기화하는 메커니즘**만 다룬다. 상속 계층을 타고 올라가는 초기화 순서(상위 생성자가 하위보다 먼저 도는 규칙, `open` 멤버를 생성자에서 호출하는 함정 M47)는 [[24 - 상속과 오버라이딩과 초기화 순서]]가 소유한다. 프로퍼티가 백킹 필드를 갖는지, 게터/세터가 어떻게 컴파일되는지(M35)는 [[22 - 프로퍼티와 백킹 필드]]로 위임한다. `equals`/`copy`를 공짜로 얻는 데이터 클래스는 [[27 - 데이터 클래스]], 인스턴스가 하나뿐인 `object`는 [[28 - object와 companion - 싱글턴과 동반 객체]]의 영역이다. 이 장은 그 모든 것이 딛고 서는 *토대*—생성자와 초기화—에 집중한다.

논증의 궤적은 이렇다. 먼저 클래스 선언의 최소 형태에서 출발해 "코틀린에는 `new`가 없다"는 사실이 무엇을 뜻하는지 본다. 그다음 클래스 이름 뒤에 괄호로 붙는 주 생성자를 해부하고, `val`/`var` 유무가 만드는 결정적 차이를 짚는다. 주 생성자가 코드를 담을 수 없다는 제약이 왜 `init` 블록을 낳았는지, 그리고 프로퍼티 초기화자와 `init`이 어떤 순서로 인터리빙(interleaving)되는지를 실행 순서 다이어그램으로 확정한다. 여기까지가 이 장의 심장이다. 이어서 부 생성자와 `this(...)` 위임을 다루며 이 장의 소유 오개념 M46—"부 생성자가 있으면 주 생성자 초기화는 안 돈다"—을 정면으로 반박한다. 마지막으로 기본 인자가 부 생성자를 대체하는 관용구, 생성자 가시성, 그리고 JVM 백엔드에서 이 모든 것이 어떤 바이트코드로 내려앉는지를 확인한다.

한 가지 예고. 코틀린의 생성자 설계는 "흔한 경우는 한 줄로, 드문 경우만 장황하게"라는 실용주의의 결정체다. `class Point(val x: Int, val y: Int)` 한 줄이 자바에서라면 필드 선언 2줄 + 생성자 6줄 + 게터 2개로 불어난다. 그 압축이 어떻게 가능한지, 그리고 그 압축이 숨기고 있는 실행 의미론이 무엇인지를 끝까지 파는 것이 이 장의 목표다.

## 1. 클래스 선언의 최소 형태와 `new`의 부재

### 1.1 가장 작은 클래스

코틀린에서 클래스를 선언하는 가장 짧은 형태는 이름 하나다.

```kotlin
class Empty
```

중괄호도, 괄호도 없다. 이 한 줄은 완결된 선언이다. 자바라면 최소한 `class Empty {}`처럼 빈 본문을 강제하지만, 코틀린은 본문이 필요 없으면 중괄호 자체를 생략한다. 인스턴스를 만드는 것도 마찬가지로 짧다.

```kotlin
val e = Empty()
// => Empty 타입의 인스턴스
```

여기서 첫 번째 놀라움. `new`가 없다. 자바의 `new Empty()`, C++의 `new Empty`, C#의 `new Empty()` 모두 키워드를 요구하지만 코틀린은 클래스 이름을 함수처럼 *호출*한다. 이것은 단순한 타이핑 절약이 아니라 언어의 일관된 세계관의 일부다.

### 1.2 `new`가 없다는 것의 의미

`new`를 없앤 결정은 코틀린이 "생성자 호출"과 "일반 함수 호출"을 문법적으로 구분하지 않기로 했음을 뜻한다. `Empty()`는 표면적으로 `println()`과 같은 모양이다. 이 통일성 덕분에 여러 것이 자연스러워진다.

첫째, **팩토리 함수와 생성자가 호출 지점에서 구별되지 않는다.** 오늘 `class Rational(...)`을 생성자로 노출했다가, 내일 캐싱이 필요해져 `fun Rational(...)`이라는 최상위 함수로 바꿔도 호출부 `Rational(1, 2)`는 그대로다. 자바였다면 `new Rational(...)`에서 `Rational.of(...)`로 전면 수정해야 했을 것이다. 코틀린에서는 대문자로 시작하는 함수 이름(관례적으로 생성자를 흉내 낸다)이 이 전환을 매끄럽게 만든다.

```kotlin
// 처음엔 생성자
class Color(val rgb: Int)
val red = Color(0xFF0000)

// 나중에 캐싱이 필요하면 — 호출부는 그대로 Color(...)
// class Color private constructor(val rgb: Int) { companion object { ... } }
// fun Color(rgb: Int): Color = cache.getOrPut(rgb) { Color(rgb) }  // 개념 예시
```

둘째, **생성자 참조가 `::Empty`로 균일하다.** 함수 참조 `::foo`와 완전히 같은 문법으로 `::Empty`가 생성자를 일급 값으로 만든다([[13 - 함수 타입과 람다와 함수 참조]]). `list.map(::Person)`처럼 생성자를 고차 함수에 넘길 수 있다.

> **역사 메모**: `new` 키워드의 제거는 코틀린만의 발명이 아니다. 스칼라, 파이썬, 러스트(튜플 구조체 `Point(1, 2)`) 등 여러 현대 언어가 같은 선택을 했다. 자바가 `new`를 유지한 것은 1990년대에 "힙 할당은 명시적이고 비용이 드는 연산이니 문법으로 눈에 띄어야 한다"는 관점이 강했기 때문이다. 코틀린은 그 관점을 물려받지 않았다. 다만 JVM 백엔드에서 `Empty()`는 여전히 바이트코드 `new Empty; dup; invokespecial Empty.<init>()V`로 컴파일된다—즉 *실행 의미*는 자바와 동일하고, 사라진 것은 소스 표면의 키워드뿐이다.

### 1.3 헤더와 본문

클래스 선언은 크게 **헤더(header)** 와 **본문(body)** 으로 나뉜다.

```text
class  Name  <T>  (헤더: 주 생성자)  : SuperType()  where ...   {  본문  }
       ↑     ↑     ↑                  ↑              ↑              ↑
      이름  타입   주 생성자          상위 타입      제약           멤버 선언
            파라미터                  위임          (제네릭)
```

이 장이 다루는 것은 주로 헤더의 괄호 안—주 생성자—과 본문 안의 `init` 블록, 부 생성자다. 타입 파라미터 `<T>`는 [[33 - 제네릭 1 - 타입 파라미터와 변성]], 상위 타입 위임 `: SuperType()`은 [[24 - 상속과 오버라이딩과 초기화 순서]]가 소유한다.

본문이 있으면 중괄호로 감싼다.

```kotlin
class Counter {
    var count = 0
    fun increment() { count++ }
}
```

본문 안에는 프로퍼티, 함수, `init` 블록, 부 생성자, 중첩 클래스([[31 - 중첩 클래스와 이너 클래스와 익명 객체]]), 동반 객체([[28 - object와 companion - 싱글턴과 동반 객체]])가 온다. 선언 순서는 대체로 자유롭다—함수는 뒤에 선언된 프로퍼티도 참조할 수 있다(전방 참조). 그러나 이 자유에는 딱 하나의 예외가 있는데, 바로 **초기화자와 `init` 블록의 실행 순서**다. 이것이 4절의 주제이며 이 장 전체가 겨누는 과녁이다.

## 2. 주 생성자 — 헤더에 접힌 생성자

### 2.1 괄호 하나에 담긴 것

주 생성자는 클래스 이름 바로 뒤에 괄호로 붙는다.

```kotlin
class Person(firstName: String, age: Int)
```

`firstName`과 `age`는 주 생성자의 **파라미터**다. 여기서 결정적으로 헷갈리기 쉬운 지점. 이 상태의 `firstName`과 `age`는 **클래스의 프로퍼티가 아니다.** 단지 생성자에 전달되는 값일 뿐이며, 인스턴스가 만들어진 뒤에는 사라진다(어디서도 저장하지 않았으므로).

```kotlin
class Person(firstName: String, age: Int)

val p = Person("Ada", 36)
// p.firstName  // 컴파일 에러: unresolved reference — 프로퍼티가 아님
```

파라미터는 오직 **주 생성자의 초기화 스코프 안**에서만 살아 있다. 즉 프로퍼티 초기화자와 `init` 블록 안에서는 쓸 수 있지만, 일반 멤버 함수에서는 볼 수 없다.

```kotlin
class Person(firstName: String, age: Int) {
    val displayName = firstName.uppercase()  // OK: 초기화자에서 파라미터 사용
    init {
        require(age >= 0)                     // OK: init에서 파라미터 사용
    }
    fun greet() {
        // println(firstName)  // 컴파일 에러: firstName은 여기서 안 보임
        println(displayName)   // OK: 저장된 프로퍼티
    }
}
```

### 2.2 `val`/`var`가 만드는 변신

파라미터 앞에 `val`이나 `var`를 붙이는 순간, 그것은 파라미터인 동시에 **프로퍼티**가 된다.

```kotlin
class Person(val firstName: String, var age: Int)

val p = Person("Ada", 36)
println(p.firstName)  // => Ada  — 이제 프로퍼티다
p.age = 37            // var이므로 재대입 가능
```

이 한 글자(`val`/`var`)가 하는 일을 자바 코드로 풀어 쓰면 그 압축률이 드러난다.

```java
// Kotlin: class Person(val firstName: String, var age: Int)
// 에 대응하는 자바:
public final class Person {
    private final String firstName;
    private int age;
    public Person(String firstName, int age) {
        this.firstName = firstName;
        this.age = age;
    }
    public String getFirstName() { return firstName; }
    public int getAge() { return age; }
    public void setAge(int age) { this.age = age; }
}
```

코틀린 한 줄이 자바에서는 필드 2개 + 생성자 + 게터 2개 + 세터 1개로 펼쳐진다. `val`은 게터만, `var`는 게터와 세터를 만든다(백킹 필드의 실제 생성 조건은 [[22 - 프로퍼티와 백킹 필드]]에서 정밀하게 다룬다). 여기서 기억할 것은 세 가지 파라미터 형태가 서로 다르다는 사실이다.

| 헤더 표기 | 파라미터인가 | 프로퍼티인가 | 재대입 |
|---|---|---|---|
| `Person(firstName: String)` | 예 | 아니오 | — (초기화 스코프에서만 읽기) |
| `Person(val firstName: String)` | 예 | 예 (읽기 전용) | 불가 |
| `Person(var firstName: String)` | 예 | 예 (읽기·쓰기) | 가능 |

> **흔한 오해**: "생성자 파라미터는 무조건 프로퍼티가 된다"는 생각은 자바(생성자 인자를 필드에 `this.x = x`로 옮기는 관습)에서 넘어온 착각이다. 코틀린에서 `val`/`var` 없는 파라미터는 필드로 저장되지 않는다. 초기화가 끝나면 소멸한다. 이것은 낭비가 아니라 의도적이다—파생 프로퍼티만 저장하고 원본 인자는 버리고 싶을 때(예: `class Angle(degrees: Double) { val radians = degrees * PI / 180 }`) 자연스럽게 표현된다.

이 구분은 메모리 레이아웃에도 그대로 반영된다. `val`/`var`가 붙은 파라미터만 인스턴스 필드로 남고, 붙지 않은 파라미터는 생성자 실행이 끝나면 스택에서 사라진다.

```text
class Angle(degrees: Double) {   // degrees: 필드 아님 (초기화 후 소멸)
    val radians = degrees * PI / 180   // radians: 필드로 저장
}

인스턴스 메모리 레이아웃 (JVM 백엔드, 개념):
┌────────────────────────┐
│ Angle 인스턴스          │
│  radians: double  ← 저장됨  │
│  (degrees는 없음)        │  ← 필드로 남지 않음
└────────────────────────┘
```

같은 값을 나중에 다시 쓰고 싶다면 `val`을 붙여 저장해야 한다. "생성자 인자를 나중에 메서드에서 읽으려는데 안 보인다"는 초보자의 흔한 당황은 바로 이 구분을 놓친 결과다.

### 2.3 `constructor` 키워드의 생략

방금까지 본 형태에서 `constructor`라는 키워드는 어디에도 없었다. 사실 주 생성자의 정식 문법은 이렇다.

```kotlin
class Person constructor(val firstName: String)
```

`constructor` 키워드는 **가시성 한정자나 애노테이션이 없을 때 생략 가능**하다. 대부분의 코드에서 생략하므로 눈에 익은 형태는 괄호만 있는 쪽이다. 그러나 생성자에 가시성을 주거나(`private`) 애노테이션을 붙이려면 키워드가 되살아난다(8절에서 상세히).

```kotlin
class Registry private constructor()           // 가시성 → constructor 필수
class Service @Inject constructor(dep: Dep)     // 애노테이션 → constructor 필수
```

### 2.4 빈 괄호와 괄호 없음

주 생성자가 파라미터를 받지 않으면 빈 괄호가 된다.

```kotlin
class Widget()   // 명시적 빈 주 생성자
class Widget     // 주 생성자 자체를 생략 (암시적 기본 생성자와 동등)
```

둘의 차이는 미묘하다. `class Widget`처럼 괄호를 아예 생략하면 **주 생성자가 없는** 상태로 간주되지만, 파라미터 없는 인스턴스화 `Widget()`는 여전히 가능하다(컴파일러가 인자 없는 생성자를 제공). 실용적으로 대부분의 경우 둘은 동등하게 동작한다. 명시적 `()`는 뒤에 가시성이나 애노테이션을 붙일 자리를 마련해 준다는 정도의 차이다. 상속을 위해 상위 클래스 생성자를 위임 호출할 때(`: Base()`)는 이 미묘함이 표면화되는데, 그 논의는 [[24 - 상속과 오버라이딩과 초기화 순서]]로 넘긴다.

## 3. `init` 블록 — 주 생성자가 담을 수 없는 코드

### 3.1 왜 주 생성자에는 코드를 못 쓰는가

주 생성자에는 **실행할 코드를 직접 넣을 수 없다.** 헤더의 괄호는 파라미터 목록만 담을 뿐, 문(statement)을 담는 본문이 없다. 자바처럼 생성자 몸통에 로직을 적는 자리가 헤더에는 존재하지 않는다.

```kotlin
class Person(name: String) {
    // 헤더 괄호 안에는 println("...") 같은 코드를 쓸 자리가 없다
}
```

이 제약을 메우는 것이 `init` 블록이다. `init`은 "주 생성자의 몸통"이라고 생각하면 정확하다. 주 생성자가 호출될 때 실행되어야 할 코드를 담는다.

```kotlin
class Person(name: String) {
    val displayName: String
    init {
        require(name.isNotBlank()) { "name must not be blank" }
        displayName = name.trim().replaceFirstChar { it.uppercase() }
        println("Person 생성: $displayName")
    }
}

val p = Person("  ada  ")
// => "Person 생성: Ada" 출력
// p.displayName == "Ada"
```

`init` 블록 안에서는 주 생성자 파라미터(`name`)와, 그 위에 이미 선언·초기화된 프로퍼티를 자유롭게 참조할 수 있다.

### 3.2 여러 개의 `init` 블록

`init` 블록은 클래스 하나에 여러 개 둘 수 있다. 이들은 **선언된 순서대로** 실행된다.

```kotlin
class Trace {
    init { println("첫 번째 init") }
    init { println("두 번째 init") }
    init { println("세 번째 init") }
}
Trace()
// => 첫 번째 init
//    두 번째 init
//    세 번째 init
```

여러 `init`을 둘 수 있다는 사실 자체는 사소해 보이지만, 이것이 다음 절의 핵심—프로퍼티 초기화자와의 인터리빙—과 맞물리면 초기화 순서가 미묘해진다.

### 3.3 프로퍼티 초기화자도 "코드"다

여기서 중요한 개념 전환. 프로퍼티에 붙는 초기화 식(`val x = ...`)도 실행 시점을 갖는 **코드**다. 상수처럼 보이는 `val area = width * height`도 사실은 생성자가 도는 순간 계산되는 표현식이다.

```kotlin
class Rectangle(val width: Int, val height: Int) {
    val area = width * height   // 생성 시점에 계산되어 저장됨
    val perimeter = 2 * (width + height)
}
```

`area`와 `perimeter`는 리터럴이 아니라 계산 결과다. 이 계산이 언제 일어나는지는 `init` 블록의 실행과 함께 하나의 순서열로 엮인다. 코틀린 명세는 프로퍼티 초기화자와 `init` 블록을 **동등한 지위의 초기화 단계**로 취급하며, 둘을 소스에 나타난 순서 그대로 실행한다. 이 규칙이 다음 절의 전부다.

> **명세 정밀**: 코틀린 언어 명세는 프로퍼티 초기화자와 `init` 블록을 합쳐 클래스의 "초기화 코드(initialization code)"라 부르고, 이들이 클래스 본문에 나타난 텍스트 순서(top-to-bottom)대로 실행됨을 보장한다. 이 순서는 컴파일러 최적화로도 재배열되지 않는다—관찰 가능한 부수효과(예외 던지기, 로그 출력, 다른 프로퍼티 읽기)를 가질 수 있으므로 순서가 의미론의 일부다.

### 3.4 `init`과 프로퍼티 초기화자, 언제 무엇을?

둘 다 초기화 코드지만 쓰임이 갈린다. 값을 계산해 프로퍼티에 담는 것은 초기화자로, 검증·로깅·여러 프로퍼티를 함께 세팅하는 로직은 `init`으로 두는 것이 관례다.

| 구분 | 프로퍼티 초기화자 | `init` 블록 |
|---|---|---|
| 형태 | `val x = 식` | `init { 문들 }` |
| 주 목적 | 단일 프로퍼티에 값 대입 | 검증·부수효과·복합 로직 |
| 여러 프로퍼티 동시 세팅 | 불가(하나씩) | 가능 |
| 조건 분기로 값 정하기 | `= if(...) ... else ...`로 제한적 | 자유롭게 `if`/`when`/루프 |
| 파라미터·앞 프로퍼티 참조 | 가능 | 가능 |

특히 "선언은 위에서 하되 값은 조건에 따라 `init`에서 대입"하는 패턴이 유용하다.

```kotlin
class HttpStatus(code: Int) {
    val category: String   // 선언만 (초기화자 없음)
    init {
        category = when (code / 100) {   // init에서 조건에 따라 대입
            2 -> "성공"
            4 -> "클라이언트 오류"
            5 -> "서버 오류"
            else -> "기타"
        }
    }
}
HttpStatus(404).category   // => "클라이언트 오류"
```

이때 `val category`는 초기화자 없이 선언만 하고 `init`에서 정확히 한 번 대입한다. 컴파일러는 "모든 실행 경로에서 `val`이 정확히 한 번 대입되는가"를 확정 대입 분석(definite assignment analysis)으로 검사한다—경로에 따라 대입이 빠지거나 두 번 되면 컴파일 에러다.

## 4. 초기화 실행 순서 — 이 장의 심장

### 4.1 전체 순서 다이어그램

`val obj = SomeClass(args)`가 실행될 때 정확히 무슨 일이 벌어지는가. 상속을 잠시 배제하고(상위 타입은 [[24 - 상속과 오버라이딩과 초기화 순서]]로), 단일 클래스의 초기화 순서를 그리면 다음과 같다.

```text
SomeClass(args) 호출
   │
   ▼
① 주 생성자 인자 평가 (호출 지점에서)
   │
   ▼
② (상위 타입 초기화 — 24장 소유, 여기선 생략)
   │
   ▼
③ 클래스 본문을 위에서 아래로 훑으며:
   ├─ 프로퍼티 초기화자를 만나면 → 그 식을 평가해 프로퍼티에 대입
   └─ init 블록을 만나면       → 그 블록을 실행
   (프로퍼티 초기화자와 init은 "한 줄기 순서"로 섞여 실행됨)
   │
   ▼
④ (부 생성자로 진입했다면) 부 생성자 본문 실행 — 6절
   │
   ▼
객체 완성, 참조 반환
```

핵심은 ③이다. 프로퍼티 초기화자와 `init` 블록은 **서로 다른 두 단계가 아니라, 소스 순서로 뒤섞인 하나의 순서열**이다.

### 4.2 인터리빙 실전

말보다 코드가 확실하다.

```kotlin
class Order(val id: Int) {
    val a = log("a 초기화자")           // 1
    init { log("첫 init") }             // 2
    val b = log("b 초기화자")           // 3
    init { log("둘째 init") }           // 4
    val c = log("c 초기화자")           // 5

    private fun log(msg: String): String {
        println(msg); return msg
    }
}

Order(1)
// => a 초기화자
//    첫 init
//    b 초기화자
//    둘째 init
//    c 초기화자
```

출력이 소스의 위→아래 순서와 정확히 일치한다. 프로퍼티 초기화자를 모두 먼저 처리하고 나서 `init`을 처리하는 것이 *아니다.* 텍스트에 나타난 대로 한 줄 한 줄 실행한다.

### 4.3 "선언 후 사용" 규칙 — 아직 초기화 안 된 프로퍼티

이 순서 규칙에는 강력한 안전 장치가 따라온다. **초기화자·`init` 블록은 자기보다 뒤에 선언된 프로퍼티를 읽을 수 없다.** 컴파일러가 정적으로 막는다.

```kotlin
class Broken {
    val first = second + 1   // 컴파일 에러: Variable 'second' must be initialized
    val second = 10
}
```

`first`를 계산하는 시점에 `second`는 아직 초기화 순서상 뒤에 있으므로 값이 없다. 코틀린은 이 "앞에서 뒤를 읽기"를 컴파일 타임에 진단한다. 이것은 자바의 함정—초기화 순서상 아직 0/`null`인 필드를 읽어도 컴파일러가 침묵하는 문제—을 언어 차원에서 제거한 것이다.

```java
// Java: 컴파일은 통과하지만, first를 second보다 위에 두면
// 초기화 순서상 second는 아직 0이라 first = 0+1 = 1이 된다 (의도한 11이 아님).
// 참조 타입이면 같은 상황에서 NullPointerException이 조용히 터진다.
class Broken {
    int first = second + 1;  // second가 아직 0 → first = 1 (버그의 씨앗)
    int second = 10;
}
```

단, 이 정적 검사에는 우회로가 존재한다. `init` 블록 안에서 **함수를 통해** 간접적으로 뒤 프로퍼티를 건드리면 컴파일러의 흐름 분석을 벗어날 수 있고, 그러면 런타임에 미초기화 상태(원시 타입은 0/false, 참조 타입은 `null`)를 읽게 된다. 특히 `open` 함수를 생성자에서 호출해 하위 클래스의 미초기화 필드를 건드리는 시나리오가 악명 높은데, 그것이 M47이며 [[24 - 상속과 오버라이딩과 초기화 순서]]의 소유다. 이 장의 단일 클래스 범위에서도 축소판 함정을 볼 수 있다.

```kotlin
class Sneaky {
    init {
        println(peek())   // peek()이 아직 초기화 안 된 value를 읽는다
    }
    val value: String = "설정됨"
    fun peek(): String = value
}
Sneaky()
// => null  (JVM 백엔드에서 value 필드는 이 시점에 아직 null)
//    선언은 String(비-널)인데 런타임엔 null이 관찰된다 — 초기화 순서의 함정
```

`value`의 선언 타입은 비-널 `String`인데도 `init`이 함수를 거쳐 미초기화 시점에 읽으면 `null`이 나온다. 코틀린의 널 안전성([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]])조차 초기화 순서의 허점 앞에서는 뚫린다. 규칙은 단순하다: **생성자/`init`에서 아직 초기화되지 않았을 수 있는 것을 함수로 우회해 읽지 마라.**

> **성능 주의**: 프로퍼티 초기화자를 여러 개 두는 것 자체는 성능 부담이 없다—각 초기화자는 어차피 한 번씩 실행될 대입일 뿐이다. 다만 `init` 블록에서 무거운 연산(파일 I/O, 네트워크, 큰 컬렉션 순회)을 하면 그것이 곧 "객체 생성 비용"이 된다는 점을 의식해야 한다. 생성은 흔히 뜨거운 경로(hot path)에 있으므로, 무거운 초기화는 [[23 - 위임 프로퍼티]]의 `by lazy`로 미루는 편이 나은 경우가 많다.

### 4.4 초기화 도중 예외

`init` 블록이나 프로퍼티 초기화자에서 예외가 던져지면 객체 생성은 실패하고, 부분적으로 초기화된 객체는 (정상 경로로는) 외부에 노출되지 않는다.

```kotlin
class BankAccount(initialBalance: Long) {
    val balance: Long = initialBalance
    init {
        require(balance >= 0) { "잔액은 음수가 될 수 없다: $balance" }
    }
}

val bad = BankAccount(-100)
// => IllegalArgumentException: 잔액은 음수가 될 수 없다: -100
//    bad 변수에는 아무것도 대입되지 않는다 (생성자가 예외로 종료)
```

이 패턴—`init`에서 `require`/`check`로 불변식(invariant)을 강제하는 것—은 코틀린에서 **유효하지 않은 객체가 애초에 존재할 수 없게** 만드는 관용구다. 자바의 "생성자에서 `IllegalArgumentException` 던지기"와 같은 목적이지만, `require`/`check`가 조건과 메시지를 간결하게 묶어 준다. `require`는 인자 검증(위반 시 `IllegalArgumentException`), `check`는 상태 검증(위반 시 `IllegalStateException`)이라는 관례가 있다.

## 5. 부 생성자 — `constructor`와 `this(...)` 위임

### 5.1 부 생성자의 문법

주 생성자만으로 부족할 때—예컨대 인자를 받는 방식이 여러 가지여야 할 때—본문 안에 `constructor` 키워드로 **부 생성자**를 추가한다.

```kotlin
class Point(val x: Int, val y: Int) {
    constructor(both: Int) : this(both, both)   // 대각선 점
}

val p1 = Point(3, 4)   // 주 생성자
val p2 = Point(5)      // 부 생성자 → this(5, 5) → 주 생성자
println("${p2.x}, ${p2.y}")   // => 5, 5
```

부 생성자의 헤더에는 `constructor` 키워드가 **필수**다(주 생성자와 달리 생략 불가). 그리고 `: this(...)`로 다른 생성자에 위임한다.

### 5.2 주 생성자가 있으면 위임은 필수

클래스에 주 생성자가 존재하면, **모든 부 생성자는 반드시 주 생성자로 위임**해야 한다. 직접(`this(...)`) 위임하거나, 다른 부 생성자를 거쳐 간접적으로라도 결국 주 생성자에 도달해야 한다.

```kotlin
class Temperature(val celsius: Double) {
    constructor(value: Double, unit: String) : this(
        when (unit) {
            "F" -> (value - 32) * 5 / 9
            "K" -> value - 273.15
            else -> value
        }
    )
    // 이 부 생성자는 계산 결과를 this(celsius)로 넘겨 주 생성자를 호출한다
}

val t = Temperature(212.0, "F")
println(t.celsius)   // => 100.0
```

주 생성자로 위임하지 않는 부 생성자는 컴파일 에러다.

```kotlin
class Bad(val x: Int) {
    constructor(s: String) {   // 컴파일 에러: Primary constructor call expected
        // this(...)로 주 생성자를 부르지 않았다
    }
}
```

이 강제 위임이 M46을 이해하는 열쇠다. 부 생성자가 결국 주 생성자를 부른다는 것은, 주 생성자에 딸린 초기화(프로퍼티 초기화자 + `init` 블록)가 **부 생성자 본문보다 반드시 먼저** 실행된다는 뜻이기 때문이다. 다음 절에서 정면으로 다룬다.

### 5.3 위임 체인

부 생성자들이 서로 위임하는 체인을 만들 수 있다.

```kotlin
class Pizza(val size: String, val toppings: List<String>) {
    constructor(size: String) : this(size, emptyList())
    constructor() : this("medium")   // 부 생성자 → 부 생성자 → 주 생성자
}

Pizza()
// => this("medium") → this("medium", emptyList()) → 주 생성자(size, toppings)
```

체인의 끝에는 언제나 주 생성자가 있다. 위임의 방향은 항상 "더 구체적인 생성자 → 더 근본적인 생성자"이며, 순환 위임(`A → B → A`)은 컴파일 에러다.

### 5.4 자바의 텔레스코핑 생성자와의 대조

부 생성자 체인은 자바의 "텔레스코핑 생성자(telescoping constructor)" 안티패턴을 떠올리게 한다. 자바에서는 선택적 인자 조합마다 생성자를 하나씩 만들어야 했다.

```java
// Java: 텔레스코핑 생성자 — 인자 조합이 늘면 폭발한다
class Pizza {
    Pizza(String size) { this(size, false, false); }
    Pizza(String size, boolean cheese) { this(size, cheese, false); }
    Pizza(String size, boolean cheese, boolean pepperoni) { ... }
    // "size + pepperoni만" 조합은? 또 다른 생성자가 필요...
}
```

인자가 $n$개면 조합은 최대 $2^n$가지로, 자바는 이 폭발을 감당 못 해 결국 빌더 패턴(Builder)으로 도망친다. 코틀린은 이 문제 자체를 언어 차원에서 없앤다—기본 인자와 이름 붙은 인자(7절)가 $2^n$ 조합을 헤더 한 줄로 흡수하므로, 부 생성자는 "값 변환이 필요한 소수의 경우"로만 남는다. 즉 코틀린에서 부 생성자를 여러 개 나열하고 있다면, 그것은 대개 기본 인자로 리팩터링할 신호다.

> **역사 메모**: 자바가 빌더 패턴에 의존하게 된 근본 원인은 "기본 인자 부재"다. 조슈아 블로크의 『이펙티브 자바』가 빌더를 권한 것도 텔레스코핑 생성자의 가독성 붕괴 때문이었다. 코틀린은 기본 인자 + 이름 붙은 인자로 빌더의 상당 부분을 불필요하게 만들었다. 다만 "단계별로 나눠 구성하다가 마지막에 빌드"하는 진짜 빌더 시맨틱(예: DSL 스타일 구성)이 필요하면 코틀린도 [[37 - 타입 안전 빌더와 DSL]]의 수신 객체 지정 람다로 더 우아하게 표현한다.

## 6. M46 교정 — "부 생성자가 있으면 주 생성자 초기화는 안 돈다"는 거짓

### 6.1 오개념의 형태

이 장이 소유한 오개념은 이렇다: **"부 생성자를 통해 객체를 만들면, 주 생성자에 딸린 초기화(프로퍼티 초기화자와 `init` 블록)는 실행되지 않는다."** 자바에서 생성자마다 독립적인 몸통을 갖고, 한 생성자가 다른 생성자를 명시적으로 `this(...)`로 부르지 않으면 필드 초기화자만 돌고 다른 생성자 코드는 안 도는 경험에서 흔히 넘어온다. 코틀린에서는 **틀렸다.**

### 6.2 실증

```kotlin
class Widget(val name: String) {
    val id = nextId()
    init {
        println("init 블록 실행: name=$name, id=$id")
    }

    constructor(name: String, priority: Int) : this(name) {
        println("부 생성자 본문 실행: priority=$priority")
    }

    companion object {
        private var counter = 0
        private fun nextId() = ++counter
    }
}

println("=== 부 생성자로 생성 ===")
val w = Widget("gear", 5)
// => === 부 생성자로 생성 ===
//    init 블록 실행: name=gear, id=1      ← 주 생성자 초기화가 "먼저" 돈다
//    부 생성자 본문 실행: priority=5       ← 그 다음 부 생성자 본문
```

출력이 진실을 말한다. 부 생성자 `Widget("gear", 5)`를 호출했는데도, 프로퍼티 초기화자(`id = nextId()`)와 `init` 블록이 **부 생성자 본문보다 먼저** 실행됐다. 이유는 5.2절에서 본 강제 위임이다. 부 생성자 `: this(name)`이 주 생성자를 호출하고, 주 생성자의 초기화가 완료된 뒤에야 부 생성자 본문(`{ println(...) }`)으로 제어가 돌아온다.

정확한 순서는 이렇다.

```text
Widget("gear", 5) 호출
   │
   ▼
부 생성자 진입 → : this(name) 위임을 "먼저" 실행
   │
   ├──▶ 주 생성자 진입
   │       ├─ val id = nextId()  실행  (프로퍼티 초기화자)
   │       └─ init { ... }        실행  (init 블록)
   │       주 생성자 완료 ◀──────┐
   │                              │
   ◀──────────────────────────────┘
   │
   ▼
부 생성자 본문 { println("부 생성자 본문...") } 실행
   │
   ▼
객체 완성
```

`this(...)` 위임은 부 생성자 본문의 첫 문장보다 **앞서** 실행된다. 이것은 문법적으로도 강제된다—위임 호출은 부 생성자 시그니처의 일부(`: this(...)`)로, 본문 `{}` 바깥에 온다.

### 6.3 주 생성자가 **없는** 경우

그렇다면 주 생성자가 아예 없는 클래스는 어떻게 될까? 이때는 프로퍼티 초기화자와 `init` 블록이 "어느 주 생성자에 딸릴지"가 불명확해 보인다. 코틀린의 규칙은 명확하다: **주 생성자가 없으면, 초기화 코드(프로퍼티 초기화자 + `init`)는 각 부 생성자가 상위 타입을 초기화하는 시점에 실행된다.** 즉 부 생성자 본문보다 여전히 먼저 돈다.

```kotlin
class NoPrimary {
    val log = mutableListOf<String>()
    init {
        log.add("init 실행")
    }

    constructor(x: Int) {
        log.add("부 생성자(Int) 본문: $x")
    }
    constructor(s: String) {
        log.add("부 생성자(String) 본문: $s")
    }
}

println(NoPrimary(42).log)
// => [init 실행, 부 생성자(Int) 본문: 42]
//    init이 부 생성자 본문보다 먼저 실행됐다

println(NoPrimary("hi").log)
// => [init 실행, 부 생성자(String) 본문: hi]
//    다른 부 생성자로 만들어도 init은 항상 먼저 돈다
```

주 생성자가 없어도(그래서 `: this(...)` 위임이 없어도) 각 부 생성자는 진입 시 초기화 코드를 실행한 다음 자기 본문을 실행한다. JVM 백엔드에서 이것은 컴파일러가 각 부 생성자의 바이트코드 앞부분에 프로퍼티 초기화자와 `init` 블록을 복제해 넣는 방식으로 구현된다(상위 클래스 `super()` 호출 직후). 결론적으로, **주 생성자의 유무와 관계없이 초기화 코드는 언제나 부 생성자 본문보다 먼저 실행된다.** M46은 어떤 경우에도 성립하지 않는다.

> **명세 정밀**: 주 생성자가 없는 클래스에서 부 생성자가 상위 타입을 초기화하는 방식은 두 가지다—`: super(...)`로 직접 상위 생성자를 부르거나, `: this(...)`로 다른 부 생성자에 위임하거나. 여러 부 생성자가 서로 다른 상위 생성자를 부를 수도 있다(주 생성자가 있으면 상위 위임은 주 생성자 헤더 `: Base()` 한 곳으로 고정되므로 이런 자유가 없다). 어느 경로든 초기화 코드는 "상위 초기화가 끝나고 본문이 시작되기 전"이라는 자리에 삽입된다. 이 세부는 [[24 - 상속과 오버라이딩과 초기화 순서]]에서 상속과 함께 완결된다.

### 6.4 오개념이 낳는 실제 버그

M46을 믿으면 어떤 버그가 생기는가. 개발자가 "부 생성자로 만들 땐 `init`이 안 도니까, 부 생성자 본문에서 검증을 다시 하자"고 생각해 이중 검증·이중 부수효과를 넣는 경우가 대표적이다.

```kotlin
class Config(val timeoutMs: Int) {
    init {
        require(timeoutMs > 0) { "timeout은 양수여야 한다" }
        println("리소스 예약: $timeoutMs")   // 부수효과 (예: 카운터 증가)
    }
    // M46을 믿는 개발자가 "부 생성자에선 init이 안 도니 여기서도 예약"이라 착각하면...
    constructor(seconds: Double) : this((seconds * 1000).toInt()) {
        // println("리소스 예약: ...")  ← 여기 또 넣으면 이중 예약 버그!
    }
}

Config(1.5)
// => 리소스 예약: 1500   (딱 한 번. init은 위임을 통해 정확히 한 번 실행됨)
```

진실을 알면 부 생성자 본문에는 "주 생성자가 이미 한 일 이후의 추가 작업"만 적으면 된다. 초기화·검증·불변식 강제는 `init`에 한 번만 두는 것이 정석이며, 어떤 생성자로 진입하든 그 코드는 정확히 한 번 실행된다.

## 7. 기본 인자로 부 생성자 대체하기

### 7.1 "부 생성자 대신 기본 인자"

부 생성자의 가장 흔한 용도는 "일부 인자를 생략하고 기본값으로 채우는 오버로드"를 만드는 것이다. 자바에서는 생성자 오버로딩(telescoping constructor)이 유일한 수단이지만, 코틀린에는 **기본 인자(default arguments)** 가 있어 부 생성자가 대부분 불필요해진다([[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]).

```kotlin
// 부 생성자로 오버로드를 흉내 내는 (비추천) 방식:
class Pizza1(val size: String, val cheese: Boolean) {
    constructor(size: String) : this(size, cheese = true)
    constructor() : this("medium", cheese = true)
}

// 기본 인자로 같은 것을 한 줄에:
class Pizza2(val size: String = "medium", val cheese: Boolean = true)

Pizza2()                       // medium, cheese=true
Pizza2("large")                // large, cheese=true
Pizza2("small", cheese = false)
Pizza2(cheese = false)         // 이름 붙은 인자로 앞 인자를 건너뜀
```

기본 인자 + 이름 붙은 인자의 조합은 부 생성자 여러 개가 하던 일을 헤더 한 줄로 압축한다. 게다가 부 생성자로는 표현하기 번거로운 "가운데 인자만 생략" 같은 조합도 이름 붙은 인자로 자연스럽게 해결된다.

> **흔한 오해**: "기본 인자는 항상 부 생성자보다 낫다"는 과장이다. 기본 인자는 *같은 최종 형태로 위임*하는 오버로드에만 적합하다. 초기화 로직 자체가 인자 조합마다 근본적으로 다를 때—예컨대 "문자열에서 파싱" vs "이미 파싱된 값 받기"처럼 변환 단계가 낀 경우—는 부 생성자가 더 명확하다(5.2절 `Temperature` 예처럼).

### 7.2 부 생성자가 여전히 필요한 경우

기본 인자로 대체되지 않는 부 생성자의 정당한 용도들.

1. **입력 형태가 근본적으로 다를 때.** `Point(x, y)`와 `Point(both)`, `Temperature(celsius)`와 `Temperature(value, unit)`처럼 위임 전에 변환·계산이 필요한 경우.

2. **자바 상호운용에서 특정 시그니처가 필요할 때.** 어떤 자바 프레임워크가 "인자 없는 생성자"나 특정 시그니처를 리플렉션으로 요구하면 부 생성자로 맞춰 준다.

3. **상위 타입의 서로 다른 생성자를 골라 불러야 할 때.** 주 생성자는 상위 위임을 헤더 한 곳(`: Base(...)`)으로 고정하므로, 상위 생성자를 상황에 따라 다르게 부르려면 주 생성자 없이 부 생성자들로 분기해야 한다(6.3절 명세 정밀 참고).

### 7.3 `@JvmOverloads` — 자바에서 본 기본 인자

기본 인자는 코틀린 호출부에서는 완벽하지만, **자바에서는 보이지 않는다.** 자바에는 기본 인자 개념이 없으므로, 자바 코드가 `new Pizza2("large")`를 부르려면 그런 시그니처의 생성자가 실제로 존재해야 한다. 기본적으로 코틀린은 모든 파라미터를 받는 생성자 하나만 만든다.

이 간극을 메우는 것이 `@JvmOverloads`다. 이 애노테이션은 기본값을 가진 파라미터를 하나씩 뒤에서 벗겨 낸 오버로드들을 자바용으로 자동 생성한다.

```kotlin
class Pizza3 @JvmOverloads constructor(
    val size: String = "medium",
    val cheese: Boolean = true,
)
// 자바에서 볼 수 있는 생성자들:
//   Pizza3()
//   Pizza3(String size)
//   Pizza3(String size, boolean cheese)
```

여기서 앞서 예고한 규칙이 등장한다—애노테이션(`@JvmOverloads`)을 주 생성자에 붙이려면 **`constructor` 키워드가 되살아난다.** 그냥 `class Pizza3 @JvmOverloads (...)`는 문법 에러다. 이 상호운용의 세부는 [[45 - Java 상호운용]]이 소유한다.

## 8. 생성자 가시성과 `constructor` 키워드가 필요한 순간

### 8.1 `private` 생성자와 팩토리

생성자에 가시성 한정자를 붙이면 인스턴스 생성 경로를 통제할 수 있다. 가장 흔한 것은 `private constructor`로 외부의 직접 생성을 막고, 동반 객체의 팩토리 함수만 노출하는 패턴이다.

```kotlin
class Session private constructor(val token: String) {
    companion object {
        private val active = mutableMapOf<String, Session>()
        fun of(token: String): Session =
            active.getOrPut(token) { Session(token) }   // 내부에선 생성 가능
    }
}

val s = Session.of("abc")
// val bad = Session("abc")   // 컴파일 에러: constructor is private
```

`private constructor`는 [[28 - object와 companion - 싱글턴과 동반 객체]]의 팩토리 패턴, 캐싱, 인스턴스 수 제한(예: 싱글턴 흉내)의 토대다. 여기서도 가시성 한정자 `private`을 붙이는 순간 `constructor` 키워드가 필수가 된다.

### 8.2 `constructor` 키워드가 필수가 되는 두 경우

정리하면, 주 생성자 앞의 `constructor` 키워드는 다음 둘 중 하나라도 있으면 **생략 불가**다.

| 상황 | 예시 | `constructor` |
|---|---|---|
| 한정자·애노테이션 없음 | `class C(val x: Int)` | 생략 가능 |
| 가시성 한정자 있음 | `class C private constructor(val x: Int)` | 필수 |
| 애노테이션 있음 | `class C @Inject constructor(dep: Dep)` | 필수 |
| 둘 다 | `class C @Inject internal constructor(...)` | 필수 |

이유는 파서의 모호성 제거다. `class C private (...)` 같은 표기는 `private`이 무엇을 수식하는지 애매하므로, 언어가 "한정자/애노테이션이 오면 그 뒤에 `constructor`를 명시하라"고 규정한다. 부 생성자는 애초에 항상 `constructor`로 시작하므로 이 문제가 없다.

### 8.3 부 생성자의 가시성

부 생성자에도 가시성을 줄 수 있다.

```kotlin
class Repository private constructor(val name: String) {
    private constructor() : this("default")   // 부 생성자도 private 가능
    companion object {
        fun create(name: String) = Repository(name)
    }
}
```

주 생성자와 부 생성자의 가시성은 독립적이다—주 생성자는 `private`, 특정 부 생성자만 `internal`로 열어 두는 식의 세밀한 통제가 가능하다. 가시성 한정자 각각의 의미(특히 `internal`이 모듈 단위라는 것, M44)는 [[26 - 가시성 한정자]]가 소유한다.

### 8.4 생성자 애노테이션

주 생성자에 애노테이션을 붙이는 대표적 용도는 의존성 주입 프레임워크(`@Inject` 등)나 직렬화(`@JsonCreator` 등)와의 연동이다.

```kotlin
class UserService @Inject constructor(
    private val repo: Repository,
    private val clock: Clock,
)
```

애노테이션이 주 생성자에 어떻게 부착되고 어떤 사용지점 타깃(`@param:`, `@field:` 등)으로 갈라지는지는 [[44 - 애노테이션과 리플렉션]]의 영역이다. 이 장에서 기억할 것은 "애노테이션 → `constructor` 키워드 필수"라는 문법 규칙 하나다.

## 9. 컴파일된 형태와 마지막 함정들

### 9.1 JVM 백엔드에서의 생성자

JVM 백엔드에서 코틀린 생성자는 자바의 `<init>` 메서드로 컴파일된다. 주 생성자는 하나의 `<init>`, 각 부 생성자는 또 다른 오버로드된 `<init>`이 되며, 부 생성자의 `<init>`는 내부에서 다른 `<init>`를 `invokespecial`로 호출한다(위임). 개념적 바이트코드 스케치는 이렇다.

```text
class Point(val x: Int, val y: Int) {
    constructor(both: Int) : this(both, both)
}

// JVM 백엔드 (개념):
Point.<init>(int x, int y):        // 주 생성자
    invokespecial Object.<init>()  // super
    this.x = x                     // val 프로퍼티 → final 필드
    this.y = y
    return

Point.<init>(int both):            // 부 생성자
    aload both
    aload both
    invokespecial Point.<init>(II) // this(both, both) 위임
    return
```

`val` 프로퍼티는 `final` 필드로, `var`는 일반 필드로 내려간다(백킹 필드 생성의 정확한 조건은 [[22 - 프로퍼티와 백킹 필드]]). 이 매핑은 디컴파일로 직접 확인할 수 있다—IntelliJ의 "Tools → Kotlin → Show Kotlin Bytecode → Decompile"이 표준 도구다. 무언가 확신이 안 설 때 소스를 상상만 하지 말고 실제 바이트코드/디컴파일 결과를 보는 습관이 오개념을 예방한다.

### 9.2 기본 인자의 컴파일 — 합성 생성자

기본 인자를 가진 생성자는 JVM 백엔드에서 흥미롭게 컴파일된다. 코틀린은 "모든 인자를 받는 실제 생성자"와, "어떤 인자가 생략됐는지 비트마스크로 받는 합성 생성자(synthetic constructor)"를 함께 생성한다.

```kotlin
class Box(val w: Int = 1, val h: Int = 1)

// JVM 백엔드 (개념):
//   Box.<init>(int w, int h)                              // 실제 생성자
//   Box.<init>(int w, int h, int mask, DefaultConstructorMarker)  // 합성
//
// Box() 호출 → 합성 생성자를 mask=0b11로 불러 생략된 인자를 기본값으로 채움
```

`DefaultConstructorMarker`라는 합성 타입 인자는 이 특수 생성자를 일반 오버로드와 구별하기 위한 표식이다. 이 세부를 알 필요는 없지만, "코틀린 소스 한 줄이 여러 생성자로 펼쳐질 수 있다"는 사실은 자바 상호운용이나 리플렉션([[44 - 애노테이션과 리플렉션]])에서 예기치 않은 시그니처를 마주칠 때 이해의 실마리가 된다. 비트마스크 방식이 오버로드마다 생성자를 만드는 `@JvmOverloads`(7.3절)와 다른 점도 여기서 드러난다—기본 인자의 기본 컴파일은 합성 생성자 하나에 마스크로 처리하고, `@JvmOverloads`는 자바에서 부를 수 있는 진짜 오버로드들을 추가로 찍어낸다. 전자는 코틀린 호출부만, 후자는 자바 호출부까지 겨냥한다.

> **성능 주의**: 이 컴파일 세부는 성능에 거의 영향이 없다—합성 생성자 호출 한 번의 비트마스크 분기는 무시할 수준이다. 다만 아주 뜨거운 경로에서 수백만 번 객체를 만든다면, 기본 인자 호출이 "모든 인자를 명시한 호출"보다 미세하게 더 많은 바이트코드를 거친다는 점은 사실이다. 실무에서 이것이 병목이 되는 일은 거의 없으므로, 가독성을 희생하면서까지 기본 인자를 피할 이유는 없다. 최적화는 프로파일러가 지목한 뒤에 하라.

### 9.3 함정 1 — 초기화 순서 의존

4.3절에서 본 "선언 후 사용" 함정을 다시 강조한다. 프로퍼티들이 서로를 참조하며 초기화될 때, 선언 순서가 곧 실행 순서이므로 순서를 바꾸면 값이 달라지거나 미초기화 `null`을 읽는다.

```kotlin
class Circle(radius: Double) {
    val area = Math.PI * radius * radius   // radius(파라미터)만 참조 — 안전
    val diameterHint = "지름 힌트"
    // val bad = derived()  ← 뒤 프로퍼티를 함수로 우회해 읽으면 위험
}
```

원칙: **초기화자는 자기 앞의 것(주 생성자 파라미터 + 먼저 선언된 프로퍼티)에만 의존하라.** 복잡한 상호 의존이 생긴다면 그것은 설계 냄새이며, `init`에서 명시적으로 순서를 통제하거나 [[23 - 위임 프로퍼티]]의 `by lazy`로 계산을 미루는 편이 안전하다.

### 9.4 함정 2 — 생성자에서 `this` 누출

객체가 완전히 초기화되기 전에 `this` 참조를 외부로 넘기면(리스너 등록, 컬렉션에 자기 추가, 콜백 전달), 다른 코드가 반쯤 만들어진 객체를 보게 된다.

```kotlin
class Observer(registry: MutableList<Observer>) {
    val name: String
    init {
        registry.add(this)   // 위험: name이 아직 대입되기 전에 this가 밖으로 샌다
        name = "observer"
    }
}
```

여기서 `registry.add(this)`가 실행되는 순간 `name`은 아직 대입 전이다. 만약 `registry`를 관찰하던 다른 스레드나 코드가 이 `Observer`의 `name`을 읽으면 `null`(비-널 선언인데도)을 볼 수 있다. 규칙: **`init`이나 생성자에서 `this`를 외부로 넘기지 마라.** 특히 멀티스레드 환경에서 이 누출은 [[43 - 동시성과 메모리 모델]]의 가시성 문제와 결합해 재현하기 어려운 버그를 만든다.

### 9.5 함정 3 — `open` 클래스 생성자에서 오버라이드 멤버 호출 (M47 예고)

이 장의 축소판으로 4.3절에서 이미 봤지만, 상속이 끼면 훨씬 위험해진다. `open` 클래스의 생성자/초기화자가 `open` 멤버를 호출하면, 하위 클래스가 그것을 오버라이드했을 때 **하위 클래스의 필드가 아직 초기화되기 전에** 그 오버라이드가 실행된다.

```kotlin
open class Base {
    open val label: String = "base"
    init {
        println("Base.init이 보는 label: $label")   // 오버라이드된 값? 함정!
    }
}
class Derived : Base() {
    override val label: String = "derived"
}
Derived()
// => Base.init이 보는 label: null
//    Derived.label 초기화는 Base 생성자가 끝난 뒤이므로, Base.init 시점엔 null
```

이것이 M47이며, 상위→하위 초기화 순서와 함께 [[24 - 상속과 오버라이딩과 초기화 순서]]가 정본으로 해부한다. 이 장에서 미리 각인할 교훈은 하나다: **생성자·`init`·프로퍼티 초기화자에서 `open` 멤버를 호출하지 마라.** 초기화가 완료되기 전의 세계는 널 안전성마저 보장되지 않는 회색 지대다.

---

지금까지의 여정을 한 줄기로 회수하자. `class Point(val x: Int, val y: Int)` 한 줄은 단순한 문법 설탕이 아니라, 주 생성자·프로퍼티 선언·게터/세터 생성이라는 세 개념을 한자리에 접은 압축이었다. `new`의 부재는 생성자와 함수를 통일된 호출 문법 아래 두려는 세계관의 표현이었고, `init` 블록은 "코드를 담을 수 없는 주 생성자"의 몸통을 대신하는 자리였다. 프로퍼티 초기화자와 `init`은 두 개의 분리된 단계가 아니라 소스 순서로 뒤섞인 하나의 실행열이며, 그 순서가 "선언 후 사용" 규칙과 미초기화 함정의 뿌리였다. 그리고 이 장의 핵심 교정—부 생성자로 객체를 만들어도 주 생성자의 초기화는 위임을 통해 언제나 먼저, 정확히 한 번 실행된다(M46). 부 생성자는 자바식 오버로딩의 유물이 아니라, 기본 인자로 표현할 수 없는 "입력 형태의 근본적 차이"를 위한 도구였다. 객체가 어떻게 태어나는가에 대한 이 그림을 손에 쥐었으니, 이제 그 객체가 값을 담는 방식—프로퍼티가 언제 백킹 필드를 갖고 게터/세터가 어떻게 짜이는가—으로 넘어갈 차례다.

## 핵심 요약

- **주 생성자는 클래스 헤더의 괄호에 접혀 있으며, `val`/`var` 없는 파라미터는 프로퍼티가 아니라 초기화 스코프에서만 사는 임시값이다.** `val`/`var`를 붙여야 저장되는 프로퍼티가 되며, 이 한 글자가 자바의 필드+생성자대입+게터/세터를 대체한다.
- **주 생성자에는 실행 코드를 담을 수 없고, 그 몸통을 `init` 블록이 대신한다.** `init`은 여러 개 둘 수 있고 선언 순서대로 실행된다.
- **프로퍼티 초기화자와 `init` 블록은 별개 단계가 아니라, 클래스 본문의 텍스트 순서로 뒤섞여 실행되는 하나의 초기화열이다.** 이 순서는 컴파일러가 재배열하지 않으며 관찰 가능한 의미론의 일부다.
- **부 생성자로 객체를 만들어도 주 생성자의 초기화(프로퍼티 초기화자 + `init`)는 언제나 먼저, 정확히 한 번 실행된다 (M46).** 주 생성자가 있으면 부 생성자는 `this(...)`로 위임이 강제되고, 위임이 본문보다 먼저 돌기 때문이다.
- **주 생성자가 아예 없는 클래스에서도 초기화 코드는 각 부 생성자의 본문보다 먼저 실행된다 (M46).** JVM 백엔드에서 컴파일러가 각 부 생성자 앞부분에 초기화 코드를 삽입한다.
- **초기화자·`init`은 자기보다 뒤에 선언된 프로퍼티를 직접 읽을 수 없고, 컴파일러가 이를 정적으로 막는다.** 단 함수로 우회하면 미초기화 상태(비-널 선언인데도 `null`)를 런타임에 읽을 수 있다 (M47 관련).
- **코틀린에는 `new`가 없어 생성자 호출이 일반 함수 호출과 문법적으로 같다.** 덕분에 생성자를 팩토리 함수로 무중단 교체할 수 있고 `::Class` 생성자 참조가 함수 참조와 균일하다.
- **기본 인자 + 이름 붙은 인자가 대부분의 부 생성자를 대체하지만, 입력 형태가 근본적으로 다르거나 상위 생성자를 상황별로 골라야 할 때는 부 생성자가 필요하다.** 자바에서 기본 인자를 보이게 하려면 `@JvmOverloads`가 필요하다.
- **생성자에 가시성 한정자나 애노테이션을 붙이는 순간 생략됐던 `constructor` 키워드가 되살아난다.** 파서 모호성 제거를 위한 규칙이다.
- **`init`은 `require`/`check`로 불변식을 강제해 "유효하지 않은 객체가 존재조차 못 하게" 만드는 자리다.** 초기화 도중 예외가 나면 객체는 완성되지 않고 참조도 대입되지 않는다.
- **생성자·`init`에서 `this`를 외부로 누출하거나 `open` 멤버를 호출하면, 반쯤 초기화된 객체가 노출되어 널 안전성마저 뚫린다 (M47).** 초기화 완료 전은 언어의 안전 보장이 유예되는 회색 지대다.
