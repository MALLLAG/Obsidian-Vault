[[20 - 구조 분해]]에서는 이미 만들어진 객체를 여러 이름으로 *풀어내는* 문법을 다뤘다. `componentN` 관례를 이용해 `val (x, y) = point`가 위치를 기준으로 분해되는 과정을 보았다. 그러나 그 논의는 모두 "객체가 이미 존재한다"는 전제에서 출발했다. 이 장에서는 그보다 앞 단계, 즉 객체가 *어떻게 만들어지는가*를 다룬다. 클래스 선언 문법, 주 생성자와 부 생성자, 그리고 인스턴스를 만들 때 코틀린 런타임이 어떤 순서로 필드를 채우는지를 살펴본다.

이 장에서는 **하나의 클래스가 자기 자신을 초기화하는 메커니즘**만 다룬다. 상속 계층을 따라 올라가는 초기화 순서(상위 생성자가 하위 생성자보다 먼저 실행되는 규칙, 생성자에서 `open` 멤버를 호출할 때의 함정)는 [[24 - 상속과 오버라이딩과 초기화 순서]]에서, 프로퍼티가 백킹 필드를 갖는지와 게터/세터가 컴파일되는 방식은 [[22 - 프로퍼티와 백킹 필드]]에서 설명한다.

`equals`/`copy`를 자동으로 얻는 데이터 클래스는 [[27 - 데이터 클래스]], 인스턴스가 하나뿐인 `object`는 [[28 - object와 companion - 싱글턴과 동반 객체]]에서 다룬다. 이 장은 그 모든 기능의 바탕이 되는 생성자와 초기화에 집중한다.

순서는 다음과 같다. 클래스 선언의 최소 형태와 "코틀린에는 `new`가 없다"는 사실의 의미를 먼저 보고, 주 생성자와 `val`/`var` 유무의 차이, `init` 블록, 프로퍼티 초기화자와 `init`이 번갈아(interleaving) 실행되는 순서를 확인한다.

이어서 부 생성자와 `this(...)` 위임을 다루면서 "부 생성자가 있으면 주 생성자 초기화는 실행되지 않는다"는 오해를 바로잡는다. 마지막으로 기본 인자로 부 생성자를 대체하는 관용구, 생성자 가시성, 그리고 이 모든 것이 JVM 백엔드에서 어떤 바이트코드로 컴파일되는지 확인한다.

코틀린의 생성자 설계는 "흔한 경우는 한 줄로, 드문 경우만 길게"라는 실용적인 원칙을 따른다. `class Point(val x: Int, val y: Int)` 한 줄을 자바로 쓰면 필드 선언 2줄, 생성자 6줄, 게터 2개로 늘어난다. 이 장의 목표는 그 압축이 어떻게 가능한지, 그리고 압축된 문법 뒤에 어떤 실행 규칙이 있는지를 끝까지 살펴보는 것이다.

## 1. 클래스 선언의 최소 형태와 `new`가 없다는 점

### 1.1 가장 작은 클래스

코틀린에서 가장 짧은 클래스 선언은 이름 하나로 이루어진다.

```kotlin
class Empty
```

중괄호도 괄호도 없지만, 이 한 줄은 완결된 선언이다. 자바는 최소한 `class Empty {}`처럼 빈 본문을 요구하지만, 코틀린은 본문이 필요 없으면 중괄호를 생략할 수 있다. 인스턴스를 만드는 코드도 마찬가지로 짧다.

```kotlin
val e = Empty()
// => Empty 타입의 인스턴스
```

여기서 먼저 눈에 띄는 점은 `new`가 없다는 것이다. 자바의 `new Empty()`, C++의 `new Empty`, C#의 `new Empty()`는 모두 키워드를 요구하지만, 코틀린은 클래스 이름을 함수처럼 *호출*한다. 이는 단순히 입력할 글자를 줄이려는 것이 아니라, 언어 전체에 일관되게 적용된 설계 방침의 일부다.

### 1.2 `new`가 없다는 것의 의미

`new`를 없앴다는 것은 코틀린이 "생성자 호출"과 "일반 함수 호출"을 문법으로 구분하지 않기로 했다는 뜻이다. `Empty()`는 겉보기에 `println()`과 모양이 같다. 이렇게 통일한 덕분에 여러 가지가 자연스러워진다.

첫째, **호출하는 쪽에서는 팩토리 함수와 생성자를 구별할 수 없다.** 처음에는 `class Rational(...)`을 생성자로 노출했다가 나중에 캐싱이 필요해져 `fun Rational(...)`이라는 최상위 함수로 바꿔도, 호출부의 `Rational(1, 2)`는 바뀌지 않는다. 자바였다면 `new Rational(...)`을 `Rational.of(...)`로 모두 고쳐야 했을 것이다.

코틀린에서는 대문자로 시작하는 함수 이름(관례적으로 생성자처럼 보이게 쓴다) 덕분에 이런 전환이 매끄럽다.

```kotlin
// 처음엔 생성자
class Color(val rgb: Int)
val red = Color(0xFF0000)

// 나중에 캐싱이 필요하면 — 호출부는 그대로 Color(...)
// class Color private constructor(val rgb: Int) { companion object { ... } }
// fun Color(rgb: Int): Color = cache.getOrPut(rgb) { Color(rgb) }  // 개념 예시
```

둘째, **생성자 참조도 `::Empty`라는 같은 형태로 쓴다.** 함수 참조 `::foo`와 똑같은 문법으로 `::Empty`를 쓰면 생성자를 일급 값으로 다룰 수 있다([[13 - 함수 타입과 람다와 함수 참조]]). 따라서 `list.map(::Person)`처럼 생성자를 고차 함수에 넘길 수 있다.

> [!info] 역사 메모
> `new` 키워드를 없앤 것은 코틀린만의 발명이 아니다. 스칼라, 파이썬, 러스트(튜플 구조체 `Point(1, 2)`) 등 여러 현대 언어가 같은 선택을 했다. 자바가 `new`를 유지한 것은 1990년대에 "힙 할당은 비용이 드는 명시적인 연산이므로 문법에서 눈에 띄어야 한다"는 관점이 강했기 때문이다. 코틀린은 그 관점을 따르지 않았다.
>
> 다만 JVM 백엔드에서 `Empty()`는 여전히 바이트코드 `new Empty; dup; invokespecial Empty.<init>()V`로 컴파일된다. 즉 *실행 의미*는 자바와 같고, 소스 코드에서 키워드만 사라졌다.

### 1.3 헤더와 본문

클래스 선언은 크게 **헤더(header)** 와 **본문(body)** 으로 나뉜다.

```text
class  Name  <T>  (헤더: 주 생성자)  : SuperType()  where ...   {  본문  }
       ↑     ↑     ↑                  ↑              ↑              ↑
      이름  타입   주 생성자          상위 타입      제약           멤버 선언
            파라미터                  위임          (제네릭)
```

이 장에서 주로 다루는 것은 헤더의 괄호 안에 있는 주 생성자, 그리고 본문 안의 `init` 블록과 부 생성자다. 타입 파라미터 `<T>`는 [[33 - 제네릭 1 - 타입 파라미터와 변성]]에서, 상위 타입 위임 `: SuperType()`은 24장(상속과 오버라이딩과 초기화 순서)에서 다룬다.

본문이 있으면 중괄호로 감싼다.

```kotlin
class Counter {
    var count = 0
    fun increment() { count++ }
}
```

본문에는 프로퍼티, 함수, `init` 블록, 부 생성자, 중첩 클래스([[31 - 중첩 클래스와 이너 클래스와 익명 객체]]), 동반 객체(28장 object와 companion)가 올 수 있다. 선언 순서는 대체로 자유로워서, 함수는 뒤에 선언된 프로퍼티도 참조할 수 있다(전방 참조). 그러나 딱 하나 예외가 있는데, 바로 **초기화자와 `init` 블록의 실행 순서**다. 이것이 4절의 주제이자 이 장에서 가장 중요한 내용이다.

## 2. 주 생성자: 헤더에 들어간 생성자

### 2.1 괄호 하나에 담긴 것

주 생성자는 클래스 이름 바로 뒤에 괄호로 붙인다.

```kotlin
class Person(firstName: String, age: Int)
```

`firstName`과 `age`는 주 생성자의 **파라미터**다. 여기서 헷갈리기 쉬운 점이 있다. 이 상태의 `firstName`과 `age`는 **클래스의 프로퍼티가 아니다.** 생성자에 전달되는 값일 뿐이며, 어디에도 저장하지 않았으므로 인스턴스가 만들어진 뒤에는 사라진다.

```kotlin
class Person(firstName: String, age: Int)

val p = Person("Ada", 36)
// p.firstName  // 컴파일 에러: unresolved reference — 프로퍼티가 아님
```

파라미터는 **주 생성자의 초기화 스코프 안**에서만 유효하다. 즉 프로퍼티 초기화자와 `init` 블록 안에서는 쓸 수 있지만, 일반 멤버 함수에서는 보이지 않는다.

```kotlin
class Person(firstName: String, age: Int) {
    val displayName = firstName.uppercase()  // OK: 초기화자에서 파라미터 사용
    init {
        require(age >= 0)                     // OK: init에서 파라미터 사용
    }
    fun greet() {
        // println(firstName)  // 컴파일 에러: firstName은 여기서 안 보임
        println(displayName)   // OK: 저장된 프로퍼티
    }
}
```

### 2.2 `val`/`var`를 붙이면 달라지는 것

파라미터 앞에 `val`이나 `var`를 붙이면, 그 파라미터는 파라미터인 동시에 **프로퍼티**가 된다.

```kotlin
class Person(val firstName: String, var age: Int)

val p = Person("Ada", 36)
println(p.firstName)  // => Ada  — 이제 프로퍼티다
p.age = 37            // var이므로 재대입 가능
```

`val`/`var` 키워드 하나가 하는 일을 자바 코드로 풀어 쓰면 코틀린이 얼마나 많은 코드를 줄여 주는지 알 수 있다.

```java
// Kotlin: class Person(val firstName: String, var age: Int)
// 에 대응하는 자바:
public final class Person {
    private final String firstName;
    private int age;
    public Person(String firstName, int age) {
        this.firstName = firstName;
        this.age = age;
    }
    public String getFirstName() { return firstName; }
    public int getAge() { return age; }
    public void setAge(int age) { this.age = age; }
}
```

코틀린 한 줄이 자바에서는 필드 2개, 생성자, 게터 2개, 세터 1개로 늘어난다. `val`은 게터만, `var`는 게터와 세터를 만든다(백킹 필드가 실제로 생성되는 조건은 22장(프로퍼티와 백킹 필드)에서 자세히 다룬다). 여기서 기억할 점은 세 가지 파라미터 형태가 서로 다르다는 것이다.

| 헤더 표기 | 파라미터인가 | 프로퍼티인가 | 재대입 |
|---|---|---|---|
| `Person(firstName: String)` | 예 | 아니오 | - (초기화 스코프에서만 읽기) |
| `Person(val firstName: String)` | 예 | 예 (읽기 전용) | 불가 |
| `Person(var firstName: String)` | 예 | 예 (읽기·쓰기) | 가능 |

> [!warning] 흔한 오해
> "생성자 파라미터는 무조건 프로퍼티가 된다"는 생각은 생성자 인자를 `this.x = x`로 필드에 옮기는 자바의 관습에서 온 착각이다. 코틀린에서 `val`/`var`가 없는 파라미터는 필드로 저장되지 않고, 초기화가 끝나면 사라진다. 이는 낭비가 아니라 의도된 설계다. 원본 인자는 버리고 파생 프로퍼티만 저장하고 싶을 때(예: `class Angle(degrees: Double) { val radians = degrees * PI / 180 }`) 이를 자연스럽게 표현할 수 있다.

이 구분은 메모리 레이아웃에도 그대로 반영된다. `val`/`var`가 붙은 파라미터만 인스턴스 필드로 남고, 붙지 않은 파라미터는 생성자 실행이 끝나면 스택에서 사라진다.

```text
class Angle(degrees: Double) {   // degrees: 필드 아님 (초기화 후 소멸)
    val radians = degrees * PI / 180   // radians: 필드로 저장
}

인스턴스 메모리 레이아웃 (JVM 백엔드, 개념):
┌────────────────────────┐
│ Angle 인스턴스          │
│  radians: double  ← 저장됨  │
│  (degrees는 없음)        │  ← 필드로 남지 않음
└────────────────────────┘
```

같은 값을 나중에 다시 쓰려면 `val`을 붙여 저장해야 한다. 초보자가 "생성자 인자를 나중에 메서드에서 읽으려는데 보이지 않는다"며 당황하는 것은 대부분 이 구분을 놓쳤기 때문이다.

### 2.3 `constructor` 키워드의 생략

지금까지 본 형태에는 `constructor`라는 키워드가 없었다. 사실 주 생성자의 정식 문법은 다음과 같다.

```kotlin
class Person constructor(val firstName: String)
```

`constructor` 키워드는 **가시성 한정자나 애노테이션이 없을 때 생략할 수 있다.** 대부분의 코드에서 생략하므로 괄호만 있는 형태가 더 익숙하다. 그러나 생성자에 가시성(`private`)을 지정하거나 애노테이션을 붙이려면 키워드를 써야 한다(8절에서 자세히 설명한다).

```kotlin
class Registry private constructor()           // 가시성 → constructor 필수
class Service @Inject constructor(dep: Dep)     // 애노테이션 → constructor 필수
```

### 2.4 빈 괄호와 괄호 없음

주 생성자가 파라미터를 받지 않으면 빈 괄호로 쓴다.

```kotlin
class Widget()   // 명시적 빈 주 생성자
class Widget     // 주 생성자 자체를 생략 (암시적 기본 생성자와 동등)
```

둘의 차이는 미묘하다. `class Widget`처럼 괄호를 아예 생략하면 **주 생성자가 없는** 상태로 간주되지만, 컴파일러가 인자 없는 생성자를 제공하므로 `Widget()`으로 인스턴스를 만들 수 있다.

실제로는 대부분의 경우 둘이 똑같이 동작하며, 명시적인 `()`는 뒤에 가시성이나 애노테이션을 붙일 자리를 마련해 준다는 정도의 차이만 있다. 상속할 때 상위 클래스 생성자를 위임 호출하면(`: Base()`) 이 차이가 드러나는데, 이 내용은 24장(상속과 오버라이딩과 초기화 순서)에서 다룬다.

## 3. `init` 블록: 주 생성자에 넣을 수 없는 코드

### 3.1 주 생성자에 코드를 쓸 수 없는 이유

주 생성자에는 **실행할 코드를 직접 넣을 수 없다.** 헤더의 괄호에는 파라미터 목록만 들어가고, 문(statement)을 담는 본문이 없다. 자바처럼 생성자 본문에 로직을 적는 자리가 헤더에는 없다.

```kotlin
class Person(name: String) {
    // 헤더 괄호 안에는 println("...") 같은 코드를 쓸 자리가 없다
}
```

이 제약을 보완하는 것이 `init` 블록이다. `init`은 "주 생성자의 본문"이라고 생각하면 정확하다. 주 생성자가 호출될 때 실행해야 할 코드를 여기에 넣는다.

```kotlin
class Person(name: String) {
    val displayName: String
    init {
        require(name.isNotBlank()) { "name must not be blank" }
        displayName = name.trim().replaceFirstChar { it.uppercase() }
        println("Person 생성: $displayName")
    }
}

val p = Person("  ada  ")
// => "Person 생성: Ada" 출력
// p.displayName == "Ada"
```

`init` 블록 안에서는 주 생성자 파라미터(`name`)와, 블록보다 위에서 이미 선언하고 초기화한 프로퍼티를 자유롭게 참조할 수 있다.

### 3.2 여러 개의 `init` 블록

한 클래스에 `init` 블록을 여러 개 둘 수 있다. 이 블록들은 **선언된 순서대로** 실행된다.

```kotlin
class Trace {
    init { println("첫 번째 init") }
    init { println("두 번째 init") }
    init { println("세 번째 init") }
}
Trace()
// => 첫 번째 init
//    두 번째 init
//    세 번째 init
```

`init`을 여러 개 둘 수 있다는 사실 자체는 사소해 보인다. 하지만 다음 절의 핵심인 프로퍼티 초기화자와 번갈아 실행되는 규칙과 결합하면 초기화 순서가 미묘해진다.

### 3.3 프로퍼티 초기화자도 "코드"다

여기서 관점을 하나 바꿔야 한다. 프로퍼티에 붙는 초기화 식(`val x = ...`)도 실행 시점이 있는 **코드**다. 상수처럼 보이는 `val area = width * height`도 실제로는 생성자가 실행되는 순간 계산되는 표현식이다.

```kotlin
class Rectangle(val width: Int, val height: Int) {
    val area = width * height   // 생성 시점에 계산되어 저장됨
    val perimeter = 2 * (width + height)
}
```

`area`와 `perimeter`는 리터럴이 아니라 계산 결과다. 이 계산은 `init` 블록의 실행과 함께 하나의 순서로 묶여 실행된다. 코틀린 명세는 프로퍼티 초기화자와 `init` 블록을 **같은 지위의 초기화 단계**로 취급하며, 소스에 나타난 순서 그대로 실행한다. 다음 절은 이 규칙 하나를 자세히 살펴본다.

> [!note] 명세 기준
> 코틀린 언어 명세는 프로퍼티 초기화자와 `init` 블록을 합쳐 클래스의 "초기화 코드(initialization code)"라고 부르고, 이 코드가 클래스 본문에 적힌 순서(top-to-bottom)대로 실행된다고 보장한다. 컴파일러 최적화로도 이 순서는 바뀌지 않는다. 초기화 코드는 예외 던지기, 로그 출력, 다른 프로퍼티 읽기처럼 관찰 가능한 부수 효과를 가질 수 있으므로, 순서 자체가 의미의 일부이기 때문이다.

### 3.4 `init`과 프로퍼티 초기화자, 언제 무엇을 쓰는가

둘 다 초기화 코드지만 쓰임은 다르다. 값을 계산해 프로퍼티에 담을 때는 초기화자를 쓰고, 검증이나 로깅, 여러 프로퍼티를 함께 설정하는 로직은 `init`에 두는 것이 관례다.

| 구분 | 프로퍼티 초기화자 | `init` 블록 |
|---|---|---|
| 형태 | `val x = 식` | `init { 문들 }` |
| 주 목적 | 단일 프로퍼티에 값 대입 | 검증·부수 효과·복합 로직 |
| 여러 프로퍼티 동시 설정 | 불가(하나씩) | 가능 |
| 조건 분기로 값 정하기 | `= if(...) ... else ...`로 제한적 | `if`/`when`/루프를 자유롭게 사용 |
| 파라미터·앞 프로퍼티 참조 | 가능 | 가능 |

특히 "선언은 위에서 하고, 값은 조건에 따라 `init`에서 대입"하는 패턴이 유용하다.

```kotlin
class HttpStatus(code: Int) {
    val category: String   // 선언만 (초기화자 없음)
    init {
        category = when (code / 100) {   // init에서 조건에 따라 대입
            2 -> "성공"
            4 -> "클라이언트 오류"
            5 -> "서버 오류"
            else -> "기타"
        }
    }
}
HttpStatus(404).category   // => "클라이언트 오류"
```

여기서 `val category`는 초기화자 없이 선언만 하고, `init`에서 정확히 한 번 대입한다. 컴파일러는 확정 대입 분석(definite assignment analysis)으로 "모든 실행 경로에서 `val`이 정확히 한 번 대입되는가"를 검사한다. 어떤 경로에서 대입이 빠지거나 두 번 일어나면 컴파일 에러가 난다.

## 4. 초기화 실행 순서: 이 장의 핵심

### 4.1 전체 순서 다이어그램

`val obj = SomeClass(args)`가 실행될 때 정확히 어떤 일이 일어날까? 상속은 잠시 제외하고(상위 타입은 24장에서 다룬다) 단일 클래스의 초기화 순서를 그리면 다음과 같다.

```text
SomeClass(args) 호출
   │
   ▼
① 주 생성자 인자 평가 (호출 지점에서)
   │
   ▼
② (상위 타입 초기화 — 24장 소유, 여기선 생략)
   │
   ▼
③ 클래스 본문을 위에서 아래로 훑으며:
   ├─ 프로퍼티 초기화자를 만나면 → 그 식을 평가해 프로퍼티에 대입
   └─ init 블록을 만나면       → 그 블록을 실행
   (프로퍼티 초기화자와 init은 "한 줄기 순서"로 섞여 실행됨)
   │
   ▼
④ (부 생성자로 진입했다면) 부 생성자 본문 실행 — 6절
   │
   ▼
객체 완성, 참조 반환
```

핵심은 ③이다. 프로퍼티 초기화자와 `init` 블록은 **서로 다른 두 단계가 아니라, 소스 순서대로 섞인 하나의 순서**다.

### 4.2 번갈아 실행되는 모습 확인하기

설명보다 코드로 보는 편이 확실하다.

```kotlin
class Order(val id: Int) {
    val a = log("a 초기화자")           // 1
    init { log("첫 init") }             // 2
    val b = log("b 초기화자")           // 3
    init { log("둘째 init") }           // 4
    val c = log("c 초기화자")           // 5

    private fun log(msg: String): String {
        println(msg); return msg
    }
}

Order(1)
// => a 초기화자
//    첫 init
//    b 초기화자
//    둘째 init
//    c 초기화자
```

출력 순서는 소스의 위에서 아래 순서와 정확히 같다. 프로퍼티 초기화자를 모두 처리한 다음 `init`을 처리하는 것이 *아니다.* 텍스트에 적힌 순서대로 하나씩 실행한다.

### 4.3 "선언 후 사용" 규칙: 아직 초기화되지 않은 프로퍼티

이 순서 규칙에는 강력한 안전장치가 따라온다. **초기화자와 `init` 블록은 자신보다 뒤에 선언된 프로퍼티를 읽을 수 없다.** 컴파일러가 이를 정적으로 막는다.

```kotlin
class Broken {
    val first = second + 1   // 컴파일 에러: Variable 'second' must be initialized
    val second = 10
}
```

`first`를 계산하는 시점에 `second`는 초기화 순서상 뒤에 있으므로 아직 값이 없다. 코틀린은 이렇게 앞에서 뒤의 값을 읽는 코드를 컴파일 타임에 진단한다. 자바에서는 초기화 순서상 아직 0이나 `null`인 필드를 읽어도 컴파일러가 아무 경고도 하지 않는데, 코틀린은 이 함정을 언어 차원에서 없앴다.

```java
// Java: 컴파일은 통과하지만, first를 second보다 위에 두면
// 초기화 순서상 second는 아직 0이라 first = 0+1 = 1이 된다 (의도한 11이 아님).
// 참조 타입이면 같은 상황에서 NullPointerException이 조용히 터진다.
class Broken {
    int first = second + 1;  // second가 아직 0 → first = 1 (버그의 씨앗)
    int second = 10;
}
```

다만 이 정적 검사를 우회하는 길이 있다. `init` 블록 안에서 **함수를 통해** 간접적으로 뒤의 프로퍼티를 읽으면 컴파일러의 흐름 분석을 벗어날 수 있고, 그러면 런타임에 초기화되지 않은 상태(원시 타입은 0/false, 참조 타입은 `null`)를 읽게 된다. 특히 생성자에서 `open` 함수를 호출해 하위 클래스의 초기화되지 않은 필드를 읽는 경우가 악명 높은데, 이 내용은 24장에서 다룬다. 단일 클래스 범위에서도 이 함정의 축소판을 볼 수 있다.

```kotlin
class Sneaky {
    init {
        println(peek())   // peek()이 아직 초기화 안 된 value를 읽는다
    }
    val value: String = "설정됨"
    fun peek(): String = value
}
Sneaky()
// => null  (JVM 백엔드에서 value 필드는 이 시점에 아직 null)
//    선언은 String(비-널)인데 런타임엔 null이 관찰된다 — 초기화 순서의 함정
```

`value`의 선언 타입은 널이 될 수 없는 `String`인데도, `init`이 초기화 전에 함수를 거쳐 읽으면 `null`이 나온다. 코틀린의 널 안전성([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]])도 초기화 순서의 허점은 막지 못한다. 규칙은 단순하다. **생성자나 `init`에서 아직 초기화되지 않았을 수 있는 값을 함수로 우회해 읽지 않는다.**

> [!caution] 성능 주의
> 프로퍼티 초기화자를 여러 개 두는 것 자체는 성능 부담이 없다. 각 초기화자는 어차피 한 번씩 실행되는 대입일 뿐이다. 다만 `init` 블록에서 파일 I/O, 네트워크, 큰 컬렉션 순회 같은 무거운 연산을 하면 그 비용이 곧 객체 생성 비용이 된다는 점을 의식해야 한다. 객체 생성은 자주 실행되는 경로(hot path)에 있는 경우가 많으므로, 무거운 초기화는 [[23 - 위임 프로퍼티]]의 `by lazy`로 미루는 편이 나은 경우가 많다.

### 4.4 초기화 도중 예외

`init` 블록이나 프로퍼티 초기화자에서 예외가 발생하면 객체 생성은 실패하고, 일부만 초기화된 객체는 (정상 경로로는) 외부에 노출되지 않는다.

```kotlin
class BankAccount(initialBalance: Long) {
    val balance: Long = initialBalance
    init {
        require(balance >= 0) { "잔액은 음수가 될 수 없다: $balance" }
    }
}

val bad = BankAccount(-100)
// => IllegalArgumentException: 잔액은 음수가 될 수 없다: -100
//    bad 변수에는 아무것도 대입되지 않는다 (생성자가 예외로 종료)
```

`init`에서 `require`/`check`로 불변식(invariant)을 강제하는 패턴은 코틀린에서 **유효하지 않은 객체가 아예 존재할 수 없게** 만드는 관용구다. 자바에서 생성자가 `IllegalArgumentException`을 던지는 것과 목적은 같지만, `require`/`check`는 조건과 메시지를 간결하게 묶어 준다.

관례상 `require`는 인자 검증(위반 시 `IllegalArgumentException`)에, `check`는 상태 검증(위반 시 `IllegalStateException`)에 쓴다.

## 5. 부 생성자: `constructor`와 `this(...)` 위임

### 5.1 부 생성자의 문법

인자를 받는 방식이 여러 가지여야 할 때처럼 주 생성자만으로 부족하면, 본문 안에 `constructor` 키워드로 **부 생성자**를 추가한다.

```kotlin
class Point(val x: Int, val y: Int) {
    constructor(both: Int) : this(both, both)   // 대각선 점
}

val p1 = Point(3, 4)   // 주 생성자
val p2 = Point(5)      // 부 생성자 → this(5, 5) → 주 생성자
println("${p2.x}, ${p2.y}")   // => 5, 5
```

부 생성자의 헤더에는 주 생성자와 달리 `constructor` 키워드가 **필수**다. 그리고 `: this(...)`로 다른 생성자에 위임한다.

### 5.2 주 생성자가 있으면 위임은 필수

클래스에 주 생성자가 있으면 **모든 부 생성자는 반드시 주 생성자로 위임**해야 한다. `this(...)`로 직접 위임하든, 다른 부 생성자를 거쳐 간접적으로 위임하든 결국에는 주 생성자에 도달해야 한다.

```kotlin
class Temperature(val celsius: Double) {
    constructor(value: Double, unit: String) : this(
        when (unit) {
            "F" -> (value - 32) * 5 / 9
            "K" -> value - 273.15
            else -> value
        }
    )
    // 이 부 생성자는 계산 결과를 this(celsius)로 넘겨 주 생성자를 호출한다
}

val t = Temperature(212.0, "F")
println(t.celsius)   // => 100.0
```

주 생성자로 위임하지 않는 부 생성자는 컴파일 에러가 난다.

```kotlin
class Bad(val x: Int) {
    constructor(s: String) {   // 컴파일 에러: Primary constructor call expected
        // this(...)로 주 생성자를 부르지 않았다
    }
}
```

이 강제 위임이 다음 절의 오해를 이해하는 열쇠다. 부 생성자가 결국 주 생성자를 호출한다는 것은, 주 생성자에 딸린 초기화(프로퍼티 초기화자와 `init` 블록)가 **부 생성자 본문보다 반드시 먼저** 실행된다는 뜻이다. 이 내용은 다음 절에서 자세히 다룬다.

### 5.3 위임 체인

부 생성자끼리 서로 위임하는 체인을 만들 수도 있다.

```kotlin
class Pizza(val size: String, val toppings: List<String>) {
    constructor(size: String) : this(size, emptyList())
    constructor() : this("medium")   // 부 생성자 → 부 생성자 → 주 생성자
}

Pizza()
// => this("medium") → this("medium", emptyList()) → 주 생성자(size, toppings)
```

체인의 끝에는 언제나 주 생성자가 있다. 위임은 항상 "더 구체적인 생성자"에서 "더 기본이 되는 생성자" 방향으로 이루어지며, 순환 위임(`A → B → A`)은 컴파일 에러다.

### 5.4 자바의 텔레스코핑 생성자와 비교

부 생성자 체인은 자바의 "텔레스코핑 생성자(telescoping constructor)" 안티패턴을 떠올리게 한다. 자바에서는 선택적 인자의 조합마다 생성자를 하나씩 만들어야 했다.

```java
// Java: 텔레스코핑 생성자 — 인자 조합이 늘면 폭발한다
class Pizza {
    Pizza(String size) { this(size, false, false); }
    Pizza(String size, boolean cheese) { this(size, cheese, false); }
    Pizza(String size, boolean cheese, boolean pepperoni) { ... }
    // "size + pepperoni만" 조합은? 또 다른 생성자가 필요...
}
```

선택적 인자가 $n$개면 조합은 최대 $2^n$가지다. 자바는 이렇게 늘어나는 조합을 감당하지 못해 결국 빌더 패턴(Builder)을 쓰게 된다. 코틀린은 이 문제를 언어 차원에서 없앴다. 기본 인자와 이름 붙은 인자(7절)가 $2^n$가지 조합을 헤더 한 줄로 처리하므로, 부 생성자는 "값 변환이 필요한 소수의 경우"에만 쓰인다. 따라서 코틀린에서 부 생성자를 여러 개 나열하고 있다면, 대개는 기본 인자로 리팩터링하라는 신호다.

> [!info] 역사 메모
> 자바가 빌더 패턴에 의존하게 된 근본 원인은 기본 인자가 없다는 점이다. 조슈아 블로크의 『이펙티브 자바』가 빌더를 권한 것도 텔레스코핑 생성자가 가독성을 크게 떨어뜨리기 때문이었다. 코틀린은 기본 인자와 이름 붙은 인자로 빌더가 필요한 경우를 상당 부분 없앴다. 다만 여러 단계에 걸쳐 구성한 뒤 마지막에 빌드하는 진짜 빌더 방식(예: DSL 스타일 구성)이 필요하다면, 코틀린에서도 [[37 - 타입 안전 빌더와 DSL]]의 수신 객체 지정 람다로 더 깔끔하게 표현할 수 있다.

## 6. 오해 바로잡기: "부 생성자가 있으면 주 생성자 초기화는 실행되지 않는다"는 틀렸다

### 6.1 오해의 내용

바로잡을 오해는 다음과 같다. **"부 생성자로 객체를 만들면, 주 생성자에 딸린 초기화(프로퍼티 초기화자와 `init` 블록)는 실행되지 않는다."** 자바에서는 생성자마다 독립된 본문이 있고, 한 생성자가 다른 생성자를 `this(...)`로 명시적으로 호출하지 않으면 필드 초기화자만 실행되고 다른 생성자의 코드는 실행되지 않는다. 이런 경험 때문에 흔히 생기는 오해지만, 코틀린에서는 **틀렸다.**

### 6.2 실제로 확인하기

```kotlin
class Widget(val name: String) {
    val id = nextId()
    init {
        println("init 블록 실행: name=$name, id=$id")
    }

    constructor(name: String, priority: Int) : this(name) {
        println("부 생성자 본문 실행: priority=$priority")
    }

    companion object {
        private var counter = 0
        private fun nextId() = ++counter
    }
}

println("=== 부 생성자로 생성 ===")
val w = Widget("gear", 5)
// => === 부 생성자로 생성 ===
//    init 블록 실행: name=gear, id=1      ← 주 생성자 초기화가 "먼저" 돈다
//    부 생성자 본문 실행: priority=5       ← 그 다음 부 생성자 본문
```

출력을 보면 알 수 있다. 부 생성자 `Widget("gear", 5)`를 호출했는데도 프로퍼티 초기화자(`id = nextId()`)와 `init` 블록이 **부 생성자 본문보다 먼저** 실행되었다. 이유는 5.2절에서 본 강제 위임이다. 부 생성자의 `: this(name)`이 주 생성자를 호출하고, 주 생성자의 초기화가 끝난 뒤에야 부 생성자 본문(`{ println(...) }`)으로 제어가 돌아온다.

정확한 순서는 다음과 같다.

```text
Widget("gear", 5) 호출
   │
   ▼
부 생성자 진입 → : this(name) 위임을 "먼저" 실행
   │
   ├──▶ 주 생성자 진입
   │       ├─ val id = nextId()  실행  (프로퍼티 초기화자)
   │       └─ init { ... }        실행  (init 블록)
   │       주 생성자 완료 ◀──────┐
   │                              │
   ◀──────────────────────────────┘
   │
   ▼
부 생성자 본문 { println("부 생성자 본문...") } 실행
   │
   ▼
객체 완성
```

`this(...)` 위임은 부 생성자 본문의 첫 문장보다 **앞서** 실행된다. 문법도 이를 강제한다. 위임 호출은 부 생성자 시그니처의 일부(`: this(...)`)이므로 본문 `{}` 바깥에 온다.

### 6.3 주 생성자가 **없는** 경우

그렇다면 주 생성자가 아예 없는 클래스는 어떨까? 이때는 프로퍼티 초기화자와 `init` 블록이 어느 주 생성자에 딸리는지 불분명해 보인다. 하지만 코틀린의 규칙은 분명하다. **주 생성자가 없으면 초기화 코드(프로퍼티 초기화자와 `init`)는 각 부 생성자가 상위 타입을 초기화하는 시점에 실행된다.** 즉 이 경우에도 부 생성자 본문보다 먼저 실행된다.

```kotlin
class NoPrimary {
    val log = mutableListOf<String>()
    init {
        log.add("init 실행")
    }

    constructor(x: Int) {
        log.add("부 생성자(Int) 본문: $x")
    }
    constructor(s: String) {
        log.add("부 생성자(String) 본문: $s")
    }
}

println(NoPrimary(42).log)
// => [init 실행, 부 생성자(Int) 본문: 42]
//    init이 부 생성자 본문보다 먼저 실행됐다

println(NoPrimary("hi").log)
// => [init 실행, 부 생성자(String) 본문: hi]
//    다른 부 생성자로 만들어도 init은 항상 먼저 돈다
```

주 생성자가 없어서 `: this(...)` 위임이 없더라도, 각 부 생성자는 진입할 때 초기화 코드를 먼저 실행하고 나서 자신의 본문을 실행한다. JVM 백엔드에서는 컴파일러가 각 부 생성자의 바이트코드 앞부분(상위 클래스 `super()` 호출 직후)에 프로퍼티 초기화자와 `init` 블록을 복제해 넣는 방식으로 이를 구현한다. 결국 **주 생성자가 있든 없든 초기화 코드는 언제나 부 생성자 본문보다 먼저 실행된다.** 앞의 오해는 어떤 경우에도 성립하지 않는다.

> [!note] 명세 기준
> 주 생성자가 없는 클래스에서 부 생성자가 상위 타입을 초기화하는 방법은 두 가지다. `: super(...)`로 상위 생성자를 직접 호출하거나, `: this(...)`로 다른 부 생성자에 위임하는 것이다. 여러 부 생성자가 서로 다른 상위 생성자를 호출할 수도 있다. 주 생성자가 있으면 상위 위임은 주 생성자 헤더의 `: Base()` 한 곳으로 고정되므로 이런 자유가 없다.
>
> 어느 경로든 초기화 코드는 "상위 초기화가 끝나고 본문이 시작되기 전" 위치에 삽입된다. 이 세부 사항은 24장에서 상속과 함께 마무리한다.

### 6.4 오해가 만드는 실제 버그

이 오해를 믿으면 어떤 버그가 생길까? 대표적인 예는 개발자가 "부 생성자로 만들 때는 `init`이 실행되지 않으니 부 생성자 본문에서 검증을 다시 하자"고 생각해 검증이나 부수 효과를 두 번 넣는 경우다.

```kotlin
class Config(val timeoutMs: Int) {
    init {
        require(timeoutMs > 0) { "timeout은 양수여야 한다" }
        println("리소스 예약: $timeoutMs")   // 부수효과 (예: 카운터 증가)
    }
    // M46을 믿는 개발자가 "부 생성자에선 init이 안 도니 여기서도 예약"이라 착각하면...
    constructor(seconds: Double) : this((seconds * 1000).toInt()) {
        // println("리소스 예약: ...")  ← 여기 또 넣으면 이중 예약 버그!
    }
}

Config(1.5)
// => 리소스 예약: 1500   (딱 한 번. init은 위임을 통해 정확히 한 번 실행됨)
```

실제 동작을 알면 부 생성자 본문에는 "주 생성자가 이미 한 일 이후의 추가 작업"만 적으면 된다는 것을 알 수 있다. 초기화, 검증, 불변식 강제는 `init`에 한 번만 두는 것이 정석이며, 어떤 생성자로 진입하든 그 코드는 정확히 한 번 실행된다.

## 7. 기본 인자로 부 생성자 대체하기

### 7.1 "부 생성자 대신 기본 인자"

부 생성자를 가장 흔히 쓰는 경우는 "일부 인자를 생략하고 기본값으로 채우는 오버로드"를 만들 때다. 자바에서는 생성자 오버로딩(telescoping constructor)이 유일한 방법이지만, 코틀린에는 **기본 인자(default arguments)** 가 있어 부 생성자가 대부분 필요 없다([[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]).

```kotlin
// 부 생성자로 오버로드를 흉내 내는 (비추천) 방식:
class Pizza1(val size: String, val cheese: Boolean) {
    constructor(size: String) : this(size, cheese = true)
    constructor() : this("medium", cheese = true)
}

// 기본 인자로 같은 것을 한 줄에:
class Pizza2(val size: String = "medium", val cheese: Boolean = true)

Pizza2()                       // medium, cheese=true
Pizza2("large")                // large, cheese=true
Pizza2("small", cheese = false)
Pizza2(cheese = false)         // 이름 붙은 인자로 앞 인자를 건너뜀
```

기본 인자와 이름 붙은 인자를 함께 쓰면, 부 생성자 여러 개가 하던 일을 헤더 한 줄로 줄일 수 있다. 게다가 부 생성자로는 표현하기 번거로운 "가운데 인자만 생략" 같은 조합도 이름 붙은 인자로 자연스럽게 해결된다.

> [!warning] 흔한 오해
> "기본 인자가 항상 부 생성자보다 낫다"는 것은 과장이다. 기본 인자는 *같은 최종 형태로 위임*하는 오버로드에만 적합하다. "문자열에서 파싱"과 "이미 파싱된 값 받기"처럼 변환 단계가 끼어 있어서 인자 조합마다 초기화 로직 자체가 근본적으로 다를 때는 부 생성자가 더 명확하다(5.2절의 `Temperature` 예).

### 7.2 부 생성자가 여전히 필요한 경우

기본 인자로 대체할 수 없는, 부 생성자를 쓰는 것이 타당한 경우는 다음과 같다.

1. **입력 형태가 근본적으로 다를 때.** `Point(x, y)`와 `Point(both)`, `Temperature(celsius)`와 `Temperature(value, unit)`처럼 위임하기 전에 변환이나 계산이 필요한 경우다.

2. **자바 상호운용에서 특정 시그니처가 필요할 때.** 어떤 자바 프레임워크가 리플렉션으로 "인자 없는 생성자"나 특정 시그니처를 요구하면 부 생성자로 맞춰 준다.

3. **상위 타입의 서로 다른 생성자를 골라 호출해야 할 때.** 주 생성자는 상위 위임을 헤더 한 곳(`: Base(...)`)으로 고정하므로, 상황에 따라 다른 상위 생성자를 호출하려면 주 생성자 없이 부 생성자들로 나눠야 한다(6.3절의 명세 기준 참고).

### 7.3 `@JvmOverloads`: 자바에서 본 기본 인자

기본 인자는 코틀린 호출부에서는 완벽하게 동작하지만, **자바에서는 보이지 않는다.** 자바에는 기본 인자 개념이 없으므로, 자바 코드가 `new Pizza2("large")`를 호출하려면 그런 시그니처의 생성자가 실제로 있어야 한다. 그런데 코틀린은 기본적으로 모든 파라미터를 받는 생성자 하나만 만든다.

이 차이를 메우는 것이 `@JvmOverloads`다. 이 애노테이션을 붙이면 기본값이 있는 파라미터를 뒤에서부터 하나씩 뺀 오버로드들이 자바용으로 자동 생성된다.

```kotlin
class Pizza3 @JvmOverloads constructor(
    val size: String = "medium",
    val cheese: Boolean = true,
)
// 자바에서 볼 수 있는 생성자들:
//   Pizza3()
//   Pizza3(String size)
//   Pizza3(String size, boolean cheese)
```

여기서 앞에서 예고한 규칙이 나온다. 주 생성자에 애노테이션(`@JvmOverloads`)을 붙이려면 **`constructor` 키워드를 다시 써야 한다.** 그냥 `class Pizza3 @JvmOverloads (...)`라고 쓰면 문법 에러다. 상호운용의 세부 내용은 [[45 - Java 상호운용]]에서 다룬다.

## 8. 생성자 가시성과 `constructor` 키워드가 필요한 경우

### 8.1 `private` 생성자와 팩토리

생성자에 가시성 한정자를 붙이면 인스턴스를 만드는 경로를 제어할 수 있다. 가장 흔한 것은 `private constructor`로 외부에서 직접 생성하지 못하게 막고, 동반 객체의 팩토리 함수만 노출하는 패턴이다.

```kotlin
class Session private constructor(val token: String) {
    companion object {
        private val active = mutableMapOf<String, Session>()
        fun of(token: String): Session =
            active.getOrPut(token) { Session(token) }   // 내부에선 생성 가능
    }
}

val s = Session.of("abc")
// val bad = Session("abc")   // 컴파일 에러: constructor is private
```

`private constructor`는 28장(object와 companion)에서 다루는 팩토리 패턴, 캐싱, 인스턴스 수 제한(예: 싱글턴 흉내)의 바탕이 된다. 여기서도 가시성 한정자 `private`을 붙이면 `constructor` 키워드가 필수가 된다.

### 8.2 `constructor` 키워드가 필수가 되는 두 경우

정리하면 주 생성자 앞의 `constructor` 키워드는 다음 둘 중 하나라도 있으면 **생략할 수 없다.**

| 상황 | 예시 | `constructor` |
|---|---|---|
| 한정자·애노테이션 없음 | `class C(val x: Int)` | 생략 가능 |
| 가시성 한정자 있음 | `class C private constructor(val x: Int)` | 필수 |
| 애노테이션 있음 | `class C @Inject constructor(dep: Dep)` | 필수 |
| 둘 다 | `class C @Inject internal constructor(...)` | 필수 |

이는 파서가 모호하게 해석하지 않도록 하기 위해서다. `class C private (...)` 같은 표기는 `private`이 무엇을 수식하는지 애매하므로, 언어는 "한정자나 애노테이션이 오면 그 뒤에 `constructor`를 명시하라"고 정한다. 부 생성자는 처음부터 항상 `constructor`로 시작하므로 이런 문제가 없다.

### 8.3 부 생성자의 가시성

부 생성자에도 가시성을 지정할 수 있다.

```kotlin
class Repository private constructor(val name: String) {
    private constructor() : this("default")   // 부 생성자도 private 가능
    companion object {
        fun create(name: String) = Repository(name)
    }
}
```

주 생성자와 부 생성자의 가시성은 서로 독립적이다. 따라서 주 생성자는 `private`으로 두고 특정 부 생성자만 `internal`로 열어 두는 식으로 세밀하게 제어할 수 있다. 가시성 한정자 각각의 의미(특히 `internal`이 모듈 단위라는 점)는 [[26 - 가시성 한정자]]에서 다룬다.

### 8.4 생성자 애노테이션

주 생성자에 애노테이션을 붙이는 대표적인 용도는 의존성 주입 프레임워크(`@Inject` 등)나 직렬화(`@JsonCreator` 등)와의 연동이다.

```kotlin
class UserService @Inject constructor(
    private val repo: Repository,
    private val clock: Clock,
)
```

애노테이션이 주 생성자에 어떻게 붙고 어떤 사용 지점 대상(`@param:`, `@field:` 등)으로 나뉘는지는 [[44 - 애노테이션과 리플렉션]]에서 다룬다. 이 장에서는 "애노테이션을 붙이면 `constructor` 키워드가 필수"라는 문법 규칙 하나만 기억하면 된다.

## 9. 컴파일된 형태와 마지막 함정들

### 9.1 JVM 백엔드에서의 생성자

JVM 백엔드에서 코틀린 생성자는 자바의 `<init>` 메서드로 컴파일된다. 주 생성자는 `<init>` 하나가 되고, 각 부 생성자는 오버로드된 또 다른 `<init>`이 된다. 부 생성자의 `<init>`는 내부에서 다른 `<init>`를 `invokespecial`로 호출한다(위임). 개념적인 바이트코드 스케치는 다음과 같다.

```text
class Point(val x: Int, val y: Int) {
    constructor(both: Int) : this(both, both)
}

// JVM 백엔드 (개념):
Point.<init>(int x, int y):        // 주 생성자
    invokespecial Object.<init>()  // super
    this.x = x                     // val 프로퍼티 → final 필드
    this.y = y
    return

Point.<init>(int both):            // 부 생성자
    aload both
    aload both
    invokespecial Point.<init>(II) // this(both, both) 위임
    return
```

`val` 프로퍼티는 `final` 필드로, `var`는 일반 필드로 컴파일된다(백킹 필드가 생성되는 정확한 조건은 22장에서 다룬다). 이 매핑은 디컴파일로 직접 확인할 수 있으며, IntelliJ의 "Tools → Kotlin → Show Kotlin Bytecode → Decompile"이 표준 도구다. 확신이 서지 않을 때 소스만 보고 추측하지 말고 실제 바이트코드나 디컴파일 결과를 확인하는 습관을 들이면 잘못된 이해를 예방할 수 있다.

### 9.2 기본 인자의 컴파일: 합성 생성자

기본 인자가 있는 생성자는 JVM 백엔드에서 흥미로운 방식으로 컴파일된다. 코틀린은 "모든 인자를 받는 실제 생성자"와 "어떤 인자가 생략되었는지를 비트마스크로 받는 합성 생성자(synthetic constructor)"를 함께 만든다.

```kotlin
class Box(val w: Int = 1, val h: Int = 1)

// JVM 백엔드 (개념):
//   Box.<init>(int w, int h)                              // 실제 생성자
//   Box.<init>(int w, int h, int mask, DefaultConstructorMarker)  // 합성
//
// Box() 호출 → 합성 생성자를 mask=0b11로 불러 생략된 인자를 기본값으로 채움
```

`DefaultConstructorMarker`라는 합성 타입 인자는 이 특수 생성자를 일반 오버로드와 구별하기 위한 표식이다. 이 세부 사항까지 알 필요는 없다. 하지만 "코틀린 소스 한 줄이 여러 생성자로 컴파일될 수 있다"는 사실을 알아 두면, 자바 상호운용이나 리플렉션(44장 애노테이션과 리플렉션)에서 예상하지 못한 시그니처를 만났을 때 이해의 실마리가 된다.

이 비트마스크 방식이 오버로드마다 생성자를 만드는 `@JvmOverloads`(7.3절)와 어떻게 다른지도 여기서 드러난다. 기본 인자는 기본적으로 합성 생성자 하나와 마스크로 처리되고, `@JvmOverloads`는 자바에서 호출할 수 있는 진짜 오버로드들을 추가로 만든다. 전자는 코틀린 호출부만을, 후자는 자바 호출부까지 대상으로 한다.

> [!caution] 성능 주의
> 이 컴파일 방식은 성능에 거의 영향을 주지 않는다. 합성 생성자를 한 번 호출할 때 생기는 비트마스크 분기는 무시할 수 있는 수준이다. 다만 자주 실행되는 경로에서 객체를 수백만 번 만든다면, 기본 인자를 쓴 호출이 "모든 인자를 명시한 호출"보다 조금 더 많은 바이트코드를 거치는 것은 사실이다.
>
> 실무에서 이것이 병목이 되는 일은 거의 없으므로, 가독성을 희생하면서까지 기본 인자를 피할 이유는 없다. 최적화는 프로파일러가 문제를 지목한 뒤에 한다.

### 9.3 함정 1: 초기화 순서 의존

4.3절에서 본 "선언 후 사용" 함정을 다시 강조한다. 프로퍼티들이 서로를 참조하며 초기화될 때는 선언 순서가 곧 실행 순서이므로, 순서를 바꾸면 값이 달라지거나 초기화되지 않은 `null`을 읽게 된다.

```kotlin
class Circle(radius: Double) {
    val area = Math.PI * radius * radius   // radius(파라미터)만 참조 — 안전
    val diameterHint = "지름 힌트"
    // val bad = derived()  ← 뒤 프로퍼티를 함수로 우회해 읽으면 위험
}
```

원칙은 다음과 같다. **초기화자는 자신보다 앞에 있는 것(주 생성자 파라미터와 먼저 선언된 프로퍼티)에만 의존해야 한다.** 복잡한 상호 의존이 생긴다면 설계에 문제가 있다는 신호이며, `init`에서 순서를 명시적으로 제어하거나 23장(위임 프로퍼티)의 `by lazy`로 계산을 미루는 편이 안전하다.

### 9.4 함정 2: 생성자에서 `this` 누출

객체가 완전히 초기화되기 전에 리스너 등록, 컬렉션에 자신을 추가하기, 콜백 전달 등으로 `this` 참조를 외부에 넘기면, 다른 코드가 절반만 만들어진 객체를 보게 된다.

```kotlin
class Observer(registry: MutableList<Observer>) {
    val name: String
    init {
        registry.add(this)   // 위험: name이 아직 대입되기 전에 this가 밖으로 샌다
        name = "observer"
    }
}
```

`registry.add(this)`가 실행되는 순간 `name`에는 아직 값이 대입되지 않았다. 이때 `registry`를 관찰하던 다른 스레드나 코드가 이 `Observer`의 `name`을 읽으면, 널이 될 수 없는 타입으로 선언했는데도 `null`을 볼 수 있다. 규칙은 **`init`이나 생성자에서 `this`를 외부로 넘기지 않는 것**이다. 특히 멀티스레드 환경에서는 이 누출이 [[43 - 동시성과 메모리 모델]]에서 다루는 가시성 문제와 결합해, 재현하기 어려운 버그를 만든다.

### 9.5 함정 3: `open` 클래스 생성자에서 오버라이드 멤버 호출

4.3절에서 이 함정의 축소판을 이미 보았지만, 상속이 끼면 훨씬 위험해진다. `open` 클래스의 생성자나 초기화자가 `open` 멤버를 호출할 때 하위 클래스가 그 멤버를 오버라이드했다면, **하위 클래스의 필드가 초기화되기 전에** 그 오버라이드가 실행된다.

```kotlin
open class Base {
    open val label: String = "base"
    init {
        println("Base.init이 보는 label: $label")   // 오버라이드된 값? 함정!
    }
}
class Derived : Base() {
    override val label: String = "derived"
}
Derived()
// => Base.init이 보는 label: null
//    Derived.label 초기화는 Base 생성자가 끝난 뒤이므로, Base.init 시점엔 null
```

이 함정은 상위에서 하위로 진행되는 초기화 순서와 함께 24장(상속과 오버라이딩과 초기화 순서)에서 자세히 다룬다. 이 장에서 미리 기억해 둘 교훈은 하나다. **생성자, `init`, 프로퍼티 초기화자에서 `open` 멤버를 호출하지 않는다.** 초기화가 끝나기 전의 객체는 널 안전성조차 보장되지 않는 상태다.
