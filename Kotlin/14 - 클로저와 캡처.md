[[13 - 함수 타입과 람다와 함수 참조]]에서는 함수를 값처럼 다루는 방법을 배웠다. `(Int) -> Int` 같은 함수 타입, `{ x -> x + 1 }` 같은 람다 리터럴, `::foo` 같은 함수 참조는 모두 "코드 조각을 변수에 담아 두었다가 나중에 실행한다"는 발상을 언어에 도입한 것이다.

그런데 그 코드 조각이 자신이 정의된 위치의 지역 변수를 기억해 두었다가 나중에 참조한다면, 이 코드 조각은 함수 본문만으로 설명할 수 없다. 함수가 바깥 환경의 일부를 함께 가지고 다니기 때문이다. 이처럼 함수와 그 함수가 캡처한 환경을 묶은 것을 클로저(closure)라고 부른다.

이 장에서는 클로저가 캡처하는 대상이 값이 아니라 변수라는 점, 캡처된 `var`가 JVM에서 표현되는 방식, 루프 변수를 캡처할 때 생기는 함정, 캡처 때문에 생기는 객체 할당 비용, 그리고 람다 안에서 `return`이 동작하는 규칙(비지역 반환과 라벨 반환)을 다룬다. `inline`이 비지역 반환을 가능하게 하는 원리는 [[15 - 인라인 함수와 reified]]에서 자세히 설명한다.

## 1. 클로저란 무엇인가: 렉시컬 스코프와 자유 변수

### 1.1 자유 변수: 함수 밖에서 온 이름

함수 본문에 등장하는 이름은 두 종류로 나뉜다. 첫째는 함수가 직접 도입한 이름, 즉 파라미터와 지역 변수이다. 이런 이름을 **바운드 변수(bound variable, 속박 변수)** 라고 한다. 둘째는 함수 본문에 등장하지만 함수가 도입하지 않은 이름, 즉 바깥 스코프에서 정의된 이름이다. 이런 이름을 **자유 변수(free variable)** 라고 한다.

```kotlin
fun makeAdder(base: Int): (Int) -> Int {
    return { x -> x + base }   // x는 바운드(람다 파라미터), base는 자유 변수
}

val add10 = makeAdder(10)
val add100 = makeAdder(100)
println(add10(5))    // => 15
println(add100(5))   // => 105
```

`{ x -> x + base }`에서 `x`는 람다가 직접 도입한 파라미터이므로 바운드 변수이다. 반면 `base`는 바깥 함수 `makeAdder`의 파라미터이므로, 람다 입장에서는 자유 변수이다. `makeAdder`가 반환되면 스택 프레임도 사라지지만, `add10`은 `base=10`을, `add100`은 `base=100`을 각각 기억하고 있다. 이렇게 함수가 자신의 자유 변수를 캡처해 두는 현상을 클로저라고 한다.

클로저라는 이름은 수학에서 왔다. 자유 변수가 있는 함수 본문은 그 자체로는 "열린(open)" 식이다. 자유 변수의 값이 정해지지 않으면 실행할 수 없기 때문이다. 함수가 주변 환경을 캡처해 자유 변수에 값을 채우면 식이 "닫힌다(closed)". 그래서 클로저, 우리말로는 폐포(閉包)라고 부른다.

> [!info] 역사 메모
> 클로저는 람다 계산에서 출발해 1970년대 Scheme 계열 언어에서 정립된 개념이다(용어는 1964년 Peter Landin이 처음 사용했다). 이 개념의 핵심은 **렉시컬 스코프(lexical scope, 어휘적 스코프)** 이다. 렉시컬 스코프에서는 이름이 어느 변수를 가리키는지를 코드가 *작성된 위치*에 따라 정적으로 결정한다.
>
> 반대 개념은 호출 시점의 환경으로 결정하는 다이나믹 스코프인데, 현대 언어는 대부분 렉시컬 스코프를 사용한다. 코틀린도 렉시컬 스코프를 사용한다. 따라서 `base`가 무엇을 가리키는지는 람다를 *어디서 정의했는지*로 정해지고, 어디서 호출했는지와는 관계가 없다.

### 1.2 렉시컬 스코프: 정의한 위치가 이름을 결정한다

렉시컬 스코프가 실제로 어떻게 동작하는지 확인해 보자. 아래 코드에는 `shift`라는 이름이 두 번 나오지만, 람다가 캡처하는 것은 람다를 *작성한 위치*에서 보이는 `shift`이다.

```kotlin
fun outer(): (Int) -> Int {
    val shift = 100
    val lambda = { n: Int -> n + shift }   // 여기서 보이는 shift는 100
    return lambda
}

fun main() {
    val shift = -999                       // 이름은 같지만 다른 변수
    val f = outer()
    println(f(1))                          // => 101  (main의 shift가 아님!)
}
```

`f(1)`을 `main` 안에서 호출했지만, 결과는 `-998`이 아니라 `101`이다. 람다는 자신이 정의된 `outer`의 환경을 캡처했고, 그 환경에서 `shift`는 `100`이기 때문이다. 호출하는 시점에 `main`에 `shift=-999`가 있더라도 결과에는 영향을 주지 않는다. 즉 **캡처할 대상은 정의 시점에 이름을 해석한 결과로 정해진다.**

### 1.3 클로저를 만드는 코틀린 구성 요소

람다만 클로저를 만드는 것은 아니다. 코틀린에서는 여러 구성 요소가 자유 변수를 캡처할 수 있다.

```kotlin
fun demo() {
    val captured = 42

    // (1) 람다
    val l = { captured + 1 }

    // (2) 익명 함수
    val anon = fun(): Int { return captured + 2 }

    // (3) 지역 함수 (12장)
    fun local() = captured + 3

    // (4) 익명 객체 (31장)
    val obj = object : Runnable {
        override fun run() { println(captured + 4) }
    }

    println(l())         // => 43
    println(anon())      // => 44
    println(local())     // => 45
    obj.run()            // => 46
}
```

람다와 익명 함수, 지역 함수, 익명 객체는 모두 클로저를 만든다. 문법과 `return` 규칙(7절에서 설명)은 서로 다르지만, 자유 변수를 캡처한다는 점은 같다. 따라서 이 장에서 설명하는 캡처 규칙은 네 가지 모두에 적용된다.

> [!note] 명세 기준
> 코틀린 언어 명세는 클로저를 "람다, 익명 함수, 지역 함수, 객체 표현식이 자신을 감싸는 스코프의 값과 변수를 캡처하는 것"으로 정의한다. 명세의 원문은 "captures the values and variables"이다. 즉 코틀린은 *값*뿐 아니라 *변수*도 캡처한다고 명시하고 있으며, 이 점에서 Java와 차이가 생긴다. 다음 절에서 이 차이를 살펴본다.

## 2. 값이 아니라 변수를 캡처한다: Java와 비교

### 2.1 Java의 규칙: effectively final인 변수의 값만 캡처한다

캡처의 의미를 이해하려면 Java와 비교해 보는 것이 가장 빠르다. Java의 람다와 익명 클래스는 지역 변수를 캡처할 때 엄격한 조건을 요구한다. **그 변수는 `final`이거나 `effectively final`(초기화한 뒤 다시 대입하지 않는 변수)이어야 한다.**

```java
// Java
int counter = 0;
Runnable r = () -> {
    // counter++;              // 컴파일 에러: Variable used in lambda should be final or effectively final
    System.out.println(counter);
};
counter = 5;                    // 이 재대입도 위 람다를 컴파일 에러로 만든다
```

Java가 이렇게 제한하는 이유는 캡처 방식이 **값 복사**이기 때문이다. Java 람다는 지역 변수 `counter`의 *현재 값*을 자신의 숨은 필드에 복사한다. 이 상태에서 바깥의 `counter`를 바꾸면 람다 안의 복사본은 바뀌지 않으므로, 바깥과 안이 서로 다른 값을 보게 된다. Java는 이런 혼란을 막으려고 캡처되는 변수를 바꾸지 못하게 한다. 결국 Java의 캡처는 **변하지 않는 값을 복사해 두는 방식**이다.

### 2.2 코틀린의 규칙: var도 캡처하고, 변수 자체를 공유한다

코틀린은 반대로 설계되었다. 코틀린 람다는 `val`과 `var`를 모두 캡처할 수 있다. 또한 캡처한 `var`를 람다 안에서 **수정할 수 있고, 수정한 값은 바깥에서도 보인다**.

```kotlin
fun main() {
    var counter = 0
    val increment = { counter++ }          // var 캡처 — Java라면 불가능
    val report = { println(counter) }

    increment()
    increment()
    increment()
    report()                               // => 3   (람다 안 수정이 바깥에 반영됨)

    counter = 100                           // 바깥에서 수정
    report()                               // => 100 (람다가 바깥 수정도 봄)
}
```

`increment` 람다가 `counter`를 세 번 증가시켰고, 그 결과는 바깥 스코프와 다른 람다(`report`)에서도 그대로 보인다. 바깥에서 `counter = 100`으로 바꾸면 `report`도 바뀐 값을 출력한다. Java처럼 값을 복사하는 방식이라면 이런 결과가 나올 수 없다.

코틀린의 클로저는 값을 복사하지 않고 **변수 자체, 즉 값을 저장하는 공간(storage cell)을 공유**한다. 바깥 스코프와 람다가 같은 저장 공간을 가리키므로, 어느 쪽에서 수정하든 양쪽에서 모두 보인다.

두 언어의 차이를 표로 정리하면 다음과 같다.

| | Java | Kotlin |
|---|---|---|
| 캡처 대상 제약 | `final`/effectively final만 | `val`·`var` 모두 |
| 캡처 방식 | 값 복사(스냅샷) | 변수(저장 셀) 공유 |
| 람다 안에서 재대입 | 불가(컴파일 에러) | `var`면 가능 |
| 바깥 수정의 가시성 | 캡처 후 수정 자체가 금지 | 서로 보임 |

> [!warning] 흔한 오해
> "코틀린 람다도 `var`를 캡처할 때 값을 복사한다"는 생각은 틀렸다. 값을 복사한다면 `increment()`를 세 번 호출해도 바깥의 `counter`는 바뀌지 않아야 한다. 그러나 위 예제에서 `report()`는 `3`을 출력한다. 코틀린은 변수를 공유하기 때문이다. 그런데 JVM의 지역 변수 슬롯은 원래 공유할 수 없다. 코틀린이 이 문제를 어떻게 해결하는지는 다음 절에서 설명한다.

### 2.3 코틀린이 다르게 설계한 이유

Java 방식은 안전하지만 표현력이 떨어진다. 상태를 계속 갱신하는 카운터나 누산기, 콜백의 결과를 모으는 코드는 `var`를 캡처할 수 없으면 작성하기 어색하다. 그래서 Java에서는 길이가 1인 배열(`int[] c = {0}`)이나 `AtomicInteger`를 사용해 이 제약을 우회한다.

코틀린은 함수형 스타일을 실용적으로 쓸 수 있도록, 이런 우회 코드를 컴파일러가 대신 만들어 주는 방식을 택했다. 다음 절에서 설명할 `Ref` 래핑이 바로 그 방식이다. 개발자가 직접 `IntArray(1)`을 만들 필요 없이 컴파일러가 자동으로 처리한다.

물론 대가도 있다. 변수를 공유하면 동시성 문제가 생길 수 있다. 여러 스레드가 같은 저장 공간을 수정하면 가시성 문제와 경쟁 조건이 그대로 발생한다([[43 - 동시성과 메모리 모델]] 참고). Java 방식은 구조적으로 이 위험을 줄였지만, 코틀린은 표현력을 선택하고 위험 관리는 개발자에게 맡겼다. 이 트레이드오프를 알아야 캡처를 안전하게 사용할 수 있다.

## 3. 캡처된 var가 JVM에서 표현되는 방식: Ref 래핑

### 3.1 문제: JVM의 지역 변수는 공유할 수 없다

2절에서 "변수를 공유한다"고 설명했지만, 이 설명을 JVM에서 그대로 구현할 수는 없다. JVM에서 지역 변수는 스택 프레임의 로컬 변수 슬롯(local variable slot)에 저장되고, 스택 프레임은 메서드가 반환되면 사라진다. 그런데 람다는 JVM 백엔드에서 대개 별도의 객체로 구현되며, 메서드가 반환된 뒤에도 남아 있어야 한다. 곧 사라질 스택 슬롯을, 계속 남아 있어야 하는 객체와 공유할 방법이 필요하다.

게다가 로컬 슬롯은 객체의 필드가 아니라 원시적인 저장 위치이다. JVM 바이트코드에는 두 개의 독립된 대상(바깥 스택 프레임과 람다 객체)이 같은 슬롯을 가리키게 하는 방법이 없다. 따라서 한쪽에서 슬롯 값을 바꿔도 다른 쪽은 그 변화를 알 수 없다.

### 3.2 해법: 힙에 있는 참조 셀로 옮긴다

**JVM 백엔드에서** 코틀린 컴파일러는 이 문제를 다음과 같이 해결한다. **캡처되고 수정되는 `var`를 지역 슬롯에 두지 않고, 힙에 할당한 작은 래퍼 객체의 필드로 옮긴다.** 이 래퍼는 표준 라이브러리 내부의 `kotlin.jvm.internal.Ref` 계열 클래스이다.

```text
개념도: var counter = 0 이 람다에 의해 캡처될 때 (JVM 백엔드)

  [스택 프레임: main]                    [힙]
  +---------------------+       +-------------------------+
  | ref  ───────────────┼──────>| Ref.IntRef              |
  +---------------------+       |   element: int = 3      |<──┐
                                +-------------------------+   │
  [힙: 람다 객체 increment]                                   │
  +---------------------+                                     │
  | $counter ───────────┼─────────────────────────────────────┘
  +---------------------+
       두 쪽 모두 같은 IntRef를 가리킨다 → element 수정이 서로 보인다
```

원래 코드는 개념적으로 아래 의사 코드처럼 변환된다.

```kotlin
// 사용자가 쓴 코드
fun main() {
    var counter = 0
    val increment = { counter++ }
    increment(); increment(); increment()
    println(counter)   // => 3
}

// JVM 백엔드가 만드는 것에 가까운 의사 코드
fun main() {
    val counter = IntRef()          // kotlin.jvm.internal.Ref.IntRef
    counter.element = 0
    val increment = Increment(counter)   // Ref를 필드로 붙잡는 람다 객체
    increment.invoke(); increment.invoke(); increment.invoke()
    println(counter.element)        // => 3
}
class Increment(val c: IntRef) : Function0<Unit> {
    override fun invoke() { c.element = c.element + 1 }
}
```

이제 `counter`는 스택 슬롯이 아니라 힙 객체의 `element` 필드이다. `main`의 스택 프레임과 람다 객체가 *같은 `IntRef` 인스턴스*를 가리키므로, 어느 쪽에서 `element`를 바꿔도 다른 쪽에서 바뀐 값을 볼 수 있다. 스택 프레임이 사라져도 힙 객체는 참조가 남아 있는 동안 계속 존재한다. 2절에서 설명한 "변수 공유"는 실제로 이렇게 구현된다.

### 3.3 Ref의 종류, 그리고 val과의 차이

`Ref`에는 타입별로 특화된 클래스가 있다. **JVM 백엔드에서는** 대략 다음과 같이 나뉜다.

| 캡처된 var의 타입 | 래핑 클래스(개념) | 필드 |
|---|---|---|
| `Int` | `Ref.IntRef` | `int element` |
| `Long` | `Ref.LongRef` | `long element` |
| `Double` | `Ref.DoubleRef` | `double element` |
| `Boolean` | `Ref.BooleanRef` | `boolean element` |
| 참조 타입(`String`, 사용자 클래스 등) | `Ref.ObjectRef<T>` | `T element` |

여기서 중요한 점이 있다. **재대입되는 `var`만 `Ref`로 옮겨진다.** 캡처된 변수가 초기화된 뒤 어디에서도 재대입되지 않는다면(`val`이거나 사실상 final인 `var`라면), 값을 람다 객체의 필드에 그대로 복사해도 된다. 아무도 값을 바꾸지 않으므로 바깥과 안의 값이 달라질 일이 없기 때문이다.

이때 기준은 "람다가 변수를 수정하는가"가 아니라 "변수가 람다 안이든 바깥이든 어디에서든 재대입되는가"이다. 람다가 변수를 읽기만 하더라도, 캡처한 뒤 바깥에서 그 `var`를 다시 대입한다면 람다가 갱신된 값을 볼 수 있어야 한다. 따라서 이 경우에도 `Ref`로 옮겨진다.

```kotlin
fun example() {
    val base = 10                    // val — 수정 없음 → Ref 없이 값으로 캡처
    var acc = 0                       // var, 수정됨 → IntRef로 승격
    val fn = {
        acc += base                   // acc는 Ref.element, base는 그냥 int 필드
    }
    fn(); fn()
    println(acc)                      // => 20
}
```

즉 코틀린의 캡처는 두 가지 전략을 함께 사용한다. **재대입되지 않는 변수는 Java처럼 값을 복사하고, 재대입되는 변수만 참조 셀로 공유한다.** 자유 변수는 대부분 읽기만 하므로, 캡처의 대부분은 래퍼 없이 값 복사로 처리된다. 공유가 꼭 필요한 `var`에만 `Ref` 비용이 든다.

> [!note] 명세 기준
> `Ref` 래핑은 **JVM 백엔드의 구현 방식**이다. 언어 명세가 요구하는 것은 "캡처된 `var`를 수정하면 모든 클로저와 원래 스코프에서 일관되게 보여야 한다"는 *관찰 가능한 동작*이지, `IntRef`라는 특정 클래스를 쓰라는 것이 아니다.
>
> Kotlin/Native와 Kotlin/JS, Wasm 백엔드는 각자 다른 방식으로 같은 동작을 구현한다(JS에서는 언어 자체의 클로저가 변수를 공유하므로 별도 래핑이 덜 필요할 수 있다). 따라서 "코틀린은 `var`를 `Ref`로 감싼다"는 설명에는 반드시 "JVM 백엔드에서"라는 조건을 붙여야 한다. 디컴파일로 확인할 수 있는 것도 JVM `.class` 파일뿐이다([[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]] 참고).

### 3.4 Java의 우회 방법과 비교: 코틀린이 자동화한 것

`Ref`가 무엇을 자동화했는지는 Java 개발자가 직접 작성하던 우회 코드와 비교하면 분명해진다. Java에서 람다 안의 값을 갱신하려면 `effectively final` 제약을 우회해야 했다. 보통 길이가 1인 배열이나 별도의 홀더 객체를 사용했다.

```java
// Java: 캡처된 값을 갱신하려는 고전적 우회로
int[] counter = { 0 };            // 배열 참조는 effectively final, 내용은 가변
Runnable r = () -> counter[0]++;  // 배열 원소는 바꿀 수 있다
r.run(); r.run();
System.out.println(counter[0]);   // => 2
```

배열 `counter`의 *참조*는 재대입되지 않으므로 `effectively final`이고, 람다는 이 참조를 값으로 복사해 캡처한다. 그러나 배열의 *내용*은 바꿀 수 있으므로 `counter[0]++`이 동작한다.

코틀린의 `Ref.IntRef`는 바로 이 "길이가 1인 가변 홀더"를 컴파일러가 대신 만들어 주는 것이다. Java 개발자가 직접 작성하던 `int[]{0}`을, 코틀린은 `var counter = 0`이라는 자연스러운 문법 뒤에 숨겼다. 덕분에 코틀린 코드는 우회 코드 없이 읽기 쉽지만, 내부에서 힙 홀더를 공유한다는 점은 Java와 같다. 이 비교를 보면 코틀린의 `var` 캡처가 특별한 기법이 아니라, 이미 알려진 관용구를 언어에 내장한 것임을 알 수 있다.

### 3.5 Ref로 옮길 때 드는 비용

`Ref`로 옮기는 데에도 비용이 든다. 원래 스택에 있으면 되는 `Int`가 힙에 할당된 `IntRef` 객체가 된다. 즉 **캡처되고 수정되는 원시 타입 `var` 하나마다 힙 할당이 한 번 발생**하고, 값을 읽고 쓸 때마다 필드를 거쳐 간접적으로 접근해야 한다. 원시 값 하나를 다루려고 객체를 하나 만드는 셈이므로, 자주 실행되는 루프(hot loop)에서 이런 캡처가 반복되면 GC 부담이 커진다. 인라인으로 이 비용을 없애는 방법은 8절에서 설명한다.

## 4. 캡처 대상: this, 파라미터, 수신 객체

### 4.1 지역 변수만 캡처되는 것은 아니다

클로저가 캡처하는 자유 변수는 지역 `val`/`var`만이 아니다. 다음 대상도 캡처된다.

- **함수 파라미터** (지역 변수와 동일하게 취급된다)
- **바깥 함수에 정의된 지역 함수와 람다**
- **바깥 클래스의 `this`**: 프로퍼티나 메서드에 접근하면 `this`를 캡처한다.
- **수신 객체 지정 람다의 수신 객체** (`this@label`)

특히 클래스 안에서 프로퍼티를 참조하는 람다는 프로퍼티의 값이 아니라 **인스턴스(`this`)에 대한 참조**를 캡처한다는 점에 주의해야 한다.

```kotlin
class Counter {
    var count = 0
    fun makeIncrementer(): () -> Unit {
        return { count++ }        // this.count++ — Counter 인스턴스를 캡처
    }
}

fun main() {
    val c = Counter()
    val inc = c.makeIncrementer()
    inc(); inc()
    println(c.count)              // => 2
}
```

`{ count++ }`는 겉보기에는 지역 변수를 캡처하는 것처럼 보이지만, `count`는 `Counter`의 프로퍼티이므로 실제로는 `this.count++`이다. 따라서 이 람다는 `Counter` 인스턴스 `c` 전체를 캡처한다. `inc`가 살아 있는 동안에는 `c`도 메모리에서 해제되지 않는다. 6절에서 다룰 메모리 누수는 여기서 시작된다.

### 4.2 값 캡처와 참조 캡처를 혼동하지 말자

흔히 혼동하는 부분을 정리해 보자. "값을 캡처하는가, 참조를 캡처하는가"라는 질문에는 사실 서로 다른 두 질문이 섞여 있다.

1. **저장 공간(변수)을 캡처하는가, 값을 캡처하는가**: 2절과 3절에서 다룬 내용이다. JVM 백엔드에서 재대입되는 `var`는 저장 공간을 공유하고, `val`은 값을 복사한다.
2. **캡처한 값이 참조 타입이라면, 그 참조가 가리키는 객체는 여전히 변할 수 있다**: `val`은 재대입만 막을 뿐, 가리키는 객체까지 불변으로 만들지는 않는다([[11 - 변수와 초기화 - val과 const와 lateinit]] 참고).

두 질문은 서로 독립적이다. `val`로 캡처했더라도, 그 `val`이 가리키는 객체가 가변 객체라면 람다는 객체의 변화를 볼 수 있다.

```kotlin
fun main() {
    val list = mutableListOf(1, 2, 3)   // val — 재대입 불가
    val printer = { println(list) }      // list(참조 값)를 복사 캡처

    list.add(4)                          // 객체 자체를 변경 (재대입 아님)
    printer()                            // => [1, 2, 3, 4]  — 변화가 보인다!
}
```

`list`는 `val`이므로 3절의 기준에 따라 값 복사로 캡처된다. 그러나 이때 복사되는 값은 "리스트 객체를 가리키는 참조"이다. 원본과 복사본이 *같은 리스트 객체*를 가리키므로, 리스트에 원소를 추가하면 양쪽 모두 그 변화를 본다. 여기서 "값 복사"라는 표현을 오해하면 안 된다. 복사되는 것은 참조값이며, 리스트 전체를 깊게 복사하는 것이 아니다. 따라서 `val`로 캡처했다고 해서 불변이 보장되는 것은 아니다.

### 4.3 수신 객체 지정 람다의 캡처

수신 객체 지정 람다(`T.() -> R`, [[16 - 스코프 함수와 수신 객체 관용구]]에서 자세히 설명)에서는 수신 객체 `this`도 캡처 대상에 포함된다. 수신 객체가 여러 겹으로 중첩되어 있다면 `this@label`로 어떤 수신 객체를 가리키는지 명시한다.

```kotlin
class Html {
    val children = mutableListOf<String>()
    fun body(block: Html.() -> Unit) { this.block() }
    fun p(text: String) { children.add("<p>$text</p>") }
}

fun main() {
    val outer = "제목"                    // 지역 변수도 함께 캡처
    val page = Html()
    page.body {
        p(outer)                          // this(=page)와 outer를 함께 캡처
    }
    println(page.children)                // => [<p>제목</p>]
}
```

`{ p(outer) }` 블록은 수신 객체 `this`(=`page`)를 통해 `p`를 호출하면서, 동시에 지역 변수 `outer`를 캡처한다. 이처럼 클로저는 렉시컬 스코프에 있는 여러 종류의 이름(수신 객체, 지역 변수, 바깥 클래스의 `this`)을 한꺼번에 캡처할 수 있다.

### 4.4 캡처와 SAM 변환: Java 인터페이스로 전달할 때

캡처는 코틀린 함수 타입에서만 일어나지 않는다. 람다를 Java의 단일 추상 메서드 인터페이스(SAM)로 변환해 전달할 때에도 캡처는 그대로 유지된다. 이때 만들어지는 SAM 구현 객체도 캡처한 값을 필드로 가지고 있다.

```kotlin
fun scheduleAll(tasks: List<String>, run: (Runnable) -> Unit) {
    var done = 0
    for (task in tasks) {
        run(Runnable {                    // Runnable은 Java SAM 인터페이스
            done++                         // 캡처된 var done 공유
            println("$task 완료 (누적 $done)")
        })
    }
}
```

`Runnable { ... }`은 SAM 변환을 거쳐 `Runnable` 구현 객체가 되고, 이 객체가 재대입되는 `var`인 `done`을 캡처한다. **JVM 백엔드에서는** 3절과 마찬가지로 `Ref.IntRef`를 공유하는 방식으로 구현된다.

여기서 주의할 점은 이런 SAM 객체가 스레드 풀이나 이벤트 루프 같은 *다른 실행 환경*으로 전달되는 경우가 많다는 것이다. 그러면 여러 스레드가 캡처된 `done`을 동시에 수정할 수 있고, 공유된 저장 공간에서 경쟁 조건이 발생한다. 언어는 캡처 자체를 안전하게 처리해 주지만, 캡처된 변수에 동시에 접근하는 것까지 안전하게 만들어 주지는 않는다. SAM 변환의 전체 규칙은 [[45 - Java 상호운용]]에서 설명한다.

## 5. 루프 변수 캡처: 반복할 때마다 새 변수가 만들어질까

### 5.1 잘 알려진 함정과 코틀린의 동작

여러 언어에서 초보자가 자주 겪는 함정이 있다. 루프 안에서 람다를 만들어 리스트에 담은 뒤, 루프가 끝나고 람다를 모두 호출하면 전부 마지막 값만 출력하는 문제이다. 이 문제는 루프 변수가 모든 반복에서 *공유*될 때 생긴다(JavaScript의 `var` 루프가 대표적이다). 코틀린의 `for`에서는 이 문제가 생기지 않는다.

```kotlin
fun main() {
    val fns = mutableListOf<() -> Int>()
    for (i in 1..3) {
        fns.add { i }                    // 각 반복의 i를 캡처
    }
    println(fns.map { it() })            // => [1, 2, 3]   (3, 3, 3 아님!)
}
```

결과는 `[1, 2, 3]`이다. 코틀린 `for` 루프의 변수 `i`는 **반복할 때마다 새로 바인딩되는 불변 변수**처럼 동작한다. 첫 번째, 두 번째, 세 번째 반복의 `i`는 서로 다른 저장 공간이므로, 각 람다는 자신이 만들어진 반복의 값을 정확히 캡처한다. 게다가 `for`의 루프 변수는 재대입할 수 없는 `val`과 같으므로, 하나의 저장 공간을 공유하면서 값이 갱신되는 일도 없다.

> [!warning] 흔한 오해
> "JavaScript처럼 코틀린 루프도 마지막 값만 캡처될 것"이라는 걱정은 코틀린 `for`에는 해당하지 않는다. JavaScript의 함정은 `var`로 선언한 함수 스코프 변수를 모든 반복이 공유해서 생긴 문제였고, 그래서 `let`이 도입되었다. 코틀린의 `for` 변수는 처음부터 반복마다 새로 바인딩되는 불변 변수이다. 다만 5.2절처럼 *루프 바깥에 선언한 `var`* 를 캡처하면 결과가 완전히 달라진다.

### 5.2 실제로 문제가 되는 경우: 루프 바깥의 var를 캡처할 때

문제가 되는 것은 루프 변수가 아니라, 루프 *바깥*에 선언하고 루프 안에서 갱신하는 `var`를 캡처하는 경우이다. 이때는 3절의 `Ref` 공유가 그대로 적용되므로, 모든 람다가 **같은 저장 공간**을 캡처한다.

```kotlin
fun main() {
    val fns = mutableListOf<() -> Int>()
    var j = 0                            // 루프 바깥 var — 단일 셀
    while (j < 3) {
        fns.add { j }                    // 모두 같은 IntRef 공유
        j++
    }
    println(fns.map { it() })            // => [3, 3, 3]   (모두 최종값)
}
```

여기서 `j`는 루프 바깥에 선언된 하나의 `var`이다. 세 람다가 모두 같은 `IntRef`를 캡처하므로, 루프가 끝나 `j`가 `3`이 된 뒤에 호출하면 모두 `3`을 반환한다. 이것은 버그가 아니라, 변수를 공유하는 캡처 규칙에 따른 정상적인 결과이다. 반복마다 다른 값을 캡처하려면, 각 반복에서 **새 지역 변수**에 값을 담아 두어야 한다.

```kotlin
fun main() {
    val fns = mutableListOf<() -> Int>()
    var j = 0
    while (j < 3) {
        val snapshot = j                 // 반복마다 새 val — 값 고정
        fns.add { snapshot }
        j++
    }
    println(fns.map { it() })            // => [0, 1, 2]
}
```

`val snapshot = j`는 반복할 때마다 새로 선언되는 불변 변수이므로, 각 람다는 해당 반복 시점의 값을 캡처한다. 루프 안에서 캡처할 때는 이렇게 새 지역 변수에 값을 담아 두는 방법을 주로 사용한다. 정리하면 다음과 같다. **반복마다 새로 바인딩되는 변수(`for` 변수, 반복 안에서 선언한 `val`)를 캡처하면 반복별 값을 보고, 모든 반복이 공유하는 하나의 변수(`while` 바깥의 `var`)를 캡처하면 마지막 값을 본다.**

### 5.3 for와 while의 결과가 다른 이유

`for`와 `while`에서 결과가 다른 것은 우연이 아니다. 반복할 때마다 새 스코프가 만들어지는지에 따라 달라진다. `for (i in range)`에서 `i`는 언어가 반복마다 새로 도입하는 이름이다. 반면 `while` 조건에 사용한 `var j`는 루프 바깥에 한 번만 선언된 변수이므로, 루프는 그 하나의 저장 공간을 계속 갱신할 뿐이다. 그래서 `for`에서는 대체로 안전하고, `while`에서 바깥의 `var`를 캡처할 때는 주의해야 한다.

## 6. 캡처와 객체 수명: 캡처된 객체는 해제되지 않는다

### 6.1 캡처하면 참조가 유지된다

클로저가 어떤 객체를 캡처하면, 클로저가 살아 있는 동안 그 객체는 GC 대상이 되지 않는다. 나중에 실행될 코드가 그 객체를 사용할 수도 있으므로, 런타임이 임의로 회수할 수 없기 때문이다. 문제는 의도하지 않게 크고 오래 사는 객체를 캡처했을 때 생긴다.

```kotlin
class HeavyResource {
    val bigBuffer = ByteArray(100_000_000)   // 큰 메모리
    fun makeCallback(): () -> Int {
        // bigBuffer를 직접 안 쓰더라도 this를 캡처하면 HeavyResource 전체가 산다
        return { bigBuffer.size }
    }
}
```

`makeCallback`이 반환한 람다는 `bigBuffer.size` 한 줄만 사용한다. 하지만 `bigBuffer`는 `this.bigBuffer`이므로, 람다는 1억 바이트 버퍼를 포함한 `HeavyResource` 인스턴스 전체를 캡처한다. 이 콜백을 오래 유지되는 리스트나 전역 레지스트리에 등록하면, `HeavyResource`를 더 이상 사용하지 않더라도 콜백 때문에 버퍼가 회수되지 않는다. 클로저 때문에 생기는 전형적인 메모리 누수이다.

### 6.2 필요한 값만 지역 변수로 꺼내서 캡처하자

해결 방법은 인스턴스 전체를 캡처하지 않고, 필요한 값만 지역 변수에 복사한 뒤 그 변수를 캡처하는 것이다.

```kotlin
class HeavyResource {
    val bigBuffer = ByteArray(100_000_000)
    fun makeCallback(): () -> Int {
        val size = bigBuffer.size            // 필요한 값만 지역으로 뽑음
        return { size }                       // this가 아니라 size(Int)만 캡처
    }
}
```

이제 람다는 `Int` 값 하나만 캡처하고, `HeavyResource` 인스턴스는 캡처하지 않는다. `makeCallback`이 반환된 뒤 다른 참조가 없다면, 버퍼를 포함한 `HeavyResource`는 정상적으로 회수된다. 이너 클래스가 바깥 인스턴스를 캡처해서 생기는 누수도 원인이 같으며, 해결 방법도 같다. 바깥 인스턴스 대신 필요한 값만 캡처하면 된다([[31 - 중첩 클래스와 이너 클래스와 익명 객체]] 참고).

> [!caution] 성능 주의
> Android나 데스크톱 UI, 오래 유지되는 이벤트 버스, 캐시, 정적 컬렉션에 콜백을 등록할 때 특히 위험하다. 수명이 짧은 컴포넌트가 만든 람다를 수명이 긴 곳에 등록하면, 람다가 캡처한 컴포넌트와 그 컴포넌트가 참조하는 뷰 트리 전체가 함께 유지된다. 콜백을 등록했다면 반드시 해제하고, 캡처하는 대상은 필요한 값 몇 개로 최소화해야 한다. 람다를 작성할 때는 "이 람다가 정확히 무엇을 캡처하는가"를 항상 확인하는 것이 좋다.

### 6.3 인라인된 람다는 캡처 객체를 만들지 않는다

다행히 람다가 **인라인 함수**에 전달되어 인라인되면, 람다 객체 자체가 만들어지지 않는다. 람다 본문이 호출 위치에 그대로 펼쳐지므로 캡처한 값을 보관할 객체가 없고, 따라서 그 객체 때문에 생기는 누수도 없다. 표준 라이브러리의 컬렉션 연산(`forEach`, `map`, `filter` 등)은 대부분 인라인 함수이므로, 여기에 전달한 람다는 힙에 남지 않는다. 누수는 주로 **인라인되지 않고 어딘가에 저장되는** 람다에서 생긴다.

## 7. 비지역 반환과 라벨 반환: return은 어디로 돌아갈까

### 7.1 흔한 오해: "람다 안의 return은 람다만 끝낸다"

많은 개발자가 "람다 안에서 `return`을 쓰면 그 람다만 끝나고 바깥 함수는 계속 실행된다"고 생각한다. 그러나 이 생각은 **틀렸다.** 코틀린에서 람다 안에 라벨 없이 쓴 `return`은, 문법적으로 허용되는 경우에 한해 람다가 아니라 **람다를 감싸는 함수 전체를 반환시킨다.** 이를 **비지역 반환(non-local return)** 이라고 한다.

```kotlin
fun findFirstEven(nums: List<Int>): Int? {
    nums.forEach { n ->
        if (n % 2 == 0) return n         // 이 return은 findFirstEven을 끝낸다!
    }
    return null
}

fun main() {
    println(findFirstEven(listOf(1, 3, 4, 5, 6)))   // => 4
}
```

`return n`은 `forEach`에 전달한 람다 안에 있지만, 람다만 끝내는 것이 아니라 바깥 함수 `findFirstEven`을 `n`을 반환하며 즉시 종료시킨다. 그래서 첫 번째 짝수인 `4`를 찾자마자 함수 전체가 끝나고 `4`가 반환된다. 만약 `return`이 람다만 끝낸다면 루프가 계속 돌고, 마지막에 `null`이 반환되었을 것이다. 이처럼 `return`이 자신이 작성된 람다를 넘어 바깥 함수를 끝내는 것이 비지역 반환이다.

### 7.2 forEach에서는 되고, 저장된 람다에서는 안 되는 이유

그런데 비지역 반환이 모든 람다에서 가능한 것은 아니다. **인라인 함수에 전달된 람다에서만** 사용할 수 있다. 위 예제가 동작한 것도 `forEach`가 `inline` 함수이기 때문이다. 인라인되지 않는 곳에 전달한 람다에서 라벨 없는 `return`을 쓰면 **컴파일 에러**가 발생한다.

```kotlin
fun demo(): Int {
    val lambda = { n: Int -> return n }
    // 컴파일 에러: 'return' is not allowed here
    //   ('return' is prohibited in a lambda that is not inlined)
    return lambda(5)
}
```

이런 제약이 있는 이유는 다음과 같다. 비지역 반환은 "이 `return`을 만나면 바깥 함수의 스택 프레임을 끝내고 그 함수의 반환 지점으로 이동하라"는 뜻이다. 이렇게 하려면 람다 본문이 바깥 함수의 스택 프레임 *안에서* 실행되고 있어야 한다. **인라인 함수는 람다 본문을 호출 위치에 그대로 펼쳐 넣기 때문에**, 람다 안의 `return`은 바깥 함수 본문에 있는 평범한 `return`이 되고, 아무 문제 없이 프레임을 끝낼 수 있다.

반면 인라인되지 않는 람다는 별도의 함수 객체로 컴파일되어 *독립된 스택 프레임*에서 실행된다(3절 참고). 이 상황에서 람다 안의 `return`이 바깥 함수를 끝내려면, 이미 반환되었을 수도 있는 바깥 프레임으로 이동해야 한다. 바깥 함수가 끝난 뒤에 람다가 호출되면 돌아갈 프레임 자체가 없다. 이런 동작은 안전하게 구현할 수 없으므로, 코틀린은 컴파일 시점에 금지한다.

> [!info] 역사 메모
> JVM에는 이렇게 "멀리 떨어진 프레임으로 반환하는" 저수준 기능이 없다. 인라인되지 않는 람다에서 비지역 반환을 흉내 내려면, 특수한 예외를 던지고 바깥에서 잡는 방식을 써야 한다(실제로 일부 언어는 이렇게 구현한다). 코틀린은 이런 복잡성과 비용을 감수하는 대신 "인라인 람다에서만 허용한다"는 명확한 규칙을 선택했다. 그래서 비지역 반환은 인라인과 항상 함께 다뤄야 한다.

### 7.3 라벨 반환: 람다만 끝내고 싶을 때

람다만 끝내고 바깥 함수는 계속 실행하고 싶다면 **라벨을 붙인 반환 `return@label`** 을 사용한다. 이를 **지역 반환(local return)** 이라고 한다.

```kotlin
fun printNonNegatives(nums: List<Int>) {
    nums.forEach { n ->
        if (n < 0) return@forEach        // 이 람다 호출(=이번 반복)만 끝냄
        println(n)
    }
    println("완료")                       // 음수를 건너뛰고 여기까지 온다
}

fun main() {
    printNonNegatives(listOf(1, -2, 3))
    // => 1
    // => 3
    // => 완료
}
```

`return@forEach`는 `forEach`에 전달된 람다의 이번 호출, 즉 현재 반복만 끝낸다. `continue`처럼 다음 원소로 넘어가는 효과가 있다. 함수 전체는 끝나지 않으므로 마지막에 `"완료"`가 출력된다. 라벨 이름 `forEach`는 람다를 전달받은 함수의 이름으로, 컴파일러가 **암시적 라벨**로 붙여 준 것이다. 라벨을 직접 지정할 수도 있다.

```kotlin
fun printNonNegatives(nums: List<Int>) {
    nums.forEach loop@{ n ->
        if (n < 0) return@loop           // 명시적 라벨
        println(n)
    }
}
```

람다 안의 반환은 다음 두 종류로 정리할 수 있다.

| 형태 | 이름 | 무엇을 끝내나 | 어디서 가능한가 |
|---|---|---|---|
| `return` (라벨 없음) | 비지역 반환 | 감싸는 **함수** 전체 | 인라인 람다에서만 |
| `return@label` | 지역 반환 | 그 **람다 호출**만 | 어디서나 |

정리하면 다음과 같다. **람다 안에 라벨 없이 쓴 `return`은 람다가 아니라 바깥 함수를 끝낸다(비지역 반환). 람다만 끝내려면 반드시 `return@label`을 사용해야 한다. 그리고 라벨 없는 `return`은 인라인 람다에서만 허용된다.**

### 7.4 익명 함수의 return은 동작이 다르다

여기서 람다와 익명 함수의 차이가 드러난다. **익명 함수(`fun(...) {...}`)의 `return`은 익명 함수 자신만 끝낸다.** 즉 라벨이 없어도 지역 반환으로 동작한다. 이것이 람다와 익명 함수의 가장 큰 차이이다.

```kotlin
fun printNonNegatives(nums: List<Int>) {
    nums.forEach(fun(n: Int) {           // 람다가 아니라 익명 함수
        if (n < 0) return               // 이 익명 함수만 끝냄 (지역 반환)
        println(n)
    })
    println("완료")                       // 정상 도달
}
```

똑같이 라벨 없는 `return`이지만, 람다였다면 비지역 반환(바깥 함수 종료)이 되었을 코드가 익명 함수에서는 자기 자신만 끝내는 지역 반환이 된다. 따라서 콜백 한 번만 끝내고 싶은데 `return@label`을 쓰고 싶지 않다면, 익명 함수를 사용하는 것이 자연스럽다. 두 형태의 차이는 다음 표와 같다.

| | 람다 `{ ... }` | 익명 함수 `fun(...) { ... }` |
|---|---|---|
| 라벨 없는 `return` | 비지역(바깥 함수 종료), 인라인에서만 | 지역(자기 자신 종료), 항상 |
| `it` 사용 | 단일 파라미터면 가능(13장) | 불가(파라미터 이름 필수) |
| 반환 타입 | 추론 | 명시 가능 |

### 7.5 crossinline과 noinline: 비지역 반환 제어하기

인라인 함수를 만드는 쪽에서는 비지역 반환을 허용할지 결정할 수 있다. 인라인 함수가 전달받은 람다를 다른 스레드나 저장된 콜백 같은 *다른 실행 환경*으로 넘겨야 한다면, 그 람다에서 비지역 반환이 일어나면 위험하다. 그 시점에는 바깥 함수가 이미 끝났을 수도 있기 때문이다. 이런 경우에 `crossinline`을 사용해 비지역 반환을 막는다.

```kotlin
inline fun runLater(crossinline block: () -> Unit) {
    val r = Runnable { block() }          // 다른 문맥으로 넘김
    r.run()
    // block은 인라인되지만 crossinline이라 비지역 return 금지
}
```

`crossinline`이 붙은 람다에서 라벨 없는 `return`을 쓰면 컴파일 에러가 발생한다. 그 람다는 인라인되기는 하지만, 비지역 반환은 허용되지 않는다. 반대로 `noinline`을 붙이면 람다를 아예 인라인하지 않고 일반 함수 객체로 만든다. 따라서 이 경우에도 비지역 반환을 쓸 수 없다. 두 키워드는 15장에서 자세히 다룬다. 이 장에서는 "비지역 반환은 인라인과 연결되어 있고, 인라인 함수를 만드는 쪽에서 허용 여부를 정할 수 있다"는 점만 기억하면 된다.

### 7.6 중첩된 람다와 라벨의 모호성

인라인 람다가 중첩되어 있으면, 라벨 없는 `return`이 어디로 돌아가는지 특히 헷갈리기 쉽다. 규칙은 간단하다. **라벨 없는 `return`은 항상 가장 가까운 `fun`(이름 있는 함수)을 끝낸다.** 그 사이에 인라인 람다가 몇 겹 있든 상관없다.

```kotlin
fun hasPair(rows: List<List<Int>>, target: Int): Boolean {
    rows.forEach { row ->
        row.forEach { cell ->
            if (cell == target) return true   // forEach 두 겹을 관통해 hasPair를 끝냄
        }
    }
    return false
}

fun main() {
    println(hasPair(listOf(listOf(1, 2), listOf(3, 4)), 3))   // => true
}
```

`return true`는 안쪽 `forEach`나 바깥쪽 `forEach`가 아니라, 이름 있는 함수 `hasPair` 전체를 끝낸다. 두 겹의 인라인 람다를 모두 빠져나가는 비지역 반환이다. 그래서 `3`을 찾자마자 두 루프를 한꺼번에 벗어난다. 만약 안쪽 루프에서 현재 원소만 건너뛰고 싶다면 `return@forEach`를 쓰면 된다. 그런데 이때는 `forEach`가 두 개이므로 어느 쪽을 가리키는지 모호해진다. 이런 경우에는 **명시적 라벨**을 붙여 대상을 분명히 한다.

```kotlin
fun countMatches(rows: List<List<Int>>, target: Int): Int {
    var count = 0
    rows.forEach outer@{ row ->
        row.forEach inner@{ cell ->
            if (cell != target) return@inner   // 안쪽 forEach의 이번 원소만 건너뜀
            count++
        }
    }
    return count
}
```

암시적 라벨 `return@forEach`는 가장 가까운 `forEach`, 즉 안쪽 람다를 가리킨다. 하지만 람다가 중첩되어 헷갈린다면 `outer@`나 `inner@`처럼 라벨을 직접 붙여서 의도를 드러내는 편이 안전하다. 요약하면, 라벨 없는 `return`은 함수를 끝내고, `return@label`은 지정한 람다를 끝낸다. 이 두 가지만 정확히 구분하면 람다가 아무리 깊이 중첩되어 있어도 실행 흐름을 놓치지 않는다.

> [!warning] 흔한 오해
> "인라인 람다가 여러 겹이면 `return`할 때마다 한 겹씩 빠져나간다"고 생각하기 쉽지만 그렇지 않다. 라벨 없는 `return`에는 "한 겹만 빠져나간다"는 개념이 없고, 곧바로 가장 가까운 이름 있는 함수까지 빠져나간다. 한 겹만 빠져나가고 싶다면 해당 람다의 라벨을 명시해야 한다. 기본 동작은 함수 끝까지 빠져나가고, 한 겹만 빠져나가려면 명시해야 한다는 이 비대칭을 기억해 두자.

## 8. 캡처의 비용과 성능: 객체 할당, 그리고 인라인으로 없앨 수 있는 비용

### 8.1 아무것도 캡처하지 않는 람다는 싱글턴이 될 수 있다

캡처 비용을 이해하려면, 먼저 캡처가 *없을* 때 어떤 일이 일어나는지 살펴봐야 한다. **JVM 백엔드에서** 자유 변수를 하나도 캡처하지 않는 람다는 상태가 없으므로, 매번 새 객체를 만들 필요가 없다. 컴파일러는 이런 람다를 **하나의 싱글턴 인스턴스**로 만들어 재사용할 수 있다.

```kotlin
fun noCapture(): (Int) -> Int {
    return { x -> x + 1 }        // 자유 변수 없음 → 싱글턴 재사용 가능(JVM)
}

fun main() {
    val a = noCapture()
    val b = noCapture()
    println(a === b)             // JVM 백엔드에서 대개 true (같은 싱글턴)
}
```

`{ x -> x + 1 }`은 파라미터 `x` 외에는 캡처하는 것이 없다. 상태가 없으므로 여러 번 호출해도 같은 인스턴스를 반환할 수 있고, 그러면 할당이 전혀 발생하지 않는다. 반대로 캡처하는 값이 있으면 그 값을 담을 필드가 필요하므로, **호출할 때마다 새 객체**를 할당해야 한다. 따라서 "이 람다가 무언가를 캡처하는가"는 곧 성능과 관련된 질문이다. 캡처가 없으면 할당을 피할 수 있고, 캡처가 있으면 매번 할당이 발생한다.

> [!caution] 성능 주의
> `a === b`가 `true`가 되는 것은 **JVM 백엔드의 최적화** 결과이며, 언어가 보장하는 동작이 아니다. 따라서 두 람다가 같은 참조인지에 의존하는 코드를 작성하면 안 된다. 참조 동일성은 최적화 방식에 따라 달라질 수 있다([[10 - 불리언과 동등성과 동일성]] 참고). 여기서 중요한 것은 두 람다가 같다는 사실이 아니라, "캡처가 없으면 할당을 줄일 수 있다"는 원리이다.
>
> Kotlin 2.0부터 JVM 람다는 기본적으로 `invokedynamic`(LambdaMetafactory 기반)으로 컴파일된다. 이 방식도 익명 클래스를 생성하는 비용을 줄이기 위한 것이며, 캡처 여부가 할당에 영향을 준다는 점은 같다.

### 8.2 캡처하면 두 종류의 할당이 생길 수 있다

값을 캡처하는 람다는 힙 할당을 최대 두 번 일으킬 수 있다.

```text
캡처 있는 람다의 비용 (JVM 백엔드, 인라인 안 될 때)

  var acc = 0
  val fn = { acc += it }

  ① 캡처된 var acc → Ref.IntRef 객체 1개 할당
  ② 람다 자체 → Function 객체 1개 할당 (IntRef를 필드로 붙듦)

  두 개의 힙 객체가 생긴다.
```

읽기만 하는 `val`을 캡처한다면 ①은 없고, 값을 필드로 가진 람다 객체인 ②만 할당된다. 재대입되는 `var`를 캡처하면 ①의 `Ref`까지 추가로 할당된다(3.5절). 이 비용은 주로 **자주 실행되는 루프**에서 문제가 된다. 반복할 때마다 새 람다를 만들어 컬렉션 연산에 전달하면, 반복 횟수만큼 객체가 생성된다.

### 8.3 인라인하면 캡처 비용이 모두 사라진다

이런 비용을 근본적으로 없애는 방법이 인라인이다. 람다가 인라인 함수에 전달되어 인라인되면 람다 객체도, 캡처용 `Ref`도 만들 필요가 없다. 람다 본문이 호출 위치에 펼쳐지고, 캡처된 변수는 같은 스코프의 지역 변수가 되기 때문이다.

```kotlin
inline fun repeatAction(times: Int, action: (Int) -> Unit) {
    var i = 0
    while (i < times) { action(i); i++ }
}

fun main() {
    var sum = 0
    repeatAction(1_000_000) { sum += it }   // 인라인 → 람다 객체·Ref 할당 없음
    println(sum)                             // => 499999500000
}
```

`repeatAction`이 `inline` 함수이므로, `{ sum += it }`은 객체로 만들어지지 않고 `while` 루프 안에 그대로 펼쳐진다. `sum`도 `Ref`로 옮겨질 필요 없이 `main`의 지역 변수로 직접 접근된다. 백만 번 반복해도 캡처 때문에 생기는 힙 할당은 없다.

표준 라이브러리가 `forEach`와 `map`, `filter`, 스코프 함수처럼 람다를 받는 함수를 상당수 `inline`으로 만든 이유가 여기에 있다. 함수형 스타일로 작성하더라도 캡처 할당 비용을 치르지 않게 하려는 것이다.

여기서 7절의 비지역 반환과 이 절의 성능 문제가 하나로 연결된다. 비지역 반환이 인라인 람다에서만 가능한 이유(7.2절)와, 인라인하면 캡처 비용이 사라지는 이유(8.3절)는 같은 사실에서 나온다. **인라인 람다는 별도의 객체나 스택 프레임이 아니라, 호출 위치에 펼쳐진 코드**라는 사실이다. 그래서 바깥 함수를 끝낼 수 있고(비지역 반환), 캡처를 위한 객체도 필요 없다.

### 8.4 캡처 비용을 신경 써야 하는 경우

그렇다고 모든 캡처를 피할 필요는 없다. 대부분의 코드에서 람다 하나를 할당하는 비용은 무시해도 될 만큼 작다. 실제로 신경 써야 하는 경우는 다음 세 가지 정도이다.

1. 초당 수백만 번 실행되는 루프에서 매번 값을 캡처하는 람다를 새로 만드는 경우
2. 저장되는 콜백이나 다른 스레드로 넘기는 작업처럼 인라인되지 않는 곳에 람다를 전달하면서, 큰 객체를 캡처하는 경우(6절의 메모리 누수와도 관련된다)
3. [[40 - 시퀀스와 지연 평가]]처럼 원소마다 람다를 호출하는 파이프라인

이런 경우가 아니라면, 미세한 할당을 줄이는 것보다 캡처를 사용해 코드를 명확하게 작성하는 편이 훨씬 가치 있다. 성능은 추측이 아니라 측정해서 판단해야 한다.
