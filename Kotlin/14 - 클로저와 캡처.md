**이 장이 답하는 질문:**

- 코틀린 람다는 변수의 *값*을 붙잡는가, 변수 그 자체를 붙잡는가?
- Java는 `effectively final`인 지역 변수만 캡처하는데, 코틀린은 왜 `var`도 캡처하고 심지어 수정할 수 있는가?
- 캡처한 `var`는 JVM 백엔드에서 도대체 무엇으로 컴파일되기에 람다 안에서의 수정이 바깥에 보이는가?
- `for` 루프 안에서 만든 람다 열 개는 같은 반복 변수를 공유하는가, 아니면 각자 다른 값을 기억하는가?
- 람다 안에 쓴 `return`은 람다만 끝내는가, 바깥 함수까지 끝내는가? (M41)
- 왜 비지역 반환(non-local return)은 인라인 람다에서만 허용되는가?
- `return@label`은 정확히 어디로 돌아가며, 익명 함수의 `return`과 무엇이 다른가?
- 클로저가 붙잡은 객체는 언제까지 살아 있으며, 어떻게 메모리 누수가 되는가?

---

[[13 - 함수 타입과 람다와 함수 참조]]에서 우리는 함수를 값처럼 다루는 법을 배웠다. `(Int) -> Int`라는 타입, `{ x -> x + 1 }`라는 리터럴, `::foo`라는 참조 — 이 모든 것은 "코드 조각을 변수에 담아 나중에 실행한다"는 발상을 언어에 새겨 넣은 것이었다. 그런데 그 코드 조각이 자기가 태어난 자리의 지역 변수를 *기억해서* 나중까지 참조한다면, 그것은 더 이상 순수한 함수가 아니다. 함수는 자신을 감싸던 환경의 일부를 등에 짊어지고 떠난다. 이 "함수 + 자신이 붙잡은 환경"의 조합을 클로저(closure)라 부른다. 이 장은 그 짊어짐의 기계학을 해부한다.

이 장이 다루는 것과 다루지 않는 것의 경계를 먼저 못 박자. **다루는 것**: 클로저가 정확히 무엇을 붙잡는지(값이 아니라 변수), 붙잡힌 `var`가 기계 수준에서 어떻게 표현되는지, 루프 변수 캡처의 함정, 캡처가 만드는 객체 할당 비용, 그리고 캡처된 코드 안에서의 `return` 의미론(비지역 반환과 라벨 반환, M41). **다루지 않는 것**: 람다 문법 자체와 함수 참조는 앞 장 [[13 - 함수 타입과 람다와 함수 참조]]이 소유한다. `inline`/`reified`가 비지역 반환을 어떻게 가능하게 만드는지의 전체 기계학은 [[15 - 인라인 함수와 reified]]가 정본이다(이 장은 M41을 소유하므로 비지역 반환의 *의미*를 정면에서 다루되, 인라이닝의 세부는 15장으로 위임한다). 수신 객체 지정 람다(`T.() -> R`)가 만드는 스코프는 [[16 - 스코프 함수와 수신 객체 관용구]]가, 이너 클래스의 외부 참조 캡처는 [[31 - 중첩 클래스와 이너 클래스와 익명 객체]]가, 캡처된 상태의 스레드 가시성은 [[43 - 동시성과 메모리 모델]]이 소유한다.

이 장의 논증 궤적은 이렇다. 먼저 렉시컬 스코프와 자유 변수라는 개념에서 출발해 "클로저는 변수를 붙잡는다"는 핵심 명제를 세운다. 그 다음 Java와 정면 대조해 코틀린의 `var` 캡처가 왜 특별한지 보이고, 그 특별함을 지탱하는 기계 장치(JVM 백엔드의 `Ref` 래핑)를 파헤친다. 이어서 루프 변수 캡처의 미묘함, 캡처의 수명과 메모리 누수를 짚고, 마지막으로 이 장이 소유한 오개념 M41 — "람다의 `return`은 람다만 벗어난다"는 착각 — 을 비지역 반환과 라벨 반환의 정확한 규칙으로 교정한다. 캡처는 편리하지만 공짜가 아니다. 그 대가를 아는 것이 이 장의 목적이다.

## 1. 클로저란 무엇인가 — 렉시컬 스코프와 자유 변수

### 1.1 자유 변수: 함수 밖에서 온 이름

어떤 함수 본문에 등장하는 이름들은 두 부류로 나뉜다. 하나는 그 함수가 스스로 도입한 이름 — 파라미터와 지역 변수 — 이고, 이를 **바운드 변수(bound variable, 속박 변수)** 라 한다. 다른 하나는 함수 본문에 등장하지만 함수가 도입하지 않은 이름, 즉 바깥 스코프에서 정의된 이름을 참조하는 것으로, 이를 **자유 변수(free variable)** 라 한다.

```kotlin
fun makeAdder(base: Int): (Int) -> Int {
    return { x -> x + base }   // x는 바운드(람다 파라미터), base는 자유 변수
}

val add10 = makeAdder(10)
val add100 = makeAdder(100)
println(add10(5))    // => 15
println(add100(5))   // => 105
```

`{ x -> x + base }` 안에서 `x`는 람다 스스로 도입한 파라미터라 바운드 변수다. 반면 `base`는 람다가 아니라 바깥 함수 `makeAdder`의 파라미터다. 람다 입장에서 `base`는 자유 변수다. 그런데 `makeAdder`는 이미 반환되어 스택 프레임이 사라졌는데도 `add10`은 `base=10`을, `add100`은 `base=100`을 각자 정확히 기억한다. 이 "함수가 자신의 자유 변수를 붙잡아 두는" 현상이 바로 클로저다.

클로저라는 이름은 수학적 은유다. 함수 본문은 자유 변수 때문에 그 자체로는 "열려 있는(open)" 식이다 — 자유 변수의 값이 정해지지 않으면 실행할 수 없다. 함수가 자신을 둘러싼 환경을 붙잡아 그 자유 변수들에 값을 채워 넣으면, 식은 비로소 "닫힌다(closed)". 그래서 클로저, 즉 폐포(閉包)다.

> **역사 메모**: 클로저는 람다 계산에 뿌리를 두고 1970년대 Scheme 계열 언어에서 정립된 개념이다(용어 자체는 1964년 Peter Landin이 명명). 핵심은 **렉시컬 스코프(lexical scope, 어휘적 스코프)** — 이름이 어느 변수를 가리키는지가 코드가 *쓰여진 위치*로 정적으로 결정된다는 원칙이다. 반대는 다이나믹 스코프(호출 시점의 환경으로 결정)인데, 현대 언어는 거의 전부 렉시컬 스코프를 택한다. 코틀린도 예외 없이 렉시컬이다. `base`가 무엇을 가리키는지는 람다가 *어디서 정의됐는가*로 정해지지, 어디서 호출됐는가로 정해지지 않는다.

### 1.2 렉시컬 스코프: 정의 위치가 이름을 결정한다

렉시컬 스코프의 결과를 눈으로 확인해 보자. 아래에서 `shift`라는 이름이 두 번 등장하지만, 람다가 붙잡는 것은 자신이 *쓰여진 자리*에서 보이던 `shift`다.

```kotlin
fun outer(): (Int) -> Int {
    val shift = 100
    val lambda = { n: Int -> n + shift }   // 여기서 보이는 shift는 100
    return lambda
}

fun main() {
    val shift = -999                       // 이름은 같지만 다른 변수
    val f = outer()
    println(f(1))                          // => 101  (main의 shift가 아님!)
}
```

`f(1)`을 `main` 안에서 호출했지만 결과는 `-998`이 아니라 `101`이다. 람다는 자신이 태어난 `outer`의 렉시컬 환경을 붙잡았고, 그 환경의 `shift`는 `100`이다. 호출 시점에 `main`에 `shift=-999`가 있다는 사실은 아무 영향도 주지 못한다. 이것이 렉시컬 스코프의 정수다: **캡처는 정의 시점의 이름 결정을 따른다.**

### 1.3 클로저는 코틀린의 어떤 구성요소가 만드는가

클로저를 만드는 것은 람다만이 아니다. 코틀린에서 자유 변수를 붙잡을 수 있는 구성요소는 여러 가지다.

```kotlin
fun demo() {
    val captured = 42

    // (1) 람다
    val l = { captured + 1 }

    // (2) 익명 함수
    val anon = fun(): Int { return captured + 2 }

    // (3) 지역 함수 (12장)
    fun local() = captured + 3

    // (4) 익명 객체 (31장)
    val obj = object : Runnable {
        override fun run() { println(captured + 4) }
    }

    println(l())         // => 43
    println(anon())      // => 44
    println(local())     // => 45
    obj.run()            // => 46
}
```

람다, 익명 함수, 지역 함수([[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]]), 익명 객체([[31 - 중첩 클래스와 이너 클래스와 익명 객체]]) — 이들은 모두 클로저를 만든다. 각자 문법과 `return` 의미론(뒤의 7절)은 다르지만, "자유 변수를 붙잡는다"는 캡처의 본질은 공통이다. 이 장의 규칙은 이 네 가지 모두에 적용된다.

> **명세 정밀**: 코틀린 언어 명세는 "closure"를 람다·익명 함수·지역 함수·객체 표현식이 자신을 감싸는 스코프의 값과 변수를 포획하는 것으로 정의한다. 명세의 표현은 "captures the values and variables" — 즉 코틀린은 의도적으로 *값*뿐 아니라 *변수*를 붙잡는다고 못 박는다. 이 "변수까지 붙잡는다"가 다음 절의 주제이자, Java와 갈라지는 지점이다.

## 2. 값 캡처가 아니라 변수 캡처 — Java와의 정면 대조

### 2.1 Java의 규칙: effectively final만, 값으로

캡처의 의미를 이해하는 가장 빠른 길은 Java와 나란히 놓는 것이다. Java의 람다(와 익명 클래스)는 지역 변수를 캡처할 때 엄격한 제약을 건다: **그 변수가 `final`이거나 `effectively final`(사실상 최종 — 초기화 후 재대입되지 않는)이어야 한다.**

```java
// Java
int counter = 0;
Runnable r = () -> {
    // counter++;              // 컴파일 에러: Variable used in lambda should be final or effectively final
    System.out.println(counter);
};
counter = 5;                    // 이 재대입도 위 람다를 컴파일 에러로 만든다
```

Java가 이렇게 막는 이유는 그 캡처 모델이 **값 복사**이기 때문이다. Java 람다는 지역 변수 `counter`의 *현재 값*을 자신의 숨은 필드로 복사해 넣는다. 만약 바깥에서 `counter`를 바꿔도 람다 안의 복사본은 그대로다 — 그러면 "바깥과 안이 다른 값을 본다"는 혼란이 생긴다. Java는 이 혼란을 원천 차단하려고 아예 "캡처되는 변수는 변하지 않아야 한다"고 강제한다. 즉 Java에서 캡처는 사실상 **불변 스냅샷의 값 복사**다.

### 2.2 코틀린의 규칙: var도, 변수 자체를

코틀린은 정반대의 선택을 했다. 코틀린 람다는 `val`이든 `var`이든 캡처할 수 있고, 캡처한 `var`를 람다 안에서 **수정할 수 있으며, 그 수정은 바깥에도 보인다**.

```kotlin
fun main() {
    var counter = 0
    val increment = { counter++ }          // var 캡처 — Java라면 불가능
    val report = { println(counter) }

    increment()
    increment()
    increment()
    report()                               // => 3   (람다 안 수정이 바깥에 반영됨)

    counter = 100                           // 바깥에서 수정
    report()                               // => 100 (람다가 바깥 수정도 봄)
}
```

`increment` 람다가 `counter`를 세 번 증가시켰고, 그 결과가 바깥과 다른 람다(`report`)에도 온전히 보인다. 게다가 바깥에서 `counter = 100`으로 바꾸자 `report`도 그 값을 본다. 이것은 Java의 값 복사로는 절대 나올 수 없는 동작이다. 코틀린의 클로저는 값을 복사하는 것이 아니라 **변수 그 자체(변수라는 저장 위치, storage cell)를 공유**한다. 바깥 스코프와 람다는 같은 셀을 가리키므로, 누가 수정하든 서로에게 보인다.

이 차이를 한 줄로 요약하면 이렇다.

| | Java | Kotlin |
|---|---|---|
| 캡처 대상 제약 | `final`/effectively final만 | `val`·`var` 모두 |
| 캡처 방식 | 값 복사(스냅샷) | 변수(저장 셀) 공유 |
| 람다 안에서 재대입 | 불가(컴파일 에러) | `var`면 가능 |
| 바깥 수정의 가시성 | 캡처 후 수정 자체가 금지 | 서로 보임 |

> **흔한 오해**: "코틀린 람다는 `var`를 캡처할 때 값을 복사한다"는 생각은 틀렸다. 만약 값 복사라면 `increment()`를 세 번 불러도 바깥 `counter`는 그대로여야 하지만, 위 예에서 `report()`는 `3`을 찍는다. 코틀린은 변수를 공유한다. 다만 그 "공유"를 JVM 위에서 어떻게 구현하는지는 다음 절의 흥미로운 이야기다 — JVM 지역 변수 슬롯은 원래 공유가 불가능하기 때문이다.

### 2.3 왜 코틀린은 다른 선택을 했나

Java의 "불변 스냅샷"은 안전하지만 표현력을 깎는다. 반복적으로 상태를 갱신하는 카운터, 누산기, 콜백에서 결과를 모으는 패턴 등은 캡처된 `var` 없이는 어색해진다(Java에서는 그래서 길이 1짜리 배열 `int[] c = {0}`이나 `AtomicInteger` 같은 우회로를 쓴다). 코틀린은 함수형 스타일을 실용적으로 쓰게 하려고, 그 우회로를 언어가 대신 만들어 주기로 했다. 바로 다음 절에서 볼 `Ref` 래핑이 그 언어 차원의 우회로다 — 사용자가 손으로 `IntArray(1)`을 만들 필요 없이, 컴파일러가 자동으로 해 준다.

물론 대가는 있다. 변수 공유는 동시성 위험을 낳는다(여러 스레드가 같은 셀을 만지면 [[43 - 동시성과 메모리 모델]]의 가시성·경쟁 문제가 그대로 온다). Java의 불변 스냅샷은 이 위험을 구조적으로 줄였지만, 코틀린은 표현력을 택하고 위험 관리는 개발자에게 맡긴 셈이다. 이 트레이드오프를 아는 것이 캡처를 안전하게 쓰는 출발점이다.

## 3. 캡처된 var의 기계 표현 — JVM 백엔드의 Ref 래핑

### 3.1 문제: JVM 지역 변수는 공유할 수 없다

2절의 "변수를 공유한다"는 서술은 개념 수준에서는 맞지만, JVM 위에서 곧이곧대로 구현할 수 없다. JVM에서 지역 변수는 스택 프레임의 로컬 변수 슬롯(local variable slot)에 산다. 스택 프레임은 메서드가 반환하면 사라진다. 그런데 람다(JVM 백엔드에서는 대개 별도의 객체로 구현된다)는 그 메서드가 반환된 뒤에도 살아남아야 한다. 사라질 스택 슬롯을, 살아남을 객체가 어떻게 공유한단 말인가?

게다가 로컬 슬롯의 값은 객체 필드가 아니라 원시적 저장 위치라, 두 개의 독립된 객체(바깥 프레임과 람다 객체)가 "같은 슬롯"을 가리키게 만들 방법이 JVM 바이트코드에는 없다. 한쪽이 슬롯 값을 바꿔도 다른 쪽은 모른다.

### 3.2 해법: 힙 위의 참조 셀로 승격

**JVM 백엔드에서** 코틀린 컴파일러는 이 문제를 이렇게 푼다: **캡처되면서 수정되는 `var`를, 지역 슬롯이 아니라 힙에 놓인 작은 래퍼 객체 안의 필드로 승격시킨다.** 표준 라이브러리 내부의 `kotlin.jvm.internal.Ref` 계열 클래스들이 그 래퍼다.

```text
개념도: var counter = 0 이 람다에 의해 캡처될 때 (JVM 백엔드)

  [스택 프레임: main]                    [힙]
  +---------------------+       +-------------------------+
  | ref  ───────────────┼──────>| Ref.IntRef              |
  +---------------------+       |   element: int = 3      |<──┐
                                +-------------------------+   │
  [힙: 람다 객체 increment]                                   │
  +---------------------+                                     │
  | $counter ───────────┼─────────────────────────────────────┘
  +---------------------+
       두 쪽 모두 같은 IntRef를 가리킨다 → element 수정이 서로 보인다
```

원본 코드가 개념적으로 이렇게 변형된다고 보면 된다(의사 코드).

```kotlin
// 사용자가 쓴 코드
fun main() {
    var counter = 0
    val increment = { counter++ }
    increment(); increment(); increment()
    println(counter)   // => 3
}

// JVM 백엔드가 만드는 것에 가까운 의사 코드
fun main() {
    val counter = IntRef()          // kotlin.jvm.internal.Ref.IntRef
    counter.element = 0
    val increment = Increment(counter)   // Ref를 필드로 붙잡는 람다 객체
    increment.invoke(); increment.invoke(); increment.invoke()
    println(counter.element)        // => 3
}
class Increment(val c: IntRef) : Function0<Unit> {
    override fun invoke() { c.element = c.element + 1 }
}
```

이제 `counter`는 스택 슬롯이 아니라 힙 객체의 `element` 필드다. `main`의 프레임과 람다 객체는 *같은 `IntRef` 인스턴스*를 가리키므로, 어느 쪽이 `element`를 바꿔도 다른 쪽이 본다. 스택이 사라져도 힙 객체는 참조가 살아 있는 한 남는다. 2절에서 본 "변수 공유"의 정체가 이것이다.

### 3.3 Ref의 종류와 val의 차이

`Ref`에는 여러 특화 버전이 있다. **JVM 백엔드에서** 대략 이렇게 나뉜다.

| 캡처된 var의 타입 | 래핑 클래스(개념) | 필드 |
|---|---|---|
| `Int` | `Ref.IntRef` | `int element` |
| `Long` | `Ref.LongRef` | `long element` |
| `Double` | `Ref.DoubleRef` | `double element` |
| `Boolean` | `Ref.BooleanRef` | `boolean element` |
| 참조 타입(`String`, 사용자 클래스 등) | `Ref.ObjectRef<T>` | `T element` |

여기서 결정적인 구별이 있다. **재대입되는 `var`만 `Ref`로 승격된다.** 캡처되더라도 초기화 후 어디서도 재대입되지 않는다면(즉 `val`이거나, 사실상 final인 `var`라면) 래핑이 필요 없다 — 값을 람다 객체의 필드로 그냥 복사해 넣어도 아무도 불평하지 않는다. 여기서 기준은 "람다가 수정하는가"가 아니라 "그 변수가 어디서든(람다 안이든 바깥 스코프든) 재대입되는가"임에 주의하라. 람다는 읽기만 하더라도 바깥에서 캡처 후 그 `var`를 다시 대입하면, 갱신된 값이 람다에 보여야 하므로 여전히 `Ref`로 승격된다. 왜냐하면 아무도 그 값을 바꾸지 않으니 "바깥과 안이 달라지는" 문제가 생기지 않기 때문이다.

```kotlin
fun example() {
    val base = 10                    // val — 수정 없음 → Ref 없이 값으로 캡처
    var acc = 0                       // var, 수정됨 → IntRef로 승격
    val fn = {
        acc += base                   // acc는 Ref.element, base는 그냥 int 필드
    }
    fn(); fn()
    println(acc)                      // => 20
}
```

즉 코틀린의 캡처는 실은 두 전략의 혼합이다. **수정 안 되는 것은 값 복사(Java와 동일), 수정되는 것만 참조 셀 공유.** 이 최적화 덕분에 대부분의 캡처(자유 변수는 보통 읽기만 한다)는 추가 래퍼 없이 값 복사로 끝나고, 정말로 공유가 필요한 `var`에만 `Ref` 비용을 지불한다.

> **명세 정밀**: `Ref` 래핑은 **JVM 백엔드의 구현 세부**다. 언어 명세가 요구하는 것은 "캡처된 `var`의 수정은 모든 클로저와 원래 스코프에 일관되게 보인다"는 *관찰 가능한 의미론*이지, "`IntRef`를 써라"가 아니다. Kotlin/Native·Kotlin/JS·Wasm 백엔드는 각자 다른 방식으로 같은 의미론을 달성한다(JS 백엔드는 클로저가 언어 차원에서 변수를 공유하므로 별도 래핑이 덜 필요할 수 있다). 따라서 "코틀린은 `var`를 `Ref`로 박싱한다"는 서술은 반드시 "JVM 백엔드에서"로 한정해야 정확하다. 디컴파일([[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]])로 확인할 수 있는 것도 JVM `.class`에 한한다.

### 3.4 Java 우회로와의 대조 — 코틀린이 자동화한 것

3절의 `Ref`가 무엇을 자동화한 것인지는 Java 개발자가 손으로 쓰던 우회로와 나란히 놓으면 선명하다. Java에서 람다 안에서 값을 갱신하려면 `effectively final` 제약을 우회해야 했고, 관용적으로 길이 1짜리 배열이나 별도 홀더 객체를 썼다.

```java
// Java: 캡처된 값을 갱신하려는 고전적 우회로
int[] counter = { 0 };            // 배열 참조는 effectively final, 내용은 가변
Runnable r = () -> counter[0]++;  // 배열 원소는 바꿀 수 있다
r.run(); r.run();
System.out.println(counter[0]);   // => 2
```

`counter` 배열 *참조*는 재대입되지 않으니 `effectively final`이고, 람다는 그 참조를 값으로 복사해 캡처한다. 하지만 배열의 *내용*은 얼마든지 바꿀 수 있으므로 `counter[0]++`이 통한다. 코틀린의 `Ref.IntRef`는 정확히 이 "길이 1짜리 가변 홀더"를 컴파일러가 대신 만들어 주는 것이다. Java 개발자가 손으로 만들던 `int[]{0}`을, 코틀린은 `var counter = 0`이라는 자연스러운 문법 뒤에 숨긴 셈이다. 이 자동화 덕에 코틀린 코드는 우회로 없이 직관적으로 읽히지만, 그 밑에서 벌어지는 일(힙 홀더 공유)은 본질적으로 같다. 이 대비를 알면 "왜 코틀린 `var` 캡처가 되는가"가 마법이 아니라 잘 알려진 관용구의 언어 차원 내장임이 분명해진다.

### 3.5 성능 비용으로서의 승격

`Ref` 승격에는 대가가 따른다. 원래 스택에 살면 됐을 `Int`가 이제 힙에 할당된 `IntRef` 객체가 된다. 즉 **캡처되고 수정되는 원시 `var` 하나마다 힙 할당 한 번**이 발생하고, 값을 읽고 쓸 때마다 필드 접근(간접 참조)을 거친다. 원시 값 하나 다루자고 객체를 하나 만드는 셈이니, 뜨거운 루프에서 이런 캡처가 반복되면 GC 압력이 된다. 이 비용은 8절에서 인라인이 어떻게 제거하는지와 함께 다시 다룬다.

## 4. 무엇이 캡처되는가 — this, 파라미터, 수신자

### 4.1 캡처의 대상은 지역 변수만이 아니다

클로저가 붙잡는 자유 변수는 지역 `val`/`var`뿐이 아니다. 다음도 캡처 대상이다.

- **함수 파라미터** (사실상 지역 변수와 동일)
- **바깥 함수의 지역 함수/람다**
- **바깥 클래스의 `this`** — 프로퍼티/메서드에 접근하면 `this`를 붙잡는다
- **수신 객체 지정 람다의 수신자** (`this@label`)

특히 클래스 안에서 프로퍼티를 참조하는 람다는 그 프로퍼티 값이 아니라 **인스턴스(`this`) 참조**를 붙잡는다는 점이 중요하다.

```kotlin
class Counter {
    var count = 0
    fun makeIncrementer(): () -> Unit {
        return { count++ }        // this.count++ — Counter 인스턴스를 캡처
    }
}

fun main() {
    val c = Counter()
    val inc = c.makeIncrementer()
    inc(); inc()
    println(c.count)              // => 2
}
```

`{ count++ }`는 겉보기엔 지역 변수를 붙잡는 것 같지만, `count`는 `Counter`의 프로퍼티라 실제로는 `this.count++`이다. 따라서 이 람다는 `Counter` 인스턴스 `c`를 통째로 캡처한다. `inc`가 살아 있는 한 `c`도 살아 있다 — 이것이 6절 메모리 누수의 씨앗이다.

### 4.2 값 캡처 vs 참조 캡처를 오해하지 말라

여기서 흔한 혼동 하나를 정리하자. "값을 캡처하느냐 참조를 캡처하느냐"라는 질문은 사실 두 개의 서로 다른 질문이 섞인 것이다.

1. **변수(저장 셀)를 붙잡느냐, 값을 붙잡느냐** — 이것이 2·3절의 주제. `var`는 셀 공유, `val`은 값 복사(JVM 백엔드).
2. **붙잡은 값이 참조 타입일 때, 그 객체는 여전히 가변일 수 있다** — 이것은 [[11 - 변수와 초기화 - val과 const와 lateinit]]의 M3(“val은 재대입 불가일 뿐, 대상 객체는 가변”)와 이어진다.

이 둘은 독립이다. `val`로 캡처했어도, 그 `val`이 가리키는 객체가 가변이면 람다는 그 객체의 변화를 본다.

```kotlin
fun main() {
    val list = mutableListOf(1, 2, 3)   // val — 재대입 불가
    val printer = { println(list) }      // list(참조 값)를 복사 캡처

    list.add(4)                          // 객체 자체를 변경 (재대입 아님)
    printer()                            // => [1, 2, 3, 4]  — 변화가 보인다!
}
```

`list`는 `val`이라 3절 기준 값 복사로 캡처된다. 하지만 복사되는 값은 "리스트 객체를 가리키는 참조"다. 원본과 캡처본이 *같은 리스트 객체*를 가리키므로, 그 객체에 원소를 추가하면 양쪽 다 본다. 여기서 "값 복사"라는 말에 속으면 안 된다 — 복사된 것은 참조값이지 리스트의 깊은 사본이 아니다. `val` 캡처가 불변을 보장한다는 착각(M3의 사촌)은 이렇게 깨진다.

### 4.3 수신 객체 지정 람다에서의 캡처

수신 객체 지정 람다(`T.() -> R`, 자세히는 [[16 - 스코프 함수와 수신 객체 관용구]])에서는 수신자 `this`도 캡처의 일부가 된다. 여러 수신자가 중첩되면 `this@label`로 어느 것을 가리키는지 명시한다.

```kotlin
class Html {
    val children = mutableListOf<String>()
    fun body(block: Html.() -> Unit) { this.block() }
    fun p(text: String) { children.add("<p>$text</p>") }
}

fun main() {
    val outer = "제목"                    // 지역 변수도 함께 캡처
    val page = Html()
    page.body {
        p(outer)                          // this(=page)와 outer를 함께 캡처
    }
    println(page.children)                // => [<p>제목</p>]
}
```

`{ p(outer) }` 블록은 수신자 `this`(=`page`)를 통해 `p`를 부르면서, 동시에 지역 변수 `outer`를 캡처한다. 클로저는 이렇게 렉시컬 스코프 상의 여러 종류의 이름 — 수신자, 지역 변수, 바깥 `this` — 을 한꺼번에 붙잡는다.

### 4.4 캡처와 SAM 변환 — Java 인터페이스로 넘어갈 때

캡처는 코틀린 함수 타입 안에만 갇혀 있지 않다. 람다를 Java의 단일 추상 메서드 인터페이스(SAM, [[13 - 함수 타입과 람다와 함수 참조]])로 변환해 넘길 때도 캡처는 그대로 따라간다. 이때 만들어지는 SAM 구현체 역시 캡처된 값을 필드로 붙든 객체다.

```kotlin
fun scheduleAll(tasks: List<String>, run: (Runnable) -> Unit) {
    var done = 0
    for (task in tasks) {
        run(Runnable {                    // Runnable은 Java SAM 인터페이스
            done++                         // 캡처된 var done 공유
            println("$task 완료 (누적 $done)")
        })
    }
}
```

`Runnable { ... }`는 SAM 변환으로 `Runnable` 구현 객체가 되고, 그 객체가 `done`(수정되는 `var`)을 캡처한다 — **JVM 백엔드에서** 이는 3절과 똑같이 `Ref.IntRef` 공유로 구현된다. 중요한 함정은 이 SAM 객체가 흔히 *다른 실행 문맥*(스레드 풀, 이벤트 루프)으로 넘어간다는 점이다. 그러면 캡처된 `done`을 여러 스레드가 동시에 만질 수 있어, 셀 공유가 곧 경쟁 조건이 된다([[43 - 동시성과 메모리 모델]]). 캡처 자체는 언어가 안전하게 해 주지만, 캡처된 셀에 대한 동시 접근의 안전은 언어가 보장하지 않는다 — 이 경계는 늘 기억해야 한다. Java 상호운용 전반의 SAM 규칙은 [[45 - Java 상호운용]]이 소유한다.

## 5. 루프 변수 캡처 — 각 반복은 새 변수인가

### 5.1 고전적 함정과 코틀린의 답

여러 언어에서 초심자를 무너뜨리는 고전적 함정이 있다: 루프 안에서 람다를 만들어 리스트에 담은 뒤, 루프가 끝나고 모두 호출하면 전부 마지막 값만 찍는 문제다. 이는 루프 변수가 반복 사이에 *공유*될 때 생긴다(대표적으로 JavaScript의 `var` 루프). 코틀린의 `for`는 이 함정을 피한다.

```kotlin
fun main() {
    val fns = mutableListOf<() -> Int>()
    for (i in 1..3) {
        fns.add { i }                    // 각 반복의 i를 캡처
    }
    println(fns.map { it() })            // => [1, 2, 3]   (3, 3, 3 아님!)
}
```

결과는 `[1, 2, 3]`이다. 코틀린의 `for` 루프 변수(`i`)는 **각 반복마다 새로 바인딩되는 불변 변수**처럼 동작한다. 반복 1의 `i`, 반복 2의 `i`, 반복 3의 `i`는 서로 다른 셀이므로, 각 람다는 자기 반복의 값을 정확히 붙잡는다. 게다가 `for`의 루프 변수는 재대입할 수 없는 사실상 `val`이라, 애초에 하나의 셀을 공유하며 갱신되지도 않는다.

> **흔한 오해**: "JavaScript처럼 코틀린 루프도 마지막 값만 캡처될 것"이라는 걱정은 코틀린 `for`에는 해당되지 않는다. JavaScript의 함정은 `var`로 선언한 함수 스코프 변수가 반복 간 공유되기 때문이었고(그래서 `let`이 도입됐다), 코틀린의 `for` 변수는 처음부터 반복별 불변 바인딩이다. 다만 아래 5.2처럼 *루프 바깥의 `var`* 를 캡처하면 이야기가 완전히 달라진다.

### 5.2 진짜 함정: 루프 바깥의 var를 캡처할 때

문제가 되는 것은 루프 변수가 아니라, 루프 *바깥*에서 선언하고 루프 안에서 갱신하는 `var`를 캡처할 때다. 이때는 3절의 `Ref` 공유가 정확히 작동해 — 모든 람다가 **같은 셀**을 붙잡는다.

```kotlin
fun main() {
    val fns = mutableListOf<() -> Int>()
    var j = 0                            // 루프 바깥 var — 단일 셀
    while (j < 3) {
        fns.add { j }                    // 모두 같은 IntRef 공유
        j++
    }
    println(fns.map { it() })            // => [3, 3, 3]   (모두 최종값)
}
```

여기서 `j`는 루프 바깥에서 선언된 하나의 `var`다. 세 람다 모두 같은 `IntRef`를 붙잡으므로, 루프가 끝나 `j`가 `3`이 된 뒤에 호출하면 전부 `3`을 본다. 이것은 버그가 아니라 캡처 규칙의 정확한 결과다 — 변수 공유이기 때문이다. 반복별 값을 원한다면 각 반복에서 **새 지역 변수**로 값을 고정해야 한다.

```kotlin
fun main() {
    val fns = mutableListOf<() -> Int>()
    var j = 0
    while (j < 3) {
        val snapshot = j                 // 반복마다 새 val — 값 고정
        fns.add { snapshot }
        j++
    }
    println(fns.map { it() })            // => [0, 1, 2]
}
```

`val snapshot = j`는 반복마다 새로 도입되는 불변 변수라, 각 람다는 자기 반복 시점의 값을 붙잡는다. 이 "새 지역 변수로 값을 고정하는" 관용구가 루프 캡처의 정석이다. 요약하면: **캡처되는 것이 반복별 새 바인딩(`for` 변수, 반복 안의 `val`)이면 반복별 값을, 반복을 가로지르는 하나의 셀(`while` 바깥의 `var`)이면 최종 공유값을 본다.**

### 5.3 왜 for와 while이 다르게 느껴지는가

`for`와 `while`의 이 차이는 우연이 아니라 각 반복이 새 스코프를 여느냐의 문제다. `for (i in range)`에서 `i`는 언어가 반복마다 새로 도입하는 이름이다. 반면 `while`의 조건에 쓰인 `var j`는 루프 바깥에 한 번 선언된 변수라, 루프는 그 하나의 셀을 계속 갱신할 뿐이다. 그래서 `for`는 대개 안전하고, `while`에서 바깥 `var`를 캡처하면 조심해야 한다. 이 규칙만 알면 루프 캡처는 더 이상 미스터리가 아니다.

## 6. 캡처의 수명과 메모리 — 클로저가 붙잡는 것은 죽지 않는다

### 6.1 캡처는 참조를 살려 둔다

클로저가 어떤 객체를 캡처하면, 그 클로저가 살아 있는 한 캡처된 객체도 GC 대상이 되지 못한다. 이것은 클로저의 본질적 성질이다 — 나중에 실행할 코드가 그 객체를 필요로 할지 모르니, 런타임은 함부로 회수할 수 없다. 문제는 이 "살려 둠"이 의도치 않게 크고 오래 사는 객체를 붙잡아 둘 때 생긴다.

```kotlin
class HeavyResource {
    val bigBuffer = ByteArray(100_000_000)   // 큰 메모리
    fun makeCallback(): () -> Int {
        // bigBuffer를 직접 안 쓰더라도 this를 캡처하면 HeavyResource 전체가 산다
        return { bigBuffer.size }
    }
}
```

`makeCallback`이 반환한 람다는 `bigBuffer.size` 한 줄만 쓰지만, `bigBuffer`는 `this.bigBuffer`이므로 람다는 `HeavyResource` 인스턴스 전체(1억 바이트 버퍼 포함)를 캡처한다. 이 콜백을 오래 사는 리스트나 전역 레지스트리에 등록해 두면, 정작 `HeavyResource`를 다 썼는데도 콜백 때문에 버퍼가 회수되지 않는다. 이것이 클로저에 의한 메모리 누수의 전형이다.

### 6.2 필요한 값만 지역 변수로 뽑아 캡처하라

해법은 인스턴스 전체가 아니라 정말 필요한 값만 지역 변수로 복사한 뒤 그것을 캡처하는 것이다.

```kotlin
class HeavyResource {
    val bigBuffer = ByteArray(100_000_000)
    fun makeCallback(): () -> Int {
        val size = bigBuffer.size            // 필요한 값만 지역으로 뽑음
        return { size }                       // this가 아니라 size(Int)만 캡처
    }
}
```

이제 람다는 `Int` 값 하나만 캡처하고 `HeavyResource` 인스턴스는 붙잡지 않는다. `makeCallback`이 반환된 뒤 다른 참조가 없으면 `HeavyResource`(버퍼 포함)는 정상적으로 회수될 수 있다. 이너 클래스([[31 - 중첩 클래스와 이너 클래스와 익명 객체]])가 외부 인스턴스를 캡처해 누수를 만드는 문제도 같은 뿌리이며, 같은 처방("바깥 인스턴스 말고 필요한 값만")을 쓴다.

> **성능 주의**: 안드로이드/데스크톱 UI, 장수하는 이벤트 버스, 캐시, 정적 컬렉션에 콜백을 등록할 때가 특히 위험하다. 짧게 사는 컴포넌트가 만든 람다를 오래 사는 곳에 넣으면, 그 람다가 캡처한 컴포넌트(와 그것이 붙든 뷰 트리 전체)가 함께 산다. 등록했으면 반드시 해제하거나, 캡처 범위를 값 몇 개로 최소화하라. "이 람다가 정확히 무엇을 캡처하는가"는 항상 물어야 할 질문이다.

### 6.3 인라인이면 애초에 캡처 객체가 없다

한 가지 안심되는 사실: 람다가 **인라인 함수**([[15 - 인라인 함수와 reified]])에 전달되어 인라이닝되면, 애초에 람다 객체 자체가 만들어지지 않는다. 본문이 호출부에 그대로 펼쳐지므로 "캡처를 붙든 객체"가 존재하지 않고, 따라서 그 객체에 의한 누수도 없다. 표준 라이브러리의 컬렉션 연산 대부분(`forEach`, `map`, `filter` 등, [[39 - 컬렉션 연산과 함수형 파이프라인]])이 인라인 함수라, 여기에 넘긴 람다는 힙에 남지 않는다. 누수는 주로 **인라인되지 않고 어딘가에 저장되는** 람다에서 생긴다.

## 7. 비지역 반환과 라벨 반환 — return은 어디로 가는가 (M41)

### 7.1 오개념 M41: "람다의 return은 람다만 벗어난다"

이 장이 소유한 오개념을 정면으로 세우자. 많은 개발자가 "람다 안에 `return`을 쓰면 그 람다만 끝나고 바깥 함수는 계속된다"고 믿는다(M41). 이는 **틀렸다.** 코틀린에서 람다 안의 벌거벗은 `return`은 — 그것이 문법적으로 허용되는 경우 — 람다가 아니라 **자신을 감싸는 함수 전체를 반환시킨다.** 이것을 **비지역 반환(non-local return)** 이라 한다.

```kotlin
fun findFirstEven(nums: List<Int>): Int? {
    nums.forEach { n ->
        if (n % 2 == 0) return n         // 이 return은 findFirstEven을 끝낸다!
    }
    return null
}

fun main() {
    println(findFirstEven(listOf(1, 3, 4, 5, 6)))   // => 4
}
```

`return n`이 `forEach`에 넘긴 람다 안에 있지만, 이 `return`은 람다를 끝내는 것이 아니라 바깥 함수 `findFirstEven`을 즉시 `n`으로 반환시킨다. 그래서 첫 짝수 `4`를 찾자마자 함수 전체가 끝나고 `4`가 나온다. 만약 M41의 믿음대로 "람다만" 끝났다면 루프는 계속 돌아 마지막에 `null`이 나왔을 것이다. 이것이 비지역 반환이다 — `return`이 자신의 렉시컬 위치를 뛰어넘어 바깥 함수를 끝낸다.

### 7.2 왜 forEach에서는 되고 저장된 람다에서는 안 되는가

그런데 비지역 반환은 아무 람다에서나 되는 게 아니다. **인라인 함수에 전달된 람다에서만** 가능하다. `forEach`가 `inline` 함수이기 때문에 위 예가 동작한 것이다. 인라인되지 않는 곳에 넘긴 람다에서 벌거벗은 `return`을 쓰면 **컴파일 에러**다.

```kotlin
fun demo(): Int {
    val lambda = { n: Int -> return n }
    // 컴파일 에러: 'return' is not allowed here
    //   ('return' is prohibited in a lambda that is not inlined)
    return lambda(5)
}
```

왜 이런 제약이 있는가? 비지역 반환의 의미는 "이 `return`을 만나면 바깥 함수의 스택 프레임을 끝내고 그 함수의 반환 지점으로 점프하라"이다. 이 점프가 물리적으로 가능하려면, 람다의 본문이 바깥 함수의 프레임 *안에서* 실행되고 있어야 한다. **인라인 함수는 람다 본문을 호출부에 그대로 펼쳐 넣으므로**, `return`은 그냥 바깥 함수 본문 안의 평범한 `return`이 되어 아무 문제 없이 프레임을 끝낼 수 있다.

반면 인라인되지 않는 람다는 별도의 함수 객체로 컴파일되어 *독립된 프레임*에서 실행된다(3절). 이 상황에서 람다 안의 `return`이 바깥 함수를 끝내려면, 이미 반환되었을지도 모르는 바깥 프레임으로 점프해야 한다 — 바깥 함수가 이미 끝났는데 람다가 나중에 호출되면 돌아갈 프레임이 없다. 이것은 안전하게 구현할 수 없으므로, 코틀린은 아예 컴파일 타임에 금지한다.

> **역사 메모**: JVM에는 이런 "먼 곳으로의 반환"을 위한 저수준 장치가 없다. 인라인되지 않는 람다에서 억지로 비지역 반환을 흉내 내려면 특수 예외를 던지고 바깥에서 잡는 식의 트릭이 필요한데(실제로 일부 언어가 그렇게 한다), 코틀린은 그 복잡성과 비용 대신 "인라인 람다에서만 허용"이라는 명료한 규칙을 택했다. 그래서 비지역 반환은 인라인([[15 - 인라인 함수와 reified]])과 뗄 수 없는 짝이다.

### 7.3 라벨 반환: 람다만 끝내고 싶을 때

그렇다면 정말로 "람다만" 끝내고 바깥 함수는 계속하고 싶으면 어떻게 하는가? **라벨을 붙인 반환 `return@label`** 을 쓴다. 이것을 **지역 반환(local return)** 이라 한다.

```kotlin
fun printNonNegatives(nums: List<Int>) {
    nums.forEach { n ->
        if (n < 0) return@forEach        // 이 람다 호출(=이번 반복)만 끝냄
        println(n)
    }
    println("완료")                       // 음수를 건너뛰고 여기까지 온다
}

fun main() {
    printNonNegatives(listOf(1, -2, 3))
    // => 1
    // => 3
    // => 완료
}
```

`return@forEach`는 `forEach`의 람다 한 번의 호출(이 반복)만 끝낸다. `continue`처럼 다음 원소로 넘어가는 효과다. 함수 전체는 끝나지 않아 마지막 `"완료"`가 찍힌다. 라벨 이름 `forEach`는 람다가 전달된 함수 이름을 컴파일러가 **암시적 라벨**로 붙여 준 것이다. 직접 라벨을 지정할 수도 있다.

```kotlin
fun printNonNegatives(nums: List<Int>) {
    nums.forEach loop@{ n ->
        if (n < 0) return@loop           // 명시적 라벨
        println(n)
    }
}
```

정리하면 람다 안의 반환은 두 종류다.

| 형태 | 이름 | 무엇을 끝내나 | 어디서 가능한가 |
|---|---|---|---|
| `return` (벌거벗은) | 비지역 반환 | 감싸는 **함수** 전체 | 인라인 람다에서만 |
| `return@label` | 지역 반환 | 그 **람다 호출**만 | 어디서나 |

M41을 정확히 교정하면: **람다의 벌거벗은 `return`은 람다가 아니라 바깥 함수를 끝낸다(비지역 반환). "람다만" 끝내려면 반드시 `return@label`을 명시해야 한다. 그리고 벌거벗은 `return` 자체가 인라인 람다에서만 허용된다.**

### 7.4 익명 함수의 return은 또 다르다

여기서 람다와 익명 함수의 미묘한 차이가 드러난다. **익명 함수(`fun(...) {...}`)의 `return`은 그 익명 함수 자신을 끝낸다** — 라벨 없이도 지역 반환이다. 이것이 람다와 익명 함수의 가장 큰 의미론적 차이다.

```kotlin
fun printNonNegatives(nums: List<Int>) {
    nums.forEach(fun(n: Int) {           // 람다가 아니라 익명 함수
        if (n < 0) return               // 이 익명 함수만 끝냄 (지역 반환)
        println(n)
    })
    println("완료")                       // 정상 도달
}
```

똑같이 벌거벗은 `return`이지만, 람다였다면 비지역 반환(바깥 함수 종료)이 됐을 것이 익명 함수에서는 자기 자신만 끝내는 지역 반환이다. 그래서 "함수 전체가 아니라 콜백 한 번만 끝내고 싶은데 `return@label`을 쓰기 싫다"면 익명 함수가 자연스럽다. 이 차이를 한 표로.

| | 람다 `{ ... }` | 익명 함수 `fun(...) { ... }` |
|---|---|---|
| 벌거벗은 `return` | 비지역(바깥 함수 종료), 인라인에서만 | 지역(자기 자신 종료), 항상 |
| `it` 사용 | 단일 파라미터면 가능(M42, 13장) | 불가(파라미터 이름 필수) |
| 반환 타입 | 추론 | 명시 가능 |

### 7.5 crossinline과 noinline: 비지역 반환의 통제

인라인 함수를 설계하는 쪽에서는 비지역 반환을 허용할지 통제할 수 있다. 인라인 함수가 받은 람다를 *다른 실행 문맥*(예: 다른 스레드, 저장된 콜백)으로 넘겨야 한다면, 그 람다에서 비지역 반환이 일어나면 위험하다(바깥 함수는 이미 끝났을 수 있다). 이를 막는 것이 `crossinline`이다.

```kotlin
inline fun runLater(crossinline block: () -> Unit) {
    val r = Runnable { block() }          // 다른 문맥으로 넘김
    r.run()
    // block은 인라인되지만 crossinline이라 비지역 return 금지
}
```

`crossinline`이 붙은 람다에서 벌거벗은 `return`을 시도하면 컴파일 에러가 난다 — 그 람다는 인라인되긴 하지만 비지역 반환은 허용되지 않는다. 반대로 `noinline`은 아예 그 람다를 인라인하지 않아 일반 함수 객체로 만든다(따라서 역시 비지역 반환 불가). 이 키워드들의 전체 이야기는 이 장의 몫이 아니라 [[15 - 인라인 함수와 reified]]의 몫이다. 여기서는 "비지역 반환이 인라인과 얽혀 있고, 인라인 함수 작성자가 그것을 켜고 끌 수 있다"는 것만 붙잡으면 된다.

### 7.6 중첩된 람다와 라벨의 모호성

인라인 람다가 중첩되면 벌거벗은 `return`이 어디로 가는지가 특히 헷갈린다. 규칙은 단순하다: **벌거벗은 `return`은 언제나 가장 가까운 `fun`(감싸는 이름 있는 함수)을 끝낸다.** 중간에 몇 겹의 인라인 람다가 있든 상관없다.

```kotlin
fun hasPair(rows: List<List<Int>>, target: Int): Boolean {
    rows.forEach { row ->
        row.forEach { cell ->
            if (cell == target) return true   // forEach 두 겹을 관통해 hasPair를 끝냄
        }
    }
    return false
}

fun main() {
    println(hasPair(listOf(listOf(1, 2), listOf(3, 4)), 3))   // => true
}
```

`return true`는 안쪽 `forEach`도 바깥 `forEach`도 아닌, 이름 있는 함수 `hasPair`를 통째로 끝낸다 — 두 겹의 인라인 람다를 관통하는 비지역 반환이다. 그래서 `3`을 찾자마자 두 루프를 한꺼번에 탈출한다. 만약 안쪽 루프의 이번 원소만 건너뛰고 싶다면 `return@forEach`를 쓰는데, 여기서 라벨이 모호해진다 — `forEach`가 둘이라 어느 것인가? 이럴 때 **명시적 라벨**로 못 박는다.

```kotlin
fun countMatches(rows: List<List<Int>>, target: Int): Int {
    var count = 0
    rows.forEach outer@{ row ->
        row.forEach inner@{ cell ->
            if (cell != target) return@inner   // 안쪽 forEach의 이번 원소만 건너뜀
            count++
        }
    }
    return count
}
```

암시적 라벨 `return@forEach`는 가장 가까운 `forEach`(즉 안쪽)를 가리키지만, 중첩되어 헷갈릴 땐 `outer@`/`inner@`처럼 이름을 직접 붙여 의도를 드러내는 편이 안전하다. 요컨대 벌거벗은 `return`은 함수로, `return@label`은 지정한 람다로 — 이 두 좌표만 정확히 잡으면 아무리 깊이 중첩돼도 흐름을 놓치지 않는다.

> **흔한 오해**: "인라인 람다가 여러 겹이면 `return`이 한 겹씩 벗겨진다"고 상상하기 쉽지만 그렇지 않다. 벌거벗은 `return`에는 "한 겹만"이라는 개념이 없다 — 곧장 가장 가까운 이름 있는 함수까지 간다. "한 겹만" 벗기고 싶으면 그 겹의 라벨을 명시해야 한다. 이 비대칭(기본은 끝까지, 한 겹은 명시)이 M41의 실전 버전이다.

## 8. 캡처의 비용과 성능 — 할당, 그리고 인라인이 없애는 것

### 8.1 캡처하지 않는 람다는 싱글턴이 될 수 있다

캡처의 비용을 이해하려면 캡처가 *없을* 때 무슨 일이 일어나는지부터 봐야 한다. **JVM 백엔드에서**, 자유 변수를 하나도 캡처하지 않는 람다는 상태가 없으므로 매번 새 객체를 만들 필요가 없다. 컴파일러는 이런 람다를 **하나의 싱글턴 인스턴스**로 만들어 재사용할 수 있다.

```kotlin
fun noCapture(): (Int) -> Int {
    return { x -> x + 1 }        // 자유 변수 없음 → 싱글턴 재사용 가능(JVM)
}

fun main() {
    val a = noCapture()
    val b = noCapture()
    println(a === b)             // JVM 백엔드에서 대개 true (같은 싱글턴)
}
```

`{ x -> x + 1 }`은 `x` 말고 붙잡는 게 없다. 상태가 없으니 여러 번 호출해도 같은 인스턴스를 돌려줄 수 있고, 그러면 할당이 0이다. 반대로 캡처가 있으면 캡처된 값을 담을 필드가 필요하므로 **호출마다 새 객체**를 할당해야 한다. 그래서 "이 람다가 무언가를 캡처하는가"는 그 자체로 성능 질문이다: 캡처 없음 → 할당 없음(가능), 캡처 있음 → 매번 할당.

> **성능 주의**: `a === b`가 `true`가 되는 것은 **JVM 백엔드의 최적화**이지 언어가 보장하는 의미론이 아니다. 두 람다의 참조 동일성에 의존하는 코드를 짜면 안 된다([[10 - 불리언과 동등성과 동일성]]의 M48 정신과 같다 — 참조 동일성은 최적화에 흔들린다). 여기서 요점은 "동일하다"가 아니라 "캡처가 없으면 할당을 아낄 여지가 생긴다"는 성능 원리다. Kotlin 2.0부터 JVM 람다는 기본적으로 `invokedynamic`(LambdaMetafactory 기반)으로 컴파일되는데, 이 역시 익명 클래스 생성 비용을 줄이려는 방향이며, 캡처 유무가 할당에 미치는 영향의 큰 그림은 동일하다.

### 8.2 캡처는 두 종류의 할당을 부를 수 있다

캡처가 있는 람다는 잠재적으로 두 번의 힙 할당을 부른다.

```text
캡처 있는 람다의 비용 (JVM 백엔드, 인라인 안 될 때)

  var acc = 0
  val fn = { acc += it }

  ① 캡처된 var acc → Ref.IntRef 객체 1개 할당
  ② 람다 자체 → Function 객체 1개 할당 (IntRef를 필드로 붙듦)

  두 개의 힙 객체가 생긴다.
```

읽기만 하는 `val` 캡처라면 ①은 없고 ②(값 필드를 가진 람다 객체)만 있다. 수정되는 `var`를 캡처하면 ①의 `Ref`까지 추가된다(3.4절). 이 비용이 문제가 되는 곳은 대개 **뜨거운 루프**다. 반복마다 새 람다를 만들어 컬렉션 연산에 넘기면, 반복 횟수만큼 객체가 쌓인다.

### 8.3 인라인이 캡처 비용을 통째로 없앤다

이 모든 비용을 근본적으로 없애는 것이 인라인이다. 람다가 인라인 함수에 전달되어 인라이닝되면, 람다 객체도, 캡처된 `Ref`도 만들 필요가 없다 — 본문이 호출부에 펼쳐지고 캡처된 변수는 그냥 같은 스코프의 지역 변수가 되기 때문이다.

```kotlin
inline fun repeatAction(times: Int, action: (Int) -> Unit) {
    var i = 0
    while (i < times) { action(i); i++ }
}

fun main() {
    var sum = 0
    repeatAction(1_000_000) { sum += it }   // 인라인 → 람다 객체·Ref 할당 없음
    println(sum)                             // => 499999500000
}
```

`repeatAction`이 `inline`이라, `{ sum += it }`은 객체로 만들어지지 않고 `while` 루프 안에 그대로 펼쳐진다. `sum`도 별도 `Ref`로 승격될 필요 없이 `main`의 지역 변수 그대로 접근된다. 백만 번 반복해도 캡처에 의한 힙 할당은 0이다. 이것이 표준 라이브러리가 `forEach`·`map`·`filter`·스코프 함수 등 람다를 받는 함수 상당수를 `inline`으로 만든 이유다 — 함수형 스타일을 쓰되 캡처 할당의 대가는 치르지 않게 하려는 것.

이 지점에서 M41(7절)과 성능이 하나로 묶인다. 비지역 반환이 인라인 람다에서만 되는 이유(7.2)와, 캡처 비용이 인라인에서 사라지는 이유(8.3)는 같은 사실의 두 얼굴이다: **인라인 람다는 별도 객체·별도 프레임이 아니라 호출부에 펼쳐진 코드**라는 것. 그래서 바깥 함수를 끝낼 수도 있고(비지역 반환), 캡처를 위한 객체도 필요 없다.

### 8.4 언제 캡처 비용을 신경 쓸 것인가

그렇다고 모든 캡처를 두려워할 필요는 없다. 대부분의 코드에서 람다 하나의 할당은 무시할 만하다. 실제로 신경 써야 할 곳은 좁다: (1) 초당 수백만 번 도는 뜨거운 루프에서 매번 캡처 람다를 새로 만드는 경우, (2) 인라인되지 않는 곳(저장되는 콜백, 다른 스레드로 넘기는 작업)에 넘기는데 캡처가 큰 객체를 붙드는 경우(6절 누수와도 연결), (3) [[40 - 시퀀스와 지연 평가]]처럼 원소마다 람다를 호출하는 파이프라인. 이런 곳이 아니라면 캡처의 명료함이 미세한 할당보다 훨씬 값지다. 성능은 측정으로 판단할 일이지 지레 겁먹을 일이 아니다.

---

지금까지의 궤적을 한 줄기로 회수하자. 클로저는 함수가 자신의 렉시컬 환경에서 온 자유 변수를 붙잡는 현상이고, 코틀린은 이를 Java처럼 값 스냅샷으로 붙잡는 대신 **변수 그 자체를 공유**하는 방식으로 구현했다 — 그래서 `var`도 캡처·수정 가능하고, 그 수정이 바깥과 안에 일관되게 보인다. 이 공유를 JVM 위에서 가능하게 한 장치가 `Ref` 래핑이었고(수정되는 `var`만 힙 셀로 승격), 그것이 곧 캡처의 할당 비용이자 인라인이 없애는 대상이었다. 루프에서는 무엇이 반복별 새 바인딩(`for` 변수, 반복 안 `val`)이고 무엇이 하나의 공유 셀(바깥 `var`)인지가 캡처 결과를 갈랐다. 캡처는 붙잡은 객체를 살려 두므로 누수의 씨앗이 되며, 처방은 언제나 "필요한 값만 좁게 캡처하라"였다. 마지막으로 이 장의 오개념 M41 — 람다의 `return`이 람다만 끝낸다는 착각 — 을, 벌거벗은 `return`은 바깥 함수를 끝내는 비지역 반환이며 그것이 인라인 람다에서만 허용되고, 람다만 끝내려면 `return@label`을 써야 한다는 규칙으로 교정했다. 캡처는 코틀린 함수형 스타일의 편의를 지탱하는 기둥이지만, 그 편의 뒤에는 언제나 "무엇을 붙잡고, 얼마나 살리고, 무엇을 할당하는가"라는 질문이 숨어 있다. 그 질문을 던질 줄 아는 것이 이 장이 준 도구다.

## 핵심 요약

- **클로저는 함수가 렉시컬 환경의 자유 변수를 붙잡는 현상이며, 이름 결정은 정의 위치로 정적으로 정해진다(렉시컬 스코프).** 호출 위치는 캡처된 이름을 바꾸지 못한다. 람다·익명 함수·지역 함수·익명 객체가 모두 클로저를 만든다.
- **코틀린 클로저는 값이 아니라 변수(저장 셀)를 캡처한다.** Java는 `effectively final`만 값으로 복사 캡처하지만, 코틀린은 `var`도 캡처하고 람다 안 수정이 바깥에 보인다 — 셀을 공유하기 때문이다.
- **JVM 백엔드에서 수정되는 캡처 `var`는 `Ref.IntRef`/`Ref.ObjectRef` 같은 힙 래퍼로 승격되어 공유된다.** 이는 언어 명세가 아니라 JVM 구현 세부이며, 요구되는 것은 "수정이 일관되게 보인다"는 관찰 가능한 의미론뿐이다. 수정 안 되는 `val`은 값 복사로 캡처된다.
- **`val` 캡처가 불변을 보장하지는 않는다.** 캡처된 참조가 가리키는 객체가 가변이면 람다는 그 변화를 본다(11장 M3와 이어짐). "값 복사"는 참조값의 복사이지 깊은 복사가 아니다.
- **`for` 루프 변수는 반복마다 새 불변 바인딩이라 각 람다가 반복별 값을 캡처한다.** 반면 루프 바깥의 하나의 `var`를 캡처하면 모든 람다가 같은 셀을 공유해 최종값을 본다. 반복별 값이 필요하면 반복 안에서 새 `val`로 고정한다.
- **클로저는 캡처한 객체를 살려 둔다 — 이것이 메모리 누수의 씨앗이다.** 클래스 프로퍼티를 참조하는 람다는 값이 아니라 `this` 인스턴스 전체를 붙잡으므로, 필요한 값만 지역 변수로 뽑아 좁게 캡처하는 것이 처방이다.
- **람다의 벌거벗은 `return`은 람다가 아니라 감싸는 함수 전체를 끝내는 비지역 반환이다(M41).** "람다만" 끝내려면 반드시 `return@label`(지역 반환)을 써야 한다. 이 착각이 M41의 핵심이다.
- **비지역 반환은 인라인 함수에 전달된 람다에서만 허용된다(M41, 15장 연결).** 인라인 람다는 본문이 호출부에 펼쳐져 바깥 프레임에서 실행되기 때문이다. 인라인되지 않는 람다의 벌거벗은 `return`은 컴파일 에러다.
- **익명 함수의 `return`은 라벨 없이도 지역 반환이다 — 자기 자신만 끝낸다.** 같은 벌거벗은 `return`이라도 람다(비지역)와 익명 함수(지역)의 의미가 다르다.
- **캡처 없는 람다는 JVM 백엔드에서 싱글턴으로 재사용될 수 있어 할당이 없고, 캡처가 있으면 람다 객체(그리고 수정 var면 `Ref`까지) 할당이 발생한다.** 인라인은 이 캡처 할당을 통째로 제거한다 — 비지역 반환 허용과 캡처 비용 제거는 "인라인 람다는 펼쳐진 코드"라는 한 사실의 두 얼굴이다.
- **캡처 비용을 실제로 걱정할 곳은 뜨거운 루프·저장되는 콜백·원소별 파이프라인으로 좁다.** 그 밖에서는 명료함이 미세 할당보다 값지며, 성능은 지레짐작이 아니라 측정으로 판단한다.

- [[31 - 중첩 클래스와 이너 클래스와 익명 객체]] — `inner` 클래스·익명 객체의 외부 인스턴스 캡처와 그로 인한 누수는 이 장 6절과 같은 뿌리다.
- [[43 - 동시성과 메모리 모델]] — 캡처된 `var`를 여러 스레드가 공유하면 가시성·경쟁 문제가 생긴다. 캡처의 셀 공유가 동시성 위험이 되는 지점.
- [[10 - 불리언과 동등성과 동일성]] — 캡처 없는 람다의 싱글턴 최적화가 만드는 `===` 결과(M48)의 정신과 이어진다. 참조 동일성은 최적화에 흔들린다.
- [[40 - 시퀀스와 지연 평가]] — 원소마다 람다를 호출하는 지연 파이프라인에서 캡처 할당이 성능에 드러나는 대표 사례.
- [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]] — `Ref` 래핑·람다 컴파일 형태는 JVM `.class`를 디컴파일해 확인할 수 있다. 이 장의 기계 수준 주장을 눈으로 보는 법.
