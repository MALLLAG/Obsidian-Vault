**이 장이 답하는 질문:**

- 코틀린이 아무 한정자도 안 붙였을 때 왜 하필 `public`을 골랐고, 자바의 "패키지-프라이빗 기본값"과 갈라선 대가는 무엇인가?
- `internal`은 자바의 package-private과 정말 같은가, 아니면 근본적으로 다른 것을 재는 자인가? (M44)
- "모듈(module)"이란 대체 무엇인가—파일인가, 패키지인가, 프로젝트인가, 아니면 그 어느 것도 아닌 무엇인가?
- 최상위 `private`과 클래스 멤버 `private`은 같은 단어인데 왜 스코프가 다른가? 같은 클래스의 *다른 인스턴스*의 private에는 접근할 수 있는가?
- 코틀린 `protected`는 자바 `protected`와 무엇이 다르며, 그 차이가 JVM 상호운용에서 왜 조용히 새어 나가는가?
- `private set` 한 줄로 "읽기는 공개, 쓰기는 비공개"라는 비대칭 캡슐화가 어떻게 가능한가?
- `internal` 함수가 컴파일되면 왜 이름이 `foo$app` 같은 괴상한 형태로 뒤틀리는가(name mangling), 그리고 그것을 자바에서 부르면 어떻게 되는가?
- `public` 함수가 `internal` 타입을 반환하려 하면 컴파일러가 왜 화를 내는가—가시성은 선언 하나의 문제가 아니라 *관계*의 문제인가?

[[25 - 인터페이스]]에서 우리는 계약(contract)을 다뤘다. 인터페이스는 "무엇을 할 수 있는가"를 선언하되 "어떻게 하는가"는 구현 클래스에 맡긴다. 그런데 인터페이스가 노출하는 계약의 *바깥쪽* 경계, 즉 "누가 이 선언을 볼 수 있는가"라는 질문은 인터페이스 문법과는 다른 축에서 결정된다. 그 축이 바로 이 장의 주제인 **가시성(visibility)** 이다. 캡슐화(encapsulation)라는 객체 지향의 오래된 미덕은 결국 "내부를 감추고 계약만 드러낸다"로 요약되는데, 그 "감춤"의 정밀한 문법 장치가 가시성 한정자다.

이 장의 경계를 못박아 두자. 여기서는 **선언이 어디에서 참조 가능한가**를 결정하는 네 한정자—`public`, `private`, `protected`, `internal`—의 의미론과 규칙 차이만 다룬다. 가시성과 얽히지만 이 장이 소유하지 않는 주제들은 명확히 위임한다. 오버라이딩할 때 가시성을 어떻게 좁히거나 넓힐 수 있는가의 *상속 측면*은 이 장에서 규칙만 확정하고 초기화 순서와의 상호작용은 [[24 - 상속과 오버라이딩과 초기화 순서]]가 소유한다. 프로퍼티의 게터/세터가 어떤 백킹 필드로 컴파일되는지(M35)는 [[22 - 프로퍼티와 백킹 필드]]로, 중첩·이너 클래스가 바깥 인스턴스를 어떻게 참조하는지는 [[31 - 중첩 클래스와 이너 클래스와 익명 객체]]로, `internal`이 자바 쪽에서 어떤 맹글링된 이름으로 보이는가의 상호운용 총람은 [[45 - Java 상호운용]]으로 넘긴다. 이 장은 그 모든 것이 딛고 서는 *가시성 규칙 자체*에 집중한다.

논증의 궤적은 이렇다. 먼저 "왜 가시성이 캡슐화의 도구인가"와 코틀린이 기본값을 `public`으로 정한 결정의 무게를 잰다. 그다음 네 한정자를 하나씩 해부하되, 각각이 *선언 위치*(최상위·멤버·생성자·지역)에 따라 규칙이 어떻게 갈라지는지를 파고든다. 이 장의 심장은 5절과 8절이다. 5절에서 이 장의 소유 오개념 **M44**—"`internal`은 자바의 package-private이다"—를 정면으로 반박하며 "모듈"이라는 낯선 단위를 정의한다. 8절에서 그 추상적 규칙이 JVM 백엔드에서 어떤 바이트코드와 이름 맹글링으로 내려앉는지, 그리고 그 과정에서 코틀린의 가시성 보장이 자바 상호운용의 틈으로 어떻게 새는지를 확인한다.

한 가지 예고. 가시성은 겉보기엔 "키워드 네 개 외우면 끝"처럼 보이는 얕은 주제다. 그러나 그 아래에는 "컴파일 단위란 무엇인가", "JVM에는 모듈 개념이 없는데 코틀린은 그것을 어떻게 흉내 내는가", "가시성은 선언의 속성인가 관계의 속성인가" 같은 깊은 질문이 깔려 있다. 이 장은 그 얕아 보이는 표면을 끝까지 긁어 아래의 기계를 드러낸다.

## 1. 왜 가시성인가 - 캡슐화와 네 개의 한정자

### 1.1 가시성이 푸는 문제

가시성 한정자는 "이 선언을 코드베이스의 어디에서 이름으로 참조할 수 있는가"를 컴파일러가 강제하도록 만드는 장치다. 그 목적은 단순한 접근 제어가 아니라 **변경 가능성의 경계 긋기**다. `private`으로 감춘 것은 언제든 자유롭게 바꿀 수 있다—아무도 그 이름에 의존할 수 없으므로. `public`으로 드러낸 것은 계약이 되어 버린다—누군가 의존하는 순간 함부로 바꾸면 그의 코드가 깨진다.

이 관점에서 가시성은 미래의 자신과 협업자에게 보내는 신호다.

```kotlin
class BankAccount(initial: Long) {
    var balance: Long = initial
        private set              // 읽기는 공개, 쓰기는 클래스 내부에서만

    private var pin: String = ""  // 완전히 감춤: 밖에서 존재조차 모른다

    fun deposit(amount: Long) {
        require(amount > 0)
        balance += amount         // 내부에서는 자유롭게 변경
    }
}

val acc = BankAccount(1000)
println(acc.balance)   // => 1000  (읽기 허용)
// acc.balance = 5000  // 컴파일 에러: cannot assign, setter is private
// acc.pin            // 컴파일 에러: pin is private in BankAccount
```

`pin`을 `private`으로 감췄기 때문에, 훗날 이 필드를 삭제하고 해시로 대체하든 외부 서비스로 옮기든 `BankAccount`의 사용자는 아무 영향도 받지 않는다. 반대로 `balance`를 `public`으로 노출한 순간, 그 이름과 타입은 계약이 되었다.

### 1.2 네 한정자의 개관

코틀린에는 정확히 네 개의 가시성 한정자가 있다.

| 한정자 | 한 줄 정의 | 최상위 허용 | 멤버 허용 |
|--------|-----------|:----------:|:--------:|
| `public` | 어디서나 보임 (기본값) | ✅ | ✅ |
| `private` | 최상위=같은 파일 / 멤버=같은 클래스 | ✅ | ✅ |
| `protected` | 해당 클래스와 하위 클래스에서만 | ❌ | ✅ |
| `internal` | 같은 모듈 안에서 보임 | ✅ | ✅ |

여기서 즉시 눈에 띄는 비대칭이 두 가지다. 첫째, `protected`는 **최상위 선언에 붙일 수 없다**—"하위 클래스"라는 개념이 클래스 없는 최상위 함수에는 무의미하기 때문이다. 둘째, `private`은 최상위와 멤버에서 *같은 단어이지만 다른 스코프*를 뜻한다. 이 두 비대칭이 이 장 3절과 4절의 핵심이다.

> **명세 정밀**: 코틀린은 자바나 C#과 달리 가시성 한정자를 **조합할 수 없다**. C#에는 `protected internal`(protected 또는 같은 어셈블리)과 `private protected`(protected 그리고 같은 어셈블리)라는 조합이 있지만, 코틀린은 네 한정자 중 정확히 하나만 붙인다. `protected internal fun f()`는 컴파일 에러다. 이 단순함은 의도된 설계로, "가시성은 단일 축"이라는 규칙을 지킨다.

### 1.3 가시성은 컴파일 타임 계약이다

강조할 점: 가시성은 **컴파일 타임에만** 검사된다. `private` 필드도 런타임에는 리플렉션([[44 - 애노테이션과 리플렉션]]은 아직이지만)이나 JVM의 낮은 수준 접근으로 얼마든지 읽을 수 있다. 가시성은 실행 시점의 보안 장벽이 아니라 *컴파일러가 실수를 막아 주는 정적 계약*이다.

```kotlin
class Secret(private val token: String)

val s = Secret("abc")
// s.token  // 컴파일 에러 — 하지만 이는 정적 검사일 뿐

// 리플렉션으로는 뚫린다 (JVM 백엔드, 개념 예시):
val field = Secret::class.java.getDeclaredField("token")
field.isAccessible = true
println(field.get(s))  // => abc  — 가시성은 보안이 아니다
```

이 사실은 실무에서 중요하다. `private`으로 감춘 값은 "설계상 아무도 만지지 말 것"이라는 *약속*이지, 암호학적 비밀 보관소가 아니다. 민감 데이터의 진짜 보호는 가시성이 아니라 별도의 보안 메커니즘이 담당한다. 가시성이 주는 것은 오직 하나—**컴파일 타임에 잘못된 의존을 차단하는 힘**이다.

## 2. public - 기본값이자 최대 노출

### 2.1 명시할 필요가 없는 한정자

코틀린에서 아무 한정자도 쓰지 않으면 `public`이다. 이것은 자바와의 **결정적 갈림길**이다. 자바는 아무것도 안 쓰면 package-private(같은 패키지에서만 보임)이 기본인데, 코틀린은 최대 노출인 `public`이 기본이다.

```kotlin
// 이 두 선언은 정확히 동등하다
fun greet() = "hello"
public fun greet2() = "hello"

class Circle(val radius: Double) {
    fun area() = Math.PI * radius * radius        // public
    public fun area2() = Math.PI * radius * radius // 위와 동등, 불필요한 명시
}
```

`public` 키워드를 명시적으로 쓰는 것은 문법상 허용되지만 관례상 생략한다. 코틀린 스타일 가이드는 "기본값과 같은 한정자는 쓰지 말라"고 권한다. 그래서 실전 코틀린 코드에서 `public`이라는 단어를 보기는 드물다—그것이 도처에 있기 때문에 역설적으로 보이지 않는다.

### 2.2 왜 최대 노출을 기본으로 골랐는가

이 선택은 논쟁적이다. "안전한 기본값(secure by default)" 관점에서는 캡슐화를 위해 가장 좁은 가시성을 기본으로 삼는 편이 낫다. 자바의 package-private 기본값, 러스트의 "기본은 private" 정책이 그 철학이다. 코틀린은 왜 반대로 갔는가?

첫째, **실용주의**다. 코틀린은 애플리케이션 코드에서 대부분의 선언이 결국 어딘가에서 쓰이려고 존재한다고 봤다. 매번 `public`을 타이핑하게 만드는 것은 흔한 경우에 세금을 매기는 꼴이다. "흔한 경우는 짧게, 드문 경우는 명시적으로"라는 코틀린의 일관된 철학([[21 - 클래스와 생성자]]의 생성자 설계와 같은 정신)이 여기서도 작동한다.

둘째, 코틀린에는 자바의 package-private에 정확히 대응하는 개념이 **아예 없다**. 자바의 기본값은 패키지 스코프인데, 코틀린은 패키지를 가시성 경계로 삼지 않기로 했다(→ 5절 M44). 그래서 "패키지-프라이빗을 기본으로" 삼을 수조차 없었고, 남은 자연스러운 후보는 `public`이었다.

그 대가는 분명하다. 라이브러리를 만들 때 개발자가 부주의하면 **의도치 않게 API 표면이 부풀어 오른다**. 감췄어야 할 헬퍼 함수가 `public`으로 새어 나가 외부가 의존하기 시작하면, 나중에 그것을 바꾸기 어려워진다. 코틀린은 이 위험을 인지하고 라이브러리 저자를 위한 안전망을 따로 두었다—**explicit API mode**(9절).

> **흔한 오해**: "코틀린은 기본이 `public`이니 캡슐화에 약하다"는 말은 절반만 맞다. 애플리케이션 코드에서는 확실히 노출이 헤퍼질 수 있다. 하지만 라이브러리 코드에서는 explicit API mode(`-Xexplicit-api=strict`)를 켜면 public 선언에 명시적 한정자와 반환 타입을 *강제*할 수 있어, 오히려 자바보다 엄격한 규율을 세울 수 있다. 기본값이 느슨한 것과 언어가 캡슐화를 지원하지 않는 것은 별개다.

## 3. private - 두 얼굴 (최상위 vs 멤버)

`private`은 가장 강한 감춤이지만, 정확히 무엇을 감추는지는 **선언이 놓인 위치**에 따라 완전히 달라진다. 같은 단어가 두 개의 스코프를 가리킨다.

### 3.1 최상위 private = 파일 스코프

파일의 최상위(top-level)에 놓인 `private` 선언은 **그 파일 안에서만** 보인다. 패키지가 아니라 *파일*이 경계다.

```kotlin
// ==== geometry.kt ====
private const val PI = 3.14159       // 이 파일 안에서만
private fun square(x: Double) = x * x // 이 파일 안에서만

fun circleArea(r: Double) = PI * square(r)  // OK — 같은 파일

// ==== main.kt ====  (같은 패키지라 해도)
fun test() {
    // circleArea(2.0)  // OK — public
    // square(2.0)      // 컴파일 에러: square is private in file geometry.kt
    // println(PI)      // 컴파일 에러
}
```

여기서 결정적 사실: `main.kt`가 `geometry.kt`와 *같은 패키지*에 있어도 `square`와 `PI`에 접근할 수 없다. 최상위 `private`의 경계는 패키지가 아니라 **파일**이기 때문이다. 이는 자바에 정확히 대응하는 개념이 없다—자바에는 "파일 스코프 private 함수"라는 것이 없다(자바의 최상위는 클래스뿐이고, 파일 스코프 자유 함수 자체가 없다).

이 파일 스코프 `private`은 실무에서 대단히 유용하다. 한 파일 안에서만 쓰는 헬퍼 함수, 상수, 심지어 보조 클래스를 파일에 가둬 두어 파일 밖 네임스페이스를 오염시키지 않을 수 있다.

```kotlin
// ==== rational.kt ====
private fun gcd(a: Long, b: Long): Long =
    if (b == 0L) a else gcd(b, a % b)  // 이 파일 전용 유틸

class Rational(numerator: Long, denominator: Long) {
    private val g = gcd(numerator, denominator)  // 파일 private을 자유롭게 사용
    val num = numerator / g
    val den = denominator / g
}
```

`gcd`는 `Rational`을 구현하는 데만 쓰이는 도구라서 파일에 가둔다. 다른 파일에서 `gcd`라는 이름을 다시 써도 충돌하지 않는다.

### 3.2 멤버 private = 클래스 스코프

클래스나 인터페이스 안의 `private` 멤버는 **그 클래스(선언한 클래스) 본문 전체**에서 보인다. 여기서 "본문 전체"는 그 클래스의 모든 멤버 함수, 프로퍼티 초기화자, `init` 블록, 그리고 **중첩 클래스의 본문**까지 포함한다(→ 3.4).

```kotlin
class Stack<T> {
    private val items = mutableListOf<T>()   // 클래스 내부에서만
    private var topIndex = -1

    fun push(item: T) {
        items.add(item)      // OK
        topIndex++           // OK
    }
    fun pop(): T {
        val v = items[topIndex]
        items.removeAt(topIndex)
        topIndex--
        return v
    }
}

val s = Stack<Int>()
s.push(1)
// s.items  // 컴파일 에러: items is private in Stack
```

`items`와 `topIndex`는 `Stack`의 구현 세부사항이다. 리스트를 배열로 바꾸든 인덱스 추적 방식을 바꾸든, 외부는 `push`/`pop`이라는 계약만 보므로 영향받지 않는다. 이것이 캡슐화의 교과서적 실현이다.

### 3.3 같은 클래스의 다른 인스턴스 접근

미묘하지만 중요한 규칙: `private`은 "이 인스턴스만"이 아니라 "이 클래스만"이다. 그래서 **같은 클래스의 다른 인스턴스**의 private 멤버에도 접근할 수 있다. 이는 자바와 동일하다.

```kotlin
class Money(private val cents: Long) {
    // 다른 Money 인스턴스의 private cents를 읽는다 — 허용됨
    operator fun plus(other: Money) = Money(this.cents + other.cents)
    fun isMoreThan(other: Money) = this.cents > other.cents
    override fun toString() = "$${cents / 100}.${cents % 100}"
}

val a = Money(1500)
val b = Money(250)
println(a + b)            // => $17.50  — other.cents 접근이 정상 동작
println(a.isMoreThan(b))  // => true
```

`plus` 안에서 `other.cents`에 접근하는 것은 완전히 합법이다. `cents`는 "이 인스턴스에서만 비공개"가 아니라 "`Money` 클래스에서만 접근 가능"이기 때문이다. 이 규칙이 없다면 `equals`, `compareTo`, 산술 연산 오버로딩([[19 - 연산자 오버로딩과 관례]]) 같이 두 인스턴스를 비교·결합하는 연산을 private 필드로 구현하는 것이 불가능해진다.

> **명세 정밀**: 가시성 스코프의 단위는 "런타임 객체"가 아니라 "정적 선언 위치"다. `private`은 소스 코드의 어느 텍스트 영역에서 이름을 쓸 수 있는가를 정하는 규칙이지, 어느 힙 객체가 어느 힙 객체를 만질 수 있는가를 정하는 규칙이 아니다. 그래서 인스턴스 경계가 아니라 클래스 선언 경계로 작동한다.

### 3.4 중첩 클래스와 private의 비대칭 (자바와 다른 지점)

여기 자바 개발자를 놀라게 하는 규칙이 있다. 코틀린에서 **중첩·이너 클래스는 바깥 클래스의 private 멤버에 접근할 수 있지만, 바깥 클래스는 중첩 클래스의 private 멤버에 접근할 수 없다.** 접근이 한 방향으로만 흐른다.

```kotlin
class Outer {
    private val secret = 42

    inner class Inner {
        fun reveal() = secret       // OK — 안쪽이 바깥의 private을 봄
    }

    class Nested {
        private val hidden = 99
        fun show() = hidden         // OK — 자기 자신의 private
    }

    fun peek(n: Nested): Int {
        // return n.hidden          // 컴파일 에러: hidden is private in Nested
        return n.show()             // public 통해서만
    }
}
```

`Inner`(그리고 `Nested`)는 `Outer.secret`을 본다. 그러나 `Outer`는 `Nested.hidden`을 보지 못한다. 이것은 자바와 정반대다—**자바에서는 최상위 클래스와 그 안의 모든 중첩 클래스가 서로의 private을 양방향으로 공유**한다. 코틀린은 이 공유를 안쪽→바깥쪽 한 방향으로만 허용한다.

```java
// Java — 양방향 접근이 합법
class Outer {
    private int secret = 42;
    class Inner {
        private int hidden = 99;
        void f() { System.out.println(secret); }  // OK
    }
    void g(Inner i) { System.out.println(i.hidden); }  // Java에선 OK! (코틀린에선 에러)
}
```

이 차이의 근거는 코틀린 명세의 `private` 정의에 있다. 명세는 "클래스 `C`의 private 멤버 `D`는 `C` 본문 안—`C`의 멤버 본문과 `C`의 *중첩 분류자(nested classifier)의 본문*을 포함—에서 보인다"고 규정한다. 즉 private의 가시 영역은 "선언한 분류자의 안쪽으로 파고드는" 방향으로만 확장된다. `Nested`의 private은 `Nested` 안쪽으로만 흐르고, 그 바깥인 `Outer`로는 새어 나가지 않는다. 반대로 `Outer`의 private은 `Outer` 안쪽(중첩 클래스 포함)으로 흐른다.

> **흔한 오해**: "중첩 클래스는 바깥 클래스의 일부니 private을 자유롭게 공유한다"는 자바적 직관은 코틀린에서 절반만 맞다. 안→밖 접근은 되지만 밖→안 접근은 안 된다. 이 비대칭을 모르면 바깥 클래스에서 중첩 클래스의 내부 상태를 직접 만지려다 컴파일 에러를 만난다. 해법은 중첩 클래스가 `internal`이나 적절한 접근자를 노출하는 것이다.

### 3.5 클래스와 동반 객체 사이의 private 공유

`private`의 "선언 안쪽으로 흐른다" 규칙이 만드는 편리한 결과가 하나 더 있다. 클래스와 그 **동반 객체(companion object, [[28 - object와 companion - 싱글턴과 동반 객체]])** 는 서로의 private에 접근할 수 있다. 동반 객체는 클래스 본문 안에 중첩된 특별한 객체이므로, 3.4절의 "바깥의 private을 안쪽이 본다" 규칙이 적용되고, 코틀린은 그 역방향(클래스가 companion의 private을 봄)도 허용한다.

```kotlin
class Temperature private constructor(val celsius: Double) {
    companion object {
        private const val ABSOLUTE_ZERO = -273.15   // companion의 private
        fun of(c: Double): Temperature {
            require(c >= ABSOLUTE_ZERO)              // companion 안에서 자기 private
            return Temperature(c)                    // 클래스의 private 생성자 호출 — OK
        }
    }
    fun isColderThan(other: Temperature) =
        this.celsius < other.celsius                 // 다른 인스턴스 private (3.3)
}

val t = Temperature.of(25.0)   // 팩토리를 통해서만 생성
// Temperature(25.0)           // 컴파일 에러: constructor is private
```

`of` 팩토리 함수가 `private` 생성자 `Temperature(...)`를 호출할 수 있는 것이 이 상호 접근의 핵심이다. 이것이 "생성자를 private으로 감추고 companion 팩토리로만 만들게 하는" 관용구를 성립시킨다. companion과 클래스는 캡슐화의 관점에서 하나의 단위처럼 작동한다.

## 4. protected - 하위 클래스 전용 (Java와의 결정적 차이)

### 4.1 protected의 의미

`protected` 멤버는 **선언한 클래스와 그 하위 클래스에서만** 보인다. 외부 코드는 물론이고, 같은 패키지의 무관한 클래스도 보지 못한다. `protected`는 "상속 계층 내부의 확장 지점"을 여는 도구다.

```kotlin
open class Shape {
    protected open fun computeArea(): Double = 0.0  // 하위가 재정의할 훅
    fun describe(): String = "area = ${computeArea()}"  // public 진입점
}

class Rectangle(val w: Double, val h: Double) : Shape() {
    override fun computeArea() = w * h   // OK — 하위 클래스라 protected 접근
}

val r = Rectangle(3.0, 4.0)
println(r.describe())   // => area = 12.0
// r.computeArea()      // 컴파일 에러: computeArea is protected
```

`computeArea`는 하위 클래스가 채워 넣는 확장 지점이고, 외부에는 `describe`라는 공개 얼굴만 보인다. 이것이 템플릿 메서드 패턴(template method pattern)의 골격이다.

### 4.2 Java와의 결정적 차이 - 패키지 접근이 없다

자바 `protected`는 **두 가지**를 동시에 허용한다: (1) 하위 클래스, 그리고 (2) *같은 패키지의 모든 코드*. 코틀린 `protected`는 (1) 하위 클래스만 허용한다. **패키지 접근이 없다.**

```text
                     하위 클래스에서   같은 패키지 무관 클래스에서
  Java protected          O                    O
  Kotlin protected        O                    X   ← 이 지점이 다르다
```

```kotlin
// ==== animals.kt (package zoo) ====
open class Animal {
    protected val energy = 100
}

// 같은 패키지 zoo의 무관한 클래스
class Zookeeper {
    fun feed(a: Animal) {
        // a.energy   // 컴파일 에러: energy is protected — 상속 관계가 아니므로
    }
}

class Cat : Animal() {
    fun purr() = energy > 50   // OK — 하위 클래스
}
```

`Zookeeper`가 `Animal`과 같은 패키지에 있어도 `energy`에 접근하지 못한다. 상속 관계가 아니기 때문이다. 자바였다면 같은 패키지라는 이유만으로 접근이 뚫렸을 것이다. 코틀린이 이 패키지 접근을 뺀 이유는 **패키지를 가시성 경계로 쓰지 않는다는 일관된 방침**(→ 5절) 때문이다. 코틀린에서 패키지는 이름 정리(namespacing) 수단일 뿐, 접근 제어의 단위가 아니다.

> **성능 주의는 아니지만 상호운용 주의**: 이 차이는 JVM에서 조용히 새어 나간다. 코틀린 `protected` 멤버는 JVM 바이트코드에서 자바의 `protected`로 컴파일되는데, 자바 `protected`는 패키지 접근을 *포함*한다. 그래서 코틀린이 `protected`로 감춘 멤버가, **같은 패키지에 자바 클래스를 두면 그 자바 코드에서는 접근 가능해진다.** 코틀린의 "하위 클래스 전용" 보장이 JVM의 표현 한계 때문에 자바 쪽에서만 느슨해지는 것이다. 자세한 상호운용 함정은 [[45 - Java 상호운용]] 참고.

### 4.3 protected는 최상위에 붙을 수 없다

`protected`는 "하위 클래스"라는 상속 개념에 의존한다. 최상위 함수·프로퍼티에는 상속이라는 것이 없으므로 `protected`가 의미를 갖지 못한다. 그래서 컴파일러가 막는다.

```kotlin
// protected fun helper() { }   // 컴파일 에러: modifier 'protected' is not applicable to 'top level declaration'
```

같은 이유로, 최상위 선언에 쓸 수 있는 한정자는 `public`(기본), `private`(파일 스코프), `internal`(모듈 스코프) 세 개뿐이다. 4개 중 `protected`만 빠진다는 것을 표로 다시 정리하면 1.2절의 개관과 맞물린다.

### 4.4 protected 멤버와 companion·중첩

`protected`는 클래스 멤버 전용이지만, 몇 가지 미묘한 상호작용이 있다. `protected`로 선언한 중첩 클래스는 하위 클래스에서만 보인다. 또한 protected 멤버는 하위 클래스가 *자신의 protected로 재노출*하거나 public으로 넓힐 수 있는데, 이는 9.1절의 오버라이드 가시성 규칙과 연결된다.

한편 인터페이스([[25 - 인터페이스]])에는 `protected`를 쓸 수 없다. 인터페이스 멤버에 허용되는 가시성은 `public`(기본)과 `private`(구현이 있는 헬퍼용)뿐이다. `protected`와 `internal`은 인터페이스 본문에서 금지된다. 이유는 인터페이스가 상태 없는 계약(M37)이며, "하위 클래스 전용"이라는 개념이 다중 구현이 가능한 인터페이스의 의미와 잘 맞지 않기 때문이다.

## 5. internal - 모듈 가시성 (M44 정면 교정)

이제 이 장의 심장, 그리고 소유 오개념 **M44**를 다룰 차례다. 자바 배경 개발자가 `internal`을 처음 보면 거의 반사적으로 "아, 자바의 package-private 같은 거구나"라고 생각한다. **이것은 틀렸다.** `internal`은 패키지가 아니라 **모듈(module)** 을 재는 자다.

### 5.1 모듈이란 무엇인가

`internal`을 이해하려면 먼저 "모듈"의 정의를 못박아야 한다. 코틀린에서 **모듈은 함께 컴파일되는 코틀린 파일들의 집합**이다. 구체적으로 다음 중 하나가 하나의 모듈을 이룬다.

- IntelliJ IDEA의 모듈 하나
- Maven 프로젝트 하나
- Gradle 소스 세트(source set) 하나 (단, `test` 소스 세트는 `main`의 `internal` 선언을 볼 수 있는 예외가 있다)
- 하나의 Ant 태스크 호출로 함께 컴파일되는 파일들
- 코틀린 컴파일러를 한 번 호출할 때 함께 넘긴 파일들

핵심은 **"한 번의 컴파일 단위"** 라는 것이다. 모듈은 패키지도 아니고, 파일도 아니고, 프로젝트 전체도 아니다. "같이 컴파일되는 덩어리"다.

```text
  ┌─────────── 모듈 A (예: :core Gradle 소스셋) ───────────┐
  │  package math                                          │
  │    internal fun helper()   ← 모듈 A 어디서나 보임        │
  │  package geometry                                      │
  │    fun useHelper() = helper()   ← 다른 패키지지만 OK!    │
  └────────────────────────────────────────────────────────┘

  ┌─────────── 모듈 B (예: :app Gradle 소스셋, A에 의존) ───┐
  │  package math                                          │
  │    fun tryHelper() = helper()   ← 같은 패키지지만 에러!  │
  │                     (helper는 모듈 A의 internal)        │
  └────────────────────────────────────────────────────────┘
```

이 다이어그램이 M44의 핵심을 그대로 보여 준다. `internal`은 **패키지를 가로질러도** 같은 모듈이면 보이고, **같은 패키지여도** 다른 모듈이면 안 보인다.

### 5.2 internal ≠ package-private (M44)

두 규칙을 나란히 놓으면 차이가 명백해진다.

| 상황 | Java package-private | Kotlin internal |
|------|:---:|:---:|
| 같은 패키지, 같은 모듈 | ✅ 보임 | ✅ 보임 |
| **다른 패키지**, 같은 모듈 | ❌ 안 보임 | ✅ **보임** |
| 같은 패키지, **다른 모듈** | ✅ 보임* | ❌ **안 보임** |

(*자바에는 모듈 개념이 없어 "다른 모듈"은 클래스패스상 같은 패키지면 그냥 보인다.)

두 축(패키지 vs 모듈)이 서로 **직교**한다는 것이 요점이다. 자바의 경계는 패키지, 코틀린 `internal`의 경계는 모듈이며, 이 둘은 겹치는 부분도 있지만 근본적으로 다른 것을 잰다.

```kotlin
// ==== 모듈 :library, package data ====
internal class ConnectionPool {   // 모듈 전체에서 재사용할 내부 구현
    fun acquire(): Connection = TODO()
}

// ==== 모듈 :library, package service (다른 패키지, 같은 모듈) ====
class UserService {
    private val pool = ConnectionPool()  // OK! internal은 모듈 전체에서 보임
}

// ==== 모듈 :app (:library에 의존, 다른 모듈) ====
class AppMain {
    // val pool = ConnectionPool()  // 컴파일 에러: ConnectionPool is internal — 다른 모듈
}
```

`ConnectionPool`은 `:library` 모듈 안에서라면 어느 패키지에서든 마음껏 쓰인다. 그러나 `:library`를 의존성으로 가져다 쓰는 `:app` 모듈에서는 존재하지 않는 것처럼 감춰진다. 이것이 `internal`의 진짜 쓸모다.

### 5.3 왜 모듈인가 - 라이브러리 설계의 관점

`internal`이 왜 이렇게 설계됐는지는 **라이브러리 저자의 문제**에서 나온다. 라이브러리를 만들 때 개발자에게는 두 종류의 코드가 있다.

1. **공개 API**: 라이브러리 사용자가 의존해도 되는 계약. `public`.
2. **내부 구현**: 라이브러리 안의 여러 패키지가 협력하는 데 필요하지만, 사용자에게는 감춰야 하는 것.

문제는 (2)다. 내부 구현은 종종 여러 패키지에 흩어져 협력해야 한다. `private`(파일 스코프)은 너무 좁아서 다른 파일과 협력할 수 없다. `public`은 너무 넓어서 사용자에게 새어 나간다. 자바에서는 이 딜레마를 해결하기 어려웠다—package-private은 패키지를 못 넘고, 여러 패키지가 협력하려면 결국 `public`으로 열 수밖에 없어 "실수로 공개된 내부 API" 문제가 만연했다.

`internal`은 정확히 이 틈을 메운다. **"내 모듈 안에서는 자유롭게 협력하되, 모듈 밖으로는 절대 새지 않는다."** 라이브러리의 공개 표면(published API)과 내부 구현을 깔끔하게 가른다. 이것이 코틀린이 패키지가 아니라 모듈을 가시성 단위로 삼은 근본 이유다—패키지는 사용자에게 노출되지만, 모듈 경계는 배포 단위와 일치하기 때문이다.

> **역사 메모**: 자바도 이 문제를 결국 인정하고 Java 9(2017)에서 JPMS(Java Platform Module System, "Jigsaw")로 모듈 개념을 도입했다. `module-info.java`의 `exports` 지시어로 "이 패키지만 밖으로 노출"을 선언한다. 흥미롭게도 코틀린 `internal`(2016 정식 출시 시점부터 존재)은 JPMS보다 먼저, 훨씬 가벼운 형태로 같은 문제를 풀었다. 다만 둘의 층위는 다르다—JPMS는 런타임 강제(모듈 경계를 JVM이 검사)인 반면, 코틀린 `internal`은 컴파일 타임 규칙이며 JVM에는 이름 맹글링(→ 8절)이라는 우회로 남는다.

### 5.4 internal의 전파와 상속

`internal` 선언은 같은 모듈 안에서는 `public`처럼 자유롭게 상속·구현·오버라이드된다.

```kotlin
internal abstract class BaseRepository {
    internal abstract fun connect()
}

// 같은 모듈에서 상속 — OK
internal class SqlRepository : BaseRepository() {
    override fun connect() { /* ... */ }
}
```

한편 `internal`과 다른 한정자의 조합 노출 규칙도 있다. 예를 들어 `internal` 클래스의 `public` 멤버는 결국 `internal`만큼만 도달 가능하다—클래스 자체가 모듈 밖에서 안 보이므로 그 멤버도 실질적으로 모듈에 갇힌다. 가시성은 "가장 좁은 상위 선언"에 의해 상한이 정해진다. 이 "관계로서의 가시성"은 9절에서 노출 규칙으로 다시 다룬다.

또한 앞서 언급한 Gradle의 예외를 기억하자: `test` 소스 세트는 같은 프로젝트 `main` 소스 세트의 `internal` 선언을 볼 수 있다. 이는 특별 배려로, 내부 구현을 테스트하려면 접근이 필요하기 때문이다. 엄밀히는 별개 모듈이지만 테스트 편의를 위해 열어 둔 통로다.

### 5.5 모듈 경계를 눈으로 확인하기

"모듈"이라는 추상이 손에 잡히지 않는다면, Gradle 멀티프로젝트 구조로 구체화해 보자. 아래 세 소스 세트가 각각 하나의 모듈이다.

```text
  project/
  ├── core/  src/main/kotlin/   ← 모듈 core-main
  │          src/test/kotlin/    ← 모듈 core-test (core-main의 internal 봄)
  └── app/   src/main/kotlin/    ← 모듈 app-main (core에 의존)
             src/test/kotlin/    ← 모듈 app-test
```

```kotlin
// core/src/main/kotlin/data/Cache.kt   (모듈 core-main)
package data
internal class Cache { fun size() = 0 }

// core/src/main/kotlin/service/Loader.kt (모듈 core-main, 다른 패키지)
package service
import data.Cache
fun load() = Cache().size()       // OK — 같은 모듈, 패키지만 다름

// core/src/test/kotlin/CacheTest.kt   (모듈 core-test)
import data.Cache
fun test() = Cache().size()       // OK — test는 main의 internal을 봄 (예외)

// app/src/main/kotlin/Main.kt       (모듈 app-main)
import data.Cache
// fun run() = Cache().size()      // 컴파일 에러: Cache is internal (다른 모듈)
```

같은 `data.Cache`가 어디서 참조되느냐에 따라 보임/안 보임이 갈린다. 결정 요인은 "패키지가 같은가"가 절대 아니라 "**같은 모듈로 컴파일되는가**"다. `app-main`은 `core`를 라이브러리 의존성으로 가져오지만, 의존성으로 들어온 `internal`은 소비 측에서 감춰진다. 이것이 라이브러리 저자가 원했던 정확한 경계다—배포된 아티팩트의 소비자에게는 `internal`이 존재하지 않는 것과 같다.

### 5.6 internal과 멀티플랫폼

`internal`의 "모듈 = 컴파일 단위" 정의는 JVM에만 매인 개념이 아니다. 코틀린 멀티플랫폼([[46 - 멀티플랫폼과 진화와 어두운 구석]])에서 `common` 소스 세트에 선언한 `internal`은 그 모듈의 플랫폼별 소스 세트에서도 보인다—모듈 경계가 소스 세트 그룹 전체를 아우르기 때문이다. 즉 `internal`은 특정 백엔드의 기교가 아니라 **언어 수준의 컴파일 단위 규칙**이며, JVM의 이름 맹글링(8절)은 그 언어 규칙을 JVM이라는 특정 플랫폼에서 근사하는 *구현 세부*일 뿐이다. 이 층위 구분—규칙은 언어, 맹글링은 백엔드—을 기억해 두면 8절이 훨씬 명료해진다.

> **명세 정밀**: 자바 `package-private`이 "런타임에 클래스로더·패키지가 일치해야" 성립하는 반면, 코틀린 `internal`은 순수하게 **컴파일 타임** 개념이다. 컴파일이 끝나 바이트코드가 되면 모듈이라는 정보는 (맹글링된 이름의 흔적을 빼면) 사라진다. 그래서 리플렉션이나 바이트코드 조작으로는 `internal` 경계를 손쉽게 넘을 수 있다—1.3절에서 말했듯 가시성은 보안이 아니라 정적 계약이다.

## 6. 선언 위치별 규칙 차이

가시성 한정자는 어디에 붙느냐에 따라 허용 여부와 의미가 달라진다. 3~5절에서 부분적으로 봤지만, 여기서 위치별로 정리한다.

### 6.1 최상위 선언

파일 최상위의 함수·프로퍼티·클래스·타입 별칭에 붙일 수 있는 한정자는 세 개다.

```kotlin
public fun a() {}     // 기본, 어디서나
private fun b() {}    // 같은 파일에서만
internal fun c() {}   // 같은 모듈에서만
// protected fun d() {}  // 에러 — 최상위에 protected 불가
```

- `public`(기본): 이 선언을 볼 수 있는 모든 곳.
- `private`: **같은 파일**(패키지 아님).
- `internal`: **같은 모듈**.
- `protected`: **금지**.

### 6.2 클래스·인터페이스 멤버

클래스 안의 멤버에는 네 한정자가 모두(단, 인터페이스는 public/private만) 붙는다.

```kotlin
open class Widget {
    public val id = 0        // 어디서나 (기본)
    private val cache = 0    // Widget 안에서만
    protected val state = 0  // Widget과 하위 클래스에서만
    internal val debug = 0   // 같은 모듈에서 Widget이 보이는 곳
}
```

여기서 `private`의 스코프는 최상위와 달리 **클래스**다. 같은 단어의 두 얼굴(3.1 vs 3.2)이 이 표에서 확정된다.

### 6.3 생성자 가시성과 constructor 키워드

주 생성자([[21 - 클래스와 생성자]])는 기본이 `public`이다. 가시성을 바꾸려면 `constructor` 키워드를 명시해야 한다—평소엔 생략하던 그 키워드가 한정자를 붙이는 순간 필수가 된다.

```kotlin
// 평소: constructor 생략
class Point(val x: Int, val y: Int)

// private 생성자: constructor 명시 필요
class Registry private constructor() {
    companion object {
        val instance = Registry()   // 내부에서만 만든다 (싱글턴 유도)
    }
}

// val r = Registry()  // 컴파일 에러: constructor is private
```

`private` 생성자는 팩토리 패턴이나 싱글턴 유도([[28 - object와 companion - 싱글턴과 동반 객체]]는 이를 더 우아하게 풀지만)에 쓰인다. `internal constructor`는 "모듈 안에서만 이 클래스를 만들 수 있다"를 뜻해, 라이브러리가 인스턴스 생성을 통제하면서 타입은 노출하고 싶을 때 유용하다.

```kotlin
class Token internal constructor(val value: String)
// 모듈 밖에서는 Token 타입을 받을 수는 있으나 직접 생성 불가 — 팩토리 함수만 노출
```

부 생성자에도 같은 규칙이 적용된다: `protected constructor(...)`, `private constructor(...)` 모두 가능하다.

### 6.4 지역 선언에는 한정자가 없다

함수 본문 안의 지역 변수, 지역 함수, 지역 클래스에는 **가시성 한정자를 붙일 수 없다.** 그것들의 스코프는 이미 자신을 감싼 블록으로 한정되어 있어, 가시성 한정자가 표현할 것이 없기 때문이다.

```kotlin
fun compute(): Int {
    // private val x = 1   // 컴파일 에러: modifier 'private' is not applicable to 'local variable'
    val x = 1              // 지역 변수는 항상 블록 스코프
    fun helper() = x + 1   // 지역 함수도 마찬가지 — 한정자 불가
    return helper()
}
```

지역 선언의 가시성은 **렉시컬 스코프**(어휘적 유효 범위, [[14 - 클로저와 캡처]]와 연결)가 전적으로 결정한다. 한정자는 파일·클래스 수준 선언에만 의미가 있다.

정리하면 위치별 허용 표는 다음과 같다.

| 위치 | public | private | protected | internal |
|------|:---:|:---:|:---:|:---:|
| 최상위 | ✅ | ✅(파일) | ❌ | ✅ |
| 클래스 멤버 | ✅ | ✅(클래스) | ✅ | ✅ |
| 인터페이스 멤버 | ✅ | ✅ | ❌ | ❌ |
| 생성자 | ✅ | ✅ | ✅ | ✅ |
| 지역 | ❌(불가) | ❌ | ❌ | ❌ |

## 7. 세터 가시성과 프로퍼티 비대칭

### 7.1 private set - 읽기 공개, 쓰기 비공개

프로퍼티([[22 - 프로퍼티와 백킹 필드]])는 게터와 세터를 따로 갖는다. 코틀린은 이 둘의 가시성을 **다르게** 정할 수 있게 하여, "읽기는 넓게, 쓰기는 좁게"라는 흔한 비대칭 캡슐화를 한 줄로 표현한다.

```kotlin
class Counter {
    var count: Int = 0
        private set          // 게터는 public, 세터만 private

    fun increment() { count++ }   // 클래스 내부에서는 쓰기 가능
}

val c = Counter()
c.increment()
println(c.count)   // => 1   (읽기 OK)
// c.count = 100   // 컴파일 에러: cannot assign — setter is private
```

`count`는 밖에서 읽을 수 있지만 오직 `increment`를 통해서만 바뀐다. 불변식(invariant)을 클래스가 독점 관리하는 전형적 패턴이다. `internal set`, `protected set`도 같은 방식으로 가능하다.

핵심 제약: **세터는 프로퍼티(게터)보다 더 넓을 수 없다.** 게터가 `private`인데 세터가 `public`인 것은 논리적으로 말이 안 되므로 금지된다. 세터의 가시성은 프로퍼티 가시성보다 같거나 좁아야 한다.

```kotlin
class Bad {
    // private var x = 0
    //     public set    // 컴파일 에러: setter visibility must be at most property visibility
}
```

또 하나: 세터 가시성은 지정할 수 있어도 **게터 가시성은 따로 지정할 수 없다.** 게터의 가시성은 곧 프로퍼티 전체의 가시성이다. 그래서 "게터만 좁히기"는 프로퍼티 자체를 좁히는 것과 같다.

### 7.2 백킹 프로퍼티 패턴 - private set으로 안 되는 경우

`private set`은 "타입은 같고 쓰기만 막기"에 완벽하다. 그러나 때로는 **외부에 노출하는 타입과 내부에서 다루는 타입 자체를 다르게** 하고 싶다. 예컨대 내부에서는 `MutableList`로 다루되 밖에는 읽기 전용 `List`([[38 - 컬렉션 - 읽기 전용과 가변]])로 내놓고 싶을 때. 이때는 `private set`으로 부족하고 **백킹 프로퍼티(backing property)** 패턴을 쓴다.

```kotlin
class TodoBoard {
    private val _tasks = mutableListOf<String>()   // 내부 전용 가변 뷰
    val tasks: List<String> get() = _tasks         // 외부엔 읽기 전용 노출

    fun add(task: String) { _tasks.add(task) }
}

val board = TodoBoard()
board.add("write chapter")
println(board.tasks)     // => [write chapter]
// board.tasks.add("x")  // 컴파일 에러: List에는 add가 없다
```

`_tasks`(관례적으로 밑줄 접두사)는 `private`이라 밖에서 보이지 않고, `tasks`는 그것을 `List`로 상향 노출한다. `private set`은 "같은 타입, 쓰기 차단"이고, 백킹 프로퍼티는 "다른 타입, 능력 자체 차단"이다. 둘의 차이를 구분하는 것이 실무 캡슐화의 핵심이다. (읽기 전용 `List`가 진짜 불변은 아니라는 함정 M26·M27은 [[38 - 컬렉션 - 읽기 전용과 가변]]이 다룬다—여기서 `_tasks`를 노출하지 않는 것이 그 함정을 막는 실천이다.)

## 8. JVM 백엔드에서의 표현 - 이름 맹글링과 상호운용

지금까지의 규칙은 언어 수준의 추상이다. 그런데 코틀린이 JVM 바이트코드로 컴파일될 때, JVM에는 `internal`도, "파일 스코프"도, 코틀린식 `protected`도 정확히 대응하는 개념이 없다. 코틀린은 이 간극을 여러 우회로 메운다. 이 절은 JVM 백엔드 한정 이야기다(Native/JS/Wasm 백엔드는 각자 다른 방식을 쓴다).

### 8.1 각 한정자의 바이트코드 매핑

JVM 백엔드에서 대략 다음과 같이 내려간다(구현·JVM 타깃 버전에 따라 세부는 달라질 수 있다).

| 코틀린 | JVM 바이트코드 표현 | 비고 |
|--------|---------------------|------|
| `public` 멤버 | `public` | 그대로 |
| `private` 멤버 | `private` | 그대로 (단 중첩 접근은 8.4) |
| `protected` 멤버 | `protected` | JVM protected는 패키지 접근 포함 → 4.2 누수 |
| `internal` 멤버 | `public` + **이름 맹글링** | JVM에 모듈 개념 없음 → 8.2 |
| 최상위 `private` | 파일 파사드 클래스의 제한 멤버 | 파일 스코프를 클래스 스코프로 근사 |
| `internal` 클래스 | `public` 클래스 (경고 동반) | 클래스 이름은 맹글링 안 됨 |

두 항목이 특히 흥미롭다: `internal`은 JVM에 대응물이 없어서 **`public`으로 컴파일된 뒤 이름을 뒤틀어** 접근을 억제하고, `protected`는 JVM protected가 더 넓어서 **의도보다 새어 나간다.**

### 8.2 internal의 이름 맹글링

`internal` 함수·프로퍼티 접근자는 JVM 바이트코드에서 이름에 모듈 이름이 접미사로 붙는다. 대략 `함수이름$모듈이름` 형태다.

```kotlin
// Kotlin, 모듈 이름이 "app"이라고 하자
internal fun calculate(x: Int): Int = x * 2
```

이 함수는 JVM에서 대략 다음처럼 보인다.

```java
// 개념적으로 디컴파일된 모습 (모듈명·구분자 세부는 구현에 따라 다름)
public static final int calculate$app(int x) { return x * 2; }
```

**왜 맹글링하는가?** 두 가지 목적이다.

첫째, **자바에서 실수로 부르거나 오버라이드하는 것을 억제**한다. `internal`은 "모듈 밖에서 쓰지 말 것"이라는 계약인데, JVM `public`으로 그냥 두면 자바 코드가 `calculate(x)`를 태연히 호출할 수 있다. 이름을 `calculate$app`으로 뒤틀어 두면 자바 개발자가 우연히 그 이름을 타이핑할 일이 없어 사실상 감춰진다. (완벽한 차단은 아니다—맹글링된 이름 `calculate$app`을 자바에서 직접 쓰면 여전히 호출된다. 강제가 아니라 억제다.)

둘째, **시그니처 충돌 방지**다. 서로 다른 모듈이 우연히 같은 이름의 `internal` 멤버를 갖더라도, 모듈명 접미사가 다르면 JVM 수준에서 충돌하지 않는다.

```text
  모듈 "core"의  internal fun helper()  →  helper$core
  모듈 "ui"의    internal fun helper()  →  helper$ui
                              ↑ JVM에서 이름이 달라 충돌하지 않음
```

> **명세 정밀**: 맹글링되는 것은 **함수와 프로퍼티 접근자**이지 **클래스 이름**이 아니다. `internal class Foo`는 JVM에서 그냥 `public class Foo`가 되고 이름이 뒤틀리지 않는다. 그래서 자바 코드가 `internal` 클래스 자체는 이름으로 참조할 수 있다(코틀린 컴파일러가 경고를 낼 수 있지만 JVM 차원에서는 열려 있다). 이 비대칭—멤버는 맹글링, 클래스는 노출—은 코틀린 가시성 보장이 자바 상호운용에서 완벽하지 않음을 보여 준다. 완전한 격리가 필요하면 JPMS나 별도 배포 단위를 써야 한다.

### 8.3 자바에서 본 코틀린 가시성 요약

자바 코드가 코틀린 코드를 볼 때 각 한정자가 어떻게 나타나는지 정리하면([[45 - Java 상호운용]]의 축약판):

- `public` → 자바에서도 그대로 `public`.
- `private` 멤버 → 자바에서도 `private`(접근 불가).
- `protected` → 자바 `protected`(그런데 자바는 **같은 패키지에서도 접근**되므로 코틀린 의도보다 넓게 열림).
- `internal` → 자바에서는 **맹글링된 이름의 `public`**으로 보임(억제되지만 뚫을 수는 있음).
- 최상위 `private` → 자바에서 접근 불가(파일 파사드 클래스에 갇힘).

핵심 교훈: **코틀린의 가시성 보장은 코틀린→코틀린 방향에서는 견고하지만, 자바→코틀린 방향에서는 JVM의 표현 한계 때문에 느슨해진다.** `internal`은 억제일 뿐 강제가 아니고, `protected`는 패키지로 새며, `internal` 클래스는 열려 있다. 이 틈을 아는 것이 상호운용 코드의 방어선을 세우는 출발점이다.

### 8.4 private 멤버와 중첩 접근 - 합성 접근자와 nestmate

3.4절에서 이너 클래스가 바깥의 `private`에 접근함을 봤다. 그런데 JVM의 전통적 규칙에서는 한 클래스의 `private` 멤버를 *다른 클래스*(중첩 클래스도 JVM에서는 별개 클래스다)가 직접 접근할 수 없었다. 코틀린(그리고 자바)은 이 간극을 두 방식 중 하나로 메운다.

- **합성 접근자(synthetic accessor)**: 컴파일러가 `access$getSecret$p(...)` 같은 패키지 수준 다리 메서드를 자동 생성해, 중첩 클래스가 그 다리를 통해 바깥의 private에 닿는다. 오래된 방식이다.
- **네스트메이트(nestmate) 기반 접근**: JVM 11부터 도입된 nest-based access control을 쓰면, 중첩 관계에 있는 클래스들이 서로의 private에 합성 다리 없이 직접 접근할 수 있다. 코틀린도 충분히 최신 JVM 타깃에서는 이 방식을 활용할 수 있다.

어느 방식이 쓰이는지는 **컴파일러 버전과 JVM 타깃 버전에 따라 다르다.** 학습자가 기억할 것은 결과다: 소스 수준에서는 "이너 클래스가 바깥의 private을 자연스럽게 본다"는 규칙이 성립하고, 그 뒤에서 컴파일러가 JVM의 제약을 우회하는 기계 장치를 깔아 준다. 이 세부는 언어 명세가 아니라 백엔드 구현 재량이므로 "구현에 따라 다름"으로 남겨 두는 것이 정확하다.

```text
  [소스 수준]                    [JVM 백엔드가 까는 기계]
  Inner.reveal() → Outer.secret   ─┬─ (구식) Outer.access$getSecret 다리 호출
                                    └─ (신식) nestmate 직접 접근 (JVM 11+)
```

## 9. 가시성은 관계다 - 노출 규칙과 오버라이드

마지막 절은 가시성의 가장 미묘한 측면을 다룬다. 지금까지 가시성을 "선언 하나에 붙는 라벨"로 봤지만, 실제 규칙은 **선언들 사이의 관계**를 강제한다. 좁게 감춘 것을 넓은 선언이 노출하면 캡슐화가 뚫리기 때문이다.

### 9.1 오버라이드는 가시성을 좁힐 수 없다

하위 클래스가 상위의 멤버를 오버라이드([[24 - 상속과 오버라이딩과 초기화 순서]])할 때, 오버라이드한 멤버의 가시성은 **원본보다 좁을 수 없다.** 같거나 넓어야 한다.

```kotlin
open class Base {
    protected open fun step() {}
}

class Derived : Base() {
    public override fun step() {}   // OK — protected를 public으로 넓힘
    // private override fun step() {}  // 컴파일 에러: cannot narrow visibility
}
```

이유는 **리스코프 치환 원칙(Liskov Substitution)** 이다. `Base` 타입으로 `Derived` 인스턴스를 다룰 때 `step`이 protected로 접근 가능해야 하는데, 하위가 그것을 `private`으로 좁히면 그 계약이 깨진다. 그래서 넓히기(protected→public)는 허용, 좁히기(protected→private)는 금지다. 오버라이드 시 한정자를 생략하면 원본의 가시성을 그대로 상속한다.

### 9.2 public 선언은 덜 보이는 타입을 노출할 수 없다

가장 중요한 관계 규칙: **어떤 선언은 자신보다 가시성이 좁은 타입을 자신의 공개 시그니처에 노출할 수 없다.** `public` 함수가 `internal` 타입을 반환하거나 파라미터로 받으면 컴파일 에러다.

```kotlin
internal class InternalConfig(val port: Int)

// public 함수가 internal 타입을 노출 — 에러
// public fun loadConfig(): InternalConfig = InternalConfig(8080)
//   컴파일 에러: 'public' function exposes its 'internal' return type InternalConfig

// 해결책 1: 함수를 internal로 좁힌다
internal fun loadConfig(): InternalConfig = InternalConfig(8080)

// 해결책 2: public 인터페이스로 노출하고 internal 구현은 감춘다
interface Config { val port: Int }
internal class InternalConfigImpl(override val port: Int) : Config
fun loadConfigPublic(): Config = InternalConfigImpl(8080)  // OK
```

왜 이 규칙이 필요한가? 만약 `public fun loadConfig(): InternalConfig`가 허용된다면, 모듈 밖 사용자가 `loadConfig()`를 호출해 `InternalConfig` 타입의 값을 손에 쥐게 된다. 그런데 그 타입은 `internal`이라 이름조차 쓸 수 없다—사용자는 "이름 없는 타입의 값"을 받아 아무것도 못 하는 모순에 빠진다. 컴파일러는 이 모순을 미리 막는다. **가시성은 선언 하나의 속성이 아니라 시그니처 전체가 형성하는 도달 가능성의 그물**이라는 것을 이 규칙이 증명한다.

같은 원리가 `private` 필드가 `public` 함수를 통해 새는 것도 막고, 프로퍼티 타입, 상위 타입, 제네릭 인자([[33 - 제네릭 1 - 타입 파라미터와 변성]])에도 적용된다.

> **명세 정밀**: 노출 규칙은 "선언의 가시성 ≤ 그 시그니처에 등장하는 모든 타입의 가시성"으로 요약된다. 즉 어떤 선언도 자신보다 감춰진 타입을 자신의 공개 얼굴에 담을 수 없다. 이 규칙 덕분에 "public API만 따라가면 필요한 모든 타입에 도달할 수 있다"는 폐쇄성(closure)이 보장된다. 캡슐화가 부분적으로 뚫린 채 방치되는 상황을 언어가 원천 차단한다.

### 9.3 explicit API mode - 라이브러리를 위한 엄격 모드

2절에서 예고한 안전망을 마무리하자. 라이브러리 저자는 컴파일러 옵션 `-Xexplicit-api={strict|warning}`으로 **explicit API mode**를 켤 수 있다. 이 모드에서는 public/protected 선언에 대해 다음을 강제한다.

- **가시성 한정자 명시 필수**: `public`을 생략할 수 없다. "실수로 public이 된" 선언이 사라진다—모든 public은 의도적으로 타이핑된 것이어야 한다.
- **반환 타입 명시 필수**: public 선언의 반환 타입을 추론에 맡기지 못하고 적어야 한다. 리팩터링 중 반환 타입이 슬쩍 바뀌어 API가 깨지는 것을 막는다.

```kotlin
// explicit API mode (strict)에서:
fun helper() = 42          // 경고/에러: public 선언에 가시성·반환 타입 명시 필요
public fun helper2(): Int = 42   // OK — 의도가 명시됨
private fun helper3() = 42        // OK — public이 아니므로 규칙 면제
```

이 모드는 2절에서 지적한 "기본값이 public이라 API 표면이 부주의하게 부푼다"는 위험의 해독제다. 애플리케이션 코드에서는 보통 끄지만, 공개 라이브러리에서는 켜서 모든 공개 표면을 의식적으로 관리한다. [[46 - 멀티플랫폼과 진화와 어두운 구석]]에서 다룰 "안정적 공개 API 관리"의 실천적 도구 중 하나다.

---

가시성 한정자는 키워드 네 개짜리 얕은 주제처럼 보였지만, 그 아래에는 캡슐화의 철학과 JVM의 물리적 한계가 팽팽히 맞서는 지형이 있었다. 코틀린은 흔한 경우를 짧게 하려고 `public`을 기본으로 골랐고(2절), 그 대가인 API 표면 팽창을 explicit API mode로 상쇄했다(9.3절). `private`은 위치에 따라 파일 스코프와 클래스 스코프라는 두 얼굴을 갖고(3절), 같은 클래스의 다른 인스턴스는 보되 중첩 클래스로는 한 방향으로만 흐르는 비대칭을 지녔다(3.3~3.4절). `protected`는 자바의 패키지 접근을 떼어 내 하위 클래스 전용으로 좁혔지만, JVM 표현의 한계로 자바 쪽에서 다시 새어 나갔다(4.2절). 그리고 이 장의 핵심 `internal`은 자바의 package-private과 근본적으로 다른 것—패키지가 아니라 **모듈**이라는 컴파일 단위—을 재는 자였다(M44, 5절). JVM에는 모듈이 없기에 코틀린은 이름 맹글링이라는 우회로 `internal`을 근사했고(8.2절), 그 근사의 틈이 상호운용의 함정을 낳았다. 마지막으로 가시성은 선언 하나의 라벨이 아니라 시그니처 전체가 형성하는 도달 가능성의 그물임을(9절)—좁게 감춘 것을 넓은 얼굴로 노출할 수 없다는 규칙을 통해—확인했다. "누가 이 이름을 볼 수 있는가"라는 단순한 질문이, 실은 언어 설계·컴파일러 구현·플랫폼 한계가 만나는 교차로였던 셈이다.

## 핵심 요약

- **코틀린의 기본 가시성은 `public`이며, 자바의 package-private 기본값과 정반대다.** "흔한 경우는 짧게"라는 실용주의의 결과로, 대가인 API 표면 팽창은 explicit API mode로 상쇄한다.
- **`internal`은 자바 package-private이 아니라 "모듈(컴파일 단위)" 가시성이다 (M44).** 패키지를 가로질러도 같은 모듈이면 보이고, 같은 패키지여도 다른 모듈이면 안 보인다—패키지와 모듈은 직교하는 다른 축이다.
- **모듈은 파일도 패키지도 프로젝트도 아니라 "한 번에 함께 컴파일되는 파일들의 집합"이다.** Gradle 소스 세트, Maven 프로젝트, IntelliJ 모듈 등이 각각 하나의 모듈이며, `test` 소스 세트가 `main`의 `internal`을 보는 예외가 있다.
- **최상위 `private`은 파일 스코프, 멤버 `private`은 클래스 스코프로 같은 단어가 다른 경계를 뜻한다.** 최상위 private은 같은 패키지의 다른 파일에서도 안 보인다.
- **`private`은 인스턴스가 아니라 클래스가 경계라서, 같은 클래스의 다른 인스턴스의 private에는 접근할 수 있다.** 이 규칙이 없으면 `equals`·산술 연산 오버로딩을 private 필드로 구현할 수 없다.
- **중첩·이너 클래스는 바깥의 private을 보지만, 바깥은 중첩의 private을 못 본다 (자바와 반대의 한 방향 흐름).** 자바는 양방향 공유, 코틀린은 안→밖 방향만 허용한다.
- **코틀린 `protected`는 자바와 달리 패키지 접근이 없고 하위 클래스 전용이다.** 그러나 JVM protected로 컴파일되면서 같은 패키지의 자바 코드에는 다시 노출되는 상호운용 누수가 있다 (M8·M44 참조, [[45 - Java 상호운용]]).
- **`protected`는 최상위 선언과 인터페이스 멤버에 쓸 수 없다.** 최상위엔 상속 개념이 없고, 인터페이스는 public/private만 허용한다. 지역 선언에는 네 한정자 모두 붙지 못한다.
- **세터 가시성은 `private set` 등으로 게터보다 좁게(같거나 좁게) 지정할 수 있지만 넓게는 못 한다.** "읽기는 공개, 쓰기는 비공개"의 비대칭 캡슐화가 한 줄로 표현된다.
- **생성자는 기본 public이며 가시성을 바꾸려면 `constructor` 키워드를 명시해야 한다.** `private constructor`로 싱글턴·팩토리를, `internal constructor`로 모듈 내부 생성 통제를 구현한다.
- **JVM 백엔드에서 `internal`은 `public` + 이름 맹글링(`foo$module`)으로 근사되어 자바 접근을 억제할 뿐 강제 차단하지는 않으며, `internal` 클래스 이름은 맹글링되지 않아 열려 있다.** 코틀린 가시성 보장은 코틀린→코틀린에서는 견고하나 자바→코틀린에서는 느슨하다.
- **가시성은 선언 하나의 속성이 아니라 관계의 속성이다.** public 선언은 더 좁은 타입을 시그니처에 노출할 수 없고, 오버라이드는 가시성을 좁힐 수 없다(넓히기만 가능)—이로써 "public API만 따라가면 필요한 모든 타입에 도달한다"는 폐쇄성이 보장된다.

## 연결 노트

- [[25 - 인터페이스]] — 인터페이스 멤버에는 public/private만 허용되고 protected/internal이 금지되는 이유(상태 없는 계약 M37)가 이 장의 가시성 규칙과 맞물린다.
- [[24 - 상속과 오버라이딩과 초기화 순서]] — 오버라이드 시 가시성을 좁힐 수 없다는 규칙(9.1절)의 상속 측면과 초기화 순서를 소유한다.
- [[22 - 프로퍼티와 백킹 필드]] — `private set`과 백킹 프로퍼티 패턴(7절)이 게터/세터가 백킹 필드로 컴파일되는 방식(M35) 위에서 작동한다.
- [[21 - 클래스와 생성자]] — 생성자 가시성과 `constructor` 키워드(6.3절)가 이 장의 토대이며, `private constructor`로 인스턴스 생성을 통제한다.
- [[28 - object와 companion - 싱글턴과 동반 객체]] — `private constructor` + companion 팩토리로 유도하던 싱글턴을 더 우아하게 언어 차원에서 해결한다(M24·M25).
- [[31 - 중첩 클래스와 이너 클래스와 익명 객체]] — 중첩·이너 클래스의 private 접근 비대칭(3.4절)이 이들이 바깥 인스턴스를 참조하는 방식과 어떻게 연결되는지 다룬다.
- [[45 - Java 상호운용]] — `internal` 이름 맹글링, `protected` 패키지 누수, 최상위 private의 파일 파사드 등 JVM 상호운용 함정(8절)의 총람 (M8·M44).
- [[38 - 컬렉션 - 읽기 전용과 가변]] — 백킹 프로퍼티로 `MutableList`를 `List`로 감추는 패턴(7.2절)이 읽기 전용 ≠ 불변(M26·M27)이라는 함정과 이어진다.
- [[46 - 멀티플랫폼과 진화와 어두운 구석]] — explicit API mode(9.3절)와 안정적 공개 API 관리, 그리고 가시성 보장이 플랫폼별로 달라지는 어두운 구석을 종합한다.
- [[04 - 파일과 패키지와 선언 - 프로그램의 골격]] — 패키지가 가시성 경계가 아니라 이름 정리 수단이라는 이 장의 전제가 파일·패키지 구조 위에서 성립한다.
