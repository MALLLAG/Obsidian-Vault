[[25 - 인터페이스]]에서는 계약(contract)을 다뤘다. 인터페이스는 "무엇을 할 수 있는가"를 선언하고, "어떻게 하는가"는 구현 클래스에 맡긴다. 그런데 인터페이스가 드러내는 계약의 *바깥쪽* 경계, 즉 "누가 이 선언을 볼 수 있는가"라는 질문은 인터페이스 문법과는 별개로 결정된다. 이것이 이 장의 주제인 **가시성(visibility)** 이다.

객체 지향에서 오래전부터 강조해 온 캡슐화(encapsulation)는 "내부를 감추고 계약만 드러낸다"로 요약할 수 있다. 가시성 한정자는 이 "감춤"을 정밀하게 표현하는 문법 장치다.

이 장에서는 **선언을 어디에서 참조할 수 있는가**를 결정하는 네 한정자 `public`, `private`, `protected`, `internal`의 의미와 규칙 차이를 다룬다. 오버라이딩할 때 가시성을 좁히거나 넓히는 규칙은 여기서 정리하고, 초기화 순서와의 상호작용은 [[24 - 상속과 오버라이딩과 초기화 순서]]에서 다룬다.

프로퍼티의 게터와 세터가 어떤 백킹 필드로 컴파일되는지는 [[22 - 프로퍼티와 백킹 필드]]에서, 중첩 클래스와 이너 클래스가 바깥 인스턴스를 참조하는 방식은 [[31 - 중첩 클래스와 이너 클래스와 익명 객체]]에서, `internal`이 자바 쪽에서 어떤 맹글링된 이름으로 보이는지를 포함한 상호운용 전반은 [[45 - Java 상호운용]]에서 설명한다.

특히 5절과 8절이 중요하다. 5절에서는 "`internal`은 자바의 package-private이다"라는 흔한 오해를 바로잡으면서 "모듈"이라는 단위를 정의한다. 8절에서는 이 규칙이 JVM 백엔드에서 어떤 바이트코드와 이름 맹글링으로 구현되는지, 그리고 그 과정에서 코틀린의 가시성 보장이 자바 상호운용을 통해 어떻게 깨지는지 확인한다.

가시성은 겉보기에는 키워드 네 개만 외우면 끝나는 단순한 주제 같다. 그러나 그 아래에는 "컴파일 단위란 무엇인가", "JVM에는 모듈 개념이 없는데 코틀린은 이를 어떻게 구현하는가", "가시성은 선언의 속성인가, 관계의 속성인가" 같은 질문이 깔려 있다.

## 1. 왜 가시성인가: 캡슐화와 네 개의 한정자

### 1.1 가시성이 해결하는 문제

가시성 한정자는 "이 선언을 코드베이스의 어디에서 이름으로 참조할 수 있는가"를 컴파일러가 강제하게 하는 장치다. 목적은 단순한 접근 제어가 아니라 **어디까지 자유롭게 바꿀 수 있는지 경계를 정하는 것**이다. `private`으로 감춘 선언은 아무도 그 이름에 의존할 수 없으므로 언제든 자유롭게 바꿀 수 있다. 반면 `public`으로 드러낸 선언은 계약이 된다. 누군가 그 선언에 의존하기 시작하면, 함부로 바꿨을 때 그 사람의 코드가 깨진다.

이런 관점에서 가시성은 미래의 자신과 협업자에게 보내는 신호다.

```kotlin
class BankAccount(initial: Long) {
    var balance: Long = initial
        private set              // 읽기는 공개, 쓰기는 클래스 내부에서만

    private var pin: String = ""  // 완전히 감춤: 밖에서 존재조차 모른다

    fun deposit(amount: Long) {
        require(amount > 0)
        balance += amount         // 내부에서는 자유롭게 변경
    }
}

val acc = BankAccount(1000)
println(acc.balance)   // => 1000  (읽기 허용)
// acc.balance = 5000  // 컴파일 에러: cannot assign, setter is private
// acc.pin            // 컴파일 에러: pin is private in BankAccount
```

`pin`을 `private`으로 감췄으므로, 나중에 이 필드를 삭제하고 해시로 대체하든 외부 서비스로 옮기든 `BankAccount`를 사용하는 쪽은 아무 영향도 받지 않는다. 반대로 `balance`는 `public`으로 노출한 순간 그 이름과 타입이 계약이 되었다.

### 1.2 네 한정자 개관

코틀린의 가시성 한정자는 정확히 네 개다.

| 한정자 | 한 줄 정의 | 최상위 허용 | 멤버 허용 |
|--------|-----------|:----------:|:--------:|
| `public` | 어디서나 보임 (기본값) | ✅ | ✅ |
| `private` | 최상위=같은 파일 / 멤버=같은 클래스 | ✅ | ✅ |
| `protected` | 해당 클래스와 하위 클래스에서만 | ❌ | ✅ |
| `internal` | 같은 모듈 안에서 보임 | ✅ | ✅ |

표에서 바로 눈에 띄는 비대칭이 두 가지 있다. 첫째, `protected`는 **최상위 선언에 붙일 수 없다**. 클래스에 속하지 않는 최상위 함수에는 "하위 클래스"라는 개념이 의미가 없기 때문이다. 둘째, `private`은 최상위와 멤버에서 *같은 단어로 다른 스코프*를 뜻한다. 이 두 비대칭을 3절과 4절에서 자세히 다룬다.

> [!note] 명세 기준
> 코틀린은 자바나 C#과 달리 가시성 한정자를 **조합할 수 없다**. C#에는 `protected internal`(protected 또는 같은 어셈블리)과 `private protected`(protected 그리고 같은 어셈블리)라는 조합이 있지만, 코틀린에서는 네 한정자 중 정확히 하나만 붙인다. `protected internal fun f()`는 컴파일 에러다. 이 단순함은 의도된 설계이며, "가시성은 하나의 축"이라는 규칙을 지킨다.

### 1.3 가시성은 컴파일 타임 계약이다

여기서 강조할 점이 있다. 가시성은 **컴파일 타임에만** 검사된다. `private` 필드도 런타임에는 리플렉션([[44 - 애노테이션과 리플렉션]]에서 다룬다)이나 JVM의 저수준 접근으로 얼마든지 읽을 수 있다. 가시성은 실행 시점의 보안 장벽이 아니라, *컴파일러가 실수를 막아 주는 정적 계약*이다.

```kotlin
class Secret(private val token: String)

val s = Secret("abc")
// s.token  // 컴파일 에러 — 하지만 이는 정적 검사일 뿐

// 리플렉션으로는 뚫린다 (JVM 백엔드, 개념 예시):
val field = Secret::class.java.getDeclaredField("token")
field.isAccessible = true
println(field.get(s))  // => abc  — 가시성은 보안이 아니다
```

이 사실은 실무에서 중요하다. `private`으로 감춘 값은 "설계상 아무도 건드리지 말 것"이라는 *약속*이지, 암호학적으로 안전한 비밀 보관소가 아니다. 민감한 데이터는 가시성이 아니라 별도의 보안 메커니즘으로 보호해야 한다. 가시성이 제공하는 것은 **컴파일 타임에 잘못된 의존을 차단하는 기능** 하나뿐이다.

## 2. public: 기본값이자 최대 노출

### 2.1 명시할 필요가 없는 한정자

코틀린에서는 한정자를 아무것도 쓰지 않으면 `public`이다. 이 점이 자바와 **결정적으로 다르다**. 자바는 아무것도 쓰지 않으면 package-private(같은 패키지에서만 보임)이 기본인데, 코틀린은 가장 넓게 노출하는 `public`이 기본이다.

```kotlin
// 이 두 선언은 정확히 동등하다
fun greet() = "hello"
public fun greet2() = "hello"

class Circle(val radius: Double) {
    fun area() = Math.PI * radius * radius        // public
    public fun area2() = Math.PI * radius * radius // 위와 동등, 불필요한 명시
}
```

`public` 키워드를 명시하는 것은 문법상 허용되지만 관례상 생략한다. 코틀린 스타일 가이드도 "기본값과 같은 한정자는 쓰지 말라"고 권한다. 그래서 실제 코틀린 코드에서는 `public`이라는 단어를 보기 드물다. 모든 곳에 적용되어 있기 때문에 오히려 눈에 보이지 않는 것이다.

### 2.2 왜 최대 노출을 기본값으로 골랐는가

이 선택에는 논란이 있다. "안전한 기본값(secure by default)" 관점에서는 캡슐화를 위해 가장 좁은 가시성을 기본으로 삼는 편이 낫다. 자바의 package-private 기본값과 러스트의 "기본은 private" 정책이 이런 철학을 따른다. 그렇다면 코틀린은 왜 반대로 갔을까?

첫째, **실용성** 때문이다. 코틀린은 애플리케이션 코드에서 대부분의 선언이 결국 어딘가에서 쓰이기 위해 존재한다고 봤다. 매번 `public`을 입력하게 만드는 것은 가장 흔한 경우에 비용을 물리는 셈이다. "흔한 경우는 짧게, 드문 경우는 명시적으로"라는 코틀린의 일관된 철학이 여기서도 적용된다. [[21 - 클래스와 생성자]]에서 본 생성자 설계도 같은 철학에서 나왔다.

둘째, 코틀린에는 자바의 package-private에 정확히 대응하는 개념이 **아예 없다**. 자바의 기본값은 패키지 스코프인데, 코틀린은 패키지를 가시성 경계로 삼지 않기로 했다(5절). 그래서 package-private을 기본값으로 삼을 수조차 없었고, 남은 자연스러운 후보가 `public`이었다.

그 대가는 분명하다. 라이브러리를 만들 때 개발자가 주의하지 않으면 **의도하지 않게 API 표면이 커진다**. 감춰야 할 헬퍼 함수가 `public`으로 노출되어 외부 코드가 의존하기 시작하면, 나중에 그 함수를 바꾸기 어려워진다. 코틀린은 이 위험을 알고 라이브러리 작성자를 위한 안전장치인 **explicit API mode**를 따로 마련했다(9절).

> [!warning] 흔한 오해
> "코틀린은 기본값이 `public`이라 캡슐화에 약하다"는 말은 절반만 맞다. 애플리케이션 코드에서는 확실히 선언이 과하게 노출되기 쉽다. 하지만 라이브러리 코드에서는 explicit API mode(`-Xexplicit-api=strict`)를 켜면 public 선언에 명시적 한정자와 반환 타입을 *강제*할 수 있으므로, 오히려 자바보다 엄격한 규칙을 적용할 수 있다. 기본값이 느슨하다는 것과 언어가 캡슐화를 지원하지 않는다는 것은 별개의 문제다.

## 3. private: 최상위와 멤버에서 다른 의미

`private`은 가장 강하게 감추는 한정자지만, 정확히 무엇을 감추는지는 **선언이 놓인 위치**에 따라 완전히 달라진다. 같은 단어가 두 가지 스코프를 가리킨다.

### 3.1 최상위 private = 파일 스코프

파일의 최상위(top-level)에 놓인 `private` 선언은 **그 파일 안에서만** 보인다. 경계는 패키지가 아니라 *파일*이다.

```kotlin
// ==== geometry.kt ====
private const val PI = 3.14159       // 이 파일 안에서만
private fun square(x: Double) = x * x // 이 파일 안에서만

fun circleArea(r: Double) = PI * square(r)  // OK — 같은 파일

// ==== main.kt ====  (같은 패키지라 해도)
fun test() {
    // circleArea(2.0)  // OK — public
    // square(2.0)      // 컴파일 에러: square is private in file geometry.kt
    // println(PI)      // 컴파일 에러
}
```

여기서 중요한 사실은 `main.kt`가 `geometry.kt`와 *같은 패키지*에 있어도 `square`와 `PI`에 접근할 수 없다는 점이다. 최상위 `private`의 경계는 패키지가 아니라 **파일**이기 때문이다. 자바에는 이에 정확히 대응하는 개념이 없다. 자바에는 "파일 스코프 private 함수"가 없다. 자바의 최상위에는 클래스만 올 수 있으므로, 파일 스코프의 자유 함수라는 것 자체가 존재하지 않는다.

파일 스코프 `private`은 실무에서 매우 유용하다. 한 파일 안에서만 쓰는 헬퍼 함수나 상수, 심지어 보조 클래스까지 파일 안에 가둬 두면 파일 밖의 네임스페이스를 어지럽히지 않는다.

```kotlin
// ==== rational.kt ====
private fun gcd(a: Long, b: Long): Long =
    if (b == 0L) a else gcd(b, a % b)  // 이 파일 전용 유틸

class Rational(numerator: Long, denominator: Long) {
    private val g = gcd(numerator, denominator)  // 파일 private을 자유롭게 사용
    val num = numerator / g
    val den = denominator / g
}
```

`gcd`는 `Rational`을 구현하는 데만 쓰는 도구이므로 파일 안에 가둔다. 다른 파일에서 `gcd`라는 이름을 다시 써도 충돌하지 않는다.

### 3.2 멤버 private = 클래스 스코프

클래스나 인터페이스 안의 `private` 멤버는 **그 멤버를 선언한 클래스의 본문 전체**에서 보인다. 여기서 "본문 전체"에는 그 클래스의 모든 멤버 함수, 프로퍼티 초기화자, `init` 블록, 그리고 **중첩 클래스의 본문**까지 포함된다(3.4절).

```kotlin
class Stack<T> {
    private val items = mutableListOf<T>()   // 클래스 내부에서만
    private var topIndex = -1

    fun push(item: T) {
        items.add(item)      // OK
        topIndex++           // OK
    }
    fun pop(): T {
        val v = items[topIndex]
        items.removeAt(topIndex)
        topIndex--
        return v
    }
}

val s = Stack<Int>()
s.push(1)
// s.items  // 컴파일 에러: items is private in Stack
```

`items`와 `topIndex`는 `Stack`의 구현 세부 사항이다. 리스트를 배열로 바꾸든 인덱스를 추적하는 방식을 바꾸든, 외부에서는 `push`/`pop`이라는 계약만 보므로 영향을 받지 않는다. 캡슐화를 교과서대로 구현한 예다.

### 3.3 같은 클래스의 다른 인스턴스에 접근하기

미묘하지만 중요한 규칙이 있다. `private`의 범위는 "이 인스턴스"가 아니라 "이 클래스"다. 그래서 **같은 클래스의 다른 인스턴스**가 가진 private 멤버에도 접근할 수 있다. 이 점은 자바와 같다.

```kotlin
class Money(private val cents: Long) {
    // 다른 Money 인스턴스의 private cents를 읽는다 — 허용됨
    operator fun plus(other: Money) = Money(this.cents + other.cents)
    fun isMoreThan(other: Money) = this.cents > other.cents
    override fun toString() = "$${cents / 100}.${cents % 100}"
}

val a = Money(1500)
val b = Money(250)
println(a + b)            // => $17.50  — other.cents 접근이 정상 동작
println(a.isMoreThan(b))  // => true
```

`plus` 안에서 `other.cents`에 접근하는 것은 완전히 합법이다. `cents`는 "이 인스턴스에서만 비공개"가 아니라 "`Money` 클래스 안에서만 접근 가능"하기 때문이다. 이 규칙이 없다면 `equals`, `compareTo`, 산술 연산자 오버로딩([[19 - 연산자 오버로딩과 관례]])처럼 두 인스턴스를 비교하거나 결합하는 연산을 private 필드로 구현할 수 없다.

> [!note] 명세 기준
> 가시성 스코프의 단위는 "런타임 객체"가 아니라 "정적인 선언 위치"다. `private`은 소스 코드의 어느 텍스트 영역에서 이름을 쓸 수 있는지를 정하는 규칙이지, 어떤 힙 객체가 다른 힙 객체를 건드릴 수 있는지를 정하는 규칙이 아니다. 그래서 인스턴스 경계가 아니라 클래스 선언 경계를 기준으로 동작한다.

### 3.4 중첩 클래스와 private의 비대칭 (자바와 다른 점)

자바 개발자가 놀라는 규칙이 하나 있다. 코틀린에서 **중첩 클래스와 이너 클래스는 바깥 클래스의 private 멤버에 접근할 수 있지만, 바깥 클래스는 중첩 클래스의 private 멤버에 접근할 수 없다.** 접근이 한 방향으로만 허용된다.

```kotlin
class Outer {
    private val secret = 42

    inner class Inner {
        fun reveal() = secret       // OK — 안쪽이 바깥의 private을 봄
    }

    class Nested {
        private val hidden = 99
        fun show() = hidden         // OK — 자기 자신의 private
    }

    fun peek(n: Nested): Int {
        // return n.hidden          // 컴파일 에러: hidden is private in Nested
        return n.show()             // public 통해서만
    }
}
```

`Inner`(그리고 `Nested`)는 `Outer.secret`을 볼 수 있다. 그러나 `Outer`는 `Nested.hidden`을 보지 못한다. 이것은 자바와 정반대다. **자바에서는 최상위 클래스와 그 안의 모든 중첩 클래스가 서로의 private을 양방향으로 공유**한다. 코틀린은 이 공유를 안쪽에서 바깥쪽으로 향하는 한 방향으로만 허용한다.

```java
// Java — 양방향 접근이 합법
class Outer {
    private int secret = 42;
    class Inner {
        private int hidden = 99;
        void f() { System.out.println(secret); }  // OK
    }
    void g(Inner i) { System.out.println(i.hidden); }  // Java에선 OK! (코틀린에선 에러)
}
```

이 차이의 근거는 코틀린 명세의 `private` 정의에 있다. 명세는 "클래스 `C`의 private 멤버 `D`는 `C`의 본문 안에서 보이며, 여기에는 `C`의 멤버 본문과 `C`의 *중첩 분류자(nested classifier) 본문*이 포함된다"고 규정한다. 즉 private이 보이는 영역은 선언한 분류자의 안쪽 방향으로만 넓어진다.

`Nested`의 private은 `Nested` 안쪽에서만 보이고, 그 바깥인 `Outer`로는 드러나지 않는다. 반대로 `Outer`의 private은 중첩 클래스를 포함한 `Outer`의 안쪽 전체에서 보인다.

> [!warning] 흔한 오해
> "중첩 클래스는 바깥 클래스의 일부이므로 private을 자유롭게 공유한다"는 자바식 직관은 코틀린에서 절반만 맞다. 안쪽에서 바깥쪽으로는 접근할 수 있지만, 바깥쪽에서 안쪽으로는 접근할 수 없다. 이 비대칭을 모르면 바깥 클래스에서 중첩 클래스의 내부 상태를 직접 건드리려다 컴파일 에러를 만난다. 해결책은 중첩 클래스가 `internal` 멤버나 적절한 접근자를 노출하는 것이다.

### 3.5 클래스와 동반 객체 사이의 private 공유

`private`이 선언의 안쪽으로 보인다는 규칙에서 나오는 편리한 결과가 하나 더 있다. 클래스와 그 **동반 객체(companion object, [[28 - object와 companion - 싱글턴과 동반 객체]])** 는 서로의 private에 접근할 수 있다. 동반 객체는 클래스 본문 안에 중첩된 특별한 객체이므로 3.4절의 "안쪽은 바깥의 private을 본다" 규칙이 적용된다. 여기에 더해 코틀린은 그 역방향, 즉 클래스가 companion의 private을 보는 것도 허용한다.

```kotlin
class Temperature private constructor(val celsius: Double) {
    companion object {
        private const val ABSOLUTE_ZERO = -273.15   // companion의 private
        fun of(c: Double): Temperature {
            require(c >= ABSOLUTE_ZERO)              // companion 안에서 자기 private
            return Temperature(c)                    // 클래스의 private 생성자 호출 — OK
        }
    }
    fun isColderThan(other: Temperature) =
        this.celsius < other.celsius                 // 다른 인스턴스 private (3.3)
}

val t = Temperature.of(25.0)   // 팩토리를 통해서만 생성
// Temperature(25.0)           // 컴파일 에러: constructor is private
```

이 상호 접근에서 핵심은 `of` 팩토리 함수가 `private` 생성자 `Temperature(...)`를 호출할 수 있다는 점이다. 덕분에 "생성자를 private으로 감추고 companion 팩토리로만 객체를 만들게 하는" 관용구가 가능하다. 캡슐화 관점에서 companion과 클래스는 하나의 단위처럼 동작한다.

## 4. protected: 하위 클래스 전용 (Java와의 결정적 차이)

### 4.1 protected의 의미

`protected` 멤버는 **선언한 클래스와 그 하위 클래스에서만** 보인다. 외부 코드는 물론이고, 같은 패키지에 있는 무관한 클래스도 보지 못한다. `protected`는 상속 계층 내부에 확장 지점을 열어 두는 도구다.

```kotlin
open class Shape {
    protected open fun computeArea(): Double = 0.0  // 하위가 재정의할 훅
    fun describe(): String = "area = ${computeArea()}"  // public 진입점
}

class Rectangle(val w: Double, val h: Double) : Shape() {
    override fun computeArea() = w * h   // OK — 하위 클래스라 protected 접근
}

val r = Rectangle(3.0, 4.0)
println(r.describe())   // => area = 12.0
// r.computeArea()      // 컴파일 에러: computeArea is protected
```

`computeArea`는 하위 클래스가 채워 넣는 확장 지점이고, 외부에는 `describe`라는 공개 진입점만 보인다. 이것이 템플릿 메서드 패턴(template method pattern)의 기본 구조다.

### 4.2 Java와의 결정적 차이: 패키지 접근이 없다

자바의 `protected`는 **두 가지**를 동시에 허용한다. 하나는 하위 클래스이고, 다른 하나는 *같은 패키지의 모든 코드*다. 코틀린의 `protected`는 하위 클래스만 허용한다. **패키지 접근은 없다.**

```text
                     하위 클래스에서   같은 패키지 무관 클래스에서
  Java protected          O                    O
  Kotlin protected        O                    X   ← 이 지점이 다르다
```

```kotlin
// ==== animals.kt (package zoo) ====
open class Animal {
    protected val energy = 100
}

// 같은 패키지 zoo의 무관한 클래스
class Zookeeper {
    fun feed(a: Animal) {
        // a.energy   // 컴파일 에러: energy is protected — 상속 관계가 아니므로
    }
}

class Cat : Animal() {
    fun purr() = energy > 50   // OK — 하위 클래스
}
```

`Zookeeper`는 `Animal`과 같은 패키지에 있어도 `energy`에 접근하지 못한다. 상속 관계가 아니기 때문이다. 자바였다면 같은 패키지라는 이유만으로 접근할 수 있었을 것이다. 코틀린이 이 패키지 접근을 뺀 것은 **패키지를 가시성 경계로 쓰지 않는다는 일관된 방침**(5절) 때문이다. 코틀린에서 패키지는 이름을 정리하는(namespacing) 수단일 뿐, 접근 제어의 단위가 아니다.

> [!note] 상호운용 주의
> 성능 문제는 아니지만, 이 차이는 JVM에서 조용히 무너진다. 코틀린의 `protected` 멤버는 JVM 바이트코드에서 자바의 `protected`로 컴파일되는데, 자바의 `protected`는 패키지 접근을 *포함*한다. 그래서 코틀린에서 `protected`로 감춘 멤버라도 **같은 패키지에 자바 클래스를 두면 그 자바 코드에서는 접근할 수 있다.**
>
> JVM의 표현 한계 때문에 코틀린의 "하위 클래스 전용" 보장이 자바 쪽에서만 느슨해지는 것이다. 자세한 상호운용 함정은 45장(Java 상호운용)을 참고한다.

### 4.3 protected는 최상위에 붙일 수 없다

`protected`는 "하위 클래스"라는 상속 개념에 의존한다. 최상위 함수와 프로퍼티에는 상속이 없으므로 `protected`가 의미를 가질 수 없다. 그래서 컴파일러가 이를 막는다.

```kotlin
// protected fun helper() { }   // 컴파일 에러: modifier 'protected' is not applicable to 'top level declaration'
```

같은 이유로 최상위 선언에 쓸 수 있는 한정자는 `public`(기본), `private`(파일 스코프), `internal`(모듈 스코프) 세 개뿐이다. 네 개 중 `protected`만 빠진다는 점은 1.2절의 표와 일치한다.

### 4.4 protected 멤버와 companion, 중첩 클래스

`protected`는 클래스 멤버에만 쓸 수 있지만, 몇 가지 미묘한 상호작용이 있다. `protected`로 선언한 중첩 클래스는 하위 클래스에서만 보인다. 또한 하위 클래스는 protected 멤버를 *자신의 protected로 다시 노출*하거나 public으로 넓힐 수 있는데, 이는 9.1절의 오버라이드 가시성 규칙과 연결된다.

한편 인터페이스(25장)에는 `protected`를 쓸 수 없다. 인터페이스 멤버에 허용되는 가시성은 `public`(기본)과 `private`(구현이 있는 헬퍼용)뿐이며, `protected`와 `internal`은 인터페이스 본문에서 금지된다. 인터페이스는 상태가 없는 계약이고, "하위 클래스 전용"이라는 개념이 여러 클래스가 구현할 수 있는 인터페이스의 의미와 잘 맞지 않기 때문이다.

## 5. internal: 모듈 가시성 (package-private이 아니다)

이제 이 장에서 가장 중요한 내용이자, 흔한 오해 하나를 바로잡을 차례다. 자바에 익숙한 개발자가 `internal`을 처음 보면 거의 반사적으로 "자바의 package-private 같은 것"이라고 생각한다. **이것은 틀렸다.** `internal`의 기준은 패키지가 아니라 **모듈(module)** 이다.

### 5.1 모듈이란 무엇인가

`internal`을 이해하려면 먼저 "모듈"을 정확히 정의해야 한다. 코틀린에서 **모듈은 함께 컴파일되는 코틀린 파일의 집합**이다. 구체적으로는 다음 중 하나가 모듈 하나를 이룬다.

- IntelliJ IDEA의 모듈 하나
- Maven 프로젝트 하나
- Gradle 소스 세트(source set) 하나 (단, `test` 소스 세트는 `main`의 `internal` 선언을 볼 수 있는 예외가 있다)
- 하나의 Ant 태스크 호출로 함께 컴파일되는 파일들
- 코틀린 컴파일러를 한 번 호출할 때 함께 넘긴 파일들

핵심은 **"한 번의 컴파일 단위"** 라는 점이다. 모듈은 패키지도, 파일도, 프로젝트 전체도 아니다. 함께 컴파일되는 묶음이다.

```text
  ┌─────────── 모듈 A (예: :core Gradle 소스셋) ───────────┐
  │  package math                                          │
  │    internal fun helper()   ← 모듈 A 어디서나 보임        │
  │  package geometry                                      │
  │    fun useHelper() = helper()   ← 다른 패키지지만 OK!    │
  └────────────────────────────────────────────────────────┘

  ┌─────────── 모듈 B (예: :app Gradle 소스셋, A에 의존) ───┐
  │  package math                                          │
  │    fun tryHelper() = helper()   ← 같은 패키지지만 에러!  │
  │                     (helper는 모듈 A의 internal)        │
  └────────────────────────────────────────────────────────┘
```

이 다이어그램이 핵심을 그대로 보여 준다. `internal` 선언은 **패키지가 달라도** 같은 모듈이면 보이고, **패키지가 같아도** 다른 모듈이면 보이지 않는다.

### 5.2 internal ≠ package-private

두 규칙을 나란히 놓으면 차이가 분명해진다.

| 상황 | Java package-private | Kotlin internal |
|------|:---:|:---:|
| 같은 패키지, 같은 모듈 | ✅ 보임 | ✅ 보임 |
| **다른 패키지**, 같은 모듈 | ❌ 안 보임 | ✅ **보임** |
| 같은 패키지, **다른 모듈** | ✅ 보임* | ❌ **안 보임** |

(*자바에는 모듈 개념이 없으므로, "다른 모듈"이라도 클래스패스상 같은 패키지면 그냥 보인다.)

요점은 패키지와 모듈이라는 두 축이 서로 **직교**한다는 것이다. 자바의 경계는 패키지이고 코틀린 `internal`의 경계는 모듈이다. 둘은 겹치는 부분도 있지만 근본적으로 다른 것을 기준으로 삼는다.

```kotlin
// ==== 모듈 :library, package data ====
internal class ConnectionPool {   // 모듈 전체에서 재사용할 내부 구현
    fun acquire(): Connection = TODO()
}

// ==== 모듈 :library, package service (다른 패키지, 같은 모듈) ====
class UserService {
    private val pool = ConnectionPool()  // OK! internal은 모듈 전체에서 보임
}

// ==== 모듈 :app (:library에 의존, 다른 모듈) ====
class AppMain {
    // val pool = ConnectionPool()  // 컴파일 에러: ConnectionPool is internal — 다른 모듈
}
```

`ConnectionPool`은 `:library` 모듈 안이라면 어느 패키지에서든 자유롭게 쓸 수 있다. 그러나 `:library`를 의존성으로 가져다 쓰는 `:app` 모듈에서는 존재하지 않는 것처럼 감춰진다. 이것이 `internal`의 진짜 쓰임새다.

### 5.3 왜 모듈인가: 라이브러리 설계 관점

`internal`이 이렇게 설계된 이유는 **라이브러리 작성자가 겪는 문제**에 있다. 라이브러리를 만들 때 개발자가 다루는 코드는 두 종류다.

1. **공개 API**: 라이브러리 사용자가 의존해도 되는 계약. `public`.
2. **내부 구현**: 라이브러리 안의 여러 패키지가 협력하는 데 필요하지만, 사용자에게는 감춰야 하는 것.

문제는 두 번째다. 내부 구현은 여러 패키지에 흩어진 채 서로 협력해야 하는 경우가 많다. 파일 스코프인 `private`은 너무 좁아서 다른 파일과 협력할 수 없고, `public`은 너무 넓어서 사용자에게 노출된다. 자바에서는 이 딜레마를 해결하기 어려웠다. package-private은 패키지를 넘지 못하므로, 여러 패키지가 협력하려면 결국 `public`으로 열 수밖에 없었다. 그 결과 "실수로 공개된 내부 API" 문제가 흔했다.

`internal`은 바로 이 빈틈을 메운다. **"내 모듈 안에서는 자유롭게 협력하되, 모듈 밖으로는 절대 노출하지 않는다."** 이렇게 라이브러리의 공개 표면(published API)과 내부 구현을 깔끔하게 나눈다. 코틀린이 패키지가 아니라 모듈을 가시성 단위로 삼은 근본적인 이유도 여기에 있다. 패키지는 사용자에게 노출되지만, 모듈 경계는 배포 단위와 일치하기 때문이다.

> [!info] 역사 메모
> 자바도 결국 이 문제를 인정하고 Java 9(2017)에서 JPMS(Java Platform Module System, "Jigsaw")로 모듈 개념을 도입했다. `module-info.java`의 `exports` 지시어로 밖에 노출할 패키지를 선언한다. 흥미롭게도 코틀린 `internal`(2016년 정식 출시 때부터 존재)은 JPMS보다 먼저, 훨씬 가벼운 형태로 같은 문제를 해결했다.
>
> 다만 둘은 동작하는 층위가 다르다. JPMS는 JVM이 모듈 경계를 검사하는 런타임 강제인 반면, 코틀린 `internal`은 컴파일 타임 규칙이며 JVM에는 이름 맹글링(8절)이라는 우회 방식으로만 남는다.

### 5.4 internal의 전파와 상속

`internal` 선언은 같은 모듈 안에서는 `public`처럼 자유롭게 상속하고 구현하고 오버라이드할 수 있다.

```kotlin
internal abstract class BaseRepository {
    internal abstract fun connect()
}

// 같은 모듈에서 상속 — OK
internal class SqlRepository : BaseRepository() {
    override fun connect() { /* ... */ }
}
```

`internal`과 다른 한정자를 조합했을 때의 노출 규칙도 있다. 예를 들어 `internal` 클래스의 `public` 멤버는 결국 `internal`만큼만 도달할 수 있다. 클래스 자체가 모듈 밖에서 보이지 않으므로 그 멤버도 사실상 모듈 안에 갇힌다. 즉 가시성의 상한은 "가장 좁은 상위 선언"이 정한다. 이처럼 관계로서의 가시성은 9절에서 노출 규칙으로 다시 다룬다.

앞서 언급한 Gradle의 예외도 기억해 두자. `test` 소스 세트는 같은 프로젝트에 있는 `main` 소스 세트의 `internal` 선언을 볼 수 있다. 내부 구현을 테스트하려면 접근이 필요하기 때문에 둔 특별한 예외다. 엄밀히는 별개의 모듈이지만, 테스트 편의를 위해 열어 둔 통로다.

### 5.5 모듈 경계를 눈으로 확인하기

"모듈"이라는 개념이 잘 와닿지 않는다면 Gradle 멀티프로젝트 구조로 구체화해 보자. 아래의 각 소스 세트가 모듈 하나다.

```text
  project/
  ├── core/  src/main/kotlin/   ← 모듈 core-main
  │          src/test/kotlin/    ← 모듈 core-test (core-main의 internal 봄)
  └── app/   src/main/kotlin/    ← 모듈 app-main (core에 의존)
             src/test/kotlin/    ← 모듈 app-test
```

```kotlin
// core/src/main/kotlin/data/Cache.kt   (모듈 core-main)
package data
internal class Cache { fun size() = 0 }

// core/src/main/kotlin/service/Loader.kt (모듈 core-main, 다른 패키지)
package service
import data.Cache
fun load() = Cache().size()       // OK — 같은 모듈, 패키지만 다름

// core/src/test/kotlin/CacheTest.kt   (모듈 core-test)
import data.Cache
fun test() = Cache().size()       // OK — test는 main의 internal을 봄 (예외)

// app/src/main/kotlin/Main.kt       (모듈 app-main)
import data.Cache
// fun run() = Cache().size()      // 컴파일 에러: Cache is internal (다른 모듈)
```

같은 `data.Cache`라도 어디서 참조하느냐에 따라 보이기도 하고 보이지 않기도 한다. 결정 요인은 결코 "패키지가 같은가"가 아니라 "**같은 모듈로 컴파일되는가**"이다. `app-main`은 `core`를 라이브러리 의존성으로 가져오지만, 의존성으로 들어온 `internal` 선언은 사용하는 쪽에서 감춰진다. 이것이 라이브러리 작성자가 원했던 경계다. 배포된 아티팩트를 사용하는 쪽에서 보면 `internal` 선언은 존재하지 않는 것과 같다.

### 5.6 internal과 멀티플랫폼

`internal`의 "모듈 = 컴파일 단위"라는 정의는 JVM에만 묶인 개념이 아니다. 코틀린 멀티플랫폼([[46 - 멀티플랫폼과 진화와 어두운 구석]])에서 `common` 소스 세트에 선언한 `internal`은 같은 모듈의 플랫폼별 소스 세트에서도 보인다. 모듈 경계가 소스 세트 그룹 전체를 포함하기 때문이다.

즉 `internal`은 특정 백엔드의 기법이 아니라 **언어 수준의 컴파일 단위 규칙**이다. JVM의 이름 맹글링(8절)은 이 언어 규칙을 JVM이라는 특정 플랫폼에서 근사하는 *구현 세부 사항*일 뿐이다. 규칙은 언어가 정하고 맹글링은 백엔드가 구현한다는 이 층위 구분을 기억해 두면 8절을 훨씬 쉽게 이해할 수 있다.

> [!note] 명세 기준
> 자바의 `package-private`은 런타임에 클래스로더와 패키지가 일치해야 성립하는 반면, 코틀린의 `internal`은 순수한 **컴파일 타임** 개념이다. 컴파일이 끝나 바이트코드가 되면 모듈 정보는 맹글링된 이름의 흔적을 빼고는 사라진다. 그래서 리플렉션이나 바이트코드 조작으로 `internal` 경계를 쉽게 넘을 수 있다. 1.3절에서 말했듯 가시성은 보안이 아니라 정적 계약이다.

## 6. 선언 위치별 규칙 차이

가시성 한정자는 어디에 붙이느냐에 따라 허용 여부와 의미가 달라진다. 3~5절에서 일부를 살펴봤는데, 여기서 위치별로 정리한다.

### 6.1 최상위 선언

파일 최상위의 함수, 프로퍼티, 클래스, 타입 별칭에 붙일 수 있는 한정자는 세 개다.

```kotlin
public fun a() {}     // 기본, 어디서나
private fun b() {}    // 같은 파일에서만
internal fun c() {}   // 같은 모듈에서만
// protected fun d() {}  // 에러 — 최상위에 protected 불가
```

- `public`(기본): 이 선언을 볼 수 있는 모든 곳.
- `private`: **같은 파일**(패키지 아님).
- `internal`: **같은 모듈**.
- `protected`: **금지**.

### 6.2 클래스와 인터페이스의 멤버

클래스 멤버에는 네 한정자를 모두 붙일 수 있다(단, 인터페이스 멤버에는 public과 private만 쓸 수 있다).

```kotlin
open class Widget {
    public val id = 0        // 어디서나 (기본)
    private val cache = 0    // Widget 안에서만
    protected val state = 0  // Widget과 하위 클래스에서만
    internal val debug = 0   // 같은 모듈에서 Widget이 보이는 곳
}
```

여기서 `private`의 스코프는 최상위와 달리 **클래스**다. 같은 단어가 위치에 따라 두 가지 의미를 갖는다는 점(3.1절과 3.2절)이 여기서 다시 확인된다.

### 6.3 생성자 가시성과 constructor 키워드

주 생성자(21장 클래스와 생성자)는 기본이 `public`이다. 가시성을 바꾸려면 `constructor` 키워드를 명시해야 한다. 평소에는 생략하던 키워드가 한정자를 붙이는 순간 필수가 된다.

```kotlin
// 평소: constructor 생략
class Point(val x: Int, val y: Int)

// private 생성자: constructor 명시 필요
class Registry private constructor() {
    companion object {
        val instance = Registry()   // 내부에서만 만든다 (싱글턴 유도)
    }
}

// val r = Registry()  // 컴파일 에러: constructor is private
```

`private` 생성자는 팩토리 패턴이나 싱글턴을 구현할 때 쓴다(28장 object와 companion에서는 싱글턴을 더 깔끔하게 만드는 방법을 다룬다). `internal constructor`는 "이 클래스는 모듈 안에서만 생성할 수 있다"는 뜻이다. 라이브러리가 타입은 노출하면서 인스턴스 생성은 통제하고 싶을 때 유용하다.

```kotlin
class Token internal constructor(val value: String)
// 모듈 밖에서는 Token 타입을 받을 수는 있으나 직접 생성 불가 — 팩토리 함수만 노출
```

부 생성자에도 같은 규칙이 적용되므로 `protected constructor(...)`와 `private constructor(...)` 모두 쓸 수 있다.

### 6.4 지역 선언에는 한정자가 없다

함수 본문 안의 지역 변수, 지역 함수, 지역 클래스에는 **가시성 한정자를 붙일 수 없다.** 이런 선언의 스코프는 이미 자신을 감싼 블록으로 한정되어 있으므로, 가시성 한정자로 표현할 것이 없기 때문이다.

```kotlin
fun compute(): Int {
    // private val x = 1   // 컴파일 에러: modifier 'private' is not applicable to 'local variable'
    val x = 1              // 지역 변수는 항상 블록 스코프
    fun helper() = x + 1   // 지역 함수도 마찬가지 — 한정자 불가
    return helper()
}
```

지역 선언의 가시성은 전적으로 **렉시컬 스코프**(어휘적 유효 범위, [[14 - 클로저와 캡처]]와 연결)가 결정한다. 한정자는 파일 수준과 클래스 수준의 선언에만 의미가 있다.

위치별로 허용되는 한정자를 표로 정리하면 다음과 같다.

| 위치 | public | private | protected | internal |
|------|:---:|:---:|:---:|:---:|
| 최상위 | ✅ | ✅(파일) | ❌ | ✅ |
| 클래스 멤버 | ✅ | ✅(클래스) | ✅ | ✅ |
| 인터페이스 멤버 | ✅ | ✅ | ❌ | ❌ |
| 생성자 | ✅ | ✅ | ✅ | ✅ |
| 지역 | ❌(불가) | ❌ | ❌ | ❌ |

## 7. 세터 가시성과 프로퍼티 비대칭

### 7.1 private set: 읽기는 공개, 쓰기는 비공개

프로퍼티(22장 프로퍼티와 백킹 필드)는 게터와 세터를 따로 가진다. 코틀린에서는 이 둘의 가시성을 **다르게** 정할 수 있으므로, "읽기는 넓게, 쓰기는 좁게"라는 흔한 비대칭 캡슐화를 한 줄로 표현할 수 있다.

```kotlin
class Counter {
    var count: Int = 0
        private set          // 게터는 public, 세터만 private

    fun increment() { count++ }   // 클래스 내부에서는 쓰기 가능
}

val c = Counter()
c.increment()
println(c.count)   // => 1   (읽기 OK)
// c.count = 100   // 컴파일 에러: cannot assign — setter is private
```

`count`는 밖에서 읽을 수 있지만, 값은 오직 `increment`를 통해서만 바뀐다. 클래스가 불변식(invariant)을 혼자 관리하는 전형적인 패턴이다. `internal set`과 `protected set`도 같은 방식으로 쓸 수 있다.

여기에는 중요한 제약이 있다. **세터는 프로퍼티(게터)보다 넓은 가시성을 가질 수 없다.** 게터가 `private`인데 세터가 `public`인 것은 논리적으로 맞지 않으므로 금지된다. 세터의 가시성은 프로퍼티의 가시성과 같거나 그보다 좁아야 한다.

```kotlin
class Bad {
    // private var x = 0
    //     public set    // 컴파일 에러: setter visibility must be at most property visibility
}
```

또 하나, 세터의 가시성은 지정할 수 있지만 **게터의 가시성은 따로 지정할 수 없다.** 게터의 가시성이 곧 프로퍼티 전체의 가시성이기 때문이다. 따라서 "게터만 좁히기"는 프로퍼티 자체를 좁히는 것과 같다.

### 7.2 백킹 프로퍼티 패턴: private set으로 부족한 경우

`private set`은 "타입은 그대로 두고 쓰기만 막는" 데는 완벽하다. 그러나 때로는 **외부에 노출하는 타입과 내부에서 다루는 타입 자체를 다르게** 하고 싶을 때가 있다. 예를 들어 내부에서는 `MutableList`로 다루면서 밖에는 읽기 전용 `List`([[38 - 컬렉션 - 읽기 전용과 가변]])로 내놓고 싶은 경우다. 이때는 `private set`으로는 부족하므로 **백킹 프로퍼티(backing property)** 패턴을 쓴다.

```kotlin
class TodoBoard {
    private val _tasks = mutableListOf<String>()   // 내부 전용 가변 뷰
    val tasks: List<String> get() = _tasks         // 외부엔 읽기 전용 노출

    fun add(task: String) { _tasks.add(task) }
}

val board = TodoBoard()
board.add("write chapter")
println(board.tasks)     // => [write chapter]
// board.tasks.add("x")  // 컴파일 에러: List에는 add가 없다
```

관례적으로 밑줄 접두사를 붙이는 `_tasks`는 `private`이므로 밖에서 보이지 않고, `tasks`는 그것을 `List` 타입으로 올려서 노출한다. `private set`은 "같은 타입에서 쓰기를 차단"하는 것이고, 백킹 프로퍼티는 "다른 타입으로 노출해 쓰기 기능 자체를 차단"하는 것이다. 이 둘을 구분하는 것이 실무 캡슐화의 핵심이다.

읽기 전용 `List`가 진짜 불변은 아니라는 함정은 38장(컬렉션)에서 다룬다. 여기서 `_tasks`를 직접 노출하지 않는 것이 바로 그 함정을 막는 방법이다.

## 8. JVM 백엔드에서의 표현: 이름 맹글링과 상호운용

지금까지 본 규칙은 언어 수준의 추상이다. 그런데 코틀린을 JVM 바이트코드로 컴파일할 때, JVM에는 `internal`도, "파일 스코프"도, 코틀린식 `protected`도 정확히 대응하는 개념이 없다. 코틀린은 여러 우회 방법으로 이 차이를 메운다. 이 절의 내용은 JVM 백엔드에만 해당한다(Native, JS, Wasm 백엔드는 각자 다른 방식을 쓴다).

### 8.1 각 한정자의 바이트코드 매핑

JVM 백엔드에서는 대략 다음과 같이 컴파일된다(세부 사항은 구현과 JVM 타깃 버전에 따라 달라질 수 있다).

| 코틀린 | JVM 바이트코드 표현 | 비고 |
|--------|---------------------|------|
| `public` 멤버 | `public` | 그대로 |
| `private` 멤버 | `private` | 그대로 (단 중첩 접근은 8.4) |
| `protected` 멤버 | `protected` | JVM protected는 패키지 접근 포함 → 4.2 누수 |
| `internal` 멤버 | `public` + **이름 맹글링** | JVM에 모듈 개념 없음 → 8.2 |
| 최상위 `private` | 파일 파사드 클래스의 제한 멤버 | 파일 스코프를 클래스 스코프로 근사 |
| `internal` 클래스 | `public` 클래스 (경고 동반) | 클래스 이름은 맹글링 안 됨 |

특히 두 항목이 흥미롭다. `internal`은 JVM에 대응하는 개념이 없어서 **`public`으로 컴파일한 뒤 이름을 바꿔** 접근을 억제한다. `protected`는 JVM의 protected가 더 넓기 때문에 **의도보다 넓게 노출된다.**

### 8.2 internal의 이름 맹글링

`internal` 함수와 프로퍼티 접근자는 JVM 바이트코드에서 이름 뒤에 모듈 이름이 접미사로 붙는다. 대략 `함수이름$모듈이름` 형태다.

```kotlin
// Kotlin, 모듈 이름이 "app"이라고 하자
internal fun calculate(x: Int): Int = x * 2
```

이 함수는 JVM에서 대략 다음처럼 보인다.

```java
// 개념적으로 디컴파일된 모습 (모듈명·구분자 세부는 구현에 따라 다름)
public static final int calculate$app(int x) { return x * 2; }
```

**왜 맹글링할까?** 목적은 두 가지다.

첫째, **자바에서 실수로 호출하거나 오버라이드하는 것을 막기 위해서**다. `internal`은 "모듈 밖에서 쓰지 말 것"이라는 계약인데, JVM에서 그냥 `public`으로 두면 자바 코드가 아무렇지 않게 `calculate(x)`를 호출할 수 있다. 이름을 `calculate$app`으로 바꿔 두면 자바 개발자가 우연히 그 이름을 입력할 일이 없으므로 사실상 감춰진다.

다만 완벽하게 차단되지는 않는다. 맹글링된 이름 `calculate$app`을 자바에서 직접 쓰면 여전히 호출할 수 있다. 강제가 아니라 억제인 것이다.

둘째, **시그니처 충돌을 막기 위해서**다. 서로 다른 모듈에 우연히 같은 이름의 `internal` 멤버가 있더라도, 모듈 이름 접미사가 다르면 JVM 수준에서 충돌하지 않는다.

```text
  모듈 "core"의  internal fun helper()  →  helper$core
  모듈 "ui"의    internal fun helper()  →  helper$ui
                              ↑ JVM에서 이름이 달라 충돌하지 않음
```

> [!note] 명세 기준
> 맹글링되는 것은 **함수와 프로퍼티 접근자**이고, **클래스 이름**은 맹글링되지 않는다. `internal class Foo`는 JVM에서 그냥 `public class Foo`가 되고 이름도 바뀌지 않는다. 그래서 자바 코드는 `internal` 클래스 자체를 이름으로 참조할 수 있다(코틀린 컴파일러가 경고를 낼 수는 있지만 JVM 차원에서는 열려 있다).
>
> 멤버는 맹글링하고 클래스는 그대로 노출하는 이 비대칭은 자바 상호운용에서 코틀린의 가시성 보장이 완벽하지 않다는 것을 보여 준다. 완전한 격리가 필요하다면 JPMS나 별도의 배포 단위를 써야 한다.

### 8.3 자바에서 본 코틀린 가시성 요약

자바 코드에서 코틀린 코드를 볼 때 각 한정자가 어떻게 나타나는지 정리하면 다음과 같다(45장 Java 상호운용의 축약판이다).

- `public` → 자바에서도 그대로 `public`.
- `private` 멤버 → 자바에서도 `private`(접근 불가).
- `protected` → 자바 `protected`(그런데 자바에서는 **같은 패키지에서도 접근**할 수 있으므로 코틀린의 의도보다 넓게 열림).
- `internal` → 자바에서는 **맹글링된 이름의 `public`** 으로 보임(억제되지만 뚫을 수는 있음).
- 최상위 `private` → 자바에서 접근 불가(파일 파사드 클래스에 갇힘).

핵심은 이것이다. **코틀린의 가시성 보장은 코틀린에서 코틀린을 쓸 때는 견고하지만, 자바에서 코틀린을 쓸 때는 JVM의 표현 한계 때문에 느슨해진다.** `internal`은 강제가 아니라 억제일 뿐이고, `protected`는 패키지 단위로 열리며, `internal` 클래스는 그대로 노출된다. 이 빈틈을 알아야 상호운용 코드를 제대로 방어할 수 있다.

### 8.4 private 멤버와 중첩 접근: 합성 접근자와 nestmate

3.4절에서 이너 클래스가 바깥 클래스의 `private`에 접근하는 것을 봤다. 그런데 JVM의 전통적인 규칙에서는 한 클래스의 `private` 멤버에 *다른 클래스*가 직접 접근할 수 없었다(중첩 클래스도 JVM에서는 별개의 클래스다). 코틀린(그리고 자바)은 다음 두 방식 중 하나로 이 차이를 메운다.

- **합성 접근자(synthetic accessor)**: 컴파일러가 `access$getSecret$p(...)` 같은 패키지 수준의 중계 메서드를 자동으로 생성하고, 중첩 클래스는 이 메서드를 거쳐 바깥 클래스의 private에 접근한다. 오래된 방식이다.
- **네스트메이트(nestmate) 기반 접근**: JVM 11부터 도입된 nest-based access control을 쓰면, 중첩 관계에 있는 클래스들이 중계 메서드 없이 서로의 private에 직접 접근할 수 있다. 코틀린도 충분히 최신인 JVM을 타깃으로 하면 이 방식을 활용할 수 있다.

어느 방식을 쓰는지는 **컴파일러 버전과 JVM 타깃 버전에 따라 다르다.** 기억할 것은 결과다. 소스 수준에서는 "이너 클래스가 바깥 클래스의 private을 자연스럽게 본다"는 규칙이 성립하고, 그 뒤에서 컴파일러가 JVM의 제약을 우회하는 장치를 마련해 준다. 이 세부 사항은 언어 명세가 아니라 백엔드 구현이 정하는 부분이므로, "구현에 따라 다르다"고 남겨 두는 것이 정확하다.

```text
  [소스 수준]                    [JVM 백엔드가 까는 기계]
  Inner.reveal() → Outer.secret   ─┬─ (구식) Outer.access$getSecret 다리 호출
                                    └─ (신식) nestmate 직접 접근 (JVM 11+)
```

## 9. 가시성은 관계다: 노출 규칙과 오버라이드

마지막 절에서는 가시성의 가장 미묘한 측면을 다룬다. 지금까지는 가시성을 "선언 하나에 붙는 라벨"로 봤지만, 실제 규칙은 **선언 사이의 관계**를 강제한다. 좁게 감춘 것을 넓게 공개된 선언이 노출하면 캡슐화가 깨지기 때문이다.

### 9.1 오버라이드는 가시성을 좁힐 수 없다

하위 클래스가 상위 클래스의 멤버를 오버라이드(24장 상속과 오버라이딩)할 때, 오버라이드한 멤버의 가시성은 **원본보다 좁을 수 없다.** 원본과 같거나 더 넓어야 한다.

```kotlin
open class Base {
    protected open fun step() {}
}

class Derived : Base() {
    public override fun step() {}   // OK — protected를 public으로 넓힘
    // private override fun step() {}  // 컴파일 에러: cannot narrow visibility
}
```

이유는 **리스코프 치환 원칙(Liskov Substitution)** 이다. `Base` 타입으로 `Derived` 인스턴스를 다룰 때 `step`은 protected로 접근할 수 있어야 하는데, 하위 클래스가 이를 `private`으로 좁히면 그 계약이 깨진다. 그래서 넓히기(protected→public)는 허용하고 좁히기(protected→private)는 금지한다. 오버라이드할 때 한정자를 생략하면 원본의 가시성을 그대로 물려받는다.

### 9.2 public 선언은 덜 보이는 타입을 노출할 수 없다

가장 중요한 관계 규칙은 이것이다. **어떤 선언도 자신보다 가시성이 좁은 타입을 자신의 공개 시그니처에 노출할 수 없다.** `public` 함수가 `internal` 타입을 반환하거나 파라미터로 받으면 컴파일 에러다.

```kotlin
internal class InternalConfig(val port: Int)

// public 함수가 internal 타입을 노출 — 에러
// public fun loadConfig(): InternalConfig = InternalConfig(8080)
//   컴파일 에러: 'public' function exposes its 'internal' return type InternalConfig

// 해결책 1: 함수를 internal로 좁힌다
internal fun loadConfig(): InternalConfig = InternalConfig(8080)

// 해결책 2: public 인터페이스로 노출하고 internal 구현은 감춘다
interface Config { val port: Int }
internal class InternalConfigImpl(override val port: Int) : Config
fun loadConfigPublic(): Config = InternalConfigImpl(8080)  // OK
```

이 규칙은 왜 필요할까? 만약 `public fun loadConfig(): InternalConfig`가 허용된다면, 모듈 밖의 사용자가 `loadConfig()`를 호출해 `InternalConfig` 타입의 값을 얻게 된다. 그런데 그 타입은 `internal`이라 사용자는 이름조차 쓸 수 없다. 결국 사용자는 "이름 없는 타입의 값"을 받고도 아무것도 할 수 없는 모순에 빠진다. 컴파일러는 이 모순을 미리 막는다.

이 규칙은 **가시성이 선언 하나의 속성이 아니라, 시그니처 전체가 만드는 도달 가능성의 네트워크**라는 것을 보여 준다. 같은 원리로 `private` 필드가 `public` 함수를 통해 노출되는 것도 막으며, 이 원리는 프로퍼티 타입, 상위 타입, 제네릭 인자([[33 - 제네릭 1 - 타입 파라미터와 변성]])에도 적용된다.

> [!note] 명세 기준
> 노출 규칙은 "선언의 가시성 ≤ 그 시그니처에 등장하는 모든 타입의 가시성"으로 요약할 수 있다. 즉 어떤 선언도 자신보다 감춰진 타입을 자신의 공개 시그니처에 담을 수 없다. 이 규칙 덕분에 "public API만 따라가면 필요한 모든 타입에 도달할 수 있다"는 폐쇄성(closure)이 보장된다. 캡슐화가 일부 깨진 채 방치되는 상황을 언어가 원천적으로 차단하는 것이다.

### 9.3 explicit API mode: 라이브러리를 위한 엄격 모드

2절에서 예고한 안전장치를 마지막으로 살펴보자. 라이브러리 작성자는 컴파일러 옵션 `-Xexplicit-api={strict|warning}`으로 **explicit API mode**를 켤 수 있다. 이 모드에서는 public/protected 선언에 다음을 강제한다.

- **가시성 한정자 명시 필수**: `public`을 생략할 수 없다. 따라서 "실수로 public이 된" 선언이 사라지고, 모든 public 선언은 의도적으로 입력한 것이 된다.
- **반환 타입 명시 필수**: public 선언의 반환 타입을 추론에 맡기지 못하고 직접 적어야 한다. 리팩터링 중에 반환 타입이 슬그머니 바뀌어 API가 깨지는 것을 막는다.

```kotlin
// explicit API mode (strict)에서:
fun helper() = 42          // 경고/에러: public 선언에 가시성·반환 타입 명시 필요
public fun helper2(): Int = 42   // OK — 의도가 명시됨
private fun helper3() = 42        // OK — public이 아니므로 규칙 면제
```

이 모드는 2절에서 지적한 "기본값이 public이라 부주의하게 API 표면이 커진다"는 위험에 대한 해결책이다. 애플리케이션 코드에서는 보통 끄지만, 공개 라이브러리에서는 켜 두고 모든 공개 표면을 의식적으로 관리한다. 46장(멀티플랫폼과 진화)에서 다룰 "안정적인 공개 API 관리"를 실천하는 도구 중 하나다.
