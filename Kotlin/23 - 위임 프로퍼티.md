**이 장이 답하는 질문:**

- `val x: Int by Something()`에서 `by`는 정확히 무슨 일을 하는가? 이건 클래스 위임 `by`와 같은 키워드인가, 다른 것인가?
- 프로퍼티 접근을 "다른 객체에게 위임한다"는 말은 컴파일된 바이트코드에서 무슨 형태가 되는가? 숨은 필드는 어디에 생기는가?
- `getValue`의 두 번째 파라미터 `property: KProperty<*>`는 도대체 어디서 오고, 왜 매 접근마다 새 객체가 할당되지 않는가?
- `by lazy { ... }`는 첫 접근에 초기화를 딱 한 번만 한다는데, 두 스레드가 동시에 첫 접근을 하면 초기화 람다는 몇 번 도는가? 그건 어떻게 보장되는가?
- `Delegates.observable`의 콜백은 값이 바뀌기 전에 불리는가 후에 불리는가? `vetoable`은 무엇을 되돌릴 수 있는가?
- `lateinit`과 `by Delegates.notNull()`은 언제 갈리는가? 왜 `Int`에는 `lateinit`을 못 쓰는데 `notNull`은 되는가?
- `provideDelegate`는 왜 존재하는가? 위임 객체를 그냥 `by 표현식`으로 넘기면 되는데 굳이 프로퍼티를 "제공"하는 한 겹을 더 두는 이유는?
- 위임 프로퍼티는 공짜인가? 매 읽기마다 함수 호출이 하나 더 끼는데, 그 비용은 어디서 나타나고 어디서 사라지는가?

이 장은 [[22 - 프로퍼티와 백킹 필드]]가 세운 토대 위에 정확히 한 겹을 더 얹는다. 22장은 Kotlin의 프로퍼티가 필드가 아니라 **접근자(get/set)의 추상**이며(M35), 백킹 필드 `field`는 접근자가 필요로 할 때만 컴파일러가 몰래 만들어 주는 저장소라는 사실을 보였다. 커스텀 게터·세터를 직접 써서 "값을 어떻게 읽고 쓸지"의 로직을 프로퍼티마다 손으로 짜 넣을 수 있었다. 그런데 그 로직 — 예컨대 "처음 읽을 때 계산하고 캐시한다", "값이 바뀔 때마다 로그를 남긴다", "맵에서 이름으로 찾아 온다" — 는 프로퍼티마다 거의 똑같이 반복된다. 위임 프로퍼티(delegated property)는 바로 그 **반복되는 접근자 로직을 하나의 객체로 뽑아내어 재사용**하게 하는 장치다.

핵심 이동은 이렇다. 22장에서 프로퍼티는 자기 백킹 필드를 직접 읽고 썼다. 이 장에서 프로퍼티는 백킹 필드를 아예 갖지 않고, 대신 **위임 객체(delegate)** 하나를 붙들고서, 자기가 읽히면 `delegate.getValue(...)`를, 자기가 쓰이면 `delegate.setValue(...)`를 호출한다. 프로퍼티는 껍데기가 되고, 진짜 저장과 로직은 위임 객체 안으로 들어간다. `by`라는 키워드가 이 연결을 선언한다. 그리고 `getValue`/`setValue`는 [[19 - 연산자 오버로딩과 관례]]가 소개한 **관례(convention) 함수** 가문의 일원이다(M40) — 정해진 이름과 시그니처를 가진 함수를 `operator`로 정의하면 언어가 특정 문법(`by`)으로 그것을 호출해 준다.

경계를 못 박자. 이 장은 **프로퍼티 위임**을 소유한다: `by` 뒤에 위임 객체를 두고 프로퍼티 하나의 읽기/쓰기를 그 객체에 넘기는 메커니즘, 표준 위임(`lazy`, `observable`, `vetoable`, `notNull`, 맵), `provideDelegate`, 로컬 변수 위임, 그리고 그 모든 것의 컴파일된 형태다. 이름은 같지만 완전히 다른 주제인 **클래스 위임**(`class C(b: Base) : Base by b`, 인터페이스 전체를 다른 객체에 넘겨 데코레이터/컴포지션을 만드는 것)은 [[32 - 클래스 위임]]이 소유한다. 두 `by`는 문법적 형제일 뿐 의미가 다르다는 점을 §1에서 분명히 한다. `getValue`/`setValue`가 관례라는 큰 그림은 [[19 - 연산자 오버로딩과 관례]]에, `by lazy`의 스레드 안전이 기대는 메모리 가시성·happens-before는 [[43 - 동시성과 메모리 모델]]에, 프로퍼티 참조 `::x`의 리플렉션 정체는 [[44 - 애노테이션과 리플렉션]]에 뿌리를 둔다.

논증의 궤적은 이렇다. 먼저 `by`가 접근자를 어떻게 위임 호출로 바꾸는지, 그 관례 시그니처가 정확히 무엇인지 세운다(§1~§2). 그다음 컴파일된 형태 — 숨은 `$delegate` 필드와 재사용되는 `KProperty` 객체 — 를 디컴파일 수준에서 해부한다(§3). 이어 표준 라이브러리가 제공하는 위임들을 하나씩 판다: 가장 중요한 `lazy`와 그 세 가지 스레드 모드(§4), `observable`/`vetoable`(§5), `notNull`과 맵 위임(§6). 그리고 위임을 만드는 위임인 `provideDelegate`(§7), 함수 안에서 쓰는 로컬 위임(§8)을 거쳐, 성능과 함정과 오개념으로 닫는다(§9).

## 1. `by`가 하는 일 — 접근자를 객체에게 넘기다

### 1.1 두 개의 `by`, 하나의 키워드

Kotlin에서 `by`라는 키워드는 문법적으로 **두 자리**에 등장하고, 그 둘은 이름만 같을 뿐 하는 일이 다르다.

```kotlin
// (1) 클래스 위임 — 32장의 주제. 인터페이스 "전체"를 다른 객체에 넘긴다.
interface Printer { fun print(): String }
class LoudPrinter(private val p: Printer) : Printer by p   // Printer의 모든 멤버를 p에 전달

// (2) 프로퍼티 위임 — 이 장의 주제. 프로퍼티 "하나"의 접근을 위임 객체에 넘긴다.
val greeting: String by lazy { "hello" }                   // greeting의 get을 lazy에 넘김
```

(1)은 `LoudPrinter`가 `Printer`를 상속하되, `Printer`가 요구하는 메서드들의 구현을 `p` 객체에게 전부 떠넘기는 것이다. 클래스 수준의 컴포지션이며 [[32 - 클래스 위임]]이 정본이다. (2)는 `greeting`이라는 프로퍼티 하나가 자기 값을 어떻게 내놓을지를 `lazy { ... }`가 만든 객체에게 맡기는 것이다. 스코프가 완전히 다르다: 하나는 타입의 인터페이스 계약 전체, 다른 하나는 프로퍼티 접근자 한 쌍.

이 장은 (2)만 다룬다. 헷갈리지 않는 요령: `by` 앞에 **프로퍼티 선언**(`val`/`var`)이 오면 프로퍼티 위임, `by` 앞에 **슈퍼타입 이름**이 오면 클래스 위임이다.

### 1.2 위임의 직관 — "이 프로퍼티를 어떻게 읽고 쓸지, 네가 정해라"

평범한 프로퍼티는 자기 값을 스스로 관리한다. 커스텀 게터/세터([[22 - 프로퍼티와 백킹 필드]])를 쓰면 로직을 넣을 수 있지만, 그 로직은 프로퍼티에 **박제**된다. 같은 로직을 다른 프로퍼티에도 쓰려면 복사해야 한다.

```kotlin
// 22장 방식: "처음 읽을 때 계산하고 캐시" 로직이 프로퍼티에 박혀 있다
class Circle(val radius: Double) {
    private var _area: Double? = null
    val area: Double
        get() {
            if (_area == null) _area = Math.PI * radius * radius
            return _area!!
        }
}
```

이 "지연 캐시" 패턴을 원 넓이뿐 아니라 둘레에도, 다른 클래스의 다른 프로퍼티에도 쓰고 싶다면? 매번 `_x: T? = null`과 `if (null) 계산` 보일러플레이트를 반복한다. 위임 프로퍼티는 이 패턴을 **한 객체로 캡슐화**해 재사용하게 한다.

```kotlin
// 위임 방식: "지연 캐시" 로직은 lazy 객체 안에 있고, 프로퍼티는 그것을 붙들 뿐
class Circle(val radius: Double) {
    val area: Double by lazy { Math.PI * radius * radius }
}
```

`area`는 이제 백킹 필드가 없다. `area`를 읽으면 컴파일러가 그것을 "붙들고 있는 `lazy` 객체에게 값을 물어보는 호출"로 번역한다. 로직은 `lazy`가 안다. 프로퍼티는 창구일 뿐이다.

### 1.3 `by`의 탈설탕(desugaring) — 개념적 번역

`by` 선언이 무엇으로 번역되는지를 먼저 개념적으로 못 박자. 다음 선언이 있다고 하자.

```kotlin
class Owner {
    var prop: String by Delegate()
}
```

컴파일러는 이것을 대략 다음과 **동등한** 형태로 바꾼다(정확한 컴파일 형태는 §3에서).

```kotlin
class Owner {
    private val prop$delegate = Delegate()          // 위임 객체를 담는 숨은 필드
    var prop: String
        get() = prop$delegate.getValue(this, ::prop)          // 읽기 → getValue
        set(value) { prop$delegate.setValue(this, ::prop, value) }  // 쓰기 → setValue
}
```

세 가지가 핵심이다. 첫째, `by 표현식`(`Delegate()`)은 **딱 한 번** 평가되어 숨은 필드 `prop$delegate`에 저장된다. 매 접근마다 새로 만들어지지 않는다. 둘째, `val`이면 게터만, `var`이면 게터와 세터가 만들어진다 — 그래서 `var` 위임은 `getValue`뿐 아니라 `setValue`도 필요하다. 셋째, 두 접근자는 각각 위임 객체의 `getValue`/`setValue` **관례 함수**를 부르며, 그때 `this`(소유 객체)와 `::prop`(프로퍼티 자신의 메타데이터)을 넘긴다.

> **명세 정밀**: `prop$delegate`, `getValue`, `setValue` 호출은 컴파일러가 생성하는 **합성(synthetic)** 코드다. 소스에는 `by Delegate()` 한 줄뿐이지만, 프론트엔드가 이를 접근자 본문으로 확장한다. 위 "동등 형태"는 소스 언어로 표현한 근사치이고, 실제 바이트코드는 `::prop`을 매번 만들지 않는 등 더 최적화되어 있다(§3).

## 2. `getValue`/`setValue` 관례 — 시그니처의 해부

### 2.1 정확한 시그니처

위임 객체가 되려면 두 관례 함수를 (필요한 만큼) 제공해야 한다. `val` 프로퍼티는 `getValue`만, `var` 프로퍼티는 둘 다 요구한다.

```kotlin
import kotlin.reflect.KProperty

class Delegate {
    operator fun getValue(thisRef: Any?, property: KProperty<*>): String {
        return "$thisRef 의 '${property.name}' 을 읽음"
    }
    operator fun setValue(thisRef: Any?, property: KProperty<*>, value: String) {
        println("$thisRef 의 '${property.name}' 에 '$value' 를 씀")
    }
}

class Owner(val label: String) {
    var prop: String by Delegate()
    override fun toString() = "Owner($label)"
}

fun main() {
    val o = Owner("a")
    println(o.prop)        // => Owner(a) 의 'prop' 을 읽음
    o.prop = "새값"        // => Owner(a) 의 'prop' 에 '새값' 를 씀
}
```

시그니처를 성분별로 뜯어보자.

- **`operator`**: 필수. 이것이 없으면 그냥 `getValue`라는 이름의 평범한 메서드일 뿐, `by`가 그것을 관례로 인식하지 못한다([[19 - 연산자 오버로딩과 관례]]의 원칙 그대로).
- **`thisRef: Any?`**: 프로퍼티를 **소유한 객체**. 위 예에서 `Owner` 인스턴스다. 이 파라미터의 타입은 위임이 어디에 붙을 수 있는지를 제약한다(§2.2). 최상위/로컬 프로퍼티에는 소유 객체가 없어 `null`이 들어온다.
- **`property: KProperty<*>`**: 위임된 프로퍼티 **자신의 메타데이터**. `property.name`으로 이름을, `property.returnType` 등으로 타입 정보를 얻는다. 이 객체가 어디서 오는지는 §3.2에서.
- **반환 타입 / `value` 타입**: 프로퍼티의 타입과 호환되어야 한다. `getValue`의 반환 타입은 프로퍼티 타입의 하위타입, `setValue`의 `value` 타입은 프로퍼티 타입의 상위타입이면 된다(위치에 따른 변성).

### 2.2 `thisRef`의 타입이 위임의 부착 위치를 제약한다

`thisRef` 파라미터의 타입은 단순한 장식이 아니다. **이 위임이 어떤 종류의 클래스/객체의 프로퍼티에 붙을 수 있는가**를 컴파일 타임에 강제한다.

```kotlin
class Animal(val name: String)

class NameEcho {
    // thisRef를 Animal로 못 박음 → Animal의 프로퍼티에만 붙을 수 있다
    operator fun getValue(thisRef: Animal, property: KProperty<*>): String =
        thisRef.name
}

class Dog {
    val echoed: String by NameEcho()   // 컴파일 에러: thisRef가 Dog인데 getValue는 Animal을 기대
}
```

`Dog`의 프로퍼티에 `NameEcho`를 붙이면, 컴파일러가 만든 게터는 `nameEcho.getValue(this /*Dog*/, ::echoed)`를 부르려 하는데, `getValue`는 `Animal`을 받으므로 `Dog`를 넣을 수 없다 → 컴파일 에러. `thisRef: Any?`로 두면 어떤 소유자든 받아들여 아무 데나 붙는다. `thisRef: Animal`로 좁히면 그 타입 계층에만 붙는 특화 위임이 된다. 이것은 위임을 **문맥에 안전하게** 만드는 강력한 도구다 — 예컨대 "이 위임은 특정 인터페이스를 구현한 소유자에만 붙어라"를 타입으로 강제할 수 있다.

### 2.3 확장 함수로서의 관례 — 표준 위임의 비밀

`getValue`/`setValue`는 **멤버 함수일 필요가 없다**. 확장 함수여도 관례로 인정된다([[35 - 확장 함수와 프로퍼티]]). 이 사실이 표준 라이브러리 위임들이 작동하는 방식의 핵심이다. `lazy { ... }`가 돌려주는 `Lazy<T>`에는 `getValue` 멤버가 없다. 대신 표준 라이브러리가 확장 함수를 제공한다.

```kotlin
// kotlin.Lazy에 대한 stdlib의 확장 (개념)
public inline operator fun <T> Lazy<T>.getValue(thisRef: Any?, property: KProperty<*>): T = value
```

그래서 `val x by lazy { ... }`가 컴파일되면 게터는 `lazyInstance.getValue(this, ::x)`를 부르고, 이 확장이 `Lazy.value`를 돌려준다. `Lazy` 인터페이스 자체는 위임의 존재를 모른다 — 위임 관례는 바깥에서 확장으로 얹혀 있다. 이는 "이미 존재하는 타입을 위임 객체로 쓰기"를 가능하게 한다. 예컨대 `Map`은 위임을 염두에 두고 만들어지지 않았지만, stdlib가 `Map`에 대한 `getValue` 확장을 제공하므로 맵을 위임으로 쓸 수 있다(§6.2).

### 2.4 표준 인터페이스 — `ReadOnlyProperty`와 `ReadWriteProperty`

직접 위임을 만들 때 관례 시그니처를 손으로 외울 필요는 없다. 표준 라이브러리가 두 함수형 인터페이스를 제공한다.

```kotlin
public fun interface ReadOnlyProperty<in T, out V> {
    operator fun getValue(thisRef: T, property: KProperty<*>): V
}

public interface ReadWriteProperty<in T, V> : ReadOnlyProperty<T, V> {
    override operator fun getValue(thisRef: T, property: KProperty<*>): V
    operator fun setValue(thisRef: T, property: KProperty<*>, value: V)
}
```

이 인터페이스를 구현하면 시그니처가 자동으로 맞춰진다. 타입 파라미터 `T`(소유자 타입)와 `V`(값 타입)의 변성 표기(`in T`, `out V`)는 §2.2에서 본 부착 위치·값 변성 규칙을 타입으로 인코딩한 것이다.

```kotlin
import kotlin.properties.ReadWriteProperty
import kotlin.reflect.KProperty

// 값을 쓸 때마다 최댓값으로만 갱신되는(단조 증가) 위임
class HighWaterMark(private var current: Int) : ReadWriteProperty<Any?, Int> {
    override fun getValue(thisRef: Any?, property: KProperty<*>): Int = current
    override fun setValue(thisRef: Any?, property: KProperty<*>, value: Int) {
        if (value > current) current = value    // 더 큰 값만 반영
    }
}

class Gauge {
    var peak: Int by HighWaterMark(0)
}

fun main() {
    val g = Gauge()
    g.peak = 5;  println(g.peak)   // => 5
    g.peak = 3;  println(g.peak)   // => 5  (3은 5보다 작아 무시됨)
    g.peak = 9;  println(g.peak)   // => 9
}
```

`ReadOnlyProperty`가 `fun interface`(SAM)라는 점도 유용하다 — 람다 하나로 읽기 전용 위임을 만들 수 있다.

```kotlin
import kotlin.properties.ReadOnlyProperty

val random: Int by ReadOnlyProperty { _, _ -> (0..100).random() }
// random을 읽을 때마다 새 난수. 백킹 필드 없음.
```

## 3. 컴파일된 형태 — 숨은 필드와 재사용되는 KProperty

### 3.1 `$delegate` 필드

§1.3에서 개념적으로 봤듯, 각 위임 프로퍼티는 위임 객체를 담는 숨은 인스턴스 필드를 하나 갖는다. JVM 백엔드에서 이 필드의 이름은 관례적으로 `프로퍼티이름$delegate`이며 `private final`이다. 생성자(또는 초기화 지점)에서 `by 표현식`을 평가해 이 필드에 대입한다.

```text
// JVM 백엔드에서 class Owner { var prop: String by Delegate() } 가 만드는 것 (개념)
class Owner {
    private final Delegate prop$delegate;      // 위임 객체 저장

    Owner() {
        this.prop$delegate = new Delegate();   // by 표현식은 여기서 딱 한 번 평가
    }

    public String getProp() {
        return prop$delegate.getValue(this, <KProperty for prop>);
    }
    public void setProp(String value) {
        prop$delegate.setValue(this, <KProperty for prop>, value);
    }
}
```

여기서 두 가지가 분명해진다. **위임 객체는 프로퍼티마다 하나씩** 존재하고 소유 인스턴스 안에 산다. 소유 객체를 100개 만들면 위임 객체도 100개 만들어진다(각 소유 인스턴스가 자기 위임을 가짐). 그리고 **`by 표현식`의 평가 시점**은 그 필드가 초기화되는 시점 — 즉 소유 객체 생성 시(멤버 프로퍼티) 또는 선언 도달 시(로컬)다. `by lazy { 무거운계산() }`이라도 `lazy(...)` **함수 호출 자체**는 객체 생성 시 일어난다(단지 `Lazy` 래퍼를 만들 뿐, 안의 람다는 아직 안 돈다).

### 3.2 재사용되는 `KProperty` — `$$delegatedProperties` 배열

`getValue(this, ::prop)`에서 `::prop`은 프로퍼티 참조, 즉 `KProperty` 객체다([[44 - 애노테이션과 리플렉션]]). 순진하게 생각하면 매 접근마다 이 참조 객체를 새로 할당해야 할 것 같지만, 그러면 읽기 한 번에 객체 하나가 쓰레기로 쌓인다. 컴파일러는 이를 피한다.

JVM 백엔드에서 컴파일러는 클래스마다 **위임된 프로퍼티들의 `KProperty` 메타데이터를 담는 정적 배열**을 하나 생성한다(관례적으로 `$$delegatedProperties`라 불린다). 각 위임 프로퍼티의 접근자는 이 배열의 고정된 인덱스에서 미리 만들어진 `KProperty` 객체를 꺼내 쓴다.

```text
// 개념적 형태 (JVM 백엔드)
class Owner {
    static final KProperty[] $$delegatedProperties = {
        // prop에 대한 KPropertyImpl, 클래스 로드 시 한 번 생성
        Reflection.mutableProperty1(new MutablePropertyReference1Impl(Owner.class, "prop", "getProp()...")),
    };
    public String getProp() {
        return prop$delegate.getValue(this, $$delegatedProperties[0]);   // 재사용
    }
}
```

즉 `KProperty` 객체는 **프로퍼티당 하나**만 만들어져 클래스 수명 내내 공유된다. 매 접근에 새로 할당되지 않으므로 GC 압박이 없다.

> **성능 주의**: 위임을 쓰면 이 `KProperty` 메타데이터 때문에 아주 약간의 클래스 로드 비용과 정적 메모리가 든다. 대부분 무시할 수준이지만, 위임 프로퍼티가 수천 개인 코드를 생성한다면 메타데이터도 그만큼 쌓인다. 또한 새 Kotlin 버전들은 위임이 `property` 파라미터를 **실제로 쓰지 않을 때** 이 메타데이터 생성을 생략하는 최적화를 도입해 왔다(구현·버전에 따라). 그래서 "위임 프로퍼티는 항상 `KProperty` 객체를 만든다"는 서술은 현대 컴파일러에서는 정확하지 않을 수 있다 — 위임이 프로퍼티 메타데이터를 참조하는지에 따라 달라진다.

### 3.3 왜 `getValue`가 `property`를 받는가 — 자기 성찰하는 위임

`property: KProperty<*>` 파라미터는 위임에게 "내가 지금 어느 프로퍼티를 대신 처리하고 있는가"를 알려 준다. 이것이 위임을 **문맥 인지적(context-aware)** 으로 만든다. 하나의 위임 구현이 여러 프로퍼티에 붙어, 프로퍼티 이름에 따라 다르게 동작할 수 있다. 맵 위임(§6.2)이 대표적이다 — `getValue`가 `property.name`을 키로 써서 맵을 조회한다. 이름이 없으면 위임은 자기가 어떤 키를 봐야 하는지 알 수 없다.

```kotlin
import kotlin.reflect.KProperty

// property.name을 키로 삼아 환경 변수를 읽는 위임 (일반 도메인 예)
class EnvVar {
    operator fun getValue(thisRef: Any?, property: KProperty<*>): String? =
        System.getenv(property.name)
}

object Config {
    val PATH: String? by EnvVar()      // property.name == "PATH" 로 조회
    val HOME: String? by EnvVar()      // property.name == "HOME" 으로 조회
}
// 같은 EnvVar 구현이 프로퍼티 이름에 따라 다른 변수를 읽는다
```

### 3.4 평범한 프로퍼티 vs 위임 프로퍼티 — 바이트코드 대조

두 프로퍼티가 컴파일되면 얼마나 다른지를 나란히 보면, 위임의 간접비가 어디서 오는지 눈에 들어온다. JVM 백엔드 기준 개념적 형태다.

```text
// (A) 평범한 프로퍼티: class Owner { var plain: String = "x" }
class Owner {
    private String plain = "x";               // 진짜 백킹 필드
    public String getPlain() { return plain; }             // 필드 로드 한 번
    public void setPlain(String v) { plain = v; }          // 필드 저장 한 번
}

// (B) 위임 프로퍼티: class Owner { var deleg: String by Delegate() }
class Owner {
    static final KProperty[] $$delegatedProperties = { /* deleg 메타데이터 */ };
    private final Delegate deleg$delegate = new Delegate();      // 위임 객체
    public String getDeleg() {
        return deleg$delegate.getValue(this, $$delegatedProperties[0]);  // 호출 한 번 + 메타 로드
    }
    public void setDeleg(String v) {
        deleg$delegate.setValue(this, $$delegatedProperties[0], v);      // 호출 한 번 + 메타 로드
    }
}
```

(A)의 게터는 필드 하나를 읽어 돌려준다 — JIT가 인라인하면 사실상 필드 접근이다. (B)의 게터는 `deleg$delegate` 필드를 로드하고, 메타데이터 배열에서 `KProperty`를 꺼내고, `getValue`를 **가상 호출**한다. 이 가상 호출이 위임의 근본 비용이다(§9.1). 단, `getValue`가 `inline`이면([[15 - 인라인 함수와 reified]]) 컴파일러가 그 본문을 게터 안에 펼쳐 호출을 지울 수 있다 — `Lazy.getValue`가 `inline`인 이유가 이것이다. 그래서 "위임은 항상 호출 오버헤드가 있다"는 서술은 부정확하다. **인라인 가능한 위임은 오버헤드가 사라진다.**

```java
// Java 관점에서 위임 프로퍼티를 부르는 코드 (상호운용, 45장)
Owner o = new Owner();
String s = o.getDeleg();     // Kotlin의 by는 Java에는 그냥 getter로 보인다
```

Java에서 보면 위임 프로퍼티는 그냥 `getDeleg()`/`setDeleg()` 메서드 쌍일 뿐이다. `by`도, `KProperty`도, 위임 객체도 Java 소스에는 드러나지 않는다 — 전부 Kotlin 컴파일러가 게터/세터 본문 안에 감춘 구현 세부다.

## 4. `lazy` — 지연 초기화와 세 가지 스레드 모드

표준 라이브러리에서 가장 널리 쓰이는 위임은 `lazy`다. "값이 처음 필요해질 때 딱 한 번 계산하고, 이후에는 캐시된 값을 돌려준다"는 지연 초기화(lazy initialization)를 캡슐화한다. [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 예고된 `by lazy`가 여기서 정본으로 다뤄진다.

### 4.1 기본 동작과 `Lazy<T>` 인터페이스

```kotlin
class Report {
    val summary: String by lazy {
        println("...무거운 계산 수행...")
        "요약 결과"
    }
}

fun main() {
    val r = Report()
    println("리포트 생성됨 (아직 summary 계산 안 함)")
    println(r.summary)    // => ...무거운 계산 수행... \n 요약 결과   (여기서 처음 계산)
    println(r.summary)    // => 요약 결과   (캐시, 람다 재실행 없음)
}
// 출력:
// 리포트 생성됨 (아직 summary 계산 안 함)
// ...무거운 계산 수행...
// 요약 결과
// 요약 결과
```

`lazy(initializer)`는 `Lazy<T>` 인터페이스를 구현한 객체를 돌려준다.

```kotlin
public interface Lazy<out T> {
    public val value: T                 // 접근 시 (필요하면) 초기화 후 반환
    public fun isInitialized(): Boolean // 이미 초기화됐는지 (초기화 유발 없이)
}
```

`getValue`는 stdlib 확장(§2.3)이 `value`로 위임한다. `isInitialized()`로 "계산이 이미 일어났는지"를 부수효과 없이 확인할 수 있다.

```kotlin
val lazyVal = lazy { 42 }
println(lazyVal.isInitialized())   // => false
val x: Int by lazyVal
// x를 아직 안 읽었으므로 여전히 미초기화
```

주의: `by lazy`는 `val`에만 쓴다. `Lazy<T>`에는 `getValue` 확장만 있고 `setValue`가 없으므로, `var`에 붙이면 컴파일 에러다. 지연 "초기화"는 한 번 정해지면 끝이라는 의미상 당연하다.

### 4.2 세 가지 스레드 안전 모드

`lazy`의 핵심 미묘함은 **여러 스레드가 동시에 첫 접근을 할 때** 무슨 일이 벌어지느냐다. `lazy`는 세 가지 모드로 이를 다스린다. `LazyThreadSafetyMode` enum이다.

| 모드 | 락 사용 | 초기화 람다 실행 횟수(경합 시) | 여러 스레드 안전 | 비용 |
|------|---------|------------------------------|----------------|------|
| `SYNCHRONIZED` (기본) | 예 (이중 검사 락) | 정확히 1회 | 예 | 락 획득 오버헤드 |
| `PUBLICATION` | 아니오 (CAS) | 1회 이상 가능, 첫 성공 값만 채택 | 예 | 람다 중복 실행 가능 |
| `NONE` | 아니오 | 정의되지 않음(경합 시 깨짐) | **아니오** | 가장 빠름 |

```kotlin
// 기본: 인자 없는 lazy(initializer)는 SYNCHRONIZED
val a: Int by lazy { compute() }

// 명시적 모드 지정
val b: Int by lazy(LazyThreadSafetyMode.PUBLICATION) { compute() }
val c: Int by lazy(LazyThreadSafetyMode.NONE) { compute() }
```

각 모드를 뜯어보자.

**`SYNCHRONIZED`(기본)**: 초기화 시 락(모니터)을 획득해 이중 검사 락(double-checked locking)을 수행한다. 여러 스레드가 동시에 첫 접근을 해도 **초기화 람다는 정확히 한 번만** 돈다. 나머지 스레드는 락을 기다렸다가 완성된 값을 받는다. 안전하지만 첫 접근에 동기화 비용이 든다(초기화 이후 읽기는 락 없이 빠르다 — 값이 채워지면 락 경로를 타지 않음).

**`PUBLICATION`**: 락 대신 원자적 compareAndSet을 쓴다. 여러 스레드가 동시에 첫 접근을 하면 **초기화 람다가 여러 번 실행될 수 있다**. 그러나 그중 **가장 먼저 CAS에 성공한 값 하나만** 저장되고, 모든 스레드가 그 값을 본다. 람다가 부수효과 없이 순수하고, 여러 번 계산돼도 무방하며, 락 경합을 피하고 싶을 때 쓴다.

**`NONE`**: 아무 동기화도 하지 않는다. **단일 스레드에서만** 안전하다. 여러 스레드가 경합하면 초기화가 중복되거나, 심하게는 다른 스레드가 미완성/부분 초기화 상태를 볼 수 있다(메모리 가시성 미보장). 절대 여러 스레드가 접근하지 않음이 보장될 때만, 최소 비용을 위해 쓴다.

```text
SYNCHRONIZED 초기화 (개념)          PUBLICATION 초기화 (개념)
  스레드1: 락 획득                      스레드1: 람다 실행 → CAS 시도
  스레드2: 락 대기 ────┐                스레드2: 람다 실행 → CAS 시도
  스레드1: 람다 1회 실행 │               (둘 다 실행되지만)
  스레드1: 값 저장, 락 해제              첫 CAS 성공값만 채택 → 나머지 버림
  스레드2: 락 획득 → 값 이미 있음 → 반환   모든 스레드 같은 값 관측
```

> **역사 메모**: `lazy`의 기본 모드가 `SYNCHRONIZED`인 것은 "안전이 기본, 최적화는 선택"이라는 Kotlin의 보수적 기본값 철학을 보여 준다. 많은 지연 프로퍼티가 사실은 단일 스레드에서만 쓰이지만, 라이브러리는 사용자가 스레드 안전성을 명시적으로 포기(`NONE`)하기 전까지 안전한 쪽을 준다. 이는 `val`이 기본이고 `var`가 선택인 것, 타입이 기본 non-null이고 `?`로 nullable을 여는 것과 같은 결의 설계다.

### 4.3 `lazy`의 스레드 안전이 기대는 것

`SYNCHRONIZED` 모드의 "정확히 1회"와 `PUBLICATION`의 "완성된 값만 관측"은 그냥 되는 게 아니라 **메모리 모델**의 보장 위에 서 있다. 이중 검사 락이나 원자적 CAS가 올바르려면, 한 스레드가 쓴 초기화 결과가 다른 스레드에게 **완전히 보여야**(happens-before) 한다. JVM 백엔드에서 이는 `volatile` 시맨틱과 모니터/원자 연산의 메모리 배리어로 보장된다. 이 기반이 없으면 이중 검사 락은 악명 높은 "부분 초기화 객체 관측" 버그로 무너진다. 그 메커니즘의 정본은 [[43 - 동시성과 메모리 모델]]이다.

`NONE`이 위험한 정확한 이유가 이것이다 — `NONE`은 이 메모리 배리어를 생략한다. 그래서 한 스레드의 초기화가 다른 스레드에게 안 보이거나, 심지어 필드는 보이는데 그 필드가 가리키는 객체의 내부는 미완성으로 보이는 재배열이 이론적으로 가능하다. "단일 스레드 전용"이라는 조건은 이 배리어 부재를 상쇄하는 유일한 전제다.

### 4.4 `lazy`의 내부 — 센티넬 값과 이중 검사

`SYNCHRONIZED` 모드의 `lazy`가 내부적으로 무엇을 하는지 개념을 스케치하면, "첫 접근에 한 번"이 어떻게 구현되는지가 드러난다. 핵심은 **"아직 초기화 안 됨"을 나타내는 특별한 센티넬(sentinel) 값**과 이중 검사 락이다.

```kotlin
// SynchronizedLazyImpl의 개념적 스케치 (실제 stdlib 구현의 단순화)
private object UNINITIALIZED     // "아직 계산 안 됨"을 뜻하는 유일한 표식

class SynchronizedLazyImpl<T>(initializer: () -> T) : Lazy<T> {
    private var initializer: (() -> T)? = initializer
    @Volatile private var _value: Any? = UNINITIALIZED   // volatile: 스레드 간 가시성
    private val lock = this

    override val value: T
        get() {
            val v1 = _value
            if (v1 !== UNINITIALIZED) {          // 1차 검사 (락 없이, 빠른 경로)
                @Suppress("UNCHECKED_CAST")
                return v1 as T
            }
            return synchronized(lock) {
                val v2 = _value
                if (v2 !== UNINITIALIZED) {      // 2차 검사 (락 안에서)
                    @Suppress("UNCHECKED_CAST")
                    v2 as T
                } else {
                    val computed = initializer!!()   // 딱 한 번 실행
                    _value = computed
                    initializer = null               // 초기화 후 람다 참조 해제 (GC 도움)
                    computed
                }
            }
        }

    override fun isInitialized(): Boolean = _value !== UNINITIALIZED
}
```

세 가지가 중요하다. 첫째, **`@Volatile`** 이 `_value`에 붙어 한 스레드가 쓴 값이 다른 스레드에 즉시 보이도록 한다(happens-before, [[43 - 동시성과 메모리 모델]]). 이것 없이는 이중 검사 락이 깨진다. 둘째, **1차 검사가 락 없이** 일어나 이미 초기화된 값의 읽기는 락 경로를 타지 않는다 — 그래서 초기화 이후 반복 읽기가 빠르다. 셋째, 초기화가 끝나면 **`initializer = null`** 로 람다 참조를 놓아 준다. 람다가 캡처한 무거운 객체들([[14 - 클로저와 캡처]])이 값 계산 후엔 더 필요 없으니 GC 대상이 되게 하는 배려다.

`NONE` 모드(`UnsafeLazyImpl`)는 이 스케치에서 `@Volatile`과 `synchronized` 블록을 통째로 뺀 버전이다 — 그래서 빠르지만 여러 스레드가 경합하면 센티넬 검사 자체가 깨져 초기화가 중복되거나 부분 상태가 새어 나온다. `PUBLICATION` 모드(`SafePublicationLazyImpl`)는 락 대신 원자적 업데이터로 `_value`를 `UNINITIALIZED`에서 계산값으로 **compareAndSet** 한다 — 여러 스레드가 동시에 `initializer`를 실행할 수 있지만, CAS에 처음 성공한 하나의 값만 심어지고 나머지는 버려진다.

> **성능 주의**: `lazy`의 `@Volatile` 읽기는 JVM에서 아주 저렴하지만 완전히 공짜는 아니다(메모리 배리어). 극단적으로 뜨거운 루프에서 이미 초기화된 `lazy` 프로퍼티를 수백만 번 읽는다면, 값을 지역 변수로 한 번 꺼내 두는 편이 `volatile` 읽기를 반복하는 것보다 빠를 수 있다. 대부분의 코드에서는 무의미한 차이다 — 측정 없이 미리 최적화하지 말 것.

### 4.5 `lazy` vs `lateinit` — 갈림길

[[11 - 변수와 초기화 - val과 const와 lateinit]]의 `lateinit`과 `by lazy`는 둘 다 "나중 초기화"를 다루지만 성격이 다르다.

| | `by lazy` | `lateinit var` |
|---|-----------|----------------|
| 변경 가능성 | `val` (한 번 계산 후 불변) | `var` (여러 번 대입 가능) |
| 초기화 주체 | 위임이 **스스로**(첫 접근 시 람다) | **외부**가 대입해 줘야 함 |
| 초기화 시점 | 첫 읽기 시 자동 | 임의 시점, 개발자 책임 |
| 미초기화 접근 | 불가능(항상 람다로 초기화됨) | `UninitializedPropertyAccessException` (M9) |
| 원시 타입(JVM) | 가능(`Int` 등 OK) | **불가**(`lateinit var n: Int` 컴파일 에러) |
| 스레드 안전 | 모드로 선택 | 없음(그냥 필드) |
| 초기화 여부 확인 | `isInitialized()` | `::prop.isInitialized` |

요지: 값이 **스스로 계산될 수 있고 한 번 정해지면 끝**이면 `by lazy`. 값이 **외부(프레임워크, DI, 세터)에서 주입**되고 그전엔 없으며 나중에 바뀔 수도 있으면 `lateinit var`. 원시 타입을 지연시키고 싶은데 `lateinit`이 안 될 때, "외부 주입"이 필요하면 `by Delegates.notNull()`(§6.1)이 다리가 된다.

## 5. `observable`과 `vetoable` — 변경을 관측하고 거부하기

`kotlin.properties.Delegates`는 몇 가지 이미 만들어진 위임 팩토리를 제공한다. 그중 `observable`과 `vetoable`은 **값이 바뀔 때 콜백**을 걸어 주는 `var` 위임이다.

### 5.1 `observable` — 변경 후 통지

`Delegates.observable(초기값) { property, oldValue, newValue -> ... }`는 프로퍼티가 대입될 때마다 **대입이 일어난 후** 콜백을 호출한다.

```kotlin
import kotlin.properties.Delegates

class TemperatureSensor {
    var celsius: Int by Delegates.observable(0) { prop, old, new ->
        println("${prop.name}: $old°C -> $new°C")
    }
}

fun main() {
    val s = TemperatureSensor()
    s.celsius = 20     // => celsius: 0°C -> 20°C
    s.celsius = 25     // => celsius: 20°C -> 25°C
    s.celsius = 25     // => celsius: 25°C -> 25°C  (같은 값이어도 콜백은 불린다)
}
```

콜백의 세 인자: 프로퍼티 메타데이터(`KProperty`), 이전 값, 새 값. 콜백은 **값이 이미 저장된 뒤** 불리므로, 반환값이 없다(`Unit`) — 변경을 되돌릴 수 없고 그저 통지받을 뿐이다. 같은 값으로 재대입해도 콜백이 불린다는 점에 유의(값 동일성 검사를 하지 않음).

### 5.2 `vetoable` — 변경 전 거부권

`Delegates.vetoable(초기값) { property, oldValue, newValue -> Boolean }`은 대입이 **일어나기 전**에 콜백을 호출하고, 콜백이 `false`를 돌려주면 **대입을 취소**한다(veto = 거부).

```kotlin
import kotlin.properties.Delegates

class BoundedCounter {
    // 0 미만으로는 내려가지 못하는 카운터
    var count: Int by Delegates.vetoable(0) { _, _, new ->
        new >= 0     // 새 값이 음수면 false → 대입 거부
    }
}

fun main() {
    val c = BoundedCounter()
    c.count = 5;   println(c.count)   // => 5   (5 >= 0, 허용)
    c.count = -3;  println(c.count)   // => 5   (-3 < 0, 거부 → 이전 값 유지)
    c.count = 10;  println(c.count)   // => 10
}
```

`vetoable`의 콜백은 `Boolean`을 반환한다는 점이 `observable`과의 결정적 차이다. `true`면 대입 진행, `false`면 이전 값 유지. 콜백은 **대입 확정 전**에 불리므로 새 값을 검증(validation)하는 게이트로 쓴다. 검증 실패 시 값이 조용히 안 바뀌는 것이 마음에 걸리면, 콜백 안에서 예외를 던져 "거부"를 "실패"로 승격할 수도 있다.

### 5.3 둘의 공통 뿌리 — `ObservableProperty`

`observable`과 `vetoable`은 사실 stdlib의 추상 클래스 `ObservableProperty<T>` 하나에서 갈라진 형제다. 이 클래스는 값을 필드에 들고 있으면서, 대입 시 두 훅을 부른다: `beforeChange`(대입 전, `Boolean` 반환 — false면 취소)와 `afterChange`(대입 후, 통지). `vetoable`은 `beforeChange`를, `observable`은 `afterChange`를 당신의 람다로 채운 것이다. 원하면 이 추상 클래스를 직접 상속해 둘을 결합한 위임을 만들 수 있다.

```kotlin
import kotlin.properties.ObservableProperty
import kotlin.reflect.KProperty

// 대입 전 검증 + 대입 후 로그를 함께
class ValidatedLogged(initial: Int) : ObservableProperty<Int>(initial) {
    override fun beforeChange(property: KProperty<*>, oldValue: Int, newValue: Int): Boolean {
        return newValue in 0..100     // 범위 밖이면 거부
    }
    override fun afterChange(property: KProperty<*>, oldValue: Int, newValue: Int) {
        println("${property.name}: $oldValue -> $newValue 저장됨")
    }
}

class Percentage {
    var value: Int by ValidatedLogged(0)
}
```

이 구조를 보면, `observable`/`vetoable`은 마법이 아니라 **관례를 구현한 평범한 클래스**임이 드러난다. 위임 프로퍼티의 강력함은 바로 이것 — 언어가 특별한 위임을 몇 개 내장한 게 아니라, 누구나 관례만 만족하면 위임 객체를 만들 수 있고, 표준 라이브러리의 위임도 그렇게 만들어져 있다는 점이다.

## 6. `notNull`과 맵 위임 — 나머지 표준 위임

### 6.1 `Delegates.notNull` — `lateinit`이 닿지 못하는 곳

`Delegates.notNull<T>()`는 **읽기 전에 반드시 쓰여야 하는** non-null `var` 위임을 만든다. 초기화 전에 읽으면 `IllegalStateException`을 던진다.

```kotlin
import kotlin.properties.Delegates

class Connection {
    var port: Int by Delegates.notNull()    // 초기값 없음. 쓰기 전 읽으면 예외.
}

fun main() {
    val c = Connection()
    // println(c.port)   // => IllegalStateException: Property port should be initialized before get.
    c.port = 8080
    println(c.port)      // => 8080
}
```

이것은 `lateinit`과 무엇이 다른가? 겉보기 의미는 거의 같다 — "나중에 주입될 non-null 값, 그전에 읽으면 예외". 하지만 결정적 차이가 하나 있다: **원시 타입(JVM)**. `lateinit var`은 JVM 백엔드에서 "미초기화" 상태를 `null`로 표현하는데, 원시 타입(`Int`, `Long`, `Double`, `Boolean` 등)은 `null`이 될 수 없어 `lateinit`을 쓸 수 없다.

```kotlin
class Bad {
    lateinit var n: Int    // 컴파일 에러: 'lateinit' modifier is not allowed on properties of primitive types
}
class Good {
    var n: Int by Delegates.notNull()   // OK — 위임 객체가 Int?를 내부에 들고 미초기화를 관리
}
```

`notNull`은 내부적으로 값을 `T?`(nullable 박스)로 들고 있다가, `getValue` 시 null이면 예외를 던지고 아니면 언박싱해 돌려준다. 그래서 원시 타입도 지연 초기화할 수 있다. 대가는 **박싱**(JVM에서 `Int`가 위임 필드 안에서 `Integer`로 박스됨)과 위임 객체 자체의 할당이다. 그래서 원시 타입이 아니라면 대개 `lateinit`이 더 가볍다. `notNull`은 "원시 타입인데 지연 초기화가 필요하다"는 좁은 틈을 메우는 도구로 이해하는 게 정확하다.

> **흔한 오해**: "`lateinit`이 있으니 `notNull`은 필요 없다"는 생각. 원시 타입에는 `lateinit`을 못 쓴다는 점, 그리고 `notNull`은 어떤 타입에도(제네릭 `T` 포함) 적용 가능하다는 점에서 둘의 관할이 다르다. 반대로 참조 타입이라면 `lateinit`이 박싱·위임 객체 없이 더 효율적이다.

### 6.2 맵 위임 — `by map`

프로퍼티를 맵의 항목으로 백킹하는 위임이다. 동적 데이터(JSON 파싱 결과, 설정 맵 등)를 타입 있는 프로퍼티처럼 다룰 때 쓴다. stdlib가 `Map`과 `MutableMap`에 대한 `getValue`/`setValue` 확장을 제공하므로, 맵을 그대로 `by` 뒤에 둘 수 있다.

```kotlin
class Account(map: Map<String, Any?>) {
    val name: String by map      // map["name"] 을 읽어 String으로
    val balance: Int by map      // map["balance"] 을 읽어 Int로
}

fun main() {
    val acc = Account(mapOf(
        "name" to "Alice",
        "balance" to 1000
    ))
    println(acc.name)      // => Alice
    println(acc.balance)   // => 1000
}
```

`val name: String by map`에서 게터는 `map.getValue(this, ::name)` → 확장이 `map["name"]`을 조회한다. **프로퍼티 이름이 곧 맵 키**다(§3.3의 `property.name` 활용의 전형). 조회 결과는 프로퍼티 타입으로 캐스팅된다.

`var` 프로퍼티는 `MutableMap`을 쓴다 — `setValue` 확장이 `map[property.name] = value`로 되받아 쓴다.

```kotlin
class MutableAccount(val map: MutableMap<String, Any?>) {
    var name: String by map
}
fun main() {
    val m = mutableMapOf<String, Any?>("name" to "Bob")
    val a = MutableAccount(m)
    a.name = "Carol"
    println(m["name"])   // => Carol  (위임 세터가 원본 맵에 되씀)
}
```

맵 위임의 함정: 키가 없거나 타입이 안 맞으면 **런타임에** 터진다. `by map`은 컴파일 타임에 "그 키가 맵에 있는지"를 검증하지 못한다 — 맵 내용은 실행 중에나 알 수 있으니까. 키 부재 시 `getValue` 확장(`Map`의)은 `NoSuchElementException`을, 타입 불일치는 `ClassCastException`을 던진다. 정적 타입 언어의 안전망 밖에 있는, 편의를 위한 얇은 다리라는 점을 잊지 말아야 한다.

> **명세 정밀**: `Map`에 대한 위임 확장에는 두 갈래가 있다. `Map<String, V>.getValue`는 키가 없으면 예외를 던지지만, 프로퍼티가 nullable(`by map`을 `String?`에 쓰는 등)이고 stdlib 오버로드가 다르게 해소되는 경우 동작이 달라질 수 있다. 정확한 거동은 사용하는 확장 오버로드에 의존하므로, "맵 위임은 항상 예외를 던진다/null을 준다"고 단정하지 말고 대상 타입에 맞춰 확인하는 게 안전하다.

### 6.3 커스텀 위임을 처음부터 끝까지 짜 보기

지금까지 조각으로 본 관례들을 하나의 완성된 위임으로 엮어 보자. 요구사항: "은행 계좌의 잔액 프로퍼티는 음수가 될 수 없고, 변경될 때마다 감사 로그를 남기며, 특정 인터페이스를 구현한 소유자에만 붙는다." 이 셋을 각각 `setValue`의 검증, `setValue`의 부수효과, `thisRef` 타입 제약으로 충족한다.

```kotlin
import kotlin.reflect.KProperty

// 소유자가 갖춰야 할 계약 — thisRef 타입으로 강제할 대상
interface Auditable {
    fun audit(message: String)
}

// 음수 금지 + 감사 로그 + Auditable 소유자 전용 위임
class NonNegativeMoney(private var amount: Long) {
    operator fun getValue(thisRef: Auditable, property: KProperty<*>): Long = amount

    operator fun setValue(thisRef: Auditable, property: KProperty<*>, value: Long) {
        require(value >= 0) { "${property.name} 는 음수가 될 수 없다: $value" }
        val old = amount
        amount = value
        thisRef.audit("${property.name}: $old -> $value")   // 소유자의 audit 호출
    }
}

class Account(initial: Long) : Auditable {
    var balance: Long by NonNegativeMoney(initial)
    override fun audit(message: String) = println("[감사] $message")
}

fun main() {
    val acc = Account(100)
    println(acc.balance)   // => 100
    acc.balance = 250      // => [감사] balance: 100 -> 250
    println(acc.balance)   // => 250
    // acc.balance = -5    // => IllegalArgumentException: balance 는 음수가 될 수 없다: -5
}
```

여기서 세 관례가 동시에 일한다. **`thisRef: Auditable`** 은 이 위임이 `Auditable`을 구현하지 않은 클래스에는 붙지 못하게 컴파일 타임에 막는다(§2.2). **`setValue`의 `require`** 는 불변식(invariant)을 강제한다. **`thisRef.audit(...)`** 는 소유자의 능력을 위임 안에서 호출한다 — 위임이 소유자와 협력하는 패턴이다. 만약 `NonNegativeMoney`를 `Auditable`이 아닌 클래스에 붙이면 이렇게 된다.

```kotlin
class Wallet {
    var cash: Long by NonNegativeMoney(0)
    // 컴파일 에러: getValue/setValue가 Auditable thisRef를 기대하는데 Wallet은 Auditable이 아님
}
```

이 예가 보여 주는 것은, 위임이 단순히 "값을 대신 저장하는 상자"가 아니라 **타입 제약·불변식·소유자 협력을 한데 묶는 재사용 단위**라는 점이다. 같은 `NonNegativeMoney`를 여러 `Auditable` 클래스의 여러 금액 프로퍼티에 붙이면, 음수 금지와 감사 로깅이라는 정책이 단 한 곳(위임 구현)에 집중된다. 이것이 22장의 커스텀 접근자가 주지 못한, 위임만의 재사용 가치다.

## 7. `provideDelegate` — 위임을 만드는 위임

지금까지 `by 표현식`의 `표현식`은 곧바로 위임 객체였다. `provideDelegate`는 그 사이에 **한 겹**을 끼운다: `by 표현식`을 평가한 결과가 위임 객체가 아니라 **"위임 객체를 만들어 주는 공장"** 이 되고, 컴파일러가 그 공장에게 프로퍼티 메타데이터를 넘겨 진짜 위임을 받아 온다.

### 7.1 시그니처와 호출 시점

```kotlin
import kotlin.reflect.KProperty

operator fun provideDelegate(thisRef: Any?, property: KProperty<*>): ActualDelegate
```

`by 표현식`의 결과 객체에 `provideDelegate`가 정의돼 있으면, 컴파일러는 `$delegate` 필드를 채울 때 `표현식` 자체를 넣는 대신 `표현식.provideDelegate(thisRef, property)`를 **호출한 결과**를 넣는다.

```text
provideDelegate 없을 때:
    prop$delegate = 표현식

provideDelegate 있을 때:
    prop$delegate = 표현식.provideDelegate(this, ::prop)
```

결정적 이점: `provideDelegate`는 **프로퍼티가 초기화되는 시점(객체 생성 시)에, 프로퍼티 메타데이터에 접근하며** 실행된다. 그래서 위임을 만드는 그 순간에 검증·등록 같은 일을 할 수 있다. 반면 일반 `getValue`는 **프로퍼티가 읽힐 때**에야 불린다. "생성 시점에 뭔가 하고 싶다"가 `provideDelegate`의 존재 이유다.

### 7.2 언제 쓰나 — 생성 시점 검증의 예

가장 흔한 용도는 "이 위임이 붙는 프로퍼티가 어떤 조건을 만족하는지 **생성 시점에** 검사"하는 것이다. 예컨대 프로퍼티 이름이 규칙에 맞는지, 소유 클래스가 특정 조건을 갖췄는지를 첫 접근을 기다리지 않고 즉시 확인한다.

```kotlin
import kotlin.reflect.KProperty
import kotlin.properties.ReadOnlyProperty

// 프로퍼티 이름이 대문자로 시작해야만 허용하는 위임 (일반 도메인 규칙 예)
class UppercaseChecked<T>(private val value: T) {
    operator fun provideDelegate(thisRef: Any?, property: KProperty<*>): ReadOnlyProperty<Any?, T> {
        require(property.name.first().isUpperCase()) {
            "프로퍼티 '${property.name}' 는 대문자로 시작해야 한다"
        }
        return ReadOnlyProperty { _, _ -> value }
    }
}

fun <T> checked(value: T) = UppercaseChecked(value)

class Registry {
    val Alpha: String by checked("ok")    // OK — 객체 생성 시 검증 통과
    // val beta: String by checked("no")  // 객체 생성 시 IllegalArgumentException
}
```

`Alpha`는 아직 한 번도 **읽지 않았는데도** `Registry` 객체를 만드는 순간 `provideDelegate`가 돌아 이름을 검증한다. 만약 이 검증을 `getValue`에 뒀다면, 프로퍼티를 실제로 읽기 전까지 오류가 숨어 있을 것이다. `provideDelegate`는 오류를 **더 이른 시점(생성)** 으로 당겨 준다.

### 7.3 `PropertyDelegateProvider` — 표준 인터페이스

`getValue`/`setValue`에 `ReadOnlyProperty`/`ReadWriteProperty`가 있듯, `provideDelegate`에도 표준 함수형 인터페이스가 있다: `PropertyDelegateProvider<in T, out D>`.

```kotlin
public fun interface PropertyDelegateProvider<in T, out D> {
    operator fun provideDelegate(thisRef: T, property: KProperty<*>): D
}
```

이를 쓰면 공장을 람다로 간결히 표현할 수 있다.

```kotlin
import kotlin.properties.PropertyDelegateProvider
import kotlin.properties.ReadOnlyProperty

fun namedConstant(value: Int) = PropertyDelegateProvider<Any?, ReadOnlyProperty<Any?, Int>> { _, property ->
    println("위임 생성: ${property.name}")
    ReadOnlyProperty { _, _ -> value }
}

class Box {
    val size: Int by namedConstant(10)   // 객체 생성 시 "위임 생성: size" 출력
}
```

`provideDelegate`가 돌려주는 `D`는 다시 `getValue`(그리고 필요하면 `setValue`) 관례를 만족해야 한다. 즉 두 겹의 관례가 맞물린다: 바깥은 "위임을 제공"(`provideDelegate`), 안쪽은 "값을 제공"(`getValue`/`setValue`).

## 8. 로컬 위임 — 함수 안의 위임 변수

위임은 클래스 프로퍼티뿐 아니라 **함수 안의 지역 변수**에도 붙일 수 있다. `val`/`var` 지역 변수를 `by`로 위임한다.

```kotlin
fun process() {
    val config: String by lazy {
        println("설정 로드")
        readConfigFromDisk()
    }

    if (needsConfig()) {
        println(config)    // 여기 처음 도달할 때만 "설정 로드" + readConfigFromDisk()
    }
    // needsConfig()가 false면 config는 끝내 초기화되지 않음
}
```

로컬 위임의 값은 **분기에 따라 진짜로 필요할 때만** 계산을 미룰 수 있다는 데 있다. 위 예에서 `needsConfig()`가 거짓이면 디스크 읽기는 아예 일어나지 않는다. 지역 변수를 그냥 `val config = readConfigFromDisk()`로 두면 도달 즉시 계산되지만, `by lazy`로 두면 실제 사용 지점까지 미뤄진다.

로컬 위임에서 `getValue`/`setValue`의 `thisRef`는 **`null`** 이다 — 지역 변수에는 소유 객체가 없기 때문이다. 그래서 로컬 위임에 쓸 위임 객체의 `getValue`는 `thisRef: Nothing?`(또는 `Any?`)를 받아야 한다. `property` 파라미터는 여전히 유효해서, 로컬 변수의 이름 등 메타데이터를 제공한다.

컴파일 형태도 멤버 위임과 유사하되 더 단순하다 — 위임 객체는 지역 슬롯(또는 클로저 캡처, [[14 - 클로저와 캡처]])에 저장되고, 변수 읽기/쓰기가 `getValue`/`setValue` 호출로 번역된다. 로컬 위임은 특히 스코프 안에서만 의미 있는 지연·관측 로직을 깔끔히 표현할 때 쓰인다.

## 9. 성능·함정·오개념 — 위임은 공짜가 아니다

### 9.1 위임의 런타임 비용

위임 프로퍼티는 편의를 준 만큼 **간접비**를 얹는다. 정확히 어디에 비용이 붙는지 보자.

- **읽기당 함수 호출 하나**: 평범한 프로퍼티 읽기가 필드 접근 한 번이라면, 위임 프로퍼티 읽기는 `게터 → $delegate 필드 로드 → getValue 호출`이다. `getValue`가 `inline`이면(예: `Lazy.getValue`) 이 호출은 인라인되어 사라질 수 있지만([[15 - 인라인 함수와 reified]]), 인라인 안 되는 위임은 매 읽기마다 가상 호출이 하나 낀다.
- **위임 객체 할당**: 소유 인스턴스마다 위임 객체가 하나씩 만들어진다. `Lazy` 래퍼, `ObservableProperty` 인스턴스 등이 그것이다. 프로퍼티가 많고 인스턴스가 많으면 이 할당이 쌓인다.
- **박싱**: `notNull`처럼 값을 `T?`로 드는 위임은 원시 타입을 박싱한다(§6.1). `Int` 프로퍼티 하나가 위임 안에서 `Integer`가 된다.
- **`KProperty` 메타데이터**: §3.2의 정적 배열. 프로퍼티당 한 번이라 대개 무시할 수준이나, 존재하긴 한다.

핵심은 **`lazy`처럼 이득이 비용을 압도하는 경우**(무거운 계산을 정말로 미룸)와, **단순 프로퍼티에 위임을 남용하는 경우**(간단한 저장에 위임 객체·간접호출을 얹음)를 구분하는 것이다. 값이 그냥 필드면 그냥 `var`/`val`을 쓰는 게 항상 더 빠르다. 위임은 "재사용할 만한 접근자 로직"이 있을 때 값을 한다.

> **성능 주의**: `by lazy(LazyThreadSafetyMode.SYNCHRONIZED)`(기본)는 초기화 시 락을 잡는다. **초기화 이후** 읽기는 락 없이 빠르지만, 초기화가 잦은 짧은 수명 객체를 대량으로 만든다면 이 락 비용이 누적된다. 단일 스레드가 확실하면 `NONE`이, 순수 계산이면 `PUBLICATION`이 더 가볍다. 다만 항상 측정으로 확인할 것 — 대개 `lazy`의 락은 병목이 아니다.

### 9.2 `by 표현식`은 딱 한 번 평가된다 — 그러나 위임 객체는 인스턴스마다

흔한 혼동: "위임 객체가 여러 프로퍼티에 공유되는가, 아니면 인스턴스마다 새로 생기는가?"

`by 표현식`은 **각 프로퍼티의 초기화 지점에서** 평가된다. 멤버 프로퍼티면 소유 객체가 생성될 때마다다. 그래서 아래는 위험하다.

```kotlin
// 안티패턴: 모든 인스턴스가 같은 위임 객체를 공유하려는 의도라면 이건 틀렸다
class Node {
    var state: Int by Delegates.observable(0) { _, o, n -> log(o, n) }
}
// Node를 100개 만들면 observable 위임 객체도 100개 (각자 자기 state 저장)
```

각 `Node`가 자기 `observable` 위임을 갖는다 — 이게 대개 **원하는** 동작이다(각 노드가 독립적인 상태를 가져야 하니까). 하지만 만약 위임 객체를 여러 인스턴스가 공유하길 원했다면(예: 전역 카운터), `by` 표현식이 인스턴스마다 새 객체를 만드므로 의도와 어긋난다. 공유하려면 위임 객체를 클래스 밖(top-level/companion)에 만들어 두고 `by` 뒤에서 그 참조를 써야 한다 — 그러나 그러면 위임의 `thisRef`가 인스턴스마다 다르게 들어오므로, 위임이 상태를 어떻게 관리하는지 신중히 설계해야 한다.

### 9.3 오개념 정리

이 장이 건드리는 오개념들을 정면으로 정리한다.

**"`by`는 하나의 기능이다"** — 아니다. 프로퍼티 위임(`val x by ...`)과 클래스 위임(`class C : I by ...`, [[32 - 클래스 위임]])은 다른 기능이다. §1.1.

**"위임 프로퍼티는 백킹 필드를 갖는다"** — 아니다(M35 관련). 위임 프로퍼티는 백킹 **필드**(`field`)가 없다. 대신 위임 **객체**를 담는 `$delegate` 필드를 갖는다. 값의 저장은 위임 객체 내부의 책임이지 프로퍼티의 백킹 필드가 아니다. [[22 - 프로퍼티와 백킹 필드]]의 `field`는 위임 프로퍼티에서 접근할 수 없다(존재하지 않으므로).

**"`getValue`/`setValue`는 특별한 언어 기능이다"** — 아니다(M40 관련). 이들은 [[19 - 연산자 오버로딩과 관례]]의 관례 함수 가문의 일원일 뿐이다. `operator` 키워드 + 정해진 이름/시그니처면 누구나 위임을 만든다. 표준 위임(`lazy` 등)도 그렇게 만들어진 평범한 라이브러리 코드다.

**"`by lazy`는 항상 스레드 안전하다"** — 기본(`SYNCHRONIZED`)은 그렇지만, `NONE` 모드는 단일 스레드 전용이다(§4.2). 모드를 명시적으로 바꿨다면 안전성도 바뀐다.

**"`by lazy`는 `var`에도 쓸 수 있다"** — 아니다. `Lazy`에는 `setValue`가 없어 `val` 전용이다(§4.1).

**"맵 위임은 안전하다"** — 정적 타입 검사를 우회한다(§6.2). 키 부재·타입 불일치는 런타임에야 터진다.

**"위임은 성능 최적화다"** — `lazy`는 계산을 미뤄 이득을 줄 수 있지만, 위임 자체는 간접호출·객체 할당·(경우에 따라) 박싱이라는 **비용**을 얹는다(§9.1). 최적화가 아니라 **추상화·재사용** 도구로 이해해야 정확하다.

### 9.4 언제 위임을 쓰는가 — 판단 기준

정리하면, 위임 프로퍼티는 다음 신호가 있을 때 값을 한다.

- **접근자 로직이 반복된다**: "지연 초기화", "변경 감지", "외부 소스 조회" 같은 패턴이 여러 프로퍼티에 걸쳐 나타난다 → 위임으로 한 번 만들어 재사용.
- **계산이 비싸고 조건부다**: 값이 항상 필요하진 않고, 필요할 때만 계산하고 싶다 → `by lazy`.
- **프레임워크가 프로퍼티 이름을 활용한다**: 맵·설정·환경 변수처럼 프로퍼티 이름을 키로 쓰는 매핑 → 맵 위임 또는 커스텀 위임의 `property.name`.

반대로, 단순히 값을 담기만 하는 프로퍼티, 성능이 극도로 중요한 핫 패스의 프로퍼티, 로직이 그 프로퍼티에만 고유해 재사용 여지가 없는 경우에는 위임의 간접비가 이득 없이 얹힌다. 그럴 땐 평범한 프로퍼티나 커스텀 접근자([[22 - 프로퍼티와 백킹 필드]])가 낫다.

---

이 장의 질문들로 돌아가자. `by`는 프로퍼티의 게터/세터를 위임 객체의 `getValue`/`setValue` 호출로 바꾸는, 클래스 위임과는 다른 기능이었다(§1). 그 두 함수는 특별한 언어 기능이 아니라 `operator`가 붙은 관례 함수이고, `thisRef`(소유자)와 `property`(자기 메타데이터)를 받는다(§2). 컴파일하면 위임 객체는 인스턴스마다 `$delegate` 필드에, 프로퍼티 메타데이터는 클래스당 하나의 재사용되는 `KProperty` 객체로 저장된다(§3). `by lazy`는 첫 접근 시 딱 한 번 계산하되, `SYNCHRONIZED`(기본)면 락으로 정확히 1회를, `PUBLICATION`이면 CAS로 완성값 하나만을, `NONE`이면 아무 보장 없이 단일 스레드 전용으로 이를 처리했다(§4). `observable`은 변경 후 통지, `vetoable`은 변경 전 거부권이며(§5), `notNull`은 원시 타입에 `lateinit`이 닿지 못하는 틈을, 맵 위임은 동적 데이터와 정적 프로퍼티 사이의 다리를 놓았다(§6). `provideDelegate`는 위임을 만드는 그 순간에 프로퍼티 메타데이터로 검증·등록을 하게 해 오류를 이른 시점으로 당겼다(§7). 그리고 위임은 결코 공짜가 아니라 간접호출·할당·박싱을 얹는 추상화이므로, "무엇을 재사용하려는가"가 분명할 때만 값을 한다(§9). 프로퍼티가 접근자의 추상이라는 [[22 - 프로퍼티와 백킹 필드]]의 통찰은 여기서 한 걸음 더 나아가, 그 접근자마저 다른 객체에게 넘길 수 있는 데까지 이르렀다.

## 핵심 요약

- **위임 프로퍼티의 `by`는 클래스 위임의 `by`와 이름만 같은 다른 기능이다.** 프로퍼티 위임은 프로퍼티 하나의 접근자를 위임 객체에 넘기고, 클래스 위임([[32 - 클래스 위임]])은 인터페이스 전체를 다른 객체에 넘긴다.
- **`by 표현식`은 프로퍼티의 get/set을 위임 객체의 `getValue`/`setValue` 관례 호출로 번역한다.** `val`은 `getValue`만, `var`는 둘 다 요구한다. 이들은 [[19 - 연산자 오버로딩과 관례]]의 관례 함수이며 `operator` 키워드가 필수다(M40 관련).
- **위임 프로퍼티는 백킹 필드(`field`)를 갖지 않는다.** 대신 위임 객체를 담는 숨은 `$delegate` 필드를 갖고, 값의 저장은 위임 객체 내부의 책임이다. [[22 - 프로퍼티와 백킹 필드]]의 `field`는 위임 프로퍼티에 존재하지 않는다(M35 관련).
- **`getValue`/`setValue`의 시그니처는 `(thisRef, property, [value])`이다.** `thisRef`는 소유 객체(최상위·로컬은 `null`)이고 그 타입이 위임의 부착 위치를 제약하며, `property: KProperty<*>`는 프로퍼티 자신의 메타데이터로 이름 기반 위임(맵·환경변수)을 가능케 한다.
- **`KProperty` 객체는 매 접근마다 할당되지 않는다.** JVM 백엔드에서 컴파일러가 클래스당 정적 배열에 프로퍼티당 하나씩 미리 만들어 재사용하며, 위임이 메타데이터를 안 쓰면 생성을 생략하기도 한다(구현·버전에 따라).
- **`by lazy`는 첫 읽기에 딱 한 번 계산하는 `val` 전용 위임이고, 세 가지 스레드 모드를 갖는다.** 기본 `SYNCHRONIZED`는 락으로 정확히 1회, `PUBLICATION`은 CAS로 완성값 하나만, `NONE`은 무보장·단일 스레드 전용이다. 스레드 안전은 [[43 - 동시성과 메모리 모델]]의 happens-before 위에 선다.
- **`lazy`와 `lateinit`은 관할이 다르다.** `lazy`는 스스로 계산하는 불변 `val`, `lateinit`은 외부가 주입하는 가변 `var`이며 원시 타입(JVM)에는 `lateinit`을 못 쓰지만 `by Delegates.notNull()`은 된다(박싱 대가).
- **`observable`은 변경 후 통지, `vetoable`은 변경 전 거부권이다.** 둘 다 `ObservableProperty`의 `afterChange`/`beforeChange` 훅에서 갈라진 형제이며, 마법이 아니라 관례를 구현한 평범한 클래스다.
- **맵 위임(`by map`)은 프로퍼티 이름을 키로 맵을 조회한다.** 동적 데이터와 정적 프로퍼티를 잇는 편의지만, 키 부재·타입 불일치는 컴파일이 아니라 런타임에 예외로 터지는 안전망 밖의 다리다.
- **`provideDelegate`는 위임을 만드는 위임이다.** `by 표현식`이 위임을 직접 주는 대신 공장이 되어, 객체 생성 시점에 프로퍼티 메타데이터로 검증·등록을 수행해 오류를 첫 접근보다 이른 시점으로 당긴다.
- **위임은 공짜가 아니다.** 읽기당 간접 함수 호출, 인스턴스마다 위임 객체 할당, 경우에 따라 박싱(`notNull`)과 정적 메타데이터를 얹는다. 성능 최적화가 아니라 접근자 로직의 **재사용·추상화** 도구로 이해할 때 정확하다.

## 연결 노트

- [[22 - 프로퍼티와 백킹 필드]] — 프로퍼티가 접근자의 추상이며 `field`가 언제 생기는지. 이 장은 그 접근자마저 다른 객체에 넘기는 확장이다.
- [[19 - 연산자 오버로딩과 관례]] — `getValue`/`setValue`/`provideDelegate`가 속한 관례 함수 가문의 정본. `operator` 키워드와 이름 기반 번역의 원리.
- [[11 - 변수와 초기화 - val과 const와 lateinit]] — `by lazy`가 예고된 곳. `lateinit`과 `notNull`의 대조, `const`/`lazy`의 위상.
- [[32 - 클래스 위임]] — 이름은 같은 `by`지만 인터페이스 전체를 위임하는 다른 기능. §1.1에서 명확히 구분한다.
- [[43 - 동시성과 메모리 모델]] — `by lazy`의 `SYNCHRONIZED`/`PUBLICATION`이 기대는 happens-before와 이중 검사 락의 정본.
- [[44 - 애노테이션과 리플렉션]] — `getValue`가 받는 `KProperty<*>`, 프로퍼티 참조 `::prop`의 리플렉션 정체와 비용.
- [[15 - 인라인 함수와 reified]] — `Lazy.getValue` 같은 `inline` 관례가 위임 호출을 어떻게 지워 비용을 없애는지.
- [[35 - 확장 함수와 프로퍼티]] — 표준 위임이 `getValue`를 확장 함수로 제공하는 메커니즘. 확장 프로퍼티에는 백킹 필드가 없다는 연결.
- [[14 - 클로저와 캡처]] — 로컬 위임 변수가 클로저에 캡처되는 방식, `by lazy` 람다가 캡처하는 것.
- [[24 - 상속과 오버라이딩과 초기화 순서]] — 위임 프로퍼티가 상속 계층에서 초기화되는 순서, `open` 프로퍼티 위임의 함정.
