이 장은 [[22 - 프로퍼티와 백킹 필드]]에서 다룬 내용 위에 한 단계를 더 쌓는다. 22장에서는 Kotlin의 프로퍼티가 필드가 아니라 **접근자(get/set)를 추상화한 것**이고, 백킹 필드 `field`는 접근자가 필요로 할 때만 컴파일러가 만들어 주는 저장소라는 점을 확인했다. 커스텀 게터와 세터를 작성하면 "값을 어떻게 읽고 쓸지"를 프로퍼티마다 직접 구현할 수 있었다.

그런데 그런 로직, 예컨대 "처음 읽을 때 계산해서 캐시한다", "값이 바뀔 때마다 로그를 남긴다", "맵에서 이름으로 값을 찾아 온다" 같은 로직은 프로퍼티마다 거의 똑같이 반복된다. 위임 프로퍼티(delegated property)는 이렇게 **반복되는 접근자 로직을 하나의 객체로 분리해 재사용**할 수 있게 하는 기능이다.

22장과 달라지는 점은 다음과 같다. 22장에서는 프로퍼티가 자신의 백킹 필드를 직접 읽고 썼다. 이 장에서 다루는 프로퍼티는 백킹 필드를 갖지 않는다. 대신 **위임 객체(delegate)** 하나를 참조하고, 프로퍼티를 읽으면 `delegate.getValue(...)`를, 프로퍼티에 쓰면 `delegate.setValue(...)`를 호출한다. 프로퍼티는 껍데기만 남고, 실제 저장과 로직은 위임 객체가 맡는다.

이 연결은 `by` 키워드로 선언한다. 그리고 `getValue`/`setValue`는 [[19 - 연산자 오버로딩과 관례]]에서 소개한 **관례(convention) 함수**의 하나이다. 정해진 이름과 시그니처를 가진 함수를 `operator`로 정의하면, 언어가 특정 문법(`by`)을 만났을 때 그 함수를 호출해 준다.

이 장에서는 `by`가 접근자를 위임 호출로 바꾸는 방식과 관례 시그니처, 컴파일된 형태(숨은 `$delegate` 필드와 `KProperty` 객체), 표준 위임(`lazy`, `observable`, `vetoable`, `notNull`, 맵), `provideDelegate`, 로컬 변수 위임, 그리고 성능과 함정을 차례로 다룬다.

이름은 같지만 인터페이스 전체를 다른 객체에 넘기는 **클래스 위임**(`class C(b: Base) : Base by b`)은 [[32 - 클래스 위임]]에서 다루며, 두 `by`의 차이는 1절에서 짚는다.

## 1. `by`가 하는 일: 접근자를 객체에 넘긴다

### 1.1 키워드 하나, 두 가지 `by`

Kotlin에서 `by` 키워드는 문법적으로 **두 위치**에 나온다. 두 경우는 이름만 같을 뿐 하는 일이 다르다.

```kotlin
// (1) 클래스 위임 — 32장의 주제. 인터페이스 "전체"를 다른 객체에 넘긴다.
interface Printer { fun print(): String }
class LoudPrinter(private val p: Printer) : Printer by p   // Printer의 모든 멤버를 p에 전달

// (2) 프로퍼티 위임 — 이 장의 주제. 프로퍼티 "하나"의 접근을 위임 객체에 넘긴다.
val greeting: String by lazy { "hello" }                   // greeting의 get을 lazy에 넘김
```

(1)은 `LoudPrinter`가 `Printer`를 상속하면서, `Printer`가 요구하는 메서드의 구현을 모두 `p` 객체에 맡기는 것이다. 클래스 수준의 컴포지션이며 32장(클래스 위임)에서 자세히 다룬다. (2)는 `greeting`이라는 프로퍼티 하나가 자신의 값을 어떻게 돌려줄지를 `lazy { ... }`가 만든 객체에 맡기는 것이다. 두 경우는 범위가 전혀 다르다. 하나는 타입의 인터페이스 계약 전체이고, 다른 하나는 프로퍼티 접근자 한 쌍이다.

이 장에서는 (2)만 다룬다. 둘을 구분하는 방법은 간단하다. `by` 앞에 **프로퍼티 선언**(`val`/`var`)이 오면 프로퍼티 위임이고, `by` 앞에 **슈퍼타입 이름**이 오면 클래스 위임이다.

### 1.2 위임의 직관: "이 프로퍼티를 어떻게 읽고 쓸지는 위임 객체가 정한다"

일반 프로퍼티는 자신의 값을 스스로 관리한다. 22장에서 본 커스텀 게터/세터를 쓰면 로직을 넣을 수 있지만, 그 로직은 해당 프로퍼티에 **고정**된다. 같은 로직을 다른 프로퍼티에서도 쓰려면 코드를 복사해야 한다.

```kotlin
// 22장 방식: "처음 읽을 때 계산하고 캐시" 로직이 프로퍼티에 박혀 있다
class Circle(val radius: Double) {
    private var _area: Double? = null
    val area: Double
        get() {
            if (_area == null) _area = Math.PI * radius * radius
            return _area!!
        }
}
```

이 "지연 캐시" 패턴을 원의 넓이뿐 아니라 둘레에도, 다른 클래스의 다른 프로퍼티에도 쓰고 싶다면 어떻게 해야 할까? 매번 `_x: T? = null`과 `if (null) 계산` 같은 보일러플레이트를 반복해야 한다. 위임 프로퍼티를 쓰면 이 패턴을 **객체 하나로 캡슐화**해 재사용할 수 있다.

```kotlin
// 위임 방식: "지연 캐시" 로직은 lazy 객체 안에 있고, 프로퍼티는 그것을 붙들 뿐
class Circle(val radius: Double) {
    val area: Double by lazy { Math.PI * radius * radius }
}
```

이제 `area`에는 백킹 필드가 없다. `area`를 읽으면 컴파일러는 이를 "`area`가 참조하는 `lazy` 객체에 값을 요청하는 호출"로 번역한다. 로직은 `lazy`가 가지고 있고, 프로퍼티는 창구 역할만 한다.

### 1.3 `by`의 탈설탕(desugaring): 개념적 번역

먼저 `by` 선언이 무엇으로 번역되는지 개념적으로 정리해 보자. 다음과 같은 선언이 있다고 하자.

```kotlin
class Owner {
    var prop: String by Delegate()
}
```

컴파일러는 이 선언을 대략 다음과 **동등한** 형태로 바꾼다(정확한 컴파일 형태는 3절에서 설명한다).

```kotlin
class Owner {
    private val prop$delegate = Delegate()          // 위임 객체를 담는 숨은 필드
    var prop: String
        get() = prop$delegate.getValue(this, ::prop)          // 읽기 → getValue
        set(value) { prop$delegate.setValue(this, ::prop, value) }  // 쓰기 → setValue
}
```

핵심은 세 가지이다.

- `by 표현식`(`Delegate()`)은 **딱 한 번** 평가되어 숨은 필드 `prop$delegate`에 저장된다. 접근할 때마다 새로 만들어지지 않는다.
- `val`이면 게터만, `var`이면 게터와 세터가 함께 만들어진다. 그래서 `var` 위임에는 `getValue`뿐 아니라 `setValue`도 필요하다.
- 두 접근자는 각각 위임 객체의 `getValue`/`setValue` **관례 함수**를 호출하고, 이때 `this`(소유 객체)와 `::prop`(프로퍼티 자신의 메타데이터)을 인자로 넘긴다.

> [!note] 명세 기준
> `prop$delegate` 필드와 `getValue`, `setValue` 호출은 컴파일러가 생성하는 **합성(synthetic)** 코드이다. 소스에는 `by Delegate()` 한 줄만 있지만, 컴파일러 프론트엔드가 이를 접근자 본문으로 확장한다. 위의 "동등한 형태"는 소스 언어로 표현한 근사치이고, 실제 바이트코드는 `::prop`을 매번 만들지 않는 등 더 최적화되어 있다(3절).

## 2. `getValue`/`setValue` 관례: 시그니처 살펴보기

### 2.1 정확한 시그니처

위임 객체가 되려면 두 관례 함수를 필요한 만큼 제공해야 한다. `val` 프로퍼티에는 `getValue`만 있으면 되고, `var` 프로퍼티에는 둘 다 필요하다.

```kotlin
import kotlin.reflect.KProperty

class Delegate {
    operator fun getValue(thisRef: Any?, property: KProperty<*>): String {
        return "$thisRef 의 '${property.name}' 을 읽음"
    }
    operator fun setValue(thisRef: Any?, property: KProperty<*>, value: String) {
        println("$thisRef 의 '${property.name}' 에 '$value' 를 씀")
    }
}

class Owner(val label: String) {
    var prop: String by Delegate()
    override fun toString() = "Owner($label)"
}

fun main() {
    val o = Owner("a")
    println(o.prop)        // => Owner(a) 의 'prop' 을 읽음
    o.prop = "새값"        // => Owner(a) 의 'prop' 에 '새값' 를 씀
}
```

시그니처를 구성 요소별로 살펴보자.

- **`operator`**: 반드시 붙여야 한다. 이 수식어가 없으면 `getValue`는 이름만 같은 일반 메서드일 뿐이고, `by`가 이를 관례로 인식하지 못한다. 19장(연산자 오버로딩과 관례)에서 본 원칙과 같다.
- **`thisRef: Any?`**: 프로퍼티가 속한 객체, 즉 **소유 객체**이다. 위 예에서는 `Owner` 인스턴스이다. 이 파라미터의 타입은 위임을 어디에 붙일 수 있는지를 제한한다(2.2절). 최상위 프로퍼티나 로컬 프로퍼티에는 소유 객체가 없으므로 `null`이 전달된다.
- **`property: KProperty<*>`**: 위임된 **프로퍼티 자신의 메타데이터**이다. `property.name`으로 이름을, `property.returnType` 등으로 타입 정보를 얻을 수 있다. 이 객체가 어디서 오는지는 3.2절에서 설명한다.
- **반환 타입과 `value` 타입**: 프로퍼티의 타입과 호환되어야 한다. `getValue`의 반환 타입은 프로퍼티 타입의 하위 타입이면 되고, `setValue`의 `value` 타입은 프로퍼티 타입의 상위 타입이면 된다(위치에 따른 변성).

### 2.2 `thisRef`의 타입이 위임을 붙일 위치를 제한한다

`thisRef` 파라미터의 타입은 형식적인 요소가 아니다. **이 위임을 어떤 클래스나 객체의 프로퍼티에 붙일 수 있는지**를 컴파일 타임에 강제한다.

```kotlin
class Animal(val name: String)

class NameEcho {
    // thisRef를 Animal로 못 박음 → Animal의 프로퍼티에만 붙을 수 있다
    operator fun getValue(thisRef: Animal, property: KProperty<*>): String =
        thisRef.name
}

class Dog {
    val echoed: String by NameEcho()   // 컴파일 에러: thisRef가 Dog인데 getValue는 Animal을 기대
}
```

`Dog`의 프로퍼티에 `NameEcho`를 붙이면, 컴파일러가 만든 게터는 `nameEcho.getValue(this /*Dog*/, ::echoed)`를 호출하려 한다. 그런데 `getValue`는 `Animal`을 받으므로 `Dog`를 넘길 수 없고, 결국 컴파일 에러가 난다. `thisRef: Any?`로 선언하면 어떤 소유 객체든 받을 수 있으므로 어디에나 붙일 수 있다. 반대로 `thisRef: Animal`처럼 좁히면 그 타입 계층에만 붙는 특화된 위임이 된다.

이 방법을 쓰면 위임을 **문맥에 맞게 안전하게** 제한할 수 있다. 예를 들어 "이 위임은 특정 인터페이스를 구현한 소유 객체에만 붙일 수 있다"는 조건을 타입으로 강제할 수 있다.

### 2.3 확장 함수로 제공되는 관례: 표준 위임이 동작하는 방식

`getValue`/`setValue`는 **멤버 함수가 아니어도 된다**. 확장 함수로 정의해도 관례로 인정된다([[35 - 확장 함수와 프로퍼티]]). 표준 라이브러리의 위임은 바로 이 점을 활용한다. `lazy { ... }`가 반환하는 `Lazy<T>`에는 `getValue` 멤버가 없다. 대신 표준 라이브러리가 확장 함수를 제공한다.

```kotlin
// kotlin.Lazy에 대한 stdlib의 확장 (개념)
public inline operator fun <T> Lazy<T>.getValue(thisRef: Any?, property: KProperty<*>): T = value
```

따라서 `val x by lazy { ... }`를 컴파일하면 게터는 `lazyInstance.getValue(this, ::x)`를 호출하고, 이 확장 함수가 `Lazy.value`를 돌려준다. `Lazy` 인터페이스 자체는 위임에 대해 알지 못하며, 위임 관례는 바깥에서 확장 함수로 덧붙여진 것이다.

이 방식 덕분에 이미 있는 타입도 위임 객체로 쓸 수 있다. 예를 들어 `Map`은 위임을 염두에 두고 설계된 타입이 아니지만, stdlib가 `Map`에 대한 `getValue` 확장을 제공하므로 맵을 위임으로 쓸 수 있다(6.2절).

### 2.4 표준 인터페이스: `ReadOnlyProperty`와 `ReadWriteProperty`

위임을 직접 만들 때 관례 시그니처를 외울 필요는 없다. 표준 라이브러리가 두 인터페이스를 제공하기 때문이다.

```kotlin
public fun interface ReadOnlyProperty<in T, out V> {
    operator fun getValue(thisRef: T, property: KProperty<*>): V
}

public interface ReadWriteProperty<in T, V> : ReadOnlyProperty<T, V> {
    override operator fun getValue(thisRef: T, property: KProperty<*>): V
    operator fun setValue(thisRef: T, property: KProperty<*>, value: V)
}
```

이 인터페이스를 구현하면 시그니처가 자동으로 맞춰진다. 타입 파라미터 `T`(소유 객체 타입)와 `V`(값 타입)에 붙은 변성 표기(`in T`, `out V`)는 2.1절과 2.2절에서 본 값 변성 규칙과 부착 위치 규칙을 타입으로 표현한 것이다.

```kotlin
import kotlin.properties.ReadWriteProperty
import kotlin.reflect.KProperty

// 값을 쓸 때마다 최댓값으로만 갱신되는(단조 증가) 위임
class HighWaterMark(private var current: Int) : ReadWriteProperty<Any?, Int> {
    override fun getValue(thisRef: Any?, property: KProperty<*>): Int = current
    override fun setValue(thisRef: Any?, property: KProperty<*>, value: Int) {
        if (value > current) current = value    // 더 큰 값만 반영
    }
}

class Gauge {
    var peak: Int by HighWaterMark(0)
}

fun main() {
    val g = Gauge()
    g.peak = 5;  println(g.peak)   // => 5
    g.peak = 3;  println(g.peak)   // => 5  (3은 5보다 작아 무시됨)
    g.peak = 9;  println(g.peak)   // => 9
}
```

`ReadOnlyProperty`가 `fun interface`(SAM)라는 점도 유용하다. 람다 하나만으로 읽기 전용 위임을 만들 수 있기 때문이다.

```kotlin
import kotlin.properties.ReadOnlyProperty

val random: Int by ReadOnlyProperty { _, _ -> (0..100).random() }
// random을 읽을 때마다 새 난수. 백킹 필드 없음.
```

## 3. 컴파일된 형태: 숨은 필드와 재사용되는 KProperty

### 3.1 `$delegate` 필드

1.3절에서 개념적으로 살펴보았듯이, 위임 프로퍼티마다 위임 객체를 담는 숨은 인스턴스 필드가 하나씩 생긴다. JVM 백엔드에서 이 필드의 이름은 관례적으로 `프로퍼티이름$delegate`이고, `private final`로 선언된다. 생성자(또는 초기화 지점)에서 `by 표현식`을 평가해 이 필드에 대입한다.

```text
// JVM 백엔드에서 class Owner { var prop: String by Delegate() } 가 만드는 것 (개념)
class Owner {
    private final Delegate prop$delegate;      // 위임 객체 저장

    Owner() {
        this.prop$delegate = new Delegate();   // by 표현식은 여기서 딱 한 번 평가
    }

    public String getProp() {
        return prop$delegate.getValue(this, <KProperty for prop>);
    }
    public void setProp(String value) {
        prop$delegate.setValue(this, <KProperty for prop>, value);
    }
}
```

이 코드에서 두 가지를 알 수 있다. 첫째, **위임 객체는 프로퍼티마다 하나씩** 존재하고 소유 인스턴스 안에 저장된다. 소유 객체를 100개 만들면 위임 객체도 100개 만들어진다(소유 인스턴스마다 자신의 위임 객체를 가진다).

둘째, **`by 표현식`을 평가하는 시점**은 그 필드가 초기화되는 시점이다. 멤버 프로퍼티라면 소유 객체를 생성할 때이고, 로컬 변수라면 선언에 도달했을 때이다. `by lazy { 무거운계산() }`이라고 써도 `lazy(...)` **함수 호출 자체**는 객체를 생성할 때 일어난다. 이때는 `Lazy` 래퍼만 만들 뿐이고, 안의 람다는 아직 실행되지 않는다.

### 3.2 재사용되는 `KProperty`: `$$delegatedProperties` 배열

`getValue(this, ::prop)`의 `::prop`은 프로퍼티 참조, 즉 `KProperty` 객체이다([[44 - 애노테이션과 리플렉션]]). 단순하게 생각하면 접근할 때마다 이 참조 객체를 새로 할당해야 할 것 같다. 하지만 그러면 한 번 읽을 때마다 객체 하나가 쓰레기로 쌓이므로, 컴파일러는 이런 방식을 쓰지 않는다.

JVM 백엔드에서 컴파일러는 클래스마다 **위임된 프로퍼티들의 `KProperty` 메타데이터를 담는 정적 배열**을 하나 생성한다. 이 배열은 관례적으로 `$$delegatedProperties`라고 부른다. 각 위임 프로퍼티의 접근자는 이 배열의 고정된 인덱스에서 미리 만들어 둔 `KProperty` 객체를 꺼내 쓴다.

```text
// 개념적 형태 (JVM 백엔드)
class Owner {
    static final KProperty[] $$delegatedProperties = {
        // prop에 대한 KPropertyImpl, 클래스 로드 시 한 번 생성
        Reflection.mutableProperty1(new MutablePropertyReference1Impl(Owner.class, "prop", "getProp()...")),
    };
    public String getProp() {
        return prop$delegate.getValue(this, $$delegatedProperties[0]);   // 재사용
    }
}
```

즉 `KProperty` 객체는 **프로퍼티당 하나**만 만들어지고, 클래스가 살아 있는 동안 계속 공유된다. 접근할 때마다 새로 할당하지 않으므로 GC 부담이 없다.

> [!caution] 성능 주의
> 위임을 쓰면 이 `KProperty` 메타데이터 때문에 클래스 로드 비용과 정적 메모리가 아주 조금 더 든다. 대부분은 무시할 만한 수준이지만, 위임 프로퍼티가 수천 개인 코드를 생성한다면 메타데이터도 그만큼 쌓인다.
>
> 또한 최근 Kotlin 버전들은 위임이 `property` 파라미터를 **실제로 쓰지 않을 때** 이 메타데이터 생성을 생략하는 최적화를 도입해 왔다(구현과 버전에 따라 다르다). 따라서 "위임 프로퍼티는 항상 `KProperty` 객체를 만든다"는 설명은 최신 컴파일러에서는 정확하지 않을 수 있다. 위임이 프로퍼티 메타데이터를 참조하는지에 따라 달라진다.

### 3.3 `getValue`가 `property`를 받는 이유: 자신이 처리하는 프로퍼티를 아는 위임

`property: KProperty<*>` 파라미터는 위임 객체에 "지금 어느 프로퍼티를 대신 처리하고 있는지"를 알려 준다. 이 정보 덕분에 위임은 **문맥을 인지(context-aware)** 할 수 있다. 위임 구현 하나를 여러 프로퍼티에 붙이고, 프로퍼티 이름에 따라 다르게 동작하게 만들 수 있다.

대표적인 예가 맵 위임(6.2절)이다. 맵 위임의 `getValue`는 `property.name`을 키로 사용해 맵을 조회한다. 이름을 모르면 위임은 어떤 키를 조회해야 할지 알 수 없다.

```kotlin
import kotlin.reflect.KProperty

// property.name을 키로 삼아 환경 변수를 읽는 위임 (일반 도메인 예)
class EnvVar {
    operator fun getValue(thisRef: Any?, property: KProperty<*>): String? =
        System.getenv(property.name)
}

object Config {
    val PATH: String? by EnvVar()      // property.name == "PATH" 로 조회
    val HOME: String? by EnvVar()      // property.name == "HOME" 으로 조회
}
// 같은 EnvVar 구현이 프로퍼티 이름에 따라 다른 변수를 읽는다
```

### 3.4 일반 프로퍼티와 위임 프로퍼티의 바이트코드 비교

두 프로퍼티를 컴파일한 결과를 나란히 놓고 보면, 위임의 간접 비용이 어디서 생기는지 알 수 있다. 아래는 JVM 백엔드 기준의 개념적 형태이다.

```text
// (A) 평범한 프로퍼티: class Owner { var plain: String = "x" }
class Owner {
    private String plain = "x";               // 진짜 백킹 필드
    public String getPlain() { return plain; }             // 필드 로드 한 번
    public void setPlain(String v) { plain = v; }          // 필드 저장 한 번
}

// (B) 위임 프로퍼티: class Owner { var deleg: String by Delegate() }
class Owner {
    static final KProperty[] $$delegatedProperties = { /* deleg 메타데이터 */ };
    private final Delegate deleg$delegate = new Delegate();      // 위임 객체
    public String getDeleg() {
        return deleg$delegate.getValue(this, $$delegatedProperties[0]);  // 호출 한 번 + 메타 로드
    }
    public void setDeleg(String v) {
        deleg$delegate.setValue(this, $$delegatedProperties[0], v);      // 호출 한 번 + 메타 로드
    }
}
```

(A)의 게터는 필드 하나를 읽어 돌려준다. JIT가 인라인하면 사실상 필드에 바로 접근하는 것과 같다. (B)의 게터는 `deleg$delegate` 필드를 로드하고, 메타데이터 배열에서 `KProperty`를 꺼낸 뒤, `getValue`를 **가상 호출**한다. 이 가상 호출이 위임의 근본적인 비용이다(9.1절).

단, `getValue`가 `inline`이면([[15 - 인라인 함수와 reified]]) 컴파일러가 그 본문을 게터 안에 펼쳐 넣어 호출을 없앨 수 있다. `Lazy.getValue`가 `inline`인 이유도 여기에 있다. 따라서 "위임에는 항상 호출 오버헤드가 있다"는 설명은 정확하지 않다. **인라인할 수 있는 위임은 호출 오버헤드가 사라진다.**

```java
// Java 관점에서 위임 프로퍼티를 부르는 코드 (상호운용, 45장)
Owner o = new Owner();
String s = o.getDeleg();     // Kotlin의 by는 Java에는 그냥 getter로 보인다
```

Java에서 보면 위임 프로퍼티는 `getDeleg()`/`setDeleg()` 메서드 한 쌍일 뿐이다. `by`나 `KProperty`, 위임 객체는 Java 소스에 드러나지 않는다. 모두 Kotlin 컴파일러가 게터와 세터 본문 안에 감춘 구현 세부 사항이다.

## 4. `lazy`: 지연 초기화와 세 가지 스레드 모드

표준 라이브러리에서 가장 널리 쓰이는 위임은 `lazy`이다. `lazy`는 "값이 처음 필요할 때 한 번만 계산하고, 이후에는 캐시한 값을 돌려준다"는 지연 초기화(lazy initialization)를 캡슐화한다. [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 잠깐 언급한 `by lazy`를 이 절에서 자세히 다룬다.

### 4.1 기본 동작과 `Lazy<T>` 인터페이스

```kotlin
class Report {
    val summary: String by lazy {
        println("...무거운 계산 수행...")
        "요약 결과"
    }
}

fun main() {
    val r = Report()
    println("리포트 생성됨 (아직 summary 계산 안 함)")
    println(r.summary)    // => ...무거운 계산 수행... \n 요약 결과   (여기서 처음 계산)
    println(r.summary)    // => 요약 결과   (캐시, 람다 재실행 없음)
}
// 출력:
// 리포트 생성됨 (아직 summary 계산 안 함)
// ...무거운 계산 수행...
// 요약 결과
// 요약 결과
```

`lazy(initializer)`는 `Lazy<T>` 인터페이스를 구현한 객체를 돌려준다.

```kotlin
public interface Lazy<out T> {
    public val value: T                 // 접근 시 (필요하면) 초기화 후 반환
    public fun isInitialized(): Boolean // 이미 초기화됐는지 (초기화 유발 없이)
}
```

`getValue`는 stdlib 확장 함수(2.3절)가 `value`에 위임한다. `isInitialized()`를 쓰면 "계산이 이미 일어났는지"를 부수 효과 없이 확인할 수 있다.

```kotlin
val lazyVal = lazy { 42 }
println(lazyVal.isInitialized())   // => false
val x: Int by lazyVal
// x를 아직 안 읽었으므로 여전히 미초기화
```

주의할 점이 있다. `by lazy`는 `val`에만 쓸 수 있다. `Lazy<T>`에는 `getValue` 확장만 있고 `setValue`는 없으므로, `var`에 붙이면 컴파일 에러가 난다. 지연 "초기화"는 한 번 정해지면 끝난다는 의미이므로 당연한 제약이다.

### 4.2 세 가지 스레드 안전 모드

`lazy`에서 가장 까다로운 부분은 **여러 스레드가 동시에 처음 접근할 때** 어떤 일이 일어나는가이다. `lazy`는 세 가지 모드로 이 상황을 처리하며, 이 모드는 `LazyThreadSafetyMode` enum으로 지정한다.

| 모드 | 락 사용 | 초기화 람다 실행 횟수(경합 시) | 여러 스레드 안전 | 비용 |
|------|---------|------------------------------|----------------|------|
| `SYNCHRONIZED` (기본) | 예 (이중 검사 락) | 정확히 1회 | 예 | 락 획득 오버헤드 |
| `PUBLICATION` | 아니오 (CAS) | 1회 이상 가능, 첫 성공 값만 채택 | 예 | 람다 중복 실행 가능 |
| `NONE` | 아니오 | 정의되지 않음(경합 시 깨짐) | **아니오** | 가장 빠름 |

```kotlin
// 기본: 인자 없는 lazy(initializer)는 SYNCHRONIZED
val a: Int by lazy { compute() }

// 명시적 모드 지정
val b: Int by lazy(LazyThreadSafetyMode.PUBLICATION) { compute() }
val c: Int by lazy(LazyThreadSafetyMode.NONE) { compute() }
```

각 모드를 차례로 살펴보자.

**`SYNCHRONIZED`(기본)**: 초기화할 때 락(모니터)을 획득해 이중 검사 락(double-checked locking)을 수행한다. 여러 스레드가 동시에 처음 접근해도 **초기화 람다는 정확히 한 번만** 실행된다. 나머지 스레드는 락을 기다렸다가 완성된 값을 받는다. 안전하지만 첫 접근에 동기화 비용이 든다. 초기화한 뒤의 읽기는 락 없이 빠르다. 값이 채워지면 락을 거치는 경로로 들어가지 않기 때문이다.

**`PUBLICATION`**: 락 대신 원자적 compareAndSet을 쓴다. 여러 스레드가 동시에 처음 접근하면 **초기화 람다가 여러 번 실행될 수 있다**. 하지만 그중 **가장 먼저 CAS에 성공한 값 하나만** 저장되고, 모든 스레드가 그 값을 본다. 람다가 부수 효과 없는 순수 함수라서 여러 번 계산해도 문제가 없고, 락 경합을 피하고 싶을 때 쓴다.

**`NONE`**: 동기화를 전혀 하지 않으므로 **단일 스레드에서만** 안전하다. 여러 스레드가 경합하면 초기화가 중복되거나, 심하면 다른 스레드가 완성되지 않았거나 일부만 초기화된 상태를 볼 수 있다(메모리 가시성을 보장하지 않는다). 여러 스레드가 절대 접근하지 않는다고 보장할 수 있을 때만, 비용을 최소로 줄이기 위해 쓴다.

```text
SYNCHRONIZED 초기화 (개념)          PUBLICATION 초기화 (개념)
  스레드1: 락 획득                      스레드1: 람다 실행 → CAS 시도
  스레드2: 락 대기 ────┐                스레드2: 람다 실행 → CAS 시도
  스레드1: 람다 1회 실행 │               (둘 다 실행되지만)
  스레드1: 값 저장, 락 해제              첫 CAS 성공값만 채택 → 나머지 버림
  스레드2: 락 획득 → 값 이미 있음 → 반환   모든 스레드 같은 값 관측
```

> [!info] 역사 메모
> `lazy`의 기본 모드가 `SYNCHRONIZED`라는 점에서 "안전이 기본이고 최적화는 선택"이라는 Kotlin의 보수적인 기본값 철학을 볼 수 있다. 실제로는 많은 지연 프로퍼티가 단일 스레드에서만 쓰이지만, 라이브러리는 사용자가 스레드 안전성을 명시적으로 포기(`NONE`)하기 전까지 안전한 쪽을 기본으로 제공한다. `val`이 기본이고 `var`가 선택인 것, 타입이 기본적으로 non-null이고 `?`를 붙여야 nullable이 되는 것과 같은 방향의 설계이다.

### 4.3 `lazy`의 스레드 안전성을 뒷받침하는 것

`SYNCHRONIZED` 모드의 "정확히 1회"와 `PUBLICATION` 모드의 "완성된 값만 관측"은 저절로 보장되는 것이 아니라 **메모리 모델**의 보장에 기대고 있다. 이중 검사 락이나 원자적 CAS가 올바르게 동작하려면, 한 스레드가 쓴 초기화 결과가 다른 스레드에 **완전히 보여야**(happens-before) 한다.

JVM 백엔드에서는 `volatile` 시맨틱과 모니터 및 원자 연산의 메모리 배리어가 이를 보장한다. 이 기반이 없으면 이중 검사 락은 악명 높은 "부분 초기화된 객체 관측" 버그 때문에 제대로 동작하지 않는다. 이 메커니즘은 [[43 - 동시성과 메모리 모델]]에서 자세히 설명한다.

`NONE`이 위험한 이유도 여기에 있다. `NONE`은 이 메모리 배리어를 생략한다. 그래서 한 스레드가 초기화한 결과가 다른 스레드에 보이지 않을 수 있고, 심지어 필드는 보이지만 그 필드가 가리키는 객체의 내부는 완성되지 않은 상태로 보이는 재배열도 이론적으로 가능하다. "단일 스레드 전용"이라는 조건은 이런 배리어 부재를 상쇄하는 유일한 전제이다.

### 4.4 `lazy`의 내부: 센티넬 값과 이중 검사

`SYNCHRONIZED` 모드의 `lazy`가 내부에서 하는 일을 개념적으로 그려 보면, "첫 접근에 한 번"이 어떻게 구현되는지 알 수 있다. 핵심은 **"아직 초기화되지 않음"을 나타내는 특별한 센티넬(sentinel) 값**과 이중 검사 락이다.

```kotlin
// SynchronizedLazyImpl의 개념적 스케치 (실제 stdlib 구현의 단순화)
private object UNINITIALIZED     // "아직 계산 안 됨"을 뜻하는 유일한 표식

class SynchronizedLazyImpl<T>(initializer: () -> T) : Lazy<T> {
    private var initializer: (() -> T)? = initializer
    @Volatile private var _value: Any? = UNINITIALIZED   // volatile: 스레드 간 가시성
    private val lock = this

    override val value: T
        get() {
            val v1 = _value
            if (v1 !== UNINITIALIZED) {          // 1차 검사 (락 없이, 빠른 경로)
                @Suppress("UNCHECKED_CAST")
                return v1 as T
            }
            return synchronized(lock) {
                val v2 = _value
                if (v2 !== UNINITIALIZED) {      // 2차 검사 (락 안에서)
                    @Suppress("UNCHECKED_CAST")
                    v2 as T
                } else {
                    val computed = initializer!!()   // 딱 한 번 실행
                    _value = computed
                    initializer = null               // 초기화 후 람다 참조 해제 (GC 도움)
                    computed
                }
            }
        }

    override fun isInitialized(): Boolean = _value !== UNINITIALIZED
}
```

중요한 점은 세 가지이다.

- `_value`에 **`@Volatile`** 이 붙어 있어서, 한 스레드가 쓴 값이 다른 스레드에 즉시 보인다(happens-before, 43장 동시성과 메모리 모델). 이 어노테이션이 없으면 이중 검사 락이 깨진다.
- **1차 검사는 락 없이** 수행되므로, 이미 초기화된 값을 읽을 때는 락을 거치지 않는다. 그래서 초기화 이후의 반복 읽기가 빠르다.
- 초기화가 끝나면 **`initializer = null`** 로 람다 참조를 해제한다. 람다가 캡처한 무거운 객체들([[14 - 클로저와 캡처]])은 값을 계산한 뒤에는 더 이상 필요 없으므로, GC가 회수할 수 있게 하려는 것이다.

`NONE` 모드(`UnsafeLazyImpl`)는 이 스케치에서 `@Volatile`과 `synchronized` 블록을 모두 뺀 버전이다. 그래서 빠르지만, 여러 스레드가 경합하면 센티넬 검사 자체가 깨져 초기화가 중복되거나 부분적인 상태가 노출된다.

`PUBLICATION` 모드(`SafePublicationLazyImpl`)는 락 대신 원자적 업데이터를 써서 `_value`를 `UNINITIALIZED`에서 계산한 값으로 **compareAndSet** 한다. 여러 스레드가 동시에 `initializer`를 실행할 수는 있지만, CAS에 처음 성공한 값 하나만 저장되고 나머지는 버려진다.

> [!caution] 성능 주의
> `lazy`의 `@Volatile` 읽기는 JVM에서 매우 저렴하지만 완전히 공짜는 아니다(메모리 배리어가 있다). 아주 자주 실행되는 루프(hot loop)에서 이미 초기화된 `lazy` 프로퍼티를 수백만 번 읽는다면, 값을 지역 변수로 한 번 꺼내 두는 편이 `volatile` 읽기를 반복하는 것보다 빠를 수 있다. 대부분의 코드에서는 의미 없는 차이이므로, 측정하지 않고 미리 최적화하지는 말자.

### 4.5 `lazy`와 `lateinit` 중 무엇을 쓸까

11장(변수와 초기화)에서 본 `lateinit`과 `by lazy`는 둘 다 "나중에 초기화"하는 상황을 다루지만, 성격이 다르다.

| | `by lazy` | `lateinit var` |
|---|-----------|----------------|
| 변경 가능성 | `val` (한 번 계산 후 불변) | `var` (여러 번 대입 가능) |
| 초기화 주체 | 위임이 **스스로**(첫 접근 시 람다) | **외부**가 대입해 줘야 함 |
| 초기화 시점 | 첫 읽기 시 자동 | 임의 시점, 개발자 책임 |
| 미초기화 접근 | 불가능(항상 람다로 초기화됨) | `UninitializedPropertyAccessException` |
| 원시 타입(JVM) | 가능(`Int` 등 OK) | **불가**(`lateinit var n: Int` 컴파일 에러) |
| 스레드 안전 | 모드로 선택 | 없음(그냥 필드) |
| 초기화 여부 확인 | `isInitialized()` | `::prop.isInitialized` |

정리하면 다음과 같다. 값을 **스스로 계산할 수 있고 한 번 정해지면 바뀌지 않는다면** `by lazy`를 쓴다. 값이 **외부(프레임워크, DI, 세터)에서 주입**되고, 주입 전에는 값이 없으며, 나중에 바뀔 수도 있다면 `lateinit var`를 쓴다. 원시 타입을 지연 초기화하고 싶은데 `lateinit`을 쓸 수 없고 "외부 주입"이 필요하다면, `by Delegates.notNull()`(6.1절)이 대안이 된다.

## 5. `observable`과 `vetoable`: 변경을 관측하고 거부하기

`kotlin.properties.Delegates`는 미리 만들어 둔 위임 팩토리 몇 가지를 제공한다. 그중 `observable`과 `vetoable`은 **값이 바뀔 때 콜백**을 호출해 주는 `var` 위임이다.

### 5.1 `observable`: 변경 후 통지

`Delegates.observable(초기값) { property, oldValue, newValue -> ... }`는 프로퍼티에 값을 대입할 때마다, **대입이 끝난 뒤** 콜백을 호출한다.

```kotlin
import kotlin.properties.Delegates

class TemperatureSensor {
    var celsius: Int by Delegates.observable(0) { prop, old, new ->
        println("${prop.name}: $old°C -> $new°C")
    }
}

fun main() {
    val s = TemperatureSensor()
    s.celsius = 20     // => celsius: 0°C -> 20°C
    s.celsius = 25     // => celsius: 20°C -> 25°C
    s.celsius = 25     // => celsius: 25°C -> 25°C  (같은 값이어도 콜백은 불린다)
}
```

콜백은 프로퍼티 메타데이터(`KProperty`), 이전 값, 새 값의 세 인자를 받는다. 콜백은 **값이 이미 저장된 뒤**에 호출되므로 반환값이 없다(`Unit`). 즉 변경을 되돌릴 수 없고 통지만 받는다. 같은 값을 다시 대입해도 콜백이 호출된다는 점에 주의해야 한다(값이 같은지 검사하지 않는다).

### 5.2 `vetoable`: 변경 전 거부권

`Delegates.vetoable(초기값) { property, oldValue, newValue -> Boolean }`은 대입이 **일어나기 전**에 콜백을 호출하고, 콜백이 `false`를 돌려주면 **대입을 취소**한다(veto는 거부라는 뜻이다).

```kotlin
import kotlin.properties.Delegates

class BoundedCounter {
    // 0 미만으로는 내려가지 못하는 카운터
    var count: Int by Delegates.vetoable(0) { _, _, new ->
        new >= 0     // 새 값이 음수면 false → 대입 거부
    }
}

fun main() {
    val c = BoundedCounter()
    c.count = 5;   println(c.count)   // => 5   (5 >= 0, 허용)
    c.count = -3;  println(c.count)   // => 5   (-3 < 0, 거부 → 이전 값 유지)
    c.count = 10;  println(c.count)   // => 10
}
```

`observable`과 가장 크게 다른 점은 `vetoable`의 콜백이 `Boolean`을 반환한다는 것이다. `true`면 대입이 진행되고, `false`면 이전 값이 유지된다. 콜백은 **대입이 확정되기 전**에 호출되므로, 새 값을 검증(validation)하는 관문으로 쓸 수 있다. 검증에 실패했을 때 값이 조용히 바뀌지 않는 것이 문제가 된다면, 콜백 안에서 예외를 던져 "거부"를 "실패"로 바꿀 수도 있다.

### 5.3 둘의 공통 기반: `ObservableProperty`

`observable`과 `vetoable`은 사실 stdlib의 추상 클래스 `ObservableProperty<T>` 하나에서 파생된 위임이다. 이 클래스는 값을 필드에 저장하고, 대입할 때 두 훅을 호출한다. 하나는 대입 전에 호출되어 `Boolean`을 반환하는 `beforeChange`(false면 취소)이고, 다른 하나는 대입 후에 통지하는 `afterChange`이다.

`vetoable`은 `beforeChange`를, `observable`은 `afterChange`를 사용자의 람다로 채운 것이다. 필요하다면 이 추상 클래스를 직접 상속해 두 기능을 합친 위임을 만들 수도 있다.

```kotlin
import kotlin.properties.ObservableProperty
import kotlin.reflect.KProperty

// 대입 전 검증 + 대입 후 로그를 함께
class ValidatedLogged(initial: Int) : ObservableProperty<Int>(initial) {
    override fun beforeChange(property: KProperty<*>, oldValue: Int, newValue: Int): Boolean {
        return newValue in 0..100     // 범위 밖이면 거부
    }
    override fun afterChange(property: KProperty<*>, oldValue: Int, newValue: Int) {
        println("${property.name}: $oldValue -> $newValue 저장됨")
    }
}

class Percentage {
    var value: Int by ValidatedLogged(0)
}
```

이 구조를 보면 `observable`/`vetoable`이 특별한 장치가 아니라 **관례를 구현한 평범한 클래스**라는 것을 알 수 있다. 위임 프로퍼티가 강력한 이유가 여기에 있다. 언어에 특별한 위임 몇 개가 내장된 것이 아니라, 관례만 만족하면 누구나 위임 객체를 만들 수 있고, 표준 라이브러리의 위임도 같은 방식으로 만들어져 있다.

## 6. `notNull`과 맵 위임: 나머지 표준 위임

### 6.1 `Delegates.notNull`: `lateinit`을 쓸 수 없는 곳

`Delegates.notNull<T>()`는 **읽기 전에 반드시 값을 써야 하는** non-null `var` 위임을 만든다. 초기화하기 전에 읽으면 `IllegalStateException`을 던진다.

```kotlin
import kotlin.properties.Delegates

class Connection {
    var port: Int by Delegates.notNull()    // 초기값 없음. 쓰기 전 읽으면 예외.
}

fun main() {
    val c = Connection()
    // println(c.port)   // => IllegalStateException: Property port should be initialized before get.
    c.port = 8080
    println(c.port)      // => 8080
}
```

이것은 `lateinit`과 무엇이 다를까? 겉으로 보이는 의미는 거의 같다. 둘 다 "나중에 주입될 non-null 값이고, 그 전에 읽으면 예외가 난다"는 뜻이다. 하지만 결정적인 차이가 하나 있는데, 바로 **원시 타입(JVM)** 이다. `lateinit var`은 JVM 백엔드에서 "초기화되지 않음" 상태를 `null`로 표현한다. 그런데 원시 타입(`Int`, `Long`, `Double`, `Boolean` 등)은 `null`이 될 수 없으므로 `lateinit`을 쓸 수 없다.

```kotlin
class Bad {
    lateinit var n: Int    // 컴파일 에러: 'lateinit' modifier is not allowed on properties of primitive types
}
class Good {
    var n: Int by Delegates.notNull()   // OK — 위임 객체가 Int?를 내부에 들고 미초기화를 관리
}
```

`notNull`은 내부에 값을 `T?`(nullable 박스)로 저장해 두고, `getValue`를 호출했을 때 값이 null이면 예외를 던지고 아니면 언박싱해 돌려준다. 그래서 원시 타입도 지연 초기화할 수 있다.

그 대가로 **박싱**(JVM에서 `Int`가 위임 필드 안에서 `Integer`로 박싱된다)과 위임 객체 자체의 할당 비용이 생긴다. 따라서 원시 타입이 아니라면 대개 `lateinit`이 더 가볍다. `notNull`은 "원시 타입인데 지연 초기화가 필요하다"는 좁은 경우를 위한 도구로 이해하는 것이 정확하다.

> [!warning] 흔한 오해
> "`lateinit`이 있으니 `notNull`은 필요 없다"고 생각하기 쉽다. 하지만 원시 타입에는 `lateinit`을 쓸 수 없고, `notNull`은 어떤 타입에도(제네릭 `T` 포함) 적용할 수 있으므로 둘이 쓰이는 범위가 다르다. 반대로 참조 타입이라면 박싱과 위임 객체가 필요 없는 `lateinit`이 더 효율적이다.

### 6.2 맵 위임: `by map`

맵 위임은 프로퍼티 값을 맵의 항목에 저장하는 위임이다. JSON 파싱 결과나 설정 맵 같은 동적 데이터를 타입이 있는 프로퍼티처럼 다룰 때 쓴다. stdlib가 `Map`과 `MutableMap`에 대한 `getValue`/`setValue` 확장을 제공하므로, 맵을 그대로 `by` 뒤에 둘 수 있다.

```kotlin
class Account(map: Map<String, Any?>) {
    val name: String by map      // map["name"] 을 읽어 String으로
    val balance: Int by map      // map["balance"] 을 읽어 Int로
}

fun main() {
    val acc = Account(mapOf(
        "name" to "Alice",
        "balance" to 1000
    ))
    println(acc.name)      // => Alice
    println(acc.balance)   // => 1000
}
```

`val name: String by map`에서 게터는 `map.getValue(this, ::name)`을 호출하고, 확장 함수가 `map["name"]`을 조회한다. 즉 **프로퍼티 이름이 곧 맵의 키**이다. 3.3절에서 설명한 `property.name` 활용의 전형적인 예이다. 조회한 결과는 프로퍼티 타입으로 캐스팅된다.

`var` 프로퍼티에는 `MutableMap`을 쓴다. 이때 `setValue` 확장이 `map[property.name] = value`로 맵에 값을 다시 쓴다.

```kotlin
class MutableAccount(val map: MutableMap<String, Any?>) {
    var name: String by map
}
fun main() {
    val m = mutableMapOf<String, Any?>("name" to "Bob")
    val a = MutableAccount(m)
    a.name = "Carol"
    println(m["name"])   // => Carol  (위임 세터가 원본 맵에 되씀)
}
```

맵 위임에는 함정이 있다. 키가 없거나 타입이 맞지 않으면 **런타임에** 오류가 난다. 맵의 내용은 실행 중에만 알 수 있으므로, `by map`은 컴파일 타임에 "그 키가 맵에 있는지"를 검증하지 못한다. 키가 없으면 `Map`의 `getValue` 확장이 `NoSuchElementException`을 던지고, 타입이 맞지 않으면 `ClassCastException`이 발생한다. 맵 위임은 정적 타입 검사의 보호를 받지 못하는, 편의를 위한 얇은 연결 장치라는 점을 기억해야 한다.

> [!note] 명세 기준
> `Map`에 대한 위임 확장은 두 가지로 나뉜다. `Map<String, V>.getValue`는 키가 없으면 예외를 던진다. 하지만 프로퍼티가 nullable이고(`by map`을 `String?`에 쓰는 경우 등) stdlib 오버로드가 다르게 해소되면 동작이 달라질 수 있다. 정확한 동작은 어떤 확장 오버로드를 쓰는지에 달려 있으므로, "맵 위임은 항상 예외를 던진다" 또는 "항상 null을 준다"고 단정하지 말고 대상 타입에 맞춰 확인하는 것이 안전하다.

### 6.3 커스텀 위임을 처음부터 끝까지 작성하기

지금까지 따로따로 살펴본 관례들을 하나의 완성된 위임으로 묶어 보자. 요구 사항은 "은행 계좌의 잔액 프로퍼티는 음수가 될 수 없고, 변경될 때마다 감사 로그를 남기며, 특정 인터페이스를 구현한 소유 객체에만 붙일 수 있다"는 것이다. 이 세 가지를 각각 `setValue`의 검증, `setValue`의 부수 효과, `thisRef`의 타입 제약으로 구현한다.

```kotlin
import kotlin.reflect.KProperty

// 소유자가 갖춰야 할 계약 — thisRef 타입으로 강제할 대상
interface Auditable {
    fun audit(message: String)
}

// 음수 금지 + 감사 로그 + Auditable 소유자 전용 위임
class NonNegativeMoney(private var amount: Long) {
    operator fun getValue(thisRef: Auditable, property: KProperty<*>): Long = amount

    operator fun setValue(thisRef: Auditable, property: KProperty<*>, value: Long) {
        require(value >= 0) { "${property.name} 는 음수가 될 수 없다: $value" }
        val old = amount
        amount = value
        thisRef.audit("${property.name}: $old -> $value")   // 소유자의 audit 호출
    }
}

class Account(initial: Long) : Auditable {
    var balance: Long by NonNegativeMoney(initial)
    override fun audit(message: String) = println("[감사] $message")
}

fun main() {
    val acc = Account(100)
    println(acc.balance)   // => 100
    acc.balance = 250      // => [감사] balance: 100 -> 250
    println(acc.balance)   // => 250
    // acc.balance = -5    // => IllegalArgumentException: balance 는 음수가 될 수 없다: -5
}
```

이 코드에서는 세 가지 관례가 함께 동작한다.

- **`thisRef: Auditable`** 은 `Auditable`을 구현하지 않은 클래스에 이 위임을 붙이지 못하도록 컴파일 타임에 막는다(2.2절).
- **`setValue`의 `require`** 는 불변식(invariant)을 강제한다.
- **`thisRef.audit(...)`** 는 위임 안에서 소유 객체의 기능을 호출한다. 위임이 소유 객체와 협력하는 패턴이다.

`NonNegativeMoney`를 `Auditable`이 아닌 클래스에 붙이면 다음과 같이 된다.

```kotlin
class Wallet {
    var cash: Long by NonNegativeMoney(0)
    // 컴파일 에러: getValue/setValue가 Auditable thisRef를 기대하는데 Wallet은 Auditable이 아님
}
```

이 예에서 알 수 있듯이, 위임은 단순히 "값을 대신 저장하는 상자"가 아니라 **타입 제약과 불변식, 소유 객체와의 협력을 하나로 묶는 재사용 단위**이다. 같은 `NonNegativeMoney`를 여러 `Auditable` 클래스의 여러 금액 프로퍼티에 붙이면, 음수 금지와 감사 로그라는 정책이 위임 구현 한 곳에 모인다. 22장의 커스텀 접근자로는 얻을 수 없는, 위임만의 재사용 가치이다.

## 7. `provideDelegate`: 위임을 만드는 위임

지금까지는 `by 표현식`의 `표현식`이 바로 위임 객체였다. `provideDelegate`는 그 사이에 **한 단계**를 더 둔다. `by 표현식`을 평가한 결과가 위임 객체가 아니라 **"위임 객체를 만들어 주는 팩토리"** 가 되고, 컴파일러가 이 팩토리에 프로퍼티 메타데이터를 넘겨 실제 위임 객체를 받아 온다.

### 7.1 시그니처와 호출 시점

```kotlin
import kotlin.reflect.KProperty

operator fun provideDelegate(thisRef: Any?, property: KProperty<*>): ActualDelegate
```

`by 표현식`의 결과 객체에 `provideDelegate`가 정의되어 있으면, 컴파일러는 `$delegate` 필드를 채울 때 `표현식` 자체를 넣지 않는다. 대신 `표현식.provideDelegate(thisRef, property)`를 **호출한 결과**를 넣는다.

```text
provideDelegate 없을 때:
    prop$delegate = 표현식

provideDelegate 있을 때:
    prop$delegate = 표현식.provideDelegate(this, ::prop)
```

가장 큰 이점은 실행 시점에 있다. `provideDelegate`는 **프로퍼티가 초기화되는 시점(객체 생성 시)에, 프로퍼티 메타데이터에 접근할 수 있는 상태로** 실행된다. 그래서 위임을 만드는 바로 그 순간에 검증이나 등록 같은 작업을 할 수 있다. 반면 일반 `getValue`는 **프로퍼티를 읽을 때**가 되어서야 호출된다. "생성 시점에 어떤 작업을 하고 싶다"는 요구가 `provideDelegate`가 존재하는 이유이다.

### 7.2 언제 쓰나: 생성 시점 검증의 예

가장 흔한 용도는 "이 위임이 붙은 프로퍼티가 어떤 조건을 만족하는지 **생성 시점에** 검사"하는 것이다. 예를 들어 프로퍼티 이름이 규칙에 맞는지, 소유 클래스가 특정 조건을 갖췄는지를 첫 접근까지 기다리지 않고 바로 확인할 수 있다.

```kotlin
import kotlin.reflect.KProperty
import kotlin.properties.ReadOnlyProperty

// 프로퍼티 이름이 대문자로 시작해야만 허용하는 위임 (일반 도메인 규칙 예)
class UppercaseChecked<T>(private val value: T) {
    operator fun provideDelegate(thisRef: Any?, property: KProperty<*>): ReadOnlyProperty<Any?, T> {
        require(property.name.first().isUpperCase()) {
            "프로퍼티 '${property.name}' 는 대문자로 시작해야 한다"
        }
        return ReadOnlyProperty { _, _ -> value }
    }
}

fun <T> checked(value: T) = UppercaseChecked(value)

class Registry {
    val Alpha: String by checked("ok")    // OK — 객체 생성 시 검증 통과
    // val beta: String by checked("no")  // 객체 생성 시 IllegalArgumentException
}
```

`Alpha`를 한 번도 **읽지 않았는데도**, `Registry` 객체를 만드는 순간 `provideDelegate`가 실행되어 이름을 검증한다. 이 검증을 `getValue`에 두었다면, 프로퍼티를 실제로 읽기 전까지는 오류가 드러나지 않았을 것이다. `provideDelegate`를 쓰면 오류를 **더 이른 시점(생성)** 으로 앞당길 수 있다.

### 7.3 `PropertyDelegateProvider`: 표준 인터페이스

`getValue`/`setValue`에 `ReadOnlyProperty`/`ReadWriteProperty`가 있듯이, `provideDelegate`에도 `PropertyDelegateProvider<in T, out D>`라는 표준 함수형 인터페이스가 있다.

```kotlin
public fun interface PropertyDelegateProvider<in T, out D> {
    operator fun provideDelegate(thisRef: T, property: KProperty<*>): D
}
```

이 인터페이스를 쓰면 팩토리를 람다로 간결하게 표현할 수 있다.

```kotlin
import kotlin.properties.PropertyDelegateProvider
import kotlin.properties.ReadOnlyProperty

fun namedConstant(value: Int) = PropertyDelegateProvider<Any?, ReadOnlyProperty<Any?, Int>> { _, property ->
    println("위임 생성: ${property.name}")
    ReadOnlyProperty { _, _ -> value }
}

class Box {
    val size: Int by namedConstant(10)   // 객체 생성 시 "위임 생성: size" 출력
}
```

`provideDelegate`가 돌려주는 `D`는 다시 `getValue`(필요하면 `setValue`도) 관례를 만족해야 한다. 즉 두 단계의 관례가 맞물린다. 바깥 단계는 "위임을 제공"하는 `provideDelegate`이고, 안쪽 단계는 "값을 제공"하는 `getValue`/`setValue`이다.

## 8. 로컬 위임: 함수 안의 위임 변수

위임은 클래스 프로퍼티뿐 아니라 **함수 안의 지역 변수**에도 붙일 수 있다. `val`/`var` 지역 변수를 `by`로 위임하면 된다.

```kotlin
fun process() {
    val config: String by lazy {
        println("설정 로드")
        readConfigFromDisk()
    }

    if (needsConfig()) {
        println(config)    // 여기 처음 도달할 때만 "설정 로드" + readConfigFromDisk()
    }
    // needsConfig()가 false면 config는 끝내 초기화되지 않음
}
```

로컬 위임의 장점은 **분기에 따라 실제로 필요할 때만** 계산하도록 미룰 수 있다는 점이다. 위 예에서 `needsConfig()`가 거짓이면 디스크 읽기는 아예 일어나지 않는다. 지역 변수를 그냥 `val config = readConfigFromDisk()`로 선언하면 선언에 도달하자마자 계산되지만, `by lazy`로 선언하면 실제로 사용하는 지점까지 계산이 미뤄진다.

로컬 위임에서 `getValue`/`setValue`가 받는 `thisRef`는 **`null`** 이다. 지역 변수에는 소유 객체가 없기 때문이다. 그래서 로컬 위임에 쓸 위임 객체의 `getValue`는 `thisRef: Nothing?`(또는 `Any?`)를 받아야 한다. `property` 파라미터는 그대로 유효해서, 로컬 변수의 이름 같은 메타데이터를 제공한다.

컴파일된 형태는 멤버 위임과 비슷하지만 더 단순하다. 위임 객체는 지역 슬롯에 저장되거나 클로저에 캡처되고(14장 클로저와 캡처), 변수 읽기와 쓰기는 `getValue`/`setValue` 호출로 번역된다. 로컬 위임은 특히 스코프 안에서만 의미가 있는 지연 로직이나 관측 로직을 깔끔하게 표현할 때 쓰인다.

## 9. 성능과 함정, 흔한 오해: 위임은 공짜가 아니다

### 9.1 위임의 런타임 비용

위임 프로퍼티는 편리한 만큼 **간접 비용**이 든다. 정확히 어디에서 비용이 생기는지 살펴보자.

- **읽을 때마다 함수 호출 하나**: 일반 프로퍼티를 읽으면 필드에 한 번 접근하지만, 위임 프로퍼티를 읽으면 `게터 → $delegate 필드 로드 → getValue 호출`을 거친다. `getValue`가 `inline`이면(예: `Lazy.getValue`) 이 호출이 인라인되어 사라질 수 있지만(15장 인라인 함수와 reified), 인라인되지 않는 위임은 읽을 때마다 가상 호출이 하나씩 들어간다.
- **위임 객체 할당**: 소유 인스턴스마다 위임 객체가 하나씩 만들어진다. `Lazy` 래퍼, `ObservableProperty` 인스턴스 등이 여기에 해당한다. 프로퍼티와 인스턴스가 많으면 이 할당이 쌓인다.
- **박싱**: `notNull`처럼 값을 `T?`로 저장하는 위임은 원시 타입을 박싱한다(6.1절). `Int` 프로퍼티 하나가 위임 안에서 `Integer`가 된다.
- **`KProperty` 메타데이터**: 3.2절에서 본 정적 배열이다. 프로퍼티당 한 번만 만들어지므로 대개 무시할 만하지만, 비용이 없는 것은 아니다.

핵심은 두 경우를 구분하는 것이다. 하나는 **`lazy`처럼 이득이 비용보다 훨씬 큰 경우**(무거운 계산을 실제로 미루는 경우)이고, 다른 하나는 **단순한 프로퍼티에 위임을 남용하는 경우**(간단한 저장에 위임 객체와 간접 호출을 더하는 경우)이다. 값을 필드에 저장하기만 한다면 그냥 `var`/`val`을 쓰는 편이 항상 더 빠르다. 위임은 "재사용할 만한 접근자 로직"이 있을 때 가치가 있다.

> [!caution] 성능 주의
> `by lazy(LazyThreadSafetyMode.SYNCHRONIZED)`(기본)는 초기화할 때 락을 잡는다. **초기화한 뒤의** 읽기는 락 없이 빠르지만, 수명이 짧아 초기화가 자주 일어나는 객체를 대량으로 만든다면 락 비용이 누적된다. 단일 스레드임이 확실하면 `NONE`이, 순수한 계산이면 `PUBLICATION`이 더 가볍다. 다만 항상 측정으로 확인해야 한다. 대개 `lazy`의 락은 병목이 아니다.

### 9.2 `by 표현식`은 한 번만 평가되지만, 위임 객체는 인스턴스마다 생긴다

"위임 객체가 여러 프로퍼티에 공유되는가, 아니면 인스턴스마다 새로 생기는가?"는 자주 헷갈리는 질문이다.

`by 표현식`은 **각 프로퍼티의 초기화 지점에서** 평가된다. 멤버 프로퍼티라면 소유 객체가 생성될 때마다 평가된다. 그래서 아래 코드는 의도에 따라 문제가 될 수 있다.

```kotlin
// 안티패턴: 모든 인스턴스가 같은 위임 객체를 공유하려는 의도라면 이건 틀렸다
class Node {
    var state: Int by Delegates.observable(0) { _, o, n -> log(o, n) }
}
// Node를 100개 만들면 observable 위임 객체도 100개 (각자 자기 state 저장)
```

각 `Node`는 자신만의 `observable` 위임을 가진다. 대개는 이것이 **원하는** 동작이다. 노드마다 독립적인 상태를 가져야 하기 때문이다. 하지만 전역 카운터처럼 여러 인스턴스가 위임 객체를 공유하기를 원했다면, `by` 표현식이 인스턴스마다 새 객체를 만들기 때문에 의도와 어긋난다.

위임 객체를 공유하려면 클래스 밖(top-level이나 companion)에 위임 객체를 만들어 두고, `by` 뒤에서 그 참조를 써야 한다. 다만 이렇게 하면 위임의 `thisRef`로 인스턴스마다 다른 객체가 들어오므로, 위임이 상태를 어떻게 관리할지 신중하게 설계해야 한다.

### 9.3 흔한 오해 정리

이 장의 내용과 관련된 흔한 오해들을 정리한다.

**"`by`는 하나의 기능이다"**: 그렇지 않다. 프로퍼티 위임(`val x by ...`)과 클래스 위임(`class C : I by ...`, 32장 클래스 위임)은 서로 다른 기능이다(1.1절).

**"위임 프로퍼티는 백킹 필드를 갖는다"**: 그렇지 않다. 위임 프로퍼티에는 백킹 **필드**(`field`)가 없다. 대신 위임 **객체**를 담는 `$delegate` 필드가 있다. 값을 저장하는 것은 위임 객체 내부가 맡을 일이지, 프로퍼티의 백킹 필드가 하는 일이 아니다. 22장(프로퍼티와 백킹 필드)에서 본 `field`는 위임 프로퍼티에서 접근할 수 없다(존재하지 않기 때문이다).

**"`getValue`/`setValue`는 특별한 언어 기능이다"**: 그렇지 않다. 이 함수들은 19장(연산자 오버로딩과 관례)에서 본 관례 함수의 하나일 뿐이다. `operator` 키워드를 붙이고 정해진 이름과 시그니처를 따르면 누구나 위임을 만들 수 있다. `lazy` 같은 표준 위임도 그렇게 만들어진 평범한 라이브러리 코드이다.

**"`by lazy`는 항상 스레드 안전하다"**: 기본 모드(`SYNCHRONIZED`)는 스레드 안전하지만, `NONE` 모드는 단일 스레드 전용이다(4.2절). 모드를 명시적으로 바꿨다면 안전성도 달라진다.

**"`by lazy`는 `var`에도 쓸 수 있다"**: 그렇지 않다. `Lazy`에는 `setValue`가 없으므로 `val`에만 쓸 수 있다(4.1절).

**"맵 위임은 안전하다"**: 맵 위임은 정적 타입 검사를 거치지 않는다(6.2절). 키가 없거나 타입이 맞지 않으면 런타임에야 오류가 난다.

**"위임은 성능 최적화다"**: `lazy`는 계산을 미뤄 이득을 줄 수 있지만, 위임 자체는 간접 호출과 객체 할당, 경우에 따라 박싱이라는 **비용**을 더한다(9.1절). 위임은 최적화 도구가 아니라 **추상화와 재사용**을 위한 도구로 이해하는 것이 정확하다.

### 9.4 언제 위임을 쓰는가: 판단 기준

위임 프로퍼티는 다음과 같은 경우에 쓸 만하다.

- **접근자 로직이 반복된다**: "지연 초기화", "변경 감지", "외부 소스 조회" 같은 패턴이 여러 프로퍼티에 걸쳐 나타난다면, 위임으로 한 번 만들어 재사용한다.
- **계산이 비싸고 조건에 따라 필요하다**: 값이 항상 필요하지는 않고 필요할 때만 계산하고 싶다면 `by lazy`를 쓴다.
- **프레임워크가 프로퍼티 이름을 활용한다**: 맵이나 설정, 환경 변수처럼 프로퍼티 이름을 키로 쓰는 매핑이라면, 맵 위임이나 커스텀 위임에서 `property.name`을 활용한다.

반대로 값을 담기만 하는 프로퍼티, 성능이 매우 중요한 핫 패스의 프로퍼티, 로직이 그 프로퍼티에만 해당해 재사용할 여지가 없는 경우에는 위임의 간접 비용만 늘어날 뿐 이득이 없다. 이럴 때는 일반 프로퍼티나 커스텀 접근자(22장 프로퍼티와 백킹 필드)를 쓰는 편이 낫다.
