[[37 - 타입 안전 빌더와 DSL]]에서는 수신 객체 지정 람다로 계층적인 데이터 구조를 안전하게 조립하는 방법을 살펴보았다. 그렇게 조립한 결과물은 대개 리스트, 맵, 집합 같은 컬렉션이다. 이 장에서는 코틀린이 컬렉션을 *타입 시스템 수준에서* 어떻게 나누어 설계했는지 살펴본다.

코틀린 컬렉션 프레임워크에서 가장 잘 알려져 있으면서 가장 많이 오해받는 특징은 **읽기 전용 인터페이스와 가변 인터페이스의 분리**이다. `List`와 `MutableList`, `Set`과 `MutableSet`, `Map`과 `MutableMap`이 그 예이다. 이 분리 때문에 코틀린을 처음 배우는 사람은 "코틀린에는 불변 컬렉션이 있구나"라고 생각하기 쉽다. 이 생각은 절반은 맞지만, 나머지 절반은 위험할 정도로 틀렸다.

이 장에서는 컬렉션의 **정적 구조**를 다룬다. 인터페이스 계층의 구성, 타입 관계에서 본 읽기 전용과 가변의 의미, 팩토리 함수(`listOf`, `mutableListOf`, `buildList`)가 내부에서 만드는 객체, 배열이 이 계층 밖에 있는 이유, 진짜 불변성이 필요할 때 쓸 수 있는 방법이 그 내용이다. 특히 읽기 전용은 불변이 아니라는 점, `List`가 `MutableList`의 슈퍼타입이라는 점, 배열은 컬렉션이 아니라는 점을 중점적으로 설명한다.

`map`/`filter`/`fold` 같은 즉시 평가(eager) 연산은 [[39 - 컬렉션 연산과 함수형 파이프라인]]에서, 지연(lazy) 평가를 하는 시퀀스는 [[40 - 시퀀스와 지연 평가]]에서 다룬다. 변성(`out`/`in`)의 일반 이론은 [[33 - 제네릭 1 - 타입 파라미터와 변성]]에서, 타입 소거는 [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]에서 설명한다.

## 1. 읽기 전용과 가변을 나눈 이유

### 1.1 Java에서 물려받은 문제와 코틀린의 구분

Java 컬렉션 프레임워크에는 근본적인 비대칭이 하나 있다. `java.util.List` 인터페이스는 `get`, `size` 같은 조회 연산과 `add`, `remove`, `set` 같은 변경 연산을 **모두 한 인터페이스에** 담고 있다. 그래서 "이 리스트는 읽기만 하고 절대 바꾸지 않겠다"는 의도를 타입으로 표현할 방법이 없다.

관례적으로 `Collections.unmodifiableList`로 감싸기는 하지만, 이것은 타입이 아니라 런타임 동작이다. 컴파일러는 `unmodifiableList`가 반환한 객체에 `add`를 호출하는 코드를 아무 경고 없이 통과시키고, 실행 시점에 `UnsupportedOperationException`이 발생한다.

코틀린은 이 문제를 타입 수준에서 다시 정리했다. **조회 연산만 담은 인터페이스**(`List`, `Set`, `Map`, `Collection`, `Iterable`)와 **변경 연산까지 담은 인터페이스**(`MutableList`, `MutableSet`, `MutableMap`, `MutableCollection`, `MutableIterable`)를 나눈 것이다.

함수가 `List<Int>`를 파라미터로 받으면, 그 함수 본문에서는 리스트에 요소를 추가하거나 제거할 문법적 수단이 아예 없다. `List` 인터페이스에는 `add`라는 멤버가 없기 때문이다.

```kotlin
fun sum(numbers: List<Int>): Int {
    var acc = 0
    for (n in numbers) acc += n
    // numbers.add(99)  // 컴파일 에러: 'add'는 List의 멤버가 아님
    return acc
}
```

이 구분의 가치는 **의도를 표현한다**는 데 있다. `List`를 받는 함수는 "이 컬렉션을 읽기만 하겠다"고 시그니처로 약속한다. 반대로 `MutableList`를 받는 함수는 "이 컬렉션을 바꿀 수도 있다"고 알린다. 호출하는 쪽은 시그니처만 보고도 자기 컬렉션이 함수 안에서 변경될지 판단할 수 있다.

### 1.2 이 구분은 어느 층위에 있는가

여기서 아주 중요한 점이 하나 있다. 읽기 전용과 가변의 구분은 **코틀린 타입 시스템(인터페이스)의 층위**에 있고, 런타임 객체의 층위에 있지 않다. 인터페이스는 "이 참조로 무엇을 호출할 수 있는가"를 정할 뿐이고, "이 객체가 물리적으로 변경 불가능한가"를 정하지 않는다.

```text
층위 1 — 타입/인터페이스 (컴파일 타임):
    List<E>        →  조회 멤버만 노출 (읽기 전용 "능력")
    MutableList<E> →  조회 + 변경 멤버 노출 (가변 "능력")

층위 2 — 런타임 객체 (JVM 백엔드에서):
    실제 인스턴스는 대개 java.util.ArrayList 같은 "물리적으로 가변인" 객체
    → 어떤 인터페이스로 참조하든, 객체 자체는 여전히 가변일 수 있다
```

두 층위가 분리되어 있다는 사실이 이 장 전체의 출발점이다. `List`라는 *참조*에는 변경 능력이 없지만, 그 참조가 가리키는 *객체*는 여전히 물리적으로 가변일 수 있다. 이 차이 때문에 두 가지 큰 오해가 생긴다(3절, 4절).

[[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]에서 본 `String?`과 비교하면 이해하기 쉽다. `String?` 타입은 "이 참조에 null이 들어올 수 있다"는 능력에 관한 것이지, 값이 실제로 null인지에 관한 것이 아니다. 마찬가지로 `List`는 "이 참조로는 변경할 수 없다"는 능력에 관한 것이지, 객체가 불변인지에 관한 것이 아니다.

> [!note] 명세 기준
> 코틀린 표준 라이브러리에서 `List`, `MutableList` 등은 `kotlin.collections` 패키지의 인터페이스이고, **공통(common) 소스셋**에 선언되어 있다. 즉 JVM 전용 개념이 아니다.
>
> JVM 백엔드에서는 이 인터페이스가 `java.util.List` 등과 "매핑된 타입(mapped type)"으로 연결되지만, Kotlin/Native·JS·Wasm 백엔드에서는 각 플랫폼의 자체 구현이 같은 인터페이스 계약을 만족한다. 읽기 전용과 가변의 구분은 언어 수준의 개념이다.

### 1.3 "불변"이 아니라 "읽기 전용"을 택한 이유: 설계 결정

코틀린 설계자들은 왜 진짜 불변 컬렉션 대신 읽기 전용 인터페이스를 택했을까? 여기에는 세 가지 이유가 함께 작용한다.

- **Java 상호운용**: 코틀린은 방대한 Java 생태계 위에서 동작해야 하는데, Java의 컬렉션은 모두 가변이다. 코틀린이 진짜 불변 컬렉션만 다룬다면 Java에서 넘어오는 `ArrayList`를 매번 불변 구조로 복사해야 하고, 상호운용 경계마다 비용이 생긴다. 읽기 전용 *인터페이스*를 쓰면 기존 Java 가변 객체를 복사하지 않고 `List`로 볼 수 있다. 더 좁은 인터페이스로 참조할 뿐이기 때문이다.
- **공변성(covariance)의 이점**: 읽기 전용 `List<out E>`는 공변으로 선언할 수 있다(4.3절). 즉 `List<Cat>`을 `List<Animal>`로 안전하게 다룰 수 있다. 이 안전성은 바로 "변경할 수 없다"는 점 때문에 성립한다. 가변 리스트라면 `List<Animal>`에 `Dog`를 넣어 `List<Cat>`을 오염시킬 수 있으므로 위험하다. 읽기 전용이라는 제약 덕분에 공변성이라는 유연성을 얻는 것이다.
- **점진성(gradualism)**: 진짜 영속(persistent) 자료구조는 성능 특성이 다르고(구조 공유, 별도 구현체), 표준 라이브러리에 강제로 넣으면 모든 사용자가 그 비용과 이점을 함께 떠안게 된다. 그래서 코틀린은 인터페이스 분리라는 가벼운 규칙을 기본으로 제공하고, 진짜 불변이 필요한 사람은 별도 라이브러리(`kotlinx.collections.immutable`)를 선택하도록 했다(8절).

## 2. 컬렉션 인터페이스 계층의 구조

### 2.1 전체 구조

코틀린 컬렉션의 인터페이스 계층은 읽기 전용 축과 가변 축이 나란히 놓인 격자 구조이다.

```text
                    Iterable<out T>            MutableIterable<out T>
                         │  △                        │  △
                         │  └────────────────────────┘  (Mutable*는 읽기 전용 짝을 확장)
                         │
                    Collection<out E>          MutableCollection<E>
                       │      │                  │        │
              ┌────────┘      └────────┐   ┌─────┘        └──────┐
              │                        │   │                     │
         List<out E>              Set<out E> │                   │
              △                        △    │                   │
              │                        │    │                   │
         MutableList<E> ──────────────────┘  MutableSet<E>       │
              (List + MutableCollection 둘 다 확장)  (Set + MutableCollection)

     Map<K, out V>              MutableMap<K, V>
         △                          △
         └──────────────────────────┘
         (Map은 Collection 계층 바깥의 독립 인터페이스)
```

이 그림에서 알 수 있는 핵심은 세 가지이다.

1. 모든 `Mutable*` 인터페이스는 자신의 읽기 전용 짝을 **확장(상속)한다**. 예를 들어 `MutableList<E> : List<E>`이다. 즉 가변 리스트는 읽기 전용 리스트의 하위 타입이다. 이 관계는 4절에서 자세히 살펴본다.
2. `List`, `Set`, `Collection`, `Iterable`은 타입 파라미터에 `out`이 붙어 있으므로 **공변**이다. `MutableList`, `MutableSet` 등은 `out`이 없으므로 **무공변(invariant)** 이다.
3. `Map`은 `Collection`을 확장하지 *않는다*. `Map`은 요소의 컬렉션이 아니라 키와 값의 대응이므로 별도의 계보를 이룬다. 이 내용은 6절에서 다룬다.

### 2.2 각 인터페이스의 계약

읽기 전용 축을 아래에서 위로 올라가면 능력이 하나씩 추가된다.

| 인터페이스 | 추가하는 멤버(요지) | 변성 |
|---|---|---|
| `Iterable<out T>` | `iterator()` | 공변 |
| `Collection<out E>` | `size`, `isEmpty()`, `contains(e)`, `containsAll(c)` | 공변 |
| `List<out E>` | `get(index)`, `indexOf`, `subList`, 순서 보장 | 공변 |
| `Set<out E>` | (멤버는 Collection과 거의 같지만) 원소 유일성 계약 | 공변 |
| `Map<K, out V>` | `keys`, `values`, `entries`, `get(key)`, `containsKey/Value` | V에 대해 공변 |

가변 축은 여기에 변경 능력을 더한다.

| 인터페이스 | 추가하는 변경 멤버(요지) |
|---|---|
| `MutableIterable<out T>` | `iterator()`가 `MutableIterator` 반환(`remove()` 가능) |
| `MutableCollection<E>` | `add`, `remove`, `addAll`, `removeAll`, `retainAll`, `clear` |
| `MutableList<E>` | `set(index, e)`, `add(index, e)`, `removeAt(index)`, `listIterator` |
| `MutableSet<E>` | (MutableCollection의 변경 멤버) |
| `MutableMap<K, V>` | `put`, `remove(key)`, `putAll`, `clear`, `MutableEntry.setValue` |

```kotlin
val ro: List<Int> = listOf(1, 2, 3)
ro.size            // => 3       (Collection)
ro.contains(2)     // => true    (Collection)
ro[0]              // => 1       (List.get, 연산자 관례)
ro.indexOf(3)      // => 2       (List)
// ro.add(4)       // 컴파일 에러: List엔 add 없음

val mut: MutableList<Int> = mutableListOf(1, 2, 3)
mut.add(4)         // MutableCollection의 멤버
mut[0] = 10        // MutableList.set (연산자 관례)
mut.removeAt(1)    // MutableList
// mut => [10, 3, 4]
```

`ro[0]`이 동작하는 것은 `List.get`이 `operator`로 선언된 관례 함수이기 때문이고(자세한 내용은 [[19 - 연산자 오버로딩과 관례]]), `mut[0] = 10`은 `MutableList.set` 관례를 사용한다. 그래서 인덱스 대입 문법은 가변 리스트에서만 컴파일된다.

### 2.3 `iterator`와 변경이 만나는 지점

읽기 전용 `Iterable`도 `iterator()`를 제공한다. 하지만 이 이터레이터는 `kotlin.collections.Iterator`이고 `remove()`가 없다. 반면 `MutableIterable.iterator()`는 `MutableIterator`를 반환하며, 여기에는 `remove()`가 있다. 따라서 순회하면서 삭제하는 작업은 가변 축에서만 할 수 있다.

```kotlin
val mut = mutableListOf("a", "b", "c")
val it = mut.iterator()       // MutableIterator (mut이 MutableList이므로)
while (it.hasNext()) {
    if (it.next() == "b") it.remove()
}
// mut => [a, c]

val ro: List<String> = mut
val it2 = ro.iterator()       // 그냥 Iterator
// it2.remove()               // 컴파일 에러: Iterator엔 remove 없음
```

이 예는 읽기 전용과 가변의 구분이 순회 계층의 가장 아래까지 일관되게 적용된다는 것을 보여 준다. `for` 루프가 사용하는 `iterator()` 관례([[18 - 범위와 진행과 반복]])도 이 두 축을 구별한다.

> [!info] 역사 메모
> 이 인터페이스 분리는 코틀린 1.0 이전부터 확립된 설계이다. Scala는 `scala.collection.immutable`과 `scala.collection.mutable`을 **패키지**로 나누었지만, 코틀린은 같은 패키지 안에서 **인터페이스 이름**(`Mutable` 접두사)으로 나누었다. 근본적인 차이는 Scala의 immutable은 진짜 영속 자료구조이고, 코틀린의 읽기 전용은 인터페이스일 뿐이라는 점이다. 이름은 비슷해 보여도 보장하는 수준이 다르다.

## 3. 읽기 전용은 불변이 아니다

### 3.1 흔한 오해와 반례

가장 널리 퍼진 오해는 **"`listOf(1, 2, 3)`는 불변(immutable) 리스트다."** 라는 생각이다. 정확히 말하면 `listOf`가 반환하는 것은 *읽기 전용 인터페이스로 참조한* 리스트이고, 물리적으로 변경할 수 없는 자료구조가 아니다. 다음 세 가지 반례로 이 차이를 확인해 보자.

**반례 1: 캐스팅으로 변경하기.** `List` 참조를 `MutableList`로 캐스트하면, 런타임 객체가 실제로 가변인 경우 변경할 수 있다.

```kotlin
val ro: List<Int> = mutableListOf(1, 2, 3)  // 실제 객체는 ArrayList(가변)
(ro as MutableList<Int>).add(4)             // 성공! 캐스트가 통한다
println(ro)                                  // => [1, 2, 3, 4]
```

`ro`의 정적 타입은 `List`이므로 컴파일러는 `add`를 막는다. 하지만 런타임 객체가 `ArrayList`이므로 `MutableList`로의 다운캐스트가 성공하고, 그 순간 변경할 수 있게 된다. 진짜 불변 자료구조라면 이 캐스트가 불가능하거나(타입이 다르므로), 변경할 때 예외가 발생해야 한다.

**반례 2: 별칭(aliasing)을 통한 원격 변경.** 가변 참조와 읽기 전용 참조가 같은 객체를 가리키면, 가변 참조로 바꾼 내용이 읽기 전용 참조에도 그대로 보인다.

```kotlin
val mutable: MutableList<Int> = mutableListOf(1, 2, 3)
val readOnly: List<Int> = mutable         // 같은 객체를 좁은 타입으로 참조
mutable.add(99)
println(readOnly)                          // => [1, 2, 3, 99]  (변했다!)
```

`readOnly`로는 요소를 추가할 수 없지만, `readOnly`가 가리키는 객체가 다른 이름(`mutable`)으로 변경되는 것은 막을 수 없다. 읽기 전용은 "이 참조로는 바꿀 수 없다"는 뜻일 뿐이고, "이 객체는 바뀌지 않는다"는 뜻이 아니다.

**반례 3: 요소 자체의 가변성.** 컬렉션이 정말 불변이더라도, 그 안에 담긴 *요소*가 가변이면 요소를 통해 상태가 바뀐다.

```kotlin
class Counter(var value: Int)

val list: List<Counter> = listOf(Counter(0), Counter(0))
list[0].value = 42        // 컬렉션은 안 건드리지만 요소 상태를 바꿈
println(list[0].value)    // => 42
```

이것은 [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 본 `val`의 함정과 같은 층위의 문제이다. `val`이 재대입만 막고 대상 객체의 가변성은 막지 못하듯이, 읽기 전용 컬렉션도 컨테이너의 구조 변경만 막고 요소 내부의 변경은 막지 못한다. 진짜 불변성을 얻으려면 컨테이너와 요소가 모두 불변이라는 조건이 재귀적으로 성립해야 한다.

### 3.2 `listOf`가 내부에서 만드는 객체

이 오해를 완전히 풀려면 팩토리 함수가 실제로 만드는 객체를 봐야 한다. 표준 라이브러리의 `listOf`는 대략 다음과 같이 정의되어 있다.

```kotlin
// 개념적 정의 (stdlib)
public fun <T> listOf(vararg elements: T): List<T> =
    if (elements.isNotEmpty()) elements.asList() else emptyList()
```

요소가 없으면 `emptyList()`가 `EmptyList`라는 코틀린 싱글턴을 반환한다(진짜 불변이며 상태가 없다). 하지만 요소가 있으면 `elements.asList()`를 반환한다. JVM 백엔드에서 `Array<out T>.asList()`는 내부적으로 배열을 감싸는 뷰를 만든다. 개념상 `java.util.Arrays.asList(배열)`에 해당하는 고정 크기 리스트이다.

```text
JVM 백엔드에서 listOf(1, 2, 3)의 실체:

   listOf(1, 2, 3)
        │
        ▼
   vararg 배열 [1, 2, 3]  ── (힙의 Integer[] 또는 int[]→박싱)
        │
        ▼
   asList() → 배열을 감싸는 고정 크기 List 뷰
        │
        ▼
   반환 타입은 kotlin.collections.List<Int> (읽기 전용)
   실체는 배열 기반 뷰: add/remove는 불가하나 내부 set은 물리적으로 가능
```

즉 `listOf`가 반환한 리스트는 크기를 바꿀 수는(add/remove) 없지만, 이것을 "영속 불변 자료구조"라고 부르는 것은 과장이다. 배열 위에 놓인 고정 크기 뷰를 읽기 전용 인터페이스로 노출했을 뿐이기 때문이다. 구현은 백엔드마다 다를 수 있으므로, 이 설명은 "JVM 백엔드에서"로 한정해야 한다. 다른 플랫폼은 자체 읽기 전용 구현체를 사용한다.

> [!caution] 성능 주의
> `listOf(x)`처럼 요소가 하나이면 JVM 백엔드에서 단일 원소에 최적화된 구현(개념상 `Collections.singletonList`에 해당)을 사용하는 등, 크기에 따라 다른 내부 구현이 선택될 수 있다. 이런 세부 사항은 표준 라이브러리 구현이 재량으로 정하므로, 특정 클래스에 의존하는 코드는 깨지기 쉽다. 코드가 의존해도 되는 것은 인터페이스 계약(`List`가 노출하는 멤버)뿐이다.

### 3.3 뷰: 읽기 전용이 만드는 착시

읽기 전용 컬렉션이 특히 위험해지는 경우가 **뷰(view)** 이다. 뷰는 어떤 컬렉션의 일부나 변환 결과를 실제로 복사하지 않고 "바라보기만" 하는 객체이다. 대표적인 예가 `subList`이다.

```kotlin
val backing: MutableList<Int> = mutableListOf(0, 1, 2, 3, 4)
val view: List<Int> = backing.subList(1, 4)   // [1, 2, 3]을 바라보는 뷰
println(view)             // => [1, 2, 3]
backing[2] = 99           // 원본을 변경
println(view)             // => [1, 99, 3]  (뷰에 반영됨!)
```

`view`는 읽기 전용 `List`이지만 독립된 복사본이 아니라 `backing`의 일부를 들여다보는 창이다. 따라서 원본이 바뀌면 뷰로 보이는 내용도 바뀐다. "읽기 전용이니 내가 받은 리스트는 바뀌지 않을 것"이라는 가정은 여기서 깨진다. 함수가 `List`를 반환한다고 해서 그것이 방어적 복사본이라는 보장은 없다.

이 절의 핵심 교훈은 다음과 같다. `List` 타입을 받거나 반환했다는 사실만으로 "이 데이터는 앞으로 변하지 않는다"고 결론 내려서는 안 된다. 그 리스트가 (a) 어딘가의 가변 참조와 별칭 관계인지, (b) 뷰인지, (c) 캐스트로 변경할 수 있는지, (d) 요소가 가변인지를 모르면 불변성을 주장할 수 없다. 진짜 불변이 필요하다면 8절에서 소개하는 도구를 써야 한다.

## 4. 참조 능력의 문제: `List`는 `MutableList`의 슈퍼타입이다

### 4.1 흔한 오해

두 번째로 흔한 오해는 **"`List`와 `MutableList`는 서로 무관한 별개의 두 타입이다."** 라는 생각이다. `List`는 "불변 리스트 클래스"이고 `MutableList`는 "가변 리스트 클래스"인 형제 관계로 나란히 존재한다고 상상하는 것이다. 실제로는 정반대이다. 두 타입은 형제가 아니라 **부모와 자식** 관계이다.

```kotlin
// stdlib의 실제 선언(요지)
public interface List<out E> : Collection<E> { /* 조회만 */ }
public interface MutableList<E> : List<E>, MutableCollection<E> { /* 조회 + 변경 */ }
//                                ^^^^^^^ MutableList는 List를 확장한다
```

선언에서 보듯 `MutableList<E> : List<E>`, 즉 `MutableList`는 `List`의 **하위 타입**이다. 모든 가변 리스트는 읽기 전용 리스트이기도 하며, 단지 더 많은 능력을 가졌을 뿐이다. 이 관계는 리스코프 치환 원칙과 정확히 맞아떨어진다. 가변 리스트는 읽기 전용 리스트가 할 수 있는 모든 일을 할 수 있으므로, `List`를 기대하는 곳이라면 어디든 `MutableList`를 넣을 수 있다.

```text
       List<out E>          ← 조회 능력만 (부모)
           △
           │  extends
           │
    MutableList<E>          ← 조회 + 변경 능력 (자식)

  ∴ MutableList<E> <: List<E>   (하위 타입)
  ∴ MutableList를 List 자리에 넣는 건 항상 안전 (능력만 좁아짐)
```

이 관계를 잘못 이해하면 "읽기 전용 리스트가 가변 리스트로 자동 변환될 것"이라고 기대하거나, 반대로 "두 타입은 서로 캐스트할 수 없는 별개 타입"이라고 오해하게 된다. 실제로는 상향 캐스트(`MutableList` → `List`)는 암시적으로 일어나고 항상 안전하다. 하향 캐스트(`List` → `MutableList`)는 명시적으로 해야 하고, 런타임 객체에 따라 성공하거나 실패한다(3.1절 반례 1).

### 4.2 가변성은 "객체의 성질"이 아니라 "참조의 능력"이다

이 절에서 얻어야 할 핵심은 다음과 같다. **가변성은 객체 자체에 고정된 성질이 아니라, 그 객체를 어떤 타입으로 참조하는지의 문제이다.** `ArrayList` 인스턴스 하나를 두 이름으로 참조할 때, 한 이름은 `MutableList`로, 다른 이름은 `List`로 볼 수 있다. 객체는 하나이지만 능력은 참조마다 다르다.

```kotlin
val arrayList = ArrayList<Int>()      // 타입: ArrayList<Int> (가변 구현)
arrayList.add(1); arrayList.add(2)

val asMutable: MutableList<Int> = arrayList   // 같은 객체, 가변 뷰
val asReadonly: List<Int> = arrayList         // 같은 객체, 읽기 전용 뷰

asMutable.add(3)          // OK
// asReadonly.add(3)      // 컴파일 에러: 능력 없음
println(asReadonly.size)  // => 3  (같은 객체라 변경이 보임)
```

세 참조(`arrayList`, `asMutable`, `asReadonly`)는 모두 힙에 있는 같은 `ArrayList` 객체를 가리킨다. 그 객체는 물리적으로 하나뿐이고 항상 가변이다. 달라지는 것은 그 객체를 어떤 타입을 통해 보느냐이다. `List` 타입으로 보면 변경 멤버가 사라지고, `MutableList` 타입으로 보면 변경 멤버가 나타난다. 이렇게 보면 3절의 오해와 이 절의 오해는 같은 원리로 설명된다. 읽기 전용은 객체의 상태가 아니라 참조의 권한이다.

```text
힙:   ┌─────────────────────────┐
      │  ArrayList 인스턴스       │  ← 물리적으로 하나, 항상 가변
      │  [1, 2, 3]               │
      └─────────────────────────┘
         △        △        △
         │        │        │
   arrayList  asMutable  asReadonly
   (가변)     (가변 렌즈) (읽기 전용 렌즈)
```

### 4.3 변성이 적용되는 방식

이제 `List<out E>`의 `out`이 왜 안전한지 분명해진다. `out E`는 `E`가 "출력(반환)" 위치에만 나타난다는 뜻이다(33장 제네릭 1). `List`에는 변경 멤버가 없으므로 `E`를 새로 *저장하는* 멤버(`add(e: E)` 같은)가 처음부터 없다. 그래서 공변이 성립한다.

엄밀히 말하면 `contains`/`indexOf`는 인자로 `E`를 받는 입력 위치 멤버이다. 하지만 값을 저장하지 않고 조회만 하므로, 표준 라이브러리는 이들을 `@UnsafeVariance`로 표시해 공변을 안전하게 허용한다.

```kotlin
open class Animal
class Cat : Animal()

val cats: List<Cat> = listOf(Cat(), Cat())
val animals: List<Animal> = cats     // OK! List<out E>라서 공변
// 안전한 이유: animals로 할 수 있는 건 Animal을 꺼내는 것뿐.
//             Cat 리스트에서 Animal을 꺼내는 건 항상 안전.
```

반면 `MutableList<E>`는 무공변이므로 이 대입이 허용되지 않는다.

```kotlin
val catsM: MutableList<Cat> = mutableListOf(Cat())
// val animalsM: MutableList<Animal> = catsM   // 컴파일 에러: 무공변
// 만약 허용됐다면: animalsM.add(Dog())  → Cat 리스트에 Dog가 섞임 (재앙)
```

즉 변경 멤버가 없다는 읽기 전용의 제약이 공변성이라는 유연성을 가능하게 한다. `MutableList`가 무공변인 것은 임의로 정한 규칙이 아니라 타입 안전을 위해 반드시 필요한 결과이다. "읽기 전용이면 공변이 가능하고, 가변이면 무공변이어야 한다"는 대칭은 변성 이론이 컬렉션에 적용되는 가장 깔끔한 사례이다. 이론은 33장에서, Java의 유명한 실수인 배열의 공변 문제와의 비교는 34장(제네릭 2)에서 다룬다.

> [!warning] 흔한 오해
> "`List`가 공변이니 `MutableList`도 `List`처럼 공변일 것"이라고 생각하기 쉽지만, 틀린 생각이다. 하위 타입인 `MutableList`는 상위 타입인 `List`보다 *능력이 많은* 대신 *변성은 더 엄격하다*. 능력과 변성은 반비례한다. 할 수 있는 일이 많은 타입일수록 치환할 수 있는 범위는 더 좁아진다.

## 5. 팩토리 함수와 구현체: 어떤 함수가 어떤 객체를 만드는가

### 5.1 읽기 전용 팩토리와 가변 팩토리

표준 라이브러리는 컬렉션 생성 함수를 두 종류로 제공한다. 이름에 `mutable`이 없으면 읽기 전용 인터페이스로 반환하고, 있으면 가변 인터페이스로 반환한다.

| 함수 | 반환 타입 | JVM 백엔드의 대략적 실체 |
|---|---|---|
| `emptyList<T>()` | `List<T>` | `EmptyList` 싱글턴 (상태 없음) |
| `listOf(a, b, c)` | `List<T>` | 배열 기반 고정 크기 뷰 |
| `listOf(a)` | `List<T>` | 단일 원소 리스트 |
| `mutableListOf(a, b)` | `MutableList<T>` | `java.util.ArrayList` |
| `arrayListOf(a, b)` | `ArrayList<T>` | `java.util.ArrayList` |
| `buildList { … }` | `List<T>` | 빌더로 채운 뒤 읽기 전용으로 반환 |
| `emptySet()` / `setOf(…)` | `Set<T>` | 빈 싱글턴 / `LinkedHashSet` |
| `mutableSetOf(…)` | `MutableSet<T>` | `LinkedHashSet` (삽입 순서 유지) |
| `hashSetOf(…)` | `HashSet<T>` | `java.util.HashSet` (순서 없음) |
| `emptyMap()` / `mapOf(…)` | `Map<K,V>` | 빈 싱글턴 / `LinkedHashMap` |
| `mutableMapOf(…)` | `MutableMap<K,V>` | `LinkedHashMap` |
| `hashMapOf(…)` | `HashMap<K,V>` | `java.util.HashMap` |

이 표에서 눈여겨볼 점이 두 가지 있다. 첫째, `mutableSetOf`/`mutableMapOf`는 JVM 백엔드에서 `LinkedHashSet`/`LinkedHashMap`을 반환한다. 즉 **삽입 순서가 유지된다**. 이것은 코틀린이 명시적으로 보장하는 유용한 특성이며, 순서가 없는 `HashSet`이 필요하면 `hashSetOf`를 명시해야 한다.

둘째, `arrayListOf`/`hashSetOf`/`hashMapOf`는 반환 타입이 구체 클래스(`ArrayList` 등)이므로 더 넓은 API를 노출한다. 하지만 구현을 바꿀 수 있는 유연성을 위해 대개는 인터페이스 타입으로 받는 것이 좋다.

### 5.2 `buildList`: 가변으로 만들고 읽기 전용으로 반환한다

코틀린 1.6부터 안정화된 빌더 함수 `buildList`/`buildSet`/`buildMap`은 "가변으로 편하게 만든 뒤 읽기 전용으로 내보내는" 관용구이다.

```kotlin
val result: List<Int> = buildList {
    add(1)              // 이 람다의 수신자는 MutableList
    add(2)
    if (someCondition()) add(3)
    addAll(listOf(4, 5))
}
// result의 정적 타입은 List<Int> (읽기 전용)
```

`buildList`에 넘긴 람다는 수신자가 `MutableList`이므로 그 안에서는 자유롭게 변경할 수 있다. 함수가 끝나면 결과를 `List`로 반환한다. 이것은 [[16 - 스코프 함수와 수신 객체 관용구]]와 37장(타입 안전 빌더와 DSL)에서 본 수신 객체 지정 람다 패턴을 컬렉션 생성에 적용한 예이다. "만드는 동안에는 가변이고, 완성되면 읽기 전용"이라는 흐름을 타입으로 표현한다.

> [!caution] 성능 주의
> `buildList`는 내부적으로 가변 리스트를 만들어 채운 뒤 반환한다. 반환된 리스트를 나중에 `MutableList`로 캐스트해 변경하면, 구현에 따라 예외가 발생하거나 정의되지 않은 동작이 일어날 수 있으므로 이렇게 해서는 안 된다. `buildList`가 약속하는 것은 "읽기 전용 결과"이지 "특정 가변 구현"이 아니다.

### 5.3 복사 함수: `toList`, `toMutableList`, `toSet`

컬렉션을 다른 종류로 바꾸거나 스냅샷을 만들 때는 `to*` 계열 함수를 쓴다. 이 함수들은 별칭을 만드는 것이 아니라 **새 컬렉션을 만든다**(복사).

```kotlin
val src = mutableListOf(1, 2, 3)

val snapshot: List<Int> = src.toList()          // 얕은 복사, 읽기 전용
val copyMut: MutableList<Int> = src.toMutableList()  // 얕은 복사, 가변

src.add(4)
println(snapshot)   // => [1, 2, 3]   (복사본이라 영향 없음)
println(copyMut)    // => [1, 2, 3]   (별도 객체)
```

`toList`는 3절에서 본 별칭과 뷰의 함정을 막는 가장 흔한 도구이다. `src.toList()`는 현재 요소를 새 읽기 전용 리스트로 복사하므로, 이후 `src`가 바뀌어도 `snapshot`은 복사한 시점의 값을 유지한다. 다만 **얕은 복사**라는 점에 유의해야 한다. 요소 객체 자체는 공유되므로, `Counter` 같은 가변 요소를 한쪽에서 바꾸면 양쪽에서 모두 보인다. 이것은 [[27 - 데이터 클래스]]의 `copy`가 얕은 복사인 것과 같은 층위의 주의 사항이다.

```text
snapshot = src.toList()  후:

  snapshot ──▶ [ref0, ref1, ref2]  ← 새 리스트 컨테이너
                  │     │     │
  src ─────▶ [ref0, ref1, ref2, ref3]  ← 별도 컨테이너
                  │     │     │
                  ▼     ▼     ▼
              (요소 객체들은 공유됨 — 얕은 복사)
```

## 6. Set과 Map: 유일성과 대응, 그리고 Map이 컬렉션이 아닌 이유

### 6.1 Set의 계약: 멤버는 같아도 의미가 다르다

`Set<out E>` 인터페이스가 노출하는 멤버는 `Collection<E>`와 거의 같다. `List`처럼 인덱스 접근(`get`)을 추가하지도 않는다. 그렇다면 `Set`은 `Collection`과 무엇이 다를까? 바로 **원소 유일성**이라는 계약이다.

```kotlin
val s: Set<Int> = setOf(1, 2, 2, 3, 3, 3)
println(s)          // => [1, 2, 3]   (중복 제거)
println(s.size)     // => 3
```

`setOf`는 중복을 자동으로 걸러 낸다. 이 유일성은 `equals`/`hashCode`를 기준으로 판단한다([[10 - 불리언과 동등성과 동일성]]). 두 원소가 `equals`로 같고 `hashCode`도 같으면 같은 원소로 취급한다. 따라서 `equals`/`hashCode` 계약을 어긴 요소를 `Set`에 넣으면 유일성이 깨진다.

```kotlin
// hashCode/equals를 오버라이드하지 않은 클래스
class Point(val x: Int, val y: Int)

val points = setOf(Point(1, 2), Point(1, 2))   // "같은" 좌표 둘
println(points.size)   // => 2  (기본 equals는 참조 동일성 → 다른 객체로 봄)
```

`Point`가 `equals`를 오버라이드하지 않으면 기본 참조 동일성(`===` 수준)이 쓰이므로, 두 `Point(1,2)`는 서로 다른 원소로 남는다. `data class Point(val x: Int, val y: Int)`로 바꿔 구조적 `equals`를 자동으로 생성하면(27장 데이터 클래스) 유일성이 기대한 대로 동작한다. 이처럼 Set의 유일성은 요소의 `equals`/`hashCode` 계약에 의존하므로, 10장과 27장의 내용이 이 장과 연결된다.

`mutableSetOf`는 `LinkedHashSet`을 반환하므로 삽입 순서가 유지되지만, `Set`은 원칙적으로 **순서를 계약하지 않는다**. `hashSetOf`로 만든 집합은 순회 순서가 삽입 순서와 관계없다. 순서에 의존하는 코드라면 `List`를 쓰거나 정렬된 집합을 명시해야 한다.

### 6.2 Set의 동등성: 순서와 무관하다

`List`의 `equals`는 순서를 따지지만, `Set`의 `equals`는 순서를 따지지 않는다. 원소 집합이 같으면 삽입 순서가 달라도 같다고 판단한다.

```kotlin
val a = setOf(1, 2, 3)
val b = setOf(3, 2, 1)
println(a == b)     // => true   (집합은 순서 무관)

val la = listOf(1, 2, 3)
val lb = listOf(3, 2, 1)
println(la == lb)   // => false  (리스트는 순서 유의미)
```

이 차이는 각 자료구조의 수학적 의미를 그대로 반영한다. 집합 $\{1,2,3\}$과 $\{3,2,1\}$은 같은 집합이지만, 순서열 $(1,2,3)$과 $(3,2,1)$은 다른 순서열이다.

### 6.3 Map이 Collection이 아닌 이유

2.1절의 계층 구조에서 `Map<K, out V>`는 `Collection` 밖에 따로 떨어져 있다. `Map`은 `Iterable`도 `Collection`도 확장하지 않는다. 그 이유는 개념에 있다. **Map은 원소의 모음이 아니라 키에서 값으로의 대응(mapping)이다.** "Map의 원소"가 무엇인지도 모호하다. 키인지, 값인지, 아니면 키-값 쌍인지 정하기 어렵다. Java도 같은 이유로 `Map`을 `Collection` 밖에 두었다.

그 대신 Map은 **세 가지 컬렉션 뷰**를 제공한다.

```kotlin
val m: Map<String, Int> = mapOf("a" to 1, "b" to 2, "c" to 3)

m.keys      // Set<String>            → [a, b, c]
m.values    // Collection<Int>        → [1, 2, 3]
m.entries   // Set<Map.Entry<String, Int>>
```

키는 유일하므로 `keys`는 `Set`이고, 값은 중복될 수 있으므로 `values`는 `Collection`이다. `entries`는 키-값 쌍의 `Set`이다. Map은 이 뷰들을 통해서만 컬렉션과 연결된다. `for` 순회도 `entries`를 거친다.

```kotlin
for ((key, value) in m) {          // Map.Entry의 구조 분해
    println("$key -> $value")
}
// a -> 1
// b -> 2
// c -> 3
```

`(key, value)` 구조 분해가 동작하는 것은 `Map.Entry`에 `component1()`(키)과 `component2()`(값) 확장이 정의되어 있기 때문이다([[20 - 구조 분해]]). 그리고 `to`는 특별한 문법이 아니라 `Pair`를 만드는 중위(infix) 확장 함수이다.

```kotlin
public infix fun <A, B> A.to(that: B): Pair<A, B> = Pair(this, that)
// "a" to 1  ≡  "a".to(1)  ≡  Pair("a", 1)
```

즉 `mapOf("a" to 1)`은 `mapOf(Pair("a", 1))`과 같다. `mapOf`는 `Pair`를 vararg로 받아 맵을 만든다. 사소해 보이지만, 이 사실은 `to`가 언어 키워드가 아니라 평범한 확장 함수라는 것을 보여 준다. 또한 [[35 - 확장 함수와 프로퍼티]]와 19장(연산자 오버로딩과 관례)에서 다룬 관용구가 표준 라이브러리 곳곳에 쓰이고 있다는 것도 알 수 있다.

### 6.4 Map의 가변 뷰와 원격 변경

`MutableMap`의 `entries`, `keys`, `values`도 뷰이므로 3절에서 본 함정이 그대로 나타난다. `MutableMap.MutableEntry.setValue`로 값을 바꾸면 원본 맵이 바뀐다.

```kotlin
val mm: MutableMap<String, Int> = mutableMapOf("a" to 1, "b" to 2)
for (entry in mm.entries) {
    entry.setValue(entry.value * 10)   // 뷰를 통해 원본 변경
}
println(mm)     // => {a=10, b=20}
```

`entries`는 별도의 스냅샷이 아니라 맵을 들여다보는 창이므로, `setValue`는 그 뒤에 있는 맵을 바꾼다. 6.3절의 읽기 전용 `Map` 뷰가 안전해 보여도 실제로는 그 뒤에 가변 맵이 있을 수 있다. 읽기 전용이 불변이 아니라는 3절의 결론이 Map에서도 똑같이 성립한다.

## 7. 배열은 컬렉션이 아니다

### 7.1 흔한 오해: `Array<T>`는 `List`가 아니다

세 번째로 흔한 오해는 **"코틀린 배열은 리스트다"** 또는 "`Array<T>`는 `Collection`의 일종이다"라는 생각이다. 이것은 완전히 틀렸다. `Array<T>`는 코틀린 컬렉션 계층(2.1절)과 **완전히 분리된 별개의 클래스**이다. `Array<T>`는 `Iterable`도, `Collection`도, `List`도 구현하지 않는다.

```kotlin
val arr: Array<Int> = arrayOf(1, 2, 3)
// val asList: List<Int> = arr    // 컴파일 에러: Array는 List가 아님
// arr.add(4)                     // 컴파일 에러: add 없음
// arr.contains(2)  ← 이건 됨! (확장 함수라서, 아래 설명)

val fromArr: List<Int> = arr.toList()   // 명시적 변환이 필요
```

배열은 `List`로 자동 취급되지 않는다. `List`가 필요한 자리에 `arr`를 바로 넣을 수 없고, `toList()`로 변환해야 한다. 반대로 `List`도 `Array`가 아니므로 `toTypedArray()`로 변환해야 한다.

### 7.2 배열이 컬렉션처럼 보이는 이유

혼란이 생기는 이유는 배열이 컬렉션 메서드를 *가진 것처럼* 보이기 때문이다. `arr.map { }`, `arr.filter { }`, `arr.contains(2)`, `for (x in arr)`가 모두 동작한다. 하지만 이것은 배열이 컬렉션 계층에 속하기 때문이 아니라 **확장 함수**(35장 확장 함수와 프로퍼티) 덕분이다.

```kotlin
// stdlib엔 Array를 위한 확장이 방대하게 정의돼 있다 (Iterable용과 별개로)
public inline fun <T, R> Array<out T>.map(transform: (T) -> R): List<R> { … }
public inline fun <T> Array<out T>.filter(predicate: (T) -> Boolean): List<T> { … }
public operator fun <T> Array<out T>.contains(element: T): Boolean { … }
```

표준 라이브러리는 `Iterable`용 함수와 **똑같은 이름의 확장을 `Array`용으로 따로** 제공한다. 그래서 겉으로 보이는 API는 비슷하지만, 둘은 상속 관계가 아니라 나란히 따로 정의된 확장 집합이다. `for (x in arr)`가 동작하는 것도 `Array`에 `operator fun iterator()`가 멤버로 있기 때문이지, `Array`가 `Iterable`이기 때문이 아니다.

```text
      Iterable<out T>          Array<T>
          │                       │
     Collection                 (독립 클래스, 계층 밖)
          │                       │
       List, Set                iterator()는 멤버 operator
          │                       │
   map/filter는 Iterable 확장   map/filter는 Array 확장 (별도 복제)
          │                       │
          └── 겉보기 API는 닮았지만 타입 계층은 무관 ──┘
```

이 구조를 모르면 "배열을 `List`를 받는 함수에 넘기면 되겠지"라고 착각하게 된다. 하지만 타입 계층이 다르므로 그렇게 할 수 없다.

### 7.3 `Array<T>`의 물리적 성질: 크기는 고정, 요소는 가변

코틀린에서 `Array<T>`는 **크기가 고정되어 있고 요소는 바꿀 수 있는** 자료구조이다. 크기는 생성할 때 정해지며 바꿀 수 없지만(add/remove 없음), 각 인덱스의 요소는 바꿀 수 있다.

```kotlin
val arr = arrayOf(1, 2, 3)
arr[0] = 99          // 요소 변경 OK (Array.set 관례)
println(arr[0])      // => 99
println(arr.size)    // => 3  (크기는 프로퍼티, 불변)
// arr.size = 5      // 불가: 크기 변경 수단 없음
```

`arr[0] = 99`는 `Array`의 `operator fun set` 관례로 동작한다. 흥미롭게도 `Array<T>`는 `MutableList`처럼 무공변이다. 요소 대입(set)이 있으므로 공변이면 타입 안전이 깨지기 때문이다. Java 배열은 공변이고, 그 때문에 런타임에 `ArrayStoreException`이 발생할 수 있다. 반면 코틀린 `Array<T>`는 무공변이어서 이 함정을 컴파일 타임에 막는다. 이 비교는 34장(제네릭 2)에서 자세히 다룬다.

> [!note] 명세 기준
> JVM 백엔드에서 `Array<T>`는 JVM 참조 배열(`T[]`, 예: `Integer[]`, `String[]`)로 컴파일된다. 그래서 `Array<Int>`의 요소는 박싱된 `Integer`가 된다. 이 점이 다음 절에서 다룰 원시 배열과의 결정적인 차이이다.

### 7.4 원시 배열: `IntArray`는 `Array<Int>`가 아니다

배열에 관한 오해에는 두 번째 층위도 있다. **원시 배열은 `Array<T>`와도 다른 별개의 타입이다.**

코틀린에는 `IntArray`, `LongArray`, `DoubleArray`, `FloatArray`, `ShortArray`, `ByteArray`, `CharArray`, `BooleanArray`라는 특수 배열 클래스가 있다. 이들은 JVM 백엔드에서 원시 배열(`int[]`, `long[]` 등)로 컴파일되므로 **박싱을 피한다**([[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]).

```kotlin
val boxed: Array<Int> = arrayOf(1, 2, 3)       // JVM: Integer[] (박싱)
val primitive: IntArray = intArrayOf(1, 2, 3)  // JVM: int[] (박싱 없음)

// val x: Array<Int> = primitive   // 컴파일 에러: IntArray ≠ Array<Int>
val converted: Array<Int> = primitive.toTypedArray()   // 명시 변환(박싱 발생)
val back: IntArray = boxed.toIntArray()                // 반대 변환(언박싱)
```

`IntArray`와 `Array<Int>`는 서로 자동으로 변환되지 않는 별개의 타입이다. 이 구분은 성능 면에서 중요하다. 수치 연산에서 `IntArray`는 `int[]`이므로 캐시 지역성과 언박싱의 이점이 크다. 반면 `Array<Int>`는 `Integer[]`이므로, 각 요소가 힙에 있는 박스 객체를 가리키는 포인터 배열이다.

```text
IntArray(3) [1, 2, 3]  ── JVM int[] ──▶  연속 메모리: [ 1 | 2 | 3 ]  (박싱 없음)

Array<Int>(3) [1, 2, 3] ── JVM Integer[] ──▶ [ ref | ref | ref ]
                                                 │     │     │
                                                 ▼     ▼     ▼
                                              Integer Integer Integer  (힙의 박스)
```

세 층위를 정리하면 배열에 관한 전체 그림은 다음과 같다.

| 타입 | 계층 | JVM 실체 | 크기 | 요소 |
|---|---|---|---|---|
| `List<E>` | 컬렉션 계층 | 대개 `java.util.List` 계열 | 구현마다 | 참조(박싱) |
| `Array<T>` | 계층 밖 독립 클래스 | `T[]` (참조 배열) | 고정 | 박싱 |
| `IntArray` 등 | 계층 밖, 별도 | `int[]` (원시 배열) | 고정 | 원시(무박싱) |

이 셋은 서로 자동으로 변환되지 않으며, 각자 다른 계약과 성능 특성을 가진다. "코틀린 배열은 리스트다"라는 한 문장의 오해는 이 세 층위의 구분을 모두 흐려 버린다.

> [!caution] 성능 주의
> 자주 실행되는 수치 루프(hot loop)에서 `List<Int>`나 `Array<Int>`를 쓰면 박싱 비용이 누적된다. 이런 경우에는 `IntArray`가 더 나은 선택일 때가 많다. 반대로 대부분의 일반 코드에서는 `List`의 유연성(크기 가변, 풍부한 API, 공변)이 원시 배열의 성능 이점보다 훨씬 크다. "배열이 빠르다"는 통념은 원시 배열에 한해서, 그리고 요소 접근이 성능 병목일 때만 맞는 말이다.

## 8. 진짜 불변이 필요할 때: 방어적 복사에서 영속 컬렉션까지

### 8.1 세 가지 방어 수준

3~4절에서 읽기 전용이 불변이 아니라는 것을 확인했다. 그렇다면 실무에서는 진짜 불변성이 필요할 때 무엇을 써야 하는지가 문제가 된다. 방어 수준은 세 단계로 나눌 수 있다.

**수준 1: 방어적 복사(defensive copy).** 외부에서 받은 컬렉션을 그대로 보관하지 말고, `toList()`로 스냅샷을 만들어 별칭 관계를 끊는다.

```kotlin
class Playlist(songs: List<String>) {
    // 받은 리스트가 나중에 외부에서 바뀔 수 있으므로 복사해서 보관
    private val songs: List<String> = songs.toList()

    fun titles(): List<String> = songs.toList()   // 내보낼 때도 복사(선택)
}
```

`songs.toList()`가 없으면, 생성자에 넘긴 리스트가 `MutableList`였을 경우 나중에 외부에서 변경될 때 `Playlist`의 내부 상태도 모르는 사이에 바뀐다. 이것은 3절과 4절에서 본 문제를 실무에서 막는 가장 기본적이고 흔한 패턴이다. 다만 얕은 복사이므로, 요소가 가변이면 요소는 여전히 공유된다는 점을 기억해야 한다(5.3절).

**수준 2: 변경 불가 래퍼.** JVM에서는 `java.util.Collections.unmodifiableList` 같은 래퍼로 감싸면, 변경을 시도할 때 런타임에 `UnsupportedOperationException`을 던지는 뷰를 얻는다. 하지만 이 방법으로는 별칭 문제를 완전히 해결하지 못한다. 원본이 바뀌면 래퍼를 통해서도 바뀐 내용이 보이기 때문이다. 또한 코틀린 `List`에는 처음부터 변경 멤버가 없으므로, 이 래퍼는 주로 Java와의 경계에서만 의미가 있다.

**수준 3: 영속(persistent) 컬렉션.** 진짜 불변 자료구조가 필요하면 `kotlinx.collections.immutable` 라이브러리의 `PersistentList`/`PersistentSet`/`PersistentMap`을 쓴다. 이들은 표준 라이브러리 밖의 별도 의존성이며, 변경 연산은 원본을 건드리지 않고 **구조를 공유하는 새 버전**을 반환한다.

```kotlin
// kotlinx.collections.immutable (별도 라이브러리)
import kotlinx.collections.immutable.persistentListOf

val a = persistentListOf(1, 2, 3)
val b = a.add(4)         // a는 그대로, b는 새 리스트
println(a)               // => [1, 2, 3]   (원본 불변)
println(b)               // => [1, 2, 3, 4]
```

`ImmutableList` 인터페이스는 "변경되지 않는다"는 것을 **계약으로 보장**한다. 이 점에서 변경 멤버가 없을 뿐인 표준 `List`와 근본적으로 다르다. `PersistentList.add`는 전체를 복사하지 않고, 구조 공유(structural sharing)를 이용해 새 버전을 효율적으로 만든다.

### 8.2 표준 List와 영속 List의 개념적 차이

| 성질 | `List` (stdlib) | `PersistentList` (kotlinx) |
|---|---|---|
| 변경 멤버 | 없음(읽기 전용 인터페이스) | 없음, 대신 `add`가 *새 인스턴스* 반환 |
| 별칭 안전성 | 없음 (뒤 객체가 가변일 수 있음) | 있음 (진짜 불변) |
| 캐스트로 변경 | 가능할 수 있음 (구현 따라) | 불가능 (변경 API 자체가 없음) |
| 변경 시 비용 | 해당 없음 | 구조 공유로 효율적 |
| 표준 포함 여부 | stdlib 기본 | 별도 라이브러리 |

핵심은 이렇다. 표준 `List`는 "이 참조로는 바꿀 수 없다"는 뜻이고, `PersistentList`는 "이 객체는 바뀌지 않는다"는 뜻이다. 전자는 능력의 제한이고, 후자는 자료구조 자체의 성질이다. 동시성([[43 - 동시성과 메모리 모델]])에서는 진짜 불변성이 별도의 비용 없이 스레드 안전을 보장하므로, 공유 상태를 다룰 때 영속 컬렉션의 가치가 두드러진다.

> [!info] 역사 메모
> `kotlinx.collections.immutable`은 오랫동안 실험/프리릴리스 상태였고, 코틀린 팀은 이 기능을 표준 라이브러리에 넣을지 논의해 왔다. 표준에 넣지 않고 별도 라이브러리로 둔 것은 1.3절에서 본 "점진성" 설계 철학을 이어 간 결과이다. 모두에게 강제하기보다 필요한 사람이 선택하게 한 것이다.

### 8.3 관용구 정리: 어떤 도구를 언제 쓰는가

```text
"함수 파라미터로 컬렉션 받기"        → List/Set/Map (읽기 전용 인터페이스로)
"함수 안에서 컬렉션 변경 필요"        → 내부에서 toMutableList()로 복사 후 작업
"필드에 외부 컬렉션 저장"            → 생성자에서 toList()로 방어적 복사
"컬렉션을 짓고 읽기 전용으로 반환"    → buildList { }
"현재 상태 스냅샷"                  → toList()
"진짜 불변 + 스레드 안전"           → kotlinx PersistentList
"수치 성능 극한"                   → IntArray 등 원시 배열
```

이 관용구들은 모두 "읽기 전용은 의도를 표현할 뿐, 불변을 보장하지 않는다"는 원칙에서 나온다. 인터페이스로 의도를 좁히되, 안전이 실제로 필요한 지점에서는 복사나 영속 구조로 보강하는 것이다.

## 9. Java 상호운용과 플랫폼 컬렉션

### 9.1 매핑된 타입: 코틀린 List와 java.util.List의 이중성

JVM 백엔드에서 코틀린의 `kotlin.collections.List`는 Java의 `java.util.List`와 **매핑된 타입**으로 연결된다. 소스 수준에서 코틀린은 자신의 인터페이스를 보지만, 바이트코드 수준에서는 `java.util.List`가 된다. 이 이중성 덕분에 Java 라이브러리와 컬렉션을 복사 없이 주고받을 수 있다.

```text
소스(코틀린)         바이트코드(JVM)
List<E>       ──▶   java.util.List
MutableList<E> ──▶  java.util.List   ← 둘 다 같은 Java 타입으로!
```

여기에는 흥미로운 비대칭이 있다. 코틀린의 `List`와 `MutableList`는 서로 다른 코틀린 인터페이스이지만, **JVM에서는 둘 다 `java.util.List`로 지워진다.** Java에는 읽기 전용과 가변의 구분이 없기 때문이다. 이 사실은 3.1절 반례 1(캐스팅으로 변경하기)이 가능한 근본 원인이기도 하다. 런타임에는 두 타입 사이의 경계가 없다.

### 9.2 플랫폼 컬렉션 타입: `(Mutable)List!`

Java 메서드가 컬렉션을 반환하면, 코틀린은 그 컬렉션의 널 가능성과 가변성을 알 수 없다. Java의 `List<String>`은 null일 수도 있고, 가변일 수도, 읽기 전용일 수도 있다(Java 타입에는 이 정보가 없다). 그래서 코틀린은 이를 **플랫폼 타입**으로 취급한다(6장 널 안전성). 컬렉션은 `(Mutable)List<String!>!` 같은 형태로 표기된다.

```java
// Java
public class Library {
    public List<String> getBooks() { … }   // null? 가변? 알 수 없음
}
```

```kotlin
// Kotlin에서 호출
val books = Library().books   // 타입: (Mutable)List<String!>!
// 코틀린은 이를 List로도 MutableList로도 받을 수 있게 유연하게 취급
val ro: List<String> = Library().books        // OK
val mut: MutableList<String> = Library().books // OK (하지만 위험할 수 있음)
```

이 유연성은 편리하지만 위험하다. Java가 반환한 것이 실제로는 `Collections.unmodifiableList`였다면, 코틀린에서 `MutableList`로 받아 `add`를 호출하는 순간 런타임에 `UnsupportedOperationException`이 발생한다. 플랫폼 타입이라 가변성 판단이 뒤로 미뤄졌기 때문에, 컴파일러는 이를 막지 못한다.

방어책은 두 가지이다. 하나는 Java 경계에서 받은 컬렉션을 명시적으로 `List`(읽기 전용) 타입으로 지정해, 변경 시도를 컴파일 타임에 막는 것이다. 다른 하나는 `toList()`로 복사해 직접 관리하는 것이다.

> [!warning] 흔한 오해
> "Java에서 받은 리스트를 `MutableList`로 받을 수 있으니 가변일 것"이라고 믿고 변경했다가 런타임 예외를 만나기 쉽다. 플랫폼 타입의 가변성은 *약속이 아니라 판단을 미룬 것*이다. 코틀린은 "원하는 타입으로 받게 해 주겠지만, 그 타입이 맞는지는 개발자가 책임져야 한다"고 말할 뿐이다.

### 9.3 코틀린 컬렉션을 Java에 노출할 때

반대 방향에도 비슷한 함정이 있다. 코틀린에서 `List<String>`(읽기 전용)을 반환하는 함수를 Java에서 호출하면, Java는 그 값을 `java.util.List`로 보고 `add`를 호출할 수 있다. Java에는 읽기 전용 개념이 없으므로 컴파일 에러도 나지 않는다. 실제 객체가 고정 크기 뷰였다면 런타임에 예외가 발생한다.

```kotlin
// Kotlin
fun titles(): List<String> = listOf("a", "b")   // 읽기 전용 의도
```

```java
// Java — 컴파일러가 못 막음
List<String> t = KotlinFileKt.titles();
t.add("c");   // 런타임: UnsupportedOperationException 가능
```

즉 코틀린의 읽기 전용 계약은 코틀린 컴파일러 안에서만 강제되고, Java 상호운용 경계를 넘으면 그 보장이 사라진다. Java에서도 진짜 불변을 강제하려면 8절의 영속 컬렉션이나 명시적인 `unmodifiable` 래퍼가 필요하다. 상호운용의 함정 전반은 [[45 - Java 상호운용]]에서 정리한다.

### 9.4 널 원소와 컬렉션

컬렉션은 null 원소를 담을 수 있다. `List<Int?>`와 `List<Int>`는 다른 타입이다. 전자는 null을 요소로 허용하고, 후자는 허용하지 않는다.

```kotlin
val withNulls: List<Int?> = listOf(1, null, 3)
val noNulls: List<Int> = withNulls.filterNotNull()  // null 제거 → List<Int>
println(noNulls)    // => [1, 3]

val map: Map<String, Int?> = mapOf("a" to 1, "b" to null)
map["b"]            // => null  (값이 null)
map["z"]            // => null  (키가 없어도 null)
```

`Map`을 조회할 때는 특히 주의해야 한다. `map["z"]`가 null을 반환했을 때, 그것이 "키가 없음"인지 "값이 null임"인지 구별할 수 없다. 이 모호성을 없애려면 `containsKey`를 써야 한다.

`Map<K, V?>`에서 `get`은 `V?`를 반환하므로, 값이 null일 수 있는 맵에서는 이 구분이 실제 버그의 원인이 된다. 6장(널 안전성)에서 본 안전 호출과 엘비스 연산자도 여기서 유용하지만, 키가 존재하는지 검사할 때는 `containsKey`를 쓰는 것이 정확하다.
