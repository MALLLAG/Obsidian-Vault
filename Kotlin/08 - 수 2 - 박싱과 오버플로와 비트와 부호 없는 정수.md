앞의 [[07 - 수 1 - Int와 Long과 부동소수점]]에서는 Kotlin의 정수 타입과 부동소수 타입이 무엇인지, 왜 암시적 확대 변환이 없는지(`Int`를 `Long` 자리에 그냥 넣을 수 없다), 리터럴의 타입이 어떻게 추론되는지를 살펴보았다.

그 장의 마지막 내용은 "Kotlin에는 원시 타입이 없다"는 오해를 바로잡는 것이었다. 소스 코드에는 `int`도 `double`도 없고 클래스 `Int`와 `Double`만 있지만, JVM 백엔드는 가능한 곳에서 이들을 실제 원시형 `int`, `double`로 컴파일한다. 이 장에서는 이 문장의 "가능한 곳에서"라는 단서를 자세히 살펴본다.

"가능하지 않은 곳"이 있기 때문이다. 널을 담아야 할 때, 제네릭 타입 인자가 되어야 할 때, `Any`로 취급되어야 할 때 Kotlin의 수는 다시 객체, 즉 **박스(box)** 로 감싸진다. 이 장에서는 먼저 박싱과 언박싱이 일어나는 경계를 정확히 정리한다. 그리고 JVM은 성능을 위해 박스에 캐시를 두는데, 이 캐시 때문에 `===`(참조 동일성)의 결과를 예측하기 어려워진다. 이 함정 자체는 [[10 - 불리언과 동등성과 동일성]]에서 다루고, 여기서는 그 원인인 박싱을 살펴본다.

수가 기계 위에서 유한한 비트 패턴이라는 사실에서 두 가지 결과가 더 나온다. 하나는 **오버플로**이다. 유한한 비트가 넘칠 때 Kotlin은 예외를 던지지 않고 조용히 래핑(wrap)한다. 다른 하나는 비트 패턴을 직접 조작하는 **비트 연산**과, 부호 비트의 해석을 바꾸는 **부호 없는 정수**이다.

부호 없는 정수는 Kotlin이 `value class`를 이용해 "박싱 없는 새 수 타입"을 사용자 코드 수준에서 어떻게 만들었는지 보여 주는 실제 사례이다(이 기법은 [[36 - 타입 별칭과 인라인 value class]]에서 다룬다). 마지막으로 수의 컬렉션인 **배열**을 살펴본다. `IntArray`는 원시 배열이고 `Array<Int>`는 박스 배열이며, 둘 다 `List`가 아니다.

리터럴 문법과 확대 변환, 정수 나눗셈의 기본은 07장(Int와 Long과 부동소수점)에서, `==`와 `===`의 의미와 `equals`/`hashCode` 계약은 10장(불리언과 동등성과 동일성)에서, `value class`의 일반 이론과 박싱 예외의 전체 표는 36장(타입 별칭과 인라인 value class)에서 다룬다. 배열의 공변 함정과 타입 소거, 읽기 전용 컬렉션과 배열의 차이도 뒤의 장으로 미루고, 이 장은 수가 비트로 존재할 때 생기는 현상에 집중한다.

## 1. 클래스이면서 원시형인 수

### 1.1 소스에서는 클래스, 기계에서는 원시형

Kotlin 소스에서 `Int`, `Long`, `Double`, `Boolean`은 모두 **클래스**이다. `5`는 `Int` 클래스의 인스턴스이고, 여기에 `5.toLong()`, `5.coerceAtLeast(0)`, `5.and(3)` 같은 메서드를 호출할 수 있다. Java의 `int`처럼 "메서드가 없는 원시 값"이 아니다. 07장(Int와 Long과 부동소수점)에서 바로잡은 내용도 이것이었다. **소스 수준에서 Kotlin의 수는 완전한 객체이다.**

하지만 JVM에서 이 "객체"를 매번 힙에 할당한 실제 객체로 만든다면, 정수 하나를 더할 때마다 메모리 할당과 포인터 추적이 일어나 성능이 크게 떨어진다. 그래서 K2 컴파일러의 JVM 백엔드는 다음 방법을 쓴다. **원시형으로 표현할 수 있는 곳에서는 원시형으로 컴파일하고, 참조가 필요한 곳에서만 박스로 감싼다.**

```kotlin
val a: Int = 5            // JVM 백엔드: 원시 int
val b: Int = a + 1        // 원시 int 산술 (iadd 바이트코드)
```

```java
// 위 Kotlin이 JVM 백엔드에서 개념적으로 대응하는 Java
int a = 5;
int b = a + 1;   // 힙 할당 없음, 스택 위의 int
```

> [!note] 명세 기준
> "원시형으로 컴파일된다"는 설명은 **JVM 백엔드에만** 해당한다. Kotlin/Native는 LLVM IR 위의 값 표현을, Kotlin/JS는 자바스크립트 `number`(`Long`은 특수 표현)를, Kotlin/Wasm은 Wasm 수치 타입을 사용한다. 세 백엔드 모두 "박싱"의 세부 동작이 다르다. 이 장에서 설명하는 박싱은 따로 언급하지 않는 한 JVM 백엔드를 기준으로 한다. 언어 명세가 보장하는 것은 *의미*(값의 동등성, 산술 결과)이지 *표현*이 아니다.

### 1.2 이 이중성이 좋은 언어 설계인 이유

Java는 이 문제를 언어 수준에서 드러낸다. Java 개발자는 `int`(원시)와 `Integer`(래퍼)를 직접 구별해야 하고, `List<int>`는 쓸 수 없고 `List<Integer>`만 쓸 수 있다는 규칙을 외워야 한다. Kotlin은 이 구별을 **타입 시스템에서 없애고 컴파일러가 처리하게 했다.** 개발자는 항상 `Int` 하나만 쓰고, 박스로 만들지 원시형으로 둘지는 컴파일러가 문맥을 보고 결정한다.

이 설계의 대가는 하나뿐이다. 개발자가 언제 박스로 감싸지는지를 *모르면* 성능과 동일성(`===`) 판정에서 함정에 빠진다. 그래서 이 장에서 가장 중요한 지식이 바로 이것이다. 결론부터 정리하면 다음과 같다.

```text
Int가 원시 int로 남는 경우            Int가 Integer 박스로 감싸지는 경우
─────────────────────────           ──────────────────────────────
지역 변수 val x: Int = 5             널 가능 타입 Int?  (널을 담으려면 참조 필요)
원시 산술 x + y, x * y               제네릭 타입 인자 List<Int>, T = Int
함수 인자/반환 fun f(n: Int)         Any/Comparable 등 상위 타입으로 상향변환
IntArray의 원소                     Array<Int>의 원소
```

이 장에서는 이 표의 오른쪽 열을 하나씩 살펴본다.

## 2. 박싱과 언박싱: 박스는 언제 만들어지는가

### 2.1 박싱의 정의

**박싱(boxing)** 은 원시 값을 힙에 할당한 객체로 감싸는 것이다. JVM 백엔드에서 `Int`의 박스는 `java.lang.Integer`, `Long`의 박스는 `java.lang.Long`, `Double`의 박스는 `java.lang.Double`이다. **언박싱(unboxing)** 은 그 반대로, 박스에서 원시 값을 꺼내는 것이다.

박싱이 필요한 근본 이유는 하나이다. **JVM의 원시형은 참조가 아니다.** 원시 `int`는 힙의 주소가 아니라 스택이나 레지스터에 있는 32비트 값 그 자체이다. 그런데 다음 세 경우에는 모두 "참조"가 필요하다.

1. **널(null)을 담아야 할 때.** 원시 `int`에는 "값 없음"을 표현할 비트 패턴이 없다(2³²개의 패턴이 모두 유효한 정수이다). 널은 참조 타입만 가질 수 있다.
2. **제네릭 타입 인자일 때.** JVM 제네릭은 타입 소거([[34 - 제네릭 2 - 타입 소거와 reified와 바운드]])로 구현되어 모든 타입 파라미터가 `Object`로 지워진다. `Object`는 참조 타입이므로 `int`가 들어갈 수 없다.
3. **상위 타입으로 취급될 때.** `Any`, `Number`, `Comparable<Int>` 같은 상위 타입 자리에 `Int`를 넣으면, 그 자리는 참조를 기대하므로 박싱된다.

```kotlin
val primitive: Int = 42          // 원시 int
val boxed: Int? = 42             // Integer 박스 (널 담을 준비)
val asAny: Any = 42              // Integer 박스 (Any는 참조)
val inList: List<Int> = listOf(42) // 원소가 Integer 박스
```

### 2.2 바이트코드에서 박싱과 언박싱은 어떻게 일어나는가

JVM 백엔드에서 박싱은 정적 메서드 `Integer.valueOf(int)` 호출로, 언박싱은 인스턴스 메서드 `Integer.intValue()` 호출로 번역된다.

```kotlin
val n: Int = 7
val boxed: Any = n      // 박싱
val back: Int = boxed as Int   // 언박싱
```

```text
// 개념적 바이트코드
iconst_7                 // 원시 int 7을 스택에
invokestatic Integer.valueOf(int) : Integer    // ← 박싱
astore boxed
...
aload boxed
checkcast Integer
invokevirtual Integer.intValue() : int          // ← 언박싱
istore back
```

박싱하면 **힙 할당**이 일어난다(캐시된 경우는 예외이며 4.2절에서 설명한다). 언박싱은 할당은 없지만 메서드 호출과 널 검사가 따른다. 자주 실행되는 루프(hot loop)에서 무심코 `Int?`나 `List<Int>`를 쓰면 반복할 때마다 이 비용이 든다.

> [!caution] 성능 주의
> K2 컴파일러는 한 메서드 본문 안에서 박싱과 언박싱이 연달아 일어나면 중간 박스를 **제거**할 수 있다. `val x: Int? = 5; val y = x!! + 1`에서 `x`를 힙에 할당했다가 바로 꺼내는 대신, 옵티마이저가 원시 산술로 바꿀 수 있다.
>
> 하지만 값이 메서드 경계(파라미터, 필드, 반환값, 제네릭 슬롯)를 넘어가면 이 최적화는 적용되지 않는다. 경계에서는 표현이 고정되어야 하기 때문이다. "박싱은 성능에 나쁘다"가 항상 맞는 것은 아니지만, "경계를 넘는 박스는 실제로 존재한다"는 항상 맞다.

### 2.3 자동 박싱과 언박싱은 눈에 보이지 않는다

Kotlin은 박싱과 언박싱을 **암시적으로** 삽입한다. 소스에는 아무 표시도 없다. 편리하지만 함정이 되기도 한다.

```kotlin
fun sumList(xs: List<Int>): Int {
    var acc = 0                 // acc는 원시 int
    for (x in xs) {             // x는 List에서 꺼낼 때 언박싱
        acc += x                // 원시 산술
    }
    return acc
}
```

`List<Int>`는 원소를 `Integer`로 저장하므로, `for (x in xs)`는 원소마다 `intValue()`로 언박싱한다. 같은 알고리즘을 `IntArray`로 작성하면(9절) 박스가 전혀 생기지 않는다. 소스는 거의 같아 보여도 기계 수준에서는 완전히 다르다. 이 장의 목표는 이렇게 보이지 않는 비용을 알아볼 수 있게 되는 것이다.

## 3. `Int?`는 정말 항상 박싱되는가

### 3.1 흔한 단정과 절반만 맞는 사실

인터넷과 입문서에 널리 퍼진 단정이 있다. **"`Int?`는 항상 박싱된 래퍼이다."** 이 문장은 절반은 맞고 절반은 틀리다. 정확히 어디까지 맞는지 구분해 보자.

**맞는 부분**: JVM 백엔드에서 정적 타입이 `Int?`인 값이 **메서드 경계를 넘거나 저장될 때** 그 표현은 `java.lang.Integer`(박스)이다. 널을 표현하려면 참조가 필요한데, 원시 `int`에는 널을 나타낼 비트가 없기 때문이다. 함수 파라미터 `fun f(n: Int?)`, 프로퍼티 `val x: Int?`, 제네릭 슬롯 같은 자리에서 `Int?`는 `Integer`이다.

```kotlin
class Box(val value: Int?)      // value 필드는 Integer 타입 (JVM 백엔드)
fun accept(n: Int?) { }         // 파라미터 n은 Integer 타입
```

**틀린 부분**: "항상"이 과장인 이유는 세 가지이다.

1. **메서드 본문 안의 지역 데이터 흐름에서는 박스가 제거될 수 있다.** K2 옵티마이저는 `Int?` 값이 실제로 널일 수 있는 경로와 그렇지 않은 경로를 분석한다. 그리고 스마트 캐스트([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]) 이후 비-널로 좁혀진 구간에서는 원시 `int`로 유지한다. 박스는 필요한 순간(경계를 넘거나 실제로 널을 담을 때)에만 생긴다.

```kotlin
fun f(n: Int?): Int {
    if (n == null) return 0
    // 여기서 n은 스마트 캐스트로 Int (비-널). 
    // 옵티마이저는 이 구간을 원시 int로 다룰 수 있다.
    return n * 2 + n
}
```

2. **박싱했다가 바로 언박싱하는 과정은 제거된다.** 2.2절에서 보았듯이 한 표현식 안에서 박싱한 뒤 즉시 언박싱하는 패턴은 옵티마이저가 원시 연산으로 바꾼다.

3. **JVM이 아닌 백엔드는 Java식 박싱을 쓰지 않는다.** Kotlin/Native, JS, Wasm에서 `Int?`의 널은 각 플랫폼의 방식(예: 태그된 유니온, `null`/`undefined`, 옵셔널 표현)으로 표현하며, "`Integer` 힙 객체"라는 개념 자체가 없다. "항상 박싱된 래퍼"라는 단정은 은연중에 JVM만 전제한 것이다. Kotlin은 JVM만을 위한 언어가 아니다.

그래서 정확하게는 이렇게 말해야 한다. **"JVM 백엔드에서 `Int?`는 값이 참조 경계를 넘는 순간 `Integer`로 박싱되지만, 지역 계산에서는 옵티마이저가 박스를 없앨 수 있고, 다른 백엔드는 아예 다른 표현을 쓴다."** "항상"이라는 단어 때문에 원래 문장은 틀린 문장이 된다.

### 3.2 그래도 실무 규칙은 "널 가능 수는 박스라고 가정하라"

정확한 사실은 위와 같지만, 실무에서 성능을 따질 때는 여전히 "널 가능 수와 제네릭에 담긴 수는 박스"라고 어림하는 편이 안전하다. 옵티마이저의 박스 제거는 보장이 아니라 최선 노력(best effort)이고, 경계를 넘으면 박스가 실제로 생기기 때문이다. 두 설명은 서로 모순되지 않는다.

- **명세와 정확성의 관점**: "항상"은 틀렸다. 박싱은 표현의 세부이고 백엔드와 문맥에 따라 달라진다.
- **성능 어림의 관점**: 자주 실행되는 경로에서 `Int?`나 `List<Int>`가 보이면 "박스가 생길 수 있다"고 주의한다.

숙련된 개발자는 두 관점을 함께 기억한다. "항상 박싱된다"고 외우면 어떤 경우에 박스가 보이지 않는 이유를 설명하지 못하고, "박싱되지 않는다"고 방심하면 컬렉션 루프에서 GC 부담에 놀라게 된다.

| 위치 | JVM 백엔드 표현 | 박싱? |
|------|----------------|-------|
| `val x: Int = 5` | 원시 `int` | 아니오 |
| `val x: Int? = 5` (경계·저장) | `Integer` | 예 |
| `val x: Int? = 5` 후 스마트캐스트 구간 | 원시 `int` 가능 | 옵티마이저 재량 |
| `List<Int>`의 원소 | `Integer` | 예 |
| `IntArray`의 원소 | `int` | 아니오 |
| `Any`로 상향된 `Int` | `Integer` | 예 |
| 제네릭 `fun <T> id(x: T)`에 `Int` | `Integer` | 예 |

## 4. 박싱 캐시와 `===`의 함정

### 4.1 같은 값, 다른 박스

박싱이 힙 할당이라는 말은 **"같은 정수 값이라도 서로 다른 박스 객체가 될 수 있다"** 는 뜻이다. 그런데 참조 동일성 `===`는 "같은 객체인가"를 묻는다. 여기서 유명한 함정이 생긴다.

```kotlin
val a: Int? = 127
val b: Int? = 127
println(a == b)    // => true   (구조적 동등: 값이 같다)
println(a === b)   // => true   (?! 같은 박스 객체다)

val c: Int? = 128
val d: Int? = 128
println(c == d)    // => true   (값이 같다)
println(c === d)   // => false  (?! 다른 박스 객체다)
```

`127`에서는 `===`가 `true`인데 `128`에서는 `false`이다. 두 경우 모두 값은 서로 같은데 참조 동일성만 다르다. 이유는 전적으로 **JVM의 박싱 구현 세부**에 있다.

### 4.2 `Integer.valueOf`의 캐시

JVM 백엔드에서 박싱은 `Integer.valueOf(int)`를 호출한다. 그런데 `java.lang.Integer` 명세에 따르면 이 메서드는 **-128부터 127까지의 값에 대해 캐시된 인스턴스를 재사용**한다. 즉 이 범위 안의 정수를 박싱하면 항상 같은 싱글턴 박스가 나오고, 범위를 벗어나면 매번 새 박스를 할당한다.

```text
Integer.valueOf(127)  →  캐시 배열의 고정 인스턴스 (항상 동일 객체)
Integer.valueOf(128)  →  new Integer(128)  (매번 새 객체)
```

그래서 `127`은 두 변수가 같은 캐시 객체를 가리키므로 `===`가 `true`이고, `128`은 서로 다른 새 객체이므로 `false`가 된다. 이것은 정수의 성질도 아니고 Kotlin 언어의 규칙도 아니다. `java.lang.Integer`라는 **표준 라이브러리 클래스의 최적화**일 뿐이다.

> [!note] 명세 기준
> 캐시 하한 -128은 고정이지만, 상한 127은 JVM 옵션 `-XX:AutoBoxCacheMax`로 늘릴 수 있어서 실제 경계는 실행 환경에 따라 달라질 수 있다. 따라서 "128부터 `===`가 false"라는 것조차 이식성 있는 규칙이 아니다.
>
> `Long` 박스(`Long.valueOf`)도 -128..127 캐시를 두고, `Boolean`, `Byte`, `Char`(0..127), `Short`(-128..127)에도 비슷한 캐시가 있지만 **`Float`와 `Double`에는 캐시가 없다.** 세부 동작은 [[45 - Java 상호운용]]에서 다루는 표준 라이브러리 계약에 따라 정해진다.

### 4.3 교훈: 수의 동일성을 `===`로 묻지 마라

이 함정의 전체 내용, 즉 `==`가 어떻게 `equals`로 풀리는지, `===`가 언제 의미가 있고 언제 없는지, 원시형으로 컴파일되는 값에서 왜 `===`를 예측할 수 없는지는 10장(불리언과 동등성과 동일성)에서 다룬다. 이 장에서 확인한 것은 이 함정이 **물리적으로 어디서 생기는가**이다. 박스는 힙 객체이고, JVM은 작은 정수 박스를 캐시하며, 그래서 참조 동일성의 결과가 값에 따라 달라진다.

실무 규칙은 간단하다. **수가 "같은지"는 항상 `==`로 물어라.** `===`로 수를 비교하는 것은 거의 항상 버그이다(캐시 범위 안에서는 우연히 맞기 때문에 더 위험하다). 이 규칙을 지키면 코드가 박싱이라는 표현 세부에 의존하지 않게 된다.

```kotlin
val a: Int? = 1000
val b: Int? = 1000
// if (a === b) ...   // 함정: 1000은 캐시 밖 → false. 값 비교가 의도라면 버그.
if (a == b) { }       // 올바름: 값이 같은가를 묻는다
```

## 5. 오버플로: 예외 없이 조용히 래핑된다

### 5.1 유한한 비트는 넘치지만 예외는 없다

`Int`는 32비트, `Long`은 64비트이다. 비트 수가 유한하므로 표현 범위도 유한하다. `Int`는 $-2^{31}$부터 $2^{31}-1$까지, 즉 `-2147483648`부터 `2147483647`까지이다. 이 범위를 벗어나는 산술을 하면 어떻게 될까? **Kotlin은 예외를 던지지 않는다. 2의 보수(two's complement) 규칙에 따라 조용히 래핑한다.**

```kotlin
val max = Int.MAX_VALUE          // 2147483647
println(max + 1)                 // => -2147483648  (Int.MIN_VALUE로 뒤집힘!)
println(max * 2)                 // => -2  
println(Int.MIN_VALUE - 1)       // => 2147483647   (반대편으로 되감김)
```

`2147483647 + 1`은 예외가 아니라 `-2147483648`이 된다. 32비트가 넘치면서 최상위 비트(부호 비트)로 캐리(carry)가 넘어가 값이 음수로 뒤집힌 것이다. 수학적으로는 결과를 $2^{32}$로 나눈 나머지를 취하는 것과 같다.

$$
(2147483647 + 1) \bmod 2^{32} = 2^{31} \equiv -2^{31} \pmod{2^{32}}
$$

> [!info] 역사 메모
> 조용한 래핑은 설계를 게을리한 결과가 아니라 JVM 정수 산술의 의미를 그대로 따른 것이다. JVM 바이트코드 `iadd`, `imul` 등은 오버플로를 검사하지 않고 하위 32비트만 남긴다. Kotlin이 산술마다 오버플로 검사를 넣었다면 성능이 크게 떨어졌을 것이다. 그래서 Kotlin은 "기본은 빠르게, 필요하면 명시적으로 검사"하는 방식을 택했다. 대부분의 시스템 언어(C, Java, Go 등의 부호 있는 정수)도 같은 선택을 했다.

### 5.2 오버플로 때문에 생기는 고전적인 버그

**(1) 두 큰 정수의 평균.** `(a + b) / 2`는 `a + b`가 오버플로하면 틀린 값이 된다. 이진 탐색에서 중간 인덱스를 계산할 때 생기는 것으로 유명한 버그이다.

```kotlin
val a = 2_000_000_000
val b = 2_000_000_000
println((a + b) / 2)          // => -147483648  (오버플로! 음수)
println(a + (b - a) / 2)      // => 2000000000  (안전한 관용구)
```

**(2) `abs(Int.MIN_VALUE)`는 음수이다.** 가장 직관에 어긋나는 함정이다. 원인은 범위가 비대칭이라는 데 있다. `Int.MIN_VALUE`는 `-2147483648`인데, 그 절댓값 `2147483648`은 `Int.MAX_VALUE`(`2147483647`)보다 커서 표현할 수 없다. 그래서 `abs`는 입력값을 그대로 돌려준다.

```kotlin
import kotlin.math.abs
println(abs(Int.MIN_VALUE))   // => -2147483648  (여전히 음수!)
println(-Int.MIN_VALUE)       // => -2147483648  (부호 반전도 실패)
```

부호 있는 2의 보수에서는 음수가 양수보다 하나 더 많다(음수는 $-2^{31}$까지, 양수는 $2^{31}-1$까지이다). 그 "하나 더"인 `MIN_VALUE`에는 짝이 되는 양수가 없으므로, 이 값에서는 부호 반전과 절댓값이 제대로 동작하지 않는다.

**(3) `Int.MIN_VALUE / -1`.** 나눗셈이 오버플로하는 유일한 경우이다. `-2147483648 / -1`의 참값은 `2147483648`인데 범위를 넘으므로 다시 `MIN_VALUE`로 래핑된다(JVM에서 예외는 발생하지 않는다).

```kotlin
println(Int.MIN_VALUE / -1)   // => -2147483648  (오버플로, 예외 아님)
```

### 5.3 검사가 필요하면 명시적으로: `Math.*Exact`

오버플로를 조용히 넘기고 싶지 않다면, JVM 백엔드에서는 `java.lang.Math`의 `*Exact` 계열 함수를 쓴다. 이 함수들은 오버플로가 일어나면 `ArithmeticException`을 던진다.

```kotlin
println(Math.addExact(Int.MAX_VALUE, 1))
// 컴파일 에러 아님. 런타임에 ArithmeticException: integer overflow

println(Math.multiplyExact(100_000, 100_000)) // 예외 (Int 범위 초과)
println(Math.toIntExact(3_000_000_000L))       // 예외 (Long→Int 축소 오버플로)
```

> [!note] 명세 기준
> `Math.addExact` 등은 JVM 표준 라이브러리 함수이므로 **JVM 백엔드에서만** 쓸 수 있다. 멀티플랫폼 공통 코드에서 오버플로 검사가 필요하면 더 넓은 타입(`Long`)으로 승격해 계산한 뒤 범위를 직접 확인하거나, 부호 없는 정수(7절)로 의미를 분명히 한다. Kotlin 표준 라이브러리에는 여러 플랫폼에서 공통으로 쓸 수 있는 "checked arithmetic" 연산자가 기본으로 들어 있지 않다.

### 5.4 0으로 나누기: 정수와 부동소수의 차이

오버플로와 함께 알아 둘 것이 0으로 나누기이다. **정수와 부동소수의 동작이 다르다.**

```kotlin
// println(5 / 0)          // 런타임 ArithmeticException: / by zero
// println(5 % 0)          // 런타임 ArithmeticException

println(5.0 / 0.0)         // => Infinity        (예외 아님)
println(-5.0 / 0.0)        // => -Infinity
println(0.0 / 0.0)         // => NaN
```

정수 나눗셈 `/ 0`은 예외를 던지지만, 부동소수 `/ 0.0`은 IEEE 754 규칙에 따라 예외 없이 `Infinity`나 `NaN`을 결과로 낸다. 이 차이는 뒤에서 살펴볼 부동소수의 특이값으로 이어진다(10절).

## 6. 비트 연산: 비트 패턴을 직접 다루기

### 6.1 Kotlin의 비트 연산자는 연산자가 아니라 중위 함수이다

많은 언어에서 비트 연산은 기호(`&`, `|`, `^`, `<<`, `>>`)로 쓴다. Kotlin은 이 기호들을 **쓰지 않는다.** 대신 `Int`와 `Long`의 **중위(infix) 함수**로 제공한다. 이는 [[19 - 연산자 오버로딩과 관례]]에서 볼 "관례 함수 이름"과는 다른 방식이다. 비트 연산은 오버로딩할 수 있는 연산자가 아니라 이름이 붙은 함수이다.

```kotlin
val flags = 0b1010
println(flags and 0b0110)   // => 2   (0b0010, 비트 AND)
println(flags or 0b0110)    // => 14  (0b1110, 비트 OR)
println(flags xor 0b0110)   // => 12  (0b1100, 비트 XOR)
println(flags.inv())        // => -11 (모든 비트 반전; inv는 중위 아님, 단항 함수)
println(flags shl 2)        // => 40  (왼쪽 시프트 2칸)
println(flags shr 1)        // => 5   (부호 유지 오른쪽 시프트)
println(flags ushr 1)       // => 5   (부호 무시 오른쪽 시프트)
```

| 함수 | 의미 | 형태 | 정의 대상 |
|------|------|------|-----------|
| `and` | 비트 AND | 중위 | Int, Long, (Boolean) |
| `or` | 비트 OR | 중위 | Int, Long, (Boolean) |
| `xor` | 비트 XOR | 중위 | Int, Long, (Boolean) |
| `inv()` | 비트 NOT(1의 보수) | 단항 메서드 | Byte, Short, Int, Long |
| `shl` | 왼쪽 시프트 | 중위 | Int, Long |
| `shr` | 산술 오른쪽 시프트(부호 유지) | 중위 | Int, Long |
| `ushr` | 논리 오른쪽 시프트(0 채움) | 중위 | Int, Long |

> [!warning] 흔한 오해
> "비트 연산은 모든 정수 타입에 있다"는 틀렸다. 표준 라이브러리에서 `shl`/`shr`/`ushr`/`and`/`or`/`xor`는 **`Int`와 `Long`에만** 정의되어 있다. `Byte`와 `Short`에는 비트 중위 함수가 없으므로 먼저 `toInt()`로 승격해야 한다. `Boolean`에는 `and`/`or`/`xor`/`not()`이 있지만(논리 연산, 10장 불리언과 동등성과 동일성) 시프트는 없다. `UInt`/`ULong`에도 비트 함수가 있다(7절).

```kotlin
val b: Byte = 0b0110
// println(b and 0b0010)   // 컴파일 에러: Byte에 and 없음
println(b.toInt() and 0b0010)  // => 2   (Int로 승격 후)
```

### 6.2 `shr`와 `ushr`: 부호 비트를 어떻게 처리하는가

오른쪽 시프트가 두 가지인 이유는 **부호 비트**를 처리하는 방식이 다르기 때문이다. `shr`(산술 시프트)는 최상위 부호 비트를 복제해 빈자리를 채우므로 음수는 음수로 남는다. `ushr`(논리 시프트)는 항상 0으로 채우므로 음수의 부호 비트가 밀려나 큰 양수가 된다.

```kotlin
val neg = -8                       // 0b111...11111000 (32비트, 상위 다 1)
println(neg shr 1)                 // => -4   (부호 유지: 상위에 1 채움)
println(neg ushr 1)                // => 2147483644  (0 채움 → 거대 양수)

println((-1) shr 31)               // => -1   (부호 비트 계속 복제)
println((-1) ushr 31)             // => 1    (0 채우니 최하위 1비트만 남음)
```

```text
-8을 32비트로:  1111 1111 ... 1111 1000
shr 1 (부호): 1111 1111 ... 1111 1100  = -4
ushr 1 (0):  0111 1111 ... 1111 1100  = 2147483644
```

부호 없는 정수가 없던 시절에는 `ushr`이 "비트를 부호 없이 다루는" 유일한 도구였다. 이제는 `UInt`(7절)가 더 명확한 대안이다.

### 6.3 시프트 횟수는 마스킹된다: `1 shl 32 == 1`

가장 직관에 어긋나는 함정이다. **시프트 횟수가 비트 폭 이상이면 비트가 모두 밀려나 0이 되는 것이 아니라, 횟수를 비트 폭으로 나눈 나머지만큼 시프트한다.**

```kotlin
println(1 shl 32)    // => 1    (32칸이 아니라 32 mod 32 = 0칸 시프트!)
println(1 shl 33)    // => 2    (33 mod 32 = 1칸)
println(1 shl -1)    // => -2147483648  (-1 mod 32 → 31칸, 부호비트로)

println(1L shl 64)   // => 1    (Long은 64로 마스킹: 64 mod 64 = 0)
println(1L shl 65)   // => 2    (65 mod 64 = 1)
```

이유는 JVM 시프트 명령의 정의에 있다. `Int` 시프트(`ishl`/`ishr`/`iushr`)는 시프트 횟수의 **하위 5비트만** 사용하고($\bmod\ 32$), `Long` 시프트(`lshl` 등)는 하위 6비트를 사용한다($\bmod\ 64$). Kotlin의 `shl` 등은 이 JVM 동작을 그대로 따른다.

$$
\text{shift count 실제값} = n \bmod 32 \quad (\text{Int}), \qquad n \bmod 64 \quad (\text{Long})
$$

> [!caution] 성능 주의
> 이 마스킹 때문에 "가변 비트 폭 시프트"를 작성할 때 `x shl width`에서 `width == 32`(Int)나 `width == 64`(Long)를 따로 처리하지 않으면, 0을 기대한 자리에 원래 값이 그대로 나온다. 비트 마스크, 해시 함수, 직렬화 코드에서 자주 나오는 조용한 버그이다.

### 6.4 표준 라이브러리의 비트 유틸리티

Kotlin 1.5부터 정수 타입에 여러 비트 조작 함수가 안정 API로 들어왔다(`kotlin.experimental` 표시 없이 사용할 수 있다).

```kotlin
println(0b10110.countOneBits())        // => 3   (1인 비트 수, popcount)
println(1.countLeadingZeroBits())      // => 31  (최상위부터 0의 개수, Int는 32비트)
println(8.countTrailingZeroBits())     // => 3   (최하위부터 0의 개수)
println(0b10110.takeHighestOneBit())   // => 16  (가장 높은 1비트만 남김)
println(0b10110.takeLowestOneBit())    // => 2   (가장 낮은 1비트만 남김)
println(1.rotateLeft(4))               // => 16  (회전 시프트, 밀린 비트가 반대편으로)
println(Int.MIN_VALUE.rotateLeft(1))   // => 1   (부호비트가 최하위로 회전)
```

이 함수들은 마스킹, 플래그, 비트셋, 저수준 최적화에서 직접 작성하던 관용구를 대신한다. JVM 백엔드에서는 대개 `Integer.bitCount` 같은 인트린식으로 컴파일되어 빠르다.

### 6.5 실전: 비트 플래그로 여러 상태를 정수 하나에 담기

비트 연산의 대표적인 용도는 여러 불리언 상태를 하나의 정수에 **플래그(flag)** 로 압축하는 것이다. 각 비트가 참/거짓 하나를 나타낸다. 동물의 특성을 예로 들어, 날 수 있는지, 헤엄칠 수 있는지, 야행성인지, 독이 있는지를 4비트에 담아 보자.

```kotlin
const val CAN_FLY   = 1 shl 0   // 0b0001
const val CAN_SWIM  = 1 shl 1   // 0b0010
const val NOCTURNAL = 1 shl 2   // 0b0100
const val VENOMOUS  = 1 shl 3   // 0b1000

// 박쥐: 날 수 있고 야행성
val bat = CAN_FLY or NOCTURNAL      // 0b0101 = 5

fun has(traits: Int, flag: Int): Boolean = (traits and flag) != 0
fun add(traits: Int, flag: Int): Int = traits or flag
fun remove(traits: Int, flag: Int): Int = traits and flag.inv()
fun toggle(traits: Int, flag: Int): Int = traits xor flag

println(has(bat, CAN_FLY))          // => true   (AND으로 비트 존재 확인)
println(has(bat, CAN_SWIM))         // => false
val bat2 = add(bat, VENOMOUS)       // 독 추가 → 0b1101
println(has(bat2, VENOMOUS))        // => true
val bat3 = remove(bat2, NOCTURNAL)  // 야행성 제거 → 0b1001
println(has(bat3, NOCTURNAL))       // => false
println(bat.countOneBits())         // => 2   (켜진 특성 수)
```

각 연산의 비트 논리를 정리하면 다음과 같다.

| 연산 | 비트 관용구 | 원리 |
|------|-------------|------|
| 켜짐 검사 | `(traits and flag) != 0` | AND로 해당 비트만 남겨 0인지 확인 |
| 추가 | `traits or flag` | OR로 비트를 1로 설정 |
| 제거 | `traits and flag.inv()` | 마스크를 반전해 AND → 해당 비트만 0으로 |
| 토글 | `traits xor flag` | XOR는 1과 만나면 비트를 반전 |

제거할 때 `inv()`가 왜 필요한지 보자. `VENOMOUS`는 `0b1000`이고, `inv()`를 적용하면 `0b…11110111`(그 비트만 0이고 나머지는 모두 1)이 된다. 이 값과 AND하면 그 비트만 지워지고 나머지는 그대로 남는다. 이 관용구는 파일 권한(rwx), 네트워크 프로토콜 플래그, 그래픽 상태 비트 등 여러 곳에서 쓰인다.

> [!caution] 성능 주의
> 비트 플래그는 매우 조밀하고 빠르지만(정수 하나에 불리언 32개), 가독성이 떨어진다. 플래그 수가 적고 성능이 중요한 경우에만 쓰고, 그 밖에는 `Set<Enum>`이나 데이터 클래스의 `Boolean` 프로퍼티가 더 명확하다. JVM의 `EnumSet` 같은 추상화는 타입 안전성을 제공하면서 내부적으로 이 비트 기법을 쓴다. 추가 비용 없이 추상화의 이점을 얻는 셈이다.

### 6.6 XOR의 성질: 원래 값으로 되돌리기와 토글

`xor`에는 특별한 대수적 성질이 있다. `a xor a == 0`, `a xor 0 == a`이고, 결합 법칙과 교환 법칙이 성립한다. 이 성질에서 몇 가지 관용구가 나온다.

```kotlin
val a = 0b1100
println(a xor a)                    // => 0    (자기 자신과 XOR = 0)
println(a xor 0)                    // => 12   (0과 XOR = 자기 자신)
println((a xor 0b1010) xor 0b1010)  // => 12   (같은 값 두 번 XOR = 원상복귀)
```

"같은 값을 두 번 XOR하면 원래 값으로 돌아온다"는 성질($(a \oplus k) \oplus k = a$)은 단순한 마스킹, 체크섬, 토글의 바탕이 된다. 앞의 6.5절에서 본 `toggle`이 바로 이 성질을 이용한다. 같은 플래그를 두 번 토글하면 원래 상태로 돌아온다. XOR의 이런 가역성은 비트 연산 가운데 유일하게 "정보를 잃지 않는" 성질이어서, 되돌릴 수 있는 변환이 필요한 곳에서 특히 중요하다.

## 7. 부호 없는 정수: value class로 만든 새 수 타입

### 7.1 부호 없는 정수가 필요한 이유

부호 있는 `Int`는 최상위 비트를 부호로 쓰기 때문에, 32비트를 모두 크기로 쓰는 값(예: `0xFFFFFFFF` = 4294967295)을 담지 못하고 `-1`로 해석한다. 바이트 스트림, 색상 값(`0xFFRRGGBB`), 해시, 네트워크 프로토콜의 부호 없는 필드를 다룰 때 이런 부호 해석이 걸림돌이 된다. 그래서 Kotlin은 네 가지 부호 없는 정수 타입을 제공한다.

| 타입 | 비트 | 범위 | 대응 부호 타입 |
|------|------|------|----------------|
| `UByte` | 8 | 0 .. 255 | `Byte` |
| `UShort` | 16 | 0 .. 65535 | `Short` |
| `UInt` | 32 | 0 .. 4294967295 | `Int` |
| `ULong` | 64 | 0 .. 18446744073709551615 | `Long` |

```kotlin
val u: UInt = 4_294_967_295u        // Int로는 불가능한 값
println(u)                          // => 4294967295
println(u + 1u)                     // => 0   (오버플로 래핑: mod 2^32)
println(0u - 1u)                    // => 4294967295  (부호 없는 되감김)

val color: UInt = 0xFF3366FFu
val alpha = (color shr 24) and 0xFFu  // => 255u
```

리터럴은 접미사 `u`/`U`로 표기하고, `ULong`은 `uL`을 쓴다. 예를 들면 `100uL`, `0xFFu`, `255U`와 같다.

### 7.2 동작 원리: `@JvmInline value class`

부호 없는 정수에서 놀라운 점은 이 타입들이 **언어의 기본 원시 타입이 아니라, 표준 라이브러리가 `value class`로 정의한 사용자 수준 타입**이라는 것이다. 개념적으로 `UInt`는 다음과 같이 정의되어 있다.

```kotlin
// 표준 라이브러리의 개념적 정의 (실제 시그니처를 단순화)
@JvmInline
value class UInt internal constructor(private val data: Int) {
    operator fun plus(other: UInt): UInt = UInt(this.data + other.data)
    operator fun compareTo(other: UInt): Int = 
        Integer.compareUnsigned(this.data, other.data)  // JVM: 부호 없이 비교
    override fun toString(): String = 
        Integer.toUnsignedString(data)                   // JVM: 부호 없이 문자열화
    // ...
}
```

핵심은 **`UInt`가 내부적으로 `Int`를 그대로 감싸고, 그 비트를 부호 없이 다시 해석한다**는 점이다. `UInt`의 최댓값 `4294967295u`는 내부 `Int`로는 `-1`이다(비트 패턴 `0xFFFFFFFF`가 같다). 저장하는 비트는 같고, 연산 규칙만 다르다.

- `plus`: 비트 덧셈은 부호가 있든 없든 결과가 같다(2의 보수의 장점이다). 그래서 `Int`의 `+`를 그대로 쓴다.
- `compareTo`: 부호 있는 비교와 결과가 다르므로, JVM 백엔드에서는 `Integer.compareUnsigned`를 호출한다.
- `div`/`rem`: 부호 없는 나눗셈이므로 `Integer.divideUnsigned`/`remainderUnsigned`를 호출한다.
- `toString`: `Integer.toUnsignedString`을 호출한다.

> [!note] 명세 기준
> `Integer.compareUnsigned` 같은 호출은 **JVM 백엔드**의 구현 방식이다. 다른 백엔드는 같은 *의미*를 각자의 방식으로 구현한다. 언어가 보장하는 것은 "`UInt`는 0..2³²−1 범위에서 부호 없는 산술 의미를 갖는다"는 것이지, "내부적으로 `Integer.compareUnsigned`를 호출한다"는 것이 아니다.

### 7.3 value class이므로 대개 언박싱되지만, 조건에 따라 박싱된다

`value class`의 이점은 **런타임에 래퍼 객체 없이 내부 값으로 표현된다**는 것이다. `UInt`는 대부분의 문맥에서 원시 `int`로 컴파일되므로 힙 할당도 박싱도 없다. 이 인라이닝을 지시하는 것이 `@JvmInline`이다.

```kotlin
fun brightness(color: UInt): UInt {   // 파라미터·반환이 원시 int로 인라인 (JVM)
    val r = (color shr 16) and 0xFFu
    val g = (color shr 8) and 0xFFu
    val b = color and 0xFFu
    return (r + g + b) / 3u
}
```

하지만 `value class`도 **박싱을 완전히 피하지는 못한다.** 다음 경우에는 `UInt`가 래퍼 객체로 박싱된다.

1. **널 가능(`UInt?`)**: 널을 표현하려면 박스가 필요하다(3절과 같은 이유).
2. **제네릭 타입 인자(`List<UInt>`, `T = UInt`)**: 타입 소거 때문에 참조가 필요하다.
3. **상위 타입으로 상향(`Any`, `Comparable<UInt>`)**: 참조를 기대하는 자리이다.
4. **컬렉션이나 배열에 담길 때**(전용 `UIntArray`는 제외).

"value class는 항상 박싱을 없앤다"는 오해가 틀린 이유를 보여 주는 실제 사례이다. 언박싱 조건 전체 표와 그 이론은 36장(타입 별칭과 인라인 value class)에서 다룬다. 여기서 기억할 것은 **부호 없는 정수도 결국 value class이므로 원시 `Int`와 똑같은 박싱 규칙을 따른다**는 일관성이다.

### 7.4 부호 없는 배열과 변환

박싱 없이 부호 없는 정수를 대량으로 담으려면 전용 배열 타입 `UByteArray`, `UShortArray`, `UIntArray`, `ULongArray`를 쓴다(이 타입들도 안정 API이다). `List<UInt>`가 원소를 박싱하는 것과 대비된다(9절).

```kotlin
val bytes: UByteArray = ubyteArrayOf(0xDEu, 0xADu, 0xBEu, 0xEFu)
val nums: UIntArray = UIntArray(4) { (it * it).toUInt() }
```

변환은 두 가지로 나뉜다. **비트 재해석**(`toUInt`/`toInt`)과 **값 변환**을 구별해야 한다.

```kotlin
val signed: Int = -1
println(signed.toUInt())          // => 4294967295  (비트 그대로 재해석)
println(signed.toUInt().toInt())  // => -1          (왕복하면 원상복귀)

val big: UInt = 300u
println(big.toByte())             // => 44  (300 mod 256, 하위 8비트만)
println(big.toUByte())            // => 44u (부호 없는 축소도 하위 8비트)
```

### 7.5 실전: 부호 없는 바이트로 색상 채널 다루기

부호 없는 정수가 특히 유용한 곳은 "비트가 곧 데이터"인 영역이다. 32비트 색상 `0xAARRGGBB`(알파, 빨강, 초록, 파랑 각 8비트)를 부호 걱정 없이 분해하고 합성해 보자.

```kotlin
fun channels(argb: UInt): List<UByte> = listOf(
    ((argb shr 24) and 0xFFu).toUByte(),   // 알파
    ((argb shr 16) and 0xFFu).toUByte(),   // 빨강
    ((argb shr 8) and 0xFFu).toUByte(),    // 초록
    (argb and 0xFFu).toUByte(),            // 파랑
)

fun compose(a: UByte, r: UByte, g: UByte, b: UByte): UInt =
    (a.toUInt() shl 24) or (r.toUInt() shl 16) or (g.toUInt() shl 8) or b.toUInt()

val orange: UInt = 0xFFFF8800u
println(channels(orange))                  // => [255, 255, 136, 0]
println(compose(255u, 255u, 136u, 0u) == orange)  // => true
```

같은 코드를 부호 있는 `Int`로 작성하면 `0xFFFF8800`이 음수(`-30720`)로 해석되고, `shr`이 부호 비트를 복제하면서 상위 채널 값이 오염된다(그래서 Java에서는 `>>>`(ushr)를 빠짐없이 써야 했다). `UInt`에는 부호 비트라는 개념이 없어서 `shr`이 항상 0을 채우므로, 이런 오염이 처음부터 생기지 않는다. **데이터가 부호 없는 값을 뜻한다면 부호 없는 타입을 써서 그 의미를 타입으로 표현하는 것**, 이것이 이 기능이 존재하는 이유이다.

> [!info] 역사 메모
> 부호 없는 정수는 Kotlin 1.3(2018)에서 **실험적(experimental)** 기능으로 도입되었고, 사용하려면 `@ExperimentalUnsignedTypes` opt-in이 필요했다. 오랜 설계와 피드백을 거쳐 **Kotlin 1.5(2021)에서 안정(stable) 기능이 되었다.**
>
> 구현의 토대는 `value class`이다(`value class` 역시 1.5에서 `inline class`를 이어받아 안정화되었다). 실험적 도입, opt-in, 안정화로 이어지는 이 과정은 Kotlin이 언어를 확장하는 표준 절차이며, 이 제도는 [[46 - 멀티플랫폼과 진화와 어두운 구석]]에서 다룬다.

## 8. 진법과 변환: 리터럴에서 문자열까지

### 8.1 정수 리터럴의 진법 표기

Kotlin은 세 가지 진법의 리터럴을 지원한다. 특이하게도 **8진법(octal) 리터럴은 없다.**

```kotlin
val dec = 255            // 10진
val hex = 0xFF           // 16진 (0x/0X 접두)
val bin = 0b1111_1111    // 2진 (0b/0B 접두)
// val oct = 0o377       // 컴파일 에러: Kotlin에 8진 리터럴 없음
// val bad = 0377        // 컴파일 에러: 선행 0 리터럴 금지(8진 오해 방지)
```

숫자 사이에 `_`(밑줄)를 자릿수 구분자로 넣을 수 있다. 예를 들면 `1_000_000`, `0xFF_EC_DE_5E`, `0b0100_1101`과 같다. 밑줄은 값에 영향을 주지 않고 가독성만 높인다.

> [!info] 역사 메모
> C와 Java는 선행 `0`을 8진법으로 해석한다(`0377` == 255). 그래서 `010`이 8인지 10인지 헷갈리는 버그가 자주 생겼다. Kotlin은 이 함정을 아예 없앴다. 선행 0으로 시작하는 정수 리터럴은 **문법 오류**이다(단, `0` 자체와 `0.5` 같은 소수는 예외이다). 8진수가 필요하면 명시적으로 파싱해야 한다.

### 8.2 문자열과 수 사이의 진법 변환

`toString(radix)`로 원하는 진법의 문자열을 만들고, `toInt(radix)`/`toLong(radix)`로 파싱한다.

```kotlin
println(255.toString(16))        // => "ff"
println(255.toString(2))         // => "11111111"
println(255.toString(8))         // => "377"  (8진 리터럴은 없어도 변환은 됨)

println("ff".toInt(16))          // => 255
println("11111111".toInt(2))     // => 255
println("z".toInt(36))           // => 35   (radix는 2..36)

// println("ff".toInt())         // 런타임 NumberFormatException (기본 10진)
println("ff".toIntOrNull(16))    // => 255
println("xyz".toIntOrNull(16))   // => null (실패 시 예외 대신 null)
```

`radix`는 2부터 36까지 쓸 수 있다(0-9와 a-z를 자릿수로 사용한다). 범위를 벗어나면 예외가 발생한다. 파싱에 실패하면 `toInt`는 `NumberFormatException`을 던지고 `toIntOrNull`은 `null`을 돌려주므로, 방어적으로 파싱할 때는 `toIntOrNull`이 안전하다.

### 8.3 부호 없는 문자열 변환의 함정

부호 있는 값을 16진 문자열로 만들면 음수에는 부호가 붙는다. 부호 없는 비트 표현을 원한다면 `UInt`로 변환한 뒤 문자열로 만들어야 한다.

```kotlin
println((-1).toString(16))            // => "-1"   (부호 있는 해석)
println((-1).toUInt().toString(16))   // => "ffffffff"  (부호 없는 32비트)

// JVM 백엔드 대안:
println(Integer.toHexString(-1))      // => "ffffffff"  (Java 유틸, JVM 전용)
println(Integer.toBinaryString(5))    // => "101"
```

`(-1).toString(16)`이 `"-1"`인 것은 논리적으로 옳다. `-1`이라는 *값*을 16진수로 쓴 것이기 때문이다. 하지만 "이 정수의 비트를 16진수로 보고 싶다"면 `toUInt()`로 부호 해석을 없애야 `"ffffffff"`가 나온다. 이 차이를 놓치면 로그나 직렬화 결과에 음수가 이상하게 찍힌다.

## 9. 배열: 원시 배열과 박스 배열, 그리고 배열은 List가 아니다

### 9.1 `Array<T>`와 `IntArray`는 다른 타입이다

수를 여러 개 담는 가장 낮은 수준의 자료 구조가 배열이다. Kotlin에는 두 계열의 배열이 있고, 둘은 **메모리 레이아웃이 근본적으로 다르다.**

- **`Array<T>`**: 제네릭 참조 배열이다. 원소가 참조(객체)이며, `Array<Int>`의 원소는 `Integer` **박스**이다. JVM 백엔드에서는 `Integer[]`가 된다.
- **`IntArray`, `LongArray`, `DoubleArray`, `ByteArray`, `ShortArray`, `CharArray`, `FloatArray`, `BooleanArray`**: 원시 배열이다. 원소가 원시 값으로 빈틈없이 저장된다. JVM 백엔드에서는 `int[]`, `long[]` 등이 되며 **박싱이 없다.**

```kotlin
val boxed: Array<Int> = arrayOf(1, 2, 3)     // Integer[] — 원소마다 박스
val prim: IntArray = intArrayOf(1, 2, 3)     // int[] — 박스 없음
```

```text
Array<Int> (Integer[])            IntArray (int[])
┌───┐ ┌───┐ ┌───┐                ┌───┬───┬───┐
│ • │ │ • │ │ • │   참조 배열     │ 1 │ 2 │ 3 │  값이 촘촘
└─┬─┘ └─┬─┘ └─┬─┘                └───┴───┴───┘
  ▼     ▼     ▼
 [1]   [2]   [3]  힙에 흩어진 박스
```

`Array<Int>`는 원소마다 별도의 `Integer` 객체를 힙에 두고, 배열에는 그 객체들의 주소를 담는다. 그래서 캐시 지역성이 나쁘고 GC 부담이 크다. `IntArray`는 `int` 값이 배열 안에 연속으로 저장되어 있어 캐시 친화적이고 할당도 없다. **수를 대량으로 저장할 때는 원시 배열을 써라.** `IntArray` 등이 존재하는 이유는 이것 하나뿐이다.

```kotlin
val a = IntArray(5)                    // [0, 0, 0, 0, 0]
val b = IntArray(5) { it * it }        // [0, 1, 4, 9, 16]
val c = intArrayOf(3, 1, 4, 1, 5)
val d = Array(5) { "item$it" }         // Array<String>, 참조 배열은 이쪽
```

### 9.2 배열은 List가 아니다

**"Kotlin 배열은 List이다"는 흔한 오해이다.** `Array<T>`도 `IntArray`도 `List`가 아니며, `List` 인터페이스를 구현하지도 않는다. 세 타입은 완전히 다른 타입 계약을 갖는다.

```kotlin
val arr: IntArray = intArrayOf(1, 2, 3)
// val list: List<Int> = arr        // 컴파일 에러: IntArray는 List가 아니다
val list: List<Int> = arr.toList()  // 명시적 변환 필요 (원소를 박싱함!)

val objArr: Array<Int> = arrayOf(1, 2, 3)
// val list2: List<Int> = objArr    // 컴파일 에러: Array<Int>도 List 아님
```

세 타입의 계약 차이를 표로 정리하면 다음과 같다.

| 성질 | `IntArray` | `Array<T>` | `List<T>` |
|------|-----------|-----------|-----------|
| 크기 | 고정 | 고정 | 읽기전용 뷰(가변 구현은 변경 가능) |
| 원소 변경 | 가능(`arr[0] = 9`) | 가능 | `List`는 불가, `MutableList`만 |
| 원소 표현 | 원시(박스 없음) | 참조(박스) | 참조(박스) |
| `==` 의미 | 참조 동일성 | 참조 동일성 | 구조적 동등 |
| 변성 | 무공변 | 무공변 | 공변(`out`) |
| 최상위 타입 | `Any` | `Any` | `Collection`→`Iterable` |

`List`는 크기를 바꿀 수 없는 **읽기 전용 인터페이스**이고([[38 - 컬렉션 - 읽기 전용과 가변]]), 배열은 **크기는 고정이지만 원소는 언제나 바꿀 수 있는** 저수준 저장소이다. `Array<T>`에서는 인덱스 대입 `arr[i] = x`가 항상 가능하지만 `add`/`remove`는 없다. `List`는 반대로, 읽을 수는 있지만 원소 대입조차 인터페이스에 없다. 이 대비를 이해하면 배열과 읽기 전용 `List`의 차이를 함께 정리할 수 있다.

### 9.3 배열의 동등성 함정: `==`는 내용을 비교하지 않는다

가장 곤란한 함정이다. 배열은 `equals`를 재정의하지 않으므로 `==`가 **참조 동일성**(같은 배열 객체인가)을 검사한다. 내용이 똑같아도 서로 다른 배열이면 `false`이다.

```kotlin
val a = intArrayOf(1, 2, 3)
val b = intArrayOf(1, 2, 3)
println(a == b)                 // => false  (?! 내용은 같지만 다른 객체)
println(a === b)                // => false  (당연히 다른 객체)
println(a.contentEquals(b))     // => true   (내용 비교는 이걸로)

println(a.contentToString())    // => "[1, 2, 3]"  (toString도 별도)
println(a.contentHashCode())    // => 30817 (내용 기반 해시)
// println(a.toString())        // => "[I@1b6d3586" 같은 참조 문자열
```

> [!warning] 흔한 오해
> `arr1 == arr2`가 내용을 비교한다고 착각하면, 배열을 키로 쓰거나 `distinct`/`contains`에 배열을 넣을 때 조용히 잘못 동작한다. 배열은 `equals`/`hashCode`가 참조 기반이어서 `HashSet<IntArray>`도 내용이 아니라 객체의 정체성을 기준으로 동작한다.
>
> **내용을 비교해야 한다면 항상 `contentEquals`/`contentHashCode`/`contentToString`을 쓴다.** 중첩 배열에는 `contentDeepEquals`를 쓴다. 이 함정은 10장(불리언과 동등성과 동일성)에서 설명하는 `equals` 계약에서 비롯된다.

### 9.4 배열은 무공변이다: Java의 함정을 막다

Java에서 배열은 **공변**이므로 `Integer[]`를 `Object[]`에 대입할 수 있고, 그 결과 런타임에 `ArrayStoreException`이 발생할 수 있다. Kotlin은 이 구멍을 막았다. `Array<T>`는 **무공변(invariant)** 이다.

```kotlin
val strs: Array<String> = arrayOf("a", "b")
// val objs: Array<Any> = strs    // 컴파일 에러: Array<String>은 Array<Any> 아님
```

```java
// Java — 컴파일은 되지만 런타임 폭탄
Object[] objs = new String[]{"a", "b"};   // 공변 허용 (구멍)
objs[0] = 42;   // 런타임 ArrayStoreException!
```

Kotlin은 이런 잠재적 오류를 **컴파일 타임에** 막는다. 배열 공변성의 위험과 Kotlin의 무공변 선택, `Array<out T>` 프로젝션은 34장(타입 소거와 reified와 바운드)과 [[33 - 제네릭 1 - 타입 파라미터와 변성]]에서 다룬다. 여기서 기억할 것은 **배열은 List가 아닐 뿐 아니라 변성 규칙도 다르다**는 점이다(무공변 배열과 공변 `List<out T>`).

### 9.5 배열과 컬렉션을 변환하는 비용

배열과 컬렉션 사이를 변환할 때는 박싱 비용을 의식해야 한다.

```kotlin
val prim = intArrayOf(1, 2, 3)
val list: List<Int> = prim.toList()   // 원소 3개가 Integer로 박싱됨
val back: IntArray = list.toIntArray() // 다시 언박싱해 int[]로

val boxedArr: Array<Int> = prim.toTypedArray()  // int[] → Integer[] (박싱)
val primAgain: IntArray = boxedArr.toIntArray() // 다시 int[] (언박싱)
```

`IntArray.toList()`는 겉보기에는 무해하지만 원소마다 박스를 할당한다. 성능이 중요한 수치 코드에서 배열을 컬렉션 API로 처리하고 싶어지면 이렇게 숨은 박싱이 생긴다. 원시 배열은 원시 배열 API(`sum()`, `forEach`, 인덱스 루프. `map`은 박싱하므로 주의한다)로 다루는 것이 원칙이다.

## 10. 부동소수의 특이값: NaN과 무한대

### 10.1 세 가지 특이값

정수는 오버플로가 일어나면 래핑하지만, 부동소수 `Double`/`Float`는 범위를 넘거나 계산할 수 없는 결과를 **특이값**으로 표현한다. IEEE 754가 정의한 특이값은 세 가지이다.

```kotlin
println(1.0 / 0.0)               // => Infinity  (양의 무한대)
println(-1.0 / 0.0)              // => -Infinity
println(0.0 / 0.0)               // => NaN       (Not a Number)
println(Double.MAX_VALUE * 2)    // => Infinity  (오버플로 → 무한대)

println(Double.POSITIVE_INFINITY)
println(Double.NEGATIVE_INFINITY)
println(Double.NaN)
```

정수와 결정적으로 다른 점은 부동소수 산술이 **예외를 던지지 않는다**는 것이다. `0.0/0.0`은 예외 대신 `NaN`을, `1.0/0.0`은 `Infinity`를 결과로 낸다(정수 `1/0`은 예외였다, 5.4절). 이런 차이는 두 체계가 범위 초과를 처리하는 방식이 다르기 때문이다. 정수는 "닫힌 유한 고리(래핑)"이고, 부동소수는 "특이값으로 확장된 실수선(IEEE)"이다.

### 10.2 NaN은 자기 자신과 같지 않지만, 문맥에 따라 달라진다

`NaN`의 가장 유명한 성질은 **어떤 값과도, 심지어 자기 자신과도 `==`가 `false`** 라는 것이다. 하지만 Kotlin에서는 이 규칙이 정적 타입에 따라 다르게 적용된다.

```kotlin
val x = Double.NaN
println(x == x)                       // => false  (IEEE 규칙: NaN != NaN)
println(x != x)                       // => true   (NaN을 감지하는 관용구)
println(x.isNaN())                    // => true   (명시적 검사, 권장)

val a: Any = Double.NaN
val b: Any = Double.NaN
println(a == b)                       // => true   (?! Any로 보면 같다)

println(listOf(Double.NaN).contains(Double.NaN))  // => true  (컬렉션은 total order)
```

정적 타입이 `Double`이면 `==`는 IEEE 754 규칙(`NaN != NaN`)을 따른다. 하지만 값이 `Any`로 상향되거나(박싱되거나) 컬렉션 안에 있으면, Kotlin은 **total order**(모든 값에 순서를 매기는 규칙)를 써서 `NaN`이 자기 자신과 같다고 판정한다.

이처럼 부동소수 `==`가 정적 타입에 따라 IEEE 규칙과 total order 사이를 오가는 현상은 10장(불리언과 동등성과 동일성)에서 자세히 다룬다. 이 장에서는 그 원인이 **박싱**(값이 `Any`나 컬렉션으로 넘어갈 때 표현과 비교 규칙이 바뀜)이라는 점만 확인하면 충분하다.

### 10.3 `-0.0`과 `0.0`: 비트는 다르지만 값은 같다

IEEE 754에는 부호 있는 0이 있다. `0.0`과 `-0.0`은 비트 패턴이 서로 다르지만 산술적으로는 같다.

```kotlin
println(0.0 == -0.0)                  // => true   (Double로 비교: IEEE, 값 같음)
println(0.0.equals(-0.0))             // => false  (equals: total order, 비트 다름)

val z1: Any = 0.0
val z2: Any = -0.0
println(z1 == z2)                     // => false  (Any: total order로 구별)

println(1.0 / 0.0)                    // => Infinity
println(1.0 / -0.0)                   // => -Infinity  (부호 있는 0이 방향 결정)
```

`1.0 / -0.0`이 `-Infinity`인 이유는 `-0.0`이 "음의 방향에서 0에 접근한 극한"을 표현하기 때문이다. 지수와 가수의 비트 배치, 서브노멀, 반올림 모드 같은 IEEE 754의 세부 동작은 이 시리즈의 범위를 넘어서므로 데이터 표현이나 컴퓨터 구조 자료를 참고해야 한다. 이 장에서는 "부동소수의 범위 초과와 특이값은 정수의 래핑과 근본적으로 다르게 동작하며, 그 차이가 박싱과 동등성 판정에 영향을 준다"는 점만 짚어 둔다.

> [!caution] 성능 주의
> 부동소수 특이값을 `x == Double.NaN`으로 검사하면 **결과가 항상 false이므로 NaN을 절대 감지하지 못한다**(NaN != NaN). 반드시 `x.isNaN()`이나 `x != x` 관용구를 써라. 무한대는 `x.isInfinite()`로, 유한한지는 `x.isFinite()`로 검사한다. 값이 정상인지를 이 함수들로 명시적으로 검사하는 습관을 들이면 부동소수 버그의 절반을 막을 수 있다.
