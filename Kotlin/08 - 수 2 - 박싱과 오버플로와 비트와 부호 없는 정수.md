**이 장이 답하는 질문:**

- 소스에는 원시 타입이 없다는데, `val x: Int = 5`는 기계 위에서 대체 무엇으로 존재하는가? 언제 `int`이고 언제 `Integer`인가?
- `Int?`는 정말 "항상 박싱된 래퍼"인가? 이 흔한 단정은 어디까지 참이고 어디서부터 거짓인가?
- `val a: Int? = 127`은 `a === 127`이 `true`인데 `128`은 왜 `false`인가? 이 예측 불가능성의 진원지는 어디인가?
- `Int.MAX_VALUE + 1`은 예외를 던지는가, 아니면 조용히 음수로 뒤집히는가? `abs(Int.MIN_VALUE)`는 왜 음수인가?
- `1 shl 32`는 왜 `0`이 아니라 `1`인가? 시프트 횟수는 어디로 사라지는가?
- 부호 없는 정수 `UInt`는 어떤 마법으로 만들어졌는가? 왜 클래스 하나가 원시 성능을 낼 수 있는가(M39)?
- `intArrayOf(1,2,3)`과 `arrayOf(1,2,3)`은 메모리에서 무엇이 다른가? 배열은 `List`인가(M43)?
- `arr1 == arr2`는 왜 내용이 같아도 `false`가 되는가? 배열의 동등성은 왜 함정인가?

앞의 [[07 - 수 1 - Int와 Long과 부동소수점]]에서 우리는 Kotlin의 정수·부동소수 타입이 무엇이고, 왜 암시적 확대 변환이 없으며(`Int`를 `Long` 자리에 그냥 넣을 수 없다), 리터럴이 어떻게 추론되는지를 세웠다. 그 장의 마지막 못은 M4 — "Kotlin엔 원시 타입이 없다"는 오해의 교정이었다. 소스 코드에는 `int`도 `double`도 없고 오직 클래스 `Int`, `Double`만 있지만, JVM 백엔드는 가능한 곳에서 이들을 진짜 원시형 `int`, `double`으로 컴파일한다. 이 장은 바로 그 문장의 "가능한 곳에서"라는 단서를 정면으로 파고든다.

왜냐하면 "가능하지 않은 곳"이 있기 때문이다. 널을 담아야 할 때, 제네릭 타입 인자가 되어야 할 때, `Any`로 취급되어야 할 때 — Kotlin의 수는 다시 객체의 옷, 곧 **박스(box)** 를 입는다. 이 박싱과 언박싱의 경계선을 정확히 그리는 것이 이 장의 첫 번째 임무다(M5). 그리고 그 박스에는 성능을 위해 JVM이 몰래 심어 둔 캐시가 있는데, 이 캐시가 `===`(참조 동일성)의 결과를 예측 불가능하게 만든다(M48은 [[10 - 불리언과 동등성과 동일성]]이 소유하지만, 그 진원지인 박싱은 이 장이 해부한다).

수가 기계 위의 유한한 비트 패턴이라는 사실은 두 가지 결과를 더 낳는다. 하나는 **오버플로** — 유한한 비트가 넘칠 때 Kotlin은 예외를 던지지 않고 조용히 래핑(wrap)한다. 다른 하나는 그 비트 패턴을 직접 조작하는 **비트 연산**과, 부호 비트의 해석을 바꾸는 **부호 없는 정수**다. 부호 없는 정수는 Kotlin이 `value class`라는 무기로 "박싱 없는 새 수 타입"을 어떻게 사용자 코드 수준에서 지어 올렸는지를 보여주는 살아 있는 사례다([[36 - 타입 별칭과 인라인 value class]]가 그 기법을 소유한다). 마지막으로 우리는 수의 컬렉션 — **배열** — 로 내려간다. `IntArray`는 원시 배열이고 `Array<Int>`는 박스 배열이며, 둘 다 `List`가 아니다(M43).

이 장이 다루지 *않는* 것도 못박아 둔다. `Int`/`Long`/`Double`의 리터럴 문법과 확대 변환, 정수 나눗셈의 기본은 [[07 - 수 1 - Int와 Long과 부동소수점]]이 정본이다. `==`와 `===`의 완전한 의미론, `equals`/`hashCode` 계약, 박싱 캐시가 `===`를 망가뜨리는 전모(M48)는 [[10 - 불리언과 동등성과 동일성]]이 소유한다 — 여기서는 그 함정의 *원인*인 박스만 판다. `value class`의 일반 이론과 박싱 예외의 완전한 표(M39)는 [[36 - 타입 별칭과 인라인 value class]]가, 배열의 공변 함정과 타입 소거는 [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]가, 읽기 전용 컬렉션과 배열의 계약 차이(M43의 컬렉션 측면)는 [[38 - 컬렉션 - 읽기 전용과 가변]]이 소유한다. 이 장은 "수가 비트로 존재할 때의 물리학"에 집중한다.

## 1. 두 얼굴의 수 — 클래스이면서 원시형

### 1.1 소스에는 클래스, 기계에는 원시형

Kotlin 소스에서 `Int`, `Long`, `Double`, `Boolean`은 모두 **클래스**다. `5`는 `Int` 클래스의 인스턴스이고, 그 위에서 `5.toLong()`, `5.coerceAtLeast(0)`, `5.and(3)` 같은 메서드를 부를 수 있다. Java의 `int`처럼 "메서드가 없는 원시 값"이 아니다. 이것이 [[07 - 수 1 - Int와 Long과 부동소수점]]에서 세운 M4의 교정이었다: **소스 수준에서 Kotlin의 수는 온전한 객체다.**

하지만 이 "객체"를 JVM에서 매번 힙에 할당된 진짜 객체로 만든다면, 정수 하나를 더할 때마다 메모리 할당과 포인터 추적이 일어나 성능이 파국을 맞는다. 그래서 K2 컴파일러의 JVM 백엔드는 트릭을 쓴다: **표현할 수 있는 곳에서는 원시형으로 컴파일하고, 참조가 필요한 곳에서만 박스로 감싼다.**

```kotlin
val a: Int = 5            // JVM 백엔드: 원시 int
val b: Int = a + 1        // 원시 int 산술 (iadd 바이트코드)
```

```java
// 위 Kotlin이 JVM 백엔드에서 개념적으로 대응하는 Java
int a = 5;
int b = a + 1;   // 힙 할당 없음, 스택 위의 int
```

> **명세 정밀**: "원시형으로 컴파일된다"는 서술은 **JVM 백엔드에 한정**된다. Kotlin/Native는 LLVM IR 위의 값 표현을, Kotlin/JS는 자바스크립트 `number`(또는 `Long`의 경우 특수 표현)를, Kotlin/Wasm은 Wasm 수치 타입을 쓴다. 세 백엔드 모두 "박싱"의 세부는 다르다. 이 장의 박싱 논의는 특별히 언급하지 않는 한 JVM 백엔드를 기준으로 한다. 언어 명세가 보장하는 것은 *의미론*(값의 동등성·산술 결과)이지 *표현*이 아니다.

### 1.2 왜 이 이중성이 언어 설계의 승리인가

Java는 이 문제를 언어 수준에서 노출한다. Java 개발자는 `int`(원시)와 `Integer`(래퍼)를 손으로 구별하고, `List<int>`는 불가능하며 `List<Integer>`만 가능하다는 규칙을 외운다. Kotlin은 이 구별을 **타입 시스템에서 지우고 컴파일러에게 떠넘겼다.** 개발자는 언제나 `Int` 하나만 쓰고, "박스냐 원시냐"는 컴파일러가 문맥에서 결정한다.

이 설계의 대가는 딱 하나 — 개발자가 "언제 박스가 씌워지는가"를 *모르면* 성능과 동일성(`===`) 판정에서 함정에 빠진다는 것이다. 그래서 이 지식이 이 장의 핵심 자산이다. 결론부터 요약하면 이렇다:

```text
Int가 원시 int로 남는 경우            Int가 Integer 박스로 감싸지는 경우
─────────────────────────           ──────────────────────────────
지역 변수 val x: Int = 5             널 가능 타입 Int?  (널을 담으려면 참조 필요)
원시 산술 x + y, x * y               제네릭 타입 인자 List<Int>, T = Int
함수 인자/반환 fun f(n: Int)         Any/Comparable 등 상위 타입으로 상향변환
IntArray의 원소                     Array<Int>의 원소
```

이 표의 오른쪽 열이 이 장의 무대다. 하나씩 해부하자.

## 2. 박싱과 언박싱 — 박스는 언제 씌워지는가

### 2.1 박싱의 정의

**박싱(boxing)** 은 원시 값을 힙에 할당된 객체로 감싸는 것이다. JVM 백엔드에서 `Int`의 박스는 `java.lang.Integer`, `Long`의 박스는 `java.lang.Long`, `Double`의 박스는 `java.lang.Double`이다. **언박싱(unboxing)** 은 그 반대 — 박스에서 원시 값을 꺼내는 것이다.

박싱이 필요한 근본 이유는 단 하나다: **JVM의 원시형은 참조가 아니다.** 원시 `int`는 그 자체로 힙의 주소가 아니라 스택/레지스터 위의 32비트 값이다. 그런데 다음 세 가지는 모두 "참조"를 요구한다.

1. **널(null)을 담아야 할 때.** 원시 `int`에는 "값 없음"을 표현할 비트 패턴이 없다(모든 2³² 패턴이 유효한 정수다). 널은 참조 타입만의 특권이다.
2. **제네릭 타입 인자일 때.** JVM 제네릭은 타입 소거([[34 - 제네릭 2 - 타입 소거와 reified와 바운드]])로 구현되어, 모든 타입 파라미터가 `Object`로 지워진다. `Object`는 참조 타입이므로 `int`는 들어갈 수 없다.
3. **상위 타입으로 취급될 때.** `Any`, `Number`, `Comparable<Int>` 같은 상위 타입 자리에 `Int`를 넣으면, 그 자리는 참조를 기대하므로 박싱된다.

```kotlin
val primitive: Int = 42          // 원시 int
val boxed: Int? = 42             // Integer 박스 (널 담을 준비)
val asAny: Any = 42              // Integer 박스 (Any는 참조)
val inList: List<Int> = listOf(42) // 원소가 Integer 박스
```

### 2.2 박싱·언박싱은 바이트코드에서 무슨 일인가

JVM 백엔드에서 박싱은 정적 메서드 `Integer.valueOf(int)` 호출로, 언박싱은 인스턴스 메서드 `Integer.intValue()` 호출로 번역된다.

```kotlin
val n: Int = 7
val boxed: Any = n      // 박싱
val back: Int = boxed as Int   // 언박싱
```

```text
// 개념적 바이트코드
iconst_7                 // 원시 int 7을 스택에
invokestatic Integer.valueOf(int) : Integer    // ← 박싱
astore boxed
...
aload boxed
checkcast Integer
invokevirtual Integer.intValue() : int          // ← 언박싱
istore back
```

박싱은 **힙 할당**을 수반한다(캐시된 경우 제외, 3.2절). 언박싱은 할당은 없지만 메서드 호출과 널 검사를 수반한다. 뜨거운 루프에서 무심코 `Int?`나 `List<Int>`를 쓰면 매 반복마다 이 비용을 치른다.

> **성능 주의**: K2 컴파일러는 한 메서드 본문 안에서 박스-언박스가 왕복하는 경우 중간 박스를 **소거**할 수 있다. `val x: Int? = 5; val y = x!! + 1`에서 `x`를 굳이 힙에 할당했다가 즉시 꺼내지 않고, 옵티마이저가 원시 산술로 접을 수 있다. 하지만 이 최적화는 값이 메서드 경계(파라미터·필드·반환값·제네릭 슬롯)를 넘는 순간 멈춘다 — 경계에서는 표현이 고정되어야 하기 때문이다. "박싱이 성능에 나쁘다"가 항상 참은 아니지만, "경계를 넘는 박스는 실재한다"는 항상 참이다.

### 2.3 자동 박싱·언박싱은 조용하다

Kotlin은 박싱·언박싱을 **암시적으로** 삽입한다. 소스에는 아무 표시가 없다. 이것이 편의이자 함정이다.

```kotlin
fun sumList(xs: List<Int>): Int {
    var acc = 0                 // acc는 원시 int
    for (x in xs) {             // x는 List에서 꺼낼 때 언박싱
        acc += x                // 원시 산술
    }
    return acc
}
```

`List<Int>`는 원소를 `Integer`로 저장하므로, `for (x in xs)`는 매 원소마다 `intValue()`로 언박싱한다. 같은 알고리즘을 `IntArray`로 쓰면(9절) 박스가 전혀 없다. 소스는 거의 똑같아 보이지만 기계 수준에서는 딴판이다. 이 "보이지 않는 비용"을 읽어내는 눈이 이 장의 목표다.

## 3. `Int?`는 정말 항상 박싱되는가 — M5 정면 교정

### 3.1 흔한 단정과 그 반쪽 진실

인터넷과 입문서에 널리 퍼진 단정이 있다: **"`Int?`는 항상 박싱된 래퍼다."**(M5) 이 문장은 반쯤 맞고 반쯤 틀리다. 정확히 어디까지 참인지 그어 보자.

**참인 부분**: JVM 백엔드에서 정적 타입이 `Int?`인 값이 **메서드 경계를 넘거나 저장될 때**, 그 표현은 `java.lang.Integer`(박스)다. 왜냐하면 널을 표현하려면 참조가 필요하고, 원시 `int`에는 널 비트가 없기 때문이다. 함수 파라미터 `fun f(n: Int?)`, 프로퍼티 `val x: Int?`, 제네릭 슬롯 — 이 자리들에서 `Int?`는 `Integer`다.

```kotlin
class Box(val value: Int?)      // value 필드는 Integer 타입 (JVM 백엔드)
fun accept(n: Int?) { }         // 파라미터 n은 Integer 타입
```

**틀린 부분 — "항상"이 과장인 세 가지 이유**:

1. **메서드 본문 안의 지역 데이터플로에서는 박스가 소거될 수 있다.** K2 옵티마이저는 `Int?` 값이 실제로 널일 수 있는 경로와 아닌 경로를 분석해, 스마트 캐스트([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]) 이후 비-널로 좁혀진 구간에서는 원시 `int`로 유지한다. 박스는 필요한 순간(경계를 넘거나 실제로 널을 담을 때)에만 생긴다.

```kotlin
fun f(n: Int?): Int {
    if (n == null) return 0
    // 여기서 n은 스마트 캐스트로 Int (비-널). 
    // 옵티마이저는 이 구간을 원시 int로 다룰 수 있다.
    return n * 2 + n
}
```

2. **박스-언박스 왕복은 제거된다.** 2.2절에서 봤듯 한 표현식 안에서 박싱했다 즉시 언박싱하는 패턴은 옵티마이저가 접는다.

3. **비-JVM 백엔드는 Java식 박싱을 쓰지 않는다.** Kotlin/Native·JS·Wasm에서 `Int?`의 널 표현은 각 플랫폼의 방식(예: 태그된 유니온, `null`/`undefined`, 옵셔널 표현)을 따르며, "`Integer` 힙 객체"라는 개념 자체가 없다. "항상 박싱된 래퍼"라는 단정은 은연중에 JVM만 상정한 것이다(M2 — Kotlin은 JVM만의 언어가 아니다).

그래서 정확한 문장은 이렇다: **"JVM 백엔드에서 `Int?`는 값이 참조 경계를 넘는 순간 `Integer`로 박싱되지만, 지역 계산에서는 옵티마이저가 박스를 없앨 수 있고, 다른 백엔드는 아예 다른 표현을 쓴다."** "항상"이라는 단어가 이 문장을 거짓으로 만든다.

### 3.2 그럼에도 실무 규칙은 "널 가능 수는 박스라고 가정하라"

정밀한 진실이 위와 같더라도, 실무에서 성능을 걱정할 때의 안전한 어림은 여전히 "널 가능 수·제네릭에 담긴 수는 박스"다. 옵티마이저의 소거는 보장이 아니라 최선 노력이고, 경계를 넘는 순간 박스가 실재하기 때문이다. 두 문장은 모순이 아니다:

- **명세·정확성 층위**: "항상"은 틀렸다(M5). 박싱은 표현 세부이고 백엔드·문맥 의존이다.
- **성능 어림 층위**: 뜨거운 경로에서 `Int?`/`List<Int>`를 보면 "박스가 생길 수 있다"고 경계하라.

이 두 층위를 함께 쥐는 것이 프로다. "항상 박싱"이라고 외우면 왜 어떤 경우엔 박스가 안 보이는지 설명하지 못하고, "박싱 안 된다"고 방심하면 컬렉션 루프에서 GC 압력에 놀란다.

| 위치 | JVM 백엔드 표현 | 박싱? |
|------|----------------|-------|
| `val x: Int = 5` | 원시 `int` | 아니오 |
| `val x: Int? = 5` (경계·저장) | `Integer` | 예 |
| `val x: Int? = 5` 후 스마트캐스트 구간 | 원시 `int` 가능 | 옵티마이저 재량 |
| `List<Int>`의 원소 | `Integer` | 예 |
| `IntArray`의 원소 | `int` | 아니오 |
| `Any`로 상향된 `Int` | `Integer` | 예 |
| 제네릭 `fun <T> id(x: T)`에 `Int` | `Integer` | 예 |

## 4. 박싱 캐시와 `===`의 함정 — M48의 진원지

### 4.1 같은 값, 다른 박스

박싱이 힙 할당이라는 사실은 곧 **"같은 정수 값이라도 서로 다른 박스 객체가 될 수 있다"** 를 뜻한다. 그리고 참조 동일성 `===`는 "같은 객체인가"를 묻는다. 여기서 유명한 함정이 태어난다.

```kotlin
val a: Int? = 127
val b: Int? = 127
println(a == b)    // => true   (구조적 동등: 값이 같다)
println(a === b)   // => true   (?! 같은 박스 객체다)

val c: Int? = 128
val d: Int? = 128
println(c == d)    // => true   (값이 같다)
println(c === d)   // => false  (?! 다른 박스 객체다)
```

`127`은 `===`가 `true`인데 `128`은 `false`다. 값은 똑같이 서로 같은데, 참조 동일성만 갈린다. 이유는 순수하게 **JVM의 박싱 구현 세부**에 있다.

### 4.2 `Integer.valueOf`의 캐시

JVM 백엔드에서 박싱은 `Integer.valueOf(int)`를 호출한다. 그런데 이 메서드는 `java.lang.Integer`의 명세상 **-128부터 127까지의 값에 대해 캐시된 인스턴스를 재사용**한다. 즉 이 범위 안의 정수를 박싱하면 항상 같은 싱글턴 박스가 나오고, 범위를 벗어나면 매번 새 박스를 할당한다.

```text
Integer.valueOf(127)  →  캐시 배열의 고정 인스턴스 (항상 동일 객체)
Integer.valueOf(128)  →  new Integer(128)  (매번 새 객체)
```

그래서 `127`은 두 변수가 같은 캐시 객체를 가리켜 `===`가 `true`, `128`은 서로 다른 새 객체라 `false`가 된다. 이것은 정수의 성질도 Kotlin 언어의 규칙도 아니고, `java.lang.Integer`라는 **표준 라이브러리 클래스의 최적화**일 뿐이다.

> **명세 정밀**: 캐시 하한 -128과 상한 127 중 하한은 고정이지만, 상한은 JVM 옵션 `-XX:AutoBoxCacheMax`로 늘릴 수 있어 실제 경계는 실행 환경에 따라 달라질 수 있다. 그러므로 "128부터 `===`가 false"조차 이식성 있는 규칙이 아니다. `Long` 박스(`Long.valueOf`)도 -128..127 캐시를, `Boolean`·`Byte`·`Char`(0..127)·`Short`(-128..127)도 유사한 캐시를 갖지만 **`Float`·`Double`은 캐시가 없다.** 세부는 [[45 - Java 상호운용]]의 표준 라이브러리 계약에 달려 있다.

### 4.3 교훈 — 수의 동일성을 `===`로 묻지 마라

이 함정의 완전한 해부 — `==`가 어떻게 `equals`로 탈설탕되는지, `===`가 언제 의미가 있고 언제 없는지, 왜 원시로 컴파일되는 값에서 `===`가 예측 불가능한지 — 는 M48로서 [[10 - 불리언과 동등성과 동일성]]이 소유한다. 이 장에서 우리가 확인한 것은 그 함정의 **물리적 진원지**다: 박스는 힙 객체이고, JVM은 작은 정수 박스를 캐시하며, 그래서 참조 동일성이 값에 따라 널뛴다.

실무 규칙은 짧다: **수의 "같음"은 언제나 `==`로 물어라.** `===`로 수를 비교하는 것은 거의 항상 버그다(캐시 범위 안에서 우연히 맞아 더 위험하다). 이 규칙은 박싱이라는 표현 세부에 코드가 의존하지 않게 하는 방어선이다.

```kotlin
val a: Int? = 1000
val b: Int? = 1000
// if (a === b) ...   // 함정: 1000은 캐시 밖 → false. 값 비교가 의도라면 버그.
if (a == b) { }       // 올바름: 값이 같은가를 묻는다
```

## 5. 오버플로 — 조용한 래핑의 세계

### 5.1 유한한 비트는 넘친다, 그러나 예외는 없다

`Int`는 32비트, `Long`은 64비트다. 유한한 비트는 표현 범위가 유한하다: `Int`는 $-2^{31}$부터 $2^{31}-1$까지, 곧 `-2147483648`부터 `2147483647`까지다. 이 범위를 벗어나는 산술을 하면 어떻게 될까? **Kotlin은 예외를 던지지 않는다. 조용히 2의 보수(two's complement) 규칙으로 래핑한다.**

```kotlin
val max = Int.MAX_VALUE          // 2147483647
println(max + 1)                 // => -2147483648  (Int.MIN_VALUE로 뒤집힘!)
println(max * 2)                 // => -2  
println(Int.MIN_VALUE - 1)       // => 2147483647   (반대편으로 되감김)
```

`2147483647 + 1`이 예외가 아니라 `-2147483648`이 된다. 32비트가 넘쳐 최상위 비트(부호 비트)로 캐리(carry)가 흘러들어가 값이 음수로 뒤집힌 것이다. 수학적으로는 결과가 $\bmod\ 2^{32}$로 접힌다:

$$(2147483647 + 1) \bmod 2^{32} = 2^{31} \equiv -2^{31} \pmod{2^{32}}$$

> **역사 메모**: 조용한 래핑은 게으름이 아니라 JVM 정수 산술 의미론을 그대로 따른 것이다. JVM 바이트코드 `iadd`, `imul` 등은 오버플로를 검사하지 않고 하위 32비트만 남긴다. Kotlin이 매 산술마다 오버플로 검사를 넣었다면 성능이 크게 떨어졌을 것이다. 언어는 "빠른 기본값, 필요하면 명시적 검사"를 택했다. 이는 대부분의 시스템 언어(C, Java, Go 등 부호 있는 정수)와 같은 선택이다.

### 5.2 오버플로가 만드는 고전적 버그들

**(1) 두 큰 정수의 평균.** `(a + b) / 2`는 `a + b`가 오버플로하면 틀린다. 이진 탐색의 중간 인덱스 계산에서 유명한 버그다.

```kotlin
val a = 2_000_000_000
val b = 2_000_000_000
println((a + b) / 2)          // => -147483648  (오버플로! 음수)
println(a + (b - a) / 2)      // => 2000000000  (안전한 관용구)
```

**(2) `abs(Int.MIN_VALUE)`는 음수다.** 이것이 가장 반직관적인 함정이다. 범위가 비대칭이기 때문이다: `Int.MIN_VALUE`는 `-2147483648`인데 그 절댓값 `2147483648`은 `Int.MAX_VALUE`(`2147483647`)를 넘어 표현할 수 없다. 그래서 `abs`는 자기 자신을 돌려준다.

```kotlin
import kotlin.math.abs
println(abs(Int.MIN_VALUE))   // => -2147483648  (여전히 음수!)
println(-Int.MIN_VALUE)       // => -2147483648  (부호 반전도 실패)
```

부호 있는 2의 보수는 음수가 양수보다 하나 더 많다($-2^{31}$개 vs $2^{31}-1$개). 그 "하나 더"인 `MIN_VALUE`가 짝을 잃은 고아라서, 부호 반전과 절댓값이 그 위에서 깨진다.

**(3) `Int.MIN_VALUE / -1`.** 나눗셈도 오버플로할 수 있는 유일한 경우다. `-2147483648 / -1`의 참값은 `2147483648`인데 범위를 넘으므로 다시 `MIN_VALUE`로 래핑된다(JVM에서 예외 없이).

```kotlin
println(Int.MIN_VALUE / -1)   // => -2147483648  (오버플로, 예외 아님)
```

### 5.3 검사가 필요하면 명시적으로 — `Math.*Exact`

오버플로를 조용히 넘기고 싶지 않다면 JVM 백엔드에서는 `java.lang.Math`의 `*Exact` 계열이 오버플로 시 `ArithmeticException`을 던진다.

```kotlin
println(Math.addExact(Int.MAX_VALUE, 1))
// 컴파일 에러 아님. 런타임에 ArithmeticException: integer overflow

println(Math.multiplyExact(100_000, 100_000)) // 예외 (Int 범위 초과)
println(Math.toIntExact(3_000_000_000L))       // 예외 (Long→Int 축소 오버플로)
```

> **명세 정밀**: `Math.addExact` 등은 JVM 표준 라이브러리 함수이므로 **JVM 백엔드 전용**이다. 멀티플랫폼 공통 코드에서 오버플로 검사가 필요하면, 더 넓은 타입(`Long`)으로 승격해 계산 후 범위를 직접 확인하거나, 부호 없는 정수(7절)로 의미를 명확히 하는 방법을 쓴다. Kotlin 표준 라이브러리 자체에는 크로스플랫폼 "checked arithmetic" 연산자가 언어 기본으로 들어 있지 않다.

### 5.4 나눗셈 0의 두 얼굴

오버플로와 나란히 알아둘 것이 0으로 나누기다. **정수와 부동소수의 동작이 다르다.**

```kotlin
// println(5 / 0)          // 런타임 ArithmeticException: / by zero
// println(5 % 0)          // 런타임 ArithmeticException

println(5.0 / 0.0)         // => Infinity        (예외 아님)
println(-5.0 / 0.0)        // => -Infinity
println(0.0 / 0.0)         // => NaN
```

정수 나눗셈 `/ 0`은 예외를 던지지만, 부동소수 `/ 0.0`은 IEEE 754 규칙에 따라 `Infinity`나 `NaN`을 낳는다(예외 없음). 이 비대칭은 부동소수의 특이값 세계로 이어진다(10절).

## 6. 비트 연산 — 비트 패턴을 직접 만지기

### 6.1 Kotlin의 비트 연산자는 연산자가 아니라 중위 함수다

많은 언어에서 비트 연산은 기호(`&`, `|`, `^`, `<<`, `>>`)다. Kotlin은 이 기호들을 **쓰지 않는다.** 대신 `Int`와 `Long`의 **중위(infix) 함수**로 제공한다. 이것은 [[19 - 연산자 오버로딩과 관례]]에서 볼 "관례 함수 이름"과는 다른 선택 — 비트 연산은 오버로딩 가능한 연산자가 아니라 이름 붙은 함수다.

```kotlin
val flags = 0b1010
println(flags and 0b0110)   // => 2   (0b0010, 비트 AND)
println(flags or 0b0110)    // => 14  (0b1110, 비트 OR)
println(flags xor 0b0110)   // => 12  (0b1100, 비트 XOR)
println(flags.inv())        // => -11 (모든 비트 반전; inv는 중위 아님, 단항 함수)
println(flags shl 2)        // => 40  (왼쪽 시프트 2칸)
println(flags shr 1)        // => 5   (부호 유지 오른쪽 시프트)
println(flags ushr 1)       // => 5   (부호 무시 오른쪽 시프트)
```

| 함수 | 의미 | 형태 | 정의 대상 |
|------|------|------|-----------|
| `and` | 비트 AND | 중위 | Int, Long, (Boolean) |
| `or` | 비트 OR | 중위 | Int, Long, (Boolean) |
| `xor` | 비트 XOR | 중위 | Int, Long, (Boolean) |
| `inv()` | 비트 NOT(1의 보수) | 단항 메서드 | Byte, Short, Int, Long |
| `shl` | 왼쪽 시프트 | 중위 | Int, Long |
| `shr` | 산술 오른쪽 시프트(부호 유지) | 중위 | Int, Long |
| `ushr` | 논리 오른쪽 시프트(0 채움) | 중위 | Int, Long |

> **흔한 오해**: "비트 연산은 모든 정수 타입에 있다"는 틀렸다. 표준 라이브러리에서 `shl`/`shr`/`ushr`/`and`/`or`/`xor`는 **`Int`와 `Long`에만** 정의된다. `Byte`와 `Short`에는 비트 중위 함수가 없다 — 먼저 `toInt()`로 승격해야 한다. `Boolean`에는 `and`/`or`/`xor`/`not()`이 있지만(논리 연산, [[10 - 불리언과 동등성과 동일성]]) 시프트는 없다. `UInt`/`ULong`에도 비트 함수가 있다(7절).

```kotlin
val b: Byte = 0b0110
// println(b and 0b0010)   // 컴파일 에러: Byte에 and 없음
println(b.toInt() and 0b0010)  // => 2   (Int로 승격 후)
```

### 6.2 `shr` vs `ushr` — 부호 비트의 운명

오른쪽 시프트가 두 개인 이유는 **부호 비트**를 어떻게 처리하느냐다. `shr`(산술 시프트)는 최상위 부호 비트를 복제해 채운다 → 음수는 음수로 남는다. `ushr`(논리 시프트)는 항상 0을 채운다 → 음수의 부호 비트가 밀려나며 큰 양수가 된다.

```kotlin
val neg = -8                       // 0b111...11111000 (32비트, 상위 다 1)
println(neg shr 1)                 // => -4   (부호 유지: 상위에 1 채움)
println(neg ushr 1)                // => 2147483644  (0 채움 → 거대 양수)

println((-1) shr 31)               // => -1   (부호 비트 계속 복제)
println((-1) ushr 31)             // => 1    (0 채우니 최하위 1비트만 남음)
```

```text
-8을 32비트로:  1111 1111 ... 1111 1000
shr 1 (부호): 1111 1111 ... 1111 1100  = -4
ushr 1 (0):  0111 1111 ... 1111 1100  = 2147483644
```

`ushr`은 부호 없는 정수가 없던 시절 "비트를 부호 없이 다루는" 유일한 도구였다. 이제는 `UInt`(7절)가 더 명확한 대안이다.

### 6.3 시프트 횟수는 마스킹된다 — `1 shl 32 == 1`

가장 반직관적인 함정. **시프트 횟수가 비트 폭 이상이면 "그만큼 다 밀려 0이 되는" 게 아니라, 횟수가 비트 폭으로 나눈 나머지로 접힌다.**

```kotlin
println(1 shl 32)    // => 1    (32칸이 아니라 32 mod 32 = 0칸 시프트!)
println(1 shl 33)    // => 2    (33 mod 32 = 1칸)
println(1 shl -1)    // => -2147483648  (-1 mod 32 → 31칸, 부호비트로)

println(1L shl 64)   // => 1    (Long은 64로 마스킹: 64 mod 64 = 0)
println(1L shl 65)   // => 2    (65 mod 64 = 1)
```

이유는 JVM 시프트 명령의 정의다: `Int` 시프트(`ishl`/`ishr`/`iushr`)는 시프트 횟수의 **하위 5비트만** 사용한다($\bmod\ 32$). `Long` 시프트(`lshl` 등)는 하위 6비트($\bmod\ 64$). Kotlin의 `shl` 등은 이 JVM 의미론을 그대로 노출한다.

$$\text{shift count 실제값} = n \bmod 32 \quad (\text{Int}), \qquad n \bmod 64 \quad (\text{Long})$$

> **성능 주의**: 이 마스킹 때문에 "가변 비트 폭 시프트"를 짤 때 `x shl width`에서 `width == 32`(Int)나 `width == 64`(Long)를 특수 처리하지 않으면, 0을 기대한 자리에서 원본이 그대로 튀어나온다. 비트 마스크·해시 함수·직렬화 코드에서 조용한 버그의 단골이다.

### 6.4 표준 라이브러리 비트 유틸리티

Kotlin 1.5부터 정수 타입에 여러 비트 조작 함수가 안정 API로 들어왔다(`kotlin.experimental` 딱지 없이 사용).

```kotlin
println(0b10110.countOneBits())        // => 3   (1인 비트 수, popcount)
println(1.countLeadingZeroBits())      // => 31  (최상위부터 0의 개수, Int는 32비트)
println(8.countTrailingZeroBits())     // => 3   (최하위부터 0의 개수)
println(0b10110.takeHighestOneBit())   // => 16  (가장 높은 1비트만 남김)
println(0b10110.takeLowestOneBit())    // => 2   (가장 낮은 1비트만 남김)
println(1.rotateLeft(4))               // => 16  (회전 시프트, 밀린 비트가 반대편으로)
println(Int.MIN_VALUE.rotateLeft(1))   // => 1   (부호비트가 최하위로 회전)
```

이들은 마스킹·플래그·비트셋·저수준 최적화에서 손으로 짜던 관용구를 대체한다. JVM 백엔드에서는 대체로 `Integer.bitCount` 같은 인트린식으로 컴파일되어 빠르다.

### 6.5 실전 — 비트 플래그로 상태를 한 정수에 담기

비트 연산의 대표적 쓸모는 여러 개의 불리언 상태를 하나의 정수에 **플래그(flag)** 로 압축하는 것이다. 각 비트가 하나의 참/거짓을 뜻한다. 동물의 특성을 예로 들자 — 날 수 있는가, 헤엄칠 수 있는가, 야행성인가, 독이 있는가를 4비트에 담는다.

```kotlin
const val CAN_FLY   = 1 shl 0   // 0b0001
const val CAN_SWIM  = 1 shl 1   // 0b0010
const val NOCTURNAL = 1 shl 2   // 0b0100
const val VENOMOUS  = 1 shl 3   // 0b1000

// 박쥐: 날 수 있고 야행성
val bat = CAN_FLY or NOCTURNAL      // 0b0101 = 5

fun has(traits: Int, flag: Int): Boolean = (traits and flag) != 0
fun add(traits: Int, flag: Int): Int = traits or flag
fun remove(traits: Int, flag: Int): Int = traits and flag.inv()
fun toggle(traits: Int, flag: Int): Int = traits xor flag

println(has(bat, CAN_FLY))          // => true   (AND으로 비트 존재 확인)
println(has(bat, CAN_SWIM))         // => false
val bat2 = add(bat, VENOMOUS)       // 독 추가 → 0b1101
println(has(bat2, VENOMOUS))        // => true
val bat3 = remove(bat2, NOCTURNAL)  // 야행성 제거 → 0b1001
println(has(bat3, NOCTURNAL))       // => false
println(bat.countOneBits())         // => 2   (켜진 특성 수)
```

각 연산의 비트 논리를 정리하면:

| 연산 | 비트 관용구 | 원리 |
|------|-------------|------|
| 켜짐 검사 | `(traits and flag) != 0` | AND로 해당 비트만 남겨 0 여부 확인 |
| 추가 | `traits or flag` | OR로 비트를 1로 |
| 제거 | `traits and flag.inv()` | 마스크를 반전해 AND → 해당 비트만 0으로 |
| 토글 | `traits xor flag` | XOR는 1과 만나면 반전 |

`inv()`가 제거에서 왜 필요한지 보자. `VENOMOUS`는 `0b1000`이고 `inv()`하면 `0b…11110111`(그 비트만 0, 나머지 전부 1)이 된다. 이것과 AND하면 그 비트만 지워지고 나머지는 보존된다. 이 관용구는 파일 권한(rwx), 네트워크 프로토콜 플래그, 그래픽 상태 비트 등 도처에 있다.

> **성능 주의**: 비트 플래그는 극도로 조밀하고 빠르지만(정수 하나 = 32개 불리언), 가독성을 희생한다. 플래그 수가 적고 성능이 임계적일 때만 쓰고, 그 외에는 `Set<Enum>`이나 데이터 클래스의 `Boolean` 프로퍼티가 명확하다. JVM의 `EnumSet` 같은 추상화는 타입 안전하면서 내부적으로 이 비트 트릭을 쓴다 — 추상화의 이점을 공짜로 얻는 셈이다.

### 6.6 XOR의 성질 — 원상복귀와 토글

`xor`은 특별한 대수적 성질을 갖는다: `a xor a == 0`, `a xor 0 == a`, 그리고 결합·교환 법칙이 성립한다. 이 성질에서 몇 가지 관용구가 나온다.

```kotlin
val a = 0b1100
println(a xor a)                    // => 0    (자기 자신과 XOR = 0)
println(a xor 0)                    // => 12   (0과 XOR = 자기 자신)
println((a xor 0b1010) xor 0b1010)  // => 12   (같은 값 두 번 XOR = 원상복귀)
```

"같은 값을 두 번 XOR하면 원래로 돌아온다"는 성질($ (a \oplus k) \oplus k = a $)은 단순 마스킹·체크섬·토글의 바탕이다. 앞 6.5절의 `toggle`이 바로 이 성질을 쓴다 — 같은 플래그를 두 번 토글하면 원상태로 돌아온다. XOR의 이 가역성은 비트 연산 중 유일하게 "정보를 잃지 않는" 성질이라, 되돌릴 수 있는 변환이 필요한 곳에서 특별한 자리를 차지한다.

## 7. 부호 없는 정수 — value class가 지어 올린 새 수

### 7.1 왜 부호 없는 정수가 필요한가

부호 있는 `Int`는 최상위 비트를 부호로 쓰기 때문에, 32비트를 전부 크기에 쓰는 값(예: `0xFFFFFFFF` = 4294967295)을 담지 못하고 `-1`로 해석한다. 바이트 스트림, 색상 값(`0xFFRRGGBB`), 해시, 네트워크 프로토콜의 부호 없는 필드를 다룰 때 이 부호 해석이 걸림돌이 된다. 그래서 Kotlin은 네 개의 부호 없는 정수 타입을 제공한다:

| 타입 | 비트 | 범위 | 대응 부호 타입 |
|------|------|------|----------------|
| `UByte` | 8 | 0 .. 255 | `Byte` |
| `UShort` | 16 | 0 .. 65535 | `Short` |
| `UInt` | 32 | 0 .. 4294967295 | `Int` |
| `ULong` | 64 | 0 .. 18446744073709551615 | `Long` |

```kotlin
val u: UInt = 4_294_967_295u        // Int로는 불가능한 값
println(u)                          // => 4294967295
println(u + 1u)                     // => 0   (오버플로 래핑: mod 2^32)
println(0u - 1u)                    // => 4294967295  (부호 없는 되감김)

val color: UInt = 0xFF3366FFu
val alpha = (color shr 24) and 0xFFu  // => 255u
```

리터럴은 접미사 `u`/`U`로 표기하고, `ULong`은 `uL`을 쓴다: `100uL`, `0xFFu`, `255U`.

### 7.2 마법의 정체 — `@JvmInline value class`

부호 없는 정수의 놀라운 점은 이것이 **언어 기본 원시 타입이 아니라, 표준 라이브러리가 `value class`로 정의한 사용자 수준 타입**이라는 것이다. 개념적으로 `UInt`의 정의는 이렇게 생겼다:

```kotlin
// 표준 라이브러리의 개념적 정의 (실제 시그니처를 단순화)
@JvmInline
value class UInt internal constructor(private val data: Int) {
    operator fun plus(other: UInt): UInt = UInt(this.data + other.data)
    operator fun compareTo(other: UInt): Int = 
        Integer.compareUnsigned(this.data, other.data)  // JVM: 부호 없이 비교
    override fun toString(): String = 
        Integer.toUnsignedString(data)                   // JVM: 부호 없이 문자열화
    // ...
}
```

핵심은 **`UInt`가 내부적으로 `Int`를 그대로 감싸되, 그 비트를 부호 없이 재해석한다**는 것이다. `UInt`의 최댓값 `4294967295u`는 내부 `Int`로는 `-1`이다(비트 패턴 `0xFFFFFFFF`가 동일). 저장 비트는 같고, 연산 규칙만 바꾼다.

- `plus`: 비트 덧셈은 부호 유무와 무관하게 같다(2의 보수의 아름다움). 그래서 그냥 `Int`의 `+`를 쓴다.
- `compareTo`: 부호 있는 비교와 다르다 → JVM 백엔드에서 `Integer.compareUnsigned`로 위임.
- `div`/`rem`: 부호 없는 나눗셈 → `Integer.divideUnsigned`/`remainderUnsigned`.
- `toString`: `Integer.toUnsignedString`.

> **명세 정밀**: `Integer.compareUnsigned` 같은 위임은 **JVM 백엔드**의 구현이다. 다른 백엔드는 같은 *의미론*을 각자의 방식으로 구현한다. 언어가 보장하는 것은 "`UInt`는 0..2³²−1 범위에서 부호 없는 산술 의미론을 갖는다"이지, "내부적으로 `Integer.compareUnsigned`를 부른다"가 아니다.

### 7.3 value class이기에 — 대개 언박싱, 그러나 조건부 박싱(M39)

`value class`의 이점은 **런타임에 래퍼 객체 없이 내부 값으로 표현된다**는 것이다. `UInt`는 대부분의 문맥에서 그냥 원시 `int`로 컴파일되어, 힙 할당도 박싱도 없다. `@JvmInline`이 그 인라이닝을 지시한다.

```kotlin
fun brightness(color: UInt): UInt {   // 파라미터·반환이 원시 int로 인라인 (JVM)
    val r = (color shr 16) and 0xFFu
    val g = (color shr 8) and 0xFFu
    val b = color and 0xFFu
    return (r + g + b) / 3u
}
```

하지만 `value class`도 **박싱을 완전히 피하지는 못한다.** 다음 경우 `UInt`는 래퍼 객체로 박싱된다:

1. **널 가능(`UInt?`)** — 널 표현을 위해 박스 필요(3절과 같은 이유).
2. **제네릭 타입 인자(`List<UInt>`, `T = UInt`)** — 타입 소거로 참조 필요.
3. **상위 타입으로 상향(`Any`, `Comparable<UInt>`)** — 참조 자리.
4. **컬렉션·배열에 담길 때**(전용 `UIntArray` 제외).

이것이 M39("value class는 항상 박싱을 없앤다"는 오해)의 실사례다. 완전한 언박싱 조건표와 그 이론은 [[36 - 타입 별칭과 인라인 value class]]가 소유한다. 여기서 기억할 것은 **부호 없는 정수도 결국 value class라, 원시 `Int`와 정확히 같은 박싱 규칙을 따른다**는 통일성이다.

### 7.4 부호 없는 배열과 변환

박싱 없이 부호 없는 정수를 대량으로 담으려면 전용 배열 타입 `UByteArray`, `UShortArray`, `UIntArray`, `ULongArray`가 있다(이들도 안정 API). `List<UInt>`가 원소를 박싱하는 것과 대비된다(9절).

```kotlin
val bytes: UByteArray = ubyteArrayOf(0xDEu, 0xADu, 0xBEu, 0xEFu)
val nums: UIntArray = UIntArray(4) { (it * it).toUInt() }
```

변환은 두 갈래다. **비트 재해석**(`toUInt`/`toInt`)과 **값 변환**은 구별해야 한다.

```kotlin
val signed: Int = -1
println(signed.toUInt())          // => 4294967295  (비트 그대로 재해석)
println(signed.toUInt().toInt())  // => -1          (왕복하면 원상복귀)

val big: UInt = 300u
println(big.toByte())             // => 44  (300 mod 256, 하위 8비트만)
println(big.toUByte())            // => 44u (부호 없는 축소도 하위 8비트)
```

### 7.5 실전 — 부호 없는 바이트로 색상 채널 다루기

부호 없는 정수가 진가를 발휘하는 곳은 "비트가 곧 데이터"인 영역이다. 32비트 색상 `0xAARRGGBB`(알파·빨강·초록·파랑 각 8비트)를 부호 걱정 없이 분해·합성해 보자.

```kotlin
fun channels(argb: UInt): List<UByte> = listOf(
    ((argb shr 24) and 0xFFu).toUByte(),   // 알파
    ((argb shr 16) and 0xFFu).toUByte(),   // 빨강
    ((argb shr 8) and 0xFFu).toUByte(),    // 초록
    (argb and 0xFFu).toUByte(),            // 파랑
)

fun compose(a: UByte, r: UByte, g: UByte, b: UByte): UInt =
    (a.toUInt() shl 24) or (r.toUInt() shl 16) or (g.toUInt() shl 8) or b.toUInt()

val orange: UInt = 0xFFFF8800u
println(channels(orange))                  // => [255, 255, 136, 0]
println(compose(255u, 255u, 136u, 0u) == orange)  // => true
```

같은 코드를 부호 있는 `Int`로 짜면 `0xFFFF8800`이 음수(`-30720`)로 해석되어, `shr`이 부호 비트를 복제하며 상위 채널이 오염된다(그래서 Java에서는 `>>>`(ushr)를 강박적으로 써야 했다). `UInt`는 부호 비트라는 개념 자체가 없어 `shr`이 항상 0을 채우므로, 이 오염이 원천적으로 사라진다. **의미가 부호 없는 데이터라면, 부호 없는 타입을 써서 그 의미를 타입에 새기는 것**이 이 기능의 존재 이유다.

> **역사 메모**: 부호 없는 정수는 Kotlin 1.3(2018)에서 **실험적(experimental)** 기능으로 도입되어, `@ExperimentalUnsignedTypes` opt-in을 요구했다. 오랜 설계·피드백 끝에 **Kotlin 1.5(2021)에서 안정(stable)화**되었다. `value class`(역시 1.5에서 `inline class`를 계승해 안정화)가 그 구현 토대다. 이 진화 경로 — 실험적 도입 → opt-in → 안정화 — 는 Kotlin이 언어를 확장하는 표준 절차이며 [[46 - 멀티플랫폼과 진화와 어두운 구석]]이 그 제도를 소유한다.

## 8. 진법과 변환 — 리터럴에서 문자열까지

### 8.1 정수 리터럴의 진법 표기

Kotlin은 세 가지 진법 리터럴을 지원한다. 특이하게 **8진법(octal) 리터럴은 없다.**

```kotlin
val dec = 255            // 10진
val hex = 0xFF           // 16진 (0x/0X 접두)
val bin = 0b1111_1111    // 2진 (0b/0B 접두)
// val oct = 0o377       // 컴파일 에러: Kotlin에 8진 리터럴 없음
// val bad = 0377        // 컴파일 에러: 선행 0 리터럴 금지(8진 오해 방지)
```

숫자 사이에 `_`(밑줄)를 자릿수 구분자로 넣을 수 있다: `1_000_000`, `0xFF_EC_DE_5E`, `0b0100_1101`. 밑줄은 값에 영향을 주지 않고 가독성만 높인다.

> **역사 메모**: C·Java는 선행 `0`을 8진법으로 해석한다(`0377` == 255). 이는 `010`이 8인지 10인지 헷갈리는 악명 높은 버그원이었다. Kotlin은 이 함정을 아예 제거했다 — 선행 0으로 시작하는 정수 리터럴은 **문법 오류**다(단, `0` 자체와 `0.5` 같은 소수는 예외). 8진이 필요하면 명시적으로 파싱해야 한다.

### 8.2 문자열 ↔ 수: 진법 변환

`toString(radix)`로 임의 진법 문자열을 만들고, `toInt(radix)`/`toLong(radix)`로 파싱한다.

```kotlin
println(255.toString(16))        // => "ff"
println(255.toString(2))         // => "11111111"
println(255.toString(8))         // => "377"  (8진 리터럴은 없어도 변환은 됨)

println("ff".toInt(16))          // => 255
println("11111111".toInt(2))     // => 255
println("z".toInt(36))           // => 35   (radix는 2..36)

// println("ff".toInt())         // 런타임 NumberFormatException (기본 10진)
println("ff".toIntOrNull(16))    // => 255
println("xyz".toIntOrNull(16))   // => null (실패 시 예외 대신 null)
```

`radix`는 2부터 36까지(0-9와 a-z를 자릿수로 사용). 범위를 벗어나면 예외다. 파싱 실패 시 `toInt`는 `NumberFormatException`을 던지고, `toIntOrNull`은 `null`을 돌려준다 — 후자가 방어적 파싱에 안전하다.

### 8.3 부호 없는 문자열화의 함정

부호 있는 값을 16진 문자열로 만들 때, 음수는 부호를 붙여 나온다. 부호 없는 비트 표현을 원하면 `UInt`를 거쳐야 한다.

```kotlin
println((-1).toString(16))            // => "-1"   (부호 있는 해석)
println((-1).toUInt().toString(16))   // => "ffffffff"  (부호 없는 32비트)

// JVM 백엔드 대안:
println(Integer.toHexString(-1))      // => "ffffffff"  (Java 유틸, JVM 전용)
println(Integer.toBinaryString(5))    // => "101"
```

`(-1).toString(16)`이 `"-1"`인 것은 논리적으로 옳다 — `-1`이라는 *값*을 16진으로 쓴 것이니까. 하지만 "이 정수의 비트를 16진으로 보고 싶다"면 `toUInt()`로 부호 해석을 벗겨야 `"ffffffff"`가 나온다. 이 구별을 놓치면 로그·직렬화에서 음수가 이상하게 찍힌다.

## 9. 배열 — 원시 배열과 박스 배열, 그리고 배열은 List가 아니다(M43)

### 9.1 `Array<T>`와 `IntArray`는 다른 타입이다

수를 여러 개 담는 가장 낮은 수준의 그릇이 배열이다. Kotlin에는 두 계열이 있고, 이 둘은 **메모리 레이아웃이 근본적으로 다르다.**

- **`Array<T>`**: 제네릭 참조 배열. 원소가 참조(객체)다. `Array<Int>`는 원소가 `Integer` **박스**다. JVM 백엔드에서 `Integer[]`.
- **`IntArray`, `LongArray`, `DoubleArray`, `ByteArray`, `ShortArray`, `CharArray`, `FloatArray`, `BooleanArray`**: 원시 배열. 원소가 원시 값으로 촘촘히 박힌다. JVM 백엔드에서 `int[]`, `long[]` 등. **박싱 없음.**

```kotlin
val boxed: Array<Int> = arrayOf(1, 2, 3)     // Integer[] — 원소마다 박스
val prim: IntArray = intArrayOf(1, 2, 3)     // int[] — 박스 없음
```

```text
Array<Int> (Integer[])            IntArray (int[])
┌───┐ ┌───┐ ┌───┐                ┌───┬───┬───┐
│ • │ │ • │ │ • │   참조 배열     │ 1 │ 2 │ 3 │  값이 촘촘
└─┬─┘ └─┬─┘ └─┬─┘                └───┴───┴───┘
  ▼     ▼     ▼
 [1]   [2]   [3]  힙에 흩어진 박스
```

`Array<Int>`는 원소 하나마다 별도의 `Integer` 객체를 힙에 두고, 배열은 그 객체들의 주소를 담는다. 캐시 지역성이 나쁘고 GC 압력이 크다. `IntArray`는 `int` 값이 배열 안에 연속으로 박혀 있어 캐시 친화적이고 할당이 없다. **수의 대량 저장에는 원시 배열을 써라** — 이것이 `IntArray` 등이 존재하는 유일한 이유다.

```kotlin
val a = IntArray(5)                    // [0, 0, 0, 0, 0]
val b = IntArray(5) { it * it }        // [0, 1, 4, 9, 16]
val c = intArrayOf(3, 1, 4, 1, 5)
val d = Array(5) { "item$it" }         // Array<String>, 참조 배열은 이쪽
```

### 9.2 배열은 List가 아니다 — M43 정면 교정

**"Kotlin 배열은 List다"는 흔한 오해다(M43).** `Array<T>`도 `IntArray`도 `List`가 아니며, `List` 인터페이스를 구현하지도 않는다. 셋은 완전히 다른 타입 계약을 갖는다.

```kotlin
val arr: IntArray = intArrayOf(1, 2, 3)
// val list: List<Int> = arr        // 컴파일 에러: IntArray는 List가 아니다
val list: List<Int> = arr.toList()  // 명시적 변환 필요 (원소를 박싱함!)

val objArr: Array<Int> = arrayOf(1, 2, 3)
// val list2: List<Int> = objArr    // 컴파일 에러: Array<Int>도 List 아님
```

셋의 계약 차이를 표로 못박자:

| 성질 | `IntArray` | `Array<T>` | `List<T>` |
|------|-----------|-----------|-----------|
| 크기 | 고정 | 고정 | 읽기전용 뷰(가변 구현은 변경 가능) |
| 원소 변경 | 가능(`arr[0] = 9`) | 가능 | `List`는 불가, `MutableList`만 |
| 원소 표현 | 원시(박스 없음) | 참조(박스) | 참조(박스) |
| `==` 의미 | 참조 동일성 | 참조 동일성 | 구조적 동등 |
| 변성 | 무공변 | 무공변 | 공변(`out`) |
| 최상위 타입 | `Any` | `Any` | `Collection`→`Iterable` |

`List`는 크기 변경이 불가한 **읽기 전용 인터페이스**이고(M26, [[38 - 컬렉션 - 읽기 전용과 가변]]), 배열은 **크기 고정이지만 원소는 언제나 변경 가능한** 저수준 저장소다. `Array<T>`는 인덱스 대입 `arr[i] = x`가 항상 되지만 `add`/`remove`는 없다. `List`는 그 반대 성격 — 읽기는 되지만 원소 대입조차 인터페이스에 없다. 이 대비는 M43과 M26을 나란히 이해하는 열쇠다.

### 9.3 배열의 동등성 함정 — `==`는 내용을 보지 않는다

가장 아픈 함정. 배열은 `equals`를 재정의하지 않으므로 `==`가 **참조 동일성**(같은 배열 객체인가)을 검사한다. 내용이 똑같아도 서로 다른 배열이면 `false`다.

```kotlin
val a = intArrayOf(1, 2, 3)
val b = intArrayOf(1, 2, 3)
println(a == b)                 // => false  (?! 내용은 같지만 다른 객체)
println(a === b)                // => false  (당연히 다른 객체)
println(a.contentEquals(b))     // => true   (내용 비교는 이걸로)

println(a.contentToString())    // => "[1, 2, 3]"  (toString도 별도)
println(a.contentHashCode())    // => 30817 (내용 기반 해시)
// println(a.toString())        // => "[I@1b6d3586" 같은 참조 문자열
```

> **흔한 오해**: `arr1 == arr2`가 내용을 비교한다고 착각하면, 배열을 키로 쓰거나 `distinct`/`contains`에 배열을 넣을 때 조용히 오작동한다. 배열은 `equals`/`hashCode`가 참조 기반이라 `HashSet<IntArray>`도 내용이 아니라 정체성으로 동작한다. **내용 비교가 필요하면 항상 `contentEquals`/`contentHashCode`/`contentToString`.** 중첩 배열은 `contentDeepEquals`. 이 함정의 뿌리는 [[10 - 불리언과 동등성과 동일성]]의 `equals` 계약이다.

### 9.4 배열은 무공변이다 — Java의 함정을 닫다

Java에서 배열은 **공변**이라 `Integer[]`를 `Object[]`에 대입할 수 있고, 그 결과 런타임에 `ArrayStoreException`이 터질 수 있다. Kotlin은 이 구멍을 막았다 — `Array<T>`는 **무공변(invariant)** 이다.

```kotlin
val strs: Array<String> = arrayOf("a", "b")
// val objs: Array<Any> = strs    // 컴파일 에러: Array<String>은 Array<Any> 아님
```

```java
// Java — 컴파일은 되지만 런타임 폭탄
Object[] objs = new String[]{"a", "b"};   // 공변 허용 (구멍)
objs[0] = 42;   // 런타임 ArrayStoreException!
```

Kotlin은 이 잠재 오류를 **컴파일 타임에** 막는다. 배열 공변성의 위험과 Kotlin의 무공변 선택, `Array<out T>` 프로젝션은 [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]와 [[33 - 제네릭 1 - 타입 파라미터와 변성]]이 소유한다. 여기서 기억할 것은 **배열은 List가 아닐 뿐 아니라, 변성 규칙마저 다르다**는 점이다(무공변 배열 vs 공변 `List<out T>`).

### 9.5 배열 ↔ 컬렉션 변환의 비용

배열과 컬렉션을 오갈 때 박싱 비용을 의식해야 한다.

```kotlin
val prim = intArrayOf(1, 2, 3)
val list: List<Int> = prim.toList()   // 원소 3개가 Integer로 박싱됨
val back: IntArray = list.toIntArray() // 다시 언박싱해 int[]로

val boxedArr: Array<Int> = prim.toTypedArray()  // int[] → Integer[] (박싱)
val primAgain: IntArray = boxedArr.toIntArray() // 다시 int[] (언박싱)
```

`IntArray.toList()`는 겉보기엔 무해하지만 원소마다 박스를 할당한다. 성능이 중요한 수치 코드에서 배열을 컬렉션 API로 처리하려는 유혹은 이 숨은 박싱을 부른다. 원시 배열은 원시 배열 API(`sum()`, `map`은 박싱하니 주의, `forEach`, 인덱스 루프)로 다루는 것이 원칙이다.

## 10. 부동소수의 특이값 — NaN과 무한대

### 10.1 세 개의 특이값

정수가 오버플로로 래핑한다면, 부동소수 `Double`/`Float`는 넘침·불능을 **특이값**으로 표현한다. IEEE 754가 정의한 세 가지다.

```kotlin
println(1.0 / 0.0)               // => Infinity  (양의 무한대)
println(-1.0 / 0.0)              // => -Infinity
println(0.0 / 0.0)               // => NaN       (Not a Number)
println(Double.MAX_VALUE * 2)    // => Infinity  (오버플로 → 무한대)

println(Double.POSITIVE_INFINITY)
println(Double.NEGATIVE_INFINITY)
println(Double.NaN)
```

정수와의 결정적 차이: 부동소수 산술은 **예외를 던지지 않는다.** `0.0/0.0`은 예외가 아니라 `NaN`을 낳고, `1.0/0.0`은 `Infinity`를 낳는다(정수 `1/0`은 예외였다, 5.4절). 이 비대칭은 두 세계의 넘침 처리 철학이 다르기 때문이다 — 정수는 "닫힌 유한 고리(래핑)", 부동소수는 "특이값으로 확장된 실수선(IEEE)".

### 10.2 NaN은 자기 자신과 같지 않다 — 그러나 문맥에 따라 다르다

`NaN`의 가장 악명 높은 성질: **`NaN`은 어떤 값과도, 심지어 자기 자신과도 `==`가 `false`다.** 하지만 Kotlin에서는 이 규칙이 정적 타입에 따라 두 얼굴을 갖는다.

```kotlin
val x = Double.NaN
println(x == x)                       // => false  (IEEE 규칙: NaN != NaN)
println(x != x)                       // => true   (NaN을 감지하는 관용구)
println(x.isNaN())                    // => true   (명시적 검사, 권장)

val a: Any = Double.NaN
val b: Any = Double.NaN
println(a == b)                       // => true   (?! Any로 보면 같다)

println(listOf(Double.NaN).contains(Double.NaN))  // => true  (컬렉션은 total order)
```

정적 타입이 `Double`일 때 `==`는 IEEE 754 규칙(`NaN != NaN`)을 따른다. 하지만 `Any`로 상향되거나(박싱되어) 컬렉션 안에 있으면, Kotlin은 **total order**(모든 값에 순서를 주는 규칙)를 써서 `NaN`을 자기 자신과 같다고 판정한다. 이 이중성 — 부동소수 `==`가 정적 타입에 따라 IEEE와 total order 사이를 오가는 것 — 의 완전한 해부는 M48과 나란히 [[10 - 불리언과 동등성과 동일성]]이 소유한다. 이 장에서는 그 뿌리가 **박싱**(값이 `Any`/컬렉션으로 갈 때 표현과 비교 규칙이 바뀜)임을 확인하는 것으로 충분하다.

### 10.3 `-0.0`과 `0.0` — 비트는 다르되 값은 같다

IEEE 754에는 부호 있는 0이 있다. `0.0`과 `-0.0`은 서로 다른 비트 패턴이지만 산술적으로는 같다.

```kotlin
println(0.0 == -0.0)                  // => true   (Double로 비교: IEEE, 값 같음)
println(0.0.equals(-0.0))             // => false  (equals: total order, 비트 다름)

val z1: Any = 0.0
val z2: Any = -0.0
println(z1 == z2)                     // => false  (Any: total order로 구별)

println(1.0 / 0.0)                    // => Infinity
println(1.0 / -0.0)                   // => -Infinity  (부호 있는 0이 방향 결정)
```

`1.0 / -0.0`이 `-Infinity`인 것은 `-0.0`이 "음의 방향에서 0에 접근한 극한"을 표현하기 때문이다. 이 세밀한 IEEE 754 의미론 — 지수·가수 비트 배치, 서브노멀, 반올림 모드 — 의 완전한 물리학은 이 시리즈의 범위를 넘어 데이터 표현/컴퓨터 구조 자료를 참조해야 한다. 이 장에서는 "부동소수의 넘침·특이값은 정수의 래핑과 근본적으로 다른 세계이며, 그 차이가 박싱·동등성 판정과 얽힌다"는 연결만 세운다.

> **성능 주의**: 부동소수 특이값 검사는 `x == Double.NaN`으로 하면 **항상 false라 절대 감지 못 한다**(NaN != NaN). 반드시 `x.isNaN()` 또는 `x != x` 관용구를 써라. 무한대는 `x.isInfinite()`, 유한성은 `x.isFinite()`. 정상 값 여부를 이 함수들로 명시적으로 검사하는 습관이 부동소수 버그의 절반을 막는다.

---

수가 기계 위의 유한한 비트라는 하나의 사실에서 이 장의 모든 이야기가 뻗어 나왔다. 소스의 `Int`는 클래스지만 JVM 백엔드에서 대개 원시 `int`로 살고, 널이나 제네릭이나 상위 타입이 참조를 요구하는 경계에서만 박스를 입는다 — 그래서 "`Int?`는 항상 박싱"이라는 단정은 경계에서는 맞고 지역 계산과 타 백엔드에서는 틀리다(M5). 그 박스가 힙 객체이고 JVM이 작은 정수 박스를 캐시하기에 `===`가 값에 따라 널뛴다(M48의 진원지). 유한한 비트는 넘칠 때 예외 없이 조용히 래핑하고(그래서 `abs(Int.MIN_VALUE)`가 음수다), 그 비트를 직접 만지는 도구가 중위 비트 함수이며(시프트 횟수는 마스킹된다), 부호 비트의 해석을 바꾼 것이 `value class`로 지어진 부호 없는 정수다(그것도 원시 `Int`와 같은 박싱 규칙을 따른다, M39). 그리고 수를 대량으로 담을 때 `IntArray`는 원시 배열이라 박스가 없지만 `Array<Int>`는 박스 배열이며, 어느 쪽도 `List`가 아니고 `==`조차 내용이 아니라 정체성을 본다(M43). 부동소수는 이 모든 것의 반대편 — 넘침을 래핑이 아닌 특이값으로 처리하고, `NaN`은 자기 자신과도 같지 않되 박싱되면 얼굴을 바꾼다. "언제 박스가 씌워지는가"를 읽는 눈 하나가 이 모든 함정을 관통하는 실이다.

## 핵심 요약

- **소스의 `Int`는 클래스이지만 JVM 백엔드에서 가능한 곳은 원시 `int`로, 참조가 필요한 곳(널·제네릭·상위타입·`Array<Int>`)에서만 박스 `Integer`로 컴파일된다.** 이 표현 이중성은 언어 명세가 아니라 백엔드의 최적화이며, 다른 타깃은 다른 표현을 쓴다.
- **"`Int?`는 항상 박싱된 래퍼"는 과장이다(M5).** JVM 경계에서는 널 표현을 위해 `Integer`로 박싱되지만, 메서드 본문의 지역 계산에서는 옵티마이저가 박스를 소거할 수 있고, 비-JVM 백엔드는 Java식 박싱을 아예 쓰지 않는다. "항상"이라는 단어가 문장을 거짓으로 만든다.
- **작은 정수 박스(-128..127)는 `Integer.valueOf`가 캐시하므로, `Int?` 값에 `===`를 쓰면 값에 따라 결과가 널뛴다.** `127 === 127`은 true지만 `128 === 128`은 false다. 수의 "같음"은 언제나 `==`로 물어라(M48의 진원지, 정본은 [[10 - 불리언과 동등성과 동일성]]).
- **정수 오버플로는 예외가 아니라 2의 보수 래핑이다.** `Int.MAX_VALUE + 1`은 `Int.MIN_VALUE`가 되고, 범위 비대칭 탓에 `abs(Int.MIN_VALUE)`는 여전히 음수다. 검사가 필요하면 JVM 백엔드의 `Math.addExact` 등으로 명시적으로 던지게 하라.
- **정수 `/ 0`은 `ArithmeticException`이지만 부동소수 `/ 0.0`은 예외 없이 `Infinity`/`NaN`이다.** 정수는 닫힌 유한 고리(래핑), 부동소수는 IEEE 특이값으로 확장된 세계라는 철학 차이다.
- **비트 연산은 연산자 기호가 아니라 중위 함수(`and`/`or`/`xor`/`shl`/`shr`/`ushr`)와 단항 `inv()`이며, `Int`·`Long`에만 정의된다.** `Byte`/`Short`는 `toInt()` 승격이 필요하다. `shr`은 부호 유지, `ushr`은 0 채움이다.
- **시프트 횟수는 마스킹된다 — `Int`는 $\bmod\ 32$, `Long`은 $\bmod\ 64$.** 그래서 `1 shl 32 == 1`이다. 가변 폭 시프트에서 이 경계를 특수 처리하지 않으면 0을 기대한 자리에 원본이 튀어나온다.
- **부호 없는 정수 `UInt`/`ULong`/`UByte`/`UShort`는 언어 원시 타입이 아니라 표준 라이브러리가 `@JvmInline value class`로 지어 올린 타입이다.** 내부 부호 있는 정수의 비트를 부호 없이 재해석하며, Kotlin 1.3 실험적 도입 → 1.5 안정화의 경로를 밟았다.
- **부호 없는 정수도 value class이므로 `Int`와 정확히 같은 박싱 규칙을 따른다(M39).** 대개 언박싱되어 원시 성능을 내지만, 널 가능·제네릭·상위타입·컬렉션에서는 박싱된다. 완전한 언박싱 조건은 [[36 - 타입 별칭과 인라인 value class]]가 소유한다.
- **`IntArray`는 원시 배열(박스 없음, 캐시 친화), `Array<Int>`는 박스 배열이며, 어느 쪽도 `List`가 아니다(M43).** 셋은 크기·변경·표현·`==`·변성 계약이 모두 다르다. 수의 대량 저장에는 원시 배열을 쓰고 컬렉션 변환의 숨은 박싱을 경계하라.
- **배열의 `==`는 내용이 아니라 참조 동일성이다.** 내용 비교는 `contentEquals`/`contentHashCode`/`contentToString`(중첩은 `contentDeepEquals`). 배열을 `HashSet`에 넣거나 키로 쓸 때 이 함정이 조용히 오작동을 부른다.
- **`NaN`은 자기 자신과도 `==`가 false(IEEE)지만, `Any`로 박싱되거나 컬렉션에 들어가면 total order로 자기 자신과 같아진다.** `-0.0`과 `0.0`도 `Double`로는 같고 `equals`/`Any`로는 다르다. 부동소수 특이값은 반드시 `isNaN()`/`isInfinite()`로 명시 검사하라.

## 연결 노트

- [[07 - 수 1 - Int와 Long과 부동소수점]] — 이 장의 직전. 정수·부동소수 타입, 리터럴, 확대 변환 없음, 정수 나눗셈의 기본과 M4(원시 없다는 오해)를 세웠다. 이 장은 그 "가능한 곳에서 원시형"의 단서를 박싱으로 판다.
- [[10 - 불리언과 동등성과 동일성]] — `==`/`===`의 완전한 의미론, `equals`/`hashCode` 계약, 박싱 캐시가 `===`를 망가뜨리는 M48, 부동소수 `==`의 이중성을 소유한다. 이 장이 드러낸 박스 함정의 정본 해부.
- [[36 - 타입 별칭과 인라인 value class]] — `value class`의 일반 이론과 언박싱/박싱 조건표, M39("value class가 항상 박싱을 없앤다"는 오해)를 소유한다. 이 장의 부호 없는 정수가 그 기법의 살아 있는 사례다.
- [[38 - 컬렉션 - 읽기 전용과 가변]] — `List`가 읽기 전용 인터페이스일 뿐임(M26)과 배열이 컬렉션과 다른 계약임(M43의 컬렉션 측면)을 소유한다. 이 장의 배열/List 대비의 확장.
- [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]] — 타입 소거(M19)가 왜 제네릭 슬롯의 수를 박싱하게 만드는지, 배열의 공변 함정을 소유한다. 이 장 박싱 원인 (2)와 배열 무공변의 이론.
- [[33 - 제네릭 1 - 타입 파라미터와 변성]] — 무공변 배열 대 공변 `List<out T>`의 변성 규칙을 소유한다. 배열이 List와 변성마저 다른 이유.
- [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]] — 스마트 캐스트가 `Int?`를 비-널로 좁혀 옵티마이저가 박스를 소거하는 근거. M5의 지역 최적화가 여기 맞닿는다.
- [[19 - 연산자 오버로딩과 관례]] — 비트 연산이 왜 오버로딩 가능한 연산자가 아니라 이름 붙은 중위 함수인지의 대비. `UInt`의 `plus`/`compareTo`가 어떻게 관례로 연결되는지의 정본.
- [[45 - Java 상호운용]] — `Integer.valueOf` 캐시, `Math.*Exact`, `Integer.compareUnsigned` 같은 JVM 표준 라이브러리 계약과 박싱의 Java 표현을 소유한다. 이 장의 JVM 한정 사실들의 뿌리.
- [[46 - 멀티플랫폼과 진화와 어두운 구석]] — 부호 없는 정수의 실험적→안정 진화 제도(opt-in, 안정성 등급)와 박싱·배열 공변 등 "어두운 구석"의 종합 회수를 소유한다.
