[[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]]에서는 Kotlin이 단순한 "JVM 언어"가 아니라 JVM, Native, JS, Wasm의 네 타깃을 겨냥하는 멀티플랫폼 언어라는 점을 확인했다. 또한 Kotlin은 Java의 문법 설탕이 아니라 널 가능성, 변성, `Nothing`을 갖춘 독립된 타입 시스템을 가진 언어라는 점도 확인했다. 이 주장들은 모두 **언어의 의미는 컴파일러가 결정한다**는 사실을 전제로 한다.

`val`은 다시 대입할 수 없다는 규칙, `Int?`는 널을 표현할 수 있다는 규칙, 확장 함수는 정적으로 디스패치된다는 규칙은 모두 명세에 적혀 있고, 컴파일러가 그 명세를 코드에 강제한다. 따라서 언어를 기계 수준에서 이해하려면 이 규칙을 집행하는 컴파일러 자체를 들여다봐야 한다.

이 장에서는 소스 텍스트가 렉서(lexer)를 거쳐 구문 트리가 되고, 프론트엔드에서 이름 해소(resolution), 타입 추론, 진단(diagnostic)을 거친 뒤, 공통 중간 표현(IR)으로 낮춰지고, 네 백엔드 중 하나가 이를 실제 타깃 코드로 바꾸는 과정을 따라간다. 특히 2.0에서 기본이 된 **K2/FIR** 프론트엔드가 무엇을 다시 설계했는지, 그리고 하나의 프론트엔드에서 네 백엔드가 갈라지는 IR 구조가 왜 Kotlin 발전의 핵심이었는지를 살펴본다.

컴파일 타임에 무엇이 확정되고, 소거되고, 인라이닝되는지도 파이프라인 관점에서 정리한다.

다만 `inline`/`reified`의 의미는 [[15 - 인라인 함수와 reified]], 타입 소거의 전체 내용은 [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]], `suspend`의 CPS 변환은 [[42 - suspend와 코루틴 - 언어 수준의 중단]], Java 상호운용의 바이트코드 계약은 [[45 - Java 상호운용]]에서 자세히 다룬다. 이 장에서는 이들이 컴파일러의 어느 단계에서 처리되는지만 짚는다.

## 1. 컴파일러라는 파이프라인: 왜 한 덩어리가 아닌가

### 1.1 "번역"은 한 번에 일어나지 않는다

단순하게 생각하면 컴파일러는 텍스트를 받아 기계어를 내놓는 블랙박스다. 하지만 실제로는 그렇지 않다. `kotlinc`는 소스 텍스트라는 *구조 없는 문자열*을 여러 단계에 걸쳐 조금씩, 의미가 완전히 확정된 *구조화된 표현*으로 바꾼다. 각 단계는 앞 단계의 산출물을 입력으로 받아, 정보가 더 풍부하고 더 낮은(기계에 가까운) 표현을 내놓는다.

이렇게 단계를 나누는 이유는 세 가지다.

- **관심사 분리**: "이 텍스트가 문법적으로 옳은가", "이 이름이 무엇을 가리키는가", "이 표현식의 타입은 무엇인가"는 서로 다른 질문이고, 각각 다른 알고리즘이 필요하다.
- **재사용**: 프론트엔드(의미 분석)가 만든 결과를 여러 백엔드가 공유할 수 있다면, JVM용, JS용, Native용 컴파일러가 타입 추론 로직을 각자 따로 세 번 구현하지 않아도 된다.
- **도구 지원**: IntelliJ IDEA의 코드 완성, 인라인 에러 표시, 리팩터링은 컴파일러 프론트엔드와 같은 코드를 공유한다. 편집기가 키를 누를 때마다 전체 컴파일을 돌릴 수는 없으므로, 프론트엔드는 빠르게, 그리고 부분적으로 실행할 수 있도록 설계되어야 한다.

```text
소스 텍스트 (.kt)
      │  렉서(lexer): 문자열 → 토큰 스트림
      ▼
   토큰 스트림
      │  파서(parser): 토큰 → 구문 트리(PSI/AST)
      ▼
   구문 트리                     ┐
      │  이름 해소·타입 추론·진단  │  프론트엔드
      ▼                          │  (K1: descriptors / K2: FIR)
   해소된 의미 트리               ┘
      │  (K1: PSI2IR / K2: FIR2IR)
      ▼
   백엔드 IR (공통 중간 표현)     ┐
      │  로워링(lowering) 패스들   │  백엔드
      ▼                          │  (JVM / JS / Native / Wasm)
   타깃 코드 (.class / .js / 기계어 / .wasm)  ┘
```

### 1.2 프론트엔드와 백엔드

이 파이프라인에는 뚜렷한 경계가 하나 있다. **프론트엔드**는 "이 프로그램은 무슨 뜻인가"라는 질문에 답한다. 파싱, 이름 해소, 타입 추론, 그리고 명세 위반에 대한 진단(에러와 경고)이 프론트엔드의 일이다. 프론트엔드는 타깃을 알지 못한다. `val x: Int = 3`이 JVM에서 `int`가 될지, JS에서 `number`가 될지는 프론트엔드가 신경 쓰지 않는다. 프론트엔드의 산출물은 타입이 모두 붙고 이름이 모두 해소되었지만, 아직 어떤 기계와도 관계없는 의미 트리다.

**백엔드**는 "이 의미를 이 기계에서 어떻게 실현하는가"라는 질문에 답한다. 타깃은 여기서 처음 등장한다. JVM 백엔드는 `when`을 `tableswitch`/`lookupswitch` 바이트코드로, 데이터 클래스의 `equals`를 실제 메서드로, 인라인 함수를 호출 지점에 펼친 코드로 낮춘다. JS 백엔드는 같은 의미 트리를 JavaScript 함수와 프로토타입으로 낮춘다.

이 분리가 Kotlin에 준 실질적인 이득은 1장(코틀린이란 무엇인가)에서 말한 멀티타깃 전략 그 자체다. 하나의 언어 의미(프론트엔드)에서 네 가지 실행 환경(백엔드)으로 갈라질 수 있는 것은 경계가 명확한 파이프라인 덕분이다. 그 경계의 이름이 5절에서 볼 **IR**이다.

> [!note] 명세 기준
> "컴파일러"는 단수 명사처럼 쓰이지만, 실제로는 여러 컴포넌트가 협력하는 구조다. `kotlinc-jvm`, `kotlinc-js`, Native 컴파일러(`konanc` 계열)는 프론트엔드를 공유하고 백엔드가 서로 다른, 사실상 별개의 실행 파일이다.
>
> 따라서 "Kotlin 컴파일러가 X를 한다"는 서술을 보면 프론트엔드가 하는 일인지, 특정 백엔드가 하는 일인지를 항상 다시 따져 봐야 한다. 예를 들어 원시 타입으로 컴파일하는 것은 **JVM 백엔드**가 정하는 일이지, 언어나 프론트엔드가 정하는 일이 아니다.

### 1.3 한 번 읽기와 여러 번 읽기

초기 C나 Pascal 같은 옛 언어의 컴파일러는 성능과 메모리 제약 때문에 소스를 앞에서 뒤로 한 번만 읽는 단일 패스(single-pass) 방식을 지향했다. 그래서 "사용하기 전에 선언해야 한다"는 규칙을 문법으로 강제했다.

Kotlin은 다르다. 최상위 선언의 순서가 자유롭고([[04 - 파일과 패키지와 선언 - 프로그램의 골격]]에서 다룰 전방 참조), 타입 추론이 함수 경계를 넘어 함께 동작하며, 완전성(exhaustiveness) 검사처럼 전역적인 판단이 필요하다. 즉 컴파일러가 소스 전체를 **여러 번** 읽을 수 있어야 한다.

```kotlin
fun describe(n: Int): String = classify(n)     // 아래에 선언된 함수를 위에서 참조
fun classify(n: Int): String =
    if (n > 0) "양수" else if (n < 0) "음수" else "영"
// => 컴파일 성공. 선언 순서 무관.
```

이 코드가 컴파일되려면 `describe`를 분석하는 시점에 `classify`의 시그니처를 이미 알고 있어야 한다. 그래서 프론트엔드는 최소한 두 단계로 일한다. 먼저 모든 선언의 *헤더*(시그니처)를 수집하고, 그다음에 각 함수의 *본문*을 분석한다. 이렇게 헤더를 먼저 보고 본문을 나중에 보는 구조는 K2/FIR의 다단계 해소에서 훨씬 정교해지며, 이 내용은 3절에서 다룬다.

## 2. 프론트엔드 1: 렉서와 파서, 텍스트가 트리가 되기까지

### 2.1 렉서: 문자에서 토큰으로

파이프라인의 첫 단계는 렉서(어휘 분석기)다. 렉서는 소스를 문자 단위로 읽어 **토큰**(token)이라는 의미 단위로 자른다. `val x = 42`는 `[val][x][=][42]`의 네 토큰(키워드, 식별자, 연산자, 정수 리터럴)이 된다. 공백, 줄바꿈, 주석은 대부분 여기서 걸러진다. 하지만 Kotlin에서는 줄바꿈을 완전히 버리지 않는다. 세미콜론 추론([[03 - 렉시컬 구조와 세미콜론 추론]])에 줄바꿈 정보가 필요하기 때문이다.

렉서 수준에서도 언어의 성격이 드러난다. Kotlin의 식별자에는 유니코드 문자를 쓸 수 있고, 백틱으로 감싸면 키워드도 이름으로 쓸 수 있다(``` `fun` ```, ``` `is` ```). 렉서는 문자열 리터럴 세 종류(`"..."`, `"""..."""`, 템플릿 `$x`)를 구분해야 하고, 숫자 리터럴의 밑줄 구분자, 진법 접두사, 타입 접미사(`1_000`, `0xFF`, `3.14f`, `100L`)도 인식해야 한다.

이런 어휘 규칙은 3장(렉시컬 구조와 세미콜론 추론)과 [[07 - 수 1 - Int와 Long과 부동소수점]]에서 자세히 다룬다.

> [!warning] 흔한 오해
> 렉서가 타입을 안다고 생각하기 쉽지만 그렇지 않다. 렉서는 `42`가 정수 리터럴이라는 *어휘적* 사실만 안다. 그 값이 `Int`인지 `Long`인지, 더 나아가 `Byte`로 좁혀지는지는 훨씬 뒤의 타입 추론 단계(4절)에서 문맥을 보고 결정된다. 어휘 분류와 타입 결정은 파이프라인에서 멀리 떨어진 별개의 단계다.

### 2.2 파서: 토큰에서 구문 트리로

파서는 토큰 스트림을 받아 언어 문법에 따라 **구문 트리**를 만든다. Kotlin 컴파일러와 IntelliJ는 오래전부터 이 트리를 PSI(Program Structure Interface)라는 형태로 표현해 왔다. PSI는 편집기에 적합한 구조다. 원본 텍스트의 모든 문자(공백과 주석 포함)를 보존하고, 각 노드가 원본의 어느 위치에서 왔는지 추적한다. 그래서 같은 트리로 컴파일도 하고, "이 심볼의 정의로 이동" 같은 IDE 기능도 구현한다.

```kotlin
val total = price * quantity + tax
```

이 한 줄이 만드는 트리의 골격은 다음과 같다.

```text
프로퍼티 선언 (val total = ...)
└─ 대입식 초기화
   └─ 이항식 (+)
      ├─ 이항식 (*)
      │  ├─ 참조 (price)
      │  └─ 참조 (quantity)
      └─ 참조 (tax)
```

파서가 `*`를 `+`보다 트리의 더 깊은 곳에 둔다는 점에 주목하자. 연산자 우선순위는 문법에 고정되어 있다([[19 - 연산자 오버로딩과 관례]]에서 다루는 내용의 근거다). 사용자가 `operator fun times`를 정의해도 우선순위는 바꿀 수 없는데, 언어 문법이 파서 단계에서 이미 정해 두었기 때문이다. 파싱 단계에서는 아직 `price`가 무엇인지, `*`가 어떤 함수를 호출하는지 전혀 모른다. 이는 다음 단계에서 결정한다.

### 2.3 구문 오류와 의미 오류

파서 단계에서 나오는 진단은 **구문 오류**다. 괄호 짝이 맞지 않거나, `val` 뒤에 이름이 없거나, `when`의 분기 문법이 깨지는 것처럼 문장 구조 자체가 문법에 어긋나는 경우다. 파서는 오류에 관대하다. 오류 하나에서 멈추지 않고 최대한 복구(error recovery)해 트리를 끝까지 만들려고 한다. 그래야 편집기가 여러 오류를 한 번에 표시하고, 오류 지점 이후의 코드에도 완성 제안을 줄 수 있다.

```kotlin
val x = (1 + 2          // 컴파일 에러: 닫는 괄호 ')' 가 없음 (구문 오류)
fun f(): Int = "hello"  // 컴파일 에러: String을 Int로 반환할 수 없음 (의미/타입 오류)
```

두 오류는 성격이 다르다. 첫 줄은 구조가 성립하지 않으므로 파서가 잡는다. 둘째 줄은 문법적으로 완벽하게 옳은 함수 선언이므로 파서를 통과한다. 이 오류는 **의미 분석**, 즉 타입 검사 단계에서야 드러난다. 이 구분은 실무에서 중요하다. 편집기에 빨간 줄이 떴을 때 그것이 구조의 문제인지 의미의 문제인지를 알면, 어느 단계를 의심해야 할지 정할 수 있다.

## 3. 프론트엔드 2: K1에서 K2로, FIR이라는 재설계

### 3.1 K1의 한계: 디스크립터와 BindingContext

파싱이 끝나면 프론트엔드는 트리의 각 이름과 표현식에 의미를 붙여야 한다. `price`는 어느 프로퍼티를 가리키는가? `price * quantity`의 `*`는 어느 `times` 함수를 호출하는가? 그 결과 타입은 무엇인가? 2.0 이전의 컴파일러(오늘날 K1이라고 부른다)는 이 정보를 **디스크립터**(descriptor)라는 객체와 **BindingContext**라는 거대한 조회 테이블에 담았다.

문제는 이 설계가 두 가지 표현을 함께 관리했다는 점이다. 한쪽에는 구문을 담은 PSI 트리가 있고, 다른 쪽에는 의미를 담은 디스크립터가 있었다. BindingContext는 "이 PSI 노드는 이 디스크립터"라는 방대한 매핑으로 둘을 연결했다.

이 구조는 오랫동안 동작했지만 무거웠다. 더 똑똑한 스마트 캐스트나 더 정교한 타입 추론 같은 새 언어 기능을 넣을 때마다 두 표현과 그 사이의 매핑을 함께 고쳐야 했다. 이는 컴파일 속도와 유지보수성 모두에 부담이 되었다.

### 3.2 K2와 FIR: 점점 채워지는 하나의 트리

K2 프론트엔드의 핵심은 **FIR**(Front-end Intermediate Representation, 프론트엔드 중간 표현)이다. 별도의 디스크립터와 매핑을 두는 대신, **하나의 트리를 여러 번의 변환 패스로 점진적으로 채워 나간다**는 것이 FIR의 아이디어다.

처음에는 PSI에서 이름도 해소되지 않고 타입도 붙지 않은 "raw FIR"이 만들어진다. 그다음 일련의 해소 단계(resolution transformer)가 이 트리를 제자리에서 조금씩 채워 나간다. 마지막에는 모든 이름이 해소되고 모든 표현식에 타입이 붙은 "완전히 해소된 FIR"이 된다.

```text
raw FIR
  │  1) 임포트/패키지 해소
  │  2) 슈퍼타입 해소   (클래스 계층 확정)
  │  3) 타입 해소       (선언에 쓰인 타입 참조 확정)
  │  4) 시그니처(헤더) 해소  (함수/프로퍼티 시그니처 확정)
  │  5) 본문 해소       (표현식·타입 추론·스마트캐스트·진단)
  ▼
resolved FIR  ── (FIR2IR) ──▶  백엔드 IR
```

이 다단계 구조는 1.3절에서 말한 "헤더 먼저, 본문 나중" 방식을 명시적인 파이프라인으로 만든 것이다. 슈퍼타입과 시그니처가 본문보다 먼저 확정되므로, 선언 순서와 관계없이 서로를 참조할 수 있다. A가 B를 상속하고 B가 A를 참조하는 순환 참조도 단계별로 안전하게 처리된다.

> [!info] 역사 메모
> K2는 2.0(2024년 5월)에서 기본 컴파일러가 되었다. "K2"는 컴파일러 세대를, "FIR"은 그 프론트엔드가 쓰는 자료 표현을 가리킨다. 두 말은 흔히 같은 뜻으로 쓰이지만 엄밀히는 다르다. FIR은 K2 프론트엔드의 *구현 표현*이고, K2는 그 프론트엔드를 포함한 컴파일러 전체의 이름이다.
>
> 백엔드 IR(5절)과 혼동하지 않도록 주의하자. 둘 다 이름이 "IR"로 끝나지만, FIR은 프론트엔드의 의미 트리이고, (백엔드) IR은 프론트엔드와 백엔드 사이의 경계에 있는 별개의 표현이다.

### 3.3 K2 이후 사용자가 느끼는 변화

사용자는 K2를 대부분 "더 빠르고 더 정확해졌다"는 형태로 느낀다. 컴파일 속도가 개선되었고, 특히 스마트 캐스트([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]])와 타입 추론이 이전보다 더 많은 경우를 이해한다. 예를 들어 제어 흐름을 따라가며 널 가능성을 판단하는 분석이 더 정밀해졌다.

```kotlin
fun printLength(s: String?) {
    if (s == null) return
    // 여기서 s는 스마트 캐스트로 String (Nothing 반환 return이 흐름을 끊었으므로)
    println(s.length)   // => 안전. ?. 불필요.
}
```

이런 흐름 분석은 K1도 상당 부분 했지만, K2는 흐름 분석과 타입 추론을 더 통합된 방식으로 처리하기 때문에 경계 사례에서 예상 밖의 결과가 덜 나온다. 다만 이 장에서 강조하려는 것은 결과가 아니라 *위치*다. **스마트 캐스트, 널 안전성 검사, 완전성 검사는 모두 이 프론트엔드 단계에서 일어난다.**

즉 이 검사들은 대부분 컴파일 타임에 이루어진다. 널 안전성은 런타임 검사가 아니라 주로 컴파일 타임 분석이다. 런타임에 남는 검사는 `!!`, 플랫폼 타입, 리플렉션, Java 상호운용처럼 컴파일러가 확신할 수 없는 지점뿐이다.

## 4. 프론트엔드 3: 컴파일러가 타입을 만들어 내는 타입 추론

### 4.1 추론은 "생략"이 아니라 "계산"이다

Kotlin은 정적 타입이면서 강타입인 언어지만, 코드에 타입을 거의 적지 않는다. `val x = 42`에서 타입을 적지 않아도 컴파일러는 `x`가 `Int`라는 것을 안다. 이는 단순히 오른쪽의 타입을 왼쪽에 복사하는 일이 아니다. 타입 추론(type inference)은 표현식 사이의 제약(constraint)을 수집하고, 그 제약을 만족하는 타입을 *풀어내는* 과정이다.

```kotlin
val a = 42            // Int (정수 리터럴의 기본 타입)
val b = 42L           // Long (L 접미사)
val c = 3.14          // Double (부동소수 리터럴의 기본 타입)
val d = listOf(1, 2, 3)          // List<Int>
val e = listOf(1, 2L)            // List<Long>  ← 공통 상위 타입으로 통일
val f = listOf(1, "x")           // List<Any>   ← 더 위로 올라감
val g = if (cond) 1 else "x"     // Any (K2 기준. 참고로 K1은 Comparable<*> & Serializable 교집합을 줬다)
```

`listOf(1, 2L)`에서 컴파일러는 두 인자의 타입(`Int`, `Long`)을 보고 원소 타입 `T`에 대한 제약을 세운다. 그다음 둘을 모두 담을 수 있는 최소 공통 상위 타입을 계산해 `Long`으로 정한다.

`listOf(1, "x")`는 `Int`와 `String`의 공통 상위 타입인 `Any`까지 올라간다(Kotlin의 타입 계층은 [[05 - 타입 시스템의 지형 - Any와 Unit과 Nothing]]에서 다룬다). 이처럼 추론은 "모든 제약을 만족하면서 가장 구체적인 타입"을 찾는 최적화 문제에 가깝다.

### 4.2 리터럴의 타입은 문맥이 정한다

숫자 리터럴은 타입 추론이 문맥과 함께 동작하는 좋은 예다. `42`는 그 자체로는 "정수 리터럴"일 뿐, 아직 어떤 구체 타입으로도 확정되지 않은 상태다. 기대 타입(expected type)이 있으면 그 타입에 맞춰지고, 없으면 기본형인 `Int`가 된다.

```kotlin
val x: Long = 42       // 기대 타입이 Long → 42가 Long 리터럴로 해석됨. toLong() 불필요.
val y: Byte = 42       // 기대 타입 Byte, 42가 Byte 범위 안 → OK
val z: Byte = 200      // 컴파일 에러: 200은 Byte(-128..127) 범위를 벗어남
val w = 42             // 기대 타입 없음 → 기본형 Int
```

`val x: Long = 42`에 `42.toLong()`이 필요 없는 것은 기대 타입 `Long`이 리터럴 해석에 반영되기 때문이다. 반면 변수끼리는 이런 자동 확대가 일어나지 않는다. Kotlin에는 암시적 확대 변환이 없다(7장 수 1에서 다룬다).

```kotlin
val i: Int = 42
val l: Long = i        // 컴파일 에러: Int는 Long이 아님. i.toLong() 필요.
```

리터럴 `42`는 문맥이 타입을 정할 수 있는 상수식이고, 변수 `i`는 이미 타입이 `Int`로 확정된 값이다. 앞의 것은 추론이 기대 타입에 맞출 수 있는 대상이고, 뒤의 것은 이미 타입이 굳은 값이다.

### 4.3 추론이 함수 경계를 넘을 때와 그 한계

람다와 제네릭이 함께 쓰이면 추론은 인자와 반환 값을 오가며 이루어진다.

```kotlin
val lengths = listOf("a", "bb", "ccc").map { it.length }
// map의 원소 타입 String → it: String → it.length: Int → 결과 List<Int>
```

`map`의 수신 리스트가 `List<String>`이므로 람다 파라미터 `it`은 `String`으로 추론된다(`it`은 [[13 - 함수 타입과 람다와 함수 참조]]에서 다룬다). 그 결과 `it.length`는 `Int`가 되고, 최종 결과는 `List<Int>`가 된다. 이처럼 추론은 "밖에서 안으로"(리스트 타입에서 람다 파라미터로), 그리고 "안에서 밖으로"(람다 반환에서 결과 타입으로) 양방향으로 정보를 전달한다.

하지만 추론에는 원칙적인 한계가 있다. **함수의 공개 시그니처(파라미터와 반환 타입)는 명시해야 하는 경우가 많다.** 재귀 함수의 반환 타입이나 공개 API의 반환 타입을 추론에만 맡기면 순환이 생기거나 의도가 흐려진다.

```kotlin
fun factorial(n: Int) = if (n <= 1) 1 else n * factorial(n - 1)
// 컴파일 에러: 재귀 함수는 반환 타입을 추론할 수 없음 → 명시 필요
fun factorial2(n: Int): Int = if (n <= 1) 1 else n * factorial2(n - 1)  // OK
```

`factorial`의 반환 타입을 추론하려면 `factorial`의 반환 타입을 이미 알고 있어야 하므로 순환이 생긴다. 그래서 컴파일러는 재귀 함수에 반환 타입을 명시하도록 요구한다. 추론은 만능이 아니다. 이 규칙에는 "지역적으로 결정할 수 있는 것"과 "전역적인 계약으로 정해 두어야 하는 것"을 구분하는 언어 설계가 반영되어 있다.

> [!caution] 성능 주의
> 타입 추론, 특히 복잡한 제네릭과 람다 체인의 추론은 컴파일러가 가장 많은 일을 하는 지점 중 하나다. 아주 긴 빌더 체인이나 깊이 중첩된 람다 때문에 컴파일이 느려진다면, 중간에 타입을 명시해 제약 해결의 범위를 끊어 주는 것이 실질적인 해결책이다. 추론은 편리하지만 비용이 없지는 않다.

## 5. IR: 하나의 트리, 네 개의 백엔드

### 5.1 공통 중간 표현이 필요한 이유

프론트엔드가 완전히 해소된 FIR을 만들었다. 이제 이것을 실제 코드로 바꿔야 하는데, 타깃이 넷이다. 단순하게 접근하면 "FIR에서 JVM 바이트코드로", "FIR에서 JS로", "FIR에서 기계어로", "FIR에서 Wasm으로" 바꾸는 독립 변환기 네 개를 만들게 된다. 그러면 각 변환기가 데이터 클래스 생성, 인라인 함수 펼치기, `when` 완전성 같은 수많은 공통 로직을 제각각 다시 구현해야 하고, 유지보수가 매우 어려워진다.

해법은 **IR**(Intermediate Representation, 중간 표현)이다. 프론트엔드의 결과를 먼저 타깃과 무관한 공통 IR로 낮춘다(FIR2IR). 그다음 그 IR에 **로워링**(lowering)이라고 부르는 변환 패스를 적용해 점점 저수준으로 만들고, 마지막 단계에서만 타깃별 코드를 내보낸다. 데이터 클래스의 멤버 합성, 지역 함수 처리, `when`의 정규화 같은 많은 로워링은 타깃과 관계가 없으므로, IR 수준에서 한 번만 구현해 모든 백엔드가 공유한다.

```text
                     resolved FIR
                          │  FIR2IR
                          ▼
                    공통 백엔드 IR
                          │  타깃 공통 로워링 패스들
                          ▼
             ┌────────────┼────────────┬────────────┐
             ▼            ▼            ▼            ▼
        JVM 백엔드    JS 백엔드    Native 백엔드   Wasm 백엔드
             │            │            │            │
             ▼            ▼            ▼            ▼
        .class 파일    .js 파일   LLVM→기계어     .wasm
```

IR 기반 구조로 통합한 것은 Kotlin 백엔드 발전의 큰 흐름이었다. 한때 JVM 백엔드는 오랫동안 IR 없이 PSI에서 곧바로 바이트코드를 만들었지만, 지금은 JVM을 포함한 모든 타깃이 공통 IR을 거친다. 그 결과 언어 기능 하나를 추가할 때 백엔드 로직을 네 번 고치는 대신, IR 로워링을 한 번 고쳐 네 타깃에 반영할 수 있게 되었다.

### 5.2 로워링: 고수준 개념을 저수준으로 낮추기

로워링은 IR 트리를 입력받아 더 원시적인 IR 트리를 출력하는 변환이다. 이름 그대로 언어의 고수준 개념을 기계가 이해할 수 있는 저수준 구성으로 낮춘다. 예를 들어 다음 개념들이 IR 로워링 단계에서 풀린다(각 개념의 자세한 의미는 오른쪽 열의 장에서 다룬다).

| 고수준 개념    | 로워링이 하는 일                                             | 다루는 장                                   |
| --------- | ----------------------------------------------------- | -------------------------------------- |
| 데이터 클래스   | `equals`/`hashCode`/`toString`/`componentN`/`copy` 합성 | [[27 - 데이터 클래스]]                       |
| 기본 인자     | 인자 채움 로직, 합성 오버로드/`$default` 생성                        | [[12 - 함수 - 인자와 vararg와 지역 함수와 꼬리 재귀]] |
| 인라인 함수    | 호출 지점에 본문 펼치기, 람다 인라이닝                                  | 15장(인라인 함수와 reified)               |
| `when`    | 조건 사슬이나 `switch` 계열로 정규화                                  | [[17 - 표현식으로서의 제어 흐름 - if와 when]]      |
| 지역/익명 함수  | 별도 함수나 클래스로 추출                                         | [[14 - 클로저와 캡처]]                       |
| `suspend` | CPS와 상태 기계로 변환                                         | 42장(suspend와 코루틴)      |

여기서 중요한 점은 **우리가 "언어 기능"이라고 부르는 것 중 상당수가 실은 컴파일러가 IR 단계에서 자동으로 생성하는 코드**라는 것이다. 데이터 클래스의 `copy`는 런타임 라이브러리가 제공하는 특별한 기능이 아니라, 컴파일러가 대신 작성해 준 평범한 메서드다. 10절에서는 디컴파일로 컴파일러가 작성한 이 코드를 직접 확인한다.

### 5.3 IR이 있어도 백엔드마다 다른 것

IR이 공통이라고 해서 네 타깃의 결과가 같은 것은 아니다. IR 이후에는 각 백엔드가 자기 타깃의 현실에 맞춰 고유한 결정을 내린다. 대표적인 예가 **원시 타입**이다.

```kotlin
fun add(a: Int, b: Int): Int = a + b
```

JVM 백엔드에서 이 함수의 `Int`는 가능한 곳에서 원시 `int`로 컴파일된다. Kotlin 소스에 원시 타입이 없다고 해서 실행 코드에도 없는 것은 아니다. 소스에는 없지만 JVM 백엔드가 원시형으로 낮춘다. JS 백엔드에는 `int`라는 개념 자체가 없으므로 JavaScript의 `number`로 표현된다. IR은 같아도 실현 방식은 다르다.

널 가능성의 표현도 백엔드마다 다르다. `Int?`는 널을 표현해야 하므로 JVM 백엔드에서는 대개 박싱된 `java.lang.Integer`가 된다. 다만 "항상 박싱된다"는 것은 오해다. 널을 표현해야 할 때 박싱되며, 백엔드가 최적화할 여지도 있다. 정확한 조건은 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]에서 다룬다.

요점은 **어떤 타입을 어떻게 표현할지는 프론트엔드가 아니라 백엔드가 정한다**는 것이다. 그래서 이 장에서는 이런 질문을 항상 "JVM 백엔드에서"라는 한정어와 함께 다룬다.

> [!note] 명세 기준
> "Kotlin은 원시 타입으로 컴파일한다"는 문장은 절반만 맞다. 정확히 말하면 "JVM 백엔드가, 가능한 문맥에서, `Int` 같은 타입을 원시 `int`로 컴파일한다"이다. Native, JS, Wasm 백엔드에는 JVM의 `int`/`Integer` 이분법이 없다. 멀티타깃 언어를 이야기할 때 백엔드를 밝히지 않고 "컴파일된다"고 서술하면 항상 의심해 봐야 한다.

## 6. JVM 백엔드: `.kt`가 `.class`가 되는 과정

### 6.1 파일 하나가 클래스 하나로 대응하지 않는다

JVM에서는 모든 코드가 클래스 안에 있어야 한다. 하지만 Kotlin에서는 파일 최상위에 함수와 프로퍼티를 둘 수 있다(4장 파일과 패키지와 선언). 이 차이를 맞추기 위해 JVM 백엔드는 **파일마다 합성 클래스를 하나씩** 만들고, 그 파일의 최상위 선언을 이 클래스에 담는다. 이름은 "파일명 + `Kt`" 규칙을 따른다.

```kotlin
// 파일: MathUtils.kt
package geometry

const val PI = 3.14159
fun areaOfCircle(r: Double): Double = PI * r * r
```

이 파일은 JVM 백엔드에서 `geometry.MathUtilsKt`라는 클래스로 컴파일되고, `areaOfCircle`은 그 클래스의 `public static` 메서드가 된다. 그래서 45장(Java 상호운용)에서 보듯이 Java 코드가 이 함수를 호출할 때는 `MathUtilsKt.areaOfCircle(...)`처럼 클래스 이름을 거친다.

```java
// Java에서 본 모습
double a = geometry.MathUtilsKt.areaOfCircle(2.0);
```

이 클래스 이름은 `@file:JvmName`으로 바꿀 수 있고, 여러 파일의 최상위 선언을 한 클래스로 합칠 수도 있다(`@JvmMultifileClass`). 자세한 내용은 45장(Java 상호운용)에서 다룬다. 여기서 알아 둘 것은 **`FooKt`가 특별한 클래스가 아니라, JVM의 "코드는 클래스 안에만 있다"는 제약을 만족시키려고 컴파일러가 만든 컨테이너**라는 사실 하나다.

### 6.2 반대 방향: 클래스 하나가 파일 하나로 대응하지도 않는다

반대 방향도 마찬가지다. 소스 파일 하나가 여러 `.class`를 만들 수 있다. 클래스마다 `.class`가 하나씩 나오는 것은 물론이고, 다음 선언들도 각각 별개의 `.class`를 만든다.

```kotlin
// 파일: Shapes.kt
class Circle(val r: Double)                 // Circle.class
class Rectangle(val w: Double, val h: Double) // Rectangle.class

data class Point(val x: Int, val y: Int)    // Point.class (+ 합성 멤버 내장)

fun makeGreeter(name: String): () -> String {
    return { "Hi, $name" }   // 람다 → 별도 합성 클래스 (또는 인라인이면 사라짐)
}

object Registry                              // Registry.class (싱글턴, INSTANCE 필드 포함)
enum class Dir { N, S, E, W }                // Dir.class
```

람다, 익명 객체, `object`, 중첩 클래스([[31 - 중첩 클래스와 이너 클래스와 익명 객체]])는 각각 클래스 파일을 만든다. 그래서 `.kt` 파일 하나를 컴파일하면 `.class` 파일이 여러 개 나오는 것이 정상이다. 파일과 클래스가 1대 1로 대응한다는 Java식 직관은 Kotlin에서 양방향 모두 성립하지 않는다.

### 6.3 프로퍼티는 필드 하나가 아니다

Kotlin 프로퍼티는 필드가 아니라 접근자(getter/setter)를 추상화한 것이다([[22 - 프로퍼티와 백킹 필드]]). JVM 백엔드는 프로퍼티를 필요한 경우 백킹 필드(private 필드) 하나와 `getX()` 메서드로 낮추고, `var`라면 `setX(...)` 메서드도 함께 만든다.

```kotlin
class Account(var balance: Long)
```

JVM 백엔드에서 이 클래스는 대략 다음과 같이 낮춰진다(개념적으로 같은 Java 코드).

```java
public final class Account {
    private long balance;               // 백킹 필드
    public Account(long balance) { this.balance = balance; }
    public final long getBalance() { return this.balance; }        // getter
    public final void setBalance(long value) { this.balance = value; } // setter
}
```

`account.balance = 100`이라는 프로퍼티 대입은 실제로는 `account.setBalance(100)` 메서드 호출로 컴파일된다. 반대로 계산 프로퍼티(백킹 필드 없이 게터만 있는 프로퍼티)는 필드 없이 메서드만 생성된다. `@JvmField`를 붙이면 접근자 없이 public 필드로 노출되는데, 이 트레이드오프는 22장(프로퍼티와 백킹 필드)과 45장(Java 상호운용)에서 자세히 다룬다.

### 6.4 클래스는 기본이 final이고, 함수는 기본이 static이 아니다

JVM 백엔드가 내보내는 접근 제어자에도 언어 철학이 반영되어 있다. Kotlin 클래스는 기본이 `final`이므로([[24 - 상속과 오버라이딩과 초기화 순서]]), 위 `Account`의 바이트코드에서는 클래스와 메서드에 `final`이 붙는다. `open`을 명시해야만 상속하거나 오버라이드할 수 있는 형태로 생성된다. 이는 "상속은 명시적인 설계 결정"이라는 Kotlin의 입장을 바이트코드 수준에서 강제한 것이다. 8절의 all-open 플러그인이 필요한 배경이기도 하다.

가시성도 대응된다. `public`은 Java의 `public`으로, `private`은 `private`으로 간다. 하지만 `internal`(모듈 가시성, [[26 - 가시성 한정자]])은 JVM에 대응하는 개념이 없다. 그래서 `public`으로 내보내되, 이름을 맹글링(mangling)해서 Java에서 실수로 호출하기 어렵게 만든다. 언어의 가시성 모델이 타깃의 가시성 모델과 정확히 겹치지 않을 때 백엔드가 어떻게 타협하는지 보여 주는 예다.

## 7. 컴파일 타임에 사라지는 것들: inline, reified, const

### 7.1 `const val`: 상수는 호출 지점으로 복사된다

`const val`은 컴파일 상수다([[11 - 변수와 초기화 - val과 const와 lateinit]]). 이 사실은 백엔드에서 중요한 의미를 가진다. **`const val`을 참조하는 곳의 바이트코드에는 그 이름이 아니라 값 자체가 들어간다.**

```kotlin
const val MAX_RETRIES = 3
fun retryPolicy(): Int = MAX_RETRIES
```

`retryPolicy`의 바이트코드는 `MAX_RETRIES`라는 필드를 읽지 않는다. 그냥 상수 `3`을 상수 풀에서 로드한다(`iconst_3`이나 `ldc` 계열 명령). 즉 컴파일 시점에 값이 호출 지점으로 인라인된다. 성능 면에서는 이점이지만 함정도 있다.

라이브러리의 `const val`을 바꾸고 그 라이브러리만 다시 빌드하면, 그 값을 이미 자기 바이트코드에 넣어 둔 소비자 쪽은 다시 컴파일하기 전까지 옛 값을 그대로 쓴다. 상수 인라이닝 때문에 생기는 이런 재컴파일 의존성은 9절의 증분 컴파일이 신경 써야 하는 문제다.

```kotlin
val runtimeMax = 3            // 일반 val: 필드 read (인라인 아님)
const val compileMax = 3      // const val: 호출처에 값 3이 박힘
```

일반 `val`과의 차이가 여기서 생긴다. `const`가 될 수 있는 것은 원시 타입이나 String이고, 최상위나 `object`/companion 안에 있으며, 리터럴로 초기화되어 컴파일 타임에 값이 확정되는 상수뿐이다. 이 제약이 바로 호출 지점에 값을 넣기 위한 전제 조건이다.

### 7.2 `inline`: 함수를 호출하는 대신 펼친다

`inline` 함수는 호출되는 대신 호출 지점에 본문이 펼쳐진다(15장 인라인 함수와 reified). 이것은 성능 힌트가 아니라 **의미를 바꾸는 변환**이며, IR 로워링(5.2절) 단계에서 일어난다.

```kotlin
inline fun measure(block: () -> Unit) {
    val start = System.nanoTime()
    block()
    println("elapsed: ${System.nanoTime() - start}")
}

fun run() {
    measure { println("일") }
}
```

`run`을 컴파일하면 `measure`를 호출하는 코드가 남지 않는다. 대신 `measure`의 본문과 람다 `{ println("일") }`이 `run` 안에 직접 펼쳐진다. 개념적으로는 다음과 같다.

```kotlin
fun run() {              // 인라이닝 후의 개념적 모습
    val start = System.nanoTime()
    println("일")         // 람다도 인라인 → 함수 객체 할당 없음
    println("elapsed: ${System.nanoTime() - start}")
}
```

여기서는 두 가지가 사라진다. 하나는 함수 호출의 프레임 비용이고, 다른 하나는 **람다를 담을 함수 객체의 할당**이다. 인라인이 아닌 고차 함수라면 `{ println("일") }`은 `Function0` 인터페이스를 구현하는 객체로 만들어져 힙에 할당된다(13장 함수 타입과 람다와 함수 참조의 FunctionN). 인라인 함수라면 그 객체 자체가 존재하지 않는다. 이것이 인라인의 진짜 가치이고, 동시에 코드가 여러 호출 지점에 복제되어 커지는 비용의 원인이다.

### 7.3 `reified`: 소거된 타입을 되살리는 컴파일 타임 기법

제네릭 타입은 JVM에서 소거된다(34장 제네릭 2). 즉 런타임에는 `List<String>`과 `List<Int>`를 구분할 수 없다. 그런데 `inline` 함수의 타입 파라미터에 `reified`를 붙이면, 런타임에 타입을 아는 것처럼 `is T`나 `T::class`를 쓸 수 있다. 이것이 가능한 이유는 전적으로 컴파일 타임에 있다.

```kotlin
inline fun <reified T> firstOfType(items: List<Any>): T? {
    for (item in items) if (item is T) return item   // is T 사용 가능
    return null
}

val nums = listOf("a", 1, "b", 2, 3.0)
val n = firstOfType<Int>(nums)   // => 1
```

`firstOfType<Int>`를 호출하면 인라이닝 과정에서 `T`가 구체 타입 `Int`로 **치환**된다. 즉 호출 지점에는 소거와 관계없는 구체적인 검사인 `if (item is Int)`가 펼쳐진다. 런타임에 타입 정보를 전달한 것이 아니라, 컴파일 타임에 호출 지점마다 타입을 넣어 둔 것이다.

그래서 `reified`는 치환할 자리, 즉 본문이 펼쳐질 자리가 있어야 하므로 반드시 `inline`과 함께 써야 한다. 또한 최상위 타입만 되살릴 수 있다. `List<String>`의 `String`은 여전히 소거된다. `reified`가 아는 것은 `T` 자체이지 `T`의 타입 인자가 아니다.

```kotlin
inline fun <reified T> typeName(): String = T::class.simpleName ?: "?"
typeName<String>()          // => "String"
typeName<List<Int>>()       // => "List"  ← 안쪽 Int는 알 수 없음(소거)
```

세 예(`const`, `inline`, `reified`)가 공통으로 보여 주는 것은 **런타임에 일어나는 특별한 동작처럼 보이는 많은 기능이 실은 컴파일 타임의 코드 변형으로 구현된다**는 점이다. 성능 이점이나 타입 정보가 실행 중에 생긴다고 오해하기 쉽지만, 사실은 컴파일러가 미리 코드를 작성해 두었을 뿐이다. 이 관점은 성능을 추론할 때(무엇이 할당되고 무엇이 할당되지 않는가)와 한계를 이해할 때(왜 `reified`는 인라인 없이 쓸 수 없는가) 모두 필요하다.

> [!caution] 성능 주의
> 인라인이 좋다고 아무 함수에나 `inline`을 붙여서는 안 된다. 본문이 큰 함수를 여러 곳에서 호출하면 그 본문이 모든 호출 지점에 복제되어 바이트코드가 커지고(코드 캐시 압박), 오히려 느려질 수 있다.
>
> `inline`을 쓸 타당한 이유는 대개 람다 인자의 객체 할당 제거, `reified`, 비지역 반환의 세 가지다. 그 밖에 "그냥 빠를 것 같아서"라는 이유는 근거가 약하다. 자세한 판단 기준은 15장(인라인 함수와 reified)에서 다룬다.

## 8. 컴파일러 플러그인: 외부 코드가 컴파일러 동작에 개입하는 통로

### 8.1 플러그인이 필요한 이유: final이라는 제약

6.4절에서 Kotlin 클래스는 기본이 `final`이라고 했다. 그런데 일부 JVM 프레임워크(대표적으로 프록시 기반 라이브러리)는 런타임에 클래스를 상속해 프록시를 만들어야 동작한다. `final` 클래스는 상속할 수 없으니 문제가 된다. 그렇다고 매번 `open`을 직접 붙이면 번거롭고 실수하기도 쉽다.

이 문제를 컴파일러 수준에서 해결하는 것이 **컴파일러 플러그인**이다. `all-open` 플러그인은 지정한 애노테이션이 붙은 클래스를 컴파일 시점에 자동으로 `open`으로 만든다. 소스에서는 `final`이지만 바이트코드에서는 `open`으로 생성된다.

```kotlin
// all-open 플러그인이 (가령) @Entity를 대상으로 설정돼 있다면
@Entity
class Product(val name: String)   // 소스상 final처럼 보이지만, 컴파일 결과는 open
```

비슷한 플러그인으로 `no-arg`(지정한 애노테이션이 붙은 클래스에 합성 무인자 생성자 추가), `kotlinx.serialization`(직렬화 코드 생성), `Compose` 관련 플러그인 등이 있다. 이들의 공통점은 **언어를 바꾸지 않고 컴파일러의 동작을 확장**한다는 것이다. 플러그인은 IR 로워링 단계 같은 곳에 훅(hook)을 걸어 IR을 추가하거나 변형한다.

> [!warning] 흔한 오해
> "Kotlin 언어 기능"과 "컴파일러 플러그인이 해 주는 일"을 혼동하기 쉽다. `data class`의 멤버 합성은 언어 명세의 일부(컴파일러 코어)지만, `@Serializable`의 직렬화 코드 생성은 별도 플러그인이 한다. 후자는 그 플러그인이 빌드에 설정되어 있을 때만 동작한다. "이 애노테이션이 왜 아무 효과가 없지?"라는 질문의 흔한 답은 "해당 컴파일러 플러그인이 켜져 있지 않다"이다.

### 8.2 kapt: Java 스텁을 거치는 옛 방식

애노테이션 프로세싱은 애노테이션이 붙은 선언을 읽어 새 코드를 생성하는, JVM 생태계의 오래된 기법이다. Java에는 `javac`의 애노테이션 처리 API(APT)가 있고, 수많은 라이브러리가 이 API를 기반으로 코드를 생성한다. 문제는 이 API가 **Java 소스 모델**을 전제한다는 점이다. Kotlin 코드는 Java 소스가 아니다.

`kapt`(Kotlin Annotation Processing Tool)는 이 문제를 우회해서 해결한다. Kotlin 코드에서 **Java 스텁**(stub), 즉 시그니처만 있고 본문은 비어 있는 가짜 Java 소스를 생성한 뒤, 기존 Java 애노테이션 프로세서를 그 스텁 위에서 실행한다.

```text
Kotlin 소스 ──▶ (kapt) Java 스텁 생성 ──▶ javac APT ──▶ 생성 코드
                     ▲ 이 스텁 생성 단계가 느림
```

이 스텁 생성 단계가 kapt의 병목이다. 실제로는 필요 없는 정보까지 담은 Java 소스를 만들어야 하고, `javac`를 한 번 더 실행하는 비용도 든다. 그래도 kapt는 Java 프로세서 생태계 전체와 호환된다는 큰 장점이 있어서 오랫동안 표준으로 쓰였다. 현재 kapt는 유지보수 모드에 가깝고, 새 코드에는 다음에 설명할 KSP를 권장한다.

### 8.3 KSP: Kotlin을 직접 이해하는 새 방식

**KSP**(Kotlin Symbol Processing)는 스텁을 거치는 우회 과정을 없앤다. KSP는 Java 소스 모델이 아니라 **Kotlin의 해소된 심볼(symbol)을 직접** 프로세서에 제공한다. 프로세서는 Kotlin 함수, 프로퍼티, 타입을 있는 그대로 순회하며 코드를 생성한다.

| | kapt | KSP |
|---|---|---|
| 동작 방식 | Java 스텁 생성 → javac APT | Kotlin 심볼 API 직접 제공 |
| 속도 | 느림(스텁+javac 왕복) | 빠름(스텁 없음) |
| Kotlin 이해도 | Java로 투영된 근사 | 널 가능성·`suspend` 등 Kotlin 개념 그대로 |
| 생태계 | 기존 Java 프로세서 호환 | KSP용으로 작성/이식된 프로세서 |
| 권장도(현재) | 유지보수 모드 | 신규 권장 |

KSP가 빠른 근본적인 이유는 파이프라인에서의 위치에 있다. KSP는 프론트엔드가 이미 해소해 둔 심볼 정보를 재사용하므로, Java 스텁을 만들고 `javac`를 다시 실행하는 중복 작업이 없다. 또한 KSP 프로세서는 `String?`과 `String`을 구분하고 `suspend` 함수를 인식하는 등, Java로 투영하면 사라졌을 Kotlin 고유의 정보를 그대로 볼 수 있다. 다만 프로세서를 KSP API로 새로 작성하거나 다시 작성해야 하므로, 생태계 전환이 필요했다.

리플렉션([[44 - 애노테이션과 리플렉션]])과의 관계도 짚어 둘 만하다. KSP와 kapt는 **컴파일 타임 코드 생성**이고, 리플렉션은 **런타임 타입 조사**다. 애노테이션 기반 동작이라는 같은 목적을 컴파일 타임에 정적으로 해결하면 KSP, 런타임에 동적으로 해결하면 리플렉션이다. 앞의 것은 시작이 빠르고 안전하지만 유연성이 떨어지고, 뒤의 것은 그 반대다. 이 트레이드오프는 44장(애노테이션과 리플렉션)에서 자세히 다룬다.

## 9. 증분 컴파일과 빌드: 두 번째 빌드가 빠른 이유

### 9.1 전부 다시 컴파일하지 않기

작은 프로젝트에도 파일은 수백 개가 있다. 파일 하나를 고칠 때마다 전부 다시 컴파일하면 개발 주기가 느려진다. **증분 컴파일**(incremental compilation)은 바뀐 것과 그 변경에 영향을 받는 것만 다시 컴파일한다. 핵심은 무엇이 영향을 받는지를 어떻게 알아내느냐다.

컴파일러와 빌드 도구는 이전 컴파일의 산출물과 함께 파일 사이의 **의존 관계**를 기록해 둔다. 어떤 파일이 바뀌면, 그 파일이 노출하는 API(공개 시그니처)가 바뀌었는지 확인한다. 함수 *본문*만 바뀌고 공개 시그니처가 그대로라면, 그 파일을 참조하는 다른 파일은 다시 컴파일할 필요가 없다. 그 파일들이 의존하는 계약(시그니처)이 변하지 않았기 때문이다.

반대로 파라미터 추가나 반환 타입 변경처럼 공개 시그니처가 바뀌면, 그 선언을 쓰는 모든 파일이 다시 컴파일할 대상(dirty)이 된다.

```text
Foo.kt의 private 헬퍼 본문만 수정
  → Foo.kt만 재컴파일, 소비자는 그대로

Foo.kt의 public 함수 시그니처 변경
  → Foo.kt + 그 함수를 부르는 모든 파일 재컴파일
```

### 9.2 ABI: 재컴파일 여부를 가르는 경계

이 판단의 기준은 **ABI**(Application Binary Interface), 즉 다른 모듈이나 파일이 의존할 수 있는 공개 표면이다. 공개 함수 시그니처, 공개 프로퍼티 타입, 클래스 계층 등이 ABI에 속한다. private 구현 세부는 ABI가 아니다. 증분 컴파일은 ABI가 바뀌었는지를 기준으로 영향 범위를 정한다.

7.1절의 `const val` 인라이닝이 여기서 다시 문제가 된다. `const val`의 값은 소비자의 바이트코드에 들어가므로, 그 값을 바꾸면 시그니처는 그대로여도 소비자를 다시 컴파일해야 올바른 값이 반영된다. 따라서 증분 컴파일은 이런 값 수준의 의존성도 추적해야 한다. 증분 컴파일이 단순히 시그니처만 보면 되는 문제가 아니라는 점을 보여 주는 예다.

> [!caution] 성능 주의
> 증분 컴파일의 이점을 최대한 살리려면 공개 API를 자주 바꾸지 않는 것이 좋다. 널리 쓰이는 유틸 파일의 public 시그니처를 자주 바꾸면 그때마다 대규모 재컴파일이 일어난다. 반대로 구현을 `private`/`internal`로 잘 감싸 두면, 내부를 아무리 고쳐도 영향이 그 파일(또는 모듈) 안에 머문다. 캡슐화(26장 가시성 한정자)는 좋은 설계 원칙일 뿐 아니라 빌드 성능 전략이기도 하다.

### 9.3 컴파일 산출물과 메타데이터

JVM 백엔드의 산출물은 `.class` 파일이지만, 그 안에는 Java에 없는 정보도 담긴다. Kotlin 컴파일러는 각 클래스 파일에 `@Metadata` 애노테이션을 넣어, 널 가능성, 프로퍼티, 기본 인자, `internal`의 원래 이름처럼 **Java 바이트코드로는 표현되지 않는 Kotlin 고유 정보**를 보존한다. 다른 Kotlin 모듈이 이 클래스를 라이브러리로 참조하면, 컴파일러는 이 메타데이터를 읽어 원래의 Kotlin 시그니처를 복원한다.

이 메타데이터 덕분에 컴파일된 라이브러리를 사용하는 쪽에서도 널 안전성이나 기본 인자 같은 기능이 그대로 동작한다. 순수 Java 라이브러리를 쓸 때처럼 메타데이터가 없으면, 컴파일러는 널 가능성을 알 수 없으므로 **플랫폼 타입 `T!`** 로 취급한다(6장 널 안전성, 45장 Java 상호운용). Kotlin 라이브러리는 널 안전한데 Java 라이브러리는 그렇지 않은 이유가 바로 이 메타데이터의 유무다.

## 10. 디컴파일: 컴파일 결과를 직접 확인하는 방법

### 10.1 직접 확인해야 하는 이유

이 장의 주장은 대부분 "컴파일러가 X를 한다"는 형태다. 데이터 클래스는 `equals`를 생성하고, `const`는 값을 호출 지점에 넣고, 인라인은 람다 객체를 없앤다. 이런 주장을 확인하는 가장 확실한 방법은 컴파일 결과를 직접 보는 것이다. Kotlin이 실용적인 언어라는 점은 이 검증을 쉽게 할 수 있도록 만들어 두었다는 데서도 드러난다.

가장 흔한 방법은 IntelliJ IDEA의 **Tools → Kotlin → Show Kotlin Bytecode**다. 이 메뉴는 현재 파일의 JVM 바이트코드를 보여 주고, 그 창의 **Decompile** 버튼을 누르면 바이트코드를 다시 *Java 소스로* 역변환해 보여 준다. 즉 내 Kotlin 코드가 어떤 Java 코드에 해당하는지를 대략적으로 볼 수 있다. 명령줄에서는 컴파일한 `.class`에 `javap -c`를 실행해 원시 바이트코드 명령을 볼 수도 있다.

> [!info] 역사 메모
> 디컴파일해서 확인하는 문화는 Kotlin 학습의 오랜 관습이다. 초창기부터 어떤 문법 설탕이 실제로 무엇으로 바뀌는지를 Java로 역변환해 이해하는 방식이 널리 쓰였다.
>
> 다만 주의할 점이 있다. 디컴파일 결과는 **JVM 백엔드**의 산출물을 근사한 것이고, 합성 클래스 이름이나 브리지 메서드 유무 같은 세부는 컴파일러 버전에 따라 달라질 수 있다. 개념을 확인하는 용도이지 명세가 아니다. 또한 이 결과는 다른 백엔드에는 해당하지 않는다.

### 10.2 데이터 클래스를 디컴파일하면

```kotlin
data class Point(val x: Int, val y: Int)
```

이 한 줄을 디컴파일하면(개념적으로 같은 Java 코드) 컴파일러가 대신 작성해 준 코드가 드러난다.

```java
public final class Point {
    private final int x;
    private final int y;
    public Point(int x, int y) { this.x = x; this.y = y; }
    public final int getX() { return this.x; }
    public final int getY() { return this.y; }
    public final int component1() { return this.x; }   // 구조 분해용
    public final int component2() { return this.y; }
    public final Point copy(int x, int y) { return new Point(x, y); }
    public String toString() { return "Point(x=" + x + ", y=" + y + ")"; }
    public int hashCode() { return this.x * 31 + this.y; }   // 개념적
    public boolean equals(Object other) { /* x,y 비교 */ }
}
```

여기서 5.2절과 27장(데이터 클래스)의 주장을 직접 확인할 수 있다. `component1`/`component2`는 구조 분해([[20 - 구조 분해]])를 뒷받침한다. `copy`는 새 인스턴스를 만드는 평범한 메서드일 뿐이므로 얕은 복사라는 점도 보인다. 또한 `equals`/`hashCode`가 **주 생성자 프로퍼티만** 사용한다는 점, 즉 본문에 선언한 프로퍼티는 여기에 포함되지 않는다는 점이 드러난다. 특별한 기능처럼 보이던 것이 실은 생성된 평범한 코드다.

### 10.3 인라인과 const를 디컴파일하면

7절의 주장도 확인할 수 있다. 다음 코드를 컴파일한 뒤 이를 사용하는 함수를 디컴파일해 보자.

```kotlin
const val LIMIT = 10
inline fun repeatTwice(action: () -> Unit) { action(); action() }

fun demo() {
    val x = LIMIT              // 디컴파일: int x = 10;  ← 상수가 박힘
    repeatTwice { println("!") }  // 디컴파일: println("!"); println("!");  ← 펼쳐짐, 람다 객체 없음
}
```

`LIMIT`이 있던 자리에는 `10`이 들어가고, `repeatTwice` 호출은 사라진 채 본문이 두 번 펼쳐지며, 람다를 담을 함수 객체는 아예 만들어지지 않은 것을 볼 수 있다. 반대로 `inline`을 빼고 같은 코드를 디컴파일하면, `repeatTwice`는 호출로 남고 람다는 `Function0` 구현 객체로 만들어진다. 이 둘을 비교해 보면 인라인이 무엇을 없애는지 가장 분명하게 알 수 있다.

### 10.4 검증하는 습관이 이해로 이어진다

디컴파일은 단순한 요령이 아니라 지식을 확인하는 태도다. "컴파일러가 이렇게 할 것이다"라는 추측을 "컴파일러가 이렇게 한다"는 관찰로 바꿔 준다. 무엇이 할당되는지 같은 성능 문제, Java에서 이 함수의 이름이 무엇인지 같은 상호운용 문제, 이 애노테이션이 정말 코드를 생성했는지 같은 언어 기능의 실체에 관한 문제의 답은 대개 컴파일 결과에 있다.

이 습관은 이 시리즈 전체에서 계속 쓰인다. 앞으로 어떤 장에서 "컴파일러가 X를 한다"고 말하면, 독자는 그것을 직접 열어 확인할 수 있어야 한다.
