[[43 - 동시성과 메모리 모델]]까지는 코드가 *실행되는* 세계를 다뤘다. 값이 스레드 사이에서 어떻게 보이는지, 언제 재배열되는지, 어떤 연산이 원자적인지를 살펴보았다. 이 장에서는 방향을 바꿔, 코드가 *자기 자신을 서술하고 자기 자신을 들여다보는* 능력을 다룬다.

애노테이션(annotation)은 선언에 붙는 구조화된 메타데이터이고, 리플렉션(reflection)은 실행 중인 프로그램이 자신의 클래스, 함수, 프로퍼티를 값처럼 다루는 능력이다. 애노테이션은 선언에 대해 무언가를 기록해 두고, 리플렉션은 기록된 내용을 나중에 읽어 내므로 둘은 한 쌍을 이룬다. 직렬화 라이브러리, 의존성 주입 컨테이너, ORM, 테스트 프레임워크는 모두 애노테이션으로 "표시"하고 리플렉션으로 "발견"하는 구조를 바탕으로 동작한다.

이 장에서는 애노테이션의 동작 방식(선언, 파라미터, 사용 지점 타깃, 메타 애노테이션, 리텐션)과 리플렉션의 동작 방식(`KClass`, `KCallable`, `KType`, 호출과 접근)을 다룬다. 애노테이션이 Java 쪽에서 어떻게 보이는지, `@JvmStatic`·`@JvmField`·`@JvmName`·`@Throws`가 상호운용에서 왜 필요한지는 [[45 - Java 상호운용]]에서 전체적으로 설명하고, 여기서는 리플렉션과 관련된 부분만 짚는다.

함수 참조 `::foo`의 문법은 [[13 - 함수 타입과 람다와 함수 참조]]에서 설명했으며, 이 장에서는 그 참조가 사실 `KFunction` 객체라는 점을 덧붙인다. `reified`가 소거를 국소적으로 우회하는 방식은 [[15 - 인라인 함수와 reified]]와 [[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]에서 다루고, 이 장에서는 `typeOf`가 타입 정보를 캡처하는 방식이 그와 어떻게 다른지 비교한다.

마지막으로 리플렉션의 실제 비용과, 그 비용을 컴파일 타임으로 옮기는 대안인 KSP를 살펴본다.

## 1. 애노테이션이란 무엇인가: 선언에 붙는 구조화된 상수

### 1.1 애노테이션은 코드에 대한 메타데이터다

애노테이션은 클래스, 함수, 프로퍼티, 파라미터 같은 *선언*(declaration)에 붙이는 이름표다. 이 이름표는 프로그램의 동작을 직접 바꾸지 않고, "이 선언에는 이런 성질이 있다"는 사실만 기록한다. 컴파일러나 애노테이션 프로세서, 런타임 라이브러리가 나중에 그 기록을 읽고 실제 작업을 *수행한다*. 애노테이션 자체는 아무 일도 하지 않는다.

```kotlin
annotation class Positive

class BankAccount(@Positive val balance: Long)
```

`@Positive`는 `balance`에 "이 값은 양수여야 한다"고 표시했을 뿐이고, 그 자체로는 아무것도 검증하지 않는다. 누군가 리플렉션이나 애노테이션 프로세서로 `@Positive`를 찾아 검사 코드를 만들어야 비로소 의미가 생긴다. 이처럼 애노테이션은 스스로 동작하지 않으며, 명령이 아니라 *데이터*다.

"애노테이션은 데이터다"라는 관점은 이 장 전체에 적용된다. 애노테이션 인스턴스는 사실상 컴파일 타임에 확정되는 불변 값이므로, 그 안에 담을 수 있는 값에는 강한 제약이 있다(1.3절). 또한 데이터이므로 어딘가에 저장되어야 하는데, 어디에 얼마나 오래 저장되는지를 정하는 것이 리텐션이다(3.2절).

### 1.2 왜 주석이 아니라 애노테이션인가

일반 주석(`// ...`, `/* ... */`)은 렉서가 토큰화 단계에서 버리므로([[03 - 렉시컬 구조와 세미콜론 추론]]) 컴파일러에게는 존재하지 않는 것과 같다. 반면 애노테이션은 문법의 정식 구성 요소이고, 타입 검사와 이름 해소(resolution)를 거친다. `@Positvie`처럼 오타를 내면 "그런 애노테이션이 없다"는 컴파일 에러가 난다. 주석에 오타가 있어도 아무 일도 일어나지 않는 것과 다르다.

```kotlin
@Deprecated("use transfer() instead")  // 진짜 선언을 참조 — 타입 검사됨
fun withdraw(amount: Long) { /* ... */ }

// @Deprcated("...")  // 만약 애노테이션이었다면: 컴파일 에러 (이름 없음)
```

즉 애노테이션은 컴파일러가 이해하고 검증하며, 필요하면 보존하는 구조화된 메타데이터다. 사람만 읽는 자유 텍스트인 주석과는 수준이 다르다. KDoc 주석(`/** ... */`)도 컴파일된 산출물에는 남지 않지만, 애노테이션은 리텐션 설정에 따라 `.class` 파일이나 런타임까지 남는다.

### 1.3 애노테이션 파라미터가 될 수 있는 것: 컴파일 상수만

애노테이션은 파라미터를 가질 수 있지만, 그 값은 반드시 *컴파일 타임 상수*여야 한다. 애노테이션 인스턴스는 클래스 메타데이터에 통째로 기록되므로, 실행 시점에야 정해지는 값(예: `readLine()`의 결과)은 담을 수 없다. 명세가 허용하는 파라미터 타입은 다음으로 제한된다.

| 허용되는 파라미터 타입 | 예 |
|------------------------|-----|
| JVM 원시형에 대응하는 타입 | `Int`, `Long`, `Double`, `Boolean`, `Char`, `Byte`, `Short` |
| `String` | `"use transfer()"` |
| 클래스 리터럴 (`KClass`) | `String::class`, `BankAccount::class` |
| enum 상수 | `AnnotationRetention.RUNTIME` |
| 다른 애노테이션 | `ReplaceWith("transfer()")` |
| 위 타입들의 배열 | `["a", "b"]`, `[Int::class, Long::class]` |

이 목록에 없는 타입은 모두 쓸 수 없다. 임의의 객체, 컬렉션(`List`/`Set`/`Map`), nullable 타입, 함수 타입은 애노테이션 파라미터가 될 수 없다.

```kotlin
annotation class Config(
    val name: String,           // OK
    val level: Int,             // OK
    val target: KClass<*>,      // OK — 클래스 리터럴
    val tags: Array<String>,    // OK — 배열
)

// annotation class Bad(val items: List<String>)  // 컴파일 에러: List는 애노테이션 인자로 부적합
// annotation class Bad2(val name: String?)        // 컴파일 에러: nullable 불가
```

> [!note] 명세 기준
> 애노테이션 파라미터로 `List`는 쓸 수 없고 `Array`만 쓸 수 있는 이유는 역사적이면서 구조적이다. 애노테이션은 JVM의 애노테이션 모델에서 비롯되었고, 이 모델에서 컬렉션 값은 배열로만 표현된다. Kotlin은 이 제약을 그대로 물려받았다. 그래서 여러 값을 받으려면 `vararg`(내부적으로 배열)나 `Array`를 쓴다. [[38 - 컬렉션 - 읽기 전용과 가변]]에서 다루는 `Array`와 `List`의 계약 차이가 실무에서 드러나는 사례 가운데 하나다.

`vararg`도 쓸 수 있으며, 사실 배열 파라미터의 자연스러운 대안이다.

```kotlin
annotation class Roles(vararg val names: String)

@Roles("admin", "auditor")
class AdminPanel
```

nullable을 쓸 수 없다는 점은 실무에서 자주 걸림돌이 된다. "옵션 없음"을 표현하려면 nullable 대신 빈 문자열이나 특별한 상수 같은 *센티널*(sentinel) 기본값을 관례로 쓴다. 예를 들어 `@JsonProperty(val name: String = "")`에서 빈 문자열은 "프로퍼티 이름을 그대로 쓰라"는 뜻으로 약속되어 있다.

### 1.4 기본값과 애노테이션 인스턴스화

애노테이션 파라미터는 기본값(`= ...`)을 가질 수 있고, 이 기본값도 컴파일 상수여야 한다. 애노테이션을 붙이는 문법 `@Config("x")`는 사실 애노테이션 인스턴스를 *생성*하는 문법이다.

```kotlin
annotation class Retryable(
    val maxAttempts: Int = 3,
    val backoffMillis: Long = 100L,
)

@Retryable                       // 둘 다 기본값
fun fetchRate() { /* ... */ }

@Retryable(maxAttempts = 5)      // 하나만 지정 — 이름 붙은 인자
fun fetchQuote() { /* ... */ }
```

Kotlin에서는 리플렉션으로 애노테이션 인스턴스를 읽은 뒤 *생성*할 수도 있다. 애노테이션 클래스는 사실상 프로퍼티만 가진 특별한 형태이므로, 리플렉션이 반환하는 애노테이션 객체의 프로퍼티를 그대로 읽으면 된다.

```kotlin
val ann = ::fetchQuote.annotations.filterIsInstance<Retryable>().first()
println(ann.maxAttempts)     // => 5
println(ann.backoffMillis)   // => 100  (기본값)
```

여기서 이미 리플렉션이 등장했다. `::fetchQuote.annotations`는 함수 참조의 리플렉션 API다. 애노테이션과 리플렉션은 실제로 이렇게 함께 쓰인다. 다만 위 코드가 `ann.maxAttempts`로 `5`를 읽으려면 `@Retryable`이 *런타임까지 보존*되어야 한다. 이 내용은 3.2절에서 다룬다.

## 2. 애노테이션 선언: `annotation class`의 구조

### 2.1 `annotation class`는 무엇으로 컴파일되는가

`annotation class`는 일반 클래스가 아니다. 상태(백킹 필드)를 가진 로직을 넣을 수 없고, 본문에 함수를 둘 수 없으며, 상속 계층에도 참여하지 않는다. 애노테이션은 불변 데이터이므로 파라미터는 반드시 `val`이어야 하고 `var`는 쓸 수 없다.

```kotlin
annotation class Audited(val by: String)

// annotation class Broken(var by: String)      // 컴파일 에러: var 불가
// annotation class Broken2(val by: String) {    // 본문 로직 제약
//     fun doSomething() {}                       // 컴파일 에러: 멤버 함수 불가
// }
```

JVM 백엔드에서 애노테이션 클래스는 `java.lang.annotation.Annotation`을 확장하는 인터페이스 형태의 특수한 바이트코드로 컴파일된다. 덕분에 Java에서도 Kotlin 애노테이션을 애노테이션으로 인식하며, 이것이 상호운용의 기반이 된다(45장 Java 상호운용). 다른 백엔드(Native/JS/Wasm)에서는 표현 방식이 다르고, 리플렉션 기능도 JVM과 같지 않다. 이 장의 리플렉션 설명은 따로 언급하지 않는 한 JVM 백엔드를 기준으로 한다.

애노테이션 클래스는 중첩 선언으로 다른 애노테이션이나 enum, 애노테이션 파라미터로 쓸 상수를 담을 수 있다. 다만 이것은 "본문에 로직을 넣는 것"과는 다른, 순수한 선언적 중첩이다.

### 2.2 애노테이션에 애노테이션 붙이기: 중첩 구조

애노테이션 파라미터의 타입으로 다른 애노테이션을 쓸 수 있다는 점(1.3절)은 실무에서 애노테이션을 구조화하는 데 활용된다.

```kotlin
annotation class Column(val name: String, val nullable: Boolean = true)

annotation class Table(
    val name: String,
    val columns: Array<Column>,
)

@Table(
    name = "accounts",
    columns = [
        Column("id", nullable = false),
        Column("balance"),
    ],
)
class AccountSchema
```

`[Column(...), Column(...)]`은 배열 리터럴이고, 그 원소는 애노테이션 인스턴스다. 이 전체가 컴파일 타임 상수로 클래스 메타데이터에 기록된다. 실행 중에 어떤 계산도 끼어들지 않기 때문에 애노테이션이 "선언적"이라고 할 수 있다.

### 2.3 애노테이션 클래스는 인스턴스화할 수 없(었)다: 그리고 지금은

예전에는 Kotlin에서 `Audited("x")`처럼 코드로 애노테이션 클래스의 인스턴스를 직접 만들 수 없었고, `@Audited("x")` 형태로 붙이는 것만 가능했다. Kotlin 1.6부터는 애노테이션 클래스를 *생성자처럼* 호출해 인스턴스를 만들 수 있다.

```kotlin
val marker = Audited(by = "system")   // 1.6+ : 애노테이션 인스턴스 생성 가능
println(marker.by)                    // => system
```

> [!info] 역사 메모
> 이 기능(annotation class instantiation, Kotlin 1.6)은 리플렉션으로 애노테이션을 다룰 때 "찾은 애노테이션과 비교할 기준값"을 만들거나, 애노테이션을 요구하는 라이브러리 API에 값을 넘길 때 쓴다. 애노테이션 인스턴스는 여전히 불변이며, 프로퍼티를 읽는 것 외의 로직은 없다. 인스턴스화가 가능해졌다고 해서 애노테이션이 일반 클래스가 된 것은 아니다.

## 3. 메타 애노테이션: 애노테이션을 규정하는 애노테이션

애노테이션에 붙는 애노테이션을 메타 애노테이션이라고 한다. 메타 애노테이션은 "이 애노테이션을 어디에, 얼마나 오래, 몇 번 붙일 수 있는가"를 정한다. 핵심은 `@Target`, `@Retention`, `@Repeatable`, `@MustBeDocumented` 네 가지다.

### 3.1 `@Target`: 붙일 수 있는 자리

`@Target`은 애노테이션을 붙일 수 있는 선언 종류를 `AnnotationTarget` enum으로 제한한다.

```kotlin
@Target(AnnotationTarget.CLASS, AnnotationTarget.FUNCTION)
annotation class Component

@Component class Service       // OK
@Component fun handler() {}    // OK

// @Component val x = 1        // 컴파일 에러: 프로퍼티는 대상이 아님
```

`AnnotationTarget`의 값은 `CLASS`, `ANNOTATION_CLASS`, `TYPE_PARAMETER`, `PROPERTY`, `FIELD`, `LOCAL_VARIABLE`, `VALUE_PARAMETER`, `CONSTRUCTOR`, `FUNCTION`, `PROPERTY_GETTER`, `PROPERTY_SETTER`, `TYPE`, `EXPRESSION`, `FILE`, `TYPEALIAS`이다.

이 가운데 `TYPE`, `EXPRESSION`, `TYPE_PARAMETER`는 선언이 아니라 *사용처*에 붙는 특별한 대상이다.

> [!note] 명세 기준
> `@Target`을 생략하면 애노테이션은 *대부분의 선언 대상*(클래스, 함수, 프로퍼티, 생성자, 값 파라미터 등)에 붙을 수 있는 기본 집합을 갖는다. 하지만 `EXPRESSION`이나 `TYPE` 같은 특수 대상은 기본 집합에 들어 있지 않다.
>
> 따라서 지역 표현식에 붙이는 `@Suppress`처럼 표현식에 붙이는 애노테이션을 만들려면 `@Target(AnnotationTarget.EXPRESSION)`을 명시해야 한다. 또한 표현식은 바이너리에 선언으로 남지 않으므로, 그런 애노테이션은 `SOURCE` 리텐션이어야 한다.

`EXPRESSION` 대상 애노테이션이 반드시 `@Retention(SOURCE)`여야 한다는 규칙은 논리적으로 당연하다. 표현식은 `.class` 파일에 별도의 선언으로 남지 않으므로, 거기에 붙은 애노테이션을 바이너리에 저장할 자리가 없다.

### 3.2 `@Retention`: 얼마나 오래 남는가

리텐션은 이 장에서 실무적으로 가장 중요한 메타 애노테이션이다. 리텐션은 애노테이션이 컴파일 파이프라인의 어느 단계까지 보존되는지를 결정한다.

```text
소스(.kt) ──컴파일──> 바이너리(.class) ──클래스로딩──> 런타임(JVM)
   │                        │                              │
 SOURCE                  BINARY                        RUNTIME
 여기서 버림           여기까지 남음                  여기까지 남음
 (프로세서만 봄)       (리플렉션 X)                   (리플렉션 O)
```

| 리텐션 | `.class`에 저장? | 런타임 리플렉션으로 읽힘? | 용도 |
|--------|:---:|:---:|------|
| `SOURCE` | ✗ | ✗ | 컴파일러/애노테이션 프로세서 전용 (`@Suppress`, `@JvmSynthetic`) |
| `BINARY` | ✓ | ✗ | 바이트코드 도구용이지만 런타임 리플렉션에는 숨김 |
| `RUNTIME` | ✓ | ✓ | 런타임 리플렉션으로 읽어야 하는 애노테이션 (기본값) |

핵심은 **Kotlin 애노테이션의 기본 리텐션은 `RUNTIME`** 이라는 점이다. 이 점은 Java와 다르다. Java 애노테이션의 기본 리텐션은 `CLASS`(= Kotlin의 `BINARY`)다. 그래서 Kotlin에서는 `@Retention`을 붙이지 않아도 리플렉션으로 애노테이션을 읽을 수 있다.

```kotlin
annotation class Tag(val v: String)   // @Retention 없음 → RUNTIME (기본)

@Tag("hot")
class Cache

fun main() {
    val found = Cache::class.annotations.filterIsInstance<Tag>().firstOrNull()
    println(found?.v)   // => hot   (RUNTIME이라 읽힘)
}
```

리텐션을 `@Retention(AnnotationRetention.SOURCE)`나 `BINARY`로 바꾸면 리플렉션이 애노테이션을 볼 수 없으므로 위의 `firstOrNull()`은 `null`을 반환한다.

> [!warning] 흔한 오해
> "애노테이션을 붙였는데 리플렉션으로 읽히지 않는다"는 버그는 대부분 리텐션 때문에 생긴다. 특히 Java로 정의된 애노테이션을 Kotlin에서 쓸 때는 주의해야 한다. Java의 기본 리텐션은 런타임에 읽히지 않는 `CLASS`이므로, `@Retention(RetentionPolicy.RUNTIME)`이 명시되어 있는지 확인해야 한다. Kotlin 애노테이션끼리라면 기본값이 `RUNTIME`이라 이 함정에 덜 빠진다.

`SOURCE` 리텐션의 대표적인 예는 `@Suppress`다. `@Suppress`는 컴파일러에게 경고를 억제하라고 지시할 뿐이므로, 컴파일한 뒤에는 흔적을 남길 이유가 없다. 애노테이션 프로세서(KSP/kapt)가 사용하는 애노테이션도 대개 `SOURCE`나 `BINARY`다. 코드 생성이 끝나면 런타임까지 가져갈 필요가 없기 때문이다.

### 3.3 `@Repeatable`: 같은 자리에 여러 번

기본적으로 같은 애노테이션을 한 선언에 두 번 붙이면 에러가 난다. `@Repeatable`을 붙이면 여러 번 붙일 수 있다.

```kotlin
@Repeatable
annotation class Schedule(val cron: String)

@Schedule("0 0 * * *")
@Schedule("0 12 * * *")
fun runBatch() { /* ... */ }
```

> [!note] 명세 기준
> JVM 백엔드에서 `@Repeatable` 애노테이션을 여러 번 붙이면, 컴파일러가 내부적으로 그 애노테이션들을 담는 *컨테이너 애노테이션*을 합성한다(Java의 repeatable annotation 모델과 호환된다). Kotlin 1.6부터는 `RUNTIME` 리텐션 애노테이션도 반복할 수 있으며, 리플렉션(`kotlin-reflect`)은 반복된 애노테이션을 풀어서 각각을 리스트로 돌려준다. 그 이전에는 런타임 반복 애노테이션 지원에 제약이 있었다.

### 3.4 `@MustBeDocumented`

`@MustBeDocumented`는 해당 애노테이션을 API 문서(예: Dokka로 생성하는 문서)에 포함하라는 표시다. 동작에는 영향을 주지 않는 순수한 문서화 지침이며, `@Deprecated`나 `@Throws`처럼 공개 API 계약의 일부인 애노테이션에 어울린다.

## 4. 사용 지점 타깃: Kotlin 애노테이션에서 가장 어려운 부분

### 4.1 하나의 프로퍼티는 여러 선언으로 나뉜다

Kotlin에서 애노테이션이 어렵게 느껴지는 진짜 이유가 여기에 있다. [[22 - 프로퍼티와 백킹 필드]]에서 보았듯이 Kotlin의 프로퍼티는 단일한 요소가 아니라 여러 요소의 묶음이다. `class C(val name: String)` 한 줄은 JVM 백엔드에서 대략 다음과 같이 펼쳐진다.

```text
class C(val name: String)   ──펼치면──>

  ├─ 생성자 파라미터  name          (VALUE_PARAMETER / @param:)
  ├─ 백킹 필드        name          (FIELD / @field:)
  ├─ 게터            getName()      (PROPERTY_GETTER / @get:)
  └─ (var라면) 세터   setName(v)     (PROPERTY_SETTER / @set:)
      그리고 그 세터 파라미터        (@setparam:)
```

그렇다면 프로퍼티에 `@Foo`를 붙였을 때, 이 애노테이션은 필드와 게터, 생성자 파라미터 가운데 어디로 가야 할까? 이 모호함을 해결하는 것이 **사용 지점 타깃**(use-site target)이다. `@get:`, `@set:`, `@field:`, `@param:` 같은 접두어로 애노테이션을 정확히 어느 요소에 붙일지 지정한다.

```kotlin
class Person(
    @field:Positive val age: Int,        // 백킹 필드에
    @get:JvmName("fullName") val name: String,  // 게터에
    @param:NotBlank val id: String,      // 생성자 파라미터에
)
```

### 4.2 사용 지점 타깃의 전체 목록

| 타깃 | 가리키는 대상 |
|------|--------------|
| `@file:` | 파일 (최상위, `@file:JvmName` 등) |
| `@property:` | 프로퍼티 자체 (Kotlin 메타데이터에만 저장되고 Java에서는 보이지 않음) |
| `@field:` | 백킹 필드 |
| `@get:` | 게터 |
| `@set:` | 세터 |
| `@param:` | 생성자 값 파라미터 |
| `@setparam:` | 세터의 파라미터 |
| `@receiver:` | 확장 함수/프로퍼티의 수신 객체 파라미터 |
| `@delegate:` | 위임 프로퍼티가 저장하는 위임 인스턴스 필드 |

`@file:`은 파일 맨 위, 패키지 선언보다도 앞에 온다. 이 애노테이션은 파일이 컴파일된 클래스(`FooKt`)에 영향을 준다.

```kotlin
@file:JvmName("MathUtils")
package geometry

fun area(r: Double) = Math.PI * r * r
```

`@receiver:`는 확장의 수신 객체를 대상으로 한다.

```kotlin
fun @receiver:Positive Int.factorial(): Long { /* ... */ }
```

`@delegate:`는 [[23 - 위임 프로퍼티]]에서 위임 객체를 담는 숨은 필드를 대상으로 한다. 예를 들어 `by lazy`로 만든 위임 필드에 `@Transient`를 붙이고 싶다면 `@delegate:Transient`를 쓴다.

### 4.3 타깃을 생략하면 어떻게 되는가

사용 지점 타깃을 생략하면 컴파일러는 애노테이션의 `@Target`을 보고 *적용할 수 있는 첫 번째* 대상을 자동으로 고른다. 이때 우선순위가 정해져 있다.

```text
타깃 생략 시 자동 선택 우선순위:
   param  →  property  →  field
   (앞에서부터, 애노테이션이 그 대상을 허용하는 첫 번째로)
```

즉 애노테이션이 `VALUE_PARAMETER`를 허용하면 생성자 파라미터에 붙고, 허용하지 않으면 `PROPERTY`에, 그것도 아니면 `FIELD`에 붙는다. 이 자동 규칙은 종종 직관과 어긋난다.

```kotlin
annotation class NotBlank   // @Target 없음 → 여러 대상 허용

class User(@NotBlank val name: String)
// name은 생성자 파라미터(param)이기도, 프로퍼티이기도, 필드이기도 하다.
// 자동 규칙상 param이 먼저 → @NotBlank는 생성자 파라미터에 붙는다.
```

검증 라이브러리가 리플렉션으로 *필드*를 훑는데 애노테이션이 *파라미터*에 붙어 버렸다면, 라이브러리는 그 애노테이션을 찾지 못한다. "분명히 붙였는데 적용되지 않는다"는 문제의 또 다른 흔한 원인이다. 해결책은 `@field:NotBlank`처럼 타깃을 명시하는 것이다.

> [!warning] 흔한 오해
> "프로퍼티에 애노테이션을 붙이면 그 프로퍼티의 모든 요소(필드, 게터, 파라미터)에 붙는다"고 오해하는 경우가 많다. 실제로는 *정확히 하나의 대상*에만 붙는다. 여러 곳에 붙이고 싶다면 `@field:Foo @get:Foo val x`처럼 각각을 명시해야 한다. 자동 선택은 "여러 곳"이 아니라 "우선순위상 첫 번째 하나"를 고른다.

`@property:` 타깃은 특이하다. 이 타깃은 Kotlin의 프로퍼티라는 개념 자체에 붙고, 그 정보는 Kotlin 메타데이터에만 저장된다. 따라서 Java 리플렉션으로는 보이지 않고 Kotlin 리플렉션(`kotlin-reflect`)으로만 읽을 수 있다. 프레임워크가 "Kotlin 프로퍼티" 단위의 애노테이션을 원할 때 쓴다.

Java와 비교하면 왜 이렇게 설계할 수밖에 없었는지가 분명해진다. Java에서는 필드와 게터가 서로 다른 이름을 가진 별개의 선언이므로, 애노테이션을 필드에 붙일지 게터에 붙일지가 문법적으로 이미 구분되어 있다.

```java
// Java: 필드와 게터가 문법적으로 별개 — 애노테이션 위치가 자명
class Person {
    @Positive private int age;        // 필드에
    @JsonProperty public int getAge() { return age; }  // 게터에
}
```

반면 Kotlin은 `val age: Int` 한 줄에 이 세 요소가 모두 들어 있으므로, 애노테이션을 붙일 자리를 문법으로 다시 고를 수 있게 해야 했다. 그 수단이 접두어다.

### 4.4 왜 이렇게 설계했는가: 상호운용의 대가

이 복잡함은 Kotlin이 스스로 만든 것이 아니다. Java/JVM의 애노테이션 모델과 Kotlin의 프로퍼티 추상 사이의 불일치에서 생긴 것이다. Java에는 "프로퍼티"라는 개념이 없고 필드와 메서드만 있다. Kotlin은 그 위에 프로퍼티라는 상위 추상을 두었기 때문에, 프로퍼티가 JVM에서 여러 요소로 분해될 때 애노테이션을 어느 요소로 보낼지 프로그래머가 제어할 수 있어야 했다. 사용 지점 타깃은 그 제어 수단이다.

이 주제는 45장(Java 상호운용)에서 `@JvmField`·`@JvmName`이 실제로 어느 요소를 대상으로 하는지와 함께 다시 나온다.

실전에서 자주 만나는 함정을 하나 덧붙인다. 검증 프레임워크(예: Bean Validation 계열)는 관례상 *필드*나 *게터*에 붙은 애노테이션을 리플렉션으로 스캔한다. 그런데 Kotlin에서 `class User(@NotBlank val name: String)`처럼 별생각 없이 쓰면, 애노테이션이 자동 규칙에 따라 *생성자 파라미터*에 붙어 프레임워크의 스캔 범위를 벗어난다.

그래서 이런 라이브러리를 Kotlin에서 쓸 때는 `@field:NotBlank`(또는 `@get:`)를 명시하는 것이 사실상 필수 관용구다. "왜 검증이 적용되지 않을까?"라는 문제의 90%는 이 타깃 누락 때문이다.

## 5. 표준 애노테이션과 그 역할

### 5.1 코틀린 표준 애노테이션 개관

표준 라이브러리는 언어와 밀접하게 연결된 애노테이션을 여럿 제공한다. 그중 몇 가지를 성격별로 정리하면 다음과 같다.

| 애노테이션 | 리텐션(대략) | 역할 |
|-----------|------|------|
| `@Deprecated` | RUNTIME | 폐기 표시, `ReplaceWith`로 자동 마이그레이션 제안 |
| `@Suppress` | SOURCE | 컴파일러 경고 억제 |
| `@JvmStatic` | - | 동반 객체/object 멤버를 JVM `static`으로 노출 |
| `@JvmField` | - | 프로퍼티를 접근자 없이 공개 필드로 노출 |
| `@JvmName` | - | JVM에서의 이름 재지정 (시그니처 충돌 회피) |
| `@JvmOverloads` | - | 기본 인자에 대해 Java용 오버로드 생성 |
| `@Throws` | - | Java에 검사 예외 시그니처 노출 |
| `@Volatile` | - | 필드에 JVM `volatile` 부여 (43장 동시성과 메모리 모델) |
| `@Synchronized` | - | 메서드에 JVM `synchronized` 부여 |
| `@Transient` | - | 직렬화에서 필드 제외 |
| `@RequiresOptIn` | BINARY | 옵트인 API 표시 ([[46 - 멀티플랫폼과 진화와 어두운 구석]]) |

`@Deprecated`는 `DeprecationLevel`(WARNING/ERROR/HIDDEN)과 `ReplaceWith`를 통해 단순한 표시를 넘어 IDE의 자동 수정까지 이끌어 낸다.

```kotlin
@Deprecated(
    message = "Use transfer(to, amount) instead",
    replaceWith = ReplaceWith("transfer(to, amount)"),
    level = DeprecationLevel.WARNING,
)
fun send(to: String, amount: Long) { /* ... */ }
```

### 5.2 상호운용 애노테이션과 리플렉션

`@JvmStatic`과 `@JvmField`는 이 장의 주제는 아니지만, 리플렉션과 관련이 있으므로 여기서 짚고 넘어간다.

[[28 - object와 companion - 싱글턴과 동반 객체]]에서 자세히 다루듯이, 동반 객체의 멤버는 *진짜 정적 멤버가 아니라* `Companion`이라는 실제 인스턴스의 멤버다. `@JvmStatic`을 붙여야 JVM 바이트코드에 진짜 `static` 메서드가 생기고, Java에서 `ClassName.method()`로 호출할 수 있다.

리플렉션에서도 마찬가지다. `@JvmStatic` 없이 Java `Class.getMethod`로 정적 메서드를 찾으면, 멤버가 `Companion` 인스턴스에 있으므로 찾지 못한다.

22장(프로퍼티와 백킹 필드)에서 설명한 "프로퍼티는 필드가 아니라 접근자 추상"이라는 점도 리플렉션에서 그대로 드러난다. Kotlin 프로퍼티를 Java 리플렉션으로 보면 필드가 아니라 `getX()`/`setX()` 메서드로 보인다. `@JvmField`를 붙여야 접근자가 사라지고 공개 필드로 나타난다. 즉 애노테이션이 리플렉션에 *보이는 형태*를 바꾸는 셈이다.

```kotlin
class Point(val x: Int, @JvmField val y: Int)

// Java 리플렉션에서:
//   x → getX() 메서드로 보임 (필드는 private)
//   y → public 필드 y로 보임 (게터 없음)
```

이 관계에서 중요한 점을 알 수 있다. **애노테이션은 컴파일 결과의 형태를 바꾸고, 리플렉션은 그 형태를 관찰한다.** 두 기능은 같은 대상을 서로 반대 방향에서 다룬다.

## 6. 리플렉션의 두 세계: `KClass`와 Java `Class`

### 6.1 `::class`는 `KClass`를, `.java`는 `Class`를 준다

이제 리플렉션으로 넘어간다. 리플렉션은 "클래스를 값으로 다루는 것"에서 출발한다. Kotlin에는 클래스를 표현하는 방식이 두 가지 있다.

```kotlin
val kc: KClass<String> = String::class          // Kotlin 리플렉션의 KClass
val jc: Class<String> = String::class.java        // JVM(Java)의 Class
val back: KClass<String> = jc.kotlin              // Class → KClass 변환
```

`Foo::class`는 항상 `KClass`를 만든다. Java의 `Foo.class`에 정확히 대응하는 것은 `Foo::class.java`이므로, 둘을 혼동하면 안 된다. `KClass`는 Kotlin의 개념(프로퍼티, 동반 객체, 가시성 한정자, `data`/`sealed` 여부 등)을 아는 상위 추상이고, `Class`는 JVM의 개념(필드, 메서드, 생성자)만 안다.

> [!note] 명세 기준
> `::class` 연산자 자체와 `KClass`의 몇몇 가벼운 연산(`simpleName`, `qualifiedName`, `isInstance`, 동등성 비교)은 JVM 백엔드에서 `kotlin-reflect` 의존성 없이도 동작한다. 이 연산들은 내부적으로 `java.lang.Class`에 기대는 경량 구현으로 처리된다.
>
> 하지만 `members`, `declaredMemberProperties`, `constructors`, `isData`, `primaryConstructor` 같은 *본격적인* 리플렉션에는 `kotlin-reflect` 아티팩트가 필요하며, 없으면 `KotlinReflectionNotSupportedError`가 발생한다. 실무에서는 이 경계 때문에 당황하는 경우가 많다.

```kotlin
// kotlin-reflect 없이도 OK:
println(BankAccount::class.simpleName)     // => BankAccount

// kotlin-reflect 필요 (없으면 런타임 에러):
println(BankAccount::class.declaredMemberProperties)  // KotlinReflectionNotSupportedError
```

### 6.2 정적 타입과 런타임 타입: `Foo::class`와 `obj::class`

여기에는 미묘하지만 중요한 구분이 있다. 클래스 리터럴 `Foo::class`는 컴파일 타임에 알려진 그 타입의 `KClass`를 준다. 반면 인스턴스에 `::class`를 붙인 `obj::class`는 *런타임의 실제 클래스*를 준다.

```kotlin
open class Shape
class Circle : Shape()

val s: Shape = Circle()

println(Shape::class.simpleName)   // => Shape   (정적: 리터럴 그대로)
println(s::class.simpleName)       // => Circle  (런타임: 실제 객체의 클래스)
```

이는 Java의 `Shape.class`(정적)와 `s.getClass()`(런타임)의 관계에 정확히 대응한다. Kotlin에서 `s.javaClass`는 `s.getClass()`에 해당하고, `s::class`는 그 결과를 `KClass`로 감싼 것이다.

```kotlin
val jc: Class<out Shape> = s.javaClass    // getClass() 대응
val kc: KClass<out Shape> = s::class      // getClass()를 KClass로
```

`s::class`의 정적 타입이 `KClass<Shape>`가 아니라 `KClass<out Shape>`라는 점에 주목하자. 런타임 타입은 `Shape`일 수도, 그 하위 타입일 수도 있으므로, 컴파일러는 공변 프로젝션([[33 - 제네릭 1 - 타입 파라미터와 변성]])으로 상한만 안전하게 보장한다.

### 6.3 `KClass`가 아는 것: Kotlin 고유 정보

`KClass`는 Java `Class`가 모르는 Kotlin 개념을 노출한다. `kotlin-reflect`가 있으면 다음과 같이 쓸 수 있다.

```kotlin
data class Money(val amount: Long, val currency: String)

fun main() {
    val kc = Money::class
    println(kc.isData)            // => true
    println(kc.isSealed)          // => false
    println(kc.isCompanion)       // => false
    println(kc.visibility)        // => PUBLIC
    println(kc.primaryConstructor) // => fun <init>(kotlin.Long, kotlin.String): Money
    println(kc.declaredMemberProperties.map { it.name })  // => [amount, currency]
}
```

`isData`, `isSealed`, `objectInstance`(object 선언의 싱글턴 인스턴스), `sealedSubclasses`(봉인 계층의 하위 목록, [[30 - sealed 클래스와 대수적 데이터 타입]]), `primaryConstructor`는 모두 Kotlin 언어의 개념이며 Java `Class`에는 없다. 그래서 Kotlin 고유의 특성을 다루려면 반드시 `KClass`(= `kotlin-reflect`)가 필요하다.

`sealedSubclasses`는 특히 유용하다. sealed 계층의 모든 하위 타입을 런타임에 열거할 수 있으므로 다형적 직렬화 같은 곳에서 쓰인다.

```kotlin
sealed interface Event
data class Deposit(val amount: Long) : Event
data class Withdrawal(val amount: Long) : Event

println(Event::class.sealedSubclasses.map { it.simpleName })
// => [Deposit, Withdrawal]
```

## 7. `KCallable` 계층: 함수와 프로퍼티를 값으로

### 7.1 참조는 리플렉션 객체다

13장(함수 타입과 람다와 함수 참조)에서 `::foo`가 함수 참조라는 것을 배웠다. 이제 그 참조의 정체를 살펴본다. `::foo`는 `KFunction` 객체이고, `::prop`은 `KProperty` 객체다. 둘 다 "호출할 수 있는 무언가"를 나타내는 리플렉션 인터페이스 `KCallable`을 구현한다.

```text
KAnnotatedElement
      │
   KCallable<out R>
      ├── KFunction<out R>        (함수/생성자)
      │      ├─ KFunction0<R>, KFunction1<P1,R>, ...
      │
      └── KProperty<out V>        (읽기 가능 프로퍼티)
             └── KMutableProperty<V>   (읽기+쓰기)
                   ├─ KProperty0/1/2 (수신자 개수별)
                   └─ KMutableProperty0/1/2
```

수신자 개수는 타입에 반영된다. `KProperty0`는 수신자 없이 값을 가진 프로퍼티(최상위, 지역)이고, `KProperty1`은 인스턴스를 하나 받아야 값이 나오는 프로퍼티(멤버)다.

```kotlin
val topLevel = 42
val ref0: KProperty0<Int> = ::topLevel        // 수신자 0개
println(ref0.get())                            // => 42

class Box(val size: Int)
val ref1: KProperty1<Box, Int> = Box::size     // 수신자 1개 (Box 필요)
println(ref1.get(Box(10)))                     // => 10
```

`Box::size`는 "어떤 `Box`를 받든 그 `size`를 꺼내는 함수"처럼 동작한다. 실제로 `KProperty1`은 `(Box) -> Int` 함수 타입으로도 쓸 수 있다(SAM/함수 타입 호환). 그래서 `boxes.map(Box::size)`라고 쓸 수 있다.

### 7.2 함수를 리플렉션으로 호출하기: `call`과 `callBy`

`KFunction`은 `call(vararg args)`로 실제로 호출할 수 있다. 리플렉션 호출은 정적 호출보다 느리지만(9.1절), 어떤 함수를 호출할지 컴파일 타임에 모를 때는 유일한 수단이다.

```kotlin
fun greet(name: String, times: Int): String = "hi $name".repeat(times)

fun main() {
    val f: KFunction<String> = ::greet
    println(f.call("kim", 2))    // => hi kimhi kim
}
```

기본 인자가 있을 때 `call`은 모든 파라미터를 요구하므로 불편하다. `callBy(Map<KParameter, Any?>)`를 쓰면 일부 파라미터만 지정하고 나머지는 기본값을 쓸 수 있다.

```kotlin
fun connect(host: String, port: Int = 8080, tls: Boolean = true) { /* ... */ }

val f = ::connect
val params = f.parameters
f.callBy(mapOf(params[0] to "example.com"))
// host만 지정, port=8080·tls=true는 기본값 사용
```

`callBy`가 기본값을 채울 수 있는 것은, 컴파일러가 기본 인자를 처리하려고 생성한 합성 메서드(`$default`)를 리플렉션이 활용하기 때문이다. DI 컨테이너나 역직렬화기가 "생성자에 이름 붙은 인자로 값을 주입"하는 기능도 이 메커니즘을 바탕으로 구현한다.

### 7.3 프로퍼티 읽기·쓰기와 가시성 우회

`KProperty`는 `get`으로 값을 읽고, `KMutableProperty`는 `set`으로 값을 쓴다. 그런데 리플렉션의 진짜 힘(이자 위험)은 *private 멤버에 접근*할 수 있다는 데 있다.

```kotlin
class Secret {
    private val token: String = "abc123"
}

fun main() {
    val prop = Secret::class.declaredMemberProperties.first { it.name == "token" }
    prop.isAccessible = true              // 가시성 검사 우회
    println(prop.get(Secret()))           // => abc123
}
```

`isAccessible = true`는 [[26 - 가시성 한정자]]에서 컴파일 타임에 강제한 `private`을 런타임에 무력화한다. 직렬화, DI, 테스트 같은 프레임워크에는 꼭 필요한 기능이지만, 캡슐화를 깨뜨리는 위험한 기능이기도 하다. 리플렉션은 가시성이 어디까지나 *컴파일러가 지키는 계약*일 뿐, 런타임의 물리적 장벽이 아니라는 사실을 보여 준다.

> [!caution] 성능 주의
> 접근할 때마다 `isAccessible = true`를 설정하고 매번 `declaredMemberProperties`로 프로퍼티를 찾으면 비용이 크다. 리플렉션을 쓰는 라이브러리는 대개 `KProperty` 객체를 한 번 찾아 캐시해 두고 재사용한다. 리플렉션 비용의 대부분은 "메타데이터 탐색"에서 생기며, 이미 얻어 둔 `KCallable`을 반복 호출하는 비용은 상대적으로 적다(그래도 정적 호출보다는 느리다).

### 7.4 바운드 참조와 언바운드 참조

인스턴스에 묶인 참조(bound reference)와 묶이지 않은 참조(unbound)의 구분도 리플렉션 수준에서 나타난다.

```kotlin
class Account(val id: String)
val acc = Account("A-1")

val unbound: KProperty1<Account, String> = Account::id   // 수신자 필요
val bound: KProperty0<String> = acc::id                   // acc에 묶임

println(unbound.get(acc))   // => A-1  (수신자를 인자로)
println(bound.get())        // => A-1  (이미 묶여 있음)
```

`bound`는 이미 `acc`를 담고 있으므로 `get()`에 수신자가 필요 없다. 그래서 타입이 `KProperty0`(수신자 0개)가 된다. 13장에서 함수 타입으로 다룬 바운드/언바운드 참조의 구분이 리플렉션 타입 계층에도 그대로 반영된 것이다.

### 7.5 생성자 참조와 `KParameter`: 역직렬화기의 핵심

생성자도 `KFunction`이다. `::ClassName`은 생성자 참조이며, `KClass.primaryConstructor`나 `constructors`로도 얻을 수 있다. 역직렬화기와 DI 컨테이너는 생성자를 리플렉션으로 다루는 이 기능을 바탕으로 "이름 붙은 인자로 객체를 조립"한다.

```kotlin
data class Rectangle(val width: Int, val height: Int = 1)

fun main() {
    val ctor = Rectangle::class.primaryConstructor!!
    for (p in ctor.parameters) {
        println("${p.name} : ${p.type} (optional=${p.isOptional})")
    }
    // => width : kotlin.Int (optional=false)
    // => height : kotlin.Int (optional=true)

    val byName = ctor.parameters.associateBy { it.name }
    val r = ctor.callBy(mapOf(byName["width"]!! to 5))
    println(r)   // => Rectangle(width=5, height=1)   ← height는 기본값
}
```

`KParameter`는 파라미터의 `name`, `type`(`KType`), `isOptional`(기본값 유무), `kind`(값/디스패치 수신자/확장 수신자)를 노출한다. `isOptional`이 `true`이면 `callBy`에서 그 키를 생략해도 되고, 컴파일러가 만든 기본값 채움 로직이 대신 값을 넣는다.

JSON 역직렬화기는 바로 이 지점에서 "필드가 빠져도 기본값으로 채운다"는 동작을 구현한다. 이 기능은 [[27 - 데이터 클래스]]의 자동 생성 생성자, `copy`와 결합해 데이터 클래스를 리플렉션으로 "기계가 조립하기 쉬운 값"으로 만든다.

> [!note] 명세 기준
> `KParameter.name`이 유효하려면 컴파일할 때 파라미터 이름 메타데이터가 보존되어야 한다. Kotlin은 `kotlin-reflect`를 통해 자체 메타데이터에서 파라미터 이름을 읽는다. 따라서 JVM 순수 리플렉션(`java.lang.reflect.Parameter`)이 이름을 잃는 경우(`-parameters` 미지정)와 달리 이름을 안정적으로 얻을 수 있다. 이름 기반 주입에서 `kotlin-reflect`를 선호하는 이유 가운데 하나다.

## 8. 리플렉션과 타입: 소거를 부분적으로만 우회한다

### 8.1 `KType`과 `typeOf`: 컴파일 타임에 캡처한 타입

34장(제네릭 2 타입 소거와 reified와 바운드)에서 자세히 다루듯이, JVM 백엔드에서 제네릭 타입 인자는 런타임에 소거된다. `List<String>`이든 `List<Int>`든 런타임의 실제 클래스는 그냥 `List`다. 그렇다면 리플렉션은 이 제약을 넘어설 수 있을까? **부분적으로만 가능하고, 방식에 따라 다르다.**

핵심은 타입 정보를 *어디에서* 얻느냐다. 런타임 인스턴스의 클래스(`list::class`)로는 이미 소거되었으므로 `String`을 절대 복구할 수 없다. 하지만 `typeOf<List<String>>()`는 `String`을 안다. `typeOf`는 런타임 인스턴스를 보는 것이 아니라, *호출 지점의 컴파일 타임 타입*을 캡처해 `KType`으로 구체화하기 때문이다.

```kotlin
import kotlin.reflect.typeOf

val t = typeOf<List<String>>()
println(t)                          // => kotlin.collections.List<kotlin.String>
println(t.arguments)                // => [kotlin.String]
println(t.arguments.first().type)   // => kotlin.String

val list: List<String> = listOf("a")
println(list::class)                // => class java.util.ArrayList (또는 유사)
//   ↑ String 정보 없음 — 런타임 클래스는 소거됨
```

이 차이는 이 장에서 가장 정확하게 이해해야 할 부분이다.

```text
              타입 정보를 얻는 두 경로

  typeOf<List<String>>()          list::class  /  list.javaClass
        │                                │
  컴파일 타임 타입을 캡처          런타임 객체의 클래스를 읽음
        │                                │
  <String>까지 보존                 소거되어 raw List만
  (KType.arguments 존재)           (타입 인자 복구 불가)
```

`typeOf`는 사실 15장(인라인 함수와 reified)의 `reified`와 같은 원리, 즉 컴파일 타임 타입 캡처로 동작한다. 다만 `reified`는 최상위 타입만 `is T`/`T::class`로 쓸 수 있는 반면, `typeOf`는 `List<String>`의 `String`까지 포함한 전체 타입 구조를 `KType` 트리로 보존한다.

그래서 `typeOf`는 `reified`보다 풍부한 타입 정보를 준다. 대신 그 결과는 런타임 캐스팅(`is`)에 바로 쓸 수 없는 리플렉션 데이터일 뿐이다.

> [!note] 명세 기준
> `typeOf`가 반환하는 `KType`에는 `arguments`(타입 인자), `classifier`(어떤 클래스나 타입 파라미터인지), `isMarkedNullable`(널 가능 여부)이 담긴다. 이는 소거를 "우회한" 것이 아니라, *소거되기 전 시점(컴파일 타임)의 정보를 별도 경로로 전달한 것*이다. 런타임에 임의의 객체를 받아 그 안의 타입 인자를 알아낼 방법은 없다. `typeOf`는 호출 지점이 타입을 정적으로 알고 있을 때만 쓸 수 있다.

### 8.2 스타 프로젝션과 소거의 흔적

리플렉션으로 멤버의 타입을 순회하다 보면 `*`(스타 프로젝션, 33장 제네릭 1 타입 파라미터와 변성)나 타입 파라미터를 만난다. 소거된 제네릭 타입을 리플렉션으로 다룰 때 컴파일 타임 정보가 없으면, 결국 상한(`Any?`)까지만 알 수 있다.

```kotlin
class Container<T>(val items: List<T>)

val prop = Container::class.declaredMemberProperties.first()
println(prop.returnType)        // => kotlin.collections.List<T>  (T는 여전히 타입 파라미터)
```

여기서 `T`는 구체 타입으로 확정되지 않는다. `Container<String>`의 인스턴스가 있더라도, 그 인스턴스의 `KClass`에서 `T`가 `String`이라는 정보를 복구할 수는 없다. 소거 때문에 생기는 당연한 결과다. `typeOf<Container<String>>()`처럼 정적으로 타입을 알려 줄 때만 `T = String`이 보존된다.

### 8.3 배열의 특수성

38장(컬렉션 읽기 전용과 가변)에서 다루듯이 `Array<T>`는 `List`와 성격이 다른 타입이다. 리플렉션에서도 배열은 특별하게 취급된다. JVM 백엔드에서 `Array<String>`은 소거되지 않고 런타임에 `String[]`으로 남는다(배열은 실체화된 제네릭에 가깝다). 그래서 배열은 제네릭 컬렉션과 달리 원소 타입 정보의 일부를 런타임에 유지한다.

```kotlin
val arr: Array<String> = arrayOf("a", "b")
println(arr::class.java)              // => class [Ljava.lang.String;  (String[] — 원소 타입 유지!)

val list: List<String> = listOf("a")
println(list::class.java)            // => class java.util.ArrayList  (원소 타입 없음)
```

배열은 원소 타입을 런타임에 유지하지만 제네릭 컬렉션은 소거된다. 이 비대칭 때문에 Java에서 배열의 공변성이 런타임 `ArrayStoreException`을 일으키며, 이 내용은 34장에서 다룬다. 리플렉션을 쓰면 이 차이를 직접 관찰할 수 있다.

## 9. 리플렉션의 비용과 대안: `kotlin-reflect`, KSP, 애노테이션 프로세싱

### 9.1 리플렉션은 왜 비싼가

리플렉션은 편리하지만 공짜가 아니다. 비용은 세 가지다.

- **의존성 무게**: Kotlin의 완전한 리플렉션을 쓰려면 `kotlin-reflect`라는 별도 아티팩트(수 MB 규모)가 필요하다. 이 아티팩트를 넣지 않으면 `KClass.members` 등에서 `KotlinReflectionNotSupportedError`가 난다(6.1절). 라이브러리나 앱 크기에 민감하다면 이 무게가 부담이 된다.
- **탐색 비용**: `declaredMemberProperties`로 프로퍼티를 찾거나 애노테이션을 순회하는 작업은 클래스 메타데이터를 파싱해야 하므로 느리다. 정적으로 컴파일된 필드 접근이 나노초 단위라면, 리플렉션 탐색은 그보다 훨씬 오래 걸린다(구체적인 배수는 JVM, 워밍업, 캐시 상태에 따라 크게 다르므로 단정하지 않는다).
- **호출 비용**: `KCallable.call`은 인자를 박싱하고 접근성을 확인한 뒤 대상 메서드로 디스패치한다. 그만큼 정적 호출보다 오버헤드가 있다.

> [!caution] 성능 주의
> 리플렉션 성능의 실전 원칙은 "한 번 찾고 캐시하라"다. 프레임워크는 클래스가 처음 등장할 때 그 `KClass`·`KProperty`·애노테이션을 리플렉션으로 훑어 내부 표(예: 필드 매핑)를 만들고, 이후에는 그 표를 재사용한다. 요청마다 `declaredMemberProperties`를 다시 호출하면 리플렉션의 성능이 가장 나빠진다. 그렇게 하더라도 리플렉션은 정적 코드보다 근본적으로 느리고, 인라인이나 정적 최적화(15장 인라인 함수와 reified)의 이점도 얻지 못한다.

### 9.2 컴파일 타임 대안: KSP와 애노테이션 프로세싱

리플렉션의 비용을 근본적으로 피하려면 "런타임에 발견"하던 일을 "컴파일 타임에 생성"하는 쪽으로 옮기면 된다. 여기서 애노테이션의 또 다른 역할이 드러난다. 애노테이션은 런타임 리플렉션이 찾는 표식일 뿐 아니라, 컴파일 타임 코드 생성기의 입력이기도 하다.

- **kapt**(Kotlin Annotation Processing Tool): Kotlin에서 Java 애노테이션 프로세싱 API를 쓸 수 있게 해 주는 도구다. Kotlin 코드를 Java 스텁으로 변환해 기존 Java 프로세서를 실행한다. 느리고, 사실상 유지보수 모드에 가깝다.
- **KSP**(Kotlin Symbol Processing): Kotlin을 위해 새로 설계한 심볼 처리 API다. Kotlin의 프로퍼티, 널 가능성, 확장 같은 언어 개념을 직접 이해하고, Java 스텁 없이 동작하므로 훨씬 빠르다. [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]에서 개관한 컴파일러 플러그인 생태계의 일부다.

두 방식을 비교하면 다음과 같다.

| | 런타임 리플렉션 | KSP (컴파일 타임) |
|---|---|---|
| 언제 동작 | 프로그램 실행 중 | 컴파일 중 |
| 산출물 | 없음 (즉석 탐색) | 소스 코드 생성 |
| 성능 | 런타임 오버헤드 | 런타임 오버헤드 0 (생성된 코드는 정적) |
| 의존성 | `kotlin-reflect` 필요 | 런타임 의존성 없음 (빌드 타임만) |
| 유연성 | 실행 중 어떤 클래스든 | 컴파일 시점에 아는 것만 |
| 타입 안전 | 런타임 오류 위험 | 컴파일 타임 검증 |

직렬화를 예로 들어 보자. 런타임 리플렉션 기반 라이브러리는 객체마다 리플렉션으로 구조를 분석해 필드를 읽는다. 반면 `kotlinx.serialization`은 컴파일러 플러그인으로 각 `@Serializable` 클래스의 직렬화 코드를 *컴파일 타임에 생성*한다.

그래서 런타임 리플렉션 없이(또는 최소한으로만 써서) 동작하고, 멀티플랫폼(46장 멀티플랫폼과 진화와 어두운 구석)에서도 작동한다. JVM 밖에는 완전한 리플렉션이 없으므로, 멀티플랫폼에서는 컴파일 타임 생성이 사실상 유일한 선택지가 되기도 한다.

### 9.3 언제 무엇을 쓸까

- **런타임 리플렉션**: 컴파일 타임에 대상을 알 수 없을 때(예: 사용자가 지정한 클래스 이름으로 인스턴스 생성)나 도구, 디버깅에 쓴다. 유연하지만 비용이 크고 JVM에 치우쳐 있다.
- **KSP/컴파일 타임 생성**: 대상이 컴파일 타임에 정해지고 성능, 멀티플랫폼, 타입 안전이 중요할 때 쓴다. 오늘날 라이브러리 생태계의 흐름은 이쪽으로 옮겨 왔다.
- **리플렉션 없이 애노테이션만**: 애노테이션을 컴파일러 지시(`@Suppress`, `@Deprecated`)나 문서 표식으로만 쓸 때다. 이 경우에는 `SOURCE`/`BINARY` 리텐션이면 충분하다.

### 9.4 멀티플랫폼에서의 리플렉션 제약

이 장의 리플렉션 설명은 JVM 백엔드를 기준으로 했다. Kotlin은 여러 타깃을 지원하는 언어이고([[01 - 코틀린이란 무엇인가 - 설계 철학과 세 개의 타깃]]), JVM 밖에서는 리플렉션 기능이 JVM과 같지 않다. Kotlin/JS와 Kotlin/Native는 완전한 `kotlin-reflect`를 제공하지 않으며, `::class`의 일부 기능(`simpleName` 등)만 제한적으로 지원한다. 그래서 멀티플랫폼 코드에서 런타임 리플렉션에 의존하면 이식성이 깨진다.

이 점도 멀티플랫폼 라이브러리에서 KSP 같은 컴파일 타임 방식을 선호하는 이유다. 코드 생성은 어느 타깃에서든 정적 코드를 만들어 내므로 리플렉션 기능에 의존하지 않는다.
