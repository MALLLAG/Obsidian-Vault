이 장에서는 KMP(Kotlin Multiplatform)의 언어 메커니즘(`expect`/`actual`, 소스셋 계층, 공통 표준 라이브러리)과 언어 진화의 계약 구조(안정성 등급, opt-in, deprecation 사이클)를 다룬다. Gradle 빌드 스크립트나 Ktor·Compose Multiplatform 같은 라이브러리 사용법, 코루틴의 멀티플랫폼 특성([[42 - suspend와 코루틴 - 언어 수준의 중단]])은 다루지 않는다.

마지막으로 앞 장들에서 바로잡은 오개념을 하나의 인과 관계로 묶어, 그것들이 "정적 타입 + 멀티백엔드 + Java 공존"이라는 세 제약이 겹치는 곳에서 함께 생겨났음을 보인다.

## 1. 하나의 프론트엔드와 여러 백엔드: 멀티플랫폼의 기본 구조

### 1.1 "하나의 언어"로 공유하는 부분과 타깃마다 달라지는 부분

[[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]에서는 컴파일 파이프라인이 두 부분으로 나뉜다고 설명했다. 하나는 **프론트엔드**(K2/FIR: 어휘 분석, 파싱, 이름 해석, 타입 추론, 진단)이고, 다른 하나는 공통 IR을 각 타깃에 맞게 변환하는 **백엔드**이다. 멀티플랫폼이 무엇인지는 이 그림에서 바로 알 수 있다.

```text
        소스(.kt)  ──▶  [ 프론트엔드: K2/FIR ]  ──▶  공통 IR
                          (타입 시스템·널 안전·                │
                           변성·스마트캐스트 —                 ├─▶ [JVM 백엔드]   ─▶ .class (바이트코드)
                           모든 타깃에서 동일)                  ├─▶ [Native 백엔드] ─▶ LLVM ─▶ 기계어
                                                              ├─▶ [JS 백엔드]    ─▶ .js
                                                              └─▶ [Wasm 백엔드]  ─▶ .wasm
```

**타입 시스템은 프론트엔드에 있다.** 따라서 `Int?`가 nullable이라는 점, `when`이 완전성 검사를 받는다는 점, `out T`가 공변이라는 점, 스마트캐스트가 언제 적용되고 언제 적용되지 않는지는 **타깃과 관계없이 똑같다.** "하나의 언어"라는 말은 정확히 이 뜻이다. 문법, 타입 관계, 오버로드 해석, 널 안전 같은 언어 규칙은 JVM으로 컴파일하든 Native로 컴파일하든 하나뿐이다.

타깃마다 달라지는 것은 **백엔드가 언어의 추상을 실제 기계에 맞게 구현하는 방식**이다. `Int`를 JVM에서 원시 `int`로 변환할지, Native에서 32비트 정수로 변환할지는 백엔드가 결정한다. `String`이 JVM에서 `java.lang.String`(UTF-16)인지, Native에서 별도의 표현을 쓰는지도 마찬가지다. 언어 명세가 보장하는 것은 "`String`은 불변 UTF-16 시퀀스처럼 동작한다"는 **관찰 가능한 계약**이고, 실제 바이트 레이아웃은 보장하지 않는다.

> [!note] 명세 기준
> "Kotlin에는 원시 타입이 없다"는 설명은 언어 수준에서 참이고, 모든 타깃에서 참이다. 반면 "가능하면 `int`로 컴파일된다"는 설명은 **JVM 백엔드에만 해당하는** 구현 사실이다. 이 시리즈가 계속 "JVM 백엔드에서"라는 한정어를 붙인 이유가 바로 이 프론트엔드와 백엔드의 분리이다. 언어가 약속하는 것과 백엔드가 구현하는 방식을 구분하지 않으면 오개념이 생긴다.

### 1.2 소스셋 계층: 코드가 어느 타깃 범위에 속하는가

멀티플랫폼 프로젝트에서 소스 파일은 **소스셋(source set)** 이라는 논리적 묶음에 속한다. 맨 위에 `commonMain`이 있고, 아래로 내려갈수록 타깃이 구체적으로 정해진다.

```text
                       commonMain           ← 모든 타깃이 공유. 여기 있는 코드는
                      /    |    \             플랫폼 API를 직접 못 부른다(공통 API만).
                     /     |     \
              nativeMain  jsMain  jvmMain    ← 중간/플랫폼 소스셋. 각 타깃의
                /    \       │       │          라이브러리를 직접 부를 수 있다.
        linuxMain  macosMain │       └─▶ java.* 등 JVM 전용 라이브러리 접근 가능
```

핵심 규칙은 **가시성이 한 방향으로만 흐른다**는 것이다. 아래쪽(더 구체적인) 소스셋은 위쪽(더 공통적인) 소스셋의 선언을 볼 수 있지만, 반대 방향은 불가능하다. `jvmMain`의 코드는 `commonMain`의 함수를 호출할 수 있다. 하지만 `commonMain`의 코드는 `jvmMain`의 함수도, `java.io.File` 같은 JVM 전용 API도 볼 수 없다. 공통 코드는 "모든 타깃에 있다고 보장된 것"만 쓸 수 있기 때문이다.

```kotlin
// commonMain 소스셋
fun greet(name: String): String = "Hello, $name"   // OK: String은 모든 타깃에 존재

// import java.io.File                              // 컴파일 에러: commonMain에서 java.* 안 보임
```

```kotlin
// jvmMain 소스셋
import java.io.File
fun readConfig(): String = File("config.txt").readText()  // OK: JVM 타깃에서만 컴파일됨
```

멀티플랫폼의 타입 안전은 이 방향성 덕분에 유지된다. 공통 코드가 실수로 플랫폼 전용 API를 쓰면 그 코드는 더 이상 "공통"이 아닌데, 컴파일러가 소스셋 경계에서 이를 **정적으로** 막는다. 즉 "이 코드가 정말 모든 타깃에서 컴파일되는가?"라는 질문의 답을 런타임이 아니라 컴파일 타임에 확인하게 한다.

> [!info] 역사 메모
> 초기 KMP에서는 `commonMain` 아래에 각 타깃 소스셋을 직접 연결해야 했고, `nativeMain` 같은 **중간 소스셋**을 만들려면 Gradle에서 의존 관계를 직접 선언해야 했다. Kotlin 1.9.20부터는 **기본 계층 템플릿(default hierarchy template)** 이 도입되어, 타깃만 선언하면 `nativeMain`, `appleMain` 같은 중간 소스셋이 자동으로 구성된다.
>
> 이것은 빌드를 편하게 해 주는 기능이며 언어 규칙이 바뀐 것은 아니다. 소스셋 계층에서 가시성이 흐르는 방향은 처음부터 같았다.

### 1.3 이런 구조가 필요한 이유

멀티플랫폼을 "한 번 작성해서 어디서나 실행한다"로 오해하기 쉽지만, 이 표현은 정확하지 않다. 정확히는 **"공통 로직은 한 번 작성하고, 플랫폼마다 다른 부분만 나누어 작성한다"** 이다. 도형의 넓이 계산, 은행 계좌의 잔액 규칙, 좌표 변환 같은 순수한 도메인 로직은 어느 플랫폼에서나 같다. 반면 파일 읽기, 현재 시각 읽기, 난수 생성, 네트워크 호출은 플랫폼마다 API가 다르다. 소스셋 계층은 이 두 종류의 코드를 **물리적으로 분리**하도록 강제한다.

```kotlin
// commonMain — 플랫폼과 무관한 순수 도메인
class Circle(val radius: Double) {
    fun area(): Double = Math.PI * radius * radius   // ← 잠깐, Math.PI가 공통에 있나?
}
```

위 코드에서 `Math.PI`는 함정이다. `java.lang.Math`는 JVM 전용이므로 `commonMain`에서 쓸 수 없다. 공통 코드에서는 `kotlin.math.PI`를 써야 한다.

```kotlin
// commonMain — 올바른 버전
import kotlin.math.PI
class Circle(val radius: Double) {
    fun area(): Double = PI * radius * radius   // OK: kotlin.math는 공통 표준 라이브러리
}
```

`java.lang.Math.PI`와 `kotlin.math.PI`의 차이는 사소해 보이지만, 3절에서 다룰 "표준 라이브러리의 층 구조"로 이어진다. 그리고 플랫폼마다 API가 실제로 다른 부분을 공통 코드에서 타입 안전하게 호출하는 방법이 2절에서 다룰 `expect`/`actual`이다.

## 2. expect / actual: 공통 코드에서 플랫폼 API를 타입 안전하게 부르는 통로

### 2.1 문제 설정: 공통 코드에서 플랫폼 API를 호출해야 할 때

`commonMain`에서는 플랫폼 전용 API를 볼 수 없다. 그런데 공통 로직에 "현재 시각"이나 "플랫폼 이름" 같은 플랫폼 의존 값이 필요하다면 어떻게 해야 할까? 인터페이스를 정의하고 각 플랫폼이 구현체를 주입하는 방법(런타임 다형성)도 있지만, Kotlin은 **컴파일 타임에 해석되는** 더 직접적인 메커니즘을 제공한다. 바로 `expect`/`actual`이다.

```kotlin
// commonMain — 선언만 하고 본문은 비운다
expect fun platformName(): String

// commonMain — 공통 로직은 이 "약속된" 함수를 자유롭게 부른다
fun banner(): String = "Running on ${platformName()}"
```

```kotlin
// jvmMain — 실제 구현
actual fun platformName(): String = "JVM ${System.getProperty("java.version")}"
```

```kotlin
// nativeMain — 다른 실제 구현
actual fun platformName(): String = "Native"
```

`expect`는 "이 선언이 존재한다고 약속하며, 시그니처는 이렇고, 본문은 각 플랫폼이 채운다"는 뜻이다. 공통 코드는 `platformName()`을 이미 정의된 함수처럼 호출할 수 있다. 컴파일러는 **각 타깃을 컴파일할 때** 대응하는 `actual`을 찾아 연결한다. 예를 들어 JVM 타깃을 빌드하면 `commonMain`의 `expect`가 `jvmMain`의 `actual`과 짝지어진다.

### 2.2 추상 함수도 아니고 인터페이스도 아니다

본문이 없는 함수라는 겉모습만 보면 `expect`를 추상 함수(`abstract fun`)와 혼동하기 쉽다. 하지만 결정적인 차이가 세 가지 있다.

첫째, **구현을 고르는 시점이 다르다.** 추상 함수는 런타임에 가상 디스패치로 구현을 고른다. `expect`/`actual`은 **컴파일 타임(정확히는 링크 타임)** 에 정적으로 연결된다. 최종 바이너리에는 `expect` 선언의 흔적이 남지 않고, 그 자리에 해당 플랫폼의 `actual` 구현이 직접 들어간다. 따라서 가상 디스패치 오버헤드가 없다.

둘째, **적용 대상이 넓다.** 추상 선언은 클래스 멤버에만 쓸 수 있지만, `expect`는 **최상위 함수, 프로퍼티, 클래스(애노테이션과 enum 포함), 객체**에 모두 붙일 수 있다. 타입 별칭은 우변이 반드시 있어야 하므로 `expect`가 될 수 없고, 아래 2.3절처럼 `actual` 쪽에서만 쓴다.

```kotlin
// commonMain
expect val platformLineSeparator: String        // 프로퍼티
expect class FileHandle(path: String) {          // 클래스: 시그니처만 약속
    fun read(): String
    fun close()
}
expect annotation class Serializable()           // 애노테이션도 가능
```

셋째, **"하나의 이름에 N개의 구현"이 아니라 "N번의 컴파일마다 구현이 하나씩"이다.** 인터페이스라면 한 프로그램 안에 여러 구현이 동시에 존재하고 런타임에 골라서 쓴다. `expect`/`actual`에서는 JVM 바이너리에 JVM `actual`만, Native 바이너리에 Native `actual`만 들어간다. 한 실행 파일 안에 두 구현이 함께 있지 않다.

> [!warning] 흔한 오해
> "`expect`는 인터페이스를 다른 문법으로 쓴 것이다"라는 생각은 틀렸다. 인터페이스는 **런타임 다형성**(한 프로세스에 여러 구현이 함께 있고 가상 디스패치로 고름)이고, `expect`/`actual`은 **컴파일 타임 특수화**(타깃마다 구현 하나만 정적으로 연결됨)이다. 성격이 다르므로 쓰임새도 다르다. 런타임에 구현을 바꿔 끼워야 한다면 인터페이스를 쓰고, 플랫폼별로 컴파일 시점에 코드를 나누어야 한다면 `expect`/`actual`을 쓴다.

### 2.3 actual의 세 가지 형태와 규칙

`actual`이 약속을 이행하는 방식은 세 가지이다.

**(a) 직접 구현.** 위 예처럼 `actual fun`이나 `actual class`로 본문을 제공한다.

**(b) `actual typealias`로 기존 플랫폼 타입에 연결.** 플랫폼에 이미 딱 맞는 타입이 있다면, 새 클래스를 작성하지 않고 별칭으로 연결한다. KMP에서 가장 실용적인 패턴이다.

```kotlin
// commonMain
expect class UUID {
    override fun toString(): String
}

// jvmMain — 자바에 이미 java.util.UUID가 있다. 새로 짜지 말고 별칭으로.
actual typealias UUID = java.util.UUID
```

`actual typealias`는 [[36 - 타입 별칭과 인라인 value class]]에서 다룬 별칭(typealias는 새 타입이 아니라 별명이다)이 멀티플랫폼에서 특히 유용해지는 지점이다. `commonMain`의 코드는 `UUID`라는 이름으로 프로그래밍하지만, JVM에서는 그 이름이 곧 `java.util.UUID` 타입이다. 감싸는 비용도, 어댑터도 필요 없다.

**(c) 확장과 상속으로 시그니처 충족.** `actual` 선언은 `expect`가 요구한 멤버를 모두 제공해야 하며, 기본 인자와 추가 멤버 등에 대한 세부 규칙이 있다. 예를 들어 `actual`은 `expect class`의 멤버 시그니처를 정확히 맞춰야 하고, `expect`가 명시하지 않은 멤버(플랫폼 전용 편의 메서드)를 **추가**할 수 있다.

```kotlin
// commonMain
expect class Clock {
    fun nowMillis(): Long
}

// jvmMain
actual class Clock {
    actual fun nowMillis(): Long = System.currentTimeMillis()
    fun nowInstant(): java.time.Instant = java.time.Instant.now()   // JVM 전용 추가 멤버 OK
}
```

이때 `nowInstant()`는 `commonMain`에서 보이지 않는다. 공통 코드가 아는 것은 `expect`가 약속한 `nowMillis()`뿐이다. 플랫폼에 특화된 메서드는 해당 플랫폼 소스셋에서만 접근할 수 있다.

> [!note] 명세 기준
> `expect`와 `actual`의 시그니처는 엄격하게 맞춰야 한다. 파라미터의 타입과 개수, 반환 타입이 일치해야 하고, 가시성과 모디파이어에도 제약이 있다. 특히 `expect class`(그리고 `expect`에 대응하는 `actual`이 클래스인 경우)는 언어 버전에 따라 **베타/실험 경고**를 낼 수 있다.
>
> Kotlin 2.x 초기 버전에서는 `actual` 클래스를 쓰면 `'expect'/'actual' classes ... are in Beta` 경고가 떴고, `-Xexpect-actual-classes` 플래그로 이 경고를 억제했다. 함수, 프로퍼티, 타입 별칭 형태는 오래전부터 안정적이다. "지금 `expect class`가 안정 상태인가"는 시점에 따라 달라지는 사실이므로 **사용하는 Kotlin 버전의 릴리스 노트에서 확인**해야 한다.

### 2.4 expect/actual에서 자주 틀리는 지점

**함정 1: `actual`을 빠뜨리면 링크 에러가 난다.** `expect`를 선언하고 특정 타깃에 `actual`을 제공하지 않으면, 그 타깃을 빌드할 때 에러가 발생한다. 이것은 바람직한 성질이다. "플랫폼 X에서 이 기능을 빠뜨렸다"는 실수를 컴파일 타임에 잡아 주기 때문이다.

```text
commonMain:  expect fun randomSeed(): Long
jvmMain:     actual fun randomSeed(): Long = System.nanoTime()   // OK
jsMain:      (actual 없음)
             → JS 타깃 빌드 시: "Expected function 'randomSeed' has no actual declaration"
```

**함정 2: `expect`와 `actual`에 기본 인자를 중복해서 주면 안 된다.** 기본값은 `expect` 쪽에만 선언한다. `actual`에서 기본값을 다시 주면 충돌이 난다.

```kotlin
// commonMain
expect fun log(msg: String, level: Int = 0)

// jvmMain — 올바름: 기본값 반복 금지
actual fun log(msg: String, level: Int) { /* ... */ }   // level에 = 0 다시 쓰면 에러
```

**함정 3: `actual typealias`가 가리키는 플랫폼 타입이 `expect`의 계약보다 넓으면, 공통 코드는 넘치는 부분을 볼 수 없다.** `java.util.UUID`에 `commonMain`이 모르는 메서드가 100개 있어도, 공통 코드는 `expect UUID`가 선언한 것만 쓸 수 있다. 반대로 플랫폼 소스셋에서는 그 100개를 모두 볼 수 있다. 그래서 공통 코드라고 착각하고 플랫폼 전용 메서드를 호출하면 다른 타깃에서 빌드가 깨진다.

**함정 4: `expect`/`actual`을 남용하면 결합도가 높아진다.** 플랫폼 차이를 표현하는 방법이 `expect`/`actual`만 있는 것은 아니다. 인터페이스와 의존성 주입을 쓰거나, 상위 소스셋에 공통 구현을 두고 하위 소스셋에서 일부만 오버라이드하는 방식이 더 유연할 때가 많다. `expect`/`actual`은 "플랫폼마다 근본적으로 다르고 컴파일 타임에 확정되는 소수의 지점"에만 아껴 써야 하는 도구이다.

## 3. 공통 표준 라이브러리: 무엇이 어느 층에 있는가

### 3.1 kotlin-stdlib의 층 구조

1.3절에서 `kotlin.math.PI`는 공통 라이브러리에 있고 `java.lang.Math.PI`는 JVM 전용이라는 점을 확인했다. 이 관찰을 일반화해 보자. Kotlin 표준 라이브러리(`kotlin-stdlib`)는 **공통 핵(common core)과 플랫폼별 확장**이라는 층으로 이루어져 있다.

```text
┌─────────────────────────────────────────────────────────┐
│ 공통 표준 라이브러리 (모든 타깃에 존재 보장)              │
│  kotlin.*          : Any, Unit, Nothing, Int, String ... │
│  kotlin.collections: List, Map, Set, Sequence ...        │
│  kotlin.text       : StringBuilder, Regex, trimIndent    │
│  kotlin.math       : PI, sqrt, abs, sin ...              │
│  kotlin.io         : print, readLine (제한적)            │
│  kotlin.coroutines : Continuation, suspend 기반          │
└─────────────────────────────────────────────────────────┘
            │                    │                    │
            ▼                    ▼                    ▼
   ┌────────────────┐  ┌────────────────┐  ┌────────────────┐
   │ JVM 확장       │  │ JS 확장        │  │ Native 확장    │
   │ java.* 상호운용 │  │ dynamic, JS    │  │ C 상호운용,    │
   │ 파일·스레드 등 │  │ 인터롭         │  │ 포인터 등      │
   └────────────────┘  └────────────────┘  └────────────────┘
```

공통 핵에 있는 것들은 타깃과 관계없이 같은 API로 쓸 수 있다. 5장(타입 시스템의 지형)의 `Any`·`Unit`·`Nothing`, [[38 - 컬렉션 - 읽기 전용과 가변]]의 `List`/`MutableList`, [[40 - 시퀀스와 지연 평가]]의 `Sequence`, [[09 - 문자와 문자열 - 유니코드와 템플릿]]의 `String`/`StringBuilder`가 여기에 속한다. Kotlin으로 작성한 순수 로직을 다른 플랫폼으로 옮길 수 있는 것은 이 층 덕분이다.

### 3.2 파일 I/O는 공통 라이브러리에 없고 컬렉션은 있는 이유

`List`는 공통 라이브러리에 있는데 `java.io.File`은 왜 없을까? 기준은 **"모든 타깃이 같은 의미로 제공할 수 있는가"** 이다.

- 리스트, 맵, 문자열, 수학 함수는 순수한 계산이다. 힙과 CPU만 있으면 어느 플랫폼에서나 **같은 의미**로 구현할 수 있으므로 공통 핵에 넣을 수 있다.
- 파일 시스템, 스레드, 시계, 네트워크는 **운영체제나 런타임이 제공하는 서비스**이다. JVM의 파일 API, 브라우저 JS의 (존재하지 않는) 파일 접근, Native의 POSIX는 근본적으로 다르다. 이것들을 하나의 공통 API로 묶으면 어떤 플랫폼에서는 사실과 다른 약속이 된다.

그래서 이런 기능은 (a) 각 플랫폼 소스셋에 전용 API로 두거나, (b) `kotlinx-io`, `kotlinx-datetime` 같은 **별도의 멀티플랫폼 라이브러리**가 `expect`/`actual`로 공통 추상을 제공한다. 표준 라이브러리의 공통 핵은 의도적으로 "순수 계산"에 가까운 범위로 좁혀져 있다. 이식성을 얻으려면 이렇게 범위를 절제해야 한다.

> [!warning] 흔한 오해
> "`kotlin.io`가 있으니 파일 읽기도 공통 라이브러리에 있을 것이다"라고 생각하기 쉽다. 하지만 `kotlin.io`의 공통 부분은 `print`/`println` 같은 최소한의 기능뿐이고, `File(...).readText()`처럼 파일을 다루는 확장은 **JVM 소스셋**에 있다. 공통 코드에서 파일을 다루려면 멀티플랫폼 I/O 라이브러리를 추가하거나 `expect`/`actual`로 직접 추상을 만들어야 한다.

### 3.3 같은 API, 다른 구현: 계약은 하나, 구현은 여러 개

공통 핵의 API도 백엔드마다 **구현**이 다르다. [[10 - 불리언과 동등성과 동일성]]과 8장(수 2)에서 반복해서 다룬 "언어 계약과 백엔드 구현의 구분"을 보여 주는 마지막 사례이다.

```kotlin
// commonMain — 어느 타깃에서든 컴파일되고, 관찰 가능한 결과는 같다
fun sumTo(n: Int): Long {
    var acc = 0L
    for (i in 1..n) acc += i
    return acc
}
```

[[18 - 범위와 진행과 반복]]에서 보았듯 `for (i in 1..n)`는 `IntRange`를 순회한다. JVM 백엔드는 이 루프를 원시 `int` 카운터 루프로 최적화한다. Native 백엔드도 자기 방식대로 변환한다.

합계, 종료 조건, 오버플로 시 래핑(오버플로가 나도 예외 없이 래핑된다) 같은 **관찰 가능한 결과**는 명세가 보장하므로 모든 타깃에서 같다. 하지만 실제로 생성되는 코드는 다르다. 계약은 공유하고 구현은 나누는 것, 이것이 멀티플랫폼과 멀티백엔드가 함께 동작하는 방식이다.

정수 오버플로를 예로 들면, `Int.MAX_VALUE + 1`은 **모든 타깃에서** `Int.MIN_VALUE`로 래핑된다. 2의 보수 산술이 언어 계약이기 때문이다. 반대로 `Int?`가 실제로 박싱되는지는 백엔드가 결정한다. JVM에서는 대개 박싱되지만, 이것을 "언어의 약속"으로 오해하면 안 된다.

## 4. 언어의 진화: 릴리스 주기와 안정성 계약

이제 공간(멀티플랫폼)에서 시간(진화)으로 관점을 옮긴다. Kotlin은 매년 언어를 바꾸면서도 "기존 코드가 갑자기 깨지지 않는다"고 약속한다. 이 약속을 지키는 세 가지 장치인 **안정성 등급, deprecation 사이클, opt-in**이 4절과 5절의 주제이다.

### 4.1 릴리스 주기와 언어 버전

Kotlin은 대략 6개월마다 언어 기능이 포함된 릴리스를 낸다. 2.0에서는 K2 컴파일러가 기본이 되었고(2장 K2와 IR 백엔드), 2.1에서는 `when`의 **가드 조건**(`is X if cond ->`)이 추가되었다([[17 - 표현식으로서의 제어 흐름 - if와 when]]). 이렇게 릴리스마다 문법과 표준 라이브러리, 컴파일러가 조금씩 발전한다.

중요한 점은 **언어 버전과 컴파일러 버전을 분리**할 수 있다는 것이다. 새 컴파일러를 쓰면서도 `-language-version 1.9`처럼 지정하면 이전 언어 규칙으로 컴파일할 수 있다. 이 분리 덕분에 팀은 컴파일러(도구)를 먼저 올리고 새 언어 기능은 나중에 도입하는 식으로 위험을 나눌 수 있다.

> [!info] 역사 메모
> Kotlin은 1.0(2016)부터 **하위 호환성**을 핵심 약속으로 내세웠다. "이미 작성한 코드의 의미가 새 버전에서 조용히 바뀌지 않는다"는 원칙이다. 그래서 새 기능은 대개 **추가하는(additive)** 방식으로 들어오고, 기존 의미를 바꿔야 할 때는 다음 절의 deprecation 사이클을 거친다.
>
> 이 시리즈가 45장(Java 상호운용)에서 강조한 이벤트와 시그니처의 호환성 감각도 "이미 배포된 것과의 계약을 존중한다"는 같은 원칙에서 나왔고, 언어는 이 원칙을 자기 자신에게도 적용한다.

### 4.2 안정성 등급: Experimental / Alpha / Beta / Stable

표준 라이브러리 API와 언어 기능에는 **안정성 등급**이 붙는다. 등급은 "이 API의 계약이 앞으로 얼마나 바뀔 수 있는가"를 알려 주는 신호이다.

| 등급 | 의미 | 사용자에게 주는 계약 |
|------|------|----------------------|
| **Experimental** | 실험 중. 시그니처와 의미가 언제든 바뀔 수 있음 | opt-in 필요. 프로덕션 사용은 자기 책임 |
| **Alpha** | 방향은 정해졌으나 아직 유동적 | opt-in이 필요할 수 있음. 마이그레이션을 감수해야 함 |
| **Beta** | 거의 완성. 큰 변경은 미리 알리고 진행 | 대체로 안전하나 작은 변경은 있을 수 있음 |
| **Stable** | 안정. 하위 호환 보장 | 조용히 깨지지 않음. 변경은 deprecation 사이클을 거침 |

부호 없는 정수(`UInt`/`ULong` 등, 8장 수 2)가 좋은 사례이다. 도입 초기에는 Experimental이라 opt-in이 필요했지만, 여러 릴리스를 거쳐 **Stable**로 올라갔다. Kotlin/Wasm은 이 글을 쓰는 2.x 시점을 기준으로 여전히 **Alpha**에 가깝기 때문에, 대상 API가 릴리스마다 조정될 수 있다. 즉 안정성 등급은 고정된 라벨이 아니라 **시간이 지나면서 강해지는 계약의 강도**이다.

> [!note] 명세 기준
> 특정 기능이 "지금 어떤 등급인가"는 시점에 따라 달라지는 사실이다. 이 장에서 "X는 안정, Y는 실험"이라고 단정하면 그 문장은 시간이 지나 틀리게 된다. "부호 없는 정수는 도입 당시 실험 단계였고 이후 안정화되었다", "Wasm은 2.x 시점에 알파였다"처럼 **시점을 명시**하는 것이 정확한 태도이다. 실무에서는 사용하는 버전의 공식 문서와 릴리스 노트를 기준으로 삼아야 한다.

### 4.3 Deprecation 사이클: 한 번에 지우지 않는 이유

기존 API를 없애야 할 때 Kotlin은 여러 릴리스에 걸쳐 `WARNING → ERROR → HIDDEN`의 세 단계를 밟는다. 이 단계는 `@Deprecated` 애노테이션의 `level` 파라미터로 표현한다.

```kotlin
@Deprecated(
    message = "각도 단위가 모호합니다. radians를 명시하세요.",
    replaceWith = ReplaceWith("rotateRadians(angle)"),
    level = DeprecationLevel.WARNING          // 1단계: 경고만, 여전히 컴파일됨
)
fun rotate(angle: Double) { /* ... */ }
```

```text
릴리스 N   : DeprecationLevel.WARNING  — 쓰면 경고. 코드는 컴파일된다.
             (IDE가 ReplaceWith로 자동 교체를 제안)
릴리스 N+k : DeprecationLevel.ERROR    — 쓰면 컴파일 에러. 하지만 바이너리엔 남아
                                         이미 컴파일된 옛 코드는 계속 링크된다.
릴리스 N+m : DeprecationLevel.HIDDEN   — 소스에서 안 보임. 바이너리 호환만 유지.
             (마침내) 제거
```

단계마다 하는 일이 다르다.

- **WARNING**: 소스 호환과 바이너리 호환을 모두 유지한다. 사용자에게 옮기라고 알리지만 강제하지는 않는다. `ReplaceWith`는 IDE가 **자동 리팩터링**을 제안하는 근거가 된다.
- **ERROR**: 소스 호환은 깨진다(새로 컴파일하면 에러가 난다). 하지만 **바이너리 호환은 유지**되므로, 이 심볼을 참조하도록 이미 컴파일된 다른 모듈은 계속 링크된다. 의존하는 라이브러리가 옛 API를 쓰고 있어도 앱이 망가지지 않는 이유가 이것이다.
- **HIDDEN**: 소스에서 완전히 사라져 자동완성이나 이름 해석에 나타나지 않는다. 바이너리 호환만을 위해 시그니처가 남는다.

이렇게 세 단계로 천천히 진행하기 때문에 4.1절에서 말한 "조용히 깨지지 않는다"는 약속이 지켜진다. 어떤 개발자도 어느 날 갑자기 컴파일이 깨지는 일을 겪지 않는다. 경고가 먼저 나오고, 에러는 그다음이며, 제거는 훨씬 나중이다. 그 사이에 코드를 옮길 시간이 있고, `ReplaceWith`라는 자동 이전 경로도 있다.

> [!note] 실무 감각
> 성능 주의와는 관계없지만 실무에서 알아 둘 점이다. `@Deprecated`의 `ReplaceWith`는 단순한 문자열이 아니라 **표현식 템플릿**이다. IDE는 이것을 파싱해 실제로 리팩터링을 수행한다. 따라서 `ReplaceWith`에는 컴파일할 수 있고 의미가 보존되는 대체 표현을 정확히 적어야 한다. 잘못 적으면 자동 이전이 코드를 망가뜨린다.

### 4.4 진화 도구로서의 컴파일러 플러그인: kapt에서 KSP로

언어의 진화는 문법만의 문제가 아니다. 컴파일러를 **확장할 수 있다**는 사실 자체가 생태계가 발전하는 또 하나의 축이다. [[44 - 애노테이션과 리플렉션]]에서 리플렉션의 런타임 비용을 살펴보았는데, 그 대안이 컴파일 타임 코드 생성이다.

- **kapt**(Kotlin Annotation Processing Tool): Java 애노테이션 처리기(APT)를 Kotlin에서 쓰기 위한 연결 도구이다. Kotlin 코드에서 Java 스텁을 만든 뒤 Java의 APT를 실행한다. 스텁 생성 비용 때문에 느리다.
- **KSP**(Kotlin Symbol Processing): Kotlin 전용으로 설계된 심볼 처리 API이다. Java 스텁을 거치지 않고 Kotlin의 선언 구조를 직접 순회한다. kapt보다 빠르고 K2와도 잘 맞는다.

kapt에서 KSP로의 전환은 언어 진화가 "문법 추가"에 그치지 않고 **"컴파일 파이프라인 자체의 개선"** 이기도 하다는 것을 보여 준다. all-open, no-arg, serialization 같은 공식 플러그인도 컴파일러 확장으로 동작한다. Kotlin은 이런 개방성을 통해 직렬화, 의존성 주입, ORM 같은 프레임워크와 결합한다. 자세한 동작은 2장(K2와 IR 백엔드)에서 설명하고, 여기서는 진화의 축이 여러 개라는 점만 짚는다.

## 5. Opt-in 메커니즘: 계약에 서명하기

### 5.1 @RequiresOptIn: "이 API는 아직 계약이 확정되지 않았다"

4.2절에서 Experimental API를 쓰려면 opt-in이 필요하다고 했다. 이제 그 메커니즘을 자세히 살펴보자. 핵심은 **opt-in이 "위험 경고"가 아니라 "명시적 동의의 기록"** 이라는 점이다.

라이브러리 작성자는 아직 안정화하지 않은 API에 **마커 애노테이션**을 붙인다. 이 마커 자체에는 `@RequiresOptIn`이라는 메타 애노테이션이 붙는다.

```kotlin
@RequiresOptIn(
    message = "이 이미징 API는 실험적입니다. 시그니처가 바뀔 수 있습니다.",
    level = RequiresOptIn.Level.WARNING          // 또는 ERROR
)
@Retention(AnnotationRetention.BINARY)
annotation class ExperimentalImaging

// 이 API를 실험적이라고 표시
@ExperimentalImaging
fun renderVector(scene: Scene): Bitmap = TODO()
```

이제 `renderVector`를 호출하는 쪽은 컴파일러에게서 "이 API는 실험적이니, 알고 있다는 사실을 표시하라"는 요구를 받는다. 응답하는 방법은 두 가지이다.

### 5.2 사용하는 쪽의 두 가지 선택: 전파하거나 그 자리에서 끝내거나

**(a) `@OptIn`으로 그 지점에서 끝낸다.** "나는 이 API가 실험적이라는 것을 알고 여기서 책임진다. 내 호출자에게는 전파하지 않는다"는 뜻이다.

```kotlin
@OptIn(ExperimentalImaging::class)
fun drawLogo(): Bitmap {
    return renderVector(logoScene())   // 실험적 API 사용을 이 함수 안으로 봉인
}
// drawLogo를 부르는 쪽은 아무 opt-in도 필요 없다 — 실험성이 여기서 멈춘다.
```

**(b) 같은 마커를 다시 붙여 전파한다.** "나도 실험적이니, 나를 쓰는 사람도 동의해야 한다"는 뜻이다.

```kotlin
@ExperimentalImaging                    // 전파: 이 함수도 실험적으로 물든다
fun drawLogo(): Bitmap = renderVector(logoScene())
// drawLogo를 부르는 쪽도 @OptIn(ExperimentalImaging::class)이 필요하다.
```

opt-in이 잘 설계된 이유는 이 두 가지 선택에 있다. 실험성은 **호출자에게 계속 전파되거나, 특정 지점에서 멈추거나** 둘 중 하나로 명시적으로 처리되며, 조용히 새어 나가지 않는다. 라이브러리 전체가 실험적 API를 쓴다면 모듈 단위로 `-opt-in=com.example.ExperimentalImaging` 컴파일러 플래그를 주어 한 번에 동의할 수도 있다.

### 5.3 "서명"인 이유: deprecation과의 대칭

opt-in과 deprecation은 API 생애의 양 끝에서 대칭을 이룬다.

```text
       API의 생애
  ┌──────────────┬──────────────┬──────────────┐
  │ Experimental │    Stable    │  Deprecated  │
  │  (opt-in 필요)│  (자유 사용) │ (WARN→ERR→HIDE)│
  └──────────────┴──────────────┴──────────────┘
        ▲                              ▲
        │                              │
   "아직 확정 안 됨.             "이제 걷어낸다.
    바뀌어도 동의했잖아"          옮길 시간 준다"
```

- **Deprecation**은 안정 API를 **은퇴**시키는 계약이다. 이미 쓰고 있는 사람을 보호하기 위해 천천히 제거한다.
- **Opt-in**은 아직 안정화되지 않은 API를 **미리 공개**하는 계약이다. 작성자는 "바꿀 수 있다"는 재량을 확보하고, 사용자는 "그 재량을 알고 있다"고 서명한다.

둘 다 본질은 **계약을 명시하는 것**이다. Kotlin은 "이 API가 얼마나 확정되었는가"를 타입 시스템에 버금가는 정적 장치(애노테이션과 컴파일러 검사)로 표현한다. 그래서 실험적 API가 실수로 프로덕션에 들어가는 일은 "런타임에 터지는 사고"가 아니라 "컴파일 타임 경고를 무시한 명시적 선택"이 된다. 이 시리즈에서 반복한 주제인 **"실수를 런타임이 아니라 컴파일 타임에 잡는다"** 가 언어 진화 관리에도 그대로 적용된 것이다.

> [!warning] 흔한 오해
> "`@OptIn`을 붙이면 그 API가 안정된다"는 생각은 틀렸다. `@OptIn`은 API를 바꾸지 않는다. 그것은 **"이 API가 바뀔 수 있다는 것을 알고도 쓴다"는 사용자 쪽의 선언**일 뿐이다. 다음 릴리스에서 시그니처가 바뀌면 여전히 코드를 마이그레이션해야 한다. opt-in은 책임을 면제해 주는 것이 아니라, 알고 있었다는 사실을 기록하는 것이다.

## 6. 어두운 구석 종합 1: 널 안전의 경계선

여기서부터 세 절에 걸쳐 이 시리즈의 내용을 종합한다. 앞 장들에서 바로잡은 오개념들을 하나의 인과 관계로 다시 연결한다. 첫 번째 주제는 널이다.

### 6.1 정적 널 안전이 실제로 보장하는 것

6장(널 안전성)에서는 널 안전이 런타임 검사가 아니라 대부분 컴파일 타임에 이루어진다고 설명했다. 플랫폼 타입, `!!`, 리플렉션, Java 호출이 없는 순수 Kotlin 코드에서는 NPE가 실제로 **발생할 수 없다**. `String`과 `String?`는 타입 시스템에서 서로 다른 타입이고, 널 검사 없이 `String?`을 역참조하는 코드는 컴파일되지 않기 때문이다.

```kotlin
fun length(s: String?): Int {
    // return s.length          // 컴파일 에러: nullable을 안전 호출 없이 역참조 불가
    return s?.length ?: 0        // OK: 안전 호출 + 엘비스
}
```

이것이 Kotlin 널 안전의 핵심 가치이다. 하지만 이 보장에는 **정확한 경계선**이 있다. NPE가 없어진 것이 아니라, **네 개의 좁은 통로로만 들어올 수 있도록 막아 둔 것**이다.

```text
순수 Kotlin 영역 (NPE 불가능)
  │
  │  ┌─── 문 1: !! 연산자 — 개발자가 "널 아님"을 강제 단언
  │  ├─── 문 2: 플랫폼 타입 T! — Java에서 넘어온, 널 여부 미상의 값 (M8)
  ├──┼─── 문 3: 리플렉션·역직렬화 — 타입 검사를 우회해 null 주입
  │  └─── 문 4: 초기화 함정 — lateinit 미초기화, open 생성자의 미초기화 필드 (M9, M47)
  │
NPE가 들어올 수 있는 좁은 문들
```

### 6.2 문 1과 문 2: !!와 플랫폼 타입

`!!`는 6장(널 안전성)에서 "그 죄"라고 부른 연산자이다. `x!!`는 "x가 널이면 지금 여기서 NPE를 던져라"라는 명령이다. 즉 개발자가 **직접, 명시적으로** 널 안전에 구멍을 내는 것이다. 그래도 최소한 정직하다. 코드에 `!!`가 보이므로 위험한 지점이 드러나기 때문이다.

플랫폼 타입 `T!`는 이보다 눈에 잘 띄지 않는다. Java 메서드가 `String`을 반환하는데 널 가능성 애노테이션이 없으면, Kotlin은 그 반환 타입을 `String!`이라는 **플랫폼 타입**으로 본다. "널일 수도 있고 아닐 수도 있으니 검사를 미룬다"는 상태이다. 위험은 플랫폼 타입을 널 검사 없이 non-null처럼 그대로 쓸 때 드러난다.

```java
// Java 코드
public class Registry {
    public static String lookup(String key) { return map.get(key); }  // null 반환 가능
}
```

```kotlin
// Kotlin 코드
val name = Registry.lookup("missing")   // 컴파일 OK! name의 정적 타입은 플랫폼 타입 String! — 검사 유예
println(name.length)                    // 런타임 NPE — lookup이 null을 줬다면 여기서 늦게 터진다
```

이 코드에서 컴파일러는 아무 경고도 내지 않는다. `name`이 플랫폼 타입 `String!`이므로, 널 검사 없이 `.length`로 역참조하는 것을 허용하기 때문이다. 만약 `val name: String = ...`처럼 non-null로 선언했다면 대입 지점에 널 검사가 삽입되어, 오히려 그 자리에서 일찍 예외가 난다.

이것이 플랫폼 타입이 위험한 정확한 이유이다. **플랫폼 타입은 널 검사를 사용하는 곳으로 미루는데, 사용하는 곳에서 아무도 검사하지 않으면 NPE가 늦게 터진다.**

이를 막으려면 타입을 명시적으로 선언해야 한다.

```kotlin
val name: String? = Registry.lookup("missing")   // nullable로 못 박으면
val len = name?.length ?: 0                       // 이후 널 안전이 강제된다
```

45장(Java 상호운용)에서 다룬 이 상호운용 함정은 6.1절 그림의 "문 2"에 해당한다. 그렇다면 이 통로는 왜 존재할까? **Java에는 널 가능성을 표현하는 타입이 없기 때문**이다. Kotlin의 널 안전은 자기 코드 안에서는 완전하지만, 널 정보가 없는 언어와 만나는 접점에서는 그 정보를 만들어 낼 수 없다.

플랫폼 타입은 두 극단 사이의 **실용적인 타협**이다. 한쪽 극단은 모든 것을 nullable로 강제해 상호운용을 고통스럽게 만드는 "거짓 안전"이고, 다른 극단은 모든 것을 non-null로 가정하는 "거짓 확신"이다.

### 6.3 문 4: 초기화 순서가 만드는 틈

세 번째 종류의 NPE(정확히는 NPE와 관련된 예외)는 **초기화 순서**에서 생긴다. [[11 - 변수와 초기화 - val과 const와 lateinit]]의 `lateinit`과 [[24 - 상속과 오버라이딩과 초기화 순서]]의 open 멤버 함정이 여기에 속한다.

```kotlin
class Service {
    lateinit var config: Config
    fun run() = config.load()   // config 미초기화 상태에서 호출 시:
}                               // UninitializedPropertyAccessException (NPE 아님, 하지만 형제)

Service().run()                 // 예외: lateinit property config has not been initialized
```

`lateinit`은 "non-null이지만 초기화를 미룬다"는 약속이다. `lateinit`은 nullable이 아니다. 그 대신 초기화하기 전에 접근하면 널이 아니라 **전용 예외**가 발생한다. 타입은 non-null인데 실제로는 "아직 값이 없는" 시간상의 틈이 존재하는 것이다.

open 멤버 함정은 이보다 미묘하다. 상위 클래스 생성자가 open 멤버를 호출하면, 그 시점에 하위 클래스의 필드는 **아직 초기화되지 않은 상태**이다.

```kotlin
open class Base {
    open val label: String = "base"
    init { println("init: label = $label") }   // 하위 클래스에서 오버라이드된 label을 부른다
}

class Derived : Base() {
    override val label: String = "derived"
}

Derived()
// 출력: init: label = null     ← derived의 label 초기화 전에 Base.init이 label을 읽음
```

`label`은 타입상 non-null `String`인데 **`null`이 출력된다.** 초기화 순서상 `Base`의 `init`이 `Derived`의 `label = "derived"`보다 먼저 실행되고, 그 시점에 `label`의 백킹 필드는 아직 기본값(참조 타입이므로 null)이기 때문이다. 이 값은 JVM 백엔드에서 관찰되는 구체적인 결과이고, 핵심은 "초기화되지 않은 상태가 노출된다"는 점이다.

"open 멤버를 생성자에서 호출하면 안전하지 않다"는 말은 바로 이런 뜻이다. 널 안전 타입 시스템도 **초기화 순서라는 시간상의 함정** 앞에서는 완벽하지 않다. 타입은 "이 값은 항상 non-null이다"라고 말하지만, 초기화가 끝나기 전의 짧은 구간에서는 그 약속이 아직 지켜지지 않는다.

> [!note] 명세 기준
> 세 통로(문 1, 2, 4)는 모두 같은 구조를 가진다. 타입 시스템이 보장하려던 non-null 불변식이 시스템의 경계(개발자의 단언, 다른 언어, 시간)에서 깨진다는 것이다. 순수 Kotlin의 정상 흐름 안에서 NPE가 불가능하다는 말은 여전히 참이다. 어두운 구석은 정상 흐름 **바깥**의 좁은 통로에 있다.

## 7. 어두운 구석 종합 2: 수, 박싱, 동등성, 배열

두 번째 주제는 값의 표현이다. 여기서 다루는 함정은 모두 같은 원인에서 생긴다. **"모든 것은 객체"라는 언어 모델과 "효율을 위해 원시 타입으로 변환한다"는 백엔드 최적화가 서로 충돌하기 때문이다.**

### 7.1 박싱과 ===: 캐시 범위에 따라 달라지는 결과

8장(수 2)과 10장(불리언과 동등성과 동일성)에서 함께 다룬, 가장 악명 높은 함정이다. `Int?`는 박싱될 수 있고, 박싱된 정수에 `===`(참조 동일성)를 쓰면 결과가 **캐시 범위에 따라 달라진다**.

```kotlin
val a: Int? = 127
val b: Int? = 127
println(a === b)      // true  — JVM 백엔드: -128..127은 캐시된 박스라 같은 인스턴스

val c: Int? = 128
val d: Int? = 128
println(c === d)      // false — JVM 백엔드: 128은 캐시 밖, 매번 새 박스
println(c == d)       // true  — == 는 equals(구조적)이라 값이 같으면 true
```

이렇게 결과를 예측할 수 없는 이유를 정확히 짚어 보자. 10장에서 설명했듯 `===`는 **참조 동일성**이고, 참조 동일성은 **객체에만 의미가 있다**. `Int`는 원시 타입으로 변환될 수 있는 값이므로, 언제 박싱되어 객체가 되는지와 그 박스가 어떤 인스턴스인지는 백엔드 최적화(정수 캐시)에 달려 있다. `127`과 `128`의 차이를 만드는 것은 언어 명세가 아니라 **JVM의 `Integer.valueOf` 캐시 구현**이다.

그래서 규칙은 이렇다. **원시 타입으로 컴파일될 수 있는 값에는 `===`를 쓰지 않는다.** 수, 불리언, 문자의 동등성은 항상 `==`(구조적 동등성)로 판단한다. `===`는 "이것과 저것이 같은 객체 인스턴스인가"를 확인해야 하는 진짜 참조 타입에만 쓴다.

### 7.2 Float의 ==: 두 가지 동등성

부동소수점의 동등성은 10장에서 가장 세밀하게 다룬 부분이다. `Double`/`Float`는 **정적 타입으로 쓸 때와 박싱되거나 제네릭으로 쓸 때 동등성 규칙이 다르다.**

```kotlin
val nan = Double.NaN

// (1) 정적 Double 타입: IEEE 754 규칙
println(nan == nan)          // false  — IEEE: NaN은 자기 자신과도 다르다
println(0.0 == -0.0)         // true   — IEEE: +0.0과 -0.0은 같다

// (2) 박싱되거나 컬렉션/제네릭 경유: 전 순서(total order) 규칙
println(nan.equals(nan))     // true   — 전 순서: NaN은 자기 자신과 같다
println(0.0.equals(-0.0))    // false  — 전 순서: +0.0과 -0.0을 구분한다
println(setOf(nan).contains(nan))  // true — 컬렉션은 equals(전 순서)를 쓴다
```

같은 두 값에 대해 `==`와 `.equals()`가 **정반대의 결과**를 낸다. 왜 그럴까? 컬렉션(`Set`, `Map`)과 정렬에는 **일관된 전 순서**가 필요하다. NaN이 자기 자신과 다르면 해시셋에서 원소를 다시 찾을 수 없고, 정렬이 무한 루프에 빠질 수도 있다.

그래서 박싱이나 제네릭 문맥에서는 IEEE의 "부분 순서" 대신 Kotlin이 정의한 **전 순서**(`NaN`을 가장 큰 값으로, `-0.0 < 0.0`으로 취급)를 쓴다. 반면 정적 `Double` 산술에서는 하드웨어의 부동소수 비교(IEEE)를 그대로 쓴다.

이것도 7.1과 같은 충돌에서 나온 결과이다. `Double`이 원시 타입으로 변환될 때(정적 타입)와 객체로 다뤄질 때(컬렉션, 제네릭) 동등성의 의미가 달라진다. 실무 규칙은 이렇다. **부동소수를 셋이나 맵의 키로 쓰거나 정렬할 때는 전 순서가 적용된다는 점을 기억하고, 근사 비교가 필요하면 `==` 대신 허용 오차(epsilon) 비교를 직접 작성한다.**

$$
|a - b| < \varepsilon \quad\text{가 필요한 곳에 } a == b \text{ 를 쓰지 말 것}
$$

### 7.3 배열의 공변: Kotlin이 Java의 구멍을 막은 부분

[[34 - 제네릭 2 - 타입 소거와 reified와 바운드]]에서 다루고, 38장(컬렉션)의 "`Array`는 `List`가 아니다"와도 이어지는 내용이다. **Java의 배열은 공변(covariant)이어서 타입 구멍이 있다. Kotlin의 `Array<T>`는 무공변(invariant)이어서 그 구멍을 막았다.**

```java
// Java — 배열 공변은 컴파일되지만 런타임에 터진다
Object[] arr = new String[3];   // 공변: String[]을 Object[]로 취급 허용
arr[0] = 42;                    // 컴파일 OK! 런타임: ArrayStoreException
```

```kotlin
// Kotlin — Array<T>는 무공변이라 애초에 컴파일이 안 된다
val strings: Array<String> = arrayOf("a", "b", "c")
// val objs: Array<Any> = strings   // 컴파일 에러: Array<String>은 Array<Any>가 아니다
```

Java 배열의 공변은 제네릭 이전 시대에서 물려받은 것으로, "정적으로는 허용하고 런타임에 검사(store check)한다"는 타협이다. Kotlin은 [[33 - 제네릭 1 - 타입 파라미터와 변성]]의 변성 규칙을 배열에도 일관되게 적용해 `Array<T>`를 무공변으로 만들었다.

읽기와 쓰기를 모두 하는 배열은 `T`를 생산하기도 하고 소비하기도 하므로(`get`은 out, `set`은 in) 어느 방향으로도 변성을 줄 수 없다. 그래서 `Array<String>`을 `Array<Any>`로 업캐스트하는 것 자체가 컴파일 에러이다. Java에서 `ArrayStoreException`으로 런타임에 드러나는 함정을 Kotlin은 **컴파일 타임에 막는다**.

여기에 또 하나의 오해가 겹친다. `Array<T>`는 `List<T>`가 **아니다.** 둘은 별개의 타입이고, 원시 배열(`IntArray`, `DoubleArray` 등)은 또 다른 타입이다. `IntArray`는 JVM 백엔드에서 원시 `int[]`로 변환되어 박싱을 피하고, `Array<Int>`는 박싱된 `Integer[]`가 된다.

`List<Int>`, `Array<Int>`, `IntArray` 이 세 타입은 계약도 표현도 다르다. "Kotlin 배열은 List다"라는 통념은 세 측면 모두에서 틀렸다.

| 타입 | 계약 | JVM 백엔드 표현 | 변성 |
|------|------|-----------------|------|
| `List<Int>` | 읽기 전용 인터페이스 | `List` (박싱 원소) | 공변(`out E`) |
| `Array<Int>` | 고정 크기, 읽기·쓰기 | `Integer[]` (박싱) | 무공변 |
| `IntArray` | 고정 크기, 읽기·쓰기 | `int[]` (원시) | 무공변 |

### 7.4 오버플로: 예외 없는 래핑

마지막은 8장에서 다룬 오버플로이다. 정수 산술의 결과가 범위를 넘으면 Kotlin은 **예외를 던지지 않고 2의 보수로 래핑**한다. 이것은 백엔드가 정하는 것이 아니라 **언어 계약**이므로 모든 타깃에서 똑같다.

```kotlin
println(Int.MAX_VALUE + 1)      // -2147483648  (모든 타깃에서 래핑)
println(Int.MAX_VALUE)          // 2147483647
```

"범위를 넘으면 예외가 나겠지"라는 기대는 틀렸다. 안전한 산술이 필요하면 `Math.addExact`(JVM) 같은 검사 연산을 명시적으로 쓰거나, 처음부터 범위를 넘지 않도록 `Long`을 쓴다. 오버플로가 조용히 일어나는 것은 성능을 위한 선택(연산마다 오버플로 검사를 넣지 않음)이고, 그 대신 범위는 개발자가 책임져야 한다. 이것은 7장(수 1)의 "암시적 확대 변환 없음"과 같은 설계 태도이다. 즉 **수의 표현과 한계를 개발자가 명시적으로 통제한다.**

## 8. 어두운 구석 종합 3: 제네릭, 스마트캐스트, 디스패치

세 번째 주제는 타입 정보가 컴파일과 런타임 사이에서 사라지거나, 정적으로 해석되어 직관과 다르게 동작하는 지점들이다.

### 8.1 타입 소거: 런타임에 사라지는 제네릭

34장(제네릭 2)에서 설명했듯 **JVM 백엔드에서는 제네릭 타입 인자가 런타임에 소거된다.** `List<String>`과 `List<Int>`는 런타임에 둘 다 그냥 `List`이다.

```kotlin
val a: List<String> = listOf("x")
val b: List<Int> = listOf(1)
// a is List<String>              // 컴파일 에러: 소거된 타입은 is로 검사 불가
println(a is List<*>)             // true  — 스타 프로젝션으로만 검사 가능
```

소거를 우회하는 방법은 [[15 - 인라인 함수와 reified]]에서 다룬 `reified`뿐이다. `inline` 함수의 `reified` 타입 파라미터는 호출하는 곳에 인라인되면서 실제 타입으로 바뀌므로, 그 안에서 `T::class`나 `is T`가 동작한다. 단, 최상위 타입에만 해당하며 `List<String>`의 `String`은 여전히 소거된다.

```kotlin
inline fun <reified T> Any.asOrNull(): T? = this as? T

val x: Any = "hello"
println(x.asOrNull<String>())     // hello  — reified라 런타임에 String 검사 가능
println(x.asOrNull<Int>())        // null
```

그렇다면 왜 소거할까? 45장(Java 상호운용)에서 본 답은 **Java와의 바이너리 호환**이다. JVM 제네릭 자체가 소거 방식이므로, Kotlin이 제네릭 타입을 런타임에 유지하면 Java와의 상호운용이 깨진다. 소거는 Kotlin이 선택했다기보다 **JVM 플랫폼을 타깃으로 삼은 대가**이다. 다른 백엔드(예: Native)에서는 사정이 다를 수 있지만, 언어는 이식성을 위해 소거를 전제로 설계되었고 `reified`라는 명시적인 탈출구를 제공한다.

### 8.2 스마트캐스트가 적용되지 않는 곳

6장(널 안전성)에서 다루었듯 **스마트캐스트가 항상 적용되는 것은 아니다.** 스마트캐스트는 "이 지점 이후로 이 값의 타입이 좁혀졌다"는 사실을 컴파일러가 제어 흐름 분석으로 증명하는 것이다. 그런데 이 증명이 **불가능한 조건**이 있다.

```kotlin
class Box(var content: String?)               // var 프로퍼티

fun show(box: Box) {
    if (box.content != null) {
        // println(box.content.length)         // 컴파일 에러: var 프로퍼티는 스마트캐스트 불가
    }
    val c = box.content
    if (c != null) println(c.length)           // OK: 지역 val로 받으면 스마트캐스트 됨
}
```

`box.content`가 스마트캐스트되지 않는 이유는 분명하다. `content`는 `var`이므로 검사와 사용 사이에 다른 스레드나 커스텀 게터가 값을 바꿀 수 있다. 따라서 컴파일러는 "검사할 때 non-null이었으니 사용할 때도 non-null"이라고 **증명할 수 없다.** 스마트캐스트가 막히는 대표적인 조건은 다음과 같다.

```text
스마트캐스트 불가 조건 (컴파일러가 불변을 증명 못 하는 경우)
  ├─ var 프로퍼티          — 검사와 사용 사이에 바뀔 수 있음
  ├─ 커스텀 게터를 가진 val — 매 접근이 다른 값을 줄 수 있음
  ├─ 다른 모듈의 open val   — 오버라이드가 커스텀 게터일 수 있음
  └─ 캡처된 var (클로저)    — 클로저가 언제든 수정 가능 (14장)
```

이것은 널 안전 시스템의 함정이 아니라 오히려 **정직함**을 보여 준다. 컴파일러는 증명할 수 있는 경우에만 스마트캐스트한다. 증명할 수 없는 곳에서 스마트캐스트를 강행했다면 그것이야말로 오류이다. 검사한 뒤에 값이 바뀌어 NPE가 날 수 있기 때문이다.

대부분은 지역 `val`로 값을 고정(스냅샷)하면 해결된다. K2 컴파일러는 이전보다 정교한 데이터 흐름 분석으로 스마트캐스트가 가능한 범위를 넓혔지만, 가변성, 다른 모듈, 커스텀 게터라는 근본적인 제약은 안전을 위해 그대로 유지한다.

### 8.3 확장 함수의 정적 디스패치: 다형성처럼 보이지만 다형성이 아니다

[[35 - 확장 함수와 프로퍼티]]에서 설명했듯 **확장 함수는 정적으로 디스패치된다.** 멤버 함수처럼 `receiver.method()` 문법으로 호출하지만, 어떤 확장이 호출될지는 런타임의 실제 타입이 아니라 **수신자의 정적(선언) 타입**으로 결정된다.

```kotlin
open class Shape
class Circle : Shape()

fun Shape.describe() = "shape"
fun Circle.describe() = "circle"

val s: Shape = Circle()          // 정적 타입 Shape, 실제 타입 Circle
println(s.describe())            // "shape"  — 정적 타입 Shape로 해소됨!

val c: Circle = Circle()
println(c.describe())            // "circle" — 정적 타입 Circle
```

`s`의 실제 객체는 `Circle`인데 `Shape.describe()`가 호출된다. 멤버 함수였다면 가상 디스패치로 `Circle`의 오버라이드가 호출되었을 것이다. 35장에서 보았듯 확장 함수는 컴파일할 때 **수신자를 첫 번째 인자로 받는 정적 메서드**로 변환된다.

```kotlin
// 개념적 컴파일 결과 (JVM 백엔드)
fun describe(receiver: Shape): String = "shape"
fun describe(receiver: Circle): String = "circle"
// s.describe()는 오버로드 해소로 describe(Shape) 선택 — s의 정적 타입이 Shape이므로
```

즉 확장 함수 호출은 컴파일 타임의 **오버로드 해석**이고, 런타임의 오버라이드 디스패치가 아니다. 여기에 규칙이 하나 더 있다. **이름이 같은 멤버 함수가 있으면 항상 멤버가 우선한다.** 확장은 멤버가 없는 타입에 기능을 "빌려주는" 정적 도구이며, 클래스에 메서드를 실제로 추가하는 것이 아니다. 이 정적인 성격을 잊고 다형성을 기대하면 "`Circle`인데 왜 `shape`가 나오지?"라며 당황하게 되는데, 이것이 8.3절에서 말하는 함정이다.

### 8.4 세 주제의 공통 원인

6절, 7절, 8절의 함정을 나란히 놓으면 하나의 그림이 보인다.

```text
       세 개의 설계 제약이 교차하는 곳에서 어두운 구석이 태어난다

   [정적 타입 시스템]          [멀티 백엔드 최적화]        [Java 공존]
   널/변성/제네릭을 정적 검사   객체를 원시로 낮춤          널 정보 없는 언어와 악수
         │                          │                          │
         ▼                          ▼                          ▼
   스마트캐스트 한계(M13)      박싱된 ===(M48)            플랫폼 타입 NPE(M8)
   타입 소거(M19)             Float ==의 이중성          !! 의 필요(M7 경계)
   확장 정적 디스패치(M14)     Int? 박싱(M5), 오버플로     소거의 근원(호환)
```

어두운 구석은 언어의 **결함**이 아니다. "정적 안전", "여러 기계에서 빠른 실행", "20년 된 Java 생태계와의 공존"이라는 서로 다른 세 목표를 동시에 만족시키려는 설계에서 **필연적으로 생기는 접점**이다. 각 함정은 그 접점에서 한 목표가 다른 목표에 양보한 흔적이다. 이렇게 보면 함정들은 "외워야 할 예외 목록"이 아니라 "설계 트레이드오프에서 논리적으로 따라 나오는 결과"가 된다.

## 9. 언어의 미래: K2 이후, Wasm, 그리고 플러그인 생태계

### 9.1 K2가 가능하게 한 것: 프론트엔드의 재구축

2장(K2와 IR 백엔드)에서 보았듯 2.0의 K2는 단순한 속도 개선이 아니라 **프론트엔드(FIR)를 다시 설계한 것**이다. 이것이 왜 미래와 관련이 있을까? 프론트엔드는 타입 추론, 스마트캐스트, 진단이 이루어지는 곳이다. 그 기반이 견고해지면 그 위에 새 언어 기능을 더하기가 쉬워진다. K2 이후 논의되는 더 정교한 스마트캐스트, 문맥 수신자(context receivers/parameters), 명시적 null 처리 개선 같은 방향은 모두 새로 구축한 프론트엔드가 있기에 가능하다.

다만 여기서는 조심해야 한다. "다음 버전에 무엇이 들어온다"고 단정하는 것은 이 장의 범위를 벗어나고, 시점에 따라 달라지는 예측이기도 하다. 확실히 말할 수 있는 것은 **방향성**이다. Kotlin은 하위 호환을 지키면서(4절) 실험 기능을 opt-in으로 미리 공개하고(5절), 안정화한 뒤 정식으로 포함하는 주기를 반복한다. 미래의 기능도 이 과정을 거친다.

### 9.2 Wasm: 네 번째 타깃의 등장

1절의 백엔드 그림에서 Wasm은 가장 최근에 추가된 타깃이다. Kotlin/Wasm에는 브라우저와 런타임을 위한 `wasmJs`, WASI 기반의 `wasmWasi` 두 가지가 있다. 이 글을 쓰는 2.x 시점을 기준으로 Wasm 타깃은 **알파**에 가까우며(4.2절의 안정성 등급), 그래서 API와 성능 특성이 릴리스마다 조정된다.

Wasm이 중요한 이유는 멀티플랫폼의 그림을 완성하기 때문이다. Kotlin은 JVM(서버, 안드로이드), Native(iOS, 데스크톱, 임베디드), JS(웹)에 이어 Wasm(고성능 웹, 플러그인, 크로스플랫폼 런타임)까지 "하나의 언어, 여러 플랫폼"의 범위를 넓혀 왔다. 타깃을 추가할 때마다 1절의 원칙인 **프론트엔드는 공유하고 백엔드만 추가한다**를 되풀이한다. Wasm 백엔드가 추가되어도 `Int?`의 널 가능성이나 `when`의 완전성 같은 언어 규칙은 바뀌지 않는다.

> [!note] 명세 기준
> Wasm의 안정성 등급, 지원하는 표준 라이브러리 범위, 상호운용 방식은 빠르게 바뀌고 있다. "Kotlin/Wasm은 X를 지원한다"는 문장은 반드시 버전과 함께 확인해야 한다. 이 장에서 단정하는 것은 "Wasm이 네 번째 백엔드 타깃으로 자리 잡아 가고 있으며, 2.x 시점에 알파였다"처럼 시점을 명시한 사실뿐이다.

### 9.3 컴파일러 플러그인 생태계: 언어 바깥으로의 확장

4.4절에서 다룬 KSP나 all-open 같은 컴파일러 플러그인은 앞으로도 중요한 축이다. Kotlin의 진화는 언어 문법에 기능을 추가하는 데서 그치지 않고, **컴파일러를 열어 도구와 프레임워크가 자기 기능을 넣을 수 있게** 하는 방향으로 나아간다. 직렬화(`kotlinx.serialization`), Compose의 `@Composable` 변환, 의존성 주입의 코드 생성이 모두 컴파일러 확장으로 동작한다.

이것은 1장(코틀린이란 무엇인가)에서 말한 언어 설계 철학인 "실용주의"에서 자연스럽게 따라 나온다. 모든 기능을 언어 코어에 넣으면 언어가 비대해진다. 그래서 코어는 공통 표준 라이브러리(3절)처럼 작고 견고하게 유지하고, 확장은 플러그인 생태계에 맡긴다. "작은 코어와 열린 확장"은 Kotlin이 멀티플랫폼 UI, 서버, 데이터 같은 새 영역으로 뻗어 나가는 방식이다.

### 9.4 진화가 지켜야 하는 것: 쌓여 가는 신뢰

미래를 이야기하면서 한 가지를 강조하고 싶다. 언어가 매년 바뀌어도 **개발자의 신뢰가 계속 쌓이는** 이유는 4절과 5절의 계약(하위 호환, deprecation 사이클, opt-in)을 지키기 때문이다. 만약 어떤 릴리스가 조용히 의미를 바꿔 이미 배포된 코드를 깨뜨린다면, 그 한 번의 일로 수년간 쌓은 신뢰가 무너진다.

45장(Java 상호운용)에서 강조한 바이너리와 시그니처 호환 감각, 그리고 이 장에서 다룬 안정성 계약은 같은 원리에서 나온다. **이미 배포된 것과의 약속을 지키는 것이 진화의 전제 조건**이다. 언어를 오래 살아남게 하는 것은 새 기능을 더하는 능력보다 옛 약속을 깨지 않는 규율이다.
