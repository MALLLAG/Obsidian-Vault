[[21 - 클래스와 생성자]]에서는 클래스 하나가 만들어지는 과정, 즉 주 생성자와 `init` 블록, 프로퍼티 초기화의 순서를 바이트코드 수준에서 살펴봤다. [[27 - 데이터 클래스]]와 [[30 - sealed 클래스와 대수적 데이터 타입]]에서는 클래스를 "값을 담는 형태"로 특수화하는 방법을, [[28 - object와 companion - 싱글턴과 동반 객체]]에서는 클래스 없이 이름 붙은 인스턴스를 딱 하나 만드는 `object` 선언을 다뤘다.

이 장에서는 이 내용을 "클래스가 다른 클래스나 함수의 *본문 안*에 놓일 때"라는 관점에서 다시 살펴본다. 선언 위치가 바뀌면 스코프가 바뀌고, 스코프가 바뀌면 그 타입이 무엇을 볼 수 있는지, 무엇을 캡처하는지, 언제 사라지는지가 모두 달라진다.

이 장은 클래스·인터페이스·`object`·`enum`을 다른 선언의 본문 안에 중첩하는 문법과 의미를 다룬다. 구체적으로는 바깥 참조의 유무(`inner`), 한정된 `this`(`this@Outer`), 지역 클래스의 변수 캡처, 이름 없는 일회용 인스턴스를 만드는 **객체 표현식(object expression)** 이다.

먼저 Kotlin이 Java와 반대로 **정적 중첩(외부 참조 없음)을 기본값** 으로 정한 이유를 보고, `inner`가 추가하는 합성 필드, 지역 클래스와 익명 객체, 익명 객체와 람다/SAM의 선택 기준을 차례로 설명한 뒤, 이런 구조가 바깥 객체를 캡처해 메모리 누수를 만드는 경로와 그것을 끊는 방법으로 마무리한다.

이름 있는 싱글턴 `object`와 `companion object`는 28장에서 다루고, 여기서는 익명 객체와 비교할 때만 언급한다. Kotlin이 값이 아니라 변수를 캡처한다는 원리와 `var`를 `Ref`로 감싸는 방식은 [[14 - 클로저와 캡처]]에서 설명했으므로, 이 장에서는 그 원리가 지역 클래스와 익명 객체에서 어떻게 나타나는지만 본다.

람다 문법과 함수 참조는 [[13 - 함수 타입과 람다와 함수 참조]]에서, 수신 객체 지정 람다의 `this`는 [[16 - 스코프 함수와 수신 객체 관용구]]에서 다룬다.

## 1. 왜 클래스 안에 클래스를 두는가: 중첩의 동기와 두 종류

### 1.1 문제: 개념적으로 종속된 타입을 어디에 둘 것인가

프로그램을 작성하다 보면 "어떤 타입은 다른 타입 안에서만 의미가 있다"는 상황을 자주 만난다. 이진 트리의 `Node`는 `Tree` 밖에서 따로 쓰일 이유가 없고, 상태 기계의 `State`는 그 기계에 속한 개념이며, 파서의 `Token`은 파서가 쓰는 어휘다. 이런 타입을 최상위(top-level)에 그대로 두면 이름공간이 지저분해지고, 어떤 타입이 어떤 타입에 종속되는지가 코드에 드러나지 않는다.

Kotlin은 이런 개념적 종속을 문법으로 표현할 수 있도록 **선언의 중첩(nesting)** 을 허용한다. 클래스, 인터페이스, `object`, `enum`, 데이터 클래스, 봉인 클래스 등 사실상 모든 타입 선언을 다른 클래스의 본문 안에 넣을 수 있다.

```kotlin
class Tree {
    // Node는 Tree의 내부 어휘. 밖에서는 Tree.Node로만 부른다.
    class Node(val value: Int, var left: Node? = null, var right: Node? = null)

    private var root: Node? = null

    fun insert(value: Int) { /* ... */ }
}

fun main() {
    val n = Tree.Node(42)   // 바깥에서 접근 시 Tree. 을 앞에 붙인다
    println(n.value)         // => 42
}
```

여기서 `Node`는 `Tree`라는 이름공간 안에 있다. `Tree.Node`라는 완전한 이름(qualified name) 자체가 "이 노드는 트리에 속한다"는 사실을 알려 준다. 이름공간 정리, 캡슐화, 응집(cohesion)이 중첩을 쓰는 첫 번째 이유다.

### 1.2 중요한 구분: 바깥 인스턴스를 아는가, 모르는가

그런데 "클래스 안의 클래스"에는 근본적으로 다른 두 종류가 있다. 이 구분이 이 장 전체의 기준이다.

1. **중첩 클래스(nested class)**: 바깥 클래스의 *이름공간*에만 속한다. 바깥 클래스의 특정 **인스턴스**와는 아무 관계가 없다. `Tree.Node`를 만들 때 `Tree` 객체는 필요하지 않다. 위 예제가 바로 이 경우다.

2. **이너 클래스(inner class)**: `inner` 키워드를 붙이면, 이 클래스의 모든 인스턴스는 자신을 만든 바깥 클래스의 **특정 인스턴스**에 대한 참조를 갖는다. 그래서 그 바깥 인스턴스의 프로퍼티와 메서드를 자기 것처럼 쓸 수 있다.

```kotlin
class Outer {
    private val name = "바깥"

    class Nested {
        // fun show() = name  // 컴파일 에러: 바깥 인스턴스가 없어 name에 닿지 못함
        fun show() = "중첩 클래스는 바깥 인스턴스를 모른다"
    }

    inner class Inner {
        fun show() = "이너는 바깥의 name을 안다: $name"  // OK
    }
}

fun main() {
    println(Outer.Nested().show())      // 바깥 인스턴스 없이 생성
    println(Outer().Inner().show())     // 바깥 인스턴스가 있어야 생성: Outer() 먼저
}
// => 중첩 클래스는 바깥 인스턴스를 모른다
// => 이너는 바깥의 name을 안다: 바깥
```

`main`의 두 줄을 자세히 보자. `Outer.Nested()`는 `Outer`의 인스턴스 없이 바로 만들어진다. 반면 `Outer().Inner()`는 먼저 `Outer()`로 바깥 인스턴스를 만든 다음, *그 인스턴스에 대해* `.Inner()`를 호출한다. 이 생성 문법의 차이가 두 종류의 본질적인 차이를 보여 준다. 이너 클래스는 반드시 바깥 인스턴스가 있어야 만들 수 있다.

### 1.3 Java와 반대인 기본값

여기서 초보자가 거의 예외 없이 빠지는 함정이 있다. **Java에서는 정반대다.** Java의 중첩 클래스는 `static`을 붙이지 *않으면* 자동으로 이너 클래스가 되어 바깥 인스턴스를 참조한다. 그래서 Java 개발자는 "중첩 클래스는 자동으로 바깥에 접근할 수 있다"는 직관을 갖고 있다.

Kotlin은 이 기본값을 반대로 정했다. Kotlin에서 아무 수식어 없는 중첩 클래스는 기본적으로 **바깥 참조가 없고(Java의 `static` 중첩 클래스에 해당)**, 바깥 인스턴스를 참조하려면 `inner`를 *명시적으로* 붙여야 한다.

```java
// Java
class Outer {
    class Inner {}          // 암시적으로 바깥 인스턴스를 붙잡음 (실수의 온상)
    static class Nested {}  // 명시적으로 static을 붙여야 독립적
}
```

```kotlin
// Kotlin — 기본값이 뒤집혔다
class Outer {
    class Nested {}         // 기본: 바깥 참조 없음 (Java의 static에 해당)
    inner class Inner {}    // 명시적 inner를 붙여야 바깥 인스턴스를 붙잡음
}
```

이렇게 정한 데는 이유가 있다. Java의 암시적 이너 클래스는 오랫동안 **의도하지 않은 메모리 누수**의 대표적인 원인이었다(8절에서 자세히 본다). 개발자가 `static`을 깜빡하면, 별생각 없이 선언한 중첩 클래스가 바깥 객체 전체를 계속 살려 두는 참조 경로가 된다.

Kotlin은 위험한 쪽, 즉 바깥을 참조하는 쪽을 반드시 직접 선언하게 해서 실수가 안전한 쪽으로 일어나도록 했다. 이는 Kotlin 설계 전반에 나타나는 "안전한 기본값(safe by default)" 원칙의 한 사례다. `final`이 기본이고 `open`을 명시해야 하는 것([[24 - 상속과 오버라이딩과 초기화 순서]]), 널 불가가 기본이고 `?`를 명시해야 하는 것([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]])과 같은 원칙이다.

> [!warning] 흔한 오해
> "중첩 클래스는 당연히 바깥 필드를 읽을 수 있다"는 생각은 Java 습관에서 온 직관이며, Kotlin에서는 틀리다. `inner` 없는 중첩 클래스는 바깥 *인스턴스*를 전혀 참조하지 못하고, 컴파일러가 "unresolved reference"로 바로 막는다. 바깥 멤버에 접근하려면 `inner`를 붙이거나, 바깥 인스턴스를 생성자 인자로 직접 넘겨야 한다.

### 1.4 두 종류를 한 표로 정리

| 관점 | 중첩 클래스 (`class`) | 이너 클래스 (`inner class`) |
|------|----------------------|----------------------------|
| 바깥 인스턴스 참조 | 없음 | 있음 (합성 필드로 저장) |
| 생성 문법 | `Outer.Nested()` | `Outer().Inner()` (인스턴스 필요) |
| 바깥 인스턴스 멤버 접근 | 불가 (인스턴스 없음) | 가능 (`this@Outer` 암시) |
| 바깥의 `companion`/정적 멤버 | 접근 가능 | 접근 가능 |
| JVM 컴파일 형태 | 정적 중첩 클래스 | 합성 필드 `this$0` 보유 |
| Java 대응 | `static` 중첩 클래스 | (기본) 이너 클래스 |
| 메모리 수명 | 바깥과 독립 | 바깥 인스턴스를 살려 둠 |
| 기본값 여부 | **기본** | 명시적 `inner` 필요 |

이제 이 표의 각 행을 하나씩 살펴보면서, 왜 그런지, 바이트코드에서 어떤 일이 일어나는지, 어디서 실수하기 쉬운지를 설명한다.

## 2. 중첩 클래스: 바깥 인스턴스와 관계없는 독립 타입

### 2.1 이름공간만 공유하고 인스턴스 관계는 없다

수식어 없는 중첩 클래스는 바깥 클래스의 이름공간 안에만 있다. 그 인스턴스는 바깥 클래스의 어떤 인스턴스와도 연결되지 않는다. 개념적으로는 "최상위에 선언한 클래스의 이름만 안쪽으로 옮긴 것"과 같다. 실제로 다음 두 코드는 `Node`가 어떤 인스턴스에 묶이느냐는 관점에서 완전히 같다.

```kotlin
// (A) 중첩
class Graph {
    class Edge(val from: Int, val to: Int)
}
// (B) 최상위 + 이름 규칙
class Graph2
class Graph2Edge(val from: Int, val to: Int)
```

차이는 이름공간과 가시성 제어뿐이다. `Graph.Edge`는 "간선은 그래프에 속한 개념"이라는 사실을 이름으로 표현한다. 또한 `Edge`를 `private`로 숨겨 그래프 밖에서는 아예 만들 수 없게 할 수도 있다(2.4).

### 2.2 바깥의 `private` 멤버에 접근할 수 있는가: 인스턴스가 있으면 가능하다

여기에는 미묘한 부분이 있다. 중첩 클래스는 바깥 *인스턴스*를 참조하지 못한다. 그러나 Kotlin의 `private` 가시성은 "선언을 감싸는 클래스와 그 안의 모든 멤버(중첩·이너 클래스 포함)에게 보인다"는 렉시컬 규칙이다([[26 - 가시성 한정자]]). 따라서 중첩 클래스가 바깥 인스턴스를 **인자로 넘겨받으면** 그 인스턴스의 `private` 멤버에 접근할 수 있다.

```kotlin
class BankAccount(private val balance: Long) {
    // 중첩 클래스: 바깥 인스턴스를 스스로는 모르지만,
    // 인자로 받으면 그 private 멤버에 닿는다 (렉시컬 가시성)
    class Auditor {
        fun snapshot(account: BankAccount): Long =
            account.balance   // OK: private balance에 접근 가능
    }
}

fun main() {
    val audit = BankAccount.Auditor()
    println(audit.snapshot(BankAccount(10_000)))  // => 10000
}
```

그래서 "인스턴스는 따로 필요하지만 `private` 접근은 가능하다"는 두 사실이 함께 성립한다. 중첩 클래스는 바깥 인스턴스를 *암시적으로* 갖지 않을 뿐이고, 렉시컬하게 안쪽에 있으므로 `private` 멤버에 접근할 권한은 있다.

> [!note] 명세 기준
> Kotlin의 `private`는 파일 최상위 선언에서는 "같은 파일"에, 클래스 멤버에서는 "그 클래스와 그 안의 모든 중첩·이너 선언"에 보인다. 즉 Kotlin의 `private`는 Java의 `private`(클래스 단위)와 대체로 같지만, 중첩·이너 클래스의 경계를 자연스럽게 넘는다.
>
> JVM 백엔드에서 이렇게 경계를 넘는 private 접근은 보통 컴파일러가 만든 **합성 접근자 메서드**(예: `access$getBalance$p`)를 통해 이루어진다. 실제 JVM의 `private` 필드는 다른 클래스가 직접 읽을 수 없기 때문이다. 이 부분은 백엔드 구현 사항이며 소스 수준의 의미에는 드러나지 않는다.

### 2.3 바깥의 `companion`·정적 멤버는 자유롭게 접근할 수 있다

바깥 클래스에 `companion object`가 있으면, 그 멤버는 인스턴스 없이 접근하는 "클래스 수준" 멤버이므로 중첩 클래스에서도 그대로 쓸 수 있다.

```kotlin
class Config {
    companion object {
        const val VERSION = 3
        private fun defaultTimeout() = 30
    }

    class Loader {
        fun describe() = "config v$VERSION, timeout=${defaultTimeout()}s"
        // companion의 private 멤버까지 접근 가능 (렉시컬 내부자)
    }
}

fun main() {
    println(Config.Loader().describe())  // => config v3, timeout=30s
}
```

`companion object`는 28장(object와 companion)에서 자세히 다룬다. 여기서 기억할 점은 중첩 클래스가 바깥 인스턴스는 모르더라도, 바깥의 클래스 수준 선언(companion, 다른 중첩 타입, 상수)에는 접근할 수 있다는 것이다.

### 2.4 가시성과 완전한 이름: 밖에서 부르는 방법

중첩 클래스에도 가시성 한정자를 적용할 수 있다. `private`로 선언하면 바깥 클래스 안에서만 쓰는 구현 세부가 되어, 외부 코드가 `Outer.Nested`로 접근할 수 없다.

```kotlin
class LinkedStack<T> {
    // 스택의 내부 표현. 밖에서는 존재조차 몰라야 한다.
    private class Cell<T>(val value: T, val next: Cell<T>?)

    private var top: Cell<T>? = null

    fun push(v: T) { top = Cell(v, top) }
    fun pop(): T? {
        val c = top ?: return null
        top = c.next
        return c.value
    }
}

fun main() {
    val s = LinkedStack<String>()
    s.push("a"); s.push("b")
    println(s.pop())   // => b
    // val c = LinkedStack.Cell("x", null)  // 컴파일 에러: Cell은 private
}
```

`Cell`을 `private` 중첩 클래스로 두었기 때문에 연결 리스트라는 내부 구현이 완전히 캡슐화된다. 사용자는 `push`/`pop`이라는 계약만 보고, `Cell`이라는 내부 표현은 볼 수 없다. 이런 **구현 타입의 은닉**은 중첩 클래스의 가장 유용한 쓰임 중 하나다.

기본 가시성은 `public`이므로, 한정자 없는 중첩 클래스는 어디서든 `Outer.Nested`로 접근할 수 있다. 필요하면 `internal`(모듈 단위, 26장 가시성 한정자 참고)이나 `protected`(바깥 클래스의 하위 클래스에서만)로 범위를 조절한다.

### 2.5 JVM에서 컴파일된 결과

> [!note] 명세 기준 / JVM 백엔드
> JVM 백엔드에서 중첩 클래스 `Outer.Nested`는 별도의 `.class` 파일인 `Outer$Nested.class`로 컴파일되며, Java의 **정적 중첩 클래스**로 표현된다. 즉 바깥 인스턴스를 가리키는 합성 필드가 없다. Kotlin/Native·JS·Wasm 백엔드는 각자의 방식으로 "바깥 참조 없음"을 표현하지만, 바깥 인스턴스와 무관하다는 소스 수준의 의미는 모든 타깃에서 같다.

이 사실은 실무에서도 중요하다. 중첩 클래스의 인스턴스는 바깥 인스턴스를 살려 두지 않으므로, 오래 유지되는 자료구조의 원소로 써도 안전하다. 8절에서 다룰 "누수를 막기 위해 `inner`를 중첩 클래스로 바꾸기"의 근거가 바로 이것이다.

### 2.6 클래스만 중첩할 수 있는 것은 아니다: 인터페이스·object·enum·sealed

클래스 말고도 인터페이스, `object`, `enum class`, 데이터 클래스, 봉인 계층을 모두 중첩할 수 있다. 특히 봉인 계층(30장 sealed 클래스)에서는 이렇게 쓰는 것이 관용적이다.

```kotlin
sealed interface Shape {
    // 봉인 계층의 변형들을 바깥 이름공간 안에 모은다
    data class Circle(val radius: Double) : Shape
    data class Rectangle(val w: Double, val h: Double) : Shape
    data object Empty : Shape           // data object: 27장/28장
}

fun area(s: Shape): Double = when (s) {   // else 불필요 — 완전성 검사
    is Shape.Circle -> Math.PI * s.radius * s.radius
    is Shape.Rectangle -> s.w * s.h
    Shape.Empty -> 0.0
}
```

여기서 `Circle`, `Rectangle`, `Empty`는 모두 `Shape`의 중첩 선언이면서 하위 타입이다. 봉인 계층의 모든 변형을 한 이름공간에 모아 두는 이 패턴은 Kotlin에서 대수적 데이터 타입을 표현하는 표준적인 방법이다. 중첩된 `object`인 `Empty`는 그 자체로 싱글턴이면서 바깥 이름공간에 속한다는 점에서, 이 장의 주제와 28장의 주제가 만나는 지점이다.

## 3. 이너 클래스: 바깥 인스턴스를 참조한다

### 3.1 `inner`가 하는 일: 암시적 바깥 참조

`inner` 키워드를 붙이면 클래스는 자신을 만든 바깥 인스턴스에 대한 **암시적 참조**를 갖는다. 이 참조 덕분에 이너 클래스의 코드는 바깥 인스턴스의 프로퍼티와 메서드를 한정자 없이 직접 호출할 수 있다.

```kotlin
class Grid(val width: Int, val height: Int) {
    private val cells = Array(width * height) { 0 }

    inner class Cursor(private var x: Int, private var y: Int) {
        // width, height, cells 모두 바깥 Grid 인스턴스의 것 — 직접 접근
        fun read(): Int = cells[y * width + x]
        fun moveRight(): Boolean {
            return if (x + 1 < width) { x++; true } else false
        }
    }

    fun cursorAt(x: Int, y: Int) = Cursor(x, y)  // 바깥 몸통 안이므로 그냥 Cursor()
}

fun main() {
    val grid = Grid(3, 2)
    val cur = grid.cursorAt(0, 0)
    println(cur.moveRight())   // => true  (width=3 안이므로 이동 성공)
    println(cur.read())        // => 0
}
```

`Cursor`는 `width`, `height`, `cells`를 자기 필드처럼 쓰지만, 이들은 사실 `Cursor`를 만든 `grid` 인스턴스의 멤버다. 커서는 격자 없이는 의미가 없다는 도메인의 사실을 `inner`가 코드 구조로 표현한다.

### 3.2 바깥 인스턴스가 있어야 만들 수 있다

이너 클래스는 바깥 인스턴스 없이는 존재할 수 없다. 그래서 생성 문법이 다르다. 바깥 클래스 *본문 안에서는* 암시적인 바깥 인스턴스(`this`)가 있으므로 그냥 `Cursor(...)`로 만든다. 그러나 바깥에서 만들 때는 반드시 바깥 인스턴스를 앞에 써야 한다.

```kotlin
fun main() {
    val grid = Grid(3, 2)
    val c1 = grid.Cursor(1, 1)   // 바깥 인스턴스 grid에 대고 생성
    // val c2 = Grid.Cursor(1, 1)  // 컴파일 에러: 이너는 바깥 인스턴스가 필요
}
```

인스턴스에 점을 찍고 생성자를 호출하는 `grid.Cursor(1, 1)`이라는 낯선 문법이 이너 클래스의 성격을 그대로 보여 준다. 컴파일러 입장에서 이 호출은 "`grid`를 바깥 참조로 삼는 `Cursor`를 하나 만들라"는 뜻이다.

### 3.3 JVM 바이트코드에서 일어나는 일

> [!note] 명세 기준 / JVM 백엔드
> JVM 백엔드에서 `inner class Cursor`는 바깥 인스턴스를 담는 합성 필드(관례적으로 `this$0`)를 갖고, 그 생성자는 첫 번째 인자로 바깥 인스턴스를 받는 형태로 컴파일된다. 개념적으로 다음 Java 코드와 같다.

```java
// inner 클래스의 개념적 컴파일 형태 (JVM)
public final class Grid {
    // ...
    public final class Cursor {
        // synthetic 필드: 바깥 인스턴스를 붙잡는다
        private final Grid this$0;
        // 생성자 첫 인자로 바깥 인스턴스가 주입됨
        Cursor(Grid outer, int x, int y) { this$0 = outer; /* ... */ }

        public int read() {
            // cells[...] 는 사실 this$0.cells[...]
            return this$0.getCells()[/* ... */];
        }
    }
}
```

즉 "바깥을 안다"는 것에 특별한 비밀은 없다. 이너 클래스는 바깥 인스턴스를 **필드에 저장해** 두고 있을 뿐이며, 바깥 멤버에 대한 접근은 모두 `this$0.멤버`를 거친다.

이 사실을 알면 두 가지가 분명해진다. 첫째, 이너 인스턴스가 바깥 인스턴스보다 오래 살면 바깥 인스턴스도 계속 살아 있게 된다(누수, 8절). 둘째, 이너 인스턴스마다 참조 필드 하나만큼 메모리가 더 든다.

### 3.4 이너 클래스도 상속과 오버라이드에 참여한다

이너 클래스도 일반 클래스처럼 다른 클래스를 상속하거나 인터페이스를 구현할 수 있다. 바깥 상태에 접근하면서 동시에 어떤 계약을 이행하는 객체를 만들 때 유용하다.

```kotlin
class Playlist(private val songs: List<String>) {
    // 이너 클래스가 Iterator 인터페이스를 구현 — 바깥의 songs에 접근하면서
    inner class SongIterator : Iterator<String> {
        private var index = 0
        override fun hasNext() = index < songs.size
        override fun next() = songs[index++]
    }

    fun iterator() = SongIterator()
}

fun main() {
    val p = Playlist(listOf("아침", "저녁"))
    val it = p.iterator()
    while (it.hasNext()) print("${it.next()} ")  // => 아침 저녁
}
```

`SongIterator`는 `Iterator<String>` 계약을 이행하면서 바깥 `Playlist`의 `songs`를 읽는다. 바깥의 상태를 순회하거나 조작하는 보조 객체는 이너 클래스를 쓰기에 알맞은 전형적인 경우다. 다만 실무에서는 이런 반복자를 대부분 익명 객체나 `iterator {}` 빌더로 더 간결하게 작성한다(6절, [[40 - 시퀀스와 지연 평가]]).

## 4. 한정된 `this`와 레이블: 중첩 스코프에서 `this`는 누구인가

### 4.1 `this`의 모호성 문제

이너 클래스 안에서 `this`가 가리킬 수 있는 대상은 두 가지다. 이너 인스턴스 자신과, 그 인스턴스가 참조하는 바깥 인스턴스다. Kotlin은 기본적으로 `this`를 **가장 안쪽 스코프의 인스턴스**로 해석한다. 바깥 인스턴스를 명시적으로 가리키려면 **한정된 this(qualified this)** 인 `this@Outer`를 쓴다.

```kotlin
class Outer(val id: Int) {
    inner class Inner(val id: Int) {   // 같은 이름 id — 가림(shadowing)
        fun describe(): String {
            val innerThis = this          // Inner 인스턴스
            val outerThis = this@Outer    // Outer 인스턴스
            return "inner.id=${this.id}, outer.id=${this@Outer.id}"
        }
    }
}

fun main() {
    println(Outer(1).Inner(2).describe())  // => inner.id=2, outer.id=1
}
```

`this@Outer`의 `@Outer`는 "이름이 `Outer`인 가장 가까운 스코프의 `this`"를 선택한다. 이 문법이 없으면 안쪽 `id`가 바깥 `id`를 완전히 가려서 바깥 값에 접근할 방법이 없다.

### 4.2 레이블로서의 `this@Label`: 하나의 규칙

`this@Outer`의 `@Outer`는 사실 **레이블(label)** 이다. Kotlin에는 여러 종류의 암시적 `this`가 있고, 모두 같은 레이블 문법으로 구별한다.

- 클래스/이너 클래스: 클래스 이름이 레이블이다. `this@Outer`, `this@Inner`.
- 수신 객체 지정 람다: 함수 이름이 레이블이다. `this@apply`, `this@run` 등(16장 스코프 함수).
- 확장 함수: 확장 함수 이름이 레이블이다.

```kotlin
class Robot(val name: String) {
    inner class Arm(val side: String) {
        fun greet(): String = buildString {
            // buildString의 수신자는 StringBuilder — this@buildString
            append("팔(")
            append(this@Arm.side)        // Arm 인스턴스
            append(") of ")
            append(this@Robot.name)      // Robot 인스턴스
        }
    }
}

fun main() {
    println(Robot("R2").Arm("왼쪽").greet())  // => 팔(왼쪽) of R2
}
```

이 예제에는 `this`가 될 수 있는 후보가 세 개나 겹쳐 있다. `buildString` 람다의 `StringBuilder`(암시적 수신자), `Arm` 인스턴스, `Robot` 인스턴스다. `append(...)`는 가장 안쪽인 `StringBuilder`의 메서드이고, 바깥의 두 인스턴스는 `this@Arm`과 `this@Robot`으로 정확히 지정한다. 중첩과 수신 객체가 많이 겹칠수록 이 한정 문법이 더 유용해진다.

> [!note] 명세 기준
> 한정되지 않은 `this`는 "가장 가까운 둘러싼 스코프"의 `this`로 해석된다. `this@Label`은 레이블과 일치하는 가장 안쪽 스코프를 선택한다. 이 규칙은 이너 클래스, 수신 객체 지정 람다, 확장 함수에 똑같이 적용되는 하나의 메커니즘이다.

### 4.3 `super@Outer`: 상속 계층까지 겹칠 때

`this`뿐 아니라 `super`도 한정할 수 있다. 이너 클래스와 바깥 클래스가 각각 슈퍼클래스를 가질 때, 이너 클래스 안에서 바깥 클래스의 슈퍼 구현을 호출하려면 `super@Outer`를 쓴다. 실무에서 쓸 일은 드물지만, 여러 스코프가 겹친 상황에서 `super`의 대상을 명확히 정하는 유일한 방법이다.

```kotlin
open class Vehicle {
    open fun sound() = "..."
}

class Car : Vehicle() {
    override fun sound() = "부릉"

    inner class Horn {
        // Car의 sound가 아니라 Vehicle의 원래 sound를 부르고 싶다
        fun test() = super@Car.sound()   // Vehicle.sound() 호출
    }
}

fun main() {
    println(Car().Horn().test())  // => ...
}
```

### 4.4 확장 함수의 수신자와 이너 클래스가 겹칠 때

확장 함수([[35 - 확장 함수와 프로퍼티]])를 이너 클래스 안에서 정의하거나 호출하면 수신자가 겹칠 수 있다. 이때도 레이블 규칙으로 어느 수신자를 쓸지 정한다. 핵심은 모든 경우가 하나의 원칙으로 설명된다는 점이다. 암시적 수신자가 여러 개일 때 이름 없는 접근은 항상 가장 안쪽 수신자를 선택하고, 바깥 수신자는 레이블로 지정한다.

## 5. 지역 클래스: 함수 본문 안의 타입

### 5.1 함수 안에서 클래스를 선언한다

클래스는 최상위나 클래스 본문뿐 아니라 **함수의 본문 안**에도 선언할 수 있다. 이런 클래스를 지역 클래스(local class)라고 한다. 지역 클래스는 그 함수 안에서만 보이며, 함수가 반환되면 이름은 사라진다(인스턴스는 참조가 남아 있으면 계속 살아 있다).

```kotlin
fun analyze(numbers: List<Int>): String {
    // 오직 이 함수 안에서만 쓰이는 보조 타입
    class Stats {
        var sum = 0L
        var count = 0
        fun add(n: Int) { sum += n; count++ }
        fun mean() = if (count == 0) 0.0 else sum.toDouble() / count
    }

    val stats = Stats()
    for (n in numbers) stats.add(n)
    return "평균=${stats.mean()}, 개수=${stats.count}"
}

fun main() {
    println(analyze(listOf(10, 20, 30)))  // => 평균=20.0, 개수=3
}
```

`Stats`는 `analyze` 밖에서는 존재하지 않는다. 함수 내부 로직을 구조화하면서도 그 구조를 외부에 전혀 드러내지 않으므로, 가장 강한 형태의 캡슐화다.

### 5.2 지역 클래스는 바깥 지역 변수를 캡처한다

지역 클래스의 중요한 능력은 **자신을 둘러싼 함수의 지역 변수를 캡처(capture)할 수 있다**는 점이다. 캡처의 원리는 클로저와 같으며, 자세한 내용은 14장(클로저와 캡처)에서 설명했다. 여기서 강조할 점은 Kotlin이 **값이 아니라 변수를 캡처한다**는 것, 그래서 `var`도 캡처하고 수정까지 할 수 있다는 것이다. Java의 지역 클래스는 `final`이거나 effectively final인 변수만 캡처하므로 큰 차이가 있다.

```kotlin
fun makeCounter(start: Int): () -> Int {
    var current = start          // 지역 var

    class Counter {
        fun next(): Int {
            val result = current
            current++            // 캡처한 var를 수정
            return result
        }
    }

    val c = Counter()
    return { c.next() }
}

fun main() {
    val counter = makeCounter(10)
    println(counter())  // => 10
    println(counter())  // => 11
    println(counter())  // => 12
}
```

`Counter`는 `makeCounter`의 지역 변수 `current`를 캡처하고, `next()`를 호출할 때마다 그 변수를 증가시킨다. `makeCounter`가 이미 반환된 뒤에도 `current`는 계속 살아 있다. `Counter` 인스턴스가 그 변수를 캡처하고 있기 때문이다.

> [!note] 명세 기준 / JVM 백엔드
> JVM 백엔드에서 캡처된 `val`은 값이 지역 클래스의 합성 필드에 복사되지만, 캡처된 `var`는 원소 하나짜리 배열이나 `Ref` 객체(예: `kotlin.jvm.internal.Ref.IntRef`)로 감싸져 그 **참조**가 공유된다. 그래야 바깥 함수와 지역 클래스가 같은 변수를 보고 함께 수정할 수 있다. `Ref`로 감싸는 방식은 14장에서 자세히 다룬다. 여기서 중요한 것은 지역 클래스도 람다와 똑같이 캡처한다는 사실이다.

### 5.3 지역 클래스와 `inner`, 그리고 바깥 클래스 인스턴스

지역 클래스가 어떤 클래스의 메서드 안에 있고, 그 바깥 클래스의 인스턴스 멤버에 접근하려면 어떻게 될까? 메서드 안의 지역 클래스는 **바깥 클래스 인스턴스에도 암시적으로 접근**할 수 있다. 메서드에는 `this`가 있으므로 지역 클래스가 그 `this`를 캡처하기 때문이다. 이때 지역 클래스는 사실상 이너 클래스처럼 동작한다.

```kotlin
class Meter(private var reading: Int) {
    fun makeRecorder(): () -> Unit {
        // 메서드 안의 지역 클래스는 바깥 Meter 인스턴스도 캡처한다
        class Recorder {
            fun tick() { reading++ }   // 바깥 Meter의 private reading에 접근·수정
        }
        val r = Recorder()
        return { r.tick() }
    }
    fun current() = reading
}

fun main() {
    val m = Meter(0)
    val rec = m.makeRecorder()
    rec(); rec(); rec()
    println(m.current())  // => 3
}
```

`Recorder`에는 `inner`를 쓰지 않았지만, `makeRecorder`가 `Meter`의 메서드이므로 그 `this`(즉 `m`)를 캡처해 `reading`을 변경한다. 지역 클래스는 지역 변수든 바깥 클래스 인스턴스든, 자신을 둘러싼 *모든* 스코프를 캡처할 수 있다. 이렇게 제약이 적기 때문에 지역 클래스도 누수의 원인이 될 수 있다(8절).

### 5.4 언제 지역 클래스를 쓰는가

지역 클래스는 "함수 하나 안에서만 의미가 있고 상태를 가진 보조 개념"에 적합하다. 다만 상태가 단순하고 인터페이스 하나만 구현하면 되는 경우에는 다음 절의 익명 객체나 람다가 더 간결하다. 지역 클래스가 특히 유용한 경우는 다음과 같다.

- 이름이 있어야 코드를 읽기 쉬운 경우
- 인스턴스를 여러 번 만들어야 하는 경우
- 여러 메서드와 여러 필드를 가진 복잡한 보조 타입인 경우

## 6. 익명 객체: 이름 없는 일회용 인스턴스

### 6.1 객체 표현식(object expression)의 문법

지금까지는 이름이 있는 중첩·이너·지역 클래스를 살펴봤다. Kotlin은 이름을 짓지 않고 **그 자리에서 인스턴스를 하나 만드는** 문법도 제공한다. 이 문법을 객체 표현식(object expression)이라 하고, 그 결과를 익명 객체(anonymous object)라고 부른다.

```kotlin
val comparator = object : Comparator<Int> {
    override fun compare(a: Int, b: Int): Int = b - a  // 내림차순
}

fun main() {
    val list = mutableListOf(3, 1, 2)
    list.sortWith(comparator)
    println(list)  // => [3, 2, 1]
}
```

`object : Comparator<Int> { ... }`는 "`Comparator<Int>`를 구현하는 이름 없는 클래스를 만들고, 곧바로 그 인스턴스를 하나 생성하라"는 표현식이다. 클래스 선언과 인스턴스 생성이 하나의 표현식으로 합쳐진 것이다.

이 표현식은 `object` 선언(28장 object와 companion)과 키워드는 같지만 근본적으로 다르다. 선언은 이름 붙은 싱글턴이고, 표현식은 평가될 때마다 새 인스턴스를 만드는 값이다(6.5에서 비교한다).

### 6.2 슈퍼타입이 없거나, 하나이거나, 여럿인 경우

객체 표현식에는 슈퍼타입을 0개, 1개, 또는 여러 개 지정할 수 있다.

```kotlin
// (1) 슈퍼타입 없이 — 즉석에서 프로퍼티/메서드 묶음을 만든다
val point = object {
    val x = 3
    val y = 4
    fun distanceFromOrigin() = Math.hypot(x.toDouble(), y.toDouble())
}
println(point.distanceFromOrigin())  // => 5.0

// (2) 하나의 슈퍼타입 구현
val runnable = object : Runnable {
    override fun run() = println("실행")
}

// (3) 여러 슈퍼타입을 동시에 — 클래스 하나 + 인터페이스 여럿
open class Animal { open fun sound() = "..." }
interface Named { val name: String }

val cat = object : Animal(), Named {
    override val name = "고양이"
    override fun sound() = "야옹"
}
println("${cat.name}: ${cat.sound()}")  // => 고양이: 야옹
```

특히 (3)을 눈여겨볼 만하다. 이름 있는 클래스로 "클래스 하나를 상속하고 인터페이스 여러 개를 구현"하려면 새 클래스를 선언해야 한다. 반면 익명 객체는 그 자리에서 여러 타입을 한 번에 조합한다. 일회성 어댑터를 만들 때 이보다 간결한 방법은 없다.

> [!info] 역사 메모
> 슈퍼타입 없는 `object { ... }`(예제의 (1))는 Java에는 없는 기능이다. Java의 익명 클래스는 반드시 하나의 슈퍼타입(클래스나 인터페이스)을 상속하거나 구현해야 한다. Kotlin은 "프로퍼티 몇 개를 묶은 즉석 값"을 만드는 것까지 허용해서, 지역적으로만 쓰는 임시 데이터 묶음을 가볍게 표현할 수 있게 했다.

### 6.3 익명 객체도 캡처한다

객체 표현식도 자신을 둘러싼 스코프의 변수와 인스턴스를 캡처한다. 지역 클래스나 람다와 완전히 같은 원리다(14장 클로저와 캡처).

```kotlin
fun counterFrom(start: Int): Iterator<Int> {
    var value = start
    // 익명 객체가 지역 var value를 캡처하고 수정한다
    return object : Iterator<Int> {
        override fun hasNext() = true          // 무한
        override fun next(): Int = value++
    }
}

fun main() {
    val it = counterFrom(100)
    println(it.next())  // => 100
    println(it.next())  // => 101
}
```

여기서 익명 `Iterator`는 `value`를 캡처하고 `next()`를 호출할 때마다 증가시킨다. Java의 익명 클래스는 `final` 지역 변수만 캡처할 수 있고 수정할 수도 없었다. 반면 Kotlin의 익명 객체는 `var`를 캡처해 자유롭게 수정한다. 이 차이 덕분에 상태를 가진 반복자나 콜백을 훨씬 자연스럽게 작성할 수 있다.

### 6.4 익명 객체의 타입이 보이는 경우와 축소되는 경우

이 부분이 객체 표현식에서 가장 미묘한 규칙이고, 많은 사람이 자주 헷갈리는 지점이다. 익명 객체에는 이름이 없는데, 슈퍼타입 없이 `object { val x = 5 }`를 만들면 그 `x`에는 어떻게 접근할까? 답은 **선언 위치의 가시성**에 따라 달라진다.

- **지역 변수**나 **`private` 멤버**(private 함수의 반환값, private 프로퍼티)에 담기면, 익명 객체의 *실제 타입*(모든 멤버 포함)이 그대로 드러난다. 그래서 그 고유 멤버에 접근할 수 있다.
- 그러나 `public`·`internal`·`protected` 함수의 반환 타입이나 프로퍼티 타입으로 밖에 드러나면, 컴파일러는 그 타입을 익명 객체가 상속한 **슈퍼타입**(없으면 `Any`)으로 축소한다. 그러면 고유 멤버는 보이지 않는다.

```kotlin
class Factory {
    // (A) private 함수: 익명 타입이 그대로 노출 → count 접근 가능
    private fun makeCounter() = object {
        var count = 0
        fun inc() { count++ }
    }

    fun demo() {
        val c = makeCounter()
        c.inc()
        println(c.count)   // => 1   (private 함수라 익명 타입이 보인다)
    }

    // (B) public 함수: 반환 타입이 Any로 축소 → 고유 멤버 안 보임
    fun makeCounterPublic() = object {
        var count = 0
    }
}

fun main() {
    val f = Factory()
    f.demo()
    val obj = f.makeCounterPublic()
    // println(obj.count)   // 컴파일 에러: Any에는 count가 없다
    println(obj)            // Any로만 보이므로 toString 정도만 가능
}
```

그리고 **지역 변수**에 담을 때는 언제나 익명 타입이 보인다.

```kotlin
fun main() {
    val anon = object {          // 지역 변수 → 익명 타입 노출
        val label = "임시"
        fun greet() = "안녕, $label"
    }
    println(anon.greet())         // => 안녕, 임시
}
```

> [!note] 명세 기준
> 익명 객체의 타입(고유 멤버까지 포함하는 타입)은 **지역 선언과 `private` 선언**에서만 그 선언의 타입이 될 수 있다. `public`/`protected`/`internal`로 노출되는 함수의 반환 타입이나 프로퍼티 타입은, 그 익명 객체가 명시적으로 상속하거나 구현한 슈퍼타입이 된다(선언된 슈퍼타입이 둘 이상이면 컴파일러가 하나를 고를 수 없으므로 선언에 타입을 명시해야 한다). 슈퍼타입을 하나도 붙이지 않았다면 `Any`가 된다.
>
> 이유는 분명하다. 이름 없는 타입을 모듈 경계 너머로 노출할 방법이 없기 때문이다. 이름이 없으니 다른 모듈에서는 그 타입을 적을 수 없다.

이 규칙 때문에 실무에서 "왜 내 익명 객체의 프로퍼티가 안 보이지?" 하고 당황하는 일이 생긴다. 해결 방법은 다음 세 가지다.

- 익명 객체를 private 선언이나 지역 변수에 둔다.
- 명시적인 인터페이스를 슈퍼타입으로 붙이고, 그 인터페이스의 멤버로 접근한다.
- 아예 이름 있는 클래스로 바꾼다.

### 6.5 객체 표현식과 객체 선언: 같은 키워드, 다른 의미

`object` 키워드는 두 곳에서 쓰이지만 의미는 거의 정반대다. 두 가지의 비교는 28장에서 자세히 다루지만, 익명 객체를 이해하려면 여기서도 분명히 짚어 둘 필요가 있다.

| 관점 | 객체 **선언** `object Foo { }` | 객체 **표현식** `object : T { }` |
|------|-------------------------------|--------------------------------|
| 이름 | 있음 (`Foo`) | 없음 (익명) |
| 인스턴스 수 | 하나 (싱글턴) | 평가될 때마다 새로 생성 |
| 초기화 시점 | 최초 접근 시 지연·스레드 안전 | 표현식이 평가될 때마다 |
| 값인가 선언인가 | 선언(문) | 값(표현식), 변수에 담긴다 |
| 캡처 | (최상위면) 캡처 없음 | 둘러싼 스코프 캡처 |
| 용도 | 전역 싱글턴, 상수 묶음 | 일회용 어댑터·콜백·리스너 |

가장 중요한 차이는 **인스턴스 수**다. 객체 선언은 프로그램 전체에서 딱 하나뿐이다(`object`는 정적 클래스가 아니라 실제 인스턴스다). 반면 객체 표현식은 그 표현식이 실행될 때마다 새 인스턴스를 만든다. 루프 안에 객체 표현식을 두면 반복할 때마다 새 객체가 만들어진다.

```kotlin
object Logger {            // 선언: 프로그램 전체에서 단 하나
    fun log(msg: String) = println("[LOG] $msg")
}

fun listeners(): List<Runnable> = List(3) {
    // 표현식: 세 번 평가 → 세 개의 서로 다른 익명 객체
    object : Runnable {
        override fun run() = println("리스너")
    }
}

fun main() {
    val ls = listeners()
    println(ls[0] === ls[1])  // => false  (서로 다른 인스턴스)
    println(Logger === Logger) // => true   (선언은 언제나 같은 인스턴스)
}
```

> [!warning] 흔한 오해
> "익명 객체도 `object` 키워드를 쓰니 싱글턴일 것이다"라는 생각은 틀리다. 표현식으로 쓴 `object`는 평가될 때마다 새 인스턴스를 만든다. 싱글턴은 이름 붙은 `object` **선언**뿐이다. 둘을 혼동하면 루프에서 익명 객체를 만들면서 "왜 매번 새로 생기지?" 하고 당황하거나, 반대로 상태를 공유하려고 익명 객체를 썼다가 문제를 겪는다.

## 7. 익명 객체, 람다, SAM 변환: 무엇을 언제 쓰는가

### 7.1 함수형 인터페이스라면 람다로 대체할 수 있다

객체 표현식으로 인터페이스 하나를 구현하면 코드가 장황해지기 쉽다. 그 인터페이스가 **추상 메서드가 하나뿐인 인터페이스**(Single Abstract Method, SAM)라면 익명 객체 대신 람다를 쓸 수 있다. 이것을 SAM 변환(SAM conversion)이라고 한다. SAM 변환은 13장(함수 타입과 람다)과 [[25 - 인터페이스]]에서 자세히 다루지만, 익명 객체와 비교하는 관점에서 여기서 정리한다.

```kotlin
// (A) 익명 객체 — 장황하지만 언제나 통한다
val r1 = object : Runnable {
    override fun run() = println("A")
}

// (B) SAM 변환 — Runnable은 Java의 함수형 인터페이스라 람다로 축약
val r2 = Runnable { println("B") }
```

SAM 변환은 대상 인터페이스가 다음 중 하나일 때 가능하다.

1. **Java에서 선언된** 함수형 인터페이스
2. Kotlin에서 `fun interface`로 명시한 함수형 인터페이스

Kotlin의 일반 인터페이스는 메서드가 하나뿐이더라도 람다로 직접 변환되지 *않는다*. 이 비대칭 때문에 초보자가 자주 당황한다.

```kotlin
// Kotlin의 일반 인터페이스 (fun interface 아님)
interface Handler {
    fun handle(x: Int)
}

// val h = Handler { println(it) }   // 컴파일 에러: 일반 인터페이스는 SAM 변환 안 됨
val h = object : Handler {           // 익명 객체로는 언제나 가능
    override fun handle(x: Int) = println(x)
}

// fun interface로 선언했다면 람다 가능
fun interface Handler2 {
    fun handle(x: Int)
}
val h2 = Handler2 { println(it) }    // OK: fun interface라 SAM 변환
```

> [!note] 명세 기준
> `fun interface`(functional interface)는 추상 멤버 함수가 정확히 하나인 인터페이스에만 붙일 수 있고, 이때 람다로부터의 SAM 변환이 가능해진다. 프로퍼티나 두 번째 추상 함수가 있으면 `fun interface`로 선언할 수 없다. Java 인터페이스는 함수형이기만 하면 별도 표시 없이도 SAM 변환된다. Kotlin이 Java 상호운용을 위해 특별히 처리하는 부분이다([[45 - Java 상호운용]]).

### 7.2 언제 익명 객체를 써야 하는가

람다가 더 간결하지만, 다음 경우에는 익명 객체를 써야 한다.

- **추상 멤버가 둘 이상**일 때(예: `addListener`가 여러 콜백을 요구하는 경우). 람다는 함수 하나만 표현하므로 쓸 수 없다.
- **상태(프로퍼티)를 가진 구현**이 필요할 때. 익명 객체는 자기 필드를 가질 수 있다.
- **여러 슈퍼타입**을 동시에 구현하거나 상속할 때(6.2의 (3)).
- **슈퍼타입 없는** 즉석 값 묶음이 필요할 때(6.2의 (1)).

```kotlin
interface MouseListener {
    fun onClick()
    fun onDoubleClick()   // 추상 멤버 둘 → 람다 불가, 익명 객체 필요
}

val listener = object : MouseListener {
    private var clicks = 0                  // 자기 상태
    override fun onClick() { clicks++; println("click #$clicks") }
    override fun onDoubleClick() { println("double") }
}
```

### 7.3 인스턴스 생성 비용: 캐싱의 미묘한 차이

> [!caution] 성능 주의
> 객체 표현식은 평가될 때마다 새 인스턴스를 만든다. 반면 **아무것도 캡처하지 않는** 람다는 구현과 백엔드에 따라 컴파일러나 런타임이 싱글턴으로 캐싱할 수 있어서, 매번 새 객체를 만들지 않을 수 있다. 예를 들어 아무 변수도 캡처하지 않는 람다를 넘기는 코드는 반복 호출해도 같은 인스턴스를 재사용할 수 있다. 그러나 익명 객체는 이 최적화 대상이 아니므로 평가할 때마다 반드시 새로 생긴다.
>
> 자주 실행되는 경로(hot path)에서 캡처 없는 콜백을 만든다면 할당 측면에서 람다가 유리할 수 있다. 다만 이는 백엔드 최적화이므로 "항상 그렇다"고 단정하지 말고, 실제 병목이 확인될 때만 신경 쓰는 편이 옳다. 대부분의 코드에서는 이 차이가 의미 없다.

이 절의 원칙을 정리하면 이렇다. "인터페이스 하나이고 상태가 없으면" 가능한 한 람다를 쓰고, "추상 멤버가 둘 이상이거나, 상태가 있거나, 여러 타입을 구현해야 하면" 익명 객체를 쓴다. 표현력이 부족한 도구에 억지로 맞추지 말고, 필요한 만큼의 최소 도구를 고른다.

## 8. 메모리와 누수: 바깥 객체로 이어지는 참조 끊기

### 8.1 `inner`·익명 객체·지역 클래스가 만드는 강한 참조

지금까지 살펴본 내용을 메모리 관점에서 다시 보면 하나의 위험한 패턴이 보인다. `inner` 클래스, 익명 객체, 지역 클래스는 모두 **바깥 인스턴스(또는 캡처한 지역 변수)에 대한 강한 참조(strong reference)** 를 갖는다.

이 참조 때문에, 보조 객체가 오래 유지되는 컬렉션이나 콜백 목록에 등록되면 더 이상 필요 없는 바깥 객체까지 함께 살아남아 가비지 컬렉션되지 못한다. 이것이 전형적인 메모리 누수(memory leak)다.

```text
누수 사슬:

  [오래 사는 이벤트 버스]
        │ 강한 참조
        ▼
  [익명 리스너 객체]  ── 캡처 ──▶  [바깥의 무거운 객체]
                                        (이제 필요 없는데도 살아남음)
```

핵심은 보조 객체가 얼마나 오래 살아 있느냐다. 그 수명이 바깥 객체에 의도한 수명보다 길면 누수가 된다.

### 8.2 구체적인 예: 콜백 등록의 함정

일반적인 상황으로 재현해 보자. 오래 유지되는 온도 센서 허브 객체에 리스너를 등록하는 경우다.

```kotlin
class SensorHub {
    private val listeners = mutableListOf<() -> Unit>()
    fun subscribe(listener: () -> Unit) { listeners.add(listener) }
    fun fire() { listeners.forEach { it() }
    }
}

class ReportScreen(private val hub: SensorHub) {
    private val hugeBuffer = IntArray(10_000_000)  // 무거운 상태

    fun activate() {
        // 익명 람다가 this(ReportScreen)를 캡처 → hub가 이 화면 전체를 붙잡는다
        hub.subscribe { println("갱신, buffer size=${hugeBuffer.size}") }
    }
    // 문제: 화면이 닫혀도 hub.listeners가 이 람다를, 람다가 hugeBuffer를 붙잡아
    //       ReportScreen과 1000만짜리 배열이 GC되지 못한다.
}
```

`activate`가 넘긴 람다는 `hugeBuffer`를, 따라서 `ReportScreen` 인스턴스를 캡처한다. `hub`가 그 람다를 목록에 계속 갖고 있는 한, 화면이 논리적으로 "닫혀도" 실제 메모리는 해제되지 않는다. 리스너가 `inner class`나 익명 객체였더라도 똑같은 참조 경로가 생긴다.

### 8.3 참조를 끊는 방법

이 누수를 막는 방법은 여러 가지이며, 각각 이 장에서 다룬 개념과 직접 연결된다.

**(1) `inner`를 중첩 클래스로 바꿔 처음부터 캡처하지 않는다.** 보조 객체가 바깥 상태를 실제로 필요로 하지 않는다면, `inner`를 빼서 바깥 참조 자체를 없앤다. 필요한 값만 생성자 인자로 명시적으로 넘긴다(2.1~2.2). 이렇게 하면 무엇을 캡처하는지가 코드에 드러나고, 무거운 객체를 실수로 캡처할 일도 없다.

```kotlin
class SensorHub2 {
    private val listeners = mutableListOf<Runnable>()
    fun subscribe(r: Runnable) { listeners.add(r) }
    fun unsubscribe(r: Runnable) { listeners.remove(r) }  // 해지 경로 필수
}

class ReportScreen2(private val hub: SensorHub2) {
    // nested: 바깥을 안 붙잡고, 필요한 최소 값만 받는다
    private class UpdateTask(private val label: String) : Runnable {
        override fun run() = println("갱신: $label")
    }
    private val task = UpdateTask("보고서")

    fun activate() = hub.subscribe(task)
    fun deactivate() = hub.unsubscribe(task)   // 명시적 해지
}
```

**(2) 등록한 것은 반드시 해지(unsubscribe)한다.** 참조를 아무리 잘 관리해도, 오래 유지되는 컬렉션에 넣은 것을 빼지 않으면 누수가 된다. 등록과 해지를 한 쌍으로 만들고, 리소스 수명에 맞춰 해지한다. 여기에는 `use`(AutoCloseable) 패턴이나 명시적인 생명주기 훅을 쓴다([[41 - 예외와 Nothing]]의 `use`).

**(3) 약한 참조(weak reference)를 쓴다.** 콜백을 강한 참조 대신 약한 참조로 보관하면, 바깥 객체를 다른 곳에서 더 이상 참조하지 않을 때 GC가 회수할 수 있다. 다만 약한 참조를 쓰면 콜백이 예상보다 일찍 사라질 수 있으므로 신중하게 써야 한다. 이 기법은 JVM이나 플랫폼별 GC 특성에 의존한다([[43 - 동시성과 메모리 모델]]).

> [!caution] 성능 주의 / JVM 백엔드
> `inner` 클래스의 바깥 참조는 눈에 보이지 않는 합성 필드라서 특히 잊기 쉽다. 코드에서 `this@Outer`를 한 번도 쓰지 않았더라도, `inner`로 선언한 이상 바깥 참조 필드는 존재하며 GC가 따라가는 참조 경로에 포함된다.
>
> "안 쓰니까 참조하지 않겠지"라는 가정은 틀리다. `inner` 키워드 자체가 참조를 만든다. 바깥을 정말 쓰지 않는다면 `inner`를 빼는 것이 확실한 유일한 해결책이다.

### 8.4 지역 클래스·익명 객체의 캡처도 같은 위험이 있다

지역 클래스와 익명 객체에는 `inner` 같은 명시적 키워드가 없지만, 둘러싼 스코프를 **캡처**하면 똑같이 강한 참조가 생긴다(5.3, 6.3). 특히 메서드 안에서 만든 익명 객체는 그 메서드의 `this`(바깥 클래스 인스턴스)까지 캡처하므로, `inner`와 사실상 같은 누수 위험이 있다.

캡처 여부는 익명 객체 안에서 바깥 지역 변수나 바깥 인스턴스 멤버를 참조하느냐로 결정된다. 아무것도 참조하지 않으면 캡처가 없으므로 위험도 없다.

정리하면, 이 장에서 다룬 `inner`, 지역 클래스, 익명 객체는 표현력을 얻는 대신 **바깥을 캡처하는 능력**을 갖는다. 이 능력은 유용하지만, "참조된 객체는 GC되지 않는다"는 원칙과 맞물려 누수를 만든다. 누수를 피하려면 먼저 이 보조 객체가 무엇을 캡처하고 얼마나 오래 살아 있는지를 늘 의식해야 한다.

### 9.1 결정 트리

지금까지 살펴본 선택지를 하나의 흐름으로 정리하면 다음과 같다.

```text
클래스를 어디에, 어떻게 둘 것인가?

바깥 클래스 상태에 접근해야 하나?
├─ 아니오 → 이름이 필요한가?
│           ├─ 예, 재사용/여러 인스턴스 → 중첩 클래스 (class)         [2절]
│           └─ 아니오, 일회용 →
│                   슈퍼타입이 함수형 하나 + 상태 없음?
│                   ├─ 예 (fun interface / Java SAM) → 람다           [7.1]
│                   └─ 아니오 (여럿/상태/여러 타입) → 익명 객체        [6절]
│
└─ 예, 바깥 인스턴스를 붙잡아야 함 →
            수명이 바깥보다 짧다고 보장되나?
            ├─ 예 → inner 클래스 또는 캡처하는 익명 객체              [3, 6절]
            └─ 아니오 (오래 산다) → 위험! nested + 명시적 인자 전달    [8.3]
                                      + 반드시 해지 경로 마련
```

### 9.2 컴파일 결과 한눈에 보기

> [!note] 명세 기준 / JVM 백엔드
> 아래 표는 JVM 백엔드에서 만들어지는 결과를 대략 정리한 것이다. 다른 백엔드는 표현 방식이 다르지만 소스 수준의 의미는 같다.

| 소스 구조 | JVM 산물(개념) | 바깥 참조 필드 | 새 인스턴스 시점 |
|-----------|----------------|----------------|------------------|
| 중첩 클래스 | `Outer$Nested` (정적 중첩) | 없음 | 생성자 호출마다 |
| 이너 클래스 | `Outer$Inner` + `this$0` | 있음 | `outer.Inner()`마다 |
| 지역 클래스 | `Outer$method$LocalName` | 캡처 시 있음 | 생성자 호출마다 |
| 익명 객체 | `Outer$method$1` 등 익명 | 캡처 시 있음 | 표현식 평가마다 |
| 객체 선언 | `Foo` (INSTANCE 싱글턴) | (최상위면) 없음 | 최초 접근 시 1회 |
| 캡처 없는 람다 | 합성 클래스/`INSTANCE` | 없음 | (캐싱 가능) |

### 9.3 선언 방식이 곧 설계다

선언의 위치와 종류는 단순한 문법 취향이 아니라 **설계 결정**이다. 중첩 클래스는 "이 타입은 저 타입에 속한 어휘"라는 소속 관계를 이름으로 표현한다. `inner`는 "이 객체는 저 객체 없이 존재할 수 없다"는 의존 관계를 구조로 표현한다. 지역 클래스와 익명 객체는 "여기서만, 잠깐 쓴다"는 수명을 스코프로 표현한다.

그리고 이 선택은 모두 곧바로 세 가지 질문의 답을 결정한다. 무엇을 볼 수 있는가(가시성), 무엇을 캡처하는가(캡처), 얼마나 오래 사는가(수명)이다. Kotlin이 `inner`를 기본값이 아니라 명시적인 선택으로 만든 것은, 개발자가 이 결정을 무심코 내리지 않고 의식적으로 내리게 하려는 것이다.
