**이 장이 답하는 질문:**

- 클래스 안에 클래스를 선언하면, Kotlin은 그것을 바깥 인스턴스에 묶는가 아닌가 — 그리고 왜 기본값이 Java와 정반대인가?
- `inner` 키워드 하나가 바이트코드에 정확히 무엇을 추가하는가? "바깥을 등에 업는다"는 말은 메모리에서 무슨 뜻인가?
- 중첩 클래스는 바깥 클래스의 `private` 멤버에 접근할 수 있는가, 없는가 — 접근에 인스턴스가 필요한가?
- `this@Outer`는 어디서 태어나며, 중첩 스코프에서 `this`가 가리키는 대상은 어떻게 결정되는가?
- 함수 몸통 안에 선언한 지역 클래스는 바깥 지역 변수를 어떻게 붙잡는가 — 값인가 참조인가?
- `object { ... }` 표현식이 만드는 익명 객체의 "타입"은 왜 어떤 곳에서는 보이고 어떤 곳에서는 `Any`로 뭉개지는가?
- 익명 객체와 람다는 언제 갈아탈 수 있고 언제 갈아탈 수 없는가 — SAM 변환의 경계는?
- `inner` 클래스와 익명 객체는 어떻게 메모리 누수의 온상이 되는가, 그리고 어떻게 그 사슬을 끊는가?

앞선 [[21 - 클래스와 생성자]]에서 우리는 하나의 클래스가 어떻게 태어나는지 — 주 생성자, `init` 블록, 프로퍼티 초기화의 순서 — 를 기계 수준에서 뜯어봤다. [[27 - 데이터 클래스]]와 [[30 - sealed 클래스와 대수적 데이터 타입]]은 클래스를 "값을 담는 형태"로 특수화하는 방법을 보여 줬고, [[28 - object와 companion - 싱글턴과 동반 객체]]는 클래스 없이도 인스턴스를 이름 붙여 딱 하나 만드는 `object` 선언을 다뤘다. 이 장은 그 모든 이야기를 "클래스가 다른 클래스나 함수의 *몸통 안*에 놓일 때"라는 한 축으로 다시 조명한다. 선언의 위치가 바뀌면 스코프가 바뀌고, 스코프가 바뀌면 그 타입이 무엇을 볼 수 있는지, 무엇을 붙잡는지, 언제 사라지는지가 통째로 달라지기 때문이다.

이 장이 다루는 것과 다루지 않는 것의 경계를 먼저 못박자. 클래스·인터페이스·`object`·`enum`을 다른 선언의 *몸통 안에 중첩*하는 문법과 의미론 — 바깥 참조의 유무(`inner`), 한정된 `this`(`this@Outer`), 지역 클래스의 변수 캡처, 그리고 이름 없는 일회용 인스턴스를 만드는 **객체 표현식(object expression)** — 이 이 장의 심장이다. 반면 이름을 가진 싱글턴 `object`와 `companion object`의 전모는 [[28 - object와 companion - 싱글턴과 동반 객체]]가 소유하며, 여기서는 그 사촌인 *익명* 객체와 대조하는 선에서만 건드린다. 변수 캡처의 근본 원리 — Kotlin이 값이 아니라 변수를 붙잡는다는 사실, `var`가 `Ref`로 감싸지는 방식 — 는 [[14 - 클로저와 캡처]]가 정본으로 소유하고, 여기서는 그 원리가 지역 클래스·익명 객체에 어떻게 재현되는지만 본다. 람다의 문법과 함수 참조는 [[13 - 함수 타입과 람다와 함수 참조]]가, 수신 객체 지정 람다의 `this`는 [[16 - 스코프 함수와 수신 객체 관용구]]가 소유한다.

논증의 궤적은 이렇다. 먼저 "왜 클래스를 다른 클래스 안에 두는가"라는 동기에서 출발해, Kotlin이 Java와 정반대로 **기본을 정적 중첩(외부 참조 없음)** 으로 잡은 설계 결정을 정면으로 마주한다(이것이 이 장의 중심 오해 교정이다 — Java 습관으로 "중첩은 자동으로 바깥에 접근한다"고 믿는 사람이 매우 많다). 그다음 `inner`가 붙는 순간 컴파일러가 몰래 추가하는 합성 필드와 생성자 인자를 바이트코드 수준에서 드러내고, `this@Label`의 정체를 밝힌다. 이어 함수 몸통 속 지역 클래스의 캡처, 이름 없는 익명 객체의 표현식 문법과 그 "노출되는 타입" 규칙, 익명 객체와 람다/SAM의 갈림길을 차례로 판 뒤, 마지막으로 이 모든 구조가 어떻게 바깥 객체를 붙잡아 메모리 누수를 만드는지 — 그리고 그 사슬을 어떻게 끊는지 — 로 마무리한다.

## 1. 왜 클래스 안에 클래스를 두는가 — 중첩의 동기와 두 갈래

### 1.1 문제: 개념적으로 종속된 타입의 자리

프로그램을 짜다 보면 "어떤 타입은 다른 타입 안에서만 의미가 있다"는 상황을 끊임없이 만난다. 이진 트리의 `Node`는 `Tree` 밖에서 홀로 떠다닐 이유가 없고, 상태 기계의 `State`는 그 기계에 소속된 개념이며, 파서의 `Token`은 파서의 어휘다. 이런 타입을 최상위(top-level)에 그냥 풀어놓으면 이름공간이 오염되고, 어떤 타입이 어떤 타입에 종속되는지가 코드에서 사라진다.

Kotlin은 이 "개념적 종속"을 문법으로 표현하도록 **선언의 중첩(nesting)** 을 허용한다. 클래스·인터페이스·`object`·`enum`·데이터 클래스·봉인 클래스 — 사실상 모든 타입 선언을 다른 클래스의 몸통 안에 넣을 수 있다.

```kotlin
class Tree {
    // Node는 Tree의 내부 어휘. 밖에서는 Tree.Node로만 부른다.
    class Node(val value: Int, var left: Node? = null, var right: Node? = null)

    private var root: Node? = null

    fun insert(value: Int) { /* ... */ }
}

fun main() {
    val n = Tree.Node(42)   // 바깥에서 접근 시 Tree. 을 앞에 붙인다
    println(n.value)         // => 42
}
```

여기서 `Node`는 `Tree`라는 이름공간 안에 산다. `Tree.Node`라는 완전 이름(qualified name)이 곧 "이 노드는 트리의 것"이라는 문서다. 이름공간·캡슐화·응집(cohesion) — 이것이 중첩의 첫째 동기다.

### 1.2 결정적 갈림길: 바깥 인스턴스를 아는가 모르는가

그런데 "클래스 안의 클래스"에는 근본적으로 다른 두 종류가 있다. 이 구분이 이 장 전체를 가르는 축이다.

1. **중첩 클래스(nested class)** — 바깥 클래스의 *이름공간*에만 속한다. 바깥 클래스의 특정 **인스턴스**와는 아무 관계가 없다. `Tree.Node`를 만들 때 어떤 `Tree` 객체도 필요하지 않다. 위 예제가 정확히 이것이다.

2. **이너 클래스(inner class)** — `inner` 키워드를 붙이면, 이 클래스의 모든 인스턴스는 자신을 만들어 낸 바깥 클래스의 **특정 인스턴스**를 등에 업는다. 그 바깥 인스턴스의 프로퍼티·메서드를 마치 자기 것처럼 쓸 수 있다.

```kotlin
class Outer {
    private val name = "바깥"

    class Nested {
        // fun show() = name  // 컴파일 에러: 바깥 인스턴스가 없어 name에 닿지 못함
        fun show() = "중첩 클래스는 바깥 인스턴스를 모른다"
    }

    inner class Inner {
        fun show() = "이너는 바깥의 name을 안다: $name"  // OK
    }
}

fun main() {
    println(Outer.Nested().show())      // 바깥 인스턴스 없이 생성
    println(Outer().Inner().show())     // 바깥 인스턴스가 있어야 생성: Outer() 먼저
}
// => 중첩 클래스는 바깥 인스턴스를 모른다
// => 이너는 바깥의 name을 안다: 바깥
```

두 줄의 `main`을 자세히 보라. `Outer.Nested()`는 `Outer`의 인스턴스 없이 곧장 만들어진다. 반면 `Outer().Inner()`는 먼저 `Outer()`로 바깥 인스턴스를 만든 다음, *그 인스턴스에 대고* `.Inner()`를 호출한다. 이 생성 문법의 차이가 두 종류의 본질을 그대로 드러낸다 — 이너는 반드시 "부모 인스턴스"가 있어야 태어난다.

### 1.3 Java 습관을 뒤집는 기본값 — 이 장의 중심 교정

여기서 초심자가 거의 예외 없이 걸려 넘어지는 함정이 있다. **Java에서는 정반대다.** Java의 중첩 클래스는 `static`을 붙이지 *않으면* 자동으로 "이너 클래스"가 되어 바깥 인스턴스를 붙잡는다. 즉 Java 개발자는 "중첩 = 자동으로 바깥에 접근"이라는 직관을 갖고 있다.

Kotlin은 이 기본값을 뒤집었다. Kotlin에서 아무 수식어 없는 중첩 클래스는 **바깥 참조가 없는(Java의 `static` 중첩에 해당)** 것이 기본이고, 바깥을 붙잡고 싶으면 `inner`를 *명시적으로* 붙여야 한다.

```java
// Java
class Outer {
    class Inner {}          // 암시적으로 바깥 인스턴스를 붙잡음 (실수의 온상)
    static class Nested {}  // 명시적으로 static을 붙여야 독립적
}
```

```kotlin
// Kotlin — 기본값이 뒤집혔다
class Outer {
    class Nested {}         // 기본: 바깥 참조 없음 (Java의 static에 해당)
    inner class Inner {}    // 명시적 inner를 붙여야 바깥 인스턴스를 붙잡음
}
```

이 뒤집기는 우연이 아니다. Java의 암시적 이너 클래스는 오랫동안 **의도치 않은 메모리 누수**의 대표적 원인이었다(8절에서 자세히 본다). 개발자가 `static`을 붙이는 것을 잊으면, 별생각 없이 선언한 중첩 클래스가 바깥 객체 전체를 살려 두는 사슬이 된다. Kotlin은 "위험한 쪽(바깥을 붙잡는 쪽)을 반드시 손으로 선언하게" 만들어, 실수의 방향을 안전한 쪽으로 기울였다. 이는 Kotlin 설계 철학 전반에 흐르는 "안전한 기본값(safe by default)"의 한 사례다 — `final`이 기본이고 `open`을 명시하는 것([[24 - 상속과 오버라이딩과 초기화 순서]]), 널 불가가 기본이고 `?`를 명시하는 것([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]])과 같은 결.

> **흔한 오해**: "중첩 클래스는 당연히 바깥 필드를 읽을 수 있지." — Java 습관에서 온 이 직관은 Kotlin에서 틀리다. `inner` 없는 중첩 클래스는 바깥 *인스턴스*를 아예 참조하지 못한다. 컴파일러가 "unresolved reference"로 즉시 막는다. 접근하려면 `inner`를 붙이거나, 바깥 인스턴스를 생성자 인자로 직접 넘겨야 한다.

### 1.4 두 갈래를 한 장에 정리

| 관점 | 중첩 클래스 (`class`) | 이너 클래스 (`inner class`) |
|------|----------------------|----------------------------|
| 바깥 인스턴스 참조 | 없음 | 있음 (합성 필드로 저장) |
| 생성 문법 | `Outer.Nested()` | `Outer().Inner()` (인스턴스 필요) |
| 바깥 인스턴스 멤버 접근 | 불가 (인스턴스 없음) | 가능 (`this@Outer` 암시) |
| 바깥의 `companion`/정적 멤버 | 접근 가능 | 접근 가능 |
| JVM 컴파일 형태 | 정적 중첩 클래스 | 합성 필드 `this$0` 보유 |
| Java 대응 | `static` 중첩 클래스 | (기본) 이너 클래스 |
| 메모리 수명 | 바깥과 독립 | 바깥 인스턴스를 살려 둠 |
| 기본값 여부 | **기본** | 명시적 `inner` 필요 |

이 표의 각 행을 이제 하나씩, "왜 그런가 / 바이트코드에서 무슨 일이 / 어디서 틀리는가"까지 파고든다.

## 2. 중첩 클래스 — 바깥과 인연이 없는 독립체

### 2.1 기본은 이름공간뿐, 인스턴스 관계는 없음

수식어 없는 중첩 클래스는 오직 바깥 클래스의 이름공간 안에 산다. 그 인스턴스는 바깥 클래스의 어떤 인스턴스와도 연결되지 않는다. 개념적으로 이것은 "최상위에 선언한 클래스를 그냥 이름만 안쪽으로 옮긴 것"과 동등하다. 실제로 다음 두 코드는 `Node`가 어떤 인스턴스에 묶이느냐의 관점에서 완전히 같다.

```kotlin
// (A) 중첩
class Graph {
    class Edge(val from: Int, val to: Int)
}
// (B) 최상위 + 이름 규칙
class Graph2
class Graph2Edge(val from: Int, val to: Int)
```

차이는 오직 이름공간과 가시성 제어에 있다. `Graph.Edge`는 "간선은 그래프의 개념"임을 이름으로 표현하고, `Edge`를 `private`로 감춰 그래프 밖에서는 아예 못 만들게 할 수도 있다(2.4).

### 2.2 바깥의 `private` 멤버에 접근할 수 있는가 — 인스턴스가 있으면 가능

여기에 미묘한 지점이 있다. 중첩 클래스는 바깥 *인스턴스*를 참조하지 못한다. 그러나 Kotlin의 `private` 가시성은 "선언을 감싸는 클래스와 그 안의 모든 멤버(중첩·이너 클래스 포함)에게 보인다"는 렉시컬 규칙이다([[26 - 가시성 한정자]]). 따라서 중첩 클래스가 바깥 인스턴스를 **인자로 넘겨받으면**, 그 인스턴스의 `private` 멤버에 접근할 수 있다.

```kotlin
class BankAccount(private val balance: Long) {
    // 중첩 클래스: 바깥 인스턴스를 스스로는 모르지만,
    // 인자로 받으면 그 private 멤버에 닿는다 (렉시컬 가시성)
    class Auditor {
        fun snapshot(account: BankAccount): Long =
            account.balance   // OK: private balance에 접근 가능
    }
}

fun main() {
    val audit = BankAccount.Auditor()
    println(audit.snapshot(BankAccount(10_000)))  // => 10000
}
```

이것이 "인스턴스는 필요하지만, `private` 접근은 가능하다"는 두 사실이 공존하는 이유다. 중첩 클래스는 바깥 인스턴스를 *암시적으로* 갖지 않을 뿐, `private` 벽을 넘는 특권(렉시컬 내부자 자격)은 갖는다.

> **명세 정밀**: Kotlin의 `private`는 파일 최상위 선언에서는 "같은 파일", 클래스 멤버에서는 "그 클래스와 그 안의 모든 중첩·이너 선언"에 보인다. 즉 `private`은 Java의 `private`(클래스 단위)과 대체로 같되, 중첩/이너 경계를 자연스럽게 넘는다. JVM 백엔드에서 이 "경계를 넘는 private 접근"은 통상 컴파일러가 만든 **합성 접근자 메서드**(예: `access$getBalance$p`)를 통해 이뤄진다. 진짜 JVM `private` 필드는 다른 클래스가 직접 못 읽기 때문이다. 이 세부는 백엔드 구현 사항이며 소스 의미론에는 드러나지 않는다.

### 2.3 바깥의 `companion`·정적 멤버는 자유롭게 접근

바깥 클래스에 `companion object`가 있으면, 그 멤버는 인스턴스가 필요 없는 "클래스 수준" 접근점이므로 중첩 클래스에서도 그냥 쓸 수 있다.

```kotlin
class Config {
    companion object {
        const val VERSION = 3
        private fun defaultTimeout() = 30
    }

    class Loader {
        fun describe() = "config v$VERSION, timeout=${defaultTimeout()}s"
        // companion의 private 멤버까지 접근 가능 (렉시컬 내부자)
    }
}

fun main() {
    println(Config.Loader().describe())  // => config v3, timeout=30s
}
```

`companion object`의 전모는 [[28 - object와 companion - 싱글턴과 동반 객체]]가 소유한다. 여기서 기억할 것은 "중첩 클래스가 바깥 인스턴스는 몰라도, 바깥의 클래스 수준 선언(companion, 다른 중첩 타입, 상수)은 안다"는 점이다.

### 2.4 가시성과 완전 이름 — 밖에서 부르는 법

중첩 클래스에도 가시성 한정자가 적용된다. `private`로 두면 바깥 클래스 안에서만 쓰이는 구현 세부가 되어, 외부 코드가 `Outer.Nested`로 접근할 수 없다.

```kotlin
class LinkedStack<T> {
    // 스택의 내부 표현. 밖에서는 존재조차 몰라야 한다.
    private class Cell<T>(val value: T, val next: Cell<T>?)

    private var top: Cell<T>? = null

    fun push(v: T) { top = Cell(v, top) }
    fun pop(): T? {
        val c = top ?: return null
        top = c.next
        return c.value
    }
}

fun main() {
    val s = LinkedStack<String>()
    s.push("a"); s.push("b")
    println(s.pop())   // => b
    // val c = LinkedStack.Cell("x", null)  // 컴파일 에러: Cell은 private
}
```

`Cell`을 `private` 중첩 클래스로 둔 덕분에, 연결 리스트라는 내부 구현이 완전히 캡슐화된다. 사용자는 `push`/`pop`이라는 계약만 보고, `Cell`이라는 표현은 볼 수 없다. 이것이 중첩 클래스의 가장 값진 쓰임 중 하나다 — **구현 타입의 은닉**.

기본 가시성은 `public`이므로, 아무 한정자 없는 중첩 클래스는 `Outer.Nested`로 어디서든 접근된다. 필요에 따라 `internal`(모듈 단위, [[26 - 가시성 한정자]]) 또는 `protected`(바깥 클래스의 하위에서만)로 조절한다.

### 2.5 JVM에서의 컴파일 산물

> **명세 정밀 / JVM 백엔드**: JVM 백엔드에서 중첩 클래스 `Outer.Nested`는 별도의 `.class` 파일 `Outer$Nested.class`로 컴파일되며, Java의 **정적 중첩 클래스**로 표현된다. 즉 바깥 인스턴스를 가리키는 합성 필드가 없다. Kotlin/Native·JS·Wasm 백엔드는 각자의 방식으로 이 "바깥 참조 없음"을 표현하지만, 소스 수준 의미론(바깥 인스턴스 무관)은 모든 타깃에서 동일하다.

이 컴파일 사실은 곧바로 실무적 함의를 낳는다. 중첩 클래스의 인스턴스는 바깥 인스턴스를 살려 두지 않으므로, 오래 사는 자료구조의 원소로 안전하다. 이것이 8절에서 다룰 "누수 방지를 위해 `inner`를 nested로 바꾸기"의 근거다.

### 2.6 클래스만이 아니다 — 인터페이스·object·enum·sealed의 중첩

중첩할 수 있는 것은 클래스만이 아니다. 인터페이스, `object`, `enum class`, 데이터 클래스, 봉인 계층 전부 중첩 가능하다. 이는 특히 봉인 계층([[30 - sealed 클래스와 대수적 데이터 타입]])에서 관용적이다.

```kotlin
sealed interface Shape {
    // 봉인 계층의 변형들을 바깥 이름공간 안에 모은다
    data class Circle(val radius: Double) : Shape
    data class Rectangle(val w: Double, val h: Double) : Shape
    data object Empty : Shape           // data object: 27장/28장
}

fun area(s: Shape): Double = when (s) {   // else 불필요 — 완전성 검사
    is Shape.Circle -> Math.PI * s.radius * s.radius
    is Shape.Rectangle -> s.w * s.h
    Shape.Empty -> 0.0
}
```

여기서 `Circle`·`Rectangle`·`Empty`는 모두 `Shape`의 중첩 선언이자 하위 타입이다. 봉인 계층의 모든 변형을 한 이름공간에 모아 두는 이 패턴은 대수적 데이터 타입을 표현하는 Kotlin의 정석이다. 중첩된 `object`(`Empty`)는 그 자체가 싱글턴이면서 바깥 이름공간에 소속된다는 점에서, 이 장과 [[28 - object와 companion - 싱글턴과 동반 객체]]의 교차점이다.

## 3. 이너 클래스 — 바깥 인스턴스를 등에 업다

### 3.1 `inner`가 하는 일: 암시적 바깥 참조

`inner` 키워드를 붙이면 클래스는 자신을 만들어 낸 바깥 인스턴스에 대한 **암시적 참조**를 갖는다. 이 참조 덕분에 이너 클래스의 코드는 바깥 인스턴스의 프로퍼티·메서드를 한정 없이 직접 부를 수 있다.

```kotlin
class Grid(val width: Int, val height: Int) {
    private val cells = Array(width * height) { 0 }

    inner class Cursor(private var x: Int, private var y: Int) {
        // width, height, cells 모두 바깥 Grid 인스턴스의 것 — 직접 접근
        fun read(): Int = cells[y * width + x]
        fun moveRight(): Boolean {
            return if (x + 1 < width) { x++; true } else false
        }
    }

    fun cursorAt(x: Int, y: Int) = Cursor(x, y)  // 바깥 몸통 안이므로 그냥 Cursor()
}

fun main() {
    val grid = Grid(3, 2)
    val cur = grid.cursorAt(0, 0)
    println(cur.moveRight())   // => true  (width=3 안이므로 이동 성공)
    println(cur.read())        // => 0
}
```

`Cursor`는 `width`·`height`·`cells`를 자기 필드처럼 쓴다. 이들은 사실 `Cursor`를 낳은 `grid` 인스턴스의 것이다. 커서라는 개념이 격자 없이는 의미가 없다는 도메인 사실을, `inner`가 코드 구조로 못박는다.

### 3.2 바깥 인스턴스가 있어야 태어난다

이너 클래스는 바깥 인스턴스가 없으면 존재할 수 없다. 그래서 생성 문법이 다르다. 바깥 클래스 *몸통 안에서는* 암시적 바깥 인스턴스(`this`)가 있으므로 그냥 `Cursor(...)`로 만든다. 그러나 바깥에서 만들려면 반드시 바깥 인스턴스를 앞에 두어야 한다.

```kotlin
fun main() {
    val grid = Grid(3, 2)
    val c1 = grid.Cursor(1, 1)   // 바깥 인스턴스 grid에 대고 생성
    // val c2 = Grid.Cursor(1, 1)  // 컴파일 에러: 이너는 바깥 인스턴스가 필요
}
```

`grid.Cursor(1, 1)`이라는 낯선 문법 — 인스턴스에 점을 찍고 생성자를 부르는 — 이 이너 클래스의 정체를 그대로 노출한다. 컴파일러 입장에서 이 호출은 "grid를 바깥 참조로 삼는 `Cursor`를 하나 만들어라"는 뜻이다.

### 3.3 JVM 바이트코드에서 무슨 일이 일어나는가

> **명세 정밀 / JVM 백엔드**: JVM 백엔드에서 `inner class Cursor`는 바깥 인스턴스를 담는 합성 필드(관례적으로 `this$0`)를 갖고, 그 생성자는 첫 인자로 바깥 인스턴스를 받는 형태로 컴파일된다. 개념적으로 다음 Java와 등가다.

```java
// inner 클래스의 개념적 컴파일 형태 (JVM)
public final class Grid {
    // ...
    public final class Cursor {
        // synthetic 필드: 바깥 인스턴스를 붙잡는다
        private final Grid this$0;
        // 생성자 첫 인자로 바깥 인스턴스가 주입됨
        Cursor(Grid outer, int x, int y) { this$0 = outer; /* ... */ }

        public int read() {
            // cells[...] 는 사실 this$0.cells[...]
            return this$0.getCells()[/* ... */];
        }
    }
}
```

즉 "바깥을 안다"는 마법은 없다. 이너 클래스는 그저 바깥 인스턴스를 **필드로 붙잡고** 있을 뿐이고, 바깥 멤버 접근은 모두 `this$0.멤버`로 우회된다. 이 사실을 아는 순간 두 가지가 자명해진다. 첫째, 이너 인스턴스는 바깥 인스턴스보다 오래 살면 바깥을 계속 살려 둔다(누수, 8절). 둘째, 이너 인스턴스 하나마다 참조 필드 하나만큼의 메모리가 더 든다.

### 3.4 이너 클래스는 상속·오버라이드에도 참여한다

이너 클래스도 보통 클래스처럼 다른 클래스를 상속하거나 인터페이스를 구현할 수 있다. 이는 "바깥 상태에 접근하면서, 동시에 어떤 계약을 이행하는 객체"를 만들 때 유용하다.

```kotlin
class Playlist(private val songs: List<String>) {
    // 이너 클래스가 Iterator 인터페이스를 구현 — 바깥의 songs에 접근하면서
    inner class SongIterator : Iterator<String> {
        private var index = 0
        override fun hasNext() = index < songs.size
        override fun next() = songs[index++]
    }

    fun iterator() = SongIterator()
}

fun main() {
    val p = Playlist(listOf("아침", "저녁"))
    val it = p.iterator()
    while (it.hasNext()) print("${it.next()} ")  // => 아침 저녁
}
```

`SongIterator`는 `Iterator<String>` 계약을 이행하면서 바깥 `Playlist`의 `songs`를 읽는다. 이것이 이너 클래스의 전형적 정당한 쓰임 — "바깥의 상태를 순회·조작하는 보조 객체"다. 다만 실무에서는 대부분 이런 반복자를 익명 객체나 `iterator {}` 빌더로 더 간결히 쓴다(6절, [[40 - 시퀀스와 지연 평가]]).

## 4. 한정된 `this`와 레이블 — 중첩 스코프에서 나는 누구인가

### 4.1 `this`의 모호성 문제

이너 클래스 안에서는 `this`가 두 개의 후보를 갖는다. 이너 인스턴스 자신과, 그가 등에 업은 바깥 인스턴스다. Kotlin은 기본적으로 `this`를 **가장 안쪽 스코프의 인스턴스**로 해석한다. 바깥 인스턴스를 명시적으로 가리키려면 **한정된 this(qualified this)** `this@Outer`를 쓴다.

```kotlin
class Outer(val id: Int) {
    inner class Inner(val id: Int) {   // 같은 이름 id — 가림(shadowing)
        fun describe(): String {
            val innerThis = this          // Inner 인스턴스
            val outerThis = this@Outer    // Outer 인스턴스
            return "inner.id=${this.id}, outer.id=${this@Outer.id}"
        }
    }
}

fun main() {
    println(Outer(1).Inner(2).describe())  // => inner.id=2, outer.id=1
}
```

`this@Outer`의 `@Outer`는 "가장 가까운, 이름이 `Outer`인 스코프의 `this`"를 고른다. 이것이 없으면 안쪽 `id`가 바깥 `id`를 완전히 가려, 바깥 값에 닿을 방법이 없어진다.

### 4.2 레이블로서의 `this@Label` — 통일된 규칙

`this@Outer`의 `@Outer`는 사실 **레이블(label)** 이다. Kotlin에는 여러 종류의 암시적 `this`가 있고, 모두 같은 레이블 문법으로 구별한다.

- 클래스/이너 클래스: 클래스 이름이 레이블. `this@Outer`, `this@Inner`.
- 수신 객체 지정 람다: 함수 이름이 레이블. `this@apply`, `this@run` 등([[16 - 스코프 함수와 수신 객체 관용구]]).
- 확장 함수: 확장 함수 이름이 레이블.

```kotlin
class Robot(val name: String) {
    inner class Arm(val side: String) {
        fun greet(): String = buildString {
            // buildString의 수신자는 StringBuilder — this@buildString
            append("팔(")
            append(this@Arm.side)        // Arm 인스턴스
            append(") of ")
            append(this@Robot.name)      // Robot 인스턴스
        }
    }
}

fun main() {
    println(Robot("R2").Arm("왼쪽").greet())  // => 팔(왼쪽) of R2
}
```

이 예제 안에는 무려 세 개의 `this` 후보가 겹쳐 있다 — `buildString` 람다의 `StringBuilder`(암시적 수신자), `Arm` 인스턴스, `Robot` 인스턴스. `append(...)`는 가장 안쪽인 `StringBuilder`의 것이고, 바깥 두 인스턴스는 `this@Arm`·`this@Robot`으로 정확히 지목한다. 중첩과 수신 객체가 겹칠수록 이 한정 문법의 값이 커진다.

> **명세 정밀**: 한정되지 않은 `this`는 "가장 가까운 둘러싼 스코프"의 `this`로 해석된다. `this@Label`은 레이블과 일치하는 가장 안쪽 스코프를 고른다. 이 규칙은 이너 클래스든 수신 객체 지정 람다든 확장 함수든 동일하게 적용되는 하나의 통일된 메커니즘이다.

### 4.3 `super@Outer` — 상속 계층까지 겹칠 때

`this`뿐 아니라 `super`도 한정할 수 있다. 이너 클래스와 바깥 클래스가 각각 슈퍼클래스를 가질 때, 이너 클래스 안에서 바깥의 슈퍼 구현을 부르려면 `super@Outer`를 쓴다. 실무에서 드물지만, 다중 스코프에서 `super`의 대상을 못박는 유일한 방법이다.

```kotlin
open class Vehicle {
    open fun sound() = "..."
}

class Car : Vehicle() {
    override fun sound() = "부릉"

    inner class Horn {
        // Car의 sound가 아니라 Vehicle의 원래 sound를 부르고 싶다
        fun test() = super@Car.sound()   // Vehicle.sound() 호출
    }
}

fun main() {
    println(Car().Horn().test())  // => ...
}
```

### 4.4 확장 함수의 수신자와 이너 클래스가 겹칠 때

확장 함수([[35 - 확장 함수와 프로퍼티]])를 이너 클래스 안에서 정의하거나 호출하면 수신자가 겹칠 수 있다. 이때도 레이블 규칙으로 어느 수신자를 쓸지 결정한다. 핵심은 "암시적 수신자가 여러 개일 때, 이름 없는 접근은 항상 가장 안쪽을 고르고, 바깥은 레이블로 지목한다"는 하나의 원칙으로 모든 경우가 설명된다는 것이다.

## 5. 지역 클래스 — 함수 몸통 속의 타입

### 5.1 함수 안에서 클래스를 선언한다

클래스는 최상위나 클래스 몸통뿐 아니라, **함수의 몸통 안**에도 선언할 수 있다. 이를 지역 클래스(local class)라 한다. 이 클래스는 오직 그 함수 안에서만 보이며, 함수가 반환되면 이름은 사라진다(인스턴스는 참조가 남아 있으면 산다).

```kotlin
fun analyze(numbers: List<Int>): String {
    // 오직 이 함수 안에서만 쓰이는 보조 타입
    class Stats {
        var sum = 0L
        var count = 0
        fun add(n: Int) { sum += n; count++ }
        fun mean() = if (count == 0) 0.0 else sum.toDouble() / count
    }

    val stats = Stats()
    for (n in numbers) stats.add(n)
    return "평균=${stats.mean()}, 개수=${stats.count}"
}

fun main() {
    println(analyze(listOf(10, 20, 30)))  // => 평균=20.0, 개수=3
}
```

`Stats`는 `analyze` 밖에서는 존재하지 않는다. 함수 내부 로직을 구조화하되 그 구조를 외부에 노출하지 않는, 가장 강한 캡슐화다.

### 5.2 지역 클래스는 바깥 지역 변수를 캡처한다

지역 클래스의 진짜 힘은 **자신을 둘러싼 함수의 지역 변수를 붙잡을(capture) 수 있다**는 데 있다. 이 캡처의 원리는 클로저와 같으며, 정본은 [[14 - 클로저와 캡처]]가 소유한다. 여기서 강조할 것은 Kotlin이 **값이 아니라 변수를 붙잡는다**는 점, 그래서 `var`도 캡처하고 심지어 수정할 수 있다는 점이다(Java의 지역 클래스는 `final`/effectively final 변수만 캡처한다 — 큰 차이).

```kotlin
fun makeCounter(start: Int): () -> Int {
    var current = start          // 지역 var

    class Counter {
        fun next(): Int {
            val result = current
            current++            // 캡처한 var를 수정
            return result
        }
    }

    val c = Counter()
    return { c.next() }
}

fun main() {
    val counter = makeCounter(10)
    println(counter())  // => 10
    println(counter())  // => 11
    println(counter())  // => 12
}
```

`Counter`가 `makeCounter`의 지역 변수 `current`를 붙잡고, `next()`를 부를 때마다 그 변수를 증가시킨다. `makeCounter`가 이미 반환했는데도 `current`는 계속 살아 있다 — `Counter` 인스턴스가 그것을 붙잡고 있기 때문이다.

> **명세 정밀 / JVM 백엔드**: JVM 백엔드에서 캡처된 `val`은 지역 클래스의 합성 필드로 값이 복사되지만, 캡처된 `var`는 한 원소 배열이나 `Ref` 객체(예: `kotlin.jvm.internal.Ref.IntRef`)로 감싸져 그 **참조**가 공유된다. 이렇게 해야 바깥 함수와 지역 클래스가 같은 변수를 보고 함께 수정할 수 있다. 이 `Ref` 래핑 메커니즘의 전모는 [[14 - 클로저와 캡처]]에서 다룬다. 여기서는 "지역 클래스도 람다와 똑같이 캡처한다"는 사실이 핵심이다.

### 5.3 지역 클래스와 `inner`, 그리고 바깥 클래스 인스턴스

지역 클래스가 어떤 클래스의 메서드 안에 있고, 그 바깥 클래스의 인스턴스 멤버에 접근하려면 어떻게 될까? 흥미롭게도 메서드 안의 지역 클래스는 **암시적으로 바깥 클래스 인스턴스에도 접근**할 수 있다(메서드가 `this`를 가지므로 그 `this`를 캡처한다). 이 경우 지역 클래스는 사실상 이너처럼 행동한다.

```kotlin
class Meter(private var reading: Int) {
    fun makeRecorder(): () -> Unit {
        // 메서드 안의 지역 클래스는 바깥 Meter 인스턴스도 캡처한다
        class Recorder {
            fun tick() { reading++ }   // 바깥 Meter의 private reading에 접근·수정
        }
        val r = Recorder()
        return { r.tick() }
    }
    fun current() = reading
}

fun main() {
    val m = Meter(0)
    val rec = m.makeRecorder()
    rec(); rec(); rec()
    println(m.current())  // => 3
}
```

`Recorder`는 `inner`라고 쓰지 않았지만, `makeRecorder`가 `Meter`의 메서드이므로 그 `this`(즉 `m`)를 캡처해 `reading`을 조작한다. 지역 클래스는 자신을 둘러싼 *모든* 스코프 — 지역 변수든 바깥 클래스 인스턴스든 — 를 붙잡을 수 있다. 이 관대함 때문에 지역 클래스 역시 누수의 잠재적 원천이다(8절).

### 5.4 언제 지역 클래스를 쓰나

지역 클래스는 "함수 하나 안에서만 의미 있는, 상태를 가진 보조 개념"에 적합하다. 다만 상태가 단순하고 인터페이스 하나만 구현하면 다음 절의 익명 객체나 람다가 더 간결하다. 지역 클래스가 빛나는 경우는 (1) 이름이 있어야 가독성이 사는 경우, (2) 인스턴스를 여러 번 만들어야 하는 경우, (3) 여러 메서드와 여러 필드를 가진 복잡한 보조 타입인 경우다.

## 6. 익명 객체 — 이름 없는 일회용 인스턴스

### 6.1 객체 표현식(object expression)의 문법

지금까지는 이름이 있는 중첩·이너·지역 클래스를 봤다. Kotlin은 이름조차 짓지 않고 **그 자리에서 인스턴스를 하나 만드는** 문법을 제공한다. 이를 객체 표현식(object expression), 그 결과를 익명 객체(anonymous object)라 부른다.

```kotlin
val comparator = object : Comparator<Int> {
    override fun compare(a: Int, b: Int): Int = b - a  // 내림차순
}

fun main() {
    val list = mutableListOf(3, 1, 2)
    list.sortWith(comparator)
    println(list)  // => [3, 2, 1]
}
```

`object : Comparator<Int> { ... }`는 "`Comparator<Int>`를 구현하는 이름 없는 클래스를 만들고, 즉시 그 인스턴스 하나를 생성하라"는 표현식이다. 클래스 선언과 인스턴스 생성이 한 표현식으로 합쳐진 것이다. 이는 `object` 선언([[28 - object와 companion - 싱글턴과 동반 객체]])과 키워드는 같지만 근본적으로 다르다 — 선언은 이름 붙은 싱글턴이고, 표현식은 평가될 때마다 새 인스턴스를 낳는 값이다(6.5에서 대조).

### 6.2 슈퍼타입 없이, 하나, 또는 여럿

객체 표현식은 슈퍼타입을 0개, 1개, 또는 여러 개 지정할 수 있다.

```kotlin
// (1) 슈퍼타입 없이 — 즉석에서 프로퍼티/메서드 묶음을 만든다
val point = object {
    val x = 3
    val y = 4
    fun distanceFromOrigin() = Math.hypot(x.toDouble(), y.toDouble())
}
println(point.distanceFromOrigin())  // => 5.0

// (2) 하나의 슈퍼타입 구현
val runnable = object : Runnable {
    override fun run() = println("실행")
}

// (3) 여러 슈퍼타입을 동시에 — 클래스 하나 + 인터페이스 여럿
open class Animal { open fun sound() = "..." }
interface Named { val name: String }

val cat = object : Animal(), Named {
    override val name = "고양이"
    override fun sound() = "야옹"
}
println("${cat.name}: ${cat.sound()}")  // => 고양이: 야옹
```

(3)은 특히 주목할 만하다. 이름 있는 클래스로는 "클래스 하나 상속 + 인터페이스 여럿 구현"을 하려면 새 클래스를 선언해야 하지만, 익명 객체는 그 자리에서 여러 타입을 한 번에 조립한다. 일회성 어댑터를 만들 때 이보다 간결한 방법이 없다.

> **역사 메모**: 슈퍼타입 없는 `object { ... }`(예 (1))는 Java에는 없는 기능이다. Java의 익명 클래스는 반드시 하나의 슈퍼타입(클래스나 인터페이스)을 상속·구현해야 한다. Kotlin은 "그냥 프로퍼티 몇 개를 묶은 즉석 값"을 만드는 것까지 허용해, 지역적으로만 쓰이는 임시 데이터 묶음을 가볍게 표현하게 했다.

### 6.3 익명 객체도 캡처한다

객체 표현식 역시 자신을 둘러싼 스코프의 변수와 인스턴스를 캡처한다 — 지역 클래스, 람다와 완전히 같은 원리다([[14 - 클로저와 캡처]]).

```kotlin
fun counterFrom(start: Int): Iterator<Int> {
    var value = start
    // 익명 객체가 지역 var value를 캡처하고 수정한다
    return object : Iterator<Int> {
        override fun hasNext() = true          // 무한
        override fun next(): Int = value++
    }
}

fun main() {
    val it = counterFrom(100)
    println(it.next())  // => 100
    println(it.next())  // => 101
}
```

여기서 익명 `Iterator`는 `value`를 붙잡고 매 `next()`마다 증가시킨다. Java의 익명 클래스가 `final` 지역 변수만 캡처하고 수정할 수 없었던 것과 달리, Kotlin의 익명 객체는 `var`를 붙잡아 자유롭게 수정한다. 이 차이는 상태를 가진 반복자·콜백을 훨씬 자연스럽게 쓰게 한다.

### 6.4 익명 객체의 타입은 언제 보이고 언제 뭉개지는가

이것이 객체 표현식의 가장 미묘한 규칙이자, 사람들이 가장 자주 헷갈리는 지점이다. 익명 객체에는 이름이 없는데, 슈퍼타입 없이 `object { val x = 5 }`를 만들면 그 `x`에 어떻게 접근하는가? 답은 **선언 위치의 가시성**에 달려 있다.

- **지역 변수**나 **`private` 멤버**(private 함수의 반환, private 프로퍼티)에 담기면, 익명 객체의 *실제 타입*(모든 멤버 포함)이 그대로 노출된다. 그래서 그 고유 멤버에 접근할 수 있다.
- 그러나 `public`·`internal`·`protected` 함수의 반환 타입이나 프로퍼티 타입으로 새어 나가면, 컴파일러는 그 타입을 익명 객체가 상속한 **슈퍼타입**(없으면 `Any`)으로 축소한다. 그러면 고유 멤버는 보이지 않는다.

```kotlin
class Factory {
    // (A) private 함수: 익명 타입이 그대로 노출 → count 접근 가능
    private fun makeCounter() = object {
        var count = 0
        fun inc() { count++ }
    }

    fun demo() {
        val c = makeCounter()
        c.inc()
        println(c.count)   // => 1   (private 함수라 익명 타입이 보인다)
    }

    // (B) public 함수: 반환 타입이 Any로 축소 → 고유 멤버 안 보임
    fun makeCounterPublic() = object {
        var count = 0
    }
}

fun main() {
    val f = Factory()
    f.demo()
    val obj = f.makeCounterPublic()
    // println(obj.count)   // 컴파일 에러: Any에는 count가 없다
    println(obj)            // Any로만 보이므로 toString 정도만 가능
}
```

또 하나, **지역 변수**에 담을 때는 언제나 익명 타입이 보인다.

```kotlin
fun main() {
    val anon = object {          // 지역 변수 → 익명 타입 노출
        val label = "임시"
        fun greet() = "안녕, $label"
    }
    println(anon.greet())         // => 안녕, 임시
}
```

> **명세 정밀**: 익명 객체의 타입(그 고유 멤버까지 포함하는 타입)은 오직 **지역 선언과 `private` 선언**에서만 그 선언의 타입이 될 수 있다. `public`/`protected`/`internal`로 노출되는 함수의 반환 타입이나 프로퍼티 타입은, 그 익명 객체가 명시적으로 상속·구현한 슈퍼타입(여럿이면 그 교집합 개념이 아니라 실제로는 표현 가능한 상위 타입)이 되고, 슈퍼타입을 하나도 안 붙였으면 `Any`가 된다. 이유는 명확하다 — 이름 없는 타입을 모듈 경계 너머로 노출할 방법이 없기 때문이다. 이름이 없으니 다른 모듈이 그 타입을 적을 수가 없다.

이 규칙은 실무에서 "왜 내 익명 객체의 프로퍼티가 안 보이지?"라는 당혹의 근원이다. 해결책은 (1) private/지역으로 두거나, (2) 명시적 인터페이스를 슈퍼타입으로 붙여 그 인터페이스 멤버로 접근하거나, (3) 아예 이름 있는 클래스로 승격하는 것이다.

### 6.5 객체 표현식 vs 객체 선언 — 같은 키워드, 다른 세계

`object`라는 키워드는 두 곳에서 쓰이지만 의미가 정반대에 가깝다. 이 대조는 [[28 - object와 companion - 싱글턴과 동반 객체]]가 소유하지만, 익명 객체를 이해하려면 여기서 못박아야 한다.

| 관점 | 객체 **선언** `object Foo { }` | 객체 **표현식** `object : T { }` |
|------|-------------------------------|--------------------------------|
| 이름 | 있음 (`Foo`) | 없음 (익명) |
| 인스턴스 수 | 하나 (싱글턴) | 평가될 때마다 새로 생성 |
| 초기화 시점 | 최초 접근 시 지연·스레드 안전 | 표현식이 평가되는 매 순간 |
| 값인가 선언인가 | 선언(문) | 값(표현식) — 변수에 담긴다 |
| 캡처 | (최상위면) 캡처 없음 | 둘러싼 스코프 캡처 |
| 용도 | 전역 싱글턴, 상수 묶음 | 일회용 어댑터·콜백·리스너 |

가장 중요한 차이는 **인스턴스 수**다. 객체 선언은 프로그램 전체에서 딱 하나(M24 — `object`는 정적 클래스가 아니라 진짜 인스턴스다). 반면 객체 표현식은 그 표현식이 실행될 때마다 새 인스턴스를 낳는다. 루프 안에 객체 표현식을 두면 반복마다 새 객체가 만들어진다.

```kotlin
object Logger {            // 선언: 프로그램 전체에서 단 하나
    fun log(msg: String) = println("[LOG] $msg")
}

fun listeners(): List<Runnable> = List(3) {
    // 표현식: 세 번 평가 → 세 개의 서로 다른 익명 객체
    object : Runnable {
        override fun run() = println("리스너")
    }
}

fun main() {
    val ls = listeners()
    println(ls[0] === ls[1])  // => false  (서로 다른 인스턴스)
    println(Logger === Logger) // => true   (선언은 언제나 같은 인스턴스)
}
```

> **흔한 오해**: "익명 객체도 `object` 키워드를 쓰니 싱글턴이겠지." — 아니다. 표현식으로서의 `object`는 평가될 때마다 새 인스턴스를 만든다. 싱글턴은 오직 이름 붙은 `object` **선언**뿐이다(M24 참조). 이 둘을 혼동하면, 루프에서 익명 객체를 만들면서 "왜 매번 새로 생기지?"라거나, 반대로 상태를 공유하려 익명 객체를 쓰다 낭패를 본다.

## 7. 익명 객체 vs 람다 vs SAM 변환 — 어디서 갈아탈 수 있는가

### 7.1 함수형 인터페이스라면 람다로 대체

객체 표현식으로 인터페이스 하나를 구현하는 코드는 종종 장황하다. 그 인터페이스가 **추상 메서드 하나짜리**(Single Abstract Method, SAM)라면, 익명 객체 대신 람다를 쓸 수 있다. 이것이 SAM 변환(SAM conversion)이다. 정본은 [[13 - 함수 타입과 람다와 함수 참조]]와 [[25 - 인터페이스]]가 나눠 소유하지만, 익명 객체와의 갈림길로서 여기서 정리한다.

```kotlin
// (A) 익명 객체 — 장황하지만 언제나 통한다
val r1 = object : Runnable {
    override fun run() = println("A")
}

// (B) SAM 변환 — Runnable은 Java의 함수형 인터페이스라 람다로 축약
val r2 = Runnable { println("B") }
```

SAM 변환이 되는 조건은 대상 인터페이스가 (1) **Java에서 선언된** 함수형 인터페이스이거나, (2) Kotlin에서 `fun interface`로 명시된 함수형 인터페이스인 경우다. 그냥 Kotlin의 일반 인터페이스는 — 설령 메서드가 하나뿐이어도 — 람다로 직접 변환되지 *않는다*. 이 비대칭은 초심자를 자주 당황시킨다.

```kotlin
// Kotlin의 일반 인터페이스 (fun interface 아님)
interface Handler {
    fun handle(x: Int)
}

// val h = Handler { println(it) }   // 컴파일 에러: 일반 인터페이스는 SAM 변환 안 됨
val h = object : Handler {           // 익명 객체로는 언제나 가능
    override fun handle(x: Int) = println(x)
}

// fun interface로 선언했다면 람다 가능
fun interface Handler2 {
    fun handle(x: Int)
}
val h2 = Handler2 { println(it) }    // OK: fun interface라 SAM 변환
```

> **명세 정밀**: `fun interface`(functional interface)는 정확히 하나의 추상 멤버 함수를 가진 인터페이스에만 붙일 수 있고, 그때 람다로부터의 SAM 변환이 활성화된다. 프로퍼티나 두 번째 추상 함수가 있으면 `fun interface`로 선언할 수 없다. Java 인터페이스는 별도 표시 없이도 함수형이면 SAM 변환된다(Kotlin이 Java 상호운용을 위해 특별 대우, [[45 - Java 상호운용]]).

### 7.2 언제 익명 객체를 써야 하는가

람다가 더 간결하지만, 다음 경우에는 익명 객체여야 한다.

- **추상 멤버가 둘 이상**일 때 (예: `addListener`가 여러 콜백을 요구). 람다는 함수 하나만 표현하므로 불가.
- **상태(프로퍼티)를 가진 구현**이 필요할 때. 익명 객체는 자기 필드를 가질 수 있다.
- **여러 슈퍼타입**을 동시에 구현·상속할 때(6.2의 (3)).
- **슈퍼타입 없는** 즉석 값 묶음이 필요할 때(6.2의 (1)).

```kotlin
interface MouseListener {
    fun onClick()
    fun onDoubleClick()   // 추상 멤버 둘 → 람다 불가, 익명 객체 필요
}

val listener = object : MouseListener {
    private var clicks = 0                  // 자기 상태
    override fun onClick() { clicks++; println("click #$clicks") }
    override fun onDoubleClick() { println("double") }
}
```

### 7.3 인스턴스 생성 비용 — 캐싱의 미묘함

> **성능 주의**: 객체 표현식은 평가될 때마다 새 인스턴스를 만든다. 반면 **아무것도 캡처하지 않는** 람다는 컴파일러/런타임이 싱글턴으로 캐싱할 수 있어(구현·백엔드에 따라), 매번 새 객체를 만들지 않을 수 있다. 예컨대 아무 변수도 캡처하지 않는 람다를 넘기는 코드는 반복 호출에서도 같은 인스턴스를 재사용할 수 있다. 그러나 익명 객체는 이 최적화의 대상이 아니라, 평가마다 확실히 새로 생긴다. 뜨거운 경로(hot path)에서 캡처 없는 콜백을 만든다면 람다가 할당 측면에서 유리할 수 있다. 다만 이는 백엔드 최적화이므로 "항상 그렇다"고 단정하지 말고, 실제 병목이 확인될 때만 신경 쓰는 편이 옳다. 대부분의 코드에서 이 차이는 무의미하다.

이 절을 관통하는 원칙은 이렇다. "인터페이스 하나 + 상태 없음"이면 람다(가능하면), "둘 이상 / 상태 있음 / 여러 타입"이면 익명 객체. 표현력이 부족한 쪽으로 억지로 몰지 말고, 필요한 최소 도구를 고른다.

## 8. 메모리와 누수 — 바깥을 붙잡는 사슬을 끊기

### 8.1 `inner`·익명 객체·지역 클래스가 만드는 강한 참조

지금까지의 논의를 메모리 관점으로 재조립하면 하나의 위험 패턴이 드러난다. `inner` 클래스, 익명 객체, 지역 클래스는 모두 **바깥 인스턴스(또는 캡처한 지역 변수)에 강한 참조(strong reference)** 를 갖는다. 그 참조 사슬 때문에, 이 보조 객체가 어딘가 오래 사는 컬렉션·콜백 목록에 등록되면, 정작 필요 없어진 바깥 객체까지 함께 살아남아 가비지 컬렉션되지 못한다. 이것이 고전적인 메모리 누수(memory leak)다.

```text
누수 사슬:

  [오래 사는 이벤트 버스]
        │ 강한 참조
        ▼
  [익명 리스너 객체]  ── 캡처 ──▶  [바깥의 무거운 객체]
                                        (이제 필요 없는데도 살아남음)
```

핵심은 "보조 객체가 얼마나 오래 사는가"다. 그 수명이 바깥 객체의 의도된 수명보다 길면 누수가 된다.

### 8.2 구체적 예 — 콜백 등록의 함정

일반 도메인으로 재현해 보자. 어떤 온도 센서 허브(장수 객체)에 리스너를 등록하는 상황이다.

```kotlin
class SensorHub {
    private val listeners = mutableListOf<() -> Unit>()
    fun subscribe(listener: () -> Unit) { listeners.add(listener) }
    fun fire() { listeners.forEach { it() }
    }
}

class ReportScreen(private val hub: SensorHub) {
    private val hugeBuffer = IntArray(10_000_000)  // 무거운 상태

    fun activate() {
        // 익명 람다가 this(ReportScreen)를 캡처 → hub가 이 화면 전체를 붙잡는다
        hub.subscribe { println("갱신, buffer size=${hugeBuffer.size}") }
    }
    // 문제: 화면이 닫혀도 hub.listeners가 이 람다를, 람다가 hugeBuffer를 붙잡아
    //       ReportScreen과 1000만짜리 배열이 GC되지 못한다.
}
```

`activate`가 넘긴 람다는 `hugeBuffer`(따라서 `ReportScreen` 인스턴스)를 캡처한다. `hub`가 그 람다를 목록에 계속 갖고 있는 한, 화면이 논리적으로 "닫혀도" 실제 메모리는 해제되지 않는다. `inner class`나 익명 객체 리스너였어도 동일한 사슬이 생긴다.

### 8.3 사슬을 끊는 방법들

이 누수를 끊는 방법은 여럿이며, 각각 이 장의 개념과 직접 연결된다.

**(1) `inner`를 nested로 바꿔 애초에 안 붙잡기.** 보조 객체가 바깥 상태를 정말 필요로 하지 않는다면, `inner`를 빼서 바깥 참조 자체를 없앤다. 필요한 값만 생성자 인자로 명시적으로 넘긴다(2.1~2.2). 이렇게 하면 "무엇을 붙잡는지"가 코드에 드러나고, 무거운 것을 실수로 붙잡을 일이 없다.

```kotlin
class SensorHub2 {
    private val listeners = mutableListOf<Runnable>()
    fun subscribe(r: Runnable) { listeners.add(r) }
    fun unsubscribe(r: Runnable) { listeners.remove(r) }  // 해지 경로 필수
}

class ReportScreen2(private val hub: SensorHub2) {
    // nested: 바깥을 안 붙잡고, 필요한 최소 값만 받는다
    private class UpdateTask(private val label: String) : Runnable {
        override fun run() = println("갱신: $label")
    }
    private val task = UpdateTask("보고서")

    fun activate() = hub.subscribe(task)
    fun deactivate() = hub.unsubscribe(task)   // 명시적 해지
}
```

**(2) 등록을 반드시 해지(unsubscribe)하기.** 아무리 참조를 잘 관리해도, 장수 컬렉션에 넣은 것을 빼지 않으면 누수다. 등록과 해지를 쌍으로 만들고, 리소스 수명에 맞춰 해지한다. `use`(AutoCloseable) 패턴이나 명시적 생명주기 훅이 여기에 쓰인다([[41 - 예외와 Nothing]]의 `use`).

**(3) 약한 참조(weak reference)를 쓰기.** 콜백을 강한 참조 대신 약한 참조로 보관하면, 바깥 객체가 다른 곳에서 참조되지 않는 순간 GC가 회수할 수 있다. 다만 약한 참조는 "콜백이 예상보다 일찍 사라질 수 있음"을 감수해야 하므로 신중히 쓴다. 이는 JVM/플랫폼별 GC 특성에 의존하는 기법이다([[43 - 동시성과 메모리 모델]]).

> **성능 주의 / JVM 백엔드**: `inner` 클래스의 바깥 참조는 눈에 안 보이는(합성) 필드라 특히 잊기 쉽다. 코드에 `this@Outer`를 한 번도 안 썼는데도, `inner`로 선언된 이상 바깥 참조 필드는 존재하며 GC 사슬에 포함된다. "안 쓰니까 안 붙잡겠지"라는 가정은 틀리다 — `inner` 키워드 자체가 참조를 만든다. 바깥을 정말 안 쓴다면 `inner`를 빼는 것이 유일한 확실한 해법이다.

### 8.4 지역 클래스·익명 객체의 캡처도 같은 위험

지역 클래스와 익명 객체는 `inner`처럼 명시적 키워드는 없지만, 둘러싼 스코프를 **캡처**하는 순간 같은 강한 참조를 만든다(5.3, 6.3). 특히 메서드 안에서 만든 익명 객체는 그 메서드의 `this`(바깥 클래스 인스턴스)까지 캡처하므로, `inner`와 실질적으로 동일한 누수 위험을 갖는다. 캡처 여부는 "익명 객체 안에서 바깥 지역 변수나 바깥 인스턴스 멤버를 참조하는가"로 결정된다. 아무것도 참조하지 않으면 캡처가 없어 위험도 없다.

정리하면, 이 장의 세 구조 — `inner`, 지역 클래스, 익명 객체 — 는 표현력의 대가로 **바깥을 붙잡을 능력**을 갖는다. 그 능력은 유용하지만, "붙잡은 것은 붙잡은 것을 살려 둔다"는 GC의 철칙과 만나 누수를 낳는다. 안전의 첫걸음은 "이 보조 객체가 무엇을 붙잡고, 얼마나 오래 사는가"를 항상 의식하는 것이다.

## 9. 종합 — 무엇을 언제 고를 것인가

### 9.1 결정 트리

지금까지의 모든 선택지를 하나의 흐름으로 정리한다.

```text
클래스를 어디에, 어떻게 둘 것인가?

바깥 클래스 상태에 접근해야 하나?
├─ 아니오 → 이름이 필요한가?
│           ├─ 예, 재사용/여러 인스턴스 → 중첩 클래스 (class)         [2절]
│           └─ 아니오, 일회용 →
│                   슈퍼타입이 함수형 하나 + 상태 없음?
│                   ├─ 예 (fun interface / Java SAM) → 람다           [7.1]
│                   └─ 아니오 (여럿/상태/여러 타입) → 익명 객체        [6절]
│
└─ 예, 바깥 인스턴스를 붙잡아야 함 →
            수명이 바깥보다 짧다고 보장되나?
            ├─ 예 → inner 클래스 또는 캡처하는 익명 객체              [3, 6절]
            └─ 아니오 (오래 산다) → 위험! nested + 명시적 인자 전달    [8.3]
                                      + 반드시 해지 경로 마련
```

### 9.2 컴파일 산물 한눈에

> **명세 정밀 / JVM 백엔드**: 아래는 JVM 백엔드에서의 대략적 산물이다. 다른 백엔드는 표현이 다르되 소스 의미론은 같다.

| 소스 구조 | JVM 산물(개념) | 바깥 참조 필드 | 새 인스턴스 시점 |
|-----------|----------------|----------------|------------------|
| 중첩 클래스 | `Outer$Nested` (정적 중첩) | 없음 | 생성자 호출마다 |
| 이너 클래스 | `Outer$Inner` + `this$0` | 있음 | `outer.Inner()`마다 |
| 지역 클래스 | `Outer$method$LocalName` | 캡처 시 있음 | 생성자 호출마다 |
| 익명 객체 | `Outer$method$1` 등 익명 | 캡처 시 있음 | 표현식 평가마다 |
| 객체 선언 | `Foo` (INSTANCE 싱글턴) | (최상위면) 없음 | 최초 접근 시 1회 |
| 캡처 없는 람다 | 합성 클래스/`INSTANCE` | 없음 | (캐싱 가능) |

### 9.3 이름이 곧 설계다

이 장을 마무리하며 다시 강조할 것은, 선언의 위치와 종류가 단순한 문법 취향이 아니라 **설계 결정**이라는 사실이다. 중첩 클래스는 "이 타입은 저 타입의 어휘"라는 소속을 이름으로 말하고, `inner`는 "이 객체는 저 객체 없이 존재할 수 없다"는 의존을 구조로 말하며, 지역 클래스와 익명 객체는 "이것은 여기서만, 잠깐만"이라는 수명을 스코프로 말한다. 그리고 그 모든 선택은 곧바로 "무엇을 볼 수 있는가(가시성), 무엇을 붙잡는가(캡처), 얼마나 사는가(수명)"라는 세 물음의 답을 결정한다. Kotlin이 `inner`를 기본이 아니라 명시로 만든 것은, 이 결정을 개발자가 무의식적으로가 아니라 의식적으로 내리게 하려는 배려다.

---

우리는 "클래스 안의 클래스"라는 단순해 보이는 주제에서 출발해, Kotlin이 Java의 위험한 기본값을 뒤집어 **바깥 참조 없는 중첩을 기본으로** 삼았다는 설계 결정을 마주했고, `inner`가 붙는 순간 태어나는 합성 필드 `this$0`와 그로 인한 바깥 인스턴스 종속을 바이트코드 수준에서 확인했다. 한정된 `this@Label`이 어떻게 여러 겹의 수신자 사이에서 "나는 누구인가"를 결정하는 하나의 통일된 규칙인지 보았고, 함수 몸통 속 지역 클래스와 이름 없는 익명 객체가 람다와 똑같은 원리로 변수를 — 값이 아니라 변수를 — 붙잡는다는 것, 그리고 익명 객체의 타입이 선언의 가시성에 따라 노출되거나 `Any`로 뭉개지는 미묘한 규칙을 파헤쳤다. 익명 객체와 람다·SAM 변환의 갈림길에서는 "인터페이스 하나 + 무상태면 람다, 그 밖에는 익명 객체"라는 실천적 경계를 세웠다. 마지막으로 이 세 구조가 공유하는 어두운 면 — 바깥을 붙잡는 능력이 곧 누수의 사슬이 된다는 것 — 과 그 사슬을 끊는 방법을 정리했다. 이 장이 던진 첫 질문 "중첩은 바깥을 아는가"의 답은 이제 명확하다. **기본은 모른다. 알고 싶으면 손으로 선언해야 한다. 그리고 안다는 것은 붙잡는다는 것이고, 붙잡는다는 것은 책임진다는 것이다.**

## 핵심 요약

- **Kotlin의 기본 중첩 클래스는 바깥 인스턴스를 참조하지 않는다 — Java와 정반대의 기본값이다.** 바깥을 붙잡으려면 `inner`를 명시해야 하며, 이는 Java에서 `static`을 빠뜨려 생기는 누수를 구조적으로 예방하려는 "안전한 기본값" 설계다.

- **`inner` 클래스는 자신을 만든 바깥 인스턴스에 대한 암시적 참조(JVM 백엔드에서 합성 필드 `this$0`)를 갖는다.** "바깥을 안다"는 마법은 없다 — 그저 바깥 인스턴스를 필드로 붙잡고 모든 접근을 그 참조로 우회할 뿐이다.

- **중첩 클래스는 바깥 인스턴스를 몰라도, 바깥 인스턴스를 인자로 받으면 그 `private` 멤버에 접근할 수 있다.** `private`은 렉시컬 규칙이라 중첩·이너 경계를 넘기 때문이다. "인스턴스 필요"와 "private 접근 가능"은 모순이 아니다.

- **한정된 `this@Label`은 여러 겹의 수신자(이너 인스턴스·바깥 인스턴스·수신 객체 지정 람다·확장 함수) 중 하나를 정확히 지목하는 통일된 규칙이다.** 이름 없는 `this`는 언제나 가장 안쪽을, 레이블은 지정한 스코프를 고른다.

- **지역 클래스와 익명 객체는 람다와 똑같이 둘러싼 스코프의 변수를 캡처한다 — 값이 아니라 변수를.** 그래서 `var`도 붙잡아 수정할 수 있다(Java의 `final`-only 캡처와 대비). JVM 백엔드에서 `var`는 `Ref`로 감싸져 참조가 공유된다([[14 - 클로저와 캡처]]).

- **객체 표현식 `object : T { }`는 평가될 때마다 새 인스턴스를 만드는 값이다 — 이름 붙은 `object` 선언(싱글턴)과는 근본적으로 다르다(M24 참조).** 같은 키워드지만, 하나는 선언(딱 하나), 다른 하나는 표현식(매번 새로).

- **익명 객체의 고유 멤버는 그것이 담기는 선언의 가시성이 지역이거나 `private`일 때만 보인다.** `public`/`internal`/`protected`로 노출되면 타입이 슈퍼타입(없으면 `Any`)으로 축소된다 — 이름 없는 타입을 경계 너머로 적을 방법이 없기 때문이다.

- **함수형 인터페이스(Java SAM 또는 Kotlin `fun interface`)만 람다로 SAM 변환된다.** 일반 Kotlin 인터페이스는 메서드가 하나여도 람다로 변환되지 않으니 익명 객체가 필요하다. 추상 멤버가 둘 이상, 상태가 있거나, 여러 타입을 동시에 구현할 때도 익명 객체여야 한다.

- **`inner`·지역 클래스·캡처하는 익명 객체는 모두 바깥에 강한 참조를 만들어, 오래 사는 컬렉션·콜백에 등록되면 메모리 누수의 사슬이 된다.** `inner` 키워드 자체가 참조를 만들므로 "안 쓰니 안 붙잡는다"는 가정은 틀리다.

- **누수를 끊는 정공법은 `inner`를 nested로 바꿔 애초에 안 붙잡거나, 필요한 최소 값만 인자로 넘기고, 등록에는 반드시 해지 경로를 두는 것이다.** 약한 참조는 보조 수단이며 GC 특성에 의존한다([[43 - 동시성과 메모리 모델]]).

- **선언의 위치와 종류는 문법 취향이 아니라 가시성·캡처·수명을 결정하는 설계 행위다.** 중첩은 소속을, `inner`는 의존을, 지역/익명은 수명을 코드 구조로 말한다.

## 연결 노트

- [[21 - 클래스와 생성자]] — 하나의 클래스가 태어나는 순서(주 생성자·`init`)를 다룬다. 이 장은 그 클래스를 다른 선언의 몸통 안에 놓을 때 무엇이 달라지는지를 본다.
- [[28 - object와 companion - 싱글턴과 동반 객체]] — 이름 붙은 `object` 선언(싱글턴)의 정본. 이 장의 익명 객체(표현식)와 짝을 이루며 대조된다(M24).
- [[14 - 클로저와 캡처]] — 변수 캡처의 근본 원리(값이 아니라 변수, `var`의 `Ref` 래핑). 지역 클래스·익명 객체의 캡처가 이 원리를 그대로 재현한다.
- [[13 - 함수 타입과 람다와 함수 참조]] — 람다와 SAM 변환의 정본. 익명 객체를 언제 람다로 갈아탈 수 있는지의 경계를 여기와 나눠 소유한다.
- [[16 - 스코프 함수와 수신 객체 관용구]] — `this@apply` 같은 수신 객체 지정 람다의 레이블. 이 장의 `this@Outer`와 동일한 한정 규칙을 공유한다.
- [[26 - 가시성 한정자]] — `private`이 왜 중첩·이너 경계를 넘는지, 익명 객체 타입 노출이 왜 가시성에 달렸는지의 배경.
- [[25 - 인터페이스]] — `fun interface`와 SAM, 익명 객체가 여러 인터페이스를 동시에 구현하는 방식의 배경.
- [[30 - sealed 클래스와 대수적 데이터 타입]] — 봉인 계층의 변형을 중첩 선언으로 모으는 관용구가 이 장의 중첩 개념과 만난다.
- [[24 - 상속과 오버라이딩과 초기화 순서]] — `super@Outer`로 한정하는 상속, 그리고 `final` 기본값 같은 "안전한 기본값" 철학의 다른 사례.
- [[43 - 동시성과 메모리 모델]] — 8절의 누수·약한 참조·GC 사슬을 메모리 모델과 스레드 안전의 관점에서 더 깊이 다룬다.
