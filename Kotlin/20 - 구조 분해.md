**이 장이 답하는 질문:**

- `val (a, b) = pair`는 이름으로 필드를 꺼내는가, 아니면 위치로 꺼내는가?
- 구조 분해는 언어에 내장된 문법인가, 아니면 어떤 함수 호출로 번역되는 관례(convention)인가?
- data 클래스만 구조 분해할 수 있는가? 그렇다면 `Pair`, `Map.Entry`, `List`는 어떻게 분해되는가?
- `map { (k, v) -> ... }`의 람다는 파라미터가 두 개인가 하나인가?
- 프로퍼티 선언 순서를 바꾸면 왜 컴파일 에러 없이 프로그램이 조용히 틀린 값을 내놓는가?
- 언더스코어 `_`를 쓰면 정확히 무엇이 절약되는가?
- Kotlin의 구조 분해는 Scala·Rust의 패턴 매칭과 무엇이 결정적으로 다른가?
- 왜 중첩 구조 분해(`val ((a, b), c) = ...`)는 안 되는가?

---

앞의 [[19 - 연산자 오버로딩과 관례]]에서 우리는 Kotlin이 특정 이름(`plus`, `get`, `invoke`, `compareTo`…)의 함수를 특정 문법에 연결하는 **관례(convention)** 메커니즘을 해부했다. 연산자 오버로딩이 "정해진 이름의 함수만 정해진 기호에 대응된다"(M40)는 규칙 위에 서 있다는 것을 보았다. 이 장은 그 목록에서 아직 정면으로 다루지 않은 한 쌍의 관례 — `component1()`, `component2()`, `component3()`… — 을 확대경 아래 놓는다. 구조 분해(destructuring)는 새로운 문법처럼 보이지만, 실제로는 이 `componentN` 관례 함수들에 대한 **얇은 문법 설탕(syntactic sugar)**일 뿐이다. 이 사실 하나를 이해하면 구조 분해의 모든 능력과 모든 함정이 한꺼번에 설명된다.

이 장이 다루는 것은 좁고 명확하다. `val (a, b) = e`라는 선언이 무엇으로 번역되는가, 어떤 타입이 그 대상이 될 수 있는가, for 루프와 람다 파라미터에서 어떻게 나타나는가, 그리고 이 기능이 **위치 기반(positional)** 이기 때문에 생기는 특유의 조용한 버그가 무엇인가. 반대로 이 장이 다루지 *않는* 것도 분명히 해 두자. `componentN`을 자동으로 만들어 주는 data 클래스의 전체 계약은 [[27 - 데이터 클래스]]가 소유한다(equals/hashCode/copy 등). 구조 분해가 얹히는 람다·함수 타입의 본질은 [[13 - 함수 타입과 람다와 함수 참조]]가, for 루프의 이터레이터 기반 반복은 [[18 - 범위와 진행과 반복]]가, 읽기 전용 컬렉션의 계층은 [[38 - 컬렉션 - 읽기 전용과 가변]]가 소유한다. 이 장은 그 조각들이 `componentN`을 통해 어떻게 하나의 해체 문법으로 수렴하는지에 집중한다.

논증의 궤적은 이렇다. 먼저 구조 분해가 무엇이며 무엇이 아닌지를 못박고(패턴 매칭이 아니다, 이름 기반이 아니다), 그것을 구동하는 `componentN` 관례를 분해한 뒤, data 클래스가 이 함수들을 어떻게 자동 생성하는지 본다. 이어 `Pair`/`Triple`/`Map.Entry`/`List`/`Array` 같은 표준 라이브러리 타입에서의 실제 쓰임을 훑고, for 루프와 람다 파라미터라는 두 특수 문맥을 파고든 다음, 언더스코어를 통한 부분 해체를 다룬다. 마지막 두 절은 이 장의 무게 중심이다. 구조 분해가 이름이 아니라 **위치**에 의존한다는 사실이 어떻게 컴파일러가 잡아 주지 못하는 논리 버그를 낳는지, 그리고 커스텀 `componentN`을 손수 설계할 때 어떤 계약과 한계를 짊어지게 되는지를 정면으로 본다.

## 1. 구조 분해란 무엇인가 — 위치 기반 해체의 본질

### 1.1 선언 하나가 여러 지역 변수로

구조 분해 선언(destructuring declaration)은 하나의 객체를 여러 개의 지역 변수로 한 번에 풀어내는 문법이다. 가장 익숙한 형태는 이렇다.

```kotlin
data class Point(val x: Int, val y: Int)

val p = Point(10, 20)
val (x, y) = p        // 구조 분해 선언
println(x)            // => 10
println(y)            // => 20
```

겉보기에는 `p`의 `x` 필드를 `x`라는 변수에, `y` 필드를 `y`라는 변수에 넣는 것처럼 보인다. 하지만 이 인상은 절반만 맞고 절반은 위험하게 틀렸다. 컴파일러가 실제로 하는 일은 다음과 완전히 동등하다.

```kotlin
val x = p.component1()   // 첫 번째 위치
val y = p.component2()   // 두 번째 위치
```

즉 `x`, `y`라는 변수 이름은 아무 의미도 없다. 컴파일러는 왼쪽 괄호 안의 이름을 오른쪽 객체의 프로퍼티 이름과 대조하지 않는다. 그저 괄호 안 **첫 번째 자리**에 오는 변수에는 `component1()`의 결과를, **두 번째 자리**에는 `component2()`의 결과를 대입할 뿐이다. 이름을 바꿔 써도 결과는 똑같다.

```kotlin
val (banana, apple) = p
println(banana)   // => 10   (p.component1(), 즉 p.x)
println(apple)    // => 20   (p.component2(), 즉 p.y)
```

`banana`가 `x`를 받고 `apple`이 `y`를 받는다. 이름은 순전히 지역 변수를 부르는 라벨일 뿐, 어떤 필드에서 값을 가져올지 결정하지 못한다. **위치가 모든 것을 결정한다.** 이 한 문장이 이 장 전체를 관통하는 핵심이며, 8절에서 다룰 모든 함정의 뿌리다.

> **명세 정밀**: 구조 분해 선언 `val (a, b, …, n) = e`는 형식적으로 `val a = e.component1(); val b = e.component2(); …; val n = e.componentN()`으로 번역된다. `componentN()`은 `operator` 한정자가 붙은 함수여야 하며, 이 번역은 Kotlin 언어 명세에 명시된 결정론적 규칙이다. 오른쪽 표현식 `e`는 정확히 한 번만 평가된다(각 `componentN` 호출은 같은 `e` 값에 대해 이뤄진다).

### 1.2 무엇이 아닌가 — 패턴 매칭도, 이름 기반도 아니다

구조 분해를 처음 만나면 두 가지 다른 언어의 기능과 혼동하기 쉽다. 둘 다 명확히 선을 그어야 한다.

**첫째, 이것은 패턴 매칭(pattern matching)이 아니다.** Scala의 `case Point(x, y) =>`나 Rust의 `let Point { x, y } = p`, 혹은 `match` 표현식은 값의 *모양을 검사*하면서 동시에 바인딩한다. 어떤 생성자로 만들어졌는지 판별하고, 조건에 따라 분기하고, 실패하면 다음 case로 넘어간다. Kotlin의 구조 분해에는 그런 검사가 전혀 없다. `val (x, y) = p`는 언제나 성공하거나(=componentN이 존재하면) 아예 컴파일되지 않거나(=존재하지 않으면) 둘 중 하나다. "이 값이 Point 모양이면 분해하고 아니면 다른 걸 시도"라는 조건부 의미가 없다. Kotlin은 타입 판별과 분기를 `when`(is 검사)과 [[30 - sealed 클래스와 대수적 데이터 타입]]의 완전성(exhaustiveness) 검사에 맡기고, 값의 해체는 구조 분해에 맡긴다. 이 둘은 분리되어 있다.

```kotlin
sealed interface Shape
data class Circle(val radius: Double) : Shape
data class Rectangle(val w: Double, val h: Double) : Shape

fun area(s: Shape): Double = when (s) {
    // 타입 검사(is)와 스마트 캐스트는 when이 담당.
    is Circle -> {
        val (r) = s          // 구조 분해는 이미 Circle로 좁혀진 뒤에만 가능
        Math.PI * r * r
    }
    is Rectangle -> {
        val (w, h) = s
        w * h
    }
}
```

Scala라면 `case Circle(r) => ...`처럼 판별과 분해를 한 줄에서 했겠지만, Kotlin은 `is Circle`로 먼저 좁히고(그러면 스마트 캐스트가 `s`를 `Circle`로 취급), 그 안에서 `val (r) = s`로 분해한다. 판별과 해체가 별개의 단계다.

**둘째, 이것은 이름 기반 구조 분해가 아니다.** JavaScript의 객체 구조 분해 `const { x, y } = p`는 이름으로 프로퍼티를 찾는다. `const { y, x } = p`라고 순서를 바꿔 써도 `y`는 `p.y`를, `x`는 `p.x`를 정확히 받는다. 이름이 곧 키다. Kotlin은 정반대다. 앞서 봤듯 `val (y, x) = p`라고 쓰면 `y`라는 변수가 `component1()`(=첫 번째 프로퍼티)을 받는다. 이름이 우연히 `y`일 뿐, 값은 첫 번째 위치의 것이다.

```javascript
// JavaScript — 이름 기반
const p = { x: 10, y: 20 };
const { y, x } = p;   // y === 20, x === 10  (이름으로 매칭)
```

```kotlin
// Kotlin — 위치 기반
val p = Point(x = 10, y = 20)
val (y, x) = p        // y == 10 (component1=x), x == 20 (component2=y) — 헷갈림 유발!
```

같은 `{ y, x }` / `(y, x)` 표기가 두 언어에서 정반대로 동작한다. JavaScript에 익숙한 개발자가 Kotlin에서 가장 자주 데는 지점이 바로 이 차이다. 8.3절에서 이름 기반의 부재와 그 미래 계획을 다시 다룬다.

> **흔한 오해**: "구조 분해의 괄호 안 이름은 대상 객체의 프로퍼티 이름과 일치해야 한다." 아니다. 이름은 자유다. `val (첫째, 둘째) = point`처럼 아무 이름이나 쓸 수 있고, 컴파일러는 오직 위치만 본다. 이름을 프로퍼티와 똑같이 쓰는 것은 순전히 **가독성을 위한 규율**일 뿐 언어가 강제하는 규칙이 아니다.

### 1.3 어디서 쓸 수 있고 어디서 못 쓰는가

구조 분해 선언은 아무 데서나 쓸 수 있는 게 아니다. 세 가지 문맥에서만 허용된다.

1. **지역 변수 선언** (함수 본문, `init` 블록, 다른 지역 스코프 안):

```kotlin
fun process() {
    val (name, age) = getPerson()   // OK — 지역 변수
    // ...
}
```

2. **for 루프의 루프 변수**:

```kotlin
for ((index, value) in list.withIndex()) { /* ... */ }   // OK
```

3. **람다 파라미터**:

```kotlin
map.forEach { (key, value) -> /* ... */ }                // OK
```

반면 다음 위치에서는 구조 분해를 **쓸 수 없다.**

```kotlin
// 클래스/최상위 프로퍼티로는 불가
class Container {
    val (a, b) = getPair()   // 컴파일 에러: 구조 분해는 프로퍼티 선언에 못 쓴다
}

// 최상위(파일 레벨)에서도 불가
val (x, y) = Point(1, 2)     // 컴파일 에러 (지역 스코프가 아님)

// 일반 함수 파라미터로는 불가 (람다 파라미터만 가능)
fun draw(point: (x, y)) { }  // 문법 에러

// 대입만으로는 불가 — 반드시 val/var 선언이어야
var a = 0; var b = 0
(a, b) = getPair()           // 컴파일 에러: 이런 대입 문법 없음
```

특히 마지막이 중요하다. 파이썬이나 JavaScript에는 이미 존재하는 변수에 구조 분해로 *재대입*하는 문법(`[a, b] = f()`)이 있지만, Kotlin에는 없다. 구조 분해는 항상 **새 변수를 선언**하는 것이며, 반드시 `val` 또는 `var` 키워드로 시작해야 한다. 이는 [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 본 Kotlin의 선언/대입 구분을 그대로 따른다.

`var`로 선언하면 각 변수는 개별적으로 재대입 가능한 지역 변수가 된다.

```kotlin
var (count, label) = 0 to "empty"
count = 5           // OK — count는 var
label = "filled"    // OK
```

하지만 실무에서 `var` 구조 분해는 드물다. 대부분은 값을 꺼내 읽기만 하므로 `val`이 자연스럽다.

## 2. componentN 관례 — 구조 분해의 엔진

### 2.1 operator fun componentN()

1절에서 구조 분해가 `componentN()` 호출로 번역된다고 했다. 이제 그 함수 자체를 들여다보자. 어떤 타입을 구조 분해하려면, 그 타입에 다음 형태의 함수가 있어야 한다.

```kotlin
operator fun component1(): T1
operator fun component2(): T2
operator fun component3(): T3
// ...
```

세 가지 요구 조건이 있다.

- **이름이 정확히 `componentN`** 이어야 한다(N은 1부터 시작하는 연속된 양의 정수). `component0`이나 `getFirst` 같은 이름은 구조 분해에 쓰이지 않는다.
- **`operator` 한정자**가 붙어야 한다. 이는 [[19 - 연산자 오버로딩과 관례]]에서 본 것과 같은 규칙이다. `operator`가 없으면 그냥 평범한 함수이며 구조 분해 대상이 되지 못한다.
- **파라미터가 없어야** 한다(수신 객체만으로 값을 계산). 반환 타입은 자유다.

이 세 조건은 M40 — "연산자 오버로딩은 정해진 관례 이름만 가능하다"는 진실 — 의 직접적 사례다. `componentN`은 임의 이름이 아니라 언어가 예약한 관례 함수 목록의 일원이다. 컴파일러는 이 정확한 이름과 `operator` 표식을 보고 나서야 괄호 문법을 그 함수 호출로 번역한다.

```kotlin
class NameParts(fullName: String) {
    private val parts = fullName.split(" ")
    operator fun component1(): String = parts.getOrElse(0) { "" }
    operator fun component2(): String = parts.getOrElse(1) { "" }
}

val (first, last) = NameParts("Ada Lovelace")
println(first)   // => Ada
println(last)    // => Lovelace
```

`NameParts`는 data 클래스가 아니고, 프로퍼티조차 `parts` 하나뿐이다. 그럼에도 구조 분해가 되는 이유는 오직 `operator fun component1/2()`를 손수 정의했기 때문이다. 이것이 구조 분해의 진짜 정체다. data 클래스는 이 함수들을 자동으로 만들어 줄 뿐, 구조 분해 자체는 data 클래스에 묶인 기능이 아니다.

### 2.2 디슈가링: (a, b) = e → component1()/component2()

컴파일러의 번역(desugaring)을 다이어그램으로 못박아 보자.

```text
원본 소스                          컴파일러가 번역한 형태
─────────────────────────         ──────────────────────────────
val (a, b) = e             ─────►  val tmp = e            (e를 한 번만 평가)
                                   val a = tmp.component1()
                                   val b = tmp.component2()

val (a, b, c) = e          ─────►  val tmp = e
                                   val a = tmp.component1()
                                   val b = tmp.component2()
                                   val c = tmp.component3()
```

여기서 세 가지 미묘한 점이 드러난다.

**첫째, `e`는 한 번만 평가된다.** `e`가 부수 효과가 있는 표현식(예: 카운터를 증가시키는 함수 호출)이라도, 그 표현식은 딱 한 번 실행되고 그 결과에 대해 `component1()`, `component2()`가 호출된다.

```kotlin
var calls = 0
fun makePair(): Pair<Int, Int> { calls++; return 1 to 2 }

val (a, b) = makePair()
println(calls)   // => 1  (makePair는 한 번만 호출됨)
```

**둘째, 각 `componentN`은 별도의 함수 호출이다.** 구조 분해는 무료가 아니다. 각 변수마다 실제 메서드 호출이 일어난다(인라인되지 않는 한). data 클래스의 `componentN`은 대개 단순 필드 접근으로 컴파일되고 JIT이 인라인하므로 비용이 거의 없지만, 커스텀 `componentN`이 무거운 계산을 한다면 그 비용이 그대로 반복된다.

**셋째, 타입을 명시할 수 있다.** 각 변수에 타입 주석을 달 수 있으며, 이는 해당 `componentN`의 반환 타입과 호환되어야 한다.

```kotlin
val (x: Int, y: Int) = Point(3, 4)     // 타입 명시
val (name: String, age: Int) = getPerson()
```

타입을 명시하면 오독을 줄일 수 있지만, 잘못 쓰면 컴파일 에러로 잡힌다(예: `component1()`이 `String`을 반환하는데 `Int`로 선언하면 에러).

### 2.3 arity와 순서, trailing 생략

구조 분해로 요청하는 변수 개수(arity)와 대상 타입이 제공하는 `componentN`의 개수 사이에는 규칙이 있다.

**요청한 개수만큼의 `componentN`이 존재해야** 한다. `n`개의 변수를 요청하면 `component1()`부터 `componentN()`까지가 모두 있어야 한다. 하나라도 없으면 컴파일 에러다.

```kotlin
val pair = 1 to 2                  // Pair는 component1, component2만 있음

val (a, b) = pair                  // OK
val (a, b, c) = pair               // 컴파일 에러: component3()이(가) 없음
```

**반대로, 제공되는 것보다 적게 요청하는 것은 허용된다** — 단 앞에서부터의 연속된 접두(prefix)여야 한다. 3개의 컴포넌트를 가진 타입에서 앞 2개만 꺼낼 수 있다.

```kotlin
data class Rgb(val r: Int, val g: Int, val b: Int)
val color = Rgb(255, 128, 0)

val (red, green) = color           // OK — component1, component2만 호출. component3(b)은 무시
println(red)                       // => 255
println(green)                     // => 128
```

"뒤쪽(trailing)을 생략"하는 것은 되지만, "중간을 건너뛰기"는 위치를 밀 수 없으므로 그냥은 안 된다. 두 번째만 빼고 첫째·셋째를 원한다면 언더스코어를 써야 한다(7절).

이 규칙에서 중요한 결론이 나온다. **구조 분해는 항상 왼쪽(component1)부터 순서대로 채워진다.** `(a, b)`에서 `a`는 반드시 `component1`, `b`는 반드시 `component2`다. 이 순서는 언어가 고정한 것이며 바꿀 방법이 없다. 뒤에서 볼 위치 기반 함정의 원인이 바로 이 고정된 순서다.

### 2.4 확장 componentN

`componentN`은 반드시 클래스의 멤버일 필요가 없다. **확장 함수([[35 - 확장 함수와 프로퍼티]])** 로도 정의할 수 있다. 이 사실은 표준 라이브러리가 `List`나 `Array`처럼 우리가 소유하지 않은 타입에 구조 분해 능력을 부여하는 방식을 설명한다.

```kotlin
// 우리가 만들지 않은 표준 타입에 구조 분해를 확장으로 추가
class Vector3(val values: DoubleArray)

operator fun Vector3.component1() = values[0]
operator fun Vector3.component2() = values[1]
operator fun Vector3.component3() = values[2]

val v = Vector3(doubleArrayOf(1.0, 2.0, 3.0))
val (x, y, z) = v
println("$x $y $z")   // => 1.0 2.0 3.0
```

확장 `componentN`은 다른 확장 함수와 똑같이 **정적 디스패치**되고(M14), import 스코프에 있어야 사용 가능하다. 표준 라이브러리는 바로 이 방식으로 `List<T>`에 `component1()`부터 `component5()`까지, `Array<T>`에도 마찬가지로 확장 연산자를 정의해 두었다. 그래서 임의의 리스트를 (앞 다섯 개까지) 구조 분해할 수 있는 것이다(4절, 5절에서 다룸).

> **성능 주의**: 확장 `componentN`은 정적 메서드로 컴파일되며 수신 객체를 첫 인자로 받는다. data 클래스의 멤버 `componentN`이 단순 필드 반환이라 JIT이 쉽게 인라인하는 것과 달리, 확장 컴포넌트가 매번 배열 인덱싱이나 컬렉션 순회를 한다면(예: `LinkedList`에서 `component3()`이 O(3) 순회) 숨은 비용이 생긴다. `List.component5()`가 다섯 번째 원소를 가져오는 것은 `RandomAccess` 리스트에선 싸지만 연결 리스트에선 그렇지 않다.

## 3. data 클래스와 자동 생성 (M21 참조)

### 3.1 주 생성자 프로퍼티만 componentN

실무에서 구조 분해를 쓰는 압도적 다수의 경우는 data 클래스를 대상으로 한다. 그 이유는 명확하다. data 클래스는 컴파일러가 `componentN` 함수들을 **자동으로 생성**해 주기 때문이다. [[27 - 데이터 클래스]]가 이 자동 생성의 전체 계약(equals/hashCode/toString/copy/componentN)을 소유하지만, 구조 분해와 직결되는 부분은 여기서 정확히 짚어야 한다.

핵심 규칙은 **주 생성자(primary constructor)에 선언된 프로퍼티만** `componentN`으로 노출된다는 것이다. 이것이 바로 M21 — "data 클래스는 완전한 값 타입이 아니며, 주 생성자 프로퍼티만 equals/hashCode/toString/copy/componentN에 참여한다" — 의 구조 분해 측면이다.

```kotlin
data class Account(
    val id: Long,          // 주 생성자 프로퍼티 → component1()
    val balance: Int       // 주 생성자 프로퍼티 → component2()
) {
    var lastAccessed: Long = 0L    // 본문(body) 프로퍼티 → componentN 없음!
}

val acc = Account(1L, 5000).apply { lastAccessed = 99L }

val (id, balance) = acc            // OK
println("$id $balance")            // => 1 5000

val (id2, balance2, last) = acc    // 컴파일 에러: component3()이 없음
                                   // lastAccessed는 componentN에 참여하지 않음
```

`lastAccessed`는 엄연히 `Account`의 프로퍼티지만, 주 생성자가 아니라 클래스 본문에 선언됐으므로 `component3()`이 생성되지 않는다. 구조 분해로는 절대 꺼낼 수 없다. 오직 `acc.lastAccessed`처럼 이름으로 접근해야 한다.

### 3.2 body 프로퍼티는 제외되는 이유

왜 본문 프로퍼티는 제외될까? 이것은 버그가 아니라 의도된 설계다. data 클래스가 자동 생성하는 것들(equals, hashCode, copy, componentN)은 모두 "이 객체를 구성하는 **핵심 데이터가 무엇인가**"라는 하나의 정의에 근거한다. 그 핵심 데이터는 주 생성자 파라미터로 못박힌다. 주 생성자는 "이 객체를 만들려면 이 값들이 필요하다"는 계약이므로, Kotlin은 그것을 객체의 정체성(identity)으로 삼는다.

본문 프로퍼티는 흔히 파생 상태(derived state)나 캐시, 가변 부가 정보다. `lastAccessed` 같은 값을 equals나 componentN에 넣으면 오히려 문제가 된다. 두 계정이 잔액과 id가 같은데 마지막 접근 시각만 다르다고 서로 "다른 계정"이 되면 곤란하다. Kotlin은 이 판단을 개발자에게 강제로 떠넘기지 않고, "주 생성자에 넣으면 정체성, 본문에 넣으면 부가 상태"라는 단순한 규칙으로 갈랐다.

이 규칙의 실용적 함의는 이렇다. **구조 분해로 꺼내고 싶은 값은 주 생성자에 두어야 한다.** 만약 어떤 파생값을 구조 분해에 포함시키고 싶다면, 주 생성자 프로퍼티로 만들거나(계산해서 넣거나) 커스텀 `componentN`을 손수 추가해야 한다(9절).

```kotlin
data class Segment(val start: Point, val end: Point) {
    // 본문 프로퍼티는 componentN에 없음. 구조 분해하려면 커스텀 추가.
    val length: Double get() = hypot(
        (end.x - start.x).toDouble(), (end.y - start.y).toDouble()
    )
    operator fun component3(): Double = length   // 손수 추가하면 3항 분해 가능
}

val seg = Segment(Point(0, 0), Point(3, 4))
val (s, e, len) = seg
println(len)   // => 5.0
```

여기서 `component1()`, `component2()`는 컴파일러가 `start`, `end`로 자동 생성하고, `component3()`만 우리가 `length`에 연결했다. 자동 생성과 수동 정의가 공존할 수 있다.

### 3.3 순서 = 선언 순서

data 클래스가 생성하는 `componentN`의 번호는 **주 생성자에 프로퍼티가 선언된 순서**를 그대로 따른다. 첫 번째 프로퍼티가 `component1`, 두 번째가 `component2`… 이 매핑은 프로퍼티 *이름*과 무관하며 오직 *선언 순서*에 달렸다.

```kotlin
data class Coordinate(val latitude: Double, val longitude: Double)
//                        ↑ component1()        ↑ component2()

val seoul = Coordinate(37.5665, 126.9780)
val (lat, lng) = seoul   // lat = latitude, lng = longitude
```

`latitude`가 첫 번째로 선언됐으므로 `component1()`이 되고, `val (lat, lng)`에서 `lat`이 그 값을 받는다. 여기까지는 자연스럽다. 문제는 누군가 나중에 이 클래스의 선언 순서를 바꿀 때 발생한다 — 이것이 8절의 주제이며, data 클래스의 자동 생성이 편리한 만큼 위험한 이유다.

> **명세 정밀**: data 클래스의 `componentN`은 `public operator`로 생성되며, 주 생성자의 `val`/`var` 프로퍼티에 대해서만 만들어진다. 주 생성자 파라미터 중 `val`/`var`가 아닌 순수 파라미터(예: `data class D(val a: Int, b: Int)`의 `b`)는 프로퍼티가 아니므로 `componentN`에 포함되지 않는다 — 사실 data 클래스는 모든 주 생성자 파라미터가 `val`/`var`여야 하므로 이 상황 자체가 컴파일 에러다. 즉 data 클래스에서는 "주 생성자 파라미터 = 프로퍼티 = componentN"이 항상 일치한다.

## 4. Pair·Triple·표준 라이브러리

### 4.1 Pair/Triple의 componentN

Kotlin 표준 라이브러리는 구조 분해를 위해 두 개의 범용 튜플 타입을 제공한다. `Pair<A, B>`와 `Triple<A, B, C>`다. 둘 다 data 클래스로 정의되어 있어 `componentN`을 자동으로 갖는다.

```kotlin
// stdlib 정의(개념)
public data class Pair<out A, out B>(
    public val first: A,
    public val second: B
)
public data class Triple<out A, out B, out C>(
    public val first: A,
    public val second: B,
    public val third: C
)
```

`Pair`는 `component1()`(=first), `component2()`(=second)를, `Triple`은 거기에 `component3()`(=third)까지 갖는다. 그래서 함수가 여러 값을 반환할 때 흔히 이렇게 쓴다.

```kotlin
fun minMax(numbers: List<Int>): Pair<Int, Int> {
    return numbers.min() to numbers.max()
}

val (lo, hi) = minMax(listOf(3, 1, 4, 1, 5, 9))
println("$lo..$hi")   // => 1..9
```

여러 값을 돌려주고 싶을 때 별도의 결과 클래스를 만들 필요 없이 `Pair`/`Triple`로 묶어 반환하고 호출부에서 구조 분해로 푸는 것이 관용구다.

### 4.2 왜 Triple에서 멈추는가

표준 라이브러리에는 `Pair`(2항)와 `Triple`(3항)만 있고 `Quadruple`(4항)이나 그 이상은 **없다.** 이것은 누락이 아니라 의도적 설계 결정이다.

이유는 위치 기반 구조 분해의 근본적 취약성에 있다. 익명 튜플의 원소가 2~3개일 때는 `(lo, hi)`, `(x, y, z)`처럼 사람이 위치를 머릿속에 담을 수 있다. 하지만 4개를 넘어가면 "세 번째가 무엇이었더라?"를 기억하기 어려워지고, 8절에서 볼 위치 혼동 버그의 위험이 급격히 커진다. 그래서 Kotlin은 4개 이상의 값을 묶어야 한다면 **이름 있는 프로퍼티를 가진 data 클래스를 정의하라**고 유도한다.

```kotlin
// 나쁨(존재하지도 않음): 익명의 4-튜플. 위치를 기억해야 함
// val (a, b, c, d) = quadrupleOf(...)   // Quadruple 없음

// 좋음: 의미가 이름에 담긴 data 클래스
data class ParsedUrl(
    val scheme: String,
    val host: String,
    val port: Int,
    val path: String
)

fun parse(raw: String): ParsedUrl { /* ... */
    return ParsedUrl("https", "example.com", 443, "/index")
}

val url = parse("...")
println(url.host)   // 이름으로 접근 — 위치 기억 불필요
val (scheme, host, port, path) = url   // 원하면 구조 분해도 가능(단 여전히 위치 기반)
```

`Pair`/`Triple`은 "지역적이고 즉시 풀 짧은 쌍/삼중"을 위한 도구이고, 그 이상은 data 클래스로 가라는 것이 표준 라이브러리의 무언의 조언이다.

> **역사 메모**: `Pair`/`Triple`의 `to` 중위 함수(`1 to 2`)는 Kotlin 초기부터 있었고, 이 조합이 맵 리터럴 관용구 `mapOf("a" to 1, "b" to 2)`의 기반이다. `to`는 `infix fun <A, B> A.to(that: B): Pair<A, B>`로 정의된 확장 중위 함수일 뿐, 특별한 문법이 아니다([[19 - 연산자 오버로딩과 관례]]의 infix). 즉 `1 to 2`는 `1.to(2)`이고 결과는 `Pair(1, 2)`이며, 이것을 구조 분해하면 `component1/2`가 호출된다.

### 4.3 List와 Array의 구조 분해

앞서 2.4절에서 언급했듯, 표준 라이브러리는 `List`와 `Array`에도 확장 `componentN`을 제공한다 — 단 **`component1()`부터 `component5()`까지, 다섯 개만**이다.

```kotlin
// stdlib가 제공하는 확장(개념)
public operator fun <T> List<T>.component1(): T = get(0)
public operator fun <T> List<T>.component2(): T = get(1)
// ... component5까지

val list = listOf(10, 20, 30, 40, 50, 60)
val (a, b, c) = list         // OK — 앞 세 개
println("$a $b $c")          // => 10 20 30

val (p, q, r, s, t, u) = list  // 컴파일 에러: component6()이 없음
```

여기에 두 가지 함정이 숨어 있다.

**첫째, 원소 개수를 검사하지 않는다.** `val (a, b, c) = list`는 리스트에 원소가 최소 3개 있다고 *가정*할 뿐, 검사하지 않는다. 리스트가 더 짧으면 런타임에 `IndexOutOfBoundsException`이 터진다.

```kotlin
val short = listOf(1, 2)
val (a, b, c) = short   // 컴파일은 됨! 런타임에 component3() → get(2) → 예외
// 실행 시: IndexOutOfBoundsException: Index 2 out of bounds for length 2
```

data 클래스나 `Pair`는 컴포넌트 개수가 타입 수준에서 고정되어 있어 이런 일이 없지만, 리스트는 길이가 타입에 담기지 않으므로 컴파일러가 막아 주지 못한다. `List` 구조 분해는 이래서 위험하며, 실무에서는 대개 피하는 편이 낫다.

**둘째, `List`는 이름이 없으므로 순수하게 위치에만 의존한다.** `val (first, second) = coordinates`에서 `first`가 x인지 y인지는 오직 리스트를 만든 쪽의 관례에 달렸다. 이것은 data 클래스보다도 취약하다.

`Array`도 동일하게 `component1()`~`component5()` 확장을 가진다. 원시 배열(`IntArray`, `DoubleArray` 등)도 각각 대응하는 확장 컴포넌트를 갖는다.

```kotlin
val point = intArrayOf(3, 4)
val (x, y) = point   // IntArray.component1(), component2()
println("$x $y")     // => 3 4
```

`Array`가 `List`와 별개 타입이라는 사실(M43)은 [[38 - 컬렉션 - 읽기 전용과 가변]]이 소유하지만, 구조 분해 관점에서는 둘 다 "5개까지, 길이 검사 없음"이라는 같은 성질을 공유한다.

## 5. Map과 for 루프 구조 분해

### 5.1 Map.Entry의 component1/2

구조 분해가 가장 빛나는 곳 중 하나가 맵 순회다. `Map<K, V>`를 순회하면 각 원소는 `Map.Entry<K, V>` 타입이고, 표준 라이브러리는 이 `Entry`에 확장 `componentN`을 정의해 두었다.

```kotlin
// stdlib 확장(개념)
public operator fun <K, V> Map.Entry<K, V>.component1(): K = key
public operator fun <K, V> Map.Entry<K, V>.component2(): V = value
```

`component1()`은 **키**, `component2()`는 **값**이다. 이 순서는 외워 둘 가치가 있다(키가 먼저, 값이 나중). 덕분에 맵을 순회할 때 엔트리를 키와 값으로 곧장 풀 수 있다.

```kotlin
val ages = mapOf("Alice" to 30, "Bob" to 25)

for (entry in ages) {
    val (name, age) = entry     // entry.component1()=key, component2()=value
    println("$name is $age")
}
// => Alice is 30
// => Bob is 25
```

### 5.2 for ((k, v) in map)

위 예제는 더 간결하게 쓸 수 있다. for 루프의 루프 변수 자리에서 바로 구조 분해할 수 있기 때문이다.

```kotlin
for ((name, age) in ages) {
    println("$name is $age")
}
```

이것은 완전히 등가이며, 컴파일러는 이렇게 번역한다.

```text
for ((name, age) in ages) { body }
        │
        ▼  번역
for (entry in ages) {              // ages를 이터레이트 → Map.Entry
    val name = entry.component1()  // = entry.key
    val age  = entry.component2()  // = entry.value
    body
}
```

for 루프의 구조 분해는 [[18 - 범위와 진행과 반복]]에서 본 이터레이터 기반 반복 위에 얹힌다. `ages`를 순회해 각 `Entry`를 얻고, 그 `Entry`를 `componentN`으로 푼다. 이 두 관례(`iterator`/`hasNext`/`next`와 `componentN`)의 조합이 `for ((k, v) in map)`이라는 깔끔한 문법을 만든다.

주의할 점 하나. **여기서도 위치가 이름을 지배한다.** `for ((k, v) in map)`에서 첫 변수는 언제나 키, 둘째는 언제나 값이다. 실수로 `for ((value, key) in map)`이라고 쓰면 `value`라는 변수에 실제로는 키가 담긴다.

```kotlin
for ((value, key) in ages) {   // 이름을 거꾸로 붙인 흔한 실수
    println("$value = $key")   // value엔 이름(키)이, key엔 나이(값)가 들어감!
}
// => Alice = 30   (이름이 value에, 나이가 key에 — 완전히 헷갈림)
```

컴파일러는 이것을 잡아 주지 못한다. 문법적으로 완벽히 유효하기 때문이다.

### 5.3 withIndex·indices·그 외

인덱스와 값을 함께 순회할 때도 구조 분해가 관용구다. `Iterable.withIndex()`는 `IndexedValue<T>`(data 클래스)를 방출하고, 이것은 `component1()`(=index), `component2()`(=value)를 갖는다.

```kotlin
val fruits = listOf("apple", "banana", "cherry")

for ((index, fruit) in fruits.withIndex()) {
    println("$index: $fruit")
}
// => 0: apple
// => 1: banana
// => 2: cherry
```

여기서도 순서를 기억하자 — **인덱스가 먼저, 값이 나중**이다(`Map.Entry`의 키/값 순서와 개념적으로 일관된다: "위치 식별자가 먼저"). `IndexedValue`의 정의를 보면 명확하다.

```kotlin
public data class IndexedValue<out T>(public val index: Int, public val value: T)
//                                          ↑ component1        ↑ component2
```

C 스타일 for 루프(`for (int i = 0; ...)`)가 없는 Kotlin([[18 - 범위와 진행과 반복]])에서 인덱스가 필요할 때 `withIndex()` + 구조 분해가 가장 관용적인 대체다.

`associateBy`, `groupBy`, `partition` 같은 컬렉션 연산([[39 - 컬렉션 연산과 함수형 파이프라인]])의 결과도 종종 구조 분해로 푼다. 특히 `partition`은 조건을 만족/불만족하는 두 리스트의 `Pair`를 반환하므로 구조 분해가 자연스럽다.

```kotlin
val numbers = listOf(1, 2, 3, 4, 5, 6)
val (evens, odds) = numbers.partition { it % 2 == 0 }
println(evens)   // => [2, 4, 6]
println(odds)    // => [1, 3, 5]
```

`partition`이 `Pair<List<T>, List<T>>`를 반환하고, 첫 번째가 술어를 만족하는 것들, 두 번째가 불만족하는 것들이다 — 또 하나의 위치 관례다.

## 6. 람다 파라미터 구조 분해 (M42 참조)

### 6.1 하나의 파라미터를 해체 — Function2가 아니다

구조 분해가 가장 오해받는 문맥이 람다 파라미터다. 다음 코드를 보자.

```kotlin
val ages = mapOf("Alice" to 30, "Bob" to 25)

ages.forEach { (name, age) ->
    println("$name: $age")
}
```

`{ (name, age) -> ... }`를 보면 파라미터가 두 개인 람다처럼 보인다. **하지만 아니다.** 이것은 파라미터가 **하나**인 람다이며, 그 하나의 파라미터(`Map.Entry`)를 구조 분해한 것이다. 괄호 `( )`가 바로 "이 하나의 파라미터를 componentN으로 풀어라"는 표시다.

이 차이는 [[13 - 함수 타입과 람다와 함수 참조]]에서 다루는 함수 타입의 arity와 직결된다. `forEach`가 받는 것은 `(Map.Entry<K, V>) -> Unit`, 즉 **1-인자** 함수 타입이다. 만약 파라미터가 정말 둘이라면 `(K, V) -> Unit`이어야 하는데 그렇지 않다.

이 사실은 M42 — "`it`은 단일 파라미터 람다의 암시적 이름일 뿐" — 과 연결된다. 람다의 파라미터가 하나이므로, 구조 분해 없이도 `it`으로 접근할 수 있다.

```kotlin
// 아래 세 람다는 모두 파라미터가 '하나'다
ages.forEach { it -> println("${it.key}: ${it.value}") }   // it = Entry
ages.forEach { entry -> println("${entry.key}: ${entry.value}") }  // 이름 붙임
ages.forEach { (name, age) -> println("$name: $age") }     // 구조 분해
```

셋 다 동일한 1-인자 람다다. 마지막이 그 하나의 인자를 두 지역 변수로 푼 것뿐이다.

### 6.2 map { (k, v) -> } 디슈가링

컴파일러의 번역을 보면 이 "하나의 파라미터" 성질이 분명해진다.

```text
ages.map { (k, v) -> "$k=$v" }
        │
        ▼  번역
ages.map { entry ->                    // 파라미터는 여전히 하나(entry)
    val k = entry.component1()
    val v = entry.component2()
    "$k=$v"
}
```

구조 분해는 람다 본문의 맨 앞에 `val k = ...; val v = ...`를 삽입하는 것과 같다. 파라미터 개수는 변하지 않는다.

JVM 백엔드에서 이 람다는 `Function1`(1-인자 함수 인터페이스)을 구현하는 객체로 컴파일된다. 만약 파라미터가 진짜 두 개였다면 `Function2`가 됐을 것이다. 이 표현 차이는 SAM 변환이나 함수 참조와 상호작용할 때 드러난다.

한 걸음 더. 람다는 여러 파라미터를 가질 수 있고, 그중 일부만 구조 분해할 수도 있다.

```kotlin
// fold의 람다는 2-인자: (누적값, 원소). 두 번째만 구조 분해
val points = listOf(Point(1, 2), Point(3, 4), Point(5, 6))
val sumX = points.fold(0) { acc, (x, _) -> acc + x }
//                          ↑    ↑ 이 파라미터(Point)를 구조 분해, y는 무시(_)
println(sumX)   // => 9  (1+3+5)
```

여기서 람다는 파라미터가 둘이다(`acc`와 `Point`). 첫 번째 `acc`는 그대로 두고, 두 번째 파라미터만 `(x, _)`로 구조 분해했다. 이렇게 "여러 파라미터 중 특정 위치의 것만 해체"하는 것도 가능하다.

### 6.3 타입 명시와 함정

람다 파라미터 구조 분해에서도 각 컴포넌트에 타입을 명시할 수 있다.

```kotlin
ages.forEach { (name: String, age: Int) ->
    println("$name: $age")
}
```

그러나 여기엔 미묘한 함정이 있다. 구조 분해 괄호를 쓰면 파라미터 **전체의 타입**을 명시할 자리가 사라진다. 즉 `Map.Entry<String, Int>` 자체를 어디에 쓸지가 모호해지고, 각 컴포넌트 타입만 쓸 수 있다. 대부분은 타입 추론이 해결하지만, 추론이 안 되는 문맥에서는 구조 분해 대신 파라미터 이름을 명시하고 본문에서 풀어야 할 수 있다.

또 하나의 함정. 람다 파라미터 구조 분해는 **오직 componentN을 가진 타입**에서만 된다. 임의의 파라미터를 괄호로 감싼다고 다 되는 게 아니다.

```kotlin
listOf("a", "bb", "ccc").map { (c) -> c }
// 컴파일 에러: String에는 component1()이 없음(정확히는 CharSequence.component 없음)
```

`String`에는 `component1()`이 없으므로 구조 분해할 수 없다. 이것은 `List`나 `data class`처럼 컴포넌트를 제공하는 타입에서만 통한다.

> **흔한 오해**: "`{ (a, b) -> }`는 2-인자 람다다." 아니다. 1-인자 람다에서 그 인자를 두 조각으로 푼 것이다. 이 오해는 함수 타입 시그니처를 잘못 읽게 만들고, 특히 `Map`의 `forEach`가 `(Entry) -> Unit`을 받는 확장인지 `(K, V) -> Unit`을 받는 것인지 헷갈리게 한다. 실제로 `Map.forEach`(kotlin의 확장)는 `(Map.Entry<K, V>) -> Unit`을 받으며, `(k, v)`는 그 Entry를 구조 분해한 것이다. (반면 `Map`의 자바 `forEach(BiConsumer)`는 2-인자다 — 상호운용 시 혼동 주의.)

## 7. 언더스코어와 부분 해체

### 7.1 _ 로 componentN 호출 자체를 건너뛴다

구조 분해에서 어떤 위치의 값이 필요 없을 때, 그 자리에 밑줄(underscore) `_`을 쓸 수 있다. 그러면 그 위치에 지역 변수가 만들어지지 않는다.

```kotlin
data class Rgb(val r: Int, val g: Int, val b: Int)
val color = Rgb(255, 128, 0)

val (_, green, _) = color     // 첫째·셋째는 무시, 가운데만 꺼냄
println(green)                // => 128
```

여기서 중요한 최적화가 하나 있다. **언더스코어 위치의 `componentN()`은 아예 호출되지 않는다.** 위 예에서 `component1()`(r)과 `component3()`(b)은 호출조차 되지 않고, `component2()`(g)만 호출된다. 컴파일러는 언더스코어를 보면 그 컴포넌트 접근을 통째로 생략한다.

```text
val (_, green, _) = color
        │
        ▼  번역
val green = color.component2()      // component1(), component3()은 호출 안 함
```

이 최적화는 커스텀 `componentN`이 무거운 계산을 할 때 의미가 있다. `component1()`이 비싼 파싱을 하는데 그 값이 필요 없다면, `_`로 그 호출을 건너뛰어 실제 비용을 절약한다.

```kotlin
class Expensive {
    operator fun component1(): Int { println("계산 1"); return 1 }
    operator fun component2(): Int { println("계산 2"); return 2 }
}

val (_, second) = Expensive()   // "계산 2"만 출력됨. "계산 1"은 안 나옴
println(second)                 // => 2
// 출력: 계산 2 / 2
```

`component1()`의 부수 효과("계산 1")가 출력되지 않는 것을 보면 호출이 실제로 생략됐음을 확인할 수 있다.

### 7.2 trailing 생략 vs 중간 건너뛰기

두 가지 "건너뛰기"를 구분하자.

**뒤쪽(trailing) 생략**: 필요한 것보다 적게 요청하면 뒤쪽 컴포넌트는 자연히 호출되지 않는다(2.3절). `val (r, g) = color`는 `component3()`을 부르지 않는다. 이때는 언더스코어조차 필요 없다.

**중간(interior) 건너뛰기**: 앞이나 중간의 컴포넌트를 건너뛰고 뒤의 것을 원한다면, 위치를 밀 수 없으므로 반드시 언더스코어로 자리를 채워야 한다.

```kotlin
val (r, g, b) = color

val (r, g)      = color   // b 무시(trailing 생략) — 언더스코어 불필요
val (_, _, b)   = color   // r, g 무시(중간 건너뛰기) — 언더스코어 필수
val (r, _, b)   = color   // g만 무시 — 언더스코어로 자리 유지
```

`b`를 얻으려면 그것이 세 번째 위치임을 유지해야 하므로 앞의 두 자리를 `_, _`로 메워야 한다. 언더스코어가 없으면 `component3()`이 첫 번째 변수로 가 버릴 것이기 때문이다. **위치가 고정이라는 규칙**이 여기서도 지배한다.

### 7.3 성능·의도 표현

언더스코어의 두 가지 가치를 정리하면 이렇다.

**의도 표현**: `_`은 "이 값은 의도적으로 쓰지 않는다"를 코드로 선언한다. 쓰지 않는 변수에 `unused` 경고가 뜨는 것을 피하고, 읽는 사람에게 "여기 값이 있지만 관심 없다"를 명확히 전한다.

```kotlin
for ((_, count) in wordCounts) {   // 단어는 관심 없고 빈도만
    total += count
}
```

**성능**: 7.1절에서 봤듯 언더스코어 위치의 `componentN`은 호출을 생략한다. data 클래스의 컴포넌트는 대개 싸므로 성능 차이가 미미하지만, 커스텀·확장 컴포넌트가 무거운 경우엔 실질적 절약이 된다.

주의: 언더스코어는 하나의 구조 분해 선언 안에서 여러 개 쓸 수 있고(`val (_, _, x) = ...`), 각각 독립적으로 해당 위치를 건너뛴다. 다만 `_` 자체는 변수가 아니므로 나중에 참조할 수 없다. `_`이라는 이름의 지역 변수가 만들어지는 게 아니라, 그 위치가 통째로 사라지는 것이다.

> **역사 메모**: 구조 분해 선언에서의 언더스코어는 Kotlin 1.1(2017)에서 도입됐다. 같은 릴리스에서 람다 파라미터의 언더스코어(`{ _, value -> }` — 사용하지 않는 파라미터)도 함께 들어왔다. 둘은 표기가 같지만 다른 기능이다: 하나는 구조 분해 컴포넌트를 건너뛰고, 다른 하나는 람다 파라미터 자체를 익명화한다. 혼동하지 말 것.

## 8. 위치 기반의 함정 (핵심 위험)

이 장의 무게 중심이다. 구조 분해가 편리한 만큼 위험한 이유 — 그것이 이름이 아니라 **위치**에 의존한다는 사실 — 이 낳는 조용한 버그들을 정면으로 본다.

### 8.1 프로퍼티 재배치가 조용히 깨뜨린다

가장 악명 높은 함정이다. data 클래스의 `componentN`은 **선언 순서**를 따른다(3.3절). 그런데 이 순서는 리팩터링 중에 쉽게 바뀐다. 누군가 클래스를 정리하다가 프로퍼티 순서를 바꾸면, 그 클래스를 구조 분해하던 모든 호출부가 **컴파일 에러 없이 조용히 틀린 값을 받게** 된다.

```kotlin
// 버전 1
data class User(val name: String, val email: String)

val (name, email) = getUser()
sendMail(to = email, subject = "환영, $name 님")   // 정상 동작
```

이제 누군가 `User`의 필드 순서를 "알파벳 순으로 정리"한다고 바꿨다.

```kotlin
// 버전 2 — email이 앞으로 옴
data class User(val email: String, val name: String)

// 호출부는 그대로! 하지만 이제:
val (name, email) = getUser()
// name  = component1() = 이제 email 값!
// email = component2() = 이제 name 값!
sendMail(to = email, subject = "환영, $name 님")
// to에 사람 이름이, subject에 이메일 주소가 들어감 — 메일 발송 실패 또는 오발송
```

`name`이라는 변수에 실제로는 이메일이, `email`에는 이름이 담긴다. **타입이 둘 다 `String`이라 컴파일러가 전혀 눈치채지 못한다.** 프로그램은 멀쩡히 컴파일되고 실행되지만 논리가 완전히 뒤집혔다. 이런 버그는 런타임에, 그것도 종종 프로덕션에서야 발견된다.

이것이 위치 기반 구조 분해의 근본 위험이다. 같은 타입의 프로퍼티가 인접해 있을 때, 순서를 바꾸면 컴파일러의 안전망이 완전히 사라진다. data 클래스가 `componentN`을 편리하게 자동 생성해 주는 바로 그 편리함이, 이 취약성의 원천이다.

### 8.2 같은 타입 필드의 뒤바뀜

8.1이 리팩터링 시점의 문제라면, 이것은 애초에 코드를 쓸 때부터 생기는 문제다. 같은 타입의 값이 여럿일 때, 어느 위치가 무엇인지 헷갈려 처음부터 뒤바꿔 받는 것이다.

```kotlin
data class Range(val min: Int, val max: Int)

fun getTemperatureRange(): Range = Range(min = -5, max = 30)

// 위치를 헷갈려 거꾸로 받음
val (max, min) = getTemperatureRange()   // 이름은 max/min이지만 실제로는...
// max = component1() = -5  (실제 min!)
// min = component2() = 30  (실제 max!)
println("최고 $max, 최저 $min")   // => 최고 -5, 최저 30 (완전히 뒤바뀜)
```

컴파일러는 `max`라는 변수 이름과 `min` 프로퍼티를 대조하지 않으므로 이 실수를 잡지 못한다. 두 값이 모두 `Int`라 타입 검사도 무력하다.

**방어책**은 세 가지다.

첫째, 헷갈릴 소지가 있으면 **구조 분해를 쓰지 말고 이름으로 접근**한다. `val range = getTemperatureRange(); range.min; range.max`는 절대 뒤바뀌지 않는다. 이것이 가장 안전하다.

둘째, 구조 분해하는 즉시 변수 이름을 프로퍼티와 **정확히 일치**시키는 규율을 지킨다(`val (min, max) = ...`). 이름이 프로퍼티와 같으면 최소한 사람이 읽을 때 뒤바뀜을 알아챌 여지가 생긴다.

셋째, IDE가 제공하는 구조 분해 힌트(각 위치가 어느 프로퍼티인지 인레이 힌트로 표시)를 켜 둔다. 이건 언어가 아니라 도구의 보완이다.

> **성능 주의**: 위치 기반 함정을 피하려고 무조건 이름 접근만 쓰는 것도 극단이다. `for ((k, v) in map)`이나 `partition`의 `(pass, fail)`처럼 관례가 확립되어 오해 여지가 거의 없는 경우엔 구조 분해가 훨씬 읽기 좋다. 판단 기준은 "이 위치가 무엇인지 한눈에 명확한가"이다. 명확하면 구조 분해, 애매하면 이름 접근.

### 8.3 이름 기반 구조 분해의 부재 (미래 계획)

1.2절에서 봤듯 JavaScript는 이름 기반 구조 분해(`const { name, email } = user`)를 제공하고, 이는 위치 함정을 원천 차단한다. 이름으로 매칭하므로 프로퍼티 순서가 바뀌어도 아무 영향이 없다. Kotlin은 2.x stable 기준으로 **오직 위치 기반만** 지원한다.

Kotlin 팀은 이 한계를 인지하고 있으며, 이름 기반(또는 프로퍼티 이름 기반) 구조 분해가 언어 진화의 논의 대상으로 오랫동안 다뤄져 왔다. 그러나 **집필 시점(Kotlin 2.x stable)에서 이름 기반 구조 분해는 안정 기능이 아니다.** 미래에 형태가 어떻게 될지, 실제로 도입될지는 확정되지 않았으므로, 현재 코드는 위치 기반이 유일한 현실이라고 가정하고 작성해야 한다.

지금 이름 기반의 안전성을 흉내 내려면, 구조 분해를 포기하고 명시적 프로퍼티 접근을 쓰는 수밖에 없다.

```kotlin
// 위치 기반 구조 분해 (순서 변경에 취약)
val (name, email) = user

// 이름 기반의 안전성을 원하면 — 구조 분해를 쓰지 않는다
val name = user.name       // 순서 무관, 이름으로 확정
val email = user.email
```

후자는 조금 장황하지만, 프로퍼티 순서가 바뀌어도 절대 깨지지 않는다. "구조 분해의 간결함"과 "이름 접근의 견고함" 사이의 트레이드오프를 상황에 맞게 선택해야 한다.

> **명세 정밀**: Kotlin의 향후 버전에서 논의되는 이름 기반 구조 분해가 어떤 문법(`val (name = n, email = e) = user` 유형 등)으로 안정화될지는 이 글을 쓰는 시점에 확정되지 않았다. 확정되지 않은 실험/제안 기능을 프로덕션 지식으로 가정하면 안 되므로, 여기서는 "현재 위치 기반만 안정"이라는 사실만 단정한다.

### 8.4 커스텀 componentN의 오용

커스텀 `componentN`(9절에서 설계)을 정의할 때, 위치 규칙을 개발자 스스로 관리해야 하므로 함정이 하나 더 늘어난다. `component1`과 `component2`의 반환 순서를 프로퍼티 선언과 어긋나게 짜면, 그 클래스를 구조 분해하는 모든 코드가 예상과 다른 값을 받는다.

```kotlin
class Fraction(val numerator: Int, val denominator: Int) {
    // 실수: 순서를 뒤집어 정의
    operator fun component1() = denominator   // "첫째"인데 분모를 반환!
    operator fun component2() = numerator
}

val (num, den) = Fraction(3, 4)
println("$num/$den")   // => 4/3   (뒤집힘! 3/4를 기대했는데)
```

`Fraction(3, 4)`는 3/4를 의미하지만, `component1()`이 분모를 반환하도록 잘못 짜여 있어 구조 분해가 4/3을 준다. 이런 커스텀 컴포넌트의 순서 오류는 클래스 정의에 숨어 있어 호출부만 봐서는 발견하기 매우 어렵다.

**원칙**: 커스텀 `componentN`을 정의한다면, 그 반환 순서를 "이 타입을 구조 분해하는 사람이 가장 자연스럽게 기대할 순서"에 정확히 맞추고, 클래스 문서에 그 순서를 명시하라. 순서가 자명하지 않은 타입이라면 애초에 `componentN`을 제공하지 않는 편이 안전하다 — 구조 분해를 막고 이름 있는 프로퍼티 접근만 노출하면 위치 함정이 원천 봉쇄된다.

## 9. 커스텀 componentN 설계와 한계

### 9.1 비-data 클래스에 componentN 달기

data 클래스가 아닌 일반 클래스에도 `operator fun componentN()`을 손수 정의하면 구조 분해 대상이 된다. 언제 이렇게 할까?

주로 세 경우다. (1) data 클래스로 만들 수 없거나(예: 이미 다른 클래스를 상속해야 함 — data 클래스는 상속 제약이 있다), (2) equals/hashCode/copy 같은 다른 data 클래스 기능은 원치 않고 구조 분해만 필요하거나, (3) 컴포넌트로 노출하고 싶은 값이 주 생성자 프로퍼티가 아니라 파생값일 때다.

```kotlin
// 파생값을 컴포넌트로 노출하는 예
class Duration(val totalSeconds: Long) {
    operator fun component1(): Long = totalSeconds / 3600          // 시
    operator fun component2(): Long = (totalSeconds % 3600) / 60   // 분
    operator fun component3(): Long = totalSeconds % 60            // 초
}

val (hours, minutes, seconds) = Duration(3725)
println("${hours}h ${minutes}m ${seconds}s")   // => 1h 2m 5s
```

`Duration`은 내부적으로 총 초만 저장하지만, 구조 분해할 때는 시/분/초로 분해된다. `componentN`이 저장된 필드를 그대로 반환할 필요가 없다는 것을 보여준다 — 계산 결과를 반환해도 된다. 이는 data 클래스의 자동 생성으로는 표현할 수 없는 유연함이다(data 클래스의 `componentN`은 언제나 필드를 그대로 반환한다).

### 9.2 componentN이 만드는 계약

`componentN`을 공개(public)로 정의하면, 그것은 클래스의 **공개 API 계약**의 일부가 된다. 이 사실을 가볍게 여기면 안 된다.

일단 `component1()`, `component2()`를 공개하고 나면, 외부 코드가 그 순서와 타입에 의존해 구조 분해하기 시작한다. 나중에 그 순서를 바꾸거나 반환 타입을 바꾸면, 8.1절에서 본 것처럼 그 코드가 조용히 깨진다. 즉 **컴포넌트의 순서와 타입은 하위 호환성을 지켜야 하는 계약**이다.

이 관점에서 data 클래스의 자동 `componentN`도 다시 봐야 한다. data 클래스의 프로퍼티 순서를 바꾸는 것은 단순한 내부 정리가 아니라 **공개 계약의 변경**이다. 라이브러리 API로 노출되는 data 클래스라면 특히 그렇다. 이 때문에 널리 쓰이는 data 클래스의 프로퍼티 순서는 함부로 바꾸지 않는 것이 관례다.

```text
componentN이 공개 API 계약인 이유
─────────────────────────────────────
클래스 정의                외부 호출부
─────────────              ─────────────
component1(): A    ◄────   val (a, b) = obj   ← 순서/타입에 의존
component2(): B    ◄────
       │
       ▼ 순서를 바꾸면
component1(): B    ◄────   val (a, b) = obj   ← a에 B가, b에 A가 (조용히 깨짐)
component2(): A
```

### 9.3 중첩 구조 분해의 부재, 대안

Kotlin 구조 분해의 마지막 큰 한계는 **중첩(nested) 구조 분해가 안 된다**는 것이다. JavaScript는 `const { a: { b, c } } = obj`처럼 중첩된 구조를 한 번에 풀 수 있지만, Kotlin에는 이런 문법이 없다.

```kotlin
data class Point(val x: Int, val y: Int)
data class Segment(val start: Point, val end: Point)

val seg = Segment(Point(0, 0), Point(3, 4))

// 중첩 구조 분해 — 문법 에러
val ((sx, sy), (ex, ey)) = seg    // 컴파일 에러: 이런 문법 없음
```

`val ((sx, sy), (ex, ey))` 같은 중첩 괄호는 Kotlin 문법이 허용하지 않는다. 구조 분해는 **한 단계(one level)만** 깊이 들어간다. 각 컴포넌트를 다시 분해하려면 별도의 선언으로 풀어야 한다.

```kotlin
// 대안 1: 단계별로 푼다
val (start, end) = seg
val (sx, sy) = start
val (ex, ey) = end
println("$sx,$sy -> $ex,$ey")   // => 0,0 -> 3,4

// 대안 2: 필요한 것만 이름으로 접근 (더 명확할 때가 많다)
val startX = seg.start.x
val endY = seg.end.y
```

왜 Kotlin은 중첩 구조 분해를 지원하지 않을까? 부분적으로는 위치 기반 구조 분해의 취약성이 중첩되면 더 심해지기 때문이다. `val ((a, b), (c, d)) = ...`는 네 개의 위치를 동시에 머릿속에 담아야 하고, 어느 하나라도 순서가 바뀌면 추적이 극히 어려워진다. 얕은(한 단계) 구조 분해만 지원하는 것은 이 복잡도를 억제하는 보수적 선택으로 볼 수 있다. 깊은 구조를 풀어야 한다면, 단계별 분해나 이름 접근이 더 읽기 좋고 안전하다.

또한 구조 분해는 **널 안전성과도 잘 어울리지 않는다**([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]). nullable 값은 곧장 구조 분해할 수 없다 — `component1()`을 널 참조에 호출할 수 없기 때문이다.

```kotlin
val maybe: Point? = getPointOrNull()
val (x, y) = maybe    // 컴파일 에러: nullable에는 component1()을 호출할 수 없음

// 널을 먼저 처리해야 한다
maybe?.let { (x, y) ->      // let 안에서는 non-null로 스마트 캐스트됨
    println("$x, $y")
}
// 또는
if (maybe != null) {
    val (x, y) = maybe      // 스마트 캐스트로 non-null
    println("$x, $y")
}
```

`?.let { (x, y) -> ... }`는 널이 아닐 때만 람다가 실행되고, 그 안에서 파라미터가 non-null `Point`로 좁혀지므로 구조 분해가 가능하다. 이는 6절의 람다 파라미터 구조 분해와 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]의 `?.let` 관용구가 결합한 흔한 패턴이다.

---

구조 분해는 처음 보면 마법 같은 문법이지만, 이 장을 통과한 지금은 그 정체가 투명하다. `val (a, b) = e`는 언제나 `val a = e.component1(); val b = e.component2()`의 다른 표기일 뿐이며(1절, 2절), data 클래스는 주 생성자 프로퍼티에 대해 이 함수들을 자동으로 만들어 주고(3절, M21), `Pair`·`Map.Entry`·`List`·`Array`는 표준 라이브러리가 같은 관례로 컴포넌트를 제공한다(4절, 5절). for 루프와 람다 파라미터에서의 우아한 형태(`for ((k, v) in map)`, `map { (k, v) -> }`)는 모두 이 `componentN` 호출 위에 얹힌 얇은 설탕이며, 특히 람다에서는 그것이 2-인자가 아니라 1-인자를 푼 것이라는 사실(6절, M42)이 함수 타입을 정확히 읽는 열쇠였다. 언더스코어는 필요 없는 컴포넌트의 호출 자체를 건너뛰고(7절), 그 모든 편리함의 이면에는 **이 기능이 이름이 아니라 위치에 의존한다**는 단 하나의 사실이 도사린다. 프로퍼티 순서를 바꾸면 컴파일러 경고 없이 프로그램이 조용히 틀린 값을 내놓고(8절), 커스텀 `componentN`은 지켜야 할 공개 계약을 만들며(9절), 중첩·널 값과는 잘 어울리지 않는다. 도입부의 질문 — "이름으로 꺼내는가 위치로 꺼내는가", "왜 순서를 바꾸면 조용히 틀리는가" — 은 이제 하나의 답으로 수렴한다. Kotlin의 구조 분해는 관례에 기반한 위치 기반 해체이며, 그 간결함을 누리려면 위치가 무엇을 의미하는지 항상 명확한 곳에서만 써야 한다.

## 핵심 요약

- **구조 분해 `val (a, b) = e`는 이름 매칭이 아니라 `val a = e.component1(); val b = e.component2()`로 번역되는 위치 기반 문법이다.** 괄호 안 변수 이름은 자유이며, 컴파일러는 오직 위치만 보고 값을 대입한다. (M40 참조 — 관례 함수 이름은 정해져 있다)
- **구조 분해는 패턴 매칭이 아니다.** Scala·Rust의 `match`처럼 값의 모양을 검사하며 분기하는 기능이 없다. 타입 판별은 `when`/`is`([[17 - 표현식으로서의 제어 흐름 - if와 when]])와 sealed 계층([[30 - sealed 클래스와 대수적 데이터 타입]])이, 해체는 구조 분해가 별개로 담당한다.
- **구조 분해는 이름 기반이 아니다.** JavaScript의 `const { x, y }`는 이름으로 매칭하지만 Kotlin의 `val (x, y)`는 위치로 매칭한다. 같은 표기가 정반대로 동작하므로 JS 습관이 함정이 된다. Kotlin 2.x stable에는 이름 기반 구조 분해가 없다.
- **`componentN`은 정해진 이름과 `operator` 한정자를 요구하는 관례 함수다.** data 클래스가 이 함수를 자동 생성할 뿐, 구조 분해는 data 클래스 전용 기능이 아니다. 커스텀·확장 `componentN`으로 어떤 타입에도 부여할 수 있다. (M40)
- **data 클래스는 주 생성자 프로퍼티에 대해서만 `componentN`을 만든다.** 클래스 본문에 선언한 프로퍼티는 구조 분해로 꺼낼 수 없다. 컴포넌트 번호는 선언 순서를 그대로 따른다. (M21)
- **`Pair`·`Triple`만 있고 4항 이상 튜플은 없다.** 4개 이상은 이름 있는 data 클래스를 쓰라는 의도된 유도이며, 위치 기억의 한계를 넘지 않으려는 설계다. `Map.Entry`는 키(component1)·값(component2), `IndexedValue`는 인덱스·값 순서다.
- **`List`·`Array`는 `component1()`~`component5()`까지만 구조 분해되고 길이를 검사하지 않는다.** 원소가 부족하면 런타임 `IndexOutOfBoundsException`이 나므로, 컴파일러가 안전을 보장하는 data 클래스·`Pair`보다 취약하다. ([[38 - 컬렉션 - 읽기 전용과 가변]], M43 참조)
- **람다의 `{ (a, b) -> ... }`는 2-인자가 아니라 1-인자 람다에서 그 인자를 푼 것이다.** 함수 타입은 `(Entry) -> R`이지 `(K, V) -> R`이 아니며, 인자가 하나이므로 `it`으로도 접근 가능하다. (M42 참조)
- **언더스코어 `_`는 해당 위치의 `componentN()` 호출 자체를 생략한다.** 단순히 변수를 버리는 게 아니라 계산을 건너뛰므로, 무거운 커스텀 컴포넌트에서는 실질적 성능 절약이 된다. 중간 건너뛰기에는 언더스코어가 필수, 뒤쪽 생략에는 불필요하다.
- **위치 기반이라는 사실이 구조 분해의 근본 위험이다.** 같은 타입 프로퍼티의 순서를 바꾸면 컴파일 에러 없이 프로그램이 조용히 틀린 값을 받는다. `componentN`의 순서는 지켜야 할 공개 API 계약이며, 헷갈릴 소지가 있으면 구조 분해 대신 이름 접근을 쓰는 것이 안전하다.
- **중첩 구조 분해는 지원되지 않고, nullable 값은 곧장 분해할 수 없다.** `val ((a,b),(c,d))`는 문법 에러이며, 널 값은 `?.let { (a, b) -> }`처럼 먼저 non-null로 좁힌 뒤에만 풀 수 있다. ([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]])

## 연결 노트

- [[19 - 연산자 오버로딩과 관례]] — `componentN`은 이 장이 정본으로 다루는 관례 함수 목록(M40)의 일원이다. 구조 분해는 그 관례가 만드는 문법 설탕의 한 사례다.
- [[27 - 데이터 클래스]] — data 클래스가 `componentN`을 자동 생성하는 전체 계약(equals/hashCode/copy 포함)의 소유 장. "주 생성자 프로퍼티만 참여"(M21)의 정본.
- [[13 - 함수 타입과 람다와 함수 참조]] — 람다 파라미터 구조 분해가 왜 2-인자가 아닌 1-인자인지, `it`(M42)이 무엇인지의 소유 장.
- [[18 - 범위와 진행과 반복]] — `for ((k, v) in map)`와 `withIndex()` 구조 분해가 얹히는 이터레이터 기반 반복의 소유 장. C 스타일 for의 부재와 연결.
- [[38 - 컬렉션 - 읽기 전용과 가변]] — `List`·`Array`·`Map.Entry`의 구조 분해, `Array`가 별개 타입이라는 사실(M43)의 소유 장.
- [[39 - 컬렉션 연산과 함수형 파이프라인]] — `partition`·`groupBy` 등 구조 분해로 자연스럽게 푸는 연산들의 소유 장.
- [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]] — nullable 값을 구조 분해하기 전 `?.let`·스마트 캐스트로 좁히는 방법의 소유 장.
- [[35 - 확장 함수와 프로퍼티]] — `component1()`을 확장 함수로 정의하는 원리(정적 디스패치 M14). 표준 라이브러리가 `List`에 컴포넌트를 부여하는 방식.
- [[30 - sealed 클래스와 대수적 데이터 타입]] — 구조 분해와 대비되는 타입 판별·완전성 검사. Kotlin이 패턴 매칭 대신 택한 길.
- [[11 - 변수와 초기화 - val과 const와 lateinit]] — 구조 분해가 `val`/`var` 선언이어야 하고 재대입 문법이 아닌 이유. `var` 구조 분해의 의미.
