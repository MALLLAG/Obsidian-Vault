앞의 [[19 - 연산자 오버로딩과 관례]]에서는 Kotlin이 특정 이름(`plus`, `get`, `invoke`, `compareTo`…)의 함수를 특정 문법에 연결하는 **관례(convention)** 메커니즘을 살펴보았다. 그리고 연산자 오버로딩이 "정해진 이름의 함수만 정해진 기호에 대응된다"는 규칙 위에 서 있다는 것도 확인했다.

이 장에서는 그 목록에서 아직 자세히 다루지 않은 관례인 `component1()`, `component2()`, `component3()`…을 살펴본다. 구조 분해(destructuring)는 새로운 문법처럼 보이지만, 실제로는 이 `componentN` 관례 함수를 호출하는 **얇은 문법 설탕(syntactic sugar)** 일 뿐이다. 이 사실 하나를 이해하면 구조 분해로 할 수 있는 일과 구조 분해의 함정을 모두 설명할 수 있다.

이 장에서는 `val (a, b) = e` 선언이 무엇으로 번역되는지, 어떤 타입을 구조 분해할 수 있는지, for 루프와 람다 파라미터에서 구조 분해가 어떻게 쓰이는지를 다룬다. 이어서 언더스코어로 일부만 해체하는 방법을 보고, 구조 분해가 이름이 아니라 **위치**에 의존하기 때문에 컴파일러가 잡지 못하는 논리 버그가 생기는 과정과 커스텀 `componentN`을 직접 설계할 때 지켜야 할 계약과 한계를 살펴본다.

## 1. 구조 분해란 무엇인가: 위치를 기준으로 해체한다

### 1.1 선언 하나가 여러 지역 변수로

구조 분해 선언(destructuring declaration)은 객체 하나를 여러 지역 변수로 한 번에 풀어내는 문법이다. 가장 익숙한 형태는 다음과 같다.

```kotlin
data class Point(val x: Int, val y: Int)

val p = Point(10, 20)
val (x, y) = p        // 구조 분해 선언
println(x)            // => 10
println(y)            // => 20
```

겉보기에는 `p`의 `x` 필드를 `x` 변수에, `y` 필드를 `y` 변수에 넣는 것처럼 보인다. 하지만 이 인상은 절반만 맞고, 나머지 절반은 위험할 만큼 틀렸다. 컴파일러가 실제로 하는 일은 다음 코드와 완전히 같다.

```kotlin
val x = p.component1()   // 첫 번째 위치
val y = p.component2()   // 두 번째 위치
```

즉 `x`, `y`라는 변수 이름에는 아무 의미도 없다. 컴파일러는 왼쪽 괄호 안의 이름을 오른쪽 객체의 프로퍼티 이름과 대조하지 않는다. 괄호 안 **첫 번째 자리**의 변수에는 `component1()`의 결과를, **두 번째 자리**의 변수에는 `component2()`의 결과를 대입할 뿐이다. 따라서 이름을 바꿔 써도 결과는 같다.

```kotlin
val (banana, apple) = p
println(banana)   // => 10   (p.component1(), 즉 p.x)
println(apple)    // => 20   (p.component2(), 즉 p.y)
```

`banana`가 `x`를 받고 `apple`이 `y`를 받는다. 이름은 지역 변수를 부르는 라벨일 뿐이고, 어떤 필드에서 값을 가져올지는 결정하지 못한다. **위치가 모든 것을 결정한다.** 이 문장이 이 장 전체의 핵심이며, 8절에서 다룰 모든 함정의 원인이다.

> [!note] 명세 기준
> 구조 분해 선언 `val (a, b, …, n) = e`는 형식적으로 `val a = e.component1(); val b = e.component2(); …; val n = e.componentN()`으로 번역된다. `componentN()`은 `operator` 한정자가 붙은 함수여야 하며, 이 번역은 Kotlin 언어 명세에 명시된 결정론적 규칙이다. 오른쪽 표현식 `e`는 정확히 한 번만 평가된다(각 `componentN` 호출은 같은 `e` 값에 대해 이루어진다).

### 1.2 무엇이 아닌가: 패턴 매칭도, 이름 기반도 아니다

구조 분해를 처음 접하면 다른 언어의 두 가지 기능과 혼동하기 쉽다. 둘 다 분명히 구분해 두어야 한다.

**첫째, 구조 분해는 패턴 매칭(pattern matching)이 아니다.** Scala의 `case Point(x, y) =>`나 Rust의 `let Point { x, y } = p`, 또는 `match` 표현식은 값의 *모양을 검사*하면서 동시에 바인딩한다. 값이 어떤 생성자로 만들어졌는지 판별하고, 조건에 따라 분기하고, 실패하면 다음 case로 넘어간다.

Kotlin의 구조 분해에는 그런 검사가 전혀 없다. `val (x, y) = p`는 항상 성공하거나(componentN이 있으면) 아예 컴파일되지 않거나(없으면) 둘 중 하나다. "이 값이 Point 모양이면 분해하고, 아니면 다른 방법을 시도한다"는 조건부 의미가 없다.

Kotlin은 타입 판별과 분기를 `when`(is 검사)과 [[30 - sealed 클래스와 대수적 데이터 타입]]의 완전성(exhaustiveness) 검사에 맡기고, 값의 해체는 구조 분해에 맡긴다. 두 기능은 분리되어 있다.

```kotlin
sealed interface Shape
data class Circle(val radius: Double) : Shape
data class Rectangle(val w: Double, val h: Double) : Shape

fun area(s: Shape): Double = when (s) {
    // 타입 검사(is)와 스마트 캐스트는 when이 담당.
    is Circle -> {
        val (r) = s          // 구조 분해는 이미 Circle로 좁혀진 뒤에만 가능
        Math.PI * r * r
    }
    is Rectangle -> {
        val (w, h) = s
        w * h
    }
}
```

Scala라면 `case Circle(r) => ...`처럼 판별과 분해를 한 줄에서 처리했을 것이다. Kotlin은 먼저 `is Circle`로 타입을 좁히고(그러면 스마트 캐스트가 `s`를 `Circle`로 취급한다), 그 안에서 `val (r) = s`로 분해한다. 판별과 해체가 별개의 단계이다.

**둘째, 구조 분해는 이름 기반이 아니다.** JavaScript의 객체 구조 분해 `const { x, y } = p`는 이름으로 프로퍼티를 찾는다. `const { y, x } = p`처럼 순서를 바꿔 써도 `y`는 `p.y`를, `x`는 `p.x`를 정확히 받는다. 이름이 곧 키이다.

Kotlin은 정반대다. 앞에서 보았듯이 `val (y, x) = p`라고 쓰면 `y` 변수가 `component1()`, 즉 첫 번째 프로퍼티를 받는다. 이름이 우연히 `y`일 뿐이고, 값은 첫 번째 위치의 것이다.

```javascript
// JavaScript — 이름 기반
const p = { x: 10, y: 20 };
const { y, x } = p;   // y === 20, x === 10  (이름으로 매칭)
```

```kotlin
// Kotlin — 위치 기반
val p = Point(x = 10, y = 20)
val (y, x) = p        // y == 10 (component1=x), x == 20 (component2=y) — 헷갈림 유발!
```

같은 `{ y, x }`와 `(y, x)` 표기가 두 언어에서 정반대로 동작한다. JavaScript에 익숙한 개발자가 Kotlin에서 가장 자주 실수하는 지점이 바로 이 차이다. 이름 기반 구조 분해가 없다는 점과 이에 관한 향후 계획은 8.3절에서 다시 다룬다.

> [!warning] 흔한 오해
> "구조 분해의 괄호 안 이름은 대상 객체의 프로퍼티 이름과 일치해야 한다"는 생각은 틀렸다. 이름은 자유롭게 정할 수 있다. `val (첫째, 둘째) = point`처럼 아무 이름이나 쓸 수 있고, 컴파일러는 위치만 본다. 이름을 프로퍼티와 똑같이 맞추는 것은 **가독성을 위한 관행**일 뿐이고, 언어가 강제하는 규칙이 아니다.

### 1.3 쓸 수 있는 곳과 쓸 수 없는 곳

구조 분해 선언은 아무 데서나 쓸 수 있는 것이 아니다. 다음 세 가지 문맥에서만 허용된다.

1. **지역 변수 선언** (함수 본문, `init` 블록, 그 밖의 지역 스코프 안):

```kotlin
fun process() {
    val (name, age) = getPerson()   // OK — 지역 변수
    // ...
}
```

2. **for 루프의 루프 변수**:

```kotlin
for ((index, value) in list.withIndex()) { /* ... */ }   // OK
```

3. **람다 파라미터**:

```kotlin
map.forEach { (key, value) -> /* ... */ }                // OK
```

반면 다음 위치에서는 구조 분해를 **쓸 수 없다.**

```kotlin
// 클래스/최상위 프로퍼티로는 불가
class Container {
    val (a, b) = getPair()   // 컴파일 에러: 구조 분해는 프로퍼티 선언에 못 쓴다
}

// 최상위(파일 레벨)에서도 불가
val (x, y) = Point(1, 2)     // 컴파일 에러 (지역 스코프가 아님)

// 일반 함수 파라미터로는 불가 (람다 파라미터만 가능)
fun draw(point: (x, y)) { }  // 문법 에러

// 대입만으로는 불가 — 반드시 val/var 선언이어야
var a = 0; var b = 0
(a, b) = getPair()           // 컴파일 에러: 이런 대입 문법 없음
```

특히 마지막 경우가 중요하다. 파이썬이나 JavaScript에는 이미 있는 변수에 구조 분해로 *재대입*하는 문법(`[a, b] = f()`)이 있지만, Kotlin에는 없다. 구조 분해는 항상 **새 변수를 선언**하는 문법이므로 반드시 `val` 또는 `var` 키워드로 시작해야 한다. 이는 [[11 - 변수와 초기화 - val과 const와 lateinit]]에서 본 Kotlin의 선언과 대입 구분을 그대로 따른 것이다.

`var`로 선언하면 각 변수는 따로 재대입할 수 있는 지역 변수가 된다.

```kotlin
var (count, label) = 0 to "empty"
count = 5           // OK — count는 var
label = "filled"    // OK
```

하지만 실무에서 `var` 구조 분해는 드물다. 대부분은 값을 꺼내 읽기만 하므로 `val`이 자연스럽다.

## 2. componentN 관례: 구조 분해를 움직이는 함수

### 2.1 operator fun componentN()

1절에서 구조 분해가 `componentN()` 호출로 번역된다고 했다. 이제 그 함수 자체를 살펴보자. 어떤 타입을 구조 분해하려면 그 타입에 다음 형태의 함수가 있어야 한다.

```kotlin
operator fun component1(): T1
operator fun component2(): T2
operator fun component3(): T3
// ...
```

요구 조건은 세 가지다.

- **이름이 정확히 `componentN`** 이어야 한다(N은 1부터 시작하는 연속된 양의 정수). `component0`이나 `getFirst` 같은 이름은 구조 분해에 쓰이지 않는다.
- **`operator` 한정자**가 붙어 있어야 한다. 19장(연산자 오버로딩과 관례)에서 본 것과 같은 규칙이다. `operator`가 없으면 평범한 함수일 뿐이고 구조 분해에 쓰이지 않는다.
- **파라미터가 없어야** 한다(수신 객체만으로 값을 계산한다). 반환 타입은 자유롭게 정할 수 있다.

이 세 조건은 "연산자 오버로딩은 정해진 관례 이름으로만 할 수 있다"는 원칙이 그대로 적용된 사례다. `componentN`은 임의로 지은 이름이 아니라 언어가 예약한 관례 함수 목록에 속한다. 컴파일러는 정확히 이 이름과 `operator` 표시를 확인한 뒤에야 괄호 문법을 이 함수 호출로 번역한다.

```kotlin
class NameParts(fullName: String) {
    private val parts = fullName.split(" ")
    operator fun component1(): String = parts.getOrElse(0) { "" }
    operator fun component2(): String = parts.getOrElse(1) { "" }
}

val (first, last) = NameParts("Ada Lovelace")
println(first)   // => Ada
println(last)    // => Lovelace
```

`NameParts`는 data 클래스가 아니고, 프로퍼티도 `parts` 하나뿐이다. 그런데도 구조 분해를 할 수 있는 이유는 `operator fun component1/2()`를 직접 정의했기 때문이다. 이것이 구조 분해의 실체다. data 클래스는 이 함수들을 자동으로 만들어 줄 뿐이고, 구조 분해 자체는 data 클래스에 묶인 기능이 아니다.

### 2.2 디슈가링: (a, b) = e → component1()/component2()

컴파일러의 번역(desugaring)을 그림으로 정리하면 다음과 같다.

```text
원본 소스                          컴파일러가 번역한 형태
─────────────────────────         ──────────────────────────────
val (a, b) = e             ─────►  val tmp = e            (e를 한 번만 평가)
                                   val a = tmp.component1()
                                   val b = tmp.component2()

val (a, b, c) = e          ─────►  val tmp = e
                                   val a = tmp.component1()
                                   val b = tmp.component2()
                                   val c = tmp.component3()
```

여기서 세 가지 세부 사항을 알 수 있다.

**첫째, `e`는 한 번만 평가된다.** `e`가 부수 효과가 있는 표현식(예: 카운터를 증가시키는 함수 호출)이더라도 그 표현식은 딱 한 번 실행되고, 그 결과에 대해 `component1()`과 `component2()`가 호출된다.

```kotlin
var calls = 0
fun makePair(): Pair<Int, Int> { calls++; return 1 to 2 }

val (a, b) = makePair()
println(calls)   // => 1  (makePair는 한 번만 호출됨)
```

**둘째, 각 `componentN`은 별도의 함수 호출이다.** 구조 분해에도 비용이 든다. 인라인되지 않는 한 변수마다 실제 메서드 호출이 일어난다. data 클래스의 `componentN`은 대개 단순한 필드 접근으로 컴파일되고 JIT이 인라인하므로 비용이 거의 없다. 하지만 커스텀 `componentN`이 무거운 계산을 한다면 그 비용이 그대로 반복된다.

**셋째, 타입을 명시할 수 있다.** 각 변수에 타입 주석을 달 수 있으며, 그 타입은 해당 `componentN`의 반환 타입과 호환되어야 한다.

```kotlin
val (x: Int, y: Int) = Point(3, 4)     // 타입 명시
val (name: String, age: Int) = getPerson()
```

타입을 명시하면 잘못 읽을 가능성을 줄일 수 있고, 타입을 잘못 쓰면 컴파일 에러로 드러난다(예: `component1()`이 `String`을 반환하는데 `Int`로 선언하면 에러가 난다).

### 2.3 arity와 순서, trailing 생략

구조 분해로 요청하는 변수 개수(arity)와 대상 타입이 제공하는 `componentN`의 개수 사이에는 규칙이 있다.

**요청한 개수만큼 `componentN`이 있어야** 한다. 변수 `n`개를 요청하면 `component1()`부터 `componentN()`까지가 모두 있어야 한다. 하나라도 없으면 컴파일 에러다.

```kotlin
val pair = 1 to 2                  // Pair는 component1, component2만 있음

val (a, b) = pair                  // OK
val (a, b, c) = pair               // 컴파일 에러: component3()이(가) 없음
```

**반대로, 제공되는 것보다 적게 요청하는 것은 허용된다.** 단, 앞에서부터 연속된 접두(prefix)여야 한다. 컴포넌트가 3개인 타입에서 앞의 2개만 꺼낼 수 있다.

```kotlin
data class Rgb(val r: Int, val g: Int, val b: Int)
val color = Rgb(255, 128, 0)

val (red, green) = color           // OK — component1, component2만 호출. component3(b)은 무시
println(red)                       // => 255
println(green)                     // => 128
```

뒤쪽(trailing)을 생략할 수는 있지만, 위치를 밀 수 없으므로 중간을 그냥 건너뛸 수는 없다. 두 번째만 빼고 첫째와 셋째를 꺼내려면 언더스코어를 써야 한다(7절).

이 규칙에서 중요한 결론이 나온다. **구조 분해는 항상 왼쪽(component1)부터 순서대로 채워진다.** `(a, b)`에서 `a`는 반드시 `component1`이고 `b`는 반드시 `component2`이다. 이 순서는 언어가 고정한 것이어서 바꿀 방법이 없다. 뒤에서 볼 위치 기반 함정의 원인이 바로 이 고정된 순서다.

### 2.4 확장 componentN

`componentN`이 반드시 클래스의 멤버일 필요는 없다. **확장 함수([[35 - 확장 함수와 프로퍼티]])** 로도 정의할 수 있다. 표준 라이브러리가 `List`나 `Array`처럼 우리가 만들지 않은 타입에 구조 분해 기능을 제공하는 방식도 이것이다.

```kotlin
// 우리가 만들지 않은 표준 타입에 구조 분해를 확장으로 추가
class Vector3(val values: DoubleArray)

operator fun Vector3.component1() = values[0]
operator fun Vector3.component2() = values[1]
operator fun Vector3.component3() = values[2]

val v = Vector3(doubleArrayOf(1.0, 2.0, 3.0))
val (x, y, z) = v
println("$x $y $z")   // => 1.0 2.0 3.0
```

확장 `componentN`은 다른 확장 함수와 마찬가지로 **정적 디스패치**되고, import 스코프에 있어야 사용할 수 있다. 표준 라이브러리는 이 방식으로 `List<T>`에 `component1()`부터 `component5()`까지의 확장 연산자를 정의해 두었고, `Array<T>`에도 같은 확장 연산자를 정의해 두었다. 그래서 임의의 리스트를 앞의 다섯 개까지 구조 분해할 수 있다(4절과 5절에서 다룬다).

> [!caution] 성능 주의
> 확장 `componentN`은 정적 메서드로 컴파일되며 수신 객체를 첫 인자로 받는다. data 클래스의 멤버 `componentN`은 필드를 반환하기만 하므로 JIT이 쉽게 인라인한다. 반면 확장 컴포넌트가 매번 배열 인덱싱이나 컬렉션 순회를 한다면(예: `LinkedList`에서 `component3()`이 O(3) 순회) 숨은 비용이 생긴다. `List.component5()`로 다섯 번째 원소를 가져오는 일은 `RandomAccess` 리스트에서는 싸지만 연결 리스트에서는 그렇지 않다.

## 3. data 클래스와 자동 생성

### 3.1 주 생성자 프로퍼티만 componentN이 된다

실무에서 구조 분해를 쓰는 경우는 대부분 data 클래스가 대상이다. 이유는 분명하다. data 클래스에서는 컴파일러가 `componentN` 함수를 **자동으로 생성**해 주기 때문이다. 이 자동 생성의 전체 계약(equals/hashCode/toString/copy/componentN)은 [[27 - 데이터 클래스]]에서 다루지만, 구조 분해와 직접 관련된 부분은 여기서 정확히 짚어 두어야 한다.

핵심 규칙은 **주 생성자(primary constructor)에 선언된 프로퍼티만** `componentN`으로 노출된다는 것이다. "data 클래스는 완전한 값 타입이 아니며, 주 생성자 프로퍼티만 equals/hashCode/toString/copy/componentN에 참여한다"는 원칙을 구조 분해 쪽에서 본 모습이다.

```kotlin
data class Account(
    val id: Long,          // 주 생성자 프로퍼티 → component1()
    val balance: Int       // 주 생성자 프로퍼티 → component2()
) {
    var lastAccessed: Long = 0L    // 본문(body) 프로퍼티 → componentN 없음!
}

val acc = Account(1L, 5000).apply { lastAccessed = 99L }

val (id, balance) = acc            // OK
println("$id $balance")            // => 1 5000

val (id2, balance2, last) = acc    // 컴파일 에러: component3()이 없음
                                   // lastAccessed는 componentN에 참여하지 않음
```

`lastAccessed`는 분명히 `Account`의 프로퍼티이지만, 주 생성자가 아니라 클래스 본문에 선언되었으므로 `component3()`이 생성되지 않는다. 따라서 구조 분해로는 절대 꺼낼 수 없고, `acc.lastAccessed`처럼 이름으로만 접근해야 한다.

### 3.2 본문 프로퍼티가 제외되는 이유

본문 프로퍼티는 왜 제외될까? 이것은 버그가 아니라 의도된 설계다. data 클래스가 자동 생성하는 것들(equals, hashCode, copy, componentN)은 모두 "이 객체를 구성하는 **핵심 데이터가 무엇인가**"라는 하나의 정의에 근거한다. 그 핵심 데이터는 주 생성자 파라미터로 정해진다. 주 생성자는 "이 객체를 만들려면 이 값들이 필요하다"는 계약이므로, Kotlin은 그 값들을 객체의 정체성(identity)으로 삼는다.

본문 프로퍼티는 흔히 파생 상태(derived state)나 캐시, 가변적인 부가 정보다. `lastAccessed` 같은 값을 equals나 componentN에 넣으면 오히려 문제가 된다. 두 계정의 잔액과 id가 같은데 마지막 접근 시각만 다르다는 이유로 서로 "다른 계정"이 되면 곤란하다. Kotlin은 이 판단을 매번 개발자에게 맡기지 않고, "주 생성자에 넣으면 정체성, 본문에 넣으면 부가 상태"라는 단순한 규칙으로 나누었다.

이 규칙에서 나오는 실용적인 결론은 다음과 같다. **구조 분해로 꺼내고 싶은 값은 주 생성자에 두어야 한다.** 어떤 파생값을 구조 분해에 포함하고 싶다면 주 생성자 프로퍼티로 만들거나(계산해서 넣거나), 커스텀 `componentN`을 직접 추가해야 한다(9절).

```kotlin
data class Segment(val start: Point, val end: Point) {
    // 본문 프로퍼티는 componentN에 없음. 구조 분해하려면 커스텀 추가.
    val length: Double get() = hypot(
        (end.x - start.x).toDouble(), (end.y - start.y).toDouble()
    )
    operator fun component3(): Double = length   // 손수 추가하면 3항 분해 가능
}

val seg = Segment(Point(0, 0), Point(3, 4))
val (s, e, len) = seg
println(len)   // => 5.0
```

여기서 `component1()`과 `component2()`는 컴파일러가 `start`와 `end`로 자동 생성하고, `component3()`만 우리가 `length`에 연결했다. 이처럼 자동 생성된 함수와 직접 정의한 함수를 함께 쓸 수 있다.

### 3.3 번호는 선언 순서를 따른다

data 클래스가 생성하는 `componentN`의 번호는 **주 생성자에 프로퍼티가 선언된 순서**를 그대로 따른다. 첫 번째 프로퍼티가 `component1`, 두 번째 프로퍼티가 `component2`가 되는 식이다. 이 대응은 프로퍼티 *이름*과는 관계없고 *선언 순서*로만 정해진다.

```kotlin
data class Coordinate(val latitude: Double, val longitude: Double)
//                        ↑ component1()        ↑ component2()

val seoul = Coordinate(37.5665, 126.9780)
val (lat, lng) = seoul   // lat = latitude, lng = longitude
```

`latitude`가 첫 번째로 선언되었으므로 `component1()`이 되고, `val (lat, lng)`에서 `lat`이 그 값을 받는다. 여기까지는 자연스럽다. 문제는 나중에 누군가 이 클래스의 선언 순서를 바꿀 때 생긴다. 이 문제가 8절의 주제이며, data 클래스의 자동 생성이 편리한 만큼 위험하기도 한 이유다.

> [!note] 명세 기준
> data 클래스의 `componentN`은 `public operator`로 생성되며, 주 생성자의 `val`/`var` 프로퍼티에 대해서만 만들어진다. 주 생성자 파라미터 가운데 `val`/`var`가 아닌 순수 파라미터(예: `data class D(val a: Int, b: Int)`의 `b`)는 프로퍼티가 아니므로 `componentN`에 포함되지 않는다.
>
> 사실 data 클래스는 모든 주 생성자 파라미터가 `val`/`var`여야 하므로, 이런 선언 자체가 컴파일 에러다. 즉 data 클래스에서는 "주 생성자 파라미터 = 프로퍼티 = componentN"이 항상 일치한다.

## 4. Pair·Triple과 표준 라이브러리

### 4.1 Pair/Triple의 componentN

Kotlin 표준 라이브러리는 구조 분해에 쓸 수 있는 범용 튜플 타입 두 가지, `Pair<A, B>`와 `Triple<A, B, C>`를 제공한다. 둘 다 data 클래스로 정의되어 있으므로 `componentN`을 자동으로 갖는다.

```kotlin
// stdlib 정의(개념)
public data class Pair<out A, out B>(
    public val first: A,
    public val second: B
)
public data class Triple<out A, out B, out C>(
    public val first: A,
    public val second: B,
    public val third: C
)
```

`Pair`는 `component1()`(=first)과 `component2()`(=second)를 갖고, `Triple`은 여기에 `component3()`(=third)까지 갖는다. 그래서 함수가 여러 값을 반환할 때 흔히 다음과 같이 쓴다.

```kotlin
fun minMax(numbers: List<Int>): Pair<Int, Int> {
    return numbers.min() to numbers.max()
}

val (lo, hi) = minMax(listOf(3, 1, 4, 1, 5, 9))
println("$lo..$hi")   // => 1..9
```

여러 값을 돌려주고 싶을 때 별도의 결과 클래스를 만들지 않고 `Pair`/`Triple`로 묶어 반환한 뒤, 호출하는 쪽에서 구조 분해로 푸는 것이 관용적인 방법이다.

### 4.2 왜 Triple에서 멈추는가

표준 라이브러리에는 `Pair`(2항)와 `Triple`(3항)만 있고, `Quadruple`(4항)이나 그 이상은 **없다.** 이것은 빠뜨린 것이 아니라 의도적인 설계 결정이다.

이유는 위치 기반 구조 분해가 근본적으로 취약하다는 데 있다. 익명 튜플의 원소가 2~3개일 때는 `(lo, hi)`, `(x, y, z)`처럼 사람이 위치를 기억할 수 있다. 하지만 4개를 넘어가면 "세 번째가 무엇이었지?"를 기억하기 어려워지고, 8절에서 볼 위치 혼동 버그의 위험이 급격히 커진다. 그래서 Kotlin은 4개 이상의 값을 묶어야 한다면 **이름 있는 프로퍼티를 가진 data 클래스를 정의하라**고 유도한다.

```kotlin
// 나쁨(존재하지도 않음): 익명의 4-튜플. 위치를 기억해야 함
// val (a, b, c, d) = quadrupleOf(...)   // Quadruple 없음

// 좋음: 의미가 이름에 담긴 data 클래스
data class ParsedUrl(
    val scheme: String,
    val host: String,
    val port: Int,
    val path: String
)

fun parse(raw: String): ParsedUrl { /* ... */
    return ParsedUrl("https", "example.com", 443, "/index")
}

val url = parse("...")
println(url.host)   // 이름으로 접근 — 위치 기억 불필요
val (scheme, host, port, path) = url   // 원하면 구조 분해도 가능(단 여전히 위치 기반)
```

`Pair`/`Triple`은 "한 곳에서 만들어 바로 풀어 쓰는 짧은 쌍이나 삼중"을 위한 도구이고, 그보다 많은 값은 data 클래스로 묶으라는 것이 표준 라이브러리 설계에 담긴 조언이다.

> [!info] 역사 메모
> `Pair`/`Triple`과 함께 쓰는 `to` 중위 함수(`1 to 2`)는 Kotlin 초기부터 있었고, 이 조합이 맵 리터럴 관용구 `mapOf("a" to 1, "b" to 2)`의 기반이다. `to`는 `infix fun <A, B> A.to(that: B): Pair<A, B>`로 정의된 확장 중위 함수일 뿐이고, 특별한 문법이 아니다(19장 연산자 오버로딩과 관례의 infix).
>
> 즉 `1 to 2`는 `1.to(2)`이고 결과는 `Pair(1, 2)`이며, 이것을 구조 분해하면 `component1/2`가 호출된다.

### 4.3 List와 Array의 구조 분해

2.4절에서 언급했듯이 표준 라이브러리는 `List`와 `Array`에도 확장 `componentN`을 제공한다. 단, **`component1()`부터 `component5()`까지 다섯 개만** 제공한다.

```kotlin
// stdlib가 제공하는 확장(개념)
public operator fun <T> List<T>.component1(): T = get(0)
public operator fun <T> List<T>.component2(): T = get(1)
// ... component5까지

val list = listOf(10, 20, 30, 40, 50, 60)
val (a, b, c) = list         // OK — 앞 세 개
println("$a $b $c")          // => 10 20 30

val (p, q, r, s, t, u) = list  // 컴파일 에러: component6()이 없음
```

여기에는 두 가지 함정이 있다.

**첫째, 원소 개수를 검사하지 않는다.** `val (a, b, c) = list`는 리스트에 원소가 최소 3개 있다고 *가정*할 뿐이고, 실제로 검사하지는 않는다. 리스트가 더 짧으면 런타임에 `IndexOutOfBoundsException`이 발생한다.

```kotlin
val short = listOf(1, 2)
val (a, b, c) = short   // 컴파일은 됨! 런타임에 component3() → get(2) → 예외
// 실행 시: IndexOutOfBoundsException: Index 2 out of bounds for length 2
```

data 클래스나 `Pair`는 컴포넌트 개수가 타입 수준에서 고정되어 있으므로 이런 일이 없다. 하지만 리스트는 길이가 타입에 담기지 않으므로 컴파일러가 막아 주지 못한다. 이런 이유로 `List` 구조 분해는 위험하며, 실무에서는 대개 피하는 편이 낫다.

**둘째, `List`에는 이름이 없으므로 위치에만 의존한다.** `val (first, second) = coordinates`에서 `first`가 x인지 y인지는 리스트를 만든 쪽의 관례에 달려 있다. 그래서 data 클래스보다도 더 취약하다.

`Array`도 마찬가지로 `component1()`~`component5()` 확장을 가진다. 원시 배열(`IntArray`, `DoubleArray` 등)에도 각각 대응하는 확장 컴포넌트가 있다.

```kotlin
val point = intArrayOf(3, 4)
val (x, y) = point   // IntArray.component1(), component2()
println("$x $y")     // => 3 4
```

`Array`가 `List`와 별개의 타입이라는 점은 [[38 - 컬렉션 - 읽기 전용과 가변]]에서 다룬다. 다만 구조 분해 관점에서는 둘 다 "5개까지 지원하고, 길이를 검사하지 않는다"는 성질이 같다.

## 5. Map과 for 루프 구조 분해

### 5.1 Map.Entry의 component1/2

구조 분해가 특히 유용한 곳 중 하나가 맵 순회다. `Map<K, V>`를 순회하면 각 원소는 `Map.Entry<K, V>` 타입이고, 표준 라이브러리는 이 `Entry`에 확장 `componentN`을 정의해 두었다.

```kotlin
// stdlib 확장(개념)
public operator fun <K, V> Map.Entry<K, V>.component1(): K = key
public operator fun <K, V> Map.Entry<K, V>.component2(): V = value
```

`component1()`은 **키**이고 `component2()`는 **값**이다. 키가 먼저, 값이 나중이라는 이 순서는 외워 둘 만하다. 이 확장 덕분에 맵을 순회할 때 엔트리를 키와 값으로 바로 풀 수 있다.

```kotlin
val ages = mapOf("Alice" to 30, "Bob" to 25)

for (entry in ages) {
    val (name, age) = entry     // entry.component1()=key, component2()=value
    println("$name is $age")
}
// => Alice is 30
// => Bob is 25
```

### 5.2 for ((k, v) in map)

위 예제는 더 간결하게 쓸 수 있다. for 루프의 루프 변수 자리에서 바로 구조 분해할 수 있기 때문이다.

```kotlin
for ((name, age) in ages) {
    println("$name is $age")
}
```

이 코드는 앞의 코드와 완전히 같으며, 컴파일러는 다음과 같이 번역한다.

```text
for ((name, age) in ages) { body }
        │
        ▼  번역
for (entry in ages) {              // ages를 이터레이트 → Map.Entry
    val name = entry.component1()  // = entry.key
    val age  = entry.component2()  // = entry.value
    body
}
```

for 루프의 구조 분해는 [[18 - 범위와 진행과 반복]]에서 본 이터레이터 기반 반복 위에서 동작한다. `ages`를 순회해 각 `Entry`를 얻고, 그 `Entry`를 `componentN`으로 푼다. 두 관례(`iterator`/`hasNext`/`next`와 `componentN`)가 조합되어 `for ((k, v) in map)`이라는 깔끔한 문법이 만들어진다.

주의할 점이 하나 있다. **여기서도 이름보다 위치가 우선한다.** `for ((k, v) in map)`에서 첫 번째 변수는 항상 키이고, 두 번째 변수는 항상 값이다. 실수로 `for ((value, key) in map)`이라고 쓰면 `value` 변수에 실제로는 키가 담긴다.

```kotlin
for ((value, key) in ages) {   // 이름을 거꾸로 붙인 흔한 실수
    println("$value = $key")   // value엔 이름(키)이, key엔 나이(값)가 들어감!
}
// => Alice = 30   (이름이 value에, 나이가 key에 — 완전히 헷갈림)
```

컴파일러는 이 실수를 잡아 주지 못한다. 문법적으로 완벽히 유효한 코드이기 때문이다.

### 5.3 withIndex·indices와 그 밖의 경우

인덱스와 값을 함께 순회할 때도 구조 분해를 쓰는 것이 관용적이다. `Iterable.withIndex()`는 `IndexedValue<T>`(data 클래스)를 내보내고, 이 타입은 `component1()`(=index)과 `component2()`(=value)를 갖는다.

```kotlin
val fruits = listOf("apple", "banana", "cherry")

for ((index, fruit) in fruits.withIndex()) {
    println("$index: $fruit")
}
// => 0: apple
// => 1: banana
// => 2: cherry
```

여기서도 순서를 기억해 두자. **인덱스가 먼저, 값이 나중**이다. 이는 `Map.Entry`의 키/값 순서와 개념적으로 일관된다. 둘 다 "위치를 식별하는 값이 먼저"이다. `IndexedValue`의 정의를 보면 분명하다.

```kotlin
public data class IndexedValue<out T>(public val index: Int, public val value: T)
//                                          ↑ component1        ↑ component2
```

Kotlin에는 C 스타일 for 루프(`for (int i = 0; ...)`)가 없으므로(18장 범위와 진행과 반복), 인덱스가 필요할 때는 `withIndex()`와 구조 분해를 함께 쓰는 것이 가장 관용적인 대안이다.

`associateBy`, `groupBy`, `partition` 같은 컬렉션 연산([[39 - 컬렉션 연산과 함수형 파이프라인]])의 결과도 구조 분해로 푸는 경우가 많다. 특히 `partition`은 조건을 만족하는 원소와 만족하지 않는 원소를 담은 두 리스트를 `Pair`로 반환하므로, 구조 분해로 받는 것이 자연스럽다.

```kotlin
val numbers = listOf(1, 2, 3, 4, 5, 6)
val (evens, odds) = numbers.partition { it % 2 == 0 }
println(evens)   // => [2, 4, 6]
println(odds)    // => [1, 3, 5]
```

`partition`은 `Pair<List<T>, List<T>>`를 반환하는데, 첫 번째가 술어를 만족하는 원소들이고 두 번째가 만족하지 않는 원소들이다. 이것도 위치에 기댄 관례의 하나다.

## 6. 람다 파라미터 구조 분해

### 6.1 파라미터 하나를 해체한다: Function2가 아니다

구조 분해를 가장 많이 오해하는 문맥이 람다 파라미터다. 다음 코드를 보자.

```kotlin
val ages = mapOf("Alice" to 30, "Bob" to 25)

ages.forEach { (name, age) ->
    println("$name: $age")
}
```

`{ (name, age) -> ... }`는 파라미터가 두 개인 람다처럼 보인다. **하지만 그렇지 않다.** 이 람다는 파라미터가 **하나**이며, 그 파라미터(`Map.Entry`)를 구조 분해한 것이다. 괄호 `( )`가 바로 "이 파라미터 하나를 componentN으로 풀어라"는 표시다.

이 차이는 [[13 - 함수 타입과 람다와 함수 참조]]에서 다루는 함수 타입의 arity와 직접 관련된다. `forEach`가 받는 것은 `(Map.Entry<K, V>) -> Unit`, 즉 **1-인자** 함수 타입이다. 파라미터가 정말 두 개라면 `(K, V) -> Unit`이어야 하지만 그렇지 않다.

이 사실은 "`it`은 파라미터가 하나인 람다의 암시적 이름일 뿐"이라는 점과도 연결된다. 람다의 파라미터가 하나이므로, 구조 분해 없이 `it`으로도 접근할 수 있다.

```kotlin
// 아래 세 람다는 모두 파라미터가 '하나'다
ages.forEach { it -> println("${it.key}: ${it.value}") }   // it = Entry
ages.forEach { entry -> println("${entry.key}: ${entry.value}") }  // 이름 붙임
ages.forEach { (name, age) -> println("$name: $age") }     // 구조 분해
```

세 람다는 모두 같은 1-인자 람다다. 마지막 람다는 그 인자 하나를 지역 변수 두 개로 풀었을 뿐이다.

### 6.2 map { (k, v) -> } 디슈가링

컴파일러의 번역을 보면 파라미터가 하나라는 점이 분명해진다.

```text
ages.map { (k, v) -> "$k=$v" }
        │
        ▼  번역
ages.map { entry ->                    // 파라미터는 여전히 하나(entry)
    val k = entry.component1()
    val v = entry.component2()
    "$k=$v"
}
```

구조 분해는 람다 본문의 맨 앞에 `val k = ...; val v = ...`를 넣는 것과 같다. 파라미터 개수는 변하지 않는다.

JVM 백엔드에서 이 람다는 `Function1`(1-인자 함수 인터페이스)을 구현하는 객체로 컴파일된다. 파라미터가 정말 두 개였다면 `Function2`가 되었을 것이다. 이 표현 차이는 SAM 변환이나 함수 참조와 함께 쓸 때 드러난다.

한 걸음 더 나아가 보자. 람다는 파라미터를 여러 개 가질 수 있고, 그중 일부만 구조 분해할 수도 있다.

```kotlin
// fold의 람다는 2-인자: (누적값, 원소). 두 번째만 구조 분해
val points = listOf(Point(1, 2), Point(3, 4), Point(5, 6))
val sumX = points.fold(0) { acc, (x, _) -> acc + x }
//                          ↑    ↑ 이 파라미터(Point)를 구조 분해, y는 무시(_)
println(sumX)   // => 9  (1+3+5)
```

이 람다는 파라미터가 두 개다(`acc`와 `Point`). 첫 번째 `acc`는 그대로 두고, 두 번째 파라미터만 `(x, _)`로 구조 분해했다. 이처럼 여러 파라미터 가운데 특정 위치의 것만 해체할 수도 있다.

### 6.3 타입 명시와 함정

람다 파라미터 구조 분해에서도 각 컴포넌트에 타입을 명시할 수 있다.

```kotlin
ages.forEach { (name: String, age: Int) ->
    println("$name: $age")
}
```

그러나 여기에는 미묘한 함정이 있다. 구조 분해 괄호를 쓰면 파라미터 **전체의 타입**을 적을 자리가 사라진다. 즉 `Map.Entry<String, Int>`라는 타입 자체는 쓸 곳이 없고, 각 컴포넌트의 타입만 쓸 수 있다. 대부분은 타입 추론으로 해결되지만, 추론이 되지 않는 문맥에서는 구조 분해 대신 파라미터 이름을 명시하고 본문에서 풀어야 할 수도 있다.

함정이 하나 더 있다. 람다 파라미터 구조 분해는 **componentN을 가진 타입**에서만 할 수 있다. 아무 파라미터나 괄호로 감싼다고 되는 것이 아니다.

```kotlin
listOf("a", "bb", "ccc").map { (c) -> c }
// 컴파일 에러: String에는 component1()이 없음(정확히는 CharSequence.component 없음)
```

`String`에는 `component1()`이 없으므로 구조 분해할 수 없다. 람다 파라미터 구조 분해는 `List`나 `data class`처럼 컴포넌트를 제공하는 타입에서만 통한다.

> [!warning] 흔한 오해
> "`{ (a, b) -> }`는 2-인자 람다다"라는 생각은 틀렸다. 이것은 1-인자 람다에서 그 인자를 두 조각으로 푼 것이다. 이 오해 때문에 함수 타입 시그니처를 잘못 읽게 되고, 특히 `Map`의 `forEach`가 `(Entry) -> Unit`을 받는 확장인지, `(K, V) -> Unit`을 받는 함수인지 헷갈리게 된다.
>
> 실제로 `Map.forEach`(Kotlin의 확장)는 `(Map.Entry<K, V>) -> Unit`을 받으며, `(k, v)`는 그 Entry를 구조 분해한 것이다. 반면 `Map`의 Java `forEach(BiConsumer)`는 2-인자이므로, 상호운용할 때 혼동하지 않도록 주의해야 한다.

## 7. 언더스코어와 부분 해체

### 7.1 _ 로 componentN 호출 자체를 건너뛴다

구조 분해에서 어떤 위치의 값이 필요 없으면 그 자리에 밑줄(underscore) `_`을 쓸 수 있다. 그러면 그 위치에는 지역 변수가 만들어지지 않는다.

```kotlin
data class Rgb(val r: Int, val g: Int, val b: Int)
val color = Rgb(255, 128, 0)

val (_, green, _) = color     // 첫째·셋째는 무시, 가운데만 꺼냄
println(green)                // => 128
```

여기에는 중요한 최적화가 하나 있다. **언더스코어 위치의 `componentN()`은 아예 호출되지 않는다.** 위 예에서 `component1()`(r)과 `component3()`(b)은 호출되지 않고, `component2()`(g)만 호출된다. 컴파일러는 언더스코어를 보면 해당 컴포넌트 접근을 통째로 생략한다.

```text
val (_, green, _) = color
        │
        ▼  번역
val green = color.component2()      // component1(), component3()은 호출 안 함
```

이 최적화는 커스텀 `componentN`이 무거운 계산을 할 때 의미가 있다. `component1()`이 비싼 파싱을 하는데 그 값이 필요 없다면, `_`로 호출을 건너뛰어 실제 비용을 줄일 수 있다.

```kotlin
class Expensive {
    operator fun component1(): Int { println("계산 1"); return 1 }
    operator fun component2(): Int { println("계산 2"); return 2 }
}

val (_, second) = Expensive()   // "계산 2"만 출력됨. "계산 1"은 안 나옴
println(second)                 // => 2
// 출력: 계산 2 / 2
```

`component1()`의 부수 효과("계산 1")가 출력되지 않으므로, 호출이 실제로 생략되었음을 확인할 수 있다.

### 7.2 trailing 생략과 중간 건너뛰기

두 가지 "건너뛰기"를 구분해 보자.

**뒤쪽(trailing) 생략**: 필요한 것보다 적게 요청하면 뒤쪽 컴포넌트는 자연히 호출되지 않는다(2.3절). `val (r, g) = color`는 `component3()`을 호출하지 않는다. 이때는 언더스코어도 필요 없다.

**중간(interior) 건너뛰기**: 앞이나 중간의 컴포넌트를 건너뛰고 뒤의 것을 꺼내려면, 위치를 밀 수 없으므로 반드시 언더스코어로 자리를 채워야 한다.

```kotlin
val (r, g, b) = color

val (r, g)      = color   // b 무시(trailing 생략) — 언더스코어 불필요
val (_, _, b)   = color   // r, g 무시(중간 건너뛰기) — 언더스코어 필수
val (r, _, b)   = color   // g만 무시 — 언더스코어로 자리 유지
```

`b`를 얻으려면 그 값이 세 번째 위치라는 점을 유지해야 하므로, 앞의 두 자리를 `_, _`로 채워야 한다. 언더스코어가 없으면 `component3()`의 값이 첫 번째 변수로 가 버리기 때문이다. 여기서도 **위치가 고정되어 있다는 규칙**이 적용된다.

### 7.3 성능과 의도 표현

언더스코어가 주는 이점은 두 가지로 정리할 수 있다.

**의도 표현**: `_`은 "이 값은 의도적으로 쓰지 않는다"는 뜻을 코드로 나타낸다. 쓰지 않는 변수에 `unused` 경고가 뜨는 것을 피할 수 있고, 읽는 사람에게 "여기 값이 있지만 관심이 없다"는 뜻을 분명히 전한다.

```kotlin
for ((_, count) in wordCounts) {   // 단어는 관심 없고 빈도만
    total += count
}
```

**성능**: 7.1절에서 보았듯이 언더스코어 위치의 `componentN`은 호출이 생략된다. data 클래스의 컴포넌트는 대개 비용이 작으므로 성능 차이가 미미하지만, 커스텀 컴포넌트나 확장 컴포넌트가 무거운 경우에는 실제로 비용을 아낄 수 있다.

주의할 점도 있다. 언더스코어는 구조 분해 선언 하나 안에서 여러 개 쓸 수 있고(`val (_, _, x) = ...`), 각각이 독립적으로 해당 위치를 건너뛴다. 다만 `_` 자체는 변수가 아니므로 나중에 참조할 수 없다. `_`이라는 이름의 지역 변수가 만들어지는 것이 아니라, 그 위치가 통째로 사라지는 것이다.

> [!info] 역사 메모
> 구조 분해 선언의 언더스코어는 Kotlin 1.1(2017)에서 도입되었다. 같은 릴리스에서 람다 파라미터의 언더스코어(`{ _, value -> }`, 즉 사용하지 않는 파라미터)도 함께 들어왔다. 둘은 표기가 같지만 서로 다른 기능이다. 하나는 구조 분해 컴포넌트를 건너뛰고, 다른 하나는 람다 파라미터 자체를 익명으로 만든다. 두 기능을 혼동하지 않도록 주의해야 한다.

## 8. 위치 기반의 함정 (핵심 위험)

이 절은 이 장에서 가장 중요한 부분이다. 구조 분해는 편리한 만큼 위험하다. 이름이 아니라 **위치**에 의존하기 때문이다. 이 절에서는 그 때문에 생기는, 겉으로 드러나지 않는 버그들을 살펴본다.

### 8.1 프로퍼티 순서를 바꾸면 조용히 깨진다

가장 악명 높은 함정이다. data 클래스의 `componentN`은 **선언 순서**를 따른다(3.3절). 그런데 이 순서는 리팩터링 중에 쉽게 바뀐다. 누군가 클래스를 정리하다가 프로퍼티 순서를 바꾸면, 그 클래스를 구조 분해하던 모든 호출부가 **컴파일 에러 없이 조용히 틀린 값을 받게** 된다.

```kotlin
// 버전 1
data class User(val name: String, val email: String)

val (name, email) = getUser()
sendMail(to = email, subject = "환영, $name 님")   // 정상 동작
```

이제 누군가 `User`의 필드를 "알파벳 순으로 정리"한다며 순서를 바꿨다고 하자.

```kotlin
// 버전 2 — email이 앞으로 옴
data class User(val email: String, val name: String)

// 호출부는 그대로! 하지만 이제:
val (name, email) = getUser()
// name  = component1() = 이제 email 값!
// email = component2() = 이제 name 값!
sendMail(to = email, subject = "환영, $name 님")
// to에 사람 이름이, subject에 이메일 주소가 들어감 — 메일 발송 실패 또는 오발송
```

`name` 변수에는 실제로 이메일이 담기고, `email` 변수에는 이름이 담긴다. **두 프로퍼티의 타입이 모두 `String`이라서 컴파일러는 전혀 알아채지 못한다.** 프로그램은 문제없이 컴파일되고 실행되지만 논리는 완전히 뒤집혔다. 이런 버그는 런타임에야, 그것도 프로덕션에서야 발견되는 경우가 많다.

이것이 위치 기반 구조 분해의 근본적인 위험이다. 같은 타입의 프로퍼티가 나란히 있을 때 순서를 바꾸면 컴파일러라는 안전망이 완전히 사라진다. data 클래스가 `componentN`을 자동으로 생성해 준다는 바로 그 편리함이 이 취약성의 원인이다.

### 8.2 같은 타입 필드의 뒤바뀜

8.1절이 리팩터링 시점의 문제라면, 이번에는 처음 코드를 작성할 때부터 생기는 문제다. 같은 타입의 값이 여러 개일 때 어느 위치가 무엇인지 헷갈려서 처음부터 거꾸로 받는 경우다.

```kotlin
data class Range(val min: Int, val max: Int)

fun getTemperatureRange(): Range = Range(min = -5, max = 30)

// 위치를 헷갈려 거꾸로 받음
val (max, min) = getTemperatureRange()   // 이름은 max/min이지만 실제로는...
// max = component1() = -5  (실제 min!)
// min = component2() = 30  (실제 max!)
println("최고 $max, 최저 $min")   // => 최고 -5, 최저 30 (완전히 뒤바뀜)
```

컴파일러는 `max`라는 변수 이름과 `min` 프로퍼티를 대조하지 않으므로 이 실수를 잡지 못한다. 두 값이 모두 `Int`라서 타입 검사도 소용이 없다.

**방어책**은 세 가지다.

- 헷갈릴 여지가 있으면 **구조 분해를 쓰지 말고 이름으로 접근**한다. `val range = getTemperatureRange(); range.min; range.max`는 절대 뒤바뀌지 않는다. 이 방법이 가장 안전하다.
- 구조 분해할 때는 변수 이름을 프로퍼티 이름과 **정확히 일치**시키는 관행을 지킨다(`val (min, max) = ...`). 이름이 프로퍼티와 같으면 적어도 사람이 읽을 때 뒤바뀐 것을 알아챌 여지가 생긴다.
- IDE가 제공하는 구조 분해 힌트(각 위치가 어느 프로퍼티인지 인레이 힌트로 표시)를 켜 둔다. 이것은 언어가 아니라 도구로 보완하는 방법이다.

> [!caution] 성능 주의
> 위치 기반 함정을 피하려고 무조건 이름으로만 접근하는 것도 극단적이다. `for ((k, v) in map)`이나 `partition`의 `(pass, fail)`처럼 관례가 확립되어 오해할 여지가 거의 없는 경우에는 구조 분해가 훨씬 읽기 좋다. 판단 기준은 "이 위치가 무엇인지 한눈에 분명한가"이다. 분명하면 구조 분해를 쓰고, 애매하면 이름으로 접근한다.

### 8.3 이름 기반 구조 분해의 부재 (향후 계획)

1.2절에서 보았듯이 JavaScript는 이름 기반 구조 분해(`const { name, email } = user`)를 제공하므로 위치 함정이 원천적으로 생기지 않는다. 이름으로 매칭하기 때문에 프로퍼티 순서가 바뀌어도 아무 영향이 없다. 반면 Kotlin은 2.x stable 기준으로 **오직 위치 기반만** 지원한다.

Kotlin 팀은 이 한계를 알고 있으며, 이름 기반(또는 프로퍼티 이름 기반) 구조 분해는 오랫동안 언어 발전의 논의 대상이었다. 그러나 **집필 시점(Kotlin 2.x stable)에서 이름 기반 구조 분해는 안정 기능이 아니다.** 앞으로 어떤 형태가 될지, 실제로 도입될지는 확정되지 않았다. 따라서 현재 코드는 위치 기반 구조 분해만 존재한다고 가정하고 작성해야 한다.

지금 이름 기반의 안전성을 얻으려면 구조 분해를 포기하고 프로퍼티에 명시적으로 접근하는 수밖에 없다.

```kotlin
// 위치 기반 구조 분해 (순서 변경에 취약)
val (name, email) = user

// 이름 기반의 안전성을 원하면 — 구조 분해를 쓰지 않는다
val name = user.name       // 순서 무관, 이름으로 확정
val email = user.email
```

후자는 조금 장황하지만, 프로퍼티 순서가 바뀌어도 절대 깨지지 않는다. 구조 분해의 간결함과 이름 접근의 견고함 사이에서 상황에 맞게 선택해야 한다.

> [!note] 명세 기준
> Kotlin의 향후 버전에서 논의되는 이름 기반 구조 분해가 어떤 문법(`val (name = n, email = e) = user` 유형 등)으로 안정화될지는 이 글을 쓰는 시점에 확정되지 않았다. 확정되지 않은 실험 기능이나 제안 기능을 프로덕션 지식으로 가정해서는 안 되므로, 여기서는 "현재는 위치 기반만 안정 기능"이라는 사실만 확실하게 말한다.

### 8.4 커스텀 componentN의 오용

커스텀 `componentN`(9절에서 설계)을 정의할 때는 위치 규칙을 개발자가 직접 관리해야 하므로 함정이 하나 더 생긴다. `component1`과 `component2`의 반환 순서를 프로퍼티 선언과 어긋나게 작성하면, 그 클래스를 구조 분해하는 모든 코드가 예상과 다른 값을 받는다.

```kotlin
class Fraction(val numerator: Int, val denominator: Int) {
    // 실수: 순서를 뒤집어 정의
    operator fun component1() = denominator   // "첫째"인데 분모를 반환!
    operator fun component2() = numerator
}

val (num, den) = Fraction(3, 4)
println("$num/$den")   // => 4/3   (뒤집힘! 3/4를 기대했는데)
```

`Fraction(3, 4)`는 3/4를 뜻하지만, `component1()`이 분모를 반환하도록 잘못 작성되어 있어 구조 분해 결과는 4/3이 된다. 이런 커스텀 컴포넌트의 순서 오류는 클래스 정의 안에 숨어 있으므로 호출부만 봐서는 발견하기가 매우 어렵다.

**원칙**: 커스텀 `componentN`을 정의한다면 반환 순서를 "이 타입을 구조 분해하는 사람이 가장 자연스럽게 기대할 순서"에 정확히 맞추고, 클래스 문서에 그 순서를 명시한다. 순서가 자명하지 않은 타입이라면 처음부터 `componentN`을 제공하지 않는 편이 안전하다. 구조 분해를 막고 이름 있는 프로퍼티 접근만 제공하면 위치 함정이 원천적으로 차단된다.

## 9. 커스텀 componentN 설계와 한계

### 9.1 data 클래스가 아닌 클래스에 componentN 정의하기

data 클래스가 아닌 일반 클래스도 `operator fun componentN()`을 직접 정의하면 구조 분해할 수 있다. 이렇게 하는 경우는 주로 다음 세 가지다.

- data 클래스로 만들 수 없는 경우(예: 이미 다른 클래스를 상속해야 하는 경우. data 클래스에는 상속 제약이 있다)
- equals/hashCode/copy 같은 다른 data 클래스 기능은 원하지 않고 구조 분해만 필요한 경우
- 컴포넌트로 노출하고 싶은 값이 주 생성자 프로퍼티가 아니라 파생값인 경우

```kotlin
// 파생값을 컴포넌트로 노출하는 예
class Duration(val totalSeconds: Long) {
    operator fun component1(): Long = totalSeconds / 3600          // 시
    operator fun component2(): Long = (totalSeconds % 3600) / 60   // 분
    operator fun component3(): Long = totalSeconds % 60            // 초
}

val (hours, minutes, seconds) = Duration(3725)
println("${hours}h ${minutes}m ${seconds}s")   // => 1h 2m 5s
```

`Duration`은 내부적으로 총 초만 저장하지만, 구조 분해하면 시/분/초로 나뉜다. 이 예는 `componentN`이 저장된 필드를 그대로 반환할 필요가 없고, 계산 결과를 반환해도 된다는 점을 보여 준다. data 클래스의 `componentN`은 항상 필드를 그대로 반환하므로, 자동 생성으로는 이런 유연함을 표현할 수 없다.

### 9.2 componentN이 만드는 계약

`componentN`을 공개(public)로 정의하면 그 함수는 클래스의 **공개 API 계약**의 일부가 된다. 이 사실을 가볍게 여겨서는 안 된다.

일단 `component1()`과 `component2()`를 공개하면 외부 코드가 그 순서와 타입에 의존해 구조 분해하기 시작한다. 나중에 순서나 반환 타입을 바꾸면 8.1절에서 본 것처럼 그 코드가 조용히 깨진다. 즉 **컴포넌트의 순서와 타입은 하위 호환성을 지켜야 하는 계약**이다.

이 관점에서 data 클래스가 자동으로 만드는 `componentN`도 다시 봐야 한다. data 클래스의 프로퍼티 순서를 바꾸는 것은 단순한 내부 정리가 아니라 **공개 계약의 변경**이다. 라이브러리 API로 노출되는 data 클래스라면 특히 그렇다. 그래서 널리 쓰이는 data 클래스의 프로퍼티 순서는 함부로 바꾸지 않는 것이 관례다.

```text
componentN이 공개 API 계약인 이유
─────────────────────────────────────
클래스 정의                외부 호출부
─────────────              ─────────────
component1(): A    ◄────   val (a, b) = obj   ← 순서/타입에 의존
component2(): B    ◄────
       │
       ▼ 순서를 바꾸면
component1(): B    ◄────   val (a, b) = obj   ← a에 B가, b에 A가 (조용히 깨짐)
component2(): A
```

### 9.3 중첩 구조 분해의 부재와 대안

Kotlin 구조 분해의 마지막 큰 한계는 **중첩(nested) 구조 분해가 안 된다**는 것이다. JavaScript는 `const { a: { b, c } } = obj`처럼 중첩된 구조를 한 번에 풀 수 있지만, Kotlin에는 이런 문법이 없다.

```kotlin
data class Point(val x: Int, val y: Int)
data class Segment(val start: Point, val end: Point)

val seg = Segment(Point(0, 0), Point(3, 4))

// 중첩 구조 분해 — 문법 에러
val ((sx, sy), (ex, ey)) = seg    // 컴파일 에러: 이런 문법 없음
```

`val ((sx, sy), (ex, ey))` 같은 중첩 괄호는 Kotlin 문법에서 허용되지 않는다. 구조 분해는 **한 단계(one level)만** 들어간다. 각 컴포넌트를 다시 분해하려면 별도의 선언으로 풀어야 한다.

```kotlin
// 대안 1: 단계별로 푼다
val (start, end) = seg
val (sx, sy) = start
val (ex, ey) = end
println("$sx,$sy -> $ex,$ey")   // => 0,0 -> 3,4

// 대안 2: 필요한 것만 이름으로 접근 (더 명확할 때가 많다)
val startX = seg.start.x
val endY = seg.end.y
```

Kotlin은 왜 중첩 구조 분해를 지원하지 않을까? 한 가지 이유는 위치 기반 구조 분해의 취약성이 중첩되면 더 심해지기 때문이다. `val ((a, b), (c, d)) = ...`는 네 위치를 동시에 기억해야 하고, 그중 하나라도 순서가 바뀌면 추적하기가 매우 어려워진다. 얕은(한 단계) 구조 분해만 지원하는 것은 이런 복잡도를 억제하려는 보수적인 선택으로 볼 수 있다. 깊은 구조를 풀어야 한다면 단계별 분해나 이름 접근이 더 읽기 좋고 안전하다.

또한 구조 분해는 **널 안전성과도 잘 어울리지 않는다**([[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]). nullable 값은 바로 구조 분해할 수 없다. 널 참조에 `component1()`을 호출할 수 없기 때문이다.

```kotlin
val maybe: Point? = getPointOrNull()
val (x, y) = maybe    // 컴파일 에러: nullable에는 component1()을 호출할 수 없음

// 널을 먼저 처리해야 한다
maybe?.let { (x, y) ->      // let 안에서는 non-null로 스마트 캐스트됨
    println("$x, $y")
}
// 또는
if (maybe != null) {
    val (x, y) = maybe      // 스마트 캐스트로 non-null
    println("$x, $y")
}
```

`?.let { (x, y) -> ... }`에서는 값이 널이 아닐 때만 람다가 실행되고, 그 안에서 파라미터가 non-null `Point`로 좁혀지므로 구조 분해할 수 있다. 6절의 람다 파라미터 구조 분해와 6장(널 안전성)의 `?.let` 관용구를 함께 쓰는 흔한 패턴이다.
