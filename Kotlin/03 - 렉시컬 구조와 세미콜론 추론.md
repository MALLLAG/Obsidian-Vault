**이 장이 답하는 질문:**

- 컴파일러가 소스 텍스트를 처음 마주할 때, `val x = 1`이라는 문자열은 정확히 어떤 단위로 잘려서 파서에게 넘어가는가?
- Kotlin에는 왜 세미콜론이 "선택적"인가? 자바스크립트의 ASI(자동 세미콜론 삽입)와 무엇이 같고 무엇이 다른가?
- `val x = 1` 다음 줄에 `+ 2`를 쓰면 왜 `x`가 `3`이 아니라 `1`이 되는가?
- 왜 `listOf(1,2,3)` 다음 줄에 `.map { ... }`을 쓰는 체이닝은 되는데, `1` 다음 줄에 `shl 2`를 쓰는 건 안 되는가?
- `return` 다음 줄에 값을 쓰면 왜 그 값이 반환되지 않는데, `throw`는 다음 줄에 예외를 써도 되는가?
- `fun`, `data`, `it`, `field`는 다 키워드인가? 왜 어떤 건 변수 이름으로 쓸 수 있고 어떤 건 안 되는가?
- `0x10`, `0b1010`은 되는데 왜 `010`(8진수)은 Kotlin에서 에러이거나 십진수 10인가?
- `` `fun` ``처럼 백틱으로 감싸면 키워드도 식별자가 되는 이유는 무엇이고, 그 한계는 어디까지인가?

앞선 [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]에서 우리는 컴파일 파이프라인의 전체 지형—프론트엔드(파싱·리졸션·타입추론)에서 IR을 거쳐 JVM 바이트코드/Native/JS/Wasm 백엔드로 갈라지는 흐름—을 조감했다. 그 파이프라인의 가장 첫 관문, 소스 문자열이 의미 있는 조각으로 처음 쪼개지는 자리가 **렉싱(lexing, 어휘 분석)** 이다. 이 장은 바로 그 관문에 현미경을 댄다. 컴파일러가 `.kt` 파일의 바이트 스트림을 읽어 **토큰(token)** 의 시퀀스로 바꾸는 규칙, 그리고 그 규칙이 만들어 내는 놀랍도록 실무적인 함정들—특히 **세미콜론 추론(semicolon inference)**—이 이 장의 주제다.

이 장이 다루는 것과 다루지 않는 것의 경계를 먼저 못박자. 이 장은 *토큰 수준*의 이야기다. 즉 문자열이 어떻게 키워드·식별자·리터럴·연산자·구두점·줄바꿈으로 잘리는가, 그 조각들 사이에서 문장의 끝이 어떻게 추론되는가까지다. 그 토큰들이 *어떤 문법 구조로 조립되어 선언과 패키지를 이루는가*는 [[04 - 파일과 패키지와 선언 - 프로그램의 골격]]의 몫이다. 리터럴이 *어떤 타입으로 추론되고 어떻게 표현되는가*(예: `Int` 대 `Long`, 박싱)는 [[07 - 수 1 - Int와 Long과 부동소수점]]과 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]가, 문자열의 *유니코드 의미론*은 [[09 - 문자와 문자열 - 유니코드와 템플릿]]이 소유한다. 여기서는 그 리터럴들이 소스에서 *어떻게 생겼는가*(렉시컬 형태)만 본다.

이 장의 논증 궤적은 이렇다. 먼저 렉서가 무엇을 만들어 내는지(토큰의 분류)를 보고, 그 중 사람이 가장 헷갈려 하는 세 부류—키워드, 식별자, 리터럴—를 차례로 해부한다. 그다음 연산자·구두점 토큰과 "가장 긴 일치(maximal munch)" 규칙을 짚고, 마지막 두 대섹션에서 이 장의 하이라이트인 **세미콜론 추론**의 원리와 함정을 밑바닥까지 판다. 결론에서 우리는 이 모든 규칙이 사실 하나의 설계 철학—"기계가 사람의 의도를 최대한 추론하되, 추론이 위험한 곳에서는 침묵하지 않는다"—의 표현임을 보게 될 것이다.

## 1. 렉싱이라는 첫 번째 관문 — 소스 텍스트에서 토큰으로

### 1.1 파이프라인에서 렉서의 자리

컴파일러가 `Circle.kt`를 열면, 그 안에 든 것은 사람에게는 코드지만 기계에게는 그저 문자(정확히는 유니코드 코드포인트)의 일차원 스트림이다. 이 스트림을 의미 단위로 쪼개는 첫 단계가 렉서(어휘 분석기)다. 렉서의 출력은 파서가 소비할 **토큰 시퀀스**다.

```text
소스 텍스트           렉서              토큰 시퀀스               파서
"val r = 5"    ──▶  [어휘 분석]  ──▶  VAL · WS · IDENT("r")    ──▶  [문법 분석]
                                      · WS · ASSIGN · WS         ──▶  프로퍼티 선언 노드
                                      · INT_LIT("5") · EOF
```

렉서는 문맥을 (거의) 모른다. 그저 규칙표에 따라 "이 위치에서 가장 긴, 규칙에 맞는 문자열 조각"을 하나의 토큰으로 떼어 낼 뿐이다. 그래서 렉서를 정규 언어(regular language) 수준의 기계, 파서를 문맥 자유 문법(context-free grammar) 수준의 기계로 나눠 부른다. 이 분업이 이 장 전체를 관통하는 핵심이다. **세미콜론 추론의 상당 부분은 렉서가 만든 "줄바꿈 토큰"을 파서가 문맥에 따라 무시하거나 존중하는 협업**으로 일어난다. 이 점은 7절에서 정면으로 다룬다.

> **명세 정밀**: Kotlin의 문법은 공식적으로 두 겹의 문법으로 명세된다—어휘 문법(lexical grammar, 토큰을 정의)과 구문 문법(syntactic grammar, 토큰으로 프로그램을 정의). `grammar.kotlinlang.org`에 ANTLR 형식으로 공개되어 있다. 이 장에서 인용하는 규칙명(`semi`, `memberAccessOperator`, `jumpExpression` 등)은 그 문법의 실제 규칙이다. 다만 프로덕션 컴파일러(K2/FIR)는 이 문법을 그대로 구현하지 않고 손으로 작성된 렉서·파서를 쓰므로, 여기서는 "관찰 가능한 동작"과 "명세 문법"을 함께 제시하되 구현 세부는 "구현에 따라"로 한정한다.

### 1.2 토큰의 여섯 부류

Kotlin 소스에서 렉서가 만들어 내는 토큰은 크게 여섯 부류로 나눌 수 있다.

| 부류 | 예 | 이 장에서 다루는 절 |
|------|-----|------|
| 키워드(keyword) | `fun`, `val`, `when`, `data`, `it` | 2절 |
| 식별자(identifier) | `radius`, `반지름`, `` `class` `` | 3절 |
| 리터럴(literal) | `42`, `3.14`, `'a'`, `"hi"`, `true`, `null` | 4절 |
| 연산자·구두점(operator/punctuation) | `+`, `?.`, `..<`, `::`, `->`, `,`, `(` | 6절 |
| 주석(comment) | `// ...`, `/* ... */`, `/** ... */` | 5절 |
| 공백·줄바꿈(whitespace/newline) | 스페이스, 탭, `\n` | 1.3, 7절 |

이 중 대부분은 파서가 그대로 소비하지만, **공백과 주석은 "트리비아(trivia)"** 로 취급되어 파서에게는 대체로 보이지 않는다(리졸션·타입추론에 영향을 주지 않는다). 결정적 예외가 **줄바꿈**이다. 줄바꿈은 공백처럼 생겼지만 완전히 버려지지 않고, 파서가 문맥에 따라 "문장 종결자"로 쓸 수 있는 **의미 있는 토큰(NL)** 으로 남는다. 이 비대칭—스페이스는 무의미하지만 줄바꿈은 의미가 있다—이 세미콜론 추론의 전제다.

### 1.3 소스의 인코딩·공백·줄바꿈

Kotlin 소스 파일의 인코딩은 UTF-8이 표준이다. 렉서는 유니코드 코드포인트 단위로 소스를 읽으므로, 식별자·문자열·주석에 한글·이모지·수학 기호를 자유롭게 쓸 수 있다(식별자 규칙의 한계는 3절에서).

공백으로 취급되는 문자는 스페이스(`U+0020`), 탭(`U+0009`), 그리고 몇몇 유니코드 공백이다. **인덴트(들여쓰기)는 문법적으로 무의미하다.** Python과 달리 Kotlin은 블록을 중괄호 `{}`로 구분하지, 들여쓰기 깊이로 구분하지 않는다. 아래 두 코드는 렉싱·파싱 결과가 완전히 동일하다.

```kotlin
fun area(r: Double) = 3.14159 * r * r

fun area(r:Double)=3.14159*r*r     // 공백을 다 지워도 동일 (토큰 경계만 유지되면)
```

줄바꿈은 `\n`(LF), `\r\n`(CRLF), `\r`(CR) 모두 하나의 논리적 줄바꿈으로 정규화되어 NL 토큰이 된다. 즉 Windows(`\r\n`)와 Unix(`\n`) 소스가 렉싱 관점에서 같게 동작한다.

> **역사 메모**: 파일 맨 앞의 **바이트 순서 표시(BOM, `U+FEFF`)** 와 **셔뱅(shebang) 줄**(`#!...`)은 특별 취급된다. 셔뱅은 Kotlin 스크립트(`.kts` 및 CLI 스크립트)를 실행 파일처럼 만들기 위해 파일 첫 줄에 `#!/usr/bin/env kotlin` 같은 줄을 허용한 것이다. 일반 `.kt` 소스에서 `#`는 유효한 토큰이 아니므로, 셔뱅은 "파일 첫 줄에 한해 무시되는 특례"다.

### 1.4 렉서는 문맥을 얼마나 아는가

앞서 렉서가 문맥을 "거의" 모른다고 했다. 완전히 모른다고 하지 않은 이유가 있다. Kotlin에는 렉서가 국소적 문맥(직전/직후 문자의 공백 여부)에 민감한 몇몇 토큰이 있다. 대표적으로 안전 호출 `?.`의 `?`는 "뒤에 공백이 없는 물음표(`QUEST_NO_WS`)"와 "뒤에 공백이 있는 물음표(`QUEST_WS`)"로 구분되어 렉싱된다. 이 미묘한 구분이 nullable 타입 표기(`Int?`)와 안전 호출(`a?.b`)과 엘비스(`a ?: b`)를 문법적으로 분리한다. 자세한 건 6.4에서 본다. 여기서 기억할 것은, Kotlin의 렉서가 완전한 문맥 무지(context-free) 기계가 아니라 국소 공백을 살피는 실용적 기계라는 점이다.

## 2. 키워드의 3분류 (그리고 특수 식별자)

키워드는 언어가 특별한 의미를 부여한 단어다. 많은 언어에서 키워드는 "예약어(reserved word)"—절대 식별자로 쓸 수 없는 단어—와 동의어다. Kotlin은 여기서 실용적 타협을 한다. 키워드를 **세 등급**으로 나눠, 어떤 것은 완전히 예약하고 어떤 것은 특정 문맥에서만 키워드로 취급해 나머지 문맥에서는 평범한 식별자로 쓰게 한다. 이 설계 덕분에 `data`, `value`, `field` 같은 자주 쓰이는 단어를 변수 이름으로도 자유롭게 쓸 수 있다.

### 2.1 하드 키워드 — 절대 예약어

**하드 키워드(hard keyword)** 는 어디서든 항상 키워드다. 식별자로 쓸 수 없다(백틱으로 감싸는 예외는 3.2절). 전체 목록은 다음과 같다.

```text
as   as?  break  class  continue  do   else  false  for  fun  if
in   !in  interface  is  !is  null  object  package  return  super
this  throw  true  try  typealias  typeof  val  var  when  while
```

이들을 변수 이름으로 쓰면 즉시 렉싱 이후 문법 오류가 난다.

```kotlin
val class = 3      // 컴파일 에러: expecting property name or receiver type
val fun = { }      // 컴파일 에러: expecting property name
val is = true      // 컴파일 에러
```

`in`, `is`는 하드 키워드이며, 부정형 `!in`, `!is`는 **한 개의 토큰**으로 렉싱된다(6절의 maximal munch). `as?`도 하나의 토큰이다.

> **흔한 오해**: `typeof`는 하드 키워드 목록에 있지만 Kotlin에는 `typeof` 연산자가 없다. 미래 확장을 위해 예약만 해 둔 단어라 지금 쓰면 그냥 오류다. 반대로 `it`은 키워드처럼 느껴지지만 하드 키워드가 아니다(2.4절).

### 2.2 소프트 키워드 — 문맥 의존

**소프트 키워드(soft keyword)** 는 특정 구문 위치에서만 키워드로 해석되고, 그 밖에서는 평범한 식별자다. 목록:

```text
by  catch  constructor  delegate  dynamic  field  file  finally
get  import  init  param  property  receiver  set  setparam  value  where
```

예컨대 `value`는 `@JvmInline value class Money(...)`(→ [[36 - 타입 별칭과 인라인 value class]])에서는 키워드지만, 그냥 변수 이름으로도 완벽히 유효하다.

```kotlin
fun demo() {
    val value = 42          // OK: value는 여기선 식별자
    val by = "delegate"     // OK: by도 식별자로 쓸 수 있음
    val where = "here"      // OK
    println(value + by.length + where.length)   // => 54
}
```

`get`/`set`은 프로퍼티 접근자 선언(→ [[22 - 프로퍼티와 백킹 필드]])에서만 키워드다.

```kotlin
val radius: Double = 5.0
    get() = field          // 여기서 get은 키워드, field도 키워드(백킹 필드)

fun scope() {
    val get = "not a getter here"   // OK: get은 식별자
    println(get)                     // => not a getter here
}
```

### 2.3 모디파이어 키워드 — 선언 수식어 자리에서만

**모디파이어 키워드(modifier keyword)** 는 선언의 수식어(modifier) 목록에 나타날 때만 키워드이고, 그 외에는 식별자다. 목록:

```text
abstract  actual  annotation  companion  const  crossinline  data
enum  expect  external  final  infix  inline  inner  internal
lateinit  noinline  open  operator  out  override  private  protected
public  reified  sealed  suspend  tailrec  vararg
```

이 목록에 `data`, `open`, `sealed`, `enum`, `inline`, `operator`, `suspend` 같은 매우 흔한 단어가 다 들어 있다. 그런데도 이들을 변수·함수 이름으로 자유롭게 쓸 수 있다.

```kotlin
fun process() {
    val data = listOf(1, 2, 3)     // OK: data는 식별자
    val open = true                 // OK
    val sealed = false              // OK
    fun operator() = "hi"           // OK: operator라는 이름의 함수
    println(data.size)              // => 3
}

data class Point(val x: Int, val y: Int)   // 여기서 data는 모디파이어 키워드
```

`suspend`가 모디파이어 키워드라는 사실은 실용적으로 중요하다. `suspend`는 함수 선언 앞(`suspend fun fetch()`)이나 함수 타입 앞(`suspend () -> Int`)에서만 키워드이고, 그 밖에서는 식별자다(→ [[42 - suspend와 코루틴 - 언어 수준의 중단]], M33·M34 참조).

### 2.4 특수 식별자 — `it`과 `field`

마지막으로 컴파일러가 특정 문맥에서 "자동으로 이름을 정의해 주는" 특수 식별자가 있다.

- **`it`**: 파라미터가 하나인 람다의 암시적 파라미터 이름(→ [[13 - 함수 타입과 람다와 함수 참조]], M42 참조). 그러나 `it`은 키워드가 아니라 식별자이므로, 변수 이름으로 얼마든지 쓸 수 있다.

```kotlin
fun demo() {
    val it = "I am a normal variable"   // OK: it은 식별자
    println(it)                          // => I am a normal variable
    listOf(1, 2, 3).forEach { println(it) }   // 여기 it은 람다의 암시적 파라미터
}
```

- **`field`**: 프로퍼티 접근자 본문 안에서만 백킹 필드를 가리키는 특수 식별자(→ [[22 - 프로퍼티와 백킹 필드]]). 그 밖에서는 식별자다.

이 3+1 등급을 표로 정리하면 렉서/파서가 문맥에 따라 얼마나 정교하게 단어의 신분을 판정하는지 보인다.

| 등급 | 예약 강도 | 예 | 다른 문맥에서 식별자? |
|------|-----------|-----|:---:|
| 하드 키워드 | 항상 예약 | `fun`, `val`, `when`, `class`, `return` | ✗ (백틱만) |
| 소프트 키워드 | 특정 구문에서만 | `by`, `get`, `where`, `value`, `catch` | ✓ |
| 모디파이어 키워드 | 수식어 자리에서만 | `data`, `open`, `sealed`, `suspend`, `inline` | ✓ |
| 특수 식별자 | 컴파일러가 문맥 주입 | `it`, `field` | ✓ |

> **명세 정밀**: 이 3분류가 가능한 것은 Kotlin 문법이 이들을 렉서 단계가 아니라 파서 단계에서 구분하기 때문이다. 렉서는 `data`를 그냥 "식별자 토큰"으로 떼어 내고, 파서가 "이 식별자가 클래스 선언의 수식어 자리에 있는가?"를 보고 키워드로 승격시킨다. 하드 키워드만 렉서 단계에서 고정된 토큰이다. 이 분업 덕분에 언어에 새 소프트/모디파이어 키워드를 추가해도(예: `value`, `expect`/`actual`) 기존 코드의 식별자가 깨지지 않는 **하위호환 진화**가 가능하다.

## 3. 식별자와 백틱 이스케이프

### 3.1 일반 식별자 규칙

식별자는 이름이다—변수, 함수, 클래스, 파라미터, 패키지의 이름. Kotlin 식별자의 어휘 규칙은 대략 다음과 같다.

$$\text{Identifier} = (\text{Letter} \mid \text{\_})\ (\text{Letter} \mid \text{\_} \mid \text{UnicodeDigit})^{*}$$

즉 첫 글자는 유니코드 문자(letter) 또는 밑줄 `_`이고, 그 뒤로 문자·밑줄·유니코드 숫자가 온다. 핵심은 "Letter"가 ASCII `a-z`, `A-Z`에 국한되지 않고 **유니코드 문자 범주 전체**라는 점이다. 그래서 한국어 개발자에게 반가운 다음이 전부 합법이다.

```kotlin
val 반지름 = 5.0                       // OK: 한글 식별자
val π = 3.141592653589793             // OK: 그리스 문자
val 넓이 = π * 반지름 * 반지름          // OK
val café = "coffee"                    // OK: 결합 문자 포함
println(넓이)                          // => 78.53981633974483
```

주의: 밑줄 `_` 하나만으로 된 식별자(`val _ = ...`)는 "값을 버린다"는 특수 의미를 가지므로 일반 이름으로는 피한다(→ [[20 - 구조 분해]]). 그리고 이모지(😀)는 유니코드 "문자(letter)"가 아니라 기호/그림 범주라서 일반 식별자로는 쓸 수 없다—백틱으로 감싸도 JVM 백엔드에서는 대개 거부된다(3.3절).

### 3.2 백틱 이스케이프 식별자

하드 키워드를 이름으로 써야 할 때가 있다. 대표적으로 Java 라이브러리가 `is`, `in`, `object` 같은 Kotlin 하드 키워드를 멤버 이름으로 가지고 있어 Kotlin에서 호출해야 할 때다. 이를 위해 Kotlin은 **백틱 이스케이프**를 제공한다. 이름을 백틱 `` ` `` 으로 감싸면, 그 안의 내용은 무조건 식별자로 취급된다.

```kotlin
// 하드 키워드를 이름으로 사용
val `fun` = "this is fun"
val `class` = "no class"
val `is` = true
println(`fun`)     // => this is fun

// 자바 상호운용: 자바의 Thread.getName()이 Kotlin 키워드와 충돌한다고 가정
// javaObject.`in`   // 자바 필드 in에 접근

// 이름에 공백·특수문자 (주로 테스트 함수명에)
fun `radius should be positive`() { /* ... */ }
```

가장 흔한 실전 용도는 **테스트 함수 이름을 서술문으로 쓰는 것**이다. JUnit 같은 테스트 프레임워크에서 `` fun `사각형 넓이는 가로 곱하기 세로다`() `` 처럼 쓰면 리포트에 사람이 읽는 문장이 그대로 나온다.

### 3.3 백틱의 한계 — JVM의 벽

백틱이 무엇이든 넣게 해 주는 건 아니다. 어휘적으로는 백틱 안에 거의 모든 문자를 넣을 수 있지만, **컴파일 대상 플랫폼의 제약**이 벽으로 작용한다.

> **명세 정밀**: JVM 백엔드에서는 클래스·메서드·필드 이름이 JVM 명세의 제약을 받는다. 이름에 `.`, `;`, `[`, `]`, `/`, `<`, `>`, `:`, `\` 문자를 쓸 수 없다. 따라서 `` `my.name` `` 이나 `` `a/b` `` 는 JVM 백엔드에서 거부된다. 흥미롭게도 **공백은 허용**되므로 테스트 함수의 서술문 이름이 가능한 것이다. 이 제약은 백엔드마다 다르다—Kotlin/JS나 Native는 규칙이 다르므로, 여기서 든 금지 문자 집합은 "JVM 백엔드에서"라고 한정한다.

또 하나: 백틱 안에 백틱 자신을 넣을 수는 없고, 줄바꿈도 넣을 수 없다. 백틱 식별자는 어디까지나 "한 줄 안의 이스케이프된 이름"이다.

### 3.4 섀도잉과 이름 해소는 렉싱 이후

식별자가 어느 선언을 가리키는지(이름 해소, name resolution)와 안쪽 스코프가 바깥 이름을 가리는지(섀도잉, shadowing)는 **렉싱이 아니라 파싱·리졸션 단계의 문제**다. 렉서는 그저 `radius`라는 식별자 토큰을 만들 뿐, 그것이 어떤 `radius`인지 모른다. 이 장은 렉싱까지만 다루므로 이름 해소의 규칙은 [[04 - 파일과 패키지와 선언 - 프로그램의 골격]]과 스코프를 다루는 [[14 - 클로저와 캡처]]로 넘긴다. 다만 렉시컬 수준에서 하나 못박아 두자. **같은 철자의 식별자 토큰은 렉서에게 전부 동일하다.** 신분은 파서가 부여한다.

## 4. 리터럴 — 값의 어휘적 형태

리터럴은 소스에 값을 직접 적는 표기다. Kotlin의 리터럴은 정수·부동소수·문자·문자열·불리언·null의 여섯 종류다. 이 절은 각각의 *어휘적 형태*(어떻게 생겼는가)에 집중하고, 그 값들이 *어떤 타입으로 추론되고 표현되는가*는 뒤 장으로 위임한다.

### 4.1 정수 리터럴 — 진법과 분리자, 그리고 없는 것들

정수 리터럴은 세 가지 진법으로 쓸 수 있다.

```kotlin
val dec = 255          // 십진수
val hex = 0xFF         // 16진수 (0x 접두)  => 255
val bin = 0b1111_1111  // 2진수  (0b 접두)  => 255
val long = 255L        // Long 접미사 L (소문자 l은 1과 혼동되어 금지)
```

여기서 Kotlin의 렉시컬 설계가 드러난다.

**8진수가 없다.** C·Java에는 `010`이 8진수 8을 뜻하는 악명 높은 규칙이 있다. Kotlin은 이 함정을 아예 없앴다. Kotlin에는 8진수 리터럴 문법이 없고, 게다가 **십진수 리터럴에 불필요한 선행 0을 허용하지 않는다**.

```kotlin
val a = 010    // 컴파일 에러: 선행 0 금지 (8진수로 착각할 여지를 제거)
val b = 0      // OK: 0 하나는 괜찮다
val c = 0x0A   // OK: 16진수는 접두가 명확하므로 문제없음
```

> **역사 메모**: C 계열 언어에서 `int mask = 0755;`(파일 권한을 8진수로 쓰려던 코드)가 있을 때, Kotlin으로 옮기면 `0755`는 컴파일 오류가 된다. 이는 버그가 아니라 의도된 방어다. 8진수를 정말 쓰고 싶으면 명시적으로 변환하거나(`"755".toInt(8)`), 비트값이면 2진수/16진수 리터럴을 쓰라는 것이 Kotlin의 입장이다. "가독성 있는 표기가 하나 줄어드는 대신, 조용한 오해석이 사라진다"는 교환이다.

**밑줄 분리자.** 긴 숫자의 가독성을 위해 자릿수 사이에 밑줄 `_`을 넣을 수 있다. 밑줄은 값에 아무 영향이 없다(렉서가 무시).

```kotlin
val credit = 1_000_000            // => 1000000
val bytes  = 0xFF_EC_DE_5E        // 16진수 그룹핑
val bits   = 0b0100_1000_1010     // 니블 단위 그룹핑
val bad1   = 1__000               // OK 실제로는 연속 밑줄도 허용되지만 스타일상 지양
val bad2   = _1000                // 컴파일 에러: 밑줄로 시작 불가 (식별자로 렉싱됨)
val bad3   = 1000_                // 컴파일 에러: 밑줄로 끝날 수 없음
```

밑줄은 숫자 *사이*에만 올 수 있다. 맨 앞·맨 뒤·접두(`0x`) 직후·접미(`L`) 직전에는 못 온다. 특히 `_1000`은 밑줄로 시작하므로 숫자가 아니라 **식별자**로 렉싱되어 "정의되지 않은 이름" 오류가 난다—렉싱 규칙이 의미를 바꾸는 좋은 예다.

리터럴의 기본 추론 타입(`Int`, 넘치면 `Long`), 표현(JVM 백엔드의 원시형 컴파일, M4), 오버플로 동작은 [[07 - 수 1 - Int와 Long과 부동소수점]]과 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]의 몫이다. 여기서는 어휘적 형태까지다.

### 4.2 부동소수 리터럴

부동소수 리터럴은 소수점 또는 지수 표기를 포함한다. 기본 타입은 `Double`, 접미사 `f`/`F`를 붙이면 `Float`다.

```kotlin
val pi   = 3.14159        // Double
val g    = 9.8f           // Float (f 접미)
val big  = 6.022e23       // 지수 표기 (Double)
val small = 1.6e-19       // 음수 지수
val d2    = 100.0         // Double, 소수부 필수
```

Kotlin의 부동소수 리터럴에는 두 가지 어휘적 제약이 있다.

**소수점 양쪽에 숫자가 있어야 한다.** C·Java가 허용하는 `.5`(앞자리 생략)나 `5.`(뒷자리 생략)는 Kotlin에서 부동소수 리터럴이 아니다.

```kotlin
val a = .5      // 컴파일 에러: 앞자리 숫자 필요 → 0.5로 써야 함
val b = 5.      // '5.'는 리터럴이 아님. 5 다음에 . 토큰이 온 것으로 렉싱됨
```

이 규칙은 렉싱 모호성을 없앤다. `5.toLong()`에서 `5.`은 "정수 `5` 뒤에 멤버 접근 `.`"으로 명확히 갈린다. 만약 `5.`을 부동소수로 렉싱했다면 `5.toLong()`이 모호해졌을 것이다. 그래서 Kotlin에서 정수 리터럴에 멤버를 호출할 때 `5.toLong()`처럼 붙여 써도 안전하다.

**16진수 부동소수가 없다.** Java의 `0x1.8p1` 같은 16진수 부동소수 리터럴을 Kotlin은 지원하지 않는다. 부동소수는 십진 표기만 가능하다.

NaN·무한대·`-0.0` 같은 IEEE 754의 미묘함, 그리고 `Float`/`Double`의 동등성 함정은 [[08 - 수 2 - 박싱과 오버플로와 비트와 부호 없는 정수]]와 [[10 - 불리언과 동등성과 동일성]]으로 넘긴다.

### 4.3 문자 리터럴

문자 리터럴은 작은따옴표로 감싼 **하나의 문자**다. Kotlin의 `Char`는 자바처럼 UTF-16 코드 유닛 하나(16비트)이지 정수가 아니다(→ [[09 - 문자와 문자열 - 유니코드와 템플릿]]).

```kotlin
val a = 'A'          // Char
val nl = '\n'        // 이스케이프: 개행
val tab = '\t'       // 탭
val quote = '\''     // 작은따옴표 이스케이프
val back = '\\'      // 역슬래시
val uni = 'é'   // 유니코드 문자 é (직접 표기, 이스케이프 아님)
val won = '₩'   // ₩
```

허용되는 이스케이프 시퀀스는 정해져 있다: `\t`, `\b`, `\n`, `\r`, `\'`, `\"`, `\\`, `\$`, 그리고 `\uXXXX`(정확히 네 자리 16진수) 유니코드 이스케이프. C의 8진 이스케이프(`\101`)는 없다.

```kotlin
val bad1 = 'ab'      // 컴파일 에러: 문자는 하나만
val bad2 = ''        // 컴파일 에러: 빈 문자 리터럴 불가
val bad3 = '\x41'    // 컴파일 에러: \x 이스케이프 없음 (Kotlin은 \u만)
```

한 가지 유니코드 함정을 예고한다. `'😀'`처럼 BMP(기본 다국어 평면)를 벗어난 문자는 UTF-16에서 **서로게이트 쌍**(코드 유닛 2개)으로 표현되므로 `Char` 하나에 담기지 않는다. 이건 [[09 - 문자와 문자열 - 유니코드와 템플릿]]의 핵심 주제다.

### 4.4 문자열 리터럴 — 렉싱 관점

문자열 리터럴은 두 형태다: **이스케이프 문자열**(큰따옴표 하나)과 **원시 문자열(raw string)**(큰따옴표 셋).

```kotlin
val esc = "line1\nline2\t\"quoted\""      // 이스케이프 해석됨
val raw = """
    C:\Users\name          라고 써도 \n이 개행이 아님
    "따옴표"도 그냥 문자
""".trimIndent()
```

렉싱 관점에서 문자열은 단순한 토큰이 아니다. **문자열 템플릿** 때문이다. `"$name"`이나 `"${expr}"`처럼 문자열 안에 표현식을 끼워 넣을 수 있는데, 이 안의 표현식은 렉서/파서가 다시 재귀적으로 파싱해야 한다. 즉 문자열 리터럴은 "여러 조각으로 이루어진 복합 토큰 구조"다.

```kotlin
val name = "사각형"
val w = 3; val h = 4
val msg = "$name: 넓이는 ${w * h}, 둘레는 ${2 * (w + h)}"
// => 사각형: 넓이는 12, 둘레는 14
```

렉시컬 규칙:

- `$` 뒤에 식별자가 바로 오면 단순 삽입: `$name`. `$`와 식별자 사이에 공백이 있으면 삽입이 아니라 리터럴 `$`.
- `${ ... }`은 임의의 표현식 삽입.
- 이스케이프 문자열에서 리터럴 `$`를 쓰려면 `\$`.
- **원시 문자열에는 이스케이프가 없으므로** 리터럴 `$`가 필요하면 `${'$'}`라는 관용구를 쓴다(원시 문자열 안에 `$` 문자 하나를 삽입하는 표현식).

```kotlin
val price = 100
val a = "가격: \$${price}"      // 이스케이프 문자열: => 가격: $100
val b = """가격: ${'$'}$price"""  // 원시 문자열: => 가격: $100
```

문자열의 불변성, `CharSequence` 계약, UTF-16 의미론, `trimIndent`/`trimMargin`의 세부는 [[09 - 문자와 문자열 - 유니코드와 템플릿]]이 소유한다. 여기서는 "문자열 리터럴이 템플릿 때문에 렉싱상 재귀 구조를 가진다"는 점만 못박는다.

### 4.5 불리언과 null

가장 단순한 리터럴 셋: `true`, `false`, `null`. 셋 다 하드 키워드로 렉싱되며 각각 `Boolean`의 두 값과, 모든 nullable 타입의 바닥값이다.

```kotlin
val flag: Boolean = true
val nothing: String? = null
```

`null`이 어떤 타입 체계 안에 있는지(nullable 타입, `Nothing?`), `true`/`false`가 단축 평가와 어떻게 엮이는지는 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]과 [[10 - 불리언과 동등성과 동일성]]으로 위임한다. 리터럴로서 이들은 그냥 예약된 세 단어다.

## 5. 주석과 KDoc

### 5.1 라인 주석과 블록 주석

Kotlin의 주석은 세 종류다.

```kotlin
// 라인 주석: 줄 끝까지

/* 블록 주석:
   여러 줄에 걸칠 수 있다 */

/** KDoc: 문서화 주석 (5.2절) */
```

렉서 관점에서 주석은 **트리비아**다—토큰으로 파서에게 넘어가지 않고 폐기된다(단 KDoc는 도구가 별도로 수집). 따라서 주석은 코드의 의미에 영향을 주지 않는다. 단, 라인 주석이 줄바꿈을 "먹지는" 않는다는 점은 세미콜론 추론과 얽혀 중요하다. `foo() // 설명` 다음의 줄바꿈은 여전히 NL 토큰으로 남아 문장을 종결시킨다.

### 5.2 블록 주석은 중첩된다

여기 Kotlin이 C·Java와 다른 어휘적 특징이 하나 있다. **Kotlin의 블록 주석은 중첩(nesting)이 가능하다.**

```kotlin
/* 바깥 주석 시작
   /* 안쪽 주석 */
   바깥 주석은 여기까지 (안쪽 */ 로 끝나지 않음) */
val x = 1     // 정상 컴파일
```

Java·C에서는 `/* */`가 중첩되지 않아서, 이미 블록 주석이 들어 있는 코드를 통째로 주석 처리하면 첫 번째 `*/`에서 주석이 끊겨 버린다. Kotlin은 여는 `/*`와 닫는 `*/`의 개수를 세어 짝을 맞추므로, 주석 안에 주석이 있어도 안전하게 통째 주석 처리할 수 있다.

> **역사 메모**: 중첩 블록 주석은 D, Swift, Rust 같은 현대 언어들이 공유하는 실용적 선택이다. "코드를 임시로 통째 주석 처리한다"는 흔한 작업을 안전하게 만들기 위한 것으로, 렉서가 완전한 정규 언어(중첩을 못 셈)를 살짝 벗어나 카운터를 하나 두는 실용적 타협이다.

### 5.3 KDoc — 문서화 주석

`/** ... */`로 시작하는 블록 주석은 **KDoc**로 취급된다. Kotlin의 공식 문서화 형식으로, Markdown 문법과 `@param`, `@return`, `@throws`, `@property`, `@sample` 같은 블록 태그, 그리고 대괄호 링크(`[다른요소]`)를 지원한다.

```kotlin
/**
 * 원의 넓이를 계산한다.
 *
 * @param radius 반지름 (0 이상이어야 함)
 * @return 넓이 [Double]
 * @throws IllegalArgumentException radius가 음수면
 */
fun circleArea(radius: Double): Double {
    require(radius >= 0)
    return Math.PI * radius * radius
}
```

KDoc는 렉싱상 블록 주석이지만, Dokka 같은 도구와 IDE가 별도로 파싱한다. 애노테이션(`@Deprecated` 등)과 혼동하지 말 것—KDoc 태그(`@param`)는 주석 안의 텍스트일 뿐 언어 애노테이션이 아니다. 진짜 애노테이션은 [[44 - 애노테이션과 리플렉션]]의 영역이다.

## 6. 연산자와 구두점 토큰

### 6.1 토큰 목록

Kotlin의 연산자·구두점 토큰을 범주별로 모으면 다음과 같다.

| 범주 | 토큰 |
|------|------|
| 산술 | `+` `-` `*` `/` `%` |
| 대입 | `=` `+=` `-=` `*=` `/=` `%=` |
| 증감 | `++` `--` |
| 논리 | `&&` `\|\|` `!` |
| 동등·동일 | `==` `!=` `===` `!==` |
| 비교 | `<` `>` `<=` `>=` |
| 인덱싱·그룹 | `[` `]` `(` `)` `{` `}` |
| 멤버·참조 | `.` `?.` `::` |
| 범위 | `..` `..<` |
| 널 관련 | `?` `?:` |
| 람다·화살표 | `->` |
| 구분자 | `,` `;` |
| 특수 | `@` `$` `_` |

이 중 산술·비교·인덱스·범위 연산자 대부분은 **관례 함수**(`plus`, `compareTo`, `get`, `rangeTo` 등)로 오버로딩된다(→ [[19 - 연산자 오버로딩과 관례]], M40 참조). 즉 렉서는 `+`를 그냥 하나의 토큰으로 떼어 내고, 그것이 `Int`의 덧셈인지 사용자 정의 `plus`인지는 파서·리졸버·타입추론이 결정한다.

> **흔한 오해**: "연산자 오버로딩이 되니 아무 기호나 연산자로 만들 수 있다"는 착각이 흔하다(M40). 렉서가 인식하는 연산자 토큰 집합은 위 표로 **고정**되어 있다. 임의의 유니코드 기호(`⊕`, `∘` 등)를 새 연산자로 도입할 수 없다. 오버로딩이란 기존 연산자 토큰에 대응하는 정해진 이름의 함수(`plus`, `times`, ...)를 정의하는 것일 뿐이다. 우선순위·결합성도 언어가 고정한다.

### 6.2 가장 긴 일치 — Maximal Munch

렉서가 여러 토큰으로 갈릴 수 있는 문자열을 만나면 **가장 긴 유효 토큰**을 취한다. 이를 maximal munch(또는 longest match) 규칙이라 한다. 형식적으로, 위치 $i$에서 시작하는 문자열에 대해 렉서는

$$\text{token}(i) = \underset{t\ \in\ \text{Valid}(i)}{\arg\max}\ \text{length}(t)$$

를 고른다. 예:

```kotlin
val a = 1..2     // '..' 하나의 토큰 (범위). '.' '.' 두 개가 아님
val b = 1..<2    // '..<' 하나의 토큰 (rangeUntil)
val c = a === b  // '===' 하나. '==' '=' 가 아님
val d = x ?: y   // '?:' 하나 (엘비스). '?' ':' 가 아님
```

가장 긴 일치는 대개 직관적이지만, 가끔 공백을 강제하는 원인이 된다. 예컨대 어떤 문맥에서 `a ..b`처럼 의도치 않은 긴 토큰이 생기지 않게 하려면 공백으로 끊어야 할 때가 있다. 실무에서 가장 자주 만나는 건 다음 절의 물음표 계열이다.

### 6.3 물음표의 세 얼굴 — `?`, `?.`, `?:`

물음표는 세 가지 서로 다른 문법 요소에 등장한다.

```kotlin
val a: Int? = null      // '?': nullable 타입 표기
val b = a?.toString()   // '?.': 안전 호출
val c = a ?: 0          // '?:': 엘비스 연산자
```

이 셋이 어떻게 렉싱상 구분되는지가 6.4절의 미묘한 지점이다.

- `Int?`의 `?`는 타입 뒤에 붙는 nullable 표시.
- `a?.b`의 `?.`은 안전 호출(→ [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]], M32와 함께 다뤄짐).
- `a ?: b`의 `?:`은 엘비스—좌변이 null이면 우변을 평가(M32; 우변에 `throw`/`return`을 넣어 제어흐름으로 쓰는 관용구는 [[06 - 널 안전성 - nullable와 스마트 캐스트와 플랫폼 타입]]과 [[41 - 예외와 Nothing]]에서).

### 6.4 공백에 민감한 물음표

1.4절에서 예고했듯 렉서는 `?` 뒤의 공백 여부를 본다. 안전 호출 `?.`은 "공백 없는 물음표 + `.`"으로 렉싱되는 반면, 엘비스 `?:`은 별개 토큰이다. 이 때문에 다음이 문법적으로 갈린다.

```kotlin
val a: Int? = 5
val x = a?.plus(1)     // 안전 호출: a가 non-null이면 a+1, null이면 null
// val y = a ? .plus(1) // ?와 . 사이 공백은 안전 호출을 깨뜨린다 (문법 오류 유발)
```

> **명세 정밀**: Kotlin 어휘 문법에는 `QUEST_NO_WS`(뒤에 공백 없는 `?`)와 `QUEST_WS`(뒤에 공백 있는 `?`) 두 토큰이 있다. 안전 호출은 `QUEST_NO_WS` 다음에 `.`이 와야 성립한다(`safeNav`). 반면 nullable 타입 표기의 `?`나 엘비스의 `?:`은 다른 경로로 처리된다. 실무 결론은 단순하다: **안전 호출은 `?.`을 붙여 쓰고 `? .`처럼 띄우지 말라.** 이 국소 공백 민감성이 앞서 말한 "렉서가 완전한 문맥 무지 기계가 아니다"의 구체적 증거다.

### 6.5 트레일링 콤마

Kotlin 1.4부터 **후행 쉼표(trailing comma)** 가 허용된다. 인자 목록, 파라미터 목록, `when` 분기, 구조 분해, 컬렉션 리터럴 위치 등에서 마지막 요소 뒤에 쉼표를 붙여도 된다.

```kotlin
fun rect(
    width: Int,
    height: Int,      // ← 마지막 파라미터 뒤 쉼표 OK
) { }

val list = listOf(
    "a",
    "b",
    "c",              // ← 후행 쉼표 OK
)

val color = when (code) {
    0 -> "red"
    1 -> "green",     // when 분기에도 후행 쉼표 가능
    else -> "black",
}
```

> **역사 메모**: 후행 쉼표는 순전히 렉시컬/문법적 편의다. 버전 관리에서 "마지막 줄에 요소를 추가할 때 앞 줄의 쉼표 유무 때문에 두 줄이 diff되는" 문제를 없애 준다. 요소의 순서를 바꾸거나 추가·삭제할 때 각 줄이 독립적으로 편집되어 diff가 깔끔해진다. 값에는 아무 영향이 없다.

## 7. 세미콜론 추론 — 원리

이제 이 장의 심장으로 들어간다. Kotlin에서 세미콜론은 "선택적"이라고들 하지만, 그 말은 정확하지 않다. 정확히는 **줄바꿈이 대부분의 위치에서 문장 종결자로 추론되고, 세미콜론은 그 추론이 통하지 않는 소수의 경우에만 필요하다**. 이 절은 그 추론이 *어떻게* 작동하는지 밑바닥부터 세운다.

### 7.1 왜 세미콜론을 없앴는가 — 그리고 JS와의 대조

C·Java 계열은 세미콜론으로 문장을 명시적으로 끝낸다. 명시적이라 모호함이 없지만, 사람 눈에는 시각적 잡음이다. 많은 현대 언어(Kotlin, Swift, Scala, Go, 자바스크립트)가 세미콜론을 선택적으로 만들었다. 그런데 그 "선택적"을 구현하는 방식이 언어마다 다르고, 그 차이가 함정의 위치를 결정한다.

자매 시리즈 JavaScript에서 다루는 **ASI(자동 세미콜론 삽입)** 는 "세미콜론이 없어서 파싱이 실패하는 지점에 세미콜론을 삽입한다"는 사후 교정 방식이다. 파서가 일단 최대한 붙여 읽다가 막히면 그 자리에 세미콜론을 넣는다. 이 방식은 유명한 함정을 낳는다—예컨대 `return` 다음 줄바꿈이 있으면 강제로 세미콜론이 삽입되어 그 아래 값이 버려진다.

Kotlin의 접근은 다르지만 결과적으로 겹치는 함정이 있다. Kotlin은 **줄바꿈을 처음부터 의미 있는 토큰(NL)으로 만들고, 문법의 특정 위치에서 "여기서는 줄바꿈을 무시해도 된다(`NL*`)"고 명시**한다. 즉 "삽입"이 아니라 "선택적 무시"다. 문법이 `NL*`를 심어 둔 곳에서는 줄바꿈이 무시되어 문장이 계속되고, 심어 두지 않은 곳에서는 줄바꿈이 종결자로 남는다.

```text
JavaScript ASI:   파싱하다 막히면 → 세미콜론 삽입 (사후 교정)
Kotlin 추론:      줄바꿈은 항상 NL 토큰 → 문법이 NL*로 무시할 곳을 미리 지정 (사전 규정)
```

이 차이 때문에 Kotlin의 함정은 "문법이 어디에 `NL*`를 두었는가"를 알면 정확히 예측 가능하다. 그것이 이 절과 다음 절의 목표다.

### 7.2 NL 토큰과 `semi`/`semis` 규칙

Kotlin 문법에서 문장과 선언을 구분하는 규칙은 `semi`(단수)와 `semis`(복수)다. 개념적으로:

```text
semi  :  (';' | NL) NL*        // 세미콜론 하나 또는 줄바꿈 하나 (+뒤따르는 여분 줄바꿈)
semis :  (';' | NL)+           // 하나 이상의 구분자
```

즉 **세미콜론과 줄바꿈은 문장 구분자로서 동등**하다. 블록 안의 문장들은 `semi`로 구분된다.

```kotlin
fun demo() {
    val a = 1       // 줄바꿈 = semi
    val b = 2; val c = 3   // 세미콜론 = semi (한 줄에 여러 문장)
    println(a + b + c)     // => 6
}
```

핵심 통찰: **줄바꿈이 문장을 끝낼 수 있는 것은, 그 위치에서 문법이 `semi`를 기대하기 때문이다.** 반대로 어떤 표현식이 아직 끝나지 않은(문법적으로 더 와야 하는) 위치에서는 줄바꿈이 `semi`로 해석되지 않고 그냥 무시되거나 무의미하다.

### 7.3 문법이 `NL*`를 심어 둔 곳 = 문장이 계속되는 곳

문장이 줄바꿈을 넘어 계속되는(줄바꿈이 종결자가 되지 않는) 대표적 위치들이다. 이들은 모두 문법 규칙에 `NL*`가 명시된 자리다.

**(1) 이항 연산자 뒤.** 줄이 이항 연산자로 끝나면 표현식이 아직 안 끝났으므로 다음 줄로 이어진다.

```kotlin
val sum = 1 +
          2 +
          3            // => 6, 세 줄이 한 표현식
```

**(2) 여는 괄호 안, 쉼표 뒤.** 인자 목록·컬렉션은 괄호가 닫힐 때까지 줄바꿈이 무시된다.

```kotlin
val area = rectangleArea(
    width = 10,
    height = 20,
)                       // 괄호 안 줄바꿈은 전부 무시
```

**(3) 대입 `=`, 화살표 `->` 뒤.**

```kotlin
val perimeter =
    2 * (10 + 20)       // = 다음 줄바꿈 무시 => 60
```

**(4) 멤버 접근 `.`/`?.` **앞** (선행 점 체이닝).** 이게 아름다운 부분이다. 문법의 `memberAccessOperator` 규칙은 `NL* '.'`—즉 점 **앞**의 줄바꿈을 무시한다. 그래서 다음 줄을 점으로 시작하는 메서드 체이닝이 성립한다.

```kotlin
val result = listOf(1, 2, 3, 4, 5)
    .map { it * it }
    .filter { it > 5 }
    .sum()               // => 50, 각 줄이 점으로 시작하지만 한 표현식
```

이 `.map`, `.filter`, `.sum`이 각각 별개 문장으로 잘리지 않는 이유는 **점 앞에 `NL*`가 있어 줄바꿈이 무시되기 때문**이다. 안전 호출 `?.`도 마찬가지(`NL* safeNav`).

**(5) `if`/`else`/`when` 등 제어 구조 내부.** 조건과 본문 사이, `else` 앞뒤 등에도 `NL*`가 있어 줄바꿈이 무시된다(→ [[17 - 표현식으로서의 제어 흐름 - if와 when]]).

```kotlin
val label = if (score >= 60)
    "pass"
else
    "fail"               // if-else가 여러 줄에 걸쳐도 하나의 표현식
```

### 7.4 세미콜론이 필수인 곳

반대로 줄바꿈으로는 안 되고 세미콜론이 반드시 필요한 경우는 의외로 적다. 대표적인 둘.

**(1) 한 줄에 두 문장.** 줄바꿈이 없으니 명시적 구분자가 필요하다.

```kotlin
val a = 1; val b = 2        // 세미콜론 필수
println("$a $b")            // => 1 2
```

**(2) enum 상수 목록과 멤버 선언 사이.** enum 클래스에서 상수 나열이 끝나고 메서드·프로퍼티가 이어질 때, 그 경계에 세미콜론이 필요하다(→ [[29 - enum 클래스]]).

```kotlin
enum class Direction {
    NORTH, SOUTH, EAST, WEST;      // ← 이 세미콜론이 필수

    fun opposite(): Direction = when (this) {
        NORTH -> SOUTH
        SOUTH -> NORTH
        EAST -> WEST
        WEST -> EAST
    }
}
```

이 세미콜론을 빼면 파서가 `WEST` 다음의 `fun`을 상수 나열의 연장으로 오해하지 못하도록—정확히는 상수 목록의 끝을 표시하기 위해—필요하다.

그 밖에 빈 문장으로서의 세미콜론(`;`)이나 `for (i in 1..10) ;`(빈 본문) 같은 용법이 있지만, 실무에서 세미콜론을 손으로 쓸 일은 위 두 경우가 거의 전부다. Kotlin 공식 스타일 가이드는 불필요한 세미콜론을 쓰지 말라고 명시한다.

## 8. 세미콜론 추론의 함정

원리를 알았으니 이제 사람들이 실제로 걸려 넘어지는 함정들을 하나씩 해부한다. 이 함정들의 공통 구조는 언제나 같다: **프로그래머는 "표현식이 다음 줄로 이어진다"고 의도했지만, 그 위치에 `NL*`가 없어서 줄바꿈이 문장을 끝내 버린다**(혹은 그 반대).

### 8.1 선행 이항 연산자 — `+`, `-`의 배신

가장 유명한 함정. 이항 연산자를 **줄 끝**에 두면 이어지지만(7.3-(1)), **다음 줄 앞**에 두면 이어지지 않는다. 왜냐하면 이항 연산자 앞에는 `NL*`가 없기 때문이다. 그래서 앞 줄에서 문장이 끝나고, 다음 줄의 연산자는 **단항 연산자**로 재해석된다.

```kotlin
fun trap() {
    val x = 1
        + 2
        - 3
    println(x)     // => 1  (기대: -1 이나 0)
}
```

무슨 일이 벌어졌나? 파서 눈에는 이렇게 보인다.

```text
val x = 1          ← 여기서 문장 종결 (val x = 1)
    + 2            ← 별개 문장: 단항 플러스 (+2), 결과 미사용
    - 3            ← 별개 문장: 단항 마이너스 (-3), 결과 미사용
```

`+2`와 `-3`은 각각 "값을 계산하고 버리는" 문장이 되고, 컴파일러는 "expression is unused" 경고를 낸다(에러는 아님—이게 함정을 조용하게 만든다). `x`는 그대로 `1`이다.

**교훈**: 여러 줄 산술은 연산자를 **줄 끝**에 두라.

```kotlin
val x = 1 +        // 연산자를 줄 끝에
        2 -
        3
// => 0, 의도대로
```

> **성능 주의는 아니지만 정확성 주의**: 이 함정은 컴파일 에러가 아니라 경고에 그치기 때문에 특히 위험하다. `+2`나 `-3`이 순수한 값 계산이라 부작용이 없어 런타임 오류도 안 나고, 결과만 조용히 틀린다. 코드 리뷰에서 "연산자가 줄 앞에 있는가"를 눈여겨봐야 하는 이유다.

### 8.2 선행 점은 되는데 선행 infix는 안 된다

7.3-(4)에서 선행 점 체이닝(`\n.map`)이 되는 이유가 "점 앞의 `NL*`"라고 했다. 그런데 Kotlin에는 점 없이 함수를 중위(infix)로 호출하는 문법도 있다(→ [[19 - 연산자 오버로딩과 관례]]). 예: `1 shl 4`, `mapOf("a" to 1)`. 여기서 대칭이 깨진다.

infix 호출의 문법은 대략 `rangeExpression (simpleIdentifier NL* rangeExpression)*`이다. 잘 보면 `NL*`가 **함수 이름 뒤, 다음 피연산자 앞**에 있다. 함수 이름 **앞**에는 없다. 그래서:

```kotlin
// 케이스 A: infix 이름 뒤에 줄바꿈 → 이어짐 (이름 뒤에 NL*)
val a = 1 shl
        4                // => 16, 이어짐

// 케이스 B: infix 이름 앞에 줄바꿈 → 끊김 (이름 앞엔 NL* 없음)
val b = 1
        shl 4            // ← '1'에서 문장 종결, 'shl 4'는 별개 → 컴파일 에러
```

케이스 B에서 `shl 4`는 앞의 `1`과 분리되어 별개 문장이 되는데, `shl 4`만으로는 유효한 문장이 아니라 오류가 난다(`shl`이라는 이름이 그 자리에 홀로 있을 수 없음). 이건 점 체이닝과 정확히 반대다.

```text
점 체이닝:   memberAccessOperator = NL* '.'      → 점 '앞' NL 무시 → 선행 점 OK
infix 호출:  ... (identifier NL* expr) ...        → 이름 '뒤' NL 무시 → 선행 이름 X
```

이 비대칭을 외우지 말고 원리로 이해하라: **문법이 `NL*`를 심어 둔 방향으로만 줄바꿈이 무시된다.** 점은 앞에, infix 이름은 뒤에 `NL*`가 있다.

### 8.3 `return`과 `throw`의 비대칭

이 장에서 가장 미묘하고 실무적으로 중요한 함정. `return`, `break`, `continue`, `throw`는 모두 "점프 표현식(jump expression)"이지만, 줄바꿈 처리가 서로 다르다.

문법을 보자(개념).

```text
jumpExpression :
      'throw' NL* expression        ← throw 뒤에 NL* 있음! 줄바꿈 무시
    | 'return' expression?          ← return 뒤에 NL* 없음. 줄바꿈이 종결
    | 'break' | 'continue' | ...
```

**`return`은 뒤에 `NL*`가 없다.** 그래서 `return` 다음에 줄바꿈이 오면, 그 줄바꿈이 문장을 끝내 버리고 아래 값은 `return`과 무관해진다. `return`은 값 없이(즉 `Unit`을 반환) 실행된다.

```kotlin
fun compute(): Int {
    return
        42          // ← 이 42는 return 되지 않는다!
}
// 컴파일 에러: 'return' expression required (Unit을 반환하려는데 반환 타입이 Int)
```

값 타입이 맞아떨어지면 더 은밀하다.

```kotlin
fun sideEffect() {       // 반환 타입 Unit
    return
    println("도달 못 함")   // ← unreachable code 경고, 실행 안 됨
}
```

**반면 `throw`는 뒤에 `NL*`가 있어** 줄바꿈을 넘어 예외 표현식을 가져온다.

```kotlin
fun validate(age: Int) {
    if (age < 0) throw
        IllegalArgumentException("음수 나이")   // ← 정상 동작! throw는 줄바꿈을 넘음
}
```

이 비대칭(`return`은 값을 다음 줄로 못 넘기고, `throw`는 넘긴다)은 처음 보면 당황스럽지만 문법의 `NL*` 배치로 완벽히 설명된다.

> **흔한 오해**: JavaScript의 ASI에서도 `return` 다음 줄바꿈이 값을 버리는 같은 함정이 있다(자매 JavaScript 시리즈 참조). 두 언어가 **다른 메커니즘**(JS는 사후 세미콜론 삽입, Kotlin은 문법의 `NL*` 부재)으로 **같은 결과**에 도달한다. 실무 교훈은 양쪽 동일: **반환값은 `return`과 같은 줄에 써라.** 정 여러 줄로 쓰려면 괄호로 감싸라: `return (\n 42\n)`—여는 괄호 안은 줄바꿈이 무시되므로 안전하다.

```kotlin
fun computeSafe(): Int {
    return (
        42            // 괄호 안이므로 줄바꿈 무시 → 정상 반환
    )
}
// => 42
```

### 8.4 호출 뒤 줄바꿈 후 여는 중괄호 — 후행 람다 오인

Kotlin은 함수의 마지막 인자가 람다일 때 괄호 밖으로 빼는 **후행 람다(trailing lambda)** 문법을 지원한다(→ [[13 - 함수 타입과 람다와 함수 참조]], [[16 - 스코프 함수와 수신 객체 관용구]]). 그런데 이 후행 람다의 문법에도 `NL*`가 들어 있어, 줄바꿈을 넘어 여는 중괄호 `{`가 앞의 호출에 **붙어 버릴** 수 있다.

```kotlin
fun greet() = println("hi")

fun trap() {
    val x = greet()
    { println("이건 별개 블록일까 후행 람다일까?") }
    // 파서는 { ... }를 앞의 greet()에 후행 람다로 붙이려 시도한다.
    // greet()는 람다 인자를 받지 않으므로 → 컴파일 에러 (too many arguments)
}
```

파서 관점에서 `greet()\n{ ... }`는 `greet() { ... }`(후행 람다 동반 호출)로 해석되려 한다. 이는 여는 중괄호 앞에 `NL*`가 허용되기 때문이다. 만약 `greet`가 람다를 받는 함수였다면 조용히 붙어서 의도와 다르게 동작할 수도 있다.

이 함정은 특히 "값을 반환하는 호출" 다음 줄에 독립적인 블록/람다를 두려 할 때 나타난다. 그래서 Kotlin 공식 스타일 가이드는 **후행 람다를 호출과 같은 줄에서 시작**하도록 권한다(`foo {`처럼). 별개의 블록이 필요하면 `run { ... }`이나 명시적 구분으로 의도를 드러내라.

> **명세 정밀**: `callSuffix`의 `annotatedLambda`가 `... NL* lambdaLiteral` 형태라, 호출 뒤 줄바꿈이 있어도 후행 람다로 결합될 여지가 있다. 정확한 결합 여부는 앞의 피호출자가 호출 가능한 함수인지 등 문맥에 따라 파서가 판정하므로, 여기서는 "붙을 수 있다"는 위험만 못박고 세부 결합 규칙은 구현·문맥에 따른다고 한정한다. 실무 결론: **여는 중괄호를 호출과 다른 줄에서 시작하지 말라.**

### 8.5 대입과 단일 표현식 함수의 경계

단일 표현식 함수(`fun square(x: Int) = x * x`)와 프로퍼티 초기화(`val pi = 3.14`)의 `=` 뒤에는 `NL*`가 있어 줄바꿈이 무시된다(7.3-(3)). 그래서 다음은 안전하다.

```kotlin
fun area(r: Double) =
    Math.PI * r * r        // = 다음 줄바꿈 무시, 정상

val greeting =
    "Hello, " +
    "World"                // => Hello, World
```

하지만 여기서도 8.1의 함정이 재발할 수 있다. `=` 뒤 첫 줄이 완결된 표현식이고 다음 줄이 이항 연산자로 시작하면, 앞 8.1처럼 끊긴다. 요컨대 `=`은 "첫 표현식의 시작"까지만 줄바꿈을 무시하지, 그 표현식 내부의 이항 연산자 배치까지 구해 주지는 않는다.

```kotlin
val total =                 // = 뒤 줄바꿈 무시됨
    100                     // 여기서 표현식(100)이 완결
    + 50                    // ← 별개 문장 (+50), total은 100
// 경고: expression is unused. total == 100
```

이 마지막 예가 이 절 전체를 요약한다. **줄바꿈 무시는 문법이 명시한 국소 지점에서만 일어난다.** `=` 뒤 한 번 무시됐다고 해서 그 아래 전체가 하나의 표현식으로 묶이는 게 아니다. 표현식이 완결되는 순간, 다음 줄바꿈은 다시 종결자가 될 수 있다.

## 9. 렉시컬 규율과 확인 방법

### 9.1 스타일 가이드는 렉싱과 무관한데 왜 규칙을 두는가

Kotlin 공식 코딩 컨벤션은 "세미콜론을 쓰지 말라", "여러 줄 표현식에서 연산자를 줄 끝에 두라", "후행 람다는 같은 줄에서 시작하라" 같은 규칙을 둔다. 흥미로운 점은 이 규칙들이 **미적 취향이 아니라 렉시컬 함정의 회피책**이라는 것이다. 8절에서 본 함정들과 정확히 대응한다.

| 스타일 규칙 | 회피하는 함정 |
|-------------|---------------|
| 이항 연산자를 줄 끝에 | 8.1 선행 연산자 → 단항 오인 |
| 반환값을 `return`과 같은 줄에 | 8.3 `return` 줄바꿈 → 값 버림 |
| 후행 람다를 호출과 같은 줄에서 시작 | 8.4 `{` 후행 람다 오인 |
| 불필요한 세미콜론 금지 | 가독성(함정 아님) |

즉 스타일 가이드를 따르면 이 장의 함정 대부분을 자동으로 피한다. 규칙의 "왜"를 이해하면 기계적으로 외우지 않아도 된다.

### 9.2 의심스러우면 확인하는 법

렉싱·세미콜론 추론 결과가 의심스러울 때 확인하는 실용적 방법들이다.

1. **컴파일러 경고를 신뢰하라.** "expression is unused"나 "unreachable code" 경고가 뜬다면 8.1·8.3 같은 함정에 걸렸을 가능성이 높다. Kotlin은 이런 실수를 대개 에러가 아닌 경고로 잡으므로, 경고를 무시하지 않는 규율이 중요하다.

2. **IDE의 구조 하이라이트.** IntelliJ는 표현식이 어디서 끝나는지 구문 강조로 보여 준다. 여러 줄 표현식이 의도대로 묶였는지 눈으로 확인할 수 있다.

3. **바이트코드/IR 확인.** [[02 - 컴파일러의 해부 - K2와 IR 백엔드와 바이트코드]]에서 언급한 디컴파일(예: IntelliJ의 "Show Kotlin Bytecode" → Decompile)을 쓰면, `x`가 정말 `1`인지 `0`인지 최종 결과로 확인할 수 있다.

4. **괄호로 의도를 못박기.** 확신이 안 서면 여는 괄호 `(`로 감싸라. 괄호 안은 줄바꿈이 전부 무시되므로(7.3-(2)), 여러 줄 표현식의 경계 모호성이 사라진다. 이건 함정을 이해했는지와 별개로 항상 안전한 방어책이다.

### 9.3 렉시컬 구조는 문법의 토대다

이 장에서 본 것—토큰, 키워드 3분류, 식별자, 리터럴, 연산자, 그리고 줄바꿈이 만드는 세미콜론 추론—은 그 자체로는 "언어의 표면"처럼 보인다. 하지만 이 표면이 그 위에 세워질 모든 문법 구조의 토대다. 다음 장 [[04 - 파일과 패키지와 선언 - 프로그램의 골격]]은 이 토큰들이 어떻게 조립되어 파일·패키지·최상위 선언을 이루는지, 즉 렉싱 다음의 파싱을 다룬다. 거기서도 세미콜론 추론은 계속 작동한다—선언과 선언 사이도 결국 `semi`로 구분되기 때문이다.

---

이 장을 열며 던진 질문들로 돌아가자. `val x = 1` 다음 줄의 `+ 2`가 `x`를 `3`으로 만들지 않는 것은, 이항 연산자 앞에 문법이 `NL*`를 심어 두지 않아 줄바꿈이 문장을 끝내고 `+2`가 단항 연산으로 재해석되기 때문이었다. 선행 점 체이닝(`.map`)은 되고 선행 infix(`shl`)는 안 되는 것은, 문법이 점 **앞**과 infix 이름 **뒤**에 각각 `NL*`를 두었기 때문이었다. `return`이 값을 다음 줄로 못 넘기고 `throw`는 넘기는 것도, 딱 그 두 규칙의 `NL*` 유무 차이였다. `fun`은 하드 키워드라 어디서도 이름이 될 수 없지만 `data`·`value`·`it`은 문맥 밖에서 평범한 이름이 되는 것은, Kotlin이 키워드를 세 등급으로 나눠 진화 여지를 남긴 실용적 설계였다. `010`이 8진수가 아닌 것은, C 계열의 조용한 함정을 아예 제거하려는 의도였다. 이 모든 규칙을 관통하는 하나의 원리는 이것이다—**Kotlin의 렉시컬 설계는 기계가 사람의 의도를 최대한 추론하되, 추론이 위험한 지점에서는 침묵하지 않고(경고·에러) 알린다.** 세미콜론을 없애 잡음을 줄이되, 그 대가로 생기는 함정은 문법의 `NL*` 배치라는 예측 가능한 규칙으로 봉인해 두었다. 이 예측 가능성이 "선택적 세미콜론"을 혼돈이 아니라 규율로 만든다.

## 핵심 요약

- **렉서는 소스 문자열을 토큰 시퀀스로 자르는 첫 관문이며, 공백·주석은 폐기하지만 줄바꿈은 의미 있는 NL 토큰으로 남긴다.** 이 NL 토큰의 선택적 무시가 세미콜론 추론의 전체 메커니즘이다.
- **Kotlin 키워드는 하드/소프트/모디파이어 3등급으로 나뉘고, 여기에 특수 식별자(`it`, `field`)가 더해진다.** 하드 키워드(`fun`, `val`, `when` 등)만 항상 예약되고, 나머지는 문맥 밖에서 평범한 식별자가 되어 언어의 하위호환 진화를 가능케 한다.
- **`data`, `value`, `open`, `suspend`, `by`, `get`, `it`은 모두 변수·함수 이름으로 쓸 수 있다.** 키워드로 승격되는 것은 파서가 특정 구문 위치에서 판정할 때뿐이다(M42 관련: `it`은 키워드가 아니라 단일 파라미터 람다의 암시적 식별자).
- **식별자는 유니코드 문자를 허용해 한글·그리스 문자로 이름을 지을 수 있고, 백틱(`` `fun` ``)으로 감싸면 하드 키워드나 공백 포함 이름도 식별자가 된다.** 단 백틱의 한계는 JVM 백엔드에서 `.` `;` `[` `]` `/` `<` `>` `:` `\` 금지 등 대상 플랫폼의 제약을 받는다.
- **정수 리터럴은 10진·16진(`0x`)·2진(`0b`)만 있고 8진수는 없으며, 선행 0(`010`)은 에러다.** 이는 C 계열의 `010 == 8` 함정을 의도적으로 제거한 것이다. 밑줄(`1_000`)은 숫자 사이에만 올 수 있다.
- **부동소수 리터럴은 소수점 양쪽에 숫자가 있어야 하고(`.5`·`5.` 불가), 16진 부동소수도 없다.** `5.` 금지 덕분에 `5.toLong()` 같은 정수 리터럴 멤버 호출이 모호하지 않게 렉싱된다.
- **블록 주석은 중첩 가능(`/* /* */ */`)해 Java·C와 달리 이미 주석이 든 코드를 안전하게 통째 주석 처리할 수 있다.** 이는 렉서에 여닫기 카운터를 둔 실용적 확장이다.
- **세미콜론과 줄바꿈은 문장 구분자로 동등하며(`semi = ';' | NL`), 세미콜론이 필수인 곳은 한 줄 다중 문장과 enum 상수/멤버 경계 정도로 드물다.** 나머지는 줄바꿈이 종결자로 추론된다.
- **줄바꿈이 문장을 종결하지 않고 넘어가는 곳은 문법이 `NL*`를 명시한 지점(이항 연산자 뒤, 괄호 안, `=`/`->` 뒤, 점/`?.` 앞, `if`/`else` 내부)뿐이다.** 이 `NL*` 배치를 알면 모든 함정이 예측 가능하다.
- **선행 이항 연산자(`\n + 2`)는 단항으로 재해석되어 조용히 틀린 값을 낳고(경고만 발생), `return`은 값을 다음 줄로 못 넘기지만 `throw`는 넘긴다.** 이 비대칭은 전부 문법의 `NL*` 유무로 설명되며, 실무 방어책은 "연산자를 줄 끝에, 반환값을 `return`과 같은 줄에, 여는 중괄호를 호출과 같은 줄에"다.
- **선행 점 체이닝(`\n.map`)은 되지만 선행 infix(`\n shl 2`)는 안 된다.** 문법이 점 **앞**과 infix 이름 **뒤**에 각각 `NL*`를 두었기 때문이며, 방향을 외우지 말고 `NL*` 위치로 이해해야 한다.
- **Kotlin의 세미콜론 추론은 JavaScript의 ASI(사후 세미콜론 삽입)와 메커니즘이 다르지만(문법의 사전 `NL*` 규정), `return` 값 버림 같은 겹치는 함정을 낳는다.** Kotlin 쪽이 규칙 기반이라 함정의 위치가 더 예측 가능하다.
