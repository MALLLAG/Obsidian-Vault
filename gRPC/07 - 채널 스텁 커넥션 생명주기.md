## 1. 들어가며: "연결을 연다"는 말의 함정

REST/HTTP1.1을 쓰던 시절의 직관에서 출발해 보자. 보통 "서버에 연결한다"고 하면 다음과 같은 그림을 떠올린다.

```text
클라이언트  ──── TCP 소켓 1개 ────▶  서버
              (요청 보내고 응답 받고 닫음)
```

소켓 하나가 곧 연결이고, 연결 하나가 곧 요청 하나(또는 keep-alive를 쓰면 몇 개)다. 이 직관은 단순하지만 gRPC를 이해할 때는 오히려 방해가 된다. gRPC에서 코드로 만드는 `Channel`은 소켓이 **아니다**. `Channel`은 "어떤 목적지(target)로 RPC를 보내고 싶다"는 의도를 담은 **논리적 추상화**이고, 실제 TCP 소켓은 그 아래에서 gRPC 라이브러리가 직접 만들고, 끊고, 다시 연결한다.

이 차이를 한 문장으로 요약하면 다음과 같다.

> **채널은 "정책"이고, 소켓은 "메커니즘"이다.** 사용자는 "이 서비스와 통신하겠다"는 정책을 선언하고, gRPC 런타임은 그 정책을 만족하는 데 필요한 만큼 소켓을 직접 운영한다.

이 장에서는 gRPC 런타임이 소켓을 운영하는 방식을 단계별로 살펴본다. 채널이라는 추상화의 계층, 그 아래의 서브채널, 서브채널이 가진 실제 HTTP/2 연결, 그 연결이 거치는 상태 기계, 연결이 끊겼을 때의 자동 복구, 그리고 그 위에 올라가는 스텁까지 다룬다. gRPC를 처음 접하는 백엔드·네트워크 엔지니어가 이 장을 읽고 나서 "채널을 요청마다 만들면 안 된다"는 점을 확실히 이해하는 것이 목표다.

전송 계층의 메커니즘(프레임, 스트림, 멀티플렉싱)은 [[04 - HTTP2 깊이 보기 - 전송 계층]]에서 이미 다뤘다고 가정한다. 이 장은 그 위에서 동작하는 **클라이언트 측 연결 관리**에 집중한다.

## 2. 채널이라는 추상화: 가상 연결의 구조

### 2.1 정확한 정의

gRPC 공식 용어로 **채널(channel)** 은 다음과 같이 정의된다.

> A gRPC channel provides a connection to a gRPC server on a specified host and port. (gRPC 채널은 지정된 호스트와 포트의 gRPC 서버로 가는 연결을 제공한다.)

여기서 "a connection"이라는 단수 표현 때문에 오해가 생기기 쉽다. 더 정확하게 말하면 채널은 **하나의 타겟(target)으로 향하는 가상 연결**이다. 타겟이 DNS 이름이면 그 이름 뒤에 백엔드 IP가 여러 개 있을 수 있고, 이때 채널 하나가 내부적으로 **실제 연결 여러 개**를 관리한다.

계층 구조를 그림으로 보자.

```text
   당신의 코드가 만지는 것 ──────────────────────────────┐
                                                          ▼
   ┌──────────────────────────────────────────────────────────────┐
   │  Channel  ("orderservice.internal:50051" 로 가는 가상 연결)    │
   │                                                                │
   │   ┌─ Name Resolver: 타겟 → [10.0.0.11, 10.0.0.12, 10.0.0.13] │
   │   │                                                            │
   │   ┌─ LB Policy: 어느 백엔드로 보낼지 고르는 정책 (round_robin) │
   │   │                                                            │
   │   ▼                                                            │
   │  ┌────────────┐  ┌────────────┐  ┌────────────┐                │
   │  │ Subchannel │  │ Subchannel │  │ Subchannel │   ← 백엔드별   │
   │  │ 10.0.0.11  │  │ 10.0.0.12  │  │ 10.0.0.13  │                │
   │  └─────┬──────┘  └─────┬──────┘  └─────┬──────┘                │
   │        │               │               │                       │
   └────────┼───────────────┼───────────────┼───────────────────────┘
            ▼               ▼               ▼
      ┌──────────┐    ┌──────────┐    ┌──────────┐
      │ TCP +    │    │ TCP +    │    │ TCP +    │   ← 실제 소켓
      │ TLS +    │    │ TLS +    │    │ TLS +    │     (HTTP/2 conn)
      │ HTTP/2   │    │ HTTP/2   │    │ HTTP/2   │
      └──────────┘    └──────────┘    └──────────┘
```

정리하면 다음과 같은 3계층 모델이 된다.

| 층 | 이름 | 정체 | 개수 | 코드에서 직접 다루는가? |
|----|------|------|------|---------------------|
| 1 | **Channel** | 타겟으로 가는 가상 연결(정책) | 보통 1 | O (코드로 생성) |
| 2 | **Subchannel** | 단일 백엔드 주소로 가는 연결 관리 단위 | 백엔드 수만큼 | X (런타임이 관리) |
| 3 | **Transport / Socket** | 실제 TCP+TLS+HTTP/2 연결 | 서브채널당 1개(보통) | X (런타임이 관리) |

채널과 소켓을 구분하는 핵심은 다음 한 가지다. **소켓은 끊어질 수 있지만 채널은 끊어지지 않는다.** 백엔드 하나가 죽어서 그쪽 소켓이 끊겨도 채널은 계속 살아 있다. 채널은 그 백엔드의 서브채널을 `TRANSIENT_FAILURE` 상태로 표시하고, 살아 있는 다른 서브채널로 트래픽을 보내거나, 끊긴 서브채널을 백오프한 뒤 다시 연결한다. "가상"이라는 말의 실제 의미가 여기에 있다. 채널은 물리적 연결이 살아 있는지와 관계없이 논리적으로 계속 존재하는 통로다.

### 2.2 왜 이렇게 설계했는가

이 3계층 구조는 불필요한 추상화가 아니다. 채널이 곧 소켓이었다면 다음과 같은 문제가 생긴다.

1. **로드밸런싱을 할 수 없다.** [[12 - 이름 해석과 로드밸런싱]]에서 다루듯, gRPC는 L4 로드밸런서 없이 **클라이언트 측 로드밸런싱(client-side load balancing)** 을 기본 기능으로 지원한다. 채널이 서브채널 여러 개를 관리해야 round_robin 같은 정책으로 요청을 분산할 수 있다.
2. **장애를 격리할 수 없다.** 백엔드 3대 중 1대가 죽었을 때 채널=소켓 모델이라면 채널 전체가 죽는다. 서브채널을 분리해 두었기 때문에 죽은 1대만 격리하고 나머지로 서비스를 계속할 수 있다.
3. **연결 비용을 숨길 수 없다.** TCP 핸드셰이크, TLS 핸드셰이크, HTTP/2 설정은 비용이 크다. 이 비용이 매번 드러나면 애플리케이션 코드가 연결 풀을 직접 관리해야 한다. 채널 추상화는 이 복잡성을 모두 흡수한다.

즉 채널은 **"연결 관리라는 분산 시스템의 까다로운 부분을 라이브러리 안으로 옮기기 위한 경계선"** 이다.

## 3. 서브채널과 HTTP/2 멀티플렉싱: 연결 하나에 얼마나 많은 요청을 담을 수 있나

### 3.1 연결 하나로 요청 수천 개를 처리하는 멀티플렉싱

HTTP/1.1에서는 TCP 연결 하나로 한 번에 요청 하나만 처리한다(파이프라이닝은 사실상 쓰이지 않는다). 그래서 브라우저가 도메인마다 연결을 6개씩 여는 식의 우회책이 필요했다.

HTTP/2는 이 모델을 근본적으로 바꿨다. TCP 연결 하나 위에서 **스트림(stream)** 이라는 논리적 채널 여러 개를 동시에 전송한다. 이것이 **멀티플렉싱(multiplexing)** 이다. gRPC의 RPC 하나는 HTTP/2 스트림 하나에 대응한다.

```text
            하나의 TCP 연결 (HTTP/2)
   ┌───────────────────────────────────────────────┐
   │  stream 1  ▶ RPC: GetOrder(id=1)               │
   │  stream 3  ▶ RPC: GetOrder(id=2)   ← 동시 진행  │
   │  stream 5  ▶ RPC: ListOrders()                 │
   │  stream 7  ▶ RPC: CreateOrder(...)             │
   │   ...      각 스트림의 DATA/HEADERS 프레임이      │
   │            인터리빙되어 한 소켓으로 흐름           │
   └───────────────────────────────────────────────┘
```

그래서 gRPC는 **연결 하나로도 매우 많은 RPC를 동시에 처리**할 수 있다. "채널 하나를 만들어 앱 전체가 공유하라"는 권고의 기술적 근거가 바로 이것이다. 동시 요청이 수백 개여도 연결 하나로 충분한 경우가 많다.

참고로 클라이언트가 시작하는 HTTP/2 스트림의 ID는 항상 홀수(1, 3, 5, 7, ...)이고, 서버가 시작하는 스트림(gRPC에서는 거의 쓰지 않는다)의 ID는 짝수다. 위 그림에서 RPC들이 홀수 ID를 가진 이유가 이것이다.

### 3.2 한계: MAX_CONCURRENT_STREAMS

스트림을 무한정 담을 수는 없다. HTTP/2의 SETTINGS 프레임에는 `SETTINGS_MAX_CONCURRENT_STREAMS`라는 파라미터가 있고, 서버는 이 값으로 "연결 하나당 동시에 열 수 있는 스트림은 N개까지"라고 알린다. gRPC 서버는 이 값을 흔히 **100** 근처로 설정한다(구현과 설정에 따라 다르다).

서버가 보내는 SETTINGS 프레임을 실제 바이트 단위로 직접 디코딩해 보자. HTTP/2 프레임 헤더는 9바이트로 고정되어 있다.

```text
HTTP/2 Frame Header (9 bytes)
+-----------------------------------------------+
|                 Length (24 bit)               |
+---------------+---------------+---------------+
|   Type (8)    |   Flags (8)   |
+-+-------------+---------------+-------------------------------+
|R|                 Stream Identifier (31 bit)                 |
+=+=============================================================+
|                   Frame Payload (Length bytes)              ...
+---------------------------------------------------------------+
```

서버가 "MAX_CONCURRENT_STREAMS = 100"을 알리는 SETTINGS 프레임의 바이트는 다음과 같다.

```text
바이트열:  00 00 06   04   00   00 00 00 00   00 03   00 00 00 64
           └──┬───┘   │    │    └────┬─────┘   └─┬─┘   └────┬────┘
           Length=6  Type Flags  StreamID=0   ID=0x3   Value=0x64
            (6바이트  =0x04 =0    (SETTINGS는   (=MAX_   (=100)
             payload) SETTINGS     stream 0     CONCURRENT
                                   고정)         _STREAMS)
```

- `00 00 06`: payload 길이 6바이트(설정 1개 = 식별자 2바이트 + 값 4바이트).
- `04`: 프레임 타입 0x4 = SETTINGS.
- `00`: 플래그 0. ACK 비트가 꺼져 있으므로 "새 설정값을 선언한다"는 뜻이다. ACK이면 0x1이다.
- `00 00 00 00`: 스트림 ID 0. SETTINGS는 항상 연결 전체에 적용되므로 스트림 0(연결 자체)에서만 보낸다.
- `00 03`: 설정 식별자 0x3 = `SETTINGS_MAX_CONCURRENT_STREAMS`.
- `00 00 00 64`: 값 0x64 = 100.

이제 핵심 질문이다. **동시 RPC를 101번째로 보내면 어떻게 되는가?** 연결이 요청을 거부하지 않는다. gRPC 클라이언트가 그 RPC를 **큐에 넣고 기다리게** 한다. 앞선 스트림 중 하나가 끝나서 자리가 비면 그때 새 스트림을 연다. 즉 단일 연결의 동시 스트림 한도는 **암묵적인 동시성 상한**으로 작동한다.

### 3.3 고부하에서는 단일 연결이 병목이 된다

실무에서 많은 사람이 이 부분에서 당황한다. "채널 하나면 충분하다고 했는데, 왜 처리량이 나오지 않을까?"

**단일 서브채널은 단일 TCP 연결**이고, 그 연결은 `MAX_CONCURRENT_STREAMS`(예: 100)에 묶여 있기 때문이다. 트래픽이 백엔드 하나로만 몰리는 경우(백엔드가 1대뿐이거나, LB 정책이 `pick_first`라서 연결을 하나만 쓰는 경우)를 생각해 보자. 평균 RPC 지연이 10ms이고 초당 50,000건을 보내고 싶다면, 리틀의 법칙(Little's Law)으로 필요한 동시성을 계산할 수 있다.

```text
필요한 동시성 ≈ throughput × latency
            = 50,000 req/s × 0.010 s
            = 500 개의 동시 인-플라이트(in-flight) RPC

그런데 연결 하나의 한계 = 100 스트림
→ 500 / 100 = 최소 5개의 연결이 필요
→ 연결 1개로는 동시성 100에 묶여 throughput ≈ 10,000 req/s 에서 천장
```

해법은 두 가지다.

1. **백엔드를 여러 대 두고 `round_robin` 같은 LB 정책을 쓴다.** 그러면 채널이 백엔드마다 서브채널을 만들어 여러 연결로 요청을 분산한다(12장 이름 해석과 로드밸런싱 참고).
2. **백엔드가 한 대라면 채널을 여러 개 만들거나(채널 풀링), 라이브러리의 멀티 커넥션 옵션을 쓴다.** 단, 같은 타겟으로 채널을 여러 개 만들 때는 각 채널이 `subchannel`을 공유하지 않도록 일부러 서로 다르게 만드는 방법이 필요하다(언어에 따라 로컬 서브채널 풀을 강제하거나, 의미 없는 더미 인자를 붙여 채널을 구분한다).

백프레셔(backpressure), 처리량 한계, flow control window가 서로 어떻게 영향을 주는지는 [[15 - 성능과 Flow Control 백프레셔]]에서 자세히 다룬다. 여기서는 다음 한 가지만 기억하자. **멀티플렉싱은 강력하지만 무한하지 않다. `MAX_CONCURRENT_STREAMS`가 단일 연결의 동시성 상한이다.**

## 4. 연결 생명주기의 핵심: 연결 상태 기계(Connectivity State Machine)

이제 이 장의 핵심 내용이다. 채널(정확히는 채널 안의 각 서브채널과, 이를 집계한 채널 전체)은 5가지 **연결 상태(connectivity state)** 사이를 오간다. gRPC의 모든 언어 구현이 이 상태 기계를 공통으로 사용한다.

```text
                         ┌─────────────────────────────────────┐
                         │                                     │
   (생성 직후 / 유휴)      ▼                                     │
        ┌──────────────────────┐                               │
   ┌───▶│        IDLE          │                               │
   │    └──────────┬───────────┘                               │
   │               │  RPC 발생 OR Connect() 호출                 │
   │               │  OR 일정 유휴시간 후 재진입                  │
   │               ▼                                            │
   │    ┌──────────────────────┐                               │
   │    │     CONNECTING       │  TCP+TLS+HTTP/2 핸드셰이크 중   │
   │    └──────┬────────────┬──┘                               │
   │           │ 성공        │ 실패                              │
   │           ▼            ▼                                   │
   │  ┌────────────┐   ┌──────────────────────┐                │
   │  │   READY    │   │  TRANSIENT_FAILURE   │                │
   │  └─────┬──────┘   └──────────┬───────────┘                │
   │        │ 연결 끊김 / GOAWAY    │ 백오프 타이머 만료           │
   │        │ / keepalive 실패     │ → 재시도                    │
   │        ▼                     └────────────────────────────┘
   │  ┌──────────────────────┐         (다시 CONNECTING 으로)
   │  │  TRANSIENT_FAILURE   │
   │  └──────────────────────┘
   │
   │  유휴 타임아웃(idle timeout) 경과 시 READY → IDLE 로 복귀 가능
   └──────────────────────────────────────────────────────────┐
                                                               │
   어느 상태에서든 channel.shutdown() 호출 시 ──────────────────▶│
                                                  ┌────────────▼──────┐
                                                  │     SHUTDOWN      │ (종착)
                                                  └───────────────────┘
```

각 상태를 "무엇이 전이를 일으키고 내부에서 무슨 일이 일어나는가"를 중심으로 하나씩 살펴본다.

### 4.1 IDLE: 지연된 시작

채널을 생성하면 보통 **IDLE** 상태로 시작한다. 여기서 중요한 점은 **채널을 만든다고 해서 TCP 연결이 바로 열리지는 않는다**는 것이다. gRPC는 연결을 지연해서(lazy) 연다. "아직 보낼 RPC가 없으면 연결을 미리 열어 둘 이유가 없다"는 설계 원칙 때문이다. 연결은 파일 디스크립터, 메모리, 서버 측 슬롯 같은 자원을 쓰므로 실제로 필요할 때까지 만들지 않는다.

IDLE에서 벗어나는 계기는 두 가지다.

1. **첫 RPC가 발생할 때.** 누군가 스텁으로 RPC를 호출하면 채널은 연결이 필요하다고 판단하고 CONNECTING으로 전이한다.
2. **`Connect()`(또는 언어별로 같은 역할을 하는 API)를 명시적으로 호출할 때.** "지금 미리 연결을 준비해 두라(warm up)"고 요청하는 것으로, 첫 RPC의 지연을 줄이고 싶을 때 쓴다.

또한 READY 상태였던 채널도 **일정 시간 동안 RPC가 한 건도 없으면 다시 IDLE로 돌아간다.** 이를 유휴 타임아웃(idle timeout)이라고 하며, 예를 들어 grpc-go의 기본값은 30분이다. 이때 채널은 연결을 닫아 자원을 반환하고, 다음 RPC가 오면 다시 CONNECTING으로 전이한다. 서버도 사용하지 않는 연결의 슬롯을 돌려받을 수 있으므로 양쪽 모두에 이득이다.

### 4.2 CONNECTING: 핸드셰이크 단계

CONNECTING은 "지금 실제 연결을 맺는 중"이라는 상태다. 이 상태에서는 다음 단계가 순서대로 일어난다.

```text
CONNECTING 내부의 단계들 (TLS 채널 기준)
  1) 이름 해석 결과에서 백엔드 주소 하나를 고른다 (LB가 결정)
  2) TCP 3-way handshake         (SYN → SYN/ACK → ACK)
  3) TLS handshake               (ClientHello → ... → Finished)
        └ ALPN 으로 "h2" 협상      ([[11 - 보안 - TLS mTLS 인증]])
  4) HTTP/2 connection preface 교환
        클라이언트: "PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n" + SETTINGS
        서버:       SETTINGS (MAX_CONCURRENT_STREAMS 등)
  5) 양쪽 SETTINGS ACK 교환
  → 여기까지 성공하면 READY
```

이 과정의 비용이 왜 큰지 한눈에 보인다. 왕복(RTT)이 여러 번 필요하고(TCP 1 RTT + TLS 1~2 RTT + HTTP/2 설정), TLS의 비대칭 암호 연산도 더해진다. **이 비용을 RPC마다 치르면 안 된다**는 점이 8절 안티패턴 논의의 핵심 근거다.

`MIN_CONNECT_TIMEOUT`이라는 상수도 이 단계에서 작동한다. 연결 시도 1회에 최소한 이만큼은 기다린다는 하한값(기본 20초)이다. 백오프 간격이 이보다 짧더라도 연결 시도 자체에는 최소 20초가 주어진다.

CONNECTING에서 핸드셰이크가 실패하면(SYN에 응답이 없거나, RST를 받거나, TLS 검증에 실패하는 등) **TRANSIENT_FAILURE**로 가고, 성공하면 **READY**로 간다.

### 4.3 READY: 요청을 처리하는 상태

READY는 "연결이 살아 있고 RPC를 보낼 수 있다"는 상태로, 가장 바람직한 상태다. 이 상태에서 스트림이 열리고 DATA 프레임이 오가며 실제 작업이 이루어진다.

READY에서 벗어나는 계기는 다음과 같다.

- **연결이 끊긴다**(상대가 FIN/RST를 보내거나, 네트워크가 단절되거나, keepalive ping이 실패한다). 이때는 TRANSIENT_FAILURE로 간다.
- **서버가 GOAWAY 프레임을 보낸다**(서버가 연결을 정상적으로 닫겠다고 미리 알린다). 진행 중인 RPC는 마저 처리하고 새 연결을 준비한다(11절 graceful shutdown에서 자세히 설명한다).
- **유휴 타임아웃**에 따라 한동안 RPC가 없으면 IDLE로 간다.

### 4.4 TRANSIENT_FAILURE: "지금은 안 되지만 곧 될 수 있다"

이름에 담긴 **Transient(일시적)** 라는 말이 중요하다. 영구적인 실패가 아니라 "지금은 연결할 수 없지만 잠시 후 다시 시도하면 될 수도 있다"는 낙관적인 상태다. 백엔드가 재시작 중이거나, 네트워크가 잠깐 끊겼거나, 일시적으로 과부하일 때 이 상태에 머문다.

이 상태의 가장 중요한 성질은 **TRANSIENT_FAILURE에 계속 머물러 있지 않는다**는 것이다. gRPC는 자동으로 백오프 타이머를 설정하고, 타이머가 만료되면 스스로 CONNECTING으로 돌아가 재연결을 시도한다. 애플리케이션 코드에서 재연결 로직을 작성할 필요가 전혀 없다. 이 자동 복구가 gRPC 연결 관리의 가장 큰 장점이다.

이때 **RPC 쪽에서는 동작이 두 갈래로 나뉜다.** 채널이 TRANSIENT_FAILURE 상태일 때 새 RPC가 들어오면 어떻게 될까?

- **Fail Fast (기본)**: RPC를 즉시 `UNAVAILABLE` 에러로 실패시킨다. "지금은 연결할 수 없으니 기다리지 말고 바로 알린다"는 방식이다.
- **Wait for Ready (옵션)**: RPC를 실패시키지 않고 **채널이 READY가 될 때까지 큐에 넣고 기다린다.** 데드라인이 만료되면 그때 실패한다(5절에서 자세히 설명한다).

### 4.5 SHUTDOWN: 종료 상태

`channel.shutdown()`(언어마다 이름이 다르다)을 호출하면 들어가는 **최종 상태**다. 한 번 SHUTDOWN이 되면 그 채널로는 새 RPC를 시작할 수 없고, 채널이 다시 살아나지도 않는다. 새 채널을 만들어야 한다. graceful shutdown의 동작 방식은 11절에서 다룬다.

### 4.6 상태 전이 표

| From | To | 트리거 |
|------|-----|--------|
| (생성) | IDLE | 채널 생성(게으른 기본값) |
| IDLE | CONNECTING | 첫 RPC 발생 / `Connect()` 호출 |
| CONNECTING | READY | 핸드셰이크 성공 |
| CONNECTING | TRANSIENT_FAILURE | 핸드셰이크 실패 |
| READY | TRANSIENT_FAILURE | 연결 끊김 / keepalive 실패 |
| READY | IDLE | 유휴 타임아웃 |
| READY | CONNECTING/IDLE | 서버 GOAWAY (새 연결 준비) |
| TRANSIENT_FAILURE | CONNECTING | 백오프 타이머 만료 → 재시도 |
| (any) | SHUTDOWN | `channel.shutdown()` |

### 4.7 상태를 코드로 관찰하기

상태 기계는 추상적인 개념에 그치지 않고 API로 노출된다. 채널의 현재 상태를 조회하고, 상태 변화를 구독할 수 있다.

Go 예시는 다음과 같다.

```go
package main

import (
	"context"
	"log"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/connectivity"
	"google.golang.org/grpc/credentials/insecure"
)

func main() {
	// grpc.NewClient: 채널을 만들지만 즉시 연결하지 않는다(IDLE).
	conn, err := grpc.NewClient(
		"dns:///orderservice.internal:50051",
		grpc.WithTransportCredentials(insecure.NewCredentials()),
	)
	if err != nil {
		log.Fatal(err)
	}
	defer conn.Close()

	log.Printf("생성 직후 상태: %v", conn.GetState()) // IDLE

	// 명시적으로 연결을 데운다(IDLE → CONNECTING).
	conn.Connect()

	// 상태 변화를 구독하며 READY 까지 기다린다.
	for {
		s := conn.GetState()
		log.Printf("현재 상태: %v", s)
		if s == connectivity.Ready {
			break
		}
		// 상태가 s에서 바뀔 때까지 블록(또는 데드라인까지).
		ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
		changed := conn.WaitForStateChange(ctx, s)
		cancel()
		if !changed {
			log.Println("상태 변화 없이 타임아웃")
			break
		}
	}
}
```

Java 예시는 다음과 같다.

```java
import io.grpc.ConnectivityState;
import io.grpc.ManagedChannel;
import io.grpc.ManagedChannelBuilder;

ManagedChannel channel = ManagedChannelBuilder
        .forTarget("dns:///orderservice.internal:50051")
        .usePlaintext()           // 데모용. 운영은 TLS.
        .build();

// requestConnection=true 이면 IDLE 일 때 연결을 트리거한다.
ConnectivityState state = channel.getState(/* requestConnection */ true);
System.out.println("현재 상태: " + state);

// 상태가 바뀌면 콜백을 받는다.
channel.notifyWhenStateChanged(state, () -> {
    ConnectivityState next = channel.getState(false);
    System.out.println("상태 전이: " + next);
});
```

Python에도 같은 개념이 있다.

```python
import grpc

channel = grpc.insecure_channel("orderservice.internal:50051")

def on_change(state: grpc.ChannelConnectivity):
    print("상태 전이:", state)

channel.subscribe(on_change, try_to_connect=True)
# state 는 grpc.ChannelConnectivity.IDLE / CONNECTING / READY /
#         TRANSIENT_FAILURE / SHUTDOWN 중 하나
```

이 API는 운영에서 매우 유용하다. 예를 들어 헬스 대시보드에 "이 채널이 지금 READY인지 TRANSIENT_FAILURE인지"를 표시하거나, 채널이 READY가 될 때까지 앱 부팅을 막는 readiness 게이트를 만들 수 있다.

## 5. WaitForReady: 실패를 기다림으로 바꾸는 스위치

4.4절에서 잠깐 나온 `WaitForReady`를 자세히 살펴보자. 분산 시스템 설계에서 의외로 중요한 의미를 가지는 옵션이다.

### 5.1 두 가지 철학: Fail Fast vs Wait for Ready

```text
                      RPC 시작 시점에 채널이 READY 가 아니라면?

  ┌─────────────────────────────┐     ┌─────────────────────────────┐
  │   Fail Fast (기본값)         │     │   Wait for Ready (옵션)       │
  ├─────────────────────────────┤     ├─────────────────────────────┤
  │ 즉시 UNAVAILABLE 로 실패      │     │ READY 될 때까지 큐에서 대기     │
  │ "지금 안 되니 바로 알려줄게"    │     │ "될 때까지 기다릴게"           │
  │                             │     │ 단, 데드라인 만료되면 실패        │
  │ 빠른 피드백, 빠른 폴백 가능     │     │ 일시적 장애를 호출자에게 숨김     │
  └─────────────────────────────┘     └─────────────────────────────┘
```

기본값은 **Fail Fast**다. 채널이 TRANSIENT_FAILURE 상태면 RPC는 기다리지 않고 즉시 `UNAVAILABLE`로 실패한다. 이것이 기본값인 이유는 분산 시스템에서는 "빠른 실패"가 더 안전하기 때문이다. 호출자는 실패를 바로 알고 재시도하거나, 폴백하거나, 서킷 브레이커를 작동시킬 수 있다. 응답을 무한정 기다리다가 시스템 전체가 느려지는 것보다 낫다.

**Wait for Ready**는 이 동작을 반대로 바꾼다. RPC를 시작할 때 채널이 아직 연결 중이거나 일시 장애 상태여도, RPC를 실패시키지 않고 채널이 READY가 될 때까지 보류한다. 이 옵션이 유용한 대표적인 상황은 다음과 같다.

- **앱이 부팅할 때 의존 서비스가 아직 뜨지 않은 경우.** 부팅 순서를 강제하지 않고 "곧 뜰 테니 기다렸다가 보내라"고 지정할 수 있다.
- **일시적인 네트워크 불안정을 호출자에게 숨기고 싶은 경우.** 단, 반드시 데드라인([[10 - Deadline 취소 타임아웃]])과 함께 써야 한다. 데드라인이 없는 Wait for Ready는 영원히 기다릴 수 있는 위험한 조합이다.

주의할 점이 있다. Wait for Ready가 보장하는 것은 "연결 단계의 일시적 실패를 기다린다"는 것이다. RPC가 서버에 도달해 처리되다가 실패한 경우까지 무한히 기다려 준다는 뜻은 아니다. 연결이 확립되고 RPC가 시작된 뒤의 재시도는 별개의 메커니즘([[13 - 안정성 - Retry Health Check Keepalive]])이 담당한다.

### 5.2 코드

Go (호출 단위 옵션):

```go
import "google.golang.org/grpc"

// 반드시 데드라인과 함께!
ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
defer cancel()

resp, err := client.GetOrder(ctx, &pb.GetOrderRequest{Id: "order-1"},
	grpc.WaitForReady(true), // 채널이 READY 될 때까지 기다림(데드라인 내에서)
)
```

Java (CallOptions를 통해 스텁 단위로 설정):

```java
OrderServiceGrpc.OrderServiceBlockingStub stub =
        OrderServiceGrpc.newBlockingStub(channel)
            .withWaitForReady()                          // wait-for-ready 켬
            .withDeadlineAfter(3, TimeUnit.SECONDS);     // 반드시 데드라인
```

Python:

```python
resp = stub.GetOrder(
    order_pb2.GetOrderRequest(id="order-1"),
    wait_for_ready=True,
    timeout=3.0,   # 데드라인
)
```

### 5.3 "연결 실패가 곧 RPC 실패는 아니다"

이 절의 핵심을 한 문장으로 정리하면 다음과 같다. **채널이 TRANSIENT_FAILURE 상태라는 사실만으로 RPC가 실패하는 것은 아니다.** Fail Fast면 실패하고, Wait for Ready면 기다린다. 즉 RPC의 결과는 채널 상태, wait-for-ready 정책, 데드라인이라는 세 요소의 조합으로 정해진다. 이 세 가지를 분리해서 생각하는 습관이 gRPC를 성숙하게 운영하는 기준이 된다.

## 6. 재연결 백오프: 재시도 폭주를 막는 지수적 대기

앞에서 TRANSIENT_FAILURE 상태에서는 자동으로 재시도한다고 했다. 그렇다면 **얼마나 자주** 재시도할까? 1ms마다 재시도한다면, 클라이언트 수천 대가 죽은 서버에 초당 수백만 번 SYN을 보내서 막 복구되려던 서버를 다시 다운시킨다. 이것이 잘 알려진 **thundering herd(쇄도) / retry storm(재시도 폭풍)** 문제다.

gRPC는 이 문제를 **지수 백오프 + 지터(exponential backoff with jitter)** 로 막는다. 이 정책은 gRPC 공식 "Connection Backoff" 명세에 표준 상수와 함께 정의되어 있다.

### 6.1 표준 알고리즘과 기본 상수

```text
파라미터 (gRPC connection-backoff 명세 권장값)
  INITIAL_BACKOFF     = 1 초     (첫 실패 후 대기)
  MULTIPLIER          = 1.6      (실패할 때마다 곱하는 배수)
  JITTER              = 0.2      (±20% 무작위 흔들기)
  MAX_BACKOFF         = 120 초   (대기 상한)
  MIN_CONNECT_TIMEOUT = 20 초    (연결 시도 1회의 최소 허용 시간)
```

알고리즘을 의사코드로 쓰면 다음과 같다.

```text
current_backoff = INITIAL_BACKOFF              # 1s
첫 연결 시도 즉시 수행
loop:
    이번 연결 시도에 최소 MIN_CONNECT_TIMEOUT(20s) 기회를 준다
    실패하면:
        sleep_for = current_backoff
                    × random(1 - JITTER, 1 + JITTER)   # ±20%
        wait(sleep_for)
        current_backoff = min(current_backoff × MULTIPLIER, MAX_BACKOFF)
    성공하면:
        current_backoff = INITIAL_BACKOFF   # 다시 1s 로 리셋
        break
```

### 6.2 실제 대기 시간이 어떻게 커지는가

지터를 빼고 중앙값만 보면 대기 시간은 다음과 같이 늘어난다.

| 시도 | 백오프(지터 전) | 지터 적용 범위(±20%) |
|------|----------------|----------------------|
| 1차 실패 후 | 1.0s | 0.8s ~ 1.2s |
| 2차 | 1.6s | 1.28s ~ 1.92s |
| 3차 | 2.56s | 2.05s ~ 3.07s |
| 4차 | 4.10s | 3.28s ~ 4.92s |
| 5차 | 6.55s | 5.24s ~ 7.86s |
| 6차 | 10.49s | 8.39s ~ 12.58s |
| ... | (×1.6씩) | ... |
| n차 | min(1.6^(n-1), 120)s | ... |
| 충분히 큰 n | 120s (상한) | 96s ~ 144s |

```text
대기시간(초)
120 ┤                                      ●━━━━━━━━━●  ← MAX_BACKOFF 천장
    │                                 ●
    │                            ●
    │                       ●
 10 ┤                  ●
    │             ●
  5 ┤        ●
    │    ●
  1 ┤●
    └┬───┬───┬───┬───┬───┬───┬───┬───┬───┬──▶ 재시도 횟수
     1   2   3   4   5   6   7   8  ...
```

### 6.3 지터가 중요한 이유

지터가 없다고 가정해 보자. 데이터센터 네트워크가 잠깐 끊겼다가 복구될 때 **클라이언트 1만 대가 정확히 동시에** 백오프 타이머를 시작했다면, 모든 클라이언트가 정확히 1초 후, 2.56초 후, ... 같은 시점에 한꺼번에 재연결을 시도한다. 복구된 서버는 이렇게 동기화된 트래픽이 몰리면서 다시 다운된다.

지터는 이 동기화를 깨뜨린다. ±20%의 무작위성이 1만 대의 재시도 시점을 시간 축에 흩어 놓으므로, 한꺼번에 몰리던 트래픽이 완만하게 분산된다. **지터는 다른 시스템에 부담을 주지 않는 분산 시스템 구성 요소라면 반드시 갖춰야 할 요소다.**

```text
지터 없음:           지터 있음:
  ████ (동시 폭주)      ▁▂▃▄▃▂▁▂▃▂▁  (시간에 분산)
   ↑                    완만하게 퍼짐
 서버 다시 죽음          서버 살아남음
```

### 6.4 백오프와 RPC의 관계

다시 강조하면, 백오프는 **연결 수준**의 자동 복구이고 **RPC 수준**의 재시도가 아니다. 둘은 서로 다른 계층에 속한다.

- **연결 백오프**: 끊긴 서브채널을 다시 연결하는 시점을 제어한다. 항상 켜져 있고, 끌 수 없으며, 애플리케이션이 신경 쓸 필요가 없다.
- **RPC 재시도(retry)**: 실패한 개별 RPC를 다시 보낼지 정하는 정책이다. 명시적으로 설정해야 하고, 멱등성(idempotency)을 고려해야 한다. 이 내용은 13장(안정성)에서 다룬다.

두 메커니즘은 함께 동작한다. 연결이 백오프를 거쳐 복구되는 동안 wait-for-ready RPC는 데드라인까지 기다리고, retry 정책은 재시도할 수 있는 에러에 한해서 요청을 다시 보낸다.

## 7. 스텁(Stub): 채널 위에 올리는 가벼운 클라이언트 객체

지금까지는 무거운 객체인 채널을 살펴봤다. 이제 가벼운 객체인 스텁을 살펴본다.

### 7.1 스텁이란 무엇인가

스텁(stub)은 [[06 - 코드 생성과 protoc 툴체인]]에서 설명한 도구가 `.proto`로부터 생성하는 **타입 안전한 클라이언트 객체**다. "원격 메서드를 로컬 함수처럼" 호출할 수 있게 해 주는 얇은 어댑터다. 스텁 자체에는 연결, 상태, 자원이 거의 없다. 스텁은 **채널 참조와 메서드 시그니처를 묶어 놓은 것**에 불과하다.

```text
   채널 (무겁다: 소켓·상태기계·백오프·LB 보유)
        ▲
        │ 참조만 들고 있음
   ┌────┴────┬──────────┬──────────┐
 스텁A      스텁B       스텁C       스텁D    ← 전부 같은 채널 공유
(blocking) (async)   (future)   (다른서비스)
```

여기서 핵심은 **스텁은 비용이 작고, 채널은 비용이 크다**는 점이다. 스텁은 얼마든지 만들어도 된다. 요청마다 만들어도 되고, 메서드마다 다른 옵션을 붙인 스텁을 파생시켜도 된다. 하지만 채널은 절대 함부로 만들면 안 된다(8절).

### 7.2 스텁의 종류: 호출 스타일별

같은 서비스라도 보통 여러 종류의 스텁이 생성된다. 스텁은 "RPC의 결과를 어떻게 받을 것인가"에 따라 나뉜다.

| 스텁 종류 | 호출 방식 | 반환 | 적합한 곳 |
|-----------|-----------|------|-----------|
| **Blocking / Sync** | 결과 올 때까지 스레드 블록 | 응답 객체 직접 | 단순 코드, 스크립트, 순차 로직 |
| **Async (callback/observer)** | 콜백/옵저버로 결과 받음 | void, 콜백 호출 | 논블로킹, 스트리밍, 고동시성 |
| **Future** | `Future<Response>` 반환 | 나중에 `.get()` | 여러 RPC 병렬 후 합류 |

Java는 이 세 가지를 명시적으로 나누어 생성한다.

```java
// 같은 채널 위에 세 가지 스타일의 스텁을 만든다 (모두 같은 채널 공유)
ManagedChannel channel = ManagedChannelBuilder
        .forTarget("dns:///orderservice.internal:50051")
        .useTransportSecurity()      // 운영은 TLS
        .build();

// 1) Blocking: 결과가 올 때까지 현재 스레드를 막는다.
OrderServiceGrpc.OrderServiceBlockingStub blocking =
        OrderServiceGrpc.newBlockingStub(channel);
OrderResponse r = blocking.getOrder(GetOrderRequest.newBuilder().setId("o1").build());

// 2) Future: ListenableFuture 로 받아 나중에 합류.
OrderServiceGrpc.OrderServiceFutureStub future =
        OrderServiceGrpc.newFutureStub(channel);
ListenableFuture<OrderResponse> f =
        future.getOrder(GetOrderRequest.newBuilder().setId("o2").build());

// 3) Async: StreamObserver 콜백으로 받는다. 스트리밍에 필수.
OrderServiceGrpc.OrderServiceStub async =
        OrderServiceGrpc.newStub(channel);
async.getOrder(GetOrderRequest.newBuilder().setId("o3").build(),
    new StreamObserver<OrderResponse>() {
        @Override public void onNext(OrderResponse value) { /* 응답 도착 */ }
        @Override public void onError(Throwable t) { /* 에러 */ }
        @Override public void onCompleted() { /* 종료 */ }
    });
```

스트리밍(서버, 클라이언트, 양방향)은 본래 비동기이므로 보통 async 스텁(또는 언어별 스트리밍 API)을 쓴다. 4가지 통신 방식은 [[05 - 통신의 4가지 방식 - Unary와 Streaming]]을 참고한다.

### 7.3 Go의 단일 클라이언트 모델

Go는 위처럼 스텁을 세 종류로 나누지 않는다. 생성되는 클라이언트는 하나이고, 동기·비동기, 타임아웃, 취소 같은 제어는 모두 첫 번째 인자인 `context.Context`로 표현한다. 호출 정책을 "스타일"이 아니라 "컨텍스트"로 전달하는 설계다.

```go
// 생성된 클라이언트는 하나. 채널(conn)을 감싸는 얇은 래퍼.
client := pb.NewOrderServiceClient(conn)

// 동기처럼 보이지만, ctx 로 데드라인/취소를 주입한다.
ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
defer cancel()

resp, err := client.GetOrder(ctx, &pb.GetOrderRequest{Id: "o1"})
// 병렬이 필요하면 goroutine 으로 여러 번 호출하면 된다.
```

이 차이는 기억해 둘 만하다. **Java/Python은 스텁 종류로 스타일을 나누고, Go는 단일 client와 context로 제어한다.** 어느 쪽이든 "채널을 공유하는 가벼운 클라이언트 객체"라는 본질은 같다.

### 7.4 스텁에서 옵션을 적용한 스텁 파생하기 (불변 객체 패턴)

Java 스텁은 불변(immutable)이다. `withDeadlineAfter`, `withWaitForReady`, `withCompression` 같은 메서드는 **원본을 바꾸지 않고 옵션을 적용한 새 스텁을 반환**한다. 덕분에 채널 하나 위에서 RPC마다 다른 정책을 안전하게 적용할 수 있다.

```java
OrderServiceGrpc.OrderServiceBlockingStub base =
        OrderServiceGrpc.newBlockingStub(channel);

// 빠르게 끊어야 하는 호출: 짧은 데드라인 + fail fast
OrderResponse fast = base
        .withDeadlineAfter(500, TimeUnit.MILLISECONDS)
        .getOrder(req);

// 배치처럼 느려도 되는 호출: 긴 데드라인 + wait-for-ready + 압축
OrderResponse slow = base
        .withDeadlineAfter(30, TimeUnit.SECONDS)
        .withWaitForReady()
        .withCompression("gzip")
        .listOrders(req2);
```

`base` 스텁은 바뀌지 않는다. 파생된 스텁들은 채널을 공유하고 호출별 옵션만 다르다. "스텁은 비용이 작다"는 말이 실무에서 드러나는 모습이 이것이다.

## 8. 기본 원칙: 채널은 만들어서 공유하고, 절대 요청마다 만들지 마라

이 장에서 단 하나만 기억해야 한다면 다음 원칙이다.

> **채널은 thread-safe하고 비용이 크다. 앱 생명주기 동안 타겟당 하나(또는 소수)를 만들어 모든 곳에서 공유하라. 요청마다 채널을 새로 만드는 것은 치명적인 안티패턴이다.**

### 8.1 채널은 thread-safe하다

gRPC 채널은 여러 스레드나 고루틴이 동시에 사용해도 안전하도록 설계되었다. 멀티플렉싱 덕분에 채널 하나로 RPC 수백 개를 동시에 보내도 내부에서 스트림을 나눠 처리한다. 따라서 채널을 스레드마다 만들 이유가 전혀 없다. 하나를 만들어 공유하면 된다.

### 8.2 요청마다 채널을 만들면 무슨 일이 일어나는가

안티패턴 코드를 보자(절대 따라 하지 말 것).

```go
// 끔찍한 안티패턴: 요청마다 채널 생성/파괴 (절대 금지)
func handleRequest(orderID string) (*pb.OrderResponse, error) {
	conn, _ := grpc.NewClient("dns:///orderservice:50051",
		grpc.WithTransportCredentials(insecure.NewCredentials()))
	defer conn.Close() // 매번 닫는다 = 매번 연결을 버린다

	client := pb.NewOrderServiceClient(conn)
	ctx, cancel := context.WithTimeout(context.Background(), time.Second)
	defer cancel()
	return client.GetOrder(ctx, &pb.GetOrderRequest{Id: orderID})
}
```

이 코드가 요청마다 치르는 비용을 나누어 보면 다음과 같다.

```text
요청 1건당 발생하는 낭비:
  1) DNS 조회                              (이름 해석 캐시 무력화)
  2) TCP 3-way handshake          1 RTT
  3) TLS handshake               1~2 RTT  (비대칭 암호 연산까지)
  4) HTTP/2 preface + SETTINGS 교환  1 RTT
  ───────────────────────────────────────
     => 핸드셰이크에만 3~4 RTT + CPU 암호연산
        그리고 곧바로 close 로 다 버림

  5) TCP Slow Start: 막 연 연결은 혼잡 윈도우(cwnd)가 작아
     처음엔 느리게 보낸다. 워밍업이 되기도 전에 닫음.
  6) 파일 디스크립터(FD) 낭비 + TIME_WAIT 소켓 누적
     → 고부하 시 "too many open files" / 포트 고갈
  7) 서버 측 연결 슬롯/메모리 폭증, 서버 GC 압박
```

핵심 손실을 표로 정리하면 다음과 같다.

| 항목 | 채널 공유 | 요청마다 생성 |
|------|-----------|----------------|
| 핸드셰이크 비용 | 앱 시작 시 1회 | 요청마다 매번 |
| TCP slow start | 한 번 데우면 끝 | 매번 콜드 스타트 |
| 멀티플렉싱 활용 | O (한 연결로 수백 RPC) | X (연결당 1 RPC) |
| FD/소켓 | 소수 유지 | 폭증, TIME_WAIT 누적 |
| 지연(latency) | 낮음(핸드셰이크 생략) | 매 요청 +수 RTT |
| 서버 부하 | 안정적 | 연결 폭주 |

특히 5번 **TCP Slow Start**는 눈에 잘 띄지 않지만 영향이 크다. 새로 연결된 TCP는 혼잡 제어 때문에 처음에는 적은 양의 데이터만 보낸다(혼잡 윈도우가 작다). 연결을 오래 유지하면 윈도우가 커지면서 처리량이 늘어나지만, 매번 새로 연결하면 연결이 계속 초기 상태에 머문다. 채널을 공유하면 "충분히 워밍업된 연결을 계속 쓴다"는 점에서 그만큼 빠르다.

### 8.3 올바른 패턴

```go
// 앱 시작 시 한 번 만들어 전역(또는 DI 컨테이너)으로 공유 (올바른 패턴)
type App struct {
	orderClient pb.OrderServiceClient
	conn        *grpc.ClientConn
}

func NewApp() (*App, error) {
	conn, err := grpc.NewClient(
		"dns:///orderservice.internal:50051",
		grpc.WithTransportCredentials(insecure.NewCredentials()),
		// keepalive, 메시지 크기 한계 등은 여기서 한 번 설정
	)
	if err != nil {
		return nil, err
	}
	return &App{
		conn:        conn,
		orderClient: pb.NewOrderServiceClient(conn), // 스텁은 가볍다
	}, nil
}

// 요청 핸들러는 공유된 client(스텁)만 쓴다. 채널은 건드리지 않는다.
func (a *App) handleRequest(ctx context.Context, id string) (*pb.OrderResponse, error) {
	return a.orderClient.GetOrder(ctx, &pb.GetOrderRequest{Id: id})
}

// 앱 종료 시 한 번만 닫는다.
func (a *App) Shutdown() { a.conn.Close() }
```

```java
// Java: 채널은 싱글턴/빈으로 한 번, 스텁은 그 위에서 자유롭게 (올바른 패턴)
@Configuration
class GrpcConfig {
    @Bean(destroyMethod = "shutdownNow")   // 컨테이너 종료 시 닫힘
    ManagedChannel orderChannel() {
        return ManagedChannelBuilder
                .forTarget("dns:///orderservice.internal:50051")
                .useTransportSecurity()
                .keepAliveTime(30, TimeUnit.SECONDS)
                .build();
    }

    @Bean
    OrderServiceGrpc.OrderServiceBlockingStub orderStub(ManagedChannel ch) {
        return OrderServiceGrpc.newBlockingStub(ch);
    }
}
```

### 8.4 "소수"라고 한 이유

"하나"가 원칙이지만 "소수"가 맞는 경우도 있다. 3.3절에서 봤듯이, 단일 연결의 `MAX_CONCURRENT_STREAMS`에 묶여 처리량이 막히는 초고부하 상황에서는 같은 타겟에 채널을 2~4개 두는 **채널 풀링**이 타당하다. 또한 지연에 민감한 트래픽과 배치 트래픽을 분리하려고 채널을 나누기도 한다.

핵심은 채널 수가 "요청마다" 늘어나는 것이 아니라 "용도와 부하에 따라 정해 둔 소수"라는 점이다. 이 트레이드오프를 정량적으로 판단하는 방법은 15장(성능과 Flow Control 백프레셔)에서 다룬다.

## 9. 이름 해석·로드밸런싱과 채널의 관계

채널이 생성될 때 가장 먼저 하는 일은 **타겟(target) 문자열을 실제 주소 목록으로 해석**하는 것이다. 이 과정의 자세한 내용은 12장(이름 해석과 로드밸런싱)에서 다루고, 여기서는 **채널 생명주기 관점에서 무슨 일이 일어나는지**만 살펴본다.

### 9.1 타겟 문자열의 구조

```text
   dns:///orderservice.internal:50051
   └─┬─┘   └──────────┬──────────┘└─┬─┘
   scheme          host            port
  (resolver를      (해석 대상)
   고름)

  예:
   dns:///foo.bar:50051        → DNS resolver 로 foo.bar 의 A/AAAA 레코드 조회
   passthrough:///10.0.0.5:50051 → 해석 없이 주소 그대로 사용
   unix:///var/run/svc.sock    → 유닉스 도메인 소켓
   xds:///foo.bar              → xDS(서비스 메시) 제어 평면에서 해석
```

scheme이 **resolver(이름 해석기)** 를 결정하고, resolver가 host를 주소 목록으로 해석한다.

### 9.2 채널 생성 → 해석 → 서브채널 → LB

```text
channel 생성
   │
   ▼
[Name Resolver]  dns:///orderservice.internal:50051
   │  → [10.0.0.11:50051, 10.0.0.12:50051, 10.0.0.13:50051]
   │  (그리고 백그라운드에서 주기적으로 재해석 → 주소 변동 반영)
   ▼
[LB Policy]  예: round_robin
   │  → 받은 주소마다 Subchannel 을 만들라고 지시
   ▼
Subchannel(.11)  Subchannel(.12)  Subchannel(.13)
   각자 4절의 상태기계(IDLE→CONNECTING→READY...)를 독립적으로 돈다
   │
   ▼
RPC 가 오면 LB Policy 가 READY 인 서브채널 중 하나를 골라(picker) 보낸다
```

여기서 채널 생명주기와 관련된 중요한 사실은 다음과 같다.

- **채널의 전체 상태는 서브채널 상태를 집계한 결과**다. 예를 들어 round_robin에서는 서브채널이 하나라도 READY면 채널을 READY로 보고, 서브채널이 모두 TRANSIENT_FAILURE여야 채널이 TRANSIENT_FAILURE가 된다.
- **resolver는 한 번 해석하고 끝나지 않는다.** 주기적으로(또는 연결 실패 같은 이벤트가 발생하면) 다시 해석해서 백엔드 추가와 제거를 반영한다. 새 주소가 생기면 새 서브채널이 만들어지고, 주소가 사라지면 해당 서브채널이 graceful하게 정리된다.
- **LB 정책에 따라 연결 개수가 달라진다.** `pick_first`(기본)는 주소 목록을 순서대로 시도해 **연결 하나만** 쓴다. `round_robin`은 **모든 백엔드에 연결**을 만들어 요청을 분산한다. 이 선택은 3.3절의 처리량 한계와 직접 연결된다.

## 10. 채널 옵션과 인자: 생성 시점에 정해 두는 정책

채널을 만들 때 넘기는 옵션(Go의 `DialOption`, Java의 빌더 메서드, C-core의 channel args)은 그 채널의 동작 전반을 결정한다. 대부분 다른 장에서 자세히 다루므로, 여기서는 **무엇을 어디서 설정하는지 한눈에 보여 주는 표**만 제공한다.

| 옵션 범주 | 무엇 | 자세히 다루는 장 | Go 예 | Java 예 |
|-----------|------|------------------|-------|---------|
| 보안/자격증명 | TLS/mTLS/plaintext | [[11 - 보안 - TLS mTLS 인증]] | `WithTransportCredentials` | `useTransportSecurity()` |
| 메시지 크기 한계 | 송수신 최대 바이트 | 15장(성능과 Flow Control 백프레셔) | `WithDefaultCallOptions(MaxCallRecvMsgSize)` | `maxInboundMessageSize()` |
| Keepalive | ping 주기/타임아웃 | 13장(안정성) | `WithKeepaliveParams` | `keepAliveTime/keepAliveTimeout` |
| 압축 | gzip 등 | 15장(성능과 Flow Control 백프레셔) | `UseCompressor` (call opt) | `withCompression("gzip")` |
| 인터셉터 | 횡단 관심사 훅 | [[08 - 메타데이터와 인터셉터]] | `WithUnaryInterceptor` | `intercept(...)` |
| 이름 해석/LB | resolver, LB 정책 | 12장(이름 해석과 로드밸런싱) | `WithResolvers`, `WithDefaultServiceConfig` | `defaultLoadBalancingPolicy()` |
| 재시도 | retry 정책(service config) | 13장(안정성) | service config JSON | service config JSON |
| 유휴 타임아웃 | READY→IDLE 시간 | (이 장) | `WithIdleTimeout` | `idleTimeout()` |

메시지 크기 한계만 간단히 살펴보자. gRPC는 기본적으로 **수신 메시지 크기를 4MB로 제한**한다(송신 크기는 기본적으로 제한하지 않는 구현이 많다). 큰 메시지를 주고받아야 하면 이 한계를 올려야 한다. 단, 큰 메시지는 메모리와 지연 측면에서 비용이 크므로 보통은 스트리밍으로 나누어 보내는 편이 낫다(5장 통신의 4가지 방식).

```go
conn, _ := grpc.NewClient(target,
	grpc.WithTransportCredentials(creds),
	grpc.WithDefaultCallOptions(
		grpc.MaxCallRecvMsgSize(16*1024*1024), // 수신 16MB 허용
	),
)
```

인터셉터를 등록하는 시점이 채널 생성 시점이라는 점도 기억하자. 메타데이터 주입, 인증 토큰 첨부, 로깅·트레이싱·메트릭 같은 횡단 관심사를 인터셉터로 한 번 등록하면 그 채널의 모든 RPC에 적용된다(8장 메타데이터와 인터셉터).

## 11. Graceful Shutdown: 연결을 정상적으로 종료하기

이제 채널과 연결의 마지막 단계인 **종료**를 살펴본다. 소켓을 그냥 `close()`하면 진행 중이던 RPC가 중간에 끊겨 에러가 난다. gRPC는 클라이언트 채널과 서버 양쪽에서 **우아한 종료(graceful shutdown)** 를 지원한다.

### 11.1 클라이언트 측: shutdown vs shutdownNow

Java는 두 방식을 명확히 구분한다.

```java
ManagedChannel channel = /* ... */;

// 우아한 종료: 진행 중 RPC는 끝까지 처리, 새 RPC만 거부.
channel.shutdown();

// 종료 완료를 일정 시간 기다린다(블록).
if (!channel.awaitTermination(5, TimeUnit.SECONDS)) {
    // 5초 안에 못 끝내면 강제 종료: 진행 중 RPC도 취소(CANCELLED).
    channel.shutdownNow();
    channel.awaitTermination(2, TimeUnit.SECONDS);
}
```

```text
shutdown()      : "문을 닫되, 안에 있는 손님은 다 나갈 때까지 기다린다"
                  - 새 RPC 거부, 기존 RPC 완료 대기, 끝나면 연결 종료
shutdownNow()   : "지금 당장 닫는다. 안에 있는 손님도 내보낸다"
                  - 진행 중 RPC를 CANCELLED 로 취소하고 즉시 종료
awaitTermination: 종료가 실제로 끝날 때까지 블록(타임아웃 포함)
```

Go에는 `conn.Close()` 하나만 있다. 진행 중인 RPC는 컨텍스트 취소로 정리되며, 실무에서는 `Close()`를 호출하기 전에 워커들이 끝나기를 기다리는 패턴을 직접 작성한다.

```go
// 우아한 종료 패턴
func (a *App) Shutdown(ctx context.Context) error {
	// 1) 새 작업 받기를 멈추고, 진행 중 작업이 끝나길 기다린다(앱 레벨).
	a.stopAccepting()
	a.waitInflight(ctx)
	// 2) 채널을 닫는다.
	return a.conn.Close()
}
```

### 11.2 서버 측: GOAWAY 프레임

서버가 종료하거나(배포, 스케일다운) 연결을 정리하려고 할 때는 연결을 갑자기 끊지 않고 **GOAWAY** 프레임을 보낸다. GOAWAY는 HTTP/2 표준 메커니즘이다(RFC 7540 §6.8, RFC 9113으로 갱신). "이제 이 연결로는 새 스트림을 받지 않는다. 단, 마지막으로 처리한 스트림 ID까지는 책임지고 끝내겠다"고 미리 알리는 것이다.

GOAWAY 프레임을 바이트 단위로 디코딩해 보자.

```text
바이트열:  00 00 08   07   00   00 00 00 00   00 00 00 09   00 00 00 00
           └──┬───┘   │    │    └────┬─────┘   └────┬─────┘   └────┬────┘
           Length=8  Type Flags  StreamID=0   LastStreamID    ErrorCode
            (8바이트  =0x07 =0    (GOAWAY도     =9 (이 ID 이하   =0 (NO_ERROR)
             payload) GOAWAY      stream 0)    스트림은 처리됨)
```

- `00 00 08`: payload 8바이트 (Last-Stream-ID 4 + Error Code 4. 디버그 데이터는 없다).
- `07`: 프레임 타입 0x7 = GOAWAY.
- `00`: 플래그 없음.
- `00 00 00 00`: 스트림 0(연결 전체).
- `00 00 00 09`: **Last-Stream-ID = 9.** "스트림 9까지는 서버가 처리했거나 처리 중이다. 그보다 큰 번호의 스트림은 시작도 하지 않았으므로 클라이언트가 다른 연결에서 재시도해도 안전하다"는 뜻이다.
- `00 00 00 00`: 에러 코드 0 = NO_ERROR(정상 종료).

GOAWAY를 받은 클라이언트 채널은 다음과 같이 반응한다.

```text
1) Last-Stream-ID 이하의 진행 중 RPC → 계속 진행해 끝맺는다.
2) Last-Stream-ID 초과로 보내려던/막 보낸 RPC → 이 연결에선 처리 보장 안 됨.
   클라이언트는 이들을 새 연결에서 안전하게 재시도할 수 있다.
3) 이 연결로는 새 스트림을 더 열지 않는다.
4) 동시에 새 연결(새 서브채널 또는 같은 백엔드로의 새 연결)을 준비한다.
   → 채널 전체로 보면 무중단(connection draining).
```

덕분에 서버를 **무중단 배포(graceful rolling deploy)** 할 수 있다. 새 파드가 뜨면 기존 파드가 GOAWAY로 연결을 비우고(drain), 진행 중인 요청을 모두 끝낸 뒤 종료한다. 클라이언트는 그 사이에 다른 연결로 자연스럽게 옮겨 간다. GOAWAY와 keepalive, health check가 함께 무중단 운영을 만드는 방식은 13장(안정성)에서 더 살펴본다.

### 11.3 양방향 종료 순서 한눈에 보기

```text
   클라이언트 채널                         서버
        │                                  │
        │     RPC 들 진행 중 (stream 1,3,5)  │
        │◀────────── 데이터 ──────────────▶│
        │                                  │  (서버 종료 시작)
        │◀──────────── GOAWAY(last=5) ─────│  "5까지만 받음"
        │                                  │
        │  stream 1,3,5 는 끝까지 마무리      │
        │◀────────── 응답 ─────────────────│
        │                                  │
        │  새 RPC 는 새 연결로 ──────────────│ (다른 파드/연결)
        │                                  │
        │           (기존 연결 close)        │  서버 종료 완료
```

## 12. 언어별 차이 메모

개념은 같지만 API의 형태는 언어마다 다르다. 여기서는 자주 헷갈리는 부분만 모았다.

### 12.1 Go: Dial에서 NewClient로

grpc-go는 비교적 최근(v1.63 무렵)에 채널 생성 API를 크게 바꿨다. 이 변화를 알아 두어야 예전 코드와 새 코드를 모두 읽을 수 있다.

| 구분 | 옛 방식 `grpc.Dial` / `DialContext` (deprecated) | 새 방식 `grpc.NewClient` (권장) |
|------|--------------------------------------------------|---------------------------------|
| 연결 시점 | 옵션에 따라 eager 연결 가능(`WithBlock`) | 항상 lazy. 생성 시 IDLE, 첫 RPC에 연결 |
| `WithBlock`/`WithReturnConnectionError` | 지원(생성이 연결까지 블록) | 없음(개념적으로 부적합해 제거) |
| 기본 resolver scheme | `passthrough`(주소 그대로) | `dns`(DNS 조회) |
| 권장 여부 | deprecated | 권장 |

```go
// 옛 방식 (deprecated): 연결될 때까지 블록하던 패턴
conn, err := grpc.DialContext(ctx, "orderservice:50051",
	grpc.WithTransportCredentials(insecure.NewCredentials()),
	grpc.WithBlock(),                    // 연결 완료까지 대기 (NewClient엔 없음)
)

// 새 방식 (권장): 게으른 생성. 연결 워밍업이 필요하면 Connect()를 명시 호출
conn, err := grpc.NewClient("dns:///orderservice:50051",
	grpc.WithTransportCredentials(insecure.NewCredentials()),
)
// conn.Connect()  // 원하면 미리 연결을 데운다
```

`WithBlock`이 사라진 것이 처음에는 불편하지만 설계 원칙상 옳다. "채널 생성"과 "연결 성공"은 별개의 사건이고, 채널은 본래 연결을 지연해서 열고 스스로 복구해야 하기 때문이다. 부팅할 때 연결을 보장해야 한다면 `Connect()`를 호출한 뒤 `WaitForStateChange`로 READY를 기다리거나, 첫 호출을 wait-for-ready RPC로 보낸다.

함정이 하나 더 있다. 기본 scheme이 `passthrough`에서 `dns`로 바뀌었기 때문에, `grpc.Dial("localhost:50051", ...)`처럼 scheme 없이 쓰던 코드를 `grpc.NewClient`로 옮기면 `localhost`를 DNS로 해석하려고 한다. `dns:///`나 `passthrough:///`를 명시적으로 붙이는 습관을 들이는 편이 안전하다.

### 12.2 Java: ManagedChannel과 빌더

Java에서 채널 타입은 `ManagedChannel`이고, 채널을 만들 때는 `ManagedChannelBuilder`를 쓴다. "Managed"는 "수명과 연결을 라이브러리가 관리한다"는 뜻이다.

```java
ManagedChannel channel = ManagedChannelBuilder
        .forTarget("dns:///orderservice.internal:50051")
        .useTransportSecurity()           // 또는 usePlaintext() (데모)
        .keepAliveTime(30, TimeUnit.SECONDS)
        .maxInboundMessageSize(16 * 1024 * 1024)
        .build();

// ... 스텁으로 RPC ...

// 종료(11.1절)
channel.shutdown();
channel.awaitTermination(5, TimeUnit.SECONDS);
```

종료 메서드 3종(`shutdown`/`shutdownNow`/`awaitTermination`)의 차이는 11.1절에서 본 그대로다. 운영 코드에서는 보통 `shutdown()` → `awaitTermination(timeout)` → (끝나지 않으면) `shutdownNow()` 순서의 단계적 패턴을 쓴다.

### 12.3 Python과 기타 언어

- **Python**: `grpc.insecure_channel(target)` / `grpc.secure_channel(target, creds)`로 채널을 생성한다. `channel.subscribe(callback, try_to_connect=True)`로 상태를 구독한다. `with grpc.insecure_channel(...) as channel:` 컨텍스트 매니저를 쓰면 자동으로 종료된다. 동기 스텁과 `grpc.aio`(asyncio) 비동기 스텁이 따로 있다.
- **C++ / C-core 계열(Python, Ruby, PHP, C# 일부)**: 내부적으로 C-core를 공유하며 channel args(키-값)로 옵션을 준다. 키는 `GRPC_ARG_KEEPALIVE_TIME_MS` 같은 문자열이다.
- 어떤 언어든 **개념(채널=가상 연결, 서브채널, 상태 기계, 백오프, 스텁 공유)은 같다.** API 이름만 바꿔서 이해하면 된다.

## 13. 전체를 연결하는 시나리오: RPC 하나의 생애

지금까지 살펴본 내용을 하나의 타임라인으로 엮어 보자. 앱이 부팅하고, 첫 주문 조회 RPC를 보내고, 백엔드가 잠깐 죽었다가 다시 살아나고, 앱이 종료될 때까지의 과정이다.

```text
t0  앱 시작: grpc.NewClient(dns:///orderservice:50051)
    → Channel 생성. 상태 = IDLE. 아직 소켓 0개.

t1  첫 RPC: client.GetOrder("o-1")
    → IDLE → CONNECTING.
    → resolver: dns 조회 → [10.0.0.11, 10.0.0.12]
    → LB(round_robin): 두 백엔드에 Subchannel 생성
    → 각 서브채널 TCP+TLS+HTTP/2 핸드셰이크
    → 둘 다 성공: Subchannel READY → Channel READY
    → stream 1 열림, GetOrder 전송, 응답 수신. 끝.

t2  정상 트래픽: 수백 개 RPC가 두 연결로 멀티플렉싱.
    한 연결당 MAX_CONCURRENT_STREAMS(=100) 한도 내에서 인터리빙.

t3  백엔드 .11 파드가 죽음(배포):
    → 서버가 GOAWAY(last_stream_id) 전송
    → 진행 중 RPC는 마무리, 새 RPC는 .12 로
    → .11 소켓 끊김 → Subchannel(.11) READY → TRANSIENT_FAILURE
    → Channel 은 여전히 READY (.12 가 살아 있으므로)
    → .11 서브채널: 백오프 시작 (1s, 1.6s, 2.56s ... ±지터)

t4  새 .11 파드가 뜸, resolver 가 재해석으로 인지:
    → 백오프 타이머 만료 시 .11 Subchannel CONNECTING → READY
    → 다시 두 연결로 분산. (애플리케이션은 아무것도 안 했다!)

t5  앱 종료: channel.shutdown() / conn.Close()
    → 진행 중 RPC 마무리(graceful), 새 RPC 거부
    → 소켓 정리, Channel SHUTDOWN. 끝.
```

이 타임라인에서 애플리케이션 코드가 직접 한 일은 t0(채널 생성), t1~t2(RPC 호출), t5(종료)뿐이다. t3~t4의 장애 감지, 격리, 백오프, 재연결, 재해석은 **모두 채널이 스스로** 처리했다. 이것이 채널 추상화가 주는 이점이다. 동시에 8절에서 "채널을 요청마다 만들면 이 모든 자가 복구 메커니즘을 매번 버리게 된다"고 경고한 이유이기도 하다.

## 14. 흔한 오해와 함정 (FAQ)

**Q. 채널을 만들었는데 연결이 열리지 않아요. 버그인가요?**
A. 아니다. `grpc.NewClient`(및 최신 권장 경로)는 연결을 지연해서 연다. 채널은 IDLE로 시작하고, 첫 RPC가 오거나 `Connect()`를 호출할 때 연결한다. 부팅할 때 연결을 확인하려면 `Connect()`를 명시적으로 호출하고 상태 변화를 기다리거나, 헬스 체크 RPC를 한 번 보내면 된다.

**Q. `GetState()`가 TRANSIENT_FAILURE인데 RPC는 성공해요. 왜죠?**
A. 채널 상태는 서브채널 상태를 집계한 결과다. 일부 서브채널이 실패해도 READY인 서브채널이 있으면 RPC는 그쪽으로 간다. 또한 wait-for-ready RPC라면 잠깐의 TRANSIENT_FAILURE를 기다렸다가 성공할 수 있다.

**Q. 채널을 스레드마다 하나씩 만들어야 동시성이 좋아지지 않나요?**
A. 아니다. 채널은 thread-safe하고 연결 하나로 멀티플렉싱한다. 스레드마다 채널을 만들면 연결 수만 늘어나고 핸드셰이크 비용과 메모리만 낭비된다. 처리량이 실제로 `MAX_CONCURRENT_STREAMS`에 막힐 때만(3.3절) 정해진 소수의 채널 풀을 고려한다.

**Q. RPC가 `UNAVAILABLE`로 실패해요.**
A. 채널이 연결을 맺지 못했거나(TRANSIENT_FAILURE), GOAWAY나 연결 끊김 직후일 가능성이 크다. Fail Fast가 기본값이므로 이때는 즉시 `UNAVAILABLE`이 난다. 일시적 장애를 견디려면 wait-for-ready와 데드라인을 함께 쓰거나, retry 정책(13장 안정성)을 쓴다. 단, 멱등성을 반드시 확인해야 한다. 상태 코드의 의미는 [[09 - 에러 모델 - 상태 코드와 Rich Error]]에서 설명한다.

**Q. 데드라인 없이 wait-for-ready를 켜도 되나요?**
A. 위험하다. 채널이 끝내 READY가 되지 않으면 RPC도 영원히 기다린다. wait-for-ready는 항상 데드라인(10장 Deadline 취소 타임아웃)과 함께 써야 한다.

**Q. `Connect()`를 호출하면 연결이 보장되나요?**
A. 보장하지 않는다. `Connect()`는 연결 시도를 시작하게 하는 계기일 뿐이다. 채널을 IDLE에서 CONNECTING으로 전이시키기만 하고, 성공 여부는 핸드셰이크 결과에 달려 있다. 연결을 보장하려면 상태가 READY가 될 때까지 관찰해야 한다.
