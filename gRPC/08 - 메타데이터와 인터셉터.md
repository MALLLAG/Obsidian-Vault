## 1. 본문과 봉투: 메타데이터가 필요한 이유

편지를 부치는 상황을 생각해 보자. 편지지에 적힌 글은 **수신자가 읽을 내용**이다. 그런데 봉투 겉면에는 글의 내용과 관계없는 정보가 많이 붙는다. 우표, 우편번호, 등기 여부, 빠른등기 스티커, 발신 우체국 소인 같은 것들이다. 이런 정보는 편지의 *의미*가 아니라 편지를 *어떻게 처리할지*를 알려 준다. 우체국 직원은 봉투를 보고 분류하고 배송하며, 편지를 열어 읽은 뒤 처리 방식을 정하지 않는다.

gRPC에서 **메시지 본문(message body)** 은 편지지에 해당하고, **메타데이터(metadata)** 는 봉투 겉면에 해당한다. 본문에는 [[02 - Protocol Buffers 1 - 문법과 타입 시스템]]에서 정의한 protobuf 메시지가 [[03 - Protocol Buffers 2 - 인코딩과 와이어 포맷]]의 규칙에 따라 직렬화되어 들어간다. 본문은 비즈니스 로직이 읽고 처리하는 "내용"이다.

반면 메타데이터는 그 RPC를 *어떻게* 처리할지에 대한 부가 정보이다. 누가 호출했는지(인증 토큰), 이 요청을 추적하는 ID가 무엇인지(trace ID), 클라이언트가 어떤 압축을 쓰는지, 응답을 얼마나 기다릴 것인지 같은 정보가 여기에 들어간다.

```text
┌─────────────────────────────────────────────┐
│  하나의 RPC 호출                              │
│                                              │
│  ┌────────────────┐   ┌──────────────────┐  │
│  │  메타데이터     │   │  메시지 본문      │  │
│  │  (봉투의 우표)  │   │  (편지지)         │  │
│  │                │   │                  │  │
│  │  authorization │   │  GetOrderRequest │  │
│  │  x-request-id  │   │  { order_id: 42 }│  │
│  │  trace-parent  │   │                  │  │
│  └────────────────┘   └──────────────────┘  │
│   HTTP/2 HEADERS        HTTP/2 DATA 프레임   │
│   /TRAILERS 프레임                           │
└─────────────────────────────────────────────┘
```

이렇게 나누는 것은 보기 좋게 하려는 것이 아니라 **관심사의 분리(separation of concerns)** 라는 설계 결정이다. 인증 토큰이나 trace ID를 메시지 본문(protobuf 필드)에 넣는다면 어떻게 될까? 모든 `proto` 메시지에 `string auth_token = 99;` 같은 필드를 반복해서 넣어야 하고, 인증 미들웨어는 본문을 역직렬화해야만 토큰을 꺼낼 수 있다. 결국 미들웨어가 비즈니스 타입에 의존하게 된다.

메타데이터로 분리하면 인증 인터셉터는 본문을 *전혀 건드리지 않고도* 봉투의 우표만 보고 통과시킬지 거부할지를 결정할 수 있다. 우체국 직원이 편지를 뜯지 않고 봉투만 보고 분류하는 것과 같다.

> [!note] 핵심 직관
> **본문은 "무엇을 요청하는가"를, 메타데이터는 "이 요청을 어떻게 다룰 것인가"를 담는다.** 둘을 섞으면 미들웨어가 비즈니스 로직에 결합된다.

## 2. 메타데이터의 물리적 실체: HTTP/2 HEADERS와 TRAILERS

gRPC는 추상적인 개념에 머물지 않고, [[04 - HTTP2 깊이 보기 - 전송 계층]]에서 다룬 HTTP/2 위에 구체적으로 매핑된다. 메타데이터가 실제로 무엇인지 이해하려면 unary RPC 한 번이 HTTP/2 프레임으로 어떻게 전개되는지를 봐야 한다.

RPC 하나는 HTTP/2 **스트림(stream)** 하나에 대응한다. 그 스트림 안에서 프레임은 다음 순서로 오간다.

```text
시간 →

클라이언트                                서버
   │                                       │
   │── HEADERS (요청 헤더 = 요청 메타데이터)─→│   ┐
   │   :method POST, :path /pkg.Svc/Method  │   │ leading
   │   content-type application/grpc        │   │ (요청)
   │   authorization Bearer ...             │   ┘
   │── DATA (길이-접두 protobuf 메시지)─────→│
   │   END_STREAM (요청 끝)                  │
   │                                       │
   │                                       │ 서버 처리...
   │                                       │
   │←─ HEADERS (응답 초기 헤더 = leading)────│   ┐ leading
   │   :status 200                          │   │ (응답)
   │   content-type application/grpc        │   ┘
   │←─ DATA (길이-접두 protobuf 응답)────────│
   │                                       │
   │←─ HEADERS (응답 종료 = TRAILERS)────────│   ┐ trailing
   │   grpc-status 0                        │   │ (응답)
   │   grpc-message ...                     │   │
   │   END_STREAM (응답 끝)                  │   ┘
   │                                       │
```

여기서 메타데이터가 실리는 자리는 세 곳이다.

| 자리 | HTTP/2 프레임 | gRPC 용어 | 방향 | 담는 것 |
|------|--------------|-----------|------|---------|
| 요청 헤더 | HEADERS (스트림 시작) | request metadata (leading) | client → server | 인증 토큰, request-id, trace-parent, 압축 알고리즘 |
| 응답 초기 헤더 | HEADERS (응답 DATA 전) | response header / leading | server → client | 서버 측 부가 정보, 일부 트레이싱 응답 |
| 응답 종료 | HEADERS (END_STREAM) | trailer / trailing | server → client | `grpc-status`, `grpc-message`, 처리 통계 |

가장 중요한 점은 **gRPC가 응답의 최종 상태(status)를 본문이 아니라 trailer에 넣는다**는 것이다. HTTP/1의 `200 OK`는 응답을 *시작할 때* 정해진다. 그런데 서버가 응답 메시지를 절반쯤 스트리밍한 뒤에 에러가 났다면 어떻게 될까? HTTP/1에서는 이미 200을 보내 버렸기 때문에 나중에 "사실은 실패했다"고 알릴 자리가 없다.

HTTP/2의 **트레일러(trailing headers)** 가 바로 이 문제를 해결한다. 응답 데이터를 모두 보낸 *뒤에* `grpc-status: 0`(성공)이나 `grpc-status: 13`(내부 오류)을 붙일 수 있다. 그래서 gRPC의 실제 결과 코드는 HTTP의 `:status`가 아니라 **trailer의 `grpc-status`** 이다. 이 메커니즘은 [[09 - 에러 모델 - 상태 코드와 Rich Error]]에서 자세히 다룬다.

gRPC가 HTTP/1이 아니라 HTTP/2를 요구하는 결정적인 이유 중 하나가 이것이다. HTTP/1.1에도 chunked transfer의 trailer가 명세상 존재하지만, 실제 프록시와 브라우저의 지원이 매우 부족하다. 반면 HTTP/2는 trailer를 1급 시민으로 다룬다.

### 2.1 HPACK: 헤더가 실제로 전송되는 바이트

HTTP/2의 HEADERS 프레임은 헤더 이름과 값을 평문으로 보내지 않고, **HPACK(RFC 7541)** 이라는 헤더 압축을 거친다. HPACK은 두 가지 방법을 쓴다.

1. **정적 테이블(static table)**: `:method GET`, `:status 200`처럼 자주 쓰는 헤더에는 미리 번호가 매겨져 있다(RFC 7541 부록 A의 61개 엔트리). 예를 들어 `:method GET`은 인덱스 2, `:method POST`는 인덱스 3, `:status 200`은 인덱스 8이다. gRPC는 항상 `POST`를 쓰므로 메서드 줄은 인덱스 3 하나(1바이트)로 줄어든다.
2. **동적 테이블(dynamic table)**: 같은 연결에서 한 번 보낸 헤더(예: `authorization: Bearer eyJ...`)는 동적 테이블에 등록된다. 그래서 다음 요청부터는 긴 토큰 문자열 대신 인덱스 번호만 보내면 된다.

직접 디코딩해 보자. 클라이언트가 `te: trailers` 헤더를 보낸다고 하자. HPACK은 이때 "리터럴 헤더 필드 + 증분 인덱싱(literal header field with incremental indexing)" 표현을 쓴다. `te` 헤더의 바이트열은 다음과 같다.

```text
바이트:  40 02 74 65 08 74 72 61 69 6c 65 72 73
         │  │  └─┬─┘ │  └────────┬──────────┘
         │  │   "te" │       "trailers"
         │  │        │
         │  │        └ 값 길이 = 0x08 = 8
         │  └ 이름 길이 = 0x02 = 2
         └ 0x40 = 0b0100_0000
           = "Literal Header Field with Incremental Indexing,
              new name" 패턴 (상위 2비트 01, 인덱스 0)
```

- `0x40`: 상위 2비트가 `01`이면 "증분 인덱싱하는 리터럴"이고, 하위 6비트가 `000000`(=0)이면 "이름도 리터럴로 뒤따른다"는 뜻이다.
- `0x02`: 이름 길이 2 (HPACK 정수이며, 최상위 비트가 0이면 Huffman을 사용하지 않는다).
- `74 65`: ASCII `t`(0x74) `e`(0x65) = `"te"`.
- `0x08`: 값 길이 8.
- `74 72 61 69 6c 65 72 73`: ASCII `trailers`.

즉 이 13바이트가 그대로 `te: trailers`이다. 그런데 같은 연결에서 두 번째 요청부터는 이 헤더가 동적 테이블에 들어 있으므로 1~2바이트(인덱스 참조)로 줄어든다. **메타데이터를 작고 반복적으로 유지해야 하는 이유**가 여기에 있다(9.3절에서 다시 다룬다).

### 2.2 ASCII 값과 바이너리 값, `-bin` 접미사

HTTP/2 헤더 값은 원칙적으로 텍스트(특정 바이트 범위의 octet)를 담는다. 그런데 gRPC 메타데이터로는 바이너리 데이터(예: 직렬화된 protobuf, 원본 토큰 바이트, 압축된 trace context)도 보내고 싶을 때가 있다. HPACK과 HTTP/2 헤더는 NUL이나 개행 같은 임의의 바이트를 안전하게 다룬다고 보장하지 않는다.

gRPC의 해법은 명료하다. **키 이름이 `-bin`으로 끝나면 그 값은 바이너리이며, 와이어에서는 base64로 인코딩된다.** 이 처리는 gRPC 라이브러리가 자동으로 한다.

```text
애플리케이션 코드:    md.set("trace-ctx-bin", []byte{0x01, 0xFF, 0x00, 0x7E})
와이어 위(HEADERS):  trace-ctx-bin: Af8Afg          (base64, 자동)
받는 쪽:            md.get("trace-ctx-bin") → []byte{0x01, 0xFF, 0x00, 0x7E}
```

- `{0x01, 0xFF, 0x00, 0x7E}`를 base64로 바꾸는 과정은 다음과 같다. 바이트 `01 FF 00 7E` → 비트열 `0000_0001 1111_1111 0000_0000 0111_1110` → 6비트씩 끊으면 `000000 011111 111100 000000 011111 10`(마지막 2비트는 0으로 채워 `100000`) → 인덱스 `0, 31, 60, 0, 31, 32` → base64 알파벳에서 `A f 8 A f g` → `Af8Afg`.
- gRPC는 `-bin` 헤더를 **패딩 없는(unpadded) base64**로 와이어에 싣는다(Go는 `base64.RawStdEncoding`). 표준 패딩을 붙이면 `Af8Afg==`가 되지만, 와이어 스펙상 보내는 쪽은 패딩을 생략하고, 받는 쪽은 패딩이 있든 없든 모두 받아들여야 한다.
- 받는 쪽 라이브러리는 키가 `-bin`으로 끝나므로 값을 base64로 디코딩해 원래 바이트를 복원한다.

규칙을 표로 정리하면 다음과 같다.

| 규칙                 | 내용                                | 이유                                                                    |
| ------------------ | --------------------------------- | --------------------------------------------------------------------- |
| 키는 소문자 ASCII       | `Content-Type` 아님, `content-type` | HTTP/2는 헤더 이름이 소문자여야 한다(대문자는 프로토콜 오류). 라이브러리가 소문자로 바꿔 주지만 처음부터 소문자로 다루는 편이 안전하다 |
| 키 문자 집합            | `[a-z0-9-_.]`                     | HTTP 토큰 규칙 + gRPC 관례. 공백·콜론 등 금지                                      |
| `-bin` 접미사         | 값이 바이너리, base64 자동 인·디코딩          | 임의의 바이트를 헤더에 안전하게 싣기 위해                                                      |
| 같은 키 다중 값          | 허용(콤마 결합 또는 복수 엔트리)               | HTTP 헤더의 다중 값 의미와 동일                                                  |
| 값은 ASCII(비 `-bin`) | 출력 가능 ASCII 권장                    | HPACK 안전성                                                             |

`-bin`이 아닌 일반 키에 멀티바이트 문자(한글 등)나 제어 문자를 넣으면 라이브러리나 프록시에 따라 깨지거나 거부된다. 사람이 읽는 라벨이라도 ASCII로 두고, 실제 바이너리는 `-bin` 키를 써야 한다.

### 2.3 예약된 헤더: 건드리면 안 되는 영역

gRPC 와이어 프로토콜은 일부 헤더를 **직접 관리**한다. 애플리케이션이 메타데이터로 같은 이름을 설정하려 하면 라이브러리가 무시하거나 에러를 낸다. 이런 헤더는 "시스템 봉투" 영역이므로 사용자가 손대면 안 된다.

| 예약 헤더 | 누가 정함 | 의미 |
|-----------|----------|------|
| `:method` | HTTP/2 의사 헤더 | 항상 `POST` |
| `:path` | gRPC | `/{package}.{Service}/{Method}` |
| `:authority` | 전송 계층 | 대상 호스트(authority). [[07 - 채널 스텁 커넥션 생명주기]] |
| `:scheme` | 전송 계층 | `http`/`https` |
| `content-type` | gRPC | `application/grpc`(+`+proto`/`+json`) |
| `te` | gRPC | `trailers` (trailer 사용 협상) |
| `grpc-timeout` | gRPC | Deadline 전파. [[10 - Deadline 취소 타임아웃]] |
| `grpc-encoding` | gRPC | 메시지 압축 알고리즘(gzip 등) |
| `grpc-accept-encoding` | gRPC | 받을 수 있는 압축 |
| `grpc-status` | gRPC (trailer) | 최종 상태 코드. 9장(에러 모델) |
| `grpc-message` | gRPC (trailer) | 상태 메시지(퍼센트 인코딩) |
| `user-agent` | gRPC | 클라이언트 식별 |

규칙은 이렇다. **콜론(`:`)으로 시작하는 의사 헤더와 `grpc-`로 시작하는 헤더는 예약어이다.** 사용자 정의 메타데이터는 이 접두사를 피해야 하며, 관례적으로 `x-` 접두사(예: `x-request-id`)나 표준화된 이름(`traceparent`, `authorization`)을 쓴다. `grpc-`로 시작하는 키를 설정하려 하면 대부분의 구현이 조용히 버리거나 거부한다.

`grpc-timeout`은 메타데이터처럼 보이지만 사용자가 직접 다루지 않는다는 점이 중요하다. Deadline은 별도의 1급 개념이며, 컨텍스트나 CallOption으로 설정하면 라이브러리가 `grpc-timeout: 30S` 같은 형태로 자동 변환한다. 자세한 인코딩 방식(`100m`, `30S`, `1H` 등의 단위)은 10장(Deadline 취소 타임아웃)에서 다룬다.

## 3. Leading과 Trailing: 언제 무엇을 보낼 수 있는가

스트리밍을 이해하면 메타데이터를 보내는 "타이밍"도 자연스럽게 이해된다. 핵심 제약은 HTTP/2의 동작 방식에서 나온다. **HEADERS는 DATA보다 먼저 가야 하고, TRAILERS는 모든 DATA 뒤에 가야 한다.** 헤더를 한 번 내보내면(flush) 되돌릴 수 없다.

```text
서버가 응답에서 메타데이터를 보낼 수 있는 두 창(window):

   [응답 시작]                              [응답 끝]
       │                                       │
       ▼                                       ▼
   ┌───────┐  ┌──────┐ ┌──────┐ ┌──────┐  ┌────────┐
   │HEADERS│→ │ DATA │ │ DATA │ │ DATA │ →│TRAILERS│
   │leading│  │msg 1 │ │msg 2 │ │msg 3 │  │trailing│
   └───────┘  └──────┘ └──────┘ └──────┘  └────────┘
       ▲                                       ▲
   여기서 SetHeader/SendHeader               여기서 SetTrailer
   가능. 첫 메시지 전에만!                    응답 종료 직전.
```

서버 쪽 규칙을 정리하면 다음과 같다.

- **Leading metadata(응답 초기 헤더)**: 서버는 **첫 응답 메시지를 보내기 전**에만 leading 헤더를 보낼 수 있다. 첫 `DATA` 프레임이 나가는 순간 HEADERS는 이미 flush되었으므로, 그 뒤에 leading을 추가하려 하면 무시되거나 에러가 난다. Go에서 `grpc.SetHeader(ctx, md)`는 값을 누적하고, `grpc.SendHeader(ctx, md)`는 즉시 flush한다. `SendHeader`를 한 번 호출하거나 첫 메시지를 전송하면 leading은 고정된다.
- **Trailing metadata(트레일러)**: 응답이 끝날 때 항상 전송된다. 서버 핸들러가 정상적으로 반환하든 에러를 반환하든, 라이브러리가 `grpc-status`와 함께 trailer를 flush한다. 사용자가 `grpc.SetTrailer(ctx, md)`로 추가한 항목도 함께 실린다. **에러가 나도 trailer는 전송된다**는 점이 중요하다. 따라서 실패 사유를 trailer에 실어 보낼 수 있다.

클라이언트 쪽 규칙은 다음과 같다.

- **Request metadata(leading)**: 클라이언트는 요청을 *시작할 때* 메타데이터를 컨텍스트나 CallOption에 실어 보낸다. 이 메타데이터는 요청 HEADERS 프레임에 들어간다. 양방향 스트리밍이나 클라이언트 스트리밍이라도 요청 메타데이터는 첫 메시지 전에 고정된다(스트림 헤더는 한 번만 보낸다).
- 클라이언트는 응답의 leading 헤더와 trailer를 따로 받을 수 있다. Go에서는 `grpc.Header(&headerMD)`, `grpc.Trailer(&trailerMD)` CallOption에 포인터를 넘겨서 받는다.

### 3.1 스트리밍에서의 실제 타이밍

server-streaming을 예로 들어 보자. 서버가 헤더로 "총 몇 건이 올지"를 미리 알려 주고, 마지막에 "실제로 몇 건을 보냈는지"를 trailer로 정정한다고 하자.

```go
func (s *server) ListOrders(req *pb.ListOrdersRequest, stream pb.OrderService_ListOrdersServer) error {
    // leading: 첫 메시지 전에 보내야 한다.
    header := metadata.Pairs("x-estimated-count", "100")
    if err := stream.SendHeader(header); err != nil { // 즉시 flush
        return err
    }

    sent := 0
    for _, o := range s.queryOrders(req) {
        if err := stream.Send(toProto(o)); err != nil { // 이제 DATA가 흐른다
            return err
        }
        sent++
    }

    // trailing: 모든 메시지 후, 반환 직전. SetTrailer는 누적.
    stream.SetTrailer(metadata.Pairs("x-actual-count", fmt.Sprint(sent)))
    return nil
}
```

이 코드의 순서를 어기면, 예를 들어 `stream.Send` 뒤에 `SendHeader`를 호출하면, leading은 이미 전송되었으므로 아무 효과가 없다. 헤더는 흐르는 강물과 같아서 한 번 흘러가면 거슬러 올라갈 수 없다고 기억해 두자.

[[05 - 통신의 4가지 방식 - Unary와 Streaming]]에서 본 네 가지 호출 형태별로 메타데이터를 보낼 수 있는 창을 정리하면 다음과 같다.

| 호출 형태 | 요청 leading | 응답 leading | 응답 trailing |
|-----------|-------------|-------------|--------------|
| Unary | 요청 헤더 1회 | 응답 헤더(본문 전) | 본문 후, 상태와 함께 |
| Server streaming | 요청 헤더 1회 | 첫 응답 메시지 전 | 스트림 끝 |
| Client streaming | 요청 헤더 1회(첫 메시지 전) | 단일 응답 전 | 응답 후 |
| Bidi streaming | 요청 헤더 1회(첫 메시지 전) | 첫 응답 메시지 전 | 스트림 끝 |

모든 형태에 공통된 점은 **메타데이터(헤더와 트레일러)가 메시지 흐름의 양 끝에만 붙는다**는 것이다. 메시지 사이사이에 끼워 넣을 수는 없다. 메시지 단위로 부가 정보를 보내야 한다면 메타데이터가 아니라 본문 메시지의 필드(예: oneof로 데이터 이벤트와 메타 이벤트를 구분)로 모델링해야 한다.

## 4. 컨텍스트 전파: 메타데이터가 전달하는 정보

메타데이터가 가장 실용적으로 쓰이는 곳은 **분산 컨텍스트 전파(distributed context propagation)** 이다. 마이크로서비스 환경에서는 사용자 요청 하나가 여러 서비스를 거쳐 처리된다. 누가 호출했는지, 이 요청의 추적 ID가 무엇인지, 어느 테넌트의 요청인지처럼 그 흐름 전체에 걸친 정보를 서비스 경계 너머로 전달하는 통로가 메타데이터이다.

```text
   사용자
     │  HTTP: Authorization, traceparent
     ▼
┌──────────┐  gRPC metadata:           ┌──────────┐  gRPC metadata:   ┌──────────┐
│ API GW   │─ authorization ──────────→│ Order    │─ traceparent ────→│ Inventory│
│          │  x-request-id: abc123     │ Service  │  x-request-id     │ Service  │
│          │  traceparent: 00-...      │          │  (그대로 전파)     │          │
└──────────┘                           └──────────┘                   └──────────┘
```

메타데이터로 전달하는 대표적인 정보는 다음과 같다.

1. **인증/인가 토큰**: `authorization: Bearer eyJhbGci...`. OAuth2나 JWT 토큰을 표준 `authorization` 헤더에 싣고, 서버 인터셉터가 검증한다(7.1절).
2. **요청 ID / 상관 ID**: `x-request-id: 7f3a...`. 사용자 요청 하나에 부여한 고유 ID이다. 모든 로그에 이 ID를 함께 남기면 여러 서비스의 로그를 하나의 흐름으로 이어 볼 수 있다.
3. **분산 트레이싱 컨텍스트**: W3C Trace Context의 `traceparent`/`tracestate`, 또는 B3(`x-b3-traceid` 등). OpenTelemetry가 이 헤더들을 메타데이터에 주입하거나 메타데이터에서 추출해 스팬(span)을 연결한다(7.4절).
4. **테넌트/로캘/기능 플래그**: `x-tenant-id`, `accept-language`, `x-feature-flags`. 멀티테넌시, 국제화, 실험에 필요한 컨텍스트이다.

여기서 자주 헷갈리는 점이 하나 있다. **Deadline은 메타데이터로 직접 전파하지 않는다.** Deadline은 1급 개념이므로 라이브러리가 남은 시간을 계산해 `grpc-timeout` 헤더로 자동 변환하고 전파한다.

서비스 A가 30초 deadline으로 호출을 받은 뒤 B를 호출하면, A에 남은 시간(예: 28초)이 B로 전파된다. 이 "deadline 전파"는 *내부적으로* 메타데이터 메커니즘을 쓰지만, 사용자는 컨텍스트만 넘기면 된다. 자세한 내용은 10장(Deadline 취소 타임아웃)에서 다룬다.

W3C `traceparent`의 형식을 직접 뜯어보면 메타데이터로 얼마나 압축적으로 정보를 전달하는지 알 수 있다.

```text
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └──────────────┬───────────────┘ └───────┬──────┘ │
           버전              trace-id (16바이트)      span-id (8B)  flags
           (00)            전체 요청을 식별          현재 구간     (01=sampled)
```

`Order Service`의 트레이싱 인터셉터는 들어온 요청 메타데이터에서 `traceparent`를 **추출(extract)** 해 부모 스팬을 복원하고, 자신의 작업을 새 자식 스팬으로 만든다. 그리고 `Inventory Service`를 호출할 때 새 `span-id`를 담은 `traceparent`를 메타데이터에 **주입(inject)** 한다. 모든 서비스가 이 추출과 주입을 반복하면 분산된 호출이 하나의 트레이스 트리로 합쳐진다.

이 추출과 주입을 *자동으로* 해 주는 것이 바로 인터셉터이다. 다음 절부터 인터셉터를 살펴본다.

## 5. 인터셉터란 무엇인가: RPC를 감싸는 미들웨어

웹 프레임워크의 미들웨어를 써 봤다면 인터셉터도 익숙할 것이다. 미들웨어는 요청이 핸들러에 도달하기 *전*과 응답이 나간 *뒤*에 끼어들어 공통 처리를 하는 함수이다. gRPC 인터셉터(interceptor)가 정확히 이런 역할을 한다. 즉 인터셉터는 **RPC 호출 경로를 양파 껍질처럼 감싸는 함수**이다.

```text
        바깥                                           안
   ┌─────────────────────────────────────────────────────┐
   │ 인터셉터 A (로깅)                                     │
   │  ┌───────────────────────────────────────────────┐  │
   │  │ 인터셉터 B (인증)                              │  │
   │  │  ┌─────────────────────────────────────────┐  │  │
   │  │  │ 인터셉터 C (메트릭)                     │  │  │
   │  │  │  ┌───────────────────────────────────┐  │  │  │
   │  │  │  │  실제 핸들러 (비즈니스 로직)       │  │  │  │
   │  │  │  │  GetOrder(req) → resp             │  │  │  │
   │  │  │  └───────────────────────────────────┘  │  │  │
   │  │  └─────────────────────────────────────────┘  │  │
   │  └───────────────────────────────────────────────┘  │
   └─────────────────────────────────────────────────────┘

   호출:  A 진입 → B 진입 → C 진입 → 핸들러 → C 복귀 → B 복귀 → A 복귀
```

각 인터셉터는 두 가지를 할 수 있다.

1. **다음 단계를 호출하기 전후에 코드를 넣는다.** 호출 전에는 토큰을 검증하거나 타이머를 시작하거나 트레이스 스팬을 시작한다. 호출 후에는 응답을 로깅하거나 메트릭을 기록하거나 스팬을 종료한다.
2. **다음 단계를 호출할지, 무엇을 넘길지 결정한다.** 인증에 실패하면 다음 단계를 *호출하지 않고* 즉시 에러를 반환한다(short-circuit). 컨텍스트를 변형해서(예: 요청 ID 주입) 다음 단계에 넘기기도 한다.

이 구조의 가치는 **횡단 관심사(cross-cutting concerns)의 분리**에 있다. 인증, 로깅, 트레이싱은 모든 RPC에 공통으로 필요하지만 어느 비즈니스 로직에도 속하지 않는다. 이런 코드를 핸들러마다 복사해 붙여 넣으면 유지보수가 불가능해진다. 인터셉터로 한 번 작성해 모든 RPC에 일괄 적용하면 핸들러에는 순수한 비즈니스 로직만 남는다.

### 5.1 네 종류의 인터셉터

gRPC는 **양쪽(client/server) × 두 형태(unary/stream) = 4종**의 인터셉터를 정의한다. unary와 stream을 나누는 이유는 두 형태의 시그니처가 근본적으로 다르기 때문이다. unary는 "요청 1개 → 응답 1개"이므로 입력과 출력을 직접 다룰 수 있다. 반면 stream은 메시지 여러 개가 시간에 걸쳐 오가므로 "스트림 객체"를 감싸야 한다.

| 종류 | 위치 | 감싸는 대상 | 메시지 후킹 |
|------|------|------------|------------|
| Unary client | 클라이언트 | 단일 요청/응답 호출 | req/resp 직접 |
| Stream client | 클라이언트 | ClientStream 생성 | 스트림 wrap |
| Unary server | 서버 | 단일 핸들러 호출 | req/resp 직접 |
| Stream server | 서버 | ServerStream 핸들러 | 스트림 wrap |

```text
                  클라이언트 측                    서버 측
              ┌──────────────────┐          ┌──────────────────┐
   Unary      │ UnaryClient      │          │ UnaryServer      │
              │ Interceptor      │  ──RPC──→ │ Interceptor      │
              │ (req,resp 직접)  │          │ (req,resp 직접)  │
              └──────────────────┘          └──────────────────┘
              ┌──────────────────┐          ┌──────────────────┐
   Stream     │ StreamClient     │          │ StreamServer     │
              │ Interceptor      │  ──RPC──→ │ Interceptor      │
              │ (ClientStream    │          │ (ServerStream    │
              │  wrap)           │          │  wrap)           │
              └──────────────────┘          └──────────────────┘
```

## 6. 언어별 인터셉터의 형태

추상적인 개념은 구체적인 시그니처로 확인해야 제대로 이해할 수 있다. Go, Java, Python 순서로 살펴본다.

### 6.1 Go: 함수형 인터셉터

Go의 인터셉터는 함수이다. 핵심은 `handler`(서버)나 `invoker`(클라이언트)라는 **"다음 단계"를 인자로 받아, 그것을 호출하기 전후에 코드를 넣는** 패턴이다.

```go
// 서버 unary 인터셉터의 시그니처
type UnaryServerInterceptor func(
    ctx context.Context,
    req any,
    info *UnaryServerInfo,    // FullMethod 이름 등 호출 정보
    handler UnaryHandler,     // "다음 단계" = 실제 핸들러(또는 다음 인터셉터)
) (resp any, err error)

// 서버 stream 인터셉터의 시그니처
type StreamServerInterceptor func(
    srv any,
    ss ServerStream,          // 감쌀 스트림
    info *StreamServerInfo,
    handler StreamHandler,    // "다음 단계"
) error
```

가장 단순한 로깅 인터셉터는 다음과 같다.

```go
func LoggingUnaryServer(
    ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler,
) (any, error) {
    start := time.Now()

    // ── 호출 전 (요청이 핸들러에 닿기 전) ──
    log.Printf("→ %s 시작", info.FullMethod)

    // ── 다음 단계 호출 (핵심!) ──
    resp, err := handler(ctx, req)

    // ── 호출 후 (응답이 나가기 전) ──
    code := status.Code(err)
    log.Printf("← %s 완료 code=%s dur=%s", info.FullMethod, code, time.Since(start))

    return resp, err
}
```

서버에는 다음과 같이 등록한다.

```go
srv := grpc.NewServer(
    grpc.ChainUnaryInterceptor(   // 여러 개를 바깥→안 순서로
        TracingUnaryServer,       // 가장 바깥
        LoggingUnaryServer,
        AuthUnaryServer,
        RecoveryUnaryServer,      // 가장 안 (핸들러에 가장 가까움)
    ),
    grpc.ChainStreamInterceptor(
        TracingStreamServer,
        LoggingStreamServer,
        AuthStreamServer,
    ),
)
```

클라이언트 측도 같은 구조이다.

```go
type UnaryClientInterceptor func(
    ctx context.Context,
    method string,
    req, reply any,
    cc *ClientConn,
    invoker UnaryInvoker,         // "다음 단계" = 실제 전송
    opts ...CallOption,
) error

func RequestIDUnaryClient(
    ctx context.Context, method string, req, reply any,
    cc *grpc.ClientConn, invoker grpc.UnaryInvoker, opts ...grpc.CallOption,
) error {
    // 컨텍스트에 메타데이터를 실어 다음으로 넘긴다.
    reqID := uuid.NewString()
    ctx = metadata.AppendToOutgoingContext(ctx, "x-request-id", reqID)
    return invoker(ctx, method, req, reply, cc, opts...) // 다음 단계
}

conn, _ := grpc.NewClient(target,
    grpc.WithChainUnaryInterceptor(RequestIDUnaryClient, RetryUnaryClient),
)
```

### 6.2 Go에서 stream 인터셉터로 메시지 단위 후킹

stream에서는 메시지가 여러 개 오가므로, stream 인터셉터는 `ServerStream`/`ClientStream`을 **래핑(wrap)** 해서 `SendMsg`/`RecvMsg`를 가로채야 한다. 이 점이 unary와 결정적으로 다르다.

```go
// ServerStream을 감싸 메시지마다 후킹
type wrappedServerStream struct {
    grpc.ServerStream
    onRecv func(any)
    onSend func(any)
}

func (w *wrappedServerStream) RecvMsg(m any) error {
    err := w.ServerStream.RecvMsg(m) // 실제 수신
    if err == nil {
        w.onRecv(m)                  // 메시지 1개마다 후킹
    }
    return err
}

func (w *wrappedServerStream) SendMsg(m any) error {
    w.onSend(m)
    return w.ServerStream.SendMsg(m)
}

func CountingStreamServer(
    srv any, ss grpc.ServerStream,
    info *grpc.StreamServerInfo, handler grpc.StreamHandler,
) error {
    var in, out int
    wrapped := &wrappedServerStream{
        ServerStream: ss,
        onRecv: func(any) { in++ },
        onSend: func(any) { out++ },
    }
    err := handler(srv, wrapped) // 래핑한 스트림을 핸들러에 넘김
    log.Printf("%s in=%d out=%d", info.FullMethod, in, out)
    return err
}
```

여기서 **비용**에 주목해야 한다. stream 인터셉터로 메시지마다 후킹하면, 초당 수천 건의 메시지가 오가는 스트림에서 메시지마다 함수 호출, 클로저, 로깅이 끼어든다. unary 인터셉터는 호출당 한 번 실행되지만, stream의 메시지 후킹은 메시지당 한 번 실행된다(9.2절에서 다시 다룬다).

### 6.3 Java: 인터페이스 기반 인터셉터

Java에서는 함수 대신 인터페이스를 구현한다. 메타데이터를 다루는 `Metadata` 클래스와 컨텍스트를 다루는 `Context` 클래스가 명시적으로 등장한다.

```java
// 서버 인터셉터
public class AuthServerInterceptor implements ServerInterceptor {
    static final Metadata.Key<String> AUTH_KEY =
        Metadata.Key.of("authorization", Metadata.ASCII_STRING_MARSHALLER);
    static final Context.Key<String> USER_CTX = Context.key("userId");

    @Override
    public <ReqT, RespT> ServerCall.Listener<ReqT> interceptCall(
            ServerCall<ReqT, RespT> call,
            Metadata headers,                 // 들어온 요청 메타데이터
            ServerCallHandler<ReqT, RespT> next) {

        String token = headers.get(AUTH_KEY); // 봉투에서 토큰 꺼내기
        String userId = verify(token);
        if (userId == null) {
            call.close(Status.UNAUTHENTICATED.withDescription("토큰 없음/무효"),
                       new Metadata());
            return new ServerCall.Listener<ReqT>() {}; // no-op 리스너, 핸들러 미호출
        }
        // 검증된 userId를 Context에 실어 다음으로
        Context ctx = Context.current().withValue(USER_CTX, userId);
        return Contexts.interceptCall(ctx, call, headers, next);
    }
}
```

바이너리 메타데이터를 다룰 때는 `Metadata.Key.of("trace-bin", Metadata.BINARY_BYTE_MARSHALLER)`처럼 키 마샬러를 바꾼다. 이때 키 이름은 `-bin`으로 끝나야 한다.

클라이언트 측에서는 `ClientInterceptor`를 구현하고, `ForwardingClientCall`로 호출을 감싸서 메타데이터를 주입한다.

```java
public class RequestIdClientInterceptor implements ClientInterceptor {
    static final Metadata.Key<String> REQ_ID =
        Metadata.Key.of("x-request-id", Metadata.ASCII_STRING_MARSHALLER);

    @Override
    public <ReqT, RespT> ClientCall<ReqT, RespT> interceptCall(
            MethodDescriptor<ReqT, RespT> method, CallOptions opts, Channel next) {
        return new SimpleForwardingClientCall<ReqT, RespT>(
                next.newCall(method, opts)) {
            @Override
            public void start(Listener<RespT> responseListener, Metadata headers) {
                headers.put(REQ_ID, UUID.randomUUID().toString()); // 봉투에 우표 붙이기
                super.start(responseListener, headers);
            }
        };
    }
}
```

Java에서 stream을 후킹할 때는 `ForwardingServerCallListener`/`ForwardingClientCall`로 `onMessage`/`sendMessage`를 오버라이드한다. 개념은 Go의 wrappedStream과 같다.

### 6.4 Python: 추상 클래스 인터셉터

Python(`grpcio`)도 인터셉터를 제공한다. 서버는 `grpc.ServerInterceptor`를, 클라이언트는 `grpc.UnaryUnaryClientInterceptor` 같은 호출 형태별 클래스를 구현한다.

```python
import grpc, uuid

class RequestIdClientInterceptor(grpc.UnaryUnaryClientInterceptor):
    def intercept_unary_unary(self, continuation, client_call_details, request):
        # 기존 메타데이터에 우표를 덧붙인다 (튜플 리스트)
        md = list(client_call_details.metadata or [])
        md.append(("x-request-id", str(uuid.uuid4())))
        new_details = client_call_details._replace(metadata=md)
        return continuation(new_details, request)  # 다음 단계

channel = grpc.intercept_channel(
    grpc.insecure_channel("localhost:50051"),
    RequestIdClientInterceptor(),
)
```

서버 측은 다음과 같다.

```python
class AuthServerInterceptor(grpc.ServerInterceptor):
    def intercept_service(self, continuation, handler_call_details):
        md = dict(handler_call_details.invocation_metadata)
        token = md.get("authorization", "")
        if not verify(token):
            def deny(request, context):
                context.abort(grpc.StatusCode.UNAUTHENTICATED, "토큰 무효")
            return grpc.unary_unary_rpc_method_handler(deny)
        return continuation(handler_call_details)  # 통과
```

세 언어에 공통된 골격은 다음과 같다.

```text
1. "다음 단계"를 인자로 받는다 (handler / invoker / continuation / next)
2. 다음 단계 호출 전: 메타데이터/컨텍스트를 읽거나 쓴다
3. 다음 단계를 호출한다 (또는 호출하지 않고 short-circuit)
4. 다음 단계 호출 후: 결과를 가공/관찰한다
```

## 7. 대표 활용: 인터셉터로 무엇을 하는가

### 7.1 인증/인가 (서버 인터셉터)

가장 흔한 용도이다. 모든 RPC에 대해 핸들러에 도달하기 전에 토큰을 검증하고, 검증에 실패하면 핸들러를 *호출하지 않고* `UNAUTHENTICATED`/`PERMISSION_DENIED`로 차단한다.

```go
func AuthUnaryServer(
    ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler,
) (any, error) {
    // 공개 메서드는 통과 (예: 헬스체크)
    if info.FullMethod == "/grpc.health.v1.Health/Check" {
        return handler(ctx, req)
    }
    md, ok := metadata.FromIncomingContext(ctx)
    if !ok {
        return nil, status.Error(codes.Unauthenticated, "메타데이터 없음")
    }
    auth := md.Get("authorization") // []string
    if len(auth) == 0 || !strings.HasPrefix(auth[0], "Bearer ") {
        return nil, status.Error(codes.Unauthenticated, "Bearer 토큰 필요")
    }
    claims, err := verifyJWT(strings.TrimPrefix(auth[0], "Bearer "))
    if err != nil {
        return nil, status.Error(codes.Unauthenticated, "토큰 검증 실패")
    }
    // 검증된 신원을 컨텍스트에 실어 핸들러로
    ctx = context.WithValue(ctx, userKey{}, claims.Subject)
    return handler(ctx, req)
}
```

`UNAUTHENTICATED`(인증되지 않음, 코드 16)와 `PERMISSION_DENIED`(인증은 되었으나 권한 없음, 코드 7)의 구분은 9장(에러 모델)을 따른다. 토큰은 TLS 위에서 전송해야 안전하다. 평문 연결에 Bearer 토큰을 실으면 도청될 수 있다([[11 - 보안 - TLS mTLS 인증]]).

### 7.2 로깅 (서버/클라이언트)

호출의 메서드, 상태 코드, 소요 시간, 요청 ID를 구조화 로그로 남긴다. 6.1절의 `LoggingUnaryServer`가 기본 형태이다. 핵심은 **메타데이터의 `x-request-id`를 로그에 함께 남겨서** 여러 서비스의 로그를 서로 연관(correlate)시키는 것이다.

```go
func LoggingUnaryServer(ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
    reqID := firstOrEmpty(metadataGet(ctx, "x-request-id"))
    start := time.Now()
    resp, err := handler(ctx, req)
    log.Printf(`{"method":%q,"code":%q,"dur_ms":%d,"req_id":%q}`,
        info.FullMethod, status.Code(err), time.Since(start).Milliseconds(), reqID)
    return resp, err
}
```

### 7.3 메트릭 (서버/클라이언트)

호출 수, 지연 시간, 에러율을 Prometheus 등으로 집계한다. 보통 메서드 이름과 상태 코드를 라벨로 붙인다.

```go
var rpcDuration = prometheus.NewHistogramVec(
    prometheus.HistogramOpts{Name: "grpc_server_handling_seconds"},
    []string{"method", "code"},
)

func MetricsUnaryServer(ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
    start := time.Now()
    resp, err := handler(ctx, req)
    rpcDuration.WithLabelValues(info.FullMethod, status.Code(err).String()).
        Observe(time.Since(start).Seconds())
    return resp, err
}
```

라벨 카디널리티에 주의해야 한다. `FullMethod`는 값의 종류가 유한하므로 안전하지만, `x-request-id`처럼 값이 무한히 늘어나는 항목은 절대 라벨로 쓰면 안 된다(메트릭 폭발). 관찰성 전반은 [[14 - 관찰성과 디버깅 - Reflection grpcurl]]에서 다룬다.

### 7.4 분산 트레이싱 컨텍스트 주입·추출

4절에서 본 `traceparent` 추출과 주입을 인터셉터가 자동으로 처리한다. 서버 인터셉터는 들어온 메타데이터에서 부모 컨텍스트를 추출하고, 클라이언트 인터셉터는 나가는 메타데이터에 현재 컨텍스트를 주입한다.

```go
// 서버: 들어온 메타데이터에서 trace context 추출 → 자식 스팬 시작
func TracingUnaryServer(ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
    md, _ := metadata.FromIncomingContext(ctx)
    parent := propagator.Extract(ctx, MetadataCarrier(md)) // traceparent 읽기
    ctx, span := tracer.Start(parent, info.FullMethod)
    defer span.End()
    resp, err := handler(ctx, req)
    if err != nil {
        span.RecordError(err)
    }
    return resp, err
}

// 클라이언트: 현재 스팬을 나가는 메타데이터에 주입
func TracingUnaryClient(ctx context.Context, method string, req, reply any,
    cc *grpc.ClientConn, invoker grpc.UnaryInvoker, opts ...grpc.CallOption) error {
    md, _ := metadata.FromOutgoingContext(ctx)
    md = md.Copy()
    propagator.Inject(ctx, MetadataCarrier(md)) // traceparent 쓰기
    ctx = metadata.NewOutgoingContext(ctx, md)
    return invoker(ctx, method, req, reply, cc, opts...)
}
```

실무에서는 이런 인터셉터를 직접 작성하기보다 OpenTelemetry의 `otelgrpc` 같은 표준 인터셉터를 등록한다. 직접 만들어 보면서 얻을 수 있는 교훈은 **추출은 서버 인터셉터가, 주입은 클라이언트 인터셉터가 맡는다**는 대칭성이다.

### 7.5 패닉 복구 (서버 인터셉터)

핸들러에서 패닉(Go)이나 예외(Java/Python)가 발생하면, 기본 설정에서는 연결이나 서버 전체가 위험해질 수 있다. 복구 인터셉터는 패닉을 잡아 `INTERNAL` 에러로 변환한 뒤 클라이언트에 정상적인 에러 응답으로 돌려준다. 핸들러의 패닉을 바로 잡으려면 **가장 안쪽(핸들러에 가장 가까운 위치)에 두어야** 한다.

```go
func RecoveryUnaryServer(ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp any, err error) {
    defer func() {
        if r := recover(); r != nil {
            stack := debug.Stack()
            log.Printf("PANIC %s: %v\n%s", info.FullMethod, r, stack)
            err = status.Errorf(codes.Internal, "내부 오류") // 스택은 로그에만!
        }
    }()
    return handler(ctx, req)
}
```

보안상 중요한 점이 있다. 패닉 메시지나 스택 트레이스를 클라이언트에 보내는 에러에 노출하면 안 된다. 내부 구현이 드러나기 때문이다. 이런 정보는 로그에만 남기고, 클라이언트에는 일반적인 `INTERNAL` 에러를 돌려준다.

### 7.6 요청 검증 (서버 인터셉터)

`protoc-gen-validate` 같은 도구로 protobuf 메시지에 `Validate()` 메서드를 생성해 두었다면, 인터셉터에서 일괄 검증해서 핸들러에 들어가기 전에 `INVALID_ARGUMENT`로 걸러낼 수 있다.

```go
type validator interface{ Validate() error }

func ValidateUnaryServer(ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
    if v, ok := req.(validator); ok {
        if err := v.Validate(); err != nil {
            return nil, status.Errorf(codes.InvalidArgument, "검증 실패: %v", err)
        }
    }
    return handler(ctx, req)
}
```

### 7.7 재시도·서킷브레이커 (클라이언트 인터셉터)

클라이언트 인터셉터에서 `invoker`를 여러 번 호출하면 재시도가 된다. 다만 단순한 재시도는 멱등성(idempotency)을 깨뜨릴 수 있고, gRPC는 서비스 설정에 기반한 내장 retry 정책을 따로 제공한다. 따라서 인터셉터 수준의 재시도는 세밀한 제어가 필요할 때만 쓴다.

이 주제는 [[13 - 안정성 - Retry Health Check Keepalive]]에서 자세히 다루므로, 여기서는 "클라이언트 인터셉터가 invoker를 감싸 재시도나 차단 로직을 넣을 수 있다"는 점만 짚어 둔다.

```go
func RetryUnaryClient(ctx context.Context, method string, req, reply any,
    cc *grpc.ClientConn, invoker grpc.UnaryInvoker, opts ...grpc.CallOption) error {
    var err error
    for attempt := 0; attempt < 3; attempt++ {
        err = invoker(ctx, method, req, reply, cc, opts...)
        if status.Code(err) != codes.Unavailable { // 재시도 가능 코드만
            return err
        }
        time.Sleep(backoff(attempt))
    }
    return err
}
```

## 8. 체이닝과 순서: 인터셉터를 쌓는 순서

### 8.1 체이닝 라이브러리

표준 gRPC는 Go에서는 `ChainUnaryInterceptor`/`ChainStreamInterceptor`로, Java에서는 여러 ServerInterceptor를 등록하는 방식으로 체이닝을 지원한다. 생태계에는 `go-grpc-middleware`처럼 자주 쓰는 인터셉터 모음(로깅, 인증, 복구, 트레이싱, 메트릭, 검증)과 깔끔한 체이닝 API를 함께 제공하는 라이브러리도 있다.

```go
import (
    "github.com/grpc-ecosystem/go-grpc-middleware/v2/interceptors/recovery"
    "github.com/grpc-ecosystem/go-grpc-middleware/v2/interceptors/logging"
)

srv := grpc.NewServer(
    grpc.ChainUnaryInterceptor(
        TracingUnaryServer,                 // 1. 가장 바깥
        logging.UnaryServerInterceptor(lg), // 2. 로깅
        AuthUnaryServer,                    // 3. 인증
        ValidateUnaryServer,                // 4. 검증
        recovery.UnaryServerInterceptor(),  // 5. 가장 안 (핸들러 직전)
    ),
)
```

### 8.2 등록 순서가 의미를 바꾼다

체인의 순서는 취향의 문제가 아니라 **동작의 정확성에 영향을 준다.** 바깥쪽에 둔 인터셉터일수록 먼저 진입하고 나중에 복귀한다.

```text
등록 순서:  [Tracing, Logging, Auth, Validate, Recovery]

진입(요청):  Tracing → Logging → Auth → Validate → Recovery → 핸들러
복귀(응답):  Tracing ← Logging ← Auth ← Validate ← Recovery ← 핸들러
```

왜 이 순서여야 할까? 각 위치에 둔 이유를 따져 보자.

| 순서 | 인터셉터 | 왜 이 자리인가 |
|------|---------|--------------|
| 1 (최외곽) | Tracing | 인증 실패를 포함한 모든 처리를 스팬에 담으려면 가장 바깥에 있어야 한다. 인증 실패도 트레이스에 보여야 하기 때문이다 |
| 2 | Logging | 트레이스 ID가 이미 컨텍스트에 있어야 로그에 함께 남는다. 그래서 Tracing보다 안쪽에 둔다 |
| 3 | Auth | 검증과 핸들러보다 먼저 차단해 불필요한 작업을 막는다 |
| 4 | Validate | 인증된 요청만 검증한다. 검증 비용은 인증을 통과한 요청에만 쓴다 |
| 5 (최내곽) | Recovery | 핸들러 패닉을 즉시 잡으려면 핸들러에 가장 가까이 둔다 |

**대표적인 함정**은 트레이싱을 로깅보다 *안쪽*에 두는 것이다. 이렇게 하면 로깅 인터셉터가 실행될 때 아직 trace 컨텍스트가 없어서 로그에 trace ID가 남지 않고, 로그와 트레이스를 연관 지을 수 없다. 그래서 트레이싱을 로깅보다 바깥에 두는 것이 정석이다.

또 다른 함정은 Recovery를 *바깥쪽*에 두는 것이다. 그러면 안쪽 인터셉터(예: 메트릭)가 핸들러 패닉의 영향을 받은 뒤에야 복구가 일어나서, 패닉 때문에 메트릭이 기록되지 않을 수 있다. Recovery는 가장 안쪽에 두는 것이 안전하다(다만 인터셉터 자체의 버그까지 잡으려면 따로 고려해야 한다).

클라이언트 측도 원리는 같다. 예를 들어 재시도 인터셉터를 트레이싱보다 바깥에 두면 재시도 전체가 하나의 스팬으로 묶이고, 안쪽에 두면 각 시도가 별도의 스팬이 된다. 어느 쪽을 원하는지에 따라 순서를 정하면 된다.

## 9. 함정과 주의점

### 9.1 메타데이터·컨텍스트의 불변성

인터셉터에서 메타데이터를 변경할 때는 **공유 상태를 직접 수정하면 안 된다.** Go의 `metadata.MD`는 맵이므로 여러 고루틴이 공유할 수 있다. 변경하기 전에 `md.Copy()`로 복사해야 안전하다.

```go
// 위험: 원본 메타데이터를 직접 수정 (다른 RPC와 공유될 수 있음)
md, _ := metadata.FromOutgoingContext(ctx)
md.Set("x-tenant", tenant)   // ✗ 공유 맵 변형

// 안전: 복사 후 수정
md, _ := metadata.FromOutgoingContext(ctx)
md = md.Copy()               // ✓
md.Set("x-tenant", tenant)
ctx = metadata.NewOutgoingContext(ctx, md)
```

Java의 `Context`는 불변(immutable)이므로 `withValue`가 항상 새 컨텍스트를 만든다. API 설계로 안전성을 강제하는 좋은 예이다. Go의 `context.Context`도 불변이지만 `metadata.MD`(맵)는 가변이므로 직접 신경 써야 한다. 컨텍스트 전파와 취소의 의미는 10장(Deadline 취소 타임아웃)에서 더 자세히 다룬다.

incoming 메타데이터와 outgoing 메타데이터도 헷갈리지 말아야 한다. Go에서 서버가 받은 메타데이터는 `FromIncomingContext`로, 클라이언트가 보낼 메타데이터는 `FromOutgoingContext`/`AppendToOutgoingContext`로 다룬다. 서버가 받은 incoming 메타데이터는 다음 호출의 outgoing으로 **자동 전파되지 않는다.** 컨텍스트를 전파하려면 인터셉터에서 명시적으로 복사해 넘겨야 한다.

```go
// 서버 인터셉터에서 incoming의 request-id를 outgoing으로 잇기
func PropagateUnaryServer(ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {
    if md, ok := metadata.FromIncomingContext(ctx); ok {
        if ids := md.Get("x-request-id"); len(ids) > 0 {
            ctx = metadata.AppendToOutgoingContext(ctx, "x-request-id", ids[0])
        }
    }
    return handler(ctx, req)
}
```

### 9.2 스트리밍 메시지 가로채기 비용

6.2절에서 짚었듯이, stream 인터셉터로 메시지를 하나하나 후킹하면 비용이 메시지 수에 비례해 늘어난다. 양방향 스트림에서 초당 1만 개의 메시지를 후킹하면 메시지마다 클로저 호출, 로깅, 복사가 일어난다.

따라서 메시지 단위 후킹은 꼭 필요할 때만 쓰고, 후킹 함수는 카운터를 증가시키는 정도로 아주 가볍게 유지하는 것이 좋다. 메시지 내용 전체를 매번 로깅하면 처리량이 급격히 떨어진다. 흐름 제어와 백프레셔 관점의 추가 논의는 [[15 - 성능과 Flow Control 백프레셔]]에서 다룬다.

### 9.3 메타데이터 크기 폭증과 HPACK 동적 테이블 압박

메타데이터에도 비용이 든다. 2.1절에서 봤듯이 메타데이터는 HPACK 동적 테이블에 들어가 압축되지만, **테이블 크기는 유한하다**(기본 4KB 권장). 요청마다 다른 큰 메타데이터를 보내면(예: 매번 다른 거대한 JWT, 매번 다른 base64 페이로드) 동적 테이블의 항목이 계속 갱신되고 축출(eviction)되어 압축 효율이 떨어지고, 요청마다 헤더 바이트가 커진다.

```text
좋은 패턴: 작고 반복적인 메타데이터
  x-request-id: 16바이트 UUID   → 매번 다르지만 짧음 (OK)
  authorization: 같은 토큰 반복  → 동적 테이블 1회 등록 후 인덱스 참조 (최적)

나쁜 패턴: 크고 매번 다른 메타데이터
  x-debug-context-bin: 8KB base64 → 동적 테이블 초과, 매번 풀 전송 (HPACK 무력화)
  x-trace-blob: 매 요청 다른 4KB  → 테이블 축출 유발, 압축 효율 붕괴
```

또한 일부 게이트웨이와 프록시는 헤더 총량에 상한(예: 8KB, 16KB)을 둔다. 메타데이터가 이 상한을 넘으면 RPC가 거부(`RESOURCE_EXHAUSTED`나 연결 거부)된다. 큰 데이터는 메타데이터가 아니라 **본문 메시지**로 보내야 한다. 봉투에 책 한 권을 넣으면 안 되는 것과 같다. 봉투는 우표를 붙이는 곳이지 내용을 담는 곳이 아니다.

### 9.4 예약 영역 침범과 대소문자

2.3절에서 봤듯이 `grpc-`나 `:`로 시작하는 키는 라이브러리가 관리한다. 사용자 키 이름을 `grpc-my-thing`처럼 지으면 일부 구현은 그 키를 버린다. 또 HTTP/2에서는 헤더 이름이 반드시 소문자여야 하므로, 대문자 키를 설정하면 대부분의 라이브러리는 소문자로 바꾸고 일부는 오류를 낸다. 키는 항상 소문자로 다루는 습관을 들이는 것이 좋다.

### 9.5 trailer-only 응답과 에러 시 메타데이터

서버가 요청을 즉시 에러로 거부하면(예: 인증 실패) 응답 DATA 없이 trailer만 전송되는 **trailer-only 응답**이 된다. 이때 클라이언트의 `Header()` CallOption은 빈 헤더를 받고, 에러 상세 정보는 trailer와 status로 전달된다. 인터셉터로 추가한 trailing 메타데이터는 이 경우에도 전달되므로, 실패와 관련된 컨텍스트(예: `x-rate-limit-remaining`)를 trailer에 실어 보낼 수 있다.

## 10. 종합 예제: 요청 ID 부여 + Bearer 토큰 검증

이제 지금까지 배운 내용을 묶어, 일반적인 "주문 서비스"를 예로 client와 server 양쪽 인터셉터를 구현해 보자. 시나리오는 다음과 같다. 클라이언트는 모든 요청에 고유한 `x-request-id`를 부여하고 `authorization: Bearer <token>`을 싣는다. 서버는 토큰을 검증하고, 요청 ID를 로그에 남기며, 응답 trailer에 처리 시간을 실어 보낸다.

### 10.1 proto 정의

```proto
syntax = "proto3";
package order.v1;
option go_package = "example.com/order/v1;orderv1";

service OrderService {
  rpc GetOrder(GetOrderRequest) returns (GetOrderResponse);
}

message GetOrderRequest  { int64 order_id = 1; }
message GetOrderResponse {
  int64  order_id = 1;
  string status   = 2;
  int64  amount   = 3;
}
```

[[06 - 코드 생성과 protoc 툴체인]]의 절차에 따라 `protoc`/`buf`를 실행해 `orderv1` 패키지의 스텁을 생성했다고 가정한다.

### 10.2 클라이언트 인터셉터 (요청 ID + 토큰 주입)

```go
package main

import (
    "context"

    "github.com/google/uuid"
    "google.golang.org/grpc"
    "google.golang.org/grpc/metadata"
)

// 모든 호출에 x-request-id와 authorization을 주입하는 클라이언트 인터셉터
func clientAuthAndReqID(token string) grpc.UnaryClientInterceptor {
    return func(ctx context.Context, method string, req, reply any,
        cc *grpc.ClientConn, invoker grpc.UnaryInvoker, opts ...grpc.CallOption) error {

        reqID := uuid.NewString()
        // outgoing 컨텍스트에 메타데이터 덧붙이기 (봉투에 우표)
        ctx = metadata.AppendToOutgoingContext(ctx,
            "x-request-id", reqID,
            "authorization", "Bearer "+token,
        )

        // 응답 헤더/트레일러를 받아볼 포인터
        var header, trailer metadata.MD
        opts = append(opts, grpc.Header(&header), grpc.Trailer(&trailer))

        err := invoker(ctx, method, req, reply, cc, opts...) // 다음 단계

        // 서버가 trailer에 실어 보낸 처리 시간 읽기
        if dur := trailer.Get("x-processing-ms"); len(dur) > 0 {
            // 관찰: 서버 처리 시간 = dur[0] ms, req_id = reqID
        }
        return err
    }
}

func dial(target, token string) (*grpc.ClientConn, error) {
    return grpc.NewClient(target,
        grpc.WithTransportCredentials(loadTLS()), // 토큰은 TLS 위에서만!
        grpc.WithChainUnaryInterceptor(clientAuthAndReqID(token)),
    )
}
```

`metadata.AppendToOutgoingContext`는 기존 메타데이터를 유지하면서 새 항목을 덧붙이므로, 여러 인터셉터가 각자 키를 추가해도 충돌하지 않는다. 토큰을 실어 보내므로 반드시 `WithTransportCredentials`(TLS)를 써야 한다(11장 보안).

### 10.3 서버 인터셉터 (토큰 검증 + 로깅 + trailer)

```go
package main

import (
    "context"
    "fmt"
    "log"
    "strings"
    "time"

    "google.golang.org/grpc"
    "google.golang.org/grpc/codes"
    "google.golang.org/grpc/metadata"
    "google.golang.org/grpc/status"
)

type ctxKey string
const userIDKey ctxKey = "userID"

// 1) 인증 인터셉터 (안쪽: 검증 통과한 요청만 다음으로)
func serverAuth(ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {

    md, ok := metadata.FromIncomingContext(ctx)
    if !ok {
        return nil, status.Error(codes.Unauthenticated, "메타데이터 없음")
    }
    auths := md.Get("authorization")
    if len(auths) == 0 || !strings.HasPrefix(auths[0], "Bearer ") {
        return nil, status.Error(codes.Unauthenticated, "Bearer 토큰 필요")
    }
    userID, err := verifyToken(strings.TrimPrefix(auths[0], "Bearer "))
    if err != nil {
        return nil, status.Error(codes.Unauthenticated, "토큰 검증 실패")
    }
    ctx = context.WithValue(ctx, userIDKey, userID) // 신원을 핸들러로
    return handler(ctx, req)
}

// 2) 로깅 + trailer 인터셉터 (바깥: 모든 결과를 관찰)
func serverLogging(ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (any, error) {

    start := time.Now()
    reqID := first(metadata.ValueFromIncomingContext(ctx, "x-request-id"))

    resp, err := handler(ctx, req)

    dur := time.Since(start)
    // 응답 trailer에 처리 시간을 실어 보낸다
    _ = grpc.SetTrailer(ctx, metadata.Pairs(
        "x-processing-ms", fmt.Sprint(dur.Milliseconds())))

    log.Printf(`{"method":%q,"code":%q,"dur_ms":%d,"req_id":%q}`,
        info.FullMethod, status.Code(err), dur.Milliseconds(), reqID)
    return resp, err
}

func first(ss []string) string { if len(ss) > 0 { return ss[0] }; return "" }

func newServer() *grpc.Server {
    return grpc.NewServer(
        grpc.ChainUnaryInterceptor(
            serverLogging, // 바깥: 인증 실패도 로깅하고 trailer를 단다
            serverAuth,    // 안쪽: 통과한 요청만 핸들러로
        ),
    )
}
```

### 10.4 흐름 추적: 봉투 한 장이 전달되는 과정

이 예제에서 `GetOrder` 호출 한 번이 메타데이터 관점에서 어떻게 진행되는지 ASCII 다이어그램으로 따라가 보자.

```text
클라이언트                                                     서버
   │                                                            │
 [clientAuthAndReqID 진입]                                      │
   │ ctx += x-request-id: 7f3a..., authorization: Bearer eyJ... │
   │                                                            │
   │── HEADERS ───────────────────────────────────────────────→│
   │   :path /order.v1.OrderService/GetOrder                    │
   │   content-type application/grpc                            │
   │   x-request-id 7f3a...                                     │
   │   authorization Bearer eyJ...                              │
   │── DATA (GetOrderRequest{order_id:42}) END_STREAM ─────────→│
   │                                                          [serverLogging 진입] start=t0
   │                                                          [serverAuth 진입]
   │                                                            │ md.Get("authorization") OK
   │                                                            │ verifyToken → userID=u_99
   │                                                          [핸들러 GetOrder 실행]
   │                                                            │ resp = {42, "PAID", 12000}
   │                                                          [serverAuth 복귀]
   │                                                          [serverLogging 복귀]
   │                                                            │ SetTrailer x-processing-ms: 7
   │                                                            │ log{method,code=OK,req_id=7f3a}
   │←─ HEADERS (응답 leading) :status 200 ─────────────────────│
   │←─ DATA (GetOrderResponse{42,"PAID",12000}) ───────────────│
   │←─ HEADERS (trailing) grpc-status 0 ───────────────────────│
   │   x-processing-ms 7  END_STREAM                            │
 [clientAuthAndReqID 복귀]                                      │
   │ trailer.Get("x-processing-ms") = ["7"]                     │
   ▼                                                            ▼
```

이 다이어그램에는 이 장에서 다룬 내용이 모두 담겨 있다. 봉투(메타데이터)는 HEADERS와 TRAILERS에 실리고, 인터셉터는 양쪽 끝에서 그 봉투를 읽고 쓰며, 본문(DATA)은 그 사이로 전달된다. 인증은 본문을 건드리지 않고 봉투만 보고 통과시킬지 거부할지를 결정한다. 로깅은 봉투의 request-id로 분산된 로그를 하나로 이어 주고, trailer는 응답이 끝난 뒤에 처리 통계를 덧붙인다.

### 10.5 grpcurl로 메타데이터 직접 보내기

서버를 띄워 두고 14장(관찰성과 디버깅)에서 소개하는 grpcurl로 메타데이터를 직접 실어 호출해 보면 개념을 더 확실히 이해할 수 있다.

```bash
# -H 로 메타데이터(헤더)를 직접 주입한다
grpcurl -plaintext \
  -H 'x-request-id: 7f3a-test-0001' \
  -H 'authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1Xzk5In0.sig' \
  -d '{"order_id": 42}' \
  localhost:50051 order.v1.OrderService/GetOrder

# 응답 헤더/트레일러까지 보려면 -v
grpcurl -plaintext -v \
  -H 'authorization: Bearer <token>' \
  -d '{"order_id": 42}' \
  localhost:50051 order.v1.OrderService/GetOrder
# Response trailers received:
#   x-processing-ms: 7
```

`-v` 옵션을 주면 `Response headers received`(leading)와 `Response trailers received`(trailing)가 따로 출력된다. 3절에서 본 두 창을 실제로 확인할 수 있는 것이다. 토큰 없이 호출하면 `Code: Unauthenticated`로 거부되는 것도 확인할 수 있다.
