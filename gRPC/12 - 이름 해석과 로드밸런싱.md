## 12.0 들어가며: "주소를 안다"와 "어디로 보낼지 안다"는 다른 문제다

[[07 - 채널 스텁 커넥션 생명주기]]에서는 채널(channel)이 만들어지는 과정과, 그 아래에서 실제 TCP/TLS 연결을 맡는 subchannel이 따르는 상태(state) 머신을 살펴보았다. [[04 - HTTP2 깊이 보기 - 전송 계층]]에서는 TCP 연결 하나 위에서 여러 스트림(stream)을 멀티플렉싱(multiplexing)하는 HTTP/2의 동작을 자세히 보았다.

그런데 지금까지 일부러 미뤄 둔 질문이 하나 있다. 채널을 만들 때 적는 다음 한 줄에 관한 질문이다.

```go
conn, err := grpc.NewClient("dns:///orders.svc.cluster.local:50051", opts...)
```

이 문자열은 **정확히 무엇을 의미하는가?** `orders.svc.cluster.local`이라는 이름은 어떻게 실제 IP 주소로 바뀌는가? 그 서비스 뒤에 파드(pod)가 10개 떠 있다면 내 요청은 그중 어디로 가는가? 파드 하나가 죽으면 누가 그 사실을 알아차리고 목록에서 빼는가? 스케일아웃(scale-out)으로 새 파드가 추가되면 클라이언트는 언제 그 사실을 알게 되는가?

이 질문들에 답하는 것이 이 장의 주제인 **이름 해석(name resolution)** 과 **로드밸런싱(load balancing)** 이다.

전통적인 모놀리식 서버나 단순한 REST 클라이언트에서는 이 두 가지를 대개 인프라(DNS + L4 로드밸런서)가 맡았다. 클라이언트는 `https://api.example.com`으로 요청을 보내기만 하면 되고, 그 뒤에서 무슨 일이 일어나는지 몰라도 됐다.

그러나 **gRPC는 이 결정 권한의 상당 부분을 클라이언트 라이브러리 안으로 가져왔다.** 이 장의 절반은 gRPC가 왜 그렇게 설계했는지를 이해하는 데 쓰고, 나머지 절반은 그 결과 내부에서 실제로 어떤 일이 일어나는지를 살펴보는 데 쓴다.

먼저 그림으로 전체 구조를 잡아 보자. gRPC 채널 안에는 서로 협력하는 구성 요소가 세 개 있다.

```text
              gRPC Channel (논리적 연결)
  ┌─────────────────────────────────────────────────────────┐
  │                                                           │
  │   target URI: "dns:///orders.svc:50051"                   │
  │        │                                                  │
  │        │  scheme("dns") 로 플러그인 선택                  │
  │        ▼                                                  │
  │  ┌──────────────┐   resolved addresses + service config   │
  │  │ Name Resolver│ ─────────────────────────────┐          │
  │  │  (DNS)       │   [10.0.0.1:50051,            │          │
  │  └──────────────┘    10.0.0.2:50051,            │          │
  │        ▲             10.0.0.3:50051]            ▼          │
  │        │ 재해석(re-resolve)        ┌────────────────────┐  │
  │        │ (TTL 만료/연결 실패 시)   │   LB Policy        │  │
  │        └───────────────────────────│ (round_robin 등)   │  │
  │                                     └────────────────────┘  │
  │                                       │     │     │        │
  │                            subchannel 집합을 생성·관리      │
  │                                       ▼     ▼     ▼        │
  │                                  ┌──────┐┌──────┐┌──────┐  │
  │                                  │ SC#1 ││ SC#2 ││ SC#3 │  │
  │                                  │READY ││READY ││TRANS.│  │
  │                                  └──┬───┘└──┬───┘└──┬───┘  │
  └─────────────────────────────────────┼───────┼───────┼─────┘
                                         ▼       ▼       ▼
                                    10.0.0.1  10.0.0.2  10.0.0.3
                                     (백엔드 파드들)
```

- **Name Resolver(이름 해석기)**: target URI의 호스트 부분을 입력으로 받아 **주소 목록(list of addresses)** 과 **service config(JSON)** 를 출력한다. 즉 "이 이름에 해당하는 IP는 이것들이고, 이 채널은 이런 정책으로 동작하라"는 두 가지 정보를 채널에 전달한다.
- **LB Policy(로드밸런싱 정책)**: resolver가 준 주소 목록을 받아 주소마다 **subchannel** 을 만들고 그 상태를 추적한다. 그리고 RPC마다 "이번에는 어느 subchannel로 보낼지"를 결정하는 **picker**(피커)를 채널에 제공한다.
- **Subchannel(서브채널)**: 백엔드 주소 하나에 대한 실제 연결이다. 상태 머신은 7장(채널 스텁 커넥션 생명주기)에서 본 `IDLE → CONNECTING → READY → TRANSIENT_FAILURE`와 같다.

세 구성 요소가 어떻게 협력하는지 기억해 두면, 이 장의 나머지 내용은 이 그림의 상자 하나하나를 확대해서 살펴보는 과정이라고 보면 된다.

## 12.1 target URI: 채널 생성의 실제 문법

### 12.1.1 호스트:포트가 아니라 URI다

`grpc.NewClient("localhost:50051")`을 보면 많은 사람이 "호스트와 포트구나" 하고 넘어간다. 절반만 맞는 생각이다. gRPC가 받는 이 문자열은 실제로는 **RFC 3986** 형식의 **URI**이며, 정식 형태는 다음과 같다.

```text
  scheme :// authority / endpoint_name
  ─────     ─────────   ─────────────
  어떤      (선택)       이름 해석기에
  resolver  authority    넘길 실제 "이름"
  를 쓸까
```

예를 들어 `dns:///orders.svc.cluster.local:50051`을 나누어 보면 다음과 같다.

| 구성 요소 | 값 | 의미 |
|-----------|-----|------|
| scheme | `dns` | DNS resolver 플러그인을 사용한다 |
| authority | `` (비어 있음) | DNS 서버를 지정하지 않았으므로 시스템 기본 resolver를 사용한다 |
| endpoint | `orders.svc.cluster.local:50051` | 해석 대상 이름과 포트 |

여기서 슬래시가 세 개(`///`)인 이유를 알 수 있다. `scheme://` 다음에는 authority가 오는데, authority가 비어 있으면 곧바로 `/`와 함께 endpoint가 시작된다. `dns://8.8.8.8/orders.svc:50051`처럼 적으면 authority 자리에 `8.8.8.8`이 들어가고, "구글 DNS 서버를 사용해 해석하라"는 뜻이 된다.

그렇다면 `grpc.NewClient("localhost:50051")`처럼 scheme 없이 적어도 동작하는 이유는 무엇일까?

gRPC는 scheme을 파싱하지 못했거나 해당 scheme으로 등록된 resolver가 없으면 **기본 scheme(default scheme)** 을 적용한다. 대부분의 구현에서 이 기본값은 `dns`이다(Go에서는 `resolver.SetDefaultScheme`으로 바꿀 수 있다). 따라서 `localhost:50051`은 사실상 `dns:///localhost:50051`로 처리된다.

> [!warning] 함정
> Windows 경로나 일부 호스트 문자열이 우연히 `C:\...`처럼 생겼다면 `C`가 scheme으로 잘못 해석될 수 있다. 그래서 scheme을 명시적으로 붙이는 습관이 안전하다.

> [!warning] 함정(Go)
> "기본 scheme이 `dns`"라는 설명은 권장 API인 `grpc.NewClient`의 동작이다. NewClient는 scheme이 없으면 `dns`를 적용한다(`grpc.WithDefaultScheme`로 변경할 수 있다). 반면 **레거시 `grpc.Dial`(deprecated)은 전역 기본 scheme이 `passthrough`** 였다.
>
> 그래서 같은 `"localhost:50051"` 문자열이라도 어떤 API로 채널을 만드느냐에 따라 DNS 해석을 거치는지(`NewClient`), 문자열 그대로 dial하는지(`Dial`)가 달라졌다.
>
> 이 차이 때문에 "왜 예전 코드에서는 DNS 재해석이 일어나지 않지?" 같은 혼란이 생긴다. 새로 작성하는 코드에서는 `NewClient`를 쓰고, 의도가 분명히 드러나도록 scheme을 명시하자.

### 12.1.2 scheme과 resolver 플러그인의 대응

scheme은 일종의 **플러그인 선택 키**다. gRPC 런타임은 내부에 resolver 레지스트리(registry)를 두고, 각 resolver는 자신이 처리할 scheme을 등록한다. 대표적인 내장 scheme은 다음과 같다.

| scheme | resolver | 동작 | 대표 용도 |
|--------|----------|------|-----------|
| `dns:///` | DNS resolver | A/AAAA (+ 선택적 SRV/TXT) 조회로 주소 목록 생성 | Kubernetes headless service, 일반 도메인 |
| `passthrough:///` | passthrough resolver | 이름을 해석하지 않고 **문자열 그대로** 단일 주소로 사용 | 이미 IP를 아는 경우, 프록시 뒤, 사이드카 |
| `unix:` / `unix-abstract:` | unix resolver | 유닉스 도메인 소켓(UDS) 경로 | 같은 호스트 내 IPC, 사이드카 통신 |
| `ipv4:` | ipv4 resolver | 콤마로 구분된 IPv4 주소 목록을 그대로 사용 | 정적 주소 집합, 테스트 |
| `ipv6:` | ipv6 resolver | IPv6 주소 목록을 그대로 사용 | 정적 IPv6 집합 |
| `xds:///` | xDS resolver | xDS 컨트롤 플레인(예: Istiod)에서 동적으로 받아옴 | proxyless 서비스 메시 |

각 scheme의 정확한 표기를 익혀 두자.

```text
dns:///my-service.default.svc.cluster.local:50051
   └─ K8s 클러스터 내부 DNS. headless service면 모든 파드 IP 반환.

dns://10.96.0.10/my-service:50051
   └─ authority에 특정 DNS 서버 IP를 지정.

unix:/var/run/app.sock
   └─ 절대 경로. 슬래시 하나 주의(unix:///path 도 허용되는 구현 있음).

unix-abstract:my-socket
   └─ 리눅스 추상 네임스페이스 소켓(파일시스템에 안 보임). 앞에 NUL 바이트.

ipv4:10.0.0.1:50051,10.0.0.2:50051,10.0.0.3:50051
   └─ 세 개의 정적 주소. round_robin과 조합하면 즉석 분산 테스트.

ipv6:[::1]:50051,[2001:db8::1]:50051
   └─ IPv6는 대괄호로 감싼다.

passthrough:///already.resolved.host:50051
   └─ DNS 안 거치고 "already.resolved.host"를 그대로 dial.

xds:///orders.svc.cluster.local
   └─ scheme이 xds면 컨트롤 플레인이 라우팅·정책·엔드포인트를 내려줌.
```

`passthrough`가 따로 있는 이유를 생각해 볼 만하다. 이미 IP를 알고 있거나, **앞단에 프록시/사이드카가 있어서 gRPC 클라이언트가 해석을 하지 말아야** 하는 상황이라면, "여러 IP를 반환하고 round_robin으로 분산하는" DNS resolver의 동작이 오히려 방해가 된다.

이때 `passthrough`는 "이 문자열은 이미 최종 목적지이니 손대지 말고 단일 subchannel로 연결하라"고 지시한다. 실제로 Envoy 사이드카를 쓰는 전통적인 서비스 메시에서는 클라이언트가 `passthrough`로 로컬 사이드카에 연결하고, 분산은 사이드카가 처리한다.

### 12.1.3 authority의 두 가지 의미

authority는 두 곳에서 의미를 가진다.

1. **resolver 관점의 authority**: 앞에서 본 것처럼 "어떤 DNS 서버를 사용할지" 같은 resolver 동작 파라미터다.
2. **HTTP/2 `:authority` 의사 헤더(pseudo-header)로서의 authority**: 4장(HTTP2 깊이 보기)에서 본 `HEADERS` 프레임의 `:authority`다. TLS의 SNI와 인증서 검증, 서버 측 가상 호스팅과 라우팅에 쓰인다.

이 둘은 혼동하기 쉽다. gRPC는 기본적으로 target의 endpoint 호스트 부분을 `:authority`로 사용하지만, Go의 `grpc.WithAuthority("override.example.com")` 같은 옵션으로 명시적으로 덮어쓸 수 있다. 이 옵션은 TLS 인증서를 검증할 호스트를 바꾸거나, 같은 IP에 여러 논리 서비스가 있는 환경에서 라우팅 키를 바꿀 때 사용한다. 보안 측면의 세부 사항은 [[11 - 보안 - TLS mTLS 인증]]에서 다룬다.

## 12.2 Name Resolver: resolver가 정확히 무엇을 반환하는가

resolver의 출력은 단순한 IP 목록이 아니라 **두 가지**다. 이 둘을 명확히 구분하는 것이 중요하다.

```text
   Resolver.Resolve(target)  ──▶  {
       Addresses:     []Address{ {Addr:"10.0.0.1:50051", ...}, ... },
       ServiceConfig:  <파싱된 JSON 객체 또는 에러>,
       Attributes:     <LB 정책에 전달할 부가 메타데이터>,
   }
```

### 12.2.1 출력 1: 주소 목록(addresses)

각 주소(Address)는 단순한 문자열이 아니라 부가 속성을 붙일 수 있는 구조체다. 특히 중요한 것은 **localities(지역성)** 나 **weight(가중치)** 같은 attribute다. round_robin은 이런 attribute를 무시하지만, weighted round robin이나 xDS 기반 LB는 이 값을 읽어 동작을 바꾼다.

또한 gRPC의 추상화에서는 주소를 **endpoint** 단위로 묶을 수 있다. 논리적인 엔드포인트 하나가 여러 물리 주소(예: IPv4/IPv6 듀얼스택)를 가지면, LB는 이를 "이 엔드포인트에 연결한다(둘 중 연결되는 쪽으로)"는 의미로 처리한다. 이 부분은 비교적 최근에 정교해졌고 구현마다 차이가 있으므로 개념만 알아 두자. **주소 목록은 "flat한 IP 리스트"가 아니라, "엔드포인트들의 집합이며 각 엔드포인트가 하나 이상의 주소를 가질 수 있는" 구조**다.

### 12.2.2 출력 2: service config (JSON)

service config는 매우 강력하지만 자주 간과되는 부분이다. resolver는 주소뿐 아니라 **채널이 어떻게 동작해야 하는지를 기술한 JSON 설정**도 함께 내려줄 수 있다. 이 설정을 **service config**라고 부른다.

service config에 담을 수 있는 대표 항목은 다음과 같다.

```json
{
  "loadBalancingConfig": [
    { "round_robin": {} }
  ],
  "methodConfig": [
    {
      "name": [
        { "service": "orders.v1.OrderService", "method": "GetOrder" }
      ],
      "timeout": "2s",
      "retryPolicy": {
        "maxAttempts": 4,
        "initialBackoff": "0.1s",
        "maxBackoff": "1s",
        "backoffMultiplier": 2.0,
        "retryableStatusCodes": ["UNAVAILABLE"]
      }
    }
  ],
  "healthCheckConfig": {
    "serviceName": "orders.v1.OrderService"
  }
}
```

이 설정에는 **이 장과 직접 관련된 항목이 두 개 들어 있다.**

1. `loadBalancingConfig`: "이 채널은 round_robin을 사용하라"는 뜻이다. 즉 **LB 정책을 resolver가 정한다.** 클라이언트 코드를 고치지 않고 서버 쪽 설정만으로 정책을 바꿀 수 있다.
2. `healthCheckConfig`: "subchannel 헬스체크를 켜고, 이 서비스 이름으로 watch하라"는 뜻이다. 헬스 상태를 반영하는 LB를 켜는 스위치다.

나머지 항목(`methodConfig`의 timeout, retryPolicy)은 각각 [[10 - Deadline 취소 타임아웃]]과 [[13 - 안정성 - Retry Health Check Keepalive]]에서 다루므로, 여기서는 깊이 들어가지 않는다. resolver가 이런 설정도 함께 내려준다는 사실만 기억하자.

service config를 얻는 경로는 두 가지다.

- **resolver가 내려주는 설정**: DNS resolver라면 `_grpc_config.<host>`라는 이름의 `TXT` 레코드에 JSON을 넣어 둘 수 있다(레코드 값은 `grpc_config=` 접두사 뒤에 service config JSON 배열이 오는 형식이다). xDS resolver는 컨트롤 플레인에서 받은 설정을 변환한다. 이 방식의 장점은 **중앙 관리**다. 운영자가 DNS나 컨트롤 플레인만 바꾸면 모든 클라이언트가 자동으로 새 정책을 받는다.
- **클라이언트가 코드에 넣는 default service config**: `grpc.WithDefaultServiceConfig(jsonString)`를 사용한다. resolver가 service config를 주지 않거나, 보안상 DNS TXT를 신뢰하지 않을 때 쓴다. 실무에서는 이 방식이 더 흔하다.

```go
// 클라이언트 코드에서 직접 service config를 박는 방법 (Go)
const svcCfg = `{
  "loadBalancingConfig": [ { "round_robin": {} } ],
  "methodConfig": [{
    "name": [{ "service": "orders.v1.OrderService" }],
    "timeout": "3s"
  }]
}`

conn, err := grpc.NewClient(
    "dns:///orders.svc.cluster.local:50051",
    grpc.WithTransportCredentials(insecure.NewCredentials()),
    grpc.WithDefaultServiceConfig(svcCfg),
)
```

> [!caution] 보안 주의
> DNS TXT로 service config를 받는다는 것은 임의의 DNS 응답이 클라이언트 동작을 바꿀 수 있다는 뜻이다. 그래서 많은 환경에서 이 기능은 기본적으로 꺼져 있거나 명시적으로 켜야(opt-in) 한다. 신뢰 경계를 넘어오는 DNS 응답을 함부로 믿지 말아야 하며, 이는 "외부 라이브러리와 외부 입력에 대한 신뢰를 최소화한다"는 원칙과도 통한다.

### 12.2.3 resolver의 생명주기: 한 번 해석하고 끝나지 않는다

resolver의 중요한 특징은 **일회성 함수가 아니라 watch(감시) 모델이라는 점**이다. resolver는 주소를 한 번 내려준 뒤에도 계속 살아 있으면서, 다음 조건에서 **재해석(re-resolution)** 을 수행하고 갱신된 목록을 채널에 푸시한다.

```text
재해석을 트리거하는 이벤트들
  ┌───────────────────────────────────────────────────────┐
  │ 1. LB policy가 "연결 실패가 났다, 주소를 다시 받고      │
  │    싶다"고 resolver에게 ResolveNow()를 호출            │
  │ 2. DNS resolver의 경우, 내부 타이머(최소 갱신 주기)가  │
  │    돌면서 주기적으로 재조회 (예: 기본 30초 최소 간격)  │
  │ 3. xDS resolver의 경우, 컨트롤 플레인이 새 설정을      │
  │    스트리밍으로 푸시 → 즉시 갱신                       │
  └───────────────────────────────────────────────────────┘
            │
            ▼
   새 주소 목록을 LB policy에 전달
            │
            ▼
   LB policy가 diff 계산:
     - 사라진 주소 → 해당 subchannel 종료(graceful)
     - 새로 생긴 주소 → subchannel 생성·연결
     - 그대로인 주소 → 유지
```

운영에서는 특히 **DNS resolver의 갱신 주기**가 중요하다. gRPC DNS resolver는 RPC마다 DNS를 조회하지 않는다(그렇게 하면 DNS 서버가 버티지 못한다). 대신 **최소 재해석 간격(minimum re-resolution interval)** 을 두고, 그 사이에는 캐시된 결과를 사용한다. 이 값이 크면 백엔드가 바뀌었는데도 클라이언트가 한참 동안 모르는 갱신 지연(staleness)이 생긴다. 이것이 12.8에서 다룰 운영 함정의 근본 원인이다.

## 12.3 DNS Resolver: 가장 흔하고, 함정도 가장 많다

DNS resolver는 가장 많이 쓰이지만 가장 많이 오해받기도 한다. 동작 방식과 **구조적 한계**를 정확히 알아 두어야 한다.

### 12.3.1 무엇을 조회하는가

DNS resolver는 `orders.svc.cluster.local:50051`을 받으면 내부적으로 다음 조회를 수행한다.

```text
1. A 레코드 조회   → IPv4 주소들  (10.0.0.1, 10.0.0.2, 10.0.0.3 ...)
2. AAAA 레코드 조회 → IPv6 주소들  (2001:db8::1 ...)
3. (선택) TXT 조회  → _grpc_config.orders.svc... 에서 service config JSON
4. (선택/구현별) SRV 조회 → grpclb 백엔드 발견용 (레거시)
```

이렇게 모은 IP에 **포트(50051)를 붙여** 주소 목록을 만든다. 핵심은 **이름에 해당하는 IP가 여러 개면 DNS가 그 IP를 모두 돌려준다** 는 점이다.

Kubernetes의 **headless service**(`clusterIP: None`)가 바로 이 동작을 활용한다. headless service에 A 레코드를 조회하면 모든 백엔드 파드의 IP가 반환된다. 그래서 `dns:///my-svc:50051`과 headless service, round_robin을 조합하는 방식이 K8s에서 가장 표준적인 클라이언트 사이드 LB 구성이다.

반대로 일반(ClusterIP) service는 A 레코드로 **가상 IP(VIP) 하나** 만 반환하고, 분산은 kube-proxy의 L4(iptables/IPVS)가 맡는다. 이렇게 하면 12.4에서 설명할 L4 LB의 쏠림 문제가 그대로 생긴다. **그래서 K8s에서 gRPC 트래픽을 제대로 분산하려면 headless service를 써야 한다**는 말이 나온다.

### 12.3.2 DNS resolver의 세 가지 구조적 한계

이 절에서 가장 중요한 내용이다. DNS는 1980년대에 설계된 프로토콜이고, 마이크로서비스 로드밸런싱을 위해 만들어지지 않았다. 그래서 DNS만 단독으로 쓰면 다음 세 가지 한계가 문제가 된다.

**한계 1: 헬스 정보가 없다.**

DNS A 레코드는 "이 이름의 IP는 이것들"이라는 정보만 준다. 그중 어떤 파드가 살아 있고 어떤 파드가 죽어 가는지 **DNS는 모른다.** 죽은 파드의 IP가 TTL이 만료되기 전까지 응답에 남아 있을 수도 있다. 따라서 DNS만으로는 건강한 백엔드만 고를 수 없다.

이 빈틈을 메우는 것이 **subchannel 자체의 연결 상태**(연결이 끊기면 TRANSIENT_FAILURE)와 **gRPC 헬스체크 프로토콜**(13장 안정성)이다. 즉 DNS는 후보 명단만 주고, 백엔드가 실제로 살아 있는지는 LB policy와 subchannel, 헬스체크가 판단하는 분업 구조다.

**한계 2: 갱신이 느리고 중간에 캐시가 있다.**

DNS는 계층적인 캐시 시스템이다. 클라이언트 OS resolver, 사이드카, 클러스터 DNS(CoreDNS), 그 위의 권위 서버까지 단계마다 TTL 기반 캐시가 있다. 게다가 gRPC DNS resolver도 자체적으로 최소 재해석 간격을 둔다. 그 결과 백엔드 토폴로지가 바뀐 순간과 클라이언트가 그 사실을 알게 되는 순간 사이에 **수 초~수십 초의 지연**이 생긴다.

트래픽이 급변하는 오토스케일링 환경에서는 이 지연 때문에 새로 뜬 파드에 한참 동안 트래픽이 가지 않거나, 죽은 파드로 계속 연결을 시도하는 증상이 나타난다.

**한계 3: 가중치·우선순위·메타데이터를 표현하기 어렵다.**

DNS A 레코드는 IP 목록일 뿐이다. "이 파드는 트래픽 70%, 저 파드는 30%" 같은 가중치나, "이 리전을 우선하고 장애가 나면 다른 리전으로" 같은 지역성 라우팅을 A 레코드로 표현할 방법은 사실상 없다(SRV에는 priority/weight가 있지만 gRPC LB에서는 일반적으로 활용되지 않고, 표현력도 제한적이다). 이런 정교한 정책이 필요하면 DNS를 넘어서 **xDS** 같은 표현력이 풍부한 컨트롤 플레인이 필요하다(12.6).

세 한계를 표 하나로 정리하면 다음과 같다.

| 요구사항 | DNS resolver 단독 | 보완책 |
|----------|-------------------|--------|
| 건강한 백엔드만 선택 | 불가 (헬스 모름) | subchannel 상태 + gRPC 헬스체크 (13장 안정성) |
| 빠른 토폴로지 반영 | 느림 (TTL/캐시/최소간격) | MAX_CONNECTION_AGE 강제 재분배, xDS push |
| 가중치/지역성 라우팅 | 사실상 불가 | xDS (LDS/RDS/CDS/EDS) |
| 중앙 정책 배포 | TXT로 가능하나 빈약·보안우려 | xDS, 또는 코드의 default service config |

기억해 두자. **DNS resolver는 "충분히 좋은 기본값"이지 "완전한 솔루션"이 아니다.** 단순한 환경에서는 충분하지만, 정교한 트래픽 관리가 필요해지는 순간 한계에 부딪힌다. 바로 이 한계 때문에 gRPCLB와 xDS가 등장했다.

## 12.4 클라이언트 사이드 L7 LB: gRPC가 L4 프록시를 버린 이유

이 절에서는 이 장 전체에서 **가장 중요한 "왜"** 를 다룬다. 차근차근 살펴보자.

### 12.4.1 L4 로드밸런서와 HTTP/2가 만날 때 생기는 문제

전통적인 로드밸런싱은 **L4(전송 계층) 프록시**로 한다. 클라이언트는 LB의 VIP로 TCP 연결을 맺고, LB는 그 연결을 백엔드 하나로 포워딩한다. 핵심은 백엔드를 **연결 단위로** 고른다는 점이다.

HTTP/1.1에서는 이 방식이 잘 동작했다. HTTP/1.1은 연결 하나에서 한 번에 요청 하나만 처리하고(파이프라이닝은 사실상 쓰지 않는다), 클라이언트는 부하를 처리하려고 연결을 여러 개 열기 때문이다. 연결이 많으니 L4가 연결을 분산하면 요청도 자연스럽게 분산되었다.

그런데 **HTTP/2는 정반대로 설계됐다.** 4장(HTTP2 깊이 보기)에서 보았듯이, HTTP/2의 핵심 장점은 **오래 유지되는(long-lived) TCP 연결 하나에서 수많은 스트림을 멀티플렉싱**한다는 것이다. 연결 핸드셰이크 비용을 한 번만 치르고, HOL(head-of-line) 블로킹 없이 여러 RPC를 동시에 처리한다. gRPC는 HTTP/2 위에서 동작하므로, **gRPC 클라이언트는 보통 백엔드 하나당 연결을 하나만 유지한다.**

이제 L4 LB 뒤에 gRPC를 두면 어떤 일이 생기는지 보자.

```text
   [L4 LB 뒤의 gRPC: 연결 쏠림(connection pinning) 문제]

   Client A ──(1개의 영속 TCP 연결)──┐
                                      │  L4 LB가 연결을
   Client B ──(1개의 영속 TCP 연결)──┤  맺을 때 백엔드 고정
                                      ▼
                              ┌───────────────┐
                              │     L4 LB      │
                              └───┬───────┬────┘
                  연결 고정! ─────┘       └──── 연결 고정!
                                  ▼               ▼
                            ┌─────────┐     ┌─────────┐     ┌─────────┐
                            │Backend 1│     │Backend 2│     │Backend 3│
                            │ A,B의   │     │  (놀고   │     │ (아예    │
                            │ 모든    │     │  있음)   │     │  연결    │
                            │ RPC!    │     │          │     │  없음)   │
                            └─────────┘     └─────────┘     └─────────┘
```

L4 LB는 **연결을 맺는 순간 한 번만** 백엔드를 고른다. 그 연결이 한 시간 동안 유지되면서 RPC가 10만 개 오가더라도, **그 10만 개는 전부 같은 백엔드로 간다.** L4는 연결 안에서 오가는 개별 요청(스트림)을 보지 못하기 때문이다(그것은 L7의 역할이다). 클라이언트 수가 백엔드 수보다 적거나, 클라이언트들의 연결이 우연히 같은 백엔드로 몰리면 심각한 불균형이 생긴다. **어떤 백엔드는 과부하가 걸리고, 어떤 백엔드는 놀고, 어떤 백엔드는 연결조차 받지 못한다.**

게다가 스케일아웃을 해도 효과가 없다. 새 백엔드(Backend 4)를 추가해도 **이미 맺어진 영속 연결들은 기존 백엔드에 그대로 붙어 있다.** 새 백엔드는 새 연결이 생길 때까지 놀게 된다. 오래 유지되는 연결이라는 장점이 분산에는 오히려 방해가 되는 것이다.

### 12.4.2 두 가지 해법: L7 프록시와 클라이언트 사이드 LB

이 문제를 푸는 방법은 두 가지다.

**해법 A: L7 프록시 LB.** LB가 HTTP/2를 이해하게 만드는 방법이다. Envoy나 nginx 같은 L7 프록시는 연결을 종단(terminate)하고, **각 스트림(요청)을 개별적으로** 백엔드에 분배한다. 클라이언트 연결 하나 위의 RPC 100개가 백엔드 100개로 흩어질 수 있다. 정확하고 강력한 방법이다. 대신 **모든 요청이 프록시를 한 번 더 거친다.** 추가 홉(hop)만큼 지연(latency)이 늘고, 프록시 자체를 운영하고 확장해야 하며, 프록시가 또 하나의 장애 지점이자 병목이 된다는 비용이 있다.

**해법 B: 클라이언트 사이드 LB.** 프록시를 아예 없애는 방법이다. **클라이언트가 모든 백엔드에 직접 연결을 맺고, 요청마다 어느 백엔드로 보낼지 스스로 고른다.** gRPC는 이 방식을 기본 모델로 채택했다.

```text
   [클라이언트 사이드 L7 LB: 요청 단위 분산]

   Client (round_robin LB policy)
     │
     ├──(연결1)──▶ Backend 1   ┐
     ├──(연결2)──▶ Backend 2   ├─ 모든 백엔드에 직접 연결
     └──(연결3)──▶ Backend 3   ┘
     │
     매 RPC마다 picker가 "이번엔 1, 다음엔 2, 다음엔 3..." 순환
     → 요청 단위(L7) 분산이 클라이언트 안에서 일어남
     → 추가 네트워크 홉 없음 (프록시 없음)
```

클라이언트 사이드 LB의 장점은 다음과 같다.

- **요청 단위 분산**: round_robin이라면 RPC마다 다음 백엔드를 골라 실제로 고르게 분산한다. L4에서 생기던 연결 쏠림이 원천적으로 사라진다.
- **추가 홉 없음**: 클라이언트가 백엔드에 직접 연결하므로 프록시로 인한 지연이나 병목이 없다. 마이크로서비스 사이의 east-west 트래픽처럼 양이 많은 구간에서 특히 유리하다.
- **백엔드 상태 직접 파악**: 클라이언트가 각 subchannel의 연결 상태를 직접 보므로, 죽은 백엔드를 picker에서 바로 뺄 수 있다.

치러야 할 비용도 있다.

- **클라이언트가 똑똑해야 한다**: 모든 클라이언트의 gRPC 라이브러리가 resolver와 LB policy를 구현해야 한다. 그래서 gRPC는 이 로직을 라이브러리 안에 내장했다. 여러 언어의 SDK가 모두 이 로직을 구현해야 한다는 부담이 생기는데, 이것이 [[16 - gRPC-Web과 REST 게이트웨이]]에서 설명하는, 브라우저 환경에서 클라이언트 LB를 할 수 없는 이유와 이어진다.
- **연결 수 폭증 가능성**: 클라이언트 N개와 백엔드 M개가 있으면 연결이 N×M개 생긴다. 백엔드가 수천 개라면 클라이언트마다 수천 개의 연결을 유지해야 한다. round_robin은 "모든 백엔드에 연결"하므로 이 문제가 실제로 생긴다. 그래서 대규모 환경에서는 일부 백엔드에만 연결하는 subsetting이나, look-aside LB로 후보를 줄이는 전략을 쓴다.
- **멤버십 최신화는 여전히 resolver의 책임**: 클라이언트가 아무리 똑똑해도 백엔드 목록이 갱신되지 않으면 새 백엔드를 알 수 없다(12.3.2의 갱신 지연). 이 문제는 12.8에서 다룬다.

### 12.4.3 gRPC의 기본 철학

gRPC의 설계 결정은 다음과 같이 요약할 수 있다.

> "HTTP/2의 오래 유지되는 멀티플렉싱 연결은 성능에는 좋지만 L4 분산에는 해롭다. 그러니 분산을 **연결 계층(L4)이 아니라 요청 계층(L7)에서**, 그것도 **프록시가 아니라 클라이언트 안에서** 하자. 그 대신 클라이언트 라이브러리에 resolver와 LB policy를 내장해 클라이언트를 똑똑하게 만들자."

이 결정이 이 장 전체를 관통하는 기본 구조다. resolver(백엔드가 어디 있는가), LB policy(어디로 보낼 것인가), subchannel(실제 연결)로 나뉜 3분할 구조는 모두 이 철학을 구현한 것이다.

## 12.5 LB Policy 깊이 보기: pick_first와 round_robin의 내부

이제 LB policy 상자를 확대해 보자. LB policy가 하는 일은 두 가지다.

1. resolver가 준 주소 목록으로 **subchannel을 만들고 관리**한다(연결 시작, 상태 추적, 사라진 주소의 subchannel 정리).
2. RPC를 보낼 때마다 호출되는 **picker(피커)** 를 채널에 제공한다. picker는 이 RPC를 어느 subchannel로 보낼지 동기적으로 결정한다.

핵심은 이 picker 추상화다. 채널이 RPC를 보내는 경로는 "picker에게 subchannel 하나를 달라고 요청하고, 받은 subchannel로 보낸다"가 전부다. 따라서 LB policy를 바꾼다는 것은 **picker의 선택 알고리즘을 바꾸는 것**이다.

### 12.5.1 pick_first: 기본값과 그 이유

`pick_first`는 gRPC의 **기본 LB policy**다. 이름 그대로 동작한다.

```text
   pick_first 동작
   ────────────────
   resolver가 [A, B, C] 주소를 줌
        │
        ▼
   주소들을 순서대로 시도하며 "처음으로 연결되는 하나"를 찾음
   (A 시도 → 실패하면 B 시도 → ... 최근엔 happy-eyeballs식 병렬 시도도)
        │
        ▼
   연결된 그 하나의 subchannel만 READY로 유지
        │
        ▼
   picker는 항상 "그 하나"를 반환
   → 모든 RPC가 단일 백엔드로 감
        │
        ▼
   그 연결이 끊기면? 다음 주소로 넘어가 다시 "처음 되는 하나"를 찾음
   (필요시 resolver에 재해석 요청)
```

pick_first는 **백엔드 하나에만 연결**하고, 분산을 하지 않는다. 그런데도 이것이 기본값인 이유는 세 가지다.

1. **단일 엔드포인트가 가장 흔하다**: 많은 target은 실제로 단일 서버이거나, 앞단에 이미 L7 프록시나 L4 LB가 있어서 클라이언트는 그곳 하나로만 보내면 된다. 이럴 때 모든 백엔드에 연결을 맺는 round_robin은 과하다.
2. **연결 수 최소화**: pick_first는 연결을 딱 하나만 쓴다. 12.4.2에서 본 N×M 연결 폭증 문제가 없고, 리소스를 적게 쓴다.
3. **프록시·메시와 잘 맞는다**: 앞에 사이드카가 있으면 분산은 사이드카가 하고, 클라이언트는 사이드카로 연결 하나만 맺으면 된다. pick_first가 이 구조에 딱 맞는다.

즉 pick_first를 기본값으로 삼은 것은 보수적인 설계다. 안전하고 가벼우며 대부분의 단순한 경우에 맞고, 분산이 필요하면 명시적으로 round_robin으로 바꾸라는 뜻이다.

> [!note] 참고
> pick_first도 resolver가 여러 주소를 주면 그 주소들을 **후보**로 받아 연결되는 하나를 고른다. 그래서 DNS가 여러 IP를 주더라도 pick_first라면 트래픽은 그중 하나로만 간다. 이것을 보고 "분산되겠지"라고 오해하면 안 된다. 분산을 원한다면 round_robin을 명시해야 한다.

### 12.5.2 round_robin: 모든 백엔드에 연결하고 순환한다

`round_robin`은 분산이 필요할 때 쓰는 대표 정책이다.

```text
   round_robin 동작
   ─────────────────
   resolver가 [A, B, C] 주소를 줌
        │
        ▼
   "모든" 주소에 대해 subchannel 생성 + 연결 시작
        │
        ▼
   각 subchannel의 상태를 추적
   READY인 subchannel들만 모아 "ready 리스트" 구성
        │  예: A=READY, B=READY, C=TRANSIENT_FAILURE
        │      → ready 리스트 = [A, B]   (C는 제외!)
        ▼
   picker: 호출될 때마다 ready 리스트를 원형으로 한 칸씩 진행
        RPC1 → A
        RPC2 → B
        RPC3 → A   (C는 빠졌으니 A,B만 순환)
        RPC4 → B
        ...
   C가 복구되어 READY가 되면 ready 리스트에 다시 합류 → [A,B,C] 순환
```

round_robin에서 기억할 점은 두 가지다.

- **모든 백엔드에 연결을 유지**한다. 그래서 어느 백엔드로든 즉시 보낼 수 있다(연결을 미리 데우는 비용이 없다). 대신 백엔드 수만큼 연결이 필요하다.
- **READY 상태인 subchannel만 순환 대상**이다. 이것이 헬스 상태를 반영하는(health-aware) 첫 번째 방어선이다. subchannel이 TRANSIENT_FAILURE 상태면 picker가 자동으로 제외하므로, **죽은 백엔드로는 보내지 않는다.** 별도의 헬스체크가 없어도 연결이 끊긴 백엔드는 자동으로 빠진다. 다만 TCP 연결은 살아 있지만 앱이 not-serving 상태인 경우처럼 애플리케이션 수준의 헬스 문제까지 잡으려면, 13장(안정성)에서 다루는 gRPC 헬스체크가 필요하다.

round_robin은 앞에서 본 service config의 `loadBalancingConfig`로 켠다.

```go
const svcCfg = `{ "loadBalancingConfig": [ { "round_robin": {} } ] }`

conn, err := grpc.NewClient(
    "dns:///orders.svc.cluster.local:50051",
    grpc.WithTransportCredentials(insecure.NewCredentials()),
    grpc.WithDefaultServiceConfig(svcCfg),
)
```

`dns:///`(headless service)와 `round_robin`의 조합이 K8s에서 gRPC 클라이언트 사이드 LB를 구성하는 가장 기본적이고 표준적인 방법이다. DNS가 모든 파드 IP를 주고, round_robin이 그 파드 모두에 연결해 RPC를 고르게 나눠 보낸다.

### 12.5.3 더 똑똑한 정책들: weighted, least_request, ring_hash

round_robin은 단순하다는 장점이 있지만, **모든 백엔드의 처리 능력이 같다고 가정**한다. 현실은 그렇지 않기 때문에 더 정교한 정책들이 있다.

| 정책 | 핵심 아이디어 | 언제 쓰나 |
|------|---------------|-----------|
| `round_robin` | 무조건 차례대로 | 균질한 백엔드, 단순함 우선 |
| `weighted_round_robin` | 각 백엔드의 가중치(처리 능력, 또는 서버가 보고하는 부하)에 비례해 분배 | 백엔드 스펙이 다르거나, 부하 기반 동적 가중 (서버가 부하 리포트) |
| `least_request` | 진행 중(in-flight)인 요청이 가장 적은 백엔드로 | 요청 처리 시간 편차가 클 때, 느린 백엔드 회피 |
| `ring_hash` / `maglev` | 요청의 어떤 키(예: 세션 ID)를 해시해 **같은 키는 같은 백엔드로** (consistent hashing) | 세션 어피니티(sticky), 캐시 지역성이 중요할 때 |
| `pick_first` | 되는 것 하나만 | 단일 엔드포인트, 프록시 뒤 |

특히 `weighted_round_robin`을 눈여겨볼 만하다. 정적 가중치뿐 아니라, **서버가 자신의 실시간 부하(CPU, 큐 길이 등)를 응답에 실어 보내면(ORCA: Open Request Cost Aggregation 같은 메커니즘)** 클라이언트가 그 값을 받아 가중치를 동적으로 조정할 수 있다. 그래서 지금 한가한 서버로 더 많이 보내는 적응형 분산이 가능하다.

round_robin처럼 상태를 보지 않고 순환하는 방식보다 훨씬 똑똑하지만, 그만큼 클라이언트와 서버 양쪽의 구현이 복잡해진다.

`ring_hash`는 분산과는 목적이 다른 정책으로, **어피니티(affinity)** 를 위해 쓴다. 예를 들어 사용자 ID를 해시해서 같은 사용자의 요청을 항상 같은 백엔드로 보내면, 그 백엔드의 로컬 캐시 적중률이 올라간다. consistent hashing을 쓰므로 백엔드가 추가되거나 제거되어도 **재배치되는 키가 최소화**된다(모든 키가 흩어지지 않는다). 세션이 있는 워크로드나 캐시 지역성이 중요한 곳에서 쓴다.

### 12.5.4 LB policy는 계층적으로 합성된다

한 단계 더 들어가 보자. 실제 gRPC의 LB policy는 **단일 평면이 아니라 트리(tree)로 합성**된다. 예를 들어 xDS 환경에서는 다음과 같은 구조가 된다.

```text
   xds_cluster_manager        (어느 클러스터로?)
        └─ priority            (리전 우선순위: 1순위 죽으면 2순위로)
             └─ weighted_target (지역성 가중치: us-east 70%, us-west 30%)
                  └─ round_robin (그 지역 안에서 백엔드 순환)
                       └─ (각 백엔드 subchannel)
```

각 계층은 자식 policy에게 특정 부분집합을 맡기고, 자식은 다시 picker를 만들어 부모에게 올린다. picker들이 중첩되어 최종적으로 "이 RPC는 이 subchannel로 보낸다"는 결정 하나가 나온다. 이 합성 구조 덕분에 "리전 페일오버 + 지역성 가중치 + 그 안에서 라운드로빈" 같은 복합 정책을 부품처럼 조립할 수 있다. 이 트리를 직접 구성하기는 매우 번거롭지만, **xDS 컨트롤 플레인이 이 트리를 자동으로 만들어 내려준다**(12.6).

## 12.6 Look-aside LB와 xDS: 외부 컨트롤 플레인의 등장

DNS resolver의 한계(12.3.2)와 클라이언트 사이드 LB의 한계(연결 폭증, 멤버십 지연)를 함께 극복하려는 흐름에서 나온 것이 **look-aside LB**와 그 후속 기술인 **xDS**다.

### 12.6.1 in-band와 look-aside

지금까지 본 DNS + round_robin은 **in-band(인밴드)** 모델이다. 클라이언트가 백엔드들에 직접 연결하고, 그 데이터 연결을 통해 상태를 파악한다. resolver는 주소 목록만 주고 더는 관여하지 않는다.

**look-aside(룩어사이드)** 모델은 다르다. 별도의 **로드밸런서 서버(컨트롤 플레인)** 가 있고, 클라이언트는 데이터 트래픽과 **별개의 채널**로 그 LB 서버에게 "지금 어느 백엔드로 보내면 되는지, 가중치와 헬스 상태는 어떤지"를 묻는다. LB 서버는 전체 백엔드를 모니터링하면서 "현재 살아 있는 백엔드와 그 가중치"를 담은 목록을 **스트리밍으로** 내려준다. 클라이언트는 실제 데이터를 백엔드에 직접 보내지만(여전히 클라이언트 사이드 LB다), **누구에게 보낼지와 가중치는 외부 컨트롤 플레인이 정해 준다.**

```text
   look-aside LB 모델
   ───────────────────
                  ┌──────────────────────┐
                  │  LB 서버 (컨트롤플레인)│  ← 백엔드 헬스/부하를 모니터
                  └─────────┬────────────┘
       "이 백엔드들 써,      │  스트리밍으로
        가중치는 이렇게"      ▼  백엔드 목록+정책 push
                  ┌──────────────────────┐
                  │       Client          │
                  └───┬─────────┬────────┘
        실제 RPC는    │         │   (데이터는 백엔드로 직접)
        백엔드로 직접 ▼         ▼
                  Backend 1   Backend 2 ...
```

이 모델을 처음 구현한 것이 **gRPCLB**였다. gRPCLB는 SRV 레코드로 LB 서버를 찾고, 그 LB 서버와 `LoadBalancer` gRPC 서비스로 통신해 백엔드 목록을 받았다. gRPCLB 덕분에 DNS로는 할 수 없던, 헬스와 가중치를 반영한 분산이 가능해졌다.

하지만 **gRPC 전용**이라는 한계가 있어서 HTTP나 다른 RPC 프레임워크에서는 쓸 수 없었다. 그래서 **gRPCLB는 현재 deprecated(폐기 예정)** 상태이고, 그 자리를 더 일반적이고 강력한 **xDS**가 대신하고 있다.

### 12.6.2 xDS: Envoy가 만든 보편 표준

**xDS**는 원래 **Envoy 프록시**가 자신의 설정(라우팅, 클러스터, 엔드포인트)을 동적으로 받으려고 만든 **API 군(group)** 이다. 이름은 "x Discovery Service"의 약자이며, x 자리에 여러 종류가 들어간다. gRPC는 이 xDS API를 **직접** 사용하도록 구현되어 있어서, Envoy와 **같은 컨트롤 플레인(예: Istio의 Istiod)** 을 공유할 수 있다.

xDS에서 알아야 할 주요 디스커버리 서비스는 네 가지다.

| 약자 | 풀네임 | 무엇을 내려주나 | 비유 |
|------|--------|----------------|------|
| **LDS** | Listener Discovery Service | 리스너(어떤 트래픽을 어떻게 받을지) | "현관문 설정" |
| **RDS** | Route Discovery Service | 라우팅 규칙(호스트/경로/헤더 → 어느 클러스터로) | "이 손님은 이 방으로" |
| **CDS** | Cluster Discovery Service | 클러스터(논리적 백엔드 그룹)와 LB 정책 | "이 방엔 이런 그룹의 서버들" |
| **EDS** | Endpoint Discovery Service | 엔드포인트(클러스터에 속한 실제 IP들 + 가중치 + 지역성 + 헬스) | "그 그룹에 실제로 이 IP들이 있고 상태는 이렇다" |

이 네 서비스는 **계단식으로 연결**된다. 클라이언트가 `xds:///orders.svc`로 채널을 만들면 다음 순서로 진행된다.

```text
   xds:///orders.svc 채널 생성
        │
        ▼
   [LDS] "orders.svc 리스너 설정 줘" → 라우트 설정(RDS)을 가리킴
        │
        ▼
   [RDS] "이 호스트의 라우팅 규칙 줘"
         → "/orders.v1.OrderService/* 는 cluster=orders-prod 로,
            가중치 카나리: orders-prod 95% / orders-canary 5%"
        │
        ▼
   [CDS] "cluster=orders-prod 의 설정 줘"
         → "LB정책=round_robin, 헬스체크=켬, 엔드포인트는 EDS로"
        │
        ▼
   [EDS] "orders-prod 의 엔드포인트 줘"
         → [ {10.0.0.1:50051, weight=1, locality=us-east, health=HEALTHY},
              {10.0.0.2:50051, weight=1, locality=us-east, health=HEALTHY},
              {10.0.1.7:50051, weight=1, locality=us-west, health=HEALTHY} ]
        │
        ▼
   이 모든 정보가 gRPC 내부에서
   resolver(주소+config) + LB policy 트리(12.5.4)로 변환됨
```

위 그림에서는 네 디스커버리 서비스를 별개의 단계로 그렸지만, 실제 gRPC의 xDS 클라이언트는 이들을 **하나의 양방향 스트림으로 다중화**해서 받는다. 이를 **ADS(Aggregated Discovery Service)** 라고 한다.

굳이 스트림 하나로 묶는 이유는, LDS/RDS/CDS/EDS를 각각 별도 스트림으로 받으면 **갱신 순서가 어긋나** 일시적으로 라우팅이 깨질 수 있기 때문이다. 예를 들어 새 CDS(클러스터)가 먼저 도착했는데 그 클러스터의 EDS(엔드포인트)가 아직 오지 않았다면, 가리키는 곳은 있는데 보낼 IP가 없는 중간 상태가 생긴다.

스트림 하나로 묶으면 컨트롤 플레인이 갱신을 **일관된 순서로**(CDS→EDS, LDS→RDS) 내려보낼 수 있어서 이런 빈틈이 사라진다. gRPC의 xDS 구현은 이 ADS 방식을 기본으로 쓴다. 프로토콜 차원에서도 클라이언트가 받은 설정을 제대로 적용했는지 컨트롤 플레인에 알리는 ACK/NACK 흐름(State-of-the-World 또는 증분 xDS)이 있다. 잘못된 설정이 내려오면 클라이언트는 NACK으로 거부하고 직전의 정상 설정을 유지한다.

핵심은 **xDS가 DNS resolver로는 할 수 없던 일을 모두 한다**는 점이다.

- 헬스 반영: EDS가 health 상태를 직접 내려준다.
- 가중치: EDS의 weight와 RDS의 트래픽 분할(카나리/A-B 테스트)로 표현한다.
- 지역성(locality) 라우팅: locality 정보로 "같은 리전 우선, 장애 시 다른 리전"으로 페일오버한다.
- 즉시 갱신: 스트리밍 push 방식이라 TTL 지연이 없다. 백엔드가 죽으면 컨트롤 플레인이 바로 목록에서 빼서 내려준다.
- 중앙 정책: 모든 트래픽 규칙을 컨트롤 플레인 한 곳에서 관리한다.

### 12.6.3 proxyless 서비스 메시: 사이드카 없이 컨트롤 플레인만 사용한다

전통적인 서비스 메시(Istio + Envoy)는 **모든 파드 옆에 Envoy 사이드카**를 붙인다. 애플리케이션은 평범하게 통신하고, 사이드카가 트래픽을 가로채 라우팅과 mTLS, 관측을 처리한다. 강력한 방식이지만, **사이드카마다 프록시 홉 하나만큼 지연이 늘어나고**, 메모리와 CPU도 많이 쓴다.

**proxyless(프록시리스) 모드**는 이 문제를 영리하게 절충한다. **사이드카 프록시를 없애고, 그 대신 gRPC 라이브러리가 xDS를 직접 사용한다.** gRPC 클라이언트가 컨트롤 플레인(Istiod)에 직접 연결해 LDS/RDS/CDS/EDS를 받고, 이를 **자신 안의 resolver와 LB policy로 변환**한다. 데이터 트래픽은 사이드카를 거치지 않고 백엔드로 바로 간다.

```text
   사이드카 메시 vs proxyless 메시
   ────────────────────────────────

   [사이드카]                        [proxyless]
   App → Envoy(사이드카)             App(gRPC, xDS 내장)
          │  xDS                          │  xDS
          ▼                               ▼
       Istiod ◀──────────────────────  Istiod
          ▲                               
          │ (반대편도 사이드카)            데이터는 직접:
   Envoy ← App                        App ──직접──▶ Backend
                                      (프록시 홉 없음!)
   데이터: App→Envoy→네트워크→Envoy→App
   (홉 2개 추가)
```

- **장점**: 프록시 홉이 없어 지연과 리소스 사용이 줄어든다. 그러면서도 메시가 제공하는 중앙 정책, 가중치 라우팅, 지역성 같은 기능은 그대로 쓸 수 있다.
- **비용**: 메시 기능은 gRPC 라이브러리에 구현된 만큼만 동작한다. 사이드카가 제공하던 일부 기능(L7 정책 일부, gRPC가 아닌 프로토콜 처리, 일부 보안 기능)은 쓰지 못할 수 있다. 또 클라이언트가 컨트롤 플레인에 직접 의존하므로, 컨트롤 플레인이 어디 있는지 알려 주는 부트스트랩 설정이 필요하다.

proxyless gRPC는 보통 **부트스트랩 파일**(`GRPC_XDS_BOOTSTRAP` 환경변수가 가리키는 JSON)로 "xDS 서버는 여기, 노드 ID는 이것"이라는 정보를 받아서 시작한다. 그 뒤로는 `xds:///` target만 쓰면 모든 동적 설정이 컨트롤 플레인에서 들어온다.

이 영역의 mTLS와 인증서 자동 발급(SDS: Secret Discovery Service)은 11장(보안)의 내용과 이어진다. xDS는 보안 설정(인증서)도 SDS로 내려줄 수 있다.

## 12.7 헬스 인지 로드밸런싱: 죽은 백엔드를 빼는 메커니즘

건강한 백엔드만 고른다는 목표는 여러 계층이 협력해서 달성한다. 한 가지 장치로 해결하는 것이 아니라 **여러 방어선을 겹쳐 두는** 방식이다.

```text
   헬스 인지의 3중 방어선
   ──────────────────────
   1차) subchannel 연결 상태
        TCP/HTTP2 연결이 끊기면 그 subchannel은 TRANSIENT_FAILURE.
        round_robin picker가 ready 리스트에서 자동 제외.
        → "TCP가 죽은" 백엔드를 잡는다. 추가 설정 불필요.

   2차) gRPC 애플리케이션 헬스체크 (grpc.health.v1.Health)
        TCP는 살아 있어도 앱이 "NOT_SERVING"일 수 있다(예: DB 끊김).
        service config의 healthCheckConfig로 활성화하면,
        LB가 각 subchannel에 대해 Health/Watch 스트림을 열어
        SERVING/NOT_SERVING을 구독.
        NOT_SERVING이면 그 subchannel을 ready에서 제외.
        → "TCP는 살아 있으나 앱이 아픈" 백엔드를 잡는다.
        (상세는 [[13 - 안정성 - Retry Health Check Keepalive]])

   3차) outlier detection (xDS/Envoy 계열, 통계적 추방)
        실시간 에러율/지연을 보고 "통계적으로 이상한" 백엔드를
        일정 시간 추방(eject)했다가 복귀시킴.
        → 헬스체크는 통과하지만 실제로 에러를 뱉는 백엔드를 잡는다.
```

핵심은 **DNS는 후보 명단만 주고, 실제로 보낼지는 이 3중 방어선이 걸러 낸다**는 점이다. 그래서 12.3.2에서 본 "DNS에는 헬스 정보가 없다"는 한계가 치명적이지 않다. 그 빈틈을 subchannel 상태와 헬스체크가 메우기 때문이다. 다만 1차 방어선(subchannel 상태)만으로는 앱에 문제가 있는데 TCP는 멀쩡한 경우를 잡지 못한다. 그러므로 신뢰성이 중요하다면 2차 방어선(gRPC 헬스체크)을 켜야 한다.

service config에서 헬스체크를 켜는 방법은 다음과 같다.

```json
{
  "loadBalancingConfig": [ { "round_robin": {} } ],
  "healthCheckConfig": {
    "serviceName": "orders.v1.OrderService"
  }
}
```

`serviceName`은 서버의 헬스 서비스에 `Check`/`Watch`를 호출할 때 넘기는 이름이다. 빈 문자열이면 서버 전체의 헬스를 보고, 특정 서비스 이름을 넣으면 그 서비스의 헬스만 본다. 자세한 프로토콜과 서버 측 구현은 13장(안정성)에서 다룬다.

## 12.8 운영 함정: DNS만 믿다가 겪는 일들

이론을 살펴보았으니 실전에서 실제로 자주 부딪히는 함정들을 보자. 모두 이름 해석과 LB가 서로 어떻게 작용하는지 오해해서 생기는 문제다.

### 12.8.1 함정 1: 스케일아웃해도 기존 연결이 새 파드를 모른다

가장 흔하고 피해도 큰 함정이다. 다음 시나리오를 보자.

```text
   T0: 백엔드 파드 3개. 클라이언트가 round_robin으로 셋에 연결. 잘 분산됨.
   T1: 트래픽 급증 → 오토스케일러가 파드를 3 → 10으로 늘림.
   T2: ... 그런데 클라이언트는 여전히 기존 3개로만 보낸다!
       새 파드 7개는 놀고 있다. 기존 3개는 과부하.
```

이런 일이 생기는 이유는 **클라이언트가 새 파드가 있다는 사실을 모르기 때문이다.** 클라이언트가 새 파드를 알려면 **resolver가 재해석해서 갱신된 주소 목록을 주어야** 하는데(12.2.3), DNS resolver는 최소 재해석 간격과 TTL 캐시 때문에 한참 뒤에야 갱신한다. 게다가 더 까다로운 점은, **기존 연결이 멀쩡히 살아 있으면 재해석을 트리거할 이유조차 없다**는 것이다. 연결이 모두 READY 상태라면 round_robin에는 resolver를 다시 호출할 동기가 없다.

해결책은 여러 가지다.

**(a) 서버가 연결을 주기적으로 끊게 한다: `MAX_CONNECTION_AGE`.**

이것이 표준적인 해법이다. 서버 측에 "연결 하나는 최대 N분(또는 N초)까지만 유지하고, 그 뒤에는 우아하게 종료(GOAWAY)하라"는 설정을 건다.

```go
// 서버 측 (Go): 연결 강제 재분배
import "google.golang.org/grpc/keepalive"

srv := grpc.NewServer(
    grpc.KeepaliveParams(keepalive.ServerParameters{
        MaxConnectionAge:      30 * time.Minute, // 연결 최대 수명
        MaxConnectionAgeGrace: 5 * time.Minute,  // 진행 중 RPC 마무리 유예
    }),
)
```

연결이 `MaxConnectionAge`에 도달하면 서버는 `GOAWAY` 프레임(4장 HTTP2 깊이 보기)을 보내 이 연결을 그만 쓰자고 알린다. 클라이언트는 진행 중인 RPC를 마치고 연결을 닫은 뒤, **새 연결을 맺으려고 resolver를 다시 호출한다. 이때 그사이 갱신된 DNS 결과를 받아 새 파드를 발견한다.**

즉 MAX_CONNECTION_AGE는 일부러 연결을 주기적으로 새로 맺게 해서 멤버십을 강제로 최신 상태로 만드는 기법이다. K8s에서 gRPC를 운영할 때 거의 필수 설정으로 여겨진다.

```text
   MAX_CONNECTION_AGE의 효과
   ──────────────────────────
   연결 수명 ──────────┐ MaxConnectionAge 도달
   ─────────────────────▶ 서버가 GOAWAY 전송
                          │
                          ▼ 클라이언트: 진행 RPC 마치고 연결 닫음
                          │
                          ▼ 새 연결 위해 resolver 재호출
                          │
                          ▼ DNS 재조회 → [기존3 + 새7] 받음!
                          │
                          ▼ round_robin이 10개 모두에 연결 → 분산 복구
```

**(b) DNS 최소 재해석 간격을 짧게** 줄이는 방법(구현이 허용하는 경우)도 있고, **(c) xDS로 전환**하는 방법도 있다. xDS에서는 컨트롤 플레인이 즉시 push하므로 이 문제가 원천적으로 사라진다.

### 12.8.2 함정 2: pick_first인 줄 모르고 분산을 기대한다

"DNS가 IP를 10개 주니까 알아서 분산되겠지"라는 생각은 틀렸다. **기본 LB policy는 pick_first**이므로 트래픽은 10개 중 **하나로만** 간다(12.5.1). 분산을 원하면 service config에서 `round_robin`을 **명시**해야 한다. 이 한 줄을 빠뜨려서 "왜 한 파드만 터지지?"를 디버깅하는 경우가 정말 많다.

### 12.8.3 함정 3: ClusterIP service로 gRPC 분산을 기대한다

K8s의 일반 ClusterIP service는 DNS A 레코드로 **VIP 하나**만 준다(12.3.1). 클라이언트는 그 VIP로 연결 하나를 맺고, 분산은 kube-proxy(L4)가 맡는다. 결국 12.4.1의 **연결 쏠림**이 그대로 생긴다. gRPC 트래픽을 제대로 분산하려면 **headless service(`clusterIP: None`)** 를 써서 모든 파드 IP가 노출되게 하고 round_robin을 사용해야 한다.

```yaml
# gRPC 클라이언트 사이드 LB를 위한 headless service
apiVersion: v1
kind: Service
metadata:
  name: orders
spec:
  clusterIP: None          # ← 핵심! headless. A 레코드가 모든 파드 IP 반환
  selector:
    app: orders
  ports:
    - port: 50051
      targetPort: 50051
```

### 12.8.4 함정 4: 단일 연결 쏠림, 즉 멤버십 최신화 지연의 일반형

함정 1을 일반화한 경우다. **클라이언트 사이드 LB는 resolver가 준 멤버십이 최신일 때만 제대로 분산한다.** 파드 교체, 롤링 배포, 노드 드레인 등으로 IP가 바뀌었는데 클라이언트가 모르면 멤버십이 낡은(stale) 상태가 된다. 그러면 트래픽이 사라진 IP로 가서 에러가 나거나, 남아 있는 소수의 백엔드로 쏠린다. 롤링 배포 중에 특히 두드러진다. 해법은 함정 1과 같다. MAX_CONNECTION_AGE로 강제로 갱신하거나, push 기반인 xDS를 쓴다.

### 12.8.5 함정 5: 연결 폭증

round_robin은 **모든 백엔드에 연결**한다(12.5.2). 백엔드가 수백~수천 개라면 클라이언트마다 그만큼의 연결을 유지해야 한다. 클라이언트까지 많으면 서버 측 연결 수가 폭발적으로 늘어난다. 이럴 때는 다음 방법을 고려한다.

- (a) subsetting: 각 클라이언트가 백엔드의 부분집합에만 연결한다.
- (b) look-aside/xDS로 후보를 줄인다.
- (c) 처음부터 pick_first + L7 프록시 같은 다른 토폴로지를 쓴다.

round_robin은 공짜가 아니며 연결 비용을 치른다는 점을 기억하자.

함정들을 표 하나로 정리하면 다음과 같다.

| 함정 | 증상 | 근본 원인 | 처방 |
|------|------|-----------|------|
| 스케일아웃 무시 | 새 파드 노는데 기존 과부하 | resolver 갱신 안 됨 + 연결 살아있어 재해석 안 함 | MAX_CONNECTION_AGE, xDS |
| pick_first 오해 | 한 파드만 받음 | 기본이 pick_first | round_robin 명시 |
| ClusterIP 분산 기대 | VIP 하나로 L4 쏠림 | A 레코드가 VIP만 | headless service |
| 멤버십 지연 | 롤링 중 에러/쏠림 | stale resolver 결과 | 강제 재해석, push 기반 |
| 연결 폭증 | 연결 수 폭발 | round_robin이 전체 연결 | subsetting, 후보 축소 |

## 12.9 직접 만들어보기: 커스텀 resolver와 LB policy 등록

내장 플러그인으로 해결할 수 없는 요구 사항(특수한 서비스 디스커버리, 회사 자체 메타데이터 기반 분산 등)이 있다면 플러그인을 **직접 등록**할 수 있다. 전체 구현은 방대하므로, 어떤 인터페이스를 채워야 하는지 기본 구조만 살펴보자. 목적은 개념을 이해하는 것이다.

### 12.9.1 커스텀 resolver의 기본 구조 (Go)

resolver는 두 인터페이스를 구현한다. scheme을 등록하고 인스턴스를 만드는 `Builder`와, 재해석을 처리하는 `Resolver`다.

```go
package myresolver

import "google.golang.org/grpc/resolver"

// 1) Builder: scheme 등록 + resolver 인스턴스 생성
type myBuilder struct{}

func (b *myBuilder) Scheme() string { return "my" } // my:/// 를 처리

func (b *myBuilder) Build(
    target resolver.Target,
    cc resolver.ClientConn,        // 결과를 채널에 보고하는 통로
    opts resolver.BuildOptions,
) (resolver.Resolver, error) {
    r := &myResolver{target: target, cc: cc}
    r.start() // 최초 해석 + watch 시작
    return r, nil
}

// 2) Resolver: 재해석 처리
type myResolver struct {
    target resolver.Target
    cc     resolver.ClientConn
}

func (r *myResolver) start() {
    // 어딘가(컨피그서버/etcd/커스텀 디스커버리)에서 주소를 구해 온다
    addrs := []resolver.Address{
        {Addr: "10.0.0.1:50051"},
        {Addr: "10.0.0.2:50051"},
    }

    // service config(JSON)를 파싱해서 함께 보고 (round_robin 강제 등)
    sc := r.cc.ParseServiceConfig(`{"loadBalancingConfig":[{"round_robin":{}}]}`)

    // 핵심: 채널에 "이게 새 상태다"라고 보고. 이게 LB policy로 흘러간다.
    r.cc.UpdateState(resolver.State{
        Addresses:     addrs,
        ServiceConfig: sc,
    })
}

// LB policy가 "주소 다시 받고 싶다"고 할 때 호출됨
func (r *myResolver) ResolveNow(resolver.ResolveNowOptions) {
    r.start() // 재해석. 보통은 watch로 비동기 갱신을 권장.
}

func (r *myResolver) Close() { /* watch 정리 */ }

// 3) 프로세스 시작 시 전역 등록
func init() {
    resolver.Register(&myBuilder{})
}
```

이제 클라이언트가 `grpc.NewClient("my:///some-name", ...)`을 호출하면 scheme `my`에 따라 이 builder가 선택되고, 우리가 만든 resolver가 동작한다. 가장 중요한 줄은 `r.cc.UpdateState(...)`다. 12.2에서 말한 resolver의 출력(주소 + service config)을 채널로 밀어 넣는 지점이 바로 여기다.

### 12.9.2 커스텀 LB policy의 기본 구조 (개념)

LB policy도 비슷하게 `Builder`로 등록하며, 핵심은 두 콜백이다.

```text
   LB policy가 구현해야 하는 두 가지
   ─────────────────────────────────
   1. UpdateClientConnState(state):
        resolver가 준 주소 목록을 받아
        - 새 주소 → cc.NewSubConn(addr)로 subchannel 생성·연결
        - 사라진 주소 → 해당 subchannel 종료
        를 수행

   2. UpdateSubConnState(subConn, state):
        각 subchannel의 상태(IDLE/CONNECTING/READY/TRANSIENT_FAILURE)
        변화를 받아
        - "지금 보낼 수 있는 subchannel 집합"을 갱신하고
        - 새 picker를 만들어 cc.UpdateState(balancer.State{Picker: ...})로 보고

   그리고 Picker:
        Pick(info) (PickResult, error)
        → 매 RPC마다 호출. 어느 subConn으로 보낼지 반환.
          round_robin이면 여기서 원형 카운터를 한 칸 돌린다.
```

예를 들어 "round_robin이되, 짝수 시각에는 us-east만, 홀수 시각에는 전체로" 같은 회사 고유의 정책이 필요하다면, Picker의 `Pick` 로직과 subchannel 집합 관리만 바꾸면 된다. 실무에서 커스텀 LB를 직접 작성하는 일은 드물다. 하지만 **"LB policy = subchannel 집합 관리 + picker 제공"이라는 본질**을 이해하면 내장 정책들이 어떻게 동작하는지 모두 쉽게 이해할 수 있다.

### 12.9.3 다른 언어에서 대응하는 API

- **Java**: `NameResolverProvider`/`NameResolver`와 `LoadBalancerProvider`/`LoadBalancer`를 구현하고, SPI(`META-INF/services`)나 `NameResolverRegistry`로 등록한다. 정책은 `ManagedChannelBuilder.defaultLoadBalancingPolicy("round_robin")`이나 `defaultServiceConfig(...)`로 지정한다.
- **Python**: 채널 옵션 `grpc.lb_policy_name`이나 service config JSON(`grpc.service_config`)으로 지정한다. 커스텀 resolver는 C-core 플러그인 수준에서 만들어야 하므로 Go나 Java만큼 다루기 쉽지 않다.
- **C++/core**: 모든 언어의 기반인 gRPC Core에 resolver/LB 레지스트리가 있고, 위 언어들은 대개 이를 감싸서 사용한다.

언어마다 겉으로 드러나는 API는 달라도 **모델은 같다**. scheme이 resolver를 고르고, resolver가 주소와 service config를 내놓고, LB policy가 subchannel 집합과 picker를 제공한다. 이 공통 모델은 [[01 - gRPC란 무엇인가]]에서 강조한 "언어 중립적 설계"를 보여 주는 또 다른 예다.

## 12.10 종합 예제: 처음부터 끝까지 따라가기

지금까지 살펴본 내용을 하나의 흐름으로 이어 보자. K8s에서 `orders` 서비스를 round_robin으로 호출하는 클라이언트가 동작하는 전체 과정을 따라간다.

```proto
// orders.proto
syntax = "proto3";
package orders.v1;

service OrderService {
  rpc GetOrder(GetOrderRequest) returns (Order);
}

message GetOrderRequest { string order_id = 1; }
message Order {
  string order_id = 1;
  string status   = 2;
  int64  amount   = 3;
}
```

```go
// client.go
package main

import (
    "context"
    "log"
    "time"

    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials/insecure"
    orderspb "example.com/orders/v1"
)

const serviceConfig = `{
  "loadBalancingConfig": [ { "round_robin": {} } ],
  "methodConfig": [{
    "name": [{ "service": "orders.v1.OrderService" }],
    "timeout": "2s",
    "retryPolicy": {
      "maxAttempts": 3,
      "initialBackoff": "0.1s",
      "maxBackoff": "1s",
      "backoffMultiplier": 2.0,
      "retryableStatusCodes": ["UNAVAILABLE"]
    }
  }],
  "healthCheckConfig": { "serviceName": "orders.v1.OrderService" }
}`

func main() {
    // dns:/// + headless service "orders" → 모든 파드 IP를 받는다
    conn, err := grpc.NewClient(
        "dns:///orders.default.svc.cluster.local:50051",
        grpc.WithTransportCredentials(insecure.NewCredentials()),
        grpc.WithDefaultServiceConfig(serviceConfig),
    )
    if err != nil {
        log.Fatalf("dial: %v", err)
    }
    defer conn.Close()

    client := orderspb.NewOrderServiceClient(conn)

    // 여러 번 호출하면 round_robin으로 파드들에 고르게 분산된다
    for i := 0; i < 6; i++ {
        ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
        resp, err := client.GetOrder(ctx, &orderspb.GetOrderRequest{OrderId: "o-123"})
        cancel()
        if err != nil {
            log.Printf("call %d failed: %v", i, err)
            continue
        }
        log.Printf("call %d → status=%s (served by some pod)", i, resp.Status)
    }
}
```

이 코드가 실행될 때 내부에서 일어나는 일을 시간 순서로 보면 다음과 같다.

```text
   t=0   grpc.NewClient("dns:///orders...:50051", ...)
         - target 파싱: scheme="dns", endpoint="orders...:50051"
         - dns resolver builder 선택 → Build() 호출
         - default service config 적용: round_robin + 헬스체크 + 재시도

   t=1   dns resolver가 A/AAAA 조회
         → [10.244.1.5:50051, 10.244.2.7:50051, 10.244.3.9:50051]
         - cc.UpdateState({addrs, serviceConfig})

   t=2   round_robin LB policy가 상태 수신
         - 세 주소 모두에 NewSubConn → 연결 시작 (CONNECTING)
         - healthCheckConfig 켜져 있으니 각 subchannel에 Health/Watch 스트림 염

   t=3   subchannel들이 하나씩 READY로
         - 헬스체크도 SERVING 확인
         - ready 리스트 = [SC1, SC2, SC3]
         - round_robin picker 생성 → cc.UpdateState(picker)
         - 채널 상태 IDLE→READY (이제 RPC 가능)

   t=4+  GetOrder 호출 6번
         - call 0 → picker → SC1 (10.244.1.5)
         - call 1 → picker → SC2 (10.244.2.7)
         - call 2 → picker → SC3 (10.244.3.9)
         - call 3 → picker → SC1
         - call 4 → picker → SC2
         - call 5 → picker → SC3
         → 6번 호출이 3개 파드에 2번씩 고르게!

   (만약 t=4 시점에 SC2의 파드가 죽으면)
         - SC2: READY → TRANSIENT_FAILURE
         - round_robin이 ready 리스트에서 SC2 제외 → [SC1, SC3]
         - 호출은 SC1, SC3로만 순환 (에러 없이 자동 우회)
         - LB가 resolver에 ResolveNow → DNS 재조회로 교체 파드 발견 시도
```

이 타임라인에는 이 장에서 다룬 개념이 모두 들어 있다. target 파싱(12.1), DNS resolver의 주소와 config 출력(12.2, 12.3), round_robin의 subchannel 관리와 picker(12.5), 헬스 상태에 따른 제외(12.7), 재해석(12.2.3, 12.8)이 차례로 일어난다. 이 흐름을 머릿속에서 한 번 따라갈 수 있다면 이 장의 내용을 이해한 것이다.

## 12.11 디버깅: 지금 내 채널은 어디에 연결되어 있나

이름 해석과 LB 문제는 눈에 보이지 않아서 어렵다. 그래서 내부 상태를 드러내는 도구가 필수다. 자세한 내용은 [[14 - 관찰성과 디버깅 - Reflection grpcurl]]에서 다루고, 여기서는 이 장의 맥락에서 유용한 것만 소개한다.

- **channelz**: gRPC에 내장된 디버그 서비스다. 현재 채널이 가진 subchannel과 각 subchannel의 상태(READY/TRANSIENT_FAILURE), 대상 주소, 누적 RPC 수와 에러 수를 볼 수 있다. "round_robin이라는데 왜 한 곳으로만 가지?"를 진단할 때 channelz로 subchannel 목록을 보면 바로 원인을 알 수 있다(ready 상태가 1개뿐인지 확인한다).
- **환경변수 트레이싱**(Go): `GRPC_GO_LOG_SEVERITY_LEVEL=info`, `GRPC_GO_LOG_VERBOSITY_LEVEL=2`로 resolver/balancer 로그를 켜면, DNS가 어떤 주소를 주었고 LB가 어떤 subchannel을 만들었는지가 로그에 남는다. C-core 계열에서는 `GRPC_TRACE=resolver,round_robin,pick_first`와 `GRPC_VERBOSITY=DEBUG`를 쓴다.
- **dig / nslookup**: 문제가 의심스러우면 DNS부터 확인하라. `dig +short orders.default.svc.cluster.local`로 DNS가 실제로 IP를 몇 개 주는지 직접 확인한다. 하나만 나온다면 headless service가 아니라 ClusterIP service를 쓰고 있는 것이다(함정 3).

```bash
# DNS가 정말 여러 파드 IP를 주는지 확인 (클러스터 내부에서)
dig +short orders.default.svc.cluster.local
# 기대: 여러 줄의 파드 IP. 한 줄(VIP)만 나오면 headless가 아님!

# resolver/LB 내부 동작 로깅 (Go 클라이언트)
GRPC_GO_LOG_SEVERITY_LEVEL=info \
GRPC_GO_LOG_VERBOSITY_LEVEL=2 \
  ./client
```

14장(관찰성과 디버깅)에서 다루는 `grpcurl`은 LB를 거의 쓰지 않지만(보통 단일 타깃에 연결한다), 백엔드마다 서버가 실제로 응답하는지 직접 요청을 보내 확인하는 데 유용하다.

## 12.12 한 발 물러서서: 이 장을 관통하는 설계 철학

마지막으로 전체 그림을 다시 정리해 보자. 이 장에서 다룬 세부 사항은 모두 **하나의 긴장 관계**에서 나온다.

```text
   HTTP/2의 미덕              ↔        분산의 요구
   ─────────────                       ──────────
   적은 수의                            많은 백엔드에
   롱리브드 멀티플렉싱 연결    vs       고르게 퍼뜨리기
   (연결 비용↓, HOL 회피)              (한 곳 쏠림 방지)
```

이 긴장을 해소하는 여러 방식을 차례로 늘어놓으면, 그것이 곧 이 장의 목차였다.

| 접근 | 어디서 분산? | 똑똑함의 위치 | 트레이드오프 |
|------|-------------|--------------|--------------|
| L4 프록시 | 연결 계층 | 인프라 | 단순하지만 HTTP/2에서 쏠림 |
| L7 프록시(Envoy) | 요청 계층, 프록시에서 | 프록시 | 정확하지만 추가 홉·운영비 |
| 클라 사이드 + DNS | 요청 계층, 클라에서 | 클라이언트 라이브러리 | 빠르지만 멤버십 갱신·헬스 표현 한계 |
| 클라 사이드 + xDS(proxyless) | 요청 계층, 클라에서 | 클라 + 중앙 컨트롤 플레인 | 강력하지만 컨트롤 플레인 의존·복잡 |

gRPC의 **기본** 구성은 "클라이언트 사이드 + DNS + pick_first(또는 round_robin)"다. 이는 단순한 환경에 잘 맞도록 의도적으로 보수적으로 정한 출발점이다. 그리고 헬스 반영, 가중치, 지역성, 즉각 갱신, 카나리처럼 요구가 커지면 **xDS로 점진적으로 발전**할 수 있는 길을 열어 두었다.

resolver와 LB policy를 플러그인으로 추상화한 이유가 바로 이것이다. **같은 채널 API를 유지하면서, 그 아래의 디스커버리·분산 메커니즘만 교체할 수 있게 하려는 것이다.**

이처럼 추상화를 통해 발전 가능성을 열어 두는 방식은 1장(gRPC란 무엇인가)에서 본 gRPC의 일관된 철학이다. 또한 [[17 - 실전 - proto 관리와 하위호환성]]에서 다룰 "인터페이스를 안정적으로 유지하면서 구현을 발전시킨다"는 원칙을 인프라 수준에 적용한 것이기도 하다.
