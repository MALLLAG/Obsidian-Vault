## 1. 들어가며: "함수를 호출하듯 네트워크 너머를 호출한다"는 오래된 꿈

프로그래밍을 처음 배울 때는 함수 호출을 당연하게 여긴다.

```go
total := order.CalculateTotal(items)
```

이 한 줄에는 많은 가정이 들어 있다. `CalculateTotal`은 **반드시** 실행된다. 호출은 나노초 단위로 **즉시** 반환된다. 인자 `items`는 **손실 없이** 전달된다. 호출하는 쪽과 호출받는 쪽은 **같은 메모리, 같은 언어, 같은 타입 시스템**을 공유한다. 실패하면 명확한 예외(panic, exception)로 드러난다. 한 프로세스 안에서는 이 다섯 가지 가정이 거의 비용 없이 성립한다.

분산 시스템의 역사는 이 편리한 함수 호출의 추상화를 **네트워크 너머로 확장하려는 시도와, 그 시도가 반드시 부딪히는 물리 법칙 사이의 긴 줄다리기**였다. RPC(Remote Procedure Call, 원격 프로시저 호출)의 핵심 아이디어는 단순하고 매력적이다.

> "원격 서버의 함수를 로컬 함수처럼 호출하자. 중간에 네트워크가 있다는 사실은 프레임워크가 감춰 주자."

이 문장에는 RPC의 장점과 함정이 함께 들어 있다. 장점은 **개발자 경험**이다. 개발자는 소켓을 열고, 바이트를 직렬화하고, 패킷 경계를 처리하고, 다시 조립하는 저수준 작업에서 벗어나 도메인 로직(`주문 합계 계산`, `재고 차감`)에만 집중할 수 있다.

함정은 **감춘다는 사실 자체**이다. 네트워크는 로컬 메모리와 다르다. 패킷은 유실되고, 지연은 마이크로초가 아니라 밀리초나 초 단위이며, 서버는 호출 도중에 죽고, 같은 요청이 두 번 도착하기도 한다. RPC가 네트워크를 잘 감춰 줄수록 개발자는 이런 현실을 잊은 채 코드를 작성하게 된다.

따라서 gRPC를 제대로 이해하려면 **네트워크를 감추려는 유혹과 현실을 드러내야 할 필요 사이에서 gRPC가 어디에 선을 그었는지**를 이해해야 한다. 결론부터 말하면, gRPC는 함수 호출의 *편리한 문법*은 가져오되 *분산 환경의 현실*(타임아웃, 취소, 부분 실패, 백프레셔)은 감추지 않았다. 오히려 이것들을 API의 1급 개념으로 끌어올렸다. 이런 균형이 어디서 왔는지 알려면 먼저 gRPC가 기반으로 삼은 40년에 걸친 RPC의 계보를 살펴봐야 한다.

```text
        "로컬 함수처럼 편하게"  ←──────────────→  "분산의 현실을 인정하라"
              (추상의 유혹)                          (물리 법칙)
                  │                                      │
   Sun RPC ─ CORBA ─ RMI ─ DCOM ─ SOAP ─ Thrift ─────────┤
   (대체로 '편함'에 베팅, 현실에 데임)                    │
                                                          │
   gRPC: 문법은 함수처럼, 의미론은 분산을 정직하게 ────────┘
```

## 2. RPC의 역사적 계보: 40년의 시행착오

gRPC는 갑자기 등장한 기술이 아니다. 적어도 다섯 세대에 걸친 RPC 실험에서 **쌓인 교훈**을 바탕으로 만들어졌다. 각 세대가 무엇을 해결했고 무엇에 실패했는지 따라가 보면, gRPC의 설계 결정 하나하나가 앞선 기술의 실패에 대한 의도적인 대응이라는 것을 알 수 있다.

### 2.1 1980년대 초: Sun RPC / ONC RPC와 XDR

현대적 의미의 RPC가 산업계에 대규모로 자리 잡은 첫 사례는 **Sun Microsystems의 Sun RPC**이다. 나중에 ONC RPC(Open Network Computing RPC)라는 이름으로 표준화되었다(RFC 1057/1831/5531). 1980년대 중반 Sun은 네트워크 파일 시스템인 **NFS**를 만들면서 그 기반으로 RPC가 필요했다. 여기서 두 가지 중요한 아이디어가 나왔다.

1. **IDL(Interface Definition Language)의 분리**: `.x` 파일에 인터페이스(프로시저 시그니처와 데이터 구조)를 *특정 언어에 의존하지 않는 방식으로* 기술하면, `rpcgen` 컴파일러가 클라이언트 **스텁(stub)** 과 서버 **스켈레톤(skeleton)** 을 자동으로 생성한다. 직렬화 코드를 손으로 작성하지 않는다는 이 아이디어는 이후 거의 모든 RPC의 기본 구조가 되었다. gRPC의 `.proto` + `protoc`는 이 패턴을 직접 계승한 것이다.
2. **XDR(External Data Representation)**: 서로 다른 머신(빅엔디안과 리틀엔디안, 워드 크기가 다른 CPU)이 데이터를 손실 없이 주고받으려면 **표준 바이트 표현**이 필요하다. XDR은 "와이어 위에서는 모두가 합의한 한 가지 형식을 쓴다"는 방식으로, 오늘날 Protocol Buffers 와이어 포맷이 해결하는 것과 같은 문제를 이미 1980년대에 해결했다.

Sun RPC가 해결한 것은 **언어와 플랫폼에 중립적인 인터페이스 계약과 코드 생성**이다. 한계도 있었다. 절차적이어서 객체 개념이 없었고, C 중심이었으며, 전송 방식이 단순했다(주로 UDP/TCP 위의 자체 포맷). 인증, 스트리밍, 버전 관리 같은 현대적 요구도 거의 지원하지 못했다.

### 2.2 Apollo NCS와 DCE RPC: 표준화의 첫 번째 큰 시도

비슷한 시기에 Apollo Computer는 **NCS(Network Computing System)** 와 그 IDL인 **NIDL**을 내놓았다. NCS는 이후 OSF(Open Software Foundation)의 **DCE(Distributed Computing Environment) RPC**로 흡수되었다. 1990년대 초의 DCE RPC는 오랫동안 쓰이게 될 개념들을 정립했다.

- **UUID(Universally Unique Identifier)** 로 인터페이스와 객체를 식별했다. 오늘날 우리가 쓰는 UUID는 여기서 표준화되었다.
- 인터페이스 **버전 번호**를 1급 개념으로 다루었다. 하위 호환성 문제를 일찍부터 의식한 것이다(gRPC가 이 문제를 어떻게 다루는지는 [[17 - 실전 - proto 관리와 하위호환성]]에서 살펴본다).
- **Microsoft RPC(MSRPC)** 가 DCE RPC를 기반으로 만들어졌고, 이것이 Windows의 DCOM으로 이어졌다.

DCE RPC가 해결한 것은 **엔터프라이즈급 식별, 버전, 보안 모델**이다. 반면 무겁고 구현이 복잡했으며, 특정 벤더 생태계에 묶이는 경향이 있었다.

### 2.3 CORBA와 IIOP: 분산 "객체"의 전성기와 몰락

1990년대는 객체지향(OOP)의 시대였다. 자연스럽게 원격 *프로시저*를 넘어 원격 *객체*를 호출하고 싶다는 요구가 생겼다. OMG(Object Management Group)가 1991년에 발표한 **CORBA(Common Object Request Broker Architecture)** 는 이런 목표를 가장 크게 추구한 기술이다.

CORBA의 핵심 구성은 다음과 같다.

```text
   클라이언트 객체                         서버 객체(Servant)
        │                                      │
     [Stub]                                 [Skeleton]
        │                                      │
        └────────► ORB ◄── IIOP ──► ORB ◄──────┘
              (Object Request Broker)
        - IDL로 인터페이스 정의
        - ORB가 원격 객체 참조(IOR)를 들고 메시지 라우팅
        - IIOP(Internet Inter-ORB Protocol)로 ORB 간 통신
```

CORBA는 **언어 중립 IDL**, **ORB(Object Request Broker)** 라는 미들웨어 버스, 그리고 서로 다른 벤더의 ORB가 상호 운용할 수 있게 하는 **IIOP**(CORBA 2.0, 1996)를 제시했다. 목표는 거대했다. C++ 객체가 자바 객체의 메서드를 호출하고, 그 자바 객체가 다시 코볼 객체의 메서드를 투명하게 호출하는 세상이었다.

그러나 CORBA는 실패했다. 그 실패 원인은 gRPC 설계자들에게 **피해야 할 사례를 모은 교과서**가 되었다.

| CORBA의 문제 | 결과 | gRPC가 취한 반대 선택 |
|---|---|---|
| 사양이 거대하고 모호함 | 벤더마다 ORB 구현이 조금씩 달라 상호 운용에 실패 | 명세를 작게 유지하고, HTTP/2라는 기존 표준 위에 구축 |
| 분산 객체 모델 자체 | 원격 객체의 생명주기, GC, 상태 공유를 다루기가 매우 어려움 | **객체가 아니라 무상태 메서드 호출**(서비스/메서드)로 회귀 |
| IIOP가 방화벽과 프록시를 통과하기 어려움 | 인터넷 환경에서 쓰기 곤란 | **HTTP/2** 위에 올려 기존 인프라(LB, 프록시)와 잘 맞게 함 |
| 가파른 학습 곡선 | 개발자들이 외면 | `.proto` 파일 하나로 시작하는 단순함 |

CORBA가 남긴 가장 중요한 교훈은 **원격 객체라는 개념 자체가 환상**이라는 것이다. 객체에는 *상태*와 *정체성(identity)*, *생명주기*가 있다. 이것을 네트워크 너머로 투명하게 공유하려고 하면 분산 가비지 컬렉션, 객체 마이그레이션, 상태 동기화처럼 풀기 어려운 문제가 한꺼번에 생긴다.

gRPC는 이 교훈을 받아들여 **원격 객체에서 원격 *메서드 호출*로 의식적으로 범위를 좁혔다.** gRPC 서비스는 상태를 공유하는 객체라기보다, 입력 메시지를 받아 출력 메시지를 돌려주는 *무상태 함수의 모음*에 가깝다. 상태는 서버 내부에서 관리하며 와이어 모델에는 드러나지 않는다.

### 2.4 Java RMI와 Microsoft DCOM: 특정 언어와 플랫폼에 갇히다

CORBA가 지나치게 보편적이려다 실패했다면, 같은 시기의 두 강자는 반대 방향의 함정에 빠졌다. **특정 언어나 플랫폼에 갇힌 것이다.**

- **Java RMI(Remote Method Invocation)**(JDK 1.1, 1997): 자바 객체가 다른 JVM에 있는 자바 객체의 메서드를 호출한다. `java.io.Serializable` 기반 객체 직렬화, 스텁/스켈레톤에 **분산 가비지 컬렉션**까지 제공했다. 잘 동작했지만 **자바끼리만** 통신할 수 있었다. 직렬화 포맷이 자바 전용이라 여러 언어를 함께 쓰는(폴리글랏) 환경에는 맞지 않았고, 자바 직렬화는 나중에 심각한 보안 취약점의 원인이 되었다.
- **Microsoft DCOM(Distributed COM)**(1996): MSRPC 위에서 COM 객체를 분산 환경으로 확장했다. Windows 생태계에서는 강력했지만 본질적으로 **Windows에 종속**되었고, 인터넷 환경과도 잘 맞지 않았다.

두 기술의 공통 교훈은 **RPC가 실제로 가치를 가지려면 언어와 플랫폼의 경계를 자유롭게 넘을 수 있어야 한다**는 것이다. 자바 서비스가 Go 서비스를 호출하고, Python 데이터 파이프라인이 Kotlin 서비스를 호출하는 폴리글랏 마이크로서비스 환경에서 "자바끼리만" 또는 "Windows끼리만"은 치명적인 제약이다. gRPC는 처음부터 **언어 중립 IDL과 언어별 코드 생성**을 핵심으로 삼아 이 제약을 없앴다([[06 - 코드 생성과 protoc 툴체인]] 참고).

### 2.5 분산 객체의 환상과 "분산 컴퓨팅의 8가지 오류"

앞의 실패들에는 공통된 근본 오류가 하나 있다. **원격 호출을 로컬 호출과 똑같이 다루려는 욕심이다.** 1994년 Sun의 L. Peter Deutsch는 이 욕심이 불러오는 문제를 **"분산 컴퓨팅의 8가지 오류(8 Fallacies of Distributed Computing)"** 로 정리했다(8번째 항목은 이후 James Gosling이 추가했다). 분산 시스템을 처음 다루는 엔지니어가 *암묵적으로 참이라고 가정하지만 실제로는 거짓인* 명제들이다.

| # | 오류 (틀린 가정) | 현실 | gRPC가 이를 다루는 챕터 |
|---|---|---|---|
| 1 | 네트워크는 신뢰할 수 있다 | 패킷은 유실되고 연결은 끊긴다 | [[13 - 안정성 - Retry Health Check Keepalive]] |
| 2 | 지연(latency)은 0이다 | RTT는 ms~수백 ms | [[10 - Deadline 취소 타임아웃]] |
| 3 | 대역폭은 무한하다 | 유한하며, 직렬화 크기가 중요 | [[03 - Protocol Buffers 2 - 인코딩과 와이어 포맷]] |
| 4 | 네트워크는 안전하다 | 도청·변조·위장 위협이 늘 있음 | [[11 - 보안 - TLS mTLS 인증]] |
| 5 | 토폴로지는 변하지 않는다 | 인스턴스는 생겼다 사라진다 | [[12 - 이름 해석과 로드밸런싱]] |
| 6 | 관리자는 한 명이다 | 여러 팀과 조직이 운영 | [[14 - 관찰성과 디버깅 - Reflection grpcurl]] |
| 7 | 전송 비용은 0이다 | 직렬화/역직렬화 비용과 인프라 비용이 있음 | [[15 - 성능과 Flow Control 백프레셔]] |
| 8 | 네트워크는 균질하다 | 다양한 OS·언어·하드웨어 | 6장(코드 생성과 protoc 툴체인) |

이 대응 관계는 우연이 아니다. **gRPC의 기능 목록은 사실상 8가지 오류에 대한 체계적인 방어책으로 읽을 수 있다.** 과거의 RPC들은 이런 오류를 추상화 뒤에 감추려 했고, 그 결과 개발자가 방심하게 만들었다. gRPC는 반대로 **각 오류를 명시적인 API로 드러낸다.**

예를 들어 데드라인을 지정하지 않으면 호출이 끝없이 대기할 수 있다는 사실을 gRPC는 감추지 않고 `context`/`Deadline`으로 개발자에게 직접 제시한다. 이 점이 1세대 RPC와 gRPC를 가르는 철학적 분기점이다.

### 2.6 2000년대 초: XML-RPC, SOAP, 그리고 WS-*의 무게

2000년대에 들어서며 흐름이 바뀌었다. 인터넷과 방화벽, HTTP가 표준이 되자 "이진 프로토콜로 방화벽과 씨름하지 말고, 어디서나 통과되는 HTTP와 사람이 읽을 수 있는 XML 위에 RPC를 올리자"는 움직임이 생겼다.

- **XML-RPC**(1998, Dave Winer): 매우 단순하다. HTTP POST 본문에 `<methodCall>` XML을 담고, 응답에는 `<methodResponse>`를 담는다. 장점은 단순함이고, 약점은 장황함과 빈약한 타입 시스템이다.
- **SOAP**(원래 이름은 Simple Object Access Protocol, 2000년 무렵): XML-RPC를 엔터프라이즈급으로 확장했다. 인터페이스 정의용 **WSDL**과 함께 WS-Security, WS-Addressing, WS-ReliableMessaging 같은 **WS-\* 스택**이 뒤따랐다.

SOAP이 걸어간 길은 시사하는 바가 크다. SOAP은 엄격한 계약(WSDL)과 코드 생성이라는, gRPC와 비슷한 올바른 방향을 잡고 있었다. 그러나 **XML의 장황함**과 **WS-\* 표준의 폭발적인 복잡성**이 발목을 잡았다. 단순한 호출 하나에도 수 KB짜리 XML 봉투(envelope), 네임스페이스, 스키마 검증이 따라붙었다. 개발자들은 "이렇게까지 복잡해야 하는가"라고 물었고, 이 질문이 뒤에서 볼 REST의 부상으로 이어졌다.

gRPC는 SOAP의 교훈을 다음과 같이 받아들였다. **엄격한 계약과 코드 생성은 옳다. 그러나 직렬화 포맷은 사람이 읽는 장황한 텍스트(XML)가 아니라 작고 빠른 이진 포맷(Protocol Buffers)이어야 하고, 표준은 거대한 위원회가 만든 것이 아니라 작고 실용적이어야 한다.**

### 2.7 Apache Thrift(2007): gRPC 바로 앞의 가장 가까운 선배

gRPC를 이해할 때 빼놓을 수 없는 직전 선배가 **Apache Thrift**이다. 2007년 Facebook의 Mark Slee 등이 만들었고, 이후 Apache 재단에 기증되었다. Thrift는 gRPC가 8년 뒤에 하게 될 일의 대부분을 이미 해냈다.

- 언어 중립 **IDL**(`.thrift` 파일)로 서비스와 구조체를 정의한다.
- 수많은 언어로 **코드를 생성**한다(C++, Java, Python, PHP, Ruby, Go ...).
- **직렬화 프로토콜을 교체**할 수 있다(Binary, Compact, JSON).
- **전송(transport) 방식을 교체**할 수 있다(socket, framed, HTTP).

Thrift는 여러 언어를 쓰는 사내 RPC로서 훌륭하게 동작했다. 그렇다면 왜 gRPC가 또 필요했을까? 차이는 주로 **전송 계층에 대한 목표**에 있다. Thrift가 나온 2007년에는 아직 **HTTP/2가 없었다**(SPDY는 2009년, HTTP/2 RFC 7540은 2015년에 나왔다). Thrift의 전송은 대체로 단순한 TCP 스트림이어서 **단일 연결 위의 다중 스트림 멀티플렉싱, 헤더 압축, 서버 스트리밍, 흐름 제어** 같은 현대적 기능이 부족했다.

gRPC는 Thrift가 잘한 IDL, 코드 생성, 다언어 지원은 이어받으면서, 마침 성숙해진 **HTTP/2를 전송 계층으로 채택**해 멀티플렉싱과 양방향 스트리밍을 1급 기능으로 끌어올렸다([[04 - HTTP2 깊이 보기 - 전송 계층]], [[05 - 통신의 4가지 방식 - Unary와 Streaming]] 참고).

### 2.8 REST의 부상: RPC의 일시적 패배와 그 빈틈

2000년 Roy Fielding이 박사 논문에서 정의한 **REST(REpresentational State Transfer)** 는 2000년대부터 2010년대까지 웹 API의 주도권을 잡았다. REST의 성공은 SOAP/WS-\* 같은 RPC의 복잡성에 대한 반작용이었고, 동시에 HTTP 자체의 의미론을 영리하게 재사용한 결과였다.

REST의 핵심은 **리소스(명사) 중심**이라는 점이다. `/orders/42`라는 URL은 "42번 주문"이라는 *리소스*를 가리키고, HTTP 동사(GET/POST/PUT/DELETE)가 그 리소스에 대한 표준 동작을 나타낸다. 여기에 사람이 읽을 수 있고 어디서나 파싱할 수 있는 텍스트 포맷인 JSON이 결합하면서, REST는 **낮은 진입 장벽**과 함께 **브라우저, 캐시, 프록시 같은 기존 웹 인프라와 완벽하게 호환되는 장점**을 얻었다.

그러나 REST에도 빈틈이 있었고, 바로 그 자리를 gRPC가 채운다.

- **느슨한 계약**: REST는 본질적으로 관례(convention)이지 강제되는 계약이 아니다. 어떤 엔드포인트가 어떤 필드를 어떤 타입으로 받는지는 문서나 OpenAPI에 의존하며, 컴파일 시점에 보장되지 않는다.
- **텍스트 직렬화 비용**: JSON은 파싱이 느리고 크기가 크다. 서비스 사이에 초당 수십만 건의 호출이 오가는 내부망에서는 이 오버헤드가 쌓인다(3장 Protocol Buffers 2 참고).
- **어색한 스트리밍**: REST/HTTP1.1 위에서 양방향 실시간 스트리밍을 구현하기는 부자연스럽다(SSE, 롱폴링, WebSocket 같은 별도 기법이 필요하다).
- **N+1 문제와 과다/과소 페칭**: 리소스 중심이어서 한 화면을 그리는 데 여러 번 왕복하기 쉽다.

정리하면 2010년대 초 업계 상황은 다음과 같았다. **외부 공개 API나 브라우저를 대상으로 할 때는 REST가 잘 맞았지만, 폴리글랏 마이크로서비스가 내부망에서 낮은 지연과 높은 처리량으로 빈번하게 통신하는 영역에서는 REST가 최선이 아니었다.** 구글은 이 내부망의 빈틈을 이미 사내에서 **Stubby**라는 자체 도구로 메우고 있었다.

## 3. Stubby에서 gRPC로: 구글 내부의 이야기

구글은 2000년대 초부터 사내의 모든 서비스를 연결하는 **Stubby**라는 RPC 프레임워크를 운영해 왔다. Stubby는 구글 데이터센터에서 **초당 약 100억 건(10^10) 규모**의 호출을 처리했다(gRPC 공개 당시 구글이 밝힌 수치). 사실상 구글 인프라의 혈관 역할을 한 셈이다.

Stubby는 직렬화에 **Protocol Buffers**를 사용했다. 프로토콜 버퍼 역시 구글이 2001년 무렵부터 내부에서 만들었고, 2008년에 오픈소스로 공개되었다. Stubby에는 로드밸런싱, 인증, 데드라인, 추적 같은 운영상의 요구가 깊이 반영되어 있었다.

그렇다면 **세계 최대 규모로 검증된 Stubby가 이미 있는데, 왜 2015년에 gRPC를 새로 만들었을까?** 이유는 기능이 부족해서가 아니라 **개방성과 표준이 없었기 때문**이다.

1. **사내 인프라와의 강한 결합**: Stubby는 구글 내부의 네이밍, 인증, 부하 분산 인프라에 강하게 묶여 있어서 그대로는 외부에 공개할 수 없었다. 표준 위에 만들어진 것이 아니었기 때문이다.
2. **표준 전송이 없다는 한계**: Stubby는 자체 프로토콜 위에서 동작했다. 그사이 업계 표준으로 **HTTP/2**(SPDY의 후속, RFC 7540, 2015년 5월)가 성숙했다. HTTP/2는 단일 연결 멀티플렉싱, 헤더 압축, 스트리밍을 표준으로 제공한다. Stubby가 사내에서 자체 구현하던 기능을 이제 누구나 *표준*으로 쓸 수 있게 된 것이다.
3. **오픈소스 생태계라는 시대 흐름**: 마이크로서비스와 클라우드 네이티브가 확산되면서, 외부에서도 "구글이 내부에서 쓰는 그 RPC"를 쓰고 싶어 했다.

그래서 구글은 **Stubby의 개념과 운영 노하우를 HTTP/2라는 개방 표준 위에 다시 구현**하기로 했다. 그것이 **gRPC**이다. gRPC는 2015년 2월에 공개되었고, 2017년 3월 **CNCF(Cloud Native Computing Foundation)** 에 기증되었다. 이후 인큐베이팅을 거쳐 클라우드 네이티브 스택의 일원으로 성숙했고, Kubernetes, Envoy 등과 함께 표준 통신 계층으로 자리 잡았다.

한 줄로 정리하면 **gRPC는 "Stubby의 검증된 RPC 모델"에 "HTTP/2라는 개방 표준 전송"과 "오픈소스·다언어 생태계"를 더한 것이다.** Stubby가 구글 안에서만 쓰던 비공개 도구였다면, gRPC는 이것을 누구나 쓸 수 있는 표준 부품으로 다시 조립한 결과이다.

```text
   2001~      구글 내부
   ┌──────────────────────────────┐
   │ Protocol Buffers (직렬화)     │  ← 2008년 오픈소스
   │ Stubby (RPC, 사내 전송)       │  ← 비공개, 인프라 결합
   └──────────────┬───────────────┘
                  │  "표준 위에 다시 짓자"
                  ▼
   2015  gRPC = Stubby의 개념 + HTTP/2 + 오픈소스
                  │
   2017  CNCF 기증 → 클라우드 네이티브 표준 통신 계층
```

## 4. 이름에 담긴 농담과 의미

**gRPC**라는 이름은 공식적으로 **재귀 약어(recursive acronym)** 이다. 풀어 쓰면 **"gRPC Remote Procedure Calls"** 이고, 약어 안에 자기 자신(g**RPC**)이 들어 있다. GNU("GNU's Not Unix")와 같은 해커 전통의 농담이다.

더 재미있는 부분은 맨 앞의 소문자 **g**이다. gRPC 팀은 **마이너 릴리스마다 g가 무엇을 뜻하는지를 매번 다르게 정하는** 장난을 이어 왔다. 저장소에는 버전별로 g의 뜻을 모아 둔 문서(`g_stands_for`)가 있다. 예를 들면 다음과 같다.

| 버전 | g가 뜻하는 것 | 비고 |
|---|---|---|
| 1.0 | **g**RPC | 그냥 자기 자신 |
| 1.1 | **g**ood | |
| 1.2 | **g**reen | |
| ... | ... | 매 릴리스마다 새 단어 |

(전체 목록은 버전마다 바뀌므로 정확한 내용은 공식 저장소를 기준으로 삼는다. 여기서 중요한 것은 정확한 단어가 아니라 **이 장난이 보여 주는 문화**이다. gRPC는 거대한 위원회가 만든 표준이 아니라, 빠르게 릴리스하면서도 유머를 잃지 않는 실용적인 오픈소스 프로젝트라는 점이다.)

이름에서 알 수 있는 사실은 두 가지이다.

- **"Remote Procedure Calls"**: gRPC는 자신을 *프로시저(절차/함수) 호출*로 정의한다. REST 같은 *리소스*도, CORBA 같은 *객체*도 아니다. 이 단어 선택은 6절에서 다룰 RPC와 REST의 철학 비교로 바로 이어진다.
- **재귀 약어와 g 장난**: 진지한 인프라이지만 권위적이지 않고, 실용과 유머를 지향한다는 정체성을 보여 준다.

## 5. gRPC의 네 가지 기둥

이제 gRPC를 받치는 **네 개의 기둥**을 정리해 보자. 이 책의 나머지 16개 챕터는 사실상 이 네 기둥을 하나씩 확대해서 살펴보는 작업이다. 먼저 그림으로 전체 구조를 보자.

```text
        ┌───────────────────────────────────────────────────────┐
        │                      gRPC                              │
        ├───────────────┬───────────────┬───────────────────────┤
        │  기둥 1        │  기둥 2        │  기둥 3                │
        │  IDL+직렬화    │  전송          │  다언어 코드 생성       │
        │  Protocol      │  HTTP/2        │  protoc 툴체인          │
        │  Buffers       │  (RFC 7540/    │  (Go/Java/Py/C++/...)  │
        │                │   9113)        │                        │
        ├───────────────┴───────────────┴───────────────────────┤
        │  기둥 4: 교체 가능한(pluggable) 런타임                  │
        │  인증 · 이름해석 · 로드밸런싱 · 재시도 · 인터셉터 ...    │
        └───────────────────────────────────────────────────────┘
```

### 5.1 기둥 1: IDL과 직렬화(Protocol Buffers)

gRPC의 **계약(contract)** 은 `.proto` 파일에 작성한다. 이때 `.proto`는 두 가지 역할을 동시에 한다.

1. **IDL(인터페이스 정의 언어)**: 어떤 *서비스*에 어떤 *메서드*가 있고, 각 메서드가 어떤 *요청/응답 메시지*를 주고받는지를 특정 언어에 의존하지 않는 방식으로 선언한다.
2. **직렬화 스키마**: 그 메시지가 와이어 위에서 어떤 이진 바이트로 인코딩되는지를 정한다.

가장 작은 예는 다음과 같다.

```proto
syntax = "proto3";

package order.v1;

// 주문 서비스: 무엇을 할 수 있는지(동사)를 선언한다
service OrderService {
  // 주문 하나를 조회하는 단순(unary) 호출
  rpc GetOrder(GetOrderRequest) returns (Order);
}

// 메시지: 무엇을 주고받는지(데이터 모양)를 선언한다
message GetOrderRequest {
  string order_id = 1;   // 필드 번호 1
}

message Order {
  string order_id = 1;
  string item      = 2;
  int32  quantity  = 3;
  int64  total     = 4;  // 통화 최소단위(예: 원). 부동소수 금지!
}
```

여기서 중요한 점은 두 가지이다.

- **강한 타입 계약**: `GetOrder`는 *반드시* `GetOrderRequest`를 받아 `Order`를 돌려준다. 클라이언트와 서버는 이 계약을 *컴파일 시점에* 공유한다. REST에서 "이 엔드포인트가 어떤 필드를 받지?"를 문서로 확인해야 했던 불확실성이 사라진다.
- **필드 번호(tag)**: `order_id = 1`의 `1`은 변수 이름이 아니라 **와이어 위에서 쓰이는 식별자**이다. 이 번호가 직렬화의 핵심이며, *이름이 바뀌어도 번호만 유지하면 하위 호환성이 유지*되는 것도 이 번호 덕분이다.

메시지, 열거형, oneof, map, 중첩 같은 문법은 [[02 - Protocol Buffers 1 - 문법과 타입 시스템]]에서, 그 바이트가 어떻게 인코딩되는지(varint, zigzag, 와이어 타입)는 3장(Protocol Buffers 2)에서 자세히 다룬다. 계약을 바꿀 때 무엇이 안전하고 무엇이 심각한 문제를 일으키는지는 17장(proto 관리와 하위호환성)에서 다룬다.

**왜 텍스트(JSON)가 아니라 이진 포맷(Protocol Buffers)을 쓸까?** 이유는 세 가지이다.

- **크기**: 필드 이름을 매번 보내지 않고 작은 정수 태그만 보내므로 페이로드가 훨씬 작다.
- **속도**: 파싱이 문자열 스캔이 아니라 바이트 시프트이므로 빠르다.
- **스키마 진화**: 필드 번호를 기준으로 하므로 안전하게 진화시키는 규칙이 명확하다.

대가는 **사람이 눈으로 읽을 수 없다**는 점인데, 이는 14장(관찰성과 디버깅)에서 다루는 리플렉션과 grpcurl로 보완한다.

### 5.2 기둥 2: 전송(HTTP/2)

gRPC는 **HTTP/2**(RFC 7540, 개정판 RFC 9113) 위에서 동작한다. 이것은 단순한 구현상의 선택이 아니라 gRPC를 과거의 RPC들과 구분하는 핵심이다. HTTP/2가 gRPC에 제공하는 것은 다음과 같다.

| HTTP/2 기능 | gRPC에 주는 의미 |
|---|---|
| **스트림 멀티플렉싱** | 하나의 TCP 연결 위에서 수많은 RPC가 동시에 오간다. 호출마다 새 소켓을 열 필요가 없다(HTTP/1.1의 head-of-line blocking을 피한다). |
| **양방향 스트리밍** | 클라이언트와 서버가 같은 스트림에서 메시지를 *계속* 주고받을 수 있다. 4가지 통신 방식의 토대가 된다(5장 통신의 4가지 방식 참고). |
| **헤더 압축(HPACK)** | 메타데이터와 헤더를 압축해 오버헤드를 줄인다([[08 - 메타데이터와 인터셉터]] 참고). |
| **흐름 제어(flow control)** | 스트림 단위와 연결 단위의 윈도로 백프레셔를 표준으로 제공한다(15장 성능과 Flow Control 참고). |
| **바이너리 프레이밍** | 모든 통신이 정해진 형식의 *프레임* 단위로 이루어지므로 파싱이 명확하고 효율적이다. |

> [!note] 정밀한 단서
> HTTP/2의 멀티플렉싱은 HTTP/1.1 *애플리케이션 계층*의 head-of-line blocking을 없앤다. 그러나 모든 스트림이 단 하나의 TCP 연결을 공유하므로, TCP 세그먼트 하나가 유실되면 그 연결의 *모든* 스트림이 재전송을 기다리며 함께 멈춘다. 이 **TCP 계층의 head-of-line blocking**은 여전히 남는다.
>
> 이 마지막 문제까지 없애려면 전송을 UDP 기반 QUIC으로 바꾼 HTTP/3가 필요하다. gRPC는 HTTP/2를 1차 전송으로 삼는다. 이 한계와 HTTP/3라는 대안은 4장(HTTP2 깊이 보기)에서 다룬다.

gRPC 호출 하나는 HTTP/2의 **스트림(stream) 하나** 에 대응한다. 요청은 `:method: POST`, `:path: /order.v1.OrderService/GetOrder` 같은 **HEADERS 프레임**으로 시작하고, 직렬화된 메시지는 **DATA 프레임**으로 전달되며, 호출 결과 상태(`grpc-status`)는 마지막 **트레일러(trailing HEADERS) 프레임**으로 전달된다. 이 구조는 9절에서 바이트 단위로 다시 살펴본다.

HTTP/2의 프레임 타입, 우선순위, SETTINGS, 윈도 업데이트 같은 전송 계층의 세부 사항은 모두 4장(HTTP2 깊이 보기)에서 다룬다.

> [!note] 참고
> HTTP/2를 선택했기 때문에 치르는 **대가**도 있다. 브라우저의 자바스크립트는 HTTP/2 프레임을 직접(raw) 제어할 수 없으므로, *브라우저가 gRPC 서버를 직접 호출하지 못한다*. 이 제약과 우회 방법(gRPC-Web, 프록시)은 [[16 - gRPC-Web과 REST 게이트웨이]]에서 다룬다.

### 5.3 기둥 3: 다언어 코드 생성

**`protoc`** 컴파일러와 언어별 플러그인은 `.proto` 계약 하나로부터 각 언어의 **타입 안전한 스텁과 메시지 코드**를 자동으로 생성한다. 같은 `order.proto`에서 만든 Go 서버, Java 클라이언트, Python 분석 스크립트는 *모두 같은 계약*을 공유한다.

```text
                 order.proto  (단일 진실의 원천)
                      │
            ┌─────────┴──────────┐    protoc + 언어 플러그인
            ▼         ▼          ▼
        Go 코드   Java 코드   Python 코드   ... (C++, C#, Ruby, Node, Kotlin, Dart)
        (서버)    (클라)      (배치잡)
```

이것이 2.4절에서 본 언어와 플랫폼의 제약을 없애는 열쇠이다. RMI는 자바끼리만, DCOM은 Windows끼리만 통신할 수 있었지만, gRPC는 계약 하나에서 **N개 언어의 코드를 생성한다.** 폴리글랏 마이크로서비스 환경에서 결정적인 이점이다. `protoc` 툴체인, 플러그인, 빌드 통합, 버전 관리는 6장(코드 생성과 protoc 툴체인)에서 자세히 다룬다.

### 5.4 기둥 4: 교체 가능한(pluggable) 런타임

가장 과소평가된 기둥이다. gRPC는 단순히 직렬화와 전송을 묶은 것이 아니라, **분산 시스템 운영에 필요한 횡단 관심사를 교체 가능한 컴포넌트로 추상화한 런타임**이다. 1세대 RPC가 "함수처럼 편하게"에 기대다가 8가지 오류로 곤란을 겪었다면, gRPC는 각 오류에 대한 *방어 장치*를 끼워 넣을 수 있는 슬롯을 만들었다.

- **인증과 보안(pluggable credentials)**: TLS, mTLS, 토큰 기반 인증을 자격 증명(credentials) 추상화로 끼워 넣는다(11장 보안 참고).
- **이름 해석(name resolver)**: `dns:///`, `xds:///` 등 스킴별 resolver로 "이 서비스가 어느 주소에 있는가"를 해결한다(12장 이름 해석과 로드밸런싱 참고).
- **로드밸런싱 정책**: round_robin, pick_first 같은 정책을 끼워 넣는다(12장 참고).
- **재시도, 헬스 체크, keepalive**: 일시적인 장애를 흡수하는 안정성 장치이다(13장 안정성 참고).
- **인터셉터(interceptor)**: 모든 호출을 가로채 로깅, 인증, 메트릭, 트레이싱을 넣는 미들웨어이다(8장 메타데이터와 인터셉터 참고).
- **데드라인과 취소**: 모든 호출에 시간 상한을 부여하고 이를 전파한다(10장 Deadline 취소 타임아웃 참고).
- **에러 모델**: 상태 코드와 Rich Error(상세 에러)로 실패를 구조화한다([[09 - 에러 모델 - 상태 코드와 Rich Error]] 참고).

이 네 번째 기둥 덕분에 gRPC는 단순한 RPC 라이브러리를 넘어 **마이크로서비스 통신을 위한 미들웨어 플랫폼**이 된다. 개발자는 도메인 로직만 작성하고, 재시도, 인증, 관찰성 같은 운영 관심사는 런타임의 슬롯에 끼워 넣으면 된다.

## 6. RPC 패러다임과 REST 패러다임: 철학의 차이

gRPC를 처음 접하는 REST 경험자가 가장 자주 헷갈리는 부분이 바로 이것이다. 둘은 단지 프로토콜만 다른 것이 아니라 **세계를 모델링하는 방식 자체가 다르다.**

- **REST는 명사(리소스) 중심이다.** 세계를 *리소스*의 집합으로 본다. `/orders/42`는 "42번 주문"이라는 명사이다. 동작은 HTTP 동사라는 *고정된 작은 집합*(GET/POST/PUT/PATCH/DELETE)으로만 표현한다. "주문을 환불 처리한다"를 표현하려면 `POST /orders/42/refunds`처럼 *새 리소스*를 만들어 끼워 맞춰야 한다.
- **RPC(gRPC)는 동사(프로시저) 중심이다.** 세계를 *동작(메서드)* 의 집합으로 본다. `OrderService.RefundOrder(...)`처럼 도메인 동사가 그대로 API가 된다. "주문을 환불한다"가 곧 메서드 하나이므로 리소스로 돌아갈 필요가 없다.

같은 "주문 환불"을 두 패러다임이 어떻게 표현하는지 보자.

```text
REST (리소스/명사 중심)              gRPC (프로시저/동사 중심)
─────────────────────────           ──────────────────────────
POST /orders/42/refunds             rpc RefundOrder(RefundOrderRequest)
Content-Type: application/json          returns (RefundOrderResponse);
{
  "amount": 5000,                   message RefundOrderRequest {
  "reason": "고객 변심"               string order_id = 1;
}                                      int64  amount   = 2;
                                       string reason   = 3;
→ 200 / 201 / 4xx (의미는 약속)      }
→ 본문은 JSON (스키마는 문서 의존)    → grpc-status + RefundOrderResponse
                                        (계약이 컴파일 타임 강제)
```

핵심 트레이드오프를 표로 정리하면 다음과 같다.

| 축 | REST | gRPC(RPC) |
|---|---|---|
| 모델 단위 | 리소스(명사) | 프로시저(동사) |
| 계약 강제 | 느슨함(관례/OpenAPI, 런타임 의존) | 강함(`.proto`, 컴파일 타임 강제) |
| 직렬화 | 텍스트(주로 JSON) | 이진(Protocol Buffers) |
| 사람이 읽기 | 쉬움(`curl`로 바로 확인) | 어려움(도구 필요, → grpcurl) |
| 페이로드 크기 | 큼 | 작음 |
| 파싱 속도 | 느림 | 빠름 |
| 스트리밍 | 어색함(SSE/WebSocket 등 별도 기법) | 1급 지원(4가지 방식) |
| 멀티플렉싱 | HTTP/1.1에서는 제약 | HTTP/2로 기본 제공 |
| 브라우저 직접 호출 | 자연스러움 | 불가(gRPC-Web 필요) |
| 캐시(HTTP 캐시) | 잘 맞음 | 부적합 |
| 진입 장벽 | 낮음 | 다소 높음(툴체인) |
| 코드 생성 | 선택(OpenAPI codegen) | 핵심(거의 필수) |
| 적합한 영역 | 공개 API, 브라우저, 단순 CRUD | 내부 마이크로서비스, 저지연·고처리량, 폴리글랏, 스트리밍 |

여기서 흔한 오해 하나를 바로잡자. **"gRPC가 REST보다 우월하다"는 생각은 잘못된 프레임이다.** 둘은 *서로 다른 문제*를 해결한다. REST는 전 세계 누구나 브라우저로 접근하고, 사람이 읽을 수 있으며, HTTP 캐시와 프록시 인프라를 그대로 활용해 리소스를 다루는 데 가장 적합하다. gRPC는 신뢰할 수 있는 내부망에서 폴리글랏 서비스들이 강한 계약을 바탕으로 작고 빠른 이진 메시지를, 때로는 스트리밍으로 빈번하게 주고받는 데 가장 적합하다.

**계약의 강도와 텍스트 가독성은 서로 맞바꾸는 관계**이며, 어느 쪽을 택할지는 *누가 이 API를 사용하는가*에 달려 있다. 사람(브라우저, 외부 개발자)이 사용한다면 REST 쪽으로, 기계(내부 서비스)가 사용한다면 gRPC 쪽으로 무게가 실린다.

> [!note] 덧붙임
> GraphQL은 클라이언트가 질의를 주도한다는 또 다른 축이며, 이 책의 범위를 벗어난다. 다만 리소스(REST), 동사(RPC), 질의(GraphQL)가 서로 다른 모델링 철학이라는 큰 그림은 기억해 두자.

## 7. gRPC를 써야 할 때와 피해야 할 때

도구는 알맞은 곳에 써야 한다. gRPC의 강점이 잘 드러나는 곳과 오히려 해가 되는 곳을 구분해 보자.

### 7.1 gRPC가 잘 맞는 곳

1. **내부 마이크로서비스 간 통신**: 신뢰 경계 안에서 서비스들이 낮은 지연과 높은 처리량으로 호출을 주고받는 경우이다. 이진 직렬화의 작은 크기와 HTTP/2 멀티플렉싱이 곧바로 성능 이득이 된다. 강한 계약 덕분에 팀 간 통합 버그를 컴파일 시점에 잡을 수 있다.
2. **폴리글랏 환경**: Go, Java, Python, Kotlin, C++ 서비스가 섞여 있고, 모두가 *하나의 `.proto` 계약*을 공유해야 하는 경우이다. 코드 생성이 언어 사이의 경계를 매끄럽게 연결한다.
3. **스트리밍이 본질인 도메인**: 실시간 위치 업데이트, 채팅, 로그/메트릭 스트림, 대용량 파일 청크 전송처럼 *연속적인 데이터 흐름*이 필요한 경우이다. 양방향 스트리밍을 1급으로 지원한다(5장 통신의 4가지 방식 참고).
4. **엄격한 스키마와 진화가 중요한 시스템**: 여러 팀과 여러 버전의 클라이언트가 공존하면서 하위 호환성을 유지한 채 진화해야 하는 경우이다. 필드 번호를 기준으로 한 진화 규칙이 강력하다(17장 proto 관리와 하위호환성 참고).
5. **모바일 ↔ 백엔드(대역폭과 배터리에 민감한 경우)**: 작은 페이로드와 효율적인 파싱이 모바일 환경에서 의미 있는 이득을 준다.

### 7.2 gRPC를 피하거나 신중하게 써야 할 곳

1. **브라우저에서 서버를 직접 호출하는 경우**: 브라우저의 JS는 HTTP/2 프레임을 직접(raw) 제어할 수 없으므로 gRPC를 *직접* 호출할 수 없다. **gRPC-Web**과 프록시(Envoy 등)를 쓸 수는 있지만 계층이 하나 더 생기고, 양방향 스트리밍 등에 제약이 있다(16장 gRPC-Web과 REST 게이트웨이 참고). 브라우저가 주된 사용자라면 REST나 GraphQL이 더 단순한 선택인 경우가 많다.
2. **외부에 공개하는 API**: 외부 개발자에게 공개하는 API라면 진입 장벽이 낮고 어디서나 `curl`로 호출해 볼 수 있는 REST/JSON의 채택률이 훨씬 높다. gRPC는 클라이언트에게 툴체인과 코드 생성을 요구한다.
3. **사람이 직접 디버깅하는 단순 CRUD**: 이진 페이로드는 사람이 눈으로 읽을 수 없다. grpcurl이나 리플렉션으로 보완할 수는 있지만, 정말 단순한 CRUD라면 그런 부담을 감수할 이유가 없을 수도 있다.
4. **HTTP 캐시와 CDN을 적극 활용하는 읽기 트래픽**: GET 캐싱처럼 HTTP 캐시 의미론에 의존하는 워크로드에는 REST가 자연스럽다.
5. **인프라가 HTTP/2를 온전히 지원하지 않는 경우**: 일부 구형 프록시, 로드밸런서, 게이트웨이가 HTTP/2 트레일러(gRPC가 상태 코드를 담는 곳)나 오래 유지되는 스트림을 제대로 처리하지 못하면 운영상 문제가 된다.

**실무에서는** *둘 다 쓰는 방식*이 흔하다. 외부 경계(브라우저, 외부 개발자)에는 REST나 GraphQL을 노출하고, 그 게이트웨이 뒤의 **내부 서비스 메시는 gRPC**로 연결한다. gRPC ↔ REST 변환은 게이트웨이로 자동화할 수 있다(16장 참고).

## 8. 생태계 지형도: 구현체가 둘로 나뉘는 이유

실무에서 gRPC를 다루다 보면 곧 알게 되는 사실이 있다. **gRPC 구현체는 크게 두 갈래**로 나뉜다는 것이다. 이 구분을 모르면 "왜 Go와 Python의 동작이 조금씩 다를까" 같은 의문을 풀기 어렵다.

```text
                 gRPC 구현체의 두 갈래
   ┌───────────────────────────────┬───────────────────────────────┐
   │ (A) 순수 네이티브 구현          │ (B) C-core 위의 래퍼            │
   ├───────────────────────────────┼───────────────────────────────┤
   │ gRPC-Go  : 순수 Go             │ C++  : C-core 직접/근접         │
   │ gRPC-Java: 순수 Java(Netty)    │ Python, Ruby, C#, PHP,          │
   │ gRPC-Dart: 순수 Dart           │ Node.js(과거), Objective-C ...  │
   │                                │  → 모두 동일한 C 코어를 공유     │
   │                                │    하고 언어별 얇은 바인딩       │
   └───────────────────────────────┴───────────────────────────────┘
```

- **(A) 순수 네이티브 구현**: **gRPC-Go**(순수 Go), **gRPC-Java**(JVM, 내부적으로 Netty 등을 사용), **gRPC-Dart** 등은 해당 언어로 *처음부터 끝까지* 구현되었다. C 라이브러리에 의존하지 않는다.
- **(B) C-core 위의 래퍼**: **C++, Python, Ruby, C#, PHP, Objective-C** 등 상당수는 **공통 C 코어(gRPC C-core)** 를 공유하고, 그 위에 언어별 *얇은 바인딩*을 올린 형태이다. 전송, HTTP/2, 흐름 제어 같은 핵심 로직은 C로 한 번 구현하고, 각 언어는 그것을 호출한다.

**왜 두 갈래로 나뉘었을까?** 엔지니어링 트레이드오프의 결과이다.

- *공통 C 코어 전략*의 장점은 **일관성과 유지보수 효율**이다. HTTP/2나 흐름 제어처럼 복잡하고 까다로운 핵심 로직을 한 번만 정확하게 구현하면 여러 언어가 검증된 코어를 공유할 수 있다. 버그 수정이나 성능 개선도 한곳에서 하면 모든 언어에 반영된다.
- 그러나 *Go와 Java는 다른 길*을 택했다. **런타임 모델이 충돌하기 때문이다.** Go의 고루틴, 스케줄러, GC와 JVM의 스레드, GC는 자체 스레드 풀, 메모리 관리, 이벤트 루프를 가진 C 라이브러리와 매끄럽게 섞이기 어렵다.

  C로 작성한 이벤트 루프를 Go 런타임에 넣으면 고루틴 스케줄링과 충돌하고, FFI(cgo/JNI) 경계를 넘나드는 비용도 크다. 그래서 두 거대 생태계는 **각 언어의 동시성 모델에 자연스럽게 맞는 순수 구현**을 선택했다.

**실무에서 주의할 점**은 다음과 같다.

- **언어마다 기능의 성숙도와 세부 동작이 조금씩 다를 수 있다.** 재시도, keepalive, 특정 로드밸런싱 정책 같은 고급 기능은 구현체마다 지원 시점과 정확한 의미가 다를 수 있다. 따라서 다언어 시스템에서는 *각 언어 구현체의 문서와 버전*을 확인해야 한다.
- **성능 특성도 다르다.** 순수 Go/Java 구현은 해당 런타임에 최적화되어 있고, C-core 래퍼 언어는 FFI 경계를 넘나드는 비용을 부담한다.
- **디버깅할 때는 어느 계층의 문제인지 의식해야 한다.** C-core 래퍼 언어에서 이상한 동작이 보이면 언어 바인딩의 문제인지 C 코어의 문제인지 구분해야 할 수도 있다.

이 차이는 채널과 연결의 생명주기([[07 - 채널 스텁 커넥션 생명주기]])나 안정성 기능(13장 안정성)을 다룰 때 다시 나온다. "gRPC의 동작"으로 뭉뚱그리지 말고 "이 *구현체*에서 일어나는 동작"으로 생각하는 습관을 들이자.

## 9. "Hello World" 호출 한 번을 끝까지 따라가기

이제 지금까지의 추상적인 설명을 호출 한 줄에 담아, **클라이언트가 메서드 하나를 호출한 순간부터 응답이 돌아올 때까지 와이어 위에서 실제로 무슨 일이 일어나는지**를 끝까지 따라가 보자. 이 절의 그림이 이 책 전체의 **로드맵**이다. 이후 챕터에서는 이 그림의 각 부분을 확대해서 살펴본다.

### 9.1 계약: `.proto`

```proto
syntax = "proto3";

package greet.v1;

option go_package = "example.com/greet/v1;greetv1";

service Greeter {
  // 단순(unary) RPC: 요청 1개 → 응답 1개
  rpc SayHello(HelloRequest) returns (HelloReply);
}

message HelloRequest {
  string name = 1;
}

message HelloReply {
  string message = 1;
}
```

### 9.2 코드 생성

```bash
# protoc로 Go용 메시지 + gRPC 스텁 생성
protoc \
  --go_out=. --go_opt=paths=source_relative \
  --go-grpc_out=. --go-grpc_opt=paths=source_relative \
  greet/v1/greet.proto
# → greet/v1/greet.pb.go      (메시지 타입)
# → greet/v1/greet_grpc.pb.go (Greeter 클라이언트/서버 스텁)
```

(`protoc`와 플러그인의 작동 원리는 6장 코드 생성과 protoc 툴체인에서 다룬다.)

### 9.3 서버 (Go)

```go
package main

import (
	"context"
	"log"
	"net"

	"google.golang.org/grpc"
	greetv1 "example.com/greet/v1"
)

// 생성된 인터페이스(greetv1.GreeterServer)를 구현한다
type server struct {
	greetv1.UnimplementedGreeterServer
}

// 우리가 짜는 것은 '도메인 로직'뿐. 직렬화/전송은 런타임이 처리한다.
func (s *server) SayHello(ctx context.Context, req *greetv1.HelloRequest) (*greetv1.HelloReply, error) {
	return &greetv1.HelloReply{Message: "안녕하세요, " + req.GetName() + "님"}, nil
}

func main() {
	lis, err := net.Listen("tcp", ":50051")
	if err != nil {
		log.Fatal(err)
	}
	s := grpc.NewServer()
	greetv1.RegisterGreeterServer(s, &server{})
	log.Println("listening on :50051")
	if err := s.Serve(lis); err != nil { // HTTP/2 서버 시작
		log.Fatal(err)
	}
}
```

### 9.4 클라이언트 (Go)

```go
package main

import (
	"context"
	"log"
	"time"

	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
	greetv1 "example.com/greet/v1"
)

func main() {
	// 1) 채널(연결 추상)을 만든다. 아직 도메인 호출은 없다.
	conn, err := grpc.NewClient(
		"localhost:50051",
		grpc.WithTransportCredentials(insecure.NewCredentials()), // 데모용 평문
	)
	if err != nil {
		log.Fatal(err)
	}
	defer conn.Close()

	// 2) 스텁: 마치 로컬 객체처럼 보이는 원격 프록시
	client := greetv1.NewGreeterClient(conn)

	// 3) 데드라인을 '반드시' 건다 — 분산의 현실을 숨기지 않는다(8가지 오류 #2)
	ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second)
	defer cancel()

	// 4) 호출: 문법은 로컬 함수와 똑같다
	reply, err := client.SayHello(ctx, &greetv1.HelloRequest{Name: "Shawn"})
	if err != nil {
		log.Fatalf("RPC 실패: %v", err) // 실패는 error로 정직하게 드러난다
	}
	log.Println(reply.GetMessage()) // → 안녕하세요, Shawn님
}
```

다른 언어의 클라이언트도 *같은 계약*에서 생성된다. 예를 들어 Python 클라이언트는 다음과 같다.

```python
import grpc
import greet.v1.greet_pb2 as pb
import greet.v1.greet_pb2_grpc as rpc

with grpc.insecure_channel("localhost:50051") as channel:
    stub = rpc.GreeterStub(channel)
    reply = stub.SayHello(pb.HelloRequest(name="Shawn"), timeout=2.0)
    print(reply.message)  # → 안녕하세요, Shawn님
```

Go 서버와 Python 클라이언트가 코드 한 줄 고치지 않고 맞물려 동작한다. 이것이 기둥 3(다언어 코드 생성)의 힘이다.

### 9.5 호출 한 줄 뒤에서 일어나는 일 (전체 그림)

`client.SayHello(ctx, &HelloRequest{Name:"Shawn"})` 한 줄 뒤에서 실제로 일어나는 일을 단계별로 살펴보자.

```text
[클라이언트]                                            [서버]
   │
   │ ① 스텁이 호출을 가로챈다
   │    (스텁 = 원격 메서드의 로컬 프록시)
   │
   │ ② Protocol Buffers 직렬화
   │    HelloRequest{name:"Shawn"}  →  바이트 0a 05 53 68 61 77 6e
   │    (필드1 LEN, 길이5, "Shawn")     [[03 - Protocol Buffers 2 - 인코딩과 와이어 포맷]]
   │
   │ ③ gRPC 길이-접두 프레이밍
   │    [압축플래그 00][길이 00 00 00 07][payload 0a 05 53 68 61 77 6e]
   │
   │ ④ 채널/연결에서 HTTP/2 스트림 1개 확보
   │    [[07 - 채널 스텁 커넥션 생명주기]]
   │
   │ ⑤ HEADERS 프레임 전송 ───────────────────────────►
   │    :method: POST
   │    :scheme: http
   │    :path: /greet.v1.Greeter/SayHello
   │    :authority: localhost:50051
   │    content-type: application/grpc
   │    grpc-timeout: 2S         ← ctx의 데드라인 [[10 - Deadline 취소 타임아웃]]
   │    (+ 사용자 메타데이터)      [[08 - 메타데이터와 인터셉터]]
   │
   │ ⑥ DATA 프레임 전송(③의 바이트) ─────────────────►
   │    (END_STREAM 플래그로 "요청 끝" 표시)
   │                                                  ⑦ 서버가 프레임 수신
   │                                                     디프레이밍 → 역직렬화
   │                                                     → HelloRequest{name:"Shawn"}
   │                                                  ⑧ 핸들러(SayHello) 실행
   │                                                     도메인 로직 → HelloReply
   │                                                  ⑨ 응답 직렬화 + 프레이밍
   │ ◄──────────── HEADERS(응답 헤더) ─────────────────
   │ ◄──────────── DATA(응답 메시지) ──────────────────
   │ ◄──────────── HEADERS(트레일러) ──────────────────
   │                grpc-status: 0 (OK)  ← 결과 상태!
   │                grpc-message: ""      [[09 - 에러 모델 - 상태 코드와 Rich Error]]
   │
   │ ⑩ 클라이언트: 디프레이밍 → 역직렬화 → HelloReply
   │    grpc-status==0 이므로 정상 반환
   ▼
 reply.GetMessage() == "안녕하세요, Shawn님"
```

이 그림에서 주목할 설계 포인트는 세 가지이다.

1. **요청과 결과 상태가 분리되어 있다.** HTTP 상태 코드(200 등)는 *전송*이 성공했는지만 알려 준다. *도메인* 차원의 성공과 실패는 **트레일러의 `grpc-status`** 로 따로 전달된다. 그래서 "HTTP는 200인데 grpc-status는 에러"인 상황이 자연스럽게 생긴다. 이 분리가 9장(에러 모델)의 출발점이다.

   응답 본문 없이 곧바로 실패하며 종료하는 경우에는 초기 헤더와 트레일러를 HEADERS 프레임 하나로 합쳐 보내는 *Trailers-Only* 형태를 쓰기도 한다.
2. **데드라인이 헤더(`grpc-timeout`)에 담겨 와이어를 통해 전파된다.** 클라이언트가 정한 "2초"라는 시간 상한이 서버까지 전달되고, 더 깊은 호출로 계속 전파될 수 있다. 8가지 오류 중 2번(지연은 0이 아니다)에 대한 구조적인 대응이다(10장 Deadline 취소 타임아웃 참고).

   위 그림에서는 읽기 쉽게 `2S`로 표기했지만, 실제 구현은 보통 더 작은 단위를 써서 8자리 이내의 정수로 인코딩하며, 게다가 *남은 시간*을 카운트다운하면서 값을 정한다. 즉 `grpc-timeout`의 값은 절대 시각이 아니라 상대적인 잔여 시간이다.
3. **인터셉터가 ①과 ⑧을 감쌀 수 있다.** 클라이언트 인터셉터는 ①의 스텁 호출을, 서버 인터셉터는 ⑧의 핸들러 실행을 감싼다. 모든 호출의 진입과 이탈을 가로채 인증, 로깅, 메트릭, 트레이싱을 한곳에서 넣는다(8장 메타데이터와 인터셉터 참고).

### 9.6 ②~③의 바이트를 직접 디코딩하기

추상적인 설명 대신 실제 바이트를 보자. `HelloRequest{ name: "Shawn" }`은 Protocol Buffers로 어떻게 인코딩될까?

- 필드 `name`은 **필드 번호 1**이고 타입이 `string`이므로 와이어 타입은 **2(LEN, 길이 지정)** 이다.
- **태그 바이트** = `(field_number << 3) | wire_type` = `(1 << 3) | 2` = `0x0A`.
- 그다음 **길이**: `"Shawn"`은 5바이트이므로 `0x05`이다.
- 그다음 **UTF-8 바이트**: `S=0x53, h=0x68, a=0x61, w=0x77, n=0x6E`.

```text
프로토버프 페이로드 (7바이트):
  0A        05        53 68 61 77 6E
  └tag┘     └len┘     └─── "Shawn" ───┘
  field1    길이5      UTF-8 bytes
  LEN(=2)
```

이제 gRPC는 이 7바이트를 **길이 접두 메시지(Length-Prefixed-Message)** 로 감싼다. 형식은 `[1바이트 압축 플래그][4바이트 빅엔디안 길이][payload]`이다.

```text
gRPC DATA 프레임 본문 (5 + 7 = 12바이트):
  00            00 00 00 07          0A 05 53 68 61 77 6E
  └압축플래그┘   └─ 길이=7(빅엔디안)┘  └──── 프로토버프 payload ────┘
  0=비압축
```

이 12바이트가 HTTP/2 **DATA 프레임**의 페이로드로 전송된다. HTTP/2 프레임은 다시 `[길이3 | 타입1 | 플래그1 | 스트림ID4]` 형식의 9바이트 헤더로 감싸지는데, 자세한 내용은 4장(HTTP2 깊이 보기)에서 살펴본다. varint, zigzag, packed 같은 더 깊은 인코딩 규칙은 3장(Protocol Buffers 2)에서 바이트 단위로 자세히 다룬다.

정리하면, **로컬 함수처럼 호출하는 편리한 한 줄 뒤에서는 직렬화, 길이 프레이밍, HTTP/2 프레임, 멀티플렉싱, 전송, 그리고 그 역과정이 정확하게 맞물려 동작한다.** gRPC의 가치는 이 복잡함은 *감추면서도* 분산 환경의 현실(데드라인, 상태 코드, 취소)은 *감추지 않는* 균형에 있다.

### 9.7 이 그림에서 출발하는 책의 로드맵

| 9절 그림의 단계 | 확대해 보는 챕터 |
|---|---|
| ② 직렬화 / 메시지 정의 | 2장(Protocol Buffers 1), 3장(Protocol Buffers 2) |
| ⑤⑥ HTTP/2 프레임·스트림 | 4장(HTTP2 깊이 보기) |
| 요청/응답이 1개인지 스트림인지 | 5장(통신의 4가지 방식) |
| ② 코드(스텁) 생성 | 6장(코드 생성과 protoc 툴체인) |
| ④ 채널·연결 확보 | 7장(채널 스텁 커넥션 생명주기) |
| ⑤ 헤더/메타데이터, ①⑧ 가로채기 | 8장(메타데이터와 인터셉터) |
| ⑨ 트레일러의 grpc-status | 9장(에러 모델) |
| ⑤ grpc-timeout, 취소 | 10장(Deadline 취소 타임아웃) |
| ④ 연결 보안 | 11장(보안) |
| ④ 어느 서버로 보낼지 | 12장(이름 해석과 로드밸런싱) |
| 실패 시 재시도/생존 확인 | 13장(안정성) |
| 무슨 일이 일어났는지 들여다보기 | 14장(관찰성과 디버깅) |
| ⑥ 너무 빨리/느리게 보낼 때 | 15장(성능과 Flow Control) |
| 브라우저/REST와의 연결 | 16장(gRPC-Web과 REST 게이트웨이) |
| 계약 진화 | 17장(proto 관리와 하위호환성) |
