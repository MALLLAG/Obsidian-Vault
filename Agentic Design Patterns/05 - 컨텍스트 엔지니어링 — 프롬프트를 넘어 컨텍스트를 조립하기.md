앞의 네 장에서 재료와 골격을 세웠다. [[02 - LLM이라는 재료 — 확률적 생성기 위에 시스템을 짓는다는 것]]에서는 모델 API가 **무상태(stateless)** 라는 사실을 확인했다. 서버는 대화를 기억하지 않으므로, 요청을 보낼 때마다 우리가 전체 이력을 다시 만들어 보내야 한다.

[[04 - 에이전트 루프의 해부 — 관찰·결정·행동·정지]]에서는 루프 한 바퀴가 컨텍스트 조립, 모델 결정, 행동 실행, 결과 통합의 네 지점으로 나뉜다고 했다. 이 장에서는 그중 첫 번째 지점만 따로 떼어 깊이 살펴본다.

이렇게 나누는 것이 인위적이지 않다는 점을 먼저 짚어 두자. 에이전트 시스템에서 우리가 코드로 실제로 통제할 수 있는 것은 많지 않다. 모델의 가중치는 고정되어 있고, 샘플링은 확률적이며, 도구 실행 결과는 외부 세계가 정한다. 남는 것은 **모델이 다음 토큰을 예측할 때 무엇을 보게 할 것인가** 하나뿐이다. 이것이 우리가 온전히 통제할 수 있는 유일한 레버다.

[[43 - 에이전트와 소프트웨어 아키텍처 — 결정론 경계와 기존 패턴의 재해석]]에서 말하는 "결정론 경계" 안쪽에서 일어나는 일 가운데, 설계 판단이 가장 많이 몰리는 곳이 여기인 것도 그 때문이다.

그런데 이 레버에는 한계가 있다. 컨텍스트 창은 크지만 무한하지 않고, 크더라도 모든 위치가 똑같이 잘 읽히지는 않으며, 채우는 만큼 비용과 시간이 든다. 그래서 문제의 형태가 "문장을 잘 쓰는 일"에서 **"제한된 예산을 항목별로 배분하는 일"** 로 바뀐다. 무엇을 넣을지, 얼마나 넣을지, 어떤 순서로 놓을지, 넘칠 때 무엇을 버릴지, 그리고 버린 것이 나중에 어떤 문제로 돌아오는지가 이 장에서 다룰 배분 문제다.

메모리의 이론적 문제는 [[21 - 메모리의 문제 — 컨텍스트 윈도·상태·망각]]부터, 검색 기법 자체(청킹·임베딩·재랭킹)는 [[24 - RAG와 에이전틱 검색 — 검색을 행동으로]]에서, 캐싱 비용 계산은 [[40 - 비용과 지연 — 캐싱·모델 라우팅·예산 관리]]에서 다룬다. 이 장은 그보다 **상류**에서 어떤 정보를 어떤 형태로 창의 어느 위치에 놓을지 정하는 층을 다룬다.

## 1. 프롬프트 엔지니어링은 사라지지 않고 부분집합이 되었다

### 1.1 무상태 API 때문에 매번 다시 조립해야 한다

아주 구체적인 사실에서 출발하자. 다음 두 코드는 겉보기에 똑같이 "대화를 이어 가는" 일을 하지만, 실제로 일어나는 일은 두 번째 코드다.

```python
# 착시: 세션 객체가 대화를 '기억한다'고 느끼게 만드는 API 표면.
session.send("이 결제가 왜 실패했지?")
session.send("그럼 재시도하면 성공할까?")   # 서버가 앞 문맥을 갖고 있는 것처럼 보인다

# 실제: 두 번째 호출에서 클라이언트가 보내는 것.
# 서버에 남은 상태는 없다. 우리가 매번 전부 다시 만들어 보낸다.
messages = [
    {"role": "user", "content": "이 결제가 왜 실패했지?"},
    {"role": "assistant", "content": [{"type": "tool_use", "name": "get_payment", ...}]},
    {"role": "user", "content": [{"type": "tool_result", "content": "...(3,200 토큰)..."}]},
    {"role": "assistant", "content": "PG 응답 코드 8104는 ..."},
    {"role": "user", "content": "그럼 재시도하면 성공할까?"},
]
resp = llm.complete(system=SYSTEM, tools=TOOLS, messages=messages)
```

편의 래퍼를 쓰더라도 내부에서는 두 번째 형태로 변환된다. 여기서 나오는 결론 세 가지가 이 장 전체의 전제다.

**첫째, 컨텍스트는 한 번 쓰고 끝나는 문서가 아니라 매 턴 새로 조립되는 자료구조다.** 우리가 설계하는 것은 문자열이 아니라 그 문자열을 만들어 내는 함수, 즉 조립기(assembler)다. 조립기의 입력은 (대화 이력, 현재 상태, 검색 가능한 지식, 예산)이고, 출력은 (system, tools, messages) 튜플이다. 이 함수는 순수 함수로 만들 수 있고, 그렇게 만들어야 테스트할 수 있다. [[30 - 함수형 아키텍처 — 순수 코어와 명령 껍질]]의 구도가 그대로 적용된다. 조립은 순수 코어이고, 모델 호출과 도구 실행은 껍질이다.

**둘째, 비용은 대화 길이에 선형으로 늘지 않는다.** $t$번째 턴에서 보내는 입력 토큰 수가 대략 $c + \sum_{i<t} l_i$라고 하자($c$는 시스템 프롬프트와 도구 정의 같은 고정분, $l_i$는 $i$번째 턴이 추가한 길이). 그러면 대화 전체의 누적 입력 토큰은

$$
\sum_{t=1}^{T}\Big(c + \sum_{i<t} l_i\Big) \;=\; cT + \sum_{t=1}^{T}\sum_{i<t} l_i
$$

가 되어 턴 수에 대해 이차적으로 늘어난다. 과금은 대개 토큰 수에 선형이므로, 이 이차성은 **누적 토큰 수**에서 나온다. 여기에 서버 측 연산의 성질이 하나 더 겹친다. 어텐션 항의 계산량은 시퀀스 길이에 대해 이차이므로, 긴 프롬프트는 토큰당 비용과 별개로 **지연** 면에서도 불리하다.

따라서 20턴짜리 에이전트 세션을 두고 "마지막 턴이 비싸다"고 말하기보다 **"세션 전체 비용이 마지막 턴의 길이에 좌우된다"** 고 말하는 편이 정확하다. 프롬프트 캐싱이 실무에서 선택이 아니라 필수가 되는 이유(5절)와, 압축이 비용 문제이기도 한 이유(6절)가 여기에 있다.

**셋째, 컨텍스트의 대부분은 사람이 쓴 문장이 아니다.** 토큰 점유율을 실제로 재 보면 손으로 쓴 시스템 프롬프트는 한 자릿수 퍼센트에 그치는 경우가 흔하다. 나머지는 도구 정의, 도구 출력, 검색 결과, 모델이 이전 턴에 쓴 발화가 차지한다. 프롬프트를 다듬는 데 하루를 쓰면서 3,200토큰짜리 도구 출력은 그대로 흘려보내고 있다면, 노력을 엉뚱한 항목에 쏟고 있는 것이다.

> [!warning] 흔한 오해
> "프롬프트만 잘 쓰면 된다"는 생각은 요약·번역·분류 같은 단발 호출에서는 대체로 맞지만, 루프를 도는 에이전트에서는 대체로 틀리다. 단발 호출의 컨텍스트는 우리가 100% 직접 작성하지만, 에이전트의 컨텍스트는 대부분 **런타임에 생성된다**. 도구가 내놓은 JSON, 검색기가 가져온 문서, 모델이 이전 턴에 쓴 문장이 그렇다. 우리가 정할 수 있는 것은 이런 생성물의 **형식과 상한과 배치**뿐이다. 프롬프트 엔지니어링은 사라지지 않지만, 그것만으로는 부족하다.

### 1.2 용어가 바뀐 이유

"컨텍스트 엔지니어링"이라는 표현은 2025년 중반에 업계에서 빠르게 자리 잡았다. 새로운 기술이 발명되어서가 아니라, 사람들이 하던 일과 그 일을 부르는 이름이 맞지 않았기 때문이다. 도구를 여러 개 붙이고 루프를 돌리기 시작하자 "프롬프트"는 더 이상 문자열 하나가 아니었다. 시스템 지시, 수십 개의 도구 스키마, 검색된 문서, 누적된 도구 출력, 요약된 과거를 한 창에 배치하는 일을 가리키기에는 그 이름이 너무 좁았다.

> [!info] 역사 메모
> 이런 관점 자체는 새롭지 않다. 용량이 작고 빠른 저장소와 용량이 크고 느린 저장소 사이에서 무엇을 올려 둘지 정하는 문제는, 가상 메모리([[18 - 가상 메모리와 페이지 폴트]])와 캐시 계층([[16 - 캐시의 해부]])이 수십 년 동안 다뤄 온 문제와 형태가 같다. 2023년의 MemGPT(Packer 등, "MemGPT: Towards LLMs as Operating Systems")는 이 유추를 명시적으로 채택했다.
>
> 컨텍스트 창을 "메인 컨텍스트(메인 메모리)"로, 외부 저장소를 "외부 컨텍스트(디스크)"로 두고, 모델이 함수 호출로 직접 페이징을 지휘하게 하는 설계를 제안했다.
>
> 이 유추가 유용한 이유는 워킹셋, 지역성, 축출 정책, 스래싱 같은 실무 직관을 그대로 가져올 수 있다는 데 있다. 다만 한계도 분명하다. CPU 캐시는 미스가 나면 **느려질 뿐 결과가 틀리지는 않지만**, 컨텍스트에서 미스가 나면 모델은 아무 표시 없이 내용을 **지어낸다.** 이 비대칭 때문에 컨텍스트의 축출 정책은 훨씬 보수적이어야 한다.

### 1.3 조립기라는 컴포넌트

이제 개념을 구체적인 코드로 옮겨 보자. 이 장에서 권하는 첫 번째 실무 조치는 조립기를 이름이 있는 독립 컴포넌트로 만드는 것이다. 프롬프트 문자열이 코드 곳곳에 흩어져 f-string으로 이어 붙여지고 있다면, 지금 무엇이 몇 토큰 들어가는지, 무엇이 잘렸는지, 캐시가 왜 깨졌는지 같은 컨텍스트에 관한 질문에 하나도 답할 수 없다.

```python
# 조립기: 컨텍스트를 '블록의 리스트'로 다루는 순수 함수.
# 핵심은 각 블록이 자기 메타데이터를 갖는다는 것 —
# 우선순위(버릴 때 순서), 안정성(캐시 경계 판단), 토큰 수(예산 회계).
Stability = Literal["static", "session", "turn"]   # 캐시 무효화 주기

@dataclass(frozen=True)
class Block:
    kind: str                  # "system" | "tools" | "examples" | "state" | "history" | ...
    text: str
    tokens: int                # 정확한 토크나이저 카운트. 문자수/4 같은 추정은 회계를 망친다
    stability: Stability
    priority: int              # 낮을수록 먼저 버린다
    droppable: bool = True     # False면 예산 초과 시 잘라내지 않고 실패시킨다

@dataclass(frozen=True)
class Assembled:
    blocks: Sequence[Block]; dropped: Sequence[Block]; total_tokens: int

def assemble(candidates: Sequence[Block], budget: int) -> Assembled:
    # 안정성 순 → 캐시 접두사가 최대한 길게 유지되도록 static·session을 앞에 고정한다.
    order = {"static": 0, "session": 1, "turn": 2}
    ordered = sorted(candidates, key=lambda b: (order[b.stability], b.priority))

    # 필수 블록부터 자리를 확보한다. 필수가 예산을 넘으면 설계 실패이므로 조용히 넘어가지 않는다.
    used = sum(b.tokens for b in ordered if not b.droppable)
    if used > budget:
        raise ContextBudgetError(f"필수 블록만으로 예산 초과: {used} > {budget}")

    kept, dropped = [], []
    for b in ordered:
        if not b.droppable or used + b.tokens <= budget:
            kept.append(b)
            used += b.tokens if b.droppable else 0
        else:
            dropped.append(b)   # 버린 것을 반드시 반환한다. 조용한 절단이 최악의 버그다
    return Assembled(blocks=kept, dropped=dropped, total_tokens=used)
```

중요한 것은 알고리즘보다 **인터페이스**다. 컨텍스트를 블록의 리스트로 다루면 각 블록의 토큰 점유를 로깅할 수 있고(11절), 무엇이 버려졌는지 관측할 수 있으며, 캐시 경계를 계산할 수 있다(5절). f-string을 이어 붙이는 방식으로는 셋 다 할 수 없다.

**이 접근이 통하지 않는 경우.** 블록 단위 회계는 블록 경계에 의미가 있을 때만 유효하다. 논리적 단위 하나가 여러 블록에 걸쳐 있는데 그중 일부만 버려지면, 남은 조각이 오해를 부른다. 예를 들어 계약 조건 3개 중 2개만 남으면 모델은 "조건이 2개뿐"이라고 읽는다. 따라서 블록은 **자기완결적 단위**로 자르고, 일부만 버리면 위험한 블록은 `droppable=False`로 묶어야 한다.

두 번째로 조심할 것은 토큰을 세는 비용이다. 블록을 만들 때 한 번 세어 캐시해 두되, "문자 수 ÷ 4" 같은 추정은 쓰지 않는다. 한국어, JSON, 코드는 이 비율에서 크게 벗어나고, 회계가 몇 퍼센트만 틀려도 예고 없이 절단이 시작된다.

## 2. 컨텍스트는 예산이다: 항목별 회계 없이는 아무것도 통제할 수 없다

### 2.1 구성 요소 지도

컨텍스트에 들어가는 것을 성질별로 나누면 여덟 종류쯤 된다. 이 표는 이 장 나머지 부분의 목차 역할도 한다.

| 구성요소 | 전형적 점유 | 변동성 | 캐시 친화성 | 주된 위험 |
|---|---|---|---|---|
| 시스템 프롬프트 | 500~3,000 토큰 | 배포 단위로만 변함 | 매우 높음(접두사) | 고도(altitude) 오류 (4절) |
| 도구 정의 | 도구당 100~400 토큰 | 배포 단위 | 매우 높음 | 도구 폭발 ([[13 - 도구 사용 II — 도구 설계의 기술과 도구 폭발 문제]]) |
| few-shot 예시 | 예시당 200~1,500 토큰 | 고정 또는 동적 | 고정이면 높음 | 분포 불일치·캐시 파괴 (9절) |
| 세션 상태 요약 | 200~2,000 토큰 | 압축 시점에만 | 중간 | 손실의 지연 청구 (6절) |
| 대화 이력 | **무제한 증가** | 매 턴 | 접미사만 증가면 높음 | 열화·비용 (3절) |
| 도구 출력 | 호출당 50~50,000 토큰 | 매 턴 | 낮음 | 창 폭파 (8절) |
| 검색 결과 | 질의당 1,000~20,000 토큰 | 매 질의 | 낮음 | 방해자 유입 (7절) |
| 현재 지시 | 20~500 토큰 | 매 턴 | 없음(꼬리) | 위치가 잘못되면 묻힘 |

표의 토큰 범위는 벤치마크 결과가 아니라 **설계할 때 자릿수를 가늠하기 위한 어림값**이다. 저자가 실무에서 관측한 수준을 근거로 했으며, 도메인과 언어, 직렬화 방식에 따라 두세 배쯤은 쉽게 벗어난다. 그대로 믿을 값이 아니라 자기 시스템에서 직접 재 볼 항목의 목록으로 읽는 편이 맞다. 재는 방법은 11절에서 설명한다.

그렇더라도 가장 먼저 눈여겨볼 것은 **점유 범위의 자릿수 차이**다. 시스템 프롬프트는 3,000토큰을 넘기지 않으려고 애쓰는 항목인데, `SELECT *` 하나나 로그 조회 하나가 그 열 배를 아무렇지 않게 밀어 넣는다. 따라서 컨텍스트 관리의 성패는 손으로 쓰는 항목보다 **런타임에 생성되는 항목의 상한**에서 갈린다.

두 번째로 볼 것은 변동성 열이다. 변동성이 곧 캐시 레이아웃을 결정하고(5절), 조립 순서도 여기에 따라 정해진다. 배포 단위로만 바뀌는 것은 앞에, 매 턴 바뀌는 것은 뒤에 둔다.

### 2.2 예산을 선언적으로 쓰기

예산은 코드 곳곳에 흩어진 매직 넘버가 아니라 한곳의 선언으로 관리해야 한다. 그래야 리뷰할 수 있고, 환경별로 다르게 줄 수 있으며, 위반했을 때 알람을 걸 수 있다.

```yaml
# context-budget.yaml — 결제 지원 에이전트
# 총합이 모델 창보다 한참 작다는 점이 핵심. 창을 꽉 채우는 것은 목표가 아니다.
model:
  window: 200000            # 광고된 창
  reserve_output: 8000      # 출력 토큰 몫. 빼먹으면 긴 답변에서 잘린다
  working_limit: 60000      # 실제 운용 상한 — 창의 30%. 근거는 3절(열화)과 40장(비용)
allocation:
  system:        { max: 2500,  droppable: false }
  tools:         { max: 6000,  droppable: false }   # 초과하면 도구를 줄인다, 설명을 줄이지 않는다
  examples:      { max: 4000,  droppable: true,  priority: 30 }
  state_summary: { max: 3000,  droppable: false }   # 압축 산출물은 절대 안 버린다
  history:       { max: 24000, droppable: true,  priority: 20, strategy: drop_oldest_pairs }
  retrieval:     { max: 12000, droppable: true,  priority: 10 }
  tool_output:   { max: 8000,  droppable: true,  priority: 10, per_call_max: 4000 }
compaction:
  trigger_ratio: 0.75       # working_limit의 75% 도달 시
  hard_preserve: [decisions, open_items, constraints, identifiers]
alerts:
  truncation_rate_gt: 0.02  # 절단이 2%를 넘으면 예산 설계가 틀린 것
  cache_hit_rate_lt: 0.60
```

`working_limit`을 `window`의 30%로 잡은 근거는 다음 절에서 다룬다. 여기서는 **`reserve_output`** 을 짚고 넘어가자. 입력 예산만 세고 출력 몫을 빼먹는 것은 놀랄 만큼 흔한 버그이고, 증상도 까다롭다. 평소에는 멀쩡하다가 모델이 긴 답변을 시도할 때만 출력이 잘린다. 잘린 출력은 대개 JSON 중간에서 끊겨 파싱 실패로 나타나므로([[11 - 구조화된 출력 — 스키마·제약 디코딩·파싱 실패의 처리]]), 원인이 예산이라는 것을 알아채기까지 시간이 걸린다.

> [!note] 실무 규칙
> 컨텍스트 예산은 "모델 창 − 출력 몫 − 안전 마진"으로 정하지 말고, **과업에 실제로 필요한 양에서 출발해 위로 쌓아 올린 값**으로 정해야 한다. 창에서 빼는 방식으로 정하면 늘 창을 꽉 채우게 되고, 채운 만큼 열화와 비용을 치른다.

### 2.3 예산 회계가 통하지 않는 경우

세 가지 경우가 있다.

**항목 하나가 예산 전체를 넘을 때.** 고객이 40MB짜리 정산 CSV를 첨부했다면 어떤 배분표도 소용이 없다. 이때 필요한 것은 예산이 아니라 **처리 전략의 변경**이다. 코드로 처리하고 결과만 넣거나([[26 - 환경과 행동 공간 — 코드 실행·CodeAct·브라우저·컴퓨터 사용]]), 데이터는 외부에 두고 포인터만 넘긴다(7절). 예산 초과를 절단으로 처리하면 모델은 잘린 CSV의 앞 200줄만 보고 전체를 판단한다.

**우선순위가 실제 유용성과 관계없을 때.** `priority` 숫자는 우리의 추측일 뿐이다. 검색 결과가 이력보다 중요한지는 과업마다 다르고 턴마다 다르다. 고정 우선순위는 평균적으로만 맞고, 평균적으로 맞는 값이 특정 케이스에서는 치명적으로 틀릴 수 있다. 해법은 우선순위를 더 정교하게 만드는 것이 아니다. 그 방향으로는 끝이 없다. 그보다 **버려진 것을 관측하고, 무언가 버려진 뒤 실패한 케이스를 모아 예산을 조정해야 한다.**

**압축 자체가 예산을 쓸 때.** 요약을 만들려면 요약할 대상을 모델에 넣어야 하고, 그 호출에도 토큰과 시간이 든다. 이력이 계속 늘어나는 긴 세션에서는 압축이 또 다른 압축을 부르고, 어느 순간 "일하는 시간보다 정리하는 시간이 더 긴" 상태가 된다. 6절에서 압축 트리거를 비율이 아니라 **경계**로 잡으라고 권하는 것도 이 때문이다.

## 3. "다 넣으면 안전하다"는 생각은 왜 틀렸을까: 컨텍스트 열화

컨텍스트 창이 8K였을 때는 예산 관리가 물리적으로 피할 수 없는 일이었다. 창이 200K, 1M으로 커진 지금은 사정이 달라서 "이제 다 넣으면 되지 않나?"라는 질문이 나온다. 답은 **아니다**이고, 이유는 세 가지다. 비용, 지연(prefill 시간이 길이에 비례해 늘어난다), 그리고 가장 중요한 **정확도**다. 앞의 두 가지는 분명하니 세 번째를 자세히 살펴보자.

### 3.1 모든 위치가 똑같이 읽히지는 않는다

가장 잘 재현된 관측부터 시작하자. Nelson F. Liu 등의 "Lost in the Middle: How Language Models Use Long Contexts"(2023년 arXiv 프리프린트, TACL 2024 게재)는 다중 문서 QA와 키-값 검색 과업에서, 정답이 들어 있는 문서의 **위치**에 따라 정확도가 달라진다는 것을 보였다. 성능 곡선은 U자 모양이다. 맨 앞과 맨 뒤에서 높고 가운데에서 낮다.

문서 수를 늘려 컨텍스트를 길게 하면 전체 성능이 더 떨어진다. 이 결과는 이후 여러 모델과 과업에서 같은 형태로 반복 관찰되었고, 지금은 긴 컨텍스트를 설계할 때 기본으로 전제하는 사실처럼 취급된다.

왜 U자가 되는지에 대해서는 몇 가지 설명이 나와 있다. 학습 데이터에서 문서의 시작부와 끝부분이 구조적으로 중요하다는 점, 위치 인코딩이 최근 토큰에 유리하다는 성질, 지시 튜닝 데이터의 형태 등이다. 이 중 무엇이 주된 원인인지는 단정하지 않는 편이 안전하다. 실무에서 중요한 것은 **이 관측이 견고하다는 사실**과 거기서 나오는 배치 규칙이다.

```
컨텍스트 창의 유효 주의 (도식 — 정확한 곡선이 아니라 형태의 요약)

 정확도 ^
   |█                                                     █
   |███                                                 ███
   |█████                                          █████
   |██████████                            ██████████
   |███████████████                  ███████████████
   +--------------------------------------------------------> 위치
   시작                        가운데                       끝
   ↑                            ↑                           ↑
 시스템·도구 정의        여기 묻힌 것은            현재 지시·최신 도구 결과
 (안정, 반복 노출)        "없는 것에 가깝다"        (가장 강하게 작동)
```

여기서 세 가지 배치 규칙이 나온다.

- **결정적인 지시는 앞과 뒤 양쪽에 둔다.** 시스템 프롬프트에 규칙을 쓰고, 긴 문서 뒤에 "위 문서를 근거로 답하되 문서에 없는 내용은 '자료 없음'이라고 하라"는 지시를 다시 붙인다. 중복이지만 효과가 있는 중복이다.
- **중요한 검색 결과를 가운데에 묻지 않는다.** 재랭킹 점수가 높은 것을 앞뒤에, 낮은 것을 가운데에 두는 배열이 실무에서 자주 쓰인다. 다만 순위를 신뢰할 수 있을 때만 의미가 있다.
- **긴 것 자체를 줄인다.** 앞의 두 규칙은 완화책일 뿐 해결책이 아니다.

### 3.2 방해자는 적극적으로 오답을 유도한다

실무에서는 위치 편향보다 **방해자(distractor)** 가 더 자주 사고를 낸다. 무관한 정보가 컨텍스트에 있으면 모델의 주의가 흐려지는 데서 그치지 않고, 그 정보가 **오답의 재료로 쓰인다.**

결제 도메인에서 예를 들어 보자. "카드 결제가 실패했다"는 문의에 검색기가 문서 12개를 가져왔는데, 그중 하나가 **다른 PG사의** 오류 코드표다. 거기에도 `8104`가 있지만 의미는 다르다. 모델은 정답 문서와 방해자를 모두 보고 있다. 이때 나타나는 실패는 "모른다"가 아니라 **"다른 PG의 해석을 자신 있게 답하는 것"** 이다. 방해자가 없었다면 "해당 코드에 대한 자료가 없다"고 답했을 수도 있다. 문서를 더 넣었기 때문에 정확도가 떨어진 것이다.

Chroma Research가 2025년 7월에 발표한 기술 보고서 "Context Rot: How Increasing Input Tokens Impacts LLM Performance"(Kelly Hong, Anton Troynikov, Jeff Huber)는 18개 모델을 대상으로, 입력 길이가 늘어나면 성능이 **일관되게 유지되지 않고** 아주 단순한 과업에서도 열화가 나타난다고 보고했다.

이 보고서가 강조하는 점 하나는 특히 실무에 유용하다. 중요한 것은 관련 정보가 컨텍스트에 **존재하는지**가 아니라 **어떻게 제시되는지**라는 점이다.

> [!warning] 흔한 오해
> "needle-in-a-haystack 테스트를 100% 통과했으니 이 모델은 긴 컨텍스트를 잘 다룬다"는 생각은 틀렸다. NIAH 계열 테스트는 대개 **어휘적으로 눈에 띄는 문장 하나**를 무관한 텍스트 더미에 심어 두고 찾게 한다. 이것은 검색 과업이지 추론 과업이 아니다. 실제 에이전트는 컨텍스트 전체에 흩어진 여러 사실을 **종합**하고, 서로 모순되는 정보 중 무엇이 최신인지 판단하고, 관련 있어 보이지만 실제로는 관련 없는 것을 **배제**해야 한다.
>
> 실제로 질문과 needle 사이의 어휘 중첩을 일부러 없애서, 잠재적 연관을 추론해야만 풀 수 있게 만든 벤치마크(Modarressi 등, "NoLiMa: Long-Context Evaluation Beyond Literal Matching", ICML 2025)에서는 같은 모델의 점수가 훨씬 빨리 떨어진다. 논문이 든 예에서 GPT-4o의 정확도는 짧은 컨텍스트에서 99.3%였다가 32K 지점에서 69.7%로 내려간다. NIAH는 하한을 확인하는 도구이지, 상한을 보증하는 도구가 아니다.

### 3.3 유효 컨텍스트는 자기 도메인에서 재야 한다

2.2절에서 "창의 30%를 운용 상한으로 잡는다"고 한 숫자는 어디서 나왔을까? 솔직히 말하면 **일반적으로 통하는 상수는 없다.** 모델, 과업, 컨텍스트 구성 방식마다 다르고, 벤더가 발표하는 장문 벤치마크 점수도 컨텍스트 구성이 우리 시스템과 달라 그대로 가져다 쓸 수 없다. 필요한 것은 **자기 과업으로 만든 열화 곡선**이며, 만드는 방법은 단순하다.

```python
# 유효 컨텍스트 측정: 정답이 고정된 케이스에 '패딩'을 늘려 가며 정확도를 잰다.
# 패딩은 로렘입숨이 아니라 '그럴듯하지만 무관한 우리 도메인 문서'여야 한다 —
# 무의미한 패딩은 모델이 쉽게 무시하므로 열화를 과소평가하게 된다.
LENGTHS = [4_000, 8_000, 16_000, 32_000, 64_000, 128_000]

def measure(cases, distractor_pool, llm) -> dict[int, float]:
    curve = {}
    for target in LENGTHS:
        correct = 0
        for case in cases:
            padding = sample_until(distractor_pool, target - case.tokens)
            # 위치 편향을 평균화하기 위해 정답 문서 위치를 무작위화한다.
            ctx = shuffle_with_answer_at_random_position(case.answer_doc, padding)
            correct += case.check(llm.complete(system=SYSTEM, messages=[user(ctx, case.question)]))
        curve[target] = correct / len(cases)
    return curve

# 판독: 정확도가 기준선 대비 유의미하게 꺾이는 지점이 그 과업의 '유효 컨텍스트'다.
# 모델 교체·프롬프트 변경 때마다 다시 재야 한다 — 41장의 회귀 테스트 대상이다.
```

이렇게 재 보면 흔히 두 가지 결과가 나온다. 하나는 곡선이 꺾이는 지점이 **광고된 창보다 훨씬 앞**에 있다는 것이다. 다른 하나는 꺾이는 신호가 **정확도가 아닌 다른 지표에서 먼저 나타난다**는 것이다. 답은 여전히 맞지만 형식 준수가 무너지거나(JSON 필드 누락), 지시 준수가 무너진다(금지한 표현을 쓴다).

긴 컨텍스트에서 시스템 프롬프트의 제약이 먼저 약해지는 현상은 실무에서 반복해서 보고된다. 4절의 시스템 프롬프트 설계와 3.1절의 "지시를 뒤에도 반복한다"는 규칙이 여기서 연결된다.

**이 측정이 잘못된 결론으로 이끄는 경우.** 합성 패딩으로 만든 곡선은 실제 세션의 열화를 과소평가한다. 실제 세션은 무관한 문서가 아니라 **모델 자신의 과거 발화**로 채워져 있고, 그중 일부는 지금 상황과 모순된다. 3턴 전에 "이 결제는 취소됐다"고 판단했다가 나중에 뒤집힌 경우가 그렇다. 이렇게 모순된 자기 이력은 무관한 문서보다 훨씬 강력한 방해자다. 따라서 곡선은 상한의 근사치로만 쓰고, 실제 상한은 프로덕션 트레이스에서 세션 길이와 실패율의 상관관계로 확인하는 편이 낫다([[39 - 관측성 — 트레이싱·로깅·리플레이·디버깅]]).

> [!warning] 흔한 오해
> "컨텍스트가 1M이니 RAG는 필요 없다"는 생각은 세 가지 면에서 동시에 틀렸다.
>
> - **비용**: 1M 토큰을 매 턴 다시 보내는 것은 캐시를 감안해도 검색보다 몇 자릿수 비싸다.
> - **지연**: prefill 비용은 길이에 대해 최소한 선형으로 늘고, 어텐션 항까지 세면 그보다 더 늘어난다. 사용자 체감은 첫 토큰이 나오기까지의 시간에 좌우된다.
> - **정확도**: 위에서 본 열화가 그대로 나타난다.
>
> 긴 컨텍스트가 바꾼 것은 "검색이 필요 없어졌다"가 아니라 **"청크를 더 크게 가져가도 된다"** 와 **"재랭킹 정밀도에 대한 요구가 완화됐다"** 이다. RAG가 끝난 것이 아니라 하이퍼파라미터가 이동한 것이다(24장 RAG와 에이전틱 검색).

## 4. 시스템 프롬프트의 고도: 너무 낮으면 부서지고 너무 높으면 흔들린다

시스템 프롬프트는 컨텍스트에서 토큰 비중은 가장 작지만 영향력은 가장 큰 블록이다. 매 턴 반복해서 노출되고, 창의 맨 앞(3.1절 U자 곡선에서 유리한 자리)에 있으며, 다른 모든 블록을 해석하는 규칙을 정한다. 그래서 무엇을 어떤 **추상 수준**으로 쓸지가 따로 다뤄야 할 설계 문제가 된다. 이 추상 수준을 "고도(altitude)"라고 부르자.

### 4.1 세 가지 고도의 실제 모습

결제 실패 문의를 처리하는 지원 에이전트라는 같은 과업을 세 가지 고도로 써서 나란히 놓아 보자.

**저고도 (하드코딩된 논리).**

```text
결제 실패 문의를 처리하라.
- pg_code가 8104이면 "KCP 상점 승인 상태 문제입니다. KCP에 문의하세요"라고 답하라.
- pg_code가 504412이면 "가상계좌 부분환불 미계약입니다"라고 답하라.
- pg_code가 01이고 채널이 이니시스이면 ... (이하 60줄)
- 위에 없는 코드이면 "확인 후 회신드리겠습니다"라고 답하라.
- 단, 채널이 KCP_V2이고 pg_code가 8104이고 storeId가 store-1234이면 ...
```

**중고도 (판단 기준과 절차).**

```text
너는 PG 연동 결제의 실패 원인을 판별하는 지원 엔지니어다.

## 판별 절차
1. 결제 건을 조회해 채널·PG사·시각·금액·상태를 확정한다. 사용자가 말한 것과
   조회 결과가 다르면 조회 결과를 따르되, 차이를 답변에 명시한다.
2. PG 원본 응답(코드·메시지)을 확보한다. 확보하지 못했으면 추측하지 않는다.
3. 원인을 세 범주 중 하나로 분류한다:
   - 가맹점 설정 문제(PG측 계약·개통·MID 설정) → 고객이 PG사에 요청해야 함
   - 우리 시스템 문제(요청 조립·상태 전이·타임아웃) → 내부 티켓 생성
   - 고객 행동(사용자 취소, 잔액 부족, 창 이탈) → 안내로 종결
4. 범주가 확정되지 않으면 "확정되지 않음"으로 두고 사람에게 넘긴다.

## 원칙
- 코드표 해석은 반드시 채널의 PG사와 일치하는 표에서 온 것이어야 한다.
  다른 PG사의 같은 숫자 코드는 의미가 다르다.
- 금액·식별자·시각은 원문 그대로 인용한다. 요약하거나 반올림하지 않는다.
- 되돌릴 수 없는 조치는 제안만 하고 실행하지 않는다.
```

**고고도 (막연한 역할 부여).**

```text
너는 도움이 되고 정확하며 전문적인 결제 지원 전문가다.
고객의 문제를 신속하게 파악하고 최선의 해결책을 제시하라. 항상 친절하게 응대하라.
```

저고도 프롬프트는 **행동을 완전히 예측할 수 있게 해 주지만, 처음 보는 입력에는 무너진다.** 코드표가 60줄이면 61번째 코드에서 무너지고, PG사가 늘어날 때마다 조합이 곱으로 늘어난다. 무엇보다 코드로 써야 할 것을 프롬프트로 쓴 것이다. 결정론적 매핑은 딕셔너리 조회로 처리하고, 그 조회를 **도구**로 제공해야 한다. 이런 매핑을 프롬프트에 넣으면 매 턴 토큰을 쓰면서 확률적으로 실행되는 룩업 테이블이 생긴다.

고고도 프롬프트는 반대 방향으로 실패한다. "정확하게"가 무엇인지는 모델이 알아서 채우고, 그 내용이 요청마다 달라진다. 게다가 이런 프롬프트는 **평가할 수 없다.** 무엇이 위반인지 정의되어 있지 않으니 회귀를 감지할 수 없다.

목표는 중고도다. 절차는 있지만 각 단계의 판단은 모델에게 맡기고, **하지 말아야 할 것과 확신이 없을 때 할 행동**을 명시하며, 모든 서술을 검증할 수 있다. 예를 들어 "다른 PG사 코드표를 인용하지 않는다"는 규칙은 평가 케이스로 만들 수 있다.

| 고도 | 형태 | 강점 | 실패 방식 | 진짜 처방 |
|---|---|---|---|---|
| 저 | if-else 나열, 케이스 열거 | 열거된 케이스에서 완벽 | 미열거 입력에서 붕괴, 조합 폭발, 유지보수 불가 | 코드/도구/DB로 옮긴다 |
| 중 | 절차 + 판단 기준 + 금지 + 기권 | 일반화되고 평가 가능 | 도메인이 크게 바뀌면 절차 자체가 낡음 | 절차를 버전으로 관리 |
| 고 | 역할·형용사 나열 | 짧고 유연 | 행동 분산, 회귀 감지 불가 | 관측된 실패를 규칙으로 승격 |

> [!note] 실무 규칙
> 시스템 프롬프트에 조건 분기가 세 개 이상 쌓이기 시작하면 고도가 낮아지고 있다는 신호다. 이때는 그 분기를 **결정론적으로 판단할 수 있는지** 물어야 한다. 판단할 수 있으면 코드로 옮기고, 판단할 수 없으면 그 판단의 **기준**을 쓴다. "A면 B하라"가 아니라 "A인지 판단하는 방법과 그 결과로 무엇이 달라지는지"를 쓰는 것이다.

### 4.2 고도를 유지하는 문서 구조

중고도를 유지하려면 프롬프트에 구조가 있어야 한다. 실무에서 반복해서 수렴하는 형태는 다음 여섯 절이다.

- **역할과 범위**: 무엇을 하고 무엇은 하지 않는가.
- **입력에 대해 알아야 할 것**: 데이터의 성질과 신뢰도, 알려진 함정.
- **절차**: 번호를 매긴 단계. 각 단계는 관찰할 수 있는 산출물을 남긴다.
- **판단 기준**: 애매한 경계를 가르는 방법. 긍정 예와 부정 예를 함께 든다.
- **금지와 기권**: 절대 하지 않을 것과 확신이 없을 때의 행동.
- **출력 형식**: 다만 스키마는 여기에 쓰지 않고 응답 스키마로 강제한다.

이 중 자주 과소평가되는 항목이 **"금지와 기권"** 이다. 모델은 기본적으로 답을 만들어 내는 쪽으로 기울며, "모른다"는 선택지는 명시하지 않으면 사실상 없는 것과 같다. 02장(LLM이라는 재료)에서 다룬 것처럼, 평가 관행이 추측을 벌하지 않으면 추측이 남는다. 기권 경로를 **1급 결과**로 만드는 한 줄이 오답률을 눈에 띄게 줄이는 경우가 많다. 다만 기권을 너무 매력적으로 만들면 쉬운 문제까지 넘기므로, 기권 조건을 구체적으로 쓰는 것이 균형을 잡는 방법이다.

판단 기준에는 **부정 예**를 반드시 넣는다. "환불 요청으로 분류한다"만 있으면 "배송이 늦어 짜증난다"도 환불 요청이 된다. "단, 아직 환불을 요구하지 않은 불만 표현은 제외한다"는 문장이 있어야 경계가 선다. 도구 설명에도 똑같이 적용되는 원리다(13장 도구 사용 II).

### 4.3 고도 조절이 통하지 않는 경우

**모델 능력이 절차를 따라가지 못할 때.** 고도는 절대적인 속성이 아니라 모델 능력에 따라 달라진다. 같은 중고도 프롬프트라도 강한 모델에서는 잘 작동하고, 작은 모델에서는 단계를 건너뛴다. 따라서 모델을 낮은 티어로 바꾸면(40장(비용과 지연)의 비용 라우팅) 고도를 낮춰야 할 수도 있다. "모델만 바꿨는데 왜 깨지죠?"라는 질문의 답은 대개 여기에 있다.

**규칙끼리 충돌할 때.** "간결하게 답하라"와 "모든 근거를 인용하라"가 함께 있으면, 모델은 둘 중 하나를 임의로 고르고 그 선택이 입력마다 달라진다. 이것은 고도가 아니라 **일관성**의 문제이며, 해법은 충돌하는 지시에 명시적인 우선순위를 주는 것이다. 프롬프트가 200줄을 넘으면 이런 잠재적 충돌을 사람이 다 추적하지 못한다. 그렇게 길어졌다는 것 자체가 프롬프트를 나눠야 한다는 신호다.

**긴 컨텍스트에서 지시가 약해질 때.** 3.3절에서 보았듯이 컨텍스트가 길어지면 정확도보다 지시 준수가 먼저 무너진다. 대응 방법은 두 가지다. 하나는 결정적인 제약을 **꼬리에서 반복**하는 것이고, 다른 하나는 제약을 프롬프트가 아니라 **바깥에서 강제**하는 것이다. 스키마 검증(11장 구조화된 출력), 도구 화이트리스트, 승인 게이트([[35 - 휴먼 인 더 루프 — 승인·개입·에스컬레이션]])가 여기에 해당한다. 프롬프트의 지시는 부드러운 사전확률일 뿐 보안 경계가 아니다. 이 구분은 [[37 - 프롬프트 인젝션과 에이전트 보안 — 신뢰 경계의 붕괴]]에서 훨씬 심각한 맥락으로 다시 등장한다.

> [!warning] 흔한 오해
> "시스템 프롬프트에 넣었으니 모델이 반드시 지킨다"는 생각은 틀렸다. 역할 계층(system > developer > user > tool)은 학습으로 주입된 **경향성**일 뿐, 실행 시점에 강제되는 규칙이 아니다. 컨텍스트가 길어지거나, 사용자 입력이 반대 방향으로 강하게 밀거나, 도구 출력에 지시처럼 보이는 문자열이 섞이면 이 경향성은 얼마든지 뒤집힌다. 판단 기준은 하나다. **위반이 일어났을 때 되돌릴 수 없는가?** 되돌릴 수 없다면 코드로 강제한다.

## 5. 컨텍스트 배치는 캐시 레이아웃 문제다

여기서 성격이 다른 제약이 하나 들어온다. 지금까지의 관심사가 "모델이 잘 읽게 하려면 어떻게 할까"였다면, 이제는 "같은 것을 두 번 계산하지 않으려면 어떻게 할까"다. 이 제약은 배치 순서를 사실상 정해 버린다.

### 5.1 접두사 캐싱의 동작 원리

02장(LLM이라는 재료)에서 본 것처럼 생성은 prefill과 decode로 나뉘고, prefill 단계에서는 입력 전체를 병렬로 처리해 각 토큰의 KV 텐서를 만든다. 여기서 중요한 성질이 하나 있다. 인과 어텐션(causal attention)에서 **위치 $i$의 KV는 위치 $0..i$의 토큰에만 의존한다.** 뒤에 무엇이 오든 앞부분의 KV는 바뀌지 않는다.

접두사 캐싱이 성립하는 이유는 이것이 전부다. 두 요청의 토큰 시퀀스가 앞에서 $k$개까지 **완전히 같으면** 그 $k$개의 KV를 재사용할 수 있다. 반대로 $k+1$번째에서 한 토큰이라도 다르면 그 뒤는 모두 다시 계산해야 한다.

```
요청 A: [시스템 2,400][도구 5,800][예시 3,900][이력 18,000][현재 지시 120]
요청 B: [시스템 2,400][도구 5,800][예시 3,900][이력 18,000 + 도구결과 1,400][현재 지시 90]
         └──────────── 동일한 접두사 30,100 토큰 ────────────┘
                                                    ↑ 여기부터 재계산

→ B의 prefill 비용: 30,100 토큰은 캐시 읽기, 1,490 토큰만 신규 계산.

반대 배치였다면:
요청 A: [현재 지시 120][이력 18,000][예시 3,900][도구 5,800][시스템 2,400]
요청 B: [현재 지시 90 ][...]
         └ 첫 토큰부터 다름 → 캐시 적중 0. 30,000 토큰을 매 턴 다시 계산.
```

주요 프로바이더의 과금 구조에도 이 성질이 반영되어 있다. Anthropic API를 예로 들면(2026년 초 기준) 캐시 쓰기는 기본 입력 단가의 1.25배(5분 TTL 기준, 1시간 TTL은 2배), 캐시 읽기는 0.1배로 과금되고, 캐시할 수 있는 최소 길이가 모델별로 정해져 있다(대형 모델 기준 1,024토큰 수준). 계산은 단순하다. 캐시 없이 두 번 호출하면 $1.0 + 1.0 = 2.0$이고, 캐시를 걸면 $1.25 + 0.1 = 1.35$다. 즉 **한 번만 재사용해도 이득이다.**

OpenAI 계열은 명시적인 마커 없이 자동으로 접두사를 캐싱하는 형태로 제공되어 왔다. 세부 수치는 바뀌기 마련이니 구조를 기억해 두는 편이 낫다. 쓰기는 조금 비싸고, 읽기는 훨씬 싸며, 정확히 일치하는 접두사에만 적용된다.

```json
// 캐시 경계를 명시적으로 두는 요청 형태(중립화된 표현).
// 경계 앞은 '재사용 대상', 뒤는 '매 턴 변하는 것'.
{
  "system": [{ "type": "text", "text": "너는 PG 연동 결제의...(2,400토큰)",
               "cache_control": { "type": "ephemeral" } }],
  "tools": [{ "name": "get_payment", "input_schema": {} }],
  "messages": [
    { "role": "user", "content": [
        { "type": "text", "text": "...세션 상태 요약(압축 산출물, 1,800토큰)...",
          "cache_control": { "type": "ephemeral" } }]},
    { "role": "user", "content": "...최근 4턴 원문..." },
    { "role": "user", "content": "그럼 재시도하면 성공할까?" }
  ]
}
```

경계를 앞쪽에만 두면 캐시 적중 구간이 짧다. 뒤쪽까지 경계를 여러 개 두면 적중 구간은 길어지지만 쓰기 비용이 늘고 관리가 복잡해진다. 실무에서 기본으로 쓰는 경계는 두 개다. 하나는 **도구 정의 끝**(배포 단위로만 바뀐다)이고, 다른 하나는 **압축 산출물 끝**(압축할 때만 바뀐다)이다.

### 5.2 캐시를 깨뜨리는 흔한 실수

아래 실수는 모두 "동작은 하는데 비용이 몇 배로 드는" 형태로 나타난다. 그래서 캐시 적중률을 계측하지 않으면 몇 달이 지나도 모르고 지나간다.

| 실수 | 왜 깨지는가 | 대안 |
|---|---|---|
| 시스템 프롬프트에 `현재 시각: 2026-07-20 14:33:21` | 매 요청 접두사 첫 블록이 달라짐 | 시각은 꼬리에 넣거나, 도구로 조회하게 한다 |
| 시스템 프롬프트에 요청 ID·트레이스 ID | 위와 동일 | 로깅 메타데이터로만 보관 |
| 도구 목록을 상황에 따라 동적 구성 | 도구 정의가 접두사인데 매번 다름 | 도구 집합을 소수의 고정 프로필로 묶고 프로필 단위로 라우팅 |
| 도구 정의를 `dict` 순회로 직렬화 | 순서가 실행마다 달라질 수 있음 | 항상 결정론적 정렬로 직렬화 |
| few-shot을 매 턴 검색으로 선택 | 예시 블록이 매번 다름 | 고정된 표준 예시를 쓰거나, 동적 예시를 캐시 경계 **뒤**로 |
| 대화 이력 중간을 편집·재요약 | 접두사가 소급 변경됨 | 압축은 접미사만 남기고 앞을 통째로 교체하는 방식으로 |
| JSON 직렬화 시 공백·키 순서가 불안정 | 토큰 시퀀스가 미세하게 달라짐 | 정규화된 직렬화기 하나로 통일 |

마지막 항목은 특히 알아차리기 어렵다. `json.dumps`의 기본 구분자와 `ensure_ascii` 설정, 키 정렬 여부가 호출 지점마다 다르면, 논리적으로 같은 내용이 서로 다른 토큰 시퀀스가 된다. [[41 - JSON과 직렬화]]에서 다룬 직렬화 안정성 문제가 여기서는 곧바로 비용 문제가 된다.

```python
# 캐시 안정성을 위한 정규화된 직렬화. 조립기 전체가 이것만 쓰게 강제한다.
# sort_keys: 키 순서 고정 / separators: 공백 제거로 토큰 절약 및 형태 고정
# ensure_ascii=False: 한국어를 \uXXXX로 부풀리지 않는다(토큰 수가 크게 달라진다)
stable = lambda o: json.dumps(o, sort_keys=True, ensure_ascii=False, separators=(",", ":"))
```

> [!warning] 흔한 오해
> "프롬프트 캐싱은 켜기만 하면 비용이 줄어든다"는 생각은 틀렸다. 캐시 쓰기는 기본 단가보다 비싸므로, **재사용되지 않는 접두사에 캐시를 걸면 오히려 손해**다. 한 번 호출하고 끝나는 단발 분류 요청이나, 사용자가 몇 시간에 한 번 오는 저빈도 세션에 건 5분 TTL 캐시가 그렇다. 캐시는 "재사용 확률 × 접두사 길이"가 충분히 클 때만 이득이다. 적중 여부는 응답 메타데이터에 보고되므로 **추정하지 말고 재야 한다.**

### 5.3 캐시 친화성과 신선도가 충돌하는 지점

캐시가 배치를 정한다는 말은, 정보의 중요도가 아니라 **변동 주기**에 따라 순서가 정해진다는 뜻이다. 여기서 실제로 충돌이 생긴다.

가장 흔한 충돌은 **동적 컨텍스트의 위치**다. "이 고객은 VIP이고 최근 3건의 클레임이 있다" 같은 정보는 중요하므로 앞에 두고 싶다. 하지만 고객마다 다르기 때문에 앞에 두면 캐시가 고객 단위로 쪼개진다. 선택지는 세 가지다.

- **꼬리로 보낸다.** 캐시는 지키지만 U자 곡선에서 유리한 자리를 쓰지 못한다.
- **고객별 캐시를 받아들인다.** 같은 고객이 여러 턴을 이어 가는 세션에서는 이득이지만, 한 턴만 쓰고 떠나면 손해다.
- **정적 부분과 동적 부분을 분리한다.** 대부분의 경우 이것이 최선이다. "VIP 고객 응대 원칙"이라는 긴 설명은 시스템 프롬프트에 두고 캐시하며, "이 고객은 VIP다"라는 짧은 사실만 꼬리에 매 턴 새로 넣는다.

두 번째 충돌은 **압축과 캐시** 사이에서 생긴다. 압축하면 이력의 앞부분이 요약으로 교체되므로, 그 지점 이후의 접두사가 모두 무효가 된다. 즉 압축은 토큰을 아끼는 대신 **캐시를 통째로 버린다.** 압축 직후 한 턴은 전체를 다시 계산해야 하고, 그 비용이 압축으로 아낀 몫을 상당 부분 상쇄한다. 그래서 자주 조금씩 압축하는 것은 나쁜 전략이고, **드물게 크게** 압축하는 편이 낫다.

> [!note] 실무 규칙
> 캐시 적중률과 압축 빈도는 **함께** 봐야 한다. 적중률이 60% 아래인데 압축이 잦다면 트리거가 너무 예민한 것이다. 적중률이 낮은데 압축은 드물다면 접두사에 변동 요소가 섞여 있는 것이다(위 표에서 찾아본다). 둘을 따로 보면 원인을 가려낼 수 없다.

## 6. 압축은 손실 압축이다: 무엇을 버릴지 정하는 문제

컨텍스트가 예산에 도달했을 때 선택지는 세 가지뿐이다. **자르거나(truncation), 요약하거나(compaction), 밖으로 내보내는(externalization)** 것이다. 이 절에서는 두 번째를, 다음 절에서는 세 번째를 다룬다.

### 6.1 자르기는 왜 거의 항상 나쁠까

가장 단순한 전략은 오래된 메시지부터 버리는 것(FIFO)이다. 구현은 쉽지만, 접두사를 바꾸기 때문에 캐시 관점에서도 사실 좋지 않다. 그런데 무엇보다 나쁜 점은 **버려지는 것이 대개 가장 중요한 것**이라는 데 있다. 에이전트 세션의 초반 턴에는 사용자의 원래 요청, 제약 조건, 합의된 목표, 초기 조사에서 확정한 사실이 들어 있다. 후반 턴에는 세부 조정과 반복되는 도구 호출이 쌓인다.

FIFO는 정확히 거꾸로 버리는 셈이다. 20턴짜리 조사 세션에서 "원래 무엇을 찾으라고 했는지"가 사라지면 에이전트는 방향을 잃고 표류한다. 04장(에이전트 루프)에서 말한 "진행 없는 루프"가 생기는 흔한 원인이다.

예외는 대화가 **에피소드 단위**로 끊기고 턴 사이의 의존이 약한 경우다. 판단 기준은 "3턴 전 내용을 몰라도 지금 턴을 처리할 수 있는가?"이다. 그렇다면 자르기로 충분하고, 그렇지 않다면 압축이 필요하다.

### 6.2 무엇을 보존하고 무엇을 버릴까

압축의 핵심은 요약 품질이 아니라 **보존 목록의 설계**다. 요약 프롬프트를 잘 쓰는 것보다, 무엇을 반드시 남길지 명시적으로 정하는 쪽이 훨씬 큰 차이를 만든다.

| 반드시 보존             | 이유                                | 버려도 되는 것      | 이유                   |
| ------------------ | --------------------------------- | ------------- | -------------------- |
| 원래 목표와 제약          | 표류 방지. 가장 자주 유실되고 가장 비싸다          | 실패한 시도의 원문    | 결론만 남기면 된다           |
| 확정된 결정과 그 근거       | 재논의 방지. 근거가 없으면 뒤집힌다              | 중간 탐색 경로      | "A를 봤는데 아니었다"만 남기면 됨 |
| 미해결 항목(open items) | 잊히면 영원히 안 돌아온다                    | 도구 호출의 원본 인자  | 결과만 남으면 대개 충분        |
| **식별자 원문**         | paymentId·txId·경로·URL. 요약하면 복구 불가 | 장황한 서술문       | 정보 밀도가 낮다            |
| 사용자가 명시한 선호·금지     | 위반 시 신뢰 상실                        | 인사·확인 응답      | 정보 없음                |
| 실패한 접근의 **결론**     | 같은 실패 반복 방지                       | 성공한 도구 출력의 전문 | 요약 + 재조회 가능성         |

이 중 굵게 표시한 **식별자 원문**은 특히 중요하다. 요약 모델은 `paymentId: pay_01HQ8ZK3M9X2`를 "결제 건"으로 바꿔 버리는 경향이 있고, 그렇게 되는 순간 그 건을 다시 조회할 방법이 사라진다. 해법은 요약을 자유 텍스트로 두지 않고 **구조화된 상태 객체**로 만드는 것이다.

```kotlin
// 압축 산출물을 자유 텍스트가 아니라 타입으로 정의한다.
// 이렇게 하면 (1) 식별자가 문자열 요약에 녹아 사라지지 않고
//            (2) 필드별로 크기 상한을 걸 수 있고
//            (3) 압축의 회귀를 테스트할 수 있다 (필드 유실 = 실패)
data class SessionState(
    val goal: String,                              // 원래 요청. 요약 대상 아님 — 원문 보존
    val constraints: List<String>,                 // 사용자가 명시한 제약·금지
    val decisions: List<Decision>,                 // 확정된 것과 그 근거
    val openItems: List<String>,                   // 아직 안 끝난 것
    val entities: Map<String, EntityRef>,          // 식별자 테이블 — 절대 요약 금지
    val ruledOut: List<RuledOut>,                  // 시도했고 아니었던 것 (반복 방지)
    val narrative: String                          // 위에 안 담기는 나머지의 자유 요약
) {
    init {
        // 압축이 상태를 망가뜨리는 것을 조립 시점에 잡는다.
        require(goal.isNotBlank()) { "압축이 원래 목표를 소실시켰다" }
        require(narrative.length <= 4000) { "narrative가 예산을 초과했다" }
    }
}

data class Decision(val what: String, val because: String, val atTurn: Int)
data class RuledOut(val hypothesis: String, val evidence: String)
data class EntityRef(val kind: String, val id: String, val note: String)   // id는 원문 그대로
```

이렇게 하면 따라오는 이득도 크다. **압축 결과를 테스트할 수 있게 된다.** "20턴짜리 트레이스를 압축했을 때 `entities`의 모든 식별자가 보존되는가"는 자동으로 검사할 수 있는 명제다. 자유 텍스트 요약으로는 이런 검사를 할 수 없다.

```python
# 압축 함수. 핵심은 '이전 상태 + 최근 원문' → '새 상태'라는 누적 형태.
# 매번 전체 이력을 다시 요약하면 (a) 비용이 이차로 늘고 (b) 손실이 복리로 쌓인다.
def compact(prev: SessionState | None, recent: list[Message], llm) -> SessionState:
    payload = {"previous_state": prev and prev.to_dict(), "new_messages": [m.to_dict() for m in recent]}
    # 구조화 출력으로 강제한다. 자유 텍스트를 파싱하는 순간 필드 유실이 조용해진다.
    state = llm.complete_structured(system=COMPACTION_PROMPT, input=stable(payload), schema=SessionState)

    if prev:
        # 이전 상태의 식별자는 하나도 사라지면 안 된다(단조성).
        # 실패시키지 않고 되살린다 — 압축은 정보를 추가만 하고 삭제는 명시적으로만.
        lost = set(prev.entities) - set(state.entities)
        state.entities.update({k: prev.entities[k] for k in lost})
        metrics.incr("compaction.entity_recovered", len(lost))
        # 미해결 항목이 통째로 비면 의심한다(해결 근거가 decisions에 있어야 한다).
        if prev.open_items and not state.open_items and not _resolved_in(state, prev.open_items):
            metrics.incr("compaction.open_items_vanished")
    return state
```

### 6.3 압축 시점: 비율이 아니라 경계로 정한다

`working_limit`의 75%에 도달하면 압축한다는 규칙(2.2절)은 출발점으로는 괜찮지만 충분하지 않다. **압축이 아무 지점에서나 일어난다**는 것이 문제다. 도구 호출과 그 결과 사이에 압축이 끼어들면, 모델은 자기가 방금 무엇을 요청했는지 모르는 상태로 결과를 받는다. 더 나은 트리거는 **의미적 경계**다.

```
좋은 압축 지점                        나쁜 압축 지점
 · 하위 과업 완료 직후                  · tool_use 와 tool_result 사이
   (세부는 결론만 남기면 된다)            (대응이 깨진다. 일부 API는 아예 거부)
 · 도구 호출-결과 쌍이 닫힌 직후        · 다단계 추론 중간
   (열린 요청이 없다)                     (논증의 앞부분만 사라진다)
 · 사용자가 새 주제를 꺼낸 직후         · 사용자 응답 대기 중
 · 계획이 끝나고 실행에 진입할 때         (사용자가 참조한 것이 없어진다)
```

실제 구현에서는 두 조건을 AND로 묶는다. "예산의 X%를 넘었고, **그리고** 안전한 경계에 도달했을 때" 압축한다. 하드 리밋에 닿았는데도 경계가 오지 않으면 강제로 압축하되 알람을 남긴다. 이런 상황이 잦다면 과업 하나가 너무 큰 것이므로, 압축이 아니라 분해가 필요하다([[09 - 오케스트레이터-워커 — 동적 분해와 종합]]).

### 6.4 압축의 대가가 돌아오는 방식: 압축이 통하지 않는 경우

압축으로 생긴 손실은 바로 드러나지 않는다. 압축 직후에는 멀쩡해 보이고, 손실은 **나중에 다른 형태로** 나타난다. 압축과 관련된 버그를 디버깅하기 어려운 것도 이 때문이다. 관찰되는 형태는 다음과 같다.

**(1) 이미 배제한 가설로 되돌아간다.** `ruledOut`을 보존하지 않으면 에이전트는 15턴 전에 확인한 경로를 다시 탐색한다. 증상은 "루프가 끝나지 않는다"이고, 원인은 압축이다.

**(2) 제약을 위반한다.** 3턴에서 "테스트 환경은 건드리지 마세요"라고 했는데 25턴에서 건드린다. `constraints`가 누락된 경우다.

**(3) 식별자를 지어낸다.** 가장 위험한 형태다. 원문 식별자가 사라진 자리를 모델이 **형태만 그럴듯한 가짜**로 채운다. `pay_01HQ8ZK3M9X2`가 요약 과정에서 "해당 결제 건"이 되었다가, 다시 필요해졌을 때 `pay_01HQ8ZK3M9X3` 같은 값으로 나온다. 형식이 맞으니 검증도 통과한다. 결제 도메인에서 이것은 사고이며, 6.2절의 `entities` 테이블과 단조성 검증이 이 문제에 대응한다.

**(4) 요약을 거듭 요약하면서 원본에서 멀어진다.** 이전 요약 위에 압축을 반복하면 세대마다 정보가 빠지고, 요약 특유의 **일반화**가 쌓인다. "KCP 채널의 8104 오류"가 "PG 오류"가 되고, 다시 "결제 실패"가 된다. 대응 방법은 원본 이력을 외부에 저장해 다시 압축할 수 있게 해 두거나, 압축 세대 수에 상한을 두고 이를 넘으면 사람에게 넘기는 것이다.

> [!warning] 흔한 오해
> "요약은 공짜다"라는 생각은 틀렸다. 요약에는 세 가지 비용이 든다.
>
> - **토큰 비용**: 요약하려면 대상을 모델에 넣어야 하므로, 아끼려던 내용을 한 번 더 읽게 된다.
> - **캐시 비용**: 5.3절에서 보았듯이 압축하면 접두사가 무효가 된다.
> - **정보 비용**: 손실은 되돌릴 수 없고, 무엇을 잃었는지조차 알 수 없다.
>
> 정보이론의 용어로 말하면 이 압축은 무손실 압축이 아니라 손실 압축이며, 무엇을 버릴지 정하는 일이 곧 설계다([[39 - 정보이론]]).

**압축 자체를 하지 말아야 하는 경우.** 세션이 감사 대상일 때다. 규제 산업의 상담 기록이나 금융 거래 승인 이력처럼 "무엇을 근거로 그렇게 판단했는가"를 나중에 재구성해야 한다면, 압축된 컨텍스트는 증거가 되지 못한다. 이때 필요한 것은 **압축과 기록의 분리**다. 모델에게 주는 컨텍스트는 압축하되, 원본 트레이스는 모두 별도로 영속화한다(39장 관측성).

## 7. 사전 적재에서 적시 검색으로: 컨텍스트에 포인터 넣기

압축이 "이미 들어온 것을 줄이는" 전략이라면, 이 절에서 다룰 것은 "애초에 넣지 않는" 전략이다. 두 전략은 서로 경쟁하지 않고 보완하며, 잘 설계된 시스템은 둘 다 쓴다.

### 7.1 두 극단과 그 사이

| | 사전 적재(pre-loading) | 적시 검색(just-in-time) |
|---|---|---|
| 방식 | 필요할 것 같은 정보를 미리 컨텍스트에 넣음 | 식별자·목록만 넣고 필요할 때 도구로 읽음 |
| 지연 | 첫 턴이 무겁고 이후 빠름 | 턴마다 도구 왕복이 추가됨 |
| 토큰 | 안 쓸 정보에도 비용 지불 | 쓴 것에만 지불 |
| 캐시 | 접두사에 넣으면 잘 캐시됨 | 매 턴 다른 내용 → 캐시 어려움 |
| 정확도 | 방해자 유입 위험 | 잘못 검색하면 정보 자체가 없음 |
| 신선도 | 적재 시점에 고정 | 항상 최신 |
| 적합 | 소량·고빈도·안정적 지식 | 대량·저빈도·변동 지식 |

적시 검색의 핵심 발상은 **컨텍스트에 데이터 대신 포인터를 둔다**는 것이다. 이 패턴의 원형은 파일 시스템이다. 코딩 에이전트는 저장소의 모든 파일을 컨텍스트에 넣지 않고, 디렉터리 목록과 경로만 본 뒤 필요한 파일을 그때 읽는다. 사람 엔지니어가 일하는 방식과 똑같다. 이 방식을 결제 도메인에 적용하면 다음과 같다.

```typescript
// 나쁨: 조회 결과 전체를 컨텍스트에 밀어 넣는다.
// 결제 1건에 이벤트 200개, 각 이벤트가 PG 원본 응답을 통째로 담으면 40K 토큰이 넘는다.
const bad = () => db.query("SELECT * FROM payment_events WHERE payment_id = $1", [id]);

// 좋음: 요약 + 핸들. 모델이 필요하다고 판단할 때만 상세를 읽게 한다.
type EventDigest = {
  seq: number;
  type: string;          // "Prepared" | "Approved" | "ApproveFailed" | ...
  at: string;
  summary: string;       // 120자 상한. 정보 밀도 높은 한 줄
  hasDetail: boolean;    // 상세 조회가 의미 있는가
};

async function getPayment(id: string): Promise<{
  header: PaymentHeader;         // 상태·금액·채널 — 거의 항상 필요
  events: EventDigest[];         // 200건이어도 ~3K 토큰
  detailHandle: string;          // "payment_events:pay_01HQ8ZK3M9X2"
}> { /* ... */ }

// 상세는 별도 도구로. 범위를 강제해 한 번에 창을 폭파하지 못하게 한다.
async function readEventDetail(handle: string, seq: number[]) {
  // 오류 메시지가 곧 모델에게 주는 지시다 — 8.2절 참조
  if (seq.length > 5) throw new Error("한 번에 최대 5건. 범위를 좁혀 다시 요청하라.");
  return renderEvents(await loadEvents(handle, seq), { maxTokensPerEvent: 800 });
}
```

이 설계로 얻는 것은 토큰 절약만이 아니다. **모델의 탐색 경로를 관측할 수 있게 된다.** 어떤 이벤트의 상세를 읽었는지가 도구 호출 로그로 남으므로, 오답이 나왔을 때 "무엇을 보지 않고 판단했는지"를 알 수 있다. 전부 밀어 넣는 설계에서는 이것을 알 수 없다.

### 7.2 점진적 공개(progressive disclosure)

적시 검색을 일반화하면 **점진적 공개**가 된다. 정보를 계층으로 구성하고, 각 계층에 다음 계층으로 가는 포인터를 넣어 두는 방식이다.

```
계층 0 (항상 컨텍스트에)    : 시스템 프롬프트, 도구 목록, 세션 상태 요약
계층 1 (첫 조회로 들어옴)   : 헤더·목록·요약 — "무엇이 있는가"
계층 2 (모델이 선택해 읽음) : 개별 항목의 본문
계층 3 (드물게, 명시적으로) : 원본 페이로드, 전체 로그, 첨부 파일

각 계층은 다음 계층으로 가는 '주소'를 포함한다. 모델이 계층을 내려가는 것 자체가 추론 흔적이다.
  헤더 → 이벤트 목록(seq) → 이벤트 상세(seq 지정) → PG 원본 응답(raw handle)
```

이 구조가 사람이 조사하는 방식과 닮은 것은 우연이 아니다. 작업 기억이 유한한 행위자가 큰 정보 공간을 다룰 때 쓰는 일반적인 해법이기 때문이다. 24장(RAG와 에이전틱 검색)에서 "검색을 전처리가 아니라 행동으로 본다"고 할 때 말하는 구조도 이것이다.

> [!note] 실무 규칙
> 반환값의 크기는 **모델이 아니라 도구가** 통제해야 한다. "필요하면 알아서 적게 요청하겠지"라는 기대는 맞지 않는다. 모델은 기본적으로 전부 달라고 한다. 따라서 `limit` 기본값은 작게 두고, 상한은 하드 리밋으로 강제하며, 상한을 넘으면 "범위를 좁혀 다시 요청하라"는 내용을 오류 메시지에 담는다.

### 7.3 적시 검색이 통하지 않는 경우

**탐색 자체가 실패할 때.** 포인터만 준다는 것은 모델이 올바른 포인터를 고를 수 있다고 가정하는 것이다. 이벤트 200건의 한 줄 요약만 보고 "3번, 47번, 198번을 읽어야 한다"고 맞히기는 쉽지 않다. 요약이 나쁘면 모델은 엉뚱한 것을 읽고, 필요한 것을 찾지 못했다는 사실도 모른 채 결론을 낸다. 즉 **한 줄 요약의 품질이 설계 전체의 병목**이다. 이 요약은 사람이 설계해야 한다. 모델에게 생성하게 하면 다시 압축 손실 문제로 돌아간다.

**지연이 쌓일 때.** 계층을 하나 내려갈 때마다 모델 턴이 하나씩 필요하고, 턴마다 prefill과 decode가 들어간다. 대응 방법은 **예측 적재**다. 헤더를 반환할 때 "거의 항상 다음에 읽히는 것"을 함께 붙여 준다. 캐시 프리페치와 같은 발상이며([[28 - 캐싱 (Caching) - 전략·무효화·축출·장애 패턴]]), 쓰이지 않으면 낭비라는 위험도 똑같이 안고 있다.

**정보가 한꺼번에 필요할 때.** "이 100건의 정산 내역 중 합계가 맞지 않는 건을 찾아라"는 전체를 봐야 풀 수 있다. 이것을 점진적 공개로 나누면 모델이 100번 왕복하며 부분 합계를 누적해야 하는데, 이는 모델이 할 일이 아니다. 답은 컨텍스트 전략이 아니라 **계산을 코드로 옮기는 것**이다(26장 환경과 행동 공간). "모델에게 데이터를 주는 대신, 데이터에 대한 질문을 실행할 능력을 준다"고 보는 편이 더 정확하다.

**신선도가 오히려 문제가 될 때.** 적시 검색은 늘 최신 값을 읽기 때문에, 한 세션 안에서 같은 것을 두 번 읽으면 값이 달라질 수 있다. 조사하는 도중에 결제 상태가 바뀌면 모델은 모순된 두 사실을 보게 되고, 대개 이를 명시적으로 처리하지 못한다. 대응 방법은 **세션 스냅샷**이다. 첫 조회 시점의 값을 고정해 두고, 다시 조회했을 때 달라진 점을 명시적으로 알린다. 분산 시스템의 읽기 일관성 문제가 그대로 나타나는 셈이다([[18 - 일관성 모델 (Consistency Models) - 선형화·인과·최종·세션 보장]]).

## 8. 도구 출력이 컨텍스트를 망가뜨린다: 반환값 설계는 컨텍스트 설계다

2.1절의 표에서 점유 범위가 가장 넓었던 항목은 도구 출력이다. 도구 출력은 **우리가 완전히 통제할 수 있는데도 대부분의 팀이 통제하지 않는** 항목이다. 도구의 입력 스키마는 공들여 설계하면서([[12 - 도구 사용 I — 함수 호출의 메커니즘과 계약]]) 반환값은 `JSON.stringify(row)`로 끝내 버리는 코드를 자주 볼 수 있다.

### 8.1 반환값의 세 가지 상한

반환값에는 다음 세 가지 상한을 둔다.

- **항목 수 상한.** `limit` 기본값을 작게(10~20) 두고 하드 상한(100)을 강제한다. 상한을 넘는 요청은 잘라서 주지 말고, **거부하면서 범위를 좁히라고 지시**한다. 조용히 잘라서 주면 모델은 그것이 전부라고 여긴다.
- **항목당 크기 상한.** 로그 라인, PG 원본 응답, 예외 스택처럼 항목 하나가 클 수 있다. 항목마다 상한을 걸고, 잘렸다는 사실을 `...[2,140자 생략, 상세는 read_detail(seq=47)]`처럼 명시한다.
- **전체 토큰 상한.** 앞의 두 상한을 통과해도 합계가 클 수 있다. 그래서 조립기 단계에서 도구 출력 블록 전체에 예산을 걸고(2.2절 YAML의 `tool_output.max`), 예산을 넘으면 오래된 것부터 요약본으로 교체한다.

```python
# 도구 출력 후처리: 도구 구현마다 흩어지지 않게 한 곳에서 강제한다.
# '무엇을 잘랐는지'를 모델이 읽을 수 있게 남기는 것이 핵심 —
# 조용한 절단은 모델에게 '이게 전부'라는 잘못된 신호를 준다.
def shape(name: str, raw, budget: int) -> str:
    body = renderers[name](raw)                  # 도구별로 사람이 설계한 렌더러
    n = count_tokens(body)
    if n <= budget:
        return body
    return (f"{truncate_to(body, budget - 120)}\n\n"
            f"[출력이 {n}토큰이라 {budget}토큰으로 잘렸다. 전체가 필요하면 필터를 좁혀 "
            f"다시 호출하라. 사용 가능한 필터: {', '.join(filters_of(name))}]")
```

### 8.2 오류 메시지는 모델에게 주는 지시다

도구가 실패했을 때 컨텍스트에 무엇이 들어가느냐가 재시도 성공률을 크게 좌우한다. 04장(에이전트 루프)에서 "재시도 피드백이 컨텍스트에 들어가지 않는 것이 가장 흔한 버그"라고 했는데, 그다음으로 흔한 버그는 피드백이 **쓸모없는 형태로 들어가는 것**이다.

| 반환된 오류 | 모델이 할 수 있는 일 | 평가 |
|---|---|---|
| `Internal Server Error` | 없음. 같은 호출을 반복한다 | 최악 |
| 500줄 스택 트레이스 | 원인 추정은 되지만 토큰 500~2,000 소모 | 비쌈 |
| `INVALID_ARGUMENT: from_date must be <= to_date` | 인자를 고쳐 재시도 | 좋음 |
| `NOT_FOUND: payment_id 'pay_X' 없음. 최근 30일 밖이면 archive_search를 쓰라` | 다른 도구로 전환 | 최선 |

원칙은 하나다. **오류 메시지에 다음 행동을 담는다.** 무엇이 잘못됐는지(진단)와 무엇을 하면 되는지(처방)를 함께 담아야 한다. 스택 트레이스는 사람이 보는 로그로 보내고, 모델에게는 구조화된 오류를 준다([[09 - 에러 모델 - 상태 코드와 Rich Error]]). gRPC rich error를 설계할 때 하던 고민과 같은 종류이며, 다른 점은 소비자가 코드가 아니라 확률적 생성기라는 것뿐이다.

**이 접근이 통하지 않는 경우.** 오류가 **재시도로 해결할 수 없는 종류**라면 친절한 오류 메시지가 오히려 모델을 무한 루프로 몰아넣는다. "권한이 없다"는 오류에 "확인하고 다시 시도하라"를 붙이면 모델은 계속 시도한다. 되돌릴 수 없거나 복구할 수 없는 오류에는 처방 대신 **종료 신호**를 담아야 한다. 오류를 재시도할 수 있는 것과 없는 것으로 분류하는 일도 도구 설계의 일부다.

## 9. few-shot 예시: 잘 고른 예시가 개수보다 중요하다

### 9.1 예시가 실제로 하는 일

예시는 서로 다른 두 가지 일을 한다.

- **형식 앵커**: 출력의 모양을 보여 준다. 이 용도는 구조화된 출력과 제약 디코딩이 상당 부분 대신하게 되었다(11장 구조화된 출력). 스키마로 강제할 수 있는 것을 예시로 가르치는 것은 토큰 낭비다.
- **판단 기준 전달**: 규칙으로 쓰기 어려운 경계를 사례로 보여 준다. 이것은 스키마로 할 수 없는 일이며, **예시의 진짜 가치는 여기에 있다.**

이 구분에서 예시를 고르는 기준이 나온다. 좋은 예시는 전형적인 사례가 아니라 **경계에 있는 사례**다. 명백한 환불 요청 5개보다, 환불처럼 보이지만 환불이 아닌 사례 1개와 애매하지만 환불인 사례 1개가 낫다. 각 예시에 **왜 그렇게 판단했는지 한 줄**을 붙이면 일반화가 크게 좋아진다.

```typescript
// 예시는 문자열 더미가 아니라 구조를 갖는다.
// rationale 이 있으면 모델이 표면 패턴이 아니라 판단 근거를 모방한다.
type Shot = {
  input: string; output: string;
  rationale: string;      // 왜 이 출력인가 — 한 줄
  covers: string;         // 이 예시가 담당하는 경계. 중복 예시를 걸러내는 데 쓴다
};

const SHOTS: Shot[] = [
  { input: "배송이 3주째 안 와요. 진짜 짜증나네요",
    output: '{"intent":"shipping_delay","refund_requested":false}',
    rationale: "불만 표현이지만 환불을 요구하지 않았다. 감정 강도는 의도가 아니다.",
    covers: "불만 ≠ 환불요청" },
  { input: "이거 그냥 취소해주세요. 돈 다시 넣어주시고요",
    output: '{"intent":"refund_request","refund_requested":true}',
    rationale: "'취소'와 '환불'을 다른 말로 표현했다. 표현이 아니라 요구를 본다.",
    covers: "동의어 표현" },
];
```

### 9.2 개수의 한계효용과 캐시 충돌

형식 앵커가 목적이라면 예시는 2~3개면 충분하다. 형식은 한 번 보면 알 수 있기 때문이다. 판단 기준을 전달하는 것이 목적이라면 예시가 많을수록 도움이 될 수 있다.

긴 컨텍스트에 예시를 수백~수천 개 넣는 many-shot 접근이 여러 생성·판별 과업에서 few-shot보다 나은 결과를 보였다는 보고도 있다(Agarwal 등, "Many-Shot In-Context Learning", NeurIPS 2024). 다만 그 이득은 과업에 따라 다르고(같은 논문도 과업마다 포화 지점과 역전 지점이 다르다고 보고한다), 늘어난 만큼 3절에서 본 열화와 비용을 치른다.

실무에서 훨씬 자주 문제가 되는 것은 개수가 아니라 **분포 불일치**다. 예시가 실제 입력 분포와 어긋나면 예시는 도움이 아니라 방해자가 된다(3.2절). 6개월 전 트래픽에서 뽑은 예시가 지금 들어오는 문의와 형태가 다르면, 모델은 지금 입력을 예시 쪽으로 억지로 끌어당겨 해석한다. 라우터 드리프트([[07 - 라우팅 — 분류와 전문화된 경로]])와 같은 문제다.

게다가 **예시를 동적으로 고르면 캐시가 깨진다**(5.2절). 절충안은 계층을 나누는 것이다. 고정된 표준 예시 3~5개는 캐시 경계 앞에 두고, 검색으로 고른 예시 1~2개는 경계 뒤에 둔다.

> [!warning] 흔한 오해
> "few-shot 예시는 많을수록 좋다"는 생각은 두 가지 면에서 틀렸다. 첫째, 예시가 늘면 컨텍스트가 길어지고 3절에서 본 열화가 시작된다. 둘째, 예시는 **암묵적인 제약**도 함께 가르친다. 예시 10개가 모두 짧은 답변이면 모델은 "짧게 답해야 한다"고 배우고, 예시가 모두 특정 형식의 ID를 쓰면 그 형식을 일반 규칙으로 받아들인다. 그래서 예시를 추가할 때는 "이 예시가 의도치 않게 무엇을 함께 가르치는가?"를 물어야 한다.

**few-shot을 아예 빼야 하는 경우.** 추론 모델을 쓸 때다. 사고 토큰을 쓰는 모델에서는 few-shot 예시가 오히려 성능을 떨어뜨린 사례가 보고되어 왔다. 모델이 스스로 전개하려던 추론 경로를 예시의 패턴이 좁히기 때문이라는 설명이 나와 있다. 이런 변화는 [[20 - 추론 모델의 시대 — test-time compute가 바꾼 패턴 지형]]에서 다룬다. 지금은 **모델을 바꾸면 예시의 효과를 다시 재야 한다**는 점 하나만 기억하자.

## 10. 서브에이전트는 컨텍스트를 나누는 장치다

### 10.1 진짜 목적은 창을 나누는 것이다

멀티에이전트를 "여러 전문가의 협업"으로 설명하는 글이 많지만, 컨텍스트 관점에서는 훨씬 단순하고 솔직하게 설명할 수 있다. **서브에이전트는 탐색에 쓰인 원문을 부모 컨텍스트 밖에서 소비하고 버리기 위한 장치다.**

```
격리 없음 — 부모 창에 전부 쌓인다
│ 시스템 │ 도구 │ 검색40K │ 로그28K │ 코드15K │ ...본 과업 │ → 열화·비용·절단

격리 있음 — 원문은 자식 창에서 소각, 결론만 올라온다
│ 부모: 시스템 │ 도구 │ 결론A 800 │ 결론B 600 │ 본 과업 │
           │        └────────────┐
   ┌───────▼────────┐    ┌───────▼────────┐
   │ 자식A: 검색 40K │    │ 자식B: 로그 28K │   ← 이 창은 반환 후 버려진다
   │  → 결론 800     │    │  → 결론 600     │
   └────────────────┘    └────────────────┘
```

무엇을 얻고 무엇을 내주는지는 분명하다. **총 토큰은 늘고, 부모 컨텍스트는 줄며, 늘어난 지연은 병렬화로 가린다.** 이 교환이 정당하려면 세 가지 조건을 만족해야 한다.

- 탐색 원문이 결론보다 훨씬 크다(압축비 10:1 이상).
- 부모의 전체 맥락 없이도 자식 과업을 명세할 수 있다.
- 결론 형식이 정해져 있어서, 부모가 결론만 보고 판단할 수 있다.

하나라도 어긋나면 서브에이전트는 비용만 늘린다.

### 10.2 반환 계약

자식이 무엇을 돌려줄지를 자연어로 정해 두면 종합 단계가 무너진다. 반환 형식은 타입으로 고정해야 한다.

```typescript
// 서브에이전트 반환 계약. 자연어 보고서가 아니라 구조화된 결과.
type SubagentResult = {
  status: "complete" | "partial" | "failed";
  findings: { claim: string; evidence: string; sourceId: string }[];  // 근거 없는 주장 금지
  identifiers: Record<string, string>;   // 부모의 후속 조회를 위해 원문 보존(6.2절)
  notExplored: string[];                 // 안 본 것을 명시 — 부모가 모르면 과신한다
};
```

이 가운데 `notExplored`가 특히 중요하다. "찾지 못했다"와 "찾아보지 않았다"를 구분해 주지 않으면, 부모는 이를 "찾지 못했다"로 읽고 실제로 존재하는 사실을 없는 것으로 확정한다. 이 실패는 종합 단계에서 드러나지 않고 최종 답변에서야 드러난다.

**서브에이전트가 통하지 않는 경우.**

- **자식들이 서로의 결정을 알아야 할 때.** 격리한다는 것은 곧 자식끼리 서로를 볼 수 없다는 뜻이다. 두 자식이 서로 모순된 전제로 진행하면, 부모는 종합할 수 없는 결과 두 개를 받는다([[32 - 멀티에이전트 실패 모드 — 조율 실패의 분류학]]).
- **원문 없이는 결론을 검증할 수 없을 때.** 부모가 결론을 그대로 믿을 수밖에 없는 구조에서는 자식의 오류가 커진다. `evidence`와 `sourceId`를 강제하는 이유가 여기에 있다.
- **부모의 맥락이 자식 과업에 결정적일 때.** 명세를 제대로 쓰려다가 부모 컨텍스트를 거의 다 복사하게 된다면, 격리의 이득은 사라지고 비용만 남는다.

자세한 판단 기준은 [[27 - 멀티에이전트는 언제 필요한가 — 분업의 이득과 비용]]과 09장(오케스트레이터-워커)에서 다룬다.

## 11. 컨텍스트를 관측할 수 있게 만들기

컨텍스트는 눈에 보이지 않는 자원이다. 그래서 관측하지 않으면 잘못된 배분이 몇 달 동안 아무도 모르게 이어진다.

### 11.1 무엇을 남길까

```sql
-- 턴마다 한 행. 컨텍스트 조립의 결과를 그대로 기록한다.
CREATE TABLE agent_turn_context (
  trace_id TEXT, session_id TEXT, turn_no INT,
  model       TEXT,   -- 버전까지. 모델 교체가 회귀 원인일 때 필요
  prompt_hash TEXT,   -- 시스템+도구 정의의 해시. 프롬프트 버전 추적
  tokens      JSONB,  -- {"system":2400,"tools":5800,"history":18000,...}
  total_input INT, cache_read INT, cache_write INT,   -- 응답 메타데이터에서
  dropped     JSONB,  -- 예산 때문에 버린 블록의 kind와 토큰
  compact_gen INT,    -- 압축 세대 수 (6.4절의 '요약의 요약' 감지)
  outcome     TEXT    -- ok | schema_fail | tool_error | escalated | ...
);
```

이 기록에서 나오는 네 가지 지표로 대시보드를 구성한다.

| 지표 | 정의 | 이상 신호 | 해석 |
|---|---|---|---|
| 절단율 | `dropped ≠ {}` 인 턴 비율 | 2% 초과 | 예산 배분이 실제 수요와 어긋남 |
| 캐시 적중률 | `cache_read / total_input` | 60% 미만 | 접두사에 변동 요소 혼입 또는 압축 과다 |
| 점유 분포 | `tokens` 항목별 백분위 | 한 항목이 p95에서 50% 초과 | 그 항목에 상한이 없음 |
| 압축 세대 | `compact_gen` 분포 | 3 이상 꼬리가 두꺼움 | 과업이 너무 큼 → 분해 필요 |

### 11.2 회귀를 잡는 방법

컨텍스트 회귀는 배포 시점이 아니라 **입력 분포가 바뀔 때** 드러난다. 그래서 배포 게이트에 넣어야 할 것은 정확도만이 아니다.

```bash
# 배포 전 컨텍스트 회귀 검사. 골든 트레이스로 조립기만 돌린다(모델 호출 없이).
# 조립기가 순수 함수이기 때문에 가능한 검사다(1.1절).
$ agentctl context-diff --baseline v1.42 --candidate HEAD --traces golden/*.jsonl

  system        2,400 → 3,180  (+780)   ⚠ 접두사 증가: 캐시 쓰기 비용 상승
  prefix_hash   a3f1... → 9c04...       ⚠ 접두사 변경: 전체 캐시 무효화 1회 발생
  truncation      0.4% → 3.1%           ✗ 절단율 임계 초과 (2.0%)
  identifiers   보존율 100% → 97.2%      ✗ 압축이 식별자를 잃고 있다
```

`identifiers 보존율`을 조립기 수준에서 검사할 수 있는 것은 6.2절에서 상태를 구조화해 둔 덕분이다. 자유 텍스트 요약이었다면 이런 검사 자체를 만들 수 없다.

**계측이 잘못된 결론으로 이끄는 경우.** 30K 토큰이 한 편의 균질한 문서인 세션과, 30K 토큰이 서로 모순되는 도구 출력 40개로 이루어진 세션은 숫자는 같아도 난이도가 전혀 다르다. 토큰 수는 **품질을 대신 보여 주는 지표일 뿐**이다. 그래서 트레이스를 사람이 직접 읽는 습관이 필요하다. 이 습관 없이 대시보드만 보는 팀은 결국 "지표는 전부 초록색인데 답이 이상하다"는 상황을 맞는다([[38 - 평가 — 에이전트를 측정하는 법]]).
