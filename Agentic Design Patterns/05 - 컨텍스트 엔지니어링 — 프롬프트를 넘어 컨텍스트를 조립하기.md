**이 장이 답하는 질문:**

- 왜 "좋은 프롬프트를 쓰는 일"이 아니라 "매 턴 컨텍스트를 조립하는 일"이 문제가 되었는가?
- 컨텍스트 창이 100만 토큰으로 커졌는데도 왜 "다 넣으면 된다"가 여전히 틀린가? 무엇이 정확히 열화하는가?
- 시스템 프롬프트의 "적정 고도"는 무엇으로 판별하는가? 너무 구체적인 것과 너무 추상적인 것 중 어느 쪽이 더 위험한가?
- 이력 압축(compaction)에서 무엇을 보존하고 무엇을 버려야 하며, 그 손실은 언제 청구서로 돌아오는가?
- 프롬프트 캐싱이 컨텍스트 배치 순서를 어떻게 강제하는가? 캐시 친화성과 정보 신선도는 어디서 충돌하는가?
- 도구 출력과 검색 결과는 왜 컨텍스트를 가장 빨리 죽이는가? 반환값 설계는 왜 컨텍스트 설계와 같은 문제인가?
- few-shot 예시를 늘리면 왜 어느 지점부터 성능이 떨어지는가?

---

앞의 네 장에서 재료와 골격을 세웠다. [[02 - LLM이라는 재료 — 확률적 생성기 위에 시스템을 짓는다는 것]]에서 모델 API가 **무상태(stateless)** 라는 사실을 확인했다. 서버는 대화를 기억하지 않는다. 매 요청마다 우리가 전체 이력을 다시 만들어 보낸다. [[04 - 에이전트 루프의 해부 — 관찰·결정·행동·정지]]에서는 루프 한 바퀴가 네 지점으로 나뉜다고 했다 — 컨텍스트 조립, 모델 결정, 행동 실행, 결과 통합. 그중 첫 번째 지점만 따로 떼어내 끝까지 파는 것이 이 장이다.

이 분리가 인위적이지 않다는 점을 먼저 말해 두는 편이 좋겠다. 에이전트 시스템에서 우리가 실제로 코드로 통제하는 것은 많지 않다. 모델의 가중치는 고정돼 있고, 샘플링은 확률적이며, 도구 실행 결과는 외부 세계가 정한다. 남는 것은 하나다 — **모델이 다음 토큰을 예측할 때 무엇을 보고 있게 할 것인가.** 이것이 유일하게 완전히 우리 것인 레버다. [[43 - 에이전트와 소프트웨어 아키텍처 — 결정론 경계와 기존 패턴의 재해석]]이 말한 "결정론 경계"의 안쪽에서 벌어지는 일 중 가장 많은 설계 판단이 여기 몰려 있는 이유다.

그런데 이 레버는 유한하다. 컨텍스트 창은 크지만 무한하지 않고, 크더라도 균질하지 않으며, 채우는 만큼 돈과 시간을 낸다. 그래서 문제의 형태가 "문장을 잘 쓰기"에서 **"제한된 예산을 항목별로 배분하기"** 로 바뀐다. 무엇을 넣을지, 얼마나 넣을지, 어떤 순서로 놓을지, 넘칠 때 무엇을 버릴지, 그리고 버린 것이 나중에 어떻게 되돌아오는지 — 이 장은 그 배분 문제를 다룬다.

경계를 미리 그어 둔다. 메모리의 이론적 문제는 [[21 - 메모리의 문제 — 컨텍스트 윈도·상태·망각]]부터의 몫이고, 검색 자체의 기법(청킹·임베딩·재랭킹)은 [[24 - RAG와 에이전틱 검색 — 검색을 행동으로]]가, 캐싱 비용의 계산은 [[40 - 비용과 지연 — 캐싱·모델 라우팅·예산 관리]]가 담당한다. 이 장은 그것들의 **상류** — 어떤 정보를, 어떤 형태로, 창의 어느 위치에 놓을 것인가를 정하는 층이다.

## 1. 프롬프트 엔지니어링은 사라지지 않았다, 부분집합이 되었다

### 1.1 무상태 API가 강제하는 재조립

먼저 아주 구체적인 사실에서 출발하자. 다음 두 코드는 겉보기에 "대화를 이어 간다"는 같은 일을 하지만, 두 번째만이 실제로 일어나는 일이다.

```python
# 착시: 세션 객체가 대화를 '기억한다'고 느끼게 만드는 API 표면.
session.send("이 결제가 왜 실패했지?")
session.send("그럼 재시도하면 성공할까?")   # 서버가 앞 문맥을 갖고 있는 것처럼 보인다

# 실제: 두 번째 호출에서 클라이언트가 보내는 것.
# 서버에 남은 상태는 없다. 우리가 매번 전부 다시 만들어 보낸다.
messages = [
    {"role": "user", "content": "이 결제가 왜 실패했지?"},
    {"role": "assistant", "content": [{"type": "tool_use", "name": "get_payment", ...}]},
    {"role": "user", "content": [{"type": "tool_result", "content": "...(3,200 토큰)..."}]},
    {"role": "assistant", "content": "PG 응답 코드 8104는 ..."},
    {"role": "user", "content": "그럼 재시도하면 성공할까?"},
]
resp = llm.complete(system=SYSTEM, tools=TOOLS, messages=messages)
```

편의 래퍼가 있더라도 아래에서는 두 번째 형태로 변환된다. 여기서 따라 나오는 결론이 이 장 전체의 전제다.

**첫째, 컨텍스트는 한 번 쓰는 문서가 아니라 매 턴 새로 조립되는 자료구조다.** 우리가 설계하는 것은 문자열이 아니라 그 문자열을 만들어 내는 함수 — 조립기(assembler)다. 조립기의 입력은 (대화 이력, 현재 상태, 검색 가능한 지식, 예산)이고 출력은 (system, tools, messages) 튜플이다. 이 함수는 순수 함수로 만들 수 있고, 그래야 테스트할 수 있다. [[30 - 함수형 아키텍처 — 순수 코어와 명령 껍질]]의 구도가 그대로 적용된다 — 조립은 순수 코어, 모델 호출과 도구 실행은 껍질.

**둘째, 비용이 대화 길이에 대해 선형이 아니다.** $t$번째 턴에서 보내는 입력 토큰 수가 대략 $c + \sum_{i<t} l_i$ 라면($c$는 시스템·도구 정의 등 고정분, $l_i$는 $i$턴이 추가한 길이), 대화 전체의 누적 입력 토큰은

$$\sum_{t=1}^{T}\Big(c + \sum_{i<t} l_i\Big) \;=\; cT + \sum_{t=1}^{T}\sum_{i<t} l_i$$

가 되어 턴 수에 대해 이차적으로 자란다. 과금은 대개 토큰 수에 선형이므로 이 이차성은 **누적 토큰 수**에서 나오는 것이고, 여기에 서버 측 연산의 성질이 하나 더 겹친다 — 어텐션 항의 계산량은 시퀀스 길이에 대해 이차이므로 긴 프롬프트는 토큰당 비용이 아니라 **지연**에서 추가로 불리하다. 20턴짜리 에이전트 세션에서 "마지막 턴이 비싸다"가 아니라 **"세션 전체가 마지막 턴 길이에 지배된다"** 가 맞는 서술이다. 프롬프트 캐싱이 실무에서 선택이 아니라 필수가 되는 이유가 여기 있고(5절), 압축이 비용 문제이기도 한 이유가 여기 있다(6절).

**셋째, 컨텍스트의 대부분은 사람이 쓴 문장이 아니다.** 토큰 점유를 실제로 재 보면 손으로 쓴 시스템 프롬프트는 한 자릿수 퍼센트인 경우가 흔하고, 나머지는 도구 정의·도구 출력·검색 결과·이전 턴의 자기 발화다. 프롬프트를 다듬는 데 하루를 쓰면서 3,200토큰짜리 도구 출력을 그대로 흘려보내고 있다면, 노력을 잘못된 항목에 쓰고 있는 것이다.

> **흔한 오개념.** "프롬프트만 잘 쓰면 된다." 단발 호출(요약·번역·분류)에서는 대체로 맞고 루프를 도는 에이전트에서는 대체로 틀리다. 단발 호출의 컨텍스트는 우리가 100% 저작한 것이지만, 에이전트에서는 대부분이 **런타임에 생성된 것**이다 — 도구가 뱉은 JSON, 검색기가 가져온 문서, 모델 자신이 이전 턴에 쓴 문장. 우리가 저작할 수 있는 것은 그 생성물의 **형식과 상한과 배치**뿐이다. 프롬프트 엔지니어링은 사라지지 않지만 그것만으로는 부족하다.

### 1.2 용어가 이동한 이유

"컨텍스트 엔지니어링"이라는 표현은 2025년 중반에 업계에서 빠르게 자리 잡았다. 새 기술이 발명돼서가 아니라 사람들이 하던 일의 이름이 실제와 어긋나 있었기 때문이다. 도구를 여러 개 붙이고 루프를 돌리기 시작하자 "프롬프트"는 더 이상 단일 문자열이 아니게 되었다 — 시스템 지시, 수십 개의 도구 스키마, 검색된 문서, 누적된 도구 출력, 요약된 과거를 한 창에 배치하는 일에 그 이름은 너무 작았다.

> **역사 메모**: 관점 자체는 새롭지 않다. 유한한 빠른 저장소와 무한한 느린 저장소 사이에서 무엇을 올려 둘지 정하는 문제는 가상 메모리([[18 - 가상 메모리와 페이지 폴트]])와 캐시 계층([[16 - 캐시의 해부]])이 수십 년 다뤄 온 것과 형태가 같다. 2023년의 MemGPT(Packer 등, "MemGPT: Towards LLMs as Operating Systems")는 이 유추를 명시적으로 채택해 컨텍스트 창을 "메인 컨텍스트(메인 메모리)", 외부 저장소를 "외부 컨텍스트(디스크)"로 두고 모델이 함수 호출로 스스로 페이징을 지휘하게 하는 설계를 제안했다. 유추의 힘은 워킹셋·지역성·축출 정책·스래싱 같은 실무 직관을 그대로 옮겨 준다는 데 있다. 다만 한계도 분명하다 — CPU 캐시는 미스가 나면 **느려질 뿐 틀리지 않지만**, 컨텍스트는 미스가 나면 모델이 조용히 **지어낸다.** 이 비대칭이 축출 정책을 훨씬 보수적으로 만들어야 하는 이유다.

### 1.3 조립기라는 컴포넌트

말을 실체로 만들자. 조립기를 하나의 명명된 컴포넌트로 승격시키는 것이 이 장에서 권하는 첫 번째 실무 조치다. 프롬프트 문자열이 코드 곳곳에 흩어져 f-string으로 이어 붙여지고 있다면, 컨텍스트에 대해 어떤 질문도 답할 수 없다 — 지금 무엇이 몇 토큰 들어가는지, 무엇이 잘렸는지, 캐시가 왜 깨졌는지.

```python
# 조립기: 컨텍스트를 '블록의 리스트'로 다루는 순수 함수.
# 핵심은 각 블록이 자기 메타데이터를 갖는다는 것 —
# 우선순위(버릴 때 순서), 안정성(캐시 경계 판단), 토큰 수(예산 회계).
Stability = Literal["static", "session", "turn"]   # 캐시 무효화 주기

@dataclass(frozen=True)
class Block:
    kind: str                  # "system" | "tools" | "examples" | "state" | "history" | ...
    text: str
    tokens: int                # 정확한 토크나이저 카운트. 문자수/4 같은 추정은 회계를 망친다
    stability: Stability
    priority: int              # 낮을수록 먼저 버린다
    droppable: bool = True     # False면 예산 초과 시 잘라내지 않고 실패시킨다

@dataclass(frozen=True)
class Assembled:
    blocks: Sequence[Block]; dropped: Sequence[Block]; total_tokens: int

def assemble(candidates: Sequence[Block], budget: int) -> Assembled:
    # 안정성 순 → 캐시 접두사가 최대한 길게 유지되도록 static·session을 앞에 고정한다.
    order = {"static": 0, "session": 1, "turn": 2}
    ordered = sorted(candidates, key=lambda b: (order[b.stability], b.priority))

    # 필수 블록부터 자리를 확보한다. 필수가 예산을 넘으면 설계 실패이므로 조용히 넘어가지 않는다.
    used = sum(b.tokens for b in ordered if not b.droppable)
    if used > budget:
        raise ContextBudgetError(f"필수 블록만으로 예산 초과: {used} > {budget}")

    kept, dropped = [], []
    for b in ordered:
        if not b.droppable or used + b.tokens <= budget:
            kept.append(b)
            used += b.tokens if b.droppable else 0
        else:
            dropped.append(b)   # 버린 것을 반드시 반환한다. 조용한 절단이 최악의 버그다
    return Assembled(blocks=kept, dropped=dropped, total_tokens=used)
```

중요한 것은 알고리즘이 아니라 **인터페이스**다. 컨텍스트가 블록의 리스트가 되는 순간 각 블록의 토큰 점유를 로깅할 수 있고(11절), 무엇이 버려졌는지 관측할 수 있고, 캐시 경계를 계산할 수 있다(5절). f-string 연결에서는 셋 다 불가능하다.

**언제 이 접근이 작동하지 않는가.** 블록 단위 회계는 블록 경계가 의미 있을 때만 유효하다. 하나의 논리적 단위가 여러 블록에 걸쳐 있고 일부만 버려지면 남은 조각이 오해를 유발한다 — 계약 조건 3개 중 2개만 남으면 모델은 "조건이 2개뿐"이라고 읽는다. 블록은 **자기완결적 단위**로 자르고, 부분 폐기가 위험한 것은 `droppable=False`로 묶는다. 두 번째 실패 조건은 토큰 카운트 비용이다. 블록 생성 시 한 번 세고 캐시하되 "문자수 ÷ 4" 추정은 쓰지 않는다 — 한국어·JSON·코드는 이 비율에서 크게 벗어나고, 회계가 몇 퍼센트만 틀려도 절단이 예고 없이 시작된다.

## 2. 컨텍스트는 예산이다 — 항목별 회계 없이는 아무것도 통제되지 않는다

### 2.1 구성요소 지도

컨텍스트에 들어가는 것들을 성질별로 나누면 여덟 종류쯤 된다. 이 표는 이 장 나머지의 목차 역할도 한다.

| 구성요소 | 전형적 점유 | 변동성 | 캐시 친화성 | 주된 위험 |
|---|---|---|---|---|
| 시스템 프롬프트 | 500~3,000 토큰 | 배포 단위로만 변함 | 매우 높음(접두사) | 고도(altitude) 오류 — 4절 |
| 도구 정의 | 도구당 100~400 토큰 | 배포 단위 | 매우 높음 | 도구 폭발 — [[13 - 도구 사용 II — 도구 설계의 기술과 도구 폭발 문제]] |
| few-shot 예시 | 예시당 200~1,500 토큰 | 고정 또는 동적 | 고정이면 높음 | 분포 불일치·캐시 파괴 — 9절 |
| 세션 상태 요약 | 200~2,000 토큰 | 압축 시점에만 | 중간 | 손실의 지연 청구 — 6절 |
| 대화 이력 | **무제한 증가** | 매 턴 | 접미사만 증가면 높음 | 열화·비용 — 3절 |
| 도구 출력 | 호출당 50~50,000 토큰 | 매 턴 | 낮음 | 창 폭파 — 8절 |
| 검색 결과 | 질의당 1,000~20,000 토큰 | 매 질의 | 낮음 | 방해자 유입 — 7절 |
| 현재 지시 | 20~500 토큰 | 매 턴 | 없음(꼬리) | 위치가 잘못되면 묻힘 |

표의 토큰 범위는 벤치마크가 아니라 **설계 시 자릿수를 잡기 위한 어림값**이다(저자의 실무 관측 수준의 근거이며, 도메인·언어·직렬화 방식에 따라 쉽게 두세 배 벗어난다). 그대로 믿을 값이 아니라 자기 시스템에서 재 볼 대상의 목록으로 읽는 편이 맞다 — 재는 방법은 11절에 있다. 그럼에도 가장 먼저 눈에 띄어야 할 것은 **점유 범위의 자릿수 차이**다. 시스템 프롬프트는 3,000토큰을 넘기지 않으려고 애쓰는 항목인데, `SELECT *` 하나·로그 조회 하나가 그 열 배를 아무렇지 않게 밀어 넣는다. 컨텍스트 관리의 실질적 승부처는 손으로 쓰는 항목이 아니라 **런타임 생성 항목의 상한**에 있다. 두 번째로 볼 것은 변동성 열이다. 이것이 곧 캐시 레이아웃이고(5절) 조립 순서를 강제한다 — 배포 단위로만 변하는 것을 앞에, 매 턴 변하는 것을 뒤에.

### 2.2 예산을 선언적으로 쓰기

예산은 코드에 흩어진 매직 넘버가 아니라 하나의 선언으로 있어야 한다. 그래야 리뷰할 수 있고, 환경별로 다르게 줄 수 있고, 위반을 알람으로 걸 수 있다.

```yaml
# context-budget.yaml — 결제 지원 에이전트
# 총합이 모델 창보다 한참 작다는 점이 핵심. 창을 꽉 채우는 것은 목표가 아니다.
model:
  window: 200000            # 광고된 창
  reserve_output: 8000      # 출력 토큰 몫. 빼먹으면 긴 답변에서 잘린다
  working_limit: 60000      # 실제 운용 상한 — 창의 30%. 근거는 3절(열화)과 40장(비용)
allocation:
  system:        { max: 2500,  droppable: false }
  tools:         { max: 6000,  droppable: false }   # 초과하면 도구를 줄인다, 설명을 줄이지 않는다
  examples:      { max: 4000,  droppable: true,  priority: 30 }
  state_summary: { max: 3000,  droppable: false }   # 압축 산출물은 절대 안 버린다
  history:       { max: 24000, droppable: true,  priority: 20, strategy: drop_oldest_pairs }
  retrieval:     { max: 12000, droppable: true,  priority: 10 }
  tool_output:   { max: 8000,  droppable: true,  priority: 10, per_call_max: 4000 }
compaction:
  trigger_ratio: 0.75       # working_limit의 75% 도달 시
  hard_preserve: [decisions, open_items, constraints, identifiers]
alerts:
  truncation_rate_gt: 0.02  # 절단이 2%를 넘으면 예산 설계가 틀린 것
  cache_hit_rate_lt: 0.60
```

`working_limit`이 `window`의 30%라는 점의 근거는 다음 절에서 다룬다. 여기서는 **`reserve_output`** 을 짚는다. 입력 예산만 세고 출력 몫을 빼먹는 것은 놀랄 만큼 흔한 버그이며 증상이 고약하다 — 평소에는 멀쩡하다가 모델이 긴 답변을 시도할 때만 잘리고, 잘린 출력은 대개 JSON 중간에서 끊어져 파싱 실패로 나타나므로([[11 - 구조화된 출력 — 스키마·제약 디코딩·파싱 실패의 처리]]) 원인이 예산이라는 것을 알아채기까지 시간이 걸린다.

> **실무 규칙**: 컨텍스트 예산은 "모델 창 − 출력 몫 − 안전 마진"이 아니라 **과업이 실제로 필요로 하는 양에서 출발해 위로 쌓아 올린 값**이어야 한다. 창에서 빼는 방식으로 정하면 항상 창을 꽉 채우게 되고, 채운 만큼 열화와 비용을 낸다.

### 2.3 언제 예산 회계가 작동하지 않는가

세 경우다.

**단일 항목이 예산 전체를 초과할 때.** 고객이 40MB짜리 정산 CSV를 첨부했다면 어떤 배분표도 소용없다. 필요한 것은 예산이 아니라 **처리 전략의 변경** — 코드로 처리하고 결과만 넣거나([[26 - 환경과 행동 공간 — 코드 실행·CodeAct·브라우저·컴퓨터 사용]]), 외부에 두고 포인터만 넘기는 것(7절). 예산 초과를 절단으로 처리하면 모델은 잘린 CSV의 앞 200줄만 보고 전체를 판단한다.

**우선순위가 실제 유용성과 무관할 때.** `priority` 숫자는 우리의 추측이다. 검색 결과가 이력보다 중요한지는 과업마다 다르고 턴마다 다르다. 고정 우선순위는 평균적으로 맞을 뿐이며, 평균적으로 맞는 것이 특정 케이스에서 치명적으로 틀릴 수 있다. 처방은 우선순위를 정교하게 만드는 것이 아니라 — 그 방향은 끝이 없다 — **버려진 것을 관측하고, 버려진 뒤 실패한 케이스를 모아 예산을 조정하는 것**이다.

**압축 자체가 예산을 먹을 때.** 요약을 생성하려면 요약 대상을 모델에 넣어야 하고, 그 호출도 토큰과 지연을 쓴다. 이력이 계속 자라는 긴 세션에서는 압축이 압축을 부르고, 어느 순간 "일하는 시간보다 정리하는 시간이 긴" 상태가 된다. 6절에서 압축 트리거를 비율이 아니라 **경계**로 잡으라고 권하는 이유다.

## 3. "다 넣으면 안전하다"는 왜 틀렸는가 — 컨텍스트 열화의 해부

컨텍스트 창이 8K였을 때는 예산 관리가 물리적 필연이었다. 200K, 1M이 된 지금은 그렇지 않아서 "이제 다 넣으면 되는 것 아닌가"라는 질문이 나온다. 답은 **아니오**이며 이유는 세 겹이다 — 비용, 지연(prefill이 길이에 비례해 늘어남), 그리고 가장 중요한 **정확도**. 앞의 둘은 명백하니 셋째를 파고들자.

### 3.1 위치는 균질하지 않다

가장 잘 재현된 관측부터 시작한다. Nelson F. Liu 등의 "Lost in the Middle: How Language Models Use Long Contexts"(2023년 arXiv 프리프린트, TACL 2024 게재)는 다중 문서 QA와 키-값 검색 과업에서, 정답이 들어 있는 문서의 **위치**에 따라 정확도가 달라진다는 것을 보였다. 성능 곡선이 U자를 그린다 — 맨 앞과 맨 뒤가 높고 가운데가 낮다. 문서 수를 늘려 컨텍스트를 길게 하면 전체적으로 더 떨어진다. 이 결과는 이후 여러 모델·과업에서 형태가 반복 관찰됐고, 지금은 "긴 컨텍스트 설계의 기본 상수"처럼 취급된다.

왜 U자인가에 대해서는 학습 데이터에서 문서의 시작부와 종결부가 구조적으로 중요하다는 점, 위치 인코딩이 최근 토큰에 유리하다는 성질, 지시-튜닝 데이터의 형태 등 몇 가지 설명이 제시돼 있다. 어느 것이 주된 원인인지는 단정하지 않는 편이 안전하다. 실무적으로 중요한 것은 **관측이 견고하다는 사실**과 거기서 나오는 배치 규칙이다.

```
컨텍스트 창의 유효 주의 (도식 — 정확한 곡선이 아니라 형태의 요약)

 정확도 ^
   |█                                                     █
   |███                                                 ███
   |█████                                          █████
   |██████████                            ██████████
   |███████████████                  ███████████████
   +--------------------------------------------------------> 위치
   시작                        가운데                       끝
   ↑                            ↑                           ↑
 시스템·도구 정의        여기 묻힌 것은            현재 지시·최신 도구 결과
 (안정, 반복 노출)        "없는 것에 가깝다"        (가장 강하게 작동)
```

여기서 배치 규칙 셋이 나온다. **결정적인 지시는 앞과 뒤 양쪽에 둔다** — 시스템 프롬프트에 규칙을 쓰고, 긴 문서 뒤에 "위 문서를 근거로 답하되 문서에 없는 내용은 '자료 없음'이라고 하라"를 다시 붙인다. 중복이지만 유효한 중복이다. **중요한 검색 결과를 가운데 묻지 않는다** — 재랭킹 점수가 높은 것을 앞뒤로, 낮은 것을 가운데 두는 배열이 실무에서 자주 쓰이되 순위 신뢰도가 있을 때만 의미가 있다. 그리고 **긴 것 자체를 줄인다** — 앞의 두 규칙은 완화책이지 해결책이 아니다.

### 3.2 방해자가 오답을 능동적으로 유인한다

위치 편향보다 실무에서 더 자주 사고를 내는 것은 **방해자(distractor)** 다. 무관한 정보가 컨텍스트에 있으면 모델의 주의가 희석되는 정도가 아니라, 그 정보가 **오답의 재료로 쓰인다.**

결제 도메인의 예를 들자. "카드 결제가 실패했다"는 문의에 검색기가 문서 12개를 가져왔고, 그중 하나가 **다른 PG사의** 오류 코드표인데 거기에도 `8104`가 있으며 의미는 다르다. 모델은 정답 문서와 방해자를 둘 다 보고 있다. 이때 관찰되는 실패는 "모른다"가 아니라 **"자신 있게 다른 PG의 해석을 답한다"** 이다. 방해자가 없었다면 "해당 코드에 대한 자료가 없다"고 답했을 수 있다. 문서를 더 넣어서 정확도가 떨어진 것이다.

Chroma Research가 2025년 7월 발표한 기술 보고서 "Context Rot: How Increasing Input Tokens Impacts LLM Performance"(Kelly Hong, Anton Troynikov, Jeff Huber)는 18개 모델을 대상으로 입력 길이가 늘어남에 따라 성능이 **일관되게 유지되지 않는다**는 것, 그 열화가 아주 단순한 과업에서도 나타난다는 것을 보고했다. 보고서가 강조하는 점 하나가 특히 실무적이다 — 중요한 것은 관련 정보가 컨텍스트에 **존재하는지**가 아니라 **어떻게 제시되는지**라는 것.

> **흔한 오개념.** "needle-in-a-haystack 테스트를 100% 통과했으니 이 모델은 긴 컨텍스트를 잘 다룬다." NIAH 계열은 대개 **어휘적으로 눈에 띄는 문장 하나**를 무관한 텍스트 더미에 심고 찾게 한다. 검색 과업이지 추론 과업이 아니다. 실제 에이전트는 컨텍스트 전체에 흩어진 여러 사실을 **종합**하고, 모순되는 정보 중 무엇이 최신인지 판단하고, 관련 있어 보이지만 아닌 것을 **배제**해야 한다. 실제로 질문과 needle 사이의 어휘 중첩을 의도적으로 제거해 잠재적 연관을 추론해야만 풀리게 만든 벤치마크(Modarressi 등, "NoLiMa: Long-Context Evaluation Beyond Literal Matching", ICML 2025)에서는 같은 모델의 점수가 훨씬 빠르게 떨어진다 — 논문이 든 예로 GPT-4o는 짧은 컨텍스트에서 99.3%이던 정확도가 32K 지점에서 69.7%로 내려간다. NIAH는 하한을 확인하는 도구지 상한을 보증하는 도구가 아니다.

### 3.3 유효 컨텍스트는 자기 도메인에서 재야 한다

"창의 30%를 운용 상한으로 잡는다"는 2.2절의 숫자는 어디서 왔는가? 정직하게 말하면 **일반적으로 통용되는 상수는 없다.** 모델·과업·컨텍스트 구성 방식마다 다르고, 벤더가 발표하는 장문 벤치마크 점수도 컨텍스트 구성이 우리 것과 달라 그대로 옮겨 쓸 수 없다. 필요한 것은 **자기 과업으로 만든 열화 곡선**이며, 방법은 단순하다.

```python
# 유효 컨텍스트 측정: 정답이 고정된 케이스에 '패딩'을 늘려 가며 정확도를 잰다.
# 패딩은 로렘입숨이 아니라 '그럴듯하지만 무관한 우리 도메인 문서'여야 한다 —
# 무의미한 패딩은 모델이 쉽게 무시하므로 열화를 과소평가하게 된다.
LENGTHS = [4_000, 8_000, 16_000, 32_000, 64_000, 128_000]

def measure(cases, distractor_pool, llm) -> dict[int, float]:
    curve = {}
    for target in LENGTHS:
        correct = 0
        for case in cases:
            padding = sample_until(distractor_pool, target - case.tokens)
            # 위치 편향을 평균화하기 위해 정답 문서 위치를 무작위화한다.
            ctx = shuffle_with_answer_at_random_position(case.answer_doc, padding)
            correct += case.check(llm.complete(system=SYSTEM, messages=[user(ctx, case.question)]))
        curve[target] = correct / len(cases)
    return curve

# 판독: 정확도가 기준선 대비 유의미하게 꺾이는 지점이 그 과업의 '유효 컨텍스트'다.
# 모델 교체·프롬프트 변경 때마다 다시 재야 한다 — 41장의 회귀 테스트 대상이다.
```

이 측정에서 흔히 나오는 결과가 둘 있다. 하나는 꺾이는 지점이 **광고된 창보다 훨씬 앞**이라는 것. 다른 하나는 꺾이는 지점이 **정확도보다 다른 지표에서 먼저 나타난다**는 것 — 답은 여전히 맞지만 형식 준수가 무너지거나(JSON 필드 누락), 지시 준수가 무너진다(금지한 표현을 쓴다). 긴 컨텍스트에서 시스템 프롬프트의 제약이 먼저 약해지는 현상은 실무에서 반복적으로 보고되며, 4절의 시스템 프롬프트 설계와 3.1절의 "지시를 뒤에도 반복" 규칙이 여기서 만난다.

**언제 이 측정이 오도하는가.** 합성 패딩으로 만든 곡선은 실제 세션의 열화를 과소평가한다. 실제 세션은 무관한 문서가 아니라 **자기 자신의 과거 발화**로 차 있고 그중 일부는 지금 상황과 모순되는데(3턴 전에 "이 결제는 취소됐다"고 판단했다가 뒤집힌 경우), 모순된 자기 이력은 무관 문서보다 훨씬 강력한 방해자다. 곡선은 상한의 근사치로 쓰고, 실제 상한은 프로덕션 트레이스에서 세션 길이와 실패율의 상관으로 확인하는 편이 낫다([[39 - 관측성 — 트레이싱·로깅·리플레이·디버깅]]).

> **흔한 오개념.** "컨텍스트가 1M이니 RAG는 필요 없다." 세 가지가 동시에 틀렸다. **비용** — 1M 토큰을 매 턴 재전송하는 것은 캐시를 감안해도 검색보다 몇 자릿수 비싸다. **지연** — prefill 비용은 길이에 대해 최소 선형이고 어텐션 항까지 세면 그 이상으로 늘며, 첫 토큰까지의 시간이 사용자 체감을 지배한다. **정확도** — 위에서 본 열화. 긴 컨텍스트가 바꾼 것은 "검색이 필요 없어졌다"가 아니라 **"청크를 더 크게 가져가도 된다"** 와 **"재랭킹의 정밀도 요구가 완화됐다"** 이다. RAG의 종말이 아니라 하이퍼파라미터의 이동이다([[24 - RAG와 에이전틱 검색 — 검색을 행동으로]]).

## 4. 시스템 프롬프트의 고도 — 너무 낮으면 부서지고 너무 높으면 흔들린다

시스템 프롬프트는 컨텍스트에서 토큰 비중이 가장 작으면서 영향력은 가장 큰 블록이다. 매 턴 반복 노출되고, 창의 맨 앞에 있으며(3.1절 U자 곡선의 유리한 자리), 다른 모든 블록의 해석 규칙을 정한다. 그래서 여기서 무엇을 어떤 **추상 수준**으로 쓸 것인가가 독립적인 설계 문제가 된다. 이 추상 수준을 "고도(altitude)"라고 부르자.

### 4.1 세 고도의 실제 모습

결제 실패 문의를 처리하는 지원 에이전트라는 같은 과업에 대해 세 고도를 나란히 놓는다.

**저고도 (하드코딩된 논리).**

```text
결제 실패 문의를 처리하라.
- pg_code가 8104이면 "KCP 상점 승인 상태 문제입니다. KCP에 문의하세요"라고 답하라.
- pg_code가 504412이면 "가상계좌 부분환불 미계약입니다"라고 답하라.
- pg_code가 01이고 채널이 이니시스이면 ... (이하 60줄)
- 위에 없는 코드이면 "확인 후 회신드리겠습니다"라고 답하라.
- 단, 채널이 KCP_V2이고 pg_code가 8104이고 storeId가 store-1234이면 ...
```

**중고도 (판단 기준과 절차).**

```text
너는 PG 연동 결제의 실패 원인을 판별하는 지원 엔지니어다.

## 판별 절차
1. 결제 건을 조회해 채널·PG사·시각·금액·상태를 확정한다. 사용자가 말한 것과
   조회 결과가 다르면 조회 결과를 따르되, 차이를 답변에 명시한다.
2. PG 원본 응답(코드·메시지)을 확보한다. 확보하지 못했으면 추측하지 않는다.
3. 원인을 세 범주 중 하나로 분류한다:
   - 가맹점 설정 문제(PG측 계약·개통·MID 설정) → 고객이 PG사에 요청해야 함
   - 우리 시스템 문제(요청 조립·상태 전이·타임아웃) → 내부 티켓 생성
   - 고객 행동(사용자 취소, 잔액 부족, 창 이탈) → 안내로 종결
4. 범주가 확정되지 않으면 "확정되지 않음"으로 두고 사람에게 넘긴다.

## 원칙
- 코드표 해석은 반드시 채널의 PG사와 일치하는 표에서 온 것이어야 한다.
  다른 PG사의 같은 숫자 코드는 의미가 다르다.
- 금액·식별자·시각은 원문 그대로 인용한다. 요약하거나 반올림하지 않는다.
- 되돌릴 수 없는 조치는 제안만 하고 실행하지 않는다.
```

**고고도 (막연한 역할 부여).**

```text
너는 도움이 되고 정확하며 전문적인 결제 지원 전문가다.
고객의 문제를 신속하게 파악하고 최선의 해결책을 제시하라. 항상 친절하게 응대하라.
```

저고도는 **행동을 완전히 예측 가능하게 만드는 대신 미지의 입력에 부서진다.** 코드표가 60줄이면 61번째 코드에서 무너지고, PG사가 늘어날 때마다 조합이 곱으로 늘어난다. 무엇보다 코드로 쓸 것을 프롬프트로 쓴 것이다 — 결정론적 매핑은 딕셔너리 조회로 하고 그 조회를 **도구**로 제공해야 한다. 프롬프트에 넣으면 매 턴 토큰을 내면서 확률적으로 실행되는 룩업 테이블을 갖게 된다.

고고도는 반대 실패다. "정확하게"가 무엇인지 모델이 알아서 채우고, 그 채움이 요청마다 달라진다. 그리고 이런 프롬프트는 **평가할 수 없다** — 무엇이 위반인지 정의돼 있지 않으니 회귀를 감지할 수 없다.

중고도가 목표다. 절차는 있지만 각 단계의 판단은 모델에게 맡기고, **하지 말아야 할 것과 확신 없을 때의 행동**이 명시돼 있으며, 서술이 모두 검증 가능하다 — "다른 PG사 코드표를 인용하지 않는다"는 평가 케이스로 만들 수 있다.

| 고도 | 형태 | 강점 | 실패 방식 | 진짜 처방 |
|---|---|---|---|---|
| 저 | if-else 나열, 케이스 열거 | 열거된 케이스에서 완벽 | 미열거 입력에서 붕괴, 조합 폭발, 유지보수 불가 | 코드/도구/DB로 옮긴다 |
| 중 | 절차 + 판단 기준 + 금지 + 기권 | 일반화되고 평가 가능 | 도메인이 크게 바뀌면 절차 자체가 낡음 | 절차를 버전으로 관리 |
| 고 | 역할·형용사 나열 | 짧고 유연 | 행동 분산, 회귀 감지 불가 | 관측된 실패를 규칙으로 승격 |

> **실무 규칙**: 시스템 프롬프트에 조건 분기가 세 개 이상 쌓이기 시작하면 고도가 낮아지고 있다는 신호다. 그 분기가 **결정론적으로 판단 가능한가**를 물어라. 가능하면 코드로 내리고, 불가능하면 그 판단의 **기준**을 쓴다. "A면 B하라"가 아니라 "A인지 판단하는 방법과 그 결과로 무엇이 달라지는지"를 쓰는 것.

### 4.2 고도를 유지하는 문서 구조

중고도를 유지하려면 프롬프트가 구조를 가져야 한다. 실무에서 반복 수렴하는 형태는 여섯 절이다 — **역할과 범위**(무엇을 하고 무엇은 하지 않는가), **입력에 대해 알아야 할 것**(데이터의 성질·신뢰도·알려진 함정), **절차**(번호 매긴 단계, 각 단계는 관찰 가능한 산출을 남긴다), **판단 기준**(애매한 경계를 가르는 법, 긍정 예와 부정 예), **금지와 기권**(절대 하지 않을 것, 확신 없을 때의 행동), **출력 형식**(단, 스키마는 여기가 아니라 응답 스키마로 강제한다).

자주 과소평가되는 항목이 **"금지와 기권"** 이다. 모델의 기본 성향은 답을 만드는 쪽이며 "모른다"는 선택지는 명시하지 않으면 사실상 없다. [[02 - LLM이라는 재료 — 확률적 생성기 위에 시스템을 짓는다는 것]]에서 다룬 것처럼 평가 관행이 추측을 벌하지 않으면 추측이 남는다. 기권 경로를 **1급 결과**로 만드는 한 줄이 오답률을 눈에 띄게 줄이는 경우가 많되, 너무 매력적으로 만들면 쉬운 것까지 넘긴다 — 기권 조건의 구체화가 균형점이다.

판단 기준에는 **부정 예**를 반드시 넣는다. "환불 요청으로 분류한다"만 있으면 "배송이 늦어 짜증난다"도 환불이 된다. "단, 아직 환불을 요구하지 않은 불만 표현은 제외한다"가 있어야 경계가 선다. 도구 설명에도 똑같이 적용되는 원리다([[13 - 도구 사용 II — 도구 설계의 기술과 도구 폭발 문제]]).

### 4.3 언제 고도 조절이 작동하지 않는가

**모델 능력이 절차를 소화하지 못할 때.** 고도는 절대적 속성이 아니라 모델 능력에 상대적이다. 같은 중고도 프롬프트가 강한 모델에서는 잘 작동하고 작은 모델에서는 단계를 건너뛴다. 모델을 낮은 티어로 바꾸는 순간([[40 - 비용과 지연 — 캐싱·모델 라우팅·예산 관리]]의 비용 라우팅) 고도를 낮춰야 할 수 있다. "모델만 바꿨는데 왜 깨지죠"의 답은 대개 여기 있다.

**규칙이 서로 충돌할 때.** "간결하게 답하라"와 "모든 근거를 인용하라"가 함께 있으면 모델은 둘 중 하나를 임의로 택하고, 그 선택이 입력마다 달라진다. 이건 고도가 아니라 **일관성**의 문제이며, 처방은 충돌하는 지시에 명시적 우선순위를 주는 것이다. 프롬프트가 200줄을 넘으면 이런 잠재 충돌을 사람이 다 추적하지 못한다. 그 자체가 분해 신호다.

**긴 컨텍스트에서 지시가 약해질 때.** 3.3절에서 본 대로 컨텍스트가 길어지면 정확도보다 지시 준수가 먼저 무너진다. 대응은 결정적 제약을 **꼬리에서 반복**하는 것과, 제약을 프롬프트가 아니라 **바깥에서 강제**하는 것이다 — 스키마 검증([[11 - 구조화된 출력 — 스키마·제약 디코딩·파싱 실패의 처리]]), 도구 화이트리스트, 승인 게이트([[35 - 휴먼 인 더 루프 — 승인·개입·에스컬레이션]]). 프롬프트의 지시는 소프트한 사전확률이지 보안 경계가 아니며, 이 구분은 [[37 - 프롬프트 인젝션과 에이전트 보안 — 신뢰 경계의 붕괴]]에서 훨씬 심각한 맥락으로 돌아온다.

> **흔한 오개념.** "시스템 프롬프트에 넣었으니 모델이 반드시 지킨다." 역할 계층(system > developer > user > tool)은 학습으로 주입된 **경향성**이지 실행 시점의 강제가 아니다. 컨텍스트가 길어지면, 사용자 입력이 강하게 반대 방향을 밀면, 도구 출력에 지시처럼 보이는 문자열이 섞이면 이 경향성은 얼마든지 뒤집힌다. 판별 기준 하나 — **위반이 발생했을 때 되돌릴 수 없는가.** 되돌릴 수 없으면 코드로 강제한다.

## 5. 컨텍스트 배치는 캐시 레이아웃 문제다

여기서 성격이 다른 제약이 들어온다. 지금까지는 "모델이 잘 읽게 하려면"이었다면 이제는 "같은 것을 두 번 계산하지 않으려면"이고, 이 제약은 배치 순서를 거의 강제한다.

### 5.1 접두사 캐싱의 기계학

[[02 - LLM이라는 재료 — 확률적 생성기 위에 시스템을 짓는다는 것]]에서 본 것처럼 생성은 prefill과 decode로 나뉘고, prefill은 입력 전체를 병렬 처리해 각 토큰의 KV 텐서를 만든다. 여기서 중요한 성질 하나 — 인과 어텐션(causal attention)에서 **위치 $i$의 KV는 위치 $0..i$ 의 토큰에만 의존한다.** 뒤에 무엇이 오든 앞부분의 KV는 바뀌지 않는다.

이것이 접두사 캐싱이 성립하는 이유의 전부다. 두 요청의 토큰 시퀀스가 앞에서 $k$개까지 **완전히 동일**하면 그 $k$개의 KV를 재사용할 수 있고, $k+1$번째에서 한 토큰이라도 다르면 그 이후는 전부 다시 계산해야 한다.

```
요청 A: [시스템 2,400][도구 5,800][예시 3,900][이력 18,000][현재 지시 120]
요청 B: [시스템 2,400][도구 5,800][예시 3,900][이력 18,000 + 도구결과 1,400][현재 지시 90]
         └──────────── 동일한 접두사 30,100 토큰 ────────────┘
                                                    ↑ 여기부터 재계산

→ B의 prefill 비용: 30,100 토큰은 캐시 읽기, 1,490 토큰만 신규 계산.

반대 배치였다면:
요청 A: [현재 지시 120][이력 18,000][예시 3,900][도구 5,800][시스템 2,400]
요청 B: [현재 지시 90 ][...]
         └ 첫 토큰부터 다름 → 캐시 적중 0. 30,000 토큰을 매 턴 다시 계산.
```

주요 프로바이더의 과금 구조도 이를 반영한다. Anthropic API를 예로 들면(2026년 초 기준) 캐시 쓰기는 기본 입력 단가의 1.25배(5분 TTL, 1시간 TTL은 2배), 캐시 읽기는 0.1배로 과금되며 캐시 가능한 최소 길이가 모델별로 정해져 있다(대형 모델 기준 1,024토큰 수준). 산술은 단순하다 — 캐시 없이 두 번 부르면 $1.0 + 1.0 = 2.0$, 캐시를 걸면 $1.25 + 0.1 = 1.35$. 즉 **한 번만 재사용해도 본전을 넘긴다.** OpenAI 계열은 명시적 마커 없이 자동 접두사 캐싱을 하는 형태로 제공돼 왔다. 세부 수치는 바뀌므로 구조를 기억하는 편이 낫다 — 쓰기는 약간 비싸고, 읽기는 훨씬 싸며, 정확히 일치하는 접두사에만 적용된다.

```json
// 캐시 경계를 명시적으로 두는 요청 형태(중립화된 표현).
// 경계 앞은 '재사용 대상', 뒤는 '매 턴 변하는 것'.
{
  "system": [{ "type": "text", "text": "너는 PG 연동 결제의...(2,400토큰)",
               "cache_control": { "type": "ephemeral" } }],
  "tools": [{ "name": "get_payment", "input_schema": {} }],
  "messages": [
    { "role": "user", "content": [
        { "type": "text", "text": "...세션 상태 요약(압축 산출물, 1,800토큰)...",
          "cache_control": { "type": "ephemeral" } }]},
    { "role": "user", "content": "...최근 4턴 원문..." },
    { "role": "user", "content": "그럼 재시도하면 성공할까?" }
  ]
}
```

경계를 앞쪽에만 두면 캐시 히트 구간이 짧고, 뒤쪽까지 여러 개 두면 히트 구간은 길어지지만 쓰기 비용이 늘고 관리가 복잡해진다. 실무의 기본형은 두 개다 — **도구 정의 끝**(배포 단위로만 변함)과 **압축 산출물 끝**(압축 시에만 변함).

### 5.2 캐시를 깨뜨리는 실수 도감

아래는 전부 "동작은 하는데 비용이 몇 배"라는 형태로 나타나므로, 캐시 적중률을 계측하지 않으면 몇 달이고 모른 채 지낸다.

| 실수 | 왜 깨지는가 | 대안 |
|---|---|---|
| 시스템 프롬프트에 `현재 시각: 2026-07-20 14:33:21` | 매 요청 접두사 첫 블록이 달라짐 | 시각은 꼬리에 넣거나, 도구로 조회하게 한다 |
| 시스템 프롬프트에 요청 ID·트레이스 ID | 위와 동일 | 로깅 메타데이터로만 보관 |
| 도구 목록을 상황에 따라 동적 구성 | 도구 정의가 접두사인데 매번 다름 | 도구 집합을 소수의 고정 프로필로 묶고 프로필 단위로 라우팅 |
| 도구 정의를 `dict` 순회로 직렬화 | 순서가 실행마다 달라질 수 있음 | 항상 결정론적 정렬로 직렬화 |
| few-shot을 매 턴 검색으로 선택 | 예시 블록이 매번 다름 | 고정 정본 예시를 쓰거나, 동적 예시를 캐시 경계 **뒤**로 |
| 대화 이력 중간을 편집·재요약 | 접두사가 소급 변경됨 | 압축은 접미사만 남기고 앞을 통째로 교체하는 방식으로 |
| JSON 직렬화 시 공백·키 순서가 불안정 | 토큰 시퀀스가 미세하게 달라짐 | 정규화된 직렬화기 하나로 통일 |

마지막 항목이 특히 음험하다. `json.dumps`의 기본 구분자와 `ensure_ascii` 설정, 키 정렬 여부가 호출 지점마다 다르면 같은 논리적 내용이 다른 토큰 시퀀스가 된다. [[41 - JSON과 직렬화]]의 직렬화 안정성 문제가 여기서 비용으로 직결된다.

```python
# 캐시 안정성을 위한 정규화된 직렬화. 조립기 전체가 이것만 쓰게 강제한다.
# sort_keys: 키 순서 고정 / separators: 공백 제거로 토큰 절약 및 형태 고정
# ensure_ascii=False: 한국어를 \uXXXX로 부풀리지 않는다(토큰 수가 크게 달라진다)
stable = lambda o: json.dumps(o, sort_keys=True, ensure_ascii=False, separators=(",", ":"))
```

> **흔한 오개념.** "프롬프트 캐싱은 켜기만 하면 싸진다." 캐시 쓰기가 기본 단가보다 비싸므로 **재사용되지 않는 접두사에 캐시를 걸면 오히려 손해**다 — 한 번 부르고 끝나는 단발 분류 요청, 사용자가 수 시간에 한 번 오는 저빈도 세션의 5분 TTL 캐시가 그렇다. 캐시는 "재사용 확률 × 접두사 길이"가 충분히 클 때만 이득이며, 히트 여부는 응답 메타데이터에 보고되므로 **추정하지 말고 재야 한다.**

### 5.3 캐시 친화성과 신선도가 충돌하는 지점

캐시가 배치를 강제한다는 말은, 정보의 중요도가 아니라 **변동 주기**로 순서가 정해진다는 뜻이다. 여기서 실제 충돌이 생긴다.

가장 흔한 것이 **동적 컨텍스트의 위치 문제**다. "이 고객은 VIP이고 최근 3건의 클레임이 있다" 같은 정보는 중요하므로 앞에 두고 싶지만, 고객마다 다르므로 앞에 두면 캐시가 고객 단위로 쪼개진다. 선택지는 셋이다. **꼬리로 보내면** 캐시는 지키지만 U자 곡선의 유리한 자리를 못 쓴다. **고객별 캐시를 받아들이면** 같은 고객이 여러 턴을 이어 가는 세션에서는 이득이고 한 턴만 쓰고 떠나면 손해다. 대부분의 경우 최선은 셋째 — **정적 부분과 동적 부분의 분리**다. "VIP 고객 응대 원칙"이라는 긴 설명은 시스템 프롬프트에 두어 캐시하고, "이 고객이 VIP임"이라는 짧은 사실만 꼬리에 매 턴 새로 넣는다.

두 번째 충돌은 **압축과 캐시**다. 압축이 일어나면 이력 앞부분이 요약으로 교체되므로 그 지점 이후 접두사가 전부 무효화된다. 즉 압축은 토큰을 아끼는 대신 **캐시를 통째로 버린다.** 압축 직후 한 턴은 전체 재계산이 필요하고, 그 비용은 압축으로 아낀 것을 상당 부분 상쇄한다. 그래서 압축을 자주 조금씩 하는 것은 나쁜 전략이다 — **드물게, 크게** 하는 편이 낫다.

> **실무 규칙**: 캐시 적중률과 압축 빈도를 **함께** 본다. 적중률이 60% 아래인데 압축이 잦다면 트리거가 너무 예민한 것이고, 적중률이 낮은데 압축은 드물다면 접두사에 변동 요소가 섞인 것이다(위 표에서 찾는다). 따로 보면 원인을 못 가른다.

## 6. 압축은 손실 압축이다 — 무엇을 버릴지 정하는 문제

컨텍스트가 예산에 도달했을 때 선택지는 셋뿐이다 — **자르거나(truncation), 요약하거나(compaction), 밖으로 내보내거나(externalization).** 이 절은 두 번째를, 다음 절은 세 번째를 다룬다.

### 6.1 자르기는 왜 거의 항상 나쁜가

가장 단순한 전략은 오래된 메시지부터 버리는 것(FIFO)이다. 구현이 쉽고, 캐시 관점에서도 접두사를 바꾸므로 사실 좋지도 않다. 그런데 무엇보다 나쁜 것은 **버려지는 것이 대개 가장 중요한 것**이라는 점이다. 에이전트 세션의 초반 턴에는 사용자의 원래 요청, 제약 조건, 합의된 목표, 초기 조사에서 확정한 사실이 있다. 후반 턴에는 세부 조정과 도구 호출의 반복이 있다. FIFO는 정확히 거꾸로 버린다. 20턴짜리 조사 세션에서 "원래 무엇을 찾으라고 했는지"가 사라지면 에이전트는 방향을 잃고 표류한다 — [[04 - 에이전트 루프의 해부 — 관찰·결정·행동·정지]]에서 말한 "진행 없는 루프"의 흔한 원인이다.

예외는 대화가 **에피소드적**이고 턴 간 의존이 약한 경우다. 판별 기준: "3턴 전 내용을 몰라도 지금 턴을 처리할 수 있는가." 예라면 자르기로 충분하고, 아니오라면 압축이 필요하다.

### 6.2 무엇을 보존하고 무엇을 버리는가

압축의 본질은 요약 품질이 아니라 **보존 목록의 설계**다. 요약 프롬프트를 잘 쓰는 것보다 무엇을 반드시 남길지 명시적으로 정하는 쪽이 훨씬 큰 차이를 만든다.

| 반드시 보존             | 이유                                | 버려도 되는 것      | 이유                   |
| ------------------ | --------------------------------- | ------------- | -------------------- |
| 원래 목표와 제약          | 표류 방지. 가장 자주 유실되고 가장 비싸다          | 실패한 시도의 원문    | 결론만 남기면 된다           |
| 확정된 결정과 그 근거       | 재논의 방지. 근거가 없으면 뒤집힌다              | 중간 탐색 경로      | "A를 봤는데 아니었다"만 남기면 됨 |
| 미해결 항목(open items) | 잊히면 영원히 안 돌아온다                    | 도구 호출의 원본 인자  | 결과만 남으면 대개 충분        |
| **식별자 원문**         | paymentId·txId·경로·URL. 요약하면 복구 불가 | 장황한 서술문       | 정보 밀도가 낮다            |
| 사용자가 명시한 선호·금지     | 위반 시 신뢰 상실                        | 인사·확인 응답      | 정보 없음                |
| 실패한 접근의 **결론**     | 같은 실패 반복 방지                       | 성공한 도구 출력의 전문 | 요약 + 재조회 가능성         |

굵게 표시한 **식별자 원문**을 특히 강조한다. 요약 모델은 `paymentId: pay_01HQ8ZK3M9X2`를 "결제 건"으로 바꿔 버리는 경향이 있고, 그 순간 그 건을 다시 조회할 방법이 사라진다. 처방은 요약을 자유 텍스트로 두지 않고 **구조화된 상태 객체**로 만드는 것이다.

```kotlin
// 압축 산출물을 자유 텍스트가 아니라 타입으로 정의한다.
// 이렇게 하면 (1) 식별자가 문자열 요약에 녹아 사라지지 않고
//            (2) 필드별로 크기 상한을 걸 수 있고
//            (3) 압축의 회귀를 테스트할 수 있다 (필드 유실 = 실패)
data class SessionState(
    val goal: String,                              // 원래 요청. 요약 대상 아님 — 원문 보존
    val constraints: List<String>,                 // 사용자가 명시한 제약·금지
    val decisions: List<Decision>,                 // 확정된 것과 그 근거
    val openItems: List<String>,                   // 아직 안 끝난 것
    val entities: Map<String, EntityRef>,          // 식별자 테이블 — 절대 요약 금지
    val ruledOut: List<RuledOut>,                  // 시도했고 아니었던 것 (반복 방지)
    val narrative: String                          // 위에 안 담기는 나머지의 자유 요약
) {
    init {
        // 압축이 상태를 망가뜨리는 것을 조립 시점에 잡는다.
        require(goal.isNotBlank()) { "압축이 원래 목표를 소실시켰다" }
        require(narrative.length <= 4000) { "narrative가 예산을 초과했다" }
    }
}

data class Decision(val what: String, val because: String, val atTurn: Int)
data class RuledOut(val hypothesis: String, val evidence: String)
data class EntityRef(val kind: String, val id: String, val note: String)   // id는 원문 그대로
```

부수적 이득이 크다 — **압축 결과를 테스트할 수 있다.** "20턴짜리 트레이스를 압축했을 때 `entities`의 모든 식별자가 보존되는가"는 자동 검사가 가능한 명제다. 자유 텍스트 요약에서는 불가능하다.

```python
# 압축 함수. 핵심은 '이전 상태 + 최근 원문' → '새 상태'라는 누적 형태.
# 매번 전체 이력을 다시 요약하면 (a) 비용이 이차로 늘고 (b) 손실이 복리로 쌓인다.
def compact(prev: SessionState | None, recent: list[Message], llm) -> SessionState:
    payload = {"previous_state": prev and prev.to_dict(), "new_messages": [m.to_dict() for m in recent]}
    # 구조화 출력으로 강제한다. 자유 텍스트를 파싱하는 순간 필드 유실이 조용해진다.
    state = llm.complete_structured(system=COMPACTION_PROMPT, input=stable(payload), schema=SessionState)

    if prev:
        # 이전 상태의 식별자는 하나도 사라지면 안 된다(단조성).
        # 실패시키지 않고 되살린다 — 압축은 정보를 추가만 하고 삭제는 명시적으로만.
        lost = set(prev.entities) - set(state.entities)
        state.entities.update({k: prev.entities[k] for k in lost})
        metrics.incr("compaction.entity_recovered", len(lost))
        # 미해결 항목이 통째로 비면 의심한다(해결 근거가 decisions에 있어야 한다).
        if prev.open_items and not state.open_items and not _resolved_in(state, prev.open_items):
            metrics.incr("compaction.open_items_vanished")
    return state
```

### 6.3 압축 시점 — 비율이 아니라 경계로

`working_limit`의 75%에 도달하면 압축한다는 규칙(2.2절)은 출발점으로는 괜찮지만 부족하다. **압축이 아무 데서나 일어난다**는 것이 문제다 — 도구 호출과 그 결과 사이에서 끼어들면 모델은 자기가 방금 무엇을 요청했는지 모르는 상태로 결과를 받는다. 더 나은 트리거는 **의미적 경계**다.

```
좋은 압축 지점                        나쁜 압축 지점
 · 하위 과업 완료 직후                  · tool_use 와 tool_result 사이
   (세부는 결론만 남기면 된다)            (대응이 깨진다. 일부 API는 아예 거부)
 · 도구 호출-결과 쌍이 닫힌 직후        · 다단계 추론 중간
   (열린 요청이 없다)                     (논증의 앞부분만 사라진다)
 · 사용자가 새 주제를 꺼낸 직후         · 사용자 응답 대기 중
 · 계획이 끝나고 실행에 진입할 때         (사용자가 참조한 것이 없어진다)
```

실무 구현은 두 조건의 AND다 — "예산의 X%를 넘었고 **그리고** 안전한 경계에 도달했을 때". 하드 리밋에 닿았는데 경계가 안 오면 강제 압축하되 알람을 남긴다. 그런 상황이 잦다면 과업 하나가 너무 큰 것이므로 압축이 아니라 분해가 필요하다([[09 - 오케스트레이터-워커 — 동적 분해와 종합]]).

### 6.4 압축이 청구서를 보내는 방식 — 언제 작동하지 않는가

압축의 손실은 즉시 드러나지 않는다. 압축 직후에는 멀쩡해 보이고, 손실은 **나중에 다른 형태로** 나타난다. 이것이 압축 관련 버그가 디버깅하기 어려운 이유다. 관찰되는 형태들.

**(1) 이미 배제한 가설로 되돌아간다.** `ruledOut`을 보존하지 않으면 에이전트가 15턴 전에 확인한 경로를 다시 탐색한다. 증상은 "루프가 안 끝난다"이고 원인은 압축이다. **(2) 제약을 위반한다.** 3턴에서 "테스트 환경은 건드리지 마세요"라고 했는데 25턴에서 건드린다 — `constraints` 누락.

**(3) 식별자를 지어낸다.** 가장 위험한 형태. 원문 식별자가 사라진 자리에 모델이 **형태가 그럴듯한 가짜**를 채운다. `pay_01HQ8ZK3M9X2`가 요약에서 "해당 결제 건"이 되었다가, 다시 필요해졌을 때 `pay_01HQ8ZK3M9X3` 같은 것이 나온다. 형식이 맞아서 검증도 통과한다. 결제 도메인에서 이건 사고이며, 6.2절의 `entities` 테이블과 단조성 검증이 여기 대응한다.

**(4) 요약의 요약이 원본에서 멀어진다.** 압축을 이전 요약 위에 반복하면 세대마다 정보가 빠지고 요약 특유의 **일반화**가 누적된다. "KCP 채널의 8104 오류"가 "PG 오류"가 되고 다시 "결제 실패"가 된다. 대응은 원본 이력을 외부에 저장해 재압축을 가능하게 두거나, 압축 세대 수에 상한을 두고 넘으면 사람에게 넘기는 것.

> **흔한 오개념.** "요약은 공짜다." 세 가지 비용이 있다. **토큰 비용** — 요약하려면 대상을 모델에 넣어야 하므로 아끼려는 것을 한 번 더 읽는다. **캐시 비용** — 5.3절에서 본 대로 압축은 접두사를 무효화한다. **정보 비용** — 손실은 되돌릴 수 없고, 무엇을 잃었는지조차 알 수 없다. 정보이론의 언어로 압축은 무손실이 아니라 손실 압축이며, 무엇을 버릴지 정하는 것이 곧 설계다([[39 - 정보이론]]).

**언제 압축 자체를 하지 말아야 하는가.** 세션이 감사 대상일 때다. 규제 산업의 상담 기록, 금융 거래 승인 이력처럼 "무엇을 근거로 그렇게 판단했는가"를 사후에 재구성해야 하면 압축된 컨텍스트는 증거가 되지 못한다. 필요한 것은 **압축과 기록의 분리** — 모델에게 주는 컨텍스트는 압축하되 원본 트레이스는 전부 별도로 영속화한다([[39 - 관측성 — 트레이싱·로깅·리플레이·디버깅]]).

## 7. 사전 적재에서 적시 검색으로 — 컨텍스트를 포인터로 바꾸기

압축이 "이미 들어온 것을 줄이는" 전략이라면 이 절은 "애초에 넣지 않는" 전략이다. 둘은 경쟁이 아니라 보완 관계이며 잘 설계된 시스템은 둘 다 쓴다.

### 7.1 두 극단과 그 사이

| | 사전 적재(pre-loading) | 적시 검색(just-in-time) |
|---|---|---|
| 방식 | 필요할 것 같은 정보를 미리 컨텍스트에 넣음 | 식별자·목록만 넣고 필요할 때 도구로 읽음 |
| 지연 | 첫 턴이 무겁고 이후 빠름 | 턴마다 도구 왕복이 추가됨 |
| 토큰 | 안 쓸 정보에도 비용 지불 | 쓴 것에만 지불 |
| 캐시 | 접두사에 넣으면 잘 캐시됨 | 매 턴 다른 내용 → 캐시 어려움 |
| 정확도 | 방해자 유입 위험 | 잘못 검색하면 정보 자체가 없음 |
| 신선도 | 적재 시점에 고정 | 항상 최신 |
| 적합 | 소량·고빈도·안정적 지식 | 대량·저빈도·변동 지식 |

적시 검색의 핵심 발상은 **컨텍스트에 데이터 대신 포인터를 둔다**는 것이고, 파일 시스템이 이 패턴의 원형이다. 코딩 에이전트는 저장소의 모든 파일을 컨텍스트에 넣지 않는다 — 디렉터리 목록과 경로만 보고 필요한 파일을 그때 읽는다. 사람 엔지니어가 하는 일과 정확히 같다. 결제 도메인으로 옮기면 이렇게 된다.

```typescript
// 나쁨: 조회 결과 전체를 컨텍스트에 밀어 넣는다.
// 결제 1건에 이벤트 200개, 각 이벤트가 PG 원본 응답을 통째로 담으면 40K 토큰이 넘는다.
const bad = () => db.query("SELECT * FROM payment_events WHERE payment_id = $1", [id]);

// 좋음: 요약 + 핸들. 모델이 필요하다고 판단할 때만 상세를 읽게 한다.
type EventDigest = {
  seq: number;
  type: string;          // "Prepared" | "Approved" | "ApproveFailed" | ...
  at: string;
  summary: string;       // 120자 상한. 정보 밀도 높은 한 줄
  hasDetail: boolean;    // 상세 조회가 의미 있는가
};

async function getPayment(id: string): Promise<{
  header: PaymentHeader;         // 상태·금액·채널 — 거의 항상 필요
  events: EventDigest[];         // 200건이어도 ~3K 토큰
  detailHandle: string;          // "payment_events:pay_01HQ8ZK3M9X2"
}> { /* ... */ }

// 상세는 별도 도구로. 범위를 강제해 한 번에 창을 폭파하지 못하게 한다.
async function readEventDetail(handle: string, seq: number[]) {
  // 오류 메시지가 곧 모델에게 주는 지시다 — 8.2절 참조
  if (seq.length > 5) throw new Error("한 번에 최대 5건. 범위를 좁혀 다시 요청하라.");
  return renderEvents(await loadEvents(handle, seq), { maxTokensPerEvent: 800 });
}
```

이 설계에서 얻는 것은 토큰 절약만이 아니다. **모델의 탐색 경로가 관측 가능해진다** — 어떤 이벤트의 상세를 읽었는지가 도구 호출 로그로 남으므로, 오답이 났을 때 "무엇을 안 보고 판단했는지"를 알 수 있다. 전부 밀어 넣는 설계에서는 그걸 알 수 없다.

### 7.2 점진적 공개(progressive disclosure)

적시 검색을 일반화하면 **점진적 공개**가 된다. 정보를 계층으로 구성하고, 각 계층이 다음 계층으로 가는 포인터를 갖게 한다.

```
계층 0 (항상 컨텍스트에)    : 시스템 프롬프트, 도구 목록, 세션 상태 요약
계층 1 (첫 조회로 들어옴)   : 헤더·목록·요약 — "무엇이 있는가"
계층 2 (모델이 선택해 읽음) : 개별 항목의 본문
계층 3 (드물게, 명시적으로) : 원본 페이로드, 전체 로그, 첨부 파일

각 계층은 다음 계층으로 가는 '주소'를 포함한다. 모델이 계층을 내려가는 것 자체가 추론 흔적이다.
  헤더 → 이벤트 목록(seq) → 이벤트 상세(seq 지정) → PG 원본 응답(raw handle)
```

이 구조가 사람의 조사 방식과 닮은 것은 우연이 아니다. 유한한 작업 기억을 가진 행위자가 큰 정보 공간을 다루는 일반적 해법이며, [[24 - RAG와 에이전틱 검색 — 검색을 행동으로]]에서 "검색을 전처리가 아니라 행동으로 본다"고 할 때의 그 구조다.

> **실무 규칙**: 반환값의 크기를 **모델이 아니라 도구가** 통제한다. "필요하면 알아서 적게 요청하겠지"는 성립하지 않는다 — 모델은 기본적으로 다 달라고 한다. `limit` 기본값을 작게 두고 상한을 하드 리밋으로 강제하며, 초과 시 "범위를 좁혀 다시 요청하라"를 오류 메시지에 담는다.

### 7.3 언제 적시 검색이 작동하지 않는가

**탐색 자체가 실패할 때.** 포인터만 준다는 것은 모델이 올바른 포인터를 고를 수 있다고 가정하는 것이다. 이벤트 200건의 요약 한 줄만 보고 "3번, 47번, 198번을 읽어야 한다"를 맞추는 일은 쉽지 않다. 요약이 나쁘면 모델은 엉뚱한 것을 읽고, 못 찾았다는 사실도 모른 채 결론을 낸다. **요약 한 줄의 품질이 전체 설계의 병목**이다. 이 요약은 사람이 설계해야 하며, 모델이 생성하게 하면 다시 압축 손실 문제로 돌아온다.

**지연이 누적될 때.** 계층을 내려갈 때마다 모델 턴이 하나씩 들고 각각 prefill과 decode를 포함한다. 대응은 **예측 적재** — 헤더를 반환할 때 "거의 항상 다음에 읽히는 것"을 함께 붙이는 것. 캐시 프리페치와 같은 발상이고([[28 - 캐싱 (Caching) - 전략·무효화·축출·장애 패턴]]), 안 쓰이면 낭비라는 같은 위험을 공유한다.

**정보가 원자적으로 필요할 때.** "이 100건의 정산 내역 중 합계가 맞지 않는 건을 찾아라"는 전체를 봐야 한다. 점진적 공개로 나누면 모델이 100번 왕복하며 부분 합계를 누적하는데, 이건 모델이 할 일이 아니다. 정답은 컨텍스트 전략이 아니라 **계산을 코드로 내리는 것**이다([[26 - 환경과 행동 공간 — 코드 실행·CodeAct·브라우저·컴퓨터 사용]]). "모델에게 데이터를 주는 대신 데이터에 대한 질문을 실행할 능력을 준다"가 더 정확한 프레이밍이다.

**신선도가 오히려 문제가 될 때.** 적시 검색은 항상 최신을 읽으므로 한 세션 안에서 같은 것을 두 번 읽었을 때 값이 달라질 수 있다. 결제 상태가 조사 중에 바뀌면 모델은 모순된 두 사실을 보게 되고 대개 이를 명시적으로 처리하지 못한다. 대응은 **세션 스냅샷** — 첫 조회 시점의 값을 고정하고 재조회 시 차이를 명시적으로 알리는 것. 분산 시스템의 읽기 일관성 문제가 그대로 재현된다([[18 - 일관성 모델 (Consistency Models) - 선형화·인과·최종·세션 보장]]).

## 8. 도구 출력이 컨텍스트를 죽인다 — 반환값 설계는 컨텍스트 설계다

2.1절의 표에서 점유 범위가 가장 넓었던 항목이 도구 출력이고, 이것은 **우리가 완전히 통제할 수 있으면서 대부분의 팀이 통제하지 않는** 항목이다. 도구의 입력 스키마는 공들여 설계하면서([[12 - 도구 사용 I — 함수 호출의 메커니즘과 계약]]) 반환값은 `JSON.stringify(row)`로 끝내는 코드를 자주 본다.

### 8.1 반환값의 세 가지 상한

**항목 수 상한.** `limit` 기본값을 작게(10~20) 두고 하드 상한(100)을 강제한다. 초과 요청은 잘라서 주는 것이 아니라 **거부하고 좁히라고 지시**한다. 조용히 잘라 주면 모델은 그게 전부인 줄 안다. **항목당 크기 상한.** 항목 하나가 클 수 있다(로그 라인, PG 원본 응답, 예외 스택). 항목마다 상한을 걸고 잘렸음을 명시한다 — `...[2,140자 생략, 상세는 read_detail(seq=47)]`. **전체 토큰 상한.** 위 둘을 통과해도 합계가 클 수 있으므로 조립기 단계에서 도구 출력 블록 전체에 예산을 걸고(2.2절 YAML의 `tool_output.max`), 넘으면 오래된 것부터 요약본으로 교체한다.

```python
# 도구 출력 후처리: 도구 구현마다 흩어지지 않게 한 곳에서 강제한다.
# '무엇을 잘랐는지'를 모델이 읽을 수 있게 남기는 것이 핵심 —
# 조용한 절단은 모델에게 '이게 전부'라는 잘못된 신호를 준다.
def shape(name: str, raw, budget: int) -> str:
    body = renderers[name](raw)                  # 도구별로 사람이 설계한 렌더러
    n = count_tokens(body)
    if n <= budget:
        return body
    return (f"{truncate_to(body, budget - 120)}\n\n"
            f"[출력이 {n}토큰이라 {budget}토큰으로 잘렸다. 전체가 필요하면 필터를 좁혀 "
            f"다시 호출하라. 사용 가능한 필터: {', '.join(filters_of(name))}]")
```

### 8.2 오류 메시지는 모델에게 주는 지시다

도구가 실패했을 때 컨텍스트에 들어가는 것이 재시도 성공률을 크게 좌우한다. [[04 - 에이전트 루프의 해부 — 관찰·결정·행동·정지]]에서 "재시도 피드백이 컨텍스트에 안 들어가는 것이 가장 흔한 버그"라고 했는데, 그 다음으로 흔한 것이 **쓸모없는 형태로 들어가는 것**이다.

| 반환된 오류 | 모델이 할 수 있는 일 | 평가 |
|---|---|---|
| `Internal Server Error` | 없음. 같은 호출을 반복한다 | 최악 |
| 500줄 스택 트레이스 | 원인 추정은 되지만 토큰 500~2,000 소모 | 비쌈 |
| `INVALID_ARGUMENT: from_date must be <= to_date` | 인자를 고쳐 재시도 | 좋음 |
| `NOT_FOUND: payment_id 'pay_X' 없음. 최근 30일 밖이면 archive_search를 쓰라` | 다른 도구로 전환 | 최선 |

원칙은 하나다. **오류 메시지에 다음 행동을 담는다** — 무엇이 잘못됐는지(진단)와 무엇을 하면 되는지(처방)를 함께. 스택 트레이스는 사람 로그로 보내고 모델에게는 구조화된 오류를 준다([[09 - 에러 모델 - 상태 코드와 Rich Error]]). gRPC rich error를 설계할 때 하던 고민과 같은 종류이며, 차이는 소비자가 코드가 아니라 확률적 생성기라는 점뿐이다.

**언제 이 접근이 작동하지 않는가.** 오류가 **재시도로 해결 불가능한 종류**일 때, 친절한 오류 메시지는 오히려 모델을 무한 루프에 밀어 넣는다. "권한이 없다"에 "확인하고 다시 시도하라"를 붙이면 모델은 계속 시도한다. 비가역·비복구 오류는 처방 대신 **종료 신호**를 담아야 한다. 오류를 재시도 가능/불가능으로 분류하는 일이 도구 설계의 일부다.

## 9. few-shot 예시 — 정본성이 개수를 이긴다

### 9.1 예시가 실제로 하는 일

예시는 서로 다른 두 일을 한다. **(1) 형식 앵커** — 출력의 모양을 보여 준다. 이 용도는 구조화 출력과 제약 디코딩이 상당 부분 대체했다([[11 - 구조화된 출력 — 스키마·제약 디코딩·파싱 실패의 처리]]). 스키마로 강제할 수 있는 것을 예시로 가르치는 것은 토큰 낭비다. **(2) 판단 기준 전달** — 규칙으로 쓰기 어려운 경계를 사례로 보여 준다. 이건 스키마가 못 하며, **예시의 진짜 가치는 여기 있다.**

이 구분에서 선택 기준이 따라 나온다. 좋은 예시는 전형적인 것이 아니라 **경계에 있는 것**이다. 명백한 환불 요청 5개보다, 환불처럼 보이지만 아닌 것 1개와 애매한데 환불인 것 1개가 낫다. 각 예시에 **왜 그렇게 판단했는지 한 줄**을 붙이면 일반화가 크게 좋아진다.

```typescript
// 예시는 문자열 더미가 아니라 구조를 갖는다.
// rationale 이 있으면 모델이 표면 패턴이 아니라 판단 근거를 모방한다.
type Shot = {
  input: string; output: string;
  rationale: string;      // 왜 이 출력인가 — 한 줄
  covers: string;         // 이 예시가 담당하는 경계. 중복 예시를 걸러내는 데 쓴다
};

const SHOTS: Shot[] = [
  { input: "배송이 3주째 안 와요. 진짜 짜증나네요",
    output: '{"intent":"shipping_delay","refund_requested":false}',
    rationale: "불만 표현이지만 환불을 요구하지 않았다. 감정 강도는 의도가 아니다.",
    covers: "불만 ≠ 환불요청" },
  { input: "이거 그냥 취소해주세요. 돈 다시 넣어주시고요",
    output: '{"intent":"refund_request","refund_requested":true}',
    rationale: "'취소'와 '환불'을 다른 말로 표현했다. 표현이 아니라 요구를 본다.",
    covers: "동의어 표현" },
];
```

### 9.2 개수의 한계효용과 캐시 충돌

형식 앵커 용도라면 예시는 2~3개에서 포화한다 — 형식은 한 번 보면 알 수 있다. 판단 기준 전달이라면 더 많은 예시가 도움이 될 수 있고, 긴 컨텍스트에 수백~수천 개를 넣는 many-shot 접근이 여러 생성·판별 과업에서 few-shot 대비 이득을 보인다는 보고가 있다(Agarwal 등, "Many-Shot In-Context Learning", NeurIPS 2024). 다만 그 이득은 과업 의존적이고 — 같은 논문도 과업에 따라 포화·역전 지점이 다르다고 보고한다 — 늘어난 만큼 3절의 열화와 비용을 낸다.

실무에서 훨씬 자주 문제가 되는 것은 개수가 아니라 **분포 불일치**다. 예시가 실제 입력 분포와 어긋나면 예시는 도움이 아니라 방해자가 된다(3.2절). 6개월 전 트래픽에서 뽑은 예시가 지금 문의와 다른 형태라면 모델은 지금 입력을 예시 쪽으로 억지로 끌어당겨 해석한다. 라우터 드리프트([[07 - 라우팅 — 분류와 전문화된 경로]])와 같은 병이다. 그리고 **동적 예시 선택은 캐시를 깬다**(5.2절) — 절충안은 고정 정본 예시 3~5개를 캐시 경계 앞에, 검색된 예시 1~2개를 경계 뒤에 두는 계층 분리다.

> **흔한 오개념.** "few-shot은 많을수록 좋다." 두 가지가 동시에 틀렸다. 첫째, 예시가 늘면 컨텍스트가 길어지고 3절의 열화가 시작된다. 둘째, 예시는 **암묵적 제약**을 함께 가르친다 — 예시 10개가 모두 짧은 답변이면 모델은 "짧게 답해야 한다"를 배우고, 모두 특정 형식의 ID를 쓰면 그 형식을 일반 규칙으로 받아들인다. 예시를 추가할 때는 "이 예시가 우연히 무엇을 함께 가르치는가"를 물어야 한다.

**언제 few-shot을 아예 빼야 하는가.** 추론 모델을 쓸 때다. 사고 토큰을 쓰는 모델에서는 few-shot이 오히려 성능을 떨어뜨리는 경우가 보고돼 왔고, 모델이 스스로 전개하려던 추론 경로를 예시 패턴이 좁히기 때문이라는 설명이 제시된다. 이 지형 변화는 [[20 - 추론 모델의 시대 — test-time compute가 바꾼 패턴 지형]]에서 다룬다. 지금 기억할 것은 하나 — **모델을 바꾸면 예시의 유효성을 다시 재야 한다.**

## 10. 서브에이전트는 컨텍스트를 나누는 장치다

### 10.1 창을 나누는 것이 진짜 목적

멀티에이전트를 "여러 전문가의 협업"으로 설명하는 서술이 많지만, 컨텍스트 관점에서는 훨씬 단순하고 정직한 설명이 가능하다. **서브에이전트는 탐색의 원문을 부모 컨텍스트 밖에서 태우기 위한 장치다.**

```
격리 없음 — 부모 창에 전부 쌓인다
│ 시스템 │ 도구 │ 검색40K │ 로그28K │ 코드15K │ ...본 과업 │ → 열화·비용·절단

격리 있음 — 원문은 자식 창에서 소각, 결론만 올라온다
│ 부모: 시스템 │ 도구 │ 결론A 800 │ 결론B 600 │ 본 과업 │
           │        └────────────┐
   ┌───────▼────────┐    ┌───────▼────────┐
   │ 자식A: 검색 40K │    │ 자식B: 로그 28K │   ← 이 창은 반환 후 버려진다
   │  → 결론 800     │    │  → 결론 600     │
   └────────────────┘    └────────────────┘
```

교환 관계가 명확하다. **총 토큰은 늘고, 부모 컨텍스트는 줄고, 지연은 병렬화로 숨긴다.** 이 교환이 정당한 조건은 셋 — 탐색 원문이 결론보다 훨씬 크고(압축비 10:1 이상), 자식 과업이 부모의 전체 맥락 없이 명세 가능하며, 결론 형식이 정해져 있어 부모가 그것만으로 판단할 수 있을 때. 하나라도 어긋나면 서브에이전트는 비용만 늘린다.

### 10.2 반환 계약

자식이 무엇을 돌려줄지를 자연어로 두면 종합 단계가 무너진다. 반환을 타입으로 고정한다.

```typescript
// 서브에이전트 반환 계약. 자연어 보고서가 아니라 구조화된 결과.
type SubagentResult = {
  status: "complete" | "partial" | "failed";
  findings: { claim: string; evidence: string; sourceId: string }[];  // 근거 없는 주장 금지
  identifiers: Record<string, string>;   // 부모의 후속 조회를 위해 원문 보존(6.2절)
  notExplored: string[];                 // 안 본 것을 명시 — 부모가 모르면 과신한다
};
```

`notExplored`가 특히 중요하다. "찾지 못했다"와 "찾아보지 않았다"를 구분해 주지 않으면 부모는 전자로 읽고 존재하는 사실을 없는 것으로 확정한다. 이 실패는 종합 단계가 아니라 최종 답변에서만 드러난다.

**언제 작동하지 않는가.** **자식들이 서로의 결정을 알아야 할 때** — 격리의 정의상 자식은 서로를 못 본다. 두 자식이 모순된 전제로 진행하면 부모가 종합할 수 없는 결과 두 개를 받는다([[32 - 멀티에이전트 실패 모드 — 조율 실패의 분류학]]). **결론이 원문 없이 검증 불가능할 때** — 부모가 결론을 믿어야만 하는 구조는 자식의 오류를 증폭한다. `evidence`와 `sourceId`를 강제하는 이유가 이것이다. **부모의 맥락이 자식 과업에 결정적일 때** — 명세를 제대로 쓰려다 부모 컨텍스트를 거의 다 복사하게 된다면 격리의 이득은 사라지고 비용만 남는다. 상세한 판단은 [[27 - 멀티에이전트는 언제 필요한가 — 분업의 이득과 비용]]과 [[09 - 오케스트레이터-워커 — 동적 분해와 종합]]으로 넘긴다.

## 11. 컨텍스트를 관측 가능하게 만들기

컨텍스트는 눈에 안 보이는 자원이라, 관측하지 않으면 잘못된 배분이 몇 달간 조용히 유지된다.

### 11.1 무엇을 남기는가

```sql
-- 턴마다 한 행. 컨텍스트 조립의 결과를 그대로 기록한다.
CREATE TABLE agent_turn_context (
  trace_id TEXT, session_id TEXT, turn_no INT,
  model       TEXT,   -- 버전까지. 모델 교체가 회귀 원인일 때 필요
  prompt_hash TEXT,   -- 시스템+도구 정의의 해시. 프롬프트 버전 추적
  tokens      JSONB,  -- {"system":2400,"tools":5800,"history":18000,...}
  total_input INT, cache_read INT, cache_write INT,   -- 응답 메타데이터에서
  dropped     JSONB,  -- 예산 때문에 버린 블록의 kind와 토큰
  compact_gen INT,    -- 압축 세대 수 (6.4절의 '요약의 요약' 감지)
  outcome     TEXT    -- ok | schema_fail | tool_error | escalated | ...
);
```

여기서 나오는 네 지표가 대시보드를 이룬다.

| 지표 | 정의 | 이상 신호 | 해석 |
|---|---|---|---|
| 절단율 | `dropped ≠ {}` 인 턴 비율 | 2% 초과 | 예산 배분이 실제 수요와 어긋남 |
| 캐시 적중률 | `cache_read / total_input` | 60% 미만 | 접두사에 변동 요소 혼입 또는 압축 과다 |
| 점유 분포 | `tokens` 항목별 백분위 | 한 항목이 p95에서 50% 초과 | 그 항목에 상한이 없음 |
| 압축 세대 | `compact_gen` 분포 | 3 이상 꼬리가 두꺼움 | 과업이 너무 큼 → 분해 필요 |

### 11.2 회귀를 잡는 법

컨텍스트 회귀는 배포 시점이 아니라 **분포가 이동할 때** 드러난다. 그래서 배포 게이트에 넣을 것은 정확도만이 아니다.

```bash
# 배포 전 컨텍스트 회귀 검사. 골든 트레이스로 조립기만 돌린다(모델 호출 없이).
# 조립기가 순수 함수이기 때문에 가능한 검사다(1.1절).
$ agentctl context-diff --baseline v1.42 --candidate HEAD --traces golden/*.jsonl

  system        2,400 → 3,180  (+780)   ⚠ 접두사 증가: 캐시 쓰기 비용 상승
  prefix_hash   a3f1... → 9c04...       ⚠ 접두사 변경: 전체 캐시 무효화 1회 발생
  truncation      0.4% → 3.1%           ✗ 절단율 임계 초과 (2.0%)
  identifiers   보존율 100% → 97.2%      ✗ 압축이 식별자를 잃고 있다
```

`identifiers 보존율`이 조립기 수준에서 검사 가능하다는 점이 6.2절 구조화 상태의 배당금이다. 자유 텍스트 요약이었다면 이 검사 자체가 존재할 수 없다.

**언제 계측이 오도하는가.** 30K 토큰이 균질한 문서 한 편인 세션과, 30K가 서로 모순되는 도구 출력 40개로 이뤄진 세션은 같은 숫자지만 난이도가 전혀 다르다. 토큰 수는 **품질의 대리 지표일 뿐**이므로 트레이스를 사람이 읽는 습관이 필요하고, 그것 없이 대시보드만 보는 팀은 "지표는 다 초록인데 답이 이상하다"에 도달한다([[38 - 평가 — 에이전트를 측정하는 법]]).

---

이 장의 처방을 도입 비용이 낮은 순으로 압축하면 이렇게 된다. 조립을 **명명된 순수 함수**로 분리한다 → 블록별 토큰을 정확히 세고 로깅한다 → 도구 출력에 상한을 걸고 잘랐음을 모델에게 알린다 → 접두사를 안정성 순으로 정렬한다 → 시스템 프롬프트의 조건 분기가 셋을 넘으면 코드로 내린다 → 압축 산출물을 타입으로 정의하고 식별자 보존을 검증한다 → 큰 데이터는 포인터로 바꾼다 → 자기 도메인 데이터로 열화 곡선을 그려 운용 상한을 정한다. 이 목록이 프롬프트 문구에 대한 조언을 하나도 담고 있지 않다는 점이 이 장의 요지다.

## 핵심 요약

- **모델 API는 무상태이므로 컨텍스트는 매 턴 새로 조립되는 자료구조다.** 우리가 설계하는 것은 문자열이 아니라 조립기라는 함수이며, 이 함수를 순수하게 유지하면 테스트·계측·회귀 검사가 전부 가능해지고 f-string 연결로 두면 셋 다 불가능하다. 그리고 매 턴 누적 이력을 다시 보내므로 세션 전체의 입력 토큰은 $cT + \sum_t \sum_{i<t} l_i$ 형태로 자란다 — 캐싱과 압축은 최적화가 아니라 구조적 요구다.

- **컨텍스트 창이 커져도 "다 넣기"는 여전히 틀렸다.** 이유는 비용·지연·정확도 셋이고 셋째가 가장 중요하다. 위치에 따른 성능 차이(Liu 등의 "Lost in the Middle", 2023)와 입력 길이에 따른 열화(Chroma Research의 "Context Rot" 보고서, 2025)가 반복 관측된다. 방해자는 주의를 희석하는 데 그치지 않고 오답의 재료로 쓰인다. 유효 컨텍스트에 일반 상수는 없으므로 자기 도메인 데이터로 열화 곡선을 그려야 하며, 흔히 정확도보다 **지시 준수**가 먼저 무너진다.

- **시스템 프롬프트의 고도가 낮으면 부서지고 높으면 흔들린다.** 조건 분기를 나열한 저고도 프롬프트는 미열거 입력에서 붕괴하고 조합 폭발을 겪는다 — 결정론적 매핑은 코드나 도구로 내려야 한다. 역할 형용사만 나열한 고고도 프롬프트는 행동이 분산되고 평가할 수 없다. 목표는 절차·판단 기준·금지·기권이 명시된 중고도이며, 고도는 모델 능력에 상대적이라 모델을 바꾸면 다시 조정해야 한다.

- **캐시가 배치 순서를 강제한다.** 인과 어텐션에서 앞부분 KV는 뒤에 무엇이 오든 불변이므로, 접두사가 정확히 일치할 때만 재사용된다. 안정성 순 배치(시스템 → 도구 → 예시 → 상태 → 이력 → 현재 지시)는 미학이 아니라 이 성질의 귀결이다. 시스템 프롬프트의 타임스탬프 한 줄이 캐시 전체를 무효화한다.

- **압축은 손실 압축이며 세 가지 비용이 있다.** 요약 대상을 다시 읽는 토큰 비용, 접두사를 무효화하는 캐시 비용, 되돌릴 수 없는 정보 비용. 그래서 압축은 자주 조금씩이 아니라 드물게 크게, 아무 데서나가 아니라 의미적 경계에서 해야 한다. 그리고 진짜 설계는 요약 품질이 아니라 **보존 목록**이다 — 목표·제약·결정과 근거·미해결 항목·**식별자 원문**·배제된 가설을 반드시 남긴다. 타입 있는 상태 객체로 만들면 보존을 검증할 수 있고, 식별자가 요약에 녹아 사라진 뒤 모델이 형태만 그럴듯한 가짜를 지어내는 최악의 실패를 막을 수 있다.

- **큰 데이터는 컨텍스트에 넣는 대신 포인터로 바꾼다.** 요약·목록·핸들만 주고 상세는 도구로 읽게 하는 점진적 공개는 토큰을 아낄 뿐 아니라 모델의 탐색 경로를 관측 가능하게 만든다. 다만 요약 한 줄의 품질이 병목이고, 왕복 지연이 누적되며, 집계처럼 전체를 봐야 하는 과업에는 맞지 않는다 — 그런 과업은 계산을 코드로 내리는 것이 정답이다.

- **few-shot에서 중요한 것은 개수가 아니라 경계와 정본성이다.** 형식 앵커 용도는 스키마가 대체했고, 남은 가치는 규칙으로 쓰기 어려운 판단 경계를 사례로 전달하는 것이다. 예시는 의도하지 않은 규칙까지 함께 가르치며 그 부작용은 개수에 비례한다. 동적 예시 선택은 캐시를 깨므로 고정 정본과 계층을 나눈다.

- **서브에이전트는 협업 장치이기 이전에 컨텍스트 격리 장치다.** 탐색 원문을 자식 창에서 태우고 결론만 올린다. 총 토큰은 늘고 부모 창은 줄며 지연은 병렬화로 숨긴다. 이 교환은 압축비가 크고, 자식 과업이 부모 맥락 없이 명세 가능하고, 결론 형식이 정해져 있을 때만 정당하다.

- **관측하지 않으면 컨텍스트 설계는 검증되지 않는다.** 절단율·캐시 적중률·항목별 점유 분포·압축 세대가 최소 집합이며, 조립기가 순수 함수이므로 모델 호출 없이 배포 전에 회귀를 검사할 수 있다. 다만 토큰 수는 품질의 대리 지표일 뿐이라 트레이스를 사람이 읽는 습관을 대체하지 못한다.
