앞의 두 장에서는 제어 흐름을 **직렬로 나누는 방법**과 **분기시키는 방법**을 살펴봤다. [[06 - 프롬프트 체이닝 — 분해와 순차적 정제]]는 한 번에 잘 처리되지 않는 일을 순서 있는 단계로 나눠 단계마다 컨텍스트를 좁히는 패턴이었다. [[07 - 라우팅 — 분류와 전문화된 경로]]는 입력의 종류에 따라 경로 하나를 골라, 그 경로에 전문화된 처리를 붙이는 패턴이었다.

두 패턴에는 공통점이 있다. 어느 순간에도 **활성화된 경로가 하나**라는 점이다. 체이닝은 한 번에 한 단계를, 라우팅은 한 번에 한 분기를 실행한다. 그래서 두 패턴은 비용과 지연을 계산하기가 단순하다. 경로 위에 있는 단계들의 비용을 더하기만 하면 된다.

이 장에서는 그 가정을 깬다. 여러 LLM 호출이 **동시에** 실행될 때 무엇이 달라질까? 겉으로 보이는 답은 "빨라진다"이지만, 이 답은 세 가지 이유로 거의 항상 불완전하다.

- 병렬화라는 이름 아래에 서로 다른 문제를 푸는 패턴이 적어도 두 개 섞여 있다. 입력을 나누는 **섹셔닝**(sectioning)과, 같은 입력에 대해 시행 횟수를 늘리는 **투표**(voting)이다. 두 패턴은 병합 의미론이 근본적으로 다르고, 실패 모드도 겹치지 않는다.
- 병렬화로 얻은 이득은 병합 단계의 비용으로 상쇄되고, 그 비용은 가지 수에 비례해 커진다. 그래서 폭을 한없이 넓히면 오히려 느려진다.
- 동시성은 공짜 자원이 아니다. 프로바이더의 속도 제한, 토큰 예산, 그리고 무엇보다 **꼬리 지연**이 병렬화의 실질적인 상한을 정한다.

이 장에서 말하는 병렬화는 **분해 방식이 고정된** 병렬화다. 몇 갈래로 나눌지, 각 갈래에 무엇을 줄지가 코드에 정해져 있거나 입력의 구조에서 기계적으로 유도된다. 모델이 **실행 시점에** 하위 과업을 만들어 내는 구조는 [[09 - 오케스트레이터-워커 — 동적 분해와 종합]]에서 다룬다.

여러 에이전트가 서로의 주장을 읽고 반박하면서 수렴하는 구조는 [[30 - 토론과 합의 — multi-agent debate·투표·심판]]에서 다룬다. 판정자를 어떻게 만들고 그 신뢰도를 어떻게 측정하는지(루브릭 설계, 인간 라벨과의 상관, 판정자 메타평가)는 [[38 - 평가 — 에이전트를 측정하는 법]]에서 설명한다. 이 장에서는 이 세 구조의 **아래층**에 있는 실행 구조, 즉 "여러 호출을 동시에 실행하고 결과를 하나로 합치는 일"의 동작 원리를 다룬다.

한 가지를 덧붙인다. 이 장의 논의는 대부분 **분산 시스템에서 이미 알려진 내용을 다시 확인하는 것**이다. scatter-gather, MapReduce, 정족수 읽기, 헤지 요청, 백프레셔에는 모두 이미 이름이 있다. 새로운 점은 하나뿐이지만, 그 하나가 결정적이다. **가지 하나하나가 확률적이고, 병합해야 할 대상이 바이트가 아니라 의미라는 점이다.**

분산 시스템의 scatter-gather는 각 샤드가 자기 영역에 대해 정확한 답을 준다고 가정하고, 병합은 정렬이나 합집합 같은 순수 함수로 처리한다. 반면 LLM 팬아웃에서는 각 가지가 틀릴 수 있다. 두 가지가 같은 내용을 다른 말로 표현하기도 하고, 서로 모순되는 내용을 자신 있게 말하기도 한다. 그래서 이 장의 절반은 병합에 관한 이야기다.

## 1. 병렬화는 하나의 패턴이 아니다: 섹셔닝과 투표는 다른 문제를 푼다

설계 회의에서 "병렬화"라는 단어가 나오면, 사람들이 떠올리는 그림은 적어도 세 가지다. 그리고 세 가지는 목적도, 병합 방식도, 실패 방식도 다르다. 이 구분을 정확히 세워 두지 않으면 이 장의 나머지 내용이 뒤섞인다.

### 1.1 세 가지 형태: 무엇이 다른가

**섹셔닝**은 입력을 나눈다. 200페이지 계약서를 20페이지씩 10조각으로 나누고, 조각마다 "이 조각에서 지불 조건에 해당하는 조항을 뽑아라"를 실행한다. 각 가지는 **서로 다른 입력**을 받아 **서로 다른 부분 답**을 낸다. 병합은 부분 답을 모아 전체 답을 구성하는 일이다. 전형적인 map-reduce이다.

섹셔닝의 이득은 두 가지다. 하나는 동시에 실행하므로 줄어드는 지연이고, 다른 하나가 사실 더 중요하다. **각 호출의 컨텍스트가 좁아져 정확도가 오른다.** 200페이지를 한 번에 넣고 "다 뽑아라"라고 하면 중간 부분이 조용히 누락되지만, 20페이지짜리 10개는 그렇지 않다. 이것은 지연 최적화가 아니라 [[05 - 컨텍스트 엔지니어링 — 프롬프트를 넘어 컨텍스트를 조립하기]]의 문제다.

**투표**는 입력을 나누지 않는다. 같은 입력을 $n$번 실행해 $n$개의 후보 답을 얻고, 그중 하나를 고르거나 합의를 만든다. 각 가지는 **같은 입력**을 받아 **같은 질문에 대한 경쟁하는 답**을 낸다. 병합은 선택이다. 다수결, 검증자 통과, 판정자 선택이 여기에 해당한다.

투표의 이득은 지연이 아니라 **정확도**다. 꼬리가 늘어나므로 지연은 오히려 나빠질 수도 있다. 투표는 "한 번 실행해서는 틀릴 확률이 무시하지 못할 만큼 크다"는 진단에 대한 처방이다.

**팬아웃**은 애매한 중간 지대이지만, 실무에서는 가장 흔하다. 같은 입력에 대해 **서로 다른 관점, 도구, 자원**으로 동시에 질의하고 그 결과를 합친다. 예를 들어 사용자 질문 하나를 검색 질의 세 개로 확장해 동시에 보낸다.

문서 하나에서 "요약", "위험 조항", "누락된 필수 항목"을 각각 다른 프롬프트로 동시에 뽑는 것도 팬아웃이다. 입력은 같지만 산출물은 경쟁 관계가 아니라 **상보적**이다. 따라서 병합은 선택이 아니라 통합이다.

```
섹셔닝 (입력 분할, 상보적 산출)
  input ──split──┬─► f(s1) ──┐
                 ├─► f(s2) ──┤
                 ├─► f(s3) ──┼─► merge ─► output
                 └─► f(s4) ──┘
   전제: s_i 끼리 독립. 병합 = 합집합/연결/집계

투표 (입력 동일, 경쟁적 산출)
  input ─────────┬─► f(x; seed1) ─┐
                 ├─► f(x; seed2) ─┤
                 ├─► f(x; seed3) ─┼─► select ─► output
                 └─► f(x; seed4) ─┘
   전제: 답이 이산·유일. 병합 = 최빈값/검증자/판정자

팬아웃 (입력 동일, 상보적 산출)
  input ─────────┬─► g1(x) ──┐     g1..g4 는 서로 다른 렌즈
                 ├─► g2(x) ──┤     (다른 프롬프트/도구/자원)
                 ├─► g3(x) ──┼─► synthesize ─► output
                 └─► g4(x) ──┘
   전제: 렌즈가 겹치지 않게 정의됨. 병합 = 종합/조립
```

| | 섹셔닝 | 투표 | 팬아웃 |
|---|---|---|---|
| 각 가지의 입력 | 다름(분할) | 같음 | 같음 |
| 각 가지의 산출 | 부분 답(상보) | 후보 답(경쟁) | 측면 답(상보) |
| 주 이득 | 지연 + 컨텍스트 축소로 인한 정확도 | 정확도(분산 축소) | 커버리지 |
| 병합 연산 | 합집합·연결·집계 | 최빈값·검증·선택 | 종합·조립 |
| 가지 하나 실패 시 | 그 부분이 **빈다** | 표본이 하나 줄 뿐 | 그 측면이 **빈다** |
| 대표 실패 | 조각 간 모순·용어 드리프트 | 오류 상관, 최빈답이 오답 | 렌즈 중복·공백 |
| 늘리면 | 조각이 잘게 쪼개져 문맥 상실 | 한계이득 체감 | 종합기 컨텍스트 초과 |

실무에서 가장 큰 차이를 만드는 것은 표의 끝에서 두 번째 행이다. **투표는 부분 실패에 강하고, 섹셔닝과 팬아웃은 약하다.** 표본 5개 중 2개가 타임아웃되더라도 남은 3개로 다수결을 하면 품질이 조금 나빠질 뿐이다.

반면 10조각 중 2조각이 타임아웃되면 계약서의 20%를 읽지 못한 것이고, 병합 결과만 봐서는 그 사실을 알 수 없다. 이 비대칭이 뒤에서 다룰 부분 실패 정책(8.3절)의 근거가 된다.

> [!info] 역사 메모
> 세 형태 가운데 섹셔닝은 전혀 새로운 것이 아니다. Dean과 Ghemawat의 MapReduce(OSDI 2004)가 정확히 같은 구조다. 입력을 분할해 map을 병렬로 실행하고, 키로 묶어 reduce한다. MapReduce가 감춰 두었던 어려움도 그대로 다시 나타난다. 스트래글러(느린 워커) 처리, 부분 실패 재시도, 그리고 reduce가 결합적이어야 combiner를 끼워 넣을 수 있다는 제약이다.
>
> 다른 점은 map 함수가 순수하지 않고 확률적이라는 것 하나뿐이다. 그러나 그 하나 때문에 재시도 의미론과 병합 대수가 전부 흔들린다([[42 - 일괄 처리와 분산 파일시스템 (Batch Processing & Distributed Filesystems) - MapReduce·HDFS]]).

### 1.2 이 구분이 코드에 드러나야 하는 이유

세 형태를 헬퍼 하나로 묶고 싶은 마음이 들기 쉽다. `parallel(tasks) -> results` 하나면 되지 않을까? 실제로는 안 된다. **부분 실패가 일어났을 때 무엇이 옳은 동작인지**가 형태마다 다르기 때문이다.

```typescript
// 안티패턴: 세 형태를 하나의 시그니처로 뭉갠 것.
// 반환 타입이 results[] 하나뿐이라, 호출자는 "몇 개가 실패했는지"를 모른 채 병합한다.
async function parallel<T>(tasks: Array<() => Promise<T>>): Promise<T[]> {
  return Promise.all(tasks.map((t) => t()));   // 하나 실패하면 전부 버림 — 투표에선 과하고
}                                              // allSettled 로 바꾸면 섹셔닝에서 조용히 구멍이 남는다

// 형태별로 결과 타입이 다르다는 사실을 타입으로 드러낸다.
type Sectioned<T> = {
  kind: "sectioned";
  parts: Array<{ sectionId: string; value: T } | { sectionId: string; error: Error }>;
  // 섹셔닝은 '어느 구간이 비었는가'가 결과의 일부다. 커버리지를 값으로 들고 다닌다.
  coverage: { total: number; ok: number; missingSectionIds: string[] };
};

type Voted<T> = {
  kind: "voted";
  candidates: T[];               // 실패한 시행은 그냥 없는 것으로 둔다 — 표본이 줄 뿐
  attempted: number;             // 단, 몇 번 시도했는지는 남긴다(합의도 계산의 분모)
  agreement: number;             // 0..1. 이 값이 낮으면 결과를 신뢰하지 말라는 신호
};

type FannedOut<T> = {
  kind: "fanned_out";
  lenses: Record<string, T | { error: Error }>;
  // 팬아웃은 렌즈마다 중요도가 다르다. 빠져도 되는 렌즈와 빠지면 안 되는 렌즈를 구분한다.
  requiredLensesMissing: string[];
};
```

타입을 이렇게 나눠 두면 병합기는 자신이 무엇을 다루는지 알 수 있다. 무엇보다 **"결과가 불완전하다"는 사실이 값으로 전달된다.** 이것은 스타일의 문제가 아니다. 병렬화에서 가장 흔한 실무 사고가 "일부 가지가 실패했는데 최종 산출물이 그럴듯해서 아무도 몰랐다"는 유형이기 때문이다.

계약서 10조각 중 3조각이 429로 실패했는데도, 병합 결과는 여전히 "지불 조건 7건을 찾았습니다"라고 말한다. 7건이 전부인지 아닌지를 알 수 있는 방법은 커버리지를 값으로 들고 다니는 것뿐이다.

> [!warning] 흔한 오해
> "병렬화는 실행 전략일 뿐이므로 결과의 의미는 직렬 실행과 같다." 그렇지 않다. 이 말은 순수 함수를 병렬로 실행할 때만 참이고, LLM 호출은 순수 함수가 아니다. 섹셔닝은 각 호출이 보는 컨텍스트를 바꾸므로 **답의 분포 자체가 달라진다**. 200페이지를 한 번에 읽은 모델과 20페이지만 읽은 모델은 같은 질문에 다른 답을 한다.
>
> 즉 병렬화는 최적화가 아니라 **다른 프로그램**이다. 그래서 "일단 직렬로 만들고 나중에 병렬로 바꾸자"는 계획은 성능 튜닝 일정이 아니라 재설계 일정이며, 회귀 테스트 세트를 새로 만들어야 하는 변경이다.

### 1.3 섞어 쓰기: 합성할 수 있지만 비용은 곱해진다

세 형태는 서로 합성할 수 있다. 실무에서 자주 보는 조합은 **섹셔닝 안의 투표**다. 계약서 10조각 각각을 3번씩 실행하고 다수결로 조항을 확정한 뒤 병합하는 방식이다. 이렇게 하면 호출 수는 $10 \times 3 = 30$이 된다.

반대 방향도 있다. **투표 안의 섹셔닝**은 전체 파이프라인을 통째로 3번 실행해 최종 산출물 3개를 비교하는 방식이다. 호출 수는 같지만 병합하는 지점이 다르다.

어느 쪽이 나은지는 **오류가 어디서 발생하는지**에 달려 있다. 한 조항을 잘못 읽는 것처럼 오류가 조각 단위로 국소적이라면 조각 안에서 투표하는 것이 맞다. 전체 문서의 성격을 오판해 전부 다르게 해석하는 것처럼 오류가 전역적이라면, 파이프라인 전체를 반복해야 잡힌다.

실무에서는 대부분 전자이므로 조각 안 투표가 기본값이다. 하지만 이 판단은 직관으로 정하지 말고, 실제 오류 사례를 몇 건 읽어 본 뒤에 내려야 한다.

$$
N_{\text{calls}} = \underbrace{n_{\text{sections}}}_{\text{폭}} \times \underbrace{k_{\text{votes}}}_{\text{깊이}} \times \underbrace{r_{\text{lenses}}}_{\text{렌즈}} + \underbrace{m}_{\text{병합·종합}}
$$

곱셈이라는 점이 중요하다. 각 인자를 "겨우 3배"라고 생각하며 따로따로 정하면 $3\times3\times3=27$배가 된다. 팬아웃 예산은 각 축이 아니라 **곱에** 걸어야 한다(8.1절).

## 2. 지연은 최댓값, 비용은 합: 병렬화의 비용 계산과 최적 폭

병렬화를 논의할 때 가장 먼저 세워야 할 것은 비용 계산이다. 이 계산은 단순하지만, 단순한 형태 그대로 쓰면 거의 항상 낙관적인 쪽으로 틀린다.

### 2.1 기본 항등식과 그 식이 감추는 것

$n$개의 가지를 동시에 실행할 때 지연과 비용은 다음과 같다.

$$
T_{\text{total}} = T_{\text{split}} + \max_{i \in [n]} T_i + T_{\text{merge}}, \qquad C_{\text{total}} = C_{\text{split}} + \sum_{i \in [n]} C_i + C_{\text{merge}}
$$

지연은 최댓값이고, 비용은 합이다. 여기까지는 누구나 안다. 문제는 이 식의 세 항이 모두 $n$에 의존한다는 사실이 가려져 있다는 점이다.

**$\sum C_i$는 원래 작업량보다 크다.** 섹셔닝에서 각 가지는 자기 조각만 받지 않고, 공유 서문(시스템 프롬프트, 용어집, 출력 스키마, few-shot 예시)도 함께 받는다. 공유 서문의 토큰 수를 $c_0$, 조각마다 고유한 토큰 수를 $c_u$라고 하면 입력 비용은 $n c_0 + \sum c_u$이다. 단일 호출보다 $(n-1)c_0$만큼 늘어나는 것이다.

서문이 길고 조각이 짧으면 이 오버헤드가 비용의 대부분을 차지한다. 프롬프트 캐싱이 바로 이 항을 줄이는 장치다. 캐시 적중을 전제로 팬아웃 폭을 정하느냐에 따라 비용이 몇 배 차이 난다([[40 - 비용과 지연 — 캐싱·모델 라우팅·예산 관리]]).

**$T_{\text{merge}}$는 $n$에 비례해 커진다.** 병합기는 $n$개의 결과를 모두 읽어야 한다. 결과 하나가 평균 $b$ 토큰이면 병합 입력은 $nb$이다. 입력 토큰 수에 대해 지연이 대략 선형이라면 $T_{\text{merge}} \approx \beta n$이 된다. 병렬화의 이득을 깎아 먹는 주된 원인이 이 항이다.

**$\max_i T_i$는 평균이 아니라 꼬리에 좌우된다.** 이 내용은 2.3절에서 따로 다룬다.

### 2.2 최적 팬아웃 폭이 존재한다

이제 세 항을 모두 넣고 최적화해 보자. 전체 작업량이 고정되어 있고, $n$조각으로 나누면 조각당 작업이 $1/n$로 줄어든다고 하자. 조각 처리 지연이 조각 크기에 대략 선형이라면 $\max_i T_i \approx B/n$이다(스트래글러를 무시한 낙관적 근사). 병합은 $\beta n$이다. 여기에 고정 비용 $A$(분할, 네트워크 왕복, 스케줄링)를 더하면 다음과 같다.

$$
T(n) = A + \frac{B}{n} + \beta n
$$

$$
\frac{dT}{dn} = -\frac{B}{n^2} + \beta = 0 \quad \Longrightarrow \quad n^{*} = \sqrt{\frac{B}{\beta}}, \qquad T(n^{*}) = A + 2\sqrt{B\beta}
$$

**여기서 결론이 두 가지 나온다.** 첫째, 최적 폭은 유한하며 $\sqrt{B/\beta}$이다. 폭을 한없이 넓히면 병합 비용이 이득을 모두 없앤다. 둘째, 최선의 지연이 $A + 2\sqrt{B\beta}$이므로 **아무리 병렬화해도 $2\sqrt{B\beta}$ 아래로는 내려가지 못한다.**

이는 병합기를 싸고 빠르게 만드는 것($\beta$를 줄이는 것)이 가지 수를 늘리는 것보다 이득이 큰 구간이 넓다는 뜻이다. 4절에서 "병합기는 가능하면 코드로 작성하라"고 주장하는 정량적 근거가 여기에 있다.

이 형태는 Amdahl의 법칙보다 나쁘다. Amdahl은 직렬 구간의 비율이 **고정**되어 있다고 본다. $S(n) = 1/((1-P) + P/n)$이므로 $n \to \infty$에서 $1/(1-P)$로 수렴한다. 반면 우리 식에서는 직렬 구간이 $n$에 비례해 **커진다**.

이 현상은 Gunther의 보편 확장성 법칙(Universal Scalability Law)에서 일관성 유지 비용(coherency) 항이 만드는 모양과 같다. 확장성 곡선이 평평해지는 데 그치지 않고, 정점을 지나 **내려간다**([[03 - 성능의 본질 (Performance Fundamentals) - 꼬리 지연·백분위수·큐잉·확장성 법칙]]).

> [!warning] 흔한 오해
> "병렬화하면 항상 빨라진다." 위 식이 반례다. 병합기가 LLM이고 각 결과가 길어서 $\beta$가 크면, 최적 $n^{*}$는 2~4 정도로 작아진다. 그보다 넓히면 오히려 느려진다. 실제로 LLM 병합기는 입력이 길어질수록 출력도 길어지는 경향이 있어서, $\beta$가 선형보다 나쁠 수 있다.
>
> 게다가 이 모델에는 아직 속도 제한이 들어 있지 않다. 8절에서 속도 제한을 넣으면, $n$이 임계치를 넘는 순간 큐잉이 시작되어 $\max_i T_i$가 $B/n$을 따르지 않고 다시 증가한다.

### 2.3 꼬리가 지배한다: $0.99^n$의 산수

$n$개 가지의 지연이 독립적으로 같은 분포 $F$를 따른다고 하면, 팬아웃 전체 지연의 분포는 다음과 같다.

$$
P\!\left[\max_i T_i \le t\right] = F(t)^n
$$

개별 호출의 p99 지연을 $L$이라고 하자. $F(L) = 0.99$이므로 모든 가지가 $L$ 안에 끝날 확률은 $0.99^n$이다.

| $n$ | 모든 가지가 개별 p99 안에 끝날 확률 | 팬아웃 p99를 맞추려면 각 가지에 요구되는 분위수 |
|---|---|---|
| 2 | 98.0% | p99.5 |
| 4 | 96.1% | p99.75 |
| 8 | 92.3% | p99.875 |
| 16 | 85.1% | p99.94 |
| 32 | 72.5% | p99.97 |

핵심은 오른쪽 열이다. 팬아웃 전체의 p99를 지키려면 각 가지의 $1 - 0.01/n$ 분위수를 봐야 한다. $n=16$이면 개별 호출의 p99.94 지연이 전체의 p99가 된다.

LLM 프로바이더의 지연 분포는 구조적으로 꼬리가 두꺼울 수밖에 없다. 응답 시간은 출력 토큰 수에 대략 비례하는데, 그 수가 답마다 크게 다르다. 여기에 프로바이더 측의 큐잉과 내부 재시도가 더해진다. 꼬리가 얼마나 두꺼운지는 프로바이더, 모델, 시간대마다 다르므로 여기서 배수를 인용하지는 않겠다.

요점은 **p99와 p99.9의 간격을 직접 재 보지 않고 팬아웃 폭을 정해서는 안 된다**는 것이다. 그 간격이 벌어져 있을수록 오른쪽 열의 대가가 커진다. 그러면 "8개를 병렬로 실행해 8배 빨라졌다"는 계산은 평균에서만 맞고, p99에서는 이득이 대부분 사라진다.

이것은 Dean과 Barroso가 "The Tail at Scale"(CACM, 2013)에서 정리한 문제와 똑같다. 그들의 처방도 그대로 가져올 수 있다.

- **헤지 요청**(hedged request): 일정 시간(예: p95) 안에 응답이 오지 않으면 같은 요청을 하나 더 보내고, 먼저 도착한 응답을 쓴다.
- **묶인 요청**(tied request): 두 곳에 동시에 보내고, 하나가 시작되면 다른 하나를 취소한다.
- **마이크로 파티셔닝**: 가지를 워커 수보다 잘게 나눠서, 느린 워커가 맡은 작업을 다른 워커가 가져가게 한다.

다만 헤지 요청을 LLM에 그대로 적용하려면 원 논문의 전제를 확인해야 한다. 헤지가 이득인 것은 지연 꼬리가 **요청 고유의 성질이 아니라 일시적인 혼잡**에서 올 때다. 스토리지 읽기라면 이 전제가 대체로 맞다. 같은 키를 다시 읽는 일의 난이도는 똑같으므로, 느린 이유는 그 노드의 상태에 있다.

LLM 호출은 다르다. 응답 시간의 큰 부분이 **출력 토큰 수**에 좌우된다. 이는 그 요청이 어떤 답을 만들지에 달린, 요청에 내재된 성질이다. 따라서 복제본을 띄워도 프롬프트가 같다면 비슷하게 길어질 가능성이 높다. 즉 **LLM의 지연 꼬리에는 혼잡 성분과 길이 성분이 섞여 있고, 헤지로 줄일 수 있는 것은 혼잡 성분뿐이다.**

실무에서 얻을 수 있는 시사점은 두 가지다. 먼저 헤지를 켜기 전에 **꼬리를 성분별로 나눠 봐야 한다**. 느린 요청들의 출력 토큰 수가 유난히 길다면 꼬리는 길이 성분이 지배하고 있는 것이다. 이때 헤지는 비용만 두 배로 들고 지연은 줄이지 못한다.

그 경우의 처방은 헤지가 아니라 `max_tokens` 상한, 출력 스키마 축소, 또는 긴 답이 예상되는 요청의 분리다. 반대로 같은 프롬프트로 재시도한 요청이 눈에 띄게 빨리 끝난다면 혼잡 성분이 크다는 뜻이고, 이때는 헤지가 효과가 있다.

여기에 두 가지 조건이 더 붙는다.

- 요청에 부작용이 없어야 한다. 도구 호출이 포함된 턴을 헤지하면 같은 도구가 두 번 실행된다(10절).
- 헤지된 요청은 비용이 두 배가 되므로, 헤지 임계를 p95 이상으로 잡아 헤지 비율을 5% 안팎으로 묶는다(임계를 p95로 두면 정의상 약 5%가 헤지된다).

```python
# 헤지 요청: 임계 시간 안에 안 오면 복제본을 하나 더 띄우고 먼저 오는 쪽을 쓴다.
# 전제: call 은 부작용이 없어야 한다. 도구를 실행하는 턴에는 절대 쓰지 않는다.
import asyncio
from typing import Awaitable, Callable, TypeVar

T = TypeVar("T")


async def hedged(
    call: Callable[[], Awaitable[T]],
    hedge_after: float,       # 보통 관측된 p95. 낮추면 비용이 선형으로 는다.
    hard_timeout: float,
) -> T:
    first = asyncio.create_task(call())
    done, _ = await asyncio.wait({first}, timeout=hedge_after)
    if done:
        return first.result()

    # 여기 도달했다는 것 자체가 "이 요청은 꼬리에 있다"는 관측이다.
    # 복제본을 띄우되 원본을 죽이지 않는다 — 원본이 거의 다 왔을 수도 있으므로.
    second = asyncio.create_task(call())
    try:
        done, pending = await asyncio.wait(
            {first, second},
            timeout=hard_timeout - hedge_after,
            return_when=asyncio.FIRST_COMPLETED,
        )
        if not done:
            raise TimeoutError("both hedged attempts timed out")
        for p in pending:
            p.cancel()        # 진 쪽은 반드시 취소한다. 안 그러면 토큰을 계속 태운다.
        return next(iter(done)).result()
    finally:
        for t in (first, second):
            if not t.done():
                t.cancel()
```

> [!note] 실무 규칙
> 팬아웃을 설계할 때 지연 목표는 **평균이 아니라 $\max$의 분위수**로 세운다. 대시보드에 "가지별 p99"만 있고 "팬아웃 전체 p99"가 없으면 지연 회귀를 절대 잡을 수 없다. 그리고 가지 수를 늘리는 변경은 지연 SLO에 영향을 주므로 릴리스 노트에 적어야 한다([[41 - 배포와 운영 — 버저닝·회귀·점진적 롤아웃]]).

### 2.4 처리량과 지연을 혼동하지 않기

병렬화가 착시를 일으키는 가장 흔한 경우는 다음과 같다. **시스템이 이미 속도 제한이나 동시성 상한에 걸려 있다면, 요청 하나를 병렬화해도 처리량은 늘지 않고 지연만 재배치된다.**

분당 토큰 한도가 $R$이고 요청 하나가 평균 $w$ 토큰을 쓴다면, 시스템 처리량은 $R/w$로 고정된다. 한 요청을 8갈래로 나누면 그 요청의 응답 시간은 짧아지지만, 같은 시간 동안 한도를 8배로 소모하므로 **다른 요청들이 대기**하게 된다.

리틀의 법칙 $L = \lambda W$로 보면 재고 $L$은 그대로이고 $W$의 분포만 바뀐다. 부하가 낮을 때는 순수한 이득이지만, 부하가 높을 때는 제로섬이고 심하면 손해다. 팬아웃이 큐를 채워 큐잉 지연이 생기면 전체가 나빠지기 때문이다.

```
저부하 (한도 여유 있음)              고부하 (한도 포화)
  직렬:  [====================]        직렬:  [====][====][====][====]   4건 처리
  병렬:  [=====]                       병렬:  [=]queue[=]queue[=]queue    4건 처리
         ↑ 순수 이득                          ↑ 같은 처리량, 지연 분산만 악화
```

> [!note] 실무 규칙
> 병렬화를 지연 개선책으로 도입하기 전에, **현재 부하에서 프로바이더 한도까지 여유가 얼마나 있는지**를 먼저 잰다. 여유가 30% 미만이면 병렬화는 지연을 개선하지 못하고 꼬리만 두껍게 만든다. 이 경우의 올바른 처방은 병렬화가 아니라 캐싱, 모델 다운그레이드, 또는 한도 증설이다.

## 3. 섹셔닝의 전제는 독립성이고, 그 전제는 대개 거짓이다

섹셔닝은 세 형태 중 개념적으로 가장 단순해 보이지만, 실패 사례는 가장 많다. 이유는 하나다. **조각들이 서로 독립이라는 전제를 검증하지 않고 나누기 때문이다.**

### 3.1 독립성의 정확한 정의

여기서 필요한 독립성은 통계적 독립이 아니라 **결정 의존성이 없는 것**이다. 정확히 말하면 다음과 같다.

> 조각 $s_i$에 대한 올바른 산출 $y_i$가 다른 조각의 **내용**에도, 다른 조각에 대해 내려진 **결정**에도 의존하지 않을 때 조각들은 독립이다.

두 조건이 다르다는 점에 주목하자. 내용 의존은 비교적 알아채기 쉽다. 7번 조각을 처리하려면 1번 조각의 정의 조항을 알아야 한다면 명백히 의존 관계다. 결정 의존은 훨씬 교묘하다. 각 조각 안에서 **자유롭게 선택할 수 있는 것**이 있고, 그 선택이 전역적으로 일관되어야 할 때 생긴다.

예를 들어 각 조각에서 발견한 오류에 카테고리 이름을 붙이는 작업은 조각별로 완결된다. 그런데 조각 A는 "PG 응답 지연"이라고 부르고 조각 B는 "게이트웨이 타임아웃"이라고 부르면, 병합한 뒤 같은 대상이 둘로 갈라진다. 내용 의존은 없지만 결정 의존은 있는 경우다.

이 구분은 함수형 관점에서 깔끔하게 표현할 수 있다. 독립 효과를 나란히 놓는 것은 적용 펑터(applicative)로 표현되고, 순차 의존에는 모나드가 필요하다([[16 - 적용 펑터 — 독립 효과의 병치]], [[17 - 모나드 — 순차 효과와 do 표기의 정체]]). `traverse`가 `Applicative`만 요구한다는 사실이 곧 "병렬화할 수 있다"는 형식적 진술이다([[19 - Foldable과 Traversable — 구조를 접고 가로지르기]]).

결정 의존이 있는 작업을 억지로 applicative로 표현하면 타입 검사는 통과하지만 의미가 깨진다. 타입 시스템이 잡아 주지 못하는 층위의 결합이기 때문이다.

### 3.2 독립성 위반의 네 가지 유형

실무에서 만나는 위반을 분류해 두면 진단이 빨라진다.

- **(a) 용어와 표현의 드리프트.** 각 조각이 자유롭게 이름을 붙이는데, 그 이름이 전역적으로 일관되어야 하는 경우다. 문서 번역을 청크로 나누면 고유명사와 존댓말 수준이 조각마다 달라진다. 로그 분류를 배치로 나누면 같은 원인에 다른 라벨이 붙는다. 코드 리팩터링을 파일별로 나누면 같은 개념에 다른 이름이 생긴다.
- **(b) 전역 제약 위반.** 조각들의 산출이 만족해야 할 전역 불변식이 있는 경우다. 정산 명세서를 항목별로 검증하면 각 항목은 통과하는데 합계가 맞지 않는다. 계약서 조항을 조각별로 요약하면 각 요약은 정확한데 서로 모순된다(1조는 "환불 불가", 12조는 "30일 내 환불 가능"이다. 어느 쪽이 우선하는지는 문서 전체를 봐야 안다).
- **(c) 경계 걸침**(boundary straddling). 찾아야 할 대상이 조각 경계에 걸쳐 있는 경우다. 20페이지씩 자른 계약서에서 19~21페이지에 걸친 조항은 어느 조각에서도 온전히 보이지 않는다. 대화 로그를 시간으로 자르면 경계에 걸친 대화가 잘린다. 이것은 독립성 위반이라기보다 **분할 자체의 결함**이지만 증상은 비슷하다. 결과에 구멍이 생기는데 아무도 모른다.
- **(d) 중복과 공백(팬아웃의 경우).** 렌즈를 자연어로 정의하면 렌즈끼리 겹치거나 사이에 빈 곳이 생긴다. "위험 조항을 뽑아라"와 "불리한 조건을 뽑아라"는 상당 부분 겹치고, 둘 다 "명시되지 않은 것"은 잡지 못한다.

| 위반 유형 | 증상 | 진단 방법 | 처방 |
|---|---|---|---|
| 용어 드리프트 | 병합 후 동의어 클러스터 폭증 | 병합 전 라벨 카디널리티가 예상보다 큼 | 공유 어휘를 프롬프트에 고정, 또는 병합 시 정규화 패스 |
| 전역 제약 위반 | 합계·정합성 불변식 실패 | 병합 후 불변식 검사 | 불변식을 병합기가 아니라 **코드**로 검사하고 위반 시 재처리 |
| 경계 걸침 | 특정 위치의 항목만 지속적으로 누락 | 조각 경계 근처 항목의 재현율을 따로 측정 | 겹침 창(overlap window) + 중복 제거 |
| 렌즈 중복·공백 | 종합 결과에 같은 말 반복, 특정 측면 부재 | 렌즈별 산출의 자카드 유사도 | 렌즈를 배타적 스키마 필드로 정의 |

### 3.3 독립성은 발견하는 것이 아니라 만드는 것이다

여기서 관점을 하나 바꿔야 한다. 독립성은 데이터에서 **발견하는** 것이 아니라 설계로 **만드는** 것이다. 이를 위한 도구가 세 가지 있다.

**공유 컨텍스트 주입.** 조각을 처리하기 전에 값싼 사전 패스로 전역 정보를 뽑아 모든 조각에 넣어 준다. 문서 번역이라면 용어집과 문체 지침을, 계약서 분석이라면 정의 조항과 문서 유형을, 로그 분류라면 미리 정한 카테고리 열거형을 넣는다.

이것은 결정 의존을 **내용 의존으로 낮추는** 기법이다. 각 조각이 스스로 결정하던 것을 미리 고정해 주면, 조각 사이의 일치를 조율할 필요가 없어진다. 대가는 사전 패스의 지연과 비용이며, 이것이 2.2절 식의 $A$에 들어간다.

**겹침 창.** 조각을 자를 때 인접 조각과 일정 부분이 겹치게 한다. 경계 걸침 문제의 표준 해법이고, 대가도 분명하다. 겹침 비율만큼 비용이 늘고, 겹친 영역에서 중복 산출이 나오므로 병합할 때 중복 제거가 필수가 된다. 중복을 제거하려면 산출에 **안정적인 식별자**가 있어야 한다(4.2절).

**분할 축 다시 고르기.** 가장 자주 무시되지만 가장 효과가 큰 처방이다. 페이지가 아니라 조항 단위로, 시간이 아니라 세션 단위로, 파일이 아니라 모듈 단위로 자른다. 자연스러운 경계를 따라 자르면 (b)와 (c)가 함께 완화된다. 이 경계를 찾는 데 값싼 모델이나 정규식을 한 번 쓰는 것은 거의 항상 남는 장사다.

```python
# 섹셔닝: 자연 경계 + 겹침 창 + 공유 컨텍스트.
# 세 가지가 전부 '독립성을 만드는' 장치라는 점이 핵심이다.
from dataclasses import dataclass


@dataclass(frozen=True)
class Section:
    section_id: str        # 안정적이어야 한다. 재실행·재시도에서 같은 조각은 같은 id.
    text: str
    span: tuple[int, int]  # 원본에서의 위치. 중복 제거와 인용 복원에 쓴다.


def split(doc: str, boundaries: list[int], overlap_chars: int) -> list[Section]:
    """boundaries 는 자연 경계(조항 시작 오프셋). 고정 길이 분할보다 거의 항상 낫다."""
    out = []
    for i, start in enumerate(boundaries):
        end = boundaries[i + 1] if i + 1 < len(boundaries) else len(doc)
        # 겹침은 뒤로만 준다. 앞뒤로 다 주면 중복이 두 배가 되고 이득은 같다.
        ext_end = min(len(doc), end + overlap_chars)
        out.append(Section(f"s{i:03d}", doc[start:ext_end], (start, ext_end)))
    return out


async def run_sectioned(doc: str, llm, glossary: str, boundaries: list[int]):
    sections = split(doc, boundaries, overlap_chars=800)
    # 공유 컨텍스트: 조각이 '스스로 정해야 했던 것'을 미리 고정해 결정 의존을 제거한다.
    shared = (
        f"용어집(반드시 이 표기를 사용):\n{glossary}\n"
        "분류는 아래 열거형만 사용: [PAYMENT, REFUND, LIABILITY, TERM, OTHER]"
    )

    async def one(s: Section):
        # span 을 함께 요구하는 이유: 중복 제거 키를 만들고 인용을 검증하기 위해서.
        return await llm.json(
            system=shared,
            user=f"[section {s.section_id}, chars {s.span}]\n{s.text}",
            schema=CLAUSE_SCHEMA,
        )

    return sections, await gather_with_coverage(sections, one)
```

### 3.4 섹셔닝이 작동하지 않는 경우

1. **전역 판단이 목적일 때.** "이 계약이 우리에게 유리한가"는 조각별 판단을 합한 것이 아니다. 조각에서 뽑을 수 있는 것은 사실이고, 판단은 사실이 다 모인 뒤에만 할 수 있다. 섹셔닝은 **추출**에 쓰고, **판단**은 병합한 뒤 한 번에 한다. 이 분리를 지키지 않으면 각 조각이 부분 정보로 내린 판단이 병합기에서 화해할 수 없는 모순으로 나타난다.
2. **조각이 너무 작아 문맥이 사라질 때.** $n$을 키우면 조각당 문맥이 줄고, 어느 지점부터는 각 호출의 정확도가 급락한다. 2.2절의 모델은 조각의 정확도가 $n$과 무관하다고 가정했는데, 이 가정이 깨지면 최적 $n^{*}$는 훨씬 작아진다. 실무에서 관찰한 바로는 "사람이 그 조각만 보고도 그 질문에 답할 수 있는가"가 좋은 기준이다.
3. **순서 자체가 산출물일 때.** 사건 타임라인 재구성, 인과 사슬 추적, 논증 흐름 요약처럼 산출물의 본질이 순서와 연결이라면, 조각으로 나눈 뒤 이어 붙이는 것으로는 복원되지 않는다.
4. **조각 수가 적고 단일 호출이 컨텍스트에 들어갈 때.** 3조각으로 나눌 생각이라면 대개 한 번에 넣는 편이 낫다. 병합 비용과 오버헤드가 이득보다 크기 때문이다. 섹셔닝은 조각 수가 두 자릿수에 가까워질 때 효과가 있다.

> [!warning] 흔한 오해
> "컨텍스트 윈도가 커졌으니 섹셔닝은 곧 필요 없어진다." 이 주장은 세 가지 점에서 틀렸다. 첫째, 긴 컨텍스트에서는 중간 부분의 정보가 덜 활용되는 경향(이른바 lost-in-the-middle)이 보고되어 있다. **넣을 수 있다는 것과 잘 활용한다는 것은 다르다.** 둘째, 섹셔닝이 주는 이득 중 지연은 컨텍스트 크기와 무관하다. 100만 토큰을 한 번에 처리하는 호출은 그 자체로 느리다.
>
> 셋째, 비용은 대체로 토큰 수에 비례하므로 컨텍스트가 커진다고 싸지지 않는다. 컨텍스트가 커져서 사라지는 것은 "물리적으로 들어가지 않아서 어쩔 수 없이 나눈다"는 이유 하나뿐이다. 그것은 섹셔닝을 쓰는 여러 이유 가운데 하나에 불과하다([[21 - 메모리의 문제 — 컨텍스트 윈도·상태·망각]]).

## 4. 진짜 어려움은 병합이다: 병합기가 모노이드가 아니면 결과가 흔들린다

분해 방식은 설계 회의에서 30분이면 정해진다. 병합에서는 배포 후 6개월 동안 버그가 나온다. 이 비대칭에는 이유가 있다. 분해는 입력의 구조를 보고 정하면 되지만, 병합은 **가지들이 실제로 무엇을 내놓는지**를 알아야 정할 수 있고, 그것은 실행해 보기 전에는 알 수 없다.

### 4.1 병합기에 요구되는 대수적 성질과 그 운영상의 의미

병합기를 이항 연산 $\oplus$로 보자. 병합은 $r_1 \oplus r_2 \oplus \cdots \oplus r_n$이 된다. 여기에 세 가지 성질을 요구할 수 있다. 각 성질은 순수하게 수학적인 요구가 아니라, **운영 요구사항을 다르게 표현한 것**이다.

**결합법칙**(associativity) $(a \oplus b) \oplus c = a \oplus (b \oplus c)$가 성립해야 부분 병합을 할 수 있다. 결과가 도착하는 대로 접어 나갈 수 있고, 트리 모양으로 병합해 병합 자체를 병렬화할 수 있으며, 중간 결과를 체크포인트로 저장했다가 이어서 병합할 수 있다. 결합법칙이 깨지면 병합 순서가 결과를 바꾼다.

**LLM 병합기는 거의 항상 결합법칙을 만족하지 않는다.** 세 개의 부분 결과에서 (A,B)를 먼저 합치고 C를 붙인 것과, A에 (B,C)를 합친 것을 붙인 것은 다르다. 순서에 따라 어느 정보가 살아남는지가 달라지기 때문이다.

**항등원**(identity) $e \oplus a = a \oplus e = a$가 있어야 **빈 결과와 실패한 가지를 똑같은 방식으로 다룰 수 있다.** 항등원이 정의되어 있으면 `fold(results, e, merge)`가 $n=0$일 때도 정상적으로 동작하고, 실패한 가지를 $e$로 대체해 특수 분기 없이 처리할 수 있다. 항등원이 없으면 병합기 안에 "결과가 하나뿐일 때", "결과가 없을 때" 같은 분기가 늘어난다.

**멱등성**(idempotence) $a \oplus a = a$가 성립해야 **재시도가 안전하다.** 429로 실패한 가지를 재시도했는데 사실 첫 시도도 성공했다면(응답만 받지 못했다면), 같은 결과가 두 번 들어온다. 병합이 멱등이면 아무 일도 일어나지 않지만, 그렇지 않으면 중복이 생긴다.

결합법칙과 항등원을 갖추면 모노이드다. 여기에 교환법칙까지 있으면 도착 순서와 완전히 무관해지고, 멱등성까지 있으면 결합 반격자(join-semilattice)가 되어 재시도와 중복 전달에 전혀 영향을 받지 않는다. 이 계층은 분산 시스템에서 CRDT를 설계할 때 요구하는 것과 정확히 같다([[20 - 코디네이션·분산 락·CRDT (Coordination, Distributed Locks & CRDTs)]], [[14 - 반군과 모노이드 — 결합·항등의 대수와 병렬성]]).

| 성질 | 없을 때 생기는 운영 문제 | 확보 방법 |
|---|---|---|
| 결합법칙 | 병합 순서가 결과를 바꿔 재현 불가. 스트리밍 병합·트리 병합 불가 | 병합을 집합 연산·집계로 환원. LLM 병합은 마지막 한 번만 |
| 항등원 | 실패·빈 결과마다 특수 분기. $n$이 작을 때 코드 경로가 갈라짐 | 빈 컬렉션·중립 레코드를 명시적 값으로 정의 |
| 교환법칙 | 도착 순서(=꼬리 지연 변동)가 결과에 새어 듦 | 정렬 키를 결과에 넣고 병합 전 정렬 |
| 멱등성 | 재시도·중복 전달이 중복 산출 | 안정적 식별자 기반 dedup |

> [!warning] 흔한 오해
> "병합은 결과를 이어 붙이는 마지막 잡일이다." 결과의 의미를 정하는 것은 병합이다. 같은 부분 결과 집합이라도 병합 규칙에 따라 최종 산출물이 완전히 달라진다. 중복을 어떻게 판정하는지, 모순을 어느 쪽으로 해소하는지, 우선순위를 무엇으로 매기는지가 모두 병합 규칙이다.
>
> 이것은 잡일이 아니라 **도메인 로직**이다. 도메인 로직을 프롬프트 속에 자연어로 묻어 두면 테스트할 수 없다. 이 절의 결론은 병합 규칙을 코드로 꺼내라는 것이다.

### 4.2 결정론적 병합의 레퍼토리: 먼저 코드로 되는지 확인한다

LLM 병합기를 꺼내기 전에, 코드로 해결되는 경우가 생각보다 많다는 점을 확인해야 한다. 조건은 하나다. **부분 결과가 구조화되어 있고 안정적인 식별자를 가져야 한다.** 그래서 섹셔닝의 출력 스키마를 설계하는 일과 병합을 설계하는 일은 같은 작업이다([[11 - 구조화된 출력 — 스키마·제약 디코딩·파싱 실패의 처리]]).

```json
{
  "section_id": "s003",
  "clauses": [
    {
      "clause_key": "12.2",
      "category": "REFUND",
      "summary": "결제일로부터 30일 이내 전액 환불 가능",
      "evidence_span": [48210, 48533],
      "evidence_quote": "구매자는 결제일로부터 30일 이내에...",
      "confidence": 0.86,
      "conflicts_with": ["1.4"]
    }
  ],
  "coverage_note": "이 조각에서 조항 번호가 없는 문단 2개는 분류하지 않음"
}
```

병합에 필요한 것이 이 스키마에 모두 들어 있다. `clause_key`는 dedup 키다(겹침 창에서 나온 중복은 이 키로 합쳐진다). `evidence_span`은 인용 검증과 정렬에 쓰는 키다. `conflicts_with`는 모순 해소를 병합기로 미루지 않고, **모순 감지를 가지 안에서 하도록** 옮겨 놓은 것이다. `coverage_note`는 커버리지 자체를 값으로 만든 것이다.

```sql
-- 부분 결과를 테이블에 부어 놓고 SQL로 병합하는 방식.
-- 왜 SQL인가: 결합·교환·멱등이 전부 공짜로 따라오고, 병합 규칙이 리뷰 가능한 텍스트로 남는다.
-- (같은 clause_key 가 여러 조각에서 나오면 confidence 가 가장 높은 것을 택하고 근거는 모두 보존)
WITH ranked AS (
  SELECT
    clause_key,
    category,
    summary,
    evidence_span,
    confidence,
    section_id,
    ROW_NUMBER() OVER (
      PARTITION BY run_id, clause_key
      ORDER BY confidence DESC, section_id ASC   -- 타이브레이커를 반드시 결정론적으로
    ) AS rn,
    COUNT(*)      OVER (PARTITION BY run_id, clause_key) AS n_witness,
    COUNT(DISTINCT category)
                  OVER (PARTITION BY run_id, clause_key) AS n_categories
  FROM section_results
  WHERE run_id = :run_id
)
SELECT
  clause_key,
  category,
  summary,
  n_witness,                        -- 몇 개 조각이 같은 조항을 봤는가 = 겹침 창의 교차 검증
  n_categories > 1 AS needs_review  -- 분류가 갈렸다 = 결정 의존 위반의 흔적. 사람에게 올린다.
FROM ranked
WHERE rn = 1
ORDER BY clause_key;
```

이 쿼리의 핵심은 `needs_review` 컬럼이다. 겹침 창 덕분에 같은 조항을 두 조각이 보게 되는데, 두 조각의 분류가 다르면 그것 자체가 **모델 불확실성을 공짜로 관측한 값**이 된다. 투표를 따로 실행하지 않고도 투표와 비슷한 신호를 얻는 것이다. 섹셔닝과 투표를 합성하는 값싼 방법이기도 하다.

결정론적 병합의 표준 레퍼토리를 정리하면 다음과 같다.

- **키 기반 dedup**: 안정적인 키로 그룹을 묶은 뒤 대표를 선택한다. 대표 선택 규칙은 결정론적이어야 한다(위 SQL의 타이브레이커).
- **집합 합집합과 교집합**: 여러 가지가 뽑은 엔티티를 합치거나, 여러 가지가 **모두** 동의한 것만 남긴다(정밀도 우선).
- **수치 집계**: 합, 최대, 평균을 구한다. 전역 제약(합계 일치)은 여기서 검사한다.
- **우선순위 격자**: 심각도나 신뢰도처럼 순서가 있는 값은 최댓값 병합(join)이 자연스럽고, 이 병합은 자동으로 결합적, 교환적, 멱등적이다.
- **정렬 후 연결**: 순서가 있는 산출(타임라인, 조항 목록)은 정렬 키로 이어 붙인다. 조각 순서에 의존하지 않으려면 정렬 키가 원본에서의 위치여야 한다.

```typescript
// 병합기를 '모노이드'로 명시하고, 그 법칙을 테스트로 강제한다.
// 이 인터페이스를 만족하면 도착 순서·재시도·부분 실패에 대해 자동으로 안전해진다.
interface Merger<T> {
  readonly empty: T;                    // 항등원 — 실패한 가지의 자리를 메운다
  readonly concat: (a: T, b: T) => T;   // 결합적이어야 한다
}

type Findings = { byKey: Map<string, Finding> };

const findingsMerger: Merger<Findings> = {
  empty: { byKey: new Map() },
  concat: (a, b) => {
    const out = new Map(a.byKey);
    for (const [k, v] of b.byKey) {
      const prev = out.get(k);
      // 병합 규칙이 여기 한 곳에만 있다. 프롬프트에 흩어져 있지 않다.
      out.set(k, prev === undefined ? v : pickHigherConfidence(prev, v));
    }
    return { byKey: out };
  },
};

// 법칙 테스트. 이걸 안 짜면 위 규칙이 조용히 비결합적으로 바뀐다.
// (예: pickHigherConfidence 가 동점에서 '나중 것'을 택하도록 바뀌는 순간 결합법칙이 깨진다)
function assertMonoidLaws<T>(m: Merger<T>, samples: T[], eq: (x: T, y: T) => boolean) {
  for (const a of samples) {
    console.assert(eq(m.concat(m.empty, a), a), "left identity");
    console.assert(eq(m.concat(a, m.empty), a), "right identity");
    for (const b of samples) for (const c of samples) {
      console.assert(
        eq(m.concat(m.concat(a, b), c), m.concat(a, m.concat(b, c))),
        "associativity",
      );
    }
  }
}
```

### 4.3 LLM 병합기: 언제 필요하고 무엇이 깨지는가

코드로 해결되지 않는 것도 있다. "결제 실패"와 "승인 거절"이 같은 것인지 판단하는 **의미적 중복 제거**, 두 조각이 반대되는 말을 할 때 어느 쪽이 맞는지 정하는 **모순 해소**, 부분 결과를 읽을 만한 보고서로 만드는 **자연어 종합**이 그렇다. 이런 일에는 LLM 병합기가 필요하다. 대신 다음 네 가지 문제가 따라온다.

**(1) 컨텍스트 초과.** 병합 입력이 $nb$ 토큰이므로 $n$이 커지면 컨텍스트를 넘긴다. 이것이 팬아웃 폭의 실질적인 상한이 되는 경우가 아주 흔하다. 처방은 계층 병합(4.4절)이거나, 부분 결과를 병합 전에 압축하는 것이다. 압축은 손실을 한 번 더 겪는 것이므로 공짜가 아니다([[22 - 단기 메모리 — 대화 관리·요약·압축]]).

**(2) 중간 소실.** 긴 병합 입력에서는 가운데 놓인 부분 결과가 덜 반영된다. 그리고 이 편향은 **조각 순서와 결합**한다. 조각을 원본 순서대로 나열하면 문서의 중간 부분이 체계적으로 덜 반영된다. 완화하려면 부분 결과를 중요도 순으로 재배열하거나(이 경우 원본 순서 정보가 사라진다), 계층 병합으로 각 병합 입력을 짧게 유지한다.

**(3) 인용 소실.** 부분 결과에 있던 `evidence_span`이 종합 과정에서 사라진다. 병합기가 문장을 다시 쓰면서 출처를 빠뜨리기 때문이다. 처방은 병합기의 출력 스키마에도 인용 필드를 강제하고, **병합한 뒤 인용이 원본에 실제로 있는지 코드로 검증**하는 것이다. 이 검증은 비용이 적고 효과가 크다.

**(4) 비결합성.** 4.1절에서 말했듯이 LLM 병합은 순서에 의존한다. 그래서 **같은 부분 결과 집합으로 두 번 실행하면 최종 산출이 달라진다.** 도착 순서나 부분 실패 때문에 병합 입력의 배열이 바뀌면 결과도 바뀐다. 감사 대상이나 회귀 테스트처럼 재현이 필요한 파이프라인에서는 치명적이다.

최소한의 처방은 **병합 입력을 항상 결정론적인 순서로 정렬해서 넣는 것**이다. 놀랍게도 이렇게 하지 않는 구현이 많은데, 비결정성이 들어오는 경로가 두 갈래이기 때문이다.

하나는 **완료 순으로 수집하는 API**다. `asyncio.as_completed`, `ZIO`의 스트리밍 수집, 완료 콜백에서 리스트에 append하는 코드는 모두 도착 순서를 결과 순서로 만든다. 반면 `Promise.all`과 `Promise.allSettled`, `ZIO.foreachPar`는 입력 인덱스 순서를 보존하므로 이 경로에서는 안전하다.

다른 하나는 **실패한 가지를 걸러내는 것**이다. 인덱스 순서가 보존되더라도 실패한 가지를 제거하면 남는 원소 집합이 실행마다 달라지고, 병합기가 보는 입력도 달라진다. 이 경로는 정렬로 고칠 수 없다. 실패한 자리에 항등원(4.1절)을 채워 넣어야 없어진다.

> [!note] 실무 규칙
> 병합을 **두 단계**로 나눈다. 먼저 코드가 dedup, 집계, 정렬, 불변식 검사를 수행해 구조화된 중간 결과를 만든다. 그다음 LLM이 그 중간 결과를 읽고 **서술만** 한다. 이렇게 하면 사실 관계는 결정론적으로 확정되고, LLM은 표현만 담당한다. LLM에게 dedup까지 맡기면 무엇이 합쳐졌는지 로그에 남지 않아 디버깅할 수 없게 된다.

### 4.4 계층 병합: 컨텍스트는 지키지만 순서 의존이 생긴다

$n$이 커서 한 번에 병합할 수 없으면 트리 모양으로 접는다.

```
선형 폴드 (fold-left)                 트리 리듀스 (tournament)
  r1─┐                                  r1─┐
     ├─m─┐                                 ├─m─┐
  r2─┘   ├─m─┐                          r2─┘   │
  r3─────┘   ├─m─┐                             ├─m─┐
  r4─────────┘   ├─m ► out              r3─┐   │   │
  r5─────────────┘                         ├─m─┘   ├─m ► out
                                        r4─┘       │
  깊이 n-1, 각 단계 입력 = 누적+1        r5─┐       │
  → 누적 결과가 계속 커진다                 ├─m─────┘
  → 앞쪽 정보가 반복 재작성되며 마모      r6─┘

                                        깊이 ⌈log2 n⌉, 각 단계 입력 = 2개
                                        → 각 병합 입력이 짧고 병합끼리 병렬
                                        → 대신 정보가 log n 번 재작성된다
```

트리 리듀스는 병합 지연을 $\beta n$에서 $\beta' \log n$ 수준으로 낮춰, 2.2절의 최적 폭을 크게 끌어올린다. 대신 다음과 같은 대가가 있다.

- **재작성으로 인한 마모.** 각 정보가 $\lceil \log_2 n \rceil$번 병합기를 거치면서 매번 조금씩 다시 쓰인다. 요약의 요약의 요약이 되어 원본에서 멀어진다. 세부 사실과 인용이 가장 먼저 사라진다.
- **순서 의존이 트리 모양으로 옮겨 간다.** 어떤 짝을 먼저 묶느냐가 결과를 바꾼다. 원본 순서에서 인접한 것끼리 묶으면 국소 맥락이 보존되어 대체로 낫지만, 그 선택 자체가 결과에 영향을 준다는 사실은 그대로 남는다.
- **전역 판단을 할 수 없다.** 리프에서 "가장 중요한 3개만 남겨라" 같은 절단을 하면, 국소적으로 중요한 것을 남기고 전역적으로 중요한 것을 버리게 된다. 절단은 반드시 루트에서 한 번만 한다.

**계층 병합이 작동하지 않는 경우**는 전체를 한 번에 봐야 산출물이 성립할 때다. 예를 들어 "이 100개 로그를 원인별로 클러스터링하라"는 과업을 트리로 접으면, 각 서브트리는 자기 안에서만 클러스터를 만든다. 상위에서는 그 클러스터들을 다시 클러스터링해야 하는데, 이 단계는 원본 로그를 보지 못하므로 잘못 합치게 된다.

이런 과업은 (a) 클러스터 정의를 미리 고정하거나(3.3절의 공유 컨텍스트), (b) 임베딩 같은 결정론적 방법으로 후보 그룹을 먼저 만들고 LLM에게는 이름만 붙이게 하는 편이 낫다.

## 5. 투표: 다수결은 정답이 아니라 모델의 최빈답으로 수렴한다

투표는 개념이 단순해서 오히려 오해가 많다. 이 절의 목표는 투표가 **정확히 무엇으로 수렴하는지**를 확정하고, 거기서 self-consistency의 상한과 실패 조건을 모두 이끌어 내는 것이다.

### 5.1 Condorcet의 조건과 그 한계

이진 판단부터 보자. $n$명의 투표자가 각각 확률 $p$로 맞히고 서로 독립이라면, 다수결이 맞을 확률은 다음과 같다.

$$
P_n = \sum_{k=\lceil (n+1)/2 \rceil}^{n} \binom{n}{k} p^k (1-p)^{n-k}
$$

$p > 1/2$이면 $n \to \infty$에서 $P_n \to 1$이고, $p < 1/2$이면 $P_n \to 0$이다. 이것이 Condorcet 배심원 정리다. **정리의 후반부가 훨씬 중요하다.** 개별 정확도가 절반에 못 미치면 투표를 늘릴수록 **더 확실하게 틀린다.** 다수결은 신호를 증폭하는 장치이므로, 신호가 음수면 음수를 증폭한다.

정리의 전제는 세 가지다. (i) 답이 이산적이고 정답이 하나이며, (ii) 투표자들이 서로 독립이고, (iii) 모든 투표자의 $p$가 같다. LLM 투표에서는 세 전제를 모두 조심스럽게 봐야 한다. (i)은 5.2절에서, (ii)는 6절에서 다룬다.

(iii)은 다른 모델을 섞을 때 문제가 된다. 실력 차이가 큰 투표자들을 같은 가중치로 섞으면, 약한 투표자가 강한 투표자의 정확도를 끌어내릴 수 있다. 가중 투표가 해답이지만, 가중치를 정하려면 검증 세트가 필요하다.

### 5.2 무엇으로 수렴하는가: self-consistency의 진짜 상한

이제 이진이 아닌 일반적인 경우로 넘어가자. 모델이 답 공간 $\mathcal{A}$ 위에 분포 $q(\cdot \mid x)$를 유도한다고 보자(샘플링 온도 등에 따라 결정되는 분포다). $n$개를 뽑아 최빈값을 취하면, 대수의 법칙에 따라 다음이 성립한다.

$$
\hat{a}_n \;\xrightarrow[n \to \infty]{}\; \arg\max_{a \in \mathcal{A}} \; q(a \mid x)
$$

**다수결은 정답으로 수렴하지 않는다. 모델의 최빈답으로 수렴한다.** 이 한 문장으로 self-consistency에 대한 오해가 거의 모두 풀린다.

따라서 표본이 무한할 때의 정확도 상한은 다음과 같다.

$$
\text{acc}_\infty = \Pr_x\!\left[\arg\max_a q(a \mid x) = a^{*}(x)\right]
$$

그리고 단일 샘플의 기대 정확도는 $\text{acc}_1 = \mathbb{E}_x[q(a^{*} \mid x)]$이다. **투표로 얻을 수 있는 이득은 $\text{acc}_\infty - \text{acc}_1$이 전부다.** 이 차이는 유한하다. 대개 작지 않지만, 무한하지도 않다.

그리고 이 차이의 크기는 문제 유형에 달려 있다. 모델이 "대체로 맞히지만 가끔 계산 실수를 하는" 유형의 문제에서는 차이가 크다(정답이 최빈값이고 오답은 흩어진다). 반면 모델이 "체계적으로 오해하는" 유형에서는 0이거나 음수다(오답이 최빈값이다).

> [!info] 역사 메모
> self-consistency는 Wang 등이 2022년에 제안한 기법으로(ICLR 2023에서 발표), 사고 연쇄로 여러 추론 경로를 샘플링한 뒤 **최종 답에 대해서만** 다수결을 취하는 것이 핵심이다. 논문의 관점은 정확하다. 이것은 추론 경로를 잠재 변수로 보고 **주변화**(marginalization)하는 것이다. $p(a \mid x) = \sum_z p(a, z \mid x)$에서 $z$(추론 경로)를 적분해 없애는 근사다.
>
> 이 관점이 중요한 이유는 무엇을 세면 안 되는지 알려 주기 때문이다. **추론 경로를 세면 안 되고, 답만 세야 한다.** 같은 답에 도달한 서로 다른 경로가 표를 나눠 가지면 주변화가 아니라 분열이 된다. 자세한 계보와 CoT 자체의 한계는 [[15 - 사고 연쇄 — CoT·self-consistency와 그 한계]]에서 다룬다.

### 5.3 정규화: 표를 세려면 같은 것을 같다고 판정해야 한다

주변화가 제대로 되려면 "같은 답"을 같다고 인식해야 한다. 실무에서 self-consistency를 구현할 때는 이 부분이 대부분을 차지한다.

- 수치: `0.5`, `1/2`, `50%`, `0.50`, `₩1,500`과 `1500원`. 정규화하지 않고 세면 표가 모두 갈린다.
- 열거형: 프롬프트는 `REFUND`를 요구했는데 모델이 `Refund`, `환불`, `refund_request`를 낸다. 제약 디코딩으로 막는 것이 최선이고, 막지 못하면 매핑 테이블이 필요하다.
- 구조체: 필드 하나가 다르면 다른 답일까? 부분 일치는 어떻게 셀까? 대개는 **투표 대상을 좁히는 것**이 해답이다. 구조체 전체가 아니라 결정적인 필드 하나(승인/거절, 금액, 카테고리)에 대해서만 투표하고, 나머지는 이긴 후보의 값을 쓴다.
- 자유 텍스트: 정규화할 수 없다. 5.4절에서 다룬다.

```python
# self-consistency: 정규화 → 집계 → 합의도 기반 기권.
# 핵심은 세 가지다.
#   (1) 추론 경로가 아니라 '정규화된 최종 답'을 센다
#   (2) 합의도를 함께 반환한다 — 이게 없으면 다수결 결과를 무비판적으로 쓰게 된다
#   (3) 합의도가 낮으면 결과를 내지 않고 에스컬레이션한다
from collections import Counter
from dataclasses import dataclass


@dataclass
class VoteResult:
    answer: str | None
    agreement: float      # 최빈답 득표율. 1/n_distinct 근처면 사실상 무작위
    margin: float         # 1위와 2위의 득표 차 비율. 동률 근처인지 판단
    n_valid: int


def normalize_amount(raw: str) -> str:
    """도메인 정규화. 이 함수의 품질이 투표 품질을 좌우한다."""
    digits = "".join(ch for ch in raw if ch.isdigit())
    return str(int(digits)) if digits else raw.strip().lower()


def vote(samples: list[str | None], normalize=normalize_amount,
         min_agreement: float = 0.5, min_margin: float = 0.15) -> VoteResult:
    valid = [normalize(s) for s in samples if s is not None]
    if not valid:
        return VoteResult(None, 0.0, 0.0, 0)

    counts = Counter(valid).most_common()
    top, top_n = counts[0]
    second_n = counts[1][1] if len(counts) > 1 else 0
    agreement = top_n / len(valid)
    margin = (top_n - second_n) / len(valid)

    # 기권 조건. "다수결이니까 이게 답"이라고 밀어붙이지 않는다.
    # 합의도가 낮다는 것은 모델의 분포가 평평하다는 뜻이고,
    # 평평한 분포의 최빈값은 표본 노이즈에 지배된다.
    if agreement < min_agreement or margin < min_margin:
        return VoteResult(None, agreement, margin, len(valid))
    return VoteResult(top, agreement, margin, len(valid))
```

특히 중요한 것은 `margin` 검사다. 5표가 2:2:1로 나뉘면 최빈답은 40%를 얻었지만 2위와의 차이는 0이다. 표본을 하나 더 뽑으면 순위가 뒤집힐 수 있다. **최빈값을 그대로 쓰는 것과, 최빈값이 안정적일 때만 쓰는 것은 다른 알고리즘이다.**

### 5.4 자유 형식 생성에는 다수결이 그대로 통하지 않는다

"이 계약서를 요약하라"는 요청에 답이 5개 왔다면 다수결로 셀 것이 없다. 모두 다른 문자열이므로 모든 답이 1표씩이다. 여기서 택할 수 있는 길은 세 가지다.

**(a) 투표 대상을 이산화한다.** 자유 텍스트 전체가 아니라 그 안에 들어 있는 **판정할 수 있는 명제**를 뽑아, 명제마다 투표한다. 요약 5개에서 사실 주장을 추출하고, 3개 이상에서 등장하는 주장만 남기는 식이다. 사실상 앙상블 추출이다.

이 기법은 환각을 억제하는 데 효과가 있다. 한 번만 나온 주장은 그 표본에서만 만들어졌을 가능성이 높기 때문이다. 대신 추출 단계가 추가되므로 **비용이 크고**, 여러 표본이 공유하는 체계적 환각은 잡지 못한다(6절).

**(b) 일관성 판단을 모델에게 맡긴다.** 후보 $n$개를 모두 보여 주고 "다른 답들과 가장 일관된 것을 골라라"라고 시키는 변형이 있다(흔히 universal self-consistency라고 부른다). 다수결의 취지를 자유 형식으로 옮긴 것인데, 여기서는 선택자가 곧 판정자이므로 7절에서 다룰 판정자 편향이 그대로 들어온다.

특히 길이 편향이 위험하다. 긴 답일수록 다른 답들의 내용을 더 많이 포함하므로 "가장 일관된 것"으로 뽑히기 쉽다.

**(c) 투표를 포기하고 best-of-n으로 간다.** 합의를 만들려 하지 말고, 검증자나 판정자로 하나를 고른다. 7절에서 다룬다.

**투표가 작동하지 않는 경우**를 정리하면 다섯 가지다.

1. **개별 정확도가 50% 미만인 문제.** Condorcet 정리의 후반부에 해당한다. 표본을 늘릴수록 오답이 굳어진다. 이때는 투표가 아니라 프롬프트, 컨텍스트, 모델을 바꿔야 한다.
2. **정답이 여러 개이거나 답 공간이 연속인 문제.** "적절한 환불 금액"처럼 허용 구간이 있는 답에서는 최빈값이 의미가 없다. 중앙값이나 구간 합의로 바꿔야 한다.
3. **자유 형식.** 위에서 본 대로다.
4. **모델의 최빈답이 체계적으로 오답인 문제.** 5.2절의 상한이 낮은 경우다. 투표는 아무것도 고치지 못하고 비용만 $n$배가 된다. 이런 문제에서는 **오히려 단일 샘플보다 나빠질 수 있다.** 단일 샘플은 가끔 운 좋게 소수파인 정답을 뽑지만, 다수결은 그 정답을 확실히 버리기 때문이다.
5. **오류가 상관된 경우.** 다음 절 전체가 이 이야기다.

> [!warning] 흔한 오해
> "다수결을 쓰면 정확도가 오른다." 정확도가 오르는 것은 **분산**이 줄기 때문이지 편향이 줄기 때문이 아니다. 통계 용어로 말하면 투표는 variance reduction이지 bias reduction이 아니다. 모델이 체계적으로 틀리는 문제에서 투표는 그 체계적 오류를 더 확실하게 만든다.
>
> 그래서 투표를 도입하기 전에 반드시 "우리 모델의 오류는 무작위인가, 체계적인가"를 물어야 한다. 이 질문의 답은 실패 사례 20건을 읽어 보면 대개 나온다. 같은 방식으로 틀리면 체계적이고, 매번 다르게 틀리면 무작위다.

## 6. 오류 상관: 유효 표본 수는 $1/\rho$에서 멈춘다

이 절에서는 Condorcet 정리의 두 번째 전제인 독립성이 LLM 투표에서 어떻게 깨지는지, 그리고 그 대가가 정확히 얼마인지를 살펴본다. "샘플을 늘릴수록 좋아진다"는 오해를 정량적으로 반박하는 절이다.

### 6.1 설계 효과: 상관이 있으면 표본 효과는 포화된다

표본 조사 이론에서 잘 알려진 결과를 빌려 오자. 표본들 사이에 급내 상관(intra-class correlation) $\rho$가 있으면, $n$개 표본의 **유효 표본 수**는 다음과 같다.

$$
n_{\text{eff}} = \frac{n}{1 + (n-1)\rho}
$$

$n \to \infty$이면 다음으로 수렴한다.

$$
n_{\text{eff}} \;\longrightarrow\; \frac{1}{\rho}
$$

**상한이 $1/\rho$이다.** $\rho = 0.5$이면 표본을 아무리 늘려도 독립 표본 2개 분량을 넘지 못한다. $\rho = 0.2$이면 5개 분량이다. $\rho = 0.05$는 되어야 20개 분량이 나온다.

| $\rho$ | $n=5$ 의 $n_{\text{eff}}$ | $n=20$ 의 $n_{\text{eff}}$ | $n \to \infty$ 상한 |
| ------ | ------------------------ | ------------------------- | ----------------- |
| 0.0    | 5.0                      | 20.0                      | ∞                 |
| 0.05   | 4.2                      | 10.3                      | 20                |
| 0.1    | 3.6                      | 6.9                       | 10                |
| 0.3    | 2.3                      | 3.0                       | 3.3               |
| 0.5    | 1.7                      | 1.9                       | 2                 |

같은 모델, 같은 프롬프트에서 온도만 바꿔 뽑은 표본들의 $\rho$는 작지 않다고 볼 이유가 있다. 이것은 측정한 상수가 아니라 구조에서 나오는 논증이므로 그렇게 읽어야 한다. 오류의 원인은 대부분 **표본 단위가 아니라 조건 단위**로 작용한다.

프롬프트의 모호한 문장, 컨텍스트에 들어간 잘못된 문서, 모델이 학습 과정에서 굳힌 잘못된 사전 지식 같은 원인은 모든 표본에 똑같이 작용한다. 온도가 바꾸는 것은 그 위에 얹힌 표면적인 변동뿐이다.

$\rho$를 직접 재기는 어렵지만 **간접적으로 관측하기는 쉽다**. 오답인 케이스에서 표본들이 얼마나 같은 오답을 냈는지 세면 된다. 5개 중 5개가 똑같이 틀렸다면 그 문제에서 $\rho \approx 1$이다. 이 지표를 평가 파이프라인에 넣어 두면 "표본을 늘리면 좋아질 문제"와 "늘려도 소용없는 문제"를 구분할 수 있고, 그것이 곧 예산 배분 규칙이 된다.

### 6.2 한계효용의 산수

상관이 0이더라도 표본의 한계효용은 빠르게 떨어진다. 직관적으로 보면, 추가 표본이 결과를 바꾸려면 **현재 표가 거의 동점**이어야 한다. 동점에 가까울 확률은 $n$이 커질수록 대략 $O(n^{-1/2})$로 줄어든다(이항 분포의 최빈값 근처 확률질량). 따라서 다음이 성립한다.

$$
\text{한계이득}(n) = O(n^{-1/2}), \qquad \text{한계비용}(n) = O(1) \quad\Longrightarrow\quad \frac{\text{이득}}{\text{비용}} = O(n^{-1/2})
$$

$p$가 $1/2$에서 멀면 이득은 지수적으로 떨어진다(Chernoff 한계). 어느 쪽이든 **비용은 선형으로 늘지만 이득은 그보다 훨씬 느리게 늘어난다.** $n=3$에서 $n=5$로 늘리는 것은 대개 효과가 있지만, $n=5$에서 $n=20$으로 늘리는 것은 거의 효과가 없다. 이것은 정성적인 감각이 아니라 위 식에서 바로 나오는 결과다.

여기에 5.2절의 상한이 겹친다. 유한한 상한($\text{acc}_\infty$)에 $O(n^{-1/2})$ 속도로 다가가므로, 곡선은 빠르게 평평해진 뒤 그대로 멈춘다. 반복 샘플링에 관한 연구들이 관측한 것도 이런 형태다. 다만 주의해야 할 구분이 하나 있다.

**커버리지(pass@k, 즉 $k$개 중 하나라도 맞을 확률)와 정확도(다수결이 맞을 확률)는 완전히 다른 곡선이다.** 커버리지는 표본을 늘리면 계속 오른다(정답이 분포의 꼬리에 있어도 언젠가는 뽑히기 때문이다). 다수결 정확도는 최빈답에서 멈춘다.

이 둘을 혼동하면 "표본을 $k$개 뽑았더니 pass@$k$가 이만큼 나오더라"는 관측에서 "그러니 다수결로 그만큼 얻는다"는 결론을 내리게 되는데, 이것은 틀렸다. pass@$k$는 **정답이 후보 집합 안에 있었다**는 진술일 뿐, 그것을 골라냈다는 진술이 아니다. **커버리지를 정확도로 바꾸려면 정답을 골라낼 수 있는 검증자가 필요하고, 그 검증자가 바로 7절의 주제다.**

> [!warning] 흔한 오해
> "샘플을 늘릴수록 좋아진다." 이 말은 세 가지 점에서 틀렸다. (1) 상관이 있으면 유효 표본이 $1/\rho$에서 포화된다. (2) 상관이 없어도 한계이득은 $O(n^{-1/2})$로 떨어지는데 비용은 선형으로 는다. (3) 다수결의 상한은 모델의 최빈답 정확도이므로, 그 상한에 도달한 뒤로는 표본을 무한히 늘려도 개선은 정확히 0이다.
>
> 표본 수를 늘리는 것은 조정할 수 있는 수단 가운데 **가장 먼저 시도하고 가장 빨리 포기해야 할** 수단이다.

### 6.3 다양성 주입: $\rho$를 낮추는 것이 $n$을 늘리는 것보다 낫다

$n_{\text{eff}} \le 1/\rho$라는 상한이 알려 주는 처방은 분명하다. **$n$을 키우지 말고 $\rho$를 낮춰라.** $\rho$를 낮춘다는 것은 표본들이 서로 다른 이유로 틀리게 만든다는 뜻이다. 방법은 결국 "가지들이 공유하는 조건을 서로 다르게 만드는 것"이다.

| 다양성 주입 방법 | $\rho$ 감소 효과 | 추가 비용 | 부작용 |
|---|---|---|---|
| 온도 상승 | 매우 작음 | 없음 | 개별 정확도 $p$가 떨어져 Condorcet 조건이 나빠짐 |
| 프롬프트 문구 변형(paraphrase) | 작음~중간 | 프롬프트 관리 비용 | 변형끼리 $p$가 달라 균등 가중이 부적절해짐 |
| 추론 전략 변형(직접 답 / CoT / 역산 검증) | 중간~큼 | 프롬프트 세트 관리 | 전략별 출력 형식이 달라 정규화가 어려워짐 |
| 컨텍스트 변형(다른 검색 결과·다른 근거 문서) | 큼 | 검색 비용 추가 | 근거가 다르면 정답도 달라질 수 있음(과업 정의가 흔들림) |
| 서로 다른 모델·서로 다른 프로바이더 | 가장 큼 | 통합·검증·계약 비용 | $p$ 격차, 가중치 결정 필요, 운영 복잡도 급증 |

표의 값은 측정치가 아니라 **정성적인 순위**다. 실제 크기는 과업과 모델에 따라 달라지므로, 각자의 파이프라인에서 6.1절의 간접 지표(오답 케이스에서 표본들이 일치하는 비율)로 재 봐야 한다. 그래도 순위 자체는 꽤 견고하다.

표의 첫 줄이 중요하다. **온도만으로 얻는 다양성은 가장 싸지만 가장 얕다.** 온도를 올리면 표본들이 서로 달라 보이지만, 달라지는 부분은 대개 표현이고 답을 결정하는 판단은 그대로인 경우가 많다. 게다가 온도를 올리면 $p$ 자체가 떨어져 Condorcet 조건이 나빠진다. $\rho$는 조금 내려가고 $p$는 확실히 내려가면, 순효과는 음수일 수 있다.

가장 효과가 큰 방법은 서로 다른 모델을 섞는 것이지만, 대가도 크다. 출력 형식 정규화, 프로바이더별 실패 모드, 비용 차이가 생기고, 무엇보다 **모델마다 $p$가 다르다.** 균등 가중 다수결은 $p$가 같다는 전제를 쓰므로, 실력 차이가 크면 강한 모델의 정답이 약한 모델 둘의 오답에 밀린다.

이 문제를 고치려면 검증 세트로 가중치를 재야 하는데, 검증 세트가 있다면 애초에 강한 모델만 쓰는 편이 나을 수 있다. 이런 순환 때문에 다중 모델 투표는 실무에서 생각만큼 널리 쓰이지 않는다.

```yaml
# 투표 설정을 코드가 아니라 설정으로 빼면, '왜 이 값인가'를 검증 결과와 함께 남길 수 있다.
voting:
  # 서로 다른 이유로 틀리게 만드는 것이 목적. 온도만 흔드는 구성은 여기 없다.
  strategies:
    - id: direct
      prompt: prompts/extract_direct.md
      temperature: 0.2
    - id: cot
      prompt: prompts/extract_cot.md          # 추론 경로를 쓰게 함
      temperature: 0.7
    - id: backward                            # 답을 가정하고 근거를 역으로 확인
      prompt: prompts/extract_backward.md
      temperature: 0.2
  samples_per_strategy: 2                     # 총 6표. 5.x 절 기준 대부분 여기가 무릎
  aggregate:
    normalize: amount_krw                     # 정규화기 지정 — 없으면 표가 갈린다
    min_agreement: 0.5
    min_margin: 0.15
    on_no_consensus: escalate_to_human        # 억지로 답을 만들지 않는다
  # 관측: 오답 케이스에서의 표본 일치율. 이 값이 높으면 표본 수를 늘려도 소용없다는 신호.
  observe:
    - metric: agreement_on_wrong_cases
      alert_above: 0.8
```

**다양성 주입이 작동하지 않는 경우**는 오류의 원인이 **컨텍스트에 있을 때**다. 검색이 잘못된 문서를 가져왔거나 시스템 프롬프트에 잘못된 도메인 규칙이 들어 있으면, 어떤 모델을 몇 개 섞든 모두 같은 결론을 낸다. 이 경우 $\rho \approx 1$이고 투표는 순수한 낭비다.

진단은 간단하다. **오답 케이스의 표본들이 같은 근거를 인용하고 있는지** 보면 된다. 같은 근거를 인용하면서 함께 틀렸다면, 고쳐야 할 것은 투표가 아니라 검색이다([[24 - RAG와 에이전틱 검색 — 검색을 행동으로]]).

## 7. best-of-n과 판정자: 선택 문제로 바꾸면 검증자의 품질이 상한이 된다

투표는 후보들이 서로를 지지하게 하는 방식이다. best-of-n은 다르다. **외부의 채점자가 후보 가운데 하나를 고른다.** 6.2절에서 본 커버리지와 정확도 사이의 간극을 메우는 유일한 방법이고, 그래서 이 접근이 test-time compute 논의의 중심에 있다([[20 - 추론 모델의 시대 — test-time compute가 바꾼 패턴 지형]]).

### 7.1 세 가지 선택 장치

| 장치 | 선택 근거 | 신뢰도 | 비용 | 적용 조건 |
|---|---|---|---|---|
| 다수결 | 후보들 간 합의 | 최빈답 정확도가 상한 | $n$ | 답이 이산·유일 |
| 결정론적 검증자 | 실행·검사 통과 여부 | 검증자가 완전하면 매우 높음 | $n \times$ 검사비 | 검사 가능한 산출(코드, 스키마, 수식) |
| LLM 판정자 | 루브릭 기반 평가 | 판정자 정확도가 상한 | $n$ + 판정 비용 | 나머지 전부 |

표의 순서가 곧 우선순위다. **결정론적 검증자가 있으면 그것을 쓴다.** 코드 생성이라면 컴파일과 테스트, 구조화 출력이라면 스키마 검증, SQL이라면 파싱과 EXPLAIN, 수치 계산이라면 역산 검증이 여기에 해당한다.

이 방법은 원리적으로 우월하다. 검증자가 확률적이지 않으므로 **상한이 검증자의 완전성에만 달려 있기** 때문이다. 자기검증의 이론적 한계와 외부 검증자의 우위는 [[19 - 검증 — 자기검증의 한계와 외부 검증자]]에서 본격적으로 다룬다.

> [!info] 역사 메모
> 생성기와 별도로 **검증자**(verifier)를 두고 여러 후보의 순위를 다시 매기는 접근은, Cobbe 등이 2021년 GSM8K 수학 문제 데이터셋을 소개한 연구에서 체계적으로 제시했다. 핵심 관측은 단순하다. 생성 능력과 판별 능력은 다르고, 판별이 더 쉽다.
>
> 이 비대칭이 best-of-n이 작동하는 근본적인 이유이면서, 뒤에서 다룰 실패 조건의 원인이기도 하다. 판별이 쉽다는 것은 **평균적으로** 쉽다는 뜻이지, 최적화 압력을 받는 극단에서도 쉽다는 뜻은 아니다.

### 7.2 판정자 편향: 무엇이 알려져 있는가

LLM 판정자에게 체계적인 편향이 있다는 것은 여러 연구에서 반복해서 관측되었다. 대표적인 것은 Zheng 등의 MT-Bench 연구(2023)가 정리한 편향들이다.

- **위치 편향**(position bias): 두 후보를 나란히 제시하면 특정 위치에 놓인 후보를 선호한다. 순서를 바꾸면 판정이 뒤집히는 비율을 무시할 수 없다.
- **장황함 편향**(verbosity bias): 더 긴 답을 더 좋게 평가하는 경향이다. 내용이 같아도 길면 이긴다.
- **자기 선호**(self-enhancement bias): 자기 자신(또는 같은 계열 모델)이 생성한 답을 선호하는 경향이다.

여기에 실무에서 관측되는 편향이 더 있다. 형식 편향(마크다운 표와 굵은 글씨가 있으면 좋아 보인다)과 자신감 편향(단정적인 문장이 조심스럽게 단서를 단 문장을 이긴다. 심지어 단서를 다는 편이 옳을 때도 그렇다)이 있다. 그리고 **판정자 자신이 생성기일 때의 순환**도 있다. 생성기와 판정자가 같은 모델이면, 생성기가 보지 못한 것은 판정자도 보지 못한다.

```python
# 판정자 편향 완화의 최소 세트.
#  (1) 위치 스왑으로 위치 편향 상쇄
#  (2) 길이 균형 — 후보를 길이대로 짝지어 비교하거나, 길이를 프롬프트에서 명시적으로 배제
#  (3) 판정자가 생성기와 다른 모델
#  (4) 결정론적 사전 필터를 먼저 통과시켜 판정 대상 자체를 줄인다
import itertools


async def judge_pairwise(a: str, b: str, judge_llm, rubric: str) -> float:
    """a 가 b 보다 낫다고 판정될 확률 추정. 위치를 바꿔 두 번 묻고 평균낸다."""
    async def ask(first: str, second: str) -> int:
        r = await judge_llm.classify(
            instruction=(
                f"{rubric}\n"
                # 길이 편향 억제: 명시적으로 배제해도 완전히 사라지지는 않는다.
                "길이·서식은 평가 대상이 아니다. 사실 정확성과 요구사항 충족만 본다.\n"
                "더 나은 쪽의 라벨만 출력: A 또는 B"
            ),
            input=f"[A]\n{first}\n\n[B]\n{second}",
            enum=["A", "B"],
        )
        return 1 if r == "A" else 0

    forward = await ask(a, b)          # a 가 앞
    backward = await ask(b, a)         # b 가 앞 → 이때 'B' 가 a
    # 두 판정이 일치하지 않으면 위치 편향에 지배된 것 = 사실상 무작위.
    return (forward + (1 - backward)) / 2


async def best_of_n(candidates: list[str], judge_llm, rubric: str,
                    deterministic_filter=lambda c: True) -> tuple[str, float]:
    # 결정론적 필터가 먼저다. 컴파일 안 되는 코드를 판정자에게 보여 줄 이유가 없다.
    pool = [c for c in candidates if deterministic_filter(c)]
    if not pool:
        raise ValueError("no candidate passed deterministic checks")
    if len(pool) == 1:
        return pool[0], 1.0

    # 전쌍 비교는 O(n^2). n 이 크면 스위스 토너먼트나 단일 제거로 줄인다.
    scores = {i: 0.0 for i in range(len(pool))}
    for i, j in itertools.combinations(range(len(pool)), 2):
        s = await judge_pairwise(pool[i], pool[j], judge_llm, rubric)
        scores[i] += s
        scores[j] += 1 - s
    best = max(scores, key=scores.__getitem__)
    # 승률 마진이 작으면 '고르지 못했다'고 보고해야 한다. 5.3절의 margin 과 같은 정신.
    margin = (scores[best] - sorted(scores.values())[-2]) / (len(pool) - 1)
    return pool[best], margin
```

**전쌍 비교에는 $O(n^2)$번의 판정 호출이 필요**하므로, $n$이 조금만 커져도 비용이 폭발한다. $n=8$이면 28쌍에 위치 스왑 2회를 곱해 56회다. 실무에서는 (a) 점수 매기기(pointwise scoring)로 $O(n)$까지 줄이거나, (b) 단일 제거 토너먼트로 비교 횟수를 $O(n)$으로 줄인다.

둘 다 대가가 있다. pointwise 방식은 절대 점수의 보정(calibration)이 나쁘고(같은 답에 매번 다른 점수를 준다), 토너먼트는 위치와 대진 운에 좌우된다.

### 7.3 판정자로 최적화하면 판정자의 오차를 최적화하게 된다

best-of-n의 가장 근본적인 실패 모드가 이것이다. 판정자 $J$가 참 품질 $Q$를 잡음 섞인 값으로 추정한다고 하자. 즉 $J = Q + \varepsilon$이다. 후보 $n$개 중 $J$가 가장 큰 것을 고르면, 고른 후보는 $Q$가 높은 것이 아니라 **$Q + \varepsilon$이 높은 것**이다.

$n$이 커질수록 극단값 통계에 따라 $\varepsilon$이 큰 후보가 선택될 확률이 커진다. 즉 다음과 같다.

$$
\mathbb{E}[Q \mid J \text{ 최대}] \;=\; \underbrace{\mathbb{E}[Q]+\text{선택 이득}}_{n \text{에 대해 증가}} \;-\; \underbrace{\text{잡음에 대한 과적합}}_{n \text{에 대해 증가}}
$$

두 항이 모두 $n$에 대해 증가하고, 결국 잡음 항이 이긴다. 그래서 **$n$을 늘리면 어느 지점부터 실제 품질이 다시 떨어진다.** 이 현상은 보상 모델 과최적화(reward model overoptimization)라는 이름으로 정리되어 있다.

Gao, Schulman, Hilton의 "Scaling Laws for Reward Model Overoptimization"(2022, ICML 2023)은 best-of-n과 강화학습 양쪽에서 KL 거리를 늘릴 때의 형태를 보고했다. 대리 보상은 계속 오르지만, 참 보상(더 큰 '골드' 보상 모델로 잰 값)은 정점을 지나 떨어졌다. 정확한 함수 형태나 계수는 설정에 따라 다르므로 여기서 숫자를 인용하지는 않겠다. 하지만 **정점이 존재한다는 정성적 사실은 여러 설정에서 재현되었다.**

실무로 옮겨 보면 이렇다. 판정자가 긴 답을 좋아하면, $n$을 늘릴수록 더 긴 답이 뽑힌다. 판정자가 마크다운 표를 좋아하면 표가 있는 답이 뽑힌다. 판정자가 단정적인 어조를 좋아하면 **틀렸지만 자신 있는 답**이 맞지만 조심스러운 답을 이긴다.

결제 도메인에서 이것은 그냥 위험하다. "이 거래는 정상 승인되었습니다"가 "PG 응답이 모호해 확인이 필요합니다"를 이기는 파이프라인은 오탐을 조용히 만들어 낸다.

> [!warning] 흔한 오해
> "판정자를 붙였으니 후보를 많이 만들수록 좋은 것을 고른다." 판정자의 신뢰도가 상한이고, $n$을 키우면 그 상한 **아래로** 내려간다. 선택은 판정자의 오차 방향으로 후보 분포를 밀어내는 최적화이기 때문이다. 처방은 세 가지다.
>
> (1) $n$을 작게 유지한다. 정점의 위치는 판정자 잡음의 크기에 달려 있어 보편적인 상수가 없다. 따라서 자기 판정자에 대해 $n$을 늘려 가며 사람 라벨과의 일치율이 꺾이는 지점을 찾아야 한다(그 측정을 아직 하지 않았다면 한 자릿수에서 시작하는 것이 업계 관행이다).
>
> (2) 결정론적 검증을 먼저 통과시켜 판정 대상을 줄인다. (3) 판정자를 주기적으로 사람 라벨과 대조해 편향의 드리프트를 잰다. 판정자도 회귀할 수 있는 컴포넌트이기 때문이다. 이 측정 방법은 38장(평가)에서 다룬다.

### 7.4 best-of-n이 작동하지 않는 경우

1. **판별이 생성만큼 어려운 과업.** best-of-n은 "판별이 생성보다 쉽다"는 전제에 기대는데, 이 전제가 성립하지 않는 영역이 있다. 사실 확인이 필요한 주장(판정자도 사실을 모른다), 긴 문서의 일관성(판정자가 다 읽지 못한다), 창의성이나 적합성 같은 주관적 기준이 그렇다. 이런 영역에서는 판정자가 사실상 무작위이고, best-of-n은 무작위 선택에 $n$배의 비용을 쓴 셈이 된다.
2. **후보들이 서로 너무 비슷할 때.** $\rho$가 높으면 후보의 다양성이 낮아 판정자가 고를 것이 없다. 여기서도 6.3절의 다양성 주입이 선결 조건이다.
3. **판정자와 생성기가 같은 모델, 같은 컨텍스트일 때.** 생성기가 놓친 것을 판정자가 볼 이유가 없다. 이것은 자기비평의 한계와 뿌리가 같은 문제이며, 생성자와 평가자를 분리하는 조건은 [[10 - 평가자-최적화기 — 생성과 비평의 순환]]에서 따로 다룬다.
4. **지연 예산이 빠듯할 때.** best-of-n에서는 $n$개를 병렬로 생성한 뒤 판정 단계가 **직렬로** 붙는다. 2.2절 식의 $\beta$가 커지는 것이다. 대화형 인터페이스에서는 이 추가 왕복 때문에 체감 품질이 오히려 떨어질 수 있다.

## 8. 동시성은 예산이 있는 자원이다: 팬아웃 폭발과 속도 제한

지금까지는 병렬화의 논리를 살펴봤다. 이제 그 논리를 실제 인프라 위에 올릴 때 무엇이 문제를 일으키는지 본다. 요약하면 한 가지다. **팬아웃은 곱해지지만, 자원은 그만큼 늘어나지 않는다.**

### 8.1 팬아웃 예산은 각 축이 아니라 곱에 건다

1.3절의 식을 다시 보자. 호출 수는 폭, 깊이, 렌즈를 곱한 값이다. 여기에 에이전트 루프가 더해지면 축이 하나 더 붙는다. 각 가지가 그 자체로 도구를 호출하는 루프라면, 가지당 호출 수가 다시 곱해진다([[04 - 에이전트 루프의 해부 — 관찰·결정·행동·정지]]). 그리고 오케스트레이터-워커 구조에서 워커가 다시 팬아웃하면 재귀적으로 곱해진다(9장 오케스트레이터-워커).

곱셈 구조에서 각 축에 따로 상한을 거는 방식은 실패한다. "가지는 최대 8개", "투표는 최대 5회", "루프는 최대 20턴"은 각각 합리적으로 보이지만, 곱하면 800회다. 예산은 **트리 전체에 대해 하나의 스칼라로** 걸고, 부모가 자식에게 나눠 주는 방식이어야 한다.

```yaml
# 팬아웃 예산: 축별 상한이 아니라 '요청 하나가 태울 수 있는 총량'을 건다.
# 축별 상한은 방어선이 아니라 위생 규칙으로만 둔다.
request_budget:
  total_llm_calls: 60          # 트리 전체. 부모가 자식에게 배분한다.
  total_input_tokens: 900_000
  total_output_tokens: 60_000
  wall_clock_ms: 45_000        # 전체 벽시계. 가지별 타임아웃은 여기서 파생된다.
  max_concurrency: 8           # 동시에 살아 있을 수 있는 호출 수 (속도 제한 보호)

  # 위생 규칙 — 이걸로 폭주를 막는 게 아니라 명백한 설계 실수를 잡는다.
  hygiene:
    max_fanout_width: 16
    max_votes: 5
    max_recursion_depth: 2     # 워커의 워커까지. 3부터는 대개 설계 실수다.

  # 예산 소진 시 동작. '조용히 잘라내기'가 최악이다.
  on_exhausted: return_partial_with_coverage
```

설계 결정 중 가장 중요한 것은 `on_exhausted`이다. 선택지는 세 가지이고, 어느 것이 맞는지는 도메인이 정한다.

- **부분 반환과 커버리지 표시**: 문서 분석이나 리서치처럼 부분 답도 유용한 경우다. 무엇이 빠졌는지를 반드시 값으로 전달한다.
- **실패**: 정산 검증처럼 부분 답이 위험한 경우다. 90%만 검증한 정산서는 검증하지 않은 정산서보다 나쁘다. 검증되었다는 착각을 주기 때문이다.
- **에스컬레이션**: 사람에게 넘긴다([[35 - 휴먼 인 더 루프 — 승인·개입·에스컬레이션]]).

> [!note] 실무 규칙
> 예산은 **요청 진입점에서 한 번 만들어 트리 전체에 전파**한다. 각 가지가 자기 예산을 새로 만들면, 예산이 아니라 축별 상한으로 전락한다. Kotlin이라면 `CoroutineContext` 원소로, Scala/ZIO라면 `FiberRef`로, Node라면 `AsyncLocalStorage`로 전달하는 것이 자연스럽다([[06 - CoroutineScope와 구조적 동시성]]).

### 8.2 429 폭주와 재시도 폭풍

속도 제한은 병렬화를 도입한 팀이 가장 먼저 부딪히는 벽이다. 그리고 순진하게 대응하면 상황이 더 나빠지는 대표적인 사례이기도 하다. 전형적인 사고는 다음 순서로 일어난다.

1. 팬아웃 16개를 동시에 보낸다.
2. 절반이 429를 받는다.
3. 클라이언트가 재시도한다.
4. 재시도가 같은 순간에 몰린다(동기화된 백오프).
5. 다시 429를 받는다.
6. 재시도 횟수를 모두 소진하고 실패한다.
7. 사용자가 새로고침한다. 이제 원래 부하의 두 배가 같은 상태의 시스템에 들어온다.

여기서 필요한 것은 모두 이미 알려진 기법이다([[31 - 분산 ID·속도 제한·조정 빌딩블록 (Distributed ID, Rate Limiting & Coordination)]], [[33 - 내결함성과 부하 관리 (Fault Tolerance & Load Management)]]).

- **클라이언트 측 동시성 상한.** 세마포어로 동시 호출 수를 프로바이더 한도 아래로 묶는다. 429를 받은 뒤에 줄이는 것보다 처음부터 한도를 넘기지 않는 것이 훨씬 싸다.
- **토큰 단위 회계.** 요청 수가 아니라 **토큰**으로 한도가 걸리는 경우가 많으므로, 세마포어의 단위도 토큰이어야 한다. 긴 입력 하나가 짧은 요청 열 개만큼의 한도를 소모한다.
- **지터를 넣은 지수 백오프.** 지터가 없으면 재시도가 동기화되어 폭주가 반복된다.
- **`Retry-After` 존중.** 프로바이더가 알려 주는 값이 있으면, 그 값이 우리의 추정보다 정확하다.
- **적응형 조절(AIMD).** 429가 나면 동시성을 곱셈으로 줄이고, 성공이 이어지면 덧셈으로 늘린다. TCP 혼잡 제어와 같은 구조다.
- **재시도 예산.** 전체 요청 중 재시도가 차지할 수 있는 비율에 상한을 둔다(예: 10%). 이것 하나로 재시도 폭풍을 구조적으로 막을 수 있다.

```kotlin
// 토큰 단위 세마포어 + AIMD 적응형 동시성.
// 요점: 429 를 '오류'가 아니라 '부하 신호'로 다룬다.
class AdaptiveLlmGate(
    initialPermits: Int = 8,
    private val minPermits: Int = 1,
    private val maxPermits: Int = 32,
) {
    private val mutex = Mutex()
    private var permits = initialPermits
    private var available = initialPermits
    private val waiters = ArrayDeque<CancellableContinuation<Unit>>()

    /** 예상 토큰 수만큼 슬롯을 잡는다. 긴 입력은 더 많은 슬롯을 먹어야 공평하다. */
    suspend fun <T> withSlot(estimatedTokens: Int, block: suspend () -> T): T {
        val cost = (estimatedTokens / 4_000).coerceIn(1, 4)
        acquire(cost)
        try {
            val r = block()
            onSuccess()          // 성공이 이어지면 천천히 늘린다 (additive increase)
            return r
        } catch (e: RateLimited) {
            onRateLimited()      // 429 는 즉시 곱셈 감소 (multiplicative decrease)
            throw e
        } finally {
            release(cost)
        }
    }

    private suspend fun onRateLimited() = mutex.withLock {
        // 여기서 절반으로 줄이는 것이 핵심. 선형으로 줄이면 폭주를 못 따라잡는다.
        permits = (permits / 2).coerceAtLeast(minPermits)
    }

    private suspend fun onSuccess() = mutex.withLock {
        // 성공 하나에 1씩 늘리면 너무 공격적이라, 확률적으로 늘린다.
        if (permits < maxPermits && Random.nextDouble() < 0.05) permits += 1
    }
    // acquire/release/waiters 처리는 생략 — 표준 카운팅 세마포어와 동일
}
```

**이 처방이 작동하지 않는 경우**는 프로세스가 여러 개일 때다. 클라이언트 측 세마포어는 **프로세스 로컬**이므로, 파드가 20개이고 각각 8개씩 잡으면 전체 동시성은 160이 된다. 이 경우에는 분산 속도 제한기(중앙 토큰 버킷)나 게이트웨이 계층의 조절이 필요한데, 그 자체가 추가 지연과 단일 장애점을 만든다.

실무에서는 **파드 수로 나눈 로컬 한도와 서버 429에 대한 AIMD를 조합**하는 것으로 타협한다. 정확하지는 않지만 대체로 잘 작동한다.

### 8.3 부분 실패: 정족수, 타임아웃, 그리고 커버리지

1.1절에서 본 비대칭을 정책으로 만든다. 부분 실패를 올바르게 처리하는 방법은 형태마다 다르다.

| 형태 | 부분 실패 정책 | 실패로 볼 임계 | 결과에 실어야 할 것 |
|---|---|---|---|
| 섹셔닝 | 실패 조각만 재시도 → 그래도 실패하면 **커버리지 표시** | 도메인이 정함(정산은 0%, 리서치는 20%) | 누락 조각 id 목록 |
| 투표 | 성공한 표만으로 집계 | $n_{\text{valid}} < 3$ 이면 합의 판정 불가 | 유효 표본 수, 합의도 |
| 팬아웃 | 필수 렌즈/선택 렌즈 구분 | 필수 렌즈 하나라도 실패 | 실패한 렌즈 목록 |

```
scatter-gather 타임라인 (섹셔닝, n=6, soft/hard 타임아웃)

t=0   ├─ s1 ────────────────►✓
      ├─ s2 ──────►✓
      ├─ s3 ─────────────────────────────────────►✓   (스트래글러)
      ├─ s4 ──────────►✗ 429
      ├─ s5 ────────────►✓
      └─ s6 ─────────────────────────────────────────────── (응답 없음)
                                    │                │
                          soft deadline        hard deadline
                          (여기서 s4 재시도 포기)   (여기서 s6 포기, s3 는 아슬하게 성공)

결과: ok=[s1,s2,s3,s5]  missing=[s4,s6]  coverage=4/6=0.67
      → 병합은 4개로 하되, coverage 를 결과에 실어 호출자가 판단하게 한다.
      → 여기서 coverage 를 버리면 "지불 조건 7건" 이 전부인 줄 알게 된다.
```

데드라인을 두 개 두는 것이 요령이다. **소프트 데드라인**에서는 재시도를 중단하고(더 시도해 봐야 하드 데드라인 안에 끝나지 않는다), **하드 데드라인**에서는 남은 가지를 취소한다. 취소가 실제로 전파되는지는 반드시 확인해야 한다. 취소된 코루틴이 HTTP 연결을 닫지 않으면 토큰이 계속 소모된다.

```scala
// ZIO 로 표현한 섹셔닝 + 정족수 + 커버리지.
// 요점: 실패를 예외로 날리지 않고 '결과의 일부'로 만든다.
final case class Coverage(total: Int, ok: Int, missing: List[SectionId]) {
  def ratio: Double = ok.toDouble / total
}

def runSections[A](
  sections: List[Section],
  process: Section => ZIO[Any, Throwable, A],
  perSectionTimeout: Duration,
  concurrency: Int,
  minCoverage: Double,           // 도메인이 정한다. 정산 검증이면 1.0.
): ZIO[Any, InsufficientCoverage, (List[(SectionId, A)], Coverage)] =
  for {
    // foreachPar + withParallelism: 동시성 상한이 코드에 드러나야 한다.
    settled <- ZIO.foreachPar(sections) { s =>
                 process(s)
                   .timeoutFail(new TimeoutException(s.id.value))(perSectionTimeout)
                   .either                       // 실패를 값으로. 여기서 던지면 전체가 죽는다.
                   .map(s.id -> _)
               }.withParallelism(concurrency)
    oks      = settled.collect { case (id, Right(a)) => id -> a }
    missing  = settled.collect { case (id, Left(_)) => id }
    cov      = Coverage(sections.size, oks.size, missing)
    // 커버리지 게이트: 병합 '전에' 판정한다. 병합 후에는 무엇이 빠졌는지 안 보인다.
    _       <- ZIO.fail(InsufficientCoverage(cov))
                 .when(cov.ratio < minCoverage)
  } yield (oks, cov)
```

**부분 결과 병합이 작동하지 않는 경우**는 산출물이 **전수**(exhaustive)를 전제로 한 **주장**일 때다. "이 계약서에 독소 조항은 없습니다"는 전체를 다 읽었을 때만 할 수 있는 말이다. 커버리지가 0.9인데 "없습니다"라고 답하면 거짓말이 된다.

이런 과업에서는 커버리지 임계를 1.0으로 두고, 임계에 못 미치면 부분 결과를 **반환하되 주장의 양태를 바꿔야** 한다. 예를 들어 "검토한 범위에서는 발견되지 않았습니다(미검토 구간 2개)"라고 말하는 식이다. 이 문장 변환은 LLM 병합기에게 맡기지 말고 코드로 강제하는 편이 안전하다.

## 9. 가드레일 병렬화: 지연을 숨기지만 스트리밍과 충돌한다

병렬화의 용도 가운데 앞의 세 가지와 성격이 다른 것이 하나 있다. **검사를 본 작업과 동시에 실행해 검사의 지연을 숨기는 것**이다. 입력 안전성 검사, 정책 위반 탐지, PII 스캔, 프롬프트 인젝션 탐지는 모두 본 응답 생성과 논리적으로 독립이므로 동시에 실행할 수 있다.

```
직렬 (지연 = 가드 + 본작업 + 출력가드)
  ├─ input guard ──►├─ main ──────────────────►├─ output guard ──► 응답
                                                                   t = 3구간

병렬 (지연 = max(가드, 본작업) + 출력가드)
  ├─ input guard ──►│
  ├─ main ──────────────────────────►│
                                      ├─ output guard ──► 응답
                                                          t ≈ 2구간
  단, input guard 가 거부하면 main 의 결과를 버린다 (비용은 이미 지불)
```

이득은 지연이고, 대가는 비용이다. 입력 가드가 거부하면 본 작업에 쓴 토큰은 낭비된다. 낭비의 기댓값은 $p_{\text{block}} \times C_{\text{main}}$이므로, 이 교환은 **차단율이 낮을 때만** 성립한다. 차단율이 1% 수준이면 거의 공짜지만, 적대적 트래픽이 몰리는 엔드포인트에서 차단율이 30%가 되면 비용이 크게 늘어난다.

그래서 이 패턴에는 **차단율에 따라 병렬과 직렬을 전환하는 스위치**를 두는 것이 합리적이다.

```kotlin
// 가드레일 병렬화. 구조적 동시성으로 '실패 시 반드시 취소'를 보장한다.
suspend fun answerWithGuards(req: Request, cfg: GuardConfig): Reply = coroutineScope {
    // 입력 가드와 본작업을 동시에 시작. 가드가 거부하면 본작업을 취소한다.
    val guard = async { inputGuard.check(req) }          // 값싼 소형 모델 또는 규칙
    val main = async { mainModel.generate(req) }

    val verdict = guard.await()
    if (verdict.blocked) {
        main.cancel()                                     // 토큰 낭비를 즉시 멈춘다
        return@coroutineScope Reply.blocked(verdict.reason)
    }

    val draft = try {
        main.await()
    } catch (e: Exception) {
        // 가드는 통과했는데 본작업이 실패. 가드 비용은 이미 지불했다.
        throw e
    }

    // 출력 가드는 본작업 결과에 의존하므로 병렬화 불가. 이 직렬 구간은 남는다.
    // 여기서 fail-open/fail-closed 를 정해야 한다.
    val outVerdict = withTimeoutOrNull(cfg.outputGuardTimeoutMs) {
        outputGuard.check(draft)
    } ?: if (cfg.failClosed) Verdict.blocked("output guard timeout")
        else Verdict.allowed(degraded = true)             // 관측 가능한 형태로 열어 준다

    if (outVerdict.blocked) Reply.blocked(outVerdict.reason) else Reply.ok(draft)
}
```

이 코드에서 가장 중요한 줄은 `failClosed` 분기다. 출력 가드가 타임아웃되었을 때 **막을지 통과시킬지**는 순수하게 도메인이 결정할 문제이고, 기본값을 잘못 정하면 조용한 사고가 난다. 금융, 의료, 미성년자 대상 서비스라면 fail-closed가 기본이고, 내부 도구라면 fail-open이 합리적일 수 있다.

어느 쪽이든 `degraded = true`처럼 **관측할 수 있는 흔적**을 남겨야 한다. 정책 집행 설계는 [[36 - 가드레일과 권한 — 정책 집행·최소 권한·샌드박스]]에서 자세히 다룬다.

**가드레일 병렬화가 작동하지 않는 경우**는 세 가지다.

1. **스트리밍과 충돌할 때.** 사용자에게 토큰을 흘려보내면서 출력 가드를 실행하면, 가드가 거부를 결정하는 시점에 이미 일부가 화면에 나가 있다. 되돌릴 수 없다. 처방은 (a) 스트리밍을 포기하거나, (b) 청크 단위로 가드를 실행하면서 지연 버퍼를 두거나(문장 하나만큼 늦게 내보낸다), (c) 위험 구간에서만 버퍼링하는 하이브리드 방식이다. 어느 쪽도 공짜가 아니다. (b)는 문맥이 잘린 조각에 대해 가드를 실행하는 것이라 탐지율이 떨어진다.
2. **가드가 본 작업의 출력에 의존할 때.** 병렬화할 수 있는 것은 입력 가드뿐이다. 출력 가드는 본질적으로 직렬이며, 이 직렬 구간은 어떤 병렬화로도 없앨 수 없다.
3. **차단율이 높을 때.** 위에서 본 비용 계산 때문이다.

> [!warning] 흔한 오해
> "가드를 병렬로 실행하면 안전성 검사가 공짜가 된다." 지연이 숨겨질 뿐 비용은 그대로이고, 차단된 요청에서는 본 작업의 비용이 **추가로** 낭비된다. 게다가 병렬화는 가드의 **품질**에 아무 영향을 주지 않는다. 값싼 가드 모델의 탐지율이 낮다면, 병렬로 실행하든 직렬로 실행하든 똑같이 낮다. 병렬화는 지연 문제의 해법이지 안전성 문제의 해법이 아니다.

## 10. 부작용이 있는 도구를 병렬로 호출하려면 멱등성이 먼저다

지금까지는 가지들이 순수하다고 가정했다. 이 가정을 깨면 병렬화는 성능의 문제에서 **정합성의 문제**로 바뀐다.

### 10.1 한 턴에 나온 여러 도구 호출은 독립이 아닐 수 있다

최근 모델은 한 번의 응답에서 여러 도구 호출을 동시에 낼 수 있다([[12 - 도구 사용 I — 함수 호출의 메커니즘과 계약]]). 런타임은 보통 이 호출들을 병렬로 실행한다. 여기에는 조용한 가정이 하나 들어 있다. **모델이 동시에 낸 호출들은 서로 독립이라는 가정이다.** 모델은 이 계약을 알지 못하고, 실제로 의존 관계가 있는 호출을 동시에 내기도 한다.

```
모델이 한 턴에 낸 호출:
  [1] search_payments(merchant="acme", status="failed")
  [2] refund_payment(payment_id="pay_...")     ← [1] 의 결과에 의존해야 할 것

런타임이 병렬 실행하면 [2] 는 [1] 의 결과 없이 실행된다.
모델은 payment_id 를 어디서 얻었나? 앞선 컨텍스트 또는 환각.
```

방어는 런타임 쪽에서 해야 한다.

- **부작용이 있는 도구는 병렬 배치에서 분리한다.** 도구 정의에 `sideEffect: true` 같은 표시를 두고, 배치에 그런 도구가 하나라도 있으면 순차 실행으로 바꾼다. 대부분의 과업에서는 읽기 도구가 다수이므로 손해가 크지 않다.
- **인자의 출처를 검증한다.** 부작용 도구의 식별자 인자가 이번 세션에서 실제로 관측된 값인지 대조한다. 결제 도메인이라면 `payment_id`가 앞선 조회 결과에 등장한 적이 있는지 확인하는 것만으로도 환각으로 인한 환불을 상당수 막을 수 있다.
- **쓰기 도구는 동시에 실행하지 않는다.** 같은 자원에 대한 쓰기는 순차적으로 처리한다. 액터 모델이 메일박스로 하는 일과 같다([[16 - 동시성과 순차성 - single-writer와 메일박스]]).

### 10.2 멱등키는 선택이 아니라 전제다

병렬화에는 재시도, 헤지, 타임아웃 후 재실행이 필연적으로 따라온다. 세 가지 모두 **같은 부작용이 두 번 일어날 수 있는 경로**다. 결제 도메인에서는 이중 결제, 티켓팅에서는 이중 예약, 문서 처리에서는 중복 발송이 된다.

```kotlin
// 병렬 도구 실행의 최소 안전장치.
// 멱등키를 '호출자'가 아니라 '계획'에서 결정론적으로 유도하는 것이 핵심.
data class ToolCall(
    val id: String,            // 모델이 부여한 호출 id
    val name: String,
    val args: JsonObject,
)

fun idempotencyKey(runId: String, call: ToolCall): String =
    // runId + 도구명 + 정규화된 인자의 해시.
    // 왜 call.id 를 안 쓰는가: 재시도로 모델이 다시 생성하면 id 가 바뀐다.
    // 왜 runId 를 넣는가: 서로 다른 요청의 같은 인자는 서로 다른 부작용이어야 한다.
    sha256("$runId|${call.name}|${canonicalJson(call.args)}")

suspend fun executeBatch(runId: String, calls: List<ToolCall>, reg: ToolRegistry): List<ToolResult> {
    val (effectful, pure) = calls.partition { reg.spec(it.name).hasSideEffect }

    // 순수 도구만 병렬. 여기서 실패는 재시도해도 안전하다.
    val pureResults = coroutineScope {
        pure.map { c -> async { runCatching { reg.invoke(c) } } }.awaitAll()
    }

    // 부작용 도구는 순차 + 멱등키. 순차인 이유는 성능이 아니라 인과성 때문이다.
    val effectResults = effectful.map { c ->
        val key = idempotencyKey(runId, c)
        runCatching { reg.invokeIdempotent(c, key) }   // 서버가 key 로 중복을 흡수
    }

    return (pure.zip(pureResults) + effectful.zip(effectResults)).map { (c, r) -> toResult(c, r) }
}
```

요령은 멱등키를 **계획에서 결정론적으로 유도**하는 것이다. 모델이 만든 호출 id를 쓰면 재시도할 때 키가 바뀌어 중복 방지가 무력해진다. 인자를 정규화한 해시를 쓰면 "같은 의도의 같은 호출"이 같은 키를 갖는다.

이 설계는 사가와 outbox의 멱등성 논의와 정확히 같은 문제다([[26 - 사가와 분산 정합성 (Sagas & Distributed Consistency) - 보상·outbox·멱등성]]). 에이전트 맥락에서의 자세한 내용은 [[34 - 내구성 있는 실행 — 상태·체크포인트·재시도·멱등성]]에서 다룬다.

### 10.3 취소가 만드는 고아 부작용

병렬화에는 취소가 따라온다. 하드 데드라인에서 남은 가지를 중단하고, 헤지에서 진 쪽을 중단하고, 가드가 거부하면 본 작업을 중단한다. 이때 **취소된 가지가 이미 부작용을 일으켰다면**, 그 부작용은 아무도 모르는 채로 남는다.

이것은 이론적인 걱정이 아니다. 결제 시스템에서 실제로 반복되는 패턴이 있다. 내부 타임아웃이 외부 시스템의 타임아웃보다 짧으면, 우리는 실패로 처리하는데 상대는 성공으로 처리한다. 코루틴 취소로 HTTP 요청을 끊었는데 서버는 이미 승인을 진행한 경우가 대표적이다. 병렬화는 타임아웃을 더 자주, 더 짧게 쓰게 만들므로 이 문제를 **증폭**한다.

처방은 세 가지다.

1. 부작용 도구는 취소 대상에서 제외한다(하드 데드라인이 와도 진행 중인 결제 호출은 끝까지 기다린다).
2. 취소할 때 **보상 트랜잭션**을 예약한다.
3. 최소한 취소된 부작용 호출을 **미확정 상태로 기록**해 두고, 나중에 조회해서 확정한다.

셋 중 (3)이 가장 실용적이다. 그러려면 취소 경로에 로깅이 있어야 한다. `finally` 블록에서 취소를 감지해 기록하는 코드가 없으면, 이 사건은 로그에 흔적조차 남지 않는다([[39 - 관측성 — 트레이싱·로깅·리플레이·디버깅]]).

> [!warning] 흔한 오해
> "도구 호출을 병렬로 실행하는 것은 순수한 성능 최적화다." 부작용이 하나라도 있으면 그것은 성능 최적화가 아니라 **동시성 프로그램**이고, 동시성 프로그램의 정확성 조건(멱등성, 순서, 원자성)을 모두 만족해야 한다.
>
> 읽기 전용 도구만 병렬화하고 쓰기는 순차로 두면, 손해는 거의 없으면서 이 문제 전체를 없앨 수 있다. 병렬 쓰기의 이득이 실제로 필요한 경우는 생각보다 드물다.

## 11. 결정 절차: 언제 무엇을 쓰고, 언제 병렬화하지 않는가

지금까지의 논의를 판단 절차로 정리한다. 이 절은 요약이 아니라 **적용하는 순서**다.

### 11.1 먼저 물어야 할 다섯 가지 질문

1. **얻으려는 것이 지연인가, 정확도인가, 커버리지인가?** 지연이라면 섹셔닝, 정확도라면 투표나 best-of-n, 커버리지라면 팬아웃을 쓴다. 세 가지를 한꺼번에 얻으려 하면 곱이 폭발한다.
2. **한도까지 여유가 있는가?** 여유가 없으면 병렬화는 지연을 개선하지 못한다(2.4절). 캐싱과 모델 라우팅이 먼저다.
3. **조각들이 내용과 결정 양쪽에서 정말 독립인가?** 결정 의존이 있다면 공유 컨텍스트로 내용 의존으로 낮출 수 있는지 본다(3.3절). 그럴 수 없다면 섹셔닝을 쓰지 않는다.
4. **병합을 코드로 작성할 수 있는가?** 작성할 수 있다면 코드로 작성한다. 작성할 수 없다면 그 이유를 정확히 적어 두고, 그 부분만 LLM에게 맡긴다(4.3절).
5. **부작용이 있는가?** 있다면 멱등키와 순차 쓰기가 선행 조건이다(10절).

### 11.2 실패 모드와 처방 대응표

| 실패 모드 | 관측되는 증상 | 근본 원인 | 처방 |
|---|---|---|---|
| 조용한 부분 실패 | 산출물은 그럴듯한데 항목이 빈다 | 커버리지가 값으로 전달되지 않음 | 결과 타입에 커버리지 필드 강제, 게이트를 병합 전에 |
| 용어 드리프트 | 병합 후 동의어 클러스터 폭증 | 조각 간 결정 의존 | 공유 어휘 사전 고정, 병합 시 정규화 패스 |

| 429 폭주 | 팬아웃 확대 직후 오류율 급등 | 클라이언트 동시성 무제한 | 토큰 단위 세마포어 + AIMD + 재시도 예산 |
| 꼬리 지연 악화 | 평균은 좋은데 p99가 나빠짐 | $\max$의 분위수 미고려 | 헤지 요청, 소프트/하드 데드라인, 폭 축소 |

### 11.3 병렬화하지 않는 것이 정답인 경우

패턴 전체에 대해 "쓰지 말아야 할 때"를 분명히 적어 둔다.

- **과업이 본질적으로 순차적일 때.** 각 단계가 앞 단계의 결정을 필요로 한다면, 병렬화는 표현할 수 없는 것을 표현하려는 시도다. 억지로 나누면 3.2절의 위반이 모두 나타난다.
- **트래픽이 적고 지연이 문제가 되지 않을 때.** 병렬화는 코드 복잡도, 관측 복잡도, 실패 모드를 모두 늘린다. 하루 수백 건을 처리하는 배치 파이프라인에서 지연 30초와 5초의 차이는 대개 아무 의미가 없다.
- **정확도 문제를 병렬화로 덮으려 할 때.** 투표는 분산을 줄이지 편향을 줄이지 않는다(5.4절). 프롬프트가 모호하거나 컨텍스트가 잘못되었다면, 그것을 고치는 편이 $n$배 싸다. **투표는 최후의 수단이지 첫 번째 시도가 아니다.**
- **재현성이 요구되는 경로.** 감사 대상 산출물이나 회귀 테스트의 골든 세트가 여기에 해당한다. 병렬화는 도착 순서, 부분 실패, 병합의 비결합성을 통해 비결정성을 들여온다. 이것을 모두 막을 수는 있지만(정렬, 커버리지 게이트, 코드 병합), 그만한 노력을 들일 가치가 있는지 먼저 따져야 한다.
- **관측 인프라가 없을 때.** 병렬 실행의 트레이스는 서로 뒤섞여 있어서, 가지별 span과 안정적인 branch id가 없으면 디버깅이 사실상 불가능하다. 병렬화를 켜기 전에 트레이싱을 먼저 켜는 것이 올바른 순서다.

### 11.4 관측성에 대한 최소 요구사항

병렬화를 운영하려면 트레이스에 다음 항목이 있어야 한다. 전반적인 설계는 39장(관측성)에서 다루므로, 여기서는 병렬화에 고유한 요구사항만 짚어 둔다.

- **가지마다 안정적인 id**(`section_id`, `vote_index`, `lens_id`). 재실행할 때 같은 가지가 같은 id를 가져야 두 실행을 비교할 수 있다.
- **팬아웃 전체의 지연**과 **가지별 지연 분포**를 따로 기록한다. 전자만 있으면 스트래글러를 찾지 못하고, 후자만 있으면 2.3절의 $\max$ 문제를 보지 못한다.
- **커버리지 메트릭**. 성공한 가지 수를 시도한 가지 수로 나눈 값이다. 이 값이 조용히 떨어지는 것이 병렬 파이프라인에서 가장 흔한 품질 회귀다.
- **합의도 분포**(투표를 쓴다면). 합의도가 낮은 케이스가 늘어난다면 모델, 프롬프트, 데이터 중 어딘가가 바뀌었다는 신호다.
- **재시도와 헤지의 비율**. 이 값이 예산을 넘으면 폭주 직전이다.

```bash
# 배포 직후 병렬 파이프라인의 건강 확인. 순서가 중요하다 —
# 커버리지 → 꼬리 지연 → 429 → 합의도. 앞의 것이 나쁘면 뒤는 볼 필요가 없다.

# 1) 커버리지: 조용한 부분 실패를 가장 먼저 잡는다
otel-query 'avg(section_coverage) by (pipeline) over 30m' --alert-below 0.98

# 2) 팬아웃 전체 지연 vs 가지 지연: 스트래글러가 지배하는지 본다
otel-query 'p99(fanout_total_ms) / p99(branch_ms) by (pipeline)' --alert-above 2.5

# 3) 속도 제한: 429 비율과 재시도 비율을 함께 본다 (재시도 폭풍 조기 탐지)
otel-query 'rate(llm_429_total) / rate(llm_calls_total) over 10m' --alert-above 0.02
otel-query 'rate(llm_retry_total) / rate(llm_calls_total) over 10m' --alert-above 0.10

# 4) 합의도: 투표 파이프라인의 품질 프록시
otel-query 'histogram(vote_agreement) by (task_type) over 1h'
```
